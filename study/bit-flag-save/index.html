비트 플래그 저장 패턴 - 인벤토리를 효율적으로 저장하는 법

Part 1. 인벤토리 저장 문제

인벤토리 저장할 때 뭐가 문제야?

인벤토리 슬롯이 몇 개야?

200칸? 300칸?

맞아. 근데 한 번에 다 저장하면 데이터가 너무 커.

[인벤토리 데이터 크기] 한 슬롯 = 아이템 코드(4) + 수량(4) + 강화(4) + 옵션(20) + ... ≈ 80바이트 300슬롯 = 80 × 300 = 24,000바이트 = 24KB SQL Server 컬럼 최대 크기: 8000바이트 → 한 컬럼에 못 담음!
그래서 어떻게 해?

청크(Chunk)로 나눠서 저장해.

[청크 분할] 전체 인벤토리 (300슬롯) ├── Chunk 0: 슬롯 0~49 (binary 4000) ├── Chunk 1: 슬롯 50~99 (binary 4000) ├── Chunk 2: 슬롯 100~149 (binary 4000) ├── Chunk 3: 슬롯 150~199 (binary 4000) ├── Chunk 4: 슬롯 200~249 (binary 4000) └── Chunk 5: 슬롯 250~299 (binary 4000)

Part 2. 청크로 나눴는데...

그럼 저장할 때 6개 청크 다 저장해?

그러면 낭비야.

유저가 1번 슬롯 아이템만 사용했는데 6개 청크 다 저장할 필요 있어?

[시나리오: 유저가 1번 슬롯의 포션 사용] 변경된 곳: Chunk 0 (슬롯 0~49) 중 1번 슬롯 변경 안 된 곳: Chunk 1, 2, 3, 4, 5 전체 저장: 24KB 전송 + 6번 UPDATE 필요한 저장: 4KB 전송 + 1번 UPDATE → 6배 낭비!
어떤 청크가 변경됐는지 어떻게 알아?

비트 플래그!

Part 3. 비트 플래그가 뭐야?

비트 플래그?

숫자 하나로 여러 개의 ON/OFF 상태를 표현하는 방법이야.

[비트 플래그 기초] 1바이트(TINYINT) = 8비트 = 8개의 ON/OFF 표현 가능 비트 위치: 7 6 5 4 3 2 1 0 값: 0 0 1 0 0 1 0 1 = 37 (십진수) 의미: - 비트 0 (값 1): Chunk 0 변경됨 ✓ - 비트 1 (값 2): Chunk 1 변경 안 됨 - 비트 2 (값 4): Chunk 2 변경됨 ✓ - 비트 5 (값 32): Chunk 5 변경됨 ✓ 37 = 1 + 4 + 32 = Chunk 0, 2, 5가 변경됨

비트 연산 기초:

연산 기호 설명 예시
AND & 특정 비트 확인 37 & 4 = 4 (비트2 ON)
OR | 비트 설정 37 | 8 = 45 (비트3 추가)
Left Shift << 비트 이동 1 << 3 = 8 (비트3 마스크)

Part 4. SQL에서 비트 플래그 사용

프로시저에서 어떻게 써?

파라미터로 비트 플래그를 받아서 조건 체크해.

CREATE PROCEDURE gp_save_inventory @charunique BIGINT, @bySaveBits TINYINT, -- 비트 플래그! @Inventory0 BINARY(4000), @Inventory1 BINARY(4000), @Inventory2 BINARY(4000), ... AS BEGIN -- Chunk 0이 변경됐으면 (비트 0 체크) IF (@bySaveBits & 1) > 0 UPDATE TInventory SET data0 = @Inventory0 WHERE ... -- Chunk 1이 변경됐으면 (비트 1 체크) IF (@bySaveBits & 2) > 0 UPDATE TInventory SET data1 = @Inventory1 WHERE ... -- Chunk 2가 변경됐으면 (비트 2 체크) IF (@bySaveBits & 4) > 0 UPDATE TInventory SET data2 = @Inventory2 WHERE ... END

@bySaveBits & N: N번 비트가 1인지 확인

결과가 0보다 크면 해당 청크 저장!

Part 5. 우리 프로젝트 실제 코드

실제 코드 - gp_save_pc_inventory

ALTER PROCEDURE gp_save_pc_inventory @pc_uid BIGINT, @bySaveBits TINYINT, @Inventory1 BINARY(8000), @Inventory2 BINARY(8000), ... AS BEGIN SET NOCOUNT ON; SET XACT_ABORT ON; BEGIN TRAN -- 변경된 청크만 SELECT해서 UPDATE UPDATE TInventory SET chunk_id = src.chunk_id, data = src.data FROM TInventory t INNER JOIN ( SELECT 0 AS chunk_id, @Inventory1 AS data WHERE (@bySaveBits & 1) > 0 UNION ALL SELECT 1, @Inventory2 WHERE (@bySaveBits & 2) > 0 UNION ALL SELECT 2, @Inventory3 WHERE (@bySaveBits & 4) > 0 ... ) src ON t.chunk_id = src.chunk_id WHERE t.charunique = @pc_uid COMMIT TRAN END

이 코드의 특징:

• UNION ALL로 변경된 청크만 선택

• 한 번의 UPDATE로 여러 청크 처리

• 비트 플래그로 불필요한 데이터 전송 방지

Part 6. 게임 서버에서는?

C++에서는 어떻게 비트 플래그를 만들어?

인벤토리 변경될 때마다 해당 청크의 비트를 켜.

// C++ 게임 서버 코드 (개념) // 인벤토리 변경 시 void OnInventoryChanged(int slotIndex) { int chunkIndex = slotIndex / SLOTS_PER_CHUNK; // 50 m_byDirtyBits |= (1 << chunkIndex); // 해당 비트 ON } // 저장 시 void SaveInventory() { if (m_byDirtyBits == 0) return; // 변경 없으면 스킵 // m_byDirtyBits와 변경된 청크 데이터만 전송 DBCall_SaveInventory(m_byDirtyBits, ...); m_byDirtyBits = 0; // 저장 후 초기화 }

Part 7. 얼마나 효과가 있어?

인벤토리 저장 최적화 효과

전체 저장
48KB
비트 플래그 (평균)
~8KB

실제 시나리오별 효과:

상황 변경 청크 비트값 절약률
포션 1개 사용 1개 1 (0x01) 83%
장비 교체 2개 3 (0x03) 67%
대량 아이템 획득 6개 63 (0x3F) 0%

핵심 정리

  • 청크 분할: 큰 데이터를 여러 조각으로 나눠 저장
  • 비트 플래그: 1바이트로 8개의 ON/OFF 상태 표현
  • @bySaveBits & N: N번 비트가 켜져있는지 확인
  • 우리 프로젝트: gp_save_pc_inventory에서 이 패턴 사용
  • 효과: 평균 60~80% 데이터 전송량 감소
  • 활용: 인벤토리, 스킬, 퀘스트 등 대용량 binary 데이터
