컴파일러: MSVC vs GCC vs Clang

같은 소스코드를 넣었는데, 왜 컴파일러마다 다른 결과가 나올까?

Compiler = 번역기

Compile = 모으다, 편집하다 (라틴어 compilare)

Compiler = 소스코드(사람의 언어)를 기계어(CPU의 언어)로 번역하는 프로그램

같은 C++ 소스도 MSVC, GCC, Clang 세 컴파일러가 만드는 기계어는 다르다. 최적화 방식, 표준 해석, 확장 기능이 모두 다르기 때문.

Part 1. 컴파일러가 뭐야? — 소스코드 → 기계어 번역기

컴파일러가 뭐야?

프로그래머가 쓴 소스코드(.cpp)를 CPU가 실행할 수 있는 기계어(.exe, .o)로 변환하는 프로그램이다.

쉽게 말하면 사람 언어 → CPU 언어 통역사다.

인터프리터랑 뭐가 달라?

컴파일러는 전체를 한 번에 번역한다 (C++, Rust). 인터프리터는 한 줄씩 번역하면서 실행한다 (Python, JavaScript).

컴파일러가 더 빠른 실행파일을 만든다. 미리 전부 번역해두니까 실행 시점에 번역 비용이 없기 때문.

소스코드 (.cpp) | v [ 컴파일러 ] ← MSVC / GCC / Clang 중 하나 | v 실행파일 (.exe) 또는 오브젝트 파일 (.o / .obj)

Part 2. 컴파일 과정 — 전처리 → 컴파일 → 어셈블 → 링크

컴파일이 한 단계로 끝나?

아니, 4단계를 거친다.

main.cpp | | (1) 전처리 (Preprocessing) | #include, #define 처리 v main.i | | (2) 컴파일 (Compilation) | C++ → 어셈블리어 v main.s | | (3) 어셈블 (Assembly) | 어셈블리 → 기계어 v main.o / main.obj | | (4) 링크 (Linking) | .o 파일들 + 라이브러리 결합 v main.exe (실행파일)
각 단계에서 에러가 나면?

전처리 에러 — #include 경로를 못 찾음, 매크로 문법 오류

컴파일 에러 — 문법 오류, 타입 불일치, 선언 누락

링크 에러 — 함수 정의를 못 찾음 (unresolved external symbol). 링크 에러가 가장 디버깅하기 어렵다. 컴파일은 통과했는데 링크에서 터지면 "어디서 빠졌지?" 찾기 힘들기 때문.

Part 3. MSVC는 뭐야? — Visual Studio의 컴파일러

MSVC가 뭐야?

Microsoft Visual C++ Compiler. Visual Studio에 내장된 컴파일러다. Windows 전용.

MSVC의 특징은?

Windows API / COM / ATL 완벽 지원 — Windows 프로그래밍에 최적화.

MSVC 전용 확장 — __declspec, __forceinline 등 표준에 없는 키워드 제공.

SEH (Structured Exception Handling) — Windows 구조적 예외 처리 지원.

PDB 디버그 심볼 — Visual Studio 디버거와 완벽한 연동.

게임 서버가 Windows에서 돈다면 MSVC가 사실상 표준이다.

// MSVC 전용 코드 예시 // DLL 내보내기 선언 __declspec(dllexport) void InitServer(); // 라이브러리 자동 링크 #pragma comment(lib, "ws2_32.lib") // 강제 인라인 __forceinline int GetPlayerHP(int id) { return g_players[id].hp; } // 구조적 예외 처리 (SEH) __try { ProcessPacket(pData); } __except(EXCEPTION_EXECUTE_HANDLER) { LogError("Crash in ProcessPacket"); }

주의: MSVC는 C++ 표준 준수가 GCC/Clang보다 느린 편이었지만, 최근 크게 개선됨. /permissive- 옵션으로 엄격한 표준 모드를 켤 수 있다.

Part 4. GCC는 뭐야? — Linux의 기본 컴파일러

GCC가 뭐야?

GNU Compiler Collection. Linux에서 기본 컴파일러다. 오픈소스. C, C++, Fortran, Go 등 다양한 언어를 지원한다.

GCC의 특징은?

가장 오래된 성숙한 컴파일러 — 1987년부터 개발. 수십 년간의 최적화 노하우 축적.

최적화 수준이 강력 — -O0(최적화 없음)부터 -O3(최대 최적화), -Os(크기 최적화), -Ofast(표준 무시 최대 속도)까지 세밀한 제어 가능.

크로스 컴파일 지원 우수 — x86에서 ARM용 바이너리를 만드는 등.

다양한 CPU 아키텍처 지원 — x86, ARM, MIPS, RISC-V, PowerPC 등.

# GCC 컴파일 명령어 예시 # 기본 컴파일 g++ main.cpp -o main # 최적화 + 경고 + C++17 표준 g++ -O2 -Wall -std=c++17 main.cpp -o main # 디버그 빌드 (디버그 심볼 포함) g++ -g -O0 -Wall main.cpp -o main_debug # 최대 최적화 + 링크 타임 최적화 g++ -O3 -flto -march=native main.cpp -o main_fast

Part 5. Clang은 뭐야? — LLVM 기반, 에러 메시지가 친절

Clang은 뭐야?

LLVM 프로젝트의 C/C++ 컴파일러다. Apple이 주도적으로 개발. macOS의 기본 컴파일러.

Clang이 GCC보다 좋은 점은?

1) 에러 메시지가 매우 친절하고 정확 — 어디서 틀렸는지, 어떻게 고쳐야 하는지까지 알려줌.

2) 컴파일 속도가 빠름 — 대규모 프로젝트에서 체감 차이가 큼.

3) 모듈식 구조(LLVM) — sanitizer, static analyzer 등 다양한 도구와 연동 용이.

4) 라이선스가 더 자유로움 — Apache 2.0 (GCC는 GPL).

// 같은 에러에 대한 에러 메시지 비교 // 코드: int x = "hello"; // --- GCC 에러 메시지 --- error: invalid conversion from 'const char*' to 'int' // --- Clang 에러 메시지 --- error: cannot initialize a variable of type 'int' with an lvalue of type 'const char[6]' int x = "hello"; ^ ~~~~~~~ note: did you mean to use a string type? // Clang은 "어디서", "왜" 틀렸는지, 심지어 "이렇게 고쳐볼까?"까지 제안한다.

Part 6. 같은 코드인데 왜 다르게 동작해? — 최적화 차이, 재배치 공격성

같은 C++ 소스인데 컴파일러마다 결과가 다를 수 있어?

Undefined Behavior(UB)가 있으면 컴파일러마다 다른 최적화를 적용해서 결과가 달라질 수 있다. UB는 "C++ 표준이 정의하지 않은 동작"이다. 컴파일러가 마음대로 해석해도 되는 영역.

// UB 예시 1: signed integer overflow int x = INT_MAX; x = x + 1; // UB! 결과가 컴파일러마다 다를 수 있음 // MSVC: 보통 wrap-around (INT_MIN) // GCC -O2: "overflow는 안 일어난다"고 가정하고 코드 제거 가능 // Clang: GCC와 유사하게 최적화 // UB 예시 2: 초기화 안 된 변수 읽기 int y; printf("%d", y); // UB! 쓰레기 값... 또는 0... 또는 크래시 // MSVC Debug: 0xCCCCCCCC로 초기화 // MSVC Release: 쓰레기 값 // GCC/Clang: 레지스터에 남아있던 값 // UB 예시 3: null pointer dereference int* p = nullptr; *p = 42; // UB! 크래시... 또는 아무 일도 안 일어남 // 컴파일러가 "p는 null이 아니다"라고 가정하고 체크 코드를 제거할 수 있음
최적화 공격성이 뭐야?

컴파일러마다 얼마나 적극적으로 코드를 변환하는지가 다르다.

GCC가 가장 공격적 — UB를 이용한 최적화를 적극적으로 수행.

Clang은 중간 — 비슷하지만 약간 덜 공격적.

MSVC는 보수적인 편 — "프로그래머 의도를 존중"하는 경향.

핵심: UB를 피하고 표준 C++를 작성하면 세 컴파일러 모두 같은 결과를 보장한다. 컴파일러를 탓하기 전에 내 코드에 UB가 없는지 먼저 확인하자.

Part 7. 그래서 어떤 걸 써야 해? — 플랫폼별 선택 기준

실무에서 어떤 컴파일러를 써야 해?

플랫폼에 따라 결정된다.

플랫폼 기본 컴파일러 대안
Windows 게임 서버 MSVC (Visual Studio) Clang-cl
Linux 게임 서버 GCC Clang
macOS / iOS Clang (Xcode) GCC (Homebrew)
크로스 플랫폼 CMake + 세 컴파일러 모두 CI/CD에서 전부 테스트
게임 서버에서 추천은?

Windows라면 MSVC (Visual Studio). 이 프로젝트(조선협객전)도 MSVC + Visual Studio를 사용한다.

크로스 플랫폼이라면 CMake + 세 컴파일러 모두 CI 테스트가 정석이다. 관련 내용은 CMake 크로스 플랫폼 빌드에서 자세히 다룬다.

핵심 정리

  • 컴파일러 = 소스코드를 기계어로 번역하는 프로그램 (전처리 → 컴파일 → 어셈블 → 링크)
  • MSVC = Windows 전용, Visual Studio, 게임 서버에서 사실상 표준
  • GCC = Linux 기본, 오픈소스, 가장 넓은 플랫폼 지원, 공격적 최적화
  • Clang = LLVM 기반, macOS 기본, 친절한 에러 메시지, 빠른 컴파일
  • 같은 코드가 다르게 동작하면 → Undefined Behavior 의심. 표준 C++ 준수가 핵심
  • 크로스 플랫폼이라면 CMake + 세 컴파일러 CI 테스트
