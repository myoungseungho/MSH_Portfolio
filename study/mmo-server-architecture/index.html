100만 동접 MMO, 서버를 어떻게 나눌까?

대규모 MMO 서버 아키텍처 설계의 핵심 판단들

왜 서버 1대로 안 되는가

MMO에서 서버 1대로 100만 명을 못 받나?

절대 못 받아. 서버 1대의 물리적 한계를 생각해 보자.

물리적 한계가 뭔데?

서버가 게임을 돌리려면 크게 세 가지 자원이 필요해.

1. CPU 틱 처리량

틱(Tick)이란 서버가 게임 세계를 한 번 업데이트하는 주기야.

정의: 서버가 "모든 유저의 입력을 받고 → 게임 로직 계산하고 → 결과를 보내는" 한 사이클.

왜 필요: 틱이 없으면 게임 세계가 멈춤. 보통 초당 20~60틱.

안 쓰면: 유저 행동이 반영 안 되고, 서버가 아무것도 처리 못 함.

100만 명의 이동/전투/스킬을 한 틱 안에 계산? CPU 1개론 물리적으로 불가능.

2. 메모리

유저 1명당 서버에 저장해야 하는 데이터: 위치, HP, 인벤토리, 버프, 파티 정보...

유저 1명 = 대략 10~50KB. 100만 명이면? 10~50GB 순수 유저 데이터만.

거기에 몬스터, NPC, 아이템, 맵 데이터까지? RAM이 터짐.

3. 네트워크 대역폭

유저 1명한테 초당 보내는 데이터 = 약 5~20KB.

100만 명이면? 초당 5~20GB. NIC (Network Interface Card, 네트워크 카드) 1장으로는 감당 불가.

서버 1대의 현실적 한계: CPU: 1틱(50ms) 안에 처리 가능한 유저 = 수천 명 메모리: 64~128GB RAM 기준 = 유저 수만~수십만 (데이터 복잡도에 따라) 네트워크: 10Gbps NIC 1장 = 초당 ~1.25GB (유저 수만 명 수준) 결론: Zone/Game 서버 1대당 동시접속 2,000~5,000명이 현실적 상한선
비유: 식당

서버 1대 = 요리사 1명인 식당.
손님 10명? 괜찮아.
손님 100명? 좀 밀려.
손님 100만 명? 요리사를 수백 명 고용하고, 주방을 수백 개로 나눠야지.
그게 바로 서버를 나누는 이유야.

공통 뼈대 - 모든 MMO가 갖는 레이어

서버를 나눈다는 건 알겠어. 그런데 어떤 구조로 나눠?

아키텍처(설계 방식)에 따라 세부 구현은 다르지만, 거의 모든 MMO 서버는 같은 뼈대를 공유해.

하나씩 뜯어보자.

Gateway 서버가 뭐야?

Gateway (= Proxy) 서버

정의: 클라이언트가 가장 먼저 접속하는 서버. 연결을 관리하고, 패킷을 적절한 내부 서버로 전달(라우팅)해 줌.

왜 필요: 유저가 직접 Game 서버에 붙으면, Game 서버 IP가 노출되고, 서버 교체/확장이 불가능해짐.

안 쓰면: 서버 점검할 때 유저 전원 튕기고, DDoS 공격에 Game 서버가 직접 노출됨.

Stateless 서비스가 뭐야?

Stateless (상태 비저장형) 서비스

정의: 서버가 이전 요청의 결과를 기억하지 않는 방식. 요청이 올 때마다 독립적으로 처리.

왜 필요: 상태를 안 가지니까 서버를 마음대로 늘리거나 줄일 수 있음 (수평 확장).

안 쓰면: 서버 1대가 죽으면 그 서버에 있던 유저 데이터가 날아감.

Login, Lobby, Chat, Matchmaking 같은 건 전부 Stateless로 만들 수 있어.

그러면 World/Zone 서버는?

World/Zone 서버 (= Game 서버) - 게임 로직의 핵심.

정의: 유저의 이동, 전투, 스킬, 충돌 판정 등 실시간 게임 로직을 처리하는 서버.

왜 필요: 게임의 "세계"가 실제로 돌아가는 곳. 이게 없으면 게임이 안 됨.

안 쓰면: 게임 자체가 존재하지 않음.

이건 Stateful (상태 보존형)이야. 유저의 현재 위치, HP, 전투 상태를 계속 들고 있어야 하니까.

DB랑 Cache는?

Cache (캐시) = Redis 같은 인메모리 저장소. 자주 쓰는 데이터를 메모리에 올려두고 빠르게 읽음.

DB (Database, 데이터베이스) = MSSQL, MySQL 같은 영구 저장소. 유저 계정, 인벤토리 등을 디스크에 저장.

Cache는 빠르고(마이크로초), DB는 느리지만(밀리초) 안전해. 둘 다 써야 해.

마지막으로 모니터링 / Admin / 로그 수집 레이어도 있어.

서버가 수백 대인데, 어디가 병목인지 어떻게 알아? 로그 수집하고 대시보드로 보는 거야.

이건 게임 로직과 직접 관련은 없지만, 없으면 장애 발생 시 원인 파악이 불가능.

[클라이언트] | ┌───────┴───────┐ | Gateway / | | Proxy 서버 | ← 연결 관리, 패킷 라우팅 └───────┬───────┘ | ┌─────────────────┼─────────────────┐ | | | ┌─────┴─────┐ ┌─────┴─────┐ ┌─────┴─────┐ | Login / | | World / | | Chat / | | Lobby | | Zone 서버 | | Match | ← Stateless & Stateful | (Stateless)| | (Stateful)| | (Stateless)| └───────────┘ └─────┬─────┘ └───────────┘ | ┌──────┼──────┐ | | ┌─────┴─────┐ ┌────┴────┐ | Redis | | MSSQL | | (Cache) | | (DB) | ← 캐시 + 영구 저장소 └───────────┘ └─────────┘ + 모니터링 / Admin / 로그 수집 (전체 서버를 감시)

선택지 A - 채널 분산 (가장 흔함)

뼈대는 알겠어. 그러면 Game 서버를 어떻게 나누느냐가 관건이잖아. 첫 번째 방법은?

가장 흔하고 검증된 방법: 채널 분산.

정의: 같은 맵(월드)을 여러 개로 복제해서, 각 복제본을 "채널"이라 부르고 별도 서버에서 돌리는 방식.

왜 필요: 서버 1대에 수천 명밖에 못 받으니까, 같은 맵을 여러 채널로 복사해서 유저를 분산.

안 쓰면: 서버 1대에 유저가 몰려서 틱이 느려지고, 게임이 렉 걸림.

메이플스토리 헤네시스를 생각해 봐: [헤네시스 1채널] - 서버 A - 유저 3,000명 [헤네시스 2채널] - 서버 B - 유저 3,000명 [헤네시스 3채널] - 서버 C - 유저 3,000명 ... [헤네시스 334채널] - 서버 N - 유저 3,000명 합계: 약 100만 명
강점은?

구현이 단순하고, 스케일링이 쉬움.

유저가 늘어나면? 채널을 추가하면 됨. 서버 1대 더 붙이고 "4채널" 열면 끝.

각 채널은 독립적이라 서로 영향도 없어.

약점은?

친구가 다른 채널이면 같이 못 놀아.

"나 1채널인데 너 3채널이야? 채널 옮겨와" - 이런 경험 해봤을 거야.

그리고 "하나의 거대한 세계"라는 느낌이 약해. 채널마다 별개의 세계니까.

이 방식 쓰는 게임이 뭐야?

메이플스토리, 던전앤파이터, 로스트아크 (마을 구간) 같은 채널 기반 게임.

사실 대부분의 한국 MMO가 이 방식이야.

100만 동접이면?

채널당 3,000명 x 334채널. 가장 현실적인 접근.

인프라 비용도 예측 가능하고, 장애 범위도 채널 단위로 격리돼.

선택지 B - Zone 분할 (오픈월드)

채널 방식은 세계가 분리되잖아. "진짜 하나의 세계"를 만들고 싶으면?

그러면 Zone 분할 방식을 써야 해.

정의: 하나의 월드를 지리적 영역(Zone)으로 잘라서, 각 Zone을 별도 서버가 담당하는 방식.

왜 필요: 오픈월드 게임은 "채널 바꾸기" 없이 걸어서 어디든 갈 수 있어야 하니까.

안 쓰면: 오픈월드 자체가 불가능. 서버 1대로 전체 월드를 돌릴 수 없으니까.

WoW (월드 오브 워크래프트) 구조 예시: ┌──────────────┬──────────────┐ | | | | 엘윈 숲 | 서부 몰락지대 | | (Zone 서버 A)| (Zone 서버 B)| | | | ├──────────────┼──────────────┤ | | | | 저습지 | 불모의 땅 | | (Zone 서버 C)| (Zone 서버 D)| | | | └──────────────┴──────────────┘ 유저가 엘윈 숲에서 서부 몰락지대로 걸어가면 → 서버 A에서 서버 B로 핸드오프(이전) 발생
강점은?

"진짜 하나의 세계"를 만들 수 있어.

유저 입장에서 채널 같은 거 신경 안 써도 됨. 그냥 걸어가면 됨.

월드가 살아있다는 몰입감이 훨씬 강해.

약점은?

Zone 경계 처리가 지옥이야.

유저가 Zone 경계 위에 서 있으면? 양쪽 서버 모두에 존재해야 해.

Zone A에서 화살을 쏴서 Zone B에 있는 적을 맞추면? 두 서버 간 통신이 필요해.

이 "경계 처리"가 구현 난이도의 대부분을 차지해.

그리고 인기 Zone에 핫스팟(병목)이 생겨.

수도 같은 인기 지역에 유저가 몰리면 그 Zone 서버만 터짐. 다른 Zone 서버는 한가한데.

이 방식 쓰는 게임은?

WoW (월드 오브 워크래프트), 리니지, EVE Online, 뉴월드 같은 오픈월드 MMO.

100만 동접이면?

Zone당 부하 불균형이 심각해.

조용한 필드 Zone은 유저 50명, 수도 Zone은 유저 50,000명. 같은 스펙 서버에 넣으면? 수도 서버만 죽음.

그래서 인기 Zone은 더 좋은 서버를 쓰거나, 내부적으로 채널을 섞기도 해.

선택지 C - Dynamic Spatial Partitioning (동적 공간 분할)

Zone 분할의 핫스팟 문제를 해결할 방법은 없어?

이론적으로 완벽한 해답이 있어. Dynamic Spatial Partitioning (동적 공간 분할).

정의: Zone의 크기와 경계를 고정하지 않고, 실시간 부하에 따라 자동으로 나누고 합치는 방식.

왜 필요: 고정 Zone은 유저가 몰리면 핫스팟이 생기니까, 부하에 따라 유동적으로 분할.

안 쓰면: 인기 Zone에 유저가 몰릴 때마다 수동으로 서버를 증설해야 함.

평소: Zone이 크게 2개로 나뉨 ┌────────────────┬────────────────┐ | 서버 A | 서버 B | | (유저 2000) | (유저 2000) | └────────────────┴────────────────┘ 이벤트 시작! 왼쪽에 유저 몰림: ┌────────┬───────┬────────────────┐ | 서버 A | 서버 C | 서버 B | | (2000) | (3000) | (1000) | └────────┴───────┴────────────────┘ ↑ 부하가 높은 영역을 자동으로 쪼개서 서버 C가 떠맡음
강점은?

부하 분산이 가장 유연하고, 이론적으로 무한 스케일이 가능.

유저가 어디에 몰리든, 시스템이 알아서 서버를 배분해.

약점은?

구현 난이도가 극상이야.

공간이 분할될 때, 그 안에 있는 유저(Entity)의 데이터를 새 서버로 옮겨야 해.

Entity가 뭐야?

Entity (엔티티)

정의: 게임 세계에 존재하는 모든 객체. 유저 캐릭터, 몬스터, NPC, 드롭 아이템 등.

왜 필요: 서버가 게임 세계를 관리하려면, 모든 것을 "Entity"라는 단위로 추적해야 해.

안 쓰면: "이 몬스터를 누가 관리하지?"가 불분명해져서 동기화 오류 발생.

공간 분할이 일어나면 Authority (권한) 이전이 필요해.

정의: 특정 Entity를 "누가 제어할 권한을 가지는가"를 정하는 것.

왜 필요: 두 서버가 동시에 같은 몬스터를 제어하면 충돌이 나니까, 반드시 1개 서버만 권한을 가져야 해.

안 쓰면: 몬스터 HP가 서버마다 달라지고, 유저에게 다른 결과가 보임.

이 Authority 이전이 실시간으로 깔끔하게 되려면 엄청나게 정교한 설계가 필요해.

그러면 실제로 쓰는 곳이 있어?

완전한 Dynamic Spatial Partitioning을 쓰는 상용 게임은 거의 없어.

현실에서는 A(채널) 또는 B(Zone)를 기반으로 깔아놓고, 특정 상황에서만 부분적으로 C를 도입해.

예: 대규모 공성전 영역만 동적 분할, 나머지는 고정 Zone.

SpatialOS 같은 미들웨어가 이걸 시도했지만, 아직 업계 표준은 아님.

진짜 병목은 어디인가

서버를 잘 나눴어. 채널이든 Zone이든. 그러면 100만 동접 해결된 거야?

아직 멀었어.

100만 동접의 진짜 병목은 Game 서버 자체가 아니야.

진짜 병목은 DB 쓰기와 서버 간 통신이야.

DB 쓰기가 왜 병목이야?

유저가 아이템을 줍거나, 퀘스트를 깨거나, 레벨업 할 때마다 DB에 기록해야 해.

100만 명이 동시에 행동하면? 초당 수백만 건의 DB 쓰기 요청이 폭주.

MSSQL/MySQL은 디스크 I/O 기반이라 초당 수천~수만 건이 한계.

해결책:

1. Write-Behind (지연 쓰기): 바로 DB에 안 쓰고, Redis에 먼저 쌓아두고 묶어서 한 번에 DB로 밀어넣기.

2. DB 샤딩: 유저 ID 기준으로 여러 DB 서버에 분산.

3. 중요하지 않은 데이터 (채팅 로그 등)는 NoSQL이나 로그 시스템으로 분리.

서버 간 통신은?

Zone A에 있는 유저가 Zone B에 있는 유저에게 귓속말을 보내면?

Zone A 서버 → Gateway → Zone B 서버. 서버 간 통신이 발생해.

파티, 길드, 거래, 경매장 같은 크로스 서버 기능이 많아질수록 서버 간 통신량이 폭발해.

서버 간 통신 지연(latency)이 유저 체감 렉에 직접 영향.

해결책:

1. 서버 간 통신에 Message Queue (메시지 큐)를 사용. 비동기로 처리해서 부하 분산.

2. 같은 데이터센터 안에 서버를 배치해서 물리적 거리를 최소화.

3. 크로스 서버 기능을 전담하는 별도 서비스 (Chat 서버, Guild 서버 등)를 둠.

Gateway가 죽으면 어떻게 돼?

Gateway는 모든 유저의 연결이 지나가는 곳이야. 여기가 죽으면?

해당 Gateway에 연결된 유저 전원이 튕김.

그러면 어떻게 해?

Gateway 다중화가 필수야.

Gateway를 여러 대 두고, 앞에 Load Balancer (로드 밸런서, 부하 분산기)를 놓아서 유저를 분산.

Gateway 1대가 죽어도 다른 Gateway가 이어받음.

근데 Gateway가 죽으면 유저의 세션 정보도 날아가지 않아?

맞아. 그래서 Redis에 세션 정보를 저장해 둬.

유저가 다른 Gateway로 재접속하면, Redis에서 세션을 복원해서 이어서 플레이할 수 있게.

이걸 Redis 세션 복원이라고 해.

Gateway 다중화 + Redis 세션 복원: [유저] → [Load Balancer] | ┌────────┼────────┐ | | | [GW #1] [GW #2] [GW #3] ← Gateway 다중화 | | | └────────┼────────┘ | [Redis] ← 세션 정보 공유 저장소 | ┌────────┼────────┐ [Game #1] [Game #2] [Game #3] GW #2가 죽으면: 1. 유저가 Load Balancer를 통해 GW #3에 재접속 2. GW #3이 Redis에서 세션 정보 조회 3. 유저는 끊긴 지점부터 이어서 플레이

용어 사전

용어 뜻
Tick (틱) 서버가 게임 세계를 한 번 업데이트하는 주기. 보통 초당 20~60회.
Gateway / Proxy 클라이언트가 가장 먼저 접속하는 서버. 연결 관리 + 패킷 라우팅.
Stateless (상태 비저장) 이전 요청을 기억하지 않는 서비스. 수평 확장이 쉬움.
Stateful (상태 보존) 유저의 현재 상태를 계속 기억하는 서비스. Game 서버가 대표적.
Entity (엔티티) 게임 세계의 모든 객체 (유저, 몬스터, NPC, 아이템 등).
Authority (권한) 특정 Entity를 제어할 수 있는 서버의 권한.
Hotspot (핫스팟) 유저가 특정 영역에 몰려서 서버 부하가 집중되는 현상.
Write-Behind (지연 쓰기) DB에 바로 안 쓰고 캐시에 모아뒀다가 한 번에 쓰는 기법.
Load Balancer (로드 밸런서) 들어오는 요청을 여러 서버에 분산시키는 장치.
Message Queue (메시지 큐) 서버 간 비동기 통신을 위한 대기열. 보내는 쪽과 받는 쪽을 분리.

핵심 정리: 100만 동접 MMO 서버 아키텍처

  • Gateway - 연결 관리 + 패킷 라우팅. 다중화 필수, Redis로 세션 복원.
  • 채널 분산 - 같은 맵을 복제. 가장 현실적이고 스케일링이 쉬움.
  • Zone 분할 - 월드를 지역별로 나눔. 오픈월드 필수이지만 경계 처리가 핵심 난제.
  • Dynamic Spatial - 부하에 따라 자동 분할. 이상적이지만 현실에서는 부분 적용.
  • 진짜 병목 - Game 서버가 아니라 DB 쓰기 + 서버 간 통신. 여기를 해결해야 100만 동접이 가능.
