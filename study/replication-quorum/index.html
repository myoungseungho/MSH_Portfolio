서버가 죽어도 데이터가 안 날아가는 이유

복제(Replication)와 쿼럼(Quorum) - 데이터를 안전하게 지키는 원리

Part 1. 서버 1대에 저장하면 왜 위험해?

DB 서버 1대면 뭐가 문제야?

그 서버 하드디스크가 고장나면?

유저의 모든 캐릭터 데이터가 증발해.

결제한 캐시템도 다 날아가.

💀 단일 서버의 위험: [유저] ──저장──▶ [DB 서버 1대] │ ▼ 디스크 고장 💥 데이터 전부 소실! "어제 결제한 100만원 캐시템 어디 갔어요?!" "6개월 육성한 캐릭터가 사라졌어요!" → 서비스 종료 각...
그래서 복제를 하는 거야?

맞아. 같은 데이터를 여러 서버에 복사해두는 거야.

1대가 죽어도 다른 서버에 데이터가 있으니까.

✅ 복제(Replication)의 힘: [유저] ──저장──▶ [Primary] │ ┌───────┼───────┐ ▼ ▼ ▼ [Replica1] [Replica2] [Replica3] │ ▼ Primary 디스크 고장 💥 [Replica1] 👑 승격! "데이터는 안전해요~" → 서비스 계속 운영!

Part 2. 복제 방식: 동기 vs 비동기

복제하면 느려지지 않아?

복제 방식에 따라 달라.

동기 복제와 비동기 복제가 있어.

🔄 동기 복제 (Synchronous): [유저] ──저장──▶ [Primary] │ ▼ 복제 완료까지 대기 ┌───────┼───────┐ ▼ ▼ ▼ [R1 ✓] [R2 ✓] [R3 ✓] │ ▼ [유저] ◀──완료──── [Primary] ✅ 장점: 모든 복제본이 항상 최신 ❌ 단점: 느림 (복제 완료까지 대기)
⚡ 비동기 복제 (Asynchronous): [유저] ──저장──▶ [Primary] ──완료──▶ [유저] │ ▼ (나중에 복제) ┌───────┼───────┐ ▼ ▼ ▼ [R1 ✓] [R2 ✓] [R3 ...] ✅ 장점: 빠름 (바로 응답) ❌ 단점: 복제 완료 전에 Primary 죽으면 데이터 유실!
게임에선 뭘 써?

상황에 따라 다르게 써:

데이터 종류 복제 방식 이유
결제 정보 동기 돈 관련은 절대 유실 불가
인벤토리 동기 아이템 복구는 민원 폭탄
채팅 로그 비동기 좀 날아가도 큰 문제 아님
위치 정보 비동기 어차피 계속 바뀜

Part 3. 쿼럼(Quorum)이 뭐야?

"과반수"랑 비슷한 거야?

맞아! 쿼럼 = 최소 동의 수야.

"3대 중 2대가 저장 완료하면 OK" 같은 규칙.

📊 쿼럼(Quorum) 개념: 3대 서버, 쿼럼 = 2 쓰기 요청: [Primary] ──저장──▶ [R1] ✓ (1/2) [R2] ✓ (2/2) ← 쿼럼 달성! [R3] ... (아직 복제 중) │ ▼ "2대 저장 완료 = 쓰기 성공!" (R3는 나중에 따라잡으면 됨)
왜 전부 기다리지 않아?

전부 기다리면 가장 느린 서버에 맞춰야 해.

네트워크 지연, 디스크 느림... 다 기다릴 수 없어.

쿼럼만 충족하면 "충분히 안전하다"고 판단하는 거야.

⏱️ 전체 대기 vs 쿼럼 대기: [전체 대기] 3대 모두: R1: 10ms ✓ R2: 15ms ✓ R3: 200ms ✓ ← 네트워크 느림 총 응답: 200ms 😢 [쿼럼 대기] 2대만: R1: 10ms ✓ R2: 15ms ✓ ← 쿼럼 달성! R3: (나중에 복제) 총 응답: 15ms 🚀

Part 4. WAL(Write-Ahead Log)이 뭐야?

저장 중에 서버가 죽으면?

DB에 직접 쓰다가 중간에 죽으면 데이터가 깨져.

그래서 먼저 로그에 기록하는 거야.

📝 WAL(Write-Ahead Log) 원리: ❌ 직접 쓰기 (위험): [쓰기 요청] ──▶ [DB 파일에 직접 쓰기] │ ▼ 쓰는 중에 전원 꺼짐! 💥 데이터 파일 손상... ✅ WAL 방식 (안전): [쓰기 요청] ──▶ [로그에 먼저 기록] ──▶ [DB 파일에 적용] │ ▼ 전원 꺼짐! 💥 "로그 보고 복구하면 돼"
왜 로그에 먼저 쓰면 안전해?

로그는 append-only야.

끝에 추가만 하니까 중간에 끊겨도 기존 데이터는 멀쩡해.

재시작하면 로그를 읽어서 못 한 작업만 다시 해.

🔄 WAL 복구 과정: 1️⃣ 정상 동작: [Log] 트랜잭션 #1: INSERT item_id=100 ✓ [Log] 트랜잭션 #2: UPDATE gold=5000 ✓ [Log] 트랜잭션 #3: DELETE quest_id=50 (기록 중 💥) 2️⃣ 재시작 후 복구: 로그 스캔: #1 완료됨, #2 완료됨, #3 미완료 → #3은 롤백 (없던 일로) → 데이터 일관성 유지!
게임 서버에서 어디 쓰여?

사실 네가 쓰는 MSSQL, MySQL 다 WAL 써.

MSSQL = Transaction Log, MySQL = Redo Log.

Redis도 AOF(Append Only File) 모드가 WAL이야.

Part 5. 읽기 쿼럼과 쓰기 쿼럼

읽을 때도 쿼럼이 필요해?

최신 데이터를 보장하려면 필요해.

중요한 공식이 있어:

📐 쿼럼 공식: W + R > N W = 쓰기 쿼럼 (몇 대에 써야 성공?) R = 읽기 쿼럼 (몇 대에서 읽어야 함?) N = 전체 복제본 수 예시: N=3, W=2, R=2 쓰기: 3대 중 2대에 저장 ──▶ 성공 읽기: 3대 중 2대에서 읽기 ──▶ 최신 데이터 보장 왜? W + R = 4 > 3 = N → 읽기와 쓰기가 반드시 겹치는 서버가 있음! → 그 서버에는 최신 데이터가 있음!
예시로 보여줘

3대 서버에서 W=2, R=2일 때:

🔍 쿼럼이 최신 데이터를 보장하는 원리: 쓰기 (W=2): [S1: 100] ✓ ← 새 값 저장됨 [S2: 100] ✓ ← 새 값 저장됨 [S3: 50] ← 아직 옛날 값 읽기 (R=2): 최소 2대에서 읽으면... Case 1: S1, S2 선택 → [100, 100] → 최신값 100 ✓ Case 2: S1, S3 선택 → [100, 50] → 최신값 100 ✓ Case 3: S2, S3 선택 → [100, 50] → 최신값 100 ✓ → 어떤 조합이든 최신 값을 가진 서버가 포함됨!
설정 W R 특징
강한 일관성 N 1 항상 최신 / 쓰기 느림
밸런스 N/2+1 N/2+1 읽기/쓰기 균형
빠른 읽기 N 1 읽기 빠름 / 쓰기 느림
빠른 쓰기 1 N 쓰기 빠름 / 읽기 느림

Part 6. 게임 서버에서 어떻게 써?

실제 게임에서 복제는 어떻게 구성해?

데이터 중요도에 따라 다르게 구성해:

🎮 게임 서버 복제 구성 예시: 1️⃣ 결제/인벤토리 (절대 유실 불가) ┌─────────────────────────────────────┐ │ Primary ══동기══▶ Replica1 │ │ │ │ │ └══════동기══▶ Replica2 │ │ (둘 다 확인해야 커밋) │ └─────────────────────────────────────┘ 2️⃣ 길드/친구 (중요하지만 약간 지연 OK) ┌─────────────────────────────────────┐ │ Primary ══동기══▶ Replica1 (로컬) │ │ │ │ │ └──비동기──▶ Replica2 (다른 DC) │ └─────────────────────────────────────┘ 3️⃣ 로그/통계 (유실 일부 감수) ┌─────────────────────────────────────┐ │ Primary ──비동기──▶ Replica1 │ │ │ │ │ └──비동기──▶ Replica2 │ └─────────────────────────────────────┘
복제본은 어디에 배치해?

다른 물리적 위치에 둬야 해.

같은 서버실에 두면 화재나면 다 날아가.

🌍 복제본 배치 전략: ❌ 같은 랙에 모두: [서버 랙 1] ├─ Primary ├─ Replica1 └─ Replica2 → 랙 스위치 고장나면 전멸! ✅ 분산 배치: [서버실 A] [서버실 B] ├─ Primary ├─ Replica2 └─ Replica1 [다른 도시 IDC] └─ Replica3 (재해 복구용) → 서버실 하나 날아가도 서비스 계속!

⚠️ 복제 시 주의사항

1. 복제 지연(Replication Lag) - 비동기 복제 시 복제본이 뒤처질 수 있음

2. Split Brain - 네트워크 분리 시 두 Primary 발생 가능 → 쿼럼으로 방지

3. Failover 시간 - Primary 죽으면 Replica 승격까지 시간 필요

4. 비용 - 복제본 = 서버 비용 × N배

📝 핵심 정리

  • 복제 = 같은 데이터를 여러 서버에 저장 → 1대 죽어도 안전
  • 동기 복제 = 안전하지만 느림, 비동기 = 빠르지만 유실 위험
  • 쿼럼 = "N대 중 M대 동의하면 OK" → 속도와 안전성 균형
  • WAL = 로그 먼저 쓰기 → 중간에 죽어도 복구 가능
  • W + R > N = 읽기/쓰기 쿼럼이 겹쳐서 최신 데이터 보장
