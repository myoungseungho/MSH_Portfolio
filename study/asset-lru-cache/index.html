LRU 캐시

가장 오래 안 쓴 놈부터 버린다 - 메모리 관리의 핵심 전략

Part 1. LRU 캐시란 무엇인가?

LRU가 뭐야? 왜 이름이 그래?

LRU = Least Recently Used = "가장 최근에 안 쓴 것"

캐시가 꽉 찼을 때 어떤 걸 버릴지 결정하는 알고리즘이야.

핵심 아이디어: "최근에 쓴 건 또 쓸 확률이 높다" (Temporal Locality)

LRU의 핵심 원리: 시간적 지역성 (Temporal Locality)

    시간 →
    ├─────────────────────────────────────────────────────────┤

    [에셋 A 로드]──[A 사용]──[A 사용]──────────[A 사용]────→ 자주 씀!
         │
    [에셋 B 로드]──[B 사용]──────────────────────────────────→ 가끔 씀
         │
    [에셋 C 로드]────────────────────────────────────────────→ 한번 쓰고 안씀


    메모리 부족 시 누굴 버릴까?
    ┌─────────────────────────────────────────────────────────┐
    │  C를 버린다! (가장 오래 안 씀)                           │
    │  B는 아직 기회를 준다                                    │
    │  A는 계속 유지 (자주 쓰니까)                             │
    └─────────────────────────────────────────────────────────┘
다른 방법도 있어? FIFO나 Random은?

캐시 교체 정책(Cache Replacement Policy) 비교:

캐시 교체 정책 비교

┌──────────────┬────────────────────────────────────────────────────────┐
│    정책      │                       특징                              │
├──────────────┼────────────────────────────────────────────────────────┤
│              │                                                        │
│   FIFO       │  먼저 들어온 놈 먼저 나감                               │
│  (Queue)     │  단순하지만 "자주 쓰는 것도 버림"                       │
│              │  ❌ 게임에 부적합 (UI 텍스처가 자꾸 빠짐)               │
│              │                                                        │
├──────────────┼────────────────────────────────────────────────────────┤
│              │                                                        │
│   Random     │  무작위로 버림                                          │
│              │  구현 최고로 간단 (rand() 한방)                         │
│              │  ❌ 예측 불가, 중요한 에셋도 버려질 수 있음              │
│              │                                                        │
├──────────────┼────────────────────────────────────────────────────────┤
│              │                                                        │
│   LRU        │  가장 오래 안 쓴 놈 버림                                │
│  ⭐ 추천     │  "최근에 쓴 건 또 쓴다" 원리 활용                       │
│              │  ✅ 게임에 적합! 대부분의 엔진이 사용                    │
│              │                                                        │
├──────────────┼────────────────────────────────────────────────────────┤
│              │                                                        │
│   LFU        │  가장 적게 쓴 놈 버림 (Least Frequently Used)           │
│              │  사용 횟수 카운트 필요                                   │
│              │  △ 오래된 인기 에셋이 영원히 남음 (문제 가능)            │
│              │                                                        │
└──────────────┴────────────────────────────────────────────────────────┘

게임에서 LRU가 좋은 이유:
━━━━━━━━━━━━━━━━━━━━━━━━━
• 마을에서 던전으로 이동 → 마을 에셋 LRU로 자동 퇴장
• 던전에서 마을로 복귀 → 던전 에셋 LRU로 자동 퇴장
• 자연스러운 메모리 관리!

Part 2. LRU 캐시의 자료구조

LRU를 어떻게 구현해? O(1)이 가능해?

핵심: 더블 링크드 리스트 + 해시맵 조합!

이 조합으로 모든 연산을 O(1)에 처리할 수 있어.

LRU 캐시 자료구조 설계

┌─────────────────────────────────────────────────────────────────────────┐
│                         LRU Cache                                        │
├─────────────────────────────────────────────────────────────────────────┤
│                                                                          │

연산별 시간 복잡도:
━━━━━━━━━━━━━━━━━━
• Get(key)   : O(1) - HashMap으로 찾고, 리스트 앞으로 이동
• Put(key)   : O(1) - HashMap에 추가, 리스트 앞에 삽입
• Evict()    : O(1) - 리스트 끝(TAIL)에서 제거
노드 구조는 어떻게 생겼어?

더블 링크드 리스트의 각 노드:

// LRU 캐시 노드 구조 template<typename TKey, typename TValue> struct LRUNode { TKey Key; // 에셋 키 (파일 경로 등) TValue Value; // 에셋 데이터 (또는 포인터) size_t MemorySize; // 이 에셋의 메모리 크기 uint64_t LastAccessTime;// 마지막 접근 시간 (디버깅용) LRUNode* Prev; // 이전 노드 (더 최신) LRUNode* Next; // 다음 노드 (더 오래됨) LRUNode(const TKey& key, const TValue& value, size_t size) : Key(key) , Value(value) , MemorySize(size) , LastAccessTime(GetCurrentTimestamp()) , Prev(nullptr) , Next(nullptr) {} };

Part 3. LRU 캐시 기본 구현

실제 코드로 보여줘!

기본 LRU 캐시 클래스 전체 구현:

template<typename TKey, typename TValue> class LRUCache { private: using Node = LRUNode<TKey, TValue>; std::unordered_map<TKey, Node*> m_HashMap; // O(1) 검색 Node* m_Head; // 더미 헤드 (가장 최신) Node* m_Tail; // 더미 테일 (가장 오래됨) size_t m_Capacity; // 최대 개수 size_t m_Count; // 현재 개수 public: LRUCache(size_t capacity) : m_Capacity(capacity) , m_Count(0) { // 더미 노드로 경계 처리 간단화 m_Head = new Node(); m_Tail = new Node(); m_Head->Next = m_Tail; m_Tail->Prev = m_Head; } // O(1) 조회 - 없으면 nullptr TValue* Get(const TKey& key) { auto it = m_HashMap.find(key); if (it == m_HashMap.end()) { return nullptr; // Cache Miss } Node* node = it->second; // 핵심! 사용했으니 맨 앞으로 이동 MoveToHead(node); return &node->Value; // Cache Hit } // O(1) 삽입 void Put(const TKey& key, const TValue& value, size_t memSize) { auto it = m_HashMap.find(key); if (it != m_HashMap.end()) { // 이미 있으면 값 갱신하고 앞으로 이동 Node* node = it->second; node->Value = value; node->MemorySize = memSize; MoveToHead(node); return; } // 새 노드 생성 Node* newNode = new Node(key, value, memSize); m_HashMap[key] = newNode; AddToHead(newNode); m_Count++; // 용량 초과 시 LRU 퇴출 if (m_Count > m_Capacity) { EvictLRU(); } } private: // 노드를 리스트에서 분리 void RemoveNode(Node* node) { node->Prev->Next = node->Next; node->Next->Prev = node->Prev; } // 노드를 헤드 바로 뒤에 추가 (가장 최신 위치) void AddToHead(Node* node) { node->Next = m_Head->Next; node->Prev = m_Head; m_Head->Next->Prev = node; m_Head->Next = node; } // 노드를 맨 앞으로 이동 void MoveToHead(Node* node) { RemoveNode(node); AddToHead(node); node->LastAccessTime = GetCurrentTimestamp(); } // LRU 퇴출 (테일 바로 앞 노드) void EvictLRU() { Node* lru = m_Tail->Prev; if (lru == m_Head) return; // 비어있음 RemoveNode(lru); m_HashMap.erase(lru->Key); delete lru; m_Count--; } };

Part 4. 게임 에셋 관리용 LRU 확장

게임에서는 "개수"가 아니라 "메모리 크기"로 관리해야 하지 않아?

맞아! 실제 게임에서는 Memory Budget 기반 LRU를 사용해.

4KB 텍스처 1000개보다 4GB 텍스처 1개가 문제니까!

class AssetLRUCache { private: using Node = LRUNode<AssetKey, AssetHandle>; std::unordered_map<AssetKey, Node*> m_HashMap; Node* m_Head; Node* m_Tail; size_t m_MemoryBudget; // 최대 메모리 (bytes) size_t m_CurrentMemory; // 현재 사용량 // 에셋 타입별 우선순위 std::unordered_map<AssetType, int> m_TypePriority; public: AssetLRUCache(size_t budgetMB) : m_MemoryBudget(budgetMB * 1024 * 1024) , m_CurrentMemory(0) { InitDummyNodes(); SetupDefaultPriorities(); } // 메모리 기반 퇴출 void Put(const AssetKey& key, AssetHandle handle, size_t memorySize) { // 이미 있으면 업데이트 if (Contains(key)) { UpdateExisting(key, handle, memorySize); return; } // 새 에셋이 들어갈 공간 확보 while (m_CurrentMemory + memorySize > m_MemoryBudget) { if (!EvictOne()) { // 더 이상 퇴출 불가 (모두 고정됨) LogWarning("Memory budget exceeded, cannot evict!"); break; } } // 새 노드 추가 Node* newNode = new Node(key, handle, memorySize); m_HashMap[key] = newNode; AddToHead(newNode); m_CurrentMemory += memorySize; } private: // 하나 퇴출 (LRU이면서 퇴출 가능한 것) bool EvictOne() { Node* candidate = m_Tail->Prev; // 퇴출 가능한 노드를 찾을 때까지 역순회 while (candidate != m_Head) { if (CanEvict(candidate)) { size_t freedMemory = candidate->MemorySize; RemoveNode(candidate); m_HashMap.erase(candidate->Key); // 에셋 실제 해제 ReleaseAsset(candidate->Value); delete candidate; m_CurrentMemory -= freedMemory; return true; } candidate = candidate->Prev; } return false; // 퇴출 가능한 노드 없음 } // 퇴출 가능 여부 판단 bool CanEvict(Node* node) { AssetHandle handle = node->Value; // 1. 현재 사용 중인가? if (handle->GetRefCount() > 0) return false; // 2. 고정(Pinned) 에셋인가? if (handle->IsPinned()) return false; // 3. 필수 에셋인가? (UI, 공통 등) if (IsEssentialAsset(node->Key)) return false; return true; } };
메모리 기반 LRU vs 개수 기반 LRU

[개수 기반 LRU] Capacity = 3
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  [4KB] [4KB] [4KB]  = 12KB 사용

  새로운 4GB 텍스처 추가하면?
  → [4KB] 하나 퇴출
  → [4KB] [4KB] [4GB] = 4GB + 8KB ← 💥 메모리 폭발!


[메모리 기반 LRU] Budget = 500MB
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  [100MB] [150MB] [200MB] = 450MB / 500MB

  새로운 100MB 텍스처 추가하면?
  → 450 + 100 = 550MB > 500MB
  → [200MB] 퇴출 (LRU)
  → 450 - 200 + 100 = 350MB ✅

  → 아직 부족하면? 계속 퇴출!

Part 5. 퇴출 정책 고급 기능

모든 에셋을 똑같이 취급하면 안 되지 않아?

맞아! 실제 게임에서는 Priority 시스템을 함께 사용해.

UI 텍스처는 플레이어가 항상 보니까 쉽게 버리면 안 돼!

// 에셋 우선순위 정의 enum class AssetPriority { Critical = 0, // 절대 퇴출 금지 (셰이더, 필수 UI) High = 1, // 웬만하면 유지 (주인공, 메인 BGM) Normal = 2, // 일반 에셋 Low = 3, // 우선 퇴출 (먼 배경, 희귀 몬스터) Preload = 4, // 프리로드용 (필요 시 바로 퇴출 OK) }; class PriorityAwareLRUCache { private: // 우선순위별 LRU 리스트 std::array<DoublyLinkedList, 5> m_PriorityLists; std::unordered_map<AssetKey, Node*> m_HashMap; public: // 퇴출 순서: Low → Normal → High // Critical은 절대 퇴출하지 않음 bool EvictOne() { // 낮은 우선순위부터 시도 for (int p = (int)AssetPriority::Preload; p >= (int)AssetPriority::High; p--) { auto& list = m_PriorityLists[p]; if (Node* lru = list.GetTail()) { if (CanEvict(lru)) { DoEvict(lru); return true; } } } return false; // Critical만 남음 } // 접근 시 우선순위 리스트 내에서 앞으로 이동 void Touch(const AssetKey& key) { Node* node = m_HashMap[key]; int priority = (int)node->Priority; m_PriorityLists[priority].MoveToHead(node); } };

AssetType → Priority 매핑으로 자동화:

class AssetPriorityMapper { private: std::unordered_map<AssetType, AssetPriority> m_TypeToPriority; public: AssetPriorityMapper() { // 기본 매핑 설정 m_TypeToPriority[AssetType::Shader] = AssetPriority::Critical; m_TypeToPriority[AssetType::CoreUI] = AssetPriority::Critical; m_TypeToPriority[AssetType::Font] = AssetPriority::Critical; m_TypeToPriority[AssetType::PlayerModel] = AssetPriority::High; m_TypeToPriority[AssetType::PlayerTexture] = AssetPriority::High; m_TypeToPriority[AssetType::MainBGM] = AssetPriority::High; m_TypeToPriority[AssetType::NPCModel] = AssetPriority::Normal; m_TypeToPriority[AssetType::MonsterModel] = AssetPriority::Normal; m_TypeToPriority[AssetType::MapTexture] = AssetPriority::Normal; m_TypeToPriority[AssetType::DistantBG] = AssetPriority::Low; m_TypeToPriority[AssetType::RareEffect] = AssetPriority::Low; m_TypeToPriority[AssetType::Prefetched] = AssetPriority::Preload; } AssetPriority GetPriority(AssetType type) const { auto it = m_TypeToPriority.find(type); return (it != m_TypeToPriority.end()) ? it->second : AssetPriority::Normal; // 기본값 } };

LRU-K는 뭐야?

K번 이상 접근해야 진짜 캐시에 들어가는 방식!

1번만 쓴 건 "테스트 영역"에 두고, K번 쓰면 승격시켜.

class LRU2Cache // LRU-2 (K=2) { private: // 2개의 LRU 리스트 LRUList m_Probation; // 수습 영역 (1번 접근) LRUList m_Protected; // 보호 영역 (2번+ 접근) std::unordered_map<AssetKey, Node*> m_HashMap; public: void Access(const AssetKey& key) { Node* node = m_HashMap[key]; if (node->IsInProbation()) { // 수습 영역에서 2번째 접근! → 보호 영역으로 승격 m_Probation.Remove(node); m_Protected.AddToHead(node); node->MarkProtected(); } else { // 보호 영역 내에서 앞으로 이동 m_Protected.MoveToHead(node); } } void Insert(const AssetKey& key, AssetHandle handle) { // 새 에셋은 항상 수습 영역에서 시작 Node* node = new Node(key, handle); node->MarkProbation(); m_Probation.AddToHead(node); m_HashMap[key] = node; // 퇴출은 수습 영역에서 먼저! TryEvict(); } private: void TryEvict() { // 수습 영역 LRU부터 퇴출 if (m_Probation.GetSize() > 0) { Node* victim = m_Probation.GetTail(); Evict(victim); } // 수습이 비면 보호 영역에서 퇴출 else if (m_Protected.GetSize() > 0) { Node* victim = m_Protected.GetTail(); Evict(victim); } } };

2Q 알고리즘은 뭐가 달라?

2Q는 LRU-2를 개선한 건데, FIFO + LRU 조합을 써.

class TwoQueueCache // 2Q Algorithm { private: // A1in: 최초 진입 (FIFO 방식) FIFOQueue m_A1in; // 작은 크기 (전체의 25%) // A1out: 퇴출된 적 있는 키 기록 (값은 없음, 히스토리) FIFOQueue m_A1out; // 키만 저장 // Am: 2번+ 접근 (LRU 방식) LRUList m_Am; // 큰 크기 (전체의 75%) public: void Access(const AssetKey& key) { // 이미 Am에 있으면 LRU 갱신 if (m_Am.Contains(key)) { m_Am.MoveToHead(key); return; } // A1in에 있으면 아직 1회 접근 if (m_A1in.Contains(key)) { // A1in 내에서는 이동 없음 (FIFO) return; } // A1out에 있으면 (과거에 퇴출된 적 있음) → Am으로 직행 if (m_A1out.Contains(key)) { m_A1out.Remove(key); m_Am.AddToHead(key, LoadAsset(key)); return; } // 완전 새로운 에셋 → A1in에 추가 InsertToA1in(key); } private: void InsertToA1in(const AssetKey& key) { // A1in이 꽉 찼으면 FIFO로 빼서 A1out으로 이동 if (m_A1in.IsFull()) { AssetKey evicted = m_A1in.PopFront(); m_A1out.PushBack(evicted); // 히스토리 기록 // A1out도 크기 제한 if (m_A1out.IsFull()) { m_A1out.PopFront(); // 오래된 히스토리 삭제 } } m_A1in.PushBack(key, LoadAsset(key)); } };

Part 8. 게임 엔진에서의 LRU 적용

Unity에서 LRU 캐시를 어떻게 만들어?

Unity의 Addressables와 연동하는 LRU 캐시:

public class AddressableLRUCache { private class CacheNode { public string Address; public AsyncOperationHandle Handle; public long MemorySize; public CacheNode Prev, Next; } private Dictionary<string, CacheNode> _cache; private CacheNode _head, _tail; private long _budgetBytes; private long _currentBytes; public async Task<T> LoadAsync<T>(string address) { // 캐시 히트 if (_cache.TryGetValue(address, out var node)) { MoveToHead(node); return (T)node.Handle.Result; } // 캐시 미스 - Addressables로 로드 var handle = Addressables.LoadAssetAsync<T>(address); await handle.Task; long size = EstimateMemorySize(handle.Result); // 공간 확보 while (_currentBytes + size > _budgetBytes) { if (!EvictLRU()) break; } // 캐시에 추가 var newNode = new CacheNode { Address = address, Handle = handle, MemorySize = size }; _cache[address] = newNode; AddToHead(newNode); _currentBytes += size; return (T)handle.Result; } private bool EvictLRU() { var lru = _tail.Prev; if (lru == _head) return false; // Addressables 해제 Addressables.Release(lru.Handle); RemoveNode(lru); _cache.Remove(lru.Address); _currentBytes -= lru.MemorySize; return true; } }
Unreal Engine에서는?

Unreal은 Streaming Manager가 내부적으로 LRU를 사용해.

커스텀 캐시가 필요하면 이렇게:

class FAssetLRUCache { private: struct FCacheEntry { FName AssetPath; TSharedPtr<FStreamableHandle> Handle; int64 MemorySize; FCacheEntry* Prev; FCacheEntry* Next; }; TMap<FName, FCacheEntry*> Cache; FCacheEntry* Head; FCacheEntry* Tail; int64 BudgetBytes; int64 CurrentBytes; FStreamableManager& StreamableManager; public: template<typename T> T* LoadAssetSync(const FSoftObjectPath& Path) { FName Key = Path.GetAssetFName(); // 캐시 히트 if (FCacheEntry** Found = Cache.Find(Key)) { MoveToHead(*Found); return Cast<T>((*Found)->Handle->GetLoadedAsset()); } // 동기 로드 TSharedPtr<FStreamableHandle> Handle = StreamableManager.RequestSyncLoad(Path); if (!Handle.IsValid()) return nullptr; int64 Size = GetAssetMemorySize(Handle->GetLoadedAsset()); // LRU 퇴출로 공간 확보 while (CurrentBytes + Size > BudgetBytes) { if (!EvictOne()) break; } // 캐시 추가 FCacheEntry* Entry = new FCacheEntry(); Entry->AssetPath = Key; Entry->Handle = Handle; Entry->MemorySize = Size; Cache.Add(Key, Entry); AddToHead(Entry); CurrentBytes += Size; return Cast<T>(Handle->GetLoadedAsset()); } };

Part 9. LRU 캐시 성능 최적화

LRU 캐시 성능을 더 높이려면?

몇 가지 최적화 기법들:

// 1. 노드 풀링 - new/delete 오버헤드 제거 class NodePool { private: std::vector<Node*> m_FreeList; std::vector<std::unique_ptr<Node[]>> m_Chunks; static constexpr size_t CHUNK_SIZE = 256; public: Node* Allocate() { if (m_FreeList.empty()) { // 청크 단위로 미리 할당 auto chunk = std::make_unique<Node[]>(CHUNK_SIZE); for (size_t i = 0; i < CHUNK_SIZE; ++i) { m_FreeList.push_back(&chunk[i]); } m_Chunks.push_back(std::move(chunk)); } Node* node = m_FreeList.back(); m_FreeList.pop_back(); return node; } void Deallocate(Node* node) { m_FreeList.push_back(node); // 실제 삭제 안 함 } }; // 2. 배치 퇴출 - 여러 개 한번에 처리 class BatchEvictLRU { public: void EvictBatch(size_t targetFreeBytes) { std::vector<Node*> toEvict; size_t accumulated = 0; // 먼저 퇴출 대상 수집 Node* curr = m_Tail->Prev; while (curr != m_Head && accumulated < targetFreeBytes) { if (CanEvict(curr)) { toEvict.push_back(curr); accumulated += curr->MemorySize; } curr = curr->Prev; } // 한번에 처리 for (Node* node : toEvict) { DoEvict(node); } } }; // 3. Lock-Free Read (읽기가 많을 때) class ConcurrentLRU { private: std::shared_mutex m_Mutex; // Read-Write Lock public: AssetHandle Get(const AssetKey& key) { // 읽기는 shared lock (여러 스레드 동시 가능) std::shared_lock lock(m_Mutex); auto it = m_HashMap.find(key); if (it == m_HashMap.end()) return nullptr; // 접근 시간만 원자적 갱신 (리스트 이동은 나중에) it->second->LastAccessTime.store(GetTimestamp()); return it->second->Value; } void DeferredReorder() // 주기적으로 호출 { // 쓰기 lock으로 실제 순서 재정렬 std::unique_lock lock(m_Mutex); // LastAccessTime 기준으로 정렬 SortByAccessTime(); } };

Trade-off 주의:
• 지연 재정렬은 순서 정확도가 약간 떨어짐 (실시간 LRU가 아님)
• 게임에서는 대부분 괜찮음 (프레임 단위로 재정렬하면 됨)

핵심 정리

  • LRU = Least Recently Used - 가장 오래 안 쓴 것 먼저 퇴출
  • 자료구조: 더블 링크드 리스트 + 해시맵 = O(1) 연산
  • 게임에서는 메모리 기반 - 개수가 아닌 바이트 단위로 관리
  • Priority 시스템 - Critical > High > Normal > Low > Preload
  • 메모리 압박 대응 - Warning → Critical → Emergency 단계별
  • 변형 알고리즘: LRU-K, 2Q - 스캔 오염 방지
  • 최적화: 노드 풀링, 배치 퇴출, 지연 재정렬
