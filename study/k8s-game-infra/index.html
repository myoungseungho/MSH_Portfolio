쿠버네티스로 게임 서버 운영하기

컨테이너 오케스트레이션 기초부터 게임 서버 적용까지

Part 1. 컨테이너가 뭐야?

컨테이너? 도커? 그게 뭔데?

컨테이너는 프로그램을 실행하는 데 필요한 모든 것을 한 박스에 담은 거야.

비유: 이사 박스

이사할 때 물건을 박스에 넣잖아?
- 박스 안에 뭐가 있든 어떤 트럭에 실어도 잘 가져갈 수 있어
- 컨테이너도 똑같아. 어떤 서버에서든 똑같이 실행돼!
왜 필요해? 그냥 서버에 직접 설치하면 안 돼?

"내 컴퓨터에선 되는데요?" 문제 때문이야.

[직접 설치의 문제] 개발자 PC: - Windows 10 - Java 11 - MySQL 5.7 → 잘 돌아감! 서버: - Ubuntu 20.04 - Java 8 (버전 다름!) - MySQL 8.0 (버전 다름!) → 에러 발생! [컨테이너 사용] 개발자 PC: ┌─────────────────────┐ │ 컨테이너 │ │ - Ubuntu 20.04 │ │ - Java 11 │ │ - MySQL 5.7 │ └─────────────────────┘ → 잘 돌아감! 서버: ┌─────────────────────┐ │ 똑같은 컨테이너 │ │ - Ubuntu 20.04 │ │ - Java 11 │ │ - MySQL 5.7 │ └─────────────────────┘ → 똑같이 잘 돌아감!
도커(Docker)는 뭐야?

도커는 컨테이너를 만들고 실행하는 도구야. 가장 유명한 컨테이너 플랫폼이지.

# 도커 기본 명령어 # 1. 이미지 다운로드 (프로그램 설치 파일 같은 거) docker pull nginx # 2. 컨테이너 실행 (프로그램 실행) docker run -d -p 80:80 nginx # 3. 실행 중인 컨테이너 확인 docker ps # 결과: # CONTAINER ID IMAGE PORTS # a1b2c3d4e5f6 nginx 0.0.0.0:80->80/tcp

Part 2. 왜 쿠버네티스가 필요해?

도커만 있으면 되는 거 아냐?

컨테이너가 1개면 도커로 충분해. 근데 100개면?

[게임 서버 규모 예시] 작은 게임: - 로그인 서버: 2개 - 게임 서버: 5개 - DB: 1개 = 총 8개 컨테이너 대형 게임 (출시일): - 로그인 서버: 20개 - 게임 서버: 100개 - 매칭 서버: 10개 - DB: 5개 - 캐시: 10개 = 총 145개 컨테이너 이걸 일일이 수동으로 관리한다고? → docker run 145번 치기? → 하나 죽으면 어떻게 알아? → 트래픽 늘어나면 어떻게 늘려?
그래서 쿠버네티스가 뭘 해주는데?

쿠버네티스(K8s)는 컨테이너들을 자동으로 관리해주는 시스템이야.

비유: 오케스트라 지휘자

오케스트라에서 지휘자가 뭘 해?
- 바이올린 "여기서 시작해!"
- 트럼펫 "조금 쉬어!"
- 드럼 "더 세게!"

쿠버네티스도 똑같아:
- 게임 서버 "5개로 늘려!"
- 죽은 서버 "다시 살려!"
- 트래픽 "이 서버로 보내!"
기능 수동 관리 쿠버네티스
서버 100개 시작 명령어 100번 설정 1줄
서버 죽으면? 모니터링 + 수동 재시작 자동 재시작
트래픽 급증 새벽에 일어나서 서버 추가 자동 스케일링
배포 하나씩 업데이트 롤링 업데이트 자동

Part 3. 쿠버네티스 기본 개념

쿠버네티스에서 쓰는 용어들이 뭐야?

핵심 개념 4가지만 알면 돼:

[쿠버네티스 핵심 개념] 1. Pod (파드) = 컨테이너의 집 ┌─────────────────────┐ │ Pod │ │ ┌───────────────┐ │ │ │ 게임 서버 │ │ │ │ 컨테이너 │ │ │ └───────────────┘ │ └─────────────────────┘ 2. Deployment (디플로이먼트) = Pod 관리자 "게임 서버 Pod를 항상 5개 유지해!" 3. Service (서비스) = 네트워크 창구 "외부에서 게임 서버에 접근하려면 여기로!" 4. Node (노드) = 실제 서버 컴퓨터 Pod들이 실행되는 물리적인 장소
Deployment가 정확히 뭘 해?

Deployment는 "이 상태를 유지해"라고 선언하는 거야.

# game-server-deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: game-server spec: replicas: 5 # ← "항상 5개 유지해!" selector: matchLabels: app: game-server template: spec: containers: - name: game-server image: my-game:v1.0 # ← 이 이미지로 ports: - containerPort: 8080 # 이 설정을 적용하면? # → 게임 서버 Pod 5개가 자동 생성 # → 하나가 죽어도 자동으로 다시 5개로 복구!
5개에서 10개로 늘리고 싶으면?

명령어 하나면 끝!

# 현재 상태 확인 kubectl get pods # 결과: game-server-xxx (5개) # 10개로 스케일 업 kubectl scale deployment game-server --replicas=10 # 다시 확인 kubectl get pods # 결과: game-server-xxx (10개!) # → 5개가 자동으로 추가됨

Part 4. 게임 서버에 왜 필요해?

게임 서버는 특별한 거 아니야?

게임 서버의 특징을 보면:

특징 왜 문제? 쿠버네티스가 해결
트래픽 변동이 큼 출시일/이벤트 때 10배 증가 자동 스케일링
점검이 잦음 매주 업데이트 배포 롤링 업데이트
서버가 많음 로그인, 게임, 매칭, DB... 중앙 관리
실시간 필수 서버 죽으면 유저 이탈 자동 복구
실제로 어떤 효과가 있어?

예시 시나리오를 보자:

[시나리오: 신규 게임 글로벌 출시] Before (쿠버네티스 없이): - 한국: 서버 50대 수동 설정 (1주일) - 일본: 비슷한 작업 반복 (1주일) - 미국: 또 반복... (1주일) - 문제 발생: 각 리전마다 설정이 조금씩 다름! After (쿠버네티스): - 한국: YAML 설정 파일 작성 (1일) - 일본: 같은 파일 복사 + 리전만 변경 (1시간) - 미국: 같은 파일 복사 + 리전만 변경 (1시간) - 모든 리전이 동일한 구성 보장!
핵심 가치: 재현 가능성

"Dev 환경에서 된 건 Prod에서도 된다!"
- 개발 환경 = 운영 환경 (동일한 설정)
- 새 리전 추가 = 기존 설정 복사

Part 5. 배포는 어떻게 해?

점검 없이 업데이트할 수 있어?

롤링 업데이트로 무중단 배포가 가능해!

[롤링 업데이트 과정] 시작: v1.0 서버 5개 운영 중 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │v1.0│ │v1.0│ │v1.0│ │v1.0│ │v1.0│ └────┘ └────┘ └────┘ └────┘ └────┘ Step 1: 새 버전 1개 추가 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │v1.0│ │v1.0│ │v1.0│ │v1.0│ │v1.0│ │v1.1│ └────┘ └────┘ └────┘ └────┘ └────┘ └────┘ Step 2: 구버전 1개 제거 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │v1.0│ │v1.0│ │v1.0│ │v1.0│ │v1.1│ └────┘ └────┘ └────┘ └────┘ └────┘ ... (반복) ... 완료: v1.1 서버 5개 ┌────┐ ┌────┐ ┌────┐ ┌────┐ ┌────┐ │v1.1│ │v1.1│ │v1.1│ │v1.1│ │v1.1│ └────┘ └────┘ └────┘ └────┘ └────┘ → 유저는 계속 접속 가능!
문제 생기면 롤백은?

명령어 하나로 즉시 롤백!

# 배포 히스토리 확인 kubectl rollout history deployment/game-server # 출력: # REVISION CHANGE-CAUSE # 1 v1.0 initial # 2 v1.1 new feature # 3 v1.2 bug fix ← 현재 (버그 있음!) # 이전 버전으로 롤백 kubectl rollout undo deployment/game-server # 또는 특정 버전으로 kubectl rollout undo deployment/game-server --to-revision=1 # 롤백 상태 확인 kubectl rollout status deployment/game-server # → 30초 내 완료!

Part 6. GitOps가 뭐야?

GitOps?

Git에 저장된 설정 = 실제 서버 상태를 유지하는 방식이야.

비유: 레시피북

요리사가 레시피북을 갖고 있어.
- 레시피: "파스타 = 면 200g + 소스 100ml"
- 누가 물어보면? 레시피북 확인!
- 새 요리사 와도? 레시피북대로 하면 똑같은 맛!

GitOps도 똑같아:
- Git 저장소 = 레시피북
- 서버 설정 = 레시피
- 누구나 Git만 보면 현재 서버 상태를 알 수 있어!
[GitOps 워크플로우] 1. 개발자가 설정 변경 game-deployment.yaml: - replicas: 5 → replicas: 10 2. Git에 커밋 & PR "서버 10개로 증설" 3. 코드 리뷰 후 머지 4. ArgoCD가 자동 감지 "Git이랑 실제 서버랑 다르네?" 5. 자동으로 서버에 적용 → 실제 서버도 10개로! 6. 롤백 필요하면? → Git에서 revert하면 끝!
왜 이게 좋아?

모든 변경이 기록으로 남아!

전통 방식 GitOps
"누가 서버 설정 바꿨어?" Git 커밋 로그에 다 있음
"왜 바꿨는지 모르겠어" 커밋 메시지에 이유 기록
"이전 설정이 뭐였지?" Git 히스토리에 전부 보관
"검토 없이 적용됨" PR 리뷰 후 적용

Part 7. 실제 게임 회사는 어떻게 써?

사례: 데브시스터즈 (쿠키런 킹덤)

7년간의 점진적 도입:

  • 2014년: 쿠버네티스 연구 시작
  • 2018년: 개발/QA 환경에 적용
  • 2021년: 쿠키런 킹덤 글로벌 출시 성공

핵심 전략: "서버 팜 찍어내기"

동일한 인프라를 Dev/QA/Staging/Prod에 빠르게 복제

바로 적용하면 안 돼?

천천히! 단계별로 적용하는 게 핵심이야.

[권장 도입 순서] Level 1: 학습 (1~3개월) ├── 로컬에서 minikube로 실습 ├── 기본 개념 숙지 └── 간단한 웹 앱 배포해보기 Level 2: 내부 도구 (3~6개월) ├── 사내 CI/CD 서버를 K8s로 이전 ├── 개발 도구들 K8s 환경으로 └── 운영 경험 축적 Level 3: 개발 환경 (6~12개월) ├── 개발 서버를 K8s로 ├── QA 환경 구축 └── 문제 발생해도 영향 적음 Level 4: 프로덕션 (1년 이후) ├── 비핵심 서비스부터 적용 ├── 점진적으로 핵심 서비스 이전 └── 충분한 운영 노하우 확보 후
데브시스터즈의 조언

"처음부터 프로덕션에 적용하지 마세요. 개발 환경부터 천천히 시작하세요."
"팀의 쿠버네티스 숙련도를 높이는 것이 먼저입니다."
"데브시스터즈도 7년이 걸렸습니다. 조급해하지 마세요."

핵심 정리

  • 컨테이너 - 프로그램 + 환경을 하나로 포장. 어디서든 동일하게 실행
  • 쿠버네티스 - 컨테이너들을 자동 관리. 스케일링, 복구, 배포 자동화
  • Deployment - "이 상태 유지해" 선언. Pod 개수 자동 관리
  • 롤링 업데이트 - 무중단 배포. 하나씩 교체하며 업데이트
  • GitOps - Git = 서버 상태. 모든 변경이 기록으로 남음
  • 도입 전략 - 학습 → 내부 도구 → 개발 환경 → 프로덕션 순서로 천천히
