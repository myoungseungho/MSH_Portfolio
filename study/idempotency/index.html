이벤트가 2번 와도 1번만 처리하는 법

멱등성(Idempotency)으로 중복 처리 방지하기

Part 1. 왜 같은 요청이 2번 와?

요청은 1번 보냈는데 왜 2번 처리돼?

분산 시스템에서 중복은 피할 수 없어.

[중복 발생 시나리오] 1️⃣ 네트워크 재시도 클라이언트 → 서버 (요청 전달됨) 서버 → 클라이언트 (응답 유실!) 클라이언트: "응답 없네? 다시 보내자" → 서버는 같은 요청 2번 받음 2️⃣ 메시지 큐 재전송 Producer → Queue → Consumer (처리 완료) Consumer: Ack 보내기 전에 죽음 Queue: "Ack 없네? 다시 보내자" → 새 Consumer가 같은 메시지 또 받음 3️⃣ 유저 더블클릭 "구매" 버튼 연타 → 결제 요청 여러 번
그러면 돈이 2번 빠져나가는 거야?

멱등성 없으면 진짜 2번 빠져나가!

이게 바로 멱등성이 필요한 이유야.

Part 2. 멱등성이 뭐야?

멱등성(Idempotency)이 뭐야?

"같은 연산을 여러 번 해도 결과가 같다"

[멱등 vs 비멱등] ✅ 멱등한 연산: x = 5; // 100번 해도 x는 5 DELETE user_123 // 이미 삭제됐으면 그냥 OK SET gold = 1000 // 100번 해도 골드는 1000 ❌ 비멱등한 연산: x += 1; // 할 때마다 x 증가 gold += 100; // 할 때마다 골드 증가 INSERT log(...) // 할 때마다 로그 추가
아, "설정"은 멱등하고 "증가"는 비멱등하구나

정확해! 비멱등한 연산을 멱등하게 만드는 게 핵심이야.

Part 3. 방법 1: Idempotency Key

비멱등 연산을 어떻게 멱등하게 만들어?

요청마다 고유 ID를 붙여서 "이미 처리했는지" 체크해.

[Idempotency Key 방식] 클라이언트 요청: { "idempotency_key": "uuid-abc-123", // 고유 ID "action": "buy_item", "item_id": 999, "price": 100 } 서버 처리: 1. Redis 조회: "uuid-abc-123" 처리됐나? if (redis.exists("idem:uuid-abc-123")) { return redis.get("idem:uuid-abc-123"); // 이전 결과 반환 } 2. 처리 안 됐으면 실행 result = processPayment(); 3. 결과 저장 (TTL: 24시간) redis.setex("idem:uuid-abc-123", 86400, result); 4. 결과 반환
같은 key로 또 요청 오면?

Redis에 이미 있으니까 실행 안 하고 이전 결과만 반환!

Part 4. 방법 2: 상태 체크

[상태 기반 멱등성] 예시: 퀘스트 완료 보상 수령 요청: "퀘스트 123 보상 받기" 처리: 1. DB 조회: 퀘스트 상태? SELECT reward_claimed FROM quests WHERE user_id = ? AND quest_id = 123 2. 이미 받았으면? if (reward_claimed == true) { return "이미 보상을 받았습니다"; } 3. 아직이면 지급 + 상태 변경 BEGIN TRANSACTION; INSERT INTO inventory...; UPDATE quests SET reward_claimed = true WHERE...; COMMIT; → 같은 요청 10번 와도 보상은 1번만!
이게 더 간단해 보이는데?

상태가 있는 작업은 이게 좋아.

상태 없는 작업(API 호출 등)은 Idempotency Key가 낫고.

Part 5. 방법 3: 버전 체크

[버전 기반 멱등성 - Optimistic Lock] 예시: 골드 증가 요청: { "user_id": 123, "add_gold": 100, "expected_version": 5 // 현재 버전이 5라고 알고 있음 } 처리: UPDATE users SET gold = gold + 100, version = version + 1 WHERE user_id = 123 AND version = 5; // 버전 일치할 때만! if (rows_affected == 0) { // 버전 불일치 = 누가 이미 수정함 return "다시 시도해주세요"; } → 같은 요청 2번 와도, 첫 번째만 성공, 두 번째는 버전 불일치!

Part 6. 게임 서버 멱등성 사례

[게임 서버 멱등성 적용] 1️⃣ 결제 처리 - 결제 요청에 transaction_id 필수 - 같은 transaction_id 재요청 → 기존 결과 반환 - "결제 2번" 방지 2️⃣ 아이템 지급 - 보상 코드 사용: code_used 플래그 체크 - 이미 사용한 코드 → "이미 사용됨" 반환 - "보상 중복" 방지 3️⃣ 메일 수령 - 메일 상태: UNREAD → READ → CLAIMED - CLAIMED 상태에서 수령 요청 → 무시 - "첨부 아이템 2번 받기" 방지 4️⃣ 거래소 구매 - 매물 상태: SELLING → SOLD - 이미 SOLD인 매물 구매 요청 → "이미 판매됨" - "동시 구매" 충돌 방지 5️⃣ 이벤트 참여 - 참여 기록 테이블: (user_id, event_id) UNIQUE - 중복 INSERT → 실패 (이미 참여함) - "보상 중복 수령" 방지

Part 7. 메시지 큐에서 멱등성

Kafka 같은 큐에서도 중복 메시지 오잖아?

맞아. Consumer 쪽에서 멱등성 보장해야 해.

[메시지 큐 멱등성 처리] 메시지 구조: { "message_id": "msg-uuid-456", // 메시지 고유 ID "event_type": "item_drop", "user_id": 123, "item_id": 999 } Consumer 처리: 1. 처리 완료 테이블 조회 SELECT 1 FROM processed_messages WHERE message_id = 'msg-uuid-456'; 2. 이미 처리됐으면 스킵 if (exists) { ack(); // 메시지 처리 완료 신호 return; } 3. 실제 처리 + 기록 (트랜잭션) BEGIN; INSERT INTO inventory...; INSERT INTO processed_messages(message_id) VALUES(...); COMMIT; 4. Ack 전송

핵심: "처리 로직"과 "처리 기록"을 같은 트랜잭션에

이래야 "처리는 됐는데 기록 안 됨" 문제 방지!

핵심 정리

  • 멱등성 = 여러 번 해도 결과가 같음
  • 중복 발생 원인 = 네트워크 재시도, 큐 재전송, 더블클릭
  • Idempotency Key = 요청마다 고유 ID, Redis에 결과 캐시
  • 상태 체크 = 이미 처리됐는지 DB 상태로 확인
  • 버전 체크 = 낙관적 락으로 동시 수정 방지
  • 메시지 큐 = 처리 + 기록을 같은 트랜잭션에
