Push Model & Dormancy — '변경분만'을 더 똑똑하게

안 바뀐 건 검사도 하지 말고, 안 변하는 액터는 아예 잠재워라

30초 요약

Pull(기본): 매 틱 모든 복제 속성을 이전 값과 비교 — 안 바뀐 것도 검사(낭비).

Push Model: '바뀌었다'고 표시된 것만 검사(MARK_PROPERTY_DIRTY) — 우리 더티플래그와 같은 발상.

Dormancy: 한동안 안 변할 액터는 통째로 휴면 → 검사·복제 0. 가장 센 절약.

Part 1. '변경분만'에도 비용이 있다

Ch9에서 '변경분만 보낸다'고 했잖아. 더 아낄 게 있어?

보내는 건 변경분만 맞아. 근데 '뭐가 바뀌었는지' 알려면 엔진이 매 틱 모든 속성을 이전 값과 비교해야 해(Pull). 액터 1만 개 × 속성 수십 개면 그 비교만으로도 무거워.

그래서 '비교 자체를 줄이자'가 이 챕터야.

어떻게 줄여?

두 단계. ① Push Model: 값을 바꾼 코드가 '나 dirty야'라고 직접 표시 → 엔진은 그것만 검사. ② Dormancy: 아예 안 변하는 액터는 휴면시켜 검사 목록에서 빼버려.

Part 2. 틱당 검사량을 봐

세 방식의 틱당 검사량을 비교해봐.

Part 3. 우리 더티플래그와 같은 발상

Push Model이 우리 더티플래그랑 같아?

거의 똑같아. 우리도 '값 바뀐 것만 저장/전송'하려고 더티플래그를 둬(수집이벤트 DB 최적화에서 쓴 그것).

UE의 Push Model도 '바꾼 쪽이 dirty 표시 → 그것만 처리'. 다른 점은 UE는 이걸 켜고 끌 수 있는 엔진 옵션이고, 우리는 처음부터 손으로 박는다는 것.

Dormancy는 우리로 치면?

오래 안 변하는 객체(닫힌 상점, 멈춘 몹)를 갱신 루프에서 빼는 거랑 같아. '변할 일이 생기면 그때 깨운다(FlushNetDormancy)'.

게임은 사실 대부분의 액터가 대부분의 시간 안 변해 — 그래서 Dormancy의 절약 효과가 커.

UE 매크로Push Model 매크로

값을 바꿀 때 MARK_PROPERTY_DIRTY를 같이 호출해서 '나 바뀌었어' 표시. 엔진은 dirty 표시된 속성만 검사해 전송 — 안 바뀐 건 비교조차 안 함.

// 클래스 등록 시 Push 모델 켜기 DOREPLIFETIME_WITH_PARAMS_FAST(AMyChar, Health, FDoRepLifetimeParams{COND_None, REPNOTIFY_OnChanged, true}); // 값 변경 시 void AMyChar::SetHealth(float NewHP) { Health = NewHP; MARK_PROPERTY_DIRTY_FROM_NAME(AMyChar, Health, this); } // Dormancy 깨우기 SetNetDormancy(DORM_DormantAll); // 잠재움 FlushNetDormancy(); // 깨움(값 바꾸기 전 호출)
우리 서버

더티플래그를 직접 멤버 변수로 두고, 변경 시 bit set. 자동저장·SaveDB에서 dirty만 처리.

언리얼

매크로 한 줄로 dirty 표시. SetNetDormancy로 휴면, FlushNetDormancy로 깨움.

함정: SetHealth 안 거치고 Health = 50으로 직접 대입하면 dirty 표시 누락 → 영영 안 보내짐. Setter 강제가 핵심.

Part 4. 실제 + 트레이드오프

방식틱당 비용주의
Pull (기본)모든 속성 비교단순하지만 규모에 약함
Push Modeldirty만표시 누락 시 '안 보내짐' 버그
Dormancy휴면은 0깨우기(Flush) 빠뜨리면 갱신 멈춤
위험은?

Push/더티플래그의 함정은 '표시를 빼먹으면 영영 안 보내짐'이야. 값은 바뀌었는데 dirty 표시를 안 해서 클라가 옛 값을 보는 버그.

Dormancy도 깨우기(FlushNetDormancy)를 빼먹으면 그 액터가 멈춰 보여. 최적화는 항상 '빠뜨림' 리스크를 같이 짊어져.

조건부 복제 — COND_* 로 "누구에게 보낼지" 더 좁히기

Relevancy가 "이 액터 자체를 보낼까?"라면, COND_*는 "이 속성을 누구에게 보낼까?"야. 예: 인벤토리 내용은 본인에게만 보내야 (남이 보면 안 됨).

조건의미예시
COND_None (기본)모두에게위치, 체력
COND_OwnerOnly액터 소유자에게만본인 인벤토리, 비밀 상태
COND_SkipOwner소유자만 빼고본인은 이미 알아서 안 보내는 값
COND_InitialOnly처음 한 번만변하지 않는 초기 설정
COND_SimulatedOnly시뮬레이션 클라(예측 안 함)에만물리 시뮬용 정보
COND_AutonomousOnly본인이 조종하는 클라에만입력 처리용 보정값

등록 시:

DOREPLIFETIME_CONDITION(AMyChar, Inventory, COND_OwnerOnly);
DOREPLIFETIME_CONDITION(AMyChar, AmmoDisplay, COND_SkipOwner);

왜 중요해? 월핵·인벤토리 핵 방지의 1차 방어가 여기야. 패킷에 안 실리는 정보는 핵으로도 못 봐. Ch11의 "벽 뒤 적도 거리만 가까우면 보인다"는 한계의 1차 보완책이지.

핵심 정리

  • Pull(기본) = 매 틱 전 속성 비교(낭비). Push = dirty 표시된 것만
  • Dormancy = 안 변하는 액터 휴면 → 검사·복제 0 (가장 센 절약)
  • 우리 더티플래그와 같은 발상 — UE는 엔진 옵션, 우리는 수동
  • 함정: Push는 dirty 표시 누락, Dormancy는 깨우기(Flush) 누락 → '안 갱신' 버그
  • 게임은 대부분 액터가 대부분 시간 안 변함 → 휴면 절약 효과 큼

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. dirty 표시를 깜빡한 버그는 어떻게 찾아?

가장 까다로운 버그 유형 — "값이 바뀌었는데 클라에 안 가는" 상황이라 재현이 산발적이야.

예방·탐지 기법:

  • Setter 강제: 변수에 직접 대입을 막고 항상 Setter를 거치게. Setter 안에서 dirty 표시.
  • 검증 빌드: 디버그 빌드에서는 Push Model을 끄고 Pull과 비교해, "Pull에선 보내졌는데 Push에선 안 보낸" 케이스를 자동 검출.
  • 린트/매크로: 코드 분석으로 "Replicated 변수에 직접 = 대입"을 경고.
[자동 비교 빌드] 매 틱마다: Pull 모드: 전 속성 검사 → 변경분 목록 A Push 모드: dirty 표시된 것만 → 변경분 목록 B if (A != B) Log("MARK_DIRTY 누락!");
우리 서버에서도 더티플래그 누락은 흔한 함정. "왜 클라에 안 보이지?" 디버깅 시 첫 의심은 "값은 바뀌었는데 변경 통지를 안 했나?".
Q. Dormancy 깨우기(Flush)를 놓치면?

그 액터가 멈춰 보여. 값은 바뀌었는데 클라에 안 가니까 "프리즈"처럼 보이지.

[Flush 누락 시나리오] 액터: 평소 안 변함 → Dormancy ON 코드: SomeProperty = NewValue; ← FlushNetDormancy() 호출 누락 결과: 변수는 변했지만 복제 대상에서 제외돼 클라가 옛 값 봄

예방:

  • Setter에 Flush 포함: 변경하는 코드 경로마다 자동으로 Flush 호출.
  • 이벤트 기반: "이 액터가 변하기 시작" 이벤트에서 Dormancy를 잠시 끔.
  • 주기적 강제 깨움: 안전하게 N초마다 한 번씩 Flush.
Q. 가끔 변하는 액터를 자주 재웠다 깨웠다 하면 더 비싼 거 아냐?

맞아. Dormancy 전이 자체에 비용이 있어 — 채널 정리·재개·상태 동기.

Dormancy는 "한동안 확실히 안 변하는" 액터용. 자주 변하는 액터에 쓰면 오히려 손해.

판단 기준:

  • 적용 좋음: 가구·간판·완료된 퀘스트 NPC·매치 종료된 액터 등 "사실상 정적".
  • 적용 나쁨: 캐릭터·발사체·동적 NPC.

중간(가끔 변함): "한 번 변하면 N초간 안 변할 것"으로 예측 가능하면 그 N초 동안만 깨워두는 식으로 절충.

Q. Push가 그렇게 좋으면 왜 기본이 Pull이야?

안전 마진 때문이야. Pull은 느리지만 절대로 "변했는데 안 보냄" 사고가 없어.

  • Pull(기본): 모든 속성을 매 틱 검사 → 빠뜨림 불가능. 대신 비쌈.
  • Push: 빠름. 대신 표시 누락 = 안 보냄 사고 가능 → 코드 규율 필요.
실무 전략: 신규 프로젝트는 Pull로 시작 → 부하 측정으로 병목 액터 찾기 → 그 액터만 Push로 전환. 한 번에 전체 전환은 위험.

UE5 Iris부터는 Push가 더 권장 — 데이터 지향 구조라 Pull이 더 비싸짐. 시대가 바뀌는 중.
