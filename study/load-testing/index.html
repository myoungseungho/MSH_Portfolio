Load Testing

게임 서버 성능 테스트 자동화하는 법

1. 왜 부하 테스트를 해?

출시 전에 테스트하면 되지 않아?

기능 테스트 != 부하 테스트

실제 사례: 기능 테스트: - QA 10명이 플레이 - "기능 정상!" 확인 - 출시 승인 출시 당일: - 10만명 동시 접속 - 서버 응답 5초 -> 30초 -> 타임아웃 - "렉 미쳤다" 커뮤니티 폭발 - 앱스토어 별점 1점 세례 원인: - 10명 테스트에서 발견 못 한 병목 - DB 커넥션 풀 소진 - 메모리 누수 (10명은 OK, 10만명은 OOM)
부하 테스트로 뭘 알 수 있어?
질문 부하 테스트로 답 찾기
서버 1대당 몇 명? 최대 동시 접속자 수 측정
응답 시간은? 평균/95퍼센타일/99퍼센타일
어디가 병목? CPU/메모리/DB/네트워크 분석
언제 터져? 한계점 도달 시점

2. 어떤 도구를 써?

k6가 유명하던데?
도구 특징 적합한 경우
k6 JS 스크립트, 가벼움 HTTP API 테스트
Locust Python, 분산 실행 복잡한 시나리오
Gatling Scala, 상세 리포트 대규모 엔터프라이즈
더미 클라이언트 직접 구현, 완벽 제어 게임 프로토콜 테스트

게임 서버는 더미 클라이언트가 가장 정확해!

k6 예시 보여줘
// k6 부하 테스트 스크립트 import http from 'k6/http'; import { check, sleep } from 'k6'; export const options = { stages: [ { duration: '2m', target: 100 }, // 2분간 100명까지 증가 { duration: '5m', target: 100 }, // 5분간 100명 유지 { duration: '2m', target: 1000 }, // 2분간 1000명까지 증가 { duration: '5m', target: 1000 }, // 5분간 1000명 유지 { duration: '2m', target: 0 }, // 2분간 0명으로 감소 ], thresholds: { http_req_duration: ['p(95)<200'], // 95% 요청이 200ms 이내 http_req_failed: ['rate<0.01'], // 에러율 1% 미만 }, }; export default function () { // 로그인 API 테스트 const loginRes = http.post('https://api.game.com/login', { userId: `user_${__VU}_${__ITER}`, password: 'test123' }); check(loginRes, { 'login status 200': (r) => r.status === 200, 'login time < 100ms': (r) => r.timings.duration < 100, }); sleep(1); // 게임 데이터 조회 const token = loginRes.json('token'); const dataRes = http.get('https://api.game.com/player/data', { headers: { Authorization: `Bearer ${token}` } }); check(dataRes, { 'data status 200': (r) => r.status === 200, }); sleep(Math.random() * 3); // 1~3초 랜덤 대기 }

3. 게임 서버 테스트는 뭐가 달라?

HTTP API만 테스트하면 안 돼?

게임은 TCP/WebSocket 기반이야!

게임 서버 특성: 1. 지속 연결 (Persistent Connection) - HTTP: 요청-응답 후 끊김 - 게임: TCP 연결 유지 (수 시간) 2. 양방향 통신 - HTTP: 클라이언트 -> 서버 - 게임: 서버 -> 클라이언트 푸시 3. 상태 유지 (Stateful) - HTTP: Stateless - 게임: 세션, 위치, 전투 상태 등 4. 실시간 동기화 - 같은 맵의 다른 유저 움직임 - 동시 전투 처리
더미 클라이언트는 어떻게 만들어?
// C++ 더미 클라이언트 예시 class DummyClient { public: void Run(int clientId) { // 1. 서버 연결 Connect("game.server.com", 9000); // 2. 로그인 SendPacket(CM_LOGIN, { .userId = "dummy_" + std::to_string(clientId), .password = "test123" }); WaitForPacket(SM_LOGIN_RESULT); // 3. 게임 루프 시뮬레이션 while (m_running) { // 이동 (랜덤) if (RandomChance(0.3)) { SendPacket(CM_MOVE, { .x = m_position.x + RandomFloat(-10, 10), .y = m_position.y + RandomFloat(-10, 10) }); } // 스킬 사용 (10% 확률) if (RandomChance(0.1)) { SendPacket(CM_USE_SKILL, { .skillId = RandomInt(1, 10) }); } // 서버 패킷 처리 ProcessIncomingPackets(); // 틱 대기 Sleep(100); // 100ms } } private: void ProcessIncomingPackets() { while (HasPacket()) { auto packet = ReceivePacket(); switch (packet.type) { case SM_MOVE_BROADCAST: // 다른 유저 이동 처리 break; case SM_DAMAGE: // 데미지 처리 break; } } } };

4. 어떤 시나리오를 테스트해?

로그인만 테스트하면 안 돼?

실제 유저 패턴을 시뮬레이션해야 해:

게임 서버 테스트 시나리오: [기본 시나리오] 1. 로그인 -> 캐릭터 선택 -> 월드 입장 2. 필드 이동 + 몬스터 사냥 3. 던전 입장 -> 클리어 4. NPC 상점 이용 5. 로그아웃 [스트레스 시나리오] 1. 동시 로그인 폭증 (출퇴근 시간) 2. 월드 보스 100명 동시 공격 3. 대규모 PvP (50 vs 50) 4. 자정 던전 리셋 동시 입장 [엣지 케이스] 1. 연결 끊김 -> 재접속 2. 같은 아이템 동시 구매 3. 거래 중 로그아웃
유저 비율은 어떻게 정해?
유저 행동 분포 (실제 데이터 기반): [라이브 데이터 분석] - 사냥 중: 40% - 이동 중: 25% - 던전 중: 15% - 상점/창고: 10% - AFK (방치): 10% [부하 테스트 설정] class LoadTestConfig: user_distribution = { "hunting": 0.40, # 40% 사냥 "moving": 0.25, # 25% 이동 "dungeon": 0.15, # 15% 던전 "shop": 0.10, # 10% 상점 "afk": 0.10 # 10% 방치 } packets_per_second = { "hunting": 5, # 사냥: 초당 5패킷 "moving": 10, # 이동: 초당 10패킷 "dungeon": 8, # 던전: 초당 8패킷 "shop": 2, # 상점: 초당 2패킷 "afk": 0.1 # 방치: 10초당 1패킷 }

5. 병목은 어떻게 찾아?

느린 건 알겠는데 어디가 문제야?
병목 분석 체크리스트: [서버 리소스] CPU 100%? -> 게임 로직 최적화 필요 메모리 증가? -> 메모리 누수 의심 네트워크 포화? -> 패킷 크기/빈도 최적화 [데이터베이스] 쿼리 시간 증가? -> 인덱스 확인 커넥션 대기? -> 커넥션 풀 증가 락 대기? -> 트랜잭션 최적화 [애플리케이션] 특정 API 느림? -> 프로파일링 GC 멈춤? -> 메모리 관리 개선 스레드 대기? -> 동시성 문제
프로파일링은 어떻게 해?
# 부하 테스트 중 모니터링 # 1. 서버 리소스 (Grafana) CPU: avg(rate(process_cpu_seconds_total[1m])) * 100 Memory: process_resident_memory_bytes / 1024 / 1024 Network: rate(node_network_receive_bytes_total[1m]) # 2. 게임 서버 메트릭 평균 응답 시간: histogram_quantile(0.95, game_packet_latency) 처리량: rate(game_packets_processed_total[1m]) 동시 접속: game_ccu # 3. DB 모니터링 슬로우 쿼리: SELECT * FROM pg_stat_statements ORDER BY mean_time DESC LIMIT 10; 커넥션 수: SELECT count(*) FROM pg_stat_activity; # 4. 프로파일링 (C++) valgrind --tool=callgrind ./game_server # 결과 분석: kcachegrind callgrind.out.*

6. 자동화는 어떻게 해?

배포할 때마다 부하 테스트?

CI/CD 파이프라인 통합:

# .github/workflows/load-test.yml name: Load Test on: push: branches: [main, release/*] schedule: - cron: '0 2 * * *' # 매일 새벽 2시 jobs: load-test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: Deploy Test Environment run: | terraform apply -auto-approve -var="env=loadtest" - name: Run Load Test run: | k6 run --out json=results.json scripts/load-test.js - name: Analyze Results run: | python analyze_results.py results.json - name: Check Thresholds run: | python check_thresholds.py results.json \ --max-p95=200 \ --max-error-rate=0.01 - name: Upload Report uses: actions/upload-artifact@v3 with: name: load-test-report path: report/ - name: Notify Slack if: failure() run: | curl -X POST $SLACK_WEBHOOK \ -d '{"text":"Load test failed!"}' - name: Cleanup if: always() run: terraform destroy -auto-approve

핵심 정리: Load Testing

  • 도구 - k6(HTTP), Locust(복잡한 시나리오), 더미 클라이언트(게임 프로토콜)
  • 시나리오 - 실제 유저 패턴 기반 (사냥 40%, 이동 25%, 던전 15%...)
  • 메트릭 - 응답 시간(P95/P99), 에러율, 처리량, CCU
  • 병목 분석 - CPU/메모리/DB/네트워크 체크
  • 자동화 - CI/CD 파이프라인 통합, 매일 자동 실행
  • 핵심 - 출시 전에 병목을 찾아라!
