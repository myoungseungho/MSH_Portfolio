🔥 10만 명 접속해도 안 터지는지 어떻게 알아?

게임 서버 부하 테스트 - 더미 클라이언트로 출시 전에 병목 찾는 법

Part 1. QA팀이 테스트했는데 왜 또 해?

QA가 다 테스트하고 "이상 없음" 했는데?

기능 테스트 ≠ 부하 테스트

QA 테스트: → 10명이 플레이 → "로그인 되네, 던전 되네, 상점 되네" → ✅ 기능 정상! 출시 당일: → 10만 명 동시 접속 → 로그인 5초... 10초... 30초... 타임아웃 → "서버 왜 이래?" 커뮤니티 폭발 → 별점 1점 테러
10명일 때는 왜 괜찮았어?

병목은 부하가 걸려야 드러나.

10명일 때: DB 커넥션 풀: 10/100 사용 → 여유 메모리: 1GB/16GB 사용 → 여유 CPU: 5% 사용 → 여유 10만 명일 때: DB 커넥션 풀: 100/100 대기열 발생 → 병목! 메모리: 16GB/16GB + 스왑 → OOM 크래시! CPU: 100% → 응답 지연!

부하 테스트 = 출시 전에 이 병목을 찾는 것

Part 2. k6, Locust 같은 거 쓰면 안 돼?

웹에서는 k6가 유명하던데, 게임도 그거 쓰면 되지 않아?

게임 서버는 HTTP가 아니야.

도식: 웹 서버 vs 게임 서버

═══════════════════════════════════════════════════════════════ 웹 서버 (HTTP) ═══════════════════════════════════════════════════════════════ [클라이언트] [서버] │ │ │───── GET /api/users ────────────────▶│ │◀──── { users: [...] } ──────────────│ │ (연결 끊김) │ │ │ │───── POST /api/login ───────────────▶│ │◀──── { token: "xxx" } ──────────────│ │ (연결 끊김) │ → 요청-응답 후 연결 끊김 → Stateless (상태 없음) → k6, Locust로 테스트 가능 ✅ ═══════════════════════════════════════════════════════════════ 게임 서버 (TCP/UDP) ═══════════════════════════════════════════════════════════════ [클라이언트] [서버] │ │ │══════ TCP 연결 유지 ════════════════│ │ │ │───── CM_LOGIN ─────────────────────▶│ │◀──── SM_LOGIN_OK ──────────────────│ │ │ │───── CM_MOVE (x:100, y:200) ───────▶│ │◀──── SM_MOVE_BROADCAST ────────────│ (다른 유저 이동) │◀──── SM_MONSTER_SPAWN ─────────────│ (몬스터 스폰) │◀──── SM_DAMAGE ────────────────────│ (데미지 받음) │ │ │───── CM_ATTACK ────────────────────▶│ │◀──── SM_ATTACK_RESULT ─────────────│ │ │ │ (연결 유지... 수 시간) │ → TCP 연결 계속 유지 → Stateful (위치, HP, 버프 등 상태 유지) → 양방향 통신 (서버 → 클라 푸시) → k6로 테스트 불가능 ❌
그럼 게임은 뭘로 테스트해?

더미 클라이언트 (Dummy Client)

= 실제 게임 클라이언트처럼 행동하는 가짜 유저 봇

더미 클라이언트가 하는 일: 1. 실제 클라이언트처럼 TCP 연결 2. 실제 프로토콜로 패킷 주고받기 3. 실제 유저처럼 행동 (이동, 공격, 아이템 사용) 4. 서버 응답 검증 → 진짜 유저 1만 명 대신 봇 1만 개 돌리기

Part 3. 더미 클라이언트, 어디까지 발전했어?

그냥 접속만 하는 봇이야?

초창기엔 그랬어. 근데 지금은 AI처럼 행동하는 봇까지 발전했어.

단계별로 보자:

Level 1
접속만 하는 봇
TCP 연결 + 로그인만 → "동시 접속자 수" 테스트
// Level 1: 접속만 for (int i = 0; i < 10000; i++) { Connect("game.server.com", 9000); SendPacket(CM_LOGIN, { userId: "bot_" + i }); // 그냥 연결 유지 }

검증: 서버가 1만 연결을 버티는가?

Level 2
기본 플로우 봇
로그인 → 캐릭터 선택 → 월드 입장까지
// Level 2: 기본 플로우 SendPacket(CM_LOGIN); WaitForPacket(SM_LOGIN_OK); SendPacket(CM_SELECT_CHARACTER, { charId: 1 }); WaitForPacket(SM_CHARACTER_INFO); SendPacket(CM_ENTER_WORLD); WaitForPacket(SM_WORLD_ENTER_OK); // 입장 후 대기

검증: 로그인~입장 플로우가 정상 작동하는가?

Level 3
단순 반복 봇
한 가지 행동을 무한 반복 (이동, 공격)
// Level 3: 단순 반복 while (true) { // 랜덤 이동 SendPacket(CM_MOVE, { x: currentX + Random(-10, 10), y: currentY + Random(-10, 10) }); Sleep(100); // 100ms마다 }

검증: 이동 패킷 처리 성능, 브로드캐스트 부하

Level 4
시나리오 스크립트 봇
미리 정의된 시나리오를 순서대로 실행
// Level 4: 시나리오 기반 scenario = [ { action: "move_to", target: "던전 입구" }, { action: "enter_dungeon", dungeonId: 101 }, { action: "kill_monsters", count: 10 }, { action: "pickup_items" }, { action: "exit_dungeon" }, { action: "sell_items_to_npc" }, { action: "repeat" } ]; foreach (step in scenario) { Execute(step); WaitForComplete(); }

검증: 던전 플로우, NPC 상호작용, 아이템 시스템

Level 5
확률 기반 행동 봇
실제 유저 데이터 기반 행동 분포 시뮬레이션
// Level 5: 확률 기반 (실제 유저 분포 재현) behaviorDistribution = { "hunting": 40%, // 40%는 사냥 "moving": 25%, // 25%는 이동 "dungeon": 15%, // 15%는 던전 "trading": 10%, // 10%는 거래/상점 "afk": 10% // 10%는 방치 }; while (true) { behavior = WeightedRandom(behaviorDistribution); switch (behavior) { case "hunting": FindNearestMonster(); Attack(); LootItems(); break; case "dungeon": EnterRandomDungeon(); ClearDungeon(); break; // ... } }

검증: 실제 라이브 환경과 유사한 부하 패턴

Level 6 (최신)
AI 기반 자율 행동 봇
상황 판단 + 목표 기반 행동 + 예외 처리
// Level 6: AI 행동 트리 / FSM class AIBot { void Update() { // 상황 인식 if (hp < 30%) { UsePotion(); if (noPotion) FleeToSafeZone(); } else if (nearbyEnemy && enemyTargetingMe) { if (CanWin(enemy)) Attack(enemy); else CallForHelp(); } else if (inventoryFull) { GoToNearestNPC(); SellJunkItems(); } else if (questAvailable) { AcceptQuest(); ExecuteQuestObjective(); } else { Explore(); // 목표 없으면 탐험 } } }

검증: 예외 상황, 엣지 케이스, 복잡한 상호작용

💡 진보된 더미 클라이언트의 특징

NCSOFT, Nexon 급 회사들:
- Level 5~6 수준의 더미 클라이언트
- 실제 라이브 로그 기반 행동 패턴 학습
- 신규 컨텐츠 자동 테스트 (퀘스트, 던전)
- 밤새 수만 봇 자동 실행 → 아침에 리포트 확인

Part 4. 더미 클라이언트 돌리면 뭘 봐?

봇 1만 개 돌렸어. 이제 뭘 확인해?

핵심 지표 4가지:

TPS
초당 트랜잭션 수
(Transactions Per Second)
Latency
응답 시간
(P95, P99)
CCU
동시 접속자 수
(Concurrent Users)
Error Rate
에러율
(타임아웃, 실패)
TPS가 뭐야?

초당 처리한 요청 수

TPS 측정 예시: 1초 동안: - 이동 패킷 처리: 5,000건 - 공격 패킷 처리: 2,000건 - 아이템 사용: 500건 - 채팅: 300건 ───────────────────── 총 TPS: 7,800 Q. TPS가 높으면 좋은 거야? A. ㅇㅇ. 서버가 많은 요청을 처리할 수 있다는 뜻. Q. TPS가 떨어지면? A. 병목 발생! CPU, DB, 네트워크 중 하나가 한계.
Latency P95, P99가 뭐야?

상위 5%, 상위 1%의 응답 시간

1000개 요청의 응답 시간 (정렬): 요청 1~950: 10ms ~ 50ms (95%) 요청 951~990: 51ms ~ 100ms (4%) 요청 991~1000: 101ms ~ 500ms (1%) 평균: 45ms P95: 50ms ← 95%의 요청은 50ms 이내 P99: 100ms ← 99%의 요청은 100ms 이내 Q. 왜 평균 말고 P95, P99를 봐? A. 평균은 "대부분 빠르고 일부 엄청 느림"을 숨겨. P99가 높으면 1%는 렉 걸린다는 뜻!
서버 리소스는 어떻게 봐?
지표 정상 위험 의미
CPU < 70% > 90% 게임 로직 처리 한계
메모리 안정적 계속 증가 메모리 누수 의심
DB 커넥션 < 80% 100% + 대기 커넥션 풀 부족
네트워크 < 70% > 90% 대역폭 한계

Part 5. 구체적으로 뭘 검사해?

부하 테스트로 찾을 수 있는 문제가 뭐야?

출시 전에 반드시 찾아야 할 것들:

1. 메모리 누수 (Memory Leak) ───────────────────────────── 증상: 시간이 지날수록 메모리 사용량 증가 테스트: 봇 1000개로 24시간 돌리기 시작: 2GB 1시간: 2.5GB 4시간: 4GB 8시간: 6GB ← 누수 확정! 원인 예시: - 로그아웃 시 세션 객체 미해제 - 몬스터 사망 시 AI 객체 미해제 - 패킷 버퍼 재사용 안 함
2. DB 병목 (Database Bottleneck) ───────────────────────────── 증상: 부하 증가 시 응답 시간 급증 CCU 1000: 응답 50ms CCU 3000: 응답 80ms CCU 5000: 응답 200ms CCU 7000: 응답 2초 ← DB 한계! 찾는 법: - 슬로우 쿼리 로그 확인 - 커넥션 풀 대기 시간 모니터링 - 인덱스 미사용 쿼리 탐지
3. 브로드캐스트 폭발 (Broadcast Storm) ───────────────────────────── 증상: 특정 지역에 유저 몰리면 렉 평소: 100명 분산 → 정상 이벤트: 100명 한 곳 집중 → 서버 멈춤 이유: - 1명 이동 → 주변 99명에게 브로드캐스트 - 100명 이동 → 100 × 99 = 9,900 패킷/틱 - O(n²) 폭발! 테스트: 봇 100개를 같은 좌표에 모으기
4. 동시성 버그 (Race Condition) ───────────────────────────── 증상: 부하 높을 때만 간헐적 에러 테스트 방법: - 봇 100개가 동시에 같은 아이템 구매 - 봇 100개가 동시에 같은 보스 공격 - 봇 100개가 동시에 파티 신청 발견 가능한 버그: - 아이템 복사 (재화 버그) - 데드락 - 데이터 정합성 깨짐
5. 최대 수용 인원 (Capacity) ───────────────────────────── 질문: 서버 1대에 몇 명까지 가능? 테스트: CCU 1000 → P95: 30ms ✅ CCU 3000 → P95: 45ms ✅ CCU 5000 → P95: 80ms ✅ CCU 7000 → P95: 150ms ⚠️ CCU 8000 → P95: 300ms ⚠️ CCU 9000 → P95: 800ms ❌ 에러 발생 결론: 이 서버는 CCU 7000이 한계 → 출시 시 서버 대수 계획 가능

Part 6. 실제로 어떤 상황을 테스트해?

게임에서 서버가 터지는 순간은 언제야?

실제 장애 사례 기반 테스트:

시나리오 1: 자정 던전 리셋 동시 입장

시간: 23:59:55 [유저 5000명] "5... 4... 3... 2... 1..." │ ▼ 시간: 00:00:00 │ ▼ [던전 입장 요청 5000개 동시 발생] │ ▼ [서버] - 던전 인스턴스 5000개 생성? - DB 기록 5000건 동시 INSERT? - 몬스터 스폰 5000 × 20마리? → 테스트 필수!

시나리오 2: 월드 보스 100명 동시 공격

[월드 보스 HP: 1억] │ ┌────┴────┐ ▼ ▼ [유저 100명] [유저 100명] 스킬 시전 스킬 시전 │ │ ▼ ▼ [데미지 계산 200회/초] │ ▼ [브로드캐스트] - 보스 HP 변경 → 200명에게 - 각 유저 데미지 표시 → 200명에게 - 스킬 이펙트 → 200명에게 │ ▼ 200 × 200 × 3 = 120,000 패킷/초 → 이거 버티는지 테스트!

시나리오 3: 출퇴근 시간 동시 로그인

[평소] 08:00 - CCU 1000 09:00 - CCU 1500 ... [문제 상황: 점검 후 오픈] 10:00 - 점검 종료 10:00:01 - 로그인 시도 50,000건 │ ▼ [로그인 서버] - 인증 처리 50,000건 - DB 조회 50,000건 - 세션 생성 50,000건 - 캐릭터 정보 로드 50,000건 │ ▼ 처리 시간: 1건당 100ms 총 소요: 5,000,000ms = 83분??? → 로그인 큐, 동시 처리 한계 테스트!

Part 7. 매번 수동으로 해?

출시 전에 한 번만 하면 돼?

아니! 코드 바뀔 때마다 해야 해.

자동화가 필요한 이유: 월요일: 개발자 A가 아이템 코드 수정 화요일: 개발자 B가 전투 로직 수정 수요일: 개발자 C가 DB 쿼리 수정 → 각각은 "기능 테스트 통과" → 합치면? 성능 저하 가능성! 자동화: - 매일 새벽 자동 실행 (봇 5000개, 2시간) - 아침에 리포트 확인 - 성능 저하 시 알람
어떻게 자동화해?
# 부하 테스트 자동화 파이프라인 # 1. 테스트 환경 준비 (AWS/GCP) terraform apply -var="bot_count=5000" # 2. 더미 클라이언트 배포 ansible-playbook deploy-bots.yml # 3. 테스트 실행 (2시간) ./run_load_test.sh \ --bots 5000 \ --duration 2h \ --scenario "normal_play" # 4. 결과 수집 python collect_metrics.py \ --prometheus http://monitoring:9090 \ --output results/ # 5. 리포트 생성 python generate_report.py results/ \ --threshold-p95 100ms \ --threshold-error 1% # 6. 슬랙 알림 if [ $RESULT == "FAIL" ]; then curl -X POST $SLACK_WEBHOOK \ -d '{"text":"부하 테스트 실패!"}' fi # 7. 환경 정리 terraform destroy

📌 핵심 정리: 게임 서버 부하 테스트

  • k6, Locust는 HTTP용 → 게임은 TCP 지속 연결이라 안 맞음
  • 더미 클라이언트 = 진짜 유저처럼 행동하는 봇
  • 발전 단계: 접속만 → 기본 플로우 → 반복 → 시나리오 → 확률 기반 → AI
  • 측정 지표: TPS, Latency(P95/P99), CCU, Error Rate
  • 검사 항목: 메모리 누수, DB 병목, 브로드캐스트 폭발, 동시성 버그
