세마포어 vs 뮤텍스

둘 다 락인데 뭐가 다를까? 소유권의 비밀

흔한 오해: "세마포어 = 여러 개 들어갈 수 있는 뮤텍스"?

많은 사람들이 이렇게 알고 있다:

  • 뮤텍스: 1개 스레드만 진입
  • 세마포어: N개 스레드 진입 가능 (count 설정)
그럼 바이너리 세마포어(count=1)는 뮤텍스랑 같은 거 아니야?
→ 아니다! 핵심적인 차이가 있다.

스캐폴딩으로 차이점 발견하기

Q1. 뮤텍스를 잠근 스레드 A가 있어. 스레드 B가 그 뮤텍스를 해제할 수 있을까? 
스레드 A: Lock(mutex)
스레드 A: // 작업 중...
스레드 B: Unlock(mutex)  // ← 이거 가능?
A1. 불가능!
뮤텍스는 "누가 잠갔는지" 기억한다. 본인만 풀 수 있다.
Q2. 그럼 세마포어(count=1)로 같은 상황. 스레드 A가 Wait 했는데, 스레드 B가 Signal하면? 
세마포어 count = 1

스레드 A: Wait(sem)   // count: 1 → 0, 진입
스레드 A: // 작업 중...
스레드 B: Signal(sem) // ← 이거 가능?
A2. 가능!
세마포어는 "누가 Wait했는지" 기억 안 한다. 그냥 숫자만 관리한다. 
스레드 A: Wait(sem)   // count: 1 → 0
스레드 A: // 작업 중...
스레드 B: Signal(sem) // count: 0 → 1 ← 성공!
스레드 C: Wait(sem)   // count: 1 → 0, 진입 가능!
스레드 A가 아직 작업 중인데 C가 들어와버림!

핵심 차이: 소유권

뮤텍스 세마포어
소유권 있음 없음
Lock/Wait 스레드 A 스레드 A
Unlock/Signal 스레드 A만 아무나

그럼 세마포어는 언제 쓸까?

Q3. "아무나 Signal 가능"한 특성이 유용한 상황은?
힌트: 스레드 A가 "준비됐어!"라고 스레드 B에게 알려주고 싶을 때...

게임 서버 실제 예시: 패킷 처리

[네트워크 스레드] [게임 로직 스레드] 클라에서 패킷 옴 Wait(sem) ← 패킷 올 때까지 잠듦 큐에 패킷 넣음 💤 (CPU 안 씀) Signal(sem) ─────────────→ 깨어남! 큐에서 패킷 꺼내서 처리

왜 뮤텍스로는 안 될까?

[뮤텍스로 하면] while(true) { Lock(mutex) // 아무도 안 잡고 있음 → 바로 통과 if(큐 비었음) // 패킷 없네 Unlock(mutex) // 풀고 // → 다시 Lock → 통과 → 확인 → 없음 → 풀고... // 무한 반복. CPU 100%. } [세마포어로 하면] while(true) { Wait(sem) // 신호 올 때까지 잠듦. CPU 0% ProcessPacket(); // 신호 왔다 = 패킷 있다 }
핵심 차이:
• 뮤텍스 Lock: "다른 놈이 잡고 있으면" 대기
• 세마포어 Wait: "count=0이면" 대기

뮤텍스는 아무도 안 잡고 있으면 바로 통과해버림!

바이너리 세마포어의 진짜 용도

Q4. count=0으로 시작하면? 
세마포어 count = 0  ← 처음부터 0!

[게임 로직 스레드]
Wait(sem)  → count가 0이네? → ???
A4. 바로 잠든다!
첫 번째 스레드도 들어가지 못하고 신호가 올 때까지 대기한다.

게임 로딩 예시

바이너리 세마포어 count = 0 (신호 없음) [메인 스레드] [로딩 스레드] "로딩 화면 띄움" Wait(sem) ← 대기 리소스 로딩 중... ... 로딩 완료! ... Signal(sem) ──→ 신호 보냄! 깨어남! 게임 시작

핵심: 로딩 스레드가 Wait 안 했는데 Signal 함.
→ 뮤텍스론 불가능 (본인이 Lock 안 했으면 Unlock 못함)

비유로 정리

뮤텍스 = 화장실 열쇠

너가 열쇠로 문 잠금 → 너만 열 수 있음 친구가 "나 대신 열어줄게" → 안 됨, 열쇠 없음

세마포어 = 초인종

너: 집에서 초인종 기다림 (Wait) 배달원: 초인종 누름 (Signal) 너: 딩동! 문 열고 받음 배달원은 너 집에 들어간 적 없어. 그냥 "왔어!" 알려준 것뿐.

실측 테스트 결과

테스트 1: 소유권 차이

[Mutex] Thread A: Lock → 획득 Thread B: Unlock 시도 → FAILED! error=288 (ERROR_NOT_OWNER) Thread A: Unlock → Success! [Semaphore] Thread A: Wait → 획득 (count: 1→0) Thread C: Signal 시도 → Success! (count: 0→1) → 아무나 Signal 가능!

테스트 2: 신호 대기 패턴

[Semaphore - count=0으로 시작] Waiter: Wait()... → 바로 잠듦 Signaler: 1초 후 Signal! Waiter: 깨어남! (대기 시간: 1004 ms) [Mutex로는?] → count=0 개념 없음 → 아무도 안 잡고 있으면 바로 통과 → '신호 올 때까지 대기' 불가능!

테스트 3: CPU 사용량

[Mutex 폴링] 2초 동안 루프 횟수: 4,029,467회 → CPU 풀가동! [Semaphore 대기] Wait 횟수: 1회 → CPU 0%! [비교] 400만 번 vs 1번 - 이게 차이다!

테스트 4: 생산자-소비자

[3 Producers, 1 Consumer] Producer1: Signal! → Consumer: 처리! Producer2: Signal! → Consumer: 처리! Producer3: Signal! → Consumer: 처리! ... 총 처리: 9개 → 소비자는 생산될 때만 깨어남!

용도별 정리

용도 뭘 써? 이유
데이터 보호 (한 놈만 들어와) 뮤텍스 소유권으로 안전하게 보호
신호 전달 (야 끝났어!) 바이너리 세마포어 다른 스레드가 깨워줄 수 있음
리소스 제한 (N명만 들어와) 카운팅 세마포어 커넥션 풀, 동시 접속 제한
Windows에서는?
신호 전달 용도로 Event 객체를 따로 제공한다.
CreateEvent, SetEvent, WaitForSingleObject

핵심 정리

  • 뮤텍스 = 소유권 있음 → 잠근 놈만 풀 수 있음 → 보호용
  • 세마포어 = 소유권 없음 → 아무나 Signal 가능 → 신호용
  • 바이너리 세마포어 ≠ 뮤텍스 (count=1이어도 다른 물건)
  • count=0 시작 = 신호 올 때까지 대기하는 패턴
  • 폴링 vs 대기 = 400만 회 vs 1회 (CPU 효율 차이)
