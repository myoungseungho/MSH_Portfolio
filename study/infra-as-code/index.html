Part 1. Infrastructure as Code가 뭐야?

인프라를 코드로? 무슨 말이야?

서버, 네트워크, 데이터베이스 같은 인프라를 코드 파일로 정의하는 거야.

비유: 레시피

요리할 때 레시피 적어두잖아?
"밥 2공기, 계란 3개, 간장 2스푼"

IaC도 똑같아:
"서버 2대, 메모리 8GB, 서울 리전"

레시피대로 만들어줘! 하면 알아서 만들어줌!
왜 필요해? AWS 콘솔에서 클릭하면 되잖아

실제 사례를 보자:

실제 발생한 문제 (데브시스터즈 사례)

어느 날 발견: 내부망에서만 열려야 하는 서버가 외부 전체에 오픈되어 있었음!

물어보니: "구글에서 테스트해보려고 잠깐 열었어요"

문제:
- 누가 바꿨는지 추적 안 됨
- 실수인지 의도인지 알 수 없음
- 다른 서버는 괜찮은지 확인 불가
문서화하면 되지 않아?

문서화의 한계:

문서화 IaC (코드)
바쁘면 안 씀 코드 = 문서
실제와 다를 수 있음 실제 상태와 항상 일치
한 명이 안 쓰면 전체 불신 모든 변경이 Git에 기록
검색 어려움 Ctrl+F로 검색

Part 2. Terraform - 인프라 정의하기

Terraform이 뭐야?

Terraform은 "인프라의 최종 상태"를 코드로 정의하는 도구야.

HashiCorp에서 만든 오픈소스!

비유: 네비게이션

- 네비에 목적지만 입력하면? → 알아서 길 찾아줌
- 현재 위치가 어디든 상관없이 목적지까지 안내

Terraform도 똑같아:
- "서버 5대 있어야 해"라고 정의
- 현재 3대? → 2대 추가
- 현재 7대? → 2대 삭제
- 현재 5대? → 변경 없음
코드가 어떻게 생겼어?

간단한 예시:

# main.tf - EC2 서버 1대 만들기 # AWS 프로바이더 설정 provider "aws" { region = "ap-northeast-2" # 서울 리전 } # EC2 인스턴스 정의 resource "aws_instance" "game_server" { ami = "ami-12345678" # 운영체제 이미지 instance_type = "t3.medium" # 서버 사양 tags = { Name = "game-server-1" } }
이걸 어떻게 실행해?

명령어 2개만 알면 돼:

[Terraform 기본 명령어] # 1. 미리보기 (실제로 생성 안 함) terraform plan # 출력 예시: # + aws_instance.game_server will be created # + ami = "ami-12345678" # + instance_type = "t3.medium" # # Plan: 1 to add, 0 to change, 0 to destroy. # 2. 실제 적용 terraform apply # "Do you want to perform these actions?" # yes 입력하면 실제로 AWS에 서버 생성!
서버 5대 만들려면 복붙해야 해?

아니! count 쓰면 돼:

# 게임 서버 5대 만들기 resource "aws_instance" "game_server" { count = 5 # ← 이것만 바꾸면 됨! ami = "ami-12345678" instance_type = "t3.medium" tags = { Name = "game-server-${count.index}" # 0, 1, 2, 3, 4 } } # 결과: game-server-0, game-server-1, ... game-server-4 생성!
서버끼리 연결도 알아서 해줘?

자동 의존성 처리!

# 서버 생성 resource "aws_instance" "game_server" { ami = "ami-12345678" instance_type = "t3.medium" } # DNS 레코드 (서버 IP 필요) resource "aws_route53_record" "game_dns" { name = "game.example.com" type = "A" records = [aws_instance.game_server.private_ip] # ← 자동 참조! } # Terraform이 알아서 순서 파악: # 1. 먼저 서버 생성 (IP 필요하니까) # 2. IP 받으면 DNS 레코드 생성

Part 3. Terraform 실전 활용

AWS만 되는 거야?

아니! 수백 개 프로바이더 지원:

[Terraform 지원 서비스] 클라우드: ├── AWS ├── Google Cloud ├── Azure ├── 네이버 클라우드 └── DigitalOcean 모니터링: ├── Datadog ├── New Relic └── PagerDuty 기타: ├── GitHub (저장소, 팀 관리) ├── Cloudflare (DNS, CDN) └── 수백 개 더...
Datadog 대시보드도 코드로?

응! 서버 만들 때 쓴 변수를 그대로 재활용:

# 게임 서버 resource "aws_instance" "game_server" { count = 5 tags = { Name = "game-server-${count.index}" } } # Datadog 모니터링 (같은 이름 사용!) resource "datadog_monitor" "cpu_alert" { name = "CPU Alert - ${aws_instance.game_server[0].tags.Name}" type = "metric alert" query = "avg:aws.ec2.cpu{name:game-server-*} > 80" message = "CPU 80% 초과! @slack-game-alerts" } # 장점: 서버 이름 바꾸면 모니터링도 자동으로 바뀜!
IaC의 핵심 장점

1. 검색: "5000번 포트 열린 서버 찾기" = Ctrl+F
2. 리뷰: 인프라 변경도 PR로 코드 리뷰
3. 히스토리: Git log로 누가, 언제, 왜 바꿨는지 추적
4. 롤백: git revert로 이전 상태 복구

Part 4. Packer - 서버 이미지 만들기

서버 띄울 때마다 설치해야 하는 거 귀찮지 않아?

기존 방식의 문제:

[기존 서버 세팅 과정] 새 서버 시작 ↓ SSH 접속 ↓ Java 설치 (5분) ↓ Docker 설치 (3분) ↓ 모니터링 에이전트 설치 (2분) ↓ 설정 파일 복사 (1분) ↓ 드디어 게임 서버 시작! = 총 10분+ 소요 = 서버 100대면 100번 반복?!
Packer가 뭘 해결해줘?

Packer는 "미리 다 설치된 이미지"를 만들어주는 도구야.

비유: 노턴 고스트 (PC방 복원)

옛날 PC방 가면 컴퓨터 껐다 켜면 원래대로 돌아왔잖아?
- 깨끗하게 세팅된 상태를 이미지로 저장해둔 거야

Packer도 똑같아:
- Java, Docker, 모니터링 다 설치된 상태를
- "서버 이미지"로 구워두는 거야
- 새 서버 시작하면? 이미 다 설치되어 있음!
[Packer 사용 후] Packer로 미리 구운 이미지: ┌────────────────────────┐ │ Ubuntu 22.04 │ │ + Java 17 │ │ + Docker │ │ + Datadog Agent │ │ + 기본 설정 파일 │ └────────────────────────┘ 새 서버 시작: 미리 구운 이미지 → 바로 게임 서버 실행! = 1~2분 만에 서비스 가능!
Packer 코드는 어떻게 생겼어?

JSON 또는 HCL 형식:

# game-server.pkr.hcl source "amazon-ebs" "game-server" { ami_name = "game-server-{{timestamp}}" instance_type = "t3.medium" region = "ap-northeast-2" source_ami_filter { filters = { name = "ubuntu/images/*ubuntu-jammy-22.04*" } owners = ["099720109477"] # Canonical } } build { sources = ["source.amazon-ebs.game-server"] # Java 설치 provisioner "shell" { inline = ["apt-get update", "apt-get install -y openjdk-17-jdk"] } # Docker 설치 provisioner "shell" { script = "scripts/install-docker.sh" } # 모니터링 에이전트 provisioner "shell" { script = "scripts/install-datadog.sh" } }
# 이미지 빌드 packer build game-server.pkr.hcl # 결과: ami-xxxxxxxxx 이미지 생성! # 이 AMI를 Terraform에서 사용하면 됨

Part 5. Vault - 비밀 안전하게 관리하기

DB 비밀번호는 어디에 저장해?

잘못된 방법들:

비밀번호 관리의 문제

1. 코드에 직접 작성
→ 유출되면 큰일!

2. 환경변수로 저장
→ 서버마다 설정 필요, 관리 어려움

3. 설정 파일로 저장
→ 누군가 퇴사하면? 모든 비밀번호 바꿔야 함!
Vault가 뭘 해결해줘?

Vault는 "권한이 있으면 비밀번호를 내려주는" 금고야.

비유: 회사 금고

회사에 금고가 있어. 열쇠(권한)가 있는 사람만 열 수 있어.

근데 열쇠가 도난당하면? 금고 비밀번호를 바꿔야지.

Vault는 더 똑똑해:
- "이 사람이 진짜 직원인지" AWS가 보증해줌
- 서버가 "나 진짜 AWS 서버야!" 증명하면 비밀번호 줌
- 개발자 PC에서는? AWS 서명이 없으니까 안 줌!
[Vault 동작 방식] AWS 서버에서 실행: 1. 서버: "나 AWS 서버야. 이게 내 서명이야." (PKCS 서명) 2. Vault: Amazon 공개키로 검증... "진짜네!" 3. Vault: "여기 DB 비밀번호야." 4. 서버: 비밀번호로 DB 접속! 개발자 PC에서 실행: 1. PC: "나도 비밀번호 줘!" 2. Vault: "AWS 서명 없잖아. 안 줘!" → 비밀번호 유출 방지!
코드에는 뭘 써?

비밀번호 경로만 쓰면 돼:

# 코드에 작성하는 것 database_password = vault("secret/game/database/password") # 실제 비밀번호는? # → Vault가 런타임에 주입해줌! # → 코드에 비밀번호가 없으니 유출 걱정 없음!
Vault의 추가 기능

1. SSH Certificate
개인 SSH 키에 Vault가 서명 → 24시간 동안만 서버 접근 가능
퇴사하면? 서명 안 해주면 끝!

2. Dynamic Secret
DB 접속용 일회용 계정 생성
퇴사하면? 그 계정 자동 폐기!

Part 7. 정리: IaC 3종 세트

Terraform

역할: 인프라 정의 및 생성

비유: "최종 상태를 선언하면 알아서 만들어줌"

사용: 서버, 네트워크, DB, DNS 등 모든 인프라

Packer

역할: 서버 이미지 빌드

비유: "세팅 완료된 PC를 복제"

사용: AMI, 도커 베이스 이미지 등

Vault

역할: 비밀 관리

비유: "권한 있는 사람만 여는 금고"

사용: DB 비밀번호, API 키, SSH 인증서

[IaC 워크플로우 전체] 1. Packer로 베이스 이미지 생성 "Java, Docker 설치된 Ubuntu 이미지" 2. Terraform으로 인프라 정의 "이 이미지로 서버 5대, 서울 리전" 3. Vault로 비밀 관리 "서버가 시작되면 DB 비밀번호 주입" 4. Git으로 버전 관리 "모든 변경 기록 + 코드 리뷰" 5. CI/CD로 자동 적용 "PR 머지되면 자동으로 terraform apply"

핵심 정리

  • IaC - 인프라를 코드로 정의. 수동 작업의 추적 불가 문제 해결
  • Terraform - 선언적 인프라 관리. "이 상태 유지해!"
  • Packer - 서버 이미지 빌드. 부팅 시간 단축 + 일관성
  • Vault - 비밀 관리. AWS 인증 기반 자동 주입
  • Git = 기록 - 누가, 언제, 왜 바꿨는지 전부 추적
  • 코드 = 문서 - 별도 문서화 불필요, Single Source of Truth
