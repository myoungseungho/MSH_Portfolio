인프라도 코드로? Packer, Terraform, Vault

재현 가능한 게임 인프라 구축 - 데브시스터즈 NDC 발표 정리

Infrastructure as Code Terraform Packer Vault AWS DevOps

Part 1. 수동으로 인프라 관리하면 왜 문제야?

AWS 콘솔에서 클릭클릭하면서 서버 띄우면 안 돼?

쿠키런 시절에 그렇게 했어. 가장 많이 쓴 버튼이 "Launch More Like This" - 인스턴스 복제해서 설정만 살짝 바꿔서 띄우는 거였지.

그게 뭐가 문제야? 잘 돌아가잖아.

어느 날 발견했어. 어떤 서버가 내부망에서만 열려야 하는데, 전체 외부에서 접근 가능하게 열려 있었어.

물어보니까 "구글에서 테스트해보려고 글로벌 오픈했다"는 답변이...

수동 관리의 치명적 문제들

- 사람의 실수: 실수가 있어도 알아차리기 어려움
- 추적 불가: 누가 뭘 했는지 트래킹이 안 됨
- 의도 파악 불가: 이게 실수인지 의도인지 알 수 없음
- 두려움: "지금 잘 돌아가는 거 건드리면 어떻게 될지 모르니까 안 건드리자"
문서화 열심히 하면 되지 않아?

문서화의 한계가 있어.

바쁘면 뒷전으로 밀리고, 의도대로 썼는데 실제 동작이 다를 수 있고, 한 명이라도 문서를 안 쓰면 전체 문서를 못 믿게 돼.

Part 2. 게임이 여러 개면 어떻게 해?

쿠키런 하나일 때는 그래도 버틸 만했어?

응, 어떻게든 버텼지. 근데 문제는 이거야:

쿠키런 포 카카오 (하나일 때) -> 어떻게든 버틸 만함 쿠키런 오븐브레이크 + 여러 게임들 + 사내 공용 서비스 + 각 게임 툴 -> 버틸 수가 없음! 해외 서비스 준비 -> 비슷한 인프라를 지역만 바꿔서 띄워야 함 -> 했던 일을 또 반복...
대기업처럼 오퍼레이션 팀 따로 두면 안 돼?

서버 팀 규모가 20명 정도인데, 개발에서 손 떼고 오퍼레이션만 맡긴다?

솔직히 손이 떨려.

그래서 "인프라를 코드로 만들어야겠다"는 생각이 들었어.

Part 3. Terraform이 뭐야?

인프라를 코드로 만든다는 게 무슨 말이야?

Terraform이라는 도구가 있어. HashiCorp에서 만든 오픈소스야.

"나는 인프라의 최종 상태가 이렇게 되길 원해"를 코드로 정의하는 거야.

resource "aws_instance" "sample" { ami = "ami-12345678" instance_type = "t2.micro" tags = { Name = "sample-server" } }
레시피 비유

요리할 때 레시피 적어두잖아?
"밥 2공기, 계란 3개, 간장 2스푼"

Terraform도 똑같아. "EC2 1대, t2.micro, 서울 리전"
레시피대로 만들어줘! 하면 알아서 만들어줌.
그래서 어떻게 실행해?

두 가지 명령어만 알면 돼:

terraform plan -> "미리보기" - 뭐가 바뀔지 보여줌 (Dry-run) terraform apply -> "실행" - 실제로 인프라에 적용
DNS 레코드가 인스턴스 IP를 참조해야 하면? 인스턴스가 먼저 만들어져야 IP 알 수 있잖아.

Terraform이 자동으로 순서 파악해!

각 리소스별로 선행 작업이 뭔지 분석해서 순서대로 생성해.

# DNS 레코드가 인스턴스의 IP를 자동으로 참조 resource "aws_route53_record" "sample" { name = "sample.devsisters.com" type = "A" records = [aws_instance.sample.private_ip] # <- 자동 의존성! }
서버 여러 대 띄우려면 복붙해야 해?

아니, count 쓰면 돼. 프로그래밍의 반복문이랑 같아.

resource "aws_instance" "sample" { count = 3 ami = "ami-12345678" instance_type = "t2.micro" tags = { Name = "sample-${count.index}" } } # 결과: sample-0, sample-1, sample-2 인스턴스 3대 생성
프로그래밍과의 유사점
  • 리소스 참조 = 변수 참조
  • count = 반복문
  • 모듈 = 함수 정의

Part 4. 코드로 만들면 뭐가 좋아?

그래서 실질적으로 뭐가 달라져?

모든 변경이 커밋으로 관리돼!

인프라의 모든 변경 사항이 Git 커밋 로그로 남아.

활용 어떻게?
검색 "5000번 포트 열린 인스턴스 찾기" = 저장소에서 Ctrl+F
의도 파악 커밋 메시지에 작업자의 의도가 담겨있음
코드 리뷰 인프라 변경도 PR로 리뷰 가능
히스토리 Git log로 변경 이력 추적
AWS만 되는 거야?

아니! 수백 개의 프로바이더를 지원해.

Terraform이 지원하는 프로바이더: - AWS - Google Cloud Platform - Azure - DigitalOcean - 네이버 클라우드 - Datadog (모니터링!) - 그 외 수백 개...
Datadog 같은 모니터링 도구도 Terraform으로?

대시보드도 코드로!

인스턴스 만들 때 쓴 변수들(서버 이름, 리전 등)을 그대로 모니터링 대시보드에 재활용할 수 있어서 구축이 훨씬 편해.

Part 5. Packer는 뭐야?

서버 이미지(AMI) 만드는 게 왜 귀찮아?

이 과정을 봐봐:

1. 인스턴스 생성 2. SSH 접속 3. 필요한 유틸리티 설치 (Java, Docker, 모니터링 도구...) 4. 스냅샷 생성 5. 정리 -> 매번 이 과정을 반복? 미쳐!
수동 이미지 생성의 문제

- 이미지에 뭐가 들어있는지 파악 안 됨
- 변경사항 트래킹 안 됨
- SSH 키 설정, 방화벽 설정 등 잡다한 작업이 매번 필요
Packer가 뭘 해결해주는 건데?

Packer는 벤더 제공 이미지에 커스터마이즈를 해서 우리만의 부팅 디스크를 만드는 도구야.

노턴 고스트 비유

옛날에 PC방에서 "노턴 고스트"로 컴퓨터 복원하던 거 기억나?
깨끗하게 세팅된 상태를 "세이브 포인트"로 찍어두는 거야.

Packer도 똑같아. 필요한 거 다 설치된 서버를 이미지로 구워두는 거지.
이미지 미리 굽는 게 왜 좋아?

부팅 속도가 엄청 빨라져!

기존 방식: Ubuntu Base -> Java 설치 -> 모니터링 도구 설치 -> Docker 설치 -> 게임 서버 시작 = 오래 걸림 (5~10분) Packer 방식: 미리 구운 이미지 (Java, 모니터링, Docker 포함) -> 게임 서버 시작 = 빠름! (1~2분)
게임 서버 코드까지 이미지에 굽지는 않아?

이미지 스냅샷 만드는 데 5~7분 걸려.

프로덕션은 배포가 잦지 않아서 괜찮은데, 개발 서버는 Docker 이미지만 바뀌었는데 5분씩 기다리기 아까워.

그래서 Docker 이미지는 인스턴스 부팅 시 자동으로 받아오도록 구성했어.

데브시스터즈 베이스 이미지에 포함된 것들

- 개발자 SSH 접속용 CA 파일
- Docker 데몬
- Datadog 모니터링 에이전트
- 인스턴스 모니터링용 CLI 도구들

Part 6. Vault는 뭐야?

게임 서버 돌리려면 DB 비밀번호 같은 것도 필요하잖아. 어디에 저장해?

예전에는 Chef 코드 저장소에 전부 넣어뒀어.

코드에 시크릿을 넣으면?

- 유출되면 큰일
- 누군가 퇴사하면 모든 비밀번호를 바꿔야 함
- 회사가 커지면 입사/퇴사가 많아지는데, 그때마다 전체 시크릿 로테이션은 엄청난 작업
Vault가 뭘 해결해주는 건데?

Vault는 "적합한 권한이 있으면 시크릿을 내려주는" 키-밸류 스토어야.

금고 비유

회사 금고가 있어. 열쇠(권한)가 있는 사람만 열 수 있어.
근데 열쇠가 도난당하면? 금고 비밀번호를 바꿔야지.

Vault는 "이 사람이 진짜 직원인지"를 AWS가 보증해주는 방식을 써.
AWS가 보증한다는 게 무슨 말이야?

모든 AWS 인스턴스에는 PKCS 서명이 들어있어. Amazon의 Private Key로 서명된 거야.

AWS 인스턴스가 Vault에 요청: "내 PKCS 서명이야. 나 진짜 AWS 인스턴스 맞아. 권한 줘!" Vault가 Amazon Public Key로 검증: "이 서명이 진짜네. OK, 해당 권한의 토큰 내려줄게" -> 개발자가 로컬에서 실행하면? AWS 서명이 없으니 비밀번호 못 받음! -> EC2 인스턴스에서 실행하면? 자동으로 비밀번호 받아옴!
핵심 포인트

시크릿 "경로" 자체는 코드에 커밋해도 안전!
실제 비밀번호는 런타임에 Vault가 주입해주니까.
Vault로 또 뭘 할 수 있어?

엄청 많아!

기능 설명
SSH Certificate 개인의 SSH 키에 Vault가 서명 -> 24시간 동안 인프라 접근 가능. 입/퇴사 시 서버별 권한 설정 불필요!
Dynamic Secret DB 접근용 일회용 유저명/비밀번호 생성. 퇴사해도 그 유저 정보는 자동 폐기

Part 7. 도입하고 나서 뭐가 달라졌어?

실제로 효과가 있었어?

엄청났지!

Before (수동) After (코드)
실수가 있어도 알아차리기 어려움 코드 리뷰로 사전 검토
누가 뭘 했는지 추적 불가 Git 커밋 로그로 전체 이력 관리
문서화가 현실과 달라짐 코드 자체가 문서 (Single Source of Truth)
비밀번호가 코드에 노출 Vault가 런타임에 주입
환경 복제에 오랜 시간 terraform apply로 빠르게 복제
작업 분배도 달라졌어?

예전에는 "히스토리 아는 사람"에게 작업이 몰렸어.

이제는 코드만 보면 누구나 참여 가능해!

오픈소스 기여

"슬프게도" 많이 기여하게 돼. 쓰다 보면 버그를 많이 발견해.
체감 51% 오픈소스 버그, 49% 내 실수 비율로 버그를 만나게 돼.
오픈소스라서 내부 구조 파악이 쉽고, 기여할 수 있는 부분도 많아.

Part 8. 아직 해결 못한 것도 있어?

완벽한 건 아니겠지?

당연히 남은 과제들이 있어.

레거시 마이그레이션

카카오 시절 인프라를 Terraform으로 못 옮겼어.
없는 걸 새로 만드는 것보다 있는 걸 옮겨오는 난이도가 훨씬 높아.
다른 교훈은?

이름 짓기가 중요해!

실수 사례: S3 버킷 이름을 "cookierun-ovenbreak-production"으로 만들었어. 나중에 US 리전에도 띄워야 하는 상황이 생겼는데... S3는 전 세계 네임스페이스를 공유해서 같은 이름을 쓸 수 없어! 교훈: 처음 이름 지을 때부터 바뀔 수 있는 모든 가능성 (리전, 환경, 버전 등)을 고려해서 이름을 지어야 해.
보안은 완벽해?

Vault로 시크릿을 받아오지만, 서버에 접근할 수 있으면 메모리 덤프 등으로 시크릿 추출은 가능해.

완전한 보안을 위해서는 애플리케이션 단의 구현도 필요해.

핵심 정리: Infrastructure as Code 3종 세트

  • Terraform - 인프라를 코드로 정의하고 버전 관리. "최종 상태를 선언하면 알아서 만들어줌"
  • Packer - 서버 이미지를 코드로 빌드. "부팅 속도 개선 + 이미지 내용 추적"
  • Vault - 시크릿을 안전하게 관리. "AWS 인증으로 자동 주입"
  • 코드 = 문서 - 별도 문서화 필요 없음. Single Source of Truth!
  • Git = 추적 - 누가, 언제, 왜 바꿨는지 전부 기록
  • 코드 리뷰 - 인프라 변경도 PR로 검토 가능
