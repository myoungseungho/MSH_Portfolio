1. 수동 인프라 관리의 한계

상황

쿠키런 시절, AWS를 쓰고 있었지만 모든 인프라 작업을 손으로 진행했습니다. 가장 많이 쓰던 버튼이 "Launch More Like This" - 인스턴스를 복제해서 설정만 살짝 바꿔서 띄우는 방식이었어요.

문제 발견

어떤 서버가 내부망에서만 열려야 하는데, 전체 외부에서 접근 가능하게 열려 있었어요. 물어보니 "구글에서 테스트해보려고 글로벌 오픈했다"는 답변이...

수동 관리의 문제들

문제 결과
사람의 실수 실수가 있어도 알아차리기 어려움
추적 불가 누가 뭘 했는지 트래킹이 안 됨
의도 파악 불가 이게 실수인지 의도인지 알 수 없음
두려움 "지금 잘 돌아가는 거 바꾸면 어떻게 될지 모르니까 안 건드리자"

질문

문서화를 하면 되지 않나요?

문서화의 한계

바쁘면 뒷전으로 밀리고, 의도대로 썼는데 실제 동작이 다를 수 있고, 한 명이라도 문서를 안 쓰면 전체 문서를 믿을 수 없게 됩니다.

2. 게임 라인업이 늘어나면?

쿠키런 포 카카오 (하나일 때) → 어떻게든 버틸 만함 쿠키런 오븐브레이크 + 여러 게임들 + 사내 공용 서비스 + 각 게임 툴 → 버틸 수가 없음! 해외 서비스 준비 → 비슷한 인프라를 지역만 바꿔서 띄워야 함 → 했던 일을 또 반복...

질문

대형 기업처럼 오퍼레이션 팀을 따로 두면 되지 않나요?

현실

서버 팀 규모가 20명 정도인데, 개발에서 손을 떼고 오퍼레이션만 맡긴다? 솔직히 손이 떨려요. 그래서 "인프라를 코드로 만들어야겠다"는 욕구가 생겼습니다.

3. Terraform - 인프라를 코드로

Terraform이란?

HashiCorp에서 만든 오픈소스 프로젝트. HCL(HashiCorp Configuration Language)이라는 자체 문법으로 원하는 인프라를 정의합니다.

기본 예제

resource "aws_instance" "sample" {
    ami           = "ami-12345678"
    instance_type = "t2.micro"

    tags = {
        Name = "sample-server"
    }
}

핵심 개념

Terraform의 접근 방식: "나는 인프라의 최종 상태가 이렇게 되길 원해"를 코드로 정의

Terraform이 현재 상태를 체크하고, 원하는 상태와 다르면 알아서 변경을 실행해줍니다.

워크플로우

1terraform plan

실제 인프라에 어떤 변화가 일어날지 미리 보기 (Dry-run)

2terraform apply

변경 사항을 실제 인프라에 적용

리소스 참조

# DNS 레코드가 인스턴스의 IP를 자동으로 참조
resource "aws_route53_record" "sample" {
    name    = "sample.devsisters.com"
    type    = "A"
    records = [aws_instance.sample.private_ip]
}

질문

인스턴스가 먼저 생성되어야 IP를 알 수 있는데, 순서는 어떻게 처리하나요?

자동 의존성 분석

Terraform이 각 리소스별로 선행 작업이 뭔지 자동으로 파악해서 순서대로 생성합니다. 한 번에 정의하고 한 번에 적용!

반복 생성 (count)

resource "aws_instance" "sample" {
    count         = 3
    ami           = "ami-12345678"
    instance_type = "t2.micro"

    tags = {
        Name = "sample-${count.index}"
    }
}
# 결과: sample-0, sample-1, sample-2 인스턴스 3대 생성

모듈화

# 모듈 정의 (재사용 가능한 템플릿)
module "game_server" {
    source = "./modules/game-server"

    name   = "cookie-run"
    region = "ap-northeast-2"
}
# 함수처럼 input을 받아서 output을 생성하는 구조

프로그래밍과의 유사점

리소스 참조 = 변수 참조

count = 반복문

모듈 = 함수 정의

4. 인프라 코드화의 장점

모든 변경이 커밋으로 관리된다

인프라의 모든 변경 사항이 Git 커밋 로그로 남습니다.

누가, 언제, 왜 바꿨는지 추적 가능!

활용 설명
검색 "5000번 포트 열린 인스턴스 찾기" = 저장소에서 Ctrl+F
의도 파악 커밋 메시지에 작업자의 의도가 담겨있음
코드 리뷰 인프라 변경도 PR로 리뷰 가능
히스토리 Git log로 변경 이력 추적

멀티 프로바이더 지원

Terraform이 지원하는 프로바이더: - AWS - Google Cloud Platform - Azure - DigitalOcean - 네이버 클라우드 - Datadog (모니터링) - 그 외 수백 개...

질문

Datadog 같은 모니터링 도구도 Terraform으로?

대시보드도 코드로!

인스턴스를 구축할 때 쓴 변수들(서버 이름, 리전 등)을 그대로 모니터링 대시보드 설정에 재활용할 수 있어서 구축이 훨씬 편해집니다.

5. Packer - 이미지 자동 생성

상황

서버 이미지(AMI)를 만들려면: 인스턴스 생성 -> SSH 접속 -> 필요한 유틸리티 설치 -> 스냅샷 생성 -> 정리... 이 과정이 굉장히 귀찮습니다.

수동 이미지 생성의 문제

이미지에 뭐가 들어있는지 파악 안 됨, 변경사항 트래킹 안 됨, SSH 키 설정/방화벽 설정 등 잡다한 작업이 매번 필요함

Packer란?

벤더 제공 이미지에 커스터마이즈를 해서 우리만의 부팅 디스크를 만드는 도구. 노턴 고스트처럼 "세이브 포인트"를 찍어두는 것!

이미지 미리 굽기의 장점

부팅 속도 개선: 기존 방식: Ubuntu Base -> Java 설치 -> 모니터링 도구 설치 -> Docker 설치 -> 게임 서버 시작 = 오래 걸림 Packer 방식: 미리 구운 이미지 (Java, 모니터링, Docker 포함) -> 게임 서버 시작 = 빠름!

실무 적용

데브시스터즈 전체 서버가 공통으로 사용할 베이스 이미지를 Packer로 굽기 시작:

- 개발자 SSH 접속용 CA 파일

- Docker 데몬

- Datadog 모니터링 에이전트

- 인스턴스 모니터링용 CLI 도구들

질문

게임 서버까지 이미지에 굽지 않나요?

이미지 빌드 시간 고려

이미지 스냅샷 만드는 데 5~7분 걸립니다. 프로덕션은 배포가 잦지 않아서 괜찮지만, 개발 서버는 Docker 이미지만 바뀌었는데 5분씩 기다리기 아깝습니다. 그래서 Docker 이미지는 인스턴스 부팅 시 자동으로 받아오도록 구성했습니다.

6. Vault - 비밀 관리

문제 상황

게임 서버가 실행되려면 DB 비밀번호, API 시크릿 같은 민감한 데이터가 필요합니다. 예전에는 이걸 Chef 코드 저장소에 전부 넣어뒀어요.

코드에 시크릿을 넣으면?

유출되면 큰일, 누군가 퇴사하면 모든 비밀번호를 바꿔야 함. 회사가 커지면 입사/퇴사가 많아지는데, 그때마다 전체 시크릿 로테이션은 엄청난 작업이 됩니다.

Vault란?

사용자가 적합한 권한을 갖고 있으면 시크릿을 내려주는 키-밸류 스토어. "시크릿의 샘플" 키에 접근 권한이 있으면 비밀번호가 내려옵니다.

AWS 인증 연동의 마법

모든 AWS 인스턴스에는 PKCS 서명이 들어있음 (Amazon의 Private Key로 서명됨) AWS 인스턴스가 Vault에 요청: "내 PKCS 서명이야. 나 진짜 AWS 인스턴스 맞아. 권한 줘!" Vault가 Amazon Public Key로 검증: "이 서명이 진짜네. OK, 해당 권한의 토큰 내려줄게"

핵심 포인트

개발자가 직접 실행하면 AWS 서명이 없으니 비밀번호를 못 받음

EC2 인스턴스에서 실행하면 자동으로 비밀번호를 받아올 수 있음

시크릿 경로 자체는 코드에 커밋해도 안전!

Vault의 추가 기능들

기능 설명
SSH Certificate 개인의 SSH 키에 Vault가 서명 -> 24시간 동안 인프라 접근 가능. 입/퇴사 시 서버별 권한 설정 불필요!
Dynamic Secret DB 접근용 일회용 유저명/비밀번호 생성. 퇴사해도 그 유저 정보는 자동 폐기

7. 도입 후 변화

긍정적 변화

영역 개선 내용
인프라 추가 비슷한 환경을 빠르게 복제 가능, 전체 코드 퀄리티 개선
작업 분배 히스토리 아는 사람에게 작업이 몰리던 게, 누구나 코드 보고 참여 가능
접근성 AWS 자격증명, SSH 키 세팅 등 초기 설정 장벽 제거
유지보수 거대해진 모듈 분해, 리팩토링 가능
재사용 복잡한 작업(권한 설정 등)을 잘 만든 모듈로 해결

오픈소스 기여

버그 발견 비율

"슬프게도" 많이 기여하게 됩니다. 쓰다 보면 버그를 많이 발견해요.

제 체감 51% 저쪽(오픈소스 버그), 49% 저(내 실수) 비율로 버그를 만나게 됩니다.

오픈소스라서 내부 구조 파악이 쉽고, 기여할 수 있는 부분도 많습니다.

8. 남은 과제들

레거시 마이그레이션

카카오 시절 인프라를 Terraform으로 못 옮겼습니다. 없는 걸 새로 만드는 것보다 있는 걸 옮겨오는 난이도가 훨씬 높습니다.

리소스 이름 짓기의 중요성

실수 사례

S3 버킷 이름을 "cookierun-ovenbreak-production"으로 만들었는데, 나중에 US 리전에도 띄워야 하는 상황이 생겼습니다. S3는 전 세계 네임스페이스를 공유해서 같은 이름을 쓸 수 없어요!

교훈

처음 이름 지을 때부터 바뀔 수 있는 모든 가능성(리전, 환경, 버전 등)을 고려해서 이름을 지어야 합니다.

완전한 시크릿 보호

현재 Vault로 시크릿을 받아오지만, 서버에 접근할 수 있으면 메모리 덤프 등으로 시크릿을 추출할 수는 있습니다. 완전한 보안을 위해서는 애플리케이션 단의 구현도 필요합니다.

정리

Infrastructure as Code 3종 세트

Terraform = 인프라를 코드로 정의하고 버전 관리

Packer = 서버 이미지를 코드로 빌드 (부팅 속도 개선)

Vault = 시크릿을 안전하게 관리하고 자동 주입

핵심: 수동 작업의 실수, 추적 불가, 문서화 실패 문제를
"코드로 관리"함으로써 해결!

Before (수동) After (코드)
실수가 있어도 알아차리기 어려움 코드 리뷰로 사전 검토
누가 뭘 했는지 추적 불가 Git 커밋 로그로 전체 이력 관리
문서화가 현실과 달라짐 코드 자체가 문서 (Single Source of Truth)
비밀번호가 코드에 노출 Vault가 런타임에 주입
환경 복제에 오랜 시간 terraform apply로 빠르게 복제
