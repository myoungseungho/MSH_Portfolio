우리 서버 한 바퀴 — 조선협객전은 어떻게 도나

UE를 더 파기 전에, 비교 기준점인 우리 서버의 패킷 여정을 본다

30초 요약

클라 → Gate → Game ↔ GameDB. Gate가 관문이고, Game이 게임 로직, GameDB가 저장.

패킷 종류: CM_(클라→서버), SM_(서버→클라), DSM_(서버↔서버). Gate는 클라 패킷을 Game으로 forward.

이게 UE와 비교할 기준점. 이후 챕터마다 'UE는 이걸 어떻게 다르게 하나'를 본다.

Part 1. 왜 UE 전에 우리 서버부터?

UE 배우는데 왜 우리 서버를 봐?

비교 기준점이 있어야 'UE가 뭘 다르게 했는지'가 보이거든.

우리 서버를 한 바퀴 돌아두면, 다음 챕터마다 'UE의 NetDriver = 우리 Gate+IOCP', 'UE의 RPC = 우리 CM_/SM_ 핸들러' 식으로 1:1로 꿰어져.

큰 그림은?

클라가 Gate에 접속(Ch1의 15000 포트). Gate는 클라 패킷을 Game으로 넘기고, Game은 로직을 돌려 GameDB에 저장하거나 다른 서버와 통신해.

핵심은 '클라는 Game에 직접 못 붙는다' — 무조건 Gate를 거쳐.

Part 2. 패킷의 여정

패킷이 어디로 흐르는지 보자.

탭으로 ① 클라 패킷(CM_) / ② 브로드캐스트(SM_) / ③ 서버간(DSM_) 을 바꿔봐.

노드 사이를 토큰이 흐르는 걸 따라가면 각 패킷 종류의 경로가 보여.

0거친 홉(노드 이동) 수

Part 3. Gate — 모든 클라 패킷의 관문

Gate는 정확히 뭘 해?

클라이언트가 붙는 유일한 관문이야. 클라 패킷을 받아서 알맞은 서버(Game/Login/GameDB)로 forward해.

그래서 새 CM_ 패킷을 만들면 Gate의 HandleMsg switch에 case를 꼭 등록해야 해 — 안 그러면 default로 drop돼서 Game까지 도달 못 해.

왜 클라가 Game에 직접 안 붙어?

보안·구조 때문이야. 관문을 하나로 모으면 인증·필터링·연결 관리가 단순해지고, 내부 서버(Game/DB)를 외부에 직접 노출하지 않아.

UE의 데디서버는 보통 클라가 서버에 직접 붙는 단순 구조 — 우리가 Gate를 두는 건 다중 서버·영속 MMO라서야.

Part 4. 브로드캐스트와 서버간 통신

내가 움직이면 남들 화면엔 어떻게 보여?

Game이 'A가 여기로 이동' SM_ 패킷을 만들어, Gate가 주변 클라들에게 뿌려(BroadCast).

근데 '주변'이 누구까지냐가 문제 — 전부에게 뿌리면 부하 폭발이라, 관심 영역(AOI)으로 추려. UE의 Relevancy(Ch11)와 같은 고민이야.

다른 서버(채널/지역) 데이터가 필요하면?

직접 그 서버 메모리·DB를 건드리지 않고, 서버끼리 DSM_ 메시지를 주고받아.

이게 '서버 = 액터' 관점이야 — 각 서버가 자기 데이터만 갖고 메시지로만 통신. (액터모델 글 참고)

[조선협객전 서버 아키텍처] Client ──▶ Gate ──▶ Game ◀──▶ GameDB │ │ │ ├──▶ Login │ └──▶ Game(다른 서버) (DSM_) ▼ SM_ 브로드캐스트 → 주변 Client들 CM_ 클라→서버 / SM_ 서버→클라 / DSM_ 서버↔서버

한 줄로?

우리가 손으로 짜는 것(Gate forward, CM_/SM_, BroadCast)을 UE는 엔진이 자동(NetDriver, RPC, Replication)으로 해줘. 다음 챕터부터 그 '자동'의 속을 하나씩 열어볼 거야.

핵심 정리

  • 구조: Client → Gate(관문) → Game ↔ GameDB / Login / 다른 서버
  • 패킷: CM_(클라→서버), SM_(서버→클라), DSM_(서버↔서버)
  • Gate = 유일한 관문, 클라 패킷을 forward — case 등록 누락 시 drop
  • BroadCast = 주변에게 SM_ 뿌리기, 대상 추리기 = AOI(=UE Relevancy)
  • DSM_ = 서버끼리 메시지(서버=액터), 직접 데이터 안 건드림
  • 우리가 수동으로 하는 걸 UE는 엔진이 자동 — 다음 챕터부터 그 속을 연다
