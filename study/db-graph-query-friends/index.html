친구 목록을 빠르게 불러오는 법

그래프 쿼리 vs 관계형 DB

Part 1. 친구 관계의 데이터 모델

친구 관계를 DB에 어떻게 저장하나요?

가장 흔한 방식은 인접 리스트(Adjacency List)입니다:

친구 관계 데이터 모델: ┌────────────────────────────────────────────────────────────┐ │ │ │ 실제 관계 (그래프): │ │ │ │ 철수 ←──→ 영희 │ │ ↑↓ ↑↓ │ │ 민수 ←──→ 지수 │ │ │ │ 방법 1: 인접 리스트 (Adjacency List) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ friendships 테이블 │ │ │ │ ┌──────────┬──────────┬────────────┐ │ │ │ │ │ user_id │ friend_id│ created_at │ │ │ │ │ ├──────────┼──────────┼────────────┤ │ │ │ │ │ 철수 │ 영희 │ 2024-01-01 │ │ │ │ │ │ 영희 │ 철수 │ 2024-01-01 │ ← 양방향 저장│ │ │ │ 철수 │ 민수 │ 2024-01-02 │ │ │ │ │ │ 민수 │ 철수 │ 2024-01-02 │ │ │ │ │ │ ... │ ... │ ... │ │ │ │ │ └──────────┴──────────┴────────────┘ │ │ │ │ │ │ │ │ 장점: 조회 단순, 인덱스 효율적 │ │ │ │ 단점: 저장 공간 2배, INSERT 2번 │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 방법 2: 단방향 저장 (user_id < friend_id 규칙) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ friendships 테이블 │ │ │ │ ┌──────────┬──────────┐ │ │ │ │ │ user_a │ user_b │ (항상 user_a < user_b)│ │ │ │ ├──────────┼──────────┤ │ │ │ │ │ 1(철수) │ 2(영희) │ │ │ │ │ │ 1(철수) │ 3(민수) │ │ │ │ │ │ 2(영희) │ 4(지수) │ │ │ │ │ └──────────┴──────────┘ │ │ │ │ │ │ │ │ 장점: 저장 공간 절반 │ │ │ │ 단점: 조회 시 OR 조건 필요 (인덱스 비효율) │ │ │ └─────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
-- 방법 1: 양방향 저장 (권장) CREATE TABLE friendships ( user_id BIGINT NOT NULL, friend_id BIGINT NOT NULL, status TINYINT DEFAULT 1, -- 1: 활성, 0: 차단 created_at DATETIME DEFAULT CURRENT_TIMESTAMP, PRIMARY KEY (user_id, friend_id), INDEX idx_friend (friend_id, user_id) -- 역방향 조회용 ); -- 친구 추가 시 2행 INSERT INSERT INTO friendships (user_id, friend_id) VALUES (1, 2), (2, 1); -- 친구 조회: 단순! SELECT friend_id FROM friendships WHERE user_id = 1; -- 방법 2: 단방향 저장 CREATE TABLE friendships ( user_a BIGINT NOT NULL, user_b BIGINT NOT NULL, PRIMARY KEY (user_a, user_b), CHECK (user_a < user_b) -- 항상 작은 ID가 앞 ); -- 친구 조회: OR 조건 필요 SELECT CASE WHEN user_a = 1 THEN user_b ELSE user_a END AS friend_id FROM friendships WHERE user_a = 1 OR user_b = 1; -- 인덱스 2번 스캔 또는 풀스캔
인접 행렬(Adjacency Matrix)은요?

유저 수가 적고 친구 관계가 밀집된 경우에만 고려합니다:

인접 행렬 vs 인접 리스트: ┌────────────────────────────────────────────────────────────┐ │ │ │ 인접 행렬 (Adjacency Matrix): │ │ ┌──────┬────┬────┬────┬────┬────┐ │ │ │ │ 철수│ 영희│ 민수│ 지수│ ... │ │ │ ├──────┼────┼────┼────┼────┼────┤ │ │ │ 철수 │ 0 │ 1 │ 1 │ 0 │ │ │ │ │ 영희 │ 1 │ 0 │ 0 │ 1 │ │ │ │ │ 민수 │ 1 │ 0 │ 0 │ 1 │ │ │ │ │ 지수 │ 0 │ 1 │ 1 │ 0 │ │ │ │ │ ... │ │ │ │ │ │ │ │ └──────┴────┴────┴────┴────┴────┘ │ │ │ │ 공간 복잡도: O(N²) │ │ 100만 유저 × 100만 = 1조 개 셀 = 1TB │ │ │ │ 인접 리스트: │ │ 공간 복잡도: O(E) (엣지 수) │ │ 100만 유저 × 평균 100명 친구 = 1억 행 = 수 GB │ │ │ │ 결론: 게임에서는 인접 리스트가 압도적으로 유리 │ │ │ └────────────────────────────────────────────────────────────┘

Part 2. 관계형 DB에서의 친구 조회

1촌 친구 목록은 쉽죠?

네, 1촌은 단순 JOIN으로 충분합니다:

-- 1촌 친구 목록 (온라인 상태 포함) SELECT u.user_id, u.nickname, u.level, u.last_login, CASE WHEN u.last_login > DATE_SUB(NOW(), INTERVAL 5 MINUTE) THEN 'online' ELSE 'offline' END AS status FROM friendships f JOIN users u ON f.friend_id = u.user_id WHERE f.user_id = 12345 AND f.status = 1 -- 차단되지 않은 친구만 ORDER BY status DESC, u.nickname; -- 실행 계획 -- 1. friendships 인덱스 (user_id = 12345) → 친구 100명 -- 2. users 테이블 JOIN → 100번 Lookup -- 결과: 0.5ms ~ 2ms (인덱스만 잘 있으면 빠름)
2촌 친구(친구의 친구)는요?

여기서부터 성능 문제가 시작됩니다:

2촌 친구 조회의 복잡도: ┌────────────────────────────────────────────────────────────┐ │ │ │ 나 (ID: 1) │ │ │ │ │ ├── 친구 A (1촌) │ │ │ ├── 친구 A1 (2촌) │ │ │ ├── 친구 A2 (2촌) │ │ │ └── 친구 A3 (2촌) │ │ │ │ │ ├── 친구 B (1촌) │ │ │ ├── 친구 B1 (2촌) │ │ │ ├── 친구 A1 (2촌, 중복!) ← 중복 제거 필요 │ │ │ └── 나 (2촌? → 제외!) │ │ │ │ │ └── 친구 C (1촌) × 100명... │ │ │ │ 계산: │ │ • 1촌: 100명 │ │ • 2촌 후보: 100명 × 100명 = 10,000명 │ │ • 중복 제거 + 나/1촌 제외 후: ~5,000명 │ │ │ └────────────────────────────────────────────────────────────┘
-- 2촌 친구 조회 (관계형 DB) SELECT DISTINCT f2.friend_id, u.nickname FROM friendships f1 JOIN friendships f2 ON f1.friend_id = f2.user_id JOIN users u ON f2.friend_id = u.user_id WHERE f1.user_id = 12345 -- 나의 1촌 AND f2.friend_id != 12345 -- 나 자신 제외 AND f2.friend_id NOT IN ( -- 1촌 제외 (이미 친구) SELECT friend_id FROM friendships WHERE user_id = 12345 ) ORDER BY u.nickname LIMIT 100; -- 문제점: -- 1. JOIN 2번 → 행 수 폭발 (100 × 100 = 10,000) -- 2. DISTINCT → 정렬 비용 -- 3. NOT IN 서브쿼리 → 추가 스캔 -- 실행 시간: 100ms ~ 500ms
3촌은... 감당이 되나요?

관계형 DB의 한계가 드러납니다:

N촌 조회의 복잡도 폭발: ┌────────────────────────────────────────────────────────────┐ │ │ │ 촌수별 조회 비용 (평균 친구 100명 가정): │ │ │ │ ┌───────┬─────────────┬─────────────┬─────────────┐ │ │ │ 촌수 │ 후보 행 수 │ JOIN 횟수 │ 예상 시간 │ │ │ ├───────┼─────────────┼─────────────┼─────────────┤ │ │ │ 1촌 │ 100 │ 1 │ 2ms │ │ │ │ 2촌 │ 10,000 │ 2 │ 200ms │ │ │ │ 3촌 │ 1,000,000 │ 3 │ 20초 │ │ │ │ 4촌 │ 100,000,000 │ 4 │ 타임아웃 │ │ │ └───────┴─────────────┴─────────────┴─────────────┘ │ │ │ │ O(k^n) 복잡도! (k=평균 친구 수, n=촌수) │ │ │ │ 실제 소셜 네트워크 특성 (Small World): │ │ • 6단계 분리 이론: 누구나 6촌 안에 연결 │ │ • 3촌만 조회해도 거의 전체 유저 포함 │ │ │ └────────────────────────────────────────────────────────────┘
-- 3촌 조회 (관계형 DB) - 비권장! WITH RECURSIVE friend_tree AS ( -- 시작점: 나 SELECT 12345 AS user_id, 0 AS depth UNION ALL -- 재귀: 친구의 친구... SELECT f.friend_id, ft.depth + 1 FROM friend_tree ft JOIN friendships f ON ft.user_id = f.user_id WHERE ft.depth < 3 -- 3촌까지 ) SELECT DISTINCT user_id FROM friend_tree WHERE depth = 3; -- MySQL CTE는 최적화가 약함 → 매우 느림 -- 대안: 배치로 미리 계산해서 테이블에 저장

Part 3. 그래프 DB의 장점

그래프 DB는 뭐가 다른가요?

관계 순회에 최적화된 저장 구조를 사용합니다:

관계형 DB vs 그래프 DB 내부 구조: ┌────────────────────────────────────────────────────────────┐ │ │ │ 관계형 DB (테이블 기반): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ friendships 테이블 │ │ │ │ ┌──────────┬──────────┐ │ │ │ │ │ user_id │ friend_id│ ← B+Tree 인덱스 │ │ │ │ ├──────────┼──────────┤ │ │ │ │ │ 1 │ 2 │ │ │ │ │ │ 1 │ 3 │ │ │ │ │ │ 2 │ 1 │ │ │ │ │ │ 2 │ 4 │ ← 디스크 상 분산 저장 │ │ │ │ │ ... │ ... │ │ │ │ │ └──────────┴──────────┘ │ │ │ │ │ │ │ │ 2촌 조회: 인덱스 탐색 → rowid → 테이블 → 반복... │ │ │ │ 매번 인덱스 룩업 비용 발생 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 그래프 DB (포인터 기반): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ [Node: 철수] │ │ │ │ │ │ │ │ │ ├──→ [Edge: FRIEND] ──→ [Node: 영희] │ │ │ │ │ ↑ │ │ │ │ │ │ 직접 포인터! ├──→ [지수] │ │ │ │ │ └──→ [민수] │ │ │ │ │ │ │ │ │ └──→ [Edge: FRIEND] ──→ [Node: 민수] │ │ │ │ │ │ │ │ 2촌 조회: 포인터 따라가기만! │ │ │ │ O(1) 탐색 비용 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
// Neo4j Cypher 쿼리 // 1촌 친구 MATCH (me:User {id: 12345})-[:FRIEND]->(friend:User) RETURN friend.nickname, friend.level; // 2촌 친구 (중복 제거, 1촌 제외) MATCH (me:User {id: 12345})-[:FRIEND*2]->(fof:User) WHERE NOT (me)-[:FRIEND]->(fof) AND me <> fof RETURN DISTINCT fof.nickname LIMIT 100; // 3촌까지 (가변 깊이) MATCH (me:User {id: 12345})-[:FRIEND*1..3]->(distant:User) RETURN distant.id, min(length(path)) AS distance; // 최단 경로 (두 유저 사이) MATCH path = shortestPath( (a:User {id: 12345})-[:FRIEND*]-(b:User {id: 67890}) ) RETURN length(path) AS 촌수;
성능 차이가 얼마나 나요?
벤치마크: 관계형 DB vs 그래프 DB ┌────────────────────────────────────────────────────────────┐ │ │ │ 테스트 환경: │ │ • 유저: 100만 명 │ │ • 친구 관계: 5000만 개 (평균 50명/유저) │ │ │ │ 1촌 친구 조회 (50명): │ │ ┌─────────────────┬─────────────┬─────────────┐ │ │ │ DB │ 응답 시간 │ 비고 │ │ │ ├─────────────────┼─────────────┼─────────────┤ │ │ │ MySQL │ 2ms │ 인덱스 사용 │ │ │ │ Neo4j │ 1ms │ 비슷 │ │ │ └─────────────────┴─────────────┴─────────────┘ │ │ │ │ 2촌 친구 조회 (추천 친구): │ │ ┌─────────────────┬─────────────┬─────────────┐ │ │ │ DB │ 응답 시간 │ 비고 │ │ │ ├─────────────────┼─────────────┼─────────────┤ │ │ │ MySQL │ 150ms │ JOIN 비용 │ │ │ │ Neo4j │ 8ms │ 18배 빠름 │ │ │ └─────────────────┴─────────────┴─────────────┘ │ │ │ │ 3촌 경로 탐색: │ │ ┌─────────────────┬─────────────┬─────────────┐ │ │ │ DB │ 응답 시간 │ 비고 │ │ │ ├─────────────────┼─────────────┼─────────────┤ │ │ │ MySQL │ 15초+ │ 타임아웃 │ │ │ │ Neo4j │ 50ms │ 300배 빠름 │ │ │ └─────────────────┴─────────────┴─────────────┘ │ │ │ │ 깊이가 깊어질수록 그래프 DB의 장점이 기하급수적으로 증가 │ │ │ └────────────────────────────────────────────────────────────┘

Part 4. 게임에서의 현실적 선택

게임 서버에 Neo4j 쓰면 되나요?

항상 그렇지는 않습니다. 트레이드오프를 고려해야 합니다:

그래프 DB 도입 판단 기준: ┌────────────────────────────────────────────────────────────┐ │ │ │ ✅ 그래프 DB 적합한 경우: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • 추천 친구 (2촌+) 기능이 핵심 │ │ │ │ • 소셜 그래프 분석 (인플루언서 탐지) │ │ │ │ • 길드/클랜 네트워크 시각화 │ │ │ │ • 실시간 관계 기반 매칭 │ │ │ │ • 사기 탐지 (연결 패턴 분석) │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ ❌ 관계형 DB로 충분한 경우: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • 1촌 친구 목록만 필요 │ │ │ │ • 친구 수 제한 (최대 100명 등) │ │ │ │ • 트랜잭션 일관성이 중요 (재화 거래) │ │ │ │ • 기존 인프라가 관계형 DB │ │ │ │ • 운영팀이 SQL만 알고 있음 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 대부분의 게임: 관계형 DB + 캐시로 충분! │ │ │ └────────────────────────────────────────────────────────────┘
관계형 DB로 최적화하는 방법은요?

캐시 + 비동기 계산으로 대부분 해결됩니다:

// 전략 1: 1촌 친구 목록 메모리 캐시 class FriendCache { private: // user_id → [friend_ids] std::unordered_map<uint64_t, std::vector<uint64_t>> m_cache; public: // 로그인 시 로드 void LoadFriends(uint64_t userId) { auto friends = DB::Query( "SELECT friend_id FROM friendships WHERE user_id = ?", userId); m_cache[userId] = friends; } // 친구 목록 조회: O(1) const std::vector<uint64_t>& GetFriends(uint64_t userId) { return m_cache[userId]; } // 친구 추가 시 양쪽 캐시 갱신 void AddFriend(uint64_t userId, uint64_t friendId) { m_cache[userId].push_back(friendId); if (m_cache.count(friendId)) { // 친구도 로그인 중이면 m_cache[friendId].push_back(userId); } } }; // 전략 2: 추천 친구 배치 계산 // 매일 새벽에 2촌 관계를 미리 계산해서 테이블에 저장 CREATE TABLE friend_recommendations ( user_id BIGINT, recommended_id BIGINT, common_friends INT, -- 공통 친구 수 score FLOAT, -- 추천 점수 updated_at DATETIME, PRIMARY KEY (user_id, recommended_id) ); -- 배치 작업 (매일 새벽) INSERT INTO friend_recommendations (user_id, recommended_id, common_friends, score) SELECT f1.user_id, f2.friend_id, COUNT(*) AS common_friends, COUNT(*) * 10.0 AS score -- 단순 점수 계산 FROM friendships f1 JOIN friendships f2 ON f1.friend_id = f2.user_id WHERE f2.friend_id != f1.user_id AND NOT EXISTS ( SELECT 1 FROM friendships WHERE user_id = f1.user_id AND friend_id = f2.friend_id ) GROUP BY f1.user_id, f2.friend_id ON DUPLICATE KEY UPDATE common_friends = VALUES(common_friends), score = VALUES(score), updated_at = NOW();

Part 5. 하이브리드 아키텍처

둘 다 쓰면 어떨까요?

CQRS 패턴으로 용도별 DB 분리가 가능합니다:

하이브리드 아키텍처: ┌────────────────────────────────────────────────────────────┐ │ │ │ Write Path (트랜잭션): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ 게임 서버 ───→ MySQL (마스터) │ │ │ │ │ │ │ │ │ │ │ ├─ friendships (친구 관계) │ │ │ │ │ ├─ users (유저 정보) │ │ │ │ │ └─ ... (기타 게임 데이터) │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ ▼ CDC (Change Data Capture) │ │ │ │ │ │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ │ ▼ │ │ Read Path (소셜 분석): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ Kafka ───→ Neo4j (읽기 전용) │ │ │ │ │ │ │ │ │ ├─ 추천 친구 계산 │ │ │ │ ├─ 네트워크 분석 │ │ │ │ └─ 경로 탐색 │ │ │ │ │ │ │ │ │ ▼ │ │ │ │ Redis (캐시) │ │ │ │ │ │ │ │ │ ▼ │ │ │ │ 게임 서버 (조회) │ │ │ │ │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 쓰기는 MySQL, 복잡한 조회는 Neo4j로 분리 │ │ │ └────────────────────────────────────────────────────────────┘
// 실제 구현 예시 // 친구 추가 (MySQL에 쓰기) async function addFriend(userId, friendId) { await mysql.transaction(async (tx) => { // 양방향 관계 저장 await tx.query( 'INSERT INTO friendships (user_id, friend_id) VALUES (?, ?), (?, ?)', [userId, friendId, friendId, userId] ); }); // CDC가 자동으로 Neo4j에 동기화 // 또는 직접 이벤트 발행 await kafka.publish('friend.added', { userId, friendId }); } // 추천 친구 조회 (Neo4j에서 읽기, Redis 캐시) async function getRecommendedFriends(userId) { const cacheKey = `recommend:${userId}`; // 1. 캐시 확인 let recommendations = await redis.get(cacheKey); if (recommendations) return JSON.parse(recommendations); // 2. Neo4j 쿼리 const result = await neo4j.run(` MATCH (me:User {id: $userId})-[:FRIEND]->(f)-[:FRIEND]->(fof) WHERE NOT (me)-[:FRIEND]->(fof) AND me <> fof WITH fof, COUNT(f) AS commonFriends ORDER BY commonFriends DESC LIMIT 20 RETURN fof.id, fof.nickname, commonFriends `, { userId }); // 3. 캐시 저장 (1시간) await redis.setex(cacheKey, 3600, JSON.stringify(result)); return result; }

핵심 정리

  • 인접 리스트가 게임 친구 관계 저장에 가장 적합 (양방향 저장 권장)
  • 1촌 조회는 관계형 DB로 충분 (인덱스 + 캐시)
  • 2촌 이상부터 관계형 DB 성능 급락 (O(k^n) 복잡도)
  • 그래프 DB는 관계 순회에 최적화 (포인터 기반 O(1) 탐색)
  • 대부분의 게임: 관계형 DB + 배치 계산 + Redis 캐시로 충분
  • 하이브리드: 쓰기는 MySQL, 복잡한 조회는 Neo4j (CQRS 패턴)
