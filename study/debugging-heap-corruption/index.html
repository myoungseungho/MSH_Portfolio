힙 손상

delete에서 크래시 나요 — 원인은 다른 곳에 있다

Part 1. 증상

delete 또는 free에서 크래시가 납니다

delete 자체가 문제가 아니다.

이전에 힙 메타데이터가 손상되었고, delete할 때 발견된 것.

// 크래시 발생 위치 delete pPlayer; // ← 여기서 터짐 // 하지만 진짜 원인은 이전에 발생 // 버퍼 오버런, Double Free, Use-After-Free 등

Part 2. 주요 원인들

힙 손상의 원인은?

1. 버퍼 오버런: 할당된 크기를 넘어서 씀

2. Double Free: 같은 메모리를 두 번 해제

3. Use-After-Free: 해제 후 다시 사용

4. 잘못된 delete: new[]는 delete[]로

// 1. 버퍼 오버런 char* buf = new char[10]; strcpy(buf, "This is too long"); // 10바이트 넘음! // 2. Double Free delete pPlayer; delete pPlayer; // 두 번째 delete에서 크래시 // 3. Use-After-Free delete pPlayer; pPlayer->DoSomething(); // 해제된 메모리 접근 // 4. 잘못된 delete int* arr = new int[100]; delete arr; // delete[]가 아님!

Part 3. 디버깅 도구

어떻게 찾아?

힙 손상은 발생 시점 ≠ 발견 시점이라 찾기 어렵다.

전용 도구를 써야 한다:

// 1. Application Verifier (Windows) // 힙 작업마다 검증 → 손상 즉시 감지 // 2. AddressSanitizer (ASan) // 컴파일 옵션: /fsanitize=address // 모든 메모리 접근 검사 // 3. Debug Heap (CRT) // _CrtSetDbgFlag(_CRTDBG_CHECK_ALWAYS_DF) // 모든 힙 작업 시 검사 (매우 느림) // 4. PageHeap (gflags) // 각 할당을 별도 페이지에 배치 // 오버런 즉시 Access Violation

Part 4. 즉시 감지 설정

코드에서 바로 검사하려면?

CRT Debug Heap의 즉시 검사 모드를 켜면 된다.

// 프로그램 시작 시 추가 #ifdef _DEBUG int flag = _CrtSetDbgFlag(_CRTDBG_REPORT_FLAG); flag |= _CRTDBG_CHECK_ALWAYS_DF; // 매번 검사 _CrtSetDbgFlag(flag); #endif // 주의: 매우 느려짐! // 문제가 재현되면 범위를 좁혀서 사용

핵심 정리

  • delete에서 크래시 = 이전에 힙 손상됨
  • 원인: 오버런, Double Free, UAF, 잘못된 delete
  • Application Verifier 또는 ASan 사용
  • 발견 시점 ≠ 발생 시점 주의
