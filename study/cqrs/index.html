읽기용 DB, 쓰기용 DB를 왜 나눠?

CQRS(Command Query Responsibility Segregation) - 읽기와 쓰기를 분리하는 패턴

Part 1. 하나의 DB로 뭐가 문제야?

DB 하나로 읽고 쓰면 안 돼?

작은 규모에선 괜찮아.

근데 읽기와 쓰기 패턴이 완전 달라.

📊 게임에서 읽기 vs 쓰기 비율: [랭킹 시스템] ├─ 쓰기: 점수 갱신 (분당 100건) └─ 읽기: 랭킹 조회 (분당 10,000건) → 읽기가 100배 많음! [인벤토리] ├─ 쓰기: 아이템 획득/사용 (분당 1,000건) └─ 읽기: 인벤토리 열기 (분당 5,000건) → 읽기가 5배 많음 [거래소] ├─ 쓰기: 등록/구매 (분당 500건) └─ 읽기: 검색/조회 (분당 50,000건) → 읽기가 100배 많음!
읽기가 많으면 뭐가 문제야?

같은 DB에서 쓰기가 읽기를 방해해.

INSERT/UPDATE 하는 동안 SELECT가 느려져.

🚧 하나의 DB에서 충돌: [랭킹 DB] ├─ 쓰기: "점수 UPDATE 중..." 🔒 락 걸림 └─ 읽기: "랭킹 조회하려는데... 기다려야 함" ⏳ 1만 명이 랭킹 보려고 하는데 10명이 점수 갱신하느라 락 걸림 → 대기열 발생 → 랭킹 조회 느려짐 → 유저: "왜 랭킹이 안 떠요?!"

Part 2. CQRS가 뭔데?

CQRS가 뭐야?

Command = 쓰기, Query = 읽기

둘을 완전히 분리하는 거야.

쓰기용 모델과 읽기용 모델을 따로 만들어.

🔀 CQRS 기본 구조: [기존: 하나로 통합] ┌─────────────────────────────────┐ │ 랭킹 DB │ │ ┌─────────────────────────┐ │ │ │ 읽기 + 쓰기 모두 여기서 │ │ │ └─────────────────────────┘ │ └─────────────────────────────────┘ [CQRS: 분리] ┌──────────────┐ ┌──────────────┐ │ 쓰기 모델 │ │ 읽기 모델 │ │ (Command) │ ──▶ │ (Query) │ │ │동기화│ │ │ - 점수 갱신 │ │ - 랭킹 조회 │ │ - 정규화 │ │ - 비정규화 │ │ - 트랜잭션 │ │ - 캐시 최적화│ └──────────────┘ └──────────────┘
왜 분리하면 좋아?

각자 목적에 맞게 최적화할 수 있어.

항목 쓰기 모델 읽기 모델
목적 데이터 정합성 빠른 조회
구조 정규화 비정규화 (JOIN 없이)
인덱스 최소한 조회 패턴별 최적화
스케일링 단일 마스터 복제본 여러 대
일관성 강한 일관성 최종 일관성

Part 3. 랭킹 시스템으로 이해하기

랭킹에 CQRS 적용하면 어떻게 돼?

쓰기와 읽기를 완전히 분리해보자:

🏆 랭킹 CQRS 예시: [쓰기 모델 - Write DB] ┌─────────────────────────────────┐ │ 테이블: PlayerScore │ │ - player_id (PK) │ │ - score │ │ - updated_at │ │ │ │ 역할: 점수 갱신만 담당 │ │ 특징: 정규화, 트랜잭션 보장 │ └─────────────────────────────────┘ │ │ 점수 변경 시 이벤트 발행 ▼ [읽기 모델 - Read DB / Redis] ┌─────────────────────────────────┐ │ 구조: Redis Sorted Set │ │ Key: "ranking:weekly" │ │ - player_id → score (정렬됨) │ │ │ │ 역할: 랭킹 조회만 담당 │ │ 특징: 이미 정렬됨, O(log N) │ └─────────────────────────────────┘
점수 바뀌면 어떻게 동기화해?

이벤트로 전파해.

쓰기 DB에서 점수 바뀌면 → 이벤트 발행 → 읽기 모델 갱신

🔄 동기화 흐름: 1️⃣ 유저가 점수 갱신 [Game Server] ──▶ [Write DB] UPDATE score=1000 2️⃣ 이벤트 발행 [Write DB] ──▶ [Message Queue] "ScoreUpdated: player=123, score=1000" 3️⃣ 읽기 모델 갱신 [Message Queue] ──▶ [Read Model Updater] [Updater] ──▶ [Redis] ZADD ranking:weekly 1000 "player:123" 4️⃣ 조회는 읽기 모델에서 [유저] ──랭킹 조회──▶ [Redis] ZREVRANGE ranking:weekly 0 99 → 1ms 만에 응답!
실시간으로 동기화되는 거야?

약간의 지연이 있어.

점수 갱신 → 읽기 모델 반영까지 몇 ms ~ 몇 초.

이걸 최종 일관성(Eventual Consistency)이라고 해.

⏱️ 최종 일관성: [강한 일관성] - 기존 방식 쓰기 완료 = 즉시 읽기 반영 → 락 필요, 느림 [최종 일관성] - CQRS 쓰기 완료 → (약간 지연) → 읽기 반영 → 락 불필요, 빠름 랭킹의 경우: "내 점수 1000점으로 갱신했는데 랭킹에 999점으로 보여요" → 1초 후 새로고침하면 1000점으로 보임 → 대부분의 경우 문제 없음

Part 4. 언제 CQRS를 써야 해?

모든 곳에 CQRS 적용해야 해?

아니, 복잡성이 증가해.

읽기/쓰기 비율이 극단적으로 다를 때만 써.

상황 CQRS 이유
랭킹 시스템 ✅ 적합 읽기 100배 많음
거래소 ✅ 적합 검색 조회 폭발
대시보드/통계 ✅ 적합 복잡한 집계 쿼리
인벤토리 △ 상황에 따라 읽기/쓰기 비슷
채팅 ❌ 과함 단순 CRUD로 충분
설정 저장 ❌ 과함 트래픽 자체가 적음
CQRS의 단점은?

복잡성이 크게 증가해:

⚠️ CQRS의 비용: 1️⃣ 코드 복잡성 - 쓰기 로직 따로, 읽기 로직 따로 - 동기화 로직 추가 - 디버깅 어려움 증가 2️⃣ 인프라 복잡성 - DB가 2개 이상 - Message Queue 필요 - 동기화 Worker 필요 3️⃣ 일관성 처리 - 지연 발생 처리 - 에러 시 재시도 로직 - 순서 보장 필요할 수도

Part 5. 이벤트 소싱과 같이 쓰면?

CQRS랑 이벤트 소싱이랑 같이 쓴다며?

완벽한 조합이야!

이벤트 소싱 = 쓰기, 프로젝션 = 읽기

🔗 이벤트 소싱 + CQRS: [Command 처리] 유저: "1000점 획득" │ ▼ [Event Store] ← 쓰기 모델 ├─ Event #1: ScoreEarned(+1000) ├─ Event #2: ScoreEarned(+500) └─ Event #3: ScoreSpent(-200) │ │ 이벤트 발행 ▼ [Projection] → 읽기 모델 ├─ 랭킹용: Redis Sorted Set ├─ 통계용: 일별 집계 테이블 └─ 리포트용: 월간 요약 테이블 → 하나의 이벤트로 여러 읽기 모델 생성!
여러 읽기 모델을 만들 수 있어?

그게 핵심 장점이야!

같은 데이터를 용도별로 다르게 저장할 수 있어.

📊 하나의 이벤트 → 여러 읽기 모델: [점수 이벤트] ScoreEarned(player=123, score=1000, source="boss_kill") │ ├──▶ [랭킹 모델] │ Redis: ZADD ranking 1000 player:123 │ → "랭킹 몇 위인가요?" 조회용 │ ├──▶ [통계 모델] │ DB: INSERT INTO daily_stats (date, total_score, ...) │ → "오늘 총 획득 점수" 조회용 │ └──▶ [알림 모델] 서버: "보스 처치 업적 달성!" → 실시간 알림용

Part 6. 직접 구현할 때 핵심

간단하게 구현하려면?

가장 기본적인 구조:

// Command (쓰기) class UpdateScoreCommand { void Execute(int playerId, int newScore) { // 1. 쓰기 DB에 저장 m_writeDb.Update(playerId, newScore); // 2. 이벤트 발행 (읽기 모델 갱신용) m_eventBus.Publish("ScoreUpdated", playerId, newScore); } }; // Query (읽기) class GetRankingQuery { vector<RankEntry> Execute(int topN) { // 읽기 전용 모델에서 조회 (Redis) return m_redis.GetTopRanking(topN); } }; // 이벤트 핸들러 (동기화) class RankingProjection { void OnScoreUpdated(int playerId, int newScore) { // 읽기 모델 갱신 m_redis.UpdateRanking(playerId, newScore); } };

⚠️ CQRS 적용 시 주의사항

1. 최종 일관성 고려 - 읽기 모델이 최신이 아닐 수 있음을 UI에서 처리

2. 멱등성 보장 - 같은 이벤트 두 번 처리해도 결과 동일해야 함

3. 순서 보장 - 이벤트 순서가 중요하면 파티셔닝 고려

4. 재빌드 전략 - 읽기 모델 꼬이면 이벤트부터 다시 빌드 가능해야 함

📝 핵심 정리

  • CQRS = Command(쓰기)와 Query(읽기) 완전 분리
  • 각각 최적화 가능: 쓰기는 정규화, 읽기는 비정규화
  • 읽기 100배 많은 시스템에 효과적 (랭킹, 거래소)
  • 이벤트로 동기화, 약간의 지연 발생 (최종 일관성)
  • 복잡성 증가 → 정말 필요할 때만 적용
