콘솔의 메모리 예산

고정 하드웨어에서 예산을 계획하고 관리하는 전략

Part 1. 왜 콘솔에서 메모리 예산이 중요해?

PC는 메모리가 부족하면 그냥 더 많이 사면 되잖아. 콘솔은 왜 예산이라는 개념이 필요해?

핵심 차이는 하드웨어가 고정되어 있다는 점입니다.

PS5는 16GB, Xbox Series X도 16GB, Nintendo Switch는 4GB로 절대 변하지 않습니다. 모든 유저가 동일한 스펙이죠.

PC에서는 "최소 8GB, 권장 16GB"처럼 요구사항을 명시하고 유저에게 업그레이드를 맡기지만, 콘솔에서는 1바이트라도 초과하면 바로 크래시됩니다.

16GB면 꽤 많은 것 같은데, 그게 그렇게 빡빡해?

16GB 전부를 게임이 쓸 수 있는 게 아닙니다.

실제 게임이 쓸 수 있는 메모리는 약 13.5GB 정도입니다. 여기서 오픈월드 게임의 거대한 월드, 4K 텍스처, 수백 개의 NPC를 모두 감당해야 합니다.

Xbox Series X는 어때? 같은 16GB라도 다른 점이 있어?

Xbox Series X는 속도가 다른 두 종류의 메모리를 사용합니다.

Xbox Series X 메모리 구조 (Split Bandwidth)
═══════════════════════════════════════════════════════════

┌──────────────────────────────────────────────────────────┐
│  Fast Pool (10GB @ 560GB/s)                              │
│  ├─ GPU 전용 자원에 적합                                 │
│  ├─ 렌더 타겟, 프레임버퍼                                │
│  └─ 자주 접근하는 텍스처                                 │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│  Slow Pool (6GB @ 336GB/s)                               │
│  ├─ CPU 데이터에 적합                                    │
│  ├─ 오디오 버퍼, 물리 데이터                             │
│  └─ 스트리밍 대기 버퍼                                   │
└──────────────────────────────────────────────────────────┘

※ 개발자가 어떤 자원을 어느 풀에 배치할지 명시적으로 결정해야 함
※ 잘못 배치하면 성능이 크게 저하됨

이렇게 메모리 배치까지 개발자가 관리해야 하므로, 단순히 "용량"만이 아니라 "어디에 무엇을"까지 계획해야 합니다.

Part 2. 메모리 예산 분배 전략

13.5GB를 어떻게 나눠야 해? 기준이 있어?

장르와 프로젝트 특성에 따라 달라지지만, AAA 오픈월드 게임의 일반적인 예산 배분을 보면:

// 메모리 예산 정의 (AAA 오픈월드 기준) struct MemoryBudget { // 고정 예산 - 항상 로드되어 있어야 하는 것 static constexpr size_t SYSTEM_CORE = 500 * MB; // 엔진 코어, 렌더러 static constexpr size_t PLAYER_ASSETS = 800 * MB; // 플레이어 캐릭터 풀셋 static constexpr size_t UI_SYSTEM = 300 * MB; // UI 아틀라스, 폰트 static constexpr size_t AUDIO_CORE = 200 * MB; // 필수 사운드 // 유동 예산 - 상황에 따라 조절 가능 static constexpr size_t TEXTURES_POOL = 5500 * MB; // 텍스처 스트리밍 static constexpr size_t MESHES_POOL = 1800 * MB; // 메시 데이터 static constexpr size_t ANIMATION_POOL = 900 * MB; // 애니메이션 static constexpr size_t AUDIO_STREAMING = 600 * MB; // 스트리밍 오디오 static constexpr size_t PHYSICS_POOL = 500 * MB; // 물리 시뮬레이션 static constexpr size_t AI_POOL = 400 * MB; // NPC AI 데이터 // 렌더 타겟 (GPU 전용) static constexpr size_t RENDER_TARGETS = 1500 * MB; // GBuffer, 그림자 등 // 안전 마진 static constexpr size_t SAFETY_MARGIN = 500 * MB; // 절대 건드리지 않음! // 총합: 약 13.5GB };
Safety Margin은 왜 필요해? 딱 맞게 쓰면 안 돼?

절대 안 됩니다. 여러 이유가 있습니다:

안전 마진이 필수인 이유

  • 메모리 단편화: 할당/해제 반복으로 연속 공간 부족 발생
  • 피크 사용량: 로딩 중 일시적으로 더 많은 메모리 필요
  • 플랫폼 업데이트: OS 업데이트로 시스템 예약 증가 가능
  • 디버그 빌드: 개발 중에는 더 많은 메모리 사용
  • 예측 불가 상황: 유저가 예상치 못한 플레이 패턴 보일 때

실제 사례: 어떤 게임은 "도시 한복판에서 수류탄 10개 동시 폭발" 상황에서 크래시가 발생했는데, 파티클과 물리 데브리가 동시에 폭증하면서 예산을 초과했기 때문이었습니다.

예산을 어떻게 카테고리별로 강제할 수 있어?

메모리 풀(Memory Pool) 시스템을 사용합니다.

class BudgetedMemoryPool { private: std::string m_Name; size_t m_Budget; // 할당된 예산 size_t m_Used; // 현재 사용량 size_t m_PeakUsed; // 최대 사용량 (프로파일링용) std::mutex m_Lock; public: BudgetedMemoryPool(const char* name, size_t budget) : m_Name(name), m_Budget(budget), m_Used(0), m_PeakUsed(0) {} void* Allocate(size_t size, size_t alignment = 16) { std::lock_guard<std::mutex> lock(m_Lock); size_t alignedSize = AlignUp(size, alignment); // 예산 초과 체크 if (m_Used + alignedSize > m_Budget) { // 개발 빌드: 경고 + 강제 할당 (디버깅 위해) // 릴리즈 빌드: nullptr 반환 또는 저품질 대체 #if DEBUG_BUILD LogWarning("[%s] Budget exceeded! Used: %zu / %zu, Requested: %zu", m_Name.c_str(), m_Used, m_Budget, alignedSize); // 강제 할당하고 분석할 수 있게 함 #else // 릴리즈에서는 우아하게 실패 return nullptr; #endif } void* ptr = PlatformAlloc(alignedSize, alignment); if (ptr) { m_Used += alignedSize; m_PeakUsed = std::max(m_PeakUsed, m_Used); } return ptr; } void Free(void* ptr, size_t size) { std::lock_guard<std::mutex> lock(m_Lock); PlatformFree(ptr); m_Used -= AlignUp(size, 16); } float GetUsagePercent() const { return (float)m_Used / m_Budget * 100.0f; } }; // 전역 풀 관리자 class MemoryBudgetManager { private: std::unordered_map<BudgetCategory, std::unique_ptr<BudgetedMemoryPool>> m_Pools; public: void Initialize() { m_Pools[BudgetCategory::Textures] = std::make_unique<BudgetedMemoryPool>("Textures", 5500 * MB); m_Pools[BudgetCategory::Meshes] = std::make_unique<BudgetedMemoryPool>("Meshes", 1800 * MB); m_Pools[BudgetCategory::Audio] = std::make_unique<BudgetedMemoryPool>("Audio", 800 * MB); // ... 나머지 카테고리 } void* Allocate(BudgetCategory category, size_t size) { return m_Pools[category]->Allocate(size); } };

Part 3. 예산 초과 시 대응 전략

예산을 초과하면 크래시 말고 다른 방법은 없어?

품질 저하(Quality Degradation) 전략을 사용합니다. 크래시보다는 화질이 좀 떨어지는 게 낫죠.

class MemoryPressureHandler { public: enum class PressureLevel { Normal, // 80% 미만 Warning, // 80-90% Critical, // 90-95% Emergency // 95% 이상 }; private: TextureStreamingSystem* m_TextureStreaming; LODManager* m_LODManager; AudioManager* m_AudioManager; public: void HandlePressure(PressureLevel level) { switch (level) { case PressureLevel::Warning: // 단계 1: 보이지 않는 것부터 정리 m_TextureStreaming->EvictOffscreenTextures(); m_LODManager->ReduceDistantLOD(); break; case PressureLevel::Critical: // 단계 2: 품질 저하 m_TextureStreaming->ForceMipBias(1); // 한 단계 낮은 밉맵 m_LODManager->ForceLODOffset(1); // 한 단계 낮은 LOD m_AudioManager->ReduceVoiceCount(0.7f); // 동시 재생 수 감소 break; case PressureLevel::Emergency: // 단계 3: 공격적 정리 m_TextureStreaming->ForceMipBias(2); m_LODManager->ForceLODOffset(2); m_AudioManager->StopNonEssentialSounds(); UnloadDistantChunks(); ForceGarbageCollection(); LogError("Memory emergency! Quality severely degraded."); break; } } private: void UnloadDistantChunks() { // 플레이어로부터 먼 월드 청크 해제 Vector3 playerPos = GetPlayerPosition(); for (auto& chunk : m_LoadedChunks) { float distance = Distance(chunk.Center, playerPos); if (distance > EMERGENCY_UNLOAD_DISTANCE) { chunk.Unload(); } } } };
텍스처 품질을 낮추면 티가 많이 나지 않아?

영리하게 하면 잘 안 보입니다. 핵심은 유저가 주목하지 않는 곳부터 품질을 낮추는 것입니다.

품질 저하 우선순위 (덜 눈에 띄는 순서)
═══════════════════════════════════════════════════════════

1단계 (거의 안 보임)
├─ 화면 밖 오브젝트의 텍스처
├─ 멀리 있는 배경 건물
├─ 환경 앰비언트 사운드
└─ 오클루전된(가려진) 오브젝트

2단계 (주의 깊게 봐야 보임)
├─ 중거리 NPC의 복장 디테일
├─ 지면 텍스처의 디테일 레이어
├─ 파티클 밀도 감소
└─ 그림자 해상도

3단계 (눈에 띔 - 최후의 수단)
├─ 근거리 텍스처
├─ 플레이어 캐릭터
├─ UI 요소
└─ 주요 음악/보이스
실제로 품질 저하가 발생했는지 어떻게 모니터링해?

개발 빌드에서는 실시간 오버레이를 표시합니다.

class MemoryDebugOverlay { public: void Render() { if (!g_ShowDebugOverlay) return; auto& budgetMgr = MemoryBudgetManager::Get(); // 각 카테고리별 바 그래프 float y = 20.0f; for (auto& [category, pool] : budgetMgr.GetPools()) { float percent = pool->GetUsagePercent(); // 색상: 녹색 -> 노랑 -> 빨강 Color barColor = percent < 80 ? Color::Green : percent < 95 ? Color::Yellow : Color::Red; // 바 그리기 DrawRect(10, y, 200 * (percent / 100), 16, barColor); DrawText(220, y, "%s: %.1f%% (%s / %s)", GetCategoryName(category), percent, FormatBytes(pool->GetUsed()), FormatBytes(pool->GetBudget())); // 피크 마커 float peakX = 10 + 200 * (pool->GetPeakPercent() / 100); DrawLine(peakX, y, peakX, y + 16, Color::White); y += 22; } // 총합 size_t totalUsed = budgetMgr.GetTotalUsed(); size_t totalBudget = budgetMgr.GetTotalBudget(); DrawText(10, y + 10, "TOTAL: %s / %s (%.1f%%)", FormatBytes(totalUsed), FormatBytes(totalBudget), (float)totalUsed / totalBudget * 100); // 품질 저하 경고 if (g_QualityDegraded) { DrawText(10, y + 40, "⚠️ QUALITY DEGRADED: MipBias=%d, LODOffset=%d", g_CurrentMipBias, g_CurrentLODOffset); } } };

Part 4. 플랫폼별 최적화 전략

PS5와 Xbox Series X 외에 Nintendo Switch는 어떻게 대응해?

Switch는 4GB 메모리에 모바일 GPU를 사용하므로 완전히 다른 접근이 필요합니다.

Nintendo Switch 제약사항
═══════════════════════════════════════════════════════════

메모리: 4GB (게임 사용 가능 ~3GB)
├─ PS5의 1/4 수준
├─ 텍스처 해상도 대폭 감소 필수
└─ 동시 로드 에셋 수 제한

GPU: Nvidia Tegra X1 (Maxwell 기반)
├─ PS5 대비 ~1/20 성능
├─ 720p 타겟 (독모드: 1080p)
└─ 셰이더 복잡도 제한

도킹/핸드헬드 모드
├─ 독: 768MHz GPU, 1080p
├─ 핸드헬드: 307MHz GPU, 720p
└─ 런타임에 동적 예산 조정 필요
같은 게임을 PS5와 Switch 둘 다 지원하려면 어떻게 해?

플랫폼별 에셋 버전과 스케일러블 예산을 사용합니다.

// 플랫폼별 예산 정의 struct PlatformBudget { size_t texturePool; size_t meshPool; size_t audioPool; int maxTextureSize; int maxMeshLOD; int maxNPCCount; }; constexpr PlatformBudget g_PS5Budget = { .texturePool = 5500 * MB, .meshPool = 1800 * MB, .audioPool = 800 * MB, .maxTextureSize = 4096, // 4K 텍스처 .maxMeshLOD = 0, // 최고 품질 LOD .maxNPCCount = 200 // 동시 NPC 수 }; constexpr PlatformBudget g_XboxSeriesXBudget = { .texturePool = 5000 * MB, // Fast Pool 고려 .meshPool = 1600 * MB, .audioPool = 700 * MB, .maxTextureSize = 4096, .maxMeshLOD = 0, .maxNPCCount = 180 }; constexpr PlatformBudget g_SwitchBudget = { .texturePool = 800 * MB, // 대폭 감소 .meshPool = 400 * MB, .audioPool = 200 * MB, .maxTextureSize = 1024, // 1K로 제한 .maxMeshLOD = 2, // LOD2부터 시작 .maxNPCCount = 50 // NPC 수 대폭 감소 }; // 에셋 임포트 시 플랫폼별 버전 생성 class AssetPipeline { public: void ProcessTexture(const Texture& source) { // PS5/Xbox: 원본 4K ExportTexture(source, Platform::PS5, 4096, Format::BC7); ExportTexture(source, Platform::XboxSeriesX, 4096, Format::BC7); // Switch: 1K로 다운스케일 + ASTC 압축 Texture downscaled = Downscale(source, 1024); ExportTexture(downscaled, Platform::Switch, 1024, Format::ASTC_6x6); } };
Switch에서 NPC를 50명으로 줄이면 게임이 허전해지지 않아?

여러 트릭을 사용합니다.

저사양 플랫폼에서 밀도 유지 트릭

  • 임포스터(Impostor): 먼 거리 NPC를 빌보드 이미지로 대체
  • 페이크 NPC: 애니메이션만 재생하는 단순 메시 (AI 없음)
  • LOD 군중: 멀리서는 10명이 한 메시로 합쳐진 군중 LOD
  • 안개/어둠 활용: 시야 거리를 줄여서 로드해야 할 영역 감소
  • 실내 집중: 실외 오픈월드보다 실내 구간을 더 활용
// 플랫폼별 군중 렌더링 전략 class CrowdSystem { public: void UpdateCrowd(const CameraInfo& camera) { auto& budget = GetPlatformBudget(); int realNPCCount = 0; int impostorCount = 0; int fakeCount = 0; for (auto& npc : m_AllNPCs) { float distance = Distance(npc.Position, camera.Position); if (distance < REAL_NPC_DISTANCE && realNPCCount < budget.maxNPCCount) { // 가까우면 진짜 NPC (AI + 풀 메시) npc.SetRenderMode(RenderMode::Full); realNPCCount++; } else if (distance < IMPOSTOR_DISTANCE) { // 중거리: 임포스터 (빌보드 + 간단한 움직임) npc.SetRenderMode(RenderMode::Impostor); impostorCount++; } else { // 원거리: 완전히 숨김 또는 점 스프라이트 npc.SetRenderMode(RenderMode::Hidden); } } // Switch에서는 거리 기준을 더 짧게 #if PLATFORM_SWITCH REAL_NPC_DISTANCE = 30.0f; // PS5: 100.0f IMPOSTOR_DISTANCE = 60.0f; // PS5: 200.0f #endif } };

Part 5. 프로파일링과 최적화 도구

메모리 사용량을 어떻게 측정하고 분석해?

각 플랫폼마다 전용 프로파일링 도구가 있습니다.

플랫폼별 메모리 프로파일링 도구
═══════════════════════════════════════════════════════════

PlayStation 5
├─ Razor GPU Profiler - GPU 메모리 분석
├─ Memory Analyzer - 힙 분석, 누수 탐지
└─ SDK 내장 Memory Footprint API

Xbox Series X
├─ PIX (Performance Investigator for Xbox)
│   ├─ GPU Memory 탭: VRAM 사용 시각화
│   ├─ CPU Memory 탭: 힙/스택 분석
│   └─ Timeline: 시간별 메모리 변화
└─ Xbox Memory Analysis Tool

Nintendo Switch
├─ NVN Memory Viewer
├─ Nintendo SDK Memory Tracker
└─ 자체 로깅 시스템 구축 권장

크로스 플랫폼
├─ RenderDoc - GPU 리소스 분석
├─ 커스텀 인게임 오버레이
└─ 텔레메트리 시스템
PIX를 사용해서 어떻게 메모리 문제를 찾아?

PIX의 메모리 분석 기능을 활용한 일반적인 워크플로우입니다.

PIX 메모리 분석 워크플로우

  1. 타이밍 캡처 시작: 문제가 발생하는 구간에서 캡처
  2. Memory 탭 열기: GPU/CPU 메모리 사용량 확인
  3. 히트맵 분석: 어떤 리소스가 가장 많은 메모리를 사용하는지
  4. 힙 스냅샷 비교: 시간 A와 시간 B의 차이 = 누수 후보
  5. 콜스택 추적: 메모리 할당이 어디서 발생했는지 확인
// PIX와 연동하는 메모리 마커 #if PLATFORM_XBOX #include <pix3.h> class MemoryTracker { public: void* AllocateTracked(size_t size, const char* tag) { // PIX에 할당 이벤트 기록 PIXBeginEvent(PIX_COLOR_INDEX(0), "Alloc: %s (%zu bytes)", tag, size); void* ptr = PlatformAlloc(size); // 메타데이터 저장 (나중에 분석용) if (ptr) { m_AllocationMap[ptr] = { tag, size, GetStackTrace() }; } PIXEndEvent(); return ptr; } void DumpLeaks() { // 해제되지 않은 모든 할당 출력 for (auto& [ptr, info] : m_AllocationMap) { LogError("LEAK: %s - %zu bytes at %p", info.tag, info.size, ptr); LogError(" Allocated from:\n%s", info.stackTrace.c_str()); } } }; #endif
자동으로 예산 초과를 감지하고 알림 받을 수 없어?

// 빌드 파이프라인용 메모리 체크 스크립트 (Python) import subprocess import json def check_memory_budget(build_path, platform): # 게임을 헤드리스 모드로 실행하고 메모리 덤프 result = subprocess.run([ build_path, '--headless', '--run-memory-test', '--output-json', '/tmp/memory_report.json' ], capture_output=True) with open('/tmp/memory_report.json') as f: report = json.load(f) # 각 카테고리별 예산 체크 budgets = PLATFORM_BUDGETS[platform] violations = [] for category, used in report['memory_usage'].items(): budget = budgets.get(category, 0) if used > budget * 0.95: # 95% 넘으면 경고 violations.append({ 'category': category, 'used': used, 'budget': budget, 'percent': used / budget * 100 }) if violations: print("⚠️ MEMORY BUDGET VIOLATIONS:") for v in violations: print(f" {v['category']}: {v['used']/MB:.1f}MB / {v['budget']/MB:.1f}MB ({v['percent']:.1f}%)") # Slack/Teams 알림 send_notification(f"Memory budget exceeded on {platform}") return False return True # CI에서 호출 if __name__ == '__main__': for platform in ['PS5', 'XboxSeriesX', 'Switch']: if not check_memory_budget(f'./build/{platform}/game', platform): exit(1) # 빌드 실패 처리

Part 6. 런타임 예산 관리 시스템

게임 실행 중에 예산을 동적으로 조절할 수 있어?

네, 동적 예산 재분배 시스템을 구현할 수 있습니다. 게임 상황에 따라 예산을 유연하게 조절하는 거죠.

class DynamicBudgetManager { private: std::unordered_map<BudgetCategory, size_t> m_CurrentBudgets; size_t m_TotalBudget; GameContext m_Context; public: void UpdateBudgetsForContext(GameContext newContext) { if (m_Context == newContext) return; m_Context = newContext; switch (newContext) { case GameContext::OpenWorld: // 오픈월드: 텍스처와 스트리밍에 예산 집중 RebalanceBudget({ { BudgetCategory::Textures, 0.45f }, // 45% { BudgetCategory::Meshes, 0.15f }, { BudgetCategory::Audio, 0.08f }, { BudgetCategory::Animation, 0.10f }, { BudgetCategory::Physics, 0.05f }, { BudgetCategory::AI, 0.07f }, { BudgetCategory::Render, 0.10f } }); break; case GameContext::CutScene: // 컷신: 캐릭터 메시와 애니메이션에 집중 RebalanceBudget({ { BudgetCategory::Textures, 0.25f }, { BudgetCategory::Meshes, 0.25f }, // 캐릭터 고품질 { BudgetCategory::Audio, 0.15f }, // 보이스 { BudgetCategory::Animation, 0.20f }, // 페이셜 등 { BudgetCategory::Physics, 0.02f }, { BudgetCategory::AI, 0.03f }, { BudgetCategory::Render, 0.10f } }); break; case GameContext::Combat: // 전투: 파티클/이펙트와 물리에 집중 RebalanceBudget({ { BudgetCategory::Textures, 0.30f }, { BudgetCategory::Meshes, 0.12f }, { BudgetCategory::Audio, 0.10f }, { BudgetCategory::Animation, 0.12f }, { BudgetCategory::Physics, 0.12f }, // 충돌, 데브리 { BudgetCategory::AI, 0.09f }, // 적 AI { BudgetCategory::Render, 0.15f } // 이펙트 버퍼 }); break; } } private: void RebalanceBudget(const std::map<BudgetCategory, float>& ratios) { for (auto& [category, ratio] : ratios) { size_t newBudget = static_cast<size_t>(m_TotalBudget * ratio); size_t oldBudget = m_CurrentBudgets[category]; if (newBudget < oldBudget) { // 예산 감소: 먼저 메모리 해제 TrimCategory(category, oldBudget - newBudget); } m_CurrentBudgets[category] = newBudget; GetPool(category)->SetBudget(newBudget); } } };
예산 재분배 시 기존 로드된 에셋은 어떻게 돼?

예산이 줄어든 카테고리는 점진적 언로드를 수행합니다.

class GradualUnloader { private: std::queue<AssetHandle> m_UnloadQueue; size_t m_TargetReduction; size_t m_UnloadedSoFar; public: void StartGradualUnload(BudgetCategory category, size_t bytesToFree) { m_TargetReduction = bytesToFree; m_UnloadedSoFar = 0; // 우선순위 기준으로 언로드 대상 선정 std::vector<AssetInfo> candidates = GetAssetsInCategory(category); // 정렬: 마지막 사용 시간이 오래된 것 + 크기가 큰 것 std::sort(candidates.begin(), candidates.end(), [](const AssetInfo& a, const AssetInfo& b) { // 점수 = 마지막 사용 후 경과 시간 * 크기 float scoreA = a.timeSinceLastUse * a.size; float scoreB = b.timeSinceLastUse * b.size; return scoreA > scoreB; // 높은 점수 = 먼저 언로드 }); // 필요한 만큼만 큐에 추가 size_t accumulated = 0; for (auto& asset : candidates) { m_UnloadQueue.push(asset.handle); accumulated += asset.size; if (accumulated >= bytesToFree) break; } } // 매 프레임 호출 - 점진적으로 언로드 void ProcessUnloadQueue(int maxPerFrame = 3) { int processed = 0; while (!m_UnloadQueue.empty() && processed < maxPerFrame) { AssetHandle handle = m_UnloadQueue.front(); m_UnloadQueue.pop(); size_t freedBytes = UnloadAsset(handle); m_UnloadedSoFar += freedBytes; processed++; } } bool IsComplete() const { return m_UnloadedSoFar >= m_TargetReduction; } };

한 프레임에 모든 걸 언로드하면 히칭(끊김)이 발생하므로, 여러 프레임에 걸쳐 점진적으로 수행합니다.

실제 AAA 게임들은 메모리 예산을 어떻게 관리해?

실제 게임의 메모리 관리 전략

  • Spider-Man (Insomniac): 도시 전체를 8x8 그리드로 분할, 움직임 방향 예측 프리로드
  • God of War: 카메라 컷 활용한 로딩 숨기기, 협곡/좁은 통로에서 언로드

메모리 예산 관련해서 자주 발생하는 버그는 뭐야?

가장 흔한 문제들입니다.

자주 발생하는 메모리 예산 버그

  • 예상치 못한 피크: 특정 상황(보스전, 많은 적 동시 등장)에서만 초과
  • 점진적 누수: 조금씩 새서 2시간 플레이 후 크래시
  • 단편화: 총량은 여유 있지만 연속 공간 부족
  • 스트리밍 레이스: 로드 중인데 또 요청이 와서 중복 로드
  • 플랫폼 차이: PS5에서 되던 게 Switch에서 터짐
// 메모리 누수 탐지 패턴 class LeakDetector { private: std::unordered_map<void*, AllocationInfo> m_Allocations; std::vector<size_t> m_UsageHistory; // 매 분마다 기록 public: void RecordUsage() { m_UsageHistory.push_back(GetCurrentUsage()); // 지속적 증가 패턴 감지 if (m_UsageHistory.size() >= 10) { bool alwaysIncreasing = true; for (size_t i = m_UsageHistory.size() - 10; i < m_UsageHistory.size() - 1; i++) { if (m_UsageHistory[i + 1] <= m_UsageHistory[i]) { alwaysIncreasing = false; break; } } if (alwaysIncreasing) { LogWarning("⚠️ Potential memory leak detected!"); LogWarning(" Usage trend: %zu -> %zu MB over 10 minutes", m_UsageHistory[m_UsageHistory.size() - 10] / MB, m_UsageHistory.back() / MB); DumpTopAllocations(); } } } void DumpTopAllocations() { // 가장 많이 할당한 콜스택 Top 10 std::map<std::string, size_t> stackToSize; for (auto& [ptr, info] : m_Allocations) { stackToSize[info.stackTrace] += info.size; } std::vector<std::pair<std::string, size_t>> sorted( stackToSize.begin(), stackToSize.end()); std::sort(sorted.begin(), sorted.end(), [](auto& a, auto& b) { return a.second > b.second; }); LogInfo("Top 10 allocation sources:"); for (int i = 0; i < 10 && i < sorted.size(); i++) { LogInfo(" %d. %zu MB from:\n%s", i + 1, sorted[i].second / MB, sorted[i].first.c_str()); } } };
단편화 문제는 어떻게 해결해?

여러 전략이 있습니다.

메모리 단편화 해결 전략

  • 풀 할당자: 같은 크기 객체끼리 묶어서 할당/해제
  • 슬랩 할당자: 자주 쓰는 크기별 전용 슬랩
  • 압축(Compaction): 로딩 화면에서 메모리 재배치
  • 가상 메모리 활용: 물리 메모리는 단편화, 가상 주소는 연속
  • 크기별 힙 분리: 작은 객체 힙 / 큰 객체 힙 분리
// 사이즈 클래스 기반 할당자 class SizeClassAllocator { private: // 자주 사용되는 크기별 풀 FixedSizePool m_Pool16B; // 작은 구조체 FixedSizePool m_Pool64B; // 컴포넌트 FixedSizePool m_Pool256B; // 게임 오브젝트 FixedSizePool m_Pool1KB; // AI 상태 FixedSizePool m_Pool4KB; // 버퍼 GeneralHeap m_LargeHeap; // 4KB 초과 public: void* Allocate(size_t size) { // 적절한 풀 선택 if (size <= 16) return m_Pool16B.Allocate(); if (size <= 64) return m_Pool64B.Allocate(); if (size <= 256) return m_Pool256B.Allocate(); if (size <= 1024) return m_Pool1KB.Allocate(); if (size <= 4096) return m_Pool4KB.Allocate(); // 큰 할당은 일반 힙 return m_LargeHeap.Allocate(size); } // 고정 크기 풀은 단편화가 없음! // - 모든 블록이 같은 크기 // - 해제된 블록은 바로 재사용 가능 // - 내부 단편화는 있지만 외부 단편화 없음 };

핵심 정리

  • 고정 하드웨어: 콘솔은 메모리가 절대 늘어나지 않으므로 철저한 예산 관리 필수
  • 플랫폼별 차이: PS5(16GB 통합), Xbox(Fast/Slow 분리), Switch(4GB)
  • 카테고리별 예산: 텍스처, 메시, 오디오 등 용도별 풀 분리
  • 품질 저하 전략: 크래시보다 화질 저하가 나음 - 단계별 대응
  • 동적 재분배: 게임 상황(오픈월드/컷신/전투)에 따라 예산 재조정
  • 프로파일링: PIX, Razor 등 플랫폼 도구 + CI 자동 체크
  • 안전 마진: 항상 500MB 이상 여유 확보 (피크, 단편화 대비)
