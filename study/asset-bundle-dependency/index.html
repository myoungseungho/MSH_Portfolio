번들 간 의존성 관리

에셋 번들의 복잡한 참조 관계를 이해하고 효율적으로 관리하기

Part 1. 에셋 번들 의존성이란?

에셋 번들 간에 의존성이 있다는 게 무슨 말이야?

의존성(Dependency)은 한 에셋이 다른 에셋을 참조할 때 발생합니다. 번들 간 의존성은 이 참조가 다른 번들에 있는 에셋을 가리킬 때 생깁니다.

간단한 예시:

캐릭터 프리팹 (character_hero.bundle)
┌─────────────────────────────────────────────────────────┐
│ HeroPrefab                                              │
│ ├── MeshRenderer                                        │
│ │   └── Material: HeroMaterial ──────────────┐         │
│ │                                             │         │
│ └── AudioSource                               │         │
│     └── Clip: HeroVoice ─────────────────────┼────┐    │
└───────────────────────────────────────────────┼────┼────┘
                                                │    │
                                                ↓    ↓
공유 머티리얼 번들 (shared_materials.bundle)    │    │
┌─────────────────────────────────────────┐    │    │
│ HeroMaterial ←───────────────────────────┘    │    │
│ └── Texture: HeroTexture ────────────────────┼────┘
└──────────────────────────────────────────────┼────────┘
                                               │
공유 오디오 번들 (shared_audio.bundle)          │
┌──────────────────────────────────────────────┴────────┐
│ HeroVoice ←───────────────────────────────────────────┘
└───────────────────────────────────────────────────────┘

의존성 그래프:
character_hero.bundle
    ├──→ shared_materials.bundle
    └──→ shared_audio.bundle

이 예시에서 character_hero.bundle은 shared_materials.bundle과 shared_audio.bundle에 의존합니다. 캐릭터를 로드하려면 먼저 이 두 번들이 로드되어 있어야 합니다.

직접 의존성과 간접 의존성의 차이가 뭐야?

의존성에는 두 가지 유형이 있습니다:

직접 의존성 (Direct Dependency):
─────────────────────────────────
번들 A가 번들 B의 에셋을 직접 참조

A.bundle ────→ B.bundle
  (A가 B에 직접 의존)


간접 의존성 (Transitive/Indirect Dependency):
─────────────────────────────────────────────
번들 A → B → C 순서로 의존

A.bundle ────→ B.bundle ────→ C.bundle
  ↑             ↑               ↑
  A는 B에       B는 C에
  직접 의존     직접 의존

  A는 C에 간접 의존!


실제 예시:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  level_forest.bundle                                            │
│      │                                                          │
│      ├──→ characters_npc.bundle (직접 의존)                     │
│      │        │                                                 │
│      │        └──→ shared_animations.bundle (간접 의존)         │
│      │                                                          │
│      └──→ environment_trees.bundle (직접 의존)                  │
│               │                                                 │
│               └──→ shared_materials.bundle (간접 의존)          │
│                                                                 │
│  level_forest의 모든 의존성:                                     │
│  - 직접: characters_npc, environment_trees                      │
│  - 간접: shared_animations, shared_materials                    │
│  - 전체: 4개 번들                                                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

주의: 간접 의존성도 로드해야 함!

A 번들을 로드할 때 B만 로드하면 안 됩니다. C까지 모두 로드해야 A의 에셋이 정상 작동합니다.

의존성은 어떻게 자동으로 생기는 거야?

Unity에서 에셋 번들을 빌드할 때, 엔진이 자동으로 의존성을 분석합니다:

에셋 번들 빌드 시 의존성 분석 과정:

1단계: 에셋 참조 수집
┌─────────────────────────────────────────────────────────────┐
│ HeroPrefab 분석:                                             │
│                                                             │
│ - HeroPrefab (포함)                                          │
│   └── MeshRenderer                                          │
│       └── Material: "Assets/Materials/HeroMaterial.mat"     │
│           └── Texture: "Assets/Textures/HeroTex.png"        │
│   └── Animator                                              │
│       └── Controller: "Assets/Anim/HeroController.controller"│
│           └── Clip: "Assets/Anim/HeroIdle.anim"             │
└─────────────────────────────────────────────────────────────┘

2단계: 번들 할당 확인
┌─────────────────────────────────────────────────────────────┐
│ 각 에셋이 어느 번들에 속하는지 확인:                         │
│                                                             │
│ HeroPrefab           → character_hero (현재 빌드 대상)       │
│ HeroMaterial.mat     → shared_materials                     │
│ HeroTex.png          → shared_textures                      │
│ HeroController       → character_hero (같은 번들)           │
│ HeroIdle.anim        → character_hero (같은 번들)           │
└─────────────────────────────────────────────────────────────┘

3단계: 의존성 기록
┌─────────────────────────────────────────────────────────────┐
│ character_hero.bundle.manifest:                              │
│                                                             │
│ Dependencies:                                                │
│   - shared_materials                                         │
│   - shared_textures                                          │
└─────────────────────────────────────────────────────────────┘

핵심 규칙

참조하는 에셋이 다른 번들에 있으면 → 의존성 발생

참조하는 에셋이 같은 번들에 있으면 → 의존성 없음 (포함됨)

참조하는 에셋이 어떤 번들에도 없으면 → 복사되어 포함 (중복!)

Part 2. 의존성 관리가 왜 중요한가?

의존성을 관리하지 않으면 어떤 문제가 생겨?

의존성 관리 실패는 세 가지 심각한 문제를 일으킵니다:

문제 1: 에셋 중복 (Duplication)

공유 텍스처가 번들에 미할당된 경우:
HeroTexture.png (번들 미지정)

│ character_hero      │     │ character_villain   │
│ ├── HeroPrefab      │     │ ├── VillainPrefab   │
│ │   └── Material    │     │ │   └── Material    │
│ │       └── Tex ────┼──┐  │ │       └── Tex ────┼──┐
│ │                   │  │  │ │                   │  │
│ │  [HeroTexture 복사]│←─┘  │ │  [HeroTexture 복사]│←─┘
│ │  (10MB 중복!)     │     │ │  (10MB 중복!)     │

═══════════════════════════════════════════════════════════════

정상 케이스:

2. character_hero.bundle 로드 ✓
3. HeroPrefab 로드 → Material 참조 해결 ✓

오류 케이스:
1. character_hero.bundle만 로드
2. HeroPrefab 로드 → Material 참조... 어디있지?

Part 3. 의존성 추적 방법

번들의 의존성을 어떻게 확인해?

Unity에서는 여러 가지 방법으로 의존성을 확인할 수 있습니다:

// 방법 1: 매니페스트에서 직접 의존성 확인 public void CheckDirectDependencies(string bundleName) { // 마스터 매니페스트 로드 var manifestBundle = AssetBundle.LoadFromFile( Path.Combine(bundlePath, "AssetBundles") ); var manifest = manifestBundle.LoadAsset<AssetBundleManifest>( "AssetBundleManifest" ); // 직접 의존성 (1단계) string[] directDeps = manifest.GetDirectDependencies(bundleName); Debug.Log($"Direct dependencies of {bundleName}:"); foreach (var dep in directDeps) { Debug.Log($" - {dep}"); } } // 방법 2: 모든 의존성 확인 (간접 포함) public void CheckAllDependencies(string bundleName) { // GetAllDependencies는 재귀적으로 모든 의존성을 반환 string[] allDeps = manifest.GetAllDependencies(bundleName); Debug.Log($"All dependencies of {bundleName} ({allDeps.Length}):"); foreach (var dep in allDeps) { Debug.Log($" - {dep}"); } }
GetDirectDependencies vs GetAllDependencies:

의존성 구조:
A ─→ B ─→ D
    ↓
    C

GetDirectDependencies("A"):
결과: [B, C]  (1단계만)

GetAllDependencies("A"):
결과: [B, C, D]  (전체 재귀)
.manifest 파일 내용은 어떻게 생겼어?

각 번들과 함께 생성되는 .manifest 파일은 YAML 형식입니다:

HashAppended: 0 ClassTypes: - Class: 1 # GameObject - Class: 4 # Transform - Class: 23 # MeshRenderer - Class: 33 # MeshFilter - Class: 137 # SkinnedMeshRenderer SerializeReferenceClassIdentifiers: [] Assets: - Assets/Characters/Hero/HeroPrefab.prefab - Assets/Characters/Hero/HeroAnimator.controller - Assets/Characters/Hero/HeroIdle.anim Dependencies: - shared_materials - shared_textures - shared_animations

에디터에서 빌드 전에 의존성을 미리 확인할 수 있어?

AssetDatabase API를 사용하여 빌드 전에 의존성을 분석할 수 있습니다:

// 에디터 전용: 빌드 전 의존성 분석 using UnityEditor; public class DependencyAnalyzer { [MenuItem("Tools/Analyze Bundle Dependencies")] public static void AnalyzeDependencies() { // 모든 번들 이름 가져오기 string[] allBundles = AssetDatabase.GetAllAssetBundleNames(); foreach (string bundleName in allBundles) { // 이 번들에 포함된 에셋 경로들 string[] assetPaths = AssetDatabase.GetAssetPathsFromAssetBundle(bundleName); HashSet<string> dependentBundles = new(); foreach (string assetPath in assetPaths) { // 이 에셋의 모든 의존성 경로 string[] deps = AssetDatabase.GetDependencies(assetPath, true); foreach (string depPath in deps) { // 의존 에셋의 번들 이름 string depBundle = AssetImporter.GetAtPath(depPath)?.assetBundleName; if (!string.IsNullOrEmpty(depBundle) && depBundle != bundleName) { dependentBundles.Add(depBundle); } } } Debug.Log($"{bundleName} depends on: {string.Join(", ", dependentBundles)}"); } } // 중복 에셋 찾기 (번들에 할당되지 않은 공유 에셋) [MenuItem("Tools/Find Duplicate Assets")] public static void FindDuplicates() { Dictionary<string, List<string>> assetUsage = new(); string[] allBundles = AssetDatabase.GetAllAssetBundleNames(); foreach (string bundleName in allBundles) { string[] assetPaths = AssetDatabase.GetAssetPathsFromAssetBundle(bundleName); foreach (string assetPath in assetPaths) { string[] deps = AssetDatabase.GetDependencies(assetPath, true); foreach (string depPath in deps) { // 번들에 할당되지 않은 에셋 var importer = AssetImporter.GetAtPath(depPath); if (importer != null && string.IsNullOrEmpty(importer.assetBundleName)) { if (!assetUsage.ContainsKey(depPath)) assetUsage[depPath] = new List<string>(); assetUsage[depPath].Add(bundleName); } } } } // 2개 이상 번들에서 사용되는 미할당 에셋 = 중복! foreach (var kvp in assetUsage) { if (kvp.Value.Count >= 2) { Debug.LogWarning( $"DUPLICATE: {kvp.Key} used by {kvp.Value.Count} bundles" ); } } } }

Part 4. 의존성 로딩 전략

의존성이 있는 번들은 어떤 순서로 로드해야 해?

핵심 규칙: 의존 번들을 먼저 로드해야 합니다.

올바른 로딩 순서:

의존성 그래프:
character_hero ─→ shared_materials ─→ shared_textures
      │
      └─→ shared_animations

로딩 순서 (역방향):
┌─────────────────────────────────────────────────────────────┐
│ 1. shared_textures.bundle    (의존성 없음)                  │
│    ↓                                                        │
│ 2. shared_materials.bundle   (textures에 의존)              │
│    ↓                                                        │
│ 3. shared_animations.bundle  (의존성 없음)                  │
│    ↓                                                        │
│ 4. character_hero.bundle     (materials, animations에 의존) │
│    ↓                                                        │
│ 5. HeroPrefab 로드 가능!     (모든 참조 해결됨)             │
└─────────────────────────────────────────────────────────────┘
// 의존성을 포함한 번들 로드 (올바른 방법) public IEnumerator LoadBundleWithDependencies(string bundleName) { // 1. 매니페스트에서 모든 의존성 가져오기 string[] dependencies = m_Manifest.GetAllDependencies(bundleName); // 2. 의존 번들들 먼저 로드 foreach (string dep in dependencies) { if (!IsLoaded(dep)) { yield return LoadSingleBundle(dep); } } // 3. 요청한 번들 로드 yield return LoadSingleBundle(bundleName); } private IEnumerator LoadSingleBundle(string bundleName) { string path = Path.Combine(m_BundlePath, bundleName); var request = AssetBundle.LoadFromFileAsync(path); yield return request; if (request.assetBundle != null) { m_LoadedBundles[bundleName] = request.assetBundle; } }
병렬로 로드하면 더 빠르지 않아?

독립적인 번들은 병렬 로드가 가능합니다. 하지만 의존 순서는 지켜야 합니다:

병렬 로드 가능한 경우:

의존성 그래프:
character_hero
    ├──→ shared_materials ─→ shared_textures
    └──→ shared_animations

병렬화:
┌─────────────────────────────────────────────────────────────┐
│ 단계 1: 리프 노드 병렬 로드                                  │
│ ┌─────────────────┐  ┌─────────────────┐                    │
│ │ shared_textures │  │ shared_animations│   동시 로드 가능! │
│ └────────┬────────┘  └────────┬────────┘                    │
│          ↓                    ↓                             │
│ 단계 2: 중간 노드                                            │
│ ┌─────────────────┐                                         │
│ │ shared_materials│  (textures 완료 대기 후 로드)           │
│ └────────┬────────┘                                         │
│          ↓                                                   │
│ 단계 3: 루트 노드                                            │
│ ┌─────────────────┐                                         │
│ │ character_hero  │  (모든 의존성 완료 후 로드)             │
│ └─────────────────┘                                         │
└─────────────────────────────────────────────────────────────┘

시간 비교:
순차 로드: ████████████████████████████  (28초)
병렬 로드: ████████████████               (16초)
// 위상 정렬 기반 병렬 로드 public class ParallelBundleLoader { public IEnumerator LoadWithParallelDependencies(string bundleName) { // 모든 의존성 수집 var allDeps = new HashSet<string>(m_Manifest.GetAllDependencies(bundleName)); allDeps.Add(bundleName); // 의존성 레벨별로 분류 (위상 정렬) var levels = TopologicalSort(allDeps); // 레벨별로 병렬 로드 foreach (var level in levels) { // 같은 레벨은 병렬 로드 var loadOperations = new List<AssetBundleCreateRequest>(); foreach (string bundle in level) { if (!IsLoaded(bundle)) { var op = AssetBundle.LoadFromFileAsync(GetPath(bundle)); loadOperations.Add(op); } } // 이 레벨의 모든 로드 완료 대기 foreach (var op in loadOperations) { yield return op; CacheBundle(op.assetBundle); } // 다음 레벨로 (의존성 해결됨) } } private List<List<string>> TopologicalSort(HashSet<string> bundles) { var inDegree = new Dictionary<string, int>(); var levels = new List<List<string>>(); // 진입 차수 계산 foreach (var bundle in bundles) { var deps = m_Manifest.GetDirectDependencies(bundle); inDegree[bundle] = deps.Count(d => bundles.Contains(d)); } // 레벨별 분류 while (inDegree.Count > 0) { var currentLevel = inDegree .Where(kv => kv.Value == 0) .Select(kv => kv.Key) .ToList(); levels.Add(currentLevel); foreach (var bundle in currentLevel) { inDegree.Remove(bundle); // 이 번들에 의존하는 다른 번들의 차수 감소 foreach (var other in inDegree.Keys.ToList()) { if (m_Manifest.GetDirectDependencies(other).Contains(bundle)) inDegree[other]--; } } } return levels; } }

Part 5. 공통 에셋 분리 전략

공통으로 쓰이는 에셋은 어떻게 관리해?

// 에디터 스크립트: 공용 에셋 자동 번들 할당 public class SharedBundleAssigner { [MenuItem("Tools/Assign Shared Bundles")] public static void AssignSharedBundles() { // 사용 횟수 분석 var usageCount = AnalyzeAssetUsage(); foreach (var kvp in usageCount) { string assetPath = kvp.Key; int useCount = kvp.Value; var importer = AssetImporter.GetAtPath(assetPath); if (importer == null || !string.IsNullOrEmpty(importer.assetBundleName)) continue; // 이미 할당됨 // 2개 이상 번들에서 사용되면 shared로 if (useCount >= 2) { string sharedBundle = DetermineSharedBundle(assetPath); importer.assetBundleName = sharedBundle; importer.SaveAndReimport(); Debug.Log($"Assigned {assetPath} to {sharedBundle}"); } } } private static string DetermineSharedBundle(string assetPath) { // 에셋 타입에 따라 적절한 shared 번들 결정 if (assetPath.EndsWith(".png") || assetPath.EndsWith(".tga")) return "shared_textures"; if (assetPath.EndsWith(".mat")) return "shared_materials"; if (assetPath.EndsWith(".shader")) return "shared_shaders"; if (assetPath.EndsWith(".wav") || assetPath.EndsWith(".ogg")) return "shared_audio"; return "shared_misc"; } }

Part 6. 순환 의존성 문제

순환 의존성이 뭐고 왜 문제야?

순환 의존성은 A가 B에 의존하고, B가 다시 A에 의존하는 상황입니다:

순환 의존성 예시:

직접 순환:
┌─────────────┐      ┌─────────────┐
│ bundle_a    │─────→│ bundle_b    │
│             │←─────│             │
└─────────────┘      └─────────────┘
   A → B → A → B → ...  (무한 루프!)

간접 순환:
┌─────────────┐      ┌─────────────┐      ┌─────────────┐
│ bundle_a    │─────→│ bundle_b    │─────→│ bundle_c    │
│             │                           │             │
└─────────────┘                           └──────┬──────┘
      ↑                                          │
      └──────────────────────────────────────────┘
   A → B → C → A → B → C → ...

순환 의존성의 문제점

  • 무한 로드 루프: A 로드 → B 필요 → B 로드 → A 필요 → ...
  • 언로드 불가: A가 B를 참조하고 B가 A를 참조하면 둘 다 해제 불가
  • 빌드 경고/에러: Unity는 순환 의존성을 경고함
순환 의존성은 어떻게 발생해?

흔한 순환 의존성 발생 시나리오:

시나리오 1: 양방향 참조
┌─────────────────────────────────────────────────────────────┐

// 순환 의존성 감지기 public class CircularDependencyDetector { [MenuItem("Tools/Detect Circular Dependencies")] public static void DetectCircular() { var bundles = AssetDatabase.GetAllAssetBundleNames(); var dependencies = new Dictionary<string, HashSet<string>>(); // 의존성 그래프 구축 foreach (var bundle in bundles) { dependencies[bundle] = GetBundleDependencies(bundle); } // DFS로 순환 탐지 foreach (var bundle in bundles) { var visited = new HashSet<string>(); var path = new List<string>(); if (HasCycle(bundle, dependencies, visited, path)) { string cycle = string.Join(" → ", path); Debug.LogError($"Circular dependency detected: {cycle}"); } } } private static bool HasCycle( string bundle, Dictionary<string, HashSet<string>> deps, HashSet<string> visited, List<string> path) { if (path.Contains(bundle)) { path.Add(bundle); // 순환 경로 완성 return true; } if (visited.Contains(bundle)) return false; visited.Add(bundle); path.Add(bundle); if (deps.TryGetValue(bundle, out var bundleDeps)) { foreach (var dep in bundleDeps) { if (HasCycle(dep, deps, visited, path)) return true; } } path.RemoveAt(path.Count - 1); return false; } }

// 완전한 번들 매니저 (의존성 자동 처리) public class BundleManager : MonoBehaviour { private static BundleManager s_Instance; private AssetBundleManifest m_Manifest; private Dictionary<string, LoadedBundle> m_LoadedBundles = new(); private class LoadedBundle { public AssetBundle Bundle; public int RefCount; public HashSet<string> Dependencies; } // 번들 로드 (의존성 자동 처리) public IEnumerator LoadBundleAsync(string bundleName, Action<AssetBundle> onComplete) { // 이미 로드됨? if (m_LoadedBundles.TryGetValue(bundleName, out var existing)) { existing.RefCount++; onComplete?.Invoke(existing.Bundle); yield break; } // 의존성 먼저 로드 var dependencies = m_Manifest.GetAllDependencies(bundleName); foreach (var dep in dependencies) { if (!m_LoadedBundles.ContainsKey(dep)) { yield return LoadSingleBundleAsync(dep); } else { m_LoadedBundles[dep].RefCount++; // 참조 증가 } } // 메인 번들 로드 yield return LoadSingleBundleAsync(bundleName); // 의존성 기록 m_LoadedBundles[bundleName].Dependencies = new HashSet<string>(dependencies); onComplete?.Invoke(m_LoadedBundles[bundleName].Bundle); } // 번들 언로드 (의존성 자동 처리) public void UnloadBundle(string bundleName, bool unloadAllLoadedObjects = true) { if (!m_LoadedBundles.TryGetValue(bundleName, out var loaded)) return; loaded.RefCount--; if (loaded.RefCount > 0) return; // 아직 다른 곳에서 사용 중 // 의존성의 참조 카운트도 감소 if (loaded.Dependencies != null) { foreach (var dep in loaded.Dependencies) { UnloadBundle(dep, unloadAllLoadedObjects); // 재귀 } } // 번들 실제 언로드 loaded.Bundle.Unload(unloadAllLoadedObjects); m_LoadedBundles.Remove(bundleName); } private IEnumerator LoadSingleBundleAsync(string bundleName) { string path = GetBundlePath(bundleName); var request = AssetBundle.LoadFromFileAsync(path); yield return request; m_LoadedBundles[bundleName] = new LoadedBundle { Bundle = request.assetBundle, RefCount = 1 }; } }

핵심 정리

  • 의존성이란? 번들 A의 에셋이 번들 B의 에셋을 참조할 때 발생하는 관계
  • 직접 vs 간접: GetDirectDependencies(1단계), GetAllDependencies(재귀)
  • 중복 문제: 공유 에셋이 번들에 미할당되면 중복 복사됨 → Shared 번들 필수
  • 로딩 순서: 의존 번들을 먼저 로드, 병렬화 시에도 순서 유지
  • 참조 카운팅: 언로드 시 다른 번들의 참조 확인 필수
  • 순환 의존성: 인터페이스 분리, 중간 번들 도입, 런타임 연결로 해결
  • 계층 아키텍처: Core → Shared → Feature → Content 순서로 계층화
