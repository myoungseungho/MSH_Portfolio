ORM이 뭐야? SQL 안 쓰고 DB 쓸 수 있다고?

분산 환경 ORM 개발 - 게임 서버에서 SQL 없이 데이터 처리하기

Part 1. ORM이 뭐야?

SQL 쿼리 쓰기 귀찮은데... 다른 방법 없어?

ORM이라는 게 있어!

Object-Relational Mapping의 약자야. DB 데이터를 프로그래밍 언어의 객체로 다루게 해줘.

통역사 비유

한국어(객체) ↔ 영어(SQL) 사이에 통역사(ORM)가 있다고 생각해.
너는 한국어만 하면 돼. 통역사가 영어로 바꿔서 DB한테 전달해줌!
그럼 코드가 어떻게 달라져?

비교해볼게.

// SQL 방식: 쿼리 쓰고, 실행하고, 결과에서 꺼내오고... string query = "SELECT name, level FROM Character WHERE id = @id"; ExecuteQuery(query); var name = result["name"]; var level = result["level"]; // ORM 방식: 객체로 바로 접근! var character = Character.Fetch("대부대이"); var name = character.Name; var level = character.Level;
ORM의 핵심

SQL 쿼리 작성 = 0
객체 조작만으로 DB CRUD 가능!

Part 2. 왜 직접 ORM을 만들어?

ORM 라이브러리 많잖아. 왜 직접 만들어?

게임 서버는 좀 특별해. 목표가 3가지 있었거든.

목표 왜 필요해?
SQL 작업 완전 제거 게임 개발자가 쿼리에 시간 낭비 안 하도록
분산 환경 동일 작동 서버 1대 → 2대 늘려도 코드 그대로
상용 서비스 성능 실제 라이브 서비스에서도 버틸 수 있어야
분산 환경에서 동일하게 작동한다는 게 무슨 말이야?

서버가 여러 대 있어도 코드는 똑같이 쓰면 된다는 거야.

ORM이 알아서 "이 데이터 어디 있지?" 찾아서 처리해줌!

Part 3. 시스템 구조는 어떻게 생겼어?

이 ORM 내부 구조는 어떻게 돼?

4개 계층으로 나눠져 있어.

[Object Interface] - 자동 생성되는 코드, 개발자가 사용 ↓ [Object System] - 캐시, 잠금, RPC 관리 ↓ [캐시] [잠금] [RPC] - 핵심 서비스들 ↓ [Event System] - 트랜잭션, 비동기의 기반
각 계층이 뭐 하는 거야?

Object Interface: 모델 정의하면 자동 생성되는 코드. 너가 쓰는 부분!

Object System: 캐시, 잠금, 다른 서버와 통신(RPC) 처리

Event System: 비동기 처리랑 트랜잭션의 심장

Part 4. 코드 자동 생성이 뭐야?

모델 정의하면 코드가 자동으로 나온다고?

응! 흐름이 이래.

[모델 정의] → [빌드] → [인터페이스 코드 생성] → [컨텐츠 구현]
실제로 어떻게 생겼어?

먼저 모델을 정의하면...

// 1. 모델 정의 (네가 작성) class Character { string Name; int Level; int HP; } // 2. 자동 생성되는 인터페이스 (ORM이 만들어줌) static Character Create(string name); // 생성 static Character Fetch(string name); // DB에서 불러오기 int GetLevel(); // 값 읽기 void SetLevel(int value); // 값 쓰기
왜 내부는 "일반화된 오브젝트"로 구현했대?

캐시나 잠금 시스템은 "어떤 타입인지" 몰라도 동작해야 해.

그래서 공통 처리가 가능한 일반화된 오브젝트로 내부 구현!

택배 박스 비유

택배 기사는 박스 안에 뭐가 들었는지 몰라도 배달할 수 있잖아?
ORM 내부도 마찬가지야. 일반화된 박스(오브젝트)로 다루면 뭐든 처리 가능!

Part 5. 이벤트 시스템이 왜 필요해?

이벤트 시스템이 ORM이랑 무슨 상관이야?

비동기 I/O랑 트랜잭션 처리 때문에 필요해!

쉽게 말하면: 함수를 실행하는 스레드 풀이야.

이벤트 함수 상태가 3개 있다던데?

응, 이렇게 나눠져.

상태 설명
실행 준비 이벤트 큐에서 대기 중
실행 스레드가 지금 실행하는 중
중단/롤백 DB 로드 대기, 다른 이벤트가 잠금 보유 등
"중단"을 어떻게 구현해?

Exception을 throw!

// 이벤트 루프 while (true) { var event = queue.Dequeue(); try { event.Execute(); } catch (ObjectNotReadyException ex) { // 오브젝트가 캐시에 없으면 예외 발생! // DB에서 로드 후 이벤트 재실행 LoadFromDB(ex.ObjectId); queue.Enqueue(event); // 다시 큐에 넣기 } }
중단되기 전에 뭔가 수정했으면 어떡해?

수정은 임시 저장소에 먼저 저장돼!

임시 저장소 규칙

중단 시: 임시 저장 내용 삭제 (롤백)
완료 시: 원본 캐시와 DB에 반영 (커밋)

Part 6. 비동기 I/O는 어떻게 해?

DB 읽기 기다리면 다른 일 못 하잖아. 어떻게 해결해?

이벤트 시스템 덕분에 가능해!

I/O 필요 → Exception에 I/O 정보 담아서 throw ↓ 이벤트 스레드: "아 I/O 기다려야 하네, 다른 거 할게!" ↓ I/O 완료 → 해당 이벤트 재실행
중단될 때마다 Exception 던지면 느리지 않아?

맞아, 오버헤드가 있어. 그래서 캐시로 중단 발생을 최대한 줄여!

캐시 히트하면 중단 없이 바로 진행하니까.

Part 7. 캐시는 어떻게 구현해?

캐시가 왜 필요해?

2가지 이유야.

이유 효과
DB I/O 감소 성능 향상의 기본!
이벤트 중단 오버헤드 감소 캐시 히트 시 중단 없이 진행
캐시 구조는 어떻게 생겼어?

간단한 맵이야.

// 오브젝트 타입 + ID = 키, 오브젝트 = 값 Map cache; // 예: "Character:123" → Character 오브젝트
중요 규칙!

서버가 여러 개일 때, 하나의 오브젝트는 단 하나의 서버 캐시에만 존재할 수 있어!
안 그러면 동기화 지옥...

Part 8. 잠금(Lock)은 왜 필요해?

DB Lock 쓰면 되지 않아?

캐시에 로드된 오브젝트는 SQL 바깥에 있어!

DB Lock을 쓸 수가 없어. 그래서 애플리케이션 수준 잠금이 필요해.

잠금 종류가 여러 개야?

3가지 있어.

유형 설명 예시
복사본 읽기 잠금 없이 사본만 반환 친구 목록 조회
읽기 잠금 여러 이벤트 동시 읽기 가능 프로필 조회
쓰기 잠금 단독 점유, 수정 가능 레벨업 처리
데드락은 어떻게 생겨?

서로 상대방 잠금을 기다리면 발생해.

// 이벤트 1 var a = Fetch("대부대이"); // a 잠금 획득 var b = Fetch("부자이"); // b 잠금 대기... (이벤트2가 가지고 있음) // 이벤트 2 (동시에 실행 중) var b = Fetch("부자이"); // b 잠금 획득 var a = Fetch("대부대이"); // a 잠금 대기... (이벤트1이 가지고 있음) // → 둘 다 상대방 기다리며 영원히 멈춤 = 데드락!
데드락 어떻게 해결해?

2가지 방법을 시도했어.

방법 1: 타이머 기반
  • 잠금 못 얻으면 → 가진 거 다 풀고 → 잠시 후 재시도
  • 장점: 구현 간단
  • 단점: 3개 이상 경합하면 데드락 미해결
방법 2: 선점형 잠금 (최종 채택!)

모든 이벤트에 실행 시간 순서 기반 우선순위 부여
먼저 발생한 이벤트가 나중 이벤트의 잠금을 강제로 뺏을 수 있음

장점: 경합 정도와 무관하게 균등한 성능
단점: 구현이 복잡함

Part 9. 분산 환경에서는 어떻게 해?

서버가 여러 대면 오브젝트가 어디 있는지 어떻게 알아?

ZooKeeper를 써!

오픈소스 분산 코디네이션 서비스야.

// 오브젝트 소유권 = 어느 서버가 캐싱했는가 /objects/1234 → "ServerA" // 오브젝트 1234는 ServerA가 소유 // 캐시에 넣기 전에 ZooKeeper에 등록 CreateFile("/objects/{objectId}", "내 서버 ID");
다른 서버에 있는 오브젝트 쓰고 싶으면?

RPC로 빌려와!

[서버 B가 서버 A의 오브젝트에 접근하는 흐름] 1. 서버 B: ZooKeeper에서 /objects/1234 조회 2. 결과: "ServerA" → 서버 A가 소유 중 3. 서버 B → 서버 A: "잠깐 빌려줘" (Lease RPC) 4. 서버 A: 오브젝트 잠금 + 타임아웃 설정 5. 서버 A → 서버 B: 오브젝트 데이터 전송 6. 서버 B: 이벤트 처리 완료 7. 서버 B → 서버 A: "다 썼어" (Return RPC + 수정 내용) 8. 서버 A: 잠금 해제, 캐시/DB 업데이트
타임아웃이 필요한 이유

버그나 네트워크 장애로 반납 안 되면?
데드락이 전체 서버군으로 확산될 수 있어!
타임아웃으로 강제 해제해서 방지.
캐시 적중률이 낮으면 RPC 너무 많이 안 나가?

좋은 지적이야. 해결책이 있어.

도서관 비유

A 도서관에 있는 책을 B 도서관 사람들이 계속 빌려간다면?
차라리 그 책을 B 도서관으로 이전하는 게 효율적이지!
접근 빈도 기반 캐시 이전

1. 캐시에 오브젝트별 접근 빈도 계산 추가
2. 자신보다 높은 빈도로 접근하는 서버 발견
3. 캐시에서 강제로 내림
4. 더 자주 접근하는 서버가 캐시에 올림!

Part 10. 결과는?

이 ORM 개발해서 뭐가 좋아졌어?

목표 3개 다 달성!

성과 효과
게임 서버 개발 기간 단축 SQL 고민 시간 제거
SQL 작업 완전 제거 객체만 다루면 됨
분산 환경 투명 지원 서버 늘려도 코드 동일
상용 서비스 성능 달성 라이브에서도 문제 없음

핵심 정리: 분산 환경 ORM

  • ORM - SQL 대신 객체로 DB 다루기, "통역사" 역할
  • 코드 자동 생성 - 모델 정의하면 인터페이스 자동 생성
  • 이벤트 시스템 - 비동기 I/O와 트랜잭션의 기반
  • 캐시 - DB I/O 감소 + 중단 오버헤드 감소
  • 선점형 잠금 - 우선순위 기반으로 데드락 해결
  • ZooKeeper - 분산 환경에서 오브젝트 소유권 관리
  • 접근 빈도 기반 캐시 이전 - 분산 캐시 효율화
