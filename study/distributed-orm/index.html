ORM이란 무엇인가?

ORM의 정의와 기본 개념은?
ORM(Object-Relational Mapping)은 데이터베이스를 SQL이 아닌 프로그래밍 언어의 객체로 다룰 수 있게 해주는 기술이다.
게임 서버 개발 관점에서 ORM = SQL 작성 없이 객체 조작만으로 DB 데이터 처리
SQL 방식 vs ORM 방식 코드 비교?
// SQL 방식: 쿼리 작성 → 실행 → 결과에서 컬럼 읽기 string query = "SELECT name, level FROM Character WHERE id = @id"; ExecuteQuery(query); var name = result["name"]; var level = result["level"]; // ORM 방식: 객체로 직접 접근 var character = Character.Fetch("대부대이"); var name = character.Name; var level = character.Level;
ORM을 사용하면 훨씬 짧고 직관적인 코드로 동일한 기능 처리 가능

ORM 개발 목표

이 ORM을 개발하면서 세운 핵심 목표 3가지는?
1
SQL 작업 완전 제거
2
분산 환경 동일 작동
3
상용 서비스 성능
  • 서버가 1대에서 2대로 늘어나도 코드 변경 없이 동일하게 작동
  • 라이브 서비스에서 충분한 성능을 낼 수 있어야 함

구현 1: 코드 자동 생성

모델 정의부터 코드 생성까지의 흐름은?
모델 정의
→
빌드
→
인터페이스 코드 생성
→
컨텐츠 구현
// 1. 모델 정의 class Character { string Name; int Level; int HP; } // 2. 자동 생성되는 인터페이스 static Character Create(string name); // 오브젝트 생성 static Character Fetch(string name); // DB에서 불러오기 int GetLevel(); // 값 읽기 void SetLevel(int value); // 값 설정
왜 일반화된 오브젝트로 내부 구현을 했나?
생성된 클래스는 단순한 래퍼 클래스이고, 실제 구현은 일반화된 오브젝트를 참조한다.
이유: 캐시, 잠금 등의 시스템은 구체적인 타입을 알 수 없기 때문에 일반화된 오브젝트로 공통 처리
구현에는 템플릿 엔진(Jinja 등)을 사용

구현 2: 이벤트 시스템

이벤트 시스템이 ORM에 왜 필요한가?
비동기 I/O와 트랜잭션 처리를 위해 필요하다.
  • 간단히 말하면: 함수를 실행하는 스레드 풀
  • 함수를 이벤트 큐에 던지면 이벤트 스레드에서 실행됨
이벤트 함수의 3가지 상태는?
  • 실행 준비: 이벤트 큐 중간에 위치, 실행 대기 중
  • 실행: 큐 맨 앞에서 스레드가 실행 중
  • 중단/롤백: 더 이상 진행 불가 상태 (DB에서 오브젝트 로드 대기, 다른 이벤트가 잠금 보유 등)
중단(Suspend) 구현은 어떻게 했나?
// 이벤트 루프 while (true) { var event = queue.Dequeue(); try { event.Execute(); } catch (ObjectNotReadyException ex) { // 오브젝트가 캐시에 없으면 예외 발생 // DB에서 로드 후 이벤트 재실행 LoadFromDB(ex.ObjectId); queue.Enqueue(event); } }
  • 중단은 Exception을 throw하는 방식으로 구현
  • TLS(Thread Local Storage)를 활용해 간단히 구현
중단 전 오브젝트 수정은 어떻게 처리하나?
오브젝트 수정은 원본에 바로 저장되지 않고 임시 저장소에 저장된다.
  • 중단 시: 임시 저장 내용 삭제 (롤백)
  • 완료 시: 원본 캐시와 DB에 반영 (커밋)

구현 3: 비동기 I/O

비동기 I/O는 어떻게 구현했나?
이벤트 시스템을 기반으로 구현:
  • I/O 필요 시 Exception에 I/O 정보를 담아 throw
  • I/O 진행 중 이벤트 스레드는 블로킹되지 않고 다른 이벤트 처리
  • I/O 완료 후 해당 이벤트 재실행
중단 오버헤드를 어떻게 최소화했나?
중단에는 오버헤드가 있기 때문에, 캐시를 이용해 중단 발생을 최대한 줄이는 구현을 추가했다.

구현 4: 캐시

캐시가 필요한 이유 2가지는?
  1. DB I/O 감소: 성능 향상의 기본
  2. 이벤트 중단 오버헤드 감소: 캐시 히트 시 중단 없이 진행
캐시 구현 방식은?
// 오브젝트 타입 + ID를 키로, 오브젝트 값을 밸류로 하는 맵 Map<string, Object> cache; // 키: "Character:123", 밸류: Character 오브젝트
중요 규칙: 서버가 여러 개일 때, 하나의 오브젝트는 단 하나의 서버 캐시에만 존재할 수 있다.

구현 5: 잠금(Lock)

애플리케이션 수준 잠금이 필요한 이유는?
  • 하나의 오브젝트를 여러 곳에서 동시 수정하면 문제 발생
  • 캐시에 로드된 오브젝트는 SQL 외부에 있어서 DB 잠금 사용 불가
  • SQL 잠금 사용 시 로직이 DB에 쏠리는 문제
  • DB 샤딩 시 일반적인 잠금 사용 어려움
잠금의 3가지 유형은?
  • 복사본 읽기: 잠금 없이 사본만 반환 (친구 목록 조회 등)
  • 읽기 잠금: 여러 이벤트가 동시 읽기 가능
  • 쓰기 잠금: 단독 점유, 수정 가능
데드락 문제는 어떻게 발생하나?
// 이벤트 1 var a = Fetch("대부대이"); // a 잠금 var b = Fetch("부자이"); // b 잠금 대기 (이벤트2가 보유) // 이벤트 2 (동시 실행) var b = Fetch("부자이"); // b 잠금 var a = Fetch("대부대이"); // a 잠금 대기 (이벤트1이 보유) // → 서로 상대방의 잠금을 기다리며 영원히 대기: 데드락!
데드락 해결을 위해 시도한 방법 2가지는?
방법 1: 타이머 기반 (점유 대기 방지)
  • 잠금 획득 불가 시 보유한 모든 잠금 해제 후 일정 시간 뒤 재시도
  • 장점: 구현 간단
  • 단점: 3개 이상 오브젝트 경합 시 데드락 미해결
방법 2: 선점형 잠금 (비선점 방지) - 최종 채택
  • 모든 이벤트에 실행 시간 순서 기반 우선순위 부여
  • 먼저 발생한 이벤트가 나중 이벤트의 잠금을 강제로 뺏을 수 있음
  • 뺏기는 쪽은 중단 상태에서만 뺏김 (실행 중엔 곧 끝나므로 안전)
선점형 잠금 장점: 큐 기반이라 경합 정도와 무관하게 균등한 성능
단점: 경합 없을 때 타이머 방식보다 느림, 구현 복잡

구현 6: 분산 환경에서의 캐시와 잠금

분산 환경에서 ORM이 작동하려면?
Fetch 함수로 오브젝트를 불러올 때:
  • 불러오려는 오브젝트가 다른 서버에 캐시되어 있으면
  • 해당 서버로 RPC를 보내 잠금 획득
  • 해당 서버 캐시에서 오브젝트를 가져옴
오브젝트 소유권 관리에 ZooKeeper를 어떻게 사용했나?
ZooKeeper: 오픈소스 분산 코디네이션 서비스
  • 클러스터 구성 가능 (단일 장애점 없음)
  • 파일 시스템처럼 사용 (경로에 파일 생성, 내용 저장/읽기)
// 오브젝트 소유권 = 어느 서버가 캐싱했는가 /objects/1234 → "ServerA" // 오브젝트 1234는 ServerA가 소유 // 캐시에 넣기 전 ZooKeeper에 등록 CreateFile("/objects/{objectId}", "내 서버 ID");
분산 환경에서 오브젝트 접근 흐름은?
서버 B가 서버 A의 오브젝트에 접근하는 흐름
  1. 서버 B: ZooKeeper에서 /objects/1234 조회
  2. 결과: "ServerA" → 서버 A가 소유 중
  3. 서버 B → 서버 A: Lease RPC 전송
  4. 서버 A: 오브젝트 잠금 + 타임아웃 설정
  5. 서버 A → 서버 B: 오브젝트 데이터 응답
  6. 서버 B: 이벤트 처리 완료
  7. 서버 B → 서버 A: Return RPC (수정 내용 포함)
  8. 서버 A: 잠금 해제, 캐시/DB 업데이트
타임아웃이 필요한 이유: 예기치 못한 버그나 네트워크 장애로 반납이 안 되면 데드락이 전체 서버군으로 확산되는 것을 방지
캐시 적중률 문제는 어떻게 해결했나?
문제 상황:
  • 로그인 서버가 계정 데이터 캐시
  • 게임 서버는 해당 데이터에 더 자주 접근
  • 매번 RPC가 과도하게 발생
해결책: 접근 빈도 기반 캐시 이전
  • 캐시에 오브젝트별 접근 빈도 계산 코드 추가
  • 자신보다 높은 빈도로 접근하는 서버가 있으면 캐시에서 강제로 내림
  • 더 자주 접근하는 서버가 캐시에 올릴 수 있는 환경 조성
