DB를 되돌려야 하는데, 정상 유저 데이터는?

DB 롤백 전략 - 시간을 되돌리면 무고한 유저의 시간도 되돌려진다

왜 이 문제가 어려운가

버그 때문에 DB를 어제로 되돌려야 해. 근데 어제부터 지금까지 정상적으로 플레이한 유저들은?

바로 그게 문제야.

시간을 되돌리면 버그 피해자는 복구되지만, 정상 유저의 진행도가 통째로 날아감.

비유: 교실 시험

시험지에 오류가 있어서 전체 시험을 무효로 했어. 근데 오류 문제는 3번 하나뿐이고, 나머지 49문제는 멀쩡했어.
정상적으로 49문제 다 푼 학생들 입장에서는? "왜 내 답안지까지 버려?"

DB 롤백이 정확히 이 상황이야.
그러면 어떻게 해야 해?

선택지가 크게 3가지 있어. 각각 장단점이 완전히 달라.

복구하려다 더 큰 피해를 만들 수 있다. 그래서 신중하게 골라야 해.

선택지 A - 전체 롤백 + 보상 (가장 단순하지만 가장 무식)

제일 간단한 방법은 뭐야?

전체 DB를 사고 이전 시점으로 복원하는 거야.

모든 데이터를 "어제 오후 3시" 상태로 되돌리는 거지.

PITR이 뭐야?

정의: PITR (Point-in-Time Recovery) = 특정 시점 복구. DB를 원하는 과거 시점으로 되돌리는 기능.

왜 필요: "어제 오후 3시 상태로 돌려줘"처럼 정확한 시점을 지정해서 복원할 수 있어. 백업 파일 + 트랜잭션 로그를 조합해서 원하는 시점을 재현하는 원리야.

안 쓰면: 마지막 전체 백업 시점으로만 돌아갈 수 있음. 백업이 새벽 3시에 찍혔다면? 오후 3시에 사고 났어도 새벽 3시로 돌아가야 해. 12시간치 데이터가 추가로 날아감.

전체 롤백의 장점과 단점은?

강점: 확실하게 문제 해결. 구현이 단순. PITR로 시점 지정하고 복원하면 끝이야.

약점: 정상 유저 전원이 피해를 봄.

"2시간 열심히 플레이했는데 보상이 포션 10개?" 이런 불만이 폭발해. 유저 신뢰가 무너지는 거야.

-- 전체 롤백 흐름 (MSSQL 기준) 1. 서비스 긴급 점검 진입 2. PITR로 사고 직전 시점 복원 RESTORE DATABASE GameDB FROM DISK = 'D:\Backup\GameDB_Full.bak' WITH NORECOVERY; RESTORE LOG GameDB FROM DISK = 'D:\Backup\GameDB_Log.trn' WITH STOPAT = '2026-02-17 15:00:00', RECOVERY; 3. 전체 유저에게 보상 지급 4. 서비스 재개

적합한 상황: 경제 붕괴급 버그에서만. 예를 들어 복제 버그로 골드가 무한 생성됐다면, 부분 복구로는 해결이 안 돼. 최후의 수단.

선택지 B - 선택적 롤백 (Selective/Surgical Rollback)

전체를 되돌리지 않고, 영향받은 유저만 골라서 되돌릴 수는 없어?

있어. 그게 선택적 롤백이야.

Selective Rollback (선택적 롤백) = 영향받은 유저의 데이터만 과거 시점으로 교체하고, 나머지는 그대로 두는 방법.

구체적으로 어떻게 해?

순서가 있어:

1단계: PITR로 사고 직전 시점의 복원본을 별도 서버에 올려. 운영 DB를 건드리는 게 아니야.

2단계: 복원본 DB와 운영 DB를 비교해서, 영향받은 유저를 추출해.

3단계: 해당 유저의 데이터만 복원본에서 가져와서 운영 DB에 덮어씀.

-- 1단계: 복원본 DB에서 영향받은 유저 추출 SELECT user_id, item_data, gold FROM backup_db.dbo.UserInventory WHERE user_id IN (SELECT user_id FROM AffectedUsers) -- 2단계: 운영 DB에 선택적 적용 UPDATE live_db.dbo.UserInventory SET item_data = backup.item_data, gold = backup.gold FROM backup_db.dbo.UserInventory backup WHERE live_db.user_id = backup.user_id AND live_db.user_id IN (SELECT user_id FROM AffectedUsers)
장점과 단점은?

강점: 정상 유저에게 피해가 없음. 버그에 영향받은 유저만 정밀하게 복구할 수 있어.

약점: "영향받은 유저" 목록을 정확히 추출해야 해.

이 목록이 틀리면? 멀쩡한 유저 데이터를 과거로 되돌려버리는 2차 사고가 발생해. 추출 + 검증에 시간도 걸려.

필요 조건: 상세한 로그 + 백업 체계가 갖춰져 있어야 해.

로그가 부실하면 "누가 영향받았는지" 자체를 알 수 없어. 그러면 이 방법을 쓸 수가 없어.

선택지 C - 보상 트랜잭션 (Compensating Transaction)

DB 자체를 과거로 안 돌리고 해결할 수는 없어?

있어. 롤백 대신 "역연산"을 적용하는 거야.

Compensating Transaction이 뭐야?

정의: Compensating Transaction (보상 트랜잭션) = 잘못된 작업의 효과를 상쇄하는 "반대 작업"을 실행하는 것. DB를 과거로 되돌리지 않고, 현재 상태에서 수정 패치를 적용하는 방식.

왜 필요: DB 전체를 건드리지 않으니 서비스를 중단할 필요가 없어. 정상 유저 데이터는 아예 손대지 않아.

안 쓰면: 아무리 작은 버그라도 매번 DB 복원 + 서비스 점검이 필요해짐. 유저 이탈과 매출 손실이 커져.

비유: 은행 송금 실수

A에게 100만원을 잘못 보냈어. 은행이 어떻게 해?
"시간을 되돌려서 송금을 취소"하는 게 아니야. A한테서 100만원을 다시 빼서 돌려주는 거야.

DB도 마찬가지. 되돌리는 게 아니라, 반대 작업을 실행해.
예를 들면?

버그로 아이템 2개가 추가 지급됐다면:

-- 버그로 인한 잘못된 지급 내역 확인 SELECT user_id, item_id, quantity FROM BugAffectedLog WHERE bug_id = 'BUG-2026-0217' -- 역연산: 잘못 지급된 아이템 삭제 DELETE FROM UserInventory WHERE (user_id, item_id) IN ( SELECT user_id, item_id FROM BugAffectedLog WHERE bug_id = 'BUG-2026-0217' ) -- 잘못 추가된 골드 차감 UPDATE UserAccount SET gold = gold - ( SELECT wrongly_added_gold FROM BugAffectedLog WHERE BugAffectedLog.user_id = UserAccount.user_id AND bug_id = 'BUG-2026-0217' ) WHERE user_id IN ( SELECT user_id FROM BugAffectedLog WHERE bug_id = 'BUG-2026-0217' )
이거 제일 좋아 보이는데, 단점은 없어?

강점: 서비스 중단 없음. 정상 유저 영향 없음. 가장 정밀한 방법.

약점: 영향 체인이 길면 극도로 복잡해짐.

예를 들어 이런 상황을 생각해봐:

버그로 아이템 복제 → 그 아이템을 거래소에 판매 → 골드 획득 → 골드로 강화 → 강화한 장비를 다른 유저에게 거래

이 체인을 전부 역추적해서 하나하나 되돌려야 해. 체인이 5단계만 넘어도 현실적으로 불가능에 가까워.

적합한 상황: 영향 범위가 명확하고, 체인이 짧을 때. "아이템 N개가 잘못 지급됐고, 아직 거래 안 됐음" 같은 경우가 딱이야.

정상 유저 피해 전원 피해 피해 없음 피해 없음

적합 상황 경제 붕괴급 대형 사고 영향 유저 특정 가능할 때 영향 범위 명확 + 체인 짧을 때
정밀도 낮음 (전부 되돌림) 중간 (유저 단위) 높음 (작업 단위)

실무 판단 기준 - 뭘 써야 하나

사고가 터졌어. 뭘 써야 할지 어떻게 판단해?

핵심 질문은 딱 하나야:

"로그로 영향 범위를 특정할 수 있느냐?"

판단 플로우: 1. 로그로 영향받은 유저/데이터를 특정할 수 있는가? │ ├── YES: 영향 체인이 짧은가? (거래/강화 등 2차 파급 없음) │ │ │ ├── YES --> 보상 트랜잭션 (가장 정밀, 서비스 유지) │ │ │ └── NO --> 선택적 롤백 (유저 단위로 복원) │ └── NO: 영향 범위를 알 수 없다 │ └── 전체 롤백 (최후의 수단)

특정 가능 + 체인 짧음 → 보상 트랜잭션. 서비스 중단 없이 정밀 복구.

특정 가능 + 체인 길음 → 선택적 롤백. 해당 유저 데이터를 통째로 과거 시점으로 교체.

특정 불가능 → 전체 롤백. 최후의 수단. 보상 정책 필수.

바로 실행하면 되는 거야?

절대 안 돼. 어떤 방법이든 스테이징 환경에서 먼저 검증해야 해.

운영 DB에 직접 복구 스크립트를 돌렸다가, 스크립트 자체에 버그가 있으면?

"복구 스크립트가 더 큰 문제를 일으킨 사례"는 업계에서 생각보다 많아. 복구한다고 급하게 돌린 쿼리가 WHERE 조건 빠져서 전체 유저 데이터를 밀어버린 실제 사례도 있어.

복구 실행 전 체크리스트: 1. 스테이징 환경에 운영 DB 사본을 올린다 2. 복구 스크립트를 스테이징에서 먼저 실행한다 3. 결과를 검증한다 (영향받은 유저 수, 변경된 행 수 등) 4. 검증 통과 후에만 운영 DB에 적용한다 5. 적용 후에도 모니터링 (예상치 못한 사이드이펙트 감지)

MSSQL 실무 팁

MSSQL 환경에서 실제로 어떻게 써?

가장 실용적인 패턴을 알려줄게.

핵심은 "비교용 복원본"을 만드는 거야.

1단계: PITR로 사고 1분 전 시점의 복원본을 별도 서버에 올리기

-- 별도 서버(또는 별도 이름)로 사고 1분 전 시점 복원 RESTORE DATABASE GameDB_Snapshot FROM DISK = 'D:\Backup\GameDB_Full.bak' WITH NORECOVERY, MOVE 'GameDB_Data' TO 'D:\Restore\GameDB_Snapshot.mdf', MOVE 'GameDB_Log' TO 'D:\Restore\GameDB_Snapshot.ldf'; RESTORE LOG GameDB_Snapshot FROM DISK = 'D:\Backup\GameDB_Log.trn' WITH STOPAT = '2026-02-17 14:59:00', RECOVERY;

2단계: diff 쿼리로 영향 범위 파악

-- 운영 DB vs 복원본 비교: 골드 차이가 비정상인 유저 추출 SELECT live.user_id, live.gold AS current_gold, snap.gold AS before_gold, live.gold - snap.gold AS diff FROM GameDB.dbo.UserAccount live JOIN GameDB_Snapshot.dbo.UserAccount snap ON live.user_id = snap.user_id WHERE ABS(live.gold - snap.gold) > 1000000 -- 비정상 차이 기준 ORDER BY diff DESC

"비교용 복원본"이 있으면 판단이 훨씬 빨라짐.

사고가 터지면 일단 복원본부터 올려놓고, 운영 DB와 비교하면서 영향 범위를 파악해. 이게 선택적 롤백이든 보상 트랜잭션이든 모든 전략의 출발점이야.

복원본 없이 감으로 "이 유저가 영향받았을 거야"라고 판단하면? 높은 확률로 2차 사고가 난다.

핵심 정리: DB 롤백 전략

  • 전체 롤백 - 최후의 수단. 확실하지만 정상 유저 전원이 피해를 봄
  • 선택적 롤백 - 영향받은 유저만 복원. 정밀하지만 로그 품질에 의존
  • 보상 트랜잭션 - 역연산 적용. 가장 정밀하고 서비스 중단 없음. 체인 짧을 때 적합
  • 판단 기준 - "로그로 영향 범위를 특정할 수 있는가?"가 핵심
  • 복구 전 검증 - 어떤 전략이든 스테이징 환경에서 먼저 테스트 필수
