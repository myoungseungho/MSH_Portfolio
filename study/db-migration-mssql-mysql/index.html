리니지2 게임 DB를 MSSQL에서 MySQL로 전환

엔씨소프트 리니지2팀 김인정 - NDC 발표
DB Migration MSSQL MySQL 자동화

리니지2는 어떤 규모의 게임인가?

  • 2017년 10월 기준 14주년을 맞은 장수 MMORPG
  • 라이브와 클래식 두 가지 버전으로 서비스
  • 7개국 이상에서 서비스 중
  • 3개월 주기로 콘텐츠 업데이트
  • 라이브와 클래식은 완전히 다른 버전 - DB 전환 작업을 각각 별도로 진행해야 함

왜 자동화가 필수였나?

핵심 제약 조건: 작업자 1명, 최대 2년간 두 DB(MSSQL + MySQL) 동시 지원 필요
  • 라이브 버전 전환만 6개월 예상 (1인 기준)
  • 게임 업데이트가 계속되므로 DB 전환 작업도 반복 필요
  • 해외 서비스는 퍼블리셔별 협의가 필요해 전환 시점이 각각 다름
  • 클래식 버전도 별도 작업 필요
  • 해외는 현지 맞춤 컨텐츠로 또 다른 전환 작업 발생
"개발자가 도망가면 안 돼요" - 2년간 1명에게 수동 작업을 전담시키면 비효율적이고, 개발자 이탈 위험

DB 스키마 규모와 마이그레이션 방법은?

리니지2 DB 규모:

  • 테이블 300여 개
  • 컬럼 2,100여 개
  • MSSQL의 거의 모든 데이터 타입 사용

사용 도구: MySQL Workbench의 Database Migration 기능

Workbench는 오픈소스이며 대부분 Python으로 작성되어 있어 Script Shell로 커스터마이징 가능

Workbench 변환 시 어떤 문제가 발생했나?

문제 유형 상세 내용
16진수 기본값 누락 컬럼 기본값이 0x0 같은 16진수면 변환 시 누락됨
BINARY 타입 기본값 변형 BINARY/VARBINARY 컬럼의 기본값 0이 문자열 '0'으로 변환됨
인코딩 강제 설정 UCS-KR 사용해도 Workbench가 무조건 UTF-8 MB4로 강제 변환
AUTO_INCREMENT 누락 MySQL에서 AUTO_INCREMENT는 PRIMARY KEY/UNIQUE 컬럼만 가능 - 해당 조건 미충족 시 속성 누락

해결: Workbench Script Shell로 Python 커스터마이징하여 모든 테이블 자동 변환

Stored Procedure 변환은 어떻게 했나?

SP 규모:

  • 약 3만 라인 코드
  • 다양한 트랜잭션, 인덱스, 게임 로직 포함
  • MSSQL 전용 내장 함수 사용

변환 도구 선정:

  • 오픈소스 도구, 상용 도구, 자체 제작 모두 검토
  • 최종 선택: Ispirer (상용 변환 툴)
Ispirer 선택 이유:
  • DB 마이그레이션 전문 회사
  • 트라이얼 버전 테스트 시 약 90% 변환 성공률
  • 지속적인 버전 업데이트
  • 본사 및 한국 총판(이지딥스)의 빠른 문의 대응

DB 테스트는 어떻게 자동화했나?

게임 QA만으로는 불충분한 이유:

  • SQL은 컴파일이 없어 신택스 에러 등 기본 검수 안 됨
  • QA 중 에러 발생 시 → 개발팀 수정 → QA 처음부터 재시작 (일정 불가능)
  • 게임 DB 내부 로직은 게임에서 드러나지 않는 영역 존재

해결: SP UnitTest 프로그램 자체 개발

  • 다양한 파라미터로 전체 SP 실행
  • 신택스 에러 및 로직 에러 상당수 검증 성공
  • 실제 게임 QA 시 중단 이슈 전혀 발생하지 않음
  • 게임 QA 불가 영역도 SP 실행으로 검증

데이터 마이그레이션은 어떻게 진행했나?

제약 조건:

  • 라이브 서비스 중 - 정기 점검 시간 내에 완료 필수
  • 초기 테스트: 데이터 이전 약 10시간, 검증 약 6시간 = 총 16시간
  • 점검 연장 불가 (유저 경험에 직접적 악영향)

사용 도구: Workbench의 Copy Table Data 기능

주의: Workbench 6.3.10 버전에 버그 존재 - 6.3.99 버전 업데이트 후 정상 작동

성능 최적화:

  • Thread 개수 지정: 각 스레드가 테이블 하나씩 담당 (코어 수만큼 할당)
  • Bulk Data Transfer: 한 번에 여러 row 복사

데이터 검증은 어떻게 했나?

Data Compare 툴 자체 개발:

  • 초기: Python으로 개발 → 6시간 이상 소요
  • 개선: C++로 재작성하여 성능 향상

실제 적용 전략:

정기점검 시간 내 검증까지는 무리 → 일주일 전 백업본으로 마이그레이션 테스트 + 데이터 검증 완료 후, 일주일 사이 발생한 문제는 운영적으로 대처

MSSQL과 MySQL의 가장 큰 차이점은?

핵심 차이: MSSQL은 "관대"하고, MySQL은 "정확"하다
항목 MSSQL MySQL
ODBC 에러 처리 연결 끊김 시 PrepareSQL, Execute 모두 "Connection Closed" 반환 PrepareSQL에서 에러 반환 후, Execute는 "Function Sequence Error" 반환 (원인 추적 어려움)
문자열 인코딩 캐릭터 인코딩 맞지 않아도 저장해줌 잘못된 인코딩은 절대 저장 안 함 (강제 옵션 켜도 '?'로 변환)
16진수 상수 컬럼 타입에 맞춰 0xFF → INTEGER 반환 리터럴 그대로 0xFF → STRING 반환

ODBC 멀티스레드 이슈는?

리니지2 서버는 C++ 애플리케이션으로 ODBC를 통해 DB 접근

  • ODBC 장점: DBMS 종류 상관없이 동일 인터페이스 (코드 변경 불필요)
  • ODBC 단점: 각 DBMS 개발사가 별도 구현 → 내부 동작이 다름
MySQL ODBC 주의: 기본 옵션 사용 시 멀티스레드 세이프하지 않음!

해결: NO_SSPS=1 (서버 사이드 프리페어 미사용) 옵션 설정 시 멀티스레드 세이프하게 동작

MySQL 성능 우려 사항은?

가장 걱정되는 부분은 성능:

SELECT ISNULL(column, default_value) ...
  • ISNULL 같은 기본적인 쿼리문이 MySQL에서 약 1,000배 느림
  • 발표 당시 "내년(다음 해) 정도 되면 더 많은 얘기를 할 수 있을 것"이라고 언급

최종 자동화 파이프라인은?

[개발자] MSSQL 테이블/SP 작업 ↓ [일일 빌드] MSSQL 버전 DB 생성 ↓ [내부 DB 툴] 개인 서버에 MSSQL 적용 ↓ [자동 변환 툴] MySQL 버전 자동 생성 ↓ [내부 DB 툴] MySQL 버전 적용

결과: 2년 넘게 MSSQL과 MySQL 두 버전을 자동 변환/테스트하며 성공적으로 유지

이 발표에서 배울 점은?

  1. 자동화 우선: 반복 작업은 사람이 아닌 도구가 해야 함
  2. 도구 검증: 자동 변환 결과를 무조건 믿지 말고 테스트 필수
  3. 테스트 자동화: SQL은 컴파일이 없으므로 별도 테스트 프로그램 필요
  4. 성능 최적화: 멀티스레드 + 벌크 처리로 마이그레이션 시간 단축
  5. DBMS 특성 이해: MSSQL의 "관대함" vs MySQL의 "정확함" 차이 인지
  6. 버전 확인: 최신 도구에도 버그 존재 가능 - 항상 의심
