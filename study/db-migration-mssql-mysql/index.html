14년 된 게임 DB를 갈아엎는다고? MSSQL에서 MySQL로

리니지2 DB 마이그레이션 - NDC 발표 정리 (엔씨소프트 김인정)

Part 1. 리니지2가 DB를 바꾼다고?

리니지2가 뭔데? 얼마나 큰 게임이야?

2017년 기준 14주년된 장수 MMORPG야.

7개국 이상에서 서비스 중이고, 라이브와 클래식 두 가지 버전이 있어.

3개월마다 콘텐츠 업데이트가 나오고, 라이브와 클래식은 완전히 다른 DB를 써.

근데 왜 잘 돌아가던 MSSQL을 MySQL로 바꿔?

여러 이유가 있겠지만, 핵심은 비용과 라이선스야.

MSSQL은 상용 라이선스 비용이 비싸고, MySQL은 오픈소스라 비용이 적어.

특히 해외 서비스할 때 DBMS 라이선스 문제가 복잡해지거든.

Part 2. 혼자서 어떻게 해?

DB 전환 작업은 팀 단위로 하는 거 아냐?

작업자 1명이야.

거기다 최대 2년간 MSSQL + MySQL 동시 지원해야 해.

제약 조건 정리

- 라이브 버전 전환만 6개월 예상 (1인 기준)
- 게임 업데이트가 계속 됨 = DB 전환 작업도 반복
- 해외는 퍼블리셔별 전환 시점이 다름
- 클래식 버전도 별도 작업 필요
그러면 2년간 수동으로 계속 작업해야 해?

"개발자가 도망가면 안 돼요"

발표자 본인 말이야. 2년간 1명에게 수동 작업 전담시키면:

1. 비효율적이고

2. 개발자 이탈 위험이 있어

빵집 비유

매일 빵 100개를 손으로 반죽해야 해. 2년 동안.
당연히 반죽기 사야지!

DB 전환도 마찬가지. 자동화 도구가 반죽기야.
결론: 자동화가 필수!

손으로 하면 2년 걸리는 일을 자동화로 해결해야 했어.

Part 3. 테이블 300개를 어떻게 변환해?

리니지2 DB 규모가 어느 정도야?

테이블 300여 개, 컬럼 2,100여 개.

MSSQL의 거의 모든 데이터 타입을 사용하고 있었어.

뭘로 변환했어?

MySQL Workbench의 Database Migration 기능을 썼어.

오픈소스고 대부분 Python으로 작성되어 있어서 커스터마이징이 가능했거든.

근데 자동 변환이 완벽하게 됐어?

당연히 문제가 있었지!

문제 유형 뭐가 잘못됐나
16진수 기본값 누락 0x0 같은 16진수 기본값이 변환 시 사라짐
BINARY 타입 변형 기본값 0이 문자열 '0'으로 변환
인코딩 강제 설정 EUC-KR 써도 무조건 UTF-8 MB4로 강제
AUTO_INCREMENT 누락 PK/UNIQUE 아닌 컬럼은 AUTO_INCREMENT 속성 사라짐
해결 방법

Workbench Script Shell로 Python 코드 커스터마이징해서
모든 테이블을 자동 변환하도록 수정했어.

Part 4. Stored Procedure 3만 라인을 어떻게?

테이블만 옮기면 되는 거 아냐?

아니, SP(Stored Procedure)도 있어.

약 3만 라인의 코드가 있었어.

트랜잭션, 인덱스, 게임 로직, MSSQL 전용 함수들...

-- MSSQL 전용 문법들 ISNULL(column, default) -- MySQL은 IFNULL GETDATE() -- MySQL은 NOW() @@IDENTITY -- MySQL은 LAST_INSERT_ID() RAISERROR -- MySQL은 SIGNAL SQLSTATE
이것도 Workbench로?

아니, SP 변환은 Ispirer라는 상용 도구를 썼어.

오픈소스 도구, 상용 도구, 직접 제작 다 검토한 결과야.

Ispirer를 선택한 이유
  • DB 마이그레이션 전문 회사
  • 트라이얼 테스트 결과 약 90% 변환 성공률
  • 지속적인 버전 업데이트
  • 빠른 문의 대응 (본사 + 한국 총판)
90%면 10%는 수동이잖아?

맞아. 하지만 3만 라인의 90%를 자동화하면

27,000라인은 자동, 3,000라인만 수동이야.

그 차이가 엄청나지.

Part 5. 변환한 건 어떻게 검증해?

QA팀이 게임 테스트하면 되는 거 아냐?

그것만으론 부족해!

게임 QA만으로 불충분한 이유

1. SQL은 컴파일이 없어서 문법 에러가 미리 안 잡혀
2. QA 중 에러 발생 -> 수정 -> QA 처음부터 = 일정 불가능
3. DB 내부 로직은 게임에서 안 보이는 부분이 있어
그러면 어떻게 했어?

SP UnitTest 프로그램을 직접 만들었어!

[SP UnitTest 동작 방식] 1. 모든 SP 목록 가져오기 2. 각 SP에 다양한 파라미터 조합으로 실행 3. 문법 에러, 런타임 에러 자동 검출 4. 결과 리포트 생성 -> 게임 QA 전에 대부분의 에러를 잡아냄!
결과

실제 게임 QA 시 중단 이슈 전혀 발생하지 않음!
게임 QA로 확인 불가능한 영역도 SP 실행으로 검증 성공.

Part 6. 데이터 옮기기 - 점검 시간 내에 가능해?

스키마랑 SP 옮기면 끝 아냐?

아니, 실제 데이터도 옮겨야지!

유저 정보, 아이템, 캐릭터, 퀘스트 진행 상황...

이게 라이브 서비스 중이라 문제야.

라이브 중이면 뭐가 문제야?

정기 점검 시간 내에 끝내야 해!

점검 연장하면 유저들이 난리 나거든.

초기 테스트 결과

데이터 이전: 약 10시간
데이터 검증: 약 6시간
총 16시간 - 정기 점검으로는 불가능!
어떻게 시간을 줄였어?

Thread + Bulk Transfer로 최적화했어.

[성능 최적화 방법] 1. Thread 개수 지정 -> 각 스레드가 테이블 하나씩 담당 -> CPU 코어 수만큼 병렬 처리 2. Bulk Data Transfer -> 한 번에 여러 row 복사 -> INSERT INTO ... VALUES (...), (...), (...)
주의: Workbench 버전 문제

Workbench 6.3.10 버전에 버그가 있었어.
6.3.99로 업데이트 후 정상 동작!

최신 도구도 항상 의심하고 테스트해야 해.

Part 7. 데이터가 제대로 옮겨졌는지 어떻게 알아?

옮긴 데이터가 맞는지 확인은?

Data Compare 툴을 직접 개발했어.

MSSQL 데이터 vs MySQL 데이터를 비교하는 거야.

[Data Compare 개발 과정] 초기: Python으로 개발 -> 6시간 이상 소요 (느림!) 개선: C++로 재작성 -> 성능 대폭 향상!
근데 점검 시간 내에 검증까지 가능해?

솔직히 무리였어.

그래서 전략을 바꿨지.

실제 적용 전략
  • 일주일 전 백업본으로 마이그레이션 테스트
  • 데이터 검증까지 완료
  • 실제 점검일에는 이전만 수행
  • 일주일 사이 발생한 문제는 운영적으로 대처
이사 비유

이사 당일에 짐 싸고, 옮기고, 정리까지 다 하면 하루로 안 돼.
미리 짐 정리해두고, 당일엔 옮기기만 하면 빠르지!

Part 8. MSSQL이랑 MySQL이 그렇게 달라?

둘 다 SQL 쓰는 거 아냐?

표준 SQL은 비슷한데, 내부 동작이 완전 달라!

핵심 차이 한 줄 요약

MSSQL은 "관대"하고, MySQL은 "정확"하다
항목 MSSQL MySQL
ODBC 에러 연결 끊김 시 모두 "Connection Closed" "Function Sequence Error" (원인 추적 어려움)
문자열 인코딩 인코딩 안 맞아도 일단 저장 잘못된 인코딩은 절대 저장 안 함
16진수 상수 0xFF -> INTEGER 반환 0xFF -> STRING 반환
MySQL이 까다롭네?

까다로운 게 아니라 정확한 거야.

MSSQL이 "대충 해줄게"라면, MySQL은 "규칙대로 해"야.

사실 MySQL 방식이 더 안전한 측면도 있어.

Part 9. ODBC 함정 - 멀티스레드

리니지2 서버는 C++이라며? ODBC 쓰는 거야?

응, ODBC의 장점이 DBMS 상관없이 동일 인터페이스라서

코드 변경 없이 DB만 바꿀 수 있거든.

그러면 코드 안 바꿔도 되는 거 아냐?

함정이 있어!

ODBC 스펙은 같아도 각 DBMS 개발사가 별도 구현하거든.

내부 동작이 달라.

MySQL ODBC 치명적 이슈

기본 옵션 사용 시 멀티스레드 세이프하지 않음!

게임 서버는 당연히 멀티스레드인데...
기본 설정으로 쓰면 크래시 날 수 있어!
[해결 방법] 연결 문자열에 옵션 추가: NO_SSPS=1 -> 서버 사이드 프리페어를 사용하지 않음 -> 멀티스레드 세이프하게 동작

Part 11. 최종 자동화 파이프라인

결국 어떤 시스템을 만든 거야?

개발자가 MSSQL만 작업하면 MySQL 버전이 자동 생성되는 파이프라인이야.

[자동화 파이프라인] 1. [개발자] MSSQL 테이블/SP 작업 | v 2. [일일 빌드] MSSQL 버전 DB 생성 | v 3. [내부 DB 툴] 개인 서버에 MSSQL 적용 | v 4. [자동 변환 툴] MySQL 버전 자동 생성 | v 5. [내부 DB 툴] MySQL 버전 적용

Part 12. 이 발표에서 뭘 배워야 해?

핵심 교훈 6가지
  • 자동화 우선: 반복 작업은 사람이 아닌 도구가 해야 함
  • 도구 검증: 자동 변환 결과를 무조건 믿지 말고 테스트 필수
  • 테스트 자동화: SQL은 컴파일이 없으므로 별도 테스트 프로그램 필요
  • 성능 최적화: 멀티스레드 + 벌크 처리로 마이그레이션 시간 단축
  • DBMS 특성 이해: MSSQL "관대" vs MySQL "정확"
  • 버전 확인: 최신 도구에도 버그 있음 - 항상 의심

핵심 정리: DB 마이그레이션

  • 자동화 필수 - 1명이 2년간 두 DB 동시 지원해야 함
  • 스키마 변환 - Workbench + Python 커스터마이징
  • SP 변환 - Ispirer (90% 자동화)
  • 테스트 자동화 - SP UnitTest 직접 개발
  • 데이터 이전 - Thread + Bulk로 시간 단축
  • DBMS 차이 - MSSQL은 관대, MySQL은 정확
  • ODBC 주의 - MySQL은 NO_SSPS=1 필수
