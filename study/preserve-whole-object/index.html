Preserve Whole Object

객체 통째로 넘기기 - 의존성을 관리하라

Part 1. 객체 통째로 넘기기?

파라미터가 너무 많아.

객체에서 값 꺼내서 따로따로 넘기지 마.

Calculate(player.GetLevel(), player.GetStr()) 말고

그냥 Calculate(player)로.

왜 통째로 넘겨?

여러 이점이 있어:

객체 통째로 넘기기의 장점

1. 시그니처 안정 - Dex도 필요해지면? 함수 내부만 수정
2. 가독성 - 파라미터 6개 vs 1개
3. 타입 안전 - int, int, int 3개면 순서 헷갈려. Player 하나는 실수 없어
택배 보내기 비유

주소, 이름, 전화번호, 우편번호 따로따로 말하기 vs
"이 송장대로 보내주세요"라고 송장 한 장 주기

뭐가 실수 적고 효율적일까?

Part 2. 의존성 문제는?

불필요한 의존성 생기지 않아?

핵심 트레이드오프야:

트레이드오프 비교

객체 넘기면:
- 함수가 객체 타입에 의존
- 객체 전체 정보 접근 가능

값 따로 넘기면:
- 더 범용적
- 필요한 것만 전달 (최소 지식 원칙)
어떻게 판단해?

"이 함수가 해당 객체 전용이면?" → 객체 넘기기

"다양한 출처의 값 다루면?" → 값 따로 넘기기

좋은 케이스 vs 나쁜 케이스

좋음: CalculatePlayerDamage(player) - 플레이어 전용 명확
나쁨: Add(player) - 더하기 함수가 Player에 의존? 이상해

Part 3. 판단 기준

언제 객체로, 언제 값으로?

기준:

객체 통째로가 좋은 경우

- 파라미터 3개 이상 같은 객체에서 나올 때
- 함수가 그 객체 타입 전용일 때
- 나중에 다른 값도 필요할 가능성 높을 때
값 따로가 좋은 경우

- 범용 유틸리티 함수 (Max, Clamp 등)
- 서로 다른 출처 값 조합할 때
- 객체 의존성 피해야 할 때 (순환 참조 방지)
실용적 기준 있어?

"이 함수가 특정 객체에 속한다고 느껴지나?"

Yes → 객체 넘기기 (또는 그 객체의 메서드로 이동)

No → 값 넘기기

Part 4. Parameter Object와 차이

Parameter Object랑 뭐가 달라?

비슷하지만 목적이 달라:

두 기법 비교

Parameter Object:
- 관련 없는 값들을 새로운 객체로 묶기
- (x, y, z) → new Point(x, y, z)

Preserve Whole Object:
- 이미 있는 객체에서 따로 꺼내지 않기
- player.X, player.Y → player
변환 절차는?

1. 시그니처 변경 - 객체 파라미터 추가

2. 내부에서 객체.getter로 접근

3. 호출부에서 객체 전달

4. 기존 파라미터 제거, 테스트

핵심 정리: Preserve Whole Object

  • 방법: 객체에서 값 꺼내지 말고 객체 자체를 넘기기
  • 장점: 시그니처 안정, 가독성, 타입 안전
  • 주의: 불필요한 의존성 생성 여부 판단
  • 기준: 함수가 객체 전용이면 객체, 범용이면 값
  • 구분: Parameter Object는 새로 만들기, 이건 기존 활용
