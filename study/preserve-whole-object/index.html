Refactoring #20

Preserve Whole Object

객체 통째로 넘기기 - 의존성을 관리하라

객체 통째로 넘기기가 뭐예요?
객체에서 여러 값을 꺼내서 따로따로 넘기지 말고, 객체 자체를 넘기는 것이에요.

예를 들어:

Calculate(player.GetLevel(), player.GetStr(), player.GetDex())

이렇게 하지 말고:

Calculate(player)

객체를 통째로 전달하는 거죠.
왜 객체를 통째로 넘기는 게 좋아요?
여러 이점이 있어요:

1. 시그니처 안정성
나중에 Dex도 필요해지면? - 따로 넘기기: 모든 호출부 수정 - 객체 넘기기: 함수 내부만 수정

2. 가독성
파라미터가 6개 vs 1개. 뭐가 읽기 좋을까요?

3. 응집도
"이 함수는 Player 정보를 다룬다"가 명확해짐.

4. 타입 안전성
int, int, int 3개 넘기면 순서 헷갈릴 수 있어요. Player 하나면 실수할 여지가 없어요.

📦 비유: 택배 보내기

주소, 이름, 전화번호, 우편번호를 따로따로 말하기 vs
"이 송장대로 보내주세요"라고 송장 한 장 주기

어떤 게 실수가 적고 효율적일까요?
그런데 불필요한 의존성이 생기지 않나요?
좋은 질문이에요! 핵심 트레이드오프입니다.

객체를 넘기면:
- 호출받는 함수가 해당 객체 타입에 의존
- 객체 전체 정보에 접근 가능 (필요 이상)

값을 따로 넘기면:
- 더 범용적 (어떤 출처의 값이든 가능)
- 필요한 것만 전달 (최소 지식 원칙)

판단 기준:

1. 함수가 해당 객체의 것만 다루나요?
→ Yes면 객체 넘기기 유리

2. 함수가 다양한 출처의 값을 다루나요?
→ Yes면 값 따로 넘기기 유리

⚠️ 균형점 찾기

좋은 케이스: CalculatePlayerDamage(player)
→ 함수가 플레이어 전용이라는 게 명확

나쁜 케이스: Add(player)
→ 더하기 함수가 Player에 의존? 이상해요.
언제 객체로 넘기고, 언제 값으로 넘기나요?
객체 통째로가 좋은 경우:

- 파라미터가 3개 이상 같은 객체에서 나올 때
- 함수가 그 객체 타입 전용일 때
- 나중에 그 객체의 다른 값도 필요할 가능성이 높을 때

값 따로 넘기기가 좋은 경우:

- 범용 유틸리티 함수 (Max, Clamp 등)
- 서로 다른 출처의 값을 조합할 때
- 객체 의존성을 피해야 할 때 (순환 참조 방지)

💡 실용적 기준

"이 함수가 특정 객체에 속한다고 느껴지나요?"

Yes → 객체 넘기기 (또는 그 객체의 메서드로 이동 고려)
No → 값 넘기기
Parameter Object와 뭐가 달라요?
비슷하지만 목적이 달라요:

Parameter Object (파라미터 객체 도입):
- 관련 없는 여러 값들을 새로운 객체로 묶기
- 목적: 긴 파라미터 목록 정리
- 새 클래스/구조체를 만듦

Preserve Whole Object:
- 이미 있는 객체에서 값을 따로 꺼내지 않기
- 목적: 기존 객체를 그대로 활용
- 새로 만들지 않음

예시:
- Parameter Object: (x, y, z) → new Point(x, y, z)
- Preserve Whole Object: player.X, player.Y → player
변환 절차는요?
단계별 진행:

1단계: 함수 시그니처 변경
→ 개별 파라미터 대신 객체 파라미터 추가

2단계: 함수 내부 수정
→ 파라미터 변수를 객체.getter로 변경

3단계: 호출부 수정
→ 값 나열 대신 객체 전달

4단계: 기존 파라미터 제거
5단계: 테스트

IDE의 "Change Signature" 기능을 활용하면 쉬워요.

📌 Preserve Whole Object 핵심 정리

  • 객체에서 값을 꺼내지 말고 객체 자체를 넘기기
  • 시그니처 안정, 가독성, 타입 안전성 향상
  • 단, 불필요한 의존성 생성 여부 판단 필요
  • 함수가 해당 객체 전용이면 객체 넘기기 유리
  • 범용 함수라면 값 따로 넘기기 유리
