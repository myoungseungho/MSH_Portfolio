버그를 빨리 잡는 개발자 도구의 비밀

넥슨 인프라기술팀의 실전 경험 - 마비노기 프로젝트 사례

Part 1. 버그란 뭐야?

버그가 뭔지 정확히 정의해줄 수 있어?

버그 = 원하지 않는 결과가 나오는 것

이게 전부야. 복잡하게 생각할 필요 없어.

예시: - 갑자기 서버가 죽었다 - 게임 하다가 로그인 창으로 튕겼다 - 내 캐릭터가 너무 못생겼다 (의도하지 않은 결과!)
그러면 버그를 어떻게 잡아야 해?

"원인을 찾으면" 거의 해결된 거야.

버그 잡기에서 제일 어려운 건 수정이 아니라 원인 찾기야.

의사 비유

환자가 "배가 아파요" 라고 했을 때,
진단(원인 찾기)이 어렵지, 진단 나오면 치료(수정)는 비교적 쉽잖아.

버그도 마찬가지야. "어디가 문제인지" 알면 고치는 건 금방이야.

Part 2. 왜 원인 찾기가 어려워?

버그 원인 찾기가 왜 그렇게 힘들어?

크게 3가지 이유가 있어.

문제 설명 예시
1. 근거 유실 툴을 미리 붙여놔야만 정보 수집 가능 갑자기 게임이 느려졌는데, 프로파일러 안 붙여놨으면 원인 모름
2. 정보 흩어짐 수집해도 순서/위치 파악이 어려움 어떤 클라이언트? 어떤 버전? 어디서부터 봐야 해?
3. 작업자 시간 툴 붙이기, 로그 분석 등 전부 수동 작업 개발자가 하나하나 직접 해야 함
그래서 개발자들이 밤새 버그 잡느라 고생하는 거구나?

맞아. 원인 추적이 어려운 버그가 생기면,

낮에도 밤에도 새벽에도 고생하게 돼.

핵심 문제

"버그가 재현 안 돼요" → 근거가 유실됐으니까!
"어디서 발생한 건지 모르겠어요" → 정보가 흩어져있으니까!
"확인하려면 시간이 너무 걸려요" → 수동 작업이니까!

Part 3. 개발자 도구가 뭐야?

그래서 개발자 도구가 뭔데?

실행 상황을 한눈에 보고, 주요 상황을 추적할 수 있도록 도와주는 보조 도구야.

프로그래머만 쓸 수 있어?

아니! 개발에 참여한 모든 사람이 쓸 수 있어.

기획자, 아티스트, QA도 사용 가능하도록 설계해야 해.

자동차 계기판 비유

운전할 때 속도계, 연료 게이지, 경고등이 있잖아.
운전자가 엔진 구조를 몰라도 "문제 있다"는 걸 바로 알 수 있지.

개발자 도구도 마찬가지야. 코드 몰라도 "문제 상황"을 바로 볼 수 있어야 해.
어떤 정보를 수집해?

기본적으로 이런 것들:

정보 용도
스크린샷 실시간 화면 캡처 - "그때 화면이 어땠는지"
로그 시간순 정렬 - "무슨 일이 일어났는지"
지표/그래프 CPU, 메모리, 게임 내 수치 - "상태가 어땠는지"
예외/덤프 크래시 정보 - "왜 죽었는지"

Part 4. 근거 유실은 어떻게 해결해?

툴을 미리 안 붙여놓으면 정보가 없잖아. 어떻게 해?

상주 모니터링!

개발자가 인지하지 못해도 자동으로 정보를 수집하는 거야.

동작 방식: 1. 윈도우 서비스가 부팅 시 자동 실행 2. 게임 클라이언트가 시작되면 자동으로 붙음 3. 플러그인들이 독립적으로 정보 수집 4. 수집 서버로 자동 전송 → 개발자가 "툴 붙여야지" 생각 안 해도 됨!
효과

"어? 버그 났는데 로그가 없어요" → 이런 상황이 없어짐!
항상 정보가 수집되고 있으니까.

Part 5. 정보 흩어짐은 어떻게 해결해?

정보가 여기저기 흩어져있으면 어떻게 모아?

두 가지 방법이 있어.

해결책 1: 시간순 정렬
  • UTC 시간 단위로 정렬
  • 밀리초 단위까지 확인 가능
  • "A가 먼저? B가 먼저?" 순서 파악이 핵심!
순서가 왜 중요해?

예를 들어 "데이터 복사 버그"가 있다고 해봐.

A를 복사하고 B를 붙여넣기 vs B를 복사하고 A를 붙여넣기

순서가 다르면 결과가 완전히 달라지잖아!

해결책 2: 테스트 단위로 구분
  • 테스트 시작 ~ 종료를 하나의 "세션"으로
  • 어떤 빌드 버전인지, 실행 시간은 얼마인지 기록
  • 나중에 "그때 그 테스트"만 쏙 뽑아볼 수 있음
CCTV 비유

CCTV 영상이 그냥 쭉 이어져있으면 찾기 힘들잖아.
근데 "2024-01-15 14:30 ~ 15:00 / 입구 카메라" 이렇게 구분되어있으면?

필요한 부분만 바로 찾을 수 있지!

Part 6. 작업자 시간은 어떻게 줄여?

매번 수동으로 하는 게 문제라면?

세 가지 방법으로 해결해.

1. 빠른 기능 확장/축소
  • 기능을 DLL 형태로 분리
  • DLL 추가/삭제만으로 기능 on/off
  • 클라이언트 수정 없이 기능 추가 가능
2. 사용자 SDK
  • 한 줄 호출로 로그 남기기
  • 그래프 출력 API
  • 개발자가 원하는 정보를 쉽게 추가
// 예시: 보스 몬스터 밸런싱 확인 SendClientTextLog("보스 HP: %d, 플레이어 DPS: %d", bossHP, playerDPS); // 한 줄이면 끝! // 웹 화면에서 실시간으로 확인 가능
3. 실시간 확인
  • 플레이 화면과 모니터링 화면 동시에 확인
  • 문제가 생기면 바로 캐치!

Part 7. 마이크로서비스가 뭐야?

기능 확장/축소가 쉽다고 했는데, 어떻게 가능해?

마이크로서비스 아키텍처 덕분이야.

작은 서비스들을 모아서 하나의 큰 서비스를 만드는 방식이야.

레고 블록 비유

레고는 블록 하나하나가 독립적이잖아.
원하는 블록만 끼우고 빼고 할 수 있지.

마이크로서비스도 마찬가지야.
"로그 플러그인" "프로파일러 플러그인" "덤프 플러그인"...
필요한 것만 붙이고 필요 없으면 빼면 돼!
장점 개발자 도구에서는
구현 방식 상관없음 상용 프로파일러, 레거시 코드 다 붙일 수 있음
확장/축소 유리 클라이언트 수정 없이 기능 추가/삭제
부분 장애 격리 플러그인 하나 죽어도 전체는 정상 동작

Part 8. 실시간으로 어떻게 빠르게 보여줘?

세상에서 제일 빠른 서버가 뭐야?

로컬 서버!

네트워크 왕복 시간이 없으니까.

최적화 전략: 1. 로컬 웹서버 기반 → 응답 시간 최소화 2. 별도 서버 분리 → 스크린샷, 영상 등 무거운 건 따로 3. 테스트 단위별 DB 분리 → SQLite로 DB 경합 방지 4. 별개 프로세스에서 전송 → 클라이언트 죽어도 정보는 수집됨! 5. 같은 성격 정보 묶어서 전송 → 로그는 로그끼리
클라이언트가 죽어도 정보가 수집된다고?

맞아! 별개 프로세스에서 수집하니까,

게임이 크래시 나도 "왜 죽었는지" 정보는 살아있어.

이게 중요한 이유

크래시 버그가 제일 급한데,
게임이 죽으면서 정보도 같이 날아가버리면 원인을 못 찾잖아!

별개 프로세스로 분리해놓으면 → 크래시 직전까지의 정보 확보 가능!

Part 9. 전체 구조가 어떻게 생겼어?

전체 시스템 구조를 보여줄 수 있어?

이렇게 생겼어:

+------------------+ Named Pipe +------------------+ | Game Client | ================> | 사이드킥 모듈 | | (모니터링 대상) | | (Sidekick Module)| +------------------+ +------------------+ | | JSON 문자열 v +------------------+ HTTP/UDP +------------------+ | 플러그인들 | ================> | 수집 서버 | | (성능/로그/덤프) | | (로컬 웹서버) | +------------------+ +------------------+ | v +------------------+ | SQLite DB | | (테스트 단위별) | +------------------+ | v +------------------+ | 웹 인터페이스 | | (실시간 모니터링) | +------------------+
기술 스택은 뭐야?

"최소 사양"으로 구성했어.

대부분의 윈도우 개발 환경에서 돌아가게 하는 게 목표니까.

영역 기술
웹 서버/API Python Flask + GraphQL
패키징 PyInstaller (Python 설치 없이 실행)
Windows 서비스 .NET Framework
DB SQLite (파일 DB)
프로세스 간 통신 Named Pipe

Part 10. 수집한 정보를 어떻게 공유해?

다른 사람한테 버그 정보 공유하려면?

아카이빙 서버를 통해 세션 단위로 공유해.

공유 방법: 1. 세션 선택하여 업로드 2. 해시키 발급받음 3. 동료에게 해시키 전달 4. 동료가 해시키로 세션 조회 및 다운로드 → "그 버그 봐봐" → 해시키 전달 → 바로 확인!
서버가 없으면?

ZIP 파일로 임포트/익스포트 가능!

어디서든 공유할 수 있어.

Part 11. 게임이 아닌 프로그램도 모니터링할 수 있어?

우리 게임 코드에 SDK를 안 붙여도 돼?

가능해!

연동 없이 모니터링: 1. 모니터링 프로그램 생성 2. 대상 프로세스의 PID 획득 3. 사이드킥이 붙은 프록시 프로세스 실행 4. 플러그인에서 정보 수집 (스크린샷, 리소스 모니터링) → 파워포인트도 모니터링 가능!
외부 관찰자 비유

내가 달리기를 할 때,
코치가 내 몸에 센서를 붙이지 않아도 밖에서 볼 수 있잖아.

"지금 몇 초야?" "폼이 이상해!" 이런 거 확인 가능하지.
개발자 도구도 마찬가지야. 외부에서 관찰만 해도 많은 정보를 얻을 수 있어.

Part 12. 결론: 버그를 빨리 잡으려면?

3가지 원칙
  • 근거 유실을 막아라 → 상주 모니터링 (자동으로 항상 수집)
  • 정보를 모아라 → 시간순 정렬, 테스트 단위별 구분
  • 작업자 시간을 줄여라 → 빠른 기능 확장, SDK, 실시간 확인
한 줄 요약

"자동으로 모으고, 한눈에 보여주고, 쉽게 확장하라"

핵심 정리: 개발자 도구의 역할

  • 버그 - 원하지 않는 결과, 원인 찾으면 거의 해결
  • 근거 유실 - 상주 모니터링으로 자동 수집
  • 정보 흩어짐 - 시간순 정렬 + 테스트 단위 구분
  • 작업자 시간 - 마이크로서비스, SDK, 실시간 확인
  • 실시간 성능 - 로컬 서버 + 별개 프로세스 + DB 분리
  • 공유 - 아카이빙 서버 또는 ZIP 파일
