개발이 쉬워지는 생산성을 올려주는 개발자 도구 툴

버그를 빨리 잡고, 원인을 쉽게 찾는 방법

넥슨 인프라기술팀 홍진호 | NDC 발표

핵심 요약

  • 버그 = 원하지 않는 결과. 버그를 잡으려면 원인을 찾기 쉽게 만들어야 한다
  • 원인 찾기 어려운 3가지 이유: 근거 유실, 정보 흩어짐, 작업자 시간 소요
  • 개발자 도구의 역할: 로그, 프로파일러, 디버거를 통한 정보 수집과 분석 자동화
  • 마비노기 프로젝트 경험을 바탕으로 한 실전 솔루션 공유
버그란 무엇인가?

버그 = 원하지 않는 결과가 나오는 것

예시:

  • 갑자기 서버가 죽었다
  • 게임 하다가 로그인 창으로 튕겼다
  • 내 캐릭터가 너무 못생겼다 (의도하지 않은 결과)
버그를 잡기 위한 핵심은 "원인을 찾는 것"이다. 원인을 찾으면 대부분 해결 가능하다.
왜 버그 잡기가 어려울까?

버그 잡기가 힘든 이유는 원인 찾기가 힘들기 때문이다.

불특정 상황, 측정 불가한 경우에서 원인 찾기가 어려워진다.

원인 추적이 어려운 버그가 종종 생기기 때문에, 낮에도 밤에도 새벽에도 버그를 잡느라 고생하게 된다.
원인을 찾기 어려운 3가지 이유는?
문제 설명 예시
1. 근거 유실 툴을 붙여야만 수집 가능한 정보가 많음 내 PC에서 게임이 느려졌는데, 로그 툴/프로파일러/디버거를 미리 붙여놓지 않으면 근거 확보 불가
2. 정보 흩어짐 수집해도 어떤 순서인지, 어디서 발생했는지 확인 어려움 어떤 클라이언트에서 발생? 어떤 버전에서 발생? 어디서부터 봐야 하지?
3. 작업자 시간 소요 툴 붙이기, 로그 분석, 콜스택 확인, 재현 방법 파악 등 모두 수동 작업 개발자가 일일이 작업해야 함
해결책: 원인을 찾기 쉽게 만들어야 한다!
개발자 도구 툴이란 무엇인가?

클라이언트 개발 중 여러 실행 상황을 한눈에 보고, 필요한 주요 상황을 추적할 수 있도록 도와주는 보조 도구

사용 대상:

  • 개발자뿐만 아니라 개발에 참여한 모든 사람이 사용 가능
  • 프로그래머가 아니어도 사용할 수 있도록 설계

동작 방식:

  1. 툴을 시작하면 자동으로 노티 아이콘 표시
  2. 아이콘 더블클릭하면 웹 페이지로 이동
  3. 빌드 이름별, 빌드 타임별, 테스트 단위별로 구분하여 정보 확인
개발 전용: 라이브 배포 시에는 개인정보보호, 대량 데이터 수집 구조 등 고려사항이 많아 개발 환경 전용으로 설계
개발자 도구는 어떤 정보를 수집하는가?

기본 제공 정보:

  • 스크린샷 - 실시간 화면 캡처
  • 로그 - 시간순 정렬된 로그 데이터
  • 지표/그래프 - CPU, 메모리, 은행 잔고 등 수치 데이터
  • 예외/덤프 - 크래시 발생 시 어떤 예외가 발생했는지, 덤프 파일

플러그인으로 확장 가능:

  • 성능 모니터링
  • 예외 이벤트 감지
  • 덤프 생성
  • 상용 프로파일러 연동 (Very Sleepy 등)

시스템 아키텍처

+------------------+ Named Pipe +------------------+ | Game Client | ================> | 사이드킥 모듈 | | (모니터링 대상) | | (Sidekick Module)| +------------------+ +------------------+ | | JSON 문자열 v +------------------+ HTTP/UDP +------------------+ | 플러그인들 | ================> | 수집 서버 | | (성능/로그/덤프) | | (로컬 웹서버) | +------------------+ +------------------+ | v +------------------+ | SQLite DB | | (테스트 단위별) | +------------------+ | v +------------------+ | 웹 인터페이스 | | (실시간 모니터링) | +------------------+
근거 유실 문제를 어떻게 해결했는가?

해결책: 상주 모니터링

개발자가 인지하지 못해도 자동으로 정보를 수집하는 동작

구현 방법:

  1. 윈도우 서비스가 부팅 시 관련 바이너리를 미리 실행
  2. 사이드킥 모듈이 API 호출 시 관련 플러그인들을 자동 호출
  3. 플러그인들은 독립적으로 수집 서버로 정보 전송
효과: 개발자의 수고를 줄이고, 툴을 수동으로 붙이지 않아도 근거가 유실되지 않음
정보 흩어짐 문제를 어떻게 해결했는가?

해결책 1: 시간순 정렬

  • UTC 시간 단위로 인터페이스 구성
  • 밀리초 단위로 확인 가능
  • 순서를 알아야 해결 가능한 문제 대응 (데이터 복사 버그, 인게임 진입 실패 등)

해결책 2: 테스트 단위로 구분

  • 테스트 시작부터 종료까지를 하나의 단위로
  • 어떤 빌드 버전인지, 어떤 상태인지, 실행 시간은 얼마인지 카테고리화
  • 세션 만들고 해제하는 것으로 마킹 → 나중에 정보 취합 시 유용
타임라인 선택, 시간순 로그 정렬, 그래프 선택 시 해당 위치 이동 등 연동된 인터페이스 제공
작업자 시간 소요 문제를 어떻게 해결했는가?

해결책 1: 빠른 기능 확장/축소

클라이언트 작업 없이도 원하는 기능을 추가/삭제 가능

  • 기능을 DLL 형태로 분리
  • DLL 추가/삭제만으로 기능 확장/축소
  • 마이크로서비스 아키텍처 적용

해결책 2: 사용자 SDK

개발자가 원하는 정보를 쉽게 확인할 수 있는 API 제공

  • SendClientTextLog() - 한 줄 호출로 로그 남기기
  • 그래프 출력 API
  • 예: 보스 몬스터 밸런싱 확인, 실시간 지표 모니터링

해결책 3: 실시간 확인

플레이 상황과 모니터링 상황을 동시에 확인

마이크로서비스 아키텍처란?

작은 여러 개의 서비스들을 모아서 하나의 서비스를 만드는 방식

예시 - 포털 사이트:

  • 검색 서버, 유저 정보 서버 등을 각각 독립된 서버로 구성
  • 이들을 취합해서 웹 서비스 구성
장점 개발자 도구에서의 적용
각 서버 구현 방식 상관없음 다양한 기능을 빠르게 접목 (상용 프로파일러, 레거시 코드)
기능 확장/축소 유리 클라이언트 수정 없이 기능 추가/삭제 가능
전체 장애 빈도 감소 플러그인 하나 문제 생겨도 전체 수집 기능에 영향 없음
실시간 모니터링을 위해 어떤 최적화를 했는가?
핵심 질문: 세상에서 제일 빠른 서버는? → 로컬 서버!

최적화 전략:

  1. 로컬 웹서버 기반 - 응답 시간 최소화
  2. 별도 서버 분리 - 스크린샷, 영상 재생 등 리소스 많이 쓰는 기능은 별도 서버로
  3. 테스트 단위별 DB 분리 - 파일 DB(SQLite) 사용, DB 경합 방지
  4. 별개 프로세스에서 전송 - 클라이언트 상태가 나빠도 정보 수집 가능
  5. 같은 성격 정보 묶어서 전송 - 로그는 로그끼리, 프로파일러는 프로파일러끼리
수집한 정보를 어떻게 공유하는가?

아카이빙 서버를 통한 세션 단위 공유:

  1. 세션을 선택하여 업로드
  2. 해시키 발급
  3. 해시키로 세션 조회 및 가져오기
  4. 여러 세션 동시 공유 가능

서버 없는 환경에서는 ZIP 파일로 임포트/익스포트 가능

연동 없이도 사용할 수 있는가?

가능하다!

구현 방식:

  1. 모니터링 프로그램 생성
  2. 대상 PID 획득
  3. 사이드킥이 붙은 프록시 프로세스 실행
  4. 플러그인에서 연동 없이 정보 수집 (스크린샷, 로그, 리소스 모니터링)
예시: 파워포인트를 연동 없이 모니터링 - 스크린샷, 리소스 모니터링 정보 실시간 확인 가능
어떤 기술 스택을 사용했는가?
영역 기술

모듈 자체 개발
프로세스 간 통신 Named Pipe
설계 원칙: "최소 사양"으로 대부분의 윈도우 개발 환경에서 돌아가게 하는 것이 목적. 누구나 만들 수 있는 기술로 구성.
발표 핵심 정리

버그를 빨리 잡으려면?

  1. 근거 유실을 막고 → 상주 모니터링
  2. 정보를 모으고 → 시간순, 테스트 단위별 정렬
  3. 작업자의 시간을 줄인다 → 빠른 기능 확장, 사용자 SDK, 실시간 확인
핵심: 빠른 원인 파악이 중요하다. 이를 위해 상주 모니터링, 실시간 모니터링, 빠른 기능 확장, 사용자 SDK를 지원하고, 웹 인터페이스로 정보를 구분한다.
