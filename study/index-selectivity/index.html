WHERE 조건 순서를 바꿨더니 10배 빨라졌다

인덱스 선택도와 카디널리티 - 복합 인덱스 컬럼 순서의 비밀

Part 1. 똑같은 조건인데 왜 속도가 달라?

WHERE 조건에 같은 컬럼들을 썼는데, 순서만 바꿨더니 10배 빨라졌어. 왜?

인덱스 컬럼 순서 때문이야.

복합 인덱스는 첫 번째 컬럼부터 순서대로 사용해.

[복합 인덱스 예시] 인덱스: IX_Player (ServerID, Level, Class) 데이터가 정렬되는 방식: ┌─────────┬───────┬───────┐ │ServerID │ Level │ Class │ ├─────────┼───────┼───────┤ │ 1 │ 10 │ 전사 │ │ 1 │ 10 │ 마법 │ │ 1 │ 20 │ 전사 │ ← ServerID가 먼저, │ 1 │ 20 │ 도적 │ 그 안에서 Level, │ 2 │ 10 │ 전사 │ 그 안에서 Class │ 2 │ 15 │ 마법 │ └─────────┴───────┴───────┘
그래서 순서가 왜 중요한데?

전화번호부 생각해봐.

"김씨 성 → 철수 이름" 순서로 정렬되어 있어.

[전화번호부 비유] 전화번호부: (성, 이름) 순서로 정렬 ✅ "김철수" 찾기 = 쉬움 "김"으로 시작하는 페이지 → "철수" 찾기 ❌ "철수" 찾기 (성 모름) = 어려움 처음부터 끝까지 전부 뒤져야 함! 이게 바로 인덱스의 "선두 컬럼" 원리

Part 2. 선택도와 카디널리티 - 핵심 개념

선택도(Selectivity)가 뭐야?

"이 조건으로 얼마나 좁혀지느냐"야.

[선택도 예시] 테이블: TPlayer (100만 명) 컬럼별 분포: ├── Gender (성별): 2가지 (남/여) │ → 한 값 검색 시: 50만 명 (50%) │ → 선택도: 낮음 ❌ │ ├── ServerID: 10가지 (1~10 서버) │ → 한 값 검색 시: 10만 명 (10%) │ → 선택도: 중간 │ └── CharNo (캐릭터번호): 100만 가지 → 한 값 검색 시: 1명 (0.0001%) → 선택도: 높음 ✅
카디널리티(Cardinality)는?

"고유한 값의 개수"야.

컬럼 카디널리티 선택도 인덱스 효과
Gender 2 낮음 나쁨
ServerID 10 중간 보통
Level 100 중간 보통
CharNo 100만 높음 최고

카디널리티가 높을수록 = 더 많이 좁혀짐 = 인덱스 효과 좋음

Part 3. 복합 인덱스 컬럼 순서 정하기

그럼 복합 인덱스 만들 때 어떤 컬럼을 먼저 넣어야 해?

카디널리티가 높은 컬럼을 앞에!

...인 것 같지만, 사실 그것만은 아니야.

[인덱스 순서 결정 요소] 1. 등호(=) 조건 먼저 WHERE ServerID = 1 AND Level > 50 → ServerID를 먼저 (등호 조건) 2. 자주 사용되는 쿼리 패턴 항상 ServerID로 검색한다면 ServerID 먼저 3. 카디널리티 (동등 조건이면) 더 좁혀지는 컬럼 먼저 우선순위: 등호 조건 > 사용 빈도 > 카디널리티
예시 좀 보여줘.

게임 서버 아이템 검색 예시:

-- 쿼리: 특정 서버의 50레벨 이상 전사 찾기 SELECT * FROM TPlayer WHERE ServerID = 1 -- 등호 AND Level >= 50 -- 범위 AND Class = '전사' -- 등호
인덱스 순서 동작 효율
(ServerID, Class, Level) 서버→전사→레벨범위 스캔 ✅ 좋음
(Level, ServerID, Class) 레벨부터 범위스캔 → 비효율 ❌ 나쁨
(ServerID, Level, Class) 서버→레벨범위→Class 못씀 ⚠️ 보통

범위 조건 이후 컬럼은 인덱스를 못 탄다!

그래서 등호 조건을 앞에 모으는 거야.

Part 4. 실제로 얼마나 차이 나?

진짜 10배씩 차이 나?

100만 건 테이블 실측 예시:

[실측 데이터] 테이블: TInventory (100만 건) 조건: CharNo = 12345 AND ItemType = 1 케이스 1: 인덱스 (ItemType, CharNo) → ItemType = 1: 20만 건 스캔 → 그 중 CharNo = 12345: 50건 → 소요: 850ms 케이스 2: 인덱스 (CharNo, ItemType) → CharNo = 12345: 500건 스캔 → 그 중 ItemType = 1: 50건 → 소요: 3ms 차이: 283배!

CharNo의 카디널리티가 훨씬 높으니까

먼저 좁히면 훨씬 빨라.

-- 실행 계획으로 확인하기 SET STATISTICS IO ON SET STATISTICS TIME ON SELECT * FROM TInventory WHERE CharNo = 12345 AND ItemType = 1 -- 결과에서 "logical reads" 확인 -- reads가 적을수록 효율적

Part 5. 카디널리티 확인하는 법

내 테이블 컬럼들의 카디널리티를 어떻게 알아?

두 가지 방법이 있어.

-- 방법 1: 직접 카운트 SELECT COUNT(DISTINCT ServerID) AS ServerID_Card, COUNT(DISTINCT Level) AS Level_Card, COUNT(DISTINCT Class) AS Class_Card, COUNT(DISTINCT CharNo) AS CharNo_Card, COUNT(*) AS Total_Rows FROM TPlayer
-- 방법 2: 통계 정보 확인 (더 빠름) DBCC SHOW_STATISTICS ('TPlayer', 'IX_Player_ServerLevel') -- 결과에서 Density 확인 -- Density = 1 / 카디널리티 -- Density가 낮을수록 = 카디널리티 높음

Density = 1 / 카디널리티

Density 0.01 = 카디널리티 100

Density 0.000001 = 카디널리티 100만 (매우 좋음!)

Part 6. 게임 서버 실전 팁

게임 서버에서 자주 쓰는 인덱스 패턴은?

캐릭터 기준 조회가 대부분이라서...

인벤토리 테이블

인덱스: (CharNo, SlotType, SlotNo)
이유: 항상 CharNo로 먼저 검색

퀘스트 테이블

인덱스: (CharNo, QuestState)
이유: "이 캐릭터의 진행중인 퀘스트"

거래소 테이블

인덱스: (ItemType, ServerID, Price)
이유: "전사 무기 중 1서버에서 가격순 정렬"

로그 테이블

인덱스: (LogDate, LogType, CharNo)
이유: "오늘 날짜의 거래 로그" (날짜 범위 먼저)

결론: 쿼리 패턴을 먼저 분석하고,

등호 조건 → 카디널리티 높은 순으로 인덱스 설계해.

핵심 정리

  • 카디널리티 = 고유한 값의 개수 (높을수록 좋음)
  • 선택도 = 조건으로 좁혀지는 정도 (많이 좁혀질수록 좋음)
  • 인덱스 순서: 등호 조건 > 사용 빈도 > 카디널리티
  • 범위 조건 이후 컬럼은 인덱스를 제대로 못 탐
  • 게임 서버: 대부분 CharNo가 선두 컬럼
  • 확인법: COUNT(DISTINCT) 또는 DBCC SHOW_STATISTICS
