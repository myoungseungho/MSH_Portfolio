인덱스 키 vs INCLUDE - 언제 무엇을 써야 할까?

INCLUDE 컬럼의 원리와 올바른 사용법

Part 1. 인덱스 구조 복습

인덱스 키(Key)가 뭐야?

인덱스에서 정렬 기준이 되는 컬럼이야.

-- i32Level이 인덱스 키 CREATE INDEX IX_Level ON TCharacter (i32Level)
그럼 정렬이 왜 중요해?

정렬되어 있어야 빠르게 검색할 수 있어.

정렬된 사전에서 단어 찾기 vs 뒤죽박죽 사전에서 찾기

📚 정렬된 사전 (인덱스 있음): A... B... C... → "Cat" 바로 찾기 (3초) 📚 뒤죽박죽 사전 (인덱스 없음): Z... A... M... → "Cat" 처음부터 다 뒤지기 (30분)

Part 2. INCLUDE 컬럼이란?

INCLUDE 컬럼은 뭐야? 키랑 뭐가 달라?

리프 레벨에만 저장되는 컬럼이야.

검색에는 안 쓰이지만, 조회할 때 같이 가져오기 위해 포함.

리프 레벨?

인덱스 구조를 보자. B-Tree 구조야.

🌳 B-Tree 인덱스 구조: ┌───────────────┐ │ 루트 (Root) │ ← 최상위 │ [50, 100] │ └───────┬───────┘ ┌────────────┼────────────┐ ↓ ↓ ↓ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ [25,40] │ │ [75,90] │ │[125,150]│ ← 중간 레벨 └────┬────┘ └────┬────┘ └────┬────┘ ↓ ↓ ↓ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ 실제 │ │ 실제 │ │ 실제 │ ← 리프 레벨 │ 데이터 │ │ 데이터 │ │ 데이터 │ (최하위) └─────────┘ └─────────┘ └─────────┘ 💡 INCLUDE 컬럼은 리프 레벨에만 존재!
왜 리프 레벨에만 넣어?

검색에는 안 쓰이니까 상위 레벨에 없어도 돼.

상위 레벨을 작게 유지 → 인덱스 탐색이 빠름.

Part 3. 키 컬럼 vs INCLUDE 컬럼

둘의 차이를 정리해줘.

핵심 차이점:

구분 키 컬럼 INCLUDE 컬럼
저장 위치 모든 레벨 리프 레벨만
정렬 여부 정렬됨 정렬 안 됨
WHERE 조건 검색 가능 검색 불가
ORDER BY 정렬 활용 정렬 불가
SELECT 조회 가능 가능
인덱스 크기 더 큼 더 작음
그럼 INCLUDE가 항상 좋은 거 아냐?

검색이나 정렬에는 못 써!

용도가 다른 거야.

Part 4. 언제 무엇을 써야 할까?

판단 기준이 뭐야?

그 컬럼이 검색/정렬에 쓰이는가?가 기준.

🎯 판단 흐름: 해당 컬럼이... ┌─ WHERE 조건에 쓰인다? ───────→ 키 컬럼 ├─ ORDER BY에 쓰인다? ─────────→ 키 컬럼 ├─ GROUP BY에 쓰인다? ─────────→ 키 컬럼 └─ SELECT에만 나온다? ─────────→ INCLUDE 컬럼
-- 이 쿼리를 분석해보자 SELECT i32CharSID, szCharName, i32Level FROM TCharacter WHERE i32WorldNo = 1 AND i32Level >= 90 ORDER BY i32Level DESC -- 분석: -- i32WorldNo: WHERE 조건 → 키 -- i32Level: WHERE + ORDER BY → 키 -- i32CharSID: SELECT만 → INCLUDE -- szCharName: SELECT만 → INCLUDE -- 최적의 인덱스: CREATE INDEX IX_World_Level_Cover ON TCharacter (i32WorldNo, i32Level DESC) INCLUDE (i32CharSID, szCharName)

Part 5. 잘못된 사용 예시

INCLUDE를 잘못 쓰면 어떻게 돼?

인덱스를 못 쓰거나 효율이 떨어져.

-- ❌ 잘못된 예시 1: 검색 컬럼을 INCLUDE에 CREATE INDEX IX_Bad1 ON TCharacter (i32WorldNo) INCLUDE (i32Level) -- Level이 검색 조건인데! -- 이 쿼리에서 Level 범위 검색 불가 WHERE i32WorldNo = 1 AND i32Level >= 90 -- → World로 찾고, Level은 하나씩 체크 (느림)
-- ❌ 잘못된 예시 2: 정렬 컬럼을 INCLUDE에 CREATE INDEX IX_Bad2 ON TCharacter (i32WorldNo) INCLUDE (i32Level) -- 이 쿼리에서 Level 정렬 불가 ORDER BY i32Level DESC -- → 인덱스에서 못 정렬 → 추가 Sort 연산 필요
-- ✅ 올바른 예시 CREATE INDEX IX_Good ON TCharacter (i32WorldNo, i32Level DESC) -- 검색+정렬 컬럼은 키에 INCLUDE (i32CharSID, szCharName) -- 조회만 하는 건 INCLUDE

Part 6. 인덱스 크기 차이

INCLUDE 쓰면 인덱스 크기가 왜 작아?

상위 레벨에 저장 안 되니까.

📊 예시: 100만 건 테이블 Option A: 전부 키 컬럼 (WorldNo, Level, CharSID, CharName) ├── 루트 레벨: 4개 컬럼 저장 ├── 중간 레벨: 4개 컬럼 저장 └── 리프 레벨: 4개 컬럼 저장 → 총 크기: 350MB Option B: INCLUDE 사용 (WorldNo, Level) INCLUDE (CharSID, CharName) ├── 루트 레벨: 2개 컬럼 저장 ├── 중간 레벨: 2개 컬럼 저장 └── 리프 레벨: 4개 컬럼 저장 → 총 크기: 280MB 💡 약 20% 절약! (대형 테이블일수록 차이 큼)
크기가 작으면 뭐가 좋아?

메모리에 더 많이 캐싱 가능.

캐시 적중률 ↑ → 디스크 I/O ↓ → 성능 ↑

Part 7. 실전 인덱스 설계 가이드

인덱스 설계할 때 순서가 있어?

쿼리를 분석해서 단계별로 결정해.

📋 인덱스 설계 순서: Step 1️⃣ WHERE 조건 컬럼 수집 → 등호(=) 조건 먼저, 범위 조건 나중에 Step 2️⃣ ORDER BY 컬럼 추가 → WHERE와 같은 순서면 좋음 Step 3️⃣ SELECT 컬럼 확인 → 위에 없는 것들 → INCLUDE Step 4️⃣ 컬럼 순서 결정 (키 컬럼) → 선택도 높은(유니크한) 것 먼저
-- 실전 예시: 랭킹 조회 -- Step 1: 쿼리 분석 SELECT i32CharSID, szCharName, i32Level, i64Exp FROM TCharacter WHERE i32WorldNo = @WorldNo -- 등호 조건 AND i32DeleteFlag = 0 -- 등호 조건 AND i32Level >= 50 -- 범위 조건 ORDER BY i32Level DESC, i64Exp DESC -- Step 2: 키 컬럼 결정 -- 등호: i32WorldNo, i32DeleteFlag -- 범위+정렬: i32Level, i64Exp -- Step 3: INCLUDE 컬럼 결정 -- SELECT만: i32CharSID, szCharName -- 최종 인덱스 CREATE INDEX IX_Ranking ON TCharacter (i32WorldNo, i32DeleteFlag, i32Level DESC, i64Exp DESC) INCLUDE (i32CharSID, szCharName)

⚠️ 흔한 실수들

1. 모든 컬럼을 키에 넣기 → 인덱스 비대화

2. 검색 컬럼을 INCLUDE에 넣기 → 인덱스 못 씀

3. 정렬 컬럼을 INCLUDE에 넣기 → 추가 Sort 필요

4. INCLUDE에 LOB(ntext, image) 넣기 → 불가능, 에러 발생

📝 핵심 정리

  • 키 컬럼 = 검색/정렬에 사용 (모든 레벨에 저장)
  • INCLUDE 컬럼 = 조회만 (리프 레벨에만 저장)
  • WHERE, ORDER BY, GROUP BY → 키 컬럼으로
  • SELECT에만 나오는 컬럼 → INCLUDE로
  • INCLUDE 사용 → 인덱스 크기 절약 → 캐시 효율 증가
