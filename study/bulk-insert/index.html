1만 건 INSERT, 1초 안에 끝내는 법

Bulk Insert vs 개별 Insert - 실측으로 증명하는 7.7배 성능 차이

Part 1. 문제 상황

게임 종료 시 유저 데이터 1만 개를 저장해야 해. 어떻게 할래?

상황: 레이드 종료

• 참가자 100명

• 각 유저당: 인벤토리 50개 + 퀘스트 30개 + 스킬 20개

• 총 100 × 100 = 약 1만 건 INSERT

그냥 for문 돌면서 1건씩 INSERT 하면 되는 거 아니야?

그게 제일 직관적이긴 해.

INSERT INTO TInven VALUES (...) -- 1번 INSERT INTO TInven VALUES (...) -- 2번 ... INSERT INTO TInven VALUES (...) -- 10000번
시간 복잡도가 O(N)이니까 빠른 거 아니야?

맞아, O(N)이야. 1만 건이면 1만 번 연산.

근데 O(N)인데도 5초 넘게 걸릴 수 있어.

왜? CPU 연산 1만 번이면 마이크로초 단위 아니야?

CPU 연산만 보면 그래. 근데...

INSERT 한 번에 CPU 연산만 일어나는 게 아니야.

Part 2. INSERT 한 번에 뭐가 일어나?

[게임 서버] [DB 서버] | | |--- INSERT 요청 ------------>| (→ 네트워크) | | (DB 처리) |<-- 완료 응답 ---------------| (← 네트워크) | | 다음 INSERT...
아, 네트워크 왕복이 있구나?

맞아. 1번 INSERT = 네트워크 왕복 1번

환경 왕복 시간 (RTT)
localhost (같은 PC) 0.1~0.5ms
같은 데이터센터 0.5~2ms
서울 ↔ 도쿄 30~50ms
로컬이라도 0.5ms면... 1만 건이면?

1만 × 0.5ms = 5,000ms = 5초

서울↔도쿄면? 1만 × 30ms = 300초 = 5분

정리:

• CPU 연산 시간: 0.001초 (무시 가능)

• 네트워크 시간: 5초 (99.9% 차지)

O(N)인데 5초 걸리는 이유 = 네트워크 왕복이 병목

Part 3. 해결책 - 묶어서 보내기

왕복 횟수를 줄이면 되겠네?

정확해. 방법이 크게 두 가지야.

방법 1: VALUES 묶어서 한 방에

-- 개별 (왕복 3번) INSERT INTO TItem VALUES (1, 'sword'); INSERT INTO TItem VALUES (2, 'shield'); INSERT INTO TItem VALUES (3, 'potion'); -- 한 번에 (왕복 1번) INSERT INTO TItem VALUES (1, 'sword'), (2, 'shield'), (3, 'potion');

방법 2: 트랜잭션으로 묶기

BEGIN TRANSACTION INSERT INTO TItem VALUES (1, 'sword'); INSERT INTO TItem VALUES (2, 'shield'); INSERT INTO TItem VALUES (3, 'potion'); COMMIT
둘 다 "묶는다"는 건 같은데, 뭐가 달라?

직접 테스트해보자.

Part 4. 실측 결과

테스트 환경: 로컬 MSSQL 2019, 1000건 INSERT

실측 결과 (로컬 DB, 1000건)

개별 INSERT
231ms
1x (기준)
VALUES 묶음
82ms
2.8배 빠름
트랜잭션 묶음
30ms
7.7배 빠름
어? VALUES 묶는 게 제일 빠를 줄 알았는데, 트랜잭션이 더 빠르네?

좋은 관찰이야. 이유가 있어.

힌트: 로컬 DB라서 네트워크 왕복이 거의 0이야.

그럼 뭐가 병목이었던 거야?

디스크 flush (커밋)가 병목이었어.

Part 5. 잠깐, 커밋이 뭐야?

INSERT 하면 바로 디스크에 저장되는 거 아니야?

아니. 생각해봐.

만약 INSERT 하자마자 디스크에 쓰는데, 그 직후 정전이 되면?

INSERT INTO TItem VALUES (1, 'sword'); -- 디스크에 씀 INSERT INTO TItem VALUES (2, 'shield'); -- 디스크에 씀 INSERT INTO TItem VALUES (3, 'potion'); -- 쓰다가 정전! 💥
데이터가 반만 저장되잖아?

맞아. 더 심각한 예시를 보자.

상황: 아이템 거래

-- 유저 A가 유저 B에게 검 판매 (1000골드) UPDATE TInven SET owner = 'B' WHERE item = 'sword'; -- 1. 검을 B에게 UPDATE TGold SET gold = gold - 1000 WHERE user = 'B'; -- 2. B 돈 차감 UPDATE TGold SET gold = gold + 1000 WHERE user = 'A'; -- 3. A 돈 지급 💥 정전!

결과:

• 검: B한테 갔음 ✅

• B 돈: 1000골드 빠짐 ✅

• A 돈: 안 들어옴 ❌

B는 돈 냈는데 A는 돈 못 받음 = 데이터 불일치

그럼 어떻게 해야 해?

3개 다 성공하거나, 3개 다 실패하거나. 중간이 없어야 해.

이게 트랜잭션이야.

BEGIN TRANSACTION -- 시작 UPDATE TInven SET owner = 'B' WHERE item = 'sword'; UPDATE TGold SET gold = gold - 1000 WHERE user = 'B'; UPDATE TGold SET gold = gold + 1000 WHERE user = 'A'; COMMIT -- 확정!
COMMIT이 "확정"이구나. 그 전까지는?

메모리에만 임시 저장. 디스크엔 안 씀.

단계 저장 위치 속도 정전 시
COMMIT 전 메모리 빠름 날아감 (롤백)
COMMIT 후 디스크 느림 복구됨

COMMIT = "이제 진짜야. 디스크에 영구 저장해."

Part 6. 그래서 왜 트랜잭션이 빨라?

아까 개별 INSERT는 트랜잭션 안 썼잖아. 그럼 COMMIT 안 한 거야?

아니, 했어. Auto-Commit 모드라서.

-- 이렇게 쓰면 INSERT INTO T VALUES (1, 'a'); -- 실제로는 이렇게 동작 BEGIN TRANSACTION INSERT INTO T VALUES (1, 'a'); COMMIT -- 자동으로 붙음!

매 문장마다 자동 COMMIT = 매번 디스크 flush

[A] 개별 INSERT (auto-commit 모드) INSERT → 자동 COMMIT → 디스크 flush INSERT → 자동 COMMIT → 디스크 flush INSERT → 자동 COMMIT → 디스크 flush ... (1000번 디스크 쓰기) [C] 트랜잭션 묶음 BEGIN TRAN INSERT → 메모리에만 INSERT → 메모리에만 INSERT → 메모리에만 ... (1000번 메모리 쓰기) COMMIT → 디스크 flush 1번!
방식 디스크 flush 횟수
A. 개별 INSERT 1000번
C. 트랜잭션 묶음 1번

이게 7.7배 차이의 원인이야.

그럼 B(VALUES 묶음)는? 그것도 INSERT 1번이니까 flush 1번 아니야?

맞아. flush는 1번인데, 다른 문제가 있어.

-- B의 SQL 문장 (실제로 이렇게 생김) INSERT INTO T VALUES (1,'item_1',10),(2,'item_2',20),(3,'item_3',30)... -- 길이: 1000개 × 30자 = 약 3만 자짜리 SQL 문장

SQL Server가 이 3만 자를 파싱(문법 분석)해야 해.

• 괄호 1000개 체크

• 쉼표 3000개 체크

• 문법 맞는지 검증

이게 오버헤드야.

방식 디스크 flush SQL 파싱 결과
A. 개별 1000번 짧은 거 1000개 231ms
B. VALUES 묶음 1번 3만 자 1개 82ms
C. 트랜잭션 1번 짧은 거 1000개 30ms

Part 7. 원격 DB라면?

로컬 테스트 결과인데, 원격이면 어떻게 달라져?

네트워크 왕복이 추가되면 격차가 폭발해.

방식 로컬 (0ms) 데이터센터 (1ms) 서울↔도쿄 (30ms)
개별 INSERT 231ms 1,231ms 30,000ms (30초)
트랜잭션 30ms 31ms 60ms
차이 7배 40배 500배

네트워크가 멀수록 배치/트랜잭션의 효과가 극대화

"1만 건 INSERT하는데 왜 5분이나 걸려요?"

→ 개별 INSERT + 원격 DB = 죽음

핵심 정리

  • COMMIT = "이제 진짜야" - 메모리 → 디스크 영구 저장
  • Auto-Commit = 매 문장마다 자동 COMMIT → 매번 디스크 flush
  • 트랜잭션 묶음 = COMMIT 1번 = flush 1번 (7.7배 빠름)
  • VALUES 묶음 = flush 1번이지만 긴 SQL 파싱 오버헤드
  • 원격 DB = 네트워크 왕복까지 더해져 500배 차이 가능
  • 실무 원칙 = 대량 INSERT는 반드시 트랜잭션으로!
