1단계: 클라이언트-서버 통신 원리

게임에서 몬스터를 때리면 서버는 어떻게 아는 거야?

클라이언트(게임)가 서버에게 패킷(Packet)을 보내.

패킷은 일종의 "편지"야. 안에 정보가 담겨있지.

📮 비유: 편지 보내기

- 클라이언트 = 편지를 쓰는 사람
- 패킷 = 편지 내용 (누구를, 어떻게, 얼마나)
- 네트워크 = 우체국
- 서버 = 편지를 받아서 처리하는 사람
패킷 안에는 뭐가 들어있어?

게임마다 다르지만, 대략 이런 구조야:

[ 공격 패킷 예시 ]
타입: ATTACK 대상: Monster_001 스킬: 기본공격 데미지: 150 체크섬: 0xA3F2
// 실제 패킷 구조 (바이트 단위) struct AttackPacket { uint16_t packetType; // 2바이트: 패킷 종류 (0x0010 = 공격) uint32_t targetId; // 4바이트: 대상 ID uint16_t skillId; // 2바이트: 스킬 ID uint32_t damage; // 4바이트: 데미지 uint16_t checksum; // 2바이트: 무결성 검증 }; // 총 14바이트
💡 핵심 개념
게임의 모든 행동은 패킷이라는 데이터 덩어리로 변환되어
네트워크를 통해 서버로 전송된다.

2단계: 패킷 스니핑 (엿보기)

그 "편지" 내용을 몰래 볼 수 있어?

볼 수 있어. 이걸 패킷 스니핑(Sniffing)이라고 해.

Wireshark 같은 도구를 쓰면 내 컴퓨터에서 나가는 모든 패킷을 볼 수 있어.

게임 클라이언트
→
Wireshark (도청)
→
인터넷
→
게임 서버
Wireshark로 보면 뭐가 보여?

암호화가 안 되어있으면, 모든 게 다 보여:

// Wireshark에서 캡처한 패킷 (16진수) 00 10 00 00 00 01 00 05 00 00 00 96 A3 F2 // 해석: 00 10 → 패킷 타입: 0x0010 (공격) 00 00 00 01 → 대상 ID: 1 (Monster_001) 00 05 → 스킬 ID: 5 (기본공격) 00 00 00 96 → 데미지: 150 (0x96 = 150) A3 F2 → 체크섬
이걸로 뭘 알 수 있어?

패킷 구조를 분석할 수 있어:

- "내가 공격할 때마다 0x0010 패킷이 나가네"
- "데미지 값이 여기 있구나"
- "체크섬은 이렇게 계산되는구나"

패턴을 알면, 조작할 수 있어!

💡 핵심 개념
패킷 스니핑은 네트워크를 지나가는 데이터를 가로채서 읽는 것이다.
암호화되지 않은 패킷은 그 구조가 완전히 노출된다.

3단계: 패킷 변조 (거짓말하기)

패킷 구조를 알았으면, 데미지를 150에서 9999로 바꿔서 보낼 수 있어?

가능해. 이걸 패킷 변조(Tampering)라고 해.

[ 원본 패킷 ]
ATTACK Monster_001 데미지: 150
⬇️ 해커가 수정 ⬇️
[ 변조된 패킷 ]
ATTACK Monster_001 데미지: 9999
어떤 도구로 해?

여러 가지 방법이 있어:

1. 프록시 도구 - Fiddler, Burp Suite
패킷이 나가기 전에 가로채서 수정

2. 패킷 에디터 - WPE Pro (옛날에 유명했음)
실시간으로 패킷을 잡아서 바꿈

3. 메모리 조작 - 패킷이 만들어지는 시점에 값을 바꿈

// 해커의 패킷 변조 스크립트 (개념) function interceptPacket(packet) { if (packet.type === "ATTACK") { packet.damage = 9999; // 데미지 조작! packet.checksum = calculateChecksum(packet); // 체크섬 재계산 } return packet; }
서버가 "데미지 9999"를 받으면 진짜 그만큼 데미지가 들어가?

옛날 게임들은 그랬어.

클라이언트를 신뢰했기 때문이야.

// 나쁜 서버 코드 (클라이언트 신뢰) void HandleAttack(AttackPacket* packet) { Monster* target = FindMonster(packet->targetId); target->hp -= packet->damage; // 클라가 보낸 데미지 그대로 적용! }

결과: 원래 150 데미지인데 9999 데미지로 원킬!

⚔️ 이 시점에서 해커가 할 수 있는 것들

- 데미지 핵: 공격력 무한 증가

- 아이템 복사: "아이템 1개 사용" 패킷을 "10000개 획득"으로 변조

- 텔레포트: 좌표 패킷을 조작해서 순간이동

- 스피드핵: 이동 패킷을 빠르게 연속 전송

💡 핵심 개념
패킷 구조를 알면 원하는 값으로 수정해서 전송할 수 있다.
서버가 클라이언트를 신뢰하면 그대로 적용된다.

4단계: 방어 - 암호화 (TLS)

그럼 게임 개발자는 어떻게 막아?

첫 번째 방어: 패킷을 암호화해!

해커가 Wireshark로 봐도 알아볼 수 없게 만드는 거야.

암호화 전 (위험)

게임
→
ATTACK damage=150
→
서버

암호화 후 (안전)

게임
→
a7#kL9$xQ2...
→
서버
어떤 암호화를 써?

1. TLS/SSL - HTTPS처럼 전체 통신을 암호화
2. 자체 암호화 - 게임사가 만든 암호화 알고리즘
3. 패킷별 암호화 - 중요한 패킷만 암호화

// 암호화 적용 예시 void SendAttackPacket(int targetId, int damage) { AttackPacket packet = { ATTACK, targetId, damage }; // 패킷을 암호화! byte[] encrypted = AES_Encrypt(packet, sessionKey); Send(encrypted); // 암호화된 데이터만 네트워크로 나감 }
암호화하면 해커가 못 보는 거야?

네트워크에서는 못 봐.

Wireshark로 봐도 a7#kL9$xQ2... 이런 의미없는 문자만 보여.

하지만... 해커들은 다른 방법을 찾았어.

💡 핵심 개념
암호화를 적용하면 네트워크 상에서 패킷 내용을 볼 수 없다.
TLS, AES 등의 강력한 암호화 알고리즘을 사용한다.

5단계: 공격 - 메모리에서 복호화된 데이터 탈취

암호화된 패킷을 어떻게 뚫어?

해커의 발상: "네트워크에서 못 보면, 암호화되기 전에 보면 되잖아!"

패킷의 생애주기

게임 로직
→
패킷 생성
(평문)
→
암호화
→
네트워크
해커가 노리는 지점 ↑
어떻게 "암호화 전" 데이터를 봐?

방법 1: API 후킹

암호화 함수(AES_Encrypt)를 가로채서, 암호화되기 전 데이터를 빼냄

// 해커의 후킹 코드 byte[] Hooked_AES_Encrypt(byte[] plainData, byte[] key) { LogToFile(plainData); // 평문 데이터 저장! // 원본 함수 호출 return Original_AES_Encrypt(plainData, key); }
다른 방법도 있어?

방법 2: 메모리 스캔

게임 메모리에서 패킷이 만들어지는 버퍼를 찾아서 직접 읽음

방법 3: DLL 인젝션

게임 프로세스에 코드를 주입해서 내부에서 데이터를 빼냄

그럼 암호화해도 소용없는 거야?

클라이언트 쪽 암호화는 결국 뚫릴 수 있어.

왜냐하면, 암호화/복호화를 하려면 키가 클라이언트에 있어야 하니까.

해커가 충분히 파고들면 키도 찾을 수 있어.

🏠 비유: 집 안의 금고

- 암호화 = 금고에 돈을 넣는 것
- 문제 = 금고 열쇠도 같은 집에 있음
- 도둑이 집에 들어오면? = 열쇠도 찾을 수 있음

결론: 집 자체를 지켜야 함 (서버 권위)
💡 핵심 개념
클라이언트 측 암호화는 완벽한 방어가 아니다.
해커는 암호화 전/후의 메모리를 직접 읽어서 우회할 수 있다.

6단계: 최종 방어 - 서버 권위 + 이상치 탐지

그럼 진짜 막을 방법은 뭐야?

최종 답: 클라이언트를 믿지 마!

이걸 서버 권위(Server Authority)라고 해.

// ❌ 나쁜 방식: 클라이언트가 보낸 데미지를 그대로 적용 void HandleAttack_Bad(AttackPacket* packet) { monster->hp -= packet->damage; // 위험! } // ✅ 좋은 방식: 서버가 직접 계산 void HandleAttack_Good(AttackPacket* packet) { Player* player = GetPlayer(packet->senderId); Monster* monster = GetMonster(packet->targetId); // 서버가 직접 데미지 계산! int damage = CalculateDamage(player->attack, monster->defense); monster->hp -= damage; }
서버가 계산하면 해커가 데미지를 조작해도 소용없는 거야?

맞아! 해커가 "데미지 9999"라고 보내도:

// 서버의 반응 클라이언트: "데미지 9999로 공격했어!" 서버: "음... 네 공격력은 50이고, 몬스터 방어력은 10이니까..." 서버: "데미지는 40이야. 9999? 그건 무시할게." ✓
그럼 패킷에 데미지를 왜 넣어?

사실 좋은 설계에서는 안 넣어!

클라이언트는 이것만 보내면 돼:

// 클라이언트가 보내야 할 최소 정보 struct AttackPacket { uint32_t targetId; // 누구를 때렸는지 uint16_t skillId; // 어떤 스킬로 uint64_t timestamp; // 언제 }; // 데미지는 서버가 계산! 클라이언트가 보낼 필요 없음

이상치 탐지 (Anomaly Detection)

서버 권위만으로 충분해?

더 강화하려면 이상치 탐지를 추가해.

"통계적으로 말이 안 되는 행동"을 잡는 거야.

// 이상치 탐지 예시 void HandleAttack(AttackPacket* packet) { Player* player = GetPlayer(packet->senderId); // 1. 공격 속도 체크 if (currentTime - player->lastAttackTime < ATTACK_COOLDOWN) { FlagSuspicious(player, "공격 속도 비정상"); return; } // 2. 거리 체크 float distance = GetDistance(player, monster); if (distance > MAX_ATTACK_RANGE) { FlagSuspicious(player, "공격 거리 비정상"); return; } // 3. 연속 크리티컬 체크 if (player->consecutiveCriticals > 20) { FlagSuspicious(player, "크리티컬 확률 비정상"); } // 모든 검증 통과 시 공격 처리 ProcessAttack(player, monster); }
탐지 항목 정상 범위 해킹 의심
공격 속도 1초당 2회 1초당 100회
이동 속도 초당 5m 초당 500m
획득 골드 시간당 1만 시간당 1억
크리티컬 확률 10% 100%
💡 핵심 개념
서버 권위: 중요한 계산은 서버에서만 처리, 클라이언트는 신뢰하지 않음
이상치 탐지: 통계적으로 불가능한 행동 패턴을 감지하여 차단

📌 핵심 정리: 패킷 해킹의 공방전

  • 패킷 - 게임의 모든 행동은 패킷이라는 데이터로 서버에 전송됨
  • 스니핑 - Wireshark 등으로 패킷을 가로채서 구조 분석
  • 변조 - 패킷 내용을 수정해서 거짓 정보 전송
  • 암호화 - 네트워크 상에서 패킷을 읽을 수 없게 만듦
  • 메모리 탈취 - 암호화 전/후 메모리에서 평문 데이터 추출
  • 서버 권위 - 클라이언트를 신뢰하지 않고 서버가 직접 계산
  • 이상치 탐지 - 통계적으로 불가능한 패턴을 감지하여 차단

실제 온라인 게임에서 패킷을 조작하면:
- 계정 영구 정지
- 정보통신망법 위반 (3년 이하 징역 또는 3천만원 이하 벌금)
- 게임사 손해배상 청구
