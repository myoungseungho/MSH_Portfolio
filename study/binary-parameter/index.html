8000바이트 Binary, 어떻게 효율적으로?

Binary 대용량 파라미터 최적화 - 구조체 직렬화부터 압축까지

Part 1. 왜 Binary 파라미터를 쓸까?

인벤토리를 저장할 때 왜 Binary로 보내?

아이템 100개를 개별 컬럼으로 보내면?

❌ 개별 파라미터로 100개 아이템: EXEC gp_SaveInventory @Item1_ID, @Item1_Count, @Item1_Opt1, @Item1_Opt2... @Item2_ID, @Item2_Count, @Item2_Opt1, @Item2_Opt2... ... @Item100_ID, @Item100_Count... → 파라미터 400개+ → 프로시저 정의 불가능 (2100개 제한이지만 관리 불가) → 코드 유지보수 지옥
아, 그래서 묶어서 보내는구나.

맞아. 구조체를 Binary로 직렬화해서 한 파라미터로.

// C++ 구조체 struct TInventoryItem { int i32ItemID; // 4 bytes int i32Count; // 4 bytes int i32Option[5]; // 20 bytes }; // 총 28 bytes/아이템 // 100개 = 2800 bytes → Binary(3000)으로 전송

Part 2. SQL Server의 Binary 타입

Binary 타입이 뭐가 있어?

크기에 따라 다른 타입을 사용해.

타입 최대 크기 저장 방식 사용처
binary(n) 8,000 bytes 고정 길이 항상 같은 크기
varbinary(n) 8,000 bytes 가변 길이 크기 변동
varbinary(max) 2GB LOB 저장 대용량
우리는 주로 뭘 써?

varbinary(8000)이 가장 많아.

8000바이트면 아이템 280개 정도 담을 수 있어.

Part 3. 8000바이트 제한 대응

8000바이트가 넘으면 어떡해?

세 가지 방법이 있어:

📦 8000바이트 초과 시 대응: 방법 1️⃣ 분할 전송 └─ 8000바이트씩 나눠서 여러 번 호출 └─ 우리 서버가 쓰는 방식 (Chunk 패턴) 방법 2️⃣ varbinary(max) 사용 └─ 최대 2GB까지 가능 └─ 단, LOB 처리로 성능 저하 방법 3️⃣ 압축 └─ 데이터 압축 후 전송 └─ CPU vs 네트워크 트레이드오프
Chunk 패턴이 뭐야?

이전에 봤던 비트 플래그 저장에서 쓴 방식.

인벤토리를 50개씩 나눠서 저장.

// Chunk 분할 저장 void SaveInventory(int CharSID, TItem* items, int count) { const int CHUNK_SIZE = 50; // 50개씩 for (int i = 0; i < count; i += CHUNK_SIZE) { int chunkCount = min(CHUNK_SIZE, count - i); int dataSize = chunkCount * sizeof(TItem); // Binary 파라미터로 전송 CallProcedure("gp_SaveInventory_Chunk", CharSID, i / CHUNK_SIZE, // Chunk 번호 &items[i], // Binary 데이터 dataSize); } }

Part 4. 직렬화 최적화

직렬화할 때 최적화 포인트가 있어?

구조체 패딩(Padding)을 주의해야 해.

// ❌ 비효율적인 구조체 (패딩 발생) struct TItemBad { char byType; // 1 byte // 패딩 3 bytes (정렬 맞추려고) int i32ID; // 4 bytes char byGrade; // 1 byte // 패딩 3 bytes int i32Count; // 4 bytes }; // 실제: 16 bytes (데이터 10, 패딩 6) // ✅ 효율적인 구조체 (정렬 고려) struct TItemGood { int i32ID; // 4 bytes int i32Count; // 4 bytes char byType; // 1 byte char byGrade; // 1 byte char byPad[2]; // 명시적 패딩 2 bytes }; // 실제: 12 bytes (효율적)
패딩이 뭔데?

CPU가 데이터를 빠르게 읽으려고 정렬을 맞추는 빈 공간.

4바이트 단위로 정렬하면 4의 배수 주소에 위치.

📐 패딩 시각화: ❌ TItemBad: | byType(1) | 패딩(3) | i32ID(4) | byGrade(1) | 패딩(3) | i32Count(4) | 0 1 4 8 9 12 16 ✅ TItemGood: | i32ID(4) | i32Count(4) | byType(1) | byGrade(1) | Pad(2) | 0 4 8 9 10 12 💡 100개 아이템: 400바이트 절약!

Part 5. 데이터 압축

압축하면 얼마나 줄어?

게임 데이터는 보통 30~50% 압축률.

📉 압축 효과 예시: 인벤토리 200개 (5600 bytes) ├── 압축 전: 5600 bytes ├── zlib 압축: 2200 bytes (60% 감소) └── LZ4 압축: 3000 bytes (46% 감소, 더 빠름) ⚠️ 압축 비용: ├── 압축: CPU 시간 필요 ├── 해제: DB에서 또는 프로시저에서 └── 트레이드오프: CPU vs 네트워크/저장공간
언제 압축을 써야 해?

데이터가 큰 경우에만. 작으면 오버헤드가 더 커.

데이터 크기 압축 효과 추천
~1KB 오버헤드 > 절약 압축 안 함
1~8KB 상황에 따라 테스트 필요
8KB+ 효과적 압축 추천

Part 6. 프로시저에서 Binary 파싱

프로시저에서 Binary를 어떻게 풀어?

SUBSTRING으로 바이트 단위 추출.

-- Binary에서 데이터 추출 CREATE PROCEDURE gp_ParseInventory @binData varbinary(8000), @i32ItemSize int = 28 -- 아이템당 28바이트 AS BEGIN DECLARE @i int = 1 DECLARE @totalLen int = DATALENGTH(@binData) WHILE @i <= @totalLen BEGIN -- 아이템 ID (offset 0, 4 bytes) DECLARE @ItemID int = CAST(SUBSTRING(@binData, @i, 4) AS int) -- 아이템 개수 (offset 4, 4 bytes) DECLARE @Count int = CAST(SUBSTRING(@binData, @i + 4, 4) AS int) -- INSERT 또는 UPDATE -- ... SET @i = @i + @i32ItemSize END END
WHILE 루프가 느리지 않아?

맞아, 느릴 수 있어. 대안:

🚀 Binary 파싱 최적화: 1️⃣ Numbers 테이블 활용 (Set-based) └─ WHILE 대신 JOIN으로 한번에 파싱 2️⃣ CLR 함수 사용 └─ C#으로 파싱 함수 작성 → SQL에서 호출 3️⃣ 애플리케이션에서 파싱 └─ Binary 저장만 하고, 읽을 때 C++에서 파싱 └─ 우리 서버가 쓰는 방식!

Part 7. 애플리케이션에서 파싱 (우리 방식)

우리 서버는 어떻게 해?

DB는 저장만, 파싱은 C++에서.

-- 프로시저: 그냥 Binary로 저장 CREATE PROCEDURE gp_SaveInventory @i32CharSID int, @i32Chunk int, @binData varbinary(8000) AS BEGIN UPDATE TInventory SET binItemData = @binData WHERE i32CharSID = @i32CharSID AND i32ChunkNo = @i32Chunk END
// C++: Binary → 구조체로 변환 void ParseInventory(BYTE* pData, int dataLen) { int itemCount = dataLen / sizeof(TItem); TItem* pItems = (TItem*)pData; for (int i = 0; i < itemCount; i++) { // 직접 구조체로 접근 int itemID = pItems[i].i32ItemID; int count = pItems[i].i32Count; // ... } }
왜 이렇게 해?

성능이 훨씬 좋아.

C++은 포인터로 바로 구조체 접근 (0ms)

SQL은 SUBSTRING + CAST 반복 (느림)

Part 8. 바이트 순서 (Endianness)

Binary 다룰 때 주의할 게 더 있어?

엔디안(바이트 순서)을 알아야 해.

📐 엔디안이란? 숫자 0x12345678 저장 방식: Little-Endian (Intel x86, 우리 서버): 주소: [0] [1] [2] [3] 값: 78 56 34 12 ← 뒤집혀 저장! Big-Endian (네트워크 순서): 주소: [0] [1] [2] [3] 값: 12 34 56 78 ← 순서대로 저장 💡 Windows + SQL Server = 둘 다 Little-Endian → 같은 환경이면 문제 없음!
그럼 신경 안 써도 돼?

Windows-to-Windows면 OK.

다른 플랫폼(Linux, 모바일)과 통신하면 주의.

실전 가이드: Binary 파라미터 최적화

// 최적화된 Binary 저장 패턴 // 1. 구조체 정렬 최적화 #pragma pack(push, 1) // 패딩 제거 struct TItemCompact { int i32ID; short i16Count; // 65535개면 충분 BYTE byType; BYTE byGrade; }; // 8 bytes (원래 16 → 50% 절약) #pragma pack(pop) // 2. 변경분만 저장 (Dirty Checking) if (IsSlotDirty(slotNo)) { dirtyItems.push_back(items[slotNo]); } // 3. 적절한 Chunk 크기 const int CHUNK_SIZE = 50; // 50 × 8 = 400 bytes/chunk // 8000 / 400 = 20 chunk까지 가능

⚠️ Binary 파라미터 주의사항

1. 8000바이트 초과 시 Chunk 분할 - varbinary(max)는 느림

2. 구조체 패딩 확인 - #pragma pack으로 제어

3. 프로시저에서 WHILE 파싱 피하기 - 애플리케이션에서 처리

4. NULL 데이터 처리 - Binary 전체가 NULL이면 프로시저 오류 가능

📝 핵심 정리

  • Binary = 구조체 배열을 한 파라미터로 전송
  • varbinary(8000) = 가장 효율적 (LOB 아님)
  • 8000바이트 초과 시 Chunk로 분할
  • 구조체 패딩 최적화로 공간 절약
  • 파싱은 C++에서 (포인터 캐스팅으로 빠르게)
