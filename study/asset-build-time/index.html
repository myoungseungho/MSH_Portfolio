빌드 시간 단축 전략

인크리멘털 빌드, 분산 빌드, 캐싱으로 개발 효율 극대화

Part 1. 개념 이해 - 빌드 시간이 왜 중요한가?

빌드 시간이 긴 게 왜 문제야?

빌드 시간은 개발자의 반복 속도(Iteration Speed)를 결정합니다. "코드 수정 → 빌드 → 테스트" 사이클이 길면 생산성이 급락합니다.

│                                                                      │

│   ─────────────────────────────                                      │
│                                                                      │
│   [10초 미만] - 이상적                                               │
│   ┌────────────────────────────────────────────────────────┐        │
│   │ 코드 수정 → 빌드 → 테스트 → 수정 → 빌드 → ...          │        │
│   │ "플로우 상태 유지"                                       │        │
│   │ 집중력 100%                                              │        │
│   └────────────────────────────────────────────────────────┘        │
│                                                                      │
│   [1~5분] - 문제 발생                                                │
│   ┌────────────────────────────────────────────────────────┐        │
│   │ 코드 수정 → 빌드... → 웹서핑 → 빌드 완료 → 테스트      │        │

│   │ 집중력 70%                                               │        │
│   └────────────────────────────────────────────────────────┘        │
│                                                                      │
│   [10분 이상] - 심각                                                 │
│   ┌────────────────────────────────────────────────────────┐        │
│   │ 코드 수정 → 빌드... → 커피 → SNS → 빌드 완료?          │        │
│   │ "작업 내용 잊어버림"                                     │        │
│   │ 집중력 30%, 한 번에 큰 변경 → 버그 증가                  │        │

Part 2. 인크리멘털 빌드 - 변경된 것만 다시 빌드

인크리멘털 빌드가 뭐야?

인크리멘털 빌드는 변경된 파일만 다시 처리하는 방식입니다. 핵심은 의존성 추적과 변경 감지입니다.

┌─────────────────────────────────────────────────────────────────────┐
│                    인크리멘털 빌드 원리                               │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   풀 빌드 (Full Build):                                              │
│   ─────────────────────                                              │
│   ┌────────────────────────────────────────────────────────┐        │
│   │  모든 에셋 처리                                         │        │
│   │  A.png → A.dds ✓                                        │        │
│   │  B.png → B.dds ✓                                        │        │
│   │  C.png → C.dds ✓  (1000개...)                           │        │
│   │                                                         │        │
│   │  시간: 2시간                                            │        │
│   └────────────────────────────────────────────────────────┘        │
│                                                                      │
│   인크리멘털 빌드 (Incremental Build):                               │
│   ─────────────────────────────────                                  │
│   ┌────────────────────────────────────────────────────────┐        │
│   │  변경 감지                                              │        │
│   │  A.png: 해시 변경? NO  → 스킵                          │        │
│   │  B.png: 해시 변경? YES → 재처리 ✓                       │        │
│   │  C.png: 해시 변경? NO  → 스킵                          │        │
│   │                                                         │        │
│   │  시간: 30초 (B.png만)                                   │        │
│   └────────────────────────────────────────────────────────┘        │
│                                                                      │
│   변경 감지 방법:                                                    │
│   ──────────────                                                     │
│   1. 타임스탬프 (빠름, 부정확)                                       │
│      • 파일 수정 시간 비교                                           │
│      • 문제: 동기화 이슈, 복사 시 변경                               │
│                                                                      │
│   2. 해시 (느림, 정확)                                               │
│      • 파일 내용의 MD5/SHA256 해시                                   │
│      • 문제: 대용량 파일에서 느림                                    │
│                                                                      │
│   3. 혼합 방식 (실용적)                                              │
│      • 먼저 타임스탬프 체크                                          │
│      • 변경됐으면 해시로 확인                                        │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
의존성이 왜 중요해?

의존성 그래프가 정확해야 진짜 인크리멘털 빌드가 가능합니다. 의존성을 놓치면 빌드 결과물이 오래된 상태가 됩니다!

┌─────────────────────────────────────────────────────────────────────┐
│                    의존성 그래프 예시                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   Material이 Texture를 참조하는 경우:                                │
│   ───────────────────────────────────                                │
│                                                                      │
│   ┌─────────────┐      참조      ┌─────────────┐                    │
│   │ Material.mat│ ─────────────→ │ Texture.png │                    │
│   └─────────────┘                └─────────────┘                    │
│          │                              │                            │
│          ▼                              ▼                            │
│   ┌─────────────┐                ┌─────────────┐                    │
│   │ Material.dat│                │ Texture.dds │                    │
│   │ (빌드 결과) │                │ (빌드 결과) │                    │
│   └─────────────┘                └─────────────┘                    │
│                                                                      │
│   Texture.png 변경 시:                                               │
│   ─────────────────────                                              │
│   1. Texture.dds 재생성 ✓                                            │
│   2. Material.dat도 재생성 필요! (의존성)                            │
│                                                                      │
│   의존성 무시하면:                                                   │
│   ─────────────────                                                  │
│   Material.dat이 옛날 Texture.dds를 참조                             │
│   → 런타임에 깨진 렌더링 또는 크래시                                 │
│                                                                      │
│   복잡한 의존성 체인:                                                │
│   ──────────────────                                                 │
│                                                                      │
│   Shader.shader                                                      │
│        │                                                             │
│        ▼                                                             │
│   ┌─────────────────────────────────────────┐                       │
│   │         Material.mat                      │                       │
│   └─────────────────────────────────────────┘                       │
│        │                    │                                        │
│        ▼                    ▼                                        │
│   Texture_A.png        Texture_B.png                                 │
│        │                    │                                        │
│        └──────────┬─────────┘                                        │
│                   ▼                                                  │
│              Prefab.prefab                                           │
│                   │                                                  │
│                   ▼                                                  │
│              Scene.unity                                             │
│                                                                      │
│   Shader 변경 → 전체 체인 재빌드!                                    │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
// 의존성 추적 시스템 구현 예시 public class DependencyTracker { // 의존성 그래프: A가 B를 참조하면 dependsOn[A] = [B, ...] private Dictionary<string, HashSet<string>> m_DependsOn; // 역방향: B가 변경되면 재빌드할 에셋 목록 private Dictionary<string, HashSet<string>> m_DependedBy; public HashSet<string> GetAssetsToRebuild(string changedAsset) { HashSet<string> toRebuild = new HashSet<string>(); Queue<string> queue = new Queue<string>(); queue.Enqueue(changedAsset); while (queue.Count > 0) { string current = queue.Dequeue(); if (!toRebuild.Add(current)) continue; // 이 에셋에 의존하는 모든 에셋도 재빌드 if (m_DependedBy.TryGetValue(current, out var dependents)) { foreach (var dep in dependents) { queue.Enqueue(dep); } } } return toRebuild; } }

Part 3. 캐싱 전략 - 한 번 빌드한 건 다시 안 한다

빌드 캐시가 뭐야?

빌드 캐시는 이미 처리된 에셋의 결과물을 저장해두는 것입니다. 같은 입력이면 캐시에서 즉시 반환!

캐시 키는 어떻게 만들어?

캐시 키는 빌드 결과물을 식별하는 고유 ID입니다. 모든 입력 요소가 같아야 같은 키!

// 캐시 키 생성 예시 public class BuildCacheKey { public static string ComputeKey(AssetBuildContext context) { using (var sha256 = SHA256.Create()) { var builder = new StringBuilder(); // 1. 원본 에셋 내용 해시 builder.Append(ComputeFileHash(context.SourcePath)); // 2. 빌드 설정 (중요!) builder.Append(context.TargetPlatform); // Windows, Android, iOS... builder.Append(context.CompressionFormat); // BC7, ASTC, ETC2... builder.Append(context.QualityLevel); // High, Medium, Low // 3. 빌드 도구 버전 (버전 바뀌면 결과 달라짐) builder.Append(context.ToolVersion); // TextureCompressor v2.1 // 4. 의존성 해시 foreach (var dep in context.Dependencies) { builder.Append(ComputeFileHash(dep)); } // 최종 해시 계산 byte[] hash = sha256.ComputeHash( Encoding.UTF8.GetBytes(builder.ToString())); return BitConverter.ToString(hash).Replace("-", ""); } } } // 캐시 조회 및 저장 public class BuildCache { private ICache m_LocalCache; // 디스크 private ICache m_SharedCache; // 네트워크 public bool TryGet(string key, out byte[] data) { // Level 1: 로컬 캐시 if (m_LocalCache.TryGet(key, out data)) { Debug.Log($"[Cache Hit] Local: {key}"); return true; } // Level 2: 공유 캐시 if (m_SharedCache.TryGet(key, out data)) { Debug.Log($"[Cache Hit] Shared: {key}"); m_LocalCache.Put(key, data); // 로컬에도 저장 return true; } Debug.Log($"[Cache Miss] {key}"); return false; } }
⚠️ 캐시 키 주의사항:
  • 빌드 도구 버전을 포함해야 함 - 같은 소스도 컴파일러 버전 따라 결과 다름
  • 빌드 설정을 전부 포함 - Debug/Release, 플랫폼별 설정
  • 암묵적 의존성 주의 - 글로벌 설정, 환경변수 등

Part 4. 분산 빌드 - 여러 머신이 함께 빌드

분산 빌드가 뭐야?

분산 빌드는 빌드 작업을 여러 컴퓨터에 나눠서 병렬 처리하는 것입니다. N대 머신 = 빌드 시간 1/N (이론적으로)

┌─────────────────────────────────────────────────────────────────────┐

│                                                                      │
│   개발자 PC (Coordinator)                                            │
│   ┌───────────────────────────────────────────────┐                 │
│   │  빌드 시작                                     │                 │
│   │  ↓                                            │                 │
│   │  작업 분할 (Task Distribution)                 │                 │
│   │  ┌─────────┐ ┌─────────┐ ┌─────────┐         │                 │
│   │  │ Task 1  │ │ Task 2  │ │ Task 3  │ ...     │                 │
│   │  │Tex 1-100│ │Tex 101- │ │Shader X │         │                 │
│   │  └────┬────┘ └────┬────┘ └────┬────┘         │                 │
│   └───────│───────────│───────────│───────────────┘                 │
│           │           │           │                                  │
│           ▼           ▼           ▼                                  │
│   ┌───────────┐ ┌───────────┐ ┌───────────┐                        │
│   │ Worker 1  │ │ Worker 2  │ │ Worker 3  │  ...                   │
│   │ (빌드팜)  │ │ (빌드팜)  │ │ (빌드팜)  │                        │
│   │           │ │           │ │           │                        │
│   │ 텍스처    │ │ 텍스처    │ │ 쉐이더    │                        │
│   │ 압축 처리 │ │ 압축 처리 │ │ 컴파일    │                        │
│   └─────┬─────┘ └─────┬─────┘ └─────┬─────┘                        │
│         │             │             │                                │

│   ┌───────────────────────────────────────────────┐                 │

│                                                                      │

분산 빌드의 병목은?

실제로는 네트워크 전송, 직렬화 작업, 의존성 때문에 완벽한 병렬화가 안 됩니다.

면접에서 예상되는 질문은?
🎯 예상 질문과 모범 답변:

Q1: 인크리멘털 빌드가 뭐고, 어떻게 구현되나요?

A: "인크리멘털 빌드는 변경된 파일만 다시 처리하는 방식입니다. 의존성 그래프를 구축하고, 각 파일의 해시를 저장해서 변경 여부를 감지합니다. 파일이 변경되면 그 파일에 의존하는 모든 파일도 재빌드됩니다."

Q2: 분산 빌드의 한계는 뭔가요?

A: "Amdahl의 법칙에 따라, 직렬화 작업 비율만큼 가속에 한계가 있습니다. 20%가 직렬 작업이면 아무리 Worker를 늘려도 5배 이상 빨라지지 않습니다. 또한 네트워크 전송 오버헤드와 작업 분배 오버헤드도 고려해야 합니다."

Q3: 캐시 키를 설계할 때 주의점은?

A: "모든 입력 요소를 포함해야 합니다. 원본 파일 해시뿐 아니라 빌드 설정(플랫폼, 품질), 도구 버전, 의존성까지 포함해야 정확한 캐시 히트가 발생합니다. 하나라도 빠지면 잘못된 캐시를 반환할 수 있습니다."

Q4: Unity Assembly Definition의 장점은?

A: "Assembly Definition으로 코드를 분리하면, 변경된 어셈블리만 재컴파일됩니다. 기본적으로 모든 스크립트가 Assembly-CSharp.dll에 들어가는데, 이러면 파일 하나 수정해도 전체 재컴파일됩니다. 분리하면 UI 코드 수정 시 UI.dll만 재컴파일되어 훨씬 빠릅니다."

핵심 정리

  • 인크리멘털 빌드: 변경된 것만 재빌드 (의존성 추적 + 해시 비교)
  • 빌드 캐시: 로컬 → 공유 → 클라우드 계층 구조
