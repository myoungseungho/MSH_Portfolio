서버는 무조건 C++? GC 도는 C#은 정말 느릴까

C++ vs C# — 언어의 근본 차이부터, GC 공포의 진원지, '어떤 세팅을 켜면 빨라지나'까지

Part 1. C#이랑 C++, 한 줄로 뭐가 그렇게 달라?

둘 다 코드 짜서 컴파일하는 언어잖아. 뭐가 그렇게 근본적으로 다른데?

맞춰봐. 똑같이 '컴파일'이라고 부르는데, C++ 컴파일 결과물이랑 C# 컴파일 결과물은 알맹이가 완전히 달라. 뭐가 다를까?

C++은 소스코드를 곧장 기계어(네이티브 코드)로 구워서 끝이야. 나온 exe는 CPU가 바로 먹을 수 있는 완제품이지.

C#은 한 단계 덜 가. 소스코드를 IL(중간 언어)이라는 반제품으로만 굽고, 진짜 기계어 번역은 실행하는 순간 JIT(Just-In-Time) 컴파일러가 그때그때 해. 비유하면 C++은 '완제품 출고', C#은 '주문 들어오면 즉석 조리'야.

🛠 C++ (네이티브 컴파일) 소스(.cpp) ─▶ [컴파일러] ─▶ 기계어 exe ─▶ CPU 바로 실행 완제품. 출고 끝. 🛠 C# (관리형 + JIT) 소스(.cs) ─▶ [컴파일러] ─▶ IL(중간언어) ─▶ [실행 시 JIT] ─▶ 기계어 ─▶ CPU 반제품 즉석 조리 📦 메모리도 갈라져 C++ : new 한 건 네가 delete 해야 함 (수동, 통제권 = 너) C# : new 만 하면 GC가 알아서 회수 (자동, 통제권 = 런타임)
즉석 조리면 실행할 때마다 번역하느라 느린 거 아냐?

처음 한 번만. JIT가 함수를 한 번 기계어로 번역해두면 그 다음 호출부턴 캐시된 네이티브 코드를 그대로 재사용해. 그래서 '두 번째부터'는 C++이랑 같은 네이티브 속도야.

게다가 JIT는 실행 중에 '이 함수 엄청 자주 도네?' 하고 관찰해서 더 공격적으로 다시 최적화해(tiered compilation). C++ 컴파일러는 빌드 시점에 딱 한 번 추측으로 최적화하지만, JIT는 '실제로 어떻게 도는지' 보고 최적화한다는 게 오히려 강점일 때도 있어.

그럼 켜자마자 첫 호출이 버벅이는 건 손해 아냐?

맞아, 그게 JIT의 진짜 비용이야 — 워밍업 스톨(warm-up stall). 서버 막 켰을 때 핫패스가 아직 네이티브로 안 구워져서 첫 몇 초가 굼떠.

그래서 탈출구가 있어. NativeAOT / ReadyToRun으로 빌드 시점에 미리 기계어로 구워버리면 워밍업이 사라져 — C++처럼 '완제품 출고'가 되는 거지. 대신 잃는 게 있어: 실행 중 관찰 기반 재최적화(tiered)를 포기하고, 빌드 산출물도 커져. 공짜 점심은 없어.

메모리까지 C#이 알아서 해주면 더 좋은 거 아냐? 왜 굳이 C++을 써?

바로 그 '알아서'가 양날의 검이거든. C#은 GC가 안 쓰는 메모리를 알아서 회수해줘서 널 크래시·메모리 누수 사고가 확 줄어. C++ 서버 개발자가 밤새 디버깅하는 그 access violation이 구조적으로 잘 안 나.

근데 대가가 있어. GC가 '언제' 도는지를 네가 통제 못 해. 한가할 때 돌면 좋은데, 하필 공성전 피크에 끼어들면? 그 타이밍 통제권을 잃는 게 게임서버에선 치명적이라고들 믿었어. 왜 그렇게 믿게 됐는지가 다음 이야기야.

Part 2. 왜 다들 "서버는 무조건 C++"이라고 할까?

GC 돌면 게임이 멈춘다던데. 그거 때문에 C# 못 쓰는 거 아냐?

그 말 자체는 틀린 게 아니야 — 단, 옛날엔. 여기에 함정이 있어. 사람들은 '락 잘 걸면 멀티스레드 된다'처럼, 'GC=무조건 랙'을 사실로 굳혀버렸거든.

옛날 .NET Framework 시절엔 오래 산 객체를 청소하는 gen2 풀 수거가 돌면 전체 스레드를 멈추는 stop-the-world가 수십~수백 ms씩 걸렸어. 60fps 게임은 한 프레임 예산이 16.6ms인데, GC가 100ms 멈추면 6프레임이 통째로 증발해. 눈에 보이는 랙이지.

⏱ 60fps = 한 프레임에 16.6ms 안에 다 끝내야 함 정상 프레임: [■■■ 로직 8ms ] 여유 GC 끼어듦 : [■■■ 로직 8ms ][🟥🟥🟥🟥🟥 GC 정지 100ms 🟥🟥🟥🟥🟥] └─ 6프레임 증발 = 눈에 띄는 랙 → 한 세대 서버 개발자 머릿속에 'GC = 랙'이 각인됨
그럼 그 공포는 정당한 거잖아. 뭐가 문제야?

문제는 그 공포가 굳은 시점이야. 'GC=랙'이 상식으로 자리잡은 게 2000년대 초중반 .NET이거든. 근데 그때 .NET이랑 지금 .NET 8/9는 사실상 다른 물건이야. 자동차로 치면 '디젤은 시끄럽고 느려'를 1990년대 경험으로 박아두고 2020년대 디젤을 안 타보는 거랑 비슷해.

네가 '느린 C#'으로 기억하는 그 모습은, 그동안 런타임이 통째로 갈아엎어지면서 대부분 사라졌어. 진짜로 그런지 GC가 실제로 어떻게 도는지 뜯어보자.

메모리 해제 시점 네가 정확히 앎 (delete 그 줄) 런타임이 결정 (통제 약함)
널 크래시 / 누수 실수하면 바로 사고 구조적으로 잘 안 남
최악 지연(p99.99) 네가 짠 만큼 결정적 GC 끼어들 여지 (작아졌지만 0은 아님)
개발 속도 / 안전성 느리고 위험 빠르고 안전

Part 3. GC가 도는데 어떻게 안 끊겨? (현대 GC의 정체)

GC는 청소할 때 메모리 전체를 다 뒤지는 거 아냐? 그러니 느리지.

그게 가장 흔한 오해야. 현대 GC는 전체를 안 뒤져. 세대 가설(generational hypothesis)에 기대거든 — '대부분의 객체는 태어나자마자 금방 죽는다'. 전투 한 틱에서 만든 임시 객체들 생각해봐. 그 틱 끝나면 다 쓰레기잖아.

그래서 메모리를 나이로 나눠. 갓 만든 건 gen0, 살아남으면 gen1, 오래 버틴 놈만 gen2. gen0만 자주, 아주 빠르게 청소하고(보통 sub-ms), 무거운 gen2 전체 청소는 어쩌다 한 번만 해.

🗂 세대별 GC — 전체를 안 뒤지는 이유 gen0 (신생아) ──▶ 자주 청소 · 매우 빠름(sub-ms) · 대부분 여기서 죽음 │ 살아남으면 승급 gen1 (중간) ──▶ 가끔 청소 │ 또 살아남으면 gen2 (장수) ──▶ 어쩌다 청소 · 무거움 ← 옛날 'stop-the-world'의 주범 핵심: 매번 gen2까지 가지 않는다. 99%는 gen0에서 끝.
그래도 그 무거운 gen2 청소 돌면 결국 멈추는 거잖아?

거기에 두 가지 세팅이 들어와. 이게 바로 '어떤 세팅을 켜면 빨라진다'의 정체야.

① Server GC: 힙을 CPU 코어별로 쪼개서 여러 스레드가 동시에 병렬로 청소해. 16코어면 청소도 16갈래로 나눠 빨라져.

② Background GC: 무거운 gen2 청소를 게임이 도는 와중에 백그라운드로 동시에 진행해. 진짜로 전체를 멈추는 구간은 수 ms 단위로 짧아져. 옛날 수십~수백 ms가 → 현대엔 sub-ms~수 ms로 줄어든 핵심 이유야.

수 ms라도 0은 아니잖아. 아예 안 멈추게는 못 해?

할 수 있어. zero-allocation. 발상을 뒤집는 거야 — 청소를 빠르게 하는 게 아니라, 애초에 쓰레기를 안 만들면 청소할 게 없잖아.

핫패스(매 틱 도는 코드)에서 객체를 새로 안 만들어. Span<T>로 수신 버퍼를 복사 없이 그대로 썰어 쓰고, stackalloc으로 힙 대신 스택에 잡고, 객체는 풀(pool)에 미리 만들어두고 빌려 쓰고 반납해. gen2로 갈 garbage 자체가 안 생기니 GC가 올 일이 없어.

풀에 반납을 깜빡하면? 그거 결국 누수 아냐? C++이랑 뭐가 달라지는 건데.

날카로운 질문이야. 맞아, C#도 풀 반납을 깜빡하면 풀이 비대해지는 '풀 누수'가 생겨. 근데 C++ 누수랑 결정적으로 달라 — C++ 누수는 그 메모리가 영영 안 돌아와서 메모리 오염·크래시로 가지만, C#은 풀 참조를 놓치면 결국 GC가 회수해. 그러니까 '크래시'가 아니라 '성능 저하'로 끝나. 안전망이 한 겹 더 있는 거지.

대신 잃는 게 분명해. zero-allocation으로 짠 C# 코드는 편하게 짜는 C#이 아니야. Span 수명, 풀 반납, ref struct 제약을 신경 쓰는 순간 코드 난이도는 C++에 근접해. '편함'을 일부 반납하고 '속도'를 얻는 거야.

Part 4. 직접 켜보자 — 어떤 세팅을 켜면 얼마나 빨라져?

말로는 알겠는데, 세팅 하나 켤 때마다 실제로 얼마나 줄어드는지 감이 안 와.

그래서 만들었어. 아래는 한 전투 틱의 최악 프레임 시간을 보여주는 시뮬레이터야. 기본 로직(파란 칸)은 고정이고, 빨간 칸 = GC 일시정지야.

체크박스를 하나씩 켜면서 빨간 칸이 어떻게 줄어드는지 봐. 주황 선(60fps·16.6ms)과 빨간 선(30fps·33ms) 안으로 들어오면 안 끊기는 거야. 회색 막대는 비교용 C++(GC 없음)이고. 수치는 구조를 보여주는 예시값이야.

⚙ GC 세팅 빌드업 — 최악 프레임 시간 시뮬레이터
전투 한 틱 기준 · 빨간 칸이 GC 일시정지 · 예시값
C# — 현재 켠 세팅 기준 최악 프레임
C++ (수동 관리 · GC 없음) — 비교 기준
게임 로직 GC 일시정지 GC 거의 0 C++ 기준
켜보니까 ③ zero-allocation 하나만 켜도 ①②가 의미 없어지던데?

정확히 봤어. 그게 핵심 통찰이야. GC를 빠르게 만드는 것(①②)보다, GC가 올 일을 없애는 것(③)이 근본 해법이거든. 쓰레기를 안 만들면 청소 알고리즘이 아무리 느려도 상관없잖아.

그래서 실전 고성능 C# 서버는 ③을 핫패스에 깔고, ①②는 혹시 모를 잔여 할당의 안전망으로 같이 켜. ④ AOT는 시작 직후 워밍업과 잔여 지터를 깎는 마무리고. 단, ③의 대가는 Part 3에서 말한 그거 — 코드가 C++만큼 까다로워진다는 것.

Part 5. 그래도 C++이 이기는 곳은 분명히 있어

그럼 이제 C#이 다 이기는 거야? C++ 버려도 돼?

아니. 그렇게 결론 내면 이 글도 한쪽으로 치우친 거야. C++이 정당하게 이기는 구간이 분명히 있어.

① CPU-bound 핫루프: 매 틱 수백 명의 시야 판정·충돌을 도는 전투 서버. 여기선 zero-alloc을 해도 C#이 C++보다 느린 게 측정돼(짝 문서 전투 시나리오에서 53% 차이). ② p99.99 결정론적 지연: GC가 sub-ms라도 '절대 0'은 보장 못 해. 금융·초저지연처럼 꼬리 지연 한 방이 치명적인 곳은 C++. ③ 메모리 footprint가 빡센 임베디드·콘솔. ④ 이미 20년치 쌓인 IOCP C++ 자산 — 멀쩡한 걸 재작성하는 비용이 이득보다 큼.

그럼 zero-allocation C#이 결국 제일 낫네? C++ 안전성에 C++급 속도잖아.

여기에 가장 정직한 트레이드오프가 있어. zero-alloc C#은 양쪽 비용을 다 짊어질 수도 있어. C++만큼 메모리를 신경 써서 짜야 하는 '까다로움'은 그대로 가져오면서, GC 런타임·JIT라는 '관리형 부담'도 여전히 지거든.

그러니 'C#으로 zero-alloc 할 거면 차라리 그 부분은 C++ 아냐?'라는 반문이 정당해. 답은 상황별이야 — 서버의 99%가 평범한 로직이고 1%만 핫패스면, 99%를 편하고 안전한 C#으로 짜고 1%만 조이는 게 이득. 반대로 코드 절반이 핫패스인 전투 서버면 C++이 맞아.

채팅 / 브로드캐스트 네트워크 (I/O-bound) C# (async/await가 콜백 지옥 제거)

Part 6. 그래서 우리는 뭘 골라야 해?

결국 정답이 뭐야? 한 줄로 정리해줘.

'서버는 무조건 C++'은 2000년대 .NET 기준으로 굳은 믿음이고, 지금은 '대부분의 서버에선 더 이상 성능 문제가 아니다'가 정답에 가까워.

판단 기준은 언어가 아니라 병목이야. 네 서버가 DB·네트워크에서 8ms씩 기다리는 I/O-bound면, 거기서 언어 바꾸는 건 고속도로 정체 중에 차를 페라리로 바꾸는 격이야 — 0.1%도 안 빨라져. 반대로 매 틱 CPU를 갈아넣는 CPU-bound 핫루프면 그제서야 언어 차이가 실존해.

우리처럼 이미 C++ IOCP 서버가 돌고 있으면?

그대로 두는 게 거의 항상 맞아. 멀쩡히 도는 검증된 서버를 언어 때문에 재작성하는 건 가장 비싼 결정이야. C#이 빨라졌다는 게 'C++을 버려라'가 아니라, '신규 서비스나 새 서버를 짤 때 C#을 선택지에서 빼지 마라'는 뜻으로 받아들이는 게 맞아.

네가 가졌던 '서버는 무조건 C++'이라는 고정관념은, 틀렸다기보다 '유효기간이 지난 참'이었던 거지. 이제 'GC 때문에 안 돼' 대신 '병목이 어디냐'로 질문이 바뀌면 충분해.

핵심 정리

  • C++ = 소스를 네이티브로 굽고 끝(완제품) + 수동 메모리 / C# = IL로 굽고 실행 시 JIT 번역(즉석 조리) + GC 자동 메모리
  • 'GC=랙'은 stop-the-world가 수십~수백 ms였던 2000년대 .NET 기준 — 그때 굳은 믿음이 지금까지 따라온 것
  • 현대 GC는 세대별(gen0만 자주·빠르게) + Server GC(코어별 병렬) + Background GC(동시 청소)로 정지를 sub-ms~수 ms로 줄임
  • 근본 해법은 zero-allocation — Span/stackalloc/풀링으로 쓰레기를 안 만들면 GC가 올 일이 없음. 대신 코드가 C++만큼 까다로워짐
  • C++이 여전히 이기는 곳: CPU-bound 핫루프, p99.99 결정론적 지연, 빡센 footprint, 기존 IOCP 자산
  • 판단 기준은 언어가 아니라 병목 — I/O-bound면 언어 무관, CPU-bound 핫루프에서만 언어 차이가 실존

⚠ 이 문서의 정직한 한계

시뮬레이터 수치(로직 6ms, GC 45ms→sub-ms 등)는 '구조와 방향'을 보여주는 예시값 — 실제 값은 서버 워크로드·하드웨어·할당 패턴에 따라 크게 달라짐

'C#도 충분히 빠르다'는 평균·처리량 기준 — 최악 꼬리 지연(p99.99) 절대 보장이 필요한 영역은 여전히 C++ 우위

전투 시나리오 53% 차이는 짝 문서(csharp-game-server)의 예시 기준값이며, 실측이 아니라 트레이드오프를 드러내기 위한 수치
