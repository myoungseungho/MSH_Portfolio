Part 1. 전체 다운로드의 문제

게임 패치할 때마다 전체를 받으면?

실제 라이브 게임의 상황을 보겠습니다:

라이브 서비스 게임 패치 현실: ┌────────────────────────────────────────────────────────────┐ │ │ │ 게임 전체 용량: 80GB │ │ 이번 패치 변경: 버그 수정 + NPC 대사 수정 (실제 100KB) │ │ │ │ 전체 다운로드 방식: │ │ ┌────────────────────────────────────────────────────┐ │ │ │ 다운로드: 80GB │ │ │ │ 100Mbps 기준: 1시간 47분 │ │ │ │ CDN 비용: $0.08/GB × 80GB × 100만 유저 = $6,400,000 │ │ │ └────────────────────────────────────────────────────┘ │ │ │ │ 델타 패치 방식: │ │ ┌────────────────────────────────────────────────────┐ │ │ │ 다운로드: 15MB (실제 변경분 + 오버헤드) │ │ │ │ 100Mbps 기준: 1.2초 │ │ │ │ CDN 비용: $0.08/GB × 0.015GB × 100만 = $1,200 │ │ │ └────────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘ 델타 패치로 5333배 비용 절감!

Part 2. 델타 패치의 원리

바뀐 부분만 어떻게 알아내?

바이너리 diff 알고리즘으로 두 파일의 차이점만 추출합니다:

델타 패치 생성 과정: ┌──────────────────────────────────────────────────────────┐ │ │ │ Old Version (v1.0) New Version (v1.1) │ │ ┌────────────────┐ ┌────────────────┐ │ │ │ AAAA BBBB CCCC │ │ AAAA XXXX CCCC │ │ │ │ DDDD EEEE FFFF │ │ DDDD EEEE YYYY │ │ │ │ GGGG HHHH IIII │ │ GGGG HHHH IIII │ │ │ └────────────────┘ └────────────────┘ │ │ │ │ │ │ └──────────┬───────────────────┘ │ │ ▼ │ │ Binary Diff 알고리즘 │ │ │ │ │ ▼ │ │ ┌─────────────────┐ │ │ │ Delta Patch │ │ │ │ ─────────────── │ │ │ │ @offset 5: XXXX │ ← 오프셋 5에서 XXXX로 교체 │ │ │ @offset 17: YYYY│ ← 오프셋 17에서 YYYY로 교체│ │ └─────────────────┘ │ │ │ │ 원본: 48 bytes → 델타: 12 bytes (75% 절약) │ │ │ └──────────────────────────────────────────────────────────┘
어떤 diff 알고리즘을 써?

게임 업계에서 주로 사용하는 알고리즘들:

바이너리 델타 알고리즘 비교: ┌────────────────┬────────────┬────────────┬─────────────────┐ │ 알고리즘 │ 압축률 │ 속도 │ 사용처 │ ├────────────────┼────────────┼────────────┼─────────────────┤ │ bsdiff │ ★★★★★ │ ★★☆☆☆ │ Chrome, FreeBSD │ │ xdelta3 │ ★★★★☆ │ ★★★★☆ │ 게임 패처 │ │ zstd --patch │ ★★★★☆ │ ★★★★★ │ Facebook, 최신 │ │ courgette │ ★★★★★ │ ★★☆☆☆ │ Chrome (실행파일)│ │ HDiffPatch │ ★★★★☆ │ ★★★★★ │ 모바일 게임 │ └────────────────┴────────────┴────────────┴─────────────────┘ 권장: xdelta3 또는 zstd (속도와 압축률 균형)
// xdelta3 사용 예시 // 델타 패치 생성 (서버에서) // xdelta3 -e -s old_file new_file delta.patch int CreateDeltaPatch(const char* oldFile, const char* newFile, const char* patchFile) { xd3_stream stream; xd3_config config; xd3_init_config(&config, 0); config.winsize = 1 << 23; // 8MB 윈도우 xd3_config_stream(&stream, &config); // ... 델타 생성 로직 return xd3_encode_input(&stream); } // 델타 패치 적용 (클라이언트에서) // xdelta3 -d -s old_file delta.patch new_file int ApplyDeltaPatch(const char* oldFile, const char* patchFile, const char* newFile) { // 1. old_file 읽기 // 2. patch 명령어 적용 // 3. new_file 쓰기 return xd3_decode_input(&stream); }

Part 3. 델타 체인 문제

v1.0에서 v1.5로 패치하려면?

단순히 모든 델타를 순차 적용하면 문제가 생깁니다:

델타 체인 문제: 나이브 방식 (문제 있음): ┌──────────────────────────────────────────────────────────┐ │ │ │ v1.0 ─[delta1]─▶ v1.1 ─[delta2]─▶ v1.2 ─[delta3]─▶ ... │ │ │ │ v1.0 → v1.5 업데이트 시: │ │ 1. delta1 다운로드 + 적용 │ │ 2. delta2 다운로드 + 적용 │ │ 3. delta3 다운로드 + 적용 │ │ 4. delta4 다운로드 + 적용 │ │ 5. delta5 다운로드 + 적용 │ │ │ │ 문제: 5번 적용 = 5배 디스크 I/O + 중간 버전 임시 저장 │ │ │ └──────────────────────────────────────────────────────────┘ 해결책: Skip Delta ┌──────────────────────────────────────────────────────────┐ │ │ │ v1.0 ────────[skip delta]────────▶ v1.5 │ │ │ ▲ │ │ ├─[d1]─▶ v1.1 ─[d2]─▶ v1.2 │ │ │ │ │ │ │ │ │ └─[skip]────────┤ │ │ │ │ │ │ └─────────[skip delta]─────────────┘ │ │ │ │ 인기 버전 간 직행 델타 미리 생성 │ │ │ └──────────────────────────────────────────────────────────┘
어떤 Skip Delta를 만들어야 해?
// Skip Delta 생성 전략 class DeltaBuilder { void GenerateSkipDeltas() { // 전략 1: 고정 간격 // v1.0→v1.5, v1.5→v2.0, v2.0→v2.5 ... for (int i = 0; i < versions.size(); i += 5) { CreateDelta(versions[i], versions[i + 5]); } // 전략 2: 사용자 분포 기반 (추천) // 가장 많은 유저가 있는 버전에서 최신까지 auto popularVersions = Analytics::GetTopVersions(10); for (auto& ver : popularVersions) { CreateDelta(ver, latestVersion); } // 전략 3: 항상 latest-1 → latest // 대부분의 유저는 한 버전만 뒤처짐 CreateDelta(latestVersion - 1, latestVersion); } // 델타 용량이 전체의 70% 넘으면 전체 다운로드가 나음 bool ShouldUseDelta(size_t deltaSize, size_t fullSize) { return deltaSize < fullSize * 0.7; } };

Part 4. 청크 기반 델타

80GB 파일을 통째로 diff하면?

메모리 부족과 패치 실패 시 롤백 불가 문제가 생깁니다:

청크 기반 델타 시스템: ┌──────────────────────────────────────────────────────────┐ │ │ │ 전체 파일을 청크로 분할: │ │ │ │ game.pak (80GB) │ │ ├── chunk_00.pak (100MB) ─ hash: a1b2c3 │ │ ├── chunk_01.pak (100MB) ─ hash: d4e5f6 │ │ ├── chunk_02.pak (100MB) ─ hash: g7h8i9 ← 변경됨 │ │ ├── chunk_03.pak (100MB) ─ hash: j0k1l2 │ │ ... │ │ └── chunk_799.pak (100MB) │ │ │ │ Manifest.json: │ │ { │ │ "version": "1.5", │ │ "chunks": [ │ │ { "name": "chunk_00", "hash": "a1b2c3", "size": 100MB }, │ { "name": "chunk_01", "hash": "d4e5f6", "size": 100MB }, │ { "name": "chunk_02", "hash": "NEW_HASH", "size": 100MB }, │ ... │ │ ] │ │ } │ │ │ │ hash가 다른 청크만 다운로드! │ │ │ └──────────────────────────────────────────────────────────┘
// 청크 기반 패치 시스템 struct ChunkInfo { std::string name; std::string hash; // SHA-256 또는 xxHash size_t size; size_t offset; // 전체 파일 내 오프셋 }; class ChunkPatcher { void DownloadPatch(const Manifest& oldManifest, const Manifest& newManifest) { std::vector toDownload; // 1. 변경된 청크 찾기 for (const auto& newChunk : newManifest.chunks) { auto oldChunk = oldManifest.FindByName(newChunk.name); if (!oldChunk || oldChunk->hash != newChunk.hash) { toDownload.push_back(newChunk); } } // 2. 병렬 다운로드 ParallelDownload(toDownload, 8); // 8개 동시 다운로드 // 3. 검증 후 적용 for (const auto& chunk : toDownload) { if (VerifyHash(chunk)) { ApplyChunk(chunk); } else { RedownloadChunk(chunk); } } } };

Part 5. 패치 무결성 검증

패치 중 인터넷 끊기면?

원자적 업데이트가 필요합니다. 패치가 완전히 끝나기 전까지 원본을 건드리지 않습니다:

안전한 패치 적용 과정: ┌──────────────────────────────────────────────────────────┐ │ │ │ 1단계: 준비 (게임 실행 중에도 가능) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ /game/ │ │ │ │ ├── data/ (현재 버전, 사용 중) │ │ │ │ └── patch_staging/ │ │ │ │ ├── chunk_02.pak.download (다운로드 중) │ │ │ │ └── chunk_02.pak (다운로드 완료, 검증 완료) │ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 2단계: 적용 (게임 종료 후) │ │ ┌─────────────────────────────────────────────────┐ │ │ │ /game/ │ │ │ │ ├── data/ │ │ │ │ │ └── chunk_02.pak → chunk_02.pak.old (백업) │ │ │ │ └── patch_staging/ │ │ │ │ └── chunk_02.pak → data/chunk_02.pak (이동)│ │ │ └─────────────────────────────────────────────────┘ │ │ │ │ 3단계: 정리 │ │ - 성공: .old 파일 삭제 │ │ - 실패: .old 파일 복구 │ │ │ └──────────────────────────────────────────────────────────┘
// 트랜잭션 기반 패치 적용 class AtomicPatcher { bool ApplyPatch() { Transaction tx; try { // 1. 모든 준비 작업 for (auto& chunk : patchChunks) { // 현재 파일 백업 tx.Backup(chunk.targetPath); // 새 파일 준비 (아직 적용 안 함) tx.Stage(chunk.stagingPath, chunk.targetPath); } // 2. 커밋 (파일 이동만, 매우 빠름) tx.Commit(); // 3. 검증 if (!VerifyAllHashes()) { tx.Rollback(); return false; } // 4. 백업 정리 tx.Cleanup(); return true; } catch (...) { tx.Rollback(); return false; } } };

Part 6. 모바일/콘솔 특수 상황

모바일은 왜 다르게 처리해?

모바일과 콘솔은 플랫폼 제약이 있습니다:

플랫폼별 델타 패치 제약: 모바일 (iOS/Android): ┌────────────────────────────────────────────────────────┐ │ 제약: APK/IPA 자체를 수정 불가 (코드 서명 깨짐) │ │ │ │ 해결: APK Expansion File (OBB) / On-Demand Resources │ │ │ │ APK (500MB 제한) │ │ ├── classes.dex (코드) │ │ └── lib/ (네이티브) │ │ │ │ OBB (별도 다운로드, 델타 패치 가능) │ │ ├── main.obb │ │ └── patch.obb ← 이것만 델타 패치 │ │ │ └────────────────────────────────────────────────────────┘ 콘솔 (PlayStation/Xbox): ┌────────────────────────────────────────────────────────┐ │ 제약: 플랫폼 패치 시스템 필수 사용 │ │ │ │ PlayStation: pkg 패치 포맷 │ │ Xbox: XVC 청크 시스템 │ │ │ │ 장점: 플랫폼이 자동으로 델타 최적화 │ │ 제약: 패치 제출 → 심사 → 배포 (1-3일) │ │ │ └────────────────────────────────────────────────────────┘

Part 7. 델타 패치 파이프라인

실제 파이프라인은 어떻게 구성해?

CI/CD와 통합된 자동화 파이프라인:

델타 패치 자동화 파이프라인: ┌───────────────────────────────────────────────────────────┐ │ │ │ 1. 빌드 서버 │ │ ┌─────────────────────────────────────────────┐ │ │ │ 새 버전 빌드 완료 │ │ │ │ → 청크 분할 │ │ │ │ → 해시 계산 │ │ │ │ → Manifest 생성 │ │ │ └───────────────┬─────────────────────────────┘ │ │ ▼ │ │ 2. 델타 생성 서버 │ │ ┌─────────────────────────────────────────────┐ │ │ │ 이전 버전들과 비교 │ │ │ │ → 변경 청크 식별 │ │ │ │ → xdelta3로 델타 생성 │ │ │ │ → Skip Delta 생성 (인기 버전) │ │ │ └───────────────┬─────────────────────────────┘ │ │ ▼ │ │ 3. CDN 배포 │ │ ┌─────────────────────────────────────────────┐ │ │ │ /patches/v1.4_to_v1.5/ │ │ │ │ /patches/v1.0_to_v1.5/ (skip delta) │ │ │ │ /full/v1.5/ (신규 설치용) │ │ │ └─────────────────────────────────────────────┘ │ │ │ └───────────────────────────────────────────────────────────┘
// 빌드 파이프라인 스크립트 (Python) def generate_patch_pipeline(new_version, old_versions): # 1. 청크 분할 chunks = split_into_chunks(f"build/{new_version}", chunk_size=100*MB) # 2. 매니페스트 생성 manifest = { "version": new_version, "chunks": [ {"name": c.name, "hash": sha256(c), "size": c.size} for c in chunks ] } # 3. 각 이전 버전과 델타 생성 for old_ver in old_versions: old_manifest = load_manifest(old_ver) for new_chunk in manifest["chunks"]: old_chunk = find_chunk(old_manifest, new_chunk["name"]) if old_chunk and old_chunk["hash"] != new_chunk["hash"]: # xdelta3로 델타 생성 delta = create_delta( f"archive/{old_ver}/{new_chunk['name']}", f"build/{new_version}/{new_chunk['name']}" ) upload_to_cdn(f"patches/{old_ver}_to_{new_version}/{delta}") # 4. CDN 업로드 upload_manifest(manifest) invalidate_cdn_cache()

핵심 정리

  • 델타 패치는 변경된 바이트만 전송하여 대역폭/비용 절감
  • xdelta3, zstd가 속도와 압축률 균형이 좋음
  • Skip Delta로 버전 건너뛰기 최적화
  • 청크 기반으로 대용량 파일 처리 및 부분 실패 복구
  • 원자적 업데이트로 패치 중 실패해도 안전하게 롤백
  • 모바일은 OBB/ODR, 콘솔은 플랫폼 패치 시스템 사용
  • CI/CD와 통합하여 자동 델타 생성 파이프라인 구축
