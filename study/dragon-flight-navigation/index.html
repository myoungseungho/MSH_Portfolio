1프로젝트 DH 소개

프로젝트 DH는 어떤 게임인가요?

프로젝트 DH는 말을 타고 넓은 맵을 자유롭게 달리면서 용과 싸우는 액션 RPG 게임입니다.

  • 맵 규모: 6km x 6km의 광대한 오픈월드
  • 전투 방식: 활, 개인 화기, 직접 전투 등 다양한 수단으로 용 사냥
  • 멀티플레이어: 친구들과 함께 플레이 가능
  • 엔진: 언리얼 엔진 4 사용

실버 바인 모션 엔진

프로젝트 DH는 사실적인 애니메이션을 위해 "실버 바인 모션 엔진"이라는 절차적 애니메이션 시스템을 자체 개발하여 사용하고 있습니다.

2문제 정의: 용처럼 난다는 것

디렉터의 요구사항은 무엇이었나요?
  1. 공중 길찾기 기능이 필요
  2. 6km x 6km의 광대한 맵에서 동작해야 함
  3. 기획자 의도대로 가이드가 가능해야 함
  4. 무엇보다도 "용처럼 날게 해주세요"

핵심 질문

"용처럼 난다는 게 도대체 어떻게 해야 하는 거죠? 제가 용을 직접 본 일이 없어서..."

용의 비행 방식을 어떻게 분석했나요?

용이 등장하는 다양한 미디어(애니메이션, 드라마, 영화, 게임)를 조사한 결과:

기본 비행 모션

이륙, 착륙, 수직 상승/하강, 활강, 탱크턴, 선회, 급정지

상황별 특수 모션

수직 강하, 정지 비행, 절벽 따라 활강, 스파이럴

핵심 발견

방향 전환 시 일정한 선회 반경과 선회율을 유지

물리 법칙 준수

속도를 무시한 급선회는 없음 - 용도 물리 법칙의 지배를 받음

시스템 요구사항을 정리하면?
요구사항 설명
3차원 패스 파인딩 공중 길찾기 기본 기능
부드러운 경로 생성 용의 움직임에 맞는 자연스러운 곡선
즉각적 애니메이션 반응 경로 유형에 따른 모션 변화
기획자 의도 반영 경로에 디자이너 의도 적용 가능
작은 데이터 크기 6km x 6km 맵에서 관리 가능한 수준

3관련 연구 조사

기존 솔루션들을 검토한 결과는?
솔루션 특징 한계
Recast/Detour (UE4 기본) 내비게이션 메시 기반 지상 길찾기 지상 전용, 공중 확장 어려움
Path Follow Plugin 스플라인 패스 팔로잉 패스 파인딩 기능 없음
DON AI Navigation 복셀 기반 3D 내비게이션 부드러운 곡선 X, 확장성 부족, 데이터량 급증
드론 경로 최적화 논문 스플라인 기반 물리적 경로 생성 실시간이 아닌 오프라인 툴

결론

  • 기존 지상 내비게이션을 공중용으로 확장하기 어려움
  • 복셀 기반은 부드러운 움직임 표현에 부적절 + 데이터량 문제
  • 물리적 타당성에 너무 집착하지 말자 (게임이니까)
  • 스플라인이 부드러운 경로 표현에 가장 적합

4하늘길 시스템 설계

하늘길 시스템의 핵심 아이디어는?

"실크로드" 개념 - 용을 위한 안전한 길을 미리 설치하고, 이를 기반으로 자유롭게 비행 가능한 영역을 정의합니다.

하늘길 시스템 개념
[Waypoint A] -------- Sky Road (Spline) -------- [Waypoint B] | | | v v v +--------+ +-----------+ +--------+ | 안전 | | 안전 반경 | | 안전 | | 영역 | | (부피를 | | 영역 | +--------+ | 가진 길) | +--------+ +-----------+ | v 실제 이동 경로 생성 | v [Probe] --> [Dragon]
하늘길 시스템의 구성 요소는?
구성 요소 역할 특징
Waypoint (웨이포인트) 하늘길 고속도로의 IC 역할 안전 반경 구체, 연결된 하늘길 목록 관리
Sky Road (하늘길 도로) 스플라인으로 제작된 경로 일정 간격마다 안전 반경 기록, 부피를 가진 길
Probe (프로브) 패스 팔로잉을 위한 선행 객체 전체 경로 분석 결과 보유, 용의 비행 직접 제어

장점

안전이 보장된 길을 기반으로 이동 경로를 계산하므로 실행 시간 비용이 낮고, 자연스러운 용의 비행 정보를 구할 수 있습니다.

5스플라인 커브 기초

Cubic Bezier 커브와 Hermite 스플라인의 차이는?

Cubic Bezier 커브

연쇄적인 보간을 통해 시간 t에서의 위치를 결정. 파라메트릭 커브로 동일한 t에서 항상 같은 위치 반환.

Cubic Hermite 스플라인

2개의 점과 기울기(탄젠트)로 곡선 조각 표현. 점과 탄젠트의 시퀀스로 구불구불한 곡선 생성.

상호 변환 가능

Cubic Bezier와 Cubic Hermite는 서로 변환 가능합니다. 각 점에서 C1 연속(기울기 연속)을 보장합니다.

연속성(Continuity)이 왜 중요한가요?

커브의 "부드러운 정도"를 나타내며, 파라메트릭(Parametric)과 지오메트릭(Geometric) 두 가지 관점이 있습니다.

연속성 의미 효과
C0 위치만 연속 점이 이어져 있음
C1 1차 미분 연속 (속도) 일정한 속도로 이동 가능
C2 2차 미분 연속 (가속도) 기울기 변화량까지 부드러움
G1 탄젠트 방향만 같음 길이는 달라도 방향은 일치

C1 연속이 아닌 경우의 문제

탄젠트 방향은 같지만 길이가 다르면, A-B 구간은 느리게 움직이다가 B-C 구간에서 갑자기 빨라지는 현상이 발생합니다.

언리얼 엔진의 스플라인 컴포넌트 특징은?
  • Cubic Bezier 커브 세그먼트로 구성
  • 문제점: Arrive/Leave 탄젠트가 서로 다른 길이를 가질 수 있음 (C1 연속 아닐 수 있음)
  • 해결책: Re-parameterization 테이블을 별도로 관리하여 보간 속도 일관성 보장

하늘길 구현

스플라인 컴포넌트를 직접 사용하지 않고, FInterpCurve라는 코어 템플릿 자료구조로 제작했습니다.

6패스 파인딩 절차

패스 파인딩의 전체 흐름은?
패스 파인딩 절차
[1] 출발/도착 지점 --> 하늘길로 임시 링크 연결 | v [2] 그래프 최단경로 탐색 (A* Search) | v [3] 들어오는 길 / 나가는 길 경로 생성 | v [4] 전체 경로 스무딩 (Smoothing) | v [5] 최종 경로 스플라인 생성
임시 링크는 어떻게 생성하나요?

출발/도착 지점은 하늘길의 안전 영역 밖에 있을 수 있습니다. 따라서:

  1. 용의 관점에서 하늘을 바라봄
  2. 보이는 모든 하늘길에 대해 임시 링크 생성
  3. 임시 링크를 포함하여 A* 탐색 수행

가중치 설정

하늘길에 따라 가중치를 달리할 수 있습니다. 예: 용이 선호하는 길 vs 싫어하는 길

들어오는 길/나가는 길은 어떻게 부드럽게 연결하나요?

출발/도착 지점에서 하늘길로의 직선 연결은 부자연스럽습니다. 합리적인 경로 생성 알고리즘을 개발했습니다:

후보 공간 탐색 알고리즘
[출발점 탄젠트] --------+-------- [도착점 탄젠트] | +------+------+ | 후보 공간 | | 평면 | +------+------+ | +----+----+----+----+----+ | P1 | P2 | P3 | P4 | P5 | <-- 후보 지점들 +----+----+----+----+----+ | v 선호도 계산 --> 경로 유효성 검증 --> 스플라인 생성
  1. 각 지점의 탄젠트 위치를 이은 선분을 후보 공간 축으로 설정
  2. 가운데 지점을 지나는 후보 공간 평면 정의
  3. 후보 지점들의 선호도 계산 (높을수록 빨강, 낮을수록 파랑)
  4. 높은 우선순위부터 경로 유효성 검증
  5. 두 지점과 선택된 후보 지점을 거친 엣 스플라인 경로 생성

고려 요소

출발 지점의 속도(용의 초기 속도), 진입점 탄젠트, 탈출점 탄젠트, 도착 지점의 속도(목표 방향) - 4가지를 모두 고려하여 부드러운 연결

경로 스무딩은 어떻게 하나요?

웨이포인트로 연결된 꺾인 지점들을 부드럽게 만드는 과정:

  1. 웨이포인트에서 인접한 두 세그먼트의 일정 거리상 위치 샘플링
  2. 각 지점 사이가 안전 반경 내에서 안전한지 검사
  3. 용의 부피를 고려, 벗어나기 직전 두 지점을 선택
  4. 두 지점을 부드럽게 연결
  5. 탄젠트 세그먼트의 Closest Point 계산 후 탄젠트 클램핑

안전 반경 데이터

안전 반경이라는 데이터 구조를 갖고 있기 때문에 검사 비용이 크지 않습니다.

7패스 팔로잉과 프로브

왜 단순히 스플라인을 따라가면 안 되나요?

처음에는 시간 t 위치로 용의 위치를 갱신하면 될 것으로 생각했지만:

  • 단조로운 움직임: 모션이 변화 없이 일정함
  • Re-parameterization 정밀도 문제: 정밀도가 낮으면 일정한 속력으로 이동 불가
  • 경로 이탈 제어 어려움: 다른 용과 충돌하거나 피격 시 대응 불가
프로브(Probe) 시스템은 어떻게 동작하나요?

예인선(Tugboat) 모델: 작은 배가 거대한 배를 이끄는 것처럼, 프로브가 용을 이끕니다.

프로브-용 관계
Spline Path: =====[Probe]======================> | | 따라감 (적정 거리 유지) v [Dragon] | v 위치/회전/모션 갱신
  • 프로브: 스플라인 위를 정직하게 이동
  • 용: 프로브를 향해 날아감
  • 프로브의 역할: 용이 뒤처지거나 앞서지 않도록 속도 제어, 완충 장치 역할
비행 유형은 어떻게 결정하나요?

용의 비행 유형은 선형 속도와 회전 속도의 변화로 결정됩니다.

극점(Extrema) 분석

경로의 Z(높이) 성분에 대해 1차, 2차 도함수의 극점을 계산하여 속도 변화 시점을 파악합니다.

  • 1차 도함수 극점: 기울기가 +에서 -로 또는 -에서 +로 바뀌는 지점
  • 2차 도함수 극점: 기울기 변화량이 바뀌는 지점 (변곡점)

예시: 하강하다가 다시 상승하는 구간

  • A-B 구간: 속도가 점진적으로 줄어듦
  • B 지점: 더 이상 속도가 줄어들 수 없음
  • B-C 구간: 상승을 위해 날개짓 시작
극점은 어떻게 계산하나요?

Cubic Hermite 커브는 3차 다항식입니다:

// 3차 다항식 P(t) = at³ + bt² + ct + d
// 1차 미분: P'(t) = 3at² + 2bt + c (근의 공식으로 해 구함)
// 2차 미분: P''(t) = 6at + 2b (선형 방정식으로 해 구함)

// 코드 1-2줄로 구현 가능!
float t1 = (-2*b + sqrt(4*b*b - 12*a*c)) / (6*a);
float t2 = (-2*b - sqrt(4*b*b - 12*a*c)) / (6*a);

C2 연속 문제

Hermite 스플라인은 C2 연속이 아닐 수 있어 2차 미분이 불가능할 수 있습니다. 패스 스무딩 과정에서 탄젠트 길이가 달라질 수 있어 C1 연속조차 보장되지 않을 수 있습니다. 해결책: 커브의 연결 지점을 패스 구분을 위한 포인트로 강제 지정

뱅크 앵글(Bank Angle)은 어떻게 계산하나요?

선회(Turn): 항공기가 곡선을 그리듯 진로를 바꾸는 것

빠른 선회를 위해서는 양력이 선회 반경 중심을 향하도록 몸을 틀어야 합니다 (뱅크턴).

핵심 공식

  • 속력 일정 시, 선회 반경 작아짐 = 선회율 상승
  • 선회 반경 ∝ 수평 곡률
  • 수평 곡률 상승 = 뱅크 앵글 상승
// 곡률(Curvature) k = 1/R (R: 선회 반경)
// 파라메트릭 커브의 곡률 공식 적용
// X, Y 컴포넌트에 대해서만 계산 (Z 성분 불필요)

float curvature = CalculateHorizontalCurvature(point);
float bankAngle = ConvertCurvatureToBankAngle(curvature);

결과: 휘어져 있는 경로에서 용의 몸체가 회전 방향으로 기울어지는 롤(Roll) 회전 구현

프로브 제어와 용 움직임은 어떻게 구현하나요?

프로브 제어 (단순)

  • 용과 적정 거리 유지하며 스플라인 위 이동
  • 일정한 속력 유지
  • 용과 거리 가까우면 속력 높임
  • 용과 거리 멀면 속력 낮춤

용 움직임 제어 (복잡)

  1. 프로브 현재 구간 유형 확인
  2. 현재 위치 기울기로 가속력 계산
  3. 가속력으로부터 속력 계산
  4. 프로브 방향으로 구한 속력만큼 이동
  5. 프로브 방향으로 정렬 위한 회전 속력 계산
  6. 롤 회전 요소 누적
  7. 최종 회전 속력으로 델타 로테이션 계산

모션 연동

패스 유형이 바뀌는 시점에 용 객체에 통지하면, 실버 바인 모션 엔진이 해당 모션 유형에 맞는 로코모션을 재생합니다.

타겟이 이동하면 어떻게 경로를 갱신하나요?

Pruning & Grafting (가지치기 & 접붙이기) 방식:

경로 재탐색 (Re-pathfinding)
기존 경로: ====[Dragon]=====[Cut Point]=====>[Old Target] | 잘라냄 (Pruning) | v 새로운 경로 생성 (Grafting) | v 새 경로: ====[Dragon]=====[Cut Point]---->[New Target]
  1. 패스에서 적당한 지점을 찾아 잘라냄
  2. 해당 지점의 위치와 탄젠트를 유지한 채
  3. 새로운 타겟 위치로 패스 파인딩 수행
  4. 새 경로가 접붙여지고 경로 재탐색 완료

8언리얼 엔진 통합

기존 언리얼 내비게이션 흐름은 어떻게 되나요?
기존 언리얼 엔진 내비게이션 흐름
[AI Controller] | | MoveTo() 요청 v [Navigation System] | | FindPath() v [NavMesh Data] (Recast) | | NavigationPath 반환 v [Path Following Component] | | FollowPathSegment() v [AI Agent 이동]
하늘길 시스템은 어떻게 통합했나요?
하늘길 시스템 통합 흐름
[DH AI Controller] (확장) | | FlyTo() 요청 (MoveTo와 유사) v [Flight Path System] (자체 개발) | | FindPath() + 하늘길 데이터 참조 v [Probe 반환] (최종 경로 스플라인 포함) | v [DH Path Following Component] (교체) | | Follow() 요청 v [Probe Update & Follow 로직] | v [Dragon 이동 및 모션 재생]
기존 컴포넌트 확장/교체 역할
AI Controller DH AI Controller (확장) FlyTo() 요청 추가
Navigation System Flight Path System (자체) 공중 패스 파인딩
NavMesh Data 하늘길 데이터 스플라인 기반 경로
Path Following Component DH Path Following Component (교체) 프로브 기반 팔로잉

지상/공중 이동 분리

지상 이동은 기존 Path Following Component 동작 그대로 수행, 공중 이동만 프로브의 Update/Follow 로직으로 대체합니다.

에디터 툴은 어떻게 구성했나요?
  • 언리얼 엔진 에디터 내에서 바로 사용 가능
  • 스플라인으로 경로를 쉽게 편집 가능
  • 맵이 크더라도 많은 시간 들이지 않고 길 생성 가능
  • 안전 반경 자동 계산 기능

디자이너 의도 반영

복셀 기반의 최단거리 탐색은 그냥 직선으로 날아가지만, 하늘길은 일부러 낮은 고도로만 만들어서 플레이어를 따라다니며 날도록 디자이너가 원하는 형태로 용이 비행할 수 있습니다.

9향후 과제 및 느낀 점

비용(성능)은 어떤가요?

아직 자세한 프로파일링이나 최적화 작업이 수행되지 않았지만, 게임 플레이에 영향을 주지 않는 수준의 퍼포먼스를 보이고 있습니다.

최적화 대상

  • 스플라인 객체 생성/파괴: 빈번하게 발생하여 메모리 부담
  • 레이트레이스/캡슐 오버랩 테스트: 스태틱 오브젝트 충돌 처리 다수
아직 구현되지 않은 기능은?
미구현 사항 기대 효과
날개짓에 맞는 요 움직임 제어 더 자연스러운 용의 움직임 (실버 바인 모션 엔진 담당 예정)
물리 법칙에 맞는 움직임 제어 현재는 "그럴싸하게" 처리, 물리 기반 경로 수정 시 더 자연스러움
스플라인 오프셋팅 안전 반경 내에서 중심이 아닌 가장자리로도 이동 가능

연구와 실전의 차이

"연구와 실전은 상당히 많이 다르구나"를 느꼈습니다. 설계 시 고려하지 못한 코너 케이스가 굉장히 많았습니다.

정답이 없는 분야

AI 내비게이션은 역사가 깊지만 아직까지 이렇다 할 실버불릿이 없습니다. "진짜 좋은 실버불릿 알고 계시면 저도 좀 알려주세요"

욕심과 현실의 균형

더 잘 만들고 싶은 욕심은 끝이 없는데, 현실적인 일정 사이에서 균형을 잡는다는 게 참 어렵습니다.
