Distributed Tracing

분산 시스템에서 장애 원인을 5분 만에 찾는 마법

Part 1: 분산 추적이 뭐야?

그냥 로그 보면 안 돼?
비유: 택배 송장 추적

택배를 보내면 송장 번호가 생김
송장 번호로 "어디서 지연됐는지" 추적 가능!

"대전 센터에서 24시간 멈춤" → 문제 지점 바로 확인!

분산 추적 = 요청의 송장 번호
요청이 여러 서버를 거쳐갈 때, "어디서 느려졌는지" 추적!

로그만 보는 경우의 문제

[Gate Server 로그]
14:00:01.123 Request from user_123
14:00:01.125 Forward to Game Server

[Game Server 로그]
14:00:01.130 Received request
14:00:01.500 Timeout error!

질문: "어떤 유저 요청이 타임아웃 났어?"
답: 모름! 로그가 연결이 안 됨!
분산 시스템에서 왜 어려워?
단일 서버 (쉬움): ───────────────────────────── [Game Server] └─ 14:00:01 로그인 요청 └─ 14:00:02 DB 조회 └─ 14:00:03 에러 발생! ← 바로 찾음! 분산 시스템 (어려움): ───────────────────────────── [Gate] → [Game] → [GameDB] → [Redis] │ │ │ │ 로그인 캐릭터 DB조회 세션 요청 로딩 저장 "14:00:03 에러 발생" → 어느 서버에서? → 어떤 요청 때문에? → 다른 서버에서 뭘 했길래?

Part 2: Trace, Span 이해하기

Trace랑 Span이 뭐야?

Trace (트레이스)

하나의 요청이 시스템을 통과하는 전체 여정
택배 송장 번호처럼, 요청을 식별하는 고유 ID

Span (스팬)

각 서비스/작업에서의 작업 단위
택배가 각 물류센터에서 스캔되는 것처럼, 각 구간별 정보

하나의 Trace 구조: Trace ID: abc-123-def-456 │ ├── Span 1: Gate Server (50ms) │ ├── 시작: 14:00:01.000 │ └── 종료: 14:00:01.050 │ │ └── Span 2: Game Server (450ms) │ ├── 시작: 14:00:01.050 │ └── 종료: 14:00:01.500 │ │ ├── Span 3: DB Query (380ms) ← 병목! │ │ ├── 시작: 14:00:01.060 │ │ └── 종료: 14:00:01.440 │ │ │ └── Span 4: Redis (10ms) │ ├── 시작: 14:00:01.450 │ └── 종료: 14:00:01.460
부모-자식 관계가 뭐야?
용어 설명 예시
Trace ID 요청 전체를 식별하는 ID abc-123-def-456
Span ID 각 작업을 식별하는 ID span-001, span-002
Parent Span ID 호출한 쪽의 Span ID Gate가 Game 호출 시, Gate = Parent
Root Span 가장 첫 번째 Span 클라이언트 요청 받은 곳

Part 3: 서버 간 Trace 연결 방법

Trace 정보를 어떻게 전달해?

서버 간 통신할 때 헤더에 Trace 정보를 포함시킵니다.

HTTP 요청 시 헤더에 포함: ───────────────────────────── GET /api/login HTTP/1.1 Host: game-server X-Trace-Id: abc-123-def-456 ← Trace ID X-Span-Id: span-002 ← 새로 생성한 Span ID X-Parent-Span-Id: span-001 ← 호출하는 쪽의 Span ID 게임 서버 TCP 패킷: ───────────────────────────── ┌────────────────────────────────┐ │ PacketHeader │ │ ├─ packetId: CM_LOGIN │ │ ├─ size: 128 │ │ ├─ traceId: abc-123-def-456 │ ← Trace 정보 │ ├─ spanId: span-003 │ │ └─ parentSpanId: span-002 │ ├────────────────────────────────┤ │ PacketBody │ │ └─ (로그인 데이터) │ └────────────────────────────────┘
코드로 어떻게 구현해?
// Gate Server (요청 시작) void OnClientRequest(Request& req) { // 1. Trace 시작 (또는 클라이언트에서 받음) string traceId = GenerateTraceId(); // abc-123... string spanId = GenerateSpanId(); // span-001 Span span = tracer.StartSpan("gate.login", traceId, spanId); // 2. Game Server로 요청할 때 Trace 정보 전달 HttpRequest gameReq; gameReq.SetHeader("X-Trace-Id", traceId); gameReq.SetHeader("X-Parent-Span-Id", spanId); gameReq.SetHeader("X-Span-Id", GenerateSpanId()); // span-002 auto response = gameClient.Request(gameReq); span.End(); // Span 종료 (소요 시간 기록) } // Game Server (요청 받음) void OnRequest(Request& req) { // 1. Trace 정보 추출 string traceId = req.GetHeader("X-Trace-Id"); string parentSpanId = req.GetHeader("X-Parent-Span-Id"); string spanId = req.GetHeader("X-Span-Id"); // 2. 자식 Span 시작 Span span = tracer.StartSpan("game.login", traceId, spanId, parentSpanId); // 3. DB 호출 (새 Span) Span dbSpan = tracer.StartSpan("db.query", traceId); auto result = db.Query("SELECT * FROM users WHERE id = ?"); dbSpan.End(); span.End(); }

Part 4: Jaeger로 시각화하기

Jaeger가 뭐야?

Jaeger는 가장 인기 있는 분산 추적 시각화 도구입니다.

Jaeger 아키텍처: [Game Server] ──┐ │ [Gate Server] ──┼──> [Jaeger Agent] ──> [Jaeger Collector] │ │ [DB Server] ───┘ ↓ [Elasticsearch] │ ↓ [Jaeger UI] (대시보드)
Jaeger UI에서 어떻게 보여?
Trace ID: abc-123-def-456 Service: game-server | Duration: 2,530ms Timeline: |=============================================| 2530ms gate.login |===| 50ms game.login |========================| 2480ms db.user_query |====================| 2400ms ← 빨간색! redis.session |=| 30ms Tags: user_id: 12345 error: false db.query: "SELECT * FROM user_items..." Logs: 14:00:01.123 - Starting login 14:00:01.130 - DB query started 14:00:03.530 - DB query completed (SLOW!) 14:00:03.560 - Login completed
바로 보이는 것!
- DB 쿼리가 2,400ms나 걸림 (전체의 95%)
- user_items 테이블 쿼리가 문제
→ 인덱스 추가 필요!

Part 5: 실제 장애 분석 사례

"로그인이 느려요" 신고가 왔어
분산 추적 없이 (2시간)

1. Gate 로그 확인 → 정상
2. Game 로그 확인 → 정상?
3. DB 로그 확인 → 정상?
4. Redis 로그 확인 → 정상?
5. 재현 안 됨... 뭐지?

결과: 2시간 삽질, 원인 못 찾음
분산 추적으로 (5분)

1. Jaeger에서 "느린 로그인" 검색 (latency > 2000ms)
2. 해당 Trace 클릭
3. 타임라인 확인:
   - Gate: 10ms ✓
   - Game: 20ms ✓
   - DB Query: 2,500ms! ← 발견!
4. DB Span 상세 보기:
   - Query: "SELECT * FROM user_items WHERE user_id = ?"
   - user_items 테이블 인덱스 없음!

결과: 5분 만에 원인 파악 & 해결
어떤 문제들을 찾을 수 있어?
문제 유형 분산 추적에서 보이는 것
느린 DB 쿼리 특정 Span이 유독 길게 표시
N+1 쿼리 같은 종류의 Span이 수십 개 반복
순환 호출 A→B→C→A 형태의 Span 구조
타임아웃 Span이 에러로 끝나고, 시간이 딱 타임아웃 값
병목 서비스 특정 서비스의 Span만 항상 느림

Part 6: 샘플링 전략

모든 요청을 다 추적하면 너무 많지 않아?

맞습니다! 전체 추적은 비용 폭탄이에요. 샘플링이 필수!

샘플링 전략: 1. 확률 샘플링 (가장 기본) ───────────────────────── 전체 요청의 1%만 추적 → 100개 중 1개만 Trace 생성 → 정상적인 요청 패턴 파악에 충분 2. 에러 우선 샘플링 ───────────────────────── 에러 발생 → 100% 추적 정상 요청 → 1% 추적 → 문제 분석에 집중 3. 지연 시간 기반 샘플링 ───────────────────────── 응답 > 1초 → 100% 추적 응답 < 1초 → 1% 추적 → 느린 요청만 집중 분석 4. 중요도 기반 샘플링 ───────────────────────── 결제 API → 100% 추적 로그인 → 10% 추적 조회 API → 1% 추적 → 비즈니스 중요도 기준
샘플링 코드 예시 보여줘
class TracingSampler { public: bool ShouldSample(const string& traceId, const Request& req) { // 1. 에러 요청은 100% 수집 if (req.HasError()) { return true; } // 2. 느린 요청은 100% 수집 if (req.GetLatency() > 1000) { // 1초 이상 return true; } // 3. 결제 API는 100% 수집 if (req.GetPath().Contains("/payment")) { return true; } // 4. 일반 요청은 1% 샘플링 return Hash(traceId) % 100 == 0; } };
비용 vs 가시성 트레이드오프
- 샘플링 1%: 저비용, 하지만 간헐적 문제 놓칠 수 있음
- 샘플링 100%: 완벽한 가시성, 하지만 비용 폭발
- 권장: 에러/느린 요청 100% + 일반 요청 1~5%

핵심 정리: Distributed Tracing

  • 목적: 분산 시스템에서 요청의 전체 여정을 추적
  • 핵심 개념: Trace(전체 여정) + Span(각 구간) = 요청 추적
  • 연결 방법: HTTP 헤더 또는 패킷에 Trace ID 포함
  • 주요 도구: Jaeger, Zipkin (오픈소스) / Datadog, X-Ray (상용)
  • 샘플링: 에러/느린 요청 100% + 일반 요청 1~5%
  • 효과: 장애 원인 파악 2시간 → 5분!
