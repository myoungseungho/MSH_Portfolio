Auto Scaling

트래픽에 따라 서버를 자동으로 늘리고 줄여서 비용을 절반으로!

Part 1: 오토스케일링이 뭐야?

오토스케일링을 쉽게 설명해줘
비유: 레스토랑 직원 관리

점심시간 (바쁨): 직원 10명 투입
오후 3시 (한가함): 직원 3명만 남기고 퇴근
저녁시간 (피크): 다시 12명 호출

오토스케일링 = 서버판 탄력 근무제!
바쁠 때 서버 늘리고, 한가할 때 줄이고

오토스케일링의 핵심: 트래픽 많음 트래픽 적음 ┌─────────────┐ ┌─────────────┐ │ 서버 서버 │ │ 서버 │ │ 서버 서버 │ ◄────────► │ │ │ 서버 서버 │ 자동 조절 │ │ └─────────────┘ └─────────────┘ 10대 2대 "쓰는 만큼만 비용을 내자!"
서버 10대 고정으로 두면 안 돼?
고정 서버의 비극

새벽 4시: 접속자 1,000명
→ 서버 10대 중 9대가 놀고 있음
→ 낭비 비용: 9대 × $100 = $900/월

저녁 8시: 접속자 50,000명
→ 서버 10대로는 부족!
→ 결과: 서버 터짐, 유저 이탈

주말 이벤트: 접속자 100,000명
→ 서버 10대? 대참사!
오토스케일링이 있다면

새벽 4시: 자동으로 2대로 축소 → 비용 절감
저녁 8시: 자동으로 20대로 확장 → 안정 운영
주말 이벤트: 자동으로 50대로 확장 → 원활한 서비스

결과: 필요한 만큼만 쓰고, 필요한 만큼만 지불!

Part 2: 수직 vs 수평 스케일링

서버를 업그레이드하면 안 돼?
수직 스케일링 (Scale Up): ───────────────────────────── [서버 1대] 8코어, 32GB ↓ 업그레이드 64코어, 512GB "더 강한 서버로 바꾸자!" 한계: - 물리적 한계 (무한 업그레이드 불가) - 다운타임 필요 (껐다 켜야 함) - 비용 기하급수적 증가 수평 스케일링 (Scale Out): ───────────────────────────── [서버 1대] → [서버][서버][서버]... "서버를 더 붙이자!" 장점: - 이론상 무한 확장 - 무중단 확장 가능 - 선형 비용 증가
게임 서버는 수평 스케일링!
MMO 게임은 채널/월드 단위로 서버를 분리
→ 유저가 많아지면 채널 추가
→ 유저가 적어지면 채널 통합
수평 스케일링이 가능하려면?

Stateless 설계가 필수입니다!

문제되는 설계 (Stateful): ───────────────────────────── [게임 서버 A] - 유저 100명 세션 저장 ↓ A가 죽으면? → 100명 세션 날아감! 새 서버 추가? → 기존 유저 못 받음! 올바른 설계 (Stateless): ───────────────────────────── [게임 서버 A] ──┐ [게임 서버 B] ──┼──> [Redis 클러스터] (세션 저장) [게임 서버 N] ──┘ ↓ 어떤 서버든 세션 공유! 서버 추가/삭제 자유! 로드밸런서가 분배!

Part 3: 언제 서버를 늘려?

CPU 80%면 늘리면 돼?

여러 메트릭을 조합해서 판단합니다.

CPU 사용률

Scale Out: > 70% (5분 지속) Scale In: < 30% (15분 지속)

메모리 사용률

Scale Out: > 80% Scale In: < 40%

동시 접속자 (CCU)

Scale Out: > 5,000/서버 Scale In: < 1,000/서버

응답 시간

Scale Out: > 100ms Scale In: -
축소할 때 주의할 점은?
Flapping 주의!

나쁜 예:
09:00 - CPU 72% → Scale Out!
09:01 - CPU 65% → Scale In!
09:02 - CPU 73% → Scale Out!
... (무한 반복)

해결: Cooldown Period 설정
- Scale Out 후 5분간 추가 스케일링 금지
- Scale In은 더 길게 (15분) 안정화 대기

Part 4: 게임 트래픽 특성

게임 서버 트래픽은 어떤 패턴이야?
일반적인 게임 트래픽 패턴: 시간대별: ───────────────────────────── 새벽 2-6시 : ▓░░░░░░░░░ 최저 (1x) 오전 10시 : ▓▓▓░░░░░░░ 증가 (3x) 점심 12시 : ▓▓▓▓░░░░░░ 중간 (4x) 오후 3시 : ▓▓▓░░░░░░░ 감소 (3x) 저녁 8-10시: ▓▓▓▓▓▓▓▓▓▓ 피크 (10x) 자정 : ▓▓▓▓▓░░░░░ 감소 (5x) 특수 패턴: ───────────────────────────── 주말 : 평일의 1.5배 신규 업데이트: 2~3배 폭증 이벤트 시작 : 5배 폭증 자정 던전 리셋: 순간 폭증!
예측 불가능한 트래픽은?
실제 사례: 유튜버 효과

- 인기 유튜버가 갑자기 게임 방송 시작
- 30분 만에 CCU 5배 증가!
- 오토스케일링이 따라가지 못함

해결책:
- 최소 인스턴스 여유 유지 (예: 피크의 30%)
- Warm Pool: 미리 켜둔 대기 서버
- 입장 대기열 시스템

Part 5: 비용 최적화 전략

인스턴스 유형별 비용이 다르다던데?
유형 비용 용도
On-Demand 100% 피크 대응 (유동적)
Reserved 30~75% 할인 기본 서버 (항상 필요)
Spot 90% 할인 배치 작업, 테스트
Savings Plans 최대 72% 할인 장기 약정
최적의 조합은?
비용 최적화 조합 전략: [기본 트래픽] Reserved Instance ───────────────────────────── 항상 필요한 최소 서버 예: 10대 (피크의 20%) 비용: $300/월 (75% 할인) [피크 트래픽] On-Demand Auto Scaling ───────────────────────────── 트래픽에 따라 탄력 운영 예: 0~40대 (필요할 때만) 비용: 사용한 만큼 [테스트/배치] Spot Instance ───────────────────────────── 언제든 종료될 수 있음 예: 부하 테스트, 로그 처리 비용: 90% 할인

비용 절감 효과

-70%
Before: $5,000/월 → After: $1,500/월

Part 6: 실제 구현

AWS에서 어떻게 설정해?
# Terraform으로 Auto Scaling Group 설정 resource "aws_autoscaling_group" "game_server" { name = "game-server-asg" vpc_zone_identifier = var.subnet_ids target_group_arns = [aws_lb_target_group.game.arn] min_size = 2 # 최소 2대 (항상 유지) max_size = 100 # 최대 100대 desired_capacity = 5 # 기본 5대 # 헬스체크 health_check_type = "ELB" health_check_grace_period = 300 # 인스턴스 교체 전략 instance_refresh { strategy = "Rolling" preferences { min_healthy_percentage = 90 } } } # CPU 기반 스케일링 정책 resource "aws_autoscaling_policy" "cpu_policy" { name = "cpu-target-tracking" autoscaling_group_name = aws_autoscaling_group.game_server.name policy_type = "TargetTrackingScaling" target_tracking_configuration { predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" } target_value = 70.0 # CPU 70% 유지 목표 } }

Part 7: 오토스케일링 베스트 프랙티스

오토스케일링 잘 운영하는 팁 알려줘
원칙 설명
여유 있게 시작 최소 인스턴스는 피크의 30% 정도 유지
갑작스러운 트래픽에 대비
Scale Out은 빠르게 확장은 공격적으로 (1분 내)
사용자 경험이 우선!
Scale In은 천천히 축소는 보수적으로 (5~15분 대기)
Flapping 방지
예약 스케일링 활용 피크 시간, 이벤트는 미리 확장
반응형 + 예측형 조합
Warm Pool 준비 미리 부팅된 인스턴스 대기
시작 시간 단축
피해야 할 실수는?
오토스케일링 안티패턴 TOP 5

1. 최소 인스턴스 0개: 콜드 스타트 지연, 첫 유저 대기

2. 너무 민감한 임계값: CPU 50%에서 Scale Out → 불필요한 비용

3. Cooldown 없음: 스케일 업/다운 무한 반복

4. Stateful 서버에 적용: 세션 손실, 데이터 유실

5. 모니터링 없이 운영: 스케일링이 제대로 되는지 확인 필수

핵심 정리: Auto Scaling

  • 수평 스케일링: 서버 수를 늘리고 줄임 (Scale Out/In)
  • Stateless 설계: 세션은 외부 저장소 (Redis)에 저장
  • 메트릭 기반: CPU, 메모리, CCU, 응답시간 조합
  • 비용 최적화: Reserved (기본) + On-Demand (피크) + Spot (테스트)
  • 핵심 원칙: Scale Out은 빠르게, Scale In은 천천히
  • 결과: 서버 비용 50~70% 절감 + 안정적인 서비스
