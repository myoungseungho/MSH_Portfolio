Auto Scaling

서버 비용을 절반으로 줄이는 법

1. 서버를 왜 늘렸다 줄였다 해?

서버 10대 고정으로 두면 안 돼?

돈이 새나가!

게임 서버 트래픽 패턴: 새벽 4시: 1,000명 접속 -> 서버 10대? 9대가 놀고 있음! -> 낭비 비용: 9대 x $100 = $900/월 저녁 8시: 50,000명 접속 -> 서버 10대? 부족! -> 결과: 서버 터짐, 유저 이탈 주말 이벤트: 100,000명 접속 -> 서버 10대? 대참사! -> 커뮤니티: "쓰레기 운영"
그럼 서버 100대 준비하면?
서버 100대 고정: 피크 대응: OK (100,000명 가능) 비용: - 새벽 4시: 99대 놀고 있음 - 한 달 비용: 100대 x $100 = $10,000 오토스케일링: - 새벽 4시: 2대 (자동 축소) - 저녁 8시: 20대 (자동 확장) - 이벤트: 50대 (예약 스케일링) - 한 달 비용: 평균 15대 = $1,500 절약: $8,500/월 = 85%!

쓰는 만큼만 내면 된다!

2. 수평 스케일링이 뭐야?

서버를 업그레이드하면 안 돼?

수직 vs 수평:

수직 스케일링 (Scale Up): [서버 1대] 8코어, 32GB -> 64코어, 512GB "더 강한 서버로!" 한계: - 물리적 한계 (무한 업그레이드 불가) - 다운타임 필요 - 비용 기하급수적 증가 수평 스케일링 (Scale Out): [서버 1대] -> [서버 1대][서버 2대][서버 3대]... "서버를 더 붙이자!" 장점: - 이론상 무한 확장 - 무중단 확장 가능 - 선형 비용 증가

게임 서버는 수평 스케일링이 기본이야!

게임 서버도 수평으로 확장 가능해?

Stateless하게 설계해야 해:

문제되는 설계: [게임 서버 A] - 유저 100명 세션 저장 -> A가 죽으면? 100명 세션 날아감! -> 새 서버 추가해도 기존 유저 못 받음 올바른 설계: [게임 서버 A] --세션--> [Redis 클러스터] [게임 서버 B] --세션--> [Redis 클러스터] [게임 서버 N] --세션--> [Redis 클러스터] -> 어떤 서버든 세션 공유 -> 서버 추가/삭제 자유 -> 로드밸런서가 분배

3. 언제 서버를 늘려?

CPU 80%면 늘리면 돼?

여러 기준을 조합해야 해:

# AWS Auto Scaling 정책 예시 { "PolicyName": "scale-out-policy", "PolicyType": "TargetTrackingScaling", "TargetTrackingConfiguration": { "PredefinedMetricSpecification": { "PredefinedMetricType": "ASGAverageCPUUtilization" }, "TargetValue": 70.0 } }
메트릭 Scale Out (확장) Scale In (축소)
CPU > 70% (5분 지속) < 30% (15분 지속)
메모리 > 80% < 40%
CCU > 5,000/서버 < 1,000/서버
응답시간 > 100ms -
급하게 늘려야 할 때는?

예약 스케일링 사용:

# 쿠버네티스 KEDA (이벤트 기반 스케일링) apiVersion: keda.sh/v1alpha1 kind: ScaledObject metadata: name: game-server-scaler spec: scaleTargetRef: name: game-server minReplicaCount: 2 maxReplicaCount: 100 triggers: # 동시 접속자 기반 - type: prometheus metadata: serverAddress: http://prometheus:9090 metricName: game_ccu threshold: "5000" query: game_ccu # 예약 스케일링 (이벤트 시간) - type: cron metadata: timezone: Asia/Seoul start: 0 19 * * 6-0 # 주말 저녁 7시 end: 0 23 * * 6-0 # 주말 밤 11시 desiredReplicas: "50"

4. 게임 트래픽은 어떤 패턴이야?

일반 웹 서비스와 다른 점이 있어?
게임 트래픽 특성: [일반 패턴] - 새벽: 최저 (1x) - 점심: 중간 (3x) - 저녁: 피크 (10x) - 주말: 평일의 1.5배 [이벤트 패턴] - 신규 업데이트: 2~3배 폭증 - 이벤트 시작: 5배 폭증 - 복귀 이벤트: 3배 폭증 [특이 패턴] - 출퇴근 시간 급증 (모바일) - 자정 던전 리셋: 순간 폭증 - 서버 점검 후 복귀: 폭증
예측 불가능한 트래픽은?
실제 사례: 유튜버 효과

- 인기 유튜버가 갑자기 게임 방송 시작
- 30분 만에 CCU 5배 증가
- 오토스케일링이 따라가지 못함!

해결책:
- 최소 인스턴스 여유 유지
- 빠른 스케일 아웃 (Warm Pool)
- 큐 시스템으로 입장 대기

5. 더 아끼려면?

예약 인스턴스가 뭐야?
유형 비용 용도
On-Demand 100% 피크 대응 (유동적)
Reserved 30~75% 할인 기본 서버 (항상 필요)
Spot 90% 할인 배치 작업, 테스트
Savings Plans 최대 72% 할인 장기 약정
조합 전략은?
비용 최적화 전략: 기본 트래픽 (항상 유지): - Reserved Instance 10대 - 비용: $300/월 (75% 할인) 피크 대응 (탄력적): - On-Demand Auto Scaling - 최대 40대 (피크 시) - 비용: 사용한 만큼 테스트 서버: - Spot Instance - 90% 할인 - 언제든 종료될 수 있음 총 비용: - Before: 50대 On-Demand = $5,000/월 - After: 10 Reserved + Auto = $1,500/월 - 절감: 70%!

6. 실제로 어떻게 구현해?

AWS에서 설정하려면?
# Terraform으로 Auto Scaling Group 설정 resource "aws_autoscaling_group" "game_server" { name = "game-server-asg" vpc_zone_identifier = var.subnet_ids target_group_arns = [aws_lb_target_group.game.arn] min_size = 2 # 최소 2대 max_size = 100 # 최대 100대 desired_capacity = 5 # 기본 5대 launch_template { id = aws_launch_template.game_server.id version = "$Latest" } # 헬스체크 health_check_type = "ELB" health_check_grace_period = 300 # 인스턴스 교체 전략 instance_refresh { strategy = "Rolling" preferences { min_healthy_percentage = 90 } } tag { key = "Name" value = "game-server" propagate_at_launch = true } } # CPU 기반 스케일링 정책 resource "aws_autoscaling_policy" "scale_out" { name = "scale-out" autoscaling_group_name = aws_autoscaling_group.game_server.name policy_type = "TargetTrackingScaling" target_tracking_configuration { predefined_metric_specification { predefined_metric_type = "ASGAverageCPUUtilization" } target_value = 70.0 } }
쿠버네티스에서는?
# HPA (Horizontal Pod Autoscaler) apiVersion: autoscaling/v2 kind: HorizontalPodAutoscaler metadata: name: game-server-hpa spec: scaleTargetRef: apiVersion: apps/v1 kind: Deployment name: game-server minReplicas: 2 maxReplicas: 100 metrics: # CPU 기반 - type: Resource resource: name: cpu target: type: Utilization averageUtilization: 70 # 커스텀 메트릭 (CCU) - type: Pods pods: metric: name: game_ccu_per_pod target: type: AverageValue averageValue: "5000" behavior: scaleUp: stabilizationWindowSeconds: 60 policies: - type: Percent value: 100 # 100% 증가 가능 periodSeconds: 60 scaleDown: stabilizationWindowSeconds: 300 # 5분 안정화 policies: - type: Percent value: 10 # 10%씩 감소 periodSeconds: 60

핵심 정리: Auto Scaling

  • 수평 스케일링 - 서버 수를 늘리고 줄임 (Scale Out/In)
  • Stateless 설계 - 세션은 외부 저장소 (Redis)에
  • 스케일링 정책 - CPU, 메모리, CCU, 응답시간 조합
  • 예약 스케일링 - 이벤트/피크 시간 미리 설정
  • 비용 최적화 - Reserved + On-Demand + Spot 조합
  • 결과 - 서버 비용 50~85% 절감
