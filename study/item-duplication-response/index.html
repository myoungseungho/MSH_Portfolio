아이템이 복제됐다! 서버 개발자는 뭘 먼저 할까?

아이템 복제 사고 대응 - 기술보다 순서가 중요하다

시니어는 코드부터 안 본다

아이템 복제 버그 신고가 들어왔어. 뭐부터 해야 해?

주니어는 이렇게 생각해:

"코드부터 보자. 어디서 버그가 터진 거지?"

그거 맞는 말인데, 순서가 틀렸어.

코드를 고치는 데는 1시간이 걸릴 수도, 하루가 걸릴 수도 있어. 그런데 그 사이에 복제는 계속되고 있어.

비유: 수도관 터짐

수도관이 터져서 물이 콸콸 쏟아지고 있어. 이때 "파이프 재질이 뭐였지?" 분석부터 하는 사람은 없지. 먼저 밸브를 잠가.

아이템 복제도 똑같아. 원인 분석보다 출혈 차단이 먼저야.

시니어의 사고 순서는 이래:

1. 차단 → 2. 조사 → 3. 복구 → 4. 재발 방지

코드 수정은 4단계에서야 의미가 있어. 먼저 피를 멈춰야 수술하지.

즉시 대응 (5분 이내)

그럼 구체적으로 5분 안에 뭘 해야 해?

3단계야. 빠르게 가자.

Step 1. 재현 경로 확인

"어떤 행동을 하면 복제되는지"를 파악해.

유저 신고 내용, CS팀 전달 사항, 커뮤니티 글을 즉시 확인.

신고 내용 예시: "거래소에 아이템 등록하고 바로 취소하면 아이템이 2개가 됩니다" → 재현 경로: 거래소 등록 → 즉시 취소 → 관련 기능: 거래소 시스템

Step 2. 해당 기능 비활성화

거래소에서 터졌으면? 거래소를 막아.

트레이드에서 터졌으면? 트레이드를 막아.

우편함이면? 우편함을 막아.

서버를 내려야 하는 거야?

서버 전체를 내리는 건 최후의 수단이야.

잘 설계된 서버라면 기능 단위로 끌 수 있어. 그게 바로 Feature Flag (피처 플래그)야.

Feature Flag가 뭐야?

정의: 코드 배포 없이 특정 기능을 켜거나 끌 수 있는 스위치. 서버 설정값 하나로 "거래소 ON/OFF" 같은 제어가 가능해.

왜 필요: 버그가 터졌을 때 서버를 내리지 않고 해당 기능만 즉시 차단하려고.

안 쓰면: 거래소 버그 하나 때문에 서버 전체를 긴급 점검해야 해. 수만 명이 동시에 쫓겨남.

// Feature Flag 예시 (서버 설정) { "trade_enabled": true, "auction_enabled": false, // ← 거래소만 긴급 OFF "mail_enabled": true, "guild_bank_enabled": true } // 서버 코드 if (!config.auction_enabled) { return Error("거래소 점검 중입니다"); }

Feature Flag가 없으면? 기능 단위 차단이 불가능해.

그때는 어쩔 수 없이 긴급 점검을 걸어야 해. 서버 전체를 내리는 거야.

Step 3. 복제 경로 차단 확인

기능을 껐으면, 실제로 복제가 더 이상 발생하지 않는지 확인해.

로그를 실시간으로 보면서 "같은 패턴의 복제 로그가 더 찍히는지" 체크.

여기까지가 5분 안에 끝나야 하는 일이야.

"기능 단위 비활성화가 가능한 서버 구조인지"가 이미 설계 수준을 보여줘.

사고가 터진 뒤에야 Feature Flag의 소중함을 알게 되지.

조사 (수 시간)

차단했어. 이제 뭐 해?

이제 피해 규모를 파악해야 해.

누가, 언제, 얼마나 복제했는지. 그리고 그게 얼마나 퍼졌는지.

어떻게 알아내?

로그로 알아내. 아이템 생성/삭제/이동 로그, 거래 로그, 골드 로그.

이 로그가 없으면? 사실상 눈감고 수술하는 거야.

-- 1단계: 같은 아이템 ID가 2개 이상 존재하는 케이스 추출 SELECT item_id, COUNT(*) as cnt FROM inventory_log WHERE item_id IN ( SELECT item_id FROM items GROUP BY item_id HAVING COUNT(*) >= 2 ) GROUP BY item_id ORDER BY cnt DESC;
-- 2단계: 복제 아이템 보유자 + 시간대 확인 SELECT user_id, item_id, action_type, created_at FROM inventory_log WHERE item_id IN (/* 위에서 추출한 복제 아이템 ID 목록 */) ORDER BY created_at;
복제된 아이템이 거래소에서 팔렸으면?

그게 바로 2차 피해야. 조사해야 할 범위가 확 넓어져.

영향 범위 체크리스트: 1차: 복제 아이템 자체 → 누가 복제했고, 몇 개나 있는지 2차: 거래소/트레이드를 통해 다른 유저에게 넘어갔는가? → A가 복제 → 거래소에 등록 → B가 구매 3차: 골드로 환전됐는가? → B가 복제 아이템을 NPC에게 판매 → 골드 증가 → 그 골드로 또 다른 아이템 구매 추적 깊이가 깊어질수록 복구 난이도가 급상승

복구 선택지 A: 수술적 롤백

조사 끝났어. 이제 어떻게 복구해?

선택지가 3개 있어. 상황에 따라 골라야 해.

먼저 가장 정밀한 방법부터 보자.

Surgical Rollback (수술적 롤백)이 뭐야?

정의: 복제에 관여한 유저만 골라서, 그 유저의 데이터를 복제 이전 시점으로 되돌리는 것.

왜 필요: 정상적으로 플레이한 유저에게 피해를 주지 않으려고.

안 쓰면: 복제범 한 명 때문에 서버 전체를 롤백해야 해. 수만 명의 정상 플레이가 날아감.

수술적 롤백 (Surgical Rollback)

복제 관여 유저만 특정 시점으로 롤백


강점: 정상 유저에게 피해가 없음. 가장 이상적인 복구.

약점: 거래 체인 추적이 기하급수적으로 복잡해짐.

거래 체인이 왜 복잡해?

A가 복제한 아이템을 B에게 팔았어. B는 그걸 C에게 팔았어.

A를 롤백하면? A 인벤토리는 복구됨.

근데 B가 가진 아이템은? C가 가진 아이템은?

A → B → C → D... 체인이 길어질수록 추적이 기하급수적으로 복잡해져.

A (복제범) → 거래소에 검 등록 → B가 1000골드에 구매 → B가 그 검을 강화 → B가 강화된 검을 C에게 트레이드 → C가 그 검을 NPC에게 판매 (골드 획득) 이 상태에서 "A만 롤백"하면? → A의 골드 1000은 회수해야 하나? → B의 강화 비용은? → C가 NPC에게 받은 골드는? → 전부 추적해서 하나하나 되돌려야 함

수술적 롤백의 전제 조건: 아이템 생성/이동/거래 로그가 완벽해야 해.

로그에 빈 구간이 있으면 추적 자체가 불가능해.

복구 선택지 B: 전체 롤백

수술적 롤백이 너무 복잡하면?

서버 전체를 복제 발생 이전 시점으로 되돌리는 거야.

DB 백업 시점으로 전체 데이터를 덮어씀.

전체 롤백 (Full Rollback)

서버 전체를 복제 이전 시점으로 롤백


강점: 확실하고 깔끔. 복제 아이템이 100% 사라짐.

약점: 정상 유저의 플레이도 전부 날아감. 유저 이탈의 직접적 원인.

"아니, 나는 아무 잘못도 안 했는데 왜 3시간 플레이가 날아가?"

이 불만이 쏟아져. 전체 롤백은 유저 신뢰를 심각하게 훼손해.

그럼 언제 전체 롤백을 해?

복제 규모가 너무 커서 수술적 롤백이 물리적으로 불가능할 때만.

예를 들어:

복제 아이템이 이미 수천 개 유통됨.

거래 체인이 수백 명에게 퍼짐.

경제 전체가 오염됨.

이 정도면 "전체 롤백 + 보상"이 차라리 피해가 적어.

복구 선택지 C: 복제분만 회수 + 경제 보정

롤백 말고 다른 방법은 없어?

있어. 복제된 아이템만 삭제하고, 경제는 서서히 회복시키는 방법이야.

복제분 회수 + 경제 보정

복제된 아이템만 삭제, 유통된 골드는 점진적으로 흡수


강점: 서비스 중단이 최소화됨. 정상 유저 체감 피해가 적음.

약점: "정당하게 샀는데 왜 뺏어가냐" 민원 발생 가능.

구체적으로 어떻게 해?

1단계: 복제 아이템 삭제

아이템 생성 로그를 기반으로 "비정상 경로로 생성된 아이템"을 특정해서 삭제.

2단계: 유통된 골드 흡수

복제 아이템이 골드로 변환된 양을 추정하고, 게임 내 경제 시스템으로 점진적 흡수.

골드 흡수 방법 (골드 싱크): 1. NPC 상점 수리비 일시적 인상 2. 강화 비용 이벤트 (골드 소모 유도) 3. 한정 코스메틱 골드 판매 (자발적 소비 유도) 4. 세금/수수료 일시 인상 → 유저가 "이벤트네!" 하고 자연스럽게 참여하면서 초과 골드가 빠짐
근데 거래소에서 정당하게 산 사람한테서 아이템을 뺏으면 문제 아니야?

맞아. 이게 이 방법의 가장 큰 리스크야.

"나는 정가 주고 샀는데?" → 이런 유저에게는 골드 환불 + 사과 보상을 따로 해야 해.

민원 대응까지 세트로 준비해야 하는 방법이야.

적합한 상황: 복제 규모가 작거나 중간이고, 빠르게 발견했을 때.

퍼진 범위가 좁으면 회수 + 보정이 가장 현실적인 선택이야.

복구 선택지 비교

3가지 방법을 한눈에 비교하면?
A. 수술적 롤백 B. 전체 롤백 C. 회수 + 경제 보정
방법 관여 유저만 롤백 서버 전체 롤백 복제분 삭제 + 골드 흡수
정상 유저 피해 없음 큼 (플레이 날아감) 적음 (구매자 보상 필요)
서비스 중단 없음 ~ 짧음 긴 점검 필요 없음 ~ 짧음
필요 조건 완벽한 로그 DB 백업 생성 로그 + 경제 모니터링
복잡도 매우 높음 낮음 중간
적합 상황 소규모, 로그 완벽할 때 대규모, 경제 오염 심각할 때 소~중규모, 빨리 발견했을 때

실무에서는 C를 먼저 시도하고, 안 되면 A, 그래도 안 되면 B 순서가 일반적이야.

전체 롤백은 진짜 최후의 수단이야.

재발 방지 - 사고 이후가 진짜 중요하다

복구 끝났어. 이제 뭘 해야 해?

같은 사고가 다시 터지지 않게 막아야지.

그리고 더 중요한 건, 다음 사고가 터져도 더 빠르게 대응할 수 있는 구조를 만드는 거야.

구체적으로?

1. 아이템 수량 정합성 체크를 상시 가동

서버 틱이나 배치 작업으로 "같은 아이템 ID가 2개 이상 존재하는지" 주기적으로 검사해.

// 배치 잡: 매 5분마다 실행 SELECT item_id, COUNT(*) as cnt FROM player_inventory GROUP BY item_id HAVING COUNT(*) >= 2; // 결과가 있으면 → 즉시 알림 (Slack/PagerDuty) // "아이템 복제 의심 감지: item_id=38291, count=3"

2. 로그 시스템 점검

이번 사고에서 로그가 부족했던 부분이 있었나? 있었다면 보강.

아이템의 생성/이동/삭제/거래 전 생애주기가 로그에 남아야 해.

3. Feature Flag 시스템이 없었다면 구축

이번에 서버 전체를 내려야 했다면, 다음엔 기능 단위로 끌 수 있게.

핵심 교훈:

"이 버그의 대응 품질은 사고 순간이 아니라, 로그 시스템을 설계한 시점에 이미 결정된다."

로그가 없으면 수술적 롤백은 불가능해. 전체 롤백밖에 방법이 없어.

Feature Flag가 없으면 5분 안에 차단할 수 없어. 긴급 점검밖에 방법이 없어.

대응 능력은 사고 전에 이미 갖춰져 있어야 해.

핵심 정리: 아이템 복제 사고 대응

  • 차단이 먼저 - 코드 수정보다 출혈 차단이 우선. 복제가 계속되는 동안 분석하면 피해만 커짐
  • Feature Flag - 기능 단위 비활성화가 가능해야 함. 없으면 서버 전체를 내려야 함
  • 수술적 롤백 - 정밀하지만 로그 품질에 전적으로 의존. 로그 없으면 불가능
  • 전체 롤백 - 확실하지만 최후의 수단. 정상 유저 피해가 너무 큼
  • 대응 품질 - 사고 순간이 아니라 로그와 시스템을 설계한 시점에 이미 결정됨
