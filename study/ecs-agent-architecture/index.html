AI가 100% 짠 서버, 인간이 유지보수할 수 있을까?

ECS + AI 에이전트로 MMORPG 서버를 만들 때, 블랙박스 리스크와 해법

Part 1. 대전제 — 인간은 더 이상 구현하지 않는다

좀 급진적이긴 한데... 구현은 이제 AI가 다 한다고 보면 안 돼?

급진적이지만, 방향은 맞아. 이미 일어나고 있는 일이거든.

[구현자의 변화 — 실제 일어나고 있는 흐름] 2005년: 인간 10명이 서버 코드를 짠다 2015년: 인간 10명 + Stack Overflow 복붙 2023년: 인간 5명 + Copilot (자동완성) 2025년: 인간 2명 + AI 에이전트 (분석/구현/빌드 자동화) 2026년: 인간 1명(감독) + AI 에이전트 팀 → 인간의 역할: 구현자 → 감독자 → 의사결정자 → 구현의 주체: 인간 → AI 에이전트
그럼 OOP가 인간한테 유리했던 이유가 뭐야?

OOP는 "인간의 사고방식"에 맞춰서 만들어진 거야.

[OOP가 인간에게 직관적인 이유] 현실 세계의 사고: "플레이어는 체력이 있고, 인벤토리가 있고, 스킬을 쓸 수 있어" OOP로 표현: class CGamePC { int hp; // 체력 Item inventory[100]; // 인벤토리 void UseSkill(int id); // 스킬 사용 }; → 현실의 "사물"과 1:1 대응 → "플레이어 = CGamePC" — 직관적! → 인간이 "아, 이게 플레이어구나" 바로 이해
근데 이게 AI한테는 안 맞다고?

맞아. 이전 문서에서 봤듯이, OOP 코드는 "거대 클래스 + 암묵적 의존성"으로 흘러가거든.

CGamePC 하나가 3,000줄이 되면, 인간은 경험으로 "대충 어디 있는지" 알지만 AI는 전부 읽어야 해.

Part 2. ECS가 뭔데?

ECS가 뭐야? 엄청난 라이브러리가 필요한 거야?

아니, 그냥 "방식"이야. 라이브러리 없이도 만들 수 있어.

3가지 개념만 알면 돼:

[ECS의 3가지 개념] E = Entity (엔티티) → 그냥 "번호표". ID 하나. → 플레이어든 몬스터든 NPC든, 전부 그냥 번호. → Entity 42 = 플레이어일 수도, 몬스터일 수도 있음 C = Component (컴포넌트) → "데이터 덩어리". 로직 없음. 그냥 값만 들어있음. → HealthComponent = { hp: 100, maxHp: 200 } → PositionComponent = { x: 150, y: 300, mapId: 5 } S = System (시스템) → "로직". 데이터를 처리하는 함수. → CombatSystem: HealthComponent가 있는 엔티티들의 전투 처리 → MovementSystem: PositionComponent가 있는 엔티티들의 이동 처리
OOP랑 뭐가 달라? 비유로 설명해봐
[비유: 회사 조직 구조] OOP = 부서별 조직 ┌─────────────┐ │ 영업부 │ ← 영업 사원 + 영업 데이터 + 영업 로직 │ (전부 한 곳) │ 이 부서가 뭘 하는지 알려면 │ │ 부서 전체를 파악해야 함 └─────────────┘ → "영업부에 가면 영업에 관한 모든 게 있어" → 직관적이지만, 부서가 커지면 파악 어려움 ECS = 기능별 분리 [사원 명단] ← Entity (번호표만) [급여 테이블] ← Component (데이터만) [출석 테이블] ← Component (데이터만) [급여 계산기] ← System (로직만) → 사원 42번의 급여? → 급여 테이블에서 42번 찾기 → 급여 계산 로직? → 급여 계산기만 보면 됨 → 각 테이블이 작고, 독립적
MMORPG 서버에서 구체적으로 어떻게 생겨?
[OOP 방식의 MMORPG 플레이어] class CGamePC { // 기본 정보 (50줄) int level, exp, hp, mp, ...; // 전투 관련 (200줄) int attackPower, defense, ...; void Attack(CGamePC* target); void TakeDamage(int amount); void UseSkill(int skillId); // 인벤토리 (300줄) Item inventory[200]; void AddItem(Item item); void RemoveItem(int slot); // 퀘스트 (200줄) Quest quests[50]; void AcceptQuest(int questId); void CompleteQuest(int questId); // 던전 (150줄) // 길드 (200줄) // 거래 (150줄) // ... 총 3,000줄+ };
[ECS 방식의 MMORPG 플레이어] // Entity = 그냥 번호 Entity player = world.CreateEntity(); // Entity 42 // Component = 작은 데이터 덩어리 (각각 10~30줄) struct HealthComponent { int hp; int maxHp; }; struct CombatComponent { int attack; int defense; }; struct PositionComponent { float x; float y; int mapId; }; struct InventoryComponent { vector<Item> items; int maxSlots; }; struct QuestComponent { vector<Quest> active; }; struct DungeonComponent { int currentId; int clearCount; }; // 플레이어에게 필요한 컴포넌트 "붙이기" player.add<HealthComponent>(100, 200); player.add<CombatComponent>(50, 30); player.add<PositionComponent>(0, 0, 1); player.add<InventoryComponent>(); player.add<QuestComponent>(); // 몬스터? 컴포넌트 조합만 다르면 됨 Entity monster = world.CreateEntity(); monster.add<HealthComponent>(500, 500); monster.add<CombatComponent>(80, 50); monster.add<PositionComponent>(100, 200, 1); // → 인벤토리 없음, 퀘스트 없음 = 안 붙이면 그만
ECS에서 로직은 어디 있어?

System에 있어. 컴포넌트에는 데이터만, 시스템에는 로직만.

[System = 로직 담당] // 전투 시스템 — HealthComponent + CombatComponent가 있는 엔티티만 처리 class CombatSystem { void ProcessAttack(Entity attacker, Entity target) { auto& atk = attacker.get<CombatComponent>(); auto& hp = target.get<HealthComponent>(); int damage = atk.attack - target.get<CombatComponent>().defense; hp.hp -= max(1, damage); } }; // 이동 시스템 — PositionComponent가 있는 엔티티만 처리 class MovementSystem { void ProcessMove(Entity entity, float dx, float dy) { auto& pos = entity.get<PositionComponent>(); pos.x += dx; pos.y += dy; } }; 핵심: → CombatSystem은 전투"만" 알면 됨 → MovementSystem은 이동"만" 알면 됨 → 서로 모름. 독립적.

Part 3. AI 에이전트한테 왜 ECS가 압도적으로 유리해?

구체적으로 AI가 ECS를 다룰 때 뭐가 좋아?
AI 작업 OOP (CGamePC 3,000줄) ECS (컴포넌트 20줄씩)
"전투 로직 수정해줘" CGamePC.h 3,000줄 읽기 → Attack() 찾기 → 관련 멤버변수 파악 → 다른 함수 영향 확인 CombatSystem.cpp 한 파일(200줄) + CombatComponent(10줄) 읽기 끝
"새 시스템 추가해줘" CGamePC에 멤버 추가 + 여러 핸들러에 분산 작성 + 기존 코드 영향 확인 새 Component 파일 + 새 System 파일 생성. 기존 코드 터치 0
"이 기능 테스트해줘" CGamePC 전체 생성해야 테스트 가능 (의존성 덩어리) 컴포넌트만 만들고 시스템 함수만 호출 (독립 테스트)
"영향 범위 분석해줘" 전역 상태, 싱글턴 추적 → 분석 에이전트 3개 필요 System이 어떤 Component를 참조하는지 = 첫 줄에 드러남
숫자로 차이가 얼마나 나?
[AI 작업 효율 비교 — 실측 기반 추정] "던전 시스템 추가" 작업: OOP 구조: 분석: CGamePC + GameMsg + DungeonMgr + Protocol + ... (10개 파일) 읽기: 약 15,000줄 수정: 8개 파일 터치 테스트: 서버 8개 기동 후 수동 확인 → 에이전트 토큰 소모: ~150,000 토큰 → 예상 시간: 1~2시간 ECS 구조: 분석: DungeonComponent + DungeonSystem + MANIFEST (3개 파일) 읽기: 약 500줄 수정: 2개 파일 생성 (기존 파일 수정 0) 테스트: 단위 테스트 자동 실행 → 에이전트 토큰 소모: ~15,000 토큰 (1/10) → 예상 시간: 10~15분 차이: 약 10배

핵심 통찰

ECS의 러닝커브가 높았던 건 "인간이 직접 구현해야 했기 때문"이다.

인간에게 "Entity 42에 CombatComponent를 붙인다"는 표현은 비직관적이다.

하지만 AI에게는? 패턴이 명확하고, 파일이 작고, 의존성이 명시적이니까 이상적인 구조다.

구현을 AI에게 맡기는 순간, ECS의 러닝커브 문제는 사라진다.

Part 4. 그런데... 블랙박스가 되면?

AI가 100% 구현한 ECS 서버가 있어. 인간은 감독만 했어. 그런데 어느 날 AI가 없어지면? 인간이 이걸 유지보수할 수 있어?

이건 기우가 아니야. 진짜 리스크야.

근데 정확히 어떤 상황이 위험한지를 짚어야 해. "AI가 짰으니까 위험하다"가 아니라, "불투명하게 짰으니까 위험하다"가 핵심이거든.

[블랙박스의 진짜 의미] 블랙박스 ≠ "AI가 짠 코드" 블랙박스 = "왜 이렇게 되어 있는지 아무도 모르는 코드" 사실, 인간이 짠 코드도 블랙박스가 될 수 있어: 인간 블랙박스 예시 (실제로 흔함): → 10년 전 퇴사한 개발자가 짠 코드 → 주석 없음, 문서 없음, 변수명이 a, b, c → "건드리면 안 돼. 왜 되는지는 나도 몰라." → 이것도 블랙박스야! 핵심 질문: "누가 짰느냐"가 아니라 "읽을 수 있느냐"가 블랙박스를 결정한다.
그럼 AI가 짠 코드가 블랙박스가 되는 구체적 시나리오가 뭐야?

3가지 시나리오가 있어:

[위험 시나리오 1: "영리한" 코드] AI가 성능 최적화를 위해 인간이 읽기 어려운 코드를 짬: // AI가 짠 "최적화된" 전투 시스템 void ProcessCombat(EntityPool& pool) { auto view = pool.view<Health, Combat, Position>(); std::for_each(std::execution::par_unseq, view.begin(), view.end(), [&](auto entity) { auto [h, c, p] = view.get(entity); auto targets = spatial_hash.query(p.x, p.y, c.range); std::transform(targets.begin(), targets.end(), damage_buffer.begin(), [&](auto t) { return calc_dmg(c, pool.get<Combat>(t)); }); // ... 초고속이지만 인간이 읽을 수 없는 코드 }); } → 잘 돌아가. 성능도 좋아. → 근데 버그가 나면? 인간이 이걸 디버깅할 수 있어?
[위험 시나리오 2: 맥락 소실] AI가 "왜" 이렇게 짰는지를 기록하지 않음: // 5레벨 이하는 데미지 0 처리 if (attacker.level <= 5) damage = 0; → 왜 5레벨? 기획서 때문? 버그 회피? 임시 코드? → AI한테 물어보면? "이전 세션이라 기억 못 합니다" → 인간이 판단할 근거가 없음
[위험 시나리오 3: 구조적 복잡성 폭발] AI가 "자기만의 패턴"으로 일관성 없이 코드를 짬: features/ ├── dungeon/ → AI 에이전트 A가 짬 (패턴 A) ├── quest/ → AI 에이전트 B가 짬 (패턴 B) ├── combat/ → AI 에이전트 A가 짬 (패턴 A) ├── guild/ → AI 에이전트 C가 짬 (패턴 C) └── market/ → AI 에이전트 B가 짬 (패턴 B) → 3가지 다른 패턴이 섞여있음 → 인간이 보면: "이 프로젝트에 규칙이 있긴 한 거야?"
그럼 진짜 위험하잖아. OOP로 하는 게 낫지 않아?

잠깐. 여기서 중요한 걸 놓치면 안 돼.

블랙박스 리스크는 OOP든 ECS든 똑같이 존재해.

질문을 바꿔야 해. "OOP vs ECS" 가 아니라, "블랙박스가 될 확률이 어디가 더 낮은가?"

블랙박스 요인 OOP ECS
파일 크기 3,000줄 클래스 → 전체 파악 어려움 20줄 컴포넌트 → 한눈에 파악
의존성 싱글턴, 전역 → 숨겨진 연결 System 선언부에 명시
한 기능 범위 5~10개 파일에 분산 1 Component + 1 System
독립 테스트 전체 객체 생성 필요 컴포넌트만으로 테스트 가능
코드 "느낌" 인간에게 직관적 규칙적이고 기계적

ECS는 구조 자체가 블랙박스를 방지하는 장치야.

컴포넌트는 20줄이라 "읽으면 끝"이고, 시스템은 "어떤 컴포넌트를 쓰는지" 선언부에 드러나니까.

다만, 위 3가지 시나리오(영리한 코드, 맥락 소실, 패턴 불일치)는 ECS에서도 발생할 수 있어. 이걸 막는 게 핵심이야.

Part 5. 해법 — 블랙박스가 아니라 "글래스박스"

블랙박스를 막으려면 어떻게 해야 해?

"글래스박스(Glass Box)" 원칙을 적용해.

안이 훤히 보이는 상자. AI가 만들었지만, 인간이 열어보면 다 이해할 수 있는 구조.

[글래스박스 원칙 — AI에게 주는 3가지 제약] 제약 1: "단순하게 짜라" (No Clever Code) → 성능 최적화보다 가독성 우선 → for문 > 함수형 체이닝 → 명시적 > 암시적 → "인턴이 읽을 수 있는 수준"으로 제약 2: "왜를 기록하라" (Always Document Why) → 모든 비자명한 결정에 주석 → "// 5레벨 이하는 튜토리얼 구간이라 데미지 0 (기획서 v2.3)" → MANIFEST.yaml에 설계 의도 기록 제약 3: "한 가지 패턴만 써라" (One Pattern Only) → 프로젝트 전체에 동일한 패턴 강제 → AI가 어떤 모듈을 짜든 같은 구조 → 하나를 읽으면 전부 읽을 수 있음
구체적으로 어떻게 적용해?
[제약 1 적용: 단순한 코드 vs 영리한 코드] ❌ AI가 짤 수 있는 "영리한" 코드: auto targets = spatial_hash.query(p.x, p.y, c.range) | std::views::filter([](auto e) { return e.alive(); }) | std::views::transform([&](auto e) { return calc(e); }); ✅ 글래스박스 원칙으로 제약된 코드: // 범위 내 적 찾기 auto targets = FindEntitiesInRange(pos.x, pos.y, combat.range); // 살아있는 적만 필터 for (auto& target : targets) { if (!IsAlive(target)) continue; // 데미지 계산 int damage = CalcDamage(attacker, target); ApplyDamage(target, damage); } → 둘 다 같은 결과 → 아래가 느릴 수 있음 (마이크로초 차이) → 하지만 인간이 읽을 수 있음
[제약 2 적용: "왜"를 기록] // ❌ 맥락 없는 코드 if (level <= 5) damage = 0; // ✅ 글래스박스 — 왜를 기록 // 튜토리얼 구간(1~5레벨)에서는 데미지 0 // → 신규 유저 이탈 방지 목적 (기획팀 요청 2024-06) // → 6레벨부터 정상 전투 활성화 if (level <= TUTORIAL_MAX_LEVEL) { damage = 0; }
[제약 3 적용: 모든 모듈이 동일한 패턴] features/ ├── dungeon/ │ ├── MANIFEST.yaml ← 설명서 (항상 같은 구조) │ ├── components.h ← 데이터 정의 (항상 같은 구조) │ ├── system.cpp ← 로직 (항상 같은 구조) │ ├── handlers.cpp ← 메시지 처리 (항상 같은 구조) │ └── tests/ ← 테스트 (항상 같은 구조) │ ├── quest/ ← 완전히 동일한 구조! │ ├── MANIFEST.yaml │ ├── components.h │ ├── system.cpp │ ├── handlers.cpp │ └── tests/ │ └── combat/ ← 완전히 동일한 구조! ├── MANIFEST.yaml ├── components.h ├── system.cpp ├── handlers.cpp └── tests/ → 인간이 dungeon/ 하나만 이해하면 → quest/, combat/, guild/ 전부 같은 방식으로 읽을 수 있음 → "이 프로젝트의 패턴은 이거구나" 5분 만에 파악
이 제약을 AI가 지키게 하려면?

두 가지 방법이 있어:

[방법 1: 프롬프트 제약 — AI의 "헌법"] CONVENTIONS.md (프로젝트 루트): "모든 Component는 30줄 이하" "모든 System 함수는 for문으로만 반복" "모든 조건문에 // 이유 주석 필수" "새 모듈은 반드시 template/ 폴더 구조를 복사" → AI 에이전트가 이 파일을 읽고 따름 → 위반 시 리뷰어 에이전트가 걸러냄
[방법 2: 자동 검증 — 기계적 강제] // CI/CD에서 자동 체크 lint_rules: max_file_lines: 500 # 500줄 초과 → 빌드 실패 max_component_lines: 30 # 컴포넌트 30줄 초과 → 경고 require_why_comments: true # if문에 주석 없으면 → 경고 structure_check: template/ # 폴더 구조 불일치 → 빌드 실패 → AI가 "영리한 코드"를 짜도 → 자동으로 걸림 → 인간이 검토 안 해도 → 기계가 제약을 강제

Part 6. 비상 탈출구 — AI 없이 인간만으로 복구 가능한가?

최악의 시나리오: AI 서비스가 전면 중단됨. 인간 개발자만으로 이 서버를 유지보수해야 해. 가능해?

이건 진짜 핵심 질문이야. 결론부터 말하면:

글래스박스 원칙을 지킨 ECS 코드는, 인간도 유지보수할 수 있어.

심지어 OOP보다 더 쉬울 수도 있어. 왜냐면:

[인간이 글래스박스 ECS를 유지보수할 때] 장점 1: 파일이 작다 → 컴포넌트 20줄, 시스템 200줄 → "이 파일 뭐하는 건지" 5분이면 파악 → OOP의 3,000줄 클래스보다 훨씬 접근하기 쉬움 장점 2: 패턴이 동일하다 → dungeon/ 하나 이해하면 나머지 전부 같은 구조 → "아, 모든 모듈이 이 패턴이구나" → 온보딩 1시간 → OOP는 파일마다 다를 수 있음 장점 3: 테스트가 있다 → 코드 수정 후 테스트 돌리면 → 맞는지 바로 확인 → "이거 고쳤는데 다른 데 안 깨지겠지?" → 테스트가 답해줌 장점 4: MANIFEST가 있다 → "이 모듈이 뭘 하고, 뭘 의존하는지" 한 파일에 정리 → OOP에서 "선배한테 물어봐야 알던 것"이 문서에 있음

역설적 결론

AI가 글래스박스 원칙으로 짠 ECS 코드는, 20년 된 인간 OOP 코드보다 인간이 유지보수하기 더 쉬울 수 있다.

왜? "잘 짜인 코드"이기 때문이다. AI는 피곤해서 대충 짜지 않고, 제약을 주면 100% 지킨다.

인간이 못 지킨 "일관성", "문서화", "테스트"를 AI는 지킬 수 있다.

Part 7. 그래도 남는 진짜 리스크

그럼 우려가 완전히 기우야?

아니. 기우가 아닌 부분이 있어. 글래스박스로 해결되지 않는 리스크가 2가지 있어:

[진짜 리스크 1: 시스템 간 상호작용의 창발적 복잡성] 개별 System은 단순해: CombatSystem: 데미지 계산 (200줄) BuffSystem: 버프 적용 (150줄) SkillSystem: 스킬 발동 (250줄) QuestSystem: 퀘스트 진행 (200줄) → 각각은 간단해. 인간이 읽을 수 있어. 하지만 조합되면? 스킬 발동 → 버프 적용 → 데미지 변경 → 퀘스트 완료 조건 충족 → 이 "흐름"을 이해하려면 4개 System을 연결해서 봐야 함 → ECS에서 이 흐름은 "명시적으로 코드에 없음" → 런타임에 컴포넌트 조합으로 "발생"하는 거 → 부품은 투명한데, 조립 결과가 예측 어려울 수 있음
[진짜 리스크 2: "의도"의 소실] AI가 코드를 짤 때, 인간의 "의도"를 100% 이해했는지 보장 안 됨: 인간: "플레이어가 죽으면 인벤토리 아이템 일부를 떨어뜨려" AI: "OK" → 구현함 3개월 후, 다른 인간이 봄: "왜 죽으면 아이템을 떨어뜨리지?" "기획 의도가 뭐였지?" "이거 벌칙이야? 밸런스야? PvP 때문이야?" → AI는 "시키는 대로 했을 뿐" → "왜"는 인간(감독자)의 머릿속에만 있었음 → 감독자가 바뀌면 → 의도 소실
이건 어떻게 해결해?

완벽한 해결은 없어. 하지만 완화할 수 있어:

[완화책 1: 상호작용 맵 — 창발적 복잡성 대응] _meta/interaction-map.yaml: dungeon_enter: trigger: "플레이어가 던전 입장" flow: 1. DungeonSystem.Enter() → DungeonComponent 변경 2. PartySystem.Notify() → 파티원에게 알림 3. QuestSystem.Check() → "던전 입장" 퀘스트 체크 4. BuffSystem.Apply() → 던전 버프 적용 → System 간 "흐름"을 명시적으로 문서화 → 런타임 조합을 인간이 예측할 수 있게 → AI가 새 기능 추가할 때마다 이 맵도 업데이트
[완화책 2: 의사결정 로그 — 의도 소실 대응] _meta/decisions/ ├── 2024-06-death-penalty.md │ 제목: 사망 시 아이템 드랍 │ 의도: PK 리스크 부여 (PvP 밸런스) │ 결정자: 기획팀 김OO │ 근거: 유저 설문 결과 "긴장감이 부족하다" 78% │ 구현: DeathSystem + InventorySystem │ ├── 2024-07-tutorial-guard.md │ 제목: 튜토리얼 구간 무적 │ 의도: 신규 유저 이탈 방지 │ ... → "왜"를 코드가 아니라 별도 문서에 기록 → 감독자가 바뀌어도 의도가 남아있음

AGI 이전 시대의 현실적 원칙

AI에게 100% 맡기되, 인간이 0%를 이해하면 안 된다.

구현: AI 100% → OK

이해: 인간이 "읽으면 이해할 수 있는" 수준 → 필수

의도: 인간이 "왜 이렇게 했는지" 기록 → 필수

검증: 테스트로 "맞게 동작하는지" 확인 → 필수

"AI가 짓고, 인간이 감리하는 건물" — 건물을 직접 짓진 않지만, 설계도를 읽고 안전 검사는 할 수 있어야 한다.

핵심 정리

  • 대전제 — 구현은 AI가 한다. 인간은 감독한다. 이 방향은 이미 진행 중
  • ECS가 AI에 유리한 이유 — 파일이 작고(20줄), 독립적이고, 패턴이 동일하고, 테스트가 쉬움
  • 러닝커브 역전 — ECS가 어려웠던 건 인간이 구현해야 했기 때문. AI가 구현하면 문제 사라짐
  • 블랙박스 우려는 기우가 아니다 — "영리한 코드", "맥락 소실", "패턴 불일치" 3가지 리스크 존재
  • 글래스박스 원칙 — 단순하게 짜라 + 왜를 기록하라 + 한 패턴만 써라
  • 역설 — 글래스박스 ECS가 20년 된 OOP보다 인간이 유지보수하기 더 쉬울 수 있음
  • 진짜 리스크 — 시스템 간 창발적 복잡성 + 의도 소실. 완벽한 해결 없음, 완화만 가능
  • AGI 이전 원칙 — AI가 짓고, 인간이 감리한다. 설계도를 읽을 수 있어야 한다
