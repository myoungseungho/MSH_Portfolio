메모장 저장이랑 DB 저장이 똑같을까? — 데이터가 디스크에 눕는 법

파일과 무엇이 같고 무엇이 다른가 — 8KB 페이지·힙·클러스터드·B-Tree, 그리고 '왜 그냥 파일이 아닌가'

30초 요약

DB 데이터도 결국 디스크의 '파일'이야(.mdf 등). 메모장 .txt처럼 파일은 파일이지.

다른 점 4가지: ① 8KB 페이지 단위로 잘라 저장(통째 X) ② 정렬/색인(B-Tree)으로 안 훑고 찾음 ③ 여러 명 동시 접근 안전 ④ 죽어도 복구(로그).

즉 '검색·동시성·안전'을 위해 파일 위에 특수 포맷과 규칙을 얹은 게 DB야.

Part 1. DB도 결국 '파일'이야 — 근데 열어보면?

DB에 저장한 데이터도, 알고 보면 디스크 어딘가 파일로 있는 거야?

응, 맞아. MSSQL이면 .mdf 파일 하나에 테이블·행이 다 들어있어. 메모장 .txt가 디스크에 있는 것과 똑같이, DB 파일도 그냥 디스크의 파일이야. 여기까진 완전히 같아.

그럼 그 .mdf 파일을 메모장으로 열면 내 데이터가 보여?

안 보여. 열면 알아볼 수 없는 깨진 이진 덩어리가 나와. 바로 여기서 메모장 파일과 DB 파일이 갈라져.

둘 다 '파일'이지만 내부를 채우는 방식(포맷)이 완전히 달라. 메모장은 글자를 그냥 순서대로 죽 늘어놓지만, DB는 특수한 규칙으로 채워. 그 규칙이 뭔지가 이 글의 전부야 — 크게 4가지 차이가 있어.

같은 '파일', 다른 '내부' [메모장 hello.txt] [DB users.mdf] ┌──────────────┐ ┌──────────────┐ │ 안녕 반가워 │ │ ▓8KB▓ ▓8KB▓ │ ← 페이지로 잘림 │ 오늘 날씨... │ │ ▓8KB▓ ▓8KB▓ │ │ (글자 죽 나열) │ │ + B-Tree 색인 │ ← 찾기용 색인 └──────────────┘ │ + 트랜잭션 로그│ ← 복구용 통째로 읽음 └──────────────┘ 필요한 페이지만

Part 2. 차이① — 통째로 vs 8KB 페이지 단위

메모장은 파일을 어떻게 다뤄?

메모장은 파일을 열면 통째로 메모리에 다 올려. 한 글자만 바꿔도 파일 전체를 다시 저장하고. 파일이 작으니 괜찮지.

Q. 근데 DB 파일이 100GB면? 메모장식으로 하면?

A. 유저 한 명 조회하자고 100GB를 통째로 메모리에 올려야 해. 말이 안 되지.

그래서 DB는 어떻게 해?

파일을 8KB짜리 '페이지'로 잘게 잘라 관리해. 데이터를 읽고 쓰는 최소 단위가 이 페이지야. 유저 한 명이 필요하면 그 유저가 든 페이지 몇 개만 콕 집어 읽어.

예측해봐 — 100GB 테이블에서 유저 1명 찾으면 디스크에서 얼마를 읽을까? '수십 GB?' 아니. 단 몇 개의 8KB 페이지 = 수십 KB야. 아래에서 직접 비교해봐.

Part 3. 차이② — 순서 없이 쌓기(힙) vs 정렬(클러스터드)

메모장에서 특정 단어를 찾으려면?

Ctrl+F로 처음부터 끝까지 훑어. 글자가 쓴 순서대로 죽 나열돼 있을 뿐, 정렬돼 있지 않으니까.

DB도 아무 설정 없으면 비슷해. 이걸 힙(Heap)이라 불러 — 행을 빈자리에 그냥 던져넣어(순서 없음). INSERT는 빠르지만, 특정 행 찾으려면 전부 훑어(풀 스캔).

그럼 정렬해두면?

행을 키(예: id) 순서대로 정렬된 상태로 저장하는 게 클러스터드 인덱스야. 전화번호부처럼 정렬돼 있으니 'ㄱ~ㄷ은 앞쪽'하고 확 좁힐 수 있어.

Q. 그럼 항상 클러스터드가 좋아?

A. 검색은 빠른데, 정렬을 유지하려면 중간에 INSERT할 때 자리를 만들어야 해(페이지 분할). 공짜는 없어. 아래에서 힙 vs 클러스터드로 42를 찾아봐.

Part 4. 차이③ — B-Tree라는 초강력 색인

정렬돼 있어도 100만 행이면 이진탐색도 20번인데, DB는 어떻게 3번 만에 찾아?

B-Tree라는 트리 색인 덕분이야. 이진탐색은 갈래가 2개뿐이지만, B-Tree는 한 노드에서 수백 갈래로 쫙 퍼져.

동작은 초딩 버전으로: 루트에서 "42는 30~60 사이네" → 그 갈래로. 다음 노드에서 "40~50 사이" → 그 갈래로. 몇 단계 만에 잎(실제 페이지)에 도착해. 갈래가 넓으니 100만 행도 3~4단계면 끝이야.

그게 왜 그렇게 빠른 거야? 숫자로?

한 노드가 400갈래라고 하면: 1단계 400개, 2단계 16만, 3단계 6400만 개를 커버해. 즉 6400만 행을 단 3번의 페이지 읽기로 도달. 메모장엔 이런 색인이 아예 없어서 항상 전체 스캔이지.

Part 5. 차이④ — 그냥 파일 안 쓰고 왜 DB를 쓰나

검색이 빠른 건 알겠어. 근데 그게 다야?

아니, 두 개가 더 있어. 동시 접근과 안전.

메모장 파일을 두 사람이 동시에 저장하면? 한쪽이 통째로 덮어써서 한 명 작업이 통째로 날아가(앞에서 본 레이스 컨디션!). DB는 트랜잭션·락으로 '동시에 만져도 안 깨지게' 조율해.

안전은? 저장 중 정전되면?

메모장은 저장 중 정전이면 파일이 반만 써지거나 깨져. 복구 수단이 없어.

DB는 '바꾸기 전에 로그에 먼저 적어두는'(WAL) 규칙이 있어서, 죽었다 살아나도 로그를 보고 정확히 그 시점으로 복구해. (이건 다음 주제 — 로깅·복구에서 깊게)

정리하면: 검색·동시성·안전 이 세 가지 때문에, '그냥 파일' 위에 특수 포맷과 규칙을 얹은 게 DB야.

핵심 — 메모장 파일 vs DB, 같다/다르다

항목 메모장 파일 DB 파일
디스크의 파일인가 ✅ 그렇다 ✅ 그렇다 (.mdf 등)
읽는 단위 통째로 전부 8KB 페이지 단위
정렬/색인 없음 (Ctrl+F 전체 훑기) B-Tree 색인 (몇 단계로 도달)
동시에 여럿이 쓰기 덮어써서 유실 트랜잭션·락으로 조율
저장 중 죽으면 깨짐·반쪽 저장 로그(WAL)로 복구
내부 포맷 글자 나열 페이지+색인+로그 구조

핵심 정리

  • DB 데이터도 디스크의 파일이다 — 여기까진 메모장과 같다.
  • 차이①: 통째로가 아니라 8KB 페이지 단위로 잘라 필요한 것만 읽는다.
  • 차이②: 힙(순서 없이 쌓기) vs 클러스터드(정렬 저장) — 검색 속도가 갈린다.
  • 차이③: B-Tree 색인으로 100만 행도 3~4번 페이지 읽기로 찾는다(전체 스캔 아님).
  • 차이④: 동시 접근 조율(트랜잭션·락) + 죽어도 복구(WAL) — 파일엔 없는 규칙.
  • = DB는 '검색·동시성·안전'을 위해 파일 위에 특수 포맷을 얹은 것.
