채팅 서버를 왜 게임 서버랑 분리할까?

게임 채팅 서버 설계 - 채널마다 다른 전략이 필요한 이유

채널별 특성이 완전히 다르다

채팅이 그냥 메시지 보내고 받는 건데 뭐가 어렵다고?

얼핏 보면 단순해 보이지. "A가 메시지 보내면 B한테 전달" 끝 아닌가?

근데 잘 생각해봐. 게임 채팅에는 종류가 여러 개야.

귓속말, 파티, 길드, 지역, 전체... 이 채널들이 전부 메시지를 전달하는 방식이 다르다는 게 핵심이야.

채널 수신 범위 메시지 빈도 특성
귓속말 1:1 낮음 대상이 다른 서버에 있을 수 있음
파티 4~8명 중간 같은 서버일 가능성 높음
길드 수십~수백 명 중간 멤버가 여러 서버에 분산
지역 AOI 내 유저 높음 게임 서버가 이미 알고 있음
전체 전 서버 낮아야 함 브로드캐스트

보이지? 채널마다 "누구한테 보내야 하는지"가 전혀 다르다.

지역 채팅은 게임 서버가 AOI (Area of Interest, 관심 영역) 정보를 이미 갖고 있으니까 바로 처리할 수 있어.

근데 길드 채팅은? 길드원이 서버 1, 서버 3, 서버 7에 흩어져 있으면 어떻게 전달해?

하나의 방식으로 모든 채널을 처리하면 반드시 문제가 생겨.

선택지 A - 게임 서버에 내장

별도 서버 없이 게임 서버가 채팅까지 처리하면 안 돼?

당연히 가능해. 사실 가장 단순한 방법이야.

비유: 식당 직원이 서빙도 하고 계산도 하는 구조

작은 식당이면 직원 한 명이 주문받고, 서빙하고, 계산까지 다 해도 돼.
근데 손님이 100명 넘어가면? 직원이 과부하 걸리지.
게임 서버가 채팅까지 처리하는 건 이 "만능 직원" 방식이야.

지역 채팅 / 파티 채팅:

게임 서버는 이미 AOI 정보랑 파티 멤버 목록을 알고 있어.

그냥 "내 주변 유저들한테 메시지 뿌려" 하면 끝.

별도 인프라 없이 자연스럽게 처리됨.

길드 채팅 / 귓속말 (크로스 서버):

이게 문제야. 상대가 다른 게임 서버에 있으면?

게임 서버끼리 직접 메시지를 전달해야 해.

[게임 서버 1] ──귓속말──→ [게임 서버 3] │ │ └──길드 채팅──→ [게임 서버 5] │ [게임 서버 7] ←── 길드 채팅 서버가 10대면? 서버 간 연결이 최대 10 x 9 = 90개 서버가 50대면? 50 x 49 = 2,450개

강점: 추가 인프라 불필요. 지역 채팅은 AOI와 동일 구조라 자연스러움.

약점: 크로스 서버 채팅 시 서버 간 연결이 폭발적으로 증가. 게임 로직에 채팅 부하까지 추가됨.

적합: 소규모 게임, 서버 10대 이하.

선택지 B - 전용 채팅 서버 + Pub/Sub

Pub/Sub이 뭐야?

정의: Pub/Sub (Publish/Subscribe) = 발행/구독 패턴. 메시지를 보내는 쪽(Publisher)과 받는 쪽(Subscriber)이 서로를 직접 몰라도 되는 메시지 전달 방식.

왜 필요: 서버 10대가 서로 직접 연결하면 연결이 90개. 중간에 "메시지 브로커"를 하나 두면 각 서버는 브로커 하나만 연결하면 됨. 연결 수가 N x (N-1)에서 N으로 줄어든다.

안 쓰면: 서버가 늘어날 때마다 서버 간 연결이 기하급수적으로 증가하고, "이 메시지를 누구한테 보내야 하지?"를 매번 직접 관리해야 해.

비유: 유튜브 구독 알림

유튜버(Publisher)가 영상을 올리면, 구독자(Subscriber) 전원한테 알림이 감.
유튜버는 구독자가 누군지 일일이 몰라도 돼. 유튜브(브로커)가 알아서 전달해줌.
Pub/Sub도 똑같아. 메시지 보내는 쪽은 "guild:1234 채널에 발행"만 하면, 그 채널을 구독한 모든 서버가 받아.
구체적으로 어떻게 동작해?

전용 채팅 서버를 따로 두고, 게임 서버들과 채팅 서버 사이에 Redis Pub/Sub을 끼워 넣어.

[게임 서버 1] ─┐ [게임 서버 2] ─┤ [게임 서버 3] ─┼─→ [Redis Pub/Sub] ─→ [채팅 서버] ─→ 클라이언트 [게임 서버 4] ─┤ [게임 서버 5] ─┘ 길드 채팅 예시: 1. 유저 A가 길드 채팅에 "안녕" 입력 2. 게임 서버 1 → Redis 채널 "guild:1234"에 발행(publish) 3. 채팅 서버가 "guild:1234"를 구독(subscribe) 중 4. 채팅 서버 → 해당 길드원 전원에게 메시지 전달

길드원이 로그인하면 → 채팅 서버가 "guild:1234" 채널을 구독.

누군가 메시지를 보내면 → Redis가 구독 중인 모든 채팅 서버에 전파.

채팅 서버가 해당 길드원 클라이언트에 전달.

강점: 게임 서버와 완전 분리. 채팅 서버만 따로 스케일 가능. Pub/Sub 덕분에 크로스 서버 채팅이 자연스러움.

약점: Redis Pub/Sub은 메시지 유실 가능. 구독 시점 이전 메시지는 못 받아. 채팅 히스토리도 저장 안 됨.

적합: 메시지 유실이 괜찮은 일반 채팅. 대부분의 게임 채팅은 이 정도면 충분.

선택지 C - 메시지 큐 기반 (Kafka / RabbitMQ)

메시지 큐 (Message Queue)가 뭐야? Pub/Sub이랑 뭐가 달라?

정의: 메시지 큐 (Message Queue) = 메시지를 대기열에 저장해뒀다가 소비자가 가져가는 방식. 메시지가 디스크에 기록되기 때문에 유실되지 않아.

왜 필요: Pub/Sub은 "지금 듣고 있는 사람"한테만 전달하지만, 메시지 큐는 "지금 없어도 나중에 접속하면 밀린 메시지를 받을 수 있어."

안 쓰면: 오프라인이었던 유저가 접속했을 때 "내가 없는 동안 길드 채팅에 뭐 올라왔지?" 를 알 수 없어. 히스토리도 날아가.

구체적으로 어떻게 달라?

Kafka나 RabbitMQ 같은 메시지 큐를 브로커로 사용해.

[게임 서버] ─→ Kafka topic: "chat.guild.1234" ─→ [채팅 서버] ─→ 클라이언트 Pub/Sub과의 핵심 차이: - Pub/Sub: 메시지가 흘러가면 끝. 저장 안 됨. - Kafka: 메시지가 디스크에 저장됨. 나중에 다시 읽을 수 있음. 오프라인 유저 시나리오: 1. 유저 B가 오후 3시에 로그아웃 2. 오후 3시~5시 사이 길드 채팅 50개 발생 3. 유저 B가 오후 5시에 로그인 4. Kafka: "네가 마지막으로 읽은 건 offset 120이야. 121~170 보내줄게" 5. 유저 B: 밀린 메시지 50개 수신

강점: 메시지 영속성. 히스토리 자동 저장. 오프라인이었다 접속해도 밀린 메시지 수신. 메시지 순서 보장.

약점: 레이턴시가 ms 단위로 추가됨. 실시간 격투/FPS 채팅에는 과할 수 있음. 인프라가 Kafka 클러스터 + 설정까지 필요해서 복잡함.

적합: 히스토리가 중요하거나, 오프라인 메시지가 필요한 게임. 모바일 RPG, 소셜 기능이 강한 게임.

시니어의 답 - 채널마다 다르게 써라

그래서 셋 중에 뭘 골라야 해?

정답: "하나만 고르지 마. 채널마다 다르게 써."

채널별 최적 전략: [지역 채팅 / 파티 채팅] → 게임 서버가 AOI / 파티 정보로 직접 처리 → 추가 인프라 불필요. 가장 빠름. [길드 채팅 / 귓속말] (크로스 서버) → 별도 채팅 서버 + Redis Pub/Sub → 게임 서버 부하 없이 크로스 서버 전달 [전체 채팅] → 쿨타임 제한 (5초에 1번) + 채팅 서버 브로드캐스트 → 스팸 방지 필수 [채팅 히스토리] → MongoDB 등에 비동기 저장 → 채팅 서버가 메시지 전달하면서 동시에 DB에 기록

지역/파티는 게임 서버가 이미 정보를 갖고 있으니까 거기서 바로 처리하는 게 빨라.

길드/귓속말처럼 서버를 넘나드는 채팅만 별도 채팅 서버로 빼.

전체 채팅은 쿨타임을 안 걸면 서버가 죽어. 5초에 1번 정도로 제한.

히스토리는 실시간 전달과 별개로 비동기로 DB에 저장하면 돼.

핵심 원칙:

"모든 채팅을 하나의 방식으로 처리하지 않는 것."

채널의 특성(수신 범위, 빈도, 크로스 서버 여부)에 맞춰 전략을 나눠야 확장 가능한 구조가 된다.

3가지 선택지 비교

A. 게임 서버 내장 B. 채팅 서버 + Pub/Sub C. 메시지 큐 (Kafka)
구현 복잡도 낮음 중간 높음
크로스 서버 서버 간 직접 연결 (연결 폭발) Pub/Sub으로 자연스러움 토픽 기반으로 자연스러움
히스토리 별도 구현 필요 별도 구현 필요 자동 저장 (디스크)
레이턴시 가장 빠름 (같은 프로세스) 빠름 (Redis 경유) 약간 지연 (ms 단위)
적합 규모 소규모 (서버 10대 이하) 중~대규모 대규모 + 히스토리 필수

실무에서는 B를 기본으로 깔고, 지역/파티만 A 방식을 섞는 하이브리드가 가장 흔해.

히스토리가 꼭 필요하면 Kafka를 쓰기보다는 B 방식에 비동기 DB 저장을 추가하는 경우가 더 많아.

용어 사전

용어 뜻
AOI (Area of Interest) 관심 영역. 내 주변 일정 반경만 동기화하는 기법.
Pub/Sub (Publish/Subscribe) 발행/구독. 보내는 쪽과 받는 쪽이 직접 연결 없이 중간 브로커를 통해 메시지를 전달하는 패턴.
메시지 큐 (Message Queue) 메시지를 대기열에 저장해뒀다가 소비자가 꺼내가는 방식. 유실 방지, 순서 보장.
Redis 인메모리 데이터 저장소. Pub/Sub 기능을 내장하고 있어 실시간 메시지 전달에 많이 사용.
Kafka 분산 메시지 큐 시스템. 메시지를 디스크에 저장하며 대용량 처리에 특화.
브로드캐스트 (Broadcast) 모든 대상에게 동시에 메시지를 보내는 것. 전체 채팅이 대표적.

핵심 정리: 게임 채팅 서버 설계

  • 채널별 전파 방식이 다르다 - 귓속말/파티/길드/지역/전체, 각각 수신 범위와 빈도가 전혀 다름
  • 지역/파티 = 게임 서버 직접 처리 - AOI, 파티 정보를 이미 알고 있으므로 추가 인프라 불필요
  • 길드/귓속말 = 별도 채팅 서버 + Pub/Sub - 크로스 서버 메시지 전달을 브로커가 처리
  • 히스토리 = 메시지 큐 또는 비동기 DB 저장 - 오프라인 유저를 위한 메시지 보관
  • 핵심 원칙 = 모든 채팅을 하나의 방식으로 처리하지 않는다 - 채널 특성에 맞춰 전략을 나누는 것이 정답
