← AI 활용

AI가 도구를 만들고, 테스트하고, 눈으로 확인까지 한다고?

AI 풀사이클 도구 개발 — 구현부터 시각적 검증까지 인간 없이 돌아가는 루프

Part 0. 전제 — 사람이 도구를 만드는 과정을 먼저 보자

개발자 도구를 하나 만든다고 치자. 사람은 어떤 과정을 거쳐?

예를 들어 "DB에서 캐릭터 정보를 조회하는 웹 도구"를 만든다고 해볼게.

[사람이 도구를 만드는 5단계] 1단계: 설계 "캐릭터 이름 치면 인벤토리 보여주는 페이지 만들자" → 머릿속으로 구상 2단계: 구현 (코딩) → HTML 짜고, API 만들고, DB 연결하고... → 2~3일 걸림 3단계: 기능 테스트 → "검색 버튼 누르면 결과 나오나?" 직접 클릭해서 확인 → "없는 캐릭터 치면 에러 안 나나?" 직접 쳐봄 4단계: 시각적 확인 → "테이블이 깨지지 않았나?" 눈으로 확인 → "버튼 위치가 이상하지 않나?" 눈으로 확인 → "모바일에서도 괜찮나?" 직접 열어봄 5단계: 실제 사용 → 일주일 써보면서 "아 이건 불편하네" 발견 → 수정 → 다시 테스트 → 반복 핵심: 3~5단계는 전부 "사람이 직접 눈으로 보고 손으로 조작"하는 것. 이 부분을 AI가 대신하면 어떨까?
이 5단계를 전부 AI가 한다고?

각 단계마다 이미 기술이 존재해. 다만 아직 하나로 합쳐진 게 없을 뿐이야.

하나씩 풀어볼게.

[AI 풀사이클의 5단계 미리보기] 1단계: 설계/구현 → Schema-Driven UI (코드 대신 데이터로 UI 생성) 2단계: 부품 격리 → Storybook (레고 블록처럼 하나씩 확인) 3단계: 자동 조작 → Playwright (AI가 사람처럼 클릭/입력) 4단계: 시각 검증 → Multimodal AI (AI가 스크린샷 보고 판단) 5단계: 풀 루프 → 전부 연결 (실패하면 자동 수정 → 재검증) 각각은 별도의 기술이지만, 합치면 "인간 없이 돌아가는 도구 공장"이 된다.

Part 0 핵심

도구 개발에서 코딩은 20%. 나머지 80%는 "보고, 클릭하고, 확인하는 것"이다.

AI가 코딩만 하면 20%만 자동화. 보고 확인하는 것까지 해야 100% 자동화.

Part 1. Schema-Driven UI — "코드 대신 데이터로 UI를 만든다"

보통 웹 UI를 만들려면 HTML, CSS, JavaScript를 직접 짜잖아. 다른 방법이 있어?

비유부터 하나 할게.

[비유: 주문서로 가구 만들기] 방법 1: 목수가 직접 만든다 (전통적 코딩) "서랍장 만들어주세요" → 목수가 나무 자르고, 조립하고, 칠하고... → 목수마다 결과가 다름 → 시간 오래 걸림 방법 2: 주문서를 공장에 넣는다 (Schema-Driven) 주문서: 종류: 서랍장 폭: 80cm 높이: 120cm 서랍 수: 4개 색상: 화이트 → 공장 기계가 주문서 읽고 자동 생산 → 누가 주문서를 써도 같은 품질 → 빠름 "주문서" = Schema (스키마) "공장" = UI Framework
그 "주문서"가 실제로 어떻게 생겼는데?
[실제 Schema 예시 — "캐릭터 검색 폼"] 전통적 방식 (HTML을 직접 작성): <form> <label>캐릭터 이름</label> <input type="text" name="charName" /> <label>서버</label> <select name="server"> <option>1서버</option> <option>2서버</option> </select> <button type="submit">검색</button> </form> → 직접 태그를 하나하나 작성해야 함 Schema-Driven 방식 (데이터만 작성): { "fields": [ { "name": "charName", "label": "캐릭터 이름", "type": "text" }, { "name": "server", "label": "서버", "type": "select", "options": ["1서버", "2서버"] } ], "submit": "검색" } → JSON 데이터만 쓰면, 프레임워크가 자동으로 폼을 그려줌
이게 왜 AI에게 유리한 건데?

여기서 ECS와 같은 원리가 등장해.

[ECS와 Schema-Driven의 공통점] 게임 서버 (ECS): OOP: class Warrior extends Character { ... } → 상속 계층, 숨겨진 로직, AI가 읽기 어렵다 ECS: Entity에 Component(데이터)를 붙이면 System(로직)이 처리 → 데이터가 행동을 결정, AI가 다루기 쉽다 웹 도구 (Schema-Driven): 전통: HTML/CSS/JS를 직접 작성 → 스타일, 레이아웃, 이벤트가 뒤섞임, AI가 실수하기 쉽다 스키마: JSON 데이터를 작성하면 프레임워크가 UI를 생성 → 데이터가 UI를 결정, AI가 다루기 쉽다 공통 원리: "코드(로직)를 짜는 게 아니라, 데이터를 정의하면 결과가 나온다" ECS: Component(데이터) → System이 처리 Schema-Driven: Schema(데이터) → Framework이 렌더링 둘 다 AI는 "데이터만 잘 쓰면 된다"
실제로 이런 도구가 있어?
도구/프레임워크 원리 AI 친화도
JSON Forms JSON Schema → 자동 폼 생성 매우 높음
React Admin 데이터 모델 → 관리자 화면 자동 생성 높음
Retool 드래그&드롭 + 설정 → 내부 도구 보통 (GUI 기반)
Streamlit Python 코드 → 웹 앱 자동 생성 높음

Part 1 핵심

Schema-Driven UI = 코드 대신 데이터(JSON)로 UI를 정의하는 방식.

ECS와 같은 원리: "데이터가 결과를 결정"하니까 AI가 다루기 쉽다.

AI는 HTML/CSS를 짜는 것보다 JSON 구조를 만드는 게 훨씬 정확하다.

Part 2. 컴포넌트 격리 — "레고 블록처럼 하나씩 확인한다"

UI를 만들었으면 테스트해야 하잖아. 근데 웹 앱 전체를 테스트하는 건 복잡하지 않아?

비유를 하나 들어볼게.

[비유: 자동차 검사] 방법 1: 완성차를 도로에서 테스트 (통합 테스트) → 자동차를 조립하고, 도로에 나가서 달려본다 → 문제 발생: "어딘가에서 이상한 소리가 난다" → 뭐가 문제지? 엔진? 바퀴? 서스펜션? 전부 분해해봐야 안다 → 시간 오래 걸리고, 원인 찾기 어렵다 방법 2: 부품별로 따로 검사 (컴포넌트 테스트) → 엔진만 따로 돌려본다 → OK → 바퀴만 따로 굴려본다 → OK → 서스펜션만 따로 눌러본다 → 이상한 소리! 여기다! → 원인을 바로 찾을 수 있다 웹 UI도 똑같다. "전체 페이지"를 테스트하면 → 뭐가 문제인지 모른다 "버튼 하나, 테이블 하나"를 따로 테스트하면 → 바로 알 수 있다
UI 부품을 하나씩 따로 보는 도구가 있어?

Storybook이라는 도구가 정확히 이걸 해.

[Storybook이 하는 일] 일반적인 개발: 전체 앱을 실행해야 버튼 하나를 볼 수 있다 → 로그인 → 메뉴 이동 → 특정 페이지 → 거기에 있는 버튼 확인 → 버튼 하나 보려고 앱 전체를 띄워야 한다 Storybook: 버튼 하나만 독립적으로 렌더링한다 ┌───────────────────────────────┐ │ [검색 버튼] │ ← 이 버튼만 단독으로 표시 │ │ │ 상태 1: 기본 │ → 파란색 버튼 │ 상태 2: 호버 │ → 진한 파란색 │ 상태 3: 비활성 │ → 회색 │ 상태 4: 로딩 중 │ → 스피너 표시 └───────────────────────────────┘ 각 상태를 "스토리"라고 부른다. 버튼의 모든 상태를 한 화면에서 볼 수 있다. 왜 AI에게 유리한가: → 각 상태별로 스크린샷을 찍을 수 있다 → AI가 "이 상태에서 버튼이 올바르게 보이는가?" 판단 가능 → 전체 앱을 안 띄워도 된다 (빠르고 독립적)
잠깐, "상태별로 스크린샷"이라는 게 핵심인 거야?

정확해. 이게 AI 시각 검증의 기반이 돼.

[Storybook + 스크린샷 = AI의 눈] 전통적 시각 테스트 (사람): 개발자가 페이지를 열고 → 눈으로 확인 "버튼이 깨졌나?" → 눈으로 봄 "테이블이 넘치나?" → 눈으로 봄 → 사람이 없으면 확인 불가 Storybook + 스크린샷 (자동): 1. Storybook이 버튼을 렌더링 2. 스크린샷 자동 촬영 → button_default.png 3. 다음에 코드 수정 후 다시 촬영 → button_default_new.png 4. 두 이미지를 비교 → 같으면: OK (아무것도 안 깨짐) → 다르면: "여기가 바뀌었다!" 알려줌 이걸 Visual Regression Testing이라고 한다. "이전 스크린샷과 지금 스크린샷이 같은가?"를 자동으로 비교. 여기에 멀티모달 AI를 붙이면: 단순 비교가 아니라 "이 화면이 의도대로 보이는가?"를 판단할 수 있다. → 이건 Part 4에서 자세히.

Part 2 핵심

Storybook = UI 부품(컴포넌트)을 하나씩 독립적으로 볼 수 있는 도구.

각 상태별로 스크린샷을 찍을 수 있어서, AI가 시각적으로 확인할 수 있는 기반이 된다.

자동차 부품 검사처럼, 전체를 안 띄워도 부품별로 테스트 가능하다.

Part 3. 브라우저 자동화 — "AI가 사람처럼 클릭한다"

UI 부품을 따로 볼 수 있다고 해도, 결국 "전체 앱에서 실제로 동작하는지"도 봐야 하잖아?

맞아. 여기서 브라우저 자동화가 등장해.

핵심은 "사람이 브라우저에서 하는 모든 행동을 코드로 재현하는 것"이야.

[비유: 리모컨으로 조종되는 사람] 사람이 도구를 테스트하는 과정: 1. 브라우저를 연다 2. 주소를 입력한다 3. 검색창에 "홍길동"을 친다 4. 검색 버튼을 누른다 5. 결과가 나오는지 확인한다 6. 없는 이름을 쳐본다 7. 에러 메시지가 나오는지 확인한다 Playwright (브라우저 자동화 도구): 위 과정을 코드로 쓰면, 기계가 대신 해준다. "브라우저 열어" → 열림 "주소 입력해" → 입력됨 "'홍길동' 쳐" → 쳐짐 "검색 버튼 눌러" → 눌림 "결과 있어?" → "네, 3건 있습니다" "스크린샷 찍어" → 찰칵 사람이 안 해도 되고, 밤새 자동으로 반복 가능.
코드로 어떻게 "클릭하고 입력하고"를 시키는 건데?
[Playwright 실제 코드 — 의외로 간단하다] // 사람이 하는 것을 그대로 코드로: 1. 페이지 열기 await page.goto('http://localhost:3000') 2. 검색창에 이름 입력 await page.fill('#search-input', '홍길동') 3. 검색 버튼 클릭 await page.click('#search-button') 4. 결과 테이블이 나타날 때까지 기다림 await page.waitForSelector('.result-table') 5. 결과 행이 있는지 확인 const count = await page.locator('.result-row').count() expect(count).toBeGreaterThan(0) // 0보다 커야 함 6. 스크린샷 촬영 await page.screenshot({ path: 'search_result.png' }) 읽어보면 거의 한국어처럼 읽힌다: "페이지 가서, 검색창 채우고, 버튼 누르고, 테이블 나올 때까지 기다리고, 결과 있는지 확인하고, 스크린샷 찍어라."
이걸 AI가 작성한다고?

맞아. 그리고 이 부분이 AI가 특히 잘하는 영역이야.

[왜 AI가 Playwright 코드를 잘 짜는가] 이유 1: 패턴이 반복적이다 → "이동 → 입력 → 클릭 → 확인"이 모든 테스트의 공통 패턴 → AI는 반복 패턴을 잘 학습함 이유 2: 명세가 명확하다 → "검색 버튼을 누르면 결과가 나와야 한다" → 성공/실패가 확실 (나오면 성공, 안 나오면 실패) → 애매한 판단이 없음 이유 3: 실행 후 바로 결과를 알 수 있다 → 테스트 실행 → 통과/실패 즉시 확인 → AI가 "아 이게 틀렸구나, 수정하자" 할 수 있음 결론: AI에게 "이 도구의 테스트 코드 짜줘"라고 하면 Playwright 테스트를 상당히 정확하게 만들어낸다. → 사람이 클릭해서 확인하던 걸, AI가 짠 코드가 대신 확인
근데 결국 "결과가 나오는가?"만 확인하는 거잖아. "결과가 예쁘게 나오는가?"는 어떻게 해?

정확히 그 지점이야. 기능은 확인되지만, 시각적 결과는 아직 모른다.

이건 다음 Part에서.

Part 3 핵심

Playwright = 사람이 브라우저에서 하는 행동(클릭, 입력, 확인)을 코드로 자동화.

AI가 이 코드를 잘 짜는 이유: 패턴이 반복적 + 성공/실패가 명확 + 바로 확인 가능.

한계: "기능"은 확인하지만, "보이는 모습"은 확인 못 한다.

Part 4. 멀티모달 AI — "AI가 눈으로 본다"

"기능은 되는데 화면이 깨졌다"는 어떻게 잡아? 사람 눈으로만 가능한 거 아니야?

2023년까지는 그랬어. 근데 지금은 AI가 이미지를 "볼 수" 있어.

[비유: 눈 먼 검사관 vs 눈 뜬 검사관] 2023년 이전의 자동 테스트 (눈 먼 검사관): "검색 결과가 3건인지 확인해" → OK (숫자는 셀 수 있다) "결과 테이블이 존재하는지 확인해" → OK (태그는 찾을 수 있다) "테이블이 예쁘게 보이는지 확인해" → ??? (이미지를 못 봄) → 코드 레벨에서는 "데이터 3건 있음"을 확인할 수 있지만, "테이블이 깨져서 글자가 겹치고 있음"은 모른다. 2024년 이후의 멀티모달 AI (눈 뜬 검사관): 스크린샷을 AI에게 보여주면: "이 화면에 테이블이 보이나요?" → "네, 3행 4열 테이블이 보입니다" "글자가 겹치거나 잘린 건 없나요?" → "2번째 열 텍스트가 잘려 있습니다" "전체적으로 정상적인 레이아웃인가요?" → "하단 버튼이 테이블과 겹칩니다" → AI가 "이미지를 이해"할 수 있게 된 것. → 이걸 "멀티모달"이라고 한다 (텍스트 + 이미지를 함께 처리).
멀티모달이 뭔지 더 쉽게 설명해줘.
[멀티모달 = "여러 감각"을 가진 AI] 기존 AI (텍스트만): 입력: 텍스트 → AI → 출력: 텍스트 "이 코드에 버그 있어?" → "3번째 줄에 오타가 있습니다" → 글자만 읽을 수 있다 멀티모달 AI (텍스트 + 이미지): 입력: 텍스트 + 이미지 → AI → 출력: 텍스트 "이 스크린샷에서 문제점을 찾아줘" + [screenshot.png] → "테이블 헤더가 본문과 어긋나 있고, 스크롤바가 2개 보입니다" → 그림을 "볼 수" 있다 누가 할 수 있나: Claude (Anthropic) → 이미지 입력 가능 GPT-4V (OpenAI) → 이미지 입력 가능 Gemini (Google) → 이미지 입력 가능 이미 상용 서비스에서 쓸 수 있는 기술이다.
이걸 도구 테스트에 어떻게 붙이는 건데?
[Playwright + 멀티모달 AI = 완전한 시각 테스트] 흐름: 1. Playwright가 페이지를 열고 동작 수행 → 검색 입력 → 버튼 클릭 → 결과 로딩 2. Playwright가 스크린샷 촬영 → screenshot.png 저장 3. 멀티모달 AI에게 스크린샷 + 질문 전달 "이 스크린샷을 보고 답해줘: 1) 검색 결과 테이블이 정상적으로 보이는가? 2) 글자가 잘리거나 겹치는 곳이 있는가? 3) 버튼과 입력창이 정렬되어 있는가? 4) 에러 메시지가 불필요하게 표시되어 있지 않은가?" 4. AI 응답 "1) 테이블 정상. 3행 표시됨. 2) 이상 없음. 3) 검색 버튼이 입력창보다 약간 아래로 내려가 있음. 4) 에러 메시지 없음." 5. 자동 판정 → 3번에서 문제 발견 → "정렬 이슈" 리포트 생성 → 또는 AI가 직접 CSS 수정 → 재촬영 → 재확인 이전에는 사람이 "눈으로 보고" 판단하던 것을 AI가 "스크린샷을 보고" 판단하는 것으로 바뀐 거야.
이거 진짜 돼? 공상과학 아니고?

이미 되고 있어. 사실 이 기술의 각 조각은 전부 상용화 됐어.

기술 성숙도 설명
Playwright 스크린샷 완전 성숙 모든 브라우저에서 스크린샷 촬영 가능
멀티모달 AI 이미지 이해 상용 가능 Claude, GPT-4V 등이 이미지를 정확히 분석
Visual Regression 완전 성숙 Percy, Chromatic 등이 스크린샷 자동 비교
AI가 수정까지 자동 초기 단계 "문제 발견 → 자동 수정"은 아직 실험적

Part 4 핵심

멀티모달 AI = 이미지를 "볼 수 있는" AI. 스크린샷을 보고 문제를 찾을 수 있다.

Playwright(자동 조작) + 스크린샷 + 멀티모달 AI = "눈이 있는 자동 테스트".

기술은 이미 각각 상용화. 합치는 것만 하면 된다.

Part 5. Computer Use — "AI가 진짜 사람처럼 컴퓨터를 쓴다"

Playwright는 "코드로 브라우저를 조종"하는 거잖아. 근데 사람은 그냥 화면 보고 마우스로 클릭하잖아. AI도 그렇게 할 수 있어?

할 수 있어. Anthropic이 "Computer Use"라는 걸 만들었거든.

[Playwright vs Computer Use — 근본적 차이] Playwright (코드 기반): "id가 'search-button'인 요소를 클릭해" → HTML 구조를 알아야 함 → 코드가 필요함 → 정확하지만, 코드를 짜야 하는 수고가 있음 Computer Use (시각 기반): "화면에 보이는 검색 버튼을 클릭해" → HTML 구조를 몰라도 됨 → 스크린샷을 보고 버튼 위치를 찾아서 클릭 → 사람이 하는 것과 완전히 같은 방식 비유: Playwright = 리모컨으로 TV 조작 (채널 번호를 알아야 함) Computer Use = 화면을 보고 리모컨 없이 터치 (보이는 대로 누름)
이게 도구 테스트에 어떻게 쓰여?
[Computer Use로 도구 테스트하는 시나리오] AI에게 지시: "이 도구를 실행하고, 캐릭터 검색 기능을 테스트해줘" AI가 하는 일: 1. 화면을 본다 (스크린샷) → "검색창과 버튼이 보인다" 2. 검색창을 클릭한다 (마우스 좌표 계산) → 화면에서 검색창의 위치를 찾아서 클릭 3. "홍길동"을 입력한다 (키보드 입력) → 타이핑 4. 검색 버튼을 클릭한다 → 화면에서 "검색" 글자가 있는 버튼을 찾아서 클릭 5. 결과를 확인한다 (스크린샷 다시 촬영) → "테이블이 나왔고, 3건의 결과가 보인다. 레이아웃 정상." 6. 에러 케이스 테스트 → "없는이름123"을 입력하고 검색 → "적절한 에러 메시지가 표시된다. 정상." 전체 과정에서 코드가 한 줄도 필요 없다. 사람이 하는 것과 100% 같은 방식으로 동작한다.
Playwright랑 Computer Use 중에 뭘 써야 해?
비교 Playwright Computer Use
작동 방식 코드로 HTML 요소 조작 화면 보고 마우스/키보드 조작
속도 매우 빠름 느림 (스크린샷 분석 시간)
정확도 매우 높음 (코드 기반) 높음 (가끔 위치 오차)
사전 준비 테스트 코드 작성 필요 자연어 지시만으로 가능
시각 확인 별도 스크린샷 + AI 필요 기본 내장 (보면서 조작)
적합한 상황 반복 테스트 (수백 번) 탐색적 테스트 (처음 써보기)
둘 중 하나만 쓰는 게 아니라, 같이 쓰는 건가?

정확해. 용도가 다르니까 함께 쓰는 게 최적이야.

[최적 조합: Playwright + Computer Use] 단계 1: 구현 직후 — Computer Use → AI가 "사람처럼" 도구를 처음 써본다 → 코드 없이 자연어로: "이 도구를 열고, 기능을 전부 테스트해봐" → 탐색적 테스트 (예상 못한 문제 발견) 단계 2: 안정화 후 — Playwright → 발견된 시나리오를 자동 테스트 코드로 작성 → 매번 코드 수정할 때마다 자동 실행 (회귀 테스트) → 수백 번 반복해도 빠름 비유: Computer Use = 신입 테스터가 처음 써보면서 문제 찾기 Playwright = 숙련 테스터가 체크리스트 들고 매번 확인하기 처음엔 Computer Use로 탐색 → 안정화되면 Playwright로 자동화

Part 5 핵심

Computer Use = AI가 화면을 보고 마우스/키보드로 조작. 코드 없이 사람처럼 사용.

Playwright = 코드 기반 자동화. 빠르고 정확. 반복 테스트에 적합.

최적: Computer Use로 탐색 → Playwright로 자동화. 둘 다 쓴다.

Part 6. 전체 루프 — 합치면 무슨 일이 일어나는가

5개 기술을 전부 합치면 어떻게 돌아가는 건데?

전체 그림을 하나로 엮어볼게.

[AI 풀사이클 도구 개발 — 전체 루프] 인간: "캐릭터 검색 도구 만들어줘" (자연어 요청) │ ↓ [1단계: 설계] Schema-Driven AI가 JSON 스키마 작성 → { fields: [이름, 서버], action: "검색", display: "테이블" } → Framework가 UI 자동 생성 │ ↓ [2단계: 격리] Storybook 각 컴포넌트를 독립 렌더링 → 검색 폼 / 결과 테이블 / 에러 메시지 각각 따로 → 컴포넌트별 스크린샷 촬영 │ ↓ [3단계: 기능 테스트] Playwright 자동 시나리오 실행 → 검색 입력 → 클릭 → 결과 확인 → 빈 입력 → 에러 확인 → 없는 이름 → 에러 메시지 확인 │ ↓ [4단계: 시각 검증] 멀티모달 AI 스크린샷을 보고 판단 → "테이블 정상, 레이아웃 OK, 에러 메시지 색상 적절" │ ↓ [5단계: 탐색 테스트] Computer Use AI가 사람처럼 직접 사용 → "스크롤 내렸더니 하단이 짤린다" (예상 못한 문제 발견) │ ↓ [판정] ├─ 문제 없음 → 완료! 인간에게 보고 └─ 문제 발견 → AI가 코드 수정 → [2단계]로 돌아감 (자동 루프) 인간이 한 것: "캐릭터 검색 도구 만들어줘" (한 문장) AI가 한 것: 설계 → 구현 → 테스트 → 시각 확인 → 수정 → 재검증 (전부)
진짜 이게 된다고? 솔직히 말해봐.

솔직하게 말할게.

[현실 진단 — 2025년 기준] 각 조각의 성숙도: Schema-Driven UI ████████████ 95% ← 완전 성숙 Storybook ████████████ 95% ← 완전 성숙 Playwright ████████████ 95% ← 완전 성숙 멀티모달 AI (Vision) ██████████░░ 85% ← 상용 가능 Computer Use ██████░░░░░░ 50% ← 초기 단계 전체 통합 프레임워크 ██░░░░░░░░░░ 15% ← 아직 없음 핵심: 조각은 다 있다. 퍼즐 피스가 테이블 위에 펼쳐져 있는 상태. 아무도 아직 "이 퍼즐을 완성"하지 않았다. 왜 아직 없나: 1. 멀티모달 AI가 2023년에야 등장 (아직 2년도 안 됨) 2. Computer Use는 2024년에야 등장 (1년도 안 됨) 3. 각 도구의 "접착제"를 만드는 사람이 아직 적음 하지만: 2년 전에는 "AI가 이미지를 본다"는 것 자체가 불가능했다. 1년 전에는 "AI가 마우스를 클릭한다"는 것 자체가 불가능했다. 이 속도면, 통합 프레임워크는 시간 문제다.
그러면 이 통합을 직접 설계하면, 그 자체가 가치 있는 거야?

그렇지. 아무도 아직 안 했으니까.

이 아키텍처를 설계하고, 작동하는 프로토타입을 만들면 그 자체가 포트폴리오이자 기술적 기여야.

Part 6 핵심

5개 기술을 합치면 "인간이 한 문장 말하면, AI가 끝까지 다 하는" 루프가 된다.

각 조각은 이미 존재하지만, 전체를 통합한 프레임워크는 아직 없다.

이걸 설계하는 것 자체가 새로운 가치다.

Part 7. 연결 — 왜 ECS와 같은 원리인가

서버에서 ECS가 AI에 유리했듯이, 이 도구 세계에서도 같은 원리가 적용되는 거야?

정확히 같은 원리야. 전부 하나의 공통점으로 귀결돼.

[공통 원리: "AI가 다루기 쉬운 구조"의 3가지 특성] 특성 1: 데이터와 로직의 분리 ECS: Component(데이터) ↔ System(로직) — 분리됨 Schema-Driven: Schema(데이터) ↔ Framework(로직) — 분리됨 Storybook: Props(데이터) ↔ Component(렌더링) — 분리됨 → AI는 "데이터만 건드리면" 결과가 바뀐다 특성 2: 조합(Composition) ECS: Entity에 Component를 붙이면 기능이 추가됨 Schema-Driven: Schema에 Field를 추가하면 UI가 추가됨 Plugin: Core에 Plugin을 붙이면 기능이 추가됨 → AI는 "추가/제거"만 하면 된다. 상속 계층을 이해할 필요 없다. 특성 3: 명시적 경계 (Explicit Boundary) ECS: System 간 의존성 없음, 독립적 Storybook: 각 컴포넌트가 독립적으로 렌더링 Playwright: 각 테스트가 독립적으로 실행 → AI는 "한 조각"만 이해하면 된다. 전체를 안 봐도 된다.
한 문장으로 요약하면?

"AI가 잘 다루는 구조 = 데이터 중심 + 조합 가능 + 독립적"

이건 서버든 도구든 UI든 전부 같아.

영역 AI에 불리한 구조 AI에 유리한 구조 (ECS 원리)
게임 서버 OOP (깊은 상속, 숨겨진 상태) ECS (데이터+시스템 분리)
UI 구현 HTML/CSS 직접 작성 Schema-Driven (JSON → UI)
UI 테스트 전체 앱 띄워서 눈으로 확인 Storybook (부품별 독립 테스트)
기능 검증 사람이 직접 클릭 Playwright (코드로 자동 조작)
시각 검증 사람이 눈으로 확인 멀티모달 AI (스크린샷 분석)

Part 7 핵심

ECS의 원리는 서버에만 국한되지 않는다. 모든 AI-friendly 구조의 공통 원리다.

핵심 3가지: 데이터 중심 + 조합 가능 + 독립적

이 원리를 알면, 어떤 영역이든 "AI가 잘 다루는 구조"를 설계할 수 있다.

흔한 착각: "AI가 전부 해주니까 설계 안 해도 되겠지?"

아니다. AI가 자동화하는 건 "코딩, 테스트, 시각 확인"이다.

"뭘 만들지"를 결정하는 건 여전히 인간의 몫이다.

명세가 엉망이면 AI가 만든 도구도 엉망이다. "What"을 잘 정의하는 능력이 점점 중요해진다.

핵심 정리

  • 도구 개발의 80%는 "보고 확인하는 것" — 코딩은 20%. AI가 "눈"을 가지면 80%도 자동화 가능
  • Schema-Driven UI — JSON 데이터로 UI를 정의. ECS처럼 "데이터가 결과를 결정"
  • Storybook — UI 부품을 독립적으로 렌더링. 부품별 스크린샷 = AI의 눈에 보이는 단위
  • Playwright — 사람의 클릭/입력을 코드로 자동화. AI가 잘 짜는 영역
  • 멀티모달 AI — 스크린샷을 보고 "화면이 정상인지" 판단. 2023년부터 가능해진 기술
  • Computer Use — AI가 사람처럼 화면 보고 마우스/키보드 조작. 코드 없이 테스트 가능
  • 전체 통합은 아직 없다 — 조각은 전부 있지만 합친 사람이 없다. 기회의 영역
  • ECS와 같은 원리 — 데이터 중심 + 조합 가능 + 독립적 = AI가 잘 다루는 구조의 보편 원리
