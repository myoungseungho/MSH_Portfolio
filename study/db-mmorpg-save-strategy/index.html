뽑기 100번 했더니 서버가 멈췄다

MMORPG 데이터베이스 저장 전략 — 바이너리 덩어리 vs 행 단위 vs 비동기 캐시

Part 1. 인벤토리를 DB에 어떻게 넣어?

캐릭터 인벤토리가 300칸이야. DB에 어떻게 저장해?

방법이 크게 두 가지야.

1번: 300칸을 통째로 바이너리로 묶어서 DB 컬럼 하나에 넣기

2번: 아이템 1개 = DB 행(row) 1개로 따로 저장하기

비유하면 이래.

1번은 서랍 전체를 사진 찍어서 보관하는 거야. 양말 한 짝 바뀌어도 서랍 전체를 다시 찍어야 해.

2번은 물건마다 목록표에 한 줄씩 적어두는 거야. 양말이 바뀌면 그 줄만 고치면 돼.

[ 1세대: 바이너리 덩어리 ] TInventory 테이블: ┌──────────┬──────────┬─────────────────────────┐ │ char_uid │ chunk_id │ items (BINARY 8000byte) │ ├──────────┼──────────┼─────────────────────────┤ │ 12345 │ 0 │ [아이템 1~100번 통째로] │ │ 12345 │ 1 │ [아이템 101~200번 통째로] │ │ 12345 │ 2 │ [아이템 201~300번 통째로] │ └──────────┴──────────┴─────────────────────────┘ → 아이템 1개 바뀌어도 8,000바이트 전체 UPDATE [ 2세대: 행 단위 ] TItem 테이블: ┌──────────┬──────────┬───────┬───────┬─────────┐ │ item_uid │ char_uid │ index │ count │ slot_no │ ├──────────┼──────────┼───────┼───────┼─────────┤ │ 99901 │ 12345 │ 5001 │ 3 │ 1 │ │ 99902 │ 12345 │ 7020 │ 1 │ 2 │ │ 99903 │ 12345 │ 3011 │ 10 │ 3 │ └──────────┴──────────┴───────┴───────┴─────────┘ → 아이템 1개 바뀌면 그 row 1개만 UPDATE (수십 바이트)
당연히 2번이 나은 거 아냐? 왜 1번을 쓰는 거야?

2000년대 한국 MMO 개발 환경을 생각해봐.

DB 서버 성능이 지금보다 훨씬 낮았어. 캐릭터 로그인할 때 SELECT 1번으로 인벤토리 전체를 가져오는 게, SELECT 300번 날리는 것보다 훨씬 빨랐거든.

저장도 마찬가지야. UPDATE 1번이 300번보다 빠르잖아. 그래서 '바이너리 덩어리'가 초기엔 합리적인 선택이었어.

문제는 시간이 지나면서 드러나. 인벤토리가 커지고, 저장 빈도가 늘어나면 한 번에 보내는 양이 감당이 안 되기 시작해.

Part 2. 뽑기 100번에 서버가 왜 멈춰?

바이너리로 저장하면 구체적으로 뭐가 문제야? 숫자로 보여줘.

실제 운영 서버 기준으로 보자.

인벤토리 300칸, 아이템 1개 = 80바이트.

DB에는 100칸씩 3덩어리(chunk)로 저장해.

chunk 1개 = 80바이트 x 100 = 8,000바이트

저장 1회 = chunk 3개 = 24,000바이트 (24KB)

여기에 수집인벤토리, 창고, 캐릭터 정보까지 합치면 저장 1회에 약 70KB 이상이 DB로 날아가.

70KB면 별거 아닌 거 같은데?

1번이면 별거 아니야. 문제는 횟수야.

이 게임에는 '10회 뽑기 상자'가 있어. 상자 1개 쓰면 아이템 11개(10+1)가 나와. 그리고 코드에 이런 로직이 있어:

"레어 등급 이상 아이템이 나오면 → 전체 저장"

뽑기에서 레어가 나올 확률이 꽤 높거든. 그러면:

- 상자 1개 (11번 뽑기) → 저장 5~8회 → 350~560KB

- 상자 10개 (110번 뽑기) → 저장 50~80회 → 3.5~5.6MB

- 상자 100개 (1100번 뽑기) → 저장 500~800회 → 35~56MB

[ 상자 100개 열 때 서버에서 일어나는 일 ] 메인 루프 (싱글스레드): ┌──────────────────────────────────────────────┐ │ 뽑기 1번 → 레어! → SaveDB() → DB 전송 대기 │ │ 뽑기 2번 → 레어! → SaveDB() → DB 전송 대기 │ │ 뽑기 3번 → 일반 → 넘어감 │ │ 뽑기 4번 → 레어! → SaveDB() → DB 전송 대기 │ │ ... │ │ 뽑기 1100번까지 반복 │ └──────────────────────────────────────────────┘ ↑ 이 동안 다른 유저는? 다른 유저 A: "이동할래요" → 대기... 다른 유저 B: "공격할래요" → 대기... 다른 유저 C: "채팅 보낼래요" → 대기... → 전원 화면 멈춤 → 타임아웃 → 재접속
아 그러니까, 1명이 뽑기하면 같은 서버 전체가 멈추는 거야?

맞아. 이 서버는 싱글스레드 메인 루프 구조거든.

게임 로직을 처리하는 스레드가 1개야. 뽑기 처리하느라 DB에 데이터 보내고 응답 기다리는 동안, 그 서버에 접속한 모든 유저의 이동, 전투, 채팅이 전부 멈춰.

비유하면 1차선 도로에 교통경찰 1명인 거야. 한 차가 서류 처리하느라 멈추면 뒤에 줄 선 차들이 전부 꼼짝 못 해.

Part 3. 업계는 이걸 어떻게 풀었어?

다른 게임들은 어떻게 해? 다 이런 문제 겪었을 텐데.

MMORPG DB 저장 방식은 크게 3세대로 나눌 수 있어.

1세대: 바이너리 덩어리 (2000년대 초)

- 리니지1, 뮤 온라인 같은 초기 게임들

- 인벤토리를 바이너리로 통째 저장

2세대: 행 단위 저장 (2010년대)

- WoW, FF14, 메이플스토리

- 아이템 1개 = DB row 1개

3세대: 메모리 캐시 + 비동기 저장 (2020년대)

- 로스트아크, 블레이드앤소울

- Redis 같은 인메모리 캐시를 중간에 두고, DB는 나중에 저장

1세대 바이너리 2세대 행 단위 3세대 비동기 캐시
저장 단위 인벤토리 통째 (24KB) 아이템 1개 (80B) 메모리 → 주기적 flush
아이템 1개 변경 시 24KB 전체 UPDATE 80B UPDATE 1건 메모리만 변경 (0ms)
DB 부하 높음 낮음 매우 낮음
게임루프 블로킹 있음 (치명적) 있음 (경미) 없음
로드 속도 빠름 (SELECT 3건) 보통 (SELECT 300건) 매우 빠름 (Redis)
운영 편의성 나쁨 (바이너리 파싱 필요) 좋음 (SQL로 조회) 좋음
데이터 유실 위험 없음 (즉시 저장) 없음 있음 (캐시 날아가면)
대표 게임 리니지1, 뮤 온라인 WoW, FF14 로아, 블소
WoW나 FF14는 행 단위라서 이런 문제 없는 거야?

훨씬 적어. 뽑기로 아이템 50개 얻어도:

1세대: 70KB x 50회 = 3.5MB

2세대: 80B x 50회 = 4KB

같은 50번 저장인데 데이터 양이 약 900배 차이야.

게다가 행 단위 저장이면 "변경된 아이템만 저장"이 자연스러워. 바이너리는 구조적으로 "부분 저장"이 안 되거든. 300칸 중 1칸이 바뀌어도 300칸 전체를 보내야 해.

Part 4. 3가지 핵심 원칙

세대 구분은 알겠는데, 결국 어떤 원칙을 지켜야 하는 거야?

업계에서 운영하면서 수렴하는 원칙이 3가지야.

원칙 1은?

게임 루프와 DB I/O를 분리하라.

이게 제일 중요해. 게임 루프가 DB 응답을 기다리면 안 돼.

나쁜 구조:

메인루프 → SaveDB() → DB 응답 올 때까지 대기 → 다음 처리

좋은 구조:

메인루프 → "저장해" 큐에 넣기 → 바로 다음 처리

별도 스레드가 큐에서 꺼내서 DB에 저장

비유하면, 편의점 점원이 택배 보내러 우체국에 직접 가는 게 나쁜 구조야. 택배 상자를 옆에 쌓아두고, 택배 기사가 가져가는 게 좋은 구조고.

원칙 2는?

변경분만 저장하라. (Delta Save)

양말 한 짝 바뀌었는데 서랍 전체를 사진 다시 찍지 마.

이걸 구현하려면 dirty flag가 필요해. "이 데이터 바뀌었어"라고 표시해두고, 저장할 때 표시된 것만 저장하는 거야.

바이너리 덩어리 방식에서도 chunk 단위로 dirty flag를 두면 부분 저장이 가능해. 300칸 중 1번 칸이 바뀌면 chunk 0(1~100번)만 저장하고 chunk 1, 2는 건너뛰는 식이야.

원칙 3은?

즉시 저장과 지연 저장을 구분하라.

모든 변경을 즉시 DB에 쓸 필요 없어.

즉시 저장 (반드시 바로 써야 하는 것):

- 현금 결제 (캐시 구매)

- 유저 간 거래

- 우편 발송

→ 돈이 오가는 건 즉시. 유실되면 CS 폭탄이야.

지연 저장 (나중에 써도 되는 것):

- 경험치 변화

- 일반 아이템 획득

- 위치 이동

- 뽑기 결과

→ 메모리에 두고 60초마다 한 번에 저장해도 충분해.

뽑기 결과를 매번 즉시 저장할 이유가 없어. 60초 뒤 정기 저장에 맡기면 돼.

[ 3가지 원칙 적용 전 vs 후 ] 적용 전 (현재): 뽑기 1번 → 전체저장 → DB 대기 → 뽑기 2번 → 전체저장 → DB 대기 → ... |---- 500ms ----|---- 500ms ----|---- 500ms ----| 총 소요: 레어 50번 x 500ms = 25초 (서버 멈춤) 적용 후 (원칙 1+2+3): 뽑기 1~1100번 → 메모리에만 반영 (0.1ms each) → 60초 뒤 정기 저장 시 변경분만 저장 (1회) |-- 110ms --| + |-- 24KB 1회 --| 총 소요: 0.11초 + 저장 1회

Part 5. 근데 저장 안 하면 데이터 날아가잖아?

뽑기 50번째에서 서버가 죽으면 50개 아이템 증발하는 거 아냐?

맞아, 지연 저장의 트레이드오프야. 최대 60초치 데이터가 날아갈 수 있어.

근데 현실적으로 생각해봐.

지금 구조: 즉시 저장하려다가 서버가 매번 멈춰서 재접속이 발생

바꾼 구조: 서버 장애 시 최대 60초치 유실 가능

서버가 1시간에 1번 죽는 것도 심각한 장애야. 그런데 지금은 뽑기 할 때마다 멈추잖아. 발생 확률로 보면 지연 저장이 훨씬 안전한 거야.

캐시 결제처럼 진짜 중요한 건 어떡해?

그래서 즉시/지연을 구분하는 거야.

유저가 3,000원 내고 뽑기 상자를 '샀다'는 기록 → 즉시 저장 (결제 DB)

뽑기 상자를 '열어서 나온 아이템' → 지연 저장 가능

결제 사실은 이미 저장되어 있으니까, 서버가 죽어도 "결제했는데 아이템 안 나왔다"는 로그 대조로 복구할 수 있어. 결제 내역이 날아가는 건 절대 안 되지만, 뽑기 결과는 복구 가능한 데이터야.

3세대 비동기 캐시도 같은 문제 아냐? Redis 날아가면?

그래서 3세대에서는 보통 이중 안전장치를 둬.

1. Redis AOF (Append Only File): 모든 변경을 디스크에 로그로 기록. Redis가 죽어도 로그에서 복구.

2. Write-Ahead Log: DB에 쓰기 전에 변경 내역을 로그 파일에 먼저 기록.

3. 주기적 스냅샷: 5분마다 Redis → DB 전체 동기화.

완벽한 건 아니야. 0.1~1초 정도의 유실 구간은 존재해. 하지만 서버가 멈추는 것보다 이 정도 리스크가 훨씬 낫다는 판단이지.

Part 6. 현실적으로 뭘 할 수 있어?

우리 서버처럼 1세대 구조인데, 당장 뭘 할 수 있어?

구조를 한 번에 바꿀 수 없으니 단계적으로 가는 거야.

단계 방법 효과 수정 범위
즉시 뽑기 루프 안에서 SaveDB 호출 제거. 루프 끝에 1번만 호출 저장 50회 → 1회 (50배 감소) 코드 2~3곳
단기 dirty flag 활성화. 변경된 chunk만 저장 24KB → 8KB (3배 감소) 코드 + SP 수정
중기 인벤토리를 행 단위 저장으로 전환 8KB → 80B (100배 감소) DB 스키마 + SP + 코드 대공사
장기 Redis 캐시 + 비동기 저장 도입 게임루프 블로킹 0 아키텍처 전면 개편
dirty flag가 뭐야? 좀 더 설명해줘.

인벤토리가 chunk 3개로 나뉘어 있잖아.

chunk 0: 1~100번 칸

chunk 1: 101~200번 칸

chunk 2: 201~300번 칸

아이템이 5번 칸에 추가되면 chunk 0에 '바뀌었어' 표시(dirty flag)를 해둬.

저장할 때 dirty flag가 켜진 chunk만 DB에 보내.

5번 칸이 바뀌었는데 chunk 1, 2까지 보낼 필요 없잖아. 24KB → 8KB로 줄어들어.

재미있는 건, 이 게임 코드에 dirty flag가 이미 구현되어 있었는데 주석 처리되어 있었어. 누군가 만들어놓고 켜지 않은 거야.

왜 주석 처리했을까?

추측이지만, dirty flag를 쓰면 '저장 누락' 버그 가능성이 생겨.

flag를 깜빡하고 안 켜면 → 그 변경이 DB에 안 들어감 → 유저 아이템 증발

전체 저장은 무식하지만 안전하거든. "뭐가 바뀌었는지 신경 안 쓰고 다 때려넣으면 되니까." 안정성을 위해 성능을 포기한 선택이야.

하지만 뽑기처럼 대량 저장이 터지는 시점에선 그 트레이드오프가 더 이상 성립 안 돼.

주의사항

바이너리 저장은 구조체가 바뀌면 기존 데이터를 읽을 수 없다. 아이템에 필드 1개 추가하면 전체 마이그레이션이 필요하다.

행 단위 전환 시 기존 바이너리 데이터를 파싱해서 row로 옮기는 마이그레이션 도구가 필요하다.

지연 저장 도입 시, 결제/거래/우편처럼 돈이 오가는 데이터는 반드시 즉시 저장을 유지해야 한다.

dirty flag 사용 시, 아이템을 변경하는 모든 코드 경로에서 flag를 켜는 것을 빠뜨리면 데이터 유실이 발생한다.

생각해볼 질문

채팅 로그도 바이너리로 저장하면 안 될까? 어떤 차이가 있을까?

싱글스레드 서버에서 비동기 저장을 도입하려면 어떤 구조가 필요할까?

인벤토리 300칸이 3000칸으로 늘어나면 각 세대별로 어떤 일이 일어날까?

핵심 정리

  • 1세대(바이너리): 아이템 1개 바뀌어도 인벤토리 전체를 DB에 보냄. 빈도가 낮으면 괜찮지만 뽑기 같은 대량 처리에서 서버가 멈춤.
  • 2세대(행 단위): 아이템 1개 = row 1개. 변경분만 저장 가능. WoW, FF14 등 대부분의 상용 MMO가 사용.
  • 3세대(비동기 캐시): Redis 같은 인메모리 캐시를 두고, DB는 나중에 저장. 게임 루프가 DB 때문에 절대 안 멈춤.
  • 원칙 1: 게임 루프와 DB I/O를 분리하라 — 게임 루프가 DB 응답을 기다리면 안 된다.
  • 원칙 2: 변경분만 저장하라 (Delta Save) — dirty flag로 바뀐 것만 추적.
  • 원칙 3: 즉시 저장과 지연 저장을 구분하라 — 결제는 즉시, 뽑기 결과는 지연 가능.
