서버가 하루에 100MB씩 새고 있다

라이브 서버 메모리 릭 추적 - 느린 릭이 가장 무섭다

느린 릭이 왜 무서운가

서버 메모리가 하루에 100MB씩 올라가고 있어. 3일 뒤면 터질 것 같은데?

메모리가 초당 10MB씩 올라가면? 개발자가 바로 알아챈다. 서버 켜자마자 뻗으니까.

그런데 하루에 100MB? 서버 올린 당일엔 문제없어 보여. 다음 날도 괜찮아 보여. 그러다 3일째 새벽에 조용히 죽는다.

비유: 수도꼭지

수도꼭지에서 물이 콸콸 쏟아지면 바로 알아채고 잠근다.
그런데 1초에 한 방울씩 떨어지면? 며칠 뒤 수도요금 고지서 보고서야 알아챈다.
느린 릭이 바로 이거다. 발견이 늦으니까 무섭다.
OOM이 뭐야?

정의: OOM (Out of Memory) = 메모리 부족. OS가 "너 메모리 다 썼어" 하고 프로세스를 강제 종료시키는 것.

왜 중요: 서버가 OOM으로 죽으면 접속 중인 유저 전원이 튕긴다. 라이브 서비스에서 최악의 사고.

안 잡으면: 서버 메모리가 100% 차면 OS가 프로세스를 kill한다. 정상 종료가 아니라서 저장 안 된 데이터도 날아간다.

서버 메모리 4GB 기준: Day 0: 1.2GB (정상) Day 1: 1.3GB (아직 괜찮아 보임) Day 2: 1.4GB (음...) Day 3: 1.5GB (슬슬 이상한데?) ... Day 28: 4.0GB -> OOM -> 서버 크래시 느린 릭은 이렇게 조용히 다가온다.

Step 1. 릭 확인 & 패턴 분석

메모리가 올라가는 건 알겠는데, 어디서부터 봐야 해?

가장 먼저 할 일: 메모리 사용량을 시간축 그래프로 그려보기.

그래프 모양이 원인을 좁혀준다.

메모리 증가 패턴별 의미: 1) 선형 증가 (직선으로 쭉 올라감) ╱╱╱╱╱╱ -> 일정량이 지속적으로 새는 것 -> 매 요청/매 틱마다 조금씩 새고 있음 2) 계단식 증가 (뚝뚝 올라감) ┌── ┌───┘ ┘ -> 특정 이벤트마다 새는 것 -> 출석 보상? 랭킹 정산? 매치 종료? 3) 특정 시간에만 증가 ──────╱──────────╱────── 18시 18시 -> 해당 시간대 이벤트 확인 -> 매일 18시 = 일일 보상? 길드전 시작?
그래프 모양만 봐도 범인을 좁힐 수 있다고?

맞아. 계단식이면 "어떤 이벤트 때 올라가지?" 를 보면 되고, 선형이면 "항상 실행되는 코드 중에 누수가 있다" 는 뜻이야.

계단식이 오히려 잡기 쉬워. 이벤트 시점이 명확하니까 해당 코드만 집중해서 보면 된다.

Step 2. 라이브에서 추적하는 방법

패턴은 봤어. 이제 정확히 어떤 코드가 새는 건지 어떻게 찾아?

라이브 서버에서 쓸 수 있는 방법 3가지가 있어. 상황에 따라 골라야 한다.

선택지 A: 서버 내장 메모리 추적

Custom Allocator가 뭐야?

정의: Custom Allocator (커스텀 할당자) = 메모리 할당/해제를 직접 감싸서, "누가 얼마나 할당했는지" 기록하는 우리가 만든 할당기.

왜 필요: 기본 malloc/new는 "몇 바이트 할당했다" 밖에 모른다. 커스텀 할당자를 쓰면 "몬스터 시스템이 100MB, 아이템 시스템이 50MB" 식으로 카테고리별 집계가 가능하다.

안 쓰면: 메모리가 새는 건 아는데 어디서 새는지 모른다. 전체 코드를 다 뒤져야 한다.

[메모리 카테고리별 집계 예시] 몬스터 시스템: 100MB (+12MB/h) <- 이거 수상함! 아이템 시스템: 50MB (변동 없음) 패킷 버퍼: 200MB (변동 없음) 세션 관리: 80MB (+0.5MB/h) <- 이것도? NPC 시스템: 30MB (변동 없음) -> "몬스터 관련 코드"를 집중 확인!

선택지 B: 주기적 스냅샷 비교

1시간 간격으로 힙 스냅샷 (Heap Snapshot)을 기록한다.

힙 스냅샷은 "이 시점에 메모리에 뭐가 올라가 있는지" 찍은 사진이야.

두 시점의 스냅샷을 비교(diff)하면: "할당됐는데 해제 안 된 것"이 보인다.

[스냅샷 diff 결과 예시] 14:00 vs 15:00 비교: +2,340건 MonsterAI::PathNode (96 bytes each) <- 경로 노드가 계속 쌓임 +890건 SessionData (512 bytes each) <- 세션 데이터 안 지움 +12건 PacketBuffer (4096 bytes each) <- 이건 정상 범위 -> MonsterAI::PathNode를 할당하는 콜스택 확인!

선택지 C: 도구 활용

UMDH가 뭐야?

정의: UMDH (User-Mode Dump Heap) = Windows에서 제공하는 힙 분석 도구. 두 시점의 힙 스냅샷을 찍고 diff(차이)를 보여준다.

왜 필요: 커스텀 할당자가 없는 서버에서도, 어떤 콜스택에서 메모리를 할당했고 해제를 안 했는지 추적할 수 있다.

안 쓰면: 코드를 눈으로 읽으면서 "여기가 새나? 저기가 새나?" 감으로 찾아야 한다.

[UMDH 사용 흐름] 1. 서버 시작 시 스냅샷 1 찍기 > umdh -p:1234 > snap1.log 2. 1시간 후 스냅샷 2 찍기 > umdh -p:1234 > snap2.log 3. 두 스냅샷 비교 > umdh snap1.log snap2.log > diff.log 4. diff.log에서 가장 많이 증가한 콜스택 확인
VLD (Visual Leak Detector)는?

VLD (Visual Leak Detector) = C++ 프로젝트에 포함시키면 프로세스 종료 시 해제 안 된 메모리를 리포트해주는 라이브러리.

편하지만, 라이브에 붙이면 성능 하락이 심하다. 모든 할당을 추적하니까 느려진다.

실전: 라이브 서버에 직접 붙이는 게 아니라, 스테이징 서버에서 릭을 재현한 뒤 도구를 붙이는 게 일반적.

방법 장점 단점 언제 쓰나
커스텀 할당자 라이브에서 바로 확인 미리 구축해놔야 함 평소에 준비된 경우
힙 스냅샷 diff 정확한 콜스택 확인 스냅샷 찍을 때 순간 부하 원인 범위 좁힌 뒤
UMDH / VLD 상세한 리포트 성능 하락, 라이브 부적합 스테이징에서 재현 후

흔한 원인 패턴 5가지

메모리 릭의 범인이 보통 누구야? 자주 나오는 패턴이 있어?

게임 서버에서 반복적으로 나오는 패턴 5가지가 있다. 릭을 추적할 때 이 목록부터 체크하면 시간을 아낄 수 있다.

패턴 1: 컨테이너가 비워지지 않음

vector, map 같은 컨테이너에 push만 하고 erase를 안 하는 경우.

대표적인 예: 유저가 로그아웃했는데 세션 데이터가 map에 남아있음.

// 문제 코드 std::map<int, PlayerData*> activePlayers; void OnLogin(int userId) { activePlayers[userId] = new PlayerData(); // 추가함 } void OnLogout(int userId) { // activePlayers에서 제거하는 코드가 없다! // PlayerData*도 delete 안 함! } // 유저가 접속/퇴장 반복할수록 map이 무한히 커짐

패턴 2: 순환 참조

shared_ptr을 쓰면 참조 카운트가 0이 될 때 자동으로 메모리가 해제된다.

그런데 A가 B를 가리키고, B가 다시 A를 가리키면? 참조 카운트가 영원히 0이 안 된다.

// 순환 참조 예시 struct Monster { std::shared_ptr<Monster> target; // 내가 노리는 몬스터 }; auto a = std::make_shared<Monster>(); auto b = std::make_shared<Monster>(); a->target = b; // A -> B b->target = a; // B -> A (순환!) // a, b 변수가 스코프 밖으로 나가도 // 참조 카운트: A=1(B가 참조), B=1(A가 참조) // 둘 다 영원히 해제 안 됨 // 해결: 한쪽을 weak_ptr로 바꾸기 struct Monster { std::weak_ptr<Monster> target; // weak로! };

패턴 3: 캐시가 무한히 자람

TTL이 뭐야?

정의: TTL (Time To Live) = 데이터가 살아있을 수 있는 유효 시간. 이 시간이 지나면 자동으로 삭제된다.

왜 필요: 캐시에 데이터를 넣으면 빠르게 꺼내 쓸 수 있지만, 만료 없이 계속 쌓으면 메모리가 무한히 커진다.

안 쓰면: 캐시가 서버 메모리를 전부 먹어서 OOM 발생.

// 문제: expire/TTL 없는 캐시 std::map<std::string, QueryResult> dbCache; QueryResult GetPlayerRank(const std::string& key) { if (dbCache.count(key)) return dbCache[key]; // 캐시 히트 auto result = DB::Query(key); dbCache[key] = result; // 캐시에 추가... 그런데 삭제는? return result; } // 유저 100만 명이 랭킹 조회하면 // dbCache에 100만 건이 영원히 남는다 // 해결: TTL 붙이기 or LRU 캐시 사용

패턴 4: 이벤트 핸들러 미해제

Observer 패턴에서 구독만 하고 해제를 안 하는 경우.

객체가 소멸되어야 하는데, 이벤트 시스템이 참조를 잡고 있어서 소멸하지 못한다.

// 문제: 구독 해제 누락 class Monster { Monster() { EventSystem::Subscribe("OnTick", this, &Monster::Update); // 구독함 } ~Monster() { // EventSystem::Unsubscribe 안 함! } }; // Monster가 죽어서 delete 해도 // EventSystem 내부 리스트에 this 포인터가 남아있음 // -> dangling pointer + 메모리 누수 // 해결: 소멸자에서 반드시 Unsubscribe

패턴 5: 스레드 로컬 저장소 누적

스레드마다 독립적으로 가지는 저장소(thread_local)에 데이터를 쌓는데, 정리를 안 하는 경우.

스레드 풀을 쓰면 스레드가 재활용되니까, 이전 작업의 데이터가 계속 남아서 누적된다.

// 문제: thread_local 변수 정리 누락 thread_local std::vector<LogEntry> threadLog; void ProcessRequest() { threadLog.push_back(LogEntry{...}); // 요청 처리 끝나도 threadLog를 안 비움! } // 스레드 풀의 워커 스레드가 요청을 10만 번 처리하면 // threadLog에 10만 건이 쌓여있음 // 워커 스레드 8개면 x8 // 해결: 요청 처리 끝나면 threadLog.clear()

당장 서버가 죽을 것 같으면

지금 메모리 90%인데 원인 분석할 시간이 없어. 어떻게 해?

근본 수정보다 먼저 서버를 살려야 한다.

[긴급 대응 순서] 1. 해당 서버 드레인 (Drain) -> 신규 접속을 막고, 기존 유저를 다른 서버로 이동 2. 서버 재시작 -> 메모리 초기화. 일단 숨통 트임 3. 근본 수정은 별도 진행 -> 원인 분석 + 패치는 다음 점검 때
Drain이 뭐야?

정의: Drain (드레인) = "물 빼기". 서버에 신규 접속을 막고, 기존 유저가 자연스럽게 빠져나가게 하는 것.

왜 필요: 서버를 갑자기 내리면 접속 중인 유저 전원이 튕긴다. 드레인하면 유저를 안전하게 이동시킨 뒤 내릴 수 있다.

안 쓰면: 강제 종료 = 유저 데이터 손실 위험 + CS 폭주.

재시작하면 끝인 거 아니야? 왜 별도 수정이 필요해?

재시작은 메모리를 초기화할 뿐, 코드의 버그는 그대로야.

다시 릭이 시작되고, 며칠 뒤 같은 일이 반복된다.

수정 후에는 반드시 검증이 필요해.

Soak Test가 뭐야?

정의: Soak Test (소크 테스트) = "담가두기 테스트". 서버를 오랜 시간 켜놓고 메모리/CPU/디스크 등의 변화를 관찰하는 테스트.

왜 필요: 느린 릭은 짧은 테스트에서 안 보인다. 24~72시간 돌려봐야 "메모리 그래프가 평탄한지" 확인할 수 있다.

안 쓰면: "수정했습니다!" 하고 배포했는데, 3일 뒤 또 죽는다. 같은 사고 반복.

[Soak Test 판정 기준] 수정 전: 메모리 그래프가 우상향 ↗ 수정 후: 24~72시간 동안 관찰 결과 1: 평탄 ── -> 릭 수정 성공! 결과 2: 여전히 ↗ -> 다른 릭이 더 있거나, 수정이 불완전

릭을 빠르게 발견하는 것이 더 중요

릭을 아예 안 생기게 하는 방법은 없어?

C++ 서버에서 메모리 릭을 100% 방지하는 건 현실적으로 어렵다. 코드가 수십만 줄이고, 사람이 짜는 이상 실수는 생긴다.

그래서 릭을 "잡는 것"보다 "빠르게 발견하는 것"이 더 중요하다.

[방어선 3가지] 1. 서버 메모리 모니터링 + 자동 알림 -> 메모리 80% 넘으면 Slack/팀즈 알림 -> 그래프를 항상 볼 수 있는 대시보드 (Grafana 등) 2. 정기적 서버 재시작 (매일 새벽 점검) -> 릭이 있어도 매일 초기화되니까 OOM까지 안 감 -> 근본 해결은 아니지만 현실적 방어선 3. 카테고리별 메모리 집계를 평소에 구축 -> 릭 발생 시 "어디서 새는지" 즉시 확인 가능 -> 사후 대응이 아니라 사전 준비

경험상 게임 서버 메모리 릭의 가장 흔한 원인은:

세션 종료 시 정리 누락.

유저가 로그인할 때 만든 객체, 구독한 이벤트, 캐시에 넣은 데이터... 로그아웃할 때 하나라도 빼먹으면 그게 릭이 된다.

그래서 세션 종료 로직은 코드 리뷰에서 가장 꼼꼼하게 봐야 한다.

용어 사전

용어 풀네임 한 줄 설명
OOM Out of Memory 메모리 부족으로 OS가 프로세스를 강제 종료
TTL Time To Live 데이터의 유효 시간. 만료되면 자동 삭제
UMDH User-Mode Dump Heap Windows 힙 분석 도구. 두 시점 스냅샷 diff
VLD Visual Leak Detector C++ 메모리 릭 탐지 라이브러리
Drain - 신규 접속 차단 후 기존 유저를 안전하게 빼내기
Soak Test - 24~72시간 장시간 가동해서 안정성 확인
Custom Allocator - 카테고리별 메모리 사용량을 집계하는 커스텀 할당기

핵심 정리: 라이브 서버 메모리 릭 추적

  • 느린 릭이 가장 위험 - 발견이 어렵고, 발견했을 때는 이미 서버가 위험한 상태
  • 메모리 증가 패턴으로 범위 좁히기 - 선형(매 틱 누수) / 계단식(특정 이벤트 누수)
