메모리 DB? 그냥 내 코드 변수랑 뭐가 달라? — Redis

인메모리 DB가 '별도 서버'인 이유 — 공유·생존·원자성, 그리고 왜 MSSQL보다 빠른가

30초 요약

Redis는 '메모리에 있는 데이터'지만, 핵심은 그게 아니라 '내 프로세스 밖의 별도 서버'라는 것.

그래서 내 코드 변수와 달라: ① 여러 서버가 같은 데이터를 공유 ② 게임 서버가 죽어도 데이터 생존 ③ 동시 접근을 한 곳에서 원자적으로 조율.

인메모리 DB = 데이터 본진이 디스크가 아니라 RAM → 디스크 IO가 없어 MSSQL보다 수십~수백 배 빠름.

대신 RAM은 비싸고 유한·휘발성 → 역할 분담: 영구/복잡 = MSSQL, 뜨겁고 빠른 것(랭킹·캐시·세션·락) = Redis.

Part 1. "메모리 DB? 그럼 그냥 내 코드 변수 아냐?"

Redis가 인메모리 DB래. 근데 메모리에 있는 거면, 그냥 내 게임 서버 코드에서 변수(딕셔너리 같은)로 들고 있는 거랑 뭐가 달라?

진짜 좋은 질문이고, 여기서 대부분 헷갈려. 결정적 차이는 하나야:

Redis는 '네 프로세스 안의 메모리'가 아니라, '네 프로세스 밖의 독립된 별도 서버(프로세스)'야.

네 게임 서버가 네트워크로 접속해서 "이 값 넣어줘/꺼내줘" 하고 부탁하는, 따로 떠 있는 프로그램이야. 마침 그 프로그램이 데이터를 RAM에 들고 있을 뿐이지.

에이, 그래봤자 메모리인데. 별도 프로세스인 게 그렇게 중요해?

그게 전부를 바꿔. 내 프로세스 안의 변수는 세 가지 치명적 한계가 있거든:

1. 내 프로세스에만 존재 — 게임 서버가 여러 대면 서버마다 값이 따로 놀아(공유 불가).

2. 프로세스와 운명 공동체 — 게임 서버 재시작/죽으면 그 변수는 통째로 증발.

3. 동시성 조율이 내 몫 — 여러 서버가 같은 값을 건드리면 누가 맞춰줘?

별도 서버(Redis)로 빼면 이 셋이 다 풀려. 하나씩 볼게 ↓

Part 2. 그래서 뭐가 다른데 — 공유·생존·원자성

첫째, '공유'가 왜 중요해?

우리 게임은 게임 서버가 여러 대야(부하 분산). 유저 A는 서버1, 유저 B는 서버2에 붙어있을 수 있어.

전체 랭킹 킬 수를 각 서버의 로컬 변수에 두면? 서버1은 자기가 아는 킬만, 서버2는 자기 것만 알아 — '전체 1등'을 아무도 계산 못 해. Redis라는 공용 창고 하나에 모으면 모든 서버가 같은 전체 값을 봐. 아래에서 직접 갈라지는 걸 봐 ↓

🔗 로컬 변수 vs Redis — 결정적 차이는 '공유'

게임 서버가 3대야. 각 서버에서 킬 수를 +1 해봐. '로컬 변수'는 서버마다 따로 놀아 값이 갈라지고, 'Redis'는 별도 서버 하나를 같이 봐서 모두 같은 값이야.

킬 +1:
각 게임 서버가 자기 프로세스 메모리에 킬 수를 들고 있어. 서버1에서 3킬, 서버2에서 1킬 하면… 전체 랭킹은 누가 계산해?
둘째 '생존', 셋째 '원자성'은?

생존: 게임 서버를 점검/재배포로 재시작해도, 별도 프로세스인 Redis의 데이터는 그대로 남아. 로컬 변수라면 재시작마다 랭킹이 0으로 리셋되겠지.

원자성: 여러 서버가 동시에 '킬 +1'을 하면 앞에서 배운 레이스 컨디션이 터질 수 있잖아? Redis는 단일 지점에서 INCR 같은 연산을 원자적으로 처리해줘. 게다가 '분산 락'(여러 서버가 공유하는 자물쇠)도 Redis로 구현해 — 로컬 변수로는 불가능한 일이야.

Part 3. 직접 만들면 되잖아? — Redis는 '그 별도 프로세스'의 완성품

잠깐. '메모리에 자료구조 들고, 네트워크로 조회/삽입 받는 별도 프로세스'면 되잖아. 그거 내가 직접 만들면 안 돼? 왜 굳이 Redis를 써?

만들 수 있어! 근데 그렇게 만드는 순간 — 넌 Redis를 재발명하는 거야.

'메모리에 자료구조를 들고, 네트워크로 명령을 받아 조회/삽입/삭제해주는 별도 서버 프로그램' = 그게 정확히 Redis의 정의거든. Redis는 바로 그 아이디어를 10년 넘게 다듬어 놓은 완성품이야. 네 직관이 맞았다는 뜻이야 — 개념은 정확히 이해한 거고, Redis는 그걸 프로덕션 수준으로 구현해둔 제품일 뿐.

그래도 간단하지 않아? 소켓 열고 map 하나 두면 될 것 같은데.

장난감이면 그래. 근데 프로덕션이면 이걸 전부 풀어야 해:

• 동시 수천 연결을 받는 네트워크 처리(우리가 배운 IOCP/epoll)

• 여러 클라가 동시에 같은 값을 건드릴 때 원자성·레이스 방지

• Sorted Set 같은 고성능 자료구조(내부는 skiplist)

• TTL 자동 만료, 메모리 꽉 차면 뭘 버릴지(eviction, LRU)

• 죽어도 복구(지속성 RDB/AOF), 복제·장애조치

• 초당 수십만 ops 성능

이걸 다 만들고 버그 잡고 운영하느니, 이미 검증된 Redis를 쓰는 거야. '바퀴 재발명'을 안 하는 거지. 게다가 표준이라 클라이언트 라이브러리·모니터링·운영 노하우가 이미 다 있어.

Part 4. 어떻게 시키나 — 명령어를 소켓으로 (SQL과 뭐가 다른가)

그 별도 프로세스한테 '조회해/넣어/지워'를 어떻게 시켜? 패킷을 보내는 거야?

맞아. TCP 소켓으로 통신해 — 우리가 네트워크 편에서 배운 바로 그 소켓이야. 게임 서버가 Redis 서버(기본 포트 6379)에 연결해서 명령을 보내.

그럼 DB 쿼리처럼 긴 문장을 보내?

비슷하지만 결정적으로 달라. SQL 같은 복잡한 문장이 아니라 '명령어 + 인자' 형태야. 예: SET name alice / GET name / INCR kills / ZADD board 980 alice.

이게 RESP라는 Redis 전용 포맷으로 인코딩돼 바이트로 나가. 아래처럼 생겼어:

# 'SET name alice' 를 실제로 소켓에 보낼 때 (RESP 포맷) *3\r\n # 인자 3개짜리 명령 $3\r\nSET\r\n # 3글자: SET $4\r\nname\r\n # 4글자: name $5\r\nalice\r\n # 5글자: alice # 응답: +OK\r\n
SQL이랑 근본적으로 뭐가 다른 거야?

SQL은 선언적 — "이런 조건의 데이터 줘"라고 원하는 결과만 말하면 DB가 파싱→옵티마이저→실행계획→인덱스 탐색으로 방법을 알아서 찾아.

Redis 명령은 명령적 — "이 키에 이거 넣어"라고 방법을 직접 지정해. 그래서 파싱·옵티마이저·실행계획이 없어 → 이것도 빠른 이유 중 하나야.

참고로 실무에선 게임 서버가 Redis 클라이언트 라이브러리(hiredis 등)를 써서 함수만 호출하면, 라이브러리가 이 RESP 변환+소켓 전송을 대신 해줘.

🔌 명령을 보내면 — SQL(선언적) vs Redis(명령적)

'요청 보내기'를 눌러봐. 같은 일을 SQL은 '뭘 원하는지'만 말해 DB가 방법을 찾고(깊은 파이프라인), Redis는 '뭘 할지'를 직접 지정해(짧은 경로). 단계 수를 비교해봐.

Part 5. 속을 열어보면 — 그냥 자료구조 + 단일 스레드

인메모리 프로세스니까, 내부적으로는 그냥 C++ 프로세스가 쓰는 자료구조랑 똑같은 거야?

놀랍게도 거의 그래! Redis 속은 결국 C로 짠 자료구조 모음이야. 네 직관이 정확해 — '그냥 프로세스가 들고 있는 자료구조'야.

Redis 타입 내부 자료구조 C++로 치면
String 동적 문자열(SDS) std::string
Hash 해시테이블 unordered_map
List 연결리스트(quicklist) list/deque
Set 해시테이블 / intset unordered_set
Sorted Set skiplist + 해시테이블 정렬 유지 자료구조
(전체 키 공간) 하나의 큰 해시테이블 unordered_map
그럼 우리 게임 서버 코드의 map이랑 진짜 똑같으면, 뭐가 특별한 거야?

세 가지가 얹혀:

① 네트워크로 노출돼 여러 서버가 접근(그래서 '공유').

② TTL·eviction·지속성·복제가 붙음.

③ 제일 중요 — 단일 스레드 이벤트 루프로 명령을 하나씩 순차 처리해.

③ 덕분에 여러 클라가 동시에 INCR을 해도 레이스가 안 나 — 락 없이 원자적이야.

단일 스레드로 처리한다고? 그거 어디서 많이 봤는데…

맞아, 우리가 맨 처음 배운 거랑 정확히 똑같아. 게임 서버가 싱글스레드로 동시성을 회피한 그 철학이야 — 명령을 한 줄로 세워 하나씩 처리하니, 처리 도중 남이 끼어들 수가 없어 원자성이 공짜로 나와.

그래서 Redis의 INCR·ZADD 같은 게 '동시에 쏴도 안전'한 거야. 락 걸 필요도, CAS 짤 필요도 없이. 아래에서 3대가 동시에 쏴도 정확한지 직접 봐 ↓

우리가 맨 처음 배운 거랑 똑같아 — 게임 서버가 싱글스레드로 동시성을 피한 그 철학. Redis도 명령을 한 줄로 세워 처리해서 락 없이 원자적이야.

Part 6. 근데 그냥 MSSQL 쓰면? 왜 굳이 Redis

공유·생존·원자성이면 MSSQL도 다 되잖아. 이미 게임 DB 있는데 왜 Redis를 또 도입해?

맞아, MSSQL도 그 셋은 다 돼. 이유는 속도야. 여기서 '디스크 DB vs 인메모리 DB' 차이가 나와.

• MSSQL = 디스크 DB: 데이터 본진이 디스크의 페이지야. 버퍼 풀로 캐시하지만(앞 편), 미스 나면 디스크行, 게다가 락·트랜잭션·(샤딩이면 여러 DB 병합)까지 얽혀.

• Redis = 인메모리 DB: 데이터 본진이 아예 RAM이야. 디스크行이라는 개념 자체가 없어. 그래서 단순 조회는 수십~수백 배 빨라.

⚡ 왜 MSSQL보다 빠른가 — 디스크 DB vs 인메모리 DB

'전체 랭킹 조회'를 눌러봐. MSSQL은 데이터 본진이 디스크(버퍼 풀 캐시·락·정렬), Redis는 본진이 RAM(디스크行 자체가 없음). 응답 시간을 비교해봐. (예시값)

Part 7. 그럼 다 Redis 쓰면 되잖아?

이렇게 빠른데 그냥 다 Redis에 넣으면 안 돼?

안 돼. 인메모리의 대가가 있어:

1. RAM은 비싸고 유한 — 게임 전체 데이터(수백 GB)를 다 RAM에 못 올려. 디스크는 싸고 크지.

2. 휘발성 — 기본은 전원 나가면 날아가. (지속성 옵션 RDB 스냅샷·AOF 로그가 있지만 완벽한 durability는 MSSQL의 WAL만 못해)

3. 복잡한 쿼리·조인 X — Redis는 key-value + 몇 가지 자료구조뿐. JOIN, 트랜잭션 무결성, 복잡 집계는 RDBMS 몫.

그럼 어떻게 나눠 써?

역할 분담이야:

• MSSQL(디스크 DB): 영구 보관 + 복잡 쿼리 — 캐릭터/아이템/재화 원장, 결제, 통계.

• Redis(인메모리): 뜨겁고 빠르고 임시여도 되는 것 — 실시간 랭킹, 세션, 캐시, 분산 락, TTL 만료(예: 쿨타임).

'진실의 원본은 MSSQL, 빠른 사본/휘발 데이터는 Redis'로 생각하면 편해.

Part 8. 우리 게임 실전 — 랭킹은 왜 Redis가 답인가

실제로 어디에 제일 효과가 커?

실시간 전체 랭킹이 교과서 사례야. 우리 구조를 보면 — 랭킹 데이터가 관문 DB 21개(7서버 × 3채널)에 샤딩돼 있어. 각 관문 1,000명이면 2만 명이 21곳에 흩어진 거지.

MSSQL로 전체 랭킹을 뽑으려면? 21개 DB를 각각 조회해 애플리케이션에서 합치고 다시 정렬해야 해. 관문이 늘수록 무거워지고, 실시간으로 이걸 계속 하면 부하 폭발.

Redis는 이걸 어떻게 해결해?

Redis의 Sorted Set 자료구조 하나면 끝나. 킬이 나올 때마다 ZADD(점수 갱신) 한 방, 전체 상위 N명은 ZREVRANGE 0 N 한 방에 이미 정렬된 상태로 즉시 나와(내부적으로 랭킹 유지). 21곳 병합·재정렬이 통째로 사라져.

🏆 실전 — 21개 관문 DB 랭킹 vs Redis Sorted Set

우리 게임 랭킹은 관문 DB 21개에 흩어져 있어(샤딩). 전체 랭킹을 뽑으려면? MSSQL은 21곳을 다 긁어와 합쳐 정렬, Redis는 Sorted Set 하나로 즉시.

MSSQL: 21개 관문 DB에서 각각 랭킹을 긁어와(21번 조회) 애플리케이션에서 합쳐 다시 정렬 — 관문이 늘수록 무거워져. Redis: ZADD로 한 곳에 모으고 ZREVRANGE로 상위 N개 즉시.

핵심 정리

  • Redis가 '메모리'인 건 맞지만, 본질은 '내 프로세스 밖의 별도 서버'라는 것.
  • 그래서 로컬 변수와 다름: 여러 서버 공유 / 게임 서버 죽어도 생존 / 동시 접근 원자적 조율.
  • 인메모리 DB = 데이터 본진이 RAM(디스크 DB인 MSSQL과 반대) → 디스크 IO 없어 훨씬 빠름.
  • 대가: RAM 비쌈·유한, 휘발성(지속성은 옵션), 복잡 쿼리/조인 불가.
  • 역할 분담: 진실의 원본·복잡 쿼리 = MSSQL / 랭킹·캐시·세션·분산 락 = Redis.
  • 실전: 21개 샤딩 관문 DB 랭킹 병합의 지옥을 Redis Sorted Set(ZADD/ZREVRANGE) 한 방으로.
