카트라이더 네트워크 동기화 - Client Prediction & Extrapolation

1. 뭐가 문제야?

카트라이더에서 0.001초 차이로 승부가 갈린다고?

정확해! 실제 프로 게이머 경기 영상을 보면:

🏁 결과: 1등: 문호준 - 1:23.456 2등: 우영혁 - 1:23.457 차이: 0.001초 = 1/1000초

부스터 사용 시 300km/h 속도로 달리는데, 이 정도 차이로 승패가 결정돼.

그럼 네트워크 동기화가 엄청 정확해야 하겠네?

바로 그거야!

일반 게임처럼 동기화하면 절대 안 돼.

일반 FPS 게임: - 100ms 딜레이? 괜찮아, 총은 맞아 - 200ms 딜레이? 좀 버벅이지만 플레이 가능 카트라이더: - 40ms 딜레이? ❌ 지름길 진입 실패 - 0.001초 = 1ms 차이로 승부 결정 ❗

2. 보통 게임은 어떻게 동기화해?

서버한테 물어보면 되지 않아?

일반적인 Dedicated Server 방식:

클라이언트: "전진 키 눌렀어!" ↓ (20ms) 서버: "알았어, 계산할게... 앞으로 10m 이동!" ↓ (20ms) 클라이언트: "받았어!" (화면 업데이트) 총 딜레이: 40ms = 왕복 시간

미사일 같은 아이템 동기화는 이 방식으로 해:

// 미사일 발사 1. 공격자 → 서버: "미사일 발사!" 2. 서버: 미사일 아이템 있는지 검증 3. 서버 → 모든 클라이언트: "미사일 발사됨!" 4. 각자 미사일 연출 재생 // 피격 처리 5. 서버: 2초 후 피격 판정 6. 서버: 실드 있는지 검증 7. 서버 → 클라이언트: "스턴!" 또는 "방어!"
40ms면 괜찮지 않아?

카트라이더에선 치명적이야!

60fps 게임에서: - 1프레임 = 16.67ms - 40ms = 약 2.4프레임 문제 상황: - 지름길 입구는 1프레임 타이밍이 중요 - 2프레임 늦으면? → 벽 쿵!
🚗 비유: 고속도로 톨게이트

100km/h로 달리는데 톨게이트 통과 신호를 기다린다면?
→ "통과해도 돼?" (20ms)
→ "OK!" (20ms)
→ 그 사이에 이미 벽에 박음! 💥

3. 카트라이더는 어떻게 해결했어?

서버 물어보는 게 문제면 안 물어보면 되지 않아?

정답! Client Simulate Model을 써.

클라이언트: "전진 키 눌렀어!" ↓ (즉시 계산) 클라이언트: 앞으로 10m 이동! (화면 업데이트) ↓ (백그라운드 전송) 서버: "검증할게... 맞네, OK!" 딜레이: 0ms! (화면 업데이트 기준)
그럼 클라이언트가 직접 다 계산하는 거야?

정확히! 하지만 서버 검증이 있어서 치팅 방지:

// 매 프레임 (초당 16번) void Update() { // 1. 클라이언트가 직접 물리 계산 position += velocity * deltaTime; // 2. 계산 결과를 서버에 전송 (초당 16번) SendToServer({ timestamp, // 현재 시간 position, // 계산된 위치 velocity, // 속도 rotation // 회전 }); } // 서버 void Validate(packet) { // 검증: 이 속도가 가능한가? if (packet.velocity > MAX_SPEED) { Kick(player); // 스피드핵! } // 검증: 이 위치 이동이 가능한가? if (!IsReachable(prevPos, packet.position, packet.velocity)) { Kick(player); // 텔레포트 핵! } // 검증 통과 → 다른 클라이언트에게 전파 BroadcastToOthers(packet); }
P2P랑 뭐가 달라?
방식 장점 단점
P2P 빠름 (직접 전송) ❌ 검증 없음 → 핵 가능
Dedicated Server
(일반)		 ✅ 검증 확실 ❌ 느림 (40ms)
Client Simulate
(카트라이더)		 ✅ 빠름 (0ms)
✅ 검증 있음		 ⚠️ 복잡함 (다음 섹션)

3-1. 잠깐, 이게 일반적인 클라이언트 예측과 뭐가 달라?

클라이언트 예측이라는 개념은 원래 있었던 거 아니야?

맞아! 기본 개념은 예전부터 있었어:

일반적인 클라이언트 예측: ┌─────────────────────────┐ │ 1. 내 캐릭터만 예측 │ ← 기본 개념 │ 2. 서버 검증 │ │ 3. 틀리면 보정 │ └─────────────────────────┘ 예: FPS 게임에서 내가 앞으로 걷기 - 내 클라: 즉시 앞으로 이동 (예측) - 서버: 검증 후 "맞아" or "틀려" - 틀리면: 내 위치 보정

이건 "나 자신"에 대한 예측이야.

그럼 카트라이더는 뭘 추가로 한 거야?

다른 플레이어도 예측!

카트라이더 = 기본 + 추가 기술 ┌─ 일반 게임 ────────────┐ │ 내 캐릭터만 예측 │ └────────────────────────┘ ↓ ┌─ 카트라이더 ──────────────────┐ │ 1. 내 카트 예측 (기본 개념) │ │ 2. 다른 7대 카트도 예측 ⭐ │ ← 새로운 기술 │ 3. Hard Snap (보정 방법) │ ← 실전 노하우 │ 4. 거리별 차별화 (최적화) │ ← 성능 개선 │ 5. 서버 시간 동기화 (안정성) │ ← 인프라 └────────────────────────────────┘
항목 기본 개념 카트라이더 구현
누구를 예측? 내 캐릭터만 내 카트 + 다른 플레이어 7대
예측 방법 입력 기반 (내 키보드) Extrapolation (위치+속도+시간)
보정 방법 "보정한다" (추상적) Hard Snap vs 부드러운 보간
최적화 없음 거리별 차별화 (가까움=정확, 멀리=부드러움)
시간 처리 클라이언트 시간 사용 서버 시간으로 통일 (Delta 계산)
패킷 손실 재전송? 타임스탬프로 순서 보장, 늦은 패킷 무시
왜 다른 플레이어까지 예측해야 해?

200ms 지연 문제 때문이야:

기본 개념만 쓰면: - 내 카트: 즉시 업데이트 (0ms) ✅ - 다른 카트: 200ms 늦게 업데이트 ❌ 결과: - 내 화면에 다른 플레이어가 200ms 과거 모습 - 0.001초 차이로 승부 나는데 200ms(=0.2초) 오차? - 실제보다 20m 뒤에 보임!

그래서 Extrapolation (외삽)으로 다른 플레이어의 "현재 위치"를 예측해야 해!

아하! 그럼 이 문서는 "기본 개념"이 아니라 "실전 구현"을 다루는 거구나?

정확해!

📚 비유: 요리책

기본 개념: "파스타는 면을 삶아서 소스를 넣는다"
이 문서: "면은 몇 분? 소금은 얼마? 불 세기는? 면이 너무 익으면 어떡해? 소스가 모자라면?"

→ 실제로 만들 때 필요한 모든 디테일!

카트라이더는 "클라이언트 예측 + 서버 검증" 개념을 실전에서 어떻게 구현하는지 보여주는 거야!

💡 핵심 정리: 기본 vs 카트라이더

  • 기본 개념: 내 캐릭터만 예측 + 서버 검증
  • 카트라이더: 기본 + 다른 플레이어 예측 (Extrapolation)
  • 왜 필요? 0.001초 단위 경쟁에서 200ms 지연은 치명적
  • 추가 기술: Hard Snap, 거리별 차별화, 서버 시간 동기화

4. 그럼 문제 해결된 거야?

클라이언트가 직접 계산하면 끝 아니야?

새로운 문제가 생겨!

상황: - 클라이언트 A: "나 지금 100m 위치야!" (전송) - 패킷 전송 시간: 200ms - 클라이언트 B: (200ms 후) "어? A가 100m래?" 문제: - B가 패킷 받을 때 A는 이미 120m에 있음 - B 화면: A가 100m에 있음 (과거 모습) - A 화면: 내가 120m에 있음 결과: 서로 다른 화면! ❌
그럼 A가 B보다 빨리 보이겠네?

정확해! 각자 화면에서 자기가 1등이라고 착각해:

A의 화면: 🏎️ A (120m) - 1등! 🏎️ B (100m) - 2등 B의 화면: 🏎️ B (115m) - 1등! 🏎️ A (95m) - 2등 실제: A = 120m B = 115m

0.001초 차이로 승부 결정하는 게임에서 이건 재앙이야!

5. Extrapolation: 미래 예측

과거 패킷을 현재로 만들 수 있어?

Extrapolation (외삽)을 써!

📈 Interpolation vs Extrapolation

Interpolation (내삽): 과거 값 사이를 채워넣기
- 0과 10이 있을 때 → 5를 유추 (사이)

Extrapolation (외삽): 미래 값을 예측
- 0과 10이 있을 때 → 20을 유추 (미래)
어떻게 미래를 예측해?

4가지 정보를 패킷에 실어 보내:

struct MovementPacket { float timestamp; // 1. 보낸 시간 Vector3 position; // 2. 위치 Vector3 linearVelocity; // 3. 선형 속도 Vector3 angularVelocity;// 4. 각속도 (회전) };

받는 쪽에서 계산:

void OnReceive(MovementPacket packet) { // 1. 시간 차이 계산 float latency = CurrentServerTime - packet.timestamp; // latency = 200ms (0.2초) // 2. 현재 위치 예측 (거리 = 속도 × 시간) Vector3 predictedPosition = packet.position + (packet.linearVelocity * latency); // 예: position=100m, velocity=100m/s, latency=0.2s // → predictedPosition = 100 + (100 × 0.2) = 120m ✅ // 3. 회전도 예측 Vector3 predictedRotation = packet.rotation + (packet.angularVelocity * latency); // 4. 부드럽게 보간 (급격한 변화 방지) currentPosition = Lerp(currentPosition, predictedPosition, 0.8); }
그럼 이제 완벽해?

아직도 문제가 있어!

예측의 한계: 예측 시점: "이 속도로 직진하겠지?" 0.2초 후 실제: 왼쪽으로 꺾음! 결과: - 예측 위치: 120m (직진) - 실제 위치: 115m (회전) - 오차: 5m ❌

플레이어가 언제 키를 누를지는 예측 불가능이야.

6. Hard Snap: 오차 보정

예측이 틀렸으면 어떻게 해?

Hard Snap을 써: 순간이동처럼 위치를 확 바꿔버려.

void Update() { // 예측 위치와 실제 위치 차이 계산 float error = Distance(predictedPosition, actualPosition); // 오차가 크면 Hard Snap if (error > SNAP_THRESHOLD) { // 텔레포트! position = actualPosition; } else { // 오차가 작으면 부드럽게 보간 position = Lerp(position, actualPosition, 0.8); } }
텔레포트하면 화면이 뚝뚝 끊기지 않아?

의외로 안 그래!

🧠 사용자 심리

부드럽게 보간: "어? 왜 저기 있어? 버그 같은데?"
→ 계속 이상한 곳에 있으니 버그라고 생각

Hard Snap: "어? 순간이동? 랙인가?"
→ 일시적 현상이라 생각, 덜 버그처럼 느껴짐

유저들이 Hard Snap을 오히려 덜 버그라고 인지해!

7. 실전 최적화: 거리별 전략

모든 카트를 똑같이 처리해?

아니! 거리에 따라 다르게 처리해:

거리 중요도 전략 이유
가까운 유저
(10m 이내)		 ⭐⭐⭐ Hard Snap 자주
정확도 우선		 1등 경합, 충돌 판정
중간 유저
(10~50m)		 ⭐⭐ 적당히 예측 경쟁 상대
먼 유저
(50m 이상)		 ⭐ 예측 많이
부드러움 우선		 어차피 경쟁 안 함
충돌도 없음
왜 멀리 있는 유저는 정확도가 덜 중요해?
상황: 내가 1등, 꼴찌가 100m 뒤에 꼴찌가 실제로: - 100m 뒤에 있든 - 105m 뒤에 있든 내 플레이에 영향: - 1등 경합? ❌ (너무 멀어) - 충돌? ❌ (거리 차이 너무 큼) - 아이템 맞을 일? ❌ → 0.2초 과거 모습 보여줘도 OK! → Hard Snap 안 해도 돼 (부드럽게)
가까운 유저는?
상황: 1등 경합, 5m 차이 상대가: - 5.0m 앞에 있는지 - 4.9m 앞에 있는지 → 0.1m = 0.001초 차이로 승부 결정! → Hard Snap 자주 해서 정확한 위치 표시 필수!

가까운 유저는 정확도가 생명!

8. 속도별 파라미터 조정

카트라이더는 왜 특별한 파라미터가 필요해?

속도가 너무 빠르기 때문이야!

FPS 게임 (걸어다님): - 속도: 5m/s - 0.2초 이동 거리: 1m - Hard Snap 조건: 5m 오차까지 허용 → 오차 5m = 엄청 큰 차이, 즉시 보정 카트라이더 (300km/h): - 속도: 83m/s (300km/h ÷ 3.6) - 0.2초 이동 거리: 16.6m! - Hard Snap 조건: 20m 오차까지 허용 → 오차 20m = 정상 범위, 너무 자주 Snap하면 화면 끊김
회전도 다르게 처리해?

당연하지! 카트는 커브에서도 감속이 적어:

// 일반 레이싱 게임 커브 진입 → 속도 80% 감속 → 예측 쉬움 // 카트라이더 커브 진입 → 드리프트 → 속도 거의 유지! → 예측 어려움 → Angular Velocity Interpolation 파라미터 크게 설정

파라미터:

// Unreal Engine 기본값 PositionInterpolationSpeed = 0.2f; RotationInterpolationSpeed = 0.2f; // 카트라이더 PositionInterpolationSpeed = 0.8f; // 4배 빠름! RotationInterpolationSpeed = 0.9f; // 4.5배 빠름!

9. 서버 시간 동기화

아까 timestamp를 보낸다고 했는데, 시계가 다르면?

큰 문제야!

상황: - 클라이언트 A 시계: 2시 00분 - 클라이언트 B 시계: 2시 02분 (2분 빠름) A가 패킷 전송: - "나 2시 00분에 100m 위치야!" B가 받음: - "어? 지금 2시 02분인데 2시 00분 패킷이 왔네?" - "2분 전 패킷이네! 엄청 과거잖아?" - latency = 120초 (실제는 0.2초) - 예측 위치 = 100 + (100 × 120) = 12,100m! ❌
어떻게 시간을 맞춰?

서버 시간을 기준으로 삼아!

// 서버가 모든 클라이언트에게 시간 전송 (초당 1번) void ServerSendTime() { BroadcastToAll({ serverTime: GetServerWorldTime() }); } // 클라이언트가 서버 시간 받아서 Delta 계산 void OnReceiveServerTime(serverTime) { float clientTime = GetClientTime(); // Delta = 서버 시간 - 클라이언트 시간 timeDelta = serverTime - clientTime; // 예: 14:00:00 - 14:02:00 = -120초 } // 이후 패킷 보낼 때 void SendMovement() { float adjustedTime = GetClientTime() + timeDelta; // 14:02:05 + (-120) = 14:00:05 (서버 시간으로 변환) SendPacket({ timestamp: adjustedTime, // 서버 시간 기준 position: currentPosition }); }

모든 시간은 서버 시간 기준으로 통일!

10. UDP 패킷 손실 대응

UDP는 패킷이 손실될 수 있잖아?

Timestamp로 검증해:

float lastReceivedTimestamp = 0; void OnReceivePacket(packet) { // 과거 패킷이면 무시 (순서 뒤바뀜 or 재전송) if (packet.timestamp <= lastReceivedTimestamp) { return; // 버림 } lastReceivedTimestamp = packet.timestamp; // 정상 처리 Extrapolate(packet); }
패킷이 안 오면?

마지막 속도로 계속 예측:

void Update() { if (NoPacketReceived(0.5f)) { // 0.5초 동안 패킷 안 옴 // → 마지막 속도로 계속 이동 position += lastVelocity * deltaTime; } // 너무 오래 안 오면 Hard Snap if (NoPacketReceived(2.0f)) { // "연결 끊김" 표시 ShowDisconnectedIcon(); } }

📌 핵심 정리: 카트라이더 네트워크 동기화

  • 문제 - 0.001초 차이 승부인데 일반 방식은 40ms 딜레이
  • Client Simulate - 클라이언트가 직접 계산 → 0ms 딜레이
  • Extrapolation - 과거 패킷을 미래로 예측 (위치 = 받은 위치 + 속도 × 시간)
  • Hard Snap - 오차 크면 텔레포트 (유저가 덜 버그라고 인지)
  • 거리별 차별화 - 가까운 유저: 정확도 우선 / 먼 유저: 부드러움 우선
  • 속도별 파라미터 - 카트는 빠르니까 Hard Snap 조건 넉넉하게
  • 서버 시간 동기화 - 모든 timestamp는 서버 시간 기준
  • UDP 손실 대응 - Timestamp로 순서 검증, 마지막 속도로 예측
