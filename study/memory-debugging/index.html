발표자는 어떤 사람이야?

2014년 마비노기 10주년에 신입으로 합류한 개발자야.

2004년부터 마비노기 유저였던 "성공한 덕후"지!

메모리 디버깅을 왜 공부하게 됐어?

던전 콘텐츠 업데이트 후 클라이언트가 메모리 부족으로 크래시나는 문제가 급증했어.

입사 4개월차에 이 문제를 담당하게 됐는데...

사막에서 바늘 찾기

던전에는 전투, 스킬, AI 등 수많은 기능이 들어있어서
눈으로 delete 누락을 찾는 건 거의 불가능했어.

Part 2. "램은 남는데 튕겨요" 무슨 현상이야?

유저가 "메모리 16GB인데 왜 튕겨요?" 라고 물어봐. 뭐라고 해야 해?

프로세스의 가상 메모리가 부족한 거야!

물리 메모리(RAM)하고는 다른 개념이야.

중요!

메모리 부족은 유저 컴퓨터 사양 탓이 아니야!
대부분 우리가 만든 프로그램의 문제야.
운영체제 가상 메모리랑 프로세스 가상 메모리가 다르다고?

응, 완전 다른 개념이야!

구분 운영체제의 가상 메모리 프로세스의 가상 메모리
정의 디스크 일부를 RAM처럼 사용 프로세스에게 할당된 논리적 주소 공간
특징 실제 RAM보다 큰 메모리 사용 가능 RAM 용량과 무관, 플랫폼이 결정
설정 제어판에서 수정 가능 32bit/64bit에 따라 고정
32비트 프로세스는 메모리를 얼마나 쓸 수 있어?

이론상 2^32 = 4GB까지 가능한데...

실제로는 2GB만 쓸 수 있어!

왜 절반밖에 못 써?

4GB 중 절반인 2GB는 커널 모드(운영체제)가 사용해.
이 영역에는 최근 이슈가 된 CPU 보안 취약점 관련 메모리도 포함돼있어.

결론: 32비트 윈도우 지원하면 → 가상 메모리 한계 = 2GB
가상 메모리가 꽉 차면 어떻게 돼?

할당 함수들이 실패해:

malloc() → NULL 리턴 new → std::bad_alloc 예외 던짐 bad_alloc 예외 처리 없으면? → 프로그램 크래시!
64비트면 메모리 릭 안 고쳐도 되는 거 아냐?

절대 아니야! 64비트에서도 문제가 심각해:

64비트에서도 메모리 릭이 위험한 이유
  • 페이지 폴트 증가 - 찾는 정보가 RAM에 없어서 디스크까지 뒤져야 함
  • 캐시 미스 증가 - 누수된 메모리로 인한 지역성(locality) 저하
  • 퍼포먼스 저하 - 심하면 서버 성능까지 영향
  • 극단적 상황 - 메모리 때문에 서버 전체 멈춰서 긴급 점검!

Part 3. 메모리 사용량 어떻게 봐?

작업 관리자에서 메모리 보려면 어떤 컬럼을 봐야 해?

두 가지가 있어:

컬럼 영문명 의미 용도
작업 집합 Working Set 현재 RAM에 올라와 있는 메모리 실시간 RAM 사용량
커밋 크기 Commit Size OS로부터 할당받은 모든 메모리 메모리 릭 추적!
주의!

커밋 크기 컬럼은 기본으로 안 보여!
작업 관리자에서 컬럼 헤더 우클릭해서 직접 추가해야 해.
더 자세히 볼 수 있는 도구는 없어?

좋은 도구들이 있어:

메모리 분석 도구들

  • VMMap - 가상 메모리 맵 시각화
  • 성능 모니터 - 주기적으로 수치 기록할 때

Part 4. 재현 가능한 메모리 릭 잡기

메모리 릭은 어떻게 분류해?

크게 두 가지로 나눠:

분류 특징 난이도
재현 가능한 메모리 릭 로컬에서 재현 방법이 있음 비교적 쉬움 (99% 해결!)
재현 불가능한 메모리 릭 재현 조건을 찾기 어려움 어려움
재현 가능하면 어떻게 찾아?

우리가 알아야 하는 건 "어디서 메모리가 새나?" = 콜 스택이야!

메모리 릭 디버깅 핵심 전략: 1. 스택 수집 → 메모리 할당 콜 스택 수집 (할당 함수 후킹 + 스택 트레이스) 2. 스냅샷 1 → 재현 전 메모리 상태 저장 3. 재현 → 메모리 릭 재현 4. 스냅샷 2 → 재현 후 메모리 상태 저장 5. 비교 → 두 스냅샷 비교 → 어디서 메모리가 늘었나?
UMDH가 뭐야?

User-Mode Dump Heap - 동적 할당 메모리를 분석하는 무료 도구야!

Windows Debugging Tools에 포함되어 있어.

UMDH 사용법
  • 1단계: GFlags로 UST 플래그 활성화
  • 2단계: 재현 전 스냅샷
  • 3단계: 메모리 릭 재현
  • 4단계: 재현 후 스냅샷
  • 5단계: 두 스냅샷 비교
-- 1. UST 플래그 활성화 (다음 실행부터 콜 스택 자동 수집) gflags.exe /i [프로그램명] +ust -- 2. 첫 번째 스냅샷 (재현 전) umdh -p:[PID] -f:log1.txt -- 3. 메모리 릭 재현 -- 4. 두 번째 스냅샷 (재현 후) umdh -p:[PID] -f:log2.txt -- 5. 스냅샷 비교 umdh log1.txt log2.txt > diff.txt
결과!

diff.txt에서 두 스냅샷 사이에 할당되고 해제되지 않은 메모리의 콜스택 확인 가능!
UMDH 말고 다른 도구는 없어?

여러 가지가 있어:

다른 메모리 디버깅 도구들
  • Visual Studio 메모리 스냅샷 (2015부터) - 더 쉬움, VS 환경 필요
  • Application Verifier
  • Valgrind (리눅스)
  • CRT Debug Library

Part 5. 재현 불가능한 메모리 릭 잡기

서버에서 발생하는 메모리 릭은 왜 찾기 어려워?

여러 가지 이유가 있어:

재현 불가능한 메모리 릭이 어려운 이유

  • 메모리 증가 패턴이나 메시지를 특정짓기 어려움
  • 시간당 메모리 증가량이 매우 작음
  • 처리하는 메시지 수가 너무 많음
라이브 서버에 UMDH 쓰면 안 돼?

절대 안 돼!

UST 플래그 적용하면 부팅부터 너무 오래 걸리고 반응성이 크게 떨어져.

그럼 어떻게 해?

덤프 파일을 분석해!

덤프(Dump)란?

특정 시점에 프로그램 작업 상태를 기록한 파일이야.

  • 레지스터 상태
  • 스택 상태
  • 메모리 정보

풀 덤프(Full Dump) = 프로세스의 모든 메모리 정보 포함 = 누수된 메모리도 포함!
WinDbg로 힙 분석하는 방법 알려줘!

WinDbg는 Microsoft 제공 무료 디버거야. 강력한 힙 분석 기능이 있어!

-- 1. 전체 힙 상태 확인 !heap -s → 여러 힙 중 가장 많은 메모리 사용하는 힙 찾기 -- 2. 힙 통계 확인 !heap -stat -h [힙주소] → 해당 힙에서 사이즈별 할당 개수 통계 -- 3. 사이즈 필터링 !heap -flt s [사이즈] → 특정 사이즈 메모리 블록 모두 검색 -- 4. 메모리 내용 분석 → 누수된 메모리 블록 내 데이터 확인
누수된 메모리에 가상 함수가 있는 객체면?

전생에 나라를 구한 거야! (가장 쉬운 케이스)

왜 쉬워?

가상 함수가 있는 객체는 맨 앞에 vftable 포인터가 있어.
WinDbg가 자동으로 역참조해서 실제 타입(클래스 이름)을 보여줘!
클래스 이름 알면 → 해당 포인터 캐스팅 → 어떤 정보를 가진 객체인지 확인!
누수된 메모리가 문자열이면?

게임 서버에서 많이 발생하는 케이스야.

(마비노기의 2.9GB 누수가 이 경우였어!)

-- 힙 세그먼트 확인 !heap [힙주소] → 힙이 사용하는 메모리 영역 나열
힙 메모리 배치 특성

낮은 번지: 오래전 할당된 메모리 (데이터 로딩, 캐싱)
높은 번지: 최근 할당된 메모리 (활발히 사용 중)
중간: 누수된 메모리가 차곡차곡 쌓여있음!
-- 메모리 내용 확인 du [메모리주소] (유니코드 문자열) da [메모리주소] (ASCII 문자열) -- 또는 Visual Studio 메모리 창 사용
결과!

어떤 문자열이 누수되는지 알면 → 코드/데이터에서 해당 문자열 정의 부분 찾기 → 재현 방법 특정!
문자열도 없고 vftable도 없으면 어떡해?

아직 방법이 남아있어!

사이즈가 유니크한 경우 (예: 4000바이트, 380바이트)
  • _CrtSetAllocHook()로 메모리 할당에 훅 설치
  • 같은 사이즈 할당 시 브레이크포인트/로그
  • 참고: NDC 2010 "온라인 게임에서 사례로 살펴보는 디버깅" (턱이님)
사이즈가 흔한 경우 (48바이트 등)

  • 인력 투입해서 메모리 블록 내 데이터 분석
  • 내부 테스트 서버에 UMDH 적용
  • 문제 발생 시점 코드 변경점 전체 리뷰
  • 메모리 증가 시점의 유저 로그 분석
핵심!

재현 불가능한 메모리 릭 → 재현 가능한 메모리 릭으로 만드는 게 목표!

Part 6. 메모리 부족의 다양한 원인

메모리 릭 말고도 메모리 부족 원인이 있어?

응, 여러 가지가 있어:

메모리 부족의 다양한 원인
  • 메모리 릭 - delete 누락, 소멸자 virtual 미선언 등
  • 과도한 캐싱 - 너무 많은 데이터를 메모리에 들고 있음
  • 대용량 리소스 로딩 - 한 번에 너무 많이 로드
  • 메모리 단편화 - 작은 구멍들이 많아서 큰 메모리 할당 불가
  • 외부 라이브러리 문제 - 우리 코드가 아닌 곳에서 발생
어떻게 구분해?

각 원인마다 다양한 도구와 지표를 확인해야 해.

경험이 쌓이면 패턴이 보여!

핵심 정리: 윈도우 메모리 디버깅

  • 32비트 윈도우 - 가상 메모리 한계 2GB (RAM과 무관!)
  • 커밋 크기 - 메모리 릭 추적 시 봐야 할 컬럼
  • 재현 가능 - UMDH로 스냅샷 비교 → 콜스택 추적
  • 재현 불가능 - WinDbg로 풀 덤프 힙 분석
  • vftable - 가상 함수 있으면 클래스 이름 바로 확인
  • 문자열 - du/da 명령어로 내용 확인
  • 최종 목표 - 재현 불가능 → 재현 가능으로 전환!
