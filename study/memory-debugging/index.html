쉽게 발자 알아야 윈도우 메모리 디버깅

CS기초 발표자: 조성원 (마비노기 프로젝트) NDC 발표

발표 배경 및 동기

발표자는 어떤 배경에서 이 발표를 하게 되었나요?

발표자는 2014년 마비노기 10주년에 신입으로 합류했습니다. 2004년부터 마비노기 유저였던 "성공한 덕후"로, 던전 콘텐츠 업데이트 후 메모리 부족으로 클라이언트 크래시가 급증하는 문제가 발생했습니다.

핵심 계기: 입사 4개월차에 메모리 릭 이슈를 담당하게 되었고, 이 경험을 통해 메모리 디버깅 기법을 체득하게 되었습니다.
왜 메모리 릭 찾기가 어려웠나요?

마비노기는 14년간 활발한 업데이트를 이어온 게임이라 코드 양이 상상 이상으로 많았습니다. 던전 플레이라는 비교적 명확한 재현 스텝이 있음에도, 던전에는 전투, 스킬 등 수많은 기능이 포함되어 있어 눈으로 delete 누락을 찾는 것은 "사막에서 바늘 찾기"와 같았습니다.

메모리 부족 현상 (Out of Memory)

"메모리 부족하다면서 튀는데 램은 남아있다" - 이게 무슨 현상인가요?

대부분의 경우 프로세스의 가상 메모리가 부족한 현상입니다. 물리 메모리(RAM)가 부족한 경우도 있지만, 대부분은 우리가 만든 응용프로그램의 문제입니다.

중요: 메모리 부족은 유저분들 컴퓨터 사양 탓이 아닙니다!
운영체제의 가상 메모리와 프로세스의 가상 메모리는 어떻게 다른가요?
구분 운영체제의 가상 메모리 프로세스의 가상 메모리
정의 디스크 일부를 RAM처럼 사용하는 시스템 프로세스에게 할당된 논리적 주소 공간
특징 실제 RAM보다 큰 메모리 할당 가능 RAM 용량과 무관하게 플랫폼에 의해 결정
설정 제어판에서 수정 가능 32bit/64bit에 따라 고정
32비트 프로세스의 가상 메모리 한계는 얼마인가요?

32비트는 이론상 2^32 = 4GB까지 표현 가능하지만, 실제로는 2GB만 사용 가능합니다.

이유: 4GB 중 절반인 2GB는 커널 모드(운영체제)가 사용합니다. 이 커널 영역에는 최근 이슈가 된 CPU 보안 취약점 관련 메모리 영역도 포함됩니다.

결론: 32비트 윈도우를 지원한다면, 가상 메모리 한계를 2GB로 생각해야 합니다.

가상 메모리가 한계를 초과하면 어떻게 되나요?
  • malloc() → NULL 리턴
  • new 연산자 → std::bad_alloc 예외 던짐
  • bad_alloc 예외 처리가 없다면 → 프로그램 크래시
64비트면 메모리 릭을 안 고쳐도 되지 않나요?

아닙니다! 64비트에서도 메모리 릭은 심각한 문제를 일으킵니다:

  • 페이지 폴트 증가: 찾는 정보가 RAM에 없어 디스크까지 찾아야 하는 경우 증가
  • 캐시 미스 증가: 누수된 메모리로 인한 지역성(locality) 저하
  • 퍼포먼스 저하: 심각한 경우 서버 성능까지 영향
  • 극단적 상황: 메모리 때문에 서버 전체가 멈춰서 점검해야 하는 경우도 발생

메모리 사용량 측정 방법

작업 관리자에서 메모리를 볼 때 어떤 컬럼을 봐야 하나요?
컬럼 영문명 의미 용도
작업 집합 Working Set 현재 실제로 RAM에 올라와 있는 메모리 실시간 RAM 사용량 확인
커밋 크기 Commit Size OS로부터 할당받은 모든 메모리 (사용 중 + 노는 중) 메모리 릭 추적 시 사용!
팁: 커밋 크기 컬럼은 기본으로 표시되지 않습니다. 작업 관리자에서 컬럼 헤더를 우클릭하여 직접 선택해야 합니다.
메모리 분석에 유용한 도구들은 무엇인가요?

Process Explorer

프로세스의 상세 메모리 정보 확인 가능

VMMap

가상 메모리 맵 시각화 도구

성능 모니터 (Performance Monitor)

주기적으로 수치를 기록해야 할 때 유용

재현 가능한 메모리 릭 디버깅

메모리 릭을 어떻게 분류하나요?
분류 특징 난이도
재현 가능한 메모리 릭 로컬에서 재현 방법이 있는 경우 비교적 쉬움 (99% 해결 가능)
재현 불가능한 메모리 릭 재현 조건을 찾기 힘든 경우 어려움
메모리 릭 디버깅의 핵심 전략은 무엇인가요?

우리가 알아야 하는 정보는 "어디서 메모리가 새는가" = 콜 스택입니다.

  1. 스택 수집: 메모리 할당이 일어나는 콜 스택 수집 (할당 함수 후킹 + 스택 트레이스)
  2. 스냅샷 1: 메모리 릭 재현 전에 메모리 상태 저장
  3. 재현: 메모리 릭 재현
  4. 스냅샷 2: 재현 후 메모리 상태 저장
  5. 비교: 두 스냅샷 비교 → 어떤 콜스택에서 메모리가 증가했는지 확인
UMDH란 무엇이고 어떻게 사용하나요?

UMDH (User-Mode Dump Heap): 동적 할당 메모리를 분석할 수 있는 무료 도구로, Windows Debugging Tools에 포함되어 있습니다.

1. GFlags로 UST 플래그 활성화

gflags.exe /i [프로그램명] +ust

UST (User-mode Stack Trace): 다음 실행부터 콜 스택을 자동 수집

2. 첫 번째 스냅샷 (재현 전)

umdh -p:[PID] -f:log1.txt

3. 메모리 릭 재현

4. 두 번째 스냅샷 (재현 후)

umdh -p:[PID] -f:log2.txt

5. 스냅샷 비교

umdh log1.txt log2.txt > diff.txt
결과: diff.txt에서 두 스냅샷 사이에 할당되고 해제되지 않은 메모리(누수된 메모리)의 콜스택 확인 가능!
UMDH 외에 다른 메모리 디버깅 도구는 없나요?
  • Visual Studio 메모리 스냅샷 (2015부터): 더 쉽지만 VS 설치 환경에서만 가능
  • Application Verifier
  • Valgrind (리눅스)
  • CRT Debug Library

추천 자료: 김이주님의 "디버깅 어디까지 해봤니" NDC 세션

재현 불가능한 메모리 릭 디버깅

서버에서 발생하는 메모리 릭은 왜 추적하기 어려운가요?
  • 메모리가 증가하는 패턴이나 메시지를 특정짓기 어려움
  • 시간당 메모리 증가량이 매우 작음
  • 처리하는 메시지 수가 매우 많음
UMDH의 한계: 라이브 서버에 UMDH(UST 플래그)를 적용하면 부팅부터 너무 오래 걸리고 반응성이 크게 떨어져 실사용이 불가능합니다.
덤프 파일이란 무엇인가요?

덤프(Dump): 특정 시점에 프로그램 작업 상태를 기록한 파일

  • 레지스터 상태
  • 스택 상태
  • 메모리 정보

풀 덤프(Full Dump): 프로세스의 모든 메모리 정보를 포함 → 누수된 메모리도 포함!

WinDbg로 힙 분석하는 방법은?

WinDbg: Microsoft 제공 무료 디버거, 강력한 힙 분석 기능 제공

  1. 전체 힙 상태 확인 
    !heap -s

    → 여러 힙 중 가장 많은 메모리를 사용하는 힙 찾기

  2. 힙 통계 확인 
    !heap -stat -h [힙주소]

    → 해당 힙에서 사이즈별 할당 개수 통계

  3. 사이즈 필터링 
    !heap -flt s [사이즈]

    → 특정 사이즈 메모리 블록 모두 검색

  4. 메모리 내용 분석

    → 누수된 메모리 블록 내 데이터 확인

누수된 메모리가 가상 함수가 있는 객체라면?

전생에 나라를 구한 경우입니다! (가장 쉬운 케이스)

  • 가상 함수가 있는 객체는 맨 앞에 vftable 포인터가 있음
  • WinDbg가 자동으로 역참조하여 실제 타입(클래스 이름) 표시
  • 클래스 이름을 알면 해당 포인터를 캐스팅하여 어떤 정보를 가진 객체인지 확인 가능
누수된 메모리가 문자열이라면?

게임 서버에서 많이 발생하는 케이스입니다. (마비노기의 2.9GB 누수가 이 경우)

힙 세그먼트 확인

!heap [힙주소]

→ 힙이 사용하는 메모리 영역 나열

힙 메모리 배치 특성:
  • 낮은 번지: 오래전 할당된 메모리 (데이터 로딩, 캐싱)
  • 높은 번지: 최근 할당된 메모리 (활발히 사용 중)
  • 중간: 누수된 메모리가 차곡차곡 쌓여있음!

메모리 내용 확인

du [메모리주소]  (유니코드 문자열)
da [메모리주소]  (ASCII 문자열)

또는 Visual Studio 메모리 창 사용

결과: 어떤 문자열이 누수되는지 알면 → 코드/데이터에서 해당 문자열 정의 부분을 찾아 재현 방법 특정 가능!

누수된 메모리에 문자열도 없고 vftable도 없다면?

아직 방법이 남아있습니다:

사이즈가 유니크한 경우

예: 4000바이트 버퍼, 380바이트 객체

_CrtSetAllocHook()

→ 메모리 할당에 훅 설치, 같은 사이즈 할당 시 브레이크포인트/로그

참고: NDC 2010 "온라인 게임에서 사례로 살펴보는 디버깅" (턱이님)

사이즈가 흔한 경우 (48바이트 등)

  • 인력 투입하여 메모리 블록 내 데이터 분석
  • 내부 테스트 서버에 UMDH 적용
  • 문제 발생 시점 코드 변경점 전체 리뷰
  • 메모리 증가 시점의 유저 로그 분석
핵심: 재현 불가능한 메모리 릭 → 재현 가능한 메모리 릭으로 만드는 것이 목표!

핵심 요약

기억해야 할 핵심 포인트

  • 32비트 윈도우 지원 시 가상 메모리 한계는 2GB
  • 메모리 분석 시 커밋 크기(Commit Size) 확인 필수
  • 재현 가능한 메모리 릭: UMDH 등 도구로 콜스택 추적
  • 재현 불가능한 메모리 릭: WinDbg로 풀 덤프의 힙 분석
  • 최종 목표: 재현 불가능 → 재현 가능으로 전환
메모리 부족의 다양한 원인들
  • 메모리 릭 (delete 누락, 소멸자 virtual 미선언 등)
  • 과도한 캐싱
  • 대용량 리소스 로딩
  • 메모리 단편화
  • 외부 라이브러리 문제

각 원인을 구분하려면 다양한 도구와 지표를 확인해야 합니다.
