무엇을 복제할까: DOREPLIFETIME

언리얼 네트워크 · 14 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이 고민을 해봤을 거야. CChosunPlayer 안에는 HP, 좌표, 이름, 인벤토리, 소켓 상태, DB 캐시, 임시 계산값 같은 게 다 섞여 있지. 그런데 클라한테 상태를 보낼 때 이걸 전부 보내진 않아. SP_* 패킷을 만들 때도 "클라가 알아야 하는 값"만 골라 담잖아.

이 명단이 없으면 바로 사고가 난다. 매 틱 모든 변수를 다 보내면 대역폭이 터지고, 서버 전용 값이나 임시 캐시까지 밖으로 샌다. 반대로 꼭 필요한 값을 빼먹으면 HP가 안 깎이고, 소유자가 안 맞고, 권한 판단이 꼬인다. "일단 다 훑자"로 가면 IOCP 워커와 게임 로직이 같은 자료를 만지는 지점도 늘어서 락이 많아지고, 단일스레드로 순서 맞춰 처리하던 장점도 흐려진다.

그래서 언리얼의 답은 단순해. 복제할 변수 명단을 먼저 만든다. 그 명단을 채우는 함수가 GetLifetimeReplicatedProps고, 명단에 이름 한 줄 올리는 도장이 DOREPLIFETIME이야. 여기서는 값을 보내는 게 아니라 "이 변수는 네트워크로 보낼 후보야"라고 표를 붙이는 단계다.

우리 서버로 치면 CM_ 요청을 처리한 뒤 SP_ 응답에 어떤 필드를 실을지 정하는 표를 미리 만들어두는 느낌이야. 표에 없는 필드는 버스에 못 탄다. 값이 진짜 바뀌었는지, 누구에게 보낼지, 언제 묶어서 보낼지는 그다음 문제고, 일단 "누가 후보인가"부터 정해야 한다.

왜 지금 배우냐면, 앞에서 ActorChannel이 "이 액터를 복제하자"는 흐름을 봤기 때문이야. 이제 채널은 액터 안에서 무엇을 볼지 알아야 한다. 이 챕터가 그 입구고, 다음 replayout, changelist에서 이 명단을 실제 메모리 배치와 변경 감지로 바꿔 전송으로 이어간다.

손님 명단부터 쓴다

파티를 연다고 해보자. 초대장을 아무한테나 다 뿌리진 않아. "누굴 부를지" 명단을 먼저 종이에 적지. 이름을 적어야 초대장이 나가고, 명단에 없는 사람은 그냥 안 온다.

네트워크 복제(replication)도 똑같아. 액터(Actor)에는 멤버 변수가 수십 개 있어. HP, 위치, 소유자, 이름, 임시 계산용 캐시... 근데 이걸 전부 네트워크로 클라한테 보내면 대역폭이 터지고, 애초에 보낼 필요도 없는 게 태반이야. 그래서 엔진은 묻는다.

"이 액터에서 어떤 변수를 복제할래? 명단 내놔."

이 "명단 내놓기"를 실제 코드로 구현한 게 이번 챕터의 주인공, GetLifetimeReplicatedProps 함수랑 그 안에서 이름 한 줄 한 줄 적는 DOREPLIFETIME 매크로야.

한 가지만 미리 못 박자. 이건 값을 보내는 코드가 아니야. HP가 100→90으로 바뀌었다고 여기서 90을 전송하는 게 아니라, "HP라는 변수는 복제 대상이다"라고 명단에 등록만 하는 단계야. 실제 값 비교·전송은 나중 챕터(→ replayout, changelist)가 한다. 여기선 "누굴 부를지"만 정한다.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호가 보이면 바로 아래 🔤 상자에서 하나하나 풀어줄게. 코드를 다 외우는 게 아니라 "아, 이게 이거구나"만 잡으면 돼.

명단을 채우는 진입점

엔진이 액터한테 "명단 내놔" 하고 부르는 함수가 이거야.

• void = 이 함수는 답을 돌려주지 않는다는 뜻(결과는 아래 &로 넘겨받은 배열에 담아 내보내).

• & = "복사본 말고 원본을 직접 넘겨받는다". 그래서 여기 적으면 바깥의 진짜 명단이 채워져.
• const = "이 함수는 캐릭터 자신을 안 바꾼다"는 약속(명단만 적지 값은 안 건드림).

천천히 보자. 함수 시그니처의 핵심은 인자 하나야.

TArray< FLifetimeProperty > & OutLifetimeProps

OutLifetimeProps는 빈 명단 종이야. 이름 앞에 Out이 붙은 건 "이 함수가 채워서 돌려주는 출력용 배열"이라는 뜻이지. 엔진이 빈 배열을 들고 와서 함수한테 건네주면, 함수가 여기다 등록 항목을 하나씩 적어 넣는다. 함수는 return 값이 없어(void) — 결과는 전부 이 배열에 담겨 나간다.

🔁 이제 이 눈으로 첫 줄을 다시 보자. void(답 안 돌려줌) → AActor::(AActor 소속) → GetLifetimeReplicatedProps(복제 명단 가져오기) → (TArray<FLifetimeProperty>& OutLifetimeProps)(원본 명단 종이를 받아) → const(캐릭터는 안 바꾸고). 이어 읽으면 "빈 명단 종이를 받아 거기다 보낼 정보를 적어 내보내는 함수." 아까는 외계어였는데 이제 읽히지?

그 아래 DOREPLIFETIME_WITH_PARAMS_FAST(AActor, Role, ...) 한 줄이 바로 "명단에 Role이라는 이름 적기"야. AActor가 기본으로 복제하는 것들 — 소유자(Owner), 역할(Role), 숨김 여부(bHidden), 이동 복제 여부(bReplicateMovement)... 게임 액터라면 누구나 갖는 뼈대 속성들이 여기서 등록된다.

SharedParams.bIsPushBased = true 이 줄은 지금은 그냥 "이 속성들은 Push Model이라는 최적화를 쓴다" 정도로만 넘겨. 매 틱 값 비교 대신, 바뀔 때만 코드가 "나 dirty!" 하고 손드는 방식이야. 자세한 건 → push-model.

명단은 상속된다 — Super 체인

여기서 첫 반전. APawn(폰, 조종 가능한 캐릭터의 부모)은 자기만의 명단을 새로 쓸까?

맞춰봐. APawn도 AActor를 상속받으니까, 폰을 복제하려면 AActor의 기본 속성(Owner, Role, bHidden...)도 다 필요하겠지. 그럼 폰의 GetLifetimeReplicatedProps는 그 8개를 또 복사해서 적을까?

아니야. 봐봐.

Pawn.cpp:1277

void APawn::GetLifetimeReplicatedProps( TArray< FLifetimeProperty > & OutLifetimeProps ) const { Super::GetLifetimeReplicatedProps( OutLifetimeProps ); DOREPLIFETIME( APawn, PlayerState ); DOREPLIFETIME( APawn, Controller ); // Deprecated RemoteViewPitch, still loaded for old replays PRAGMA_DISABLE_DEPRECATION_WARNINGS DOREPLIFETIME_CONDITION( APawn, RemoteViewPitch, COND_ReplayOnly ); PRAGMA_ENABLE_DEPRECATION_WARNINGS DOREPLIFETIME_CONDITION( APawn, RemoteViewPitch16, COND_SkipOwner ); }

첫 줄이 전부야.

Super::GetLifetimeReplicatedProps( OutLifetimeProps );

Super는 부모 클래스(AActor)를 가리켜. 그러니까 폰은 자기 명단을 쓰기 전에, 먼저 부모한테 같은 종이(OutLifetimeProps)를 넘겨서 부모 몫을 먼저 채우게 한다. 부모가 Owner·Role·bHidden 8개를 적어 넣고 돌아오면, 그제야 폰이 그 아래에 자기 것(PlayerState, Controller)을 이어 적어. 명단 한 장이 부모→자식으로 내려오며 누적되는 거지.

ACharacter(캐릭터, 폰의 자식)도 똑같이 맨 위에서 Super::를 불러(Character.cpp:1718). 그래서 캐릭터 하나를 복제하면 명단은 이렇게 층층이 쌓인다.

AActor 몫 (Role, Owner, bHidden, ...) ← Super 체인 맨 바닥 + APawn 몫 (PlayerState, Controller) + ACharacter 몫 (조건부 속성들) ← 실제로 호출된 클래스

이게 왜 중요하냐면, Super::를 빼먹으면 부모 속성이 통째로 명단에서 빠져서 위치·소유자 복제가 조용히 안 되는 버그가 나. 오버라이드 첫 줄에 Super:: — 이건 거의 법이야.

"누구한테" 보낼지도 명단에 적는다 — CONDITION

위 코드에서 이런 줄 봤지?

DOREPLIFETIME_CONDITION( APawn, RemoteViewPitch16, COND_SkipOwner );

DOREPLIFETIME은 "전원에게 보내"지만, DOREPLIFETIME_CONDITION은 필터를 하나 단다. COND_SkipOwner는 "소유자(본인)한테는 보내지 마"라는 뜻이야. 내 캐릭터가 지금 어디를 보고 있는지(ViewPitch)는 나 자신은 이미 아는 값이니까, 굳이 서버가 나한테 되돌려줄 필요가 없거든. 남들한테만 보내면 돼.

ACharacter는 COND_SimulatedOnly(내가 직접 조종하지 않는, 시뮬레이트되는 남의 캐릭터한테만)를 쓰기도 해(Character.cpp:1723). 이 조건 필터의 전체 목록과 동작 원리는 → rep-conditions.

핵심만: 명단에 이름만 적는 게 아니라, "누구한테 보낼지" 조건표까지 같이 적는다. 그 조건을 담는 그릇이 FDoRepLifetimeParams 구조체야.

UnrealNetwork.h:134

Condition(누구에게), RepNotifyCondition(바뀌면 콜백 부를지 → repnotify), bIsPushBased(Push Model 쓸지). 그냥 DOREPLIFETIME(c,v)를 쓰면 이 구조체의 기본값(COND_None = 전원)이 들어간다.

🔤 struct = 여러 값을 한 묶음으로 든 상자. 여기선 "명단 메모"를 담는 상자야 — 안에 세 칸(누구에게 / 바뀌면 알림 줄지 / Push 쓸지). 칸 옆의 = COND_None처럼 =는 그 칸의 기본값을 미리 정해두는 것.

매크로 한 줄이 실제로 하는 일

이제 DOREPLIFETIME 한 줄을 열어보자. 마법처럼 보이지만 매크로일 뿐이야. 컴파일러가 이 한 줄을 이렇게 펼친다.

🔤 매크로(#define) = "이 글자를 보면 저 긴 코드로 바꿔치기해라"라고 컴파일러에 시키는 것. DOREPLIFETIME이라고 짧게 쓰면 컴파일러가 그 자리에 아래 긴 코드를 펼쳐 넣어. 마법이 아니라 글자 치환이야.

UnrealNetwork.h:250

#define DOREPLIFETIME_WITH_PARAMS(c,v,params) \ { \ static_assert(ValidateReplicatedClassInheritance<c, ThisClass>(), #c "." #v " is not accessible from this class."); \ FProperty* ReplicatedProperty = GetReplicatedProperty(StaticClass(), c::StaticClass(), GET_MEMBER_NAME_CHECKED(c,v)); \ PRAGMA_DISABLE_DEPRECATION_WARNINGS \ RegisterReplicatedLifetimeProperty(ReplicatedProperty, OutLifetimeProps, FixupParams<decltype(c::v)>(params)); \ PRAGMA_ENABLE_DEPRECATION_WARNINGS \ } #define DOREPLIFETIME(c,v) DOREPLIFETIME_WITH_PARAMS(c,v,FDoRepLifetimeParams())

맨 아랫줄부터 보자. DOREPLIFETIME(c,v)는 그냥 DOREPLIFETIME_WITH_PARAMS(c,v,FDoRepLifetimeParams())의 축약이야 — 기본 조건 구조체를 하나 넣어서 위 매크로를 부르는 것뿐. DOREPLIFETIME(APawn, PlayerState)라고 쓰면 세 가지 일이 순서대로 벌어진다.

  1. GetReplicatedProperty(...) — 변수 v의 이름으로 실제 FProperty*(그 멤버의 메타 정보)를 찾아온다. 그리고 검사한다.
  2. RegisterReplicatedLifetimeProperty(...) — 찾아온 프로퍼티를 명단(OutLifetimeProps)에 실제로 추가한다.

GET_MEMBER_NAME_CHECKED(c,v)는 "컴파일 시점에 c에 v라는 멤버가 진짜 있는지" 확인해주는 안전장치야. 오타 나면 컴파일이 안 돼. 첫 관문이지.

🔁 다시 매크로를 보자. 이제 DOREPLIFETIME(APawn, PlayerState)는 "PlayerState를 찾아서(검사 포함) 명단에 추가해라"로 읽혀. 마법이 아니라 함수 두 번 부르는 것으로 펼쳐질 뿐이었어.

관문 1 — "Replicated 안 붙였지?" 즉사 검사

여기가 초보자가 제일 많이 밟는 지뢰야. GetReplicatedProperty를 열어보자.

UnrealNetwork.h:218

/** wrapper to find replicated properties that also makes sure they're valid */ inline FProperty* GetReplicatedProperty(const UClass* CallingClass, const UClass* PropClass, const FName& PropName) { FProperty* TheProperty = FindFieldChecked<FProperty>(PropClass, PropName); #if !(UE_BUILD_SHIPPING || UE_BUILD_TEST) if (!(TheProperty->PropertyFlags & CPF_Net)) { UE_LOG(LogNet, Fatal,TEXT("Attempt to replicate property '%s' that was not tagged to replicate! Please use 'Replicated' or 'ReplicatedUsing' keyword in the UPROPERTY() declaration."), *TheProperty->GetFullName()); } #endif return TheProperty; }
🔤 관문1 기호 풀이
• CPF_Net = 변수에 붙는 "나 복제돼도 됨" 딱지. 헤더에서 UPROPERTY(Replicated)로 선언해야 붙어.
• & CPF_Net = 그 딱지가 붙어 있나 확인. 앞의 !(...)는 "안 붙어 있으면".
• UE_LOG(..., Fatal, ...) = 로그 등급이 Fatal(치명적) = 게임을 그 자리에서 꺼버림(경고가 아니라 크래시).
• #if ... #endif = 이 검사는 개발 빌드에서만 돎(출시 빌드엔 없음). 개발 중에 미리 잡으라는 뜻.

가운데 if가 관문이야. CPF_Net은 프로퍼티에 붙는 플래그인데, 헤더에서 변수를 이렇게 선언했을 때만 켜진다.

UPROPERTY(Replicated) // ← 이 Replicated 키워드가 CPF_Net 플래그를 세운다 int32 Health;

만약 헤더에 Replicated를 안 붙였는데 .cpp에서 DOREPLIFETIME(AMyActor, Health)를 적으면? CPF_Net 플래그가 없으니 if 안으로 들어가서 —

UE_LOG(LogNet, Fatal, ...)

Fatal. 게임이 즉사한다. 경고가 아니라 크래시야. 왜 이렇게 세게 막냐면, 이건 거의 항상 실수거든.

🔁 다시 그 if를 읽자. if (!(TheProperty->PropertyFlags & CPF_Net)) = "이 변수에 복제 딱지가 안 붙어 있으면" → 안에서 Fatal로 종료. 한 줄로: "복제 딱지도 없이 명단에 올렸으면, 그 자리에서 죽인다." "복제 등록은 했는데 정작 변수엔 복제 표시를 안 단" 반쪽짜리 상태니까.

여기서 배울 핵심: 복제는 항상 두 곳이 짝을 이뤄야 한다.

  • 헤더의 UPROPERTY(Replicated) — "이 변수는 복제 가능하다" (선언)
  • .cpp의 DOREPLIFETIME — "이 변수를 명단에 올린다" (등록)

한 짝만 있으면 안 돼. #if !(UE_BUILD_SHIPPING || ...) 로 감싼 건, 이 검사가 개발 빌드에서만 돌고 출시 빌드에선 빠진다는 뜻 — 개발 중에 미리 다 잡으라는 얘기지.

관문 2 — 명단에 실제로 추가 (+ 중복 방어)

검사를 통과한 프로퍼티는 이제 명단에 실제로 올라간다.

UnrealNetwork.cpp:48

for (int32 i = 0; i < PropertyDescriptor.ArrayDim; i++) { const uint16 RepIndex = PropertyDescriptor.RepIndex + i; FLifetimeProperty* RegisteredPropertyPtr = OutLifetimeProps.FindByPredicate([&RepIndex](const FLifetimeProperty& Var) { return Var.RepIndex == RepIndex; }); FLifetimeProperty LifetimeProp(RepIndex, Params.Condition, Params.RepNotifyCondition, Params.bIsPushBased); LifetimeProp.CreateAndRegisterReplicationFragmentFunction = Params.CreateAndRegisterReplicationFragmentFunction; if (RegisteredPropertyPtr) { // Disabled properties can be re-enabled via DOREPLIFETIME if (RegisteredPropertyPtr->Condition == COND_Never) { // Copy the new conditions since disabling a property doesn't set other conditions. (*RegisteredPropertyPtr) = LifetimeProp; } else { // Conditions should be identical when calling DOREPLIFETIME twice on the same variable. checkf((*RegisteredPropertyPtr) == LifetimeProp, TEXT("Property %s was registered twice with different conditions (old:%d) (new:%d)"), PropertyDescriptor.PropertyName, RegisteredPropertyPtr->Condition, Params.Condition); } } else { OutLifetimeProps.Add(LifetimeProp); } }

여기서 딱 두 가지만 잡고 가자.

🔤 관문2 기호 풀이
• RepIndex = 복제 대상 변수마다 엔진이 매긴 정수 번호. 명단은 "Health" 글자 대신 이 번호로 항목을 구분해(글자 비교는 느리고, 네트워크로도 번호가 쌈).
• FindByPredicate([&RepIndex](...){ ... }) = "명단에서 조건 맞는 항목 찾기". 대괄호 [...]로 시작하는 건 람다 = 즉석에서 만든 작은 함수. 있으면 그 위치, 없으면 빈손.
• checkf(조건, "메시지") = 조건이 참이면 통과, 거짓이면 메시지 남기고 죽음(개발용 안전장치).

첫째, 명단 항목은 변수 "이름"이 아니라 RepIndex(정수)로 관리된다.

const uint16 RepIndex = PropertyDescriptor.RepIndex + i;

복제 대상 프로퍼티마다 엔진이 정수 번호(RepIndex)를 매겨둬. 명단(FLifetimeProperty)은 문자열 이름 대신 이 번호로 항목을 식별한다. 문자열 비교는 느리고, 네트워크로 실을 때도 "Health"라는 글자보다 번호 하나가 훨씬 싸니까. 맨 아래 진짜 등록도 결국 이 한 줄이야.

OutLifetimeProps.Add(LifetimeProp);

이게 명단에 한 줄 추가되는 최종 지점(UnrealNetwork.cpp:73). 손님 명단에 이름 한 명 적히는 순간.

둘째, 같은 변수를 두 번 등록하면? 위쪽 if (RegisteredPropertyPtr)가 그 경우야. 이미 같은 RepIndex가 명단에 있으면 —

checkf((*RegisteredPropertyPtr) == LifetimeProp, TEXT("Property %s was registered twice with different conditions ..."))

조건이 같으면 조용히 넘어가지만(같은 걸 두 번 적었을 뿐이니 무해), 조건이 다르면 checkf가 터진다. 예를 들어 한 곳에서 COND_None(전원), 다른 곳에서 COND_SkipOwner(본인 제외)로 같은 변수를 등록하면 — 엔진 입장에선 "얘를 전원한테 보내라는 거야 말라는 거야?" 모순이니까 크래시로 알려준다. (COND_Never로 비활성화된 건 예외로, DOREPLIFETIME로 다시 켤 수 있게 덮어쓴다 — 위쪽 if 분기.)

우리 서버랑 비교해보자

우리 조선협객전 게임 서버는 IOCP 워커 스레드 여러 개가 패킷을 받아서, 각자 CChosunPlayer 같은 객체의 상태를 직접 만지지. "무슨 필드를 클라에 보낼지"는 우리가 손으로 짠 SP_* 송신 구조체에 멤버를 직접 나열하는 거고 — 어떤 필드를 넣을지는 그 구조체 정의와 SetMsgSize가 곧 "명단"인 셈이야.

UE는 이걸 선언적(declarative)으로 뒤집었어.

  • 우리: "이 상황엔 이 필드들을 담아 이 패킷을 만들어 보내라"를 매 전송 코드마다 손으로 조립.
  • UE: GetLifetimeReplicatedProps에 "복제할 변수 명단"만 등록해두면, 값이 바뀔 때 엔진이 알아서 diff 떠서 보낸다. 전송 코드를 매번 안 짠다.

그리고 실행 모델이 결정적으로 달라. UE의 복제 계산은 단일 스레드(game thread)에서 액터를 순회하며 돈다 — 우리 서버가 겁내는 "여러 IOCP 워커가 같은 객체를 동시에 건드려 데이터 레이스" 걱정이 여기선 구조적으로 없어. 대신 그 한 스레드가 프레임 안에 모든 액터의 복제를 다 처리해야 하니까, 명단을 짧게 유지하고 조건(COND_*)으로 대상을 좁히는 게 곧 성능이야. 우리가 "빈번한 경로에 동기 DB 호출 금지"로 워커를 지키듯, UE는 "필요 없는 변수는 명단에서 빼기 / 조건 걸기"로 그 한 스레드를 지킨다. 같은 문제, 정반대 무기.

이 챕터에서 딱 이것만 가져가

  • GetLifetimeReplicatedProps는 액터가 "복제할 변수 명단"을 엔진에 신고하는 오버라이드 함수. 출력용 배열 OutLifetimeProps를 채워 돌려준다.
  • DOREPLIFETIME(클래스, 변수)는 명단에 한 줄 적는 매크로. 값을 보내는 게 아니라 등록 선언일 뿐.
  • 오버라이드 첫 줄 Super::로 부모 명단을 먼저 상속받아 누적한다.
  • 헤더의 UPROPERTY(Replicated)와 .cpp의 DOREPLIFETIME는 반드시 짝. 한쪽만 있으면 Fatal 크래시.
  • "누구에게 보낼지"는 COND_* 조건으로 같은 명단에 함께 적는다.

막히면 → actorchannel-replicate (이 명단을 누가/언제 들고 도는지), server-replicate-actors (복제 큰 그림) 다음 → replayout (등록된 명단으로 실제 값을 어떻게 비교·전송하는지), rep-conditions (COND_* 필터 전모), repnotify (값 바뀌면 콜백), push-model (bIsPushBased의 정체)

🎯 원리 한 줄 요약

GetLifetimeReplicatedProps는 "복제할 변수 명단"을 신고하는 창구고, DOREPLIFETIME은 그 명단에 이름 한 줄 적는 등록 도장이다 — 값 전송이 아니라 손님 명단 작성이다.
