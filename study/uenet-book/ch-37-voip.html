VoIP: 인게임 음성 채널

언리얼 네트워크 · 37 / 43

왜 이걸 배워? — 문제의식부터

게임 서버를 짜봤으면 채팅 릴레이는 이미 알아. CM_CHAT 같은 패킷이 들어오면, 서버가 "이 말을 들을 사람들"을 골라서 SP_CHAT처럼 다시 뿌리지. 우리 조선 서버로 치면 CChosunPlayer가 속한 파티, 맵, 길드 사람들을 훑고, IOCP가 받은 요청을 결국 단일스레드 게임 로직 쪽에서 정리해서 보내는 흐름이야.

그런데 음성은 채팅보다 훨씬 까다로워. 글자 한 줄은 조금 늦어도 읽을 수 있지만, 소리는 1초만 밀려도 로봇처럼 들리고, 오래된 목소리가 뒤늦게 오면 차라리 안 오는 게 나아. 게다가 100명이 있는 방에서 20명이 동시에 말하면, 서버는 "누가 누구 목소리를 들어도 되는지"를 계속 판정해야 해. 이걸 아무 생각 없이 전원에게 다 뿌리면 CPU도 대역폭도 금방 터진다.

여기서 더 위험한 착각이 있어. "음성은 그냥 P2P로 직접 보내면 되지 않나?" 싶지만, 게임 서버 관점에서는 그럼 규칙을 강제하기가 어려워져. 음소거, 팀 보이스, 거리 기반 보이스, 차단 목록 같은 판단은 서버가 잡고 있어야 해. 우리 서버에서 클라가 마음대로 SP_*를 만들어 뿌리게 두지 않는 것처럼, UE도 내 목소리를 일단 서버로 올리고 서버가 자격 있는 사람에게만 되뿌리는 쪽을 기본 뼈대로 삼아.

그래서 이 챕터의 답이 UVoiceChannel과 UNetDriver::ReplicateVoicePacket이야. UVoiceChannel은 연결마다 붙은 "소리 전용 송신 줄"이고, ReplicateVoicePacket은 채팅 릴레이처럼 받은 음성 조각을 다른 클라들의 Voice 채널 큐에 나눠 넣는 함수야. 락을 잔뜩 걸어 여러 스레드가 뒤엉키게 하기보다, 연결별 큐에 쌓고 Tick에서 흘려보내는 방식이라 우리 단일스레드 처리 감각과도 잘 맞아.

지금 이걸 배우는 이유는, 앞에서 배운 채널·Bunch·reliable/unreliable·핸드셰이크가 실제 기능 하나에 한꺼번에 붙는 장면이 바로 음성이기 때문이야. Actor 복제처럼 "꼭 도착해야 하는 데이터"와 달리, 음성은 "옛날 것보다 지금 것"이 더 중요해. 그래서 이 챕터를 보면 UE 네트워크가 기능 성격에 따라 같은 연결 위에서도 전혀 다른 전송 규칙을 고르는 감이 잡힌다.

채팅은 글자, 음성은 소리 — 근데 흐르는 길은 똑같다

게임 서버 짜봤으면 채팅 패킷은 익숙하지. 클라가 문자열 하나 서버로 던지면, 서버가 같은 방/길드 사람들한테 되뿌린다. 원리는 단순해. "한 명이 보낸 걸 → 자격 있는 여럿에게 → 복사해서 뿌린다."

음성 채팅도 뼈대는 글자 한 판 다를 게 없어. 문자열 대신 압축된 소리 조각(음성 패킷)이 흐를 뿐이야. 한 명이 마이크에 대고 말하면 → 서버가 → 같은 채널 사람들에게 → 그 소리 조각을 복사해 뿌린다. 딱 채팅 릴레이의 음성 버전인 거지.

그런데 여기서 초보가 가장 크게 헷갈리는 지점이 하나 있어. "음성이면 P2P 아냐? 마이크 켠 사람이 상대방한테 직접 쏘는 거 아냐?" 아니야. UE 기본 모델은 서버 권위야. 내 목소리는 일단 서버로 올라가고, 서버가 "이 사람 목소리를 저 사람이 들을 자격이 있나" 판정한 다음 되뿌려. P2P가 아니라 채팅이랑 똑같은 서버 릴레이. (음소거·거리·팀 제한을 서버가 강제하려면 이래야 하거든.)

이걸 실제로 구현한 게 이번 챕터 주인공이야:

  • UVoiceChannel (VoiceChannel.h / VoiceChannel.cpp) — 음성 패킷만 나르는 전용 채널
  • UNetDriver::ReplicateVoicePacket (NetDriver.cpp) — 서버가 다른 클라들에게 되뿌리는 릴레이
채널이 뭔지, 연결 안에서 채널들이 어떻게 나뉘는지가 흐릿하면 → channel-types 먼저 보고 와. Voice 채널이 Control/Actor 채널이랑 어떻게 다른지 거기서 잡아. 여기선 다시 설명 안 하고 링크로 넘길게 — 안 그러면 챕터마다 같은 얘기 무한 반복이거든.

지금부터 실제 UE 코드가 나와. 겁먹지 마 — UCLASS, TSharedPtr, -> 같은 기호는 바로 아래 🔤 상자에서 하나씩 풀어줄 거야. 코드를 외우는 게 아니라, 음성 패킷이 어디에 쌓이고 어디로 나가는지만 따라가면 돼.

🌱 이 개념은 왜 생겼나 — Voice 채널(음성 전용 통로)
• 원래 구조: 연결 하나에 채널 여러 개가 흘러(Control·Actor…). 음성도 그냥 아무 채널에 같이 실으면 되잖아?
• 그런데 문제: 음성은 성격이 아주 달라 — 초당 수십 조각씩 쏟아지고, 옛날 소리는 차라리 안 오는 게 나아. 액터 복제("하나도 놓치면 안 돼")랑 같은 줄에 태우면 서로 방해돼.
• 그래서 필요한 것: 소리만 나르는 전용 채널에 자기 큐를 하나 두고, 틱마다 몰아 내보내자. → 이게 UVoiceChannel이야. 채팅 릴레이의 컨베이어 벨트 버전.

1. Voice 채널 = 소리만 싣는 전용 통로

먼저 채널 그릇부터. Voice 채널은 UChannel을 상속한 자식인데, 남들과 다른 딱 하나의 살림살이를 들고 있어 — 내보낼 음성 패킷 큐.

VoiceChannel.h:18-26

UCLASS(transient, customConstructor, MinimalAPI) class UVoiceChannel : public UChannel { GENERATED_UCLASS_BODY() // Variables. /** The set of outgoing voice packets for this channel */ FVoicePacketList VoicePackets;
🔤 기호 사전 — UCLASS(...) / class UVoiceChannel : public UChannel
• UCLASS(...) = UE한테 "이건 엔진이 관리하는 클래스야" 하고 붙이는 이름표. 괄호 안은 이 클래스의 성격 메모야.
• transient = 저장 파일에 오래 보관하는 물건이 아니라, 실행 중 잠깐 쓰는 물건이라는 뜻.
• customConstructor = 생성자 만드는 방식을 UE 쪽 규칙에 맞춘다는 표시. 엔진용 설정 메모라고 보면 돼.
• MinimalAPI = 다른 모듈에 꼭 필요한 만큼만 공개한다는 표시.
• class ... : public ... = "UVoiceChannel은 UChannel의 자식"이라는 상속 표시. 부모가 가진 기본 채널 기능을 물려받아.
• GENERATED_UCLASS_BODY() = UE 코드 생성기가 필요한 기본 부품을 끼워 넣는 매크로. 사람이 직접 다 쓰지 않는 접착제야.
• FVoicePacketList VoicePackets; = FVoicePacketList라는 대기열 상자를 VoicePackets라는 이름으로 하나 들고 있다는 뜻.
• ; = 한 코드 문장이 끝났다는 마침표.
🔁 이제 다시 보자. UVoiceChannel : public UChannel(채널의 자식) → GENERATED_UCLASS_BODY()(UE 기본 부품) → FVoicePacketList VoicePackets(보낼 음성 줄). 이어 읽으면 "Voice 채널은 일반 채널 기능을 물려받고, 자기 안에 보낼 음성 패킷 줄 하나를 들고 있는 클래스"야.

FVoicePacketList VoicePackets — 이게 이 채널의 전부라고 봐도 돼. "아직 안 보낸 음성 패킷들이 줄 서 있는 대기열"이야. 액터 채널이 액터 하나를 붙잡고 복잡한 프로퍼티 복제를 하는 것과 달리, Voice 채널은 그냥 이 큐에 쌓고 → 틱마다 비워 내보내는 단순한 컨베이어 벨트야.

여기서 FVoicePacket은 "압축된 소리 조각 하나", FVoicePacketList는 "그 조각들의 큐"라고만 알아두면 돼. 실제 음성을 어떤 코덱으로 어떻게 압축하는지는 온라인 서브시스템/플러그인 몫이라 이 챕터 범위 밖이야.

2. 큐에 쌓기 — 두 방향의 입구

음성 패킷이 이 큐에 들어가는 문(門)은 딱 하나야. AddVoicePacket.

• void = 이 함수는 값을 돌려주지 않는다. 큐에 넣는 일을 하고 끝.

• TSharedPtr<FVoicePacket> = FVoicePacket을 여러 곳이 같이 들 수 있는 공유 손잡이. 마지막 손잡이가 놓이면 자동 정리돼.
• if (...) = 괄호 안 조건이 맞을 때만 안쪽을 실행해.
• .IsValid() = 이 공유 손잡이가 진짜 패킷을 가리키고 있나 확인.
• .Add(...) = 리스트/큐 끝에 새 항목을 하나 붙여 넣기.

단순하지? 유효한 패킷이면 큐에 Add. 끝. 그런데 이 문을 누가 두드리냐가 방향에 따라 달라. 여기가 이 시스템의 핵심 갈림길이야.

  • 클라 → 서버 (내 목소리 올리기): 내 마이크에서 뽑힌 음성 패킷을 ServerConnection->GetVoiceChannel()에 AddVoicePacket. 즉 "서버로 가는 연결"의 Voice 채널에 쌓아. (UNetDriver::ProcessLocalClientPackets — NetDriver.cpp:1592)
  • 서버 → 다른 클라들 (남의 목소리 뿌리기): 서버가 릴레이 판정을 거친 뒤, 받을 자격 있는 각 클라 연결의 Voice 채널에 같은 패킷을 AddVoicePacket. (ReplicateVoicePacket 안에서 — 다음 절)

TSharedPtr<FVoicePacket>라는 타입에 주목해. 레퍼런스 카운트 공유 포인터야. 서버가 한 화자의 목소리를 30명한테 뿌린다고 30번 복사하는 게 아니라, 같은 패킷 하나를 여러 채널 큐가 공유 포인터로 나눠 들어. 마지막 큐가 다 쓰고 놓으면 그때 자동 해제. 릴레이할 때 메모리 안 터지게 하는 장치야.

🌱 이 개념은 왜 생겼나 — 서버 릴레이(음성이 P2P가 아닌 이유)
• 원래 구조: 음성이면 마이크 켠 사람이 상대한테 직접 쏘면(P2P) 제일 빠르잖아. 서버 안 거치고.
• 그런데 문제: 그럼 음소거·팀 보이스·거리 제한·차단 목록을 누가 강제해? 클라끼리 직접 쏘면 서버가 규칙을 못 잡아. 우리 서버에서 클라가 SP_*를 제멋대로 만들어 뿌리게 두지 않는 것과 같아.
• 그래서 필요한 것: 내 목소리를 일단 서버로 올리고, 서버가 "이 사람 목소리 저 사람이 들을 자격 있나" 판정한 뒤 되뿌리자. → 이게 ReplicateVoicePacket 서버 릴레이야.

3. 서버 릴레이 — 채팅 되뿌리기의 음성판

이제 도입에서 말한 "서버 권위 릴레이"의 실물이야. 서버가 한 명의 목소리를 받으면, 전 클라 연결을 훑으면서 되뿌려.

🔁 이제 다시 보자. for(모든 클라 연결 훑기) → CameFromConn != Conn(원 발신자는 빼기) → ShouldReplicateVoicePacketFrom(들을 자격 판정) → GetVoiceChannel()->AddVoicePacket(통과한 연결의 음성 큐에 넣기). 이어 읽으면 "서버가 모든 연결을 보며, 들을 자격 있는 사람의 Voice 큐에 같은 음성 패킷을 넣는 릴레이 함수"야.

천천히 뜯어보자. 세 개의 관문이 순서대로 있어:

  1. if (CameFromConn != Conn) — 원발신자는 건너뛴다. 내가 말한 목소리가 나한테 되돌아오면 이상하잖아. (채팅 에코 방지랑 똑같아.)
  2. Conn->ShouldReplicateVoicePacketFrom(...) — "이 연결이 저 화자의 목소리를 받을 자격이 있나?" 판정. 음소거 목록·팀·거리 같은 규칙이 여기서 걸러져. 이 한 줄이 "서버 권위"의 심장이야. 클라가 아니라 서버가 "너 이 사람 목소리 들어도 돼"를 결정해.
  3. Conn->GetVoiceChannel() → AddVoicePacket — 통과한 연결의 Voice 채널 큐에 적재.

여기서 예측 한번 해보자. for 루프가 ClientConnections 전체를 돈다는 건, 서버가 목소리 하나를 받을 때마다 접속자 전원을 순회한다는 뜻이야. 100명이 동시에 떠들면? 한 프레임에 몇 번의 순회가 돌까?

맞춰봐. "100번" 같아? 틀려 — 100 × 100, 즉 만 번에 가까워. 화자 100명 각각의 패킷마다 전 연결 100명을 훑으니까 O(N²)이야. 그래서 UE 음성은 규모가 커지면 릴레이 비용이 급격히 늘고, 실무에선 거리/팀 기반 ShouldReplicateVoicePacketFrom으로 후보를 확 줄이거나 별도 음성 서버로 빼는 거야. "전원 순회"라는 소박한 코드 뒤에 스케일 함정이 숨어 있는 거지.

주석 처리된 bReplicateAsPeer 줄들 보이지? UE엔 P2P(peer) 음성 경로도 개념상 있었는데 지금 코드는 서버 릴레이만 살아있고 peer 경로는 통째로 주석이야. 도입에서 "P2P 아니라 서버 권위"라 한 게 코드로 증명되는 지점이야.

4. 채널을 어떻게 찾나 — 고정 슬롯 조회

🌱 이 개념은 왜 생겼나 — unreliable 음성(최신성 우선)
• 원래 구조: 데이터는 다 확실히 도착시키는 게 좋지(reliable). 빠지면 재전송해서 기어이 보내고.
• 그런데 문제: 음성은 망이 막혔을 때 밀린 조각을 기어이 다 밀어내면 옛날 목소리가 뒤늦게 로봇처럼 들려. 1초 밀린 소리는 차라리 안 오는 게 나아. "빠짐없이"가 오히려 독이야.
• 그래서 필요한 것: 웬만한 음성 조각은 도착 보장 안 하고, 망 막히면 그냥 버리는 전송. → 이게 unreliable이야. 액터 복제와 정반대 선택 — "옛것 붙들지 말고 지금 것만".

5. 틱마다 큐 비우기 — 핸드셰이크와 신뢰성의 갈림길

큐에 쌓기만 해선 소리가 안 흘러. 실제로 네트워크에 밀어내는 건 매 프레임 도는 Tick이야. 여기가 "음성 데이터가 어떻게 다뤄지느냐"의 규칙이 다 박혀 있는 곳이야.

🔁 이제 다시 보자. bHandshakeCompleted(음성 준비 완료?) → for(큐를 앞에서부터 훑기) → IsNetReady(망이 막혔나?) → Bunch.bReliable = ...(이번 묶음 신뢰성 결정) → Serialize(음성을 번치에 담기). 이어 읽으면 "준비됐고 망도 괜찮을 때, 큐의 음성 패킷을 번치에 담아 내보낼 준비를 하는 틱 함수"야.

세 개의 관문이 또 순서대로 있어:

  1. 핸드셰이크 관문 — bHasVoiceHandshakeCompleted가 아직이면 이 if 블록을 통째로 안 타. 주석 그대로 "핸드셰이크 안 끝났으면 unreliable 음성은 다 버린다". 연결이 음성 준비가 끝나기 전에 새어나간 목소리 조각은 그냥 폐기돼. 미리 쌓인 소리로 상대가 놀라는 일 없게.
  2. 망 포화 관문 — if (!Connection->IsNetReady()). 네트워크가 꽉 찼으면 Network saturated 경고 찍고 break로 즉시 중단. 남은 음성 패킷은 이번 틱에 안 보내. 음성은 최신성이 생명이라, 밀린 걸 억지로 다 밀어내느니 포기하는 게 나아.
  3. 신뢰성 관문 — Bunch.bReliable = OpenAcked == false || Packet->IsReliable(). 채널 첫 송신(핸드셰이크 격)은 무조건 reliable, 그리고 명시적으로 reliable 표시된 패킷도 reliable. 그 외 일반 음성 조각은 unreliable — 도착 보장 안 하고 망 포화 때 그냥 드롭돼.

각 패킷은 FOutBunch에 Serialize돼서 (뒤이어 SendBunch로) 나가. Bunch는 채널이 주고받는 직렬화된 데이터 묶음 단위야. 음성 패킷을 Bunch에 담아 보내고, 받는 쪽은 Bunch에서 되꺼내. (Bunch가 raw 패킷과 뭐가 다른지는 → bunch-vs-packet.)

정리하면 이 Tick 하나에 "준비 안 됐으면 버리고 / 망 막히면 멈추고 / 웬만하면 unreliable로 최신 것만" 이라는 음성의 3대 원칙이 다 들어있어. 액터 복제가 "하나도 놓치면 안 돼"라면, 음성은 "옛날 것 붙들고 늘어지느니 지금 것만" 쪽이야. 성격이 정반대지.

while (!Bunch.AtEnd())로 번치 안의 음성 조각을 하나씩 SerializeRemotePacket으로 복원해. 그다음 조건이 결정적이야:

즉 콜체인이 이렇게 순환해: 클라A가 올린 목소리 → 서버 ReceivedBunch → (ServerConnection == NULL이라) ReplicateVoicePacket → 자격 있는 클라B·C의 Voice 채널 큐에 AddVoicePacket → 각자 Tick에서 송출 → 클라B·C의 ReceivedBunch(이번엔 ServerConnection 있으니 릴레이 안 하고 재생으로). 한 바퀴 도는 거야.

7. 재생측 — 이 클론엔 소리 나는 부분이 없다

리서치 단서의 VoipListenerSynthComponent(원격 음성을 실제 오디오로 합성 재생하는 컴포넌트)는 이 Engine 코어 소스 트리에 없어 (grep 0건). 얘는 엔진 코어가 아니라 OnlineSubsystemUtils 플러그인 소속이라 이 리포엔 안 딸려와. 그래서 "받은 음성 조각 → 실제 스피커 소리" 구간은 코드로 못 짚고 개념으로만 정리해.

한 문장으로: 내 목소리는 서버로 올라갔다가, 서버의 자격 판정을 거쳐, 들을 자격 있는 사람들에게만 되뿌려진다 — 채팅 릴레이의 소리 버전이고, 채널 큐 → Tick 송출 → ReceivedBunch가 한 바퀴 돈다.

9. 우리 서버랑 비교 — IOCP 릴레이 vs Voice 채널

조선협객전 서버 감각으로 매핑해보면 이래.

릴레이 구조:

  • 우리: 클라가 채팅 CM_CHAT 올리면, IOCP 워커가 핸들러에서 같은 채널/길드 세션들을 순회하며 SendPacket으로 되뿌려. "한 명 → 여럿 복사 전송"의 그 패턴.
  • UE: 클라가 음성 올리면, ReplicateVoicePacket이 ClientConnections를 순회하며 각 Voice 채널 큐에 AddVoicePacket. 똑같은 팬아웃 릴레이인데, UE는 중간에 "채널 큐"라는 버퍼를 한 겹 둬서 즉시 전송이 아니라 Tick에 몰아 보내는 게 차이. 우리는 핸들러에서 바로 쏘고, UE는 큐에 쌓았다가 프레임 경계에서 정리해 내보내.

단일 스레드 액터 대응: 우리 서버는 게임 로직이 싱글 스레드라 채팅 릴레이도 그 스레드에서 세션 리스트를 락 없이 훑어. UE 음성 릴레이도 게임 스레드에서 도는 로직이고, 각 연결의 Voice 채널이 자기 큐(VoicePackets)를 독립적으로 소유해서 서로 안 꼬여. "연결 하나 = Voice 채널 하나 = 그 연결 전용 음성 큐"라, 우리가 "세션 하나 = 그 유저 전용 송신 버퍼"로 상태를 격리하는 감각이랑 통해. 다른 연결의 음성이 이 큐를 건드릴 일이 없으니 락이 필요 없어.

성능 주의점 — 우리도 겪는 O(N²): 3절의 만 번 순회 함정, 우리 서버 채팅도 똑같아. 대형 채널에서 한 명 떠들 때마다 전원 순회하면 CPU 녹아. 우리가 채널 인원 제한·범위 필터로 팬아웃을 줄이듯, UE도 ShouldReplicateVoicePacketFrom으로 후보를 쳐내는 거야. 음성은 채팅보다 패킷 빈도가 훨씬 높아서(초당 수십 조각) 이 함정이 더 치명적이라는 것만 기억해. 우리 서버에 음성 붙일 일 있으면 릴레이 순회부터 설계하는 게 1순위야.

마무리 — 어디로 이어지나

이 챕터는 "음성이 채널을 타고 서버 릴레이로 흐르는 뼈대"까지만. 음성 코덱·오디오 합성·실제 재생은 플러그인 영역이라 뼈대 밖이야.

  • 막히면(채널이 뭔지, Voice가 Control/Actor와 어떻게 다른지) → channel-types
  • 막히면(Bunch가 raw 패킷과 뭐가 다른지) → bunch-vs-packet
  • 막히면(수신 데이터가 채널까지 어떻게 흘러오나) → receive-callchain
  • 다음(reliable/unreliable·ack 재전송 원리 — Voice는 unreliable 쪽) → reliability-ack
  • 다음(음성 핸드셰이크가 얹히는 연결 수립 전체 흐름) → handshake

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. 인게임 음성, P2P로 직접 쏘면 되지 왜 서버를 거치나요?

답 보기
P2P가 제일 빠르긴 해. 근데 그럼 음소거·팀 보이스·거리 제한·차단 목록을 누가 강제하지? 클라끼리 직접 쏘면 서버가 규칙을 못 잡아. 우리 서버에서 클라가 SP_*를 제멋대로 만들어 뿌리게 두지 않는 것과 똑같아. 그래서 UE 기본 모델은 내 목소리를 일단 서버로 올리고, 서버가 "이 사람 목소리 저 사람이 들을 자격 있나" 판정한 뒤 되뿌리는 서버 권위 릴레이야. 결국 채팅 릴레이의 소리 버전인 거지.

↳ 그 "들을 자격 판정"은 코드 어디서 이뤄지나요?

답 보기
서버가 전 연결을 훑을 때 ShouldReplicateVoicePacketFrom이 "이 연결이 저 화자 목소리 받을 자격 있나"를 판정해 — 이 한 줄이 서버 권위의 심장이야. 여기서 음소거·팀·거리 규칙이 걸러져. 클라가 아니라 서버가 결정한다는 게 핵심이고, P2P 경로(peer)는 코드상 통째로 주석 처리돼 있어서 서버 릴레이만 살아있어.

Q2. 음성이 채팅이랑 흐르는 길이 같다면, 왜 굳이 Voice 전용 채널을 따로 뒀나요?

답 보기
음성은 성격이 아주 달라. 초당 수십 조각씩 쏟아지고, 옛날 소리는 차라리 안 오는 게 나아. 이걸 액터 복제("하나도 놓치면 안 돼")랑 같은 줄에 태우면 서로 방해돼. 그래서 소리만 나르는 전용 통로에 자기 큐 하나를 두고, 틱마다 몰아 내보내. 액터 채널이 복잡한 프로퍼티 복제를 하는 것과 달리, Voice 채널은 그냥 큐에 쌓고 틱마다 비우는 단순한 컨베이어 벨트야.

↳ 그럼 음성은 왜 unreliable로 보내나요? 빠짐없이 도착시키면 더 좋지 않나요?

답 보기
음성은 정반대야. 망이 막혔을 때 밀린 조각을 기어이 다 밀어내면 옛날 목소리가 뒤늦게 로봇처럼 들려. 1초 밀린 소리는 안 오느니만 못해. "빠짐없이"가 오히려 독이야. 그래서 웬만한 음성 조각은 도착 보장 안 하고, 망 막히면 그냥 버려 — 액터 복제와 정반대 선택이야. "옛것 붙들지 말고 지금 것만."

↳ 그럼 무조건 다 unreliable인가요?

답 보기
아니, 예외가 있어. 채널 첫 송신(핸드셰이크 격)은 무조건 reliable이고, 명시적으로 reliable 표시된 패킷도 reliable로 가. 그 외 일반 음성 조각만 unreliable이야. Tick이 "준비 안 됐으면 버리고 / 망 막히면 멈추고 / 웬만하면 unreliable로 최신 것만"이라는 3대 원칙으로 큐를 비워.

Q3. 서버가 목소리 하나 받을 때마다 전 접속자를 순회한다는데, 여기 함정 없나요?

답 보기
있어. 화자 100명이 각각 떠들면 각 패킷마다 전 연결 100명을 훑으니까 100 × 100, 거의 만 번에 가까운 O(N²)이야. 음성은 채팅보다 패킷 빈도가 훨씬 높아서(초당 수십 조각) 이 함정이 더 치명적이야. 그래서 실무에선 거리/팀 기반 ShouldReplicateVoicePacketFrom으로 후보를 확 줄이거나 아예 별도 음성 서버로 빼. 우리 서버 대형 채널 채팅이 겪는 그 O(N²)랑 똑같은 함정이야.

↳ 그 릴레이는 어떻게 한 바퀴 도나요? 받은 코드가 곧 릴레이 출발점이라던데요.

답 보기
받는 ReceivedBunch 안에서 "내가 서버냐?"를 ServerConnection == NULL로 판별해 — 클라는 서버로 가는 연결이 있고, 서버는 그게 없거든. 서버면 방금 받은 목소리를 다시 릴레이로 넘겨. 그래서 클라A 목소리 → 서버가 받음 → 자격 있는 클라B·C 큐에 적재 → 각자 Tick에서 송출 → B·C가 받음(이번엔 릴레이 안 하고 재생)으로 한 바퀴 돌아.

Q4. Voice 채널은 액터 채널처럼 그때그때 만들어지나요?

답 보기
아니, 연결마다 고정 슬롯에 미리 박혀 있는 정적 채널이야. Control 채널이 0번에 예약되듯 Voice도 자기 지정석(StaticChannelIndex)을 갖고 있어. 그래서 릴레이 코드가 매번 채널을 새로 만들 필요 없이 그냥 지정석에서 꺼내 쓰면 돼. 릴레이는 목소리 하나에 여러 연결의 큐를 건드려야 하는데, 매번 생성하면 비싸잖아 — 고정 슬롯이라 조회만 하면 되는 거야.

↳ 서버가 화자 30명의 목소리를 뿌릴 때 패킷을 30번 복사하나요?

답 보기
아니, 레퍼런스 카운트 공유 포인터(TSharedPtr)로 나눠 들어. 같은 패킷 하나를 여러 채널 큐가 공유 포인터로 나눠 참조하고, 마지막 큐가 다 쓰고 놓으면 그때 자동 해제돼. 30명한테 뿌린다고 30번 복사하면 메모리가 터지니까 — 릴레이할 때 메모리 안 터지게 하는 장치야.

🎯 원리 한 줄 요약

음성은 P2P가 아니라 "내 목소리 → 서버 → 자격 판정 → 되뿌리기"의 서버 권위 릴레이고, UVoiceChannel이 연결마다 고정 슬롯에 앉아 음성 큐를 들고 있다가 Tick에서 "준비 안 됐으면 버리고·망 막히면 멈추고·unreliable로 최신 것만" 원칙으로 내보낸다 — 채팅 릴레이의 소리 버전이다.
