NetConnection — 한 연결이 담당하는 모든 것

언리얼 네트워크 · 01 / 43

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "연결 하나(UNetConnection)가 대체 무슨 일까지 책임지는가"의 전체 지도가 머릿속에 생긴다. 세부 콜체인은 다음 챕터들이 파고들 거고, 여기선 뼈대만.

왜 이걸 먼저 배워? — 문제의식부터

잠깐. NetConnection이 뭔지 설명하기 전에, 왜 하필 이걸 1번으로 배우는지부터 짚자. 이유를 알고 보면 훨씬 잘 박히거든.

네가 게임 서버를 짜봤으면 이 고민을 반드시 해봤어. 클라 한 명이 접속하는 순간, 서버는 그 사람에 관한 걸 한 뭉치로 들고 있어야 해:

  • 그 사람 전용 소켓(연결 통로)
  • 받다 만 패킷 조각 / 보낼 패킷 큐
  • 암호화 키, 어디까지 받았는지(시퀀스 번호)
  • 지금 이 연결이 열어둔 채널들…

이걸 한 곳에 안 묶어두면 어떻게 될까? 100명이 접속한 순간 누구 데이터가 누구 건지 뒤죽박죽이 돼. 그래서 우리 조선 서버도 CChosunPlayer 같은 객체 하나에 그 사람 관련 상태를 싹 묶어놓잖아. 그게 없으면 서버가 안 돌아가니까.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 UNetConnection이야. "한 연결에 관한 모든 것"을 담는 그릇. 클라 한 명 = 서버에 이 객체 하나.

그래서 이게 1번 챕터인 이유 — 앞으로 배울 거의 전부(채널·Bunch·복제·RPC·핸드셰이크)가 결국 이 그릇 안에서, 이 그릇을 통해 일어나. 여길 안 잡고 넘어가면 "채널이 어디 붙는지", "복제가 누구한테 가는지"가 전부 허공에 뜬 얘기가 돼 — 집 주소를 모르고 골목 이름만 외우는 꼴이지.

자, 그럼 이 그릇이 구체적으로 무슨 일까지 책임지는지, 비유로 먼저 감을 잡자.

0. 먼저 비유부터 — 한 손님을 끝까지 책임지는 웨이터

식당에 손님 한 명이 앉았다고 쳐. 그 손님을 전담하는 웨이터 한 명이 붙어. 이 웨이터가 하는 일을 쭉 나열해보면:

  1. 자리 세팅 — 냅킨 깔고, 물 따르고, 메뉴판 준다. (초기화)
  2. 주문받기 — 손님이 말하는 걸 주방 용어로 옮겨 적는다. (수신)
  3. 음식 나르기 — 주방이 만든 걸 손님한테 가져다준다. (송신)
  4. 테이블 여러 개 관리 — 애피타이저 접시, 메인 접시, 디저트 접시를 따로따로 챙긴다. (채널 관리)
  5. 손님 배웅 — 계산 끝나면 자리 치우고 인사하고 보낸다. (종료)
  6. 틈틈이 살핌 — "물 더 드릴까요?" 하고 주기적으로 들여다본다. (Tick)

UNetConnection이 딱 이 웨이터야. 클라이언트 한 명당 서버에 이 객체 하나가 붙어서, 그 한 연결에 관한 위 여섯 가지를 전부 책임진다. 그리고 이 웨이터의 업무 매뉴얼을 코드로 적어놓은 게 NetConnection.cpp(6498줄)야.

이번 챕터는 그 매뉴얼의 목차를 그리는 거다. 각 업무를 실제로 어떤 함수가 맡는지, 그 함수들이 어떤 순서로 손을 잡는지. 세부 구현은 안 판다 — 지도만.

1. 먼저 알고 갈 것 — 이건 "추상 클래스"다

한 가지 반전부터. UNetConnection은 혼자서는 소켓에 바이트 한 개도 못 보낸다.

무슨 소리냐면, 이 클래스는 "연결이 지는 공통 책임"의 골격만 갖고 있고, 실제로 소켓에 send()/recv()를 때리는 부분은 PURE_VIRTUAL로 비워놨어. 그 구멍은 하위 클래스 — 예를 들어 UDP 소켓을 쓰는 UIpConnection — 가 채운다.

대표적으로 비워둔 것들:

  • LowLevelSend — 실제 소켓 write (송신의 맨 끝)
  • InitRemoteConnection / InitLocalConnection — 실제 소켓을 붙잡는 초기화

왜 이렇게 나눴을까? 맞춰봐 — 소켓 종류가 UDP만 있는 게 아니거든. IP 소켓, 스팀 소켓, 데모 녹화(파일에 쓰기)... 전송 수단이 뭐든 "연결 하나가 채널 관리하고, Ack 세고, 우아하게 닫고"는 똑같아야 해. 그래서 공통 로직은 UNetConnection에 다 몰아넣고, "실제로 어디로 내보내냐"만 하위 클래스에 위임한 거야.

게임 서버로 치면 — 네트워크 계층(IOCP WSASend)이랑 게임 로직(패킷 핸들러)을 분리해두는 거랑 똑같은 발상이야. UNetConnection = 게임 로직 쪽 공통부, UIpConnection::LowLevelSend = "진짜 소켓 때리는 곳".

소켓 실물 구현은 → ipnetdriver-socket

3. 콜체인 4개 — 순서대로 밟기

A. 초기화 체인 — 자리 세팅

하위 클래스가 소켓을 붙잡으면서 InitBase를 부르는 게 시작이야. InitBase 안에서 벌어지는 일 중 핵심 한 토막:

// Reset Handler Handler.Reset(); InitHandler(); FaultRecovery = MakeUnique<FNetConnectionFaultRecovery>(); FaultRecovery->InitDefaults((Driver != nullptr ? Driver->GetNetDriverDefinition().ToString() : TEXT("")), this);

NetConnection.cpp:523

🔤 기호 사전 — 초기화 첫 토막
• Handler.Reset() = 예전에 붙어 있던 핸들러를 깨끗이 비우는 동작. .은 "이 물건 안의 기능을 부른다"는 뜻이야.
• InitHandler() = 새 핸들러를 준비하는 함수 호출. 괄호 ()가 붙으면 "실행해"라고 읽으면 돼.
• MakeUnique<FNetConnectionFaultRecovery>() = FNetConnectionFaultRecovery라는 복구 담당 상자를 새로 만들고, 소유권을 하나만 갖게 하는 안전한 만들기 방식.
• FaultRecovery->InitDefaults(...) = FaultRecovery가 가리키는 물건한테 "기본값 세팅해"라고 시키는 것. ->는 포인터가 가리키는 대상의 기능을 부를 때 쓰는 화살표야.
• Driver != nullptr = Driver가 빈손이 아닌지 확인. nullptr은 "아무것도 없음", !=는 "같지 않다".
• ? ... : ... = 조건에 따라 둘 중 하나를 고르는 짧은 if. 앞 조건이 맞으면 ? 뒤, 아니면 : 뒤를 쓴다.
• TEXT("") = 언리얼에서 문자열을 안전하게 감싸는 표기. 여기선 빈 문자열을 뜻해.
• this = 지금 이 UNetConnection 자기 자신.
🔁 이제 다시 보자. 이 토막은 Handler.Reset()으로 예전 봉인을 지우고 → InitHandler()로 새 봉인 담당을 붙이고 → MakeUnique로 장애 복구기를 만들고 → InitDefaults(..., this)로 "이 연결 기준 기본값"을 넣는 초기 세팅이야. 즉 소켓을 쓰기 전에 웨이터 장비부터 챙기는 장면으로 읽으면 된다.

여기서 InitHandler()가 PacketHandler를 만드는 지점이야. PacketHandler는 소켓 raw 바이트랑 게임 로직 사이에 낀 처리 파이프라인 — 암호화·핸드셰이크·압축을 담당하는 놈이지. 이게 있어야 수신할 때 봉인을 뜯고, 송신할 때 봉인을 붙일 수 있어.

정리하면 초기화 순서는:

InitBase (:464) ├─ InitChannelData (:414) ─ Channels[] 배열을 MaxChannelSize만큼 확보 (OpenChannels는 채널 생성 때 하나씩 Add) ├─ InitHandler (:694) ─ PacketHandler 생성 + LowLevelSend를 델리게이트로 연결 (:722) └─ FaultRecovery 셋업 ─ 장애 복구기
Handler가 뭘 하는지 자세히는 → packethandler, 핸드셰이크는 → handshake

B. 수신 체인 — 주문받기

드라이버가 소켓에서 긁어온 날 바이트를 ReceivedRawPacket에 던진다. 거기서 봉인(Handler)을 뜯고, 알맹이가 남아있으면 ReceivedPacket으로 넘겨:

if (Handler.IsValid()) { Handler->IncomingHigh(Reader); } if (Reader.GetBitsLeft() > 0) { ReceivedPacket(Reader); // Check if the out of order packet cache needs flushing FlushPacketOrderCache(); }

NetConnection.cpp:2180

🔤 기호 사전 — 수신 체인 첫 토막
• if (Handler.IsValid()) = 핸들러가 준비돼 있으면 안쪽 일을 하라는 뜻. if는 "만약에".
• { ... } = 조건이 맞을 때 실행할 코드 묶음. 중괄호 안이 한 덩어리야.
• Handler->IncomingHigh(Reader) = 핸들러한테 Reader를 넘겨 "들어온 데이터 윗단 처리를 해"라고 시키는 호출.
• Reader.GetBitsLeft() > 0 = 아직 읽을 비트가 남았는지 확인. >는 "~보다 크다".
• ReceivedPacket(Reader) = 남은 알맹이를 다음 관문인 패킷 처리 함수로 넘긴다.
• // ... = 코드 설명용 주석. 실행되는 명령이 아니라 사람한테 남기는 메모야.
• FlushPacketOrderCache() = 순서가 어긋나 잠깐 보관해둔 패킷이 이제 처리 가능한지 털어보는 함수.
🔁 이제 다시 보자. 먼저 Handler.IsValid()면 IncomingHigh(Reader)로 봉인을 뜯고, 그 다음 Reader.GetBitsLeft() > 0이면 아직 내용물이 있으니 ReceivedPacket(Reader)로 넘겨. 마지막 FlushPacketOrderCache()는 "앞번호가 도착해서 묵혀둔 패킷을 이제 꺼낼 수 있나?" 확인하는 뒷정리야.

ReceivedPacket은 헤더/Ack를 읽고 번치를 파싱하기 시작하고, 개별 번치를 DispatchPacket이 담당 채널로 배달해. 이 세 함수의 릴레이가 수신의 전부야.

이 체인만 통째로 파는 챕터가 바로 다음이야 → receive-callchain

C. 송신 체인 — 음식 나르기

방향이 반대야. 채널이 "이 번치 보내줘" 하면:

채널.SendBunch → SendRawBunch (:4391) ─ 번치를 전송버퍼에 직렬화 (머지 시도 포함) → WriteBitsToSendBuffer(:4347) ─ 버퍼에 비트 기록, 넘치면 FlushNet 유발 → FlushNet (:2338) ─ 버퍼에 패킷헤더 붙여 완성 → LowLevelSend [순수가상] ─ 진짜 소켓 write는 UIpConnection 담당
🔤 기호 사전 — 송신 체인 표기
• → = 이 단계가 끝나면 다음 단계로 넘긴다는 화살표.
• (:4391) = 실제 NetConnection.cpp 안의 줄번호 힌트. "이 함수는 대략 여기 있다"는 지도 표시야.
• 채널.SendBunch = 채널이 "이 봉투를 보내줘" 하고 연결에게 요청하는 시작점.
• SendRawBunch = 번치를 전송용 날재료로 바꾸는 함수.
• WriteBitsToSendBuffer = 전송 버퍼에 비트 단위로 꾹꾹 적는 함수.
• FlushNet = 버퍼에 모아둔 걸 패킷 모양으로 완성해서 내보낼 준비를 하는 함수.
• LowLevelSend [순수가상] = 진짜 소켓으로 쓰는 마지막 칸인데, UNetConnection 안에는 몸통이 없고 자식 클래스가 채운다는 뜻.
🔁 이제 다시 보자. 송신은 SendRawBunch가 봉투를 받는 데서 시작해서 → WriteBitsToSendBuffer가 버퍼에 적고 → FlushNet이 패킷으로 포장하고 → LowLevelSend가 실제 소켓 쪽으로 넘기는 흐름이야. 앞 세 칸은 공통 연결 로직, 마지막 칸만 실제 전송 수단 담당으로 갈라진다.

여기서 딱 하나만 기억해. FlushNet까지는 UNetConnection이 하고, 그 다음 LowLevelSend부터가 하위 클래스야. 1장에서 말한 "추상 클래스 경계선"이 실제로 코드에서 갈라지는 지점이 여기다.

송신 상세는 → send-callchain

D. 채널 생성 체인 — 접시 새로 깔기

액터 하나가 복제되기 시작하면 그 액터 전용 채널이 열려. CreateChannelByName의 핵심부:

// Create channel. UChannel* Channel = Driver->GetOrCreateChannelByName(ChName); check(Channel); Channel->Init( this, ChIndex, CreateFlags ); Channels[ChIndex] = Channel; OpenChannels.Add(Channel); if (Driver->ChannelDefinitionMap[ChName].bTickOnCreate) { StartTickingChannel(Channel); } UE_LOG(LogNetTraffic, Log, TEXT("Created channel %i of type %s"), ChIndex, *ChName.ToString()); return Channel;

NetConnection.cpp:4579

🔤 기호 사전 — 채널 생성 토막
• UChannel* Channel = UChannel을 가리키는 손잡이 하나를 만든다. *는 "실물 자체가 아니라 실물을 가리키는 포인터".
• Driver->GetOrCreateChannelByName(ChName) = 드라이버한테 "이 이름의 채널을 가져오거나 없으면 만들어줘"라고 시키는 호출.
• check(Channel) = Channel이 비어 있으면 개발 중에 바로 터뜨리는 안전 검사.
• Channel->Init(this, ChIndex, CreateFlags) = 새 채널에 "너는 이 연결(this)에 붙고, 번호는 ChIndex고, 이런 옵션으로 시작해"라고 초기화한다.
• Channels[ChIndex] = Channel = 채널 배열의 ChIndex번째 칸에 방금 만든 채널을 꽂는다. []는 몇 번째 칸인지 고르는 표기야.
• OpenChannels.Add(Channel) = 열린 채널 목록에도 같은 채널을 추가한다.
• bTickOnCreate = b로 시작하니 참/거짓 값. "만들자마자 Tick 대상이냐?"라는 스위치야.
• UE_LOG(... TEXT(...), ...) = 언리얼 로그 한 줄을 남기는 호출. TEXT(...)는 로그 문자열을 감싸는 표기야.
• return Channel = 만든 채널 손잡이를 호출한 쪽에 돌려준다.
🔁 이제 다시 보자. GetOrCreateChannelByName으로 채널을 얻고 → Channel->Init(...)으로 연결 번호와 옵션을 박고 → Channels[ChIndex]와 OpenChannels 두 목록에 등록하고 → 필요하면 StartTickingChannel까지 걸어. 마지막 return Channel은 "새 접시 준비 끝, 여기 있어" 하고 넘기는 줄이야.

빈 인덱스 하나 얻어서(GetFreeChannelIndex) 채널을 만들고 Channels[] 배열이랑 OpenChannels에 등록해. 인덱스 0번은 항상 컨트롤 채널로 예약돼 있다는 것만 기억해둬 — 로그인, 종료 사유 같은 제어 메시지가 다 그리로 다녀. 종료 체인에서 다시 나온다.

채널 종류(컨트롤/액터/보이스)는 → channel-types

4. 종료 — 여기가 이 챕터의 하이라이트

웨이터 비유에서 "손님 배웅"인데, UE는 이걸 두 갈래로 나눠놨어. 초보가 제일 헷갈리는 부분이라 천천히 가자.

갈래 1 — Close : 즉시 종료

말 그대로 지금 당장 끊어. 상태를 USOCK_Closed로 박아버리고 끝:

NetConnection.cpp:1107

🔤 기호 사전 — Close 즉시 종료 토막
• SendCloseReason(MoveTemp(CloseReason)) = 종료 이유를 보내되, CloseReason 내용을 복사하지 말고 옮겨서 쓴다. MoveTemp는 "이제 이 값은 넘겨줄게"에 가까워.
• Channels[0] != nullptr = 0번 채널이 실제로 있는지 확인. 0번은 컨트롤 채널, nullptr은 빈칸.
• Channels[0]->Close(...) = 0번 채널한테 "너도 닫아"라고 시키는 호출.
• EChannelCloseReason::Destroyed = 채널을 닫는 이유 중 "파괴됨"이라는 정해진 보기. ::는 그 묶음 안의 항목이라는 뜻.
• SetConnectionState(EConnectionState::USOCK_Closed) = 연결 상태를 "닫힘"으로 바꾼다.
• const bool bReadyToSend = 나중에 못 바꾸는 참/거짓 값 하나. b로 시작하면 보통 bool이야.
• || / && = ||는 "또는", &&는 "그리고". 조건 여러 개를 붙일 때 쓴다.
• Handler == nullptr = 핸들러가 아예 없는지 확인. ==는 "같다".
• FlushNet() = 아직 버퍼에 남은 전송물을 마지막으로 밀어내는 함수.
🔁 이제 다시 보자. SendCloseReason으로 왜 닫는지 알리고 → Channels[0]->Close로 컨트롤 채널을 닫고 → SetConnectionState(...USOCK_Closed)로 연결을 닫힘 상태로 박아. 그 다음 bReadyToSend가 참이면 FlushNet()으로 마지막 남은 말까지 밀어내고 끝낸다.

보이지? 종료 사유를 보내고(SendCloseReason), 0번 컨트롤 채널을 닫고, 상태를 Closed로 못박고, 마지막으로 FlushNet 한 번 때려서 남은 걸 밀어내. 여기서 왜 하필 Channels[0]을 닫냐 — 3장 D에서 말한 그 컨트롤 채널이야. 제어용이니까 "끝났다"는 신호도 그리로 나간다.

갈래 2 — GracefulClose : 우아한 종료

문제 상황을 하나 상상해봐. 아직 못 보낸 신뢰(reliable) 데이터가 버퍼에 남았는데 그냥 Close로 끊어버리면? 그 데이터는 영영 유실돼. 중요한 아이템 지급 패킷이었으면 사고나는 거지.

그래서 GracefulClose는 바로 안 끊고 "보낼 거 다 보냈다는 확인(Ack)"을 기다리는 상태로 들어가:

if (Channels[0] && GetConnectionState() != USOCK_Closed) { if (UE::Net::Connection::Private::bGracefulCloseEnabled && GetConnectionState() != USOCK_Closing) { UE_LOG(LogNet, Log, TEXT("Initiating graceful close. CloseReason: %s. %s"), ToCStr(CloseReason.DynamicToString(UE::Net::ENetResultString::WithChain)), *Describe()); PendingGracefulCloseResult = MakePimpl<FNetResult, EPimplPtrMode::DeepCopy>(MoveTemp(CloseReason)); SetConnectionState(EConnectionState::USOCK_Closing); GracefulCloseTimeoutDeadline = Driver->GetElapsedTime() + Driver->GracefulCloseConnectionTimeout; if (UReplicationSystem* ReplicationSystem = Driver->GetReplicationSystem()) { ReplicationSystem->SetConnectionGracefullyClosing(ConnectionHandle.GetParentConnectionId()); } // Might as well try to close immediately in case there isn't any pending reliable data. TryClosePendingGracefulClose();

NetConnection.cpp:1145

🔤 기호 사전 — GracefulClose 우아한 종료 토막
• if (Channels[0] && GetConnectionState() != USOCK_Closed) = 0번 채널이 있고, 아직 완전히 닫힌 상태가 아니면 안쪽으로 들어간다.
• UE::Net::Connection::Private::bGracefulCloseEnabled = 언리얼 네트워크 내부 설정 중 "우아한 종료 기능이 켜졌나?"를 보는 긴 이름. ::가 여러 번 나오면 폴더 안 폴더처럼 소속을 따라 들어간다고 보면 돼.
• GetConnectionState() != USOCK_Closing = 이미 닫는 중이 아니어야 새로 시작한다는 조건.
• UE_LOG(LogNet, Log, TEXT(...), ...) = 네트워크 로그에 기록을 남긴다. 여기선 크래시가 아니라 일반 기록이야.
• ToCStr(...) / *Describe() = 로그에 넣을 글자 형태로 바꿔 꺼내는 표현. *는 여기서 문자열 손잡이 안의 실제 글자를 꺼내는 느낌으로 보면 돼.
• PendingGracefulCloseResult = ... = "나중에 진짜 닫을 때 쓸 종료 이유"를 보관해둔다.
• MakePimpl<FNetResult, EPimplPtrMode::DeepCopy>(...) = FNetResult를 숨겨진 상자에 깊게 복사해 넣어 보관하는 만들기 함수.
• Driver->GetElapsedTime() + Driver->GracefulCloseConnectionTimeout = 현재 시간에 제한 시간을 더해서 "여기까지만 기다리자"는 마감 시각을 만든다.
• if (UReplicationSystem* ReplicationSystem = Driver->GetReplicationSystem()) = 복제 시스템을 꺼내보고, 있으면 그걸 ReplicationSystem이라는 포인터로 쓰겠다는 짧은 패턴.
• TryClosePendingGracefulClose() = 지금 당장 닫아도 되는지 한 번 검사하는 함수. 보낼 게 다 확인됐으면 여기서 바로 Close까지 갈 수 있어.
🔁 이제 다시 보자. 이 토막은 Channels[0]이 있고 아직 안 닫혔는지 확인한 뒤 → 기능이 켜져 있으면 종료 이유를 PendingGracefulCloseResult에 저장하고 → 상태를 USOCK_Closing으로 바꾸고 → GracefulCloseTimeoutDeadline으로 마감 시각을 건다. 마지막 TryClosePendingGracefulClose()는 "이미 기다릴 게 없으면 지금 닫자"는 즉시 점검이야.

핵심 세 줄:

  • 상태를 USOCK_Closed가 아니라 USOCK_Closing(닫는 중)으로 둔다.
  • 마감 시한(GracefulCloseTimeoutDeadline)을 걸어둔다 — 무한정 기다리진 않겠다는 안전장치.
  • 맨 아래 TryClosePendingGracefulClose()를 부른다. 이 함수(:1171)가 모든 채널의 reliable 데이터가 Ack로 확인됐는지 점검해서, 다 됐으면 그제서야 진짜 Close를 부른다.

즉 GracefulClose는 Close를 당장 부르지 않고 조건이 맞을 때까지 미루는 래퍼야. 유실 방지가 목적이지.

Ack가 뭔지 / reliable이 뭔지 → reliable-retransmit

갈래 3 — CleanUp : 최종 뒷정리

Close가 "손님 배웅"이면 CleanUp은 "테이블 완전 철거"야. 객체 자체를 없애기 전 마지막 정리:

🔤 기호 사전 — CleanUp 최종 정리 토막
• const bool bWasSocketClosed = "이미 닫혀 있었나?"를 기록하는 참/거짓 값. const라 아래에서 바꾸지 않는다.
• GetConnectionState() == USOCK_Closed = 현재 상태가 닫힘과 같은지 확인. ==는 "같다".
• UE_CLOG((조건), LogNet, Log, TEXT(...), ...) = 조건이 참일 때만 로그를 찍는 언리얼 매크로. CLOG의 C를 "Condition"으로 생각하면 쉽다.
• || !bWasSocketClosed = "앞 조건이 맞거나, 아직 닫혀 있지 않았으면". !는 참/거짓을 뒤집는 표시야.
• Close(ENetCloseResult::Cleanup) = 정리 때문에 닫는다는 이유를 붙여 Close를 한 번 부른다.
• Driver != nullptr = 드라이버가 아직 살아 있는지 확인.
• Driver->ServerConnection = 드라이버 안의 서버 연결 칸을 가리킨다.
• check(Driver->ServerConnection == this) = 그 칸에 들어 있는 게 정말 나 자신인지 검사한다.
• NULL = 예전 C++식 빈 포인터 표기. 여기선 "이제 아무것도 없음"으로 비우는 값.
• Driver->RemoveClientConnection(this) = 드라이버의 클라이언트 연결 목록에서 나 자신을 빼달라고 시키는 호출.
🔁 이제 다시 보자. bWasSocketClosed로 이미 닫혔는지 적어두고 → UE_CLOG로 필요할 때만 로그를 남기고 → Close(...Cleanup)으로 확실히 닫아. 그 다음 Driver가 있으면 서버 연결 칸을 비우거나 RemoveClientConnection(this)로 클라이언트 목록에서 자기 자신을 제거한다.

보면 CleanUp은 먼저 Close를 한 번 더 부르고(안 닫혔으면 확실히 닫고), 그 다음 드라이버의 연결 목록에서 자기를 빼. 이후엔 모든 채널을 ConditionalCleanUp 하고 끝. "닫기 → 목록에서 제거 → 자원 반납" 3단이야.

연결이 태어나서 죽기까지 전체 생애는 → connection-lifecycle

끊어야 할 상황 │ ┌───────────────┼────────────────┐ 즉시 끊어도 됨 데이터 유실 객체 파괴 │ 방지하고 싶음 │ ▼ ▼ ▼ ┌──────────┐ ┌───────────────┐ ┌──────────┐ │ Close │ │ GracefulClose │ │ CleanUp │ │ :1074 │◄───│ :1141 │ │ :1364 │ └────┬─────┘ └───────┬───────┘ └────┬─────┘ │ │ │ SendCloseReason 상태=Closing 먼저 Close 호출 Ch[0] 닫기 Ack 다 올 때까지 → 드라이버 목록서 제거 상태=Closed 기다림 → 채널 전부 정리 FlushNet │ TryClosePending GracefulClose(:1171) "Ack 다 됐나?" ──yes──► Close 호출

세 개의 관계만 잡으면 이 챕터는 통과야:

  • Close = 실행 버튼. 실제로 끊는 건 항상 얘.
  • GracefulClose = 예약 버튼. 조건(Ack 완료) 맞으면 Close를 누른다.
  • CleanUp = 철거 버튼. Close 부르고 + 자원까지 반납.

6. 우리 서버랑 비교 — IOCP 워커 vs UNetConnection

조선협객전 서버(C++, IOCP)랑 매핑해보면 감이 확 온다.

개념우리 서버 (IOCP + 싱글스레드 액터)UE (UNetConnection)
연결 하나 표현클라 세션 객체 (소켓 핸들 + 유저 상태)UNetConnection 객체 1개/클라
날 바이트 수신IOCP 워커가 GQCS로 완료통지 받음 → 세션 버퍼에 적재ReceivedRawPacket에 드라이버가 던짐
패킷 분해워커 스레드가 헤더 읽고 wID로 핸들러 디스패치ReceivedPacket → DispatchPacket → 채널
게임 로직 실행싱글스레드 액터 큐에 밀어넣어 순차 처리게임 스레드 Tick에서 처리 (엔진도 싱글스레드 로직)
송신세션 send 버퍼 채워서 WSASendSendRawBunch → FlushNet → LowLevelSend
종료세션 close + 큐에서 정리Close / GracefulClose / CleanUp

결정적 공통점: 둘 다 "IO 스레드에서 바이트를 받아 파싱은 하지만, 게임 로직은 단일 스레드에서 순차"라는 구조야. 우리 서버는 그걸 액터 큐로 강제하고, UE는 게임 스레드 하나로 몰아넣지. 그래서 UNetConnection의 수신 체인(ReceivedRawPacket→DispatchPacket)을 읽을 때 "이거 우리 워커가 하는 거랑 똑같네" 하고 읽으면 절반은 먹고 들어가.

결정적 차이점: 우리는 TCP라 순서/신뢰성을 커널이 보장해줘서 Ack/Nak/GracefulClose 같은 게 필요 없어. UE는 UDP 위에 신뢰성을 직접 얹으니까 이 챕터의 종료 3형제, 특히 GracefulClose가 존재하는 거야. TCP 썼으면 이 고민 자체가 없다. → reliable-retransmit
