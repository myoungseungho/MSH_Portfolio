Channel 종류: Control / Actor / Voice

언리얼 네트워크 · 05 / 43

하나의 선(線)에 여러 물건을 실으면 안 되나?

게임 서버 짜봤으면 소켓 하나로 온갖 걸 다 밀어넣어 본 적 있을 거야. 로그인 패킷, 이동 패킷, 채팅 패킷 전부 같은 TCP 스트림에. 그러다 보면 이런 게 헷갈리지. "지금 온 이 바이트 덩어리가 이동이야 채팅이야? 헤더 보고 분기해야지."

UE는 그 "분기"를 아예 자료구조로 만들어놨어. 하나의 연결(UNetConnection) 안에 채널(Channel) 이라는 논리적 스트림을 여러 개 파놓고, 종류별로 나눠 실어. 로그인·연결관리는 이 선으로, 액터 복제는 저 선으로, 음성은 또 다른 선으로.

비유하자면 하나의 케이블 안에 색깔 다른 전선 여러 가닥이 든 거야. 겉은 케이블 하나(소켓 하나)인데 안에서는 역할별로 갈라져 있어.

이걸 실제로 구현한 게 UChannel과 그 자식들이야. 이번 챕터 주인공은 셋:

  • Control Channel — 연결 자체를 관리하는 선 (로그인, 엔디안 협상, 종료 통보)
  • Actor Channel — 액터 딱 하나를 담당하는 선
  • Voice Channel — 음성 패킷 나르는 선

셋 다 UChannel을 상속해. 구분은 딱 하나, 생성자에서 박는 이름표(ChName)로 갈려.

전제 개념(연결이 뭔지, 채널 배열을 누가 들고 있는지)이 흐릿하면 → netconnection-overview 먼저 보고 와. 여기선 다시 설명 안 하고 링크로 넘길게. 안 그러면 챕터마다 같은 얘기 무한 반복이거든.

지금부터 실제 코드가 나와. 겁먹지 마 — 생성자, 포인터, 조건식처럼 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 코드를 외우는 게 아니라 "이 이름표를 어디에 박는지"만 보면 돼.

1. 채널의 정체성은 "이름표" 한 줄이다

먼저 셋이 뭐가 다른지부터. 놀랄 만큼 단순해. 클래스는 다 다르지만, 정체성을 박는 코드는 생성자 딱 한 줄이야.

Control:

ControlChannel.h:83-87

UControlChannel(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get()) : UChannel(ObjectInitializer) { ChName = NAME_Control; }
🔤 기호 사전 — UControlChannel(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get())
• UControlChannel(...) = UControlChannel을 새로 만들 때 자동으로 불리는 시작 함수. 클래스 이름과 같아서 생성자라고 불러.
• const FObjectInitializer& = 언리얼 객체를 만들 때 필요한 준비물 봉투를 원본으로 받되 바꾸지 않겠다는 뜻. &는 원본, const는 안 바꿈.
• = FObjectInitializer::Get() = 준비물 봉투를 따로 안 주면 기본 봉투를 쓰라는 기본값. ::Get()은 "FObjectInitializer 안의 Get".
• : UChannel(ObjectInitializer) = 부모인 UChannel도 같은 준비물로 먼저 만들라는 줄. 자식 방을 만들기 전에 건물 기초를 세우는 느낌.
• ChName = NAME_Control = 이 채널 가슴팍에 "Control" 이름표를 붙이는 줄.
🔁 이제 다시 보자. 이 생성자는 "Control 채널을 만들 때 부모 UChannel부터 세팅하고, 마지막에 ChName을 NAME_Control로 박는다"로 읽으면 돼. 복잡해 보였지만 핵심은 이름표 한 줄이야.

Voice:

VoiceChannel.h:25-35

/** The set of outgoing voice packets for this channel */ FVoicePacketList VoicePackets; /** * Default constructor */ UVoiceChannel(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get()) : UChannel(ObjectInitializer) { ChName = NAME_Voice; }
🔤 기호 사전 — FVoicePacketList VoicePackets; / ChName = NAME_Voice;
• FVoicePacketList = 음성 패킷 여러 개를 담아두는 UE식 리스트 상자.
• VoicePackets; = 그 상자의 이름. 세미콜론 ;은 "이 줄 끝"이라는 마침표.
• UVoiceChannel(...) = Voice 채널이 새로 생길 때 불리는 생성자.
• : UChannel(ObjectInitializer) = Control과 똑같이 부모 UChannel을 먼저 세팅.
• ChName = NAME_Voice = 이 인스턴스는 Voice 채널이라고 이름표를 붙이는 줄.
🔁 이제 다시 보자. 위쪽 VoicePackets는 "보낼 음성 봉투를 쌓아둘 바구니"이고, 생성자 끝의 ChName = NAME_Voice는 "나는 Voice 전용 선"이라고 도장을 찍는 부분이야.

보이지? ChName = NAME_Control / ChName = NAME_Voice. Actor 채널도 똑같이 ChName = NAME_Actor를 박아 (DataChannel.cpp:1145). 이 이름표가 나중에 라우팅할 때 "이 데이터가 어느 종류 채널행이냐"를 판단하는 근거가 돼.

우리 서버로 치면 패킷 헤더의 wID(패킷 타입) 같은 거야. 다만 UE는 그걸 채널 인스턴스에 이름으로 박아두는 게 차이.

2. Actor Channel = 액터 딱 하나

Actor 채널의 핵심은 이름부터 정직해. 액터 하나당 채널 하나.

ActorChannel.h:84-88

// Variables. UPROPERTY() TObjectPtr<AActor> Actor; // Actor this corresponds to. FNetworkGUID ActorNetGUID; // Actor GUID (useful when we don't have the actor resolved yet). Currently only valid on clients.
🔤 기호 사전 — TObjectPtr<AActor> Actor;
• UPROPERTY() = 언리얼 엔진한테 "이 멤버는 내가 관리할 물건이야" 하고 등록하는 표시. GC/리플렉션 같은 엔진 관리 대상이 돼.
• TObjectPtr<AActor> = AActor 하나를 가리키는 UE식 포인터 상자. <> 안은 "무엇을 가리키는지"야.
• Actor = 이 채널이 담당하는 액터 한 명.
• FNetworkGUID = 네트워크에서 액터를 알아보려고 붙이는 고유 번호 상자.
• // = 오른쪽은 사람이 읽는 설명. 프로그램 실행에는 영향 없음.
🔁 이제 다시 보자. TObjectPtr<AActor> Actor는 "이 ActorChannel이 맡은 액터 한 명을 가리킨다"는 뜻이고, ActorNetGUID는 그 액터를 아직 못 찾았을 때도 네트워크 번호로 붙잡아두는 표식이야. 그래서 액터 하나당 채널 하나라는 말이 코드로 보이는 거지.

멤버 Actor가 단수야. 리스트가 아니라 포인터 하나. 이 채널은 저 액터 한 놈의 스폰 정보, 프로퍼티 변경, RPC를 실어나르는 전담 배달부인 거지. 월드에 복제 대상 액터가 300개면 채널도 그만큼 생겨(대략).

여기서 초보가 자주 오해하는 것 하나 짚고 갈게. 채널이 프로퍼티 복제를 "계산"하지는 않아. 채널은 그냥 통로고, 실제로 "어떤 프로퍼티가 바뀌었나, 뭘 보낼까"를 따지는 건 FObjectReplicator라는 별도 놈이야 (ActorChannel.h 49~50 주석). 채널은 배달 트럭, 리플리케이터는 물건 싸는 창고. 이 분업은 actorchannel-replicate에서 파고들 거니까 지금은 "채널 ≠ 복제 계산기"만 챙겨.

Actor 채널의 수신은 UActorChannel::ReceivedBunch(DataChannel.cpp:3080)로 들어와서 그 액터의 스폰 정보/프로퍼티/RPC 컨텐츠 청크를 파싱해. 다만 위에서 말했듯 실제 복제 값 계산은 리플리케이터가 하고, 채널은 뜯어서 넘겨주는 역할.

3. ChIndex 0 = Control은 특별 시민이다

이제 이 챕터에서 제일 중요한 부분. 채널들은 연결 안에서 Channels[] 배열에 담겨. 그 배열의 슬롯 번호가 ChIndex야.

그리고 0번 슬롯은 항상 Control 채널로 예약돼 있어. 왜? 연결이라는 게 성립하려면 제일 먼저 "너 누구냐, 로그인해라, 엔디안 맞춰라" 같은 협상이 오가야 하잖아. 그 협상을 담당하는 게 Control이고, 얘가 없으면 나머지는 시작도 못 해.

여기서 예측 한번 해보자. 클라가 접속하자마자, 아직 아무 채널도 안 만들어진 상태에서 서버로 첫 데이터가 도착했어. 라우팅 코드는 이걸 어떻게 처리할까?

맞춰봐. "채널이 없으니까 만들 때까지 다 막는다"고 생각했어? 반은 맞고 반은 틀려. Control(0번)만은 채널이 아직 없어도 통과시켜줘. 안 그러면 협상 자체를 시작할 수가 없거든. 닭이 먼저냐 달걀이 먼저냐 — Control은 "채널 없어도 받는" 예외로 그 고리를 끊어.

NetConnection.cpp:3795-3807

if ( Channels[Bunch.ChIndex] == NULL && ( Bunch.ChIndex != 0 || Bunch.ChName != NAME_Control ) ) { // Can't handle other channels until control channel exists. if ( Channels[0] == NULL ) { UE_LOG(LogNetTraffic, Log, TEXT("ReceivedPacket: Received non-control bunch before control channel was created. ChIndex: %i, ChName: %s"), Bunch.ChIndex, *Bunch.ChName.ToString()); Close(ENetCloseResult::BunchPrematureControlChannel); return; }
🔤 기호 사전 — if ( Channels[Bunch.ChIndex] == NULL && ( Bunch.ChIndex != 0 || Bunch.ChName != NAME_Control ) )
• if (...) = 괄호 안 조건이 맞을 때만 안쪽 블록을 탄다.
• Channels[Bunch.ChIndex] = 채널 배열에서 이번 bunch가 가리키는 번호 칸을 꺼내 보는 것. []는 "몇 번 칸".
• == NULL = 그 칸이 비어 있나 확인. NULL은 "아직 아무 채널 없음".
• && = 그리고. 양쪽 조건이 둘 다 맞아야 참.
• != = 같지 않다.
• || = 또는. 둘 중 하나라도 맞으면 참.
• *Bunch.ChName.ToString() = 채널 이름을 글자로 바꾼 뒤 로그에 넣으려고 실제 글자 값을 꺼내는 모양. 여기선 출력용.
• Close(...) / return = 연결을 닫고, 이 함수 처리를 바로 끝낸다.
🔁 이제 다시 보자. 첫 if는 "이번 번호의 채널이 비어 있고, 그게 0번 Control도 아니면" 들어간다. 안쪽 if (Channels[0] == NULL)은 "아직 Control도 없는데 다른 채널이 먼저 왔네?"를 잡아서 Close(...)로 끊는 방어문이야.

조건문을 천천히 뜯어보자. 한글로 풀면:

"채널이 아직 없고(Channels[Bunch.ChIndex] == NULL) 그리고 (0번 Control이 아니면)"

이 ( Bunch.ChIndex != 0 || Bunch.ChName != NAME_Control ) 괄호가 핵심이야. ChIndex가 0이고 이름이 Control이면 이 괄호가 false가 돼서 → 전체 if가 false → 블록 안 타고 그냥 통과. 즉 0번 Control은 "채널 없어도 처리 진행" 특별대우.

반대로 다른 채널(액터/보이스)이 Control보다 먼저 도착하면? 안쪽 if ( Channels[0] == NULL )에 걸려서 BunchPrematureControlChannel로 연결을 아예 끊어버려. "컨트롤 채널도 없는데 액터 데이터부터 보내? 너 뭔가 이상해, 끊는다."

정리하면 ChIndex 0은 이 시스템의 초석이야. 얘가 서고 나서야 나머지 채널들이 지어질 수 있어.

Control만 가진 또 하나의 특권: 남의 채널 닫기

DataChannel.cpp:303 (UChannel::Close 안의 check 주석이 규칙을 못박아)

check(OpenedLocally || ChIndex == 0); // We are only allowed to close channels that we opened locally (except channel 0, so the server can notify disconnected clients)
🔤 기호 사전 — check(OpenedLocally || ChIndex == 0);
• check(...) = 안쪽 조건이 거짓이면 개발 중 바로 터뜨리는 안전벨트.
• OpenedLocally = 이쪽에서 연 채널인가를 뜻하는 참/거짓 값.
• || = 또는. 둘 중 하나만 맞아도 통과.
• ChIndex == 0 = 0번 채널인지 확인. 여기선 Control 채널 특권을 뜻해.
• // ... = 코드 오른쪽 설명. 규칙을 사람 말로 못박아둔 주석.
🔁 이제 다시 보자. 이 줄은 "내가 연 채널이면 닫아도 되고, 아니어도 0번 Control이면 닫아도 된다"는 규칙이야. 그래서 Control만 예외적으로 남의 연결 종료 통보까지 맡을 수 있어.

원칙은 "내가 연 채널만 내가 닫는다"야. 근데 예외가 ChIndex == 0. 서버가 끊긴 클라에게 "너 연결 종료됐다"고 통보하려면 0번 채널로 close를 밀어야 하거든. 그래서 0번만 이 규칙을 면제받아. 또 특별대우.

4. Control 채널이 첫 패킷에 하는 일: 엔디안 검사

Control이 왜 그렇게 유난인지, 실제로 뭘 하는지 보면 납득이 가. 새 클라 연결의 첫 bunch를 받으면 Control은 제일 먼저 바이트 순서(엔디안)부터 검사해.

DataChannel.cpp:1815-1832

void UControlChannel::ReceivedBunch( FInBunch& Bunch ) { check(!Closing); UE_NET_TRACE_SCOPE(ControlChannel, Bunch, Connection->GetInTraceCollector(), ENetTraceVerbosity::Trace); // If this is a new client connection inspect the raw packet for endianess if (Connection && bNeedsEndianInspection && !CheckEndianess(Bunch)) { // Send close bunch and shutdown this connection UE_LOG(LogNet, Warning, TEXT("UControlChannel::ReceivedBunch: NetConnection::Close() [%s] [%s] [%s] from CheckEndianess(). FAILED. Closing connection."), Connection->Driver ? *Connection->Driver->NetDriverName.ToString() : TEXT("NULL"), Connection->PlayerController ? *Connection->PlayerController->GetName() : TEXT("NoPC"), Connection->OwningActor ? *Connection->OwningActor->GetName() : TEXT("No Owner")); Connection->Close(ENetCloseResult::ControlChannelEndianCheck); return; }
🔤 기호 사전 — void UControlChannel::ReceivedBunch( FInBunch& Bunch )
• void = 결과값을 돌려주지 않는 함수.
• UControlChannel:: = UControlChannel에 딸린 함수라는 소속 표시.
• FInBunch& Bunch = 받은 bunch 봉투를 복사하지 않고 원본으로 건네받는다. &는 원본.
• check(!Closing) = "닫히는 중이면 여기 오면 안 된다"는 안전 확인. !는 "아니다".
• UE_NET_TRACE_SCOPE(...) = 네트워크 추적 도구에 "지금 ControlChannel 처리 중"이라고 표시하는 매크로.
• Connection && bNeedsEndianInspection && !CheckEndianess(Bunch) = 연결이 있고, 엔디안 검사가 필요하고, 검사에 실패했을 때만 안으로 들어간다는 뜻. &&는 전부 참이어야 함.
• -> = 포인터가 가리키는 객체 안의 멤버를 꺼내는 화살표.
• ? : = 조건에 따라 둘 중 하나를 고르는 짧은 if. 앞이 참이면 왼쪽, 거짓이면 오른쪽.
• Connection->Close(...) / return = 연결을 닫고 함수에서 바로 빠져나간다.
🔁 이제 다시 보자. 첫 줄은 "Control 채널이 받은 bunch 원본을 처리하는 함수"야. 가운데 if는 "새 연결에서 엔디안 검사가 필요한데 실패했다"를 잡고, 실패하면 로그를 남긴 뒤 Connection->Close(...)로 끊고 return으로 끝내.

빅엔디안 기계와 리틀엔디안 기계가 붙으면 숫자가 뒤집혀서 다 깨지잖아. 그래서 협상 맨 앞에서 이걸 확인하고, 틀리면 ControlChannelEndianCheck로 바로 끊어. 이게 통과하면 그 뒤로 NMT_*(NetMessageType) 컨트롤 메시지들 — 로그인, 챌린지, 접속 승인 — 을 파싱하기 시작해. (bNeedsEndianInspection 플래그는 서버로서 열린 Control 채널의 Init에서 세팅돼 — DataChannel.cpp:1761.)

• virtual = 자식 클래스가 자기 방식으로 바꿔 끼울 수 있는 함수.
• bool = 참/거짓 하나를 돌려주는 타입.
• () const override = 인자는 없고, 자기 상태를 안 바꾸며, 부모의 함수를 덮어쓴다는 표시.
• return false = "아니오"를 돌려준다. 여기선 tick을 멈춰도 되냐는 질문에 "안 됨".
• { ... } = 이 함수가 실제로 하는 일의 몸통.
🔁 이제 다시 보자. CanStopTicking()은 "나 tick 멈춰도 돼?"라는 질문이고, Control은 늘 false를 돌려줘. 그래서 Control 채널은 할 일이 없어 보여도 계속 깨어 있는 쪽으로 동작해.

다른 채널은 할 일 없으면 tick을 멈출 수 있는데 Control은 false 고정 — 매 프레임 tick하면서 ack 안 온 패킷 재전송을 챙겨. 신뢰성 보장을 위해 버퍼가 넘치면 SendBunch가 QueuedMessages로 큐잉해서 순서까지 지켜(DataChannel.cpp:2155). 연결의 생명선이니까 한순간도 눈을 안 떼는 거지. (신뢰성/재전송 원리는 reliability-ack에서.)

5. Voice 채널 — 음성만 나르는 별동대

Voice 채널은 하는 일이 제일 단순해. 위 스니펫에서 봤듯 생성자에서 ChName = NAME_Voice를 박고, 멤버로 FVoicePacketList VoicePackets(내보낼 음성 패킷 리스트)를 들고 있어.

  • UVoiceChannel::AddVoicePacket() — VoiceChannel.cpp:144 — 보낼 음성 패킷을 VoicePackets에 적재.
  • UVoiceChannel::Tick() — VoiceChannel.cpp:63 — 매 tick VoIP 상태 전송.
  • UVoiceChannel::ReceivedBunch() — VoiceChannel.cpp:29 — 인바운드 음성 추출.

Control/Actor가 DataChannel.cpp에 같이 사는 것과 달리 Voice 구현은 VoiceChannel.cpp에 따로 살아. 음성은 게임 상태 복제와 성격이 달라서(손실 좀 나도 되고, 지연 민감) 별동대처럼 떼어놓은 거로 이해하면 돼. VoIP 자체 파고들려면 → voip.

6. 채널은 언제, 누가 만드나 — 콜체인

지금까지 "어떤 채널이 있나"를 봤으니, 이제 "이 채널들이 언제 생기나"를 콜체인으로 훑자. 두 갈래야: 접속 시 미리 여는 정적 채널과 데이터 보고 그때 여는 동적 채널.

두 갈래를 한 문장으로: Control은 접속 순간 0번에 정적으로 박히고, 액터/보이스 채널은 데이터가 실제로 흐를 때 필요한 만큼 동적으로 태어난다.

인덱스 배정의 최종 숫자값(Control=0 같은 구체 default)은 BaseEngine.ini의 +ChannelDefinitions=...에 들어있는데, 이 스터디 클론엔 Config 폴더가 안 딸려와서 소스로 그 숫자 자체는 못 짚어. 코드는 LoadChannelDefinitions(NetDriver.cpp:817)로 ini에서 읽어올 뿐이야. "Control이 0을 잡는다"는 동작은 위 라우팅 코드(ChIndex != 0 || ChName != NAME_Control)로 확실히 증명되지만, 그게 ini의 몇 번 슬롯인지는 여기선 개념으로만 알아둬.

7. 우리 서버랑 비교 — IOCP 워커 vs UChannel

조선협객전 서버 감각으로 매핑해보면 이래.

수신 처리 모델:

  • 우리: IOCP 워커 스레드가 소켓에서 패킷 뽑아 → wID(패킷 ID)로 switch 분기 → CM_* 핸들러 호출. 종류 구분이 패킷 헤더의 숫자 하나.
  • UE: bunch가 도착하면 Bunch.ChIndex로 Channels[] 배열에서 담당 채널을 찾아 → 그 채널의 ReceivedBunch 호출. 종류 구분이 채널 인스턴스(ChName).

즉 우리는 매번 switch로 갈래를 고르지만, UE는 갈래마다 전담 객체가 상주하면서 상태(시퀀스, 재전송 큐, 담당 액터)를 들고 있어. 스테이트풀한 거지.

단일 스레드 액터 대응: 우리 서버는 게임 로직이 싱글 스레드라 액터(캐릭터/몹) 상태를 락 없이 만져. UE도 게임 스레드에서 액터를 만지고, ActorChannel이 액터 하나를 1:1로 붙잡고 그 액터의 복제만 책임져. "액터 하나 = 채널 하나 = 그 액터 전용 상태 보관함" 구조라, 우리가 "캐릭터 하나 = 세션 객체 하나"로 상태를 격리하는 감각이랑 통해. 다른 액터의 복제가 이 채널 상태를 건드릴 일이 없으니, 락 없이도 서로 안 꼬여.

Control 채널의 위상: 우리로 치면 로그인/세션수립 전용 핸들러(접속 직후 인증 오가는 그 구간)를 "절대 안 죽고 항상 도는 전용 채널"로 승격시켜 0번에 고정해둔 셈. 접속 관리가 데이터 복제랑 물리적으로 분리돼 있어서, 게임 트래픽이 아무리 밀려도 연결 제어선은 독립적으로 살아있어.
