Channel 종류: Control / Actor / Voice

하나의 선(線)에 여러 물건을 실으면 안 되나?

게임 서버 짜봤으면 소켓 하나로 온갖 걸 다 밀어넣어 본 적 있을 거야. 로그인 패킷, 이동 패킷, 채팅 패킷 전부 같은 TCP 스트림에. 그러다 보면 이런 게 헷갈리지. "지금 온 이 바이트 덩어리가 이동이야 채팅이야? 헤더 보고 분기해야지."

UE는 그 "분기"를 아예 자료구조로 만들어놨어. 하나의 연결(UNetConnection) 안에 채널(Channel) 이라는 논리적 스트림을 여러 개 파놓고, 종류별로 나눠 실어. 로그인·연결관리는 이 선으로, 액터 복제는 저 선으로, 음성은 또 다른 선으로.

비유하자면 하나의 케이블 안에 색깔 다른 전선 여러 가닥이 든 거야. 겉은 케이블 하나(소켓 하나)인데 안에서는 역할별로 갈라져 있어.

이걸 실제로 구현한 게 UChannel과 그 자식들이야. 이번 챕터 주인공은 셋:

  • Control Channel — 연결 자체를 관리하는 선 (로그인, 엔디안 협상, 종료 통보)
  • Actor Channel — 액터 딱 하나를 담당하는 선
  • Voice Channel — 음성 패킷 나르는 선

셋 다 UChannel을 상속해. 구분은 딱 하나, 생성자에서 박는 이름표(ChName)로 갈려.

전제 개념(연결이 뭔지, 채널 배열을 누가 들고 있는지)이 흐릿하면 → netconnection-overview 먼저 보고 와. 여기선 다시 설명 안 하고 링크로 넘길게. 안 그러면 챕터마다 같은 얘기 무한 반복이거든.

1. 채널의 정체성은 "이름표" 한 줄이다

먼저 셋이 뭐가 다른지부터. 놀랄 만큼 단순해. 클래스는 다 다르지만, 정체성을 박는 코드는 생성자 딱 한 줄이야.

Control:

ControlChannel.h:83-87

	UControlChannel(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get())
		: UChannel(ObjectInitializer)
	{
		ChName = NAME_Control;
	}

Voice:

VoiceChannel.h:25-35

	/** The set of outgoing voice packets for this channel */
	FVoicePacketList VoicePackets;
	
	/**
	 * Default constructor
	 */
	UVoiceChannel(const FObjectInitializer& ObjectInitializer = FObjectInitializer::Get())
		: UChannel(ObjectInitializer)
	{
		ChName = NAME_Voice;
	}

보이지? ChName = NAME_Control / ChName = NAME_Voice. Actor 채널도 똑같이 ChName = NAME_Actor를 박아 (DataChannel.cpp:1145). 이 이름표가 나중에 라우팅할 때 "이 데이터가 어느 종류 채널행이냐"를 판단하는 근거가 돼.

우리 서버로 치면 패킷 헤더의 wID(패킷 타입) 같은 거야. 다만 UE는 그걸 채널 인스턴스에 이름으로 박아두는 게 차이.

2. Actor Channel = 액터 딱 하나

Actor 채널의 핵심은 이름부터 정직해. 액터 하나당 채널 하나.

ActorChannel.h:84-88

	// Variables.
	UPROPERTY()
	TObjectPtr<AActor> Actor;					// Actor this corresponds to.

	FNetworkGUID	ActorNetGUID;		// Actor GUID (useful when we don't have the actor resolved yet). Currently only valid on clients.

멤버 Actor가 단수야. 리스트가 아니라 포인터 하나. 이 채널은 저 액터 한 놈의 스폰 정보, 프로퍼티 변경, RPC를 실어나르는 전담 배달부인 거지. 월드에 복제 대상 액터가 300개면 채널도 그만큼 생겨(대략).

여기서 초보가 자주 오해하는 것 하나 짚고 갈게. 채널이 프로퍼티 복제를 "계산"하지는 않아. 채널은 그냥 통로고, 실제로 "어떤 프로퍼티가 바뀌었나, 뭘 보낼까"를 따지는 건 FObjectReplicator라는 별도 놈이야 (ActorChannel.h 49~50 주석). 채널은 배달 트럭, 리플리케이터는 물건 싸는 창고. 이 분업은 actorchannel-replicate에서 파고들 거니까 지금은 "채널 ≠ 복제 계산기"만 챙겨.

Actor 채널의 수신은 UActorChannel::ReceivedBunch(DataChannel.cpp:3080)로 들어와서 그 액터의 스폰 정보/프로퍼티/RPC 컨텐츠 청크를 파싱해. 다만 위에서 말했듯 실제 복제 값 계산은 리플리케이터가 하고, 채널은 뜯어서 넘겨주는 역할.

3. ChIndex 0 = Control은 특별 시민이다

이제 이 챕터에서 제일 중요한 부분. 채널들은 연결 안에서 Channels[] 배열에 담겨. 그 배열의 슬롯 번호가 ChIndex야.

그리고 0번 슬롯은 항상 Control 채널로 예약돼 있어. 왜? 연결이라는 게 성립하려면 제일 먼저 "너 누구냐, 로그인해라, 엔디안 맞춰라" 같은 협상이 오가야 하잖아. 그 협상을 담당하는 게 Control이고, 얘가 없으면 나머지는 시작도 못 해.

여기서 예측 한번 해보자. 클라가 접속하자마자, 아직 아무 채널도 안 만들어진 상태에서 서버로 첫 데이터가 도착했어. 라우팅 코드는 이걸 어떻게 처리할까?

맞춰봐. "채널이 없으니까 만들 때까지 다 막는다"고 생각했어? 반은 맞고 반은 틀려. Control(0번)만은 채널이 아직 없어도 통과시켜줘. 안 그러면 협상 자체를 시작할 수가 없거든. 닭이 먼저냐 달걀이 먼저냐 — Control은 "채널 없어도 받는" 예외로 그 고리를 끊어.

NetConnection.cpp:3795-3807

			if ( Channels[Bunch.ChIndex] == NULL && ( Bunch.ChIndex != 0 || Bunch.ChName != NAME_Control ) )
			{
				// Can't handle other channels until control channel exists.
				if ( Channels[0] == NULL )
				{
					UE_LOG(LogNetTraffic, Log,
							TEXT("ReceivedPacket: Received non-control bunch before control channel was created. ChIndex: %i, ChName: %s"),
							Bunch.ChIndex, *Bunch.ChName.ToString());

					Close(ENetCloseResult::BunchPrematureControlChannel);

					return;
				}

조건문을 천천히 뜯어보자. 한글로 풀면:

"채널이 아직 없고(Channels[Bunch.ChIndex] == NULL) 그리고 (0번 Control이 아니면)"

이 ( Bunch.ChIndex != 0 || Bunch.ChName != NAME_Control ) 괄호가 핵심이야. ChIndex가 0이고 이름이 Control이면 이 괄호가 false가 돼서 → 전체 if가 false → 블록 안 타고 그냥 통과. 즉 0번 Control은 "채널 없어도 처리 진행" 특별대우.

반대로 다른 채널(액터/보이스)이 Control보다 먼저 도착하면? 안쪽 if ( Channels[0] == NULL )에 걸려서 BunchPrematureControlChannel로 연결을 아예 끊어버려. "컨트롤 채널도 없는데 액터 데이터부터 보내? 너 뭔가 이상해, 끊는다."

정리하면 ChIndex 0은 이 시스템의 초석이야. 얘가 서고 나서야 나머지 채널들이 지어질 수 있어.

Control만 가진 또 하나의 특권: 남의 채널 닫기

DataChannel.cpp:303 (UChannel::Close 안의 check 주석이 규칙을 못박아)

	check(OpenedLocally || ChIndex == 0);		// We are only allowed to close channels that we opened locally (except channel 0, so the server can notify disconnected clients)

원칙은 "내가 연 채널만 내가 닫는다"야. 근데 예외가 ChIndex == 0. 서버가 끊긴 클라에게 "너 연결 종료됐다"고 통보하려면 0번 채널로 close를 밀어야 하거든. 그래서 0번만 이 규칙을 면제받아. 또 특별대우.

4. Control 채널이 첫 패킷에 하는 일: 엔디안 검사

Control이 왜 그렇게 유난인지, 실제로 뭘 하는지 보면 납득이 가. 새 클라 연결의 첫 bunch를 받으면 Control은 제일 먼저 바이트 순서(엔디안)부터 검사해.

DataChannel.cpp:1815-1832

void UControlChannel::ReceivedBunch( FInBunch& Bunch )
{
	check(!Closing);

	UE_NET_TRACE_SCOPE(ControlChannel, Bunch, Connection->GetInTraceCollector(), ENetTraceVerbosity::Trace);

	// If this is a new client connection inspect the raw packet for endianess
	if (Connection && bNeedsEndianInspection && !CheckEndianess(Bunch))
	{
		// Send close bunch and shutdown this connection
		UE_LOG(LogNet, Warning, TEXT("UControlChannel::ReceivedBunch: NetConnection::Close() [%s] [%s] [%s] from CheckEndianess(). FAILED. Closing connection."),
			Connection->Driver ? *Connection->Driver->NetDriverName.ToString() : TEXT("NULL"),
			Connection->PlayerController ? *Connection->PlayerController->GetName() : TEXT("NoPC"),
			Connection->OwningActor ? *Connection->OwningActor->GetName() : TEXT("No Owner"));

		Connection->Close(ENetCloseResult::ControlChannelEndianCheck);
		return;
	}

빅엔디안 기계와 리틀엔디안 기계가 붙으면 숫자가 뒤집혀서 다 깨지잖아. 그래서 협상 맨 앞에서 이걸 확인하고, 틀리면 ControlChannelEndianCheck로 바로 끊어. 이게 통과하면 그 뒤로 NMT_*(NetMessageType) 컨트롤 메시지들 — 로그인, 챌린지, 접속 승인 — 을 파싱하기 시작해. (bNeedsEndianInspection 플래그는 서버로서 열린 Control 채널의 Init에서 세팅돼 — DataChannel.cpp:1761.)

그리고 Control은 절대 잠들지 않아:

ControlChannel.h:96-97

	/** Always tick the control channel for now. */
	virtual bool CanStopTicking() const override { return false; }

다른 채널은 할 일 없으면 tick을 멈출 수 있는데 Control은 false 고정 — 매 프레임 tick하면서 ack 안 온 패킷 재전송을 챙겨. 신뢰성 보장을 위해 버퍼가 넘치면 SendBunch가 QueuedMessages로 큐잉해서 순서까지 지켜(DataChannel.cpp:2155). 연결의 생명선이니까 한순간도 눈을 안 떼는 거지. (신뢰성/재전송 원리는 reliability-ack에서.)

5. Voice 채널 — 음성만 나르는 별동대

Voice 채널은 하는 일이 제일 단순해. 위 스니펫에서 봤듯 생성자에서 ChName = NAME_Voice를 박고, 멤버로 FVoicePacketList VoicePackets(내보낼 음성 패킷 리스트)를 들고 있어.

  • UVoiceChannel::AddVoicePacket() — VoiceChannel.cpp:144 — 보낼 음성 패킷을 VoicePackets에 적재.
  • UVoiceChannel::Tick() — VoiceChannel.cpp:63 — 매 tick VoIP 상태 전송.
  • UVoiceChannel::ReceivedBunch() — VoiceChannel.cpp:29 — 인바운드 음성 추출.

Control/Actor가 DataChannel.cpp에 같이 사는 것과 달리 Voice 구현은 VoiceChannel.cpp에 따로 살아. 음성은 게임 상태 복제와 성격이 달라서(손실 좀 나도 되고, 지연 민감) 별동대처럼 떼어놓은 거로 이해하면 돼. VoIP 자체 파고들려면 → voip.

6. 채널은 언제, 누가 만드나 — 콜체인

지금까지 "어떤 채널이 있나"를 봤으니, 이제 "이 채널들이 언제 생기나"를 콜체인으로 훑자. 두 갈래야: 접속 시 미리 여는 정적 채널과 데이터 보고 그때 여는 동적 채널.

인덱스 배정의 최종 숫자값(Control=0 같은 구체 default)은 BaseEngine.ini의 +ChannelDefinitions=...에 들어있는데, 이 스터디 클론엔 Config 폴더가 안 딸려와서 소스로 그 숫자 자체는 못 짚어. 코드는 LoadChannelDefinitions(NetDriver.cpp:817)로 ini에서 읽어올 뿐이야. 7. 우리 서버랑 비교 — IOCP 워커 vs UChannel

조선협객전 서버 감각으로 매핑해보면 이래.

수신 처리 모델:

  • 우리: IOCP 워커 스레드가 소켓에서 패킷 뽑아 → wID(패킷 ID)로 switch 분기 → CM_* 핸들러 호출. 종류 구분이 패킷 헤더의 숫자 하나.
  • UE: bunch가 도착하면 Bunch.ChIndex로 Channels[] 배열에서 담당 채널을 찾아 → 그 채널의 ReceivedBunch 호출. 종류 구분이 채널 인스턴스(ChName).

즉 우리는 매번 switch로 갈래를 고르지만, UE는 갈래마다 전담 객체가 상주하면서 상태(시퀀스, 재전송 큐, 담당 액터)를 들고 있어. 스테이트풀한 거지.

단일 스레드 액터 대응: 우리 서버는 게임 로직이 싱글 스레드라 액터(캐릭터/몹) 상태를 락 없이 만져. UE도 게임 스레드에서 액터를 만지고, ActorChannel이 액터 하나를 1:1로 붙잡고 그 액터의 복제만 책임져. "액터 하나 = 채널 하나 = 그 액터 전용 상태 보관함" 구조라, 우리가 "캐릭터 하나 = 세션 객체 하나"로 상태를 격리하는 감각이랑 통해. 다른 액터의 복제가 이 채널 상태를 건드릴 일이 없으니, 락 없이도 서로 안 꼬여.

Control 채널의 위상: 우리로 치면 로그인/세션수립 전용 핸들러(접속 직후 인증 오가는 그 구간)를 "절대 안 죽고 항상 도는 전용 채널"로 승격시켜 0번에 고정해둔 셈. 접속 관리가 데이터 복제랑 물리적으로 분리돼 있어서, 게임 트래픽이 아무리 밀려도 연결 제어선은 독립적으로 살아있어.

마무리 — 어디로 이어지나

이 챕터는 "채널이 몇 종류고, 왜 0번이 특별하고, 액터 채널이 뭘 담당하나"라는 뼈대까지만. 각 채널이 실제로 데이터를 어떻게 자르고 붙이는지(bunch 단위), 신뢰성을 어떻게 보장하는지는 다음 선반들에 있어.

채널은 "생성자에서 박은 ChName" 하나로 종류가 갈리고, ChIndex 0=Control은 "채널 없어도 받고, 남의 채널도 닫는" 특별 시민이라 얘가 서야 나머지 채널이 지어진다 — Actor 채널은 그중 액터 딱 하나를 전담하는 배달부다.
