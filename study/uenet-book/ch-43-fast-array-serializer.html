FastArraySerializer — 배열에서 바뀐 원소만 보내기

언리얼 네트워크 · 43 / 47

왜 이걸 배워? — 문제의식부터

네가 조선 서버에서 인벤토리를 짜봤으면 이 고민을 무조건 했을 거야. CChosunPlayer가 아이템 100칸을 들고 있는데, 유저가 물약 하나를 먹어서 3번 칸 개수가 5 → 4 로 줄었어. 그럼 클라에 뭘 보내지?

제일 게으른 답은 SP_INVENTORY_ALL 같은 패킷 하나 만들어서 100칸을 통째로 다시 보내는 거야. 짜기는 제일 쉬워. 근데 물약 한 번 먹을 때마다 100칸이 날아가. 파티 8명이 사냥하면서 계속 아이템을 먹고 쓰면? 대역폭이 그냥 녹아.

그래서 우리는 손으로 나눠 만들었지. SP_ITEM_ADD(아이템 하나 추가), SP_ITEM_REMOVE(하나 삭제), SP_ITEM_UPDATE(하나 수량 변경). 바뀐 칸 하나만 보내니까 대역폭은 살았어. 대신 패킷 세 개를 사람이 직접 설계·직렬화·핸들러 등록해야 하고, 클라 쪽엔 "3번 슬롯이 어디 있더라?" 하고 찾아 고치는 코드를 또 손으로 짜야 해. 버프 목록도 똑같이 SP_BUFF_ADD/REMOVE/UPDATE. 킬로그도, 팀 목록도... 배열 하나 늘어날 때마다 패킷 3종 세트가 늘어나.

언리얼도 정확히 같은 벽에 부딪혔어. TArray를 UPROPERTY(Replicated)로 걸면 통짜 복제가 돼 — 원소 하나만 바뀌어도 배열 전체가 다시 날아가. 앞에서 배운 push-model도 이건 못 고쳐. Push Model은 최상위 프로퍼티 단위로만 손을 들거든. "배열 3번 원소만 바꿨어요"를 표현할 방법 자체가 없어.

그 빈틈을 메우려고 나온 게 FastArraySerializer야. 원소마다 ID(이름표) 와 Key(버전 번호) 를 붙여서, 서버가 "추가된 놈 / 바뀐 놈 / 삭제된 놈"만 골라 보내. 우리가 손으로 만들던 SP_ITEM_ADD/REMOVE/UPDATE 3종 세트를, 엔진이 자동으로 만들어주는 것. 이 챕터는 그 자동화가 어떤 원리로 도는지를 판다.

0. 문 앞에서: TArray 통짜 복제가 진짜로 얼마나 아까운가

먼저 아무 장치 없이 배열을 복제하면 무슨 일이 벌어지는지 보자. 인벤토리 구조체가 이렇다고 쳐.

USTRUCT() struct FItemEntry { UPROPERTY() int32 ItemId; // 4바이트 UPROPERTY() int32 Count; // 4바이트 UPROPERTY() float Durability; // 4바이트 }; UPROPERTY(Replicated) TArray<FItemEntry> Items; // 100칸

여기서 Items[3].Count를 5에서 4로 바꿨어. 딱 4바이트 바뀐 거야. 그럼 클라한테 몇 바이트가 날아갈까? 맞춰봐.

원소 12바이트 × 100개 = 1200바이트짜리 배열.
그중 4바이트 하나만 바꿨어. 네트워크로는 몇 바이트가 나갈까?

...정답: 1200바이트 전부. 4바이트 바꾸겠다고 1200바이트를 보내. 300배 낭비야.

왜 이렇게 되냐면, 언리얼의 프로퍼티 비교는 배열 프로퍼티 하나를 통짜 단위로 본다. 배열 안을 들여다보고 "3번 원소만 다르네" 하고 그 원소만 changelist에 넣는 게 아니야(→ changelist). "배열이 다르다"까지만 판정하고, 다르면 배열 전체를 직렬화해서 실어.

더 고약한 건 순서야. 인벤 정렬 버튼을 눌러서 아이템 순서만 뒤바꿨다고 해보자. 데이터 총량은 하나도 안 변했어. 근데 인덱스 기준으로 비교하면 Items[0]도 다르고 Items[1]도 다르고... 전 원소가 dirty가 돼. 실제로 바뀐 정보는 "순서"뿐인데 배열 전체를 다시 보낸다.

정리하면 통짜 TArray 복제의 문제는 둘이야.

  • 원소 하나 바뀌어도 전부 재전송 — 변경량이 아니라 배열 크기에 비례해 대역폭을 쓴다.
  • 인덱스가 곧 정체성 — 순서가 밀리면 안 바뀐 원소까지 "바뀐 것"으로 잡힌다.
🌱 이 개념은 왜 생겼나 — FastArraySerializer
• 원래 구조: TArray를 UPROPERTY(Replicated)로 걸면 엔진이 배열을 통짜 하나의 프로퍼티로 보고 복제해. 다르면 전부 다시 보내.
• 그런데 문제: 아이템 100개 중 1개의 수량 4바이트만 바뀌었는데 1200바이트가 통째로 날아가. 게다가 인덱스로 비교하니까 순서만 바뀌어도 전 원소가 dirty가 돼. 인벤·버프·킬로그처럼 자주 찔끔 바뀌는 배열엔 최악이야.
• 그래서 필요한 것: 원소를 인덱스가 아니라 ID로 식별하고, 원소마다 버전 번호(Key) 를 달아서 "추가된 놈 / 키가 오른 놈 / 사라진 놈"만 골라 보내는 장치. → 그게 FastArraySerializer야. 우리가 손으로 나눠 만들던 SP_ITEM_ADD / REMOVE / UPDATE를 엔진이 자동 생성해주는 셈이지.

지금부터 진짜 코드가 나와. 겁먹지 마 — 이 챕터는 딱 두 개만 잡으면 돼. ID(누구냐) 와 Key(몇 번째 버전이냐). 나머지는 전부 이 둘의 응용이야. 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게.

1. 큰 그림: 이름표(ID)와 버전 도장(Key)

FastArraySerializer의 아이디어는 택배 송장이랑 똑같아.

배열 원소 하나하나에 바코드(ID) 를 붙여. 인덱스는 정렬하면 바뀌지만 바코드는 안 바뀌어. 그리고 그 옆에 도장 칸(Key) 을 하나 더 둬서, 내용이 바뀔 때마다 도장을 하나씩 더 찍어(숫자를 1 올려).

그럼 서버는 각 클라마다 "지난번에 이 클라한테 보낼 때, 바코드별 도장 개수가 몇이었지?"를 기억해두면 돼. 이번 프레임에 다시 훑어서:

  • 지난 기록에 없던 바코드가 있다 → 추가(Add)
  • 있던 바코드인데 도장 개수가 늘었다 → 변경(Change)
  • 지난 기록엔 있는데 지금은 없는 바코드 → 삭제(Remove)

이 세 갈래만 뽑아서 보내면 끝이야. 안 바뀐 원소는 바코드도 도장도 그대로니까 아무 갈래에도 안 걸려 → 아예 안 실린다.

그리고 배열 전체에도 도장 칸이 하나 더 있어. ArrayReplicationKey. 원소 하나라도 손대면 이 배열 도장도 같이 올라가. 왜 필요하냐면 — 서버가 매 프레임 100개 원소를 다 훑기 전에, "배열 도장이 지난번이랑 같네? 그럼 볼 것도 없이 스킵" 하고 빠져나가려고. 문 앞에서 한 번 걸러주는 거지.

세 개의 숫자만 기억해.
• ReplicationID — 원소의 바코드. 한 번 받으면 안 바뀜. 인덱스가 아니라 이게 정체성.
• ReplicationKey — 원소의 도장 개수. 내용 바뀔 때마다 +1.
• ArrayReplicationKey — 배열 전체의 도장 개수. 뭐라도 바뀌면 +1. 빠른 조기 탈출용.

2. 뼈대 코드: 원소 struct와 배열 struct

쓰려면 규칙이 두 개 있어. 원소 구조체는 FFastArraySerializerItem을 상속하고, 배열 구조체는 FFastArraySerializer를 상속한다. 엔진 헤더 주석에 그대로 예제가 박혀 있어.

"Everything related to Fast TArray Replication has been moved to "Net/Serialization/FastArraySerializer.h""
그래서 이 챕터의 코드는 전부 Runtime/Net/Core/Classes/Net/Serialization/FastArraySerializer.h에서 가져온다.

엔진이 제시하는 6단계 레시피가 헤더 주석에 통째로 박혀 있어. FastArraySerializer.h:50-108 (원소 콜백 3종 선언은 5장에서 볼 거라 여기선 접었어):

🔤 기호 사전 — 위 예제 한 줄씩
• #if 0 ... #endif = "이 안은 컴파일하지 마라"는 표시. 즉 이 예제는 실제로 빌드되는 코드가 아니라 헤더에 박아둔 복붙용 설명서야. Epic이 "이대로 베껴 쓰라"고 넣어둔 거지. Step 1~5라는 주석 번호가 그 증거고.
• USTRUCT() = "이건 언리얼이 알아봐야 할 구조체야"라고 엔진에 신고하는 표시. 이게 있어야 리플렉션·복제 대상이 돼.
• : public FFastArraySerializerItem = :는 "~을 물려받는다"는 상속 기호. 부모가 가진 ReplicationID·ReplicationKey 칸을 공짜로 얻는다는 뜻이야. (Step 1)
• GENERATED_USTRUCT_BODY() = 언리얼이 자동 생성한 코드를 여기 끼워 넣으라는 자리 표시. 신경 안 써도 돼.
• UPROPERTY() = 이 변수를 엔진이 추적하게 만드는 표시. 없으면 복제 대상 목록에 안 들어가.
• TArray<FExampleItemEntry> Items = FExampleItemEntry가 줄줄이 담긴 배열. <> 안이 "무엇이 담기느냐"야. 주석(Step 3)이 이름까지 못 박아 — "Items라는 이름의 TArray를 반드시 가져야 한다".
• NetDeltaSerialize(FNetDeltaSerializeInfo & DeltaParms) = "이 구조체는 델타(차이)로 직렬화합니다"라고 엔진에 내미는 함수. 통짜 복제 대신 이 함수가 불려. (Step 4)
• FastArrayDeltaSerialize<아이템형, 배열형>( Items, DeltaParms, *this ) = 실제 델타 계산을 대신 해주는 엔진 템플릿 함수. 우리는 "내 아이템 타입은 이거, 내 배열은 이거" 하고 넘기기만 해.
• TStructOpsTypeTraits ... WithNetDeltaSerializer = true = 엔진에게 "이 구조체는 델타 직렬화 기능을 갖고 있으니 그쪽 길로 보내줘"라고 등록하는 스위치. 이걸 빼면 위 함수를 짜놔도 안 불린다. (Step 5)
🔁 이제 다시 보자. 원소는 FFastArraySerializerItem을 상속해서 바코드·도장 칸을 얻고(Step 1), 배열은 FFastArraySerializer를 상속해서 델타 계산 능력을 얻어(Step 2). 배열 구조체는 Items라는 정해진 이름의 TArray를 두고(Step 3), NetDeltaSerialize 안에서 엔진 템플릿에 위임하고(Step 4), 마지막에 WithNetDeltaSerializer = true로 "나 델타로 보내주세요"를 신고한다(Step 5). 이 다섯 단계가 준비 끝.

그리고 Step 6부터는 네가 지켜야 할 규율이야. 주석이 MUST를 두 번 쓴다. FastArraySerializer.h:110-121:

🔁 이제 다시 보자. 여기에 이 챕터의 나머지가 전부 예고돼 있어. 바꾸면 MarkItemDirty, 지우면 MarkArrayDirty(→ 3장), 클라 알림은 콜백(→ 5장). 대문자 MUST가 두 번 나오는 건, 안 부르면 조용히 망가지기 때문이야. (맨 아래 PostReplicatedReceive는 "이번 수신 전체가 끝났다"를 한 번 알려주는 네 번째 콜백이야. 5장에서 볼 배치 콜백과 같은 결이니 거기서 같이 이해하면 돼.)

그럼 원소가 상속받는 그 "바코드·도장 칸"이 실제로 뭔지 보자. FastArraySerializer.h:286-322:

/** Base struct for items using Fast TArray Replication */ USTRUCT() struct FFastArraySerializerItem { GENERATED_USTRUCT_BODY() FFastArraySerializerItem() : ReplicationID(INDEX_NONE), ReplicationKey(INDEX_NONE), MostRecentArrayReplicationKey(INDEX_NONE) { } FFastArraySerializerItem(const FFastArraySerializerItem &InItem) : ReplicationID(INDEX_NONE), ReplicationKey(INDEX_NONE), MostRecentArrayReplicationKey(INDEX_NONE) { } FFastArraySerializerItem& operator=(const FFastArraySerializerItem& In) { if (&In != this) { ReplicationID = INDEX_NONE; ReplicationKey = INDEX_NONE; MostRecentArrayReplicationKey = INDEX_NONE; } return *this; } UPROPERTY(NotReplicated) int32 ReplicationID; UPROPERTY(NotReplicated) int32 ReplicationKey; UPROPERTY(NotReplicated) int32 MostRecentArrayReplicationKey;
🔤 기호 사전 — FFastArraySerializerItem
• FFastArraySerializerItem() : ReplicationID(INDEX_NONE), ... = 생성자야. : 뒤는 "태어날 때 이 값들로 시작한다"는 초기화 목록.
• INDEX_NONE = 언리얼에서 "없음 / 아직 안 정해짐"을 뜻하는 값(실제로는 -1). 즉 새로 만든 원소는 바코드가 없는 상태로 태어나.
• FFastArraySerializerItem(const FFastArraySerializerItem &InItem) = 복사 생성자야. 그런데 몸통을 봐 — 원본에서 값을 베껴오는 게 아니라 세 숫자를 전부 INDEX_NONE으로 리셋해버려. 바코드는 복사되지 않는다는 뜻이야. 원소를 복사해서 배열에 넣으면 그건 바코드 없는 새 놈이고, 그래서 MarkItemDirty가 새 번호를 발급해줘야 해. 남의 바코드를 물려받으면 서버가 두 원소를 같은 놈으로 착각하니까, 아예 원천봉쇄한 거지.
• operator=(const FFastArraySerializerItem& In) = 대입 연산자. 여기도 똑같이 리셋해. ItemA = ItemB;를 해도 바코드는 안 따라온다.
• UPROPERTY(NotReplicated) = "엔진은 추적하되 네트워크로는 보내지 마"라는 표시. 바코드·도장은 서버 내부 살림살이지, 그대로 전송되는 데이터가 아니야.
• int32 ReplicationID = 이 원소의 바코드. 인덱스가 아니라 이게 정체성이야.
• int32 ReplicationKey = 이 원소의 도장 개수. 내용이 바뀔 때마다 1씩 오른다.
• int32 MostRecentArrayReplicationKey = "이 원소가 마지막으로 갱신됐을 때의 배열 도장 번호". 수신측이 "얘 이번 업데이트에 손 탔나?"를 판단할 때 쓰는 메모야.
🔁 이제 다시 보자. 원소는 태어날 때 INDEX_NONE(바코드 없음)으로 시작하고, 복사해도·대입해도 바코드는 안 따라온다 — 복사 생성자와 operator=가 대놓고 리셋하거든. 바코드는 오직 MarkItemDirty만 발급한다는 규칙을 코드로 못 박은 거야. 그리고 세 숫자 전부 NotReplicated — 전송되는 값이 아니라 델타를 계산하기 위한 장부라는 뜻이야. 클라가 받는 건 "몇 번 바코드가 이렇게 바뀌었다"는 결과지, 이 필드들 자체가 아니다.
⚠️ Items 이름 규칙을 어기면? Step 3 주석이 MUST have a TArray named Items라고 못 박은 이유가 있어. 엔진의 델타 경로는 그 배열을 이름으로 찾아간다. 이름이 다르거나 엉뚱한 프로퍼티가 잡히면 컴파일은 되는데 런타임에 복제가 이상해져. "왜 인벤이 안 오지?" 하고 하루 날리는 전형적 함정이야.

3. 손드는 법: MarkItemDirty / MarkArrayDirty

이제 핵심. 바코드는 누가 발급하고, 도장은 누가 찍나? 엔진이 알아서 해줄 것 같지만 아니야. 게임 코드가 직접 손을 들어야 해. 여기서 push-model이랑 완전히 같은 철학이 나온다 — 비교하지 말고, 바꾼 놈이 신고해라.

🔤 기호 사전 — MarkItemDirty / MarkArrayDirty / IncrementArrayReplicationKey
• FFastArraySerializerItem & Item = &는 복사본이 아니라 진짜 그 원소를 받는다는 표시. 복사본에 도장 찍으면 아무 의미 없으니 반드시 원본이어야 해. (게다가 2장에서 봤듯 복사하면 바코드가 리셋되니까 복사본은 애초에 다른 원소야.)
• if (Item.ReplicationID == INDEX_NONE) = "아직 바코드가 없는 원소냐?" 즉 새로 추가된 원소냐를 묻는 거야.
• Item.ReplicationID = ++IDCounter = 배열이 들고 있는 발급기(IDCounter)를 먼저 1 올리고, 그 번호를 바코드로 준다. ++가 앞에 붙으면 "올린 다음 값을 쓴다"는 뜻.
• if (IDCounter == INDEX_NONE) { IDCounter++; } = 발급기가 한 바퀴 돌아 -1(없음 값)에 걸리면 한 칸 더 넘긴다. "없음"이라는 특별한 번호를 실수로 바코드로 쓰지 않으려는 방어야. ArrayReplicationKey에도 똑같은 방어가 붙어 있는 게 보이지?
• Item.ReplicationKey++ = 이 원소의 도장을 하나 더 찍는다. 이 한 줄이 "이 원소 바뀌었어요" 신고 그 자체.
• MarkArrayDirty() = 원소를 건드렸으면 배열 도장도 같이 올린다. 원소 신고는 항상 배열 신고를 포함해.
• ItemMap.Reset() = "바코드 → 인덱스" 캐시 지도를 싹 비운다. 배열이 흔들렸으니 지도가 낡았거든. 다음에 필요할 때 다시 만든다. 옆 주석이 이유를 하나 더 대 — 클라가 예측으로 원소를 끼워 넣어도 복제가 안 망가지게 하려고.
• CachedNumItems = INDEX_NONE = 캐시해둔 원소 개수를 "모름"으로 되돌린다. 다음 전송 때 다시 세라는 뜻.
• #if WITH_PUSH_MODEL ... MARK_PROPERTY_DIRTY_UNSAFE(OwningObject, RepIndex) = 여기가 결정적이야. 배열 도장을 올리는 김에, push-model의 dirty 비트까지 같이 켠다. #if는 "push model이 켜진 빌드에서만 이 줄을 컴파일하라"는 조건부 컴파일이야.
🔁 이제 다시 보자. MarkItemDirty(Item)는 두 가지 일을 해. ① 바코드가 없으면(INDEX_NONE) 새로 발급하고 → 이게 곧 "추가"의 표시야. ② 도장을 하나 찍고(ReplicationKey++) 배열 도장도 올린다 → 이게 "변경"의 표시. 그리고 MarkArrayDirty()는 배열 도장만 올려 — 삭제는 원소가 사라져서 도장 찍을 대상이 없으니 이쪽을 쓴다.
🌱 여기서 두 층이 실제로 만난다
• IncrementArrayReplicationKey() 마지막의 MARK_PROPERTY_DIRTY_UNSAFE(OwningObject, RepIndex)가 Push Model과 FastArray를 잇는 이음매야.
• push-model에서 배운 그 MarkPropertyDirty(RepIndex)가 여기서 불려. 즉 MarkItemDirty(Items[3]) 한 번이 두 층에 동시에 손을 든다 — 바깥층(Push Model)엔 "이 오브젝트의 Items 프로퍼티 좀 봐라", 안쪽층(FastArray)엔 "그중에서도 3번 원소만 바뀌었다".
• 그래서 둘은 경쟁이 아니라 포개진다. Push Model이 "볼지 말지"의 문을 열어주고, FastArray가 "그 안에서 무엇을 보낼지"를 고른다. 게임 코드는 MarkItemDirty 하나만 부르면 두 층이 다 갱신돼.

🌱 이 개념은 왜 생겼나 — Push Model이 못 하는 걸 FastArray가 한다
• 원래 구조: push-model은 "값 바꾼 코드가 dirty 비트를 켠다"로 폴링 비용을 없앴어. 좋은 발상이지.
• 그런데 문제: Push Model은 최상위 프로퍼티 단위로만 추적해. 배열 3번 원소만 바꿔도 켤 수 있는 건 "Items 배열이 dirty" 비트 하나뿐이야. 그럼 결국 배열 전체가 다시 나간다 — 비교를 스킵했을 뿐, 전송량은 그대로.
• 그래서 필요한 것: 배열 안쪽에서 한 층 더 손드는 장치. 프로퍼티가 아니라 원소가 손을 들게. → 그게 MarkItemDirty야. Push Model은 "어떤 프로퍼티를 볼까"를 줄이고, FastArray는 "그 배열에서 무엇을 보낼까"를 줄인다. 같은 철학(신고제), 다른 층.

여기서 정렬 문제가 자동으로 풀리는 게 보이지? 인벤을 정렬해서 순서를 통째로 뒤집었어도, 바코드와 도장은 그대로야. 그럼 델타는 비어 있다. 인덱스 기준 비교였으면 전 원소가 dirty였을 상황인데, ID 기준이라 한 바이트도 안 나간다.

역으로 이게 한계이기도 해. 서버가 순서를 바꿔도 델타가 안 나가니까, 클라 배열의 순서는 서버와 다를 수 있어. FastArray는 "이 집합에 뭐가 들었나"는 맞춰주지만 "몇 번째 칸인가"는 안 맞춰줘. 순서가 의미 있으면(정렬된 랭킹 등) 원소 안에 SortOrder 같은 값을 직접 넣어서 클라가 정렬하게 해야 해.

5. 클라 콜백: 받은 델타를 어떻게 알려주나

클라는 델타를 받아서 자기 배열을 고쳐. 근데 그냥 조용히 고치면 UI는 어떻게 알지? 인벤 창을 매 프레임 통째로 다시 그릴 순 없잖아. 그래서 FastArray는 원소 단위로 콜백을 쏴줘. 원소 구조체에 이 함수들을 정의해두면 엔진이 알아서 부른다. 2장에서 접어뒀던 그 부분이야. FastArraySerializer.h:66-75:

/** * Optional functions you can implement for client side notification of changes to items; * Parameter type can match the type passed as the 2nd template parameter in associated call to FastArrayDeltaSerialize * * NOTE: It is not safe to modify the contents of the array serializer within these functions, nor to rely on the contents of the array * being entirely up-to-date as these functions are called on items individually as they are updated, and so may be called in the middle of a mass update. */ void PreReplicatedRemove(const struct FExampleArray& InArraySerializer); void PostReplicatedAdd(const struct FExampleArray& InArraySerializer); void PostReplicatedChange(const struct FExampleArray& InArraySerializer);

그리고 이건 선택이라서, 네가 안 짜면 아무것도 안 하는 빈 함수가 대신 불려. 부모가 기본값을 들고 있거든. FastArraySerializer.h:324-346:

/** * Called right before deleting element during replication. * * @param InArraySerializer Array serializer that owns the item and has triggered the replication call * * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PreReplicatedRemove(const struct FFastArraySerializer& InArraySerializer) { } /** * Called after adding and serializing a new element * * @param InArraySerializer Array serializer that owns the item and has triggered the replication call * * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PostReplicatedAdd(const struct FFastArraySerializer& InArraySerializer) { } /** * Called after updating an existing element with new data * * @param InArraySerializer Array serializer that owns the item and has triggered the replication call * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PostReplicatedChange(const struct FFastArraySerializer& InArraySerializer) { }
🔤 기호 사전 — 세 콜백
• Pre / Post = 각각 "~하기 직전" / "~한 직후". 이 접두사가 타이밍의 전부야.
• PreReplicatedRemove = 주석 왈 Called right before deleting element — 원소가 지워지기 직전에 불려. 아직 데이터가 살아 있는 마지막 순간이라, "무슨 버프가 사라졌는지"를 읽어서 이펙트를 꺼줄 수 있어. 지워진 뒤엔 읽을 게 없으니 반드시 Pre여야 해.
• PostReplicatedAdd = 원소가 추가된 직후. 새 아이템 아이콘을 UI에 붙이거나, 새 버프의 파티클을 켜는 자리.
• PostReplicatedChange = 기존 원소의 값이 갱신된 직후. 수량 숫자만 다시 그리면 되는 자리.
• const struct FExampleArray& InArraySerializer = 나를 담고 있는 배열 본인을 넘겨준다. 원소가 "내 주인이 누구지?"(어느 컴포넌트 소속인지)를 거슬러 올라가려고 쓰는 손잡이야. const라서 읽기만 하라는 뜻.
• FORCEINLINE ... { } = 부모가 들고 있는 빈 기본 구현이야. 몸통이 { } — 아무 일도 안 해. 네가 안 짜면 이게 불리고 공짜로 사라진다(인라인이라 호출 비용도 0에 가까워). 그래서 콜백은 선택인 거야.
• NOTE: intentionally not virtual; invoked via templated code = 일부러 virtual을 안 붙였다는 뜻이야. 그래서 이 콜백들은 "가상함수 오버라이드"가 아니야. 네 원소 구조체에 같은 이름·같은 시그니처의 함수를 그냥 정의해두면, 템플릿이 컴파일 타임에 그걸 골라 부른다. 가상 테이블을 거치지 않으니 런타임 비용이 0이고, 대신 이름을 한 글자라도 틀리면 조용히 부모의 빈 함수가 불린다(에러 없이!).
• NOT safe to modify the contents ... in the middle of a mass update = 주석이 대놓고 경고해. 이 콜백은 원소 하나 처리할 때마다 개별 호출돼서, 이 시점의 배열은 공사 중이야. 여기서 배열에 원소를 추가/삭제하면 엔진이 돌던 자리가 무너진다.
⚠️ "오버라이드가 아니다"의 함정. virtual이 아니라 템플릿 이름 매칭이라, PostReplicatedAdd를 PostReplicateAdd로 오타 내도 컴파일이 된다. override 키워드가 잡아주지도 않아(가상함수가 아니니까). 그냥 부모의 빈 함수가 불리고, 클라 UI만 조용히 안 갱신돼. 이 챕터의 다른 함정들과 똑같은 종류지 — 에러 없이 조용히 아무 일도 안 일어난다.
🔁 이제 다시 보자. 클라가 델타를 풀면서, 지울 원소엔 지우기 전에 PreReplicatedRemove를, 새로 넣은 원소엔 넣은 뒤 PostReplicatedAdd를, 값만 고친 원소엔 고친 뒤 PostReplicatedChange를 부른다. UI·이펙트는 이 세 지점에만 붙이면 돼 — 폴링 없이, 바뀐 원소에 대해서만 반응하는 거지. 우리가 SP_ITEM_ADD 핸들러, SP_ITEM_REMOVE 핸들러를 손으로 등록하던 그 자리가 여기야.

배열 구조체(FFastArraySerializer) 쪽에도 배치 단위 콜백이 있어. 원소 하나하나가 아니라 "이번 업데이트에서 3개 추가, 1개 삭제됐다"를 한 번에 받는 버전이야. FastArraySerializer.h:486-505:

/** * Called before removing elements and after the elements themselves are notified. The indices are valid for this function call only! * * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PreReplicatedRemove(const TArrayView<int32>& RemovedIndices, int32 FinalSize) { } /** * Called after adding all new elements and after the elements themselves are notified. The indices are valid for this function call only! * * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PostReplicatedAdd(const TArrayView<int32>& AddedIndices, int32 FinalSize) { } /** * Called after updating all existing elements with new data and after the elements themselves are notified. The indices are valid for this function call only! * * NOTE: intentionally not virtual; invoked via templated code, @see FExampleItemEntry */ FORCEINLINE void PostReplicatedChange(const TArrayView<int32>& ChangedIndices, int32 FinalSize) { }
🔤 기호 사전 — 배치 콜백
• TArrayView<int32>& RemovedIndices = "이번에 건드린 원소들의 인덱스 목록". TArrayView는 복사 없이 남의 배열을 들여다보는 창이라고 보면 돼.
• The indices are valid for this function call only! = 느낌표까지 붙여 경고해. 이 인덱스 목록을 어디 저장해두면 안 된다는 뜻이야. 창(view)일 뿐이라 함수가 끝나면 가리키던 메모리가 사라져. 필요하면 이 함수 안에서 다 쓰거나, 값을 복사해둬.
• int32 FinalSize = 이 업데이트가 다 끝났을 때의 배열 크기. 미리 알려주니 UI 슬롯을 한 번에 잡을 수 있어.
• and after the elements themselves are notified = 호출 순서를 못 박은 문장이야. 원소 콜백이 먼저 전부 돌고, 그다음에 배열 배치 콜백이 불린다. 즉 배치 콜백 시점엔 개별 반응이 이미 끝나 있어.
• 왜 배치가 필요해? = 원소 콜백은 10개 바뀌면 10번 불려. UI를 10번 다시 그리면 낭비지. 배치 콜백은 한 번 불리니까 "인벤 새로고침 1회"로 끝낼 수 있어.
🔁 이제 다시 보자. 콜백이 두 층이고 순서가 정해져 있어 — 원소 콜백이 먼저 원소마다 돌고(and after the elements themselves are notified), 그다음 배열 배치 콜백이 한 번 돈다. 원소 콜백은 "이 아이템 하나에 무슨 일이 났나"(파티클 켜기 같은 개별 반응), 배치 콜백은 "이번 업데이트로 총 뭐가 바뀌었나"(UI 한 방 갱신). 개별 반응은 원소에, 뭉쳐서 할 일은 배열에 붙인다.

6. 실무에선 어디에 쓰나

이름은 낯설어도 언리얼 게임 만들면 거의 무조건 만나게 돼. 자주 찔끔 바뀌는 목록은 전부 후보야.

  • 인벤토리 / 장비 목록 — 아이템 하나 먹고, 하나 쓰고. 딱 FastArray용이야. Lyra 샘플의 인벤 리스트가 이 구조로 돼 있어.
  • 버프·디버프 (GameplayEffect) 목록 — GAS(Gameplay Ability System)의 활성 이펙트 컨테이너가 FastArray야. 버프 하나 걸릴 때마다 전체 버프 목록을 재전송하면 전투 중에 대역폭이 터지니까. → 클라 이펙트/아이콘은 PostReplicatedAdd·PreReplicatedRemove에서 켜고 끈다.
  • 팀 / 플레이어 목록 — 20명 방에서 1명 들어오고 1명 나갈 때, 20명 정보를 다시 보낼 이유가 없지.
  • 킬로그 / 채팅 로그 — 계속 뒤에 추가만 되는 목록. 추가된 줄만 나가면 돼.
  • 퀘스트 진행 상황, 스킬 쿨다운 목록 — 하나씩 갱신되는 전형적 케이스.

기준은 단순해. "원소 수는 많은데, 한 번에 바뀌는 건 몇 개 안 된다" → FastArray. 반대로 원소가 3~4개뿐이고 어차피 매번 다 바뀐다면? 통짜 TArray가 더 싸. FastArray는 바코드·도장·지도(ItemMap) 같은 관리 비용을 내는 대신 전송량을 줄이는 거래니까, 줄일 게 없으면 손해야.

7. 한계 — 공짜가 아니다

ch-19에서 Push Model이 "손 안 들면 안 본다"는 규칙 때문에 함정이 생겼듯, FastArray도 똑같이 대가를 치러.

  1. "원소 통짜 전송"은 옛말이다 — 하지만 원소는 여전히 얇게 유지해라. 여기는 낡은 지식이 많이 돌아다니는 대목이라 소스를 직접 봐야 해. 예전엔 정말 그랬어 — ReplicationKey가 오른 원소는 안의 필드 40개가 통째로 나갔지. 근데 UE5의 헤더 주석은 이렇게 말한다. FastArraySerializer.h:208-211:
    * Delta Serialization for inner structs is now enabled by default. That means that when a ReplicationKey changes, we will compare the current state of the * struct to the last sent state, tracking changelists and only sending properties that changed exactly like the standard replication path. * If this causes issues with a specific FastArray type, it can be disabled by calling FFastArraySerializer::SetDeltaSerializationEnabled(false) in the constructor. * The feature can be completely disabled by setting the "net.SupportFastArrayDelta" CVar to 0.
    번역하면: 원소 내부까지 델타로 쪼개는 게 이제 기본값이야. ReplicationKey가 오르면, 엔진이 그 원소를 지난번 보낸 상태와 비교해서 changelist를 만들고 바뀐 프로퍼티만 보내 — "exactly like the standard replication path", 즉 일반 복제 경로와 똑같이. 그래서 두 층의 델타가 포개져: 바깥(FastArray)이 "어떤 원소를 보낼까"를 고르고, 안쪽(changelist)이 "그 원소의 어떤 필드를 보낼까"를 고른다.
    그런데도 원소를 얇게 유지해야 하는 이유는 남아 있어. 델타가 공짜가 아니거든 — 원소가 두꺼우면 비교 비용과 클라별로 보관하는 "지난번 보낸 상태"의 메모리가 그만큼 커져. 전송량은 줄었어도 CPU와 메모리는 필드 수에 비례해. 그리고 문제가 생기면 SetDeltaSerializationEnabled(false)나 net.SupportFastArrayDelta 0으로 끌 수 있다는 건, 뒤집으면 꺼지면 다시 통짜로 돌아간다는 뜻이기도 하고.
  2. 순서 보장 없음. 4장에서 봤듯 ID 기준이라 순서 변경은 델타로 안 잡혀. 클라 배열의 인덱스 순서를 절대 신뢰하면 안 돼. 원소를 찾을 땐 인덱스가 아니라 고유값(아이템 GUID 등)으로 찾고, 순서가 의미 있으면 정렬 키를 원소 안에 넣어 보내.
  3. 마킹 안 하면 조용히 유실. MarkItemDirty를 빼먹으면 서버 값만 바뀌고 클라는 영원히 옛날 값. 로그도 에러도 없어. Push Model의 "dirty 마킹 없이 값 바꾸면 변경이 조용히 유실" 함정과 똑같은 종류야. 배열을 직접 만지는 코드를 여기저기 흩뿌리지 말고, Add/Remove/Update 함수를 하나씩 만들어 그 안에서만 마킹하는 게 유일한 방어책이야.
  4. 콜백 안에서 배열 수정 금지. 주석이 명시하듯 콜백은 대량 업데이트 중간에 원소별로 불려. 그 시점의 배열은 공사 중이라 원소를 추가·삭제하면 터진다. 뭔가 고쳐야 하면 플래그만 세워두고 다음 틱에 처리해.
  5. 관리 비용은 항상 든다. ItemMap 재구축, 원소 순회, 클라마다 지난 상태 보관 — 이건 배열이 안 바뀌어도(조기 탈출 덕에 적게나마) 계속 드는 비용이야. 원소 몇 개짜리 배열엔 오히려 손해라는 얘기.

가장 큰 사고방식 차이는 이거야. 우리는 "어떤 패킷을 언제 쏠지"를 게임 로직이 직접 결정했어. 아이템을 지우는 코드가 SP_ITEM_REMOVE를 쏘는 책임까지 졌지. 그래서 로직 분기가 늘어날 때마다 "여기서도 패킷 쏴야 하나?"를 매번 확인해야 했고, 한 군데 빼먹으면 클라가 틀어졌어.

언리얼은 그 책임을 반으로 쪼갰어. 게임 코드는 "바뀌었다"고 손만 든다(MarkItemDirty). 무엇을 어떤 형태로 보낼지는 엔진이 결정해. 손드는 건 여전히 사람 몫이라 빼먹으면 똑같이 유실되지만(그래서 함정도 같지만), 최소한 패킷 3종 세트를 설계하고 핸들러를 등록하는 노동은 사라졌어. 클라 쪽 핸들러도 콜백 세 개 override로 끝나고.

그리고 우리 서버였다면 "클라마다 지난 상태를 기억" 하는 게 제일 귀찮았을 거야. A는 30초 전에 접속했고 B는 방금 들어왔으면 델타 기준점이 다르니까. 결국 귀찮아서 신규 접속자한테 "그냥 전체 스냅샷 한 번 쏘자"로 타협했지. UE는 그 연결별 기준점을 엔진이 들고 있어서, 신규 클라에겐 자동으로 "전 원소가 ADD"인 델타가 나가. 스냅샷 코드를 따로 안 짜도 되는 거야.

초보가 헷갈리는 용어 (짧게)

  • ReplicationID: 원소의 바코드. MarkItemDirty가 처음 발급. 인덱스가 아니라 이게 원소의 정체성. 절대 직접 대입하지 마.
  • ReplicationKey: 원소의 버전 번호(도장 개수). 내용 바뀌면 +1. 지난번 보낸 값과 다르면 "변경된 원소"로 분류돼.
  • ArrayReplicationKey: 배열 전체의 버전 번호. 뭐 하나라도 바뀌면 +1. 같으면 원소를 훑지도 않고 조기 탈출하는 데 쓴다.
  • MarkItemDirty(Item): 추가·변경 신고. 바코드가 없으면 발급하고, 도장을 찍고, 배열 도장까지 올린다.
  • MarkArrayDirty(): 삭제 및 대량 변경 신고. 사라진 원소엔 도장 못 찍으니 배열 도장만 올려 "다시 훑어봐"라고 알린다.
  • NetDeltaSerialize: "이 구조체는 차이만 직렬화합니다"라는 엔진 규약. 통짜 복제 경로 대신 이쪽을 탄다. WithNetDeltaSerializer = true로 등록해야 실제로 불려.
  • 델타(delta): 전체가 아니라 차이. 이 책에서 계속 나온 개념이야 → changelist(프로퍼티 단위 델타), FastArray(배열 원소 단위 델타).

Q1. FastArraySerializer, 왜 필요한가요?

답 보기
TArray를 그냥 UPROPERTY(Replicated)로 걸면 통짜 복제가 돼. 원소 하나만 바뀌어도 배열 전체가 다시 나가. 아이템 100개짜리 인벤에서 물약 수량 4바이트 바꿨는데 1200바이트가 날아가는 거지. 게다가 인덱스로 비교하니까 정렬만 해도 전 원소가 dirty야. FastArraySerializer는 원소마다 ID(바코드)와 Key(도장)를 붙여서, 추가된 놈·도장이 오른 놈·사라진 놈만 골라 보내. 우리가 손으로 만들던 SP_ITEM_ADD/REMOVE/UPDATE 3종 세트를 엔진이 자동으로 만들어주는 셈이야.

↳ Push Model 켜면 해결되는 거 아닌가요?

답 보기
안 돼. Push Model은 최상위 프로퍼티 단위로만 추적하거든. 배열 3번 원소만 바꿔도 켤 수 있는 건 "Items 배열이 dirty"라는 비트 하나뿐이야. 그럼 비교는 스킵되지만 전송량은 그대로 — 결국 배열 전체가 나가. Push Model은 "어떤 프로퍼티를 볼까"를 줄이고, FastArray는 "그 배열에서 무엇을 보낼까"를 줄여. 같은 철학(비교 말고 신고해라), 다른 층이야. 그래서 둘은 경쟁 관계가 아니라 보완 관계지.

↳ 그럼 모든 배열에 FastArray를 쓰면 되나요?

답 보기
아니. FastArray는 바코드·도장·ItemMap·클라별 지난 상태 같은 관리 비용을 내고 전송량을 사는 거래야. 그러니까 "원소는 많은데 한 번에 바뀌는 건 몇 개 안 되는" 배열에만 이득이지. 원소가 3~4개뿐이고 어차피 매번 다 바뀌는 배열이면 줄일 게 없어서 오히려 손해야. 인벤·버프·팀 목록·킬로그처럼 길고 찔끔 바뀌는 목록이 정확한 타깃이야.

Q2. 서버는 "어떤 원소가 바뀌었는지"를 어떻게 알아내나요?

답 보기
원소마다 ReplicationID(바코드)와 ReplicationKey(도장 개수)가 있어. 서버는 클라마다 "지난번에 보낼 때 바코드별 도장이 몇이었는지"를 기억해둬. 보낼 때 현재 배열을 훑어서 대조하면 세 갈래가 나와 — 지난 기록에 없던 바코드면 ADD, 있는데 도장이 오른 거면 CHANGE, 지금 배열에 없어진 바코드면 REMOVE. 도장이 그대로인 원소는 어느 갈래에도 안 걸려서 한 바이트도 안 실려. 100개 중 1개 바꿨으면 1개만 나가는 게 이 대목이야.

↳ 배열 전체 키(ArrayReplicationKey)는 왜 또 따로 있죠?

답 보기
조기 탈출용이야. 원소별 대조를 하려면 배열을 한 번 훑어야 하잖아. 근데 대부분의 프레임에서 그 배열은 아무것도 안 바뀌어. 그래서 문 앞에서 "지난번 보낼 때 배열 도장 == 지금 배열 도장?"만 먼저 봐. 같으면 원소 100개를 훑지도 않고 즉시 빠져나가. MarkItemDirty가 원소 도장을 찍고 나서 항상 MarkArrayDirty를 같이 부르는 이유가 이거야 — 원소를 건드렸으면 배열 도장도 올라가야 조기 탈출에 안 걸리거든.

↳ 인벤을 정렬해서 순서만 뒤집으면 뭐가 나가나요?

답 보기
아무것도 안 나가. 바코드도 도장도 안 바뀌었으니 델타가 비어 있어. 인덱스 기준 비교였으면 전 원소가 dirty였을 상황인데, ID 기준이라 공짜야. 근데 이게 동전의 양면이야 — 서버가 순서를 바꿔도 클라엔 안 전달된다는 뜻이거든. 그래서 클라 배열의 인덱스 순서는 서버와 다를 수 있고, 절대 신뢰하면 안 돼. 순서가 의미 있으면 원소 안에 정렬 키를 넣어 보내서 클라가 직접 정렬하게 해야지.

Q3. MarkItemDirty를 안 부르면 어떻게 되나요?

답 보기
서버 값만 바뀌고 클라는 영원히 옛날 값이야. 도장이 안 올라갔으니 델타 계산에서 "안 바뀐 원소"로 판정돼서 안 실려. 에러도 로그도 안 나. 조선 서버에서 "DB엔 반영됐는데 클라에 안 뜬다" 하던 사고랑 정확히 같은 종류야. Push Model의 "dirty 마킹 없이 값 바꾸면 조용히 유실" 함정과도 똑같지. 방어책은 하나야 — 배열을 직접 만지는 코드를 여기저기 흩뿌리지 말고, AddItem / RemoveItem / UpdateItem 함수를 만들어 마킹을 그 안에 가둬라.

↳ 삭제는 왜 MarkItemDirty가 아니라 MarkArrayDirty인가요?

답 보기
사라진 원소엔 도장을 찍을 대상 자체가 없으니까. MarkItemDirty는 원소를 참조로 받아서 그 안의 ReplicationKey를 올리는 함수인데, 이미 배열에서 빠진 원소한테 그걸 할 수가 없잖아. 그래서 배열 도장만 올려서 "이 배열 뭔가 달라졌으니 다시 훑어봐"라고 알려. 그러면 서버가 훑다가 "지난 기록엔 있던 바코드가 지금 배열엔 없네" → REMOVE로 분류하는 거야. 삭제는 없어진 걸로 자기 증명하는 셈이지.

Q4. 클라는 받은 델타를 어떻게 처리하나요?

답 보기
클라가 델타를 풀면서 원소 단위로 콜백을 쏴줘. 지울 원소엔 지우기 직전에 PreReplicatedRemove(아직 데이터가 살아 있어야 "무슨 버프가 사라졌는지" 읽고 이펙트를 끄니까 반드시 Pre여야 해), 새로 들어온 원소엔 추가된 직후 PostReplicatedAdd, 값만 바뀐 원소엔 PostReplicatedChange. UI·이펙트는 이 세 지점에만 붙이면 되니까 폴링 없이 바뀐 원소에만 반응해. 우리가 SP_ITEM_ADD 핸들러를 손으로 등록하던 그 자리를 엔진이 자동으로 불러주는 거야. 배열 struct 쪽에 배치 콜백을 달면 "이번에 3개 추가, 1개 삭제"를 한 번에 받아서 UI를 한 방에 갱신할 수도 있어.

↳ 그 콜백 안에서 배열을 고쳐도 되나요?

답 보기
안 돼. 엔진 주석이 대놓고 경고해 — 이 콜백들은 대량 업데이트 중간에 원소별로 개별 호출되거든. 그 시점의 배열은 공사 중이라 아직 전부 최신도 아니고, 여기서 원소를 추가·삭제하면 엔진이 돌던 자리가 무너져. 뭔가 고쳐야 하면 플래그만 세워두고 다음 틱에 처리해야 해. 그리고 여기서 낡은 지식 하나를 정정하고 갈게. "FastArray는 원소를 통째로 보낸다"는 말이 아직도 돌아다니는데, UE5에선 아니야. 헤더 주석이 Delta Serialization for inner structs is now enabled by default라고 못 박아(FastArraySerializer.h:208). ReplicationKey가 오르면 엔진이 그 원소를 지난번 보낸 상태와 비교해 바뀐 프로퍼티만 보내 — 일반 복제 경로와 똑같이. 그러니까 델타가 두 층인 거지: 바깥이 "어떤 원소", 안쪽이 "그 원소의 어떤 필드". 그래도 원소는 얇게 유지하는 게 맞아 — 전송량은 줄어도 비교 비용과 클라별 "지난 상태" 메모리는 필드 수에 비례하니까.

🎯 원리 한 줄 요약

통짜 TArray 복제는 원소 하나만 바뀌어도 배열 전체를 다시 보내고, FastArraySerializer는 원소마다 ID(바코드)와 Key(도장)를 달아 "추가된 놈 / 도장이 오른 놈 / 사라진 놈"만 델타로 보낸다 — 우리가 손으로 나눠 만들던 SP_ITEM_ADD/REMOVE/UPDATE를 엔진이 자동 생성해주는 것이고, 대신 MarkItemDirty로 손드는 규율은 여전히 사람 몫이다.

  • 막히면 → changelist (바뀐 것만 모으는 델타의 원형), push-model (프로퍼티 층에서 손드는 법 — 왜 배열 안쪽은 못 잡는지)
  • 같이 보면 좋음 → subobject-replication (배열 대신 서브오브젝트 목록으로 인벤을 표현하는 다른 길)
