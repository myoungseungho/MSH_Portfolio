연결 생명주기: 접속부터 끊김까지

손님이 문을 두드리면 무슨 일이 벌어지나

가게를 하나 떠올려봐. 손님이 문을 밀고 들어와. 근데 가게 주인이 아무나 다 들이진 않아. 순서가 있어.

  1. 문 앞에서 판정 — "지금 손님 받는 가게 맞아? 아니면 문 닫는 중이야?"
  2. 신원 확인 — "예약자 명단에 있어? 밴 당한 사람 아니야?"
  3. 자리 안내 — "OK, 통과. 저기 3번 테이블로 가"
  4. 착석 완료 처리 — "앉았네. 물수건 갖다주고 주문 받자"
  5. 나갈 때 정리 — "가셨으니 테이블 치우고 명단에서 빼자"

MMORPG 서버 프로그래머면 이 흐름이 하나도 안 낯설걸. 우리 조선협객전도 클라가 소켓 붙이면 SetClient 어쩌고 하면서 세션 만들고, 끊기면 LogOut 태워서 정리하잖아. 딱 그거야.

UE도 똑같아. 다만 어느 함수가 어느 단계를 맡는지만 알면 돼. UE는 이 다섯 단계를 각각 다른 함수에 딱딱 나눠놨거든. 이번 챕터는 그 함수들을 접속→끊김 순서대로 한 번 훑는 게 전부야. 마법 없어. 그냥 "어느 문지기가 어느 관문을 지키나"만 외우면 끝.

맞춰봐. 클라가 서버에 소켓을 붙이는 그 순간, 서버가 바로 그 클라의 PlayerController(플레이어 조종 객체)를 만들어줄까?

반전. 아니야. 소켓이 붙는 것과 PlayerController가 생기는 건 한참 떨어져 있어. 그 사이에 로그인 협상(핸드셰이크), 게임코드 승인 심사, 클라의 맵 로딩까지 여러 관문이 껴 있어. PlayerController는 이 챕터 흐름에서 거의 마지막에, 클라가 "나 맵 다 깔았어!"라고 보고한 다음에야 태어나. 왜 그런지는 아래에서 하나씩 풀어줄게.

NetConnection이 소켓 위에 어떻게 얹히는지, NetDriver가 뭔지가 흐릿하면 → netconnection-overview 먼저 보고 와. 이번 챕터는 "그 연결이 태어나서 죽기까지"의 얘기라, 연결 객체가 뭔지는 잡고 오는 게 안 헤매. 여기선 다시 설명 안 하고 링크로 넘길게 — 안 그러면 챕터마다 같은 소리 무한 반복이거든.

1. 큰 그림 — 다섯 단계, 다섯 문지기

전체를 다섯 덩어리로 쪼갤 수 있어. 각 덩어리마다 대표 함수가 하나씩 있어.

  • A. 서버 기동 — 서버가 포트 열고 손님 받을 준비 (UWorld::Listen)
  • B. 접속 수락 — 문 앞 판정, 초기 채널 허용 (NotifyAcceptingConnection)
  • C. 로그인 협상 — 제어 메시지로 신원 확인·승인 심사 (NotifyControlMessage → NMT_Login)
  • D. 입장 완료 — PlayerController 생성 (NMT_Join → SpawnPlayActor → PostLogin)
  • E. 끊김 정리 — 연결 청소, 로그아웃 (CleanUp → Logout)

여기서 딱 하나만 미리 못 박고 갈게. C와 D는 별개야. 로그인(신원 확인)이 통과했다고 곧바로 캐릭터가 게임에 서 있는 게 아니야. 로그인 통과 후에 클라가 맵을 다운로드/로드하고, 그게 끝나야 D(조인)로 넘어가. 이 "협상 → 로딩 → 조인"의 2박자가 UE 접속의 핵심 리듬이야.

2. B단계 — 문 앞 판정: 손님 받아도 돼?

클라가 원격에서 접속을 시도하면, 서버는 제일 먼저 "이 접속 받아도 되나?"를 판정해. 그게 NotifyAcceptingConnection이야.

World.cpp:6962

EAcceptConnection::Type UWorld::NotifyAcceptingConnection()
{
	check(NetDriver);
	if( NetDriver->ServerConnection )
	{
		// We are a client and we don't welcome incoming connections.
		UE_LOG(LogNet, Log, TEXT("NotifyAcceptingConnection: Client refused") );
		return EAcceptConnection::Reject;
	}
	else if( NextURL!=TEXT("") )
	{
		// Server is switching levels.
		UE_LOG(LogNet, Log, TEXT("NotifyAcceptingConnection: Server %s refused"), *GetName() );
		return EAcceptConnection::Ignore;
	}

읽어보면 별거 없어. 세 갈래 판정이야.

  1. NetDriver->ServerConnection이 있으면 → Reject. ServerConnection은 "내가 누군가에게 붙은 클라다"라는 표식이야. 클라는 남의 접속을 받는 놈이 아니니까 거절. 즉 "너 서버 아니고 클라잖아"를 여기서 걸러.
  2. NextURL이 비어있지 않으면 → Ignore. 서버가 지금 레벨 전환 중이란 뜻. 이사 중엔 새 손님 안 받아. (레벨 전환이 뭔지 궁금하면 → travel)
  3. 둘 다 아니면 → Accept. 정상 가동 중인 서버. 손님 받아.

수락이 확정되면 NotifyAcceptedConnection(World.cpp:6985)이 로그/프로파일에 "OPEN" 이벤트를 남겨. 그리고 NotifyAcceptingChannel(World.cpp:6993)이 하나 더 지켜 — 클라가 맨 처음 여는 컨트롤 채널(채널0)만 허용하고 나머지는 다 거부해. 왜? 아직 로그인도 안 한 놈이 게임플레이 채널을 함부로 열게 두면 안 되잖아. 협상은 오직 채널0으로만.

채널이 뭔지, 채널0이 왜 특별한지 → channel-types

3. C단계 — 로그인 협상: 제어 메시지 상태머신

문은 통과했어. 이제 신원 확인 차례. 여기서 **컨트롤 메시지(NMT_*)**가 등장해.

컨트롤 메시지는 게임플레이 패킷이 아니야. 채널0으로만 오가는 저수준 핸드셰이크 프로토콜이야. "나 로그인할래"(NMT_Login), "어서 와, 이 레벨로 접속해"(NMT_Welcome), "맵 다 깔았어, 조인할게"(NMT_Join) 같은 협상 신호들이지.

이 신호들을 타입별로 분기하는 커다란 스위치가 UWorld::NotifyControlMessage(World.cpp:7114)야. 이게 바로 접속 협상의 상태머신이야. 그중 로그인 케이스(case NMT_Login: World.cpp:7356)를 보자.

World.cpp:7413

핵심은 이거야. 클라의 신원(PlayerId)을 커넥션에 저장한 다음, 게임코드에게 입장 허가를 물어봐 — GameMode->PreLoginAsync(...).

여기서 두 가지 포인트.

첫째, GetAuthGameMode(). GameMode는 오직 권위 서버(데디케이티드 서버)에만 존재해. 클라엔 아예 없어. 그러니 이 코드가 도는 것 자체가 "여긴 서버다"의 증거야. 로그인/로그아웃 심사는 전부 GameMode가 쥐고 있어.

둘째, PreLoginAsync — 이름에 Async가 붙었지. 밴 체크, 정원 체크 같은 심사는 DB를 때리거나 시간이 걸릴 수 있어. 그래서 비동기야. 심사가 끝나면 콜백(OnComplete → PreLoginComplete)이 불려. 우리 서버로 치면 로그인 패킷 받고 AccountDB에 조회 던지고, 응답 오면 이어서 처리하는 그 느낌이랑 똑같아.

심사가 통과하면 콜백이 이걸 실행해.

World.cpp:7725

void UWorld::PreLoginComplete(const FString& ErrorMsg, TWeakObjectPtr<UNetConnection> WeakConnection)
{
	UNetConnection* Connection = WeakConnection.Get();
	if (!PreLoginCheckError(Connection, ErrorMsg))
	{
		return;
	}

	WelcomePlayer(Connection);
}

에러 없으면 WelcomePlayer(World.cpp:7033)를 불러. 이게 클라에게 NMT_Welcome을 쏴 — "환영해, 이 레벨명·게임명으로 접속 준비해." 클라는 이 신호를 받고 나서야 해당 맵을 로드하기 시작해.

여기 WeakObjectPtr 쓴 거 봤지? 비동기 콜백이 도는 사이에 커넥션이 이미 끊겨 사라졌을 수 있거든. 약참조로 받아서 .Get()이 null이면 조용히 관두는 거야. 비동기 경계에서 객체 수명 챙기는 정석 패턴이야.

4. D단계 — 진짜 입장: PlayerController가 태어난다

클라가 맵 로딩을 끝내면 이제 NMT_Join(World.cpp:7440)을 보내. "나 준비 끝, 게임에 넣어줘." 여기가 PlayerController가 태어나는 지점이야.

World.cpp:7442

마지막 줄이 알맹이야. SpawnPlayActor(LevelActor.cpp:1071)가 이 커넥션 전용 PlayerController를 만들어. 이 안에서 GameMode->Login(...)(GameModeBase.cpp:707)이 불려서 실제 컨트롤러가 스폰돼. 그리고 스폰 직후 이 지점에 도달해.

LevelActor.cpp:1100

두 줄만 눈에 담아.

  • SetPlayer(NewPlayer) (LevelActor.cpp:1109) — 갓 만든 컨트롤러에 커넥션(UPlayer)을 결합해. 이제 이 PlayerController와 이 네트워크 연결이 1:1로 묶였어. 입력이 오면 어느 컨트롤러로 갈지 정해진 거야.
  • PostLogin(NewPlayerController) (LevelActor.cpp:1110) — 입장 완료 후처리를 태워. AGameModeBase::PostLogin(GameModeBase.cpp:1016) 안에서 GameSession->PostLogin, OnPostLogin 이벤트 방송, 그리고 HandleStartingNewPlayer가 폰(Pawn)을 스폰해.

여기서 PlayerController vs Pawn 구분이 딱 드러나. PlayerController = 접속한 플레이어 그 자체(입력·명령의 주체, 커넥션과 1:1). Pawn = 그 컨트롤러가 조종하는 게임 속 캐릭터. 순서 봤지? 컨트롤러가 먼저 태어나고(Login), 그 뒤에 폰이 붙어(PostLogin의 HandleStartingNewPlayer). 사람이 먼저 게임에 들어오고, 그 사람이 조종할 몸뚱이는 그다음에 배정되는 거야.

그리고 이 세 이름의 순서가 곧 생명주기 3단계야:

  • PreLogin = 입장 허가 심사 (밴·정원, 비동기 가능) — C단계
  • Login = PlayerController 실제 생성·초기화 — D단계 앞부분
  • PostLogin = 생성 후 후처리 (폰 스폰, 이벤트 방송) — D단계 뒷부분

조인이 성공하면 커넥션 상태가 SetClientLoginState(ReceivedJoin)(World.cpp:7477)으로 올라가. 이 플래그가 뒤에 끊김 처리에서 운명을 가르니까 기억해둬.

폰이 왜 컨트롤러랑 따로 노는지, Possess가 뭔지 더 파고들려면 → charactermovement-overview

|                     -> AController::Destroyed()  Controller.cpp:591|
|                          GameMode->Logout()  GameModeBase.cpp:1066 |
|       [PC 없으면]  PendingConnectionLost 델리게이트  NetConnection.cpp:1480 |
+-------------------------------------------------------------------+

6. E단계 — 끊김: 들어온 순서를 거꾸로 되감기

클라가 나가거나 타임아웃되면 정리가 시작돼. 시작점은 UNetConnection::CleanUp()(NetConnection.cpp:1364)이야. 자식 커넥션·채널을 치우고, Driver->RemoveClientConnection으로 서버의 클라 목록에서 빼고, 로그인 상태를 CleanedUp으로 내려. 그 안에서 소유 액터(PlayerController)를 처리하러 DestroyOwningActor로 넘어가.

NetConnection.cpp:1465

void UNetConnection::DestroyOwningActor()
{
	if (OwningActor != nullptr)
	{
		// Cleanup/Destroy the connection actor & controller
		if (!OwningActor->HasAnyFlags(RF_BeginDestroyed | RF_FinishDestroyed))
		{
			// UNetConnection::CleanUp can be called from UNetDriver::FinishDestroyed that is called from GC.
			OwningActor->OnNetCleanup(this);
		}
		OwningActor = nullptr;
		PlayerController = nullptr;
	}
	else
	{
		if (ClientLoginState < EClientLoginState::ReceivedJoin)
		{
			UE_LOG(LogNet, Log, TEXT("UNetConnection::PendingConnectionLost. %s bPendingDestroy=%d "), *Describe(), bPendingDestroy);
			FGameDelegates::Get().GetPendingConnectionLostDelegate().Broadcast(PlayerId);
		}
	}
}

여기가 아까 못 박아둔 그 갈림길이야. if (OwningActor != nullptr) — 소유 액터(PC)가 있냐 없냐로 두 세계가 갈려.

PC가 있으면 (정상 입장한 유저였음): OnNetCleanup을 태워. 이게 APlayerController::OnNetCleanup(PlayerController.cpp:1467)으로 가서 PC-커넥션 결합을 풀고 Destroy(true)로 PC를 파괴해. PC가 파괴되면 AController::Destroyed()가 불려.

Controller.cpp:591

void AController::Destroyed()
{
	if (GetLocalRole() == ROLE_Authority && PlayerState != NULL)
	{
		// if we are a player, log out
		AGameModeBase* const GameMode = GetWorld()->GetAuthGameMode();
		if (GameMode)
		{
			GameMode->Logout(this);
		}

		CleanupPlayerState();
	}

GameMode->Logout(this)(GameModeBase.cpp:1066)가 정식 로그아웃 게임코드를 돌려 — GameModeLogoutEvent 방송, GameSession->NotifyLogout. 들어올 때 Login → PostLogin 태웠던 걸 나갈 때 Logout으로 대칭적으로 되감는 거야.

PC가 없으면 (else 분기, NetConnection.cpp:1480): 이건 조인 전에 끊긴 경우야. ClientLoginState < ReceivedJoin이면 — 즉 협상 중이거나 맵 로딩 중에 나가버린 손님이면 — 만들 PC가 애초에 없었으니 파괴할 것도, Logout 태울 것도 없어. 그냥 PendingConnectionLost 델리게이트만 쏘고 끝.

이래서 아까 ReceivedJoin 플래그를 기억하랬던 거야. 이 플래그 하나가 "정식 입장한 유저의 정상 종료"와 "대기 중 이탈한 손님"을 가르는 기준이거든. 로그인 협상만 하다 튕긴 놈한테 Logout 이벤트를 쏘면 명단에 없는 유저를 로그아웃시키는 꼴이라 사고 나잖아. UE는 그걸 이 한 줄로 막아.

7. 우리 서버랑 비교 — IOCP 워커 vs UE 싱글스레드 액터

조선협객전 서버 감각으로 이걸 다시 보면 이래.

우리 서버 (IOCP 멀티스레드):

  • 클라가 소켓 붙이면 IOCP AcceptEx 완료 → 워커 스레드가 세션 객체 생성
  • 로그인 패킷(CM_LOGIN 류) 오면 워커 스레드가 AccountDB에 비동기 조회
  • 응답 오면 SetClient 태워서 TCharacter 붙이고 게임 입장
  • 끊기면 LogOut 태워서 세션·캐릭터 정리, DB 저장
  • 여러 워커 스레드가 동시에 여러 커넥션을 처리 → 공유 자원엔 락 필요

UE (싱글스레드 액터 모델):

  • 소켓 수락·컨트롤 메시지 처리 전부 게임 스레드 한 곳에서 순차로
  • NotifyControlMessage 상태머신이 우리 CM_* 핸들러 스위치에 대응
  • PreLoginAsync의 비동기는 스레드를 째는 게 아니라 콜백 델리게이트로 넘겨(응답 오면 게임 스레드에서 이어감) → 그래서 락이 거의 안 나와
  • PlayerController = 우리 TCharacter가 붙는 세션 개념 + 입력 주체를 합친 것에 가까움

핵심 대응표:

단계우리 서버 (IOCP)UE
접속 수락AcceptEx 완료 → 세션 생성NotifyAcceptingConnection → Accept
신원 심사CM_LOGIN → AccountDB 비동기 조회NMT_Login → PreLoginAsync (콜백)
입장SetClient (TCharacter 결합)NMT_Join → SpawnPlayActor+PostLogin
끊김LogOut (세션·캐릭터 정리)CleanUp → Logout

제일 큰 체감 차이는 동시성 모델이야. 우리는 워커 N개가 병렬로 굴러서 락·경합을 늘 신경 써야 해(멤버 lifecycle, 호출 순서 검증이 늘 붙는 이유가 이거지). UE는 게임 스레드 한 줄로 순차 처리라 그 스트레스가 적은 대신, 무거운 심사는 비동기 콜백으로 잘게 쪼개 넘겨야 프레임이 안 멈춰. PreLoginAsync가 딱 그 설계야.

8. 종합 — 왜 이렇게까지 단계를 쪼갰나

돌아보면 UE가 접속을 이렇게 잘게 나눈 이유가 보여.

  • 문 앞 판정(B)을 따로 둔 이유 — 로그인 로직을 돌리기도 전에, 애초에 손님 받을 상태가 아니면(클라다/레벨 전환 중) 값싸게 튕겨내려고. 값비싼 심사 앞에 값싼 게이트를 세운 거야.
  • 협상(C)과 조인(D)을 분리한 이유 — 로그인 통과와 "맵 로딩 완료"는 시점이 완전히 달라. 클라가 몇 GB짜리 맵을 까는 동안 서버가 PC를 미리 만들어두면 낭비고 위험해. 그래서 클라가 "다 깔았어"(NMT_Join)라고 보고할 때까지 PC 생성을 미뤄.
  • ReceivedJoin 플래그로 끊김을 가른 이유 — 조인 전에 튄 손님과 정식 유저를 같은 Logout 경로로 처리하면 사고 나. 만든 적 없는 걸 파괴하려 들거나, 없는 유저를 로그아웃시키니까. 그래서 "진짜 앉았던 손님이었나?"를 플래그 하나로 판정해 경로를 나눠.

각 관문이 "값싼 것 먼저, 비싼 것 나중에", "만들기 전엔 만든 척 안 하기"라는 상식을 코드로 박아둔 거야.

이 협상 과정에서 오가는 저수준 핸드셰이크 패킷의 정체가 궁금하면 → handshake 끊김 이후 커넥션 객체가 GC로 실제로 소멸하는 디테일 → netconnection-overview 막히면 → netconnection-overview 다음 → security

🎯 원리 한 줄 요약

UE 접속은 "문 앞 판정 → 신원 협상 → (클라 맵 로딩) → 조인해야 비로소 PlayerController 탄생 → 끊기면 ReceivedJoin 여부로 정식 Logout이냐 조용한 이탈이냐가 갈린다" — 값싼 게이트를 앞에, 무거운 생성을 뒤에 둔 대칭 생명주기다.
