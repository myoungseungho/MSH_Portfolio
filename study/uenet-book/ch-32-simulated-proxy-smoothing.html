남을 부드럽게: 보간 / 외삽 / 스무딩 (Simulated Proxy Smoothing)

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람. 앞 챕터에서 "내 캐릭터"가 어떻게 움직이고(예측) 서버가 어떻게 틀렸다고 고쳐주는지(보정)를 봤어. 이번엔 정반대편 — 화면에 보이는 "남"의 캐릭터를 다룬다.

0) 들어가며 — 정거장에 띄엄띄엄 도착하는 버스

친구가 버스 타고 오는 걸 지도 앱으로 본다고 해봐. 버스 GPS가 매 순간 오는 게 아니라 5초에 한 번씩 위치를 쏴. 그럼 지도 위 버스 아이콘이 어떻게 보일까.

맞춰봐. 부드럽게 미끄러질까, 아니면 뚝뚝 순간이동할까?

...순간이동이야. 5초마다 점 하나 찍히니까, 아이콘이 "여기 → (5초 정지) → 저기로 텔레포트 → (5초 정지) → 또 텔레포트" 하면서 끊겨 보여. 실제 버스는 부드럽게 굴러오는데도.

근데 잘 만든 지도 앱은 안 그래. 버스가 스르륵 미끄러지지. 비결이 뭐냐면 — 앱이 마지막 점과 새 점 사이를 지가 채워서 그려. 실제 데이터는 띄엄띄엄인데, 그 틈을 부드러운 애니메이션으로 메우는 거야.

이게 바로 네트워크 스무딩(Network Smoothing) 이야. 서버는 남의 캐릭터 위치를 초당 몇 번(10~30Hz)만 보내는데, 내 화면은 60~144Hz로 그려. 그대로 그리면 남들이 죄다 순간이동 유령처럼 보여. 그걸 부드럽게 메워주는 게 스무딩이고, 이걸 실제로 트리거하는 코드가 이번 챕터의 PostNetReceiveLocationAndRotation() → SmoothCorrection() 콜체인이야.

내 캐릭터가 왜 먼저 움직이는지(예측)가 애매하면 → client-prediction. 서버가 "틀렸어" 하고 고치는 반대편은 → server-reconciliation. CMC 전체 지도가 처음이면 → charactermovement-overview. 이 챕터는 그 위에서 "보정 안 받는 남의 캐릭터"만 판다.

즉 "누가 언제 왜 스무딩을 켜는가" (입구·트리거·정책)는 실제 소스로 다 보이고, "미끄러지는 수식 그 자체" 만 소스에 없어서 §5에서 개념으로 보충한다. 이 챕터에 실린 코드블록은 전부 이 클론에서 직접 읽어 확인한 것이고, 미포함 부분엔 🔬 배너를 달았다.

1) 큰 그림 — 캡슐과 메시를 분리해라

스무딩의 핵심 아이디어 딱 하나만 먼저 못 박자. 나머지는 다 여기서 파생돼.

충돌 캡슐(collision capsule) 은 정확한 서버 좌표로 즉시 순간이동시킨다. 눈에 보이는 메시(mesh) 만 옛 위치에 잠깐 남겨두고 서서히 따라붙게 한다.

왜 굳이 둘을 나눠? 여기서 예측 하나 해보자. 왜 캡슐까지 부드럽게 밀지 않고 순간이동시킬까?

...캡슐은 게임 규칙의 몸통이거든. 총알 히트 판정, 벽 충돌, "저 캐릭터 지금 어디 있냐"는 질문의 정답은 전부 캡슐 위치로 답해. 이걸 부드럽게 미루면 판정이 과거 위치로 틀어져. 반면 메시는 그냥 눈요기야 — 좀 늦게 도착해도 게임 규칙엔 아무 영향 없어. 그러니까:

  • 캡슐 = 정확성 담당 → 서버 좌표로 즉시 스냅(pop).
  • 메시 = 부드러움 담당 → 옛 위치와 새 위치의 차이(offset)를 저장해두고 매 틱 조금씩 0으로 줄임.

이 "차이를 저장해뒀다 녹인다"를 하는 함수가 SmoothCorrection이야. 이름 그대로 "보정(Correction)을 부드럽게(Smooth)". 캡슐이 순간이동한 그 순간, "메시가 있어야 할 곳 − 방금 캡슐이 간 곳"을 offset으로 붙잡아두고, 이후 프레임마다 이 offset을 조금씩 깎아서 메시를 캡슐에 수렴시킨다.

2) 콜체인 — 남의 위치 하나가 도착했을 때

서버가 시뮬레이션 프록시(남의 캐릭터) 위치를 하나 보내왔을 때, 그게 흐르는 길이다. 파란 박스(🔬 CMC 본문)는 이 클론에 소스 미포함 — §5에서 개념으로 다룬다.

3) Verbatim 코드 — 한 글자도 안 바꿈

[A] 스무딩 진입점 — Character.cpp:1589-1608

남의 위치가 도착하면 제일 먼저 여기 들어와. 게이트 두 개(SimulatedProxy인가 / 상대좌표 쓰나)를 통과해야 SmoothCorrection까지 간다.

void ACharacter::PostNetReceiveLocationAndRotation()
{
	if(GetLocalRole() == ROLE_SimulatedProxy)
	{
		// Don't change transform if using relative position (it should be nearly the same anyway, or base may be slightly out of sync)
		if (!GetReplicatedBasedMovement().HasRelativeLocation())
		{
			const FRepMovement& ConstRepMovement = GetReplicatedMovement();
			const FVector OldLocation = GetActorLocation();
			const FVector NewLocation = FRepMovement::RebaseOntoLocalOrigin(ConstRepMovement.Location, this);
			const FQuat OldRotation = GetActorQuat();

			CharacterMovement->bNetworkSmoothingComplete = false;
			CharacterMovement->bJustTeleported |= (OldLocation != NewLocation);
			CharacterMovement->SmoothCorrection(OldLocation, OldRotation, NewLocation, ConstRepMovement.Rotation.Quaternion());
			OnUpdateSimulatedPosition(OldLocation, OldRotation);
		}
		CharacterMovement->bNetworkUpdateReceived = true;
	}
}

읽는 포인트 딱 세 개만:

  • GetLocalRole() == ROLE_SimulatedProxy — 스무딩은 남의 캐릭터 전용. 내 폰(Autonomous)은 예측/보정으로 처리하고, 서버(Authority)는 원본이라 스무딩 안 해.
  • OldLocation을 먼저 붙잡아둔다 — 이 옛 위치가 있어야 "얼마나 튀었나(offset)"를 계산하지. SmoothCorrection에 옛/새 좌표를 둘 다 넘기는 이유가 이거야.
  • bNetworkSmoothingComplete = false — "아직 미끄러지는 중"이라고 켜두는 스위치. 이게 true가 되기 전까지 매 틱 보간이 돈다.

[B] 스무딩 모드 3종 — EngineTypes.h:1036-1049

offset을 어떤 곡선으로 0까지 녹일지 정하는 모드다.

/** Smoothing approach used by network interpolation for Characters. */
UENUM(BlueprintType)
enum class ENetworkSmoothingMode : uint8
{
	/** No smoothing, only change position as network position updates are received. */
	Disabled		UMETA(DisplayName="Disabled"),

	/** Linear interpolation from source to target. */
	Linear			UMETA(DisplayName="Linear"),

	/** Exponential. Faster as you are further from target. */
	Exponential		UMETA(DisplayName="Exponential"),

};
  • Disabled — 스무딩 끔. 위치 갱신 올 때마다 그냥 뚝뚝 스냅. 서버 데모/디버깅용.
  • Linear — 두 위치 "사이"를 시간축으로 채워. 과거를 살짝 지연 재생하는 보간(interpolation). 제일 자연스럽지만 서버 타임스탬프가 있어야 함(→ [E]).
  • Exponential — 목표에서 멀수록 빠르게 당겨오는 지수 감쇠. 타임스탬프 없이도 됨. 가벼움.

[D] 순간이동 후처리 + 끼임 체크 — Character.cpp:1566-1587

캡슐이 스냅한 뒤 부르는 뒷정리. 텔레포트로 벽/바닥에 파묻혔는지 검사한다.

void ACharacter::OnUpdateSimulatedPosition(const FVector& OldLocation, const FQuat& OldRotation)
{
	SCOPE_CYCLE_COUNTER(STAT_CharacterOnNetUpdateSimulatedPosition);

	bSimGravityDisabled = false;
	const bool bLocationChanged = (OldLocation != GetActorLocation());
	if (bClientCheckEncroachmentOnNetUpdate)
	{	
		// Only need to check for encroachment when teleported without any velocity.
		// Normal movement pops the character out of geometry anyway, no use doing it before and after (with different rules).
		// Always consider Location as changed if we were spawned this tick as in that case our replicated Location was set as part of spawning, before PreNetReceive()
		if (CharacterMovement->Velocity.IsZero() && (bLocationChanged || CreationTime == GetWorld()->TimeSeconds))
		{
			if (GetWorld()->EncroachingBlockingGeometry(this, GetActorLocation(), GetActorRotation()))
			{
				bSimGravityDisabled = true;
			}
		}
	}
	CharacterMovement->bJustTeleported |= bLocationChanged;
	CharacterMovement->bNetworkUpdateReceived = true;
}

포인트: 속도가 0일 때만 끼임 검사를 해(Velocity.IsZero()). 주석이 친절하게 설명하네 — 정상적으로 움직이는 중이면 어차피 다음 이동이 지오메트리 밖으로 밀어내니까, 굳이 검사 안 해도 돼. 순수 텔레포트(속도 0)일 때만 파묻힘을 확인하는 거지. 파묻혔으면 bSimGravityDisabled = true로 중력을 잠깐 꺼서 바닥을 뚫고 떨어지는 걸 막아.

		SetReplicatedServerLastTransformUpdateTimeStamp(0.f);
	}

왜 Linear일 때만? Linear(시간축 보간)는 "이 위치가 서버 시각 몇 초 것인가"를 알아야 두 위치 사이를 시간으로 나눠 채울 수 있어. Exponential은 그냥 "목표에서 멀수록 빨리 당겨"라서 시각이 필요 없고. 그래서 Exponential/Disabled 모드에선 이 값을 0.f로 눌러 매 업데이트마다 바뀌는 타임스탬프를 아예 안 보내 — 대역폭 절약. 스무딩 모드 하나가 네트워크 트래픽까지 바꾸는, 정책과 비용이 엮인 좋은 예시야.

[F] 리슨 서버가 원격 클라를 스무딩 — CharacterMovementComponentAsync.cpp:47-52

리슨 서버(서버 겸 플레이어)가 다른 접속자를 볼 때도 스무딩이 필요해. 남을 보는 건 남을 보는 거니까. 이 배선은 물리 비동기 경로에 있고, 현재는 대부분 TODO 주석(*/) 상태다.

			// Smooth on listen server for local view of remote clients. We may receive updates at a rate different than our own tick rate.
			if (CharacterMovementCVars::NetEnableListenServerSmoothing && !bNetworkSmoothingComplete && IsNetMode(NM_ListenServer))
			{
				SmoothClientPosition(DeltaTime);
			}
		}*/

주석 한 줄이 핵심을 말해줘 — "우리 tick 속도와 다른 속도로 업데이트를 받을 수 있다". 리슨 서버는 자기 프레임은 빠른데 원격 클라 갱신은 느리게 오니까, 그 틈을 여기서 메워. 조건에 !bNetworkSmoothingComplete가 또 나오지? [A]에서 켠 그 플래그를 여기서 확인해서, 다 미끄러졌으면 스무딩을 멈춰.

4) 헷갈리는 용어 정리

한글 라벨 + (영어 식별자)로 정리한다.

  • 시뮬레이션 프록시 (Simulated Proxy, ROLE_SimulatedProxy): 내 화면에 보이는 "남"의 캐릭터. 내가 조종 안 하고 서버가 보낸 위치만 받아 흉내 냄. 스무딩은 오직 얘한테만 적용된다.
  • 보간 (Interpolation): 이미 받은 두 위치 "사이"를 시간축으로 채우는 것. 과거를 살짝 지연 재생 → 안정적이지만 반응이 살짝 늦음. UE의 Linear 모드.
  • 외삽 (Extrapolation): 최신 위치에서 속도로 "미래"를 추정해 앞질러 그림. 패킷이 늦게 오면 엉뚱한 데로 튈 위험. (스무딩보다 예측 쪽 개념 → client-prediction)
  • 네트워크 스무딩 (NetworkSmoothing): 서버 위치가 띄엄띄엄 도착할 때 캐릭터 순간이동(pop)을 숨기는 기법. 캡슐은 정확히 스냅, 메시만 서서히 따라붙게.
  • origin rebasing (RebaseOntoLocalOrigin): 대형 월드에서 좌표 정밀도 때문에 클라마다 월드 원점이 다를 수 있음. 서버 좌표를 내 원점 기준으로 환산하는 변환. 스무딩 전에 좌표계부터 맞춘다.
  • 끼임 (Encroachment): 텔레포트로 캐릭터가 벽·바닥 지오메트리 안에 파묻힌 상태. [D]에서 검사.

5) 🔬 소스 미포함 보충 — SmoothCorrection 본체가 하는 일 (개념)

이 클론에 소스 미포함이다. 실제 대조가 필요하면 GameFramework/CharacterMovementComponent.cpp를 봐야 한다. 아래는 창작이 아니라 "왜 이게 존재하는가"의 개념 재료다.

왜 있나: 서버는 초당 10~30번만 위치를 보내는데 화면은 60~144Hz로 그려. 그대로 그리면 §0의 버스처럼 남들이 순간이동해. 그 틈을 메우려고 있다.

무엇을 하나 (3단계):

① SmoothCorrection (위치 하나 도착할 때 1회)
     캡슐 → 서버 좌표로 즉시 스냅
     "메시가 있어야 할 곳 − 방금 캡슐 간 곳" 을
       MeshTranslationOffset / MeshRotationOffset 에 저장
     bNetworkSmoothingComplete = false

② SmoothClientPosition_Interpolate (매 틱 반복)
     offset 을 목표(0)로 조금씩 감쇠
       · Linear      → 서버 타임스탬프 기반 시간 보간
       · Exponential → 목표에서 멀수록 빠르게 감쇠
     offset 이 충분히 작아지면
       bNetworkSmoothingComplete = true (종료)

③ SmoothClientPosition_UpdateVisuals (매 틱)
     감쇠된 offset 을 실제 메시 컴포넌트에 적용
     → 화면상 메시가 캡슐로 스르륵 수렴

이 클론에서 검증 가능한 사실은 여기까지다: 트리거(§2 콜체인), 3가지 모드(§3-B), Linear가 서버 타임스탬프를 필요로 한다는 정책(§3-E). offset 감쇠 수식 그 자체만 미포함이다. 표로 다시 못 박으면:

6) 우리 서버 비교 — IOCP 워커 + 싱글스레드 액터

우리 조선협객전 서버(IOCP 모델)로 이 개념을 번역해보자.

UE 스무딩우리 서버(IOCP 모델)
남의 위치 수신서버 리플리케이트 → PostNetReceive...IOCP 워커가 이동 패킷 수신
정확성(판정)캡슐 = 서버 좌표 즉시 스냅게임 로직이 보유한 권위 좌표
부드러움(표현)메시 offset 감쇠클라가 알아서 보간
갱신 빈도10~30Hz 송신, 60~144Hz 렌더서버 브로드캐스트 주기 vs 클라 프레임

여기서 우리 서버에 그대로 박아둘 원칙 두 개:

(1) 스무딩은 표현 계층, 판정은 권위 계층 — 절대 안 섞는다. UE가 캡슐(판정)과 메시(표현)를 분리한 게 이 원칙의 코드화야. 우리 서버도 "부드럽게 보이려고" 서버 권위 좌표를 흐리게 만들면 안 돼. 히트 판정·충돌·거리 계산은 정확한 권위 좌표 하나로만 하고, 부드러운 보간은 클라 표현에만 맡겨. IOCP 워커가 받은 위치는 게임 로직(싱글스레드)에서 권위값으로 확정하고, 그 확정값을 브로드캐스트하면 클라가 알아서 메시를 미끄러뜨리는 구조 — UE의 캡슐/메시 분리와 정확히 같아.

(2) 송신 빈도와 렌더 빈도가 다르다는 걸 프로토콜에 반영한다. UE가 "우리 tick과 다른 속도로 업데이트를 받는다"([F] 주석)를 대놓고 인정하듯, 우리도 남의 위치를 매 프레임 보낼 필요 없어. 초당 몇 번만 보내고 그 사이를 클라가 메우게 설계하는 게 대역폭 정답이야. 그리고 UE의 [E]처럼 — 시간 보간을 쓸 거면 서버 타임스탬프를 같이 실어야 클라가 "이건 언제 것"을 알고 시간축으로 채울 수 있어. 안 쓸 거면 그 필드 빼서 대역폭 아끼고.

🎯 원리 한 줄 요약

남의 캐릭터는 충돌 캡슐만 정확한 서버 좌표로 즉시 순간이동시키고, 눈에 보이는 메시는 옛 위치와의 차이(offset)를 저장해뒀다 매 틱 0으로 녹여서 — "정확성은 즉시, 부드러움은 서서히"로 순간이동을 숨긴다.
막히면 → client-prediction (내 캐릭터는 왜/어떻게 먼저 움직이나), server-reconciliation (서버가 틀렸다고 고치는 반대편), charactermovement-overview (CMC 전체 지도) 다음 → root-motion-replication (몽타주·루트모션이 얹히면 위치 보정은 어떻게 꼬이나), server-time-sync (Linear 보간이 목매는 그 "서버 타임스탬프" 시계는 어떻게 맞추나), lag-compensation (서버가 과거로 되감아 히트 판정하는 이야기)
