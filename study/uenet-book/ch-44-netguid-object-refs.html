NetGUID — 오브젝트 참조(포인터)를 어떻게 주고받나

언리얼 네트워크 · 44 / 47

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이런 고민을 해봤을 거야. 몬스터가 플레이어를 타겟팅했어. 서버 메모리엔 CChosunMonster::m_pTarget이 그 플레이어 객체를 가리키는 포인터로 들어 있지. 이제 클라한테 "얘 지금 저 사람 쫓아가는 중이야"를 알려줘야 해. 뭘 보낼래?

포인터 값을 그대로 보내면? 0x00007ffd8a3c1200. 이 숫자를 클라가 받아서 뭘 할 수 있을까. 아무것도 못 해. 그 주소는 서버 프로세스의 가상 메모리 안에서만 의미가 있어. 클라 프로세스에서 그 주소를 역참조하면 잘해야 크래시, 최악이면 엉뚱한 메모리를 읽어. 같은 코드를 같은 컴퓨터에서 두 번 띄워도 주소는 달라. 포인터는 프로세스 안에서만 통하는 방언이야.

그래서 우리 조선 서버는 어떻게 했지? 오브젝트 ID를 썼어. 몬스터마다 wObjectID 같은 정수 번호를 붙이고, 패킷엔 포인터 대신 그 번호를 실어 보냈지. 클라는 자기 쪽 map<ID, Object*>에서 그 번호로 객체를 찾아 연결했고. "주소 말고 번호로 부르자" — 이게 네트워크 프로그래밍에서 참조를 다루는 유일한 길이야.

언리얼도 똑같은 문제를 만났고, 그 답이 NetGUID(Network Globally Unique IDentifier, 네트워크 전역 고유 식별자)야. 서버와 클라가 같은 오브젝트를 같은 번호로 부르기로 한 공용 이름표. AActor* Target이라는 포인터 프로퍼티를 복제할 때, 봉투에 실제로 실려 나가는 건 주소가 아니라 이 번호야.

근데 우리 서버보다 문제가 한 겹 더 있어. 우리는 맵에 배치된 NPC든 런타임에 스폰된 몹이든 전부 서버가 ID를 발급했잖아. 언리얼은 맵에 이미 배치돼 있던 오브젝트와 런타임에 스폰된 오브젝트를 다르게 취급해. 그리고 더 골치 아픈 게 하나 더 있어 — "Target=몹#17"이라는 값은 도착했는데, 클라에 아직 몹#17이 없으면?" 이 상황을 UE는 자동으로 보류했다가 나중에 해결해. 이 챕터는 그 세 가지(번호표, 정적/동적, 미해결 참조)를 순서대로 판다.

0. 문 앞에서: 포인터를 그대로 보내면 벌어지는 일

가장 정직한 질문부터. 왜 AActor* Target을 그냥 memcpy 해서 8바이트 보내면 안 될까?

서버에서 Target이 가리키는 몹의 주소가 0x00007ffd8a3c1200이야.
이 8바이트를 그대로 클라에 보내면 클라는 뭘 할 수 있을까?

...정답: 아무것도. 이유를 하나씩 세어보자.

  • 프로세스마다 주소 공간이 다르다. 서버의 0x7ffd...와 클라의 0x7ffd...는 전혀 다른 물건을 가리켜. 애초에 서로 다른 컴퓨터일 수도 있고.
  • 같은 실행파일도 매번 주소가 달라진다. ASLR(주소 공간 배치 무작위화) 때문에 같은 게임을 두 번 켜도 객체 주소가 달라.
  • 클라엔 그 객체가 아예 없을 수도 있다. 서버에만 있고 클라엔 relevancy(relevancy)로 안 보낸 액터라면, 주소를 준들 가리킬 대상이 없어.

UE 소스도 이걸 딱 한 문장으로 못 박아뒀어. GuidReferences.h:29-30:

"References to Objects (including Actors, Components, etc.) are replicated as NetGUIDs, since the literal memory pointers will be different across game instances."
— Net/Core/Public/Net/Core/Misc/GuidReferences.h:29-30

"리터럴 메모리 포인터는 게임 인스턴스마다 다르다." 그래서 포인터 대신 NetGUID를 복제한다. 이 한 줄이 이 챕터 전체의 씨앗이야.

🌱 이 개념은 왜 생겼나 — NetGUID
• 원래 구조: 프로퍼티를 복제할 땐 그 값을 바이트로 그대로 떠서 보내면 되잖아. int32면 4바이트, float면 4바이트, 포인터면 8바이트. 똑같이 하면 되지.
• 그런데 문제: 포인터 값은 주소야. 주소는 그 프로세스의 가상 메모리 안에서만 뜻이 있어. 서버의 0x7ffd8a3c1200을 클라가 받아봤자 클라 메모리엔 거기 그 몹이 없어. 숫자만 옮겨진 쓰레기가 되는 거지.
• 그래서 필요한 것: 주소 말고, 서버와 클라가 둘 다 아는 공용 번호로 오브젝트를 부르기. 서버는 "몹 #17"이라 쓰고, 클라는 자기 표에서 #17을 찾아 자기 쪽 포인터로 바꾼다. → 그게 NetGUID야. 조선 서버에서 wObjectID 실어 보내던 그 발상 그대로.

이 챕터에서 볼 파일은 두 개야. Runtime/Engine/Classes/Engine/PackageMapClient.h(번호표 발급소 선언)와 Runtime/Engine/Private/PackageMapClient.cpp(구현). 여기에 미해결 참조를 다루는 Net/Core/Public/Net/Core/Misc/GuidReferences.h가 곁들여져.

지금부터 진짜 코드가 나와. 겁먹지 마 — 이름이 길고 괄호가 많아 보여도, 바로 아래 🔤 상자에서 하나씩 풀어줄게. 코드를 외우는 게 아니라 "번호가 어디서 만들어지고 어디에 저장되나"만 따라가면 돼.

1. NetGUID = 오브젝트에 붙는 공용 번호표

FNetworkGUID는 놀랄 만큼 단순해. 정수 하나야. uint64 ObjectId 딱 하나 들고 있는 게 전부.

근데 그 정수를 만드는 방식에 재밌는 트릭이 하나 숨어 있어. Core/Public/Misc/NetworkGuid.h:111-116:

static FNetworkGUID CreateFromIndex(uint64 NetIndex, bool bIsStatic) { check(NetIndex <= (MAX_uint64 >> 1)); FNetworkGUID NewGuid; NewGuid.ObjectId = NetIndex << 1 | (bIsStatic ? 1 : 0);
🔤 기호 사전 — NewGuid.ObjectId = NetIndex << 1 | (bIsStatic ? 1 : 0);
• static FNetworkGUID CreateFromIndex(...) = 번호(NetIndex)와 "정적이냐?"(bIsStatic)를 받아서 완성된 NetGUID를 만들어 돌려주는 공장 함수.
• uint64 = 0 이상 아주 큰 정수를 담는 칸. NetGUID의 알맹이가 이거 하나야.
• check(...) = "이 조건이 아니면 여기서 바로 터뜨려라"는 안전장치. 번호가 너무 커서 넘치는 걸 막아.
• << 1 = 비트를 왼쪽으로 한 칸 밀기. 숫자로는 2배가 되고, 맨 오른쪽 칸이 비게 돼. 이 빈칸이 핵심이야.
• | = 비트 OR. 방금 비운 맨 오른쪽 칸에 값을 끼워 넣는다는 뜻.
• (bIsStatic ? 1 : 0) = 삼항 연산자. "정적이면 1, 아니면 0"을 골라 그 빈칸에 넣어.
🔁 이제 다시 보자. NetGUID는 일련번호를 한 칸 왼쪽으로 밀고, 맨 오른쪽 비트에 "정적/동적" 표시를 끼워 넣은 정수야. 그래서 홀수면 정적, 짝수면 동적. 번호 하나에 "몇 번이냐"와 "어느 종류냐"가 같이 실려 있어.

확인 사살. 판정 함수가 진짜 그렇게 생겼어. NetworkGuid.h:64-77:

bool IsDynamic() const { return IsValid() && !IsStatic(); } bool IsStatic() const { return ObjectId & 1; } bool IsValid() const { return ObjectId > 0; }
🔤 기호 사전 — return ObjectId & 1;
• bool ... const = 참/거짓을 돌려주는 함수이고, 뒤의 const는 "이 함수는 물건 상태를 안 바꾼다"는 약속.
• ObjectId & 1 = 비트 AND. 1은 맨 오른쪽 비트만 켜진 값이라, 이건 곧 "맨 오른쪽 비트가 켜져 있나?"를 묻는 말이야. 켜져 있으면 홀수 → 정적.
• !IsStatic() = !는 뒤집기. "정적이 아니다" = 동적.
• && = AND. 양쪽이 다 참일 때만 참. "유효하면서 정적이 아닐 때"만 동적으로 친다.
• ObjectId > 0 = 0이면 "아직 번호 없음(무효)". 그래서 0번은 아무한테도 안 준다. nullptr을 보내면 이 0이 실려 나가.
🔁 이제 다시 보자. IsStatic()은 맨 오른쪽 비트 하나만 본다. 즉 NetGUID 숫자만 보고도 "얘가 맵에 원래 있던 놈인지, 런타임에 스폰된 놈인지"를 즉시 알 수 있어. 그리고 0은 "참조 없음(null)"이라는 뜻으로 예약돼 있어.

정리하면 NetGUID 한 개는 이렇게 생겼어:

FNetworkGUID.ObjectId (uint64) [ 일련번호 (63비트) ][정적?1비트] ↑ 1 = 정적 (맵에 배치) 0 = 동적 (런타임 스폰) ObjectId == 0 -> "참조 없음(null)" ... IsValid() == false

그리고 이 번호가 실제로 봉투에 어떻게 쓰이냐면 — SerializeIntPacked64로 압축돼서 나가. 번호가 작으면 바이트도 적게 먹어. 8바이트 포인터를 그대로 보내는 것보다 오히려 싸다. 주소를 못 보내서 번호를 쓰는 건데, 결과적으로 대역폭까지 아끼는 셈.

2. FNetGUIDCache — 번호표 발급소이자 전화번호부

번호를 붙이기로 했으면, 누군가는 번호를 발급하고 번호↔오브젝트 대응표를 들고 있어야 해. 그게 FNetGUIDCache야. NetDriver마다 하나씩 붙어 있고, 서버에도 클라에도 있어.

핵심 멤버 딱 네 줄만 보면 돼. PackageMapClient.h:279-286:

TMap< FNetworkGUID, FNetGuidCacheObject > ObjectLookup; TMap< TWeakObjectPtr< UObject >, FNetworkGUID > NetGUIDLookup; TSet< FNetworkGUID > ImportedNetGuids; TMap< FNetworkGUID, TSet< FNetworkGUID > > PendingOuterNetGuids;
🔤 기호 사전 — TMap< FNetworkGUID, FNetGuidCacheObject > ObjectLookup;
• TMap<A, B> = UE의 사전(딕셔너리). A로 찾으면 B가 나온다는 뜻. C++ 표준의 std::map이랑 같은 역할이야.
• < > = 템플릿 괄호. "무엇으로 찾고 무엇을 담는 사전인지"를 채워 넣는 자리.
• ObjectLookup = 번호 → 오브젝트 방향 사전. "17번이 누구야?"에 답한다.
• NetGUIDLookup = 오브젝트 → 번호 방향 사전. "이 몹 번호가 뭐야?"에 답한다. 방향이 반대인 표를 하나 더 두는 거야.
• TWeakObjectPtr< UObject > = 약한 포인터. 이 표가 오브젝트를 붙잡고 있어서 삭제를 못 하게 되는 걸 막아. 오브젝트가 죽으면 이 포인터는 자동으로 "없음"이 돼.
• TSet< FNetworkGUID > = 중복 없는 번호 묶음. ImportedNetGuids는 "이번에 새로 받아서 아직 처리 중인 번호들".
• TMap< FNetworkGUID, TSet<FNetworkGUID> > = 번호 하나가 여러 번호를 달고 있는 사전. PendingOuterNetGuids는 "이 바깥 오브젝트가 아직 안 와서 대기 중인 안쪽 번호들"이야.
🔁 이제 다시 보자. 캐시의 뼈대는 양방향 전화번호부 두 권이야. ObjectLookup(번호→오브젝트)과 NetGUIDLookup(오브젝트→번호). 보낼 땐 오브젝트로 번호를 찾고, 받을 땐 번호로 오브젝트를 찾으니까 두 방향이 다 필요해. 뒤의 ImportedNetGuids·PendingOuterNetGuids는 5장에서 볼 미해결 참조 대기실이야.

중요한 건 이 표가 서버에도 있고 클라에도 있다는 거야. 같은 번호에 대해 양쪽이 각자의 로컬 포인터를 들고 있는 거지. 서버의 17번 몹 포인터와 클라의 17번 몹 포인터는 주소가 완전히 다르지만 번호는 같아. 이게 전부야. 이 한 겹의 간접층이 포인터 문제를 통째로 녹인다.

번호는 누가 발급하나 — 서버만.

발급 권한은 서버 독점이야. 클라가 멋대로 번호를 만들면 서버 번호랑 충돌하니까. PackageMapClient.cpp:3240-3254:

FNetworkGUID FNetGUIDCache::AssignNewNetGUID_Server( UObject* Object ) { check( IsNetGUIDAuthority() ); // Generate new NetGUID and assign it const int32 IsStatic = IsDynamicObject( Object ) ? 0 : 1; const FNetworkGUID NewNetGuid = FNetworkGUID::CreateFromIndex(++NetworkGuidIndex[IsStatic], IsStatic != 0); RegisterNetGUID_Server( NewNetGuid, Object ); UE_NET_TRACE_ASSIGNED_GUID(Driver->GetNetTraceId(), NewNetGuid, Object->GetClass()->GetFName(), 0); return NewNetGuid; }
🔤 기호 사전 — const FNetworkGUID NewNetGuid = FNetworkGUID::CreateFromIndex(++NetworkGuidIndex[IsStatic], IsStatic != 0);
• FNetworkGUID FNetGUIDCache::AssignNewNetGUID_Server(...) = FNetGUIDCache 소속 함수. NetGUID를 새로 하나 만들어 돌려준다. 함수 이름 뒤의 _Server가 "서버 전용"이라는 대놓고 알림이야.
• check( IsNetGUIDAuthority() ) = "지금 내가 번호 발급 권한자(=서버)가 맞나?"를 강제로 확인. 아니면 여기서 터진다. 클라는 이 함수에 못 들어와.
• IsDynamicObject(Object) ? 0 : 1 = 동적이면 0, 아니면(정적이면) 1. 이 0/1이 곧 번호 통(bucket) 선택이자 맨 오른쪽 비트값이야.
• NetworkGuidIndex[IsStatic] = 칸이 2개짜리 카운터 배열. [0]은 동적용, [1]은 정적용. 통을 아예 나눠 쓴다.
• ++ = 앞에 붙었으니 "1 먼저 올리고 그 값을 쓴다". 그래서 번호는 1부터 시작하고 0은 영영 안 나와(0 = null 예약).
• RegisterNetGUID_Server(...) = 방금 만든 번호와 오브젝트를 양방향 표에 등록하는 호출. 이걸 해야 다음부터 조회가 된다.
• UE_NET_TRACE_ASSIGNED_GUID(...) = 네트워크 추적 도구에 "이 번호 발급했다"고 기록만 남기는 매크로. 로직엔 영향 없어. (→ net-tooling)
🔁 이제 다시 보자. 발급은 네 단계야. (1) 서버 맞는지 확인 → (2) 이 오브젝트가 동적인지 정적인지 판정 → (3) 해당 통의 카운터를 1 올려 번호를 만들고 마지막 비트에 정적 여부를 새김 → (4) 양방향 표에 등록. 카운터를 정적/동적 두 개로 나눠 쓰기 때문에 두 세계의 번호가 서로 침범하지 않아.
🌱 이 개념은 왜 생겼나 — 정적/동적 분리
• 원래 구조: 오브젝트 참조는 다 똑같잖아. 서버가 번호를 발급하고, 클라에 "이 번호는 이 오브젝트야"라고 알려주면 끝. 하나의 규칙으로 다 처리하면 되지.
• 그런데 문제: 근데 맵에 원래부터 배치돼 있던 오브젝트(문짝, 볼륨, 레벨 지오메트리, 배치 NPC…)는 서버도 클라도 같은 레벨 파일을 이미 로드해서 똑같이 갖고 있어. 이런 놈들까지 "이 번호는 누구다"를 매번 통신으로 알려주면, 이미 양쪽이 아는 걸 굳이 다시 말하는 낭비야. 게다가 레벨 로드 순서·타이밍이 조금만 어긋나도 매핑이 꼬여.
• 그래서 필요한 것: 이름(경로)으로 부를 수 있는 놈과 그럴 수 없는 놈을 나누기. 경로가 안정적인 놈(정적)은 "이름표"를 같이 실어 보내면 클라가 자기 레벨에서 그 이름으로 찾아내 붙일 수 있고, 런타임에 태어난 놈(동적)은 이름 자체가 없으니 서버가 번호를 찍어주고 스폰 정보를 통째로 보내야 해. → 그게 정적/동적 구분이고, NetGUID 마지막 비트에 그 구분이 박혀 있는 이유야.

3. ⭐ 정적 vs 동적 — 이 챕터의 갈림길

여기가 이 챕터에서 제일 중요한 부분이야. 맞춰봐.

레벨에 미리 배치해둔 대문(Door) 액터가 있어. 서버도 클라도 같은 Level_Village.umap을 로드했지.
이 대문의 참조를 클라에 보낼 때, 서버가 "번호 42번 = 이 대문"이라고 알려줘야만 할까?

...아니야. 놀랍게도 안 알려줘도 돼. 왜냐면 클라도 같은 맵을 로드했으니 그 대문은 이미 클라 메모리에 있거든. 서버가 할 일은 번호를 통보하는 게 아니라, "/Game/Maps/Level_Village.Level_Village:PersistentLevel.Door_3"이라는 경로 이름을 한 번만 알려주는 거야. 클라는 그 경로로 자기 쪽 대문을 찾아내서 번호와 짝지어. 그 뒤론 번호만 오가면 돼.

반대로 런타임에 스폰된 몹은? 클라 메모리에 없어. 경로 이름도 없어(런타임 생성물이라 안정적인 이름이 없음). 그래서 서버가 번호를 찍어주고 "이 클래스로 여기에 스폰해"라고 스폰 정보를 통째로 보내줘야 해. 그게 actorchannel-replicate에서 본 SerializeNewActor야.

그럼 엔진은 이 둘을 어떻게 구분할까? 딱 한 줄이야. PackageMapClient.cpp:3143-3154:

/** * Dynamic objects are actors or sub-objects that were spawned in the world at run time, and therefor cannot be * referenced with a path name to the client. */ bool FNetGUIDCache::IsDynamicObject( const UObject* Object ) { check( Object != NULL ); check( Object->IsSupportedForNetworking() ); // Any non net addressable object is dynamic return !Object->IsFullNameStableForNetworking(); }
🔤 기호 사전 — return !Object->IsFullNameStableForNetworking();
• /** ... */ = 사람이 읽는 설명 주석. 여기선 아예 정의를 적어놨어 — "동적 오브젝트란 런타임에 월드에 스폰된 액터/서브오브젝트이고, 따라서 경로 이름으로 클라에 지칭할 수 없다."
• const UObject* Object = 검사할 오브젝트를 가리키는 포인터. const라서 이 함수는 그 오브젝트를 건드리지 않아.
• -> = 포인터가 가리키는 대상에게 기능을 시키는 화살표.
• IsSupportedForNetworking() = "얘를 네트워크로 참조할 수 있나?"를 묻는 검사. 애초에 참조 불가능한 놈이 들어오면 여기서 터져.
• IsFullNameStableForNetworking() = "얘의 전체 경로 이름이 양쪽에서 똑같이 안정적인가?"를 묻는 함수. 맵에서 로드된 놈이면 참.
• ! = 뒤집기. 즉 "이름이 안정적이지 않다 = 동적이다". 정의가 아니라 부정으로 되어 있는 게 포인트야.
🔁 이제 다시 보자. 엔진은 "동적"을 직접 정의하지 않아. "경로 이름으로 부를 수 있느냐"를 먼저 묻고, 못 부르면 그게 동적이야. 기준이 "언제 만들어졌나"가 아니라 "이름으로 지칭 가능한가"라는 게 핵심 — 결국 같은 말이지만, 판정은 이름 쪽으로 한다.

그럼 "이름이 안정적"이란 뭐냐. 한 겹만 더 들어가자. CoreUObject/Private/UObject/Obj.cpp:5761-5765:

/** IsNameStableForNetworking means an object can be referred to its path name (relative to outer) over the network */ bool UObject::IsNameStableForNetworking() const { return HasAnyFlags(RF_WasLoaded | RF_DefaultSubObject | RF_ClassDefaultObject) || IsNative() || IsDefaultSubobject(); }
🔤 기호 사전 — return HasAnyFlags(RF_WasLoaded | RF_DefaultSubObject | RF_ClassDefaultObject) || IsNative() || IsDefaultSubobject();
• HasAnyFlags(...) = 이 오브젝트에 붙은 표시(플래그) 중 하나라도 켜져 있나 묻는 함수.
• RF_ = "Object Flag"의 접두사. UObject에 붙는 표시들이야.
• RF_WasLoaded = 디스크의 패키지(맵/에셋)에서 로드된 놈이라는 표시. ★ 이게 정적 판정의 주역이야. 레벨에 배치해둔 액터가 여기 해당해.
• RF_ClassDefaultObject = 클래스마다 하나씩 있는 기본 원본(CDO). 코드에 박혀 있으니 양쪽이 똑같이 갖고 있어.
• | = 비트 OR. 여기선 여러 플래그를 한 묶음으로 합쳐서 "이 중 아무거나" 검사하는 데 써.
• || = 논리 OR. 왼쪽부터 보다가 하나라도 참이면 전체가 참.
• IsNative() = C++ 코드에 박혀 있는 놈이냐. 당연히 양쪽에 다 있지.
• IsDefaultSubobject() = 생성자에서 늘 같은 이름으로 만들어지는 기본 컴포넌트냐. 예: 캐릭터의 CharacterMovement. 이름이 항상 같으니 안정적이야.
🔁 이제 다시 보자. "이름이 안정적"의 정체는 결국 "서버와 클라가 그걸 각자 똑같이 만들어냈나"야. 맵에서 로드했거나(RF_WasLoaded), C++/블루프린트 코드에 박혀 있거나(IsNative, CDO), 생성자가 늘 같은 이름으로 만드는 기본 컴포넌트거나. 이 중 하나면 양쪽이 이미 같은 놈을 갖고 있으니 경로 이름으로 부르면 된다. 하나도 아니면 → 서버만 아는 놈 → 동적.

표로 정리하면 이렇게 갈려:

정적 (Static)동적 (Dynamic)
예시레벨에 배치한 문짝·볼륨·배치 NPC, CDO, 기본 컴포넌트SpawnActor로 태어난 몹·투사체·런타임 생성 아이템

NetGUID 만드는 법번호 + 경로 이름을 한 번 export → 클라가 이름으로 찾아 매핑서버가 번호 발급 → 스폰 정보를 통째로 보내 클라가 생성

4. 포인터 하나를 봉투에 쓰는 실제 코드

이제 AActor* Target 프로퍼티를 복제할 때 실제로 뭐가 실리는지 보자. 모든 오브젝트 참조 직렬화는 결국 이 함수를 통과해. PackageMapClient.cpp:308의 UPackageMapClient::SerializeObject, 그중 보내는 쪽(saving) 알맹이. PackageMapClient.cpp:334-343:

FNetworkGUID NetGUID = GuidCache->GetOrAssignNetGUID( Object ); // Write out NetGUID to caller if necessary if (OutNetGUID) { *OutNetGUID = NetGUID; } // Write object NetGUID to the given FArchive InternalWriteObject( Ar, NetGUID, Object, TEXT( "" ), NULL );
🔤 기호 사전 — FNetworkGUID NetGUID = GuidCache->GetOrAssignNetGUID( Object );
• GuidCache = 아까 본 그 발급소/전화번호부(FNetGUIDCache) 포인터.
• GetOrAssignNetGUID(Object) = 이름이 곧 설명이야. "있으면 가져오고, 없으면 새로 발급". 이미 번호가 있는 몹이면 표에서 꺼내고, 처음 보는 몹이면 그 자리에서 번호를 찍는다.
• FArchive& Ar = 읽기·쓰기 양쪽에 다 쓰는 직렬화 통로. 보낼 때는 봉투에 쓰는 펜, 받을 때는 읽는 눈이 돼. 같은 함수가 양방향에 쓰이는 이유가 이거야.
• if (OutNetGUID) = 호출한 쪽이 "번호도 알려줘"라고 빈 상자를 건넸으면(널이 아니면) 거기에 채워준다는 뜻.
• *OutNetGUID = NetGUID = *는 그 포인터가 가리키는 진짜 상자를 열어 값을 넣는다는 표시.
• InternalWriteObject( Ar, NetGUID, Object, ... ) = 번호를 봉투에 실제로 쓰는 함수. 정적 오브젝트라 경로를 같이 보내야 하면 여기서 경로 이름도 붙는다.
• TEXT("") / NULL = "경로 이름과 아우터는 안 넘긴다"는 뜻. 오브젝트가 있으니 필요하면 함수가 알아서 꺼내 쓴다.
🔁 이제 다시 보자. 포인터 하나를 복제하는 건 두 동작이야. (1) GetOrAssignNetGUID — 포인터를 번호로 바꾼다(없으면 새로 발급). (2) InternalWriteObject — 그 번호를 봉투에 쓴다. 주소는 봉투에 절대 안 들어간다. 나가는 건 번호(+ 처음이면 경로나 스폰정보)뿐이야.

받는 쪽은 정확히 반대야. 같은 SerializeObject의 loading 갈래에서 InternalLoadObject를 불러 번호를 읽고 → 표에서 찾아 → 그 자리에 클라의 로컬 포인터를 꽂아준다.

[서버] AActor* Target = 0x00007ffd8a3c1200 (몹 객체 주소) | | GetOrAssignNetGUID(Target) PackageMapClient.cpp:334 v FNetworkGUID{ ObjectId = 34 } (동적이라 짝수) | | InternalWriteObject → Ar << NetGUID (SerializeIntPacked64로 압축) v ~~~~~~~~ 네트워크 ~~~~~~~~ [ 34 ] | v [클라] InternalLoadObject: 34번을 ObjectLookup에서 조회 | +-- 있음 -> Target = 0x000001c2f04b8800 (클라 쪽 몹 주소) | +-- 없음 -> ★ Unresolved! 보류함에 넣는다 (5장)

양쪽 주소는 완전히 다르지만 번호가 같으니 같은 몹을 가리킨다. 이게 NetGUID의 전부야.

🌱 이 개념은 왜 생겼나 — 미해결 참조(Unresolved / Unmapped)
• 원래 구조: 번호를 받으면 표에서 찾아 포인터를 꽂으면 되잖아. 34번? 표에서 꺼내서 대입. 끝.
• 그런데 문제: 근데 34번이 표에 없을 수가 있어. 몹 A가 "나 34번 쫓는 중"이라고 먼저 도착했는데, 정작 34번 몹의 스폰 봉투는 아직 안 왔거나 다른 패킷에 실려 뒤에 올 수도 있거든(패킷 순서, relevancy 차이, 채널 열리는 타이밍…). 여기서 못 찾았다고 nullptr을 넣어버리면? 34번이 나중에 도착해도 아무도 그 사실을 모르고, Target은 영영 nullptr인 채로 남아. 조용히 틀린 상태가 되는 거지.
• 그래서 필요한 것: 못 찾은 참조를 버리지 말고 보류함에 적어두고, 새 오브젝트가 등록될 때마다 보류함을 다시 훑어 "이제 찾을 수 있나?" 재시도하는 장치. → 그게 FGuidReferences(미해결 참조 보류함)이야. 조선 서버로 치면 "참조 ID가 아직 맵에 없으면 나중에 다시 붙이는 pending 큐"인데, UE는 이걸 엔진이 자동으로 해준다.

5. ⭐ Unresolved 참조 — "몹#17이 아직 없는데요"

이 챕터의 두 번째 핵심. 아까 그 상황을 다시 보자.

클라가 봉투를 열었더니 Target = NetGUID 34가 들어 있어.
근데 클라의 ObjectLookup에 34번이 없어. 아직 그 몹이 안 왔거든.
여기서 Target = nullptr을 넣고 넘어가면 뭐가 망가질까?

...망가지는 건 영구적으로 틀린 상태야. 34번 몹이 3프레임 뒤에 도착해도, Target에 그 포인터를 다시 꽂아줄 사람이 아무도 없어. 프로퍼티 복제는 바뀐 것만 보내니까(changelist), 서버 입장에선 Target은 34번 그대로라 다시 안 보내. 클라의 Target은 영영 nullptr. AI가 아무도 안 쫓는 유령이 되는 거지.

그래서 UE는 못 찾은 참조를 보류한다. 받은 비트를 버리지 않고 통째로 복사해서 대기함에 넣어둬. RepLayout.cpp:3415-3446(발췌):

// Loop over all de-serialized network guids and track them so we can manage their pointers as their replicated reference goes in/out of relevancy const TSet<FNetworkGUID>& TrackedUnmappedGuids = Bunch.PackageMap->GetTrackedUnmappedGuids(); const TSet<FNetworkGUID>& TrackedDynamicMappedGuids = Bunch.PackageMap->GetTrackedDynamicMappedGuids(); FGuidReferences* GuidReferences = GuidReferencesMap->Find(AbsOffset); if (TrackedUnmappedGuids.Num() > 0 || TrackedDynamicMappedGuids.Num()> 0) { ... if (GuidReferences == nullptr || bOutGuidsChanged) { // First time tracking these guids (or guids changed), so add (or replace) new entry GuidReferencesMap->Emplace(AbsOffset, FGuidReferences(Bunch, Mark, TrackedUnmappedGuids, TrackedDynamicMappedGuids, Cmd.ParentIndex, CmdIndex, Bunch.PackageMap)); bOutGuidsChanged = true; } }
🔤 기호 사전 — GuidReferencesMap->Emplace(AbsOffset, FGuidReferences(Bunch, Mark, ...));
• const TSet<FNetworkGUID>& TrackedUnmappedGuids = "방금 읽었는데 못 찾은 번호들" 묶음. &라서 복사가 아니라 원본을 빌려 봐. PackageMap이 읽는 동안 몰래 모아둔 거야.
• GetTrackedDynamicMappedGuids() = 반대로 "찾긴 찾았는데 동적이라 언젠가 사라질 수 있는 번호들". 사라질 때 되돌려놔야 하니 얘도 추적해.
• AbsOffset = 이 참조가 오브젝트 메모리의 몇 번째 바이트에 있는 프로퍼티인지를 나타내는 위치값. "어디에 다시 꽂아야 하나"의 주소표야.
• GuidReferencesMap->Find(AbsOffset) = 그 위치에 대해 이미 보류 중인 기록이 있나 찾아보는 호출.
• .Num() > 0 = 묶음에 원소가 하나라도 있나. 즉 "추적할 게 생겼나".
• || = OR. 못 찾은 게 있거나, 동적으로 찾은 게 있거나 — 둘 중 하나면 기록한다.
• Emplace(키, 값) = 사전에 새로 넣거나 덮어쓰는 호출.
• FGuidReferences(Bunch, Mark, ...) = ★ 보류 기록 한 장. Bunch와 Mark를 같이 넘기는 게 핵심 — 읽었던 비트 구간을 그대로 복사해서 안에 보관한다. 나중에 그 비트를 다시 읽어서 프로퍼티에 적용하려고.
🔁 이제 다시 보자. 참조를 하나 읽을 때마다 엔진은 "못 찾은 번호가 있었나?"를 확인해. 있으면 FGuidReferences라는 보류 기록을 만들어 (a) 못 찾은 번호들 (b) 이 프로퍼티의 메모리 위치 (c) 방금 받은 원본 비트 복사본을 통째로 저장해. 데이터를 버리는 게 아니라 냉동해두는 거야. 나중에 번호가 풀리면 그 비트를 해동해서 다시 적용한다.

그리고 이 보류 기록을 들고 있는 FObjectReplicator는 NetDriver의 미해결 명단에 등록돼. 매 틱, NetDriver가 그 명단을 훑으며 재시도해. NetDriver.cpp:1300-1313:

// Update properties that are unmapped, try to hook up the object pointers if they exist now for (auto It = UnmappedReplicators.CreateIterator(); It; ++It) { FObjectReplicator* Replicator = *It; bool bHasMoreUnmapped = false; Replicator->UpdateUnmappedObjects(bHasMoreUnmapped); if (!bHasMoreUnmapped) { // If there are no more unmapped objects, we can also stop checking It.RemoveCurrent(); } }
🔤 기호 사전 — Replicator->UpdateUnmappedObjects(bHasMoreUnmapped);
• UnmappedReplicators = "아직 못 붙인 참조가 남아 있는 복제 담당자들" 명단. NetDriver가 들고 있어.
• CreateIterator() = 명단을 처음부터 하나씩 훑는 도구를 만든다. ++It로 다음 칸으로 넘어가.
• FObjectReplicator* Replicator = *It = 지금 가리키는 칸의 담당자를 꺼낸다. 여기서 *는 "이터레이터가 가리키는 것을 꺼내라"는 뜻.
• bool bHasMoreUnmapped = false = "아직 못 푼 게 남았나?"를 담을 빈 상자. 아래 함수가 여기에 답을 채워준다.
• UpdateUnmappedObjects(bHasMoreUnmapped) = ★ 보류함을 다시 시도하는 함수. 보관해둔 번호를 표에서 다시 찾아보고, 이제 있으면 냉동해둔 비트를 해동해 프로퍼티에 적용해. 여전히 못 찾으면 bHasMoreUnmapped = true로 알려줘.
• if (!bHasMoreUnmapped) = 남은 게 없으면(!는 뒤집기).
• It.RemoveCurrent() = 이 담당자를 명단에서 지운다. 다 풀렸으니 더 볼 필요 없어. 명단은 이렇게 스스로 줄어들어.
🔁 이제 다시 보자. 매 틱 NetDriver는 미해결 명단을 한 바퀴 돌면서 "이제 찾을 수 있어?"를 다시 물어. 찾았으면 냉동해둔 비트를 해동해 포인터를 꽂고, 그 담당자가 더 이상 미해결이 없으면 명단에서 스스로 빠진다. 못 찾으면 남아서 다음 틱에 또 시도해. 폴링이지만 명단이 미해결이 있는 놈들만이라 아주 작아.

그리고 반대 방향도 있어. 이미 잘 붙어 있던 오브젝트가 사라지면(relevancy 밖으로 나가거나, 액터 채널이 닫히거나, 파괴되거나) 그 참조는 다시 unmapped로 되돌려지고 프로퍼티는 nullptr이 돼. 그러면서 미해결 명단에 다시 등록돼. 나중에 그 오브젝트가 돌아오면 같은 NetGUID로 다시 붙어. 소스 주석도 그걸 명시해:

"The process of Mapping and Unmapping can happen numerous times for the same object (e.g., if an Actor goes in and out of relevancy repeatedly)."
— GuidReferences.h:40-41

즉 참조 해결은 1회성 이벤트가 아니라 왕복 상태 기계야. mapped ⇄ unmapped를 몇 번이고 오간다.

6. 그래서 복제 "순서"가 중요해진다

이제 앞 챕터들과 이어붙일 시간이야. 왜 subobject-replication에서 "주인 먼저, 부품 나중"이라는 순서를 그렇게 강조했을까?

인벤토리 컴포넌트가 AWeapon* EquippedWeapon을 들고 있어.
그 무기는 이 액터의 서브오브젝트고.
만약 인벤토리 프로퍼티가 무기 서브오브젝트보다 먼저 클라에 적용되면?

...EquippedWeapon = NetGUID 51이 도착했는데 51번(무기)은 아직 클라에 없어. → Unresolved. 물론 5장에서 봤듯 엔진이 보류했다가 나중에 붙여주긴 해. 깨지진 않아. 근데 그 사이 몇 틱 동안 클라의 EquippedWeapon은 nullptr이고, 그 사이에 OnRep이 돌면(repnotify) "무기 없음"으로 처리하는 로직이 한 번 실행될 수 있어. 그리고 무기가 붙으면 OnRep이 또 돌아. 깜빡임(flicker) — 이게 UE 멀티에서 "왜 처음 한 프레임만 무기가 안 보이지?" 하는 버그의 정체야.

그래서 UE는 순서를 최대한 지켜줘:

  • 액터 채널 안에서: 스폰 정보 → 액터 본체 프로퍼티 → 서브오브젝트 순으로 한 봉투에 담긴다(→ actorchannel-replicate). 같은 봉투 안이면 앞에서부터 순서대로 적용되니 "주인 먼저"가 보장돼.
  • 서브오브젝트 등록 순서: 주인 오브젝트를 먼저 등록해야 그 안의 참조가 풀린다(→ subobject-replication).
  • 액터 사이 참조는 순서 보장이 없다: 몹 A가 몹 B를 가리키는데 A와 B는 서로 다른 액터 채널이야. 어느 봉투가 먼저 도착할지 아무도 보장 못 해. 그래서 여기선 Unresolved가 정상 상황이고, 보류 장치가 반드시 필요한 거야.
⚠️ 실무 함정: 오브젝트 참조 프로퍼티의 OnRep 안에서 그 포인터가 nullptr이 아니라고 가정하면 안 돼. Unresolved 상태에서 OnRep이 먼저 한 번 돌 수 있거든. 항상 if (Target) 널 체크를 하고, "아직 안 왔으면 아무것도 안 한다"로 짜야 해. 참조가 나중에 풀리면 OnRep이 다시 불려. 조선 서버에서 "ID로 객체 찾았는데 nullptr이면 무시하고 다음 패킷 기다리기" 하던 그 방어 코드랑 똑같은 습관이야.

참고로 채널이 언제 열리고 닫히는지 — 즉 액터가 클라에 언제 생기고 언제 사라지는지 — 는 다음 챕터에서 이어서 본다. → actor-spawn-destroy

우리 서버랑 비교

조선협객전 서버 감각으로 번역해볼게. 결론부터 말하면 발상은 완전히 같고, 자동화 수준이 다르다.

우리도 포인터를 못 보내니까 wObjectID 같은 정수를 패킷에 실었지. 클라는 map<ID, CObject*>에서 찾아 붙였고. UE의 NetGUID는 정확히 그거야. 다만 우리가 손으로 하던 걸 엔진이 프로퍼티 단위로 자동화했고, 우리가 안 하던 두 가지를 더 한다 — 정적/동적 분리와 미해결 참조 자동 보류.

가장 큰 사고방식 차이는 마지막 두 줄이야. 우리 서버에서 "참조한 몹이 아직 클라에 없다"는 버그 리포트였어. 개발자가 순서를 신경 써서 패킷을 짰거나, 아니면 조용히 유실됐지. UE는 그걸 정상 상황으로 인정하고 자동으로 복구해. 대신 그 대가로 "참조 프로퍼티는 잠깐 nullptr일 수 있다"는 규칙을 게임 코드가 받아들여야 해. 공짜는 없어 — 엔진이 복잡도를 가져간 만큼, 게임 코드는 널 체크와 재진입 가능한 OnRep이라는 규율을 내야 하는 거야.

초보가 헷갈리는 용어 (짧게)

  • NetGUID (FNetworkGUID): 서버-클라가 같은 오브젝트를 같은 번호로 부르는 uint64 번호표. 마지막 비트가 정적/동적 표시. 0은 "참조 없음(null)".
  • FNetGUIDCache: 번호 발급소 + 양방향 전화번호부. NetDriver마다 하나, 서버·클라 양쪽에 존재.
  • PackageMap (UPackageMapClient): 참조를 실제로 봉투에 쓰고 읽는 창구. 캐시를 들고 다니며 SerializeObject를 수행.
  • 정적(Static) 오브젝트: 맵/패키지에서 로드돼 경로 이름이 안정적인 오브젝트. 클라도 이미 갖고 있음. NetGUID가 홀수.
  • 동적(Dynamic) 오브젝트: 런타임에 스폰돼 경로 이름이 없는 오브젝트. 서버가 스폰 정보를 보내야 클라에 생김. NetGUID가 짝수.
  • Unresolved / Unmapped: 번호는 받았는데 그 번호의 오브젝트가 아직 로컬에 없는 상태. 프로퍼티는 nullptr이고 보류함에 등록됨.
  • FGuidReferences: 미해결 참조 보류 기록 한 장. 못 찾은 번호 + 프로퍼티 위치 + 받은 비트 복사본을 통째로 보관.
  • Export: 서버가 클라에 "이 번호는 이 경로/이 클래스다"를 알려주는 행위. 정적 오브젝트는 경로 이름을 export한다.

Q1. AActor* Target 같은 포인터 프로퍼티를 복제할 때, 왜 주소값을 그대로 못 보내나요?

답 보기
포인터는 그 프로세스의 가상 메모리 안에서만 통하는 방언이기 때문이야. 서버의 0x00007ffd8a3c1200을 클라가 받아봤자, 클라 메모리의 그 주소엔 그 몹이 없어. 잘해야 크래시고 최악이면 엉뚱한 메모리를 읽지. 애초에 다른 컴퓨터일 수도 있고, 같은 게임을 두 번 켜도 ASLR 때문에 주소가 달라져. UE 소스도 GuidReferences.h 주석에서 "the literal memory pointers will be different across game instances"라고 못 박아뒀어. 그래서 주소 대신 서버와 클라가 둘 다 아는 공용 번호로 오브젝트를 부른다 — 그게 NetGUID야.

↳ NetGUID는 정확히 어떻게 생긴 물건인가요?

답 보기
uint64 정수 하나야. 근데 만드는 방식에 트릭이 있어 — 일련번호를 왼쪽으로 한 칸 밀고(<< 1), 비워진 맨 오른쪽 비트에 "정적이냐?"를 끼워 넣어. 그래서 IsStatic()이 그냥 ObjectId & 1이야 — 홀수면 정적, 짝수면 동적. 번호 하나만 봐도 "몇 번이냐"와 "맵에 원래 있던 놈이냐, 런타임에 스폰된 놈이냐"를 동시에 알 수 있는 거지. 그리고 0은 아무한테도 안 줘 — 0은 "참조 없음(null)"으로 예약돼 있거든. 봉투엔 SerializeIntPacked64로 압축돼 실려서, 8바이트 포인터를 그냥 보내는 것보다 오히려 싸.

Q2. NetGUID는 누가 발급하나요? 클라가 만들면 안 되나요?

답 보기
서버 독점이야. 발급 함수 이름부터 AssignNewNetGUID_Server고, 첫 줄이 check(IsNetGUIDAuthority()) — 서버가 아니면 거기서 터져. 클라가 멋대로 번호를 만들면 서버가 발급한 번호와 충돌해서, 같은 번호가 서로 다른 오브젝트를 가리키는 최악의 상황이 나거든. 발급 로직은 네 단계야. 서버 맞는지 확인 → 이 오브젝트가 동적인지 정적인지 판정 → 해당 통의 카운터를 1 올려 번호를 만들고 마지막 비트에 정적 여부를 새김 → 양방향 표에 등록. 카운터가 NetworkGuidIndex[2]로 정적용/동적용 두 개라 두 세계의 번호가 서로 침범하지 않아.

↳ 그 "양방향 표"는 어디에 있고 왜 두 방향이 필요하죠?

답 보기
FNetGUIDCache야. NetDriver마다 하나씩 붙어 있고 서버에도 클라에도 있어. 안에 사전이 두 권 있는데 — ObjectLookup은 번호→오브젝트, NetGUIDLookup은 오브젝트→번호. 방향이 둘 다 필요한 이유는 쓰는 상황이 다르거든. 보낼 때는 손에 오브젝트 포인터가 있으니 "얘 번호가 뭐야?"를 물어야 하고, 받을 때는 손에 번호가 있으니 "17번이 누구야?"를 물어야 해. 그리고 오브젝트를 붙잡는 쪽은 TWeakObjectPtr라서, 이 표 때문에 오브젝트가 안 죽는 일은 없어. 핵심은 이거야 — 서버의 17번 포인터와 클라의 17번 포인터는 주소가 완전히 다르지만 번호는 같다. 이 한 겹의 간접층이 포인터 문제를 통째로 녹여.

Q3. 정적 오브젝트랑 동적 오브젝트는 뭐가 다른가요? 왜 나눴죠?

답 보기
핵심은 "클라가 이미 갖고 있느냐"야. 레벨에 배치해둔 문짝은 서버도 클라도 같은 맵 파일을 로드했으니 이미 양쪽 메모리에 있어. 이런 놈은 서버가 번호와 함께 경로 이름(...PersistentLevel.Door_3)을 한 번만 알려주면, 클라가 자기 레벨에서 그 이름으로 찾아내 번호와 짝지어. 이게 정적. 반대로 런타임에 SpawnActor된 몹은 클라 메모리에 없고 안정적인 경로 이름도 없어. 그러니 서버가 번호를 찍어주고 "이 클래스로 여기 스폰해"라는 스폰 정보를 통째로 보내야 클라에 생겨. 이게 동적. 안 나누면? 이미 양쪽이 아는 문짝까지 매번 스폰 정보를 통신으로 실어 보내는 낭비가 돼.

↳ 엔진은 정적인지 동적인지 어떻게 판정하나요?

답 보기
재밌게도 "동적"을 직접 정의하지 않아. IsDynamicObject()는 딱 한 줄인데 return !Object->IsFullNameStableForNetworking();야 — "경로 이름으로 부를 수 없으면 동적"이라는 부정 정의지. 그리고 "이름이 안정적"의 정체는 RF_WasLoaded(디스크의 맵/에셋에서 로드됨) 같은 플래그거나, IsNative()(C++ 코드에 박힘), CDO, 기본 서브오브젝트인지야. 다 같은 말로 요약돼 — "서버와 클라가 그걸 각자 똑같이 만들어냈나?" 그러면 이름으로 부를 수 있고, 아니면 서버만 아는 놈이라 동적이야. 판정 기준이 "언제 태어났나"가 아니라 "이름으로 지칭 가능한가"라는 게 포인트.

↳ 맵 파일이 서버랑 클라가 다르면 어떻게 되나요?

답 보기
정적 참조가 통째로 깨져. 서버는 "Door_3 참조해"라고 경로를 보냈는데 클라 맵엔 Door_3가 없거나 다른 게 있는 거니까. 정적 참조의 전제 자체가 "양쪽이 같은 걸 이미 갖고 있다"인데 그 전제가 무너진 거지. 그래서 UE는 경로와 함께 네트워크 체크섬(NetworkChecksum)을 같이 실어 보내서 불일치를 감지할 수 있게 해뒀어. 조선 서버에서 "클라와 서버의 리소스 버전 불일치"로 터지던 사고랑 정확히 같은 계열이야 — 원인도 같고 증상도 같아.

Q4. Target = NetGUID 34가 도착했는데 클라에 34번 오브젝트가 아직 없으면요?

답 보기
이게 이 챕터의 하이라이트야. 흔한 상황이거든 — 몹 A와 몹 B는 서로 다른 액터 채널이라 어느 봉투가 먼저 도착할지 아무도 보장 못 하니까. 여기서 못 찾았다고 nullptr 넣고 넘어가면 영구적으로 틀린 상태가 돼. 34번이 3프레임 뒤에 도착해도 다시 꽂아줄 사람이 없고, 프로퍼티 복제는 바뀐 것만 보내니 서버 입장에선 Target은 34번 그대로라 다시 안 보내거든. 그래서 UE는 못 찾은 참조를 버리지 않고 보류해. FGuidReferences라는 기록을 만들어 (a) 못 찾은 번호 (b) 이 프로퍼티의 메모리 위치 (c) 방금 받은 원본 비트 복사본을 통째로 냉동해둬. 나중에 번호가 풀리면 그 비트를 해동해 다시 적용하는 거지.

↳ 나중에 34번이 도착하면 어떻게 붙나요? 매 프레임 전부 다시 시도하나요?

답 보기
NetDriver가 UnmappedReplicators라는 미해결 명단을 들고 있어. 매 틱 그 명단만 한 바퀴 돌면서 각 담당자에게 UpdateUnmappedObjects()를 불러 "이제 찾을 수 있어?"를 다시 물어. 찾았으면 냉동해둔 비트를 해동해 포인터를 꽂고, 그 담당자가 더 이상 미해결이 없으면 It.RemoveCurrent()로 명단에서 스스로 빠져. 그래서 폴링이긴 한데 전체를 훑는 게 아니라 미해결이 남은 놈들만 훑어 — 명단이 아주 작고 스스로 줄어들지. 그리고 참조가 풀리는 순간 OnRep도 다시 불려.

↳ 반대로 이미 잘 붙어 있던 오브젝트가 사라지면요?

답 보기
자동으로 unmapped로 되돌려지고 프로퍼티는 nullptr이 돼. 그리고 미해결 명단에 다시 등록돼. 그 오브젝트가 나중에 돌아오면 같은 NetGUID로 다시 붙어. 그래서 참조 해결은 1회성 이벤트가 아니라 mapped ⇄ unmapped를 몇 번이고 오가는 왕복 상태 기계야. 소스 주석도 "같은 오브젝트에 대해 매핑/언매핑이 여러 번 일어날 수 있다 — 예를 들어 액터가 relevancy를 반복해서 들락날락하면"이라고 명시해뒀어. 액터가 시야 밖으로 나갔다 들어왔다 하면 딱 이 상황이지.

↳ 그럼 게임 코드는 뭘 조심해야 하나요?

답 보기
두 가지야. 첫째, 오브젝트 참조 프로퍼티의 OnRep 안에서 포인터가 nullptr이 아니라고 가정하면 안 돼. Unresolved 상태에서 OnRep이 먼저 한 번 돌 수 있거든. 항상 널 체크하고 "아직 안 왔으면 아무것도 안 한다"로 짜야 해. 둘째, OnRep은 다시 불릴 수 있다. 참조가 나중에 풀리면 또 오고, 오브젝트가 사라졌다 돌아오면 또 와. 그러니 OnRep은 재진입 가능하게(idempotent) 짜야 해. 이게 엔진이 복잡도를 가져간 대가야 — 자동 복구를 공짜로 주는 대신, 게임 코드는 "참조가 잠깐 nullptr일 수 있다"는 규칙을 받아들여야 하는 거지. 조선 서버에서 "ID로 객체 찾았는데 없으면 무시하고 다음 패킷 기다리기" 하던 방어 습관이랑 똑같아.
