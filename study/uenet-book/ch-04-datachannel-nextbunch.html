DataChannel: Bunch가 채널에서 풀리는 법

대상: 게임 서버는 짜봤는데 언리얼 네트워크는 처음인 사람. 막히면 → bunch-vs-packet / 다음 → channel-types

0. 먼저 택배 창고로 비유

지난 챕터에서 이렇게 배웠지. 패킷은 상자, Bunch는 그 안의 물건이고, 큰 물건은 여러 상자에 쪼개(partial) 담긴다고. (안 봤으면 → bunch-vs-packet)

근데 UDP라서 상자들이 순서 뒤죽박죽으로, 심지어 중간 게 빠진 채로 도착할 수 있어. 택배 창고 직원 입장에서 생각해봐. 3번 상자가 먼저 왔는데 2번이 아직 안 왔어. 그럼 3번을 바로 손님한테 주면 안 되지. 2번 올 때까지 선반에 얹어두고, 2번 오면 2번→3번 순서로 내보내야 해. 그리고 쪼개진 물건이면 조각을 다 모아서 하나로 붙인 다음에 내보내야 하고.

이 "순서 맞춰 세우고(정렬) + 쪼개진 거 붙이고(조립) + 완성된 것만 위층으로 올린다"를 실제로 하는 함수가 이 챕터 주인공이야. 딱 두 개.

  • UChannel::ReceivedRawBunch — 상자가 도착하는 접수 창구. 순서 게이트.
  • UChannel::ReceivedNextBunch — 순서는 맞다고 치고 조립을 담당.

전부 DataChannel.cpp 한 파일에 있어. 접수 창구부터 열어보자.

1. 접수 창구 — 상자가 오면 두 갈래로 나뉜다

UNetConnection이 패킷을 뜯어서 Bunch 하나를 꺼내면, 그걸 채널한테 넘기는 유일한 문이 ReceivedRawBunch야 (DataChannel.cpp:603).

여기서 맞춰봐. reliable(꼭 도착해야 하는) Bunch가 왔는데 순서가 밀려 있어. 지금 채널이 기다리는 건 5번인데 7번이 먼저 왔어. 창구 직원은 뭘 할까?

  • (A) 그냥 처리한다
  • (B) 버린다 (어차피 재전송 올 테니)
  • (C) 선반에 얹어두고 5, 6번 올 때까지 기다린다

game 서버 감각이면 "TCP가 알아서 해주니까 신경 안 썼는데…" 싶을 거야. 정답은 (C). 코드가 딱 두 갈래로 갈라져.

	if ( Bunch.bReliable && Bunch.ChSequence != Connection->InReliable[ChIndex] + 1 )
	{
		...  // ← 순서 안 맞음: 선반(InRec)에 정렬 보관
	}
	else
	{
		bool bDeleted = ReceivedNextBunch( Bunch, bOutSkipAck );  // ← 순서 맞음: 바로 조립으로
		...
	}

DataChannel.cpp:640 (분기 조건) / :694-696 (else 갈래)

조건을 뜯어보면 Bunch.ChSequence != InReliable[ChIndex] + 1. 여기서 InReliable[ChIndex]는 "이 채널에서 마지막으로 처리 완료한 reliable 번호"야. 그러니 +1이 "다음에 와야 할 번호". 이거랑 안 맞으면 = 구멍이 났다 = 선반행. 딱 맞으면 = else = 바로 ReceivedNextBunch로 흘려보낸다.

참고: 이 순서 분기는 reliable일 때만 걸린다. unreliable Bunch는 애초에 bReliable이 0이라 이 if를 건너뛰고 바로 else로 가. "안 믿는 물건은 순서 안 따진다"는 거지.

그리고 이 순서 판정보다 먼저 하는 일이 하나 있어. NetGUID(패키지맵 export) 소비 (:611). partial이든 순서가 밀렸든 상관없이 이건 제일 먼저 빼먹는데, 왜 그런지는 이 챕터 범위 밖이라 링크만 → bunch-vs-packet. 지금은 "순서 게이트가 핵심"만 붙잡자.

2. 순서 밀린 놈은 선반에 "정렬해서" 꽂는다

(C) 갈래로 들어왔어. 7번이 먼저 왔고 5번을 기다리는 중. 이 7번을 InRec이라는 링크드리스트에 꽂는데, 아무데나 안 꽂고 시퀀스 오름차순으로 정렬 삽입해.

		// Find the place for this item, sorted in sequence.
		UE_LOG(LogNetTraffic, Log, TEXT("      Queuing bunch with unreceived dependency: %d / %d"), Bunch.ChSequence, Connection->InReliable[ChIndex]+1 );
		FInBunch** InPtr;
		for( InPtr=&InRec; *InPtr; InPtr=&(*InPtr)->Next )
		{
			if( Bunch.ChSequence==(*InPtr)->ChSequence )
			{
				// Already queued.
				return;
			}
			else if( Bunch.ChSequence<(*InPtr)->ChSequence )
			{
				// Stick before this one.
				break;
			}
		}

		FInBunch* New = new FInBunch(Bunch);
		New->Next     = *InPtr;
		*InPtr        = New;
		NumInRec++;

DataChannel.cpp:658-678

for 루프가 리스트를 훑으면서 자리를 찾는다. 초딩 계단으로 세 가지 경우만 있어.

  • 같은 번호가 이미 있다 (==) → "Already queued", 그냥 return. 중복 도착(재전송이 겹침)은 조용히 버린다.
  • 나보다 큰 번호를 만났다 (<) → break. 그 앞에 끼워넣는다. (그래서 리스트가 항상 오름차순 유지)
  • 끝까지 갔다 → 리스트 맨 뒤에 붙는다.

자리를 찾으면 New->Next = *InPtr; *InPtr = New로 링크를 이어. 이중 포인터(FInBunch**)를 쓰는 이유가 이거야 — 리스트 맨 앞이든 중간이든 "그 자리를 가리키는 포인터"를 직접 바꿔치기해서 head 특수 케이스를 없앤 거지. C로 링크드리스트 짜본 사람이면 눈에 익은 관용구.

그리고 무한정 쌓지는 않아. NumInRec >= RELIABLE_BUFFER면 Bunch.SetError() 때리고 연결을 끊는다 (:681). 선반이 꽉 차도록 구멍이 안 메워지면 = 뭔가 심각하게 잘못된 연결이니까 포기하는 거야.

3. 구멍이 메워지는 순간 — 재정렬의 심장

이제 핵심. 아까 (A)/(C) 갈래를 다시 봐. 순서가 딱 맞는 Bunch가 오면 else로 가서 ReceivedNextBunch를 부른다고 했지. 근데 그게 5번이었다고 쳐. 5번을 처리하고 나면 InReliable[ChIndex]가 5로 갱신돼. 그럼 이제 선반에 얹어뒀던 6, 7번의 차례가 온 거잖아?

바로 그걸 처리하는 게 이 while 루프야.

		while( InRec )
		{
			// We shouldn't hit this path on 100% reliable connections
			check( !Connection->IsInternalAck() );

			if( InRec->ChSequence!=Connection->InReliable[ChIndex]+1 )
				break;
			UE_LOG(LogNetTraffic, Log, TEXT("      Channel %d Unleashing queued bunch"), ChIndex );
			FInBunch* Release = InRec;
			InRec = InRec->Next;
			NumInRec--;

DataChannel.cpp:712-723

읽어봐. 선반(InRec)이 비어있지 않은 동안, 맨 앞 놈의 시퀀스가 "다음에 와야 할 번호"랑 맞는지 본다 (:718). 맞으면 리스트에서 떼어내(Release) 다시 ReceivedNextBunch로 흘려보내(:732, 스니펫 아래쪽). 이게 돌면서 InReliable가 6, 7로 계속 갱신되니까, 루프가 6번 방출 → 7번 방출 하고 더 이상 연속이 안 되면 break로 멈춰.

로그 문구가 대놓고 "Unleashing queued bunch" — 가둬놨던 걸 풀어준다. 이 한 루프가 UDP 위에서 TCP의 순서 재조립을 앱 레벨로 흉내 내는 심장이야. 방금 도착한 5번이 열쇠가 돼서, 밀려 있던 뒤 조각들이 우르르 순서대로 풀려나가는 거지.

정리하면: ReceivedRawBunch는 "순서가 맞는 놈은 즉시, 안 맞는 놈은 선반에, 그리고 매번 처리 후 선반을 훑어 연속되는 만큼 방출". 이 함수의 존재 이유 자체가 순서 보장이야.

4. ReceivedNextBunch — 여기부턴 "순서는 맞다", 남은 건 조립

ReceivedNextBunch에 도착했다는 건 이미 순서가 보장됐다는 뜻이야. 함수 서두가 그걸 못박아.

	// Note this bunch's retirement.
	if ( Bunch.bReliable )
	{

		check( Bunch.ChSequence == Connection->InReliable[Bunch.ChIndex] + 1 );

		Connection->InReliable[Bunch.ChIndex] = Bunch.ChSequence;
	}

	FInBunch* HandleBunch = &Bunch;
	if (Bunch.bPartial)
	{
		HandleBunch = NULL;

DataChannel.cpp:775-787

두 가지가 여기서 일어나.

  1. retirement (은퇴 처리) — reliable이면 InReliable[ChIndex]를 이 시퀀스로 갱신 (:781). 3절에서 "구멍이 메워졌다"의 실체가 바로 이 줄이야. check(...)는 "여기 온 reliable은 무조건 +1이어야 한다"는 자기 확인이고.
  2. HandleBunch 세팅 — 이게 "결국 위층으로 올려보낼 완성본"을 가리키는 포인터야. non-partial이면 그냥 자기 자신(&Bunch)이라 조립 필요 없이 통과. partial이면 일단 NULL로 두고 (:787), 조립이 끝나야 채워진다.

즉 이 함수의 일은 딱 하나 남았어. partial이면 조각을 다 모아 HandleBunch에 완성본을 담는 것.

partial 조각이 왔어. 첫 조각(bPartialInitial)이면 새 조립 버퍼 InPartialBunch를 만들고 (:820), 이어지는 조각이면 거기다 갖다붙여. 붙이는 코드가 이거.

  • InPartialBunch — 조립 중인 버퍼가 실제로 있냐.
  • !InPartialBunch->bPartialFinal — 이미 완성된 버퍼에 또 붙이려는 거 아니냐.
  • bSequenceMatches — 시퀀스가 이어지냐. (reliable은 딱 +1만, unreliable은 같은 패킷 시퀀스도 허용 — :858-864. 한 패킷에 여러 조각이 실릴 수 있으니까)

bPartialFinal을 만나는 순간 "Completed Partial Bunch" 로그가 찍히고, HandleBunch = InPartialBunch — 4절에서 NULL로 비워뒀던 그 포인터에 완성된 통짜 Bunch를 담는다. 이제 위층에 올릴 물건이 준비된 거야.

만약 조립이 어긋나면(순서 깨짐, 신뢰성 충돌) bOutSkipAck = true로 세우고 InPartialBunch를 폐기해 (:924 갈래). bOutSkipAck는 "이 패킷 아직 ack 하지 마라" 신호라서, 상대가 재전송하게 만들어 신뢰성을 지켜. ack 얘기 본론은 → reliability-ack.

6. 채널 → 컨텐츠 경계

HandleBunch에 완성본이 담겼으면(non-partial이거나 partial 조립 완료), 함수 끝에서 이렇게 넘긴다.

	{
		... // 채널 open 처리 (:1014)
		// Receive it in sequence.

ReceivedBunch(Bunch)는 가상 함수라, 채널 종류에 따라 UActorChannel::ReceivedBunch(액터 프로퍼티/RPC) 또는 UControlChannel::ReceivedBunch(핸드셰이크)로 갈린다. 여기가 "순서·완결 보장된 Bunch"가 채널 배관을 떠나 실제 컨텐츠 처리로 넘어가는 문이야. 채널 종류가 뭐가 있는지는 → channel-types.

그 위(프로퍼티/RPC 역직렬화)는 완전히 다른 챕터 주제라 여기선 안 판다. 이 챕터의 종착점은 "순서·조립 끝난 완성본을 ReceivedBunch로 넘긴다"까지.

인식 차이 딱 하나만 붙잡으면 돼. 우리는 TCP라 "순서 밀린 거 다시 세우기 / 쪼갠 거 붙이기"를 커널이 공짜로 해줬지만, 언리얼은 UDP 위라 그걸 InRec 링크드리스트와 InPartialBunch 버퍼로 손수 짠다. CH04에서 본 코드의 8할이 "TCP가 해주던 걸 UDP 위에서 재구현"인 셈이야. 왜 TCP를 안 쓰고 이 고생을 하는지는 → reliability-ack. 이게 정확히 어느 스레드에서 도는지는 → netdriver-tick.

🎯 원리 한 줄 요약

ReceivedRawBunch는 순서 맞는 reliable Bunch만 즉시 통과시키고 밀린 건 InRec에 정렬 보관했다가 구멍이 메워지는 순간 while(InRec)로 우르르 풀어(재정렬), ReceivedNextBunch가 partial 조각을 InPartialBunch에 이어붙여(재조립) 마지막 조각에서 완성하면, 그 완성본만 ReceivedSequencedBunch → ReceivedBunch()로 채널 밖 컨텐츠 처리에 올려보낸다 — UDP 위에 TCP의 순서·완결 보장을 앱 레벨로 손수 얹은 것.
