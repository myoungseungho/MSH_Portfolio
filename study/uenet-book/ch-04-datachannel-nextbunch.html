막히면 → bunch-vs-packet / 다음 → channel-types

왜 이걸 배워? — 문제의식부터

네가 조선 서버에서 SP_*/CM_* 패킷을 받아 처리해봤으면 이런 그림은 익숙할 거야. IOCP 워커가 바이트를 받고, 패킷 헤더를 읽고, CChosunPlayer 같은 세션/플레이어 객체로 넘긴 다음, 게임 로직은 한 줄로 차례차례 처리하게 만들지. 특히 TCP를 쓰면 "앞 패킷이 먼저 오고, 큰 데이터는 알아서 이어 붙는다"를 커널이 거의 공짜로 해줘.

근데 언리얼 네트워크는 UDP 위에서 움직여. 그러면 택배 상자가 5번, 7번, 6번 순서로 올 수도 있고, 큰 물건을 세 조각으로 쪼개 보냈는데 가운데 조각만 늦게 올 수도 있어. 이걸 그냥 도착한 순서대로 ActorChannel이나 ControlChannel에 던지면 무슨 일이 나겠어? 아이템 지급보다 장착 RPC가 먼저 실행되거나, 아직 반쪽짜리 데이터로 액터를 만들려다가 상태가 꼬인다.

우리 서버로 치면 락으로 억지로 막을 문제가 아니야. 단일스레드 게임 로직 큐에 넣기 전에, 이 패킷이 지금 처리해도 되는 순서인지, 쪼개진 조각이 다 모였는지를 먼저 확인해야 해. 안 그러면 큐는 차분하게 도는데, 큐에 들어간 재료 자체가 뒤죽박죽인 셈이야.

그래서 이 챕터의 답이 UChannel::ReceivedRawBunch와 UChannel::ReceivedNextBunch야. ReceivedRawBunch는 번호표를 보고 "지금 들어갈 놈인지, 선반에 기다릴 놈인지"를 가르고, ReceivedNextBunch는 "조각이면 다 붙을 때까지 위층으로 올리지 마"를 맡는다. 초딩식으로 말하면, 선생님한테 제출하기 전에 번호순으로 줄 세우고 찢어진 숙제를 테이프로 붙이는 단계야.

이걸 지금 배우는 이유도 흐름상 딱 여기라서 그래. 앞 챕터에서 우리는 패킷과 Bunch, partial이 뭔지 배웠어. 이제 UNetConnection이 패킷에서 Bunch를 꺼내 채널에 던진 직후, 그 Bunch가 정말 처리 가능한 완성품인지 확인하는 문을 봐야 해.

그리고 이 문을 지나야 다음 이야기가 의미가 생겨. 여기서 순서와 조립이 끝난 Bunch만 ReceivedSequencedBunch → ReceivedBunch()로 넘어가고, 그다음에야 ActorChannel의 복제/RPC든 ControlChannel의 제어 메시지든 제대로 읽을 수 있어. 즉 CH04는 "패킷을 뜯었다"와 "게임 내용으로 처리한다" 사이에 놓인 검문소야.

0. 먼저 택배 창고로 비유

지난 챕터에서 이렇게 배웠지. 패킷은 상자, Bunch는 그 안의 물건이고, 큰 물건은 여러 상자에 쪼개(partial) 담긴다고. (안 봤으면 → bunch-vs-packet)

근데 UDP라서 상자들이 순서 뒤죽박죽으로, 심지어 중간 게 빠진 채로 도착할 수 있어. 택배 창고 직원 입장에서 생각해봐. 3번 상자가 먼저 왔는데 2번이 아직 안 왔어. 그럼 3번을 바로 손님한테 주면 안 되지. 2번 올 때까지 선반에 얹어두고, 2번 오면 2번→3번 순서로 내보내야 해. 그리고 쪼개진 물건이면 조각을 다 모아서 하나로 붙인 다음에 내보내야 하고.

이 "순서 맞춰 세우고(정렬) + 쪼개진 거 붙이고(조립) + 완성된 것만 위층으로 올린다"를 실제로 하는 함수가 이 챕터 주인공이야. 딱 두 개.

  • UChannel::ReceivedRawBunch — 상자가 도착하는 접수 창구. 순서 게이트.
  • UChannel::ReceivedNextBunch — 순서는 맞다고 치고 조립을 담당.

전부 DataChannel.cpp 한 파일에 있어. 접수 창구부터 열어보자.

1. 접수 창구 — 상자가 오면 두 갈래로 나뉜다

UNetConnection이 패킷을 뜯어서 Bunch 하나를 꺼내면, 그걸 채널한테 넘기는 유일한 문이 ReceivedRawBunch야 (DataChannel.cpp:603).

여기서 맞춰봐. reliable(꼭 도착해야 하는) Bunch가 왔는데 순서가 밀려 있어. 지금 채널이 기다리는 건 5번인데 7번이 먼저 왔어. 창구 직원은 뭘 할까?

  • (A) 그냥 처리한다
  • (B) 버린다 (어차피 재전송 올 테니)
  • (C) 선반에 얹어두고 5, 6번 올 때까지 기다린다

game 서버 감각이면 "TCP가 알아서 해주니까 신경 안 썼는데…" 싶을 거야. 정답은 (C). 코드가 딱 두 갈래로 갈라져.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호는 바로 아래 🔤 상자에서 택배 창고 말로 다시 풀어줄게. 코드를 외우는 게 아니라 "얘는 선반행, 얘는 다음 단계행"만 보면 돼.

if ( Bunch.bReliable && Bunch.ChSequence != Connection->InReliable[ChIndex] + 1 ) { ... // ← 순서 안 맞음: 선반(InRec)에 정렬 보관 } else { bool bDeleted = ReceivedNextBunch( Bunch, bOutSkipAck ); // ← 순서 맞음: 바로 조립으로 ... }

DataChannel.cpp:640 (분기 조건) / :694-696 (else 갈래)

🔤 기호 사전 — if ( Bunch.bReliable && Bunch.ChSequence != Connection->InReliable[ChIndex] + 1 )
• if = "만약 이 조건이 맞으면"이라는 갈림길 표지판.
• Bunch.bReliable = 이 Bunch에 붙은 꼭 순서 맞춰 받아야 함 딱지. b로 시작하면 보통 참/거짓 스위치야.
• && = 양쪽 조건이 둘 다 맞아야 한다는 뜻. "reliable이고, 번호도 안 맞으면"으로 읽어.
• != = "같지 않다". 여기선 도착한 번호가 기다리던 번호가 아니라는 뜻.
• Connection->InReliable[ChIndex] = 연결(Connection) 안의 reliable 처리표에서 이 채널(ChIndex) 칸을 꺼내는 말. ->는 "그 안으로 들어가서 꺼내", [..]는 "몇 번 칸".
• + 1 = 마지막 처리 번호 다음, 즉 이번에 와야 할 번호.
• else = 위 if가 아니면 타는 길. 여기선 순서가 맞아서 바로 조립 단계로 간다.
• bool bDeleted = 참/거짓 값을 담는 작은 깃발. ReceivedNextBunch가 처리하다 채널을 지웠는지 같은 결과를 받아둔다.
• ... = 책에서 중간 코드를 접어둔 표시. 실제 코드가 없는 게 아니라, 지금 설명에 필요한 핵심만 보여주는 거야.
🔁 이제 다시 보자. Bunch.bReliable(순서 지켜야 하는 물건)이고 Bunch.ChSequence != InReliable[ChIndex]+1(기다리던 다음 번호가 아니면) → 선반 InRec에 보관. 아니면 ReceivedNextBunch(...)로 바로 넘김. 한 줄로: "꼭 순서 지켜야 하는 물건만 번호 검사하고, 구멍 나면 쌓아둔다."

조건을 뜯어보면 Bunch.ChSequence != InReliable[ChIndex] + 1. 여기서 InReliable[ChIndex]는 "이 채널에서 마지막으로 처리 완료한 reliable 번호"야. 그러니 +1이 "다음에 와야 할 번호". 이거랑 안 맞으면 = 구멍이 났다 = 선반행. 딱 맞으면 = else = 바로 ReceivedNextBunch로 흘려보낸다.

참고: 이 순서 분기는 reliable일 때만 걸린다. unreliable Bunch는 애초에 bReliable이 0이라 이 if를 건너뛰고 바로 else로 가. "안 믿는 물건은 순서 안 따진다"는 거지.

그리고 이 순서 판정보다 먼저 하는 일이 하나 있어. NetGUID(패키지맵 export) 소비 (:611). partial이든 순서가 밀렸든 상관없이 이건 제일 먼저 빼먹는데, 왜 그런지는 이 챕터 범위 밖이라 링크만 → bunch-vs-packet. 지금은 "순서 게이트가 핵심"만 붙잡자.

🌱 이 개념은 왜 생겼나 — 순서 재조립 선반(InRec)
• 원래 구조: 도착한 상자를 오는 순서 그대로 처리하면 제일 쉬워. 우리 서버는 TCP라 커널이 이미 순서를 맞춰줘서 이 고민을 안 해봤을 거야.
• 그런데 문제: UDP는 상자가 5번, 7번, 6번 순서로 도착해. 지금 창고가 기다리는 건 5번인데 7번이 먼저 왔어. 이걸 그냥 손님한테 주면 아직 안 온 6번 앞 내용이 빠진 채 7번이 먼저 처리돼 → 상태가 꼬여.
• 그래서 필요한 것: 순서 밀린 상자를 바로 안 주고 선반에 번호순으로 얹어뒀다가, 빠진 번호가 도착해 구멍이 메워지는 순간 밀린 걸 순서대로 우르르 풀어주는 장치. 이 선반이 InRec이야. TCP가 커널에서 해주던 순서 재조립을 UE는 앱 레벨에서 손수 흉내 내는 거지.

2. 순서 밀린 놈은 선반에 "정렬해서" 꽂는다

(C) 갈래로 들어왔어. 7번이 먼저 왔고 5번을 기다리는 중. 이 7번을 InRec이라는 링크드리스트에 꽂는데, 아무데나 안 꽂고 시퀀스 오름차순으로 정렬 삽입해.

// Find the place for this item, sorted in sequence. UE_LOG(LogNetTraffic, Log, TEXT(" Queuing bunch with unreceived dependency: %d / %d"), Bunch.ChSequence, Connection->InReliable[ChIndex]+1 ); FInBunch** InPtr; for( InPtr=&InRec; *InPtr; InPtr=&(*InPtr)->Next ) { if( Bunch.ChSequence==(*InPtr)->ChSequence ) { // Already queued. return; } else if( Bunch.ChSequence<(*InPtr)->ChSequence ) { // Stick before this one. break; } } FInBunch* New = new FInBunch(Bunch); New->Next = *InPtr; *InPtr = New; NumInRec++;

DataChannel.cpp:658-678

🔤 기호 사전 — FInBunch** InPtr; for( InPtr=&InRec; *InPtr; InPtr=&(*InPtr)->Next )
• FInBunch** = FInBunch*(Bunch 하나를 가리키는 손가락)을 또 가리키는 손가락. 즉 손가락의 손가락이야.
• InPtr=&InRec = 선반 맨 앞(InRec)을 가리키는 자리부터 시작. &는 "그 변수의 주소, 즉 자리표를 가져와".
• *InPtr = InPtr이 가리키는 칸 안의 실제 값. *는 "손가락이 가리키는 걸 꺼내 봐".
• for(시작; 계속조건; 다음걸음) = 시작하고, 조건이 참인 동안 돌고, 매번 다음 걸음을 밟는 반복문.
• InPtr=&(*InPtr)->Next = 지금 Bunch의 Next 칸 자리로 이동. 링크드리스트에서 다음 연결고리를 따라가는 거야.
• == / < = 번호가 같으면 중복, 내 번호보다 큰 놈을 만나면 그 앞자리가 내 자리.
• return = 이 함수 일을 여기서 바로 끝냄. 이미 줄 서 있던 같은 번호면 더 할 게 없지.
• break = 반복문만 멈추고 아래 코드로 내려감. "자리 찾았으니 이제 끼워 넣자"라는 신호.
• new FInBunch(Bunch) = Bunch 복사본을 새로 만들어 선반에 올릴 물건으로 준비.
• New->Next = *InPtr; *InPtr = New = 새 물건의 뒤를 기존 줄에 연결하고, 그 자리에 새 물건을 꽂는다.
• NumInRec++ = 선반에 쌓인 개수를 하나 늘린다. ++는 1 증가.
🔁 이제 다시 보자. for가 InRec 선반을 앞에서부터 훑는다 → 같은 번호면 return으로 중복 버림 → 더 큰 번호를 만나면 break로 멈춤 → new FInBunch를 만들어 New->Next와 *InPtr로 그 자리에 끼워 넣음. 결국 이 코드는 "도착한 상자를 번호순 선반에 꽂는 코드"야.

for 루프가 리스트를 훑으면서 자리를 찾는다. 초딩 계단으로 세 가지 경우만 있어.

  • 같은 번호가 이미 있다 (==) → "Already queued", 그냥 return. 중복 도착(재전송이 겹침)은 조용히 버린다.
  • 나보다 큰 번호를 만났다 (<) → break. 그 앞에 끼워넣는다. (그래서 리스트가 항상 오름차순 유지)
  • 끝까지 갔다 → 리스트 맨 뒤에 붙는다.

자리를 찾으면 New->Next = *InPtr; *InPtr = New로 링크를 이어. 이중 포인터(FInBunch**)를 쓰는 이유가 이거야 — 리스트 맨 앞이든 중간이든 "그 자리를 가리키는 포인터"를 직접 바꿔치기해서 head 특수 케이스를 없앤 거지. C로 링크드리스트 짜본 사람이면 눈에 익은 관용구.

그리고 무한정 쌓지는 않아. NumInRec >= RELIABLE_BUFFER면 Bunch.SetError() 때리고 연결을 끊는다 (:681). 선반이 꽉 차도록 구멍이 안 메워지면 = 뭔가 심각하게 잘못된 연결이니까 포기하는 거야.

3. 구멍이 메워지는 순간 — 재정렬의 심장

이제 핵심. 아까 (A)/(C) 갈래를 다시 봐. 순서가 딱 맞는 Bunch가 오면 else로 가서 ReceivedNextBunch를 부른다고 했지. 근데 그게 5번이었다고 쳐. 5번을 처리하고 나면 InReliable[ChIndex]가 5로 갱신돼. 그럼 이제 선반에 얹어뒀던 6, 7번의 차례가 온 거잖아?

바로 그걸 처리하는 게 이 while 루프야.

// Dispatch any waiting bunches. while( InRec ) { // We shouldn't hit this path on 100% reliable connections check( !Connection->IsInternalAck() ); if( InRec->ChSequence!=Connection->InReliable[ChIndex]+1 ) break; UE_LOG(LogNetTraffic, Log, TEXT(" Channel %d Unleashing queued bunch"), ChIndex ); FInBunch* Release = InRec; InRec = InRec->Next; NumInRec--;

DataChannel.cpp:712-723

🔤 기호 사전 — while( InRec )
• while( InRec ) = InRec 선반 맨 앞에 뭔가 있는 동안 계속 돈다. 비어 있으면 멈춰.
• check( !Connection->IsInternalAck() ) = 개발용 확인문. !는 "아니어야 한다"이고, 아니면 그 자리에서 잡아낸다.
• InRec->ChSequence = 선반 맨 앞 Bunch의 번호를 꺼내 보는 말.
• != Connection->InReliable[ChIndex]+1 = 그 번호가 지금 기다리는 다음 번호와 다르면.
• break = 더 이상 연속 번호가 아니니 방출을 멈춘다. 선반에 남겨두고 다음 도착을 기다려.
• FInBunch* Release = InRec = 지금 풀어줄 맨 앞 Bunch를 Release라는 이름표로 잡아둔다.
• InRec = InRec->Next = 선반 머리를 다음 Bunch로 옮긴다. 맨 앞 하나를 떼어낸 효과야.
• NumInRec-- = 선반에 남은 개수를 하나 줄인다. --는 1 감소.
🔁 이제 다시 보자. while(InRec)로 선반을 본다 → 맨 앞 번호가 InReliable+1이 아니면 break → 맞으면 Release로 떼어내고 InRec = InRec->Next로 머리를 넘김. 즉 "구멍이 메워진 순간, 앞에서부터 연속되는 것만 차례대로 풀어주는 루프"야.

읽어봐. 선반(InRec)이 비어있지 않은 동안, 맨 앞 놈의 시퀀스가 "다음에 와야 할 번호"랑 맞는지 본다 (:718). 맞으면 리스트에서 떼어내(Release) 다시 ReceivedNextBunch로 흘려보내(:732, 스니펫 아래쪽). 이게 돌면서 InReliable가 6, 7로 계속 갱신되니까, 루프가 6번 방출 → 7번 방출 하고 더 이상 연속이 안 되면 break로 멈춰.

로그 문구가 대놓고 "Unleashing queued bunch" — 가둬놨던 걸 풀어준다. 이 한 루프가 UDP 위에서 TCP의 순서 재조립을 앱 레벨로 흉내 내는 심장이야. 방금 도착한 5번이 열쇠가 돼서, 밀려 있던 뒤 조각들이 우르르 순서대로 풀려나가는 거지.

정리하면: ReceivedRawBunch는 "순서가 맞는 놈은 즉시, 안 맞는 놈은 선반에, 그리고 매번 처리 후 선반을 훑어 연속되는 만큼 방출". 이 함수의 존재 이유 자체가 순서 보장이야.

  2. HandleBunch 세팅 — 이게 "결국 위층으로 올려보낼 완성본"을 가리키는 포인터야. non-partial이면 그냥 자기 자신(&Bunch)이라 조립 필요 없이 통과. partial이면 일단 NULL로 두고 (:787), 조립이 끝나야 채워진다.

즉 이 함수의 일은 딱 하나 남았어. partial이면 조각을 다 모아 HandleBunch에 완성본을 담는 것.

🌱 이 개념은 왜 생겼나 — 조립 버퍼(InPartialBunch)
• 원래 구조: 조각(partial) 편지가 오면 오는 족족 위층(컨텐츠 처리)으로 올려버리면 될 것 같지?
• 그런데 문제: 근데 조각은 반쪽짜리야. 3편 중 1편만 올려서 액터를 만들려고 하면, 아직 안 온 2·3편 데이터가 비어서 반쪽 상태로 액터가 꼬여. 조각이 다 모이기 전엔 처리하면 안 돼.
• 그래서 필요한 것: 조각을 임시 버퍼에 계속 이어붙여 두고, 마지막 조각(bPartialFinal)이 올 때까지 위층으로 안 올리는 대기소. 이게 InPartialBunch야. 조각을 다 붙여 완성본이 되는 순간에만 문을 열어(HandleBunch) 위로 보내지. 보내는 쪽이 쪼갠 걸 받는 쪽이 다시 한 통으로 되돌리는 자리야.

인식 차이 딱 하나만 붙잡으면 돼. 우리는 TCP라 "순서 밀린 거 다시 세우기 / 쪼갠 거 붙이기"를 커널이 공짜로 해줬지만, 언리얼은 UDP 위라 그걸 InRec 링크드리스트와 InPartialBunch 버퍼로 손수 짠다. CH04에서 본 코드의 8할이 "TCP가 해주던 걸 UDP 위에서 재구현"인 셈이야. 왜 TCP를 안 쓰고 이 고생을 하는지는 → reliability-ack. 이게 정확히 어느 스레드에서 도는지는 → netdriver-tick.

Q1. 패킷을 이미 뜯어서 Bunch를 꺼냈는데, 채널에 또 검문소(ReceivedRawBunch)를 두는 이유가 뭔가요?

답 보기
패킷을 뜯었다고 그 Bunch가 지금 처리해도 되는 완성품이란 보장이 없거든. UDP라 5·7·6번 순서로 올 수도 있고, 쪼개진 조각 중 가운데만 늦게 올 수도 있어. 이걸 도착한 순서대로 그냥 던지면 아이템 지급보다 장착 RPC가 먼저 돌거나, 반쪽 데이터로 액터를 만들다 상태가 꼬여. 그래서 채널이 게임 로직에 올리기 전에 "지금 처리해도 되는 순서인지, 조각이 다 모였는지"를 먼저 확인해. "패킷을 뜯었다"와 "게임 내용으로 처리한다" 사이에 놓인 검문소야.

↳ 그럼 이 검문소가 하는 두 가지 일이 정확히 뭐죠?

답 보기
정렬(순서 맞춰 세우기)과 조립(쪼개진 거 붙이기)이야. ReceivedRawBunch가 번호표를 보고 "지금 들어갈 놈인지, 선반에서 기다릴 놈인지" 가르고, ReceivedNextBunch가 "조각이면 다 붙을 때까지 위층으로 올리지 마"를 맡아. 선생님한테 제출하기 전에 번호순으로 줄 세우고 찢어진 숙제를 테이프로 붙이는 단계지.

Q2. reliable Bunch가 순서 밀려서 왔어요. 기다리는 건 5번인데 7번이 먼저 왔으면, 그냥 처리하나요 버리나요?

답 보기
둘 다 아니야. 선반(InRec)에 보관했다가 5·6번이 채워지면 그때 순서대로 꺼내. 지금 처리하면 아직 안 온 앞 내용이 빠진 채 뒤 게 먼저 돌아서 상태가 꼬이고, 버리면 어차피 재전송받아야 하니 낭비야. 그래서 순서 밀린 놈은 InRec이라는 링크드리스트에 시퀀스 오름차순으로 정렬 삽입해두고, 빠진 번호가 도착해 구멍이 메워지는 순간 밀린 걸 우르르 풀어줘. TCP가 커널에서 해주던 순서 재조립을 앱 레벨로 손수 흉내 내는 거야.

↳ unreliable Bunch도 이렇게 선반에 세우나요?

답 보기
아니, 순서 분기는 reliable일 때만 걸려. unreliable은 bReliable이 0이라 그 if를 건너뛰고 바로 처리로 가. "안 믿는 물건은 순서 안 따진다"는 거지 — 옛날 좌표 같은 건 순서 좀 틀려도 상관없고, 최신 게 오면 어차피 덮이니까.

↳ 선반이 무한정 쌓이면요? 앞 번호가 영영 안 오면?

답 보기
무한정 안 쌓아. 쌓인 개수가 RELIABLE_BUFFER 상한을 넘으면 에러 처리하고 연결을 끊어. 선반이 꽉 차도록 구멍이 안 메워진다는 건 = 뭔가 심각하게 잘못된 연결이란 뜻이거든. 그럴 땐 붙잡고 있어봐야 소용없으니 포기하는 거야.

Q3. 순서 검사를 통과한 다음, 쪼개진 조각(partial)은 왜 곧장 위로 안 올리고 붙일 때까지 기다리나요?

답 보기
조각은 반쪽짜리거든. 3편 중 1편만 올려서 액터를 만들려 하면 아직 안 온 2·3편 데이터가 비어서 반쪽 상태로 액터가 꼬여. 그래서 조각을 InPartialBunch라는 임시 버퍼에 계속 이어붙여 두고, 마지막 조각(bPartialFinal)이 올 때까지 위층으로 안 올려. 다 붙어 완성본이 되는 순간에만 문을 열어 위로 보내지 — 보내는 쪽이 쪼갠 걸 받는 쪽이 다시 한 통으로 되돌리는 자리야.

↳ 완성본이 준비됐는지 아닌지는 뭘로 판단하나요?

답 보기
HandleBunch라는 포인터 하나로 게이트를 만들어. non-partial이면 처음부터 자기 자신을 가리켜 통과, partial이면 일단 NULL로 비워뒀다가 마지막 조각에서 완성본을 담아. 함수 끝에서 HandleBunch != NULL일 때만 다음 단계로 넘겨 — 그러니까 조립 중이면 NULL이라 못 올라가고, 완성됐을 때만 게이트가 열려.

↳ 조립하다 순서가 깨지거나 하면 어떻게 처리해요?

답 보기
조립 버퍼를 폐기하고 bOutSkipAck = true로 세워. 이건 "이 패킷 아직 ack 하지 마라" 신호라서, 상대가 재전송하게 만들어 신뢰성을 지켜. 반쪽 조립본을 억지로 올리는 게 아니라, 아예 못 받은 셈 치고 다시 받는 거지. unreliable 조각이 reliable 조립본을 오염시키는 것도 신뢰성 플래그 비교로 막고.

Q4. 이 챕터의 순서·조립 로직은 결국 우리 TCP 서버 대비 뭘 재구현한 건가요?

답 보기
코드의 8할이 "TCP가 공짜로 해주던 걸 UDP 위에서 손수 재구현"이야. 우리는 TCP라 순서 밀린 거 다시 세우기, 쪼갠 거 붙이기를 커널이 알아서 해줬지. UE는 그걸 InRec 링크드리스트(순서 재조립)와 InPartialBunch 버퍼(조각 재조립)로 앱 레벨에서 직접 짜. 그러고 순서·조립이 끝난 완성본만 ReceivedSequencedBunch → ReceivedBunch()로 채널 밖 컨텐츠 처리에 올려보내.

↳ 그렇게 고생할 거면 그냥 TCP를 쓰면 안 되나요?

답 보기
TCP는 "전부 순서 보장"이라 하나 잃으면 뒤가 다 막히는(head-of-line blocking) 문제가 있어 — 실시간 게임엔 치명적이야. UDP를 쓰면 잃어도 되는 건 그냥 흘려보내고, 꼭 필요한 것만 골라서 reliable로 순서 보장을 얹을 수 있어. 그 "골라서 얹는" 유연함 때문에 이 고생을 감수하는 거지. 안 믿어도 되는 좌표까지 순서 기다리느라 최신 상태가 늦으면 그게 더 손해거든.

🎯 원리 한 줄 요약

ReceivedRawBunch는 순서 맞는 reliable Bunch만 즉시 통과시키고 밀린 건 InRec에 정렬 보관했다가 구멍이 메워지는 순간 while(InRec)로 우르르 풀어(재정렬), ReceivedNextBunch가 partial 조각을 InPartialBunch에 이어붙여(재조립) 마지막 조각에서 완성하면, 그 완성본만 ReceivedSequencedBunch → ReceivedBunch()로 채널 밖 컨텐츠 처리에 올려보낸다 — UDP 위에 TCP의 순서·완결 보장을 앱 레벨로 손수 얹은 것.
