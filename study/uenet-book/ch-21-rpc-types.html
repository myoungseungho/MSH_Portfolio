RPC — 함수처럼 보이는 원격 호출

들어가기 전에: "그냥 함수를 불렀을 뿐인데"

지금까지 복제(lifetime-props, replayout)는 "변수 값이 자동으로 따라가는" 얘기였어. HP를 서버에서 바꾸면 클라 HP도 슬금슬금 맞춰지는 거. 근데 게임엔 값이 아니라 사건을 보내야 할 때가 있어.

  • "이 캐릭터가 방금 총을 쐈어" → 총구 화염 이펙트 한 번
  • "너 지금 문 열기 버튼 눌렀지?" → 클라가 서버한테 요청
  • "모두 이 순간 폭발 소리 들어" → 전 클라에게 한 방

이건 변수가 아니야. 일회성 동작이지. 이걸 위해 UE가 준 게 RPC(Remote Procedure Call), 우리말로 "원격 함수 호출"이야.

핵심 마법은 이거야. 게임 코드에선 그냥 평범한 함수처럼 부른다:

ServerFireWeapon();   // 이게 함수 호출인데... 실은 네트워크로 새어나감

ServerFireWeapon()을 클라에서 부르면, 이 함수 몸통은 내 컴퓨터가 아니라 서버에서 돈다. 함수 호출 문법 그대로인데 실행 위치가 바다 건너로 순간이동하는 거지. 어떻게? 함수에 붙은 네트워크 딱지(플래그)를 보고 엔진이 "어? 이건 로컬 실행 말고 전송해야겠네" 하고 몰래 경로를 튼다.

이번 챕터 질문은 딱 하나야:

"함수처럼 생긴" RPC를, 엔진은 로컬 실행 vs 원격 전송으로 어떻게 갈라내고, 누구한테 보낼지 어떻게 정할까?

비유부터. 회사 우편함을 떠올려봐. 네가 서류(함수 호출)를 책상 위에 올려놨어. 근데 서류 겉면 도장(플래그)에 "이건 본사로", "이건 전 지점에 뿌려", "이건 그냥 여기서 처리"가 찍혀 있어. 분류원 한 명이 도장만 보고 "여긴 두고 / 저긴 부치고 / 이건 버려"를 정해. RPC의 그 분류원이 바로 GetFunctionCallspace야. 이걸 실제로 구현하는 게 아래 함수들이고. 낮은 계단으로 들어가자.

세 종류의 RPC — 방향이 전부다

먼저 용어. RPC는 딱 세 종류고, 구분 기준은 "누가 → 누구에게" 딱 하나야.

종류지정자방향예시
Server RPCServer클라 → 서버"나 문 열래" 요청
Client RPCClient서버 → (소유) 클라 1명"너만 레벨업 연출 봐"
Multicast RPCNetMulticast서버 → 전 클라"다 같이 폭발 봐"

이 방향이 왜 이렇게 고정이냐면 — 네트워크 위상 자체가 별 모양(star) 이거든. 서버가 중심, 클라들은 바큇살. 클라끼리는 서로 직접 선이 없어. 그러니 "클라 A → 클라 B"는 애초에 불가능하고, 항상 서버를 거쳐야 해. Server RPC로 서버에 올리고, 서버가 Multicast/Client RPC로 내려주는 게 유일한 길이지.

각 함수엔 이 방향이 비트 플래그로 박혀 있어: FUNC_NetServer / FUNC_NetClient / FUNC_NetMulticast. 엔진은 코드를 읽는 게 아니라 이 비트를 보고 방향을 판단해. 이게 이번 챕터 내내 나오는 열쇠야.

콜체인 한눈에 — 판정 → 위임 → 대상선택 → 직렬화

RPC가 함수 호출에서 실제 와이어 송신까지 가는 길은 네 단계야. 각 단계가 딱 한 가지 일만 해.

🔬 ①번 CallFunction/ProcessInternal은 CoreUObject 모듈 소스인데 이 클론엔 안 들어 있어. 그래서 ①은 개념으로만 설명하고, ②부터는 아래 전부 verbatim 실소스야.

계단 1 — ② 분류원 GetFunctionCallspace: 세 가지 답

②번이 이 챕터의 심장이야. 얘가 내놓는 답은 세 가지(그리고 조합):

  • Local — 여기서 그냥 실행해. (네트워크 안 씀)
  • Remote — 여기서 실행 말고 저쪽으로 부쳐.
  • Absorbed — 아무것도 안 해. 조용히 버려.
  • Local | Remote — 둘 다. 내 화면에서도 돌리고 남한테도 보내. (멀티캐스트의 특기)

이 조합을 뭉뚱그려 Callspace(콜스페이스) 라고 불러. "이 함수 호출을 어느 공간에서 처리할까"의 답이지.

계단 1-a — 멀티캐스트: 서버는 "내것도 돌리고 + 남한테도"

먼저 맞춰봐. 서버가 Multicast(폭발 연출) 함수를 부르면, 서버 자기 화면엔 폭발이 보여야 할까 안 보여야 할까?

...정답은 보여야 한다야. 서버(리슨 서버)도 결국 화면 있는 플레이어일 수 있으니, 자기도 실행하고 남한테도 뿌려야 자연스럽지. 그래서 답이 Local | Remote 조합이 나와.

Actor.cpp:5500-5520

	if ((Function->FunctionFlags & FUNC_NetMulticast))
	{
		if(bIsServer)
		{
			// Server should execute locally and call remotely
			if (RemoteRole != ROLE_None)
			{
				DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Multicast: %s"), *Function->GetName());
				return (FunctionCallspace::Local | FunctionCallspace::Remote);
			}

			DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Multicast NoRemoteRole: %s"), *Function->GetName());
			return FunctionCallspace::Local;
		}
		else
		{
			// Client should only execute locally iff it is allowed to (function is not KismetAuthorityOnly)
			DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Multicast Client: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace));
			return Callspace;
		}
	}

읽는 법:

  • 서버 + RemoteRole != ROLE_None (= 저쪽에 복제되는 액터다) → Local | Remote. 내것도 돌리고 남한테도 부친다. 이게 멀티캐스트의 진짜 모습이야.
  • 서버인데 RemoteRole == ROLE_None (= 아무한테도 복제 안 되는 액터) → 부칠 데가 없으니 Local만.
  • 클라가 멀티캐스트를 부름 → Callspace(기본 로컬)만 반환. 클라는 멀티캐스트를 뿌릴 권한이 없어. 남한테 못 보내.

여기서 벌써 규칙 하나가 보이지: 멀티캐스트를 실제로 방송할 수 있는 건 서버뿐이야.

계단 1-b — 단방향 RPC: 방향 안 맞으면 그냥 로컬

Server RPC랑 Client RPC는 "한 방향"이라 uni-directional이라 불러. 여기 판정은 재밌게도 "보낼 조건"이 아니라 "안 보낼 조건" 을 걸러내는 식이야.

Actor.cpp:5522-5540

	if (Function->FunctionFlags & (FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast))
	{
		// Handle uni-directional RPCs

		// if we are the server, and it's not a send-to-client function,
		if (bIsServer && !(Function->FunctionFlags & FUNC_NetClient))
		{
			// don't replicate
			DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Server calling Server function: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace));
			return Callspace;
		}
		// if we aren't the server, and it's not a send-to-server function,
		if (!bIsServer && !(Function->FunctionFlags & FUNC_NetServer))
		{
			// don't replicate
			DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Client calling Client function: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace));
			return Callspace;
		}
	}

말로 풀면 딱 두 문장이야:

  • 내가 서버인데, 이건 클라로 보낼 함수가 아니다 (= Server RPC) → 안 보내. 그냥 로컬. 이미 서버니까 서버에서 도는 게 맞잖아. 다시 부칠 이유가 없어.
  • 내가 클라인데, 이건 서버로 보낼 함수가 아니다 (= Client RPC) → 안 보내. 그냥 로컬. 서버가 나한테 보낸 Client RPC는 이미 도착지가 나니까 여기서 실행.

그럼 언제 Remote가 나오냐? 이 두 return을 둘 다 빠져나갔을 때야. 즉 "클라가 Server RPC를 부름"(도장은 서버行인데 나는 클라 → 부쳐야지) 또는 "서버가 Client RPC를 부름"(도장은 클라行인데 나는 서버 → 부쳐야지). 방향이 어긋난 순간에만 원격 전송이 켜져. 방향이 맞으면(이미 목적지에 있으면) 그냥 로컬.

똑똑하지. "보내야 할 때"를 일일이 나열하는 대신, "이미 도착지에 있으니 보낼 필요 없는 경우"만 쳐내는 거야.

계단 1-c — Absorbed: 권한 없는 클라의 반칙 막기

Absorbed(흡수 = 조용히 버림)는 언제 나올까. 대표 케이스가 이거야.

Actor.cpp:5465-5476

	if (NetMode == NM_Standalone)
	{
		if (LocalRole < ROLE_Authority && (Function->FunctionFlags & FUNC_NetServer))
		{
			// Don't let clients call server functions (in edge cases where NetMode is standalone (net driver is null))
			DEBUG_CALLSPACE(TEXT("GetFunctionCallspace No Authority Server Call Absorbed: %s"), *Function->GetName());
			return FunctionCallspace::Absorbed;
		}

		// Call local
		return FunctionCallspace::Local;
	}

NM_Standalone은 네트워크가 아예 안 붙은 상태(넷드라이버 null). 이 상태에서 권한 없는 쪽(LocalRole < ROLE_Authority)이 Server RPC를 부르면 → 부칠 넷드라이버도 없고, 실행하자니 권한도 없어. 그래서 크래시 대신 Absorbed. 삼켜서 없던 일로. 게임이 죽는 대신 조용히 무시하는 안전장치야.

포인트: RPC는 "부르면 무조건 실행"이 아니야. 판정에서 Absorbed가 나오면 없던 일이 돼. 이건 나중에 rpc-ownership·rpc-reliable-validation에서 보안·검증으로 크게 확장돼.

계단 2 — ③ CallRemoteFunction: "부쳐" 결정 후의 위임

②가 Remote 비트를 반환하면, ①의 VM이 이번엔 ③ CallRemoteFunction을 불러. 얘 역할은 단순해 — 살아있는 넷드라이버들한테 "이거 네가 처리해" 하고 넘기기.

Actor.cpp:5613-5633

bool AActor::CallRemoteFunction( UFunction* Function, void* Parameters, FOutParmRec* OutParms, FFrame* Stack )
{
	bool bProcessed = false;

	if (UWorld* MyWorld = GetWorld())
	{
		if (FWorldContext* const Context = GEngine->GetWorldContextFromWorld(MyWorld))
		{
			for (FNamedNetDriver& Driver : Context->ActiveNetDrivers)
			{
				if (Driver.NetDriver != nullptr && Driver.NetDriver->ShouldReplicateFunction(this, Function))
				{
					Driver.NetDriver->ProcessRemoteFunction(this, Function, Parameters, OutParms, Stack, nullptr);
					bProcessed = true;
				}
			}
		}
	}

	return bProcessed;
}

넷드라이버가 왜 여러 개(ActiveNetDrivers 루프)냐면 — 게임 넷드라이버 말고도 데모(리플레이) 넷드라이버, 빔(beacon) 넷드라이버가 동시에 붙어 있을 수 있거든(demo-replay). 각자 ShouldReplicateFunction으로 "이 함수 내가 처리할 대상 맞아?"를 답하고, 맞다는 놈마다 ProcessRemoteFunction으로 넘겨. 여기서 실제 송신 엔진 ④번으로 넘어가.

계단 3 — ④ ProcessRemoteFunction: 1명이냐 전원이냐

이제 진짜 갈림길이야. 누구한테 보낼 것인가. 그 판단의 기준 플래그를 먼저 세워:

NetDriver.cpp:7965-7966

		const bool bIsServer = IsServer();
		const bool bIsServerMulticast = bIsServer && (Function->FunctionFlags & FUNC_NetMulticast);

bIsServerMulticast = "내가 서버고 + 이 함수가 멀티캐스트다". 이 한 불리언이 아래 N명 루프 vs 1명 갈림을 정해.

계단 3-a — 멀티캐스트: 전 클라 순회

NetDriver.cpp:8009-8020 (도입부)

		// RepDriver didn't handle it, default implementation

		if (bIsServerMulticast)

			{
				Connection = ClientConnections[i];

ClientConnections는 서버가 붙잡고 있는 전 클라 커넥션 배열(netconnection-overview). 멀티캐스트는 이 배열을 처음부터 끝까지 돌아. 주석 그대로 "go to every client". 단, 모두에게 무조건 보내는 건 아니고 — 그 액터가 그 커넥션한테 릴러번스(relevance) 있는지 검사한 뒤에만 보내. (폭발이 지구 반대편 플레이어한테까지 갈 필욘 없잖아. 릴러번스는 relevancy에서.)

여기서 계단 1-a 판정이 다시 맞물려. 멀티캐스트가 이 N명 루프까지 오려면 애초에 bIsServer여야 했지. 클라가 부른 멀티캐스트는 ②에서 이미 로컬로 주저앉아서 여기 못 와. "방송은 서버만" 이 두 군데서 이중으로 지켜지는 거야.

계단 3-b — 단일 대상: 소유 커넥션 1개

멀티캐스트가 아니면(Server RPC / Client RPC), 대상은 딱 하나야.

NetDriver.cpp:8053-8062

		// Send function data to remote.
		Connection = Actor->GetNetConnection();
		if (Connection)
		{
			if (ServerConnection)
			{
				Connection = ServerConnection;
			}
			InternalProcessRemoteFunction(Actor, SubObject, Connection, Function, Parameters, OutParms, Stack, bIsServer);
		}

읽는 법:

  • Actor->GetNetConnection() — 이 액터를 소유한 커넥션을 찾아. Client RPC라면 "이 액터 주인 플레이어"의 커넥션이지. (그래서 Client RPC는 소유 클라 1명한테만 가. 이 "소유" 개념이 rpc-ownership의 핵심.)
  • if (ServerConnection) — 근데 내가 클라라면(클라는 서버 방향 커넥션 ServerConnection 하나만 가짐), 방금 찾은 걸 무시하고 무조건 ServerConnection으로 덮어써. 클라가 부친 Server RPC는 목적지가 언제나 "서버" 한 곳이니까.

정리하면 대상 선택은 세 갈래야: 멀티캐스트 = ClientConnections 전부 / Client RPC(서버발) = 소유 커넥션 1 / Server RPC(클라발) = ServerConnection 1. 그 다음 ⑤ InternalProcessRemoteFunction으로 넘어가 실제 번치 직렬화가 일어나(→ send-callchain, bunch-vs-packet).

잠깐, Iris/RepDriver는 왜 자꾸 나와?

④번 스니펫 첫 줄 주석 // RepDriver didn't handle it, default implementation 봤지. UE엔 기본 넷드라이버 위에 더 똑똑한 상위 계층이 얹힐 수 있어:

  • ReplicationDriver — 대규모 접속 최적화 계층 (replication-graph)
  • ReplicationSystem (Iris) — UE5의 차세대 복제 엔진 (iris)

이게 붙어 있으면 RPC를 걔네가 먼저 가로채서 처리하고, 위에서 본 기본 경로(전 클라 루프/단일 대상)는 건너뛰어. 그래서 코드 곳곳에 "RepDriver가 처리했으면 return" 같은 우회 체크가 깔려 있는 거야. 지금은 "기본 경로가 원리, 상위 계층은 그 위 최적화" 정도로만 알아두면 돼.

우리 서버랑 비교 — 조선협객전 IOCP vs UE RPC

이 구조, 우리 게임 서버(조선협객전) 눈으로 보면 낯설지 않아. 오히려 UE가 우리가 손으로 하던 걸 함수 문법 뒤에 숨긴 것에 가까워.

조선협객전 (C++ IOCP)UE RPC
사건 전송SP_XXX 구조체 채워 SendPacket() 명시 호출ServerXXX() 함수처럼 호출 (전송은 엔진이 몰래)
"누구에게" 판단개발자가 손으로: GetNetConnection() 골라 send② GetFunctionCallspace + ④ 대상선택이 자동
전체 방송ClientConnections 직접 for 루프 broadcastMulticast RPC → ④-a가 ClientConnections 루프
방향 강제관례로 지킴(CM_ 클라→서버, SM_ 서버→클라)플래그로 엔진이 강제 (어긋나면 Absorbed/로컬)
실행 스레드IOCP 워커 N개 → 락으로 액터 보호 필요게임 스레드 단일 — 락 없이 순차 실행

가장 큰 차이 두 개만 기억해:

  1. 명시 vs 암시. 우리는 SP_ 구조체 만들고 memset 조심하며(→ 우리 서버 규칙!) SendPacket을 직접 불러. UE는 함수 호출 한 줄이면 ②~⑤가 알아서 굴러. 편한 대신 "왜 안 갔지?"를 디버깅하려면 이 콜체인을 알아야 하는 거고.
  1. 워커 스레드 vs 단일 스레드. 우리 IOCP는 워커 여러 개가 동시에 패킷을 처리해서 액터 상태에 락이 필요해. UE 복제/RPC는 기본적으로 게임 스레드 한 줄에서 순차로 처리돼(그래서 ClientConnections for 루프가 락 없이 안전한 거야). 우리 "싱글 스레드 액터" 철학과 오히려 UE 쪽이 더 닮았어.

방향을 플래그로 엔진이 강제하는 것도 눈여겨봐. 우리는 CM_/SM_ 네이밍 관례로 "이건 클라→서버"를 지키지만 실수로 반대로 보내도 컴파일은 돼. UE는 방향 어긋나면 ②에서 로컬로 주저앉거나 Absorbed로 버려서, 틀린 방향 전송 자체가 구조적으로 막혀.

예측 한 번 더 — 정리 겸

맞춰봐. 리슨 서버(화면 있는 서버) 플레이어가 MulticastPlayExplosion()을 불렀어. 이 서버 자기 화면에 폭발이 보일까?

...보여. 계단 1-a에서 서버 멀티캐스트는 Local | Remote였잖아. Local 비트 때문에 자기도 실행하고, Remote 비트 때문에 ④-a에서 전 클라한테도 뿌려. 두 비트가 각각 "내 실행"과 "남 전송"을 담당하는 거지.

하나 더. 클라가 MulticastPlayExplosion()을 부르면? ②-a의 else 가지로 가서 Callspace(로컬)만 반환 → 자기 화면에서만 돌고 아무한테도 안 감. 클라는 방송권이 없으니까. 폭발을 남들도 보게 하려면? 클라가 Server RPC로 서버에 올리고 → 서버가 그걸 받아 Multicast로 뿌리는 2단 릴레이가 정석이야. 이게 별 모양 위상에서 사건이 퍼지는 유일한 길이야.

이 챕터가 남긴 것 / 다음

우리가 판 건 RPC의 뼈대 콜체인이야: 종류 3개(방향), 판정(②) → 위임(③) → 대상선택 1 vs N(④) → 직렬화(⑤). "함수처럼 보이는데 왜 저쪽에서 도는가"의 답은 ②의 플래그 판정에 다 들어 있었어.

아직 안 판 것들:

  • RPC가 믿을 수 있게(reliable) 도착하는가, 서버가 클라 요청을 검증(validation) 하는가 → rpc-reliable-validation
  • Client RPC가 하필 그 한 명한테만 가는 "소유(ownership)"의 정체 → rpc-ownership
  • 멀티캐스트가 누구한테 갈지를 거르는 릴러번스 → relevancy
  • 막히면 → netconnection-overview (커넥션·ClientConnections·ServerConnection이 뭔지), send-callchain (⑤ 이후 번치가 실제로 나가는 길)
  • 값 복제와의 대비가 헷갈리면 → lifetime-props (RPC는 "사건", 프로퍼티 복제는 "상태")
  • 다음 → rpc-reliable-validation

🎯 원리 한 줄 요약

RPC는 "함수 호출"의 탈을 썼을 뿐 — GetFunctionCallspace가 함수 플래그(방향)와 내 Role을 보고 "로컬/원격/버림"을 판정하고, 원격이면 넷드라이버가 멀티캐스트는 전 클라 루프로, 나머지는 소유 커넥션 1개로 흘려보낸다.
