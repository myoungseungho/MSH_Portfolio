서버 시간 맞추기 — 클라와 서버의 시계를 하나로

언리얼 네트워크 · 34 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 시간 문제를 한 번은 만났을 거야. 이벤트가 30초 뒤에 끝난다, 스킬 쿨타임이 5초 남았다, 보스 패턴이 12:00에 시작한다. 이런 건 결국 "지금 몇 시냐" 하나로 맞춰지는 약속이야.

근데 클라 시계와 서버 시계가 제멋대로면 바로 사고가 나. 어떤 유저 화면엔 이벤트가 1초 남았는데 서버는 이미 끝났다고 하고, 어떤 유저는 쿨타임이 끝난 줄 알고 CM_* 스킬 패킷을 보냈는데 서버는 아직 0.3초 남았다고 거절해. SP_* 응답으로 다시 고쳐줘도 화면은 덜컹거리고, 유저 입장에선 "방금 눌렀는데 왜 안 나가?"가 돼.

우리 조선 서버로 치면 IOCP 워커가 패킷을 받아서 단일스레드 로직 큐로 넘기고, CChosunPlayer 안에서 쿨타임과 이벤트 상태를 순서대로 처리하잖아. 락을 잘 걸어도 각 클라가 서로 다른 시계를 보고 있으면 UI 예측과 서버 판정이 계속 어긋나. 락은 데이터 충돌을 막아주지만, 시계가 다 다른 문제까지 맞춰주진 못해.

언리얼도 같은 문제를 만났고, 답은 "매번 서버한테 지금 몇 시냐고 묻기"가 아니야. 서버는 자기 시각만 복제해주고, 클라는 그걸 받아서 서버 시각과 내 시각의 차이(delta)를 스스로 계산해. 그 delta를 로컬 시계에 더하면, 클라는 서버에 계속 묻지 않고도 서버 시각을 추정할 수 있어.

그래서 이 챕터의 주인공이 AGameStateBase야. 앞에서 복제 변수와 RepNotify를 배웠으니, 이제 그 파이프를 써서 서버 시간을 클라가 어떻게 맞춰 잡는지 볼 차례야. 그리고 다음의 랙 보상에서는 "그때 그 순간"을 되감아 판정해야 하니까, 공통 시계 감각을 여기서 먼저 잡아야 해.

🌱 이 개념은 왜 생겼나 — 서버 시간 동기(server time sync)
• 원래 구조: 클라가 서버 시각이 궁금하면 그냥 "지금 몇 시야?" 물어보면 되잖아.
• 그런데 문제: 이벤트 카운트다운·쿨타임을 매 프레임 그리려면 초당 수십 번 물어야 해 — 뉴욕 친구한테 5분마다 전화 거는 꼴이야. 게다가 묻는 사이에도 시간은 흐르고 답이 오는 데 지연도 껴.
• 그래서 필요한 것: 처음에 "시차 = 14시간"만 알아내고 내 시계에 더해 쓰기. → 이게 서버 시간 동기야. 계속 안 묻고 내 시계 + 시차로 서버 시각을 추정해.

시차 이야기부터

뉴욕 사는 친구랑 통화 약속을 잡는다고 해봐. 걔 시계랑 내 시계는 애초에 안 맞아. 걔는 오전 9시, 나는 밤 11시. 그렇다고 5분마다 "지금 몇 시야?" 물어볼 순 없잖아.

똑똑한 방법은 이거야. 처음에 한 번만 물어봐서 "시차 = 14시간"이라는 값을 알아내. 그 뒤론 내 시계에 14시간만 더하면 걔 시각이 나와. 물어보는 건 시차가 틀어졌을까 봐 가끔 갱신할 때뿐이지.

MMORPG도 똑같은 문제를 풀어. "이벤트 30초 남음", "스킬 쿨타임 끝나는 시각" 같은 걸 클라 화면에 그리려면, 클라가 "지금 서버 시각"을 알아야 해. 근데 서버랑 클라의 시계는 안 맞아.

  • 서버는 새벽에 켰고 클라는 방금 접속했어. 둘 다 "레벨 시작 후 흐른 초"를 세는데 출발점이 완전히 달라.
  • 네트워크 지연도 껴. 서버가 "지금 100.0초야" 하고 쏜 순간, 그게 클라에 도착하면 이미 100.05초야.

그래서 UE도 시차 방식을 써. 클라가 "서버 시각 − 내 시각" 차이(delta)를 한 번 알아내면, 그 뒤론 자기 로컬 시계에 delta만 더해서 서버 시각을 스스로 계산해. 이걸 구현한 게 이 챕터의 주인공, AGameStateBase야.

지금부터 진짜 UE 코드가 처음 나와. 겁먹지 마 — 함수 이름 주변의 기호만 풀면, 이 줄은 그냥 "서버 시각 물어보는 버튼"으로 읽혀.

• const = 이 함수는 값을 읽어줄 뿐, 게임스테이트 안의 상태를 멋대로 바꾸지 않겠다는 약속.

🔁 이제 다시 보자. double(소수 시간 반환) → AGameStateBase::(게임스테이트 소속) → GetServerWorldTimeSeconds()(서버 시각 묻기) → const(읽기만 함). 이어 읽으면 "게임스테이트에게 지금 서버 시각 추정치를 숫자로 물어보는 함수"야.

이 함수 하나를 아무 데서나 부르면 서버 시각 추정치가 튀어나와. 어떻게 그게 가능한지가 이 챕터 전부야. 세 갈래 코드가 협력하는데, 누가 어느 머신에서 도는지가 핵심이라 역할로 나눠서 볼게.

값이 서버→클라로 어떻게 자동 전송되고, 도착하면 왜 콜백이 불리는지가 안 그려지면 → repnotify, lifetime-props 먼저 보고 와.
🌱 이 개념은 왜 생겼나 — delta(시차)는 클라가 계산
• 원래 구조: 시차(delta)가 필요하면 서버가 "너랑 나랑 3.7초 차이야" 계산해서 딱 내려주면 제일 깔끔하잖아.
• 그런데 문제: 서버는 클라가 몇 초짜리 시계를 들고 접속했는지 몰라. 클라마다 접속 시점·지연이 다 달라서 시차도 제각각 — 서버가 남의 시차를 대신 못 구해. 만 명이면 시차 만 개를 서버가 떠안아.
• 그래서 필요한 것: 서버는 자기 raw 시각만 방송, 시차는 각 클라가 "받은값 − 내 시각"으로 스스로 빼기. → delta는 복제 안 하고 클라가 만든다.

핵심 뒤틀림: delta는 복제 안 된다

여기서 먼저 맞춰봐.

질문: 서버가 "서버 시각 − 클라 시각 = 3.7초"라는 그 시차(delta)를 계산해서 클라한테 딱 내려주는 걸까? 그게 제일 간단하잖아.

.

.

반전: 아니야. 서버는 delta를 계산하지도, 내려주지도 않아. 서버가 클라로 보내는 건 오직 "내 지금 시각(raw 초)" 하나뿐이야. delta는 클라가 그 값을 받아서 스스로 계산해.

왜 이렇게? 서버는 클라가 몇 초짜리 시계를 들고 있는지 몰라. 클라마다 접속 시점이 다르니 시차도 다 달라. 그러니 서버가 남의 시차를 대신 계산해줄 방법이 없어. 서버는 그냥 자기 시각만 성실하게 방송하고, "내 시계랑 저 값의 차이"는 각 클라가 자기 자리에서 빼봐야 나오는 거지.

그래서 코드가 이렇게 갈려.

  • 서버(권한자): 0.1초마다 자기 월드 시각을 복제 변수에 실어 방송만 함.
  • 클라(비권한자): 그 값이 도착할 때마다 "저 값 − 내 시각 = delta"를 계산하고 다듬어서 보관.
  • 아무나: GetServerWorldTimeSeconds()로 "내 시각 + delta = 서버 시각" 질의.

🔤 기호 사전 — if (World->IsGameWorld() && GetLocalRole() == ROLE_Authority)
• if (...) = 괄호 안 조건이 맞을 때만 안쪽 블록을 실행하라는 문.
• World->IsGameWorld() = World가 가리키는 월드한테 "진짜 게임 월드야?"라고 묻는 것. ->는 포인터가 가리키는 대상의 기능을 부를 때 쓰는 화살표야.
• && = "그리고". 왼쪽 조건도 맞고 오른쪽 조건도 맞아야 통과해.
• == ROLE_Authority = 내 역할이 서버 권한자와 같은지 비교. ==는 "같다?", ROLE_Authority는 "서버가 주인"이라는 역할 딱지야.
• > 0.f = 갱신 주기가 0보다 큰지 확인. 0.f는 0초를 float 숫자로 적은 모양이야.
• SetTimer(...) = 타이머 알람을 등록하는 함수. 정해진 시간이 지나면 지정한 함수를 불러줘.
• this = 지금 이 AGameStateBase 객체 자신.
• &AGameStateBase::UpdateServerTimeSeconds = 타이머가 나중에 부를 함수의 주소표. &는 "이 함수가 어디 있는지 가리켜"라는 뜻으로 보면 돼.
• true = 반복 켜기. 여기서는 한 번만 울리는 알람이 아니라 계속 울리는 알람이야.
🔁 이제 다시 보자. World->IsGameWorld()(진짜 게임 월드이고) → &&(그리고) → GetLocalRole() == ROLE_Authority(내가 서버라면) → UpdateServerTimeSeconds()(지금 한 번 찍고) → SetTimer(..., true)(앞으로도 0.1초마다 반복). 한 줄 흐름은 "서버에서만 자기 시각 갱신 알람을 켠다"야.

GetLocalRole() == ROLE_Authority — 이 액터의 권한자, 즉 서버에서만 이 블록을 타. 클라는 여기 못 들어와. 서버는 즉시 한 번 UpdateServerTimeSeconds()를 부르고, 그다음 SetTimer로 주기 반복(마지막 인자 true) 등록해. 주기는 ServerWorldTimeSecondsUpdateFrequency인데 기본값이 이거야.

🔤 기호 사전 — void AGameStateBase::UpdateServerTimeSeconds()
• void = 이 함수는 값을 돌려주지 않아. 그냥 안에서 할 일을 하고 끝나.

• World->GetTimeSeconds() = 월드한테 "시작 후 몇 초 지났어?"라고 묻기.

🔁 이제 다시 보자. GetWorld()로 월드를 잡고 → if (World)로 진짜 있는지 확인하고 → World->GetTimeSeconds()로 지금 시간을 읽고 → ReplicatedWorldTimeSecondsDouble에 넣는다. 핵심은 "서버 시간이 담길 복제 변수에 raw 초를 꽂는다"야.

하는 일은 딱 하나. 자기 월드 시각(World->GetTimeSeconds())을 복제 변수 ReplicatedWorldTimeSecondsDouble에 대입. 이게 끝이야. "보내라"는 명령도, 소켓도 없어. 그냥 복제 변수에 대입하기만 하면, UE의 리플리케이션이 알아서 "값 바뀌었네" 하고 클라들로 실어 날라. (그 자동 전송 장치가 궁금하면 → server-replicate-actors)

여기서 초보가 헷갈리는 지점 하나. 서버는 delta 근처에도 안 가. 그냥 raw 초를 복제 변수에 꽂을 뿐이야. delta는 순전히 클라 몫이지.

🌱 이 개념은 왜 생겼나 — 스무딩 보간(절반씩 따라가기)
• 원래 구조: 시차 한 방울을 재면(받은값 − 내 시각) 그 값을 바로 delta로 쓰면 되지.
• 그런데 문제: 네트워크 지연이 매번 들쭉날쭉이라 한 방울은 노이즈투성이야. 그대로 쓰면 delta가 확 튀고, 화면 카운트다운이 뒤로 갔다 앞으로 갔다 덜컹거려.
• 그래서 필요한 것: 여러 방울을 누적 평균 내고, 목표로 한 번에 안 뛰고 "목표−현재의 절반"만 다가가기. → 지연 스파이크가 껴도 시계가 스르륵 수렴해. 시계는 튀는 게 제일 나쁘거든.

길어 보여도 네 계단이야. 천천히 밟자.

1계단 — 시차 1샘플 구하기 (:169).

• const double = 소수점 있는 숫자인데, 이번 샘플 값은 만든 뒤 바꾸지 않겠다는 뜻.

🔁 이제 다시 보자. ReplicatedWorldTimeSecondsDouble(방금 받은 서버 시각)에서 World->GetTimeSeconds()(내 시각)를 빼서 ServerWorldTimeDelta에 담는다. 한 줄 뜻은 "이번에 측정한 시차 샘플 하나 만들기"야.

방금 서버가 보낸 값 빼기 내 로컬 시각. 이게 "이번에 측정한 시차 한 방울"이야. 근데 이걸 그대로 쓰면 안 돼 — 네트워크 지연이 매번 들쭉날쭉이라 이 한 방울은 노이즈투성이거든. 그래서 아래 두 계단으로 눌러줘.

2계단 — 누적 평균 (:172-180). 시차 한 방울을 Sum에 더하고 개수를 하나 세. Sum / Num이 지금까지 평균 시차야. 튀는 샘플이 하나 껴도 평균이 눌러버려. 근데 무한정 쌓으면 옛날 값이 발목을 잡겠지? 그래서 250개가 넘으면 Sum을 개수로 나눠 한 값으로 접고 개수를 1로 리셋해. "지금까지 평균 하나를 새 출발점 삼아 다시 센다"는 뜻이야. 오래된 기억을 흘려보내 현재 시차를 대표하게 유지하는 거지.

3계단 — 목표 시차 (:182). TargetWorldTimeSecondsDelta = Sum / Num. 지금 이 순간 "가고 싶은 최종 시차 값"이야.

4계단 — 스무딩 보간 (:184-192). 여기가 제일 예뻐. 목표값으로 한 번에 확 안 바꿔.

ServerWorldTimeSecondsDelta += (TargetWorldTimeSecondsDelta - ServerWorldTimeSecondsDelta) * 0.5;
🔤 기호 사전 — ServerWorldTimeSecondsDelta += (TargetWorldTimeSecondsDelta - ServerWorldTimeSecondsDelta) * 0.5;
• += = 지금 값에 오른쪽 계산 결과를 더해서 다시 저장해.
• (TargetWorldTimeSecondsDelta - ServerWorldTimeSecondsDelta) = "목표 시차까지 아직 얼마나 남았나"를 재는 차이.
• * 0.5 = 그 차이의 절반만 쓰기. 100% 점프가 아니라 50%만 이동해.
• ; = C++ 문장 끝.
🔁 이제 다시 보자. Target - Current로 남은 거리를 재고 → * 0.5로 절반만 잡고 → +=로 현재 delta에 더한다. 즉 "목표 시차로 한 번에 순간이동하지 말고 반 걸음만 다가가기"야.

"목표 − 현재"의 절반만 이동해. 지금 delta가 3.0인데 목표가 3.4면, 3.4로 점프하는 게 아니라 3.2(절반)까지만 가. 다음 갱신 때 또 절반, 또 절반... 목표로 스르륵 수렴해. 왜 이렇게 굼뜨게? 시계가 튀는 게 제일 나쁘거든. delta가 확 바뀌면 화면의 카운트다운이 갑자기 뒤로 갔다 앞으로 갔다 튀어. 절반씩만 따라가면 지연 스파이크가 껴도 부드럽게 흡수돼. (단, 맨 처음 한 번은 비교할 이전값이 없으니 == 0.0 가지에서 목표값을 그냥 통째로 받아.)

이 네 계단을 통과한 결과가 ServerWorldTimeSecondsDelta에 쌓여. 그리고 이 변수는 복제 안 돼. 순전히 클라가 자기 안에서 굴린 값이야.

우리 서버랑 붙여보기

조선협객전 서버 감각으로 번역하면 이래.

서버의 0.1초 타이머 = 우리 싱글스레드 액터 루프의 주기 작업. 우리 게임 서버도 메인 루프에서 "N틱마다 이거 해라" 하고 주기 작업을 돌리잖아. UE의 SetTimer(..., 0.1f, true)가 딱 그거야 — 로직 스레드가 안전하게 0.1초마다 자기 시각을 복제 변수에 꽂아. 여기서 중요한 게 ROLE_Authority 가드야. 우리로 치면 "이 처리는 서버 권위 코드에서만 돈다"는 거고, 클라는 이 경로를 아예 안 타. UE는 같은 클래스(AGameStateBase)를 서버·클라가 공유하면서 역할(role)로 코드를 갈라 — 우리가 서버/클라 프로젝트를 물리적으로 나눈 걸, UE는 한 클래스 안에서 if (Authority)로 나누는 셈이지.

클라의 delta 계산 = IOCP 워커가 아니라 "수신 후 로직" 자리. 우리 서버에서 IOCP 워커가 패킷 바이트를 긁어오면, 그 자리에서 게임 로직을 돌리지 않고 파싱만 해서 로직 처리로 넘기잖아. UE의 OnRep_... 콜백도 똑같아 — 소켓에서 바이트를 뜯는 저수준 수신이 아니라, 값이 완전히 도착하고 반영된 뒤 안전한 지점에서 불리는 콜백이야. 그 안에서 시차 스무딩 같은 상태 갱신을 해. "받는 워커 단계 ≠ 로직 반영 단계"라는 우리 서버의 분리 철학이 여기도 그대로 있어.

핵심 교훈 하나. 우리가 이벤트 종료 시각 같은 걸 클라에 내려줄 때 "서버가 시차를 계산해서 클라에 주자"는 유혹에 빠지기 쉬운데, UE의 답은 반대야. 서버는 자기 절대 시각만 성실히 방송하고, 시차 보정은 각 클라가 자기 지연 특성에 맞춰 스스로 한다. 서버는 남의 네트워크 사정을 모르니까. 이게 확장성에도 유리해 — 서버는 클라 수가 만 명이든 delta 만 개를 관리할 필요 없이, 변수 하나만 방송하면 끝이거든.

마무리

  • 서버는 0.1초마다 자기 raw 시각을 복제 변수에 꽂아 방송할 뿐, 시차는 계산 안 한다.
  • 클라는 값이 도착할 때마다 "받은값 − 내 시각"으로 delta를 뽑고, 누적 평균 + 절반 보간으로 튀지 않게 다듬어 보관한다. 이 delta는 복제되지 않는다.
  • 서버 시각이 필요하면 GetServerWorldTimeSeconds() = 내 로컬 시각 + delta로 스스로 계산한다. 매번 물어보지 않는다.
막히면 → repnotify (값 도착 시 콜백이 어떻게 자동으로 불리나), lifetime-props (DOREPLIFETIME이 뭘 하나), server-replicate-actors (복제 변수가 어떻게 클라로 날아가나)
다음 → lag-compensation (이렇게 맞춘 서버 시각으로 "그때 그 순간"의 히트를 어떻게 되감아 판정하나)

Q1. 클라가 서버 시각이 궁금하면 그냥 매번 물어보면 되는데, 서버 시간 동기(server time sync)가 왜 따로 필요한가요?

답 보기
이벤트 카운트다운·쿨타임을 매 프레임 그리려면 초당 수십 번 물어야 하거든 — 뉴욕 친구한테 5분마다 시간 물어보는 꼴이야. 게다가 묻는 사이에도 시간은 흐르고 답이 오는 데 지연도 껴. 그래서 처음에 "시차(delta) = 몇 초" 하나만 알아내서 내 시계에 더해 쓰는 방식으로 풀어. 계속 안 묻고 로컬시각 + delta로 서버 시각을 추정하는 거지.

↳ 애초에 서버랑 클라 시계는 왜 안 맞나요?

답 보기
둘 다 "레벨 시작 후 흐른 초"를 세는데 출발점이 완전히 달라. 서버는 새벽에 켰고 클라는 방금 접속했으니까. 게다가 네트워크 지연도 껴 — 서버가 "지금 100.0초야" 하고 쏜 순간, 클라에 도착하면 이미 100.05초야. 그래서 그냥 raw 초를 받아 쓰면 안 되고 시차를 계산해서 보정해야 해.

Q2. 그 시차(delta)를 서버가 계산해서 클라한테 딱 내려주면 제일 간단하지 않나요?

답 보기
반전인데, 서버는 delta를 계산하지도 내려주지도 않아. 서버가 클라가 몇 초짜리 시계를 들고 접속했는지, 지연이 얼마인지 모르거든. 클라마다 접속 시점·지연이 다 달라서 시차도 제각각이라, 서버가 남의 시차를 대신 못 구해. 만 명이면 시차 만 개를 서버가 떠안는 꼴이고. 그래서 서버는 자기 raw 시각만 방송하고, 시차는 각 클라가 "받은값 − 내 시각"으로 스스로 빼. 확장성에도 유리해 — 서버는 변수 하나만 방송하면 끝.

↳ 서버가 그 raw 시각을 클라로 어떻게 보내나요? 소켓 코드가 있나요?

답 보기
없어. 그냥 복제 변수(ReplicatedWorldTimeSecondsDouble)에 대입하기만 해. 그럼 UE 리플리케이션이 "값 바뀌었네" 하고 알아서 클라들로 실어 날라. 서버는 0.1초마다(ROLE_Authority일 때만) 자기 월드 시각을 그 변수에 꽂는 게 전부고, "보내라"는 명령도 소켓도 안 건드려. DOREPLIFETIME으로 등록해둔 덕분이야.

Q3. 클라는 "받은값 − 내 시각"을 그냥 delta로 바로 쓰면 안 되나요?

답 보기
안 돼. 네트워크 지연이 매번 들쭉날쭉이라 그 한 방울은 노이즈투성이거든. 그대로 쓰면 delta가 확 튀고, 화면 카운트다운이 뒤로 갔다 앞으로 갔다 덜컹거려. 그래서 두 단계로 눌러 — ① 여러 샘플을 누적 평균(250개 넘으면 접고 리셋해서 오래된 기억은 흘려보냄), ② 목표로 한 번에 안 뛰고 "목표−현재의 절반"만 다가가는 스무딩 보간. 시계는 튀는 게 제일 나쁘거든.

↳ 절반씩만 따라가면 굼떠 보이는데, 왜 그렇게 하나요?

답 보기
지연 스파이크 한 방에 delta가 확 바뀌면 화면 시계가 튀는데, 그게 매번 목표로 순간이동하는 것보다 훨씬 나빠. delta가 3.0인데 목표가 3.4면 3.2까지만 가고, 다음에 또 절반, 또 절반... 목표로 스르륵 수렴해. 이러면 지연이 껴도 부드럽게 흡수돼. 정확도를 조금 늦게 얻는 대신 안정성을 사는 교환이야. (단 맨 처음 한 번은 비교할 이전값이 없으니 목표값을 통째로 받아.)

Q4. 이 delta도 서버가 관리하는 복제 변수인가요?

답 보기
아니, delta(ServerWorldTimeSecondsDelta)는 복제 안 돼. 순전히 클라가 자기 안에서 굴린 값이야. DOREPLIFETIME 목록에 raw 시각만 있고 delta는 없어 — 이 한 줄이 "서버는 raw 시각만 방송, delta는 클라가 만든다"를 증명해. 그리고 GetServerWorldTimeSeconds()는 내 로컬시각 + delta로 답하니까, 서버에선 delta가 0이라 자기 진짜 시각이 나오고 클라에선 서버랑 거의 같은 시각이 나와. 서버든 클라든 같은 답이라 리스폰 타이머 같은 걸 양쪽에서 일관되게 그릴 수 있어.

🎯 원리 한 줄 요약

서버는 자기 시각만 0.1초마다 방송하고, 클라가 "받은 서버시각 − 내 로컬시각 = delta"를 스스로 계산·스무딩해서 들고 있다가, 로컬시각 + delta로 서버 시각을 매번 물어보지 않고 추정한다.
