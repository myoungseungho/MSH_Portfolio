보낼 때 — 송신 콜체인

언리얼 네트워크 · 06 / 43

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "내가 만든 데이터 한 덩어리가 어떤 계단을 밟아 소켓까지 걸어가는지, 그리고 언제 진짜로 소켓을 때리는지(Flush)"가 머릿속에 그려질 거야.
receive-callchain의 자매편이야. 저긴 "상자를 받아 까는 길", 여긴 "상자를 싸서 내보내는 길". 방향만 반대고 뼈대는 거울처럼 대칭이야.

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 "패킷 보내기"가 그냥 send() 한 번으로 끝나지 않는다는 걸 알아. CChosunPlayer가 움직였다고 바로 SP_Move를 때리고, 아이템 먹었다고 바로 SP_ItemGet을 때리고, 채팅 하나마다 바로 소켓을 치면 일단은 쉬워 보이지.

근데 사람이 500명 되고 한 프레임에 상태 변화가 와르르 생기면 터져. IOCP 워커는 계속 WSASend 요청을 물고, 같은 플레이어 send 큐에 여러 스레드가 덤비면 락이 늘고, CM_ 처리하다 만든 응답이 어느 타이밍에 밖으로 나갔는지도 흐려져. 초딩식으로 말하면 편지 한 통마다 우체국에 뛰어가는 꼴이라, 다리가 먼저 부러진다.

그래서 제대로 된 서버는 "보낼 것 만들기"와 "진짜 소켓 치기"를 분리해. 게임 로직은 단일스레드 구간에서 SP_* 같은 논리 데이터들을 차곡차곡 쌓고, 네트워크 쪽은 정해진 순간에 묶어서 내보내야 해. 그래야 락도 줄고, 프레임 단위 순서도 읽히고, "왜 이 패킷이 지금 나갔지?"를 추적할 수 있어.

언리얼도 같은 문제를 만났고, 그 답이 이번 챕터의 송신 콜체인이야. Bunch는 보낼 일거리, SendBuffer는 임시 우체통, FlushNet은 우체부가 걷어가는 순간, LowLevelSend는 진짜 소켓 write야. 핵심은 "Bunch를 만들었다"가 곧 "소켓을 때렸다"가 아니라는 것.

이걸 지금 배우는 이유도 분명해. 앞의 receive-callchain에서 바깥에서 들어온 상자를 어떻게 까는지 봤다면, 이번에는 우리가 만든 상자를 어떻게 싸서 밖으로 보내는지 보는 차례야. 이 길을 잡아야 뒤에서 Bunch와 Packet, reliable/Ack, Tick flush, 실제 소켓 구현을 볼 때 "아, 지금은 쌓는 중이구나"와 "여기가 진짜 발사구나"를 구분할 수 있어.

0. 먼저 비유부터 — 집 앞 우체통

편지 부칠 때 생각해봐. 편지 한 통 쓸 때마다 우체국까지 뛰어가진 않잖아? 집 앞 우체통에 툭 넣어두면, 우체부가 정해진 시간에 와서 한꺼번에 걷어간다.

UE 송신도 딱 이거야.

  • 편지 한 통 = Bunch(번치). "이 액터 좌표 바뀌었어", "이 RPC 호출해" 같은 논리적 데이터 한 덩어리.
  • 우체통 = SendBuffer. 편지를 일단 쌓아두는 비트 버퍼.
  • 우체부가 걷어감 = FlushNet. 쌓인 걸 봉투(패킷) 하나로 봉해서 밖으로 내보냄.
  • 트럭이 도로를 달림 = LowLevelSend. 실제 UDP 소켓 write.

핵심 직관 하나만 먼저 박아두자.

매 Bunch마다 소켓을 때리는 게 아니다. 우체통(SendBuffer)에 모았다가, 정해진 순간에 한 번에 밀어낸다.

왜? 편지 100통을 100번 뛰어가면 다리 부러진다(= syscall 100번 = 느림). 모아서 트럭 한 번이 훨씬 싸다. 게임 서버 하는 너라면 이 감각 이미 있지? Nagle 끄고 프레임 단위로 배칭하는 그거랑 같은 동기야.

그리고 이 챕터의 진짜 질문은 이거 하나야:

"정해진 순간"이 대체 언제냐?

이걸 실제로 구현한 함수들을 하나씩 밟아보자.

용어 두 개만 미리 깔고 갈게. 자세한 건 → bunch-vs-packet
• 패킷(Packet): UDP 한 방으로 나가는 바이트 덩어리 = "봉투".
• 번치(Bunch): 그 봉투 안에 담기는 논리적 데이터 조각 = "편지". 봉투 하나에 편지 여러 통.

지금부터 진짜 엔진 경로와 코드가 나온다. 겁먹지 마 — 박스는 길어 보여도 "쌓기 → 기다리기 → Flush" 세 단어만 붙잡고 보면 된다.

🌱 이 개념은 왜 생겼나 — 번치(Bunch)
• 원래 구조: 보낼 게 생기면 그냥 바이트로 만들어 소켓에 바로 던지면 되잖아? "좌표 바뀜"이든 "RPC 호출"이든 그때그때 써서 보내.
• 그런데 문제: 봉투(패킷) 하나에 좌표·RPC·채팅이 뒤죽박죽 섞여 들어가면, 받는 쪽이 "여기부터 여기까지가 좌표 편지, 그다음이 RPC 편지"를 어떻게 잘라? 게다가 어떤 편지는 잃으면 안 되고(아이템) 어떤 건 잃어도 되는데(옛 좌표), 바이트로 뭉개면 골라낼 수가 없어.
• 그래서 필요한 것: 보낼 걸 "논리적 편지 한 통" 단위로 묶자. 각 편지에 채널·크기·신뢰성 표시를 붙여서. → 이게 번치(Bunch)야. 봉투(Packet) 하나에 편지(Bunch) 여러 통 — 그래서 잘라 읽고, 골라 등기 보낼 수 있어.

2. 잠깐, 맞춰봐 (예측-검증)

Bunch를 버퍼에 쓰려고 커넥션이 버퍼 기록을 시작했어. 순서상 뭐가 먼저 일어날까?

1. 일단 데이터를 버퍼에 쓴다 → 다 쓰고 나서 "어라, 넘쳤네?" 확인한다.
2. 쓰기 전에 "이거 지금 버퍼에 들어가?" 먼저 확인한다 → 안 되면 비우고(Flush) 쓴다.

게임 서버 감각이면 1번이 자연스러워 보여. "일단 memcpy 하고 사이즈 체크" 패턴 많이 쓰니까.

...근데 정답은 2번이야. SendRawBunch가 버퍼에 손대기 직전 코드를 봐.

[스니펫 1] 헤더 준비(Prepare) 먼저, 그다음 TimeSensitive 세팅, 그다음 기록 — NetConnection.cpp:4482-4492

PrepareWriteBitsToSendBuffer(BunchHeaderBits, BunchBits); // We want to mark the packet in which we write the data as TimeSensitive // Note: we want to mark the packet as TimeSensitive here, as PrepareWriteBitsToSendBuffer might flush the packet TimeSensitive = 1; // Report bunch UE_NET_TRACE_END_BUNCH(OutTraceCollector, Bunch, Bunch.ChName, 0, BunchHeaderBits, BunchBits, BunchCollector); // Write the bits to the buffer and remember the packet id used Bunch.PacketId = WriteBitsToSendBufferInternal(SendBunchHeader.GetData(), BunchHeaderBits, Bunch.GetData(), BunchBits, EWriteBitsDataType::Bunch);
🔤 기호 사전 — PrepareWriteBitsToSendBuffer(...) → TimeSensitive = 1 → WriteBitsToSendBufferInternal(...)
• PrepareWriteBitsToSendBuffer(...) = "쓰기 전에 우체통 자리부터 확인해" 하는 준비 함수. 실제 데이터를 아직 넣는 단계가 아니야.
• // = 코드가 아니라 사람에게 남기는 설명 메모. 컴파일러는 이 줄을 실행하지 않아.
• TimeSensitive = 1 = "이번 프레임에 보낼 게 생겼다"는 깃발을 켬. 1은 참/켜짐으로 보면 돼.
• Bunch.PacketId = Bunch라는 편지에 붙은 PacketId 칸. 점(.)은 "그 상자 안의 칸"을 꺼내는 표시야.
• GetData() = 안에 든 진짜 바이트/비트 시작 주소를 꺼내오는 함수.
• EWriteBitsDataType::Bunch = "이번에 쓰는 데이터 종류는 Bunch야"라는 이름표. ::는 "~안에 있는 이름"이라고 읽어.
🔁 이제 다시 보자. PrepareWriteBitsToSendBuffer(...)(자리 확인) → TimeSensitive = 1(이번 프레임 보낼 것 있음 표시) → WriteBitsToSendBufferInternal(...)(헤더와 Bunch 본문을 SendBuffer에 기록). 이어 읽으면 "먼저 들어갈 자리를 확인하고, 보낼 깃발을 세운 뒤, 실제 비트를 우체통에 쌓는다."

Prepare...(자리 확보) → ...Internal(실제 기록) 순서지? 쓰기 전에 자리 확보. 왜냐면 반쯤 쓰다가 "넘쳤네" 하고 되돌리는 건 비트 스트림에선 지옥이거든. 이게 반전 하나.

그리고 여기서 이 챕터 최고 중요 한 줄을 만나. 가운데 TimeSensitive = 1;. "이번 프레임에 보낼 게 생겼다"는 깃발이야. 주석도 친절하게 설명해 — *Prepare가 패킷을 flush해버릴 수 있으니, 그 전에 이 깃발부터 세운다*고. 이 깃발이 §3의 주 경로(C)를 여는 열쇠야. 지금은 "Bunch 하나 썼으면 이 깃발이 선다"만 기억해.

🌱 이 개념은 왜 생겼나 — Flush(모았다 한 번에 보내기)
• 원래 구조: 편지(Bunch) 한 통 만들 때마다 곧장 소켓에 send()를 때리면 제일 간단해. 만들었으니 바로 보낸다.
• 그런데 문제: 사람 500명이 한 프레임에 좌표·채팅·전투 패킷을 와르르 쏟아내면, 편지 한 통마다 우체국까지 뛰어가는 꼴이야. send()(=커널 진입) 수천 번이면 다리부터 부러져. 조선 서버에서 WSASend를 매 패킷 거는 거랑 똑같은 낭비지.
• 그래서 필요한 것: 편지를 우체통(SendBuffer)에 모아뒀다가, "정해진 순간"에 트럭 한 번으로 걷어가자. → 그 걷어가는 순간이 Flush야. 문제는 "정해진 순간이 언제냐" — 그 답이 이 장의 방아쇠 4개.

3. Flush는 대체 언제 터지나 — 4개의 방아쇠

이 챕터의 진짜 핵심. §0의 그 질문 "정해진 순간이 언제냐"의 답이야. Flush(우체부가 걷어가기)는 4가지 상황에서 터진다. 전부 소스 확인됨.

트리거 (A) — "쓰고 났더니 딱 꽉 찼다" → 즉시 비운다

[스니펫 2] 버퍼가 꽉 차면 즉시 flush — NetConnection.cpp:4334-4342

// Flush now if we are full if (GetFreeSendBufferBits() == 0 #if !UE_BUILD_SHIPPING || CVarForceNetFlush.GetValueOnAnyThread() != 0 #endif ) { FlushNet(); }
🔤 기호 사전 — if (GetFreeSendBufferBits() == 0 ... ) { FlushNet(); }
• if = "만약 ~라면". 괄호 안 조건이 맞을 때만 중괄호 안을 실행해.
• GetFreeSendBufferBits() = SendBuffer에 아직 남은 빈 자리(비트 수)를 물어보는 함수.
• == 0 = "0과 같다"는 비교. 남은 자리가 딱 하나도 없다는 뜻이야.
• #if !UE_BUILD_SHIPPING ... #endif = 특정 빌드에서만 끼워 넣는 컴파일 조건문. !는 "아님"이라서 여기선 Shipping 빌드가 아닐 때만 디버그 조건을 본다는 뜻.
• || = "또는". 앞 조건이 맞거나 뒤 조건이 맞으면 전체가 맞아.
• != 0 = "0이 아니다". 스위치가 꺼져 있지 않으면 켜진 걸로 보는 식이야.
• FlushNet(); = 지금까지 쌓은 SendBuffer를 패킷으로 봉해서 내보내는 함수 호출.
🔁 이제 다시 보자. if(만약) → GetFreeSendBufferBits() == 0(남은 공간이 0이면) → || CVarForceNetFlush... != 0(또는 디버그 강제 flush가 켜졌으면) → FlushNet()(바로 내보냄). 한 줄로 "우체통이 꽉 찼거나 강제 스위치가 켜졌으면 즉시 비운다."

SerializeBits로 비트를 다 쌓고 났더니 남은 공간이 정확히 0이면 그 자리에서 바로 보내버린다. 우체통이 꽉 차서 더 못 넣으니까. (CVarForceNetFlush는 디버그용 강제 flush 스위치 — "무조건 지금 보내" 하고 싶을 때 켜는 거. 실무 흐름엔 신경 안 써도 돼.)

트리거 (B) — "이거 지금 버퍼에 안 들어가" → 먼저 비우고 새 패킷 연다

[스니펫 3] 다음 데이터가 현재 패킷에 안 들어가면 flush — NetConnection.cpp:4256-4262

const int32 TotalSizeInBits = SizeInBits + ExtraSizeInBits; // Flush if we can't add to current buffer if ( TotalSizeInBits > GetFreeSendBufferBits() ) { FlushNet(); }
🔤 기호 사전 — const int32 TotalSizeInBits = SizeInBits + ExtraSizeInBits;
• const = 한 번 정하면 이 줄 아래에서 바꾸지 않겠다는 약속.
• int32 = 정수를 담는 칸. 32비트 크기의 숫자라고 보면 돼.
• TotalSizeInBits = 이번에 넣으려는 전체 크기. 데이터 본문 크기와 추가 헤더 크기를 더한 값이야.
• SizeInBits + ExtraSizeInBits = "본문 비트 수 + 덤으로 필요한 비트 수".
• > = 왼쪽이 오른쪽보다 크면 참.
• GetFreeSendBufferBits() = 지금 우체통에 남은 빈자리.
🔁 이제 다시 보자. TotalSizeInBits(이번에 넣을 총 크기)가 GetFreeSendBufferBits()(남은 자리)보다 크면 → FlushNet()으로 먼저 비운다. 즉 "새 편지가 지금 우체통에 안 들어가면, 기존 편지부터 보내고 새 우체통을 연다."

새 편지가 지금 우체통에 안 들어갈 만큼 크면? 지금 있는 걸 먼저 트럭에 실어 보내고(Flush), 빈 우체통에 새 패킷 헤더를 열어 담는다. PrepareWriteBitsToSendBuffer 안이라, 아까 스니펫 1에서 TimeSensitive=1을 *먼저* 세운 이유가 이거야 — 여기서 flush가 튀어도 깃발은 안전하게 서 있게.

트리거 (C) — 프레임당 1회 · 주 경로 ★

여기가 실전에서 편지 대부분이 나가는 길이야. UNetConnection::Tick 끝에서 매 프레임 돈다.

[스니펫 4] 프레임 끝 flush — NetConnection.cpp:4920-4930

// Flush. if ( TimeSensitive || (Driver->GetElapsedTime() - LastSendTime) > Driver->KeepAliveTime) { bool bHandlerHandshakeComplete = !Handler.IsValid() || Handler->IsFullyInitialized(); // Delay any packet sends on the server, until we've verified that a packet has been received from the client. if (bHandlerHandshakeComplete && HasReceivedClientPacket()) { FlushNet(); } }
🔤 기호 사전 — if ( TimeSensitive || ... )
• TimeSensitive = "이번 프레임에 보낼 게 있다"는 깃발. 참이면 flush 후보가 돼.
• Driver->GetElapsedTime() = 드라이버한테 지금까지 흐른 시간을 물어봄. ->는 "가리키는 객체한테 시킨다"는 화살표야.
• LastSendTime = 마지막으로 보낸 시각.
• > = 왼쪽 시간이 오른쪽 기준보다 커졌는지 비교.
• Driver->KeepAliveTime = 아무 데이터가 없어도 연결 확인용 패킷을 보내야 하는 최대 대기 시간.
• bool = 참/거짓만 담는 스위치 칸.
• !Handler.IsValid() = Handler가 없으면. !는 "아님"이야.
• || = 또는, && = 그리고. &&는 양쪽이 다 참이어야 지나가.
• HasReceivedClientPacket() = 클라이언트한테서 패킷을 받은 적이 있는지 확인하는 함수.
🔁 이제 다시 보자. TimeSensitive(보낼 것 있음) 또는 keepalive 시간이 지났고 → 핸드셰이크가 끝났고 → 클라이언트 패킷도 받은 상태면 → FlushNet(). 그래서 이 코드는 "보낼 준비와 연결 준비가 둘 다 됐을 때, 프레임 끝에서 우체통을 비운다."

TimeSensitive가 참이면 flush. 그런데 §2에서 봤듯 Bunch를 하나라도 쓰면 SendRawBunch에서 TimeSensitive=1이 된다. 그러니 보통은 이렇게 흘러:

  • 한 프레임 동안 게임 로직이 Bunch 여러 개를 우체통에 쌓기만 함 (트리거 A/B에 안 걸리면 소켓 안 감).
  • 프레임 끝 Tick에서 TimeSensitive가 서 있으니 → 한 방에 flush.

즉 "매 프레임 틱 끝에 모아서 한 번에 나간다"가 정상 경로야. §0 우체통 비유의 "정해진 시간에 우체부가 옴"이 바로 이 Tick이야. 그리고 보낼 게 하나도 없어도 KeepAliveTime이 지나면 keepalive 패킷을 한 번 flush해서 연결이 살아있음을 알린다. (틱 자체의 큰 그림은 → netdriver-tick)

트리거 (D) — 즉시성/종료 경로에서 명시적 강제 flush

특수 상황에선 코드가 그 자리에서 직접 FlushNet()을 부른다. 채널 닫기·partial 분할 중(DataChannel.cpp:1444, FlushNet(true)), reliable 버퍼 오버플로로 연결 종료(NetDriver.cpp:3158, FlushNet(true)), 리플레이 InternalAck(NetDriver.cpp:3320, FlushNet()), 서버 셧다운(NetDriver.cpp:2429은 FlushNet(), :2441은 FlushNet(true)) 등. 오버플로·종료처럼 반드시 내보내야 하는 급한 경우엔 시뮬레이션(지연·손실 흉내)까지 무시하는 FlushNet(true)를 쓴다. "지금 당장, 프레임 안 기다리고 내보내야 하는" 상황이야. 뼈대만 알아두면 돼.

정리 — 우체통은 웬만해선 안 나간다.

트리거언제성격
(A) 꽉 참쓰고 나니 Free==0어쩔 수 없이, 프레임 도중
(B) 안 들어감다음 데이터 > 남은 공간어쩔 수 없이, 프레임 도중
(C) 프레임 끝TimeSensitive / keepalive정상 · 대부분 여기로
(D) 강제종료·오버플로·리플레이특수, 명시적 FlushNet()/FlushNet(true)

핵심: SendBunch는 "버퍼에 쌓기"까지만 한다. 실제 소켓 송신은 대부분 (C) Tick 끝의 FlushNet 1회로 배칭된다. 버퍼가 넘칠 때(A/B)만 프레임 도중에도 강제로 나간다.

4. FlushNet 안쪽 — 봉투 봉하고 트럭 부른다

방아쇠가 당겨졌어. FlushNet 안에서 무슨 일이 나는지 뼈대만 보자.

[스니펫 5] FlushNet이 최종적으로 LowLevelSend 호출 — NetConnection.cpp:2436-2440

// Checked in FlushNet() so each child class doesn't have to implement this if (Driver->IsNetResourceValid()) { LowLevelSend(SendBuffer.GetData(), SendBuffer.GetNumBits(), Traits); }
🔤 기호 사전 — LowLevelSend(SendBuffer.GetData(), SendBuffer.GetNumBits(), Traits);
• Driver->IsNetResourceValid() = 네트워크 자원이 아직 유효한지 확인. 소켓/드라이버가 죽은 상태면 보내면 안 되니까 먼저 본다.
• SendBuffer.GetData() = SendBuffer 안에 쌓인 실제 데이터 시작점을 꺼냄.
• SendBuffer.GetNumBits() = SendBuffer에 몇 비트가 쌓였는지 꺼냄.
• Traits = 이 패킷에 붙는 부가 정보 상자. 어떤 성격의 전송인지 같이 넘겨준다.
• LowLevelSend(...) = 이제 진짜 아래 계층으로 "이 바이트들을 내보내" 하고 넘기는 호출.
🔁 이제 다시 보자. IsNetResourceValid()로 보낼 수 있는 상태인지 확인하고 → SendBuffer.GetData()와 GetNumBits()로 "무엇을, 얼마나" 보낼지 꺼내 → LowLevelSend(...)에 넘긴다. 즉 "봉투가 준비됐고 도로도 살아 있으면, 트럭에게 짐을 넘긴다."

읽는 순서대로 뼈대만:

  1. 보낼 게 있냐 판단 — 쌓인 비트가 있거나(GetNumBits), 보낼 ack가 있거나, keepalive 시간이 됐으면 진행. 아무것도 없으면 헛트럭 안 부른다.
  2. 봉투 봉하기 — 패킷 끝이라는 종료 비트를 마지막에 박아. 받는 쪽이 "여기까지가 이 패킷"이라고 알게. → receive-callchain에서 이 마지막 1비트를 되읽어 길이를 역산해(수신 §2의 그 트릭이 여기서 심어지는 거야). 송신·수신이 거울처럼 맞물리지.
  3. LowLevelSend(...) — 트럭 출발. 실제 소켓 write.

그리고 3번 — 아까 말했듯 여기 UNetConnection::LowLevelSend엔 본문이 없어(순수 가상).

[스니펫 6] LowLevelSend는 순수 가상 — NetConnection.h:1045-1046

virtual void LowLevelSend(void* Data, int32 CountBits, FOutPacketTraits& Traits) PURE_VIRTUAL(UNetConnection::LowLevelSend,);
🔤 기호 사전 — virtual void LowLevelSend(void* Data, int32 CountBits, FOutPacketTraits& Traits)
• virtual = 자식 클래스가 자기 방식으로 갈아끼울 수 있는 함수라는 표시.
• void = 이 함수는 호출한 쪽에 결과값을 돌려주지 않아.
• void* Data = 타입을 아직 정하지 않은 원시 데이터 주소. "바이트 덩어리 시작점"으로 보면 돼.
• int32 CountBits = 보낼 데이터 길이. 바이트가 아니라 비트 수로 센다.
• FOutPacketTraits& Traits = 패킷 성격표를 원본으로 넘김. &라서 복사본이 아니라 같은 상자를 같이 보는 거야.
• PURE_VIRTUAL(...) = 부모에는 본문이 없고, 자식이 반드시 실제 일을 채워야 한다는 UE식 표시.
🔁 이제 다시 보자. virtual(자식이 구현) → void(돌려줄 값 없음) → LowLevelSend(void* Data, int32 CountBits, FOutPacketTraits& Traits)(데이터 시작점, 비트 길이, 패킷 성격표를 받음) → PURE_VIRTUAL(부모 본문 없음). 이어 읽으면 "UNetConnection은 입구만 정하고, 진짜 소켓 전송은 자식 연결 클래스가 맡는다."

UIpConnection 같은 자식이 진짜 sendto를 해. 스니펫 5의 주석도 *"각 자식 클래스가 매번 구현 안 해도 되게 FlushNet에서 체크한다"*고 되어 있지 — 소켓 유효성 검사 같은 공통 처리는 부모가 한 번에 하고, 진짜 write만 자식에게 맡기는 구조야.

flush가 끝나면 시퀀스 번호를 올리고 통계를 갱신한 뒤, 우체통을 비워서 다음 편지 받을 준비를 해 → InitSendBuffer. malloc 새로 안 하고 Reset만 한다(커넥션당 우체통은 딱 1개니까 재사용). 매 패킷마다 할당 안 생기는 이유야 — 게임 서버에서 alloc 신경 쓰는 너라면 이 디테일 좋아할 거다.

5. 초보가 헷갈리는 용어

  • Bunch(번치): 한 채널(액터/컨트롤)이 보내는 논리적 데이터 묶음. RPC 하나, 프로퍼티 갱신 한 뭉치가 각각 Bunch. 여러 Bunch가 모여 한 Packet이 됨. (FOutBunch)
  • SendBuffer: 아직 소켓으로 안 나간, 이번 패킷에 쌓이는 중인 비트 누적 버퍼(FBitWriter). Bunch들이 SerializeBits로 여기 append됨. FlushNet 때 통째로 나가고 InitSendBuffer로 리셋.
  • FlushNet: "지금까지 쌓은 SendBuffer를 패킷으로 확정해 LowLevelSend로 내보내라." send의 실제 발사 시점.
  • TimeSensitive: "이번 프레임에 보낼 게 생겼다"는 깃발. SendRawBunch에서 1로 서고(:4486), Tick 끝에서 참이면 FlushNet. 매 flush마다 0으로 리셋. 트리거 (C) 주 경로의 스위치.
  • Partial Bunch(부분 번치): 한 Bunch가 단일 패킷 최대치(MAX_SINGLE_BUNCH_SIZE_BITS)를 넘으면 여러 조각으로 쪼갠 것. bPartialInitial/bPartialFinal로 첫/끝 조각 표시. 상세 → datachannel-nextbunch
  • LowLevelSend: 콜체인 최하단. PacketHandler 처리 후 실제 소켓으로 바이트를 내보내는 가상 함수. 실 구현(UIpConnection)은 이 학습 트리 미포함.

6. 우리 서버랑 비교 (IOCP + 싱글스레드 액터)

우리 조선협객전 서버 감각으로 매핑하면 이래.

UE 네트워크우리 서버 (IOCP + 싱글스레드)메모

그리고 배칭 감각 — 우리가 Nagle 끄고 프레임 단위로 send 묶는 그 최적화가, UE에선 TimeSensitive + Tick flush(트리거 C)로 엔진에 이미 박혀 있는 거야. 개념이 같으니 낯설지 않지?

7. 여기까지의 뼈대 (한 번 더 압축)

채널: 큰 Bunch 쪼개기 (SendBunch) ↓ 커넥션: 헤더 조립 + TimeSensitive=1 (SendRawBunch) ↓ 버퍼에 비트 누적 (WriteBitsToSendBufferInternal / SerializeBits) ↓ ← 여기서 대부분 멈춤. 소켓 안 감. 우체통에만 쌓임. 언제 Flush? (A) 꽉 참 · (B) 안 들어감 · (C) 프레임 끝(주경로) · (D) 강제 ↓ FlushNet: 종료비트 박고 봉투 마감 (FlushNet) ↓ 소켓 write (LowLevelSend — 자식 클래스) ↓ 버퍼 리셋 후 다음 준비 (InitSendBuffer)
  • 막히면 → bunch-vs-packet (Bunch랑 패킷이 왜 다른 물건인지)
  • 막히면 → netconnection-overview (커넥션이 뭘 들고 있는 객체인지)
  • 다음 → receive-callchain (지금 봉해 보낸 걸 반대편이 어떻게 까는지 — 종료 비트 되읽기)
  • 곁가지: 조각내기 상세 datachannel-nextbunch / ack·재전송 reliability-ack / 정기 flush 타이밍 netdriver-tick / 소켓 write 실물 ipnetdriver-socket

🎯 원리 한 줄 요약

Bunch는 소켓으로 바로 안 간다 — SendBuffer에 비트로 쌓였다가, "꽉 찰 때(A)·안 들어갈 때(B)·프레임 끝 TimeSensitive(C, 주경로)·강제(D)" 넷 중 하나가 걸려야 FlushNet이 종료비트로 봉해 LowLevelSend로 밀어낸다. 즉, 프레임 단위로 모았다가 한 번에.
← 이전Channel 종류: Control / Actor / Voice다음 →안 잃게: 시퀀스·ack·재전송
