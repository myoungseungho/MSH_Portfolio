터졌을 때 보는 법: 네트워크 디버깅

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이런 날을 꼭 만나. 로그에는 CM_ATTACK도 정상으로 왔고, SP_MOVE도 정상으로 보냈고, CChosunPlayer 좌표도 서버에서는 맞아. 그런데 유저는 "때렸는데 안 맞았어요", "순간이동했어요"라고 해. 코드만 보면 멀쩡한데 게임은 이상한, 제일 찝찝한 버그야.

왜 이럴까? 네 자리의 네트워크는 너무 깨끗하거든. IOCP 워커는 패킷을 바로 받고, 단일스레드 로직 큐도 순서대로 돌고, 락도 안 꼬여. 그런데 유저 집에서는 200ms 늦게 오고, 패킷 몇 개는 사라지고, 순서도 가끔 뒤집혀. 그러면 서버 코드가 맞아도 클라는 뒤늦게 보정되고, 화면에서는 캐릭터가 툭 튀어 보일 수 있어.

이걸 볼 도구가 없으면 계속 감으로 싸우게 돼. "아마 지연 때문일걸?" 하고 Sleep()을 박아보거나, 패킷 큐에서 대충 몇 개 버려보지만, 테스트할 때마다 조건이 달라져. 몇 ms가 늦었는지, 몇 %가 버려졌는지, 어느 NetDriver에 적용됐는지 숫자로 못 보면 버그를 잡은 게 아니라 운 좋게 지나간 거야.

그래서 이 챕터의 답이 네트워크 툴링이야. NetEmulation은 나쁜 네트워크를 만드는 스위치고, Network Profiler는 어디로 얼마나 흘렀는지 보는 계측기고, stat net은 지금 화면에서 바로 보는 계기판이야. 우리 서버에서 지연·드롭 테스트 코드를 손으로 심던 일을 UE는 엔진 기능으로 준비해둔 셈이지.

왜 지금 배우냐면, 이제 너는 연결·송수신·채널·reliable·복제가 대충 어디를 지나가는지 봤어. 길을 모를 때 도구를 보면 그냥 버튼 이름 외우기가 되지만, 길을 알고 나서 도구를 보면 "아, 이 스위치가 FlushNet 뒤쪽 문제를 재현하겠구나" 하고 바로 감이 와. 이 챕터는 앞에서 배운 네트워크 지도를 실제 버그 재현용 실험대로 바꾸는 자리야.

들어가기 전에

네트워크 버그는 딱 두 종류로 나뉘어.

하나는 재현되는 버그. 언제 눌러도 똑같이 터져. 이건 그냥 코드 읽으면 잡혀.

문제는 다른 하나야. "가끔" 터지는 버그. 유저는 "순간이동했어요", "때렸는데 안 맞았어요", "캐릭터가 뒤로 튀어요"라고 하는데, 내 자리(랜선 빵빵한 사무실)에서는 절대 재현이 안 돼. 왜? 네트워크가 너무 좋아서. 유저 집 와이파이는 지연 200ms에 패킷도 5%씩 흘리는데, 내 자리는 지연 1ms에 무손실이거든.

그럼 어떻게 잡아? 답은 하나야.

나쁜 네트워크를 내 자리에서 인위적으로 만들어낸다.

"지연 200ms, 손실 5%"를 콘솔 명령 한 줄로 흉내 내는 거지. 랜선은 멀쩡한데 엔진이 "일부러" 패킷을 늦게 보내고, "일부러" 몇 개를 버려. 그러면 유저 집 환경이 내 자리에 재현되고, 안 잡히던 보정 버그가 눈앞에서 터져.

이걸 실제로 구현하는 게 이번 챕터의 주인공, NetEmulation(넷 에뮬레이션)이야. 그리고 "얼마나 나가고 있나"를 재는 계측기 Network Profiler, 화면에 숫자를 뿌리는 stat net까지 셋이 한 세트야.

게임 서버 프로그래머 입장에서 이건 완전 새로운 개념은 아냐. 우리도 테스트할 때 Sleep() 박아서 지연 흉내 내거나, 패킷 큐에서 일부러 drop 시켜보잖아. UE는 그걸 엔진 레벨에 정식 기능으로 박아놨다는 게 차이야. 손으로 짤 필요 없이 콘솔 한 줄이면 돼.

1) NetEmulation — 나쁜 네트워크를 만드는 스위치

개념부터

핵심 아이디어는 어이없을 만큼 단순해.

패킷을 소켓으로 진짜 보내기 직전에, 엔진이 중간에 끼어들어서 이렇게 판단해:

  • "이 패킷, 손실 흉내로 그냥 버릴까?" → PktLoss
  • "순서를 뒤섞을까?" → PktOrder
  • "지금 안 보내고 나중에 보낼까?" → PktLag

버리면 손실, 늦게 보내면 지연. 이게 전부야. 물리적으로 랜선이 나빠진 게 아니라, 소프트웨어가 "나쁜 척"을 하는 거지.

이 수치들을 담는 그릇이 PacketSimulationSettings 구조체(NetDriver.h:454)야. 여기에 PktLoss=5, PktLag=200 같은 값이 들어가면, 송신 경로가 그 값을 보고 버리거나 늦추거나 해. 이 그릇은 콘솔·.ini([PacketSimulationSettings])·커맨드라인 세 경로로 채워질 수 있어.

콘솔 명령은 어떻게 생겨나나

NetEmulation.PktLag 200 이라고 콘솔에 치면 어떻게 될까? 이 명령어들, 하나하나 손으로 등록한 거 아니야. 매크로 하나로 찍어내. 이걸 봐.

지금부터 진짜 C++ 매크로가 나온다. 겁먹지 마 — 한 줄 한 줄 외우려 하지 말고, "짧은 콘솔 명령을 긴 등록 코드로 찍어내는 틀"이라고만 잡자. 낯선 기호는 코드 바로 아래에서 풀어줄게.

스니펫 1 — 콘솔 명령 자동 생성 매크로 NetEmulationHelper.cpp:341-351

#define BUILD_NETEMULATION_CONSOLE_COMMAND(CommandName, CommandHelp) FAutoConsoleCommandWithWorldAndArgs NetEmulation##CommandName(TEXT("NetEmulation."#CommandName), TEXT(CommandHelp), \ FConsoleCommandWithWorldAndArgsDelegate::CreateStatic([](const TArray<FString>& Args, UWorld* World) \ { \ if (Args.Num() > 0) \ { \ CreatePersistentSimulationSettings(); \ FString CmdParams = FString::Printf(TEXT(#CommandName"=%s"), *(Args[0])); \ PersistentPacketSimulationSettings.GetValue().ParseSettings(*CmdParams, nullptr); \ ApplySimulationSettingsOnNetDrivers(World, PersistentPacketSimulationSettings.GetValue()); \ } \ }));
🔤 기호 사전 — #define BUILD_NETEMULATION_CONSOLE_COMMAND(CommandName, CommandHelp) ...
• #define = "이 이름을 보면 뒤의 긴 코드로 바꿔라"라는 전처리기 약속. 컴파일 전에 글자를 바꾸는 도장 찍기야.
• \ = 매크로가 다음 줄까지 이어진다는 표시. 줄은 여러 개지만 컴파일러한테는 한 덩어리로 보여.
• ## = 두 글자를 붙여 새 이름을 만드는 풀. NetEmulation##PktLag면 NetEmulationPktLag 같은 이름이 돼.
• #CommandName = CommandName 값을 코드 이름이 아니라 문자열로 바꾸기. PktLag를 "PktLag" 글자로 만드는 버튼이야.
• TEXT(...) = UE가 문자열을 엔진이 쓰는 문자 형식으로 감싸는 포장지.
• :: = "~안에 있는 것" 표시. FString::Printf는 FString 상자 안의 Printf 기능이라고 읽으면 돼.
• [](...) { ... } = 람다. 그 자리에서 잠깐 만들어 쓰는 작은 함수야.
• const TArray<FString>& Args = 문자열 리스트를 원본 그대로 빌려온다는 뜻. 콘솔에 친 200 같은 인자가 여기 들어와.
• UWorld* World = 월드를 가리키는 포인터. 게임 세상 주소표를 넘겨받는다고 보면 돼.
• if (Args.Num() > 0) = 인자가 하나라도 있을 때만 안으로 들어가라는 문.
• *(Args[0]) = 첫 번째 인자 문자열의 속 글자를 꺼내 쓰는 표시.
• nullptr = 아무것도 안 가리키는 빈 주소표.
🔁 이제 다시 보자. #define(짧은 이름을 긴 코드로 바꿈) → NetEmulation##CommandName(명령 객체 이름 만들기) → TEXT("NetEmulation."#CommandName)(콘솔 이름 만들기) → 람다 안에서 ParseSettings와 ApplySimulationSettingsOnNetDrivers 호출. 이어 읽으면 "PktLag 같은 이름 하나를 넣으면 콘솔 명령 등록부터 설정 적용까지 자동으로 만들어주는 틀."

천천히 읽어보자. 겁먹지 마, 딱 세 줄만 이해하면 돼.

  • TEXT("NetEmulation."#CommandName) — 명령어 이름을 만들어. #CommandName이 PktLag이면 "NetEmulation.PktLag"가 돼. (#는 "글자로 바꿔라"라는 전처리기 문법이야.)
  • FString::Printf(TEXT(#CommandName"=%s"), *(Args[0])) — 네가 친 인자를 "PktLag=200" 형태 문자열로 조립해.
  • ParseSettings(...) → ApplySimulationSettingsOnNetDrivers(...) — 그 문자열을 파싱해서 설정 구조체에 넣고, 살아있는 NetDriver 전부에 적용해.

즉 매크로 한 방이 "명령어 이름 + 파싱 + 적용"을 통째로 생성하는 붕어빵 틀이야. 그리고 이 틀로 명령어들을 이렇게 찍어내:

• BUILD_NETEMULATION_CONSOLE_COMMAND(...) = 방금 위에서 만든 붕어빵 틀을 실제로 한 번 찍는 호출.
• PktLoss = 콘솔 명령 뒤에 붙을 이름 조각. 결과는 NetEmulation.PktLoss.
• "Simulates ..." = 콘솔 도움말에 보일 설명 글.
• ; = "이 한 문장 끝"이라는 마침표.

한 줄이 곧 콘솔 명령 하나야. PktLoss(손실), PktOrder(순서 뒤섞기), PktDup(중복 전송), PktLag(지연), PktLagVariance(지연 편차)... 실제 나쁜 네트워크에서 일어나는 온갖 현상을 골라서 흉내 낼 수 있어. (소스엔 이 아래로 PktIncomingLagMin/Max, PktJitter, PktBufferBloatInMS 같은 받는 쪽·지터·버퍼 부풀림까지 :360~365에 더 있어.)

맞춰봐 (예측-검증)

자 문제. NetEmulation.PktLag 200을 쳤어. 그럼 패킷이 지금 당장 안 나가고 200ms 뒤에 나가야 하잖아? 근데 엔진 입장에서 "200ms 뒤"를 어떻게 실현할까?

떠올려봐. C++엔 "이 함수를 200ms 뒤에 실행해줘" 같은 마법 스케줄러가 기본으로 없어. 그럼 어떻게...?

...

정답은 "큐에 넣고 미룬다"야. 지금 보낼 패킷을 소켓에 안 넣고, Delayed라는 배열에 짱박아 두면서 "이건 SendTime = 지금+200ms에 보낼 것"이라고 도장을 찍어. 그리고 매 틱마다 그 배열을 훑으면서 "SendTime 지난 거 있어? 있으면 지금 보내"를 반복해. 실제 코드를 보자.

스니펫 3 — PktLag: 패킷을 지연 큐에 넣고 SendTime 지정 NetConnection.cpp:2586-2594

else if (PacketSimulationSettings.PktLag) { DelayedPacket = &(Delayed.Emplace_GetRef(FDelayedPacket(SendBuffer.GetData(), SendBuffer.GetNumBits(), Traits))); // ExtraLag goes from PktLag + [-PktLagVariance, PktLagVariance] const double LagVariance = 2.0f * (FMath::FRand() - 0.5f) * double(PacketSimulationSettings.PktLagVariance); const double ExtraLag = (double(PacketSimulationSettings.PktLag) + LagVariance) / 1000.f; DelayedPacket->SendTime = CurrentTimeInS + ExtraLag; }
🔤 기호 사전 — else if (PacketSimulationSettings.PktLag) ... DelayedPacket->SendTime = ...
• else if = 앞 조건이 아니었고, 이번 조건이 맞으면 이 안으로 들어가라는 뜻.
• PacketSimulationSettings.PktLag = 설정 상자 안의 PktLag 칸. 0이면 꺼짐, 값이 있으면 지연을 흉내 내.
• Delayed.Emplace_GetRef(...) = Delayed 배열 끝에 새 패킷을 넣고, 방금 넣은 진짜 칸을 돌려받기.
• &(...) = 그 칸의 주소표를 잡기. 나중에 DelayedPacket으로 다시 만지려고 붙잡는 거야.
• FDelayedPacket(...) = "나중에 보낼 패킷" 상자를 새로 만드는 생성자 호출.
• const double = 바꾸지 않을 소수 숫자. 여기선 지연 시간을 계산한 값을 담아.
• FMath::FRand() = 0부터 1 사이 아무 숫자를 하나 뽑는 UE 함수.
• 0.5f, 2.0f, 1000.f = f가 붙은 소수 숫자. 밀리초를 초로 바꾸려고 1000으로 나눠.
• -> = 포인터가 가리키는 물건의 칸을 열기. DelayedPacket->SendTime은 지연 패킷의 발송 시각 칸.
🔁 이제 다시 보자. else if (PktLag)(지연 설정이 켜졌으면) → Delayed.Emplace_GetRef(...)(패킷을 지연 큐에 넣고) → ExtraLag(밀릴 시간을 계산해서) → SendTime = CurrentTimeInS + ExtraLag(미래 시각 도장). 한 줄로 "지금 보내지 말고, 이 시각이 되면 보내라고 큐에 맡겨두기."

봐, 그대로지?

  • Delayed.Emplace_GetRef(...) — 지금 안 보내고 Delayed 큐에 패킷을 통째로 복사해서 넣어.
  • ExtraLag — PktLag(200)에 편차를 살짝 섞어서 초 단위로 환산(/1000). 편차를 섞는 이유는 진짜 네트워크는 딱 200ms로 일정하지 않고 190~210ms처럼 흔들리거든.
  • SendTime = CurrentTimeInS + ExtraLag — "이 패킷은 이 시각에 보낼 것"이라고 미래 시각을 도장 찍어.

여기까지는 미뤄두기만 한 거야. 실제로 뒤늦게 내보내는 건 딴 데(뒤에 나옴)서 해.

손실(PktLoss)은 더 간단해 — 그냥 버려

지연이 "미뤄두기"라면, 손실은 "안 보내기"야. 확률 뽑아서 걸리면 그냥 리턴.

스니펫 4 — PktLoss: 확률로 송신 패킷을 버림 NetConnection.cpp:2629-2635

bool UNetConnection::ShouldDropOutgoingPacketForLossSimulation(int64 NumBits) const { return Driver->IsSimulatingPacketLossBurst() || (PacketSimulationSettings.PktLoss > 0 && PacketSimulationSettings.ShouldDropPacketOfSize(NumBits) && FMath::FRand() * 100.f < PacketSimulationSettings.PktLoss); }
🔤 기호 사전 — bool UNetConnection::ShouldDropOutgoingPacketForLossSimulation(int64 NumBits) const
• bool = 답이 참/거짓 둘 중 하나라는 뜻. 여기선 "버릴까?"의 답.
• UNetConnection:: = UNetConnection에 딸린 함수라는 소속 표시.
• int64 NumBits = 패킷 크기를 비트 수로 담는 큰 정수.
• const = 이 함수가 연결 객체의 상태를 바꾸지 않겠다는 약속.
• return = 계산한 답을 함수 밖으로 돌려주기.
• -> = 포인터가 가리키는 객체에게 물어보기. Driver->...는 드라이버한테 묻는 거야.
• || = 또는. 둘 중 하나만 참이어도 참.
• && = 그리고. 양쪽이 모두 참이어야 참.
• > / < = 크기 비교. PktLoss > 0은 손실 설정이 켜졌는지 보는 거야.
• FMath::FRand() * 100.f = 0~1 난수를 0~100 점수표로 바꾸기.
🔁 이제 다시 보자. return 뒤를 읽으면 Driver가 손실 폭주 중이거나(||), PktLoss가 켜져 있고(> 0) 크기도 대상이고(ShouldDropPacketOfSize) 랜덤 숫자가 손실률보다 작으면(< PktLoss) 참. 즉 "조건표와 주사위가 맞으면 이 패킷은 버린다."

FMath::FRand() * 100.f < PacketSimulationSettings.PktLoss — 이 한 줄이 핵심이야. FRand()는 0~1 난수. 거기에 100 곱하면 0~100. 그게 PktLoss(예: 5)보다 작으면 버려. 즉 100번 중 5번 꼴로 true가 나와서 그 패킷은 소켓에 안 나가. 이게 "5% 손실"의 정체야. 별거 없지?

ShouldDropPacketOfSize(NumBits)는 "이 패킷 크기가 손실 대상 범위(MinSize~MaxSize)냐"를 걸러(NetDriver.h:608). "큰 패킷만 골라 버려보기" 같은 정밀 테스트에 쓰여.

미뤄둔 걸 실제로 내보내는 순간

스니펫 3에서 큐에 넣어둔 패킷, 언제 진짜 나갈까? 매 틱 도는 UpdateDelayedPackets(NetConnection.cpp:5018)가 처리해.

스니펫 5 — 지연된 패킷을 뒤늦게 실제 송신 (PktLag 실현) NetConnection.cpp:5036-5045

else if (CurrentRealtimeSeconds > Packet.SendTime) { bSendPacket = true; } if (bSendPacket) { LowLevelSend((char*)&(Packet.Data[0]), Packet.SizeBits, Packet.Traits); Packet.bSent = true; }
🔤 기호 사전 — LowLevelSend((char*)&(Packet.Data[0]), Packet.SizeBits, Packet.Traits);
• CurrentRealtimeSeconds > Packet.SendTime = 지금 시간이 약속한 발송 시간을 지났는지 확인.
• bSendPacket = true = "이제 보내도 됨" 스위치를 켜기. b로 시작하는 이름은 보통 참/거짓 값이야.
• if (bSendPacket) = 그 스위치가 켜져 있으면 안쪽 코드를 실행.
• LowLevelSend(...) = 실제 소켓으로 패킷을 내보내는 낮은 단계 함수.
• (char*) = 이 데이터를 바이트 포인터처럼 보라고 타입을 잠깐 바꾸는 표시.
• &(Packet.Data[0]) = 패킷 데이터 배열의 첫 칸 주소를 잡기.
• Packet.SizeBits = 이 패킷이 몇 비트짜리인지 적힌 칸.
• Packet.bSent = true = "이미 보냈음" 표시를 켜기.
🔁 이제 다시 보자. CurrentRealtimeSeconds > Packet.SendTime(약속 시간이 지났으면) → bSendPacket = true(보내기 스위치 켜고) → LowLevelSend(...)(진짜 송신) → Packet.bSent = true(처리 완료 표시). 즉 "큐에서 자고 있던 패킷이 시간이 되자 소켓으로 나가는 순간."

CurrentRealtimeSeconds > Packet.SendTime — 지금 시각이 아까 도장 찍은 SendTime을 넘었어? 넘었으면 LowLevelSend로 이제야 진짜 소켓에 밀어넣어. 이 LowLevelSend가 "실제로 패킷을 내보내는 최종 함수"야(→ 송신 경로 전체는 send-callchain 참고). 아까 200ms 미뤄뒀던 패킷이 바로 여기서 뒤늦게 세상 밖으로 나가는 거지. 이 지연이 곧 유저가 느끼는 "랙"의 정체야.

⚠️ 배포 빌드엔 아예 없다

중요한 함정 하나. 위 경로 전체가 #if DO_ENABLE_NET_TEST로 감싸져 있어. 스니펫 4 바로 위 :2628에도 #if DO_ENABLE_NET_TEST가 붙어 있는 거 봤지? 이건 개발/디버그 빌드에서만 컴파일된다는 뜻이야. Shipping(배포) 빌드에선 이 코드가 통째로 사라져. 당연하지, 유저 손에 "패킷 버리는 스위치"를 쥐여주면 안 되니까. 그러니 "라이브에서 NetEmulation 왜 안 먹지?" 하고 헤매지 마. 원래 없는 거야.

콜체인 다이어그램 — 콘솔 한 줄이 패킷 드롭까지

전체 경로: #if DO_ENABLE_NET_TEST (개발 빌드 전용). 배포 빌드엔 이 상자들이 통째로 증발.

2) Network Profiler — "지금 뭐가 얼마나 나가고 있나"

에뮬레이션이 "나쁜 네트워크 만들기"라면, 프로파일러는 "내 게임이 대역폭을 어디에 쓰는지 재는 계측기"야.

MMORPG에서 흔한 사고가 있어. "어떤 액터 하나가 프로퍼티를 미친 듯이 복제해서 대역폭을 다 잡아먹는" 거. 근데 눈으로는 안 보여. 어떤 액터가 범인인지, 어떤 프로퍼티가 몇 비트씩 나가는지 알아야 잡지. 그걸 파일로 낱낱이 기록하는 게 Network Profiler야.

켜는 방법은 두 가지야.

(a) 런타임 콘솔 진입점 — 게임 돌다가 콘솔에 NETPROFILE.

스니펫 6 — Network Profiler 콘솔 진입점 UnrealEngine.cpp:5433-5438

#if USE_NETWORK_PROFILER else if( FParse::Command(&Cmd,TEXT("NETPROFILE")) ) { GNetworkProfiler.Exec( InWorld, Cmd, Ar ); } #endif
🔤 기호 사전 — #if USE_NETWORK_PROFILER ... GNetworkProfiler.Exec(...)
• #if USE_NETWORK_PROFILER = 이 기능을 켜는 빌드에서만 아래 코드를 넣으라는 전처리기 문.
• else if = 앞 명령들이 아니고, 이번 명령이면 실행.
• FParse::Command(...) = 콘솔 문자열이 특정 명령인지 읽어보는 UE 도구.
• &Cmd = Cmd 원본 위치를 넘겨줘서 함수가 읽은 만큼 앞으로 움직일 수 있게 함.
• TEXT("NETPROFILE") = NETPROFILE이라는 명령 글자를 UE 문자열로 감싼 것.
• GNetworkProfiler = 전역으로 하나 있는 네트워크 프로파일러 객체. 어디서든 찾아 쓸 수 있는 계측기라고 보면 돼.
• .Exec(...) = 그 객체에게 명령 실행을 시키는 함수 호출.
• #endif = #if로 연 개발 빌드 전용 구간 끝.

(b) 기동 시 커맨드라인 — 실행할 때 -NETWORKPROFILER=<태그> 붙이면 GameEngine.cpp:1220에서 감지해서 :1222의 GNetworkProfiler.EnableTracking(true)로 처음부터 켜져. (끄면 NetworkProfiler.cpp:214의 EnableTracking(false)가 세션을 flush 해서 파일을 닫아.)

켜지면 실제 트래픽을 이렇게 종류별로 파일에 기록해:

  • TrackReplicateActor(...) NetworkProfiler.cpp:520 — 어떤 액터가 복제됐나
  • TrackSendBunch :451 — 번치(데이터 덩어리)가 나갔나 (번치가 뭔지는 bunch-vs-packet)
  • TrackSendRPC :289 — RPC가 나갔나
  • TrackSocketSend :364 — 소켓으로 실제 몇 바이트 나갔나

프레임 경계는 TrackFrameBegin() :233이 찍어서, "이 프레임에 뭐가 나갔나"를 프레임 단위로 끊어서 볼 수 있어. 이렇게 쌓인 파일을 나중에 외부 뷰어로 열어서 "아, 저 액터가 대역폭 60%를 먹네" 하고 병목을 찾는 거야.

이것도 #if USE_NETWORK_PROFILER로 감싸져 있어서 개발 빌드 전용이야. 계측기는 그 자체로 부하니까, 배포판엔 안 들어가는 게 맞지.

3) stat net & p.NetShowCorrections — 화면에서 바로 보기

여기 둘은 이 학습용 소스 서브셋에 렌더링 코드가 안 들어있어. 그래서 개념만 정직하게 짚고 갈게.

🔬 이 클론에 소스 미포함 — 개념 위주, 실제 대조 필요.
stat net의 화면 오버레이를 그리는 RENDER_STAT(Net) 함수와, p.NetShowCorrections의 보정 시각화 로직(CharacterMovementComponent.cpp)은 이 서브셋에 폴더 자체가 없어(Runtime/Engine/Private/Components/ 부재, grep 0건). 아래는 개념 설명이고, 실제 확인은 풀 엔진 소스에서 해야 해.

stat net — 손실·핑을 화면 구석에 숫자로

stat net은 콘솔에 치면 화면 구석에 네트워크 상태(핑, 패킷 손실, in/out 대역폭)를 실시간 숫자로 띄워줘. 유저가 "렉 걸려요" 할 때 제일 먼저 켜는 거야.

렌더 코드는 없지만, 오버레이가 읽어들이는 원본 숫자는 이 서브셋에도 있어. NetConnection.h에 손실 카운터·핑 필드가 살아있고, stat net이 묶어서 보여주는 시간 측정치들은 STATGROUP_Net이라는 그룹 태그로 등록돼. 예를 들어 DataChannel.cpp:61에서 DECLARE_CYCLE_STAT(..., STATGROUP_Net)으로 특정 구간의 소요 시간을 이 그룹에 넣어. 오버레이 렌더러는 그냥 이 그룹을 읽어서 화면에 뿌리는 껍데기일 뿐이야. 숫자는 여기 있고, 그리는 건 딴 데 있다 — 이 구조만 알면 돼.

p.NetShowCorrections — 서버가 "너 틀렸어" 하고 되돌린 순간을 눈으로

이게 이동 버그 디버깅의 진짜 핵심이야.

클라이언트는 반응성을 위해 "내 캐릭터 지금 여기쯤 있겠지" 하고 예측해서 미리 움직여(client-prediction). 근데 서버가 다시 계산해보니 위치가 틀렸어. 그럼 서버가 "아니야, 넌 사실 저기 있어야 해" 하고 정답 위치를 보내서 클라를 되돌려(server-reconciliation). 이 되돌림이 화면에서 캐릭터가 순간이동/뒤로 튐으로 보이는 거야. 유저가 말하는 "순간이동했어요"의 정체.

p.NetShowCorrections 1을 켜면, 이 보정이 일어날 때마다 화면에 캡슐 두 개를 그려줘 — "클라가 예측했던 위치"와 "서버가 말한 정답 위치". 둘이 얼마나, 얼마나 자주 벌어지는지 눈으로 보면, 예측 로직 어디가 틀렸는지 바로 감이 와. 이동 예측 튐 디버깅에서 이거 없으면 장님이야.

여기서 아까 배운 NetEmulation과 한 세트로 묶여. 내 자리에선 지연이 1ms라 보정이 거의 안 일어나 → 버그가 안 보여. 그래서 NetEmulation.PktLag 200 + NetEmulation.PktLoss 5로 나쁜 네트워크를 만들고 → p.NetShowCorrections 1로 보정을 시각화 → 그제서야 유저가 겪는 순간이동이 내 눈앞에서 재현돼. "만들어내고(에뮬레이션) → 들여다본다(시각화)" 이 콤보가 네트워크 디버깅의 정석이야.

우리 서버와 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선 서버 관점에서 이 세 도구를 번역해보자.

NetEmulation ≈ 우리가 손으로 짜던 그거. 우리도 QA할 때 IOCP 워커 스레드에서 recv 완료 통지가 오면, 테스트용으로 일부러 그 패킷을 잠깐 큐에 재워두거나(지연), 랜덤으로 skip(손실)해봤잖아. UE의 Delayed 큐 + SendTime 도장 방식이 딱 그거야. 차이는 위치야. 우리는 IOCP 콜백 안에 임시로 박았다 빼지만, UE는 FlushNet → CheckOutgoingPacketEmulation이라는 송신 파이프라인의 고정된 지점에 정식으로 심어놨어. 그래서 콘솔 한 줄로 껐다 켰다 하지.

주의할 딜레마도 똑같아. UE는 UpdateDelayedPackets가 게임 스레드(싱글스레드 액터 루프) 위에서 매 틱 돌아. 우리 게임 서버도 로직은 싱글스레드지. 그래서 지연 큐가 커지면 그 순회 비용이 메인 루프 프레임을 갉아먹어 — 이건 netdriver-tick에서 본 "틱이 곧 심장박동" 이야기랑 연결돼. 반면 우리 IOCP는 여러 워커 스레드가 병렬로 recv를 처리하니까, 지연 흉내를 워커에 박으면 락 경합이 새 변수로 튀어나와. "어느 스레드에서 지연을 실현하느냐"가 두 엔진의 근본 차이야.

Network Profiler ≈ 우리 packet_analyzer + 대역폭 로그. "어떤 핸들러가 얼마나 자주, 몇 바이트 나가나"를 재는 거잖아. 우리는 사후에 로그/툴로 집계하지만, UE는 런타임에 스트림으로 실시간 기록한다는 게 차이. 목적은 똑같아 — 대역폭 병목 범인 색출.

stat net ≈ 우리 대시보드의 frame/CPU/패킷수 지표. 게이트 frame 저하 진단할 때 g_iFPS_MainThread2 보는 거랑, stat net으로 핑·손실 보는 게 같은 결의 "화면에 실시간 숫자 띄우기"야.

막히면 / 다음

  • 송신 파이프라인 전체(FlushNet → LowLevelSend가 뭔지)가 흐릿하면 → send-callchain
  • 번치가 뭔지, 패킷과 뭐가 다른지 → bunch-vs-packet
  • 틱이 왜 네트워크의 심장인지 → netdriver-tick
  • 클라 예측이 왜 필요한지 (p.NetShowCorrections 전제) → client-prediction
  • 서버가 왜 되돌리는지 (보정의 원리) → server-reconciliation
  • 지연 보정으로 "때렸는데 안 맞음"을 서버가 어떻게 되감는지 → lag-compensation

🎯 원리 한 줄 요약

네트워크 디버깅은 "나쁜 네트워크를 콘솔 한 줄로 만들어내고(NetEmulation: 버리면 손실·미루면 지연), 뭐가 얼마나 나가는지 재고(Profiler), 서버가 되돌린 순간을 눈으로 보는(NetShowCorrections)" 3종 세트 — 전부 개발 빌드 전용이라 배포판엔 아예 없다.
