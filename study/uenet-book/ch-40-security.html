보안: 서버 권위와 안티치트 표면

언리얼 네트워크 · 40 / 43

들어가기 전에

게임 서버 짜봤으면 이미 몸으로 아는 규칙이 하나 있어.

"클라가 보내는 건 의도일 뿐이다. 결정은 서버가 한다."

클라가 "나 몬스터 때려서 1000골드 먹었어"라고 패킷을 쏘면, 서버는 그 말을 곧이곧대로 믿고 골드를 주면 안 돼. 서버가 직접 "때린 게 맞나? 그 몹이 거기 있었나? 데미지가 말이 되나?"를 다시 계산해서 진짜 상태를 정한다. 이게 서버 권위(Server Authority)야. 안티치트의 뿌리가 전부 여기서 나와.

UE도 똑같은 철학인데, 재밌는 건 이 철학이 엔진 코드에 아예 박혀 있다는 거야. "클라가 서버 함수 못 부르게" 같은 걸 게임 개발자가 매번 손으로 짜는 게 아니라, RPC를 부르는 순간 엔진이 자동으로 가로막아. 이번 챕터는 그 "자동으로 가로막는 지점"들이 실제로 어느 파일 몇 번째 줄인지를 짚어보는 거야.

방어선은 안쪽에서 바깥쪽으로 4겹이야:

바깥 ┌─────────────────────────────────────────────┐ │ ④ 스테이트리스 핸드셰이크 쿠키 │ ← 커넥션을 만들기도 전에 IP 진짜인지 검증 │ ┌─────────────────────────────────────┐ │ │ │ ① Callspace 라우팅 │ │ ← 이 RPC 호출을 어디로? (로컬/원격/폐기) │ │ ┌─────────────────────────────┐ │ │ │ │ │ ③ WithValidation (_Validate)│ │ │ ← 서버가 인자 검사, false면 실행 거부 │ │ │ ┌─────────────────────┐ │ │ │ │ │ │ │ ② HasAuthority │ │ │ │ ← "진짜 상태" 바꾸는 건 여기 통과한 쪽만 │ │ │ └─────────────────────┘ │ │ │ │ │ └─────────────────────────────┘ │ │ │ └─────────────────────────────────────┘ │ └─────────────────────────────────────────────┘ 안쪽

하나씩 까보자.

① Callspace 라우팅 — "이 함수 호출을 어디로 보내지?"

개념부터

RPC(Remote Procedure Call)는 이름만 함수 호출이지, 실제론 "함수 하나 부르면 네트워크 너머에서 실행되는" 마법이야. 근데 마법이 걸리기 전에 엔진이 먼저 판단을 해야 돼.

이 호출을 지금 이 컴퓨터에서 실행할까(Local)? 네트워크 너머로 보낼까(Remote)? 아니면 그냥 조용히 버릴까(Absorbed)?

이 세 갈래 분류를 Callspace(콜스페이스)라고 불러. 그리고 이걸 정하는 최상위 함수가 이거야:

AActor::GetFunctionCallspace() — Actor.cpp:5412

이 함수가 역할(누가 서버고 누가 클라냐) × NetMode × 함수 플래그를 조합해서 세 갈래 중 하나를 뱉어. 안티치트의 1차 관문이 바로 여기야.

맞춰봐 (예측-검증)

자, 문제 하나. 클라이언트가 서버 전용 RPC(FUNC_NetServer)를 "로컬에서" 실행하려고 하면 어떻게 될까?

  • (A) 에러 팝업이 뜨고 게임이 뻗는다
  • (B) 클라 로컬에서 그냥 실행돼버린다 (치트 성공)
  • (C) 조용히 버려진다. 에러도 안 난다

...

정답은 (C). 엔진 용어로 Absorbed(흡수 = 소리 없이 폐기)야. 이게 왜 중요하냐면 — 에러를 안 내는 게 오히려 방어야. 공격자한테 "여기 막혔다"는 힌트조차 안 주고, 서버는 애초에 그 호출을 받지도 않아. 실제 코드로 보자.

지금부터 진짜 엔진 코드가 나와. 겁먹지 마 — 괄호랑 화살표랑 & 같은 기호는 바로 아래에서 하나씩 한국말로 풀어줄게. 코드를 외우는 게 아니라 "어느 조건이면 버리는구나"만 잡으면 돼.

if (NetMode == NM_Standalone) { if (LocalRole < ROLE_Authority && (Function->FunctionFlags & FUNC_NetServer)) { // Don't let clients call server functions (in edge cases where NetMode is standalone (net driver is null)) DEBUG_CALLSPACE(TEXT("GetFunctionCallspace No Authority Server Call Absorbed: %s"), *Function->GetName()); return FunctionCallspace::Absorbed; } // Call local return FunctionCallspace::Local; }

— Runtime/Engine/Private/Actor.cpp:5465-5476

🔤 기호 사전 — if (LocalRole < ROLE_Authority && (Function->FunctionFlags & FUNC_NetServer))
• if (...) = 괄호 안 조건이 맞으면 안쪽 코드를 실행하라는 뜻.
• == = "같다" 검사. NetMode == NM_Standalone은 지금 모드가 스탠드얼론인지 묻는 말이야.
• < = 왼쪽이 오른쪽보다 작냐는 비교. 여기선 LocalRole이 ROLE_Authority보다 낮으면 "나는 권위자가 아니다"로 읽으면 돼.
• && = 두 조건이 둘 다 맞아야 한다는 뜻. 하나라도 아니면 안 들어가.
• Function->FunctionFlags = Function이라는 함수 정보 상자 안의 FunctionFlags 칸을 꺼내 본다는 뜻. ->는 "그 안의 것을 꺼내라"야.
• & FUNC_NetServer = 비트 딱지 검사. 함수 플래그들 중에 FUNC_NetServer 딱지가 붙어 있나 확인해.
• DEBUG_CALLSPACE(TEXT(...)) = 디버그용 기록을 남기는 매크로. TEXT(...)는 UE 문자열을 만들 때 감싸는 포장지라고 보면 돼.
• return FunctionCallspace::Absorbed; = 이 함수 판단 결과로 "흡수, 즉 버림"을 돌려주고 여기서 끝낸다는 뜻.
🔁 이제 다시 보자. NetMode == NM_Standalone(스탠드얼론 상황)이고 → LocalRole < ROLE_Authority(나는 서버 권위자가 아님)인데 → FunctionFlags & FUNC_NetServer(서버 전용 함수 딱지가 붙음)면 → return Absorbed(조용히 버림). 한 줄로 "권위 없는 쪽이 서버 전용 RPC를 실행하려 하면, 실행하지 않고 흡수한다."

LocalRole < ROLE_Authority(= 나는 권위자가 아니다 = 클라다)인데 부르려는 함수가 FUNC_NetServer(서버 전용)면 → Absorbed 리턴. 끝. 주석도 대놓고 "Don't let clients call server functions"라고 써놨어.

방향은 단방향으로 강제된다

RPC는 방향이 정해져 있어. FUNC_NetServer(클라→서버), FUNC_NetClient(서버→특정 클라), FUNC_NetMulticast(서버→전원). 엔진은 잘못된 방향으로 쏘려는 걸 replicate 자체를 안 해버려:

if (Function->FunctionFlags & (FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast)) { // Handle uni-directional RPCs // if we are the server, and it's not a send-to-client function, if (bIsServer && !(Function->FunctionFlags & FUNC_NetClient)) { // don't replicate DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Server calling Server function: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace)); return Callspace; } // if we aren't the server, and it's not a send-to-server function, if (!bIsServer && !(Function->FunctionFlags & FUNC_NetServer)) { // don't replicate DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Client calling Client function: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace)); return Callspace; } }

— Runtime/Engine/Private/Actor.cpp:5522-5540

🔤 기호 사전 — Function->FunctionFlags & (FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast)
• FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast = 세 딱지를 한 묶음으로 합친 것. |는 "이것도 또는 저것도"를 비트로 합치는 기호야.
• & (...) = 그 묶음 중 하나라도 함수에 붙어 있나 검사하는 것.
• bIsServer = b로 시작하는 참/거짓 값. "지금 내가 서버냐?" 스위치야.
• ! = 아니다/반대. !bIsServer는 "서버가 아니면", !(...FUNC_NetClient)는 "클라로 보내는 함수가 아니면".
• return Callspace; = 지금까지 정해진 콜스페이스 값을 그대로 돌려주고 끝낸다. 여기서는 네트워크 전송을 새로 만들지 않는 쪽으로 빠져.
• FunctionCallspace::ToString(Callspace) = 콜스페이스 값을 사람이 읽는 글자로 바꿔 디버그 로그에 넣는 보조 함수야.
🔁 이제 다시 보자. 바깥 if는 "이 함수가 RPC 딱지를 달았나?"를 먼저 보고, 서버 쪽이면 FUNC_NetClient가 아닌 호출을 네트워크로 안 보내고, 클라 쪽이면 FUNC_NetServer가 아닌 호출을 안 보내. 결국 방향 딱지가 맞는 RPC만 선을 타고 나간다는 코드야.

읽는 법: 서버인데 "클라로 보내는 함수"가 아니면 → 네트워크로 안 보냄(로컬로만). 클라인데 "서버로 보내는 함수"가 아니면 → 역시 안 보냄. 즉 서버는 서버→클라 방향으로만 쏠 수 있고, 클라는 클라→서버 방향으로만 쏠 수 있다. 방향이 코드로 못 박혀 있는 거야. RPC 방향 플래그의 자세한 의미는 → rpc-types.

② HasAuthority — "진짜 상태는 나만 바꾼다"

Callspace가 "호출을 어디로 보내나"라면, HasAuthority()는 "실제 상태 변경을 실행할 자격이 있나"를 묻는 게이트야.

권위(ROLE_Authority)를 가진 쪽 — 보통 서버 — 만 액터를 파괴하거나, 스폰하거나, 핵심 상태를 바꿔. 클라가 들고 있는 값은 서버가 복제해준 사본일 뿐이고, 클라가 그 사본을 지지고 볶아봐야 서버의 진짜 값은 안 바뀌어.

패턴은 항상 이 모양이야:

if (HasAuthority()) { // 여기서만 진짜 상태를 바꾼다 (파괴 / 스폰 / 데미지 적용 ...) }
🔤 기호 사전 — if (HasAuthority())
• HasAuthority() = "내가 이 액터의 진짜 주인, 보통 서버냐?"를 묻는 함수.
• () = 함수를 부른다는 표시. HasAuthority라는 질문을 실제로 던지는 거야.
• { ... } = 조건이 맞을 때 실행할 코드 울타리. 여기 안에 있는 것만 진짜 상태 변경으로 허락돼.
• // = 코드가 아니라 사람 읽으라고 붙인 설명. 컴파일러는 이 줄을 실행하지 않아.
🔁 이제 다시 보자. if(조건 맞으면) → HasAuthority()(내가 권위자면) → { ... }(이 울타리 안에서만 파괴/스폰/데미지 같은 진짜 변경). 한 줄로 "서버 권위가 있는 쪽만 실제 상태를 바꾸게 막는 문"이야.

이 서브셋에서 HasAuthority() 정의 헤더 자체(GameFramework/Actor.h)는 안 들어있지만, 실사용처는 Actor.cpp 안에 널려 있어 — 파괴·스폰·상태변경을 감싸는 가드로 Actor.cpp:2277, :3349, :3863, :3894, :3929 등. 핵심은 "상태를 바꾸는 코드는 반드시 이 if 안에 있어야 한다"는 습관이 엔진 전반에 깔려 있다는 거야. 상태를 어떻게 복제해서 클라 사본을 만드는지는 → server-replicate-actors.

③ WithValidation — "클라 인자는 실행 전에 검사한다"

Callspace를 통과해서 서버 RPC가 진짜 서버에 도착했어. 그래도 아직 안 믿어. 도착한 인자가 정상 범위인지 실행 전에 한 번 더 검사해. 이게 WithValidation, 코드로는 _Validate 짝함수야.

Server RPC 하나를 선언하면 엔진은 함수를 둘로 쪼개:

  • ..._Validate(...) — 인자 검사. bool 리턴. false면 실행 거부 + 그 커넥션은 처벌(강제 종료) 대상.
  • ..._Implementation(...) — 실제 본체. _Validate가 true를 리턴해야만 불려.

교과서 예제가 ServerExec이야:

bool APlayerController::ServerExecRPC_Validate(const FString& Msg) { return true; } void APlayerController::ServerExecRPC_Implementation(const FString& Msg) { #if !UE_BUILD_SHIPPING ClientMessage(ConsoleCommand(Msg)); #endif } void APlayerController::ServerExec(const FString& Msg) { #if !UE_BUILD_SHIPPING if (Msg.Len() > 128) { UE_LOG(LogPlayerController, Warning, TEXT("APlayerController::ServerExec. Msg too big for network RPC. Truncating to 128 character")); } ServerExecRPC(Msg.Left(128)); #endif }

— Runtime/Engine/Private/PlayerController.cpp:1874-1896

🔤 기호 사전 — bool APlayerController::ServerExecRPC_Validate(const FString& Msg)
• bool = 답이 참/거짓 둘 중 하나인 함수라는 뜻. _Validate에선 true면 통과, false면 거부야.
• APlayerController:: = APlayerController에 딸린 함수라는 소속 표시. ::는 "~의"라고 읽어.
• _Validate = 실행 전에 검사하는 짝함수. 서버가 "이 인자 믿어도 돼?"를 먼저 묻는 자리야.
• _Implementation = 검사를 통과했을 때 실제로 실행되는 본체 함수.
• const FString& Msg = 문자열 Msg를 복사하지 않고 원본을 빌려 보되(&), 이 함수 안에서 바꾸지 않겠다는 약속(const).
• return true; = "검사 통과"라고 답하고 함수 끝. 실전 검증을 비워두면 사실상 문을 활짝 열어둔 셈이야.
• #if !UE_BUILD_SHIPPING / #endif = 출시 빌드가 아닐 때만 이 코드를 컴파일하라는 울타리. !는 "아님"이야.
• Msg.Len() > 128 = 메시지 길이가 128보다 큰지 검사.
• Msg.Left(128) = 문자열 왼쪽에서 128글자까지만 잘라 가져오기. 너무 긴 입력을 네트워크에 그대로 태우지 않으려는 거야.
🔁 이제 다시 보자. ServerExecRPC_Validate는 먼저 검사표를 통과시키고(return true), ServerExecRPC_Implementation은 통과 후 본체를 실행해. 바깥 ServerExec은 Msg.Len() > 128이면 경고를 남기고, 실제 전송은 Msg.Left(128)로 잘라서 보낸다. 핵심은 "클라가 준 문자열도 길이부터 자르고, 서버 본체는 Validate 문을 지나야 들어간다."

여기서 배울 게 세 개야:

  1. _Validate가 짝으로 존재한다는 것 자체가 방어다. 이 예제는 return true라 검사를 실질적으로 안 하지만(콘솔 명령이라 !UE_BUILD_SHIPPING으로 이미 막힘), 구조가 강제된다는 게 포인트야. 실전 RPC에선 여기서 "데미지 음수 아냐?", "인벤 슬롯 범위 안이야?"를 검사해서 false를 리턴하면 서버가 그 커넥션을 끊어버려.
  1. 길이는 보내기 전에 잘라버린다. ServerExec의 Msg.Left(128) 봐. 신뢰 못 할 문자열을 네트워크에 태우기 전에 128자로 사전 절단해. 클라가 10MB짜리 문자열을 RPC로 쏴서 서버 메모리를 터뜨리는 짓을 원천 차단하는 거지. "입력 크기를 절대 믿지 마라"의 구현.
  1. #if !UE_BUILD_SHIPPING — 콘솔 명령 실행 같은 위험한 기능은 아예 배포 빌드에서 컴파일 자체를 빼버려. 코드가 없으면 뚫을 수도 없으니까.

_Validate / _Implementation 분리가 어떻게 자동 생성되는지, false 리턴 시 처벌 흐름은 → rpc-reliable-validation.

④ 스테이트리스 핸드셰이크 쿠키 — 커넥션 생기기도 전의 문지기

개념부터

앞의 ①②③은 전부 "이미 접속한 클라"를 다뤘어. 근데 접속하기 전은? 여기가 제일 취약해.

UDP는 발신 IP를 위조(spoof)할 수 있어. 공격자가 가짜 IP로 "접속하고 싶다"는 패킷을 초당 수십만 개 쏘면, 서버는 각각에 대해 커넥션 상태(메모리)를 잡으려다 메모리가 고갈돼서 뻗어. 진짜 유저는 접속조차 못 해. IP를 밴하려 해도 IP가 다 가짜라 소용없어.

해법이 스테이트리스 핸드셰이크 쿠키야. 서버는 커넥션 상태를 저장하지 않고(그래서 stateless) 챌린지-응답 토큰(쿠키)을 주고받아서, "이 IP로 답장이 실제로 돌아온다 = 이 IP는 위조가 아니다"를 먼저 검증해. IP가 진짜라고 확인된 다음에야 커넥션(메모리)을 만들어줘. 그러면 위조 IP 홍수는 커넥션을 만드는 단계까지 도달을 못 해.

왜 필요한지 — 엔진 원주석

이 경계를 엔진이 직접 설명해:

* DDoS (Distributed Denial of Service) attacks typically hinder game servers by flooding them with so many packets, * that they are unable to process all of the packets without locking up and/or drowning out other players packets, * causing players to time out or to suffer severe packet loss which hinders gameplay. * * Typically these attacks use spoofed UDP packets, where the source IP is unverifiable, * and so IP banning is usually not an effective or advisable means of blocking such attacks. * * This DDoS detection focuses specifically on this situation, detecting/mitigating DDoS attacks based on spoofed UDP packets, * which do not originate from an existing NetConnection. Flooding attacks coming from an existing NetConnection are a separate issue, * as (due to the stateless handshake required before creating a NetConnection) the IP will be verified, * and so such attacks should be dealt with through IP banning - this and other types of DoS attacks are not dealt with by this code.

— Runtime/Net/Core/Private/Net/Core/Misc/DDoSDetection.cpp:13-23

🔤 기호 사전 — * DDoS ... NetConnection ... stateless handshake ...
• * = C++ 여러 줄 주석 안에서 줄마다 붙는 표시. 실행되는 코드가 아니라 엔진 개발자가 남긴 설명이야.
• DDoS = 서버를 못 쓰게 만들려고 패킷을 엄청 많이 보내는 공격.
• spoofed UDP packets = 보낸 사람 IP를 속인 UDP 패킷. 답장이 진짜 그 사람에게 갈지 믿을 수 없어.
• NetConnection = UE가 "이 클라이언트 하나와 연결되어 있다"고 들고 있는 연결 객체.
• stateless handshake = 서버가 아직 연결 상태를 저장하지 않고, 먼저 쿠키 문답으로 "이 IP가 진짜 답할 수 있나" 확인하는 절차.
🔁 이제 다시 보자. 이 주석은 "커넥션이 아직 없는 위조 UDP 홍수는 FDDoSDetection이 맡고, 이미 NetConnection이 있는 공격은 stateless handshake를 지나 IP가 검증된 뒤라 IP 밴 같은 다른 방식으로 다룬다"는 경계선을 설명해. 연결 전 공격과 연결 후 공격을 같은 약으로 잡지 않는다는 뜻이야.

번역하면: "이 DDoS 탐지는 커넥션이 없는 위조 UDP 홍수만 담당한다. 이미 커넥션이 있는 놈이 홍수를 내면? 그건 별개 문제다 — 커넥션을 만들려면 stateless handshake를 거쳐야 하고 그때 IP가 검증되니까, 그런 놈은 IP 밴으로 처리하면 된다."

즉 방어가 두 층으로 나뉘어 있어:

  • 커넥션 전(IP 위조 가능): FDDoSDetection이 탐지·완화. IP 밴 무의미.
  • 핸드셰이크 통과 후(IP 검증됨): 이제 IP가 진짜니까 문제 생기면 IP 밴이 먹힘.

쿠키 핸드셰이크가 이 두 층을 가르는 칼이야.

장착부 — 최외곽 레이어로 끼운다

실제 구현체는 없지만, 그걸 커넥션의 가장 바깥 레이어로 장착하는 코드는 여기 있어:

// Add handling for the stateless connect handshake, for connectionless packets, as the outermost layer TSharedPtr<HandlerComponent> NewComponent = ConnectionlessHandler->AddHandler(TEXT("Engine.EngineHandlerComponentFactory(StatelessConnectHandlerComponent)"), true); StatelessConnectComponent = StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent); if (StatelessConnectComponent.IsValid()) { StatelessConnectComponent.Pin()->SetDriver(this); }

— Runtime/Engine/Private/NetDriver.cpp:2253-2262

🔤 기호 사전 — TSharedPtr<HandlerComponent> NewComponent = ConnectionlessHandler->AddHandler(...)
• TSharedPtr<HandlerComponent> = HandlerComponent를 함께 들고 쓰는 스마트 포인터. "누가 아직 쓰고 있는지 세어주는 안전한 손잡이"라고 보면 돼.
• = = 오른쪽에서 만든 값을 왼쪽 이름에 담는다.
• ConnectionlessHandler->AddHandler(...) = 연결이 아직 없는 패킷용 핸들러에 새 컴포넌트를 끼워 넣으라는 호출.
• TEXT("...") = UE 문자열 포장. 여기선 어떤 핸들러 팩토리를 붙일지 이름으로 알려줘.
• true = 켜짐/맞음 값. 여기서는 AddHandler에 넘기는 옵션값이야.
• StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent) = 방금 받은 일반 핸들러 손잡이를 "스테이트리스 연결 핸들러" 손잡이로 바꿔 잡는 것.
• StatelessConnectComponent.IsValid() = 그 손잡이가 실제로 유효한지 확인.
• StatelessConnectComponent.Pin()->SetDriver(this) = 약한 손잡이를 잠깐 강하게 붙잡고(Pin()), 그 안의 컴포넌트에 현재 드라이버(this)를 알려준다.
🔁 이제 다시 보자. AddHandler(...)로 최외곽 핸드셰이크 컴포넌트를 붙이고 → StaticCastSharedPtr로 정확한 타입 손잡이를 잡고 → IsValid()면 → SetDriver(this)로 넷드라이버를 연결한다. 한 줄로 "커넥션 없는 패킷이 제일 먼저 지날 문지기를 NetDriver 바깥 레이어에 장착하는 코드"야.

"outermost layer(최외곽)"가 핵심 단어야. 들어오는 패킷이 게임 로직에 닿기 전에 이 컴포넌트를 제일 먼저 통과해야 해. 문지기를 정문 맨 바깥에 세우는 거지. PacketHandler 레이어 구조 전체는 → packethandler, 핸드셰이크 절차 자체는 → handshake.

그리고 커넥션마다 이 문지기를 약참조로 하나씩 들고 있어:

/** Reference to the PacketHandler component, for managing stateless connection handshakes */ TWeakPtr<StatelessConnectHandlerComponent> StatelessConnectComponent;

— Runtime/Engine/Classes/Engine/NetConnection.h:446-447

🔤 기호 사전 — TWeakPtr<StatelessConnectHandlerComponent> StatelessConnectComponent;
• TWeakPtr<...> = 약한 포인터. "있으면 찾아갈 수는 있지만, 내가 붙잡고 살려두지는 않는다"는 손잡이야.
• StatelessConnectHandlerComponent = 스테이트리스 연결 핸드셰이크를 관리하는 컴포넌트 타입.
• StatelessConnectComponent = 그 컴포넌트를 가리키는 변수 이름.
• ; = C++에서 한 문장이 끝났다는 마침표.
🔁 이제 다시 보자. TWeakPtr(약한 손잡이)로 StatelessConnectHandlerComponent(핸드셰이크 문지기)를 StatelessConnectComponent라는 이름으로 들고 있다. 즉 커넥션은 문지기를 기억하지만, 그 문지기의 수명을 억지로 붙잡지는 않는다는 뜻이야.

우리 서버랑 비교 — 조선협객전 IOCP vs UE

우리 서버(C++ 분산 서버)를 떠올려봐. 대응이 꽤 깔끔해.

관심사조선협객전 서버UE
입력 수신IOCP 워커 스레드 N개가 소켓에서 패킷 뽑음NetDriver가 소켓에서 패킷 뽑음
처리 스레드워커가 뽑되, 게임 로직은 싱글스레드로 직렬 처리 (액터 = 게임 로직 단일 소유)게임 스레드 단일. 액터 상태 변경도 여기서
"클라 말 안 믿기"CM_* 핸들러 안에서 서버가 직접 재검증 (좌표·재화·수량)_Validate 짝함수 (PlayerController.cpp:1874)가 엔진 강제
방향 강제패킷 ID 네이밍 관례 (CM_=클라→서버, SM_=서버→클라) + 핸들러 switch에서 라우팅FUNC_NetServer/NetClient 플래그로 엔진이 자동 (Actor.cpp:5522)
권위게임 서버가 GameDB의 진짜 값 소유, 클라는 표시용HasAuthority() 참인 쪽만 상태 변경
접속 전 방어Gate 서버가 앞단에서 커넥션 수용/필터StatelessConnect 쿠키 + FDDoSDetection

핵심 차이: 우리는 "클라 말 안 믿기"를 개발자가 매 CM_ 핸들러마다 손으로 짜. 빼먹으면 그게 그대로 복제·재화 사고야(그래서 packet_analyzer로 전수 검증하지). UE는 그 규율의 일부(방향·검증 짝함수·권위 게이트)를 엔진 타입 시스템에 박아서 빼먹기 어렵게 만들어놨어. 대신 UE도 _Validate 본문을 return true로 비워두면 우리가 재검증 빼먹은 거랑 똑같이 뚫려 — 위 예제가 딱 그 모양이잖아. 틀은 엔진이 강제하지만, 내용물(진짜 검증 로직)은 여전히 개발자 몫이라는 게 결론이야.

우리 서버의 CM_ 방향 관례가 왜 중요한지, Gate가 어떻게 앞단 필터를 하는지는 프로젝트 메모리의 게이트/패킷 규칙 참고.

정리 — 4겹을 한 줄씩

  • ① Callspace (GetFunctionCallspace, Actor.cpp:5412) — 이 호출을 로컬/원격/폐기 어디로 보낼지 결정. 클라의 서버함수 로컬실행은 Absorbed(5467), 방향 어긋나면 replicate 안 함(5522~).
  • ② HasAuthority (Actor.cpp:3863 등) — 진짜 상태 변경은 권위자만.
  • ③ WithValidation (_Validate, PlayerController.cpp:1874) — 서버가 인자를 실행 전에 검사, false면 거부. 길이는 송신 전 절단(1895).
  • ④ Stateless Cookie (NetDriver.cpp:2255 장착, DDoSDetection.cpp:13~ 이유) — 커넥션 만들기 전에 IP 위조 검증. 실물 구현은 이 서브셋 미포함.
