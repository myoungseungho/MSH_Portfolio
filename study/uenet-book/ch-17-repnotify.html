RepNotify — 값이 도착하면 콜백

언리얼 네트워크 · 17 / 42

초인종 이야기부터

택배가 왔어. 두 가지 방식이 있지.

하나는 네가 5초마다 문을 열어보는 거야. "왔나? 안 왔네. 왔나? 안 왔네." 이걸 폴링(polling)이라고 불러. 값이 바뀌었는지 매 프레임 직접 확인하는 방식.

다른 하나는 초인종을 달아두는 거야. 택배가 도착하는 "순간"에 딩동 하고 울려. 너는 문 열어볼 필요 없이 소리만 들으면 돼. 이게 콜백(callback)이야.

멀티플레이 게임에서 HP가 서버에서 클라로 복제(replicate)될 때, 클라는 "HP 바뀌었나?" 매번 확인하고 싶지 않아. HP가 새 값으로 도착하는 그 순간 체력바 UI를 갱신하고 싶지. 그 초인종이 바로 RepNotify야. UE에서는 이렇게 선언해.

UPROPERTY(ReplicatedUsing = OnRep_Health) float Health; UFUNCTION() void OnRep_Health(); // Health가 도착하면 자동으로 불림

ReplicatedUsing = OnRep_Health — "이 값이 도착하면 OnRep_Health()를 눌러줘"라는 초인종 배선이야. 이 배선을 실제로 눌러주는 코드가 이 챕터의 주인공이고, 두 파일에 나눠 살아.

  • Runtime/Engine/Private/RepLayout.cpp — 값을 받아 갱신하고, 바뀌었으면 "나중에 부를 목록"에 등록하고, 나중에 실제로 콜백을 부름.
  • Runtime/Engine/Private/DataReplication.cpp — 오브젝트 하나 단위로 "이제 다 받았으니 콜백 돌려" 하고 지휘함.
값이 어떻게 여기까지 도착하는지(번치 수신 → 프로퍼티 역직렬화)가 안 그려지면 → receive-callchain, replayout 먼저 보고 와.

핵심 뒤틀림: 받는 즉시 안 부른다

여기서 초보가 제일 많이 헷갈리는 지점이 하나 있어. 미리 맞춰봐.

질문: 서버가 한 번에 HP, MP, 좌표 세 개를 보냈어. 그리고 셋 다 RepNotify가 걸려 있어. 클라는 HP를 역직렬화하는 그 자리에서 바로 OnRep_Health()를 부를까?

.

.

반전: 안 불러. 받는 도중에는 그냥 "HP 초인종 눌러야 함"이라고 메모지에만 적어둬. MP도 메모, 좌표도 메모. 그리고 세 개를 다 받고 번치 수신이 완전히 끝난 뒤에, 메모지를 쭉 훑으면서 그제서야 OnRep_Health(), OnRep_Mana()... 하나씩 부르지.

왜 이렇게 미루냐고? OnRep_Health() 안에서 "HP랑 좌표를 같이 보고 UI를 그린다"고 해봐. HP만 도착하고 좌표는 아직 안 온 상태에서 콜백이 불리면, 콜백은 반쪽짜리 데이터를 보게 돼. 그래서 UE는 "이번 수신분을 전부 반영한 뒤에" 콜백을 몰아서 부르는 지연 실행(deferred) 방식을 써. 초인종은 눌러두되, 소리는 택배를 다 내려놓고 나서 한꺼번에 울리는 거야.

이 "메모지"가 바로 RepState->RepNotifies라는 배열이고, 이 챕터의 전체 흐름은 딱 두 단계야.

  • (A) 수신 중: 값 갱신 → 바뀌었으면 메모지에 프로퍼티 등록
  • (B) 수신 끝: 메모지 순회 → 실제 콜백(ProcessEvent) → 메모지 비움

(A) 받으면서 메모하기 — RepLayout.cpp:3372

프로퍼티 하나를 받는 함수 ReceivePropertyHelper 안이야. RepNotify가 걸린 프로퍼티면 이 블록을 타.

RepLayout.cpp:3372-3393

if (RepNotifies != nullptr && INDEX_NONE != Parent.RepNotifyNumParams) { // Copy current value over so we can check to see if it changed if (!bShadowDataCopied) { StoreProperty(Cmd, ShadowData + Cmd, Data + SwappedCmd); } // Read the property Cmd.Property->NetSerializeItem(Bunch, Bunch.PackageMap, Data + SwappedCmd); UE_LOG(LogRepProperties, VeryVerbose, TEXT("ReceivePropertyHelper: NetSerializeItem (WithRepNotify)")); // Check to see if this property changed if (Parent.RepNotifyCondition == REPNOTIFY_Always || !PropertiesAreIdentical(Cmd, ShadowData + Cmd, Data + SwappedCmd, NetSerializeLayouts)) { RepNotifies->AddUnique(Parent.Property); } else { UE_CLOG(LogSkippedRepNotifies > 0, LogRep, Display, TEXT("2 FReceivedPropertiesStackState Skipping RepNotify for property %s because local value has not changed."), *Cmd.Property->GetName()); } }

세 계단으로 읽어.

1계단 — 덮어쓰기 전에 사진 한 장. StoreProperty(...)로 지금 값을 ShadowData(섀도 버퍼)에 복사해둬. 곧 새 값으로 덮어쓸 거니까, "직전 값"을 미리 백업하는 거야. 왜 백업하냐면 두 가지 때문인데, (1) 정말 바뀌었는지 비교하려고, (2) 나중에 1-파라미터 OnRep에 "이전 값"을 넘겨주려고. 이 섀도 버퍼가 뭔지 더 알고 싶으면 → changelist.

2계단 — 실제 값 갱신. NetSerializeItem(...)이 네트워크 바이트를 읽어서 진짜 프로퍼티 메모리(Data)에 써넣어. 이 줄이 지나면 Health는 새 값이 됐어.

3계단 — 바뀌었나 판정 후 메모. RepNotifyCondition == REPNOTIFY_Always거나 !PropertiesAreIdentical(...)(섀도의 직전값과 지금값이 다르면)이면 → RepNotifies->AddUnique(Parent.Property). 메모지에 이 프로퍼티를 적어. AddUnique라 같은 프로퍼티는 중복 안 쌓여. 값이 같으면? else로 빠져서 스킵 로그만 찍고 메모 안 함 → 콜백도 안 불림.

여기서 REPNOTIFY_Always vs (기본)REPNOTIFY_OnChanged의 차이가 딱 저 조건 앞항이야. Always면 값이 같아도 무조건 메모, OnChanged면 실제로 달라야만 메모. 이 조건을 언제 왜 쓰는지는 → rep-conditions.

핵심은 이 함수 어디에도 OnRep_Health()를 부르는 코드가 없다는 거야. 오직 메모만 해. 초인종을 예약만 한 거지.

배열/FastArray 같은 커스텀 델타 경로는 조금 다른 문(門)으로 메모해. FObjectReplicator::QueuePropertyRepNotify(DataReplication.cpp:2709)가 CPF_RepNotify 없으면 바로 return하고(:2717), 있으면 똑같이 ReceivingRepState->RepNotifies.AddUnique(:2730). 원리는 같아 — "받는 중엔 메모만."

(B) 다 받으면 초인종 울리기

번치를 다 받으면 수신 마무리 함수가 "이제 콜백 돌려" 하고 방아쇠를 당겨.

DataReplication.cpp:1595-1605 — 수신 종료 지점

// Call PostNetReceive const bool bIsServer = (OwningChannel->Connection->Driver->ServerConnection == nullptr); if (!bIsServer && bHasReplicatedProperties) { PostNetReceive(); bHasReplicatedProperties = false; } // Call RepNotifies CallRepNotifies(true); }

번치 하나를 다 반영한 뒤 CallRepNotifies(true). 인자 true는 "채널에 아직 순서 기다리는 큐 번치가 있으면 지금은 부르지 말고 스킵"하라는 모드야(순서 꼬임 방지). 그 다음 오브젝트 단위 지휘부로 넘어가.

DataReplication.cpp:2437-2453 — 오브젝트 단위 오케스트레이션

if (Connection && Connection->Driver && Connection->Driver->ShouldSkipRepNotifies()) { return; } if (bSkipIfChannelHasQueuedBunches && (OwningChannel && OwningChannel->QueuedBunches.Num() > 0)) { return; } FReceivingRepState* ReceivingRepState = RepState->GetReceivingRepState(); RepLayout->CallRepNotifies(ReceivingRepState, Object); if (IsValid(Object)) { Object->PostRepNotifies(); }

두 개의 문지기를 지나. 드라이버가 RepNotify를 통째로 스킵하면 return, 채널에 큐 번치가 쌓여 있으면 return(위 true 모드). 둘 다 통과하면 진짜 콜백 담당인 RepLayout->CallRepNotifies(...)에 위임하고, 끝나면 Object->PostRepNotifies()(콜백 다 끝난 뒤의 후처리 훅)를 불러.

이제 메모지를 실제로 훑는 곳으로 내려가.

RepLayout.cpp:4679-4700 — 메모지 순회 + OnRep 함수 찾기

for (FProperty* RepProperty : RepState->RepNotifies) { if (!Parents.IsValidIndex(RepProperty->RepIndex)) { UE_LOG(LogRep, Warning, TEXT("FRepLayout::CallRepNotifies: Called with invalid property %s on object %s."), *RepProperty->GetName(), *Object->GetName()); continue; } UFunction* RepNotifyFunc = Object->FindFunction(RepProperty->RepNotifyFunc); if (RepNotifyFunc == nullptr) { UE_LOG(LogRep, Warning, TEXT("FRepLayout::CallRepNotifies: Can't find RepNotify function %s for property %s on object %s."), *RepProperty->RepNotifyFunc.ToString(), *RepProperty->GetName(), *Object->GetName()); continue; } const FRepParentCmd& Parent = Parents[RepProperty->RepIndex]; const int32 NumParms = RepNotifyFunc->NumParms;

메모지(RepState->RepNotifies)를 하나씩 꺼내면서, Object->FindFunction(RepProperty->RepNotifyFunc)로 그 프로퍼티에 배선된 OnRep 함수를 이름으로 찾아. RepNotifyFunc는 Health에 대해선 OnRep_Health라는 이름을 들고 있어. 못 찾으면 경고 찍고 continue.

여기서 UE 특유의 지점 하나. C++ 함수 포인터로 직접 부르는 게 아니라 리플렉션으로 이름 찾아서 부른다는 것. 그게 다음 조각이야.

RepLayout.cpp:4700-4715 — 파라미터 0개 OnRep 호출

switch (NumParms) { case 0: { Object->ProcessEvent(RepNotifyFunc, nullptr); // TODO CopyCompleteValue no matter the field is replicated or not // will be a performance regression for any RepNotify arrays. // One fix is to track the incoming changelist and then resize the array and // recursively copy over only the fields we care about. if (EnumHasAnyFlags(Parent.Flags, ERepParentFlags::HasDynamicArrayProperties) && !EnumHasAnyFlags(Parent.Flags, ERepParentFlags::IsFastArray)) { RepProperty->CopyCompleteValue(ShadowData + Parent, ObjectData + Parent); } break; }

NumParms(OnRep 함수의 파라미터 개수)로 분기해. void OnRep_Health()처럼 인자가 없으면 case 0: Object->ProcessEvent(RepNotifyFunc, nullptr). 이 한 줄이 초인종이 실제로 울리는 순간이야. ProcessEvent가 UObject 런타임 통로를 통해 OnRep_Health를 실행해. 네가 블루프린트나 C++에 적어둔 UI 갱신 코드가 여기서 돈다.

인자가 하나 있는 형태 — void OnRep_Health(float OldHealth)처럼 "이전 값"을 받고 싶으면 case 1로 가.

RepLayout.cpp:4726-4744 — 1-파라미터 OnRep 호출 + 섀도 갱신

// Handle bitfields. const FBoolProperty* BoolProperty = CastField<const FBoolProperty>(Parent.Property); if (BoolProperty && !BoolProperty->IsNativeBool()) { bool BoolPropertyValue = BoolProperty->GetPropertyValue(PropertyData); Object->ProcessEvent(RepNotifyFunc, &BoolPropertyValue); } else { Object->ProcessEvent(RepNotifyFunc, PropertyData); } // now store the complete value in the shadow buffer if (!EnumHasAnyFlags(Parent.Flags, ERepParentFlags::IsNetSerialize)) { RepProperty->CopyCompleteValue(ShadowData + Parent, ObjectData + Parent); }

ProcessEvent(RepNotifyFunc, PropertyData) — 이때 PropertyData는 ShadowData + Parent, 즉 아까 (A)에서 백업해둔 직전 값이야. 그래서 OnRep_Health(float OldHealth)의 OldHealth로 이전 값이 들어와. "새 값은 이미 멤버에 들어있고, 이전 값은 인자로 준다" — 그래서 콜백 안에서 Health - OldHealth로 델타(피해량/회복량)를 계산할 수 있어. 호출 뒤엔 CopyCompleteValue로 섀도 버퍼를 지금 값으로 갱신해서 다음 비교 기준을 맞춰둬.

(파라미터 2개 case는 커스텀 델타용 — 값 + MetaData를 같이 넘겨. 지금 원리엔 안 필요하니 넘어가.)

RepLayout.cpp:4789-4790 — 메모지 비우기

RepState->RepNotifies.Empty(); RepState->RepNotifyMetaData.Empty();

다 부른 뒤 메모지를 싹 비워. 그래서 한 프레임에 같은 프로퍼티 OnRep은 최대 한 번. 다음 수신에서 또 바뀌면 다시 메모하고, 다시 여기서 비우고. 초인종 소리는 한 번 울리고 초기화되는 거지.

우리 서버랑 붙여보기

조선협객전 서버 감각으로 번역하면 이래.

IOCP 워커 = "받는 중" 단계. 우리 서버는 IOCP 워커 스레드가 소켓에서 패킷 바이트를 긁어와 파싱하잖아. UE의 NetSerializeItem(값 역직렬화)이 딱 그 자리야. 근데 우리는 여기서 곧장 로직을 실행하지 않고 파싱된 메시지를 로직 처리로 넘기지. UE도 똑같아 — 받는 워커 단계에선 값만 갱신하고 콜백은 안 부른다. AddUnique로 메모만 하는 게, 우리로 치면 워커가 "이 캐릭터 HP 바뀜"이라고 큐에 이벤트만 꽂아두는 거랑 같아.

싱글스레드 액터 처리 = CallRepNotifies 단계. 우리 서버가 파싱과 게임 로직을 나눈 이유가 "로직은 한 흐름에서 순서대로, 데이터 완성된 상태로 처리"하려는 거잖아. UE의 지연 콜백도 정확히 같은 동기 — 받는 도중의 반쪽 상태에서 콜백을 부르면 위험하니, 수신을 다 반영한 뒤 안전한 지점에서 몰아서 실행. 우리가 로직에서 큐를 하나씩 꺼내 처리하듯, UE는 RepNotifies 배열을 순회하며 하나씩 ProcessEvent.

차이 하나만 기억해. 우리는 보통 패킷 ID로 switch 때려서 핸들러 함수를 직접 부르지만, UE는 FindFunction으로 이름 문자열을 리플렉션 조회해서 ProcessEvent로 불러. 유연한 대신 조회 비용이 붙어. 그래서 UE도 매 프레임 폴링이 아니라 "바뀐 것만, 한 번만" 부르도록 그렇게 아끼는 거야.

마무리

  • 받는 중엔 값만 갱신하고 콜백은 예약(메모)만 한다 — 반쪽 데이터로 콜백이 도는 걸 막으려고.
  • 수신이 끝난 안전한 지점에서 메모지를 순회하며 ProcessEvent로 한 번에 콜백을 부른다.
  • 1-파라미터 OnRep은 섀도 버퍼에 백업해둔 직전 값을 인자로 받아 델타 계산이 가능하다.
막히면 → replayout (RepLayout이 프로퍼티를 어떻게 펼쳐 관리하는지), changelist (섀도 버퍼/변경 추적의 정체)
다음 → rep-conditions (Always vs OnChanged, 누구에게 보낼지 조건), push-model ("바뀜"을 직접 알려주는 최적화)

🎯 원리 한 줄 요약

RepNotify는 받는 즉시 부르는 게 아니라, 값 갱신 → 바뀐 것만 메모 → 수신 끝난 뒤 메모지만 몰아서 ProcessEvent → 메모지 비움 — "도착 순간에 딱 한 번" 울리는 지연 콜백이다.
