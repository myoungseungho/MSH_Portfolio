RepNotify — 값이 도착하면 콜백

언리얼 네트워크 · 17 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이런 고민을 해봤을 거야. CChosunPlayer의 HP가 바뀌었을 때, 클라 UI는 언제 갱신해야 할까? 매 프레임 "HP 바뀌었나?" 하고 뒤져볼 수도 있고, SP_* 패킷을 받은 순간 "HP 바뀜" 이벤트를 하나 꽂아둘 수도 있어.

그런데 이 장치가 없으면 금방 지저분해져. HP, MP, 좌표, 버프가 한 번에 들어오는데 HP 처리 중간에 바로 UI 콜백을 불러버리면, 아직 좌표나 버프는 예전 값일 수 있어. 반대로 매 프레임 폴링으로 확인하면 1명일 땐 괜찮아도 100명, 1000개 프로퍼티가 되면 "혹시 바뀌었나?"만 보느라 일을 낭비해. 락까지 섞이면 더 피곤하고, 단일스레드 로직 흐름도 흐려져.

그래서 우리 서버에서도 IOCP 워커가 받은 바이트를 바로 게임 로직으로 막 흔들지 않고, CM_ 요청이나 상태 변경을 큐에 얹은 뒤 안전한 흐름에서 처리하잖아. 받는 중에는 기록만 하고, 다 받은 뒤 한 번에 처리한다. 이 감각이 RepNotify를 이해하는 핵심이야.

언리얼도 같은 문제를 만났고, 답이 바로 RepNotify야. 값이 복제돼서 도착하면 "이 프로퍼티의 초인종을 나중에 울려야 함"이라고 메모해두고, 수신이 끝난 안전한 지점에서 OnRep_Health() 같은 콜백을 딱 울려준다. 그래서 UI 갱신, 이펙트 재생, 사운드 같은 후처리를 폴링 없이 붙일 수 있어.

왜 지금 배우냐면, 앞에서 복제 데이터가 어떻게 흘러오는지 봤다면 이제는 그 값이 게임 코드의 반응으로 이어지는 순간을 볼 차례라서야. 뒤의 조건 복제, Push Model 같은 최적화도 결국 "언제 누구에게 보내고, 도착했을 때 무엇을 울릴까"의 문제로 이어져. RepNotify는 그 중간에 있는 초인종 배선도야.

초인종 이야기부터

택배가 왔어. 두 가지 방식이 있지.

하나는 네가 5초마다 문을 열어보는 거야. "왔나? 안 왔네. 왔나? 안 왔네." 이걸 폴링(polling)이라고 불러. 값이 바뀌었는지 매 프레임 직접 확인하는 방식.

다른 하나는 초인종을 달아두는 거야. 택배가 도착하는 "순간"에 딩동 하고 울려. 너는 문 열어볼 필요 없이 소리만 들으면 돼. 이게 콜백(callback)이야.

멀티플레이 게임에서 HP가 서버에서 클라로 복제(replicate)될 때, 클라는 "HP 바뀌었나?" 매번 확인하고 싶지 않아. HP가 새 값으로 도착하는 그 순간 체력바 UI를 갱신하고 싶지. 그 초인종이 바로 RepNotify야. UE에서는 이렇게 선언해.

지금부터 첫 코드가 나와. 겁먹지 마 — 이건 엔진 깊은 코드가 아니라 "이 변수에 초인종을 달겠다"는 선언 예시야. 낯선 괄호와 대문자 딱지는 바로 아래에서 하나씩 풀어볼게.

UPROPERTY(ReplicatedUsing = OnRep_Health) float Health; UFUNCTION() void OnRep_Health(); // Health가 도착하면 자동으로 불림
🔤 기호 사전 — UPROPERTY(ReplicatedUsing = OnRep_Health) / void OnRep_Health()
• UPROPERTY(...) = UE한테 "이 변수는 특별 관리 대상이야" 하고 붙이는 딱지. 괄호 안에 관리 규칙을 적어.
• ReplicatedUsing = OnRep_Health = "복제돼서 값이 도착하면 OnRep_Health라는 초인종을 눌러줘"라는 배선.
• float = 소수점 숫자를 담는 칸. 여기서는 HP 같은 실수 값을 담을 수 있어.
• UFUNCTION() = UE가 이 함수를 이름으로 찾고 호출할 수 있게 등록하는 딱지.
• void = 이 함수는 계산 결과를 return으로 돌려주지 않는다는 뜻. 울리고 끝나는 초인종 버튼에 가까워.
• () = 함수 호출 자리. 안에 아무것도 없으니 OnRep_Health()는 받을 재료가 없는 함수야.
• // = 사람만 읽는 메모. 컴파일러는 이 뒤 문장을 실행하지 않아.
🔁 이제 다시 보자. UPROPERTY(ReplicatedUsing = OnRep_Health)는 "Health에 복제 초인종을 달고", UFUNCTION()은 "그 초인종 함수가 UE에게 보이게 등록하고", void OnRep_Health()는 "값이 도착하면 눌릴 버튼"을 만든다. 한 줄로는 "Health가 복제되어 도착하면 OnRep_Health를 불러라."

ReplicatedUsing = OnRep_Health — "이 값이 도착하면 OnRep_Health()를 눌러줘"라는 초인종 배선이야. 이 배선을 실제로 눌러주는 코드가 이 챕터의 주인공이고, 두 파일에 나눠 살아.

  • Runtime/Engine/Private/RepLayout.cpp — 값을 받아 갱신하고, 바뀌었으면 "나중에 부를 목록"에 등록하고, 나중에 실제로 콜백을 부름.
  • Runtime/Engine/Private/DataReplication.cpp — 오브젝트 하나 단위로 "이제 다 받았으니 콜백 돌려" 하고 지휘함.
값이 어떻게 여기까지 도착하는지(번치 수신 → 프로퍼티 역직렬화)가 안 그려지면 → receive-callchain, replayout 먼저 보고 와.

핵심 뒤틀림: 받는 즉시 안 부른다

여기서 초보가 제일 많이 헷갈리는 지점이 하나 있어. 미리 맞춰봐.

질문: 서버가 한 번에 HP, MP, 좌표 세 개를 보냈어. 그리고 셋 다 RepNotify가 걸려 있어. 클라는 HP를 역직렬화하는 그 자리에서 바로 OnRep_Health()를 부를까?

.

.

반전: 안 불러. 받는 도중에는 그냥 "HP 초인종 눌러야 함"이라고 메모지에만 적어둬. MP도 메모, 좌표도 메모. 그리고 세 개를 다 받고 번치 수신이 완전히 끝난 뒤에, 메모지를 쭉 훑으면서 그제서야 OnRep_Health(), OnRep_Mana()... 하나씩 부르지.

왜 이렇게 미루냐고? OnRep_Health() 안에서 "HP랑 좌표를 같이 보고 UI를 그린다"고 해봐. HP만 도착하고 좌표는 아직 안 온 상태에서 콜백이 불리면, 콜백은 반쪽짜리 데이터를 보게 돼. 그래서 UE는 "이번 수신분을 전부 반영한 뒤에" 콜백을 몰아서 부르는 지연 실행(deferred) 방식을 써. 초인종은 눌러두되, 소리는 택배를 다 내려놓고 나서 한꺼번에 울리는 거야.

이 "메모지"가 바로 RepState->RepNotifies라는 배열이고, 이 챕터의 전체 흐름은 딱 두 단계야.

  • (A) 수신 중: 값 갱신 → 바뀌었으면 메모지에 프로퍼티 등록
  • (B) 수신 끝: 메모지 순회 → 실제 콜백(ProcessEvent) → 메모지 비움

(A) 받으면서 메모하기 — RepLayout.cpp:3372

프로퍼티 하나를 받는 함수 ReceivePropertyHelper 안이야. RepNotify가 걸린 프로퍼티면 이 블록을 타.

RepLayout.cpp:3372-3393

🔤 기호 사전 — if (RepNotifies != nullptr && INDEX_NONE != Parent.RepNotifyNumParams)
• if (...) = 괄호 안 조건이 맞을 때만 안쪽 일을 해. "그럴 때만 들어가는 문"이야.
• RepNotifies != nullptr = 메모지(RepNotifies)가 진짜로 준비돼 있으면. nullptr은 "아무것도 안 가리킴", !=는 "같지 않다".
• && = 양쪽 조건이 둘 다 맞아야 한다는 뜻.
• INDEX_NONE = "번호 없음"이라는 특별한 값. INDEX_NONE != Parent.RepNotifyNumParams는 "RepNotify 정보가 없음은 아니면"으로 읽어.
• !bShadowDataCopied = !는 "아니면". 아직 섀도 복사를 안 했으면 사진을 먼저 찍겠다는 뜻.
• StoreProperty(Cmd, ShadowData + Cmd, Data + SwappedCmd) = 지금 값을 섀도 버퍼 쪽에 복사해두는 줄. +는 버퍼 안에서 해당 칸 위치로 이동하는 느낌이야.
• Cmd.Property->NetSerializeItem(...) = 프로퍼티한테 "네트워크에서 온 값을 읽어서 진짜 메모리에 써" 하고 시키는 줄. ->는 "그 안의 기능을 불러라".
• UE_LOG(..., VeryVerbose, TEXT(...)) = 아주 자세한 개발 로그를 남겨. TEXT("...")는 UE식 문자열 포장지야.
• == / || / !PropertiesAreIdentical(...) = ==는 "같다", ||는 "둘 중 하나라도", !는 "아니다". 즉 "항상 울리기 조건이거나, 값이 같지 않으면".
• RepNotifies->AddUnique(Parent.Property) = 메모지에 이 프로퍼티를 적되, 이미 적혀 있으면 또 적지 않는다.
• else / UE_CLOG(...) = 조건이 아니면 스킵 쪽으로 가고, 필요할 때만 로그를 찍는다. *Cmd.Property->GetName()의 *는 로그에 넣을 글자를 꺼내는 표시로 보면 돼.
🔁 이제 다시 보자. 이 블록은 RepNotifies 메모지가 있고 RepNotify 대상이면 → StoreProperty로 직전 값 사진을 찍고 → NetSerializeItem으로 새 값을 써넣고 → REPNOTIFY_Always이거나 값이 달라졌으면 AddUnique로 나중에 울릴 초인종 목록에 적는다. 아직 OnRep_Health()는 안 불렀어. 메모만 했어.

세 계단으로 읽어.

1계단 — 덮어쓰기 전에 사진 한 장. StoreProperty(...)로 지금 값을 ShadowData(섀도 버퍼)에 복사해둬. 곧 새 값으로 덮어쓸 거니까, "직전 값"을 미리 백업하는 거야. 왜 백업하냐면 두 가지 때문인데, (1) 정말 바뀌었는지 비교하려고, (2) 나중에 1-파라미터 OnRep에 "이전 값"을 넘겨주려고. 이 섀도 버퍼가 뭔지 더 알고 싶으면 → changelist.

2계단 — 실제 값 갱신. NetSerializeItem(...)이 네트워크 바이트를 읽어서 진짜 프로퍼티 메모리(Data)에 써넣어. 이 줄이 지나면 Health는 새 값이 됐어.

3계단 — 바뀌었나 판정 후 메모. RepNotifyCondition == REPNOTIFY_Always거나 !PropertiesAreIdentical(...)(섀도의 직전값과 지금값이 다르면)이면 → RepNotifies->AddUnique(Parent.Property). 메모지에 이 프로퍼티를 적어. AddUnique라 같은 프로퍼티는 중복 안 쌓여. 값이 같으면? else로 빠져서 스킵 로그만 찍고 메모 안 함 → 콜백도 안 불림.

여기서 REPNOTIFY_Always vs (기본)REPNOTIFY_OnChanged의 차이가 딱 저 조건 앞항이야. Always면 값이 같아도 무조건 메모, OnChanged면 실제로 달라야만 메모. 이 조건을 언제 왜 쓰는지는 → rep-conditions.

핵심은 이 함수 어디에도 OnRep_Health()를 부르는 코드가 없다는 거야. 오직 메모만 해. 초인종을 예약만 한 거지.

배열/FastArray 같은 커스텀 델타 경로는 조금 다른 문(門)으로 메모해. FObjectReplicator::QueuePropertyRepNotify(DataReplication.cpp:2709)가 CPF_RepNotify 없으면 바로 return하고(:2717), 있으면 똑같이 ReceivingRepState->RepNotifies.AddUnique(:2730). 원리는 같아 — "받는 중엔 메모만."

(B) 다 받으면 초인종 울리기

번치를 다 받으면 수신 마무리 함수가 "이제 콜백 돌려" 하고 방아쇠를 당겨.

• RepLayout->CallRepNotifies(ReceivingRepState, Object) = 실제 메모지를 훑고 초인종을 울리는 일을 RepLayout한테 맡긴다.
• IsValid(Object) = 콜백 도중 오브젝트가 사라지지 않았는지 확인. 살아 있으면 PostRepNotifies() 후처리를 부른다.
🔁 이제 다시 보자. 이 코드는 먼저 두 문지기에서 return으로 빠질지 본다. 드라이버가 스킵하라 했거나, 큐 번치가 남았으면 아직 안 울려. 둘 다 통과하면 ReceivingRepState를 꺼내 RepLayout->CallRepNotifies(...)로 넘기고, 오브젝트가 아직 살아 있으면 PostRepNotifies()까지 부른다. 즉 "안전한 타이밍인지 확인한 뒤 진짜 콜백 담당에게 넘기는 지휘부"야.

두 개의 문지기를 지나. 드라이버가 RepNotify를 통째로 스킵하면 return, 채널에 큐 번치가 쌓여 있으면 return(위 true 모드). 둘 다 통과하면 진짜 콜백 담당인 RepLayout->CallRepNotifies(...)에 위임하고, 끝나면 Object->PostRepNotifies()(콜백 다 끝난 뒤의 후처리 훅)를 불러.

이제 메모지를 실제로 훑는 곳으로 내려가.

• const FRepParentCmd& Parent = 부모 명령 정보를 복사하지 않고 원본을 읽기 전용으로 빌려온다. &는 원본 빌리기, const는 안 바꾸겠다는 약속.

여기서 UE 특유의 지점 하나. C++ 함수 포인터로 직접 부르는 게 아니라 리플렉션으로 이름 찾아서 부른다는 것. 그게 다음 조각이야.

🔤 기호 사전 — switch (NumParms) / Object->ProcessEvent(RepNotifyFunc, nullptr)
• switch (NumParms) = NumParms 값이 몇 개인지에 따라 갈림길을 고르는 문. 여기서는 OnRep 인자 개수로 나눈다.

• Object->ProcessEvent(RepNotifyFunc, nullptr) = 오브젝트에게 "이 함수 실행해" 하고 UE 런타임 통로로 호출한다. 두 번째 값 nullptr은 넘길 인자가 없다는 뜻.
• EnumHasAnyFlags(...) = 깃발 묶음 안에 특정 깃발이 켜져 있는지 확인하는 함수.
• ERepParentFlags::HasDynamicArrayProperties = 부모 속성 깃발 중 "동적 배열 속성이 있음"이라는 이름표. ::는 이름표가 들어 있는 묶음을 표시해.
• && !EnumHasAnyFlags(... IsFastArray) = 동적 배열이면서 FastArray는 아닐 때만. !가 붙었으니 "FastArray 깃발은 없으면".
• CopyCompleteValue(ShadowData + Parent, ObjectData + Parent) = 지금 오브젝트 값을 섀도 버퍼 쪽으로 통째로 복사한다. 다음 비교 기준을 맞추는 정리 작업이야.
• break = 이 case 처리를 끝내고 switch 밖으로 나간다.

NumParms(OnRep 함수의 파라미터 개수)로 분기해. void OnRep_Health()처럼 인자가 없으면 case 0: Object->ProcessEvent(RepNotifyFunc, nullptr). 이 한 줄이 초인종이 실제로 울리는 순간이야. ProcessEvent가 UObject 런타임 통로를 통해 OnRep_Health를 실행해. 네가 블루프린트나 C++에 적어둔 UI 갱신 코드가 여기서 돈다.

인자가 하나 있는 형태 — void OnRep_Health(float OldHealth)처럼 "이전 값"을 받고 싶으면 case 1로 가.

🔤 기호 사전 — Object->ProcessEvent(RepNotifyFunc, PropertyData)
• const FBoolProperty* BoolProperty = bool 프로퍼티 안내판을 가리키는 포인터. const라 이 안내판 자체는 바꾸지 않겠다는 뜻이야.
• CastField<const FBoolProperty>(Parent.Property) = Parent.Property가 bool 프로퍼티인지 조심스럽게 바꿔 끼워 보는 줄. 맞으면 포인터가 나오고, 아니면 빈 값이 나와.
• if (BoolProperty && !BoolProperty->IsNativeBool()) = bool 프로퍼티가 있고, 일반 C++ bool은 아니면. 즉 비트필드처럼 특별 포장된 bool을 따로 처리한다.
• bool BoolPropertyValue = 참/거짓 하나를 임시로 담는 작은 칸.
• BoolProperty->GetPropertyValue(PropertyData) = PropertyData에 들어 있는 이전 bool 값을 꺼낸다.
• &BoolPropertyValue = 그 임시 칸의 주소를 넘긴다. 함수가 "값이 놓인 자리"를 받게 하는 표시야.
• else = 특별 bool이 아니면 일반 경로로 간다.
• ProcessEvent(RepNotifyFunc, PropertyData) = OnRep 함수에 PropertyData를 인자로 넘겨 호출한다. 여기서 PropertyData는 직전 값이 들어 있는 자리야.
• !EnumHasAnyFlags(... IsNetSerialize) = NetSerialize 특수 경로가 아니면. 특수 경로가 아닐 때만 섀도 값을 다시 맞춘다.
• CopyCompleteValue(ShadowData + Parent, ObjectData + Parent) = 호출 뒤 섀도 버퍼를 현재 값으로 갱신한다.
🔁 이제 다시 보자. 1-파라미터 OnRep은 "새 값"을 주는 게 아니라, PropertyData라는 직전 값 자리를 넘겨 호출한다. 특별한 bool 비트필드는 임시 변수 BoolPropertyValue를 만들어 &로 주소를 넘기고, 보통 값은 PropertyData를 그대로 넘긴다. 마지막 CopyCompleteValue는 다음번 비교를 위해 섀도 버퍼를 현재 값으로 맞추는 정리야.

ProcessEvent(RepNotifyFunc, PropertyData) — 이때 PropertyData는 ShadowData + Parent, 즉 아까 (A)에서 백업해둔 직전 값이야. 그래서 OnRep_Health(float OldHealth)의 OldHealth로 이전 값이 들어와. "새 값은 이미 멤버에 들어있고, 이전 값은 인자로 준다" — 그래서 콜백 안에서 Health - OldHealth로 델타(피해량/회복량)를 계산할 수 있어. 호출 뒤엔 CopyCompleteValue로 섀도 버퍼를 지금 값으로 갱신해서 다음 비교 기준을 맞춰둬.

우리 서버랑 붙여보기

조선협객전 서버 감각으로 번역하면 이래.

IOCP 워커 = "받는 중" 단계. 우리 서버는 IOCP 워커 스레드가 소켓에서 패킷 바이트를 긁어와 파싱하잖아. UE의 NetSerializeItem(값 역직렬화)이 딱 그 자리야. 근데 우리는 여기서 곧장 로직을 실행하지 않고 파싱된 메시지를 로직 처리로 넘기지. UE도 똑같아 — 받는 워커 단계에선 값만 갱신하고 콜백은 안 부른다. AddUnique로 메모만 하는 게, 우리로 치면 워커가 "이 캐릭터 HP 바뀜"이라고 큐에 이벤트만 꽂아두는 거랑 같아.

싱글스레드 액터 처리 = CallRepNotifies 단계. 우리 서버가 파싱과 게임 로직을 나눈 이유가 "로직은 한 흐름에서 순서대로, 데이터 완성된 상태로 처리"하려는 거잖아. UE의 지연 콜백도 정확히 같은 동기 — 받는 도중의 반쪽 상태에서 콜백을 부르면 위험하니, 수신을 다 반영한 뒤 안전한 지점에서 몰아서 실행. 우리가 로직에서 큐를 하나씩 꺼내 처리하듯, UE는 RepNotifies 배열을 순회하며 하나씩 ProcessEvent.

차이 하나만 기억해. 우리는 보통 패킷 ID로 switch 때려서 핸들러 함수를 직접 부르지만, UE는 FindFunction으로 이름 문자열을 리플렉션 조회해서 ProcessEvent로 불러. 유연한 대신 조회 비용이 붙어. 그래서 UE도 매 프레임 폴링이 아니라 "바뀐 것만, 한 번만" 부르도록 그렇게 아끼는 거야.

마무리

  • 받는 중엔 값만 갱신하고 콜백은 예약(메모)만 한다 — 반쪽 데이터로 콜백이 도는 걸 막으려고.
  • 수신이 끝난 안전한 지점에서 메모지를 순회하며 ProcessEvent로 한 번에 콜백을 부른다.
  • 1-파라미터 OnRep은 섀도 버퍼에 백업해둔 직전 값을 인자로 받아 델타 계산이 가능하다.
막히면 → replayout (RepLayout이 프로퍼티를 어떻게 펼쳐 관리하는지), changelist (섀도 버퍼/변경 추적의 정체)
다음 → rep-conditions (Always vs OnChanged, 누구에게 보낼지 조건), push-model ("바뀜"을 직접 알려주는 최적화)

🎯 원리 한 줄 요약

RepNotify는 받는 즉시 부르는 게 아니라, 값 갱신 → 바뀐 것만 메모 → 수신 끝난 뒤 메모지만 몰아서 ProcessEvent → 메모지 비움 — "도착 순간에 딱 한 번" 울리는 지연 콜백이다.
