IpNetDriver: 소켓과 실제로 만나는 곳

언리얼 네트워크 · 10 / 43

들어가기 전에: "택배 회사"랑 "택배 기사"는 다른 사람이야

지금까지 우리는 엔진 안쪽 이야기만 했어. 번치를 쌓고, 패킷으로 묶고, 신뢰성 체크하고, 커넥션에 흘려보내고. 근데 잠깐. 그 묶인 바이트가 진짜 랜선을 타고 나가는 그 순간 — recvfrom, sendto 같은 OS 소켓 시스템콜이 실제로 불리는 그 지점 — 은 대체 코드 어디에 있을까?

여기서 초보가 가장 많이 넘어져. "당연히 NetDriver 어딘가에 socket.Send()가 있겠지"라고 찾아. 근데 아무리 뒤져도 안 나와. UNetConnection::LowLevelSend를 열어보면 몸통이 없어. UNetDriver::GetSocketSubsystem도 몸통이 없어. 다 텅 비어 있어.

이게 버그가 아니야. 설계야.

비유하자면 이래. 택배 "회사"는 규칙만 정해. "편지는 이 봉투에 담아라", "주소는 이 형식으로 써라", "최종 배달은 반드시 기사가 한다". 근데 회사 본사 건물 안에는 트럭이 한 대도 없어. 실제로 트럭 몰고 문 앞까지 가는 건 하청 기사야.

UE 네트워크가 딱 이 구조야:

  • 택배 회사 (규칙만) = 엔진 코어의 UNetDriver / UNetConnection — "소켓으로 보내라"는 계약만 선언. 몸통은 비워둠.
  • 택배 기사 (실제 운전) = 플러그인의 UIpNetDriver / UIpConnection — 그 빈 몸통을 채워서 진짜 recvfrom / SendTo를 부름.

이번 챕터는 이 "계약과 구현의 경계선" 을 정확히 어디서 긋는지 배우는 거야. 그리고 여기엔 좀 특이한 사정이 하나 있어 —

🔬 정직 배너: 이 클론엔 "기사"가 없어

이 학습 트리에는 초점 대상인 UIpNetDriver / UIpConnection의 실제 소켓 코드가 미포함이야.
• 왜? 언리얼에서 실제 소켓 구현체는 엔진 코어(Runtime/Engine)가 아니라 OnlineSubsystemUtils 플러그인에 살아. 클래스 경로가 [/Script/OnlineSubsystemUtils.IpNetDriver]로 박혀 있는 게 그 증거야 (ReplicationDriver.h:13).
• 확인함: 이 트리에서 find -iname "*IpNetDriver*", grep -rln "UIpNetDriver" 둘 다 실제 클래스 정의는 0건. 헤더 주석/경로 문자열에만 이름이 스쳐 지나가.
• 그래서 이 챕터는: 경계선 위쪽(계약, 여기 실재) 은 verbatim 코드로 못 박고, 경계선 아래쪽(소켓 몸통, 여기 없음) 은 "이런 게 저 아래 있다"고 개념으로만 가리킬 거야. recvfrom/SendTo를 실제로 부르는 줄은 이 클론에서 못 보여줘 — 실제 대조가 필요하면 OnlineSubsystemUtils 소스를 따로 봐야 해.

재밌는 건, "여기 없다"는 사실 자체가 이 챕터의 핵심 교훈이라는 거야. 엔진 코어를 아무리 뒤져도 소켓이 안 나오는 이유 — 그게 바로 "코어는 소켓을 직접 안 만진다"는 UE의 설계 철학이거든. 없는 게 정상이야.

지금부터 코드 조각이 나오지만 겁먹지 마. 여기서 볼 건 "소켓을 직접 보내는 코드"가 아니라, 왜 어떤 함수에는 몸통이 없고 어떤 함수는 다음 칸으로 넘기는지만 읽으면 돼.

1) 왜 몸통을 비워둘까? — PURE_VIRTUAL 계약

먼저 딱 하나의 개념. PURE_VIRTUAL.

이건 언리얼 매크로인데, C++의 순수 가상 함수(= 0)랑 같은 뜻이야. "이 함수는 여기서 선언만 한다. 몸통은 하위 클래스가 반드시 채워라"는 강제 계약이지.

너네 서버로 바로 치환하면 이거야:

// 조선 서버 식으로 상상하면 class INetSender { virtual void SendRaw(void* data, int len) = 0; // 선언만. IOCP send는 파생이 채움 };
🔤 기호 사전 — virtual void SendRaw(void* data, int len) = 0
• class = 비슷한 기능을 한 묶음으로 담는 설계도. 여기선 "보내는 일을 할 물건"의 설계도야.
• virtual = "자식 클래스가 이 함수를 자기 방식으로 갈아끼울 수 있다"는 표시.
• void = 이 함수는 호출한 쪽에 답을 돌려주지 않는다는 뜻.
• void* = "무슨 모양인지 아직 정하지 않은 주소표". 그냥 바이트 덩어리의 시작 위치라고 보면 돼.
• int len = len이라는 정수 칸. 보낼 바이트가 몇 개인지 담는 숫자야.
• = 0 = "여기선 몸통을 안 만든다. 자식이 반드시 채워라"라는 순수 가상 함수 표시.
🔁 이제 다시 보자. class INetSender는 "보내기 담당 설계도"이고, virtual void SendRaw(...) = 0은 "보내는 함수 이름만 정해둘 테니 실제 전송은 자식이 채워라"야. 즉 이 예시는 계약만 있고 트럭 운전은 없는 코드로 읽으면 돼.

인터페이스에 선언만 있고, 실제 IOCP WSASend는 파생 클래스가 구현하는 그 구조 — UE도 완전히 똑같아.

자, 이제 송신 계약의 실물을 봐. 이게 그 유명한 "가장 낮은 층", 채널·번들·PacketHandler 다 끝나고 최종 바이트가 도착하는 지점이야:

NetConnection.h:1044-1046 — verbatim

// @todo: Traits should be passed within bit readers/writers, eventually virtual void LowLevelSend(void* Data, int32 CountBits, FOutPacketTraits& Traits) PURE_VIRTUAL(UNetConnection::LowLevelSend,);
🔤 기호 사전 — virtual void LowLevelSend(void* Data, int32 CountBits, FOutPacketTraits& Traits)
• virtual = "진짜 동작은 자식 클래스가 바꿔 끼울 수 있다"는 표시.
• void = 답을 돌려주는 함수가 아니라, 그냥 보내는 행동만 하는 함수라는 뜻.
• void* Data = 실제로 내보낼 바이트 덩어리의 시작 주소. 내용물 모양은 여기서 모른다.
• int32 CountBits = 32비트 정수로 적은 비트 개수. 바이트가 아니라 비트 단위 길이라는 게 포인트야.
• FOutPacketTraits& Traits = 패킷의 부가 정보 봉투를 원본으로 넘겨받는다. &는 복사본 말고 진짜 것을 만진다는 뜻.
• PURE_VIRTUAL(...) = "이 함수는 코어에 몸통이 없다. 하위 클래스가 반드시 채워라"라는 UE식 계약 매크로.
• UNetConnection::LowLevelSend = UNetConnection에 딸린 LowLevelSend라는 소속 표시. ::는 "~의"라고 읽으면 돼.
🔁 이제 다시 보자. 이 줄은 "커넥션은 Data를 CountBits만큼 낮은 층으로 보내야 한다고 약속하지만, 실제 소켓 전송 몸통은 여기 없다"야. PURE_VIRTUAL이 보이면 회사 규칙만 있고 기사는 아직 안 나온다고 읽으면 돼.

봤지? LowLevelSend인데 { ... }가 없어. PURE_VIRTUAL(...) 하나로 끝. 몸통이 없다. 이게 "택배 회사는 규칙만 정한다"의 코드 버전이야. 실제로 이 Data를 소켓에 밀어넣는 건 UIpConnection(=이 트리에 없는 기사)이 채워.

같은 패턴이 드라이버 레벨에도 있어. 소켓 서브시스템 자체를 뭘 쓸지 고르는 것도 코어는 안 정해:

NetDriver.h:1841 — verbatim

virtual class ISocketSubsystem* GetSocketSubsystem() PURE_VIRTUAL(UNetDriver::GetSocketSubsystem, return NULL;);
🔤 기호 사전 — virtual class ISocketSubsystem* GetSocketSubsystem() PURE_VIRTUAL(... return NULL;)
• virtual = 드라이버 자식 클래스가 이 함수를 자기 플랫폼용으로 채운다는 뜻.
• class ISocketSubsystem* = 소켓 서브시스템을 가리키는 주소표를 돌려준다는 뜻. *는 "실물 말고 그 실물이 있는 곳"을 가리켜.
• GetSocketSubsystem() = "어떤 소켓 시스템을 쓸지 가져와"라는 함수 이름.
• PURE_VIRTUAL = 여기서도 몸통 없음. 코어는 어떤 소켓을 쓸지 직접 모른다.
• return NULL = 만약 잘못 불리면 "가리키는 게 아무것도 없음"을 돌려주라는 기본 대답.
🔁 이제 다시 보자. GetSocketSubsystem은 "소켓 라이브러리 주소를 줘"라는 함수인데, 코어는 PURE_VIRTUAL로 비워둬. 이어 읽으면 "소켓 종류는 플랫폼별 기사 클래스가 정해라"가 된다.

"어떤 소켓 라이브러리를 쓸지는 서브클래스가 정해라. 코어는 모른다." — 이 한 줄이 코어를 OS/플랫폼으로부터 완전히 떼어놓는 장치야. Windows든, PS5든, 스팀 소켓이든, 코어 코드는 하나도 안 바뀌어. 기사만 갈아끼우면 돼.

2) 받는 길: TickDispatch → 주소 판별 → 커넥션

송신을 봤으니 이제 수신. 받는 쪽 규약은 헤더 주석에 통째로 적혀 있어. 이거 하나면 수신 경로의 큰 그림이 다 잡혀:

NetDriver.h:113-120 — verbatim

* On both Clients and Server, UNetDriver::TickDispatch is typically responsible for receiving network data. * Typically, when we receive a packet, we inspect its address and see whether or not it's from a connection we already know about. * We determine whether or not we've established a connection for a given source address by simply keeping a map from FInternetAddr to UNetConnection. * * If a packet is from a connection that's already established, we pass the packet along to the connection via UNetConnection::ReceivedRawPacket. * If a packet is not from a connection that's already established, we treat is as "connectionless" and begin the handshaking process. * * See StatelessConnectionHandlerComponent.cpp for details on how this handshaking works.
🔤 기호 사전 — UNetDriver::TickDispatch, FInternetAddr, UNetConnection::ReceivedRawPacket
• UNetDriver::TickDispatch = UNetDriver에 딸린 TickDispatch. ::는 "~소속"이고, 이 함수는 매 틱 네트워크 수신 쪽을 맡는 이름이야.
• FInternetAddr = IP와 포트를 UE식으로 감싼 주소표 상자.
• UNetConnection = "이미 알고 있는 상대와의 연결"을 나타내는 객체.
• map from FInternetAddr to UNetConnection = 주소표를 넣으면 커넥션이 나오는 주소록. "이 주소 아는 손님이야?"를 여기서 찾는다.
• UNetConnection::ReceivedRawPacket = 아는 커넥션이면 그 커넥션 소속의 ReceivedRawPacket으로 날바이트를 넘긴다는 뜻.
• connectionless = 아직 커넥션이 없는 상태. "주소는 보이는데 회원 등록은 안 된 손님" 정도로 보면 돼.
🔁 이제 다시 보자. 이 주석은 "패킷을 받으면 주소를 보고, 주소록에 있으면 그 커넥션의 ReceivedRawPacket으로 보내고, 없으면 connectionless 핸드셰이크로 간다"야. 소켓에서 어떻게 받는지는 말하지 않고, 받은 뒤 어디로 보낼지만 정한다.

한 문장씩 풀면:

  1. TickDispatch가 수신 담당이다. 매 프레임 불려서 소켓에 도착한 패킷을 꺼내와. (앞 챕터 netdriver-tick에서 본 그 앞단 진입점 맞아.)
  2. 패킷을 받으면 송신자 주소(FInternetAddr)를 본다. 이게 IP+포트를 감싼 UE 추상 주소 타입이야.
  3. 드라이버는 FInternetAddr → UNetConnection 맵을 유지해. 이 주소에서 온 패킷이 "이미 아는 커넥션"인지 판별하는 방법이 그냥 이 맵 조회야.
  4. 이미 아는 커넥션이면 → 그 커넥션의 ReceivedRawPacket으로 넘겨. (여기서부터가 앞 챕터들에서 배운 채널/번치 처리 흐름이야.)
  5. 모르는 주소면 → "connectionless"로 취급하고 핸드셰이크 시작. (자세한 건 handshake 챕터로.)

여기서 잠깐, 예측해봐: 그럼 저 주석에서 "소켓에서 실제로 바이트를 꺼내오는 recvfrom 호출"은 몇 번째 문장에 있을까?

.

.

반전: 한 문장도 없어. 위 주석은 전부 "받은 다음에 뭘 하느냐"만 말해. 정작 어떻게 받느냐(recvfrom 자체)는 UNetDriver가 아니라 UIpNetDriver::TickDispatch(=이 트리에 없는 기사)가 override해서 채워. 코어 주석은 "받는다고 치고, 그 다음 규칙은 이거다"까지만 정의해. 소켓 시스템콜은 또 경계선 아래에 있는 거지. 이 패턴이 계속 반복되는 게 느껴지지?

3) 보내는 길: FlushNet → LowLevelSend

송신 흐름은 두 함수가 짝을 이뤄. 위층 FlushNet이 "묶어서", 아래층 LowLevelSend가 "내보내".

NetConnection.h:1057-1061 — verbatim

/** * flushes any pending data, bundling it into a packet and sending it via LowLevelSend() * also handles network simulation settings (simulated lag, packet loss, etc) unless bIgnoreSimulation is true */ ENGINE_API virtual void FlushNet(bool bIgnoreSimulation = false);
🔤 기호 사전 — ENGINE_API virtual void FlushNet(bool bIgnoreSimulation = false)
• ENGINE_API = 이 함수가 엔진 모듈 밖에서도 보이게 하는 UE 표시. "다른 모듈도 이 문을 써도 됨" 정도야.
• virtual = 필요하면 자식 클래스가 동작을 바꿔 끼울 수 있다는 표시.
• void = 답을 돌려주는 함수가 아니라, 쌓인 데이터를 처리하고 끝나는 함수라는 뜻.
• bool = 참/거짓만 담는 스위치.
• bIgnoreSimulation = b로 시작하니까 보통 bool 스위치. "네트워크 시뮬레이션을 무시할까?"라는 값이야.
• = false = 아무 말 안 하고 부르면 기본값은 false, 즉 시뮬레이션을 무시하지 않는 쪽.
🔁 이제 다시 보자. FlushNet(false)는 "쌓인 데이터를 패킷으로 묶어 보내되, 기본적으로 네트워크 시뮬레이션 규칙도 적용한다"로 읽으면 돼. 여기엔 몸통이 있으니 포장 작업은 코어가 직접 한다는 뜻이야.

FlushNet은 쌓여 있던 데이터를 패킷 하나로 묶어서(bundling) LowLevelSend()로 보내. 덤으로 네트워크 시뮬레이션(일부러 랙/패킷로스 흉내내기 — 테스트용)도 여기서 처리해. 이건 ENGINE_API virtual에 몸통이 실제로 있는 함수야(계약이 아니라 구현). "봉투에 담는 일"은 코어가 직접 해.

근데 그 봉투를 트럭에 싣는 마지막 한 걸음, LowLevelSend는? 위에서 봤듯이 PURE_VIRTUAL, 몸통 없음. 딱 여기가 경계선이야:

FlushNet (몸통 있음, 코어가 봉투 포장) │ ▼ LowLevelSend (몸통 없음 ← 경계선 ← UIpConnection이 소켓 SendTo로 채움)

봉투 포장까지는 회사가, 최종 배달만 기사가. 정확히 여기서 갈려.

커넥션리스 송신은 왜 "드라이버"에 따로 있나

여기 헷갈리기 쉬운 게 하나 더 있어. 송신 계약이 두 곳에 있어. 하나는 방금 본 UNetConnection::LowLevelSend(커넥션 통해서). 다른 하나는 UNetDriver에 직접:

NetDriver.h:1697-1707 — verbatim

/** * Sends a 'connectionless' (not associated with a UNetConection) packet, to the specified address. * NOTE: Address is an abstract format defined by subclasses. Anything calling this, must use an address supplied by the net driver. * * @param Address The address the packet should be sent to (format is abstract, determined by net driver subclasses) * @param Data The packet data * @param CountBits The size of the packet data, in bits * @param Traits Traits for the packet, if applicable */ virtual void LowLevelSend(TSharedPtr<const FInternetAddr> Address, void* Data, int32 CountBits, FOutPacketTraits& Traits) PURE_VIRTUAL(UNetDriver::LowLevelSend,);
🔤 기호 사전 — virtual void LowLevelSend(TSharedPtr<const FInternetAddr> Address, void* Data, int32 CountBits, FOutPacketTraits& Traits)
• TSharedPtr<...> = 여러 곳이 같이 들고 있을 수 있는 주소표 손잡이. 아무도 안 쓰면 정리되는 UE 스마트 포인터야.
• const FInternetAddr = 주소 내용은 읽기만 하고 바꾸지 않겠다는 약속.
• Address = 아직 커넥션이 없으니 "누구한테 보낼지"를 주소로 직접 받는 칸.
• void* Data = 보낼 바이트 덩어리의 시작 주소.
• int32 CountBits = 보낼 데이터 길이. 여기서도 바이트가 아니라 비트 수야.
• FOutPacketTraits& Traits = 패킷 부가 정보를 원본으로 넘겨받는 칸. &라서 복사본이 아니야.
• PURE_VIRTUAL(UNetDriver::LowLevelSend,) = 드라이버도 "주소로 직접 보내는 계약"만 있고, 진짜 소켓 송신은 하위 클래스 몫.
🔁 이제 다시 보자. 커넥션 버전은 "이미 아는 상대에게 보내기"였고, 이 드라이버 버전은 Address를 직접 받아 아직 커넥션 없는 상대에게도 쏠 수 있는 계약이야. 그래서 핸드셰이크 첫 응답 같은 길이 여기로 간다.

왜 커넥션 버전이랑 드라이버 버전이 따로 필요할까? 답은 닭이 먼저냐 달걀이 먼저냐야. 최초 핸드셰이크 시점엔 아직 UNetConnection 객체가 없어. 아직 "이 상대가 누군지" 성립 전이니까. 근데 뭔가는 보내야 핸드셰이크가 시작되잖아. 그래서 커넥션 없이 주소만 보고 직접 쏘는 통로가 드라이버에 별도로 있는 거야. 시그니처 차이를 봐 — 이쪽은 첫 인자가 TShared Ptr<const FInternetAddr> Address야. "누구한테"를 주소로 직접 지정하지. (이것도 PURE_VIRTUAL이라 실제 몸통은 역시 기사 몫.)

소켓 직전에 끼어드는 훅

마지막으로, 이 최하단 송신 바로 앞에 가로채기 델리게이트가 하나 걸려 있어. 알아두면 좋아:

NetConnection.h:176-182 — verbatim

* Delegate for hooking the net connections 'LowLevelSend' (at the socket level, after PacketHandler parsing) * * @param Data The data being sent * @param Count The number of bytes being sent * @param bBlockSend Whether or not to block the send (defaults to false) */ DECLARE_DELEGATE_ThreeParams(FOnLowLevelSend, void* /*Data*/, int32 /*Count*/, bool& /*bBlockSend*/);
🔤 기호 사전 — DECLARE_DELEGATE_ThreeParams(FOnLowLevelSend, void* /*Data*/, int32 /*Count*/, bool& /*bBlockSend*/);
• DECLARE_DELEGATE_ThreeParams = "인자 3개짜리 델리게이트 타입을 만든다"는 UE 매크로. 델리게이트는 나중에 끼워 넣을 수 있는 콜백 자리야.
• FOnLowLevelSend = 새로 만드는 델리게이트 이름. "LowLevelSend 직전에 부를 훅"이라고 보면 돼.
• void* /*Data*/ = 보낼 데이터 시작 주소. /*Data*/는 사람에게 보여주는 이름표 주석이야.
• int32 /*Count*/ = 보낼 바이트 수를 담는 정수 칸.
• bool& /*bBlockSend*/ = "보내기를 막을까?" 스위치를 원본으로 넘긴다. &라서 콜백이 값을 바꾸면 바깥에도 반영돼.
• ; = 선언 한 줄이 여기서 끝난다는 마침표.
🔁 이제 다시 보자. 이 줄은 "소켓으로 나가기 직전, Data와 Count를 보여주고 bBlockSend를 바꿀 기회를 주는 콜백 자리를 만든다"야. 그래서 bBlockSend가 켜지면 마지막 문 앞에서 전송을 멈출 수 있어.

"소켓 레벨에서, PacketHandler 파싱까지 다 끝난 뒤" 나가기 직전 데이터를 훔쳐볼 수 있는 훅이야. bBlockSend를 true로 만들면 아예 안 나가게 막을 수도 있어. 디버깅/보안/패킷 검열 같은 데 쓰여. "정말 마지막 문 앞"이 어디인지 감이 오지?

5) 우리 서버랑 비교: IOCP 워커 ↔ IpNetDriver

이제 익숙한 땅으로 와보자. 조선 서버의 IOCP 구조랑 UE 소켓 층을 나란히 놓으면 대응이 깔끔해:

조선 서버 (IOCP + 싱글스레드 액터)UE 네트워크
IOCP 워커 스레드가 WSARecv 완료 통지 받음UIpNetDriver::TickDispatch가 recvfrom (플러그인)
받은 raw 버퍼를 세션/유저 객체로 라우팅FInternetAddr → UNetConnection 맵 조회
처리 큐에 넣어 싱글스레드 로직으로 넘김UNetConnection::ReceivedRawPacket으로 넘김
로직 스레드가 응답 패킷 만들어 WSASendFlushNet → LowLevelSend → SendTo (플러그인)
SIOCPPacket 헤더의 wID로 패킷 종류 식별FOutPacketTraits로 패킷 속성 전달

딱 하나 크게 다른 점: 조선 서버는 IOCP WSARecv/WSASend가 네 코드에 직접 박혀 있어. 소켓 시스템콜이 네 소스에서 보여. 반면 UE는 그 소켓 호출을 PURE_VIRTUAL 계약으로 코어에서 떼어내서 플러그인에 숨겨놨어.

왜 이렇게까지 할까? 조선 서버는 Windows IOCP 한 플랫폼만 돌리면 되니까 직접 박아도 돼. 근데 UE는 PC/콘솔/모바일/스팀소켓 수십 플랫폼을 같은 코어 코드로 굴려야 해. 그래서 "소켓 만지는 부분만" 갈아끼울 수 있게 계약으로 뽑아낸 거야. 네 IOCP 코드를 SendRaw() 인터페이스 뒤로 숨기고 플랫폼별로 구현체를 갈아끼운다고 상상하면, 그게 정확히 UIpConnection이야.

또 하나: 조선 서버는 IOCP 워커가 멀티스레드로 받아서 큐로 싱글스레드에 넘기잖아. UE도 큰 그림은 같아 — 소켓에서 받는 층과 게임 로직 층이 분리돼 있고, TickDispatch가 그 경계에서 "받아서 넘기는" 역할을 해. "받는 놈 따로, 처리하는 놈 따로"라는 발상은 완전히 똑같은 거지.

6) 그래서 뭘 배운 거야

  • 엔진 코어는 소켓을 직접 안 만진다. LowLevelSend, GetSocketSubsystem, 드라이버의 커넥션리스 LowLevelSend — 전부 PURE_VIRTUAL 계약일 뿐, 몸통이 비어 있어.
  • 실제 recvfrom / SendTo는 OnlineSubsystemUtils 플러그인의 UIpNetDriver / UIpConnection이 채운다. 그게 "택배 기사"고, 이 학습 트리엔 그 기사가 안 들어 있어(경계선 아래는 미포함).
  • 받는 길: TickDispatch(recv) → 주소 판별(FInternetAddr 맵) → 아는 놈은 ReceivedRawPacket, 모르는 놈은 핸드셰이크.
  • 보내는 길: FlushNet(봉투 포장) → LowLevelSend(경계선, 트럭 배달).
  • 이 "계약/구현 분리"가 UE를 수십 플랫폼에 이식 가능하게 만든 장치. 조선 서버가 IOCP를 직접 박은 것과 대비되는 지점.

전제가 헷갈리면:

  • 소켓 위 계층(채널/번치)이 안 그려지면 → netconnection-overview

  • FlushNet이 어떻게 번들링하는지 → send-callchain
  • 매 프레임 TickDispatch가 언제 불리는지 → netdriver-tick
