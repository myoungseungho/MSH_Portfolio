RepLayout: 프로퍼티를 비트로 눕히는 법

언리얼 네트워크 · 15 / 43

들어가기 전에: "무엇을 보낼까"와 "어떻게 보낼까"는 다른 문제야

네가 만든 액터에 Health, Mana, Position, 그리고 TArray<int32> Buffs 같은 프로퍼티가 있다고 하자. 이게 서버에서 바뀌면 클라로 보내야 돼. 그런데 여기엔 두 개의 서로 다른 질문이 숨어 있어.

  • 무엇을 보낼까 — 어떤 프로퍼티가 리플리케이트 대상이냐. 이건 DOREPLIFETIME 매크로가 정하는 일이고, 그 이야기는 → lifetime-props 에서 했어.
  • 어떻게 보낼까 — 정해진 그 프로퍼티들을 실제 비트로 어떻게 눕히느냐. 순서는? 배열은? 리플렉션 없이 어떻게 빠르게 훑느냐? 이게 이번 챕터, RepLayout 이야.

비유부터 하나 깔고 가자. 이삿짐을 트럭에 실을 때, 매번 방마다 뛰어다니면서 "이건 뭐지? 크기가 얼마지? 어디 실을까?" 고민하면 하루종일 걸려. 그래서 이삿짐 센터는 미리 짐 목록표(패킹 리스트) 를 만들어. "1번 상자 = 부엌, 무게 5kg, 트럭 뒤쪽. 2번 상자 = ..." 이렇게. 실을 때는 그냥 표 순서대로 번호만 따라가면 돼. 고민 제로.

언리얼도 똑같은 짓을 해. 클래스 하나당 "직렬화 명령표" 를 딱 한 번 만들어서 캐싱해 두고, 매 전송마다 그 표를 인덱스로 훑기만 해. 그 표를 만들고 들고 있는 객체가 FRepLayout, 표의 각 줄이 FRepLayoutCmd 야.

이걸 실제로 구현하는 게 이 두 파일이야:

  • Engine/Private/RepLayout.cpp (8601줄)
  • Engine/Public/Net/RepLayout.h (1909줄)

이 클론에 소스 있음. 아래 코드는 전부 실제 원문 그대로고 파일:줄번호 를 달았어.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 표처럼 생긴 코드라 처음엔 딱딱해 보이지만, 바로 아래 🔤 상자에서 낯선 기호를 하나씩 풀어줄게. 코드를 외우는 게 아니라 "아, 이 줄은 표의 한 칸을 설명하는구나"만 잡으면 돼.

1. 표의 한 줄은 어떻게 생겼나 — FRepLayoutCmd

먼저 "짐 목록표의 한 줄"부터 보자. 프로퍼티 하나가 이 구조체 하나로 눕혀져.

class FRepLayoutCmd { public: /** Pointer back to property, used for NetSerialize calls, etc. */ FProperty* Property; /** For arrays, this is the cmd index to jump to, to skip this arrays inner elements. */ uint16 EndCmd; /** For arrays, element size of data. */ uint16 ElementSize; /** Absolute offset of property in Object Memory. */ int32 Offset;

— RepLayout.h:856

🔤 기호 사전 — class FRepLayoutCmd
• class = 여러 값과 함수를 한데 묶는 설계도 상자. 여기서는 "직렬화 명령 한 줄"이 어떤 칸을 갖는지 정해.
• public: = 아래 칸들은 바깥 코드가 꺼내 볼 수 있다는 표시. 표를 훑는 코드가 Cmd.Property, Cmd.Offset 처럼 읽을 수 있어.
• FProperty* = FProperty를 직접 들고 있는 게 아니라 어디 있는지 가리키는 주소표. *는 포인터라는 뜻이야.
• /** ... */ = 긴 설명 주석. 사람한테만 보이는 메모고, 실행되는 코드는 아니야.
• uint16 / int32 = 정해진 크기의 숫자 상자. uint16은 작은 양수 번호, int32는 더 큰 정수 오프셋을 담는다고 보면 돼.
• ; = "이 한 칸 선언은 여기서 끝"이라는 마침표.
• EndCmd / Offset = 이름 그대로 표 안에서 점프할 끝 번호, 메모리에서 몇 바이트 떨어졌는지를 담는 칸.
🔁 이제 다시 보자. FProperty* Property는 "원래 프로퍼티로 돌아가는 주소표", uint16 EndCmd는 "배열을 건너뛸 점프 번호", int32 Offset은 "오브젝트 안에서 값이 있는 거리"야. 이어 읽으면 "값을 빠르게 찾고, 배열이면 건너뛸 수 있게 만든 명령표 한 줄" 로 보이지?

세 개만 눈에 담아.

  • Property — 원래 프로퍼티로 돌아가는 포인터. 실제 값을 비트로 바꿀 때 이 녀석의 NetSerializeItem 을 부른다.
  • Offset — 오브젝트 메모리에서 이 프로퍼티가 몇 바이트째에 있느냐. 이게 핵심이야. 이 오프셋만 있으면 리플렉션으로 "이름이 뭐지, 타입이 뭐지" 다시 안 물어보고, 오브젝트포인터 + Offset 으로 값 위치에 바로 꽂는다. 이삿짐 표의 "트럭 뒤쪽"에 해당해.
  • EndCmd — 배열일 때만 의미 있어. "이 배열 안쪽 요소들을 건너뛰려면 몇 번 명령으로 점프해라"는 표지판. 뒤에서 다시 나온다.

그리고 각 줄에는 "이게 어떤 종류의 짐이냐" 태그가 붙어:

enum class ERepLayoutCmdType : uint8 { DynamicArray = 0, //! Dynamic array Return = 1, //! Return from array, or end of stream Property = 2, //! Generic property PropertyBool = 3, PropertyFloat = 4, PropertyInt = 5, PropertyByte = 6, PropertyName = 7, PropertyObject = 8, PropertyUInt32 = 9, PropertyVector = 10, PropertyRotator = 11,

— RepLayout.h:722

🔤 기호 사전 — enum class ERepLayoutCmdType : uint8
• enum class = 정해진 보기 중 하나만 고르는 번호 붙은 메뉴판. 여기서는 "이 명령 줄이 배열인지, bool인지, vector인지"를 고르는 메뉴야.
• : uint8 = 그 메뉴 번호를 1바이트짜리 작은 숫자로 저장하겠다는 뜻. 작게 저장해서 표가 가벼워져.
• { ... } = 메뉴판 안쪽. 이 중 하나가 Cmd.Type에 들어간다.
• DynamicArray = 0 = DynamicArray라는 메뉴에 숫자 0번을 붙인 것. =는 여기서 "이 번호로 정하자"야.
• //! Dynamic array = 사람 읽으라고 붙인 설명 주석. 실행되는 코드는 아니야.
• , = 메뉴 항목을 다음 항목과 나누는 쉼표.
🔁 이제 다시 보자. enum class는 명령 종류 메뉴판이고, DynamicArray, Return, PropertyBool 같은 항목은 표 한 줄에 붙는 딱지야. 표를 훑는 코드는 이 딱지만 보고 "배열이면 안으로 들어가고, 숫자면 바로 직렬화" 를 고른다.

DynamicArray 와 Return 이 특수 명령이고, 나머지는 전부 리프(잎) 프로퍼티야. Bool, Float, Vector, Rotator... 흔한 타입은 아예 전용 타입 번호를 줘서 더 빠른 경로로 처리해. 표를 훑다가 이 태그만 보고 "아 이건 배열이니 재귀, 이건 일반 값이니 바로 직렬화" 를 판단하는 거지.

2. 표는 언제 만들어지나 — InitFromClass

표는 매 전송마다 만들면 안 돼. 그럼 캐싱의 의미가 없잖아. 클래스당 딱 한 번, 처음 필요할 때 만들어서 계속 재사용해. 그 진입점이 InitFromClass (RepLayout.cpp:6081) 야.

구조체용 빌드(InitFromStruct, RepLayout.cpp:6552)를 보면 표를 채우는 리듬이 잘 보여:

Parents[ParentHandle].CmdStart = Cmds.Num(); RelativeHandle = InitFromProperty_r<ERepBuildType::Struct>(SharedParams, StackParams); Parents[ParentHandle].CmdEnd = Cmds.Num(); Parents[ParentHandle].Offset = GetOffsetForProperty<ERepBuildType::Struct>(**It); SetupRepStructFlags(Parents[ParentHandle], /**bSkipCustomDeltaCheck=*/true);

— RepLayout.cpp:6587

🔤 기호 사전 — Parents[ParentHandle].CmdStart = Cmds.Num();
• Parents[ParentHandle] = Parents 배열에서 ParentHandle번 칸을 꺼내는 말. 대괄호 []는 "몇 번째 칸"이야.
• . = 그 칸 안의 작은 칸을 꺼내는 표시. CmdStart는 Parent 상자 안에 있는 값.
• Cmds.Num() = Cmds 배열에 지금 몇 줄 들어있는지 세어 달라는 함수 호출. ()는 "함수 실행".
• InitFromProperty_r<ERepBuildType::Struct>(...) = 프로퍼티 하나를 표로 펼치는 함수. <...>는 "어떤 방식으로 펼칠지"를 붙여 주는 표시고, _r은 재귀로 안쪽까지 파고든다는 힌트야.
• **It = 반복자가 가리키는 것을 한 번 더 열어 실제 프로퍼티를 꺼내는 모양. *가 두 번이라 "주소표를 두 겹 벗긴다" 정도로 봐.
• /**bSkipCustomDeltaCheck=*/true = 호출 자리에서 이 true가 무슨 뜻인지 적어 둔 주석. 실제 값은 그냥 true야.
🔁 이제 다시 보자. CmdStart = Cmds.Num()으로 시작 줄을 찍고, InitFromProperty_r(...)로 프로퍼티를 여러 명령 줄로 펼친 뒤, CmdEnd = Cmds.Num()으로 끝 줄을 찍는다. 한 줄로: "이 Parent가 Cmds 배열의 몇 번부터 몇 번까지를 차지하는지 기록한다."

읽는 법:

  1. CmdStart = Cmds.Num() — 지금 표에 몇 줄 있나 기록. "이 프로퍼티는 여기서부터 시작".
  2. InitFromProperty_r<>(...) — 프로퍼티 하나를 펼쳐서 Cmds 배열에 명령을 밀어넣어. 단순 값이면 한 줄, 구조체면 여러 줄, 배열이면 DynamicArray 시작 + 안쪽 + 끝. 이름 뒤의 _r 은 재귀(recursive)라는 뜻이야 — 구조체 안에 구조체가 있어도 파고들어 평탄하게 눕힌다.
  3. CmdEnd = Cmds.Num() — 펼치고 나서 다시 몇 줄인지 기록. "이 프로퍼티는 여기까지".

여기서 두 개의 배열이 등장하는데 헷갈리기 쉬우니 정리하자:

  • Parents (FRepParentCmd) — 최상위 프로퍼티 단위. Health 하나, Buffs 하나. 각 Parent 는 CmdStart~CmdEnd 로 "나를 구성하는 하위 명령 줄들"을 가리켜.
  • Cmds (FRepLayoutCmd) — 실제로 평탄하게 펼쳐진 명령 줄들. 구조체 프로퍼티 하나가 여러 Cmd 로 쪼개질 수 있어.

즉 트리 구조(프로퍼티 안에 프로퍼티)를 한 줄로 쭉 편 배열로 바꾸는 게 빌드 단계의 전부야. 편 다음부터는 트리를 몰라도 돼. 그냥 배열 인덱스만 있으면 돼.

3. 표를 훑어 비트로 — SerializeProperties_r

자, 이제 표가 준비됐어. 값을 실제 비트로 바꾸는 함수가 SerializeProperties_r (RepLayout.cpp:6659) 야. 이 함수 하나가 송신과 수신 둘 다 처리해. 어떻게? 곧 나와.

명령 배열을 도는 루프의 심장부:

for (int32 CmdIndex = CmdStart; CmdIndex < CmdEnd && !Ar.IsError(); CmdIndex++) { const FRepLayoutCmd& Cmd = Cmds[CmdIndex]; check(Cmd.Type != ERepLayoutCmdType::Return); if (Cmd.Type == ERepLayoutCmdType::DynamicArray) { UE_NET_TRACE_DYNAMIC_NAME_SCOPE(Cmd.Property->GetFName(), Ar, Collector, ENetTraceVerbosity::Trace); SerializeProperties_DynamicArray_r(Ar, Map, CmdIndex, Data + Cmd, bHasUnmapped, ArrayDepth + 1, SharedInfo, Collector, OwningObject); CmdIndex = Cmd.EndCmd - 1; // The -1 to handle the ++ in the for loop continue; }

— RepLayout.cpp:6672

🔤 기호 사전 — for (int32 CmdIndex = CmdStart; CmdIndex < CmdEnd && !Ar.IsError(); CmdIndex++)
• for (...) = 정해진 구간을 반복해서 도는 루프. 여기서는 CmdStart부터 CmdEnd 전까지 한 줄씩 돈다.
• CmdIndex++ = CmdIndex를 1 올려서 다음 명령 줄로 이동.
• && = "그리고". CmdIndex가 범위 안이고, Ar에 에러도 없어야 계속 돈다.
• !Ar.IsError() = Ar.IsError()가 아니면, 즉 아직 에러가 없으면.
• const FRepLayoutCmd& Cmd = 명령 줄 하나를 복사하지 않고 원본을 읽기 전용 별명으로 잡는다. &는 원본 별명, const는 안 바꾼다는 약속.
• Cmd.Type == ERepLayoutCmdType::DynamicArray = 이 명령 줄의 종류가 "동적 배열"인지 비교. ==는 같다, ::는 그 메뉴판 안의 항목이라는 뜻.
• check(...) = "이 조건은 반드시 맞아야 한다"는 개발용 안전장치. 틀리면 바로 잡으라고 터뜨린다.
• UE_NET_TRACE_DYNAMIC_NAME_SCOPE(...) = 네트워크 추적용 매크로. 실제 값 처리보다 "지금 어느 프로퍼티를 처리 중인지 기록"하는 표식에 가까워.
• Cmd.Property->GetFName() = Cmd.Property가 가리키는 프로퍼티한테 이름을 달라고 묻는 것. ->는 포인터 안쪽 함수 호출.
• Data + Cmd / ArrayDepth + 1 = 시작점에서 오프셋만큼 더 가거나, 배열 깊이를 한 단계 올리는 덧셈.
• Cmd.EndCmd - 1 = 배열 끝 번호 바로 앞까지 점프하겠다는 계산. 뒤에서 for가 ++를 한 번 더 하니까 미리 1을 뺀다.
• continue = 이번 반복은 여기서 끝내고 바로 다음 줄로 넘어가라는 신호.
🔁 이제 다시 보자. 이 루프는 Cmds 표를 CmdStart부터 한 줄씩 읽어. Cmd.Type이 DynamicArray면 배열 처리 함수로 들어갔다가, Cmd.EndCmd - 1로 배열 안쪽 명령을 건너뛴다. 즉 "표를 직선으로 훑다가 배열 표지판을 만나면 안쪽은 전용 함수에 맡기고 점프" 하는 코드야.

CmdStart 부터 CmdEnd 까지 그냥 for 로 돈다. 리플렉션 순회가 아니야. 배열 인덱싱이야. 이게 빠른 이유의 전부지.

배열(DynamicArray)을 만나면? 안쪽으로 재귀(SerializeProperties_DynamicArray_r)를 태우고, 돌아오면 CmdIndex = Cmd.EndCmd - 1 로 점프해. 아까 표 한 줄에 있던 EndCmd 가 여기서 쓰여. 배열 안쪽 요소 명령들을 한 방에 건너뛰는 표지판이었던 거지. (-1 은 for 의 ++ 가 다시 더해줄 걸 미리 빼둔 것뿐이야. 자잘한 거.)

배열이 아닌 일반 리프에 오면 진짜 직렬화가 일어나:

else { UE_NET_TRACE_DYNAMIC_NAME_SCOPE(Cmd.Property->GetFName(), Ar, Collector, ENetTraceVerbosity::Trace); GNumSharedSerializationMiss++; if (!Cmd.Property->NetSerializeItem(Ar, Map, (Data + Cmd).Data)) { bHasUnmapped = true; } }

— RepLayout.cpp:6748

🔤 기호 사전 — Cmd.Property->NetSerializeItem(Ar, Map, (Data + Cmd).Data)
• else = 위의 if가 아니면 여기로 온다. 즉 배열이 아닌 일반 프로퍼티 처리야.
• GNumSharedSerializationMiss++ = 카운터를 1 올린다. ++는 "하나 더하기".
• UE_NET_TRACE_DYNAMIC_NAME_SCOPE(...) = 추적 로그에 "지금 이 프로퍼티 처리 중"이라고 표시하는 매크로.
• -> = 포인터가 가리키는 상자 안의 함수를 부르는 화살표. Cmd.Property->NetSerializeItem은 프로퍼티한테 "네 값을 비트로 처리해"라고 시키는 것.
• !Cmd.Property->NetSerializeItem(...) = 직렬화가 성공하지 않았으면. 앞의 !는 "아니면/실패면".
• (Data + Cmd).Data = 데이터 시작점에 Cmd가 가진 오프셋 정보를 더해 진짜 값 위치를 찾고, 그 안의 Data 포인터를 꺼낸다.
• bHasUnmapped = true = "아직 매핑 안 된 참조가 있었다"는 깃발을 켠다. b로 시작하면 보통 참/거짓 값이야.
🔁 이제 다시 보자. 배열이 아니면 Cmd.Property가 알고 있는 직렬화 함수 NetSerializeItem을 부르고, 값 위치는 (Data + Cmd).Data로 바로 찍는다. 한 줄로: "표 한 줄을 보고 값 주소를 찾아, 그 타입 전용 방식으로 비트에 쓰거나 읽는다."

(Data + Cmd).Data — 오브젝트 메모리 시작 위치에 아까 그 Offset 을 더해 값의 정확한 위치를 구하고, Cmd.Property->NetSerializeItem(Ar, ...) 으로 그 값을 비트로 바꿔.

여기서 예측 하나 해봐

NetSerializeItem 은 값 → 비트로 쓰는 함수일까, 비트 → 값으로 읽는 함수일까? 송신 함수에서 불렀으니 당연히 "쓰기"겠지?

...맞춰봐.

반전: 둘 다야. 방향을 정하는 건 NetSerializeItem 이 아니라 넘겨받은 Ar(FBitArchive) 야. 송신 쪽이 FBitWriter 를 넘기면 Ar.IsSaving() 이 참이라 값을 비트로 쓰고, 수신 쪽이 FBitReader 를 넘기면 Ar.IsLoading() 이 참이라 비트를 값으로 읽어. 함수 본문은 글자 하나 안 바뀌어. 방향만 아카이브가 들고 있는 거지.

그래서 송신용 코드와 수신용 코드를 따로 안 짜. SerializeProperties_r 하나가 양방향을 다 커버해. 버그가 생겨도 한 군데만 고치면 되고, "보낼 때랑 받을 때 순서가 어긋나는" 사고가 원천적으로 안 나. 표를 같은 순서로 훑으니 송신·수신이 자동으로 짝이 맞는다 — 이게 RepLayout 설계의 진짜 우아한 점이야.

4. 배열은 왜 특별한가 — 길이부터 보낸다

배열은 요소 개수가 매번 달라지잖아. 받는 쪽은 몇 개 올지 몰라. 그래서 길이를 먼저 흘려보내:

🔤 기호 사전 — Ar << OutArrayNum
• uint16 OutArrayNum = Array->Num(); = 배열 개수를 담을 작은 숫자 상자를 만들고, 현재 배열 길이를 넣는다.
• Ar << OutArrayNum = 아카이브에 숫자를 흘려보내거나, 반대로 아카이브에서 숫자를 읽어 온다. 방향은 Ar이 Writer인지 Reader인지가 정해.
• const int32 ArrayNum = Ar.IsLoading() ? ... : ... = ? :는 조건에 따라 둘 중 하나를 고르는 짧은 if. 읽는 중이면 받은 개수, 쓰는 중이면 현재 배열 개수를 쓴다.
• (int32)OutArrayNum = OutArrayNum을 int32 숫자로 바꿔 보겠다는 형 변환.
• if (!UE_RepLayout_Private::ValidateArraySize(...)) = 배열 크기 검사가 실패하면 안으로 들어간다. !는 실패면, ::는 그 이름공간 안의 함수라는 뜻.
• Ar.SetError() = 아카이브에 "문제 생김" 깃발을 꽂는다. 뒤쪽 코드는 이 깃발을 보고 더 진행하지 않는다.
• Ar.IsLoading() && OutArrayNum != Array->Num() = 읽는 중이고, 받은 개수와 현재 배열 길이가 다르면. !=는 같지 않다는 뜻.
• (FArrayProperty*)Cmd.Property = Cmd.Property를 배열 프로퍼티 포인터로 보고 쓰겠다는 표시. 배열 크기를 바꾸려면 배열 전용 도구가 필요해.
• FScriptArrayHelper / ArrayHelper.Resize(...) = 배열을 직접 늘리고 줄이는 도우미와 그 함수. 받은 길이에 맞춰 그릇 크기를 바꾼다.
🔁 이제 다시 보자. 먼저 OutArrayNum에 길이를 담고 Ar << OutArrayNum으로 길이를 주고받는다. 받는 쪽이면 그 길이만큼 Resize해서 자리를 맞춘다. 즉 "배열은 내용보다 먼저 몇 개인지 알려 주고, 받은 쪽은 그 숫자만큼 그릇을 늘린다."

Ar << OutArrayNum 한 줄이 또 양방향이야. 보낼 땐 개수를 쓰고, 받을 땐 개수를 읽어 OutArrayNum 에 채워. 받는 쪽은 그 숫자만큼 배열을 Resize 해서 자리를 만든 뒤, 요소마다 안쪽 명령들(CmdIndex+1 ~ EndCmd-1)을 재귀로 반복해. 여기 SerializeProperties_DynamicArray_r (RepLayout.cpp:6608).

ValidateArraySize 도 눈여겨봐. 악의적인 클라가 "배열 20억 개" 라고 뻥쳐서 서버 메모리를 터뜨리는 걸 막는 방어선이야. 네트워크 코드는 항상 상대를 안 믿는다. (보안 이야기는 → security)

6. 우리 서버랑 비교하면

조선협객전 서버로 옮겨서 감을 잡자. 우리는 IOCP 워커 스레드가 패킷을 받아서, 싱글스레드 액터(게임 로직) 쪽으로 넘겨 처리하잖아.

우리가 새 패킷을 만들 때를 떠올려봐. SP_XXX 구조체를 정의하고, 멤버를 한 줄 한 줄 직접 Serialize 하거나 memcpy 하지. pkt.wID = ...; pkt.dwMoney = ...; 이런 식으로 손으로. 구조체 레이아웃이 곧 와이어 포맷이고, 그 순서를 사람이 코드로 박아 둔다. 순서 틀리면? 받는 쪽에서 밀려서 깨져. (우리가 _SERVER_INFO_FOR_TOOL 구조체 바꿀 때 모든 수신측을 lockstep 으로 같이 고쳐야 했던 그 사고랑 정확히 같은 원리야.)

언리얼의 RepLayout 은 그 "손으로 박는 순서"를 리플렉션에서 자동으로 뽑아 Cmds 배열로 만들어 놓은 것이야. 우리가 사람 머리로 유지하던 필드 순서를, 언리얼은 클래스당 한 번 빌드한 표로 유지해. 그래서:

스레드 모델도 비슷해. 우리 IOCP 워커 여러 개가 받아도 게임 로직은 싱글스레드로 직렬화하듯, 언리얼도 리플리케이션은 사실상 단일 흐름(NetDriver Tick, → netdriver-tick)에서 표를 순차로 훑어. "여러 스레드가 같은 표를 동시에 건드려 순서가 꼬이는" 걱정이 없다는 뜻이야.

한 줄로: 우리가 손으로 하던 "필드 순서 계약"을, 언리얼은 표로 자동화했다. 그게 RepLayout 이야.

7. 헷갈리기 쉬운 용어 정리

  • FRepLayout — 한 클래스/구조체/RPC 의 리플리케이트 프로퍼티들을 직렬화 명령 배열(Cmds)로 미리 펼쳐 캐싱한 객체. 매 전송마다 리플렉션을 다시 훑지 않으려고 한 번만 빌드해 재사용.
  • Cmds / FRepLayoutCmd — 프로퍼티 트리를 평탄화한 결과. 한 줄이 프로퍼티 하나(또는 배열 시작/Return)에 대응. Offset·Type·Property 를 들고 있어 순회 시 리플렉션 없이 값에 바로 접근.
  • Parents / FRepParentCmd — 최상위 프로퍼티 단위. 각 Parent 가 CmdStart~CmdEnd 로 자기 하위 Cmds 범위를 가리킴.
  • Handle — 프로퍼티를 가리키는 안정적인 번호. "무엇이 바뀌었나"를 전체 데이터 대신 이 번호로만 보내 대역폭을 아낀다. 자세히는 → changelist.
  • Shadow Memory (섀도 버퍼) — 마지막으로 보낸 값의 사본. 실제 오브젝트 메모리와 비교해 바뀐 것만 골라내는 기준선. → changelist
  • NetSerializeItem — FProperty 의 가상 함수. 아카이브 방향에 따라 값↔비트를 한 함수가 처리.

마무리 — 여기까지가 원리

이 챕터의 목표는 "모든 줄 해설"이 아니라 뼈대 하나야: 리플리케이션은 프로퍼티 트리를 평탄한 명령표로 눕혀 놓고, 그 표를 인덱스로 훑어 비트로 바꾼다. 송신도 수신도 같은 표, 같은 순서, 같은 함수.

  • 무엇이 리플리케이트되는지(표에 뭐가 올라가는지)가 아직 흐리면 → lifetime-props
  • "바뀐 것만 어떻게 골라 보내는지"(섀도 비교 · 변경 핸들)가 궁금하면, 이 표를 실제로 굴리는 다음 이야기 → changelist
  • 이 레이아웃이 실제 채널을 타고 나가는 큰 그림은 → actorchannel-replicate

🎯 원리 한 줄 요약

RepLayout 은 프로퍼티 트리를 클래스당 한 번 "평탄한 명령표(Cmds)"로 눕혀 두고, 송신·수신이 그 표를 같은 순서로 인덱싱만 하게 만들어 — 리플렉션 없이 빠르고, 방향은 아카이브가 정해 한 함수로 양방향을 처리한다.
