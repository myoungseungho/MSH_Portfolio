Dormancy: 안 바뀌는 액터는 재운다

언리얼 네트워크 · 26 / 42

0) 들어가며 — 자는 사람한테는 안부 전화 안 한다

동네에 가로등 100개가 서 있다고 쳐. 낮이든 밤이든 그 자리에 그대로야. 안 움직이고, 색도 안 변해. 그런데 서버가 매 틱마다 "가로등1 위치 (10,20), 가로등2 위치 (10,40)…" 이걸 100개 × 접속자 수만큼 계속 보낸다면?

바보 같지. 안 바뀌는데 왜 계속 보내.

이게 dormancy(도먼시, 휴면)의 전부야. 값이 안 변하는 액터는 "재운다". 재우면 서버가 그 액터를 복제 후보 목록에서 빼버려서, 그 자리에 있는 줄 클라도 알고 서버도 아는데 트래픽만 0이 돼. 그러다 진짜로 뭔가 바뀌면? 그때 딱 깨워서 한 번 더 보내고 다시 재워.

여기서 첫 함정. 이름이 헷갈려. 재우는 함수 이름엔 "Dormant"가 들어가는데, FlushNetDormancy는 이름에 Dormancy가 들어가는데도 깨우는 함수야. Flush = "휴면 목록에서 씻어내 최소 한 번 더 강제로 보냄". 자꾸 거꾸로 읽게 되니까 지금 못을 박아두자 — Flush = 깨우기.

그리고 이 챕터의 핵심 비대칭이 하나 있어. 미리 예측해봐:

재우기와 깨우기 중, 어느 쪽이 "이벤트"로 처리될까? 게임코드가 "이제 자!" 하고 부르는 쪽은 어디일까?

직관적으론 "자!"가 이벤트 같잖아. 근데 반대야. 깨우기가 이벤트고, 재우기는 이벤트가 아니야. 재우기는 서버의 리플리케이션 루프가 매 틱 스스로 "얘 재워도 되나?" 검사해서 처리해. 왜 이렇게 뒤집었는지는 3절에서 UE 개발자가 직접 코드 주석에 적어놨어. 일단 넘어가자.

지난 챕터 priority-updatefreq에서 "매 틱 후보 추리고 → 정렬하고 → 예산만큼 보낸다"는 뼈대를 봤지. dormancy는 그 첫 관문에서 액터를 아예 빼버리는 장치야. 커넥션이 뭔지 애매하면 → netconnection-overview, 채널이 뭔지 애매하면 → channel-types, 이 함수들이 프레임 어디서 불리는지 → server-replicate-actors.

1) 상태 5종 — 잠의 등급표

먼저 액터가 가질 수 있는 휴면 상태부터. 이게 NetDormancy 멤버에 담기는 값이야.

[스니펫 1] ENetDormancy enum — EngineTypes.h:3360-3374

enum ENetDormancy : int { /** This actor can never go network dormant. */ DORM_Never UMETA(DisplayName = "Never"), /** This actor can go dormant, but is not currently dormant. Game code will tell it when it go dormant. */ DORM_Awake UMETA(DisplayName = "Awake"), /** This actor wants to go fully dormant for all connections. */ DORM_DormantAll UMETA(DisplayName = "Dormant All"), /** This actor may want to go dormant for some connections, GetNetDormancy() will be called to find out which. */ DORM_DormantPartial UMETA(DisplayName = "Dormant Partial"), /** This actor is initially dormant for all connection if it was placed in map. */ DORM_Initial UMETA(DisplayName = "Initial"), DORM_MAX UMETA(Hidden), };

낮은 계단으로 하나씩 읽자.

  • DORM_Never — "절대 안 잠". 플레이어 캐릭터처럼 매 순간 뭔가 바뀌는 애들. 재울 시도 자체를 안 함.
  • DORM_Awake — "잘 수는 있는데 지금은 깨어있음". 재우기의 경계선. 이 값보다 위(> DORM_Awake)여야 재우기 후보가 돼. 코드에서 NetDormancy <= DORM_Awake면 전부 "재우지 마"로 걸러지는 걸 곧 보게 될 거야.
  • DORM_DormantAll — "모든 커넥션에 대해 통째로 잔다". 가로등이 이거야. 누가 보든 똑같이 안 변하니까.
  • DORM_DormantPartial — "커넥션마다 다르게". 이 클라한텐 자고, 저 클라한텐 깨어있고. 판정을 GetNetDormancy()가 커넥션별로 해줘. 시야 밖이면 재우는 식으로 쓸 수 있어.
  • DORM_Initial — "맵에 미리 박아둔 액터가 시작부터 자고 있음". 레벨에 배치된 장식물이 대표적. 최초로 깨어날 때 딱 한 번 DORM_DormantAll로 승급하고, 그 뒤론 평범한 dormant 액터처럼 굴러.

여기 값의 순서(정수 크기)가 로직이라는 게 포인트야. DORM_Never=0, DORM_Awake=1… 이렇게 커지니까 NetDormancy > DORM_Awake라는 한 줄 비교로 "재울 자격 있는 애들"을 싹 골라낼 수 있어. enum 순서가 그냥 라벨이 아니라 게이트라는 거.

2) 재우는 흐름 — 루프가 스스로 검사한다

재우기는 이벤트가 아니라 매 틱 서버 리플리케이션 루프가 주도해. priority-updatefreq에서 본 그 ServerReplicateActors_PrioritizeActors(NetDriver.cpp:5435) 안에서, 릴레번트한 액터를 돌 때마다 "얘 재워도 되냐?"를 물어봐.

그 질문에 답하는 게 이 함수야.

[스니펫 2] 재울지 판정 — NetDriver.cpp:5314-5334

static FORCEINLINE_DEBUGGABLE bool ShouldActorGoDormant( AActor* Actor, const TArray<FNetViewer>& ConnectionViewers, UActorChannel* Channel, const float Time, const bool bLowNetBandwidth ) { if ( Actor->NetDormancy <= DORM_Awake || !Channel || Channel->bPendingDormancy || Channel->Dormant ) { // Either shouldn't go dormant, or is already dormant return false; } if ( Actor->NetDormancy == DORM_DormantPartial ) { for ( int32 viewerIdx = 0; viewerIdx < ConnectionViewers.Num(); viewerIdx++ ) { if ( !Actor->GetNetDormancy( ConnectionViewers[viewerIdx].ViewLocation, ConnectionViewers[viewerIdx].ViewDir, ConnectionViewers[viewerIdx].InViewer, ConnectionViewers[viewerIdx].ViewTarget, Channel, Time, bLowNetBandwidth ) ) { return false; } } } return true; }

첫 if가 필터 4연발이야. 하나라도 걸리면 "재우지 마":

  1. NetDormancy <= DORM_Awake — 자격 미달(1절 경계선).
  2. !Channel — 채널도 없는데 뭘 재워.
  3. bPendingDormancy — 이미 "재우기 예약됨" 상태.
  4. Dormant — 이미 자고 있음.

두 번째 if는 Partial 전용 분기야. DORM_DormantPartial이면 커넥션(뷰어)마다 GetNetDormancy()를 호출해서, 한 명이라도 "난 깨어있어야 해"라고 하면 재우기 취소. All은 이 루프를 건너뛰니까 무조건 통과. 이게 All과 Partial의 실제 코드상 차이야.

재워도 된다고 판정나면? 바로 안 재워. 두 단계로 나눠서 재워.

[스니펫 3] 예약 → 실제 재우기, 두 단계 — DataChannel.cpp:4609-4625, 4572-4579

void UActorChannel::StartBecomingDormant() { if (bPendingDormancy || Dormant) { return; } UE_LOG(LogNetDormancy, Verbose, TEXT("StartBecomingDormant: %s"), *Describe() ); for (auto MapIt = ReplicationMap.CreateIterator(); MapIt; ++MapIt) { MapIt.Value()->StartBecomingDormant(); } bPendingDormancy = true; bIsInDormancyHysteresis = false; Connection->StartTickingChannel(this); }
void UActorChannel::BecomeDormant() { UE_LOG(LogNetDormancy, Verbose, TEXT("BecomeDormant: %s"), *Describe() ); bPendingDormancy = false; bIsInDormancyHysteresis = false; Dormant = true; Close(EChannelCloseReason::Dormancy); }

왜 두 단계냐. StartBecomingDormant는 잠들기로 예약만 해(bPendingDormancy = true). 아직 안 자. 왜냐면 "이 액터 재우기로 했으니 남아있는 변경분(프로퍼티, 서브오브젝트)은 다 밀어보내고 나서 자야" 하거든. 자다 말고 절반만 보낸 상태로 채널 닫으면 클라 화면이 어긋나.

그래서 "남은 게 정말 0인가?"를 매 틱 확인하는 게이트가 하나 더 있어.

[스니펫 4] 진짜 잘 준비 됐나 + 히스테리시스 — DataChannel.cpp:4581-4607

bool UActorChannel::ReadyForDormancy(bool suppressLogs) { // We need to keep replicating the Actor and its subobjects until none of them have // changes, and would otherwise go Dormant normally. if (!bIsInDormancyHysteresis) { for (auto MapIt = ReplicationMap.CreateIterator(); MapIt; ++MapIt) { if (!MapIt.Value()->ReadyForDormancy(suppressLogs)) { return false; } } } if (DormancyHysteresis > 0 && Connection && Connection->Driver) { bIsInDormancyHysteresis = true; const double TimePassed = Connection->Driver->GetElapsedTime() - LastUpdateTime; if (TimePassed < DormancyHysteresis) { return false; } } return true; }

변경분이 하나라도 남아있으면 return false — 계속 복제. 그리고 hysteresis(히스테리시스, 유예). 변경분이 0이 되자마자 바로 안 재우고, DormancyHysteresis 시간만큼 "조용한 상태가 지속"돼야 진짜로 재워. 왜? 재웠다 깨웠다 재웠다 깨웠다 진동하는 걸 막으려고. 살짝 움직이고 멈추고 또 살짝 움직이는 액터를 유예 없이 처리하면, 채널 닫고 열고를 반복해서 오히려 트래픽이 더 새. 유예 시간은 그 채터링을 흡수하는 완충재야.

ReadyForDormancy가 마침내 true를 뱉으면 BecomeDormant가 불려. 여기서 진짜로 잠들어: Dormant = true, 그리고 Close(EChannelCloseReason::Dormancy)로 채널을 닫아. 클라 쪽엔 ClientSetActorDormant(DataChannel.cpp:2319)가 날아가서 "얘 잔다"고 알려줘. 액터는 안 지워지고, 채널만 접혀.

마지막으로 장부 갱신. FNetworkObjectList::MarkDormant(NetworkObjectList.cpp:205)가 이 커넥션을 해당 액터의 DormantConnections에 등록해. 그리고 모든 커넥션이 다 잠들면 그 액터를 ObjectsDormantOnAllConnections로 옮겨 — 이게 결정적이야. 이 목록에 들어가면 다음 틱부터 ServerReplicateActors의 고려 목록(ConsiderList)에서 아예 빠져. 후보에 안 오르니 정렬도, 전송 계산도 안 해. 그래서 트래픽이 0이 되는 거야. 재우기의 실질적 이득은 바로 이 지점에서 발생해.

3) 깨우는 흐름 — 이건 이벤트다

이제 반대 방향. 자던 액터가 뭔가 바뀌었어. 깨워야 해. 여기는 이벤트 기반이야. 게임코드가 직접 불러.

진입점은 이거.

[스니펫 5] 깨우기 진입점 — Actor.cpp:3075-3094

void AActor::FlushNetDormancy() { if (IsNetMode(NM_Client) || NetDormancy <= DORM_Awake || IsPendingKillPending()) { return; } QUICK_SCOPE_CYCLE_COUNTER(NET_AActor_FlushNetDormancy); #if CSV_RECORD_DETAILED_ACTOR_NET_STATS ActorUtils::CsvRecordClassName(GetClass(), CSV_CATEGORY_INDEX(Actor_FlushNetDormancy)); #endif // CSV_RECORD_DETAILED_ACTOR_NET_STATS bool bWasDormInitial = false; if (NetDormancy == DORM_Initial) { // No longer initially dormant NetDormancy = DORM_DormantAll; bWasDormInitial = true; }

첫 if에서 서버가 아니거나(클라는 깨울 권한 없음), 애초에 잘 자격이 없던 액터거나(<= DORM_Awake), 죽는 중이면 그냥 리턴. 그 다음 아까 예고한 승급 — DORM_Initial이었으면 이제 DORM_DormantAll로 바꿔. "맵에 박혀서 처음부터 자던 애"가 인생 처음 깨어나는 순간, 평범한 dormant 액터로 신분 변경.

그럼 왜 재우기는 루프가 하고 깨우기는 이벤트로 할까. UE 개발자가 함수 바로 위에 주석으로 직접 답을 적어놨어.

[스니펫 6] 설계 의도 — NetDriver.cpp:4726-4738 (주석)

void UNetDriver::FlushActorDormancy(AActor* Actor, bool bWasDormInitial) { // Note: Going into dormancy is completely handled in ServerReplicateActor. We want to avoid // event-based handling of going into dormancy, because we have to deal with connections joining in progress. // It is better to have ::ServerReplicateActor check the AActor and UChannel's states to determined if an actor // needs to be moved into dormancy. The same amount of work will be done (1 time per connection when an actor goes dorm) // and we avoid having to do special things when a new client joins. // // Going out of dormancy can be event based like this since it only affects clients already joined. Its more efficient in this // way too, since we dont have to check every dormant actor in ::ServerReplicateActor to see if it needs to go out of dormancy if (GSetNetDormancyEnabled == 0) return;

풀어 읽으면 — 재우기를 이벤트로 하면 "중간에 접속하는 클라"를 특별 취급해야 해서 골치야. 서버가 "액터A 재워!" 이벤트를 쐈는데 그 직후 새 클라가 붙으면, 이 클라는 그 이벤트를 못 받았잖아. 그럼 "얘한텐 액터A를 재운 걸로 쳐야 하나 말아야 하나" 예외 처리가 줄줄이 생겨. 그래서 재우기는 매 틱 루프가 각 커넥션 상태를 보고 알아서 처리하게 뒀어. 일은 어차피 커넥션당 1번으로 똑같은데, 신규 접속 예외가 사라져.

반대로 깨우기는 이미 붙어있는 클라한테만 영향을 주니까 이벤트로 해도 안전하고, 오히려 효율적이야. 안 그러면 매 틱마다 자고 있는 모든 액터를 "너 이제 깰 때 됐니?" 하고 순회해야 하는데, 그건 dormancy로 아끼려던 걸 도로 까먹는 짓이거든.

깨우기 콜체인은 아래로 쭉 내려가:

[스니펫 7] 커넥션 순회하며 깨우기 — NetDriver.cpp:4774-4786

void UNetDriver::FlushActorDormancyInternal(AActor *Actor) { QUICK_SCOPE_CYCLE_COUNTER(STAT_NetDriver_FlushActorDormancy); // Go through each connection and remove the actor from the dormancy list for (int32 i=0; i < ClientConnections.Num(); ++i) { UNetConnection *NetConnection = ClientConnections[i]; if(NetConnection != NULL) { NetConnection->FlushDormancy(Actor); } } }

모든 클라 커넥션을 돌면서 각자 FlushDormancy(Actor). 그 안에서 FNetworkObjectList::MarkActive(NetConnection.cpp:5489에서 호출)가 dormant 장부에서 액터를 빼내 다시 복제 대상으로 돌려놔. 그리고 채널의 Dormant/bPendingDormancy도 둘 다 false로 리셋(NetConnection.cpp:5580-5581). 2절에서 채웠던 플래그가 여기서 다 풀리는 거야. 다음 틱부터 이 액터는 평범하게 복제되고, 조용해지면 또 2절 흐름 타고 다시 잠들어.

참고로 게임코드가 FlushNetDormancy를 직접 안 불러도, ForceNetUpdate가 Actor.cpp:2994에서 대신 불러줘. 프로퍼티에 push-model(→ push-model)을 쓰면 프레임워크가 알아서 깨우기도 하고. 즉 "값을 바꾸면 깨어난다"가 상위 레이어에서 자동으로 엮여 있어.

상태를 직접 갈아끼우고 싶으면 AActor::SetNetDormancy(NewDormancy)(Actor.cpp:3024)를 써. 값을 DORM_Awake 이하로 내리면 그 안에서 FlushActorDormancy를 불러 강제 기상까지 해줘.

5) 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선 게임서버로 번역하면 dormancy가 뭔지 감이 확 와.

우리 서버는 IOCP 워커 스레드들이 소켓 이벤트를 받아 처리하고, 액터(캐릭터/NPC) 상태는 사실상 싱글스레드 로직으로 굴러. 브로드캐스트는 "이 맵/시야 안의 PC들한테 이 패킷 뿌려"를 우리가 명시적으로 짜지. 예를 들어 몹 위치가 바뀌면 주변 PC 리스트 돌면서 SendPacket 뿌리는 코드를 직접 써.

UE dormancy를 우리 식으로 옮기면 이렇게 돼:

  • DORM_DormantAll = "이 NPC 방송 리스트에서 뺀다" — 우리라면 "가만히 서 있는 상점 NPC는 브로드캐스트 루프에서 skip" 같은 최적화를 손으로 짜야 해. UE는 그걸 ObjectsDormantOnAllConnections 장부로 프레임워크가 대신 해주는 거야. 우리 코드로 치면 "브로드캐스트 대상 벡터에서 이 엔티티를 제외" + "값 바뀔 때만 도로 넣기".
  • FlushNetDormancy = "값 바뀌었으니 이번 틱은 방송 리스트에 도로 넣어" — 우리가 if (몹HP 변함) 주변PC에 SP_HP 송신 하는 그 if가, UE에선 push-model + FlushNetDormancy 조합으로 자동화돼 있어.
  • hysteresis = "채터링 방지 쿨다운" — 우리도 좌표를 매 틱 다 뿌리면 대역폭 터지니까 "N ms마다" 또는 "일정 이상 움직였을 때만" 뿌리는 게이팅을 넣잖아. dormancy 유예가 딱 그 발상이야.

큰 차이 하나. 우리는 브로드캐스트 대상이 맵/시야 기준으로 우리가 계산해. UE는 커넥션(플레이어)별로 채널이 있고, 그 채널을 커넥션마다 재우거나 깨워. 그래서 DORM_DormantPartial(커넥션별 판정) 같은 게 자연스럽게 나와 — 우리 식으로는 "PC A한텐 이 NPC 안 뿌리고, PC B한텐 뿌리고"를 엔티티×PC 단위로 스위칭하는 것과 같아. 우리가 시야 컬링으로 손수 하던 걸, UE는 dormancy + relevancy(→ relevancy) 두 축으로 프레임워크화한 셈이야.

정리하면 dormancy는 새로운 마법이 아니라, 우리가 브로드캐스트 최적화로 손코딩하던 "안 바뀌면 안 보낸다"를 엔진이 상태기계로 표준화한 것. 우리는 매번 다시 짜고, UE는 액터에 값 하나(NetDormancy) 세팅하면 끝.

6) 초보가 걸려 넘어지는 지점 5개

  • Flush = 깨우기 (재우기 아님). FlushNetDormancy는 "휴면 목록에서 씻어내 강제 갱신". 이름값의 역설. 도입부에 못 박았지만 다시 한 번.
  • 재우기는 이벤트가 아님. 게임코드가 "자!"라고 안 불러. 서버 리플리케이션 루프가 매 틱 ShouldActorGoDormant로 스스로 검사해서 재워. 이유는 스니펫 6 주석 — 신규 접속 클라 예외를 없애려고.
  • bPendingDormancy ≠ Dormant. Pending은 "재우기로 예약됨, 남은 변경분 밀어보내는 중". Dormant는 "실제로 채널 닫고 잠듦". 2단계 전이(StartBecomingDormant → BecomeDormant)를 하나로 뭉뚱그리면 안 돼.
  • 잔다 ≠ 지운다. 액터는 살아있고 채널만 접혀(Close(Dormancy)). 클라도 그 자리에 있는 줄 알아. 언제든 다시 깬다.
  • DORM_Initial은 일회용 등급. 최초 기상 시 DORM_DormantAll로 승급하고 사라져. "처음부터 자던 맵 배치물"이라는 초기 조건일 뿐, 영구 상태가 아냐.

🎯 원리 한 줄 요약

안 바뀌는 액터는 리플리케이션 루프가 스스로 검사해 조용히 재우고(장부에서 빼 트래픽 0), 값이 바뀌는 순간 게임코드가 이벤트로 딱 한 번 깨워 다시 복제 대상에 올린다 — 재우기는 루프, 깨우기는 이벤트, 이 비대칭이 dormancy의 전부다.
