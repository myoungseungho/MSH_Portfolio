Dormancy: 안 바뀌는 액터는 재운다

언리얼 네트워크 · 26 / 47

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이런 고민을 해봤을 거야. IOCP 워커가 CM_MOVE, CM_ATTACK 같은 패킷을 받아서 싱글스레드 로직 큐로 넘기고, 로직 스레드는 주변 플레이어에게 SP_* 패킷을 뿌려. 여기까지는 익숙해. 그런데 아무 일도 안 일어난 애들은 어떻게 해야 할까?

상점 NPC, 맵 장식물, 닫힌 문, 움직이지 않는 몬스터가 1만 개 있다고 해보자. 얘들이 매 틱 그대로인데도 "나 아직 여기 있어요"를 모든 클라에게 계속 보내면, send 버퍼가 쌓이고, 브로드캐스트 루프가 길어지고, 락 잡는 구간도 늘고, 정작 중요한 전투 패킷이 밀린다. 안 바뀐 걸 계속 보내는 건, 잠자는 사람한테 1초마다 전화해서 "아직 자요?" 묻는 꼴이야.

그래서 서버는 질문을 바꿔야 해. "누구를 먼저 보낼까?"보다 더 앞에, "얘는 아예 안 보내도 되는 애 아닌가?" 를 물어야 해. 우리 조선 서버라면 브로드캐스트 대상 목록에서 가만히 있는 NPC를 빼고, HP나 위치가 진짜 바뀌는 순간에만 다시 SP_*를 뿌리는 최적화로 생각하면 된다.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 dormancy야. 안 바뀌는 액터는 복제 후보에서 빼서 재우고, 값이 바뀌는 순간 FlushNetDormancy로 깨워서 한 번 더 보내. 액터를 삭제하는 게 아니라, 클라와 서버가 이미 알고 있는 상태를 믿고 네트워크만 잠시 쉬게 하는 장치야.

이 챕터를 지금 배우는 이유도 흐름상 딱 맞아. 지난 챕터에서 priority와 update frequency로 "후보 중 누구를 얼마나 자주 보낼까"를 봤다면, dormancy는 그보다 더 센 카드야. 후보에 올린 뒤 아끼는 게 아니라, 첫 관문에서 후보 자체를 빼버리는 최적화거든.

그리고 이제 우리는 UNetConnection, 채널, 복제 루프를 이미 봤어. 그래서 "액터가 잔다"는 말이 실제로는 커넥션별 채널을 닫고, 장부에서 dormant로 옮기고, 필요할 때 다시 active로 돌리는 일이라는 걸 읽을 준비가 됐다. 이걸 잡아야 다음의 Replication Graph도 "대규모 서버에서 안 보내도 되는 것을 더 똑똑하게 빼는 구조"로 이어진다.

0) 들어가며 — 자는 사람한테는 안부 전화 안 한다

동네에 가로등 100개가 서 있다고 쳐. 낮이든 밤이든 그 자리에 그대로야. 안 움직이고, 색도 안 변해. 그런데 서버가 매 틱마다 "가로등1 위치 (10,20), 가로등2 위치 (10,40)…" 이걸 100개 × 접속자 수만큼 계속 보낸다면?

바보 같지. 안 바뀌는데 왜 계속 보내.

이게 dormancy(도먼시, 휴면)의 전부야. 값이 안 변하는 액터는 "재운다". 재우면 서버가 그 액터를 복제 후보 목록에서 빼버려서, 그 자리에 있는 줄 클라도 알고 서버도 아는데 트래픽만 0이 돼. 그러다 진짜로 뭔가 바뀌면? 그때 딱 깨워서 한 번 더 보내고 다시 재워.

여기서 첫 함정. 이름이 헷갈려. 재우는 함수 이름엔 "Dormant"가 들어가는데, FlushNetDormancy는 이름에 Dormancy가 들어가는데도 깨우는 함수야. Flush = "휴면 목록에서 씻어내 최소 한 번 더 강제로 보냄". 자꾸 거꾸로 읽게 되니까 지금 못을 박아두자 — Flush = 깨우기.

그리고 이 챕터의 핵심 비대칭이 하나 있어. 미리 예측해봐:

재우기와 깨우기 중, 어느 쪽이 "이벤트"로 처리될까? 게임코드가 "이제 자!" 하고 부르는 쪽은 어디일까?

직관적으론 "자!"가 이벤트 같잖아. 근데 반대야. 깨우기가 이벤트고, 재우기는 이벤트가 아니야. 재우기는 서버의 리플리케이션 루프가 매 틱 스스로 "얘 재워도 되나?" 검사해서 처리해. 왜 이렇게 뒤집었는지는 3절에서 UE 개발자가 직접 코드 주석에 적어놨어. 일단 넘어가자.

지난 챕터 priority-updatefreq에서 "매 틱 후보 추리고 → 정렬하고 → 예산만큼 보낸다"는 뼈대를 봤지. dormancy는 그 첫 관문에서 액터를 아예 빼버리는 장치야. 커넥션이 뭔지 애매하면 → netconnection-overview, 채널이 뭔지 애매하면 → channel-types, 이 함수들이 프레임 어디서 불리는지 → server-replicate-actors.

지금부터 실제 엔진 코드가 나온다. 겁먹지 마 — enum, 포인터, ->, 매크로 같은 낯선 표시는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 여기서는 "잠 상태표"와 "재우기/깨우기 스위치"만 잡으면 된다.

🌱 이 개념은 왜 생겼나 — Dormancy(재우기)
• 원래 구조: 관련 있고 갱신빈도까지 정했으면, 그 액터를 매 틱 후보 목록에 올려 "보낼 거 있나?" 확인해.
• 그런데 문제: 가로등·상점NPC·닫힌 문처럼 아예 안 바뀌는 애가 1만 개인데, 얘들도 매 틱 후보에 올라 검사받아. 자는 사람한테 1초마다 전화해서 "아직 자요?" 묻는 꼴 — 확인 자체가 낭비야.
• 그래서 필요한 것: 안 바뀌는 액터는 후보 목록에서 아예 빼서 재우는 장치. 클라도 서버도 그 자리에 있는 걸 이미 아니까 트래픽만 0으로. 값이 바뀌면 그때 깨워. → 이게 Dormancy(휴면)야. 지우는 게 아니라 네트워크만 잠깐 쉬게 하는 거.

1) 상태 5종 — 잠의 등급표

먼저 액터가 가질 수 있는 휴면 상태부터. 이게 NetDormancy 멤버에 담기는 값이야.

[스니펫 1] ENetDormancy enum — EngineTypes.h:3360-3374

enum ENetDormancy : int { /** This actor can never go network dormant. */ DORM_Never UMETA(DisplayName = "Never"), /** This actor can go dormant, but is not currently dormant. Game code will tell it when it go dormant. */ DORM_Awake UMETA(DisplayName = "Awake"), /** This actor wants to go fully dormant for all connections. */ DORM_DormantAll UMETA(DisplayName = "Dormant All"), /** This actor may want to go dormant for some connections, GetNetDormancy() will be called to find out which. */ DORM_DormantPartial UMETA(DisplayName = "Dormant Partial"), /** This actor is initially dormant for all connection if it was placed in map. */ DORM_Initial UMETA(DisplayName = "Initial"), DORM_MAX UMETA(Hidden), };
🔤 기호 사전 — enum ENetDormancy : int
• enum = 고를 수 있는 답을 미리 정해둔 보기표. 여기선 액터의 잠 상태가 이 보기 중 하나만 될 수 있어.
• ENetDormancy = 그 보기표의 이름. 앞의 E는 보통 "enum이다"라는 UE식 이름표야.
• : int = 보기표 값을 속으로는 정수 번호로 저장한다는 뜻. 그래서 DORM_Awake보다 큰지 작은지 비교할 수 있어.
• DORM_* = 실제 선택지 이름들. DORM_은 "휴면 관련 값"이라는 꼬리표야.
• UMETA(DisplayName = "...") = 에디터에서 사람한테 보여줄 이름을 붙이는 장식표. 네트워크 판단 자체는 DORM_DormantAll 같은 코드 이름으로 해.
• /** ... */ = 여러 줄 주석. 컴퓨터가 실행하지 않고, 사람 읽으라고 붙인 설명이야.
• DORM_MAX UMETA(Hidden) = 목록 끝에 있는 숨김 값. Hidden은 에디터 목록에 안 보이게 숨긴다는 뜻이야.
🔁 이제 다시 보자. enum(보기표) → ENetDormancy(휴면 상태표) → : int(속은 번호) → DORM_Never, DORM_Awake, DORM_DormantAll(선택지들). 이어 읽으면 "액터의 잠 상태는 이 다섯 등급 중 하나로 고른다." enum이 그냥 영어 목록이 아니라, 아래 코드가 비교할 번호 달린 상태표로 보이지?

낮은 계단으로 하나씩 읽자.

  • DORM_Never — "절대 안 잠". 플레이어 캐릭터처럼 매 순간 뭔가 바뀌는 애들. 재울 시도 자체를 안 함.
  • DORM_Awake — "잘 수는 있는데 지금은 깨어있음". 재우기의 경계선. 이 값보다 위(> DORM_Awake)여야 재우기 후보가 돼. 코드에서 NetDormancy <= DORM_Awake면 전부 "재우지 마"로 걸러지는 걸 곧 보게 될 거야.
  • DORM_DormantAll — "모든 커넥션에 대해 통째로 잔다". 가로등이 이거야. 누가 보든 똑같이 안 변하니까.
  • DORM_DormantPartial — "커넥션마다 다르게". 이 클라한텐 자고, 저 클라한텐 깨어있고. 판정을 GetNetDormancy()가 커넥션별로 해줘. 시야 밖이면 재우는 식으로 쓸 수 있어.
  • DORM_Initial — "맵에 미리 박아둔 액터가 시작부터 자고 있음". 레벨에 배치된 장식물이 대표적. 최초로 깨어날 때 딱 한 번 DORM_DormantAll로 승급하고, 그 뒤론 평범한 dormant 액터처럼 굴러.

여기 값의 순서(정수 크기)가 로직이라는 게 포인트야. DORM_Never=0, DORM_Awake=1… 이렇게 커지니까 NetDormancy > DORM_Awake라는 한 줄 비교로 "재울 자격 있는 애들"을 싹 골라낼 수 있어. enum 순서가 그냥 라벨이 아니라 게이트라는 거.

🌱 이 개념은 왜 생겼나 — 히스테리시스(유예)
• 원래 구조: 재워도 된다고 판정나면, 변경분이 0이 되는 그 순간 바로 채널 닫고 재우면 되지.
• 그런데 문제: 살짝 움직이고 멈추고, 또 살짝 움직이는 액터를 그렇게 처리하면 재웠다 깨웠다를 반복해. 채널을 닫고 열고 닫고 열고… 오히려 트래픽이 더 새고 CPU만 태워.
• 그래서 필요한 것: "조용해졌다"고 바로 안 재우고, 일정 시간 계속 조용해야 진짜 재우는 완충 구간. → 이게 히스테리시스(유예)야. 껐다 켰다 진동(채터링)을 흡수하는 스펀지라고 보면 돼.

2) 재우는 흐름 — 루프가 스스로 검사한다

재우기는 이벤트가 아니라 매 틱 서버 리플리케이션 루프가 주도해. priority-updatefreq에서 본 그 ServerReplicateActors_PrioritizeActors(NetDriver.cpp:5435) 안에서, 릴레번트한 액터를 돌 때마다 "얘 재워도 되냐?"를 물어봐.

그 질문에 답하는 게 이 함수야.

[스니펫 2] 재울지 판정 — NetDriver.cpp:5314-5334

static FORCEINLINE_DEBUGGABLE bool ShouldActorGoDormant( AActor* Actor, const TArray<FNetViewer>& ConnectionViewers, UActorChannel* Channel, const float Time, const bool bLowNetBandwidth ) { if ( Actor->NetDormancy <= DORM_Awake || !Channel || Channel->bPendingDormancy || Channel->Dormant ) { // Either shouldn't go dormant, or is already dormant return false; } if ( Actor->NetDormancy == DORM_DormantPartial ) { for ( int32 viewerIdx = 0; viewerIdx < ConnectionViewers.Num(); viewerIdx++ ) { if ( !Actor->GetNetDormancy( ConnectionViewers[viewerIdx].ViewLocation, ConnectionViewers[viewerIdx].ViewDir, ConnectionViewers[viewerIdx].InViewer, ConnectionViewers[viewerIdx].ViewTarget, Channel, Time, bLowNetBandwidth ) ) { return false; } } } return true; }
🔤 기호 사전 — static FORCEINLINE_DEBUGGABLE bool ShouldActorGoDormant(...)
• static = 이 파일 안에서 쓰는 작은 도구 함수처럼 묶어둔 것. 액터 멤버 함수가 아니라 바깥 helper야.
• FORCEINLINE_DEBUGGABLE = 가능하면 짧게 펼쳐서 빠르게 쓰되, 디버깅도 가능하게 하라는 UE 매크로.
• bool = 답이 true/false 둘 중 하나. 여기선 "재워도 돼?"에 대한 예/아니오.
• AActor* Actor, UActorChannel* Channel = *는 포인터. 액터/채널 원본을 가리키는 주소표를 받는다는 뜻이야.
• const TArray<FNetViewer>& ConnectionViewers = 커넥션 뷰어 목록을 복사하지 않고(&) 빌려 보되, 안 바꾸겠다고(const) 약속.
• || = "또는". 조건 네 개 중 하나라도 참이면 첫 if에 걸려.
• !Channel, !Actor->GetNetDormancy(...) = !는 "아니면/없으면". 채널이 없거나, 함수 답이 false면 안으로 들어가.
• -> = 포인터가 가리키는 물건의 멤버를 꺼내는 화살표. Actor->NetDormancy는 "그 액터의 NetDormancy".
• for (...; ...; ++viewerIdx) = 뷰어를 0번부터 끝까지 하나씩 훑는 반복문. ++viewerIdx는 번호를 1 올린다는 뜻.
• return false / return true = 여기서 즉시 결론 내고 함수 끝. false면 재우지 말고, true면 재워도 된다는 신호야.
🔁 이제 다시 보자. 첫 if는 NetDormancy <= DORM_Awake(잠잘 자격 없음) 또는 !Channel(채널 없음) 또는 이미 예약/휴면이면 바로 return false. 그 다음 DORM_DormantPartial이면 뷰어마다 GetNetDormancy()를 묻고, 한 명이라도 싫다 하면 false. 끝까지 안 걸리면 return true — "이 액터는 지금 재워도 된다"는 판정이야.

첫 if가 필터 4연발이야. 하나라도 걸리면 "재우지 마":

  1. NetDormancy <= DORM_Awake — 자격 미달(1절 경계선).
  2. !Channel — 채널도 없는데 뭘 재워.
  3. bPendingDormancy — 이미 "재우기 예약됨" 상태.
  4. Dormant — 이미 자고 있음.

두 번째 if는 Partial 전용 분기야. DORM_DormantPartial이면 커넥션(뷰어)마다 GetNetDormancy()를 호출해서, 한 명이라도 "난 깨어있어야 해"라고 하면 재우기 취소. All은 이 루프를 건너뛰니까 무조건 통과. 이게 All과 Partial의 실제 코드상 차이야.

재워도 된다고 판정나면? 바로 안 재워. 두 단계로 나눠서 재워.

🔤 기호 사전 — void UActorChannel::StartBecomingDormant()
• void = 답을 돌려주는 함수가 아니라, 안에서 상태를 바꾸고 끝나는 함수.
• UActorChannel:: = UActorChannel에 딸린 함수라는 소속 표시. 여기서 잠드는 건 액터 자체보다 액터 채널 쪽 일이야.
• if (bPendingDormancy || Dormant) = 이미 재우는 중이거나 이미 자고 있으면 또 할 필요 없다는 문지기.
• UE_LOG(..., Verbose, ...) = 아주 자세한 로그를 남기는 줄. 동작을 추적하려고 찍는 기록이야.
• for (auto MapIt = ReplicationMap.CreateIterator(); MapIt; ++MapIt) = 복제 지도 안의 항목들을 하나씩 도는 반복문. auto는 타입을 컴파일러가 알아서 맞추라는 뜻.
• MapIt.Value()->StartBecomingDormant() = 지도 항목 안의 복제 담당자에게도 "너도 재울 준비해"라고 전파.
• bPendingDormancy = true = "아직 잠든 건 아니고, 잠들 예약됨" 스위치를 켬.
• Connection->StartTickingChannel(this) = 이 채널을 계속 틱으로 확인하게 등록. this는 "바로 이 채널 자신"이야.

• bIsInDormancyHysteresis = false = 유예 시간 단계도 끝났다고 표시.

왜 두 단계냐. StartBecomingDormant는 잠들기로 예약만 해(bPendingDormancy = true). 아직 안 자. 왜냐면 "이 액터 재우기로 했으니 남아있는 변경분(프로퍼티, 서브오브젝트)은 다 밀어보내고 나서 자야" 하거든. 자다 말고 절반만 보낸 상태로 채널 닫으면 클라 화면이 어긋나.

그래서 "남은 게 정말 0인가?"를 매 틱 확인하는 게이트가 하나 더 있어.

[스니펫 4] 진짜 잘 준비 됐나 + 히스테리시스 — DataChannel.cpp:4581-4607

🔤 기호 사전 — bool UActorChannel::ReadyForDormancy(bool suppressLogs)
• bool = 이 함수의 대답은 true/false 둘 중 하나. "잘 준비 끝났어?"에 답하는 함수야.
• suppressLogs = 로그를 조용히 할지 말지 넘겨받는 스위치. 여기선 아래 복제 담당자에게 그대로 전달돼.

• ReplicationMap.CreateIterator() = 남은 복제 항목들을 훑기 위한 손가락(Iterator)을 만든다.

• && = "그리고". 세 조건이 모두 맞아야 유예 시간을 계산해.
• const double TimePassed = ... = 지나간 시간을 소수점까지 담는 변수. const라서 이 줄에서 정한 뒤 안 바꿔.
• TimePassed < DormancyHysteresis = 아직 유예 시간이 덜 지났으면.
🔁 이제 다시 보자. 먼저 ReplicationMap을 돌며 남은 변경분이 있나 묻고, 하나라도 준비 안 됐으면 return false. 그 다음 DormancyHysteresis가 있으면 LastUpdateTime 이후 충분히 조용했는지 보고, 아직 덜 지났으면 또 false. 둘 다 통과해야 마지막 return true — "이제 진짜 자도 된다"가 돼.

변경분이 하나라도 남아있으면 return false — 계속 복제. 그리고 hysteresis(히스테리시스, 유예). 변경분이 0이 되자마자 바로 안 재우고, DormancyHysteresis 시간만큼 "조용한 상태가 지속"돼야 진짜로 재워. 왜? 재웠다 깨웠다 재웠다 깨웠다 진동하는 걸 막으려고. 살짝 움직이고 멈추고 또 살짝 움직이는 액터를 유예 없이 처리하면, 채널 닫고 열고를 반복해서 오히려 트래픽이 더 새. 유예 시간은 그 채터링을 흡수하는 완충재야.

ReadyForDormancy가 마침내 true를 뱉으면 BecomeDormant가 불려. 여기서 진짜로 잠들어: Dormant = true, 그리고 Close(EChannelCloseReason::Dormancy)로 채널을 닫아. 클라 쪽엔 ClientSetActorDormant(DataChannel.cpp:2319)가 날아가서 "얘 잔다"고 알려줘. 액터는 안 지워지고, 채널만 접혀.

마지막으로 장부 갱신. FNetworkObjectList::MarkDormant(NetworkObjectList.cpp:205)가 이 커넥션을 해당 액터의 DormantConnections에 등록해. 그리고 모든 커넥션이 다 잠들면 그 액터를 ObjectsDormantOnAllConnections로 옮겨 — 이게 결정적이야. 이 목록에 들어가면 다음 틱부터 ServerReplicateActors의 고려 목록(ConsiderList)에서 아예 빠져. 후보에 안 오르니 정렬도, 전송 계산도 안 해. 그래서 트래픽이 0이 되는 거야. 재우기의 실질적 이득은 바로 이 지점에서 발생해.

🌱 이 개념은 왜 생겼나 — 깨우기는 이벤트(FlushNetDormancy)
• 원래 구조: 재우기를 매 틱 루프가 검사하니까, 깨우기도 매 틱 루프가 "자는 애들 중에 깰 때 된 거 있나?" 다 순회하면 대칭적이고 깔끔하겠지.
• 그런데 문제: 그럼 자고 있는 모든 액터를 매 틱 훑어야 해 — dormancy로 아끼려던 걸 도로 까먹는 짓이야. 자는 애가 많을수록 손해가 커져.
• 그래서 필요한 것: 깨우기는 값이 바뀌는 순간 딱 한 번 쏘는 이벤트로. 이미 붙어있는 클라만 순회하면 되니까 안전하고 싸. → 이게 FlushNetDormancy야. (이름에 Dormancy가 붙었지만 깨우는 함수인 거, 헷갈리지 마.) 재우기=루프, 깨우기=이벤트, 이 비대칭이 설계의 핵심.

3) 깨우는 흐름 — 이건 이벤트다

이제 반대 방향. 자던 액터가 뭔가 바뀌었어. 깨워야 해. 여기는 이벤트 기반이야. 게임코드가 직접 불러.

진입점은 이거.

그럼 왜 재우기는 루프가 하고 깨우기는 이벤트로 할까. UE 개발자가 함수 바로 위에 주석으로 직접 답을 적어놨어.

풀어 읽으면 — 재우기를 이벤트로 하면 "중간에 접속하는 클라"를 특별 취급해야 해서 골치야. 서버가 "액터A 재워!" 이벤트를 쐈는데 그 직후 새 클라가 붙으면, 이 클라는 그 이벤트를 못 받았잖아. 그럼 "얘한텐 액터A를 재운 걸로 쳐야 하나 말아야 하나" 예외 처리가 줄줄이 생겨. 그래서 재우기는 매 틱 루프가 각 커넥션 상태를 보고 알아서 처리하게 뒀어. 일은 어차피 커넥션당 1번으로 똑같은데, 신규 접속 예외가 사라져.

반대로 깨우기는 이미 붙어있는 클라한테만 영향을 주니까 이벤트로 해도 안전하고, 오히려 효율적이야. 안 그러면 매 틱마다 자고 있는 모든 액터를 "너 이제 깰 때 됐니?" 하고 순회해야 하는데, 그건 dormancy로 아끼려던 걸 도로 까먹는 짓이거든.

깨우기 콜체인은 아래로 쭉 내려가:

5) 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선 게임서버로 번역하면 dormancy가 뭔지 감이 확 와.

우리 서버는 IOCP 워커 스레드들이 소켓 이벤트를 받아 처리하고, 액터(캐릭터/NPC) 상태는 사실상 싱글스레드 로직으로 굴러. 브로드캐스트는 "이 맵/시야 안의 PC들한테 이 패킷 뿌려"를 우리가 명시적으로 짜지. 예를 들어 몹 위치가 바뀌면 주변 PC 리스트 돌면서 SendPacket 뿌리는 코드를 직접 써.

UE dormancy를 우리 식으로 옮기면 이렇게 돼:

  • DORM_DormantAll = "이 NPC 방송 리스트에서 뺀다" — 우리라면 "가만히 서 있는 상점 NPC는 브로드캐스트 루프에서 skip" 같은 최적화를 손으로 짜야 해. UE는 그걸 ObjectsDormantOnAllConnections 장부로 프레임워크가 대신 해주는 거야. 우리 코드로 치면 "브로드캐스트 대상 벡터에서 이 엔티티를 제외" + "값 바뀔 때만 도로 넣기".
  • FlushNetDormancy = "값 바뀌었으니 이번 틱은 방송 리스트에 도로 넣어" — 우리가 if (몹HP 변함) 주변PC에 SP_HP 송신 하는 그 if가, UE에선 push-model + FlushNetDormancy 조합으로 자동화돼 있어.
  • hysteresis = "채터링 방지 쿨다운" — 우리도 좌표를 매 틱 다 뿌리면 대역폭 터지니까 "N ms마다" 또는 "일정 이상 움직였을 때만" 뿌리는 게이팅을 넣잖아. dormancy 유예가 딱 그 발상이야.

큰 차이 하나. 우리는 브로드캐스트 대상이 맵/시야 기준으로 우리가 계산해. UE는 커넥션(플레이어)별로 채널이 있고, 그 채널을 커넥션마다 재우거나 깨워. 그래서 DORM_DormantPartial(커넥션별 판정) 같은 게 자연스럽게 나와 — 우리 식으로는 "PC A한텐 이 NPC 안 뿌리고, PC B한텐 뿌리고"를 엔티티×PC 단위로 스위칭하는 것과 같아. 우리가 시야 컬링으로 손수 하던 걸, UE는 dormancy + relevancy(→ relevancy) 두 축으로 프레임워크화한 셈이야.

정리하면 dormancy는 새로운 마법이 아니라, 우리가 브로드캐스트 최적화로 손코딩하던 "안 바뀌면 안 보낸다"를 엔진이 상태기계로 표준화한 것. 우리는 매번 다시 짜고, UE는 액터에 값 하나(NetDormancy) 세팅하면 끝.

6) 초보가 걸려 넘어지는 지점 5개

  • Flush = 깨우기 (재우기 아님). FlushNetDormancy는 "휴면 목록에서 씻어내 강제 갱신". 이름값의 역설. 도입부에 못 박았지만 다시 한 번.
  • 재우기는 이벤트가 아님. 게임코드가 "자!"라고 안 불러. 서버 리플리케이션 루프가 매 틱 ShouldActorGoDormant로 스스로 검사해서 재워. 이유는 스니펫 6 주석 — 신규 접속 클라 예외를 없애려고.
  • bPendingDormancy ≠ Dormant. Pending은 "재우기로 예약됨, 남은 변경분 밀어보내는 중". Dormant는 "실제로 채널 닫고 잠듦". 2단계 전이(StartBecomingDormant → BecomeDormant)를 하나로 뭉뚱그리면 안 돼.
  • 잔다 ≠ 지운다. 액터는 살아있고 채널만 접혀(Close(Dormancy)). 클라도 그 자리에 있는 줄 알아. 언제든 다시 깬다.
  • DORM_Initial은 일회용 등급. 최초 기상 시 DORM_DormantAll로 승급하고 사라져. "처음부터 자던 맵 배치물"이라는 초기 조건일 뿐, 영구 상태가 아냐.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. Dormancy(휴면), 대체 왜 필요한 물건인가요?

답 보기
가로등·상점 NPC·닫힌 문처럼 값이 아예 안 바뀌는 액터가 맵에 수천, 수만 개 있어. 근데 얘들도 매 틱 복제 후보 목록에 올라서 "보낼 거 있나?" 검사를 받아. 안 바뀌는데 확인하는 것 자체가 낭비지 — 자는 사람한테 1초마다 전화해서 "아직 자요?" 묻는 꼴이야. 그래서 안 바뀌는 액터는 후보 목록에서 아예 빼서 재우고, 값이 바뀌는 순간에만 깨워서 다시 넣어. 지우는 게 아니라 클라도 서버도 이미 아는 상태를 믿고 네트워크만 잠깐 쉬게 하는 장치야.

↳ 조선 서버로 치면 어떤 최적화랑 같은 거예요?

답 보기
브로드캐스트 대상 리스트에서 가만히 있는 NPC를 빼두는 그거랑 같아. 우리도 몹 HP나 좌표가 진짜 바뀔 때만 SP_*를 뿌리지, 안 바뀌는 애를 매 틱 뿌리진 않잖아. dormancy는 우리가 손으로 짜던 "안 바뀌면 안 보낸다"를 엔진이 상태기계로 표준화한 거야 — 우린 매번 다시 짜고, UE는 NetDormancy 값 하나 세팅하면 끝.

↳ 안 쓰면 뭐가 망가지나요?

답 보기
안 바뀌는 걸 계속 보내면 send 버퍼가 쌓이고, 브로드캐스트 루프가 길어지고, 락 잡는 구간도 늘어. 그래서 정작 중요한 전투 패킷이 밀려. 액터 만 개짜리 맵에서 이게 다 매 틱 후보에 오르면 정렬·전송 계산이 통째로 낭비되는 거지.

Q2. 그럼 재우는 흐름이 큰 그림에서 어떻게 도나요?

답 보기
재우기는 이벤트가 아니라 매 틱 서버 리플리케이션 루프가 스스로 하는 일이야. 릴레번트한 액터를 돌 때마다 "얘 재워도 되냐?"를 검사해. 재워도 되면 바로 안 재우고 먼저 예약만 걸어 — 남은 변경분을 다 밀어보내야 하니까. 그게 다 나가고, 유예 시간까지 지나면 그제서야 진짜로 채널을 닫고 잠들어. 그리고 모든 커넥션이 다 잠들면 그 액터를 "전부 잠든 목록"으로 옮기는데, 이 목록에 들어가면 다음 틱부터 복제 후보에서 아예 빠져 — 그래서 트래픽이 0이 되는 거야.

↳ 왜 바로 안 재우고 '예약 → 실제 재우기' 2단계로 나눴어요?

답 보기
재우기로 했어도 아직 못 보낸 변경분(프로퍼티·서브오브젝트)이 남아 있을 수 있거든. 그걸 다 안 보낸 채로 채널을 닫아버리면 클라 화면이 절반만 갱신된 상태로 어긋나. 그래서 예약해두고 "남은 게 정말 0인가?"를 매 틱 확인하다가, 다 나갔을 때만 진짜로 닫는 거야.

↳ '유예(히스테리시스)'는 또 왜 있어요? 조용해지면 바로 재우면 안 되나요?

답 보기
살짝 움직이고 멈추고, 또 살짝 움직이는 액터를 변경분 0 되는 순간 바로 재우면 재웠다 깨웠다를 반복(채터링)해. 채널을 닫고 열고 닫고 열고 하니까 오히려 트래픽이 더 새고 CPU만 태워. 그래서 "조용해졌다"고 바로 안 재우고 일정 시간 계속 조용해야 진짜 재우는 완충 구간을 둔 거야 — 진동을 흡수하는 스펀지지.

Q3. 그런데 왜 재우기는 루프가 하고, 깨우기는 이벤트로 하나요? 대칭으로 하면 깔끔하지 않아요?

답 보기
이 비대칭이 이 챕터의 핵심이야. 재우기를 이벤트로 하면 "중간에 접속하는 클라"를 특별 취급해야 해서 골치야. 서버가 "액터A 재워!" 이벤트를 쐈는데 직후에 새 클라가 붙으면, 걘 그 이벤트를 못 받았잖아. 그럼 "얘한텐 재운 걸로 쳐야 하나?" 예외가 줄줄이 생겨. 그래서 재우기는 매 틱 루프가 각 커넥션 상태를 보고 알아서 처리하게 뒀어 — 일은 어차피 커넥션당 1번으로 똑같은데 신규 접속 예외가 사라져. 반대로 깨우기는 이미 붙어있는 클라한테만 영향을 주니까 이벤트로 해도 안전하고, 오히려 효율적이야.

↳ 깨우기를 이벤트가 아니라 루프로 하면 뭐가 손해예요?

답 보기
깨우기도 루프로 하면 매 틱마다 자고 있는 모든 액터를 "너 이제 깰 때 됐니?" 하고 순회해야 해. 자는 애가 많을수록 손해가 커지는데, 그건 dormancy로 아끼려던 걸 도로 까먹는 짓이야. 그래서 깨우기는 값이 바뀌는 순간 딱 한 번, 지금 존재하는 커넥션만 돌면 끝나는 이벤트로 둔 거야.

↳ 그 깨우는 함수 이름이 FlushNetDormancy죠? 이름에 Dormancy가 들어가는데 재우는 거 아니에요?

답 보기
함정이야. Flush = 깨우기야. "휴면 목록에서 씻어내(flush) 최소 한 번 더 강제로 보냄"이라는 뜻이라, 이름에 Dormancy가 붙어 있어도 하는 일은 자던 액터를 다시 active로 돌리는 거야. 자꾸 거꾸로 읽게 되는 이름이라 못 박아두면 돼 — Flush는 깨우기.

Q4. 잔다는 게 지운다는 거랑 뭐가 달라요? 그냥 액터 삭제하면 안 되나요?

답 보기
액터는 살아있고 채널만 접히는 거야. 클라도 그 자리에 그 액터가 있는 줄 그대로 알고 있어. 지워버리면 클라 화면에서 사라지고, 값이 바뀔 때 다시 스폰·재전송하는 비용이 훨씬 커. dormancy는 "이미 서로 아는 상태니까 네트워크만 끊고, 필요하면 언제든 다시 연다"는 거라, 삭제와는 목적이 정반대야.

↳ 커넥션마다 다르게 재울 수도 있나요?

답 보기
있어. DORM_DormantAll은 모든 커넥션에 통째로 재우는 거고, DORM_DormantPartial은 커넥션마다 판정해서 이 클라한텐 자고 저 클라한텐 깨어있게 할 수 있어. 시야 밖이면 재우는 식으로 쓰지. 우리 식으로는 "PC A한텐 이 NPC 안 뿌리고, PC B한텐 뿌리고"를 엔티티×PC 단위로 스위칭하는 거랑 같아.

🎯 원리 한 줄 요약

안 바뀌는 액터는 리플리케이션 루프가 스스로 검사해 조용히 재우고(장부에서 빼 트래픽 0), 값이 바뀌는 순간 게임코드가 이벤트로 딱 한 번 깨워 다시 복제 대상에 올린다 — 재우기는 루프, 깨우기는 이벤트, 이 비대칭이 dormancy의 전부다.
