변경분만: Changelist / 델타

언리얼 네트워크 · 16 / 43

왜 이걸 배워? — 문제의식부터

게임 서버를 짜봤으면 이런 장면이 익숙할 거야. CChosunPlayer의 HP가 1 줄었거나 좌표가 조금 바뀌었는데, 우리는 습관처럼 SP_ 패킷 구조체를 통째로 채워서 주변 클라에게 뿌려. IOCP 워커가 CM_을 받아 넘기고, 단일스레드 게임 로직에서 상태를 바꾼 뒤, 다시 SP_로 알려주는 그 흐름 말이야.

처음엔 이게 제일 단순해. 그런데 사람이 10명일 땐 괜찮던 방식이, 액터 1,000개와 클라 100명이 되면 갑자기 수도꼭지를 다 열어둔 것처럼 대역폭을 먹기 시작해. 실제로 바뀐 건 HP 하나인데 위치, 버프, 장비, 이름표까지 매번 같이 싣는다면, 서버는 "새 소식"이 아니라 "집 전체 복사본"을 계속 배달하는 셈이야.

그럼 "바뀐 것만 보내자" 하고 손으로 dirty 플래그를 만들 수 있어. 하지만 여기서 또 문제가 생겨. 플래그 하나 빼먹으면 클라 화면은 옛값에 멈추고, 여러 연결이 각자 다른 타이밍에 받으면 누구는 최신이고 누구는 한 박자 뒤처져. 락으로 막자니 복잡해지고, 단일스레드로 순서 보장해도 "어디까지 보냈는지"는 연결마다 따로 기억해야 해.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 Changelist야. 현재 값과 직전에 보낸 그림자 값을 비교해서 "몇 번 프로퍼티가 바뀌었다"는 번호표만 뽑고, 그 번호표 묶음을 히스토리에 쌓아둔다. 택배 상자 전체를 다시 보내는 게 아니라, "이번엔 3번, 7번만 새로 포장해"라고 적힌 주문서부터 만드는 거야.

그래서 이 챕터는 리플리케이션의 절약 장치를 배우는 자리야. 앞에서 프로퍼티를 Cmds라는 표로 눕히는 법을 봤다면, 이번엔 그 표에서 이번 프레임에 실제로 보낼 줄만 고르는 법을 본다. 뒤에서 RepNotify나 ack/nak 재전송을 읽을 때도, "무엇이 바뀌었고, 누가 어디까지 받았나"라는 changelist 감각이 있어야 길을 잃지 않아.

한 줄로 문제의식만 잡고 가자. 통짜 송신은 쉽지만 비싸고, 손수 dirty 관리는 실수하기 쉽다. Changelist는 그 사이에서 엔진이 자동으로 "바뀐 것만" 골라 주는 장부다.

들어가기 전에: 방 사진을 매번 다시 찍지 않는다

CCTV를 생각해봐. 카메라가 1초에 30번, 매번 방 전체를 통짜 사진으로 찍어 보내면? 대역폭이 순식간에 터져. 그래서 영상 압축은 다른 짓을 해 — 첫 장(키프레임)만 통짜로 보내고, 그다음부터는 "직전 프레임과 뭐가 달라졌는지"만 보내. 사람이 손을 들었으면 손 부분 픽셀만. 배경은 안 보내. 이걸 델타(delta) 인코딩이라고 해.

리플리케이션도 똑같은 고민을 해. 액터에 Health, Mana, Position, Buffs[]... 프로퍼티가 20개 있는데, 이번 프레임에 Health 딱 하나만 깎였어. 그럼 20개를 다 보낼 이유가 없잖아. 바뀐 1개만 보내면 돼. 문제는 "뭐가 바뀌었나"를 서버가 어떻게 알아내고, 그걸 어떻게 골라 보내느냐야.

그 "뭐가 바뀌었나"를 뽑아내고 목록으로 들고 다니는 게 이번 챕터 주제, Changelist(체인지리스트) 야. 그리고 이걸 실제로 구현하는 게 이 파일들이야:

  • Runtime/Engine/Private/RepLayout.cpp — 비교·병합·송신 로직
  • Runtime/Engine/Public/Net/RepLayout.h — Changelist 자료구조
  • Runtime/Engine/Private/DataReplication.cpp — 프레임당 진입점

이 클론에 소스 있음. 아래 코드는 전부 실제 원문 그대로고 파일:줄번호를 달았어. 앞 챕터에서 "프로퍼티를 표(Cmds)로 눕히는 법"을 봤지(→ replayout). 이번엔 그 표를 굴려서 바뀐 것만 골라내는 이야기야.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 길어 보이는 줄도 결국 "비교한다 → 번호를 적는다 → 모아둔다" 세 동작이 반복될 뿐이야. 낯선 기호는 코드 바로 아래 🔤 상자에서 풀어줄게.

🌱 이 개념은 왜 생겼나 — 그림자 데이터(Shadow)
• 원래 구조: "바뀐 것만 보내자"고 마음먹었어. 근데 서버는 지금 값만 들고 있잖아 — 현재 HP가 80이라는 것만 알아.
• 그런데 문제: "바뀌었다"고 말하려면 뭐랑 비교해야 하는데, 비교할 옛날 값이 없어. 직전에 뭘 보냈는지 기억을 안 하면 매 프레임 "바뀐 건가 아닌가"를 판단할 기준선이 없어.
• 그래서 필요한 것: 직전에 보낸 값의 사본을 서버가 한 벌 더 들고 있는 것. → 이게 그림자 데이터야. 현재 값 ↔ 그림자를 비교해 다르면 "바뀜", 그리고 그림자를 새 값으로 갱신해 다음 기준선으로 삼는다.

1. "바뀐 걸 어떻게 아나" — 그림자와 비교한다

서버는 매 프레임 액터의 현재 값을 들고 있어. 근데 "바뀌었다"고 말하려면 뭐랑 비교해야 하잖아. 비교 대상이 있어야지. 그게 그림자 데이터(shadow) 야 — 직전에 보낸 값의 사본. 서버가 따로 한 벌 더 들고 있어.

흐름은 단순해:

  1. 이번 프레임 현재 값 vs 그림자(직전 값) 를 프로퍼티 하나씩 비교.
  2. 같으면? 안 바뀐 거니까 무시.
  3. 다르면? "바뀐 프로퍼티 번호(핸들)"를 목록에 적고, 그림자를 현재 값으로 덮어써(다음 비교 기준선 갱신).

이 심장부가 여기야:

else if (SharedParams.bForceFail || !PropertiesAreIdentical(Cmd, ShadowData.Data, Data.Data, SharedParams.NetSerializeLayouts)) { StoreProperty(Cmd, ShadowData.Data, Data.Data); StackParams.Changed.Add(Handle); }

— RepLayout.cpp:1682

🔤 기호 사전 — else if (SharedParams.bForceFail || !PropertiesAreIdentical(...))
• else if = 앞의 경우가 아니었을 때, "그럼 이번 조건은?" 하고 한 번 더 물어보는 갈림길.
• . = 상자 안 칸으로 들어가는 점. SharedParams.bForceFail은 SharedParams 상자의 bForceFail 칸.
• || = "또는". 왼쪽이나 오른쪽 중 하나만 맞아도 이 안으로 들어가.
• ! = 뜻을 뒤집는 표시. PropertiesAreIdentical이 "같다"인데, 앞에 !가 붙어서 "같지 않다" 가 돼.
• StoreProperty(...) = 지금 값을 그림자 칸에 복사해서 다음 비교의 기준선을 새로 박는 일.
• Changed.Add(Handle) = 바뀐 번호표(Handle)를 Changed 목록 끝에 붙이는 일.
🔁 이제 다시 보자. bForceFail(강제로 바뀐 걸로 치기)이거나 !PropertiesAreIdentical(그림자와 현재 값이 다름)이면, StoreProperty로 그림자를 새 값으로 갈아끼우고 Changed.Add(Handle)로 "이 번호가 바뀌었다"를 적는다. 값 전체를 담는 게 아니라 번호표만 적는 코드로 보이지?

한 줄씩 뜯어보자.

  • PropertiesAreIdentical(Cmd, ShadowData.Data, Data.Data, ...) — 그림자(ShadowData)와 현재 값(Data)이 똑같냐? 앞에 !가 붙었으니 "안 똑같으면" 이 if 안으로 들어와. (bForceFail은 "무조건 바뀐 걸로 쳐라"는 강제 플래그. 초기화 같은 특수 상황용.)
  • StoreProperty(Cmd, ShadowData.Data, Data.Data) — 그림자를 현재 값으로 갱신. 다음 프레임의 기준선을 여기서 새로 박아. 이걸 안 하면 다음 프레임에도 "바뀌었다"고 또 걸려서 무한히 보내게 돼.
  • StackParams.Changed.Add(Handle) — 바뀐 프로퍼티의 핸들(번호) 을 목록에 추가. 여기가 "바뀐 것만" 모으는 진짜 심장부야. 값이 아니라 번호만 담는다는 점을 꼭 기억해.

핸들이 뭐냐면, 복제 프로퍼티를 가리키는 1-based 인덱스야(0은 종료자로 예약). "3번 프로퍼티, 7번 프로퍼티가 바뀌었다" — 이렇게 번호로만 표시해. 값 20KB 대신 번호 몇 개. 이게 대역폭을 아끼는 첫 번째 트릭이야.

이 비교를 재귀로 프로퍼티 트리 전체에 돌리는 게 CompareProperties_r(RepLayout.cpp:1648)이고, 그걸 부르는 상위가 CompareProperties(RepLayout.cpp:1777)야. Push Model이 켜져 있으면 dirty로 찍힌 것만 비교하고, 아니면 전수 비교해(그 최적화 이야기는 → push-model).

🌱 이 개념은 왜 생겼나 — 핸들(번호표) 목록 = Changelist
• 원래 구조: 바뀐 걸 골랐으면, 그 프로퍼티 이름이랑 값을 통째로 목록에 담아 보내면 되잖아.
• 그런데 문제: 근데 "Health"라는 글자를 매번 같이 실으면 그것도 대역폭이고, 20개 프로퍼티 중 뭐가 바뀌었는지를 글자로 표시하면 무거워. 델타로 아낀 대역폭을 이름표로 도로 까먹어.
• 그래서 필요한 것: 프로퍼티마다 정수 번호(핸들)를 매겨두고, "3번, 7번이 바뀌었다"처럼 번호만 목록에 담는 것. → 이 번호 목록이 Changelist야. 값 자체는 여기 없고, 나중에 송신할 때 그 번호로 진짜 값을 찾아 실어.

2. Changelist 한 개의 실체 — 번호 목록 + 영수증

방금 Changed.Add(Handle)로 채운 그 목록이 바로 changelist 한 개야. 자료구조로는 이렇게 생겼어:

/** Range of the Packets that this changelist was last sent with. Used to track acknowledgments. */ FPacketIdRange OutPacketIdRange; /** List of Property Command Handles that changed in this changelist. */ TArray<uint16> Changed; /** Whether or not this Changelist should be resent due to a Nak. */ bool Resend = false;

— RepLayout.h:356 (FRepChangedHistory)

🔤 기호 사전 — FPacketIdRange OutPacketIdRange; / TArray<uint16> Changed; / bool Resend = false;
• /** ... */ = 사람만 읽는 설명 메모. 컴퓨터가 실행하는 명령은 아니야.
• FPacketIdRange = 패킷 번호의 시작과 끝을 담는 작은 상자. "어느 택배 묶음에 실어 보냈나"를 기억하려고 써.
• TArray<uint16> = uint16 번호들을 담는 UE식 리스트. 여기서는 바뀐 핸들 번호들이 줄줄이 들어가.
• bool = 켜짐/꺼짐, 참/거짓만 담는 스위치.
• = false = 처음 값은 "꺼짐"으로 시작한다는 뜻. 아직 재전송할 필요 없다는 말이야.
• ; = C++ 문장 끝 표시. 글에서 마침표 같은 역할.
🔁 이제 다시 보자. 이 구조체는 Changed에 "몇 번이 바뀌었는지" 번호 목록을 들고, OutPacketIdRange에 "어떤 패킷에 실었는지" 영수증을 붙이고, Resend로 "못 받았다면 다시 보낼지" 스위치를 들고 있어. changelist가 그냥 번호 목록만이 아니라 번호 목록 + 배송 영수증으로 보이지?

핵심은 가운데 TArray<uint16> Changed — 바뀐 핸들 번호들의 배열. 이게 changelist의 알맹이야. 나머지 둘은 "영수증" 같은 거야:

  • OutPacketIdRange — 이 changelist를 어떤 패킷에 실어 보냈나. 상대가 "그 패킷 잘 받았어(ack)"라고 하면 이 changelist는 임무 완료. (ack 이야기는 → reliability-ack)
  • Resend — 상대가 "못 받았어(nak)"라고 하면 이 플래그를 켜서 다시 보내. 델타 방식의 아킬레스건이 이거야 — "바뀐 것만" 보내는데 그게 유실되면? 다음에 그 프로퍼티가 또 바뀌기 전엔 영원히 옛날 값으로 남아. 그래서 nak 재전송이 필수야.

즉 changelist 하나 = "이 프레임에 몇 번, 몇 번이 바뀌었다(Changed)" + "어디로 보냈고 재전송 필요하냐(영수증)". 프로퍼티 데이터 자체는 여기 없어. 번호만 있어. 실제 값은 나중에 송신 시점에 그림자 말고 진짜 오브젝트 메모리에서 다시 읽어 실어.

3. 여기서 예측 하나 — "변경 추적기"는 변경을 추적할까?

소스를 뒤지다 보면 FRepChangedPropertyTracker라는 클래스를 만나. 이름이 딱 "바뀐 프로퍼티 추적기"잖아. 그럼 방금 본 그 Changed 목록이 여기 저장되겠지? 이름값 하잖아.

...맞춰봐.

반전: 아니야. 이 클래스는 "무엇이 바뀌었나"를 저장하지 않아. 헤더 주석(RepChangedPropertyTracker.h:14-20)이 스스로 고백해 — 이 클래스는 연결들 사이에서 공유되는 프로퍼티 메타데이터(이 프로퍼티가 지금 Conditional/Active 상태냐, Replay용 외부 데이터가 뭐냐)를 담을 뿐이고, "하는 일에 맞게 이름을 바꿔야 한다(TODO)"라고 적혀 있어. Epic 개발자도 이름이 거짓말이라는 걸 알고 주석에 사과문을 남긴 거지.

진짜 "변경분(changelist)" 알맹이는 우리가 1·2절에서 본 FRepChangelistState / FRepChangedHistory / CompareProperties가 담당해. 이름만 보고 넘겨짚으면 엉뚱한 파일에서 반나절 헤맨다. 네트워크 코드에서 이런 이름-실체 불일치는 흔해. 항상 주석과 실제 쓰임을 확인해.

🌱 이 개념은 왜 생겼나 — 64칸 변경 이력 버퍼
• 원래 구조: 방금 만든 changelist 하나만 들고 있다가, 모두에게 보내고 버리면 되잖아.
• 그런데 문제: 근데 연결마다 진도가 달라. 방금 접속한 클라는 최근 것만 받으면 되지만, 잠깐 랙 걸렸던 클라는 밀린 지점부터 몰아 받아야 해. 최신 하나만 들고 있으면 뒤처진 연결이 놓친 변경분을 못 챙겨줘.
• 그래서 필요한 것: 최근 변경 이력을 여러 개(64칸) 창고에 쌓아두고, 연결마다 "너는 여기부터" 하고 잘라 주는 것. → 이게 64칸 순환버퍼야. 꽉 차면 가장 오래된 걸 다음 것에 병합해 정보를 안 잃는다.

4. Changelist를 어디에 쌓나 — 64칸 순환버퍼

changelist 하나를 만들었어. 이걸 어디 보관하지? 오브젝트마다 64칸짜리 순환버퍼에 히스토리로 쌓아:

/** The maximum number of individual changelists allowed.*/ static const int32 MAX_CHANGE_HISTORY = 64; /** Circular buffer of changelists. */ FRepChangedHistory ChangeHistory[MAX_CHANGE_HISTORY]; /** Changelist state specific to Custom Delta properties. Only allocated if this RepLayout has Custom Delta Properties. */ TUniquePtr<struct FCustomDeltaChangelistState> CustomDeltaChangelistState; /** Index in the buffer where changelist history starts (i.e., the Oldest changelist). */ int32 HistoryStart = 0; /** Index in the buffer where changelist history ends (i.e., the Newest changelist). */ int32 HistoryEnd = 0;

— RepLayout.h:449 (FRepChangelistState)

🔤 기호 사전 — static const int32 MAX_CHANGE_HISTORY = 64;
• static const = 모두가 같이 보는 고정 숫자. 실행 중에 이리저리 바꿔 쓰는 값이 아니야.
• int32 = 정수를 담는 32비트 숫자 칸. 여기서는 "몇 칸까지 둘까" 같은 개수를 담아.
• MAX_CHANGE_HISTORY = "최대로 보관할 변경 이력 개수"라는 이름표.
• ChangeHistory[MAX_CHANGE_HISTORY] = ChangeHistory라는 칸을 MAX_CHANGE_HISTORY개, 즉 64칸 만들어 둔 배열.
• TUniquePtr<struct ...> = 필요할 때만 붙이는 "혼자 들고 있는 주소표". 여기서는 Custom Delta용 별도 상태가 있을 때만 붙는다.
• = 0 = 처음 시작값을 0으로 맞춰 둔다. 아직 히스토리를 하나도 안 굴린 출발점이야.
🔁 이제 다시 보자. MAX_CHANGE_HISTORY = 64로 창고 크기를 정하고, ChangeHistory[MAX_CHANGE_HISTORY]로 changelist 64칸을 만들고, HistoryStart/HistoryEnd로 그 창고의 시작과 끝을 가리킨다. 길어 보여도 핵심은 64칸짜리 변경 이력 창고 + 양쪽 포인터 두 개야.

ChangeHistory[64]가 그 순환버퍼야. HistoryStart가 가장 오래된 것, HistoryEnd가 가장 최신. 이 둘 사이 구간이 "아직 살아있는 changelist들"이야.

왜 하나만 안 들고 여러 개(64개)를 쌓냐고? 연결마다 진도가 다르기 때문이야. 방금 접속한 클라는 최근 것만 받으면 되지만, 잠깐 랙 걸렸던 클라는 좀 밀린 지점부터 몰아서 받아야 해. 하나만 들고 있으면 뒤처진 연결을 못 챙겨. 그래서 최근 64프레임치 변경 이력을 창고에 쌓아두고, 연결마다 "너는 여기부터" 하고 잘라 주는 거야.

버퍼가 꽉 차면(64개) 어떻게? 가장 오래된 걸 버리는데, 그냥 버리면 그 변경분이 증발하잖아. 그래서 바로 다음 것에 병합해서 정보를 살려:

// Null terminator Changed.Add(0); // Move end pointer RepChangelistState->HistoryEnd++; // New changes found so clear any existing shared serialization state RepChangelistState->SharedSerialization.Reset(); // If we're full, merge the oldest up, so we always have room for a new entry if ((RepChangelistState->HistoryEnd - RepChangelistState->HistoryStart) == FRepChangelistState::MAX_CHANGE_HISTORY) { const int32 FirstHistoryIndex = RepChangelistState->HistoryStart % FRepChangelistState::MAX_CHANGE_HISTORY; RepChangelistState->HistoryStart++;

— RepLayout.cpp:1895

🔤 기호 사전 — Changed.Add(0) / HistoryEnd++ / %
• Changed.Add(0) = 목록 끝에 0을 붙여서 "여기서 끝"이라고 표시. 핸들은 1부터라서 0을 끝표시로 쓸 수 있어.
• ++ = 숫자를 한 칸 앞으로 민다는 뜻. HistoryEnd++는 최신 끝 포인터를 한 칸 전진시켜.
• Reset() = 들고 있던 임시 상태를 비우는 버튼. 새 변경이 생겼으니 예전 공유 직렬화 상태를 털어내는 거야.
• if (...) = 괄호 안 조건이 맞을 때만 아래 블록을 실행하는 문.
• == = "같다" 비교. =처럼 값을 넣는 게 아니라, 양쪽이 같은지 물어보는 표시야.
• FRepChangelistState::MAX_CHANGE_HISTORY = FRepChangelistState 상자에 붙어 있는 MAX_CHANGE_HISTORY 값을 꺼내 쓰는 소속 표시.
• % = 나머지. 큰 히스토리 번호를 64칸짜리 실제 배열 칸으로 다시 접어 넣을 때 써.
🔁 이제 다시 보자. Changed.Add(0)으로 목록 끝표시를 붙이고, HistoryEnd++로 새 이력을 정식 커밋하고, 꽉 찼는지는 End - Start == 64로 확인한다. 꽉 찼으면 %로 실제 배열 칸을 찾아 가장 오래된 쪽을 밀어낼 준비를 하는 흐름이야.

읽는 법:

  1. Changed.Add(0) — 목록 끝에 0(종료자)을 박아 "여기가 끝"이라고 표시. (핸들은 1부터니까 0은 항상 끝을 뜻해.)
  2. HistoryEnd++ — 최신 포인터를 한 칸 전진. 새 changelist가 히스토리에 정식 커밋됨.
  3. 꽉 찼으면(End - Start == 64) HistoryStart++로 가장 오래된 걸 밀어내되, 그 전에 MergeChangeList로 다음 것에 합쳐. "3번이 바뀌었다"는 이력이 사라지는 게 아니라 바로 다음 슬롯으로 흡수되는 거지. 그래서 아무리 오래 안 챙긴 연결도, 최소한 병합된 형태로는 변경분을 놓치지 않아.

만약 어떤 연결이 64프레임보다 더 심하게 뒤처지면? 그땐 델타를 포기하고 "전체 다시 보내기"로 폴백해(RepLayout.cpp:2080 근처). 델타는 어디까지나 "직전 대비"라, 기준선을 잃으면 통짜로 리셋하는 게 안전하니까.

5. "하나 계산, 여러 연결이 나눠 먹기" — 공유의 묘

여기가 이 시스템에서 제일 영리한 부분이야. 서버에 접속한 클라가 100명이라고 하자. 액터 하나의 변경 비교를 연결마다 100번 하면 낭비잖아. 값은 하나인데.

그래서 언리얼은 비교를 프레임당 딱 1번만 해. 그 진입점이 UpdateChangelistMgr(RepLayout.cpp:1275)인데, "이번 프레임에 이 오브젝트 아직 비교 안 했으면 지금 해라, 이미 했으면 스킵"이야. 100개 연결이 같은 오브젝트를 복제해도 비교는 1번, 결과(changelist 히스토리)는 모두가 공유해.

그럼 연결별로 다른 건 뭐냐? "어디까지 보냈나" 하나뿐이야. 연결마다 LastChangelistIndex를 들고, 자기가 마지막으로 보낸 지점부터 최신까지를 그때그때 하나로 병합해서 보내:

// Gather all change lists that are new since we last looked, and merge them all together into a single CL for (int32 i = RepState->LastChangelistIndex; i < RepChangelistState->HistoryEnd; ++i) { const int32 HistoryIndex = i % FRepChangelistState::MAX_CHANGE_HISTORY; FRepChangedHistory& HistoryItem = RepChangelistState->ChangeHistory[HistoryIndex]; TArray<uint16> Temp = MoveTemp(Changed); MergeChangeList(Data, HistoryItem.Changed, Temp, Changed); }

— RepLayout.cpp:2099 (FRepLayout::ReplicateProperties)

🔤 기호 사전 — for (int32 i = RepState->LastChangelistIndex; i < RepChangelistState->HistoryEnd; ++i)
• for (시작; 조건; 다음) = 정해진 구간을 한 칸씩 도는 반복문. "여기서 시작해서, 이 조건이 맞는 동안, 매번 이렇게 움직여"라는 뜻이야.
• RepState->LastChangelistIndex = 이 연결이 마지막으로 본 위치. ->는 주소표가 가리키는 상자 안 칸을 꺼내는 화살표야.
• i < RepChangelistState->HistoryEnd = i가 최신 끝에 닿기 전까지만 돈다. 아직 안 본 변경분만 훑는다는 뜻.
• i % FRepChangelistState::MAX_CHANGE_HISTORY = 긴 히스토리 번호를 64칸 배열 번호로 접어 넣기.
• FRepChangedHistory& = 히스토리 한 칸을 복사하지 말고 원본으로 잡는 표시. &가 붙어서 진짜 칸을 바로 본다.
• MoveTemp(Changed) = 지금 들고 있던 목록을 잠깐 임시 상자로 옮겨 병합 재료로 쓰는 것.
• MergeChangeList(...) = 이전 목록과 새 목록을 합쳐 "그동안 바뀐 것 전부" 한 묶음으로 만드는 함수.
🔁 이제 다시 보자. LastChangelistIndex부터 HistoryEnd 전까지 for로 돌면서, 각 히스토리 칸을 % 64로 찾아오고, MergeChangeList로 누적 목록을 계속 합친다. 즉 이 코드는 이 연결이 놓친 변경분들을 한 봉투로 뭉치는 루프야.

RepState->LastChangelistIndex(이 연결이 마지막으로 본 지점)부터 HistoryEnd(최신)까지 히스토리를 돌면서, 그 사이의 changelist들을 MergeChangeList로 하나로 합쳐. 3프레임 밀린 연결이면 3개 프레임의 변경분이 한 덩어리로 뭉쳐서 "그동안 바뀐 것 전부"가 되는 거지.

이 구조를 한 문장으로: 비교(델타 계산)는 오브젝트당 1번 공유, 진도(어디까지 보냈나)만 연결당 따로. 그래서 두 개의 상태 객체로 갈라져 있어 —

  • FRepChangelistState — 오브젝트당 1개. 순환버퍼·HistoryStart/End·비교 결과. 모두가 공유하는 델타의 원천.
  • FSendingRepState — 연결당 1개. LastChangelistIndex로 이 연결의 진도만 추적.

이름이 헷갈리기 쉬운데, "State가 두 종류"라는 것만 잡고 가. 하나는 값의 창고(오브젝트), 하나는 진도표(연결).

6. 마지막 — 병합된 것만 비트로

연결별로 "그동안 바뀐 핸들 목록"을 하나로 뽑았어. 이제 그 핸들들만 실제 값으로 직렬화해서 보내면 끝이야:

🔤 기호 사전 — FChangelistIterator ... SendProperties_r(...)
• Iterator = 목록을 한 칸씩 짚고 지나가는 손가락. 직접 값을 다 들고 있는 게 아니라 "다음은 여기" 하고 가리키며 돈다.
• FChangelistIterator(Changed, 0) = Changed 목록을 0번 위치부터 읽을 준비.
• FRepHandleIterator = 핸들 번호를 실제 Cmds 표 위치로 바꿔가며 걷는 손가락.
• Cmds.Num() - 1 = Cmds의 마지막 칸 번호. 칸이 N개면 마지막 번호는 N-1이야.
• &SharedInfo = SharedInfo 복사본 말고 원본 위치를 넘긴다는 표시.
• SendProperties_r(...) = 준비된 손가락이 가리키는 프로퍼티만 실제 비트로 쓰는 함수.
🔁 이제 다시 보자. FChangelistIterator가 바뀐 번호 목록을 걷고, FRepHandleIterator가 그 번호를 Cmds 표의 실제 줄로 바꾸고, SendProperties_r이 그 줄의 값만 비트로 쓴다. 그래서 안 바뀐 19개는 애초에 이 길에 올라타지도 못해.

FChangelistIterator가 Changed(바뀐 핸들 목록)를 순회하고, FRepHandleIterator가 그 핸들을 CH15에서 본 Cmds 표의 실제 위치로 변환해. 그리고 SendProperties_r이 그 핸들에 해당하는 프로퍼티만 비트스트림에 써. 안 바뀐 19개는 이 순회에 아예 안 들어와. 그래서 와이어에는 바뀐 1개만 흘러.

여기서 CH15와 이번 챕터가 딱 맞물려. CH15의 Cmds 표는 "프로퍼티를 어떻게 눕히나"였고, 이번 changelist는 "그 표의 어느 줄만 굴릴까"를 정해. 표는 전체 명세, changelist는 이번에 실행할 부분집합인 셈이야.

8. 우리 서버랑 비교하면

조선협객전 서버로 옮겨 감을 잡자. IOCP 워커 여러 개가 패킷을 받고, 게임 로직은 싱글스레드 액터에서 처리하잖아.

우리가 캐릭터 상태를 클라에 뿌릴 때를 떠올려봐. 보통 SP_XXX 구조체를 만들어서 필요한 필드를 통짜로 채워 보내지. pkt.dwMoney = ...; pkt.iHP = ...; 다 넣고 송신. Health 하나만 바뀌었어도 구조체 전체를 다시 보내는 게 흔해. "바뀐 것만"을 하려면 우리가 손으로 dirty 플래그를 관리하거나, 변경 감지 로직을 직접 짜야 해. 대부분 안 짜고 그냥 통짜로 보내(그게 단순하니까).

언리얼의 changelist는 그 "바뀐 것만 보내기"를 엔진이 자동으로 해주는 거야. 우리가 사람 머리로 "이건 바뀌었으니 보내야지" 판단하던 걸, 언리얼은 그림자 메모리 비교로 기계가 판단해.

처리 스레드IOCP 워커 파싱 → 싱글스레드 로직NetDriver Tick (사실상 단일 흐름)

주목할 트레이드오프 하나. 우리 통짜 방식은 대역폭은 더 쓰지만 유실에 강해 — 패킷 하나 날아가도 다음 프레임 통짜에 최신값이 또 실리니까. 반면 델타 방식은 대역폭은 아끼지만 유실에 취약해서 ack/nak 추적(OutPacketIdRange/Resend)이라는 안전장치를 반드시 얹어야 해. 공짜 점심은 없어. 대역폭을 아낀 대가로 신뢰성 관리 복잡도를 떠안은 거야.

스레드 모델은 비슷해. 우리 IOCP 워커가 여럿이어도 게임 로직은 싱글스레드로 직렬화하듯, 언리얼도 리플리케이션은 사실상 단일 흐름(NetDriver Tick, → netdriver-tick)에서 히스토리 버퍼를 순차로 굴려. "여러 스레드가 같은 changelist 버퍼를 동시에 건드려 꼬이는" 걱정이 없다는 뜻이야.

한 줄로: 우리가 손으로 하던(또는 생략하던) "바뀐 것만 보내기"를, 언리얼은 그림자 비교 + 히스토리 버퍼로 자동화하고, 그 대가로 ack/nak 추적을 짊어졌다.

9. 헷갈리기 쉬운 용어 정리

  • Changelist(체인지리스트) — 한 프레임 비교에서 "값이 바뀐 프로퍼티들의 핸들 번호 목록"(TArray<uint16> Changed). 프로퍼티 데이터 자체가 아니라 "몇 번, 몇 번이 바뀌었다"는 인덱스 목록. 0은 종료자.
  • Handle(핸들) — 복제 프로퍼티를 가리키는 1-based 인덱스(0은 종료자 예약). 배열은 특수 처리 — 첫 항목이 원소 개수, 이후 각 원소 핸들, 자체 0 종료자로 끝(RepLayout.h:325).
  • Shadow data(그림자 / StaticBuffer) — 서버가 든 "직전에 보낸 값" 사본. 현재 값과 이걸 비교(PropertiesAreIdentical)해 델타를 뽑고, 바뀐 값을 StoreProperty로 그림자에 덮어써 다음 기준선을 갱신.
  • FRepChangelistState — 오브젝트당 1개. ChangeHistory[64] 순환버퍼 + HistoryStart/End/CompareIndex. 모든 연결이 공유(비교는 프레임당 1회). 델타의 원천.
  • FSendingRepState — 연결당 1개. LastChangelistIndex로 이 연결이 어디까지 보냈나 추적. 진도표.
  • FRepChangedHistory — changelist 1개. Changed(바뀐 핸들) + OutPacketIdRange(ack 추적) + Resend(nak 재전송).
  • HistoryStart / HistoryEnd — ChangeHistory[64] 순환버퍼의 유효 구간. End=최신, Start=최고(最古). 64개 꽉 차면 가장 오래된 걸 다음 것에 병합해 항상 새 자리 확보.
  • FRepChangedPropertyTracker — 이름은 "변경 추적기"지만 변경분을 저장하지 않아. 연결 간 공유 메타데이터(Conditional/Active 여부 등) 저장용. 실제 변경분은 위 셋이 담당(주석 RepChangedPropertyTracker.h:14의 자백 참고).

마무리 — 여기까지가 원리

이 챕터 목표는 "모든 줄 해설"이 아니라 뼈대 하나야: 리플리케이션은 현재 값을 그림자와 비교해 "바뀐 핸들 번호"만 뽑고(changelist), 그걸 64칸 히스토리에 쌓아 두고, 연결마다 "안 보낸 구간"만 병합해 그 값만 비트로 흘린다. 비교는 공유, 진도는 개별.

  • 프로퍼티가 애초에 어떻게 표(Cmds)로 눕는지가 흐리면 → replayout
  • "매 프레임 전수 비교 대신 dirty 찍힌 것만" 최적화가 궁금하면 → push-model
  • 바뀐 값이 클라에 도착한 뒤 콜백이 어떻게 터지는지(다음 이야기) → repnotify
  • ack/nak가 실제로 어떻게 오가는지 → reliability-ack

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. Changelist, 왜 필요한 물건인가요?

답 보기
액터에 프로퍼티가 20개 있는데 이번 프레임에 Health 하나만 바뀌었어. 20개를 통짜로 다 보내면 대역폭 낭비지. "바뀐 것만" 보내고 싶은 거야. 근데 손으로 dirty 플래그 관리하면 하나 빼먹고 실수하기 쉬워. Changelist는 그 "바뀐 것만 골라내기"를 엔진이 자동으로 해주는 장부야. CCTV 영상 압축이 첫 장만 통짜, 그다음부턴 델타만 보내는 거랑 같은 발상이지.

↳ 그럼 "바뀌었다"는 걸 서버가 어떻게 알아내나요?

답 보기
비교하려면 기준선이 있어야 하잖아. 서버는 지금 값만 들고 있으니까, 직전에 보낸 값의 사본을 한 벌 더 들고 있어 — 그게 그림자(shadow) 데이터야. 매 프레임 현재값 ↔ 그림자를 프로퍼티 하나씩 비교해서 다르면 "바뀜"으로 찍고, 그림자를 새 값으로 덮어써 다음 기준선을 갱신해. 이걸 안 하면 뭐랑 비교할지가 없어서 델타 자체가 성립을 안 해.

↳ 그럼 바뀐 값 자체를 목록에 담나요?

답 보기
아니, 값이 아니라 번호(핸들)만 담아. "3번, 7번이 바뀌었다" 이렇게 정수 번호 목록으로. 이름표("Health")를 매번 실으면 그것도 대역폭이라, 델타로 아낀 걸 이름으로 도로 까먹거든. 그래서 changelist 알맹이는 TArray<uint16> Changed 하나야. 실제 값은 나중에 송신 시점에 그 번호로 진짜 메모리에서 다시 읽어 실어.

Q2. changelist를 왜 하나만 안 들고 64개나 쌓아두나요?

답 보기
연결마다 진도가 다르기 때문이야. 방금 접속한 클라는 최근 것만 받으면 되지만, 잠깐 랙 걸렸던 클라는 밀린 지점부터 몰아 받아야 해. 최신 하나만 들고 있으면 뒤처진 연결이 놓친 변경분을 못 챙겨줘. 그래서 오브젝트마다 64칸 순환버퍼에 변경 이력을 쌓아두고, 연결마다 "너는 여기부터" 하고 잘라 주는 거야.

↳ 64칸이 꽉 차면 가장 오래된 건 그냥 버리나요?

답 보기
그냥 버리면 그 변경분이 증발하잖아. 그래서 가장 오래된 걸 바로 다음 것에 병합해서 정보를 살려. "3번이 바뀌었다"는 이력이 사라지는 게 아니라 다음 슬롯으로 흡수되는 거지. 그래서 아무리 오래 안 챙긴 연결도 최소한 병합된 형태로는 변경분을 놓치지 않아.

↳ 그것보다 더 심하게 뒤처진 연결이면요?

답 보기
64프레임보다 더 밀리면 델타를 포기하고 "전체 다시 보내기"로 폴백해. 델타는 어디까지나 "직전 대비"라 기준선을 잃으면 통짜로 리셋하는 게 안전하니까. 영상으로 치면 키프레임을 다시 한 장 통째로 보내는 거야.

Q3. 클라 100명이면 액터 하나 비교를 100번 하나요?

답 보기
아니, 그게 이 시스템의 제일 영리한 부분이야. 값은 하나인데 100번 비교하면 낭비잖아. 그래서 비교는 오브젝트당 프레임에 딱 1번만 하고 결과(히스토리)는 모두가 공유해. 연결별로 다른 건 "어디까지 보냈나"(LastChangelistIndex) 하나뿐이야. 그래서 상태 객체가 둘로 갈려 — 값의 창고(오브젝트당 1개)와 진도표(연결당 1개).

↳ 그럼 3프레임 밀린 연결한테는 뭘 보내나요?

답 보기
그 연결이 마지막으로 본 지점부터 최신까지의 changelist들을 하나로 병합해서 보내. 3프레임치 변경분이 한 덩어리로 뭉쳐서 "그동안 바뀐 것 전부"가 되는 거지. 비교는 공유하되 병합·송신만 연결마다 따로 하는 구조야.

Q4. 통짜로 보내는 우리 서버랑 비교하면 뭐가 트레이드오프인가요?

답 보기
우리 조선 서버는 SP_ 구조체를 통짜로 채워 보내니까 대역폭은 더 쓰지만 유실에 강해 — 패킷 하나 날아가도 다음 프레임 통짜에 최신값이 또 실리니까. 반면 델타는 대역폭은 아끼지만 유실에 취약해. "바뀐 것만" 보냈는데 그게 유실되면 그 프로퍼티가 또 바뀌기 전엔 영영 옛값 고착이야. 공짜 점심은 없어 — 대역폭 아낀 대가로 신뢰성 관리 복잡도를 떠안은 거야.

↳ 그래서 그 유실 문제를 뭘로 막나요?

답 보기
changelist 하나마다 "어떤 패킷에 실었나"(OutPacketIdRange)라는 영수증과 Resend 플래그를 달아둬. 상대가 ack("받았어")하면 임무 완료, nak("못 받았어")하면 Resend를 켜서 다시 보내. 이 ack/nak 재전송이 델타 방식엔 필수 안전장치야. UDP 위라 이걸 엔진이 직접 얹은 거고, TCP였으면 커널이 해줬을 일이지.

↳ 이름이 "변경 추적기"인 FRepChangedPropertyTracker가 그 변경분을 저장하겠네요?

답 보기
이름값 할 것 같지? 근데 아니야. 얘는 변경분을 저장 안 해. 연결 간 공유되는 프로퍼티 메타데이터(Conditional/Active 여부 등)만 담아. 헤더 주석에 "하는 일에 맞게 이름 바꿔야 한다(TODO)"고 Epic 개발자가 스스로 고백까지 해놨어. 실제 변경분은 FRepChangelistState/FRepChangedHistory가 담당해. 네트워크 코드에서 이름-실체 불일치는 흔하니 항상 주석과 실제 쓰임을 확인해야 한다는 교훈이지.

🎯 원리 한 줄 요약

Changelist는 현재 값을 그림자와 비교해 "바뀐 프로퍼티 번호"만 뽑아 64칸 히스토리에 쌓고 — 비교는 오브젝트당 1번 공유하되 연결마다 "안 보낸 구간"만 병합해 그 값만 보냄으로써, 대역폭을 아끼는 대신 ack/nak 재전송이라는 안전장치를 짊어진다.
