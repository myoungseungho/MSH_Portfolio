Travel: 맵/방을 오가는 법

언리얼 네트워크 · 38 / 42

방을 바꾸는데 왜 접속은 안 끊길까

게임 서버 짜봤으면 "맵 이동"은 익숙하지. 유저가 던전 입구를 밟으면, 서버가 걔를 다른 맵으로 옮긴다. 우리 조선협객전도 워프 패킷 한 방이면 다른 존으로 휙 넘어가.

그런데 여기서 초보가 처음 부딪히는 벽이 하나 있어. UE에서 "맵을 바꾼다"는 건 사실 월드(Level)를 통째로 갈아끼우는 일이야. 옛 맵을 메모리에서 지우고 새 맵을 로드해. 근데 잠깐 — 맵을 통째로 날리면 그 위에 얹혀 있던 네트워크 연결은 어떻게 되지? 소켓이며 복제 상태며 다 옛 월드에 붙어 있었을 텐데.

맞춰봐. 상식적으로는 "맵 갈아끼우면 연결도 끊기고, 클라는 로딩 화면 보다가 다시 접속(핸드셰이크)해야겠지?" 싶지.

반전. UE엔 그걸 안 끊고 넘어가는 길이 있어. 이름이 seamless travel(심리스 트래블). 연결(NetConnection)은 살려둔 채 그 밑의 맵만 살짝 바꿔치기해. 로그인·핸드셰이크를 다시 안 하니까 로딩이 매끄러워. 반대로 연결을 끊고 처음부터 다시 붙는 방식은 hard travel이라고 불러.

그럼 대체 무슨 마법으로 "맵은 바뀌는데 연결은 유지"가 되는 걸까? 이걸 실제로 구현한 게 이번 챕터 주인공이야:

  • UWorld::ServerTravel (World.cpp:9389) — 서버가 "다들 이 맵으로 가자"를 시작하는 권위 진입점
  • FSeamlessTravelHandler (World.cpp 안) — 전환을 프레임마다 굴려서 완성시키는 일꾼
  • FSeamlessTravelHandler::CopyWorldData (World.cpp:8395) — 여기가 진짜 심장. 마법의 정체가 여기 있어
NetConnection·NetDriver가 뭔지, 연결이 소켓 위에 어떻게 얹히는지가 흐릿하면 → netconnection-overview 먼저 보고 와. 이번 챕터는 "그 연결을 옛 월드에서 떼어 새 월드에 옮긴다"는 얘기라, 연결이 뭔지부터 잡고 오는 게 안 헤매. 여기선 다시 설명 안 하고 링크로 넘길게 — 안 그러면 챕터마다 같은 얘기 무한 반복이거든.

1. 두 종류의 여행 — Hard vs Seamless

먼저 큰 그림. Travel엔 두 갈래가 있어.

  • Hard travel: 연결을 끊고 → 새 맵 로드 → 클라가 다시 접속. 확실하고 깔끔하지만 로딩 화면이 뚝 끊겨. (서버 주소 자체가 바뀌는 이동엔 이 방법밖에 없어.)
  • Seamless travel: 연결을 살려둔 채 → 맵만 교체. 로딩이 부드러워. 단, 같은 서버 안에서의 이동일 때만 가능해.

그리고 이 여행의 방아쇠는 항상 서버가 당겨. 서버가 "다 같이 이 맵으로 이동" 명령을 내리고(ServerTravel), 접속한 클라들은 서버가 쏘는 신호를 받아 따라가(ClientTravel). 클라가 제멋대로 맵을 바꾸는 게 아니라 서버 권위로 움직이는 거야. 우리 서버에서 워프도 서버가 좌표를 확정해 내려주지 클라가 우기는 게 아닌 것과 똑같은 감각이야.

여기서 한 가지 더. Seamless travel은 곧장 목적지 맵으로 점프하지 않아. 중간에 트랜지션 맵(transition map)이라는 가벼운 빈 맵을 한 번 거쳐. 왜 이 귀찮은 짓을 하냐면 — 옛 맵을 GC로 안전하게 지우고 무거운 새 맵을 로드할 "숨 돌릴 시간"이 필요하거든. 이삿짐 옮길 때 텅 빈 임시 창고를 한 번 거치는 거랑 같아. (이 빈 맵 이름은 UGameMapsSettings::TransitionMap에 설정돼 있어.)

2. 서버가 여행을 시작한다 — ServerTravel

진입점부터. 서버가 "전원 이 맵으로 이동" 하고 싶으면 UWorld::ServerTravel을 불러.

World.cpp:9389

bool UWorld::ServerTravel(const FString& FURL, bool bAbsolute, bool bShouldSkipGameNotify) { AGameModeBase* GameMode = GetAuthGameMode(); if (GameMode != nullptr && !GameMode->CanServerTravel(FURL, bAbsolute)) { return false; } // Set the next travel type to use NextTravelType = bAbsolute ? TRAVEL_Absolute : TRAVEL_Relative;

읽어보면 별거 없어. 두 가지만 해.

  1. GetAuthGameMode() — 이 함수는 서버(권위자)에서만 유효한 GameMode를 꺼내. 즉 "너 서버 맞아?"를 여기서 은근히 확인하는 거야. 클라에서 부르면 여기서 튕겨.
  2. CanServerTravel — GameMode한테 "지금 여행해도 돼?"를 물어봐. 규칙상 이동 금지 상황이면 false 반환하고 여기서 끝. 우리 서버로 치면 "이 유저 지금 전투 중이라 워프 못 해" 같은 게이트를 GameMode가 쥐고 있는 거지.

그다음 NextTravelType을 정해. bAbsolute면 TRAVEL_Absolute(완전히 새 주소/서버로), 아니면 TRAVEL_Relative(지금 붙어 있는 서버 기준 상대 이동). 이 갈림길 기억해둬 — 뒤에서 "seamless는 Relative만 된다"는 규칙이 여기랑 연결돼.

허가가 떨어지면 목적지 URL을 NextURL에 넣어두고 실제 전환은 GameMode의 ProcessServerTravel로 넘겨.

3. Seamless냐 Hard냐 — 그 판정

AGameModeBase::ProcessServerTravel(GameModeBase.cpp:477)이 실제로 "이번 이동을 매끄럽게 할까, 딱 끊고 갈까"를 정해. 판정 코드가 재밌어.

GameModeBase.cpp:487

// Use game mode setting but default to full load screen if the server has been up for a long time so that TimeSeconds doesn't overflow and break everything bool bSeamless = (bUseSeamlessTravel && GetWorld()->TimeSeconds < 172800.0f); // 172800 seconds == 48 hours

bUseSeamlessTravel 설정이 켜져 있어도, 서버가 48시간(172800초) 넘게 떠 있었으면 강제로 hard travel로 떨어뜨려. 왜? 주석이 친절히 말해줘 — TimeSeconds가 너무 커지면(float 정밀도 한계) 시간 계산이 깨져서 "모든 게 부서진다(break everything)". 그래서 오래 켜진 서버는 매끄러움을 포기하고 안전하게 끊고 가는 거야. 이런 방어 코드, 우리 서버 장기 가동 이슈 겪어봤으면 짠하게 공감될걸.

bSeamless가 정해지면 GameMode는:

  1. 접속한 클라들에게 "너희도 따라와" 신호를 쏘고(각 클라의 ClientTravel),
  2. seamless면 World->SeamlessTravel(...)을 호출해서 진짜 전환을 시작해.

4. 전환 시동 — 트랜지션 맵부터 로드

UWorld::SeamlessTravel(World.cpp:9003)은 URL을 검증한 뒤 실무를 FSeamlessTravelHandler라는 전용 일꾼한테 넘겨. 이 핸들러가 전환의 상태(어디까지 진행됐나)를 들고 프레임마다 조금씩 일을 진행시켜.

핸들러가 StartTravel(World.cpp:8143)에서 제일 먼저 세우는 깃발들:

World.cpp:8190

PendingTravelURL = InURL; bSwitchedToDefaultMap = false; bTransitionInProgress = true; bPauseAtMidpoint = false; bNeedCancelCleanUp = false;

bTransitionInProgress = true — "지금 전환 중"이라는 상태 플래그. 이게 켜지면 핸들러가 "일 진행할 게 있다"고 알아. 그리고 여기서 곧장 목적지 맵을 로드하는 게 아니라, 먼저 트랜지션 맵(빈 임시 맵)을 비동기로 로드하기 시작해(StartLoadingMap).

순서를 정리하면:

  1. 트랜지션 맵 비동기 로드 시작 → 뜨면
  2. StartLoadingDestination(World.cpp:8375)에서 진짜 목적지 맵을 비동기 로드 → 완료되면
  3. SeamlessTravelLoadCallback(World.cpp:8078)이 콜백으로 불려서 로드된 월드를 핸들러에 등록.

전부 비동기라는 게 포인트. 맵 로딩은 무거워서 한 프레임에 끝낼 수 없으니, 로드는 백그라운드로 돌리고 핸들러는 "다 됐나?"를 매 프레임 확인하는 구조야.

5. 매 프레임 굴리기 — TickWorldTravel

그 "매 프레임 확인"은 엔진 틱에 박혀 있어.

UnrealEngine.cpp:15559

Context.SeamlessTravelHandler.Tick();

엔진이 월드를 틱할 때마다 이 한 줄로 핸들러를 굴려. FSeamlessTravelHandler::Tick(World.cpp:8483) 안에서 이런 일이 순서대로 벌어져:

  1. 목적지 맵 로드가 끝났나 확인 (아직이면 그냥 리턴, 다음 프레임에 또 옴)
  2. 로드된 월드가 멀쩡한지 유효성 검사
  3. BeginTearingDown — 옛 월드 철거 시작
  4. 유지할 액터 선별 — PlayerController, PlayerState 같은 "새 맵에도 데려갈 놈들"을 골라내
  5. CopyWorldData 호출 — 다음 절, 여기가 하이라이트
  6. 월드 교체 완료

4번의 "누굴 데려갈까"는 AGameModeBase::GetSeamlessTravelActorList(GameModeBase.cpp:539)와 APlayerController::GetSeamlessTravelActorList(PlayerController.cpp:3648)가 목록을 모아줘. 대부분의 액터는 옛 맵과 함께 사라지지만, 플레이어를 대표하는 액터들은 이 명단에 실려 새 맵으로 이사 가. 안 그러면 맵 바꾸는 순간 유저가 누구였는지도 다 잊어버릴 테니까.

6. 마법의 정체 — NetDriver를 새 월드에 이식

자, 1절에서 던진 질문. "맵은 바뀌는데 연결은 어떻게 유지되지?" 답이 여기 딱 여섯 줄에 있어.

World.cpp:8404

UNetDriver* const NetDriver = CurrentWorld->GetNetDriver(); LoadedWorld->SetNetDriver(NetDriver); if (CurrentCollection && LoadedCollection) { LoadedCollection->SetNetDriver(NetDriver); CurrentCollection->SetNetDriver(nullptr); }

이게 전부야. 딱 두 줄만 눈에 담아.

  • UNetDriver* const NetDriver = CurrentWorld->GetNetDriver(); — 옛 월드에서 NetDriver를 꺼내.
  • LoadedWorld->SetNetDriver(NetDriver); — 그걸 새 월드에 그대로 붙여.

NetDriver가 뭐냐면 — 실제 소켓, 각 클라와의 연결(NetConnection), 복제 상태를 통째로 쥐고 있는 객체야. 이 녀석은 한 번도 파괴되지 않아. 그냥 옛 월드에서 떼서 새 월드에 옮겨 붙일 뿐이야. 소켓은 계속 열려 있고, 클라들과의 연결도 그대로고, 핸드셰이크도 다시 안 해. 밑에 있는 컬렉션(월드 묶음)들도 NetDriver 소유권을 새 쪽으로 넘기고 옛 쪽은 nullptr로 끊어(CurrentCollection->SetNetDriver(nullptr)) — 옛 월드가 GC로 사라질 때 NetDriver까지 딸려 죽는 걸 막는 거지.

비유하면 이래. 집(월드)을 새로 지어 이사 가는데, 인터넷 회선(NetDriver)은 해지 안 하고 그대로 새 집에 옮겨 꽂는 거야. 회선 계약(연결)은 살아 있으니 인터넷이 끊긴 적이 없어. 이게 seamless의 전부야. 거창한 마법 같았는데, 알고 보면 "포인터를 옛 월드에서 새 월드로 옮기는" 딱 그거였어.

7. 클라이언트가 따라간다 — ClientTravel

서버가 전환을 시작할 때 클라들한테도 "너희도 이 맵으로 와"를 쏜다고 했지(3절). 클라의 진입점은 APlayerController::ClientTravel(PlayerController.cpp:5600)이고, 실제로 그 신호를 받아 처리하는 RPC 본체가 이거야.

PlayerController.cpp:5614

PreClientTravel(URL, TravelType, bSeamless); if (bSeamless && TravelType == TRAVEL_Relative) { World->SeamlessTravel(URL); } else {

여기 조건문이 2절에서 예고한 규칙의 실체야.

if (bSeamless && TravelType == TRAVEL_Relative)

seamless이면서 && 이동 타입이 Relative일 때만 클라도 World->SeamlessTravel(URL)로 매끄럽게 따라가. 왜 Relative만? Relative는 "지금 붙어 있는 서버 기준 상대 이동"이라 연결 상대(서버)가 그대로거든. 그러니 연결을 살려둘 수 있어. 반대로 Absolute면 서버 주소 자체가 바뀔 수 있어서 연결을 살릴 근거가 없어 — 그래서 else로 빠져 hard travel(GEngine->SetClientTravel)로 처리해.

정리하면 서버와 클라가 같은 seamless 춤을 짝 맞춰 추는 거야. 서버는 SeamlessTravel로 자기 월드를 갈고, 각 클라도 ClientTravel 신호를 받아 자기 쪽 SeamlessTravel로 월드를 갈아. 양쪽 다 NetDriver는 안 끊고. 그래서 전환이 끝나면 아무 일 없었다는 듯 같은 연결 위에서 새 맵을 함께 보고 있어.

우리 서버랑 비교 — IOCP + 싱글스레드 액터 관점

UE의 seamless travel은 단일 프로세스가 자기 안의 월드를 통째로 갈아끼우는 메커니즘이야. 우리 조선협객전 구조랑 대놓고 대응시켜보면 감이 확 와.

연결 유지 트릭 — 우리한텐 애초에 필요 없다: 우리 서버는 Gate가 클라 연결(IOCP 소켓)을 물고 있고, 뒤의 Game 서버들이 존/맵을 나눠 맡아. 유저가 다른 맵으로 워프하면 우리는 연결을 옮기는 게 아니라 워프 패킷으로 좌표·존만 바꿔 내려줘. 애초에 클라↔Gate 소켓은 그대로고 "월드 전체를 파괴"하는 개념이 없거든. 그러니 UE가 "NetDriver를 이식해서 연결을 살린다"고 애쓰는 부분이, 우리 아키텍처엔 처음부터 그 문제가 안 생기는 구조인 거야. UE는 "월드 = 프로세스 안의 것"이라 갈아끼울 때 연결이 딸려 죽을 위험이 있어서 저 이식 트릭이 필요한 거고, 우린 연결(Gate)과 월드(Game)를 프로세스로 이미 쪼개놨으니 그 위험 자체가 없어.

전환을 프레임마다 굴리는 것 — 우리 싱글스레드 틱이랑 똑같다: FSeamlessTravelHandler::Tick이 "로드 다 됐나?" 매 프레임 확인하며 조금씩 진행시키는 방식, 이거 우리 Game 서버 싱글스레드 액터 루프랑 통해. 우리도 무거운 작업(DB 로드 등)은 비동기로 던지고 메인 루프가 "완료 신호 왔나"를 폴링하듯 확인하잖아. 한 틱에 다 끝내려 하지 않고 상태 플래그(bTransitionInProgress)로 진행 단계를 들고 프레임마다 한 걸음씩 나아가는 게 핵심이야. IOCP 워커가 소켓 I/O를 백그라운드로 처리하고 게임 로직 스레드가 그 결과를 받아 처리하는 우리 분업이랑 똑같은 철학 — 무거운 건 비동기, 진행 판정은 틱에서.

폴백 방어 — 48h 규칙: TimeSeconds < 172800.0f로 오래 뜬 서버는 seamless를 포기하고 안전한 hard로 떨어뜨리는 코드(3절), 우리 서버 장기 가동 중 float/카운터 오버플로 조심하는 감각이랑 정확히 겹쳐. "매끄러움보다 안 터지는 게 우선"이라는 판단은 라이브 운영해봤으면 뼈저리게 아는 거지.

마무리 — 어디로 이어지나

이 챕터는 "연결을 살린 채 월드를 갈아끼우는 뼈대"까지만. 트랜지션 맵의 실제 GC 타이밍, 액터 목록 직렬화 세부, seamless 중 재접속 처리 같은 건 뼈대 밖이라 여기선 안 파.

  • 막히면(NetConnection·NetDriver가 애초에 뭔지) → netconnection-overview
  • 막히면(연결이 처음 어떻게 수립되는지 — seamless가 이걸 "안 다시 하는" 거야) → handshake
  • 막히면(NetDriver가 소켓 위에 어떻게 얹히는지) → ipnetdriver-socket
  • 다음(연결이 태어나서 죽기까지 전체 생애 — travel은 그 중간의 한 사건) → connection-lifecycle
  • 다음(NetDriver가 매 틱 무슨 일을 하는지 — Tick 기반 진행의 큰 그림) → netdriver-tick

🎯 원리 한 줄 요약

Seamless travel은 "옛 월드에서 NetDriver를 꺼내(CurrentWorld->GetNetDriver()) 새 월드에 그대로 붙이는(LoadedWorld->SetNetDriver(NetDriver), World.cpp:8404)" 딱 그 한 수로 연결을 안 끊고 맵만 갈아끼우며, 서버(ServerTravel)가 방아쇠를 당기고 클라(ClientTravel)가 Relative일 때만 짝 맞춰 따라가는 서버 권위 이동이다 — 회선은 그대로 두고 집만 새로 짓는 이사다.
