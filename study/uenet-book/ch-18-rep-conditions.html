조건부 복제 (COND_)

앞장 changelist까지는 "어떤 프로퍼티가 바뀌었나"를 골라냈어. 이번 장은 그 위에 필터 하나가 더 얹혀. "바뀐 건 맞는데, 이 커넥션한테도 보내야 하나?" 그게 COND_ 조건부 복제야.

1. 먼저 그림부터 — 우편함 앞의 문지기

네가 게임 서버를 짜봤으니 이 상황은 익숙할 거야. 한 액터(예: 플레이어 캐릭터)의 값이 바뀌었어. 체력, 소지금, 어떤 내부 쿨타임 같은 것들.

근데 이걸 접속 중인 모든 클라한테 똑같이 다 뿌리면 안 돼.

  • 내 소지금은 나한테만 보내야지, 옆 사람한테 내 지갑을 보여줄 순 없잖아. → COND_OwnerOnly
  • 반대로 "이 캐릭터가 지금 피격 애니 재생 중" 같은 건 나 빼고 남들한테 보내야 자연스럽고, 정작 나는 내가 클릭했으니 이미 알아. → COND_SkipOwner

즉 프로퍼티마다 "누구한테 갈지"를 미리 정해두고, 실제 보낼 때 커넥션별로 걸러내는 거야. 이 문지기 로직을 실제로 구현한 게 RepLayout.cpp / RepLayout.h의 조건부 복제 파트야.

한 줄 예측 게임 먼저 하자. UE가 이걸 어떻게 구현했을 것 같아? "프로퍼티 값을 보낼 때마다 if (COND_OwnerOnly && !소유자) continue; 하나씩 검사한다" — 이렇게 상상했지?

땡. 반전이 있어. UE는 매번 if문을 돌리지 않아. 대신 커넥션마다 "통과표(bool 테이블)"를 한 번 만들어두고, 조건 검사는 그 표를 인덱싱해서 끝내. 검사가 아니라 테이블 룩업이야. 왜 그렇게 했는지는 뒤에서 밝혀질 거야.

2. 등장인물 4명 (여기만 이해하면 끝)

낯선 타입 이름이 4개 나와. 딱 이것만 잡고 가면 콜체인이 술술 읽혀.

  • ELifetimeCondition / COND_ — 프로퍼티를 "누구에게" 보낼지 정한 조건 딱지.

등록은 매크로 한 줄: DOREPLIFETIME_CONDITION(클래스, 변수, COND_OwnerOnly). 종류: COND_OwnerOnly(소유 클라만), COND_SkipOwner(소유자 빼고), COND_SimulatedOnly, COND_Never(아예 복제 안 함) 등.

  • FReplicationFlags (RepFlags) — "지금 이 프로퍼티를 어느 커넥션 관점에서 보내는 중이냐"를 나타내는 상황 비트.

bNetOwner(이 커넥션이 이 액터 주인?), bNetInitial(첫 전송?), bNetSimulated, bReplay... → COND_(딱지) 와 RepFlags(지금 상황) 를 맞춰봐서 통과/차단을 정한다. 이게 핵심 매칭이야.

  • ConditionMap (TStaticBitArray<COND_Max>) — "이 커넥션에서 각 COND_는 통과인가?"를 담은 bool 표.

방금 말한 "통과표"가 이거야. RepFlags 하나로 딱 한 번 만들어.

  • InactiveParents (TBitArray) — 조건에 걸려서 "이번엔 안 보낼" 최상위 프로퍼티(Parent)를 표시한 비트배열.

조건 필터의 결과물이자, changelist에서 핸들을 빼낼 때의 입력.

헷갈리면 이렇게 외워: COND_ = 딱지 / RepFlags = 지금 상황 / ConditionMap = 통과표 / InactiveParents = 오늘 못 나가는 명단.

changelist가 뭔지 가물가물하면 → changelist 먼저 보고 와. 여기선 "이번 프레임에 값 바뀐 프로퍼티 핸들 목록"이라고만 알면 돼.

3. 4단 파이프라인 — 큰 그림

조건부 복제는 정확히 4단계야. 이 골격만 잡으면 나머지는 살이야.

 [A] 등록          [B] 통과표            [C] 못 나갈 명단        [D] 실제 필터링
 (클래스당 1회)    (커넥션별, RepFlags   (조건 불통과 → 비트     (changelist에서
                    바뀔 때만)            마킹)                   핸들 제거)

 COND_딱지    →    ConditionMap    →    InactiveParents    →    보낼 목록에서 빠짐
 Parent에 저장     (bool 테이블)        (TBitArray)             (이 커넥션엔 안 감)

한 문장 요약: 등록해서 딱지를 붙여두고 → 커넥션 상황(RepFlags)으로 통과표를 만들고 → 통과 못 한 애들을 명단에 올리고 → 최종 전송 목록에서 빼버린다.

이제 각 단계를 실제 코드로 보자.

4. [A단계] 등록 — 딱지를 Parent에 영구 저장

서버가 시작할 때, 클래스당 딱 한 번. 유저가 DOREPLIFETIME_CONDITION으로 등록한 프로퍼티+조건 목록을 걷어서 RepLayout에 심어.

RepLayout.cpp:6296-6305 (verbatim)

		// Don't bother doing any setup work for COND_Never properties.
		// These are never expected to replicate.
		if (COND_Never == LifetimeProp.Condition)
		{
			continue;
		}

		// Store the condition on the parent in case we need it
		RepParentCmd.Condition = LifetimeProp.Condition;
		RepParentCmd.RepNotifyCondition = LifetimeProp.RepNotifyCondition;

읽는 법:

  • COND_Never면 아예 continue — 절대 복제 안 될 애라 셋업조차 안 함. 가장 싼 조건은 처음부터 배제.
  • 나머지는 RepParentCmd.Condition에 딱지를 저장. 이게 이후 모든 필터 판정의 원천이 돼. 한 번 심어두면 커넥션마다 계속 참조해.

즉 여기까지가 "정적" 단계야. 조건은 이 시점에 확정돼 Parent에 박힌다.

5. [B단계] 통과표 만들기 — 핵심 중의 핵심

여기가 이 장의 심장이야. 아까 예측을 뒤집었던 그 "테이블".

먼저 RepFlags(지금 커넥션 상황)를 판정 불리언 5개로 풀어.

RepLayout.h:140-144 (verbatim)

		const bool bIsInitial = RepFlags.bNetInitial ? true : false;
		const bool bIsOwner = RepFlags.bNetOwner ? true : false;
		const bool bIsSimulated = RepFlags.bNetSimulated ? true : false;
		const bool bIsPhysics = RepFlags.bRepPhysics ? true : false;
		const bool bIsReplay = RepFlags.bReplay ? true : false;

이 5개 불리언(주인이냐 / 첫전송이냐 / 시뮬레이트냐 / 물리냐 / 리플레이냐)만으로 모든 COND_의 통과 여부를 계산해.

RepLayout.h:146-167 (verbatim)

		ConditionMap[COND_None] = true;
		ConditionMap[COND_InitialOnly] = bIsInitial;

		ConditionMap[COND_OwnerOnly] = bIsOwner;
		ConditionMap[COND_SkipOwner] = !bIsOwner;

		ConditionMap[COND_SimulatedOnly] = bIsSimulated;
		ConditionMap[COND_SimulatedOnlyNoReplay] = bIsSimulated && !bIsReplay;
		ConditionMap[COND_AutonomousOnly] = !bIsSimulated;

		ConditionMap[COND_SimulatedOrPhysics] = bIsSimulated || bIsPhysics;
		ConditionMap[COND_SimulatedOrPhysicsNoReplay] = (bIsSimulated || bIsPhysics) && !bIsReplay;

		ConditionMap[COND_InitialOrOwner] = bIsInitial || bIsOwner;
		ConditionMap[COND_ReplayOrOwner] = bIsReplay || bIsOwner;
		ConditionMap[COND_ReplayOnly] = bIsReplay;
		ConditionMap[COND_SkipReplay] = !bIsReplay;

		ConditionMap[COND_Custom] = true;
		ConditionMap[COND_Dynamic] = true;
		ConditionMap[COND_Never] = false;

이거 딱 두 줄만 눈으로 따라가 봐. 나머지는 전부 같은 패턴이야.

		ConditionMap[COND_OwnerOnly] = bIsOwner;
		ConditionMap[COND_SkipOwner] = !bIsOwner;
  • 이 커넥션이 주인이면(bIsOwner==true) → COND_OwnerOnly는 통과(true), COND_SkipOwner는 차단(false).
  • 이 커넥션이 남이면(bIsOwner==false) → 정확히 반대. OwnerOnly 차단, SkipOwner 통과.

봤지? OwnerOnly와 SkipOwner는 그냥 서로 ! 하나 차이야. 도입부에서 "소지금은 나한테만 / 피격모션은 남들한테만" 했던 게 이 두 줄로 그대로 코드가 됐어.

여기서 아까 예측 반전의 정체가 드러나. 왜 if문을 안 돌리고 테이블을 만들까? → 한 커넥션한테 프로퍼티를 보낼 땐 수백 개를 연달아 판정해. 그때마다 5개 불리언 조합을 다시 계산하면 낭비잖아. 그래서 커넥션 상황(RepFlags)이 바뀔 때 딱 한 번 이 표를 만들어두고, 프로퍼티마다는 ConditionMap[Condition] 인덱싱 한 방으로 끝내. 계산을 앞으로 당겨서 한 번에 몰아친 거야. 게임 서버에서 매 틱 반복 계산을 캐싱으로 빼는 거랑 완전히 같은 최적화 감각이야.

그리고 재밌는 구석:

  • COND_None, COND_Custom, COND_Dynamic은 항상 true. → 이 표에선 무조건 통과. Custom/Dynamic의 실제 on/off는 이 표가 아니라 별도 트래커(PropertyConditions)가 담당해. 이 표는 "일단 통과시키고 나중에 딴 데서 거른다"는 뜻.
  • COND_Never는 항상 false. 절대 안 나감.

6. [B단계 이어서] 통과표 → 못 나갈 명단(InactiveParents)

표를 만들었으면, 그걸로 "오늘 못 나가는 명단"을 채워. 이게 RebuildConditionalProperties야.

RepLayout.cpp:7231-7251 (verbatim)

	TStaticBitArray<COND_Max> ConditionMap = UE::Net::BuildConditionMapFromRepFlags(RepFlags);
	if (EnumHasAnyFlags(Flags, ERepLayoutFlags::HasDynamicConditionProperties) && RepState->RepChangedPropertyTracker.IsValid())
	{
		const FRepChangedPropertyTracker* RepChangedPropertyTracker = RepState->RepChangedPropertyTracker.Get();
		for (auto It = TBitArray<>::FIterator(RepState->InactiveParents); It; ++It)
		{
			ELifetimeCondition Condition = Parents[It.GetIndex()].Condition;
			if (Condition == COND_Dynamic)
			{
				Condition = RepChangedPropertyTracker->GetDynamicCondition(It.GetIndex());
			}
			It.GetValue() = !ConditionMap[Condition];
		}
	}
	else
	{
		for (auto It = TBitArray<>::FIterator(RepState->InactiveParents); It; ++It)
		{
			It.GetValue() = !ConditionMap[Parents[It.GetIndex()].Condition];
		}
	}

else 블록(일반 경로)만 보면 핵심 한 줄이야.

			It.GetValue() = !ConditionMap[Parents[It.GetIndex()].Condition];
  • Parents[...].Condition — A단계에서 심어둔 그 딱지.
  • ConditionMap[딱지] — 이 커넥션에서 통과냐? (true면 보냄)
  • 앞에 ! — 뒤집어서 InactiveParents 비트에 넣어.

왜 뒤집냐? 이 배열 이름이 InactiveParents(비활성 명단)라서 그래. "통과(active)"의 반대를 담는 배열이니까 !를 씌워서 "불통과 = 못 나감 = true"로 저장하는 거야. 통과표에서 false였던 애가 여기선 true(명단 등록)가 돼.

위쪽 if 블록은 COND_Dynamic 예외 처리야. Dynamic은 런타임에 조건이 바뀔 수 있어서, 통과표를 보기 전에 GetDynamicCondition()으로 지금 진짜 조건을 다시 물어봐서 그걸로 판정해. (원리만 알면 충분 — 세부는 넘어가도 돼.)

7. [C·D단계] 명단대로 실제 전송 목록에서 빼기

이제 명단이 완성됐어. 마지막은 간단해. changelist(바뀐 핸들 목록)를 훑으면서 명단에 오른 Parent의 핸들은 빼버리면 끝.

RepLayout.cpp:2670-2676 (FilterChangeListToActive, verbatim)

	while (HandleIterator.NextHandle())
	{
		const FRepLayoutCmd& Cmd = Cmds[HandleIterator.CmdIndex];
		if (!InactiveParents[Cmd.ParentIndex])
		{
			OutProperties.Add(HandleIterator.Handle);

if (!InactiveParents[Cmd.ParentIndex]) — 명단에 없을 때만(!inactive = active) OutProperties에 추가. 명단에 오른 애는 이 조건에서 걸러져서 최종 전송 목록에 안 담겨. 그럼 그 프로퍼티는 이 커넥션엔 안 나가. 그게 조건부 복제의 실제 "차단" 동작이야.

(값을 활성/비활성 두 버킷으로 나누는 앞단은 RepLayout.cpp:2635 — InactiveParents[Cmd.ParentIndex] ? OutInactiveProperties : OutActiveProperties. 같은 비트배열을 삼항으로 분기할 뿐, 원리는 위와 똑같아.)

여기서 꼭 짚을 것: 필터링은 "값"이 아니라 "핸들 목록"에서 일어나. 값 자체를 지우거나 0으로 만드는 게 아니라, "이번에 보낼 핸들 리스트"에서 그 핸들을 골라 빼는 방식이야. 값은 그대로 있고, 그냥 이 커넥션 앞에선 목록에서 생략되는 것뿐.

8. 언제 다시 만드나 — 트리거

통과표를 매 프레임 새로 만들면 아깝잖아. UE는 RepFlags가 바뀔 때만 다시 만들어.

RepLayout.cpp:1997-2006 (verbatim)

	// Rebuild conditional state if needed
	if (RepState->RepFlags.Value != RepFlags.Value)
	{
		RebuildConditionalProperties(RepState, RepFlags);

		// Filter out any previously inactive changes from still inactive ones
		TArray<uint16> InactiveChangelist = MoveTemp(RepState->InactiveChangelist);
		TArray<uint16> NewInactiveChangeList;

		FilterChangeList(InactiveChangelist, RepState->InactiveParents, NewInactiveChangeList, NewlyActiveChangelist);

if (RepState->RepFlags.Value != RepFlags.Value) — 저장해둔 이전 RepFlags랑 지금 RepFlags를 통째로(.Value) 비교. 다를 때만 통과표를 재구성(RebuildConditionalProperties)해. 커넥션 상황이 안 바뀌면 지난번 명단을 그대로 재활용. 앞에서 말한 "계산 몰아치기"가 이 가드로 완성되는 거야.

9. 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

조선 서버로 번역하면 이해가 확 붙어.

우리 서버는 어떤 상태가 바뀌면 그걸 누구한테 보낼지를 핸들러 코드 안에서 직접 정하잖아. 예: 소지금 변경 → 해당 유저 소켓에만 SP_MONEY 송신. 주변 시야 유저한텐 다른 패킷. 이 "누구에게"를 매번 손으로 분기해서 IOCP 워커가 그 커넥션 큐에 밀어넣지.

UE는 이걸 데이터로 선언해버린 거야.

  • 우리 if (대상 == 소유자) Send(...) 손분기 ↔ UE COND_OwnerOnly 딱지 (A단계 등록).
  • 우리는 유저별로 그때그때 판단 ↔ UE는 커넥션별 통과표를 캐싱(B단계)해서 프로퍼티마다는 룩업만.
  • 우리 IOCP 워커 = 커넥션마다 병렬. UE 서버 복제 루프 = 사실상 커넥션을 순회하며 RepFlags를 갈아끼움 → 그래서 "RepFlags 바뀔 때만 재구성"이 자연스러운 최적화가 됨(트리거 8절).

한 줄로: 우리는 "누구에게"를 코드로 매번 짠다. UE는 "누구에게"를 프로퍼티에 딱지로 붙여두고, 커넥션 상황표랑 대조해서 자동으로 걸러낸다. 손분기를 선언형 + 테이블 룩업으로 바꾼 거야.

11. 막히면 / 다음

  • changelist가 뭔지 흐릿하면 → changelist
  • Parent/Cmd, RepLayout 자체 구조가 낯설면 → replayout
  • 어떤 프로퍼티를 복제 대상으로 "등록"하는지(DOREPLIFETIME 계열)가 궁금하면 → lifetime-props
  • 조건과 짝인 RepNotify(값 바뀌면 콜백) 흐름은 → repnotify
  • 이 필터를 "매 프레임 changelist 계산"에서 "바뀔 때만 알림"으로 뒤집는 최적화가 궁금하면 → push-model
  • COND_보다 더 큰 단위(액터 통째로 이 커넥션에 보낼지)는 → relevancy

🎯 원리 한 줄 요약

프로퍼티엔 "누구에게" 딱지(COND_)를 미리 박아두고, 커넥션 상황(RepFlags)으로 만든 통과표(ConditionMap)와 대조해 불통과분을 명단(InactiveParents)에 올린 뒤, 전송 changelist에서 그 핸들만 빼버린다 — 검사(if)가 아니라 테이블 룩업이 조건부 복제의 정체다.
