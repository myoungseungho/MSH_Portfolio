조건부 복제 (COND_)

언리얼 네트워크 · 18 / 47

앞장 changelist까지는 "어떤 프로퍼티가 바뀌었나"를 골라냈어.
이번 장은 그 위에 필터 하나가 더 얹혀. "바뀐 건 맞는데, 이 커넥션한테도 보내야 하나?"
그게 COND_ 조건부 복제야.

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 "값이 바뀌었다"와 "그 값을 누구한테 보낼까"가 다른 문제라는 걸 금방 느껴봤을 거야. CChosunPlayer의 체력, 소지금, 현재 타겟, 스킬 쿨타임이 바뀌면 서버는 그걸 알고 있어야 해. IOCP 워커가 CM_* 패킷을 받아 게임 스레드로 넘기고, 단일 스레드 로직이 상태를 바꾸는 것까지는 익숙하지.

근데 바뀐 값을 그냥 SP_* 패킷으로 접속자 전원에게 뿌리면 바로 사고가 나. 내 소지금이 옆 사람 클라에 보이고, 내 입력으로 이미 아는 애니메이션이 나한테 또 오고, 100명이 보는 맵에서 사소한 내부 값까지 전부 흘러가면 대역폭도 터져. 더 무서운 건 조건 검사가 여기저기 흩어지는 거야. 패킷 핸들러마다 "이건 주인만", "이건 주인 빼고"를 따로 적기 시작하면 락 위치도 애매해지고, 한 군데 빠뜨린 버그는 찾기 어렵다.

그래서 필요한 질문은 이거야. 바뀐 프로퍼티가 맞다 해도, 지금 이 커넥션에게 보낼 자격이 있나? 우체국으로 치면 편지가 만들어진 것과 배달 주소가 맞는 것은 다른 일이야. 편지가 있다고 아무 우편함에 넣으면 안 되잖아.

언리얼도 같은 문제를 만났고, 그 답이 COND_ 조건부 복제야. 프로퍼티마다 COND_OwnerOnly, COND_SkipOwner 같은 딱지를 붙여두고, 실제 전송 순간에는 커넥션의 상황을 보고 통과시킬지 막을지 결정해. 핵심은 "무엇이 바뀌었나"가 아니라 "바뀐 것 중 이 사람에게 갈 것만 남긴다" 야.

이걸 지금 배우는 이유도 흐름상 딱 맞아. 앞장 changelist에서는 "이번 프레임에 뭐가 바뀌었나"를 골라냈어. 하지만 그 목록은 아직 전원 공용 장바구니야. 이번 장에서 그 장바구니를 커넥션별로 걸러야, 다음 전송 단계에서 진짜로 보낼 Bunch가 깨끗하게 만들어진다.

🌱 이 개념은 왜 생겼나 — COND_ 조건부 복제
• 원래 구조: 값이 바뀌면 그냥 접속자 전원한테 똑같이 뿌려. 편지 한 통 만들면 모든 우편함에 복사해 넣는 셈이야.
• 그런데 문제: 내 소지금이 옆 사람 화면에 뜨고, 내가 이미 아는 내 피격모션이 나한테 또 오고, 100명 맵에선 사소한 값까지 전부 흘러 대역폭이 터져. 게다가 "이건 주인만/이건 주인 빼고"를 패킷 핸들러마다 손으로 적으면 한 군데 빠뜨린 버그를 못 찾아.
• 그래서 필요한 것: 프로퍼티마다 "누구한테 갈지"를 미리 딱지로 붙여두고, 보낼 때 커넥션을 보고 거르는 규칙. → 그게 COND_야. COND_OwnerOnly=주인만, COND_SkipOwner=주인 빼고. 조선 서버로 치면 SP_MONEY를 손분기 없이 딱지로 선언해두는 거지.

1. 먼저 그림부터 — 우편함 앞의 문지기

네가 게임 서버를 짜봤으니 이 상황은 익숙할 거야. 한 액터(예: 플레이어 캐릭터)의 값이 바뀌었어. 체력, 소지금, 어떤 내부 쿨타임 같은 것들.

근데 이걸 접속 중인 모든 클라한테 똑같이 다 뿌리면 안 돼.

  • 내 소지금은 나한테만 보내야지, 옆 사람한테 내 지갑을 보여줄 순 없잖아. → COND_OwnerOnly
  • 반대로 "이 캐릭터가 지금 피격 애니 재생 중" 같은 건 나 빼고 남들한테 보내야 자연스럽고, 정작 나는 내가 클릭했으니 이미 알아. → COND_SkipOwner

즉 프로퍼티마다 "누구한테 갈지"를 미리 정해두고, 실제 보낼 때 커넥션별로 걸러내는 거야. 이 문지기 로직을 실제로 구현한 게 RepLayout.cpp / RepLayout.h의 조건부 복제 파트야.

한 줄 예측 게임 먼저 하자. UE가 이걸 어떻게 구현했을 것 같아? "프로퍼티 값을 보낼 때마다 if (COND_OwnerOnly && !소유자) continue; 하나씩 검사한다" — 이렇게 상상했지?

땡. 반전이 있어. UE는 매번 if문을 돌리지 않아. 대신 커넥션마다 "통과표(bool 테이블)"를 한 번 만들어두고, 조건 검사는 그 표를 인덱싱해서 끝내. 검사가 아니라 테이블 룩업이야. 왜 그렇게 했는지는 뒤에서 밝혀질 거야.

2. 등장인물 4명 (여기만 이해하면 끝)

낯선 타입 이름이 4개 나와. 딱 이것만 잡고 가면 콜체인이 술술 읽혀.

  • ELifetimeCondition / COND_ — 프로퍼티를 "누구에게" 보낼지 정한 조건 딱지.

등록은 매크로 한 줄: DOREPLIFETIME_CONDITION(클래스, 변수, COND_OwnerOnly). 종류: COND_OwnerOnly(소유 클라만), COND_SkipOwner(소유자 빼고), COND_SimulatedOnly, COND_Never(아예 복제 안 함) 등.

  • FReplicationFlags (RepFlags) — "지금 이 프로퍼티를 어느 커넥션 관점에서 보내는 중이냐"를 나타내는 상황 비트.

bNetOwner(이 커넥션이 이 액터 주인?), bNetInitial(첫 전송?), bNetSimulated, bReplay... → COND_(딱지) 와 RepFlags(지금 상황) 를 맞춰봐서 통과/차단을 정한다. 이게 핵심 매칭이야.

  • ConditionMap (TStaticBitArray<COND_Max>) — "이 커넥션에서 각 COND_는 통과인가?"를 담은 bool 표.

방금 말한 "통과표"가 이거야. RepFlags 하나로 딱 한 번 만들어.

  • InactiveParents (TBitArray) — 조건에 걸려서 "이번엔 안 보낼" 최상위 프로퍼티(Parent)를 표시한 비트배열.

조건 필터의 결과물이자, changelist에서 핸들을 빼낼 때의 입력.

헷갈리면 이렇게 외워:
COND_ = 딱지 / RepFlags = 지금 상황 / ConditionMap = 통과표 / InactiveParents = 오늘 못 나가는 명단.

changelist가 뭔지 가물가물하면 → changelist 먼저 보고 와. 여기선 "이번 프레임에 값 바뀐 프로퍼티 핸들 목록"이라고만 알면 돼.

3. 4단 파이프라인 — 큰 그림

조건부 복제는 정확히 4단계야. 이 골격만 잡으면 나머지는 살이야.

[A] 등록 [B] 통과표 [C] 못 나갈 명단 [D] 실제 필터링 (클래스당 1회) (커넥션별, RepFlags (조건 불통과 → 비트 (changelist에서 바뀔 때만) 마킹) 핸들 제거) COND_딱지 → ConditionMap → InactiveParents → 보낼 목록에서 빠짐 Parent에 저장 (bool 테이블) (TBitArray) (이 커넥션엔 안 감)

한 문장 요약: 등록해서 딱지를 붙여두고 → 커넥션 상황(RepFlags)으로 통과표를 만들고 → 통과 못 한 애들을 명단에 올리고 → 최종 전송 목록에서 빼버린다.

이제 각 단계를 실제 코드로 보자.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 풀고, 바로 이어서 "이제 다시 보자"로 한 번 더 읽어줄게. 여기서는 "딱지를 어디에 저장하고, 어떻게 표로 바꾸는가"만 따라가면 돼.

4. [A단계] 등록 — 딱지를 Parent에 영구 저장

서버가 시작할 때, 클래스당 딱 한 번. 유저가 DOREPLIFETIME_CONDITION으로 등록한 프로퍼티+조건 목록을 걷어서 RepLayout에 심어.

RepLayout.cpp:6296-6305 (verbatim)

// Don't bother doing any setup work for COND_Never properties. // These are never expected to replicate. if (COND_Never == LifetimeProp.Condition) { continue; } // Store the condition on the parent in case we need it RepParentCmd.Condition = LifetimeProp.Condition; RepParentCmd.RepNotifyCondition = LifetimeProp.RepNotifyCondition;
🔤 기호 사전 — if (COND_Never == LifetimeProp.Condition) ... RepParentCmd.Condition = LifetimeProp.Condition;
• // = 컴퓨터가 읽는 명령이 아니라, 사람이 보라고 적어둔 메모야.
• if (...) = "괄호 안 조건이 맞으면 안쪽 일을 해라"는 문지기.
• COND_Never = "절대 보내지 마" 딱지. 복제 조건 중 가장 강한 차단표야.
• == = "왼쪽과 오른쪽이 같은가?"를 물어보는 비교.
• . = 상자 안의 칸을 꺼내는 표시. LifetimeProp.Condition은 LifetimeProp 안의 Condition 칸.
• continue = 지금 반복의 나머지는 건너뛰고, 다음 항목으로 넘어가라는 뜻.
• = = 오른쪽 값을 왼쪽 칸에 넣기. RepParentCmd.Condition 칸에 조건 딱지를 저장해.
• RepNotifyCondition = 값이 바뀌었을 때 알림 콜백을 부를 조건. 지금은 "복제 조건 옆에 같이 저장되는 알림 딱지" 정도로 보면 돼.
🔁 이제 다시 보자. if (COND_Never == LifetimeProp.Condition)은 "절대 안 보낼 애면"이고, 안쪽 continue는 "셋업하지 말고 다음으로"야. 그 아래 RepParentCmd.Condition = LifetimeProp.Condition은 "나머지 애들은 Parent 칸에 조건 딱지를 박아둔다"로 읽으면 돼. 즉 이 블록은 안 보낼 애는 처음부터 빼고, 보낼 가능성이 있는 애만 조건표에 저장하는 입구야.

읽는 법:

  • COND_Never면 아예 continue — 절대 복제 안 될 애라 셋업조차 안 함. 가장 싼 조건은 처음부터 배제.
  • 나머지는 RepParentCmd.Condition에 딱지를 저장. 이게 이후 모든 필터 판정의 원천이 돼. 한 번 심어두면 커넥션마다 계속 참조해.

즉 여기까지가 "정적" 단계야. 조건은 이 시점에 확정돼 Parent에 박힌다.

🌱 이 개념은 왜 생겼나 — 통과표(ConditionMap)
• 원래 구조: 프로퍼티 하나 보낼 때마다 if (OwnerOnly && !주인) 막기처럼 즉석에서 조건을 검사하면 될 것 같아.
• 그런데 문제: 한 커넥션한테 프로퍼티 수백 개를 연달아 보내는데, 그때마다 "주인이냐/첫전송이냐/시뮬이냐" 다섯 개를 다시 계산하면 같은 답을 수백 번 다시 구하는 헛일이야.
• 그래서 필요한 것: 커넥션 상황(RepFlags)이 정해지면 딱 한 번 표를 만들어두고, 프로퍼티마다는 표[딱지] 룩업 한 방으로 끝내기. → 그게 ConditionMap이야. 조선 서버에서 매 틱 반복 계산을 캐싱으로 빼는 감각 그대로.

5. [B단계] 통과표 만들기 — 핵심 중의 핵심

여기가 이 장의 심장이야. 아까 예측을 뒤집었던 그 "테이블".

먼저 RepFlags(지금 커넥션 상황)를 판정 불리언 5개로 풀어.

RepLayout.h:140-144 (verbatim)

const bool bIsInitial = RepFlags.bNetInitial ? true : false; const bool bIsOwner = RepFlags.bNetOwner ? true : false; const bool bIsSimulated = RepFlags.bNetSimulated ? true : false; const bool bIsPhysics = RepFlags.bRepPhysics ? true : false; const bool bIsReplay = RepFlags.bReplay ? true : false;
🔤 기호 사전 — const bool bIsOwner = RepFlags.bNetOwner ? true : false;
• const = 이 줄에서 정한 뒤에는 값을 바꾸지 않겠다는 약속.
• bool = 참/거짓만 담는 작은 스위치. 켜짐(true) 또는 꺼짐(false).
• bIsOwner = b로 시작하니까 보통 bool 변수야. "주인인가?"라는 예/아니오 칸.
• RepFlags.bNetOwner = RepFlags라는 상황표 안의 bNetOwner 칸. "이 커넥션이 주인인가?"를 들고 있어.
• ? true : false = 삼항 연산자. 앞 조건이 참이면 true, 아니면 false를 고르라는 짧은 if문.
• ; = 이 한 줄 명령은 여기서 끝났다는 마침표.
🔁 이제 다시 보자. const bool bIsOwner = RepFlags.bNetOwner ? true : false;는 "RepFlags에서 주인 여부를 꺼내서, 앞으로 안 바꿀 참/거짓 값 bIsOwner로 정리한다"야. 위 다섯 줄은 전부 같은 방식으로 커넥션 상황표를 읽기 쉬운 스위치 5개로 풀어놓는 준비 단계라고 보면 돼.

이 5개 불리언(주인이냐 / 첫전송이냐 / 시뮬레이트냐 / 물리냐 / 리플레이냐)만으로 모든 COND_의 통과 여부를 계산해.

RepLayout.h:146-167 (verbatim)

ConditionMap[COND_None] = true; ConditionMap[COND_InitialOnly] = bIsInitial; ConditionMap[COND_OwnerOnly] = bIsOwner; ConditionMap[COND_SkipOwner] = !bIsOwner; ConditionMap[COND_SimulatedOnly] = bIsSimulated; ConditionMap[COND_SimulatedOnlyNoReplay] = bIsSimulated && !bIsReplay; ConditionMap[COND_AutonomousOnly] = !bIsSimulated; ConditionMap[COND_SimulatedOrPhysics] = bIsSimulated || bIsPhysics; ConditionMap[COND_SimulatedOrPhysicsNoReplay] = (bIsSimulated || bIsPhysics) && !bIsReplay; ConditionMap[COND_InitialOrOwner] = bIsInitial || bIsOwner; ConditionMap[COND_ReplayOrOwner] = bIsReplay || bIsOwner; ConditionMap[COND_ReplayOnly] = bIsReplay; ConditionMap[COND_SkipReplay] = !bIsReplay; ConditionMap[COND_Custom] = true; ConditionMap[COND_Dynamic] = true; ConditionMap[COND_Never] = false;
🔤 기호 사전 — ConditionMap[COND_SkipOwner] = !bIsOwner;
• ConditionMap[...] = 통과표에서 특정 칸 하나를 고르는 것. 대괄호 안의 COND_가 칸 번호야.
• COND_None = 조건 없음. 누구에게나 통과.
• !bIsOwner = bIsOwner를 뒤집기. 주인이면 false, 주인이 아니면 true.
• && = "그리고". 양쪽이 둘 다 true일 때만 true.
• || = "또는". 양쪽 중 하나라도 true면 true.
• ( ... ) = 먼저 묶어서 계산하라는 괄호. 산수에서 괄호 먼저 하는 것과 같아.
• COND_Custom / COND_Dynamic = 여기선 일단 true로 통과시키고, 나중에 다른 추적기가 한 번 더 거르는 특별 딱지.
• COND_Never = 여기서는 false. 통과표에서도 "절대 통과 못 함"으로 찍혀.
🔁 이제 다시 보자. ConditionMap[COND_OwnerOnly] = bIsOwner는 "주인이면 OwnerOnly 통과", ConditionMap[COND_SkipOwner] = !bIsOwner는 "주인이 아니면 SkipOwner 통과"야. &&, ||가 붙은 줄들은 조건을 두세 개 섞는 것뿐이고, 마지막 COND_Never = false는 "이 딱지는 무조건 막힘"이야. 결국 이 블록은 각 COND_ 딱지마다 오늘 이 커넥션에서 통과인지 아닌지를 미리 표에 적는 코드야.

이거 딱 두 줄만 눈으로 따라가 봐. 나머지는 전부 같은 패턴이야.

ConditionMap[COND_OwnerOnly] = bIsOwner; ConditionMap[COND_SkipOwner] = !bIsOwner;
  • 이 커넥션이 주인이면(bIsOwner==true) → COND_OwnerOnly는 통과(true), COND_SkipOwner는 차단(false).
  • 이 커넥션이 남이면(bIsOwner==false) → 정확히 반대. OwnerOnly 차단, SkipOwner 통과.

봤지? OwnerOnly와 SkipOwner는 그냥 서로 ! 하나 차이야. 도입부에서 "소지금은 나한테만 / 피격모션은 남들한테만" 했던 게 이 두 줄로 그대로 코드가 됐어.

여기서 아까 예측 반전의 정체가 드러나. 왜 if문을 안 돌리고 테이블을 만들까? → 한 커넥션한테 프로퍼티를 보낼 땐 수백 개를 연달아 판정해. 그때마다 5개 불리언 조합을 다시 계산하면 낭비잖아. 그래서 커넥션 상황(RepFlags)이 바뀔 때 딱 한 번 이 표를 만들어두고, 프로퍼티마다는 ConditionMap[Condition] 인덱싱 한 방으로 끝내. 계산을 앞으로 당겨서 한 번에 몰아친 거야. 게임 서버에서 매 틱 반복 계산을 캐싱으로 빼는 거랑 완전히 같은 최적화 감각이야.

그리고 재밌는 구석:

  • COND_None, COND_Custom, COND_Dynamic은 항상 true. → 이 표에선 무조건 통과. Custom/Dynamic의 실제 on/off는 이 표가 아니라 별도 트래커(PropertyConditions)가 담당해. 이 표는 "일단 통과시키고 나중에 딴 데서 거른다"는 뜻.
  • COND_Never는 항상 false. 절대 안 나감.
🌱 이 개념은 왜 생겼나 — 못 나갈 명단(InactiveParents)
• 원래 구조: 통과표가 있으니, 실제로 보낼 때 바뀐 핸들마다 표[딱지]를 그때그때 물어보면 되잖아.
• 그런데 문제: 바뀐 핸들이 많으면 매 핸들마다 딱지 꺼내고 표 뒤지고를 반복해. 게다가 changelist를 걸러내는 코드가 여러 군데라, 각자 또 "이거 통과야?"를 따로 물어봐야 해.
• 그래서 필요한 것: 통과 못 한 Parent만 미리 비트 하나로 굳혀둔 명단. → 그게 InactiveParents야. 이름 그대로 "오늘 못 나가는 명단" — 전송할 땐 명단만 보고 !로 뒤집어 빼면 끝.

6. [B단계 이어서] 통과표 → 못 나갈 명단(InactiveParents)

표를 만들었으면, 그걸로 "오늘 못 나가는 명단"을 채워. 이게 RebuildConditionalProperties야.

RepLayout.cpp:7231-7251 (verbatim)

TStaticBitArray<COND_Max> ConditionMap = UE::Net::BuildConditionMapFromRepFlags(RepFlags); if (EnumHasAnyFlags(Flags, ERepLayoutFlags::HasDynamicConditionProperties) && RepState->RepChangedPropertyTracker.IsValid()) { const FRepChangedPropertyTracker* RepChangedPropertyTracker = RepState->RepChangedPropertyTracker.Get(); for (auto It = TBitArray<>::FIterator(RepState->InactiveParents); It; ++It) { ELifetimeCondition Condition = Parents[It.GetIndex()].Condition; if (Condition == COND_Dynamic) { Condition = RepChangedPropertyTracker->GetDynamicCondition(It.GetIndex()); } It.GetValue() = !ConditionMap[Condition]; } } else { for (auto It = TBitArray<>::FIterator(RepState->InactiveParents); It; ++It) { It.GetValue() = !ConditionMap[Parents[It.GetIndex()].Condition]; } }
🔤 기호 사전 — It.GetValue() = !ConditionMap[Parents[It.GetIndex()].Condition];
• TStaticBitArray<COND_Max> = 크기가 정해진 bool 표. COND_Max만큼 칸을 만들어서 각 COND_의 통과 여부를 담아.
• UE::Net::BuildConditionMapFromRepFlags(...) = UE 안의 Net 영역에 있는 함수 호출. ::는 "~안에 있는"이라고 읽으면 돼.
• && = 둘 다 참이어야 통과. "동적 조건이 있고, 트래커도 유효하면"이라는 두 문을 모두 통과해야 해.
• RepState->... = RepState가 가리키는 상자 안으로 들어가서 값을 꺼내는 화살표.
• auto It = ... = 타입 이름이 길 때 컴파일러한테 "네가 알아서 타입 맞춰"라고 맡기는 선언.
• ++It = 반복자를 다음 칸으로 한 칸 이동.
• It.GetIndex() = 지금 반복자가 가리키는 Parent 번호를 꺼내기.
• Condition == COND_Dynamic = 조건 딱지가 동적인지 비교.
• It.GetValue() = ... = 지금 칸의 값을 새로 써넣기. 여기서는 InactiveParents의 현재 비트를 바꿔.
🔁 이제 다시 보자. 첫 줄은 RepFlags로 ConditionMap 통과표를 만들고, for 루프는 Parent 칸을 하나씩 돈다. 일반 조건이면 Parents[It.GetIndex()].Condition을 그대로 보고, Dynamic이면 GetDynamicCondition()으로 지금 조건을 다시 물어봐. 마지막 It.GetValue() = !ConditionMap[Condition]은 "통과표에서 false면 못 나감 명단에는 true로 적는다"야. 즉 이 코드는 통과표를 뒤집어서 InactiveParents 명단을 채우는 작업이야.

else 블록(일반 경로)만 보면 핵심 한 줄이야.

It.GetValue() = !ConditionMap[Parents[It.GetIndex()].Condition];
  • Parents[...].Condition — A단계에서 심어둔 그 딱지.
  • ConditionMap[딱지] — 이 커넥션에서 통과냐? (true면 보냄)
  • 앞에 ! — 뒤집어서 InactiveParents 비트에 넣어.

왜 뒤집냐? 이 배열 이름이 InactiveParents(비활성 명단)라서 그래. "통과(active)"의 반대를 담는 배열이니까 !를 씌워서 "불통과 = 못 나감 = true"로 저장하는 거야. 통과표에서 false였던 애가 여기선 true(명단 등록)가 돼.

위쪽 if 블록은 COND_Dynamic 예외 처리야. Dynamic은 런타임에 조건이 바뀔 수 있어서, 통과표를 보기 전에 GetDynamicCondition()으로 지금 진짜 조건을 다시 물어봐서 그걸로 판정해. (원리만 알면 충분 — 세부는 넘어가도 돼.)

7. [C·D단계] 명단대로 실제 전송 목록에서 빼기

이제 명단이 완성됐어. 마지막은 간단해. changelist(바뀐 핸들 목록)를 훑으면서 명단에 오른 Parent의 핸들은 빼버리면 끝.

RepLayout.cpp:2670-2676 (FilterChangeListToActive, verbatim)

while (HandleIterator.NextHandle()) { const FRepLayoutCmd& Cmd = Cmds[HandleIterator.CmdIndex]; if (!InactiveParents[Cmd.ParentIndex]) { OutProperties.Add(HandleIterator.Handle);
🔤 기호 사전 — if (!InactiveParents[Cmd.ParentIndex]) { OutProperties.Add(...) }
• while (HandleIterator.NextHandle()) = 다음 핸들이 있는 동안 계속 반복. 핸들이 떨어지면 멈춰.
• const FRepLayoutCmd& Cmd = Cmd를 읽기 전용으로, 복사하지 말고 원본 참조로 잡아두겠다는 뜻.
• Cmds[HandleIterator.CmdIndex] = Cmds 배열에서 현재 핸들이 가리키는 명령 칸을 꺼내기.
• !InactiveParents[...] = "못 나갈 명단에 없으면"이라는 뜻. !가 inactive를 active로 뒤집어 읽게 해줘.
• Cmd.ParentIndex = 이 Cmd가 어느 Parent에 속하는지 알려주는 번호.
• OutProperties.Add(...) = 최종으로 보낼 목록에 핸들을 하나 추가.
🔁 이제 다시 보자. while은 바뀐 핸들을 하나씩 훑고, Cmd는 그 핸들의 Parent 번호를 알려줘. if (!InactiveParents[Cmd.ParentIndex])는 "그 Parent가 못 나갈 명단에 없으면"이고, 그때만 OutProperties.Add(...)로 보낼 목록에 넣어. 그래서 이 블록은 값을 지우는 코드가 아니라, 보낼 핸들 목록에서 조건 탈락자를 빼는 코드야.

if (!InactiveParents[Cmd.ParentIndex]) — 명단에 없을 때만(!inactive = active) OutProperties에 추가. 명단에 오른 애는 이 조건에서 걸러져서 최종 전송 목록에 안 담겨. 그럼 그 프로퍼티는 이 커넥션엔 안 나가. 그게 조건부 복제의 실제 "차단" 동작이야.

(값을 활성/비활성 두 버킷으로 나누는 앞단은 RepLayout.cpp:2635 — InactiveParents[Cmd.ParentIndex] ? OutInactiveProperties : OutActiveProperties. 같은 비트배열을 삼항으로 분기할 뿐, 원리는 위와 똑같아.)

여기서 꼭 짚을 것: 필터링은 "값"이 아니라 "핸들 목록"에서 일어나. 값 자체를 지우거나 0으로 만드는 게 아니라, "이번에 보낼 핸들 리스트"에서 그 핸들을 골라 빼는 방식이야. 값은 그대로 있고, 그냥 이 커넥션 앞에선 목록에서 생략되는 것뿐.

8. 언제 다시 만드나 — 트리거

통과표를 매 프레임 새로 만들면 아깝잖아. UE는 RepFlags가 바뀔 때만 다시 만들어.

RepLayout.cpp:1997-2006 (verbatim)

// Rebuild conditional state if needed if (RepState->RepFlags.Value != RepFlags.Value) { RebuildConditionalProperties(RepState, RepFlags); // Filter out any previously inactive changes from still inactive ones TArray<uint16> InactiveChangelist = MoveTemp(RepState->InactiveChangelist); TArray<uint16> NewInactiveChangeList; FilterChangeList(InactiveChangelist, RepState->InactiveParents, NewInactiveChangeList, NewlyActiveChangelist);
🔤 기호 사전 — if (RepState->RepFlags.Value != RepFlags.Value) { RebuildConditionalProperties(...) }
• // = 사람용 메모. 여기선 "필요하면 조건 상태를 다시 만든다"는 안내문.
• RepState->RepFlags.Value = 저장해둔 예전 RepFlags 값을 꺼낸 것.
• != = 같지 않다. 예전 값과 지금 값이 다르면 true.
• RebuildConditionalProperties(...) = 조건표와 못 나갈 명단을 다시 만드는 함수.
• TArray<uint16> = uint16 숫자를 담는 UE식 리스트. 여기서는 핸들 번호 목록으로 보면 돼.
• MoveTemp(...) = 통째로 옮겨 담기. 복사본을 만드는 게 아니라 기존 목록을 새 변수로 넘겨서 재사용해.
• FilterChangeList(...) = changelist를 다시 걸러서 여전히 inactive인 것과 새로 active가 된 것을 나누는 함수.
🔁 이제 다시 보자. if (RepState->RepFlags.Value != RepFlags.Value)는 "커넥션 상황표가 지난번과 달라졌나?"야. 달라졌을 때만 RebuildConditionalProperties로 통과표/못 나갈 명단을 다시 만들고, 기존 inactive changelist도 FilterChangeList로 다시 분류해. 즉 이 블록은 매번 새로 계산하지 않고, 상황이 바뀐 순간에만 조건 상태를 갈아끼우는 트리거야.

if (RepState->RepFlags.Value != RepFlags.Value) — 저장해둔 이전 RepFlags랑 지금 RepFlags를 통째로(.Value) 비교. 다를 때만 통과표를 재구성(RebuildConditionalProperties)해. 커넥션 상황이 안 바뀌면 지난번 명단을 그대로 재활용. 앞에서 말한 "계산 몰아치기"가 이 가드로 완성되는 거야.

9. 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

조선 서버로 번역하면 이해가 확 붙어.

우리 서버는 어떤 상태가 바뀌면 그걸 누구한테 보낼지를 핸들러 코드 안에서 직접 정하잖아. 예: 소지금 변경 → 해당 유저 소켓에만 SP_MONEY 송신. 주변 시야 유저한텐 다른 패킷. 이 "누구에게"를 매번 손으로 분기해서 IOCP 워커가 그 커넥션 큐에 밀어넣지.

UE는 이걸 데이터로 선언해버린 거야.

  • 우리 if (대상 == 소유자) Send(...) 손분기 ↔ UE COND_OwnerOnly 딱지 (A단계 등록).
  • 우리는 유저별로 그때그때 판단 ↔ UE는 커넥션별 통과표를 캐싱(B단계)해서 프로퍼티마다는 룩업만.
  • 우리 IOCP 워커 = 커넥션마다 병렬. UE 서버 복제 루프 = 사실상 커넥션을 순회하며 RepFlags를 갈아끼움 → 그래서 "RepFlags 바뀔 때만 재구성"이 자연스러운 최적화가 됨(트리거 8절).

한 줄로: 우리는 "누구에게"를 코드로 매번 짠다. UE는 "누구에게"를 프로퍼티에 딱지로 붙여두고, 커넥션 상황표랑 대조해서 자동으로 걸러낸다. 손분기를 선언형 + 테이블 룩업으로 바꾼 거야.

Q1. 조건부 복제(COND_), 왜 필요한가요?

답 보기
"값이 바뀌었다"와 "그 값을 누구한테 보낼까"는 다른 문제거든. 내 소지금은 나한테만 보여야지 옆 사람 클라에 뜨면 안 되고, 내가 클릭해서 이미 아는 피격모션이 나한테 또 오면 낭비야. 100명 맵에서 사소한 내부 값까지 전부 흘리면 대역폭도 터져. 그래서 프로퍼티마다 "누구한테 갈지" 딱지를 붙여두는 게 COND_야. COND_OwnerOnly=주인만, COND_SkipOwner=주인 빼고.

↳ 그냥 패킷 핸들러마다 손으로 분기하면 안 되나요?

답 보기
우리 조선 서버가 그렇게 하지 — 소지금 바뀌면 해당 유저 소켓에만 SP_MONEY. 근데 "이건 주인만/이건 주인 빼고"를 핸들러마다 손으로 적기 시작하면 한 군데 빠뜨린 버그를 찾기 어려워. UE는 이 손분기를 데이터로 선언해버린 거야. 조건을 프로퍼티에 딱지로 박아두고 전송 순간에 자동으로 걸러내니까, 누락 버그가 구조적으로 줄어.

Q2. 그럼 프로퍼티 보낼 때마다 if로 조건을 검사하나요?

답 보기
그럴 것 같지? 반전이야. UE는 매번 if문을 안 돌려. 대신 커넥션마다 "통과표"(ConditionMap, bool 테이블)를 한 번 만들어두고, 프로퍼티마다는 그 표를 인덱싱해서 끝내. 검사가 아니라 테이블 룩업이야. "이 커넥션에서 각 COND_는 통과인가?"를 미리 다 계산해서 표로 굳혀놓는 거지.

↳ 왜 굳이 표를 만들죠? if가 더 단순해 보이는데요.

답 보기
한 커넥션한테 프로퍼티를 수백 개 연달아 보내거든. 그때마다 "주인이냐/첫전송이냐/시뮬이냐" 다섯 개 불리언 조합을 다시 계산하면 같은 답을 수백 번 구하는 헛일이야. 그래서 커넥션 상황(RepFlags)이 정해지면 딱 한 번 표를 만들고, 프로퍼티마다는 룩업 한 방. 게임 서버에서 매 틱 반복 계산을 캐싱으로 빼는 거랑 완전히 같은 최적화 감각이야.

↳ 그 통과표는 매 프레임 새로 만드나요?

답 보기
아니, 아까우니까. 커넥션 상황(RepFlags)이 바뀔 때만 다시 만들어. 저장해둔 이전 RepFlags랑 지금 걸 통째로 비교해서, 다를 때만 재구성하고 같으면 지난번 명단을 그대로 재활용해. "계산 몰아치기"가 이 가드로 완성되는 거야.

Q3. 통과표를 만들었으면, 실제로 어떻게 차단하나요?

답 보기
통과표를 뒤집어서 "오늘 못 나가는 명단"(InactiveParents)을 채워. 통과표에서 false였던 애가 여기선 true(명단 등록)가 돼. 그다음 changelist(바뀐 핸들 목록)를 훑으면서, 명단에 오른 Parent의 핸들은 최종 전송 목록에서 빼버려. 그럼 그 프로퍼티는 이 커넥션엔 안 나가. 4단이야 — 등록(딱지) → 통과표 → 못 나갈 명단 → 전송 목록에서 제거.

↳ 값을 지우거나 0으로 만드는 건가요?

답 보기
아니, 값은 건드리지 않아. 필터링은 "값"이 아니라 "핸들 목록"에서 일어나. 값은 그대로 있고, 그냥 이번에 보낼 핸들 리스트에서 그 핸들을 골라 빼는 것뿐이야. 그래서 같은 액터라도 커넥션마다 다른 목록이 나가는 거지.

Q4. 이 필터는 앞 챕터의 changelist랑 어떻게 맞물리나요?

답 보기
changelist는 "이번 프레임에 뭐가 바뀌었나"를 골라낸 전원 공용 장바구니야. 근데 그 목록을 그대로 다 보내면 안 되지. 조건부 복제가 그 장바구니를 커넥션별로 한 번 더 걸러. "바뀐 것 중 이 사람에게 갈 것만 남긴다"가 핵심이야. 그래야 다음 전송 단계에서 진짜 보낼 Bunch가 깨끗하게 만들어져. 즉 changelist 위에 필터 한 겹이 더 얹히는 구조.

↳ COND_Custom이나 COND_Dynamic은 통과표에서 항상 true던데, 그럼 안 걸러지나요?

답 보기
이 표에선 일단 통과시켜. 근데 실제 on/off는 이 표가 아니라 별도 트래커(PropertyConditions)가 담당해. "일단 통과시키고 나중에 딴 데서 거른다"는 뜻이야. 특히 Dynamic은 런타임에 조건이 바뀔 수 있어서, 명단 채울 때 GetDynamicCondition()으로 지금 진짜 조건을 다시 물어봐서 판정해. 반대로 COND_Never는 통과표에서 항상 false — 셋업조차 안 하고 처음부터 배제하는 가장 싼 조건이지.

🎯 원리 한 줄 요약

프로퍼티엔 "누구에게" 딱지(COND_)를 미리 박아두고, 커넥션 상황(RepFlags)으로 만든 통과표(ConditionMap)와 대조해 불통과분을 명단(InactiveParents)에 올린 뒤, 전송 changelist에서 그 핸들만 빼버린다 — 검사(if)가 아니라 테이블 룩업이 조건부 복제의 정체다.
