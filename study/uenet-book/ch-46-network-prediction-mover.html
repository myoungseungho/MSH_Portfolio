Mover / NetworkPrediction — Epic이 예측을 새로 만든 이유

언리얼 네트워크 · 46 / 47

왜 이걸 배워? — 문제의식부터

우리 조선 서버에서 이동을 어떻게 처리했는지 떠올려봐. 클라가 CM_MOVE를 보내면 서버가 좌표를 검사하고, 통과하면 SP_MOVE로 결과를 뿌려. 요청-응답. 클라는 서버 말을 기다렸다가 그린다. 단순하고, 치트에 강하고, 무엇보다 이해하기 쉬워.

그런데 만약 팀장이 와서 "핑 100ms에서도 손맛이 나야 해. 클라가 먼저 움직이게 해줘"라고 하면? 그때 네가 짤 코드가 뭘까. 클라가 입력을 저장해두고 먼저 움직이고, 서버 응답이 오면 그 시점으로 되감아서 저장해둔 입력을 다시 굴린다. 이게 예측·보정·리플레이야. 우리가 client-prediction, server-reconciliation에서 본 그 사이클.

자, 여기서 진짜 질문. 너는 그 코드를 어디에 짤래? 십중팔구 CChosunPlayer::Move() 안에 짜겠지. 입력 저장도 거기, 되감기도 거기, 재실행도 거기. 잘 돌아가. 6개월 뒤까지는.

6개월 뒤 기획자가 온다. "순간이동 스킬도 예측해줘. 그래야 즉발로 느껴져." 그럼 어떡하지? 스킬은 이동이 아니잖아. 근데 되감기·재실행 기계는 CChosunPlayer::Move() 안에 처박혀 있어. 스킬용으로 또 하나 만들어야 해. 그다음엔 커스텀 물리 오브젝트. 또 하나. 예측 엔진이 세 개가 되는 거야. 서로 시계도 안 맞고, 되감기 규칙도 다르고.

언리얼이 정확히 이 함정에 빠졌어. 예측·보정·리플레이 로직이 전부 CharacterMovementComponent(CMC) 안에 있거든. 그래서 GAS(스킬 시스템)는 CMC의 예측을 쓸 수가 없어서 자기만의 예측을 따로 만들었어(→ gas-prediction). 예측 엔진이 두 개가 된 거지.

그래서 Epic이 내린 결론이 이 챕터야. 예측을 CMC에서 떼어내서 일반화하자 — 그게 NetworkPrediction 플러그인. 그리고 그 위에서 이동을 처음부터 다시 쓰자 — 그게 Mover 플러그인. 20년 된 CMC를 대체하려는 시도야.

이걸 마지막 챕터로 배우는 이유도 분명해. CMC를 모르면 Mover가 뭘 고치려는 건지 절대 안 보여. 앞의 charactermovement-overview부터 server-reconciliation까지가 문제였고, 이 장이 답이야. 그리고 이 답은 iris와 정확히 같은 냄새가 난다 — 레거시를 일반화해서 재설계하기.

🔬 정직하게 먼저 — 실험적이다. 하지만 코드는 진짜다

이 챕터는 사정이 좀 다르니까 사실부터 깔고 간다.

NetworkPrediction과 Mover는 엔진 플러그인이야. Engine/Source가 아니라 Engine/Plugins 아래 산다:

  • Engine/Plugins/Runtime/NetworkPrediction/ — 예측 프레임워크(모터)
  • Engine/Plugins/Experimental/Mover/ — 그 위에 얹은 이동 구현(칼날)

엔진을 설치하면 둘 다 같이 깔려 있어. 그러니까 이 챕터도 다른 챕터와 똑같은 규칙으로 간다 — 실제 소스를 파일:줄번호로 인용하고, 각색하지 않는다. 아래 코드는 전부 진짜야.

다만 진짜 주의사항은 따로 있어. "코드를 못 본다"가 아니라 "코드가 움직인다"야:

  • Mover는 Experimental 폴더에 있다. 폴더 이름이 곧 경고문이야. 클래스·함수 이름이 엔진 버전마다 바뀐다. 실제로 이 챕터를 쓰는 UE 5.6 기준으로도, 5.6에서 OnGenerateMove() → GenerateMove_Implementation()으로 이름이 갈아엎어졌어(헤더에 UE_DEPRECATED(5.6, ...)가 그대로 박혀 있다).
  • 그러니까 줄번호와 이름을 외우지 마. 이 챕터에서 가져갈 건 설계 판단이야 — "예측 로직을 도메인 안에 박을래, 밖으로 빼서 일반화할래". 그건 엔진 버전과 무관하고, 우리 조선 서버에도 그대로 서는 갈림길이거든.

🌱 이 개념은 왜 생겼나 — 예측 프레임워크 분리
• 원래 구조: 예측이 필요한 건 결국 이동뿐이라고 봤어. 그래서 "먼저 움직이고 / 서버에 보고하고 / 틀리면 되감아 재실행"하는 기계를 이동 컴포넌트(CMC) 안에 통째로 넣었지. 실제로 20년간 잘 돌았고, 지금도 대부분의 UE 게임이 이걸로 굴러가.
• 그런데 문제: 예측이 필요한 게 이동만이 아니었어. 스킬(즉발 시전), 커스텀 물리(그래플링 훅, 차량), 상태 변화까지 다 예측하고 싶어져. 근데 되감기 기계는 CMC 뱃속에 있어서 꺼내 쓸 수가 없어. 그래서 GAS는 자기만의 예측 시스템을 처음부터 새로 만들었어. 예측 엔진이 두 개가 된 거야 — 시계도 다르고 되감기 규칙도 다른.
• 그래서 필요한 것: 되감기 기계를 "이동"이라는 도메인에서 뜯어내서, "무엇이든 시뮬레이션이면 예측해준다"는 일반 프레임워크로 만들기. → 그게 NetworkPrediction이고, 그 위에서 이동을 다시 구현한 게 Mover야. 세탁기 안에 붙박이로 박힌 모터를 떼어내서, 어디에나 꽂을 수 있는 범용 모터로 만든 셈.

0. 문 앞에서: 20년 된 만능 부엌칼

먼저 오해부터 풀자. CMC는 나쁜 코드가 아니야. 20년간 수억 명이 이걸로 뛰고 점프하고 웅크렸어. 포트나이트가 이걸로 돌아. 세상에서 제일 많이 검증된 이동 예측 코드라고 봐도 돼.

CMC는 만능 부엌칼이야. 걷기·달리기·점프·수영·비행·낙하·웅크리기·계단 오르기·발판 위에서 상대이동 — 캐릭터가 할 만한 이동은 다 들어있어. 그리고 그 전부에 예측·보정이 붙어있지. 칼 하나로 야채도 썰고 고기도 자르고 병뚜껑도 따. 대단해.

근데 만능 부엌칼의 문제가 뭘까. 한번 맞춰봐.

칼 하나에 기능을 20년간 계속 붙였어. 이제 이 칼로 "이 칼에 없는 새 작업"을 하려면 어떻게 해야 할까?

...정답: 칼을 뜯어고쳐야 해. 새 도구를 만드는 게 아니라, 기존 칼에 손잡이 하나 더 용접하고 날 하나 더 붙여야 해. 왜냐면 "자르는 힘"이 칼 손잡이 안에 들어있거든. 그 힘을 쓰려면 이 칼을 써야만 해.

CMC가 딱 그래. 되감기·재실행하는 예측 엔진이 CMC 손잡이 안에 있어. 그래서:

  • 새 이동 모드를 넣으려면 → CMC를 상속하고 여러 클래스를 같이 상속해야 해 (곧 볼 거야)
  • 이동이 아닌 걸 예측하려면 → 아예 못 써. 예측 엔진을 처음부터 새로 만들어야 해 (GAS가 실제로 그랬어)

Epic의 답은 이거야. 손잡이에서 모터를 꺼내자. "자르는 힘"(예측 엔진)을 칼에서 분리해서 범용 모터로 만들고, 칼날(이동 로직)은 그 모터에 꽂는 부품으로 다시 만들자. 모터 = NetworkPrediction, 새 칼날 = Mover.

전제가 흐릿하면 → charactermovement-overview (CMC의 세 역할), client-prediction (SavedMove와 먼저 움직이기), server-reconciliation (되감고 재실행하기)

1. CMC의 한계 — 구체적으로 뭐가 막히나

"얽혀 있어서 안 돼"는 너무 뭉뚱그린 말이야. 정확히 세 곳에서 막혀. 하나씩 못 박자.

1-1. 예측·보정·리플레이가 CMC 내부에 하드코딩

server-reconciliation에서 본 되감기 사이클을 떠올려봐. "서버가 정답을 보냄 → 클라가 그 시점으로 되감음 → 그 이후 저장해둔 입력을 다시 굴림(리플레이)." 이 사이클을 돌리는 코드가 어디 있냐면, UCharacterMovementComponent 클래스 안이야. 되감기 진입점인 ClientUpdatePositionAfterServerUpdate()도 CMC의 멤버 함수로 선언돼 있어(CharacterMovementComponent.h:2352). 전역 서비스가 아니라 이 컴포넌트의 소유물이라는 뜻이야.

이게 왜 문제냐면 — 그 함수들은 "무엇을" 되감을지를 이미 알고 있어. 위치, 속도, 발판, 이동 모드. 캐릭터의 이동 상태 말이야. 되감기 기계와 되감을 대상이 한 몸인 거지.

맞춰봐: 그럼 "스킬 쿨타임"이나 "그래플링 훅의 밧줄 길이"를 되감고 싶으면?
CMC의 되감기 함수한테 "이것도 좀 되감아줘"라고 부탁할 수 있을까?

...정답: 못 해. CMC의 되감기는 캐릭터 이동 상태만 되감도록 짜여 있어. 밧줄 길이가 뭔지 몰라. 이 되감기 기계를 재사용할 방법이 없으니, 밧줄을 예측하려면 되감기 기계를 처음부터 다시 만들어야 해.

1-2. 커스텀 이동 추가 = 상속 지옥

CMC에 없는 이동(예: 벽 타기, 대시)을 하나 넣는다고 쳐. 뭘 해야 할까? UE 커뮤니티가 "상속 지옥"이라고 부르는 절차가 이거야. 먼저 1번, FSavedMove_Character를 상속해서 내 무브 기록 클래스를 만든다. 이 클래스가 들고 있는 가상함수 목록을 봐. CharacterMovementComponent.h:2994-3028(발췌):

/** Clear saved move properties, so it can be re-used. */ ENGINE_API virtual void Clear(); /** Called to set up this saved move (when initially created) to make a predictive correction. */ ENGINE_API virtual void SetMoveFor(ACharacter* C, float InDeltaTime, FVector const& NewAccel, class FNetworkPredictionData_Client_Character & ClientData); /** Set the properties describing the position, etc. of the moved pawn at the start of the move. */ ENGINE_API virtual void SetInitialPosition(ACharacter* C); /** Returns true if this move is an "important" move that should be sent again if not acked by the server */ ENGINE_API virtual bool IsImportantMove(const FSavedMovePtr& LastAckedMove) const; ... (중략 — IsImportantMove, GetRevertedLocation 등) ... /** Set the properties describing the final position, etc. of the moved pawn. */ ENGINE_API virtual void PostUpdate(ACharacter* C, EPostUpdateMode PostUpdateMode); /** Returns true if this move can be combined with NewMove for replication without changing any behavior */ ENGINE_API virtual bool CanCombineWith(const FSavedMovePtr& NewMove, ACharacter* InCharacter, float MaxDelta) const; /** Combine this move with an older move and update relevant state. */ ENGINE_API virtual void CombineWith(const FSavedMove_Character* OldMove, ACharacter* InCharacter, APlayerController* PC, const FVector& OldStartLocation); /** Called before ClientUpdatePosition uses this SavedMove to make a predictive correction */ ENGINE_API virtual void PrepMoveFor(ACharacter* C); /** Returns a byte containing encoded special movement information (jumping, crouching, etc.) */ ENGINE_API virtual uint8 GetCompressedFlags() const;

그리고 2번, FNetworkPredictionData_Client_Character를 상속해서 "내 무브 기록을 대신 만들어줘"를 갈아끼운다. CharacterMovementComponent.h:3167-3168:

/** Allocate a new saved move. Subclasses should override this if they want to use a custom move class. */ ENGINE_API virtual FSavedMovePtr AllocateNewMove();

마지막 3번, UCharacterMovementComponent를 상속해서 위 2번을 돌려주고, 서버 쪽에서 비트를 다시 푼다. CharacterMovementComponent.h:2287 / :2392:

ENGINE_API virtual class FNetworkPredictionData_Client* GetPredictionData_Client() const override; ENGINE_API virtual void UpdateFromCompressedFlags(uint8 Flags);
🔤 기호 사전 — 위 세 클래스에 나온 이름들
• FSavedMove_Character = 클라가 "내가 이 순간 이런 입력으로 이렇게 움직였다"를 적어두는 기록 한 장. client-prediction에서 본 그 SavedMove야. 되감은 뒤 이 기록들을 다시 굴리는 게 리플레이.
• ENGINE_API virtual = virtual이 붙었다는 건 "상속해서 갈아끼우라고 열어둔 자리"라는 뜻이야. 위 목록이 전부 virtual인 게 곧 "확장하려면 상속밖에 길이 없다"는 증거고.
• Clear() = 기록 한 장을 재사용하기 전에 싹 지우는 함수. 주석 왈 so it can be re-used — 기록 객체를 매번 새로 만들면 비싸니까 돌려쓴다.
• SetMoveFor(...) = 현재 상태를 이 기록에 담는 함수. 커스텀 값을 추가했으면 여기서 같이 담아야 해.
• CanCombineWith(...) = 연속된 무브 두 개가 사실상 같은 입력이면 하나로 합쳐서 대역폭을 아낄지 판단하는 함수. 주석이 조건을 못 박아 — without changing any behavior(동작이 하나도 안 바뀔 때만). 여기서 판단을 틀리면 서버·클라가 어긋난다.
• PrepMoveFor(ACharacter* C) = 리플레이할 때 기록 → CMC로 상태를 다시 밀어넣는 함수. 주석에 before ClientUpdatePosition uses this SavedMove to make a predictive correction이라고 적혀 있지 — 되감기 직전에 불린다는 뜻이야. 여기를 빠뜨리면 되감은 뒤 값이 되살아나지 않아 계속 어긋나.
• uint8 GetCompressedFlags() const = 내 입력을 비트로 눌러담는 함수. 반환형이 uint8인 걸 봐 — 딱 한 바이트야. 1-3절에서 이게 왜 문제인지 볼 거야.
• FSavedMovePtr AllocateNewMove() = 무브 기록을 생산하는 공장 함수. 주석이 친절하게도 Subclasses should override this if they want to use a custom move class라고 알려줘 — 커스텀 기록 클래스를 쓰려면 여기를 갈아끼워야 한다는 뜻.
• FNetworkPredictionData_Client_Character = 클라의 예측 살림살이를 통째로 들고 있는 상자. 저장된 무브 목록, 시계 등. 이름에 _Character가 붙은 게 이미 결정적 증거야 — 이 예측 데이터는 캐릭터 전용으로 태어났다는 뜻이거든. 밧줄이나 스킬 쿨타임이 낄 자리가 처음부터 없어.
• UpdateFromCompressedFlags(uint8 Flags) = 서버 쪽에서, 비트로 눌러담긴 입력을 다시 펴서 복원하는 함수. 클라가 GetCompressedFlags로 담은 규칙과 정확히 짝이어야 해.
🔁 이제 다시 보자. 벽타기 하나 추가하는데 클래스 3개를 상속하고 오버라이드를 여러 개 정확히 짝 맞춰 채워야 해. 게다가 이 오버라이드들은 서로 암묵적으로 짝이야 — GetCompressedFlags에서 담은 비트를 UpdateFromCompressedFlags가 같은 규칙으로 풀어야 하고, SetMoveFor가 담은 걸 PrepMoveFor가 복원해야 해. 컴파일러는 이 짝을 검사해주지 않는다. 하나라도 어긋나면 에러가 아니라 "가끔 캐릭터가 튀는" 버그로 나타난다. 이게 상속 지옥이라 불리는 이유야.

보일러플레이트가 많은 것도 짜증나지만, 진짜 무서운 건 실수가 조용하다는 것이야. push-model에서 "dirty 마킹 빼먹으면 변경이 조용히 유실된다"고 했지? 똑같은 종류의 함정이야. 컴파일은 되는데 가끔 캐릭터가 튀어.

1-3. 그리고 비트가 모자라

위 1)번의 GetCompressedFlags()를 봐. 반환형이 uint8이었지. 이게 CompressedMoveFlags로 실려 가 — charactermovement-overview의 ServerMove RPC 파라미터에서 봤던 그 uint8.

uint8. 8비트. 한 바이트. 그런데 그 8칸이 어떻게 나뉘어 있는지, 엔진이 대놓고 적어놨어. CharacterMovementComponent.h:3039-3051:

// Bit masks used by GetCompressedFlags() to encode movement information. enum CompressedFlags { FLAG_JumpPressed = 0x01, // Jump pressed FLAG_WantsToCrouch = 0x02, // Wants to crouch FLAG_Reserved_1 = 0x04, // Reserved for future use FLAG_Reserved_2 = 0x08, // Reserved for future use // Remaining bit masks are available for custom flags. FLAG_Custom_0 = 0x10, FLAG_Custom_1 = 0x20, FLAG_Custom_2 = 0x40, FLAG_Custom_3 = 0x80, };
🔤 기호 사전 — enum CompressedFlags
• 0x01, 0x02, 0x04, 0x08... = 16진수야. 2진수로 펴면 각각 00000001, 00000010, 00000100, 00001000... — 한 칸씩 왼쪽으로 밀리는 비트 하나씩이야. 즉 이 8개 값이 한 바이트의 8칸을 하나씩 차지하고 있어.
• FLAG_JumpPressed / FLAG_WantsToCrouch = 엔진이 이미 써버린 두 칸. 점프와 웅크리기.
• FLAG_Reserved_1 / FLAG_Reserved_2 = "미래를 위해 예약됨". Epic이 나중에 쓰려고 비워둔 채 잠가둔 두 칸이야. 게임이 손대면 안 돼.
• // Remaining bit masks are available for custom flags. = 이 한 줄이 결론이야. "남은 비트는 커스텀용으로 쓸 수 있다" — 그 남은 게 FLAG_Custom_0부터 FLAG_Custom_3까지, 딱 네 개.
맞춰봐: 커스텀 입력 비트가 4개면 뭘 몇 개나 예측할 수 있을까?
대시, 벽타기, 슬라이딩, 패링, 그래플링, 이중점프, 구르기, 벽점프...

...정답: 4개. 세보면 진짜 FLAG_Custom_0/1/2/3이 전부야. 다섯 번째 능력부터는 넣을 자리가 없어. 물론 우회로는 있어 — ServerMove를 통째로 오버라이드해서 커스텀 RPC를 만들거나, 신형 패킹 무브(charactermovement-overview의 스니펫 1)를 확장하거나. 근데 그건 우회로지 설계가 열어준 길이 아니야. 우회로를 타는 순간 엔진 업데이트마다 깨질 위험을 네가 진다.

정리하면 CMC의 한계는 이거야:

막히는 곳증상근본 원인
이동 아닌 걸 예측아예 못 씀 → GAS가 별도 예측 시스템을 새로 만듦예측 엔진이 CMC 안에 박혀 있음
커스텀 이동 추가클래스 3개 상속 + 오버라이드 8개, 실수하면 조용히 튐확장점이 상속뿐 (데이터가 아니라 코드)
입력 전달커스텀 비트 4개 한계, 넘으면 우회로uint8 비트 플래그로 하드코딩
🌱 이 개념은 왜 생겼나 — Input / Sync / Aux 3분할
• 원래 구조: CMC의 FSavedMove_Character는 입력이든 결과든 부수 상태든 한 상자에 다 섞어 담았어. 어차피 캐릭터 이동 하나만 다루니까 굳이 나눌 이유가 없었지.
• 그런데 문제: 예측을 일반화하려면 프레임워크가 "이 값을 어떻게 다뤄야 하는지"를 알아야 해. 근데 다 섞여 있으면 구분을 못 해. 입력은 클라→서버로 보내야 하고, 결과 상태는 서버→클라로 보내며 보간해야 하고, 쿨타임 같은 값은 자주 안 바뀌니 보간하면 오히려 이상해져. 셋의 취급이 다른데 한 덩어리면 프레임워크가 손을 못 대.
• 그래서 필요한 것: 예측에 필요한 상태를 역할별로 세 칸으로 쪼개기. Input(내가 이번 틱에 뭘 눌렀나) / Sync(매 틱 변하고 보간되는 핵심 결과) / Aux(가끔 변하고 보간하면 안 되는 보조값). → 이렇게 나눠두면 프레임워크가 내용물이 뭔지 몰라도 예측·보정·리플레이를 대신 해줄 수 있어. 이게 NetworkPrediction의 심장이야.

2. NetworkPrediction의 발상 — 예측의 3요소

자, 여기가 이 챕터의 핵심이야. Epic이 CMC를 뜯어보고 발견한 것은 이거였어.

"예측·보정·리플레이는 사실 이동이랑 아무 상관이 없다."

생각해봐. 되감기 사이클이 실제로 하는 일이 뭐야?

  1. 클라가 입력을 하나 만든다. 그 입력으로 상태를 앞으로 굴린다(시뮬레이션).
  2. 입력과 결과를 기록해둔다.
  3. 서버가 정답 상태를 보내온다.
  4. 클라가 그 시점 상태로 되감고, 기록해둔 입력을 다시 굴린다.

이 네 줄 어디에도 "위치"나 "속도"가 안 나와. "입력"과 "상태"와 "굴리는 함수"만 있으면 돼. 그게 캐릭터 좌표든, 스킬 쿨타임이든, 밧줄 길이든 상관이 없어.

그래서 NetworkPrediction은 이 셋을 인터페이스로 추상화했어. 네가 이 셋만 채워 넣으면, 예측·보정·리플레이는 프레임워크가 공짜로 해준다.

그 추상화의 본체가 이거야. 놀랄 만큼 짧아. NetworkPredictionStateTypes.h:24-31:

// State type defines template<typename InInputCmd=void, typename InSyncState=void, typename InAuxState=void> struct TNetworkPredictionStateTypes { using InputType = InInputCmd; using SyncType = InSyncState; using AuxType = InAuxState; };
🔤 기호 사전 — TNetworkPredictionStateTypes
• template<typename InInputCmd, typename InSyncState, typename InAuxState> = "이 구조체를 쓸 때 타입 세 개를 끼워 넣어라"는 틀이야. typename은 "여기 들어올 건 어떤 타입이든 상관없다"는 뜻이고. 이 한 줄이 이 챕터의 핵심 문장이야 — 프레임워크는 내용물이 뭔지 모른다. 위치든 밧줄 길이든 스킬 쿨타임이든, 그냥 세 칸에 끼워 넣는 타입일 뿐이야.
• using InputType = InInputCmd; = "네가 준 첫 번째 타입을 앞으로 InputType이라고 부르겠다"는 별명 선언. 프레임워크는 이 별명으로만 접근해.
• =void = 기본값이 "없음". 안 채우면 그 칸은 안 쓴다는 뜻이야. Aux가 필요 없는 시뮬레이션도 있거든.
• 구조체 몸통에 데이터가 없다 = 봐, int도 float도 없어. 타입 세 개를 묶어두는 이름표가 전부야. 예측 프레임워크가 "이 시뮬레이션의 입력/동기/보조 타입은 각각 이것들이다"를 알아보는 용도지.

그럼 실제로 이 세 칸을 채운 예를 보자. Mover가 자기 타입을 끼워 넣는 딱 한 줄. MoverNetworkPredictionLiaison.h:20:

using KinematicMoverStateTypes = TNetworkPredictionStateTypes<FMoverInputCmdContext, FMoverSyncState, FMoverAuxStateContext>;
🔁 이제 다시 보자. 이 한 줄이 "상자 3개 채우기"의 실체야. <> 안에 Input, Sync, Aux 순서대로 자기 타입을 넣었지. 만약 네가 그래플링 훅을 예측하고 싶으면? TNetworkPredictionStateTypes<FMyHookInput, FMyHookSync, FMyHookAux>라고 쓰면 돼. 프레임워크 코드는 한 줄도 안 고친다. 이게 일반화야.

그리고 "굴리는 함수" 하나. MoverNetworkPredictionLiaison.h:45-49:

🔤 기호 사전 — SimulationTick(...)
• 주석 Given an starting state and timestep, produce a new state. = 이 한 문장이 함수의 전부야. "시작 상태 + 시간 조각을 주면 → 새 상태를 뱉는다." 오타(an starting)까지 그대로 옮겼어 — 엔진 주석이 진짜 이렇게 적혀 있다.
• Called by Network Prediction system. = 내가 부르는 게 아니라 프레임워크가 부른다는 뜻. 언제, 몇 번 부를지는 프레임워크 마음이야 — 예측할 때 한 번, 되감고 리플레이할 때 또 여러 번.
• const FNetSimTimeStep& TimeStep = "이번에 얼마만큼의 시간을 굴려라"는 시간 조각.
• TNetSimInput<...>& SimInput / TNetSimOutput<...>& SimOutput = 들어오는 상태와 나가는 상태를 따로 받는다는 표시. SimInput은 const야 — 읽기 전용. 입력 상태를 직접 고치는 게 아니라 새 상태를 SimOutput에 뱉는 모양이지. 그래야 되감아서 같은 입력으로 다시 굴리면 같은 결과가 나와. 리플레이가 성립하는 근거가 이 const 한 글자야.
• InitializeSimulationState(...) = 시뮬 시작할 때 초기 상태를 심어주는 함수. 역시 Called by Network Prediction system.

그럼 SimulationTick 안은 어떻게 생겼을까? Mover의 구현을 그대로 보자. 딱 "받아서 → 넘기고 → 뱉기"야. MoverNetworkPredictionLiaison.cpp:89-110:

마지막 한 조각. "내 시뮬레이션을 프레임워크에 등록"하는 법이야. 이것도 딱 이만큼. MoverNetworkPredictionLiaison.cpp:21-35:

🔁 이제 다시 보자. 새 예측 대상을 붙이는 절차가 이게 전부야 — ① 상자 3개(Input/Sync/Aux) 타입을 정하고, ② TNetworkPredictionStateTypes에 꽂고, ③ SimulationTick 하나 구현하고, ④ ModelDef로 등록한다. CMC의 "클래스 3개 상속 + 오버라이드 짝 맞추기 + 4비트 짜내기"와 비교해봐. 상속이 하나도 없다(등록만 있다). 그리고 이 어디에도 "이동"이라는 단어가 없다 — 그래서 밧줄이든 스킬 쿨타임이든 똑같이 끼워 넣을 수 있는 거야.

여기서 결정적인 게 뭐냐면 — SimulationTick 안에 "이동"이라는 말이 한 글자도 없어도 된다는 것이야. 그 함수가 캐릭터를 걷게 하든, 스킬 쿨타임을 깎든, 밧줄을 감든, 프레임워크는 신경 안 써. 입력 → 상태를 굴리는 함수이기만 하면 예측·보정·리플레이를 붙여준다.

3. Fixed tick vs Independent tick — 시계를 누가 정하나

NetworkPrediction이 CMC보다 한 발 더 나간 지점이 하나 더 있어. 시계야.

먼저 CMC가 어떻게 하는지 보자. 클라마다 프레임레이트가 다르지? 240fps인 애도 있고 30fps인 애도 있어. CMC는 각 클라가 자기 프레임 시간(DeltaTime)만큼 물리를 굴리고, "나 0.0041초짜리 무브 했어", "나 0.033초짜리 무브 했어"라고 제각각 다른 길이의 무브를 서버에 보내. 서버는 그걸 받아서 그 길이대로 재현해. 이게 Independent tick(독립 틱) 이야.

맞춰봐: 클라마다 틱 길이가 제각각이면 서버는 뭘 못 할까?
힌트 — 클라 A와 클라 B의 무브를 같은 시간 눈금 위에 나란히 놓을 수 있을까?

...정답: 서로 못 맞춰. A는 0.0041초 단위, B는 0.033초 단위로 시간을 쪼갰으니 눈금이 안 맞아. 그래서 서버는 각 클라의 무브를 따로따로 처리할 수밖에 없어. 이게 왜 아쉽냐면 — "남의 캐릭터도 예측"을 못 하거든.

지금 simulated-proxy-smoothing에서 봤듯이, 남 캐릭터(SimulatedProxy)는 예측을 안 해. 서버가 준 과거 위치를 받아서 보간만 해. 그래서 남 캐릭터는 항상 조금 과거에 있어. 격투 게임이나 근접 전투에서 이게 아프지.

Fixed tick(고정 틱) 은 이 판을 바꿔. 모든 시뮬레이션을 똑같은 크기의 시간 조각(예: 1/60초)으로만 굴려. 프레임레이트가 240이든 30이든, 시뮬은 무조건 1/60초 단위로 전진해.

Independent tick (CMC 방식) 클라A(240fps): |--|--|--|--|--|--| ← 0.0041초짜리 무브들 클라B( 30fps): |--------|--------| ← 0.033초짜리 무브들 서버 : 각자 따로 재현. 눈금이 안 맞아 나란히 못 놓음. → 남 캐릭터 예측 불가. 보간만. Fixed tick (NetworkPrediction이 지원) 클라A : |---|---|---|---| ← 전부 1/60초 클라B : |---|---|---|---| ← 전부 1/60초 서버 : 눈금이 같다 = 프레임 번호로 정렬 가능 → "지금 서버는 47번 프레임" 처럼 공통 시계가 생김 → 남 캐릭터도 같은 SimulationTick으로 앞으로 굴려볼 수 있음 (forward predict)
🔤 기호 사전 — 위 도식의 용어
• tick(틱) = 시뮬레이션이 한 번 전진하는 시간 조각. "이번 틱에 0.016초만큼 굴렸다"처럼 써.
• Independent tick(독립 틱) = 클라마다 자기 프레임 시간대로 굴리는 방식. 조각 크기가 제각각이야. CMC가 이 방식이고, NetworkPrediction도 이 모드를 지원해.
• Fixed tick(고정 틱) = 모두가 똑같은 크기 조각으로 굴리는 방식. 프레임레이트와 무관하게 시뮬 스텝이 일정해.
• forward predict(전방 예측) = 받은 상태를 그냥 보간하는 게 아니라, 같은 시뮬레이션 함수로 앞으로 굴려서 "지금쯤 여기 있겠지"를 계산하는 것. 남 캐릭터를 과거가 아니라 현재에 가깝게 그릴 수 있어.
• "프레임 번호로 정렬" = 눈금이 같으니 시간을 float 초가 아니라 정수 프레임 번호로 셀 수 있다는 뜻. 서버·클라가 "47번 프레임"을 똑같이 가리킬 수 있어 → 되감기 기준점이 훨씬 깔끔해져.
🔁 이제 다시 보자. Independent는 클라 편의(프레임레이트 자유롭게)를 사고, Fixed는 공통 시계를 산다. 공통 시계가 생기면 SimulationTick을 남의 캐릭터에도 똑같이 돌려볼 수 있으니 남 캐릭터도 예측이 가능해져. NetworkPrediction은 둘 다 지원하고, 어느 쪽을 쓸지는 게임이 고른다. CMC는 애초에 Independent 하나뿐이었어.

이게 진짜 고를 수 있는 선택지인지, 소스로 확인하자. 열거형 하나에 둘 다 들어 있어. NetworkPredictionConfig.h:9-17:

enum class ENetworkPredictionTickingPolicy : uint8 { // Client ticks at local frame rate. Server ticks clients independently at client input cmd rate. Independent = 1 << 0, // Everyone ticks at same fixed rate. Supports group rollback and physics. Fixed = 1 << 1, All = Independent | Fixed UMETA(Hidden), };
🔤 기호 사전 — ENetworkPredictionTickingPolicy
• Independent 주석 = Client ticks at local frame rate. Server ticks clients independently at client input cmd rate. — 클라는 자기 프레임레이트로 굴리고, 서버는 각 클라를 따로따로 굴린다. 위 도식 그대로지.
• Fixed 주석 = Everyone ticks at same fixed rate. Supports group rollback and physics. — 모두가 같은 고정 레이트. 그리고 결정적인 두 단어: group rollback(여러 액터를 한 덩어리로 되감기)과 physics(물리까지 되감기). Independent 주석엔 이 말이 없어 — 눈금이 안 맞으면 여럿을 나란히 되감을 수가 없거든.
• 1 << 0, 1 << 1 = 비트를 왼쪽으로 미는 연산. 각각 1, 2야. 즉 비트 플래그로 설계했다는 뜻이고, 그래서 All = Independent | Fixed처럼 둘 다 지원한다고 표시할 수도 있어. 어느 한쪽으로 못 박지 않은 게 설계 의도야.

그리고 프로젝트 설정에서 실제로 고른다. 기본값이 뭔지도 보이지. NetworkPredictionSettings.h:17-30:

(중략) ... // Frame rate to use when running Fixed Tick simulations. Note: Engine::FixedFrameRate will take precedence if Engine::bUseFixedFrameRate is enabled. UPROPERTY(config, EditAnywhere, Category = FixedTick) int32 FixedTickFrameRate = 60;
🔁 이제 다시 보자. PreferredTickingPolicy가 설정값(UPROPERTY(config, EditAnywhere) = 에디터에서 클릭으로 바꾸는 값)이라는 게 요점이야. CMC에선 이게 선택지가 아니라 운명이었어. 그리고 기본값이 Fixed고, 고정 틱 레이트 기본값이 60 — 아까 도식에서 예로 든 "1/60초"가 진짜 엔진 기본값이었던 거야. 주석의 Leave this on Fixed if you intend to use physics도 짚고 가 — 물리를 예측에 끼울 거면 Fixed가 필수라는 뜻이니까.

공짜는 아니야. Fixed tick은 프레임레이트와 시뮬레이션 속도를 분리해야 하니, 렌더 프레임과 시뮬 프레임 사이의 보간을 따로 해야 하고, 남은 시간(accumulator) 관리도 붙어. 대신 되감기 기준점이 정수 프레임 번호가 되니 server-time-sync의 시계 맞추기도 훨씬 단순해져. 어느 쪽이 옳다가 아니라, 게임이 고르게 해준다는 게 요점이야. CMC는 고를 수가 없었어.

🌱 이 개념은 왜 생겼나 — Mover의 MovementMode 분리
• 원래 구조: CMC는 걷기·낙하·수영·비행을 EMovementMode라는 enum으로 두고, 거대한 switch로 갈라서 CMC 클래스 안에 전부 구현했어. 모드가 코드 안에 박혀 있는 거야.
• 그런데 문제: 새 모드를 넣으려면 enum에 값을 추가하고 CMC를 상속해서 switch 분기를 늘려야 해. 모드끼리 코드가 뒤엉키고, 남이 만든 이동 모드를 플러그인처럼 가져다 꽂을 수가 없어. 벽타기 플러그인을 사와도 내 CMC 상속 클래스랑 합치려면 손으로 이어붙여야 하지.
• 그래서 필요한 것: 이동 모드를 enum + switch가 아니라 독립된 객체(데이터) 로 만들기. 각 모드가 자기 시뮬레이션을 스스로 들고, 컴포넌트는 "지금 어느 모드 객체를 쓸지"만 고른다. → 이게 Mover의 MovementMode야. 코드 확장(상속)에서 데이터 조립으로 넘어간 거지. iris가 "중앙 RepLayout → 객체 단위 Fragment"로 쪼갠 것과 정확히 같은 동작이야.

4. Mover — 그 위에서 이동을 다시 쓰다

NetworkPrediction은 모터야. 아무거나 예측해주지만, 그 자체로는 캐릭터를 걷게 하지 못해. 걷기·점프·낙하는 누군가 SimulationTick 안에 써넣어야 하지.

그 "누군가"가 Mover 플러그인이야. NetworkPrediction 위에서 이동을 처음부터 다시 구현한 것. CMC를 대체하는 게 목표고.

Mover의 핵심 차별점은 MovementMode를 데이터로 분리한 거야.

먼저 CMC 쪽. "거대한 switch"라는 게 과장인지 아닌지, 진짜 코드를 보자. CharacterMovementComponent.cpp:3443-3467:

🔤 기호 사전 — CMC의 switch
• switch (MovementMode) = MovementMode라는 enum 값에 따라 갈라지는 분기문. enum은 정해진 값 중 하나를 고르는 목록형 타입인데, MOVE_Walking·MOVE_Falling 같은 이름이 컴파일 시점에 못 박혀 있어. 새 값을 넣으려면 엔진 소스를 고쳐야 한다는 뜻이야.
• PhysWalking / PhysFalling / PhysSwimming... = 각 모드의 실제 이동 로직. 전부 UCharacterMovementComponent 클래스의 멤버 함수야. 즉 걷기·낙하·수영·비행이 전부 한 클래스 안에 산다.
• case MOVE_Custom: PhysCustom(...) = Epic이 마련해둔 탈출구야. "커스텀 모드는 여기로 오세요." 근데 이게 단 하나의 문이야 — 커스텀 이동이 여러 개면 PhysCustom 안에서 또 갈라야 해. CustomMovementMode라는 별도 변수로 switch 안의 switch를 짜게 되는 거지.
• default: ... unsupported movement mode = 모르는 모드가 오면 경고 찍고 MOVE_None으로 되돌린다. 목록에 없는 건 존재할 수 없다는 선언이야.

• TMap<FName, TObjectPtr<UBaseMovementMode>> MovementModes = 이 한 줄이 switch를 통째로 대체한 것이야. TMap은 "이름 → 값" 사전이고, 여기선 FName(모드 이름) → UBaseMovementMode 객체. enum이 이름표로, switch 분기가 객체로 바뀐 거지.

• 주석 Merge proposed movement from the current mode with movement from layered moves = "현재 모드의 제안을 레이어드 무브의 이동과 섞는다". GenerateMove가 왜 "제안"인지 여기서 밝혀지지 — 혼자 결정하지 않고 합쳐진다는 뜻이야.
🔁 이제 다시 보자. CMC는 모드가 코드(enum + switch) 라서 새 모드를 넣으려면 클래스를 상속해 switch를 늘려야 했어. Mover는 모드가 객체(TMap 목록) 라서 모드 객체 하나 만들어 목록에 등록하면 끝이야 — 심지어 블루프린트로도(Blueprintable). FSavedMove_Character 상속도, CompressedFlags 비트 짜내기도 필요 없어 — 그건 다 아래층(NetworkPrediction)이 이미 일반화해서 처리하고 있으니까. 디스패치 코드는 모드가 몇 개든 그대로다.

Mover가 얹은 다른 개념도 하나만 짚자. Layered Move(레이어드 무브) — "지금 이동 모드를 바꾸지 않으면서 잠깐 얹는 이동"이야. 넉백, 강제 점프, 그래플링 당김 같은 거. CMC에선 이걸 LaunchCharacter 같은 특수 함수로 억지로 밀어넣었는데, Mover는 이동 모드 위에 레이어로 겹치는 정식 개념으로 만들었어. 방금 본 디스패치 주석에 Merge proposed movement from the current mode with movement from layered moves라고 적혀 있던 그거야.

그 레이어드 무브의 기반 구조체가 이거야. LayeredMove.h:71-92(발췌):

• EMoveMixMode MixMode = 주석 왈 how this object's movement contribution should be mixed with others — 이 이동을 남의 이동과 어떻게 섞을지. 아까 디스패치 코드에서 본 EMoveMixMode::OverrideAll이 그중 하나야("모드의 제안을 무시하고 내가 다 덮는다"). "섞는 방식"이 데이터 필드라는 게 핵심이야 — CMC엔 이런 개념 자체가 없었어.
• uint8 Priority = 레이어드 무브끼리 충돌할 때 누가 이기나. 넉백 중에 또 넉백을 맞으면? 숫자 큰 놈이 이겨.
• float DurationMs = 수명. 주석이 세 경우를 갈라놔 — > 0이면 그 시간 뒤 자동 만료, 0이면 딱 한 틱만 실행(= 순간적인 발사·넉백), < 0이면 직접 끝내줄 때까지 지속(= 그래플링 밧줄처럼 매달려 있는 것).

⚠️ 여기서 반드시 브레이크를 밟자 — 아직 실험적이다

• Mover는 UE 5.4에서 experimental(실험적)로 들어왔고, 지금도 정식 기본값이 아니야. Engine/Plugins/Experimental/Mover/ — 폴더 이름이 이미 말해주지. API가 버전마다 바뀔 수 있고, 문서보다 소스가 앞서 있고, 예제도 아직 적어.

• NetworkPrediction도 마찬가지로 오래 실험적 상태였어. 몇 년째 "곧"이었지. 그동안 실제 프로덕션 게임 대부분은 그냥 CMC를 썼고, 지금도 그래. 포트나이트도 CMC 계보 위에 있어.

• 그래서 지금 상용 프로젝트를 시작한다면? 십중팔구 답은 CMC야. 20년 검증됐고, 커뮤니티 자료가 산더미고, 막히면 물어볼 사람이 있어. Mover는 "새 프로젝트 + 커스텀 이동이 극단적으로 많음 + 엔진 업데이트 따라갈 여력 있음"일 때 검토할 카드지, 기본 선택지가 아니야.

• 그럼 왜 배우냐? 첫째, CMC를 알아야 Mover가 왜 나왔는지 안다 — 거꾸로도 참이야. Mover의 설계를 보면 CMC의 어디가 아팠는지가 선명하게 보여. 둘째, 언젠가 이게 기본이 될 가능성이 높아. Iris가 걸어간 길과 같거든. 셋째, "예측을 도메인에 박을까, 밖으로 뺄까"는 우리 서버에도 서는 갈림길이야. 그건 언리얼 버전과 무관한 설계 지식이지.

5. Iris와 나란히 놓기 — 같은 흐름의 두 얼굴

여기서 이 책 전체가 한 번 연결돼. iris를 다시 떠올려봐. Iris가 뭐였지?

레거시 복제는 "이 액터의 이 프로퍼티를 어떻게 복제해"라는 지식을 UNetDriver/RepLayout 같은 중앙 덩어리에 하드코딩했어. 그래서 새 규칙을 붙이려면 그 중앙 덩어리를 매번 건드려야 했지. Iris는 그걸 Fragment라는 객체 단위로 쪼개고, 타입별 동작을 함수포인터 테이블(데이터) 로 등록하게 바꿨어.

6. 우리 서버랑 비교

우리 조선협객전 서버로 번역해보자. 먼저 정직하게 짚을 것: 우리 서버엔 예측이 아예 없어.

CM_MOVE가 오면 IOCP 워커가 받고, 단일스레드 게임 로직이 검사하고, SP_MOVE로 뿌려. 클라는 서버 응답을 기다렸다가 그린다. 요청-응답. 예측도 없고, 되감기도 없고, 리플레이도 없어. 그래서 이 챕터의 CMC vs Mover 논쟁은 우리한테 남의 집 얘기처럼 들려.

근데 아니야. 만약 우리가 예측을 넣는다면, 우리도 정확히 같은 갈림길에 선다.

갈림길 A — 이동에 하드코딩 (= CMC의 길)

// 개념 의사코드 — 우리 서버에 예측을 넣는 첫 번째 방법 class CChosunPlayer { // 이동 예측을 여기 직접 박는다 std::deque<SavedMove> m_SavedMoves; // 클라가 보낸 무브 기록 void OnClientMove(...); // 재현·검증 void SendCorrection(...); // 어긋나면 되돌림 }; // → 빠르게 만들 수 있다. 이동은 확실히 좋아진다. // → 6개월 뒤 "스킬도 예측해줘" 하면? 스킬용 되감기를 또 만든다. // (= UE에서 GAS가 자기 예측을 따로 만든 것과 똑같은 일)

7. 헷갈리는 용어 딱 정리

  • CMC (CharacterMovementComponent) — 20년 검증된 UE의 기본 이동 컴포넌트. 이동 로직 + 예측·보정·리플레이가 한 클래스 안에 다 들어있다. 지금도 프로덕션 기본값.
  • NetworkPrediction (플러그인) — 예측·보정·리플레이를 이동에서 떼어내 일반화한 프레임워크. Input/Sync/Aux 3분할 + SimulationTick 하나면 무엇이든 예측해준다. Engine/Plugins/Runtime/NetworkPrediction/. 실험적.
  • Mover (플러그인) — NetworkPrediction 위에서 이동을 다시 구현한 것. CMC 대체가 목표. MovementMode를 객체(데이터) 로 분리해 커스텀 이동 추가가 쉽다. Engine/Plugins/Experimental/Mover/. UE5.4+ 실험적.
  • Input / Sync / Aux — 예측 상태의 3분할. Input=이번 틱 입력(클라→서버), Sync=매 틱 변하고 보간되는 핵심 결과(위치·속도), Aux=가끔 변하고 보간하면 안 되는 보조값(쿨타임·최대속도).
  • Fixed tick / Independent tick — 시뮬레이션 시간 조각을 모두 같은 크기로 굴리느냐(Fixed), 클라마다 자기 프레임 시간대로 굴리느냐(Independent). Fixed면 공통 시계가 생겨 남 캐릭터도 전방 예측할 수 있다. CMC는 Independent만, NetworkPrediction은 둘 다.
  • Layered Move — 이동 모드를 바꾸지 않으면서 위에 얹는 이동. 넉백, 강제 점프, 그래플링 당김 같은 것. Mover가 정식 개념으로 승격시켰다.
  • CompressedMoveFlags — CMC가 클라 입력(점프·웅크리기 등)을 uint8 한 바이트에 눌러담는 비트 묶음. 기본 플래그가 자리를 먹어 커스텀은 4비트뿐. Mover/NP에는 이 제한이 없다(구조체니까).

8. 참조 링크

Q1. CMC는 20년 검증됐는데, Epic은 왜 이걸 다시 쓰려고 하나요?

답 보기
CMC가 나쁜 코드라서가 아니야. 오히려 세상에서 제일 많이 검증된 이동 예측 코드지. 문제는 예측·보정·리플레이 로직이 CMC 클래스 안에 하드코딩돼 있다는 거야. 되감기 기계와 되감을 대상(캐릭터 이동 상태)이 한 몸이거든. 그래서 "이동이 아닌 것"을 예측하려면 그 기계를 꺼내 쓸 수가 없어. 만능 부엌칼인데 자르는 힘이 손잡이 안에 들어있어서, 새 작업을 하려면 칼을 뜯어고쳐야 하는 상황이야. Epic의 답은 "손잡이에서 모터를 꺼내자" — 예측 엔진을 이동 밖으로 분리한 게 NetworkPrediction이고, 그 모터 위에서 이동을 다시 쓴 게 Mover야.

↳ "이동이 아닌 걸 예측 못 한다"는 게 실제로 무슨 사고를 냈나요?

답 보기
GAS(스킬 시스템)가 자기만의 예측을 처음부터 새로 만들었어. 스킬도 즉발로 느껴지려면 클라가 먼저 시전하고 서버가 틀렸다면 되돌려야 하잖아 — CMC가 이미 그 되감기 기계를 갖고 있는데, 캐릭터 이동 상태만 되감도록 짜여 있어서 스킬 쿨타임이 뭔지 몰라. 재사용이 불가능해. 그래서 GAS는 PredictionKey 같은 자기 예측 체계를 별도로 만들었고, 결국 엔진 안에 예측 엔진이 두 개가 됐어. 시계도 다르고 되감기 규칙도 다른 두 개가. 이게 "일반화하지 않은 대가"의 가장 비싼 증거야.

↳ 커스텀 이동 하나 추가하는 게 왜 그렇게 힘들죠?

답 보기
벽타기 하나 넣는데 클래스를 3개 상속해야 해. FSavedMove_Character(무브 기록), FNetworkPredictionData_Client_Character(예측 살림살이), UCharacterMovementComponent. 그리고 오버라이드를 8개쯤 짝 맞춰 채워야 하는데, 이것들이 암묵적으로 짝이야 — GetCompressedFlags로 담은 비트를 UpdateFromCompressedFlags가 같은 규칙으로 풀어야 하고, SetMoveFor가 담은 걸 PrepMoveFor가 복원해야 해. 하나라도 어긋나면 컴파일 에러가 아니라 "가끔 캐릭터가 튀는" 조용한 버그로 나타나. 게다가 입력을 담는 CompressedMoveFlags가 uint8, 즉 8비트인데 기본 플래그가 자리를 먹어서 커스텀은 4비트뿐이야. 다섯 번째 능력부터는 넣을 자리가 없어.

Q2. 그럼 NetworkPrediction의 발상은 정확히 뭔가요?

답 보기
"예측·보정·리플레이는 사실 이동이랑 아무 상관이 없다"는 발견이야. 되감기 사이클이 하는 일을 뜯어보면 — 입력을 만들고, 그걸로 상태를 굴리고, 기록하고, 서버 정답이 오면 되감아서 기록된 입력을 다시 굴린다. 여기 어디에도 "위치"나 "속도"가 안 나와. 입력 + 상태 + 굴리는 함수만 있으면 돼. 그래서 이 셋을 인터페이스로 추상화했어. 게임은 상자 3개(Input/Sync/Aux)와 함수 1개(SimulationTick) 만 채워 넣고, 예측·보정·리플레이는 프레임워크가 공짜로 해준다. SimulationTick 안에 "이동"이라는 말이 한 글자도 없어도 돼 — 캐릭터를 걷게 하든 밧줄을 감든 프레임워크는 신경 안 써.

↳ 상태를 왜 굳이 Input/Sync/Aux 셋으로 나눴어요? 하나면 안 되나요?

답 보기
셋의 취급이 완전히 다르기 때문이야. Input은 클라가 만들어서 서버로 보내는 값(방향키, 대시 눌렀나). Sync는 매 틱 변하는 핵심 결과라 예측하고 보간해야 자연스러운 값(위치, 속도). Aux는 가끔만 변하고 보간하면 오히려 이상해지는 값(쿨타임, 최대속도, 현재 모드). 위치는 두 값 사이를 부드럽게 이어야 맞지만, 쿨타임을 보간하면 말이 안 되잖아. 게다가 Aux는 자주 안 변하니 대역폭도 덜 먹게 따로 뺄 수 있고. CMC의 FSavedMove_Character는 이걸 한 상자에 다 섞어 담았어 — 캐릭터 이동 하나만 다루니 굳이 나눌 이유가 없었지. 근데 일반화하려면 프레임워크가 "이 값을 어떻게 다뤄야 하는지" 알아야 하니까 역할별로 칸을 갈라야 해. 이렇게 나눠두면 프레임워크는 내용물이 뭔지 몰라도 일을 대신 해줄 수 있어.

↳ Fixed tick과 Independent tick은 뭐가 다른가요?

답 보기
시뮬레이션 시간 조각의 크기를 누가 정하냐의 차이야. Independent는 클라마다 자기 프레임 시간대로 굴려 — 240fps는 0.0041초짜리, 30fps는 0.033초짜리 무브를 보내. CMC가 이 방식이야. 문제는 눈금이 안 맞아서 서버가 클라들의 무브를 같은 시간축에 나란히 못 놓는다는 것. 그래서 남의 캐릭터는 예측을 못 하고 과거 위치를 보간만 해(그래서 남 캐릭터는 늘 조금 과거에 있어). Fixed는 모두가 똑같은 크기(예: 1/60초)로만 굴려. 눈금이 같으니 시간을 정수 프레임 번호로 셀 수 있고, 서버·클라가 "47번 프레임"을 똑같이 가리킬 수 있어. 그럼 남 캐릭터도 같은 SimulationTick으로 앞으로 굴려볼 수 있어(전방 예측). 공짜는 아니고 렌더 프레임과 시뮬 프레임 분리·보간 비용이 붙지. 요점은 NetworkPrediction은 둘 다 지원해서 게임이 고를 수 있다는 것 — CMC는 고를 수가 없었어.

Q3. Mover는 NetworkPrediction이랑 뭐가 다른 건가요?

답 보기
층이 달라. NetworkPrediction은 "모터"야 — 아무거나 예측해주지만, 그 자체로는 캐릭터를 걷게 하지 못해. 걷기·점프·낙하는 누군가 SimulationTick 안에 써넣어야 하지. Mover가 그 "누군가"야. NetworkPrediction 위에서 이동을 처음부터 다시 구현한 플러그인이고, CMC를 대체하는 게 목표. 그래서 둘은 경쟁 관계가 아니라 위아래로 붙는 관계야 — Iris와 ReplicationGraph가 층이 다른 것과 똑같아. 실제로 Mover는 백엔드를 갈아끼울 수 있게 설계돼서, 예측을 NetworkPrediction으로 돌릴 수도 있고 물리 기반(Chaos) 예측으로 돌릴 수도 있고 싱글플레이면 예측 없이 굴릴 수도 있어. 이동 로직은 그대로 두고 아래층만 교체하는 거지 — 이게 "예측을 분리했다"의 실질적 배당금이야.

↳ MovementMode를 데이터로 분리했다는 게 무슨 뜻이고, 뭐가 좋아지죠?

답 보기
CMC는 걷기·낙하·수영을 EMovementMode라는 enum으로 두고 거대한 switch로 갈라서 CMC 클래스 안에 전부 구현했어. 모드가 코드에 박혀 있는 거야. 그래서 새 모드 = enum 추가 + CMC 상속 + switch 분기 추가. Mover는 모드를 독립된 객체로 만들고, 컴포넌트는 "이름 → 모드 객체" 목록만 들고 있어. 새 모드 = 모드 객체 하나 만들어서 목록에 등록. 끝. CMC 상속도, switch도, FSavedMove_Character 상속도, 비트 짜내기도 없어 — 그건 다 아래층(NetworkPrediction)이 이미 일반화해서 처리하니까. 코드 확장(상속)에서 데이터 조립으로 넘어간 거지. 남이 만든 이동 모드를 플러그인처럼 가져다 꽂는 것도 그제서야 가능해져.

Q4. 이거 Iris랑 무슨 상관인가요? 둘 다 나왔길래 묻습니다.

답 보기
정확히 같은 흐름의 두 얼굴이야. Iris는 복제의 재설계, NetworkPrediction/Mover는 예측의 재설계인데, 병도 처방도 똑같아. 병: 레거시가 그 지식을 중앙 덩어리에 하드코딩했다(Iris는 RepLayout/UNetDriver에, CMC는 이동 컴포넌트에). 처방: 객체 단위로 쪼개고 데이터로 조립하게 바꾼다(Iris는 Fragment + 함수포인터 테이블, Mover는 MovementMode 객체). 한 문장으로 하면 Epic이 지금 하는 일은 "10~20년간 잘 돌았지만 특정 도메인에 하드코딩된 시스템을, 일반화된 프레임워크 + 데이터 확장점으로 다시 쓴다"야. 그리고 대가도 똑같이 치러 — 둘 다 배우기 어렵고, 둘 다 실험적이고, 프로덕션은 둘 다 여전히 레거시를 쓴다. 일반화는 공짜가 아니거든. 특수화된 시스템은 그 특수한 일을 제일 잘해.

Q5. 그럼 지금 새 프로젝트 시작하면 Mover 쓰면 되나요?

답 보기
십중팔구 아니야. CMC 써. Mover는 UE 5.4에서 experimental로 들어왔고 지금도 정식 기본값이 아니야 — 폴더 경로가 Plugins/Experimental/Mover/인 게 이미 말해주지. API가 버전마다 바뀔 수 있고, 문서보다 소스가 앞서 있고, 예제도 적어. 반면 CMC는 20년 검증됐고 커뮤니티 자료가 산더미고 막히면 물어볼 사람이 있어. 포트나이트도 CMC 계보 위에 있고. Mover는 "새 프로젝트 + 커스텀 이동이 극단적으로 많음 + 엔진 업데이트를 따라갈 여력 있음"일 때 검토하는 카드지 기본 선택지가 아니야. 그럼 왜 배우냐고? CMC를 알아야 Mover가 왜 나왔는지 알고, Mover를 알아야 CMC의 어디가 아팠는지가 선명해져. 그리고 "예측을 도메인에 박을까 밖으로 뺄까"는 언리얼 버전과 무관한 설계 지식이야.

↳ 우리 조선 서버(예측 없는 요청-응답)에 예측을 넣는다면 뭘 먼저 정해야 하죠?

답 보기
두 가지야. 첫째, 이 챕터의 갈림길에 우리도 선다는 걸 알아야 해. (A) 되감기·재실행을 CChosunPlayer 안에 박는다 → 빠르게 만들고 이동은 좋아지지만, 6개월 뒤 "스킬도 예측해줘" 하면 스킬용 되감기를 또 만들게 돼. UE에서 GAS가 겪은 일 그대로. (B) 예측 엔진을 도메인 밖으로 빼서 일반화한다 → 처음이 훨씬 느리고 어렵지만 두 번째 예측 대상부터 공짜. A는 지금 싸고 나중에 비싸고, B는 지금 비싸고 나중에 싸. 예측할 게 이동 하나뿐이면 A가 옳고, 스킬·물리까지 갈 게 뻔하면 B가 옳아.

둘째, 스레드 경계를 제일 먼저 못 박아야 해. UE의 예측이 락 없이 되감고 재실행할 수 있는 건 게임 스레드 싱글스레드라는 강한 전제 덕분이야. 우리도 게임 로직은 싱글스레드니까 이 전제는 가져올 수 있어. 근데 예측 상태를 IOCP 워커가 만지는 순간 끝장이야 — 되감기 도중에 다른 스레드가 상태를 바꾸면 리플레이 결과가 매번 달라져서 영원히 수렴하지 않아. "예측 상태는 오직 게임 스레드만 만진다"를 규칙으로 박고 시작해야 해.
