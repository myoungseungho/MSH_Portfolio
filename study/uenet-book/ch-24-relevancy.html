관련성: 누구에게 보낼지 (Relevancy)

언리얼 네트워크 · 24 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이미 이 고민을 해봤을 거야. 몬스터가 움직였다, 아이템이 떨어졌다, 누가 스킬을 썼다. 그때 서버는 SP_* 패킷을 아무한테나 다 뿌리면 안 돼. 누가 이 소식을 알아야 하는지 먼저 골라야 해.

이걸 안 고르면 바로 터져. 필드에 플레이어 500명, 액터 수천 개가 있는데 몬스터 위치 갱신을 전원에게 매 틱 보내면 IOCP 워커는 WSASend 일감에 깔리고, 커넥션 send 큐는 불어나고, 결국 락 잡는 시간과 복사 비용만 늘어. 받는 클라도 문제야. 화면에 보이지도 않는 남의 전투 CM_/SP_ 조각을 계속 받으면, 게임이 아니라 우체통 정리부터 하게 돼.

우리 조선 서버도 그래서 CChosunPlayer가 있는 위치, 파티, 존, 시야셀 같은 걸 보고 "이 사람한테 보낼까 말까"를 먼저 판단하잖아. 싱글스레드 게임 로직에서 대상 목록을 좁혀놓고, IOCP는 그 결과만 나르는 구조가 되어야 서버가 산다. 관심 없는 사람에게는 안 보낸다는 규칙이 없으면, 아무리 패킷 핸들러를 잘 짜도 대역폭과 CPU가 새어 나가.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 Relevancy(관련성)야. AActor::IsNetRelevantFor는 액터마다, 커넥션마다 "이걸 이 플레이어에게 보낼 필요가 있나?"를 묻는 관문이다. 거리 안에 있으면 보내고, 주인한테만 의미 있으면 주인에게만 보내고, 전역으로 꼭 알아야 하는 건 거리와 상관없이 보낸다.

왜 지금 배우냐면, 앞에서 서버가 매 틱 복제 후보를 추리고 보내는 큰 흐름을 봤기 때문이야. 이제는 그 후보 중 애초에 누구한테 갈 자격이 있는지를 잘라야 한다. 이 챕터가 그 문이고, 다음에는 관련 있다고 통과한 애들 사이에서 "누구 먼저, 얼마나 자주" 보낼지를 다룬다.

0) 들어가며 — 파티에서 굳이 안 부르는 사람

동네잔치를 연다고 해봐. 초대장을 몇 장 찍어야 할까? 온 동네 만 명한테 다 돌려? 아니지. 잔치 소리가 들릴 거리 안에 사는 사람한테만 돌려. 옆 동네 사람한테 "우리 집 잔치해요" 초대장 보내봤자 종이 낭비, 우편배달부 다리 고생, 받는 사람도 귀찮아.

서버도 똑같아. 월드에 액터가 수천 개 떠 있어. 근데 저 멀리 지도 반대편에서 벌어지는 몬스터 싸움을, 여기 있는 내 클라에 초당 수십 번씩 보낼 이유가 없어. 화면에 보이지도 않는데. 그 트래픽은 그냥 낭비야.

그래서 서버는 액터마다 커넥션마다 이걸 물어봐.

"이 액터를, 이 플레이어한테, 보낼 필요가 있나?"

이 판정이 바로 Relevancy(관련성)야. 우리 서버 용어로 하면 AOI(Area of Interest, 관심 영역) 판정 그거랑 똑같은 개념이야. "관심 없는 대상은 안 보낸다."

그리고 이걸 실제로 구현하는 게 AActor::IsNetRelevantFor 라는 함수야. 이번 챕터는 이 함수 하나를 뜯는 거야. 앞에서 server-replicate-actors로 "매 틱 후보 추리고 정렬해서 보낸다"는 큰 그림을 봤다면, 이번엔 그 "후보에 애초에 넣을지 말지"의 관문을 보는 거지.

전제 복습은 링크로만. 커넥션이 뭔지 애매하면 → netconnection-overview, 매 틱 어디서 이게 도는지 → netdriver-tick, 우선순위·빈도로 "누구 먼저"를 정하는 건 이 챕터 다음 → priority-updatefreq.
🌱 이 개념은 왜 생겼나 — 관련성(Relevancy)
• 원래 구조: 제일 단순하게 짜면, 월드에 떠 있는 액터를 전부 모든 클라한테 매 틱 보내. 몬스터 위치, 문 상태, 남의 총알까지 싹 다.
• 그런데 문제: 플레이어 500명 × 액터 수천 개면 보낼 짝이 곱셈으로 폭발해. 지도 반대편 몬스터 싸움까지 내 화면에 초당 수십 번 날아와 — 보이지도 않는데. 대역폭도 CPU도 그냥 샌다.
• 그래서 필요한 것: 액터마다 커넥션마다 "이거 이 사람한테 보낼 필요가 있나?"를 먼저 묻는 관문. 잔치 초대장을 소리 들릴 거리 안에만 돌리듯. → 이게 관련성(Relevancy)이고, 우리 서버 말로는 AOI(관심 영역) 판정이야.

1) 큰 그림 — 예외 먼저, 거리 나중

관련성 판정은 두 층으로 되어 있어. 순서가 중요해.

  1. 예외 규칙층 — "거리 따질 것도 없이 답이 정해진 경우"를 먼저 쳐낸다.
  • 항상 보내야 하는 애(bAlwaysRelevant)? → 무조건 관련 있음.
  • 내가 주인인 애(내 캐릭터, 내 총알)? → 무조건 관련 있음.
  • 주인한테만 보이는 애(bOnlyRelevantToOwner)인데 난 주인이 아냐? → 무조건 관련 없음.
  1. 거리 컷층 — 위에서 안 걸러졌으면, 마지막에 거리로 자른다.
  • 뷰어(플레이어 시야)와 액터 사이 거리가 컷 기준보다 멀면 → 관련 없음.

핵심은 "싸고 확실한 예외를 먼저, 비싼 거리계산은 맨 나중" 이라는 순서야. bAlwaysRelevant 같은 bool 체크는 거의 공짜고, 예외에서 답이 나면 거리계산 자체를 안 해도 되니까.

이걸 그림으로 보면 이래.

한 줄 요약: IsNetRelevantFor = 예외로 먼저 답 내고, 안 나면 거리로 자른다.

지금부터 진짜 언리얼 C++가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀고, 우리는 true가 되는 길과 false가 되는 길만 보면 돼.

🌱 이 개념은 왜 생겼나 — 거리 기반 컬링(NetCullDistanceSquared)
• 원래 구조: "관심 있냐"를 판정하는 제일 자연스러운 기준은 가까우면 보내고 멀면 안 보내기야. 그럼 뷰어랑 액터 사이 거리를 재야 해.
• 그런데 문제: 진짜 거리를 구하려면 마지막에 제곱근(sqrt)을 씌워야 하는데, 이걸 액터×커넥션 수천 번을 매 틱 돌리면 sqrt 비용이 산더미로 쌓여. 게다가 "몇 미터까지가 가까운 거야?"라는 기준선도 없으면 자를 수가 없어.
• 그래서 필요한 것: 컷 거리를 미리 정해 제곱값으로 저장해두고(그래서 이름 끝이 …Squared), 거리도 제곱인 채로 비교하는 것. sqrt를 통째로 아끼면서 "가깝냐"만 딱 판정하는 게 거리 컬링이야. 기본 제곱값을 풀면 150m.

2) 거리 컷의 심장 — DistSquared 한 줄

먼저 제일 밑바닥, 실제로 "가깝냐 머냐"를 재는 함수부터 봐. 놀랄 만큼 짧아.

[A] 거리 컷 본체 — Runtime/Engine/Private/ActorReplication.cpp:377-380

bool AActor::IsWithinNetRelevancyDistance(const FVector& SrcLocation) const { return FVector::DistSquared(SrcLocation, GetActorLocation()) < GetNetCullDistanceSquared(); }
🔤 기호 사전 — bool AActor::IsWithinNetRelevancyDistance(const FVector& SrcLocation) const
• bool = 답이 true/false 둘 중 하나라는 뜻. 여기선 "관련 거리 안이야?"에 대한 예/아니오.
• AActor:: = AActor에 딸린 함수라는 소속 표시. ::는 "~의 것"이라고 읽으면 돼.
• const FVector& SrcLocation = SrcLocation이라는 좌표 상자를 복사하지 않고 원본으로 빌려 보되, 안 바꾸겠다는 뜻. FVector는 3D 위치(x,y,z) 상자야.
• return = 이 줄의 계산 결과를 함수의 답으로 돌려준다.
• FVector::DistSquared(...) = 두 좌표 사이의 제곱 거리를 재는 도구. 진짜 거리 대신 제곱값으로 비교해서 빠르게 보려는 거야.
• < = 왼쪽 값이 오른쪽 값보다 작냐는 비교. 제곱 거리가 컷 기준보다 작으면 "가깝다".
• const = 이 함수가 액터 자신을 고치지 않는다는 약속.
🔁 이제 다시 보자. bool(예/아니오 답) → AActor::IsWithinNetRelevancyDistance(액터가 관련 거리 안인지 묻는 함수) → DistSquared(SrcLocation, GetActorLocation())(뷰어와 액터 사이 제곱 거리) → < GetNetCullDistanceSquared()(컷 기준보다 작은가). 이어 읽으면 "뷰어와 액터가 컷 거리 안이면 true를 돌려주는 함수"야.

읽는 법:

  • SrcLocation = 뷰어(보는 사람)의 월드 좌표.
  • GetActorLocation() = 이 액터의 월드 좌표.
  • 둘 사이 제곱 거리가 컷 기준값보다 작으면 → true(=AOI 안, 관련 있음).

여기서 초보가 딱 걸리는 게 하나 있어. 왜 DistSquared(제곱 거리)냐? 그냥 거리 재서 비교하면 되잖아.

예측 → 검증

빠르게 맞춰봐. 왜 실제 거리 대신 거리의 제곱으로 비교할까?

...

정답: sqrt(제곱근)를 피하려고. 두 점 사이 진짜 거리를 구하려면 √((x2-x1)² + (y2-y1)² + (z2-z1)²) 처럼 마지막에 제곱근을 씌워야 해. 그런데 제곱근 연산은 덧셈·곱셈보다 비싸. 근데 우린 정확한 거리 숫자가 필요한 게 아니라 "기준보다 머냐 가깝냐" 만 알면 되잖아?

그럼 양쪽 다 제곱인 채로 비교하면 돼. 거리 < 기준 이나 거리² < 기준² 이나 대소 관계는 똑같으니까(둘 다 양수라서). 그래서 컷 기준값도 아예 이름이 NetCullDistance**Squared** — 처음부터 제곱으로 저장해둬서 매번 제곱근 안 씌우고 바로 비교해. 판정 한 번에 sqrt 한 번씩 아끼는데, 이게 액터×커넥션 수천 번 돌면 무시 못 할 절약이야.

3) 컷 기준값 — 150m는 어디서 오나

그 비교 대상인 GetNetCullDistanceSquared()가 돌려주는 값이 어디서 세팅되는지 보자.

[E] 기본값 세팅 + 접근자 — Runtime/Engine/Private/Actor.cpp:310 그리고 6948-6959

SetNetCullDistanceSquared(225000000.0f);
🔤 기호 사전 — SetNetCullDistanceSquared(225000000.0f);
• SetNetCullDistanceSquared(...) = 네트워크 컬링 거리 기준값을 세팅하는 함수. 이름 끝의 Squared가 "제곱값을 넣어라"는 힌트야.
• 225000000.0f = 소수점 있는 float 숫자. 끝의 f는 "이 숫자는 float로 써"라는 표시야.
• ; = C++에서 한 문장 끝에 찍는 마침표.
🔁 이제 다시 보자. 이 한 줄은 "이 액터의 기본 관련 거리 컷을 225,000,000이라는 제곱값으로 맞춰둔다"야. 뒤에서 이 숫자를 √로 풀면 15,000cm, 즉 150m가 되는 거고.
void AActor::SetNetCullDistanceSquared(float DistanceSq) { PRAGMA_DISABLE_DEPRECATION_WARNINGS NetCullDistanceSquared = DistanceSq; PRAGMA_ENABLE_DEPRECATION_WARNINGS } float AActor::GetNetCullDistanceSquared() const { PRAGMA_DISABLE_DEPRECATION_WARNINGS return NetCullDistanceSquared; PRAGMA_ENABLE_DEPRECATION_WARNINGS }
🔤 기호 사전 — SetNetCullDistanceSquared / GetNetCullDistanceSquared
• void = 이 함수는 답을 돌려주지 않는다. 안에서 값만 바꿔놓고 끝.
• float DistanceSq = 소수점 숫자 하나를 DistanceSq라는 이름으로 받는다. 여기선 "거리의 제곱값"이야.
• NetCullDistanceSquared = DistanceSq = 오른쪽 값을 왼쪽 저장칸에 넣는다. 컷 기준 숫자를 실제 멤버 변수에 보관하는 줄.
• float AActor::GetNetCullDistanceSquared() const = AActor의 컷 기준 제곱값을 float로 돌려주는 함수. const라서 읽기만 하고 액터는 안 바꿔.
• return NetCullDistanceSquared = 저장해둔 컷 기준값을 그대로 답으로 내보낸다.
• PRAGMA_DISABLE_DEPRECATION_WARNINGS = "이 구간에서는 낡은 방식 경고를 잠깐 꺼줘"라는 컴파일러 지시문. 게임 로직이 아니라 경고 스위치야.
🔁 이제 다시 보자. 위쪽 Set...은 컷 기준값을 저장하고, 아래쪽 Get...은 저장된 컷 기준값을 꺼내 돌려준다. 그래서 거리 비교 줄은 매번 숫자를 새로 만들지 않고 GetNetCullDistanceSquared()로 이 저장값을 읽어 쓰는 거야.

기본값이 225000000.0f야. 이게 제곱값이라고 했지? 그럼 실제 거리로 되돌리면:

√225,000,000 = 15,000

언리얼에서 길이 1단위(uu)는 1cm야. 그러니까 15,000cm = 150m. 즉 "기본적으로 나한테서 150m 안쪽에 있는 액터만 나한테 보낸다" 는 뜻이야. 150m 밖 액터는 존재는 하지만 내 클라엔 안 와.

PRAGMA_DISABLE_DEPRECATION_WARNINGS 는 신경 안 써도 돼. 이 멤버 변수가 나중에 접근 방식이 바뀌면서 "직접 건드리지 마" 경고가 붙었는데, 접근자 안에서는 어쩔 수 없이 건드려야 하니까 그 경고만 잠깐 끈 거야. 로직이랑 무관.

값을 액터마다 다르게 줄 수도 있어. 큰 보스나 멀리서도 봐야 하는 랜드마크는 이 값을 키워서 더 멀리서도 보이게 하고, 자잘한 이펙트·장식물은 줄여서 가까이서만 보이게 해 대역폭을 아껴.

소스 주의: 이 NetCullDistanceSquared 멤버가 UPROPERTY로 선언된 Actor.h, 그리고 bUseDistanceBasedRelevancy를 담은 AGameNetworkManager 클래스 헤더는 이 클론에 .h가 배포 안 됐어(.cpp만 존재). 그래서 "에디터에 어떻게 노출되나"까지는 대조 못 했지만, 기본값·접근자·실제 사용처는 위 .cpp들에서 전부 확인했어.
🌱 이 개념은 왜 생겼나 — 예외 규칙 플래그(bAlwaysRelevant / bOnlyRelevantToOwner)
• 원래 구조: 관련성을 그냥 거리 하나로만 자르면 코드가 깔끔하지. 가까우면 보내고 멀면 끝.
• 그런데 문제: 거리로만 자르면 엉뚱한 게 잘려. 게임모드·매치상태는 지도 어디 있든 전원이 알아야 하고, 내 총알은 화면 밖으로 날아가도 주인인 나한텐 계속 와야 해. 반대로 남의 개인 UI 액터는 코앞이어도 나한텐 오면 안 되고.
• 그래서 필요한 것: 거리를 재기 전에 "무조건 보낸다 / 무조건 안 보낸다"를 먼저 정하는 예외 플래그. bAlwaysRelevant(전원), bOnlyRelevantToOwner(주인만) 같은 거. 싸고 확실한 예외를 먼저 쳐내고, 남은 애만 비싼 거리계산으로 넘겨.

4) 판정 본체 — 예외들이 먼저 손을 든다

이제 진짜 관문, IsNetRelevantFor 본체야. 앞부분(예외층)부터.

[B] 관련성 판정 본체 (앞) — Runtime/Engine/Private/ActorReplication.cpp:382-413

bool AActor::IsNetRelevantFor(const AActor* RealViewer, const AActor* ViewTarget, const FVector& SrcLocation) const { if (bAlwaysRelevant || IsOwnedBy(ViewTarget) || IsOwnedBy(RealViewer) || this == ViewTarget || ViewTarget == GetInstigator()) { return true; } else if (bNetUseOwnerRelevancy && Owner) { return Owner->IsNetRelevantFor(RealViewer, ViewTarget, SrcLocation); } else if (bOnlyRelevantToOwner) { return false; }
🔤 기호 사전 — bool AActor::IsNetRelevantFor(...)
• const AActor* = AActor를 가리키는 포인터인데, 그 액터를 여기서 고치지 않겠다는 뜻. *는 "실물 전체를 복사하지 말고 위치표만 들고 있다"에 가까워.
• || = OR. 조건들 중 하나라도 참이면 전체가 참이야.
• this == ViewTarget = "지금 이 액터가 카메라가 보고 있는 바로 그 대상이냐?"를 묻는 비교.
• return true = "관련 있음. 이 커넥션에 보내도 됨"이라고 즉시 답하고 함수 종료.
• else if = 앞 조건이 실패했을 때만 다음 조건을 이어서 검사한다.
• && = AND. 왼쪽도 참이고 오른쪽도 참이어야 통과. 여기선 플래그도 켜져 있고 Owner도 있어야 해.
• Owner->IsNetRelevantFor(...) = 주인 액터한테 같은 질문을 넘긴다. ->는 "그 포인터가 가리키는 것에게 시킨다"는 화살표야.
• return false = "관련 없음. 보내지 마"라고 즉시 답하고 함수 종료.
🔁 이제 다시 보자. 첫 if는 bAlwaysRelevant || IsOwnedBy(...) || this == ViewTarget ...라서 하나라도 특별한 이유가 있으면 바로 true야. 그게 아니고 bNetUseOwnerRelevancy && Owner면 주인한테 판단을 맡기고, 그래도 아니면서 bOnlyRelevantToOwner면 주인이 아닌 사람에게는 false가 된다. 거리는 아직 한 번도 안 쟀지?

첫 if 하나에 "무조건 보낸다" 케이스가 다섯 개 OR로 묶여 있어. 하나만 참이면 바로 return true — 거리는 쳐다도 안 봐.

  • bAlwaysRelevant — "난 항상 관련 있어" 플래그. 게임모드, 매치 상태 같은 전역 액터가 이걸 켜. 지도 어디 있든 전원한테 감.
  • IsOwnedBy(ViewTarget) / IsOwnedBy(RealViewer) — 이 액터의 주인이 지금 보는 사람이면. 예: 내 총알, 내 인벤토리 액터. 멀어도 주인한텐 보내야지.
  • this == ViewTarget — 이 액터가 바로 "지금 카메라가 보고 있는 대상"이면. 내가 조종하는 폰이 화면 밖으로 잘리면 안 되잖아.
  • ViewTarget == GetInstigator() — 이 액터를 유발한 주체가 곧 시야 대상이면(예: 내가 쏜 발사체의 instigator가 나).

그 다음 두 갈래:

  • bNetUseOwnerRelevancy && Owner — "내 관련성은 내 주인 걸 따라가" — 주인의 판정에 위임(재귀 호출). 무기가 캐릭터 관련성을 물려받는 식.
  • bOnlyRelevantToOwner — "난 주인한테만 의미 있어." 근데 위 첫 if에서 이미 "내가 주인이냐"를 걸렀는데도 여기 왔다는 건 난 주인이 아니라는 뜻 → return false. (남의 개인 UI 액터 같은 거.)
여기 붙는 분기가 하나 더 있어(소스엔 존재). 부착된 액터(다른 액터에 붙어있음)면 붙은 부모의 관련성을 따르고, 숨겨져 있고 충돌도 없는 액터면 false로 자르는 규칙. 리서처가 뽑은 verbatim [B]는 bOnlyRelevantToOwner까지라 여기선 개념만 짚고 넘어가. 요지는 "예외가 층층이 먼저 걸러진다" 는 것.

반전 — 예외를 다 통과하면 그제야 거리

예외에서 답이 안 나면? 그제서야 거리 컷으로 수렴해. 같은 함수의 꼬리야.

[C] 판정 본체 (꼬리) — 거리 컷으로 수렴 — Runtime/Engine/Private/ActorReplication.cpp:405-413

🔤 기호 사전 — if (!RootComponent) / 마지막 return
• !RootComponent = RootComponent가 없다는 뜻. !는 "아님/없음/실패"를 뒤집어 묻는 표시야.
• UE_LOG(LogNet, Warning, TEXT(...)) = 네트워크 로그에 경고를 남긴다. Warning은 게임을 죽이는 Fatal이 아니라 "이상하니 알려줌"에 가까워.

• ->bUseDistanceBasedRelevancy = 그 기본 설정 안의 거리 기반 관련성 스위치를 읽는다.
• || = OR. 왼쪽이 참이면 오른쪽은 볼 필요도 없이 참이야.
• IsWithinNetRelevancyDistance(SrcLocation) = 앞에서 본 거리 컷 함수. 컷 안이면 true, 밖이면 false.
🔁 이제 다시 보자. 먼저 if (!RootComponent)로 위치 기준이 없으면 경고 찍고 false. 그 다음 마지막 줄은 !bUseDistanceBasedRelevancy || IsWithinNetRelevancyDistance(...)라서 거리 컬링을 꺼놨으면 그냥 true, 켜놨으면 거리 안에 들어올 때만 true야. 예외를 다 지나온 액터의 최종 문이 여기야.

마지막 return 한 줄이 이 챕터의 결론이야. 풀어보면:

관련있음 = (거리기반컬링을 안 쓰거나) OR (거리 안에 들어왔거나)
  • 왼쪽 !...bUseDistanceBasedRelevancy — 프로젝트가 거리 컬링 스위치를 꺼놨으면 이게 true라, OR 단락으로 거리 안 재고 그냥 관련 있음. "거리로는 안 자르겠다"는 설정.
  • 오른쪽 IsWithinNetRelevancyDistance — 스위치가 켜져 있으면 그제야 §2의 그 DistSquared 비교를 실행. 가까우면 true, 멀면 false.

그 위의 if (!RootComponent) 는 방어 코드야. 위치가 있어야 거리를 재는데 위치를 담을 루트 컴포넌트가 없으면 거리 판정이 불가능 → 경고 로그 남기고 false. 로그 문구가 친절하게 "이런 거면 bAlwaysRelevant=true로 하지 그랬어?"라고 힌트까지 줘.

5) 누가 이걸 부르나 — 커넥션 단위 소비처

이 함수는 혼자 안 돌아. 서버 리플리케이션 루프가 커넥션마다 불러. 그 진입점이 이거야.

[D] 커넥션 단위 소비처 — Runtime/Engine/Private/NetDriver.cpp:5266-5277

static FORCEINLINE_DEBUGGABLE bool IsActorRelevantToConnection( const AActor* Actor, const TArray<FNetViewer>& ConnectionViewers ) { for ( int32 viewerIdx = 0; viewerIdx < ConnectionViewers.Num(); viewerIdx++ ) { if ( Actor->IsNetRelevantFor( ConnectionViewers[viewerIdx].InViewer, ConnectionViewers[viewerIdx].ViewTarget, ConnectionViewers[viewerIdx].ViewLocation ) ) { return true; } } return false; }
🔤 기호 사전 — static FORCEINLINE_DEBUGGABLE bool IsActorRelevantToConnection(...)
• static = 이 파일 안에서 쓰는 도우미 함수처럼 보면 돼. 액터 하나에 딸린 멤버 함수가 아니라 바깥 보조 함수야.
• FORCEINLINE_DEBUGGABLE = 컴파일러에게 "짧게 펼쳐 넣어도 좋고, 디버그도 가능하게 해줘"라고 힌트 주는 UE 매크로.
• const AActor* Actor = 검사할 액터를 가리키는 포인터. 여기서 액터를 고치지 않겠다는 const가 붙어 있어.
• const TArray<FNetViewer>& ConnectionViewers = 이 커넥션의 뷰어 목록을 원본으로 빌려 본다. TArray<X>는 X들이 줄 서 있는 리스트야.
• for (...) = 목록을 처음부터 끝까지 하나씩 훑는 반복문.
• viewerIdx++ = 검사한 뒤 번호를 1 올린다. 다음 뷰어 칸으로 넘어가는 발걸음.
• ConnectionViewers[viewerIdx] = 뷰어 목록에서 viewerIdx번째 칸을 꺼낸다. []는 "몇 번째 칸"이야.
• Actor->IsNetRelevantFor(...) = 액터에게 "이 뷰어에게 너 관련 있니?"라고 묻는다.
🔁 이제 다시 보자. for가 ConnectionViewers를 하나씩 돌고, 각 칸마다 Actor->IsNetRelevantFor(...)를 묻는다. 하나라도 true면 바로 return true; 끝까지 아무도 관심 없으면 마지막 return false. 한 커넥션 안에 시야가 여러 개 있어도 하나라도 보면 보낸다는 코드야.

ConnectionViewers 가 여럿인 이유는 화면분할(split-screen) 때문이야. 한 커넥션(한 콘솔)에 두 명이 같이 붙어 플레이하면 시야가 둘. 그중 하나한테라도 관련 있으면 즉시 true — "누구 하나라도 봐야 하면 보낸다." 아무한테도 관련 없어야 비로소 false.

바로 위 함수 이름 붙은 주석도 정확히 그 말이야: *"Returns true if this actor should replicate to \*any\* of the passed in connections."*

그리고 흥미로운 곳이 하나 더 있어. 멀티캐스트 RPC를 쏘기 직전에도 (NetDriver.cpp:8034 근처) 똑같은 IsNetRelevantFor로 커넥션별 관련성을 다시 확인해. "전체에 방송(멀티캐스트)"이라고 해도 관련 없는 클라엔 안 쏴. 방송이 곧 전원 강제가 아니라, 관련성 필터를 한 번 더 거친다는 거지. RPC 종류가 헷갈리면 → rpc-types.

6) 우리 서버와 비교 — IOCP 워커 vs 싱글스레드 AOI

우리 조선 서버(C++)로 번역하면 이래.

핵심 차이: UE는 "보낼지 말지 결정하는 로직 자체가 프레임 안(싱글스레드)"에 있어. 우리처럼 "로직 스레드가 대상 뽑아 큐에 던지고 IOCP 워커가 나른다"의 그 대상 뽑기 = 관련성 판정 단계가, UE에선 매 틱 IsNetRelevantFor로 액터마다 커넥션마다 정밀하게 돌아가는 거야. IOCP 워커는 UE에서도 어차피 바이트질만 해 — 관련성은 그 위층 결정이라 스레드 모델이 달라도 개념은 1:1로 대응돼.

그리고 우리가 겪은 팔도점령전 유니온 킬카운트 폭주 사고(msg 2334, 전 36서버가 몹 처치마다 유니온 전체에 sync) 기억나? 그게 관련성 필터 없이 전원 강제 전송의 전형적 참사야. UE 식으로 보면 그 sync 액터에 좁은 NetCullDistanceSquared를 줘서 "관심 있는 커넥션한테만" 걸렀을 거고, 애초에 IsNetRelevantFor가 관계없는 커넥션을 컷했을 거야. "관심 없는 대상은 안 보낸다" — 이 한 줄이 있고 없고가 프레임 붕괴를 가른 거지.

7) 초보가 헷갈리는 용어 6개

  • Relevancy(관련성): 서버가 "이 액터를 이 클라에 보낼 필요가 있나"를 판정하는 것. 우리 AOI 판정과 같은 개념. IsNetRelevantFor가 그 관문.
  • NetCullDistanceSquared (float, 기본 225,000,000): 거리 컬링 컷 기준값. 제곱 거리라 √씌우면 15,000cm=150m. 제곱을 쓰는 이유는 sqrt 회피(비용 절감). 값을 키우면 더 멀리서도 보이고, 줄이면 대역폭 절약.
  • RealViewer / ViewTarget / SrcLocation: 판정의 시야 기준 3종. RealViewer=실제 관찰 주체(보통 PlayerController), ViewTarget=카메라가 보고 있는 액터, SrcLocation=그 시야의 월드 좌표(거리 계산의 원점).
  • bAlwaysRelevant: "거리 무시하고 전원한테 보내" 플래그. 게임모드·매치상태 같은 전역 액터용. IsNetRelevantFor 첫 줄에서 즉시 true.
  • bOnlyRelevantToOwner: "주인한테만 의미 있어" 플래그. 내가 주인이 아니면 즉시 false. 남의 개인 UI/인벤토리 액터가 나한테 안 오게.
  • bUseDistanceBasedRelevancy (AGameNetworkManager): 프로젝트 전역 스위치. false면 거리 컬링 자체를 꺼서, 예외 규칙만으로 판정하고 거리로는 안 자름. (헤더 미배포 — .cpp 사용처로만 확인.)

Q1. Relevancy(관련성)는 왜 필요한가요?

답 보기
월드엔 액터가 수천 개 떠 있는데, 지도 반대편 몬스터 싸움을 여기 있는 내 클라에 초당 수십 번 보낼 이유가 없어. 화면에 보이지도 않는데 그건 그냥 트래픽 낭비야. 안 거르면 플레이어 500명 × 액터 수천 개면 보낼 짝이 곱셈으로 폭발해서 대역폭도 CPU도 샌다. 그래서 액터마다 커넥션마다 "이거 이 사람한테 보낼 필요 있나?"를 먼저 묻는 관문이 Relevancy야. 우리 서버 말로는 AOI(관심 영역) 판정 그거랑 똑같아.

↳ 안 거르면 구체적으로 어디가 먼저 터지나요?

답 보기
양쪽 다 터져. 보내는 서버는 IOCP 워커가 WSASend 일감에 깔리고 커넥션 send 큐가 불어나. 받는 클라도 화면에 안 보이는 남의 전투 조각을 계속 받으면 게임이 아니라 우체통 정리부터 하게 돼. 우리 팔도점령전 유니온 킬카운트 폭주 사고 있잖아 — 몹 처치마다 유니온 전체에 sync 뿌린 거. 그게 관련성 필터 없이 전원 강제 전송의 전형적 참사야.

Q2. 판정은 큰 그림에서 어떤 순서로 도나요?

답 보기
두 층인데 순서가 핵심이야. 예외 먼저, 거리 나중. 먼저 "거리 따질 것도 없이 답이 정해진 경우"를 쳐내 — 항상 보내야 하는 액터(bAlwaysRelevant), 내가 주인인 액터, 주인한테만 보이는데 난 주인이 아닌 경우. 여기서 답이 안 나면 그제서야 마지막에 거리로 잘라. 이유는 bool 체크는 거의 공짜인데 거리 계산은 비싸거든. 싸고 확실한 예외를 먼저 걸러서 비싼 거리 계산 자체를 안 하게 하는 거야.

↳ 왜 실제 거리 대신 거리의 제곱(DistSquared)으로 비교하나요?

답 보기
sqrt(제곱근)를 피하려고. 진짜 거리를 구하려면 마지막에 제곱근을 씌워야 하는데 그게 덧셈·곱셈보다 비싸. 근데 우린 정확한 거리 숫자가 필요한 게 아니라 "기준보다 머냐 가깝냐"만 알면 되잖아. 그럼 양쪽 다 제곱인 채로 비교해도 대소 관계는 똑같아(둘 다 양수라). 그래서 컷 기준값도 이름이 NetCullDistanceSquared — 처음부터 제곱으로 저장해둬. 판정 한 번에 sqrt 한 번씩 아끼는데, 액터×커넥션 수천 번 돌면 무시 못 할 절약이야.

↳ 기본 컷 거리 150m는 어디서 나온 숫자예요?

답 보기
기본값이 225,000,000인데 이게 제곱값이야. √225,000,000 = 15,000. 언리얼에서 1단위(uu)가 1cm니까 15,000cm = 150m. 즉 "기본적으로 나한테서 150m 안쪽 액터만 나한테 보낸다"는 뜻이지. 액터마다 다르게 줄 수도 있어 — 큰 보스나 랜드마크는 값을 키워 멀리서도 보이게, 자잘한 이펙트는 줄여 가까이서만 보이게 해 대역폭을 아껴.

Q3. "무조건 보낸다" 같은 예외 플래그는 왜 있어요? 거리 하나로만 자르면 깔끔하지 않나요?

답 보기
거리로만 자르면 엉뚱한 게 잘려서야. 게임모드·매치상태는 지도 어디 있든 전원이 알아야 하는데 거리로 자르면 멀리 있는 사람이 매치 상태를 못 받아. 내 총알은 화면 밖으로 날아가도 주인인 나한텐 계속 와야 하고. 반대로 남의 개인 UI 액터는 코앞이어도 나한텐 오면 안 돼. 그래서 거리를 재기 전에 "무조건 보낸다(bAlwaysRelevant) / 무조건 안 보낸다(bOnlyRelevantToOwner)"를 먼저 정하는 예외 플래그가 필요한 거야.

↳ 프로젝트가 거리 컬링 스위치를 꺼두면 어떻게 되나요?

답 보기
거리로는 안 잘라. 최종 판정이 "거리기반컬링을 안 쓰거나 OR 거리 안에 들어왔거나"라서, 스위치가 꺼져 있으면 왼쪽이 참이 돼 거리 안 재고 그냥 관련 있음으로 통과해. 즉 예외 규칙만으로 판정하고 거리로는 안 거르는 모드가 되는 거지. 스위치가 켜져 있을 때만 그 DistSquared 비교가 실제로 돌아.

Q4. 이 판정은 누가, 언제 부르나요? 액터가 알아서 도는 건가요?

답 보기
혼자 안 돌아. 서버 리플리케이션 루프가 커넥션마다 불러. 한 커넥션 안에 시야(뷰어)가 여러 개일 수 있어 — 화면분할이면 한 콘솔에 두 명이 붙으니 시야가 둘이지. 그중 하나한테라도 관련 있으면 즉시 보냄. 아무한테도 관련 없어야 비로소 안 보내. "누구 하나라도 봐야 하면 보낸다"가 규칙이야.

↳ 멀티캐스트 RPC는 전체 방송이니까 관련성이랑 상관없지 않나요?

답 보기
아니야, 멀티캐스트도 쏘기 직전에 커넥션별로 IsNetRelevantFor를 다시 확인해. "전체에 방송"이라고 해도 관련 없는 클라엔 안 쏴. 방송이 곧 전원 강제가 아니라 관련성 필터를 한 번 더 거치는 거지. 지구 반대편 플레이어한테까지 폭발을 보낼 필욘 없잖아.

↳ Pawn이나 PlayerController는 이 함수를 오버라이드하던데, 그럼 판정이 완전히 달라지나요?

답 보기
예외 규칙만 몇 개 더 얹지, 최종 관문은 똑같아. Pawn·PlayerController가 자기만의 규칙을 앞에 추가해도 꼬리는 전부 같은 거리 컷으로 수렴해 — 코드가 글자 하나 안 틀리고 똑같아. "예외 규칙은 클래스마다 다르게 추가하되 거리 컷이라는 최종 관문은 하나로 공유한다"가 이 설계의 예쁜 부분이야.

🎯 원리 한 줄 요약

IsNetRelevantFor는 bAlwaysRelevant·소유·부착 같은 싸고 확실한 예외를 먼저 쳐내고, 안 걸러진 액터만 마지막에 DistSquared(뷰어,액터) < NetCullDistanceSquared(제곱 비교로 sqrt를 아낀 기본 150m)로 잘라 — "관심 영역(AOI) 밖의 관심 없는 대상은 아예 안 보내" 유한한 대역폭을 지킨다.
