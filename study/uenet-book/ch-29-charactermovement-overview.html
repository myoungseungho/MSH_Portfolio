CharacterMovement: 이동 복제의 심장

언리얼 네트워크 · 29 / 42

0) 들어가며 — 택배가 오기 전에 먼저 문을 여는 사람

너 게임에서 캐릭터 움직여봤지. 방향키 누르면 캐릭터가 즉시 움직여. 안 끊기고, 안 기다리고.

근데 잠깐. 이거 멀티플레이야. 서버가 진짜 원본이잖아. 그럼 원래대로면 이래야 정상 아냐?

방향키 누름 → 서버한테 "나 앞으로 갈래" 전송 → 서버가 "그래 가" 답장 → 그제서야 캐릭터 움직임

이러면 핑이 100ms면 방향키 누르고 0.1초 뒤에 캐릭터가 움직여. 렉걸린 것처럼. 아무도 이런 게임 안 해.

그래서 UE는 다르게 해. 클라가 서버 답을 안 기다려. 방향키 누르는 순간 클라가 자기 혼자 먼저 캐릭터를 움직여버려(=예측). 그리고 "나 이렇게 움직였어"를 서버한테 뒤늦게 보고해. 서버는 그걸 받아서 똑같이 재현해보고, 클라가 맞게 움직였으면 그냥 넘어가고, 어긋났으면(벽 통과 같은 치트나 오차) "야 너 사실 여기 있어야 해" 하고 정답을 되돌려줘. 클라는 그 정답으로 슬쩍 되감아.

이게 바로 택배 오기 전에 먼저 문 여는 사람이야. 초인종 누르는 소리 들리면 택배가 문 앞에 온 걸 예측하고 미리 문을 열어. 대부분 맞아. 가끔 아니면(옆집 초인종이었으면) 다시 닫으면 돼. 이 "미리 열기"가 지연을 숨기는 핵심 마술이고, 이걸 실제로 구현하는 게 이 챕터의 주인공 CharacterMovementComponent(CMC) 야.

전제는 링크로만 건다. RPC가 뭔지 흐릿하면 → rpc-types, "이 RPC는 이 클라만 보낸다"는 소유권 개념은 → rpc-ownership, 남의 캐릭터를 복제받는 큰 그림은 → server-replicate-actors.

🔬 소스 절반만 포함됨 — 심장은 이 클론에 없다

이 챕터는 다른 챕터랑 사정이 좀 달라. 먼저 사실부터 정직하게 깔고 간다.

CMC의 진짜 심장 — Runtime/Engine/Private/Components/CharacterMovementComponent.cpp(약 1만 줄) — 이 파일이 이 클론 트리에 없어. find로 안 나와. 그 안에 들어있는 이동 복제의 실제 로직들:

  • ReplicateMoveToServer / CallServerMovePacked — 클라가 무브를 서버로 보내는 본체
  • ServerMove_PerformMovement / ServerMovePacked_ServerReceive — 서버가 받아서 재현·검증하는 본체
  • SendClientAdjustment / ClientUpdatePositionAfterServerUpdate — 어긋났을 때 되돌리는 본체
  • SavedMove_Character, FNetworkPredictionData_Client_Character — 예측용 무브 기록 자료구조

이것들 본체는 못 읽어. 이유는 단순해 — 이 학습 트리는 Engine/Source를 일부만 클론한 상태라 CMC 본체 파일이 안 딸려왔어.

그럼 뭘 읽을 수 있냐. 인터페이스(계약)와 주변부는 실물로 있어:

파일줄수이 챕터에서 읽는 것
Character.cpp2018이동 RPC들의 선언·위임 계층(thunk) + 시뮬레이트 프록시 수신 본체
CharacterMovementComponentAsync.cpp4639물리스레드(Chaos)용 이동 시뮬레이션 본체
CharacterMovementComponentAsync.h662위 async의 입출력 구조체·함수 선언

경로 프리픽스: .../Runtime/Engine/Private/ (Async.h만 .../Public/).

그래서 이 챕터의 전략은 이거야: 본체 대신 "계약서"를 읽는다. RPC가 어떤 파라미터로 서버에 뭘 보내는지(시그니처), 남의 캐릭터를 어떻게 부드럽게 받는지(스무딩), 물리 시뮬레이션이 Role별로 어떻게 갈리는지 — 이 세 개는 실물 코드로 확인 가능하고, 그걸로 큰 그림은 충분히 그려져. 심장 근육의 세밀한 수축은 다음 챕터들(client-prediction, server-reconciliation)에서 개념으로 이어붙인다.

아래 코드블록은 전부 위 세 파일에서 한 글자도 안 바꾸고 가져왔고 file:line을 붙였어. 직접 대조도 마쳤음.

1) 큰 그림 — 세 명의 배우가 있다

CMC를 이해하려면 먼저 "누가 이 캐릭터를 보고 있냐"를 세 종류로 갈라야 해. 이걸 Role(역할) 이라고 불러. 같은 캐릭터라도 어느 컴퓨터에서 보느냐에 따라 완전히 다른 코드가 돈다.

내 컴퓨터에서 "내가 조종하는 내 캐릭터" → AutonomousProxy (자율 프록시) → 서버 안 기다리고 먼저 움직임(예측) + ServerMove로 서버에 보고 서버 컴퓨터에서 본 "모든 캐릭터의 원본" → Authority (권위) → 클라 보고를 재현·검증, 어긋나면 ClientAdjustPosition으로 정답 회신 내 컴퓨터에서 "남이 조종하는 남 캐릭터" → SimulatedProxy (시뮬레이트 프록시) → 서버가 복제해준 위치를 받아 SmoothCorrection으로 부드럽게 흉내

핵심은 이거야. 하나의 캐릭터 인스턴스가 컴퓨터마다 다른 Role을 갖는다. 내 화면의 내 캐릭터는 AutonomousProxy, 그 똑같은 캐릭터가 서버에선 Authority, 친구 화면에선 SimulatedProxy. 세 배우가 같은 대본(CMC)의 다른 페이지를 읽는 셈이야.

맞춰봐: 그럼 SimulatedProxy(남 캐릭터)도 예측을 할까? 방향키 입력이 없으니 뭘 예측하겠어… 라고 생각하기 쉬운데. 반전 — 얘도 일종의 추정을 해. 서버 패킷은 띄엄띄엄(예: 초당 10~30번) 오는데 화면은 60fps로 그려야 하니까, 마지막 받은 위치에서 보간(SmoothCorrection) 으로 그 사이를 메꿔. 입력 예측은 아니지만 "빈 프레임 메꾸기"는 해. 이건 → simulated-proxy-smoothing에서 깊게 판다.

2) 콜체인 — 이동이 흐르는 순서 (파일별 검증됨)

아래가 실제 함수들이 불리는 순서야. 회색 점선 박스는 이 클론에 본체가 없는 구간(정통 CMC.cpp), 실선 박스는 실물로 읽히는 구간이야.

읽는 법: 왼쪽 세로줄이 시간이야. 클라가 먼저 움직이고(1) → 서버에 보고(2) → 서버가 틀렸다 판정하면 정답 회신(3). 남의 캐릭터(맨 아래 박스)는 이 예측/보정 사이클과 무관하게, 그냥 복제받은 위치를 부드럽게 보간만 해.

3) Verbatim 스니펫 — 계약서를 읽는다

3-1. 클라 → 서버 이동 보고 RPC (thunk)

여기서 딱 알아야 할 건 "ACharacter에 선언은 있는데, 몸통은 CMC로 넘긴다" 는 패턴이야. RPC는 문법상 Actor에 붙어야 해서(RPC는 AActor 계보에서만 선언 가능) ACharacter에 얹혀있지만, 실제 로직은 전부 GetCharacterMovement()->...로 위임돼. 그래서 Character.cpp의 이동 RPC들은 죄다 한 줄짜리 전달책이야.

[스니펫 1] 패킹된 이동 RPC의 위임 구조 — Character.cpp:1856–1866

// ServerMovePacked void ACharacter::ServerMovePacked_Implementation(const FCharacterServerMovePackedBits& PackedBits) { GetCharacterMovement()->ServerMovePacked_ServerReceive(PackedBits); } bool ACharacter::ServerMovePacked_Validate(const FCharacterServerMovePackedBits& PackedBits) { // Can't really validate the bit stream without unpacking, and that is done in ServerMovePacked_ServerReceive() and can be rejected after unpacking. return true; }

_Validate가 return true인 게 중요해. 보통 RPC의 _Validate는 "이 파라미터 값이 말이 되냐"를 서버에서 검사해서 치트를 걸러(→ rpc-reliable-validation). 근데 여기선 데이터가 비트스트림으로 압축된 상태라 풀어보기 전엔 검증이 불가능해. 그래서 "일단 통과시키고, 언팩한 뒤 ServerReceive 안에서 진짜 검증한다"는 주석이 달려있어. 검증을 포기한 게 아니라 뒤로 미룬 거야.

[스니펫 2] 구형 ServerMove RPC — 파라미터 전체가 "무브 한 개"의 정의 — Character.cpp:1868–1877

// ServerMove void ACharacter::ServerMove_Implementation(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { GetCharacterMovement()->ServerMove_Implementation(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); } bool ACharacter::ServerMove_Validate(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { return GetCharacterMovement()->ServerMove_Validate(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

이 파라미터 목록 자체가 "클라가 서버한테 자기 이동을 설명하는 문법" 이야. 하나씩 봐:

  • TimeStamp — "이 무브는 내 시계로 몇 초에 일어났어" (서버가 순서 맞추고 되감기의 기준으로 씀)
  • InAccel — 내가 준 가속도(=방향키 입력을 힘으로 바꾼 것). FVector_NetQuantize10으로 압축.
  • ClientLoc — 예측 결과 "나 지금 여기 있어". FVector_NetQuantize100으로 압축. 서버가 이 값과 자기 재현 결과를 비교해서 어긋남을 판정해.
  • CompressedMoveFlags — 점프/웅크리기 같은 bool 입력들을 1바이트에 비트로 눌러담은 것.
  • ClientMovementBase / ClientMovementMode — "나 지금 움직이는 발판(엘리베이터 등) 위에 있어 / 걷는 중이야 나는 중이야" 상태.

신형(패킹) vs 구형(비패킹) 차이도 딱 잡고 가. 스니펫 1은 이 파라미터들을 전부 하나의 비트스트림으로 눌러담아 대역폭을 더 아낀 버전이고, 스니펫 2는 파라미터를 날것 그대로 나열한 옛 버전이야. 최신 엔진은 스니펫 1(Packed)을 기본으로 써.

3-2. 서버 → 클라 보정 RPC (thunk)

서버가 "네 예측 틀렸어" 판정하면 아래 중 하나로 정답을 되돌려줘. 셋의 차이는 오차 크기에 따라 얼마나 실어보내냐야.

  • ClientAdjustPosition_Implementation — Character.cpp:1953 — 위치 + 속도 + 발판까지 풀세트로 되돌림(일반 보정).
  • ClientVeryShortAdjustPosition_Implementation — Character.cpp:1959 — 오차가 작을 때 위치만 보내는 경량판.
  • ClientAdjustRootMotionPosition_Implementation — Character.cpp:1965 — 루트모션(몽타주 애니로 이동 중)일 때 애니 트랙 위치까지 포함해 보정(→ root-motion-replication).

이 셋도 전부 GetCharacterMovement()->...로 위임하는 thunk야(스니펫 1·2와 같은 패턴). 되감기 본체는 미포함.

3-3. 남 캐릭터 받기 — 여기만 본체가 실물이다

[스니펫 3] SimulatedProxy 위치 수신과 스무딩 — Character.cpp:1589–1608

void ACharacter::PostNetReceiveLocationAndRotation() { if(GetLocalRole() == ROLE_SimulatedProxy) { // Don't change transform if using relative position (it should be nearly the same anyway, or base may be slightly out of sync) if (!GetReplicatedBasedMovement().HasRelativeLocation()) { const FRepMovement& ConstRepMovement = GetReplicatedMovement(); const FVector OldLocation = GetActorLocation(); const FVector NewLocation = FRepMovement::RebaseOntoLocalOrigin(ConstRepMovement.Location, this); const FQuat OldRotation = GetActorQuat(); CharacterMovement->bNetworkSmoothingComplete = false; CharacterMovement->bJustTeleported |= (OldLocation != NewLocation); CharacterMovement->SmoothCorrection(OldLocation, OldRotation, NewLocation, ConstRepMovement.Rotation.Quaternion()); OnUpdateSimulatedPosition(OldLocation, OldRotation); } CharacterMovement->bNetworkUpdateReceived = true; } }

여기가 핵심 대비야. AutonomousProxy(내 캐릭터)는 "예측→서버보고→보정" 사이클을 도는데, SimulatedProxy(남 캐릭터)는 그냥 서버 위치를 받아서 SmoothCorrection으로 부드럽게 옮기기만 해. NewLocation으로 순간이동시키면 남 캐릭터가 뚝뚝 끊겨 보이니까(패킷이 띄엄띄엄 오니까), 옛 위치(OldLocation)에서 새 위치로 몇 프레임에 걸쳐 미끄러뜨리는 거야. bNetworkSmoothingComplete = false가 "아직 미끄러지는 중"이라는 표시.

[스니펫 4] 서버측: 복제 직전 이동 상태를 긁어담기 — Character.cpp:1320–1338

void ACharacter::GatherCurrentMovement() { Super::GatherCurrentMovement(); if (IsReplicatingMovement()) { FRepMovement& MutableRepMovement = GetReplicatedMovement_Mutable(); if (ShouldReplicateAcceleration()) { MutableRepMovement.bRepAcceleration = true; MutableRepMovement.Acceleration = CharacterMovement->GetCurrentAcceleration(); } else { MutableRepMovement.bRepAcceleration = false; } } }

이건 서버가 남들한테 이 캐릭터를 뿌리기 직전, 현재 이동 상태(여기선 가속도)를 RepMovement라는 복제용 봉투에 담는 단계야. 가속도까지 복제하면 SimulatedProxy 쪽에서 "이 캐릭터 지금 가속 중이니 다음 프레임엔 더 갈 거야"를 짐작해 보간 품질을 높일 수 있어. 이 봉투(FRepMovement)가 스니펫 3의 GetReplicatedMovement()로 반대편에서 열리는 거고. 송신(스니펫 4) ↔ 수신(스니펫 3)이 짝이라는 걸 봐둬.

3-4. 물리 시뮬레이션 본체 — 단, 여기 함정이 있다

CharacterMovementComponentAsync.cpp는 물리스레드(Chaos)에서 도는 이동 시뮬레이션 본체야. 이 파일은 실물로 있어. 근데 네트워크 부분이 아직 이식이 안 된 물리-단독 버전이야. 그게 코드 주석에 그대로 드러나.

이 주석 처리된 else if가 이 챕터 전체의 지도야. 정상(네트워크 이식된) 버전이었다면 여기서 갈렸을 거야:

  • 서버(Authority)면 → PerformMovement로 진짜 이동 실행
  • 클라(AutonomousProxy)면 → ReplicateMoveToServer로 서버에 보고 (= 스니펫 1·2의 RPC를 쏘는 그 지점)

즉 스니펫 1·2의 ServerMove RPC가 "어디서 발사되냐"의 답이 바로 이 주석 속 ReplicateMoveToServer야. 지금은 주석이라 안 갈리고 무조건 PerformMovement(물리)만 도는 거고. 주석이 오히려 원래 설계를 친절하게 보여주는 셈.

PerformMovement부터 아래로는 순수 물리야 — StartNewPhysics(Async.cpp:669)에서 MovementMode로 갈려 PhysWalking(725)/PhysFalling(972)로, 속도는 CalcVelocity(2120)가 마찰·감속으로 계산해. 이 물리 적분은 네트워크와 무관하게 세 Role 모두 공통으로 돌아(서버는 재현하려고, 클라는 예측하려고, 둘 다 같은 물리 공식을 써야 결과가 일치하니까). 이 "같은 공식을 양쪽이 돌린다"가 예측이 성립하는 대전제야.

4) 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선협객전 서버 감각으로 번역하면 이래.

클라 예측 = "낙관적 처리(optimistic)". 우리가 CM_ 패킷 받으면 서버가 검증하고 DB 반영하고 SM_로 답을 줘야 클라가 결과를 아는 구조지(비관적). CMC는 반대야 — 클라가 먼저 결과를 확정해버리고, 서버 검증은 뒤따라와서 틀렸을 때만 롤백해. 우리로 치면 "거래 요청 오면 일단 클라 화면엔 성공으로 보여주고, 서버 검증 실패하면 그때 되돌리는" 방식. 이동처럼 초당 수십 번 + 지연 민감한 데이터에서만 감수하는 트레이드오프야.

서버의 재현·검증 = "우리 싱글스레드 액터 루프". 우리 Game 서버가 패킷을 메인 스레드 하나에서 순서대로 처리하듯, CMC 서버쪽도 ServerMove를 TimeStamp 순서대로 재현해. 순서가 뒤섞이면 되감기 기준(TimeStamp)이 깨지니까. 이 "타임스탬프 순차 처리"가 우리 싱글스레드 액터의 순차성과 정확히 같은 이유(경합 방지)로 존재해.

RPC 수신부 검증 미룸 = "우리 IOCP 워커의 raw 바이트 검증". 스니펫 1에서 _Validate가 비트스트림을 못 풀어서 검증을 뒤로 미뤘지. 이건 우리가 IOCP 워커에서 raw 패킷 바이트를 받았을 때, 언팩 전엔 필드 검증을 못 하고 파싱 후에 값 범위를 확인하는 거랑 똑같아. 압축된 바이트는 풀어야 검증한다 — 프로토콜 공통 원리야.

차이도 하나. 우리 서버는 이동을 서버가 100% 권위로 계산(클라는 그냥 요청)하지만, UE는 지연 숨김 때문에 클라에 계산을 위임하고 서버는 감사관이 돼. 그만큼 서버 검증(→ server-reconciliation)과 되감기 보안(→ lag-compensation, security)이 훨씬 정교해야 해.

5) 헷갈리는 용어 딱 정리

  • CMC (UCharacterMovementComponent) — ACharacter에 붙는 이동 전담 컴포넌트. 걷기/낙하/수영/점프의 물리 적분 + 네트워크 예측·보정을 다 담당. RPC는 문법상 ACharacter에 선언되지만 실제 로직은 CMC에 있어서, Character.cpp의 이동 RPC가 전부 GetCharacterMovement()->...로 넘긴다(스니펫 1·2).
  • Role (LocalRole) — 이 캐릭터를 지금 이 컴퓨터에서 어떤 자격으로 보고 있냐. Authority(서버 원본) / AutonomousProxy(내가 조종, 예측+보고) / SimulatedProxy(남이 조종, 복제받아 보간). 같은 캐릭터가 컴퓨터마다 다른 Role을 가짐. Simulate()가 이 Role로 코드 경로를 가른다(스니펫 5).
  • 클라 예측(Client Prediction) — 클라가 서버 응답을 안 기다리고 자기 입력을 즉시 이동에 반영. 지연 은폐의 핵심. 깊게는 → client-prediction.
  • 서버 보정(ServerMove / ClientAdjustPosition) — 클라가 ServerMove로 보고 → 서버가 재현·검증 → 어긋나면 ClientAdjustPosition으로 정답 회신 → 클라 되감기. 깊게는 → server-reconciliation.
  • FVector_NetQuantize10 / NetQuantize100 — 대역폭 절약용으로 float 벡터의 정밀도를 줄여(소수 1자리 / 2자리 스케일) 압축 전송하는 타입. ServerMove의 InAccel(10)·ClientLoc(100)에 쓰임(스니펫 2).
  • CompressedMoveFlags — 점프·웅크리기 등 bool 이동 입력들을 uint8 한 바이트에 비트로 눌러담은 압축 플래그. ServerMove에 함께 실려감.
  • SmoothCorrection / bNetworkSmoothingComplete — SimulatedProxy가 서버 좌표를 받을 때 순간이동처럼 튀지 않게 몇 프레임에 걸쳐 시각적으로 미끄러뜨리는 처리. bNetworkSmoothingComplete = false는 "아직 미끄러지는 중"(스니펫 3). 깊게는 → simulated-proxy-smoothing.
  • FRepMovement — 이동 상태(위치·회전·속도·가속도 등)를 복제로 실어나르는 봉투 구조체. 서버가 GatherCurrentMovement로 담고(스니펫 4), 수신측이 GetReplicatedMovement로 연다(스니펫 3).

6) 참조 링크

  • 막히면 → rpc-types (RPC 개념), rpc-ownership (이 RPC를 누가 보내나), rpc-reliable-validation (서버 검증), server-replicate-actors (남 캐릭터 복제 큰 그림)
  • 이어서 → client-prediction (클라가 먼저 움직이는 심장 로직), server-reconciliation (서버가 틀림을 잡아 되돌리는 로직), simulated-proxy-smoothing (남 캐릭터 보간), root-motion-replication (애니 이동 보정)
  • 다음 → client-prediction (이번 챕터가 "누가 무엇을 주고받나"였다면, 다음은 "클라가 어떻게 먼저 확정하고 되감을 무브를 기록하나"의 심장)
