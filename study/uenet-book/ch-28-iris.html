Iris: Epic이 복제를 새로 만든 이유

언리얼 네트워크 · 28 / 42

0) 들어가며 — 김밥을 100명한테 나눠줄 때

김밥집 사장님이 있어. 손님 100명이 똑같은 김밥을 주문했어. 어떻게 만들까?

방법 A: 손님이 올 때마다 그 자리에서 재료 썰고 밥 짓고 말아. 100번 처음부터. 방법 B: 재료를 미리 딱 한 번 손질해서 김밥 완성해두고, 손님 오면 그냥 썰어서 담기만 해.

당연히 B가 빠르지. "무거운 준비(재료 손질)를 한 번만" 하고, 그 결과물을 여러 손님이 나눠 쓰는 거야.

레거시 UE 복제(지금까지 배운 RepLayout/ActorChannel 방식)는 사실 방법 A에 가까웠어. 커넥션(손님)마다 액터 상태를 다시 훑고 다시 직렬화했거든. 커넥션 500개면 같은 계산을 500번.

Iris는 방법 B로 갈아엎은 거야. Epic이 대규모 슈터(Fortnite 급)에서 커넥션 수백 개를 감당하려고 복제 시스템을 아예 새로 짠 플러그인이지. 핵심 아이디어 딱 두 개만 먼저 머리에 박아:

  1. 양자화(Quantize)를 객체당·프레임당 최대 1회만 한다. 그 결과(POD 버퍼)를 여러 커넥션이 공유·memcpy·델타.
  2. 상태 바인딩을 오브젝트 지향 파편(Fragment) 으로 쪼갠다. 레거시가 UNetDriver/RepLayout에 다 몰아넣던 걸, 객체 단위로 분해.

그리고 이걸 진짜로 구현하는 게 이 챕터가 뜯을 파일들이야. 개념 → "이걸 코드로 만든 게 여기야"로 계속 이어갈게.

전제는 링크로만 건다. 프로퍼티 복제 뼈대가 흐릿하면 → replayout, 변경분만 보내는 개념이 처음이면 → changelist, "dirty만 보낸다"는 push 모델은 → push-model.

✅ 소스 포함 확인됨 — Iris 플러그인이 이 클론의 엔진 트리 Engine/Source/Runtime/Net/Iris/에 존재. 아래 코드블록은 전부 실제 소스에서 그대로 가져왔고 file:line을 붙였어. 직접 대조도 마쳤음.

1) 큰 그림 — 3계층으로 흐른다

레거시는 "액터 → 아카이브에 직렬화" 한 방이었어. Iris는 층이 셋이야. 왜 셋이냐면, "게임값"과 "네트워크 바이트" 사이에 양자화 버퍼라는 중간 지대를 하나 끼워넣었기 때문이야. 이 중간 지대가 김밥집의 "미리 말아둔 김밥"이야.

[게임 UObject 상태] ← 외부(External) 포맷. float, FString 등 비-POD 가능 │ │ (A) Instance 계층: 게임측 값 폴링 + dirty 감지 ▼ [양자화 버퍼] ← 내부(Internal) 포맷. 반드시 POD, 비트결정적 │ 여기까지가 "커넥션 무관, 딱 1번" 구간 │ (B) State/Serializer 계층: baseline 대비 델타로 비트스트림 ▼ [네트워크 비트스트림] ← 커넥션마다 전송. 여기만 N번 반복

핵심은 이 경계선이야. 양자화 버퍼까지는 커넥션과 무관하게 딱 한 번. 그 아래(델타·전송)만 커넥션 수만큼 반복. 그래서 손님이 500명이어도 무거운 계산(float 압축, 문자열 처리)은 한 번만 돌아.

이 "한 번만" 원칙이 헛말이 아니라 소스 주석에 못박혀 있어:

[스니펫 0] 양자화는 객체·프레임당 최대 1회 — Runtime/Net/Iris/Public/Iris/Serialization/NetSerializer.h:88-93

/** * Optional, unless there's a QuantizedType typedef or Dequantize implementation. * Transforms potentially non-POD source data to POD form which can be serialized quickly. * Quantization is only performed at most once per object and frame and is an excellent opportunity to perform slightly heavier computations in order * to make the serialization quicker. */
맞춰봐: 그럼 "델타(차이만 보내기)"도 커넥션 무관하게 한 번만 하면 되지 않아? … 아니야. 반전 — 델타는 커넥션마다 달라. 왜냐면 커넥션 A는 baseline이 3틱 전, 커넥션 B는 방금 접속해서 baseline이 없을 수 있거든. 그래서 양자화(공유)와 델타(개별)를 계층으로 갈라놓은 거야. 이 분리가 Iris 설계의 뼈야.

3) 심장 — 함수포인터 테이블

레거시에서 타입마다 복제를 어떻게 정의했지? NetSerialize(FArchive&) 가상함수 오버라이드였어. 문제는 이게 커넥션마다 아카이브에 매번 다시 써넣는 구조라는 거.

Iris는 이걸 함수포인터 테이블로 바꿨어. 타입 하나(예: FRotator)가 "나를 어떻게 양자화/델타/비교/검증하냐"를 함수 12개짜리 테이블로 등록해. 가상함수 디스패치 대신 POD 데이터로 최적화한 거지.

[스니펫 A] FNetSerializer — 멤버 직렬화기 함수포인터 테이블 — NetSerializer.h:381-395

NetSerializeFunction Serialize; NetDeserializeFunction Deserialize; NetSerializeDeltaFunction SerializeDelta; NetDeserializeDeltaFunction DeserializeDelta; NetQuantizeFunction Quantize; NetDequantizeFunction Dequantize; NetIsEqualFunction IsEqual; NetValidateFunction Validate; NetCloneDynamicStateFunction CloneDynamicState; NetFreeDynamicStateFunction FreeDynamicState; NetCollectNetReferencesFunction CollectNetReferences; NetApplyFunction Apply; const FNetSerializerConfig* DefaultConfig; uint16 QuantizedTypeSize; uint16 QuantizedTypeAlignment;

여기서 오늘 볼 건 딱 세 쌍이야:

  • Quantize / Dequantize — 게임값 ↔ 양자화버퍼
  • SerializeDelta / DeserializeDelta — 양자화버퍼 ↔ 네트워크 비트 (Prev 대비)
  • QuantizedTypeSize / QuantizedTypeAlignment — "이 타입 양자화하면 몇 바이트냐" (버퍼 크기 계산용)

각 함수가 받는 인자가 이 시스템의 데이터 흐름을 그대로 말해줘.

[스니펫 B] Quantize 인자 — 외부(Source) → 양자화버퍼(Target) — NetSerializer.h:242-249

struct FNetQuantizeArgs : FNetSerializerBaseArgs { /** A pointer to the non-quantized source data. */ NetSerializerValuePointer Source; /** A pointer to the quantized state buffer which contains valid, but unknown, quantized state. */ NetSerializerValuePointer Target; }; typedef void(*NetQuantizeFunction)(FNetSerializationContext&, const FNetQuantizeArgs&);

Source(게임 원본) → Target(양자화 버퍼). 딱 방향이 보이지. 이게 김밥 마는 단계야.

[스니펫 C] SerializeDelta 인자 — ack된 이전값 Prev로 비트팩 — NetSerializer.h:206-211

struct FNetSerializeDeltaArgs : FNetSerializeArgs { /** A pointer to acked quantized data, which can be used for bit packing. */ NetSerializerValuePointer Prev; }; typedef void(*NetSerializeDeltaFunction)(FNetSerializationContext&, const FNetSerializeDeltaArgs&);

여기 Prev 하나가 델타의 전부야. "클라가 마지막으로 ack한 양자화값"을 가리켜. 지금 값이랑 Prev가 같으면? 소스 주석대로 단 1비트만 쓰고 끝(NetSerializer.h:47/79의 same-value 최적화). 안 바뀐 회전값은 1비트. 이게 대역폭이 녹는 이유야.

4) 진짜 압축 현장 — Rotator를 byte로

추상적인 함수포인터 얘기만 하면 손에 안 잡히지. 진짜 구현 하나를 보자. FRotator(Pitch/Yaw/Roll, float 3개 = 12바이트)를 어떻게 양자화하나.

[스니펫 D] Rotator 각도 → byte 압축 — Runtime/Net/Iris/Private/Iris/Serialization/RotatorNetSerializers.cpp:370-383

const SourceType& Source = *reinterpret_cast<const SourceType*>(Args.Source); QuantizedType& Target = *reinterpret_cast<QuantizedType*>(Args.Target); QuantizedType TempValue = {}; TempValue.X = SourceType::CompressAxisToByte(Source.Pitch); TempValue.Y = SourceType::CompressAxisToByte(Source.Yaw); TempValue.Z = SourceType::CompressAxisToByte(Source.Roll); TempValue.XYZIsNotZero |= (TempValue.X != 0) ? XDiffersMask : uint8(0); TempValue.XYZIsNotZero |= (TempValue.Y != 0) ? YDiffersMask : uint8(0); TempValue.XYZIsNotZero |= (TempValue.Z != 0) ? ZDiffersMask : uint8(0); Target = TempValue;

읽어봐. Source.Pitch(float 4바이트) → CompressAxisToByte → Target.X(1바이트). 각 축이 4바이트에서 1바이트로 줄어. 12바이트 → 3바이트. 회전은 360도라 1도 단위 정밀도면 충분하니까 byte로 뭉갠 거지.

그리고 마지막 세 줄이 영리해. XYZIsNotZero 비트마스크에 "이 축이 0이 아니냐"를 미리 접어둬. 세 축이 다 0(회전 없음)이면 이 비트들이 다 꺼져서, 직렬화할 때 "안 움직였음"을 극소 비트로 표현할 수 있어. 무거운 계산(float 압축 + 0판정)을 양자화 단계에서 한 번에 몰아서 해두는 거야 — 스니펫 0에서 본 "한 번만" 원칙의 실물이야.

참고: 이 Target은 반드시 POD여야 하고(memcpy로 커넥션들이 나눠 쓰니까), 비트결정적이어야 해. 소스가 대놓고 경고해 — "양자화 상태의 패딩을 조심하라, 스택에 만들면 비결정적 상태가 될 수 있다"(NetSerializer.h:239). 김밥을 똑같이 말아야 100명한테 똑같이 나눠주지, 매번 모양 다르면 공유가 안 되잖아.

5) 오브젝트 지향 — Fragment

이제 두 번째 축. "오브젝트 지향 재설계"가 무슨 뜻이냐.

레거시에선 "이 액터의 이 프로퍼티를 복제해"라는 지식이 UNetDriver / RepLayout / RepState 같은 중앙 덩어리에 흩어져 있었어. 액터가 자기 상태를 어떻게 네트워크에 태우는지가 자기 밖에 있던 거야.

Iris는 이걸 Fragment(파편) 라는 객체로 쪼갰어. Fragment 하나 = "게임 UObject 상태의 일부를 NetObject 프로토콜에 바인딩하는 단위". 그리고 수신 데이터를 실제 객체에 밀어넣는 건 순수가상 함수 하나로 통일했어.

[스니펫 E] 게임측 상태를 바인딩하는 파편 기반 클래스 — Runtime/Net/Iris/Public/Iris/ReplicationSystem/ReplicationFragment.h:175-192

class FReplicationFragment { public: FReplicationFragment(const FReplicationFragment&) = delete; FReplicationFragment& operator=(const FReplicationFragment&) = delete; explicit FReplicationFragment(EReplicationFragmentTraits InTraits) : Traits(InTraits) {} virtual ~FReplicationFragment() {} /** Traits */ inline EReplicationFragmentTraits GetTraits() const { return Traits; } /** * This is called from the ReplicationSystem / ReplicationBridge whenever we have new data */ virtual void ApplyReplicatedState(FReplicationStateApplyContext& Context) const = 0;

ApplyReplicatedState — 이 순수가상 하나가 수신 파이프라인의 종착역이야. 콜체인 12번(Dequantize)까지 와서 양자화버퍼를 게임값으로 복원한 뒤, 이 함수로 "자, 네 실제 UObject에 반영해"라고 넘겨. 복사 금지(= delete)인 것도 봐 — Fragment는 정체성 있는 객체지 값이 아니야.

대응 관계로 정리하면:

  • 레거시 RepLayout이 하던 "무슨 프로퍼티를 어떻게" → Fragment 객체들이 나눠 가짐
  • 레거시 프로퍼티별 memcpy/조건검사 → Serializer 함수포인터 테이블(스니펫 A)
  • 레거시 RepNotify 콜백 지점 → ApplyReplicatedState

즉 "중앙 집중 → 객체 단위 분산". 이게 오브젝트 지향 재설계의 실체야.

6) NetObject 정체성 — 핸들

마지막 조각. 레거시는 복제 대상을 대개 UObject 포인터 / GUID로 지칭했어. Iris는 경량 핸들 하나로 바꿨어. 64비트 안에 정체성을 통째로 패킹.

[스니펫 F] NetRefHandle — 54비트 Id + 10비트 시스템Id — Runtime/Net/Iris/Public/Iris/ReplicationSystem/NetRefHandle.h:71-79

union { struct { uint64 Id : IdBits; // Id, lowest bit indicates if the handle is static or dynamic uint64 ReplicationSystemId : ReplicationSystemIdBits; // ReplicationSystemId, when running in pie, we track the owning instance }; uint64 Value; };
  • Id(= IdBits, 이 소스에선 54비트) — 객체 고유번호. 주석대로 최하위 비트가 static/dynamic 구분이야. 홀수 Id = static(레벨에 원래 있던 것), 짝수 = dynamic(런타임 스폰). 비교 한 번으로 종류를 안다.
  • ReplicationSystemId(= ReplicationSystemIdBits, 10비트) — PIE(에디터 다중 인스턴스)에서 어느 인스턴스 소유인지.

포인터 대신 이 64비트 값 하나로 객체를 지칭하니까, 복제 시스템 내부에서 객체를 훨씬 싸게 다뤄. 해시맵 키로도 바로 쓰고(스니펫 아래 GetTypeHash), 네트워크로 넘기기도 가볍고.

7) 우리 서버 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선협객전 서버 구조랑 대보면 Iris의 "한 번만" 철학이 확 와닿아.

우리 게임서버는 IOCP 워커가 여러 개지만, 실제 게임 로직(액터 상태 변경)은 싱글스레드로 직렬화해서 처리해(메모리 §single-threaded). 왜? 상태를 여러 스레드가 동시에 만지면 락 지옥이니까. "무거운 상태 확정은 한 곳/한 번, 그 결과를 워커들이 나눠서 송신"이 우리 패턴이야.

Iris도 정확히 같은 골격이야:

축우리 서버Iris
무거운 계산 1회싱글스레드 게임로직이 상태 확정Quantize를 객체·프레임당 1회 (NetSerializer.h:91)
결과 공유확정된 상태를 IOCP 워커들이 각 소켓에 송신POD 양자화버퍼를 커넥션들이 memcpy·델타
개별 처리소켓별 send 큐커넥션별 SerializeDelta (baseline이 커넥션마다 다름)
대상 식별캐릭터 핸들/인덱스NetRefHandle 64비트 (스니펫 F)

레거시 UE(방법 A)는 우리로 치면 "커넥션 500개면 게임 상태를 500번 다시 계산해서 500번 직렬화"하는 꼴이었어 — 우리가 절대 안 하는 짓이지. Iris는 그걸 우리처럼 "한 번 확정 → 나눠 송신"으로 고친 거야. 그래서 대규모 커넥션에서 CPU가 산다.

주의: Iris는 relevancy/priority 자체를 없앤 게 아니라, "누구한테 보낼지"는 상위 계층(Replication Graph 등)이 여전히 정하고, Iris는 "정해진 대상에 어떻게 싸게 직렬화하냐"를 담당해. 관계 컬링이 궁금하면 → replication-graph, relevancy.

8) 헷갈리는 용어 딱 정리

  • 양자화(Quantize) / QuantizedType — 게임 원본값(비-POD 가능)을 네트워크용 POD·비트결정적 형태로 변환한 것. 예) float 각도 → 1byte(스니펫 D). 0이 유효한 기본상태여야 함(버퍼가 0으로 초기화되니까, NetSerializer.h:233).
  • 역양자화(Dequantize) — 수신측에서 양자화값을 원본과 "근사적으로 같은" 게임값으로 복원. Quantize가 있으면 반드시 짝으로 있어야 함(NetSerializer.h:97).
  • 델타(Delta) / 기준선(Baseline) — 통째로 안 보내고 ack된 이전값(Prev, 스니펫 C)과의 차이만 보냄. 그 기준 스냅샷이 baseline. FDeltaCompressionBaselineManager가 객체당 최대 2개 유지(DeltaCompressionBaselineManager.h:56). 같으면 1비트.
  • ChangeMask(변경 마스크) — 객체의 어떤 멤버가 dirty인지 표시하는 비트배열. 켜진 멤버만 Quantize·Serialize 대상. 개념이 낯설면 → changelist, push-model.
  • Fragment(파편) — 게임 UObject 상태 일부를 NetObject 프로토콜에 바인딩하는 오브젝트 지향 단위. ApplyReplicatedState로 수신 데이터를 실제 객체에 반영(스니펫 E).
  • NetRefHandle — 복제 대상의 경량 정체성(54비트 Id). 최하위 비트로 static/dynamic 구분(스니펫 F). UObject 포인터 대신 이 핸들로 지칭.

9) 참조 링크

  • 막히면 → replayout (프로퍼티 복제 뼈대), changelist (변경분 추적), push-model (dirty만 보내기)
  • 관계 컬링 궁금하면 → replication-graph, relevancy
  • 다음 → charactermovement-overview (이제 "무엇을 어떻게 싸게 보내나"를 봤으니, "이동값을 예측·보정하며 보내는" 실전으로)
