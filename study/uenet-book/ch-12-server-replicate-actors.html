서버가 액터를 뿌린다: ServerReplicateActors

언리얼 네트워크 · 12 / 43

들어가기 전에: 우편배달부는 편지를 "다" 못 돌려

동네 우편배달부를 한 명 떠올려봐. 오토바이 뒷칸에 편지가 300통 실려 있어. 근데 오늘 안에 다 못 돌려. 기름도 한정, 시간도 한정이거든. 그럼 어떻게 해?

  • 먼저 "오늘 배달할 것"만 추려. 어제 이미 돌린 집, 아직 갱신 안 된 안내문은 뺀다.
  • 그다음 집집마다 다르게 판단해. 김씨네는 등기라 무조건 오늘, 이씨네는 그냥 전단지라 급할 것 없음.
  • 그리고 급한 것부터 위에 쌓아. 기름 떨어지면 아래 것들은 못 돌리고 내일로 미룬다.

게임 서버가 매 프레임 하는 일이 정확히 이거야. 서버에는 액터(플레이어, 몬스터, 문짝, 투사체…)가 수천 개 있고, 걔네 상태를 붙어있는 클라 전원한테 매 프레임 다 보내는 건 불가능해. 대역폭이 한정이거든. 그래서 서버는 매 프레임 "누구한테 뭘 얼마나 보낼지"를 골라야 해.

이걸 실제로 구현하는 함수가 이 챕터의 주인공, UNetDriver::ServerReplicateActors야. 앞 챕터(netdriver-tick)에서 "프레임 뒷단 TickFlush가 이 함수를 부른다"까지는 봤지. 거기서 문 앞까지만 갔는데, 이번엔 문을 열고 들어간다. 단, 끝까지 파고들진 않아 — "어떤 기준으로 고르고 정렬하는지"라는 뼈대와 '왜'까지만. 실제 채널에 바이트를 밀어넣는 세부는 다음 챕터(actorchannel-replicate)야.

우리 조선 서버로 치면? IOCP 워커가 받아온 걸 싱글스레드 액터 루프가 처리하듯, 여기 리플리케이션도 게임 스레드 한 줄에서 커넥션을 순회해. 뒤에서 자세히 비교할게.

1) 큰 그림: "한 번 추리고, 여럿한테 나눠 판단"

핵심 리듬을 한 문장으로 먼저 박아두자.

프레임당 한 번 공통 후보를 만들고 → 커넥션마다 관련성·우선순위로 걸러 정렬 → 대역폭 허용치만큼 위에서부터 복제 → 못 보낸 건 다음 프레임으로 미룬다.

이걸 콜체인으로 펼치면 이래. 줄번호는 전부 NetDriver.cpp 기준이야.

여기서 딱 두 개의 "층"만 기억해. ①한 번 만드는 공통 후보(ConsiderList) 와 ②커넥션마다 도는 개인화 처리. 1번은 프레임당 한 번, 2번은 커넥션 수만큼. 이 구조가 있는 이유는 곧 나와.

지금부터 진짜 언리얼 코드가 나온다. 겁먹지 마 — 위 지도에서 본 흐름을 실제 코드가 어떻게 문지기처럼 나눠 맡는지만 보면 돼. 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게.

2) 진입: "할 일 없으면 빨리 빠지고, 위임할 데 있으면 통째로 넘긴다"

매 프레임 도는 함수의 첫 예의는 조기 반환이야. 클라가 하나도 안 붙어있으면? 할 일 없으니 바로 나간다.

그리고 여기 중요한 갈림길이 하나 있어. ReplicationDriver(예: Replication Graph)가 세팅돼 있으면, 이 함수는 자기가 아무 것도 안 하고 통째로 걔한테 위임하고 반환해버려.

스니펫 A — 진입·조기반환·위임 (NetDriver.cpp:6085–6093, 6103–6106)

int32 UNetDriver::ServerReplicateActors(float DeltaSeconds) { SCOPE_CYCLE_COUNTER(STAT_NetServerRepActorsTime); #if WITH_SERVER_CODE if ( ClientConnections.Num() == 0 ) { return 0; }
if (ReplicationDriver) { return ReplicationDriver->ServerReplicateActors(DeltaSeconds); }
🔤 기호 사전 — int32 UNetDriver::ServerReplicateActors(float DeltaSeconds) / return ReplicationDriver->ServerReplicateActors(DeltaSeconds);
• int32 = 정수 숫자를 담는 타입. 여기선 함수가 "몇 개 처리했나" 같은 숫자를 돌려줄 수 있다는 뜻이야.
• UNetDriver:: = ServerReplicateActors가 UNetDriver 소속이라는 표시. ::는 "~안에 있는"이라고 읽어.
• float DeltaSeconds = 지난 프레임부터 지금까지 걸린 시간을 소수로 받는 입력값. float은 소수 담는 통.
• SCOPE_CYCLE_COUNTER(...) = 이 함수가 얼마나 오래 걸렸는지 재는 프로파일링 매크로. 게임 규칙보다 스톱워치에 가까워.
• #if WITH_SERVER_CODE = 서버 코드가 켜진 빌드에서만 아래 코드를 넣으라는 컴파일 조건문.
• ClientConnections.Num() == 0 = 붙어 있는 클라 수가 0명인지 확인. Num()은 개수 세기, ==는 "같다".
• return 0 = "할 일 없음"을 숫자 0으로 돌려주고 함수에서 바로 나감.
• ReplicationDriver->ServerReplicateActors(...) = ReplicationDriver한테 같은 일을 통째로 맡김. ->는 포인터가 가리키는 객체의 함수를 부르는 화살표.
• if (...) { ... } = 괄호 안 조건이 맞을 때만 중괄호 안을 실행하는 갈림길.
🔁 이제 다시 보자. 첫 줄은 "UNetDriver의 복제 함수가 이번 프레임 시간(DeltaSeconds)을 받아 정수 결과를 돌려준다"로 읽으면 돼. ClientConnections.Num() == 0이면 손님이 없으니 return 0, ReplicationDriver가 있으면 ->ServerReplicateActors(...)로 통째로 넘긴다. 즉 "할 일 없거나 담당자가 따로 있으면 초반에 바로 빠지는 입구"야.
위 두 조각 사이(6098~6101줄쯤)에는 #if CSV_PROFILER_STATS 프로파일링 블록이 껴 있어서 연속 인용이 아니야. 그래서 일부러 끊어 실었어.

이 위임 분기가 왜 중요하냐면 — 우리가 지금 읽는 이 전통 경로는 "액터가 몇 만 개면 매 프레임 그걸 다 훑어야 하는" 구조라 대규모에선 느려. 그래서 대형 프로젝트는 ReplicationDriver를 꽂아서 "공간 격자로 미리 잘라두고 필요한 것만" 뽑는 신형 경로를 타. 그건 replication-graph 챕터 얘기고, 지금은 "아, 여기서 갈라지는구나. 우린 전통 쪽 본다" 정도만.

위임할 데가 없으면 이제 본론. 아래 세 스텝을 지휘해.

3) 스텝 1·2 — 몇 명한테, 어떤 후보를

PrepConnections — "이번 프레임 몇 명이나 상대할까" (:5006)

클라가 500명 붙어있다고 매 프레임 500명을 다 처리하면 서버 프레임이 터져. 그래서 먼저 이번 프레임에 몇 커넥션을 틱할지(NumClientsToTick)를 정해. 리슨 서버 스로틀, 최대 연결수 제한 같은 게 여기 들어가. 못 뽑힌 커넥션은 이따 루프에서 "다음에 봐줄게" 마킹만 받고 넘어가.

그와 별개로, 서버가 지금 CPU에 허덕이는지(bCPUSaturated)도 여기 근처에서 판정해둬. 이 플래그가 나중에 우선순위 계산의 "저대역폭 모드" 힌트로 흘러들어가.

스니펫 B — CPU 포화 판정 (NetDriver.cpp:6140–6157)

if ( NumClientsToTick == 0 ) { // No connections are ready this frame return 0; } AWorldSettings* WorldSettings = World->GetWorldSettings(); bool bCPUSaturated = false; float ServerTickTime = GEngine->GetMaxTickRate( DeltaSeconds ); if ( ServerTickTime == 0.f ) { ServerTickTime = DeltaSeconds; } else { ServerTickTime = 1.f/ServerTickTime; bCPUSaturated = DeltaSeconds > 1.2f * ServerTickTime; }
🔤 기호 사전 — bool bCPUSaturated = false; ... bCPUSaturated = DeltaSeconds > 1.2f * ServerTickTime;
• AWorldSettings* WorldSettings = 월드 설정 객체를 가리키는 표. *는 "진짜 물건이 아니라 그 물건의 주소를 들고 있다"는 포인터 표시야.
• bool = 참/거짓만 담는 스위치. 켜짐/꺼짐 같은 값.
• false = 처음엔 "아직 CPU 포화 아님"으로 놓고 시작한다는 뜻.
• float = 소수점 숫자를 담는 타입. 프레임 시간처럼 0.016 같은 값을 넣을 수 있어.
• GEngine->GetMaxTickRate(...) = 엔진한테 "목표 틱 속도가 얼마야?" 하고 물어보는 호출. ->는 그 객체의 함수를 부르는 화살표.
• 0.f, 1.f, 1.2f = 소수 숫자라는 표시가 붙은 값. 1.2f는 "목표 시간의 1.2배"를 뜻해.
• if / else = 조건이 맞으면 위 길, 아니면 아래 길로 가는 갈림길.
• 1.f / ServerTickTime = 초당 틱 수를 "한 틱에 걸리는 시간"으로 뒤집는 계산.
• >, * = >는 왼쪽이 더 큰지 비교, *는 곱하기.
🔁 이제 다시 보자. 이 코드는 목표 프레임 시간(ServerTickTime)을 구한 뒤, 실제 이번 프레임 시간(DeltaSeconds)이 그보다 1.2배 넘게 길면 bCPUSaturated를 켠다. 한 줄로 읽으면 "이번 프레임이 목표보다 너무 느렸으면 서버가 힘든 상태라고 표시"하는 코드야.

DeltaSeconds > 1.2f * ServerTickTime — 이번 프레임이 목표 프레임시간의 1.2배 넘게 걸렸으면 "서버 힘들다"로 본다는 뜻이야. 간단하지.

BuildConsiderList — "지금 갱신할 때 된 것만 추려" (:5111)

이제 후보 목록을 만들어. 여기가 아까 말한 "①한 번 만드는 공통 후보"야. 전체 네트워크 오브젝트를 훑어서, 커넥션과 무관한 공통 조건으로 1차 컷을 해. 대표적인 게 "업데이트 주기".

스니펫 C — 업데이트 주기 컷 (NetDriver.cpp:5127–5131)

if ( !ActorInfo->bPendingNetUpdate && World->TimeSeconds <= ActorInfo->NextUpdateTime ) { UE_LOG(LogNetTraffic, VeryVerbose, TEXT("Skipping actor: %s. bPendingNetUpdate: %s | NextUpdateTime: %f (currently %f)"), *GetNameSafe(ActorInfo->Actor), ActorInfo->bPendingNetUpdate?TEXT("true"):TEXT("false"),ActorInfo->NextUpdateTime, World->TimeSeconds); continue; // It's not time for this actor to perform an update, skip it }
🔤 기호 사전 — if ( !ActorInfo->bPendingNetUpdate && World->TimeSeconds <= ActorInfo->NextUpdateTime )
• ! = "아니다"라는 뒤집기 표시. !ActorInfo->bPendingNetUpdate는 "강제 갱신 표시가 안 켜졌으면".
• ActorInfo->... = ActorInfo가 가리키는 액터 정보 상자 안의 값을 꺼내는 화살표.
• && = 그리고. 왼쪽 조건과 오른쪽 조건이 둘 다 맞아야 전체가 맞아.
• <= = 작거나 같다. 지금 시간이 다음 갱신 시간에 아직 못 미쳤는지 보는 비교야.
• UE_LOG(...) = 로그 한 줄 남기기. 여기선 왜 스킵했는지 아주 자세히 적어둔다.
• VeryVerbose = 로그 중에서도 아주 수다스러운 등급. 평소엔 잘 안 보이게 깊은 디버그용이야.
• TEXT("...") = 언리얼에서 문자열을 안전한 형태로 감싸는 매크로.
• ? : = 작은 갈림길. 조건이 참이면 앞값, 거짓이면 뒷값을 고른다.
• continue = 이번 액터는 여기서 그만 보고, 루프의 다음 액터로 넘어가라는 뜻.
🔁 이제 다시 보자. !bPendingNetUpdate(강제 갱신 아님)이고 TimeSeconds <= NextUpdateTime(아직 갱신할 시간이 아님)이면 로그를 남기고 continue로 넘긴다. 즉 "지금 보낼 차례가 아닌 액터는 후보 목록에 넣지 않는다"는 1차 컷이야.

NextUpdateTime이 아직 안 됐고(=갱신할 때가 안 됨) 강제 갱신 플래그(bPendingNetUpdate)도 없으면 → continue, 후보에서 뺀다. 액터마다 "나는 초당 몇 번 갱신"이라는 리듬이 있는데(그건 priority-updatefreq 챕터), 그 리듬에 안 맞는 프레임엔 아예 후보에서 빠지는 거지. 이거 말고도 PendingKill(죽는 중), RemoteRole=None(복제 대상 아님), 아직 초기화/스트리밍 안 된 상태 같은 공통 필터가 여기서 걸러져.

🤔 왜 후보를 커넥션마다 안 만들고 한 번만 만들까?

잠깐 멈춰서 맞춰봐. 후보 목록을 왜 커넥션 500개마다 각각 만들지 않고, 프레임당 딱 한 번만 만들까?

...

정답: "갱신할 때가 됐나?"는 액터 개인 사정이라 보는 사람(커넥션)이 누구든 똑같으니까. 몬스터A의 NextUpdateTime은 김씨가 보든 이씨가 보든 같은 값이야. 커넥션마다 다시 계산하면 500번 중복 노동이지. 그래서 "누가 봐도 같은 판정"은 한 번에 몰아서(BuildConsiderList) 처리하고, "보는 사람마다 다른 판정"(관련성·우선순위)만 커넥션 루프 안에서 개인화하는 거야. 딱 반씩 나눈 이 설계가 이 함수의 뼈대다.

4) 스텝 3 — 커넥션 하나를 처리하는 3단 파이프라인

이제 커넥션 배열을 돌면서, 틱 대상으로 뽑힌 커넥션마다 ForConnection(:5746)을 불러. 이 안에서 뷰어(그 커넥션의 카메라 위치·시선) 목록을 만들고, 핵심인 3단 파이프라인을 순서대로 실행해.

스니펫 D — ForConnection의 3단 파이프라인 (NetDriver.cpp:5811–5821)

FActorPriority* PriorityList = NULL; FActorPriority** PriorityActors = NULL; // Get a sorted list of actors for this connection const int32 FinalSortedCount = ServerReplicateActors_PrioritizeActors(Params.Connection, Params.ConnectionViewers, Params.ConsiderList, Params.bCPUSaturated, PriorityList, PriorityActors); // Process the sorted list of actors for this connection TInterval<int32> ActorsIndexRange(0, FinalSortedCount); const int32 LastProcessedActor = ServerReplicateActors_ProcessPrioritizedActorsRange(Params.Connection, Params.ConnectionViewers, PriorityActors, ActorsIndexRange, Params.InOutUpdated); ServerReplicateActors_MarkRelevantActors(Params.Connection, Params.ConnectionViewers, LastProcessedActor, FinalSortedCount, PriorityActors);
🔤 기호 사전 — FActorPriority* PriorityList = NULL; ... TInterval<int32> ActorsIndexRange(0, FinalSortedCount);
• FActorPriority* = 우선순위 점수 상자를 가리키는 포인터. *는 "주소표"라고 생각하면 돼.
• ** = 별 두 개는 주소표를 한 번 더 타고 들어가는 모양. 여기선 우선순위 항목들을 가리키는 포인터 배열을 다루려는 표시야.
• NULL = 아직 아무것도 가리키지 않는 빈 표식.
• const int32 = 한 번 정하면 여기서 바꾸지 않을 정수.
• Params.Connection = Params라는 묶음 상자 안에서 Connection 칸을 꺼낸 것.
• TInterval<int32> = 정수 범위를 담는 상자. 여기선 0부터 FinalSortedCount까지 처리하겠다는 범위야.
• LastProcessedActor = 실제로 어디까지 처리했는지 기억하는 번호. 나중에 못 보낸 나머지를 표시할 때 쓴다.
🔁 이제 다시 보자. 먼저 PriorityList와 PriorityActors라는 빈 결과 상자를 준비하고, ServerReplicateActors_PrioritizeActors(...)가 이 커넥션용 정렬 목록을 만든다. 그다음 TInterval<int32>(0, FinalSortedCount) 범위만큼 Process...가 위에서부터 처리하고, 마지막에 Mark...가 못 처리한 뒤쪽을 챙긴다. 즉 정렬 → 처리 → 잔여 마킹 3단 릴레이야.

세 줄이 이 챕터의 심장이야. 순서대로:

  1. Prioritize — 공통 후보(ConsiderList)를 이 커넥션 기준으로 걸러 정렬 → 정렬된 배열 PriorityActors와 개수 FinalSortedCount 반환.
  2. Process — PriorityActors를 [0, FinalSortedCount) 범위로 위에서부터 실제 복제. 어디까지 처리했는지 LastProcessedActor로 반환.
  3. Mark — LastProcessedActor 이후(=못 보낸 잔여분)를 다음 프레임 재고려 대상으로 마킹.

하나씩 열어보자.

3-1. Prioritize — "이 사람한테 필요한가?"부터 걸러 (:5336)

여기서 아까 나눠둔 "②개인화 판정"이 벌어져. 후보 액터 하나하나에 대해 이 커넥션에게 관련(relevant) 있나를 묻는다. 관련성은 시야·거리·소유 관계·bAlwaysRelevant 같은 걸로 정해져(상세는 relevancy).

스니펫 E — 관련성 조기 컷 (NetDriver.cpp:5384–5401)

// Skip actor if not relevant and theres no channel already. // Historically Relevancy checks were deferred until after prioritization because they were expensive (line traces). // Relevancy is now cheap and we are dealing with larger lists of considered actors, so we want to keep the list of // prioritized actors low. if (!Channel) { if (!IsLevelInitializedForActor(Actor, Connection)) { // If the level this actor belongs to isn't loaded on client, don't bother sending continue; } if (!IsActorRelevantToConnection(Actor, ConnectionViewers)) { // If not relevant (and we don't have a channel), skip continue; } }
🔤 기호 사전 — if (!Channel) ... continue;
• Channel = 이 액터를 이 클라에게 보내는 전용 통로. 이미 있으면 예전에 보낸 적이 있다는 뜻이야.
• !Channel = 채널이 없으면. !는 "없다/아니다"로 뒤집는 표시.
• if (...) = 조건이 맞을 때만 안쪽을 실행하는 문.
• IsLevelInitializedForActor(...) = 클라가 이 액터가 속한 레벨을 읽을 준비가 됐는지 묻는 검사.
• IsActorRelevantToConnection(...) = 이 액터가 이 커넥션에게 보낼 만한지 묻는 관련성 검사.
• continue = 이번 액터는 후보에서 빼고 다음 액터로 넘어가기.
• // ... = 코드 실행엔 영향 없는 설명 주석. 개발자가 왜 이렇게 했는지 남겨둔 메모야.
🔁 이제 다시 보자. !Channel이면 아직 이 클라에게 열린 통로가 없다는 뜻이니까, 먼저 레벨이 준비됐는지 보고, 그다음 관련성이 있는지 본다. 둘 중 하나라도 아니면 continue로 잘라낸다. 즉 "새로 보낼 액터는 클라가 받을 준비가 됐고 실제로 관련 있을 때만 정렬 목록에 남긴다"는 코드야.

if (!Channel) 이 조건 하나가 은근 중요해. 이미 채널이 있으면(=예전에 이 액터를 이 클라한테 보낸 적 있어서 통로가 열려 있으면) 이 관련성 검사를 건너뛰어. 왜? 이미 보내던 애는 갑자기 안 관련돼졌어도 "이제 그만 보낼게(파괴 통보)" 같은 마무리가 필요하니까, 여기서 그냥 continue로 잘라버리면 안 되거든. 새로 시작하는 액터(채널 없음)만 "레벨 로드됐나 + 관련 있나"를 통과해야 후보에 남는 거야.

그리고 주석이 알려주는 역사 한 조각도 재밌어: 옛날엔 관련성 검사가 라인트레이스라 비싸서 정렬 뒤로 미뤘는데, 지금은 싸져서 정렬 앞으로 당겼대. 후보를 미리 줄여서 정렬 비용을 아끼려고. 코드에 붙은 시대의 흔적이지.

관련 있다고 통과한 애들은 이제 우선순위 점수를 받아.

스니펫 F — 우선순위 계산: GetNetPriority × 뷰어 최댓값 (NetDriver.cpp:4960–4970)

FActorPriority::FActorPriority(UNetConnection* InConnection, UActorChannel* InChannel, FNetworkObjectInfo* InActorInfo, const TArray<struct FNetViewer>& Viewers, bool bLowBandwidth) : ActorInfo(InActorInfo), Channel(InChannel), DestructionInfo(NULL) { const float Time = Channel ? (InConnection->Driver->GetElapsedTime() - Channel->LastUpdateTime) : InConnection->Driver->SpawnPrioritySeconds; // take the highest priority of the viewers on this connection Priority = 0; for (int32 i = 0; i < Viewers.Num(); i++) { Priority = FMath::Max<int32>(Priority, FMath::RoundToInt(65536.0f * ActorInfo->Actor->GetNetPriority(Viewers[i].ViewLocation, Viewers[i].ViewDir, Viewers[i].InViewer, Viewers[i].ViewTarget, InChannel, Time, bLowBandwidth))); } }
🔤 기호 사전 — FActorPriority::FActorPriority(...): ActorInfo(...), Channel(...), DestructionInfo(NULL)
• FActorPriority::FActorPriority = FActorPriority 상자를 새로 만들 때 자동으로 불리는 생성자. 이름이 두 번 나오는 건 "그 상자를 만드는 함수"라는 뜻이야.
• UNetConnection*, UActorChannel*, FNetworkObjectInfo* = 각각 연결, 채널, 액터 정보 상자를 가리키는 포인터. *는 주소표.
• const TArray<struct FNetViewer>& Viewers = 뷰어 목록을 원본 그대로 받는다는 뜻. TArray는 리스트, &는 복사 말고 원본 참조야.
• : ActorInfo(...), Channel(...), DestructionInfo(NULL) = 함수 몸통에 들어가기 전에 멤버 칸들을 먼저 채우는 초기화 목록.
• Channel ? A : B = 작은 갈림길. 채널이 있으면 A, 없으면 B를 고른다.
• InConnection->Driver->GetElapsedTime() = 연결 → 드라이버 → 현재 흐른 시간 순서로 화살표를 타고 들어가 값을 가져온다.
• for (int32 i = 0; i < Viewers.Num(); i++) = i를 0부터 시작해서 뷰어 개수만큼 하나씩 늘리며 반복.
• Viewers[i] = 뷰어 목록에서 i번째 칸을 꺼낸다는 뜻.
• FMath::Max<int32>(...) = 두 값 중 더 큰 정수를 고르는 도구.
• 65536.0f = 실수 우선순위를 큰 정수 점수로 바꾸려고 곱하는 값.
🔁 이제 다시 보자. 생성자는 먼저 이 우선순위 항목이 어떤 액터와 채널을 말하는지 채워둔다. Time은 채널이 있으면 마지막 갱신 뒤 지난 시간, 없으면 새 액터용 기본 시간을 고르고, for 루프는 모든 뷰어를 돌며 GetNetPriority(...) 점수 중 제일 큰 값을 Priority로 잡는다. 즉 "이 커넥션의 여러 화면 중 하나라도 중요하면 높은 점수를 주는 계산"이야.

읽는 법:

  • GetNetPriority(...)가 실수 우선순위를 뱉고, 65536.0f를 곱해 정수로 만들어(정렬을 정수로 빠르게 하려고).
  • Time은 "이 액터를 이 채널로 마지막에 갱신한 뒤 얼마나 지났나". 오래 못 보낸 애일수록 우선순위가 올라가게 설계돼 있어(굶기지 않으려고).
  • 뷰어(Viewers) 루프에서 FMath::Max — 한 커넥션에 화면(뷰어)이 여럿일 수 있어(스플릿스크린 등). 그중 가장 높은 우선순위를 그 액터의 점수로 채택해. "어느 한 화면에라도 중요하면 중요하다"는 뜻.

점수가 다 매겨지면 마지막에 내림차순 정렬.

스니펫 G — 우선순위 내림차순 정렬 (NetDriver.cpp:5477)

// Sort by priority Algo::SortBy(MakeArrayView(OutPriorityActors, FinalSortedCount), &FActorPriority::Priority, TGreater<>());
🔤 기호 사전 — Algo::SortBy(MakeArrayView(...), &FActorPriority::Priority, TGreater<>())
• Algo::SortBy = 언리얼의 정렬 도구. 목록을 어떤 기준으로 줄 세우는 함수야.
• MakeArrayView(...) = 배열 전체 중에서 실제로 볼 범위를 잘라 "이 부분만 정렬해" 하고 건네는 포장.
• &FActorPriority::Priority = FActorPriority 안의 Priority 칸을 정렬 기준으로 쓰라는 표시. &는 여기서 그 멤버를 가리키는 표식이야.
• TGreater<> = 큰 값이 앞에 오게 하는 비교 규칙.
• <> = 템플릿 자리. 여기선 타입을 알아서 맞기게 비워둔 모양이라고 보면 돼.
🔁 이제 다시 보자. OutPriorityActors 중 FinalSortedCount개만 꺼내서, 각 항목의 Priority 값을 기준으로, TGreater<> 규칙대로 큰 점수가 앞에 오게 줄 세운다. 즉 "급한 액터를 배열 맨 위로 올리는 정렬"이야.

TGreater<> — 큰 게 앞으로. 이제 배열 맨 위에 "제일 급한 액터"가 온다.

3-2. Process — "대역폭 떨어질 때까지만 위에서부터" (:5495)

정렬된 배열을 위에서부터 실제로 복제해. 여기 핵심 안전장치 하나:

스니펫 H — 대역폭 포화 시 즉시 중단 (NetDriver.cpp:5503–5508)

if (!Connection->IsNetReady() && !bIgnoreSaturation) { GNumSaturatedConnections++; // Connection saturated, don't process any actors return 0; }
🔤 기호 사전 — if (!Connection->IsNetReady() && !bIgnoreSaturation)
• Connection->IsNetReady() = 이 커넥션이 지금 더 보낼 준비가 됐는지 묻는 함수.
• !Connection->IsNetReady() = 보낼 준비가 안 됐으면. !는 결과를 뒤집는 표시야.
• && = 그리고. 왼쪽도 맞고 오른쪽도 맞아야 실행된다.
• !bIgnoreSaturation = "포화 상태를 무시하라는 특수 예외가 아니면"이라는 뜻.
• GNumSaturatedConnections++ = 포화된 커넥션 카운터를 1 올린다. ++는 하나 증가.
• return 0 = 더 이상 액터를 처리하지 않고 바로 빠져나간다.
🔁 이제 다시 보자. 커넥션이 더 보낼 준비가 안 됐고(!IsNetReady()), 포화를 무시하는 예외도 아니면(!bIgnoreSaturation), 포화 카운터를 올리고 return 0으로 중단한다. 즉 "대역폭 기름이 떨어졌으면 이번 커넥션의 남은 배달은 여기서 멈춘다"는 안전장치야.

IsNetReady()가 false = 이 커넥션 이번 프레임 송신 예산이 바닥남(saturated). 그럼 남은 액터를 더 처리하지 않고 그냥 나가. 오토바이 기름 떨어지면 아래 편지들 안 돌리고 복귀하는 그거야. 이래서 앞서 우선순위 정렬이 목숨줄인 거지 — 어차피 다 못 보내니까, 위에 쌓인 급한 것만이라도 확실히 보내려고 정렬한 거였어. (정상 액터는 여기서 관련성을 한 번 더 확인하고 채널로 복제하는데, 그 채널 안쪽 세부는 actorchannel-replicate.)

3-3. Mark — "못 보낸 건 다음에 꼭 봐줄게" (:5704)

포화로 못 보내고 남은 애들(LastProcessedActor 이후)을 다음 프레임 재고려 대상으로 마킹해. 이게 bPendingNetUpdate 플래그야. 다음 프레임 BuildConsiderList에서, 아까 스니펫 C의 !ActorInfo->bPendingNetUpdate 조건 기억나지? 이 플래그가 켜져 있으면 "아직 갱신할 때 아님" 컷을 무시하고 후보로 다시 올라와. 굶는 액터가 없게 만드는 안전망이야.

5) 한 바퀴 되짚기 — 예측하고 확인

여기까지 왔으면 스스로 물어봐. "우선순위가 낮은 액터는 영영 못 받는 거 아니야?"

...

아니야, 라는 게 반전이야. 두 겹의 안전망이 걔를 구해:

  1. Time 요소(스니펫 F) — 못 보낸 채 시간이 지나면 Time이 커지고, GetNetPriority가 그걸 반영해 점수를 끌어올려. 방치될수록 우선순위가 오른다.
  2. bPendingNetUpdate 마킹(3-3) — 이번에 잘린 액터는 다음 프레임 후보에 강제로 재진입.

그래서 저우선순위 액터도 "느리게, 하지만 언젠간" 받게 돼. 실시간성이 낮을 뿐 굶어 죽진 않아. 이게 "대역폭은 유한한데 공정하게 나눠주기"라는 문제에 대한 UE의 답이야.

6) 우리 서버랑 비교 — IOCP + 싱글스레드 액터 모델

과부하 대처보낼 게 생기면 그때 밀어냄(수동 조절)대역폭 예산으로 자동 컷 + 잔여분 다음 프레임 이월

큰 그림 공통점: 상태를 만지는 처리는 락 없이 한 줄(싱글스레드)에서 직렬로 돈다. 우리도 IOCP 워커는 여럿이지만 게임 상태 변경은 싱글스레드로 직렬화하잖아. UE의 ServerReplicateActors도 게임 스레드 한 줄에서 커넥션들을 순회해. 그래서 락 없이 안전하게 액터 상태를 읽어 복제할 수 있어.

가장 큰 차이: 우리 서버는 보통 "이벤트가 관련자에게 직접 쏘는" 모델이라, 누가 관련자인지를 로직이 그때그때 정해. UE는 반대로 "매 프레임 전 액터를 훑어 관련성·우선순위를 재계산하는" 범용 엔진 모델이야. 우리 방식은 트래픽이 적고 명시적이지만 컨텐츠마다 관련자 판정을 손으로 짜야 하고, UE 방식은 자동이고 일반적이지만 매 프레임 훑는 비용이 들어(그래서 대규모엔 replication-graph로 그 비용을 잘라내는 거고).

7) 초보가 헷갈리는 핵심 용어

  • ConsiderList (고려 목록): 프레임당 1회, 커넥션과 무관하게 "지금 갱신할 때 된" 액터만 모은 1차 후보 배열(FNetworkObjectInfo*). BuildConsiderList(:5111)가 채우고 모든 커넥션이 재사용.
  • Relevancy (관련성): 이 액터를 이 커넥션(플레이어) 에게 보낼 필요가 있나. IsActorRelevantToConnection(:5396)로 판정. 시야·거리·소유·bAlwaysRelevant 기준. 상세는 relevancy.
  • Priority (우선순위): 대역폭이 모자랄 때 누구부터 보낼지 정하는 정수 점수. GetNetPriority()에 65536.0f를 곱해 산출(:4968), 내림차순 정렬(:5477). 오래 못 보낼수록 올라감.
  • NetReady / Saturated (대역폭 포화): 커넥션의 이번 프레임 송신 예산 소진 여부. !IsNetReady()면 남은 액터 처리 없이 중단(:5503), 잔여는 다음 프레임으로.
  • ActorChannel (액터 채널): 서버↔클라 간 한 액터의 복제 상태를 담는 통로. 채널이 이미 있으면 관련성 재검사를 건너뛰는 등 흐름 분기의 기준(:5388). 채널 내부 동작은 actorchannel-replicate.
  • ReplicationDriver / bPendingNetUpdate: ReplicationDriver(예: Replication Graph)가 있으면 이 전체 흐름을 위임하고 조기 반환(:6105). bPendingNetUpdate는 못 처리한 커넥션/액터를 "다음 프레임 재고려"하게 다는 플래그(:6241, MarkRelevantActors :5704).
