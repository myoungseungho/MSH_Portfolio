큰 그림 — 언리얼 네트워크 한눈에 (여기서 시작)

언리얼 네트워크 · 00 / 43

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터는 지도야. 세부는 하나도 안 판다. 대신 전체 얼개를 머리에 넣어서, 다음 챕터부터 밑바닥을 팔 때 "이게 어느 가지였지"를 안 잃게 해주는 게 목적이야.

0. 이 책 읽는 법 — 지도 먼저, 그다음 내려간다

방대한 걸 배울 때 제일 헤매는 이유는 지도 없이 골목부터 걷기 때문이야. 그래서 순서를 이렇게 잡자.

  1. (지금 이 챕터) 큰 그림 — 위에서 전체를 내려다본다(top-down). 카테고리 트리로 얼개를 잡는다.
  2. 그다음 밑바닥으로 — VOL.2부터 바이트·채널·복제를 하나씩 판다(bottom-up). 이제 각 챕터가 트리의 어느 가지인지 알고 읽으니 안 헤맨다.

즉 "얼개 먼저 → 세부 나중". 지금은 외우지 마. "아 이런 게 있구나"만.

🌱 이 개념은 왜 생겼나 — 서버 권위(authority)
• 원래 구조: 제일 순진한 방법은 각 클라가 자기 상태를 스스로 정하고 남한테 알려주는 거야. "나 지금 HP 100이고 여기 있어" 하면 다들 그대로 믿어. 코드도 제일 간단하지.
• 그런데 문제: 그럼 누가 클라를 조작해서 "나 HP 9999, 데미지 999999, 순간이동함"이라고 보내면? 다들 믿어버려 → 핵 천국. 실제로 옛날 P2P 게임들이 이렇게 다 털렸어.
• 그래서 필요한 것: "진짜는 딱 한 명만 정한다"를 세우는 거야. 그 한 명이 서버고, 이게 서버 권위야. 클라는 "해줘"만 부탁하고 최종 판정·저장은 서버가 한다. 우리 조선 서버가 재화·아이템을 절대 클라 말대로 안 믿고 CM_ 요청을 서버가 검증·확정하는 거랑 똑같아.

1. 한 문장 + 한 그림

언리얼 네트워크를 한 문장으로 줄이면 이거야.

"서버가 진짜(권위)이고, 서버가 세계 상태를 모든 클라에게 계속 맞춰준다."

그림으로:

[ 서버 = 진짜 세계 (권위) ] │ ▲ ① 상태가 바뀜 │ │ ④ "이거 해줘" 요청 (HP 100→90)│ │ (RPC: 나 발사할래) ▼ │ ② 복제(replication)로 클라에 전송 │ │ │ ┌─────────┼──────────┐ │ ▼ ▼ ▼ │ [클라 A] [클라 B] [클라 C] ─────┘ │ ▼ ③ 각 클라 화면이 서버와 똑같아짐 (때론 ④처럼 클라가 먼저 움직이고 = 예측, 서버가 보정)

여기서 핵심 단어 네 개가 나와. 이 책 전체가 사실상 이 네 개 이야기야.

  • 서버 권위(authority) — 최종 판정은 항상 서버. 클라 말 그대로 믿으면 핵 천국.
  • 복제(replication) — 상태(변수)를 서버가 클라에 자동으로 계속 맞춰줌. "HP는 90이야"를 알아서.
  • RPC — 일회성 명령/이벤트. "지금 폭발 터뜨려", "서버야 나 발사".
  • 예측(prediction) — 지연을 숨기려고 클라가 먼저 움직이고 서버가 나중에 보정.

2. 전체 얼개 — 카테고리 트리

이 책 42챕터가 사실 이 트리의 가지들이야. 이 그림 하나만 머리에 넣고 가면 어느 챕터를 읽든 "지금 여기구나"가 잡혀.

언리얼 네트워크 │ ├─ A. 무엇을 주고받나 (데이터 = 두 기둥) │ ├─ 상태 동기화 = 복제(Replication) ← 변수를 자동으로 맞춤 │ │ ├─ 무엇을 보낼지: DOREPLIFETIME / 조건(COND) / PushModel (14·18·19) │ │ ├─ 어떻게 잘게 나눠 보낼지: RepLayout → Changelist (15·16) │ │ ├─ 큰 흐름·입구: ServerReplicateActors / ActorChannel (12·13) │ │ ├─ 도착하면 콜백: RepNotify (17) │ │ └─ 부품까지 같이: 서브오브젝트 복제 (20) │ └─ 명령/이벤트 = RPC ← 함수처럼 원격 호출 │ ├─ 방향: Server / Client / Multicast (21) │ └─ 신뢰성·검증·소유권 (22·23) │ ├─ B. 어떻게 전달되나 (전송 계층 = 밑바닥 배관) │ ├─ NetDriver — 매 프레임 도는 엔진 (11) │ ├─ NetConnection — 연결 하나가 책임지는 모든 것 (1) │ ├─ Channel / Bunch — 논리적 스트림(봉투) (4·5·3) │ ├─ Packet / 바이트 / 비트리더 — 수신·송신 콜체인 (2·6) │ ├─ 신뢰성 / ack — 순서·재전송 (7) │ └─ Handshake / PacketHandler — 연결 맺기·암호화 (9·8·10) │ ├─ C. 어떻게 감당하나 (최적화 · 스케일) │ ├─ Relevancy / Priority / Dormancy — 누구에게·얼마나·언제 멈춤 (24·25·26) │ └─ ReplicationGraph / Iris — 수천 명을 감당하는 재설계 (27·28) │ ├─ D. 움직임 (이동 · 예측) │ ├─ CharacterMovement / 클라 예측 / 서버 보정 (29·30·31) │ └─ 스무딩 / RootMotion (32·33) │ └─ E. 시간 · 판정 · 운영 (부가) ├─ 서버 시간 동기 / 랙 보상 / GAS 예측 (34·35·36) └─ VoIP / Travel / 연결 생명주기 / 보안 / 디버깅 / Replay (37·38·39·40·41·42)

읽는 순서(VOL.2~6)는 B(전송 밑바닥)부터 위로 올라와. 근데 지금 이 트리를 봤으니, B를 팔 때도 "이 바이트가 결국 A(복제/RPC)를 실어나르는구나"를 알고 읽게 돼. 그게 이 지도의 쓸모야.

🌱 이 개념은 왜 생겼나 — 복제(replication)
• 원래 구조: 서버가 정한 진짜 상태를 클라에 알려줘야 하잖아. 제일 단순하겐 바뀔 때마다 손으로 패킷을 짜서 보내. HP 바뀌면 HP패킷, 위치 바뀌면 위치패킷… 우리 서버의 SP_*를 하나하나 손으로 만드는 그거야.
• 그런데 문제: 액터 한 마리에 동기화할 변수가 수십 개고, 액터가 수백 마리야. 그걸 전부 사람이 패킷 만들고 "이번엔 뭐가 바뀌었지" 일일이 챙기면 손이 남아나질 않아. 하나 빠뜨리면 클라 화면이 서버랑 어긋나고.
• 그래서 필요한 것: "이 변수는 동기화 대상"이라고 표시만 해두면 엔진이 바뀐 것만 알아서 보내주는 자동 장치. 이게 복제(replication)야. 서버 상태를 그대로 복제해서 맞춰준다는 뜻이지. 손으로 SP_ 짜던 걸 엔진이 diff 떠서 대신 해준다고 보면 돼.

3. 제일 중요한 두 기둥: 복제 vs RPC

트리에서 딱 하나만 기억하라면 A의 두 기둥이야. 초보가 실제로 제일 먼저, 제일 자주 만지는 게 이 둘이거든.

복제(Replication)RPC
성격상태를 계속 맞춤일회성 명령/이벤트
비유"칠판에 적힌 HP를 늘 최신으로""지금 종 한 번 쳐!"
예HP·위치·소유자가 바뀌면 자동 전송발사 요청, 폭발 이펙트, 채팅
언제 값이 감값이 바뀔 때 엔진이 알아서함수를 부를 때 그 순간만
첫 챕터→ lifetime-props (14장~)→ rpc-types (21장~)

우리 조선 서버로 치면 — 복제는 "SP_ 상태 패킷을 매번 손으로 안 짜도 엔진이 diff 떠서 보내주는 것", RPC는 "CM_/SM_ 요청/응답 패킷을 함수 호출처럼 쓰는 것"에 가까워.

4. 이제 어디로 — 바텀업으로 내려가자

지도는 다 봤어. 이제 VOL.2부터 밑바닥(전송 계층)을 판다. 각 챕터가 위 트리의 어느 가지인지 알고 읽으면 돼.

  • 정공법(추천): 다음 → netconnection-overview 부터 순서대로. 바이트가 어떻게 채널·복제까지 올라오는지 "패킷의 여정"으로 쭉 따라간다.
  • 급하면 찍먹: "내가 당장 뭘 하는지" 손부터 풀고 싶으면 → lifetime-props(변수 복제) 와 rpc-types(RPC) 를 먼저 맛보고 돌아와도 좋아. 동기부여가 확 생겨.
  • 챕터끼리 파란 링크로 이어져 있으니 어느 길로 가도 안 막혀.
