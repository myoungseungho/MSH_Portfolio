서버 보정 — ClientAdjustPosition

언리얼 네트워크 · 31 / 42

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "서버가 '너 위치 틀렸어' 하고 클라를 되돌릴 때, 그 신호가 어느 함수에서 출발해서 어느 함수로 도착하는지"가 머릿속에 그려질 거야.
client-prediction의 바로 다음 편이야. 저긴 "클라가 서버 안 기다리고 먼저 움직이는 쪽", 여긴 "그 먼저 움직인 걸 서버가 채점하고, 틀렸으면 되돌리는 쪽".

0. 먼저 비유부터 — 받아쓰기 채점

받아쓰기 시험을 생각해봐. 선생님이 불러주고, 너는 공책에 네 나름대로 적어. 다 적고 나서 선생님한테 공책을 내밀지. 그럼 선생님이 두 가지 중 하나를 해.

  • 다 맞았으면 동그라미 쫙 치고 "통과". → 너는 그냥 다음 문제로 넘어감.
  • 한 군데 틀렸으면 빨간 펜으로 정답을 써주고, "여기부터 다시 써". → 너는 그 지점으로 돌아가서 다시 받아쓰기.

여기서 중요한 건, 선생님이 정답을 아는 유일한 권위자라는 거야. 네 공책이 아무리 자신 있어도, 선생님 빨간 펜이 최종이야.

서버 보정(server reconciliation)이 딱 이거야.

  • 네 공책 = 클라가 예측해서 먼저 움직인 위치.
  • 선생님한테 공책 냄 = ServerMove RPC (클라→서버, 지난 챕터 주제).
  • 선생님이 채점 = 서버가 자기 권위 시뮬레이션이랑 클라 위치를 비교.
  • 동그라미 = ClientAckGoodMove ("그 이동 OK, 통과").
  • 빨간 펜 정답 + 다시 써 = ClientAdjustPosition ("여기가 정답이야, 이 지점부터 다시 replay해").

핵심 직관 하나만 먼저 박아두자.

서버가 유일한 채점자다. 클라는 먼저 움직이지만, 최종 판정은 서버가 한다. 맞았으면 동그라미(Ack), 틀렸으면 빨간 펜(Adjust)으로 정답 위치를 강제한다.

그럼 이 챕터의 진짜 질문은 이거 하나야:

서버는 "틀렸다"는 판정을 어디서 시작해서, 어떤 함수 체인을 타고 클라한테 "되돌려" 신호를 쏘냐?

이걸 실제로 구현한 함수들을 밟아보자. 그런데 시작하기 전에 정직하게 짚을 게 하나 있어. 지난 챕터랑 똑같은 사정이야.

🔬 소스 포함 상태 — 심장은 빠져 있다

이 학습 트리에는 보정 루프의 "판정하는 심장"이 없다.

서버가 클라 위치를 실제로 비교해서 오차를 재고, 되돌림 RPC를 발사하고, 클라가 받아서 재시뮬레이션하는 정본 몸통 — ServerMoveHandleClientError, ClientAdjustPosition_Implementation의 실제 본체, SendClientAdjustment의 CMC 구현부 — 는 원래 CharacterMovementComponent.cpp(약 1만 줄)에 있는데, 그 파일이 이 서브셋에 빠져 있어. Character.h의 RPC 선언부도 없음.

그래서 이 챕터는 실물이 있는 조각으로 "심장으로 가는 배관"만 조립한다:

  1. NetDriver.cpp — 서버 틱이 매 커넥션마다 보정 송신을 촉발하는 드라이버 루프. verbatim 존재. ✅
  2. PlayerController.cpp — PC가 "이건 내가 조종하는 폰이네?" 확인하고 이동 컴포넌트로 위임하는 관문. verbatim 존재. ✅
  3. Character.cpp — 서버가 이동을 받는 RPC, 클라가 보정을 받는 RPC — 이 얇은 포워더들 verbatim 존재. ✅

즉 판정 로직으로 들어가는 입구와 나오는 출구는 다 있는데, 판정 그 자체(오차 비교·되돌림 계산)만 미포함. 그 부분은 아래 "개념 재료"로만 정리한다. 정확한 함수 본체·라인이 필요하면 UE 원본 CharacterMovementComponent.cpp를 따로 대조해야 해.

1. 전체 콜체인 한 장으로

보정 신호가 흐르는 두 방향이 있어. ① 서버가 채점 결과를 클라로 쏘는 쪽(정방향)과 ② 클라 이동이 서버로 들어와 채점을 촉발하는 쪽(역방향). ★는 이 트리에 실물 없음(CMC.cpp), ✅는 실물 있음.

── 서버 → 클라 : "되돌려" 신호 발사 ──────────────────────── UNetDriver::SendClientMoveAdjustments() NetDriver.cpp:7565 ✅ │ 모든 ClientConnections 순회 ▼ PC->SendClientAdjustment() NetDriver.cpp:7578 ✅ │ (replication tick 경로에도 별도 콜사이트) │ Connection->PlayerController->SendClientAdjustment() NetDriver.cpp:5789 ✅ ▼ APlayerController::SendClientAdjustment() PlayerController.cpp:1768 ✅ │ RemotePawn 이 AutonomousProxy 이고, 나는 서버일 때만 ▼ INetworkPredictionInterface->SendClientAdjustment() PlayerController.cpp:1778 ✅ │ ▼ ┌──────────────────────────────────────────────┐ │ ★ 여기부터 CMC 본문 (미포함) │ │ ServerMoveHandleClientError() │ │ → 오차 크면 ClientAdjustPosition RPC 발사 │ │ → 오차 없으면 ClientAckGoodMove RPC 발사 │ └──────────────────────────────────────────────┘ │ (오차 큼) │ (오차 없음) ▼ ▼ ── 클라 수신 : 채점 결과 도착 ────────────────────────────── ACharacter::ClientAdjustPosition_Impl() ACharacter::ClientAckGoodMove_Impl() Character.cpp:1953 ✅ Character.cpp:1947 ✅ │ GetCharacterMovement() 위임 │ GetCharacterMovement() 위임 ▼ ▼ ★ CMC::ClientAdjustPosition_Impl() ★ CMC::ClientAckGoodMove_Impl() "정답부터 SavedMoves 재적용(replay)" "그 이동을 SavedMove 큐에서 제거" ── (참고) 애초에 채점은 여기서 촉발됨: 클라 이동 수신 ────────── ACharacter::ServerMove_Implementation() Character.cpp:1869 ✅ │ 또는 ServerMovePacked_Implementation() Character.cpp:1857 ✅ ▼ ★ CMC::ServerMove_Implementation() └─ ServerMoveHandleClientError() 호출 → 위 발사 경로로 이어짐

한눈에 안 들어와도 괜찮아. 딱 세 줄로 압축하면 이거야:

  1. 서버 틱이 커넥션마다 SendClientAdjustment()를 부른다 (NetDriver).
  2. PC가 "이거 그 클라가 조종하는 폰 맞아?" 확인하고 이동 컴포넌트로 넘긴다 (PlayerController).
  3. 이동 컴포넌트(미포함)가 오차를 재서, 크면 ClientAdjustPosition(되돌려), 작으면 ClientAckGoodMove(통과)를 클라로 쏜다.

이제 실물 코드로 한 칸씩 밟자.

2. 실물 코드 — 배관을 따라가며

서버 틱이 전 커넥션을 돌며 보정 송신 — NetDriver.cpp:7565

서버는 매 네트워크 틱마다 접속한 모든 클라이언트를 한 바퀴 돌면서 "너한테 보정 보낼 거 있냐?"를 확인해. 그 진입 루프가 이거야.

void UNetDriver::SendClientMoveAdjustments() { QUICK_SCOPE_CYCLE_COUNTER(STAT_SendClientMoveAdjustments); for (UNetConnection* Connection : ClientConnections) { if (Connection == nullptr || Connection->ViewTarget == nullptr) { continue; } if (APlayerController* PC = Connection->PlayerController) { PC->SendClientAdjustment(); }

ClientConnections를 for로 도는 게 보이지? 커넥션 하나가 클라 한 명이야. 각자의 PlayerController한테 SendClientAdjustment()를 부른다. 여기선 아직 "보정할지 말지"를 결정 안 해. 그냥 "결정하러 가봐" 하고 각 PC한테 떠넘기는 단계야.

"보정은 패킷당 최대 1회"라는 정책 — NetDriver.cpp:5785

replication tick 경로엔 콜사이트가 하나 더 있는데, 여기 붙은 주석이 중요한 설계 철학을 담고 있어.

// send ClientAdjustment if necessary // we do this here so that we send a maximum of one per packet to that client; there is no value in stacking additional corrections if (Params.Connection->PlayerController) { Params.Connection->PlayerController->SendClientAdjustment(); }

주석 번역: "보정은 한 패킷에 최대 한 번만 보낸다. 보정을 여러 개 쌓아 보내봤자 아무 가치가 없으니까."

왜 그럴까? 잠깐 맞춰봐. 오차가 크게 났으면 보정을 여러 번 팡팡 보내서 빨리 따라잡게 하는 게 낫지 않아?

...

아니야. 정답 위치는 가장 최근 것 하나면 충분하거든. 낡은 보정 위치를 클라가 받아봤자 어차피 그 다음 최신 보정이 덮어써. 정답을 두 번 세 번 겹쳐 보내는 건 대역폭만 잡아먹는 낭비야. "최신 정답 한 방"이 제일 싸고 정확해. 이 한 줄 주석이 UE 네트워크 설계의 검약(儉約) 철학을 그대로 보여줘.

PC가 이동 컴포넌트로 위임 — PlayerController.cpp:1768

이제 각 PC 차례. 여기서 "이 폰한테 보정을 보낼 자격이 있냐"를 걸러낸다.

void APlayerController::SendClientAdjustment() { // Server sends updates. // Note: we do this for both the pawn and spectator in case an implementation has a networked spectator. APawn* RemotePawn = GetPawnOrSpectator(); if (RemotePawn && (RemotePawn->GetRemoteRole() == ROLE_AutonomousProxy) && !IsNetMode(NM_Client)) { INetworkPredictionInterface* NetworkPredictionInterface = Cast<INetworkPredictionInterface>(RemotePawn->GetMovementComponent()); if (NetworkPredictionInterface) { NetworkPredictionInterface->SendClientAdjustment(); } } }

if 조건 세 개를 뜯어보자. 이게 이 함수의 전부야.

  • RemotePawn->GetRemoteRole() == ROLE_AutonomousProxy — 그 클라가 직접 조종하는 폰일 때만. 남이 조종하는 폰(SimulatedProxy)은 어차피 보간만 하니까 보정 대상이 아니야.
  • !IsNetMode(NM_Client) — 나는 서버여야 한다. 클라가 클라한테 보정을 보낼 순 없잖아. 채점은 권위자만.
  • 조건 통과하면 → 폰의 이동 컴포넌트를 INetworkPredictionInterface로 캐스팅해서 SendClientAdjustment() 위임.

여기서 마지막 줄, NetworkPredictionInterface->SendClientAdjustment() — 이 화살표를 넘어가는 순간 CMC 본문(미포함)으로 들어간다. PC는 이동 컴포넌트의 구체 타입을 몰라. 그냥 "예측/보정 인터페이스"라는 추상 손잡이만 잡고 호출해. 실제로 오차를 재고 RPC를 쏘는 건 저 인터페이스 뒤에 숨은 CMC야.

🔬 이 지점 이후 — ServerMoveHandleClientError가 클라 최종 위치(ClientLoc)와 서버 권위 위치를 비교 → 오차가 임계값 넘으면 ClientAdjustPosition RPC, 아니면 ClientAckGoodMove RPC — 는 이 클론에 소스 미포함. 개념만, 실제 대조 필요.

클라 이동을 서버가 받는 입구 — Character.cpp:1868

역방향도 보자. 애초에 채점이 촉발되려면 클라 이동이 서버로 들어와야 해. 그 수신 RPC의 진입점이 여기야.

// ServerMove void ACharacter::ServerMove_Implementation(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { GetCharacterMovement()->ServerMove_Implementation(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

파라미터에 ClientLoc(클라가 "내가 여기 있어요" 하고 보고한 최종 위치)랑 TimeStamp(어느 이동인지 식별하는 시각 도장)가 보이지? ACharacter는 아무 판단도 안 해. 그냥 GetCharacterMovement()한테 통째로 넘겨. 실제 오차 판정(ServerMoveHandleClientError)은 저 안(미포함)에서 벌어져. ACharacter는 문지기가 아니라 우체통이야.

(비트스트림으로 압축된 신형 ServerMovePacked_Implementation은 Character.cpp:1857에서 언팩만 하고 결국 같은 판정 경로로 흘러간다.)

클라가 "되돌려" 신호를 받는 입구 — Character.cpp:1952

그리고 이 챕터의 주인공. 서버가 "네 위치 틀렸어, 이게 정답이야" 하고 쏜 보정을 클라가 받는 지점.

// ClientAdjustPosition void ACharacter::ClientAdjustPosition_Implementation(float TimeStamp, FVector NewLoc, FVector NewVel, UPrimitiveComponent* NewBase, FName NewBaseBoneName, bool bHasBase, bool bBaseRelativePosition, uint8 ServerMovementMode) { GetCharacterMovement()->ClientAdjustPosition_Implementation(TimeStamp, NewLoc, NewVel, NewBase, NewBaseBoneName, bHasBase, bBaseRelativePosition, ServerMovementMode); }

NewLoc(정답 위치), NewVel(정답 속도), TimeStamp(이 정답이 몇 번 이동에 대한 건지). 역시 ACharacter는 우체통. 되돌려-replay 하는 진짜 몸통은 GetCharacterMovement()->ClientAdjustPosition_Implementation()(미포함). 거기서 클라는 TimeStamp 이후 큐에 쌓아둔 입력(SavedMoves)을 정답 위치부터 순서대로 다시 밟아 현재 프레임까지 따라잡아. 이게 "되돌려 replay"의 실체야.

오차 없을 때 "통과" 확인 — Character.cpp:1946

틀렸을 때만 있으면 반쪽이지. 맞았을 때도 서버는 신호를 보내. "그 이동 OK".

// ClientAckGoodMove void ACharacter::ClientAckGoodMove_Implementation(float TimeStamp) { GetCharacterMovement()->ClientAckGoodMove_Implementation(TimeStamp); }

TimeStamp 하나만 달랑 있지? 위치 정보가 필요 없어. "몇 번 이동이 통과됐다"만 알려주면 클라는 SavedMoves 큐에서 그 이동을 지워. 통과된 건 더 붙들고 있을 이유가 없거든. 큐가 안 비면 메모리도 쌓이고 나중에 replay할 때 헛되게 밟게 돼. 그래서 ClientAdjustPosition(되돌려)과 ClientAckGoodMove(통과)는 동전의 양면 — 채점 결과가 둘 중 하나로 반드시 돌아온다.

3. 헷갈리는 용어 4개만

  • AutonomousProxy (ROLE_AutonomousProxy): 그 클라이언트가 "내가 직접 조종하는" 폰. 서버는 이 역할의 폰한테만 위치 보정을 쏜다. 남의 폰(SimulatedProxy)은 보간만 하니까 대상 아님. PlayerController.cpp:1773의 if 조건이 이걸 검사.
  • INetworkPredictionInterface: 이동 컴포넌트가 구현하는 "클라 예측/서버 보정" 추상 인터페이스. PC는 구체 타입(CMC인지 뭔지)을 몰라도 이 손잡이로 SendClientAdjustment()를 부른다. 다형성으로 CMC 본문을 숨기는 벽.
  • ClientAdjustPosition vs ClientAckGoodMove: 서버 채점 후 오는 두 응답. 오차 크면 ClientAdjustPosition(정답 위치 강제 → 클라가 되돌려 replay), 오차 없으면 ClientAckGoodMove(그 이동 승인 → SavedMove 큐에서 제거).
  • TimeStamp: 각 이동에 붙는 클라 시각 도장. 보정/승인 응답이 "어느 이동에 대한 것인지" 맞추는 열쇠. SavedMoves 큐에서 이 값으로 해당 이동을 찾아 제거하거나, 그 지점부터 재시뮬레이션한다. TimeStamp가 없으면 "몇 번째 걸 되돌리라는 거야?"를 알 수가 없어.

(SavedMove / ServerMove의 클라 송신 쪽 상세는 → client-prediction에서 이미 다뤘어. 여기선 링크로 대체.)

4. 우리 서버랑 비교 — IOCP 워커 vs UE 채점 루프

우리 조선 서버 감각으로 옮겨보면 이해가 확 빨라져.

우리 서버 (IOCP + 싱글스레드 액터):

[IOCP 워커 스레드 N개] ── 패킷 수신 ──▶ [단일 로직 스레드] (여러 스레드가 소켓에서 (모든 이동/판정을 이동 패킷을 긁어옴) 한 줄로 직렬 처리)

클라가 "나 (100, 50)으로 이동했음" 패킷을 보내면, IOCP 워커가 받아서 큐에 넣고, 단일 로직 스레드가 하나씩 꺼내서 "이 이동이 정상 속도냐? 벽 뚫었냐? 좌표 정상이냐?"를 검증해. 이상하면 서버가 정답 좌표를 강제 세팅하고 클라한테 "SC_위치보정" 같은 패킷을 도로 쏘지. 우리도 서버가 최종 권위자야.

UE 대응:

우리 서버UE
IOCP 워커가 이동 패킷 수신NetDriver가 커넥션에서 ServerMove RPC 수신
단일 로직 스레드가 직렬 검증게임 스레드가 ServerMoveHandleClientError로 오차 판정
"SC_위치보정" 패킷 강제 송신ClientAdjustPosition RPC 발사
"정상 처리됨" (보통 응답 생략)ClientAckGoodMove RPC (통과도 명시적으로 알림)
좌표 하드 세팅 후 끝클라가 SavedMoves를 정답부터 replay (핑 숨김 복원)

차이 하나만 콕 집으면: 우리 서버는 보통 "틀렸을 때만" 보정 패킷을 쏘고 정상이면 조용해. UE는 통과도 ClientAckGoodMove로 꼬박꼬박 알려줘 — 클라가 SavedMove 큐를 정확히 비워서 다음 replay를 깔끔하게 하려고. 그리고 UE 클라는 보정받으면 좌표만 딱 바꾸는 게 아니라 그 지점부터 그동안 쌓인 입력을 다시 재생(replay) 해서 핑만큼의 시간차를 복원해. 우리 서버는 보통 좌표 하드 세팅에서 끝나는 게 흔하지. 이 "replay로 따라잡기"가 UE 예측 시스템의 정수야.

5. 다시, 한 바퀴 정리

  • 서버는 틱마다 전 커넥션을 돌며 SendClientAdjustment()를 부른다 (NetDriver.cpp:7565).
  • PC가 "AutonomousProxy + 나는 서버" 조건을 걸러 이동 컴포넌트 인터페이스로 위임한다 (PlayerController.cpp:1768).
  • 그 뒤 CMC 본문(미포함)이 클라 위치 vs 서버 위치 오차를 재서 → 크면 ClientAdjustPosition, 작으면 ClientAckGoodMove를 쏜다.
  • 클라의 ACharacter는 그 RPC를 받아 얇게 포워딩만 하고(Character.cpp:1953/1947), 진짜 되돌려-replay는 CMC가 한다.
  • 보정은 패킷당 최대 1회 — 최신 정답 한 방이면 충분하니까 (NetDriver.cpp:5785 주석).

이 챕터에서 실물로 확인한 건 "심장으로 가는 배관과, 심장에서 나오는 배관"이야. 심장 그 자체(오차 비교·replay 계산)는 CharacterMovementComponent.cpp에 있고 이 트리엔 없어. 딱 거기까지가 이 클론으로 정직하게 말할 수 있는 범위야.

참조

  • 막히면 → client-prediction (SavedMove/ServerMove가 뭔지, 클라가 왜 먼저 움직이는지 — 이 챕터의 전제)
  • 막히면 → charactermovement-overview (캐릭터가 애초에 어떻게 움직이는지, 로컬 이동 뼈대)
  • 막히면 → rpc-types (ServerMove/ClientAdjustPosition이 어떤 종류의 RPC인지)
  • 다음 → simulated-proxy-smoothing (남이 조종하는 폰은 보정 대신 어떻게 부드럽게 보간되는지)
  • 곁가지 → server-time-sync (TimeStamp가 기준 삼는 서버-클라 시각 동기화)
  • 곁가지 → lag-compensation (서버가 과거 시점으로 되감아 판정하는 히트 보정)

서버가 유일한 채점자다 — 클라는 먼저 움직이고, 서버는 틱마다 오차를 재서 틀렸으면 ClientAdjustPosition으로 정답 위치를 강제하고(클라는 그 지점부터 replay), 맞았으면 ClientAckGoodMove로 통과시킨다. 보정은 최신 한 방이면 족하다.
