클라 예측: SavedMove로 먼저 움직이고, ServerMove로 보고하기

언리얼 네트워크 · 30 / 42

먼저 움직이고 나중에 허락받기

핑이 100ms라고 해보자. 내가 W를 눌러. 서버한테 "나 앞으로 갈게" 물어보고, 서버가 "그래 가"라고 답할 때까지 기다렸다가 움직이면? 0.1초 뒤에야 캐릭터가 꿈틀해. 조작이 진흙탕처럼 느껴져. 게임이 못 나가.

그래서 온라인 게임은 반대로 해. 일단 내 화면에선 먼저 움직여버려. 서버 허락은 안 기다려. 대신 "나 이렇게 움직였어"를 서버에 보고서로 부쳐둬. 서버가 나중에 "맞네" 하면 그대로 두고, "아닌데?" 하면 그때 되돌려. 이걸 클라이언트 예측(client-side prediction)이라고 해. 낙관적으로 먼저 믿고 가는 거지.

근데 "먼저 움직였다"는 걸 나중에 되돌리려면, 내가 뭘 어떻게 움직였는지 기록해둬야 해. 안 그러면 서버가 "너 3프레임 전 위치가 틀렸어" 했을 때 그 3프레임을 다시 밟을 수가 없잖아. 그 기록 한 장 한 장이 FSavedMove_Character고, 그걸 서버로 부치는 우편이 ServerMove RPC야.

이번 챕터는 딱 이 흐름 — "먼저 움직임 → SavedMove로 저장 → ServerMove로 발송 → 서버가 받음 → 맞다/틀리다 회신" 중에서 앞의 세 계단(예측하고 보내는 쪽)에 집중해. 서버가 틀렸다고 되돌리는 조정(reconciliation)은 다음 챕터로 넘겨.

CharacterMovement가 처음이면, "한 캐릭터가 세 역할(내 것/서버/남의 것)로 갈린다"는 큰 그림부터 → charactermovement-overview. 이 챕터는 그중 "내 것(AutonomousProxy)"이 예측하고 보고하는 한 갈래만 확대한 거야.

⚠️ 먼저: 예측의 심장(송신 루프)은 이 클론에 없어

정직하게 깔고 가자. 클라가 무브를 저장하고 서버로 부치는 진짜 송신 루프 — UCharacterMovementComponent::ReplicateMoveToServer, FSavedMove_Character::SetMoveFor, CallServerMovePacked, 그리고 서버 회신 후 되감아 재생하는 ClientUpdatePositionAfterServerUpdate — 는 전부 CharacterMovementComponent.cpp(약 1만 줄)에 있는데, 이 학습 트리엔 그 파일이 없어. grep으로 찾아도 안 나와.

🔬 이 클론에 소스 미포함 — 개념 위주, 실제 대조 필요 ReplicateMoveToServer / FSavedMove_Character(예측용 저장 무브) / FNetworkPredictionData_Client_Character(무브 버퍼) / CallServerMovePacked / ClientUpdatePositionAfterServerUpdate — 이 함수·구조체 본체는 못 읽어. 그래서 "저장하고 보내는 쪽"은 개념으로만 설명하고, 정확한 코드는 Epic 원본 트리로 대조해야 해.

그럼 이 트리에서 실물로 읽을 수 있는 건 딱 두 가지야. 둘 다 예측의 "받는 쪽·회신하는 쪽"이라, 송신 알맹이는 개념으로 세우고 이 두 실물이 그걸 양쪽에서 증언하게 엮을 거야.

파일이 챕터에서 읽을 것
CharacterMovementComponentAsync.cpp예측 송신이 어디서 갈라지는지 그 갈림길(주석 처리된 골격)
Character.cpp클라가 부친 SavedMove가 서버에 도착하는 진입점(ServerMove 계열) + 서버의 두 가지 회신(Ack / Adjust)

1) SavedMove — "되돌리기용 기록 한 장" (개념)

예측의 출발점은 저장이야. 클라가 이번 프레임에 움직이면, 그 무브를 통째로 한 장에 적어 버퍼에 쌓아둬. 한 장에 뭐가 적히냐면 — 스니펫 [S3]에서 볼 ServerMove의 인자 목록이 사실상 그 "한 장"이야. 미리 요약하면:

  • TimeStamp — 이 무브의 시각(일련번호 역할). 서버가 순서 맞추고 오래된 건 버리는 기준.
  • Acceleration — 이 프레임에 내가 준 입력 방향(가속도).
  • MoveFlags — 점프·크라우치 같은 bool 입력을 비트로 눌러담은 것.
  • (도달한 위치·이동 모드 등)

이 SavedMove들이 버퍼에 줄줄이 쌓여. 왜 하나만 안 남기고 쌓냐면 — 서버 회신은 왕복 지연(핑)만큼 늦게 오거든. 서버가 "TimeStamp 100번 무브까지 봤어"라고 답할 때, 클라는 이미 105·106·107번을 예측으로 밟고 있어. 그래서 "아직 서버 확인 못 받은 무브들"을 버려선 안 돼 — 서버가 100번을 틀렸다고 하면 101~107을 다시 밟아야 하니까(재생/reconciliation, 다음 챕터).

🔬 이 버퍼(FNetworkPredictionData_Client_Character)와 저장 함수(SetMoveFor) 본체는 미포함. 여기까진 "왜 쌓는가"만 잡고 가자.

2) 예측의 갈림길 — "먼저 움직임 vs 서버 보고" (실물 골격)

이제 실물. 이동 계산 진입점(ControlledCharacterMove)의 끝부분을 보면, 예측이 정확히 어디서 두 갈래로 갈리는지 골격이 그대로 남아 있어. 비록 주석 처리돼 있지만, 이 주석이 미포함 심장의 구조를 대신 증언해줘.

[S1] 예측의 갈림길 — CharacterMovementComponentAsync.cpp:95–104

// TODO Networking //if (LocalRole == ROLE_Authority) { PerformMovement(DeltaSeconds, Output); } /*else if (CharacterOwner->GetLocalRole() == ROLE_AutonomousProxy && IsNetMode(NM_Client)) { ReplicateMoveToServer(DeltaSeconds, Acceleration); }*/ }

이 열 줄이 이 챕터에서 제일 값진 스니펫이야. 갈림길을 봐:

  • if (LocalRole == ROLE_Authority) → PerformMovement — 직접 이동시켜. 서버(권위)가 여기 타. 그리고 예측하는 나(클라)도 사실 이 PerformMovement를 타서 "먼저 움직여."
  • else if (AutonomousProxy && 클라) → ReplicateMoveToServer — 이게 예측의 핵심 송신구. "먼저 움직인 그 무브를 SavedMove로 저장하고, ServerMove RPC로 서버에 부치는" 함수야.

정본(진짜 CMC)에선 클라가 이 둘을 한 프레임에 다 해 — PerformMovement로 내 화면에서 먼저 움직이고, 곧바로 ReplicateMoveToServer로 그 무브를 서버에 보고. "먼저 믿고 → 보고서 부치기"가 이 두 줄에 압축돼 있어.

여기서 두 가지만 못 박자.

  1. 이 async 버전은 // TODO Networking이 붙고 else 갈래가 통째로 /* */ 주석 — 즉 송신 루프가 아직 이식 안 됨. 물리(PerformMovement)만 강제로 도는 반쪽이야. 그래서 ReplicateMoveToServer 본체는 어디서도 못 읽어(🔬).
  2. 그래도 분기 조건(AutonomousProxy && 클라)은 살아 있어서, 예측이 "내 캐릭터일 때만" 일어난다는 걸 골격으로 증언해. 남 캐릭터(SimulatedProxy)는 여기 못 들어와 — 걔는 예측이 아니라 받아서 따라가니까(→ simulated-proxy-smoothing).

3) 부친 우편이 서버에 도착하는 자리 (실물)

ReplicateMoveToServer 본체는 못 봐도, 그게 부친 우편이 서버 문 앞에 도착하는 곳은 실물로 있어. 클라의 SavedMove는 결국 ServerMove RPC가 돼서 서버의 이 함수로 들어와.

한 가지 함정: RPC 함수는 문법상 ACharacter에 선언돼 있는데, 실제 로직은 CMC에 있어. 그래서 Character.cpp의 이 함수들은 전부 GetCharacterMovement()->...로 CMC에 넘기기만 해(넘겨받는 CMC 본체는 미포함). 우리가 실물로 보는 건 이 "넘기는 손"과, 무엇보다 인자 목록이야.

[S3] 클라가 실어 보낸 예측 데이터 — Character.cpp:1868–1877

// ServerMove void ACharacter::ServerMove_Implementation(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { GetCharacterMovement()->ServerMove_Implementation(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); } bool ACharacter::ServerMove_Validate(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { return GetCharacterMovement()->ServerMove_Validate(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

이 인자 목록이 바로 1번에서 말한 "SavedMove 한 장"이 전선을 타고 온 모습이야. 예측의 3대 핵심만 짚자:

  • TimeStamp — 이 무브가 몇 번째인가. 서버는 이걸로 순서를 맞추고, 자기가 이미 본 것보다 오래된 무브면 버려.
  • InAccel(FVector_NetQuantize10) — 내가 준 입력 방향. 서버가 이걸로 똑같이 이동을 재현해봐(내가 화면에서 한 계산을 서버도 반복).
  • ClientLoc(FVector_NetQuantize100) — 내가 예측으로 도달했다고 주장하는 위치. 서버는 자기 재현 결과와 이걸 비교해. 벌어지면 → 4번의 되돌리기.

FVector_NetQuantize10 / 100이 붙은 이유는 대역폭이야. 이동 보고는 초당 수십 번 날아가니까 float 정밀도를 깎아 압축 전송해(→ replayout). 그리고 _Implementation(실제 처리)과 _Validate(서버가 클라 말을 믿기 전 문지기 검증)가 짝으로 붙어다니는 건 모든 RPC 규칙이야(→ rpc-reliable-validation).

왜 "Dual"이 따로 있나 — 지연·유실 흡수

여기서 하나 더. 서버 수신 진입점엔 ServerMove만 있는 게 아니라 ServerMoveDual도 있어.

[S5] 이중 무브 수신 — Character.cpp:1890–1894

// ServerMoveDual void ACharacter::ServerMoveDual_Implementation(float TimeStamp0, FVector_NetQuantize10 InAccel0, uint8 PendingFlags, uint32 View0, float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 NewFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { GetCharacterMovement()->ServerMoveDual_Implementation(TimeStamp0, InAccel0, PendingFlags, View0, TimeStamp, InAccel, ClientLoc, NewFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

인자를 잘 봐 — TimeStamp0 / InAccel0 / PendingFlags(직전 펜딩 무브)와 TimeStamp / InAccel / NewFlags(이번 무브)가 한 함수에 두 벌 들어 있지? 이게 "이중(Dual)"의 뜻이야. 클라가 무브를 매 프레임 낱개로 부치면 패킷이 폭발하니까, 직전에 못 보낸 펜딩 무브 + 이번 무브를 한 우편에 묶어 보내. 하나가 도중에 유실돼도 다음 Dual에 실려 복구될 여지가 생기고, 패킷 수도 준다. 예측을 싸고 튼튼하게 굴리는 최적화지. 뼈대(SavedMove를 부친다)는 ServerMove와 똑같아.

4) 서버의 회신 — 맞으면 버려, 틀리면 되돌려 (실물)

우편을 받은 서버는 재현·검증하고 나서, 클라에게 둘 중 하나로 답장해. 이 두 답장이 예측 루프를 닫는 자리야. 둘 다 실물로 있어.

[S6] 두 가지 회신 — Character.cpp:1946–1956

// ClientAckGoodMove void ACharacter::ClientAckGoodMove_Implementation(float TimeStamp) { GetCharacterMovement()->ClientAckGoodMove_Implementation(TimeStamp); } // ClientAdjustPosition void ACharacter::ClientAdjustPosition_Implementation(float TimeStamp, FVector NewLoc, FVector NewVel, UPrimitiveComponent* NewBase, FName NewBaseBoneName, bool bHasBase, bool bBaseRelativePosition, uint8 ServerMovementMode) { GetCharacterMovement()->ClientAdjustPosition_Implementation(TimeStamp, NewLoc, NewVel, NewBase, NewBaseBoneName, bHasBase, bBaseRelativePosition, ServerMovementMode); }

인자를 보면 두 회신의 성격이 극명하게 갈려.

  • ClientAckGoodMove(TimeStamp) — 인자가 TimeStamp 딱 하나야. 위치 정보가 없어. "네 TimeStamp까지 무브 다 맞았어, OK." 위치를 안 보내는 게 핵심 — 예측이 맞았으니 고칠 게 없거든.
  • ClientAdjustPosition(TimeStamp, NewLoc, NewVel, ...) — 이쪽은 NewLoc(정답 위치)·NewVel(정답 속도)를 잔뜩 실어와. "네 예측 틀렸어, 진짜 위치는 여기야."

자, 예측해봐. 클라가 SavedMove 버퍼에 무브를 잔뜩 쌓아뒀다고 했지(1번). 서버가 ClientAckGoodMove(100)을 보내오면, 클라는 그 100번 무브를 다시 밟아서 재생할까?

...

아니야. 정반대야. 맞았다는 통보(Ack)를 받으면 클라는 그 무브들을 재생하는 게 아니라 폐기(버퍼에서 제거)해. 되돌릴 일이 없으니 기록을 지우는 거지 — 버퍼가 무한정 부풀지 않게. 되밟기(재생)는 오히려 반대쪽, ClientAdjustPosition(틀렸다)을 받았을 때 일어나: 서버가 준 NewLoc으로 위치를 되돌린 다음, 그 이후의 SavedMove들(101·102·...)을 다시 적용해 현재 위치를 재계산해. (반전!)

🔬 그 되밟기 재생 함수 ClientUpdatePositionAfterServerUpdate의 본체는 이 클론에 없어. async 파일엔 호출 예정 주석(// Call ClientUpdatePositionAfterServerUpdate();, CharacterMovementComponentAsync.cpp:30)만 골격으로 남아 있고, 알맹이는 다음 챕터에서 개념으로 판다 → server-reconciliation.

즉 예측 루프는 이렇게 닫혀: 맞으면 버려(Ack) / 틀리면 되돌리고 다시 밟아(Adjust). 이 두 갈래가 예측을 "낙관적이되 결국 서버가 정답"이게 만드는 안전장치야.

콜체인 한 장 그림

예측은 "클라가 먼저 → 서버가 나중"이라 시간축(왕복)으로 그리는 게 제일 잘 보여. 🔬는 이 클론에 본체 없는 구간(개념).

세 계단만 기억해. ① 클라는 먼저 움직이고(PerformMovement) 그 무브를 SavedMove로 쌓으며 ServerMove로 부친다. ② 서버는 재현·검증한다. ③ 맞으면 Ack로 버퍼를 비우고, 틀리면 Adjust로 되돌린 뒤 이후 무브를 다시 밟는다. 🔬 박스들(ReplicateMoveToServer·SavedMove 버퍼·재현검증·재생)이 이 클론에 본체 없는 심장 — 인자·진입점·회신 껍데기는 실물로 봤고 알맹이는 개념이야.

UE 클라 예측우리 서버 대응차이
예측(서버 답 안 기다리고 먼저 움직임)얇거나 없음 — 클라가 이동 요청 보내고, 서버 판정을 사실상 기다림UE는 지연 은폐가 기본, 우린 그 계층이 얇아 핑이 곧 조작감
SavedMove 버퍼(미확인 무브 보관)대응물 거의 없음 — 되돌릴 기록을 클라가 안 쌓음UE만의 롤백 준비물
ServerMove RPC(무브 보고)이동 패킷 → CM_MOVE 류 핸들러개념 동일. UE는 함수 호출로 위장, 우린 패킷 ID 스위치
ServerMove_Validate(서버 검증)이동 핸들러 안 좌표·속도 유효성 체크(맵 이탈/속도핵)목적 같음. UE는 재현까지 해 비교, 우린 룰 기반 검사 위주
ClientAckGoodMove(맞음, 버퍼 청소)대개 명시적 Ack 없음(암묵 진행)UE는 예측 루프라 Ack가 버퍼 수명관리에 필수
ClientAdjustPosition(틀림, 되돌림)서버가 강제 좌표교정 패킷(SM_ 순간이동) 송신UE는 되돌린 뒤 재생(re-sim), 우린 대개 그냥 순간이동

핵심 차이 하나만 못 박자. UE 예측 = "클라가 먼저 믿고 움직이되(예측), 미확인 무브를 SavedMove로 쌓아두고, 서버가 틀렸다면 되돌려 다시 밟는다(재생)." 이 "쌓아두고 되밟기"가 UE 이동이 부드러운데도 서버 권위를 지키는 비결이야. 우리 서버는 이 버퍼·재생 계층이 얇아서, 어긋나면 되밟기 없이 순간이동으로 끊어붙여(그래서 가끔 튐/rubber-banding이 더 거칠어).

그리고 스레드. 우리 IOCP 워커는 여러 스레드로 CM_MOVE를 받지만, 실제 이동 판정은 싱글스레드 액터 큐로 직렬화해서 처리해. UE도 ServerMove 재현·검증은 게임 스레드에서 직렬로 돌아(async 물리는 별도 Chaos 스레드지만 결과는 게임 스레드로 합류). "받는 건 병렬, 판정은 직렬" 뼈대가 양쪽 다 같아 — 우리 IOCP 액터 큐 = UE 게임 스레드 틱이라고 보면 돼.

🎯 원리 한 줄 요약

클라 예측은 서버 허락을 기다리지 않고 내 화면에서 먼저 움직인 뒤(PerformMovement), 그 무브를 SavedMove로 버퍼에 쌓으며 ServerMove RPC로 서버에 부치고, 서버 회신이 "맞음(ClientAckGoodMove)"이면 그 무브를 폐기하고 "틀림(ClientAdjustPosition)"이면 정답 위치로 되돌린 뒤 이후 무브를 다시 밟아 재생함으로써, 지연을 은폐하면서도 서버 권위를 지킨다 — 단 이 클론엔 송신 루프(ReplicateMoveToServer)·SavedMove 버퍼·재생 본체가 없어 서버 수신 진입점과 두 회신 껍데기만 실물로, 예측·저장·재생 알맹이는 개념으로 확인했다.
