RPC 신뢰성과 검증 (reliable vs unreliable, WithValidation)

언리얼 네트워크 · 22 / 47

앞 챕터에서 RPC가 "이 함수를 저쪽 컴퓨터에서 실행해줘"라는 원격 호출이란 걸 봤어.
막히면 → rpc-types

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 CM_MOVE, CM_ATTACK, CM_USE_ITEM 같은 패킷을 보낼 때 이미 이 고민을 했을 거야. 이 패킷은 꼭 도착해야 하나? 아니면 한두 번 빠져도 다음 패킷으로 덮이면 되나? 반대로 서버가 SP_ITEM_ADD나 SP_QUEST_REWARD를 보낼 때는 "이거 잃어버리면 큰일인데" 하고 생각했을 거고.

이 기준이 없으면 서버가 이상하게 망가져. 이동 좌표를 전부 "무조건 도착"으로 쌓아두면 클라가 잠깐 끊겼을 때 낡은 이동 봉투가 줄줄이 밀려와서 게임이 늦게 반응해. 반대로 아이템 지급이나 문 열기 같은 걸 "잃어버려도 됨"으로 보내면 유저 화면에는 보상이 사라진 것처럼 보일 수 있어. 빠른 게 답일 때와, 꼭 도착해야 하는 게 답일 때가 다르다.

그리고 도착만 한다고 끝도 아니야. 클라가 CM_MOVE로 "나 지금 1000미터 순간이동했어"라고 보내면, IOCP 워커가 패킷을 잘 받고 락을 잘 잡고 단일스레드 로직 큐에 잘 넘겨도 그 내용이 거짓이면 서버가 당해. CChosunPlayer 안에서 상태를 안전하게 바꾸는 것과, 클라가 보낸 값을 믿어도 되는지 검사하는 것은 다른 문제야.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 RPC의 reliable/unreliable 선택과 WithValidation 검증 관문이야. reliable은 "이건 잃어버리면 안 돼"라고 약속하는 길이고, unreliable은 "최신 값만 중요하니 빠르게 흘려보내자"는 길이야. WithValidation은 서버가 실행 전에 "이 부탁, 말이 되나?" 하고 문 앞에서 한 번 막아보는 문지기고.

왜 지금 배우냐면, 앞 챕터에서 RPC의 종류를 봤다면 이제는 "누가 누구에게 부르나"를 넘어서 이 호출을 얼마나 믿고, 얼마나 꼭 보내야 하느냐를 배워야 하거든. 이걸 잡아야 다음에 나올 ownership, 보안, 이동 보정 이야기가 뜬구름이 안 돼. RPC는 그냥 함수 호출처럼 보이지만, 실제 서버에서는 신뢰성 선택과 검증이 빠지는 순간 바로 장애나 핵으로 이어진다.

들어가기 — 택배 두 종류

너 택배 두 번 보내봤다고 생각해봐.

하나는 그냥 문 앞에 툭 던지고 가는 택배야. 도착했는지 안 했는지 확인 안 해. 잃어버려도 그만. 대신 빠르고 싸.

다른 하나는 등기우편이야. 받는 사람 서명 받아. 순서대로 1번 봉투 다음 2번 봉투. 1번이 안 왔으면 2번을 뜯지 못하게 붙잡아둬. 잃어버리면 다시 보내. 대신 느리고, 봉투 쌓이면 문제가 생겨.

UE의 RPC가 딱 이 두 종류야.

  • Unreliable RPC = 문 앞 택배. 도착·순서 보장 안 함. 회선 막히면 그냥 버려.
  • Reliable RPC = 등기우편. 재전송 + 순서 보장. 대신 대가가 있어(뒤에서 봄).

그리고 등기든 아니든, 서버가 "이 택배 내용물이 진짜 맞아?"를 뜯어보기 전에 검사하는 절차가 있어. 그게 WithValidation이야. 클라가 "나 순간이동으로 1000미터 갔어"라고 우기는 걸 서버가 걸러내는 관문.

이 추상 개념을 실제로 구현하는 게 아래 세 파일이야.

  • NetDriver.cpp — 보낼 때 reliable/unreliable가 갈리는 곳
  • DataChannel.cpp — 받을 때 순서를 붙잡아두는 곳
  • DataReplication.cpp + Character.cpp — 받아서 검증하고 실행하는 곳

하나씩 코드로 보자. 낮은 계단부터.

지금부터 진짜 C++ 코드가 나오는데, 겁먹지 마. 여기서는 코드를 외우는 게 아니라 "어디에 도장을 찍고, 어디서 막는지"만 눈에 잡으면 돼.

🌱 이 개념은 왜 생겼나 — reliable / unreliable
• 원래 구조: 보내는 건 다 "꼭 도착하게" 하면 안전하잖아. 등기우편처럼 서명 받고 순서 맞추고, 빠지면 다시 보내고.
• 그런데 문제: 초당 수십 번 나가는 이동 좌표까지 전부 등기로 보내면, 하나 밀릴 때 낡은 좌표 봉투가 줄줄이 쌓여 화면이 굼떠져. 어차피 다음 프레임에 새 좌표가 오는데 옛날 걸 굳이 재전송하는 헛일이야.
• 그래서 필요한 것: 택배를 두 종류로 나누기. unreliable(문 앞 택배 — 잃어도 됨, 빠름)과 reliable(등기 — 재전송+순서 보장). 아이템 지급은 등기, 이동은 문 앞 택배. 조선 서버에서 "이 패킷 꼭 가야 하나?"를 패킷마다 고민하던 그거야.

1단계 — reliable이냐 아니냐는 어디서 정해지나

너 게임에서 UFUNCTION(Server, Reliable) 이런 거 본 적 있을 거야. 이 Reliable 표시 하나가 어디까지 영향을 주냐면...

보내는 쪽 코드가 함수 플래그를 딱 한 번 검사해서 번치(bunch, 채널로 오가는 데이터 덩어리)에 도장을 찍어.

Runtime/Engine/Private/NetDriver.cpp:3133-3138

// Reliability. //warning: RPC's might overflow, preventing reliable functions from getting thorough. if (Function->FunctionFlags & FUNC_NetReliable) { Bunch.bReliable = 1; }
🔤 기호 사전 — Function->FunctionFlags & FUNC_NetReliable
• // = 컴퓨터가 읽는 명령이 아니라 사람이 읽는 메모. "여기부터 신뢰성 처리야"라고 붙여둔 쪽지야.
• Function->FunctionFlags = 이 RPC 함수에 붙은 표시표들을 꺼내 보는 것. Reliable, Server 같은 딱지가 여기 들어 있어.
• -> = "그 물건 안에 있는 것을 꺼내 봐"라는 화살표. Function 안의 FunctionFlags를 보는 거야.
• & FUNC_NetReliable = 여러 딱지 중에서 Reliable 딱지만 콕 집어 확인하는 비트 검사.
• if (...) = 괄호 안 말이 맞으면 아래 중괄호 안을 실행해.
• Bunch.bReliable = 1 = 이 번치에 "reliable 맞음" 도장을 찍는 줄. 1은 켜짐이야.
• ; = 한 문장이 끝났다는 마침표.
🔁 이제 다시 보자. Function->FunctionFlags에서 함수의 딱지들을 꺼내고, & FUNC_NetReliable로 Reliable 딱지가 있는지 본다. 있으면 Bunch.bReliable = 1로 번치에 등기우편 도장을 찍는다. 이 한 줄 때문에 뒤에서 순서 보장과 재전송 규칙이 따라붙어.

이게 전부야. UFUNCTION에 Reliable을 붙이면 UHT(언리얼 헤더툴)가 그 함수에 FUNC_NetReliable 플래그를 심어놓고, 보낼 때 이 if 하나가 Bunch.bReliable = 1로 도장을 찍어. 안 붙였으면 이 도장이 안 찍히고, 그냥 unreliable 번치가 돼.

여기서 하나 맞춰봐. unreliable RPC를 보내려는데 마침 연결이 꽉 막혀서(회선 포화) 지금 못 보낼 상황이야. UE는 어떻게 할까? (a) 큐에 쌓아뒀다가 나중에 보낸다 (b) 그냥 버린다

...정답은 (b) 버린다야. NetDriver.cpp:2929를 보면 !(FUNC_NetReliable) && !(FUNC_NetMulticast) && !Connection->IsNetReady()일 때 이번 unreliable RPC를 드롭해버려. "신뢰 안 하기로 한 놈"이니까 미련 없이 버리는 거지. 이게 unreliable의 정체성이야. 반대로 reliable이면 절대 안 버려. 무슨 수를 써서라도 보내려고 해.

2단계 — reliable의 대가: 버퍼 넘치면 연결을 끊는다

"reliable은 무조건 보내준다니까 다 reliable로 쓰면 되잖아?" 싶지?

아니야. 등기우편의 저주가 있어. 재전송하려면 "아직 상대가 받았다고 서명 안 한 봉투"들을 서버가 계속 들고 있어야 해. 근데 이 보관함(reliable 버퍼)은 크기가 정해져 있어. 상대가 계속 응답을 안 해서 봉투가 꽉 차버리면?

Runtime/Engine/Private/NetDriver.cpp:3144-3152

if (!Bunch.bReliable) { // Not reliable, so not fatal. This can happen a lot in debug builds at startup if client is slow to get in game UE_LOG(LogNet, Warning, TEXT("Can't send function '%s' on '%s': Reliable buffer overflow. FieldCache->FieldNetIndex: %d Max %d. Ch MaxPacket: %d"), *GetNameSafe(Function), *GetFullNameSafe(TargetObj), FieldCache->FieldNetIndex, ClassCache->GetMaxIndex(), Ch->Connection->MaxPacket ); } else { // The connection has overflowed the reliable buffer. We cannot recover from this. Disconnect this user. UE_LOG(LogNet, Warning, TEXT("Closing connection. Can't send function '%s' on '%s': Reliable buffer overflow. FieldCache->FieldNetIndex: %d Max %d. Ch MaxPacket: %d."), *GetNameSafe(Function), *GetFullNameSafe(TargetObj), FieldCache->FieldNetIndex, ClassCache->GetMaxIndex(), Ch->Connection->MaxPacket );
🔤 기호 사전 — reliable 버퍼가 넘쳤을 때
• !Bunch.bReliable = Bunch.bReliable이 꺼져 있으면. 앞의 !는 "아니면"이라는 뜻이야.
• else = 위 if가 아니면 이쪽. 여기서는 "unreliable이 아니면" = reliable이면.
• UE_LOG(...) = 언리얼 로그 창에 메시지를 찍는 함수.
• LogNet = 네트워크 쪽 로그 칸.
• Warning = 치명적 종료는 아니지만 위험하다고 알려주는 등급.
• TEXT("...") = 문자열을 언리얼 방식으로 감싸는 포장지.
• %s, %d = 나중에 실제 이름이나 숫자가 들어갈 빈칸. %s는 글자, %d는 숫자야.
• *GetNameSafe(Function) = 안전하게 이름을 구한 다음, 로그가 먹을 수 있는 글자 포인터로 꺼내 주는 모양.
• Ch->Connection->MaxPacket = Ch 안의 Connection, 그 안의 MaxPacket까지 화살표를 타고 들어가 보는 것.
🔁 이제 다시 보자. if (!Bunch.bReliable)이면 unreliable이라서 UE_LOG(... Warning ...)만 남기고 넘어갈 수 있다. 하지만 else 쪽은 reliable이니까, 주석 그대로 We cannot recover from this 상황이 된다. 그래서 같은 버퍼 넘침이라도 unreliable은 경고, reliable은 연결 종료로 이어지는 거야.

주석이 다 말해줘. unreliable이면 Not reliable, so not fatal — 경고만 찍고 넘어가. 근데 reliable이면 We cannot recover from this. Disconnect this user. — 연결을 끊어버려.

왜? reliable은 "순서대로 다 전달"이 약속인데, 봉투 하나가 증발하면 그 뒤 순서가 전부 무너져. 이건 복구가 안 돼. 그래서 차라리 유저를 끊는 거야. 이게 등기우편의 대가고, "모든 걸 reliable로 쓰면 안 되는" 이유야. 초당 수십 번 나가는 이동 정보 같은 건 unreliable로 보내야 하는 거지(잃어버려도 다음 프레임에 새 좌표가 오니까).

재전송/ACK가 실제로 어떻게 도는지 → reliability-ack
🌱 이 개념은 왜 생겼나 — 순서 보장(순번·버퍼링)
• 원래 구조: 봉투가 도착하는 족족 바로 뜯어서 처리하면 되잖아.
• 그런데 문제: UE는 UDP 기반이라 7번 봉투가 6번보다 먼저 도착할 수 있어. 그냥 뜯으면 "6번 이동 다음 7번 이동"이 뒤집혀서 캐릭터가 이상하게 튀어.
• 그래서 필요한 것: 봉투마다 순번(ChSequence)을 붙이고, "다음에 올 번호"랑 안 맞으면 뜯지 말고 붙잡아두기. → 그게 순서 보장이야. 조선 서버는 TCP가 이걸 공짜로 해주지만, UDP 위 reliable은 손으로 이 대기줄을 만들어야 해.

3단계 — 받는 쪽: 순서 보장의 실체

"reliable은 순서를 보장한다"는 말, 실제 코드로 어떻게 생겼을까?

받는 쪽은 번치마다 붙은 순번(ChSequence)을 본다. 그리고 "내가 지금까지 받은 마지막 순번 + 1"이랑 맞는지 비교해. 안 맞으면? 안 뜯어. 붙잡아둬.

Runtime/Engine/Private/DataChannel.cpp:640-645

if ( Bunch.bReliable && Bunch.ChSequence != Connection->InReliable[ChIndex] + 1 ) { // We shouldn't hit this path on 100% reliable connections check( !Connection->IsInternalAck() ); // If this bunch has a dependency on a previous unreceived bunch, buffer it. checkSlow(!Bunch.bOpen);
🔤 기호 사전 — Bunch.ChSequence != Connection->InReliable[ChIndex] + 1
• Bunch.bReliable && ... = "이 번치가 reliable이고, 그리고 뒤 조건도 맞으면". &&는 둘 다 맞아야 통과하는 문이야.
• ChSequence = 이 채널에서 번치가 몇 번째인지 적은 순번표.
• != = 같지 않다. "기대한 번호가 아니네?"를 보는 기호야.
• Connection->InReliable[ChIndex] = 이 연결에서, 이 채널(ChIndex)이 마지막으로 제대로 받은 reliable 순번.
• [ChIndex] = 여러 칸짜리 서랍에서 ChIndex번 칸을 꺼내는 표시.
• + 1 = 마지막으로 받은 번호 바로 다음 번호. 5까지 받았으면 다음은 6.
• check(...) = 개발 중에 "이 조건은 꼭 맞아야 해"라고 확인하는 안전핀.
• checkSlow(...) = 느릴 수 있어서 더 무거운 검사에 붙는 안전핀.
• !Bunch.bOpen = 이 번치가 채널을 새로 여는 번치가 아니어야 한다는 뜻.
🔁 이제 다시 보자. Bunch.bReliable인 번치만 순번 검사를 받는다. Bunch.ChSequence가 InReliable[ChIndex] + 1과 다르면 "다음 차례가 아닌 번치"라서 이 if 안으로 들어온다. 코드는 여기서 바로 뜯지 말고, 앞 순번이 올 때까지 붙잡아둘 준비를 하는 거야.

Connection->InReliable[ChIndex] + 1 — 이게 "다음에 와야 할 순번"이야. 5번까지 처리했으면 다음은 6번이어야 해. 근데 7번이 먼저 도착하면? ChSequence(7) != InReliable(5)+1(6) 이니까 이 if에 걸려서 버퍼링돼. 주석 그대로 buffer it. 6번이 도착할 때까지 7번을 대기시켜.

이게 "순서 보장"의 진짜 모습이야. 마법이 아니라, 순번 비교 한 줄 + 안 맞으면 대기열에 넣기. 6번이 오는 순간 6번, 7번 순서대로 풀려나가는 거지.

번치가 어떻게 다음 것과 이어지는지 자세히 → datachannel-nextbunch
🌱 이 개념은 왜 생겼나 — 실행 전 검증 관문(WithValidation)
• 원래 구조: 봉투가 순서대로 잘 도착했으면 안에 든 RPC를 바로 실행하면 되잖아.
• 그런데 문제: 클라가 "나 방금 1000미터 순간이동했어"라고 우기는 값을 그대로 실행하면 서버가 당해. 방향도 마찬가지 — 해킹 클라가 서버 전용 함수를 자기가 실행시키려 들 수 있어.
• 그래서 필요한 것: 실행 전에 문 앞에서 막는 관문. 방향 검사(누가 부를 자격 있나) + _Validate 값 검증(이 부탁 말이 되나). → 그게 WithValidation이야. 조선 서버 CM_ 핸들러 안에서 손으로 짜던 범위체크를, 안 짜면 빌드가 안 되게 프레임워크가 강제하는 거지.

4단계 — 받아서 실행하기 전, 두 개의 관문

번치가 순서대로 잘 도착했어. 이제 안에 든 RPC를 실행할 차례. 근데 바로 실행 안 해. 관문 두 개를 통과해야 해.

관문 1 — 방향 검사 (누가 누구한테 부를 수 있나)

Server RPC는 클라 → 서버로만 가야 해. Client RPC는 서버 → 클라로만. 이걸 어긴 RPC는 거절해. 해킹 클라가 "서버 전용 함수인데 내가 서버인 척 실행시켜줘" 하는 걸 막는 거야.

Runtime/Engine/Private/DataReplication.cpp:1346-1357

// If NetServer, NetClient, or NetMulticast flags are present, filter the RPC based on them. If not, accept the RPC for servers and clients. if ((Function->FunctionFlags & FUNC_NetServer) && !bIsServer) { UE_LOG(LogRep, Error, TEXT("Rejected server RPC function due to access rights. Object: %s, Function: %s"), *Object->GetFullName(), *FunctionName.ToString()); HANDLE_INCOMPATIBLE_RPC } if ((Function->FunctionFlags & (FUNC_NetClient | FUNC_NetMulticast)) && bIsServer) { UE_LOG(LogRep, Error, TEXT("Rejected client RPC function due to access rights. Object: %s, Function: %s"), *Object->GetFullName(), *FunctionName.ToString()); HANDLE_INCOMPATIBLE_RPC }
🔤 기호 사전 — RPC 방향 검사
• Function->FunctionFlags = 이 RPC 함수에 붙은 방향 딱지들. 서버용인지, 클라용인지, 멀티캐스트인지가 들어 있어.
• FUNC_NetServer = "서버 RPC" 딱지. 클라가 서버에게 부탁하는 함수라는 표시야.
• FUNC_NetClient = "클라이언트 RPC" 딱지. 서버가 특정 클라에게 시키는 함수라는 표시야.
• FUNC_NetMulticast = 여러 클라에게 퍼지는 RPC 딱지.
• & = 여러 딱지 중 원하는 딱지가 붙었는지 콕 집어 보는 검사.
• | = 여러 딱지를 한 묶음으로 합쳐서 "이 중 하나라도" 보려는 기호.
• && !bIsServer = 앞 조건도 맞고, 지금 실행하는 쪽이 서버가 아니면. bIsServer 앞의 !는 "서버가 아님"이야.
• UE_LOG(LogRep, Error, ...) = 복제/RPC 쪽 로그에 에러를 찍는다.
• HANDLE_INCOMPATIBLE_RPC = 방향이 틀린 RPC를 처리하는 매크로. 여기서 컷하는 절차를 대신 펼쳐 주는 이름표야.
🔁 이제 다시 보자. 첫 번째 if는 FUNC_NetServer 함수인데 지금 서버가 아니면 거절한다. 두 번째 if는 FUNC_NetClient | FUNC_NetMulticast 함수인데 지금 서버 쪽에서 받으면 거절한다. 핵심은 FunctionFlags 딱지와 bIsServer 실제 위치를 비교해서, 방향이 틀린 RPC를 실행 전에 잘라내는 거야.

FUNC_NetServer인데 나는 서버가 아니다(!bIsServer) → 거절. FUNC_NetClient인데 나는 서버다(bIsServer) → 거절. 방향이 어긋나면 Rejected ... due to access rights 로그 찍고 컷.

관문 2 — 값 검증 (WithValidation)

방향은 맞아. 근데 내용물이 정상 범위냐? 이게 WithValidation이 하는 일. 코드는 이렇게 흘러가.

Runtime/Engine/Private/DataReplication.cpp:1441-1449 — 검증 사유 슬롯을 비우고 함수를 실행:

// Reset errors from replay driver RPC_ResetLastFailedReason(); { // Call the function. if (Connection->Driver->IsExecuteRPCFunctionsEnabled()) { CallProcessEventForReceivedRPC(Object, Function, Parms); } }
🔤 기호 사전 — 검증 사유 슬롯을 비우고 실행하기
• RPC_ResetLastFailedReason() = "방금 RPC 실패 이유 적어둔 칸"을 먼저 비우는 함수. 이전 실패 이유가 남아 있으면 헷갈리니까 지워.
• { ... } = 코드를 작은 방 하나로 묶는 중괄호. 여기서는 실행 호출 부분을 감싸고 있어.
• Connection->Driver->IsExecuteRPCFunctionsEnabled() = 연결의 드라이버에게 "지금 RPC 함수 실행해도 돼?"라고 묻는 줄.
• CallProcessEventForReceivedRPC(Object, Function, Parms) = 받은 RPC를 실제 언리얼 이벤트 실행 통로로 넘기는 함수.
• Object = RPC를 받을 실제 객체.
• Function = 실행할 함수 정보.
• Parms = RPC가 들고 온 인자 꾸러미. 좌표, 시간, 플래그 같은 값들이 여기 들어 있어.
🔁 이제 다시 보자. 먼저 RPC_ResetLastFailedReason()으로 실패 메모장을 깨끗이 비운다. 그다음 IsExecuteRPCFunctionsEnabled()가 허락하면 CallProcessEventForReceivedRPC(Object, Function, Parms)로 실제 실행 통로에 태운다. 이 통로 안에서 _Validate가 먼저 불릴 수 있다는 게 다음 포인트야.

CallProcessEventForReceivedRPC 안에서 Object->ProcessEvent(...)가 불려. 그리고 여기 함정이 하나 있어 — WithValidation을 붙이면 UHT가 만든 exec 스텁이 이 ProcessEvent 안에서 네가 짠 함수명_Validate()를 먼저 부른다. false가 나오면 "부정 클라"라고 판단하고 실패 사유를 슬롯에 세팅해. (스텁 생성 코드 자체는 .gen.cpp라 이 소스 트리엔 없어. 하지만 그 결과를 소비하는 코드는 바로 아래에 있어.)

Runtime/Engine/Private/DataReplication.cpp:1461-1465 — 실행 후 슬롯을 확인:

if (RPC_GetLastFailedReason() != nullptr) { UE_LOG(LogRep, Error, TEXT("ReceivedRPC: RPC_GetLastFailedReason: %s"), RPC_GetLastFailedReason()); return false; }
🔤 기호 사전 — 실패 사유 확인
• RPC_GetLastFailedReason() = 방금 RPC 처리 중 실패 이유가 적혔는지 꺼내 보는 함수.
• nullptr = 아무것도 없음. 빈 주소, 빈 칸이라고 생각하면 돼.
• != nullptr = 빈 칸이 아니다. 즉 실패 이유가 뭔가 적혀 있다는 뜻.
• UE_LOG(LogRep, Error, ...) = 복제/RPC 로그에 에러로 남긴다.
• %s = 실패 이유 글자가 들어갈 자리.
• return false = "이 RPC 처리 실패"라고 위로 돌려보내며 여기서 끝낸다.
🔁 이제 다시 보자. RPC_GetLastFailedReason() != nullptr이면 실패 이유 칸이 비어 있지 않다는 뜻이다. 그러면 UE_LOG로 이유를 찍고 return false로 실패를 돌려준다. _Validate가 false를 냈든, 언팩이 거부됐든, 여기서 "실행 성공 아님"으로 확정되는 거야.

RPC_GetLastFailedReason()이 null이 아니다 = 아까 _Validate가 false를 뱉었거나 언팩 거부됐다 = 검증 실패. 그러면 로그 찍고 return false. 이 false가 상위로 올라가면 결국 그 연결을 정리하는 쪽으로 이어져. "검증 실패"가 런타임에서 실제로 소비되는 지점이 바로 여기야.

• void = 값을 돌려주지 않는 함수. 여기서는 "검사 결과"가 아니라 실제 일을 하는 몸통이야.
• ServerMove_Implementation = ServerMove RPC의 실제 실행 담당 함수. _Implementation은 "진짜 처리"라고 읽으면 돼.
• GetCharacterMovement() = 캐릭터 이동을 관리하는 부품을 가져오는 함수.
• ->ServerMove_Implementation(...) = 그 이동 부품 안의 실제 이동 처리 함수를 호출하는 화살표.

🔁 이제 다시 보자. _Validate는 bool로 "해도 돼?"를 묻는 문지기였고, _Implementation은 void로 실제 이동 처리를 맡기는 몸통이다. 이 코드는 GetCharacterMovement()에게 같은 인자 꾸러미를 넘겨서 진짜 이동 로직을 실행하게 한다.

구조가 딱 보이지? 같은 이름에 접미사만 달라.

  • _Validate → "이 값 써도 돼?" (bool 반환, 문지기)
  • _Implementation → "실제로 이 값으로 이동시켜" (진짜 몸통)

네가 UFUNCTION(Server, Reliable, WithValidation)이라고 선언하면, 원본 함수명(ServerMove)은 UHT가 자동 배선용으로 가져가고, 너는 ServerMove_Validate(문지기)랑 ServerMove_Implementation(로직) 두 개를 직접 짜는 거야. _Validate가 통과해야만 _Implementation이 실행돼.

• FCharacterServerMovePackedBits& PackedBits = 캐릭터 이동 정보를 비트로 꽉 눌러 담은 꾸러미를 원본 그대로 받는다는 뜻. &는 복사본 말고 원본을 받는 표시야.

큰 차이 두 개만 기억해.

첫째, 순서 보장 위치가 달라. 우리는 TCP 위에 올라타서 순서를 공짜로 받아. 그래서 우리 핸들러엔 "이 패킷이 앞 패킷보다 먼저 왔나?" 같은 코드가 없지. UE는 UDP 기반이라 순서를 직접 만들어야 해. 그게 DataChannel.cpp:640의 ChSequence 비교야. 우리가 TCP한테 위임한 걸 UE는 손으로 구현한 거지. 대신 UE는 "이건 순서 필요 없으니 unreliable로" 하고 선택적으로 포기할 수 있어 — 우리 TCP는 그런 선택권이 없어(다 순서 보장, 다 비용 지불).

둘째, 검증이 "손코딩" vs "계약". 우리는 CM_XXX 핸들러 안에서 개발자가 까먹지 않고 범위체크를 짜야 해. 까먹으면 그냥 구멍. UE는 WithValidation을 붙이는 순간 _Validate 함수가 컴파일 단계에서 강제돼(안 짜면 링크 에러). 검증을 "잊어버릴 수 없게" 프레임워크가 붙잡아주는 구조야. 우리 서버로 치면, 모든 CM_ 핸들러에 "검증 함수 없으면 빌드 실패"를 강제하는 규칙을 넣은 셈.

소스 포함 여부 (정직 표기)

  • 포함됨 (위 인용 전부 실제 파일에서 직접 대조 확인): reliable/unreliable 송신 분기(NetDriver.cpp), 순서 보장(DataChannel.cpp:640), 방향 필터 + 검증사유 소비(DataReplication.cpp ReceivedRPC), _Validate/_Implementation 실구현(Character.cpp).
  • 🔬 미포함: WithValidation 리터럴과 exec 스텁 생성 코드(UHT 산출 .gen.cpp), RPC_ValidateRequestFailed/RPC_GetLastFailedReason의 정의부(CoreUObject 매크로 헤더). 이 트리는 Engine/Source 부분 트리라 정의 파일이 없어. 단 이 심볼들을 호출·소비하는 지점은 위 인용대로 실재하고 직접 대조했어.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. reliable / unreliable, 왜 둘로 나눠놨나요? 다 reliable로 하면 안 되나요?

답 보기
택배 두 종류라고 보면 돼. unreliable은 문 앞에 툭 던지는 택배 — 빠르지만 잃어도 그만. reliable은 등기우편 — 재전송 + 순서 보장이지만 느리고 비싸. 초당 수십 번 나가는 이동 좌표까지 전부 등기로 보내면, 하나 밀릴 때 낡은 좌표 봉투가 줄줄이 쌓여서 화면이 굼떠져. 어차피 다음 프레임에 새 좌표가 오는데 옛날 걸 재전송하는 건 헛일이야. 그래서 아이템 지급은 reliable, 이동은 unreliable로 나누는 거야.

↳ 그럼 reliable로만 도배하면 구체적으로 뭐가 망가지나요?

답 보기
reliable은 "아직 상대가 받았다고 서명 안 한 봉투"를 계속 들고 있어야 해. 이 보관함(reliable 버퍼)은 크기가 정해져 있어서, 상대가 응답을 안 해 봉투가 꽉 차면 — 연결을 끊어버려. 왜? reliable은 "순서대로 다 전달"이 약속인데 봉투 하나가 증발하면 그 뒤 순서가 전부 무너지거든. 복구가 안 되니 차라리 유저를 끊는 거야. 같은 버퍼 넘침이라도 unreliable은 경고만 찍고 넘어가는데 reliable은 종료로 이어지는 이유가 이거야.

↳ unreliable RPC를 보내려는데 회선이 꽉 막혔으면 어떻게 하나요?

답 보기
그냥 버려. 큐에 쌓아두지 않아. "신뢰 안 하기로 한 놈"이니까 미련 없이 드롭하는 게 unreliable의 정체성이야. 반대로 reliable이면 무슨 수를 써서라도 보내려고 해. 이 차이가 바로 두 종류를 나눈 이유고.

Q2. "reliable은 순서를 보장한다"는데, 그 순서 보장은 큰 그림에서 어떻게 도나요?

답 보기
마법이 아니라 순번 비교 한 줄이야. 받는 쪽은 번치마다 붙은 순번을 보고 "내가 마지막으로 받은 번호 + 1"이랑 맞는지 확인해. 5번까지 받았는데 7번이 먼저 도착하면? 안 맞으니까 안 뜯고 붙잡아둬(버퍼링). 6번이 오는 순간 6번, 7번 순서대로 풀려나가. 이게 "순서 보장"의 진짜 모습이야 — 순번 안 맞으면 대기열에 넣기.

↳ TCP는 이걸 공짜로 해주잖아요. UE는 왜 손으로 하나요?

답 보기
UE는 UDP 기반이라서야. UDP는 7번 봉투가 6번보다 먼저 도착할 수 있어. 우리 조선 서버는 TCP 위에 올라타서 순서를 공짜로 받으니까 핸들러에 "이 패킷이 앞 패킷보다 먼저 왔나?" 같은 코드가 아예 없지. UE는 그 대기줄을 직접 만들어야 해. 대신 UE는 "이건 순서 필요 없으니 unreliable로" 하고 선택적으로 포기할 수 있어 — TCP는 그런 선택권이 없어. 다 순서 보장, 다 비용 지불이야.

Q3. RPC가 순서대로 잘 도착했으면 바로 실행하면 되지, 왜 관문을 또 두나요?

답 보기
관문이 둘이야. 첫째 방향 검사 — Server RPC는 클라→서버로만, Client RPC는 서버→클라로만 가야 해. 해킹 클라가 "서버 전용 함수인데 내가 서버인 척 실행시켜줘" 하는 걸 여기서 막아. 둘째 값 검증(WithValidation) — 방향은 맞는데 내용물이 정상 범위냐를 봐. 클라가 "나 방금 1000미터 순간이동했어"라고 우기는 값을 그대로 실행하면 서버가 당하잖아. 도착했다고 믿을 수 있는 건 아니거든.

↳ WithValidation은 실제로 어떤 모양으로 강제되나요?

답 보기
_Validate랑 _Implementation 두 짝으로 갈라. _Validate는 "이 값 써도 돼?"를 묻는 문지기(bool 반환), _Implementation은 "실제로 이 값으로 이동시켜"의 진짜 몸통이야. _Validate가 통과해야만 _Implementation이 실행돼. WithValidation을 붙이면 _Validate를 안 짜면 링크 에러가 나 — 검증을 "잊어버릴 수 없게" 프레임워크가 붙잡는 구조야.

↳ 검증이 실패하면 그 다음 어떻게 되나요?

답 보기
실패 사유 슬롯에 이유가 세팅되고, 실행 후 그 슬롯이 비어있지 않으면 로그 찍고 실패로 처리돼. 그 실패가 상위로 올라가면 결국 그 연결을 정리하는 쪽으로 이어져. 즉 부정 클라는 그냥 무시되는 게 아니라 끊기는 방향으로 가는 거야.

Q4. 우리 서버는 검증을 어떻게 하죠? UE랑 뭐가 다른가요?

답 보기
우리는 손코딩이야. CM_XXX 핸들러 안에서 개발자가 까먹지 않고 범위체크 if를 직접 짜야 해. 까먹으면 그냥 구멍 나는 거지. UE는 WithValidation을 붙이는 순간 _Validate가 컴파일 단계에서 강제돼. 우리 서버로 치면 모든 CM_ 핸들러에 "검증 함수 없으면 빌드 실패"를 강제하는 규칙을 넣은 셈이야. "손코딩 vs 계약"의 차이지.

↳ 그럼 UE는 항상 실행 전에 값을 검증할 수 있나요?

답 보기
항상은 아니야. 비트스트림으로 뭉쳐 보낸 이동 같은 건 풀기 전엔 검증을 못 해. 그래서 그런 경우는 _Validate에서 일단 통과시키고, 나중에 언팩한 뒤 단계에서 거절해. "항상 믿는다"가 아니라 "검사 시점을 뒤로 미룬다"에 가까워. 검증 시점이 언제나 _Validate인 건 아니라는 것도 알아둘 포인트야.
