RPC 신뢰성과 검증 (reliable vs unreliable, WithValidation)

언리얼 네트워크 · 22 / 42

앞 챕터에서 RPC가 "이 함수를 저쪽 컴퓨터에서 실행해줘"라는 원격 호출이란 걸 봤어. 막히면 → rpc-types

들어가기 — 택배 두 종류

너 택배 두 번 보내봤다고 생각해봐.

하나는 그냥 문 앞에 툭 던지고 가는 택배야. 도착했는지 안 했는지 확인 안 해. 잃어버려도 그만. 대신 빠르고 싸.

다른 하나는 등기우편이야. 받는 사람 서명 받아. 순서대로 1번 봉투 다음 2번 봉투. 1번이 안 왔으면 2번을 뜯지 못하게 붙잡아둬. 잃어버리면 다시 보내. 대신 느리고, 봉투 쌓이면 문제가 생겨.

UE의 RPC가 딱 이 두 종류야.

  • Unreliable RPC = 문 앞 택배. 도착·순서 보장 안 함. 회선 막히면 그냥 버려.
  • Reliable RPC = 등기우편. 재전송 + 순서 보장. 대신 대가가 있어(뒤에서 봄).

그리고 등기든 아니든, 서버가 "이 택배 내용물이 진짜 맞아?"를 뜯어보기 전에 검사하는 절차가 있어. 그게 WithValidation이야. 클라가 "나 순간이동으로 1000미터 갔어"라고 우기는 걸 서버가 걸러내는 관문.

이 추상 개념을 실제로 구현하는 게 아래 세 파일이야.

  • NetDriver.cpp — 보낼 때 reliable/unreliable가 갈리는 곳
  • DataChannel.cpp — 받을 때 순서를 붙잡아두는 곳
  • DataReplication.cpp + Character.cpp — 받아서 검증하고 실행하는 곳

하나씩 코드로 보자. 낮은 계단부터.

1단계 — reliable이냐 아니냐는 어디서 정해지나

너 게임에서 UFUNCTION(Server, Reliable) 이런 거 본 적 있을 거야. 이 Reliable 표시 하나가 어디까지 영향을 주냐면...

보내는 쪽 코드가 함수 플래그를 딱 한 번 검사해서 번치(bunch, 채널로 오가는 데이터 덩어리)에 도장을 찍어.

Runtime/Engine/Private/NetDriver.cpp:3133-3138

// Reliability. //warning: RPC's might overflow, preventing reliable functions from getting thorough. if (Function->FunctionFlags & FUNC_NetReliable) { Bunch.bReliable = 1; }

이게 전부야. UFUNCTION에 Reliable을 붙이면 UHT(언리얼 헤더툴)가 그 함수에 FUNC_NetReliable 플래그를 심어놓고, 보낼 때 이 if 하나가 Bunch.bReliable = 1로 도장을 찍어. 안 붙였으면 이 도장이 안 찍히고, 그냥 unreliable 번치가 돼.

여기서 하나 맞춰봐. unreliable RPC를 보내려는데 마침 연결이 꽉 막혀서(회선 포화) 지금 못 보낼 상황이야. UE는 어떻게 할까? (a) 큐에 쌓아뒀다가 나중에 보낸다 (b) 그냥 버린다

...정답은 (b) 버린다야. NetDriver.cpp:2929를 보면 !(FUNC_NetReliable) && !(FUNC_NetMulticast) && !Connection->IsNetReady()일 때 이번 unreliable RPC를 드롭해버려. "신뢰 안 하기로 한 놈"이니까 미련 없이 버리는 거지. 이게 unreliable의 정체성이야. 반대로 reliable이면 절대 안 버려. 무슨 수를 써서라도 보내려고 해.

2단계 — reliable의 대가: 버퍼 넘치면 연결을 끊는다

"reliable은 무조건 보내준다니까 다 reliable로 쓰면 되잖아?" 싶지?

아니야. 등기우편의 저주가 있어. 재전송하려면 "아직 상대가 받았다고 서명 안 한 봉투"들을 서버가 계속 들고 있어야 해. 근데 이 보관함(reliable 버퍼)은 크기가 정해져 있어. 상대가 계속 응답을 안 해서 봉투가 꽉 차버리면?

Runtime/Engine/Private/NetDriver.cpp:3144-3152

if (!Bunch.bReliable) { // Not reliable, so not fatal. This can happen a lot in debug builds at startup if client is slow to get in game UE_LOG(LogNet, Warning, TEXT("Can't send function '%s' on '%s': Reliable buffer overflow. FieldCache->FieldNetIndex: %d Max %d. Ch MaxPacket: %d"), *GetNameSafe(Function), *GetFullNameSafe(TargetObj), FieldCache->FieldNetIndex, ClassCache->GetMaxIndex(), Ch->Connection->MaxPacket ); } else { // The connection has overflowed the reliable buffer. We cannot recover from this. Disconnect this user. UE_LOG(LogNet, Warning, TEXT("Closing connection. Can't send function '%s' on '%s': Reliable buffer overflow. FieldCache->FieldNetIndex: %d Max %d. Ch MaxPacket: %d."), *GetNameSafe(Function), *GetFullNameSafe(TargetObj), FieldCache->FieldNetIndex, ClassCache->GetMaxIndex(), Ch->Connection->MaxPacket );

주석이 다 말해줘. unreliable이면 Not reliable, so not fatal — 경고만 찍고 넘어가. 근데 reliable이면 We cannot recover from this. Disconnect this user. — 연결을 끊어버려.

왜? reliable은 "순서대로 다 전달"이 약속인데, 봉투 하나가 증발하면 그 뒤 순서가 전부 무너져. 이건 복구가 안 돼. 그래서 차라리 유저를 끊는 거야. 이게 등기우편의 대가고, "모든 걸 reliable로 쓰면 안 되는" 이유야. 초당 수십 번 나가는 이동 정보 같은 건 unreliable로 보내야 하는 거지(잃어버려도 다음 프레임에 새 좌표가 오니까).

재전송/ACK가 실제로 어떻게 도는지 → reliability-ack

3단계 — 받는 쪽: 순서 보장의 실체

"reliable은 순서를 보장한다"는 말, 실제 코드로 어떻게 생겼을까?

받는 쪽은 번치마다 붙은 순번(ChSequence)을 본다. 그리고 "내가 지금까지 받은 마지막 순번 + 1"이랑 맞는지 비교해. 안 맞으면? 안 뜯어. 붙잡아둬.

Runtime/Engine/Private/DataChannel.cpp:640-645

if ( Bunch.bReliable && Bunch.ChSequence != Connection->InReliable[ChIndex] + 1 ) { // We shouldn't hit this path on 100% reliable connections check( !Connection->IsInternalAck() ); // If this bunch has a dependency on a previous unreceived bunch, buffer it. checkSlow(!Bunch.bOpen);

Connection->InReliable[ChIndex] + 1 — 이게 "다음에 와야 할 순번"이야. 5번까지 처리했으면 다음은 6번이어야 해. 근데 7번이 먼저 도착하면? ChSequence(7) != InReliable(5)+1(6) 이니까 이 if에 걸려서 버퍼링돼. 주석 그대로 buffer it. 6번이 도착할 때까지 7번을 대기시켜.

이게 "순서 보장"의 진짜 모습이야. 마법이 아니라, 순번 비교 한 줄 + 안 맞으면 대기열에 넣기. 6번이 오는 순간 6번, 7번 순서대로 풀려나가는 거지.

번치가 어떻게 다음 것과 이어지는지 자세히 → datachannel-nextbunch

4단계 — 받아서 실행하기 전, 두 개의 관문

번치가 순서대로 잘 도착했어. 이제 안에 든 RPC를 실행할 차례. 근데 바로 실행 안 해. 관문 두 개를 통과해야 해.

관문 1 — 방향 검사 (누가 누구한테 부를 수 있나)

Server RPC는 클라 → 서버로만 가야 해. Client RPC는 서버 → 클라로만. 이걸 어긴 RPC는 거절해. 해킹 클라가 "서버 전용 함수인데 내가 서버인 척 실행시켜줘" 하는 걸 막는 거야.

Runtime/Engine/Private/DataReplication.cpp:1346-1357

// If NetServer, NetClient, or NetMulticast flags are present, filter the RPC based on them. If not, accept the RPC for servers and clients. if ((Function->FunctionFlags & FUNC_NetServer) && !bIsServer) { UE_LOG(LogRep, Error, TEXT("Rejected server RPC function due to access rights. Object: %s, Function: %s"), *Object->GetFullName(), *FunctionName.ToString()); HANDLE_INCOMPATIBLE_RPC } if ((Function->FunctionFlags & (FUNC_NetClient | FUNC_NetMulticast)) && bIsServer) { UE_LOG(LogRep, Error, TEXT("Rejected client RPC function due to access rights. Object: %s, Function: %s"), *Object->GetFullName(), *FunctionName.ToString()); HANDLE_INCOMPATIBLE_RPC }

FUNC_NetServer인데 나는 서버가 아니다(!bIsServer) → 거절. FUNC_NetClient인데 나는 서버다(bIsServer) → 거절. 방향이 어긋나면 Rejected ... due to access rights 로그 찍고 컷.

관문 2 — 값 검증 (WithValidation)

방향은 맞아. 근데 내용물이 정상 범위냐? 이게 WithValidation이 하는 일. 코드는 이렇게 흘러가.

Runtime/Engine/Private/DataReplication.cpp:1441-1449 — 검증 사유 슬롯을 비우고 함수를 실행:

// Reset errors from replay driver RPC_ResetLastFailedReason(); { // Call the function. if (Connection->Driver->IsExecuteRPCFunctionsEnabled()) { CallProcessEventForReceivedRPC(Object, Function, Parms); } }

CallProcessEventForReceivedRPC 안에서 Object->ProcessEvent(...)가 불려. 그리고 여기 함정이 하나 있어 — WithValidation을 붙이면 UHT가 만든 exec 스텁이 이 ProcessEvent 안에서 네가 짠 함수명_Validate()를 먼저 부른다. false가 나오면 "부정 클라"라고 판단하고 실패 사유를 슬롯에 세팅해. (스텁 생성 코드 자체는 .gen.cpp라 이 소스 트리엔 없어. 하지만 그 결과를 소비하는 코드는 바로 아래에 있어.)

Runtime/Engine/Private/DataReplication.cpp:1461-1465 — 실행 후 슬롯을 확인:

if (RPC_GetLastFailedReason() != nullptr) { UE_LOG(LogRep, Error, TEXT("ReceivedRPC: RPC_GetLastFailedReason: %s"), RPC_GetLastFailedReason()); return false; }

RPC_GetLastFailedReason()이 null이 아니다 = 아까 _Validate가 false를 뱉었거나 언팩 거부됐다 = 검증 실패. 그러면 로그 찍고 return false. 이 false가 상위로 올라가면 결국 그 연결을 정리하는 쪽으로 이어져. "검증 실패"가 런타임에서 실제로 소비되는 지점이 바로 여기야.

그럼 _Validate는 실제로 어떻게 생겼나

말로만 하면 안 믿기지. 실물 보자. 캐릭터 이동 RPC의 검증 함수야.

Runtime/Engine/Private/Character.cpp:1874-1877

bool ACharacter::ServerMove_Validate(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { return GetCharacterMovement()->ServerMove_Validate(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

클라가 보낸 이동 파라미터(가속, 위치 등)를 받아서 CharacterMovement한테 "이 값 정상이야?"라고 물어봐. bool을 반환하고, false면 실행 안 돼.

바로 위에 짝꿍인 _Implementation도 있어 — Character.cpp:1868-1872:

// ServerMove void ACharacter::ServerMove_Implementation(float TimeStamp, FVector_NetQuantize10 InAccel, FVector_NetQuantize100 ClientLoc, uint8 CompressedMoveFlags, uint8 ClientRoll, uint32 View, UPrimitiveComponent* ClientMovementBase, FName ClientBaseBoneName, uint8 ClientMovementMode) { GetCharacterMovement()->ServerMove_Implementation(TimeStamp, InAccel, ClientLoc, CompressedMoveFlags, ClientRoll, View, ClientMovementBase, ClientBaseBoneName, ClientMovementMode); }

구조가 딱 보이지? 같은 이름에 접미사만 달라.

  • _Validate → "이 값 써도 돼?" (bool 반환, 문지기)
  • _Implementation → "실제로 이 값으로 이동시켜" (진짜 몸통)

네가 UFUNCTION(Server, Reliable, WithValidation)이라고 선언하면, 원본 함수명(ServerMove)은 UHT가 자동 배선용으로 가져가고, 너는 ServerMove_Validate(문지기)랑 ServerMove_Implementation(로직) 두 개를 직접 짜는 거야. _Validate가 통과해야만 _Implementation이 실행돼.

참고로 비트스트림으로 뭉쳐 보낸 이동은 _Validate에서 못 풀어보니까 일단 통과시키고 나중에 거절해 — Character.cpp:1862-1866:

bool ACharacter::ServerMovePacked_Validate(const FCharacterServerMovePackedBits& PackedBits) { // Can't really validate the bit stream without unpacking, and that is done in ServerMovePacked_ServerReceive() and can be rejected after unpacking. return true; }

"비트스트림은 풀기 전엔 검증 못 해. 언팩은 ServerMovePacked_ServerReceive()에서 하고 거기서 거절 가능"이라고 주석이 직접 알려줘. 검증 시점이 항상 _Validate인 건 아니고, 못 하는 경우는 뒤로 미룬다는 것도 알아두면 좋아.

호출 순서 한눈에

[송신측 — NetDriver.cpp] InternalProcessRemoteFunction (2897) │ ▼ InternalProcessRemoteFunctionPrivate (2911) │ unreliable + 회선포화 → 그냥 드롭 (2929) ▼ if (FunctionFlags & FUNC_NetReliable) ── Bunch.bReliable = 1 (3135-3138) │ ▼ Bunch.IsError()? ── reliable 버퍼 넘침 → 연결 종료 (3144-3152) │ ▼ ~~~~ 네트워크 ~~~~ │ [수신측 — DataChannel.cpp] ReceivedRawBunch (640) bReliable && ChSequence != InReliable+1 → 버퍼링(순서대기) │ (순서 맞으면 통과) ▼ [수신측 — DataReplication.cpp] FObjectReplicator::ReceivedRPC (1319) │ ▼ 방향 검사: Server/Client 플래그 vs bIsServer → 어긋나면 거절 (1346-1357) │ ▼ RPC_ResetLastFailedReason() (1441) │ ▼ CallProcessEventForReceivedRPC → ProcessEvent (1447) │ └─ [내부] Xxx_Validate() 먼저 실행 → 실패면 사유 세팅 │ └─ [내부] 통과하면 Xxx_Implementation() 실행 ▼ RPC_GetLastFailedReason() != nullptr → 로그 + return false (1461-1465)

핵심만 다시: 보낼 때 플래그로 reliable 도장(3135) → 받을 때 순번으로 순서 대기(640) → 실행 전 방향 검사(1346) + 값 검증(1441~1465).

우리 서버랑 비교 — IOCP 워커 vs UE

우리 조선협객전 서버 방식이랑 붙여보면 감이 확 와.

우리 서버 (조선)UE

스레드 모델워커는 여러 개지만 액터 로직은 사실상 단일 스레드로 직렬화게임 스레드 단일. ProcessEvent도 게임 스레드에서

큰 차이 두 개만 기억해.

첫째, 순서 보장 위치가 달라. 우리는 TCP 위에 올라타서 순서를 공짜로 받아. 그래서 우리 핸들러엔 "이 패킷이 앞 패킷보다 먼저 왔나?" 같은 코드가 없지. UE는 UDP 기반이라 순서를 직접 만들어야 해. 그게 DataChannel.cpp:640의 ChSequence 비교야. 우리가 TCP한테 위임한 걸 UE는 손으로 구현한 거지. 대신 UE는 "이건 순서 필요 없으니 unreliable로" 하고 선택적으로 포기할 수 있어 — 우리 TCP는 그런 선택권이 없어(다 순서 보장, 다 비용 지불).

둘째, 검증이 "손코딩" vs "계약". 우리는 CM_XXX 핸들러 안에서 개발자가 까먹지 않고 범위체크를 짜야 해. 까먹으면 그냥 구멍. UE는 WithValidation을 붙이는 순간 _Validate 함수가 컴파일 단계에서 강제돼(안 짜면 링크 에러). 검증을 "잊어버릴 수 없게" 프레임워크가 붙잡아주는 구조야. 우리 서버로 치면, 모든 CM_ 핸들러에 "검증 함수 없으면 빌드 실패"를 강제하는 규칙을 넣은 셈.

소스 포함 여부 (정직 표기)

  • 포함됨 (위 인용 전부 실제 파일에서 직접 대조 확인): reliable/unreliable 송신 분기(NetDriver.cpp), 순서 보장(DataChannel.cpp:640), 방향 필터 + 검증사유 소비(DataReplication.cpp ReceivedRPC), _Validate/_Implementation 실구현(Character.cpp).
  • 🔬 미포함: WithValidation 리터럴과 exec 스텁 생성 코드(UHT 산출 .gen.cpp), RPC_ValidateRequestFailed/RPC_GetLastFailedReason의 정의부(CoreUObject 매크로 헤더). 이 트리는 Engine/Source 부분 트리라 정의 파일이 없어. 단 이 심볼들을 호출·소비하는 지점은 위 인용대로 실재하고 직접 대조했어.
