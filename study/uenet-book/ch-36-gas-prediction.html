GAS 예측 — 스킬을 미리

언리얼 네트워크 · 36 / 42

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "클라가 스킬 버튼 누르는 순간, 서버 대답도 안 왔는데 왜 벌써 이펙트가 터지는지 — 그리고 그게 틀렸을 땐 어떻게 슬그머니 취소되는지"가 머릿속에 그려질 거야.
client-prediction이 "이동"을 미리 하는 얘기였다면, 여긴 "스킬/버프"를 미리 하는 얘기야. 같은 낙관적 실행(optimistic execution)인데 대상이 다름.

🔬 이 클론에 소스 미포함 — 개념 위주, 실제 대조 필요

먼저 정직하게 못 박고 시작하자. 이 학습 트리엔 GAS(Gameplay Ability System) 플러그인 소스가 없어.

  • 확인한 경로: E:/Chosun_Classic/MSH_TRUNK_NEW/_study/UE_Network/Engine
  • FScopedPredictionWindow / FPredictionKey / ScopedPredictionKey grep → 0건
  • AbilitySystemComponent / GameplayPrediction 파일명 검색 → 0건
  • 실제 엔진에선 GAS가 Engine/Plugins/Runtime/GameplayAbilities에 사는데, 그 폴더 자체가 이 서브셋에 빠져 있음. (담긴 플러그인은 ReplicationGraph와 Iris뿐 — replication-graph, iris 참고.)

그래서 이 챕터는 다른 편들과 달라. 콜체인 다이어그램에 붙일 실제 file:line이 없다. TryActivateAbility → ServerTryActivateAbility → FScopedPredictionWindow → … 이 실제 흐름의 함수/줄번호를 인용할 수가 없어. 각색·창작은 금지니까, 그 자리는 개념 흐름도로 대신하고, verbatim은 트리에 딱 하나 실재하는 GAS 흔적(§4의 Iris 주석)만 싣는다.

읽는 자세: 아래 흐름은 "GAS가 이런 원리로 동작한다"는 개념 뼈대야. 나중에 실제 GameplayPrediction.h/.cpp를 확보하면 이 뼈대에 정확한 라인을 채워 대조해야 해. 지금은 원리까지만.

0. 먼저 비유부터 — 주문부터 받고 나중에 취소

카페에서 네가 "아이스 아메리카노요" 하고 외치면, 알바생이 본사 승인 기다리고 나서 컵 꺼내디? 아니잖아. 바로 컵 꺼내서 얼음 담기 시작해. 손님 체감상 즉시 반응.

그러다 아주 가끔 "죄송한데 그 원두 지금 품절이에요" 소리가 나오면? 담던 거 엎고 손님한테 사과하고 되돌리지.

GAS 예측이 딱 이 구조야.

  • 바로 컵 꺼냄 = 클라가 서버 응답 안 기다리고 스킬을 로컬에서 먼저 실행. 애니메이션 재생, 마나 차감, 쿨다운 시작, 일부 이펙트 적용을 즉시 보여줌.
  • 주문표에 번호 적음 = PredictionKey. "이 컵은 아직 본사 확정 전(예측분)"이라고 딱지를 붙임.
  • 본사 승인 = 서버가 진짜로 판정. 대부분 통과.
  • 품절이라 엎음 = 서버가 "그 스킬 못 써"라고 하면, 미리 보여준 효과를 취소(롤백).

핵심 직관 하나 먼저 박아두자.

클라는 서버를 기다리지 않는다. 스킬을 먼저 터뜨리고, 나중에 서버가 진짜로 채점한다. 맞았으면 자연스럽게 이어지고, 틀렸으면 되돌린다.

그럼 이 챕터의 진짜 질문은 이거 하나야:

"미리 터뜨린 효과"를 어떻게 딱지 붙여 기억해뒀다가, 서버 결과가 오면 정확히 그놈만 걷어내냐?

1. 왜 굳이 별도 시스템인가 — 복제만으론 안 되는 이유

여기서 잠깐 맞춰봐. 우리는 이미 lifetime-props, repnotify에서 "프로퍼티 복제"를 배웠잖아. 서버가 값 바꾸면 클라로 자동으로 내려오는 그거. 그럼 스킬 효과도 그냥 복제로 하면 되는 거 아냐? 서버가 마나 깎으면 클라로 복제돼서 내려오고, 끝. PredictionKey니 뭐니 왜 필요해?

...

반전은 이거야. 일반 복제는 "서버가 진실, 클라는 수신"만 한다. 서버가 값을 정하고 → 클라는 받기만 함. 이 모델엔 "클라가 먼저 바꿔놓는" 개념이 아예 없어. 그래서 복제만 쓰면 클라는 무조건 RTT(왕복 지연)만큼 기다려야 마나가 깎이고 이펙트가 뜬다. 액션감이 죽지.

예측은 여기에 한 겹을 더 얹어. "클라가 잠깐 자기 진실을 만들고, 나중에 서버 진실로 화해(reconcile)" 하는 레이어. 그런데 이걸 하려면 문제가 생겨:

  • 클라가 마나를 -30 미리 깎아놨음 (예측분).
  • 그 다음 서버가 진짜로 판정하고 마나 -30을 복제로 내려보냄.
  • 순진하게 하면? 클라 화면은 -60이 돼버려. 예측분 한 번 + 복제분 한 번 = 이중 차감.

그래서 필요한 게 장부야. "이 -30은 내가 예측으로 미리 깎은 거다"라고 딱지를 붙여두면, 서버의 진짜 -30이 도착했을 때 내 예측분을 먼저 걷어내고 서버 걸로 갈아끼울 수 있어. 이 딱지가 바로 PredictionKey고, 딱지가 유효한 코드 구간이 ScopedPredictionWindow야.

한 줄로: 복제는 "받기만", 예측은 "먼저 만들고 나중에 화해". 화해하려면 뭘 걷어낼지 알아야 하니까 PredictionKey라는 장부가 따로 있다.

2. 개념 흐름도 — 스킬 한 번의 일생

소스가 없어 실제 file:line은 못 박지만, GAS 예측의 표준 흐름은 개념적으로 이렇게 돌아가. (아래 함수명은 실제 엔진의 통상 명칭이지만, 이 트리에서 라인 대조는 불가 — 개념 흐름도로 읽어.)

[ 클라(AutonomousProxy) ] [ 서버(Authority) ] │ 버튼 입력 │ ▼ TryActivateAbility() │ (1) PredictionKey 발급 — "이번 예측 = 표 #47" ├──────────────► ScopedPredictionWindow 열림 │ │ │ 로컬에서 미리 실행: │ · 애니메이션 재생 │ · 코스트 차감(마나 -30) ← "예측분, 표 #47" 딱지 │ · 쿨다운 시작 │ · 일부 GameplayEffect 적용 │ │ │ ScopedPredictionWindow 닫힘 │ │ (2) ServerTryActivateAbility(표 #47) └───────────────────────────────────────► 받음 │ 진짜 판정: · 정말 쓸 수 있나? · 마나 충분한가? │ ┌─────────────┴─────────────┐ [승인] [거부] │ │ authoritative 결과를 "표 #47 실패" 표 #47 키로 복제 ↓ 통보 ↓ ┌───────────────────────────────┘ │ ▼ ▼ (3-a) 예측이 맞음: (3-b) 예측이 틀림: 표 #47 예측분을 걷어내고 표 #47 예측분을 서버 버전으로 교체 전부 롤백(취소) → 유저는 깜빡임 없이 이어짐 → 미리 본 효과가 되돌아감

세 박자만 기억해:

  1. 발급 + 미리 실행: TryActivateAbility가 PredictionKey를 뽑고, ScopedPredictionWindow 안에서 로컬 효과를 딱지 붙여 적용.
  2. 서버로 던짐: ServerTryActivateAbility가 같은 키를 들고 서버로 감. 서버는 진짜 판정.
  3. 화해: 서버의 authoritative 결과가 그 키로 돌아오면 → 맞았으면 예측분 걷어내고 서버 걸로 교체, 틀렸으면 예측분 롤백.

client-prediction의 이동 예측이랑 뼈대가 똑같지? "먼저 하고(1) → 서버로 보내고(2) → 채점받아 화해(3)". 대상이 좌표냐 스킬효과냐만 다를 뿐이야. 되감는 쪽 원리 전체는 server-reconciliation에 있으니 겹치는 얘긴 거기로.

3. 우리 서버랑 비교 — IOCP 워커 vs 싱글스레드 액터

우리 조선협객전 서버 감각으로 번역해보자.

개념우리 C++ 서버UE GAS 예측
스킬 입력 수신IOCP 워커가 소켓에서 CM_SKILL 패킷 꺼냄RPC 언마샬링이 ServerTryActivateAbility 호출
실제 처리 스레드싱글스레드 액터/게임로직 스레드가 순차 판정서버 게임스레드가 ASC로 위임
판정 결과 통보SM_SKILL로 발동 성공/실패 브로드캐스트authoritative GameplayEffect를 PredictionKey로 복제
클라 선반영없음 — 서버 SM_SKILL 올 때까지 대기있음 — PredictionKey 딱지 붙여 미리 적용 후 나중에 화해

핵심 차이 딱 하나. 우리 서버는 클라가 스킬을 "미리 터뜨리는" 개념이 없어. 클라가 CM_SKILL 쏘면 서버가 판정하고 SM_SKILL로 결과를 내려주는 순수 서버 권위 왕복이 기본이지. 그래서 스킬 버튼 → 이펙트까지 핑이 그대로 노출돼.

GAS는 여기에 예측 레이어를 엔진 차원에서 표준화한 거야 — 클라가 서버 판정을 미리 흉내 내서 이펙트를 먼저 보여주고(ScopedPredictionWindow), 서버 판정은 뒤따라와서 틀렸을 때만 롤백. 대부분 맞으니까 체감 지연이 사라져.

IOCP 워커 ↔ 싱글스레드 액터의 "받는 손 / 처리하는 손 분리" 구조는 receive-callchain에서 봤던 그대로야. 예측은 그 위에 얹힌 애플리케이션 레벨 규약일 뿐 — 우리 서버 구조로도 흉내 낼 순 있지만(클라가 CM 쏘고 미리 이펙트 재생), "이중 차감 방지 장부(PredictionKey)"를 직접 만들어야 하는 게 GAS가 대신 해주는 일이야.

4. Verbatim — 이 트리에 실재하는 유일한 GAS 흔적

실제 예측/롤백 코드(AbilitySystemComponent.cpp, GameplayPrediction.h)는 못 읽어. 트리에 남은 유일한 GAS 원문은 Iris 다형 직렬화기가 "GAS 핸들의 동작을 흉내 냈다"고 밝히는 주석 한 토막이야. 예측 코드 자체는 아니지만, "GAS 핸들은 복제 프로퍼티가 아니라 RPC 전송용으로 설계됐다"는 걸 정직하게 뒷받침하는 1차 근거라 그대로 싣는다. (예측 데이터가 왜 지속 상태 복제가 아니라 이벤트성 RPC로 오가는지 — 그 배경.)

나머지 예측/롤백 스니펫(ScopedPredictionWindow 본문 등)은 소스 미포함이라 인용 불가. 채우려면 GameplayAbilities 플러그인 소스가 필요.

5. 용어 정의 (초보용)

  • 예측(Prediction): 서버 응답을 안 기다리고 클라가 스킬 결과를 미리 실행/표시하는 것. "낙관적 실행". 서버가 나중에 승인/거부한다.
  • PredictionKey: 예측 실행 하나를 식별하는 번호표. 클라의 로컬 변경과 서버의 확정 결과를 나중에 짝지어(reconcile), 예측분만 정확히 걷어내는 데 쓴다. 없으면 "이중 차감"을 못 막아.
  • ScopedPredictionWindow: PredictionKey가 유효한 코드 구간(스코프). 이 창 안에서 일어난 상태 변경은 "예측분"으로 딱지가 붙는다. 창을 벗어나면 딱지 발급 종료.
  • 롤백/화해(Rollback/Reconcile): 서버의 authoritative 결과가 도착하면, 클라가 미리 적용한 예측 상태를 취소하고 서버 버전으로 교체하는 과정. 맞았으면 조용히 교체, 틀렸으면 미리 본 효과가 취소돼 되돌아감.
  • 서버 권위(Server-authoritative): 최종 진실은 서버가 정한다는 원칙. 예측은 이 원칙을 깨지 않으면서 체감 지연만 숨긴다 — 클라 진실은 어디까지나 임시.
  • RPC vs 복제 프로퍼티: RPC는 일회성 함수 호출 전송, 복제 프로퍼티는 지속 상태 동기화. §4 주석대로 GAS 핸들은 RPC 전송용 — 예측 데이터가 이벤트성으로 오가는 배경. (rpc-types 참고.)

6. 참조 링크

  • 막히면 → client-prediction (같은 낙관적 실행을 "이동"으로. 이 챕터의 자매편, 전제)
  • 예측을 되감는 쪽 원리 전체 → server-reconciliation
  • 예측 데이터가 왜 RPC에 실리나 → rpc-types, rpc-reliable-validation
  • 왜 "복제만으론 안 되나"의 복제 쪽 배경 → lifetime-props, repnotify
  • §4 verbatim이 나온 Iris 직렬화 맥락 → iris
  • 다음 → voip

🎯 원리 한 줄 요약

클라는 서버를 안 기다리고 스킬을 먼저 터뜨려 PredictionKey 딱지를 붙여두고(ScopedPredictionWindow), 서버가 같은 키로 진짜 판정 결과를 내려주면 그 예측분만 정확히 걷어내 서버 버전으로 화해한다 — 맞으면 매끄럽게, 틀리면 롤백. (단, 예측/롤백 본문 소스는 이 트리에 미포함이라 개념 뼈대까지만.)
