Push Model — 폴링 대신 수동 dirty

0. 문 앞에서: "누가 바뀐 걸 어떻게 알지?"

네트워크 게임 서버는 매 틱마다 이런 고민을 해.

"이 액터의 어떤 프로퍼티가 바뀌었지? 바뀐 것만 클라에 보내야 하는데."

가장 정직한 방법은 전부 비교하는 거야. 지난번에 보낸 값을 그림자(shadow)로 하나 들고 있다가, 매 프레임 현재값이랑 하나하나 memcmp 해서 다르면 "바뀜"으로 판정. 이게 UE의 전통적 리플리케이션 방식이고, 이걸 폴링(polling) 또는 비교 방식(compare) 이라고 불러.

문제가 뭘까? 한번 맞춰봐.

액터가 10만 개, 각자 프로퍼티가 30개. 근데 이번 프레임에 실제로 바뀐 건 그중 5개뿐. 폴링은 몇 번 비교할까?

...정답: 300만 번. 5개 바꾸겠다고 300만 번을 비교해. 안 바뀐 걸 확인하려고 안 바뀐 걸 전부 만져보는 거지. UE 소스 주석도 이걸 그대로 인정해:

"Where the system starts to fall down is in terms of performance... there's no choice but to compare every property on every object." — PushModel.h:34-38

Push Model은 이 발상을 뒤집어. 비교하지 말고, 값을 바꾼 놈이 직접 손들게 하자. "나 바뀌었어요"라고 push하게. 그럼 서버는 손든 놈만 보면 돼.

  • 폴링(Pull): 서버가 매 프레임 "너 바뀌었니? 너는? 너는?" — 전부 물어봄
  • 푸시(Push): 값 바꾼 게임 코드가 "저 바뀌었어요!" — 바뀐 놈만 신고

이 챕터는 그 "손드는 장치"가 실제 코드로 어떻게 생겼는지를 본다.

전제가 헷갈리면 → replayout (프로퍼티가 RepIndex/Changelist로 어떻게 펼쳐지는지), changelist (바뀐 것만 모으는 changelist 개념)

1. 큰 그림: dirty 비트 하나 켜는 게 전부

Push Model의 핵심은 놀랄 만큼 단순해. 프로퍼티마다 비트 하나를 두고, 값이 바뀌면 그 비트를 1(dirty)로 켠다. 리플리케이트할 때 켜진 비트만 골라서 비교하고, 다 처리하면 비트를 끈다.

"바뀌었다"를 저장하는 자료구조가 TBitArray — 프로퍼티 개수만큼 비트가 늘어선 배열이야. RepIndex(프로퍼티 ID)가 곧 비트 배열의 인덱스.

정말 이게 전부인지, 값 세팅하는 실제 코드를 봐. PushModelPerObjectState.h:64:

		void MarkPropertyDirty(const uint16 RepIndex)
		{
			DirtiedThisFrame[RepIndex] = true;
			bHasDirtyProperties = true;
		}

두 줄. RepIndex번 비트를 켜고, "이 오브젝트에 dirty가 하나라도 있다"는 플래그를 세운다. 여기서 push는 끝. 매 프레임 비교하는 코드는 어디에도 없어. 값을 바꾼 순간 딱 이 두 줄만 실행되고 손을 턴다.

이게 왜 강력하냐면 — 비용이 바꾼 횟수에 비례하지, 프로퍼티 총 개수에 비례하지 않아. 5개 바꿨으면 이 함수 5번. 300만이 5가 됐어.

2. 생산측: 게임 코드가 "바뀌었다"고 신고하는 길

그럼 게임 코드는 저 MarkPropertyDirty를 어떻게 부를까? 직접 부르지 않아. 매크로 하나로 감싸.

세터에서 값 바꾼 직후 이 한 줄을 부르면 돼. PushModel.h:454:

// Marks a property dirty, given the Class Name, Property Name, and Object. This will fail to compile if the Property or Class aren't valid.
#define MARK_PROPERTY_DIRTY_FROM_NAME(ClassName, PropertyName, Object) CONDITIONAL_ON_OBJECT_NET_ID(Object, UEPushModelPrivate::MarkPropertyDirty(Object, PrivatePushId, GET_PROPERTY_REP_INDEX(ClassName, PropertyName)))

읽는 법:

  • GET_PROPERTY_REP_INDEX(ClassName, PropertyName) — 프로퍼티 이름을 컴파일 타임에 RepIndex 숫자로 바꿔치기(PushModel.h:426). 이름 오타 나면 컴파일 자체가 안 돼. 런타임 사고를 컴파일 에러로 앞당기는 거지.
  • CONDITIONAL_ON_OBJECT_NET_ID(...) — 이 오브젝트가 push 대상(net id 있음)일 때만 실제로 실행.
  • 안쪽 UEPushModelPrivate::MarkPropertyDirty(Object, PushId, RepIndex) — 여기서부터 매니저로 들어감.

그리고 세터 보일러플레이트를 아예 줄여주는 축약 매크로도 있어. PushModel.h:466:

#define COMPARE_ASSIGN_AND_MARK_PROPERTY_DIRTY(ClassName, PropertyName, NewValue, Object) \
	if (NewValue != PropertyName) { PropertyName = NewValue; MARK_PROPERTY_DIRTY_FROM_NAME(ClassName, PropertyName, Object); }

값이 실제로 달라질 때만 대입하고 dirty 마킹해. 같은 값을 또 대입하는 헛발질에는 비트를 안 켠다. (주석 왈: int·float·포인터엔 좋지만 struct엔 memcmp 비용 때문에 비추.)

여기서 매크로 → 매니저 분기 흐름은 이렇게 흘러가:

게임 세터 코드
  MARK_PROPERTY_DIRTY_FROM_NAME(Class, Prop, Obj)         PushModel.h:454
        |  (프로퍼티 이름 -> RepIndex 로 컴파일 타임 치환)
        v

3. 왜 상태가 2층이야? (글로벌 ↔ 넷드라이버별)

여기가 이 챕터에서 제일 헷갈리는 부분이자 제일 똑똑한 부분이야. dirty 상태가 한 군데가 아니라 두 군데에 있어.

  • FPushModelPerObjectState — 오브젝트 1개당 하나. 모든 넷드라이버가 공유하는 글로벌 dirty. 게임 코드는 여기에만 push해.
  • FPushModelPerNetDriverState — 넷드라이버마다 하나. 실제 리플리케이트 비교는 여기서 봄.

왜 굳이 둘로 나눴을까? 맞춰봐.

서버 하나에 넷드라이버가 여러 개일 수 있어(게임용 + 서버사이드 리플레이 녹화용 등). 게임 코드가 값 바꿀 때마다 곧바로 모든 넷드라이버 상태에 복사하면 뭐가 낭비지?

...반전: 리플리케이트 후보 액터 중 실제로 이번에 보내는 건 극히 일부야. 대부분은 relevancy·dormancy로 이번 프레임에 안 보내(→ relevancy, dormancy). 그런데 값 바꿀 때마다 넷드라이버 전부에 미리 복사해두면, 결국 안 보낼 놈들 상태까지 부지런히 갱신하는 헛수고가 돼. 소스도 이 이유를 명시해(PushModel.cpp:110-131).

그래서 lazy flush(지연 반영). 게임 코드는 글로벌에만 쌓아두고, 진짜 리플리케이트하기 직전에만 그 오브젝트의 글로벌 dirty를 각 넷드라이버로 몰아서 OR 연산으로 밀어넣어. PushModelPerObjectState.h:74:

		void PushDirtyStateToNetDrivers()
		{
			if (bHasDirtyProperties)
			{
				for (FPushModelPerNetDriverState& NetDriverObject : PerNetDriverStates)
				{
					NetDriverObject.MarkPropertiesDirty(DirtiedThisFrame);
				}

				ResetBitArray(DirtiedThisFrame);
				bHasDirtyProperties = false;
			}
		}

글로벌 dirty 비트를 넷드라이버마다 bitwise-OR로 누적시키고, 글로벌은 리셋. OR로 넣는 이유는 — 지난번에 어떤 넷드라이버가 아직 처리 못 한 dirty가 남아있을 수 있으니 덮어쓰지 않고 합치는 거야. 이 flush를 언제 부르냐면, 비교 직전 GetPerNetDriverState(Handle)가 반환 전에 슬쩍 불러(PushModel.cpp:301). 그래서 "lazy" — 필요한 순간까지 미뤘다가 그때 한 번에.

4. 소비측: dirty만 골라서 비교하고 끝나면 끈다

이제 리플리케이션이 프로퍼티를 비교하려는 순간. RepLayout이 각 프로퍼티마다 "얘 비교해야 해?"를 물어. RepLayout.cpp:1499:

	static bool IsPropertyDirty(
		const int32 ParentIndex,
		const bool bRecentlyCollectedGarbage,
		const FComparePropertiesSharedParams& SharedParams,
		FComparePropertiesStackParams& StackParams)
	{
		return SharedParams.bForceCompareProperties ||
			!(*SharedParams.PushModelProperties)[ParentIndex] || // non-push model properties are always considered dirty			
			SharedParams.PushModelState->IsPropertyDirty(ParentIndex) ||
			(bRecentlyCollectedGarbage &&
				EnumHasAnyFlags(SharedParams.Parents[ParentIndex].Flags, ERepParentFlags::HasObjectProperties | ERepParentFlags::IsNetSerialize));
	}

읽는 법 — OR로 묶인 이 조건 중 하나라도 참이면 "비교해라":

  1. bForceCompareProperties — 강제 비교 모드(디버그/특정 상황)면 무조건.
  2. !(*PushModelProperties)[ParentIndex] — push 모델을 안 쓰는 프로퍼티는 항상 dirty 취급. (신고 안 하는 놈이니 서버가 대신 매번 봐줘야 함.)
  3. PushModelState->IsPropertyDirty(ParentIndex) — push 프로퍼티는 오직 이것뿐. dirty 비트가 꺼져 있으면 false → 비교(memcmp) 통째로 스킵. 이게 절약의 핵심.
  4. 마지막 줄 — 방금 GC가 돌았고 오브젝트 참조/NetSerialize 프로퍼티면 안전하게 다시 봐(dangling 방지).

3번이 이 시스템의 존재 이유야. push 프로퍼티는 "누가 손 안 들었으면 안 본다."

한발 더 — 클래스 전체가 모든 프로퍼티를 push로 커버하면(FullPushProperties), 프로퍼티를 하나씩 돌며 묻지도 않아. 켜진 비트만 이터레이트해. RepLayout.cpp:1614:

		// If we have full push model property support, then we only need to check properties that are actually dirty.
		else if (EnumHasAnyFlags(SharedParams.Flags, ERepLayoutFlags::FullPushProperties) && !bRecentlyCollectedGarbage)
		{
			UE_LOG(LogRepCompares, VeryVerbose, TEXT("CompareParentProperties: Full push properties: Has Dirty: %d"), !!SharedParams.PushModelState->HasDirtyProperties());

			for (TConstSetBitIterator<> It = SharedParams.PushModelState->GetDirtyProperties(); It; ++It)
			{
				CompareParentPropertyHelper(It.GetIndex(), SharedParams, StackParams);
			}
		}

GetDirtyProperties()가 주는 set-bit 이터레이터 — 1인 비트만 건너뛰며 방문. 프로퍼티 총 개수는 아예 루프에 안 들어와. 폴링의 "every property" 루프가 여기서 사라진다.

비교 다 끝나면? 넷드라이버 dirty 비트를 클리어해서 다음 라운드를 준비해(ResetDirtyStates() — RepLayout.cpp:1636 → PushModelPerNetDriverState.h:40). 켜고(mark) → 골라 비교하고(compare) → 끄고(reset). 이 삼박자가 한 사이클.

비교 직전

        |  +-(반환 전에) PushDirtyStateToNetDrivers()  <- lazy flush
        v
  CompareParentProperties(...)              RepLayout.cpp:1514
        |
        +- FullPushProperties?  -> GetDirtyProperties() 로 켜진 비트만 순회   RepLayout.cpp:1614

                                    v

5. 우리 서버 비교: IOCP 워커 vs 싱글스레드 액터

우리 조선협객전 서버 감각으로 번역해볼게.

우리 서버의 폴링스러운 부분 — 예를 들어 매 틱 캐릭터 상태를 훑어서 주변에 뿌릴지 판단하는 루프가 있다고 치면, "전부 순회하며 바뀐 놈 찾기"는 폴링이야. Push Model은 이걸 "값 바꾼 코드가 dirty 큐에 넣기"로 바꾸는 것과 같아.

스레드 모델 차이가 핵심 주의점이야:

  • 우리 서버: IOCP 워커 여러 개가 패킷을 병렬 처리 → 공유 상태 바꿀 땐 락/원자성 신경 써야 함.
  • UE Push Model의 MarkPropertyDirty는 게임 스레드 싱글스레드 전제. 비트 세팅 두 줄에 락이 없는 이유가 이거야. 만약 우리처럼 IOCP 워커가 여기 손대면 DirtiedThisFrame[RepIndex] = true는 데이터 레이스가 돼.

그래서 교훈: "바뀔 때 dirty 마킹" 패턴 자체는 우리도 도입 가능하지만, 우리 환경에선 마킹 지점이 IOCP 워커 경계를 넘나드는지부터 봐야 해. UE가 락 없이 두 줄로 끝낼 수 있는 건 싱글스레드라는 강한 전제 덕분이지, 마법이 아니야.

그리고 UE의 2층 구조(글로벌↔넷드라이버별)는 우리로 치면 "공용 dirty 큐 하나 → 리플레이/샤드별로 소비 분리" 하는 것과 닮았어. 생산은 한 곳, 소비는 여러 곳.

6. 함정 세 개 (소스가 직접 경고함)

Push Model은 공짜가 아니야. "손 안 들면 안 본다"는 규칙이 곧 함정이 돼.

  1. 스위치 두 개 다 켜야 함. 컴파일 스위치 WITH_PUSH_MODEL + 런타임 CVar Net.IsPushModelEnabled. 근데 이 CVar 기본값이 false(PushModel.cpp:434). 안 켜면 있어도 안 돈다.
  1. 마킹 없이 값 바꾸면 영영 전송 안 됨. push 프로퍼티의 참조/포인터를 밖으로 들고 나가서 dirty 마킹 없이 값을 바꾸면? 아무도 손 안 들었으니 서버는 비교조차 안 하고 넘어가. 변경이 조용히 유실돼. 소스가 강한 경고로 못 박아둠(PushModel.h:199-214). (우리 서버에서 "저장했는데 클라에 반영 안 됨" 류 사고의 UE판이 딱 이거야.)
  1. 최상위 프로퍼티 단위로만 추적. 구조체·컨테이너 내부를 찔끔 바꿔도, 그 값을 담은 최상위 프로퍼티를 통째로 dirty 마킹해야 해(PushModel.h:107-115). "배열 3번 원소만 바꿨어요"를 세밀하게 추적 못 함 — 배열 프로퍼티 전체가 dirty.

마지막으로 솔직한 한 줄. 헤더 주석 스스로 이렇게 적어뒀어: "이론적 이득은 좋으나 실측 이득은 기대만큼 안 나왔다"(PushModel.h:16-18). 폴링을 없앤 대신 마킹 규율이라는 부채를 졌고, 그 손익은 프로젝트마다 다르다는 정직한 고백이야. 최적화는 언제나 트레이드오프.

🎯 원리 한 줄 요약

폴링은 "안 바뀐 걸 확인하려 전부 비교"하고, Push Model은 "값 바꾼 코드가 dirty 비트 하나 켜서" 서버가 켜진 비트만 보게 만든다 — 비용이 프로퍼티 개수가 아니라 변경 횟수에 비례한다.

  • 막히면 → replayout (RepLayout이 프로퍼티를 어떻게 펼치는지), changelist (바뀐 것만 모으는 상위 개념)
  • 다음 → rep-conditions (조건부 리플리케이션 — 누구에게 보낼지), iris (차세대 리플리케이션에서 push가 어떻게 진화하는지)
