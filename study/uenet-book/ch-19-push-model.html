Push Model — 폴링 대신 수동 dirty

언리얼 네트워크 · 19 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이런 고민을 해봤을 거야. CChosunPlayer의 체력, 위치, 버프, 장비, 퀘스트 상태가 계속 바뀌는데, 클라한테는 바뀐 것만 보내고 싶어. 안 바뀐 값까지 매 틱 SP_* 패킷으로 다 뿌리면 대역폭도 아깝고, 서버도 쓸데없는 일을 너무 많이 하니까.

가장 쉬운 방법은 매 틱 전부 훑는 거야. "체력 바뀌었니? 위치는? 버프는? 인벤은?" 하고 모든 플레이어의 모든 값을 비교해. 액터가 적을 때는 괜찮아 보이지만, 사람이 많아지고 프로퍼티가 늘어나면 안 바뀐 걸 확인하려고 안 바뀐 값까지 계속 만지는 꼴이 돼. 5개 바뀌었는지 보려고 300만 칸을 뒤지는 상황이 나오는 거지.

우리 조선 서버로 치면 IOCP 워커가 CM_* 패킷을 받아 값 하나를 바꿨는데, 나중에 단일스레드 게임 루프가 "뭐가 바뀌었더라?" 하고 전체 상태를 다시 뒤지는 그림이야. 더 무서운 건 최적화하려고 락을 여기저기 걸기 시작하면, 바뀐 값 찾는 일 자체가 서버 발목을 잡을 수 있다는 점이야.

그래서 언리얼도 같은 문제를 만났고, 그 답이 Push Model이야. 서버가 매번 "너 바뀌었니?" 하고 물어보는 대신, 값을 바꾼 코드가 그 순간 "나 바뀌었어요" 하고 dirty 비트를 켠다. 학교에서 선생님이 전교생을 하나씩 부르는 대신, 숙제 낸 애만 손드는 식이야.

이걸 지금 배우는 이유도 분명해. 앞에서 RepLayout과 changelist로 "프로퍼티가 어떤 번호로 펼쳐지고, 바뀐 목록이 어떻게 만들어지는지"를 봤다면, 이번 장은 그 바뀐 목록을 더 싸게 만드는 장치야. 다음 조건부 리플리케이션이나 Iris로 넘어가기 전에, 무엇을 보낼지 고르는 비용 자체를 어떻게 줄이는지 잡고 가야 뒤가 덜 흔들려.

0. 문 앞에서: "누가 바뀐 걸 어떻게 알지?"

네트워크 게임 서버는 매 틱마다 이런 고민을 해.

"이 액터의 어떤 프로퍼티가 바뀌었지? 바뀐 것만 클라에 보내야 하는데."

가장 정직한 방법은 전부 비교하는 거야. 지난번에 보낸 값을 그림자(shadow)로 하나 들고 있다가, 매 프레임 현재값이랑 하나하나 memcmp 해서 다르면 "바뀜"으로 판정. 이게 UE의 전통적 리플리케이션 방식이고, 이걸 폴링(polling) 또는 비교 방식(compare) 이라고 불러.

문제가 뭘까? 한번 맞춰봐.

액터가 10만 개, 각자 프로퍼티가 30개. 근데 이번 프레임에 실제로 바뀐 건 그중 5개뿐.
폴링은 몇 번 비교할까?

...정답: 300만 번. 5개 바꾸겠다고 300만 번을 비교해. 안 바뀐 걸 확인하려고 안 바뀐 걸 전부 만져보는 거지. UE 소스 주석도 이걸 그대로 인정해:

"Where the system starts to fall down is in terms of performance... there's no choice but to compare every property on every object."
— PushModel.h:34-38

Push Model은 이 발상을 뒤집어. 비교하지 말고, 값을 바꾼 놈이 직접 손들게 하자. "나 바뀌었어요"라고 push하게. 그럼 서버는 손든 놈만 보면 돼.

  • 폴링(Pull): 서버가 매 프레임 "너 바뀌었니? 너는? 너는?" — 전부 물어봄
  • 푸시(Push): 값 바꾼 게임 코드가 "저 바뀌었어요!" — 바뀐 놈만 신고

이 챕터는 그 "손드는 장치"가 실제 코드로 어떻게 생겼는지를 본다.

전제가 헷갈리면 → replayout (프로퍼티가 RepIndex/Changelist로 어떻게 펼쳐지는지), changelist (바뀐 것만 모으는 changelist 개념)

지금부터 진짜 코드가 나와. 겁먹지 마 — 이름이 길고 괄호가 많아 보여도, 바로 아래 🔤 상자에서 하나씩 풀어줄게. 코드를 외우는 게 아니라 "dirty 비트가 어디서 켜지나"만 따라가면 돼.

🌱 이 개념은 왜 생겼나 — Push Model(dirty 비트)
• 원래 구조: 서버가 매 틱 모든 액터의 모든 프로퍼티를 지난 값이랑 하나하나 비교해서 바뀐 걸 찾아. 정직하지.
• 그런데 문제: 액터 10만 개 × 프로퍼티 30개인데 이번에 바뀐 건 5개뿐이면, 그 5개 찾으려고 300만 번을 비교해. 안 바뀐 걸 확인하려고 안 바뀐 값까지 전부 만지는 헛수고야.
• 그래서 필요한 것: 서버가 묻지 말고, 값 바꾼 코드가 직접 "나 바뀌었어요" 손들게 하기. → 그게 Push Model이고, 손드는 방법이 dirty 비트 하나 켜기. 전교생 하나씩 부르는 대신 숙제 낸 애만 손드는 거지.

1. 큰 그림: dirty 비트 하나 켜는 게 전부

Push Model의 핵심은 놀랄 만큼 단순해. 프로퍼티마다 비트 하나를 두고, 값이 바뀌면 그 비트를 1(dirty)로 켠다. 리플리케이트할 때 켜진 비트만 골라서 비교하고, 다 처리하면 비트를 끈다.

"바뀌었다"를 저장하는 자료구조가 TBitArray — 프로퍼티 개수만큼 비트가 늘어선 배열이야. RepIndex(프로퍼티 ID)가 곧 비트 배열의 인덱스.

정말 이게 전부인지, 값 세팅하는 실제 코드를 봐. PushModelPerObjectState.h:64:

void MarkPropertyDirty(const uint16 RepIndex) { DirtiedThisFrame[RepIndex] = true; bHasDirtyProperties = true; }
🔤 기호 사전 — void MarkPropertyDirty(const uint16 RepIndex)
• void = 이 함수는 계산 결과를 돌려주지 않는다는 뜻. 대신 안쪽 상태를 바꿔서 표시만 해.
• const uint16 RepIndex = RepIndex라는 번호는 이 함수 안에서 바꾸지 않겠다는 약속. uint16은 작은 양의 정수 칸, 여기서는 프로퍼티 번호를 담아.
• DirtiedThisFrame[RepIndex] = DirtiedThisFrame이라는 비트 줄에서 RepIndex번째 칸을 고르는 말. 출석부에서 몇 번 학생 칸을 찍는 느낌이야.
• = true = 그 칸의 스위치를 켜라. "이번 프레임에 바뀌었다"는 표시를 남긴다.
• bHasDirtyProperties = 앞의 b는 보통 참/거짓 값이라는 신호. "dirty가 하나라도 있나?"를 담는 큰 깃발이야.
🔁 이제 다시 보자. MarkPropertyDirty(RepIndex)는 "RepIndex번 프로퍼티가 바뀌었다"고 신고하는 함수야. DirtiedThisFrame[RepIndex] = true로 그 번호 칸을 켜고, bHasDirtyProperties = true로 "이 오브젝트엔 볼 게 있어" 깃발까지 세운다. Push Model의 손들기는 여기서 끝나.

두 줄. RepIndex번 비트를 켜고, "이 오브젝트에 dirty가 하나라도 있다"는 플래그를 세운다. 여기서 push는 끝. 매 프레임 비교하는 코드는 어디에도 없어. 값을 바꾼 순간 딱 이 두 줄만 실행되고 손을 턴다.

이게 왜 강력하냐면 — 비용이 바꾼 횟수에 비례하지, 프로퍼티 총 개수에 비례하지 않아. 5개 바꿨으면 이 함수 5번. 300만이 5가 됐어.

2. 생산측: 게임 코드가 "바뀌었다"고 신고하는 길

그럼 게임 코드는 저 MarkPropertyDirty를 어떻게 부를까? 직접 부르지 않아. 매크로 하나로 감싸.

세터에서 값 바꾼 직후 이 한 줄을 부르면 돼. PushModel.h:454:

// Marks a property dirty, given the Class Name, Property Name, and Object. This will fail to compile if the Property or Class aren't valid. #define MARK_PROPERTY_DIRTY_FROM_NAME(ClassName, PropertyName, Object) CONDITIONAL_ON_OBJECT_NET_ID(Object, UEPushModelPrivate::MarkPropertyDirty(Object, PrivatePushId, GET_PROPERTY_REP_INDEX(ClassName, PropertyName)))
🔤 기호 사전 — #define MARK_PROPERTY_DIRTY_FROM_NAME(...) ...
• #define = 컴파일러에게 "이 이름을 보면 뒤의 긴 코드로 바꿔치기해라"라고 알려주는 매크로 선언.
• MARK_PROPERTY_DIRTY_FROM_NAME(ClassName, PropertyName, Object) = 함수처럼 보이지만 매크로야. ClassName, PropertyName, Object는 나중에 실제 클래스/변수/오브젝트 이름이 들어갈 빈칸.
• , = 매크로에 넣는 재료를 나누는 쉼표. "클래스 이름 / 프로퍼티 이름 / 오브젝트"를 따로 건네는 거야.
• CONDITIONAL_ON_OBJECT_NET_ID(...) = 조건문을 감싼 이름. 이 오브젝트가 push로 추적될 수 있을 때만 안쪽 dirty 마킹을 실행하게 막아주는 문지기야.
• UEPushModelPrivate::MarkPropertyDirty = UEPushModelPrivate라는 소속 안에 있는 MarkPropertyDirty를 부른다는 표시. ::는 "~안의"라고 읽으면 돼.
• GET_PROPERTY_REP_INDEX(ClassName, PropertyName) = 클래스와 프로퍼티 이름을 넣으면, 엔진이 쓰는 RepIndex 번호를 가져오는 장치.
🔁 이제 다시 보자. 이 매크로 한 줄은 "이 오브젝트가 push 대상이면 → 프로퍼티 이름을 RepIndex로 바꾸고 → 매니저의 MarkPropertyDirty를 불러라"야. 게임 코드는 이름으로 신고하지만, 안쪽으로 들어갈 때는 숫자 번호(RepIndex)로 바뀌는 거지.

읽는 법:

  • GET_PROPERTY_REP_INDEX(ClassName, PropertyName) — 프로퍼티 이름을 컴파일 타임에 RepIndex 숫자로 바꿔치기(PushModel.h:426). 이름 오타 나면 컴파일 자체가 안 돼. 런타임 사고를 컴파일 에러로 앞당기는 거지.
  • CONDITIONAL_ON_OBJECT_NET_ID(...) — 이 오브젝트가 push 대상(net id 있음)일 때만 실제로 실행.
  • 안쪽 UEPushModelPrivate::MarkPropertyDirty(Object, PushId, RepIndex) — 여기서부터 매니저로 들어감.

그리고 세터 보일러플레이트를 아예 줄여주는 축약 매크로도 있어. PushModel.h:466:

#define COMPARE_ASSIGN_AND_MARK_PROPERTY_DIRTY(ClassName, PropertyName, NewValue, Object) \ if (NewValue != PropertyName) { PropertyName = NewValue; MARK_PROPERTY_DIRTY_FROM_NAME(ClassName, PropertyName, Object); }
🔤 기호 사전 — COMPARE_ASSIGN_AND_MARK_PROPERTY_DIRTY(...)
• \ = 매크로가 다음 줄까지 이어진다는 표시. 한 줄짜리로 취급하지만 보기 좋게 줄을 나눈 거야.
• if (NewValue != PropertyName) = 새 값과 기존 값이 다르면 안으로 들어가. !=는 "같지 않다"라는 뜻.
• { ... } = 조건이 맞을 때 한꺼번에 실행할 일을 묶은 상자.
• PropertyName = NewValue = 프로퍼티에 새 값을 대입한다. 여기서 실제 값이 바뀐다.
• ; = 한 명령이 끝났다는 마침표.
• MARK_PROPERTY_DIRTY_FROM_NAME(...) = 값 바꾼 뒤 곧바로 "나 dirty 됐어" 신고를 이어서 한다.
🔁 이제 다시 보자. 이 매크로는 "값이 진짜 달라졌을 때만 대입하고, 그때만 dirty 신고하라"는 세터 보조 도구야. 같은 값을 또 넣으면 if 안으로 안 들어가니까 비트도 안 켜져.

값이 실제로 달라질 때만 대입하고 dirty 마킹해. 같은 값을 또 대입하는 헛발질에는 비트를 안 켠다. (주석 왈: int·float·포인터엔 좋지만 struct엔 memcmp 비용 때문에 비추.)

여기서 매크로 → 매니저 분기 흐름은 이렇게 흘러가:

게임 세터 코드 MARK_PROPERTY_DIRTY_FROM_NAME(Class, Prop, Obj) PushModel.h:454 | (프로퍼티 이름 -> RepIndex 로 컴파일 타임 치환) v UEPushModelPrivate::MarkPropertyDirty(Obj, PushId, RepIndex) PushModel.cpp:467 | +- Iris ID -> 델리게이트로 | +- 레거시 ID -> PushObjectManager 로 v FPushModelObjectManager_CustomId::MarkPropertyDirty(ObjId, RepIndex) PushModel.cpp:216 | (ObjectId 로 PerObjectStates 슬롯 찾아 위임) v FPushModelPerObjectState::MarkPropertyDirty(RepIndex) PushModelPerObjectState.h:64 | DirtiedThisFrame[RepIndex] = true; +-- ★ push 끝. 비교 없음.
🌱 이 개념은 왜 생겼나 — 2층 dirty 상태(글로벌 ↔ 넷드라이버별)
• 원래 구조: dirty 비트를 한 군데만 두면 깔끔하잖아. 값 바뀌면 거기 켜고, 보낼 때 거기 보고.
• 그런데 문제: 서버엔 넷드라이버가 여러 개일 수 있어(게임용 + 리플레이 녹화용 등). 값 바꿀 때마다 곧바로 모든 넷드라이버에 복사하면, 정작 relevancy·dormancy로 이번에 안 보낼 놈들 상태까지 부지런히 갱신하는 헛수고가 돼.
• 그래서 필요한 것: 게임 코드는 글로벌 한 곳에만 쌓고, 진짜 보내기 직전에만 각 넷드라이버로 몰아 넣는 지연 반영(lazy flush). 생산은 한 곳, 소비는 필요할 때 여러 곳 — 조선 서버 "공용 dirty 큐 → 샤드별 소비 분리"랑 닮았어.

3. 왜 상태가 2층이야? (글로벌 ↔ 넷드라이버별)

여기가 이 챕터에서 제일 헷갈리는 부분이자 제일 똑똑한 부분이야. dirty 상태가 한 군데가 아니라 두 군데에 있어.

  • FPushModelPerObjectState — 오브젝트 1개당 하나. 모든 넷드라이버가 공유하는 글로벌 dirty. 게임 코드는 여기에만 push해.
  • FPushModelPerNetDriverState — 넷드라이버마다 하나. 실제 리플리케이트 비교는 여기서 봄.

왜 굳이 둘로 나눴을까? 맞춰봐.

서버 하나에 넷드라이버가 여러 개일 수 있어(게임용 + 서버사이드 리플레이 녹화용 등).
게임 코드가 값 바꿀 때마다 곧바로 모든 넷드라이버 상태에 복사하면 뭐가 낭비지?

...반전: 리플리케이트 후보 액터 중 실제로 이번에 보내는 건 극히 일부야. 대부분은 relevancy·dormancy로 이번 프레임에 안 보내(→ relevancy, dormancy). 그런데 값 바꿀 때마다 넷드라이버 전부에 미리 복사해두면, 결국 안 보낼 놈들 상태까지 부지런히 갱신하는 헛수고가 돼. 소스도 이 이유를 명시해(PushModel.cpp:110-131).

그래서 lazy flush(지연 반영). 게임 코드는 글로벌에만 쌓아두고, 진짜 리플리케이트하기 직전에만 그 오브젝트의 글로벌 dirty를 각 넷드라이버로 몰아서 OR 연산으로 밀어넣어. PushModelPerObjectState.h:74:

void PushDirtyStateToNetDrivers() { if (bHasDirtyProperties) { for (FPushModelPerNetDriverState& NetDriverObject : PerNetDriverStates) { NetDriverObject.MarkPropertiesDirty(DirtiedThisFrame); } ResetBitArray(DirtiedThisFrame); bHasDirtyProperties = false; } }
🔤 기호 사전 — void PushDirtyStateToNetDrivers()
• void = 결과값을 돌려주는 함수가 아니야. 안쪽 dirty 상태를 옮기고 정리하는 일을 한다.
• if (bHasDirtyProperties) = dirty가 하나라도 있을 때만 안쪽을 실행해. 없으면 아무 넷드라이버에도 손댈 필요가 없어.
• for (FPushModelPerNetDriverState& NetDriverObject : PerNetDriverStates) = PerNetDriverStates 안의 넷드라이버 상태를 하나씩 꺼내 도는 반복문. :는 "~안에서 하나씩", &는 복사본 말고 원본을 직접 만진다는 뜻.
• . = 앞의 물건이 가진 기능을 부른다는 표시. NetDriverObject.MarkPropertiesDirty(...)는 그 넷드라이버 상태한테 dirty를 표시하라고 시키는 거야.
• ResetBitArray(DirtiedThisFrame) = 글로벌 dirty 비트 줄을 싹 비우는 호출.
• = false = "이제 글로벌 쪽엔 남은 dirty가 없다"라고 깃발을 내린다.
🔁 이제 다시 보자. PushDirtyStateToNetDrivers()는 dirty가 있을 때만 움직여. 넷드라이버별 상태를 하나씩 돌면서 DirtiedThisFrame을 밀어넣고, 다 보냈으면 글로벌 비트 줄과 bHasDirtyProperties 깃발을 꺼서 다음 변경을 기다린다.

글로벌 dirty 비트를 넷드라이버마다 bitwise-OR로 누적시키고, 글로벌은 리셋. OR로 넣는 이유는 — 지난번에 어떤 넷드라이버가 아직 처리 못 한 dirty가 남아있을 수 있으니 덮어쓰지 않고 합치는 거야. 이 flush를 언제 부르냐면, 비교 직전 GetPerNetDriverState(Handle)가 반환 전에 슬쩍 불러(PushModel.cpp:301). 그래서 "lazy" — 필요한 순간까지 미뤘다가 그때 한 번에.

4. 소비측: dirty만 골라서 비교하고 끝나면 끈다

이제 리플리케이션이 프로퍼티를 비교하려는 순간. RepLayout이 각 프로퍼티마다 "얘 비교해야 해?"를 물어. RepLayout.cpp:1499:

static bool IsPropertyDirty( const int32 ParentIndex, const bool bRecentlyCollectedGarbage, const FComparePropertiesSharedParams& SharedParams, FComparePropertiesStackParams& StackParams) { return SharedParams.bForceCompareProperties || !(*SharedParams.PushModelProperties)[ParentIndex] || // non-push model properties are always considered dirty SharedParams.PushModelState->IsPropertyDirty(ParentIndex) || (bRecentlyCollectedGarbage && EnumHasAnyFlags(SharedParams.Parents[ParentIndex].Flags, ERepParentFlags::HasObjectProperties | ERepParentFlags::IsNetSerialize)); }
🔤 기호 사전 — static bool IsPropertyDirty(...)
• static bool = bool은 참/거짓을 돌려주는 값. 이 함수는 "비교해야 해?"에 대해 예/아니오로 답한다.
• const int32 ParentIndex = ParentIndex는 지금 검사 중인 프로퍼티 번호. const라서 함수 안에서 이 번호를 바꾸지 않아.
• & SharedParams / & StackParams = 큰 정보 묶음을 복사하지 않고 원본을 빌려서 본다는 표시.
• return = 아래 조건 계산 결과를 함수의 답으로 돌려준다.
• || = OR. 왼쪽부터 보다가 하나라도 참이면 전체가 참이야. "하나라도 걸리면 비교해라"라는 뜻.
• !(*SharedParams.PushModelProperties)[ParentIndex] = !는 반대, *는 포인터가 가리키는 진짜 물건을 꺼내 보기, [ParentIndex]는 그 번호 칸 보기. 합치면 "이 프로퍼티가 push 모델이 아니면".
• -> = 포인터가 가리키는 대상에게 기능을 시키는 화살표. PushModelState->IsPropertyDirty(...)는 dirty 비트가 켜졌는지 묻는 거야.
• && = AND. 양쪽이 모두 참일 때만 참.
• | = 비트 OR. 여기서는 두 플래그(HasObjectProperties, IsNetSerialize)를 한 묶음으로 합쳐서 검사할 때 써.
🔁 이제 다시 보자. IsPropertyDirty는 네 갈래 중 하나라도 맞으면 true를 돌려줘. 강제 비교면 보고, push가 아닌 프로퍼티면 항상 보고, push 프로퍼티라면 PushModelState->IsPropertyDirty(ParentIndex)가 켜졌을 때만 본다. 그래서 손 안 든 push 프로퍼티는 memcmp까지 가지 않고 건너뛰어.

읽는 법 — OR로 묶인 이 조건 중 하나라도 참이면 "비교해라":

  1. bForceCompareProperties — 강제 비교 모드(디버그/특정 상황)면 무조건.
  2. !(*PushModelProperties)[ParentIndex] — push 모델을 안 쓰는 프로퍼티는 항상 dirty 취급. (신고 안 하는 놈이니 서버가 대신 매번 봐줘야 함.)
  3. PushModelState->IsPropertyDirty(ParentIndex) — push 프로퍼티는 오직 이것뿐. dirty 비트가 꺼져 있으면 false → 비교(memcmp) 통째로 스킵. 이게 절약의 핵심.
  4. 마지막 줄 — 방금 GC가 돌았고 오브젝트 참조/NetSerialize 프로퍼티면 안전하게 다시 봐(dangling 방지).

3번이 이 시스템의 존재 이유야. push 프로퍼티는 "누가 손 안 들었으면 안 본다."

한발 더 — 클래스 전체가 모든 프로퍼티를 push로 커버하면(FullPushProperties), 프로퍼티를 하나씩 돌며 묻지도 않아. 켜진 비트만 이터레이트해. RepLayout.cpp:1614:

// If we have full push model property support, then we only need to check properties that are actually dirty. else if (EnumHasAnyFlags(SharedParams.Flags, ERepLayoutFlags::FullPushProperties) && !bRecentlyCollectedGarbage) { UE_LOG(LogRepCompares, VeryVerbose, TEXT("CompareParentProperties: Full push properties: Has Dirty: %d"), !!SharedParams.PushModelState->HasDirtyProperties()); for (TConstSetBitIterator<> It = SharedParams.PushModelState->GetDirtyProperties(); It; ++It) { CompareParentPropertyHelper(It.GetIndex(), SharedParams, StackParams); } }
🔤 기호 사전 — else if (...) { for (...) ... }
• else if = 앞 조건이 아니었을 때, 이번 조건을 한 번 더 검사한다는 뜻.
• EnumHasAnyFlags(...) = 플래그 묶음 안에 원하는 표시가 하나라도 켜져 있나 확인하는 함수.
• ERepLayoutFlags::FullPushProperties = ERepLayoutFlags라는 보기 묶음 안의 FullPushProperties 값. ::는 "~안의"라고 읽어.
• && !bRecentlyCollectedGarbage = 방금 GC가 돈 상황이 아닐 때만 이 빠른 길을 탄다. &&는 둘 다 참, !는 반대.
• UE_LOG(..., VeryVerbose, TEXT(...), !!...) = 아주 자세한 로그를 찍는 호출. !!는 어떤 값을 확실한 참/거짓 모양으로 바꿔 로그에 넣으려는 작은 트릭이야.
• TConstSetBitIterator<> = 켜진 비트만 찾아다니는 반복자. <>는 C++ 템플릿 표시라서 "이런 종류의 도구"라고 보면 돼.
• for (...; It; ++It) = It가 유효한 동안 반복하고, 매번 ++It로 다음 켜진 비트로 넘어가.
• It.GetIndex() = 지금 이터레이터가 가리키는 dirty 비트의 번호를 꺼내는 호출.
🔁 이제 다시 보자. 이 블록은 "이 클래스가 전부 push 프로퍼티이고, 방금 GC 예외 상황도 아니면, 전체 프로퍼티를 돌지 말고 켜진 비트만 돌자"는 빠른 길이야. TConstSetBitIterator가 1인 칸만 찾아서 CompareParentPropertyHelper(It.GetIndex(), ...)에 넘긴다.

GetDirtyProperties()가 주는 set-bit 이터레이터 — 1인 비트만 건너뛰며 방문. 프로퍼티 총 개수는 아예 루프에 안 들어와. 폴링의 "every property" 루프가 여기서 사라진다.

비교 다 끝나면? 넷드라이버 dirty 비트를 클리어해서 다음 라운드를 준비해(ResetDirtyStates() — RepLayout.cpp:1636 → PushModelPerNetDriverState.h:40). 켜고(mark) → 골라 비교하고(compare) → 끄고(reset). 이 삼박자가 한 사이클.

전체 소비측 흐름:

비교 직전 GetPerNetDriverState(Handle) PushModel.cpp:301 | +-(반환 전에) PushDirtyStateToNetDrivers() <- lazy flush v CompareParentProperties(...) RepLayout.cpp:1514 | +- FullPushProperties? -> GetDirtyProperties() 로 켜진 비트만 순회 RepLayout.cpp:1614 | +- 아니면 프로퍼티마다 -> IsPropertyDirty(ParentIndex) RepLayout.cpp:1499 | push 프로퍼티 & dirty=false -> memcmp 스킵 v ResetDirtyStates() <- 다음 라운드 위해 비트 클리어 PushModelPerNetDriverState.h:40

5. 우리 서버 비교: IOCP 워커 vs 싱글스레드 액터

우리 조선협객전 서버 감각으로 번역해볼게.

우리 서버의 폴링스러운 부분 — 예를 들어 매 틱 캐릭터 상태를 훑어서 주변에 뿌릴지 판단하는 루프가 있다고 치면, "전부 순회하며 바뀐 놈 찾기"는 폴링이야. Push Model은 이걸 "값 바꾼 코드가 dirty 큐에 넣기"로 바꾸는 것과 같아.

스레드 모델 차이가 핵심 주의점이야:

  • 우리 서버: IOCP 워커 여러 개가 패킷을 병렬 처리 → 공유 상태 바꿀 땐 락/원자성 신경 써야 함.
  • UE Push Model의 MarkPropertyDirty는 게임 스레드 싱글스레드 전제. 비트 세팅 두 줄에 락이 없는 이유가 이거야. 만약 우리처럼 IOCP 워커가 여기 손대면 DirtiedThisFrame[RepIndex] = true는 데이터 레이스가 돼.

그래서 교훈: "바뀔 때 dirty 마킹" 패턴 자체는 우리도 도입 가능하지만, 우리 환경에선 마킹 지점이 IOCP 워커 경계를 넘나드는지부터 봐야 해. UE가 락 없이 두 줄로 끝낼 수 있는 건 싱글스레드라는 강한 전제 덕분이지, 마법이 아니야.

그리고 UE의 2층 구조(글로벌↔넷드라이버별)는 우리로 치면 "공용 dirty 큐 하나 → 리플레이/샤드별로 소비 분리" 하는 것과 닮았어. 생산은 한 곳, 소비는 여러 곳.

6. 함정 세 개 (소스가 직접 경고함)

Push Model은 공짜가 아니야. "손 안 들면 안 본다"는 규칙이 곧 함정이 돼.

  1. 스위치 두 개 다 켜야 함. 컴파일 스위치 WITH_PUSH_MODEL + 런타임 CVar Net.IsPushModelEnabled. 근데 이 CVar 기본값이 false(PushModel.cpp:434). 안 켜면 있어도 안 돈다.
  1. 마킹 없이 값 바꾸면 영영 전송 안 됨. push 프로퍼티의 참조/포인터를 밖으로 들고 나가서 dirty 마킹 없이 값을 바꾸면? 아무도 손 안 들었으니 서버는 비교조차 안 하고 넘어가. 변경이 조용히 유실돼. 소스가 강한 경고로 못 박아둠(PushModel.h:199-214). (우리 서버에서 "저장했는데 클라에 반영 안 됨" 류 사고의 UE판이 딱 이거야.)
  1. 최상위 프로퍼티 단위로만 추적. 구조체·컨테이너 내부를 찔끔 바꿔도, 그 값을 담은 최상위 프로퍼티를 통째로 dirty 마킹해야 해(PushModel.h:107-115). "배열 3번 원소만 바꿨어요"를 세밀하게 추적 못 함 — 배열 프로퍼티 전체가 dirty.

마지막으로 솔직한 한 줄. 헤더 주석 스스로 이렇게 적어뒀어: "이론적 이득은 좋으나 실측 이득은 기대만큼 안 나왔다"(PushModel.h:16-18). 폴링을 없앤 대신 마킹 규율이라는 부채를 졌고, 그 손익은 프로젝트마다 다르다는 정직한 고백이야. 최적화는 언제나 트레이드오프.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. Push Model, 왜 필요한가요?

답 보기
전통적 복제(폴링/비교)는 매 프레임 모든 액터의 모든 프로퍼티를 그림자랑 하나하나 비교해서 바뀐 걸 찾아. 정직하지만 비싸. 액터 10만 개 × 프로퍼티 30개인데 이번에 바뀐 건 5개뿐이면, 그 5개 찾으려고 300만 번을 비교해. 안 바뀐 걸 확인하려고 안 바뀐 값까지 전부 만지는 헛수고야. Push Model은 이걸 뒤집어 — 서버가 묻지 말고, 값 바꾼 코드가 직접 "나 바뀌었어요" 손들게 하자. 전교생 하나씩 부르는 대신 숙제 낸 애만 손드는 거지.

↳ "손드는" 게 실제로 얼마나 하는 일인가요?

답 보기
놀랄 만큼 단순해. 프로퍼티마다 비트 하나를 두고, 값 바꾸면 그 비트를 1로 켜고 "이 오브젝트에 dirty 있음" 깃발 세우는 게 전부야. 딱 두 줄. 매 프레임 비교하는 코드는 어디에도 없어. 그래서 비용이 바꾼 횟수에 비례하지 프로퍼티 총 개수에 비례하지 않아. 5개 바꿨으면 함수 5번. 300만이 5가 되는 거야.

Q2. dirty 상태를 왜 글로벌이랑 넷드라이버별, 두 층으로 나눴나요?

답 보기
서버 하나에 넷드라이버가 여러 개일 수 있거든(게임용 + 리플레이 녹화용 등). 값 바꿀 때마다 곧바로 모든 넷드라이버에 복사하면, 정작 relevancy·dormancy로 이번에 안 보낼 놈들 상태까지 부지런히 갱신하는 헛수고가 돼. 그래서 게임 코드는 글로벌 한 곳에만 쌓고, 진짜 보내기 직전에만 각 넷드라이버로 몰아 넣어. 생산은 한 곳, 소비는 필요할 때 여러 곳.

↳ "보내기 직전에만"이라는 게 lazy flush죠? 왜 미루나요?

답 보기
복제 후보 액터 중 실제로 이번에 보내는 건 극히 일부야. 대부분은 relevancy·dormancy로 이번 프레임엔 안 보내. 그런데 값 바꿀 때마다 넷드라이버 전부에 미리 복사해두면 결국 안 보낼 놈들까지 갱신하는 낭비지. 그래서 필요한 순간까지 미뤘다가, 비교 직전에 글로벌 dirty를 각 넷드라이버로 OR 연산으로 밀어넣고 글로벌은 리셋해. OR로 넣는 건 지난번에 아직 처리 못 한 dirty를 덮어쓰지 않고 합치려는 거야.

Q3. 소비측에서 dirty 비트를 어떻게 활용하나요?

답 보기
비교하려는 순간 "얘 비교해야 해?"를 물어. push 프로퍼티인데 dirty 비트가 꺼져 있으면 → 비교(memcmp) 통째로 스킵. 손 안 들었으면 안 보는 거야. 이게 절약의 핵심이지. 클래스 전체가 모든 프로퍼티를 push로 커버하면 아예 프로퍼티를 하나씩 돌지도 않고, 켜진 비트만 이터레이트해. 폴링의 "every property" 루프가 여기서 사라져. 켜고(mark) → 골라 비교하고(compare) → 끄고(reset), 이 삼박자가 한 사이클.

↳ push를 안 쓰는 프로퍼티가 섞여 있으면요?

답 보기
push 안 쓰는 프로퍼티는 항상 dirty 취급해서 매번 비교해. 신고를 안 하는 놈이니까 서버가 대신 봐줘야 하거든. 그래서 판정 조건이 OR로 묶여 있어 — 강제 비교 모드거나, push 아닌 프로퍼티거나, push인데 dirty 비트가 켜졌거나 중 하나라도 맞으면 비교해. push 프로퍼티만 "손 안 들면 안 본다"의 혜택을 받는 거지.

Q4. Push Model은 공짜인가요? 함정은요?

답 보기
공짜 아니야. "손 안 들면 안 본다"는 규칙이 곧 함정이 돼. 제일 무서운 건 — push 프로퍼티 값을 dirty 마킹 없이 바꾸면 아무도 손 안 들었으니 서버가 비교조차 안 하고, 변경이 조용히 유실돼. 에러도 안 나. 우리 서버 "저장했는데 클라에 반영 안 됨" 사고의 UE판이지. 게다가 최상위 프로퍼티 단위로만 추적해서 배열 3번 원소만 바꿔도 배열 전체를 dirty 마킹해야 해. 심지어 헤더 주석이 "이론적 이득은 좋으나 실측 이득은 기대만큼 안 나왔다"고 스스로 고백해. 최적화는 언제나 트레이드오프야.

↳ 우리 조선 서버(IOCP)에도 이 dirty 마킹 패턴을 그대로 쓸 수 있나요?

답 보기
패턴 자체는 도입 가능하지만 스레드 모델을 먼저 봐야 해. UE의 MarkPropertyDirty가 락 없이 비트 두 줄로 끝나는 건 게임 스레드 싱글스레드라는 강한 전제 덕분이야. 우리처럼 IOCP 워커 여러 개가 여기 손대면 DirtiedThisFrame[RepIndex] = true가 데이터 레이스가 돼. 그러니 마킹 지점이 워커 경계를 넘나드는지부터 확인해야지. UE가 두 줄로 끝내는 건 마법이 아니라 전제 덕분이라는 걸 잊으면 안 돼.

🎯 원리 한 줄 요약

폴링은 "안 바뀐 걸 확인하려 전부 비교"하고, Push Model은 "값 바꾼 코드가 dirty 비트 하나 켜서" 서버가 켜진 비트만 보게 만든다 — 비용이 프로퍼티 개수가 아니라 변경 횟수에 비례한다.

  • 막히면 → replayout (RepLayout이 프로퍼티를 어떻게 펼치는지), changelist (바뀐 것만 모으는 상위 개념)
  • 다음 → rep-conditions (조건부 리플리케이션 — 누구에게 보낼지), iris (차세대 리플리케이션에서 push가 어떻게 진화하는지)
