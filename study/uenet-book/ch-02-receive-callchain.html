패킷이 도착하면: 수신 콜체인

언리얼 네트워크 · 02 / 43

왜 이걸 배워? — 문제의식부터

게임 서버를 짜봤으면 이 장면을 이미 알아. IOCP 워커가 GQCS에서 완료 통지를 받고, 버퍼에 바이트가 들어왔고, 이제 SP_*든 CM_*든 뭔가 처리해야 해. 그런데 소켓이 준 건 친절한 "스킬 사용 패킷"이 아니라 그냥 바이트 덩어리야.

여기서 길을 잘못 잡으면 바로 사고가 나. 워커 스레드가 받은 바이트를 대충 CChosunPlayer에 던졌는데 패킷이 반쪽만 왔거나, 헤더 길이가 틀렸거나, 순서가 꼬였거나, 아직 복호화도 안 됐다고 해보자. 그러면 엉뚱한 CM_ 핸들러가 열리고, 잘못된 플레이어 상태를 만지고, 락을 잡은 채 게임 로직까지 들어가다가 서버가 멈칫한다.

그래서 보통 우리는 단계를 나눠. 먼저 바이트를 안전하게 풀고, 패킷 경계를 확인하고, 어떤 메시지인지 고르고, 마지막에 단일스레드 게임 로직 큐로 넘긴다. 초딩식으로 말하면 택배 상자를 받자마자 장난감을 꺼내 휘두르는 게 아니라, 포장 뜯고, 송장 보고, 방별로 분류해서 배달하는 거야.

언리얼도 같은 문제를 만났고, 그 답이 이 챕터의 수신 콜체인이야. ReceivedRawPacket이 날바이트를 받고, ReceivedPacket이 순서와 ack를 보고, DispatchPacket이 Bunch를 채널로 배달한다. 우리 서버의 "recv 완료 → 헤더 파싱 → SP_*/CM_* 디스패치"와 같은 자리라고 보면 된다.

이걸 지금 배우는 이유도 분명해. 1장에서 UNetConnection이 클라 한 명을 책임지는 그릇이라는 걸 봤지. 이제 그 그릇 안으로 처음 데이터가 들어오는 길을 봐야 다음의 채널, reliable 재전송, 복제, RPC가 어디서 시작되는지 이해된다. 입구를 모르고 집 안 구조를 외우면, 나중에 버그가 났을 때 "패킷이 어디서 사라졌는지"를 못 찾는다.

0. 들어가기 전에: "택배가 문 앞에 왔다"

우리 서버 짜본 사람은 recv()가 뭘 주는지 알잖아. 그냥 바이트 덩어리 하나 던져줘. char buf[N]에 몇 바이트 들어왔다, 끝. 그 안에 뭐가 들었는지, 어디까지가 한 패킷인지, 순서가 맞는지 — 그건 다 네가 풀어야 해.

UE도 정확히 여기서 시작해. 소켓 드라이버가 바이트 덩어리를 툭 던지고 사라져. 그 다음부터가 이 챕터야.

비유를 하나 깔자. 문 앞에 택배 상자가 도착했어.

  1. 상자를 받는다 (누가 보냈는지 아직 모름) → 날바이트 수신
  2. 포장 테이프를 뜯는다 (암호화 풀기) → 핸들러 통과
  3. 상자 안에 송장 번호가 있다 (몇 번째 택배냐, 앞에 빠진 거 없냐) → 시퀀스/ack
  4. 상자 안에 작은 봉투가 여러 개 들어있다 → 각 봉투를 담당 부서로 배달 → Bunch 디스패치

이 4단계를 실제로 구현하는 게 NetConnection.cpp의 세 함수야: ReceivedRawPacket → ReceivedPacket → DispatchPacket.

이번 챕터 목표는 하나. 날바이트가 어떻게 채널까지 배달되는가, 그 콜체인의 뼈대와 "왜" 만 머리에 넣는 거야. 라인 하나하나 다 안 봐. 계단 세 개만.

1. 전체 지도: 세 함수, 세 관문

먼저 큰 그림. 세 함수가 각자 딱 한 가지 관문만 지켜.

함수 (줄번호)관문한 줄
ReceivedRawPacket(2056)날바이트 → 비트리더포장 뜯고 비트 단위로 읽을 준비
ReceivedPacket(3143)시퀀스/ack몇 번째 패킷이냐, 순서 맞냐 판정
DispatchPacket(3496)Bunch 분해패킷 하나를 봉투 여러 개로 쪼개 채널 배달

핵심 감각: 한 함수 = 한 책임. 바이트를 만지는 놈, 순서를 따지는 놈, 쪼개는 놈이 따로야. 우리 서버로 치면 "recv 콜백 → 패킷헤더 파싱 → 핸들러 디스패치"를 세 함수로 칼같이 나눠둔 거지.

지금부터 진짜 코드가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 통째로 외우는 게 아니라 "아, 이게 이거구나"만 잡으면 돼.

🌱 이 개념은 왜 생겼나 — 터미네이터 비트
• 원래 구조: 택배 상자를 받으면 보통 "몇 바이트짜리다"를 믿고 그만큼 읽으면 돼. 바이트 단위로 딱딱 떨어지니까 편하지.
• 그런데 문제: 근데 UE는 대역폭을 아끼려고 bool 하나를 1비트로 욱여넣어. 그럼 진짜 데이터가 "N바이트"가 아니라 "N비트"에서 끝나는데, 소켓은 바이트 단위로만 보내니까 마지막 바이트의 남는 자리는 쓰레기 비트로 채워져. "어디까지가 진짜 편지고 어디부터가 포장 완충재냐"를 알 수가 없어.
• 그래서 필요한 것: 진짜 데이터 맨 끝에 1을 딱 하나 박아 "여기가 끝!" 하고 표시를 남기는 거야. 이 끝표시 비트가 터미네이터 비트. 받는 쪽은 마지막 바이트에서 제일 높은 1을 찾으면 거기가 진짜 끝이지.

2. 1층: ReceivedRawPacket — 포장 뜯기

UNetConnection::ReceivedRawPacket(void* InData, int32 Count) — 여기가 최초 진입점이야. 드라이버가 InData(바이트 포인터)랑 Count(바이트 수)만 던지고 끝. 아무 해석도 안 된 날것.

2-1. 먼저 테이프를 뜯는다 (핸들러)

들어온 바이트는 아직 암호화/인코딩된 상태일 수 있어. 그래서 제일 먼저 PacketHandler 파이프라인에 통과시켜.

NetConnection.cpp:2084~2094

if (Handler.IsValid()) { FReceivedPacketView PacketView; PacketView.DataView = {Data, Count, ECountUnits::Bytes}; EIncomingResult IncomingResult = Handler->Incoming(PacketView); if (IncomingResult == EIncomingResult::Success) { Count = PacketView.DataView.NumBytes();
🔤 기호 풀이
• Handler.IsValid() = "핸들러(암호화·압축 담당)가 준비돼 있나?" 확인. 있을 때만 통과시켜.
• -> = 화살표는 "그 놈의 것을 꺼내/시켜". Handler->Incoming() = 핸들러한테 "들어온 거 처리해" 시키기.
• EIncomingResult = 처리 결과를 담는 값. 앞의 E는 보통 "정해진 보기 중 하나"(enum)라는 신호 — 여기선 성공/실패 같은.
• == EIncomingResult::Success = "결과가 성공과 같으면". ==는 "같다", ::Success는 그 보기 중 '성공'.

Handler->Incoming()이 복호화·디코드를 해서 PacketView에 다시 담아줘. 성공하면 Count를 복호화 후 크기로 갱신해(2094). 실패하면? 위에서 안 보였지만 폴트리커버리 시도하고, 안 되면 Close로 연결을 끊어. 즉 의심스러운 바이트는 여기서 컷. (핸들러 내부가 궁금하면 → packethandler)

2-2. 여기서 첫 함정: "실제 비트 길이"를 어떻게 알아?

자, 예측 한번 해보자. 복호화 끝났으면 Count 바이트를 그냥 읽으면 될 것 같지? 맞춰봐.

...아니야. 여기 UE만의 함정이 있어.

UE는 bool 하나를 1비트로 패킹해. 8개 넣어도 1바이트야. 그러니 진짜 데이터는 "N바이트"가 아니라 "N비트"에서 끝나. 근데 소켓은 바이트 단위로만 전송하니까, 마지막 바이트의 남는 자리는 쓰레기 비트로 채워져.

그럼 "여기까지가 진짜다"를 어떻게 표시할까? 터미네이터 비트 하나를 세워둬. 마지막 유효 비트 바로 다음에 1을 딱 하나 박고, 그 뒤는 0. 받는 쪽은 마지막 바이트에서 제일 높은 1비트를 찾으면 거기가 끝이야.

NetConnection.cpp:2161~2175

uint8 LastByte = Data[Count-1]; if (LastByte != 0) { int32 BitSize = (Count * 8) - 1; // Bit streaming, starts at the Least Significant Bit, and ends at the MSB. while (!(LastByte & 0x80)) { LastByte *= 2; BitSize--; } FBitReader Reader(Data, BitSize);
🔤 비트 만지는 코드 풀이 — 여기가 이 챕터에서 제일 낯설어. 천천히.
• uint8 LastByte = Data[Count-1] = Data(바이트들이 늘어선 배열)에서 맨 마지막 칸(Count-1번째)을 꺼내 LastByte에 담아. uint8=0~255를 담는 한 바이트. 대괄호 [..]는 "몇 번째 칸".
• 0x80 = 16진수. 2진수로는 1000 0000 = 맨 왼쪽(최상위) 비트 하나만 1. "제일 높은 자리"를 콕 집는 마스크야.
• LastByte & 0x80 = 비트 AND. "맨 왼쪽 비트가 켜져 있나?"만 뽑아봐. 앞에 !(...)니까 "아직 안 켜졌으면" 계속 돌아.
• LastByte *= 2 = 2를 곱하면 2진수로는 왼쪽으로 한 칸 밀기. 다음 비트를 맨 왼쪽 자리로 끌어와 검사하려는 거야.
• 정리: 이 while은 왼쪽으로 밀며 첫 1(터미네이터)을 찾을 때까지 길이를 깎는 반복이야.

읽어보면: 일단 전체 비트 수에서 1 뺀 값으로 시작(Count*8 - 1). 마지막 바이트를 왼쪽으로 밀면서(*= 2) 최상위 비트가 1이 될 때까지 BitSize를 깎아. 그 1이 바로 터미네이터고, 그게 진짜 끝이야. 그렇게 구한 BitSize로 FBitReader를 만들어 — 이제부터 비트 단위로 읽는 리더가 준비된 거지.

🔁 이제 다시 보자. 이 코드 = "마지막 바이트에서 제일 왼쪽에 켜진 1을 찾아 → 거기가 진짜 끝 → 그 길이로 비트 리더를 만든다." 처음엔 & 0x80, *= 2가 암호였는데, 이제 '끝 표시(터미네이터) 찾기'로 읽히지?
LastByte == 0이면? 마지막 바이트가 통째로 0이라는 건 터미네이터 비트조차 없다는 뜻 = 손상된 패킷. 아래 else에서 MalformedPacket로 처리하고 버려.

2-3. 다음 계단으로

NetConnection.cpp:2185~2191

if (Reader.GetBitsLeft() > 0) { ReceivedPacket(Reader); // Check if the out of order packet cache needs flushing FlushPacketOrderCache(); }

Reader(비트리더)를 다음 함수 ReceivedPacket에 넘겨. 1층 끝. 바로 뒤 FlushPacketOrderCache()는 잠깐 접어둬 — 3층에서 "순서 어긋난 패킷 캐시" 얘기할 때 다시 나와.

1층 요약: 날바이트 → (복호화) → 터미네이터로 진짜 길이 역산 → FBitReader로 래핑 → 넘김.

🌱 이 개념은 왜 생겼나 — 시퀀스 번호·ack
• 원래 구조: 택배(패킷)를 그냥 오는 대로 열어 처리하면 될 것 같지? TCP를 쓰면 커널이 순서를 맞춰줘서 실제로 우리 서버는 이 고민을 잘 안 해.
• 그런데 문제: UE는 UDP 위라 커널이 안 도와줘. 그럼 3번 택배가 2번보다 먼저 오거나, 2번이 아예 안 오거나, 같은 택배가 두 번 오기도 해. 순서 뒤바뀐 걸 그냥 처리하면 "장착"이 "아이템 지급"보다 먼저 실행되는 사고가 나.
• 그래서 필요한 것: 택배마다 송장 번호(시퀀스)를 붙이고, 받은 쪽이 "어디까지 잘 받았다"(ack)를 알려주는 약속. 번호를 보고 "빵꾸 났으면 잠깐 보관, 옛날 거면 버림"을 판정하고, ack로 상대가 "재전송할지"를 정해. TCP가 공짜로 해주던 걸 UE는 이 번호표로 손수 하는 거야.

3. 2층: ReceivedPacket — "몇 번째 택배냐"

UNetConnection::ReceivedPacket(FBitReader& Reader, ...)(3143). 이 층의 관심사는 딱 하나. 순서와 신뢰성. UDP는 순서 보장이 없어. 3번 택배가 2번보다 먼저 올 수도, 2번이 아예 안 올 수도 있어. 그걸 여기서 정리해.

3-1. 송장 번호부터 읽는다

NetConnection.cpp:3202~3210

FNetPacketNotify::FNotificationHeader Header; if (!PacketNotify.ReadHeader(Header, Reader)) { UE_LOG(LogNet, Warning, TEXT("Failed to read PacketHeader")); HandleNetResultOrClose(ENetCloseResult::ReadHeaderFail); return; }
🔤 기호 풀이
• FNetPacketNotify::FNotificationHeader Header; = 시퀀스 헤더를 담을 빈 상자(Header) 하나 준비. F로 시작하면 보통 UE의 값 묶음(구조체).
• if (!PacketNotify.ReadHeader(...)) = 헤더를 읽어보고, !(못 읽었으면) 안으로 들어가 경고 찍고 return(함수 즉시 종료). !는 "아니면/실패면".
• UE_LOG(LogNet, Warning, ...) = 네트워크 로그에 경고 한 줄. (여긴 Fatal 아니라 Warning — 게임을 죽이진 않고 이 연결만 정리해.)

패킷 맨 앞에는 시퀀스 헤더가 붙어있어(송장 번호 + 상대가 어디까지 받았다는 ack 정보). PacketNotify.ReadHeader가 그걸 읽어. 못 읽으면 = 헤더가 깨졌다 = 신뢰 불가 → ReadHeaderFail로 연결 정리하고 리턴. 깨진 송장은 상자 안 열어봐.

3-2. 순서 판정: 갭이면 잠깐 보관, 옛날 거면 버림

헤더를 읽었으면 PacketNotify.GetSequenceDelta(Header)(3247)로 기대값과의 간격을 계산해. 세 갈래야:

  • delta == 1 (딱 다음 번호): 정상. 그대로 진행.
  • delta > 1 (중간에 빵꾸): 앞 패킷이 아직 안 왔다 → 이 패킷을 out-of-order 캐시에 보관(:3260~). 나중에 빈 자리가 채워지면 1층 끝의 FlushPacketOrderCache()가 순서대로 꺼내 처리해. (이래서 그게 1층 끝에 있었어.)
  • 이미 처리한 옛날 번호: 리플레이(중복 재전송)일 수 있으니 그냥 리턴(:3381). 같은 택배 두 번 처리 안 해.

정상 흐름이면 ReadPacketInfo(3385)로 ack 등 헤더 부가정보까지 읽고, 다음으로 넘어가. (시퀀스/ack의 자세한 원리는 → reliability-ack)

3-3. 상자 열기 + 확인/거부 통보

else { PacketNotify.AckSeq(InPacketId);
🔤 기호 풀이 — if (bDispatchPacket) DispatchPacket(...) / else ... AckSeq(...)
• bDispatchPacket = b로 시작하면 보통 참/거짓 스위치(bool). "이 패킷을 열어서 배달할까?" 값.
• AckSeq / NakSeq = 상대에게 보내는 신호. Ack="잘 받았어", Nak="못 받았어(다시 보내)". Seq=몇 번 패킷인지.

순서·검증 다 통과했으면 DispatchPacket으로 넘겨 상자를 연다(3층). 그리고 이 패킷을 어떻게 처리했는지 송신측에 알려줘 — 잘 받았으면 AckSeq(확인), 버릴 거면 NakSeq(거부, :3457). 이 신호로 상대가 "재전송할지 말지"를 정해.

DispatchPacket이 bSkipAck/bHasBunchErrors를 참조로 돌려줘. 상자 속 봉투 하나라도 썩었으면 여기로 그 사실이 올라와서, ack 안 하거나(재전송 유도) 연결을 닫는 판단에 쓰여.

2층 요약: 송장 읽기 → 순서 판정(갭=보관 / 옛날=버림 / 정상=진행) → 상자 열기 → ack/nak 통보.

4. 3층: DispatchPacket — 봉투를 부서로

UNetConnection::DispatchPacket(FBitReader& Reader, int32 PacketId, ...)(3496). 여기가 마지막 계단. 패킷 하나 안에 Bunch 여러 개가 들어있어 (한 UDP 패킷 = 여러 봉투 묶음). 그걸 하나씩 꺼내.

핵심은 while(!Reader.AtEnd()) 루프(:3511~). 리더가 끝날 때까지:

  1. FInBunch Bunch(this) 만들고 bControl/bOpen/bClose/bReliable/ChIndex 같은 Bunch 헤더를 읽어(:3525~3568). 이걸로 "이 봉투가 어느 채널(ChIndex) 거고, 채널을 새로 여는지/닫는지, 신뢰성 봉투인지" 판별.
  2. 해당 채널이 없으면 CreateChannelByName(...)(4031)으로 만들어.
  3. 채널에 배달:

NetConnection.cpp:4059~4066

// Dispatch the raw, unsequenced bunch to the channel. bool bLocalSkipAck = false; if (Channel != nullptr) { // Warning: May destroy channel Channel->ReceivedRawBunch(Bunch, bLocalSkipAck); }
🔤 기호 풀이
• while(!Reader.AtEnd()) = "리더가 끝에 안 닿은 동안 반복". 패킷 안 봉투(Bunch)를 하나씩 다 꺼낼 때까지 돌아.
• FInBunch Bunch(this) = 봉투 하나(Bunch)를 만들어. this=지금 이 연결, In=수신용.
• Channel != nullptr = "채널이 비어있지 않으면". nullptr=아무것도 안 가리킴(빈 것). 채널이 있어야 배달하지.
• Channel->ReceivedRawBunch(Bunch, ...) = 그 채널한테 "이 봉투 받아" 시키기.

Channel->ReceivedRawBunch(Bunch, ...) — 여기가 이 챕터의 종착역. 이 줄을 넘어가면 더는 "연결(Connection) 계층"이 아니라 채널 계층이야. 액터 복제, 컨트롤 메시지 같은 논리적 스트림 처리가 거기서 시작돼. (// Warning: May destroy channel 주석 보이지? 배달 도중 채널이 스스로 닫힐 수 있어서 조심하라는 거야.)

🔁 다시 보자. while(!Reader.AtEnd()) { ... Channel->ReceivedRawBunch(Bunch) } = "패킷 안 봉투를 끝까지 하나씩 꺼내 각 채널에 배달". 세 함수 릴레이(바이트→순서→분해)의 진짜 끝이 이 한 줄이야.
Bunch 하나가 채널 안에서 어떻게 조립되고 순서 맞춰지는지는 → datachannel-nextbunch
"패킷 vs Bunch"가 아직 헷갈리면 → bunch-vs-packet

3층 요약: while 돌며 Bunch 헤더 읽고 → 채널 찾거나 만들고 → ReceivedRawBunch로 배달. 끝.

6. 우리 서버랑 비교: IOCP 워커 vs UE

우리 조선 서버는 IOCP 워커 스레드가 여러 개 돌잖아. GQCS로 완료 통지 받으면 워커가 그 소켓의 수신 버퍼를 집어서 패킷 파싱하고 핸들러 태우지. 워커가 N개니까 여러 연결이 동시에 처리돼. 대신 공유 자원(인벤/재화)은 락으로 지켜야 하고 — 이게 우리가 복제 사고를 조심하는 이유고.

UE의 이 콜체인은 결이 달라. ReceivedRawPacket은 보통 게임 스레드(넷드라이버 Tick)에서 순차로 불려. 소켓에서 바이트를 긁어오는 건 별개지만, 위 세 함수 → 채널 → 액터 복제까지는 한 줄로 흘러가. 즉 우리로 치면 "싱글스레드 액터 모델"에 가까워. Bunch가 액터 상태를 건드릴 때 락이 필요 없어 — 어차피 한 스레드가 순서대로 처리하니까.

한 줄 대비: IOCP는 "동시에 여러 손님"이라 락으로 지키고, UE 수신은 "한 줄로 한 명씩"이라 순서로 지켜. 트레이드오프 — UE 방식은 락 지옥이 없는 대신 그 한 스레드가 병목이 되면 전체가 느려져(그래서 넷드라이버 Tick 최적화가 중요해 → netdriver-tick).

7. 자주 넘어지는 포인트 (짧게)

  • 왜 비트 단위(FBitReader)냐? bool 하나를 1비트로 아끼려고. 대역폭이 목숨인 실시간 게임이라 비트까지 짠다. 대신 "진짜 끝"을 표시할 터미네이터 비트가 필요해진 거고.
  • 패킷 = Bunch 아니다. 패킷은 UDP 한 방(상자), Bunch는 그 안의 논리 단위(봉투). 1:N. 헷갈리면 → bunch-vs-packet
  • ack는 여기서 안 재전송해. ReceivedPacket은 "받았다/거부한다" 신호만 보내(AckSeq/NakSeq). 실제 재전송 결정은 송신측 몫 → reliability-ack
  • out-of-order 캐시가 1층 끝(FlushPacketOrderCache)과 2층(갭 감지)에 걸쳐 있어. 두 군데가 짝이야.

🎯 원리 한 줄 요약

소켓 날바이트 → (핸들러 복호화) → 터미네이터로 진짜 비트길이 찾아 FBitReader → 시퀀스/ack로 순서 판정 → 패킷을 Bunch들로 쪼개 채널에 배달 — 세 함수가 각자 한 관문(바이트/순서/분해)만 지키며 릴레이한다.
