Bunch가 뭐고 패킷과 뭐가 다른가

언리얼 네트워크 · 03 / 43

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "패킷 하나 안에 왜 여러 개가 들었고, 큰 놈은 어떻게 쪼개져 나가는지"가 손에 잡힐 거야.

왜 이걸 배워? — 문제의식부터

게임 서버를 만들어봤다면 보통 이렇게 생각하기 쉬워. IOCP 워커가 패킷을 하나 받고, 헤더의 wSize와 wID를 읽고, CM_* 요청을 찾아서 CChosunPlayer 같은 객체로 넘긴다. 그러면 게임 로직 쪽에서는 SP_* 응답을 만들어 보내고, 필요한 상태는 락으로 보호하거나 단일스레드 큐에 태워 순서대로 처리하지.

그 감각으로 UE 네트워크를 읽으면 처음에 바로 헷갈린다. "패킷 하나를 받았으면 메시지 하나를 처리하면 되는 거 아닌가?" 하고 보는데, UE는 패킷 하나 안에서 Bunch를 여러 개 꺼내기도 하고, 반대로 큰 Bunch 하나를 여러 패킷으로 쪼개 보내기도 한다. 봉투 하나에 편지가 여러 장 들어갈 수도 있고, 너무 긴 편지는 봉투 여러 개에 나눠 담길 수도 있는 셈이야.

이 구분이 없으면 문제가 터진다. 패킷 경계만 믿고 게임 메시지 경계를 판단하면, 아직 덜 도착한 반쪽 메시지를 완성품처럼 처리하거나, 한 패킷 안의 여러 메시지 중 뒤쪽을 놓칠 수 있다. 조선 서버 식으로 말하면 IOCP에서 받은 버퍼 하나를 곧바로 CM_ 하나라고 믿고 디스패치했는데, 실제로는 그 안에 여러 작업이 붙어 있거나 한 작업이 다음 버퍼까지 이어지는 상황이 생기는 거야.

그래서 이 챕터의 답이 Packet과 Bunch의 차이다. Packet은 네트워크가 들고 다니는 봉투에 가깝고, Bunch는 UE 채널이 주고받는 실제 일거리 조각에 가깝다. Packet은 ack나 전송 단위로 중요하고, Bunch는 "어느 채널의 어떤 메시지인가", "쪼개진 조각인가", "reliable 순서를 지켜야 하나"를 담는 단위다.

지금 이걸 배우는 이유도 흐름상 딱 여기라서 그래. 앞에서 UNetConnection이 연결 하나를 책임지는 큰 그림을 봤다면, 이제 그 연결 안을 실제 데이터가 어떻게 지나가는지 봐야 한다. 이 차이를 먼저 잡아야 뒤의 수신 체인, 송신 체인, reliable/ack, 채널 처리에서 "왜 이렇게 복잡하게 읽고 쓰는지"가 단순 암기가 아니라 문제 해결 구조로 보인다.

0. 먼저 비유부터 — 봉투와 편지

우체통에 넣는 봉투 하나를 생각해 봐. 봉투는 우체국이 다루는 단위야. 소인 찍고, 몇 번째로 부쳤는지 세고, 도착했는지 확인해주는 것도 전부 "봉투" 단위지.

근데 봉투 안에 든 편지는 봉투랑 다른 얘기야.

  • 짧은 편지 여러 통을 봉투 하나에 몰아 담을 수도 있고,
  • 편지 한 통이 너무 두꺼우면 여러 봉투에 나눠 넣어야 하지. (1편, 2편, 3편… 이렇게 쪼개서)

봉투 받는 사람은 봉투를 뜯어서 편지를 하나씩 꺼내 읽어. 나눠 온 편지면 1편·2편·3편을 순서대로 모아 다시 한 통으로 합쳐 읽고.

UE 네트워크가 정확히 이거야.

  • 봉투 = 패킷(Packet) — UDP 한 방으로 날아가는 데이터그램 1개. 시퀀스 번호 붙고, ack 대상이 되는 단위. (→ receive-callchain에서 봉투 뜯는 과정 다룸)
  • 편지 = Bunch — 채널 하나에 속한 논리적 메시지 1개. 봉투에 여러 통 담기고, 두꺼우면 여러 봉투로 쪼개진다.

그리고 이 봉투-편지 관계를 실제로 구현한 게 이번 챕터의 세 파일이야:

  • DataBunch.h — 편지(Bunch)가 어떻게 생겼나 (헤더 필드 정의)
  • DataChannel.cpp — 두꺼운 편지를 쪼개고(SendBunch), 받은 조각을 다시 합치는 곳
  • NetConnection.cpp — 편지 헤더를 비트로 쓰고(write), 봉투를 뜯어 편지를 하나씩 꺼내는(read) 곳

하나씩 밟자.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 코드를 외우는 게 아니라 "아, 이 줄이 봉투/편지를 이렇게 다루는구나"만 잡으면 돼.

🌱 이 개념은 왜 생겼나 — Bunch(편지)
• 원래 구조: 게임 서버 감각이면 패킷 하나 = 메시지 하나가 제일 자연스러워. 우리 서버가 wID 하나 읽고 CM_ 핸들러 하나 부르는 그 방식이지.
• 그런데 문제: 근데 이러면 낭비랑 한계가 생겨. ① 작은 메시지 수십 개를 보낼 때마다 패킷 헤더가 수십 번 붙어(대역폭 아까워). ② 반대로 큰 액터 스냅샷은 패킷 하나(MTU)에 안 들어가. ③ 게다가 "이건 꼭 순서 지켜야 하는 신뢰 메시지", "이건 어느 채널 소속"처럼 메시지마다 성격이 달라.
• 그래서 필요한 것: 네트워크가 나르는 봉투(패킷)와, 그 안에 담기는 논리 메시지(편지)를 따로 두는 거야. 작은 편지는 봉투 하나에 몰아 담고, 큰 편지는 봉투 여러 개로 쪼개고, 편지마다 "어느 채널·신뢰성"을 적어. 이 편지 단위가 Bunch야.

1. 관계부터 정확히 — 패킷 : Bunch는 1:N (양방향)

제일 먼저 머리에 박아야 할 그림이야. 헷갈리기 딱 좋은 지점이라 천천히 가자.

(가) 담기 — 패킷 1개 : Bunch N개

작은 Bunch들은 한 패킷 안에 연속으로 줄줄이 담겨. 받는 쪽은 패킷 하나를 받아서 이런 루프를 돌아 (NetConnection.cpp:3511):

while( !Reader.AtEnd() && GetConnectionState()!=USOCK_Closed )
🔤 기호 사전 — while( !Reader.AtEnd() && GetConnectionState()!=USOCK_Closed )
• while = 괄호 안 조건이 맞는 동안 계속 반복하라는 말. 봉투 안에서 편지가 다 떨어질 때까지 손을 넣는 느낌이야.
• !Reader.AtEnd() = Reader.AtEnd()는 "끝에 닿았니?"고, 앞의 !는 아니면. 즉 "아직 끝이 아니면".
• && = "둘 다 맞아야 함". 편지도 남아 있고, 연결도 살아 있어야 계속 돈다.
• GetConnectionState()!=USOCK_Closed = 연결 상태가 USOCK_Closed와 같지 않으면. !=는 "다르다"야.
• USOCK_Closed = 소켓 연결이 닫힌 상태 이름. 닫혔으면 더 읽을 봉투가 있어도 멈춰야 해.
🔁 이제 다시 보자. while(반복) → !Reader.AtEnd()(아직 끝 아님) → &&(그리고) → GetConnectionState()!=USOCK_Closed(연결도 안 닫힘). 이어 읽으면 "패킷 안에 읽을 것이 남아 있고 연결이 살아 있는 동안 Bunch를 계속 꺼낸다." 패킷 하나에 Bunch 여러 개가 들어갈 수 있다는 말이 코드로 보이지?

"봉투 안에 편지 남아있는 동안 계속 꺼내" — 딱 이 뜻이야. 패킷 하나 = Bunch 하나가 아니라는 게 우리 서버랑 제일 다른 점이야. (§6에서 비교)

(나) 쪼개기 — Bunch 1개 : 패킷 N개

반대로 Bunch 하나가 패킷보다 크면? 그 편지는 여러 조각(partial bunch)으로 잘려서 여러 패킷에 나눠 실려. 이걸 쪼개는 루프가 DataChannel.cpp:1371에 있어 (곧 볼 거야).

그러니까 관계는 양방향이야:

작은 편지 여러 통 → 봉투 하나에 몰아담기 (패킷 1 : Bunch N) 두꺼운 편지 한 통 → 봉투 여러 개로 쪼개기 (Bunch 1 : 패킷 N)

그리고 이 모든 편지에는 "어느 채널 소속이냐"를 적은 꼬리표가 붙어. 그게 ChIndex야. 0번은 컨트롤 채널(연결 관리용), 그 외는 액터 같은 데이터 스트림. 받는 쪽이 이 번호를 보고 Channels[ChIndex]로 편지를 배달해.

2. 편지는 어떻게 생겼나 — 헤더 플래그 (DataBunch.h)

편지 한 통(FOutBunch = 보낼 것, FInBunch = 받은 것)에는 본문 앞에 플래그 비트들이 붙어. 이게 헤더야. 정의를 그대로 보자.

uint8 bReliable:1; uint8 bPartial:1; // Not a complete bunch uint8 bPartialInitial:1; // The first bunch of a partial bunch uint8 bPartialFinal:1; // The final bunch of a partial bunch uint8 bHasPackageMapExports:1; // This bunch has networkGUID name/id pairs uint8 bHasMustBeMappedGUIDs:1; // This bunch has guids that must be mapped before we can process this bunch uint8 bPartialCustomExportsFinal:1; // This bunch marks the end of the CustomExports data that needs to be processed immediately (not queued) uint8 bOutWantsFullInitState:1; // Set this true to force all replicated properties to be serialized in the initial bunch even if they do not differ from Archetype baseline

Public/Net/DataBunch.h:39-46 (FOutBunch)

🔤 기호 사전 — uint8 bReliable:1; 같은 플래그 필드
• uint8 = 0~255를 담는 한 바이트짜리 숫자 칸. 여기선 그 한 바이트를 더 잘게 쪼개 깃발들을 넣는다.
• bReliable = 앞의 b는 보통 참/거짓 깃발이라는 표시. 켜짐/꺼짐으로 보는 값이야.
• :1 = 이 필드는 딱 1비트만 쓰겠다는 뜻. 작은 스위치 하나만 자리 잡는 거야.
• ; = "이 한 줄 선언 끝" 표시. C++에서 문장 마침표 같은 역할.
• // ... = 사람에게 보여주는 설명 메모. 컴퓨터는 이 뒤 글을 실행하지 않아.
• bPartialInitial / bPartialFinal = partial 조각 중 처음인지 / 끝인지 알려주는 이름표.
🔁 이제 다시 보자. uint8 bPartial:1;은 "한 바이트 통 안에 bPartial이라는 1비트 스위치를 하나 만든다"로 읽으면 돼. 그래서 Bunch 헤더는 긴 숫자 덩어리가 아니라 켜고 끄는 작은 깃발 묶음이야.

:1 보이지? 전부 1비트짜리 필드야. UE는 플래그 하나를 1비트 단위로 아껴 쓰거든 (왜 그렇게까지 하는지는 → receive-callchain의 비트 리더 얘기). 지금 당장 알아야 할 핵심 세 개만 짚자:

  • bReliable — 이 편지가 "손실되면 재전송, 순서 보장"되는 신뢰 전송 대상이라는 표시. 이게 켜지면 ChSequence(채널 내 순번)가 따라붙어서 받는 쪽이 누락을 검사해.
  • bPartial — "나는 완전한 편지가 아니라 조각이야"라는 표시. 주석 그대로 Not a complete bunch.
  • bPartialInitial / bPartialFinal — 조각 중 첫 조각 / 마지막 조각 표시. 이 둘 사이 조각들을 모으면 원본 편지가 복원돼.

나머지(bHasPackageMapExports 등)는 GUID 매핑 같은 고급 주제라 여기선 이름만 알고 넘어가면 돼.

🌱 이 개념은 왜 생겼나 — partial bunch(조각 편지)
• 원래 구조: 편지 한 통을 봉투 하나에 넣어 보내면 제일 깔끔하지. 대부분 편지는 그렇게 보내.
• 그런데 문제: 근데 편지가 봉투(패킷 하나에 들어갈 최대치)보다 두꺼우면? 봉투에 안 들어가. 우리 서버는 TCP가 큰 데이터를 알아서 잘라 보내고 순서 맞춰 재조립해주지만, UE는 UDP 위라 아무도 안 잘라줘.
• 그래서 필요한 것: 두꺼운 편지를 앱이 직접 조각내서 봉투 여러 개에 나눠 싣는 거야. 이 조각 하나하나가 partial bunch. 그냥 자르면 받는 쪽이 헷갈리니까 첫 조각(bPartialInitial)·끝 조각(bPartialFinal) 표시를 붙여서, 그것만 보고 다시 한 통으로 합칠 수 있게 해.

3. 두꺼운 편지 쪼개기 — partial bunch가 태어나는 곳

이제 (나) 방향, 큰 Bunch가 조각으로 갈리는 실제 코드야. UChannel::SendBunch(DataChannel.cpp:1249) 안쪽이야.

if( Bunch->GetNumBits() > MAX_SINGLE_BUNCH_SIZE_BITS ) { uint8 *data = Bunch->GetData(); int64 bitsLeft = Bunch->GetNumBits(); Merge = false; while(bitsLeft > 0) { FOutBunch * PartialBunch = new FOutBunch(this, false); int64 bitsThisBunch = FMath::Min<int64>(bitsLeft, MAX_PARTIAL_BUNCH_SIZE_BITS); PartialBunch->SerializeBits(data, bitsThisBunch);

Private/DataChannel.cpp:1371-1382

🔤 기호 사전 — if( Bunch->GetNumBits() > MAX_SINGLE_BUNCH_SIZE_BITS )
• if = "만약 ~라면". 조건이 맞을 때만 안쪽 코드를 실행해.
• Bunch->GetNumBits() = Bunch한테 "너 몇 비트짜리야?" 하고 물어보는 것. ->는 포인터가 가리키는 물건에게 명령하는 화살표야.
• > = 왼쪽이 오른쪽보다 더 크면.
• MAX_SINGLE_BUNCH_SIZE_BITS = "Bunch 하나가 패킷 하나에 들어갈 수 있는 최대 비트 수" 같은 정해진 상한값. 대문자 이름은 보통 고정된 상수야.
• uint8 *data = data가 바이트들을 가리키는 주소표(포인터) 라는 뜻. *는 "값 덩어리를 직접 들고 있는 게 아니라 위치를 가리킴".
• int64 = 큰 정수를 담는 칸. 비트 수가 커질 수 있으니 넉넉한 숫자통을 쓰는 거야.
• false = 거짓. Merge = false는 "이번엔 합치기 모드 꺼"라는 스위치 내림.
• new FOutBunch(this, false) = 새 조각 편지(FOutBunch)를 하나 만든다. this는 "지금 이 채널"을 뜻해.
• FMath::Min<int64>(...) = 둘 중 작은 값을 골라주는 UE 수학 도우미. ::는 "FMath 안에 있는", <int64>는 "int64 숫자로 계산".
• SerializeBits(data, bitsThisBunch) = data에서 bitsThisBunch만큼의 비트를 이 조각에 베껴 담는 일.
🔁 이제 다시 보자. if로 "너무 큰가?"를 보고 → while(bitsLeft > 0)로 "남은 비트가 없어질 때까지" 돌고 → 매번 new FOutBunch로 조각을 만들고 → SerializeBits로 정해진 만큼만 담는다. 한 줄 요약: 큰 Bunch를 비트 단위로 잘라 partial Bunch 여러 개를 만드는 루프야.

읽는 법:

  • Bunch->GetNumBits() > MAX_SINGLE_BUNCH_SIZE_BITS — 편지가 "봉투 하나에 들어갈 최대치"를 넘으면 쪼개기 진입.
  • while(bitsLeft > 0) — 남은 비트가 0이 될 때까지 반복.
  • 매 바퀴 MAX_PARTIAL_BUNCH_SIZE_BITS 만큼만 뚝 떼서 새 FOutBunch(조각) 하나 만들고, bitsThisBunch만큼 채운 뒤 다음 조각으로. (원 코드에선 이 밑에서 bitsLeft -= bitsThisBunch로 깎아나가)

두꺼운 편지 한 통이 PartialBunch 여러 개로 갈리는 순간이야. 근데 아직 얘들은 "몇 편인지" 표시가 안 됐어. 그 표시를 붙이는 게 바로 다음 조각:

• OutgoingBunches.Num() = 지금 나갈 Bunch 조각이 몇 개인지 세는 함수. Num()은 개수 세기라고 보면 돼.
• NextBunch->bPartial = 다음에 보낼 조각의 bPartial 깃발을 만진다는 뜻. ->는 "그 조각 안의 깃발로 들어가".
• = 1 = 깃발을 켠다. 여기선 "맞다/참" 표시.
• == = 두 값이 같은지 비교. =처럼 넣는 게 아니라 "같니?"라고 묻는 기호야.
• ? 1: 0 = 앞 조건이 맞으면 1, 아니면 0을 고르는 짧은 if. PartialNum == 0 ? 1: 0은 "첫 조각이면 켜고 아니면 꺼".
• OutgoingBunches.Num() - 1 = 마지막 번호. 개수가 3이면 인덱스는 0,1,2라서 마지막은 3-1이야.
• &= = 기존 값과 조건을 같이 보고 남기는 연산. 여기선 첫 조각이 아니면 bOpen을 꺼서, 채널 열기 신호가 중간 조각에 새지 않게 해.
• && = 둘 다 참이어야 참. Bunch->bClose도 켜져 있고, 지금 조각도 마지막이어야 bClose가 켜져.
🔁 이제 다시 보자. OutgoingBunches.Num() > 1이면 조각이 여러 개라는 뜻이고, bPartial=1로 전부 "조각" 표시를 단다. PartialNum == 0은 첫 조각, PartialNum == Num()-1은 끝 조각이니까 Initial은 처음만, Final은 마지막만 켜지는 구조야.

OutgoingBunches.Num() > 1 — 조각이 2개 이상일 때만 partial 표시를 단다는 뜻이야. (안 쪼개졌으면 그냥 완전한 편지 한 통이니 partial 아님.) 그리고 이 다섯 줄이 §2의 플래그를 실제로 세팅해:

  • bPartial = 1 — 다 조각이다.
  • bPartialInitial은 PartialNum == 0, 즉 0번 조각(첫 편)만 1.
  • bPartialFinal은 PartialNum == 마지막 인덱스, 즉 끝 조각만 1.
  • bOpen은 첫 조각만 (&=로 첫 조각 외엔 다 꺼버려). 채널 여는 신호는 편지 맨 앞에서 한 번이면 되니까.
  • bClose도 마지막 조각만. 채널 닫는 신호는 편지 맨 끝에서 한 번.

정리하면, 3편짜리 편지의 플래그는 이렇게 찍혀:

조각0: bPartial=1 bPartialInitial=1 bPartialFinal=0 (bOpen 가능) 조각1: bPartial=1 bPartialInitial=0 bPartialFinal=0 조각2: bPartial=1 bPartialInitial=0 bPartialFinal=1 (bClose 가능)

받는 쪽은 이 세 플래그만 보고도 "아 지금 새 편지 시작(Initial)이구나 → 중간이구나 → 여기서 끝(Final)이구나"를 알아. 봉투마다 "3편 중 몇 편"을 굳이 안 적어도 되는 거야.

❓ 이 헤더 어디에도 "편지 본문이 몇 바이트다"라는 길이 필드가 안 보여. 게임 서버 감각이면 "본문 길이를 헤더에 박아야 받는 쪽이 어디까지가 이 편지인지 알 거 아냐?"라고 생각할 거야. 그럼 받는 쪽은 편지 경계를 대체 어떻게 찾지?

바로 확인해 보자.

길이 필드 없이 "쓴 순서 = 읽는 순서"만으로 경계를 찾는다 — 이 대칭이 깨지면(한쪽만 필드를 추가/삭제하면) 그 뒤 모든 비트가 밀려서 편지가 통째로 깨져. 그래서 write/read를 고칠 땐 반드시 짝으로 고쳐야 해.

8. 우리 서버랑 비교 (IOCP + 싱글스레드 액터)

조선협객전 서버 감각으로 매핑하면 이래.

우리 서버UE 네트워크메모
recv 버퍼 = 처리 단위 (헤더의 wSize만큼이 패킷 1개)패킷(봉투) 안에 Bunch(편지) 여러 개제일 큰 차이. 우리는 패킷 1개 = 핸들러 1개. UE는 패킷 1개 안을 Bunch로 또 쪼갬.
패킷 헤더에 wSize(본문 길이) 박음Bunch 헤더에 길이 필드 없음 — write/read 순서로 경계 찾음우리는 길이 보고 자름. UE는 "쓴 순서 그대로 읽어" 자름.
wID 하나로 switch 디스패치ChIndex로 Channels[ChIndex] 라우팅우리 wID는 "무슨 메시지냐", UE ChIndex는 "어느 스트림 소속이냐". 결이 다름.
큰 데이터도 TCP가 알아서 쪼개고 순서 맞춰 재조립큰 Bunch를 앱이 직접 partial로 쪼개고(:1371) 재조립(:785)우리는 커널(TCP)이 공짜로 해주던 걸 UE는 UDP 위에서 앱이 직접 함.
싱글스레드 액터가 패킷 순차 처리reliable은 ChSequence로 순서 보장, 채널 단위 순차개념은 비슷 — "한 스트림의 처리는 직렬로". 단 UE는 순서 보장을 스스로 만들어야 함.

핵심 차이 두 줄:

  1. 패킷 ≠ 처리 단위. UE는 봉투(패킷) 안을 편지(Bunch)로 또 나눈다. 우리 wID 하나 = 처리 하나랑 다르다.
  2. 길이 대신 순서. 우리는 wSize로 경계를 자르지만, UE Bunch는 길이 필드 없이 write/read 순서 대칭으로 경계를 찾는다.

🎯 원리 한 줄 요약

패킷(봉투)은 UDP·ack의 단위, Bunch(편지)는 채널의 논리 메시지 단위 — 작은 Bunch 여러 개는 한 패킷에 몰아담고(1:N), 큰 Bunch 하나는 partial 조각으로 쪼개 여러 패킷에 나눠 실으며(1:N), 이 조각은 bPartialInitial~Final로 다시 합쳐진다. Bunch 헤더엔 길이 필드가 없고, write 순서와 read 순서가 비트 단위로 거울처럼 대칭이라는 것 하나로 편지 경계를 찾는다.
