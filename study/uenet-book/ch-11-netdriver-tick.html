NetDriver — 프레임마다 도는 엔진

언리얼 네트워크 · 11 / 43

대상 독자: 게임 서버는 아는데 UE 네트워크는 처음인 사람.
이 챕터가 끝나면 "엔진이 매 프레임 네트워크를 언제, 어떤 순서로 돌리는지" — 특히 받는 펌프(TickDispatch)와 모든 커넥션을 도는 상위 루프(TickFlush)의 뼈대가 머릿속에 그려질 거야.
send-callchain의 자매편이야. 저긴 "번치 한 덩어리가 소켓까지 걸어가는 길", 여긴 그 길을 매 프레임 누가 불러서 돌리는가 — 한 층 위에서 내려다보는 시점이야.

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이 고민을 해봤을 거야. IOCP 워커가 CM_* 패킷을 받았다고 해서, 그 자리에서 바로 CChosunPlayer 상태를 막 고치면 편해 보이지만 곧 문제가 생겨. 몬스터 이동 중인데 데미지 패킷이 끼어들고, 인벤 저장 중인데 교환 패킷이 들어오고, 결국 락을 여기저기 붙이다가 서버가 실타래처럼 꼬여.

그래서 우리 조선 서버도 "받는 곳"과 "진짜 게임 로직을 처리하는 곳"을 나눠. 워커는 받은 걸 큐에 넣고, 싱글스레드 쪽에서 순서대로 SP_* 처리를 하게 만들지. 이렇게 해야 한 프레임, 한 턴, 한 박자 안에서 누가 먼저 움직이고 누가 나중에 맞았는지가 정리돼.

이 박자가 없으면 네트워크는 난장판이 돼. 어떤 클라는 이번 프레임 결과를 받고, 어떤 클라는 지난 프레임 결과를 받고, 어떤 패킷은 액터 복제 전에 나가고, 어떤 패킷은 복제 뒤에 나가. 서버가 "지금은 받는 시간", "지금은 게임 로직 시간", "지금은 보내는 시간"을 못 나누면, 같은 월드 안에서도 사람마다 다른 영화를 보게 되는 셈이야.

언리얼도 똑같은 문제를 만났고, 그 답이 바로 NetDriver의 프레임 틱이야. 프레임 앞쪽에서 TickDispatch가 들어온 걸 정리하고, 프레임 뒤쪽에서 TickFlush가 모든 UNetConnection을 한 바퀴 돌며 이번 프레임 몫을 내보내. 계속 아무 때나 처리하는 게 아니라, 엔진 심장 박동에 맞춰 "받기 → 게임 로직 → 보내기"로 줄을 세우는 거지.

그래서 이 챕터가 여기 있어. 앞에서 UNetConnection과 send-callchain으로 "커넥션 하나가 어떻게 보내는지"를 봤다면, 이제는 한 층 위에서 누가 매 프레임 그 커넥션들을 전부 깨워서 돌리는지를 봐야 해. 이걸 잡아야 뒤에 나오는 수신 체인, 소켓 드라이버, 액터 복제도 "아, 이 박자 안의 어느 칸이구나" 하고 제자리를 찾는다.

0. 먼저 비유부터 — 심장은 "계속" 뛰는 게 아니라 "박자"로 뛴다

우체국 하나 떠올려봐. 이 우체국은 24시간 문 열어두고 사람 올 때마다 즉석에서 처리하지 않아. 대신 정해진 박자로 움직여.

  • 아침에 문 열면 → 밤새 우편함에 쌓인 편지를 싹 걷어 안으로 들인다 (받기)
  • 하루 일 다 하고 → 오늘 나갈 편지를 봉투에 담아 트럭에 실어 내보낸다 (보내기)
  • 문 닫고, 다음 날 또 똑같이.

게임 엔진 네트워크가 정확히 이 박자야. 엔진은 매 프레임(대략 1/60초)마다 심장을 한 번 뛰는데, 그 한 박동 안에서 네트워크 담당자가 두 번 불려 나와 — 앞에서 한 번(받기), 뒤에서 한 번(보내기).

이 "네트워크 담당자"가 바로 UNetDriver야. 그리고 이 챕터는 그 담당자가 프레임마다 뭘 하는지, 뼈대만 딱 훑어.

핵심 직관 하나 먼저 박아두자.
매 프레임 = 받기 펌프 1번 + 보내기 펌프 1번. 이 두 펌프를 실제로 구현한 함수가 TickDispatch(받기)와 TickFlush(보내기)야. 이 챕터의 주인공.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 통째로 외우는 게 아니라 "아, 이게 이거구나"만 잡으면 돼.

🌱 이 개념은 왜 생겼나 — 느슨한 결합(델리게이트)
• 원래 구조: 월드가 매 프레임 netDriver->TickDispatch()를 직접 부르면 간단하잖아.
• 그런데 문제: 그러면 월드 코드가 NetDriver라는 존재를 속속들이 알아야 해. 네트워크가 없는 모드도 있고, 드라이버가 여러 개일 수도 있는데, 월드가 걔들을 일일이 이름으로 부르면 서로 꽉 묶여서 갈아끼우기 힘들어져.
• 그래서 필요한 것: 월드는 그냥 "수신 단계 시작!"이라고 방송만 하고, 관심 있는 NetDriver가 알아서 귀를 대고 있자. → 이 방송-구독 장치가 멀티캐스트 델리게이트야. 월드는 누가 듣는지 몰라도 돼.

1. 그런데 월드는 NetDriver를 어떻게 부를까? — 델리게이트 한 방

여기서 초보가 처음 넘어져. UWorld::Tick이 매 프레임 도는 건 알겠는데, 월드가 NetDriver를 직접 부르지 않아.

대신 UE는 "옵저버 패턴"을 써. 월드는 그냥 "수신 단계 시작!"이라고 방송(Broadcast)만 하고, 거기 귀 기울이고 있던 NetDriver가 알아서 반응해. 월드는 NetDriver라는 존재를 몰라도 되고, NetDriver는 자기가 필요할 때 월드 방송에 자기를 등록만 해두면 돼. 이걸 멀티캐스트 델리게이트라고 불러.

NetDriver가 초기화될 때 월드 방송에 자기를 걸어두는 코드가 이거야.

TickDispatchDelegateHandle = InWorld->OnTickDispatch ().AddUObject(this, &UNetDriver::InternalTickDispatch);

🔤 기호 사전 — TickDispatchDelegateHandle = InWorld->OnTickDispatch ().AddUObject(this, &UNetDriver::InternalTickDispatch);
• = = 오른쪽에서 만든 값을 왼쪽 이름표에 담아두는 표시. 여기선 "등록 손잡이"를 저장해.
• InWorld->OnTickDispatch () = InWorld가 가리키는 월드한테 OnTickDispatch 방송 채널을 꺼내 달라는 말. ->는 포인터 안쪽 물건을 꺼낼 때 쓰는 화살표야.
• .AddUObject(...) = 그 방송 채널에 "이 객체의 함수를 구독자로 추가해줘"라고 등록하는 호출.
• this = 지금 이 코드를 실행 중인 NetDriver 자기 자신.
• &UNetDriver::InternalTickDispatch = UNetDriver 안에 있는 InternalTickDispatch 함수의 주소표. &는 "주소를 줘", ::는 "~소속" 표시야.
• ; = 이 명령은 여기서 끝이라는 마침표.
🔁 이제 다시 보자. 이 한 줄은 "월드의 OnTickDispatch 방송에 나(this)의 InternalTickDispatch를 연결하고, 그 연결 손잡이를 TickDispatchDelegateHandle에 저장한다"로 읽으면 돼.

• TickFlushDelegateHandle = 나중에 이 등록을 빼거나 추적할 때 쓰는 손잡이 이름.
• OnTickFlush() = 월드가 프레임 뒤쪽에서 "이제 보내기 단계야" 하고 쏘는 방송 채널.
• .AddUObject(this, ...) = this 객체, 즉 지금 NetDriver를 방송 구독자로 붙이는 말.
• &UNetDriver::InternalTickFlush = 방송이 오면 부를 함수의 주소표. InternalTickFlush는 보내기 펌프를 감싸는 안쪽 입구야.
• ; = 등록 명령 한 줄 끝.
🔁 이제 다시 보자. 위 줄과 모양이 거의 같지? 첫 줄은 받기 방송(OnTickDispatch)에 받기 입구를 붙이고, 이 줄은 보내기 방송(OnTickFlush)에 보내기 입구를 붙여. 프레임 앞쪽/뒤쪽 방송에 NetDriver가 각각 예약된 것이야.

AddUObject(this, &UNetDriver::InternalTickDispatch) = "월드가 OnTickDispatch 방송을 쏘면, 나(this)의 InternalTickDispatch 함수를 불러줘"라고 예약한 거야.

🔤 기호 사전 — void UWorld::BroadcastTickDispatch(float DeltaTime)
• void = 이 함수는 계산 결과를 돌려주지 않아. 그냥 방송만 쏘고 끝나.
• UWorld:: = UWorld에 딸린 함수라는 소속 표시. ::는 "~의"라고 읽으면 돼.
• float DeltaTime = 이번 프레임이 지난 시간. float는 소수점 숫자를 담는 그릇이야.

• TickDispatchEvent.Broadcast(DeltaTime) = TickDispatchEvent에 등록된 사람들에게 DeltaTime을 들고 "지금 시작!" 하고 알리는 줄.
• ; = 이 방송 명령은 여기서 끝.
🔁 이제 다시 보자. UWorld::BroadcastTickDispatch는 거창해 보여도 속은 한 줄이야. TickDispatchEvent.Broadcast(DeltaTime) = "수신 단계 방송을 쏜다". 그러면 아까 AddUObject로 붙어 있던 NetDriver의 InternalTickDispatch가 자동으로 불려.

.Broadcast(DeltaTime) 이 딱 한 줄이 방송이야. 여기 등록된 리스너(=우리 NetDriver의 InternalTickDispatch)가 자동으로 호출돼. 월드는 NetDriver를 직접 몰라도 되는 느슨한 결합 — 이게 델리게이트를 쓰는 이유야.

잠깐 맞춰봐 🤔 — 그럼 InternalTickDispatch가 바로 소켓에서 패킷을 퍼올릴까?
... 아니야. 반전. Internal은 감싸는 층일 뿐이고, 소켓 읽기는 저 아래 또 한 겹 안쪽에 있어. 그것도 이 클론엔 절반이 없어. 왜 그런지 아래에서 풀게.

2. Broadcast → Internal → Tick, 3단 래핑

로그에서 콜스택 읽을 때 헷갈리지 말라고 미리 깔아두는 개념. NetDriver 틱은 항상 3층으로 내려가.

UWorld::BroadcastTickDispatch ← ① 월드가 "시작!" 방송만 │ (멀티캐스트 델리게이트) ▼ UNetDriver::InternalTickDispatch ← ② 가드/래핑 담당 (실제 일 X) │ ▼ UNetDriver::TickDispatch ← ③ 실제 일

가운데 Internal 층이 뭘 하는지 보자.

void UNetDriver::InternalTickDispatch(float DeltaSeconds) { TGuardValue<bool> GuardInNetTick(bInTick, true); if (ReplicationSystem) { ReplicationSystem->PreReceiveUpdate(); } TickDispatch(DeltaSeconds); if (ReplicationSystem) { ReplicationSystem->PostReceiveUpdate(); } }

— NetDriver.cpp:2354

🔤 기호 사전 — UNetDriver::InternalTickDispatch
• void = 이 함수도 결과값을 돌려주지 않아. 틱 한 번을 처리하고 끝나.
• float DeltaSeconds = 지난 프레임에서 이번 프레임까지 걸린 시간. 초 단위 소수점 숫자야.
• TGuardValue<bool> = 잠깐 켰다가 함수가 끝나면 자동으로 되돌리는 안전핀. <bool>은 참/거짓 값을 다룬다는 뜻.
• if (ReplicationSystem) = ReplicationSystem이 있으면 안쪽을 실행해. 없으면 그냥 건너뛰어.
• ReplicationSystem->PreReceiveUpdate() = ReplicationSystem이 가리키는 객체한테 수신 전 준비 함수를 시키는 말. ->는 포인터 안쪽 함수 호출.
• TickDispatch(DeltaSeconds) = 진짜 받기 펌프 본체로 내려가는 줄.
• PostReceiveUpdate() = 받기 본체가 끝난 뒤 Iris 쪽 마무리 함수를 부르는 줄.
🔁 이제 다시 보자. 이 함수는 "틱 중 표시를 켜고 → Iris가 있으면 수신 전 준비 → 진짜 TickDispatch 실행 → Iris가 있으면 수신 후 정리"야. 이름에 Internal이 붙은 이유가 보여. 실제 일을 직접 하기보다 앞뒤 안전장치로 감싸는 층이야.

이 층이 하는 일은 딱 둘.

  1. TGuardValue<bool> GuardInNetTick(bInTick, true) — 틱 실행 중임을 표시하는 재진입 방지 플래그. 스코프 들어올 때 bInTick을 true로 켜고, 함수 벗어날 때 자동으로 원래 값으로 되돌려. 조선 서버로 치면 m_bInTick = true; ... m_bInTick = false;를 손으로 짝 맞추던 걸, C++ RAII가 자동화해준 거야. return이 중간에 어디서 튀든 원복이 보장돼.
  2. Iris PreReceiveUpdate / PostReceiveUpdate로 감싸기 — 새 리플리케이션 시스템(Iris)이 켜져 있으면 수신 전후를 감싼다. Iris 얘긴 여기선 넘어가 → iris

그리고 진짜 일은 TickDispatch(DeltaSeconds) 한 줄로 내려가.

🌱 이 개념은 왜 생겼나 — 틱 예산과 히치 감지
• 원래 구조: 받기 펌프는 그냥 도착한 패킷을 퍼올리기만 하면 되지, 시간 같은 걸 왜 재?
• 그런데 문제: 어딘가 블로킹 콜이 물려서 프레임 사이가 5초씩 벌어지면, 클라 입장에선 연결이 끊긴 것처럼 보여. 근데 진짜 끊긴 건지, 서버가 잠깐 얼어붙은 건지 나중에 구분이 안 돼 — 로그만 봐선 둘 다 "타임아웃"이야.
• 그래서 필요한 것: 매 틱마다 지난 프레임과의 시간 차를 재서, 임계(5초)를 넘으면 "이번 프레임 히치났다"고 표시해두자. → 프레임에 시간 예산을 두고 넘침을 감지하는 이 습관이 나중에 "네트워크 문제냐 서버 문제냐"를 갈라줘.

3. 받기 펌프 TickDispatch — 근데 소켓을 안 읽는다고?

이제 3층 맨 아래 TickDispatch. 이름만 보면 "패킷 퍼올리는(dispatch) 데니까 여기서 recvfrom 돌리겠지" 싶지? 반전이야. 엔진 베이스 UNetDriver::TickDispatch는 소켓을 직접 안 읽어.

앞부분부터 보자. 하는 건 시간 관리랑 히치(뚝 끊김) 감지야.

• constexpr float TickLogThreshold = 5.0f = 컴파일할 때부터 정해진 기준값. 여기선 "5초 넘으면 이상하다"는 선이야.
• > = 왼쪽이 오른쪽보다 큰지 비교.
• || = 둘 중 하나라도 참이면 참. DeltaTime이 크거나 DeltaRealtime이 커도 히치로 본다는 뜻.
🔁 이제 다시 보자. 이 코드는 "현재 시간을 재고 → 지난번 시간과 차이를 계산하고 → 5초 기준보다 크면 bDidHitchLastFrame을 켠다"야. 즉 네트워크 틱 앞부분은 패킷을 읽기 전에 이번 프레임이 비정상적으로 멈췄는지 먼저 표시해둬.

DeltaTime이 5초 넘게 벌어졌으면 "이번 프레임 히치났다(bDidHitchLastFrame)"고 표시해둬. 프레임 사이가 5초씩 벌어진다는 건 어딘가 블로킹 콜이 물려서 타임아웃 유발 중이라는 신호거든. 이걸 잡아두면 나중에 "네트워크 끊긴 게 진짜 끊긴 거냐, 서버가 얼어붙어서 그런 거냐"를 구분할 수 있어.

그다음, 커넥션 청소랑 수신 준비.

for (int32 ConnIdx=ClientConnections.Num()-1; ConnIdx>=0; ConnIdx--) { UNetConnection* CurConn = ClientConnections[ConnIdx]; if (IsValid(CurConn)) { if (CurConn->GetConnectionState() == USOCK_Closed) { CurConn->CleanUp(); } else { CurConn->PreTickDispatch(); } } }

— NetDriver.cpp:2709

🔤 기호 사전 — 커넥션 역순 루프
• for (...) = 같은 일을 여러 번 반복하는 루프. 여기선 모든 클라이언트 커넥션을 훑어.
• int32 ConnIdx=ClientConnections.Num()-1 = 마지막 칸 번호부터 시작한다는 뜻. Num()은 배열 길이, -1은 마지막 인덱스.
• ConnIdx>=0 = 0번 칸까지 계속 돌라는 조건.
• ConnIdx-- = 한 번 돌 때마다 번호를 하나씩 줄여. 그래서 뒤에서 앞으로 간다.
• UNetConnection* CurConn = 커넥션 객체를 가리키는 포인터 하나. *는 "직접 물건이 아니라 위치표" 느낌이야.
• ClientConnections[ConnIdx] = 클라이언트 커넥션 배열에서 ConnIdx번째 칸을 꺼내기.
• IsValid(CurConn) = 이 포인터가 아직 쓸 수 있는 커넥션인지 확인.
• CurConn->GetConnectionState() == USOCK_Closed = 커넥션 상태가 닫힘인지 비교. ==는 "같냐?"야.
• CleanUp() / PreTickDispatch() = 닫혔으면 정리, 살아 있으면 이번 프레임 수신 준비.
🔁 이제 다시 보자. 이 루프는 "클라이언트 커넥션 배열을 뒤에서 앞으로 훑고 → 죽은 연결은 CleanUp → 살아 있는 연결은 PreTickDispatch"야. 뒤에서 도는 이유는 중간에 연결이 빠져도 남은 번호가 덜 꼬이게 하려는 거야.

역순(Num()-1부터 0까지) 루프인 게 포인트야. 중간에 CleanUp()으로 배열 원소가 빠져도 인덱스가 안 꼬이거든. 상태가 USOCK_Closed면 정리, 아니면 PreTickDispatch()로 이번 프레임 수신 준비만 시켜.

여기까지가 베이스가 하는 전부야. 시간 갱신, 히치 감지, UpdateStandbyCheatStatus()(대기 상태 치트 감지), 닫힌 커넥션 청소, 각 커넥션 PreTickDispatch(). 그럼 실제 소켓 읽기는?

### 🔬 이 클론에 소스 미포함 — 실제 소켓 recv는 대조 불가
진짜 recvfrom을 while 루프로 퍼올리는 코드는 서브클래스 IpNetDriver::TickDispatch가 이 베이스 함수를 오버라이드해서 채워. 그런데 이 학습 트리엔 Engine 모듈만 담겨 있어서 IpNetDriver.cpp / IpConnection.cpp 파일 자체가 없어 (find -iname "IpNetDriver*" → 0건).
그래서 이 챕터는 베이스 UNetDriver 흐름까지만 verbatim으로 대조했어. "소켓에서 UDP를 while로 다 빨아들이는" 부분은 개념으로만 알아둬:
• 서브클래스가 while (Socket->RecvFrom(...)) 로 이번 프레임 도착분을 싹 퍼올려서
• 보낸 주소로 커넥션을 찾고(없으면 새 커넥션/핸드셰이크)
• Connection->ReceivedRawPacket()으로 넘겨 위로 올린다
소켓에서 올라온 raw가 번치로 풀려 위로 전달되는 받는 쪽 상세 계단은 → receive-callchain, IpNetDriver 소켓 층 자체는 → ipnetdriver-socket

즉 베이스 TickDispatch의 진짜 역할은 "받기 펌프의 뼈대/관리"고, "펌프질 그 자체"는 서브클래스가 끼워 넣는 구조야. 초보가 제일 헷갈리는 지점이라 크게 박아둔다.

받고 나면 BroadcastPostTickDispatch() → UNetDriver::PostTickDispatch()(NetDriver.cpp:2762)로 수신 후처리(대기 중이던 RPC flush 등)를 하고 받기 단계 끝.

🌱 이 개념은 왜 생겼나 — 프레임 끝 상위 루프(전원 배칭 flush)
• 원래 구조: 커넥션마다 보낼 게 생길 때마다 그 자리에서 바로 소켓에 내보내면 되잖아.
• 그런데 문제: 그러면 한 프레임 안에서도 커넥션 여기저기가 제각각 소켓을 때려 — 누구는 이번 프레임 결과를, 누구는 반쯤 된 결과를 받아. send() 횟수도 헛되이 늘고, 접속자마다 다른 박자로 패킷이 나가.
• 그래서 필요한 것: 짐 쌓기(액터 복제)를 프레임 앞에서 다 끝낸 뒤, 프레임 끝에서 한 번 ClientConnections를 통째로 돌며 전원에게 이번 프레임 몫을 flush하자. → 이 "모든 커넥션 한 바퀴"가 상위 루프야. 조선 서버에서 Nagle 끄고 프레임 단위로 묶어 보내는 그 배칭이랑 똑같은 정신.

4. 보내기 펌프 TickFlush — "모든 NetConnection을 도는 상위 루프"

프레임 후반. 이번 프레임에 쌓인 액터 변화를 복제하고, 각 커넥션에 쌓인 번치를 패킷으로 묶어 내보내는 단계. 진입은 InternalTickFlush(NetDriver.cpp:2371, 여기도 bInTick 가드 래핑) → TickFlush(NetDriver.cpp:1113)야.

TickFlush가 하는 큰 일은 둘로 나뉘어.

① 서버면 액터 상태 복제 트리거

if (IsServer() && (ClientConnections.Num() > 0 || UE::Net::Private::bUpdateReplicationSystemWithNoConnections) && !bSkipServerReplicateActors) { // Update all clients. #if WITH_SERVER_CODE CSV_SCOPED_TIMING_STAT_EXCLUSIVE(ServerReplicateActors); if (ReplicationSystem) { UpdateIrisReplicationViews(); SendClientMoveAdjustments(); ReplicationSystem->NetUpdate(DeltaSeconds); }

— NetDriver.cpp:1128

🔤 기호 사전 — 서버 복제 트리거 조건
• if (...) = 조건이 맞을 때만 안쪽 코드를 실행해.
• IsServer() = 지금 NetDriver가 서버 역할인지 묻는 함수.
• && = 양쪽 조건이 모두 참이어야 참. "서버이고, 연결 조건도 맞고, 스킵도 아니어야" 들어간다.
• || = 둘 중 하나만 참이어도 참. 클라가 있거나, 연결 없어도 복제 시스템을 업데이트하라는 옵션이 켜져 있으면 통과.
• !bSkipServerReplicateActors = bSkipServerReplicateActors가 거짓일 때. !는 "아니면" 표시야.
• UE::Net::Private::... = UE 안의 Net 안의 Private에 있는 설정값. ::가 여러 번 나오면 폴더처럼 소속을 타고 들어간다고 보면 돼.
• #if WITH_SERVER_CODE = 서버 코드가 포함된 빌드에서만 이 아래를 컴파일하라는 전처리 조건.
• ReplicationSystem->NetUpdate(DeltaSeconds) = Iris 복제 시스템에게 이번 프레임 복제 갱신을 시키는 줄.
🔁 이제 다시 보자. 이 if는 "서버이고, 복제를 돌릴 이유가 있고, 스킵 명령이 없으면" 안으로 들어가. 안쪽에서는 Iris가 있으면 뷰를 갱신하고 이동 보정도 보내고, 마지막에 NetUpdate로 누구에게 무엇을 보낼지 계산을 시작해.

서버일 때만, 그리고 붙은 클라가 있을 때만 "누구한테 뭘 복제할지"를 계산해. 여기 ReplicationSystem->NetUpdate(Iris 경로) 또는 구식 ServerReplicateActors(DeltaSeconds)가 액터 상태를 각 커넥션 채널에 쌓아. "무슨 액터를 누구한테 보낼지 고르는 그 무거운 계산"은 이 챕터 범위 밖 — 통째로 → server-replicate-actors

② 그리고 이 챕터의 진짜 주인공, 상위 루프

— NetDriver.cpp:1183

🔤 기호 사전 — 모든 커넥션을 도는 루프
• QUICK_SCOPE_CYCLE_COUNTER(...) = 이 구간이 얼마나 걸렸는지 프로파일러에 찍기 위한 빠른 측정 표식.
• for (UNetConnection* Connection : ClientConnections) = ClientConnections 안에 든 커넥션을 하나씩 꺼내 Connection이라는 이름으로 쓰겠다는 반복문.
• UNetConnection* = UNetConnection 객체를 가리키는 포인터. 접속자 한 명의 네트워크 연결이라고 보면 돼.
• : = "이 목록에서 하나씩 꺼낸다"는 range-for 문법의 가운데 표시.
• Connection->Tick(DeltaSeconds) = 그 커넥션에게 이번 프레임 보내기/정리 일을 하라고 시키는 호출.
🔁 이제 다시 보자. 이 루프는 진짜 간단해. ClientConnections에 있는 접속자를 한 명씩 꺼내서 Connection->Tick(DeltaSeconds)를 부른다. 즉 TickFlush의 뒤쪽 핵심은 모든 접속자에게 이번 프레임 몫을 flush하라고 한 바퀴 도는 것이야.

이 for 루프가 "모든 NetConnection을 도는 상위 루프"의 정체야. 서버는 접속한 클라마다 UNetConnection을 하나씩 들고 ClientConnections 배열에 담아둬. TickFlush가 프레임 후반에 이 배열을 전부 돌면서 Connection->Tick()을 불러 — 각 커넥션이 자기 채널에 쌓아둔 번치를 패킷으로 묶어 실제로 소켓에 밀어내(flush). 커넥션 1개 안에서 번치가 봉투에 담겨 나가는 상세는 → send-callchain

①이 "짐을 쌓는 단계", ②가 "쌓인 짐을 트럭에 실어 내보내는 단계"라고 보면 순서가 딱 맞아. 그래서 ①이 반드시 ② 앞에 와야 해.

끝에 UpdateNetworkStats()(:1222), UpdateNetworkLagState()(:1230)로 통계/랙 상태 갱신하고 보내기 단계 종료. 마지막 BroadcastPostTickFlush()(LevelTick.cpp:1907)로 송신 후처리까지.

6. 우리 서버랑 비교 — IOCP 워커 + 싱글스레드 액터

조선 서버 하던 감각으로 매핑하면 이래.

가장 큰 차이 두 개:

  1. UE는 수신도 게임 스레드에서 프레임 단위로 편다. 조선처럼 IOCP 워커가 별도 스레드에서 항상 recv하는 게 아니라, TickDispatch 한 방에 "지난 프레임 동안 도착한 거 몰아서" 처리해. 그래서 bInTick 재진입 가드가 의미 있어 — 어차피 한 스레드니까 락이 아니라 플래그로 충분해. 조선의 싱글스레드 액터 철학이랑 오히려 더 닮았어.
  2. 송신은 매번이 아니라 프레임 끝 한 번. 이건 조선에서 Nagle 끄고 프레임 단위 배칭하는 거랑 정확히 같은 동기 — syscall 아끼려고 모아서 한 방. ClientConnections 순회 = 접속자 전원에게 이번 프레임 몫을 flush하는 브로드캐스트 루프.

즉 "IOCP 워커가 받아 큐에 넣고 싱글스레드가 처리"라는 조선 구조에서, UE는 큐 대신 프레임 경계를 쓴다고 보면 큰 그림이 맞아. 받는 순간과 처리하는 순간을 프레임으로 딱 자른 거지.

  • TickFlush 래핑에 자꾸 튀어나오던 Iris(새 리플리케이션 시스템) → iris

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. 네트워크를 매 프레임 딱 두 번 편다는데, 왜 아무 때나 처리하지 않고 박자로 나누나요?

답 보기
박자가 없으면 네트워크가 난장판이 돼. 어떤 클라는 이번 프레임 결과를 받고 어떤 클라는 지난 프레임 결과를 받고, 어떤 패킷은 액터 복제 전에 나가고 어떤 건 복제 뒤에 나가. 같은 월드인데 사람마다 다른 영화를 보게 되는 거지. 그래서 엔진은 프레임 앞에서 TickDispatch로 받고, 뒤에서 TickFlush로 내보내. "받기 → 게임 로직 → 보내기"로 줄을 세우는 거야. 우리 조선 서버가 "받는 곳"과 "처리하는 곳"을 나눠 한 박자 안에서 순서를 정리하는 거랑 같은 정신이야.

↳ 그럼 받은 즉시 그 자리에서 게임 상태를 고치면 뭐가 문제죠?

답 보기
몬스터 이동 중인데 데미지 패킷이 끼어들고, 인벤 저장 중인데 교환 패킷이 들어오고 — 결국 락을 여기저기 붙이다 서버가 실타래처럼 꼬여. 프레임 경계로 "지금은 받는 시간, 지금은 로직 시간"을 딱 자르면 그런 끼어들기가 없어지고 순서가 정리돼. 그래서 UE는 조선 서버의 큐 대신 프레임 경계를 쓴다고 보면 큰 그림이 맞아.

Q2. 월드가 NetDriver를 어떻게 부르나요? 직접 부르나요?

답 보기
직접 안 불러. 월드는 그냥 "수신 단계 시작!" 하고 방송(Broadcast)만 하고, 거기 귀 기울이던 NetDriver가 알아서 반응해. NetDriver가 초기화될 때 월드 방송(OnTickDispatch/OnTickFlush)에 자기 함수를 등록(AddUObject)해두는 거지. 이 방송-구독 장치가 멀티캐스트 델리게이트야.

↳ 그냥 월드가 netDriver->TickDispatch()를 직접 부르면 안 되나요?

답 보기
그러면 월드 코드가 NetDriver라는 존재를 속속들이 알아야 해. 네트워크 없는 모드도 있고 드라이버가 여러 개일 수도 있는데, 월드가 걔들을 일일이 이름으로 부르면 서로 꽉 묶여서 갈아끼우기 힘들어져. 방송-구독으로 하면 월드는 누가 듣는지 몰라도 되고 NetDriver만 자기를 등록하면 돼 — 느슨한 결합이지. 이게 델리게이트를 쓰는 이유야.

Q3. 받기 펌프 TickDispatch인데 정작 소켓을 안 읽는다던데, 그럼 뭘 하나요?

답 보기
베이스 UNetDriver::TickDispatch는 받기 펌프의 뼈대/관리만 해 — 시간 갱신, 히치(뚝 끊김) 감지, 닫힌 커넥션 청소, 각 커넥션 PreTickDispatch로 수신 준비. "펌프질 그 자체"(recvfrom을 while로 퍼올리기)는 서브클래스 IpNetDriver가 오버라이드해서 끼워 넣어. 앞 챕터의 계약/구현 분리가 여기서도 반복되는 거야. 이름만 보고 "여기서 소켓 읽겠지" 하면 헷갈리는 지점이라 딱 박아둬야 해.

↳ 히치 감지는 왜 굳이 하나요? 받기랑 무슨 상관인가요?

답 보기
프레임 사이가 5초씩 벌어지면 클라 입장에선 연결이 끊긴 것처럼 보여. 근데 진짜 끊긴 건지 서버가 잠깐 얼어붙은 건지 나중에 로그만 봐선 구분이 안 돼 — 둘 다 "타임아웃"이거든. 그래서 매 틱 지난 프레임과의 시간 차를 재서 5초 임계를 넘으면 "이번 프레임 히치났다"고 표시(bDidHitchLastFrame)해둬. 이게 나중에 "네트워크 문제냐 서버 문제냐"를 갈라줘.

Q4. 보내기 펌프 TickFlush의 핵심은 뭔가요?

답 보기
두 단계야. ① 서버면 액터 상태를 각 커넥션 채널에 쌓고(복제 계산), ② ClientConnections 배열을 전부 돌면서 Connection->Tick()을 불러 쌓인 번치를 패킷으로 묶어 소켓에 밀어내(flush). 이 for 루프가 "모든 NetConnection을 도는 상위 루프"의 정체야. ①이 "짐 쌓기", ②가 "짐 내보내기"라 반드시 ①이 ② 앞에 와야 해.

↳ 커넥션마다 보낼 게 생길 때 바로바로 소켓에 쏘면 안 되나요?

답 보기
그러면 한 프레임 안에서도 커넥션 여기저기가 제각각 소켓을 때려 — 누구는 이번 프레임 결과를, 누구는 반쯤 된 결과를 받아. send() 횟수도 헛되이 늘고 접속자마다 다른 박자로 패킷이 나가지. 그래서 짐 쌓기를 프레임 앞에서 다 끝낸 뒤 프레임 끝에서 한 번 전원에게 몰아서 flush하는 거야. 우리 조선 서버에서 Nagle 끄고 프레임 단위로 묶어 보내는 배칭이랑 정확히 같은 동기 — syscall 아끼려고 모아서 한 방.

↳ 조선은 IOCP 워커가 별도 스레드로 항상 recv하는데, UE는 다르지 않나요?

답 보기
달라. UE는 수신도 게임 스레드에서 프레임 단위로 편다 — TickDispatch 한 방에 "지난 프레임 동안 도착한 거 몰아서" 처리해. 어차피 한 스레드니까 재진입 방지도 락이 아니라 bInTick 플래그로 충분하지. 오히려 조선의 싱글스레드 액터 철학이랑 더 닮았어. 조선은 큐로 IO 스레드와 로직 스레드를 잇고, UE는 프레임 경계로 받는 순간과 처리하는 순간을 자른 차이일 뿐이야.

🎯 원리 한 줄 요약

엔진은 매 프레임 딱 두 번 네트워크를 편다 — 앞에서 TickDispatch로 받고(단, 소켓 read는 서브클래스가 채움), 뒤에서 TickFlush가 ClientConnections를 전부 도는 상위 루프로 접속자 전원에게 이번 프레임 몫을 한 방에 내보낸다.
