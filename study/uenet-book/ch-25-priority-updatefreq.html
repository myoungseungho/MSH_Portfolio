우선순위와 갱신빈도

언리얼 네트워크 · 25 / 42

대역폭이라는 좁은 문으로, 누굴 얼마나 자주 통과시킬까

들어가기 전에

서버가 매 틱 클라한테 액터 상태를 뿌린다고 해보자. 근데 뿌릴 게 500개인데 이번 틱에 100개어치 대역폭밖에 없어. 그럼 어떡하지?

방법은 두 축이야.

  • 시간 축 — "이 액터는 초당 몇 번만 보내면 돼" (자주 안 변하는 벽/문은 굳이 100번씩 안 보내도 됨)
  • 경쟁 축 — "대역폭 다 차면, 남은 것 중에 누굴 살리고 누굴 이번 틱 버릴까"

앞 축이 NetUpdateFrequency(갱신빈도), 뒤 축이 NetPriority(우선순위)야. 헷갈리기 쉬운데 완전히 다른 축이라는 걸 먼저 못박자.

  • 갱신빈도 = 얼마나 자주 (시간 간격)
  • 우선순위 = 누가 먼저 (포화 시 생존 순번)

그리고 이 둘을 실제로 굴리는 게 UNetDriver::ServerReplicateActors 파이프라인이야. 이 챕터는 그 파이프라인을 따라간다.

앞 단계(어떤 액터가 애초에 후보에 오르나 = relevancy)가 헷갈리면 → relevancy
이 뒤에 "안 변하는 액터는 아예 복제 끄기"가 궁금하면 → dormancy

[1] 시간 축 — 갱신빈도 게이트

먼저 이번 틱에 "고려할 가치가 있는" 액터만 추린다. 핵심은 딱 한 줄이야.

• if (...) = 괄호 안 조건이 맞으면 바로 아래 { ... } 안을 실행해.
• ! = "아니면". !ActorInfo->bPendingNetUpdate는 "강제 갱신 대기 상태가 아니면"이라고 읽어.
• -> = 포인터가 가리키는 물건 안의 값을 꺼내는 화살표. ActorInfo->NextUpdateTime = ActorInfo 안의 다음 갱신시각.
• && = "그리고". 왼쪽 조건도 맞고 오른쪽 조건도 맞아야 전체가 참이야.
• <= = "작거나 같으면". 지금 시간이 다음 갱신시각보다 아직 이르면 참.
• UE_LOG(...) = 엔진 로그에 기록 남기기. 여기선 왜 스킵했는지 아주 자세히 찍는 줄이야.
• TEXT("...") = UE가 문자열을 엔진용 문자 타입으로 감싸는 매크로.
• ? : = 조건에 따라 둘 중 하나를 고르는 짧은 if. bPendingNetUpdate ? "true" : "false" 느낌.
• *GetNameSafe(...) = 이름 문자열 상자를 로그가 읽을 수 있는 형태로 꺼내는 표시라고 보면 돼.
🔁 이제 다시 보자. !bPendingNetUpdate(강제 대기 아님) + TimeSeconds <= NextUpdateTime(아직 예약 시간이 안 옴) 둘 다 맞으면, 이 액터는 이번 틱 후보에서 빠진다. 즉 이 if 한 줄은 "아직 네 차례 아니면 줄 서지 마" 라는 시간 문지기야.

읽어보면 — "아직 NextUpdateTime 안 됐으면 skip". 즉 다음 갱신시각이 도래하기 전엔 아예 후보에서 뺀다. 이게 "초당 N회 상한"을 만드는 장본인이야.

그럼 NextUpdateTime은 어떻게 정해질까? 이번 틱에 고려된 액터는 끝에서 다음 시각을 다시 예약해.

Runtime/Engine/Private/NetDriver.cpp:5228

const float NextUpdateDelta = bUseAdapativeNetFrequency ? ActorInfo->OptimalNetUpdateDelta : 1.0f / Actor->GetNetUpdateFrequency(); float RandDelay = GNetDisableRandomNetUpdateDelay ? 0.0f : UpdateDelayRandomStream.FRand() * ServerTickTime; // then set the next update time ActorInfo->NextUpdateTime = World->TimeSeconds + RandDelay + NextUpdateDelta;
🔤 다음 갱신시각 기호 사전 — NextUpdateDelta = bUseAdapativeNetFrequency ? ... : ...
• const float = 소수점 값을 담되, 한 번 정하면 이 변수는 다시 안 바꾸겠다는 뜻.
• ? : = 조건이 참이면 왼쪽 값, 아니면 오른쪽 값을 고르는 짧은 if.
• 1.0f = C++에서 "소수 1.0"을 float로 쓰겠다는 표시. 뒤의 f는 float 꼬리표야.
• / = 나누기. 여기선 "초당 몇 번"이라는 빈도를 "몇 초마다 한 번"이라는 간격으로 뒤집는 데 써.
• Actor->GetNetUpdateFrequency() = 이 액터가 들고 있는 갱신빈도 값을 물어보는 함수 호출.
• GNetDisableRandomNetUpdateDelay = 랜덤 지연을 끌지 말지 정하는 전역 스위치.
• FRand() = 0에서 1 사이 랜덤 소수 하나 뽑기.
• World->TimeSeconds + RandDelay + NextUpdateDelta = 현재 시간에 랜덤 흔들기와 다음 대기시간을 더해서 새 예약 시각을 만드는 식.
🔁 이제 다시 보자. 1.0f / GetNetUpdateFrequency()가 "초당 N번"을 "N분의 1초 뒤"로 바꾸고, 거기에 RandDelay를 살짝 섞어 NextUpdateTime을 다시 예약한다. 그래서 빈도는 숫자가 클수록 자주, 숫자가 작을수록 뜸하게 줄에 서는 거야.

여기서 눈여겨볼 건 1.0f / GetNetUpdateFrequency(). 빈도는 항상 역수로 뒤집혀 쓰인다.

  • NetUpdateFrequency = 100 → 델타 0.01초 → 초당 100번
  • NetUpdateFrequency = 10 → 델타 0.1초 → 초당 10번

예측해봐. 안 움직이는 문짝 액터를 NetUpdateFrequency = 2로 깔면 서버 부하가 얼마나 줄까? "절반쯤?" 이라고 찍었으면 반전이야 — 기본 100에서 2로 내리면 갱신 시도가 1/50로 준다. 이 액터가 후보 리스트에 오르는 횟수 자체가 50배 뜸해지니까, 뒤따르는 점수계산·정렬·전송 비용이 통째로 절약돼. 갱신빈도는 파이프라인 맨 앞의 수도꼭지라 여기서 잠그면 하류 전체가 마른다.

RandDelay는 왜 있냐면 — 수백 개 액터가 전부 똑같은 시각에 갱신 예약되면 특정 틱만 폭주하잖아. 랜덤으로 살짝 흩어서 틱마다 부하를 고르게 편다. (원하면 GNetDisableRandomNetUpdateDelay로 끌 수 있음)

보너스: 적응형 빈도 (안 변하면 더 느리게)

한 발 더 나가면, "실제로 안 바뀌는 액터는 100Hz로 후보에 올려봤자 매번 '보낼 것 없음'으로 헛돈다". 그래서 실제 전송이 뜸해지면 빈도를 스스로 낮춰.

Runtime/Engine/Private/NetDriver.cpp:5211

// Calculate min delta (max rate actor will update), and max delta (slowest rate actor will update) const float MinOptimalDelta = 1.0f / Actor->GetNetUpdateFrequency(); // Don't go faster than NetUpdateFrequency const float MaxOptimalDelta = FMath::Max( 1.0f / Actor->GetMinNetUpdateFrequency(), MinOptimalDelta ); // Don't go slower than MinNetUpdateFrequency (or NetUpdateFrequency if it's slower) // Interpolate between MinOptimalDelta/MaxOptimalDelta based on how long it's been since this actor actually sent anything const float Alpha = FMath::Clamp( ( LastReplicateDelta - ScaleDownStartTime ) / ScaleDownTimeRange, 0.0f, 1.0f ); ActorInfo->OptimalNetUpdateDelta = FMath::Lerp( MinOptimalDelta, MaxOptimalDelta, Alpha );
🔤 적응형 빈도 기호 사전 — FMath::Clamp(...) / FMath::Lerp(...)
• FMath::Max(A, B) = A와 B 중 더 큰 값을 고르기. ::는 FMath 상자 안의 함수라는 소속 표시야.
• / = 나누기. 여기서도 빈도를 시간 간격으로 바꾸는 데 쓴다.
• Alpha = 0에서 1 사이 손잡이. 0이면 앞값 쪽, 1이면 뒷값 쪽으로 간다고 보면 돼.
• FMath::Clamp(X, 0.0f, 1.0f) = X가 0보다 작으면 0, 1보다 크면 1로 눌러서 범위 안에 가두기.
• FMath::Lerp(A, B, Alpha) = A와 B 사이를 Alpha만큼 섞어 중간값 만들기.
• ActorInfo->OptimalNetUpdateDelta = 이 액터에게 이번에 계산된 "적당한 다음 대기시간" 칸.
🔁 이제 다시 보자. LastReplicateDelta가 길어질수록 Alpha가 커지고, Lerp 결과가 MaxOptimalDelta 쪽으로 간다. 말로 풀면 "오래 실제 전송이 없던 액터는 다음 후보 등록 간격을 더 느리게 잡는다" 야.

NetUpdateFrequency(가장 빠름)와 MinNetUpdateFrequency(가장 느림) 사이를, "얼마나 오래 실제 전송이 없었나"를 Alpha로 잡아 Lerp한다. MinNetUpdateFrequency라는 이름이 함정인데 — "Min빈도 = 가장 느린 갱신 = 대역폭 절약 하한선"이야. 낮은 숫자일수록 뜸하다.

[2] 경쟁 축 — 우선순위 점수 매기고 정렬

시간 게이트를 통과한 액터들이 이제 연결(Connection)별로 점수를 받는다. 왜 연결별이냐면, 우선순위는 "그 플레이어 시점에서 얼마나 중요한가"라서 보는 사람마다 달라지거든 (내 코앞의 적 vs 지도 반대편의 적).

🔁 이제 다시 보자. 먼저 Time에 "마지막 전송 뒤 얼마나 굶었나"를 담고, for로 모든 Viewer를 돌며 GetNetPriority(...) 점수를 계산한다. Viewer가 여러 명이면 Max로 제일 큰 점수만 남겨서, 이 연결에서 그 액터의 최종 순번 재료를 만드는 코드야.

세 가지만 보면 돼.

  1. Time = ElapsedTime - Channel->LastUpdateTime — 이 액터를 마지막으로 보낸 뒤 흐른 시간. 오래 못 보냈을수록 커진다.
  2. 점수 = 65536 * GetNetPriority(...) — 65536은 그냥 정수 스케일링(float를 int 점수로). 본질은 GetNetPriority.
  3. Viewer 여럿이면 Max — 한 연결에 시점이 여러 개면(분할화면 등) 그중 가장 높은 점수 채택.

• return = 이 함수의 답을 여기서 돌려주고 끝낸다는 뜻.

🔁 이제 다시 보자. 앞에서 거리·시야·주인 여부로 Time을 키우거나 줄였고, 마지막엔 NetPriority * Time을 답으로 돌려준다. 즉 최종 점수는 액터 기본 중요도 × 얼마나 오래 굶었는지(보정 포함) 로 읽으면 돼.

최종식: NetPriority * Time.

여기서 두 재료의 성격이 확 갈려.

  • NetPriority — 액터가 들고 있는 고정 가중치. 기본 1.0. 캐릭터는 높게, 배경 장식은 낮게 세팅. 절대 순번이 아니라 배수야. 2.0이면 같은 조건에서 점수 2배.
  • Time — 상수가 아니라 "마지막 전송 후 흐른 시간". 그리고 함수 중간에서 거리/시야로 배수 조정돼:
  • 내가 보는 대상(ViewTarget)이거나 그 소유물 → Time *= 4.f (코드 :56)
  • 정면으로 똑바로 쳐다보는 중 → Time *= 2.f (:80)
  • 등 뒤 + 멀다 → Time *= 0.2f (:69)

NetPriority(고정 중요도) × Time(굶은 시간 × 거리·시야 보정) — 이 곱이 점수다.

여기가 이 설계의 묘수야. Time이 "굶은 시간"으로 계속 커지니까, NetPriority가 낮은 배경 액터도 오래 못 보내면 Time이 부풀어서 언젠가는 상위로 치고 올라온다. 기아 방지(starvation)가 공짜로 딸려온다. 우선순위 낮다고 영영 안 보내지는 게 아니야 — 뜸하게라도 반드시 차례가 온다.

점수가 다 매겨지면 정렬.

Runtime/Engine/Private/NetDriver.cpp:5476

// Sort by priority Algo::SortBy(MakeArrayView(OutPriorityActors, FinalSortedCount), &FActorPriority::Priority, TGreater<>());
🔤 정렬 기호 사전 — Algo::SortBy(...)
• Algo::SortBy = Algo 상자 안의 "정렬해줘" 함수. ::는 소속 표시야.
• MakeArrayView(...) = 배열 전체가 아니라 앞쪽 FinalSortedCount개만 보게 하는 창을 만든다.
• &FActorPriority::Priority = FActorPriority 안의 Priority 칸을 정렬 기준으로 삼겠다는 표시. 여기서 &는 그 멤버를 가리키는 표시야.
• TGreater<> = 큰 값이 먼저 오게 하는 비교 규칙.
• <> = 템플릿 자리. 타입을 넣는 꺾쇠칸인데, 여기선 기본 모양으로 둔 거야.

TGreater<> — 내림차순. 점수 높은 놈이 배열 앞에 온다. 이제 앞에서부터 보내기만 하면 돼.

[3] 예산 집행 — 대역폭 찰 때까지만

정렬된 순서대로 실제 전송에 들어간다(ProcessPrioritizedActorsRange, :5495). 여기서 "대역폭 예산"이 진짜로 집행되는데, 집행자는 우선순위가 아니라 연결의 포화 여부야.

Runtime/Engine/Private/NetDriver.cpp:5675

// second check for channel saturation if (!Connection->IsNetReady() && !bIgnoreSaturation) { // We can bail out now since this connection is saturated, we'll return how far we got though GNumSaturatedConnections++; return j; }
🔤 포화 체크 기호 사전 — if (!Connection->IsNetReady() && !bIgnoreSaturation)
• Connection->IsNetReady() = 이 연결이 지금 더 보낼 준비가 됐는지 물어보는 함수.
• !Connection->IsNetReady() = 보낼 준비가 안 됐으면. 즉 송신 쪽이 꽉 찼으면.
• && !bIgnoreSaturation = "그리고 포화를 무시하라는 옵션도 꺼져 있으면".
• GNumSaturatedConnections++ = 포화된 연결 수 카운터를 하나 올리기. ++는 1 증가야.
• return j = 여기서 함수를 멈추고, j번째까지 처리했다는 값을 돌려준다.
🔁 이제 다시 보자. IsNetReady()가 거짓이고 포화를 무시하지도 않으면, 이 연결은 이번 틱 예산을 다 쓴 거야. 그래서 GNumSaturatedConnections++로 표시만 남기고 return j로 즉시 빠져나간다. 아래쪽 액터들은 이번 틱 컷라인 밑으로 떨어진다.

IsNetReady()가 false면 — 이 연결 송신 버퍼가 이번 틱 예산을 다 썼다는 뜻. 그럼 남은 저우선순위 액터들은 미련 없이 버리고 return. return j로 "여기까지 보냈다"를 넘겨줘서 다음 처리에 쓴다.

이제 [2]의 정렬이 왜 중요했는지 보이지. 컷라인은 대역폭이 긋고, 그 컷라인 위에 누가 서 있을지를 [2]의 점수가 정한다. 포화가 오면 위에서부터 잘린 뒤 아래는 통째로 이번 틱 탈락.

그럼 탈락한 relevant 액터는 영영 못 보내나? 아니야. 포화로 못 보낸 놈은 ForceNetUpdate()류로 bPendingNetUpdate 플래그가 붙어서, 다음 틱엔 [1]의 시간 게이트(:5127)를 우회해 무조건 재고려된다. 스니펫 [1]의 !ActorInfo->bPendingNetUpdate 조건 기억나지? 이 플래그가 true면 "아직 시각 안 됐어도 skip 안 함". 시간 게이트와 기아 방지가 여기서 맞물린다.

우리 서버랑 비교 — IOCP vs 싱글스레드 액터 루프

조선 서버 감각으로 번역해보자.

우리 쪽은 IOCP 워커 여러 개가 각 소켓에 붙어서, 보낼 게 생기면 그 자리에서 WSASend로 밀어넣지. "누굴 먼저 보낼까"라는 전역 경쟁 개념이 딱히 없어 — 이벤트/패킷 단위로 각자 처리하니까. 대역폭 배분은 사실상 OS TCP 스택과 커널 버퍼에 맡기는 그림.

UE는 정반대야. 한 스레드(TickFlush)가 매 틱, 전 액터를 한 줄로 세워놓고 "이번 예산으로 위에서부터 몇 명" 하고 끊는다. 즉:

조선 서버 (IOCP)UE (ServerReplicate)
트리거이벤트/패킷 발생 시 push매 틱 전수 스캔 (pull)
누가 보낼지로직이 그때그때 결정매 틱 점수 정렬로 결정
자주 여부로직이 직접 판단NetUpdateFrequency가 시간 게이트
예산 집행OS/커널 버퍼에 위임IsNetReady() 컷라인 명시 집행
병렬성워커 N개연결 루프는 사실상 순차

핵심 차이 한 줄: 우리는 "보낼 이유가 생기면 보낸다"(push), UE는 "매 틱 후보를 줄 세워 예산만큼 자른다"(pull + budget). 그래서 UE엔 "우선순위 점수"라는 개념이 존재할 자리가 생기는 거야 — 줄을 세우는 순간 순번이 필요하니까. IOCP 모델엔 애초에 줄이 없어서 그 고민이 로직 쪽으로 흩어져 있지.

이 관점으로 보면 NetUpdateFrequency는 "이 액터를 얼마나 자주 그 줄에 세울지", NetPriority는 "줄에 섰을 때 앞자리를 얼마나 받을지"로 딱 떨어진다.

흔한 오해 정리

  • "NetPriority 높이면 더 자주 보내진다" → ✗. 우선순위는 포화 시 생존 경쟁용이야. 안 붐비면 우선순위 낮아도 다 나간다. "자주"는 NetUpdateFrequency 담당.
  • "NetPriority는 1등, 2등 순번이다" → ✗. 배수 가중치다. NetPriority * Time의 곱이라, Time(굶은 시간)이 커지면 낮은 우선순위도 역전한다.
  • "MinNetUpdateFrequency는 최소로 보장되는 빈도" → ✗. 가장 느릴 때의 하한(=대역폭 절약 바닥)이야. 이름과 반대로 "이보다 더 뜸해지진 않게" 막는 값.
  • "포화되면 우선순위 낮은 액터는 못 받는다" → ✗. bPendingNetUpdate가 붙어 다음 틱 우회 재고려된다. 뜸할 뿐 굶진 않아.

🎯 원리 한 줄 요약

갱신빈도(1/Freq)가 "얼마나 자주 후보에 올릴지"를 시간으로 잠그고, 우선순위(NetPriority × 굶은시간)가 "대역폭이 찰 때 누가 컷라인 위에 남을지"를 정한다 — 두 축이 좁은 문 앞의 배분을 나눠 맡는다.

막히면 → relevancy (애초에 후보가 되는 조건)
다음 → dormancy (안 변하는 액터는 아예 복제 정지)
← 이전관련성: 누구에게 보낼지 (Relevancy)다음 →Dormancy: 안 바뀌는 액터는 재운다
