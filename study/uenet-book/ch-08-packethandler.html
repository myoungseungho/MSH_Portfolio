PacketHandler: 암호화·압축·핸드셰이크의 관문

언리얼 네트워크 · 08 / 42

Phase 2 / 소켓과 게임로직 사이의 "검문소 줄" 막히면 → netconnection-overview · receive-callchain

0. 먼저 그림부터 — "공항 보안검색대"

너 공항 가봤지. 비행기 타기 전에 그냥 게이트로 못 걸어가. 줄을 서서 검문소를 순서대로 통과해야 해.

  1. 신분 확인 (이 사람 진짜 탑승객 맞아?)
  2. 짐 X-ray (안에 뭐 들었는지 풀어서 본다)
  3. 금속탐지 (몸에 이상한 거 없나)

그리고 내릴 때는? 정확히 반대 순서로 나와. 들어갈 때 A→B→C였으면 나올 때는 C→B→A.

네트워크 패킷도 똑같아. 소켓에서 게임 로직까지 그냥 직행 안 해. 중간에 검문소 줄이 있어:

  • 핸드셰이크 검문소: "너 진짜 우리 클라야? 아무나 접속 못 해"
  • 압축 검문소: 나갈 땐 짐 압축, 들어올 땐 압축 풀기
  • 암호화 검문소: 나갈 땐 봉인, 들어올 땐 봉인 해제

이 검문소 줄 전체를 관리하는 게 PacketHandler야. 검문소 하나하나는 HandlerComponent고.

핵심을 미리 한 문장으로 박아두자: "나가는 패킷은 안→바깥, 들어오는 패킷은 바깥→안. 양파 껍질처럼 순서가 정반대다." 왜 그런지, 그리고 이걸 코드 어디서 붙이고 어디서 통과시키는지 — 이번 챕터의 목표야.

🔬 정직 배너 — 이 클론엔 검문소 "내부"가 없다

먼저 솔직하게 짚고 간다. PacketHandler / HandlerComponent 클래스 본체는 UE의 Runtime/PacketHandlers/ 모듈에 있는데, 이 학습용 소스 subset엔 Runtime/Engine과 Runtime/Net만 들어있어. 그래서:

  • 검문소 줄을 실제로 도는 PacketHandler::Incoming/Outgoing 루프 본체
  • 암호화 컴포넌트가 실제로 AES를 돌리는 코드
  • 압축 컴포넌트 내부

이 세 개는 이 소스로는 못 읽어. 각색하거나 지어내지 않는다.

대신 — 엔진이 이 검문소 줄을 붙이고(조립), 통과시키고(호출), 켜는(암호화 ON) 통합 지점(call site)은 전부 실재하고, 아래 코드는 전부 그 실재 코드에서 한 글자도 안 바꾸고 뽑았어. 즉 "검문소 안에서 무슨 마법을 부리는지"는 개념으로, "검문소를 어디에 세우고 언제 줄 세우는지"는 verbatim 코드로 간다.

파일은 두 개다.

  • NetConnection.cpp — 검문소 줄을 세우고·통과시키고·암호화를 켜는 실제 호출부
  • PendingNetGame.cpp — 클라가 접속할 때 핸드셰이크를 시작하는 곳

1. 조립 — 커넥션이 태어날 때 검문소 줄을 세운다

검문소는 저절로 안 생겨. 커넥션(UNetConnection)이 초기화될 때 딱 한 번 세워져. 그 함수가 InitHandler()야 (NetConnection.cpp:694, InitBase가 526행에서 불러줌).

첫 스니펫. 검문소 줄의 관리자를 만들고, 줄 맨 끝 출구를 실제 소켓 송신 함수에 연결하는 부분이야.

Handler = MakeUnique<PacketHandler>(); if (Handler.IsValid()) { UE::Handler::Mode Mode = Driver->ServerConnection != nullptr ? UE::Handler::Mode::Client : UE::Handler::Mode::Server; FPacketHandlerNotifyAddHandler NotifyAddHandler; NotifyAddHandler.BindLambda([this](TSharedPtr<HandlerComponent>& NewHandler) { if (NewHandler.IsValid()) { NewHandler->InitFaultRecovery(GetFaultRecovery()); } }); Handler->InitializeDelegates(FPacketHandlerLowLevelSendTraits::CreateUObject(this, &UNetConnection::LowLevelSend), MoveTemp(NotifyAddHandler)); Handler->NotifyAnalyticsProvider(Driver->AnalyticsProvider, Driver->AnalyticsAggregator); Handler->Initialize(Mode, MaxPacket * 8, false, nullptr, nullptr, Driver->GetNetDriverDefinition());

— NetConnection.cpp:706–726

세 줄만 눈에 담자.

  • MakeUnique<PacketHandler>() (706행): 이 커넥션 전용 검문소 줄 하나 생성. 커넥션마다 자기 줄을 따로 소유해(TUniquePtr<PacketHandler> Handler;, NetConnection.h:444). 옆 커넥션이랑 안 섞여.
  • Mode (710행): 내가 클라냐 서버냐를 여기서 정해. Driver->ServerConnection이 있으면(=내가 서버에 붙은 클라면) Client, 아니면 Server. 같은 검문소라도 클라/서버 역할이 달라서 이걸 먼저 박아둬.
  • InitializeDelegates(... &UNetConnection::LowLevelSend ...) (722행): 검문소 줄의 최종 출구를 실제 소켓 송신 함수에 연결. 짐이 모든 검문소를 다 통과하면 이 함수로 나가서 소켓에 실린다.
잠깐 예측. Handler->Initialize에 MaxPacket * 8을 넘기는데(726행), 이 8은 뭘까? 맞춰봐. …정답: 바이트 → 비트 변환이야. 검문소들은 헤더를 비트 단위로 잘게 떼어 쓰거든(1비트짜리 플래그도 있음). 그래서 최대 패킷 크기를 바이트가 아니라 비트로 넘겨줘야 계산이 맞아. 뒤에서 "예약 비트" 얘기 나올 때 이게 다시 등장해.

2. 최외곽 검문소 — 무상태 핸드셰이크를 맨 바깥에 세운다

검문소 줄을 세웠으면 이제 검문소를 하나씩 쌓아. AddHandler로 쌓는데, 먼저 추가할수록 더 바깥 계층이야 (공항 입구에서 가장 먼저 만나는 검문소).

// Add handling for the stateless connect handshake, for connectionless packets, as the outermost layer TSharedPtr<HandlerComponent> NewComponent = Handler->AddHandler(TEXT("Engine.EngineHandlerComponentFactory(StatelessConnectHandlerComponent)"), true); StatelessConnectComponent = StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent); if (StatelessConnectComponent.IsValid()) { StatelessConnectHandlerComponent* CurComponent = StatelessConnectComponent.Pin().Get(); CurComponent->SetDriver(Driver); CurComponent->SetHandshakeFailureCallback([this](FStatelessHandshakeFailureInfo FailureInfo){this->OnStatelessHandshakeFailure(FailureInfo);}); } Handler->InitializeComponents(); MaxPacketHandlerBits = Handler->GetTotalReservedPacketBits();

— NetConnection.cpp:729–746

주석(729행)이 직접 말해줘: as the outermost layer — 가장 바깥 계층으로. 왜 핸드셰이크가 맨 바깥일까?

생각해봐. 아직 "진짜 클라인지도 모르는" 낯선 놈이 패킷을 던졌어. 이걸 압축 풀고 복호화하느라 CPU 쓰면 손해잖아. 그래서 문지기(핸드셰이크)를 맨 앞에 세워서, 검증 안 된 놈은 안쪽 검문소로 들이지도 않아. SYN-flood류 자원소모 공격 방어의 기본이야. (핸드셰이크 상세는 → handshake)

마지막 두 줄이 이번 챕터 후반의 복선이야.

  • InitializeComponents() (744행): 쌓아둔 검문소들 전부 초기화.
  • MaxPacketHandlerBits = Handler->GetTotalReservedPacketBits() (746행): 검문소들이 자기 헤더로 쓸 비트 총량을 커넥션이 받아 적어둬. 검문소가 헤더 자리를 먹으면 그만큼 게임 데이터가 쓸 공간이 줄거든. 이게 "예약 비트" — 뒤 §6에서 다시.

3. 수신 관문 — 소켓에서 올라온 원시 바이트를 줄에 태운다 (바깥→안)

이제 실제로 패킷이 들어올 때. 소켓에서 원시 바이트가 올라오면 ReceivedRawPacket(InData, Count) (NetConnection.cpp:2056)이 받아. 이 함수 안에서 검문소 줄에 통째로 밀어넣어:

if (Handler.IsValid()) { FReceivedPacketView PacketView; PacketView.DataView = {Data, Count, ECountUnits::Bytes}; EIncomingResult IncomingResult = Handler->Incoming(PacketView); if (IncomingResult == EIncomingResult::Success) { Count = PacketView.DataView.NumBytes(); if (Count > 0) { Data = PacketView.DataView.GetMutableData(); } // This packed has been consumed else { return; } }

— NetConnection.cpp:2084–2105

Handler->Incoming(PacketView) (2090행) 이 한 줄이 공항 입국 검문소 줄 전체야. 이 안에서 (우리 소스엔 없지만 개념상):

  1. 최외곽 핸드셰이크 검문소가 먼저 본다 → "핸드셰이크 패킷이면 여기서 먹어치우고 끝"
  2. 암호화 검문소 → 복호화
  3. 압축 검문소 → 압축 해제

그리고 결과가 재밌어. 주석 보이지? // This packed has been consumed (2100행). Count가 0이면 return으로 조용히 끝내. 무슨 뜻이냐면 — 핸드셰이크 패킷 같은 건 검문소가 먹어치우고 게임 로직엔 아무것도 안 올려. 게임 코드 입장에선 그런 패킷이 온 줄도 몰라. 검문소가 알아서 처리했으니까.

성공해서 실제 게임 데이터가 남았으면? 그 다음 Handler->IncomingHigh(Reader) (NetConnection.cpp:2182)를 거쳐 ReceivedPacket(Reader) (2187행)로 게임 채널에 전달돼. (여기서부터가 → receive-callchain의 세계)

Incoming vs IncomingHigh, 뭐가 달라? 같은 줄의 앞칸/뒷칸이야. Incoming은 소켓에 가장 가까운 바이트 단계(복호화·압축해제·핸드셰이크). IncomingHigh는 헤더·시퀀스가 붙는 비트리더 단계의 상위 처리. 들어올 땐 Incoming → IncomingHigh 순서.

실패하면? 2108~2127행에서 FaultRecovery로 복구 가능한지 보고, 복구 불가면 Close(...PacketHandlerIncomingError)로 커넥션을 끊어버려. 검문소에서 걸린 놈은 못 들어와.

4. 송신 관문 — 나갈 때는 반대 순서 (안→바깥)

들어올 때 봤으면 나갈 때도 봐야지. 누적된 송신 버퍼를 실제 패킷으로 마감하는 FlushNet() (NetConnection.cpp:~2338) 안에서, 헤더를 확정하기 직전에 상위 검문소가 개입해:

// @todo #JohnB: Since OutgoingHigh uses SendBuffer, its ReservedPacketBits needs to be modified to account for this differently if (Handler.IsValid()) { Handler->OutgoingHigh(SendBuffer); } const double PacketSentTimeInS = FPlatformTime::Seconds(); // Write the UNetConnection-level termination bit SendBuffer.WriteBit(1);

— NetConnection.cpp:2377–2386

Handler->OutgoingHigh(SendBuffer) (2380행) — 이게 출국 검문소의 상위 단계야. 아직 끝이 아니라는 게 포인트.

나가는 전체 순서는 이래:

  • OutgoingHigh (여기, 상위 비트라이터 단계) → …그 다음 최종 Handler->Outgoing(...) (바이트 단계, 최종 암호화/압축) → LowLevelSend(...)로 소켓 전송.

근데 그 최종 Outgoing→LowLevelSend 호출부는 이 subset에 없어. 구상 서브클래스 UIpConnection::LowLevelSend(소켓 드라이버 모듈)에 있는데 그 클래스가 여기 안 들어있거든. §1에서 봤듯이 UNetConnection::LowLevelSend는 델리게이트로만 연결돼(722행) 실제 몸통은 IP 커넥션에 있어. (→ ipnetdriver-socket)

정리하면 대칭이 이렇게 맞아:

수신: 소켓 → Incoming(바깥→안) → IncomingHigh → 게임로직 송신: 게임로직 → OutgoingHigh → Outgoing(안→바깥) → 소켓

양파 껍질. 들어올 땐 바깥 껍질부터 벗기고, 나갈 땐 안쪽부터 껍질을 입혀. 그래야 내가 씌운 순서 그대로 상대가 벗길 수 있어.

5. 암호화 켜기 — 검문소에서 암호화 컴포넌트를 찾아 스위치를 올린다

암호화는 접속하자마자 켜지는 게 아니야. 인증이 끝나고 "이제 암호 통신 시작" 신호가 왔을 때 켜져. 그 스위치가 EnableEncryption이야:

void UNetConnection::EnableEncryption(const FEncryptionData& EncryptionData) { if (Handler.IsValid()) { UE_LOG(LogNet, Verbose, TEXT("UNetConnection::EnableEncryption, %s"), *Describe()); TSharedPtr<FEncryptionComponent> EncryptionComponent = Handler->GetEncryptionComponent(); if (EncryptionComponent.IsValid()) { EncryptionComponent->SetEncryptionData(EncryptionData); EncryptionComponent->EnableEncryption(); } else { UE_LOG(LogNet, Warning, TEXT("UNetConnection::EnableEncryption, encryption component not found!")); }

— NetConnection.cpp:834–850

흐름이 딱 3단계라 외우기 쉬워.

  1. Handler->GetEncryptionComponent() (840행) — 검문소 줄에서 암호화 검문소를 콕 집어 꺼낸다. 커넥션은 암호화 세부를 몰라도 돼. "암호화 담당 컴포넌트 내놔" 하면 핸들러가 찾아줘.
  2. SetEncryptionData(EncryptionData) (843행) — 키를 꽂고
  3. EnableEncryption() (844행) — 스위치 ON

여기서 설계 감각 하나. 커넥션은 AES가 뭔지, 키 길이가 몇 비트인지 하나도 몰라. 그냥 "암호화 컴포넌트야, 이 데이터로 켜져" 하고 위임할 뿐. 암호화 알고리즘을 갈아끼워도 이 코드는 한 글자도 안 바뀌어. 검문소를 컴포넌트로 쪼갠 이유가 이거야.

컴포넌트가 없으면(else, 846행)? 크래시 안 나고 Warning 로그만 찍고 넘어가. 암호화 없이도 게임은 돌아가니까(개발 환경 등).

서버측은 한 단계 더 있어: EnableEncryptionServer → SendClientEncryptionAck()로 클라에 NMT_EncryptionAck를 보내고 → EnableEncryption (NetConnection.cpp:853~872). "나 이제 암호화 켠다, 너도 켜"를 클라에 알려주고 켜는 거야. 양쪽이 동시에 켜야 대화가 되니까.

6. 예약 비트 — 검문소가 자리를 먹으면 짐 넣을 공간이 준다

§2 마지막의 복선 회수. MaxPacketHandlerBits = Handler->GetTotalReservedPacketBits() (746행) 이거.

한 패킷의 크기는 정해져 있어(MTU 때문에). 그 안에 검문소들이 자기 헤더를 욱여넣으면 — 시퀀스 번호, 핸드셰이크 플래그, 암호화 IV 등 — 그만큼 게임 데이터가 쓸 공간이 줄어.

그래서 커넥션은 미리 계산해둬: "게임 페이로드 최대치 = MaxPacket*8 − 검문소들이 예약한 비트"(NetConnection.cpp:2035, .h:1345 참조). 검문소를 하나 추가할 때마다 이 예약량이 늘고, 게임이 한 패킷에 실을 수 있는 실데이터가 줄어드는 트레이드오프야. 공짜 보안은 없어. 검문소 하나마다 짐칸이 조금씩 좁아진다.

7. 호출 순서 다이어그램 (조립 → 수신 → 송신 → 핸드셰이크)

8. 우리 서버랑 비교 — IOCP 워커 + 싱글스레드 액터

우리 조선협객전 서버(C++ IOCP) 관점에서 보면 이 구조가 확 와닿아.

우리 서버:

  • IOCP 워커 스레드가 WSARecv 완료 통지를 받으면, 원시 바이트가 손에 들어와. 근데 이게 바로 게임 로직 큐로 안 가.
  • 우리도 중간에 복호화 → (패킷 조립) → 검증 단계를 태워. 완성된 패킷만 싱글스레드 액터(게임 로직 스레드)의 처리 큐에 올려.
  • 게임 로직은 단일 스레드라 "온전한 패킷 하나"만 순서대로 처리하면 돼. 워커가 지저분한 바이트 처리를 다 흡수해주니까.

UE PacketHandler에 대응시키면:

우리 서버 (IOCP)UE
IOCP 워커의 recv 후처리(복호화/조립)Handler->Incoming() (바깥→안)
완성 패킷을 게임 큐에 pushReceivedPacket() → 게임 채널
게임 로직 → send 전 암호화/직렬화Handler->OutgoingHigh → Outgoing (안→바깥)
접속 시 인증 핸드셰이크 후 데이터 허용StatelessConnectHandlerComponent → SendInitialJoin

결정적 차이 하나: 우리 서버는 검문 단계가 대체로 손코딩된 고정 파이프라인이야("복호화 함수 부르고, 그 다음 검증 함수 부르고…"). UE는 그걸 HandlerComponent 스택으로 데이터화했어. AddHandler로 검문소를 런타임에 끼웠다 뺐다 하고, 순서(바깥/안)가 스택 위치로 결정돼. 유연한 대신 예약 비트 회계(§6) 같은 부가 복잡도가 붙는 트레이드오프고 — 우리 IOCP 방식은 단순·빠른 대신 검문 단계 바꾸려면 코드를 고쳐야 해. 어느 쪽이 낫다기보다, "고정 파이프라인 vs 데이터화된 스택"의 취향 차이로 이해하면 돼.

9. 헷갈리는 용어 4개 (짧게)

  • PacketHandler: 한 커넥션에 붙는 "검문소 줄" 관리자. 소켓↔게임로직 사이에서 나가는 패킷은 안→바깥, 들어오는 패킷은 바깥→안 순서로 각 계층을 통과시킨다(양파 껍질). UNetConnection이 TUniquePtr<PacketHandler> Handler로 하나씩 소유(NetConnection.h:444).
  • HandlerComponent: 검문소 하나(암호화·압축·무상태 핸드셰이크 등). 각자 Incoming/Outgoing을 구현하고 자기 헤더용 비트를 예약. AddHandler로 쌓이며, 먼저 추가될수록 더 바깥.
  • StatelessConnectHandlerComponent: 최외곽 무상태 핸드셰이크 계층. 서버가 접속마다 메모리를 잡지 않고(쿠키/토큰 방식) 진짜 클라인지 검증해 SYN-flood류 공격을 막는다. 이게 끝나야 서버가 실제 데이터를 보냄. (→ handshake, security)
  • ReservedPacketBits / MaxPacketHandlerBits: 검문소들이 자기 헤더로 쓸 비트 예약량. 게임 페이로드 최대치 = MaxPacket*8 − 이 값(NetConnection.cpp:2035). 검문소를 더할수록 짐칸이 줄어드는 트레이드오프의 근거.

🎯 원리 한 줄 요약

PacketHandler는 소켓과 게임로직 사이의 검문소 줄이다 — 나갈 땐 안에서 바깥으로 껍질을 입히고(OutgoingHigh→Outgoing), 들어올 땐 바깥에서 안으로 껍질을 벗기며(Incoming→IncomingHigh), 최외곽 핸드셰이크를 통과한 놈만 진짜 데이터를 주고받는다.
