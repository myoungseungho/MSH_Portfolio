RPC는 어느 연결로 가나: 소유권

언리얼 네트워크 · 23 / 43

왜 이걸 배워? — 문제의식부터

네가 게임 서버를 짜봤으면 이 고민을 이미 해봤어. SP_* 패킷을 클라한테 보낼 때, 서버는 항상 "이걸 누구한테 보내지?"를 먼저 정해야 해. CChosunPlayer가 들고 있는 세션으로 보낼지, 주변 사람들에게 뿌릴지, 아니면 아무에게도 보내면 안 되는지 말이야.

이 판단이 없으면 바로 사고가 난다. A 유저가 강화 성공 UI를 봐야 하는데 B 유저한테 CM_*가 가거나, 파티 초대 응답이 엉뚱한 소켓으로 나가거나, 주인 없는 오브젝트가 서버 RPC를 쏴서 서버가 "이거 누구 요청인데?" 하고 조용히 씹어버린다. 100명이 붙어 있는 서버에서 주소 없는 패킷은 택배 송장 없는 상자랑 같아. 창고에 쌓이거나, 더 나쁘면 남의 집으로 간다.

우리 조선 서버에서는 보통 CChosunPlayer나 세션 객체가 답을 준다. IOCP 워커가 바이트를 받아도, 결국 단일스레드 게임 로직으로 넘겨서 "이 요청은 어떤 플레이어의 것인가"를 확인하고 처리하지. 락을 많이 걸어서 아무 데나 직접 만지는 게 아니라, 소유한 플레이어와 그 큐를 기준으로 안전하게 흘려보내는 식이야.

언리얼도 같은 문제를 만났고, 그 답이 바로 RPC 소유권(Ownership) 이야. RPC는 함수처럼 보이지만, 네트워크로 나가려면 결국 UNetConnection이라는 목적지가 필요해. UE는 그 목적지를 액터의 Owner 사슬을 타고 올라가며 찾고, 끝에서 만나는 PlayerController의 커넥션을 주소로 삼는다.

그래서 이 챕터는 "RPC를 어떻게 선언하나" 다음에 와야 해. 앞에서 RPC 종류를 배웠다면 이제는 더 중요한 질문, 그 RPC가 실제로 어느 연결로 가는가를 잡을 차례야. 이걸 알아야 Client RPC가 왜 어떤 액터에서는 잘 가고 어떤 액터에서는 버려지는지, Server RPC가 왜 소유 클라에서만 의미가 있는지 납득된다.

지금 여기서 소유권을 잡아두면 뒤의 코드가 훨씬 덜 무섭다. GetFunctionCallspace는 "보낼지 말지"를 정하고, GetNetConnection은 "보낸다면 누구에게 보낼지"를 정한다. 즉 이번 챕터는 RPC 문법과 실제 소켓 사이에 붙는 주소 찾기 규칙을 배우는 장이다.

편지를 부치는데 주소가 없다면

택배를 하나 부친다고 해보자. 상자는 다 쌌어. 그런데 "어디로 보내지?" 가 안 정해졌으면 이 상자는 창고에 그냥 쌓여. 버려지지도, 배달되지도 않고.

RPC(원격 함수 호출)도 똑같아. 서버에서 클라한테 이거 실행시켜 하고 함수를 부르면, 엔진은 두 가지를 순서대로 정해야 돼.

  1. 방향 — 이 호출을 *여기서* 그냥 실행할까(Local), *원격*으로 보낼까(Remote), 아니면 *조용히 버릴까*(Absorbed)?
  2. 주소 — 원격으로 보낸다면, 수많은 클라 소켓 중 정확히 누구의 소켓으로 보내지?

이 두 판정을 실제로 구현하는 게 이 챕터의 주인공, GetFunctionCallspace(방향)와 GetNetConnection(주소)이야. 그리고 주소를 정하는 열쇠가 바로 소유권(Ownership) 이다.

전제 두 개는 링크로 넘긴다 — RPC가 뭔지, 몇 종류인지는 → rpc-types / 커넥션 객체가 뭔지는 → netconnection-overview. 여기선 "이미 RPC 하나를 쏘기로 했다"는 지점부터 시작해.

지금부터 진짜 언리얼 코드가 나와. 겁먹지 마 — 낯선 기호는 코드 바로 아래 🔤 상자에서 하나씩 풀어줄게. 코드를 외우는 게 아니라 "아, 주소를 이렇게 찾는구나"만 잡으면 돼.

🌱 이 개념은 왜 생겼나 — 소유권으로 주소 찾기(Owner 사슬)
• 원래 구조: RPC를 클라한테 보내려면 "어느 소켓으로 보낼지" 주소가 있어야 해.
• 그런데 문제: 액터마다 "너는 누구 소켓으로 가"를 적은 라우팅 표를 따로 만들면, 스폰·소멸할 때마다 그 표를 손으로 맞춰야 하고 하나 어긋나면 남의 집으로 택배가 가.
• 그래서 필요한 것: 액터가 스스로 Owner 포인터를 들고, 주소를 물으면 주인한테 떠넘기며 재귀로 위로 올라가기. 무기→캐릭터→PlayerController까지 올라가면 그 PC의 커넥션이 곧 주소야. → 그게 소유권이야. 조선 서버가 캐릭터 인덱스로 세션 테이블 뒤지던 걸, UE는 오브젝트 그래프 자체로 푸는 거지.

1. 주소는 Owner를 타고 올라간다

먼저 주소부터. UE에서 모든 액터는 Owner 포인터를 하나 들 수 있어. 그리고 "이 액터의 커넥션(소켓)이 뭐냐"를 물으면, 엔진은 자기가 답을 모른다. 대신 주인한테 떠넘긴다.

스니펫 A — 소유권 체인의 뿌리 (Actor.cpp:1930)

UNetConnection* AActor::GetNetConnection() const { return Owner ? Owner->GetNetConnection() : nullptr; }
🔤 기호 사전 — return Owner ? Owner->GetNetConnection() : nullptr;
• UNetConnection* = UNetConnection을 가리키는 주소표. 진짜 커넥션 물건을 복사하는 게 아니라 "저기 있다"는 포인터야.
• AActor:: = GetNetConnection이 AActor 소속 함수라는 표시. ::는 "~ 안의"라고 읽으면 돼.
• const = 이 함수가 액터 내용을 바꾸지 않겠다는 약속.
• return = 함수가 답을 내놓고 끝난다는 뜻.
• Owner ? A : B = Owner가 있으면 A, 없으면 B를 고르는 짧은 if문.
• -> = 포인터가 가리키는 주인한테 "네 함수 좀 실행해" 하고 시키는 화살표.
• nullptr = 아무것도 안 가리키는 빈 주소. 즉 "보낼 커넥션 없음".
🔁 이제 다시 보자. UNetConnection*(커넥션 주소표를 돌려줌) → AActor::GetNetConnection(액터의 주소 찾기 함수) → Owner ? Owner->GetNetConnection() : nullptr(주인이 있으면 주인한테 물어보고, 없으면 빈 주소). 한 줄로 "내 주소를 모르면 Owner에게 넘기고, Owner도 없으면 주소 없음."

이게 전부야. "내 커넥션? 몰라. 내 주인(Owner)한테 물어봐." 주인도 또 자기 주인한테 물어봐. 재귀로 계속 위로 올라가. 무기 → 그 무기를 든 캐릭터 → 그 캐릭터를 조종하는 PlayerController… 이렇게 사슬을 타고 오른다.

그럼 이 재귀는 어디서 멈추지? 한번 맞춰봐 — 무한히 올라가진 않을 텐데.

스니펫 B — 체인의 종착: PlayerController (PlayerController.cpp:283)

UNetConnection* APlayerController::GetNetConnection() const { // A controller without a player has no "owner" return (Player != NULL) ? NetConnection : NULL; }
🔤 기호 사전 — return (Player != NULL) ? NetConnection : NULL;
• APlayerController:: = 이 함수가 PlayerController 소속이라는 뜻. 소유권 사슬의 끝 후보야.
• // = 컴퓨터가 실행하지 않는 사람용 메모.
• Player != NULL = Player가 빈칸이 아닌지 확인. !=는 "같지 않다".
• NULL = 예전식 빈 주소 표기. 여기서는 nullptr처럼 "없음"으로 읽으면 돼.
• ? : = 앞 조건이 참이면 왼쪽(NetConnection), 거짓이면 오른쪽(NULL)을 고르는 축약문.

여기서 멈춘다. PlayerController는 Owner한테 떠넘기지 않고 자기가 들고 있는 NetConnection을 직접 내놓는다. 반전 포인트 하나 — 무조건 내놓는 게 아니라 Player가 있을 때만. Player가 붙어있다는 건 "이 PC는 실제 사람(클라 연결)이 조종 중"이라는 뜻이거든. AI가 굴리는 봇 PC라면 Player가 없고, 그럼 NULL이 나와서 "이 액터한테 보낼 클라 소켓은 없다"가 된다.

정리하면 주소 사슬은 이렇게 귀결돼:

내 총(무기 액터) │ Owner ▼ 내 캐릭터(Pawn) │ Owner ▼ 내 PlayerController ──► NetConnection (내 클라의 소켓!)

"Server RPC가 소유 연결로 간다"의 정체가 이거다. 특별한 라우팅 테이블 같은 게 있는 게 아니라, Owner를 타고 올라가다 만나는 PC의 커넥션 — 그게 곧 목적지야.

2. 방향은 Role과 플래그가 정한다

주소를 구하기 *전에*, 애초에 "원격으로 보낼 상황이 맞나"를 판정해야 돼. 이걸 GetFunctionCallspace(Actor.cpp:5412)가 한다.

핵심 재료 두 개:

  • bIsServer (Actor.cpp:5492) — 지금 이 머신이 서버냐(리슨/데디). RPC 방향의 기준선.
  • FUNC_NetServer / FUNC_NetClient — 함수에 붙은 방향 플래그. Server로 선언했으면 NetServer(클라→서버), Client면 NetClient(서버→클라).

스니펫 D — 단방향 RPC 방향 판정 (Actor.cpp:5522)

if (Function->FunctionFlags & (FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast)) { // Handle uni-directional RPCs // if we are the server, and it's not a send-to-client function, if (bIsServer && !(Function->FunctionFlags & FUNC_NetClient)) { // don't replicate DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Server calling Server function: %s %s"), *Function->GetName(), FunctionCallspace::ToString(Callspace)); return Callspace; }
🔤 기호 사전 — if (Function->FunctionFlags & (FUNC_NetServer | FUNC_NetClient | FUNC_NetMulticast))
• if = "만약 이 조건이 맞으면 안으로 들어가라"는 문.
• Function->FunctionFlags = 이 함수에 붙은 깃발 목록을 꺼내 보는 것. Server RPC인지 Client RPC인지 같은 표시가 여기 들어있어.
• & = 비트 AND. 깃발 목록 안에 특정 깃발이 꽂혀 있나 검사할 때 써.
• | = 비트 OR. FUNC_NetServer, FUNC_NetClient, FUNC_NetMulticast 중 아무거나 하나라도 보겠다고 묶는 표시.
• && = 양쪽 조건이 둘 다 참이어야 한다는 뜻.
• ! = "아니다"로 뒤집기. !(... & FUNC_NetClient)는 "Client RPC 깃발이 아니다".
• DEBUG_CALLSPACE(...) = 지금 어떤 판정을 했는지 개발자가 보라고 남기는 디버그 기록.
• TEXT("...") = 문자열을 UE가 쓰는 텍스트 형태로 감싸는 매크로.
• *Function->GetName() = 함수 이름을 로그가 찍을 수 있는 글자 포인터 형태로 꺼내는 표현.
🔁 이제 다시 보자. 첫 if는 "이 함수가 네트워크 RPC 깃발을 달았나?"를 보고, 안쪽 if는 bIsServer(지금 서버임) + !FUNC_NetClient(클라로 보내는 함수가 아님)를 본다. 이어 읽으면 "서버가 서버용 RPC를 부른 거면 네트워크로 보내지 말고 여기서 끝낸다."

읽는 법: "서버인데, 클라로 보내는 함수(NetClient)가 아니다" → 원격 송신 안 함. 왜? 서버가 Server RPC를 부르면 그건 이미 자기가 권한자니까 여기서 그냥 실행하면 돼(굳이 네트워크로 자기한테 보낼 이유 없음). 반대로 클라가 Server RPC를 부르면 이 조건에 안 걸리고 계속 진행 → 원격 후보가 된다.

그다음, 원격 후보가 됐으면 권한과 소유 커넥션을 확인한다.

스니펫 C — Authority + 소유 커넥션 판정 (Actor.cpp:5549)

// Check if the actor can potentially call remote functions if (LocalRole == ROLE_Authority) { UNetConnection* NetConnection = GetNetConnection(); if (NetConnection == nullptr) { UPlayer *ClientPlayer = GetNetOwningPlayer(); if (ClientPlayer == nullptr) { // Check if a player ever owned this (topmost owner is playercontroller or beacon) if (HasNetOwner()) { // Network object with no owning player, we must absorb DEBUG_CALLSPACE(TEXT("GetFunctionCallspace Client without owner absorbed %s"), *Function->GetName()); return FunctionCallspace::Absorbed;
🔤 기호 사전 — if (LocalRole == ROLE_Authority) ... return FunctionCallspace::Absorbed;
• LocalRole == ROLE_Authority = 이 머신에서 이 액터가 권한자인지 확인. ==는 "같다".
• UNetConnection* NetConnection = 커넥션을 가리킬 수 있는 포인터 변수. 소켓 주소를 담을 빈 칸이라고 보면 돼.
• GetNetConnection() = §1에서 본 것처럼 Owner 사슬을 타고 목적지 커넥션을 찾는 함수.
• nullptr = 못 찾았다, 빈 주소다.
• UPlayer *ClientPlayer = 클라 플레이어를 가리키는 포인터. *는 "이건 진짜 물건이 아니라 주소표"라는 표시.
• HasNetOwner() = 네트워크상 주인 흔적이 있는지 묻는 함수.
• FunctionCallspace::Absorbed = FunctionCallspace라는 판정표 안의 Absorbed 값. 실행도 송신도 안 하는 "흡수" 판정이야.
🔁 이제 다시 보자. LocalRole == ROLE_Authority(권한자가 판단 중) → GetNetConnection()(주소 찾기) → NetConnection == nullptr(주소 없음) → ClientPlayer == nullptr(플레이어도 없음) → HasNetOwner()(네트워크 주인 흔적은 있음) → Absorbed. 한 줄로 "보낼 듯한 RPC인데 실제 소켓 주소가 없으면 조용히 삼킨다."

여기서 §1의 GetNetConnection()이 다시 불려. 소유 커넥션이 nullptr이면 — 즉 주소가 없으면 — 갈 곳이 없으니 Absorbed(흡수), 조용히 삼킨다. "내 RPC가 아무 반응이 없어요"의 대표 원인이 바로 이거야. Owner를 안 붙여줘서 커넥션 사슬이 nullptr로 끝난 거지.

커넥션이 멀쩡히 있으면 마지막 관문:

  • RemoteRole == ROLE_None(Actor.cpp:5597) 이면 → 애초에 복제 대상이 아니라 Absorbed.
  • 다 통과하면 Actor.cpp:5609에서 FunctionCallspace::Remote 반환. "원격으로 보내라" 확정.
용어 3개만 짚고 가자. LocalRole==ROLE_Authority = "이 머신에서 내가 이 액터의 진짜 주인(권한자)이다". Absorbed = 실행도 송신도 안 하고 소리 없이 버림. Callspace = 이 세 갈래(Local/Remote/Absorbed)의 판정 결과값, RPC 한 번의 운명.
🌱 이 개념은 왜 생겼나 — 클라는 무조건 서버 커넥션으로(ServerConnection)
• 원래 구조: §1에서 Owner 사슬로 소유 커넥션을 구했으니, 그 커넥션으로 그냥 부치면 되잖아.
• 그런데 문제: 내가 클라일 땐 소유 커넥션이 누구를 가리키든 상관없이 목적지는 언제나 유일한 서버 하나뿐이야. 클라는 서버로 가는 길 하나(ServerConnection)만 갖고 있거든.
• 그래서 필요한 것: 클라에선 방금 구한 주소를 무시하고 ServerConnection으로 덮어써 무조건 서버로 몰기. 서버가 Client RPC 보낼 땐 이게 없으니 그 클라의 소유 커넥션이 그대로 목적지가 돼. 주소가 아예 없으면? 경고 찍고 조용히 드롭.

3. Remote가 나오면 NetDriver가 실제로 부친다

GetFunctionCallspace가 Remote를 뱉었어. 이제 진짜로 소켓에 실어야지.

스니펫 F — NetDriver로 넘기는 진입점 (Actor.cpp:5613)

🔤 기호 사전 — Connection = Actor->GetNetConnection();
• Connection = ... = 오른쪽에서 찾은 값을 왼쪽 변수에 담는 대입.
• Actor->GetNetConnection() = 이 액터의 Owner 사슬을 타고 목적지 커넥션을 다시 찾는다.
• if (Connection) = Connection이 빈 주소가 아니면, 즉 보낼 소켓이 있으면 안으로 들어간다.
• ServerConnection = 클라이언트가 서버로 가기 위해 들고 있는 단 하나의 연결.
• InternalProcessRemoteFunction(...) = RPC 데이터를 실제 전송 쪽으로 넘기는 내부 함수. 여기까지 와야 진짜로 부칠 준비가 된다.
• else = 위 조건이 아니면, 여기서는 커넥션이 없으면.
• UE_LOG(LogNet, Warning, TEXT(...)) = 네트워크 로그에 경고를 남긴다. Warning이라 게임을 바로 죽이진 않고 "이 RPC는 처리 안 됐다"고 알려준다.
🔁 이제 다시 보자. Connection = Actor->GetNetConnection()(Owner 사슬로 주소 찾기) → if (Connection)(주소 있으면) → if (ServerConnection)(클라라면 서버 주소로 덮어쓰기) → InternalProcessRemoteFunction(...)(그 주소로 RPC 부치기) → else UE_LOG(...)(주소 없으면 경고만 찍고 드롭). 결국 "주소 있으면 보내고, 클라에서는 무조건 서버 연결로 보낸다."

여기 똑똑한 반전이 하나 숨어있어. 방금 §1에서 GetNetConnection()으로 소유 커넥션을 구했는데, 바로 다음 줄(8057~8060)에서 ServerConnection이 있으면 그걸로 덮어써버린다.

왜? ServerConnection이 존재한다 = "지금 이 머신은 클라이언트다"(클라는 서버로 향하는 커넥션 딱 하나만 가짐). 클라 입장에서 Server RPC의 목적지는 언제나 유일한 서버. 그러니 소유 커넥션이 누구든 상관없이 무조건 서버 커넥션으로 몰아준다. 반대로 서버에서 Client RPC를 보낼 땐 ServerConnection이 없으니까, §1에서 구한 그 클라의 소유 커넥션이 그대로 목적지가 돼.

커넥션이 nullptr이면? else 가지에서 경고 로그 찍고 드롭. 흡수랑 결과는 같아 — 아무 일도 안 일어남.

우리 서버랑 비교하면

조선 서버는 IOCP 워커 스레드가 클라 소켓을 물고 있지. 유저한테 패킷 보낼 때 우리는 이렇게 해 — 세션 객체(CClientPtr 류)를 찾아서 그 안의 소켓 핸들로 WSASend. 즉 "보낼 대상 세션을 먼저 손에 쥐고, 그 세션의 소켓으로 쏜다." 대상 세션을 어떻게 찾느냐? 우리는 보통 캐릭터/유저 인덱스로 세션 테이블을 직접 조회하지.

UE의 GetNetConnection()이 하는 일이 정확히 이 "대상 세션 찾기" 야. 다만 우리처럼 테이블을 인덱스로 뒤지는 게 아니라, Owner 포인터를 재귀로 타고 올라가 세션(=NetConnection)을 찾는다. 액터가 곧 게임 오브젝트이자 "누구 소유인지"를 스스로 아는 구조라, 별도 매핑 테이블 없이 오브젝트 그래프 자체가 라우팅 정보를 품고 있는 셈이야.

또 하나 — 우리 게임 로직은 싱글 스레드 액터 루프에서 돌잖아. 워커 스레드가 받은 패킷을 큐에 넣고, 메인 로직 스레드가 순서대로 꺼내 처리하는 그 구조. UE의 RPC도 결국 수신 측에선 커넥션이 받은 번치를 풀어 해당 액터 위에서 함수를 실행하는데, 이 실행이 게임 스레드에서 벌어진다는 점이 우리 "IOCP 수신 → 로직 스레드 실행"과 판박이야. 라우팅(어느 소켓)은 네트워크 레이어, 실행(어느 스레드)은 로직 레이어 — 이 분리가 양쪽 다 똑같다.

차이 한 줄: 우리는 "인덱스로 세션 조회", UE는 "Owner 재귀로 커넥션 조회". 발상은 같고 자료구조만 다르다.

자주 밟는 함정

  • Owner를 안 붙였다 → GetNetConnection()이 nullptr → Server/Client RPC가 Absorbed 또는 drop. "RPC가 조용해요"의 1순위 원인. 스폰할 때 SetOwner(내PC) 빠졌는지부터 봐.
  • Client RPC를 소유 안 한 PC 액터에서 → 그 클라한테만 가야 하는데 Owner가 딴 데면 엉뚱한 사람한테 가거나 흡수됨.
  • RemoteRole == ROLE_None → 복제 자체가 꺼진 액터. Actor.cpp:5597에서 흡수. 복제 설정부터 확인.

Q1. RPC 소유권(Ownership)이 왜 필요한 개념인가요?

답 보기
RPC는 함수처럼 보이지만 네트워크로 나가려면 결국 목적지 커넥션(소켓)이 필요해. 상자는 다 쌌는데 "어디로 보내지?"가 안 정해지면 창고에 쌓이거나 남의 집으로 가버려. 특히 Client RPC는 "하필 그 한 명"한테만 가야 하는데, 그 한 명을 어떻게 찾느냐가 소유권 문제야. 조선 서버로 치면 "이 SP_를 누구 세션으로 보낼지" 정하는 것과 똑같아.

↳ 그 주소를 어떻게 찾나요? 라우팅 테이블이 따로 있나요?

답 보기
테이블이 아니라 Owner 사슬을 재귀로 타고 올라가. 액터한테 "네 커넥션 뭐냐" 물으면 자기는 몰라 — 대신 자기 주인한테 떠넘겨. 무기 → 그 무기를 든 캐릭터 → 그 캐릭터를 조종하는 PlayerController… 이렇게 올라가다 만나는 PC의 커넥션이 곧 주소야. 액터가 곧 게임 오브젝트이자 "누구 소유인지"를 스스로 아는 구조라, 별도 매핑 테이블 없이 오브젝트 그래프 자체가 라우팅 정보를 품고 있는 셈이지.

↳ 그 재귀는 어디서 멈추나요?

답 보기
PlayerController에서 멈춰. PC는 주인한테 안 떠넘기고 자기가 들고 있는 NetConnection을 직접 내놔. 단 조건이 있어 — 실제 사람(Player)이 붙어 있을 때만. AI가 굴리는 봇 PC는 Player가 없어서 "보낼 클라 소켓 없음"이 나와. "Server RPC가 소유 연결로 간다"의 정체가 이거야. 특별한 라우팅이 아니라 그냥 Owner 타고 오른 PC의 커넥션.

Q2. 방향과 주소는 각각 뭐가 정하나요?

답 보기
역할이 갈려. 방향(여기서 실행/원격 전송/버림)은 GetFunctionCallspace가 LocalRole·RemoteRole과 Server/Client 플래그를 보고 정하고, 주소(원격이면 누구에게)는 GetNetConnection이 Owner 사슬로 정해. "보낼지 말지"랑 "보낸다면 누구에게"는 다른 판정이야. 이 둘이 순서대로 물려서 RPC 하나의 운명이 정해져.

↳ Owner를 안 붙이면 어떻게 되나요? "RPC가 조용해요"의 원인이 이건가요?

답 보기
그게 1순위 원인이야. Owner를 안 붙이면 GetNetConnection()이 사슬 끝에서 nullptr로 끝나. 갈 곳이 없으니 Absorbed(흡수) — 실행도 송신도 안 하고 조용히 삼켜. "내 RPC가 아무 반응이 없어요"의 대표 원인이지. 스폰할 때 SetOwner(내PC) 빠졌는지부터 봐야 해.

Q3. 서버가 소유 커넥션을 구했는데, 클라에서는 왜 그걸 무시하고 덮어쓰나요?

답 보기
클라는 목적지가 언제나 하나뿐이라서야. 내가 클라일 땐 소유 커넥션이 누굴 가리키든 상관없이 갈 곳은 유일한 서버야. 클라는 서버로 가는 길(ServerConnection) 하나만 갖고 있거든. 그래서 방금 구한 주소를 무시하고 서버 커넥션으로 덮어써서 무조건 서버로 몰아. 반대로 서버가 Client RPC 보낼 땐 ServerConnection이 없으니, 아까 구한 그 클라의 소유 커넥션이 그대로 목적지가 돼.

↳ 그럼 주소가 아예 없으면요? Absorbed랑 뭐가 다른가요?

답 보기
결과는 같아 — 아무 일도 안 일어나. 넷드라이버 단계까지 왔는데 커넥션이 없으면 경고 로그 찍고 그냥 드롭해. Absorbed는 판정 단계에서 삼키는 거고 이건 라우팅 단계에서 떨어지는 건데, 유저 입장에선 둘 다 "RPC가 조용히 사라짐"으로 똑같이 보여.

Q4. 이 구조가 우리 조선 서버의 세션 조회랑 어떻게 대응되나요?

답 보기
발상은 같고 자료구조만 달라. 우리는 유저한테 패킷 보낼 때 세션 객체를 찾아서 그 안의 소켓 핸들로 WSASend 하잖아. 대상 세션은 캐릭터/유저 인덱스로 세션 테이블을 직접 조회하지. UE의 GetNetConnection()이 하는 일이 정확히 이 "대상 세션 찾기"야. 다만 인덱스로 테이블을 뒤지는 게 아니라 Owner 포인터를 재귀로 타고 올라가 커넥션을 찾는 거지. 한 줄로: 우리는 "인덱스로 세션 조회", UE는 "Owner 재귀로 커넥션 조회".

↳ 실행되는 스레드 관점도 우리랑 비슷한가요?

답 보기
판박이야. 우리는 워커 스레드가 받은 패킷을 큐에 넣고 메인 로직 스레드가 순서대로 꺼내 처리하잖아. UE도 수신 측에선 커넥션이 받은 번치를 풀어 해당 액터 위에서 함수를 실행하는데, 이 실행이 게임 스레드에서 벌어져. 라우팅(어느 소켓)은 네트워크 레이어, 실행(어느 스레드)은 로직 레이어 — 이 분리가 양쪽 다 똑같아.
