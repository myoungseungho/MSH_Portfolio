1000명을 감당한다: ReplicationGraph

언리얼 네트워크 · 27 / 42

들어가기 전에: 반장이 모두에게 "옆자리 누구야?"를 물으면

교실에 학생이 30명 있어. 선생님이 자리 배치를 하려고 "각자 자기 주변에 누가 앉았는지 알아야 해"라고 해. 순진하게 하면 어떻게 될까? 학생 한 명이 나머지 29명을 전부 둘러보고 "얘는 가깝나? 멀나?"를 판정해. 30명이 각자 29명을 훑으니 30 × 29 ≈ 900번 비교야.

이제 30명이 아니라 1000명이라고 해봐. 1000 × 999 ≈ 100만 번. 인원이 2배 늘면 계산은 4배로 뛰어. 이게 그 유명한 N×M 폭발(O(N²))이야.

그런데 교실 바닥에 격자무늬 타일을 깔고 "너는 네가 밟고 선 타일하고, 딱 붙은 옆 타일만 보면 돼"라고 규칙을 바꾸면? 학생 한 명이 훑는 대상이 999명에서 타일 몇 칸 안의 서너 명으로 확 줄어. 전체 계산이 O(N²)에서 거의 O(N)으로 내려앉아.

게임 서버가 매 프레임 하는 "이 액터를 이 플레이어한테 보내야 하나?"(관련성, relevancy) 판정이 정확히 그 900번 / 100만 번짜리 문제야. 전통 경로(server-replicate-actors)는 매 프레임 전체 액터를 훑어. 100명까지는 버텨. 1000명이 되면 못 버텨.

이 "타일 깔기"를 실제로 구현한 게 이 챕터의 주인공, UReplicationGraphNode_GridSpatialization2D야. 월드를 CellSize 간격 격자로 쪼개고, 플레이어는 자기가 선 셀만 조회하게 만들어. 파일은 특이하게 Engine/Source가 아니라 플러그인 쪽에 있어:

소스 위치: Engine/Plugins/Runtime/ReplicationGraph/ 이 클론엔 플러그인 소스가 전량 포함돼 있어서 아래 코드는 전부 원문 대조 완료야. (미포함 항목 없음)

1) 큰 그림: N×M을 N+M으로 쪼개는 두 개의 축

핵심 리듬부터 한 문장으로 박아두자.

매 프레임 (A) 움직인 액터만 셀에 다시 넣어두고(쓰기, 커넥션 무관 1회) → (B) 커넥션마다 그 사람이 선 셀만 훑어 관련 액터를 모은다(읽기).

여기 숨은 절감 원리가 두 개야. 이 둘을 기억하면 나머지는 다 곁가지야.

절감 축 ①: 준비(쓰기)를 커넥션 루프 "밖"으로 뺀다 → N×M을 N+M으로 전통 경로는 "커넥션마다 전체 액터 훑기"라 곱셈(N×M)이야. RepGraph는 액터를 셀에 배치하는 무거운 쓰기 작업을 커넥션 루프가 돌기 전에 딱 1회만 해(PrepareForReplication). 이건 액터 수 N에만 비례해. 그다음 커넥션 루프는 "이미 정리된 셀에서 골라 담기"만 하니 M에 비례. 곱셈이 덧셈(N+M)으로 쪼개지는 거야.

절감 축 ②: 안 움직였으면 계산 안 한다 정적(static) 액터 — 문짝, 표지판 — 는 셀에 한 번 넣으면 끝. 동적(dynamic) 액터도 매 프레임 위치는 다시 읽지만, 셀 경계를 넘었을 때만 재배치해. 제자리에서 꼼지락대는 놈은 아무 일도 안 일어나.

이 둘을 콜체인으로 펼치면 이래. 줄번호는 전부 ReplicationGraph.cpp 기준이야 (헤더는 .h 명시).

2) 노드라는 발상: "관련 액터를 모으는 로직 조각"

격자 얘기 전에 한 계단 낮춰서. RepGraph의 만물은 노드(UReplicationGraphNode)야. 노드는 "관련 액터 리스트를 모으는 로직 한 조각"이고, 매 프레임 두 개의 훅을 가져 — 준비하는 PrepareForReplication과 수집하는 GatherActorListsForConnection.

격자도 노드의 한 종류일 뿐이야. "항상 관련(AlwaysRelevant)" 노드, "휴면(Dormancy)" 노드 다 형제야. 우리가 볼 격자 노드 선언은 이렇게 생겼어:

[S1] 격자 노드 클래스 선언 — ReplicationGraph.h:578-585

UCLASS(MinimalAPI) class UReplicationGraphNode_GridSpatialization2D : public UReplicationGraphNode { GENERATED_BODY() public: UE_API UReplicationGraphNode_GridSpatialization2D();

이 노드가 자기 안에 셀들을 어떻게 들고 있냐면, 2차원 TArray로 들고 있어. 그냥 Grid[X][Y] 배열이야. 미리 월드 전체 크기만큼 왕창 잡아두는 게 아니라, 필요한 X 열이 나올 때 그때 늘려:

[S6] 격자의 지연 확장 (2D TArray로 셀 저장) — ReplicationGraph.h:725-734

TArray< TArray<UReplicationGraphNode_GridCell*> > Grid; TArray<UReplicationGraphNode_GridCell*>& GetGridX(int32 X) { if (Grid.Num() <= X) { Grid.SetNum(X+1); } return Grid[X]; }

Grid.Num() <= X면 SetNum(X+1)로 그 자리까지 늘리고 반환. 맵 구석에 아무도 안 가면 그쪽 셀은 아예 안 만들어져. 메모리를 게으르게(lazy) 쓰는 거야.

3) 위치를 "셀 좌표"로 바꾸는 산수 (핵심 변환)

격자의 심장은 딱 한 줄 산수야: 월드 좌표를 CellSize로 나누면 셀 번호가 나온다. 좌표 (12000, 3400)에 CellSize가 5000이면? X 셀 = 12000/5000 = 2, Y 셀 = 3400/5000 = 0. 이 액터는 셀 (2,0)에 산다.

근데 액터가 점이 아니라 관심 반경(CullDistance)을 가진다는 게 포인트야. 저격수는 멀리서도 보여야 하니 컬 거리가 크고, 그럼 여러 셀에 걸쳐. 그래서 한 점이 아니라 사각형으로 바뀌어 — 위치 ± 컬거리를 나눠서 StartX~EndX, StartY~EndY:

[S4] 위치 → 격자 좌표 사각형 변환 — ReplicationGraph.cpp:5735-5740

CellInfo.StartX = FMath::Max<int32>(0, UE::LWC::FloatToIntCastChecked<int32>(MinX / CellSize)); CellInfo.StartY = FMath::Max<int32>(0, UE::LWC::FloatToIntCastChecked<int32>(MinY / CellSize)); CellInfo.EndX = FMath::Max<int32>(0, UE::LWC::FloatToIntCastChecked<int32>(MaxX / CellSize)); CellInfo.EndY = FMath::Max<int32>(0, UE::LWC::FloatToIntCastChecked<int32>(MaxY / CellSize)); return CellInfo;

MinX/MaxX는 이미 "위치 − 컬거리 ~ 위치 + 컬거리"로 계산돼 넘어온 값이야. 그걸 CellSize로 나눠 정수로 깎으면(FloatToIntCastChecked) 걸치는 셀 범위가 나와. Max<int32>(0, ...)로 음수 셀은 0으로 막고. 이 FActorCellInfo{StartX,StartY,EndX,EndY} 하나가 "이 액터가 지금 어느 셀들에 속하나"의 전부야.

4) 절감 축② 실물: 셀 경계 넘었을 때'만' 옮긴다

이제 매 프레임 준비 단계에서 무슨 일이 벌어지는지 보자. 동적 액터가 움직였어. 새 위치로 셀 사각형(NewCellInfo)을 다시 계산하고, 이전 프레임 사각형(PreviousCellInfo)과 겹치는지 본다.

[S7] 셀 경계 넘은 동적 액터만 셀 재배치 — ReplicationGraph.cpp:5892-5909

if (UNLIKELY(NewCellInfo.StartX > PreviousCellInfo.EndX || NewCellInfo.EndX < PreviousCellInfo.StartX || NewCellInfo.StartY > PreviousCellInfo.EndY || NewCellInfo.EndY < PreviousCellInfo.StartY)) { // No longer intersecting, we just have to remove from all previous nodes and add to all new nodes bDirty = true; GetGridNodesForActor(DynamicActor, PreviousCellInfo, GatheredNodes); for (UReplicationGraphNode_GridCell* Node : GatheredNodes) { Node->RemoveDynamicActor(ActorInfo); } GetGridNodesForActor(DynamicActor, NewCellInfo, GatheredNodes); for (UReplicationGraphNode_GridCell* Node : GatheredNodes) { Node->AddDynamicActor(ActorInfo); }

저 if 조건이 축②의 전부야. "새 사각형이 옛 사각형과 전혀 안 겹칠 때만"(완전히 왼쪽/오른쪽/위/아래로 벗어남) 재배치를 해. 조건이 참이면 옛 셀들에서 RemoveDynamicActor, 새 셀들에 AddDynamicActor. 조건이 거짓 — 즉 아직 같은 셀 안에서 꼼지락 — 이면 이 블록을 통째로 건너뛰어. 아무 리스트도 안 건드려.

그리고 UNLIKELY(...) 매크로 보이지? 컴파일러한테 "이 분기는 잘 안 일어난다"고 힌트를 주는 거야. 대부분의 프레임에서 대부분의 액터는 셀을 안 넘거든. 코드 저자도 "재배치는 드문 일"이라고 못 박아둔 셈이야.

잠깐 맞춰봐 🔮 그럼 셀을 절대 안 넘는 액터 — 벽에 걸린 문짝 — 는 매 프레임 이 위치 비교 산수라도 돌까, 아니면 그것마저 안 돌까? 반전 👉 그것마저 안 돌아. 문짝은 애초에 정적(static) 액터로 등록돼서(AddActor_Static, ReplicationGraph.h:598) 이 동적 액터 순회 루프에 들어오지도 않아. 셀에 딱 한 번 넣고 끝. 축②가 "안 움직이면 비교조차 스킵"이 아니라 "안 움직이는 놈은 아예 명단에서 뺀다"까지 간다는 거지. 위치 비교(S7)를 겪는 건 오직 매 프레임 움직일 수 있는 동적 액터뿐이야.

5) 절감 축① 실물: 준비는 밖에서 1회, 수집은 안에서 커넥션마다

이제 프레임 진입점으로 올라가서 두 루프의 배치를 눈으로 보자. 먼저 커넥션 루프가 돌기 전에 준비 훅을 한 번 쓸어:

[S2] 커넥션 루프 前, Prepare 1회 — ReplicationGraph.cpp:1173-1180

{ QUICK_SCOPE_CYCLE_COUNTER(NET_PrepareReplication); for (UReplicationGraphNode* Node : PrepareForReplicationNodes) { Node->PrepareForReplication(); } }

이 루프는 커넥션 수와 무관해. 접속자가 10명이든 1000명이든 딱 한 번 돌아. 여기서 격자 노드의 PrepareForReplication(:5831)이 불려서 §4의 셀 재배치가 벌어지는 거야. 무거운 쓰기 작업을 여기 몰아넣은 게 축①의 앞부분.

그다음이 커넥션별 수집 루프:

[S3] 커넥션별 Gather 루프 — ReplicationGraph.cpp:1290-1298

for (UReplicationGraphNode* Node : GlobalGraphNodes) { Node->GatherActorListsForConnection(Parameters); } for (UReplicationGraphNode* Node : ConnectionManager->ConnectionGraphNodes) { Node->GatherActorListsForConnection(Parameters); }

이 Gather는 커넥션 1명당 한 번씩 불려(위 코드가 커넥션 루프 안에 있어). 그럼 격자 노드는 여기서 뭘 하냐 — 전체 셀을 다 뒤질까? 아니. 그 커넥션의 뷰어가 선 셀만 골라서 그 셀에게 위임해:

[S5] 뷰어가 선 셀만 골라 위임 (N×M 절감 핵심) — ReplicationGraph.cpp:6280-6290

FIntPoint CurGridCell {CellX, CellY}; // If we have not operated on this cell yet (meaning it's not shared by anyone else), gather for it. if (!UniqueCurrentGridCells.Contains(CurGridCell)) { if (UReplicationGraphNode_GridCell* CellNode = GetCell(GetGridX(CellX), CellY)) { CellNode->GatherActorListsForConnection(Params); } UniqueCurrentGridCells.Add(CurGridCell);

여기 CellX, CellY는 뷰어 위치를 (ViewLoc - SpatialBias) / CellSize로 바꾼 셀 좌표야. 그 셀 노드(UReplicationGraphNode_GridCell)를 GetCell로 꺼내서 걔한테만 GatherActorListsForConnection을 던져. 전체 액터를 순회하는 코드가 어디에도 없지. 이게 100만 번을 서너 번으로 줄이는 바로 그 지점이야.

UniqueCurrentGridCells는 화면 분할 등으로 뷰어가 여럿일 때 같은 셀을 두 번 모으지 않게 하는 중복 방지 장치야. 이미 처리한 셀이면 스킵.

6) 격자 밖으로 나가면? — SpatialBias와 재구축

한 가지 구멍. 격자 좌표 (0,0)이 월드의 어디에 대응하는지를 SpatialBias가 정해. 근데 맵을 넓혔거나 액터가 예상 밖으로 멀리 튀어서 Bias보다 바깥(음수 셀)으로 나가버리면? §3의 Max<int32>(0, ...)가 음수를 0으로 뭉개니까, 그냥 두면 서로 다른 위치가 같은 셀 0으로 짓뭉개져 버려.

그래서 HandleActorOutOfSpatialBounds(:5796)가 이때 SpatialBias를 바깥으로 밀고 bNeedsRebuild=true를 세워서 다음 기회에 격자를 다시 짓게 예약해. 자주 일어나면 안 되는 비싼 일이라, 보통은 맵 크기에 맞춰 Bias를 넉넉히 잡아두고 이 경로를 안 타게 해.

7) 우리 조선 서버랑 비교 (IOCP + 싱글스레드)

개념우리 조선 서버 (IOCP + 싱글스레드)UE ReplicationGraph
상태 처리 스레드IOCP 워커는 여럿, 게임 상태 변경은 싱글스레드로 직렬화격자 준비·수집 모두 게임 스레드 한 줄에서 순차
"누가 관련자?"보통 맵/구역 단위로 관심 리스트를 로직이 직접 관리격자 셀이 자동으로 "이 구역 액터"를 담아줌
공간 분할맵ID·존(zone)·시야 리스트 등 컨텐츠가 손으로 짬범용 2D 격자(CellSize)로 엔진이 일괄 처리
안 움직이면이벤트 없으면 애초에 브로드캐스트 안 함정적 액터 제외 + 동적도 셀 안 넘으면 스킵(축②)
곱셈 깨기존 단위 관심 그룹으로 대상자 축소준비(N) / 수집(M) 분리로 N×M을 N+M로(축①)

닮은 골자: 둘 다 "전체를 매번 훑지 않으려고 공간을 미리 갈라둔다." 우리 서버가 맵ID·존으로 관심 대상을 자르는 그 발상이랑, RepGraph가 격자 셀로 자르는 발상이 형제야. 그리고 둘 다 상태를 만지는 처리는 락 없이 한 줄(싱글스레드)에서 직렬로 돌아 — 우리도 게임 상태는 싱글스레드고, RepGraph 준비/수집도 게임 스레드 한 줄이야.

가장 큰 차이: 우리는 컨텐츠마다 관심 그룹을 손으로 설계해(명시적이고 트래픽 예측이 쉽지만 노가다). UE는 범용 격자 하나로 자동 처리해(짜기 편하고 일반적이지만, CellSize·CullDistance를 잘못 잡으면 셀당 액터가 뭉치거나 재구축이 잦아짐). 우리 방식이 "손으로 존을 자른 결과물"이라면, RepGraph는 "존 자르기를 엔진 레벨로 일반화·자동화한 것"이라고 보면 딱 맞아.

8) 초보가 헷갈리는 핵심 용어

  • Relevancy (관련성): 이 액터를 이 커넥션(플레이어)에게 보낼 필요가 있나. 순진하게 하면 액터 N × 플레이어 M 전수 비교라 1000명에서 폭발. RepGraph는 이걸 격자로 줄인다. 판정 기준의 속살은 relevancy.
  • Node (노드): UReplicationGraphNode(.h:68). 관련 액터를 모으는 로직 한 조각. 매 프레임 GatherActorListsForConnection(수집) + 선택적 PrepareForReplication(사전 준비, .h:100-101) 두 훅. 격자·AlwaysRelevant·Dormancy가 다 서브클래스.
  • GridSpatialization2D (2D 공간 격자): 월드를 CellSize 간격 셀로 나눠 각 셀(UReplicationGraphNode_GridCell)에 그 구역 액터만 담는 노드. 플레이어는 자기 셀만 조회 → 관련 계산이 O(내 주변 셀).
  • CellInfo / CullDistance (관심 반경): FActorCellInfo(.h:665-673)는 액터가 걸치는 셀 사각형(StartX~EndY). 위치 ± CullDistance를 CellSize로 나눠 계산(GetCellInfoForActor, :5686). 컬 거리 큰 액터는 여러 셀에 동시 등록.
  • SpatialBias (공간 원점 편향): 격자 (0,0)이 대응하는 월드 좌표. 셀 좌표 = (위치 - SpatialBias) / CellSize. 이보다 바깥으로 나가면 HandleActorOutOfSpatialBounds(:5796)가 Bias를 밀고 격자 재구축(bNeedsRebuild).
  • Dynamic vs Static (동적/정적): 정적은 안 움직이니 셀에 한 번 넣고 끝(AddActor_Static, .h:598). 동적은 매 프레임 위치 재확인, 셀 벗어났을 때만 재배치(S7). "안 움직이면 계산 안 함"이 절감 축②.
  • PrepareForReplication vs Gather: 전자는 커넥션 루프 밖에서 1회(쓰기, N에 비례), 후자는 커넥션마다(읽기, M에 비례). 이 분리가 N×M을 N+M으로 쪼개는 축①.

9) 막히면 / 다음

  • "관련 있다"의 판정 기준 자체가 애매하면 → relevancy
  • 이 격자가 대체하는 전통 경로(매 프레임 전체 훑기)를 먼저 → server-replicate-actors
  • 우선순위·업데이트 주기로 대역폭 나누는 법 → priority-updatefreq
  • 안 움직이는 액터를 아예 후보에서 빼는 형제 최적화 → dormancy
  • 정렬 통과한 액터가 실제 채널을 타는 안쪽 → actorchannel-replicate
  • 다음 → iris (RepGraph의 다음 세대, 리플리케이션을 아예 다시 설계한 신형 시스템)
