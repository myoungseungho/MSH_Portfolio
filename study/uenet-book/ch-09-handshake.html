핸드셰이크: 연결은 어떻게 맺어지나

언리얼 네트워크 · 09 / 42

들어가기 전에: "노크"를 그냥 믿으면 안 돼

문을 하나 떠올려봐. 누가 밖에서 "똑똑" 노크를 해. 그럼 넌 문을 열어줄까?

집이면 열어주겠지. 근데 이 문이 수천 명이 동시에 노크하는 서버의 문이고, 그 중 상당수가 "노크 소리만 흉내 내는 가짜"라면? 노크할 때마다 네가 의자 하나씩 꺼내서 손님 자리를 미리 깔아준다면, 가짜 노크 1만 개가 의자 1만 개를 깔게 만들고 — 방이 꽉 차서 진짜 손님이 못 들어와. 이게 스푸핑(IP 위조) 홍수 공격이야.

그래서 영리한 문지기는 이렇게 해. 노크가 오면 의자를 깔지 않고, 대신 "이 종이 다시 가져와" 하면서 도장 찍힌 종이 한 장을 던져. 진짜 손님은 그 종이를 받아서 되가져와 → 그제서야 의자를 깐다. 가짜 노크(위조 IP)는 그 종이를 받을 주소가 애초에 자기가 아니라서 되가져올 수가 없어. 자동으로 걸러진다.

이 "종이 던지고 되받는" 왕복이 바로 StatelessConnectHandshake(무상태 연결 핸드셰이크)야. 그리고 이 챕터는 그게 UE 엔진 어디에 어떻게 배선(wiring)돼서 켜지고, 실패하면 뭐가 벌어지고, 왜 이게 끝나야 로그인이 시작되는지를 실제 소스로 따라가는 거야.

우리 조선 서버로 치면? Gate가 클라의 첫 접속 바이트를 받았을 때, 아직 정식 세션(UNetConnection에 해당)을 안 잡은 그 순간. 뒤에서 IOCP랑 비교할게.

🔬 정직 배너 — 이 클론엔 "종이 찍는 기계"가 없어

한 가지 먼저 솔직하게 짚고 간다.

쿠키를 실제로 만들고(GenerateCookie) 검증하는 바이트 수준 코드 — StatelessConnectHandlerComponent.cpp — 는 이 학습용 트리에 없어.

  • 이유: 그 파일은 엔진 코어(Engine/Source)가 아니라 PacketHandlers 플러그인/컴포넌트로 따로 사는데, 이 트리엔 Engine/Source만 담겨 있어.
  • 확인: find ... -iname "*StatelessConnectHandlerComponent*" → 0건. 게다가 NetDriver.h:120이 대놓고 *"See StatelessConnectionHandlerComponent.cpp for details"* 하면서 그 없는 파일로 넘겨.

그래서 이 챕터가 커버하는 범위는 이렇게 나눠져.

구간이 트리로이 챕터
핸드셰이크가 엔진에 어떻게 켜지나 (배선/진입/실패/재시작)✅ 실제 소스로 대조verbatim 코드 + file:line
Hello→Challenge→Cookie 바이트 왕복 구현❌ 미포함개념으로만, 추측 안 함

즉, "문지기를 어디에 세우고 어떤 명령을 줬는지"까지는 실물로 보여주고, "종이에 도장을 실제로 어떻게 찍는지"는 개념 설명으로 간다. 없는 걸 있는 척 지어내진 않아.

1) 개념: Stateless가 왜 "무상태"인가

핵심 단어 세 개만 먼저 깔자. (막히면 → packethandler 로 컴포넌트 계층 개념 먼저 보고 와)

  • Connectionless(커넥션리스) 패킷: 아직 UNetConnection이 안 만들어진, 처음 보는 주소에서 온 패킷. UE는 주소 → UNetConnection 맵을 뒤져서 없으면 "얘는 커넥션리스구나" 하고 핸드셰이크부터 시작해.
  • Stateless(무상태): 서버가 노크마다 메모리(=손님 상태)를 미리 안 잡아. 필요한 정보를 쿠키에 담아 클라에게 돌려보냈다가, 클라가 그걸 그대로 되돌려줄 때 검증만 해. 서버가 상태를 안 들고 있으니 → 가짜 노크 홍수로 메모리를 고갈시킬 수가 없어. 이게 "무상태"의 방어력이야.
  • Challenge–Cookie(챌린지·쿠키): 서버가 첫 Hello에 대해 비밀키로 만든 쿠키(=도장 찍은 종이)를 응답으로 던지고, 클라가 그걸 그대로 되돌려줘야 "진짜 왕복 가능한 실주소"임이 증명돼. 위조 IP는 그 응답 자체를 못 받으니 쿠키를 되돌릴 수 없어 → 가짜연결 차단.

여기서 잠깐 예측 게임 하나. 서버가 이 쿠키를 어딘가 테이블에 저장해뒀다가 나중에 비교할까? 한번 맞춰봐.

...

반전. 아니야. 저장하면 그 순간 "무상태"가 깨져. 저장 테이블이 곧 가짜 노크로 채워질 표적이 되니까. 대신 서버는 비밀키로 쿠키를 매번 재계산해서, 되돌아온 쿠키가 "내 비밀키로 만든 게 맞나"만 확인해. 저장 없이 검증 — 그래서 무상태고, 그래서 홍수에 안 무너져. (이 재계산 코드가 바로 미포함 파일 안에 있어.)

2) 뼈대 콜체인: 문지기를 세우는 순서

서버가 리스닝 → 클라가 접속 시도 → 처음 보는 주소는 "커넥션리스"로 취급 → Stateless 핸드셰이크 컴포넌트를 가장 바깥에 세워서 그 트래픽을 먼저 거른다. 이 흐름이야.

3) 실물 대조: 배선 코드 6조각

이제 위 흐름에서 실제로 존재하는 조각들을 verbatim으로 본다. 한 글자도 안 바꿨고, 전부 file:line 표기.

지금부터 진짜 C++ 조각이 이어진다. 겁먹지 마 — 꺾쇠괄호, 화살표, 람다 같은 기호는 코드 바로 아래에서 "무슨 심부름을 시키는 표시인지"만 풀어볼 거야.

조각 A — 서버: 문지기를 "가장 바깥"에 세운다

Runtime/Engine/Private/NetDriver.cpp:2253-2262

// Add handling for the stateless connect handshake, for connectionless packets, as the outermost layer TSharedPtr<HandlerComponent> NewComponent = ConnectionlessHandler->AddHandler(TEXT("Engine.EngineHandlerComponentFactory(StatelessConnectHandlerComponent)"), true); StatelessConnectComponent = StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent); if (StatelessConnectComponent.IsValid()) { StatelessConnectComponent.Pin()->SetDriver(this); }
🔤 기호 사전 — ConnectionlessHandler->AddHandler(..., true)
• TSharedPtr<HandlerComponent> = HandlerComponent를 붙잡아두는 UE식 손잡이 상자. "새 컴포넌트를 잠깐 들고 있는 손잡이"라고 보면 돼.
• NewComponent = = 방금 만든 컴포넌트 손잡이를 NewComponent라는 이름표가 붙은 칸에 담는다.
• -> = "그 손잡이가 가리키는 애한테 일을 시켜". ConnectionlessHandler->AddHandler는 핸들러한테 "컴포넌트 하나 붙여"라고 시키는 것.
• TEXT("...") = 문자열을 UE가 쓰는 문자 형식으로 감싸는 매크로. 여기서는 "이 이름의 컴포넌트를 찾아줘"라는 이름표야.
• true = 여기서는 "가장 바깥쪽에 붙여"라는 스위치. 그냥 참/거짓 중 참이 아니라, 이 함수의 두 번째 칸에 들어간 최외곽 표시야.
• StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent) = 넓은 손잡이(HandlerComponent)를 더 구체적인 손잡이(StatelessConnectHandlerComponent)로 바꿔 잡기.
• .IsValid() = 이 손잡이가 진짜 뭔가를 가리키고 있나 확인.
• .Pin()->SetDriver(this) = 약한 손잡이를 잠깐 단단히 잡고(Pin), 그 안의 컴포넌트에게 "내 드라이버는 이거야" 하고 this를 알려준다.
🔁 이제 다시 보자. AddHandler(TEXT(...), true) = "Stateless 문지기를 최외곽에 붙여라" → StaticCastSharedPtr = "그 문지기 전용 손잡이로 다시 잡아라" → IsValid() = "정상으로 붙었나 확인" → SetDriver(this) = "이 문지기가 어느 NetDriver 소속인지 알려줘라." 한 줄 한 줄이 전부 문지기 배치 작업으로 읽히지?

포인트 딱 두 개.

  • AddHandler(..., true)의 그 true가 "최외곽(outermost)" 플래그야. PacketHandler는 컴포넌트를 양파처럼 계층으로 쌓는데(→ packethandler), Stateless를 맨 바깥 껍질에 둬. 그래야 검증 안 된 트래픽이 암호화·게임로직 같은 안쪽 껍질에 닿기도 전에 먼저 걸러져.
  • 반환된 컴포넌트를 StatelessConnectComponent에 잡아두고 SetDriver(this). 이 핸들이 나중에 재시작(NotifyHandshakeBegin) 부를 때 쓰여.

조각 B — 커넥션: 똑같이 부착 + "실패하면 나 불러" 등록

Runtime/Engine/Private/NetConnection.cpp:729-741

// Add handling for the stateless connect handshake, for connectionless packets, as the outermost layer TSharedPtr<HandlerComponent> NewComponent = Handler->AddHandler(TEXT("Engine.EngineHandlerComponentFactory(StatelessConnectHandlerComponent)"), true); StatelessConnectComponent = StaticCastSharedPtr<StatelessConnectHandlerComponent>(NewComponent); if (StatelessConnectComponent.IsValid()) { StatelessConnectHandlerComponent* CurComponent = StatelessConnectComponent.Pin().Get(); CurComponent->SetDriver(Driver); CurComponent->SetHandshakeFailureCallback([this](FStatelessHandshakeFailureInfo FailureInfo){this->OnStatelessHandshakeFailure(FailureInfo);}); }
🔤 기호 사전 — CurComponent->SetHandshakeFailureCallback([this](...){...});
• Handler->AddHandler(...) = 이번에는 커넥션 쪽 Handler한테 같은 문지기를 붙이라고 시키는 화살표 호출.
• StatelessConnectHandlerComponent* = StatelessConnectHandlerComponent를 직접 가리키는 포인터. 별표 *는 "실물 자체가 아니라 위치표를 들고 있다"는 느낌이야.
• .Pin().Get() = 약한 손잡이를 잠깐 붙잡고(Pin), 그 안의 실제 포인터를 꺼내기(Get).
• CurComponent->SetDriver(Driver) = 방금 꺼낸 컴포넌트에게 드라이버를 알려준다.
• SetHandshakeFailureCallback(...) = "핸드셰이크가 실패하면 이 함수를 불러" 하고 전화번호를 등록하는 자리.
• [this](FStatelessHandshakeFailureInfo FailureInfo){...} = 람다. 즉석에서 만든 작은 함수야. [this]는 "나, 지금 이 UNetConnection을 기억해둬"라는 뜻.
• FStatelessHandshakeFailureInfo = 실패 이유와 관련 정보를 담아 오는 보고서 상자.
• this->OnStatelessHandshakeFailure(FailureInfo) = 기억해둔 이 커넥션한테 실패 보고서를 넘기며 처리 함수를 호출한다.
🔁 이제 다시 보자. AddHandler(..., true)로 커넥션에도 문지기를 붙이고 → .Pin().Get()으로 그 문지기를 꺼낸 뒤 → SetDriver로 소속을 알려주고 → SetHandshakeFailureCallback([this]...)으로 "실패하면 나한테 알려"를 등록한다. 이 조각의 핵심은 부착 + 실패 콜백 예약이야.

서버 측 조각 A랑 앞부분이 판박이지? 같은 컴포넌트를 커넥션 쪽에도 최외곽으로 붙여. 차이는 마지막 줄 — SetHandshakeFailureCallback(...)으로 실패 콜백을 등록해. 핸드셰이크가 삐끗하면 컴포넌트가 이 람다를 호출해서 OnStatelessHandshakeFailure로 제어를 넘긴다. 그게 다음 조각.

조각 C — 실패했는데 "버전이 달라서"면? 업그레이드하고 재시작

Runtime/Engine/Private/NetConnection.cpp:791-805

void UNetConnection::OnStatelessHandshakeFailure(UE::Net::FStatelessHandshakeFailureInfo HandshakeFailureInfo) { using namespace UE::Net; if (HandshakeFailureInfo.FailureReason == EHandshakeFailureReason::WrongVersion) { const bool bUpgradeSuccess = HandleReceiveNetUpgrade(HandshakeFailureInfo.RemoteNetworkVersion, HandshakeFailureInfo.RemoteNetworkFeatures, ENetUpgradeSource::StatelessHandshake); if (bUpgradeSuccess) { // Restart the handshake since the network driver is now compatible StatelessConnectComponent.Pin().Get()->NotifyHandshakeBegin(); } } }
🔤 기호 사전 — void UNetConnection::OnStatelessHandshakeFailure(...)
• void = 이 함수는 값을 돌려주지 않는다. 실패를 처리만 하고 끝난다는 뜻.
• UNetConnection:: = UNetConnection에 딸린 함수라는 소속 표시. ::는 "~안의"라고 읽으면 돼.
• UE::Net::FStatelessHandshakeFailureInfo = UE 안의 Net 묶음에 있는 실패 보고서 타입. ::가 두 번 나와서 "UE 안의 Net 안의 이름"처럼 주소를 타고 들어간다.
• using namespace UE::Net; = 아래에서 UE::Net::을 매번 길게 안 쓰게 해주는 줄.
• if (...) = 괄호 안 조건이 맞을 때만 안쪽 블록을 실행한다.
• == EHandshakeFailureReason::WrongVersion = 실패 이유가 WrongVersion과 같은지 비교. ==는 "같다", WrongVersion은 실패 이유 보기 중 하나야.
• const bool bUpgradeSuccess = 참/거짓 결과를 담는 칸. const는 한 번 담으면 이 함수 안에서 바꾸지 않겠다는 약속.
• ENetUpgradeSource::StatelessHandshake = 업그레이드 요청 출처가 "Stateless 핸드셰이크 단계"라고 찍어주는 꼬리표.
• StatelessConnectComponent.Pin().Get()->NotifyHandshakeBegin() = 문지기 컴포넌트를 다시 꺼내서 "핸드셰이크 처음부터 다시 시작해"라고 시킨다.
🔁 이제 다시 보자. if (FailureReason == WrongVersion) = "실패 이유가 버전 불일치면" → HandleReceiveNetUpgrade(...) = "버전 맞추기를 시도" → if (bUpgradeSuccess) = "성공했으면" → NotifyHandshakeBegin() = "다시 노크 절차 시작." 그래서 이 코드는 쫓아내는 코드가 아니라 맞춰보고 다시 시키는 코드로 읽으면 돼.

읽는 법. 실패 사유(FailureReason)가 WrongVersion(클라·서버 네트워크 버전 불일치)일 때만 특별 대우를 해. HandleReceiveNetUpgrade(...)로 버전 협상을 시도하고, 그게 성공하면(bUpgradeSuccess) 주석 그대로 *"Restart the handshake"* — NotifyHandshakeBegin()으로 핸드셰이크를 처음부터 다시 돌려. 이번엔 드라이버가 호환되는 상태니까 통과할 수 있어.

즉 버전 불일치는 "쫓아내기"가 아니라 "맞춰주고 다시 노크시키기"야.

조각 D — 설계 주석: "기존 커넥션 아니면 = 핸드셰이크 시작"

Runtime/Engine/Classes/Engine/NetDriver.h:117-120

* If a packet is from a connection that's already established, we pass the packet along to the connection via UNetConnection::ReceivedRawPacket. * If a packet is not from a connection that's already established, we treat is as "connectionless" and begin the handshaking process. * * See StatelessConnectionHandlerComponent.cpp for details on how this handshaking works.
🔤 주석 기호 사전 — UNetConnection::ReceivedRawPacket
• * = C++ 주석 블록 안에서 각 줄 앞에 붙는 설명 표시. 실행되는 코드는 아니야.
• UNetConnection::ReceivedRawPacket = 이미 만들어진 커넥션으로 들어온 날패킷을 넘기는 함수 이름.
• connectionless = 아직 UNetConnection이 없는 주소에서 온 패킷. "세션 없는 첫 노크"라고 보면 돼.
• handshaking process = 바로 이 챕터의 쿠키 왕복 절차. 노크한 사람이 진짜인지 확인하는 과정.
• StatelessConnectionHandlerComponent.cpp = 상세 구현이 있다는 파일 이름. 이 학습용 트리에는 없다고 앞의 정직 배너에서 못 박은 그 파일이야.

이 네 줄이 챕터 전체의 분기점이야. 기존 커넥션이면 ReceivedRawPacket으로 흘려보내고(→ receive-callchain), 아니면 커넥션리스로 보고 핸드셰이크 시작. 그리고 마지막 줄이 바로 아까 배너에서 말한 "없는 파일로 넘기는" 그 문장이야. 엔진이 직접 "세부는 저기 봐" 하는 거지.

조각 E — 핸드셰이크 끝나기 전엔 아무것도 못 보낸다

Runtime/Engine/Private/NetConnection.cpp:4248-4254

// Now that the stateless handshake is responsible for initializing the packet sequence numbers, // we can't allow any packets to be written to the send buffer until after this has completed if (CVarRandomizeSequence.GetValueOnAnyThread() > 0) { checkf(!Handler.IsValid() || Handler->IsFullyInitialized(), TEXT("Attempted to write to send buffer before packet handler was fully initialized. Connection: %s"), *Describe()); } #endif
🔤 기호 사전 — checkf(!Handler.IsValid() || Handler->IsFullyInitialized(), TEXT(...))
• if (CVarRandomizeSequence.GetValueOnAnyThread() > 0) = 랜덤 시퀀스 기능이 켜져 있을 때만 안쪽 검사를 한다. > 0은 0보다 크면 켜진 걸로 보는 비교야.
• checkf(조건, TEXT(...)) = 조건이 참이면 통과, 거짓이면 메시지를 찍고 멈추는 안전장치.
• !Handler.IsValid() = 핸들러가 아직 없으면. !는 "아니면/반대" 표시야.
• || = "또는". 왼쪽이 맞거나 오른쪽이 맞으면 전체가 통과해.
• Handler->IsFullyInitialized() = 핸들러한테 "완전히 초기화 끝났어?"라고 묻는 화살표 호출.
• TEXT("...") = 에러 메시지 문자열을 UE 문자 형식으로 감싸는 매크로.
• *Describe() = Describe()가 만든 설명 문자열을 로그에 넣을 수 있게 꺼내는 표시. 여기선 어떤 커넥션에서 터졌는지 보여주려는 거야.
• #endif = 앞에서 시작한 조건부 컴파일 구역이 여기서 끝난다는 표시.
🔁 이제 다시 보자. if (... > 0) = "시퀀스 랜덤화 검사를 켰으면" → checkf(!Handler.IsValid() || Handler->IsFullyInitialized(), ...) = "핸들러가 없거나, 있으면 완전히 초기화돼 있어야만 send buffer에 쓸 수 있다." 한 줄로 읽으면 핸드셰이크가 끝나기 전에는 패킷 쓰기 문을 잠근다는 뜻이야.

이게 "왜 로그인이 핸드셰이크 뒤에 오나"의 진짜 이유야. 주석이 설명해줘 — 핸드셰이크가 이제 패킷 시퀀스 번호 초기화를 책임진다. 시퀀스 번호(→ reliability-ack에서 신뢰성의 뼈대로 다시 나와)가 아직 안 정해졌는데 게임 패킷을 send buffer에 써버리면 순번이 엉켜. 그래서 IsFullyInitialized()가 아니면 checkf로 막아. 핸드셰이크가 완료돼야 이 문이 열리고, 그제서야 로그인/게임 패킷이 흐른다.

조각 F — 업그레이드 메시지가 "어디서 왔나" 구분

Runtime/Engine/Classes/Engine/NetConnection.h:105-110

/** The source of a net upgrade message */ enum class ENetUpgradeSource : uint8 { ControlChannel, // The upgrade message came from the control channel StatelessHandshake // The upgrade message came from the stateless handshake };
🔤 기호 사전 — enum class ENetUpgradeSource : uint8
• enum class = 정해진 보기 중 하나만 고르게 하는 이름표 묶음. 여기서는 "업그레이드 메시지가 어디서 왔나" 보기표야.
• ENetUpgradeSource = 보기표의 이름. 앞의 E는 UE에서 enum 이름에 자주 붙는 표시야.
• : uint8 = 이 보기 값을 1바이트짜리 숫자로 저장하겠다는 뜻. 작게 담는 번호표라고 보면 돼.
• ControlChannel = 이미 커넥션이 잡힌 뒤 컨트롤 채널에서 온 경우.
• StatelessHandshake = 아직 커넥션 전, 핸드셰이크 단계에서 온 경우.
• // = 뒤쪽은 사람 읽으라고 붙인 주석. 실행되는 코드는 아니야.
• }; = enum 상자 닫기. }로 묶음을 닫고 ;로 선언을 끝낸다.

작은 조각인데 의미가 있어. 버전 업그레이드 요청은 두 군데서 올 수 있어 — 컨트롤 채널(이미 커넥션 잡힌 뒤, → channel-types)이거나 Stateless 핸드셰이크(아직 커넥션 전). 조각 C에서 HandleReceiveNetUpgrade(..., ENetUpgradeSource::StatelessHandshake)로 "이건 핸드셰이크 단계에서 온 거야"라고 출처를 명시했지. 같은 업그레이드 로직이라도 어느 단계냐에 따라 처리가 달라야 하니까 이 enum으로 구분해.

4) 우리 서버랑 비교: IOCP 워커 + 싱글스레드 액터

조선 서버 하는 사람 입장에서 대응을 맞춰보자.

[ UE ] [ 우리 조선 서버 ] ──────────────────────────────────────────────────────────── 첫 바이트가 미지의 주소에서 옴 ↔ Gate가 accept 직후 첫 recv "주소→UNetConnection 맵에 없다" ↔ 아직 세션/PC 객체 안 붙은 소켓 Stateless 핸드셰이크 (쿠키 왕복) ↔ (우리는 이 무상태 쿠키 계층이 약함 — Gate가 곧장 세션 잡는 편) 최외곽 컴포넌트로 먼저 거름 ↔ IOCP 워커가 raw 바이트 받아 큐잉, 그 앞단에 검증 레이어를 두는 자리 핸드셰이크 완료 → 시퀀스 초기화 ↔ 세션 확립 → 이후 CM_ 패킷 처리 허용 로그인 패킷은 그 다음 ↔ 로그인 CM_ 는 세션 붙은 뒤에만

핵심 대응 두 개.

  • "받는 스레드"와 "처리하는 곳"의 분리: UE는 TickDispatch가 소켓에서 긁어와 커넥션리스/기존커넥션으로 분류하고, 실제 게임 로직은 그 뒤 싱글 게임 스레드에서 처리해. 우리도 IOCP 워커(멀티)가 수신·큐잉만 하고, 싱글스레드 액터 루프가 꺼내 처리하는 구조랑 정확히 같은 철학이야. UE의 "커넥션리스 판정"이 우리 IOCP 워커가 "얘 아직 세션 없네" 판단하는 그 지점.
  • 무상태 방어는 우리가 배울 점: UE는 세션(메모리) 잡기 전에 쿠키 왕복으로 실주소를 증명시켜. 우리 Gate는 상대적으로 일찍 상태를 잡는 편이라, 스푸핑 홍수 방어에선 UE의 "최외곽 무상태 문지기" 배치가 참고할 설계야. 안쪽(게임로직)에 닿기 전에 바깥 껍질에서 거른다는 순서 말이지.

5) 종착: 그래서 로그인은 언제 시작되나

한 프레임을 다시 필름으로 되감아보면 —

  1. 클라가 접속 시도 → 첫 패킷 도착 (조각 D: 기존 커넥션 아님 → 커넥션리스)
  2. 서버가 최외곽에 Stateless 문지기 세움 (조각 A)
  3. 커넥션 측도 부착 + 실패 콜백 등록 (조각 B)
  4. [미포함 구간] Hello → Challenge(쿠키) → Response 왕복으로 실주소 증명 → 가짜 노크 탈락
  5. (버전 다르면) 업그레이드 후 재시작 (조각 C, F)
  6. 완료 → 시퀀스 번호 초기화 끝 → send buffer 개방 (조각 E)
  7. 이제서야 로그인/게임 패킷 진입 → connection-lifecycle로 이어짐

문지기가 "이 손님 진짜네" 도장을 다 찍기 전까진, 로그인 창구는 셔터 내린 상태인 거야.

막히면 → packethandler (컴포넌트 양파 계층이 뭔지), netdriver-tick (TickDispatch가 프레임 어디서 도는지) 다음 → connection-lifecycle (핸드셰이크 뒤 커넥션이 로그인~종료까지 밟는 생애), security (스푸핑·DDoS 방어 큰 그림)

🎯 원리 한 줄 요약

서버는 노크가 오면 의자부터 깔지 않고 "도장 찍은 종이(쿠키)"를 최외곽에서 던져 되받는다 — 진짜 주소만 그걸 돌려줄 수 있어 가짜연결이 걸러지고, 이 왕복이 시퀀스 번호까지 초기화한 뒤에야 로그인 패킷의 셔터가 열린다.
