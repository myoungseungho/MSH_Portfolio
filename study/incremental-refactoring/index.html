Part 2. Strangler Fig Pattern (교살자 무화과 패턴)

🌿 Strangler Fig Pattern

레거시 시스템을 새 시스템으로 점진적 교체하는 전략.
무화과나무가 숙주 나무를 서서히 감싸며 교체하듯이.

구체적으로 어떻게 해?

4단계로 진행해:

  • 1 새 코드를 레거시 옆에 만든다
  • 2 호출을 하나씩 새 코드로 이동
  • 3 검증 후 다음 호출 이동
  • 4 레거시에 호출 0개 → 삭제
// 예시: SavePC 리팩토링 // Step 1: 새 함수를 옆에 만든다 bool SavePC_Legacy(CGamePC* pPC) { // 기존 (건드리지 않음) // 200줄짜리 레거시 코드 } bool SavePC_New(CGamePC* pPC) { // 새로 만듦 // 깔끔하게 리팩토링된 코드 } // Step 2: 라우터 함수로 분기 bool SavePC(CGamePC* pPC) { if (USE_NEW_SAVE) { // Feature Flag return SavePC_New(pPC); } return SavePC_Legacy(pPC); } // Step 3: 테스트 후 Flag를 true로 // Step 4: 모두 성공하면 Legacy 삭제
실제 프로젝트에 적용하면?

우리 프로젝트의 ServerMsgProcess.cpp를 예로:

// 현재: 1019줄짜리 switch문 void HandleServerMsg(int iClient, BYTE* pPacket) { switch (*pwHeader) { case SSM_SERVER_CONNECTED: // 100줄... case SSM_SERVER_DISCONNECTED: // 50줄... // ... 30개 case ... } } // Strangler Fig 적용 계획: // 1주차: SSM_SERVER_CONNECTED만 분리 // 2주차: SSM_SERVER_DISCONNECTED 분리 // ... 점진적으로 ... // N주차: switch문이 단순 라우터만 남음

Part 3. Sprout Method (새싹 메서드)

🌱 Sprout Method

기존 코드를 건드리지 않고, 새 기능을 별도 메서드로 추가.
"기존 흙에서 새싹을 틔우듯이"

언제 써?

새 기능을 추가해야 하는데, 기존 코드를 건드리기 무서울 때.

// 시나리오: 던전 입장에 "레벨 체크" 기능 추가 // ❌ 기존 코드에 직접 끼워넣기 (위험) void EnterDungeon(Player* p) { // 기존 코드 100줄... if (p->level < dungeon->minLevel) return; // 어디에 넣지? // 기존 코드 계속... } // ✅ Sprout Method로 분리 bool CheckDungeonLevelRequirement(Player* p, Dungeon* d) { return p->level >= d->minLevel; } void EnterDungeon(Player* p, Dungeon* d) { // 새 로직은 맨 앞에 추가 (기존 코드 안 건드림) if (!CheckDungeonLevelRequirement(p, d)) { SendFail(p, FAIL_LEVEL_TOO_LOW); return; } // 기존 코드 그대로... }
Sprout Method의 장점

✅ 기존 코드 수정 최소화 → 버그 위험 ↓
✅ 새 기능만 테스트 가능
✅ 나중에 새 메서드를 더 발전시킬 수 있음
✅ 코드 리뷰가 쉬움 (변경점이 명확)

Part 4. Wrap Method (감싸기 메서드)

📦 Wrap Method

기존 메서드를 감싸서 전/후에 새 동작 추가.
기존 코드를 전혀 건드리지 않음!

Sprout랑 뭐가 달라?

Sprout는 안에 새 코드 추가,
Wrap은 밖에서 감싸는 거야.

// 시나리오: SavePC 호출 전후로 로깅 추가 // 기존 코드 (건드리고 싶지 않음) void SavePC(CGamePC* pPC) { // 복잡한 저장 로직 200줄... } // ✅ Wrap Method 적용 // 1. 기존 함수 이름 변경 void SavePC_Original(CGamePC* pPC) { // 복잡한 저장 로직 200줄... (그대로!) } // 2. 새 함수가 원래 이름 사용 void SavePC(CGamePC* pPC) { // 전처리 (새로 추가) LogSaveStart(pPC); auto startTime = GetTime(); // 원본 호출 SavePC_Original(pPC); // 후처리 (새로 추가) LogSaveEnd(pPC, GetTime() - startTime); } // 호출하는 쪽은 변경 없음! 여전히 SavePC() 호출

Part 5. Feature Flag로 안전하게

새 코드가 버그 있으면 어떡해?

Feature Flag로 ON/OFF 조절해.

문제 생기면 바로 끌 수 있어.

// Feature Flag 활용 // 설정 파일 또는 서버 변수 bool g_bUseNewSaveSystem = false; // 기본 OFF void SavePC(CGamePC* pPC) { if (g_bUseNewSaveSystem) { // 새 시스템 (테스트 중) SavePC_New(pPC); } else { // 구 시스템 (안정) SavePC_Legacy(pPC); } } // 배포 순서: // 1. 새 코드 배포 (Flag = false, 아무 영향 없음) // 2. 테스트 서버에서 Flag = true로 테스트 // 3. 라이브 서버에서 10% 유저만 Flag = true // 4. 문제 없으면 100% 전환 // 5. Legacy 코드 삭제
단계 Flag 대상 리스크
배포 false - 없음
테스트 서버 true 개발팀 낮음
라이브 10% true 일부 유저 중간
라이브 100% true 전체 높지만 검증됨

Part 6. 우리 프로젝트에 적용 가이드

정리하면 어떻게 해야 해?

우리 프로젝트에 맞는 리팩토링 전략:

조선협객전 서버 리팩토링 가이드

1. 범위 선정
→ 한 번에 하나의 함수/기능만
→ 예: "이번 주는 SSM_SERVER_CONNECTED만"

2. Sprout 우선
→ 새 기능은 무조건 별도 함수로
→ 기존 코드에 호출만 추가

3. 테스트 후 병합
→ DummyClient로 시나리오 테스트
→ 문제 없으면 main에 병합

4. 점진적 삭제
→ 구 코드는 일정 기간 유지
→ 안정화 확인 후 삭제
// 실제 적용 예시: HandleServerMsg 리팩토링 계획 // Week 1: 구조만 준비 void HandleServerMsg(int iClient, BYTE* pPacket) { switch (*pwHeader) { case SSM_SERVER_CONNECTED: HandleServerConnected(iClient, pPacket); // 분리! break; // 나머지는 그대로... } } // Week 2: 다음 case 분리 case SSM_SERVER_DISCONNECTED: HandleServerDisconnected(iClient, pPacket); break; // Week N: 모든 case 분리 완료 // → switch문은 라우터 역할만 // → 각 Handler는 독립적으로 테스트/수정 가능

핵심 정리: 점진적 리팩토링

  • Strangler Fig: 새 코드를 옆에 만들고 점진적 이동
  • Sprout Method: 기존 코드 안 건드리고 새 함수 추가
  • Wrap Method: 기존 함수를 감싸서 전후 처리 추가
  • Feature Flag: ON/OFF로 안전하게 전환
  • 한 번에 하나: 범위를 좁게, 검증 후 다음 단계
  • 보이스카웃: 건드릴 때마다 조금씩 개선
