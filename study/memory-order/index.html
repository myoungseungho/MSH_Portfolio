Memory Order와 Memory Barrier

C++ / 하드웨어 멀티스레드 동기화
Memory Order Memory Barrier std::atomic Reordering Store Buffer

1. 출발점: 코드는 위에서 아래로 실행된다?

우리는 코드가 적힌 순서대로 실행된다고 믿습니다. 하지만 실제로는 컴파일러와 CPU 둘 다 순서를 바꿀 수 있습니다. 

// 우리가 적은 코드
x = 1;        // ①
ready = true;  // ②
// 컴파일러 또는 CPU가 실제로 실행하는 순서
ready = true;  // ② 먼저!
x = 1;        // ① 나중에!

왜 순서를 바꾸나?

성능 최적화 때문입니다. 컴파일러와 CPU는 "결과가 같으면 더 빠른 순서로 해도 되지 않나?"라고 판단합니다. 싱글스레드에서는 결과가 실제로 같습니다. 하지만 멀티스레드에서는 다른 스레드가 중간 상태를 볼 수 있어서 문제가 됩니다.

2. 순서를 바꾸는 두 범인

범인 1: 컴파일러 재배치 (Compiler Reordering)

컴파일러는 최적화 과정에서 메모리 접근 순서를 자유롭게 바꿉니다. "이 두 줄은 서로 의존성이 없으니 순서 바꿔도 되겠지?" 

// 원본 코드
a = 1;
b = 2;
c = a + 3;  // a에 의존 → a 다음에 실행해야 함

// 컴파일러 최적화 후 (가능한 결과)
b = 2;      // b는 a와 무관하니 먼저 해도 됨
a = 1;
c = a + 3;

범인 2: CPU 비순차 실행 (Out-of-Order Execution)

현대 CPU는 파이프라인 효율을 위해 명령어 순서를 바꿔서 실행합니다. "앞 명령어가 캐시 미스로 기다리는 동안, 뒤 명령어 먼저 하면 빠르겠다!"

CPU 파이프라인 내부: 명령어 1: STORE x = 1 → 캐시 미스! 메모리에서 가져오는 중... (느림) 명령어 2: STORE ready = true → 캐시 히트! 바로 실행 가능 CPU: "2번 먼저 하고, 1번은 메모리 오면 그때 하자" 결과: ready = true가 x = 1보다 먼저 메모리에 반영됨!

범인 3: Store Buffer

CPU가 값을 메모리에 쓸 때, 바로 쓰지 않고 Store Buffer라는 대기열에 먼저 넣습니다. 이 버퍼는 코어마다 개별이라, 다른 코어에서는 아직 안 보입니다.

[코어 0] [코어 1] x = 1 → Store Buffer에 넣음 │ 아직 x = 0으로 보임! ↓ (나중에 반영) │ 메모리: x = 0 ────────┘ → 코어 0은 x = 1이라고 생각 → 코어 1은 x = 0이라고 생각 → 같은 시점에 다른 값을 보고 있음!

세 범인 정리

범인 단계 무엇을 바꾸나
컴파일러 컴파일 타임 코드 → 기계어 변환 시 순서 변경
CPU 런타임 기계어 실행 순서 변경
Store Buffer 런타임 쓰기가 다른 코어에 보이는 시점 지연

3. 실제 버그: Flag 패턴

멀티스레드에서 흔히 쓰는 "데이터 준비 → 플래그 세팅" 패턴이 메모리 재배치 때문에 깨지는 예시입니다. 

// 공유 변수
int data = 0;
bool ready = false;

// 스레드 A (Producer)
data = 42;          // ① 데이터 준비
ready = true;       // ② "준비됐어!"

// 스레드 B (Consumer)
while (!ready) {}   // ③ 준비될 때까지 대기
print(data);        // ④ 데이터 사용

우리 의도: B가 ready == true를 보면 data는 반드시 42.

하지만 실제로는...

CPU가 ①과 ②의 순서를 바꾸면, ready = true가 먼저 보일 수 있습니다.
스레드 B는 ready == true를 보고 data를 읽지만, 아직 data = 42가 반영 안 돼서 0을 읽습니다.

시간 → 스레드 A: ready = true (②가 먼저!) ─── data = 42 (①이 나중!) │ │ 이 시점에 B가 ready를 확인 ▼ 스레드 B: ready == true! ─── data 읽기 ─── data = 0 ??? → 데이터가 준비 안 됐는데 ready는 true!

4. 해결: Memory Barrier (메모리 장벽)

Memory Barrier는 "이 줄 위의 명령어는 아래보다 먼저 실행되어야 한다"라고 컴파일러와 CPU에게 알려주는 지시어입니다.

data = 42; ─── Memory Barrier ─── ← "여기 위쪽 다 끝나야 아래쪽 시작" ready = true; → data = 42가 반드시 ready = true보다 먼저 메모리에 반영됨

C++에서의 사용

// 방법 1: atomic 변수 사용 (가장 일반적)
std::atomic<bool> ready{false};

// 스레드 A
data = 42;
ready.store(true, std::memory_order_release);
// release = "이 줄 위의 모든 쓰기가 먼저 반영"

// 스레드 B
while (!ready.load(std::memory_order_acquire)) {}
// acquire = "이 줄 아래의 읽기는 이 뒤에 실행"
print(data);  // 반드시 42!

핵심 아이디어

Release: "내가 쓴 거 다 내보내" (쓰기 쪽 장벽)
Acquire: "상대가 쓴 거 다 가져와" (읽기 쪽 장벽)
이 둘이 짝을 이루면 스레드 간 데이터 전달이 안전해집니다.

5. C++ memory_order 6가지

C++11은 6가지 메모리 순서 옵션을 제공합니다. 하지만 실무에서 쓰는 건 대부분 3가지입니다.

memory_order 의미 성능 사용 빈도
relaxed 순서 보장 없음. 원자성만 보장 가장 빠름 카운터
acquire 이 읽기 이후의 모든 접근이 이 뒤에 실행 보통 데이터 수신 측
release 이 쓰기 이전의 모든 접근이 이 앞에 실행 보통 데이터 송신 측
acq_rel acquire + release 동시 적용 보통 CAS 연산
seq_cst 모든 스레드가 같은 순서로 봄 (가장 강력) 가장 느림 기본값
consume 데이터 의존성만 보장 (거의 사용 안 함) 빠름 사실상 미사용

실무에서 알아야 할 3가지

1. relaxed - "원자성만 주세요"

// 단순 카운터. 다른 데이터와 순서 관계 불필요
std::atomic<int> counter{0};
counter.fetch_add(1, std::memory_order_relaxed);

// 적합: 통계 카운터, 접속자 수, 조회수
// 부적합: 다른 데이터를 "보호"해야 할 때

2. acquire / release - "데이터 전달 보장"

// Producer-Consumer 패턴
std::atomic<bool> ready{false};

// Producer (release로 쓰기)
data = 42;
ready.store(true, std::memory_order_release);
//          ↑ data = 42가 반드시 먼저 보임

// Consumer (acquire로 읽기)
if (ready.load(std::memory_order_acquire)) {
    // data는 반드시 42
    // ↑ ready 읽기 이후의 접근은 이 뒤에 실행
}

3. seq_cst - "그냥 안전하게" (기본값)

// memory_order 생략하면 기본이 seq_cst
std::atomic<int> x{0};

x.store(1);  // = x.store(1, memory_order_seq_cst)
x.load();    // = x.load(memory_order_seq_cst)

// 모든 스레드가 같은 순서로 본다
// 가장 안전하지만 가장 느림
seq_cst vs acquire/release 성능 차이

x86 CPU에서는 차이가 거의 없습니다. x86은 기본적으로 강한 메모리 모델(TSO)을 사용하기 때문입니다.

하지만 ARM CPU (모바일, Mac M 시리즈)에서는 차이가 큽니다. ARM은 약한 메모리 모델이라 seq_cst는 추가 barrier 명령어가 필요합니다.

CPU seq_cst 비용 acquire/release 비용
x86 (Intel/AMD) 낮음 (MFENCE 1개) 거의 무료
ARM (모바일/M시리즈) 높음 (DMB 명령어) 보통 (LDAR/STLR)

실무 팁

Windows 게임 서버(x86)에서는 seq_cst를 써도 성능 차이가 미미합니다.
확실하지 않으면 기본값(seq_cst)을 쓰고, 프로파일링 후 필요할 때만 완화하세요.

6. 실전 버그: 더블 체크 락킹 (DCLP)

싱글톤 패턴에서 자주 쓰이는 Double-Checked Locking Pattern은 Memory Order를 모르면 버그를 유발합니다.

잘못된 구현

Singleton* instance = nullptr;
mutex mtx;

Singleton* GetInstance() {
    if (instance == nullptr) {        // ① 첫 번째 체크 (락 없이)
        lock_guard<mutex> lock(mtx);
        if (instance == nullptr) {    // ② 두 번째 체크 (락 안에서)
            instance = new Singleton(); // ③ 생성
        }
    }
    return instance;
}

왜 위험한가?

instance = new Singleton()은 내부적으로 3단계입니다:

③의 내부 동작: A. 메모리 할당 (malloc) B. 생성자 호출 (Singleton 초기화) C. instance 포인터에 주소 대입 CPU가 순서를 바꾸면: A. 메모리 할당 C. instance에 주소 대입 ← 먼저! B. 생성자 호출 ← 아직 안 됨! → 다른 스레드가 ①에서 instance != nullptr을 보고 초기화 안 된 객체를 사용!

올바른 구현

std::atomic<Singleton*> instance{nullptr};
mutex mtx;

Singleton* GetInstance() {
    Singleton* p = instance.load(std::memory_order_acquire);
    if (p == nullptr) {
        lock_guard<mutex> lock(mtx);
        p = instance.load(std::memory_order_relaxed);
        if (p == nullptr) {
            p = new Singleton();
            instance.store(p, std::memory_order_release);
            // release: 생성자 완료 후에 포인터가 보이도록
        }
    }
    return p;
}

더 간단한 해결법

// C++11 이후: 이게 제일 안전하고 간단함
Singleton& GetInstance() {
    static Singleton instance;
    return instance;
}
// C++11 표준이 static 지역 변수의 스레드 안전 초기화를 보장

7. 게임 서버에서 자주 겪는 상황

사례 1: 플래그 기반 종료 신호

// 잘못된 코드 (volatile은 메모리 순서를 보장하지 않음!)
volatile bool isRunning = true;

// 메인 스레드
isRunning = false;  // 서버 종료 신호

// 워커 스레드
while (isRunning) {
    ProcessPacket();  // 이 안의 데이터와 isRunning의 순서가 보장 안 됨
}

// 올바른 코드
std::atomic<bool> isRunning{true};

// 메인 스레드
isRunning.store(false, std::memory_order_release);

// 워커 스레드
while (isRunning.load(std::memory_order_acquire)) {
    ProcessPacket();
}

volatile != atomic

C++에서 volatile은 최적화 억제만 합니다. 메모리 순서, 원자성 아무것도 보장하지 않습니다.
멀티스레드 동기화에는 반드시 std::atomic을 사용하세요.

사례 2: Lock-Free 큐의 노드 공개

// Lock-Free 큐에서 새 노드를 공개할 때
Node* newNode = new Node();
newNode->data = packet;       // 데이터 설정
newNode->next = nullptr;      // 링크 설정

// release: 위의 데이터 설정이 먼저 반영된 후 공개
tail.store(newNode, std::memory_order_release);

// 다른 스레드에서 읽을 때
Node* node = tail.load(std::memory_order_acquire);
// acquire: node->data가 안전하게 읽힘

8. 실무 판단 가이드

상황 추천 memory_order 이유
통계 카운터 (접속자 수 등) relaxed 정확한 순서 불필요. 원자성만 필요
Producer-Consumer 패턴 release / acquire 데이터 전달 순서 보장
Lock-Free 자료구조 acq_rel (CAS) 읽기+쓰기 동시 순서 보장
잘 모르겠을 때 seq_cst (기본값) 가장 안전. 프로파일링 후 완화

한 줄 정리

컴파일러와 CPU는 성능을 위해 명령어 순서를 바꿉니다. 싱글스레드에서는 문제없지만, 멀티스레드에서는 다른 스레드가 중간 상태를 볼 수 있어 버그가 됩니다. std::atomic과 memory_order로 "이 순서는 지켜줘"라고 명시해야 합니다.
