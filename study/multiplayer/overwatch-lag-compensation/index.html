내가 맞췄는데 왜 안 맞았대요?

Lag Compensation과 Favor the Shooter

Part 1: 네트워크 지연으로 인한 불일치

Q: "내 화면에선 분명히 맞췄는데, 서버는 빗나갔다고 해요. 왜 그래요?"

A: 네트워크 지연 때문에 각자 보는 게임 상태가 달라요.

문제 상황:

  • 당신의 화면: "적이 저기 있네, 쏜다!" → 명중!
  • 서버의 현실: "어? 그 적은 이미 0.1초 전에 움직였는데?"
  • 적의 화면: "나 벌써 벽 뒤로 숨었는데?"
네트워크 지연으로 인한 불일치: 시간축 → T=0초 T=0.05초 T=0.1초 T=0.15초 ───────────────────────────────────────────────────── 서버: 적 위치A 적 이동중 적 위치B 적 엄폐 완료 ● →→→ ● |█|● 당신(Ping 100ms): 화면: 적 위치A 적 위치A 적 위치A 적 이동중 ● ● ● →→ 행동: [발사!] 💥 결과: 당신 화면엔 적이 A에 있지만, 서버엔 이미 B에 있음
핵심 문제: 빛의 속도는 유한합니다.
서울-부산 왕복 핑: ~10ms
한국-미국 서버 핑: ~150ms
→ 이 시간 동안 게임 상태는 계속 변합니다.

Part 2: Lag Compensation 개념 (서버가 과거로 되돌린다)

Q: "그럼 어떻게 해결하나요? 내 화면에선 맞췄잖아요!"

A: 서버가 '과거'로 되돌아가서 판정합니다. (Lag Compensation)

핵심 아이디어:

  1. 서버는 모든 플레이어의 과거 위치를 기록해둠 (보통 1초치)
  2. 당신이 "쐈어요!"라고 보고할 때, 타임스탬프를 같이 보냄
  3. 서버는 그 시점으로 시간을 되감아서 판정
  4. "당신이 쏜 그 순간"의 적 위치를 사용
// Lag Compensation 구현 OnClientShootRequest(shooterID, targetID, hitPosition, clientTimestamp): // 1. 클라이언트가 쏜 "그 순간"의 시간 계산 shooter = GetPlayer(shooterID) shootTime = clientTimestamp - shooter.ping / 2 // 2. 서버 히스토리에서 해당 시점 찾기 targetSnapshot = GetPlayerSnapshotAt(targetID, shootTime) if targetSnapshot == null: // 너무 오래된 샷 (1초 이상) return REJECT // 3. 되돌린 상태에서 히트 판정 ray = CreateRay(shooter.position, shooter.aimDirection) serverHit = RaycastAgainst(ray, targetSnapshot) if serverHit: ApplyDamage(targetID, weapon.damage) return HIT else: return MISS
Lag Compensation 시각화: 서버의 타임라인: T=0 T=50ms T=100ms T=150ms ← 현재 ───────────────────────────────────── ●A →→→B →→→C |█|D (적의 실제 위치) 당신의 요청 도착 (T=150ms): "T=50ms에 위치 A를 쏘았어요!" ↓ 서버: "잠깐, T=50ms로 되감자" ◀──────────┘ ●A ← 이 상태로 판정 💥 결과: HIT! (당신 화면과 일치)

Part 3: Favor the Shooter (쏜 사람 기준 판정)

Q: "오버워치는 '쏜 사람이 본 게 진실'이라던데, 무슨 뜻이에요?"

A: "Favor the Shooter" - 공격자 화면 기준으로 판정합니다.

철학:

  • 쏜 사람 화면에 적이 보였으면 → 맞은 걸로 인정
  • 네트워크 문제로 맞추기 어려운 걸 보상
  • 공격 행위에 대한 보상 (반응성 우선)
// Favor the Shooter 로직 ValidateHit(shooter, target, clientTimestamp): // 1. 쏜 사람의 "그 순간" 재구성 compensatedTime = clientTimestamp - shooter.ping / 2 targetState = GetHistoricalState(target, compensatedTime) // 2. 쏜 사람이 본 화면에서 맞췄는지만 확인 if IsValidHit(shooter, targetState): // ✅ 쏜 사람 화면에 맞았으면 인정 return HIT // 3. 단, 물리적으로 불가능한 건 거부 if compensatedTime < currentTime - MAX_COMPENSATION: return REJECT // 너무 오래된 샷 if IsInsideWall(targetState): return REJECT // 벽 안에 있었음 return MISS
왜 이렇게 하나요?
만약 "피격자 기준"으로 판정하면:
→ 쏜 사람: "분명히 맞췄는데 안 맞았어요!" (좌절)
→ 게임이 답답하게 느껴짐

"Favor the Shooter"로 판정하면:
→ 쏜 사람: "내가 본 대로 맞네!" (만족)
→ 게임이 반응적으로 느껴짐

Part 4: 피격자 입장의 문제 ("나는 숨었는데?")

Q: "그럼 맞는 사람은 억울하지 않나요? 내 화면엔 벽 뒤인데..."

A: 네, 맞아요. 이게 Lag Compensation의 가장 큰 부작용입니다.

피격자의 억울한 상황: 피격자 화면 (Ping 50ms): T=0 T=50 T=100 T=150 ─────────────────────────────────── 적 발견 도망 엄폐 완료 안전! ● →→→ |█|● |█|● 하지만 서버는... 공격자 요청: "T=0에 쏘았어요" (Ping 100ms) 서버 판정: T=0 시점으로 되감기 ● 💥 HIT! ↓ 피격자: "어? 나 엄폐했는데 죽었어?!" 😡
⚠️ "Cover Me" 현상
피격자: "벽 뒤로 숨었는데 죽었어요!"
실제 상황: 공격자가 쏜 순간엔 아직 안 숨었음
→ Lag Compensation이 과거로 되돌려서 판정
→ 피격자 화면에선 이미 숨은 상태라 억울함
// 피격자 시점 재구성 (디버깅용) OnPlayerComplaint("I was behind cover!"): // 서버 로그 확인 attackerPing = 120ms victimPing = 40ms // 공격자가 쏜 시점 attackTime = currentTime - attackerPing / 2 victimStateAtAttackTime = GetSnapshot(victim, attackTime) // 피격자가 숨은 시점 victimCoverTime = victimStateAtAttackTime.timestamp + 80ms 결과: - 공격자가 쏜 시점 (T=0): 피격자 노출 상태 ✓ - 피격자 화면 (T=80): 이미 엄폐 완료 - 차이: 80ms (네트워크 지연 차이) 판정: 정상 (억울하지만 합법)

Part 5: 최대 보상 시간 제한 (250ms)

Q: "그럼 핑이 500ms인 사람도 과거로 되돌려주나요?"

A: 아니요. 최대 보상 시간이 있습니다. (보통 200~300ms)

제한 이유:

  • 너무 오래된 과거는 불공평 (1초 전에 쏘고 맞았다고 하면?)
  • 서버 메모리 절약 (모든 플레이어의 과거 상태 저장)
  • 핑이 높은 플레이어에게 페널티 (공정성)
// 최대 보상 시간 적용 const MAX_LAG_COMPENSATION = 250 // milliseconds OnShootRequest(shooter, timestamp): timeDelta = currentTime - timestamp if timeDelta > MAX_LAG_COMPENSATION: // 너무 오래된 샷 거부 LogRejection(shooter, "Shot too old", timeDelta) return REJECT if timeDelta < 0: // 미래의 샷? (클라이언트 시간 조작) LogCheatAttempt(shooter, "Future timestamp") return REJECT // 정상 범위 내 보상 compensatedSnapshot = GetSnapshot(target, timestamp) return ProcessHit(shooter, compensatedSnapshot)
보상 시간 제한 효과: 핑이 낮은 플레이어 (50ms): 보상 범위: ◀───50ms───▶ ✅ 충분히 보상 공격자 서버 핑이 높은 플레이어 (300ms): 실제 지연: ◀──────────300ms──────────▶ 보상 범위: ◀───250ms───▶|❌ 여기부터 거부 ✅ ❌ 결과: 핑 높으면 타이밍 더 정확해야 함 (페널티)
공정성 밸런스:
✅ 낮은 핑 플레이어: 전체 지연 보상 → 유리함
⚠️ 높은 핑 플레이어: 일부만 보상 → 불리함
💡 결론: 좋은 인터넷 환경 = 게임 실력의 일부

Part 6: 다른 게임의 접근법

Q: "모든 게임이 'Favor the Shooter'를 쓰나요?"

A: 아니요. 게임 장르와 철학에 따라 다릅니다.

1. 오버워치 - Favor the Shooter

철학: "공격자가 본 게 진실" - 쏜 사람 화면에 맞으면 → 맞은 것 - 히트스캔 무기 (솔저, 위도우) 특히 유리 - 트레이드오프: 피격자가 가끔 억울함

2. 하이퍼스케이프 - No Lag Compensation

철학: "서버의 현재 상태만 진실" - Lag Compensation 없음 - 쏜 사람이 직접 예측해야 함 (리딩샷) - 장점: 피격자가 억울한 일 없음 - 단점: 핑 높으면 사실상 불가능

3. 발로란트 - 하이브리드

철학: "중간 지점" - 기본은 Favor the Shooter - BUT: 서버가 히트 위치 재검증 - 명백히 이상한 샷은 거부 (벽 뚫기 등) - 밸런스: 반응성 + 공정성
게임별 보상 스펙트럼: 하이퍼스케이프 발로란트 오버워치 │ │ │ ▼ ▼ ▼ 보상 없음 중간 보상 전체 보상 (서버 진실) (검증 후 인정) (쏜 사람 진실) │ │ │ 피격자 유리 균형 공격자 유리 느린 반응 적당함 빠른 반응

📚 핵심 요약

  • 문제: 네트워크 지연으로 각자 다른 게임 상태를 봄
  • 해결책: Lag Compensation - 서버가 과거로 되돌려서 판정
  • Favor the Shooter: 쏜 사람 화면 기준으로 판정 (공격자 우선)
  • 부작용: 피격자는 "나 숨었는데?" 억울함 (Cover Me 현상)
  • 제한: 최대 250ms까지만 보상 (핑 높으면 불리)
  • 게임별 차이: 오버워치(공격자 유리), 하이퍼스케이프(보상 없음), 발로란트(중간)

트레이드오프: 반응성(쏜 사람 만족) vs 공정성(맞는 사람 만족)
대부분 FPS는 반응성을 우선합니다. (게임이 재밌어야 하니까!)
