멀티플레이어 게임 네트워킹으로 돌아가기

핑 차이가 있는데 왜 공평하게 느껴져요?

Delay-based Netcode vs Rollback Netcode

Part 1: 네트워크 지연의 현실

한국 유저는 핑 10ms인데 미국 유저는 핑 150ms예요. 어떻게 공평하게 대전할 수 있나요?

물리적으로 빛의 속도가 한계예요. 광케이블로도 서울-LA 왕복에 최소 120ms가 걸려요. 이건 기술로 극복할 수 없어요!

전 세계 주요 도시 간 핑 (왕복 시간)

출발 → 도착 거리 이론적 최소 핑 실제 핑
서울 → 서울 0 km 0 ms 5~10 ms
서울 → 부산 325 km 2 ms 10~15 ms
서울 → 도쿄 1,160 km 8 ms 30~50 ms
서울 → 로스앤젤레스 9,600 km 64 ms 120~180 ms
서울 → 런던 8,900 km 59 ms 250~300 ms
빛의 속도 한계 (광케이블): ┌────────────────────────────────────────────────────┐ │ 서울 LA │ │ │◄──────── 9,600 km ──────────►│ │ │ │ │ │ │ │ 패킷 전송 ────────────────────►│ (60ms) │ │ │◄──────────────────── 패킷 응답 │ (60ms) │ │ │ │ │ │ 총 왕복 시간: 120ms (최소) │ │ 실제: 라우터 지연 + 처리 시간 = 150~180ms │ └────────────────────────────────────────────────────┘ 결론: 물리법칙은 피할 수 없다! → 그럼 네트워크 코드로 해결해야 함
핵심 문제: 네트워크 지연을 0으로 만들 수 없어요. 그럼 지연이 있어도 공평하게 느껴지게 만들어야 해요!

Part 2: Delay-based 방식 - 모두 기다리기

Delay-based Netcode가 뭔가요?

입력을 일부러 지연시켜서 모든 플레이어의 입력이 도착할 때까지 기다리는 방식이에요. LoL, Dota2가 이 방식을 사용해요.

작동 원리

Delay-based Netcode 타임라인: Player A (핑 20ms): Time 0ms: 스킬 버튼 누름 🔘 Time 20ms: 서버 도착 (대기 중...) Time 150ms: ← Input Delay 끝, 실행! ⚡ (130ms 동안 기다림) Player B (핑 150ms): Time 0ms: 스킬 버튼 누름 🔘 Time 150ms: 서버 도착, 즉시 실행! ⚡ (기다린 시간 0ms) 결과: 두 플레이어 모두 Time 150ms에 스킬 발동 → 공평함! 하지만 둘 다 느림 
// Delay-based 구현 (의사코드)
class DelayBasedServer {
    const INPUT_DELAY = 150;  // ms

    function onReceiveInput(playerId, input) {
        currentTime = now();

        // 입력을 미래 시점에 실행하도록 예약
        scheduledTime = currentTime + INPUT_DELAY;

        inputQueue.add({
            playerId: playerId,
            input: input,
            executeAt: scheduledTime
        });

        // 모든 클라이언트에 "이 입력이 예약됨" 통보
        broadcast({
            type: "INPUT_SCHEDULED",
            playerId: playerId,
            input: input,
            executeAt: scheduledTime
        });
    }

    function mainLoop() {
        while (running) {
            currentTime = now();

            // 실행 시간이 된 입력들 처리
            foreach (input in inputQueue) {
                if (input.executeAt <= currentTime) {
                    executeInput(input);
                    inputQueue.remove(input);
                }
            }

            sleep(1ms);  // 다음 프레임까지 대기
        }
    }
}

장단점

장점 단점
✅ 완벽하게 공평함 ❌ 입력 지연이 느껴짐
✅ 구현이 단순함 ❌ 빠른 액션에 부적합
✅ 예측 오류 없음 ❌ 반응성이 떨어짐
✅ 서버 부하 낮음 ❌ 느린 플레이어에 영향받음
사용 사례:
  • League of Legends: ~130ms Input Delay
  • Dota 2: ~100~150ms
  • StarCraft 2: 게임 속도 옵션에 따라 가변
이 게임들은 전략과 판단이 중요해서 100ms 지연을 수용할 수 있어요.

Part 3: Rollback 방식 - 예측하고 되돌리기

Rollback Netcode는 뭐가 다른가요?

상대방의 입력을 예측해서 즉시 실행하고, 예측이 틀리면 되돌려서 다시 실행하는 방식이에요. 격투 게임에서 많이 써요!

작동 원리

Rollback Netcode 타임라인: Player A (로컬): Time 0ms: 펀치 버튼 누름 👊 Time 0ms: 즉시 화면에 펀치 애니메이션 (예측) Time 50ms: 서버에서 B의 입력 수신: "가드" 🛡️ Time 50ms: 롤백! → Time 0ms로 돌아가서 B가 가드하는 상태로 재계산 Time 50ms: 결과: 펀치가 막힘! (수정된 애니메이션) Player B (원격): Time 0ms: 가드 버튼 누름 🛡️ Time 50ms: A에게 도착 (핑 50ms) A의 시점에서 보면: ───────────────────────────────────────────────── Time 0ms: 내가 펀치 → 상대 안 움직임 (예측) Time 50ms: 어? 상대가 가드했네! (롤백) 화면이 살짝 "꺾이는" 느낌 
// Rollback 구현 (의사코드)
class RollbackClient {
    List stateHistory;  // 과거 상태 저장
    int currentFrame = 0;

    function onLocalInput(input) {
        // 1. 즉시 로컬에서 실행 (예측)
        predictedState = simulateFrame(
            currentState,
            localInput: input,
            remoteInput: lastKnownRemoteInput  // 예측!
        );

        // 2. 히스토리에 저장
        stateHistory[currentFrame] = predictedState;

        // 3. 서버로 전송
        sendToRemote(input, currentFrame);

        currentFrame++;
    }

    function onRemoteInput(remoteInput, frameId) {
        // 예측했던 프레임과 실제 입력 비교
        if (remoteInput != predictedRemoteInput[frameId]) {
            // 예측 실패! 롤백 필요
            rollbackToFrame(frameId);

            // 그 시점부터 다시 시뮬레이션
            for (frame = frameId; frame <= currentFrame; frame++) {
                newState = simulateFrame(
                    stateHistory[frame - 1],
                    localInput: savedLocalInputs[frame],
                    remoteInput: actualRemoteInput[frame]  // 실제 입력!
                );

                stateHistory[frame] = newState;
            }

            // 화면 업데이트 (롤백된 결과)
            displayState(stateHistory[currentFrame]);
        }
    }
}

Rollback의 시각적 효과

예측이 틀렸을 때 화면: 내가 본 것 (예측): ┌─────────────────────────────────────┐ │ 나: 펀치 👊 ───→ ■ 상대 (가만히) │ │ "맞았다!" │ └─────────────────────────────────────┘ ↓ 50ms 후 롤백 발생 실제 상황 (수정): ┌─────────────────────────────────────┐ │ 나: 펀치 👊 ──X→ 🛡️ 상대 (가드) │ │ "어? 막혔네?" (화면 꺾임) │ └─────────────────────────────────────┘ 느낌: - 살짝 "텔레포트"하는 것처럼 보임 - 고핑에서는 화면이 자주 "되감기"됨 - 하지만 입력은 즉시 반응! (Delay-based보다 빠름)
Rollback의 철학: "조금 이상해 보여도, 내 입력이 즉시 반응하는 게 더 중요하다!"

Part 4: 두 방식의 상세 비교

항목 Delay-based Rollback
입력 반응 속도 느림 (100~150ms 지연) 즉각적 (0~5ms)
고핑 경험 모두 똑같이 느림 화면 꺾임/텔레포트
구현 난이도 쉬움 매우 어려움
서버 부하 낮음 높음 (재계산 필요)
공정성 완벽 예측 품질에 따라 다름
메모리 사용 적음 많음 (히스토리 저장)
적합 장르 MOBA, RTS, 턴제 격투, FPS, 빠른 액션

네트워크 품질별 경험 비교

핑 상태 Delay-based 경험 Rollback 경험
10~30ms (매우 좋음) 약간 느림 (Input Delay 때문) 완벽 (거의 롤백 없음)
50~80ms (좋음) 여전히 약간 느림 가끔 화면 꺾임
100~150ms (보통) 동일 (Input Delay가 흡수) 자주 롤백, 답답함
200ms+ (나쁨) Input Delay 증가 필요 화면 텔레포트, 플레이 불가 
// 두 방식의 핵심 차이를 코드로 비교

// Delay-based: 기다렸다가 실행
function delayBasedHandleInput(input) {
    // 1. 입력 받음
    receiveTime = now();

    // 2. 미래에 실행 예약 (모두 기다림)
    executeAt = receiveTime + INPUT_DELAY;
    schedule(input, executeAt);

    // 3. 그 시간이 되면 실행
    waitUntil(executeAt);
    execute(input);
}

// Rollback: 일단 실행, 틀리면 되돌림
function rollbackHandleInput(input) {
    // 1. 입력 받음
    receiveTime = now();

    // 2. 즉시 예측 실행 (기다림 없음!)
    predictedState = predict(input);
    display(predictedState);

    // 3. 나중에 실제 입력 도착
    onRealInputArrived(realInput) {
        if (realInput != predictedInput) {
            // 4. 예측 틀림! 되돌려서 다시
            rollback(receiveTime);
            correctState = reSimulate(realInput);
            display(correctState);  // 화면 수정
        }
    }
}

Part 5: LoL/Dota2는 왜 Delay-based인가?

LoL은 왜 Rollback을 안 쓰나요? 더 빠를 것 같은데...

MOBA 장르의 특성상 Delay-based가 더 적합해요. 여러 이유가 있어요:

이유 1: 전략적 게임플레이

  • 판단 시간이 중요: "스킬을 언제 쓸까?" - 100ms 지연은 결정에 영향 없음
  • 마우스 클릭 기반: 정밀한 타이밍보다 위치 선택이 중요
  • 쿨다운 관리: 10초 쿨다운 스킬에서 0.1초는 오차범위

이유 2: 10명 동시 플레이

// Rollback으로 10명 게임을 구현한다면?

function rollbackWith10Players() {
    // 1. 나의 입력 (Player 1)
    myInput = getInput();
    execute(myInput);  // 즉시 실행

    // 2. 9명의 입력을 예측해야 함!
    for (i = 2; i <= 10; i++) {
        predictedInput[i] = predict(player[i]);
    }

    // 3. 실제 입력 도착 시
    onRealInputs(realInputs) {
        // 9명 중 한 명이라도 예측 틀리면?
        if (anyPredictionWrong(realInputs)) {
            rollback();  // 9명의 상호작용 모두 재계산!

            // 문제: 엄청나게 복잡함
            // - 스킬 상호작용 (기절, 침묵, 넉백 등)
            // - 팀파이트 중 10명의 AOE 스킬들
            // - 미니언/정글 몬스터까지...
        }
    }
}

결론: Rollback으로 10명을 정확히 예측하는 건
      사실상 불가능하거나 너무 복잡함!

이유 3: 복잡한 게임 상태

요소 격투 게임 (1:1) MOBA (5:5)
플레이어 수 2명 10명
NPC 없음 미니언 수백 개, 몬스터 수십 개
스킬 종류 ~30개 (캐릭터당) ~600개 (챔피언 150명 × 4개)
상태 크기 ~10KB ~500KB+
롤백 비용 낮음 매우 높음
Riot의 선택: "LoL은 반응 속도 게임이 아니라 판단력 게임이다. 100ms Input Delay는 수용 가능하고, 대신 완벽한 공정성과 안정성을 보장한다."

Part 6: 격투 게임은 왜 Rollback인가?

그럼 격투 게임은 왜 Rollback을 쓰나요?

격투 게임은 프레임 단위의 정밀함이 생명이에요. 1프레임 = 16.6ms 차이로 기술이 막히거나 맞아요!

격투 게임의 프레임 정밀도

격투 게임의 프레임 데이터 (예: Street Fighter): Ryu의 승룡권: ┌──────────────────────────────────────────────────┐ │ Frame 1~3: 준비 동작 (3프레임 = 50ms) │ │ Frame 4: 무적 판정 시작 ⭐ │ │ Frame 5~8: 공격 판정 (4프레임 = 66ms) │ │ Frame 9~15: 경직 (7프레임 = 116ms) │ └──────────────────────────────────────────────────┘ 상대의 선택: - Frame 3에 가드: 막힘 ✅ - Frame 4에 공격: 내가 무적이라 안 맞음 ❌ - Frame 5에 가드: 늦음, 맞음 ❌ 1프레임 = 16.6ms 차이로 승패가 갈림! → Delay-based 100ms는 너무 느림 (6프레임 지연)

왜 Rollback이 필수인가?

// 격투 게임에 Delay-based 적용한다면?

function fightingGameWithDelay() {
    INPUT_DELAY = 100ms;  // 6프레임

    // 문제 1: 콤보가 불가능
    player.press("P");  // 펀치
    wait(100ms);        // 기다림...
    enemy.block();      // 상대가 여유롭게 가드 가능

    // 문제 2: 반응 불가능
    enemy.attack();     // 상대 공격 (Frame 1)
    // 100ms 후에야 내 가드 입력 가능
    // → 이미 맞았음!

    // 문제 3: 프로 플레이어들의 근육기억 파괴
    // 프로들은 1프레임 단위로 훈련됨
    // 6프레임 지연 = 완전히 다른 게임
}

// Rollback 적용 시
function fightingGameWithRollback() {
    // 문제 없음!
    player.press("P");  // 즉시 펀치
    enemy.block();      // 즉시 가드
    // 예측 틀리면 롤백하지만,
    // 1:1 단순 상태라 계산 부담 적음
}

💡 핵심 정리

Delay-based vs Rollback 한눈에 비교

Delay-based (LoL, Dota2): 입력 → [기다림 100ms] → 실행 ↑ 모든 플레이어가 여기서 대기 → 느리지만 완벽하게 공평 Rollback (격투, FPS): 입력 → [즉시 실행] → 예측 틀리면 되돌림 ↑ ↓ 기다림 없음 롤백 발생 → 빠르지만 가끔 화면 꺾임

선택 기준

게임 특성 권장 방식 이유
1~2명, 빠른 액션 Rollback 예측 단순, 반응속도 중요
5~10명, 전략 중심 Delay-based 예측 복잡, 판단력 중요
프레임 정밀도 필요 Rollback 1프레임 차이로 승패
많은 NPC/오브젝트 Delay-based 롤백 비용 너무 높음

실제 게임 사례

  • Delay-based: LoL, Dota 2, StarCraft 2, Hearthstone, Auto Chess
  • Rollback: Street Fighter, Guilty Gear, Mortal Kombat, Rocket League
  • 하이브리드: PUBG (서버 권위 + 클라이언트 예측), Valorant (부분 Rollback)

핵심 교훈

  • 완벽한 방식은 없다: 모두 트레이드오프
  • 장르에 맞춰 선택: 게임 특성이 결정
  • 플레이어 경험 우선: 기술보다 느낌이 중요
  • 물리법칙은 못 이김: 네트워크 지연은 불가피, 어떻게 숨길 것인가?

미래 방향

5G/6G 시대에도 물리적 거리는 극복 못 해요. 하지만 하이브리드 접근 (상황에 따라 Delay/Rollback 전환)이 연구되고 있어요!
