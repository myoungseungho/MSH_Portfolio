물리 엔진 결과가 클라마다 다르면 어떡해요?

Deterministic Physics Sync

Part 1: 물리 시뮬레이션이 왜 클라마다 다른가요?

같은 물리 엔진을 쓰더라도, CPU/OS/타이밍이 다르면 결과가 달라집니다.

문제 상황: 공이 벽에 튕기는 시뮬레이션

[같은 입력, 다른 결과] 플레이어 A (Intel CPU): 플레이어 B (AMD CPU): 공 발사! 공 발사! ● ● │ │ ↓ (60 FPS) ↓ (59.98 FPS) ⚽ ↘ ⚽ ↘ ↓ ↘ 벽 ╔═══ 벽 ╔═══ ↗ ↓ ⚽ (반사각 45°) ⚽ (반사각 44.9°) → 10초 후 위치가 달라짐!
비결정성의 원인
  • 부동소수점 연산: CPU마다 반올림 방식 미묘하게 다름
  • 프레임 타이밍: 60 FPS vs 59.98 FPS → 시간 차이 누적
  • 연산 순서: 멀티스레드 시 계산 순서 무작위
  • 최적화 수준: 컴파일러 최적화에 따라 결과 변함
// 비결정적 물리 시뮬레이션 (문제 있는 코드) void UpdatePhysics(float deltaTime) { // deltaTime이 클라마다 다름! // 60 FPS: 0.01666... // 59 FPS: 0.01694... ball.velocity += gravity * deltaTime; ball.position += ball.velocity * deltaTime; // 충돌 체크 if (CheckCollision(ball, wall)) { ball.velocity = Reflect(ball.velocity, wall.normal); // ↑ 부동소수점 오차 누적됨 } } // 문제: 10초 후 클라이언트마다 공 위치가 다름 // 클라 A: (100.5, 200.3) // 클라 B: (100.8, 200.1) ← 0.3 단위 차이!

왜 문제인가?

  • 클라 A: "내가 공을 쳤다!"
  • 클라 B: "공이 이미 지나갔는데?" (위치 불일치)
  • → 충돌 판정 불일치
  • → 멀티플레이어 혼란

전통적인 해결책 (서버 권위)

  • 서버가 유일한 진실
  • 클라는 예측만 함
  • → 하지만 로켓 리그는 초당 60번 물리 연산
  • → 서버 부하 너무 큼

Part 2: 부동소수점이 뭐가 문제인가요?

0.1 + 0.2 ≠ 0.3 이기 때문입니다.

// JavaScript/C++에서 실행해보세요 console.log(0.1 + 0.2); // 출력: 0.30000000000000004 ← 0.3이 아님! console.log(0.1 + 0.2 === 0.3); // 출력: false

왜 이런 일이?

컴퓨터는 10진수가 아닌 2진수로 소수를 표현합니다.

[부동소수점 오차] 10진수: 0.1 2진수: 0.0001100110011001100110011... └─ 무한 반복! → 유한한 비트로 표현 불가 → 반올림 필요 → 미세한 오차 발생

물리 엔진에서의 문제:

// 매 프레임마다 오차 누적 float position = 0.0f; for (int i = 0; i < 1000; i++) { position += 0.1f; // 0.1씩 더함 } // 기대: 100.0 // 실제: 100.0000152587890625 ← 오차! // 클라 A (Intel): 100.0000152587890625 // 클라 B (AMD): 100.0000152587890624 ← 다름!
누적 오차의 심각성
  • 1프레임: 0.0001 차이 (무시 가능)
  • 60프레임: 0.006 차이
  • 3600프레임(1분): 0.36 차이
  • → 공 반경이 0.5라면 충돌 판정 달라짐!

CPU별 차이:

  • Intel: SSE4.2 명령어 사용
  • AMD: SSE4a 명령어 사용
  • → 같은 연산, 미묘하게 다른 결과
// CPU별 사인 함수 결과 차이 float angle = 0.5f; // Intel CPU: sin(0.5) = 0.479425538604203 // AMD CPU: sin(0.5) = 0.479425538604202 ← 마지막 자리 다름! // 1만 번 반복하면? // 차이가 수 단위까지 벌어짐

전통 게임의 해결법:

  • 물리는 서버만 실행
  • 클라는 결과만 받아서 렌더링
  • → 하지만 로켓 리그는 8명이 동시에 초고속 물리 연산
  • → 서버 방식으로는 불가능

Part 3: Deterministic Physics는 어떻게 구현하나요?

고정소수점 + 연산 순서 보장 + 동일 입력으로 해결합니다.

해결책 1: 고정소수점(Fixed-Point) 사용

// 부동소수점 (비결정적) float pos = 0.1f; // 내부적으로 이진수 근사값 // 고정소수점 (결정적) struct Fixed { int64_t value; // 정수로 저장 static const int SCALE = 1000000; // 스케일 // 0.1을 표현: 100000 (0.1 * 1000000) }; Fixed pos = Fixed::FromFloat(0.1f); // value = 100000 // 덧셈 Fixed a = Fixed::FromFloat(0.1); Fixed b = Fixed::FromFloat(0.2); Fixed c = a + b; // 300000 → 정확히 0.3! // 모든 CPU에서 동일한 결과 보장
고정소수점의 원리 정수로만 연산하므로 CPU/OS 관계없이 동일한 결과가 나옵니다.
  • 0.5 → 500000
  • 1.234 → 1234000
  • 덧셈/뺄셈: 그냥 정수 연산
  • 곱셈: 곱한 후 스케일로 나눔

해결책 2: 연산 순서 고정

// 문제 있는 코드 (순서 불확정) foreach (var car in cars) { // 순서 보장 안 됨 Physics.Simulate(car); } // 해결 코드 (순서 고정) cars.SortByID(); // ID로 정렬 foreach (var car in cars) { Physics.Simulate(car); } // 이제 모든 클라에서 같은 순서로 연산

해결책 3: 동일 입력 보장

// Lockstep 방식 void SimulateFrame(int frameNumber) { // 1. 모든 클라가 같은 입력 수집 List inputs = GatherInputsForFrame(frameNumber); // 2. 입력 정렬 (플레이어 ID 순) inputs.SortByPlayerID(); // 3. 순서대로 물리 연산 foreach (Input input in inputs) { ApplyInput(input); Physics.Step(); // 고정 시간 간격 (1/60초) } // 결과: 모든 클라에서 동일한 월드 상태 }
[Deterministic Physics 흐름] Frame N: 모든 클라 입력 수집 정렬 ● ● ● → [A키, B키, C키] → [A,B,C] ↓ 고정소수점 연산 ↓ ⚽ (100.300000) ↓ 모든 클라에서 동일한 결과!

로켓 리그의 실제 구현:

  • PhysX 엔진 사용 (NVIDIA)
  • → 하지만 Deterministic 모드로 설정
  • 부동소수점 대신 내부적으로 정수 연산
  • 입력은 120Hz로 수집, 물리는 60Hz로 실행

Part 4: 로켓 리그는 어떤 방식을 선택했나요?

서버 권위 + 클라이언트 예측을 혼합했습니다.

[로켓 리그 물리 아키텍처] 서버 (권위) 클라이언트 (예측) ┌──────┐ ┌──────┐ │ ⚽ │ │ ⚽' │ │ 물리 │ │ 물리 │ │ 시뮬 │ │ 시뮬 │ └──┬───┘ └───┬──┘ │ │ │ ←─── 입력 전송 ────────── │ │ │ │ ──── 상태 보정 ────────→ │ │ (30Hz) │
하이브리드 방식
  • 서버: 권위적 시뮬레이션 (Deterministic)
  • 클라: 예측 시뮬레이션 (Deterministic)
  • 둘 다 같은 물리 엔진 사용 → 대부분 일치
  • 불일치 발생 시 → 서버 결과로 보정
// 클라이언트 예측 void ClientUpdate() { // 1. 로컬 입력 즉시 적용 MyInput input = GetLocalInput(); ApplyInput(input); Physics.Simulate(); // 예측 시뮬레이션 // 2. 서버로 입력 전송 SendToServer(input); // 3. 서버 상태 수신 (30Hz) if (ReceivedServerState) { ServerState state = GetServerState(); // 4. 차이 확인 float diff = Distance(myPredictedPos, state.ballPos); if (diff > TOLERANCE) { // 5. 보정 필요 SmoothCorrect(myPredictedPos, state.ballPos); } } } // 서버 void ServerUpdate() { // 1. 모든 클라 입력 수집 List inputs = GatherAllInputs(); // 2. Deterministic 시뮬레이션 inputs.SortByPlayerID(); foreach (Input input in inputs) { ApplyInput(input); } Physics.Simulate(); // 3. 상태 브로드캐스트 (30Hz) BroadcastState(ball.pos, ball.vel, ...); }

왜 Deterministic이 필요한가?

  • 클라 예측이 서버 결과와 거의 일치해야 함
  • → 보정 빈도 감소
  • → 부드러운 게임플레이

보정 주기:

  • 물리 시뮬레이션: 60Hz (초당 60번)
  • 입력 전송: 120Hz
  • 서버 상태 브로드캐스트: 30Hz
  • → 대부분의 프레임은 예측만으로 처리
  • → 2프레임마다 한 번씩 서버 보정
[타임라인 (60 FPS 기준)] Frame: 1 2 3 4 5 6 클라: 예측 예측 보정 예측 예측 보정 ● ● ● ● ● ● │ │ ↑ │ │ ↑ └────┴────┘ └────┴────┘ 서버 상태 서버 상태 수신 (30Hz) 수신

Part 5: 리플레이는 어떻게 작동하나요?

Deterministic 덕분에 입력만 저장하면 됩니다.

리플레이의 마법 물리 엔진이 결정적이면, 같은 입력을 다시 넣으면 똑같은 결과가 나옵니다. → 매 프레임 상태를 저장할 필요 없음!
// 리플레이 녹화 (매우 가벼움) class ReplayRecorder { List frames; void RecordFrame(int frameNum, List inputs) { frames.Add(new FrameInput { frameNumber = frameNum, inputs = inputs // 입력만 저장! }); } // 5분 경기 리플레이 크기: // 60 FPS * 300초 * 8명 * 10바이트 // = 약 1.4 MB ← 매우 작음! } // 리플레이 재생 class ReplayPlayer { void PlayReplay(List frames) { ResetPhysicsWorld(); // 초기 상태로 foreach (FrameInput frame in frames) { // 녹화 당시와 동일한 입력 적용 foreach (Input input in frame.inputs) { ApplyInput(input); } Physics.Simulate(); // Deterministic 연산 Render(); // 그리기 } // 결과: 원본 경기와 정확히 동일한 재생! } }
[리플레이 vs 비디오] 비디오 녹화: 매 프레임 화면 저장 ┌───┬───┬───┬───┐ │IMG│IMG│IMG│...│ 5분 = 5 GB └───┴───┴───┴───┘ Deterministic 리플레이: 입력만 저장 ┌───┬───┬───┬───┐ │INP│INP│INP│...│ 5분 = 1.4 MB └───┴───┴───┴───┘ ↓ 물리 재연산 → 동일 결과!

리플레이 기능들:

  • 카메라 자유 이동: 입력 재연산만 하므로 시점 자유롭게 변경
  • 슬로우 모션: 시뮬레이션 속도만 조절
  • 되감기: 특정 프레임부터 재시작
  • 플레이어 시점 전환: 8명 모두의 시점 확인 가능
// 슬로우 모션 구현 void PlaySlowMotion(float speed) { // speed = 0.5 → 반속도 // speed = 0.1 → 1/10 속도 foreach (FrameInput frame in frames) { ApplyInputs(frame.inputs); Physics.Simulate(); Render(); // 느리게 재생 Thread.Sleep((int)(16.67f / speed)); // 원래 60 FPS } } // 되감기 구현 void Rewind(int targetFrame) { // 처음부터 다시 시뮬레이션 ResetPhysicsWorld(); for (int i = 0; i < targetFrame; i++) { ApplyInputs(frames[i].inputs); Physics.Simulate(); } // 이제 targetFrame 상태에 도달 }

비교: 비결정적 시스템이라면?

  • 매 프레임 모든 객체 상태 저장 필요
  • 공, 차 8대, 파티클 등 = 수 GB
  • 카메라 자유 이동 불가 (저장된 시점만)
  • → Deterministic 덕분에 가능한 기능들

Part 6: 물리 보간과 외삽은 뭔가요?

서버 업데이트 사이의 빈 프레임을 메우는 기술입니다.

상황: 서버는 30Hz, 클라는 60Hz 렌더링

[30Hz 서버, 60Hz 렌더링] 서버: S1 S2 S3 ●─────────●─────────● (30Hz, 33ms 간격) 클라: ●──●──●──●──●──●──● (60Hz, 16ms 간격) C1 C2 C3 C4 C5 C6 C2, C4, C6 프레임은 서버 데이터가 없음! → 보간/외삽으로 채움

보간 (Interpolation): 과거 두 지점 사이 메우기

// 선형 보간 Vector3 Interpolate(Vector3 prev, Vector3 next, float t) { // t = 0.0 → prev // t = 0.5 → 중간 // t = 1.0 → next return prev + (next - prev) * t; } // 사용 예시 void RenderFrame() { // 서버 업데이트 2개 받음 Vector3 ballPos_t0 = serverStates[0].ballPos; // 33ms 전 Vector3 ballPos_t1 = serverStates[1].ballPos; // 현재 // 중간 프레임 보간 float t = (currentTime - t0) / (t1 - t0); // 0.0 ~ 1.0 Vector3 smoothPos = Interpolate(ballPos_t0, ballPos_t1, t); RenderBall(smoothPos); }
보간의 단점 과거 데이터 사용 → 실제보다 약간 늦게 보임 (33ms 지연)

외삽 (Extrapolation): 미래 위치 예측

// 외삽 (속도 기반 예측) Vector3 Extrapolate(Vector3 pos, Vector3 vel, float deltaTime) { // 속도를 이용해 미래 위치 예측 return pos + vel * deltaTime; } // 사용 예시 void RenderFrame() { // 마지막 서버 상태 Vector3 ballPos = lastServerState.ballPos; Vector3 ballVel = lastServerState.ballVel; // 서버 업데이트 후 지난 시간 float elapsedTime = currentTime - lastServerTime; // 미래 위치 예측 Vector3 predictedPos = Extrapolate(ballPos, ballVel, elapsedTime); RenderBall(predictedPos); }
[보간 vs 외삽] 보간 (과거): S1 ────── S2 ────── S3 ● ● ● ↖ C1 (중간값) 부드럽지만 지연됨 외삽 (미래): S1 ────── S2 ────── ? ● ● ● ↗ C1 (예측) 지연 없지만 부정확

로켓 리그의 선택:

// 하이브리드 접근 void SmoothBallPosition() { Vector3 serverPos = lastServerState.ballPos; Vector3 predictedPos = clientPhysics.GetBallPos(); float error = Distance(serverPos, predictedPos); if (error < SMALL_THRESHOLD) { // 오차 작음 → 외삽 (예측 그대로 사용) renderPos = predictedPos; } else if (error < LARGE_THRESHOLD) { // 오차 중간 → 부드럽게 보정 renderPos = Lerp(predictedPos, serverPos, 0.3f); } else { // 오차 큼 → 즉시 보정 (텔레포트) renderPos = serverPos; } }

실제 경험:

  • 평소: 클라 예측이 정확 → 외삽 사용 (지연 없음)
  • 충돌 순간: 약간의 오차 → 부드럽게 보정
  • 렉 걸릴 때: 큰 오차 → 공이 순간이동 (고스팅)
Deterministic의 이점 물리가 결정적이므로 클라 예측이 거의 정확 → 외삽 오차 최소화 → 부드러운 플레이

📚 핵심 요약

  • 비결정성 문제: 부동소수점 오차 + CPU 차이로 물리 결과가 클라마다 다름
  • 고정소수점: 정수 연산으로 모든 CPU에서 동일한 결과 보장
  • Deterministic Physics: 같은 입력 → 항상 같은 결과 (연산 순서도 고정)
  • 하이브리드 방식: 서버 권위 + 클라 예측 (Deterministic 덕분에 거의 일치)
  • 리플레이: 입력만 저장해도 경기 완벽 재현 (1.4 MB로 5분 저장)
  • 보간/외삽: 서버 업데이트 사이 프레임 메우기 (부드러운 60 FPS)
