Sea of Thieves Shared World Matchmaking
← 멀티플레이어 목록으로

한 줄 요약

씨오브시브즈는 Shared World 구조로 같은 서버에 여러 팀이 공존하며, 매치메이킹 알고리즘이 플레이어 밀도를 조절하여 "적당한 만남"을 연출합니다.

Part 1: Shared World 개념 (같은 서버, 다른 팀)

Q. Shared World가 뭐예요? 일반 멀티플레이어와 뭐가 달라요?

Shared World는 여러 팀이 같은 월드에서 독립적으로 플레이하는 구조입니다:

┌─────────────────────────────────────────────────────┐ │ 일반 멀티 vs Shared World │ └─────────────────────────────────────────────────────┘ [일반 멀티플레이어 (예: 오버워치)] 팀 A vs 팀 B → 매치 종료 → 해체 - 고정된 대결 구도 - 명확한 시작/끝 [Shared World (씨오브시브즈)] 서버 1: ├─ 팀 A (슬루프, 2명) ← 보물 찾는 중 ├─ 팀 B (브리건틴, 3명) ← 해골 섬 공격 중 ├─ 팀 C (갤리온, 4명) ← 다른 배 사냥 중 └─ 팀 D (슬루프, 2명) ← 낚시 중 - 각 팀은 독립적 목표 - 우연히 만나면 싸우거나 협력 - 지속적인 월드 (끝이 없음)
Shared World의 특징
  • 영속적 월드 - 서버는 24시간 돌아감
  • 비대칭 목표 - 각 팀이 다른 일을 함
  • 예측 불가능한 만남 - PvE와 PvP 혼재
  • 동적 참여 - 플레이어가 떠나고 들어옴
Q. 왜 이 방식을 선택했나요?

게임 디자인 목표를 달성하기 위해서입니다:

  • 긴장감 - "언제 다른 배를 만날지 모르는" 스릴
  • 선택의 자유 - 싸울지, 도망칠지, 협력할지 결정
  • 이야기 창발 - 예측 불가능한 상황이 재미있는 이야기 생성
  • 리플레이 가치 - 매번 다른 경험

Part 2: 동적 서버 할당

Q. 서버는 어떻게 배정되나요?

매치메이킹 서비스가 서버를 동적으로 할당합니다:

// 서버 할당 알고리즘 (의사코드) class MatchmakingService { List servers; GameServer FindServer(Crew crew) { // 1. 적합한 서버 찾기 List candidates = []; for (server in servers) { if (server.CanAccept(crew)) { candidates.add(server); } } // 2. 점수 기반 정렬 candidates.sort((a, b) => { return a.CalculateScore(crew) - b.CalculateScore(crew); }); // 3. 최적 서버 선택 GameServer best = candidates[0]; if (best.score < THRESHOLD) { // 새 서버 생성 return CreateNewServer(crew); } return best; } } class GameServer { int currentPlayers; int maxPlayers = 24; // 최대 6개 팀 (4명 × 6) Region region; Map shipCounts; bool CanAccept(Crew crew) { // 수용 가능 여부 체크 if (currentPlayers + crew.size > maxPlayers) { return false; } // 같은 배 타입 너무 많으면 거부 if (shipCounts[crew.shipType] >= 3) { return false; } return true; } float CalculateScore(Crew crew) { float score = 0; // 1. 플레이어 밀도 (중간이 최적) float density = currentPlayers / maxPlayers; score += abs(density - 0.5) * 100; // 50% 채워진 게 이상적 // 2. 배 타입 다양성 score += shipCounts[crew.shipType] * 10; // 3. 지역 Ping score += crew.region.PingTo(this.region); return score; // 낮을수록 좋음 } }
Q. 서버가 꽉 차면요?

새 서버를 자동 생성합니다:

┌─────────────────────────────────────────────────────┐ │ 서버 스케일링 │ └─────────────────────────────────────────────────────┘ [초기] 플레이어 적음 Server 1: [팀A, 팀B] (8명 / 24명) → 매치메이킹: 새 팀을 Server 1에 추가 [중기] 플레이어 증가 Server 1: [팀A, 팀B, 팀C, 팀D] (18명 / 24명) → 매치메이킹: 거의 찼음, 새 서버 준비 [피크] 플레이어 폭증 Server 1: [팀A, 팀B, 팀C, 팀D, 팀E] (23명 / 24명) Server 2: [팀F, 팀G] (6명 / 24명) ← 새로 생성 Server 3: [팀H, 팀I] (7명 / 24명) ← 새로 생성 → 매치메이킹: 부하 분산 [야간] 플레이어 감소 Server 1: [팀A] (4명 / 24명) Server 2: [팀B, 팀C] (9명 / 24명) → 서버 통합 (Server Migration)

Part 3: 플레이어 밀도 관리 (너무 많아도, 없어도 안 됨)

Q. 바다가 너무 텅 비어도, 너무 붐벼도 재미없을 것 같아요.

맞습니다! 플레이어 밀도(Player Density)가 핵심입니다:

밀도에 따른 게임 경험
  • 너무 낮음 (1-2팀) - 지루함, 외로움, PvP 없음
  • 적정 (4-5팀) - 긴장감, 가끔 만남, 균형
  • 너무 높음 (7-8팀) - 혼돈, 즉사, PvE 불가
// 밀도 관리 알고리즘 class DensityManager { const TARGET_DENSITY = 0.5; // 50% 채우기 const MIN_DENSITY = 0.3; const MAX_DENSITY = 0.7; void OnPlayerLeave(GameServer server) { float density = server.currentPlayers / server.maxPlayers; if (density < MIN_DENSITY) { // 서버가 너무 비었음 → 통합 시도 TryMergeServer(server); } } void TryMergeServer(GameServer source) { // 다른 서버 찾기 GameServer target = FindMergeTarget(source); if (target != null) { // 서버 마이그레이션 MigrateAllPlayers(source, target); ShutdownServer(source); } } void OnPlayerJoin(GameServer server) { float density = server.currentPlayers / server.maxPlayers; if (density > MAX_DENSITY) { // 서버가 너무 붐빔 → 신규 팀을 다른 서버로 server.acceptingNewPlayers = false; } } }
Q. 플레이어를 어떻게 분산시키나요?

지역 기반 스폰(Spawn Location)을 활용합니다:

┌─────────────────────────────────────────────────────┐ │ 서버 내 플레이어 분산 │ └─────────────────────────────────────────────────────┘ [게임 맵 - 바다] [전초기지 1] [전초기지 2] ▲ ▲ │ 스폰 │ 스폰 │ │ [팀 A] [팀 C] ↘ ↙ [보물 섬 A] │ │ 자연스럽게 만남! │ [보물 섬 B] ↗ ↖ [팀 B] [팀 D] │ 스폰 │ 스폰 ▼ ▼ [전초기지 3] [전초기지 4] 매치메이킹 로직: - 팀 A → 북쪽 스폰 - 팀 B → 남쪽 스폰 - 팀 C → 동쪽 스폰 - 팀 D → 서쪽 스폰 → 시작은 멀리, 플레이하다 보면 만남!

Part 4: 조우 시스템 (의도된 만남)

Q. 만남이 완전히 랜덤인가요? 아니면 조작되나요?

부분적으로 조작됩니다. 조우 유도(Encounter Design)가 있습니다:

// 조우 유도 시스템 class EncounterSystem { void GenerateWorldEvents(GameServer server) { // 1. 고가치 이벤트 생성 if (random() < 0.3) { Vector2 location = GetCentralLocation(); SpawnSkullFort(location); // 해골 요새 // → 모든 팀이 몰림 → 조우 발생! } // 2. 보물 배치 List treasures = []; for (team in server.teams) { Vector2 nearTeam = team.position + randomOffset(); treasures.add(SpawnTreasure(nearTeam)); } // 3. 크라켄/메갈로돈 (위협 요소) if (server.teams.count >= 4) { // 플레이어 많을 때만 보스 스폰 SpawnKraken(randomLocation); } } Vector2 GetCentralLocation() { // 모든 팀의 중심 계산 Vector2 center = (0, 0); for (team in server.teams) { center += team.position; } return center / server.teams.count; } }
의도된 조우 패턴
  • 해골 요새 - 중앙에 스폰 → 여러 팀 경쟁
  • 보물 맵 - 같은 섬을 가리킴 → 도착 시 만남
  • 상인 의뢰 - 특정 전초기지로 유도 → 교차점에서 만남
  • 크라켄 - 도망가다 다른 배와 충돌
Q. 만남 빈도를 어떻게 조절하나요?

플레이어 행동 분석으로 조절합니다:

// 조우 빈도 조절 class EncounterFrequency { const ENCOUNTER_COOLDOWN = 10 * 60; // 10분 Map lastEncounterTime; void Update(GameServer server) { for (team in server.teams) { float timeSinceEncounter = Time.now - lastEncounterTime[team]; if (timeSinceEncounter > ENCOUNTER_COOLDOWN) { // 오랫동안 만남 없음 → 유도 EncourageEncounter(team); } } } void EncourageEncounter(Team team) { // 1. 근처에 다른 팀 찾기 Team nearbyTeam = FindNearestTeam(team); if (nearbyTeam != null) { // 2. 두 팀 사이에 이벤트 스폰 Vector2 midpoint = (team.position + nearbyTeam.position) / 2; SpawnMegalodon(midpoint); // → 두 팀 다 향하게 됨! } } void OnEncounter(Team a, Team b) { // 만남 발생 시 기록 lastEncounterTime[a] = Time.now; lastEncounterTime[b] = Time.now; } }

Part 5: 서버 마이그레이션 (플레이어 이탈 시)

Q. 서버에 사람이 다 떠나면 어떻게 되나요?

서버 마이그레이션(Server Migration)이 발생합니다:

┌─────────────────────────────────────────────────────┐ │ 서버 통합 프로세스 │ └─────────────────────────────────────────────────────┘ [초기 상태] Server A: [팀1, 팀2, 팀3] (12명) Server B: [팀4, 팀5] (8명) [팀2, 팀3 퇴장] Server A: [팀1] (4명) ← 너무 비었음! Server B: [팀4, 팀5] (8명) [매치메이킹 서비스 감지] → "Server A 너무 비었으니 통합하자" [마이그레이션 시작] 1. Server B에 여유 확인 (4명 추가 가능?) 2. 팀1에게 "서버 이동합니다" 알림 3. 팀1의 상태 저장 (위치, 보물, 퀘스트) 4. Server B로 전송 5. Server B에서 팀1 복원 6. Server A 종료 [최종 상태] Server B: [팀1, 팀4, 팀5] (12명)
Q. 마이그레이션 중에 게임이 끊기나요?

로딩 화면이 짧게 나타납니다:

// 마이그레이션 시퀀스 [클라이언트] 1. "서버 병합 중..." 메시지 표시 2. 현재 상태 스냅샷 { ship: { position, rotation, velocity, ... }, cargo: [ treasure1, treasure2, ... ], quest: { progress, ... } } 3. 서버 연결 해제 4. 새 서버 연결 - IP 주소 받기 - 핸드셰이크 5. 상태 복원 - 서버가 저장된 상태 전송 - 배, 보물, 퀘스트 복구 6. "병합 완료" 메시지 총 소요 시간: 5-10초 [플레이어 경험] - 잠깐 로딩 (바다 배경 이미지) - 게임 재개 시 모든 것 그대로 - 새로운 팀들이 보임!
주의사항

마이그레이션 중에는 전투 불가입니다. 안전한 타이밍(전투 아닐 때)에만 실행됩니다.

Part 6: 스케일링과 인스턴싱

Q. 동시 접속자가 100만 명이면 어떻게 하나요?

수평 스케일링(Horizontal Scaling)으로 서버를 무한히 추가합니다:

// 클라우드 오토스케일링 class ServerOrchestrator { const PLAYERS_PER_SERVER = 24; List activeServers; void OnPlayerCountChange(int totalPlayers) { int requiredServers = ceil(totalPlayers / PLAYERS_PER_SERVER); int currentServers = activeServers.count; if (requiredServers > currentServers) { // 서버 추가 int toAdd = requiredServers - currentServers; for (int i = 0; i < toAdd; i++) { SpawnNewServer(); } } else if (requiredServers < currentServers) { // 서버 축소 (마이그레이션으로 통합) int toRemove = currentServers - requiredServers; for (int i = 0; i < toRemove; i++) { ShutdownLeastPopulatedServer(); } } } void SpawnNewServer() { // 클라우드 VM 생성 (Azure / AWS) GameServer server = CloudProvider.CreateInstance( image: "SeaOfThieves-GameServer-v1.2.3", region: SelectBestRegion(), resources: { cpu: 4, ram: 8GB } ); // 서버 풀에 추가 activeServers.add(server); RegisterWithMatchmaking(server); } } 예시: 100만 명 = 41,667개 서버 각 서버 = 4 vCPU, 8GB RAM 총 필요: 166,668 vCPU, 333TB RAM → Azure/AWS 자동 프로비저닝
Q. 모든 서버가 독립적이면 친구랑 어떻게 같이 하나요?

파티 시스템(Party System)이 있습니다:

┌─────────────────────────────────────────────────────┐ │ 파티 매칭 우선순위 │ └─────────────────────────────────────────────────────┘ [플레이어 A, B, C가 파티] ↓ [매치메이킹 서비스] "3명 파티를 수용할 서버 찾기" ↓ [조건] - 빈 자리 3개 이상 - Ping 낮은 곳 - 브리건틴 배 가능 (3-4명용) ↓ [서버 할당] Server 5: [팀X, 팀Y] (8명) + [파티 A,B,C] (3명) → 총 11명 / 24명 ↓ [게임 시작] 파티는 같은 배에 스폰 다른 팀들도 같은 월드에 존재

정리

  • Shared World: 여러 팀이 같은 서버에서 독립적 플레이
  • 동적 할당: 매치메이킹이 밀도/다양성 고려하여 서버 배정
  • 밀도 관리: 50% 목표, 너무 비거나 붐비지 않게 조절
  • 조우 유도: 이벤트를 중앙 배치하여 의도된 만남 연출
  • 서버 마이그레이션: 플레이어 이탈 시 서버 통합
  • 수평 스케일링: 서버 무한 추가로 동시 접속 확장

핵심 교훈: Shared World는 "우연같지만 설계된" 만남을 통해 예측 불가능한 재미를 만듭니다. 기술적으로는 동적 서버 관리와 플레이어 밀도 알고리즘이 핵심입니다.
