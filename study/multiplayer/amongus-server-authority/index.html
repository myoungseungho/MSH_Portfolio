누가 임포스터인지 서버만 알아요?

Among Us 서버 권위와 정보 은닉

한 줄 요약

어몽어스는 서버가 모든 비밀 정보를 관리하며, 클라이언트는 자기 역할만 알 수 있어 메모리 해킹으로도 다른 사람의 역할을 알 수 없습니다.

Part 1: 정보 은닉이 왜 중요한가 (심리 게임)

Q. 어몽어스는 추리 게임인데, 왜 "정보 은닉"이 핵심인가요?

어몽어스의 재미는 "누가 임포스터인지 모르는 것"에서 나옵니다:

정보 비대칭이 만드는 긴장감
  • 크루메이트: 누가 적인지 모름 → 의심, 추리
  • 임포스터: 자신만 진실을 알고 거짓말 → 연기, 속임수
  • 회의: 불완전한 정보로 투표 → 갈등, 배신

만약 역할 정보가 클라이언트에 있다면:

// ❌ 잘못된 설계 (클라이언트에 모든 정보) class GameState { Player[] players = [ { name: "Red", role: IMPOSTOR }, // ← 메모리에 있음! { name: "Blue", role: CREWMATE }, { name: "Green", role: CREWMATE }, ... ]; } → 메모리 해킹 툴로 players 배열 읽기 → 누가 임포스터인지 즉시 파악 → 게임 망함!
Q. 그럼 어떻게 해야 하나요?

서버만 모든 정보를 알고, 클라이언트는 최소한만 받습니다:

┌─────────────────────────────────────────────────────┐ │ 정보 분산: 서버 vs 클라이언트 │ └─────────────────────────────────────────────────────┘ [서버] ┌──────────────────────────────┐ │ 전지적 시점 (모든 비밀 관리) │ ├──────────────────────────────┤ │ Red: IMPOSTOR │ │ Blue: CREWMATE │ │ Green: CREWMATE │ │ ... │ │ │ │ 킬 쿨다운: Red = 15초 남음 │ │ 벤트 위치: Red가 Electrical │ └──────────────────────────────┘ │ 각 클라이언트에게 개별 전송 │ ┌────────┴────────┐ ▼ ▼ [Red 클라이언트] [Blue 클라이언트] "너는 IMPOSTOR" "너는 CREWMATE" (다른 역할 모름) (다른 역할 모름)

Part 2: 서버만 아는 것들 (역할 배정, 킬 쿨다운)

Q. 구체적으로 서버가 관리하는 비밀은 뭐가 있나요?

서버의 권위(Authority) 영역:

// 서버만 가진 정보 (의사코드) class ServerGameState { // 1. 역할 정보 Map roleAssignments; // Red → IMPOSTOR // Blue → CREWMATE // Green → CREWMATE // 2. 임포스터 능력 쿨다운 Map killCooldown; Map ventCooldown; // 3. 비공개 상태 Map isVenting; // 벤트 타는 중 Map lastKillPos; // 마지막 킬 위치 // 4. 검증용 데이터 Map> assignedTasks; // 각 플레이어의 태스크 Map lastKnownPosition; // 치팅 방지용 }
클라이언트는 절대 모름
  • 다른 사람의 역할
  • 임포스터의 쿨다운 (추측만 가능)
  • 누가 벤트 안에 있는지 (임포스터끼리는 보임)
Q. 게임 시작 시 역할 배정은 어떻게 하나요?

서버가 랜덤 배정 후 개별 통보:

// 역할 배정 시퀀스 [서버] 게임 시작 1. 플레이어 목록: [Red, Blue, Green, Yellow, ...] 2. 임포스터 수 결정: 설정에 따라 (10명이면 2명) 3. 랜덤 선택: random.shuffle(players) impostors = players[0:2] // Red, Green 4. 각 클라이언트에게 **개별** 메시지: → Red에게: { role: IMPOSTOR } → Blue에게: { role: CREWMATE } → Green에게: { role: IMPOSTOR } ... [클라이언트] 5. 받은 역할만 메모리에 저장 myRole = IMPOSTOR; // Red의 경우 6. UI 표시: if (myRole == IMPOSTOR) { ShowImpostorUI(); // 킬 버튼, 사보타지 } else { ShowCrewmateUI(); // 태스크 목록 }

Part 3: 클라이언트 해킹 방지

Q. 메모리 해킹 프로그램으로 역할을 못 본다고 했는데, 정말 불가능한가요?

자기 역할은 볼 수 있지만, 다른 사람 역할은 절대 불가:

┌─────────────────────────────────────────────────────┐ │ 메모리 해킹 시도 vs 실제 데이터 │ └─────────────────────────────────────────────────────┘ [Red의 클라이언트 메모리] myRole = IMPOSTOR ← 해킹으로 읽을 수 있음 myTasks = null ← 임포스터는 태스크 없음 otherPlayers = [ { id: "Blue", position: (10, 5), isAlive: true }, { id: "Green", position: (15, 8), isAlive: true } ] ← role 정보가 없음! 서버가 안 보냈음! [해커가 시도할 수 있는 것] ✓ 자기 역할 확인 (하지만 이미 화면에 나옴) ✓ 자기 위치 조작 (→ 서버 검증으로 차단) ✗ 다른 사람 역할 확인 (데이터 자체가 없음)
핵심 원칙

"클라이언트는 알 필요가 있는 것만 받는다."

Q. 그럼 해킹이 완전히 불가능한가요?

아닙니다. 행동 기반 해킹은 가능합니다:

// 해킹 가능한 것들 (자기 클라이언트만) 1. 이동 속도 조작 → 서버 검증: "거리/시간" 계산, 불가능한 속도면 차단 2. 벽 통과 → 서버 검증: 충돌 체크, 벽 안쪽 위치면 거부 3. 태스크 자동 완료 → 서버 검증: 최소 시간 체크, 너무 빠르면 의심 4. 킬 쿨다운 무시 (클라이언트에서 쿨다운 제거) → 서버 검증: 서버도 타이머 관리, 쿨다운 안 끝났으면 거부 5. 무한 비전 (시야 확장) → 막기 어려움! (클라이언트 렌더링 영역)

완벽한 방지는 불가능하지만, 중요한 것들은 서버 검증으로 막습니다.

Part 4: 투표 시스템의 서버 권위

Q. 투표 조작은 어떻게 막나요?

투표는 서버가 완전히 통제합니다:

// 투표 시스템 (서버 권위) [클라이언트] 1. 플레이어가 "Red" 선택 2. "나는 Red에게 투표" → 서버 전송 { voterID: "Blue", targetID: "Red" } [서버] 3. 검증: ✓ Blue가 살아있는가? ✓ 이미 투표했는가? (중복 투표 방지) ✓ Red가 유효한 대상인가? ✓ 투표 시간이 끝나지 않았는가? 4. 투표 기록 votes["Blue"] = "Red"; 5. 모든 플레이어에게 브로드캐스트 "Blue가 투표를 완료했습니다" (누구한테인지는 숨김!) [투표 종료] 6. 서버가 집계 Red: 5표 Blue: 2표 Skip: 3표 7. 결과 계산 (과반수 체크) totalVotes = 10; Red가 5표 → 50% (과반수 아님, 동점 처리) 8. 결과 브로드캐스트 "아무도 추방되지 않았습니다"
클라이언트는 못 보는 것
  • 투표 진행 중 누가 누구한테 투표했는지 (익명)
  • 실시간 득표 수
  • 투표 결과 집계 과정

모든 계산은 서버에서만 발생!

Part 5: 메모리 해킹 시도와 방어

Q. 실제 해커들은 뭘 시도하나요?

실제로 발생했던 해킹 사례들:

┌─────────────────────────────────────────────────────┐ │ 어몽어스 해킹 케이스 │ └─────────────────────────────────────────────────────┘ 1. 이동 속도 해킹 (Speed Hack) [해킹] 클라이언트: moveSpeed = 999 [방어] 서버: 이동 거리 검증 if (distance > maxSpeed * deltaTime) { RejectPosition(); FlagPlayer(); } 2. 비전 해킹 (Wallhack / Extended Vision) [해킹] 클라이언트: visionRadius = 999 [방어] 불가능 (클라이언트 렌더링) → 게임플레이에 치명적이진 않음 3. 투표 조작 [해킹] "나 10표 투표했어" 전송 [방어] 서버: 1인 1표 검증 if (alreadyVoted[playerID]) { Reject(); } 4. 임포스터 사칭 [해킹] "나 킬 할래" (크루메이트가 전송) [방어] 서버: if (role != IMPOSTOR) { Reject(); Ban(); } 5. 회의 스팸 [해킹] 긴급 회의 버튼 연타 [방어] 서버: 쿨다운 + 횟수 제한 검증
Q. 서버 검증의 한계는 뭔가요?

클라이언트에서 계산하는 것은 막기 어렵습니다:

  • 시야 확장 - 클라이언트가 렌더링하므로 조작 가능
  • ESP (벽 투시) - 다른 플레이어 위치를 화면에 표시
  • 자동 에임 - 어몽어스는 슈팅이 아니라 해당 없음
트레이드오프

모든 렌더링을 서버에서 하면 해킹 방지는 쉽지만, 입력 지연이 생기고 서버 비용이 폭증합니다. 어몽어스는 게임플레이 중요도에 따라 선택적으로 방어합니다.

Part 6: 모드/핵 문제와 대응

Q. 모드는 어떻게 만들어지나요?

어몽어스는 공식 모드 지원 없음, 하지만 비공식 모드가 많습니다:

// 비공식 모드 작동 방식 1. 클라이언트 바이너리 역컨파일 → Unity 게임이라 비교적 쉬움 (IL2CPP 난독화 있지만) 2. 코드 수정 - 새 역할 추가 (Jester, Sheriff 등) - UI 변경 - 새 능력 추가 3. 수정된 클라이언트 배포 → 모드 사용자끼리만 플레이 가능 [문제점] - 공식 서버와 호환 안 됨 - 해킹과 구분 어려움 - 업데이트 시 깨짐
개발사의 딜레마
  • 모드 허용 → 창의적 플레이, 하지만 해킹과 경계 모호
  • 모드 금지 → 깔끔하지만 커뮤니티 불만

어몽어스는 비공식 모드 묵인 정책 (공식 서버만 보호)

Q. 앞으로 어떻게 개선할 수 있나요?

가능한 개선 방향:

// 개선 방안 1. 안티치트 강화 - 클라이언트 무결성 검증 (해시 체크) - 행동 패턴 AI 분석 (비정상 플레이 탐지) - 신고 시스템 + 수동 리뷰 2. 공식 모드 API 제공 - 서버 측 스크립팅 (안전한 커스터마이징) - 역할/규칙 커스텀 옵션 - 치팅 불가능한 범위 내에서 자유도 제공 3. 신뢰 시스템 - 정상 플레이어: 신뢰 점수 상승 - 의심 플레이어: 별도 매칭 풀 - 신고 누적 시 영구 차단 4. 서버 측 검증 확대 - 더 많은 계산을 서버로 이동 - 클라이언트는 입력만 전송 (하지만 비용 증가 트레이드오프)

정리

  • 정보 은닉: 서버만 모든 비밀을 알고, 클라이언트는 필요한 것만
  • 역할 배정: 서버가 랜덤 선택 후 개별 통보, 메모리 해킹 불가
  • 서버 검증: 킬, 투표, 태스크 등 핵심 액션은 서버가 판정
  • 해킹 방어: 중요도에 따라 선택적 방어 (완벽 방지는 불가)
  • 투표 익명성: 투표 과정은 서버만 알고 결과만 공개
  • 모드 딜레마: 비공식 모드 묵인, 공식 서버는 엄격 관리

핵심 교훈: "클라이언트를 절대 믿지 마라." 모든 중요한 결정은 서버에서, 클라이언트는 UI만 담당하게 설계합니다.
