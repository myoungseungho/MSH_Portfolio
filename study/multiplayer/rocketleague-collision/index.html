물리 충돌 권위 서버

Part 1: 동시 충돌은 왜 문제인가요?

네트워크 지연 때문에 "동시"의 기준이 애매합니다.

상황: 양쪽에서 공을 향해 돌진

[플레이어 시점 vs 실제 타이밍] 플레이어 A (한국, 핑 20ms): 내 화면: 00:00.000 → 공 터치! ⚽ ←● 서버 도착: 00:00.020 플레이어 B (미국, 핑 100ms): 내 화면: 00:00.000 → 공 터치! ⚽ ←● 서버 도착: 00:00.100 서버 입장: A가 먼저 도착 (0.020) B가 나중 도착 (0.100) → A의 터치가 먼저! 하지만 B의 화면에서는: "내가 먼저 쳤는데?" ← 불공평하게 느껴짐
동시 충돌의 딜레마
  • 모든 플레이어가 자기 화면에서는 "먼저 쳤다"고 생각
  • 하지만 서버에는 순차적으로 도착
  • 누구를 우선할 것인가?
// 동시 충돌 시나리오 struct CollisionEvent { PlayerID player; Timestamp clientTime; // 클라 화면에서의 시간 Timestamp serverTime; // 서버 수신 시간 Vector3 ballPos; Vector3 carPos; } // 서버가 받은 이벤트들 CollisionEvent eventA = { player: A, clientTime: 00:00.000, // 둘 다 같은 시간! serverTime: 00:00.020, // 하지만 도착 시간 다름 ... }; CollisionEvent eventB = { player: B, clientTime: 00:00.000, // 둘 다 같은 시간! serverTime: 00:00.100, ... }; // 누구 것을 채택?

추가 복잡도:

  • 핑 차이: 20ms vs 100ms
  • 패킷 손실: A의 입력이 누락되면?
  • 순서 역전: 네트워크 라우팅으로 순서 바뀜
  • 프레임 차이: A는 144 FPS, B는 60 FPS

해결책이 필요합니다 → 서버 권위

Part 2: 서버가 유일한 진실이란?

Single Source of Truth: 서버만이 최종 결정권을 가집니다.

[권위 서버 모델] 클라이언트 A 서버 (권위) 클라이언트 B ● ────입력──→ ⚽ ←──입력──── ● (예측) (진실) (예측) │ │ │ │ ←───보정──── │ ────보정───→ │ ↓ ↓ ↓ 수정됨 확정됨 수정됨
서버 권위의 핵심 규칙
  1. 클라이언트는 예측만 함
  2. 서버가 물리 시뮬레이션 실행
  3. 서버 결과가 최종 진실
  4. 클라이언트는 서버 결과로 보정
// 서버 권위 충돌 처리 void ServerProcessCollisions() { // 1. 모든 입력 수집 (타임스탬프 순 정렬) List inputs = GatherAllInputs(); inputs.SortByServerTimestamp(); // 서버 도착 순서! // 2. 순서대로 물리 시뮬레이션 foreach (Input input in inputs) { ApplyCarInput(input.carID, input.steering, input.boost); Physics.Simulate(FIXED_TIMESTEP); // 1/60초 // 3. 충돌 검사 if (Physics.CheckCollision(car, ball)) { // 서버가 유일하게 충돌 판정 Vector3 impulse = CalculateImpulse(car, ball); ball.ApplyImpulse(impulse); // 4. 이벤트 기록 LogCollision(input.carID, ball.position, impulse); } } // 5. 최종 상태 브로드캐스트 BroadcastBallState(ball.position, ball.velocity); }

이 방식의 장점:

  • 일관성: 모든 플레이어가 같은 결과 받음
  • 공정성: 핑 낮은 사람이 무조건 유리하지 않음 (서버가 판단)
  • 치트 방지: 클라가 "나 골 넣었어!"라고 주장해도 서버가 검증
[동시 충돌 해결 과정] 00:00.000 - A, B 동시에 공 터치 (자기 화면에서) 00:00.020 - 서버 수신: A의 입력 → 물리 시뮬: A가 공 터치 ✓ → 공이 A 방향으로 날아감 00:00.100 - 서버 수신: B의 입력 → 물리 시뮬: 공이 이미 멀어짐 → B는 허공에 터치 ✗ 00:00.130 - 모든 클라에 결과 전송 "A가 터치함, 공 위치 (X, Y, Z)" 00:00.150 - B의 화면 보정 "어? 내가 못 쳤네?" (고스팅)

핑 보상 (Lag Compensation):

  • 서버가 클라의 핑을 고려해서 판정
  • B의 입력이 100ms 늦게 도착했지만, 100ms 전 상태로 되감기
  • → B가 입력한 시점의 월드 상태에서 충돌 검사
  • → 공정한 판정 (Favor the Shooter)

Part 3: 클라이언트 예측은 왜 필요한가요?

서버 응답을 기다리면 입력 지연이 너무 크기 때문입니다.

예측 없이 플레이한다면:

[예측 없는 경우 (핑 50ms)] 00:00.000 - 플레이어: 부스트 입력 화면: 그대로 (아무 반응 없음) 00:00.050 - 서버: 입력 수신 + 처리 서버: 차가 앞으로 감 00:00.100 - 클라: 서버 응답 수신 화면: 이제야 차가 움직임! 😱 → 입력 후 100ms 지연 = 게임 불가능
클라이언트 예측 (Client-Side Prediction) 클라이언트가 즉시 물리 시뮬레이션을 실행해서 입력 반응을 보여주고, 나중에 서버 결과로 보정합니다.
// 클라이언트 예측 흐름 void ClientUpdate() { // 1. 입력 받기 Input input = GetPlayerInput(); // 2. 즉시 로컬 시뮬레이션 (예측) ApplyInputToLocalCar(input); LocalPhysics.Simulate(); // Deterministic! // 3. 서버로 입력 전송 (비동기) SendToServer(input, currentFrame); // 4. 렌더링 (예측 결과 표시) RenderCar(localCar.position); // 즉시 반영! RenderBall(predictedBall.position); // ───────────────────────────────────── // 5. 서버 응답 수신 (나중에 도착) if (ReceivedServerUpdate) { ServerState state = GetServerState(); // 6. 예측과 비교 float error = Distance(predictedBall.pos, state.ballPos); if (error > THRESHOLD) { // 7. 보정 필요 CorrectPrediction(state); } } }
[예측 vs 보정 타임라인] 00:00.000 - 입력 (부스트!) 예측: 차 즉시 가속 ✓ 서버: 입력 전송 → 00:00.050 - 서버 처리 서버: 차 가속 계산 00:00.100 - 서버 응답 수신 비교: 예측 vs 서버 거의 일치! → 보정 없음 플레이어 경험: - 입력 즉시 반응 (0ms 지연 느낌) - 99% 예측이 맞아서 보정 안 느껴짐

예측이 정확한 이유:

  • Deterministic Physics: 같은 입력 → 같은 결과
  • 클라와 서버가 동일한 물리 엔진 사용
  • → 예측 정확도 95% 이상

예측이 틀린 경우:

  1. 다른 플레이어가 공을 쳤을 때 (내가 몰랐던 입력)
  2. 패킷 손실로 입력 누락
  3. 서버가 충돌 판정을 다르게 함 (핑 보상)

Part 4: 고스팅 현상이 뭔가요?

예측과 서버 결과가 달라서 공/차가 순간이동하는 현상입니다.

[고스팅 발생 과정] 클라이언트 예측: 00:00.000 ⚽ → → → ●공 (예측) (내가 쳤다고 생각) 서버 진실: 00:00.020 ⚽ ↑ ↑ ↑ ●공 (실제) (상대가 먼저 쳤음) 클라이언트 보정: 00:00.100 ●공 (예측) ↓ 순간이동! (고스팅) ●공 (서버 위치로 보정)
고스팅의 원인
  • 클라: "내가 공을 왼쪽으로 쳤다" (예측)
  • 서버: "상대가 먼저 쳐서 공이 위로 갔다" (진실)
  • → 공이 갑자기 위치 변경 (텔레포트)
// 고스팅 발생 시나리오 // 클라이언트 A void ClientA_Update() { // 예측: 내가 공을 쳤다! if (LocalPhysics.CheckCollision(myCar, ball)) { ball.velocity = Vector3(-100, 0, 0); // 왼쪽으로 predictedBallPos = ball.position; } } // 서버 (실제) void Server_Update() { // 사실: B가 먼저 쳤음 // (A의 입력이 10ms 늦게 도착) if (Physics.CheckCollision(carB, ball)) { ball.velocity = Vector3(0, 100, 0); // 위로! } // A의 입력 처리 시점엔 공이 이미 위로 날아감 if (Physics.CheckCollision(carA, ball)) { // 충돌 안 함 (공이 이미 멀어짐) } BroadcastBallState(ball.position); // 위쪽 위치 전송 } // 클라이언트 A (보정) void ClientA_OnServerUpdate(ServerState state) { float distance = Distance(predictedBallPos, state.ballPos); // distance = 50 (왼쪽 vs 위) // 고스팅 발생! ball.position = state.ballPos; // 갑자기 위로 이동 }

고스팅 완화 기법:

1. 스무딩 (Smoothing)

// 즉시 텔레포트 대신 부드럽게 이동 void SmoothCorrection(Vector3 predicted, Vector3 server) { float distance = Distance(predicted, server); if (distance < 10) { // 오차 작음 → 선형 보간 (0.5초에 걸쳐) LerpPosition(predicted, server, 0.5f); } else if (distance < 50) { // 오차 중간 → 빠른 보간 (0.2초) LerpPosition(predicted, server, 0.2f); } else { // 오차 큼 → 즉시 보정 (텔레포트) ball.position = server; } }

2. 예측 재계산 (Replay)

// 서버 상태로 되돌린 후 예측 재실행 void ReconcilePrediction(ServerState state, int serverFrame) { // 1. 서버 상태로 되돌리기 ball.position = state.ballPos; ball.velocity = state.ballVel; // 2. 서버 프레임 이후 입력들 재적용 for (int frame = serverFrame + 1; frame <= currentFrame; frame++) { Input input = savedInputs[frame]; ApplyInput(input); Physics.Simulate(); } // 3. 새로운 예측 결과 // (서버 진실 + 내 최근 입력들) }
[예측 재계산 과정] 서버 상태 (Frame 100): ⚽ 공 위치: (0, 100) 클라 저장된 입력: Frame 101: 부스트 Frame 102: 점프 Frame 103: 왼쪽 재계산: (0, 100) → 부스트 → 점프 → 왼쪽 → (50, 110) ↑ 서버 진실 새 예측 ↑

로켓 리그의 실제 경험:

  • 평소 (핑 30ms): 고스팅 거의 없음
  • 동시 터치 시: 약간의 떨림 (보정)
  • 렉 걸릴 때 (핑 200ms): 공이 튀어다님

Part 5: 보정을 어떻게 시각화하나요?

클라이언트 스무딩으로 부드럽게 만듭니다.

문제: 서버 업데이트가 30Hz (33ms마다)

  • 클라는 60 FPS 렌더링
  • → 서버 데이터 사이에 빈 프레임 존재
  • → 끊겨 보일 수 있음
[30Hz 서버, 60 FPS 렌더링] 서버: S1 S2 S3 S4 ●─────────●─────────●─────────● (0ms) (33ms) (66ms) (99ms) 렌더: ●──●──●──●──●──●──●──●──●──●──● 0 16 33 50 66 83 99... ↑ ↑ ↑ 보간 필요 보간 보간
다층 스무딩 전략
  1. 예측: 내 차는 즉시 반응 (입력 지연 0)
  2. 보간: 공은 서버 상태 사이 보간
  3. 외삽: 다른 차는 미래 예측
  4. 보정: 오차 발생 시 부드럽게 조정
// 객체별 스무딩 전략 // 내 차: 예측 (지연 없음) void RenderMyCar() { position = localPrediction.carPos; // 즉시 반영 Render(position); } // 공: 보간 (과거 두 지점 사이) void RenderBall() { ServerState prev = serverStates[0]; // 33ms 전 ServerState next = serverStates[1]; // 현재 float t = (currentTime - prev.time) / (next.time - prev.time); position = Lerp(prev.ballPos, next.ballPos, t); Render(position); } // 다른 플레이어: 외삽 (미래 예측) void RenderOtherCar(CarID id) { ServerState last = serverStates[0]; float elapsed = currentTime - last.time; // 속도 기반 예측 position = last.carPos + last.carVel * elapsed; Render(position); } // 충돌 시: 보정 (오차 수정) void CorrectBall() { if (predictionError > THRESHOLD) { // 3프레임에 걸쳐 부드럽게 보정 for (int i = 0; i < 3; i++) { float t = i / 3.0f; correctedPos = Lerp(wrongPos, correctPos, t); Render(correctedPos); WaitFrame(); } } }
[보정 스무딩 시각화] 프레임: 1 2 3 4 위치: 예측 ●──────●──────● \ \ \ \ \ \ 서버 보정 도착 \ \ ↘ 보정 ●──────●──────● 부드럽게 이동 vs 즉시 보정: 예측 ●──────●──────● │ 뚝 끊김! 보정 └──●

추가 시각 효과:

트레일 (Trail)

  • 공 뒤에 잔상 효과
  • 순간이동 느낌 완화
  • 속도감 강조

모션 블러

  • 빠른 움직임 시 블러 처리
  • 고스팅 눈속임

파티클 효과

  • 충돌 시 불꽃 효과
  • 위치 불확실성을 가림
// 시각 효과로 보정 숨기기 void RenderBallWithEffects() { // 1. 보정 감지 if (wasCorrected) { // 2. 파티클 효과 생성 SpawnParticles(ball.position, 10); // 3. 모션 블러 증가 motionBlurStrength = 0.8f; // 4. 트레일 길이 증가 trailLength = 5.0f; } // 5. 렌더링 RenderBall(ball.position); RenderTrail(ball.trail); RenderParticles(); }

결과: 플레이어는 보정을 거의 눈치채지 못함

Part 6: 네트워크 지연과 경쟁의 공정성은?

핑 보상(Lag Compensation)으로 공정성을 유지합니다.

문제: 핑 차이가 경쟁력 차이로 이어짐

[핑 차이의 영향] 플레이어 A (핑 20ms): 입력 → 20ms → 서버 처리 → 20ms → 결과 총 지연: 40ms 플레이어 B (핑 100ms): 입력 → 100ms → 서버 처리 → 100ms → 결과 총 지연: 200ms → A가 160ms 유리? (불공정)
핑 보상 (Lag Compensation) 서버가 각 플레이어의 핑을 고려해서 "그 시점의 과거"로 되돌려 판정합니다.
// 핑 보상 시스템 void ServerProcessInput(PlayerID player, Input input) { // 1. 플레이어 핑 확인 int ping = GetPlayerPing(player); // 예: 100ms // 2. 입력이 발생한 과거 시점 계산 Timestamp inputTime = currentTime - ping; // 3. 월드 상태를 과거로 되돌림 (Rewind) WorldState pastState = RewindToTime(inputTime); // 4. 과거 시점에서 충돌 검사 if (pastState.CheckCollision(player.car, ball)) { // 5. 충돌 인정! (공정한 판정) ApplyImpulse(ball, player.car); // 6. 현재로 돌아옴 FastForwardToPresent(); } } // 월드 되감기 구현 WorldState RewindToTime(Timestamp targetTime) { // 과거 상태 스냅샷 로드 // (보통 100ms 분량 저장) return stateHistory.GetStateAt(targetTime); }
[핑 보상 작동 원리] 현재 (100ms): A ●─────⚽ (공이 멀리 있음) B의 입력 도착 (100ms 지연): "나 50ms 전에 공 쳤어요" 서버 되감기 (50ms 시점): A ●───⚽ B ● (B가 공 터치!) ↑ 이 시점에서 충돌 검사 충돌 인정 → 공이 날아감 현재로 복귀: A ● ⚽→ B ● (B의 터치 반영됨)

공정성 보장:

  • 핑 20ms 플레이어: 20ms 전 상태로 판정
  • 핑 100ms 플레이어: 100ms 전 상태로 판정
  • → 둘 다 자기 화면에서 본 그대로 판정받음

한계:

  1. 상호 고스팅: A는 "내가 먼저 쳤는데", B도 "내가 먼저 쳤는데"
  2. 보상 한계: 핑 200ms 이상은 보상 어려움
  3. 히트박스 확장: 과거 판정이라 실제보다 넓게 느껴짐
// 핑 제한 정책 void MatchmakingFilter(Player player) { if (player.ping > 150) { // 고핑 플레이어는 별도 매칭 AssignToHighPingLobby(player); } else { // 일반 매칭 AssignToNormalLobby(player); } } // 경쟁전 핑 제한 void RankedMatchRequirement(Player player) { if (player.ping > 100) { ShowWarning("핑이 높아 경쟁력이 떨어질 수 있습니다"); } if (player.ping > 200) { BlockRankedMatch(player); // 랭크 진입 차단 } }

로켓 리그의 실제 정책:

  • 지역별 서버 (북미, 유럽, 아시아 등)
  • 핑 표시 (매치 전 확인 가능)
  • 핑 100ms 이하 권장
  • 경쟁전은 핑 150ms 제한
결론 완벽한 공정성은 불가능하지만, 핑 보상으로 대부분의 경우 공정한 판정이 가능합니다.

📚 핵심 요약

  • 동시 충돌 문제: 네트워크 지연으로 "동시"의 기준이 애매함
  • 서버 권위: 서버만이 최종 판정권 (Single Source of Truth)
  • 클라 예측: 즉시 반응 위해 로컬 시뮬레이션 → 나중에 서버 보정
  • 고스팅: 예측과 서버 결과 불일치로 순간이동 → 스무딩으로 완화
  • 다층 스무딩: 예측+보간+외삽+보정으로 부드러운 경험 제공
  • 핑 보상: 각 플레이어 핑만큼 과거로 되돌려 공정한 판정
