Projectile Replication 전략

Part 1: 히트스캔 vs 투사체

Q: "총알이랑 로켓이랑 뭐가 다른가요?"

A: 히트스캔은 즉시 판정, 투사체는 날아가는 물리 객체입니다.

히트스캔 (Assault Rifle, Pistol): ━━━━━━━━━━━━━━━━━━━━━💥 발사 즉시 레이캐스트 → 즉시 판정 빛의 속도 (무한대) 물리 객체 없음 투사체 (Rocket, Grenade): ●─────→─────→─────→💥 발사 → 비행 → 충돌 → 폭발 실제 속도 (예: 100m/s) 물리 객체 존재 (중력, 공기저항 영향)
// 히트스캔 - 간단 OnPlayerFireHitscan(): ray = CreateRay(player.position, player.aimDirection) hit = RaycastWorld(ray, maxDistance=1000m) if hit.isPlayer: ApplyDamage(hit.player, weapon.damage) // 끝! (물리 시뮬레이션 없음) // 투사체 - 복잡 OnPlayerFireProjectile(): projectile = CreateProjectile() projectile.position = player.gunMuzzle projectile.velocity = player.aimDirection * projectileSpeed // 매 프레임 업데이트 필요! AddToPhysicsSimulation(projectile)
왜 구분하나요?
히트스캔: 네트워크 부하 낮음 (판정 결과만 전송)
투사체: 네트워크 부하 높음 (위치를 계속 업데이트)
→ 투사체는 특별한 최적화가 필요!

Part 2: 투사체 동기화의 문제

Q: "100명이 로켓을 쏘면 서버가 터지지 않나요?"

A: 네, 순진하게 구현하면 터집니다. 계산해볼까요?

⚠️ 투사체 폭발 시나리오:
100명 × 초당 10발 = 초당 1000개 투사체 생성
투사체 수명: 평균 3초 (폭발/충돌까지)
동시 존재 투사체: 1000 × 3 = 3000개

매 틱마다 (초당 30틱):
• 3000개 위치 업데이트
• 3000개 × 100명 = 300,000 네트워크 메시지
• 초당 9,000,000 메시지!

대역폭: 9M × 100바이트 = 900MB/초 💥 서버 폭발!
순진한 투사체 동기화: 서버: ├─ Rocket #1: 위치 업데이트 → 100명에게 브로드캐스트 ├─ Rocket #2: 위치 업데이트 → 100명에게 브로드캐스트 ├─ ... (3000개) └─ Rocket #3000: 위치 업데이트 → 100명에게 초당 전송량: 3000 투사체 × 30 틱 × 100 플레이어 = 9,000,000 메시지 ❌ 현실적으로 불가능

Part 3: 서버 사이드 투사체 (권위 있는 판정)

Q: "그럼 어떻게 해야 하나요?"

A: 서버가 투사체를 시뮬레이션하되, 최적화 기법을 여러 개 조합합니다.

전략 1: 관심 영역(AOI) 필터링

// 가까운 투사체만 전송 OnProjectileUpdate(projectile): for player in allPlayers: distance = Distance(player.position, projectile.position) // 100m 이내 플레이어에게만 전송 if distance < 100m: SendProjectileUpdate(player, projectile) // 멀리 있는 투사체는 무시

전략 2: 업데이트 빈도 조절

// 거리에 따라 업데이트 빈도 차등 GetUpdateFrequency(player, projectile): distance = Distance(player.position, projectile.position) if distance < 20m: return 30 // 매 틱 (30Hz) elif distance < 50m: return 10 // 3틱마다 (10Hz) elif distance < 100m: return 3 // 10틱마다 (3Hz) else: return 0 // 업데이트 안 함
거리별 업데이트 빈도: 플레이어 ● ├─ 20m 이내: 🚀 30Hz (매우 정확) ├─ 50m 이내: 🚀 10Hz (적당히 정확) ├─ 100m 이내: 🚀 3Hz (대략적) └─ 100m 초과: 🚀 0Hz (업데이트 안 함) 절감 효과: 전체 업데이트: 3000 투사체 × 30Hz = 90,000/초 최적화 후: 평균 300 투사체 × 15Hz = 4,500/초 절감률: 95% 🎉

Part 4: 클라이언트 예측 투사체 (반응성)

Q: "서버에서만 시뮬레이션하면 발사가 느리지 않나요?"

A: 클라이언트도 로컬 투사체를 만들어서 즉시 보여줍니다.

// 클라이언트: 로컬 예측 투사체 OnPlayerFireProjectile(): // 1. 즉시 로컬 투사체 생성 (예측) localProjectile = CreateProjectile() localProjectile.position = gunMuzzle localProjectile.velocity = aimDirection * speed localProjectile.isPredicted = true // 서버 확인 전 // 2. 로컬 물리 시뮬레이션 AddToLocalPhysics(localProjectile) // 3. 서버에 발사 요청 SendToServer(FIRE_PROJECTILE, { position: gunMuzzle, direction: aimDirection, timestamp: currentTime }) // 서버 투사체 도착 시 OnServerProjectileCreated(netID, position, velocity): // 로컬 예측 투사체를 서버 버전으로 교체 if localProjectile.exists: // 위치 차이 계산 posError = Distance(localProjectile.position, position) if posError < 1m: // 오차 작음: 부드럽게 보정 localProjectile.netID = netID localProjectile.isPredicted = false SmoothCorrect(localProjectile, position, velocity) else: // 오차 큼: 즉시 교체 (덜컥거림) Destroy(localProjectile) CreateServerProjectile(netID, position, velocity)
클라이언트 예측 + 서버 동기화: T=0ms: 플레이어 발사 클라: 로컬 투사체 생성 🚀 (즉시!) ●─→─→ 클라: 서버에 요청 전송 T=50ms: 서버 수신 서버: 투사체 생성 (권위) ●─→ 서버: 브로드캐스트 T=100ms: 응답 도착 클라: 로컬 투사체 위치 ─→─→●─→ (예측) 서버: 서버 투사체 위치 ─→●─→ (권위) 클라: 오차 보정 (부드럽게) ─→●─→ (보정 완료)

Part 5: 하이브리드 접근 (로켓 vs 총알)

Q: "모든 투사체를 똑같이 처리하나요?"

A: 아니요. 중요도와 속도에 따라 다르게 처리합니다.

타입 1: 중요 투사체 (로켓, 유탄)

중요 투사체 = 서버 시뮬레이션 + 전체 리플리케이션 특징: • 느림 (100m/s) • 큰 데미지 (100+ HP) • 적은 개수 (동시 50개 이하) • AOE 효과 처리 방식: ✅ 서버가 물리 시뮬레이션 ✅ 모든 클라이언트에 위치 브로드캐스트 (AOI 필터) ✅ 충돌 판정도 서버에서 ✅ 클라이언트는 예측 + 보정 이유: 정확성 최우선 (한 방이 게임 바꿀 수 있음)

타입 2: 일반 투사체 (총알)

일반 투사체 = 클라이언트 시뮬레이션 + 히트만 서버 특징: • 빠름 (800m/s) • 작은 데미지 (10~20 HP) • 많은 개수 (동시 500개+) • 단일 타겟 처리 방식: ✅ 클라이언트가 물리 시뮬레이션 (로컬) ❌ 서버에 위치 전송 안 함 ✅ 충돌 시에만 서버에 보고 (히트 검증) ✅ 다른 클라이언트는 안 봄 (너무 빠름) 이유: 대역폭 절약 (너무 많고 빠름)
로켓 vs 총알 처리 차이: [로켓 - 서버 시뮬레이션] 클라: 🚀 발사 서버: ●─→─→─→ (서버가 시뮬레이션) ↓ 모든 클라: 🚀 (위치 계속 동기화) [총알 - 클라이언트만] 클라: ━━━━💥 (로컬만 보임) 서버: (위치 모름, 히트만 받음) ↓ 서버: "히트 맞나?" 검증만

Part 6: 대역폭 최적화 (스냅샷, 델타 압축)

Q: "투사체 위치를 계속 보내는 게 부담스러운데, 더 줄일 수 없나요?"

A: 델타 압축과 스냅샷 압축으로 대역폭을 줄입니다.

최적화 1: 델타 인코딩

// ❌ 전체 상태 전송 (비효율) SendProjectileUpdate(projectile): Send({ netID: 12345, // 8 bytes position: (100.5, 50.2, 30.1), // 12 bytes (float × 3) velocity: (10.0, 5.0, 0.0), // 12 bytes rotation: (0, 45, 0) // 12 bytes }) // 총 44 bytes // ✅ 델타만 전송 (효율적) SendProjectileDelta(projectile): // 이전 상태와의 차이만 전송 deltaPos = currentPos - lastSentPos Send({ netID: 12345, // 8 bytes deltaX: +0.5, // 2 bytes (int16, cm 단위) deltaY: +0.2, // 2 bytes deltaZ: +0.1 // 2 bytes }) // 총 14 bytes (68% 절감)

최적화 2: 예측 가능한 투사체는 생략

// 직선으로 날아가는 투사체는 중간 업데이트 생략 OnProjectileFire(projectile): // 초기 상태만 전송 Send({ netID: projectile.netID, startPos: projectile.position, velocity: projectile.velocity, gravity: projectile.gravity, fireTime: currentTime }) // 클라이언트가 알아서 계산 // position = startPos + velocity * t + 0.5 * gravity * t^2 // 충돌 시에만 업데이트 OnProjectileHit(projectile, hitPos): Send({ netID: projectile.netID, EVENT: "HIT", hitPos: hitPos })
예측 가능성 활용:
투사체는 물리 법칙을 따르므로 예측 가능!
→ 초기 상태(위치, 속도, 중력)만 알면 경로 계산 가능
→ 중간 업데이트 대부분 생략
→ 충돌/폭발 같은 이벤트만 전송

절감 효과: 초당 30개 업데이트 → 2개 업데이트 (93% 절감)
예측 기반 투사체 동기화: 서버 → 클라이언트: T=0: [SPAWN] 로켓 생성 {pos: (0,0,0), vel: (100,0,0), gravity: (0,-9.8,0)} ↓ 클라: "알았어, 내가 계산할게" T=1: pos = (100, -4.9, 0) ← 로컬 계산 T=2: pos = (200, -19.6, 0) ← 로컬 계산 T=3: pos = (300, -44.1, 0) ← 로컬 계산 ... ↓ T=5: [HIT] 충돌! {hitPos: (500, -122.5, 0)} ↓ 클라: "폭발 이펙트 재생!" 전송량: 2개 메시지 (SPAWN + HIT) vs 순진한 방법: 150개 메시지 (30Hz × 5초)

최적화 3: 중요도 기반 압축

// 가까운 투사체 = 높은 정밀도 // 먼 투사체 = 낮은 정밀도 EncodeProjectilePosition(projectile, playerDistance): if playerDistance < 20m: // 높은 정밀도 (float, 12 bytes) return { x: projectile.x, // float32 y: projectile.y, z: projectile.z } elif playerDistance < 100m: // 중간 정밀도 (int16, 6 bytes) return { x: int16(projectile.x / 0.1), // 10cm 단위 y: int16(projectile.y / 0.1), z: int16(projectile.z / 0.1) } else: // 낮은 정밀도 (int8, 3 bytes) return { x: int8(projectile.x / 1.0), // 1m 단위 y: int8(projectile.y / 1.0), z: int8(projectile.z / 1.0) }

  • 히트스캔 vs 투사체: 히트스캔은 즉시 판정, 투사체는 물리 시뮬레이션 필요
  • 문제: 100명 × 10발/초 = 초당 9백만 메시지 (폭발!)
  • 해결 1: AOI 필터링 (가까운 투사체만 전송) → 95% 절감
  • 해결 2: 거리별 업데이트 빈도 조절 (가까울수록 자주)
  • 해결 3: 클라이언트 예측 (즉시 반응) + 서버 보정
  • 하이브리드: 로켓은 서버 시뮬레이션, 총알은 클라이언트만
  • 압축: 델타 인코딩 + 예측 기반 생략 + 거리별 정밀도
