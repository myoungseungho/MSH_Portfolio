Deterministic Lockstep과 입력 지연

Part 1: e스포츠의 공정성 요구사항

LoL 월드 챔피언십에서 우승 상금이 수십억 원인데, 네트워크 때문에 불공평하면 안 되잖아요?

맞아요! e스포츠는 공정성이 생명이에요. 같은 상황에서 같은 입력을 하면 반드시 같은 결과가 나와야 해요.

Part 2: Deterministic이란? - 같은 입력 = 같은 결과

"Deterministic"이 뭔가요?

결정론적(Deterministic)이라는 뜻이에요. 같은 초기 상태에서 같은 입력을 주면, 항상 같은 결과가 나온다는 거예요.

Deterministic vs Non-Deterministic

// ❌ Non-Deterministic (결과가 매번 달라짐)
function calculateDamage() {
    randomValue = Math.random();  // 0~1 랜덤
    damage = baseDamage * (1 + randomValue);
    return damage;
}

// 같은 상황에서 실행해도 결과가 다름:
// 실행 1: damage = 100 * 1.523 = 152.3
// 실행 2: damage = 100 * 1.847 = 184.7  (다른 결과!)

// ✅ Deterministic (항상 같은 결과)
function calculateDamage(seed) {
    // 고정된 seed로 난수 생성
    pseudoRandom = seededRandom(seed);
    damage = baseDamage * (1 + pseudoRandom);
    return damage;
}

// 같은 seed면 항상 같은 결과:
// seed=12345: damage = 100 * 1.523 = 152.3
// seed=12345: damage = 100 * 1.523 = 152.3  (항상 같음!)

LoL에서 Deterministic이 중요한 이유

리플레이 시스템 작동 방식: 경기 중: ┌─────────────────────────────────────────────────┐ │ Frame 1: Player A presses Q at (100, 200) │ │ Frame 2: Player B moves to (150, 180) │ │ Frame 3: Minion spawns at (50, 50) │ │ ... (30분 동안 수만 개의 입력) │ └─────────────────────────────────────────────────┘ ↓ 저장 (입력만 기록) 리플레이 재생: ┌─────────────────────────────────────────────────┐ │ 저장된 입력을 처음부터 다시 실행 │ │ Deterministic이면: │ │ → 똑같은 경기가 100% 재현됨! │ │ Non-Deterministic이면: │ │ → 크리티컬 확률 달라져서 다른 경기됨 ❌ │ └─────────────────────────────────────────────────┘
실제 구현: LoL은 모든 랜덤 요소(크리티컬, 용 피해량 등)를 Seeded Random으로 구현해요. 각 프레임마다 고유한 seed를 사용하므로 재현 가능해요.

Part 3: Lockstep 방식 - 모두 기다려!

Lockstep이 뭔가요?

모든 클라이언트가 서로를 기다리는 방식이에요. 가장 느린 플레이어를 기준으로 게임이 진행돼요.

Lockstep 작동 원리

전통적인 Lockstep (StarCraft 1 같은 RTS): Frame N 시작: ┌─────────────────────────────────────────────────┐ │ Client A: 입력 전송 → 서버 │ │ Client B: 입력 전송 → 서버 │ │ Client C: 입력 전송 → 서버 │ └─────────────────────────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────┐ │ 서버: 모든 클라이언트 입력 수집 대기 │ │ (A, B, C 모두 도착할 때까지) │ └─────────────────────────────────────────────────┘ ↓ ┌─────────────────────────────────────────────────┐ │ 서버: 모든 입력을 모든 클라이언트에 브로드캐스트│ └─────────────────────────────────────────────────┘ ↓ Frame N+1 시작: ┌─────────────────────────────────────────────────┐ │ 모든 클라이언트가 동일한 입력으로 시뮬레이션 │ │ → Deterministic이므로 결과도 동일! │ └─────────────────────────────────────────────────┘ 타이밍 (핑 20ms vs 100ms): ════════════════════════════════════════════════════ Time 0ms: A, B, C 모두 입력 Time 20ms: A의 입력 도착 Time 100ms: C의 입력 도착 ← 여기까지 대기! Time 120ms: 모든 입력 수신 확인 → Frame N+1 시작 ════════════════════════════════════════════════════ 결과: 게임이 가장 느린 플레이어(C)에 맞춰짐 
// 순수 Lockstep 구현
class LockstepServer {
    int currentFrame = 0;
    Map> frameInputs;

    function onReceiveInput(playerId, input) {
        // 현재 프레임에 입력 저장
        frameInputs[currentFrame].add({
            playerId: playerId,
            input: input,
            timestamp: now()
        });

        // 모든 플레이어 입력 도착 확인
        if (frameInputs[currentFrame].size == totalPlayers) {
            // 모든 클라이언트에 브로드캐스트
            broadcast(frameInputs[currentFrame]);

            // 다음 프레임 진행
            currentFrame++;
        }
        else {
            // 대기... (느린 플레이어 기다림)
        }
    }
}

// 클라이언트 시뮬레이션
class LockstepClient {
    function onReceiveFrameInputs(inputs) {
        // 모든 입력을 게임 상태에 적용
        foreach (input in inputs) {
            applyInput(input);
        }

        // Deterministic 시뮬레이션
        simulateFrame();

        // 다음 프레임 입력 전송
        sendInput(currentFrame + 1);
    }
}

Lockstep의 장단점

장점 단점
✅ 완벽한 동기화 ❌ 가장 느린 플레이어에 맞춰짐
✅ 재현 가능 (리플레이 쉬움) ❌ 핑 높으면 모두 느려짐
✅ 서버 부하 낮음 (계산은 클라이언트) ❌ 입력 지연 느껴짐
✅ 치팅 감지 쉬움 ❌ 한 명 끊기면 전체 멈춤
역사적 사용: StarCraft 1, Age of Empires 2 같은 고전 RTS가 순수 Lockstep을 사용했어요. 하지만 "한 명 느리면 모두 느려진다"는 문제로 현대 게임은 개선된 방식을 사용해요.

Part 4: 입력 지연 트레이드오프 - Input Delay

Lockstep을 쓰면 버튼 누르고 반응이 늦는 게 당연한가요?

네, 의도적인 지연이에요. 이걸 Input Delay라고 해요. 공정성을 위해 약간의 반응성을 희생하는 거예요.

Input Delay 작동 방식

Input Delay = 100ms 설정된 경우: Time 0ms: 플레이어가 Q 스킬 버튼 누름 ↓ Time 0ms: 클라이언트 → 서버로 입력 전송 ↓ Time 50ms: 서버 수신 (핑 50ms) ↓ Time 100ms: ← Input Delay 대기 중 (아직 실행 안 함) ↓ Time 150ms: 서버가 모든 클라이언트에 브로드캐스트 ↓ Time 200ms: 클라이언트가 수신 (핑 50ms) ↓ Time 200ms: 화면에서 스킬 발동! ⚡ 총 지연: 200ms (느리게 느껴짐)

왜 Input Delay를 추가할까?

// Input Delay 없이:
Player A (핑 20ms):  Time 20ms에 스킬 발동
Player B (핑 100ms): Time 100ms에 스킬 발동
→ 80ms 차이! 불공평!

// Input Delay 100ms 적용:
Player A (핑 20ms):  Time 20+100 = 120ms에 발동
Player B (핑 100ms): Time 100+100 = 200ms에... 아니 잠깐!

// 실제 구현:
function processInput(input, playerPing) {
    // 모든 플레이어의 최대 핑을 기준으로 대기
    maxPing = getMaxPing();  // 예: 100ms
    inputDelay = maxPing + bufferTime;  // 100 + 50 = 150ms

    scheduleExecution(input, now() + inputDelay);
}

// 결과:
Player A (핑 20ms):  Time 150ms에 발동
Player B (핑 100ms): Time 150ms에 발동
→ 동시 발동! 공평!
Input Delay 설정 장점 단점 적합한 게임
0ms 즉각 반응 핑 차이로 불공평 싱글플레이어
50ms 빠른 느낌 여전히 불공평 캐주얼 게임
100~150ms 균형잡힘 약간 느림 LoL, Dota2
200ms+ 완전 공평 너무 느림 턴제 게임
LoL의 선택: 평균 ~130ms Input Delay. 프로 게이머들이 "손맛"이라고 부르는 느낌이 이것 때문이에요!

Part 5: LoL의 선택 - 서버 권위 + 예측

LoL은 순수 Lockstep을 안 쓰나요?

LoL은 Lockstep의 아이디어를 가져오되, 서버 권위(Server Authority)와 클라이언트 예측(Client Prediction)을 섞은 하이브리드 방식을 써요.

LoL의 실제 아키텍처

LoL 네트워크 모델: 클라이언트 측: ┌─────────────────────────────────────────────────┐ │ 1. 플레이어가 스킬 사용 │ │ 2. 즉시 애니메이션 재생 (Prediction) │ │ 3. 서버로 입력 전송 │ └─────────────────────────────────────────────────┘ ↓ (핑 50ms) 서버 측: ┌─────────────────────────────────────────────────┐ │ 4. 입력 수신 및 검증 │ │ 5. Deterministic 시뮬레이션 (seeded random) │ │ 6. 결과 계산 (데미지, 위치 등) │ │ 7. 모든 클라이언트에 브로드캐스트 │ └─────────────────────────────────────────────────┘ ↓ (핑 50ms) 클라이언트 측: ┌─────────────────────────────────────────────────┐ │ 8. 서버 결과 수신 │ │ 9. 예측과 비교: │ │ - 일치: 그대로 유지 │ │ - 불일치: 서버 결과로 보정 (스냅백) │ └─────────────────────────────────────────────────┘ 총 소요 시간: 100ms (50ms 왕복) + Input Delay 
// LoL 스타일 네트워크 코드 (의사코드)
class LoLClient {
    function onPlayerPressQ() {
        // 1. 즉시 로컬 예측
        localSimulation.castSkill(Q);
        playAnimation("Q_Cast");

        // 2. 서버로 입력 전송
        sendToServer({
            type: "CAST_SKILL",
            skill: Q,
            position: mousePosition,
            timestamp: now(),
            frameId: currentFrame
        });

        // 3. 서버 응답 대기 (비동기)
    }

    function onServerResponse(response) {
        if (response.result == "SUCCESS") {
            // 예측이 맞았음 - 그대로 유지
            confirmedState = response.state;
        }
        else if (response.result == "FAILED") {
            // 예측 실패 - 롤백
            rollbackToFrame(response.frameId);
            applyServerState(response.state);
            // 스킬 쿨다운 복구, 마나 복구 등
        }
    }
}

class LoLServer {
    function onReceiveInput(playerId, input) {
        // 1. 치팅 검증
        if (!isValidInput(input)) {
            return sendError("INVALID_INPUT");
        }

        // 2. 스킬 사용 가능 확인
        player = getPlayer(playerId);
        if (!player.canCastSkill(input.skill)) {
            return sendError("SKILL_ON_COOLDOWN");
        }

        // 3. Deterministic 시뮬레이션
        result = simulateSkillCast(player, input);

        // 4. 모든 플레이어에게 브로드캐스트
        broadcast({
            type: "SKILL_CAST",
            casterId: playerId,
            skill: input.skill,
            result: result,
            frameId: currentFrame
        });

        // 5. 게임 상태 업데이트
        applyResult(result);
    }
}
핵심 차이:
  • 순수 Lockstep: 모든 입력 수집까지 대기 → 모든 클라이언트 동시 실행
  • LoL 방식: 클라이언트가 먼저 예측 → 서버가 검증 → 필요 시 보정

Part 6: 실제 프레임 구조 - 30ms마다 한 틱

LoL은 초당 몇 프레임으로 돌아가나요?

서버는 30Hz (33.3ms마다 한 틱)로 작동해요. 이게 LoL의 기본 시간 단위예요!

LoL의 시간 구조

서버 틱 타임라인 (30Hz = 33.3ms per tick): Tick 0 (0ms) : 게임 상태 업데이트, 입력 처리 ↓ ... (33.3ms 대기) ↓ Tick 1 (33.3ms) : 플레이어 위치 계산, 스킬 쿨다운 감소 ↓ ... (33.3ms 대기) ↓ Tick 2 (66.6ms) : 미니언 이동, 정글 몬스터 AI ↓ ... (33.3ms 대기) ↓ Tick 3 (100ms) : 버프 지속시간 감소 ↓ 클라이언트 렌더링: 60Hz (16.6ms) └─→ 서버보다 2배 빠르게 화면 갱신 (부드럽게 보임) └─→ 서버 틱 사이는 보간(interpolation)으로 채움 
// 서버 메인 루프
class GameServer {
    const TICK_RATE = 30;  // Hz
    const TICK_DURATION = 1000.0 / TICK_RATE;  // 33.3ms

    function mainLoop() {
        while (gameRunning) {
            startTime = now();

            // 1. 입력 처리 (지난 틱 이후 쌓인 입력들)
            processAllInputs();

            // 2. 게임 로직 업데이트
            updatePlayerPositions();
            updateSkillCooldowns();
            updateBuffsDurations();
            processDamageCalculations();
            updateMinionAI();

            // 3. 상태 변경 브로드캐스트
            broadcastStateChanges();

            // 4. 다음 틱까지 대기
            elapsedTime = now() - startTime;
            sleepTime = TICK_DURATION - elapsedTime;
            if (sleepTime > 0) {
                sleep(sleepTime);
            }
        }
    }
}

// 클라이언트 보간
class GameClient {
    function renderLoop() {
        while (rendering) {
            // 서버 틱 사이를 부드럽게 연결
            interpolatePositions(
                lastServerState,
                currentServerState,
                progress
            );

            // 60fps로 화면 그리기
            renderFrame();
            sleep(16.6ms);  // 60Hz
        }
    }
}
게임 서버 Tickrate 클라이언트 FPS 느낌
LoL 30Hz (33ms) 60+ FPS 전략적, 부드러움
Dota 2 30Hz 60+ FPS LoL과 유사
CS:GO 64~128Hz (8~15ms) 200+ FPS 매우 빠름, 정밀
Valorant 128Hz (8ms) 144+ FPS 초정밀
왜 30Hz? MOBA는 FPS보다 전략이 중요해요. 30Hz면 충분히 빠르고, 서버 부하도 적어요. CS:GO처럼 128Hz 쓰면 서버 비용이 4배로 증가하는데, MOBA에선 불필요한 투자예요.

💡 핵심 정리

Deterministic Lockstep이란?

같은 입력은 항상 같은 결과를 만들고, 모든 클라이언트가 동기화된 상태에서 실행하는 네트워크 모델.

핵심 원리: 1. Deterministic (결정론적) 같은 seed + 같은 입력 = 항상 같은 결과 2. Lockstep (동기화) 모든 플레이어가 같은 프레임을 실행 ↓ 3. Input Delay (입력 지연) 공정성을 위해 약간의 반응성 희생

LoL의 하이브리드 접근

  • Deterministic: 랜덤 요소 Seed 기반 (리플레이 가능)
  • 서버 권위: 서버가 최종 판정 (치팅 방지)
  • 클라이언트 예측: 즉각 반응 (느낌 개선)
  • Input Delay ~130ms: 공정성 확보
  • 30Hz 틱: 전략 게임에 적합

장단점 비교

항목 장점 단점
Deterministic 리플레이 완벽, 치팅 감지 쉬움 난수 구현 복잡
Lockstep 완벽한 동기화 느린 플레이어에 영향
Input Delay 핑 차이 불공정 제거 반응 느림
서버 권위 치팅 방지 서버 부하 높음

왜 FPS 게임은 안 쓰나?

  • FPS는 0.01초 차이가 생사 갈림 → Input Delay 수용 불가
  • 대신 Rollback Netcode 사용 (예측 후 되돌림)
  • MOBA는 전략적 판단이 중요 → 100ms 지연 수용 가능
LoL의 교훈: "완벽한 네트워크 모델은 없다. 게임 장르와 목표(공정성 vs 반응성)에 맞춰 트레이드오프를 선택해야 한다."
