치터는 어떻게 서버에서 잡아요?

서버 사이드 안티치트 (Vanguard)

Part 1: 클라이언트 사이드 안티치트의 한계

Q: "게임에 안티치트 프로그램 깔려있잖아요. 그걸로 다 막으면 안 돼요?"

A: 클라이언트(유저 PC)는 절대 믿을 수 없어요.

치터들은 다음과 같은 방법으로 클라이언트 안티치트를 우회합니다:

  • 메모리 조작: 게임 프로세스의 메모리를 직접 수정 (HP 무한, 탄약 무한)
  • DLL 인젝션: 악성 DLL을 게임에 주입해서 코드 실행
  • 드라이버 레벨 치트: 커널 모드에서 안티치트보다 더 깊은 곳에서 동작
  • 패킷 조작: 네트워크 패킷을 중간에서 수정
핵심 원칙: "클라이언트는 적이다" (The client is in the hands of the enemy)
유저 PC에서 실행되는 모든 것은 해킹될 수 있다고 가정해야 합니다.
클라이언트 측 안티치트의 한계: ┌─────────────────────────┐ │ 유저 PC (치터 소유) │ │ ┌───────────────────┐ │ │ │ 게임 클라이언트 │ │ ◀── 메모리 조작 │ │ ┌─────────────┐ │ │ ◀── DLL 인젝션 │ │ │ 안티치트 │ │ │ ◀── 커널 드라이버 우회 │ │ └─────────────┘ │ │ │ └───────────────────┘ │ └─────────────────────────┘ │ │ 패킷 전송 ▼ ┌─────────────────────────┐ │ 게임 서버 │ ◀── 여기서 검증해야 함! └─────────────────────────┘

Part 2: 서버 권위 (Server Authority) 개념

Q: "그럼 서버에서 모든 걸 결정하면 되는 거 아닌가요?"

A: 네, 맞습니다! 이걸 '서버 권위(Server Authority)'라고 해요.

핵심 철학:

  • 클라이언트는 "요청"만 할 수 있다
  • 서버가 최종 "승인/거부"를 결정한다
  • 클라이언트가 보낸 값은 절대 그대로 믿지 않는다
// ❌ 잘못된 방식 (클라이언트 신뢰) OnClientMoveRequest(position, speed): player.position = position // 클라이언트가 보낸 대로 적용 player.speed = speed // 위험! // ✅ 올바른 방식 (서버 검증) OnClientMoveRequest(targetPosition): // 1. 속도 검증 distance = GetDistance(player.position, targetPosition) maxDistance = player.maxSpeed * deltaTime if distance > maxDistance: LogSuspiciousActivity(player) // 의심 활동 기록 RejectMove() // 이동 거부 return // 2. 맵 충돌 검증 if IsInsideWall(targetPosition): RejectMove() return // 3. 승인 player.position = targetPosition BroadcastToOtherPlayers(player.position)
서버 권위 모델: 클라이언트: "저 (500, 200) 위치로 이동할게요!" │ ▼ 서버: 검증 시작 ├─ 속도 체크: 현재 위치에서 0.1초에 갈 수 있나? ✓ ├─ 벽 충돌: 경로에 장애물 있나? ✓ ├─ 맵 경계: 맵 밖으로 나가나? ✓ └─ 스킬 상태: 이동 불가 CC기 걸려있나? ✓ │ ▼ 서버: "승인. (500, 200)으로 이동" │ ▼ 모든 클라이언트: "플레이어 A가 (500, 200)으로 이동했어요"

Part 3: 서버에서 검증하는 것들

Q: "구체적으로 서버가 뭘 체크하나요?"

A: 발로란트 서버가 검증하는 주요 항목들:

1. 이동 속도 검증

// 매 틱마다 검증 ValidateMovement(player, newPosition): timeSinceLastUpdate = currentTime - player.lastUpdateTime expectedMaxDistance = player.moveSpeed * timeSinceLastUpdate actualDistance = Distance(player.lastPosition, newPosition) if actualDistance > expectedMaxDistance * 1.1: // 10% 여유 player.suspicionScore += 10 if player.suspicionScore > 100: TriggerManualReview(player) // 수동 검토 대상

2. 사격 빈도 검증

// 무기별 발사 속도 제한 OnClientFireWeapon(weaponID): weapon = GetWeaponData(weaponID) timeSinceLastShot = currentTime - player.lastShotTime if timeSinceLastShot < weapon.fireInterval: // 연사 핵 의심 LogCheatAttempt("RapidFire", player) return REJECT player.lastShotTime = currentTime ProcessShot()

3. 히트 검증 (가장 중요!)

OnClientReportHit(targetPlayerID, hitPosition, timestamp): // 1. 타임스탬프 검증 (과거 데이터 사용 방지) if timestamp < currentTime - 500ms: return REJECT // 너무 오래된 샷 // 2. 서버에서 과거 상태 재구성 (Lag Compensation) shooterState = RewindPlayer(shooter, timestamp) targetState = RewindPlayer(target, timestamp) // 3. 서버가 직접 레이캐스트 계산 ray = CreateRay(shooterState.position, shooterState.aimDirection) serverHit = RaycastAgainstPlayer(ray, targetState) // 4. 클라이언트가 보고한 히트와 서버 계산 비교 distance = Distance(hitPosition, serverHit.position) if distance > ACCEPTABLE_THRESHOLD: // 예: 10cm LogSuspiciousHit(player) return REJECT // 5. 헤드샷 각도 검증 (Aimbot 탐지) aimSnapSpeed = CalculateAimSpeed(shooter) if aimSnapSpeed > HUMAN_POSSIBLE_SPEED: player.aimbotScore += 5 return ACCEPT
왜 클라이언트가 히트를 "보고"하나요?
네트워크 지연 때문에 서버가 모든 걸 계산하면 반응이 느려집니다. 그래서 클라이언트가 먼저 쏘고 → 서버가 나중에 검증하는 방식입니다.
클라이언트가 거짓말하면? → 서버가 거부합니다.

Part 4: 통계 기반 탐지 (Behavioral Analysis)

Q: "완벽하게 위장한 치트는 어떻게 잡아요?"

A: 통계적으로 '인간답지 않은' 패턴을 찾습니다.

// 경기 후 통계 분석 AnalyzePlayerStats(player, match): stats = { headshotPercentage: player.headshots / player.totalShots, averageReactionTime: CalculateAvgReactionTime(player), aimAcceleration: CalculateAimSmoothness(player), wallbangFrequency: player.wallbangs / player.totalKills, preFiringAccuracy: CountPreFireHits(player) } // 프로 선수 평균과 비교 if stats.headshotPercentage > 0.85: // 프로도 70% 이하 flags.push("UnhumanHeadshotRate") if stats.averageReactionTime < 150ms: // 인간 한계: ~180ms flags.push("SuperhumanReflexes") if stats.aimAcceleration > THRESHOLD: flags.push("RoboticAimMovement") // 마우스 움직임이 너무 완벽 if flags.length > 0: QueueForManualReview(player, flags)
통계 기반 탐지 흐름: 경기 데이터 수집 ├─ 헤드샷 비율: 92% ⚠️ (비정상) ├─ 평균 반응속도: 120ms ⚠️ (인간 한계 초과) ├─ 조준 움직임: 완벽한 직선 ⚠️ (로봇 같음) └─ 벽뚫 킬: 경기당 3회 ⚠️ (우연치고 많음) │ ▼ 머신러닝 모델 분석 ├─ 정상 플레이어 패턴과 비교 ├─ 과거 치터 패턴과 유사도 계산 └─ 이상 점수: 95/100 🚨 │ ▼ 수동 검토 대기열 추가 └─ 운영팀이 리플레이 확인

Part 5: Vanguard의 커널 드라이버 논란

Q: "발로란트 Vanguard는 왜 항상 켜져있고 커널 레벨인가요?"

A: 커널 드라이버 치트를 막기 위해서입니다.

  • 일반 안티치트: 유저 모드에서 실행 → 커널 치트에게 우회됨
  • Vanguard: 커널 모드에서 실행 → 치트와 같은 레벨에서 싸움
  • 항상 켜져있는 이유: 게임 시작 전에 치트가 로드되는 것 방지
트레이드오프:
✅ 장점: 커널 레벨 치트 효과적으로 차단
❌ 단점: 시스템 접근 권한이 높아서 보안/프라이버시 우려
🔍 Riot의 대응: 오픈소스 공개, 보안 감사 허용

Part 6: 오탐과 밸런스

Q: "실수로 정상 유저를 밴하면 어떡해요?"

A: 안티치트는 확신이 100%일 때만 자동 밴합니다.

// 밴 결정 로직 DecidePunishment(player): if player.certaintyScore > 99.9: // 명백한 치트 (메모리 조작 직접 탐지) IssueBan(player, permanent=true) else if player.suspicionScore > 80: // 의심스럽지만 확신 없음 flags = [ FlagForManualReview(player), IncreasedMonitoring(player), ShadowMatchmaking(player) // 다른 의심 유저와 매칭 ] else if player.suspicionScore > 50: // 약간 의심 WatchForPatterns(player)
탐지 → 처벌 파이프라인: 자동 탐지 (서버 검증) ├─ 99.9% 확신: 즉시 영구 밴 (메모리 조작 등) ├─ 80~99%: 수동 검토 대기열 │ └─ 운영팀이 리플레이 확인 → 밴 or 무죄 ├─ 50~80%: 모니터링 강화 │ └─ 다음 경기 집중 관찰 └─ 0~50%: 정상 플레이어 └─ 통계만 수집

📚 핵심 요약

  • 클라이언트는 믿을 수 없다 → 서버가 모든 걸 검증
  • 서버 권위 모델: 클라이언트는 요청만, 서버가 승인/거부
  • 검증 항목: 이동속도, 사격 빈도, 히트 정확도, 반응속도
  • 통계 기반 탐지: 인간답지 않은 패턴 찾기 (헤드샷 92% 등)
  • Vanguard: 커널 드라이버로 치트와 같은 레벨에서 싸움
  • 오탐 방지: 99.9% 확신 있을 때만 자동 밴

결론: 완벽한 안티치트는 없지만, 클라이언트 + 서버 + 통계 + 수동 검토를 조합하면 대부분의 치터를 효과적으로 걸러낼 수 있습니다.
