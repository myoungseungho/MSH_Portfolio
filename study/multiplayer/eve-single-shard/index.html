전 세계가 하나의 서버라고요?

EVE Online의 Single Shard 아키텍처

Part 1: 일반 MMO의 서버 분리 - 왜 친구랑 못 만날까?

WoW 하는데 친구가 "나 아즈샤라 서버야" 그러면 답답하지 않나요?

맞아요! 대부분의 MMO는 서버(렐름)를 수백 개로 나눠요. 그래서 같은 게임을 하는데도 친구가 다른 서버에 있으면 함께 못 놀아요.

전통적인 MMO의 서버 구조

World of Warcraft 서버 구조: 한국 리전 ├─ 아즈샤라 서버 [플레이어 A] ├─ 듀로탄 서버 [플레이어 B] ├─ 헬스크림 서버 [플레이어 C] ├─ 윈드러너 서버 └─ ... (50개 이상) 문제: A와 B는 절대 만날 수 없음! └─ 해결책: 서버 이전 ($25) 또는 새 캐릭터 생성
게임 서버 개수 문제점
World of Warcraft 글로벌 240개 이상 친구 서버 맞춰야 함
Final Fantasy XIV 데이터센터별 분리 서버 이동 제한적
리니지 100개 이상 신규 서버마다 리셋
EVE Online 1개 없음! (모두 같은 우주)
왜 서버를 나눌까?
  • 하나의 서버가 감당할 수 있는 플레이어 수 한계
  • 같은 지역에 플레이어 몰리면 서버 터짐
  • 그래서 어쩔 수 없이 수백 개로 쪼개는 거예요

Part 2: EVE의 혁신 - 전 세계가 하나의 우주

EVE는 어떻게 서버를 안 나누나요?

EVE Online은 전 세계 40만 명의 플레이어가 단 하나의 우주를 공유해요. 한국, 미국, 유럽 모두 같은 서버에서 플레이하죠!

EVE Online Single Shard: ┌───────────────────────────────┐ │ EVE Online Universe │ │ (7,800개의 Star System) │ └───────────────────────────────┘ │ ┌───────────────┼───────────────┐ │ │ │ [한국 유저] [미국 유저] [유럽 유저] 12만 명 15만 명 13만 명 │ │ │ └───────────────┴───────────────┘ 동일한 우주 공유! 서로 만날 수 있음!

Single Shard의 의미

  • Shard = 서버 조각: 다른 MMO는 수백 개의 Shard로 나눔
  • Single Shard: 단 하나의 조각, 즉 하나의 게임 세계
  • 모든 플레이어 행동이 영향을 미침: 진짜 단일 경제
  • 역사가 공유됨: "저 성계에서 대전투가 있었다" = 모두가 아는 사건
실제 사례: 2014년 B-R5RB 전투에서 파괴된 우주선 가치는 약 $300,000 (실제 돈 기준). 이게 가능한 이유는 단일 경제이기 때문이에요!

Part 3: Solar System 기반 분산 - 우주를 쪼개는 방법

그럼 어떻게 40만 명을 한 서버에 수용하나요?

비밀은 우주를 성계(Solar System) 단위로 나누는 것이에요. 전체는 하나의 우주지만, 각 성계는 독립적인 서버 노드에서 실행돼요.

EVE 우주 구조 (간소화): Tranquility Cluster (전체 서버) │ ├─ Jita System (무역 중심지) → Node #347 [4500명] │ └─ 가장 바쁜 성계, 전용 고사양 서버 │ ├─ Amarr System (제국 수도) → Node #128 [1200명] │ ├─ B-R5RB (전투 지역) → Node #89 [200명 → 4000명!] │ └─ 대규모 전투 시 Reinforcement 적용 │ ├─ Nullsec 변방 성계 → Node #1523 [5명] │ └─ 한산한 곳은 여러 성계를 하나의 노드에 │ └─ ... (총 7,800개 성계를 ~500개 노드에 분산) 특징: - 각 노드는 독립적으로 실행 - 플레이어는 성계 간 자유롭게 이동 (워프/점프) - 노드 간 통신으로 단일 우주 유지

구현 원리

// 의사코드: 성계 노드 할당
class SolarSystemNode {
    int nodeId;
    string systemName;
    int maxCapacity;
    int currentPlayers;

    function assignNode() {
        if (isHighTrafficSystem(systemName)) {
            // Jita, Amarr 같은 허브는 전용 노드
            return getDedicatedNode(systemName);
        }
        else if (currentPlayers > maxCapacity) {
            // 과부하 시 Reinforcement
            return requestReinforcementNode();
        }
        else {
            // 일반 성계는 부하 분산
            return getSharedNode(load);
        }
    }
}

// 플레이어 이동 시 노드 전환
function playerJumpToSystem(player, targetSystem) {
    currentNode = player.currentNode;
    targetNode = targetSystem.node;

    // 현재 노드에서 플레이어 상태 직렬화
    playerState = currentNode.serializePlayer(player);

    // 타겟 노드로 전송
    targetNode.receivePlayer(playerState);

    // 클라이언트에 연결 전환 지시
    sendNodeTransition(player.client, targetNode.address);
}
성계 유형 평균 인원 노드 할당 예시
무역 허브 2000~5000명 전용 고사양 노드 Jita 4-4 정거장
주요 도시 500~1500명 전용 중사양 노드 제국 수도들
일반 성계 10~100명 10~20개 성계 공유 하이섹 일반 지역
변방 지역 0~10명 50개 이상 공유 Nullsec 외곽

Part 4: Reinforcement - 대규모 전투 대비

평소엔 10명인데 갑자기 4000명이 모이면 어떻게 하나요?

Reinforcement 시스템이 작동해요! 대규모 전투가 예상되면, 그 성계를 더 강력한 전용 서버로 옮겨요.

Reinforcement 작동 방식

일반 상황: ┌────────────────────────────────┐ │ Standard Node #123 │ │ ├─ System A (10명) │ │ ├─ System B (15명) │ │ ├─ System C (8명) │ │ └─ System D (12명) │ │ Total: 45명 / 200명 capacity │ └────────────────────────────────┘ 대규모 전투 예고: └─→ System C에 1시간 뒤 대전투 예정 Reinforcement 프로세스: 1. System C를 Node #123에서 분리 2. 고사양 전용 노드(Node #999) 준비 3. System C → Node #999 이전 4. System A, B, D는 Node #123에 유지 전투 중: ┌────────────────────────────────┐ │ Reinforced Node #999 │ │ └─ System C (4000명!) │ │ Total: 4000명 / 6000 capacity │ │ TiDi Active: 10% │ └────────────────────────────────┘ 전투 종료 후: └─→ System C를 다시 일반 노드로 복귀 
// Reinforcement 신청 시스템
class ReinforcementRequest {
    string systemName;
    datetime battleTime;
    int expectedPlayers;

    function requestReinforcement() {
        // 플레이어가 직접 신청 (게임 내 UI)
        if (isValidRequest(expectedPlayers, battleTime)) {
            // 1시간 전에 노드 준비
            scheduleNodePreparation(battleTime - 1hour);

            // 공지 발송
            notifyAllPlayers(
                "System " + systemName + " will be reinforced at " + battleTime
            );

            return SUCCESS;
        }
    }
}

// 실제 노드 이전
function migrateToReinforcedNode(system, targetNode) {
    // 1. 새 노드 가동
    targetNode.start();

    // 2. 플레이어 입장 일시 차단 (1분)
    system.blockNewEntries();

    // 3. 현재 플레이어 상태 전송
    foreach (player in system.players) {
        targetNode.transferPlayer(player);
    }

    // 4. 게임 오브젝트 전송 (구조물, NPC 등)
    targetNode.transferObjects(system.objects);

    // 5. 입장 재개
    system.resumeEntries(targetNode);

    log("System migrated successfully!");
}
플레이어 협조: EVE는 대규모 전투 전에 플레이어들이 Reinforcement를 미리 신청할 수 있어요. 1시간 전에 신청하면 CCP가 전용 서버를 준비해줘요!

    // 1. 대규모 전투로 수천 척 파괴
    destroyedShips = 4000;
    materialLoss = {
        Tritanium: 100억 개,
        Pyerite: 50억 개,
        Mexallon: 10억 개

    // 2. 우주 전체 공급 감소

    // 3. 가격 상승 (실제로 발생!)

    Pyerite.price *= 1.22;    // 22% 상승

    // 5. 2주 후 가격 정상화
    waitWeeks(2);
    prices.normalize();
}

// 노드 간 통신 예시
class InterNodeCommunication {
    function sendPlayerToAnotherNode(player, targetSystem) {
        // 1. 플레이어 상태 직렬화
        state = {
            characterId: player.id,
            shipType: player.ship.type,
            cargo: player.ship.cargo,
            position: player.position,
            // ... 100개 이상의 속성
        };

        // 2. 타겟 노드로 메시지 전송
        targetNode = getNode(targetSystem);
        message = {
            type: "PLAYER_TRANSFER",
            data: state,
            timestamp: now()
        };

        targetNode.send(message);

        // 3. 현재 노드에서 제거
        currentNode.removePlayer(player);

        // 4. 클라이언트에 재연결 지시
        player.client.reconnect(targetNode.address);
    }
}

💡 핵심 정리

Single Shard란?

전 세계 모든 플레이어가 단 하나의 게임 세계를 공유하는 아키텍처. 서버를 수백 개로 나누지 않고, 하나의 통합된 우주를 만드는 것.

전통 MMO: 플레이어 ──→ 서버 선택 ──→ 격리된 세계 (친구와 서버 맞춰야 함) EVE Online: 플레이어 ──→ 단일 우주 ──→ 모두 같은 세계 (전 세계 누구나 만날 수 있음)

구현 핵심 기술

  • 성계 단위 분산: 7,800개 성계를 ~500개 노드에 동적 할당
  • Reinforcement: 대규모 전투 시 전용 서버 투입
  • Time Dilation: 과부하 시 게임 내 시간 늦춤
  • 단일 DB: 모든 데이터가 궁극적으로 하나의 DB에

게임 디자인 영향

  • 진짜 단일 경제 (실물 경제처럼 작동)
  • 전쟁과 정치가 우주 전체에 영향
  • 플레이어 행동이 역사로 남음 (B-R5RB 전투 등)
  • 커뮤니티 통합 (서버별 분리 없음)

왜 다른 게임은 안 하나?

  • 기술적 난이도: 20년 개발 경험 필요
  • 게임 장르: 느린 페이스의 우주 시뮬레이션이라 가능
  • 레이턴시: 단일 데이터센터라 일부 지역은 핑 높음
  • TiDi 수용: 플레이어가 느린 전투를 받아들여야 함
EVE의 교훈: "기술적 한계를 극복하는 방법은 더 좋은 하드웨어만이 아니다. 게임 디자인과 플레이어 경험을 재설계하는 것도 답이다."
