10명밖에 없는데 왜 이렇게 재밌어요?

Among Us 최소 State Sync 설계

한 줄 요약

어몽어스는 최소한의 상태만 동기화하여 모바일에서도 부드럽게 작동하며, 단순한 게임 메커니즘이 강력한 심리 게임을 만듭니다.

Part 1: 단순함의 힘 (적은 플레이어, 적은 상태)

Q. 배틀로얄은 100명인데, 10명이면 너무 적지 않나요?

적은 플레이어 수는 의도된 디자인입니다:

10명이 최적인 이유
  • 심리 게임 - 모든 플레이어의 행동을 기억할 수 있음
  • 대화 가능 - 회의 시간에 모두가 발언 기회
  • 낮은 복잡도 - 서버 부하 최소화
  • 빠른 매칭 - 10명만 모으면 시작
┌─────────────────────────────────────────────────────┐ │ 100명 vs 10명 네트워크 복잡도 비교 │ └─────────────────────────────────────────────────────┘ 배틀로얄 (100명): - 필요한 연결: 100명 → 서버 - 초당 업데이트: 100명 × 60Hz = 6000 메시지 - 가시 범위 필터링 필요 - 대역폭: ~1-2 Mbps per player 어몽어스 (10명): - 필요한 연결: 10명 → 서버 - 초당 업데이트: 10명 × 5Hz = 50 메시지 - 모두가 서로 볼 수 있음 - 대역폭: ~50 Kbps per player

10명 = 네트워크 부담 100분의 1 수준이며, 이것이 모바일에서 잘 돌아가는 비결입니다.

Q. 동기화해야 할 것들이 뭐가 있나요?

어몽어스의 동기화 상태는 놀랍도록 단순합니다:

// 플레이어당 동기화 상태 (의사코드) struct PlayerState { // 기본 정보 PlayerID id; // 4 bytes Vector2 position; // 8 bytes (x, y) bool isAlive; // 1 byte Color color; // 1 byte (Red, Blue, Green...) // 역할 (서버만 알고 있음, 클라에는 안 보냄!) Role role; // Crewmate / Impostor (서버 비밀) // 태스크 int tasksCompleted; // 2 bytes bool[] taskList; // 완료한 태스크 비트마스크 // 상태 플래그 bool isVenting; // 벤트 타는 중? bool isInEmergency; // 긴급 회의 중? bool isDead; // 죽음 (유령) } 총 크기: ~20-30 bytes per player 10명 × 30 bytes = 300 bytes per snapshot

초당 5번 업데이트해도 1.5 KB/s밖에 안 됩니다!

Part 2: 동기화가 필요한 상태들 (위치, 태스크, 생존)

Q. 위치 동기화는 어떻게 하나요?

어몽어스는 낮은 업데이트 주기(~5Hz)를 사용합니다:

┌─────────────────────────────────────────────────────┐ │ 위치 동기화 타임라인 │ └─────────────────────────────────────────────────────┘ 시간축: ───────────────────────────────────► t=0ms t=200ms t=400ms t=600ms │ │ │ │ [서버 스냅샷] [서버 스냅샷] [서버 스냅샷] [서버 스냅샷] │ │ │ │ ▼ ▼ ▼ ▼ 위치: 위치: 위치: 위치: (10, 5) (15, 5) (20, 7) (25, 10) 클라이언트는 중간을 보간(Interpolation)으로 채움: (10,5) → (11,5) → (12,5) → ... → (15,5)
왜 5Hz로 충분한가?
  • 느린 이동 속도 - 캐릭터가 빠르게 움직이지 않음
  • 탑다운 뷰 - 정밀한 조준 필요 없음
  • 심리 게임 중심 - 0.1초 차이는 중요하지 않음
Q. 태스크 진행 상황은 어떻게 동기화하나요?

이벤트 기반 동기화를 사용합니다:

// 태스크 완료 시퀀스 [클라이언트] 플레이어가 전선 잇기 완료 1. 미니게임 성공 검증 (로컬) 2. "태스크 완료" 이벤트 → 서버 전송 { eventType: "TASK_COMPLETE", taskID: 5, // 전기실 전선 잇기 playerID: 123 } [서버] 3. 검증: - 플레이어가 전기실에 있는가? - 이 태스크를 이미 완료했는가? 4. 검증 통과 → 서버 상태 업데이트 player.tasksCompleted++ 5. 모든 클라이언트에게 브로드캐스트 "플레이어 123이 태스크 완료, 전체 진행도: 15/20" [모든 클라이언트] 6. UI 업데이트 (진행 바 증가)

위치처럼 매 프레임 보내지 않고, 변화가 있을 때만 전송합니다.

Part 3: 이동 동기화 (위치 보간)

Q. 200ms마다 위치를 받으면 뚝뚝 끊기지 않나요?

선형 보간(Linear Interpolation)으로 부드럽게 만듭니다:

// 위치 보간 의사코드 class RemotePlayer { Vector2 lastPosition; // 마지막 서버 위치 Vector2 targetPosition; // 최신 서버 위치 float lastUpdateTime; float updateInterval = 0.2f; // 200ms void OnServerUpdate(Vector2 newPos) { lastPosition = currentDisplayPosition; targetPosition = newPos; lastUpdateTime = Time.now; } void Update() { // 0 → 1 사이 값으로 시간 경과 비율 계산 float t = (Time.now - lastUpdateTime) / updateInterval; t = Math.min(t, 1.0); // 최대 1 // 선형 보간 currentDisplayPosition = lerp(lastPosition, targetPosition, t); // 화면에 그리기 DrawCharacter(currentDisplayPosition); } } // lerp 함수 Vector2 lerp(Vector2 a, Vector2 b, float t) { return a + (b - a) * t; }
┌─────────────────────────────────────────────────────┐ │ 선형 보간 시각화 │ └─────────────────────────────────────────────────────┘ 서버 업데이트: A (10, 5) ────────────────────► B (20, 5) t=0 t=200ms 클라이언트 화면 (60fps): A → → → → → → → → → → → → → → B | | | | | | | | | 0 3 7 10 13 17 20 23 27 ms ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ ↑ 매 프레임마다 조금씩 이동 (부드러움!)
Q. 누군가 갑자기 방향을 바꾸면요?

어몽어스는 예측을 하지 않습니다. 단순히 보간만 합니다:

FPS vs 어몽어스 차이
  • FPS (예: Overwatch) - 이동 방향 예측, 빠른 반응 필요
  • 어몽어스 - 예측 없음, 200ms 지연 허용

게임 템포가 느려서 지연이 문제되지 않습니다.

Part 4: 액션 동기화 (킬, 투표, 이머전시)

Q. 임포스터가 킬 버튼 누르면 어떻게 되나요?

서버 검증 후 실행하는 방식입니다:

// 킬 액션 시퀀스 [임포스터 클라이언트] 1. 킬 버튼 클릭 (쿨다운 끝난 상태) 2. "킬 시도" → 서버 전송 { action: "KILL", targetPlayerID: 456, impostorPosition: (15, 10), targetPosition: (16, 10) } [서버] 3. 검증: ✓ 임포스터가 맞는가? ✓ 쿨다운이 끝났는가? (서버도 타이머 관리) ✓ 거리가 킬 범위 안인가? (2 타일 이내) ✓ 타겟이 살아있는가? ✓ 긴급 회의 중이 아닌가? 4. 모든 검증 통과 → 킬 실행 targetPlayer.isDead = true; impostor.killCooldown = 20; // 20초 리셋 5. 브로드캐스트 "플레이어 456이 (16, 10) 위치에서 사망" [모든 클라이언트] 6. 킬 애니메이션 재생 7. 시체 오브젝트 생성 8. 죽은 플레이어는 유령 모드로 전환
왜 서버 검증이 중요한가?

클라이언트를 믿으면 해커가 쿨다운 무시, 멀리서 킬, 크루로 킬하는 등의 치팅이 가능합니다.

Q. 투표 시스템은요?

투표는 서버가 집계합니다:

┌─────────────────────────────────────────────────────┐ │ 투표 동기화 흐름 │ └─────────────────────────────────────────────────────┘ [회의 시작] ↓ [서버] 투표 세션 생성 ↓ 각 플레이어: "Red에게 투표" → 서버 ↓ [서버] 투표 집계 Red: 5표 Blue: 2표 Skip: 3표 ↓ [서버] 결과 계산 과반수(6표) 이상? Red 추방 동점? 아무도 추방 안 됨 ↓ 브로드캐스트: "Red가 추방되었습니다" ↓ [모든 클라이언트] 추방 애니메이션

Part 5: 미니게임 동기화 (태스크)

Q. 전선 잇기 같은 미니게임은 어떻게 동기화하나요?

미니게임은 결과만 동기화합니다 (과정은 로컬):

// 미니게임 동기화 방식 [클라이언트] 1. 플레이어가 전선 잇기 미니게임 시작 → 서버에 "태스크 시작" 알림 (선택적) 2. 미니게임은 완전히 로컬에서 실행 - 전선 위치는 클라이언트가 랜덤 생성 - 타이머, UI 모두 로컬 3. 성공 시: "태스크 완료" → 서버 전송 [서버] 4. 검증: - 플레이어가 해당 위치에 있었는가? - 너무 빨리 완료한 건 아닌가? (최소 시간 체크) 5. 통과 → 태스크 완료 처리 [다른 클라이언트] 6. "플레이어 X가 전선 잇기 완료" 수신 → UI 진행 바만 업데이트 → 미니게임 화면은 안 봄 (볼 필요 없음!)
왜 과정을 동기화 안 하나?
  • 불필요 - 다른 플레이어는 미니게임 내용을 볼 수 없음
  • 대역폭 절약 - 결과만 전송 (1개 메시지)
  • 입력 지연 제거 - 네트워크 왕복 없이 즉각 반응

Part 6: 대역폭 분석 (왜 모바일에서도 잘 돌아가나)

Q. 실제 네트워크 사용량은 얼마나 되나요?

계산해봅시다:

// 대역폭 계산 === 위치 업데이트 (5Hz) === - 1명당 데이터: PlayerID(4) + Position(8) + Flags(2) = 14 bytes - 10명: 140 bytes - 초당 5회: 140 × 5 = 700 bytes/s === 태스크 완료 이벤트 === - 평균 20개 태스크 / 5분 게임 = 초당 0.067개 - 이벤트 크기: 20 bytes - 초당: 1.3 bytes/s === 킬 이벤트 === - 평균 10번 / 5분 = 초당 0.033개 - 이벤트 크기: 30 bytes - 초당: 1 byte/s === 채팅 === - 회의 중에만 발생 - 평균: 50 bytes/s (게임 시간 20% 발생) === 합계 === 700 + 1.3 + 1 + 50 = ~750 bytes/s = 6 Kbps 실제로는 프로토콜 오버헤드 포함해도 **10-20 Kbps** 수준!
┌─────────────────────────────────────────────────────┐ │ 게임별 대역폭 비교 │ └─────────────────────────────────────────────────────┘ 게임 업/다운 대역폭 (Kbps) ───────────────────────────────────── Among Us 10-20 ████ Minecraft 50-100 ████████████ League of Legends 50-80 ████████████ Fortnite 100-300 ████████████████████████████ Warzone 200-500 ████████████████████████████████████████ → 어몽어스는 모바일 데이터(4G)로도 쾌적!
Q. 왜 이렇게 적게 쓸 수 있나요?

의도적인 게임 디자인 덕분입니다:

  • 낮은 틱 레이트 - 5Hz (FPS는 60-120Hz)
  • 적은 플레이어 - 10명 (배틀로얄은 100명)
  • 단순한 상태 - 위치, 생존, 태스크만
  • 이벤트 기반 - 변화가 있을 때만 전송
  • 느린 템포 - 빠른 반응 불필요
설계 철학

"네트워크 효율을 위해 게임을 복잡하게 만들지 않았다. 게임이 단순해서 네트워크가 효율적이다."

정리

  • 10명 제한: 네트워크 복잡도를 100분의 1로 줄임
  • 최소 상태: 위치, 생존, 태스크만 동기화 (20-30 bytes/player)
  • 낮은 틱 레이트: 5Hz로 충분 (선형 보간으로 부드럽게)
  • 서버 검증: 킬, 투표 등 중요 액션은 서버가 판정
  • 로컬 미니게임: 태스크는 결과만 동기화
  • 극한의 효율: 10-20 Kbps로 모바일에서도 완벽

핵심 교훈: "덜 전송하기"가 아니라 "덜 필요하게 만들기". 게임 디자인이 네트워크 효율을 결정합니다.
