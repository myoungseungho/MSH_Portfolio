Refactoring #18

Encapsulate Field

필드 캡슐화 - 데이터를 보호하라

필드 캡슐화가 뭐예요?
public 필드를 private으로 바꾸고, getter/setter로 접근하게 하는 것이에요.

외부에서 객체의 내부 데이터에 직접 접근하지 못하게 막고, 반드시 메서드를 통해서만 읽고 쓸 수 있게 하는 거예요.

객체지향의 가장 기본적인 원칙 중 하나죠.
왜 직접 접근하면 안 되나요? 더 간단한데...
직접 접근이 위험한 이유:

1. 유효성 검사 불가
player.hp = -100 이렇게 쓰면? 음수 HP가 가능해져요. setter가 있으면 0 미만은 0으로 보정할 수 있어요.

2. 변경 추적 불가
"HP가 바뀔 때 로그 남기기"를 추가하고 싶으면? 직접 접근하는 곳을 전부 찾아서 고쳐야 해요. setter에 한 줄 추가하면 끝.

3. 내부 표현 변경 불가
나중에 HP를 int에서 float로 바꾸면? getter/setter가 있으면 내부만 바꾸면 되요. 직접 접근하면 모든 호출부를 수정해야 해요.

🏦 비유: 은행 창구

은행 금고에 직접 들어가서 돈을 가져가면? 범죄죠.

창구(getter/setter)를 통해야 해요: - 신원 확인 (유효성 검사) - 거래 기록 (로깅) - 한도 적용 (비즈니스 로직)

데이터도 "창구"를 통해 보호해야 해요.
getter/setter가 단순히 값을 전달하기만 해도 의미가 있나요?
네, 그래도 의미가 있어요!

미래의 확장성:

지금은 단순해도, 나중에 필요할 때: - 검증 로직 추가 - 로깅 추가 - 이벤트 발행 - 캐싱 처리

이 모든 걸 호출부 수정 없이 getter/setter에만 추가하면 돼요.

💡 핵심 가치

캡슐화의 진짜 가치는 "나중에 바꿀 수 있는 여지"예요.

오늘은 단순해도, 내일 요구사항이 바뀔 수 있잖아요.
getter/setter가 너무 많아지면 지저분하지 않나요?
좋은 포인트예요. getter/setter 폭발의 해결책:

1. 정말 필요한 것만
모든 필드에 getter/setter를 만들 필요 없어요. 외부에서 접근이 필요한 것만.

2. setter 최소화
가능하면 setter 없이 생성자에서 초기화. 불변 객체가 더 안전해요.

3. 의미 있는 메서드로 대체
setHp(50) 대신 TakeDamage(10), Heal(5) 같은 행동을 표현하는 메서드가 더 좋아요.

⚠️ getter/setter 남용 주의

모든 필드에 기계적으로 getter/setter를 만들면 그냥 public이랑 다를 게 없어요.

"이 필드가 정말 외부에 노출되어야 하나?"를 먼저 생각하세요.
캡슐화 절차는 어떻게 되나요?
단계별 진행:

1단계: getter/setter 생성
→ GetHp(), SetHp(int value) 메서드 추가

2단계: 직접 접근을 메서드로 교체
→ player.hp → player.GetHp()로 변경 (IDE 자동화 활용)

3단계: 테스트
4단계: 필드를 private으로 변경
→ 이제 직접 접근하면 컴파일 에러

5단계: (선택) 로직 추가
→ setter에 유효성 검사 등 추가
언어마다 캡슐화 방식이 다른가요?
네, 언어별로 조금씩 달라요:

C++:
전통적인 GetXxx()/SetXxx() 메서드 방식

C#:
프로퍼티 문법으로 깔끔하게 지원 { get; set; } 또는 { get; private set; }

Java:
GetXxx()/SetXxx() 관례. Lombok으로 자동 생성 가능

Python:
@property 데코레이터. 언더스코어로 관례적 private (_hp)

형식은 달라도 개념은 동일해요: 직접 접근 막고, 메서드로 통제.

📌 Encapsulate Field 핵심 정리

  • public 필드를 private + getter/setter로 변경
  • 유효성 검사, 로깅, 변경 추적 가능해짐
  • 내부 표현 변경 시 호출부 수정 불필요
  • setter보다 의미 있는 행동 메서드 권장
  • 모든 필드가 아닌, 필요한 것만 노출
