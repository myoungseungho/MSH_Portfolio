Encapsulate Field

필드 캡슐화 - 데이터를 보호하라

Part 1. 캡슐화가 뭐야?

public 필드 그냥 쓰면 안 돼?

private으로 바꾸고 getter/setter로 접근해.

외부에서 직접 못 건드리게 막는 거야.

왜 직접 접근하면 안 돼?

위험해:

직접 접근의 문제

1. 유효성 검사 불가 - player.hp = -100 가능해짐
2. 변경 추적 불가 - HP 바뀔 때 로그 남기려면 전부 찾아서 고쳐야
3. 내부 표현 변경 불가 - int를 float로 바꾸면 모든 호출부 수정
은행 창구 비유

은행 금고에 직접 들어가서 돈 가져가면? 범죄지.
창구(getter/setter)를 통해야 해:
- 신원 확인 (유효성 검사)
- 거래 기록 (로깅)

데이터도 "창구"를 통해 보호해야 해.

Part 2. 단순 getter/setter도 의미 있어?

그냥 값 전달만 하면 뭐가 좋아?

미래의 확장성이야.

나중에 추가할 수 있는 것들

- 검증 로직 - 음수면 0으로 보정
- 로깅 - 값 변경 기록
- 이벤트 발행 - HP 변경되면 UI 업데이트
- 캐싱 처리

이걸 호출부 수정 없이 getter/setter에만 추가하면 돼.
오늘 필요 없어도?

오늘은 단순해도, 내일 요구사항이 바뀔 수 있잖아.

캡슐화는 "나중에 바꿀 여지"를 주는 거야.

Part 3. getter/setter 남용 주의

모든 필드에 다 만들어?

아니, 필요한 것만.

getter/setter 남용 문제

모든 필드에 기계적으로 만들면
그냥 public이랑 다를 게 없어.

"이 필드가 정말 외부에 노출되어야 하나?" 먼저 생각해.
더 나은 방법

1. setter 최소화 - 가능하면 생성자에서 초기화
2. 의미 있는 메서드 - setHp(50) 대신 TakeDamage(10), Heal(5)
3. 필요한 것만 노출 - 내부 전용은 그냥 private으로

Part 4. 절차

어떻게 캡슐화해?

단계별로:

Encapsulate Field 절차

1단계: getter/setter 생성 - GetHp(), SetHp(int)
2단계: 직접 접근을 메서드로 교체 - player.hp → player.GetHp()
3단계: 테스트
4단계: 필드를 private으로 - 이제 직접 접근 시 컴파일 에러
5단계: (선택) 로직 추가 - setter에 유효성 검사 등
언어마다 달라?

형식은 달라도 개념은 동일해.

C++: GetXxx()/SetXxx(), C#: 프로퍼티, Python: @property

핵심 정리: Encapsulate Field

  • 방법: public → private + getter/setter
  • 이점: 유효성 검사, 로깅, 변경 추적 가능
  • 확장: 호출부 수정 없이 내부 로직 변경
  • 주의: 모든 필드가 아닌 필요한 것만
  • 대안: setter보다 의미 있는 행동 메서드
