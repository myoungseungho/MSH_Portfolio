게임플레이 프로그래머의 역할

유저 경험과 관련된 모든 것을 만드는 사람

최호영 (넥슨 왓 스튜디오, 듀랑고) | NDC 발표 | Q&A 학습 기록

Part 1. 게임플레이 프로그래머란?

게임플레이 프로그래머는 어떤 사람이야?

유저들의 경험과 관련된 모든 것을 만드는 사람.

깊이 있는 어떤 프로그래밍보다는 다양한 일이 전달되었을 때 빠르고 효율적으로 만드는 사람이야.

구체적으로 어떤 일을 해?

하나의 국한된 일이 아니라 굉장히 다양한 일을 처리해:

  • 퀘스트, 출석부, 친구 시스템
  • 농사, 날씨, 건축물, 사유지
  • 운영 툴, 게임 로그, 데이터 분석
  • 버그 수정, 피처 구현

듀랑고 개발 사례만 해도 아이템, 분산 환경, NoSQL 위에서 게임플레이 개발까지 다양했어.

게임플레이 프로그래머의 정의

넓이 > 깊이 - 하나를 깊게보다 다양한 것을 빠르게

유저 경험 중심 - 유저가 만지는 모든 것

다양성 - 시스템, 운영 툴, 로그까지 전방위

Part 2. 좋은 게임플레이 프로그래머란?

좋은 게임플레이 프로그래머는 어떤 사람이야?

좋은 품질의 코드를 만드는 사람.

예쁘고 아름다운 코드를 만드는 사람도 있고, 게임을 사랑하는 사람도 있겠지만...

게임플레이 프로그래머에게 가장 중요한 건 좋은 품질의 코드야. 왜냐하면 가장 어려우니까.

왜 좋은 품질의 코드가 어려워?

게임은 다양한 콘텐츠를 제공해야 해:

  • 오늘은 퀘스트, 내일은 출석부, 올해는 버그 수정
  • 계속해서 작업이 이동하고 매일 다른 일을 해
  • 하나의 작업에 집중하기 힘들어

피처들이 독립적이지도 않아. 뭔가 하나 붙이면 계속 다른 거와 연결해야 하고, 넓은 범위의 코드를 커버해야 해.

온라인 서비스의 특수성은 뭐야?

온라인 서비스는 지속적인 업데이트와 장기간 서비스가 필수야.

이 말은:

  • 내가 한 번도 건드려 본 적 없는 코드를 손대야 할 수 있어
  • 남이 짠 코드를 완전히 파악하지 못한 상태에서 수정해야 해
  • 내가 작업한 게 내가 다시 고치는 게 아니야
  • 다른 사람이 고칠 수도, 먼 미래의 나가 고칠 수도 있어
좋은 품질 유지가 어려운 이유

1. 가독성 기준이 개인적 - "내가 보기엔 충분히 이해 가능한데?"

2. 바쁘면 스스로 타협 - "이 정도면 됐어, 난 열심히 했어"

3. 문서화 어려움 - 게임은 계속 변하고, 컨텐츠도 많아서 문서 유지가 힘듦

Part 3. 코드 리뷰의 중요성

좋은 품질의 코드를 유지하려면?

코드 리뷰가 답이라고 생각해.

코드 리뷰는 단순해: 내가 작업한 걸 내가 아닌 다른 사람이 봐주는 것.

코드 리뷰가 왜 좋아?

1. 리뷰 그 자체가 좋아

한 명이 보는 것과 여러 명이 보는 건 당연히 차이가 있어.

2. 리뷰어로서의 성장

리뷰를 요청하는 사람은 곧 리뷰를 해주는 사람이야. 동료의 코드를 읽다 보면:

  • "아, 이 부분이 가독성을 해치는구나"
  • "이런 습관이 안 좋은 습관이구나"

스스로 느낄 수 있게 돼.

3. 자발적인 개선 의지

내가 리뷰를 요청했는데 리뷰어가 "잠깐, 2시간 뒤에 해줄게" 하면? 내가 리뷰받기 힘들게 코드를 짠 거야. 개선하고 싶은 의지가 저절로 생겨.

4. 일관성 있는 코딩 스타일

서로 리뷰하다 보면 자연스럽게 스타일이 맞춰지고, 신입도 자연스럽게 흡수돼.

코드 리뷰의 숨은 장점은?

문서화 효과!

문서화의 목적은 크게 두 가지야:

  • 시스템에 처음 접근할 때 어떻게 들어가야 하는지
  • 문제가 생겼을 때 왜 이런 의도로 코드가 만들어졌는지

코드 리뷰는 리뷰어와 작업자가 논의하는 과정이야. 무슨 내용에 대해 요청했는지, 어떤 코멘트가 달렸는지가 다 기록에 남아.

5년 뒤에 blame으로 찾아보면 그 위치에서 어떤 논의가 이루어졌는지 알 수 있어.

코드 리뷰의 장점

1. 품질 향상 - 여러 눈으로 검증

2. 학습 효과 - 동료 코드 읽으며 성장

3. 자발적 개선 - 리뷰받기 좋은 코드를 쓰게 됨

4. 스타일 통일 - 팀 코딩 컨벤션 자연스럽게 형성

5. 문서화 - 논의 과정 자체가 기록

Part 4. 좋은 코드 리뷰 방법

코드 리뷰가 오래 걸린다는데?

맞아, 리뷰어와 작성자가 핑퐁하면서 시간이 흘러. 하지만 좋은 리뷰와 좋은 MR(Merge Request)로 해결할 수 있어.

리뷰하기 좋은 MR은 어떤 거야?

최대한 작은 MR!

  • 코드가 크면 한 번에 파악해야 하는 컨텍스트가 너무 커
  • 리뷰가 길어지거나, 기계적으로 "확인했습니다" 체크만 하게 돼

리팩토링할 때는 지우는 것과 새로 작업하는 것을 분리해. 동시에 넣으면 뭘 바꿨는지 알 수 없어.

큰 작업은 먼저 뼈대만 만들어서 리뷰받고, 그 안에 내용을 하나씩 채워.

MR 내용은 어떻게 써야 해?

구체적이어야 해.

  • MR 내용만 봐도 전후 맥락을 파악할 수 있어야 해
  • "문제 해결했어요"가 아니라, 무슨 문제가 있었는데 이걸 어떻게 해결한 거다
  • 변수명을 직접 언급해서 오해 없이 바로 필요한 부분을 볼 수 있게
  • 관련된 다른 MR에 링크 걸어서 연결

핵심: 5년 뒤에 이 MR을 봐도 전후 맥락을 어느 정도 알 수 있어야 해.

좋은 리뷰는 어떤 거야?
  • 간결하고 건조하게 - 미사여구 붙이면 오해가 생기고 핑퐁이 길어져
  • 취향과 표준 구분 - "이건 내 취향이에요. 받아들일지는 당신이 결정하세요"
  • 작은 코멘트는 선조치 - 오타 수정 같은 뻔한 건 코멘트 남기고 바로 Approve
리뷰 시간 줄이는 팁

1. 형식적인 리뷰어 지정 금지 - 안 하는 사람, 너무 잘하는 사람에게 쏠리지 않게

2. 리뷰어 집중 방해 금지 - 합의된 빈도와 규칙 안에서만 요청

3. 투 트랙 작업 - 리뷰 기다리는 동안 다른 작업 진행

4. 시급한 건 명시적으로 - "당장 핫픽스 올려야 합니다" 따로 알림

Part 5. 일정 지키기

왜 빠른 개발이 중요해?

지금은 콘텐츠 공급 과잉의 시대야. 화면을 보면서 즐기는 것뿐 아니라 화면을 보지 않고 즐기는 것도 세상에 너무 많아.

고객들이 기다려주지 않아. 모든 실수, 모든 딜레이, 모든 지연은 전부 고객 이탈로 이어져.

일정을 왜 못 지켜?

유명한 "N+1의 법칙"이 있어:

내가 생각한 일정 x 2 + 1일 = 실제 일정

반쯤 농담이지만 꽤 맞아. 다양한 요소가 예상하지 못하게 작업을 방해해.

외부적인 요인도 있지만, 내부적인 요인으로는 잘못된 방향 설정이 가장 커. 열심히 개발했는데 "이 길이 아니었나 봐요" 하고 다시 돌아가는 일이 정말 많아.

방향 설정 실수를 어떻게 줄여?

코드 리뷰는 사후 리뷰야. 이미 작업한 다음에 받으니까 문제가 발견되면 오히려 일정이 늘어나.

듀랑고에서는 "기술 명세서 리뷰"를 시도했어:

  • 게임플레이 프로그래머가 디자인 문서를 받으면
  • 기술 명세서를 먼저 작성: "이 요청을 받았으니 이렇게 할 거다"
  • 명세서 리뷰가 통과하면 그때 작업 시작

하지만 프로그래머는 테크니컬 라이팅에 능숙하지 않고, 문서도 너무 많이 쏟아져서 대규모 피처용 문서로만 사용하게 됐어.

현실적인 대안은?

짧은 미팅으로 방향만 공유!

  • 글로 쓰기 힘드니까 말로 하자, 대신 짧게
  • 디테일을 설명하지 않고 방향만 서로 공유
  • "이 시스템 작업해야 하는데 이렇게 할 것 같다"
  • 피드백 받고, 얘기가 길어지면 관심 있는 사람들끼리 따로 회의

이렇게 하면 작업 비용 예측이 매우 정확해져.

핵심 원칙

내 작업을 언제나 동료가 알게 하는 것.

말을 줄이고 싶어지지만, 대신 간결하게 필요한 부분만 알려주고,

동료에게 인터럽트가 없게 노력해.

일정 실패 시 가장 중요한 것

일정 실패는 베테랑도 다 겪는 일이야.

가장 중요한 건 실패했음을 숨기지 않는 것.

"아, 오늘까지 끝낼 거라 생각했는데 3일은 더 있어야 끝날 것 같아요"

이 얘기를 투명하게 공개할 수 있는 분위기가 되어야 해.

이걸 놓치면 나중에 더 큰 재앙이 되어 돌아와.

Part 6. 디자이너와의 협업

게임플레이 프로그래머는 누구와 일해?

게임 디자이너로부터 요청을 받아서 실제 결과물을 내고, 피드백을 받으면 다시 수정하는 일이야.

언뜻 보면 외주 같지만...

디자이너와 프로그래머의 차이는?

게임 디자이너는 유저 시점에서 "어떻게 하면 재밌을까"를 생각해.

프로그래머는 구현 시점에서 보지.

보는 방향이 거의 반대야. 그래서 충돌이 생겨.

디자이너 프로그래머
유저가 어떻게 느낄까? 이걸 어떻게 구현하지?
재미있을까? 가능한가? 일정은?
경험적으로 앎 논리적으로 훈련됨
프로그래머가 자주 하는 불만은?
  • "우리 게임 구조에 맞지 않는 디자인을 자꾸 가져와요"
  • "이걸 지금 가져오면 나보고 어떻게 작업하라는 거예요"
  • "디자인 문서가 너무 빈 곳이 많아서 작업할 수 없어요"

근데 이거, 디자이너가 알기 힘든 부분이야:

  • 구현은 디자이너의 일이 아니라 인지 범위에 없어
  • 프로그래머는 논리적 사고를 훈련받지만, 디자이너는 그런 직군이 아니야
  • 예외사항, 코너 케이스 같은 건 경험적으로 아는 경우가 많아
어떻게 대응해야 해?

크게 두 가지 방법이 있어:

X "안 돼요" → 그냥 거절

O 역제안을 달거나 선택지를 주고 결정권을 넘기기

우리 게임에서 구현이 어려운 디자인이 오면: - "이게 왜 어려운지" 설명 - "당신의 의도를 이해했는데, 그 의도를 구현하려면 우리 게임은 이렇게 하는 게 어때요?" 역제안 큰 규모의 작업이 오면: - "이건 당신 생각보다 굉장히 커요" - "이렇게 쪼개면 좋겠고, 이거부터 먼저 할게요" 논리적으로 허점이 보이면: - 열심히 메꾸려고 노력
게임플레이 프로그래머의 진짜 역할

디자이너가 애초에 알기 힘든 부분을 제일 잘 아는 직군이 우리야.

디자이너의 부족한 부분을 메꾸고, 디자인 자체의 완결성을 높이는 직업.

열정적으로 "남들이 안 하는 것도 해야 해요"가 아니라,

게임플레이 프로그래머는 원래 이런 일을 하는 직군이라는 거야.

Part 7. 테크니컬 디자이너 역할

디자이너와 협력할 때 주의할 점은?

먼저 공감대가 필요해:

  • "나는 딴지를 걸거나 참견하는 게 아니라, 내 역할로서 피드백을 주는 것"
  • "나는 외주 작업자가 아니라, 당신과 같이 협력해서 게임플레이를 만드는 사람"

그 다음 디자이너에게 요청해야 해:

디자이너에게 요청할 것: 1. 의도를 명확히 해주세요 X "이런 시스템 만들어주세요" O "이런 의도로 이런 걸 만들고 싶은데, 난 이렇게 하면 좋을 거라 생각해요" 2. 구현 범위를 명확히 해주세요 X "이거 만들어주세요" 끝 O "이걸 만들고 나면 이 시스템과 연결하고 싶어요, 이런 상품도 팔고 싶어요" 3. 구체적인 예시를 붙여주세요 X "아이템에 뭘 붙여주세요" (시스템만) O "이거, 이거, 이거를 하고 싶기 때문에 이 시스템을 요청하는 거예요"
피드백 줄 때 조심할 점은?
  • 우리는 디자이너가 아니야 - 관심이 많다고 "나도 저분보다 잘할 것 같은데" 하면 안 돼. 그 사람들이 전문가야.
  • 단순한 거절 줄이기 - "설명하기 힘든데 일단 안 돼요"를 최대한 줄여야 해
  • 공격적인 표현 자제 - 상대방 감정만의 문제가 아니야
공격적인 표현의 진짜 문제

공격적인 표현을 쓰면 디자이너는 좋은 디자인을 가져오지 않게 돼.

최대한 안전하고, 혼나지 않을 디자인만 가져오려고 해.

"혼자서 일정도 넉넉하게 잡아야 이 검에서 인정받겠지..." 이런 생각을 하게 됨.

우리가 이런 일이 없도록 노력해야 해.

테크니컬 디자이너란?

프로그래머와 디자이너 사이에 있는 회색 지대야. 둘 다 할 수 있는 일이지.

하지만 작은 팀에서는 이 역할을 따로 둘 수 없어.

그럴 때 이 포지션에 가장 적합한 사람이 게임플레이 프로그래머라고 생각해.

리더나 매니저가 되기 위해서는 테크니컬 디자이너로서의 역량이 필수야.

Part 8. 소통 능력

디자이너 외에 누구와 일해?

프로그래머가 아닌 다양한 직군과 일해:

  • 사업팀
  • 운영팀
  • QA팀
  • 등등...
원활한 소통 능력이란?

프로그래머가 아닌 팀의 요청을 받았을 때, 프로그래머의 용어가 아닌 것으로 설명할 수 있는 능력이야.

X "이거 안 되는데요" X "일정이 너무 커서 못 받아요" O "이게 이래서 안 되는데, 이렇게 해보는 건 어때요?" O "일정이 바쁘니까 요거만 먼저 하면 안 될까요?"

협상하고, 같이 소통할 수 있는 능력이 게임플레이 프로그래머에게 요구돼.

소통의 본질

상대방의 의도를 적극적으로 파악하고

내가 가진 지식으로 상대방에게 도움을 주는 것.

그리고 동료와 계속해서 피드백을 주면서

더 좋은 길로 나아가기 위해 노력하는 것.

총정리: 게임플레이 프로그래머란?

정의

  • 유저 경험과 관련된 모든 것을 만드는 사람
  • 깊이보다 넓이가 중요
  • 다양한 요청을 빠르고 효율적으로 처리

핵심 역량

좋은 게임플레이 프로그래머 = 좋은 품질의 코드 왜 어려운가? |- 계속 다른 작업, 집중 힘듦 |- 남이 짠 코드, 장기 유지보수 |- 가독성 기준이 주관적 |- 바쁘면 타협 해결책: 코드 리뷰 |- 품질 향상 + 학습 + 문서화 효과

디자이너와의 협업

  • 외주가 아니라 협력자
  • 디자이너가 모르는 걸 제일 잘 아는 직군
  • 역제안과 선택지 제시
  • 테크니컬 디자이너 역할까지

소통 스페셜리스트

개발 도구는 계속 발전 -> 단순 구현은 쉬워짐 -> 내 경쟁력을 키워야 할 때 게임플레이 프로그래머는: |- 기술적 제너럴리스트? (X) |- 소통 스페셜리스트! (O) 핵심: 상대의 의도 이해 + 정해진 일정 + 좋은 품질의 프로그래밍 ↓ 결국 커뮤니케이션!

한 문장 정리

  • 게임플레이 프로그래머 = 상대의 의도를 이해하고, 정해진 일정에 맞춰서, 좋은 품질의 프로그래밍을 하는 사람
  • 프로그래머 기본 + 게임에 대한 관심 + 소통
