언젠가 시니어가 될 주니어를 위하여

시니어 프로그래머 정의, 커뮤니케이션, 문서 작성

Part 1. 이상적인 시니어 프로그래머 정의

이상적인 시니어 프로그래머란 어떤 사람일까?

요구사항을 읽고 스스로 상황을 파악해서 코딩하는 사람.

매니저가 일일이 지시하지 않아도, 요구사항만 보고 뭘 해야 하는지 파악하고 실행할 수 있는 사람이야.

왜 "스스로 상황 파악"이 중요할까?

매니저도 할 일이 많아. 모든 개발자에게 하나하나 설명해줄 시간이 없어.

스스로 파악하고 움직이는 사람이 있으면 매니저가 다른 중요한 일에 집중할 수 있지.

결국 팀 전체의 생산성이 올라가는 거야.

시니어의 핵심 역량

자율성 - 요구사항만 보고 스스로 판단하고 실행

맥락 파악 - 왜 이 요구사항이 나왔는지 이해

팀 기여 - 매니저의 부담을 줄여 팀 효율 향상

Part 2. 프로그래머는 코딩만 잘하면 되는 거 아닌가?

프로그래머는 코딩만 잘하면 되는 거 아닌가?

아니.

혼자 일하면 그럴 수 있어. 근데 회사는 팀으로 일하잖아.

팀으로 일하면 뭐가 달라지는데?

팀에는 위임이 발생해.

매니저가 모든 일을 직접 하면? 병목이 돼.

그래서 일을 나눠서 맡기는 거야.

위임받으면 뭘 해야 하는데?

위임받은 일을 책임지고 완료해야 해.

근데 여기서 중요한 게, 완료가 뭐냐면...

"코딩 끝났어요"가 아니야.

"요구사항이 해결됐어요"가 완료야.

매니저의 현실은 어때?

매니저는 회의, 보고, 일정 조율, 다른 부서 대응 등 할 일이 산더미야.

개발자 한 명 한 명 코드 리뷰하고, 설계 검토하고, 진행상황 체크하는 게 쉽지 않아.

그래서 스스로 알아서 하는 사람이 필요한 거야.

핵심 통찰

코딩 실력 + 팀워크 능력 = 진짜 실력

위임받은 일을 책임지고 완료하는 것이 프로

Part 3. 기획자가 "이거 되나요?"라고 물으면?

기획자가 "이거 되나요?"라고 물으면 뭐라고 해야 할까?

많은 주니어가 이렇게 대답해:

"안 돼요."

이게 왜 문제일까?

"안 돼요"가 왜 문제야?

기획자 입장에서 생각해봐.

기획자는 비즈니스 목표를 달성해야 해. 어떤 기능이 필요하다고 판단했기 때문에 물어보는 거야.

"안 돼요"라고 하면?

대화가 끝나버려. 기획자는 다른 방법을 찾아야 하는데, 아무 정보도 없어.

그럼 올바른 접근은 뭐야?

먼저 "왜 이게 필요하세요?"를 물어봐.

기획자가 진짜 원하는 게 뭔지 파악하는 거야.

그 목표를 달성할 다른 방법이 있을 수도 있거든.

"안 돼요"의 문제점

1. 대화가 끊긴다

2. 기획자에게 도움이 안 된다

3. 문제 해결이 아니라 문제 회피가 된다

Part 4. "안 돼요" 대신 뭐라고 해야 하나?

"안 돼요" 대신 뭐라고 해야 해?

구체적인 대안을 제시해야 해.

X "안 돼요." O "이 방식은 A 때문에 어렵습니다. 대신 B 방식으로 하면 목표를 달성할 수 있습니다. 일정은 X일 정도 걸립니다."
왜 대안 제시가 중요해?

기획자의 목표는 "이 기능을 만드는 것"이 아니야.

"비즈니스 목표를 달성하는 것"이야.

대안을 제시하면 기획자가 선택할 수 있어.

그게 협업이야.

대안 제시할 때 뭘 포함해야 해?
  • 왜 안 되는지 - 기술적 제약 설명
  • 대안은 뭔지 - 목표 달성 가능한 다른 방법
  • 트레이드오프 - 대안의 장단점
  • 일정 - 얼마나 걸리는지
프로의 대응

"이 방식은 [기술적 이유]로 어렵습니다."

"목표가 [X]라면, [대안 B]로 달성할 수 있습니다."

"[대안 B]는 [장점]이 있지만, [단점]도 있습니다."

"일정은 약 [N]일입니다."

Part 5. 혼날 때 멘탈 관리

일하다가 실수해서 혼나면 어떻게 해야 해?

먼저 이걸 구분해:

한 번째 실수와 두 번째 실수는 다르다.

한 번째 실수는 뭐가 달라?

한 번째 실수는 개인의 실수야.

"아, 내가 실수했구나. 조심해야지."

이건 개인이 고치면 되는 문제야.

두 번째 실수는?

같은 실수가 두 번째로 발생하면?

그건 시스템의 문제야.

"왜 같은 실수가 또 발생했지?"

시스템이 실수를 방지하지 못한 거야.

시스템 부재라는 게 무슨 뜻이야?

예를 들어:

  • 코드 리뷰가 없어서 버그가 통과됨
  • 테스트 자동화가 없어서 수동 실수 발생
  • 문서화가 없어서 같은 질문이 반복됨
  • 체크리스트가 없어서 배포 실수 발생

개인을 탓하지 말고, 시스템을 만들어야 해.

멘탈 관리 공식

1번째 실수 = 개인의 실수 -> 반성하고 조심

2번째 실수 = 시스템 부재 -> 프로세스 개선 제안

두 번째부터는 "내 탓"이 아니라 "시스템 개선 기회"로 봐라

Part 6. 매니저가 "해도 되고 안 해도 되는데"라고 하면?

매니저가 "해도 되고 안 해도 되는데..."라고 하면 뭘까?

해라.

왜? 안 해도 된다고 했잖아?

매니저가 정말 안 해도 된다고 생각하면?

아예 말을 안 꺼내.

굳이 "해도 되고 안 해도 되는데"라고 말한다는 건?

하길 바라는 거야.

왜 직접적으로 "해"라고 안 하는 거야?

여러 이유가 있어:

  • 압박감을 주기 싫어서 - 자율성 존중
  • 강제하기 애매해서 - 업무 범위가 불명확
  • 테스트 - 스스로 판단하는지 보는 것
매니저의 숨은 의미 해석
매니저가 하는 말 실제 의미
"해도 되고 안 해도 되는데..." 해라
"시간 되면 봐줄래?" 지금 봐라
"생각해볼게" 대부분 안 할 거다

Part 7. 문서 작성 템플릿

업무 문서는 어떻게 구조화해야 해?

다음 템플릿을 따라가면 돼:

1. 개요 - 이 문서가 뭔지, 왜 쓰는지 2. 문제상황 - 현재 어떤 문제가 있는지 3. 요청사항 - 뭘 해달라는 건지 (구체적으로) 4. 개선제안 - 어떻게 해결하면 좋을지 5. 결론 - 핵심 요약 6. 비고 - 참고사항, 제약조건 등
왜 이 순서가 중요해?

읽는 사람 입장에서 생각해봐.

  • 개요 - "이게 뭔지" 파악
  • 문제상황 - "왜 필요한지" 이해
  • 요청사항 - "뭘 해야 하는지" 파악
  • 개선제안 - "어떻게 할지" 방향 제시
  • 결론 - "핵심이 뭔지" 정리
  • 비고 - "추가로 알아야 할 것"

이 순서대로 읽으면 자연스럽게 이해가 돼.

문서 템플릿 체크리스트

[ ] 개요 - 문서의 목적이 명확한가?

[ ] 문제상황 - 현재 문제가 구체적인가?

[ ] 요청사항 - 요청이 명확하고 실행 가능한가?

[ ] 개선제안 - 해결책이 있는가?

[ ] 결론 - 핵심이 요약되어 있는가?

[ ] 비고 - 빠진 정보가 없는가?

Part 8. 문서 작성 팁

두괄식이 뭐야?

결론을 먼저 말하는 것.

X 미괄식 (나쁜 예) "A 때문에 B가 발생했고, C를 고려하면 D가 필요합니다. 따라서 X를 해야 합니다." O 두괄식 (좋은 예) "X를 해야 합니다. 이유: A -> B -> C -> D"
왜 두괄식이 좋아?

읽는 사람은 바빠.

결론을 먼저 보면:

  • 바쁘면 결론만 읽고 끝낼 수 있어
  • 관심 있으면 이유를 더 읽으면 돼

선택권을 주는 거야.

글머리 기호는 왜 써야 해?

긴 문장 vs 글머리 기호:

X "서버 성능 개선을 위해 캐시를 적용하고 인덱스를 추가하며 쿼리를 최적화하고 커넥션 풀을 조정해야 합니다." O 서버 성능 개선 방안: - 캐시 적용 - 인덱스 추가 - 쿼리 최적화 - 커넥션 풀 조정

한눈에 파악 가능. 읽는 사람의 시간을 아껴줘.

단락 나누기는 왜 중요해?

단락 없이 쭉 쓰면?

읽기 싫어져.

적절한 단락 나누기:

  • 주제가 바뀔 때 단락 구분
  • 3-4문장 넘어가면 끊기
  • 중요한 포인트는 별도 단락
문서 작성 3원칙

1. 두괄식 - 결론 먼저

2. 글머리 기호 - 나열은 리스트로

3. 단락 나누기 - 읽기 쉽게

Part 9. 회의 관련 팁

회의 전에 뭘 준비해야 해?

아젠다(안건)를 확인해.

아젠다가 없으면? 물어봐.

"이번 회의에서 뭘 결정해야 하나요?"

아젠다가 왜 중요해?

아젠다 없는 회의는:

  • 끝이 없어 - 언제 끝나는지 모름
  • 삼천포로 빠져 - 주제가 계속 바뀜
  • 결론이 없어 - 뭘 결정했는지 모름
결정권자가 왜 중요해?

회의에서 의견이 갈릴 때, 누가 최종 결정을 하는지 알아야 해.

결정권자가 없으면?

회의만 하고 아무것도 결정 안 돼.

회의 시작할 때 "이 건은 누가 최종 결정하나요?"를 확인해.

회의록은 왜 써야 해?

회의 끝나고 일주일 지나면?

기억 안 나.

"그때 뭐라고 했지?" -> 회의록 보면 됨

"이거 하기로 했잖아요" -> 회의록에 있음

회의록 = 증거야.

회의록에 뭘 써야 해?
회의록 필수 항목: 1. 일시/참석자 2. 안건 (아젠다) 3. 논의 내용 (핵심만) 4. 결정 사항 [중요] 5. 액션 아이템 (누가, 언제까지, 뭘) [중요] 6. 다음 회의 일정

결정 사항과 액션 아이템이 가장 중요해.

회의 3대 원칙

1. 아젠다 - 회의 전에 안건 확인

2. 결정권자 - 누가 결정하는지 명확히

3. 회의록 - 결정사항과 액션 아이템 기록

총정리: 주니어에서 시니어로

시니어 프로그래머의 정의

  • 요구사항을 읽고 스스로 상황 파악해서 코딩
  • 매니저의 부담을 줄여 팀 전체 효율 향상

커뮤니케이션

"안 돼요" 대신: |- 왜 안 되는지 설명 |- 대안 제시 |- 트레이드오프 설명 |- 일정 제시 "해도 되고 안 해도 되는데" = 해라 실수 멘탈 관리: |- 1번째 = 개인 실수 -> 반성 |- 2번째 = 시스템 부재 -> 프로세스 개선

문서 작성

템플릿: 개요 -> 문제상황 -> 요청사항 -> 개선제안 -> 결론 -> 비고 작성 원칙: |- 두괄식 (결론 먼저) |- 글머리 기호 (나열은 리스트) |- 단락 나누기 (읽기 쉽게)

회의

  • 아젠다 - 없으면 물어봐
  • 결정권자 - 누가 결정하는지 확인
  • 회의록 - 결정사항 + 액션 아이템 필수

핵심 마인드셋

  • 코딩만 잘하면 되는 게 아니라 팀에 기여해야 한다
  • 문제 해결자가 되어야 한다 (문제 회피 X)
  • 스스로 판단하고 책임지는 자세
