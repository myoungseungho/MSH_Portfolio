게임 프로그래머는 어떻게 가르치나요

신입 프로그래머를 신뢰할 수 있는 인재로 육성하는 방법

크래프톤 복해 스튜디오 홍성 | NDC 발표 | Q&A 학습 기록

Part 1. 왜 회사에서 가르쳐야 하는가

영화 감독이 배우를 연기 지도하는 것처럼, 게임에서는 누가 그 역할을 하나?

프로그래머가 그 역할을 한다.

영화에서 감독의 의도가 배우의 연기를 통해 전달되듯이, 게임에서는 기획이나 아트 등 다양한 결과물을 프로그래머가 엮어서 완성된 제품을 만든다.

프로그래머가 잘 해주지 않으면? 버그가 쏟아지고, 서버가 죽고, 아이템이 복사되고... 게임 퀄리티가 떨어진다.

학교에서 다 배워왔는데, 회사에서 또 가르쳐야 하나?

학교에서 다 배울 수 있는 게 아니다.

구분 학교 회사
제품 품질 기준 "돈 받고 팔아도 되겠다" 돈 받고 파는 것보다 훨씬 높아야
유지보수 기간 제출할 때까지 (짧으면 1일, 길어도 3-4개월) 몇 년 이상 서비스
코드 품질 기준 주석 잘 달면 좋은 코드 완전히 다른 평가 기준
경력자를 채용하면 교육이 필요 없지 않나?

경력자도 교육이 필요하다.

  • 조직마다 규칙이나 개발 환경이 다르다
  • 언어가 바뀌면 적응 시간이 오래 걸린다 (C++/C# -> Python 등)
  • 코드 리뷰를 꼼꼼하게 하는 조직이 많지 않다

연차가 오래되고 잘하는 사람을 데려와도, 조직의 문화와 스타일에 맞추기 위해 재교육이 필요하다.

핵심 통찰

내가 회사에서 일을 즐겁게 잘 하려면, 동료들이 일을 잘 해줘야 한다.

개발환경이 나쁘고 코드가 지저분하면? 수정하다가 깨진 거 복구하고, 남이 쓴 코드에서 버그 찾는 일만 하게 된다.

Part 2. 무엇을 가르쳐야 하는가

프로그래머에게 공통적으로 필요한 능력은?
1. 동료들과 커뮤니케이션 잘하는 법 2. 코드 품질을 높게 프로그래밍하는 법 3. 입사한 지 얼마 안 된 사람도 조직의 노하우를 반영할 수 있게 하는 법

이 세 가지가 교육의 가장 중요한 목표다.

이걸 어떻게 가르치나?

세 가지 방법으로 가르친다.

교육 목표 교육 방법
좋은 코드를 쓰는 것 코드 리뷰
조직의 노하우와 가치를 반영하는 것 설계 리뷰
커뮤니케이션 아침회의

Part 3. 코드 리뷰

교육 목적의 코드 리뷰는 어떻게 진행하나?
1. 자신의 일을 잘라서 나눠준다 2. 어떻게 하는지 방법을 자세히 알려준다 3. 결과물을 확인해서 피드백을 해준다 4. 반복
"자신의 일을 잘라서 나눠준다"는 게 무슨 뜻이야?

교육 목적이라도 실무를 줘야 한다.

  • 테트리스를 만들어서 출시할 게 아니라면, 테트리스 짜라고 시키지 않는다
  • 교육을 위해 예제를 새로 만드는 게 아니라, 실제로 해야 하는 일을 준다
  • 뭘 하는지, 어떻게 하는 건지 내가 충분히 알고 있는 일을 줘야 한다
"방법을 자세히 알려준다"가 마이크로 매니징 아닌가?

처음에는 프로그램 설치, 어떤 코드를 참고하면 되는지, 어떤 설계를 하면 되는지까지 다 알려준다.

중요한 것은 신입을 테스트하려는 게 아니라, 일을 완수하는 경험을 주려는 것이다.

피드백은 어떻게 하나?

결과를 보면서 내가 직접 했다면 어떤 점에서 다를지 알려준다.

"다음엔 더 잘해요"가 아니라, 내가 직접 한 것과 비슷한 수준이 될 때까지 반복해서 피드백한다.

피드백할 때는 명확한 근거가 있어야 한다. 이랬다 저랬다 일관성이 없으면 굉장히 혼란스럽다.

코드 리뷰 피드백 샘플

고쳐 달라는 내용과 함께 왜 그렇게 해야 되는지 설명한다.

중요한 규칙들은 문서로 정리해두면 피드백 반영 시 참고할 수 있다.

교육을 위해 피드백하면서 쓴 문서 -> 다른 분들 교육할 때 재사용 -> 계속 업데이트

이렇게 반복하면 어떻게 되나?

교육하는 사람과 받는 사람의 작업 스타일이 점점 비슷해진다.

나랑 비슷하니까 결과를 예측할 수 있고, 신뢰할 수 있다.

규칙이 충분히 일반성 있다면, 세부 지시가 빠지더라도 응용해서 할 수 있다.

코드 리뷰로 배우는 것
  • 팀의 규칙과 정책
  • 규칙을 만들게 된 원칙들
  • 잠재적 버그의 원인이 되는 영역 피하기
  • 코드 작성 시 함정 피하는 법
  • 코드 작성에 필요한 추상화 감각
  • 좋은 코드를 위한 여러가지 팁들

Part 4. 설계 리뷰

설계 리뷰는 언제 하나?

처음에는 모든 걸 자세히 알려주지만, 점차 스스로 고민하고 결정하는 폭을 넓혀 나가야 한다.

어느 정도 교육이 진행되면, 주어진 문제에 대한 작업 방향을 스스로 찾고 제시해보라고 한다.

설계 리뷰 피드백은 어떻게 하나?

주로 질문을 한다.

"이 기능에 사용자 수가 얼마나 되나요?" "요구사항을 충실히 반영하고 있나요?" "인터페이스 디자인은 왜 이런가요?"

어떤 설계 결정을 내리게 된 근거를 질문하는 것이다.

왜 질문 형식으로 피드백하나?

"왜 이렇게 했나요?"라고 물어봤을 때 "그냥 이렇게 썼어요"라고 대답하는 게 아니라, 근거 중심으로 생각하도록 유도하기 위해서다.

자꾸 질문을 받다 보면, 질문에 대답해야 된다는 걸 인지하고 스스로 자문하게 된다.

내 방법이 더 좋다고 반박할 수 있게 된다.

설계 리뷰로 배우는 것
  • 문제 접근 방식 - 사고의 흐름
  • 설계 시 고려하는 가치들의 우선순위 (성능 vs 편의성 vs 단순함)
  • 적절한 기준 세우는 법 (비용 분석)
  • 참고할 만한 좋은 설계와 나쁜 설계 사례
  • 변경 가능성 예측하고 대비하기
  • 설계를 함께 리뷰하는 방법 (핑퐁)
중요한 포인트

설계는 한 사람이 혼자서 다 하지 않는다.

다른 팀원과 핑퐁을 하면서 주고받는 과정이 필요하다.

프로그래머가 비슷한 수준의 동료 없이 혼자서 일하면 힘들다 - 핑퐁을 못하니까.

Part 5. 아침회의 (스탠드업 미팅)

프로그래머는 말을 잘 안 해도 되지 않나?

아니다. 프로그래머도 말을 무척 많이 한다.

코드 리뷰, 설계 리뷰 다 사람이랑 말로 하는 것이다.

프로그래머가 되려면 무슨 언어를 잘 해야 하나요? 한국어.

눈에 보이지 않는 기계의 구조와 동작을 말로 설명하는 것 - 기술적이고 전문적인 내용을 오해 없이 명료하게 설명해야 한다.

아침회의(스탠드업)가 뭐야?

매일 아침, 전날 한 일, 오늘 할 일, 있었던 이슈를 한 사람씩 돌아가면서 간단하게 얘기하는 것.

한 사람당 1분 정도. 보통 10분 정도 걸린다.

아침회의로 뭘 훈련하나?
1. 보고하고 피드백 받는 연습 - 삽질 중인지, 잘못된 방향인지 확인 2. 모르는 걸 모른다고 이야기하는 것 - "그 단어가 무슨 뜻인지 모르겠어요" - 모른다고 말해도 비난받지 않는 문화 3. 질문을 잘하는 것 - 궁금한 것 + 맥락을 함께 전달 4. 의견이 다른 동료와 대화하는 법 - 반론 제기 = 감정 싸움 X - 회사에서 써도 되는 표현, 쓰면 안 되는 표현
아침회의의 부수적 효과
  • 동료들이 갖고 있는 문제가 뭔지 알 수 있다
  • 팀이 풀고 있는 문제의 큰 그림을 볼 수 있다
  • 다른 사람이 힌트를 제공할 수 있다
  • 하나의 커다란 문제를 나눠서 풀고 있다는 연대감
아침회의의 본질

"우리가 단지 돌을 자를지라도, 언제나 대성당을 마음속에 그려야 한다."

아침회의는 우리가 만들어야 하는 대성당을 마음속에 그리는 것을 돕는다.

Part 6. 교육의 패턴과 효과

코드 리뷰, 설계 리뷰, 아침회의의 공통 패턴은?
1. 해야 하는 역할과 롤모델이 주어진다 2. 교육받는 사람은 모방을 통해 롤모델에 가까워진다 3. 교육하는 사람은 피드백을 통해 롤모델에 가까워지도록 유도한다 4. 궁극적으로 교육자가 하는 일을 피교육자가 대체한다

핵심: "개선을 한다"가 아니라 "개선을 확인한다"

내가 나아지고 있음을 인지하는 게 교육 효과에 큰 영향을 미친다.

왜 이렇게 교육하나? (업무 능력 복제)

내 능력을 복제할 수 있으면 좋은 점:

  • 내가 휴가를 가거나 자리를 비워도 잘 돌아간다
  • 채용 시 나랑 비슷하게 잘하는 사람을 뽑을 필요 없이, 가르치면 비슷하게 할 수 있을 것 같은 사람을 채용하면 된다
  • 설계할 때 핑퐁할 상대가 생긴다
  • 2명 정도 가르쳐 보면, 세 번째부터는 자기들끼리 가르친다
책이나 샘플 게임으로 교육하면 안 되나?

책: 책이 중요하지 않다는 게 아니라, 책만 가지고 충분히 교육하기가 어렵다. 책에 안 나온 얘기가 더 많다.

샘플 게임: 엔진이나 언어 사용 연습이 된다. 하지만 실제로는 샘플 게임 수준이 아니라, 탄탄한 코드 베이스 위에서 시스템을 만든다. 샘플에는 실무에서 발생하는 여러 가지 정보들이 포함되기 어렵다.

가장 좋은 교육 자료는 팀원들이 실제로 쓰고 있는 코드 베이스다.

핵심 인용

"학습 상황이란 본질적으로 자기가 무엇을 하는지 알고 있는, 정말 알고 있는 누군가를 보면서 배워가는 과정이다."

Part 7. 관리자 육성과 조직문화

신입 교육이 끝나면 코드 리뷰, 설계 리뷰 안 해도 되나?

아니다. 계속한다.

코드 리뷰, 설계 리뷰의 원래 목적은:

  • 설계와 구현 품질을 조직이 관리
  • 개인에게 과도한 책임을 묻거나 업무 환경이 나빠지는 걸 방지
  • 결과물의 품질을 팀이 함께 고민

혼자 일하지 말고, 팀과 같이 일하라는 것이다.

이런 교육이 관리자 육성과 어떤 관계가 있나?

구성원의 역할을 보면, 관리자가 담당하는 역할이 자연스럽게 조직 전체로 분산된다.

구성원의 역할: 1. 자신이 받는 교육의 방식과 의미 이해 2. 조직문화 안에서 일하기 3. 교육이나 리뷰 형태로 다른 구성원에게 전달 4. 자신의 경험이나 장점을 조직 내 쌓으면서 입지 만들기 5. 프로세스 개선에 기여

조직을 이끈다는 건 가장 뛰어난 사람이 되는 게 아니라, 시스템과 문화를 리드하면서 구성원을 성장시키는 역할이다.

관리자 육성 관점의 변화

예전: "이 사람을 어떻게 관리자로 만들지?"

지금: "저 사람에게 뭘 채워주면 관리자가 될 수 있을까?"

Part 8. 교육의 지속적 효과

교육이 일회성이 아니라 지속성이 있다는 게 무슨 뜻이야?

한 조직에서 배운 경험이 다음 프로젝트에서 활용될 가능성이 높다.

교육을 열심히 하는 게 지금 당장 가성비가 나쁘게 느껴지더라도, 장기적으로 보면 가성비가 매우 높다.

"열심히 가르쳐놨더니 회사 나가면?"

프로그래머가 성장감을 느끼면서 일하는 동안은 결코 퇴사 안 한다.

내가 성장을 멈춘 채 일을 하고 있다고 느낄 때 이직을 고민한다.

회사 다니면서 일을 잘 배울 수 있는 기회는 흔하지 않다.

그리고 퇴사한 인력이 다시 돌아오기도 한다 - 각자 다른 회사에서 배운 경험을 가지고.

업무와 교육은 어떤 관계인가?

휴대폰처럼 분리되는 게 아니다.

  • 교육하면 배우는 쪽은 업무 역량이 올라간다
  • 가르치는 쪽은 관리 역량이 올라간다
  • 구성원의 수준이 끌어올려지면서 조직 전체 퍼포먼스가 올라간다

신입사원 특훈 코스를 따로 만드는 게 아니다. CPU 용량도 안 잡아먹는다.

초기 시니어만 있는 조직의 함정

프로젝트 초기 시니어들만 모여있을 때는 잘 되다가, 사람을 많이 뽑으면 갑자기 일 진행이 안 되는 경우가 있다.

이유: 시니어들한테만 프로젝트 노하우가 쏠려 있고, 교육이 제대로 이루어지지 않으면 총력전이 되지 않고 퍼포먼스가 떨어진다.

교육이 제대로 이루어지지 않으면 프로젝트 키우기도 어렵다.

Part 9. 실제 적용 시 주의사항

코드 리뷰 3단계는?
1단계: 컨벤션이나 네이밍 (기계적으로 체크 가능) 2단계: 팀에서 정한 각종 규칙 준수 3단계: 같은 의도를 표현하는 더 나은 코드

처음부터 욕심내서 너무 많은 걸 한꺼번에 교정하려고 하지 않는다.

기계적으로 할 수 있는 것부터 교정 -> 규칙 -> 좋은 코드 순서로 진행.

리뷰어 리소스를 아끼려면?
  • 동작 테스트 안 된 코드를 리뷰 요청하면 안 된다
  • 구현 시작하기 전에 설계 리뷰를 먼저 거친다
  • 리뷰를 구체적으로 요청한다 ("이거 데드락 발생하지 않을까요?", "성능 병목 우려되는데요")
  • 커밋을 잘 쪼갠다 (포맷팅 변경만 있는 것 / 로직 변경이 있는 것 분리)
좋은 규칙이 충돌하면 어떻게 하나?

규칙을 잘 지키려고 했는데 코드가 더 나빠지는 경우가 있다.

그럴 때는 "좋은 코드인 쪽을 따르세요"라고 안내한다.

규칙이 틀렸거나, 규칙이 변경된 상황을 반영하지 못하는 것이다.

규칙은 계속 고정된 게 아니다. 같이 토론해서 규칙을 바꾸면 된다.

팀원 관리 팁
  • 눈치를 봐라 - 잘 배우고 있는지, 만족하는지, 너무 힘들지 않은지
  • 관심도 갖고 정보도 얻으려면 밥이나 술도 사줘야 한다
  • 열심히 가르쳤으면 오래 같이 일할 수 있어야 한다
  • 회사에서 가장 친밀한 관계가 교육 관계다
칭찬은 어떻게 해야 하나?

가르침 받는 사람들은 좀 위축될 수 있다. 리뷰에서 지적만 많이 달리면 힘들다.

지적한 부분 빼 나머지는 잘한 거다.

의식적으로 잘한 부분을 발견해서 칭찬해줘야 한다.

금기 단어: 센스, 실력

"센스"라는 말이 나오면?

-> 내가 지금 가르치고자 하는 걸 잘 설명하지 못하고 있구나라고 스스로 생각해야 한다.

-> 안 가르쳐 놓고 사람이 자라길 바라고 있는 게 아닌가?

총정리: 게임 프로그래머 교육

왜 가르쳐야 하나

  • 프로그래머가 잘 해줘야 게임 퀄리티 유지
  • 학교와 회사는 품질 기준, 유지보수 기간이 완전히 다르다
  • 경력자도 조직 문화에 맞추기 위해 재교육 필요
  • 내가 일을 즐겁게 하려면 동료들이 일을 잘 해야 한다

교육 방법 3가지

코드 리뷰 -> 좋은 코드 쓰는 법 설계 리뷰 -> 조직의 노하우와 가치 반영 아침회의 -> 커뮤니케이션 스킬 공통 패턴: 롤모델 제시 -> 모방 -> 피드백 -> 대체

관리자 육성과 조직문화

  • 코드 리뷰/설계 리뷰는 신입 교육용이 아니라 팀이 함께 일하는 방식
  • 교육을 통해 관리자 역할이 자연스럽게 분산
  • 조직 이끌기 = 가장 뛰어난 사람 X, 문화를 리드하고 구성원 성장시키기

좋은 엔지니어링 문화란

  • 개인이 아닌 조직 전체를 통해 성과를 낸다
  • 구성원 간의 시너지를 최대로 끌어낸다
  • 가르치고, 가르친 사람들이 좋은 성과를 내고, 좋은 관리자가 되는 선순환

핵심 마인드셋

"한 아이를 키우려면 온 마을이 필요하다" 프로그래머도 마찬가지. 서로에게 서로의 마을이 되어주고, 좋은 프로그래머로 성장할 수 있는 기회를 가졌으면 좋겠다.
