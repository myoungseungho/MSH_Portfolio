가비지 컬렉션 (Garbage Collection)

메모리 자동 청소부 - 왜 필요하고, 어떻게 동작할까?

Part 1. 메모리를 쓰려면?

프로그램에서 메모리를 쓰려면 뭘 해야 해?

할당(Allocation)을 해야 해!

// C++ int* ptr = new int[100]; // 메모리 할당: "100칸 줘!" // C# int[] arr = new int[100]; // 메모리 할당: "100칸 줘!" // 공통점: 메모리를 "빌려오는" 것
빌려왔으면 뭘 해야 해?

반납(해제)해야지!

// C++ - 수동으로 반납해야 함 int* ptr = new int[100]; // 빌림 // ... 사용 ... delete[] ptr; // 반납: "다 썼어, 돌려줄게" // 반납 안 하면? // → 메모리 누수 (Memory Leak)!

Part 2. 수동 관리의 문제점

직접 반납하면 되는 거 아니야?

이론적으론 그래. 근데 실수하기 너무 쉬워.

[문제 1: 반납 까먹음 - 메모리 누수] void process() { int* data = new int[1000]; if (error) { return; // 😱 delete 안 하고 나감! } delete[] data; } → error 나면 메모리 누수!
[문제 2: 두 번 반납 - 크래시] int* ptr = new int[100]; delete[] ptr; delete[] ptr; // 😱 이미 반납한 거 또 반납! → 프로그램 크래시!
[문제 3: 반납한 거 사용 - Dangling Pointer] int* ptr = new int[100]; delete[] ptr; ptr[0] = 42; // 😱 반납한 메모리에 쓰기! → 정의되지 않은 동작 (뭔 일이 일어날지 모름)
이런 실수 많이 해?

엄청 많이!

C/C++ 버그의 상당수가 메모리 관련.

대형 프로젝트에서는 찾기도 어려움.

Part 3. "가비지"가 뭐야?

가비지 컬렉션의 "가비지"가 뭐야?

쓰레기 = 더 이상 사용하지 않는 메모리

[가비지의 정의] 메모리는 할당됐는데, 아무도 그 메모리를 가리키지 않는 상태 = 접근할 방법이 없는 메모리 = 쓸모없는 메모리 = 가비지!
[예시] void example() { Object* obj = new Object(); // 메모리 할당, obj가 가리킴 obj = null; // 이제 아무도 그 메모리를 안 가리킴! // 메모리는 아직 할당된 상태인데 // 접근할 방법이 없음 // → 이게 "가비지"! }
그림으로 보면?
[처음] obj ──────→ [Object 메모리] (사용 중) [obj = null 후] obj ──→ null [Object 메모리] ← 아무도 안 가리킴! (가비지!) → 메모리는 차지하는데 쓸 수가 없음 → 누군가 치워줘야 함!

Part 4. 가비지 컬렉션이란?

그래서 가비지 컬렉션이 뭐야?

자동으로 가비지를 찾아서 치워주는 것!

[수동 메모리 관리] - C, C++ 개발자: "메모리 줘" (new) 시스템: "여기 있어" 개발자: (사용) 개발자: "다 썼어, 반납할게" (delete) ← 직접 해야 함! [가비지 컬렉션] - C#, Java, Python, JavaScript 개발자: "메모리 줘" (new) 시스템: "여기 있어" 개발자: (사용) 개발자: (그냥 안 씀) GC: "어? 이거 아무도 안 쓰네? 내가 치울게" ← 자동!
개발자가 delete 안 해도 돼?

맞아! GC가 알아서 해줌.

// C# 예시 void Example() { var obj = new MyClass(); // 메모리 할당 // ... 사용 ... } // 함수 끝나면 obj가 사라짐 // → GC가 나중에 알아서 메모리 정리! // delete 같은 거 안 써도 됨!

Part 5. 어떻게 가비지인지 알아?

GC가 "이건 가비지다"를 어떻게 판단해?

크게 두 가지 방법이 있어.

[방법 1: 참조 카운팅 (Reference Counting)] 각 객체가 "나를 가리키는 게 몇 개야?"를 셈 Object obj = new Object(); // 참조 카운트 = 1 Object obj2 = obj; // 참조 카운트 = 2 obj = null; // 참조 카운트 = 1 obj2 = null; // 참조 카운트 = 0 → 가비지! 카운트가 0이 되면 → 바로 해제!
참조 카운팅 좋아 보이는데?

간단하지만 치명적 문제가 있어.

[참조 카운팅의 문제: 순환 참조] class Node { Node next; } Node a = new Node(); // a 카운트 = 1 Node b = new Node(); // b 카운트 = 1 a.next = b; // b 카운트 = 2 b.next = a; // a 카운트 = 2 a = null; // a 카운트 = 1 (b.next가 가리킴) b = null; // b 카운트 = 1 (a.next가 가리킴) // 둘 다 카운트가 1이라 해제 안 됨! // 근데 둘 다 접근 불가능! // → 메모리 누수!
[그림으로 보면] 처음: a ──→ [Node A] ──→ [Node B] ←── b ↑______________| a = null, b = null 후: [Node A] ──→ [Node B] ↑______________| (서로 가리키고 있어서 카운트 0이 안 됨!) (근데 우리는 접근할 방법이 없음!) → 가비지인데 해제 안 됨!
그럼 어떻게 해?

마크 앤 스윕 (Mark and Sweep) 방식!

[방법 2: 마크 앤 스윕 (Mark and Sweep)] 1단계 - Mark (표시): "루트"에서 시작해서 접근 가능한 모든 객체에 표시 루트 = 전역 변수, 스택의 지역 변수, 레지스터 등 2단계 - Sweep (쓸기): 표시 안 된 객체 = 접근 불가능 = 가비지 → 전부 해제!
[그림으로 보면] [루트] │ ▼ [객체 A] ──→ [객체 B] [객체 C] ──→ [객체 D] (루트에서 연결 안 됨!) 1단계 - Mark: 루트 → A 표시 ✓ A → B 표시 ✓ C, D는 루트에서 못 감 → 표시 안 됨 2단계 - Sweep: 표시 안 된 C, D 해제! → 순환 참조도 해결됨! (루트에서 접근 못 하면 순환이든 뭐든 가비지)
참조 카운팅 마크 앤 스윕
방식 참조 수 세기 루트에서 탐색
해제 시점 즉시 (카운트 0일 때) GC 실행 시
순환 참조 해결 못 함 해결 가능
오버헤드 참조마다 카운트 변경 GC 실행 시 일시 정지

Part 5.5. GC가 실제로 하는 일 3단계

마크 앤 스윕이면 끝이야? 뭔가 더 있을 것 같은데.

좋은 질문! 실제로는 3단계야.

[GC의 3단계] 1. Mark (표시) → 살아있는 객체 표시 2. Sweep (해제) → 죽은 객체 해제 3. Compact (압축) → 살아있는 객체 재배치 ← 이게 숨어있었음!
왜 Compact가 필요해?

Sweep만 하면 외부 단편화가 생겨!

[Mark-Sweep만 하면 생기는 문제] 해제 전: [A][B][C][D][E][F][G][H] B, D, F 해제 후: [A][ ][C][ ][E][ ][G][H] ↑ ↑ ↑ 구멍 구멍 구멍 ← 외부 단편화! 새 객체가 3칸 필요하면? → 빈칸은 총 3칸인데... 연속이 아니라서 못 넣음! → 메모리 할당 전략 문서에서 본 그 문제!
그래서 Compact가 뭘 해?

살아있는 객체를 한쪽으로 밀어서 빈 공간을 합쳐!

[Compact 단계] Sweep 후: [A][ ][C][ ][E][ ][G][H] Compact 후: [A][C][E][G][H][ ] ↑ 연속된 빈 공간! → 이제 3칸짜리 객체도 들어갈 수 있음!
근데 그럼 참조 주소가 바뀌잖아?

맞아! 그래서 Compact가 비싸.

[Compact의 비용] 객체 이동하면: 1. 모든 포인터/참조를 업데이트해야 함 2. 이동 중에는 프로그램 완전 정지 필요 3. 메모리 복사 비용 → Stop-the-World 시간이 더 길어짐! → 그래서 매번 안 하고, 필요할 때만 하거나 아예 다른 방식을 쓰기도 함
다른 방식?

Copying GC라는 방법이 있어!

[Copying GC] 메모리를 반으로 나눔: From 영역 / To 영역 [From 영역] [To 영역] [A][ ][B][ ][C] [ ] ↓ 살아있는 것만 복사! [From 영역] [To 영역] [A][ ][B][ ][C] [A][B][C] ↑ 복사하면서 자연스럽게 압축! 그 다음 From/To 역할 교체! 장점: 압축이 공짜! 단점: 메모리의 절반만 사용 가능
GC 방식 단편화 비용 메모리
Mark-Sweep 발생함 빠름 효율적
Mark-Sweep-Compact 해결 느림 (이동) 효율적
Copying GC 해결 중간 2배 필요

Part 6. GC의 장단점

GC 좋아 보이는데 단점은?
장점 단점
메모리 누수 방지 성능 오버헤드
Dangling Pointer 방지 GC 실행 시 멈춤 (Stop-the-World)
개발 편의성 메모리 해제 시점 예측 불가
이중 해제 방지 메모리 더 많이 사용
"Stop-the-World"가 뭐야?

GC 하는 동안 프로그램이 멈추는 것!

[Stop-the-World] 프로그램: 열심히 실행 중... GC: "잠깐! 청소할게" 프로그램: (멈춤) ... GC: (모든 객체 스캔, 가비지 정리) GC: "끝!" 프로그램: 다시 실행! → 이 "멈춤" 시간이 문제! → 게임이면 프레임 드랍, 끊김!

Part 7. 게임에서 GC가 문제인 이유

게임에서 GC가 왜 문제야?

게임은 일정한 프레임을 유지해야 해.

[60fps 게임] 1프레임 = 16.6ms 안에 모든 처리 완료해야 함 프레임 1: 게임 로직 (10ms) ✅ 프레임 2: 게임 로직 (10ms) ✅ 프레임 3: 게임 로직 (10ms) + GC (50ms) ❌ → 총 60ms! → 3프레임 놓침! → 유저 체감: "끊기네?"
그럼 게임에서 어떻게 해?

GC를 최소화하는 기법들:

[기법 1: 오브젝트 풀링] // 나쁜 예 - 매번 new void Fire() { Bullet b = new Bullet(); // GC 대상 생성! // ... } // 좋은 예 - 오브젝트 풀 void Fire() { Bullet b = bulletPool.Get(); // 미리 만든 거 재사용 // ... bulletPool.Return(b); // 다 쓰면 풀에 반납 } → new 안 하니까 GC 대상 안 생김!
[기법 2: 구조체 사용 (Unity C#)] // 클래스 - 힙에 할당 → GC 대상 class Vector3Class { float x, y, z; } // 구조체 - 스택에 할당 → GC 대상 아님! struct Vector3Struct { float x, y, z; } → Unity의 Vector3는 구조체라서 GC 부담 없음!
[기법 3: 문자열 조심] // 나쁜 예 - 문자열 더하기마다 새 객체 생성 string s = "HP: " + hp + "/" + maxHp; // 임시 문자열 여러 개! // 좋은 예 - StringBuilder 사용 StringBuilder sb = new StringBuilder(); sb.Append("HP: "); sb.Append(hp); sb.Append("/"); sb.Append(maxHp); → 임시 객체 최소화!

Part 8. 언어/엔진별 GC

언어/엔진 GC 방식 특징
C/C++ 없음 (수동) 직접 new/delete
C# (Unity) 마크 앤 스윕 Boehm GC, 세대별 GC
Java 마크 앤 스윕 세대별 GC, G1 GC 등
Python 참조 카운팅 + 마크 앤 스윕 순환 참조는 별도 처리
Unreal C++ 없음 (수동) + 스마트 포인터 UObject는 별도 시스템
세대별 GC가 뭐야?

"대부분의 객체는 금방 죽는다"는 관찰에 기반!

[세대별 GC (Generational GC)] 관찰: 새로 만든 객체의 80%는 금방 안 쓰게 됨 아이디어: 젊은 객체 위주로 자주 검사하자! [0세대] - 새로 생긴 객체 → 자주 검사 (빠름, 작은 영역) → 살아남으면 1세대로 승격 [1세대] - 좀 오래 산 객체 → 가끔 검사 → 살아남으면 2세대로 승격 [2세대] - 오래 산 객체 → 거의 검사 안 함 → 전체 검사보다 효율적!
Unity랑 Unreal은 GC가 어떻게 달라?

완전히 다른 철학이야!

[Unity - 전부 GC가 관리] 언어: C# 방식: 모든 C# 객체를 GC가 자동 관리 // Unity 코드 GameObject enemy = new GameObject(); // GC 관리 대상 Vector3 pos = new Vector3(1, 2, 3); // 구조체라 스택 (GC 아님) 특징: - Boehm GC (비압축, 비세대별) → 최근 버전은 Incremental GC - 모든 class 객체가 GC 대상 - 개발자가 해제 시점 제어 불가 - GC 스파이크 주의 필요!
[Unreal - 이원화된 메모리 관리] 언어: C++ 방식: 일반 C++ + UObject 전용 GC // 일반 C++ 객체 - 수동 관리 FVector* vec = new FVector(1, 2, 3); delete vec; // 직접 해제 // 스마트 포인터 - 참조 카운팅 TSharedPtr ptr = MakeShared(); // 참조 없으면 자동 해제 (순환 참조 주의!) // UObject 파생 클래스 - 전용 GC UPROPERTY() UStaticMesh* Mesh; // 언리얼 GC가 관리 특징: - UObject만 GC 대상 (AActor, UActorComponent 등) - 일반 C++ 객체는 수동 or 스마트 포인터 - UPROPERTY() 매크로 필수 (GC에게 알려주는 것) - 더 세밀한 제어 가능, 더 복잡함
Unity (C#) Unreal (C++)
GC 대상 모든 class 객체 UObject 계열만
일반 객체 GC 자동 관리 수동 or 스마트 포인터
GC 방식 Mark-Sweep (Incremental) Mark-Sweep (UObject 전용)
개발 난이도 쉬움 (자동) 어려움 (혼합)
성능 제어 제한적 세밀함
메모리 최적화 오브젝트 풀링 필수 수동 관리로 GC 회피 가능
결국 어느 게 더 좋아?

Trade-off야!

Unity: 편하지만 GC 스파이크 조심

Unreal: 귀찮지만 성능 제어 가능

[실무 팁] Unity에서 GC 줄이기: - 오브젝트 풀링 필수 - struct 활용 (Vector3 등) - string 조심, StringBuilder 사용 - Update()에서 new 금지! Unreal에서 메모리 관리: - UObject는 UPROPERTY() 붙이기 - 일반 객체는 TSharedPtr/TUniquePtr 활용 - Raw 포인터 최소화 - AddToRoot() / RemoveFromRoot() 주의

핵심 정리

  • 가비지 = 할당됐지만 접근 불가능한 메모리
  • 가비지 컬렉션 = 가비지를 자동으로 찾아서 해제
  • 참조 카운팅 = 참조 수 세기, 순환 참조 문제
  • 마크 앤 스윕 = 루트에서 탐색, 순환 참조 해결
  • GC 3단계 = Mark → Sweep → Compact (외부 단편화 해결)
  • Copying GC = 살아있는 것만 복사, 압축이 공짜
  • Stop-the-World = GC 중 프로그램 멈춤
  • 세대별 GC = 젊은 객체 위주로 검사, 효율적
  • Unity = 전부 GC, 오브젝트 풀링 필수
  • Unreal = UObject만 GC, 나머지 수동/스마트포인터
