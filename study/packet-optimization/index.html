패킷 1바이트를 아끼면 서버비가 얼마나 줄까?

패킷 구조 설계, 직렬화, 헤더 최적화

네트워크

🤔 패킷이 뭔데?

패킷(Packet)이 뭐야?

게임 클라이언트와 서버가 주고받는 데이터 덩어리야.

예를 들어:

  • 플레이어가 이동 → 클라이언트가 "X좌표, Y좌표" 패킷 전송
  • 채팅 메시지 입력 → "닉네임, 메시지 내용" 패킷 전송
  • 스킬 사용 → "스킬 ID, 타겟 ID" 패킷 전송
패킷 크기가 왜 중요해? 몇 바이트 차이가 뭐가 중요해?

1바이트 차이가 수백만 원을 만든다.

왜냐하면:

  • 게임 서버는 초당 수만~수십만 개의 패킷을 주고받아
  • 유저가 많을수록 패킷도 기하급수적으로 늘어나
  • 클라우드 서버는 데이터 전송량에 따라 과금돼
🏪 비유: 택배 상자 크기

택배비는 상자 크기에 따라 달라지지?
- 작은 상자 (60cm): 3,000원
- 큰 상자 (100cm): 5,000원

하루에 물건 1,000개를 보낸다면?
- 작은 상자: 3,000원 × 1,000 = 300만 원
- 큰 상자: 5,000원 × 1,000 = 500만 원

상자만 줄여도 하루 200만 원 절약!

패킷도 마찬가지야. 패킷 크기를 줄이면 서버 비용이 확 줄어들어.

💰 1바이트가 만드는 충격적인 차이

진짜 1바이트가 그렇게 큰 차이를 만들어?

직접 계산해보자.

📊 실제 계산 (MMO 게임 기준)

동시 접속자(CCU): 100,000명 패킷 전송 빈도: 초당 10개 (이동, 공격, 상태 동기화) 하루 운영 시간: 24시간 1바이트 차이가 만드는 데이터량: 초당 데이터: 100,000명 × 10패킷/초 × 1바이트 = 1MB/초 하루 데이터: 1MB/초 × 86,400초 = 86.4GB/일 한 달 데이터: 86.4GB/일 × 30일 = 2,592GB (약 2.5TB)
패킷 1바이트 차이 = 한 달 2.5TB 차이

AWS 비용 기준 (데이터 전송 비용):

AWS 데이터 전송 비용: 약 $0.09/GB 월 비용 차이: 2,592GB × $0.09 = $233 (약 30만 원) 연간 비용: $233 × 12 = $2,796 (약 360만 원)
패킷 1바이트만 줄여도 연간 360만 원 절약!
헉... 진짜 큰 차이네. 그럼 패킷을 어떻게 줄일 수 있어?

방법은 크게 3가지야:

  • 1. 데이터 타입 최적화 - 꼭 필요한 크기만 쓰기
  • 2. 패킷 구조 설계 - 헤더 최적화, 비트 플래그
  • 3. 직렬화 방식 선택 - Binary vs JSON

⚡ 방법 1: 데이터 타입 최적화

데이터 타입이 뭐가 중요해? 숫자는 그냥 int 쓰면 되는 거 아니야?

아니야! 타입 선택이 패킷 크기를 2배~4배 차이나게 만들어.

타입 크기 범위 사용 예시
byte (8bit) 1바이트 0 ~ 255 레벨 (1~100), HP% (0~100)
short (16bit) 2바이트 -32,768 ~ 32,767 좌표 (맵 크기 제한), 아이템 개수
int (32bit) 4바이트 -21억 ~ 21억 유저 ID, 경험치, 골드
long (64bit) 8바이트 -922경 ~ 922경 타임스탬프, 글로벌 고유 ID

❌ 나쁜 예: 모든 숫자를 int로

struct MovePacket { int playerId; // 4바이트 int x; // 4바이트 (맵 크기: 0~1000) int y; // 4바이트 (맵 크기: 0~1000) int direction; // 4바이트 (방향: 0~7) } // 총 16바이트

✅ 좋은 예: 필요한 크기만

struct MovePacket { int playerId; // 4바이트 (필수) short x; // 2바이트 (0~32767이면 충분) short y; // 2바이트 byte direction; // 1바이트 (0~7, 8방향) } // 총 9바이트 (43% 절약!)

📊 절약 효과

패킷 크기 차이: 16바이트 → 9바이트 (7바이트 절약) 이동 패킷 전송 빈도: - 100,000명 CCU - 초당 20개 (이동이 제일 많이 일어남) 연간 절약 비용: 7바이트 × 100,000명 × 20패킷/초 × 86,400초/일 × 30일 × 12개월 = 약 435TB/년 435TB × $0.09 = $39,150 (약 5천만 원!)
이동 패킷 하나만 최적화해도 연간 5천만 원 절약

🔧 방법 2: 비트 플래그 (Bit Flag)

상태 정보(버프, 디버프)를 어떻게 보내?

플레이어 상태를 생각해봐:

  • 독 상태인가? (true/false)
  • 무적 상태인가? (true/false)
  • 스턴 상태인가? (true/false)
  • 은신 상태인가? (true/false)

이걸 어떻게 보낼까?

❌ 나쁜 예: bool 4개

struct PlayerState { bool isPoisoned; // 1바이트 bool isInvincible; // 1바이트 bool isStunned; // 1바이트 bool isInvisible; // 1바이트 } // 총 4바이트

✅ 좋은 예: 비트 플래그 1개

struct PlayerState { byte statusFlags; // 1바이트로 8개 상태 표현! } // 비트 위치로 상태 구분: // 0000 0001 = 독 (bit 0) // 0000 0010 = 무적 (bit 1) // 0000 0100 = 스턴 (bit 2) // 0000 1000 = 은신 (bit 3) // 사용: statusFlags = 0b00001101; // 독 + 스턴 + 은신 동시 표현 // 총 1바이트 (75% 절약!)
비트로 어떻게 체크해?

비트 연산으로 간단하게:

// 비트 설정 statusFlags |= (1 << 0); // 독 상태 ON statusFlags |= (1 << 2); // 스턴 상태 ON // 비트 체크 if (statusFlags & (1 << 0)) { // 독 상태다! } // 비트 해제 statusFlags &= ~(1 << 0); // 독 상태 OFF
근데 이거... 매번 (1 << 0)이 뭔지 찾아보는 거 너무 불편한데?

정확해! 실무에서는 이렇게 안 써.

비트 연산을 직접 쓰면 가독성이 끔찍하게 나빠져.

  • 0번 비트가 뭐였지?
  • 2번 비트는 무적? 스턴?
  • 새 상태 추가할 때 어느 비트 쓰지?

💼 실무에서는 이렇게 씁니다

❌ 가독성 최악 (초보자가 쓰는 방식)

// 뭐가 뭔지 모르겠음 statusFlags |= (1 << 0); statusFlags |= (1 << 2); if (statusFlags & (1 << 1)) { // 이게 뭐더라...? }

✅ 실무 코드 (C++ enum class + 래퍼 클래스)

// 1. enum class로 상태 정의 (타입 안전성) enum class PlayerStatus : uint8_t { Poisoned = 1 << 0, // 0b00000001 Invincible = 1 << 1, // 0b00000010 Stunned = 1 << 2, // 0b00000100 Invisible = 1 << 3, // 0b00001000 }; // 2. 래퍼 클래스로 추상화 class StatusFlags { private: uint8_t flags_ = 0; // 실제 패킷에 들어갈 1바이트 public: // 읽기 쉬운 인터페이스 void Add(PlayerStatus status) { flags_ |= static_cast(status); } void Remove(PlayerStatus status) { flags_ &= ~static_cast(status); } bool Has(PlayerStatus status) const { return (flags_ & static_cast(status)) != 0; } uint8_t GetRaw() const { return flags_; // 패킷 전송용 } void SetRaw(uint8_t raw) { flags_ = raw; // 패킷 수신용 } }; // 3. 사용 (매우 직관적!) StatusFlags player; player.Add(PlayerStatus::Poisoned); player.Add(PlayerStatus::Stunned); if (player.Has(PlayerStatus::Poisoned)) { // 독 데미지 입히기 } player.Remove(PlayerStatus::Poisoned); // 4. 패킷 전송 시 packet.statusFlags = player.GetRaw(); // 1바이트만 전송!
오! 이렇게 하면 코드 보기 훨씬 편하네!

맞아! 캡슐화의 힘이야.

  • 외부에서는 편하게 - Has(Poisoned)
  • 내부는 효율적으로 - 실제로는 1바이트
  • 유지보수 쉽게 - 비트 위치 몰라도 됨
🏗️ 비유: TV 리모컨

리모컨 내부는 복잡한 전기 신호지만,
사용자는 그냥 "채널 ↑" 버튼만 누르면 되지?

비트 플래그도 마찬가지야:
- 내부: 복잡한 비트 연산 (0b00001101)
- 외부: 간단한 함수 (Add, Has, Remove)

복잡한 건 클래스 안에 숨기고, 사용은 쉽게!

📦 방법 3: 직렬화 방식 선택

JSON이 편한데 왜 Binary를 쓰라고 해?

직접 비교해보자.

JSON 방식

{ "playerId": 123456, "x": 512, "y": 256, "direction": 3 } // 실제 문자열: // {"playerId":123456,"x":512,"y":256,"direction":3} // 총 52바이트

Binary 방식

struct MovePacket { int playerId; // 4바이트 short x; // 2바이트 short y; // 2바이트 byte direction; // 1바이트 } // 총 9바이트

📊 JSON vs Binary 비교

방식 크기 가독성 파싱 속도 사용 케이스
JSON 52바이트 ⭐⭐⭐⭐⭐ ⭐⭐ 웹 API, 디버깅
Binary 9바이트 ⭐ ⭐⭐⭐⭐⭐ 게임 서버, 실시간 통신
JSON 대비 Binary가 82% 작음 (52 → 9바이트)
그럼 항상 Binary를 써야 해?

아니야! 상황에 맞게 선택해야 해.

  • Binary 추천: 실시간 게임 패킷 (이동, 전투)
  • JSON 추천: 로그인, 인벤토리 조회 (빈도 낮음)
  • Protobuf: 중간 타협 (스키마 + 압축)

🎯 실전 최적화 사례

실전에서는 어떻게 쓰이나?

MMORPG 위치 동기화를 예로 들어볼게.

❌ 최적화 전 (초보자)

struct PlayerPosition { long timestamp; // 8바이트 int playerId; // 4바이트 float x; // 4바이트 (소수점) float y; // 4바이트 float z; // 4바이트 int direction; // 4바이트 bool isRunning; // 1바이트 bool isJumping; // 1바이트 } // 총 30바이트

✅ 최적화 후 (실무)

struct PlayerPosition { int playerId; // 4바이트 short x; // 2바이트 (정수로 변환: 실제 좌표 × 10) short y; // 2바이트 short z; // 2바이트 byte flags; // 1바이트 (방향 3bit + 달리기 1bit + 점프 1bit) } // 총 11바이트 (63% 절약!) // flags 구조: // [7 6 5 4 3 2 1 0] // ↑ ↑ ↑ ↑ // 점프 달리기 | // 방향(0~7)

📊 최적화 효과 계산

패킷 크기: 30바이트 → 11바이트 (19바이트 절약) 위치 동기화 빈도: - 100,000명 CCU - 초당 30개 (가장 빈번한 패킷) 연간 절약: 19바이트 × 100,000명 × 30패킷/초 = 연간 약 1.5PB 1,500TB × $0.09 = $135,000 (약 1억 7천만 원!)
위치 패킷만 최적화해도 연간 1억 7천만 원 절약

🧪 추가 최적화 기법

더 줄일 수는 없어?

있어! 고급 기법들을 소개할게.

1. 델타 압축 (Delta Compression)

변경된 값만 보내기

❌ 매번 전체 데이터: { x: 512, y: 256, hp: 100, mp: 50 } // 13바이트 ✅ 변경된 것만: { changed: 0b0001, x: 515 } // 3바이트 (x만 변경됨) // 77% 절약!

2. 가변 길이 인코딩 (VarInt)

작은 숫자는 작게, 큰 숫자는 크게

일반 int: 항상 4바이트 - 숫자 1 → 0x00000001 (4바이트) - 숫자 300 → 0x0000012C (4바이트) VarInt: 크기에 따라 1~5바이트 - 숫자 1 → 0x01 (1바이트) - 숫자 300 → 0xAC02 (2바이트) 작은 숫자가 많을 때 효과적! (레벨, 스킬 ID, 아이템 개수 등)

3. 패킷 배칭 (Batching)

여러 패킷을 한 번에 보내기

❌ 개별 전송: 헤더(2바이트) + 이동(9바이트) = 11바이트 헤더(2바이트) + 공격(5바이트) = 7바이트 헤더(2바이트) + 채팅(20바이트) = 22바이트 // 총 40바이트 ✅ 배칭: 헤더(2바이트) + 이동(9) + 공격(5) + 채팅(20) = 36바이트 // 4바이트 절약 (헤더 중복 제거)

아니야! 과도한 최적화는 독이 될 수 있어.

📋 최적화 우선순위

  1. 1순위: 가장 빈번한 패킷 (이동, 공격)
  2. 2순위: 크기가 큰 패킷 (인벤토리, 맵 데이터)
  3. 3순위: 그 외 (로그인, 설정)

📌 핵심 정리: 패킷 최적화

  • 1바이트 차이 = 연간 360만 원 - 작은 차이가 큰 비용을 만든다
  • 타입 최적화 - int 대신 byte/short 사용 (43% 절약)
  • 비트 플래그 - 8개 상태를 1바이트로 (75% 절약)
  • 실무 코드 작성법 - Enum + 래퍼 클래스로 가독성 유지 (성능과 가독성 둘 다 잡기)
  • Binary 직렬화 - JSON 대비 82% 작음
  • 델타 압축 - 변경된 값만 전송 (77% 절약)
  • VarInt - 작은 숫자는 1바이트로
  • 패킷 배칭 - 헤더 중복 제거
  • 트레이드오프 - 가독성과 성능의 균형
