프로그레스 바의 거짓말

왜 진행률은 항상 99%에서 멈추는가 - 정직한 진행률 vs 심리적 진행률의 기술적 구현

Part 1. 진행률의 불편한 진실

프로그레스 바의 진행률이 정확하지 않다는 게 무슨 뜻이야?

게임을 시작하면 보이는 로딩 화면의 프로그레스 바, 그것은 대부분 거짓말입니다. "50%" 라고 표시되어 있다고 해서 실제로 작업의 절반이 완료된 것이 아닙니다.

이것이 단순한 기술적 한계가 아니라 의도적인 설계라는 점이 핵심입니다. 왜 게임 개발자들은 정확한 진행률 대신 "조작된" 진행률을 보여줄까요?

실제 로딩 진행률 vs 표시 진행률:

시간 →  0s        5s        10s       15s       20s
        ├─────────┼─────────┼─────────┼─────────┤

실제 진행률:
        ░░░░░░░░░░██████████████████████████████
        ↑         ↑
        초기화 단계     파일 I/O (빠름)
        (매우 느림)

        실제: 0%...5%...10%...................95%→100%

표시되는 진행률:
        ████████████████████████████████████████

        표시: 0%→25%→50%→75%→90%→95%→99%→100%
              (일정한 속도로 증가하는 것처럼 보임)

★ 핵심: 정직한 진행률은 UX를 해친다!
   - 처음 5초간 5%도 안 올라가면 → "멈췄나?" 걱정
   - 갑자기 50%→95% 점프하면 → 불안정해 보임
실제 로딩 시간이 불규칙한 이유는 뭐야?

로딩 시간이 예측 불가능한 이유는 여러 계층에 걸쳐 있습니다:

로딩 시간 불확실성의 원인:

┌─────────────────────────────────────────────────────────────┐
│                    응용 프로그램 레벨                        │
│  • 초기화 로직 (일회성 설정, 캐시 구축)                      │
│  • 에셋 후처리 (밉맵 생성, 쉐이더 컴파일)                    │
│  • 의존성 해결 (A 로드 → B 필요 → B 로드)                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    압축/해제 레벨                            │
│  • 압축률이 높은 파일 = 해제 시간 증가                       │
│  • 텍스처 압축 형식 (BC7 > BC1 > 무압축)                     │
│  • 스트리밍 vs 전체 해제                                     │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    파일 시스템 레벨                          │
│  • 파일 단편화 (조각난 파일 = 느린 읽기)                     │
│  • 디렉토리 탐색 오버헤드                                    │
│  • 메타데이터 조회 (파일 크기, 수정일 등)                    │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    저장 장치 레벨                            │
│  HDD:  탐색 시간 ~10ms, 순차 읽기 ~150MB/s                  │
│  SATA SSD: 탐색 시간 ~0.1ms, 읽기 ~550MB/s                  │
│  NVMe SSD: 탐색 시간 ~0.02ms, 읽기 ~3500MB/s                │
│                                                             │
│  같은 게임이 HDD에서 20배 느릴 수 있음!                      │
└─────────────────────────────────────────────────────────────┘
                            ↓
┌─────────────────────────────────────────────────────────────┐
│                    OS/하드웨어 레벨                          │
│  • 다른 프로세스의 I/O 경쟁                                  │
│  • 페이지 캐시 상태 (핫/콜드)                                │
│  • 안티바이러스 실시간 스캔                                  │
│  • 전원 관리 (절전 모드 → 디스크 스핀업)                     │
└─────────────────────────────────────────────────────────────┘

★ 동일한 파일도 조건에 따라 로딩 시간이 10배 이상 차이남
// 예측 불가능성의 실제 예 // 같은 텍스처 파일 로딩 시간 측정 (1000회 평균) struct LoadingTimeStats { float average; float min; float max; float stdDev; }; // hero_texture.dds (4MB 파일) // 측정 결과: // HDD (캐시 없음): avg=45ms, min=20ms, max=850ms, stdDev=120ms // HDD (캐시 있음): avg=5ms, min=2ms, max=15ms, stdDev=3ms // SSD (캐시 없음): avg=8ms, min=5ms, max=25ms, stdDev=4ms // SSD (캐시 있음): avg=0.5ms, min=0.2ms, max=2ms, stdDev=0.3ms // 결론: 같은 파일이 0.2ms ~ 850ms (4250배 차이!) // 이런 상황에서 "정확한" 진행률은 의미 없음

Part 2. 진행률 측정 방식의 종류

그래도 진행률을 어떻게든 측정해야 하잖아. 어떤 방법들이 있어?

진행률을 측정하는 방식에는 여러 가지가 있고, 각각 장단점이 있습니다:

진행률 측정 방식 비교:

┌────────────────────────────────────────────────────────────────┐
│ 1. 파일 개수 기반 (Count-Based)                                │
├────────────────────────────────────────────────────────────────┤
│ 공식: progress = loadedFiles / totalFiles                      │
│                                                                │
│ 예: 100개 파일 중 50개 로드 완료 → 50%                         │
│                                                                │
│ 장점: 구현 단순, 직관적                                        │
│ 단점: 파일 크기 무시 (1KB = 1GB)                               │
│                                                                │
│ [████████░░] 80% (8/10 files)                                  │
│  ↑ 1KB 파일 8개 완료, 남은 2개가 각각 500MB면?                 │
│    실제로는 전체의 0.001%만 완료된 것!                         │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ 2. 바이트 기반 (Byte-Based)                                    │
├────────────────────────────────────────────────────────────────┤
│ 공식: progress = loadedBytes / totalBytes                      │
│                                                                │
│ 예: 1GB 중 500MB 로드 → 50%                                    │
│                                                                │
│ 장점: 데이터 양 정확히 반영                                    │
│ 단점: 압축 해제, 후처리 시간 미반영                            │
│                                                                │
│ [█████░░░░░] 50% (500MB/1GB read)                              │
│  ↑ 500MB 읽었지만 압축 해제에 3배 시간 걸리면?                 │
│    실제로는 25% 정도만 완료된 것!                              │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ 3. 가중치 기반 (Weighted)                                      │
├────────────────────────────────────────────────────────────────┤
│ 공식: progress = Σ(file[i].weight × file[i].progress)          │
│                  / Σ(file[i].weight)                           │
│                                                                │
│ 예: 텍스처(weight=3) 50% + 사운드(weight=1) 100%               │
│     → (3×0.5 + 1×1.0) / (3+1) = 62.5%                          │
│                                                                │
│ 장점: 실제 처리 시간 반영 가능                                 │
│ 단점: 가중치 수동 설정 필요, 환경마다 다름                     │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ 4. 단계 기반 (Phase-Based)                                     │
├────────────────────────────────────────────────────────────────┤
│ 공식: progress = phaseProgress × phaseWeight + completedPhases │
│                                                                │
│ 예: 초기화(20%) → 에셋(60%) → 후처리(20%)                      │
│     에셋 단계 50% 완료 → 20% + 60%×0.5 = 50%                   │
│                                                                │
│ 장점: 단계별 진행 상황 명확                                    │
│ 단점: 단계 내 불균형 여전히 존재                               │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│ 5. 시간 기반 추정 (Time-Estimated)                             │
├────────────────────────────────────────────────────────────────┤
│ 공식: progress = elapsed / estimatedTotal                      │
│       estimatedTotal = 과거 로딩 시간 평균                     │
│                                                                │
│ 예: 평소 로딩 15초, 현재 7.5초 경과 → 50%                      │
│                                                                │
│ 장점: 사용자 경험에 가장 가까움                                │
│ 단점: 첫 실행 시 데이터 없음, 환경 변화에 부정확               │
└────────────────────────────────────────────────────────────────┘
실제 게임에서는 어떤 방식을 주로 써?

대부분의 상용 게임은 하이브리드 방식을 사용합니다. 여러 측정 방식을 조합하고, 그 위에 보정 알고리즘을 적용합니다:

// 하이브리드 진행률 계산 시스템 class HybridProgressCalculator { private: // 다중 측정 소스 float m_byteProgress; // 바이트 기반 (0.0 ~ 1.0) float m_fileProgress; // 파일 개수 기반 float m_phaseProgress; // 단계 기반 float m_timeProgress; // 시간 추정 기반 // 가중치 (환경에 따라 조절) float m_byteWeight = 0.3f; float m_fileWeight = 0.1f; float m_phaseWeight = 0.4f; float m_timeWeight = 0.2f; // 보정용 히스토리 CircularBuffer<float, 60> m_progressHistory; float m_lastDisplayedProgress = 0.0f; public: float CalculateRawProgress() { // 가중 평균 계산 float raw = m_byteProgress * m_byteWeight + m_fileProgress * m_fileWeight + m_phaseProgress * m_phaseWeight + m_timeProgress * m_timeWeight; return Clamp(raw, 0.0f, 1.0f); } float CalculateDisplayProgress() { float raw = CalculateRawProgress(); // 히스토리에 추가 m_progressHistory.Push(raw); // 1. 절대 뒤로 가지 않음 float display = Max(raw, m_lastDisplayedProgress); // 2. 급격한 점프 방지 (최대 초당 15% 증가) float maxIncrease = 0.15f * deltaTime; display = Min(display, m_lastDisplayedProgress + maxIncrease); // 3. 시작 부스트 (처음에 빠르게 진행되는 느낌) if (display < 0.1f) { display = EaseOutQuad(display / 0.1f) * 0.1f; } // 4. 끝부분 브레이크 (99%에서 멈추는 것 방지) if (display > 0.9f && raw < 1.0f) { float slowdown = 1.0f - (display - 0.9f) * 5.0f; display = m_lastDisplayedProgress + maxIncrease * slowdown; } m_lastDisplayedProgress = display; return display; } };

Part 3. 심리적 진행률 설계

왜 "심리적" 진행률이 필요해? 그냥 정확한 수치를 보여주면 안 돼?

인간의 시간 인지는 비선형적입니다. 같은 10초도 상황에 따라 다르게 느껴집니다:

시간 인지와 진행률의 관계:

1. 기다림의 심리학
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  "불확실한 기다림은 확실한 기다림보다 더 길게 느껴진다"    │
│                                                            │
│  예: "곧 됩니다" vs "3분 남았습니다"                       │
│      → 3분이 더 빨리 느껴짐!                               │
│                                                            │
│  적용: 진행률 표시 = 확실성 제공 = 체감 시간 단축          │
│                                                            │
└────────────────────────────────────────────────────────────┘

2. 진행의 착시 (Progress Illusion)
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  "마지막 10%가 처음 10%보다 더 오래 걸린다고 느껴진다"     │
│                                                            │
│  0% → 10%: "오, 빠르네!"                                   │
│  90% → 100%: "왜 이렇게 안 끝나지..."                      │
│                                                            │
│  실제로 같은 시간이어도 심리적으로 다름                    │
│                                                            │
└────────────────────────────────────────────────────────────┘

3. 움직임의 중요성
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  "멈춰 있으면 고장났다고 생각한다"                         │
│                                                            │
│  ❌ [████████████░░░░░░] 60%  (3초간 정지)                 │
│     → "프리징됐나? 강제종료해야 하나?"                     │
│                                                            │
│  ✅ [████████████░░░░░░] 60%  (미세하게라도 움직임)        │
│     [████████████▒░░░░░] 60.1%                             │
│     → "아직 작동 중이구나"                                 │
│                                                            │
└────────────────────────────────────────────────────────────┘

4. 시작과 끝의 비대칭
┌────────────────────────────────────────────────────────────┐
│                                                            │
│  첫인상 효과: 처음이 빠르면 전체가 빠르게 느껴짐           │
│  피크-엔드 법칙: 마지막 경험이 전체 인상을 좌우            │
│                                                            │
│  최적 설계:                                                │
│  ┌──────────────────────────────────────────────────┐      │
│  │ 0%          25%         50%         75%    100% │      │
│  │ ███████████████████████████████████████████████ │      │
│  │ ↑           ↑                              ↑    │      │
│  │ 빠른 시작   안정적 중간                 부드러운│      │
│  │ (희망적)    (예측 가능)                  마무리 │      │
│  └──────────────────────────────────────────────────┘      │
│                                                            │
└────────────────────────────────────────────────────────────┘
그럼 구체적으로 어떤 보정을 적용해야 해?

Easing 함수를 사용하여 원시 진행률을 심리적으로 최적화된 진행률로 변환합니다:

// 심리적 진행률 보정 함수들 class ProgressEasing { public: // 1. 빠른 시작, 느린 마무리 (가장 일반적) static float EaseOutQuad(float t) { // t: 원시 진행률 (0.0 ~ 1.0) // 반환: 보정된 진행률 return t * (2.0f - t); } // 2. 더 극단적인 빠른 시작 static float EaseOutCubic(float t) { float t1 = t - 1.0f; return t1 * t1 * t1 + 1.0f; } // 3. 중간에 가속 (드라마틱한 느낌) static float EaseInOutQuad(float t) { if (t < 0.5f) { return 2.0f * t * t; } return 1.0f - pow(-2.0f * t + 2.0f, 2) / 2.0f; } // 4. 게임 로딩에 최적화된 커스텀 커브 static float GameLoadingCurve(float t) { // 0% ~ 20%: 매우 빠르게 (희망 제공) if (t < 0.2f) { return EaseOutCubic(t / 0.2f) * 0.35f; } // 20% ~ 80%: 일정한 속도 (예측 가능) if (t < 0.8f) { return 0.35f + (t - 0.2f) / 0.6f * 0.45f; } // 80% ~ 100%: 느리게 (완료 기대감 유지) return 0.8f + EaseOutQuad((t - 0.8f) / 0.2f) * 0.2f; } }; // 시각화: // // 보정된 │ ┌───────────────── // 진행률 │ ╱ // 100% │ ╱ // │ ╱ // 50% │ ╱ // │ ╱ // │ ╱ // 0% │╱__________________________ // 0% 50% 100% // 원시 진행률
Easing 함수별 진행 곡선 비교:

원시 진행률:    0%    25%    50%    75%   100%
                ├──────┼──────┼──────┼──────┤

선형 (Linear):
보정 진행률:    0%    25%    50%    75%   100%
                █████████████████████████████

EaseOutQuad (빠른 시작):
보정 진행률:    0%    44%    75%    94%   100%
                ████████████████████████░░░░░
                ↑ 초반에 빠름, 후반 느림

EaseInQuad (느린 시작):
보정 진행률:    0%    6%     25%    56%   100%
                ░░░░░████████████████████████
                ↑ 초반에 느림, 후반 빠름 (비추천!)

GameLoadingCurve (게임 최적화):
보정 진행률:    0%    35%    57%    80%   100%
                ████████████████████████▒▒▒▒▒
                ↑ 희망 → 안정 → 기대감

★ 대부분의 게임: EaseOutQuad 또는 커스텀 커브 사용

Part 4. 진행률 스무딩 알고리즘

진행률이 튀거나 멈추는 걸 방지하는 방법은?

스무딩(Smoothing)은 원시 진행률의 급격한 변화를 완화하여 부드러운 시각적 경험을 제공합니다:

// 진행률 스무딩 시스템 class ProgressSmoother { private: float m_displayProgress = 0.0f; float m_targetProgress = 0.0f; float m_velocity = 0.0f; // 스무딩 파라미터 float m_smoothTime = 0.3f; // 목표까지 도달 시간 float m_maxSpeed = 0.5f; // 초당 최대 변화량 float m_minVisibleChange = 0.001f; // 최소 표시 변화 // 정체 방지 float m_stallTimer = 0.0f; float m_stallThreshold = 2.0f; // 2초 이상 정체 시 float m_fakeProgressRate = 0.01f; // 가짜 진행 속도 public: void SetTarget(float target) { m_targetProgress = Clamp(target, 0.0f, 1.0f); } float Update(float deltaTime) { // SmoothDamp: 부드러운 감속 m_displayProgress = SmoothDamp( m_displayProgress, m_targetProgress, m_velocity, m_smoothTime, m_maxSpeed, deltaTime ); // 정체 감지 및 가짜 진행 if (Abs(m_velocity) < m_minVisibleChange) { m_stallTimer += deltaTime; if (m_stallTimer > m_stallThreshold) { // 가짜 진행 추가 (실제보다 살짝 앞서가기) float fakeProgress = m_fakeProgressRate * deltaTime; // 단, 실제 목표의 98%를 넘지 않음 float maxFake = m_targetProgress * 0.98f; m_displayProgress = Min( m_displayProgress + fakeProgress, maxFake ); } } else { m_stallTimer = 0.0f; } return m_displayProgress; } private: // Unity의 SmoothDamp와 동일한 알고리즘 static float SmoothDamp(float current, float target, float& velocity, float smoothTime, float maxSpeed, float deltaTime) { // Based on Game Programming Gems 4, Chapter 1.10 smoothTime = Max(0.0001f, smoothTime); float omega = 2.0f / smoothTime; float x = omega * deltaTime; float exp = 1.0f / (1.0f + x + 0.48f * x * x + 0.235f * x * x * x); float change = current - target; float maxChange = maxSpeed * smoothTime; change = Clamp(change, -maxChange, maxChange); float temp = (velocity + omega * change) * deltaTime; velocity = (velocity - omega * temp) * exp; float result = target + (change + temp) * exp; // 오버슈트 방지 if ((target - current > 0.0f) == (result > target)) { result = target; velocity = 0.0f; } return result; } };
스무딩 전후 비교:

원시 진행률 (실제 로딩 상태):

시간 →  0s    1s    2s    3s    4s    5s
        │     │     │     │     │     │
   100% │                         ████
    80% │                    █████
    60% │               █████
    40% │     ██████████
    20% │█████
     0% └─────────────────────────────→

        ↑ 급격한 점프와 정체 구간 존재

스무딩 적용 후 (화면에 표시):

시간 →  0s    1s    2s    3s    4s    5s
        │     │     │     │     │     │
   100% │                           ████
    80% │                       ████
    60% │                   ████
    40% │              █████
    20% │         █████
     0% └────█████────────────────────→

        ↑ 부드러운 곡선, 정체 없음

★ SmoothDamp의 특징:
   - 목표에 부드럽게 접근 (스프링처럼)
   - 오버슈트 없음 (목표를 넘어가지 않음)
   - 속도 연속성 (급격한 방향 전환 없음)
절대 뒤로 가면 안 되는 이유와 구현 방법은?

진행률이 뒤로 가면 "뭔가 잘못됐다"는 인상을 주기 때문에 절대 방지해야 합니다:

// 진행률 후진 방지 시스템 class MonotonicProgress { private: float m_highWaterMark = 0.0f; float m_displayProgress = 0.0f; float m_pendingDecrease = 0.0f; public: float Apply(float rawProgress) { if (rawProgress >= m_highWaterMark) { // 진행: 정상 업데이트 m_highWaterMark = rawProgress; m_displayProgress = rawProgress; m_pendingDecrease = 0.0f; } else { // 후진: 감소분 누적만 (표시는 유지) m_pendingDecrease += (m_displayProgress - rawProgress); // 누적된 감소분은 나중에 "느리게 진행"으로 표현 // 예: 실제로 50%→60% 갔을 때, 표시는 52%→60% } return m_displayProgress; } // 실제 진행 시 누적된 페널티 적용 float ApplyWithPenalty(float rawProgress) { if (rawProgress <= m_highWaterMark) { return Apply(rawProgress); } // 진행량의 일부로 페널티 상쇄 float increase = rawProgress - m_highWaterMark; float penaltyPayoff = Min(increase * 0.5f, m_pendingDecrease); m_pendingDecrease -= penaltyPayoff; m_highWaterMark = rawProgress; m_displayProgress = rawProgress - m_pendingDecrease; return m_displayProgress; } }; // 사용 예 MonotonicProgress progress; // 시나리오: 파일 개수로 진행률 계산 중 일부 파일 건너뛰기 progress.Apply(0.3f); // 표시: 30% progress.Apply(0.5f); // 표시: 50% progress.Apply(0.4f); // 실제 40%로 감소, 표시: 여전히 50%! progress.Apply(0.6f); // 표시: 60%

Part 5. 다단계 로딩 진행률

로딩에 여러 단계가 있을 때 진행률은 어떻게 관리해?

복잡한 로딩은 여러 단계(Phase)로 나뉘고, 각 단계마다 가중치를 부여합니다:

│                    전체 로딩 진행률                          │
│  [█████████████████████████████████████░░░░░░░░] 75%        │
└─────────────────────────────────────────────────────────────┘
                            ↑
                            │ 합산
        ┌───────────────────┼───────────────────┐
        │                   │                   │

┌───────────────┐   ┌───────────────┐   ┌───────────────┐

│ 가중치: 10%   │   │ 가중치: 70%   │   │ 가중치: 20%   │
│               │   │               │   │               │
│ [██████████]  │   │ [█████████░]  │   │ [░░░░░░░░░░]  │
│    100%       │   │    90%        │   │    0%         │
│               │   │               │   │               │

                            │

                            ▼

        │           Phase 2 세부                │
        ├───────────────────────────────────────┤
        │ 2-1. 텍스처 (40%): [██████████] 100%  │
        │ 2-2. 모델 (30%):   [████████░░] 80%   │
        │ 2-3. 사운드 (20%): [██████████] 100%  │
        │ 2-4. 스크립트(10%):[████░░░░░░] 40%   │
        │                                       │
        │ → Phase 2 진행률:                     │

★ 전체 = 10%×1.0 + 70%×0.88 + 20%×0.0 = 71.6% ≈ 72%
// 다단계 진행률 관리 시스템 class PhaseProgress { public: std::string name; float weight; float progress = 0.0f; bool completed = false; std::vector<PhaseProgress> subPhases; float GetProgress() const { if (subPhases.empty()) { return progress; } float totalWeight = 0.0f; float weightedProgress = 0.0f; for (const auto& sub : subPhases) { totalWeight += sub.weight; weightedProgress += sub.weight * sub.GetProgress(); } return totalWeight > 0.0f ? weightedProgress / totalWeight : 0.0f; } }; class MultiPhaseLoadingProgress { private: std::vector<PhaseProgress> m_phases; int m_currentPhaseIndex = 0; ProgressSmoother m_smoother; public: void Initialize() { m_phases = { { "Initialization", 0.10f, 0.0f, false, {} }, { "Asset Loading", 0.70f, 0.0f, false, { { "Textures", 0.40f }, { "Models", 0.30f }, { "Audio", 0.20f }, { "Scripts", 0.10f } }}, { "Post Processing", 0.20f, 0.0f, false, { { "Shader Compile", 0.50f }, { "Lightmap", 0.30f }, { "NavMesh", 0.20f } }} }; } void SetPhaseProgress(int phaseIndex, float progress) { if (phaseIndex < m_phases.size()) { m_phases[phaseIndex].progress = progress; if (progress >= 1.0f) { m_phases[phaseIndex].completed = true; } } } void SetSubPhaseProgress(int phaseIndex, int subIndex, float progress) { if (phaseIndex < m_phases.size() && subIndex < m_phases[phaseIndex].subPhases.size()) { m_phases[phaseIndex].subPhases[subIndex].progress = progress; } } float GetTotalProgress() { float totalWeight = 0.0f; float weightedProgress = 0.0f; for (const auto& phase : m_phases) { totalWeight += phase.weight; weightedProgress += phase.weight * phase.GetProgress(); } float rawProgress = totalWeight > 0.0f ? weightedProgress / totalWeight : 0.0f; // 스무딩 적용 m_smoother.SetTarget(rawProgress); return m_smoother.Update(deltaTime); } std::string GetCurrentStatus() { for (const auto& phase : m_phases) { if (!phase.completed) { if (!phase.subPhases.empty()) { for (const auto& sub : phase.subPhases) { if (!sub.completed) { return phase.name + ": " + sub.name; } } } return phase.name; } } return "Complete"; } };

Part 6. 에러 상황과 재시도 진행률

// 에러 내성 진행률 시스템 class ErrorResilientProgress { private: float m_progress = 0.0f; int m_retryCount = 0; int m_maxRetries = 3; std::string m_statusMessage; bool m_hasCriticalError = false; // 에러 발생 시 가짜 진행을 위한 float m_fakeProgressDuringRetry = 0.0f; public: struct LoadResult { float displayProgress; std::string status; bool showRetryUI; bool showErrorUI; }; LoadResult HandleError(ErrorType error, float currentProgress) { LoadResult result; switch (error) { case ErrorType::NetworkTimeout: case ErrorType::TemporaryFailure: if (m_retryCount < m_maxRetries) { m_retryCount++; // 재시도 중에도 미세하게 진행 m_fakeProgressDuringRetry += 0.001f; result.displayProgress = currentProgress + m_fakeProgressDuringRetry; result.status = Format("재시도 중... (%d/%d)", m_retryCount, m_maxRetries); result.showRetryUI = false; result.showErrorUI = false; } else { // 최대 재시도 초과 result.displayProgress = currentProgress; result.status = "연결에 실패했습니다"; result.showRetryUI = true; result.showErrorUI = false; } break; case ErrorType::OptionalAssetMissing: // 선택적 에셋은 무시하고 진행 LogWarning("Optional asset skipped"); result.displayProgress = currentProgress; // 유지 result.status = m_statusMessage; // 변경 없음 result.showRetryUI = false; result.showErrorUI = false; break; case ErrorType::CriticalAssetCorrupted: case ErrorType::DiskFull: m_hasCriticalError = true; result.displayProgress = currentProgress; result.status = GetErrorMessage(error); result.showRetryUI = false; result.showErrorUI = true; break; } return result; } void ResetRetryState() { m_retryCount = 0; m_fakeProgressDuringRetry = 0.0f; } };

// 상황별 로딩 표시 선택기 enum class LoadingDisplayType { ProgressBar, // 진행률 바 Spinner, // 스피너 StatusText, // 상태 텍스트 IndeterminateBar, // 불확정 진행 바 SkeletonScreen, // 스켈레톤 TipsScreen // 팁 화면 }; class LoadingDisplaySelector { public: static LoadingDisplayType SelectBest(const LoadingContext& ctx) { // 예상 로딩 시간 기반 결정 float estimatedTime = ctx.estimatedDuration; bool canMeasureProgress = ctx.hasProgressCallback; bool isUILoading = ctx.loadingType == LoadType::UI; // 결정 트리 if (estimatedTime < 0.5f) { // 0.5초 미만: 표시 없음 또는 최소 스피너 return LoadingDisplayType::Spinner; } if (estimatedTime < 2.0f) { // 2초 미만: 스피너로 충분 return LoadingDisplayType::Spinner; } if (isUILoading) { // UI 로딩: 스켈레톤이 자연스러움 return LoadingDisplayType::SkeletonScreen; } if (!canMeasureProgress) { // 진행률 측정 불가: 불확정 바 + 상태 텍스트 return LoadingDisplayType::IndeterminateBar; } if (estimatedTime > 10.0f) { // 10초 이상: 진행률 바 + 팁 return LoadingDisplayType::TipsScreen; } // 기본: 진행률 바 return LoadingDisplayType::ProgressBar; } };

Part 8. 게임 엔진별 구현

Unity와 Unreal에서 진행률 바는 어떻게 구현해?

각 엔진은 비동기 로딩 시스템과 연동되는 진행률 API를 제공합니다:

// ═══════════════════════════════════════════════════════════ // Unity - AsyncOperation과 Slider UI 연동 // ═══════════════════════════════════════════════════════════ using UnityEngine; using UnityEngine.UI; using UnityEngine.SceneManagement; using System.Collections; public class LoadingScreen : MonoBehaviour { [SerializeField] private Slider progressBar; [SerializeField] private Text statusText; [SerializeField] private Text percentText; [SerializeField] private float smoothSpeed = 0.5f; private float displayProgress = 0f; public IEnumerator LoadSceneAsync(string sceneName) { // 씬 비동기 로딩 시작 AsyncOperation operation = SceneManager.LoadSceneAsync(sceneName); // 자동 활성화 방지 (90%에서 멈춤) operation.allowSceneActivation = false; while (!operation.isDone) { // Unity의 progress는 0~0.9 범위 (allowSceneActivation=false일 때) // 0.9를 100%로 변환 float rawProgress = Mathf.Clamp01(operation.progress / 0.9f); // 심리적 보정 (빠른 시작) float easedProgress = EaseOutQuad(rawProgress); // 스무딩 (절대 후진 X) float targetProgress = Mathf.Max(displayProgress, easedProgress); displayProgress = Mathf.MoveTowards( displayProgress, targetProgress, smoothSpeed * Time.deltaTime ); // UI 업데이트 progressBar.value = displayProgress; percentText.text = Mathf.RoundToInt(displayProgress * 100) + "%"; // 로딩 완료 시 if (operation.progress >= 0.9f && displayProgress >= 0.99f) { statusText.text = "완료!"; // 잠시 대기 후 씬 활성화 yield return new WaitForSeconds(0.3f); operation.allowSceneActivation = true; } yield return null; } } private float EaseOutQuad(float t) { return t * (2f - t); } }

} // 사용 예: Level Streaming과 연동 void AMyGameMode::LoadLevelWithProgress(const FString& LevelName) { // 로딩 화면 표시 LoadingWidget = CreateWidget<ULoadingScreenWidget>(GetWorld()); LoadingWidget->AddToViewport(100); Part 9. 진행률 시스템 최적화

진행률 업데이트 자체가 성능에 영향을 줄 수 있어?

네, 잘못 구현하면 로딩을 느리게 만들 수 있습니다:

진행률 업데이트의 성능 이슈:

1. 너무 빈번한 UI 업데이트
┌────────────────────────────────────────────────────────────┐
│ 문제:                                                      │
│   - 파일 하나 읽을 때마다 UI 갱신                          │
│   - 1000개 파일 = 1000번 UI 드로우콜                       │
│                                                            │
│ ❌ BAD:                                                    │
│   for (file in files) {                                    │
│       Load(file);                                          │
│       UpdateUI();  // 매번 UI 갱신                         │
│   }                                                        │
│                                                            │
│ ✅ GOOD:                                                   │
│   for (file in files) {                                    │
│       Load(file);                                          │
│       if (time > lastUpdate + 0.033f) {  // 30FPS 제한     │
│           UpdateUI();                                      │
│           lastUpdate = time;                               │
│       }                                                    │
│   }                                                        │
└────────────────────────────────────────────────────────────┘

2. 메인 스레드 블로킹
┌────────────────────────────────────────────────────────────┐
│ 문제:                                                      │
│   - 로딩 스레드가 진행률 업데이트를 위해 락 대기           │
│   - UI 스레드가 진행률 조회를 위해 락 대기                 │
│                                                            │
│ 해결: Lock-Free 진행률 공유                                │
│                                                            │
│   std::atomic progress;  // 원자적 읽기/쓰기        │
│                                                            │
│   // 로딩 스레드                                           │
│   progress.store(newValue, std::memory_order_relaxed);     │
│                                                            │
│   // UI 스레드                                             │
│   float p = progress.load(std::memory_order_relaxed);      │
└────────────────────────────────────────────────────────────┘

3. 문자열 포맷팅 비용
┌────────────────────────────────────────────────────────────┐
│ 문제:                                                      │
│   - sprintf("Loading: %s (%.1f%%)", name, progress)        │
│   - 매 프레임 문자열 생성 = 힙 할당 = GC 부담              │
│                                                            │
│ 해결: 필요할 때만 포맷팅                                   │
│                                                            │
│   static int lastPercent = -1;                             │
│   int currentPercent = (int)(progress * 100);              │
│   if (currentPercent != lastPercent) {                     │
│       UpdateText(Format("%d%%", currentPercent));          │
│       lastPercent = currentPercent;                        │
│   }                                                        │
└────────────────────────────────────────────────────────────┘
// 최적화된 진행률 시스템 class OptimizedProgressSystem { private: // Lock-free 진행률 공유 std::atomic<float> m_rawProgress{0.0f}; std::atomic<int> m_currentPhase{0}; // UI 업데이트 제한 float m_lastUIUpdate = 0.0f; float m_uiUpdateInterval = 0.033f; // 30 FPS // 캐시된 텍스트 int m_cachedPercent = -1; std::string m_cachedText; // 상태 메시지 (변경 시에만 업데이트) std::atomic<int> m_statusVersion{0}; int m_lastStatusVersion = -1; std::string m_statusMessages[10]; // 미리 할당 public: // 로딩 스레드에서 호출 (락 프리) void ReportProgress(float progress, int phase) { m_rawProgress.store(progress, std::memory_order_relaxed); m_currentPhase.store(phase, std::memory_order_relaxed); } // UI 스레드에서 호출 bool ShouldUpdateUI(float currentTime) { if (currentTime - m_lastUIUpdate < m_uiUpdateInterval) { return false; } m_lastUIUpdate = currentTime; return true; } float GetDisplayProgress() { return m_rawProgress.load(std::memory_order_relaxed); } // 텍스트는 정수가 바뀔 때만 갱신 const std::string& GetProgressText() { int percent = static_cast<int>( GetDisplayProgress() * 100.0f ); if (percent != m_cachedPercent) { m_cachedPercent = percent; // 미리 할당된 버퍼 사용 char buffer[8]; snprintf(buffer, sizeof(buffer), "%d%%", percent); m_cachedText = buffer; } return m_cachedText; } // 상태 메시지도 버전 체크로 최적화 bool HasStatusChanged() { int current = m_statusVersion.load(std::memory_order_acquire); if (current != m_lastStatusVersion) { m_lastStatusVersion = current; return true; } return false; } }; // 사용 예: 게임 루프에서 void GameLoop() { OptimizedProgressSystem progress; // 렌더 루프 while (loading) { float time = GetTime(); // UI 업데이트 필요한지 체크 (30 FPS) if (progress.ShouldUpdateUI(time)) { // 진행률 바 업데이트 progressBar.SetValue(progress.GetDisplayProgress()); // 텍스트는 변경 시에만 percentText.SetText(progress.GetProgressText()); // 상태 메시지도 변경 시에만 if (progress.HasStatusChanged()) { statusText.SetText(progress.GetStatusMessage()); } } Render(); } }

핵심 정리: 프로그레스 바의 거짓말

  • 정직한 진행률은 UX를 해친다 - 불균일한 실제 진행률은 불안감을 유발
  • 측정 방식: 파일 개수, 바이트, 가중치, 단계, 시간 추정 (하이브리드 권장)
  • 심리적 보정: EaseOutQuad로 빠른 시작 + 느린 마무리, 움직임 유지
  • 스무딩 필수: SmoothDamp로 부드러운 진행, 절대 후진 금지
  • 에러 처리: 재시도 중에도 진행률 유지, 가짜 진행으로 희망 제공
  • 성능 최적화: Lock-free 공유, UI 업데이트 제한 (30 FPS), 텍스트 캐싱
