구글은 왜 멀쩡한 C++ 두고 Go를 새로 만들었을까

거대 빌드 지옥과 멀티코어 시대 — Go의 탄생 배경, 형태, C++/C# 대비 차이, 그리고 왜 AI 친화적인가

Part 1. 구글은 왜 또 새 언어를 만들었어?

2009년이면 C++도 Java도 다 있었잖아. 구글이 굳이 Go를 새로 만든 이유가 뭐야?

맞춰봐. 세계 최고 엔지니어들이 모인 구글이 새 언어를 만들 만큼 절박했던 고통이 뭐였을까? 화려한 신기능? 아니야 — 빌드가 너무 느려서였어.

구글 내부는 수천만 줄짜리 C++ 코드베이스 위에 돌아가는데, 코드 한 줄 고치고 빌드 걸면 수십 분에서 한 시간씩 기다렸어. 고치고→확인하는 사이클이 이렇게 길면 개발이 사실상 멈춰. 거기에 2000년대 후반은 멀티코어 시대로 막 넘어가던 때라, 서버가 코어 수십 개를 써먹어야 하는데 C++으로 동시성 짜는 건 지옥이었지.

그래서 '빠른 빌드 + 쉬운 동시성 + 단순함' 이 셋을 동시에 노리고 태어난 게 Go야. 만든 사람들도 거물이야 — 켄 톰슨(C 언어·유닉스의 아버지), 롭 파이크.

빌드가 느린 건 컴파일러 성능 문제 아냐? 언어를 새로 만든다고 빨라져?

거기에 핵심이 있어. 빌드 속도는 컴파일러가 아니라 언어 설계가 결정해.

C++은 파일마다 헤더(.h)를 매번 다시 읽어. A가 B를 쓰고 B가 C를 쓰면, C의 헤더를 수백 번 중복으로 재파싱해. 템플릿은 또 펼칠 때마다 코드를 복제하고. 구조적으로 느릴 수밖에 없어.

Go는 아예 헤더를 없앴어. 의존성 정보를 컴파일된 결과에 박아두고, '안 쓰는 import는 컴파일 에러'로 막아서 불필요한 의존성을 원천 차단해. 그래서 같은 규모를 초~수 초 단위로 빌드해. 언어 문법 자체가 '빠른 빌드'를 목표로 깎인 거야.

⏱ 코드 한 줄 고치고 → 결과 보기까지 C++ : 수정 ──▶ [헤더 수백 번 재파싱 + 템플릿 전개] ──▶ 수십 분 ⏳ └─ 개발자는 그동안 멍때림 / 집중 끊김 Go : 수정 ──▶ [헤더 없음 · 의존성 단순] ──▶ 수 초 ⚡ └─ 고치고 바로 확인 = 사이클이 살아있음 💡 Go는 '기능'이 아니라 '개발 사이클 속도'를 위해 태어났다

Part 2. 그래서 Go는 어떤 형태를 골랐어?

한마디로 Go는 어떻게 생긴 언어야?

다섯 개 기둥으로 외우면 돼.

① 작은 언어 — 키워드가 25개뿐(C++은 90개+). 문법이 작아서 하루면 훑어.

② GC 내장 — C++처럼 메모리 직접 해제 안 해. 널 크래시·누수가 구조적으로 줄어.

③ 빠른 컴파일 — Part 1에서 본 그거.

④ 단일 정적 바이너리 — 빌드하면 exe 파일 딱 하나. 필요한 게 전부 그 안에 들어있어서, 서버에 복사만 하면 돌아가.

⑤ 내장 동시성 — 고루틴(다음 Part).

기능이 적은 게 자랑이야? 그거 그냥 빈약한 언어 아냐?

그게 의도된 설계라는 게 포인트야. Go 철학은 '한 가지 일을 하는 방법은 한 가지'. C++은 같은 걸 다섯 가지 방법으로 짤 수 있어서 강력하지만, 남이 짠 코드 읽기가 어렵잖아. Go는 gofmt라는 공식 포맷터가 들여쓰기·괄호까지 강제해서, 전 세계 Go 코드가 거의 똑같이 생겼어.

여기서 트레이드오프를 정직하게 보자. 비교 대상은 C++/C#의 풍부한 기능(상속·연산자 오버로딩·매크로). 나은 점은 새 사람이 1주일이면 적응하고 코드 리뷰가 빨라져. 잃는 것은 표현력 — 영리한 추상화를 못 짜서 똑같은 코드를 반복(boilerplate)하는 경우가 늘어. '단순함'을 위해 '간결함'을 일부 포기한 거야.

비유 C++ Go
조립 난이도 풀옵션 변신로봇 — 강력하지만 설명서가 두꺼움 레고 기본블록 — 단순해서 누구나 빨리 조립
같은 기능 짜는 법 여러 갈래 (자유롭지만 제각각) 대체로 한 갈래 (지루하지만 통일)
남의 코드 읽기 스타일 편차 큼 gofmt로 거의 동일

Part 3. 고루틴 — 동접 10만에 스레드 10만 개가 필요할까?

동시성 하면 스레드잖아. 무겁고. Go는 뭐가 달라?

흔히 '동시 작업 = 스레드 = 무겁다'로 알지? 그래서 맞춰봐 — 동접 10만 명을 처리하려면 스레드가 10만 개 필요할까?

OS 스레드는 하나당 스택이 약 1MB야. 10만 개면 100GB — 머신이 즉사해. 그래서 옛날엔 스레드 풀로 수백 개만 돌려 돌려막기 했지.

Go는 발상을 바꿨어. 고루틴(goroutine)은 OS 스레드가 아니야. Go 런타임이 스레드 몇 개(코어 수만큼) 위에 고루틴 수만~수백만 개를 얹어서 돌려 — 이걸 M:N 스케줄링이라고 해. 고루틴 하나는 2KB로 시작해. 직접 켜보자.

동시 연결 수를 골라봐 · 스레드 1MB/개 vs 고루틴 2KB/개 · 예시값

고루틴 수만 개가 돌면 데이터는 어떻게 주고받아? 락 걸어?

여기에 Go의 또 다른 철학이 있어 — '메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유해라.'

락을 직접 거는 대신 채널(channel)로 값을 주고받아. 고루틴 A가 채널에 값을 넣으면 B가 꺼내 쓰는, 컨베이어 벨트 같은 구조야. 락을 손으로 만질 일이 줄어서 동시성 버그가 잘 안 나(이걸 CSP 모델이라고 해).

근데 트레이드오프가 있어. 채널이 만능은 아니야 — 잘못 쓰면 서로 기다리다 멈추는 데드락이 나. Go가 race detector(경쟁 상태 탐지기)를 기본 제공하지만, 그게 동시성 버그를 0으로 만들어주진 않아. 쉬워진 거지 사라진 게 아니야.

Part 4. C++·C#이랑 진짜 뭐가 달라?

항목 C++ C# Go
메모리 수동 (new/delete) GC GC (저지연)
컴파일 느림 중간 (IL→JIT) 매우 빠름
배포 형태 네이티브 exe + 의존 DLL .NET 런타임 필요(AOT 가능) 단일 정적 바이너리
동시성 스레드 직접 (어려움) async/await + Task 고루틴 + 채널
에러 처리 예외 + 에러코드 예외(try/catch) 에러를 값으로 (if err != nil)
언어 크기 거대 (키워드 90+) 큼 작음 (키워드 25)
C#도 GC 있고 동시성 좋잖아. Go랑 결정적으로 뭐가 달라?

둘 다 GC·동시성은 OK야. 차이는 세 군데에서 나.

① 배포: Go는 빌드하면 런타임이 필요 없는 단일 네이티브 바이너리 — 서버에 파일 하나 복사하면 끝. C#은 전통적으로 .NET 런타임이 깔려 있어야 했어(요샌 AOT로 따라잡는 중).

② 크기 철학: Go는 일부러 작게, C#은 기능을 계속 늘리는 방향.

③ 에러 처리: C#은 예외를 던지면 어디서 잡힐지 코드만 봐선 몰라(숨은 흐름). Go는 함수가 에러를 값으로 대놓고 리턴해서 `if err != nil`로 그 자리에서 처리해 — 장황하지만 실패 경로가 코드에 다 드러나. 이 '드러남'이 다음 Part(AI 친화성)의 복선이야.

Part 5. 그래서 왜 Go가 'AI 친화적'이야?

지난번에 Go가 AI 자율 개발에 좋다고 했잖아. 왜?

지난 글에서 세운 기준 기억해? 'AI한테 좋은 언어 = 검증기 품질 × 루프 속도'. AI는 짠 코드가 맞는지 매번 신호를 받아야 하는데, 그 신호가 빠르고 믿을 만할수록 재귀로 굴리기 좋아. Go는 이걸 거의 다 만족해:

• 작은 언어 표면적 → AI가 헛디딜 경우의 수가 적어서 없는 API를 지어내는 환각이 줄어

• 빠른 컴파일 → 고치고 1초 안에 '맞음/틀림' 신호. 1층 검증기(컴파일러)가 빠르게 돌아

• 단일 바이너리 → '내 환경에선 됐는데'가 구조적으로 없음 = 재현성. 자율 루프의 생명이야

• gofmt → AI 출력이 항상 같은 모양으로 정규화돼서 diff가 깨끗하고 리뷰가 쉬워

• 내장 test + race detector → 검증기가 언어에 기본 포함

• 명시적 에러(if err != nil) → 실패 경로가 코드에 드러나서 AI가 결정론적으로 추적

🤖 AI 자율 개발 루프 — Go가 잘 맞는 이유 [AI가 코드 수정] ──▶ [go build] ─⚡빠름──▶ 컴파일 에러? ──▶ AI 자가수정 │ 통과 (1층: 싸고 빠름) ▼ [go test -race] ──▶ 실패? ──▶ AI 자가수정 │ 통과 (2층: 비싸지만 신뢰) ▼ [단일 바이너리] ──▶ 어디서 돌려도 동일 (재현성) 💡 1층이 빠르고 2층이 믿을 만하면 = AI가 '빨리·확실히' 틀림 = 루프가 싸진다
그럼 AI가 Go로 짜면 무조건 잘 돌아간단 거야?

아니, 거기서 선을 그어야 해. Go가 작아서 '틀린 코드'는 빨리 걸러져. 근데 '맞지만 멍청한 코드'(반복 떡칠, 비효율 구조)는 여전히 통과해버려. 컴파일과 테스트는 '돌아가는가'를 보장하지 '잘 설계됐는가'를 보장하진 않거든.

그러니까 정확히 말하면 — Go는 AI의 검증 루프를 싸고 빠르게 만들어줘서 좋은 거지, AI의 설계 안목을 대신해주는 건 아니야. 검증기의 천장은 어디까지나 '돌아감'이고, 그 위 '좋은 코드'는 다른 문제야.

Part 6. 그럼 다 Go로 짜면 돼?

이쯤 되면 Go가 만능 같은데, 단점은 없어?

분명히 있어. raw 성능은 C++엔 못 미쳐 — GC가 돌고 저수준 메모리 제어가 약해서, 매 틱 CPU를 갈아넣는 게임 전투 루프 같은 덴 C++이 유리해. 표현력이 낮아 복잡한 도메인 모델은 답답하고, 제네릭이 2022년(1.18)에야 들어와서 그 부분 생태계는 아직 무르익는 중이야. GUI·게임 클라이언트·머신러닝 생태계도 빈약해.

Go가 진짜 빛나는 곳은 네트워크 서버·CLI 도구·인프라·마이크로서비스야. 네가 매일 쓰는 도커·쿠버네티스·테라폼이 전부 Go로 짜였어 — '많은 머신에서 안정적으로 도는 단순한 서버'가 Go의 홈그라운드인 거지.

핵심 정리

  • Go는 신기능이 아니라 '느린 빌드 + 어려운 동시성 + C++ 복잡함'이라는 구글의 고통에서 태어났다 (2009)
  • 다섯 기둥: 작은 언어 / GC / 빠른 컴파일 / 단일 정적 바이너리 / 내장 동시성(고루틴)
  • 고루틴은 OS 스레드가 아니라 2KB짜리 경량 작업 — M:N 스케줄링으로 수십만~수백만 동시 처리, 채널로 통신
  • C# 대비 차이: 단일 바이너리 배포 · 의도적으로 작은 언어 · 에러를 값으로 명시 처리
  • AI 친화적인 이유 = 작은 표면적(환각↓) + 빠른 컴파일(1층 검증 빠름) + 단일 바이너리(재현성) + gofmt + 내장 테스트
  • 단, raw 성능·표현력은 C++만 못함 — 네트워크 서버·인프라·마이크로서비스가 Go의 홈그라운드

🤔 생각해볼 것 (정답 없음)

우리 게임의 보조 서버(랭킹·매칭·정산)를 새로 짠다면 — C++ IOCP를 또 쓸까, Go로 단일 바이너리 마이크로서비스를 띄울까?

Go의 'gofmt 강제'가 AI 출력 정규화에 도움이 된다면, 우리 C++ 코드에도 clang-format을 강제하면 AI 루프가 더 깨끗해질까?

검증기가 빠르고 재현 가능한 게 핵심이라면 — 언어를 바꾸지 않고 C++ 빌드/테스트를 컨테이너로 hermetic하게 만드는 길은 없을까?
