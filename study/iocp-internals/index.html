IOCP 내부 동작 원리

소수의 스레드로 수만 연결을 처리하는 Windows의 비동기 I/O 엔진

IOCP는 무슨 뜻일까?

I/O Completion Port = I/O 완료 항구

항구(Port)에 배(I/O 작업)가 도착하면:

• 항구가 "이 배 도착했다!" 알림을 보내고

• 대기 중이던 일꾼(스레드)이 화물(데이터)을 처리하고

• 일꾼은 다시 항구로 돌아가서 다음 배를 기다린다

핵심: 배마다 전담 일꾼을 두지 않는다. 소수의 일꾼이 돌아가며 처리한다.

Part 1. 접속자 1000명이면 스레드 1000개?

가장 단순한 서버 구조는 뭐야?

"유저 1명당 스레드 1개" — Thread-per-Connection 모델.

접속하면 스레드 만들고, 그 스레드가 그 유저만 담당하는 구조.

유저 A 접속 → 스레드 1 생성 → recv() 대기 (블로킹) 유저 B 접속 → 스레드 2 생성 → recv() 대기 (블로킹) 유저 C 접속 → 스레드 3 생성 → recv() 대기 (블로킹) ... 유저 1000 접속 → 스레드 1000 생성 → recv() 대기 (블로킹)
왜 이게 문제야?

스레드 1개 = 스택 메모리 1MB. 1000개면 1GB가 스택만으로 소모.

CPU 코어는 8개인데 스레드 1000개를 돌려막기하면 전환 비용만 쌓임.

대부분의 스레드는 유저가 패킷 보낼 때까지 recv()에서 잠자고 있음.

문제 설명
메모리 낭비 1000 스레드 × 1MB = 1GB (스택만)
컨텍스트 스위칭 코어 8개에 스레드 1000개 → 전환 비용 폭발
대부분 놀고 있음 실제 일하는 건 8개뿐, 992개는 잠자는 중

Part 2. IOCP의 핵심 아이디어

스레드 1000개가 비효율이면 어떻게 해?

"스레드를 유저 수만큼 만들지 말고, CPU 코어 수만큼만 만들자."

"I/O가 끝나면 OS가 알려줄 테니, 그때 아무 스레드나 처리하면 된다."

[Thread-per-Connection] 유저 1000명 → 스레드 1000개 각 스레드가 자기 유저만 기다림 대부분 recv()에서 잠자는 중 [IOCP] 유저 1000명 → 스레드 16개 (코어×2) I/O 완료되면 OS가 통보 놀고 있는 스레드가 바로 처리
비유로 설명해줘

Thread-per-Connection = 1:1 전담 웨이터

테이블 100개 → 웨이터 100명. 95명은 멍하니 서 있음.

IOCP = 호출벨 시스템

테이블 100개 → 웨이터 8명 + 호출벨. 벨 누르면 놀고 있는 웨이터가 감.

Part 3. 내부 구조: 3개의 리스트

IOCP 내부는 어떻게 생겼어?

3개의 리스트를 관리해. 이 구조만 알면 IOCP의 모든 동작이 이해돼.

┌──────────────────────────────────────────────┐ │ Completion Port (OS 내부) │ │ │ │ ┌──────────────────────┐ │ │ │ 1. Device List │ ← 감시할 소켓 목록 │ │ │ [소켓A, 소켓B, ...] │ │ │ └──────────┬───────────┘ │ │ │ I/O 완료되면 │ │ ▼ │ │ ┌──────────────────────┐ │ │ │ 2. I/O 완료 큐 │ ← FIFO 큐 │ │ │ [완료1, 완료2, ...] │ (완료된 작업) │ │ └──────────┬───────────┘ │ │ │ 꺼내감 │ │ ▼ │ │ ┌──────────────────────┐ │ │ │ 3. 대기 스레드 큐 │ ← LIFO 스택 │ │ │ [스레드C, 스레드B] │ (쉬는 중) │ │ └──────────────────────┘ │ └──────────────────────────────────────────────┘
리스트 역할 자료구조
Device List "이 소켓들을 감시해줘" 연결 리스트
I/O 완료 큐 "이 작업 처리해줘" FIFO 큐
대기 스레드 큐 "일 생기면 깨워줘" LIFO 스택
대기 스레드 큐는 왜 LIFO(스택)야?

캐시 효율! 가장 최근에 쉬기 시작한 스레드를 먼저 깨움.

방금까지 일하던 스레드는 CPU 캐시에 데이터가 아직 남아 있어서 더 빠름.

Part 4. 패킷이 처리되기까지

유저가 "공격" 패킷을 보내면 내부에서 뭐가 일어나?
Step 1: 서버가 WSARecv()로 "데이터 오면 알려줘" 요청 (비동기) → 스레드는 블로킹 안 됨. 바로 다른 일 하러 감. Step 2: 유저가 패킷 전송 → OS가 데이터 수신 완료 → I/O 완료 큐에 "유저 A의 recv 완료" 항목 추가 Step 3: 대기 스레드 큐에서 스레드 하나 깨움 → GetQueuedCompletionStatus()가 리턴됨 Step 4: 깨어난 스레드가 패킷 파싱 → 게임 로직 실행 → 처리 끝나면 다시 대기 큐로 돌아감
시간 흐름 → 유저A: ──[패킷 전송]──────────────────────── │ OS: │ 데이터 수신 완료 ▼ 완료 큐: ── [A:recv 완료] ───────────────── │ 대기 큐: ── [스레드3, 스레드2] ──────────── │ 스레드3 깨움 ▼ 스레드3: ────── [패킷 처리] → 다시 대기 큐로

Part 5. 핵심 API 3개

코드로는 어떻게 써?

딱 3개 함수만 알면 됨.

// 1) CreateIoCompletionPort - 생성 & 등록 // IOCP 생성 HANDLE hIOCP = CreateIoCompletionPort( INVALID_HANDLE_VALUE, NULL, 0, 0 // 동시 실행 스레드 수 (0 = CPU 코어 수) ); // 소켓을 IOCP에 등록 CreateIoCompletionPort( (HANDLE)clientSocket, // 감시할 소켓 hIOCP, // 어떤 IOCP에 (ULONG_PTR)pClient, // 식별 데이터 0 );
// 2) GetQueuedCompletionStatus - 완료 대기 // 워커 스레드에서 호출 (이 줄에서 대기) GetQueuedCompletionStatus( hIOCP, // 어떤 IOCP에서 기다릴지 &bytesTransferred, // 전송된 바이트 수 &completionKey, // 등록 시 넣었던 식별 데이터 &pOverlapped, // 어떤 I/O 작업이 완료됐는지 INFINITE // 무한 대기 ); // 여기 도달 = I/O 완료! 처리 시작
// 3) WSARecv / WSASend - 비동기 I/O 요청 WSARecv(clientSocket, &wsaBuf, 1, &recvBytes, &flags, &overlapped, NULL); // 여기서 블로킹 안 함! 바로 다음 줄 실행 // 데이터 오면 IOCP 완료 큐에 통보됨

전체 흐름:

1. CreateIoCompletionPort로 IOCP 만들고 소켓 등록

2. WSARecv로 "데이터 오면 알려줘" 비동기 요청

3. 워커 스레드들이 GetQueuedCompletionStatus에서 대기

4. 데이터 도착 → OS가 완료 큐에 넣음 → 스레드 깨어남 → 처리

Part 6. 스레드 몇 개가 적당해?

워커 스레드를 몇 개 만들어야 해?

Microsoft 공식 권장: CPU 코어 수 × 2

CPU 코어 8개인 서버 → 워커 스레드 16개 IOCP 동시 실행 제한 = 8개 (코어 수만큼) [스레드 상태] Running (실행 중): 최대 8개 Waiting (대기 중): 완료 큐가 비면 잠듦 Paused (일시정지): Sleep/Lock/DB호출로 멈춤 → 이때 IOCP가 Waiting 스레드를 깨워서 투입!
왜 코어 × 2야? 딱 코어 수만큼이면 안 돼?

스레드가 DB 호출 등으로 블로킹되면 코어가 놀게 됨.

× 2를 해두면 절반이 Paused 되어도 나머지 절반이 코어를 채울 수 있음.

너무 많이(100개) 만들면 → 컨텍스트 스위칭 비용 증가. IOCP 효과 반감.

IOCP가 자동으로 조절한다고?

Running 스레드 수를 OS가 자동 관리:

• Running < 코어 수 → 대기 스레드 깨움

• Running ≥ 코어 수 → 더 이상 안 깨움

→ 컨텍스트 스위칭을 최소화!

Part 7. 다른 I/O 모델과 비교

모델 방식 성능 플랫폼
select 소켓 목록 순회 최대 64개 (Win) 모든 OS
epoll 이벤트 기반 알림 수만~수십만 Linux
IOCP 비동기 완료 통보 + 스레드 풀 수만~수십만 Windows
io_uring 커널 공유 링버퍼 수십만+ Linux 5.1+
IOCP와 epoll의 결정적 차이는?

epoll: "데이터 준비됐어" → 사용자가 recv()로 복사해야 함

IOCP: "데이터 복사까지 다 끝났어" → 바로 처리하면 됨

epoll은 준비 알림(Readiness), IOCP는 완료 알림(Completion).

IOCP가 한 단계 더 OS에 맡기는 셈.

핵심 정리

  • IOCP = I/O 완료 통보 + 스레드 풀 자동 관리 메커니즘
  • 내부 구조 = Device List + I/O 완료 큐(FIFO) + 대기 스레드 큐(LIFO)
  • 핵심 API = CreateIoCompletionPort, GetQueuedCompletionStatus, WSARecv
  • 스레드 수 = 코어 × 2. OS가 동시 실행 수를 자동 조절
  • 한 줄 요약 = 소수 스레드가 수만 연결을 효율적으로 처리하는 Windows I/O 엔진
