IOCP 비동기 I/O 스레드 풀 Completion Port 게임 서버

1. 출발점: 접속자 1000명이면 스레드 1000개?

가장 직관적인 서버 설계는 "유저 1명당 스레드 1개"입니다. 접속하면 스레드 만들고, 그 스레드가 그 유저만 담당하는 거죠.

[Thread-per-Connection 모델] 유저 A 접속 → 스레드 1 생성 → recv() 대기 (블로킹) 유저 B 접속 → 스레드 2 생성 → recv() 대기 (블로킹) 유저 C 접속 → 스레드 3 생성 → recv() 대기 (블로킹) ... 유저 1000 접속 → 스레드 1000 생성 → recv() 대기 (블로킹)

왜 이게 문제인가?

문제 설명
메모리 낭비 스레드 1개 = 스택 메모리 1MB. 1000개면 1GB가 스택만으로 소모
컨텍스트 스위칭 CPU 코어는 8개인데 스레드 1000개를 돌려막기하면 전환 비용만 쌓임
대부분 놀고 있음 유저가 패킷을 보내지 않는 동안 스레드는 recv()에서 잠자고 있음

핵심 문제

CPU 코어 8개인 서버에서 스레드 1000개를 돌리면, 실제 일하는 건 8개뿐이고 나머지 992개는 잠자면서 메모리만 차지합니다. 스레드 간 전환 비용까지 합치면 성능이 급락합니다.

2. IOCP의 핵심 아이디어

IOCP(I/O Completion Port)는 Windows가 제공하는 가장 효율적인 비동기 I/O 메커니즘입니다. 핵심 아이디어는 단순합니다:

IOCP의 발상

"스레드를 유저 수만큼 만들지 말고, CPU 코어 수만큼만 만들자."
"I/O가 끝나면 OS가 알려줄 테니, 그때 아무 스레드나 처리하면 된다."

Thread-per-Connection

유저 1000명 → 스레드 1000개

각 스레드가 자기 유저의 데이터만 기다림

대부분 recv()에서 잠자는 중

IOCP

유저 1000명 → 스레드 16개 (코어×2)

I/O 완료되면 OS가 통보

놀고 있는 스레드가 바로 처리

비유로 이해하기
[Thread-per-Connection = 1:1 전담 웨이터] 테이블 100개 → 웨이터 100명 웨이터 1: "3번 테이블 손님이 주문할 때까지 옆에서 서 있음..." 웨이터 2: "7번 테이블 손님이 주문할 때까지 옆에서 서 있음..." → 웨이터 95명이 멍하니 서 있음 [IOCP = 호출벨 시스템] 테이블 100개 → 웨이터 8명 + 호출벨 손님이 벨 누르면 → 놀고 있는 웨이터가 가서 처리 → 웨이터 8명이 100개 테이블을 효율적으로 커버

3. IOCP 내부 구조: 3개의 리스트

IOCP는 내부에 3개의 중요한 리스트를 관리합니다. 이 구조를 알면 IOCP의 모든 동작이 이해됩니다.

┌──────────────────────────────────────────────────┐ │ Completion Port (OS 내부) │ │ │ │ ┌──────────────────────┐ │ │ │ 1. Device List │ ← 감시할 소켓 목록 │ │ │ [소켓A, 소켓B, ...] │ │ │ └──────────┬───────────┘ │ │ │ I/O 완료되면 │ │ ▼ │ │ ┌──────────────────────┐ │ │ │ 2. I/O 완료 큐 │ ← FIFO 큐 │ │ │ [완료1, 완료2, ...] │ (완료된 작업 대기열) │ │ └──────────┬───────────┘ │ │ │ 꺼내감 │ │ ▼ │ │ ┌──────────────────────┐ │ │ │ 3. 대기 스레드 큐 │ ← LIFO 스택 │ │ │ [스레드C, 스레드B] │ (일 없어서 쉬는 중) │ │ └──────────────────────┘ │ └──────────────────────────────────────────────────┘

각 리스트의 역할

리스트 역할 자료구조
Device List IOCP에 등록된 소켓(핸들) 목록. "이 소켓들을 감시해줘" 연결 리스트
I/O 완료 큐 I/O가 끝난 작업이 쌓이는 곳. "이 작업 처리해줘" FIFO 큐
대기 스레드 큐 할 일 없어서 쉬는 스레드 목록. "일 생기면 깨워줘" LIFO 스택

왜 대기 스레드 큐는 LIFO(스택)인가?

가장 최근에 쉬기 시작한 스레드를 먼저 깨웁니다. 이유: 캐시 효율. 방금까지 일하던 스레드는 CPU 캐시에 관련 데이터가 아직 남아 있어서, 오래 쉰 스레드보다 더 빠르게 작업할 수 있습니다.

4. 동작 흐름: 패킷 하나가 처리되기까지

유저 A가 "공격" 패킷을 보냈을 때 IOCP 내부에서 벌어지는 일:

Step 1: 비동기 I/O 요청

서버가 WSARecv()로 "유저 A 소켓에서 데이터 오면 알려줘"라고 OS에 요청합니다.

이 시점에서 스레드는 블로킹되지 않습니다. 바로 다른 일을 하러 갑니다.

Step 2: OS가 I/O 완료

유저 A가 패킷을 보내면, OS(네트워크 드라이버)가 데이터를 받아서 버퍼에 복사합니다.

복사가 끝나면 I/O 완료 큐에 "유저 A의 recv가 완료됨"이라는 항목을 넣습니다.

Step 3: 스레드 깨우기

대기 스레드 큐에서 쉬고 있던 스레드 하나를 깨웁니다.

GetQueuedCompletionStatus()가 리턴되면서 "유저 A 데이터 왔어"를 알려줍니다.

Step 4: 처리

깨어난 스레드가 유저 A의 "공격" 패킷을 파싱하고 게임 로직을 실행합니다.

처리 끝나면 다시 GetQueuedCompletionStatus()를 호출해서 대기 스레드 큐로 돌아갑니다.

시간 흐름 → 유저A: ──────[패킷 전송]────────────────────────── │ OS: │ 데이터 수신 완료 ▼ 완료 큐: ── [A:recv 완료] ────────────────────── │ 대기 큐: ── [스레드3, 스레드2] ────────────────── │ 스레드3 깨움 ▼ 스레드3: ─────────── [패킷 처리] → 다시 대기 큐로

5. 핵심 API 3개

IOCP를 쓰려면 딱 3개 함수만 알면 됩니다.

1) CreateIoCompletionPort - 생성 & 등록

// 1단계: IOCP 생성
HANDLE hIOCP = CreateIoCompletionPort(
    INVALID_HANDLE_VALUE,  // 소켓 없이 빈 IOCP 생성
    NULL,
    0,
    0                      // 동시 실행 스레드 수 (0 = CPU 코어 수)
);

// 2단계: 소켓을 IOCP에 등록
CreateIoCompletionPort(
    (HANDLE)clientSocket,  // 감시할 소켓
    hIOCP,                 // 어떤 IOCP에 등록할지
    (ULONG_PTR)pClient,   // 이 소켓의 식별 데이터 (CompletionKey)
    0
);

2) GetQueuedCompletionStatus - 완료 대기

// 워커 스레드에서 호출 (이 줄에서 대기)
BOOL result = GetQueuedCompletionStatus(
    hIOCP,                 // 어떤 IOCP에서 기다릴지
    &bytesTransferred,     // 전송된 바이트 수
    &completionKey,        // 등록 시 넣었던 식별 데이터
    &pOverlapped,          // 어떤 I/O 작업이 완료됐는지
    INFINITE               // 무한 대기
);

// 여기 도달 = I/O가 완료됨!
// completionKey로 어떤 클라이언트인지 식별
// pOverlapped로 어떤 작업(recv/send)인지 식별

3) WSARecv / WSASend - 비동기 I/O 요청

// "이 소켓에서 데이터가 오면 알려줘" (비동기)
WSARecv(
    clientSocket,          // 어떤 소켓
    &wsaBuf,               // 데이터를 담을 버퍼
    1,
    &recvBytes,
    &flags,
    &overlapped,           // 이 구조체로 완료 통보 받음
    NULL
);
// 여기서 블로킹 안 함! 바로 다음 줄 실행

전체 흐름 요약

  1. CreateIoCompletionPort로 IOCP 만들고 소켓 등록
  2. WSARecv로 "데이터 오면 알려줘" 요청 (비동기)
  3. 워커 스레드들은 GetQueuedCompletionStatus에서 대기
  4. 데이터 도착 → OS가 완료 큐에 넣음 → 스레드 하나 깨어남 → 처리

6. 스레드는 몇 개가 적당할까?

Microsoft 공식 권장: CPU 코어 수 × 2

CPU 코어 8개인 서버 → 워커 스레드 16개 생성 → IOCP의 동시 실행 제한 = 8개 (코어 수) [상태 분류] Running (실행 중): 최대 8개 (코어 수만큼) Waiting (대기 중): 완료 큐가 비면 GetQueuedCompletionStatus에서 잠듦 Paused (일시정지): Running 스레드가 Sleep/Lock 등으로 멈추면 대기 스레드 투입

왜 코어 × 2인가?

스레드 수 상황
코어 수와 같게 (8개) 스레드가 DB 호출 등으로 블로킹되면 코어가 놀게 됨
코어 × 2 (16개) 일부가 블로킹되어도 예비 스레드가 코어를 활용. 최적
너무 많이 (100개) 컨텍스트 스위칭 비용 증가. IOCP 효과 반감

IOCP의 자동 조절

IOCP는 동시에 실행되는 스레드 수를 자동으로 조절합니다.
Running 스레드가 코어 수보다 적으면 → 대기 스레드를 깨움
Running 스레드가 코어 수 이상이면 → 더 이상 안 깨움
이렇게 해서 컨텍스트 스위칭을 최소화합니다.

7. 스레드 상태 전이

IOCP 워커 스레드는 3가지 상태를 순환합니다.

┌─────────────┐ ┌──────│ Waiting │◄──── GetQueuedCompletionStatus() 호출 │ │ (잠자는 중) │ │ └──────┬──────┘ │ │ I/O 완료 → 깨어남 │ ▼ │ ┌─────────────┐ │ │ Running │◄──── 패킷 처리 중 │ │ (일하는 중) │ │ └──┬─────┬────┘ │ │ │ │ │ │ Sleep/Lock/DB호출 등 │ │ ▼ │ │ ┌─────────────┐ │ │ │ Paused │ ← 이때 IOCP가 다른 Waiting │ │ │ (멈춰있는 중) │ 스레드를 깨워서 투입! │ │ └──────┬──────┘ │ │ │ 블로킹 해제 │ │ │ └─────────┴─────────┘ 처리 완료 → 다시 대기
Paused 상태가 중요한 이유

게임 서버에서 DB 쿼리를 동기적으로 호출하면, 그 스레드는 응답이 올 때까지 Paused 상태가 됩니다.

IOCP는 이걸 감지하고, Waiting 큐에서 다른 스레드를 깨워서 Running 스레드 수를 코어 수만큼 유지합니다.

그래서 "코어 × 2" 스레드를 만드는 겁니다. 절반이 Paused 되어도 나머지 절반이 코어를 채울 수 있으니까요.

8. 게임 서버에서의 IOCP 구조

실제 게임 서버에서 IOCP가 어떤 구조로 쓰이는지 봅시다.

┌─────────────────────────────────────────────────┐ │ 게임 서버 │ │ │ │ Accept 스레드 (1개) │ │ └→ 새 클라이언트 접속 → IOCP에 소켓 등록 │ │ │ │ IOCP 워커 스레드 (코어×2개) │ │ └→ GetQueuedCompletionStatus()로 대기 │ │ └→ 패킷 수신 완료 → 패킷 파싱 → 게임 로직 실행 │ │ └→ WSARecv() 다시 걸어서 다음 패킷 대기 │ │ │ │ 게임 로직 스레드 (선택적) │ │ └→ 타이머, 몬스터 AI, 월드 업데이트 등 │ │ │ │ DB 스레드 (별도) │ │ └→ DB 쿼리 처리 (IOCP 스레드 블로킹 방지) │ └─────────────────────────────────────────────────┘

패킷 처리 흐름

// 워커 스레드 함수 (코어×2개가 이 함수를 실행)
unsigned __stdcall WorkerThread(void* pArg) {
    while (true) {
        // 1. I/O 완료 대기 (여기서 잠듦)
        GetQueuedCompletionStatus(
            hIOCP, &bytes, &key, &overlapped, INFINITE
        );

        // 2. 여기 도달 = 패킷이 왔다!
        CClient* pClient = (CClient*)key;

        if (bytes == 0) {
            // 연결 종료
            DisconnectClient(pClient);
            continue;
        }

        // 3. 패킷 처리
        ProcessPacket(pClient, pClient->recvBuf, bytes);

        // 4. 다시 수신 대기 걸기
        WSARecv(pClient->socket, ...);
    }
}

핵심 패턴

대기 → 깨어남 → 처리 → 다시 수신 요청 → 대기
이 루프를 소수의 스레드가 수천 명의 유저를 돌아가며 처리합니다.

9. 다른 I/O 모델과 비교

모델 방식 스레드 수 성능 플랫폼
select 소켓 목록 순회하며 확인 1개 최대 64개 (Windows) 모든 OS
epoll 이벤트 기반 알림 소수 수만~수십만 Linux
IOCP 비동기 완료 통보 + 스레드 풀 코어×2 수만~수십만 Windows
io_uring 커널 공유 링버퍼 소수 수십만+ Linux 5.1+

IOCP vs epoll 결정적 차이

  • epoll: "데이터 준비됐어" → 사용자가 recv()로 복사해야 함
  • IOCP: "데이터 복사까지 다 끝났어" → 바로 처리하면 됨

epoll은 준비 알림(Readiness), IOCP는 완료 알림(Completion).
IOCP가 한 단계 더 OS에 맡기는 셈입니다.

10. 정리

개념 설명
Completion Port OS가 관리하는 I/O 완료 통보 + 스레드 풀 메커니즘
Device List 감시 대상 소켓(핸들) 목록
I/O 완료 큐 완료된 I/O 작업이 쌓이는 FIFO 큐
대기 스레드 큐 일 없이 쉬는 스레드의 LIFO 스택 (캐시 최적화)
스레드 수 코어 × 2가 일반적. OS가 동시 실행 수를 자동 조절
핵심 장점 소수 스레드로 수만 연결 처리. 컨텍스트 스위칭 최소화

한 줄 정리

IOCP는 "I/O 끝나면 OS가 알려줄 테니 스레드는 놀고 있어"라는 철학으로, 소수의 스레드가 수만 연결을 효율적으로 처리하게 해주는 Windows의 핵심 비동기 I/O 메커니즘입니다.
