Blue-Green Deployment

게임 서버 배포할 때 유저가 눈치 못 채게 하는 법

1. 왜 배포가 문제야?

게임 서버 업데이트할 때 유저한테 미리 공지하잖아?

맞아! 보통 이런 공지가 올라가지:

[점검 안내] 일시: 2025-02-03 02:00 ~ 06:00 (4시간) 내용: 서버 업데이트 및 버그 수정 점검 중에는 게임 접속이 불가능합니다. 불편을 드려 죄송합니다.

이게 전통적인 방식이야.

4시간이나? 요즘도 그래?

요즘 게임들은 24시간 서비스가 기본이야:

글로벌 게임 현실: - 한국 새벽 2시 = 미국 낮 12시 - 점검 시간 = 어딘가는 피크타임 - 4시간 점검 = 매출 손실 경쟁사: - "우리 게임은 점검 없이 업데이트합니다!" - 유저: "왜 이 게임은 아직도 점검해?"

무중단 배포가 경쟁력이 된 거야.

2. Blue-Green이 뭐야?

이름부터 이상해. 파란색? 초록색?

두 개의 환경을 운영하는 거야:

Blue-Green 구조: [로드밸런서] | -----+----- | | [Blue] [Green] (현재) (대기) v1.0 v1.0 유저 트래픽 -> Blue로 연결

항상 두 개가 준비되어 있어.

그럼 배포는 어떻게 해?

스위칭이야:

Step 1: 현재 상태 [로드밸런서] -----> [Blue v1.0] (유저 접속 중) [Green v1.0] (대기) Step 2: Green에 새 버전 배포 [로드밸런서] -----> [Blue v1.0] (유저 접속 중) [Green v2.0] (배포 완료, 대기) Step 3: 스위치! [로드밸런서] -----> [Green v2.0] (유저 접속!) [Blue v1.0] (대기) 걸린 시간: 1초 미만!

로드밸런서만 바꾸면 끝이야.

유저 입장에서는?
비유: 공항 활주로

- 활주로 A: 비행기 이착륙 중
- 활주로 B: 정비 완료, 대기

관제탑: "지금부터 활주로 B 사용!"
비행기들: (자연스럽게 B로 이동)

승객은 활주로가 바뀐 걸 모름!

3. 게임 서버에서는 어떻게 해?

웹 서버랑 게임 서버가 다르지 않아?

맞아, 게임은 더 복잡해!

구분 웹 서버 게임 서버
상태 Stateless (없음) Stateful (있음)
세션 짧음 (수초) 길음 (수시간)
연결 HTTP (요청-응답) TCP/UDP (지속 연결)
끊김 시 새로고침 전투 중 사망?
게임은 연결이 끊기면 안 되잖아!

그래서 전략이 필요해:

게임 서버 Blue-Green 전략: 1. 신규 유저 트래픽 전환 - Green: 신규 접속자만 받음 - Blue: 기존 유저 유지 2. 자연 종료 대기 - 전투 완료 -> Green으로 재접속 - 던전 클리어 -> Green으로 재접속 3. 강제 전환 (최후의 수단) - "서버 이동 중..." 메시지 - 세션 저장 -> 마이그레이션
세션은 어떻게 저장해?

Redis 같은 외부 저장소 사용:

// 세션 저장 (Blue에서) void OnUserSwitch(Player* player) { // Redis에 세션 저장 SessionData data = { .playerId = player->GetId(), .position = player->GetPosition(), .inventory = player->GetInventory(), .questProgress = player->GetQuestData() }; redis.Set(player->GetId(), data, TTL_5MIN); // 클라이언트에게 재접속 요청 SendPacket(player, SM_RECONNECT_TO_NEW_SERVER); } // 세션 복구 (Green에서) void OnUserReconnect(int playerId) { SessionData data = redis.Get(playerId); Player* player = CreatePlayer(playerId); player->SetPosition(data.position); player->SetInventory(data.inventory); // ... // 유저: "어? 끊김 없이 됐네?" }

4. 로드밸런서는 어떻게 바꿔?

스위치를 누르면 바뀌는 거야?

DNS 기반 또는 L4/L7 스위칭이 있어:

방법 1: DNS 변경 game.example.com -> 10.0.1.100 (Blue) | v game.example.com -> 10.0.2.100 (Green) 단점: DNS 캐시 때문에 전파 시간 걸림 (최대 TTL) 방법 2: L4/L7 로드밸런서 (권장) [AWS ALB / NLB] Target Group Blue: 가중치 100% Target Group Green: 가중치 0% | v (스위칭) Target Group Blue: 가중치 0% Target Group Green: 가중치 100% 장점: 즉시 전환 (1초 이내)
AWS에서는 어떻게 하는데?

실제 명령어:

# 현재 상태 확인 aws elbv2 describe-target-groups \ --names "game-server-blue" "game-server-green" # Green으로 트래픽 전환 aws elbv2 modify-listener \ --listener-arn $LISTENER_ARN \ --default-actions '[{ "Type": "forward", "ForwardConfig": { "TargetGroups": [ {"TargetGroupArn": "'$GREEN_TG_ARN'", "Weight": 100}, {"TargetGroupArn": "'$BLUE_TG_ARN'", "Weight": 0} ] } }]' # 또는 Terraform으로 resource "aws_lb_listener_rule" "game" { action { type = "forward" target_group_arn = var.active_color == "green" ? aws_lb_target_group.green.arn : aws_lb_target_group.blue.arn } }

5. 배포했는데 버그가 있으면?

Green에 버그가 있으면 어떡해?

즉시 롤백! 이게 Blue-Green의 최대 장점이야:

버그 발견! | v [Green v2.0] 에서 에러 발생! | v 스위치 되돌리기 (1초) | v [Blue v1.0] 로 복구 롤백 시간: 1초!

Blue가 그대로 있으니까 바로 돌아갈 수 있어.

DB 스키마가 바뀌었으면?

이게 어려운 부분이야!

상황: v1.0: user 테이블에 name 컬럼 v2.0: user 테이블에 first_name, last_name 컬럼 (분리) 문제: - Green v2.0 배포 시 DB 스키마 변경 - 롤백하면? Blue v1.0이 새 스키마 못 읽음! 해결: 하위 호환 마이그레이션 1. v1.5: name, first_name, last_name 모두 존재 2. v1.5 배포 -> 안정화 3. v2.0: first_name, last_name만 사용 4. v2.0 배포 -> 안정화 5. v2.5: name 컬럼 삭제

점진적 마이그레이션이 필요해.

6. 실제로 어떻게 구현해?

자동화할 수 있어?

CI/CD 파이프라인으로:

# deploy.sh #!/bin/bash # 1. 현재 활성 환경 확인 CURRENT=$(get_active_environment) # blue or green NEXT=$([ "$CURRENT" = "blue" ] && echo "green" || echo "blue") echo "Current: $CURRENT, Deploying to: $NEXT" # 2. 새 버전을 대기 환경에 배포 deploy_to_environment $NEXT $VERSION # 3. 헬스체크 대기 wait_for_health_check $NEXT 300 # 5분 대기 if [ $? -ne 0 ]; then echo "Health check failed! Aborting." exit 1 fi # 4. 트래픽 전환 switch_traffic $NEXT # 5. 검증 sleep 60 # 1분 모니터링 if check_error_rate > 0.01; then echo "Error rate too high! Rolling back." switch_traffic $CURRENT alert_team "Rollback executed!" exit 1 fi echo "Deployment successful!"
게임 서버용 헬스체크는?

게임 전용 헬스체크:

// 헬스체크 엔드포인트 app.get('/health', async (req, res) => { const checks = { // 1. 기본 체크 server: true, // 2. DB 연결 database: await db.ping(), // 3. Redis 연결 redis: await redis.ping(), // 4. 게임 로직 체크 gameLoop: gameServer.isRunning(), // 5. 월드 로딩 완료 worldLoaded: worldManager.isReady(), // 6. 접속자 수용 가능 capacity: currentPlayers < maxPlayers * 0.9 }; const healthy = Object.values(checks).every(v => v); res.status(healthy ? 200 : 503).json({ status: healthy ? 'healthy' : 'unhealthy', checks, version: process.env.VERSION }); });

문제 해결책
진행 중인 전투 전투 종료 후 마이그레이션
또는 전투 상태 직렬화
파티/길드 파티 전체 같은 서버로 이동
월드 보스 월드 보스 전투 중 배포 금지
스케줄 연동

클라이언트 버전 구버전 클라이언트 호환 또는
강제 업데이트
비용은 2배 드는 거 아니야?

맞아, 2배 인프라가 필요해. 하지만:

비용 계산: 전통적 방식: - 서버 10대: 월 $10,000 - 점검 시간: 월 8시간 (주 2회) - 점검 중 매출 손실: 월 $50,000 Blue-Green 방식: - 서버 20대: 월 $20,000 - 점검 시간: 0시간 - 매출 손실: $0 결론: - 추가 비용: +$10,000 - 절약 매출: $50,000 - 순이익: +$40,000/월

대규모 서비스일수록 이득!

핵심 정리: Blue-Green Deployment

  • 개념 - 두 개의 동일한 환경(Blue/Green)을 운영
  • 배포 - 대기 환경에 배포 후 로드밸런서 스위칭
  • 롤백 - 문제 시 즉시 이전 환경으로 전환 (1초)
  • 게임 특화 - 세션 마이그레이션, 전투 상태 저장 필요
  • DB 주의 - 하위 호환 마이그레이션으로 점진적 변경
  • 비용 - 인프라 2배지만, 무중단으로 매출 손실 방지

관련 배포 전략

전략 특징 적합한 경우
Blue-Green 전체 전환 빠른 롤백 필요
Canary 일부만 새 버전 점진적 검증 필요
Rolling 순차적 교체 리소스 제한적
