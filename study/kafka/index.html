초당 100만 메시지를 어떻게 처리해?

Kafka로 대용량 로그와 이벤트 스트림 처리하기

Part 1. Kafka가 뭐야?

RabbitMQ 같은 메시지 큐 아니야?

비슷하지만 목적이 달라.

[일반 메시지 큐 vs Kafka] [RabbitMQ 등] - 목적: 서버 간 메시지 전달 - 메시지 처리하면 삭제됨 - 실시간 작업 분배 [Kafka] - 목적: 대용량 이벤트 스트림 저장 + 전달 - 메시지 처리해도 삭제 안 됨 (디스크에 보관) - 로그처럼 계속 쌓임
메시지를 안 지운다고?

응. Kafka는 "분산 로그 시스템"이야.

메시지를 디스크에 순서대로 쭉 쌓아두고, 여러 Consumer가 각자 원하는 위치부터 읽어감.

Part 2. 어떻게 초당 100만이 가능해?

디스크에 저장하면 느린 거 아니야?

Kafka는 디스크를 순차적으로만 쓰기 때문에 빨라.

[Kafka가 빠른 이유] 1️⃣ 순차 쓰기 (Sequential Write) - 랜덤 쓰기: 100 MB/s - 순차 쓰기: 600 MB/s (SSD), 100+ MB/s (HDD) - Kafka는 로그 끝에만 추가 → 순차 쓰기만 함! 2️⃣ Zero-Copy - 일반: 디스크 → 커널 → 앱 → 커널 → 네트워크 - Kafka: 디스크 → 커널 → 네트워크 (앱 거치지 않음) 3️⃣ 배치 처리 - 메시지 1개씩 안 보냄 - 모아서 한 번에 압축해서 전송 4️⃣ 파티셔닝 - 토픽을 여러 파티션으로 분할 - 파티션마다 다른 서버 → 병렬 처리
그래서 진짜 100만 되는 거야?

LinkedIn에서 하루 7조 메시지 처리 사례 있어.

초당 100만은 클러스터 적당히 구성하면 충분히 가능.

Part 3. Topic과 Partition

Topic이 뭐야?

메시지의 카테고리야. 폴더 같은 거.

[Topic 예시] Topic: "game-logs" ← 게임 로그용 Topic: "user-events" ← 유저 이벤트용 Topic: "payment-events" ← 결제 이벤트용 각 Topic은 독립적으로 관리됨
Partition은?

Topic을 쪼갠 것. 병렬 처리의 핵심이야.

[Partition 구조] Topic: "game-logs" (Partition 3개) Partition 0: [로그1] [로그4] [로그7] ... → Broker 1 Partition 1: [로그2] [로그5] [로그8] ... → Broker 2 Partition 2: [로그3] [로그6] [로그9] ... → Broker 3 - 각 Partition은 다른 서버(Broker)에 저장 가능 - Consumer도 Partition별로 붙어서 병렬 처리 - Partition 수 = 최대 병렬 처리 수
Partition 수는 어떻게 정해?

처리량에 따라. Consumer 수 = Partition 수로 맞추는 게 좋아.

Consumer 10개면 Partition도 10개.

Part 4. Consumer Group

Consumer가 여러 개면 같은 메시지 중복으로 받는 거 아냐?

Consumer Group으로 해결해.

[Consumer Group] Topic: "game-logs" (Partition 3개) ┌─ Consumer Group A (로그 저장팀) ─────────────────┐ │ Consumer A1 ← Partition 0 │ │ Consumer A2 ← Partition 1 │ │ Consumer A3 ← Partition 2 │ └─────────────────────────────────────────────────┘ 각 Partition은 Group 내 1명만 읽음! ┌─ Consumer Group B (분석팀) ──────────────────────┐ │ Consumer B1 ← Partition 0, 1, 2 (혼자 다 읽음) │ └─────────────────────────────────────────────────┘ 다른 Group은 같은 메시지 또 읽을 수 있음!
아, 같은 Group 안에서는 분담하고, 다른 Group은 각자 받는구나

정확해!

• 로그 저장팀: 로그를 DB에 저장

• 분석팀: 같은 로그로 통계 집계

같은 데이터를 다른 용도로 동시에 활용!

Part 5. Offset - 어디까지 읽었지?

Consumer가 죽었다 살아나면 어디서부터 읽어?

Offset이 위치를 기억해.

[Offset 개념] Partition 0: [msg0] [msg1] [msg2] [msg3] [msg4] [msg5] ↑ Offset = 3 (Consumer가 여기까지 읽음) Consumer가 죽었다 살아나면: → "Offset 3까지 읽었네, 4부터 이어서 읽자" Offset은 Kafka가 자동 관리 (또는 직접 관리 가능)
다시 처음부터 읽고 싶으면?

Offset을 0으로 리셋하면 돼. 데이터가 디스크에 남아있으니까.

이게 Kafka의 장점! "시간여행"이 가능해.

Part 6. 게임 서버에서 어떻게 써?

[게임 서버 Kafka 활용] 1️⃣ 로그 수집 파이프라인 게임 서버들 → Kafka "game-logs" → Elasticsearch → S3 백업 → 실시간 대시보드 2️⃣ 이벤트 기반 처리 "아이템 획득" 이벤트 → Kafka → 업적 서버 (업적 체크) → 통계 서버 (드롭률 집계) → 로그 서버 (기록) 3️⃣ 서버 간 상태 동기화 월드 서버 A → Kafka "world-sync" → 월드 서버 B, C, D (이벤트 순서 보장됨) 4️⃣ 결제/재화 로그 (감사용) 모든 재화 변동 → Kafka → 영구 보관 (나중에 버그 발생하면 Replay 가능)

Part 7. 언제 Kafka, 언제 RabbitMQ?

Kafka RabbitMQ
목적 대용량 스트림, 로그 작업 분배, 실시간
처리량 초당 수백만 초당 수만
메시지 보관 디스크 (며칠~영구) 처리 후 삭제
순서 보장 Partition 내 보장 단일 큐 내 보장
복잡도 높음 (클러스터 운영) 낮음

Kafka 선택: 로그 수집, 이벤트 소싱, 대용량 처리

RabbitMQ 선택: 결제 처리, 메일 발송, 간단한 작업 큐

핵심 정리

  • Kafka = 분산 로그 시스템. 메시지를 디스크에 보관
  • 순차 쓰기 + Zero-Copy + 배치로 초당 100만+ 처리
  • Topic = 카테고리, Partition = 병렬 처리 단위
  • Consumer Group = 같은 그룹은 분담, 다른 그룹은 각자
  • Offset = 어디까지 읽었는지 위치. 리셋하면 재처리 가능
  • 게임 서버 = 로그 수집, 이벤트 스트림, 감사 로그에 적합
