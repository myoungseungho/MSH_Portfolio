통계가 오래되면 옵티마이저가 잘못된 선택을 한다

Statistics Update - 쿼리 옵티마이저의 "눈"을 최신으로 유지하기

Part 1. 통계(Statistics)가 뭐야?

SQL Server에서 "통계"가 뭐야?

테이블 데이터의 분포 정보야.

옵티마이저가 실행 계획을 세울 때 참고해.

[통계가 담고 있는 정보] 테이블: TCharacter (10만 행) level 컬럼 통계: ├── 최소값: 1 ├── 최대값: 300 ├── 분포: │ ├── level 1~50: 5만 명 (50%) │ ├── level 51~100: 3만 명 (30%) │ ├── level 101~200: 1.5만 명 (15%) │ └── level 201~300: 5천 명 (5%) └── 히스토그램 (더 상세한 분포)
그걸 왜 알아야 해?

옵티마이저가 "어떤 방법으로 데이터를 찾을지" 결정하거든.

Part 2. 통계가 옵티마이저에 미치는 영향

통계 보고 뭘 결정해?

대표적으로 Index Seek vs Table Scan 결정.

SELECT * FROM TCharacter WHERE level > 250
[옵티마이저의 판단] 통계에 따르면 level > 250인 행 = 약 2% (2천 행) 2% = 적은 양 → Index Seek가 유리 → 인덱스로 빠르게 2천 행만 찾기 만약 level > 10이면? = 약 95% (9.5만 행) 95% = 거의 전부 → Table Scan이 유리 → 그냥 전체 읽는 게 빠름

옵티마이저가 참조하는 것:

• 행 수 추정: 조건에 맞는 행이 몇 개일지

• 선택도(Selectivity): 조건이 얼마나 좁히는지

Part 3. 통계가 오래되면?

통계가 옛날 거면 뭐가 문제야?

옵티마이저가 잘못된 판단을 해.

[실제 사례] 6개월 전 통계: └── level > 250인 유저: 2천 명 (2%) 현재 실제 데이터: └── level > 250인 유저: 5만 명 (50%) ← 이벤트로 급증! 옵티마이저 판단: "2% = Index Seek" 실제로는: "50% = Table Scan이 나았는데..." 결과: Index Seek로 5만 행을 하나씩 찾음 → 매우 느림!

반대 경우도 있어:

• 데이터가 줄었는데 통계는 "많다"고 함 → 불필요한 Table Scan

상황 통계 실제 결과
데이터 급증 2% 50% 느린 Index Seek
데이터 급감 50% 2% 불필요한 Table Scan
정확한 통계 2% 2% 최적의 계획

Part 4. 통계 자동 업데이트

SQL Server가 자동으로 업데이트 안 해?

해. 근데 조건이 있어.

[AUTO_UPDATE_STATISTICS 트리거 조건] SQL Server 2016 이전: └── 테이블의 20% + 500행 변경 시 SQL Server 2016+: └── 동적 임계값 (큰 테이블은 더 작은 비율로) 예: 100만 행 테이블 ├── 2016 이전: 20만 행 변경 후 업데이트 └── 2016+: 수만 행 변경 후 업데이트 (동적)
20%면 너무 늦지 않아?

맞아. 큰 테이블에서 20%면 수십만 행이야.

그 사이에 잘못된 플랜으로 쿼리가 실행될 수 있어.

-- 자동 업데이트 설정 확인 SELECT name, is_auto_update_stats_on FROM sys.databases WHERE name = DB_NAME()

Part 5. 수동 업데이트

직접 업데이트하려면?

UPDATE STATISTICS 명령을 사용해.

-- 특정 테이블 통계 업데이트 UPDATE STATISTICS TCharacter -- 특정 인덱스 통계만 업데이트 UPDATE STATISTICS TCharacter IX_TCharacter_Level -- 전체 샘플링 (정확하지만 느림) UPDATE STATISTICS TCharacter WITH FULLSCAN -- 50% 샘플링 (균형) UPDATE STATISTICS TCharacter WITH SAMPLE 50 PERCENT

언제 수동 업데이트?

• 대량 INSERT/DELETE 후

• 이벤트로 데이터 분포 급변 시

• 갑자기 쿼리가 느려졌을 때

-- 통계 마지막 업데이트 시간 확인 SELECT t.name AS table_name, s.name AS stat_name, STATS_DATE(t.object_id, s.stats_id) AS last_updated FROM sys.tables t INNER JOIN sys.stats s ON t.object_id = s.object_id WHERE t.name = 'TCharacter' ORDER BY last_updated

Part 6. 게임 서버에서 적용

우리 게임에서 언제 업데이트하면 좋아?

다음 상황에서 고려해:

상황 통계 업데이트 타이밍
일일 리셋 후 권장 새벽 점검 시
대규모 이벤트 시작 권장 이벤트 시작 전/후
휴면 계정 삭제 후 필수 삭제 직후
서버 오픈 직후 권장 유저 유입 안정화 후
-- 점검 시 실행할 스크립트 EXEC sp_updatestats -- 모든 테이블 통계 업데이트 -- 또는 주요 테이블만 UPDATE STATISTICS TCharacter WITH SAMPLE 30 PERCENT UPDATE STATISTICS TInventory WITH SAMPLE 30 PERCENT UPDATE STATISTICS TQuest WITH SAMPLE 30 PERCENT

핵심 정리

  • 통계(Statistics) = 테이블 데이터 분포 정보
  • 옵티마이저가 실행 계획 세울 때 통계 참조
  • 오래된 통계 = 잘못된 계획 = 느린 쿼리
  • 자동 업데이트: 20% + 500행 변경 시 (느릴 수 있음)
  • 수동 업데이트: UPDATE STATISTICS, sp_updatestats
  • 권장 타이밍: 점검 시, 대량 변경 후, 이벤트 전후
