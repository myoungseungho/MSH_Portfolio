수만 개의 기계가 어떻게 60 FPS로 돌아갈까?

Factorio의 대규모 시뮬레이션 최적화 - 공장 자동화의 비밀

Part 1. Factorio는 왜 최적화가 어려워?

Factorio가 어떤 게임이야?

공장 자동화 게임이야.

광물 캐고 → 제련하고 → 조립하고 → 연구하고...

컨베이어 벨트, 로봇, 기계가 수만 개 돌아가.

수만 개면 얼마나 많은 거야?

대형 공장 기준:

• 컨베이어 벨트 아이템: 10만+ 개

• 조립 기계: 5,000+ 개

• 삽입기(Inserter): 10,000+ 개


이걸 매 프레임(60 FPS) 업데이트해야 해.

매 프레임 10만 개를 계산한다고?

60 FPS면 1프레임 = 16.6ms.

16ms 안에 10만 개 엔티티를 업데이트해야 해.


엔티티 하나당 0.00016ms밖에 못 써.

대충 계산해도 불가능해 보이지?

🏭 비유: 거대한 공장 관리

• 공장에 기계가 10만 대 있어
• 관리자가 1초에 60번씩 모든 기계를 점검해야 해
• 불가능하지? 그래서 "똑똑한 점검 방법"이 필요해

Part 2. 청크 시스템 - 필요한 곳만 업데이트

어떻게 10만 개를 다 처리해?

핵심: 다 처리 안 해.


맵을 32×32 타일 "청크"로 나눠.

플레이어가 없는 청크는 업데이트 빈도를 낮춰.

┌────┬────┬────┬────┐ │ 💤 │ 💤 │ 💤 │ 💤 │ 💤 = 비활성 (느리게) ├────┼────┼────┼────┤ │ 💤 │ ⚡ │ ⚡ │ 💤 │ ⚡ = 활성 (매 프레임) ├────┼────┼────┼────┤ │ 💤 │ ⚡ │ 👤 │ 💤 │ 👤 = 플레이어 위치 ├────┼────┼────┼────┤ │ 💤 │ 💤 │ 💤 │ 💤 │ └────┴────┴────┴────┘

플레이어 주변 청크만 매 프레임 업데이트, 나머지는 느리게

비활성 청크는 완전히 멈추는 거야?

아니야. 그러면 공장이 안 돌아가니까.


비활성 청크는 "요약 업데이트"를 해.

• 매 프레임 대신 10프레임마다 한 번

• 또는 "결과만 계산" (과정 생략)

"결과만 계산"이 뭐야?

예: 1초 동안 멀리 있었던 채굴기가 있어.


과정 시뮬레이션:

→ 60프레임 × (광물 캐기 → 벨트에 놓기 → ...) = 느림


결과만 계산:

→ "1초면 광물 10개 생산" → 바로 10개 추가 = 빠름

청크 상태 업데이트 방식 부하
플레이어 주변 (활성) 매 프레임 전체 시뮬레이션 높음
보이는 범위 (준활성) 5프레임마다 업데이트 중간
멀리 떨어진 (비활성) 결과만 계산, 20프레임마다 낮음

Part 3. 컨베이어 벨트 - 가장 많은 엔티티

컨베이어 벨트가 왜 문제야?

Factorio에서 가장 많은 엔티티가 벨트 위 아이템이야.

벨트 한 칸에 아이템 2개, 벨트가 수천 개면...

아이템만 수만 개.

아이템 하나하나를 물리 시뮬레이션 해?

그러면 터져.


Factorio는 벨트를 "파이프라인"으로 취급해.

아이템이 물리적으로 이동하는 게 아니라,

벨트가 "흐름"을 갖고 있는 거야.

❌ 나쁜 방법: 아이템마다 위치 계산 [🔩]→[🔩]→[🔩]→[🔩]→[🔩]→... ↑ ↑ ↑ ↑ ↑ 각각 position += speed (10만 번 계산) ✅ 좋은 방법: 벨트 단위로 "흐름" 계산 [========벨트========] 흐름량: 45/s → 입구에서 아이템 제거 → 출구에서 아이템 생성

아이템을 개별 이동시키지 않고, 벨트의 "처리량"만 계산

그럼 아이템이 벨트 위에서 움직이는 건 어떻게 보여줘?

렌더링만 그렇게 보이게 해.


실제 로직: 벨트A → 벨트B로 아이템 "전송"

화면 표시: 아이템이 부드럽게 이동하는 것처럼 보간


로직과 렌더링을 분리하는 거야.

// 벨트 업데이트 (간소화) class Belt { float flowRate; // 초당 아이템 처리량 Queue inputQueue; // 입구에 들어온 아이템 Queue outputQueue; // 출구로 나갈 아이템 void Update(float deltaTime) { // 복잡한 물리 계산 없이 "흐름"만 처리 float itemsToMove = flowRate * deltaTime; MoveItems(inputQueue, outputQueue, itemsToMove); } }

Part 4. 삽입기(Inserter) - 이벤트 기반 처리

삽입기는 뭐야?

벨트에서 아이템을 집어서 기계에 넣는 로봇 팔.

Factorio 공장에서 가장 많이 쓰이는 엔티티 중 하나.

삽입기도 매 프레임 업데이트해?

안 해. 그러면 너무 느려.


삽입기는 이벤트 기반으로 작동해.

• 벨트에 아이템 도착 → "삽입기야, 아이템 왔어!"

• 삽입기가 깨어나서 작업 시작

📱 비유: 폴링 vs 푸시 알림

폴링 (매 프레임 체크)
→ 1초에 60번 "아이템 왔어?" 확인 = 비효율

푸시 알림 (이벤트 기반)
→ 아이템 오면 그때만 알림 = 효율적

대부분의 시간 동안 삽입기는 "잠들어" 있음
이벤트 기반이 얼마나 빨라?

삽입기 10,000개가 있다고 치자.


폴링 방식: 매 프레임 10,000번 체크

이벤트 방식: 아이템 도착한 삽입기만 (보통 100~500개)


→ 20~100배 빠름

// 이벤트 기반 삽입기 class Inserter { bool isSleeping = true; void OnItemArrived(Item item) { // 이벤트 발생 시만 호출 isSleeping = false; StartPickup(item); } void Update() { if (isSleeping) return; // 대부분 여기서 종료 // 실제 작업 (집기/놓기 애니메이션) DoWork(); } }

Part 5. 멀티스레딩 - CPU 코어 전부 활용

요즘 CPU는 코어가 여러 개잖아. 다 쓸 수 있어?

쉽지 않아.


게임 로직은 보통 순서가 중요해.

A가 B에 영향을 주고, B가 C에 영향을 주면...

순서대로 해야 해서 병렬화가 어려워.

Factorio는 어떻게 해?

독립적인 작업을 찾아서 병렬화해.


예를 들어:

• 서로 멀리 떨어진 청크들 → 동시에 업데이트 가능

• 렌더링과 로직 → 별도 스레드

• 경로 탐색 (로봇) → 백그라운드 스레드

┌─────────────────────────────────────────┐ │ 메인 스레드 │ │ [게임 로직] → [동기화] → [렌더링 준비] │ └─────────────────────────────────────────┘ ↕ 작업 분배 ↕ 결과 수집 ┌──────────┐ ┌──────────┐ ┌──────────┐ │ 워커 #1 │ │ 워커 #2 │ │ 워커 #3 │ │ 청크 A,D │ │ 청크 B,E │ │ 청크 C,F │ └──────────┘ └──────────┘ └──────────┘

독립적인 청크들을 여러 워커 스레드가 동시에 처리

연결된 벨트는 어떻게 해? 순서가 중요하잖아.

벨트 네트워크 단위로 묶어.


연결된 벨트들 = 하나의 "네트워크"

네트워크 내부는 순차 처리

서로 다른 네트워크는 병렬 처리

시스템 병렬화 가능? 이유
독립된 청크 ✅ 가능 서로 영향 없음
연결된 벨트 ❌ 불가 순서대로 흘러야 함
경로 탐색 ✅ 가능 읽기 전용, 결과만 적용
전력망 계산 ✅ 가능 독립된 전력망 단위

Part 6. 데이터 지향 설계 - 캐시 친화적 구조

코드 구조도 성능에 영향을 줘?

엄청나게 영향을 줘.


CPU는 메모리에서 데이터를 가져올 때

캐시(Cache)를 사용해.

캐시 히트 = 빠름, 캐시 미스 = 느림.

캐시 미스를 줄이려면?

같이 쓰는 데이터를 메모리에 붙여놔.


객체 지향 (OOP):

→ 엔티티마다 데이터가 흩어져 있음

→ 캐시 미스 많음


데이터 지향 (DOD):

→ 같은 종류 데이터를 배열로 모음

→ 캐시 히트 많음

// ❌ 객체 지향 (캐시 비효율) class Inserter { Vector3 position; // 메모리 위치 A float rotation; Item heldItem; Machine target; // ... 수십 개 필드 } Inserter[] inserters; // 각 객체가 멀리 떨어져 있음 // ✅ 데이터 지향 (캐시 효율) struct InserterPositions { Vector3[] positions; // 위치만 연속 배열 } struct InserterRotations { float[] rotations; // 회전만 연속 배열 } // 위치 업데이트 시 positions 배열만 순회 → 캐시 히트!
얼마나 차이 나?

같은 로직이라도 2~10배 차이날 수 있어.


Factorio는 이런 최적화를 극한까지 적용해서

수십만 엔티티를 60 FPS로 돌릴 수 있는 거야.

📌 핵심 정리

  • 청크 시스템 - 플레이어 주변만 매 프레임, 나머지는 "결과만 계산"
  • 벨트 최적화 - 아이템 개별 이동 X, 벨트의 "흐름량"만 계산
  • 이벤트 기반 - 삽입기는 평소 "잠들어" 있다가 필요할 때만 깨어남
  • 멀티스레딩 - 독립적인 청크/네트워크를 여러 코어에서 병렬 처리
  • 데이터 지향 설계 - 캐시 친화적 메모리 배치로 2~10배 성능 향상
