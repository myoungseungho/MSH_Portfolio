← 게임에 적용된 기술

게임 길찾기의 진화

A* 격자 탐색에서 NavMesh, Flow Field, RVO까지 — 현대 게임 엔진의 경로 탐색 기술 계보

길찾기 기술의 진화

1968 — A* 알고리즘 발표 (격자 기반 최단 경로)

2000s — NavMesh 도입 (3D 공간을 삼각형 메시로 표현)

2004 — HPA* (계층적 A*, 대규모 맵)

2006 — Flow Field (RTS 수천 유닛 동시 이동)

2008 — ORCA/RVO (유닛 간 충돌 회피)

2009 — Recast/Detour (자동 NavMesh 생성, Unreal/Unity 채택)

현재 — NavMesh + RVO + 동적 장애물 + EQS = 현대 엔진의 길찾기 스택

Part 1. A* — 모든 길찾기의 출발점

A* 알고리즘이 뭐야?

맵을 격자(Grid)로 나누고, 시작점에서 목적지까지 가장 짧은 경로를 찾는 알고리즘이야.

핵심 공식: f(n) = g(n) + h(n)

값 의미 비유
g(n) 시작점 → 현재 노드까지 실제 비용 "여기까지 오는 데 얼마나 걸렸지?"
h(n) 현재 노드 → 목적지까지 추정 비용 (휴리스틱) "목적지까지 대충 얼마나 남았지?"
f(n) 총 예상 비용 = 지금까지 + 앞으로 "이 경로의 총 가격"
다익스트라랑 뭐가 달라?

다익스트라: 모든 방향으로 균등하게 탐색 (h = 0). 느리지만 확실.

A*: 목적지 방향을 "감"으로 알고 있음 (h > 0). 훨씬 빠름.

h(n)이 "직선 거리"를 알려주면, 목적지와 반대 방향은 탐색 안 함.

다익스트라 (h = 0): A* (h = 직선 거리): +---+---+---+---+---+ +---+---+---+---+---+ | . | . | . | . | . | | | | | . | . | +---+---+---+---+---+ +---+---+---+---+---+ | . | . | . | . | . | | | | . | . | G | +---+---+---+---+---+ +---+---+---+---+---+ | . | . | . | . | G | | | . | . | | | +---+---+---+---+---+ +---+---+---+---+---+ | . | . | . | . | . | | S | . | | | | +---+---+---+---+---+ +---+---+---+---+---+ | S | . | . | . | . | +---+---+---+---+---+ . = 탐색한 칸 (훨씬 적음!) 모든 방향 다 탐색 (느림) 목적지 방향 위주로 탐색 (빠름)
코드로 보여줘
// A* 핵심 로직 (의사 코드) priority_queue<Node> openList; // 탐색 후보 (f값 작은 것 우선) set<Node> closedList; // 이미 탐색 완료 openList.push(startNode); while (!openList.empty()) { Node current = openList.pop(); // f값 가장 작은 노드 if (current == goal) return ReconstructPath(current); // 경로 완성! closedList.insert(current); for (Node neighbor : current.neighbors()) { if (closedList.contains(neighbor)) continue; if (IsWall(neighbor)) continue; int newG = current.g + Cost(current, neighbor); if (newG < neighbor.g) { neighbor.g = newG; neighbor.h = Heuristic(neighbor, goal); // 맨해튼 or 유클리드 neighbor.f = neighbor.g + neighbor.h; neighbor.parent = current; openList.push(neighbor); } } }

Part 2. A*의 한계 — 왜 3D 게임에서 못 쓰나?

A*면 충분한 거 아냐? 왜 다른 게 필요해?

2D 타일 게임(스타크래프트, 팩맨)에서는 A*로 충분해.

하지만 3D 오픈월드에서는 치명적인 문제가 있어.

문제 설명
메모리 폭발 3D 공간을 격자로 나누면? 1000x1000x100 = 1억 개 노드. 메모리 수 GB
부자연스러운 경로 격자 기반이라 45도/90도로만 이동. 대각선 지그재그 경로 생김
지형 표현 한계 경사면, 계단, 점프대, 사다리 등을 격자로 표현하기 어려움
계산 비용 맵이 커지면 오픈 리스트가 폭발. 수천 유닛이면 프레임 드롭
2D 격자 (A*에 적합): +--+--+--+--+--+ | | |██| | | 격자 = 맵의 모든 칸을 노드로 표현 +--+--+--+--+--+ 간단하지만, 맵이 크면 노드 수 폭발 | |██|██| | | +--+--+--+--+--+ 3D 오픈월드 (A* 불가능): _____ / \ 경사면, 절벽, 다리, 터널... / ___ \ 격자로 표현하려면 해상도를 엄청 높여야 함 / / \ \ → 노드 수억 개 → 메모리+CPU 폭발 / / \ \ 다리 절벽 → 다른 방법이 필요하다!
그래서 뭘로 바꿨어?

NavMesh (Navigation Mesh) — 격자 대신, 이동 가능한 바닥면을 삼각형 메시로 표현하는 방법이야.

현재 Unreal, Unity 포함 거의 모든 3D 게임 엔진의 표준이야.

Part 3. NavMesh — 3D 길찾기의 표준

NavMesh가 뭐야?

Navigation Mesh = 캐릭터가 걸을 수 있는 바닥면을 삼각형(폴리곤) 메시로 표현한 것.

격자처럼 "모든 공간"을 노드로 만드는 게 아니라, "걸을 수 있는 면"만 표현해.

격자 기반: NavMesh 기반: +--+--+--+--+--+--+--+--+ +-----------+-------+ | | | | | | | | | | \ | /| +--+--+--+--+--+--+--+--+ | \ B | C / | | | |██|██|██| | | | | A \ | / | +--+--+--+--+--+--+--+--+ | \ |/ / | | |██|██|██| | | | +---------\--+ / +--+--+--+--+--+--+--+--+ | D \ | / | | | | | | | | | | \|/ +--+--+--+--+--+--+--+--+ +------------+ 노드 수: 64개 (8x8) 폴리곤 수: 4개 (A, B, C, D) 벽도 노드로 존재 걸을 수 있는 면만 존재 → 낭비가 심함 → 훨씬 적은 노드로 같은 맵 표현
NavMesh에서 길찾기는 어떻게 해?

2단계야:

1. 폴리곤 단위 A* — 시작 폴리곤에서 목적 폴리곤까지 경로 탐색

2. String Pulling — 폴리곤 경로를 매끄러운 직선 경로로 변환

Step 1: 폴리곤 단위 A* 시작점(S)이 폴리곤 A에 있고, 목적지(G)가 폴리곤 D에 있으면: A* 탐색: A → B → D (폴리곤 3개를 거치는 경로) Step 2: String Pulling (Funnel Algorithm) 폴리곤 경로의 "모서리(Portal)"를 이용해서 지그재그 없이 가장 짧은 직선 경로를 만듦 Before String Pulling: After String Pulling: S ----+ S | \ +----+ \ | \ +---- G G → 격자 기반처럼 꺾이지 않고, 대각선으로 자연스럽게 이동
NavMesh는 어떻게 만들어?

수동으로 안 만들어. Recast라는 알고리즘이 3D 지형을 자동 분석해서 생성해.

Unreal Engine과 Unity 둘 다 내부적으로 Recast를 쓰고 있어.

Recast의 NavMesh 자동 생성 과정: 1. Voxelization (복셀화) 3D 지형을 작은 복셀(3D 픽셀)로 분해 2. Walkable Surface (걸을 수 있는 면 추출) 경사 30도 이하 + 높이 2m 이상 통과 가능 = 걸을 수 있음 3. Region Partition (영역 분할) 걸을 수 있는 면을 연결된 영역으로 분류 4. Contour Tracing (윤곽선 추출) 각 영역의 테두리를 단순화 5. Polygon Mesh (삼각형 메시 생성) 윤곽선 내부를 삼각형으로 채움 = NavMesh 완성! Unity: Window → AI → Navigation → Bake Unreal: NavMeshBoundsVolume 배치 → 자동 생성

Part 4. HPA* — 오픈월드급 대규모 맵

NavMesh + A*면 끝 아냐?

맵이 작으면 충분해. 하지만 오픈월드(GTA, 엘든 링)에서는 NavMesh 폴리곤이 수만~수십만 개야.

A*를 그대로 돌리면 한 프레임에 수천 유닛의 경로를 못 구해.

HPA*가 뭐야?

Hierarchical Pathfinding A* — 맵을 계층적으로 나눠서 검색 범위를 줄이는 기법이야.

"서울에서 부산 가기"를 생각해봐. 집 앞 골목길부터 A*로 탐색하면 미친 짓이지.

일반 A*: 모든 노드를 탐색 (느림) S . . . . . . . . . . . . . . . . . . . . . . . . G 모든 칸을 하나하나 검사 HPA*: 계층적 탐색 (빠름) Level 2 (도시 단위): [서울] ----→ [대전] ----→ [부산] Level 1 (구역 단위): [강남] → [서초] → ... → [해운대] Level 0 (세부 경로): 실제 이동 경로 → 큰 그림 먼저, 세부 경로 나중에 → 탐색 노드 수가 1/10 ~ 1/100로 줄어듦
구체적으로 어떻게 동작해?

1. 맵을 클러스터(구역)로 분할

2. 클러스터 간 경계 노드를 추출

3. 경계 노드끼리 연결한 추상 그래프를 만듦

4. 추상 그래프에서 A* → 대략적인 경로

5. 각 클러스터 안에서만 세부 A* → 정밀 경로

비교 일반 A* HPA*
탐색 노드 수 수만 개 수백 개
사전 처리 없음 클러스터 분할 + 추상 그래프 생성
경로 품질 최적 거의 최적 (약간 우회 가능)
맵 변경 대응 즉시 해당 클러스터만 재계산

Part 5. Flow Field — 수천 유닛이 동시에 이동할 때

RTS에서 유닛 200개를 한 곳으로 보내면 A*를 200번 돌려야 해?

맞아, 그래서 A*를 유닛마다 따로 돌리면 프레임이 박살남.

StarCraft 2, Supreme Commander 같은 RTS는 Flow Field를 써.

Flow Field가 뭐야?

"목적지까지의 방향"을 맵의 모든 칸에 미리 기록해 두는 거야.

유닛은 자기 위치의 화살표 방향으로 따라가기만 하면 됨. 개별 A* 불필요.

A* 방식 (유닛 3개, 같은 목적지): 유닛1: A* 실행 → 경로 계산 ← 3번 실행! 유닛2: A* 실행 → 경로 계산 유닛3: A* 실행 → 경로 계산 Flow Field 방식: 1회 계산 → 모든 칸에 "이쪽으로 가" 화살표 생성 +-→-→-→-↓-+ | → → → ↓| | → ██ ↓ ↓| | → ██ ↓ ↓| | → → → G| G = 목적지 +---------+ 유닛이 어디에 있든, 자기 칸의 화살표를 따라가면 됨 → 유닛 1개든 1000개든 계산 비용 동일!
Flow Field 생성 과정: 1. Integration Field (비용 맵) - 목적지에서 BFS(너비 우선 탐색) - 각 칸에 "목적지까지 거리(비용)" 기록 +--+--+--+--+--+ | 4| 3| 2| 1| 0| ← 0 = 목적지 +--+--+--+--+--+ | 5| ██| ██| 2| 1| +--+--+--+--+--+ | 6| 5| 4| 3| 2| +--+--+--+--+--+ 2. Flow Field (방향 맵) - 각 칸에서 비용이 가장 낮은 이웃 방향 = 화살표 +--+--+--+--+--+ | →| →| →| →| G| +--+--+--+--+--+ | ↓| ██| ██| ↑| ↑| +--+--+--+--+--+ | →| →| →| →| ↑| +--+--+--+--+--+
비교 A* (유닛 N개) Flow Field
계산 횟수 N번 (유닛마다) 1번 (목적지당)
유닛 100개 A* x 100 Flow Field 1번
메모리 경로만 저장 맵 전체 방향 저장
적합한 장르 RPG, 소수 캐릭터 RTS, 대규모 유닛

Part 6. Local Avoidance — 유닛끼리 안 부딪히게

경로를 찾았는데 중간에 다른 유닛이 있으면?

A*나 NavMesh는 "정적 장애물"(벽, 지형)만 고려해.

"움직이는 장애물"(다른 유닛, NPC)은 별도 시스템이 필요해. 이게 Local Avoidance야.

RVO가 뭐야?

Reciprocal Velocity Obstacles — 서로의 속도 벡터를 고려해서, 충돌하지 않는 방향으로 속도를 조절하는 알고리즘이야.

"서로 비켜주는" 계산을 물리 시뮬레이션 없이 수학적으로 해결해.

상황: 두 유닛이 마주보고 걸어옴 RVO 없이: RVO 적용: A → ← B A → ← B ↓ ↘ ↙ (충돌! 멈춤) (서로 오른쪽으로 비켜감) ↗ ↖ A B → 자연스럽게 교차 핵심: 각 유닛이 "상대의 미래 위치"를 예측하고, 충돌하지 않는 속도 벡터를 선택
병목 지점에서의 RVO: 좁은 문을 100명이 통과해야 할 때: RVO 없이: RVO 적용: +---------+ +---------+ |AAAAAAAA | | A A A | |AAAAAAAA | | A A A A | +---+ +---+ +---+ +---+ | | |→| 유닛들이 자연스럽게 | | ← 막힘! |→| 줄을 서서 통과 +---+ +---+ +---+ +---+ | | | A A A | +---------+ +---------+
ORCA는?

ORCA (Optimal Reciprocal Collision Avoidance) = RVO의 개선판.

RVO는 속도 변경량이 최소인 해를 못 찾을 수 있는데, ORCA는 선형 프로그래밍으로 최적해를 보장해.

Unreal Engine의 Crowd Manager가 이걸 쓰고 있어.

Part 7. 현대 엔진의 실제 구현

Unreal Engine은 길찾기를 어떻게 해?

4개 레이어를 조합해:

Unreal Engine의 길찾기 스택: +--------------------------------------------------+ | Layer 4: EQS (Environment Query System) | | "어디로 가는 게 전술적으로 유리한가?" | | → 엄폐물 찾기, 사격 가능 위치, 도주 경로 | +--------------------------------------------------+ | Layer 3: Crowd Manager (RVO/ORCA) | | "다른 캐릭터랑 안 부딪히게" | | → 유닛 간 충돌 회피, 그룹 이동 | +--------------------------------------------------+ | Layer 2: Detour (런타임 쿼리) | | "NavMesh 위에서 경로 찾기" | | → 폴리곤 단위 A*, String Pulling, 동적 장애물 | +--------------------------------------------------+ | Layer 1: Recast (NavMesh 생성) | | "3D 지형을 NavMesh로 변환" | | → 자동 복셀화, 걸을 수 있는 면 추출 | +--------------------------------------------------+
Unity는?

Unity도 내부적으로 Recast/Detour를 쓰고 있어. 구조는 비슷해:

Unity의 길찾기 스택: NavMesh Surface ← Recast로 NavMesh 생성 ↓ NavMesh Agent ← Detour로 경로 탐색 + 이동 ↓ NavMesh Obstacle ← 동적 장애물 (런타임 NavMesh 커팅) ↓ Off-Mesh Link ← 점프, 사다리, 순간이동 등 특수 이동 // Unity 코드 NavMeshAgent agent = GetComponent<NavMeshAgent>(); agent.SetDestination(targetPosition); // 이 한 줄이 내부적으로: // 1. Recast NavMesh에서 가장 가까운 폴리곤 찾기 // 2. A*로 폴리곤 경로 탐색 // 3. String Pulling으로 경로 최적화 // 4. RVO로 다른 에이전트 회피하며 이동
동적 장애물은 어떻게 처리해?

두 가지 방식이 있어:

NavMesh Carving — 장애물 영역만큼 NavMesh를 실시간으로 잘라내기. 정확하지만 무거움.

Local Avoidance — NavMesh는 안 건드리고, 이동 시 장애물을 피해가기. 가볍지만 좁은 길에서 문제.

실무에서는 둘 다 조합: 큰 장애물(건물 파괴)은 Carving, 작은 장애물(다른 유닛)은 RVO.

Part 8. 상황별 선택 가이드

결국 어떤 상황에 뭘 써야 해?
상황 추천 이유
2D 타일 게임 A* 격자 기반, 간단하고 충분
3D 게임 (일반) NavMesh + A* 엔진 내장, 3D 지형 자동 처리
오픈월드 대규모 맵 NavMesh + HPA* 계층적 탐색으로 속도 확보
RTS (수백~수천 유닛) Flow Field 유닛 수에 무관한 계산 비용
유닛 간 충돌 회피 RVO / ORCA 물리 없이 자연스러운 회피
동적 장애물 Carving + RVO 큰 것 Carving, 작은 것 RVO
서버 사이드 길찾기 NavMesh (Recast/Detour) 서버에서도 Detour 라이브러리 사용 가능

핵심 정리

  • A* = f(n)=g(n)+h(n), 격자 기반 최단 경로. 2D 게임의 기본
  • NavMesh = 걸을 수 있는 면을 삼각형 메시로 표현. 3D 게임의 표준
  • Recast = 3D 지형에서 NavMesh를 자동 생성하는 알고리즘 (Unreal, Unity 내장)
  • Detour = NavMesh 위에서 경로를 탐색하는 런타임 라이브러리
  • String Pulling = 폴리곤 경로를 부드러운 직선으로 변환 (Funnel Algorithm)
  • HPA* = 맵을 계층적 클러스터로 나눠 탐색 범위를 줄임. 오픈월드용
  • Flow Field = 목적지까지 방향을 맵 전체에 기록. RTS 수천 유닛용
  • RVO/ORCA = 유닛 간 충돌 회피. 물리 없이 서로 비켜가기
  • 현대 엔진 = Recast(생성) + Detour(탐색) + RVO(회피) + EQS(전술) 조합
