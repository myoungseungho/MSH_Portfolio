빌드의 기초 - 전체 그림 이해하기

소스코드(.cpp)가 실행파일(.exe)이 되기까지

Part 1. 레고로 이해하는 빌드

빌드가 뭐야? 그냥 컴파일 아니야?

빌드는 컴파일 + 링킹을 합친 전체 과정이야.

레고로 비유하면 이해하기 쉬워!

🧱 레고 조립 비유

설계도(소스코드) → 각 부품 만들기(컴파일) → 부품 조립(링킹) → 완성품(실행파일)

📦 빌드 = 컴파일 + 링킹 ┌─────────────────────────────────────────────────────────────────┐ │ │ │ main.cpp ─┬─→ [컴파일러] ─→ main.obj ─┐ │ │ game.cpp ─┤ game.obj ─┼─→ [링커] ─→ game.exe│ │ player.cpp─┘ player.obj─┘ │ │ │ │ (소스코드) (번역) (부품) (조립) (완성품) │ └─────────────────────────────────────────────────────────────────┘
왜 한 번에 안 하고 두 단계로 나눠?

효율성 때문이야!

100개 파일 중 1개만 수정했다고 치자.

❌ 분리 안 하면: main.cpp 수정 → 100개 전부 다시 처리 → 5분 ✅ 분리하면: main.cpp 수정 → main.obj만 다시 컴파일 → 기존 99개 .obj 재사용 → 10초!

Part 2. .obj 파일은 뭐야?

.obj 파일이 정확히 뭔데?

Object File - 기계어로 번역된 코드 조각이야.

아직 완전한 프로그램은 아니야. "부품" 상태지.

📄 player.cpp 내용: ┌─────────────────────────────────┐ │ void Player::Attack() { │ │ // 공격 로직 │ │ } │ │ │ │ void Player::Move() { │ │ // 이동 로직 │ │ } │ └─────────────────────────────────┘ ↓ 컴파일 📦 player.obj 내용: ┌─────────────────────────────────┐ │ [기계어 코드] │ │ [심볼 테이블] │ │ - Player::Attack (정의됨) │ │ - Player::Move (정의됨) │ │ - Monster::TakeDamage (필요함)│ ← 외부 참조! └─────────────────────────────────┘
"외부 참조"가 뭐야?

Player::Attack()에서 Monster::TakeDamage()를 호출한다고 치자.

근데 Monster 코드는 다른 파일(monster.cpp)에 있잖아?

그래서 "이 함수 어딘가에 있을 거야"라고 표시만 해둬.

이게 외부 참조(External Reference)야.

Part 3. 링킹 - 부품 조립하기

그럼 링커는 뭘 해?

모든 .obj 파일을 모아서 외부 참조를 해결해!

🔗 링커의 작업 1️⃣ 모든 .obj 수집 player.obj: "Monster::TakeDamage 어딨어?" monster.obj: "Monster::TakeDamage 여기 있어!" 2️⃣ 참조 연결 player.obj의 TakeDamage 호출 → monster.obj의 TakeDamage 주소로 연결 3️⃣ 최종 주소 결정 모든 코드를 하나로 합치고 최종 메모리 주소 배정 4️⃣ 실행 파일 생성 game.exe 완성! 🎉
"unresolved external symbol" 에러는 뭐야?

링커가 "이 함수 정의를 못 찾겠어!"라고 하는 거야.

❌ 흔한 에러: error LNK2019: unresolved external symbol "Player::Attack" 원인: - player.cpp를 프로젝트에 안 넣었거나 - Attack() 함수를 선언만 하고 정의 안 했거나 - 라이브러리(.lib)를 링크 안 했거나

Part 4. 라이브러리(.lib)란?

.lib 파일은 뭐야?

미리 컴파일해둔 .obj 파일들의 묶음이야!

자주 쓰는 기능을 매번 컴파일하면 낭비잖아.

📚 라이브러리 = .obj들의 묶음 예: gniServer.lib (네트워크 라이브러리) ┌─────────────────────────────────┐ │ socket.obj - 소켓 기능 │ │ iocp.obj - IOCP 기능 │ │ encrypt.obj - 암호화 기능 │ │ ... │ └─────────────────────────────────┘ 우리 프로젝트에서 socket 기능 쓰려면? → gniServer.lib만 링크하면 됨! → socket 관련 코드 다시 컴파일 필요 없음!
그래서 빌드할 때 .lib 파일이 필요한 거구나!

맞아! Visual Studio에서 "Additional Dependencies"에

gniServer.lib, ws2_32.lib 같은 거 넣는 이유야.

Part 5. 실제 프로젝트에서

실제로 큰 프로젝트는 어떻게 돼?

조선협객전 서버 프로젝트를 예로 들면:

📊 조선협객전 서버 빌드 구조 server_Game 프로젝트: ├── 소스 파일: 약 200개 .cpp ├── 헤더 파일: 약 300개 .h ├── 중간 파일: 약 200개 .obj (빌드 중 생성) └── 최종 결과: server_Game.exe 의존 라이브러리: ├── gniServer.lib (네트워크 엔진) ├── gniUtil.lib (유틸리티) ├── ws2_32.lib (Windows 소켓) └── ...
단계 입력 출력 소요 시간 (최적화 전)
컴파일 200개 .cpp 200개 .obj 약 2분 30초
링킹 200개 .obj + .lib들 1개 .exe 약 1분
전체 - - 약 3분 30초
3분 30초면 코드 한 줄 고칠 때마다?

수정한 파일만 다시 컴파일하니까 증분 빌드는 빠르지만,

전체 리빌드는 3분 30초... 이게 하루에 10번이면 35분 낭비!

그래서 빌드 최적화가 중요해.

📝 핵심 정리

  • 빌드 = 컴파일(번역) + 링킹(조립)
  • .obj = 기계어 코드 조각 (부품)
  • 링커 = 모든 .obj를 모아 외부 참조 해결
  • .lib = 미리 컴파일된 .obj들의 묶음
  • 분리의 이유 = 수정한 파일만 다시 컴파일 (효율성)
  • "unresolved external" = 링커가 함수 정의를 못 찾음
