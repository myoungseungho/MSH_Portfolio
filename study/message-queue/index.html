서버끼리 편지 보내듯 통신한다고?

Message Queue로 서버 간 느슨한 결합 만들기

Part 1. 직접 호출하면 뭐가 문제야?

게임 서버에서 결제 서버 호출하면 바로 응답 받으면 되는 거 아냐?

간단한 경우엔 그래도 돼. 근데 문제가 생겨.

[직접 호출 - 동기 방식] 게임 서버 ──요청──▶ 결제 서버 │ │ │◀──────응답───────┘ │ ▼ (응답 올 때까지 대기) 문제 1: 결제 서버 죽으면? → 게임 서버도 에러 문제 2: 결제 서버 느리면? → 게임 서버도 멈춤 문제 3: 동시에 1만 명 결제? → 결제 서버 터짐
서버끼리 너무 딱 붙어있으면 하나 문제생기면 다 죽는구나

맞아. 이걸 "강한 결합(Tight Coupling)"이라고 해.

큰 시스템일수록 이게 치명적이야.

Part 2. 메시지 큐가 뭔데?

그럼 어떻게 해?

중간에 "우체통"을 하나 두는 거야.

[메시지 큐 - 비동기 방식] 게임 서버 ──메시지──▶ [ 📫 큐 ] ──메시지──▶ 결제 서버 │ │ ▼ (바로 다음 작업) │ (메시지 보관) │ ▼ (결제 서버가 여유 있을 때 가져감) 장점 1: 결제 서버 죽어도? → 큐에 쌓여있음, 살아나면 처리 장점 2: 결제 서버 느려도? → 게임 서버는 안 기다림 장점 3: 동시에 1만 명? → 큐에서 천천히 처리
아, 편지 보내는 거랑 비슷하네. 상대방이 없어도 우체통에 넣으면 되니까

정확해! 그래서 "느슨한 결합(Loose Coupling)"이라고 해.

Part 3. 게임 서버에서 언제 써?

게임에서 메시지 큐 쓰는 상황이 뭐가 있어?

실시간 응답이 필수가 아닌 작업들:

[메시지 큐 적합한 작업] ✅ 로그 저장 - 유저가 뭘 했는지 기록 게임 서버 → [로그 큐] → 로그 서버 → DB ✅ 메일 발송 - 보상, 공지 메일 운영 툴 → [메일 큐] → 게임 서버들 ✅ 랭킹 집계 - 매 분마다 계산 게임 서버들 → [점수 큐] → 랭킹 서버 ✅ 결제 처리 - 약간 늦어도 괜찮음 게임 서버 → [결제 큐] → 결제 서버 ✅ 푸시 알림 - 친구 접속, 길드 공지 게임 서버 → [푸시 큐] → 푸시 서버
전투나 스킬은 안 되겠네?

맞아. 실시간 응답이 필요한 건 직접 호출이 맞아.

0.1초 늦으면 "렉"이라고 느끼는 건 큐로 안 돼.

Part 4. Producer와 Consumer

메시지 큐 용어가 좀 나오던데?

핵심 용어 3개만 알면 돼:

[핵심 용어] ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ Producer │───▶│ Queue │───▶│ Consumer │ │ (생산자) │ │ (큐) │ │ (소비자) │ └─────────────┘ └─────────────┘ └─────────────┘ 메시지를 메시지를 메시지를 보내는 쪽 보관하는 곳 받아 처리하는 쪽 예시: - Producer: 게임 서버 (로그 생성) - Queue: RabbitMQ, Redis Pub/Sub - Consumer: 로그 서버 (로그 저장)
Consumer가 여러 개면?

처리량이 늘어나! 큐 하나에 Consumer 10개 붙이면 10배 빠르게 처리.

[Consumer 확장] ┌─▶ Consumer 1 (처리) │ Queue ────────────┼─▶ Consumer 2 (처리) (메시지 1000개) │ └─▶ Consumer 3 (처리) → 메시지를 나눠 가져가서 병렬 처리 → 처리량 부족하면 Consumer만 추가하면 됨!

Part 5. Pub/Sub 패턴

메시지를 여러 곳에 동시에 보내고 싶으면?

Pub/Sub (Publish/Subscribe) 패턴을 써.

[일반 큐 vs Pub/Sub] [일반 큐] - 1:1 또는 1:N 분배 메시지 → 큐 → Consumer 1개가 가져감 (다른 Consumer는 못 받음) [Pub/Sub] - 1:N 브로드캐스트 메시지 → Topic → 구독자 A (복사본 받음) → 구독자 B (복사본 받음) → 구독자 C (복사본 받음) 모든 구독자가 같은 메시지를 받음!
게임에서 언제 써?
[Pub/Sub 사용 예시] 📢 "유저 레벨업" 이벤트 발생! 게임 서버 ──publish──▶ [레벨업 Topic] │ ┌─────────┼─────────┐ ▼ ▼ ▼ 업적 서버 랭킹 서버 푸시 서버 (업적 체크) (점수 갱신) (축하 알림) → 게임 서버는 "레벨업했다"만 알림 → 누가 듣든 말든 신경 안 씀 → 새 서비스 추가? 그냥 구독만 하면 끝!

Part 6. 어떤 기술 쓰면 돼?

기술 특징 게임 서버 용도
RabbitMQ 범용, 다양한 패턴 결제, 메일, 알림
Redis Pub/Sub 초간단, 메모리 기반 실시간 알림, 채팅
Kafka 대용량, 로그 저장 로그 수집, 분석
AWS SQS 관리형, 무제한 확장 모바일 게임
뭘 쓰는 게 좋아?

• 간단하게 시작: Redis Pub/Sub (이미 Redis 쓰고 있으면)

• 안정성 중요: RabbitMQ

• 대용량 로그: Kafka

⚠️ 메시지 큐 도입 시 주의

• 메시지 유실 - 큐가 죽으면? 디스크에 저장하는 옵션 켜기

• 순서 보장 - Consumer가 여러 개면 순서 꼬일 수 있음

• 중복 처리 - 같은 메시지 2번 받을 수 있음 → 멱등성 필요

• 모니터링 - 큐에 메시지 쌓이는지 항상 체크

핵심 정리

  • 메시지 큐 = 서버 사이의 우체통. 비동기로 메시지 전달
  • 느슨한 결합 = 상대방 죽어도 내가 안 죽음
  • Producer → Queue → Consumer 기본 구조
  • Pub/Sub = 여러 구독자에게 동시에 브로드캐스트
  • 실시간 응답 필요한 건 X - 전투, 스킬은 직접 호출
  • 로그, 메일, 결제, 알림 같은 건 큐로 분리
