안 바뀐 건 왜 또 보내? — 델타 압축

전체 스냅샷 대신 '바뀐 필드만' 비트마스크로

30초 요약

매 틱 상태 전체를 보내면 안 바뀐 값까지 매번 전송 — 낭비.

델타 압축 = '뭐가 바뀌었나'를 비트마스크로 표시하고, 바뀐 필드만 붙여 보냄.

우리 더티플래그·DB 변경분 저장과 같은 원리. UE Push Model·Iris Delta도 동일.

Part 1. 전체를 매번 보내는 낭비

상태가 6개 필드인데, 한 개만 바뀌어도 6개 다 보내야 해?

전체 스냅샷 방식이면 그래. hp만 깎였는데 pos·ammo·name까지 매 틱 다시 보내 — 안 바뀐 5개가 순수 낭비야.

수천 명 × 수십 틱이면 이 낭비가 대역폭을 다 잡아먹어.

그럼 어떻게?

'바뀐 것만' 보내면 돼. 단, 받는 쪽이 '몇 번 필드가 왔는지' 알아야 하니까, 앞에 비트마스크(어느 필드가 들었는지)를 붙여.

비트마스크 1바이트 + 바뀐 필드들 = 델타. 안 바뀌면 거의 0.

Part 2. 전체 vs 델타

대역폭 차이를 봐.

탭으로 ① 전체 스냅샷 ② 델타 를 바꿔봐. 노란 필드가 '이번에 바뀐 것'이야.

전체는 매 틱 12B 고정(빨강 막대), 델타는 바뀐 만큼만(초록, 보통 훨씬 낮음). 누적 절감률을 봐.

0B누적 전송
0%전체 대비 절감

Part 3. 함정과 키프레임

델타만 보내면 위험한 거 없어?

있어. 델타는 '이전 상태 기준'이라, 중간 패킷이 유실되면 그 뒤가 어긋나(기준이 틀어짐). 신규 접속자는 이전 상태가 아예 없고.

그래서 가끔 '전체 상태(키프레임)'를 통째로 보내 기준을 다시 맞춰. 영상 코덱의 I-frame/P-frame과 똑같은 발상이야.

우리/UE는?

우리는 더티플래그로 '바뀐 것만' 저장·전송하고, 신규 접속 시 전체를 묶어 보내(키프레임). UE는 Push Model(바뀐 속성만) + 신규 채널 열 때 전체 → 이후 델타. Iris의 Delta도 같은 거야.

핵심 정리

  • 전체 스냅샷 = 매 틱 전부(낭비). 델타 = 비트마스크 + 바뀐 필드만
  • 안 바뀌면 거의 0B → 대역폭 급감
  • 함정: 델타는 이전 상태 기준 → 유실·신규접속 시 어긋남
  • 키프레임(전체 상태)을 주기적/접속 시 보내 기준 재동기 (영상 I-frame과 동일)
  • 우리 더티플래그 = UE Push Model = Iris Delta, 같은 원리
