게임 로그 100억 건을 어떻게 분석할까?

컬럼 스토어와 OLAP의 세계

Part 1. 로그 분석의 현실

게임 로그가 얼마나 쌓이나요?

라이브 서비스 게임의 현실적인 수치를 보면:

게임 로그 규모 (중형 MMORPG 기준): ┌────────────────────────────────────────────────────────────┐ │ │ │ 일일 로그 발생량: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 동시 접속자: 10만 명 │ │ │ │ 유저당 액션: 분당 60회 (이동, 공격, 채팅 등) │ │ │ │ │ │ │ │ 초당 로그: 10만 × 1 = 100,000건/초 │ │ │ │ 일일 로그: 100,000 × 86,400 = 86억 건/일 │ │ │ │ │ │ │ │ 행 크기 평균: 200 bytes │ │ │ │ 일일 용량: 86억 × 200B = 1.6TB/일 │ │ │ │ 월간 용량: 1.6TB × 30 = 48TB/월 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 로그 종류: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • 플레이 로그: 이동, 전투, 퀘스트, 스킬 사용 │ │ │ │ • 경제 로그: 아이템 획득/소모, 거래, 강화 │ │ │ │ • 소셜 로그: 채팅, 친구, 길드 활동 │ │ │ │ • 시스템 로그: 로그인/아웃, 오류, 성능 메트릭 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
MySQL로 100억 건 조회하면?

사실상 불가능합니다. Row Store의 구조적 한계 때문입니다:

Row Store에서 집계 쿼리의 문제: ┌────────────────────────────────────────────────────────────┐ │ │ │ 쿼리: "어제 아이템별 드롭 횟수" │ │ SELECT item_id, COUNT(*) FROM item_log │ │ WHERE log_date = '2024-01-15' GROUP BY item_id; │ │ │ │ Row Store 내부 동작: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 디스크 상 저장 (행 단위): │ │ │ │ │ │ │ │ [Row 1: user_id, item_id, qty, date, map, ...] │ │ │ │ [Row 2: user_id, item_id, qty, date, map, ...] │ │ │ │ [Row 3: user_id, item_id, qty, date, map, ...] │ │ │ │ ... │ │ │ │ [Row 10억: ...] │ │ │ │ │ │ │ │ 문제: item_id만 필요한데 전체 행을 다 읽어야 함! │ │ │ │ │ │ │ │ 행 크기: 200 bytes │ │ │ │ 필요한 컬럼: 8 bytes (item_id만) │ │ │ │ 읽기 낭비: 192/200 = 96% 불필요한 I/O! │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 예상 성능: │ │ • 10억 행 × 200B = 200GB 읽기 │ │ • SSD 500MB/s 기준: 400초 (6분 40초) │ │ • 인덱스? 10억 행 중 1억 행 대상이면 Random I/O 폭발 │ │ │ └────────────────────────────────────────────────────────────┘

Part 2. Row Store vs Column Store

Column Store는 뭐가 다른가요?

데이터를 열(Column) 단위로 저장합니다:

Row Store vs Column Store 저장 구조: ┌────────────────────────────────────────────────────────────┐ │ │ │ 원본 테이블: │ │ ┌─────────┬─────────┬──────┬────────────┐ │ │ │ user_id │ item_id │ qty │ log_date │ │ │ ├─────────┼─────────┼──────┼────────────┤ │ │ │ 1001 │ 5001 │ 1 │ 2024-01-15 │ │ │ │ 1002 │ 5002 │ 3 │ 2024-01-15 │ │ │ │ 1001 │ 5001 │ 2 │ 2024-01-15 │ │ │ │ 1003 │ 5003 │ 1 │ 2024-01-15 │ │ │ └─────────┴─────────┴──────┴────────────┘ │ │ │ │ Row Store (MySQL, PostgreSQL): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 디스크 블록 1: [1001,5001,1,2024-01-15] │ │ │ │ 디스크 블록 2: [1002,5002,3,2024-01-15] │ │ │ │ 디스크 블록 3: [1001,5001,2,2024-01-15] │ │ │ │ 디스크 블록 4: [1003,5003,1,2024-01-15] │ │ │ │ │ │ │ │ item_id 조회 시: 4개 블록 전체 읽기 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ Column Store (ClickHouse, BigQuery): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ user_id 파일: [1001, 1002, 1001, 1003] │ │ │ │ item_id 파일: [5001, 5002, 5001, 5003] │ │ │ │ qty 파일: [1, 3, 2, 1] │ │ │ │ log_date 파일: [2024-01-15, 2024-01-15, ...] │ │ │ │ │ │ │ │ item_id 조회 시: item_id 파일만 읽기! │ │ │ └──────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
-- 같은 쿼리, 다른 성능 -- MySQL (Row Store) - 느림 SELECT item_id, COUNT(*) as cnt FROM item_log WHERE log_date = '2024-01-15' GROUP BY item_id; -- 예상: 6분 (전체 행 스캔) -- ClickHouse (Column Store) - 빠름 SELECT item_id, COUNT(*) as cnt FROM item_log WHERE log_date = '2024-01-15' GROUP BY item_id; -- 예상: 2초 (item_id, log_date 컬럼만 읽음)
왜 그렇게 빨라지나요?

세 가지 핵심 최적화가 있습니다:

Column Store의 3가지 최적화: ┌────────────────────────────────────────────────────────────┐ │ │ │ 1. 컬럼 프로젝션 (Column Projection) │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 쿼리: SELECT item_id, COUNT(*) ... │ │ │ │ │ │ │ │ Row Store: 모든 컬럼 읽기 (200 bytes/row) │ │ │ │ Column Store: item_id만 읽기 (4 bytes/row) │ │ │ │ │ │ │ │ I/O 감소: 50배! │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 2. 압축 (Compression) │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 같은 타입 데이터가 연속 → 압축률 극대화 │ │ │ │ │ │ │ │ item_id: [5001,5001,5001,5002,5002,5003,...] │ │ │ │ → RLE: [(5001,3),(5002,2),(5003,1)] │ │ │ │ → 압축률 10:1 ~ 100:1 │ │ │ │ │ │ │ │ 압축 알고리즘: │ │ │ │ • RLE (Run-Length Encoding): 반복 값 │ │ │ │ • Dictionary: 문자열 → 정수 매핑 │ │ │ │ • Delta: 연속 증가값 (timestamp) │ │ │ │ • LZ4/ZSTD: 범용 압축 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 3. 벡터화 처리 (Vectorized Processing) │ │ ┌──────────────────────────────────────────────────┐ │ │ │ Row Store: 한 번에 1행씩 처리 │ │ │ │ for (row in rows) { if (row.date == target) } │ │ │ │ │ │ │ │ Column Store: 한 번에 수천 값 처리 (SIMD) │ │ │ │ dates[0..1023] == target (CPU 병렬 비교) │ │ │ │ │ │ │ │ CPU 효율: 10배 이상! │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 종합 효과: 50 × 10 × 10 = 최대 5000배 성능 향상! │ │ │ └────────────────────────────────────────────────────────────┘

Part 3. OLTP vs OLAP

그럼 모든 DB를 Column Store로 쓰면 되지 않나요?

아닙니다! 용도에 따라 적합한 DB가 다릅니다:

OLTP vs OLAP 비교: ┌────────────────────────────────────────────────────────────┐ │ │ │ OLTP (Online Transaction Processing): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 목적: 실시간 트랜잭션 처리 │ │ │ │ │ │ │ │ 특징: │ │ │ │ • 단일 행 조회/수정이 대부분 │ │ │ │ • 짧은 지연시간 (1ms 이하) │ │ │ │ • 높은 동시성 (초당 수만 트랜잭션) │ │ │ │ • ACID 보장 필수 │ │ │ │ │ │ │ │ 예시 쿼리: │ │ │ │ • SELECT * FROM users WHERE id = 12345 │ │ │ │ • UPDATE inventory SET qty = qty - 1 WHERE ... │ │ │ │ │ │ │ │ 적합한 DB: MySQL, PostgreSQL, MSSQL (Row Store) │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ OLAP (Online Analytical Processing): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 목적: 대량 데이터 분석 │ │ │ │ │ │ │ │ 특징: │ │ │ │ • 전체/대량 행 집계가 대부분 │ │ │ │ • 분석 시간 허용 (수 초 ~ 수 분) │ │ │ │ • 읽기 위주 (쓰기는 배치) │ │ │ │ • 비정규화된 넓은 테이블 │ │ │ │ │ │ │ │ 예시 쿼리: │ │ │ │ • SELECT item_id, SUM(qty) FROM logs GROUP BY... │ │ │ │ • 일별 매출 추이, 유저 리텐션 분석 │ │ │ │ │ │ │ │ 적합한 DB: ClickHouse, BigQuery, Redshift │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 게임 서버는 둘 다 필요! │ │ • 게임 DB (OLTP): 캐릭터 정보, 인벤토리, 거래 │ │ • 로그 DB (OLAP): 플레이 분석, 지표 대시보드 │ │ │ └────────────────────────────────────────────────────────────┘
Column Store는 왜 OLTP에 안 좋나요?

단일 행 조회/수정 시 모든 컬럼 파일을 열어야 합니다:

-- 단일 행 조회 비교 -- Row Store: user_id 인덱스로 1개 블록 읽기 SELECT * FROM users WHERE user_id = 12345; -- 1 블록 읽기 = 0.1ms -- Column Store: 모든 컬럼 파일에서 해당 위치 읽기 SELECT * FROM users WHERE user_id = 12345; -- 50개 컬럼 × 각 파일 seek = 10ms (100배 느림!) -- 단일 행 UPDATE 비교 -- Row Store: 1개 블록 수정 UPDATE users SET gold = gold + 100 WHERE user_id = 12345; -- 1 블록 쓰기 -- Column Store: gold 컬럼 파일 전체 재작성 필요 -- (또는 복잡한 delta 메커니즘 사용) -- 훨씬 비효율적!

Part 4. 실전: ClickHouse로 게임 로그 분석

ClickHouse는 어떤 DB인가요?

러시아 Yandex가 만든 오픈소스 컬럼 스토어입니다. 게임 업계에서 많이 사용합니다:

ClickHouse 특징: ┌────────────────────────────────────────────────────────────┐ │ │ │ 성능: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • 10억 행 집계: 1~3초 │ │ │ │ • 초당 수백만 행 INSERT │ │ │ │ • 압축률: 원본 대비 10~20배 절약 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 사용 사례: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • CloudFlare: DNS 로그 분석 │ │ │ │ • Uber: 실시간 분석 플랫폼 │ │ │ │ • 게임사: 넥슨, 넷마블, 스마일게이트 등 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 경쟁 제품 비교: │ │ ┌─────────────┬─────────────┬─────────────┬──────────┐ │ │ │ 제품 │ 설치 │ 비용 │ 성능 │ │ │ ├─────────────┼─────────────┼─────────────┼──────────┤ │ │ │ ClickHouse │ 셀프 호스팅 │ 무료 (OSS) │ ★★★★★ │ │ │ │ BigQuery │ 클라우드 │ 쿼리당 과금 │ ★★★★☆ │ │ │ │ Redshift │ AWS 전용 │ 시간당 과금 │ ★★★★☆ │ │ │ │ Druid │ 셀프/클라우드│ 무료 (OSS) │ ★★★★☆ │ │ │ └─────────────┴─────────────┴─────────────┴──────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
-- ClickHouse 테이블 생성 CREATE TABLE game_logs ( log_date Date, log_time DateTime, user_id UInt64, action_type LowCardinality(String), -- 딕셔너리 압축 item_id UInt32, quantity UInt16, map_id UInt16, position_x Float32, position_y Float32 ) ENGINE = MergeTree() -- ClickHouse 기본 엔진 PARTITION BY toYYYYMM(log_date) -- 월별 파티션 ORDER BY (log_date, user_id) -- 정렬 키 (=클러스터링) TTL log_date + INTERVAL 90 DAY; -- 90일 후 자동 삭제 -- 데이터 삽입 (배치) INSERT INTO game_logs SELECT * FROM mysql('game_db:3306', 'game', 'logs', 'user', 'pass') WHERE log_date = today() - 1;
실제 분석 쿼리는 어떻게 작성하나요?

게임 운영에서 자주 쓰는 분석 쿼리들입니다:

-- 1. 일별 활성 유저 (DAU) SELECT log_date, uniqExact(user_id) AS dau FROM game_logs WHERE log_date >= today() - 30 GROUP BY log_date ORDER BY log_date; -- 300억 행 스캔: 약 2초 -- 2. 아이템 드롭 분포 (상위 100개) SELECT item_id, count() AS drop_count, uniqExact(user_id) AS unique_users, avg(quantity) AS avg_qty FROM game_logs WHERE log_date = today() - 1 AND action_type = 'item_drop' GROUP BY item_id ORDER BY drop_count DESC LIMIT 100; -- 10억 행 스캔: 약 1.5초 -- 3. 유저 리텐션 (Day 1, 7, 30) WITH new_users AS ( SELECT user_id, min(log_date) AS first_date FROM game_logs GROUP BY user_id ) SELECT first_date, count() AS new_users, countIf(user_id IN ( SELECT user_id FROM game_logs WHERE log_date = first_date + 1 )) AS d1_retained, countIf(user_id IN ( SELECT user_id FROM game_logs WHERE log_date = first_date + 7 )) AS d7_retained FROM new_users WHERE first_date >= today() - 30 GROUP BY first_date; -- 4. 실시간 동접 (1분 단위) SELECT toStartOfMinute(log_time) AS minute, uniqExact(user_id) AS concurrent FROM game_logs WHERE log_date = today() AND action_type = 'heartbeat' GROUP BY minute ORDER BY minute;

Part 5. 게임 로그 파이프라인 설계

게임 서버에서 ClickHouse까지 어떻게 보내나요?

실시간 스트리밍 + 배치 조합이 일반적입니다:

게임 로그 파이프라인: ┌────────────────────────────────────────────────────────────┐ │ │ │ 게임 서버 │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ [Game Server 1] [Game Server 2] [Server N] │ │ │ │ │ │ │ │ │ │ │ └────────────────┼────────────────┘ │ │ │ │ ▼ │ │ │ │ 로그 버퍼 (메모리) │ │ │ │ │ │ │ │ └────────────────────────┼──────────────────────────┘ │ │ ▼ │ │ 메시지 큐 (Kafka) │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ [Topic: game-logs] │ │ │ │ • Partition 0: user_id % 10 == 0 │ │ │ │ • Partition 1: user_id % 10 == 1 │ │ │ │ • ... │ │ │ │ │ │ │ │ 버퍼 역할 + 재처리 가능 │ │ │ │ │ │ │ └────────────────────────┼──────────────────────────┘ │ │ ▼ │ │ ETL 레이어 │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ Option 1: Kafka → ClickHouse 직접 │ │ │ │ (kafka engine 테이블 사용) │ │ │ │ │ │ │ │ Option 2: Kafka → Flink → ClickHouse │ │ │ │ (실시간 변환/집계 필요 시) │ │ │ │ │ │ │ │ Option 3: Kafka → S3 → ClickHouse (배치) │ │ │ │ (비용 최적화, 지연 허용 시) │ │ │ │ │ │ │ └────────────────────────┼──────────────────────────┘ │ │ ▼ │ │ 분석 DB (ClickHouse) │ │ ┌──────────────────────────────────────────────────┐ │ │ │ │ │ │ │ [game_logs 테이블] │ │ │ │ • 월별 파티션 │ │ │ │ • 90일 TTL │ │ │ │ │ │ │ └────────────────────────┼──────────────────────────┘ │ │ ▼ │ │ 시각화 (Grafana, Metabase, Tableau) │ │ │ └────────────────────────────────────────────────────────────┘
// 게임 서버 로그 전송 (C++) class LogBuffer { private: std::vector<LogEntry> m_buffer; std::mutex m_mutex; KafkaProducer* m_kafka; public: // 로그 추가 (게임 스레드에서 호출) void AddLog(const LogEntry& entry) { std::lock_guard<std::mutex> lock(m_mutex); m_buffer.push_back(entry); // 버퍼가 1000개 이상이면 즉시 전송 if (m_buffer.size() >= 1000) { FlushAsync(); } } // 비동기 전송 (별도 스레드) void FlushAsync() { std::vector<LogEntry> toSend; { std::lock_guard<std::mutex> lock(m_mutex); toSend.swap(m_buffer); } if (toSend.empty()) return; // JSON 직렬화 후 Kafka 전송 std::string json = SerializeToJson(toSend); m_kafka->Send("game-logs", json); } // 주기적 플러시 (1초마다) void PeriodicFlush() { while (m_running) { std::this_thread::sleep_for(std::chrono::seconds(1)); FlushAsync(); } } };

Part 6. BigQuery vs ClickHouse

클라우드 서비스(BigQuery)는 어떤가요?

규모와 운영 역량에 따라 선택이 달라집니다:

BigQuery vs ClickHouse 비교: ┌────────────────────────────────────────────────────────────┐ │ │ │ BigQuery (Google Cloud): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 장점: │ │ │ │ • 설치/운영 필요 없음 (서버리스) │ │ │ │ • 무한 확장 (자동) │ │ │ │ • GCP 생태계 통합 (Dataflow, Looker) │ │ │ │ │ │ │ │ 단점: │ │ │ │ • 비용: 1TB 스캔당 $5 (쿼리 많으면 비쌈) │ │ │ │ • 실시간성 제한 (스트리밍 INSERT 추가 비용) │ │ │ │ • 벤더 종속 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ ClickHouse (Self-hosted): │ │ ┌──────────────────────────────────────────────────┐ │ │ │ 장점: │ │ │ │ • 비용: 서버 비용만 (쿼리 무제한) │ │ │ │ • 실시간 INSERT 최적화 │ │ │ │ • 오픈소스 (종속 없음) │ │ │ │ │ │ │ │ 단점: │ │ │ │ • 운영 필요: 모니터링, 백업, 확장 직접 관리 │ │ │ │ • 초기 설정 러닝커브 │ │ │ │ • 복제/샤딩 설정 복잡 │ │ │ └──────────────────────────────────────────────────┘ │ │ │ │ 선택 기준: │ │ ┌──────────────────────────────────────────────────┐ │ │ │ • 데이터 < 10TB, 쿼리 적음 → BigQuery │ │ │ │ • 데이터 > 10TB, 쿼리 많음 → ClickHouse │ │ │ │ • DBA 없음 → BigQuery │ │ │ │ • 실시간 중요 → ClickHouse │ │ │ │ • 이미 GCP 사용 중 → BigQuery │ │ │ └──────────────────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘
-- BigQuery 비용 계산 예시 -- 월간 데이터: 50TB -- 일일 쿼리: 100개 -- 평균 스캔: 쿼리당 500GB -- BigQuery 비용: -- 저장: 50TB × $0.02/GB = $1,000/월 -- 쿼리: 100 × 30일 × 0.5TB × $5 = $7,500/월 -- 합계: $8,500/월 -- ClickHouse 비용 (AWS 예시): -- 3x r6i.2xlarge (64GB RAM): 3 × $400 = $1,200/월 -- 10TB EBS: $800/월 -- 합계: $2,000/월 -- 차이: $6,500/월 절감 (ClickHouse) -- 단, 운영 인력 비용 고려 필요

핵심 정리

  • Row Store는 OLTP(트랜잭션)에 적합, 집계 쿼리에는 비효율적
  • Column Store는 OLAP(분석)에 최적화, 압축률과 I/O 효율 극대화
  • 벡터화 처리로 SIMD 병렬 연산, 10배 이상 CPU 효율
  • ClickHouse: 오픈소스, 자체 운영, 대용량에 비용 효율적
  • BigQuery: 서버리스, 소규모~중규모에 간편, 대용량 시 비용 주의
  • 로그 파이프라인: 게임서버 → Kafka → ETL → ClickHouse → 시각화
