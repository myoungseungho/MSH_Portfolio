게임 패치 다운로드가 빠른 사이트의 비밀

P2P 배포 - CDN만으로 부족할 때의 해결책

Part 1. 왜 CDN만으로 부족할까?

게임 패치 할 때 보면 속도가 엄청 빠르던데, 그냥 좋은 서버 쓰는 거 아니야?

그것만으론 부족해.

대형 게임 패치는 수십 GB인데, 수백만 명이 동시에 받으면?

[CDN 비용 계산 - 현실적인 예시] 게임: 신작 MMORPG 패치 크기: 30GB 동시 다운로드: 100만 명 필요한 대역폭: 30GB x 1,000,000 = 30,000,000 GB = 30 PB (페타바이트) CDN 비용 (AWS CloudFront 기준): 대략 $0.085/GB = 30,000,000 x $0.085 = $2,550,000 => 한 번 패치에 25억원?!
헐... 그래서 어떻게 해결해?

P2P (Peer-to-Peer) 배포를 함께 사용해.

다운로드 받은 사람이 다른 사람한테 파일을 나눠주는 방식!

📚 비유: 교과서 복사

CDN 방식: 선생님이 1000명한테 교과서 1권씩 직접 복사해서 나눠줌
=> 선생님 녹초

P2P 방식: 선생님이 10명한테 주고, 그 10명이 각각 10명한테 복사해줌
=> 선생님 편함, 빠르게 전파됨

Part 2. P2P 배포는 어떻게 동작할까?

P2P가 토렌트 같은 거야?

맞아! 토렌트(BitTorrent)가 대표적인 P2P 프로토콜이야.

[P2P 핵심 개념] 파일을 작은 조각(Piece)으로 나눔 └─> 각 조각을 여러 사람이 동시에 공유 용어: - Seeder: 파일 전체를 가진 사람 (업로드만) - Leecher: 파일 일부만 가진 사람 (다운+업로드) - Tracker: 누가 어떤 조각을 가졌는지 알려주는 서버 - Swarm: 같은 파일을 공유하는 모든 피어의 집합
[BitTorrent 동작 흐름] ┌─────────────┐ │ Tracker │ "A는 조각 1,2 가짐" │ Server │ "B는 조각 3,4 가짐" └──────┬──────┘ │ ┌───────────────┼───────────────┐ │ │ │ v v v ┌────────┐ ┌────────┐ ┌────────┐ │ Peer A │ <--> │ Peer B │ <--> │ Peer C │ │ [1,2] │ │ [3,4] │ │ [1,3] │ └────────┘ └────────┘ └────────┘ ^ │ │ └───────────────┴───────────────┘ 서로 부족한 조각 교환 => 서버 부담 최소화, 피어끼리 나눠 가짐
근데 처음에는 아무도 파일이 없잖아?

초기 Seeder가 필요해.

게임 회사 서버가 처음에 파일을 뿌려주고, 받은 사람들이 점점 Seeder가 되는 거야.

[시간에 따른 배포 확산] T=0: 게임사 서버만 Seeder Server [===완전체===] User A [ ] User B [ ] User C [ ] T=1: User A가 일부 받음 => A도 공유 시작 Server [===완전체===] --> User A [==..] User A [==..] --> User B, C T=2: 점점 많은 사람이 공유 Server ──┐ User A ──┼──> User D, E, F... User B ──┘ T=N: 서버 부담 거의 없음 대부분 유저끼리 공유

Part 3. 하이브리드 P2P+CDN 방식

게임사들은 순수 P2P만 쓰는 거야?

아니! 대부분 하이브리드 방식을 써.

CDN + P2P를 조합해서 장점만 취함.

방식 장점 단점
순수 CDN 안정적, 빠른 초기 속도 비용 폭탄
순수 P2P 비용 최소화 초기 느림, 방화벽 문제
하이브리드 빠르고 저렴 구현 복잡
[하이브리드 P2P+CDN 동작] 다운로드 시작: 1. CDN에서 먼저 일부 받기 시작 (빠른 시작) 2. 동시에 P2P 네트워크 연결 3. P2P에서 받을 수 있는 조각은 P2P로 4. P2P에 없거나 느린 조각은 CDN에서 보완 조각별 우선순위: ┌─────────────────────────────────────────┐ │ 조각 1: P2P에 10명 보유 => P2P로 받음 │ │ 조각 2: P2P에 0명 보유 => CDN에서 받음 │ │ 조각 3: P2P 속도 느림 => CDN으로 전환 │ └─────────────────────────────────────────┘ => "가장 빠른 경로" 자동 선택
게임사 입장에서 얼마나 절약되는 거야?
[비용 절감 효과 - 실제 사례 기반] 100만 명 동시 다운로드, 30GB 패치: 순수 CDN: - 트래픽: 30 PB - 비용: 약 25억원 하이브리드 P2P+CDN (P2P 비율 80%): - CDN 트래픽: 6 PB (20%) - P2P 트래픽: 24 PB (유저 대역폭 사용) - 비용: 약 5억원 => 80% 비용 절감!

Part 4. 실제 게임 런처 구현 사례

진짜로 쓰는 게임들이 있어?

대부분의 대형 게임이 쓰고 있어!

플랫폼/게임 P2P 기술 특징
Battle.net (블리자드) 자체 P2P + CDN 와우, 디아블로 등
Riot Games 자체 P2P (Pando 기반) LoL 패치에 활용
Steam P2P 옵션 제공 LAN 내 P2P 지원
넥슨 자체 P2P 런처 메이플스토리 등
[게임 런처 P2P 구현 개념] // 의사 코드: 하이브리드 다운로더 class HybridDownloader { CDNClient cdn; P2PClient p2p; async downloadFile(fileInfo) { // 1. 파일을 조각으로 분할 pieces = splitIntoPieces(fileInfo, PIECE_SIZE); // 2. 각 조각별로 최적 소스 선택 for (piece in pieces) { p2pPeers = p2p.findPeersWithPiece(piece.hash); if (p2pPeers.count > 3 && p2pPeers.avgSpeed > MIN_SPEED) { // P2P로 다운로드 (충분한 피어, 빠른 속도) await p2p.downloadPiece(piece); } else { // CDN fallback (피어 부족 or 느림) await cdn.downloadPiece(piece); } // 3. 받은 조각을 다른 피어에게 공유 p2p.sharePiece(piece); } } }
유저 입장에서 P2P 쓰면 뭐가 불편해?

업로드 대역폭을 쓰니까 인터넷 속도가 느려질 수 있어.

그래서 대부분 런처에서 P2P 끄는 옵션을 제공해.

[런처 P2P 설정 옵션 예시] Battle.net 런처: 설정 > 다운로드 > "업로드 속도 제한" - 무제한 (기본) - 100 KB/s - 0 (P2P 끔) Steam 런처: 설정 > 다운로드 > "로컬 네트워크 게임 전송 허용" - LAN 내에서만 P2P 활성화 => 유저 선택권 보장

Part 5. 기술적 고려사항

P2P 구현할 때 어려운 점은?

크게 세 가지 문제가 있어:

[문제 1: NAT/방화벽] 대부분의 가정집 PC는 공유기 뒤에 있음 => 외부에서 직접 연결 불가 해결책: 1. NAT Traversal (STUN/TURN) - STUN: 공인 IP 파악 + 홀펀칭 - TURN: 중계 서버 경유 (최후의 수단) 2. UPnP/NAT-PMP - 공유기에 포트 자동 개방 요청 3. Relay Server - 직접 연결 안 되면 서버가 중계
[문제 2: 무결성 검증] P2P로 받은 파일이 진짜 원본인지 확인 필요 (악의적 피어가 변조된 파일 전송 가능) 해결책: 1. 조각별 해시 검증 Piece 1: SHA256 = "abc123..." ✓ Piece 2: SHA256 = "def456..." ✓ Piece N: SHA256 = "xyz789..." ✓ 2. 전체 파일 해시 최종 검증 Complete File: SHA256 = "final_hash..." 3. 코드 서명 (게임 실행 파일) => 변조 감지 + 신뢰성 보장
[문제 3: 피어 발견 (Peer Discovery)] 어떤 피어가 어떤 조각을 가졌는지 알아야 함 방법 1: Tracker Server - 중앙 서버가 피어 목록 관리 - 단점: 서버 다운 = 네트워크 마비 방법 2: DHT (Distributed Hash Table) - 피어들이 분산해서 정보 저장 - Trackerless 운영 가능 - BitTorrent, IPFS 등에서 사용 방법 3: PEX (Peer Exchange) - 피어끼리 다른 피어 정보 교환 - "나 A, B 알아" "나 C, D 알아" => 모두 공유

Part 6. 게임 서버 개발자 관점

게임 서버 개발자가 P2P 배포를 직접 만들어?

보통은 기존 솔루션을 활용해.

하지만 원리는 알아야 트러블슈팅이 가능해.

솔루션 용도 특징
libtorrent C++ BitTorrent 라이브러리 오픈소스, 커스터마이징 가능
WebTorrent 브라우저 P2P WebRTC 기반
IPFS 분산 파일 시스템 콘텐츠 주소 기반
자체 구현 특수 요구사항 높은 개발 비용
[운영 관점에서 중요한 메트릭] 모니터링 대상: 1. P2P 비율 (P2P Traffic / Total Traffic) - 목표: 70~90% - 낮으면? CDN 비용 증가 2. Seeder 비율 (Seeders / Total Peers) - 건강한 네트워크: 20% 이상 - 낮으면? 속도 저하 3. 평균 다운로드 속도 - 유저 체감 품질 지표 4. CDN Fallback 비율 - P2P 실패 빈도 파악 => 이 지표들로 시스템 건강 상태 판단

핵심 정리

  • CDN만으로 부족 - 대용량 패치 + 대규모 유저 = 비용 폭탄
  • P2P 배포 - 다운받은 유저가 다른 유저에게 파일 공유
  • 하이브리드 방식 - CDN (안정성) + P2P (비용 절감) 조합
  • 핵심 기술 - BitTorrent, NAT Traversal, 해시 검증
  • 실제 사례 - Battle.net, Steam, 국내 게임 런처 대부분
  • 비용 절감 - 80% 이상 대역폭 비용 절약 가능
