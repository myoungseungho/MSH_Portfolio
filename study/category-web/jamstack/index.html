JAMstack - JavaScript, APIs, Markup으로 만드는 빠른 웹사이트

Part 1. JAMstack이 뭐야?

게임 공략 위키 사이트 보면 엄청 빠르던데, 비결이 뭐야?

많은 문서/위키 사이트가 JAMstack 아키텍처를 사용해.

미리 만들어둔 HTML을 CDN에서 바로 전달하니까 빨라!

[JAMstack = J + A + M] J = JavaScript 동적 기능 담당 (클라이언트에서 실행) A = APIs 서버 기능은 API로 분리 (결제, 검색, 댓글 등) M = Markup 사전에 빌드된 HTML (Static Site Generator로 생성) 핵심 아이디어: => 가능한 한 많은 것을 "미리 만들어두자" => 요청 시 서버가 할 일을 최소화하자
🍔 비유: 패스트푸드 vs 레스토랑

전통 웹 (레스토랑):
손님 주문 → 주방에서 처음부터 요리 → 10분 후 서빙

JAMstack (패스트푸드):
미리 만들어둔 버거 → 손님 오면 바로 제공 → 30초

=> 대부분의 요청에 "미리 준비된 것" 제공
그러면 동적인 기능은 어떻게 해?

JavaScript + 외부 API로 처리해!

[전통 방식 vs JAMstack] 전통 방식 (서버 사이드 렌더링): ───────────────────────────────────── 요청 → 서버가 DB 조회 → HTML 생성 → 응답 User ──> Server ──> Database │ v HTML 생성 │ v User <────────┘ 문제: 매 요청마다 서버가 일함 = 느림, 비용 증가 JAMstack (정적 사이트 + API): ───────────────────────────────────── 요청 → CDN에서 미리 만든 HTML 전달 → 끝! (동적 기능은 JavaScript가 API 호출) 빌드 시: Markdown ──> Static Site Generator ──> HTML 파일들 요청 시: User ──> CDN ──> 미리 만든 HTML (초고속!) │ v (필요시) JavaScript가 API 호출

Part 2. Static Site Generator (SSG)

미리 HTML을 만든다는 게 무슨 뜻이야?

빌드 타임에 모든 페이지를 HTML로 변환해두는 거야.

마크다운 파일 → HTML 파일로!

[Static Site Generator 동작] 소스 파일 (개발자가 작성): ──────────────────────────── docs/ ├── index.md # 메인 페이지 ├── items/ │ ├── sword.md # 검 아이템 설명 │ └── shield.md # 방패 아이템 설명 └── guides/ └── beginner.md # 초보자 가이드 │ │ npm run build (빌드 명령) v 빌드된 결과물: ──────────────────────────── dist/ ├── index.html # 완성된 HTML ├── items/ │ ├── sword.html │ └── shield.html └── guides/ └── beginner.html => 이 HTML 파일들을 CDN에 업로드!
어떤 도구들이 있어?
도구 언어 특징 용도

Gatsby React GraphQL 데이터 레이어 마케팅 사이트

VitePress Vue Vite 기반 빠른 빌드 기술 문서

Part 3. CDN 기반 배포

왜 CDN에 올리면 빨라져?

전 세계에 분산된 서버에서 가까운 곳이 응답하니까!

[CDN 배포의 장점] 전통 방식 (Origin Server만): ───────────────────────────────────── 서버 위치: 미국 한국 유저 → [태평양 횡단] → 미국 서버 → [태평양 횡단] → 한국 유저 ~200ms 처리 ~200ms 총 지연: ~400ms CDN 방식: ───────────────────────────────────── CDN Edge 서버: 서울, 도쿄, 싱가포르, 미국, 유럽... 한국 유저 → 서울 Edge → (캐시에 있음!) → 한국 유저 ~5ms ~5ms 총 지연: ~10ms => 40배 빠름!
JAMstack에서 많이 쓰는 배포 서비스는?
서비스 특징 무료 플랜
Vercel Next.js 제작사, Git 연동 최고 100GB/월
Netlify JAMstack 선두주자, 풍부한 기능 100GB/월
Cloudflare Pages 무제한 대역폭, 빠른 Edge 무제한
GitHub Pages 간단, Jekyll 내장 1GB 저장소
AWS Amplify AWS 생태계 연동 5GB 저장
[Git 기반 자동 배포 흐름] 개발자가 할 일: 1. 마크다운 파일 수정 2. git push 자동으로 일어나는 일: 1. GitHub → Vercel/Netlify에 알림 2. 빌드 서버가 소스 다운로드 3. npm run build 실행 4. 생성된 HTML을 CDN에 배포 5. 전 세계 Edge 서버 업데이트 ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ git push │ ──> │ Build │ ──> │ Deploy │ │ (GitHub) │ │ Server │ │ (CDN) │ └─────────────┘ └─────────────┘ └─────────────┘ => 수정 후 1~2분이면 전 세계 반영!

Part 4. 게임 위키/문서 사이트 적용

실제로 게임 관련 사이트들이 이 방식 써?

아주 많이! 특히 문서 사이트에 최적화돼 있어.

[게임 분야 JAMstack 적용 사례] 1. 공식 문서 사이트 - Unity Docs, Unreal Docs - 빌드 자동화로 버전별 문서 관리 2. API 레퍼런스 - 게임 SDK 문서 - 코드 예제 + 자동 생성 3. 패치 노트 - 마크다운으로 작성 → 자동 배포 - 버전 히스토리 관리 (Git) 4. 커뮤니티 위키 - 나무위키, Fandom 등은 다른 방식이지만 - 소규모 팬 위키는 JAMstack 많이 사용 5. 이 포트폴리오 사이트! - GitHub Pages + 정적 HTML
게임 패치 노트 사이트를 JAMstack으로 만들면?
[패치 노트 사이트 구조 예시] content/ ├── patches/ │ ├── 2024-01-15-v1.2.0.md │ ├── 2024-01-08-v1.1.5.md │ └── 2024-01-01-v1.1.0.md └── _templates/ └── patch-note.html # 2024-01-15-v1.2.0.md ─────────────────────────────────── --- version: "1.2.0" date: 2024-01-15 title: "새해 대규모 업데이트" categories: [신규 콘텐츠, 밸런스, 버그 수정] --- ## 신규 콘텐츠 - 신규 던전 "빛의 성소" 추가 - 신규 직업 "성기사" 추가 ## 밸런스 조정 - 전사 기본 공격력 10% 증가 - 마법사 마나 회복 속도 5% 감소 ## 버그 수정 - 특정 상황에서 게임이 종료되는 문제 수정 빌드 시: ─────────────────────────────────── 1. 모든 .md 파일 파싱 2. 날짜순 정렬 3. 목록 페이지 생성 (patches/index.html) 4. 개별 페이지 생성 (patches/2024-01-15/index.html) 5. RSS 피드 생성 (patches/feed.xml) => 마크다운 하나 추가하면 사이트 자동 업데이트!

Part 5. 동적 기능은 어떻게?

검색이나 댓글 같은 건 정적 사이트로 안 되잖아?

JavaScript + 외부 API로 처리해!

[동적 기능별 해결책] 1. 검색 기능 ───────────────────────────────── 방법 A: 빌드 시 검색 인덱스 생성 (Lunr.js, Fuse.js) 방법 B: 외부 검색 서비스 (Algolia, Elasticsearch) // 클라이언트 사이드 검색 예시 import Fuse from 'fuse.js'; const fuse = new Fuse(searchIndex, { keys: ['title', 'content'] }); const results = fuse.search(query); 2. 댓글 기능 ───────────────────────────────── 외부 서비스: Disqus, Giscus (GitHub Discussions) 3. 분석/통계 ───────────────────────────────── Google Analytics, Plausible, Fathom 4. 폼 제출 ───────────────────────────────── Serverless Function 또는 외부 서비스 // Netlify Functions 예시 export async function handler(event) { const data = JSON.parse(event.body); await sendEmail(data); return { statusCode: 200 }; }
Serverless Function이 뭐야?

서버 없이 함수 단위로 실행되는 백엔드 코드야.

필요할 때만 실행되고, 비용도 실행 시간만 청구돼.

[JAMstack + Serverless 조합] 정적 사이트 (대부분): - HTML, CSS, JS → CDN에서 제공 - 비용: 거의 무료 동적 기능 (필요할 때만): - API 호출 → Serverless Function 실행 - 비용: 호출당 과금 (매우 저렴) ┌────────────────────────────────────────────────────┐ │ CDN │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ index. │ │ about. │ │ contact. │ │ │ │ html │ │ html │ │ html │ │ │ └──────────┘ └──────────┘ └──────────┘ │ └────────────────────────────────────────────────────┘ │ │ (동적 기능 필요시) v ┌────────────────────────────────────────────────────┐ │ Serverless Functions │ │ ┌────────────┐ ┌────────────┐ ┌────────────┐ │ │ │ /api/ │ │ /api/ │ │ /api/ │ │ │ │ search │ │ comment │ │ contact │ │ │ └────────────┘ └────────────┘ └────────────┘ │ └────────────────────────────────────────────────────┘

Part 6. JAMstack 장단점

JAMstack 쓰면 뭐가 좋고 뭐가 안 좋아?
장점 설명
속도 CDN 캐시에서 바로 응답, 서버 처리 없음
보안 서버 없음 = 공격 표면 최소화
비용 CDN 호스팅 비용만 (대부분 무료)
확장성 CDN이 알아서 확장, 트래픽 폭주에 강함
개발자 경험 Git 기반 워크플로우, 버전 관리
단점 설명
빌드 시간 페이지 많으면 빌드에 수 분~수십 분
실시간 데이터 빌드 시점의 데이터만 반영 (재빌드 필요)
복잡한 동적 기능 유저별 대시보드 등은 어려움
학습 곡선 SSG 도구 + 배포 플랫폼 학습 필요
[JAMstack이 적합한 경우] 적합: - 블로그, 포트폴리오 - 문서 사이트, 위키 - 마케팅 랜딩 페이지 - 제품 소개 사이트 - 게임 패치 노트, 공략 사이트 부적합: - 실시간 대시보드 - 유저별 커스텀 페이지 - 자주 변하는 대용량 데이터 - 복잡한 인터랙션 앱

핵심 정리

  • JAMstack - JavaScript + APIs + Markup 아키텍처
  • 핵심 아이디어 - 미리 빌드된 HTML을 CDN에서 제공
  • SSG - 마크다운 → HTML 변환 도구 (Hugo, Next.js 등)
  • 배포 - Vercel, Netlify, Cloudflare Pages (Git 연동)
  • 동적 기능 - JavaScript + Serverless Function + 외부 API
  • 장점 - 빠름, 저렴, 안전, 확장성
  • 적합 - 문서 사이트, 블로그, 게임 위키/패치노트
