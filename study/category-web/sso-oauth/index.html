로그인 한 번으로 여러 게임을 하는 법

SSO와 OAuth 2.0 - 게임 플랫폼 통합 로그인의 비밀

Part 1. SSO가 뭐야?

넥슨 로그인 한 번 하면 메이플, 던파, 카트 다 되잖아. 어떻게 가능한 거야?

SSO (Single Sign-On) 덕분이야.

한 번 로그인하면 여러 서비스에서 그 인증을 공유하는 기술!

🎢 비유: 놀이공원 입장

SSO 없이: 롤러코스터 탈 때 신분증 검사, 회전목마 탈 때 또 검사, 범퍼카 탈 때 또 검사...

SSO 있으면: 입구에서 팔찌 받음 → 모든 놀이기구 그냥 탑승!

=> 팔찌 = 인증 토큰
[SSO 동작 원리] ┌─────────────────┐ │ SSO 인증 서버 │ <= 한 번만 로그인 │ (넥슨 계정) │ └────────┬────────┘ │ ┌────────────────┼────────────────┐ │ │ │ v v v ┌─────────┐ ┌─────────┐ ┌─────────┐ │ 메이플 │ │ 던파 │ │ 카트 │ │ 스토리 │ │ │ │ 라이더 │ └─────────┘ └─────────┘ └─────────┘ ^ ^ ^ └────────────────┴────────────────┘ 공통 인증 토큰 사용
그러면 각 게임 서버가 비밀번호를 공유하는 거야?

아니! 비밀번호는 절대 공유 안 해.

대신 "이 사람 인증됨" 토큰만 공유해.

[비밀번호 vs 토큰] 비밀번호: - "abc123" (실제 인증 수단) - 유출되면 끝장 - 절대로 외부 서비스에 전달 X 토큰: - "eyJhbGciOiJIUzI1..." (인증됐다는 증명서) - 유출되면? 만료 시간 지나면 무효 - 제한된 권한만 부여 가능 => 비밀번호 대신 토큰을 주고받음

Part 2. OAuth 2.0이 뭐야?

"Google로 로그인", "카카오로 로그인" 이런 것도 SSO야?

비슷하지만 조금 달라. 이건 OAuth 2.0이라고 해.

외부 서비스가 네 정보 일부에 접근할 수 있게 "허가"하는 프로토콜이야.

개념 SSO OAuth 2.0
목적 한 번 로그인, 여러 서비스 접근 제3자 앱에 권한 위임
관계 같은 회사 서비스들 다른 회사 서비스
예시 넥슨 계정 → 메이플, 던파 구글 계정 → 스팀, 트위치
OAuth가 어떻게 동작해?
[OAuth 2.0 Authorization Code Flow] 참여자: - Resource Owner: 유저 (나) - Client: 로그인하려는 앱 (게임 클라이언트) - Authorization Server: 인증 서버 (Google, 카카오) - Resource Server: 유저 정보 서버 ┌────────────────────────────────────────────────────────────┐ │ │ │ [1] 유저가 "구글로 로그인" 클릭 │ │ Client → 구글 로그인 페이지로 이동 │ │ │ │ [2] 유저가 구글에 로그인 + 권한 허용 │ │ "이 앱이 이메일, 프로필에 접근해도 될까요?" [허용] │ │ │ │ [3] 구글이 Client에게 Authorization Code 전달 │ │ redirect: https://game.com/callback?code=ABC123 │ │ │ │ [4] Client가 Code를 Access Token으로 교환 │ │ Client → Google: "code=ABC123, 내 client_secret" │ │ Google → Client: "access_token=xyz789..." │ │ │ │ [5] Client가 Access Token으로 유저 정보 요청 │ │ Client → Google API: "Authorization: Bearer xyz789" │ │ Google → Client: { email: "user@gmail.com", ... } │ │ │ └────────────────────────────────────────────────────────────┘
🔑 비유: 대리 주차

비밀번호 공유 = 마스터키 줌 (위험!)
OAuth = 발렛파킹 키 줌 (시동만 걸 수 있고, 트렁크는 못 염)

=> 필요한 권한만 제한적으로 위임

Part 3. JWT 토큰이 뭐야?

토큰, 토큰 하는데 그게 실제로 어떻게 생겼어?

요즘 가장 많이 쓰는 형식이 JWT (JSON Web Token)야.

[JWT 구조] eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9. eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE1MTYyMzkwMjJ9. SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c │ │ │ └─── Header ────┘ └──── Payload ────┘ └── Signature ──┘ ┌─────────────────────────────────────────────────────────────┐ │ Header (Base64 디코딩): │ │ { │ │ "alg": "HS256", // 서명 알고리즘 │ │ "typ": "JWT" // 토큰 타입 │ │ } │ ├─────────────────────────────────────────────────────────────┤ │ Payload (Base64 디코딩): │ │ { │ │ "sub": "user_12345", // 유저 ID │ │ "name": "John", // 유저 이름 │ │ "role": "player", // 권한 │ │ "iat": 1516239022, // 발급 시간 │ │ "exp": 1516325422 // 만료 시간 │ │ } │ ├─────────────────────────────────────────────────────────────┤ │ Signature: │ │ HMACSHA256( │ │ base64(header) + "." + base64(payload), │ │ secret_key │ │ ) │ │ => 위변조 방지용 서명 │ └─────────────────────────────────────────────────────────────┘
이 토큰이 위조되면 어떡해?

Signature 덕분에 위조 탐지 가능해.

서버만 아는 비밀키로 서명하니까, 내용 바꾸면 서명이 안 맞아.

[JWT 검증 과정] 클라이언트 → 서버: "Authorization: Bearer eyJhbG..." 서버에서: 1. 토큰을 점(.)으로 분리 2. Header, Payload 추출 3. 비밀키로 서명 재계산 4. 받은 Signature와 비교 if (계산된_서명 == 받은_서명) { // 유효한 토큰 // Payload의 정보 신뢰 가능 } else { // 위조된 토큰! // 401 Unauthorized 응답 }
JWT의 장점이 뭐야?
특징 설명
Stateless 서버가 세션 저장 안 해도 됨 (토큰 자체에 정보 있음)
확장성 서버 여러 대여도 세션 공유 문제 없음
자체 포함 유저 정보가 토큰에 들어있어서 DB 조회 최소화
단점 토큰 크기가 큼, 강제 만료 어려움

Part 4. 게임 플랫폼에서의 구현

실제 게임 회사들은 어떻게 구현해?

대부분 자체 인증 서버 + OAuth 지원 조합이야.

[게임 플랫폼 인증 아키텍처] ┌──────────────────────────────────────────────────────────────┐ │ 게임 플랫폼 (예: 스팀) │ ├──────────────────────────────────────────────────────────────┤ │ │ │ ┌────────────────┐ ┌────────────────┐ │ │ │ 자체 로그인 │ │ 소셜 로그인 │ │ │ │ (ID/PW) │ │ (OAuth 2.0) │ │ │ └───────┬────────┘ └───────┬────────┘ │ │ │ │ │ │ └──────────┬──────────┘ │ │ v │ │ ┌─────────────────────┐ │ │ │ 통합 인증 서버 │ <= 하나의 인증 토큰 발급 │ │ │ (SSO Provider) │ │ │ └──────────┬──────────┘ │ │ │ │ │ ┌────────────────┼────────────────┐ │ │ v v v │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │ 게임A │ │ 게임B │ │ 웹사이트│ │ │ └──────┘ └──────┘ └──────┘ │ │ │ └──────────────────────────────────────────────────────────────┘
게임 서버에서 JWT 검증은 어떻게 해?
[게임 서버 JWT 검증 - C++ 의사 코드] class AuthManager { string secretKey; // 인증 서버와 공유하는 비밀키 // 클라이언트 접속 시 호출 bool VerifyToken(const string& token) { // 1. 토큰 파싱 auto parts = Split(token, '.'); if (parts.size() != 3) return false; string header = parts[0]; string payload = parts[1]; string signature = parts[2]; // 2. 서명 검증 string expectedSig = HMAC_SHA256( header + "." + payload, secretKey ); if (Base64Encode(expectedSig) != signature) { Log("Invalid signature - token tampered!"); return false; } // 3. 만료 시간 확인 auto claims = JsonParse(Base64Decode(payload)); if (claims["exp"] < GetCurrentTime()) { Log("Token expired!"); return false; } // 4. 유저 정보 추출 m_userId = claims["sub"]; m_userName = claims["name"]; return true; } };
[Access Token + Refresh Token 패턴] 문제: Access Token이 만료되면 다시 로그인? 해결: Refresh Token으로 새 Access Token 발급 ┌────────────────────────────────────────────────────┐ │ Access Token │ │ - 수명: 짧음 (15분 ~ 1시간) │ │ - 용도: API 호출할 때 사용 │ │ - 저장: 메모리 │ ├────────────────────────────────────────────────────┤ │ Refresh Token │ │ - 수명: 김 (7일 ~ 30일) │ │ - 용도: Access Token 재발급 │ │ - 저장: 안전한 곳 (HttpOnly Cookie) │ └────────────────────────────────────────────────────┘ 토큰 갱신 흐름: 1. Access Token으로 API 호출 2. 401 Unauthorized (토큰 만료) 3. Refresh Token으로 새 Access Token 요청 4. 새 Access Token 받음 5. 다시 API 호출 => 유저는 재로그인 없이 계속 사용

Part 5. 보안 고려사항

토큰이 탈취되면 어떡해?

여러 방어 수단이 있어:

[토큰 보안 대책] 1. HTTPS 필수 - 네트워크에서 토큰 가로채기 방지 2. 짧은 만료 시간 - Access Token: 15분 - 탈취해도 금방 만료 3. Token Binding - 토큰 발급 시 IP, User-Agent 기록 - 다른 환경에서 사용하면 거부 4. 토큰 블랙리스트 - 로그아웃 시 토큰 무효화 목록에 추가 - 검증할 때 블랙리스트 확인 5. Refresh Token Rotation - Refresh Token 사용 시 새 Refresh Token 발급 - 기존 Refresh Token 무효화 - 탈취 감지 가능
공격 유형 방어 방법
토큰 탈취 (네트워크) HTTPS 사용
토큰 탈취 (XSS) HttpOnly Cookie, CSP
토큰 위조 서명 검증 (비밀키)
토큰 재사용 만료 시간, 블랙리스트
CSRF SameSite Cookie, CSRF 토큰

Part 6. 게임 서버 개발자가 알아야 할 것

게임 서버 개발자로서 뭘 구현해야 해?

보통 인증 서버는 별도 팀이 만들지만, 게임 서버에서 토큰 검증은 직접 해야 해.

[게임 서버 인증 체크리스트] □ 클라이언트 접속 시 토큰 검증 - 서명 확인 - 만료 시간 확인 - 필요한 권한(role) 확인 □ 토큰 갱신 처리 - 만료 임박 시 갱신 요청 응답 - 갱신 실패 시 재로그인 유도 □ 토큰 정보 캐싱 - 매번 파싱하지 않고 세션에 저장 - 유저 ID, 이름, 권한 등 □ 로그아웃/강제 종료 처리 - 블랙리스트 확인 (Redis 등) - 다중 로그인 방지 □ 에러 처리 - 401: 인증 필요 - 403: 권한 없음 - 적절한 에러 메시지

핵심 정리

  • SSO - 한 번 로그인으로 여러 서비스 이용 (같은 회사)
  • OAuth 2.0 - 외부 서비스에 제한된 권한 위임 (다른 회사)
  • JWT - Header.Payload.Signature 구조의 자체 포함 토큰
  • Access Token - 짧은 수명, API 호출용
  • Refresh Token - 긴 수명, Access Token 재발급용
  • 서명 검증 - 비밀키로 위변조 탐지
  • 게임 서버 - 토큰 검증, 캐싱, 갱신 처리 담당
