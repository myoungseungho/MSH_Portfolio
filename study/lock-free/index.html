스레드 셋이 같은 숫자를 동시에 +1 하면? — 락 vs 락프리(CAS)

레이스 컨디션을 눈으로 보고, 락프리가 '자물쇠 없이' 어떻게 안 깨지는지(CAS 재시도 루프)까지 인터랙티브로

30초 요약

보호 없이 여러 스레드가 같은 값을 '읽고 → 계산하고 → 쓰기' 하면 한쪽 결과가 덮여 사라져(레이스 컨디션).

락 = 자물쇠로 한 번에 한 명(안전하지만 줄서기·데드락 위험). 락프리 = 자물쇠 없이 CAS로 '충돌하면 다시 시도'(막힘 없음).

우리 게임 서버는 아예 싱글스레드(액터 1마리)라 이 고민 자체가 없어 — 제일 단순한 해법.

Part 1. 왜 증가가 사라지나 (레이스 컨디션)

맞춰봐 — HP 100을 스레드 A가 -30, B가 -50 동시에 했어. 결과는?

'20'이라고 생각했지? 실제론 70이거나 50이 될 수 있어.

둘 다 '100'을 동시에 읽고, A는 손에서 70을 만들고 B는 50을 만들어. 그리고 각자 자기 값을 써 — 나중에 쓴 값이 앞 걸 덮어버려. 한쪽 연산이 통째로 사라지는 거야. 이게 레이스 컨디션(경쟁 상태)이야.

왜 그런 일이 생겨?

'읽기 → 계산 → 쓰기'가 한 덩어리(원자적)가 아니라서 그래. 그 사이에 다른 스레드가 끼어들면 둘이 같은 출발값(100)을 보게 돼.

그래서 이 구간(임계영역)을 어떻게든 '한 번에 하나만' 또는 '끼어들면 다시' 하도록 보호해야 해. 아래에서 직접 봐.

Part 2. 락(자물쇠) — 안전하지만 줄서기

제일 쉬운 해법은?

공용 화장실에 자물쇠를 다는 거야. 한 명 들어가면 잠그고, 나머지는 밖에서 줄 서서 기다려. 임계영역을 한 번에 한 명만 지나가니 절대 안 깨져. 이게 락(Mutex/CriticalSection)이야.

그럼 락이 정답 아냐? 뭐가 문제인데?

두 가지가 걸려.

Q. 첫째 — 사람이 많으면?

A. 다들 밖에서 줄만 서. 스레드를 아무리 늘려도 한 번에 하나씩만 통과하니 처리량이 천장에 막혀(Part 4에서 눈으로 봄).

Q. 둘째 — 안에 있는 사람이 기절하면?

A. 나머지 전원이 영원히 못 들어가. 게다가 자물쇠를 두 개 엇갈려 잡으면(A가 1번 잠그고 2번 기다림, B가 2번 잠그고 1번 기다림) 서로 영원히 대기 — 데드락(교착)이야.

Part 3. 락프리 — 자물쇠 없이 어떻게? (CAS)

자물쇠를 안 달면 안 깨지는 걸 어떻게 보장해?

CAS(Compare-And-Swap, 비교 후 교체)라는 하드웨어가 보장하는 특수 명령을 써. 초딩 버전으로 3단계야:

1. 읽기: 지금 창고값을 손에 복사(예: 100)

2. 계산: 손에서 +1 (101)

3. 비교교체(CAS): "창고값이 아직도 100 맞아? 맞으면 101로 바꿔치기"

포인트는 3번이 '확인'과 '교체'를 쪼갤 수 없는 한 방(원자적)에 한다는 것. 확인하는 찰나에 남이 끼어들 수 없어.

근데 3번에서 '아직 100이 아니면'? 남이 먼저 바꿨으면?

그럼 CAS가 실패해. "앗, 100이 아니라 101이네 — 누가 먼저 넣었구나." 그러면 1번으로 돌아가 새 값(101)으로 다시 시도해. 이게 재시도 루프야.

Q. 줄 서서 기다리는 락이랑 뭐가 달라?

A. 락은 남이 끝날 때까지 멈춰서 기다려. CAS는 안 멈추고 계속 재도전해 — 그래서 누가 기절해도 나머지는 계속 진행돼(막힘 없음). 대신 부딪히면 헛수고(재시도)가 생기지. 아래에서 직접 돌려봐 ↓

Part 4. 락 vs 락프리 — 스레드가 늘면 처리량은?

그럼 락프리가 항상 더 빠른 거야?

경향은 그렇지만 항상은 아냐. 아래에서 스레드 수를 올려봐.

• 락: '한 번에 하나'라 스레드를 늘려도 처리량이 천장에 막혀(다 줄만 섬).

• 락프리: 막힘이 없어 더 잘 늘어. 하지만 경합이 세지면 재시도(헛수고)가 폭증해서 이득이 깎여.

📈 락 vs 락프리 — 스레드가 늘면?

스레드 수를 올려봐. 락은 '한 번에 하나'라 늘려도 처리량이 천장에 막히고(줄서기), 락프리는 더 잘 늘어. 단, 경합이 세지면 재시도 낭비도 같이 커져. (예시 모델값)

Part 5. 그래서 우리 서버는?

락프리가 이렇게 좋은데 우리도 게임 로직에 써야 해?

아니. 우리 서버는 아예 싱글스레드(액터 1마리)로 가서 '락도 CAS도 없는' 길을 택했어.

이유 — 게임 로직은 'HP 깎고 + 아이템 주고 + 로그 남기고'를 한꺼번에 원자적으로 바꿔야 하는데, 단순 CAS는 값 하나만 원자 교체할 수 있어. 여러 값을 묶어 안전하게 바꾸려면 CAS로는 지옥이야. 그래서 처리를 한 줄로 세워 동시성 자체를 없앤 거지(→ 액터 모델 글).

락프리는 만들기가 왜 그렇게 어렵다는 거야?

대표 함정이 ABA 문제야. 값이 A→B→A로 돌아오면, CAS는 '어 아직 A네' 하고 그 사이 변화를 눈치 못 채. 겉값만 같고 속은 바뀐 거지.

여기에 메모리 순서(memory ordering) — CPU가 명령 순서를 제멋대로 바꿔 실행하는 것까지 통제해야 해서, '락프리 짜봤다'는 건 동시성·CPU·메모리 모델을 아주 깊이 안다는 뜻이야. 그래서 공고 우대사항에 콕 집는 거고.

Part 6. 원자적으로 검사하는데 왜 ABA가 문제야?

CAS가 원자적으로 '아직 A야?'를 검사하잖아. 그 사이 변화를 놓쳐도 항상 검사하니 문제없는 거 아냐?

여기가 딱 함정이야. CAS는 '값'을 비교하지, '변화 여부'를 비교하지 않아.

"값이 A랑 같다"는 "그동안 아무것도 안 바뀌었다"가 아니야. 값이 A → B → A 로 돌아왔으면, CAS는 "어 A네, 그대로네" 하고 성공해버려. 실제론 세상이 바뀌었다 돌아온 건데.

근데 카운터에서 5→6→5로 돌아와도 5에 CAS 성공하는 건 맞는 결과 아냐?

맞아! 단순 숫자면 ABA는 대체로 무해해. 결과값이 맞으니까.

문제는 '값'이 '포인터(메모리 주소)'일 때야. 주소가 재사용되면 같은 주소가 완전히 다른 것을 가리켜. '값(주소)은 같은데 의미는 딴판'인 상황이 생기는 거지. 아래 스택 예시로 직접 봐 ↓

요점: 락은 이런 걸 신경 쓸 필요가 없는데, 락프리는 이걸 다 직접 처리해야 해서 어려운 거야.

Part 7. 메모리 순서 — 원자적인데 순서가 안 맞는다?

각 연산이 원자적이면, 순서 문제는 없는 거 아냐?

이것도 함정이야. 원자성(한 연산이 안 쪼개짐) ≠ 가시성 순서(남이 내 연산들을 무슨 순서로 보느냐).

CPU와 컴파일러는 성능을 위해 명령 순서를 제멋대로 재배치해. 예를 들어:

쓰는 쪽: data = 42; 그다음 ready = true;

읽는 쪽: if (ready) use(data);

의도는 'data 먼저 쓰고 ready 켜기'지만…

ready가 켜졌으면 data는 당연히 42 아냐?

아니야. CPU가 두 쓰기의 순서를 뒤집거나, 읽는 쪽 CPU가 (캐시·스토어 버퍼 때문에) ready=true를 data=42보다 먼저 볼 수 있어. 그럼 읽는 쪽은 ready는 true인데 data는 아직 옛값(0, 쓰레기)을 읽어. 아래에서 직접 재현해봐 ↓

락은 왜 이 문제가 없어?

락은 acquire(잠글 때)/release(풀 때)에 메모리 배리어가 내장돼 있어 — 임계영역 안 쓰기는 반드시 락 풀기 전에 남에게 보이도록 순서를 강제해. 그래서 우리가 신경 안 써도 됐어.

락프리는 네가 직접 메모리 배리어/오더링(acquire·release·seq_cst)을 정확히 심어야 해. 하나만 틀려도 어쩌다 한 번 터지는 '유령 버그'가 나. ABA + 이 메모리 순서 — 이 둘 때문에 '락프리 짜봤다'가 동시성·CPU·메모리 모델을 깊이 안다는 뜻인 거야.

Part 8. 메모리 배리어는 어떻게 순서를 강제하나 — 원리와 방법

그 '재배치'는 대체 어디서 생기는 거야?

두 군데서 나와:

1. 컴파일러: 최적화하면서 명령 순서를 바꿔(의존성 없어 보이면).

2. CPU: 이게 더 미묘해. 코어가 쓰기를 메모리에 바로 안 넣고 '스토어 버퍼'에 잠깐 쟁여둬(그래야 안 기다리고 다음 명령 진행). 그래서 다른 코어는 그 쓰기를 늦게 보거나, 여러 쓰기의 도착 순서가 뒤바뀌어 보여. 앞의 data/ready 사고가 바로 이거야.

그럼 배리어가 기계 수준에서 정확히 뭘 하는데?

배리어(fence)는 특수 CPU 명령이야. 두 가지를 강제해:

1. 재배치 금지선: "이 선을 넘어 메모리 연산을 옮기지 마" — 컴파일러·CPU 둘 다에게.

2. 스토어 버퍼 flush: 쌓아둔 쓰기를 순서대로 메모리에 밀어내 다른 코어가 보게 함.

종류도 있어 — 쓰기용(sfence), 읽기용(lfence), 둘 다(mfence / ARM은 dmb). 아래 위젯에서 버퍼가 비워지며 순서가 맞춰지는 걸 봐 ↓

🧱 스토어 버퍼와 배리어 — 순서를 강제하는 원리

CPU는 쓰기를 바로 메모리에 안 넣고 '스토어 버퍼'에 잠깐 쟁여둬(그래서 다른 코어가 늦게 봄). ▶ 실행으로 배리어 없을 때와 있을 때 다른 코어가 무엇을 보는지 비교해봐.

그럼 실무에선 배리어 명령을 직접 박아? 어떻게 써?

보통 어셈블리 fence를 직접 쓰진 않고, acquire/release 짝으로 표현해:

• release(쓸 때): "이 쓰기 이전의 모든 쓰기를, 이 값을 acquire로 읽는 쪽이 다 보게 하라"

• acquire(읽을 때): "이 읽기 이후의 연산은 이 값을 본 뒤에 일어나게 하라"

release-acquire 짝이 '먼저 일어남(happens-before)' 다리를 놓아 — 읽는 쪽이 release된 값을 acquire로 보면, 쓰는 쪽이 그 전에 한 일(data=42)을 반드시 보게 돼. C++ 코드로는:

// 쓰는 쪽 data = 42; // 일반 쓰기 ready.store(true, std::memory_order_release); // ← release: 위 data=42 를 먼저 보이게 // 읽는 쪽 if (ready.load(std::memory_order_acquire)) // ← acquire: 이 뒤 읽기를 뒤로 고정 use(data); // data=42 를 반드시 봄 (release-acquire 짝) // 참고: 강도 순서 // relaxed : 원자적이지만 순서 보장 없음 (순서 무관한 카운터용) // acquire/release : 위 짝 — 필요한 곳만 정확히 (빠름) // seq_cst : 전역 단일 순서, 가장 강하고 단순하지만 느림 (기본값)
memory_order 보장 비용 쓰는 곳
relaxed 원자성만 (순서 X) 최저 순서 무관 카운터
acquire/release 해당 값 기준 happens-before 중 깃발/락프리 큐
seq_cst 전역 총순서 최고 확신 없을 때 안전빵(기본)
그냥 volatile 붙이면 되는 거 아냐?

아니야, 흔한 오해. C++의 volatile은 메모리 배리어도, 원자성도 제공하지 않아 — 컴파일러가 '캐시하지 말고 매번 읽어라' 정도(주로 하드웨어 레지스터용)일 뿐, CPU 재배치·스토어 버퍼는 못 막아. (Java의 volatile은 배리어를 주지만 C++은 달라.)

트레이드오프: seq_cst는 안전하고 단순하지만 fence 비용이 커 느려. relaxed는 빠르지만 네가 순서를 직접 다 증명해야 해. '어디에 어떤 강도의 배리어를 넣느냐'를 정확히 판단하는 것 — 이게 락프리가 어려운 진짜 이유야. ABA + 이 메모리 오더링을 다 통제해야 하니까.

핵심 정리

  • 레이스 컨디션 = '읽기-계산-쓰기'가 원자적이 아니라 한쪽 결과가 덮여 사라짐
  • 락 = 자물쇠로 한 번에 하나(정확, 줄서기·데드락 위험)
  • 락프리(CAS) = 읽기→계산→비교교체, 충돌 시 재시도(막힘 없음, 경합 심하면 재시도 폭증)
  • CAS의 비밀 = '확인+교체'를 쪼갤 수 없는 한 방(원자적)에 → 확인하는 찰나 끼어들 수 없음
  • 싱글스레드(액터) = 락도 CAS도 없음 — 우리 서버의 선택(1코어 천장은 샤딩으로)
  • 락프리는 만능 아님 — 다중 값 원자 처리 부적합 + ABA/메모리순서 함정
