SQL Injection - 클라이언트가 DB를 해킹하는 법

1. 클라이언트가 DB에 접근도 못 하는데?

우리 게임은 이런 구조잖아. 클라이언트가 DB를 직접 건드릴 수 없는데 어떻게 SQL 해킹이 가능해?
📱 클라이언트 (플레이어)
⬇️ 패킷
🖥️ 게임 서버
⬇️ SQL 쿼리
💾 DB 서버

정확해! 클라이언트는 DB를 직접 건드릴 수 없어.

하지만 클라이언트가 보낸 "데이터"는 서버의 SQL 쿼리에 들어가잖아?

바로 그게 문제야.

데이터가 SQL에 들어간다고? 무슨 말이야?

예를 들어, 로그인 시스템을 생각해봐:

1. 플레이어가 아이디 "admin", 비밀번호 "1234" 입력 2. 클라이언트 → 서버: { id: "admin", pw: "1234" } 패킷 전송 3. 게임 서버가 SQL 쿼리 생성: SELECT * FROM users WHERE id = 'admin' AND password = '1234' 4. DB가 결과 반환 → 로그인 성공/실패

보이지? 클라이언트가 보낸 값(admin, 1234)이 SQL 쿼리에 그대로 들어가.

그게 뭐가 문제야? 당연한 거 아니야?

만약 해커가 비밀번호에 이걸 입력하면?

비밀번호: 1234' OR 1=1--

서버가 만드는 SQL 쿼리는:

SELECT * FROM users WHERE id = 'admin' AND password = '1234' OR 1=1--'

OR 1=1은 항상 참이야.
--는 SQL 주석이라 뒤는 무시돼.

결과: 비밀번호 몰라도 로그인 성공! 💥

2. 단계별로 뜯어보자

왜 OR 1=1이 항상 참이야?

SQL WHERE 조건을 생각해봐:

WHERE (password = '1234') OR (1=1)

OR는 둘 중 하나만 참이면 돼.

- password가 틀려도 (거짓)
- 1=1은 무조건 참 (True)
- 거짓 OR 참 = 참!

--는 뭐야?

SQL에서 --는 주석이야. 뒤에 나오는 내용을 무시해.

SELECT * FROM users WHERE id = 'admin' AND password = '1234' OR 1=1--' ↑ 이 부분 무시됨

원래 쿼리의 끝에 있던 ' (따옴표)가 주석 처리돼서 에러가 안 나.

🚪 비유: 출입 통제

정상적인 통제: "비밀번호 맞으면 들어가"
- 조건: password = '1234'

SQL Injection 후: "비밀번호 맞으면 들어가 또는 1=1이면 들어가"
- 조건: password = '1234' OR 1=1
- 1=1은 무조건 참 → 누구나 들어감

3. 게임 서버에서 실제로 일어나는 일

게임에서는 어떻게 써먹을 수 있어?

예시 1: 아이템 검색

❌ 취약한 코드 (C++ 예시): string itemName = packet->itemName; // 클라이언트가 보낸 값 string query = "SELECT * FROM items WHERE name = '" + itemName + "'"; _dbConn->Execute(query.c_str());

해커가 보내는 패킷:

itemName: "Sword' OR price = 0--"

실제 실행되는 쿼리:

SELECT * FROM items WHERE name = 'Sword' OR price = 0--'

결과: 가격이 0원인 모든 아이템 조회 가능!

그럼 아이템을 훔칠 수도 있어?

예시 2: 아이템 추가

❌ 취약한 코드 (C++): string characterName = packet->characterName; string query = "INSERT INTO inventory (character, item) VALUES ('" + characterName + "', 'Potion')"; _dbConn->Execute(query.c_str());

해커가 보내는 패킷:

characterName: "Hacker', 'LegendSword'); --"

실제 실행되는 쿼리:

INSERT INTO inventory (character, item) VALUES ('Hacker', 'LegendSword'); --', 'Potion')

결과: 레전더리 검을 인벤토리에 추가!

⚠️ 더 위험한 공격

DELETE, DROP 같은 명령어도 가능해:

username: "admin'; DROP TABLE users; --"

→ 유저 테이블 전체 삭제 💀

4. 어떻게 막아?

그럼 클라이언트 입력값을 믿으면 안 되는 거야?

정답! 클라이언트 입력은 절대 신뢰하지 마.

방어 방법 1: Prepared Statement (파라미터 바인딩)

Prepared Statement가 뭐야?

SQL 쿼리와 데이터를 분리하는 거야.

✅ 안전한 코드 (C++ MySQL): string itemName = packet->itemName; string query = "SELECT * FROM items WHERE name = ?"; auto stmt = _dbConn->PrepareStatement(query); stmt->setString(1, itemName); // 1번 파라미터에 바인딩 stmt->executeQuery();

무슨 일이 일어나?

1. SQL 쿼리 템플릿: "WHERE name = ?" 2. ?는 "값이 들어갈 자리"라고 DB에 알림 3. itemName 값은 "순수한 데이터"로 전달 4. DB가 알아서 이스케이프 처리

해커가 Sword' OR 1=1--을 보내도:

WHERE name = 'Sword'' OR 1=1--' ↑ 자동으로 ' → '' 이스케이프됨 (문자 그대로 검색됨, SQL로 해석 안 됨)

방어 방법 2: ORM 사용

ORM이 뭐야?

Object-Relational Mapping - SQL을 직접 안 쓰고 코드로 쿼리를 만드는 거야.

✅ 안전한 코드 (C++ sqlpp11 ORM): string itemName = packet->itemName; auto items = db(select(all_of(tab)) .from(tab) .where(tab.name == itemName)); // 또는 Prepared Statement 직접 사용 auto stmt = _dbConn->PrepareStatement("SELECT * FROM items WHERE name = ?"); stmt->setString(1, itemName);

C++에서는 Prepared Statement를 직접 쓰는 게 일반적이야.
ORM보다는 명시적으로 파라미터 바인딩하는 걸 추천해.

방어 방법 3: 입력값 검증

그래도 혹시 모르니까 입력값을 체크하면 안 돼?

당연히 해야 해! 하지만 이것만으로는 부족해.

✅ 추가 방어 (C++): // 1. 길이 체크 if (itemName.length() > 50) return; // 2. 특수문자 거부 if (itemName.find('\'') != string::npos || itemName.find("--") != string::npos) return; // 3. 화이트리스트 방식 (정규식) regex pattern("^[a-zA-Z0-9_]+$"); if (!regex_match(itemName, pattern)) return;

주의: 이건 보조 수단일 뿐이야.
Prepared Statement가 기본이고, 입력 검증은 추가 방어야.

5. 실전 비교표

방법 안전성 장점 단점
문자열 연결
(+ 연산자)		 🔴 매우 위험 간단함 SQL Injection 취약
입력값 검증만 🟡 불완전 추가 방어선 우회 가능
Prepared Statement 🟢 안전 완벽한 방어 코드가 약간 길어짐
ORM 🟢 안전 간결한 코드 학습 필요, 성능 오버헤드
Prepared + 검증 🟢🟢 매우 안전 다층 방어 개발 시간 증가

📌 핵심 정리: SQL Injection

  • SQL Injection이란? - 클라이언트가 보낸 입력값이 SQL 쿼리에 들어가서 DB를 조작하는 공격
  • 왜 가능? - 클라이언트가 DB에 직접 접근하는 게 아니라, 서버가 만드는 SQL에 클라이언트 값이 들어가기 때문
  • 공격 원리 - 'OR 1=1-- 같은 특수 문자로 SQL 문법을 변조
  • 방어 1: Prepared Statement - SQL과 데이터를 분리, DB가 자동으로 이스케이프 처리
  • 방어 2: ORM - SQL을 직접 안 쓰고 코드로 쿼리 생성
  • 방어 3: 입력 검증 - 길이/특수문자 체크 (보조 수단)
  • 철칙 - 클라이언트 입력값을 절대 신뢰하지 말 것

🔍 더 깊이 알고 싶다면?

NoSQL(MongoDB 같은)은 SQL Injection이 없어?

아니야, NoSQL Injection도 있어!

// MongoDB 예시 db.users.find({ username: userInput }) // 해커가 보내는 값: userInput: { $ne: null } // "null이 아닌 모든 유저" // 결과: db.users.find({ username: { $ne: null } }) → 모든 유저 조회!

해결책: NoSQL도 입력 검증 + ORM(Mongoose 등) 사용해야 해.

Prepared Statement가 느리지 않아?

옛날에는 그랬어. 하지만 지금은:

1. DB가 쿼리 플랜을 캐싱함 2. 같은 쿼리가 반복되면 재사용 3. 오히려 문자열 연결보다 빠를 수 있음

성능보다 보안이 훨씬 중요해.
해킹당하면 게임이 망해.
