왜 에이전트에게 직군을 그대로 시키면 멈출까?

게임회사 업무를 AI 실행 단위로 환원하는 제일 원리

Part 1. 직군을 복제하면 왜 바로 안 굴러갈까?

클라이언트, 서버, DB, 아트, 애니 직군 에이전트를 각각 두면 회사처럼 돌아가야 하는 거 아니야?

겉보기엔 맞아 보이지만, 실제로는 자주 멈춰.

이유는 간단해. 인간 직군 설명에는 암묵지(말로 적지 않았지만 팀이 관성으로 아는 룰)가 많고, 에이전트는 명시된 계약(입력/출력/검증이 문서로 적힌 규칙) 없이는 실행을 못 해.

직군명은 역할이고, 에이전트는 실행 단위가 필요해.

같은 지시문 사람 팀 에이전트 팀
"전투를 더 재밌게 해줘" 경험으로 맥락 보완 후 진행 해석 분기 후 충돌 가능
결정 기준 회의/관계/관성으로 수렴 명시된 기준 없으면 정지
완료 판정 "대충 됐다" 합의 가능 검증 규칙 없으면 무한 반복

시각화: 직군 이름만 복제한 상태

역할은 많아 보이지만, 핸드오프 규칙이 없어 병목이 생김

지금까지 한 줄 요약: 직군 이름이 아니라 실행 계약이 있어야 에이전트 협업이 돌아간다.

Part 2. 근본 문제는 어디에 있을까?

그럼 진짜 막히는 지점은 뭐야?

거의 항상 세 가지야.

1) 입력이 모호함, 2) 완료 조건이 없음, 3) 다음 담당자가 불명확함.

이 세 개가 빠지면 에이전트는 "생산성 높은 착각"만 만들고 끝나.

택배 분류 비유

"택배 빨리 보내"는 지시만 있으면 분류장이 마비돼.
어느 지역으로, 언제까지, 누가 인수하는지 라벨이 있어야 실제로 흐름이 생겨.
업무 실패의 80%는 기술이 아니라 계약 누락에서 발생: - Input : 어떤 데이터로 시작? - Output : 어떤 산출물이 완료? - Constraint : 시간/비용/품질 한도? - Check : 누가 무엇으로 검증? - Handoff : 다음 주체는 누구?
누락된 요소 에이전트에서 생기는 현상
입력 정의 없음 서로 다른 가정으로 병렬 작업 후 충돌
완료 기준 없음 반복 수정 루프에 갇힘
인수 조건 없음 다음 에이전트가 작업 거부 또는 재작업

시각화: 모호한 지시의 누수

단계마다 정보가 새면 마지막 결과는 처음 의도와 멀어짐

지금까지 한 줄 요약: Input/Output/Check/Handoff 중 하나라도 빠지면 자동화는 누수된다.

Part 3. 제일 원리: 업무는 역할이 아니라 상태 전이다

그럼 사람의 직무를 에이전트 작업으로 어떻게 환원해야 해?

업무 = 상태 변경 + 검증 가능한 증거로 바꾸면 돼.

"클라이언트 개발"이 아니라 "입력 지연 120ms→60ms" 같은 상태 목표로 정의하는 거야.

[Task Contract v1] Input: Output: Constraint: Check: Handoff: 이게 전부야.
항목 10초 정의 안 쓰면 생기는 일
Input (입력) 작업 시작에 필요한 데이터 사람마다 다른 가정으로 시작
Output (산출물) 작업이 끝났다고 볼 결과물 끝났는지 판정 불가
Constraint (제약) 시간/비용/품질 한도 좋아 보여도 예산 초과
Check (검증) 통과/실패를 가르는 테스트 느낌으로 승인되어 품질 흔들림
Handoff (인수) 다음 담당자에게 넘기는 형식 다음 단계에서 재작업 발생
진짜 이 다섯 줄이면 충분해?

충분해. 이 다섯 줄이 있으면 에이전트는 추측 대신 실행한다.

직군 언어를 실행 계약 언어로 치환하는 핵심 포맷이야.

인간 중심 표현 에이전트 실행 표현
"전투 밸런스 맞춰줘" Input(로그), Output(파라미터 diff), Check(KPI 기준)
"서버 안정화해줘" Output(P99 220ms→150ms), Check(부하테스트 리포트)
"아트 퀄리티 올려줘" Constraint(메모리/드로우콜), Check(씬 예산 통과)

시각화: 역할에서 계약으로 환원

모든 직군 작업을 같은 계약 형식으로 바꾸면 자동화가 가능해짐

지금까지 한 줄 요약: 업무를 "역할"이 아닌 "검증 가능한 계약"으로 바꿔야 실행된다.

Part 4. 직군별 일을 어떤 단위로 치환할까?

클라/서버/DB/아트/애니는 성격이 다른데, 진짜 같은 원리로 다룰 수 있어?

도메인은 달라도 실행 타입은 비슷해.

대부분 분석(Analyze) → 생성(Build) → 검증(Verify) → 인수(Handoff) 4단계로 귀결돼.

단계 10초 정의 왜 필요
Analyze (분석) 문제 원인과 현재 상태를 숫자로 파악 원인 모르면 패치가 운빨이 됨
Build (생성) 수정안/산출물을 실제로 만듦 아이디어만 있고 결과물이 없음
Verify (검증) 테스트 기준으로 통과/실패 판단 "좋아 보임" 착각으로 품질 흔들림
Handoff (인수) 다음 단계에서 바로 쓸 수 있게 전달 다음 담당자가 다시 분석부터 시작
직군 에이전트로 치환한 기본 작업 완료 증거
클라이언트 프레임 타임 분석, 입력 반응 수정 프레임/지연 측정 로그
서버 병목 탐지, 동시성 패치, 부하 실험 P95/P99 레이턴시 리포트
DB 쿼리 플랜 분석, 인덱스 실험 쿼리 시간 Before/After
아트/애니 예산 체크, 룩 가이드 일치 검사 메모리/드로우콜/리그 규칙 통과
무인 공장 비유

작업자 이름이 중요한 게 아니라 공정표가 중요해.
"용접팀"보다 "A부품이 B정밀도 통과 후 C라인으로 이동"이 자동화에 필요한 언어야.
추천 멀티 에이전트 구조: 1) Planner: 계약 생성/우선순위 2) Specialist: 계약 실행 3) Critic: 검증과 반려 4) Integrator: 머지와 릴리즈
역할 초보자 설명 없으면 생기는 문제
Planner 무엇을 먼저 할지 정하는 스케줄러 중요하지 않은 일부터 처리
Specialist 실제 산출물을 만드는 작업자 계획만 있고 실행이 없음
Critic 통과/실패를 판정하는 검사자 불량 결과가 다음 단계로 넘어감
Integrator 통과한 결과를 합쳐 배포하는 역할 각자 만든 결과가 분리되어 방치

시각화: Planner-Executor-Critic-Integrator

역할 분리가 아니라 검증 루프 분리가 핵심

지금까지 한 줄 요약: 직군이 달라도 실행 단계와 검증 루프는 공통 템플릿으로 통일할 수 있다.

Part 5. 자는 동안 협업하게 만들려면?

내가 자는 동안에도 에이전트들이 서로 일하게 하려면 무엇부터 고정해야 해?

밤 자동화는 세 가지가 전부야.

1) 고정된 큐, 2) 실패 시 안전 정지, 3) 아침 리포트.

WIP Limit, Validation Gate 같은 말이 어렵게 느껴져. 쉽게 말하면?

WIP Limit (Work In Progress Limit)은 동시에 벌릴 작업 개수 제한이야. 왜 필요해? 멀티태스킹 과부하를 막기 위해서야. 안 쓰면 시작만 많고 완료가 없다.

Validation Gate는 "테스트 통과한 것만 다음으로" 넘기는 문이야. 왜 필요해? 불량이 연쇄 전파되는 걸 막기 위해서야. 안 쓰면 새벽에 실패가 누적된다.

운영 요소 없을 때 있을 때
WIP Limit
(동시 작업 상한)		 작업 20개 동시 착수 후 전부 미완료 동시 3개만 처리, 완료율 상승
Validation Gate
(검증 통과 문)		 오류 상태로 연쇄 실행 테스트 실패 시 다음 단계 차단
Morning Brief
(아침 요약)		 무엇이 됐는지 파악 불가 변경/실패/보류가 한 번에 정리
[Night Runbook 22:00~06:00] 22:00 Planner가 작업 큐 확정 (최대 12개) 22:10 Specialist 병렬 실행 (WIP=3) 01:00 Critic 검증, 실패 작업 자동 반려 03:00 Integrator가 통과분만 통합 06:00 아침 요약 리포트 생성
그럼 완전 자율로 돌려도 괜찮아?

완전 자율은 금물.

고위험 작업(데이터 삭제, 결제, 보안 설정)은 Human Approval Gate를 남겨야 해.

시각화: 야간 자동 실행과 안전 정지

진행 루프와 승인 게이트를 분리하면 밤에도 안정적으로 실행 가능

지금까지 한 줄 요약: 밤 자동화는 "작업 수 제한 + 실패 차단 + 아침 요약" 3개 규칙으로 안정화된다.

Part 6. 결국 무엇을 공부해야 영감이 생길까?

직군 지식 말고, 에이전트 협업 설계를 위해 꼭 알아야 할 핵심 개념은 뭐야?

아래 6개만 먼저 잡으면 충분해.

RACI, Definition of Done, Interface Contract, WIP Limit, Validation Gate, Postmortem Loop

용어 10초 정의 왜 필요해? 안 쓰면?
RACI
(Responsible, Accountable, Consulted, Informed)		 누가 실행/최종책임/자문/공유 대상인지 역할 분리 표 책임 경계를 명확히 해서 충돌을 줄임 "이건 누가 결정해?" 상태로 정지
Definition of Done
(완료 정의)		 작업이 끝났다고 판단하는 체크 조건 완료 판정 기준을 통일하기 위해 끝났는지에 대한 논쟁이 반복됨
Interface Contract
(인터페이스 계약)		 모듈 간 입력/출력 형식을 고정한 약속 팀 간 연결 부위를 안정화하기 위해 연동 단계에서 대량 재작업
WIP Limit
(동시 작업 상한)		 동시에 벌릴 수 있는 작업 수 제한 완료율을 올리고 멀티태스킹 손실을 줄임 시작만 많고 끝난 일이 없음
Validation Gate
(검증 통과 문)		 테스트 통과분만 다음 단계로 넘기는 규칙 불량 결과의 연쇄 전파 차단 실패가 누적되어 새벽에 붕괴
Postmortem Loop
(사후 분석 루프)		 실패 원인을 기록하고 다음 규칙으로 반영 같은 실패를 반복하지 않기 위해 매주 같은 장애가 반복됨
여전히 어려운데, 한 문장으로 묶어주면?

RACI는 "누가", DoD는 "언제 끝", Interface Contract는 "무엇을 주고받는지"를 고정한다.

WIP Limit은 "몇 개를 동시에", Validation Gate는 "무엇이 통과인지", Postmortem Loop는 "실패를 다음 규칙으로" 바꾼다.

인간 직무 이해 -> 에이전트 작업 환원 -> 자동 실행 (무엇) (어떻게) (지속) 핵심은 제일 원리: "업무를 역할이 아니라 검증 가능한 상태 전이로 정의한다."

이 원리를 쓰면 직군이 늘어나도 방식은 같아진다.

그래서 클라/서버/DB/아트/애니를 하나의 운영 언어로 묶을 수 있어.

지금까지 한 줄 요약: 6개 용어는 "누가, 언제 끝, 무엇 연결, 몇 개 동시, 무엇 통과, 실패를 어떻게 학습"을 고정하는 장치다.

📌 핵심 정리: 에이전트 협업의 제일 원리

  • 직군명은 역할이고, 자동화는 실행 계약이 필요하다
  • 근본 실패 원인은 Input/Check/Handoff 누락이다
  • 업무 환원 공식: 상태 변경 + 검증 가능한 증거
  • 공통 작업 단위: Analyze → Build → Verify → Handoff
  • 야간 자동화 핵심: 큐, 실패 게이트, 아침 리포트
  • 최종 원리: 역할 중심 사고를 상태 전이 중심 사고로 치환하라
