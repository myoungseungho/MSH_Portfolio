서버 3대가 "누가 리더야?"를 정하는 법

Raft 합의 알고리즘 - 분산 시스템에서 리더를 선출하는 원리

Part 0. 잠깐, 우리는 서버 1대인데 이게 왜 필요해?

우리 MMORPG는 단일 서버로 잘 돌아가는데, 리더 선출이 뭔 소리야?

맞아. 중소 규모 MMORPG는 대부분 폐쇄형 단일 서버로 운영해.

게임 서버 1대, DB 서버 1대. 이게 왜 안 되겠어?

근데 문제는... 너만 서버 1대인 게 아니라는 거야.

🏢 "우리 서버"만 보면: [클라이언트] ──▶ [게임 서버 1대] ──▶ [DB 서버 1대] → 심플하고 좋아! 리더 선출? 그게 뭔데? 🤷 🌐 근데 실제로 쓰는 인프라를 보면: [클라이언트] │ ▼ [게임 서버 1대] │ ├──▶ [Redis Cluster 3대] ← 얘네 중 리더 있음 ├──▶ [MySQL + Replica 2대] ← 얘네 중 마스터 있음 └──▶ [etcd 3대 for 설정] ← 얘네 중 리더 있음 → 너도 모르게 분산 시스템 쓰고 있었어!
Redis Cluster? 난 그냥 Redis 1대 쓰는데?

지금은 그럴 수 있어. 근데 이런 상황 생각해봐:

🔮 언젠가 마주칠 상황들: 1️⃣ "Redis 서버 죽었는데 게임 서버도 같이 뻗었어요" → Redis Sentinel이나 Cluster 도입 검토 → 그때 "리더 선출"이 뭔지 알아야 설정 가능 2️⃣ "동접 5천 넘으니까 DB가 버텨요" → MySQL Master-Slave 구성 검토 → "마스터가 죽으면 슬레이브가 승격"이 리더 선출이야 3️⃣ "서버 설정을 실시간으로 바꾸고 싶어요" → etcd, Consul 같은 설정 서버 도입 → 얘네 전부 Raft 기반이야 4️⃣ "서버 2대로 늘려서 이중화하고 싶어요" → 두 서버 중 누가 "진짜"인지 정해야 함 → 이게 바로 리더 선출 문제
아... 나중에 필요할 수 있다는 거지?

그것보다 더 중요한 게 있어.

장애 상황을 이해하려면 이 개념이 필요해.

🚨 실제 장애 상황: "새벽 3시에 Redis 클러스터 알람 떴는데, '마스터 노드 재선출 중'이라고 뜨면서 5분간 접속 안 됨" 리더 선출 모르면: → "뭔 소리야? 재시작 해볼까?" (악화될 수 있음) → "개발사한테 문의해야겠다" (새벽 3시에?) 리더 선출 알면: → "아, 3대 중 1대가 죽어서 재선출 중이구나" → "과반수(2대) 살아있으니까 잠시 기다리면 복구되겠네" → "로그에서 Term 번호 확인해서 정상 선출됐는지 보자"

💡 이 문서를 읽는 이유

지금 당장 Raft를 구현할 일은 없어.

하지만 Redis Cluster, MySQL Replication, etcd, Consul 같은 도구를 쓸 때,

"왜 3대를 권장하지?", "마스터가 뭐지?", "페일오버가 뭐지?" 라는 질문에 답할 수 있게 돼.

그리고 장애 로그를 읽을 수 있게 돼. 이게 진짜 가치야.

Part 1. 왜 리더가 필요해?

서버 여러 대면 그냥 각자 일하면 안 돼?

게임 서버에서 길드 금고를 생각해봐.

서버 A: "길드 금고에 100골드 있음"

서버 B: "길드 금고에 150골드 있음"

누가 맞아? 충돌이 생겨.

🤔 리더 없이 3대가 각자 결정하면? 서버 A: "길드 금고 100골드" 서버 B: "길드 금고 150골드" ← 유저가 B에서 50골드 입금 서버 C: "길드 금고 100골드" → 누구 말이 맞아? 🤷 → 유저마다 다른 금고 잔액을 봄 → 대혼란!
그래서 리더가 뭘 해?

리더 = 최종 결정권자

모든 변경은 리더를 통해서만 이루어져.

리더가 "100골드 → 150골드"라고 하면, 다른 서버도 따라가.

👑 리더가 있으면? [유저] ──입금 50골드──▶ [리더 A] │ ▼ "100 → 150 확정" ┌────┴────┐ ▼ ▼ [B: 150] [C: 150] → 모든 서버가 같은 값! → 어느 서버에 접속해도 동일한 결과

Part 2. 왜 하필 3대야?

서버 2대면 안 돼?

2대 중 1대가 죽으면?

남은 1대가 리더를 해도 될까?

확신이 없어. 죽은 게 아니라 네트워크만 끊긴 거일 수도 있거든.

❌ 2대일 때 문제 (Split Brain): [A] ════════════ [B] 네트워크 끊김! A: "B가 죽었나? 내가 리더 해야지" B: "A가 죽었나? 내가 리더 해야지" → 리더가 2명! → 서로 다른 결정을 내림 → 데이터 불일치 💀
3대면 왜 괜찮아?

과반수(Majority) 때문이야.

3대 중 2대가 동의하면 결정 가능.

1대가 죽어도 남은 2대가 과반수를 이룰 수 있어.

서버 수 과반수 허용 장애 판정
1대 1대 0대 ❌ SPOF
2대 2대 0대 ❌ Split Brain
3대 2대 1대 ✅ 최소 구성
5대 3대 2대 ✅ 권장
그럼 100대면 50대까지 죽어도 돼?

이론상 그래. 근데 합의 비용이 커져.

모든 결정에 51대가 동의해야 하니까 느려져.

보통 3대 또는 5대를 써.

Part 3. 리더는 어떻게 뽑아?

반장 선거처럼 투표해?

비슷해! Raft에서는 이렇게 동작해:

🗳️ Raft 리더 선출 과정: 초기 상태: 모두 Follower ┌─────────┐ ┌─────────┐ ┌─────────┐ │Follower │ │Follower │ │Follower │ │ A │ │ B │ │ C │ └─────────┘ └─────────┘ └─────────┘ 1️⃣ 타임아웃 발생 (리더한테 연락이 없어!) A: "리더가 없네? 내가 후보로 나갈래" 2️⃣ A가 Candidate(후보)가 됨 ┌──────────┐ ┌─────────┐ ┌─────────┐ │Candidate │ │Follower │ │Follower │ │ A │ │ B │ │ C │ └──────────┘ └─────────┘ └─────────┘ │ └──▶ "나한테 투표해줘!" ──▶ B, C 3️⃣ 투표 결과 B: "ㅇㅋ A한테 투표" ✓ C: "ㅇㅋ A한테 투표" ✓ A: 3표 중 3표 (자기 포함) 4️⃣ 과반수 획득 → 리더 확정! ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Leader │ │Follower │ │Follower │ │ A 👑 │ │ B │ │ C │ └─────────┘ └─────────┘ └─────────┘
왜 타임아웃이 있어?

리더는 주기적으로 Heartbeat(심장박동)를 보내.

"나 살아있어~" 하는 신호야.

일정 시간 동안 Heartbeat가 안 오면?

"리더 죽었나보다" → 새 선거 시작!

💓 Heartbeat 메커니즘: [Leader A] ──heartbeat──▶ [B] "A 살아있음" │ └─────heartbeat──▶ [C] "A 살아있음" ⏰ 150~300ms마다 전송 만약 heartbeat가 안 오면? [B] 타이머: 300ms... 400ms... 500ms... 💥 타임아웃! [B] "리더 죽었다! 내가 후보로 나갈래!"
동시에 두 명이 후보로 나가면?

좋은 질문! 그래서 랜덤 타임아웃을 써.

각 서버마다 타임아웃 시간이 달라 (150~300ms 사이 랜덤).

먼저 타임아웃된 서버가 후보로 나가고, 대부분 그 서버가 리더가 돼.

Part 4. Term(임기)이 뭐야?

리더 바뀌면 어떻게 구분해?

각 리더 시대를 Term(임기)으로 구분해.

대통령 임기처럼 생각하면 돼.

📅 Term (임기) 개념: Term 1: A가 리더 👑 ────────────────────────▶ │ │ A 사망 💀 ▼ Term 2: B가 새 리더 👑 ────────────────────────▶ │ │ B 사망 💀 ▼ Term 3: C가 새 리더 👑 ────────────────────────▶ 규칙: - 한 Term에 리더는 최대 1명 - Term 숫자가 높을수록 최신 - 낮은 Term의 명령은 무시
왜 Term이 중요해?

네트워크 분리됐다가 복구되면 옛날 리더가 돌아올 수 있어.

그때 Term으로 "너 구시대 리더야"를 알 수 있어.

🔄 Term으로 충돌 해결: 상황: 네트워크 분리 후 복구 [구 리더 A] [현 리더 B] Term 1 Term 2 │ │ └─── 네트워크 복구 ───┘ │ ▼ A: "나 리더인데? 명령 내릴게~" (Term 1) B: "어 잠깐, 내 Term이 2야" A: "앗, 내 Term이 더 낮네... 나 Follower 할게" 🙇

Part 5. 게임에서 어디에 써?

게임 서버에서 Raft를 직접 구현해?

직접 구현하기보다 Raft 기반 시스템을 써.

시스템 용도 게임 서버 활용
etcd 분산 설정 저장 서버 목록, 설정값 관리
Consul 서비스 디스커버리 게임 서버 자동 등록/발견
TiKV 분산 Key-Value DB 글로벌 상태 저장
구체적으로 어떤 상황에서?

로아 같은 대규모 게임에서:

🎮 게임 서버에서 Raft 활용 예시: 1️⃣ 월드보스 좌표 서버 - 100개 채널에서 같은 월드보스 - 누가 HP 관리 리더인지 결정 - 리더 죽으면 자동으로 다른 서버가 인수 2️⃣ 글로벌 경매장 - 모든 서버의 주문을 하나로 모음 - 경매장 마스터 서버 선출 - 마스터 장애 시 자동 Failover 3️⃣ 길드 데이터 동기화 - 길드원이 여러 서버에 분산 - 길드 상태 변경의 순서 보장 - Split Brain 방지

Part 6. 직접 구현하려면?

포트폴리오로 Raft 구현하고 싶어

핵심 컴포넌트 3가지를 구현하면 돼:

🔧 Raft 구현 핵심 컴포넌트: 1️⃣ 상태 머신 (State Machine) ├─ Follower: 리더 명령 따름 ├─ Candidate: 투표 요청 중 └─ Leader: 명령 내림 2️⃣ 로그 복제 (Log Replication) ├─ 리더가 로그 추가 ├─ 팔로워에게 전파 └─ 과반수 확인 후 커밋 3️⃣ 리더 선출 (Leader Election) ├─ 타임아웃 감지 ├─ 투표 요청/응답 └─ Term 관리
간단한 코드로 보여줘

상태 전이 핵심 로직:

// Raft 노드 상태 enum class RaftState { Follower, Candidate, Leader }; class RaftNode { RaftState m_state = RaftState::Follower; int m_currentTerm = 0; int m_votedFor = -1; // 이번 Term에 누구한테 투표했나 void OnHeartbeatTimeout() { // 리더한테 연락이 없다 → 선거 시작! m_state = RaftState::Candidate; m_currentTerm++; // 새 임기 시작 m_votedFor = m_myId; // 자기 자신한테 투표 // 다른 노드들에게 투표 요청 BroadcastRequestVote(m_currentTerm); } void OnReceiveVote(int voteCount) { // 과반수 득표하면 리더! if (voteCount > m_totalNodes / 2) { m_state = RaftState::Leader; StartSendingHeartbeats(); // 리더 업무 시작 } } };

⚠️ 구현 시 주의사항

1. 타임아웃은 랜덤으로 - 동시 후보 방지 (150~300ms 사이 랜덤)

2. Term 비교 필수 - 낮은 Term의 메시지는 무시

3. 투표는 Term당 1번 - 한 Term에 두 번 투표하면 안 됨

4. 로그 일관성 체크 - 리더 선출 시 로그가 더 최신인 후보에게 투표

• 논문: "In Search of an Understandable Consensus Algorithm"

📝 핵심 정리

  • 리더 = 모든 결정의 최종 권한자, 데이터 일관성 보장
  • 3대 = 1대 죽어도 과반수(2대) 유지 가능한 최소 구성
  • 과반수 = 결정의 정당성 보장, Split Brain 방지
  • Term = 리더의 임기, 높은 Term이 우선권
  • 타임아웃 + 투표 = 리더 없으면 자동으로 새 리더 선출
