MTS 자동 테스트 5년의 기록

네트워크 NCSOFT NDC 발표 2025.01
게임 QA 자동화 테스트 워크벤치 적정기술 MTS 자동화 레벨

개요

NCSOFT의 MTS(Mobile Test Service) 팀이 5년간 게임 자동 테스트를 구축하고 운영하면서 얻은 교훈과 인사이트를 정리한 NDC 발표 내용입니다.

"자동 테스트? 게임에서는 안 될 거야"라는 회의론을 어떻게 극복하고 실제 서비스에 적용했는지, 그리고 적정기술이라는 관점에서 어떻게 접근했는지 살펴봅니다.

1. 자동 테스트에 대한 인식 변화

질문

게임에서 자동 테스트가 가능하다고 생각하시나요? 많은 사람들이 "게임은 변수가 너무 많아서 안 돼"라고 말하는데요.

답

처음엔 저희도 그렇게 생각했습니다. "안 될 거야"가 초기 반응이었죠.

MTS 팀이 5년간 겪은 인식의 변화 과정:

처음 (2019) 현재 (2024) │ │ ▼ ▼ "안 될 거야" ───────▶ "실제로 서비스 운영 중" │ │ │ - 게임은 너무 복잡해 │ - 정기점검 자동화 완료 │ - 변수가 너무 많아 │ - 빌드 인수테스트 자동화 │ - ROI가 안 나올 거야 │ - 확률 검증까지 확장 │ │ ▼ ▼ 회의론 검증된 시스템

핵심 깨달음

"100% 자동화"가 아닌 "효과적인 부분 자동화"가 목표였습니다.

모든 것을 자동화하려 하면 실패합니다. 자동화할 가치가 있는 부분만 선별하는 것이 핵심이었습니다.

질문

어떤 부분이 자동화하기 좋은 영역이었나요?

답

반복적이고, 규칙 기반이며, 사람이 하면 실수하기 쉬운 테스트들입니다.

자동화하기 좋은 영역 자동화하기 어려운 영역
로그인/로그아웃 반복 재미 평가
아이템 구매/판매 UI/UX 느낌
확률 검증 (가챠) 밸런스 감각
기본 기능 스모크 테스트 버그 탐지 (새로운 유형)

2. 적정기술 접근 - 딸기 수확 비유

질문

자동 테스트를 구축할 때 최신 AI 기술(이미지 인식, 딥러닝 등)을 활용해야 하지 않나요?

답

꼭 그렇지 않습니다. 발표에서 "딸기 수확" 비유가 나왔습니다.

"딸기를 자동으로 수확하려면 어떻게 해야 할까요? 고도의 AI 로봇팔이 필요할까요? 아니면 컨베이어 벨트 위에서 재배하면 될까요?"

방법 1: 고도의 기술 ┌─────────────────────────────────────────┐ │ AI 이미지 인식 → 로봇팔로 딸기 파악 │ │ → 익은 정도 판단 → 정밀하게 수확 │ │ │ │ 비용: 매우 높음 / 복잡도: 높음 │ └─────────────────────────────────────────┘ 방법 2: 적정기술 ┌─────────────────────────────────────────┐ │ 컨베이어 벨트 위에서 재배 │ │ → 익으면 자연스럽게 떨어짐 │ │ → 벨트가 수집 │ │ │ │ 비용: 낮음 / 복잡도: 낮음 │ └─────────────────────────────────────────┘

적정기술이란?

문제를 해결하는 데 "딱 필요한 수준"의 기술을 적용하는 것입니다.

최신 기술이 아니라, 상황에 맞는 기술이 정답입니다.

질문

게임 테스트에서 적정기술 접근은 어떻게 적용되나요?

답

UI를 분석하는 대신, 게임 클라이언트에 테스트용 인터페이스를 추가하는 방식입니다.

고도 기술 접근 적정기술 접근 (MTS)
화면 이미지 인식으로 버튼 찾기 테스트용 API로 버튼 ID 직접 호출
OCR로 텍스트 읽기 게임 내부 데이터 직접 조회
AI로 게임 상태 파악 상태 값을 직접 리턴받는 인터페이스

주의: 적정기술의 함정

적정기술이 "대충 하자"는 의미가 아닙니다.

문제 해결에 필요한 최소한의 기술이지만, 그 기술은 제대로 구현되어야 합니다.

3. 테스트 워크벤치 시스템 구조

질문

MTS의 자동 테스트 시스템은 어떻게 구성되어 있나요?

답

크게 3가지 핵심 컴포넌트로 구성됩니다: 스크립트 관리, 기기 관리, 리포트 시스템

1스크립트 관리 시스템

테스트 시나리오를 작성하고 관리하는 시스템입니다.

// 테스트 스크립트 예시 (의사 코드)

    Step 1: 앱 실행
    Step 2: 로그인 버튼 터치
    Step 3: 계정 정보 입력
    Step 4: 로그인 완료 확인

    Expected: 캐릭터 선택 화면 진입
}

2기기 관리 시스템

질문

모바일 게임 테스트를 위해 실제 기기가 필요한데, 수십~수백 대의 기기를 어떻게 관리하나요?

답

기기 팜(Device Farm)을 구축하고, 중앙에서 상태를 모니터링합니다.

기능 설명
기기 상태 모니터링 온라인/오프라인, 배터리, 온도 체크
기기 할당 테스트에 적합한 기기 자동 선택
원격 제어 앱 설치, 실행, 종료 원격 수행
기기 초기화 테스트 후 클린 상태로 복구

리포트는 "실패 원인을 빠르게 파악"할 수 있도록 설계되어야 합니다.

단순히 "실패"가 아니라 "왜 실패했는지"가 중요합니다.

4. 자동 테스트로 확장된 영역

질문

5년간 자동 테스트 시스템이 어떤 영역까지 확장되었나요?

답

처음엔 단순 기능 테스트였지만, 지금은 빌드 인수, 정기점검, 확률 검증까지 확장되었습니다.

4.1 빌드 인수 테스트 (BVT)

새 빌드 생성 │ ▼ ┌─────────────────────────────────────┐ │ 자동 빌드 인수 테스트 │ ├─────────────────────────────────────┤ │ - 앱 실행 가능 여부 │ │ - 로그인 성공 여부 │ │ - 핵심 기능 동작 여부 │ │ - 크래시 발생 여부 │ └─────────────────────────────────────┘ │ ├── 통과 → QA 팀에 인계 │ └── 실패 → 개발팀에 반려 (자동 알림)

효과

QA 팀이 "기본도 안 되는 빌드"를 받아서 시간 낭비하는 일이 사라졌습니다.

빌드 품질의 최소 기준을 자동으로 보장합니다.

4.2 정기점검 테스트

질문

라이브 서비스의 정기점검 후에는 어떤 테스트가 필요한가요?

답

서버 오픈 전에 핵심 기능이 정상 동작하는지 빠르게 확인해야 합니다. 이걸 수동으로 하면 시간이 너무 오래 걸립니다.

점검 항목 수동 테스트 자동 테스트
전체 스모크 테스트 2~3시간 30분
결제 테스트 30분 5분
실행 가능 시간대 업무 시간 내 새벽 4시에도 가능

4.3 확률 검증 테스트

질문

가챠(뽑기) 확률이 제대로 적용되었는지 어떻게 검증하나요?

답

수천~수만 번 뽑기를 실행해서 실제 확률이 명시된 확률과 일치하는지 검증합니다. 이건 사람이 할 수 없습니다.

// 확률 검증 로직 (의사 코드)
def verify_gacha_probability(item_id, expected_rate, iterations=10000):
    success_count = 0

    for i in range(iterations):
        result = execute_gacha()
        if result == item_id:
            success_count += 1

    actual_rate = success_count / iterations

    # 통계적 허용 오차 내에 있는지 확인
    assert is_within_tolerance(actual_rate, expected_rate)

왜 중요한가?

확률형 아이템은 법적 규제 대상입니다.

명시된 확률과 실제 확률이 다르면 법적 문제가 발생할 수 있습니다.

4.4 기타 확장 영역

  • 다국어 테스트 - 언어 변경 후 텍스트 깨짐 확인
  • 호환성 테스트 - 다양한 기기에서 동시 실행
  • 성능 테스트 - 프레임 드롭, 메모리 누수 모니터링
  • 네트워크 테스트 - 불안정한 네트워크 환경 시뮬레이션

5. 교훈: 비용과 한계

핵심 경고

"QA 비용을 줄이려고 자동 테스트를 도입하면 실패합니다."

질문

자동 테스트를 도입하면 QA 인력을 줄일 수 있지 않나요?

답

자동 테스트는 QA를 대체하는 게 아니라, QA의 역량을 확장하는 것입니다.

5.1 비용 구조의 현실

┌─────────────────────────────────────────────────────────────┐ │ 자동 테스트 비용 구조 │ ├─────────────────────────────────────────────────────────────┤ │ │ │ 초기 투자 비용 │ │ ├── 시스템 개발 비용 (개발자 인건비) │ │ ├── 인프라 구축 비용 (기기 팜, 서버) │ │ └── 테스트 스크립트 작성 비용 │ │ │ │ 운영 유지 비용 │ │ ├── 스크립트 유지보수 (게임 업데이트마다) │ │ ├── 인프라 유지 비용 │ │ └── 전담 인력 비용 │ │ │ └─────────────────────────────────────────────────────────────┘
오해 현실
"자동화하면 QA 인원 감축" 오히려 자동화 전담 인력이 필요
"한 번 만들면 계속 사용" 게임 업데이트마다 스크립트 수정 필요
"비용 절감 효과 즉시 발생" 1~2년 운영해야 ROI 발생

핵심 교훈

"개발 비용을 별도로 편성해야 합니다."

QA 예산에서 끌어쓰면 안 됩니다. 자동 테스트는 별도의 개발 프로젝트로 취급해야 합니다.

5.2 자동 테스트의 한계

질문

자동 테스트로 할 수 없는 것은 무엇인가요?

답

창의적 탐색, 사용자 경험 평가, 예상치 못한 버그 발견은 여전히 사람의 영역입니다.

자동 테스트 사람이 해야 하는 테스트
예상된 시나리오 검증 예상치 못한 상황 탐색
반복적 확인 창의적 파괴 테스트
수치 기반 판단 감각 기반 판단 (재미, UX)
회귀 테스트 신규 기능 탐색 테스트

"자동 테스트는 '이미 아는 버그'를 찾는 데 탁월합니다. '모르는 버그'를 찾는 건 여전히 사람의 몫입니다."

6. 자동 테스트 5단계 비전

질문

자율주행처럼 자동 테스트에도 레벨이 있나요?

답

MTS 팀은 자동 테스트의 성숙도를 0~5단계로 정의했습니다.

0Level 0: 수동 테스트

모든 테스트를 사람이 직접 수행. 자동화 없음.

1Level 1: 도구 지원

테스트 보조 도구 사용. 매크로, 단순 반복 자동화. 사람이 여전히 주도.

2Level 2: 부분 자동화

특정 시나리오를 자동 실행. 스모크 테스트, 회귀 테스트 자동화. 결과 판단은 사람.

3Level 3: 조건부 자동화

대부분의 테스트 자동 실행 및 판단. 예외 상황만 사람이 개입. MTS 현재 목표 단계

4Level 4: 고도 자동화

테스트 설계까지 자동화. AI가 테스트 케이스 생성. 사람은 감독 역할.

5Level 5: 완전 자동화

사람 개입 없이 전체 QA 프로세스 수행. 현재 기술로는 미래 비전.

현실적인 목표

MTS 팀은 Level 3 (조건부 자동화)를 실질적인 목표로 설정했습니다.

Level 4~5는 기술 발전에 따라 점진적으로 도전할 영역입니다.

최종 정리

MTS 5년의 핵심 교훈

1. 회의론 극복 - "안 될 거야"에서 시작해 실제 서비스 운영까지

2. 적정기술 - 고도의 AI가 아닌, 문제 해결에 딱 맞는 기술 선택

3. 시스템 구축 - 스크립트, 기기관리, 리포트의 3축 체계

4. 영역 확장 - BVT, 정기점검, 확률 검증까지 자동화

5. 비용 인식 - QA 비용 절감이 아닌 별도 개발 투자로 접근

6. 단계적 발전 - Level 0~5 중 현실적인 Level 3 목표

항목 잘못된 접근 올바른 접근
목표 QA 인력 감축 QA 역량 확장
예산 QA 예산에서 할당 별도 개발 예산 편성
범위 모든 것 자동화 효과적인 영역만 선별
