게임 QA 자동화

자동 테스트 기초부터 적정기술 접근, 실제 도입까지

Part 1. QA 자동화가 뭐야?

QA 자동화? 그게 뭔데?

QA 자동화는 사람이 직접 하던 게임 테스트를 기계가 대신 하는 거야.

비유: 자동 세차기

예전에는 손세차 했잖아?
- 사람이 직접: 느리고, 사람마다 결과 다름
- 자동 세차기: 빠르고, 항상 같은 품질

QA 자동화도 똑같아:
- 사람이 직접: "로그인 잘 되나요?" 하나하나 확인
- 자동화: 버튼 하나로 전체 테스트 자동 실행!
게임에서 자동 테스트가 가능해?

처음엔 다들 이렇게 생각해:

[초기 반응 - "안 될 거야"] "게임은 너무 복잡해..." "변수가 너무 많아..." "ROI가 안 나올 거야..." [현실] - NCSOFT MTS팀: 5년간 실제 운영 중! - 정기점검 자동화 완료 - 확률 검증까지 자동화 핵심 깨달음: "100% 자동화"가 아니라 "효과적인 부분 자동화"가 목표!

Part 2. 어떤 걸 자동화할 수 있어?

모든 테스트를 자동화할 수 있어?

아니! 자동화하기 좋은 것과 아닌 것이 있어.

자동화 O 자동화 X
로그인/로그아웃 반복 재미 평가
아이템 구매/판매 UI/UX 느낌
확률 검증 (가챠) 밸런스 감각
기본 기능 스모크 테스트 새로운 유형의 버그 탐지
왜 그래?

자동화 가능한 테스트의 특징:

[자동화 적합 조건] 1. 반복적 ← 매번 똑같이 해야 함 예: 정기점검 후 로그인 테스트 2. 규칙 기반 ← 정답이 명확함 예: "골드 1000개 있으면 구매 가능" 3. 실수하기 쉬움 ← 사람이 하면 놓침 예: 10만 번 가챠해서 확률 검증 4. 수치 판단 ← 숫자로 결과 확인 예: "HP가 0 이하면 사망" [자동화 부적합] - 창의적 판단: "이 UI가 예쁜가?" - 감각적 평가: "조작감이 좋은가?" - 탐색적 테스트: "이상한 짓 하면 뭐가 터지나?"
핵심 원칙

"이미 아는 버그를 찾는 건 자동화"
"모르는 버그를 찾는 건 사람"

Part 3. 적정기술이 뭐야?

AI로 화면 인식해서 테스트하면 안 돼?

가능하지만, 적정기술 관점에서 생각해봐:

비유: 딸기 수확

딸기를 자동으로 수확하려면?

방법 1 (고도 기술):
- AI가 딸기 위치 파악
- 로봇팔이 익은 정도 판단
- 정밀하게 수확
→ 비용 높음, 복잡함

방법 2 (적정기술):
- 컨베이어 벨트 위에서 재배
- 익으면 자연스럽게 떨어짐
- 벨트가 수집
→ 비용 낮음, 단순함
게임 테스트에서 적정기술은?

화면을 분석하지 말고, 게임에 테스트용 인터페이스를 추가!

고도 기술 접근 적정기술 접근
화면 이미지 인식으로 버튼 찾기 테스트 API로 버튼 ID 직접 호출
OCR로 텍스트 읽기 게임 내부 데이터 직접 조회
AI로 게임 상태 파악 상태 값을 직접 리턴받는 인터페이스
[적정기술 테스트 예시] # 고도 기술 (이미지 인식) screenshot = capture_screen() button = ai_find_button(screenshot, "로그인") click(button.x, button.y) # → 느림, 불안정, 복잡함 # 적정기술 (테스트 API) game.call_api("click_button", button_id="login") result = game.get_state("is_logged_in") assert result == True # → 빠름, 안정적, 단순함
주의

적정기술 ≠ 대충 하는 것

"문제 해결에 딱 필요한 수준"의 기술이지,
"아무렇게나 해도 된다"는 의미가 아님!

Part 4. 자동 테스트 시스템 구조

자동 테스트 시스템은 어떻게 생겼어?

크게 3가지 컴포넌트로 구성돼:

[테스트 워크벤치 구조] ┌────────────────────────────────────────────────┐ │ 테스트 워크벤치 │ ├────────────────────────────────────────────────┤ │ │ │ ┌──────────┐ ┌──────────┐ ┌──────────┐ │ │ │ 스크립트 │ │ 기기관리 │ │ 리포트 │ │ │ │ 관리 │ │ 시스템 │ │ 시스템 │ │ │ └────┬─────┘ └────┬─────┘ └────┬─────┘ │ │ │ │ │ │ │ ▼ ▼ ▼ │ │ 테스트 케이스 실제 폰/PC 결과 대시보드 │ │ 작성/편집 (Device Farm) 알림/분석 │ │ │ └────────────────────────────────────────────────┘
스크립트 관리는 뭐야?

테스트 시나리오를 작성하고 관리하는 시스템:

// 테스트 스크립트 예시 TestCase "로그인 테스트" { Step 1: 앱 실행 Step 2: 로그인 버튼 터치 Step 3: 계정 정보 입력 Step 4: 로그인 완료 확인 Expected: 캐릭터 선택 화면 진입 }
기기관리는?

모바일 게임이면 수십~수백 대의 실제 폰이 필요해!

기능 설명
기기 상태 모니터링 온라인/오프라인, 배터리, 온도
기기 할당 테스트에 적합한 기기 자동 선택
원격 제어 앱 설치, 실행, 종료
기기 초기화 테스트 후 클린 상태로 복구

Part 5. 실제로 어디에 써?

자동화 테스트를 어디에 활용해?

대표적인 활용 영역 3가지:

1. 빌드 인수 테스트 (BVT)

새 빌드가 만들어지면 자동으로 기본 테스트 실행:
- 앱 실행 가능?
- 로그인 가능?
- 핵심 기능 동작?
- 크래시 없음?

통과 → QA팀에 인계
실패 → 개발팀에 자동 반려!

효과: QA가 "기본도 안 되는 빌드" 받는 일이 사라짐!
2. 정기점검 테스트

라이브 서버 점검 후 자동 테스트:

항목 수동 자동
스모크 테스트 2~3시간 30분
결제 테스트 30분 5분
실행 시간 업무시간 새벽 4시 OK
3. 확률 검증 테스트

가챠 확률이 제대로 적용됐는지 검증:

# 확률 검증 로직 def verify_gacha(item_id, expected_rate): success = 0 for i in range(10000): # 1만 번 뽑기 result = execute_gacha() if result == item_id: success += 1 actual_rate = success / 10000 assert is_within_tolerance(actual_rate, expected_rate) # 이걸 사람이 한다고? 불가능! # → 자동화 필수 영역
확률형 아이템은 법적 규제 대상!
명시 확률과 실제 확률이 다르면 법적 문제!

Part 6. 현실적인 비용과 한계

자동화하면 QA 인원 줄일 수 있어?

가장 흔한 오해야!

핵심 경고

"QA 비용을 줄이려고 자동 테스트를 도입하면 실패합니다."

자동 테스트는 QA를 대체하는 게 아니라
QA의 역량을 확장하는 것!
오해 현실
"자동화하면 QA 감축" 자동화 전담 인력이 추가로 필요
"한 번 만들면 끝" 게임 업데이트마다 스크립트 수정 필요
"즉시 비용 절감" 1~2년 운영해야 ROI 발생
[자동 테스트 비용 구조] 초기 투자: ├── 시스템 개발 비용 (개발자 인건비) ├── 인프라 구축 비용 (기기 팜, 서버) └── 테스트 스크립트 작성 비용 운영 유지: ├── 스크립트 유지보수 (업데이트마다!) ├── 인프라 유지 비용 └── 전담 인력 비용
올바른 접근

자동 테스트는 별도의 개발 프로젝트로 취급해야 함!

- QA 예산에서 끌어쓰면 안 됨
- 별도 개발 예산 편성 필요
- 장기 투자로 접근

Part 7. 자동화 성숙도 레벨

자동화에도 레벨이 있어?

자율주행처럼 0~5단계로 나눌 수 있어:

0수동 테스트

모든 테스트를 사람이 직접 수행. 자동화 없음.

1도구 지원

매크로, 단순 반복 자동화. 사람이 여전히 주도.

2부분 자동화

특정 시나리오 자동 실행. 스모크 테스트, 회귀 테스트 자동화.
결과 판단은 사람.

3조건부 자동화 ← 현실적 목표!

대부분의 테스트 자동 실행 및 판단.
예외 상황만 사람이 개입.

4고도 자동화

테스트 설계까지 자동화. AI가 테스트 케이스 생성.
사람은 감독 역할.

5완전 자동화

사람 개입 없이 전체 QA 수행. 현재 기술로는 미래 비전.

MTS팀의 현실적 목표

Level 3 (조건부 자동화)가 실질적인 목표
Level 4~5는 기술 발전에 따라 점진적으로 도전

핵심 정리

  • QA 자동화 - 반복적, 규칙 기반 테스트를 기계가 대신
  • 적정기술 - AI보다 테스트 API가 더 효과적일 수 있음
  • 활용 영역 - BVT, 정기점검, 확률 검증
  • 비용 인식 - QA 절감이 아닌 별도 개발 투자
  • 현실적 목표 - Level 3 (조건부 자동화)
  • 자동화 vs 사람 - "아는 버그"는 자동, "모르는 버그"는 사람
