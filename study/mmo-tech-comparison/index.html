우리 IOCP 서버, 로스트아크랑 뭐가 다를까?

한국 MMO 서버 기술 비교 — 같은 점, 한 단계 위, 그리고 왜 쓰는지

리니지W, 검은사막, 메이플스토리, 로스트아크 — 전부 C++.

Part 2. IOCP의 천장 — RIO는 왜 나왔을까?

IOCP면 충분하지 않아? 10년 넘게 잘 써왔는데.

충분해. 동접 수천 명까지는.

근데 문제가 있어. IOCP는 매번 I/O를 요청할 때마다

커널 모드 ↔ 유저 모드 전환이 일어나거든.

이게 1번이면 괜찮은데, 초당 수만 번 반복되면

전환 비용만으로 CPU의 10~15%를 잡아먹어.

IOCP (기존): 유저모드 ──▶ 커널모드 ──▶ 유저모드 ──▶ 커널모드 Send() 완료통보 Recv() 완료통보 ↕ 전환 ↕ 전환 ↕ 전환 ↕ 전환 = I/O 1번에 모드 전환 2번 = 초당 10,000 I/O → 20,000번 전환 RIO (Registered I/O): 유저모드 ━━━━━━━━━━━━━━━━━━━━━━━━▶ 버퍼 미리 등록 → 커널이 직접 접근 Send/Recv 시 모드 전환 없음 = 초당 10,000 I/O → 전환 0번
그래서 실제로 얼마나 빨라져?

NCsoft가 리니지W에 RIO를 도입했어.

NCsoft TECH Standard EP01(2022)에서 직접 발표한 내용이야.

결과: 동일 하드웨어에서 약 10% 처리량 향상.

10%가 별로 같지? 근데 생각해봐.

서버 100대가 10% 더 처리할 수 있으면

= 서버 10대를 안 사도 된다는 거야.

그럼 우리도 IOCP를 RIO로 바꿔야 해?

당장은 아니야.

RIO가 의미 있으려면 I/O가 병목인 상황이어야 해.

우리 서버는 지금 I/O보다 게임 로직 처리가 병목이거든.

도입 시점: 동접이 현재 한계에 근접할 때.

그때 IOCP 엔진(gniServer)만 교체하면 돼.

코드 변경은 네트워크 레이어에만 한정되니까.

Part 3. 싱글스레드의 벽 — 멀티스레드 게임 로직

공성전에 500명이 모이면 메인 루프가 몇 ms 걸릴까? 맞춰봐.

우리 서버 기준으로 계산해보자.

500명 × 이동 패킷 처리 0.1ms = 50ms

500명 × 스킬 판정 0.3ms = 150ms

몬스터 AI 50마리 × 0.2ms = 10ms

기타 (버프, 아이템, 파티) = 40ms

합계: 약 250ms — 1프레임에 0.25초.

게임이 4fps로 돌아가는 거야. 사실상 슬라이드쇼.

싱글스레드니까 어쩔 수 없는 거 아니야?

맞아. 그래서 대형 게임은 이걸 깬 거야.

로스트아크는 멀티스레드 게임 로직을 쓰는 것으로 알려져 있어.

핵심 아이디어: 게임 월드를 영역별로 나눠서

각 영역을 다른 스레드가 처리하는 거야.

싱글스레드 (우리): 🧵 Thread 1: ┌─────────────────────────────────┐ │ 플레이어A │ 플레이어B │ 몬스터 │ AI │ └─────────────────────────────────┘ 전부 순서대로 처리 → 500명이면 250ms 멀티스레드 (로스트아크 방식 추정): 🧵 Thread 1: [영역 A — 200명] 🧵 Thread 2: [영역 B — 150명] 🧵 Thread 3: [영역 C — 100명] 🧵 Thread 4: [몬스터 AI 전체] 4코어 병렬 → 250ms ÷ 4 = ~63ms = 약 16fps. 플레이 가능.
그럼 왜 다들 멀티스레드 안 해?

대가가 크거든.

영역 경계를 넘는 스킬이 문제야.

A영역의 마법사가 B영역의 적을 때리면?

→ Thread 1과 Thread 2가 동시에 같은 HP를 건드려.

→ 레이스 컨디션.

이걸 해결하려면 락(Lock)을 걸어야 하는데,

락 범위가 넓어지면 사실상 싱글스레드랑 속도가 같아져.

그래서 멀티스레드 게임 로직은

'구현할 수 있는 팀'이 제한적이야.

Part 4. DB가 멈추면 서버도 멈춘다

우리 서버에서 DB 호출하면 뭐가 일어나?

동기 호출이야. DB에서 응답 올 때까지 서버가 기다려.

DB 응답이 50ms 걸리면, 그 50ms 동안 서버가 아무것도 못 해.

캐릭터 저장 1번에 50ms,

인벤토리 저장 1번에 30ms,

1000명이 동시에 저장하면?

→ 큐에 쌓여서 순차 처리 → 마지막 사람은 수십 초 대기.

대형 게임은 이걸 어떻게 해결해?

크게 두 가지 방식이 확인돼.

1. 분산 DB — 검은사막 모바일

Pearl Abyss가 GDC 2021에서 발표한 내용이야.

Azure SQL 인스턴스 46개를 사용해.

서버별, 기능별로 DB를 완전히 분리한 거야.

2. Actor 모델 + Event Sourcing — 쿠키런: 킹덤

데브시스터즈가 NDC 2023에서 발표했어.

DB에 직접 쓰지 않고, '이벤트'를 큐에 넣어.

이벤트가 비동기로 DB에 기록돼.

우리 방식 (동기 DB): 게임서버 ──(저장해줘)──▶ MSSQL 1대 ◀──(OK, 50ms)── 이 50ms 동안 서버 멈춤 ⏸️ 검은사막 모바일 (분산 DB): 게임서버 ──▶ Azure SQL #1 (캐릭터) ──▶ Azure SQL #2 (인벤토리) ──▶ Azure SQL #3 (길드) ──▶ ... 총 46개 부하가 46개로 분산 → 개별 응답 빠름 쿠키런: 킹덤 (Actor + Event Sourcing): 게임서버 ──(이벤트)──▶ 큐 ──▶ DB ↓ 즉시 다음 처리 DB 응답 안 기다림 → 서버 안 멈춤
우리도 DB 46개로 나눠야 해?

당장은 현실적이지 않아.

근데 우리 시스템에서도 할 수 있는 게 있어:

- 비동기 DB 호출: GameDB 서버를 별도 프로세스로 분리 (이미 함)

- 캐릭터 저장 배치: 60초마다 한번에 모아서 저장 (이미 함)

- 다음 단계: 읽기 전용 캐시(Redis) 도입으로 DB 부하 분산

사실 우리가 GameDB를 별도 서버로 분리한 것 자체가

'분산 DB'의 시작점이야.

Part 5. 서버 100대를 새벽에 수동 재시작?

패치 배포할 때 서버를 어떻게 내려?

솔직히 말하면, 수동이야.

서버 목록 열고, 하나씩 종료, 파일 복사, 하나씩 재시작.

10대면 30분, 50대면 2시간.

새벽 점검 때마다 이 작업을 반복하는 거야.

대형 게임은 어떻게 해?

PUBG가 Kubernetes + Agones를 쓰는 걸로 확인돼.

PUBG Corp이 GDC 2019에서 직접 발표했어.

Agones = Google이 만든 게임 서버 전용 오케스트레이터.

하는 일:

- 서버 바이너리를 컨테이너로 패키징

- '서버 100대 띄워줘' → 자동 배포

- 서버 1대가 죽으면 → 자동으로 새 서버 투입

- 패치 배포 → 롤링 업데이트 (무중단)

우리 방식 (수동): 👤 운영자 ├─ 서버1 종료 → 파일복사 → 시작 ├─ 서버2 종료 → 파일복사 → 시작 ├─ 서버3 종료 → 파일복사 → 시작 └─ ... (반복) ⏱️ 소요: 서버 수 × 10~15분 PUBG 방식 (K8s + Agones): 👤 운영자: "kubectl apply -f new-version.yaml" ├─ K8s가 새 서버 자동 생성 ├─ 유저 없는 서버부터 교체 ├─ 유저 있는 서버는 매치 끝나면 교체 └─ 전체 완료 ⏱️ 소요: 명령어 1줄 + 자동 30분
근데 우리 서버는 stateful인데, K8s가 가능해?

핵심을 짚었어.

우리 게임 서버는 CUnitPC에 유저 상태를 메모리에 들고 있어.

서버가 죽으면 그 상태가 날아가.

PUBG는 '매치' 단위라서 괜찮아.

매치 끝나면 서버 상태가 필요 없거든.

MMO는 다르지. 24시간 유저가 접속해 있으니까.

그래서 MMO에 K8s를 쓰려면

상태를 서버 밖(Redis, DB)에 저장하는 구조 변경이 필요해.

이건 단순 도입이 아니라 아키텍처 재설계야.

주의: 출처 없는 기술 비교를 조심해

이 문서에서 '확인됨'이라고 쓴 건 GDC, NDC, 공식 기술 블로그에서 직접 발표된 내용만 포함했어

로스트아크는 서버 기술을 공개 발표한 적이 거의 없어. '추정'으로 표시한 부분은 업계 관행과 간접 증거 기반이야

기술 블로그나 발표 없이 '~를 쓴다'고 단정하는 글은 의심해볼 것

핵심 정리

  • 기반 기술은 거의 같아 — C++ / Windows / IOCP / MSSQL / 채널 분산은 한국 MMO의 공통 스택
  • IOCP → RIO: 커널 모드 전환 제거로 ~10% 향상. I/O가 병목일 때 의미 있어 (리니지W, NCsoft 발표)
  • 싱글스레드 → 멀티스레드: 대규모 전투 처리량 4배. 대신 영역 경계 동기화 난이도가 극상 (로스트아크 추정)
  • 동기 DB → 분산/비동기: DB 응답 대기 제거. 우리도 GameDB 분리까지는 해놨어 (검은사막 Azure SQL 46개, 쿠키런 Actor)
  • 수동 배포 → K8s 오케스트레이션: 자동 배포/복구. 단, stateful 서버는 아키텍처 변경 필요 (PUBG Agones)
  • 도입 판단 기준: '지금 뭐가 병목이야?' — 병목이 아닌 곳을 바꿔봐야 체감 없어
