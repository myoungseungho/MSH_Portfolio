CPU 아키텍처: x86 vs ARM

PC, 서버, 모바일 — CPU가 다르면 왜 같은 코드가 다르게 동작할까?

Architecture = 설계 구조

CPU = Central Processing Unit, 명령어를 실행하는 핵심 장치

Architecture = 구조, 설계 방식 — CPU가 명령어를 어떤 방식으로 처리하는지

ISA (Instruction Set Architecture) = CPU가 이해할 수 있는 명령어 세트의 규격

같은 프로그램도 CPU 아키텍처가 다르면 기계어가 완전히 달라진다. x86용 exe는 ARM에서 실행할 수 없다.

Part 1. CPU가 뭔데? — 명령어를 실행하는 기계

CPU가 뭔데?

CPU는 명령어(instruction)를 하나씩 가져와서 실행하는 장치다. 모든 CPU는 기본적으로 같은 사이클을 반복한다.

Fetch(명령어 가져오기) → Decode(해석) → Execute(실행) → Write Back(결과 저장). 이 네 단계를 쉬지 않고 반복하는 것이 CPU의 본질이다.

CPU 실행 사이클 (Instruction Cycle) ┌─────────────────────────────────────────────────────┐ │ │ │ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌──────────┐ │ │ Fetch │──▶│ Decode │──▶│ Execute │──▶│Write Back│ │ │ 명령어 │ │ 해석 │ │ 실행 │ │결과 저장 │ │ └─────────┘ └─────────┘ └─────────┘ └──────────┘ │ ▲ │ │ └──────────────────────────────────────────┘ │ 반복 (Loop) └─────────────────────────────────────────────────────┘ PC (Program Counter) 가 다음 명령어 주소를 가리킴 → 메모리에서 명령어를 가져오고 (Fetch) → 어떤 연산인지 해석하고 (Decode) → ALU 등에서 실행하고 (Execute) → 결과를 레지스터/메모리에 저장 (Write Back)
그럼 모든 CPU가 같은 명령어를 실행해?

아니다. CPU마다 이해할 수 있는 명령어 세트(ISA)가 다르다.

x86은 Intel이 설계한 명령어를 사용하고, ARM은 ARM Holdings가 설계한 명령어를 사용한다. 마치 영어와 일본어처럼, 같은 뜻이라도 표현 방식이 완전히 다르다.

그래서 x86용으로 컴파일한 바이너리는 ARM CPU에서 실행할 수 없고, 그 반대도 마찬가지다.

Part 2. x86이 뭐야? — Intel/AMD, PC/서버의 표준

x86이 뭐야?

1978년 Intel 8086에서 시작된 CPU 아키텍처다. CISC(Complex Instruction Set Computing) 방식으로, 하나의 명령어가 복잡한 작업을 수행할 수 있다.

예를 들어 "메모리에서 값을 읽어서 더한 뒤 다시 메모리에 저장"하는 것을 한 줄의 명령어로 처리할 수 있다.

왜 PC의 표준이 됐어?

1981년 IBM PC가 Intel 8088(8086의 파생)을 채택했고, 이후 Microsoft Windows가 x86 위에서 동작하면서 사실상 PC/서버의 표준이 됐다.

Intel과 AMD가 경쟁하며 성능을 끌어올렸고, 서버 시장에서도 x86이 지배적인 위치를 차지했다. 현재 대부분의 게임 서버는 x86(x64) 위에서 동작한다.

; x86 어셈블리 예시 (Intel 문법) ; 두 수를 더하는 간단한 연산 mov eax, [num1] ; 메모리에서 num1 값을 eax 레지스터로 로드 add eax, [num2] ; eax에 num2 값을 더함 (메모리 직접 참조 가능!) mov [result], eax ; 결과를 메모리에 저장 ; CISC 특징: add 명령어가 메모리에서 직접 읽어서 더할 수 있음 ; → 하나의 명령어가 "메모리 읽기 + 연산"을 동시에 수행
항목 x86 특징
설계 방식 CISC (Complex Instruction Set Computing)
명령어 길이 가변 길이 (1~15 바이트)
단일 스레드 성능 높음
전력 소모 높음 (65~350W TDP)
메모리 접근 명령어에서 직접 메모리 참조 가능
대표 제조사 Intel, AMD

Part 3. x64는 x86이랑 다른 거야? — 32비트 → 64비트 확장

x64는 x86이랑 다른 거야?

x64 = x86의 64비트 확장이다. 원래 x86은 32비트 아키텍처였는데, AMD가 먼저 64비트로 확장해서 AMD64라고도 부른다.

Intel은 나중에 이를 채택해서 Intel 64 또는 EM64T라고 불렀다. 결국 같은 것이다.

핵심: 하위 호환 — x64 CPU는 기존 32비트 x86 코드도 그대로 실행할 수 있다. 그래서 오래된 프로그램도 동작한다.

32비트와 64비트 차이가 뭔데?

가장 큰 차이는 레지스터 크기와 메모리 주소 공간이다.

32비트는 최대 4GB 메모리만 주소 지정 가능하지만, 64비트는 이론상 16EB(엑사바이트)까지 가능하다. 실제로는 OS와 하드웨어가 48비트 주소(256TB)를 사용한다.

항목 32비트 (x86) 64비트 (x64)
레지스터 크기 32비트 (EAX, EBX...) 64비트 (RAX, RBX...)
범용 레지스터 수 8개 16개 (R8~R15 추가)
최대 메모리 4GB 16EB (실제 256TB)
포인터 크기 4바이트 8바이트
함수 호출 규약 cdecl, stdcall 등 다양 통일 (Windows: Microsoft x64, Linux: System V AMD64)
하위 호환 - 32비트 코드 실행 가능 (WoW64)

참고: 현재 "x86"이라고 하면 보통 x86-64(x64)를 포함하는 넓은 의미로 사용된다. 게임 서버는 거의 100% x64 빌드를 사용한다. 4GB 메모리 제한은 대규모 온라인 게임에서는 치명적이기 때문이다.

Part 4. ARM은 뭐가 달라? — RISC vs CISC

ARM은 뭐가 달라?

ARM은 RISC(Reduced Instruction Set Computing) 방식이다. 명령어가 단순하고 고정 길이(4바이트)다.

CISC(x86)가 "하나의 복잡한 명령어로 많은 일을 하자"라면, RISC(ARM)는 "단순한 명령어를 빠르게 많이 실행하자"는 철학이다.

명령어가 단순하니 회로도 단순해지고, 적은 전력으로 효율적이다. 그래서 스마트폰, 태블릿 등 모바일 기기에서 압도적으로 사용된다.

RISC랑 CISC의 차이가 뭔데?

CISC(x86): 하나의 복잡한 명령어가 여러 작업을 수행한다. "메모리에서 읽고 + 연산하고 + 저장"을 한 명령어로 가능.

RISC(ARM): 단순한 명령어만 존재. "메모리에서 읽기", "연산하기", "저장하기"가 각각 별도 명령어. 하지만 각 명령어가 1 클록에 실행되는 것을 목표로 설계.

; 같은 작업: "메모리의 두 값을 더해서 저장" ; === CISC (x86) === ; 메모리 직접 참조 가능 → 적은 명령어 add eax, [num2] ; 메모리에서 읽기 + 더하기를 한 번에! mov [result], eax ; 결과 저장 ; === RISC (ARM) === ; 메모리 접근은 Load/Store만 가능 → 명령어가 더 많음 LDR R0, [R2] ; 메모리에서 R0으로 로드 LDR R1, [R3] ; 메모리에서 R1으로 로드 ADD R0, R0, R1 ; R0 = R0 + R1 (레지스터끼리만 연산) STR R0, [R4] ; 결과를 메모리에 저장 ; RISC는 명령어 수가 더 많지만, ; 각 명령어가 단순해서 파이프라인 효율이 높고 ; 클록당 처리량(IPC)을 높일 수 있다.
요즘 ARM이 왜 뜨는 거야?

두 가지 큰 변화가 있었다:

1. Apple Silicon (M1~M4) — Apple이 Mac에 자체 ARM 칩을 탑재. 성능은 x86 최상위급인데 전력 효율이 압도적. 팬 없이도 고성능을 낸다.

2. AWS Graviton — Amazon이 서버용 ARM CPU를 만들어서 AWS에 배치. 같은 비용 대비 최대 40% 더 나은 가성비를 제공한다.

게임 서버도 ARM 서버를 검토하는 곳이 늘고 있다. 특히 서버 비용이 큰 대규모 서비스에서 관심이 높다. 다만 기존 x86 전용 라이브러리나 인라인 어셈블리 호환성 문제가 걸림돌이 될 수 있다.

Part 5. 메모리 모델이 왜 다르지? — 강한 vs 약한 모델

CPU 아키텍처마다 메모리 모델이 다르다는 게 무슨 뜻이야?

멀티코어 CPU에서 각 코어가 메모리를 읽고 쓰는 순서를 얼마나 보장하느냐가 아키텍처마다 다르다.

우리가 코드에 쓴 순서대로 메모리에 반영된다고 생각하지만, 실제로 CPU와 컴파일러는 성능을 위해 순서를 바꿀 수 있다. 이걸 재배치(reordering)라고 한다.

x86은 어떤 모델이야?

x86은 강한 순서 모델(TSO, Total Store Order)이다.

Store-Store 순서가 보장된다. 즉, 코어가 A를 쓰고 B를 쓰면, 다른 코어에서도 A가 먼저 보이고 B가 나중에 보인다.

그래서 x86에서는 메모리 배리어 없이도 많은 경우 정상 동작한다. 하지만 이건 "운이 좋은 것"이지 "올바른 코드"는 아니다.

ARM은?

ARM은 약한 순서 모델(Weak Memory Model)이다.

CPU가 성능을 위해 자유롭게 읽기/쓰기 순서를 바꿀 수 있다. Store-Store, Load-Load, Store-Load, Load-Store 모든 조합에서 재배치가 일어날 수 있다.

따라서 ARM에서는 반드시 명시적 메모리 배리어가 필요하다.

// x86에서 되는데 ARM에서 깨지는 예시: flag 패턴 // 공유 변수 int data = 0; int flag = 0; // flag로 "data 준비됐음"을 알림 // === Thread 1 (Writer) === data = 42; // (1) 데이터 쓰기 flag = 1; // (2) 플래그 쓰기 // === Thread 2 (Reader) === while (flag == 0) {} // (3) 플래그 대기 int r = data; // (4) 데이터 읽기 → 42여야 함 // x86 (TSO): Store-Store 순서 보장 // → (1)이 (2)보다 먼저 보임 → r == 42 ✅ // ARM (Weak): Store-Store 재배치 가능! // → (2)가 (1)보다 먼저 보일 수 있음 → r == 0 ❌ 버그! // === 올바른 코드 (아키텍처 독립적) === std::atomic<int> data{0}; std::atomic<int> flag{0}; // Thread 1 data.store(42, std::memory_order_relaxed); flag.store(1, std::memory_order_release); // 배리어! // Thread 2 while (flag.load(std::memory_order_acquire) == 0) {} // 배리어! int r = data.load(std::memory_order_relaxed); // → 모든 아키텍처에서 r == 42 ✅

주의: x86에서 잘 돌아간다고 ARM에서도 된다는 보장이 없다. 메모리 모델이 더 약하기 때문에 x86에서 "우연히" 동작하던 코드가 ARM에서 깨질 수 있다.

Part 6. 그래서 개발할 때 뭐가 달라?

같은 C++ 코드인데 CPU마다 다르게 동작할 수 있다고?

맞다. 컴파일러가 CPU에 맞는 기계어를 생성하는데, 최적화 방식도 다르고 메모리 모델도 다르다.

C++을 작성하면 컴파일러가 타겟 아키텍처에 맞는 기계어로 변환한다. 이때 x86 컴파일러와 ARM 컴파일러가 생성하는 코드가 다르고, 최적화 전략도 다르다.

항목 x86 / x64 ARM / AArch64
빌드 타겟 x86, x86_64 arm, aarch64
메모리 배리어 필요성 TSO로 일부 생략 가능 (비권장) 반드시 명시적 배리어 필요
인라인 어셈블리 x86 전용 (호환 불가) ARM 전용 (호환 불가)
SIMD 명령어 SSE, AVX, AVX-512 NEON, SVE
바이트 오더 Little-Endian Little-Endian (기본, Bi-Endian 지원)
서버 점유율 90%+ (Intel Xeon, AMD EPYC) 증가 중 (AWS Graviton, Ampere)
게임 서버 개발자가 알아야 할 핵심은?

1. 현재 게임 서버는 x86(x64) 기반이 대부분이지만, AWS Graviton 같은 ARM 서버도 빠르게 늘고 있다. 비용 절감이 확실하기 때문이다.

2. std::atomic + memory_order를 사용하면 아키텍처 독립적으로 안전하다. x86에서 "되니까 괜찮겠지"가 아니라, 표준이 보장하는 방법을 써야 한다.

3. 플랫폼 독립적 코드 작성이 중요하다. 인라인 어셈블리 대신 컴파일러 intrinsic을, 플랫폼 전용 API 대신 크로스 플랫폼 라이브러리를 쓰는 습관을 들이자.

핵심 정리

  • CPU는 명령어를 실행하는 장치, 아키텍처마다 명령어 세트(ISA)가 다르다
  • x86 = CISC, Intel/AMD, PC/서버 표준. x64는 x86의 64비트 확장 (AMD64)
  • ARM = RISC, 고정 길이 명령어, 전력 효율 우수. Apple Silicon, AWS Graviton으로 확장 중
  • x86은 강한 메모리 모델(TSO), ARM은 약한 모델 — 같은 코드가 다르게 동작할 수 있다
  • std::atomic + memory_order를 사용하면 아키텍처에 관계없이 안전한 코드 작성 가능
  • 게임 서버는 대부분 x64이지만, ARM 서버도 점차 채택 중
