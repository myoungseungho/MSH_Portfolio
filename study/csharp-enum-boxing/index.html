C# Enum 박싱 문제

왜 Enum만 쓰면 GC가 터질까? - 숨겨진 성능 함정과 해결책

Boxing Enum Generic GC Unity
1

박싱(Boxing)이 뭐야?

int를 object에 넣으면 뭐가 달라지는 거야?

값을 "박스"에 담는 거야!

C#에서 int는 값 타입(스택에 저장), object는 참조 타입(힙에 저장)이거든.

이 둘을 연결하려면 변환이 필요해. 그게 바로 박싱!

📦 택배 비유

int = 내 손에 들고 있는 물건 (스택 - 빠르게 접근 가능)

object = 택배 박스에 담아서 창고에 보관 (힙 - 찾으러 가야 함)

물건을 박스에 넣고 창고에 보내려면 박스 비용 + 배송 비용이 들지?
박싱도 마찬가지야. 힙 할당 비용 + 나중에 GC 정리 비용!

┌─────────────────────────────────────────────────────────────────┐ │ 박싱 발생 과정 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 스택 (Stack) 힙 (Heap) │ │ ┌─────────┐ ┌────────────────────┐ │ │ │ int: 42 │ ──박싱──────→ │ Object Header │ │ │ └─────────┘ │ Type Info Pointer │ │ │ │ ────────────────── │ │ │ (4 바이트) │ 값: 42 │ │ │ └────────────────────┘ │ │ (64-bit: 24 바이트!) │ │ │ │ ※ 힙 할당 = GC 대상 = 게임 끊김의 원인! │ └─────────────────────────────────────────────────────────────────┘
박싱된 객체는 얼마나 커져?

원래 값 + 헤더 오버헤드가 붙어서 6배까지 커질 수 있어!

타입 32-bit 환경 64-bit 환경
int (값 타입) 4 바이트 4 바이트
박싱된 int 12 바이트 (3배) 24 바이트 (6배)
⚠️ 실제 게임에서의 충격

한 프레임에 Equals 비교 125회 발생한다면:

• 비교당 박싱 2회 × 24바이트 = 48바이트

• 125 × 48 = 6KB/프레임

• 60fps면 360KB/초 쓰레기 발생!

2

값 타입 vs 참조 타입 - 왜 이런 구조일까?

C#은 왜 값 타입과 참조 타입을 구분해?

성능과 편의성의 트레이드오프야!

특성 값 타입 (Value Type) 참조 타입 (Reference Type)
저장 위치 스택 (빠름) 힙 (상대적 느림)
예시 int, float, struct, Enum class, object, string
복사 시 값 전체 복사 참조(주소)만 복사
GC 대상 아니오 예
근데 왜 object에 int를 넣을 수 있어?

C#의 모든 타입은 object를 상속해. 심지어 int도!

다형성(Polymorphism)을 위해 모든 걸 object로 다룰 수 있게 한 거지.

┌─────────────────────────────────────────────────────────────────┐ │ C# 타입 계층 구조 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ ┌──────────┐ │ │ │ Object │ ← 모든 타입의 최상위 │ │ └────┬─────┘ │ │ ┌───────────┼───────────┐ │ │ │ │ │ │ │ ┌─────┴─────┐ ┌───┴───┐ ┌─────┴─────┐ │ │ │ ValueType │ │ Array │ │ String │ │ │ └─────┬─────┘ └───────┘ └───────────┘ │ │ ┌───────┼───────┐ │ │ │ │ │ │ │ ┌───┴──┐ ┌──┴──┐ ┌──┴──┐ │ │ │ Int32│ │Enum │ │struct│ │ │ └──────┘ └─────┘ └──────┘ │ │ │ │ ※ Enum은 ValueType 상속 → 값 타입! │ │ ※ 하지만 object 변수에 담으려면 → 박싱 필요! │ └─────────────────────────────────────────────────────────────────┘
박싱이 자동으로 일어나는 거야?

응, 그게 문제야! 명시적으로 안 해도 컴파일러가 알아서 해.

// 박싱이 숨어있는 코드들 int num = 42; // Case 1: object 변수에 대입 object obj = num; // 박싱! // Case 2: object 파라미터를 받는 함수 Console.WriteLine(num); // 박싱! (내부적으로 object로 받음) // Case 3: 문자열 결합 string str = "값은 " + num; // 박싱! // Case 4: 인터페이스 변수에 대입 IComparable comp = num; // 박싱!
3

Enum + Generic = 박싱 지옥

Enum이랑 Generic이 만나면 왜 특히 문제야?

Equals() 메서드 시그니처 때문이야!

제네릭에서 Equals를 호출하면 object.Equals(object)가 불려.

┌─────────────────────────────────────────────────────────────────┐ │ 제네릭 Equals 호출 시 박싱 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 코드: Compare(CardRank.Ace, CardRank.King) │ │ │ │ void Compare<T>(T a, T b) where T : Enum │ │ { │ │ if (a.Equals(b)) { ... } │ │ } │ │ │ │ ──────────────────────────────────────────────────── │ │ │ │ [컴파일러가 보는 것] │ │ │ │ public virtual bool Equals(object obj) ← 시그니처 │ │ ^^^^^^ │ │ object! │ │ │ │ a.Equals(b) 호출 시: │ │ 1. b가 object로 변환 ─────────────→ 박싱 1회 (인자) │ │ 2. a에서 virtual Equals 호출 ─────→ 박싱 1회 (수신자) │ │ │ │ = 비교 1회에 박싱 2회! │ └─────────────────────────────────────────────────────────────────┘
Dictionary에서 Enum을 키로 쓰면?

검색할 때마다 박싱! Dictionary는 내부에서 Equals, GetHashCode를 호출해.

Dictionary<CardRank, int> cardValues = new(); cardValues[CardRank.Ace] = 1; // 박싱 발생! var value = cardValues[CardRank.Ace]; // 또 박싱! // Dictionary 내부에서 일어나는 일: // - key.GetHashCode() 호출 → 박싱 // - key.Equals(otherKey) 호출 → 박싱 2회
HasFlag()는 어때?

더 황당해! 성능을 위해 비트 연산 쓴 건데, 오히려 박싱으로 더 느려!

[Flags] enum Permissions { Read = 1, Write = 2, Execute = 4 } Permissions perm = Permissions.Read | Permissions.Write; // 편해 보이지만... bool canWrite = perm.HasFlag(Permissions.Write); // 박싱! // HasFlag 시그니처를 보면: public bool HasFlag(Enum flag) // Enum = 참조 타입! { // 내부에서 object로 다루므로 박싱 발생 }
🎭 역설적 상황

"비트 연산으로 성능 최적화하자!" → HasFlag 사용

→ 내부에서 박싱 발생

→ 오히려 더 느려짐!

좋은 의도가 나쁜 결과를 낳는 대표적인 케이스.

4

정석적 해법? "이게 해법이라고?"

C#에서 공식으로 제공하는 해결책은 뭐야?

IEqualityComparer 커스텀 구현이야.

Dictionary 생성자에 커스텀 Comparer를 넘기면 돼.

public class CardRankComparer : IEqualityComparer<CardRank> { public bool Equals(CardRank x, CardRank y) { return x == y; // 구체 타입이라 박싱 없음! } public int GetHashCode(CardRank obj) { return (int)obj; // int로 캐스팅, 박싱 없음 } } // 사용 var dict = new Dictionary<CardRank, int>(new CardRankComparer());
이게 왜 문제야?

프로그래머한테 일을 떠넘기는 거지!

┌─────────────────────────────────────────────────────────────────┐ │ 정석 해법의 현실적 문제 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ 영화 <극한직업> 대사가 떠오름: │ │ "이게 해법이라고 내놓는 거지?" │ │ │ │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │ │ │ │ [작업량 폭발] │ │ │ │ Enum 10개 만들면 → Comparer 10개 작성 │ │ Dictionary 100개 만들면 → 생성자 100개 수정 │ │ │ │ [실수 가능성] │ │ │ │ 까먹으면? → 다시 박싱 발생! │ │ 신규 개발자가 모르면? → 박싱 발생! │ │ │ └─────────────────────────────────────────────────────────────────┘
C# 7.3에서 where T : Enum 제약이 생겼다던데?

타입 안전성만 제공할 뿐, 박싱 문제는 해결 못 해.

void Process<T>(T value) where T : Enum { // T가 Enum임을 컴파일러가 알게 됨 // 하지만... } // IL 코드를 보면... box !!T // 여전히 박싱! callvirt Equals
⚠️ 결론

C# 7.3의 Enum 제약은 타입 안전성만 제공.

박싱 문제는 여전히 존재한다!

5

진짜 해결책: Enum → int 변환

핵심 아이디어가 뭐야?

Enum은 내부적으로 int야!

int로 바꿔서 처리하면 박싱이 발생하지 않아.

┌─────────────────────────────────────────────────────────────────┐ │ 핵심 인사이트 │ ├─────────────────────────────────────────────────────────────────┤ │ │ │ CardRank.Ace = 0 (내부적으로 int 0) │ │ CardRank.King = 1 (내부적으로 int 1) │ │ CardRank.Queen = 2 (내부적으로 int 2) │ │ │ │ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ │ │ │ │ Enum 비교 int 비교 │ │ ┌────────────────┐ ┌────────────────┐ │ │ │ Ace.Equals(King)│ │ 0 == 1 │ │ │ │ ↓ │ │ ↓ │ │ │ │ 박싱 2회 발생! │ VS │ 박싱 없음! │ │ │ └────────────────┘ └────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────────┘
근데 제네릭 T는 캐스팅이 안 되잖아?

맞아. 컴파일러가 T가 뭔지 모르니까.

void Process<T>(T value) where T : Enum { int num = (int)value; // 컴파일 에러! // T가 뭔지 모르니까 캐스팅 불가 }
그럼 어떻게 해?

방법이 3가지 있어. 플랫폼 호환성을 고려해야 해.

방법 원리 플랫폼 지원
Expression (동적 생성) 런타임에 변환 코드 생성 iOS 불가 (AOT)
FieldOffset (Union) 메모리 공유 최신 Unity 호환성 문제
Unsafe 포인터 메모리 직접 접근 모든 플랫폼 OK!
6

실전 코드: Unsafe 포인터 해법

Unsafe 포인터가 뭐야?

C#에서 C++ 스타일로 메모리를 직접 조작하는 거야.

변환 비용 없이 메모리를 그대로 읽어!

핵심 코드
Enum ↔ int 변환 유틸리티
public static class EnumToInt<TEnum> where TEnum : struct { public static unsafe int Convert(TEnum value) { int* ptr = (int*)&value; return *ptr; } } public static class IntToEnum<TEnum> where TEnum : struct { public static unsafe TEnum Convert(int value) { TEnum* ptr = (TEnum*)&value; return *ptr; } } // 사용 int num = EnumToInt<CardRank>.Convert(CardRank.Ace); // 박싱 없음! CardRank rank = IntToEnum<CardRank>.Convert(0); // 박싱 없음!
✅ 이게 최종 해법!

• 모든 플랫폼에서 동작 (iOS 포함)

• 최고 성능 (포인터 직접 접근)

• 박싱 완전 제거

응용
박싱 없는 EnumDictionary
public class EnumDictionary<TKey, TValue> where TKey : struct // Enum 제약 { private Dictionary<int, TValue> _inner = new(); public TValue this[TKey key] { get => _inner[EnumToInt<TKey>.Convert(key)]; set => _inner[EnumToInt<TKey>.Convert(key)] = value; } public bool ContainsKey(TKey key) { return _inner.ContainsKey(EnumToInt<TKey>.Convert(key)); } } // 사용 var values = new EnumDictionary<CardRank, int>(); values[CardRank.Ace] = 1; // 박싱 없음! var v = values[CardRank.Ace]; // 박싱 없음!
대안
HasFlag 대신 비트 연산 직접 사용
// 나쁜 예: HasFlag 사용 (박싱 발생!) bool canWrite = perm.HasFlag(Permissions.Write); // 좋은 예: 비트 연산 직접 사용 (박싱 없음!) bool canWrite = (perm & Permissions.Write) == Permissions.Write; // 또는 0이 아닌지 확인 bool canWrite = (perm & Permissions.Write) != 0;
⚠️ Unity에서 unsafe 활성화

Player Settings → Other Settings → Allow 'unsafe' Code 체크!

7

면접 대비 & 실무 가이드라인

기술 면접: "C#에서 박싱이 뭐고, 왜 피해야 해요?"

"박싱은 값 타입을 참조 타입(object)으로 변환하는 것입니다.

힙에 메모리가 할당되고 GC 대상이 되어, 게임처럼 실시간 성능이 중요한 환경에서는 프레임 드랍을 유발합니다."

"Enum + Dictionary 조합에서 박싱이 왜 발생해요?"

"Dictionary 내부에서 키 비교 시 Equals()와 GetHashCode()를 호출하는데,

이들의 시그니처가 object 기반이라 Enum이 박싱됩니다.

해결책은 IEqualityComparer 구현이나 unsafe 포인터로 int 변환입니다."

"HasFlag() 왜 안 쓰는 게 좋아요?"

"HasFlag 메서드가 Enum 타입을 파라미터로 받는데, 내부에서 object로 다뤄져 박싱이 발생합니다.

비트 연산자(&)를 직접 사용하면 박싱 없이 같은 결과를 얻을 수 있습니다."

문제 원인 해결책
Enum.Equals() 박싱 object.Equals(object) 호출 int로 변환 후 비교
Dictionary<Enum, T> 박싱 GetHashCode, Equals 호출 EnumDictionary 사용
HasFlag() 박싱 Enum 타입 인자 비트 연산자 직접 사용
제네릭 T 캐스팅 불가 컴파일러가 타입 모름 unsafe 포인터
🎯 한 줄 요약

"Enum + Generic = 박싱을 의심하라"

⚠️ 한계

이 기법은 32비트 Enum(기본 int)만 지원합니다.

byte, short, long 기반 Enum은 별도 처리 필요.

(실무에서 대부분 기본 int를 사용하므로 큰 문제는 아님)

📋 핵심 정리: C# Enum 박싱 문제

  • 박싱 - 값 타입 → 참조 타입 변환, 힙 할당 + GC 대상이 됨
  • Enum + Generic - Equals 호출 시 박싱 2회 발생 (비교 1회당)
  • HasFlag - 편의 함수지만 박싱 발생, 비트 연산(&)으로 대체
  • 공식 해법 - IEqualityComparer 커스텀 구현 (번거로움)
  • 실용적 해법 - unsafe 포인터로 Enum → int 직접 변환
  • 게임에서 GC = 프레임 드랍 - 박싱을 최대한 피하라!
