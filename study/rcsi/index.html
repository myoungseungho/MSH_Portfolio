Part 1. NOLOCK, 정말 괜찮을까?

게임 서버 쿼리에 WITH (NOLOCK) 왜 다 붙어있어?

락 경합을 피하려고야.

SELECT가 UPDATE를 기다리면 느려지니까, 락 없이 읽는 거지.

-- 우리 게임 DB의 전형적인 패턴 SELECT * FROM TCharacter WITH (NOLOCK) WHERE i32CharSID = @CharSID; SELECT * FROM TInventory WITH (NOLOCK) WHERE charunique = @CharID;
그러면 뭐가 문제야?

Dirty Read가 발생할 수 있어!

Dirty Read란?

트랜잭션이 아직 커밋하지 않은 데이터를 읽는 것

예시:
1. 트랜잭션 A: 골드 100 → 200으로 UPDATE (아직 COMMIT 안 함)
2. 트랜잭션 B: NOLOCK으로 읽음 → 200 반환
3. 트랜잭션 A: ROLLBACK (100으로 복구)
4. 트랜잭션 B는 존재하지 않는 200골드를 읽은 것
게임에서 그게 실제로 문제가 될까?

드물지만 심각한 버그로 이어질 수 있어.

상황 NOLOCK 문제 결과
거래 중 조회 롤백될 아이템을 읽음 아이템 복사 버그
순위 계산 중 일관성 없는 데이터 순위 꼬임
재화 검증 커밋 안 된 골드 읽음 재화 복사 가능성

Part 2. RCSI가 뭔데?

📸 스냅샷 비유

NOLOCK: "지금 작업 중인 것도 그냥 봐버림" (공사 현장 침입)

RCSI: "마지막으로 완성된 사진을 봄" (완공된 상태 스냅샷)

RCSI는 커밋된 버전의 스냅샷을 읽어!
스냅샷을 어떻게 만들어?

SQL Server가 TempDB에 이전 버전을 저장해.

┌─────────────────────────────────────────────────────┐
│                 RCSI 동작 원리                       │
├─────────────────────────────────────────────────────┤
│                                                     │
│  [트랜잭션 A - UPDATE]                              │
│      골드: 100 → 200 (UPDATE 실행)                  │
│              ↓                                      │
│      TempDB에 이전값(100) 저장                      │
│              ↓                                      │
│      데이터 페이지에 200 기록                       │
│                                                     │
│  [트랜잭션 B - SELECT]                              │
│      "골드 읽어줘"                                  │
│              ↓                                      │
│      A가 아직 COMMIT 안 했네?                       │
│              ↓                                      │
│      TempDB에서 커밋된 버전(100) 읽음               │
│              ↓                                      │
│      100 반환 ✅ (Dirty Read 없음!)                 │
│                                                     │
└─────────────────────────────────────────────────────┘
락은 안 걸려?

SELECT는 락을 안 걸어.

이전 버전을 읽으니까 UPDATE를 기다릴 필요가 없어!

RCSI의 핵심

Dirty Read
없음
커밋된 버전만 읽음
읽기 락
없음
스냅샷에서 읽음
쓰기 대기
없음
동시 실행 가능

Part 3. RCSI 켜는 방법

어떻게 적용해?

DB 레벨에서 한 줄이면 돼.

-- RCSI 활성화 (DB 레벨 설정) ALTER DATABASE chosun_game11 SET READ_COMMITTED_SNAPSHOT ON; -- 현재 설정 확인 SELECT name, is_read_committed_snapshot_on FROM sys.databases WHERE name = 'chosun_game11';
주의: 활성화 시 배타적 접근 필요

• 다른 연결이 없을 때 실행해야 함
• 서비스 점검 시간에 적용 권장
• 즉시 적용되지만, 기존 트랜잭션은 완료될 때까지 기다림
기존 코드는 수정 안 해도 돼?

코드 수정 없이 동작해!

기존 SELECT 쿼리가 자동으로 스냅샷 읽기로 바뀜.

-- RCSI 적용 전 SELECT * FROM TCharacter WITH (NOLOCK) ... -- → Dirty Read 가능 -- RCSI 적용 후 (NOLOCK 없이도 OK) SELECT * FROM TCharacter ... -- → 커밋된 스냅샷 읽기, 락 없음 -- 기존 NOLOCK 쿼리도 그대로 동작 SELECT * FROM TCharacter WITH (NOLOCK) ... -- → 여전히 동작하지만, 제거 권장
NOLOCK 제거는 점진적으로

RCSI 켜도 기존 NOLOCK 코드는 문제없이 동작해.
하지만 새 코드부터 NOLOCK 없이 작성하고,
기존 코드는 리팩토링 시 점진적으로 제거하면 돼.

Part 4. RCSI의 장단점

단점은 없어?

TempDB 부하가 증가해.

항목 NOLOCK RCSI
Dirty Read 발생 가능 발생 안 함
읽기 락 없음 없음
데이터 일관성 보장 안 됨 보장됨
TempDB 사용 추가 없음 버전 저장으로 증가
쓰기 오버헤드 없음 이전 버전 저장
코드 수정 매번 WITH (NOLOCK) 자동 적용
TempDB 부하가 많이 늘어?

UPDATE가 많으면 늘어나지만, 대부분의 게임 DB에서는 감당 가능해.

읽기가 쓰기보다 훨씬 많거든.

-- TempDB 버전 스토어 사용량 확인 SELECT SUM(version_store_reserved_page_count) * 8 / 1024 AS VersionStoreMB FROM sys.dm_db_file_space_usage; -- 장기 트랜잭션이 버전을 많이 쌓게 하니 주의 SELECT transaction_id, elapsed_time_seconds FROM sys.dm_tran_active_snapshot_database_transactions ORDER BY elapsed_time_seconds DESC;

Part 5. 게임 서버에 적용할 때

우리 게임 DB에 바로 적용해도 돼?

몇 가지 사전 점검이 필요해.

적용 전 체크리스트

1. TempDB 디스크 공간: 여유 있는지 확인 (10~20% 증가 예상)
2. TempDB 성능: SSD 권장 (버전 스토어 I/O)
3. 장기 트랜잭션: BEGIN TRAN ~ COMMIT이 오래 걸리는 곳 확인
4. 테스트 환경: 먼저 개발 DB에서 테스트
장기 트랜잭션이 왜 문제야?

트랜잭션이 끝나야 이전 버전을 정리할 수 있거든.

트랜잭션이 오래 열려있으면 버전이 계속 쌓임.

-- 문제 되는 패턴 (장기 트랜잭션) BEGIN TRANSACTION UPDATE TCharacter SET ... -- 여기서 외부 API 호출하느라 10초 대기 ← 문제! UPDATE TInventory SET ... COMMIT -- 개선 패턴 (짧은 트랜잭션) -- 외부 API는 트랜잭션 밖에서 호출 UPDATE TCharacter SET ... -- 자동 커밋 -- 외부 API 호출 UPDATE TInventory SET ... -- 자동 커밋
게임 DB에서 어떤 효과가 있어?

읽기-쓰기 경합이 줄어들어.

시나리오 개선 효과
캐릭터 저장 + 조회 동시 발생 조회가 저장 완료를 안 기다림
랭킹 계산 중 다른 쿼리 락 경합 없이 동시 진행
거래 로그 조회 + 기록 일관된 스냅샷으로 조회

Part 6. 안전한 마이그레이션 전략

라이브 서비스에 적용하려면?

단계별로 진행해야 안전해.

-- Phase 1: 테스트 환경에서 검증 -- 1. 개발 DB에 RCSI 활성화 ALTER DATABASE chosun_game_dev SET READ_COMMITTED_SNAPSHOT ON; -- 2. 부하 테스트 실행 -- 3. TempDB 사용량 모니터링 -- 4. 성능 비교 (응답 시간, CPU, I/O) -- Phase 2: 스테이징 환경 적용 -- 1. 실제 서비스와 유사한 환경에서 테스트 -- 2. 1주일 이상 안정성 확인 -- Phase 3: 라이브 적용 -- 1. 점검 시간에 활성화 ALTER DATABASE chosun_game11 SET READ_COMMITTED_SNAPSHOT ON; -- 2. 모니터링 강화 (첫 1주일) -- 3. NOLOCK 점진적 제거 (선택)
롤백 방법

문제 발생 시 다시 끌 수 있어:
ALTER DATABASE chosun_game11 SET READ_COMMITTED_SNAPSHOT OFF;

단, 활성 트랜잭션이 없어야 함.
NOLOCK 코드는 언제 제거해?

RCSI 안정화 후 점진적으로 제거해도 돼.

급하지 않아. NOLOCK이 있어도 RCSI가 더 안전하게 동작해.

핵심 정리: RCSI

  • NOLOCK 문제 = Dirty Read (커밋 안 된 데이터 읽음)
  • RCSI = 커밋된 스냅샷을 읽어서 Dirty Read 방지
  • 락 없이 읽기 = NOLOCK처럼 빠르지만 안전함
  • 적용 방법 = DB 레벨 설정 한 줄 (코드 수정 불필요)
  • TempDB 부하 = 버전 저장으로 약간 증가
  • 장기 트랜잭션 = 피해야 함 (버전 쌓임)
  • 마이그레이션 = 테스트 → 스테이징 → 라이브 단계별 적용
