Wait Statistics - SQL Server 성능 진단의 시작점

Part 1. DB가 느린데 왜인지 모르겠어

쿼리가 느린데 어디서부터 봐야 할지 모르겠어.

Wait Statistics부터 봐.

"DB가 뭘 기다리고 있는지" 알려주거든.

기다린다고?

쿼리 실행 중에 DB는 여러 가지를 기다려:

• 디스크에서 데이터 읽기

• 다른 쿼리가 잠금 풀기

• 메모리에 공간 확보

• 네트워크 응답

[쿼리 실행 시간 구성] 전체 실행 시간 = CPU 시간 + 대기 시간 예: 쿼리가 5초 걸렸다면 ├── CPU 작업: 0.5초 (10%) └── 대기 시간: 4.5초 (90%) ← 여기가 병목! ├── 디스크 I/O 대기: 3초 ├── 잠금 대기: 1초 └── 기타: 0.5초

대기 시간이 병목의 90%인 경우가 많아.

"뭘 기다리는지"를 알면 해결책이 보여.

Part 2. Wait Statistics 조회하기

어떻게 확인해?

DMV(Dynamic Management View)를 사용해.

-- 서버 전체 대기 통계 (누적) SELECT TOP 10 wait_type, wait_time_ms / 1000.0 AS wait_time_sec, waiting_tasks_count, wait_time_ms / waiting_tasks_count AS avg_wait_ms FROM sys.dm_os_wait_stats WHERE wait_type NOT LIKE '%SLEEP%' AND wait_type NOT LIKE '%IDLE%' AND wait_type NOT LIKE '%QUEUE%' ORDER BY wait_time_ms DESC

결과 예시:

wait_type wait_time_sec waiting_tasks avg_wait_ms -------------------- ------------- ------------- ----------- PAGEIOLATCH_SH 1234.5 50000 25 LCK_M_X 567.8 2000 284 WRITELOG 345.6 100000 3 CXPACKET 123.4 5000 25
이게 무슨 뜻이야?

각각 다른 종류의 "대기"야. 하나씩 볼게.

Part 3. 주요 Wait Type 해석

Wait Type 분류 의미
PAGEIOLATCH_* 디스크 I/O 디스크에서 데이터 읽기 대기
WRITELOG 디스크 I/O 트랜잭션 로그 쓰기 대기
LCK_M_* 잠금 다른 트랜잭션이 잠금 풀기 대기
CXPACKET 병렬 처리 병렬 쿼리 스레드 간 대기
RESOURCE_SEMAPHORE 메모리 쿼리 실행 메모리 할당 대기

PAGEIOLATCH_SH / PAGEIOLATCH_EX

원인: 디스크에서 데이터를 읽어와야 함 (메모리에 없음)
해결: 메모리 증설, 인덱스 최적화, SSD 전환

LCK_M_X (Exclusive Lock)

원인: 다른 트랜잭션이 해당 행/테이블 잠금 중
해결: 트랜잭션 짧게, 인덱스 추가, 잠금 범위 축소

WRITELOG

원인: 트랜잭션 로그 디스크 쓰기가 느림
해결: 로그 파일 SSD 이동, 트랜잭션 크기 줄이기

CXPACKET

원인: 병렬 쿼리에서 스레드 간 작업량 불균형
해결: MAXDOP 조정, 통계 업데이트

Part 4. 게임 서버에서 자주 보는 패턴

우리 게임 서버에서 주로 뭐가 문제야?

동기 블로킹 호출이라서 대기 시간이 곧 서버 성능이야.

[동기 호출 구조] 게임 서버 (싱글 스레드 메인 루프) │ ├── 메시지 처리 │ ↓ ├── DB 호출 (동기) ← 여기서 대기하면 전체 멈춤! │ ↓ └── 다음 메시지 처리 DB 대기 1초 = 서버 멈춤 1초

게임 서버에서 주의할 Wait Type:

Wait Type 게임 서버 영향 대응
LCK_M_* 치명적 인덱스, 트랜잭션 최소화
PAGEIOLATCH_* 심각 메모리, 인덱스 커버링
WRITELOG 중간 SSD, 배치 커밋

Part 5. 실시간으로 확인하기

지금 뭐가 느린지 실시간으로 볼 수 있어?

현재 실행 중인 쿼리와 대기 상태를 볼 수 있어.

-- 현재 대기 중인 쿼리 확인 SELECT r.session_id, r.wait_type, r.wait_time, r.blocking_session_id, t.text AS query_text FROM sys.dm_exec_requests r CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) t WHERE r.wait_type IS NOT NULL ORDER BY r.wait_time DESC
-- 블로킹 체인 확인 (누가 누굴 막고 있나) SELECT blocking.session_id AS blocker, blocked.session_id AS blocked, blocked.wait_type, blocked.wait_time FROM sys.dm_exec_requests blocked INNER JOIN sys.dm_exec_requests blocking ON blocked.blocking_session_id = blocking.session_id

핵심 정리

  • Wait Statistics = "DB가 뭘 기다리는지" 통계
  • 쿼리 시간 = CPU 시간 + 대기 시간 (대기가 90%)
  • PAGEIOLATCH: 디스크 I/O → 메모리/인덱스 개선
  • LCK_M_*: 잠금 대기 → 트랜잭션 최소화
  • 게임 서버: 동기 호출이라 대기 = 서버 멈춤
  • 모니터링: sys.dm_os_wait_stats, dm_exec_requests
