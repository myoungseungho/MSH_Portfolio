← 게임 아트

게임 에셋 하나가 화면에 나오기까지 11단계

아트 파이프라인 = 데이터 변환 체인. 각 단계의 제1원칙을 알면 에이전트가 보인다

Part 0. 너는 이미 아트 파이프라인을 알고 있다

아트 파이프라인이 뭔데?

서버 개발할 때 이런 흐름 익숙하지?

[서버 요청 파이프라인] 클라이언트 요청 (JSON) ↓ 파싱 요청 객체 (struct) ↓ 검증 검증된 데이터 ↓ 비즈니스 로직 처리 결과 ↓ 직렬화 응답 (JSON) ↓ 전송 클라이언트 화면 각 단계가 하는 것: 입력(A 포맷) → 변환 → 출력(B 포맷) → 다음 단계의 입력
아트 파이프라인도 이런 구조야?

완전히 동일한 구조야. 데이터 포맷만 다를 뿐.

[아트 파이프라인 = 데이터 변환 체인] 아이디어 (텍스트) ↓ 시각화 컨셉 이미지 (.png) ↓ 3D 변환 하이폴리 메시 (.zpr) ↓ 최적화 로우폴리 메시 (.fbx) ↓ 좌표 매핑 UV 전개 (.fbx + UV) ↓ 디테일 전사 텍스처 세트 (.png x 6) ↓ 구조 부여 스켈레탈 메시 (.fbx + bone) ↓ 시간 기록 애니메이션 클립 (.anim) ↓ 엔진 임포트 게임 화면 서버 파이프라인과 다른 점: 없음. 입력 → 변환 → 출력, 그 다음 단계의 입력이 됨. 이걸 이해하면 각 단계를 에이전트화할 수 있어. 에이전트 = "입력을 받아서 변환하고 출력하는 함수"니까.
그러면 각 단계의 "변환 규칙"만 알면 에이전트를 만들 수 있다는 거네?

정확해. 각 단계의 "제1원칙"이 바로 그 변환 규칙이야. 제1원칙을 모르면 에이전트에게 뭘 시킬지 모르고, 알면 정확하게 지시할 수 있어.

Part 1. 전체 파이프라인 지도 — 11단계 한눈에

전체 흐름을 먼저 보여줘. 각 단계에서 뭐가 들어가고 뭐가 나오는지.
[아트 파이프라인 전체 지도] 단계 입력 변환 출력 파일 포맷 ==== ==== ==== ==== ========= 1. 레퍼런스 게임 기획서 수집+정리 아트 바이블 .pdf/.fig 2. 컨셉아트 아트 바이블 시각화 3면도+컬러가이드 .psd/.png 3. 스컬핑 3면도 점토 조각 하이폴리 메시 .zpr/.obj 4. 리토폴로지 하이폴리 재구성 로우폴리 메시 .fbx/.obj 5. UV 언래핑 로우폴리 3D→2D 펼침 UV 좌표 .fbx(UV) 6. 베이킹 하이+로우(UV) 디테일 전사 노말맵/AO맵 .png/.exr 7. 텍스처링 UV메시+베이킹맵 물리 데이터 제작 PBR 6장 .png x6 8. 리깅 로우폴리+텍스처 뼈대 심기 스켈레탈 메시 .fbx(bone) 9. 애니메이션 스켈레탈 메시 동작 기록 애니메이션 클립 .anim/.fbx 10. VFX 텍스처+코드 효과 제작 파티클/셰이더 .vfx/.hlsl 11. 엔진 통합 모든 에셋 최적화+임포트 게임 빌드 .uasset 등 핵심: 모든 단계가 "입력 포맷 A → 변환 → 출력 포맷 B" 에이전트 = "A를 받아서 B를 만드는 함수" 제1원칙 = "왜 이 변환이 필요한지"
11단계나 되네. 왜 이렇게 많아? 단순화할 수 없어?

서버에서 "파싱-검증-로직-직렬화를 한 단계로 합치면 안 되나?"와 같은 질문이야. 합칠 수는 있는데, 품질이 폭락해. 각 단계가 존재하는 이유가 있어. 하나씩 보자.

Stage 1. 레퍼런스 수집 & 아트 바이블

게임을 만들겠다고 결심했어. 아트 작업의 첫 단계가 뭐야?

"어떤 느낌의 게임을 만들 건지" 기준을 세우는 거야. 이걸 아트 바이블이라고 해.

바로 그림을 그리면 안 되는 거야? 머릿속에 있잖아.

머릿속에만 있는 "중세 판타지"는 사람마다 달라. 다크 소울의 중세? 로아의 중세? 디즈니의 중세? 전부 "중세"인데 완전히 다른 비주얼이잖아.

[아트 바이블이 정의하는 것] 1. 색감 팔레트 (Color Palette) → "우리 게임은 이 10가지 색상만 쓴다" → 예: 로아 = 따뜻한 금+갈색 톤 / 디아블로 = 어두운 적+흑 톤 → 에이전트에게: "hex #8B7355, #C9A87C 계열로" 2. 비율/실루엣 규칙 (Proportion) → "우리 캐릭터는 머리가 7등신" → "무기는 캐릭터 키의 80% 이하" → 에이전트에게: "7 head-tall proportions, weapon max 80% body height" 3. 디테일 수준 (Detail Level) → "현실의 70% 디테일, 만화적 과장 30%" → 에이전트에게: "semi-realistic, slightly stylized" 4. 금지 목록 (Don’t) → "네온 색상 금지" "현대적 요소 금지" "직선 위주 금지" → 에이전트에게: negative prompt로 변환 5. 레퍼런스 보드 (Reference Board) → 비슷한 느낌의 게임/영화/일러스트 수집 → "이 느낌이야"를 구체적으로 → 에이전트에게: image-to-image 레퍼런스로 활용 입력: 게임 기획서 + 머릿속 비전 출력: 아트 바이블 문서 (.pdf, .fig, .notion) + 색감 팔레트 + 레퍼런스 이미지 보드

제1원칙: "기준이 없으면 방향이 없다"

서버에서 API 스펙 없이 개발하면 각자 다른 포맷으로 만드는 것처럼, 아트 바이블 없이 에셋을 만들면 통일감이 제로가 된다.

에이전트 설계 핵심: 아트 바이블 = 모든 아트 에이전트의 시스템 프롬프트. 이걸 먼저 정의해야 나머지 10단계의 에이전트가 일관된 결과를 낸다. LoRA 학습 데이터셋 / Stable Diffusion의 스타일 시드 / 프롬프트 템플릿이 여기서 나온다.

Stage 2. 컨셉 아트 — 2D 설계도

아트 바이블이 있으면 바로 3D 모델을 만들면 되잖아?

질문 하나. 집을 지을 때 설계도 없이 바로 벽돌을 쌓으면 어떻게 될까?

[왜 2D를 먼저 그리나 — 비용 비교] 컨셉 이미지 1장 그리기: 도구: Midjourney 프롬프트 시간: 30초 마음에 안 들면? 프롬프트 수정 → 30초 재생성 10번 수정해도? 5분 3D 모델 1개 만들기: 도구: Blender/ZBrush 시간: 2~8시간 마음에 안 들면? 전체 재작업 10번 수정해도? 80시간 비율: 2D 검증 5분 vs 3D 직접 80시간 = 960배 차이 그래서 원화가 먼저 "이런 느낌이야?"를 2D로 확인하고, 승인된 컨셉으로 3D 작업을 시작하는 거야.
컨셉 아트에서 나오는 산출물이 구체적으로 뭐야?
[컨셉 아트의 산출물 — 3D 모델러를 위한 설계도] 1. 3면도 (Turnaround / Orthographic View) 정면(Front) + 측면(Side) + 후면(Back) 왜 3면이 필요한가: 정면만 보면 "뒷모습"을 모델러가 추측해야 함 → 망토가 있나? 등에 문양이 있나? 머리 뒤는 어떤 형태? → 3면 다 보여줘야 "추측"이 사라짐 3D 모델러의 작업 화면: 모니터 왼쪽 = 3면도 띄워놓기 모니터 오른쪽 = 3D 소프트웨어 → "설계도를 보면서 입체로 만드는 것" 2. 컬러 배리에이션 (Color Variation) 같은 디자인, 다른 색상 3~5개 → "이 갑옷의 1티어/2티어/3티어 색상" → 게임에서 등급별 외형 구분에 사용 3. 소재 콜아웃 (Material Callout) 디자인 위에 화살표로 "이 부분은 금속", "이 부분은 가죽" 표시 → 텍스처 아티스트가 PBR 맵 만들 때 참고 입력: 아트 바이블 + "여전사 궁수" 같은 기획 요청 출력: 3면도 (.png) + 컬러 가이드 + 소재 콜아웃 포맷: .psd (레이어 있음) 또는 .png (최종본)

제1원칙: "3D로 만들기 전에 2D로 검증하는 게 100배 빠르다"

서버에서 코딩 전에 인터페이스를 설계하는 것과 같다. 비용이 낮은 단계에서 방향을 확정하고, 비용이 높은 단계에서는 실행만 한다.

에이전트 설계 핵심: Midjourney/Stable Diffusion으로 컨셉 대량 생성 → 인간이 선택 → 선택된 이미지를 다음 단계(3D 생성)의 입력으로. 에이전트가 "선택지를 만들고" 인간이 "고르는" 구조.

Stage 3. 스컬핑 — 디지털 점토 조각

이제 3D를 만들 차례지? 3D 모델링이 구체적으로 뭘 하는 거야?

첫 단계는 스컬핑(Sculpting)이야. 말 그대로 디지털 점토를 깎고 붙이는 것.

[스컬핑이란] 물리적 비유: 점토 조각상을 만드는 것과 동일 → 덩어리에서 시작 → 큰 형태를 먼저 잡고 (전체 실루엣) → 세부 디테일을 깎아냄 (주름, 근육, 흉터) 왜 "스컬핑"이라는 별도 단계가 있나: 3D 모델링에는 2가지 방식이 있음 방식 1: 폴리곤 모델링 → 사각형/삼각형을 하나씩 배치하고 연결 → 정확한 구조 → 유기적 형태에 부적합 → 건물, 소품, 기계 → 적합 → 캐릭터, 동물 → 부적합 방식 2: 스컬핑 → 수백만 폴리곤의 덩어리를 "조각" → 유기적 형태에 최적 (근육, 피부, 주름) → 캐릭터, 몬스터, 생물 → 적합 → 도구: ZBrush (업계 표준) 스컬핑의 결과물: "하이폴리 모델" → 폴리곤 수: 500만 ~ 2,000만개 → 모든 디테일이 실제 폴리곤으로 표현됨 → 렌더링하면 영화 수준의 디테일 → 하지만 게임에서는 사용 불가 (너무 무거움) 입력: 3면도 (.png) 출력: 하이폴리 메시 (수백만 폴리곤) 포맷: .zpr (ZBrush), .obj, .stl
게임에 쓸 수도 없는 걸 왜 만들어?

직접 쓰는 게 아니라 "디테일 원본"으로 쓰기 때문이야. 이 하이폴리의 디테일을 나중에 "사진 찍어서" 가벼운 모델에 붙이거든. Stage 6(베이킹)에서 다시 나와.

제1원칙: "형태를 먼저 잡고, 구조는 나중에"

처음부터 "게임에 넣을 수 있는 깔끔한 모델"을 만들면 디테일이 제한됨. 먼저 제약 없이 "이상적인 형태"를 만들고(하이폴리), 그 다음에 게임 제약에 맞게 간소화하는(로우폴리) 2단계 방식이 최적.

에이전트 설계 핵심: AI 3D 생성(Meshy, Tripo3D)은 이 단계를 건너뛰고 바로 중간 폴리곤 모델을 만든다. 소품은 이래도 괜찮지만, 캐릭터는 디테일 부족 문제가 생긴다. AI가 발전하면 이 단계도 자동화될 핵심 지점.

Stage 4. 리토폴로지 — 하이폴리를 게임용으로 재구성

하이폴리가 너무 무거우면, 그냥 폴리곤을 줄이면 되는 거 아니야? 자동으로 간소화하는 기능 없어?

있어. "데시메이션(Decimation)"이라고 자동 폴리곤 축소 기능이 있어. 근데 문제가 있어:

[자동 축소 vs 리토폴로지 — 왜 다시 만드나] 자동 축소 (Decimation): 하이폴리 500만 → 자동으로 1만으로 줄임 → 결과: 폴리곤이 "랜덤하게" 배치됨 → 문제: 관절 부분에 폴리곤이 부족하면? → 팔꿈치 구부릴 때 찢어짐 리토폴로지 (Retopology): 하이폴리 위에 "새로운 폴리곤"을 하나씩 깔아서 게임에 최적화된 구조의 로우폴리를 만드는 것 핵심: "어디에" 폴리곤을 배치하느냐 → 관절 부분: 폴리곤 촘촘하게 (에지 루프) → 평평한 부분: 폴리곤 듬성듬성 (절약) → 눈, 입 주변: 표정 변화를 위해 촘촘하게 비유: 자동 축소 = 고해상도 사진을 그냥 축소 (흐릿해짐) 리토폴로지 = 핵심 부분만 선명하게 다시 그리기 서버 비유: 자동 축소 = 모든 쿼리에 LIMIT 100 때리기 (데이터 유실) 리토폴로지 = 필요한 컬럼만 SELECT하는 최적화 쿼리
"에지 루프"가 뭔데? 이전 문서에서도 나왔는데.
[에지 루프 — 관절이 자연스럽게 움직이는 비밀] 에지 루프 = 메시를 한 바퀴 감싸는 폴리곤 띠 왜 필요한가: 팔꿈치를 구부린다고 생각해봐. 안쪽은 압축되고, 바깥쪽은 늘어남. 에지 루프가 없으면: 폴리곤 4개가 커다란 판으로 연결 → 접을 때 판이 통째로 꺾임 = 종이접기처럼 날카로운 선 에지 루프가 있으면: 관절 주변에 얇은 폴리곤 띠가 3~5겹 → 접을 때 띠가 하나씩 접힘 = 부드러운 곡선 어디에 필요한가: 팔꿈치, 무릎, 어깨, 손가락 관절 ← 구부러지는 곳 전부 입, 눈 주변 ← 표정이 변하는 곳 허리, 목 ← 비트는 동작 개수: 관절당 에지 루프 3~5개가 일반적 관절 12개 × 평균 4개 = 48개의 에지 루프 배치 필요 입력: 하이폴리 메시 (수백만 폴리곤) 출력: 로우폴리 메시 (5,000 ~ 30,000 폴리곤, 게임 해상도에 따라) 포맷: .fbx, .obj

제1원칙: "실시간 렌더링에는 폴리곤 예산이 있다"

초당 60프레임을 그리려면 1프레임에 16ms. 이 시간 안에 화면의 모든 폴리곤을 처리해야 한다. 캐릭터 하나에 500만 폴리곤이면 한 명도 못 그린다. 예산(Budget) 안에서 최대 효과를 내는 배치가 핵심.

에이전트 설계 핵심: 자동 리토폴로지 도구가 이미 존재함 (Instant Meshes, QuadRemesher). AI가 "폴리곤 버짓 15K, 관절에 에지루프 5겹" 같은 규칙을 받으면 Blender Python으로 자동 적용 가능. 이 단계의 에이전트화 가능성은 높다.

Stage 5. UV 언래핑 — 3D를 2D로 펼치기

UV가 뭐야? 이전 문서에서 텍스처를 "입힌다"고 했는데, 어떻게 입히는 건데?

축구공 선물 포장해 본 적 있어? 둥근 물체를 평평한 종이로 감싸려면 종이를 어딘가 잘라서 펼쳐야 하잖아. 그게 UV야.

[UV 언래핑의 핵심 개념] 문제: 3D 모델 = 입체 텍스처 이미지 = 2D 평면 어떻게 2D 이미지를 3D 표면에 감쌀까? 답: 3D 표면을 "가위로 잘라서 펼치면" 2D가 됨 이 펼쳐진 2D 좌표를 UV 좌표라고 부름 U = 가로 (x와 같은 개념) V = 세로 (y와 같은 개념) 왜 xy 안 쓰나? → 3D 공간의 xyz와 헷갈리니까 비유: 지구본 (3D) → 세계 지도 (2D) 지구본을 "메르카토르 도법"으로 펼친 게 세계 지도 그 세계 지도 위에 나라 색칠하면 지구본에도 색이 묻음 3D 캐릭터 (3D) → UV 맵 (2D) UV 맵 위에 텍스처 그리면 캐릭터에도 그림이 묻음 [UV 맵의 모습] 사각형 안에 캐릭터의 "가죽"이 납작하게 펼쳐져 있음 ┌────────────────────────┐ │ [머리] [팔L] │ │ [몸통 앞] [팔R] │ │ [몸통 뒤] [다리L] │ │ [허리] [다리R] │ └────────────────────────┘ 이 사각형 위에 색칠하면 → 3D 캐릭터에 반영됨
"어디를 자르느냐"가 중요하겠네?

핵심을 짚었어. 잘못 자르면 텍스처 이음새(seam)가 눈에 보여서 부자연스러워.

[UV 커팅의 규칙] 좋은 UV: → 이음새(seam)가 "안 보이는 곳"에 위치 → 겨드랑이 안쪽, 다리 안쪽, 머리카락 아래 → 텍스처 공간을 낭비 없이 꽉 채움 나쁜 UV: → 이음새가 얼굴 한가운데, 팔 바깥쪽 → 텍스처 공간에 빈 곳이 많음 (해상도 낭비) → 심하게 늘어나거나 찌그러진 UV 아일랜드 서버 비유: UV = 데이터베이스 인덱스 설계 → 인덱스를 어디에 거느냐에 따라 쿼리 성능이 갈리듯 → UV를 어디서 자르느냐에 따라 텍스처 품질이 갈림 → 둘 다 "보이지 않는 구조"인데 결과에 결정적 영향 입력: 로우폴리 메시 (.fbx) 출력: UV 좌표가 설정된 메시 (.fbx with UV) 포맷: 메시 파일 안에 UV 데이터가 포함됨

제1원칙: "3D 표면에 2D 이미지를 입히려면, 3D를 2D로 펼치는 좌표 매핑이 필요하다"

지구본을 세계지도로 만드는 도법과 동일한 수학적 문제. 왜곡을 최소화하면서 펼치는 것이 목표.

에이전트 설계 핵심: UV 자동 언래핑은 Blender에 내장되어 있고 (Smart UV Project), Blender Python으로 완전 자동화 가능. "이음새는 안 보이는 곳에" 같은 규칙도 코드로 설정 가능. 에이전트화 난이도 낮음.

Stage 6. 베이킹 — 하이폴리의 디테일을 로우폴리에 "굽기"

아까 스컬핑에서 "하이폴리의 디테일을 사진 찍어서 붙인다"고 했잖아. 그게 이 단계야?

맞아. "베이킹"이라고 부르는 이유는 빵을 "굽는" 것처럼, 디테일을 텍스처에 "구워넣는" 것이거든.

[베이킹의 작동 원리] 준비물: → 하이폴리 메시 (500만 폴리곤, 디테일 원본) → 로우폴리 메시 (1만 폴리곤, UV 있음) → 두 메시를 "겹쳐놓기" 과정: 로우폴리의 모든 UV 픽셀에서 "빛"을 쏨 → 그 빛이 하이폴리 표면에 부딪힘 → 부딪힌 지점의 방향 정보(노말)를 기록 → 그 방향 정보를 2D 이미지로 저장 = 노말맵 결과: 로우폴리(1만 폴리곤)인데 하이폴리(500만 폴리곤)의 디테일이 "그려져" 있음 → 빛이 이 노말맵을 보고 "울퉁불퉁하게" 반응 → 눈으로 보면 하이폴리처럼 디테일해 보임 → 실제 폴리곤은 1만개뿐 → 가벼움 비유: 하이폴리 = 대리석 조각상 (실제 요철이 있음) 로우폴리 = 매끈한 마네킹 노말맵 = 조각상의 요철을 "사진 찍어서" 마네킹에 붙인 것 빛이 비추면? 마네킹인데 조각상처럼 보임 [베이킹으로 생성되는 맵들] 노말맵 (Normal Map): 표면 방향 → 가짜 요철 AO맵 (Ambient Occlusion): 틈새 어둡기 → 깊이감 커바처맵 (Curvature): 모서리 밝기 → 마모/닳은 표현 포지션맵 (Position): 공간 위치 → 그라데이션 효과용 입력: 하이폴리 + 로우폴리(UV 있음) 출력: 노말맵, AO맵 등 (.png, .exr) 포맷: 2048x2048 또는 4096x4096 이미지

제1원칙: "디테일은 폴리곤이 아니라 텍스처로 속인다"

게임 그래픽의 핵심 트릭. 실제로 복잡한 형태를 만드는 대신, "복잡해 보이는 이미지"를 단순한 형태에 붙인다. GPU 비용 1/500로 거의 같은 시각 효과.

에이전트 설계 핵심: 베이킹은 완전 자동화 가능한 단계. Blender Python / Substance Baker로 "하이폴리+로우폴리 넣으면 노말맵+AO맵 출력" 스크립트 한 줄. 에이전트가 가장 쉽게 처리하는 단계 중 하나.

Stage 7. 텍스처링 — PBR 물리 데이터 제작

베이킹으로 노말맵은 나왔어. 이제 색칠하는 거지?

"색칠"이라고 하면 핵심을 놓쳐. 물리 데이터를 만드는 거야.

[텍스처링 = 6장의 물리 데이터를 만드는 것] "왜 그냥 색칠이 아닌가?" 옛날 게임 (2005년 이전): Albedo 1장만 있었음 → "이 부분은 금속처럼 보이게 그려" (그림으로 속이기) → 조명이 바뀌면? 속임이 깨짐 → 낮에 보면 금속 같은데, 밤에 보면 그냥 그림 현대 게임 (PBR): 6장의 물리 속성 데이터 → "이 부분은 실제로 금속이야" (물리적 사실) → 조명이 바뀌어도? 물리 법칙대로 자동 반응 → 낮이든 밤이든 동굴이든 비가 오든 자연스러움 텍스처 아티스트의 실제 작업: 1. Substance Painter에서 3D 모델 열기 2. 베이킹된 노말맵/AO맵을 가이드로 활용 3. 각 부분에 "머티리얼" 할당 → 갑옷 부분: 금속 머티리얼 (Metallic=1, Roughness=0.3) → 가죽 부분: 가죽 머티리얼 (Metallic=0, Roughness=0.7) → 보석 부분: 투명 머티리얼 (Emissive 추가) 4. 디테일 추가: 긁힌 자국, 녹, 먼지, 마모 5. 6장의 맵을 한꺼번에 내보내기 각 맵의 역할 (복습): Albedo = 순수한 색상 (빛 정보 없음) Normal = 표면 방향 (가짜 요철) [베이킹에서 옴] Roughness = 표면 거칠기 (0=거울, 1=분필) Metallic = 금속 여부 (0=비금속, 1=금속) AO = 틈새 어둡기 [베이킹에서 옴] Emissive = 자체 발광 (마법 문양, 룬) 입력: UV 있는 로우폴리 + 베이킹된 맵들 + 소재 콜아웃 출력: PBR 텍스처 세트 (6장) 포맷: .png / .tga (각 2048x2048 또는 4096x4096)

제1원칙: "빛의 물리법칙에 따라 표면 속성을 정의하면, 모든 환경에서 자연스럽다"

"보이는 대로 그리기"가 아니라 "물리적으로 맞게 데이터 넣기". 그러면 엔진의 물리 셰이더가 나머지를 자동으로 처리한다.

에이전트 설계 핵심: AI가 가장 잘하는 단계 (90%). Stable Diffusion으로 Albedo 생성 → Materialize/MatFuse로 나머지 5장 자동 생성. "stone, roughness 0.7, metallic 0" 같은 물리 파라미터를 프롬프트로 지정 가능. 에이전트 체인: 텍스처 생성 AI → PBR 변환 도구 → 품질 검증.

Stage 8. 리깅 — 뼈대와 스키닝

텍스처까지 입혔으면 이제 완성 아니야?

정적 소품(검, 건물, 나무)이면 여기서 끝. 하지만 움직여야 하는 모든 것은 리깅이 필요해.

[리깅의 데이터 변환] 입력: 정적 메시 (텍스처 입혀진 3D 모델) → 예쁜데 T자로 서있기만 함. 팔 못 내리고, 고개 못 돌리고. 변환 과정: 1. 스켈레톤 배치: 뼈 50~100개를 모델 안에 심기 → 계층 구조: 척추 → 어깨 → 팔 → 손 → 손가락 → 부모 뼈가 움직이면 자식 뼈도 따라감 → 어깨를 올리면 팔-손-손가락이 다 따라올라감 2. 스키닝: 각 폴리곤이 어떤 뼈에 붙는지 연결 → 팔 폴리곤 → 팔 뼈에 연결 → 관절 부근 폴리곤 → 2개 뼈에 비율로 연결 (웨이트) 3. 웨이트 페인팅: 스키닝의 비율을 미세 조정 → 이전 문서에서 상세 설명 출력: 스켈레탈 메시 (뼈대 + 메시 + 텍스처가 한 파일) 포맷: .fbx (스켈레톤 포함) [서버 비유] 정적 메시 = 데이터만 있는 구조체 (struct) 리깅 = 그 구조체에 "동작 인터페이스"를 부여 스켈레톤 = 메소드 시그니처 (moveShoulder, bendElbow) 웨이트 = 각 메소드가 어떤 멤버 변수에 영향을 주는지

제1원칙: "움직이려면 계층적 구조(뼈대)가 필요하다"

폴리곤 하나하나를 개별로 움직일 수 없다(수만 개). 뼈대라는 "제어 구조"를 만들고, 뼈 50개만 움직이면 수만 폴리곤이 따라가게 하는 것. 계층 구조(부모-자식)가 핵심.

에이전트 설계 핵심: 인간형 = Mixamo API로 완전 자동 (30초). Blender Python으로 Mixamo 리깅 결과를 받아서 후처리 가능. 비인간형은 "커스텀 스켈레톤 템플릿"을 미리 만들어두면 에이전트가 적용 가능.

Stage 9. 애니메이션 — 시간에 따른 변환값의 기록

리깅이 "움직일 수 있게 한 것"이면, 애니메이션은 "실제로 움직이는 것"이지?

정확해. 근데 서버 개발자라면 이 정의가 더 와닿을 거야:

[애니메이션의 본질 — 서버 개발자 관점] 애니메이션 = 타임라인 DB 테이블 시간(ms) | 어깨 회전 | 팔꿈치 각도 | 손목 회전 0 | (0, 0, 0) | 0도 | (0, 0, 0) 100 | (10, 0, 5) | -15도 | (5, 0, 0) 200 | (30, 0, 15) | -45도 | (15, 0, -5) 300 | (60, 0, 30) | -90도 | (30, 5, -10) ... 각 행 = 키프레임 (특정 시점의 뼈대 상태) 중간값 = 보간(Interpolation)으로 자동 계산 결국: 애니메이션 데이터 = 뼈 ID + 시간 + Transform(위치, 회전, 크기) → 이건 그냥 시계열 데이터 (Time Series) → DB에서 타임스탬프별 값 저장하는 것과 완전히 동일 왜 이게 중요한가: 애니메이션이 "감각의 영역"이라고 하지만, 실제 데이터 구조는 순수한 수치. 수치를 다루는 건 프로그래머가 강한 영역.
그러면 에이전트가 숫자만 생성하면 되는 거 아니야?

데이터 생성은 쉬워. 문제는 "좋은 숫자"를 생성하는 게 어렵다는 거야.

[애니메이션 데이터의 "좋은 숫자" vs "나쁜 숫자"] 물리적으로 정확한 걷기: 각 프레임의 관절 각도가 인체역학 교과서대로 → 결과: "맞는데... 로봇 같아" (언캐니 밸리) 좋은 걷기: 약간의 비대칭, 미세한 상체 흔들림, 발 딛을 때 살짝 멈춤 → 결과: "자연스럽다!" (인간의 미세 불규칙성) 차이: 물리 정확도는 AI가 잘함 "미세한 불규칙성의 리듬"은 인간 감각의 영역 해결법 (에이전트 전략): 1. 기본 동작: Mixamo 라이브러리 (이미 "좋은 숫자"가 있음) 2. 커스텀 동작: 모캡 (인간이 직접 움직여서 기록) 3. 보정: 코드로 미세 조정 (히트스톱, 과장, 블렌딩) 즉, AI가 "0에서 만드는 게 아니라" "기존 좋은 데이터를 가져와서 조합/변형"하는 전략 입력: 스켈레탈 메시 (.fbx with skeleton) 출력: 애니메이션 클립 (.anim, .fbx) 데이터: 뼈 ID × 시간 × Transform 의 테이블

제1원칙: "애니메이션은 시간에 따른 뼈대 변환값의 기록이다"

본질은 타임시리즈 데이터. 복잡해 보이지만 구조는 단순하다. 어려운 건 데이터 생성이 아니라 "좋은 데이터"의 기준이 주관적이라는 것.

에이전트 설계 핵심: "생성"보다 "조합" 전략이 유효. Mixamo에서 2000개+ 클립 다운로드 → 게임 요구에 맞게 리타겟팅/블렌딩 → 코드로 히트스톱/과장 추가. 이 "조합 파이프라인"은 완전 자동화 가능.

Stage 10. VFX & 셰이더 — 수학으로 만드는 시각 효과

모델도 있고 텍스처도 있고 애니메이션도 있으면, 이펙트는 왜 별도 단계야?

모델+텍스처+애니메이션 = "현실에 있는 것"을 표현하는 거야. VFX = "현실에 없는 것"을 보여주는 거야.

[VFX의 데이터 변환 — 다른 단계와 다른 점] 기존 단계들: 실체가 있는 오브젝트를 가공함 컨셉(실체) → 모델(실체) → 텍스처(실체) VFX: 실체가 없는 것을 "만들어냄" → 불은 고체가 아님 → 메시가 없음 → 번개는 형태가 매번 다름 → 고정 텍스처가 없음 → 마법진은 현실에 없음 → 레퍼런스가 없음 그래서 VFX는 3가지 요소의 조합: 1. 파티클 (Particle) 입력: 스프라이트 이미지 (.png, 작은 불꽃 1장) 변환: 수백~수천 개를 규칙에 따라 발사 출력: 불, 연기, 스파크, 궤적 등의 효과 규칙 = 파라미터: 발사 속도, 방향, 수명, 크기 변화, 색상 변화, 중력 2. 셰이더 (Shader) 입력: 수학 공식 (HLSL/GLSL 코드) 변환: 픽셀마다 색상을 실시간 계산 출력: 왜곡, 홀로그램, 디졸브, 에너지 흐름 효과 핵심: 셰이더 = 함수 float4 pixelColor = myFunction(uv, time, params); → 모든 픽셀에 이 함수를 적용 → 시각 효과 3. 포스트 프로세싱 (Post-Processing) 입력: 최종 렌더링된 화면 전체 (2D 이미지) 변환: 화면 전체에 필터 적용 출력: 블룸, 모션블러, 색보정, 비네팅 비유: 카메라 필터/Instagram 필터와 동일 개념 입력: 스프라이트 텍스처 + 셰이더 코드 + 파라미터 설정 출력: 파티클 시스템 + 머티리얼 + 포스트 프로세싱 설정 포맷: .hlsl(셰이더), .vfx(파티클), .mat(머티리얼)

제1원칙: "현실에 없는 것은 수학(코드)과 작은 이미지의 조합으로 만든다"

VFX의 3요소 중 파티클은 "이미지 + 파라미터(숫자)", 셰이더는 "순수 코드", 포스트프로세싱은 "설정값". 세 가지 모두 코드/데이터 영역.

에이전트 설계 핵심: 프로그래머에게 가장 유리한 단계. 셰이더 = 코드 작성 (AI 코딩 에이전트 직접 사용). 파티클 텍스처 = AI 이미지 생성. 파라미터 = 수치 최적화. 3가지 모두 에이전트가 강한 영역.

Stage 11. 엔진 통합 & 최적화 — "돌아가게" 만들기

에셋이 다 만들어졌으면 엔진에 넣기만 하면 되는 거 아니야?

"넣기만"은 되는데, 그 상태로는 프레임이 15 나와.

[엔진 통합 시 해야 하는 최적화] 문제: 에셋을 "있는 그대로" 넣으면 왜 느린가? 1. 드로우콜 (Draw Call) 문제 GPU에게 "이거 그려"라고 명령하는 횟수 → 무기 1개, 갑옷 1개, 투구 1개 = 드로우콜 3번 → 캐릭터 100명 × 3 = 300번 → 배경 소품 1000개 = 1000번 → 합계 1300번 → CPU 병목 해결: 배칭 (Batching) & 인스턴싱 (Instancing) → 같은 머티리얼을 쓰는 오브젝트를 한 번에 그림 → 나무 500그루를 1번의 드로우콜로 → CPU 부담 1/500 2. LOD (Level of Detail) 가까이 있으면: 1만 폴리곤 모델 중간 거리: 3천 폴리곤 모델 멀리 있으면: 500 폴리곤 모델 → 같은 오브젝트의 3가지 버전을 만들어둠 → 거리에 따라 자동 교체 3. 텍스처 아틀라스 (Texture Atlas) 개별 텍스처 100장 → 1장의 큰 이미지에 합치기 → GPU가 텍스처를 바꾸는 비용 절감 4. 오클루전 컬링 (Occlusion Culling) 카메라에 안 보이는 건 아예 안 그림 → 건물 뒤에 있는 NPC = 렌더링 스킵 5. 에셋 임포트 설정 텍스처 압축 포맷 (BC7, ASTC) 메시 임포트 스케일 애니메이션 압축 (키프레임 간소화) 콜리전 설정 (충돌 판정용 간소화 메시) 서버 비유: 에셋 최적화 = 쿼리 최적화 드로우콜 = DB 라운드트립 LOD = 응답 크기를 상황에 따라 조절 아틀라스 = 여러 쿼리를 배치로 합침 오클루전 = 불필요한 데이터 안 보냄 입력: 모든 에셋 (메시, 텍스처, 애니메이션, VFX) 출력: 최적화된 게임 빌드 포맷: 엔진별 전용 포맷 (.uasset, .asset 등)

제1원칙: "'보이는 것'과 '돌아가는 것'은 다르다"

아무리 예쁜 에셋도 60fps로 돌아가지 않으면 게임에 못 넣는다. 최적화 = "보이는 품질을 최대한 유지하면서 비용을 최소화하는 것". 서버의 성능 최적화와 완전히 동일한 사고 방식.

에이전트 설계 핵심: 최적화는 "규칙 기반"이라 에이전트화에 최적. "텍스처 4K 이상이면 2K로 리사이즈" "폴리곤 3만 초과면 LOD 3단계 생성" "같은 머티리얼은 아틀라스로 합침" — 전부 Blender Python + 엔진 CLI로 자동화 가능.

Part 12. 11단계를 에이전트 체인으로 — 전체 그림

11단계를 전부 봤어. 이제 이걸 에이전트로 어떻게 엮는 건데?

서버 에이전트 시스템을 생각해봐. 각 단계 = 에이전트, 산출물 = 핸드오프 포맷, 제1원칙 = 에이전트의 지시서.

[아트 에이전트 체인 — 서버 에이전트와 동일 구조] 서버 에이전트 체인: 분석(opus) → 구현(sonnet) → 빌드(haiku) → 검증 아트 에이전트 체인: 설계 → 시각화 → 조형 → 최적화 → 표면 → 구조 → 동작 → 효과 → 통합 구체적으로: Stage 에이전트 도구 입력 → 출력 ===== ======== ==== ============== 1 Art Director 프롬프트 템플릿 기획서 → 아트 바이블 2 Concept Agent Midjourney/SD 아트바이블 → 3면도 .png 3 Sculpt Agent Meshy/Tripo3D 3면도 → 하이폴리 .obj 4 Retopo Agent Blender Python 하이폴리 → 로우폴리 .fbx 5 UV Agent Blender Python 로우폴리 → UV .fbx 6 Bake Agent Blender Python 하이+로우 → 노말맵 .png 7 Texture Agent SD + MatFuse UV메시 → PBR 6장 .png 8 Rig Agent Mixamo API 메시 → 스켈레탈 .fbx 9 Anim Agent Mixamo + 모캡 스켈레톤 → 클립 .anim 10 VFX Agent 코딩 에이전트 텍스처+코드 → 파티클/셰이더 11 Optimize Agent Blender Python 모든 에셋 → 최적화 빌드 핸드오프 프로토콜: 각 에이전트의 출력 포맷이 다음 에이전트의 입력 포맷과 일치 → 서버에서 API 인터페이스를 맞추는 것과 동일 → .fbx, .png, .anim 등이 "프로토콜"의 역할

이 문서에서 1→11 직렬로 설명했지만, 실전에서는 피드백 루프가 돈다.

텍스처(7) 입혀봤더니 모델(3) 형태가 어색해 → 모델 수정 → UV(5) 재작업 → 베이킹(6) 재실행

이 반복 루프를 에이전트로 자동화하면? 서버의 "빌드 실패 → 수정 → 재빌드" 루프와 동일한 구조.

핵심: 11단계의 제1원칙을 알면 에이전트 설계가 가능하다

각 단계가 "왜" 필요한지 모르면 → "AI야 캐릭터 만들어" (불명확)

각 단계의 제1원칙을 알면 → "3면도를 입력으로 받아서, 관절에 에지루프 5겹이 있는 15K 폴리곤 로우폴리를 .fbx로 출력해" (정확)

제1원칙 = 에이전트의 입력-변환-출력 스펙. 이 문서의 녹색 박스 11개가 그 스펙이다.

핵심 정리 — 11단계의 제1원칙

  • 아트 바이블 — "기준이 없으면 방향이 없다." 모든 에이전트의 시스템 프롬프트
  • 컨셉 아트 — "2D로 검증이 100배 빠르다." 비용 낮은 단계에서 방향 확정
  • 스컬핑 — "형태 먼저, 구조는 나중에." 제약 없이 이상적 형태를 만든 뒤 간소화
  • 리토폴로지 — "폴리곤 예산이 있다." 관절에 에지루프, 평면은 듬성듬성
  • UV 언래핑 — "3D에 2D를 입히려면 좌표 매핑이 필요하다." 이음새를 안 보이는 곳에
  • 베이킹 — "디테일은 텍스처로 속인다." GPU 비용 1/500로 같은 효과
  • 텍스처링 — "물리법칙대로 데이터를 넣으면 모든 환경에서 자연스럽다." PBR 6장
  • 리깅 — "움직이려면 계층적 뼈대가 필요하다." 뼈 50개로 폴리곤 수만 개 제어
  • 애니메이션 — "시간 × 뼈대 변환값의 기록." 타임시리즈 데이터
  • VFX — "현실에 없는 건 수학(코드)+이미지로 만든다." 프로그래머 최적 영역
  • 최적화 — "'보이는 것'과 '돌아가는 것'은 다르다." 규칙 기반 자동화 최적
