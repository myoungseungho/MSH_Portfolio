서버 점검 없이 버그를 고치는 3가지 방법

무중단 핫픽스 전략 - 뭘 고치느냐에 따라 답이 다르다

핫픽스의 난이도는 "뭘 고치느냐"에 따라 다르다

라이브 서비스에서 버그를 발견했는데, 서버 점검 없이 고칠 수 있어?

경우에 따라 다르다. 핵심은 "뭘 고치느냐"야.

고치려는 것이 데이터냐, 스크립트냐, C++ 코어냐에 따라 난이도가 완전히 달라.

왜 세 가지가 달라? 어차피 코드 수정해서 배포하면 되는 거 아니야?

"코드 수정 후 배포"가 곧 "서버 끄고 켜기"를 의미하기 때문이야.

서버를 끄지 않고 바꿀 수 있는 것이 있고, 반드시 재시작해야만 바뀌는 것이 있어.

그 차이가 핫픽스 가능 여부를 결정해.

쉬움 어려움 | | v v 데이터/설정 변경 → 스크립트 로직 변경 → C++ 서버 코어 변경 (테이블 리로드) (스크립트 리로드 / (Rolling Update / Rolling Update) 바이너리 교체)

핫픽스가 가능한지는 서버 아키텍처를 설계한 시점에 이미 결정된다.

불이 나고 나서 소화기를 사는 게 아니라, 건물 지을 때 스프링클러를 설치해야 하는 것처럼.

Case 1. 데이터/설정 변경 (가장 쉬움)

"몬스터 HP가 10만으로 잡혀야 하는데, 실수로 100만으로 나갔어!" 이런 거 어떻게 고쳐?

이런 유형이 가장 쉬워.

몬스터 HP, 아이템 드랍률, 퀘스트 보상 수치 같은 건 보통 데이터 테이블에 들어 있거든.

코드 안에 "HP = 100000"이라고 박혀 있는 게 아니라, DB나 설정 파일에서 읽어오는 구조야.

그게 무슨 방식이야? 이름이 있어?

Data-Driven Design (데이터 드리븐 디자인)이라고 해.

정의: 게임 동작에 필요한 수치/설정을 코드가 아닌 외부 데이터(DB, JSON, CSV 등)에서 읽어오는 설계 방식.

왜 필요: 기획자가 코드를 수정하지 않고도 게임 밸런스를 조정할 수 있어. 핫픽스도 서버 재시작 없이 가능.

안 쓰면: 몬스터 HP 하나 바꾸려고 코드 수정 → 빌드 → 서버 점검 → 재배포. 수치 하나에 30분 점검.

그래서 데이터 드리븐이면 어떻게 핫픽스해?

리로드 명령 하나면 끝이야.

DB에서 몬스터 HP를 100만 → 10만으로 고치고, 서버에 "테이블 다시 읽어!"라고 명령하면 돼.

[핫픽스 흐름] 1. 기획팀: "몬스터 HP 100만은 너무 높아!" 2. DB에서 수정: UPDATE monster_stats SET hp = 100000 WHERE id = 301; 3. 운영툴에서 리로드 명령: POST /admin/reload-table/monster_stats 4. 서버가 DB에서 데이터를 다시 읽어옴 5. 다음 전투부터 HP 10만 적용 서버 재시작? 필요 없음. 유저 접속 끊김? 없음. 소요 시간? 수 초.
이거 아무 서버에서나 돼?

아니. 전제 조건이 있어.

게임 데이터가 코드에 하드코딩되어 있으면 불가능해.

// 하드코딩 (핫픽스 불가능) int monsterHP = 1000000; // 이거 바꾸려면 코드 수정 → 빌드 → 재시작 // 데이터 드리븐 (핫픽스 가능) int monsterHP = DataTable::Get("monster_stats", 301, "hp"); // DB에서 읽어오니까 DB만 바꾸면 됨

결론: 데이터 드리븐으로 설계된 서버라면, 수치 버그는 점검 없이 수 초 만에 핫픽스 가능.

Case 2. 스크립트/로직 변경 (중간 난이도)

"퀘스트 완료 조건 판정 로직에 버그가 있어. 10마리 잡아야 하는데 9마리만 잡아도 완료 처리돼." 이건?

이건 수치가 아니라 로직이 잘못된 거잖아.

DB 값을 바꿔서 해결되는 게 아니야. 코드를 고쳐야 해.

여기서 두 가지 방법이 있어.

방법 A: 스크립트 핫 리로드

서버의 게임 로직을 Lua, Python 같은 스크립트 언어로 작성해뒀다면,

스크립트 파일만 수정하고 "다시 읽어!" 명령을 보내면 돼.

C++ 서버 바이너리를 재시작할 필요가 없어.

[스크립트 핫 리로드 흐름] 1. 버그 발견: quest_complete.lua에서 >= 대신 > 사용 2. 스크립트 수정: if kill_count >= required_count then ... 3. 운영툴에서: POST /admin/reload-script/quest_complete 4. 서버가 Lua VM에 스크립트를 다시 로드 5. 다음 퀘스트 완료 판정부터 수정 적용 서버 재시작? 필요 없음. 유저 접속 끊김? 없음.
스크립트 레이어가 없으면? 로직이 C++에 있으면?

그러면 방법 B로 가야 해.

Rolling Update (롤링 업데이트)로 서버를 한 대씩 교체하는 거야.

Rolling Update가 뭐야?

정의: 서버를 한꺼번에 끄지 않고, 한 대씩 순서대로 새 버전으로 교체하는 배포 방식.

왜 필요: 서버가 여러 대일 때, 전체를 동시에 끄면 서비스 중단. 한 대씩 바꾸면 나머지가 살아 있으니까 유저 입장에선 "점검 없음".

안 쓰면: 서버 10대를 한 번에 내리면 전체 유저가 동시에 접속 끊김 = 점검 공지 필수.

구체적으로 어떤 순서야?

서버가 A, B, C 세 대 있다고 하자.

[Rolling Update 상세 흐름] 1단계: 서버 A를 "드레인 모드"로 전환 → 서버 A에 신규 접속 차단 (기존 유저만 유지) 2단계: 서버 A의 기존 유저를 서버 B, C로 이전 → 세션 마이그레이션 (유저가 잠깐 로딩 화면 봄) 3단계: 서버 A 종료 → 새 바이너리 배포 → 재시작 → 이 동안 서버 B, C가 트래픽 처리 4단계: 서버 A 다시 활성화 → 새 버전으로 정상 운영 시작 5단계: 서버 B에 대해 1~4단계 반복 6단계: 서버 C에 대해 1~4단계 반복 결과: 전체 점검 없이 모든 서버가 새 버전으로 교체됨
"드레인 모드"가 뭐야?

Drain Mode (드레인 모드) - 서버를 "물 빠지듯" 비우는 상태.

정의: 서버가 신규 접속은 거부하고, 기존 접속만 유지하는 모드. 기존 유저가 나가거나 이전되면 서버가 자연스럽게 비워짐.

왜 필요: 서버를 끄기 전에 유저를 안전하게 빼내야 하니까. 갑자기 끄면 유저가 진행 중이던 전투/거래 데이터가 날아갈 수 있어.

안 쓰면: 서버 강제 종료 → 유저 강제 퇴장 → "내 아이템 어디 갔어!" 민원 폭주.

Rolling Update의 장단점은?

강점: 전체 점검 없음. 유저는 잠깐 로딩 화면을 보는 정도.

약점: 세션 마이그레이션이 구현되어 있어야 함.

게임 서버가 유저 상태(HP, 위치, 인벤토리)를 메모리에 들고 있는 Stateful 서버라면, 유저를 다른 서버로 옮기는 게 매우 어려워.

"지금 보스전 중인 유저를 다른 서버로 옮겨"가 말처럼 쉽지 않거든.

그러면 언제 Rolling Update를 쓸 수 있어?

Stateless에 가까운 서비스이거나, 세션 이전 로직을 이미 구현해놓은 경우에 적합해.

예를 들어 웹 API 서버, 매칭 서버, 또는 세션 데이터를 Redis 같은 외부 저장소에 두는 구조.

Case 3. C++ 서버 코어 변경 (가장 어려움)

"서버에 메모리 릭이 있어서 3일마다 크래시가 나." 이건 어떻게 핫픽스해?

이건 가장 어려운 케이스야.

메모리 릭, 크래시 버그, 네트워크 처리 로직 같은 건 전부 C++ 서버 바이너리 안에 있어.

C++ 바이너리는 실행 중에 코드를 교체하는 게 사실상 불가능해.

왜 불가능해? 파일만 바꾸면 안 돼?

C++ 바이너리는 실행할 때 메모리에 올라가.

디스크의 파일을 바꿔봤자, 이미 메모리에서 돌고 있는 코드는 안 바뀌어.

바이너리를 교체하려면 프로세스를 종료하고 다시 시작해야 해.

= 결국 서버를 꺼야 한다는 뜻.

그러면 방법이 아예 없어?

한 가지 방법이 있어: Rolling Update가 사실상 유일한 방법.

아까 Case 2에서 봤던 그 방식이야.

서버를 한 대씩 끄고 → 새 바이너리 배포 → 재시작.

전체 점검은 아니지만, 서버 한 대 한 대는 재시작이 필요해.

DLL로 분리하면 교체 가능하지 않아?

이론적으로는 가능해. 특정 로직을 DLL (Dynamic Link Library, 동적 링크 라이브러리)로 분리하고, 런타임에 언로드 → 교체 → 리로드하는 방식.

하지만 이건 서버 설계 시점부터 DLL 핫 리로드를 고려해야 해.

이미 모노리식으로 빌드된 서버에 "지금부터 DLL 분리해서 핫 리로드 합시다"는 거의 불가능에 가까워.

메모리 레이아웃, 전역 상태, 스레드 안전성까지 전부 고려해야 하거든.

핵심: 설계 시점에 결정된다

결국 핫픽스를 잘 하려면 뭘 준비해야 해?

3가지가 갖춰져 있으면 대부분의 라이브 버그를 무점검으로 고칠 수 있어.

[무중단 핫픽스 3종 세트] 1. Data-Driven Design (데이터 드리븐) → 게임 수치를 외부 데이터로 분리 → 수치 변경은 리로드 한 방 2. 스크립트 레이어 분리 → 게임 로직을 Lua/Python 등으로 분리 → 로직 변경은 스크립트 리로드로 해결 3. 세션 마이그레이션 → 유저를 다른 서버로 안전하게 옮기는 기능 → C++ 코어 변경 시 Rolling Update 가능

문제는, 이 3가지를 라이브 중에 추가하는 건 거의 불가능하다는 거야.

서비스 시작한 뒤에 "아, 핫픽스 인프라를 만들어야겠다" 하면 이미 늦어.

서버 아키텍처를 설계하는 시점에 미리 준비해야 해.

비유: 건물 화재 대응

화재 대응은 불이 났을 때가 아니라, 건물을 설계할 때 결정된다.

스프링클러, 비상구, 방화벽 - 전부 건물 지을 때 넣는 거지,
불나고 나서 "스프링클러 설치합시다"는 안 돼.

서버도 마찬가지야.
데이터 드리븐, 스크립트 분리, 세션 마이그레이션 -
전부 서버 설계할 때 넣는 거지,
라이브 터지고 나서 "핫픽스 인프라 만들자"는 안 돼.

용어 사전

용어 의미
Hotfix (핫픽스) 라이브 서비스 중에 긴급하게 버그를 수정하는 패치
Data-Driven Design (데이터 드리븐 디자인) 게임 수치/설정을 코드가 아닌 외부 데이터(DB, 파일)에서 읽어오는 설계
Hot Reload (핫 리로드) 서버를 재시작하지 않고, 데이터나 스크립트를 다시 불러오는 것
Rolling Update (롤링 업데이트) 서버를 한 대씩 순서대로 새 버전으로 교체하는 배포 방식
Drain Mode (드레인 모드) 서버가 신규 접속을 거부하고, 기존 접속만 유지하며 서서히 비워지는 상태
Session Migration (세션 마이그레이션) 유저의 접속 상태를 한 서버에서 다른 서버로 안전하게 옮기는 것
DLL (Dynamic Link Library, 동적 링크 라이브러리) 실행 중에 로드/언로드할 수 있는 코드 모듈. 런타임 교체에 활용 가능
Stateful / Stateless Stateful: 서버가 유저 상태를 메모리에 보관. Stateless: 상태를 외부에 저장하여 서버가 상태를 갖지 않음

핵심 정리: 무중단 핫픽스 전략

  • 데이터 변경 - 테이블 리로드로 즉시 적용 (가장 쉬움)
  • 스크립트 변경 - 스크립트 핫 리로드 또는 Rolling Update
  • C++ 코어 변경 - Rolling Update가 사실상 유일한 방법
  • 핵심 원칙 - 핫픽스 가능 여부는 아키텍처 설계 시점에 결정된다
  • 3종 세트 - 데이터 드리븐 + 스크립트 분리 + 세션 마이그레이션
