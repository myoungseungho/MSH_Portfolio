False Sharing

캐시 라인 충돌로 멀티스레드가 10배 느려지는 원인과 해결법

False Sharing은 무슨 뜻일까?

False(거짓) + Sharing(공유) = 거짓 공유

각 스레드가 "다른 변수"를 사용하는데, CPU 입장에서는 "같은 캐시 라인"에 있어서 공유하는 것처럼 간섭이 발생합니다.

공유하지 않는데 공유하는 것처럼 느려지는 현상.

비유: 아파트 같은 층 다른 방을 쓰는데, 한 사람이 불 끄면 층 전체가 꺼지는 상황.

Part 1. 멀티스레드로 바꿨는데 오히려 느려졌다?

싱글스레드를 멀티스레드로 바꿨는데 더 느려질 수 있어?

있어. 락도 안 쓰고, 각 스레드가 다른 변수를 건드리는데도 느려지는 경우가 있어.

struct Counters { int count_a; // 스레드 A만 사용 int count_b; // 스레드 B만 사용 }; Counters g_counters; // 스레드 A for (int i = 0; i < 100000000; i++) g_counters.count_a++; // A만 건드림 // 스레드 B for (int i = 0; i < 100000000; i++) g_counters.count_b++; // B만 건드림 // 서로 다른 변수를 건드리니까 빨라야 하는데... // 실측: 싱글스레드보다 느림! 왜?
다른 변수를 건드리는데 왜 느려져?

False Sharing 때문이야.

변수가 "다르다"는 건 프로그래머만 알고, CPU는 "같은 캐시 라인"만 봐.

같은 캐시 라인에 있는 변수를 다른 코어가 건드리면 → 캐시를 서로 무효화시켜.

Part 2. 배경 지식: CPU 캐시

캐시가 뭐고 왜 필요해?

CPU가 데이터를 읽을 때 메모리(RAM)까지 가면 너무 느려. 그래서 자주 쓰는 데이터를 가까운 곳에 복사해 둬.

저장소 접근 시간 비유
L1 캐시 ~1ns (4 사이클) 책상 위 메모지
L2 캐시 ~3ns (12 사이클) 서랍
L3 캐시 ~10ns (40 사이클) 캐비닛
메인 메모리 (RAM) ~100ns (400 사이클) 건물 밖 창고
캐시 라인(Cache Line)이 뭐야?

CPU는 데이터를 바이트 단위가 아니라 64바이트 덩어리(캐시 라인)로 한꺼번에 가져와.

메모리에서 int x를 읽으면: CPU가 원하는 건: [x] (4바이트) 실제로 가져오는 건: [.... x .... ....] (64바이트) <--- 캐시 라인 1개 ---> -> x 주변의 데이터도 함께 캐시에 올라옴 -> 이게 "공간 지역성(Spatial Locality)" 활용
비유로 설명해줘

메모리 = 도서관 창고 (멀리 있음)

캐시 = 내 책상 (바로 앞)

책 1권(변수 1개)이 필요해도, 도서관에서 가져올 때 "선반 1칸(64바이트)"을 통째로 가져와.

옆에 있는 책(변수)도 같이 와서 다음에 빨리 읽을 수 있지만... 다른 사람이 같은 선반 책을 수정하면 문제!

Part 3. 캐시 일관성 프로토콜 (MESI)

멀티코어에서 같은 데이터를 여러 코어가 캐시하면 어떻게 돼?

각 코어는 자기만의 L1 캐시를 가져. 같은 메모리를 캐시하면 일관성을 유지해야 해.

[코어 0] [코어 1] L1 캐시 L1 캐시 +---------+ +---------+ | x = 42 | | x = 42 | <- 같은 데이터의 복사본 +---------+ +---------+ | | +--- 메모리 -----+ x = 42
코어 0이 x를 수정하면?

이런 일이 벌어져:

1. 코어 0: x = 99로 수정 (자기 캐시에서)

2. 코어 0 → 코어 1에게: "이 캐시 라인 무효야!"

3. 코어 1: 자기 캐시의 x를 "Invalid"로 표시

4. 코어 1이 x를 다시 읽으려면: 코어 0에서 가져와야 함

→ 이 과정이 수십~수백 사이클 소모

여기서 False Sharing이랑 뭔 관계야?

핵심: 무효화 단위는 "캐시 라인" 전체

x 하나만 바뀌어도, x가 포함된 64바이트 전체가 무효화돼.

같은 캐시 라인에 있는 다른 변수도 함께 날아가. 이게 False Sharing의 원인이야.

Part 4. False Sharing: 구체적으로 무슨 일이?

아까 예제 코드에서 정확히 무슨 일이 벌어지는 거야?
struct Counters { int count_a; // 오프셋 0~3 (4바이트) int count_b; // 오프셋 4~7 (4바이트) }; // sizeof(Counters) = 8바이트 // 둘 다 같은 캐시 라인(64바이트)에 들어감! 캐시 라인 (64바이트): +----------+----------+-----------------------------+ | count_a | count_b | (남은 56바이트) | | 4바이트 | 4바이트 | | +----------+----------+-----------------------------+ 코어 0 코어 1 이것만 이것만 건드림 건드림 -> 그런데 같은 캐시 라인!
시간 흐름: 코어 0: count_a++ (캐시 라인 수정) -> 코어 1의 캐시 라인 무효화! 코어 1: count_b++ (캐시 라인 다시 가져와야 함) <- 느림! -> 코어 0의 캐시 라인 무효화! 코어 0: count_a++ (캐시 라인 다시 가져와야 함) <- 느림! -> 코어 1의 캐시 라인 무효화! ... 매번 캐시를 주고받는 "핑퐁" 발생! 각 반복마다 ~100 사이클 추가 (L1 히트면 4 사이클인데)

멀티스레드가 싱글스레드보다 10배 이상 느려질 수 있어.

변수가 "다르다"는 건 프로그래머만 알고, CPU는 "같은 캐시 라인"만 보니까.

Part 5. 성능 비교: False Sharing vs 해결 후

실제로 얼마나 차이가 나?
// Case 1: False Sharing 발생 struct Bad { int count_a; // 같은 캐시 라인 int count_b; // 같은 캐시 라인 }; // Case 2: False Sharing 해결 struct Good { alignas(64) int count_a; // 캐시 라인 1 alignas(64) int count_b; // 캐시 라인 2 (별도!) };

1억 회 반복, 2스레드 결과:

False Sharing (Bad)

~850ms

해결 후 (Good)

~95ms

싱글스레드 참고

~180ms
케이스 시간 비고
False Sharing ~850ms 싱글스레드보다 4.7배 느림!
해결 후 ~95ms 싱글스레드보다 1.9배 빠름 (정상)
싱글스레드 ~180ms 기준점

alignas(64) 한 줄 추가로 850ms → 95ms. 약 9배 성능 차이.

같은 코드, 같은 로직인데 메모리 배치만 바꿨을 뿐이야.

Part 6. 해결 방법 3가지

방법 1: alignas (C++11)
struct ThreadData { alignas(64) int count; // 64바이트 경계에 정렬 }; ThreadData data[NUM_THREADS]; // 각 스레드의 데이터가 별도 캐시 라인에 위치
방법 2: 패딩 (Padding)
struct PaddedCounter { int count; char padding[60]; // 4 + 60 = 64바이트 (캐시 라인 크기) }; // 또는 C++17의 hardware_destructive_interference_size struct Counter { alignas(std::hardware_destructive_interference_size) int count; };
방법 3: 스레드 로컬 누적 후 합산
// 가장 실용적인 패턴 void WorkerThread(int threadId) { int localCount = 0; // 스택 변수 (자기 캐시 라인) for (int i = 0; i < N; i++) { localCount++; // 로컬에서 누적 } // 마지막에 한 번만 공유 변수에 합산 g_totalCount.fetch_add(localCount); }
어떤 방법을 먼저 써야 해?

방법 3: 로컬 변수로 누적 → 마지막에 합산 (가장 깔끔)

방법 1: alignas(64) (구조체 변경이 가능할 때)

방법 2: 패딩 (레거시 코드에서 구조체를 못 바꿀 때)

Part 7. 게임 서버에서 False Sharing이 일어나는 곳

사례 1: 스레드별 통계 카운터
// 위험: 워커 스레드별 패킷 처리 횟수 struct WorkerStats { int packetCount; // 스레드 0 int packetCount1; // 스레드 1 int packetCount2; // 스레드 2 <- 전부 같은 캐시 라인! int packetCount3; // 스레드 3 }; // 안전: 각 스레드 데이터를 캐시 라인 단위로 분리 struct WorkerStats { alignas(64) int packetCount; }; WorkerStats stats[MAX_WORKERS];
사례 2: 배열을 스레드별로 분할 처리
// 몬스터 AI 업데이트를 4스레드로 분할 Monster monsters[10000]; // 스레드 0: monsters[0~2499] // 스레드 1: monsters[2500~4999] // 스레드 2: monsters[5000~7499] // 스레드 3: monsters[7500~9999] // 경계 지점에서 False Sharing 가능! // monsters[2499]와 monsters[2500]이 같은 캐시 라인일 수 있음 // 해결: 경계를 캐시 라인 단위(64바이트)로 정렬 int monstersPerLine = 64 / sizeof(Monster); // 분할 시작점을 monstersPerLine의 배수로 맞춤
사례 3: 락 변수와 데이터가 인접
// 위험: 락과 데이터가 같은 캐시 라인 struct SharedData { std::mutex mtx; // 40바이트 int importantData; // 같은 캐시 라인에 있을 수 있음 }; // 스레드 A가 락을 걸면 -> 캐시 라인 전체가 무효화 // 스레드 B가 importantData만 읽으려 해도 캐시 미스! // 안전: 분리 struct SharedData { alignas(64) std::mutex mtx; alignas(64) int importantData; };

Part 8. False Sharing 진단 방법

False Sharing이 발생하는지 어떻게 확인해?
도구 방법 확인할 지표
Intel VTune Memory Access Analysis 캐시 라인 충돌 횟수, Contested Access
perf (Linux) perf c2c Cache-to-Cache 전송 빈도
Visual Studio CPU Counters L1 캐시 미스 비율 급증 여부
수동 확인 오프셋 출력 스레드별 데이터가 64바이트 내에 있는지
// 수동 확인: 오프셋 출력 printf("count_a offset: %zu\n", offsetof(Counters, count_a)); printf("count_b offset: %zu\n", offsetof(Counters, count_b)); // 출력: 0, 4 -> 같은 캐시 라인 (64바이트 안)! // 64 이상 차이가 나야 안전

가장 빠른 확인법: offsetof()로 변수 간 거리를 출력해 봐.

64바이트 이상 차이가 나면 안전해.

핵심 정리

  • 캐시 라인 = CPU가 메모리를 가져오는 단위 (보통 64바이트)
  • MESI 프로토콜 = 한 코어가 캐시 라인을 수정하면 다른 코어의 복사본을 무효화
  • False Sharing = 다른 변수인데 같은 캐시 라인 → 불필요한 캐시 무효화로 10배 느려짐
  • 해결 = alignas(64), 패딩, 로컬 변수 누적 (실무에서는 방법 3 우선)
  • 진단 = VTune, perf c2c, offsetof()로 변수 간 거리 확인
