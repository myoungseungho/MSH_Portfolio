DX12는 그래픽을 예쁘게 만드는 API가 아니다

DX11 개발자들의 3가지 비명, 그리고 같은 그림을 6배 싸게 그리게 된 이야기

Part 1. 오해부터 깨자 — DX12는 '화질 업그레이드'가 아니다

DX12로 만들면 그래픽이 더 좋아지는 거 아냐? 숫자가 더 크잖아.

그럼 맞춰봐. 어떤 게임을 DX11에서 DX12로 포팅하면, 그래픽 옵션에 뭐가 새로 생길까?

정답: 아무것도 안 생겨. 화면은 픽셀 단위로 똑같아. 달라지는 건 프레임타임이야.

DX12의 본질은 같은 그림을 훨씬 싸게(CPU를 덜 쓰고) 그리는 API거든. 셰이더가 더 예뻐지는 게 아니라, GPU한테 일을 시키는 전달 비용이 싸지는 거야.

그래서 이 문서의 질문은 "뭐가 예뻐졌나"가 아니라 — "DX11 개발자들은 뭐가 그렇게 괴로워서 멀쩡해 보이는 API를 갈아엎었나"야.

괴로웠다고? DX11로도 게임 잘만 나왔잖아.

나왔지. 근데 그 시절 그래픽 프로그래머들이 지르던 비명이 세 가지 있어.

① "드로우콜이 모자라!" — 화면에 그릴 물체 수가 CPU 때문에 막힌다

② "코어가 8개인데 1개만 일해!" — 렌더링 제출이 멀티스레드가 안 된다

③ "드라이버가 뭘 하는지 모르겠어!" — 갑자기 프레임이 튀는데 내 코드가 아니다

이 세 비명을 하나씩 따라가면 DX12의 모든 기능이 왜 그렇게 생겼는지가 자동으로 풀려. 순서대로 가자.

Part 2. 비명 ① — "드로우콜이 모자라!"

드로우콜이 뭔데 모자라? GPU한테 '이거 그려' 한 마디 하는 거 아냐?

한 마디처럼 보이는데, DX11에서 그 한 마디의 뒤에선 이런 일이 벌어져:

드라이버가 현재 바인딩된 상태 전부를 검증하고, 셰이더·블렌드·래스터 상태 조합을 추적하고, 리소스 충돌(해저드)을 검사하고, 필요하면 커널 모드로 전환해서 GPU 커맨드 버퍼에 번역해 넣어.

이게 드로우콜 하나당 CPU 수 마이크로초(µs)야. 별거 아닌 것 같지? 60fps의 프레임 예산은 16.6ms야. 콜당 5µs면 3,300개에서 프레임 예산이 끝나 — GPU가 아니라 CPU 때문에.

개발자가 쓴 코드: context->DrawIndexed(...) ← "한 마디" DX11 드라이버 내부: [상태 검증][해저드 추적][셰이더 조합 확인] [리소스 상주 확인][커널 전환][커맨드 번역] = 콜당 수 µs × 수천 콜 × 매 프레임 결과: GPU는 한가한데 CPU 한 코어가 비명 → "드로우콜 예산"이라는 말이 생김
그래서 그 시절에 인스턴싱이니 배칭이니 하면서 묶어 그렸던 거야?

정확해. 전부 드로우콜을 줄이기 위한 우회로였어. 트레이드오프로 보면:

배칭/인스턴싱 — 나은 점: 콜 수가 1/N. 잃는 것: 같은 재질·같은 메시끼리만 묶임 → 아트 제작 규칙이 기술 제약에 종속돼. "나무는 3종류만 써주세요" 같은 요구가 아티스트한테 가는 거야.

텍스처 아틀라스 — 나은 점: 재질 전환(상태 변경) 감소. 잃는 것: 텍스처 관리 지옥, 밉맵 블리딩.

즉 DX11 시대의 최적화 기법 상당수는 API의 한계를 콘텐츠 쪽이 떠안은 것이었어. DX12는 이 비용을 API가 도로 가져가겠다는 선언이고.

잠깐 — GPU는 놀고 있다며. 그럼 그래픽카드를 더 좋은 걸로 바꿔도 소용없었겠네?

그게 그 시절 PC 게이머들이 겪던 미스터리의 정체야. CPU-bound 장면에선 GPU를 2배 좋은 걸로 바꿔도 FPS가 거의 안 올라.

물체가 빽빽한 도심 장면에서 프레임이 떨어지는데, GPU 사용률을 보면 60%밖에 안 돼 — 제출(드로우콜)이 막혀서 GPU가 굶고 있는 거지.

이 증상은 아래 Part 5 시뮬레이터에서 직접 재현해볼 수 있어.

Part 3. 비명 ② "1코어만 일해!" + 비명 ③ "드라이버가 뭘 하는지 몰라!"

CPU가 병목이면 스레드를 나누면 되잖아. 8코어 시대였는데?

DX11의 구조적 한계가 바로 여기야. 렌더링 명령을 받는 immediate context는 단 1개고, 스레드 안전하지 않아 — 사실상 한 스레드만 GPU에 말을 걸 수 있어.

MS도 알아서 DX11에 deferred context(여러 스레드가 명령을 미리 기록)를 넣긴 했어. 근데 드라이버 내부에서 결국 한 줄로 직렬화돼서 실효가 거의 없었어 — 일부 벤더만 부분적으로 이득을 냈고.

결과: 게임 로직은 8코어로 돌리는데, 렌더링 제출은 2009년식 1코어. 3DMark API Overhead 실측이 이걸 그대로 보여줘 — DX11은 멀티스레드 모드로 돌려도 초당 약 260만 콜에서 멈춰. 코어를 더 줘도 첫 코어만 일하거든.

비명 ③은 뭐야? 드라이버가 뭘 하는지 모른다는 게 무슨 말이야?

DX11에서 드라이버는 착한 마법사야. 상태를 추적해주고, 배리어를 알아서 넣어주고, 메모리 상주도 알아서 관리해줘. 문제는 마법의 비용이 언제 청구되는지 모른다는 거야.

대표 사례 — 게임이 새로운 셰이더+상태 조합으로 처음 그리는 순간, 드라이버가 그 자리에서 최종 GPU 코드를 재컴파일해. 수십 ms짜리 작업이 전투 중 이펙트가 처음 터지는 프레임에 끼어드는 거지. 유저가 느끼는 '갑자기 컥 하는' 히치의 고전적 원인이야.

게다가 이 마법은 NVIDIA/AMD/Intel마다 달라서, 같은 코드가 벤더별로 성능이 들쭉날쭉했어. 내 코드 밖에서 일어나니 프로파일링도 안 잡혀.

그건 드라이버가 똑똑해지면 해결될 문제 아냐? 왜 API를 갈아엎어?

10년 가까이 그 방향으로 가봤는데 한계가 명확했어. 드라이버는 다음 프레임에 뭐가 나올지 모르니까 항상 방어적으로(최악을 가정하고) 일해야 해.

반면 게임 엔진은 자기 장면을 다 알아 — 이 텍스처는 이번 프레임에 읽기만 한다, 이 셰이더 조합은 로딩 때 다 알 수 있다, 이 리소스는 3프레임 뒤에나 쓴다.

그래서 결론이 뒤집힌 거야: "드라이버야, 추측하지 마. 아는 쪽(엔진)이 직접 말해줄게" — 이게 DX12의 설계 철학 전부고, AMD가 Mantle(2013)로 먼저 증명했고, DX12(2015)와 Vulkan(2016)이 그 직계야.

Part 4. DX12의 응답 — 비명 3개에 기능 3개

그래서 DX12가 뭘 바꿨는데? 기능 목록으로 나열하지 말고 비명에 대응시켜줘.

비명 ① 드로우콜 부족 → 얇아진 제출 경로. 검증·추적을 드라이버에서 들어내니 콜당 비용이 수 분의 1로. 3DMark API Overhead 실측(2015): DX11 MT 초당 262만 콜 → DX12 1,567만 콜, 약 6배.

비명 ② 1코어 → Command List 병렬 기록. 워커 스레드 여럿이 각자 커맨드 리스트를 기록하고, 큐에 던지면 끝. 8코어가 전부 제출에 참여해.

비명 ③ 드라이버 마법 → PSO(Pipeline State Object). 셰이더+블렌드+래스터 상태 전부를 로딩 시점에 미리 컴파일해서 불변 객체로 고정. 런타임 재컴파일 히치가 구조적으로 불가능해져.

그게 정확한 요약이야. DX12 = 자동변속기를 수동변속기로 바꾼 것.

비유 하나 더: DX11은 풀서비스 식당이야 — 주문만 하면 알아서 나와. 느린 날이 있어도 원인을 알 수 없지. DX12는 주방을 통째로 빌려준 것이고 — 동선 설계를 잘하면 회전율이 몇 배가 되지만, 위생(동기화)을 놓치면 식중독(GPU 크래시)이 나.

그래서 DX12는 '더 좋은 API'가 아니라 '제어권과 책임을 통째로 넘기는 계약'이야. 이 계약이 이득인 팀과 손해인 팀이 갈리고 — 그 갈림길이 Part 6의 주제야.

Part 5. 직접 봐 — 같은 장면, 같은 GPU, API만 바꿔서

말로는 알겠는데, 그 차이가 체감이 안 돼.

아래 시뮬레이터를 돌려봐. 장면(GPU 비용 8ms 고정)과 그래픽카드는 동일하고, 바꾸는 건 API뿐이야.

드로우콜 슬라이더를 끝까지 밀어보고, '전투 중 새 이펙트 등장' 체크박스로 비명 ③(런타임 재컴파일 히치)도 재현해봐.

※ 콜당 비용(DX11 5µs / DX12 1µs, 4코어 분산)은 구조를 보여주기 위한 예시값이다. 실제 값은 드라이버·하드웨어·상태 변경 빈도에 따라 달라진다.

돌려보니까 이상한 게 있어. 드로우콜 1,000개일 땐 DX11이랑 DX12랑 FPS가 똑같던데?

그걸 발견했다면 이 문서의 절반은 가져간 거야. 병목이 GPU(8ms)에 있을 때는 제출 비용을 아무리 줄여도 FPS가 안 변해.

이게 실제로 벌어진 일이기도 해 — 초기 DX12 포팅 게임 중 일부는 DX11보다 오히려 느렸어. GPU-bound 게임이라 DX12의 이득은 없는데, 드라이버 엔지니어 10년치 노하우(메모리 관리, 배리어 최적화)를 게임 팀이 첫 시도로 이기지 못했거든.

교훈: DX12는 'CPU 제출이 병목인 게임'에서만 마법이 일어난다. 물체 수천 개의 오픈월드·RTS·도심 장면이 그 무대고, 복도형 GPU-bound 게임은 계약 비용만 내는 거야.

Part 6. 정직한 청구서 — 그래서 지금은 어떻게 됐나

PSO가 히치를 없앴다며. 근데 요즘 게임들 '셰이더 컴파일' 스터터는 왜 그래?

좋은 지적이야 — 비명 ③이 죽지 않고 자리를 옮긴 거야.

DX11: 드라이버가 게임 중에 몰래 컴파일 → 산발적 히치, 개발자는 원인도 모름.

DX12: 엔진이 미리 컴파일해야 함 → 그런데 어떤 조합이 쓰일지 수집을 못 하면? 결국 처음 그 조합이 등장하는 순간 컴파일 = 스터터. 요즘 UE 계열 게임들이 욕먹는 그 증상이야.

차이는 책임의 위치야. DX11에선 드라이버 문제라 손쓸 수 없었지만, DX12에선 엔진 문제라서 고칠 수 있어 — 그래서 요즘 게임들이 첫 실행 때 '셰이더 최적화 중...' 화면으로 비용을 미리, 보이게 지불하는 거야. 히치가 사라진 게 아니라 예측 가능한 곳으로 옮겨진 것.

그럼 그래픽이 진짜 좋아지는 건 DX12에 하나도 없어?

본체에는 없고, 그 위에 얹힌 확장에는 있어. DX12 Ultimate(2020)가 그 묶음이야:

DXR(레이트레이싱) — 화면 밖 물체까지 비추는 진짜 반사/그림자. 이건 픽셀이 실제로 달라져.

메시 셰이더 — 지오메트리 파이프라인 재설계, VRS — 화면 영역별 셰이딩 해상도 조절.

단, 이것들이 DX12에만 올라간 이유가 중요해 — 레이트레이싱처럼 GPU를 쥐어짜는 기능은 드라이버 마법 위에선 못 세워. 명시적 제어라는 토대가 있어야 가능했던 거야. 즉 'DX12의 그래픽 발전'도 사실은 Part 3 철학(아는 쪽이 직접 제어)의 열매야.

근데 아직도 DX11로 나오는 게임이 많잖아. 10년이 지났는데 왜?

계약 비용이 모두에게 이득은 아니거든. 정리하면:

DX12가 남는 장사 — 자체 엔진 보유 + 물체 수만 개 장면 + 전담 렌더링 팀. (대형 오픈월드, RTS, 도심 시뮬)

DX11이 남는 장사 — GPU-bound거나 장면이 단순함 + 렌더링 인력 소수 + 검증된 안정성 우선. (인디, 라이브 서비스 장수 게임)

그리고 현실적인 제3의 길 — 상용 엔진(UE/Unity)이 DX12 계약을 대신 이행해주니까, 요즘 신작은 엔진 뒤에 숨어서 DX12를 쓰는 셈이야. 수동변속을 엔진이 대신 밟아주는 거지.

우리처럼 오래된 자체 클라이언트를 가진 팀이 'DX12 포팅하면 빨라지나?'를 물을 때 첫 질문은 하나야 — 지금 병목이 제출 CPU인가? 아니라면 포팅은 비용만 낸다.

핵심 정리

  • DX12는 화질 API가 아니다 — 같은 그림을 싸게 그리는 API다 (화면은 픽셀 단위로 동일)
  • DX11의 3가지 비명: 드로우콜 예산(콜당 수 µs × 1코어), 멀티스레드 제출 불가, 드라이버 마법의 불투명성(런타임 재컴파일 히치)
  • DX12의 응답: 얇은 제출 경로(3DMark 실측 6배) + Command List 병렬 기록 + PSO 사전 컴파일 + 명시적 배리어/메모리/멀티 큐
  • 본질은 계약 — 드라이버의 제어권과 책임을 엔진이 통째로 인수 (자동변속 → 수동변속)
  • GPU-bound면 DX12는 이득이 0 — 초기 포팅 게임들이 DX11보다 느렸던 이유
  • 히치는 사라진 게 아니라 이동했다 — 런타임 몰래 컴파일(DX11) → 로딩 화면의 '셰이더 최적화 중'(DX12)
  • 진짜 그래픽 차이는 DX12 Ultimate(DXR·메시 셰이더·VRS) — 그것도 명시적 제어라는 토대 위에서만 가능했다

⚠ 이 문서의 정직한 한계

시뮬레이터의 콜당 비용(5µs/1µs)은 구조를 보여주는 예시값이다. 실제는 상태 변경 빈도, 드라이버 세대, 리소스 바인딩 방식에 따라 수 배 단위로 달라진다.

3DMark API Overhead는 '아무것도 안 그리는 순수 제출' 벤치마크다 — 실게임의 이득은 6배가 아니라 'CPU 제출 병목이 풀리는 만큼'이다.

여기서 다룬 건 그래픽 API 관점이다. 디스크립터 힙, 루트 시그니처, residency 관리 같은 실구현 디테일은 각각 별도 문서감이다.

🤔 생각해볼 것 (정답 없음)

우리 클라이언트(DX9 세대)를 현대화한다면 DX11와 DX12 중 어디서 멈추는 게 맞을까? 첫 질문은 '병목이 어디인가'다 — 어떻게 측정할래?

'아는 쪽이 직접 제어한다'는 DX12 철학을 게임서버에 대입하면? OS 스레드 스케줄러 vs 자체 잡 시스템, OS 페이지 캐시 vs 자체 캐시 — 같은 구조가 보이지 않아?

PSO 조합 폭발 문제는 본질적으로 '모든 경우의 수를 미리 알 수 있는가'다 — 우리 서버의 프로시저 플랜 캐시 워밍업과 뭐가 같고 뭐가 다를까?
