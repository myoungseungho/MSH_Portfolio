Refactoring #15

Introduce Explaining Variable

설명 변수 도입 - 복잡한 표현식에 이름 붙이기

설명 변수가 뭐예요?
복잡한 표현식의 결과를 의미 있는 이름의 변수에 담는 것이에요.

길고 복잡한 조건문이나 계산식을 읽다가 "이게 뭘 의미하지?"라는 생각이 들 때 사용해요.

변수 이름이 곧 그 표현식의 의도를 설명하는 역할을 하죠.
왜 필요한 건가요? 그냥 주석 달면 안 되나요?
주석과 비교해 볼게요:

주석의 단점:
- 코드가 바뀌면 주석을 안 바꾸는 경우가 많음
- 주석과 코드가 따로 놀 수 있음
- 읽을 때 시선이 왔다갔다 해야 함

설명 변수의 장점:
- 코드 자체가 문서가 됨
- 값이 바뀌면 변수 할당도 자동으로 바뀜
- 디버깅 시 중간값 확인 가능

📝 비유: 수학 문제 풀이

복잡한 공식을 한 줄에 다 쓰면 검산이 어렵죠.

중간 계산 결과를 "둘레 = ...", "넓이 = ..." 이렇게 써두면 어느 단계에서 틀렸는지 바로 알 수 있어요.

설명 변수도 똑같아요. 복잡한 로직의 각 단계에 이름을 붙이는 거예요.
어떤 상황에서 쓰면 좋나요?
이런 상황들에서 효과적이에요:

1. 복잡한 조건문
if 조건이 3개 이상의 AND/OR로 연결될 때, 각 조건을 설명 변수로 분리하면 읽기 쉬워져요.

2. 긴 계산식
여러 단계의 수학 연산이 한 줄에 있을 때, 중간 결과에 의미 있는 이름을 붙이세요.

3. 메서드 체이닝
여러 메서드가 줄줄이 연결될 때, 중간 결과를 변수에 담으면 디버깅이 쉬워져요.

4. 매직 표현식
"왜 이런 계산을 하지?"라는 의문이 드는 코드.
설명 변수를 너무 많이 쓰면 오히려 복잡해지지 않나요?
맞아요! 균형이 필요해요.

과도한 사용의 문제:
- 한 줄이면 될 코드가 5줄이 됨
- 사소한 것에도 이름 붙이면 오히려 시끄러움
- 변수가 너무 많으면 추적이 어려움

적절한 사용 기준:

1. "이게 뭐지?"라는 생각이 들 때만 사용
2. 한 메서드에 설명 변수가 5개 넘어가면 → 메서드 분리 고려
3. 단순한 표현식에는 사용하지 않음

⚠️ 불필요한 설명 변수

isPositive = (value > 0) 같은 건 과해요.

value > 0 자체가 이미 충분히 명확하거든요.

표현식 자체가 이미 의도를 드러내면 변수는 불필요해요.
Replace Temp with Query와 반대 아닌가요?
좋은 질문이에요! 비슷해 보이지만 목적이 달라요:

Replace Temp with Query:
- 재사용을 위해 변수를 메서드로 승격
- 다른 곳에서도 같은 계산이 필요할 때

Introduce Explaining Variable:
- 가독성을 위해 표현식에 이름 부여
- 지금 이 자리에서 이해를 돕기 위해

실제로는 순서대로 적용하기도 해요:

1. 복잡한 표현식 → 설명 변수 도입 (가독성 개선)
2. 그 변수가 다른 곳에서도 필요하면 → 질의 메서드로 승격

💡 리팩토링은 단계별로

처음엔 설명 변수로 시작해서 가독성을 확보하고,
나중에 필요하면 메서드로 발전시키세요.

한 번에 완벽할 필요 없어요.
좋은 설명 변수 이름은 어떻게 짓나요?
이름 짓기 원칙:

1. "무엇"이 아니라 "왜"를 담기
❌ calculatedValue
✅ isEligibleForDiscount

2. 불리언은 is/has/can으로 시작
isExpired, hasPermission, canDelete

3. 도메인 용어 사용
게임이라면: isInCombat, hasEnoughMana
커머스라면: isInStock, meetsMinimumOrder

4. 부정형 피하기
❌ isNotExpired
✅ isValid

이름만 봐도 "아, 이걸 확인하는구나"가 느껴져야 해요.

📌 Introduce Explaining Variable 핵심 정리

  • 복잡한 표현식에 의미 있는 이름을 붙이는 것
  • 코드가 곧 문서가 되어 주석보다 유지보수에 좋음
  • 디버깅 시 중간값 확인 가능
  • 과도하게 사용하면 오히려 복잡해짐
  • 이름은 "왜"를 담고, 도메인 용어를 사용
