링킹 단계 - .obj를 .exe로 조립하기

심볼 해결, 재배치, 그리고 링크 최적화 옵션들

Part 1. 링커가 하는 일

컴파일 끝나면 바로 실행 가능한 거 아니야?

아니! .obj 파일은 아직 부품이야.

링커가 이 부품들을 조립해서 완성품(.exe)을 만들어.

🔗 링커의 4단계 작업 ┌─────────────────────────────────────────────────────────┐ │ 1️⃣ 심볼 수집 │ │ 각 .obj에서 정의된 함수/변수 목록 추출 │ │ │ │ 2️⃣ 심볼 해결 (Symbol Resolution) │ │ "이 함수 호출하는데, 정의는 어디?"를 연결 │ │ │ │ 3️⃣ 재배치 (Relocation) │ │ 모든 코드를 하나로 합치고 최종 주소 배정 │ │ │ │ 4️⃣ 실행 파일 출력 │ │ .exe 또는 .dll 생성 │ └─────────────────────────────────────────────────────────┘

Part 2. 심볼 해결이란?

심볼이 뭐야?

함수 이름, 변수 이름 같은 거야!

코드에서 쓰는 모든 이름이 심볼이야.

📦 player.obj의 심볼 테이블 ┌─────────────────────────────────────────┐ │ 정의된 심볼 (이 파일에 구현 있음): │ │ ✅ Player::Attack │ │ ✅ Player::Move │ │ ✅ Player::Die │ │ │ │ 참조하는 심볼 (다른 곳에 있음): │ │ ❓ Monster::TakeDamage │ │ ❓ EffectManager::PlayEffect │ │ ❓ SoundManager::PlaySound │ └─────────────────────────────────────────┘
❓ 표시된 건 어떻게 찾아?

링커가 다른 모든 .obj를 뒤져서 찾아!

🔍 심볼 해결 과정 player.obj: "Monster::TakeDamage 어딨어?" ↓ 검색 monster.obj: "Monster::TakeDamage 여기 있어! 주소: 0x1234" ↓ 연결 player.obj의 호출 코드 → 0x1234 주소로 점프하도록 수정

Part 3. 유명한 에러 - unresolved external symbol

이 에러 자주 보는데 뭐야?

링커가 "이 심볼 정의를 못 찾겠어!"라고 하는 거야.

error LNK2019: unresolved external symbol "public: void __cdecl Player::Attack(void)" referenced in function "main"
왜 이런 에러가 나?

주로 세 가지 원인이야:

원인 상황 해결책
1. 정의 누락 헤더에 선언만 하고 cpp에 구현 안 함 cpp 파일에 구현 추가
2. 파일 누락 cpp 파일을 프로젝트에 안 넣음 프로젝트에 파일 추가
3. 라이브러리 누락 필요한 .lib를 링크 안 함 Additional Dependencies에 추가
💡 디버깅 팁 에러 메시지 해석: "Player::Attack ... referenced in main" ↑ ↑ 못 찾는 함수 호출하는 곳 → Player::Attack의 정의가 어디 있는지 확인! → player.cpp가 프로젝트에 있는지 확인! → 혹시 다른 라이브러리에 있는 건 아닌지?

Part 4. 링크 최적화 옵션들

링킹도 최적화할 수 있어?

당연하지! 특히 안 쓰는 코드 제거가 핵심이야.

🔧 /Gy - Function-Level Linking

각 함수를 별도 섹션에 배치

→ 링커가 안 쓰는 함수만 제거 가능!

📦 /Gy의 효과 ❌ /Gy 없음: ┌─────────────────────────────────────┐ │ [FuncA][FuncB][FuncC] │ ← 하나의 섹션 └─────────────────────────────────────┘ FuncB 안 써도 제거 불가 (뭉쳐있어서) ✅ /Gy 적용: ┌──────────┐ ┌──────────┐ ┌──────────┐ │ [FuncA] │ │ [FuncB] │ │ [FuncC] │ ← 각각 별도 섹션 └──────────┘ └──────────┘ └──────────┘ FuncB 안 쓰면 해당 섹션만 제거! ✂️

🔧 /Gw - Optimize Global Data

전역 변수/상수도 별도 섹션에 배치

→ 안 쓰는 전역 데이터 제거!

📦 /Gw의 효과 전역변수들: const char* UNUSED_STRING = "never used"; const int UNUSED_VALUE = 12345; int usedCounter = 0; /Gw 적용 후: → UNUSED_STRING, UNUSED_VALUE는 제거됨! → usedCounter만 최종 exe에 포함

🔧 /Zc:inline - Remove Unreferenced COMDAT

참조되지 않은 인라인 함수 제거

→ .obj 파일 크기 감소 → 링킹 속도 향상

Part 5. Debug 빌드 빠르게 - /DEBUG:FASTLINK

디버그 빌드 링킹이 느린데, 빠르게 할 수 있어?

/DEBUG:FASTLINK 옵션을 써봐!

⚡ /DEBUG:FASTLINK 일반 디버그 링킹: 모든 .obj의 디버그 정보 → PDB 파일 하나로 복사 시간: 30초 FASTLINK: 디버그 정보는 .obj에 그대로 두고, PDB는 참조만 시간: 5초! 단점: - .obj 파일 지우면 디버깅 안 됨 - 배포용으로 부적합 (개발 중에만 사용)
개발 중에만 쓰라는 거지?

맞아! Release 빌드에서는 일반 /DEBUG 써야 해.

Debug 빌드 반복할 때 엄청 빨라져!

Part 6. 실제 프로젝트에 적용

조선협객전에는 어떻게 적용했어?

Debug와 Release 각각 다르게 설정했어!

옵션 Debug|x64 Release|x64
/Gy Yes Yes
/Gw Yes Yes
/Zc:inline Yes Yes
/DEBUG:FASTLINK Yes (개발용) No (배포용)
/CGTHREADS:8 Yes Yes
📊 링킹 시간 변화 Debug 빌드: ├── 적용 전: 40초 ├── /Gy, /Gw, /Zc:inline: 35초 (5초 단축) ├── /DEBUG:FASTLINK: 20초 (15초 단축) └── /CGTHREADS:8: 15초 (5초 단축) 총: 40초 → 15초 (62% 감소) Release 빌드: ├── 적용 전: 60초 ├── /Gy, /Gw, /Zc:inline: 50초 (10초 단축) └── /CGTHREADS:8: 40초 (10초 단축) 총: 60초 → 40초 (33% 감소)

Part 7. 링크 에러 해결 치트시트

링크 에러 종류별로 해결법 정리해줘!

자주 나오는 에러들과 해결책:

에러 의미 해결
LNK2019 외부 심볼 못 찾음 .cpp 추가 / .lib 링크
LNK2001 심볼 정의 없음 가상 함수 구현 확인
LNK1120 N개 외부 참조 못 찾음 위 에러들 N개 해결
LNK2005 심볼 중복 정의 헤더에 inline / static
LNK1104 파일 열 수 없음 .lib 경로 확인

⚠️ LNK2005 중복 정의 해결

헤더에 함수 정의가 있으면 여러 .obj에 포함됨!

해결: inline 키워드 추가 또는 .cpp로 옮기기

📝 핵심 정리

  • 링커 = .obj들을 모아 .exe로 조립
  • 심볼 해결 = 함수 호출과 정의 연결
  • LNK2019 = 가장 흔한 에러, 정의/파일/lib 확인
  • /Gy, /Gw = 안 쓰는 함수/데이터 제거
  • /DEBUG:FASTLINK = Debug 링킹 획기적 단축
  • /CGTHREADS = 링킹 병렬화
