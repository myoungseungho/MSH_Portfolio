리플리케이션 본질 — 상태를 자동으로 맞춘다

변수에 표시만 하면 엔진이 변경분을 클라로. RPC가 '이벤트'면 이건 '상태'

30초 요약

리플리케이션 = 서버 변수에 'Replicated' 표시만 하면 값이 바뀔 때 엔진이 클라로 자동 전송.

클라는 받으면 그 변수를 갱신하고 OnRep 콜백을 호출(예: 체력바 갱신).

핵심: ① 패킷 수동 작성 불필요(선언만) ② 바뀐 속성만 전송(안 바뀐 건 생략).

Part 1. RPC랑 뭐가 달라?

Ch8에서 RPC 했는데, 또 다른 동기화 방법이야?

RPC는 '이벤트'(한 번 일어나는 행동)야. 리플리케이션은 '상태'(계속 유지되는 값)야.

체력 70 → 이건 값이라 복제, '스킬 이펙트 터짐' → 이건 이벤트라 RPC. 새로 접속한 클라도 복제로 '현재 상태'를 받아 맞춰.

그럼 뭘 어떻게 표시해?

변수에 Replicated를 달고, GetLifetimeReplicatedProps에서 DOREPLIFETIME(클래스, 변수)로 등록해. 그럼 끝 — 엔진이 값 변화를 감지해 보내.

받는 쪽에서 반응이 필요하면 그 변수에 RepNotify를 달아 OnRep_변수() 함수를 만들어.

Part 2. 값이 바뀌면 클라가 따라온다

서버 값이 바뀌면 클라가 어떻게 되는지 보자.

서버 속성이 바뀌면 그 값이 클라로 날아가고, 클라 패널의 값이 갱신되며 'OnRep!'이 깜빡여.

탭으로 어떤 값이 바뀌게 할지 골라봐. 그리고 — 안 바뀐 속성은 안 보낸다는 것(아래 '전송 절약' 카운트)에 주목.

0복제 전송(변경분)
0전송 절약(안 바뀜)

Part 3. OnRep — 받았을 때 반응하기

OnRep은 언제 불려?

그 변수가 '복제로 갱신될 때' 클라에서 불려. 서버에선 안 불려(서버는 그냥 값을 바꾼 거니까).

그래서 체력바·이펙트처럼 '값이 바뀌면 화면을 갱신'하는 코드를 OnRep에 둬. 값 동기화(엔진)와 반응(OnRep)을 분리하는 거야.

우리 서버는 이걸 어떻게 해?

우리는 값이 바뀌면 SM_ 패킷을 직접 만들어 보내고, 클라는 그 패킷 핸들러에서 화면을 갱신해. 즉 'DOREPLIFETIME + OnRep'을 우리는 'SM_ 송신 + 클라 핸들러'로 손수 하는 셈.

UE는 '뭘 보낼지'를 엔진이 정하고, 우리는 '언제 뭘 보낼지'를 개발자가 정해 — 더 세밀하지만 더 손이 가.

UE 매크로Replicated + DOREPLIFETIME

변수에 Replicated 표시 + DOREPLIFETIME으로 등록하면 끝. 엔진이 값 변화를 감지해 클라에 자동 전송. 받는 쪽에서 반응이 필요하면 RepNotify로 OnRep_xxx 함수 자동 호출.

UPROPERTY(Replicated) float Health; UPROPERTY(ReplicatedUsing=OnRep_Ammo) int32 Ammo; void AMyChar::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& Out) const { DOREPLIFETIME(AMyChar, Health); DOREPLIFETIME(AMyChar, Ammo); } void AMyChar::OnRep_Ammo() { // 클라가 새 값 받았을 때만 호출 (서버에선 호출 X) UpdateAmmoHUD(); }
우리 서버

값 바뀌면 SM_AMMO_UPDATE 패킷 직접 만들어 송신. 클라는 핸들러에서 HUD 갱신.

언리얼

UPROPERTY(Replicated) 한 줄. 엔진이 변경 감지·전송·OnRep 호출 다 자동.

Part 4. 우리 vs UE

항목조선협객전 (우리)언리얼
무엇을 보낼지개발자가 SM_ 직접 작성엔진이 변경 감지·자동
변경분만개발자가 더티플래그로 관리엔진이 last state와 비교
받았을 때 반응클라 패킷 핸들러OnRep 콜백
신규 접속자 동기화로그인 시 상태 패킷 묶음복제가 자동으로 현재 상태 전달
한 줄로?

UE 리플리케이션의 매력은 '선언만 하면 됨'이야. 대신 '언제·누구에게·얼마나 자주'를 더 통제하려면 다음 챕터들(Push Model, Dormancy, Relevancy)을 알아야 해. 우리는 처음부터 그걸 다 손으로 통제하는 거고.

핵심 정리

  • 리플리케이션 = 상태(값) 자동 동기화. RPC(이벤트)와 짝
  • 표시: Replicated + DOREPLIFETIME → 엔진이 변경분 자동 전송
  • OnRep = 클라가 복제로 값을 받았을 때 호출(서버 X) → 화면 갱신
  • 변경분만 보냄(안 바뀐 속성 생략) — last state와 비교
  • 우리 = SM_ 수동 + 더티플래그 + 클라 핸들러, UE = 선언 + 엔진 자동 + OnRep

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. OnRep은 클라에서만 불린다며, 서버도 같은 반응하려면 두 번 짜?

아니, 한 번만 짜면 돼. 패턴이 정해져 있어:

[Setter 패턴] void AMyChar::SetHealth(float NewHP) { Health = NewHP; OnHealthChanged(); // 서버에서 직접 호출 } void AMyChar::OnRep_Health() { OnHealthChanged(); // 클라에서 복제 받을 때 호출 } void AMyChar::OnHealthChanged() { // 체력바 갱신, 사운드 재생 등 // 서버·클라 공통 반응 로직 }

이렇게 하면 서버는 SetHealth에서, 클라는 OnRep에서 모두 OnHealthChanged를 부르게 돼. 한 함수로 양쪽 반응을 통일.

함정: 서버에서 그냥 Health = 70으로 변수에 직접 대입하면 OnHealthChanged가 안 불려서 서버 쪽 반응이 빠짐. 그래서 변경은 항상 Setter를 거치게 코드 규율을 잡아.
Q. 변경분 패킷이 유실되면 클라는 옛 값에 머물러?

크게 걱정 안 해도 돼.

  • reliable 속성이면 자동 재전송 → 결국 맞춰져.
  • unreliable이어도, 복제는 "최신 상태를 계속 맞추는" 거라 다음 갱신이 오면 최신 값으로 수렴.
[유실 → 수렴] 서버: HP 100 → 70 → 50 클라: HP 100 → 70 → (50 패킷 유실) → 30 (다음 갱신) └─ 50을 못 봤어도 30으로 따라옴, 결국 일치

위험은 "값을 본 순간 반응해야 하는데 못 본 경우" — 예: HP 50에서 트리거되는 이펙트가 안 발동. 그래서 중요한 트리거는 별도 RPC로 명시 송신해 보완해.

Q. 한 틱에 100→50→100으로 두 번 바뀌면 중간값 50을 봐?

보통 못 봐. 복제는 틱 끝의 현재 상태를 보내. 100→50→100이면 클라는 그냥 "100 → (틱 후) 100"로 변화를 못 느낄 수도 있어.

[틱 안 다중 변경] 서버 틱 시작: HP=100 데미지 50: HP=50 (안 보냄, 틱 내부) 포션 +50: HP=100 (안 보냄) 서버 틱 끝: HP=100, 변경 없음 → 클라에 안 보냄

중간 변화가 중요하면(피격 → 사운드 발화):

  • RPC로 명시 송신: "맞았어!"를 Multicast로 별도 알림. 값과 별개로 사건을 보장.
  • OnRep RepNotify: 값이 같으면 OnRep이 안 불리니, 이벤트는 RPC가 정답.
콤보가 빠른 격투 게임에서 흔한 함정. "체력 변화"가 아닌 "피격 이벤트"를 신호로 써야 콤보 카운트가 정확해.
Q. 복제 순서가 보장돼? B가 A보다 먼저 도착하면?

같은 액터 안의 속성들은 한 묶음(Bunch)으로 한 번에 가서 일관돼. 단 액터 사이 순서는 보장 약함.

[액터 간 순서 함정] 서버: PlayerA가 ItemB를 픽업 - PlayerA.Inventory에 B 추가 - ItemB.bDestroyed = true 복제: - 클라 A: ItemB 파괴 도착 → 이후 인벤 갱신 - 클라 B: 인벤 갱신 도착 → 이후 ItemB 파괴 → 일관성은 결국 맞지만 순간 짝짝이

의존이 있는 두 값은:

  • 한 액터로 묶기: PlayerA 안에 두 값을 함께 두면 한 Bunch에 묶여 동기.
  • RPC로 명시: "픽업 완료" 한 메시지로 두 변화를 함께 전달.
  • OnRep에서 검증: 클라가 받았을 때 다른 액터 상태를 확인하고 필요시 보정.
