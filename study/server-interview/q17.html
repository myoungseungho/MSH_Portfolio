Q17. DB가 병목이다. 캐시를 넣는다면 무엇을·어디에 두고, 무효화는 어떻게?

1차 답변

0. "DB가 병목"이 무슨 병목인지부터 좁힙니다

저는 "캐시 넣죠"로 바로 안 갑니다. 먼저 어떤 병목인지 묻습니다. 캐시는 읽기 병목만 풉니다. 만약 초당 쓰기가 넘쳐서 DB가 죽는 거라면, 앞에 캐시를 붙여봐야 쓰기는 결국 DB로 내려가니 병목이 그대로거나 오히려 일관성 문제만 늘어납니다. 그래서 첫 질문은 "읽기가 아픈가, 쓰기가 아픈가"입니다.

두 번째로 짚는 게 있습니다. MMORPG 게임 서버는 이미 거대한 캐시입니다. 웹 서버는 요청마다 상태가 없어서(stateless) DB를 매번 두드리니 앞에 Redis를 두는 게 당연하죠. 그런데 우리 C++ 게임 서버는 접속한 유저의 인벤·골드·위치를 전부 메모리에 authoritative하게 들고 플레이 내내 그 메모리에서 처리합니다. DB는 주기적으로 내려쓰는 백업일 뿐이에요. 즉 유저 개인 상태는 이미 캐싱돼 있습니다. 여기에 Redis를 또 얹으면 진실이 셋(게임 서버 메모리 / Redis / DB)이 되고, 진실이 셋이면 반드시 어긋납니다.

1. 순진하게 가면 이렇게 됩니다

순진한 안: DB 앞에 Redis 한 대 붙이고, 읽을 때 캐시부터 보고 없으면 DB에서 읽어 캐시에 채운다(cache-aside). "이제 DB 부하 줄었죠?"

이게 웹에서는 정답에 가깝습니다. 그런데 게임 서버에 그대로 가져오면 무효화 지옥이 열립니다. 유저가 골드를 쓰면 게임 서버 메모리에선 90인데 Redis엔 100이 남아 있습니다. 이 낡은 100을 누가, 언제 지우죠? 개인 상태처럼 초 단위로 바뀌고 게임 서버가 이미 진실을 쥔 데이터를 Redis에 또 캐싱하는 건, 문제를 푸는 게 아니라 새로 만드는 겁니다.

2. 그래서 저는 "무엇을 캐싱하느냐"부터 자릅니다

캐싱이 이득인 데이터는 딱 세 조건입니다. 자주 읽히고, 드물게 바뀌고, 여러 유저·서버가 공유하는 것. 이 셋을 만족하는 건 개인 골드가 아니라 아이템 스펙 테이블, 상점 목록, 스킬 데이터, 랭킹, 길드 정보 같은 정적·준정적 데이터입니다. 이런 건 캐시의 천국이에요. 만 명이 같은 아이템 툴팁을 보는데 매번 DB를 두드릴 이유가 없죠.

반대로 유저 개인 상태(인벤·골드·위치)는 캐싱 대상이 아니라 이미 게임 서버 메모리가 소유한 것입니다. 여기엔 Redis를 안 얹습니다. 이 구분 하나가 무효화 문제의 8할을 없앱니다 — 안 어긋나게 하는 최선은 진실을 애초에 하나로 두는 것이니까요.

3. 어디에 두나 — 로컬이냐 분산이냐

정적 데이터(아이템 스펙 등)는 프로세스 안 로컬 캐시로 충분합니다. 서버 뜰 때 통째로 메모리에 올려두고 패치 전까지 안 바꿔요. 네트워크 왕복이 아예 없으니 제일 빠릅니다. 반면 여러 서버가 공유하고 실시간으로 바뀌는 것(경매 시세, 크로스 서버 랭킹)은 로컬에 두면 서버마다 값이 달라지니 Redis 같은 분산 캐시에 둡니다. 판단축은 "이 데이터가 서버 간에 같아야 하나"입니다.

4. 무효화 — 어긋남을 어떻게 다루나

무효화 전략은 결국 "얼마나 낡아도 되나(stale 허용치)"가 정합니다.

(1) TTL(만료). 제일 단순합니다. "몇 초/몇 분 낡아도 됨"이면 그냥 시간 지나면 버립니다. 상점 목록, 랭킹 표시처럼 몇 초 지연이 무관한 데이터에 최적.

(2) 이벤트 기반 무효화. 데이터가 바뀔 때 pub/sub으로 "이거 지워"를 쏴서 즉시 무효화. 정확하지만 이벤트가 유실되면 캐시가 영영 낡은 채로 남는 위험이 있습니다.

(3) 아예 무효화 안 하기. 정적 데이터는 무효화 대신 버전으로 통째 교체합니다. 패치 때 v2를 통째로 새로 로드하고 스위치만 바꿔요. "부분 갱신"이 없으니 어긋날 일도 없습니다.

🧭 이 문제의 원칙"캐시는 진실을 하나 더 만드는 일이다. 진실이 둘이면 언젠가 어긋난다." 그러니 어긋나도 되는 것(정적·공유·읽기중심)만 캐싱하고, 게임 서버가 이미 진실을 쥔 개인 상태는 절대 이중화하지 마라. 무효화 난이도는 stale 허용치의 함수다.

면접관 꼬리질문
면접관🔥 "게임 서버 메모리가 캐시라면서요. 그럼 서버가 여러 대일 때, A 서버에서 바꾼 걸 B 서버가 어떻게 알죠?"

좋은 지적입니다. 그런데 여기서 MMORPG의 구조가 도와줍니다 — 유저는 동시에 한 서버에만 접속합니다. 제 인벤을 A 서버가 들고 있으면 그 순간 B 서버는 제 인벤을 만질 일이 없습니다. 소유가 단일이라 "두 서버가 같은 개인 데이터를 캐싱해서 어긋나는" 상황 자체가 잘 안 생깁니다. 그래서 개인 상태는 서버 간 동기화 문제가 아니라 소유권 문제로 풉니다.

진짜 크로스 서버로 공유되는 건 길드·경매·랭킹처럼 여러 서버가 같이 보는 데이터죠. 이건 공유 저장소(Redis나 DB)를 유일한 진실로 두고, 각 게임 서버는 그걸 읽어서 캐싱만 합니다. 그리고 바뀔 때 pub/sub으로 "무효화해"를 브로드캐스트하죠. 핵심은 진실의 소유자를 하나로 정하는 것입니다 — 개인 데이터는 접속한 게임 서버가, 공유 데이터는 중앙 저장소가. 소유자만 쓰고 나머지는 캐시로만 읽으면, "A가 바꾼 걸 B가 어떻게 아나"가 "소유자가 무효화 이벤트를 쏜다"로 단순해집니다.

면접관🔥 "Redis도 죽을 수 있잖아요. 캐시가 통째로 날아가면 요청이 전부 DB로 몰려서 DB가 더 빨리 죽을 텐데요?"

정확히 캐시 스탬피드(cache stampede), 다른 말로 thundering herd입니다. 캐시가 비는 순간 만 개 요청이 동시에 "없네? DB에서 읽자"로 몰려 DB를 한 방에 눕히는 거죠. TTL 만료가 한꺼번에 겹칠 때도 똑같이 터집니다.

세 가지로 막습니다. (1) 만료에 jitter를 — 모든 키를 정확히 같은 시각에 만료시키면 절벽이 생깁니다. TTL에 랜덤을 섞어 만료를 흩뜨립니다. (2) 요청 병합(single-flight) — 같은 키를 동시에 미스한 만 개 요청 중 딱 하나만 DB로 내려가고 나머지는 그 결과를 기다립니다. DB로 가는 건 만 번이 아니라 한 번이 되죠. (3) stale-while-revalidate — 만료된 값도 일단 그대로 내주고 뒤에서 조용히 갱신합니다. 잠깐 낡은 값이 DB를 지키는 방패가 됩니다.

그리고 제일 중요한 원칙 하나. 캐시를 '있으면 빠른 최적화'가 아니라 '없으면 죽는 필수 의존'으로 만들면 안 됩니다. 캐시가 다 날아가도 DB가 원래 부하를 감당할 수 있게 용량을 잡아둬야, 캐시 장애가 서비스 장애로 번지지 않습니다. 캐시는 DB를 돕는 것이지 대신하는 게 아닙니다.

면접관🔥 "무효화를 이벤트로 한다고 했는데, 그 무효화 이벤트가 유실되면요? 캐시가 영영 낡은 채로 남잖아요."

맞습니다. 이벤트 기반 무효화의 근본 약점이에요. pub/sub은 대개 "보냈는데 아무도 못 받아도 모른다"는 성질이 있어서, 무효화 메시지 하나 유실되면 그 키는 다음 변경 때까지 낡은 값을 계속 내줍니다. 그리고 이런 건 라이브에서 재현도 잘 안 됩니다.

그래서 저는 이벤트 무효화를 단독으로 안 쓰고 TTL을 안전망으로 겹칩니다. 이벤트는 "빠른 무효화"(바뀌면 거의 즉시 반영), TTL은 "최종 수렴 보장"(이벤트를 놓쳐도 최대 N초 뒤엔 무조건 만료돼 새로 읽음) — 두 겹으로 두면 정확성은 이벤트가, 안전은 TTL이 책임집니다. 낡음의 상한이 TTL로 못 박히는 거죠.

그리고 무효화는 멱등하게 설계합니다. "이 키를 지워라"는 두 번 와도, 순서가 뒤집혀도 결과가 같아야 합니다. 더 엄격하게는 값에 버전을 실어서 "이 버전보다 낮으면 무시"로 낡은 무효화가 새 값을 덮어쓰는 것까지 막습니다. 정리하면 이벤트는 빠르게, TTL은 확실하게, 멱등성으로 순서를 방어 — 이 셋이 세트입니다.
