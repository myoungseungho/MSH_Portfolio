Q81. 패킷 리플레이 공격(같은 요청 반복 전송)을 어떻게 막나?

1차 답변

0. 저는 먼저 "누가, 무엇을 다시 보내는가"를 나눕니다

리플레이라고 하면 두 가지가 섞여 있어서 먼저 나눕니다. (a) 정상 유저가 자기 패킷을 반복 전송 — "회복 물약 사용" 패킷 하나를 캡처해 1000번 다시 쏴서 물약 하나로 무한 회복, "우편 받기"를 재전송해 중복 수령. (b) 제3자가 남의 패킷을 가로채 재전송 — 로그인·인증 패킷을 캡처해 세션을 도용. 방어 도구가 서로 다릅니다.

그리고 하나 못 박습니다 — 우리가 TCP(조선협객전의 IOCP)를 쓰면 네트워크 계층의 중복은 TCP 스택이 이미 제거합니다. 그러니 우리가 막을 대상은 우연한 중복이 아니라 애플리케이션 레벨의 '의도적인 재전송'입니다. 이걸 구분 못 하고 "TCP라 리플레이 걱정 없다"고 하면 헛다리입니다.

1. 순진한 첫 안 — "암호화하면 리플레이 못 한다"

순진한 안: "패킷을 암호화하면 공격자가 내용을 모르니 재전송도 못 한다."

이건 틀렸습니다. 리플레이는 내용을 알 필요가 없습니다. 암호문을 그대로 복사해 다시 보내면, 서버는 정상적으로 복호화해서 똑같이 처리합니다. 암호화는 "내용을 숨기는" 것이지 "재사용을 막는" 게 아닙니다. 자물쇠가 걸린 편지를 통째로 복사해 여러 번 부치는 것과 같아서, 봉투를 못 열어도 공격은 성립합니다.

2. 어디서 터지나 — 한 번 유효한 요청이 여러 번 먹힌다

문제의 본질은 "한 번만 유효해야 할 요청이 여러 번 유효해지는 것"입니다. "물약 사용" 패킷을 1000번 재전송하면 물약 하나로 1000번 회복하고, "우편 수령"을 재전송하면 첨부 아이템을 중복으로 받고, "인증 성공 토큰"을 재전송하면 남의 세션에 올라탑니다. 공통점은 서버가 "이건 아까 그 요청이잖아"를 구분하지 못한다는 것입니다.

3. 개선 — 각 요청을 '한 번만 유효'하게 만든다

방어는 네 겹으로 겹칩니다.

(1) 시퀀스 번호 / nonce. 요청마다 순번을 붙이고 서버는 기대하는 다음 순번을 기억합니다. 재전송은 이미 지난 번호라 폐기됩니다.

(2) 서버 권위로 상태를 소비. "물약 사용"은 클라가 "썼다"가 아니라 서버가 인벤에서 1개 차감합니다. 재전송이 와도 재고가 없으면 그냥 실패합니다.

(3) 상태 기반 거부. 이미 처리한 요청이면(우편이 이미 claimed) 재요청을 무시합니다.

(4) 멱등키 + 시간 창. 지급·거래류는 멱등키(idempotency key)로 "같은 키는 한 번만" 처리하고, 인증류는 타임스탬프+nonce로 만료된 요청을 폐기합니다(replay window).

4. 트레이드오프 — 공짜 방어는 없다

시퀀스 번호는 서버가 커넥션마다 기대값을 상태로 들고 있어야 합니다(메모리). nonce 캐시는 만료 관리가 필요하고, 완전한 순서 강제는 재정렬이 흔한 UDP와 안 맞습니다. 모든 패킷에 서명을 박으면 CPU·대역폭이 붙습니다. 그래서 "다 서명·다 nonce"가 아니라 요청의 가치에 맞춰 방어 강도를 나눕니다.

5. 상황별 최적해

TCP 세션 내부(IOCP 게임 서버): TCP가 순서를 보장하니 커넥션당 시퀀스 카운터 하나면 세션 내 재전송은 싸게 막힙니다. 핵심 액션은 여기에 서버 권위+멱등을 이중으로.

지급·거래·결제: 멱등키가 최종 방어입니다. 리플레이든 정상 재시도든 "같은 키는 한 번"이면 안전합니다.

인증 토큰: 짧은 만료 + 1회용 nonce + 채널 바인딩(발급된 세션에서만 유효). 그래야 가로채도 재사용이 막힙니다.

UDP 실시간 전투: 패킷별 시퀀스+타임스탬프, 오래된 건 폐기. 실시간이라 지난 패킷은 어차피 무의미하니 창을 짧게.

🧭 이 문제의 원칙"리플레이 방어의 본질은 암호가 아니라 '한 번만 유효(one-time validity)'다." 순번(nonce)으로 옛 요청을 걸러내고, 설사 통과해도 서버 권위·멱등성으로 '두 번 먹지 못하게' 한다. 암호화는 내용을 숨길 뿐 재사용을 막지 않는다 — 방어는 숨김이 아니라 '유효성 소비'다.

면접관 꼬리질문
면접관🔥 "시퀀스 번호를 붙인다고요? 공격자가 그 번호를 조작해서 올려 보내면 그냥 통과하는 거 아니에요?"

맞습니다, 시퀀스가 클라가 마음대로 정하는 값이면 무력합니다. 그래서 두 가지를 겁니다. 첫째, 시퀀스의 기대값은 클라가 아니라 서버가 쥡니다. 서버가 "다음은 N번"을 기억하고, 벗어나면 폐기합니다. 공격자가 번호를 올려 봐도 세션 키로 묶인 서명·암호가 없으면 위조가 안 됩니다 — 세션 단위로 인증된 채널 안에서만 시퀀스가 의미를 갖게 합니다.

둘째, 더 중요한 건 시퀀스가 1차 필터일 뿐이라는 점입니다. 저는 시퀀스 하나에 방어를 걸지 않습니다. 설사 시퀀스를 통과시켜도 서버 권위와 멱등성이라는 2차 방어가 기다립니다 — "물약 사용"이 통과해도 인벤에 물약이 없으면 실패하고, "우편 수령"이 통과해도 이미 받은 상태면 무시됩니다. 그래서 시퀀스가 뚫려도 공격자가 실제로 얻는 이득은 0입니다. 리플레이 방어는 단일 관문이 아니라 계층 방어(defense in depth)여야 합니다 — 한 겹이 뚫려도 다음 겹에서 이득을 없애는 게 핵심입니다.

면접관🔥 "그럼 멱등키만 잘 박으면 시퀀스 번호는 필요 없는 거 아니에요? 중복이면 어차피 한 번만 처리되잖아요."

역할이 달라서 하나로 다른 하나를 대신 못 합니다. 멱등은 "같은 걸 여러 번 해도 결과가 한 번"을 보장합니다 — 지급·거래처럼 본질적으로 1회여야 하는 요청에 완벽합니다.

그런데 정상적으로 여러 번 반복 가능한 액션이 문제입니다. "회복 물약 사용"은 유저가 진짜로 10번 연속 쓸 수 있습니다. 그러면 리플레이된 요청도 "또 하나의 정상적인 사용"처럼 보여서 멱등키로는 구분이 안 됩니다 — 매번 다른 유효 요청이니까요. 이건 멱등이 아니라 서버 권위(인벤에서 실제 차감)로 막습니다. 물약이 3개면 4번째 재전송은 재고가 없어 실패합니다.

정리하면 도구가 상황별로 나뉩니다 — 1회성 요청은 멱등키, 반복 가능한 요청은 서버 권위로 상태 소비, 순서가 있는 세션은 시퀀스로 옛 요청 컷. 리플레이는 한 가지 모양이 아니라서 한 가지 도구로 다 못 막습니다. "어떤 종류의 리플레이냐"를 먼저 물어야 맞는 도구가 나옵니다.

면접관🔥 "복잡하게 나누지 말고, 그냥 모든 패킷에 타임스탬프랑 서명 박으면 리플레이 다 막히는 거 아니에요?"

매력적으로 들리지만 두 가지 이유로 그렇게 안 합니다. 첫째, 타임스탬프+서명은 '오래된' 리플레이만 막습니다. 서명으로 위조는 막고 만료로 옛 패킷은 걸러지지만, replay window 안(몇 초)의 재전송은 그대로 통과합니다. 공격자가 캡처 직후 바로 쏘면 타임스탬프도 유효하고 서명도 진짜라 못 걸러냅니다. 결국 "한 번만 유효"를 만들려면 nonce/시퀀스로 "이미 본 요청"을 기억해야 하지, 시간만으론 부족합니다.

둘째, 전 패킷 서명은 비쌉니다. 매 이동·전투 패킷마다 서명·검증을 하면 CPU와 대역폭이 붙습니다. 초당 수만 패킷이 오가는 게임 서버에서 이건 무시 못 할 상시 비용입니다. 그래서 저는 가치에 맞춰 강도를 나눕니다 — 재화·거래·인증 같은 고가치 요청에만 서명·nonce를 걸고, 일반 액션은 세션 시퀀스로 싸게 처리하고, 실시간 전투는 서버 권위로 결과를 산출해 애초에 리플레이할 '결과'가 없게 만듭니다. "다 서명"은 검증을 무조건 켜는 것과 같은 실수예요 — 방어도 비용 대비 이득으로 배치해야지, 획일적으로 최대치를 바르면 성능이 죽습니다.
