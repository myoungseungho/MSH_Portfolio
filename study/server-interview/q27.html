Q27. 멱등성(idempotency)이 왜 필요하고, 지급 로직에 어떻게 넣나?

1차 답변

0. 저는 "중복이 어디서 태어나는지"부터 짚습니다

멱등성을 "넣으면 좋은 안전장치" 정도로 말하면 면접에서 약합니다. 저는 먼저 왜 지급 로직엔 중복 요청이 반드시 들어오는지를 말합니다. 중복은 버그가 아니라 분산 시스템의 기본 조건이거든요.

(1) 네트워크 재시도. 클라가 "받기"를 눌렀는데 응답이 안 옵니다(타임아웃). 실제론 서버가 지급을 다 하고 응답만 유실됐을 수도 있죠. 클라는 성공인지 실패인지 모르니 재시도 → 같은 지급이 두 번. (2) 더블클릭·매크로. 받기 버튼 연타. (3) 큐 at-least-once. 지급을 메시지 큐로 처리하면 큐는 "적어도 한 번"을 보장하지 "정확히 한 번"을 못 해서, 같은 메시지가 두 번 소비될 수 있습니다. (4) 크래시 후 재처리. 지급 도중 서버가 죽어 재부팅 후 그 작업을 다시 돌립니다.

그래서 질문을 뒤집습니다. "중복을 어떻게 막나"가 아니라 "중복이 와도 결과가 한 번과 같게 어떻게 만드나." 이게 멱등성입니다 — 같은 요청을 1번 하든 100번 하든 최종 결과가 1번과 동일한 성질.

1. 순진한 첫 안 — "이미 받았나 확인하고 주기"

순진한 안: 지급 전에 SELECT로 "이미 받았나(claimed)" 확인 → 안 받았으면 지급하고 claimed=1 → 이미 받았으면 무시.

읽어보면 맞는 것 같습니다. 그런데 여기 함정이 둘 있습니다.

2. 어디서 터지나 — check-then-act 레이스와 반쪽 지급

(1) 동시성 레이스. 재시도와 원본이 거의 동시에 도착하면, 두 요청이 둘 다 SELECT → 둘 다 "안 받음" → 둘 다 지급 → 둘 다 claimed=1. 아이템이 두 개 나갑니다. "확인"과 "지급" 사이에 틈이 있어서죠.

(2) 두 쓰기의 원자성 결여. 지급(인벤 INSERT)은 됐는데 claimed=1 쓰기 전에 서버가 죽으면 → 재처리 때 또 지급(중복). 반대 순서면 → claimed만 되고 아이템은 안 감(유실). 순진한 안은 이 두 곳에서 깨집니다.

3. 개선 — 멱등 키를 DB 제약으로 못 박는다

핵심은 "확인 후 지급"을 두 스텝으로 하지 않고 지급의 유일성을 원자적 한 방으로 판정하는 겁니다. 지급마다 고유한 멱등 키(idempotency key)를 정하고, 지급 원장(ledger) 테이블에 그 키로 UNIQUE 제약을 겁니다. 지급 = 원장에 (key) INSERT.

키가 처음이면 INSERT 성공 → 지급 진행. 중복이면 UNIQUE 위반으로 INSERT 실패 → "이미 처리됨"으로 판단하고 조용히 성공 응답(에러가 아니라 "그때 이미 줬음"). DB가 원자적으로 "이 키가 처음인가"를 판정해주니, check와 act가 한 연산으로 합쳐져 레이스가 사라집니다.

키는 뭘로 할까요. 자연키가 있으면 그걸 씁니다. 우편 보상이면 (uid, mail_id) — 이 유저가 이 우편을 받는 건 논리적으로 한 번뿐이니까요. 외부 결제면 결제사 거래 ID, 큐 소비면 메시지 ID. 자연키가 없으면 요청 생성 시 UUID를 발급합니다.

4. 지급과 원장을 한 트랜잭션에

원장 INSERT와 실제 지급(인벤 반영)이 따로 놀면 다시 2번 문제(원자성)로 돌아갑니다. 같은 DB라면 둘을 한 트랜잭션으로 커밋합니다 — 원장 INSERT + 인벤 INSERT + 재화 UPDATE가 전부 아니면 전무. 크래시가 나도 반쪽 지급이 없습니다.

5. 트레이드오프

원장이 계속 쌓입니다. 모든 지급의 키를 영구 보관하면 테이블이 폭증하니 TTL·파티셔닝이 필요한데, 키를 지우면 그 뒤 도착한 지각 재시도가 다시 통과(중복)합니다. 그래서 보관 기간은 재시도가 올 수 있는 최대 창보다 길게 잡습니다. 키 설계가 곧 정확성입니다 — 키가 너무 좁으면(예: uid만) 서로 다른 지급을 같은 걸로 오인해 지급 누락, 너무 넓으면(매 요청 새 UUID인데 재시도가 새 키로 오면) 중복을 못 막습니다. 그리고 자연키 vs 생성키 — 자연키는 클라가 못 바꾸니 어뷰징에 강하고, 클라 생성키는 "같은 논리 요청의 재전송"엔 유효하지만 클라가 매번 새 키로 우기면 못 막습니다. 그래서 서버 권위 자연키를 우선합니다.

🧭 이 문제의 원칙"중복은 막는 게 아니라 흡수한다." 재시도가 일상인 분산 세계에서 "정확히 한 번 전송"은 신화다. 같은 요청을 몇 번 실행해도 결과가 한 번과 같게 만드는 것 — 멱등이 유일한 안전장치다.

면접관🔥 "키를 클라가 만들게 하면, 클라가 매번 다른 키로 보내서 같은 보상을 여러 번 받을 수 있잖아요?"

정확한 지적입니다. 그래서 지급 대상이 "논리적으로 한 번"이 정해진 것이면 클라 키를 신뢰하지 않고 서버 자연키를 씁니다. 우편은 (uid, mail_id)가 자연 멱등 키라, 클라가 무슨 키를 보내든 서버는 이 우편을 이 유저에게 딱 한 번만 줍니다.

클라 생성 키(UUID)의 용도는 "인프라 재시도"를 흡수하는 것이지 "논리적 중복"을 막는 게 아닙니다. 둘을 구분해야 합니다 — 인프라 재시도(같은 의도의 재전송)는 클라 키로 흡수하고, 어뷰징(다른 의도로 위장한 반복)은 서버 자연키·비즈니스 규칙으로 막습니다.

자연키가 없는 요청, 예컨대 "상점에서 물약 구매"는 각 구매가 정당한 별개라 애초에 멱등 대상이 아니라 정상 트랜잭션입니다. 대신 그 "구매 요청" 자체에 클라 발급 request_id를 붙여 그 단위로만 멱등하게 합니다. 즉 request_id는 "이 클릭"을 유일화하지 "이 상품"을 유일화하지 않습니다. 이 구분을 못 하면 더블클릭 방어(클릭 멱등)와 중복 획득 방어(자산 멱등)를 뒤섞어 엉뚱한 걸 막게 됩니다.

면접관🔥 "원장 INSERT랑 실제 지급이 다른 저장소에 있으면요? 인벤은 게임 서버 메모리고 원장은 DB면 한 트랜잭션으로 못 묶잖아요."

조선협객전이 실제로 이 모양이었습니다. 인벤은 C++ 서버 메모리에, 확정된 진실은 DB에 있었죠. 한 트랜잭션에 못 묶으니 순서와 재조정으로 풉니다.

먼저 가벼운 진실(멱등 키 + 지급 의도)을 DB에 못 박고 → 메모리 인벤에 반영 → 크래시로 그 반영이 날아가도, 재부팅 시 "원장엔 지급됐다는데 인벤에 없네"를 발견해 멱등하게 다시 지급합니다. 반대로 인벤부터 먼저 채우면, 원장 없이 준 걸 나중에 판정할 수가 없어 위험합니다. 그래서 언제나 진실을 먼저 남깁니다.

이게 outbox/저널 패턴 — DB가 WAL로 하는 걸 지급 파이프라인에서 흉내 내는 겁니다. 핵심은 "두 저장소를 원자적으로 묶으려 애쓰지 말고, 한쪽을 단일 진실로 삼고 나머지를 그 진실에서 멱등하게 재생 가능하게" 만드는 것. 우편 지급(q01)에서 "가벼운 진실 먼저 못 박고 무거운 반영은 재생 가능하게"라고 했던 것과 정확히 같은 뼈대입니다.

면접관🔥 "지급이 여러 서비스에 걸치면(재화 서버 차감 + 아이템 서버 지급) UNIQUE 하나로 못 막잖아요. exactly-once 되나요?"

정직하게, 분산에서 진짜 exactly-once는 불가능합니다. 네트워크가 응답 유실을 100% 못 막으니 "정확히 한 번 실행"은 신화예요. 실무에서 하는 건 effectively-once = at-least-once(재시도) + 멱등입니다. 각 단계가 각자 멱등하면, 전체를 몇 번 재생해도 결과는 한 번에 수렴합니다.

여러 서비스면 각 서비스가 같은 멱등 키(사가의 트랜잭션 ID)를 공유해 자기 몫을 멱등 처리하고, 중간이 실패하면 보상 트랜잭션(saga)으로 되돌립니다. 중앙 멱등 저장소(Redis SETNX나 DB)로 "이 키 처리 중/완료"를 조율할 수도 있지만, 그것도 단일 장애점이 됩니다.

그래서 저는 "완벽한 원자성"을 약속하지 않습니다. 각 단계 멱등 + 재시도 + 재조정으로 "결과적으로 한 번"에 수렴시키고, 금전처럼 오차가 치명적인 건 정산 배치로 사후 대사(reconciliation)까지 겁니다 — 로그를 훑어 "차감됐는데 지급 안 된 건" 찾아 메꾸는 거죠. q24(차감 후 지급 크래시)와 정확히 같은 뼈대이고, 우편(q01)에서 "결제는 우편과 다른 파이프"라고 선 그은 것과도 이어집니다.
