Q52. 출석·이벤트 보상을 시간 조작(클라 시계)으로 중복 수령하려는 시도를 어떻게 막나?

1차 답변

0. 저는 먼저 "그 공격이 성립하려면 뭐가 참이어야 하나"를 묻습니다

이 질문을 받으면 저는 방어책부터 나열하지 않고 공격의 전제를 먼저 봅니다. "클라 시계를 앞으로 돌려서 며칠치 출석을 한 번에 받는다"가 성립하려면, 우리 서버가 '오늘이 며칠인지'를 클라가 보낸 값으로 판정하고 있어야 합니다. 그 전제가 깨져 있으면 이 공격은 애초에 불가능하죠.

그래서 저는 질문을 뒤집습니다. "우리 지급 로직 어디에서 클라 시계를 믿고 있습니까?" 잘 짠 서버라면 답은 "어디에서도 안 믿습니다"여야 하고, 그럼 이 문제는 방어가 아니라 이미 뚫렸다면 왜 뚫렸는지를 역추적하는 문제가 됩니다.

1. 순진한 첫 안 — 클라가 "오늘 출석했어요"라고 말하게 둔다

제일 위험한 설계: 클라가 {today: "2026-07-19"} 같은 날짜를 담아 "출석 받기"를 보내고, 서버가 그 날짜를 그대로 믿고 지급한다. 또는 이벤트 종료 판정을 클라가 보낸 timestamp로 한다.

이러면 유저는 PC 시계를 내일로, 모레로 돌려가며 한 자리에서 7일치 연속 출석 보상을 쓸어담습니다. 이벤트라면 이미 끝난 이벤트 보상을 "제 시계로는 아직 기간 안이에요" 하고 계속 받습니다. 클라가 만든 값을 지급 판정에 쓴 순간 게임 경제가 뚫린 겁니다.

2. 어디서 터지나 — '시간에 값이 붙는 판정'을 클라에 맡긴 지점

구체적으로 세 군데가 사고 지점입니다. (1) 지급 여부를 클라가 보낸 날짜/시각으로 판정한다. (2) 서버 시계를 쓰긴 하는데 "이 유저가 언제 마지막으로 받았나"를 안 들고 있다 — 그럼 재접속할 때마다 "오늘 것"을 또 줍니다. (3) 이벤트 시작/종료 경계 판정을 클라 timestamp로 한다. 셋 다 뿌리는 하나예요 — 시간을 클라가 정한다.

3. 개선 — 진실은 오직 '서버가 기록한 마지막 수령 날짜' 하나

제 원칙은 단순합니다. 시간에 값이 붙는 모든 판정은 서버 시계로만 한다. 클라가 보내는 날짜는 참고조차 안 합니다. 지급의 진실은 유저별로 딱 하나 — last_claim_date(마지막으로 출석 보상을 받은 서버 기준 날짜)입니다.

흐름은 이렇습니다. 유저가 "출석 받기"를 누르면, 서버가 자기 시계로 오늘 날짜를 계산하고 → last_claim_date와 비교해 → 이미 오늘이면 거절, 아니면 지급하고 last_claim_date = today로 갱신합니다. 클라 시계를 아무리 미래로 돌려도 서버가 계산하는 "오늘"은 안 바뀌니 두 번째 수령은 막힙니다. 클라 시계는 오직 화면의 카운트다운을 그리는 데만 씁니다. 화면이 조금 틀리는 건 손해가 아니지만, 지급이 틀리는 건 경제 사고니까요.

4. 그런데 트레이드오프 — '서버의 오늘'은 누구의 오늘인가

서버 시계로 판정하면 새 질문이 생깁니다. "출석의 하루 경계(자정)는 누구 기준인가?" 서버가 여러 리전이면 UTC냐, 유저 리전이냐로 결과가 갈립니다. 또 "출석"의 정의도 정해야 합니다 — 접속만 하면 되나, 하루 한 번 버튼을 눌러야 하나, 연속 출석(streak)이 끊기는 기준은 무엇인가. 그리고 서버 시계 자체도 여러 대 사이에서 조금씩 어긋날 수 있습니다. 이건 뒤 꼬리질문에서 정면으로 다루겠습니다.

5. 상황별 최적해 — 보상의 '시간 모양'에 따라 진실의 열쇠가 다르다

단순 일일 출석이면 last_claim_date 하루 단위 비교로 충분합니다. N시간 쿨타임형(예: 6시간마다)이면 날짜가 아니라 서버 절대시각 last_claim_at을 들고 "지금 - 마지막 >= 쿨타임"으로 판정합니다. 기간 한정 이벤트면 서버 시각으로 start <= now < end를 검사하되 클라가 보낸 timestamp는 절대 안 씁니다. 연속 출석 streak이면 "어제 받았나"까지 서버 날짜 기준으로 계산해 streak을 올리거나 리셋합니다. 공통점은 하나 — 판정의 시간 축이 전부 서버 것이라는 겁니다.

🧭 이 문제의 원칙"시간에 값을 매기는 판정은 전부 서버 시계로 한다. 클라 시계는 화면을 그리는 데만 쓴다." 지급의 진실은 '클라가 말하는 오늘'이 아니라 '서버가 기록한 마지막 수령'이다. 클라가 보내는 날짜·시각은 판정에서 존재하지 않는 것처럼 다뤄라.

면접관 꼬리질문
면접관🔥 "서버 시계를 믿으라는데, 서버가 여러 대고 시계가 조금씩 어긋나면요? 자정 경계에서 A 서버는 오늘, B 서버는 어제로 판정하면 중복이 나잖아요?"

제 "서버 시계로만" 답의 빈틈을 정확히 찌르셨습니다. 서버가 분산되면 '서버 시계'가 여러 개가 되고, 그중 하나라도 판정에 끼면 그게 새 구멍이 됩니다. 그래서 저는 "판정 시각의 권위를 한 곳으로 모읍니다."

핵심은 날짜 롤오버 판정을 게임 서버 각자의 로컬 시계로 하지 않는 것입니다. 지급 조건 검사를 최종적으로 결정하는 층 — 보통 DB나 공용 스토리지 — 한 곳의 시각으로 통일합니다. 예를 들어 last_claim_date를 갱신하는 그 쿼리 안에서 DB의 now()를 기준으로 오늘을 계산하면, 게임 서버가 열 대든 스무 대든 "오늘"은 언제나 한 시계가 정합니다. 게임 서버들의 로컬 시계는 UI 카운트다운에만 쓰고, 돈이 걸린 경계 판정은 단일 권위에 위임하는 거죠.

물론 그 단일 권위도 NTP로 동기화는 해둡니다. 하지만 NTP는 '대략 맞추기'지 '정확히 같기'를 보장하진 않으니, 저는 정확성을 시계 동기화에 기대지 않고 판정 주체를 하나로 만드는 구조로 해결합니다. 시계를 맞추는 것보다 "누구의 시계로 재느냐"를 못 박는 게 훨씬 튼튼합니다. 리전별 자정 문제까지 겹치면 그건 별도로 "이 이벤트의 하루 경계는 UTC 00시"처럼 경계의 정의 자체를 서버 정책으로 고정해서 리전 로컬 자정에 흔들리지 않게 합니다.

면접관🔥 "시계 조작 말고요. 그냥 '출석 받기' 패킷을 아주 빠르게 두 번 보내면요? 더블클릭이나 매크로로. 서버가 아직 첫 번째를 처리 중일 때 두 번째가 들어오면 둘 다 지급되는 거 아닌가요?"

이건 시간 조작이 아니라 동시성(경합) 공격이죠. "읽고 → 판정 → 지급 → 기록" 사이에 두 번째 요청이 끼어들면 둘 다 "아직 안 받았네"를 보고 둘 다 지급합니다. 이걸 막는 건 판정과 기록을 하나의 원자적 연산으로 묶는 것입니다.

저는 지급 여부를 별도로 읽어보고 나서 갱신하지 않고, 조건부 갱신 한 방으로 처리합니다 — UPDATE ... SET last_claim_date = today WHERE user_id = ? AND last_claim_date < today. 이 쿼리가 1행을 바꿨으면 내가 오늘의 첫 수령자이니 지급하고, 0행이면 누군가(또는 내 첫 클릭이) 이미 받은 거라 지급을 건너뜁니다. DB의 행 단위 원자성이 "먼저 도착한 하나"만 통과시켜 주니, 두 요청이 아무리 붙어 와도 지급은 한 번입니다.

제가 조선협객전에서 쓰던 싱글스레드 액터 큐 구조라면 이야기가 더 깔끔합니다. 한 유저의 요청은 그 유저를 담당하는 큐에서 순차로만 처리되니, 두 '출석 받기'가 동시에 큐에 들어와도 하나가 완전히 끝난 뒤에 다음이 실행됩니다 — 메모리 상태만으로도 중복이 안 나죠. 다만 이때도 메모리와 DB가 크래시로 어긋나는 창은 남으니, 최종 진실은 위의 조건부 UPDATE(멱등한 기록)로 못 박아 둡니다. 큐로 막고, DB로 확정하는 이중 방어입니다.

면접관🔥 "이미 뚫려서 몇 명이 며칠치를 받아갔어요. 사후에 그 사람들을 어떻게 찾아냅니까?"

방어가 아니라 탐지·회수의 영역이군요. 여기서 저를 살리는 건 지급 로그입니다. 지급할 때마다 저는 최소한 세 가지를 남깁니다 — 누가, 서버가 판정한 대상 날짜, 요청이 실제로 도착한 서버 시각. 정상 유저는 이 셋이 나란히 갑니다(오늘 것을 오늘 받음). 어뷰저는 여기서 냄새가 납니다.

구체적 신호는 이렇습니다. (1) 한 유저가 짧은 실제 시각 안에 여러 날짜치를 수령했다(도착 시각은 다 같은 5분인데 대상 날짜는 7일치). (2) 미래 날짜의 보상을 받았다. (3) 수령 간격이 물리적으로 불가능하게 짧다. 이건 로그를 유저별로 묶어 "대상 날짜 분산 대비 실제 도착 시각 분산" 비율만 봐도 대부분 걸립니다.

다만 오탐을 조심합니다. 네트워크 재전송이나 클라 리트라이로 같은 요청이 두 번 로그에 남는 건 어뷰징이 아니라 정상이거든요. 그래서 저는 지급이 실제로 일어난 로그(0행 UPDATE는 제외)만 세고, 요청 단위가 아니라 '실제 재화가 늘어난 건' 기준으로 판정합니다. 그리고 회수는 자동 차감보다 플래그 → 표본 검증 → 일괄 조정 순으로 갑니다. 사후 대응의 목표는 한 명 잡는 게 아니라 구멍을 막고(앞의 조건부 UPDATE) 새는 총량을 되돌리는 것이니까요.
