Q91. 니가 처음부터 MMORPG 서버를 설계한다. 첫 3개월에 뭘 먼저 짜고 뭘 미루나?

1차 답변

0. 저는 먼저 "3개월의 목표"를 좁힙니다

"MMORPG 서버"라도 규모·장르·팀·일정이 다 다릅니다. 그래서 코드 순서를 말하기 전에 되묻습니다 — "이 3개월이 '플레이 가능한 첫 조각'을 보여주는 기간인가요, 아니면 '라이브까지 갈 아키텍처의 뼈대'를 세우는 기간인가요?" 저는 둘을 굳이 안 나눕니다. 제 목표는 "나중에 안 무너질 뼈대 위에서, 캐릭터가 걸어다니고 서로 보이는 한 줄기를 끝까지 관통시키는 것"입니다. 재미와 뼈대를 동시에 증명하는 3개월이요.

1. 순진한 안 — 처음부터 완벽한 분산 아키텍처

순진한 첫 안: 시작부터 존 서버 분리, 마이크로서비스, 메시지 큐, 오토스케일까지 제대로 된 대규모 분산을 다 깐다. 나중에 100만 동접이 와도 끄떡없게.

이러면 3개월을 다 쓰고도 정작 "캐릭터가 걸어다니고 서로 보이는" 것조차 못 보여줍니다. 아직 있지도 않은 규모 문제를 먼저 푸느라 게임을 못 만드는 거죠. MMORPG는 재미가 검증 안 되면 규모는 의미가 없습니다. 조기에 분산부터 깔면 개발 속도가 급락하고 디버깅이 지옥이 되는데, 정작 게임성은 미검증인 최악입니다.

2. 그렇다고 막 짜도 안 된다 — '못 바꾸는 것'의 함정

반대 극단도 위험합니다. 빨리 만들겠다고 나중에 못 바꾸는 결정을 대충 박으면 라이브에서 발목을 잡힙니다. 패킷 직렬화 포맷, 좌표계, 핵심 DB 스키마, 인증 구조 — 이런 건 유저 데이터와 클라 버전이 쌓인 뒤엔 갈아엎기가 거의 불가능합니다. 그래서 제 기준은 딱 하나로 정리됩니다: "나중에 못 바꾸는 것"을 먼저, "규모·기능"은 나중에.

3. 먼저 짤 것 — "못 바꾸는 것"을 제대로

(1) 네트워크 코어 + 패킷 프레이밍/버전. 제 경험상 여기가 심장입니다. IOCP 기반 수신 루프, 패킷 경계 자르기(스트림에서 메시지 잘라내기), 버전이 올라가도 구버전 클라가 안 깨지는 헤더 설계. 이게 나중에 갈아엎기 제일 어렵습니다.

(2) 게임 루프/틱 구조 + 스레드 모델. 한 존 로직을 싱글스레드 액터 큐로 순서대로 처리하는 원칙을 처음에 정합니다. 스레드 모델을 늦게 정하면 나중에 락 지옥이 됩니다.

(3) 서버 권위 원칙. 클라 예측은 허용하되 판정은 서버가 — 이 원칙을 코드 구조에 처음부터 박습니다. 나중에 "클라를 믿던 곳"을 서버 검증으로 바꾸는 건 보안 재설계라 훨씬 비쌉니다.

(4) 영속성 경계. "메모리가 진실, DB는 write-behind로 주기 저장"이라는 저장 시점·복구 원칙만 정합니다. 스키마 최적화(blob vs row, 샤딩)는 미룹니다.

(5) 관측 가능성. 로그·메트릭·틱 시간 측정을 첫 달부터 깝니다. 이게 없으면 나중에 아무 문제도 못 잡습니다.

그리고 이 뼈대 위로 수직 슬라이스 한 줄기를 관통시킵니다 — 접속 → 캐릭 생성 → 필드에서 걷고 서로 보이고(최소 AOI) → 몹 때리고 → 저장 → 재접속. 이 한 줄이 끝까지 돌면 뼈대가 증명된 겁니다.

4. 미룰 것 — "규모/기능"은 나중에 (YAGNI)

존 분할·심리스, 크로스서버, 마이크로서비스, 메시지 큐(Kafka 등), 오토스케일, 매치메이킹, 경매장, 길드 — 전부 미룹니다. 이것들은 "뼈대"가 아니라 "규모"거나 "부가 기능"이라, 재미와 뼈대가 증명된 뒤에 붙여도 늦지 않습니다. 단 미루되 나중에 넣을 자리(경계)는 남겨둡니다 — 예를 들어 한 프로세스로 돌더라도 "존" 개념은 코드상 논리적으로 분리해 둡니다.

5. 트레이드오프 — '제대로'의 범위를 좁혀야 한다

뼈대에 시간을 너무 쓰면 게임성 검증이 늦어집니다. 그래서 저는 "제대로"를 못 바꾸는 것에만 한정합니다. 패킷 버전은 제대로, 하지만 스킬 시스템은 하드코딩해도 됩니다(나중에 데이터화). "나중에 넣게 경계만 남기기"도 과하면 오버엔지니어링이라, 경계는 인터페이스 한 겹 정도지 실제 분산 구현이 아닙니다. 딱 그 선까지입니다.

🧭 이 문제의 원칙"3개월엔 '나중에 못 바꾸는 것'을 제대로 짜고 '규모·기능'은 미룬다." 못 바꾸는 것 = 네트워크·직렬화·스레드 모델·서버 권위·영속성 경계·관측성. 미루는 것 = 분산·확장·부가 콘텐츠. 무엇보다 '캐릭터가 걸어다니고 서로 보이는' 한 줄기를 끝까지 관통시켜, 재미와 뼈대를 동시에 증명한다.

면접관🔥 "분산을 미루라니, 나중에 단일 프로세스를 존 서버로 쪼개려면 결국 다 뜯어고쳐야 하잖아요?"

그래서 처음부터 "존"을 물리 프로세스가 아니라 논리 경계로 나눕니다. 한 프로세스 안이라도 존과 존 사이 통신을 메서드 직접 호출이 아니라 메시지 전달로 짜둡니다. 그러면 나중에 존을 다른 프로세스·다른 장비로 뺄 때, 그 메시지 경로를 네트워크로 바꾸기만 하면 됩니다. 로직은 안 건드리고요.

물리 분산은 미루되 통신 모델은 처음부터 메시지 기반 — 이게 "경계만 남긴다"의 실체입니다. 단 정직하게 말하면 이게 공짜는 아닙니다. 진짜 원격 호출이 되는 순간 지연·부분 실패·순서 문제가 새로 생기고, 그건 그때 제대로 다뤄야 합니다. 제가 남기는 건 "쉽게 쪼갤 수 있는 이음매"지 "분산이 이미 다 된 상태"가 아닙니다. 이 둘을 혼동하면 또 오버엔지니어링으로 3개월을 태웁니다.

면접관🔥 "DB 스키마를 유연하게 미루라면서, 나중에 스키마 바꾸면 마이그레이션 지옥 아닌가요?"

미루는 건 "최적화"지 "핵심 엔터티 구조"가 아닙니다. 계정·캐릭터·인벤·재화처럼 안 바뀔 핵심 구조는 첫 달에 신중히 정합니다. 여기가 흔들리면 진짜 지옥이 맞으니까요. 반면 미루는 건 blob이냐 row냐, 샤딩, 인덱스 튜닝 같은 성능 결정입니다 — 이건 데이터가 실제로 쌓이고 병목이 보인 뒤에 정하는 게 맞습니다.

그리고 라이브 전이라 데이터가 테스트뿐이면 스키마 변경이 오히려 자유롭습니다. 대신 마이그레이션 도구와 스키마 버전 관리는 첫 달에 세팅합니다 — 나중에 반드시 필요하고, 늦게 도입하면 그게 지옥이거든요. 정리하면 "구조는 신중히, 최적화는 나중에, 변경 수단은 처음부터"입니다.

면접관🔥 "3개월 목표가 재미 검증이라면, 서버를 제대로 짜는 것 자체가 낭비 아닌가요? 클라만으로 목업하지."

절반은 동의합니다. 순수한 전투 손맛 같은 건 클라 목업이나 싱글플레이로 먼저 볼 수 있습니다. 하지만 MMORPG 재미의 상당 부분이 "남이 옆에 있음"에서 나옵니다 — "둘이 접속해 서로 보이고 상호작용한다"는 서버 없이는 검증이 불가능합니다.

그래서 저는 서버를 "제대로"가 아니라 "얇게 관통"으로 짭니다. 못 바꿀 뼈대 축(네트워크·권위·틱)만 신경 쓰고 나머지는 최소한으로요. 낭비를 피하는 건 '서버를 안 짜기'가 아니라 '얇게 짜되 뼈대 축은 안 틀리기'입니다. 두껍게 짜서 낭비하는 것도, 축을 틀려서 나중에 다 뜯는 것도 둘 다 피하는 게 이 3개월의 진짜 기술이라고 봅니다. "클라만 목업하자"는 처음엔 빠르지만, 결국 서버를 급하게 짜다 뼈대 축을 틀리는 함정이 있어요.
