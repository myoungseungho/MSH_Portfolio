Q39. 클라가 조작한 패킷("순간이동", "데미지 9999")을 어떻게 막나?

1차 답변

0. 저는 먼저 "무엇을 막는 건지" 두 층으로 나눕니다

이 질문의 함정은 "조작"이 두 종류라는 겁니다. 저는 이걸 먼저 갈라놓습니다.

(가) 위조·변조 — 전송 중 바이트를 바꾼 것. 중간에서 패킷을 뜯어고치거나 없던 요청을 끼워넣는 것. 이건 암호화·서명·리플레이 방어로 어느 정도 막습니다.

(나) 형식은 완벽히 정상인데 내용이 불가능한 것. 해커는 대개 정품 클라의 메모리를 조작해 규칙상 유효해 보이는 패킷을 보냅니다. "데미지 9999", "좌표 (999,999)로 이동함" — 문법은 멀쩡해요. 암호화는 이걸 절대 못 막습니다. 오히려 조작된 클라가 정상 키로 곱게 암호화해서 보내니까요.

진짜 무서운 건 (나)입니다. 그래서 이 질문의 답은 암호화가 아니라 서버 권위(server authority)예요.

1. 순진한 첫 안 — 패킷을 암호화하면 조작 못 하겠지

순진한 기대: 패킷을 암호화해서 보내면 클라가 못 뜯어고칠 테니 조작도 막힌다. "보안 = 암호화"라고 믿는다.

이건 오답입니다. 암호화 키는 결국 클라 안에 있고(Q78), 조작 툴은 암호화 이전 단계, 즉 게임 메모리에서 값을 바꿉니다. 그러면 "데미지 9999"가 정상 키로 암호화돼 서버에 도착합니다. 서버가 그걸 그대로 믿으면 끝이에요. 암호화는 (가)를 막을 뿐 (나)엔 무력합니다.

2. 진짜 원리 — 클라가 보내는 건 '결과'가 아니라 '의도'다

핵심 한 줄입니다. 클라는 "무엇을 하려는지(입력·의도)"만 보내고, "무슨 일이 일어났는지(결과)"는 서버가 만든다.

"데미지 9999"라는 패킷이 문제가 된다는 것 자체가 설계가 틀렸다는 신호입니다. 데미지는 클라가 보내는 값이 아니어야 해요. 클라는 스킬3을 몹A에게 씀만 보내고, 데미지는 서버가 자기 스탯·버프·방어력으로 계산합니다. 그러면 "데미지 9999" 패킷은 프로토콜에 존재하지도 않습니다. 막을 필요 없이 애초에 받을 수 없게 만드는 거죠.

3. 그럼 순간이동은? — 위치는 받되 서버가 검증한다

이동은 사정이 조금 다릅니다. 반응성 때문에 클라가 위치를 "주장"하긴 합니다. 그래서 받되, 믿지 않고 검증합니다. 직전 위치와 이번 위치, 그 사이 경과 시간을 보고 "이 Δt 동안 물리적으로 가능한 최대 이동 거리"를 넘었는지 봅니다.

// 서버가 매 이동 패킷마다 dist = distance(prev_pos, claimed_pos); maxDist = maxSpeed * dt * TOLERANCE; // 여유 계수 if (dist > maxDist) { reject_or_snapback(player); // 순간이동은 여기서 걸림 }

순간이동은 "한 틱에 맵 절반을 이동"이라 이 검사에서 바로 걸립니다. 걸리면 요청을 버리거나 직전 위치로 스냅백합니다. 스피드핵도 같은 원리로 걸러지는데, 랙과의 구분은 별도 문제라 Q77에서 따로 다룹니다.

4. 층을 더 쌓는다 — 상태·불변식 검증

서버는 자기가 쥔 상태로 계속 되묻습니다. 쿨타임이 안 지났는데 스킬을 또 쓴다? 인벤에 없는 아이템을 쓴다? 사거리 밖의 몹을 때린다? 마나가 부족한데 시전한다? 전부 서버가 자기 상태로 판정해 거부합니다. 여기에 불변식(invariant)을 겁니다 — 골드는 음수가 될 수 없고, 인벤 슬롯은 상한을 못 넘고, 스탯은 정해진 범위 안에 있어야 합니다. 클라가 뭘 보내든 이 불변식을 깰 수 없게 서버 쪽에서 잠급니다.

5. 정직한 한계 — 완벽 방어는 없다

여기서 저는 솔직해집니다. 모든 조작을 실시간으로 막는 건 불가능합니다. 특히 "정상 범위 안에서의 미세한 이득"(살짝 빠른 반응, 통계적으로 유리한 판정)은 완벽히 걸러내기 어렵습니다. 그래서 목표를 "불가능하게"에서 "이득 없게 · 잡히게 · 되돌리게"로 바꿉니다. 실시간 차단이 못 잡는 건 로그와 사후 탐지가 잡습니다. 이상 행동을 로깅하고, 통계로 잡아내고, 롤백·제재로 이득을 회수하는 것 — 이게 실시간 검증만큼 중요합니다.

🧭 이 문제의 원칙"클라가 보내는 건 결과가 아니라 의도다. 결과는 서버가 만든다." 조작을 못 막는 게 아니라, 조작해봐야 서버가 안 믿게 설계한다. 그리고 완벽히 못 막으니 이득 없고·잡히고·되돌릴 수 있게 만든다. 암호화는 이 게임의 주인공이 아니다.

면접관 꼬리질문
면접관🔥 "이동도 서버가 다 계산하면 순간이동이 원천봉쇄되잖아요. 왜 굳이 클라 위치를 받아요?"

정답에 가까운 안을 던지시고 그 대가를 물으시네요. 이유는 반응성입니다.

MMORPG에서 이동을 완전히 서버 권위로만 하면, 유저가 방향키를 누른 뒤 서버 왕복(수십~수백 ms)이 끝나야 캐릭터가 움직입니다. 이 지연은 조작을 막는 대신 게임을 못 하게 만듭니다. 그래서 실무는 클라 예측(client-side prediction)을 씁니다 — 입력 즉시 클라가 먼저 움직여 보이고, 서버엔 "나 여기로 갔다"를 알립니다. 서버는 그걸 사후에 검증하고, 어긋나면 정정(보정·스냅백)합니다.

즉 "클라 위치를 받는다"는 건 클라를 믿어서가 아니라, 반응성을 위해 클라가 먼저 움직이게 허락하되 서버가 뒤에서 감시하는 구조입니다. 순간이동은 이 사후 검증에서 걸립니다. 완전 서버 권위 이동은 조작엔 강하지만 조작 방어의 대가로 플레이 감각을 죽이는 거라, 이동에선 예측+검증이 현실적 최적해예요(Q45에서 더 깊이 다룹니다).

면접관🔥 "데미지를 서버가 계산해도, 클라가 '몹이 죽었다' 패킷을 위조해 보내면요?"

이건 "결과 vs 의도"를 한 겹 더 밀어붙이는 질문이네요. 답은 같은 원리의 확장입니다. '몹이 죽었다'는 애초에 클라가 보낼 수 있는 패킷이 아니어야 합니다.

몹의 HP도, 사망 판정도 서버가 소유합니다. 클라는 몹A를 때렸다(스킬 시전 의도)만 보내고, 서버가 데미지를 계산해 HP를 깎고, HP가 0이 되면 서버가 "몹A 사망"을 판정해 클라들에게 통보합니다. '몹 사망'은 클라 → 서버 방향으로는 존재하지 않고, 서버 → 클라 방향으로만 흐릅니다. 그러니 위조할 패킷 자체가 없어요.

여기서 핵심 개념이 소유권(authority)의 경계입니다. "누가 이 객체의 상태를 결정하는가"를 명확히 그어야 합니다. 클라는 몹이 보이지만 몹을 소유하지 않습니다. "보인다 ≠ 소유한다" — 이 경계가 흐려지면 조작이 비집고 들어옵니다(Q30에서 존 경계 너머 판정으로 이어집니다). 결국 방어의 8할은 실시간 검사가 아니라 애초에 클라에게 권한을 안 주는 프로토콜 설계입니다.

면접관🔥 "검증을 그렇게 다 넣으면 CPU가 폭발한다면서요. 그럼 어디는 포기해요?"

맞습니다. 모든 패킷을 다 의심하면 서버가 검증에 짓눌립니다(Q80과 이어집니다). 그래서 저는 위험도 매트릭스로 검증 예산을 배분합니다. 기준은 두 축이에요 — 되돌릴 수 있나, 그리고 이득이 큰가.

되돌리기 어렵고 이득이 큰 것(재화·아이템·거래)은 무조건 실시간 풀 검증 + 원자성 + 로그. 여긴 한 번 뚫리면 경제가 무너지니 CPU를 아끼지 않습니다. 되돌릴 수 있고 이득이 작은 것(이동 미세 조작 같은)은 매 패킷 정밀 검증 대신 샘플링·통계 탐지로 돌리고, 실시간에 놓친 건 사후 로그로 잡습니다. 이득이 없는 것(이모트·시각 효과)은 그냥 신뢰합니다.

중요한 건 검증을 "실시간 차단"과 "사후 탐지"라는 두 예산으로 나눈다는 겁니다. 실시간에서 다 막으려 하면 CPU가 죽고, 그렇다고 다 사후로 미루면 실시간 피해가 커집니다. 그래서 "지금 막지 않으면 되돌릴 수 없는 것"만 실시간에 두고, 나머지는 로그로 흘려 배치로 잡습니다. 검증은 총량이 아니라 배분의 문제예요.
