Q21. 실시간 랭킹(100만 유저 점수, 초 단위 갱신)을 어떻게 보여주나?

1차 답변

0. "유저가 실제로 보는 게 뭔지"부터 좁힙니다

저는 "100만 명 실시간 정렬"이라는 무서운 그림을 바로 안 받습니다. 유저가 랭킹 화면에서 실제로 보는 게 뭔가부터 쪼갭니다. 대부분은 상위 Top 100 + 내 순위 + 내 주변 몇 명이지, 100만 명의 완전한 순서표가 아닙니다. 100만 등부터 99만 등까지의 정확한 순서를 궁금해하는 사람은 없어요.

그리고 "초 단위 갱신"도 나눠 봅니다. 점수는 초마다 바뀌어도, 순위 표시가 초마다 절대 정확해야 하나는 별개입니다. 대개 몇 초 지연된 근사 순위로 충분하죠. 그래서 저는 요구를 "보여줘야 할 것 = Top N + 내 순위", "정확도 = 근사 허용"으로 좁힙니다. 이렇게 좁히면 자료구조 하나로 끝나고, "전부 실시간 정확"을 고집하면 비용이 폭발합니다.

1. 순진하게 가면

순진한 안: 점수 바뀔 때마다 DB에 UPDATE, 랭킹 볼 땐 ORDER BY score DESC LIMIT 100. 내 순위는 COUNT(*) WHERE score > 내 점수.

Top 100은 인덱스가 있으면 그럭저럭 나옵니다. 문제는 규모와 갱신 빈도예요.

2. 어디서 터지나 — DB는 이 일에 안 맞는다

초당 대량 UPDATE가 인덱스를 계속 흔들어 쓰기 부하가 폭발합니다. 100만 명 점수가 쉼 없이 바뀌면 정렬 인덱스가 쉴 틈이 없어요. 더 나쁜 건 "내 순위"입니다. COUNT(*) WHERE score > 내 점수는 최악의 경우 100만 건을 세는 쿼리라, 유저마다 이걸 실시간으로 물어보면 DB가 버티질 못합니다. 관계형 DB는 "정렬된 집합에서 특정 원소의 순위"를 싸게 주도록 만들어지지 않았거든요.

3. 개선 — 이 문제를 위한 자료구조를 씁니다

정확히 이걸 위해 있는 물건이 정렬 집합(Sorted Set, 예: Redis ZSET)입니다. 점수와 함께 원소를 넣으면 내부적으로 정렬을 유지해서:

• 점수 갱신(ZADD)이 O(log N) — 100만이어도 로그 타임
• Top N 조회(ZRANGE)가 앞에서부터 N개 훑기
• 내 순위(ZRANK)도 O(log N) — DB의 100만 COUNT가 로그 타임 한 방으로 바뀜

그래서 갱신과 조회는 메모리의 정렬 집합에서 처리하고, DB는 영속화용 백업만 맡깁니다(주기적으로 스냅샷). "내 순위"라는 제일 아픈 연산이 값싸지는 게 핵심입니다. 게임 서버가 이미 메모리에 상태를 들고 있듯, 랭킹도 메모리 자료구조가 진실을 쥐고 DB는 뒤를 받치는 구조로 갑니다.

4. 트레이드오프 — 정렬 집합도 공짜는 아니다

정렬 집합 한 대도 초당 수십만 갱신이 몰리면 한계가 옵니다(Redis는 단일 스레드라 더 그렇죠). 그리고 100만 명 절대 순위를 매 순간 정확히 유지하는 건 여전히 비쌉니다. 그래서 요구를 다시 근사로 눕힙니다 — Top N만 정확히, 하위권은 티어/상위 몇 %로 근사하거나, 순위 스냅샷을 N초마다 갱신해 "초 단위 절대 정확"을 포기합니다. 유저 체감엔 차이가 없고 비용은 확 떨어집니다.

🧭 이 문제의 원칙"'실시간 랭킹'에서 실시간이어야 하는 건 Top N과 내 점수지, 100만 명의 절대 순위가 아니다." 요구를 '보여줘야 할 것'으로 좁히면 정렬 집합 하나로 끝나고, '전부 실시간 정확'을 고집하면 비용이 폭발한다. 랭킹은 정밀 계산이 아니라 표시(display) 문제다.

면접관 꼬리질문
면접관🔥 "정렬 집합 한 대가 초당 수십만 갱신을 감당 못 하면요? 단일 스레드라면서요."

맞습니다. 정렬 집합이 로그 타임이어도 초당 갱신 횟수 자체가 한 노드의 처리량을 넘으면 소용없죠. 저는 먼저 갱신 횟수를 줄이는 방향부터 봅니다 — 대개 이게 근본 해법이거든요.

(1) 쓰기 병합(coalescing). 한 유저 점수가 1초에 50번 바뀌어도 랭킹에 필요한 건 마지막 값 하나입니다. 게임 서버 메모리에서 유저별 최신 점수만 들고 있다가, 주기적으로 바뀐 유저만 모아 배치로 정렬 집합에 반영합니다. 초당 수십만 갱신이 "바뀐 유저 수만큼의 배치 반영"으로 줄어요. 대부분의 폭주는 이걸로 사라집니다.

(2) 그래도 넘치면 샤딩. 정렬 집합을 여러 대로 쪼갭니다. 다만 여기서 정직해야 하는데 — 쪼개면 "전역 순위"가 곧바로 어려워집니다. 각 샤드의 Top N을 모아 합쳐 전체 Top N을 만드는 건 되지만(부분 정렬 병합), 특정 유저의 정확한 전역 순위는 모든 샤드에 물어봐야 나옵니다. 그래서 이땐 전역 순위를 근사로 바꿉니다 — 각 샤드의 분포로 "대략 상위 몇 %"를 추정하거나, 점수 구간별 인원 카운트(버킷)로 근사 순위를 냅니다. 요컨대 병합으로 대부분을 흡수하고, 그래도 넘치면 샤딩하되 전역 정확도를 근사와 맞바꾼다는 겁니다.

면접관🔥 "내 순위를 정확히 보여줬더니, 새로고침하니 3초 만에 500등이 바뀌었어요. 유저가 '버그냐'고 항의하는데요?"

이건 성능이 아니라 UX의 역설입니다. 100만 명이 초 단위로 경쟁하면 순위는 원래 미친 듯이 출렁이는 게 정상이에요. 정확할수록 더 출렁이죠. 즉 "정확한 실시간 순위"는 기술적으로 맞아도 유저에겐 불안한 숫자입니다. 그래서 저는 여기서 정확도를 낮추는 게 오히려 옳다고 봅니다.

세 가지로 다듬습니다. (1) 순위 갱신 주기를 고정 — 실시간이 아니라 "N초마다 갱신"으로 못 박아, 볼 때마다 숫자가 튀지 않게 합니다. 유저는 안정된 값을 보고, 서버는 조회 부하도 덜죠. (2) 근사 표기 — "1,204위"처럼 딱 떨어지는 대신 "상위 3%", "약 1,200위", "브론즈 티어"처럼 표시하면 미세 변동이 안 보입니다. (3) 절대 순위 대신 상대 지표 — 다음 티어까지 몇 점, 어제보다 몇 계단처럼 유저가 통제감을 느끼는 지표로 바꿉니다.

핵심은, 랭킹 화면의 목적은 "정확한 등수 고지"가 아니라 "동기 부여"라는 겁니다. 그 목적에 맞추면 근사가 오히려 정답이에요. 정확한 순위가 필요한 유일한 순간은 보상 정산인데, 그건 실시간 표시와 분리된 별도 문제입니다 — 다음 질문이 정확히 그거네요.

면접관🔥 "시즌 종료 순간의 최종 순위로 보상을 줘야 해요. 점수가 초 단위로 바뀌는데 '마감 시점'을 어떻게 딱 고정하죠? 동점자는요?"

여기서는 근사가 안 통합니다. 보상이 걸리면 단 하나의 확정된 순위가 필요하니까요. 그래서 표시용 파이프라인과 정산용 파이프라인을 분리합니다.

마감 시점 고정은 두 방법입니다. 하나는 마감 시각에 점수 쓰기를 잠깐 막고(freeze) 스냅샷을 떠서 그걸 최종본으로 확정하는 것. 다른 하나는, 점수 변화를 처음부터 append-only 로그(타임스탬프 포함)로 남겨두고 마감 후 "마감 타임스탬프 이하만"으로 최종 점수를 재구성하는 것입니다. 후자는 서비스를 안 멈춰도 되고, 나중에 이의 제기가 와도 로그로 재검증할 수 있어 더 견고합니다.

동점 처리(tie-break)는 규칙을 미리 정해 결정론적으로 만듭니다. 흔한 건 "같은 점수면 먼저 도달한 사람이 위" — 이건 정렬 집합의 점수에 시간을 함께 인코딩하면 깔끔합니다. 예를 들어 점수를 상위 비트, "마감까지 남은 시간"을 하위 비트에 넣으면, 같은 점수 안에서 먼저 달성한 사람이 자동으로 앞섭니다. 그래도 완전히 같으면 유저 ID 같은 안정적 기준으로 마지막 tie-break를 두고요. 마지막으로 보상 지급은 랭킹 조회와 또 분리된 배치로, 멱등하게 처리합니다 — 정산이 중간에 끊겨도 다시 돌리면 같은 결과가 나오게. 이렇게 표시(근사·실시간)와 정산(정확·확정·멱등)을 서로 다른 세계로 다루는 게 핵심입니다.
