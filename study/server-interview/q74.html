Q74. 로그인 서버 - 게이트 - 게임 서버로 나눌 때 세션을 어디서 관리하나?

1차 답변

0. 저는 먼저 "세션이 하나가 아니다"부터 말합니다

이 질문에 "게임 서버요" 또는 "게이트요"라고 한 곳을 딱 찍는 순간 저는 이미 틀렸다고 봅니다. 왜냐하면 "세션"이라는 단어가 최소 세 가지를 뭉뚱그리고 있기 때문이에요. 먼저 이걸 쪼갭니다.

(1) 인증 세션 — "이 연결이 정당하게 로그인한 사람인가." (2) 연결 세션 — "이 TCP 소켓이 지금 누구와 붙어 있고 어디로 패킷을 보내야 하나." (3) 게임 세션(플레이 상태) — "이 캐릭터가 지금 어느 존에서 HP 얼마로 뭘 하고 있나." 이 셋은 성격도 수명도 다르니, 사는 집도 달라야 합니다.

세 서버의 역할부터 짧게 정리하면 — 로그인 서버는 계정·비번을 검증하고 토큰을 발급하고 빠집니다. 게이트 서버는 클라의 TCP 소켓이 실제로 꽂히는 종착점이고, 받은 패킷을 뒤의 게임 서버로 라우팅합니다(방화벽 겸 완충). 게임 서버(월드)는 실제 게임 로직·존·전투를 돌립니다.

1. 제일 순진한 안 — 게임 서버가 다 들고 있는다

순진한 안: "게임 서버가 소켓도 물고 세션도 상태도 다 관리하죠. 로그인 서버는 인증만 하고 넘기고요. 한 곳에 있으니 단순하잖아요."

단순함은 맞지만 세 군데서 깨집니다. 첫째, 게임 서버가 클라 소켓을 직접 물면 존을 넘거나 서버를 옮길 때마다 TCP를 새로 맺어야 하고, 게임 서버 하나가 죽으면 거기 붙은 연결이 다 끊깁니다. 게다가 외부 스캔·DDoS가 게임 서버에 직접 닿아요.

둘째, 세션 정보가 각 게임 서버에만 흩어져 있으면 "이 계정 지금 어디 접속했나?"를 알려면 모든 게임 서버를 다 뒤져야 합니다. 셋째, 중복 로그인을 막을 심판이 없어요 — 서로 다른 게임 서버에 같은 계정이 둘 붙어도 서로를 모릅니다.

2. 개선 — 층마다 자기 관심사만 소유한다

그래서 저는 세션을 한 곳에 몰지 않고 층마다 나눠 소유시킵니다.

인증 세션은 토큰으로. 로그인 서버가 검증 후 토큰을 발급하면, 이후엔 그 토큰만으로 stateless하게 통과시킵니다. 게이트가 입장 때 한 번 검증하면 돼요.

연결 세션은 게이트가 소유. 클라 소켓은 오직 게이트하고만 붙습니다. 게이트가 "이 소켓 = 이 유저 = 지금 이 게임 서버로 라우팅" 매핑을 들고 있어서, 존·서버 이동은 게이트 뒤에서 라우팅 대상만 바꾸면 되고 클라의 TCP는 안 끊깁니다.

게임 세션(플레이 상태)은 게임 서버가 소유(권위). 캐릭터 액터는 게임 서버 메모리에 삽니다. 이건 초당 수십 번 바뀌는 실시간 상태라 딴 데로 뺄 수가 없어요.

전역 접속 상태는 공유 레지스트리에. "이 계정이 지금 온라인인가, 어느 게이트/게임 서버에 있나"는 전역 세션 레지스트리(예: Redis)에 한 줄로 둡니다. 이게 계정 유일성의 심판이 됩니다.

3. 트레이드오프

이렇게 나누면 대가가 있습니다. 게이트라는 홉이 하나 늘어 지연이 아주 살짝 붙고, 게이트도 확장·장애 관리 대상이 됩니다. 전역 레지스트리는 단일 진실이라 편하지만, 그게 죽으면 로그인·중복체크가 마비되는 단일 장애점이 될 수 있어요. 그래서 레지스트리는 이중화하고, 저장하는 건 "얇은 정보(누가 어디 있나)"로 한정합니다.

4. 상황별 최적해

소규모·단일 서버라면 게이트를 생략하고 게임 서버가 겸해도 됩니다 — 층 나누는 게 오히려 오버예요. 중대형·다중 존이면 게이트와 게임 서버를 분리하고 전역 레지스트리를 둡니다. 글로벌 서비스면 게이트를 리전별로 두고, 계정 세션은 전역, 캐릭터 세션은 리전 로컬로 계층을 한 겹 더 나눕니다.

🧭 이 문제의 원칙"세션을 '어디에 두나'가 아니라 '어떤 세션이냐'로 쪼개라." 인증은 로그인 서버, 연결은 게이트, 플레이 상태는 게임 서버, 유일성은 전역 레지스트리. 한 곳에 다 몰면 바로 그 곳이 단일 장애점이 된다. 각 층은 자기 관심사만 소유한다.

중복 로그인 방지의 심판이 누구냐가 핵심이죠. 여기서 저는 아까 나눈 구조가 왜 필요했는지를 보여줍니다. 만약 게이트마다 따로 판단하면, 서로 다른 게이트에 붙은 두 접속은 상대를 몰라서 둘 다 통과합니다. 각 게임 서버가 판단해도 마찬가지고요. 그래서 심판은 반드시 전역 세션 레지스트리 한 곳이어야 합니다.

그리고 이건 원자적이어야 해요. 두 접속이 거의 동시에 "나 로그인할게"를 던지면, 레지스트리에서 set-if-absent 같은 원자 연산 하나로 승부를 냅니다 — 먼저 자리를 잡은 쪽만 통과하고, 진 쪽은 거부됩니다. 이 원자성이 없으면 둘 다 "비어있네" 하고 통과하는 레이스가 터져요. 재화 중복 지급이나 아이템 복사와 같은 계열의 문제입니다.

둘 다 통과시킨 뒤 하나를 고르는 게 아니라 애초에 하나만 통과시키는 겁니다. 그다음은 정책 선택이에요 — 뒤에 온 접속이 앞 세션을 킥(중복 로그인 시 이전 접속 강제 종료)하거나, 앞을 유지하고 뒤를 거부하거나. 저는 보통 계정 도용 대응이 쉬운 "뒤가 앞을 킥" 쪽을 기본으로 두되, 결제·거래 중이면 함부로 못 끊게 예외를 둡니다.

면접관🔥 "게이트 서버 한 대가 죽으면 거기 붙은 유저 수천 명이 다 튕기잖아요. 그게 게임 서버가 죽는 거랑 뭐가 나아요?"

정직하게 인정부터 하겠습니다. 게이트가 죽으면 거기 붙은 연결은 끊깁니다. 맞습니다. 게이트를 둔다고 장애가 사라지진 않아요. 하지만 저는 "게이트가 죽는 것"이 "게임 서버가 죽는 것"보다 세 가지 면에서 잃는 게 적다고 봅니다.

첫째, 게임 상태는 게임 서버에 살아있습니다. 게이트가 죽어도 캐릭터는 게임 서버 메모리에 그대로라, 유저가 다른 게이트로 재접속하면 세션 유예로 하던 걸 이어갑니다 — 연결만 다시 맺으면 돼요. 게임 서버가 죽으면 캐릭터 자체가 날아가는 것과는 급이 다릅니다.

둘째, 게이트는 로직이 얇습니다. 라우팅과 소켓 관리만 하니 게임 서버보다 훨씬 덜 죽고, 죽어도 상태가 가벼워 재시작이 빠릅니다. 셋째, 폭발 반경을 나눌 수 있어요 — 게이트를 여러 대 두고 유저를 분산시키면 한 대가 죽어도 전체가 아니라 일부만 영향받습니다. 게다가 게이트가 앞에서 외부 트래픽을 받아주니, 게임 서버가 스캔·DDoS·비정상 패킷에 직접 노출되지 않는다는 이득은 덤이고요. 그래서 "장애를 없앤다"가 아니라 "장애가 났을 때 잃는 것을 줄인다"가 게이트의 값어치입니다.

면접관🔥 "요즘 클라우드처럼 세션을 전부 Redis에 넣고 게임 서버를 stateless로 만들면 안 돼요?"

웹 서버라면 훌륭한 답이지만, 게임 서버는 그게 본질적으로 안 됩니다. 여기서 웹과 게임의 결정적 차이가 드러나요. 웹 세션은 요청과 요청 사이에 잠깐 꺼내 쓰는 얇고 가끔 바뀌는 상태라 Redis 왕복이 감당됩니다. 반면 게임 세션은 위치·전투가 초당 수십 번 바뀌는 두껍고 실시간인 상태예요.

이걸 매 틱 Redis로 넣고 빼면 네트워크 왕복 지연과 부하가 폭발합니다. 초당 수십 번 × 수천 명이면 Redis가 먼저 죽어요. 그래서 게임 서버가 캐릭터를 메모리에 들고 도는 stateful인 건 게으름이 아니라 필연입니다 — 이게 게임 서버를 웹처럼 마음대로 오토스케일 못 하는 이유이기도 하고요.

그래서 저는 "얇은 세션은 외부화, 두꺼운 세션은 게임 서버 메모리"로 선을 긋습니다. 인증·라우팅·계정 유일성 같은 가끔 바뀌고 공유돼야 하는 것만 Redis로 빼고, 위치·전투처럼 초고빈도로 바뀌는 건 게임 서버가 소유합니다. 핵심은 "무엇을 stateless로 뺄 수 있고 무엇은 절대 못 빼는가"를 구분하는 거예요. 다 빼려다 실시간성을 잃으면 게임이 게임이 아니게 됩니다.
