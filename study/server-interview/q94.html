Q94. 메시지 큐(Kafka 등)를 게임 서버에 넣을까? 어디에 쓰고 어디엔 안 쓰나?

1차 답변

0. 저는 먼저 "게임 루프 안이냐, 게임 밖 주변부냐"를 가릅니다

"게임 서버에 메시지 큐를 넣을까"는 사실 너무 뭉뚱그린 질문이라, 저는 큐를 정확히 어디에 끼우려는지부터 좁힙니다. 잠깐, 먼저 용어를 정리하면 — 메시지 큐는 보낸 쪽과 받는 쪽 사이에 끼는 "중간 우체통"입니다. A가 큐에 메시지를 넣고 가면, B가 자기 속도로 꺼내 처리합니다. 서로 직접 안 붙어도 되고(느슨한 결합), 못 받으면 큐에 남으니 유실이 줄죠. Kafka는 그중 대용량·재처리에 강한 대표 도구입니다.

문제는 이걸 어디에 끼우느냐입니다. 실시간 게임 루프 안(전투·이동·시야 판정)인가, 아니면 게임 밖 주변부(로그, 지급, 서버 간 이벤트, 통계)인가. 이 둘은 답이 정반대입니다.

1. 순진한 안 — 서버 간 통신을 전부 큐로

제일 먼저 떠오르는 안: Kafka 좋다던데, 서버 사이 통신을 다 큐로 통일하자. 느슨하게 결합되고, 유실 없고, 재처리 되고, 확장도 쉽다. 전투 이벤트든 뭐든 다 큐에 흘려보내자.

"다 큐로"가 이 안의 함정입니다. 큐를 게임 틱 안에 끼우는 순간 게임이 렉으로 죽습니다.

2. 어디서 터지나 — 큐의 밀리초가 틱의 마이크로초를 잡아먹는다

게임 실시간 루프는 시간 단위가 마이크로초입니다. 같은 서버 안에서 A가 B를 때리는 전투 판정은 인프로세스 함수 호출이나 액터 큐로 처리돼, 사실상 공짜에 가깝습니다. 제가 조선협객전에서 쓴 싱글스레드 액터 큐가 딱 이겁니다 — 메모리 안에서 순식간에.

그런데 Kafka 같은 브로커를 거치면 한 번 왕복에 수 밀리초에서 수십 밀리초가 듭니다. 네트워크를 타고 브로커에 갔다가, 디스크에 안전하게 쓰고, 복제하고, 컨슈머가 폴링해서 꺼내오는 과정이 있으니까요. 30fps 서버의 한 틱 예산이 33ms인데, 전투 한 방을 Kafka로 돌리면 그 예산을 통째로 날립니다. 게다가 Kafka는 파티션을 넘으면 순서 보장도 깨져서, "먼저 때린 게 먼저 맞는다"는 전투의 인과가 뒤엉킵니다. 처리량엔 강하지만 개별 지연과 순서 보장은 게임 루프가 원하는 특성이 전혀 아닙니다.

3. 개선 — 경계로 나눈다: 루프 안은 절대 X, 주변부는 O

그래서 저는 큐를 딱 잘라 나눕니다.

실시간 게임 루프 안(전투·이동·AOI): 절대 큐 안 씁니다. 인프로세스, 싱글스레드 액터 큐로. 여기선 마이크로초가 왕입니다.

게임 밖 비동기 주변부: 큐가 진가를 발휘합니다. 로그·지표 수집(초당 수백만 건, 조금 유실돼도 됨), 결제·지급 이벤트(멱등키 붙여 재처리), 서버 간 비실시간 이벤트(길드 생성 통보, 우편 발송 알림), 데이터 파이프라인(분석·BI로 흘려보내기). 이런 건 몇 백 ms 늦어도 게임이 안 깨지고, 오히려 유실 방지와 재처리가 큰 이득입니다.

4. 그런데 트레이드오프 — 큐는 운영 복잡도를 폭발시킨다

큐가 공짜는 아닙니다. Kafka를 넣는 순간 브로커 클러스터 운영, 파티션 설계, 컨슈머 랙 모니터링, 순서·중복 처리가 통째로 따라옵니다. 작은 팀에겐 Kafka를 안정적으로 굴리는 것 자체가 하나의 프로젝트예요. 그래서 "큐가 필요하다 = Kafka다"가 아닙니다. 규모가 작으면 DB 테이블 기반 아웃박스 큐(지급 의도를 테이블에 INSERT하고 워커가 폴링)나 Redis Stream 같은 가벼운 도구로 충분한 경우가 많습니다. 도구의 무게를 규모에 맞춰야 합니다.

5. 상황별 최적해

초당 수백만 로그·지표: Kafka가 진가. 대량 처리량과 여러 소비자 팬아웃에 최적.
지급·정산 같은 신뢰성 이벤트: 큐 + 멱등키 + 아웃박스. 유실 없이, 중복 없이.
같은 프로세스 내 실시간 판정: 인프로세스 액터 큐. Kafka는 절대 아님.
소규모 팀·단일 서버: 아예 도입 보류. DB나 인메모리 큐로 시작하고, 규모가 비용을 정당화할 때 도입.

🧭 이 문제의 원칙"메시지 큐는 서버와 서버 '사이'의 도구지, 게임 틱 '안'의 도구가 아니다." 실시간 루프엔 마이크로초가, 큐엔 밀리초가 산다. 대량·유실허용·재처리가 필요한 주변부에 쓰고, 실시간 인과가 걸린 루프 안엔 절대 끼우지 마라.

면접관🔥 "그럼 서버 간 실시간은요? 존 경계를 넘어서 전투가 벌어지면 서버끼리 실시간으로 통신해야 하는데, 그것도 큐 못 써요?"

정확한 지점입니다. "인프로세스는 액터 큐, 그럼 서버 간은?"이라는 빈틈을 찌르셨어요. 답은 서버 간이라도 '실시간이냐 신뢰성이냐'로 다시 갈린다입니다. 서버 간이라고 무조건 Kafka가 아니에요.

존 경계를 넘는 실시간 전투는 Kafka 같은 범용 브로커가 아니라 서버 사이 직접 TCP/RPC 연결(전용 저지연 채널)로 갑니다. 왜냐면 Kafka는 durability(디스크에 안전하게 쓰고 복제)를 위해 일부러 지연을 감수하는 도구인데, 존 경계 전투에서 중요한 건 durability가 아니라 지연이거든요. 옆 존 몹을 때린 판정이 디스크에 영원히 남을 필요는 없습니다. 그저 몇 ms 안에 옆 서버에 도착하기만 하면 됩니다.

그래서 제 기준은 이렇습니다 — 서버 간이라도 실시간이면 직접 연결, 신뢰성 있는 비실시간이면 큐. 존 경계 전투 = 직접 RPC. 길드 생성이나 우편 도착 통보처럼 "몇 백 ms 늦어도 되지만 절대 유실되면 안 되는" 건 = 큐. 같은 "서버 간 통신"이라도 지연 민감도가 도구를 가릅니다.

면접관🔥 "Kafka 넣으면 유실 없다면서요. 그럼 아이템 지급을 큐로 하면 안전한 거 아니에요? 근데 중복 지급 난다던데?"

여기 아주 흔한 오해가 있습니다. "유실 없음(at-least-once)"이 "정확히 한 번(exactly-once)"은 아닙니다. Kafka의 기본 보장은 "최소 한 번"이라, 오히려 같은 메시지가 두 번 이상 전달될 수 있습니다.

왜 그러냐면 — 컨슈머가 메시지를 처리하고 "다 처리했다"고 표시(오프셋 커밋)하기 직전에 죽으면, 재시작한 컨슈머는 그 메시지를 아직 안 처리한 걸로 보고 다시 꺼내서 또 처리합니다. 유실을 막으려고 "확실히 처리될 때까지 다시 보낸다"를 택한 대가로, 중복이 생기는 거죠. 이 상태에서 지급 로직이 "메시지 왔으니 아이템 준다"만 하면 이중 지급이 납니다.

그래서 반드시 컨슈머 쪽에 멱등성(idempotency)을 넣습니다. 지급마다 고유한 지급ID를 붙이고, "이 ID로 이미 지급했나?"를 먼저 확인한 뒤 처음일 때만 지급합니다. 두 번째로 같은 메시지가 와도 "이미 했음"으로 건너뛰죠. 결론은 이렇습니다 — 신뢰성은 큐가 주는 게 아니라 '큐 + 멱등 소비자'가 준다. 큐만 믿고 멱등을 안 넣으면, 유실은 막았는데 중복으로 재화가 새는 더 나쁜 상황이 됩니다.

면접관🔥 "팀원이 'Kafka 경험 쌓고 싶다, 이력서에도 좋고' 하면서 넣자고 하면 어떻게 해요?"

솔직히 흔한 상황이고, 저는 이걸 이력서 주도 개발(resume-driven development)이라고 부릅니다. 사람의 성장 욕구는 존중하지만, 프로덕션 아키텍처 결정의 근거는 학습 욕구가 아니라 규모여야 합니다.

먼저 데이터로 확인합니다. "지금 우리가 큐에 흘릴 이벤트가 초당 몇 건인가요?" 수천 건 수준이면, 앞서 말한 DB 아웃박스 테이블로 충분합니다. 그 규모에서 Kafka를 넣으면 얻는 처리량 이득은 없고, 브로커 장애 대응, 컨슈머 리밸런싱, 파티션 재배치 같은 운영 부담만 전담 인력을 잡아먹습니다. 작은 팀에선 이게 치명적이에요.

그렇다고 성장을 막진 않습니다. 타협안을 냅니다 — "지금 프로덕션엔 아웃박스로 가고, Kafka는 사이드 프로젝트나 스테이징에서 검증해보자. 실제로 규모가 그 비용을 정당화하는 시점이 오면, 그때 네가 도입을 주도해라." 이러면 학습 기회도 열어주고, 프로덕션은 규모에 맞는 도구로 지킵니다. "지금 필요한가"와 "언젠가 배우고 싶은가"를 분리하는 게 핵심입니다. 조기 도입은 조기 최적화의 사촌이거든요.
