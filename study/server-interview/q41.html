Q41. 수신 버퍼에 패킷 1.5개가 왔다. 경계를 어떻게 자르나? (스트림 vs 메시지)

1차 답변

0. 저는 먼저 이 대전제부터 못 박습니다 — TCP는 스트림이지 메시지가 아니다

이 질문의 답은 사실 한 문장에서 다 나옵니다. TCP는 바이트 스트림만 보장하지 패킷 경계를 지켜주지 않는다. 조선협객전에서 IOCP로 소켓을 다루며 몸으로 익힌 감각이에요.

클라가 send를 한 번 했다고 서버가 recv를 딱 한 번, 그 크기 그대로 받는 게 아닙니다. TCP가 보장하는 건 "보낸 바이트가 순서대로, 빠짐없이 도착한다"뿐이고, 그걸 어떻게 쪼개거나 뭉쳐서 줄지는 커널·네트워크 마음입니다. 그래서 "1.5개가 왔다"는 예외가 아니라 정상입니다. 0.5개도 오고, 3.2개도 오고, 2개가 붙어서 오기도 해요. UDP는 정반대로 메시지 경계는 지키지만 순서·도착을 안 지킵니다(Q35).

1. 순진한 첫 안 — recv 한 번 = 패킷 한 개

순진한 코드: recv()로 받은 버퍼를 곧장 패킷 구조체로 memcpy해서 처리한다. "한 번 받았으니 한 개겠지."

이러면 두 가지로 깨집니다. 반쪽만 온 경우(0.5개) 쓰레기 바이트를 구조체로 캐스팅해 엉뚱한 값을 읽거나 크래시하고, 1.5개가 온 경우 뒤의 0.5개를 통째로 버려서 다음 패킷이 영영 조립되지 않습니다. 실서비스에서 "가끔 특정 유저만 패킷이 꼬인다"의 흔한 원인이 이겁니다.

2. 경계를 긋는 세 가지 방법

(가) 길이 프리픽스(length-prefix) — 헤더 맨 앞에 "이 패킷은 몇 바이트"를 고정 필드로 둡니다. 받는 쪽은 그 길이만큼 모였는지만 확인하면 됩니다. 바이너리 게임 서버의 사실상 정답이고, 제가 쓰던 방식입니다.

(나) 구분자(delimiter) — 개행 같은 특정 바이트로 끊습니다. HTTP 헤더·Redis 같은 텍스트 프로토콜엔 좋지만, 바이너리 게임엔 데이터 안에 그 구분자 바이트가 그대로 나올 수 있어 이스케이프 지옥이 됩니다.

(다) 고정 길이 — 모든 패킷을 같은 크기로. 단순하지만 대부분 낭비거나 경직돼서 게임엔 잘 안 맞습니다.

3. 실제 파싱 루프 — 길이 프리픽스 + 소켓별 링버퍼

제가 IOCP에서 실제로 돌리던 구조는 이렇습니다. 소켓마다 수신 버퍼를 두고, recv 완료 통지가 올 때마다 받은 바이트를 버퍼 뒤에 이어 붙입니다. 그다음 "떨어질 수 있는 만큼만 떼는" 루프를 돕니다.

while (버퍼에 쌓인 양 >= 헤더 크기) { len = read_length(버퍼); // 헤더의 길이 필드 if (len < MIN || len > MAX) // ★ 남이 말한 길이를 검증 close(sock); // 조작·버그면 끊는다 if (버퍼에 쌓인 양 < len) break; // 아직 덜 왔다 → 다음 recv까지 대기 process(버퍼, len); // 온전한 한 개를 떼서 처리 버퍼 소비(len); // read 위치 전진 } // 남은 0.5개는 버퍼에 그대로 두고 다음 recv를 기다린다

포인트는 세 가지입니다. 헤더조차 다 안 왔으면(부분 헤더) 첫 조건에서 그냥 대기하고, 헤더는 왔지만 몸통이 덜 왔으면 break로 남겨두고, 온전한 게 여러 개면 루프가 다 떼어냅니다. 남는 조각은 버리지도 뭉개지도 않고 다음번에 이어붙입니다.

4. 남은 조각을 어떻게 이어붙이나 — 링버퍼 vs memmove

0.5개가 남았을 때 처리하는 방식이 두 갈래입니다. 선형 버퍼 + memmove는 남은 조각을 버퍼 앞으로 당겨오는데, 단순하지만 매번 복사 비용이 듭니다. 링버퍼(ring buffer)는 읽기/쓰기 위치만 돌려서 당김 복사가 없어 빠르지만, 경계에서 감싸는(wrap) 처리가 까다롭습니다. 수만 소켓을 다루면 memmove 비용이 쌓이므로 저는 링버퍼를 선호했지만, 트래픽이 가벼우면 단순한 선형 버퍼가 유지보수에 낫습니다.

5. 반드시 세트인 방어 — 남이 말한 길이를 믿지 마라

위 코드의 ★ 줄이 없으면 큰일 납니다. 헤더의 길이 필드를 그대로 믿고 그만큼 버퍼를 잡으려 하면, 조작된 클라가 length = 2GB를 보내는 순간 서버 메모리가 고갈되는 DoS가 됩니다. 그래서 길이를 파싱하자마자 [최소, 최대] 범위 검증을 하고, 벗어나면 즉시 연결을 끊습니다. length = 0 같은 값도 무한 루프를 유발하니 걸러야 합니다. 경계 자르기는 파싱 문제인 동시에 보안 문제이기도 해요(Q39와 이어집니다).

🧭 이 문제의 원칙"TCP는 스트림이지 메시지가 아니다. 경계는 프로토콜이 직접 그어야 한다." 길이를 먼저 말하고(length-prefix), 다 모일 때까지 기다리고, 남는 조각은 버리지도 뭉개지도 말고 이어붙여라. 그리고 남이 말한 길이를 믿지 마라 — 그 한 줄이 없으면 파서가 곧 DoS 구멍이 된다.

면접관🔥 "recv를 넉넉하게 큰 버퍼로 한 번에 받으면 어차피 다 오는 거 아니에요? 왜 그렇게 복잡하게 해요?"

흔한 오해라 정면으로 답합니다. 버퍼 크기와 경계는 아무 상관이 없습니다.

버퍼를 아무리 크게 잡아도 TCP는 자기 사정대로 쪼개거나 뭉쳐서 줍니다. MTU(한 번에 나갈 수 있는 크기), 송신측 Nagle, 네트워크 혼잡, 커널 버퍼 상태에 따라 결정되지 내 recv 버퍼가 크다고 "한 방에 다 오는" 게 아니에요. 큰 버퍼는 "운 좋으면 여러 개가 한 번에 올" 확률을 높일 뿐, "패킷이 쪼개져 올" 가능성을 0으로 만들지 못합니다.

오히려 큰 버퍼는 "한 번의 recv에 여러 패킷이 붙어 올" 경우를 더 자주 만들어서, 앞서 말한 "여러 개를 다 떼어내는 루프"를 반드시 갖춰야 하게 만듭니다. 결론은 같습니다 — 버퍼 크기에 기대지 말고, 파싱 로직이 경계를 책임져야 합니다. 이건 최적화가 아니라 정확성의 문제라 "복잡해서 안 한다"가 성립하지 않아요.

면접관🔥 "그럼 Nagle 알고리즘을 끄면(TCP_NODELAY) 패킷이 안 뭉쳐서 경계 문제가 없어지지 않아요?"

이것도 자주 헷갈리는 지점이라 짚고 넘어가겠습니다. Nagle과 경계는 다른 문제입니다.

Nagle 알고리즘은 "작은 패킷을 잠깐 모아서 한 번에 보내는" 송신측 최적화입니다. 작은 데이터를 자주 보낼 때 헤더 낭비를 줄이려고 살짝 지연시켜 뭉치는 거죠. TCP_NODELAY로 이걸 끄면 작은 데이터도 즉시 전송돼서 지연(latency)이 줄어듭니다 — 그래서 반응성이 중요한 게임은 대개 NODELAY를 켭니다.

하지만 이건 지연 최적화지 프레이밍(경계) 보장이 아닙니다. NODELAY를 켜도 수신측에서는 여전히 커널이 여러 세그먼트를 합쳐서 recv에 올려주거나, 큰 패킷이 MTU 때문에 쪼개져 도착합니다. Nagle을 꺼도 "1.5개가 오는" 상황은 그대로 남습니다. 그래서 저는 두 개를 분리해서 봅니다 — Nagle은 언제 보낼까의 문제, 경계 파싱은 어떻게 잘라 읽을까의 문제. NODELAY로 지연을 줄이는 것과 별개로, 경계는 여전히 길이 프리픽스로 직접 그어야 합니다.

면접관🔥 "IOCP로 하면 recv 여러 개를 동시에 걸 수 있잖아요. 그러면 완료 순서가 뒤바뀌어서 경계가 더 꼬이지 않아요?"

IOCP를 실제로 다뤄본 사람만 아는 함정을 정확히 짚으셨네요. 맞습니다. 한 소켓에 WSARecv를 여러 개 미리 걸어두면, 완료 통지(completion)가 반드시 건 순서대로 온다는 보장이 없습니다. 워커 스레드가 여럿이라 2번 recv의 완료가 1번보다 먼저 처리될 수 있고, 그러면 바이트 순서가 뒤집혀 스트림이 깨집니다. TCP가 보장한 순서를 애플리케이션 단에서 스스로 망가뜨리는 거죠.

그래서 제 원칙은 "소켓당 미해결 recv는 하나만"입니다. 한 recv가 완료되어 버퍼에 이어붙이고 파싱을 끝낸 뒤에 다음 recv를 겁니다. 이러면 그 소켓의 바이트는 무조건 순서대로 처리됩니다. 여러 recv를 미리 거는 방식을 굳이 쓴다면, 각 수신 조각에 시퀀스 번호를 붙여 소켓별로 재정렬해야 하는데, 이득 대비 복잡도가 커서 저는 게임 서버에선 잘 안 씁니다.

추가로 IOCP 특유의 실수 하나 더 — 완료 통지의 바이트 수를 "패킷 한 개"로 착각하면 안 됩니다. 완료가 알려주는 건 "이번에 이만큼 바이트가 도착했다"일 뿐, 여전히 0.5개일 수도 3개일 수도 있습니다. 그래서 IOCP든 epoll이든, 완료 이벤트 뒤에는 항상 소켓별 버퍼에 이어붙이고 경계 루프를 돌리는 같은 파이프라인이 붙습니다. 비동기 모델이 달라져도 "TCP는 스트림"이라는 대전제는 안 변해요.
