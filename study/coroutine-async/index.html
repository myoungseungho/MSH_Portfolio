콜백 지옥은 어떻게 푸나? — 상태머신과 코루틴/async-await

중첩 콜백 → 상태머신 → 그걸 자동 생성하는 코루틴. 그리고 한 스레드로 수천 요청까지

30초 요약

비동기는 보통 '콜백'으로 짜는데, 단계를 이어붙이면 중첩 피라미드 + 흩어진 상태 + 에러처리 지옥(콜백 지옥).

첫 해결 = 상태머신: '지금 몇 단계(state)'와 '모은 데이터(필드)'를 명시적으로 들고, 이벤트마다 switch로 전이 → 중첩이 평탄해짐.

코루틴/async-await = 그 상태머신을 컴파일러가 자동 생성. 코드는 위→아래 동기처럼 읽히고, 실행은 비동기(스레드 안 막음).

덤으로: await는 I/O 대기 중 스레드를 안 막고 다른 요청을 처리 → 한 스레드로 수천 요청.

Part 1. 콜백 지옥 — 왜 누더기가 되나

비동기를 콜백으로 짜면 뭐가 문제야?

비동기는 "이거 해줘, 다 되면 이 함수 불러줘(콜백)"로 짜. 한 단계면 괜찮은데, 여러 단계를 이어붙이면 콜백 안에 콜백이 겹겹이 쌓여:

// ❌ 콜백 지옥: 단계마다 중첩 + 상태가 콜백에 흩어짐 loadUser(id, (user) => { loadInventory(user, (inv) => { loadPrices(inv, (prices) => { render(user, inv, prices, (html) => { send(html); }); }); }); }); // + 각 단계 에러처리까지 넣으면 피라미드가 더 깊어짐(파멸의 피라미드)
뭐가 그렇게 나빠? 돌아가긴 하잖아.

세 가지가 아파:

1. 중첩: 오른쪽으로 계속 밀려 읽기 힘들어(피라미드).

2. 상태가 흩어짐: 'user, inv, prices'가 각 콜백의 클로저에 갇혀 — 전체 진행 상황을 한눈에 못 봐.

3. 에러·흐름제어 지옥: 각 단계마다 try/에러 콜백을 또 달아야 하고, 반복문·조건문과 섞이면 답이 없어져.

Part 2. 첫 해결 — 상태머신이 정확히 뭔데?

상태머신이 뭐야? 이름만 들으면 어려워 보여.

별거 아냐. '지금 몇 단계인지(state)'와 '지금까지 모은 데이터(필드)'를 명시적으로 들고 다니는 것이야.

콜백 지옥에선 이 정보가 중첩 클로저에 숨어있었지? 상태머신은 그걸 밖으로 꺼내 — state 변수 하나 + 데이터 필드들 + "이벤트 오면 지금 state 보고 다음으로 넘기는 switch". 아래에서 단계가 전이되는 걸 직접 봐 ↓

🔀 상태머신이 뭔데 — 단계와 데이터를 '명시적으로'

▶ 결과 도착을 누를 때마다 '지금 몇 단계인지(state)'가 전이되고, 모은 데이터가 필드에 쌓여. 중첩 콜백을 평탄한 switch로 펴는 게 상태머신이야.

유저 → 인벤 → 가격 → 완료. 각 단계는 이전 결과가 있어야 다음으로 가. 지금은 시작 전.
// 콜백 지옥을 '평탄한 상태머신'으로 편 것 enum State { LOAD_USER, LOAD_INV, LOAD_PRICE, DONE }; struct Session { State state = LOAD_USER; User user; Inventory inv; Prices prices; // 진행 중 데이터를 '필드'에 저장 void onResult(Result r) { switch (state) { // 지금 단계 보고 다음으로 case LOAD_USER: user = r; state = LOAD_INV; loadInventory(user); break; case LOAD_INV: inv = r; state = LOAD_PRICE; loadPrices(inv); break; case LOAD_PRICE: prices = r; state = DONE; send(render(user,inv,prices)); break; } } };

Part 3. 왜 상태머신이 콜백지옥을 푸나

이게 왜 더 나아?

콜백 지옥의 세 가지 아픔이 다 풀려:

1. 중첩 → 평탄: 피라미드가 한 층짜리 switch로 펴져. 오른쪽으로 안 밀려.

2. 흩어진 상태 → 한곳: user·inv·prices가 구조체 필드 한 곳에 모여 — 진행 상황이 명시적.

3. 단계가 데이터로: '지금 어디까지 했나'가 state 변수 하나라, 저장·복구·디버깅이 쉬워.

단점: 손으로 짜면 지루하고 실수 나기 쉬워(단계 하나 빠뜨리면 버그). 그래서 다음이 나와 ↓

Part 4. 코루틴 / async-await — 상태머신을 자동으로

그럼 코루틴/async-await가 정확히 뭘 해주는 거야?

위의 상태머신을 컴파일러가 자동으로 생성해줘. 너는 동기 코드처럼 위→아래로 선형으로 쓰면 돼:

// ✅ 코루틴: 컴파일러가 상태머신을 자동 생성. 코드는 선형(동기처럼 읽힘) task handle(int id) { User user = co_await loadUser(id); // 여기서 suspend, 응답 오면 resume Inventory inv = co_await loadInventory(user); Prices prices = co_await loadPrices(inv); co_await send(render(user, inv, prices)); } // 중첩 0, 상태는 그냥 지역변수, 에러는 평범한 try/catch. // 읽기는 동기처럼, 실행은 비동기(스레드 안 막음).
근데 await 지점에서 어떻게 '멈췄다 이어서'가 돼?

바로 그게 상태머신으로 변환됐기 때문이야. 컴파일러가:

• 각 co_await 지점 = state 하나

• 지역변수(user, inv…) = 상태머신의 필드(그래서 suspend돼도 값이 살아남아)

• resume되면 switch(state)로 멈춘 지점으로 점프

즉 async-await는 Part 2의 손코딩 상태머신을 '자동으로 써주는' 것. 그래서 둘은 같은 해법이고, async-await가 읽기 좋은 버전인 거야.

Part 5. 덤 — await는 스레드를 안 막는다(처리량)

await로 '멈춘다'며. 그럼 스레드도 멈춰서 노는 거 아냐?

아니 — 여기가 핵심 이득이야. await는 '코루틴'은 멈추지만 '스레드'는 안 멈춰. I/O 응답을 기다리는 동안 스레드는 다른 요청의 코루틴을 이어서 실행해.

블로킹이었다면 그 0.9초 I/O 대기 동안 스레드가 그냥 놀아(유휴 낭비). 코루틴은 그 시간에 다른 일을 채워 → 한 스레드로도 수천 요청을 유휴 없이 처리해. 아래에서 총 시간을 비교해봐 ↓

🧵 await는 스레드를 안 막는다 — 한 스레드로 저글링

블로킹은 I/O 기다리는 동안 스레드가 놀아(유휴). 코루틴은 await에서 다른 요청으로 갈아타 유휴를 채워. ▶ 실행해 총 시간을 비교해봐. (예시값)

Part 6. 우리 서버는?

우리 서버는 이걸 어떻게 해?

우리 서버는 싱글스레드 로직 + IOCP야. DB에 요청(DCM_)을 던지고 응답을 기다리는 동안 스레드를 안 막고 다른 유저 패킷을 처리해 — 그리고 DB 응답이 오면 '그 유저가 어느 단계였는지' 세션 상태를 보고 이어서 처리하지.

눈치챘어? 이게 바로 손으로 짠 상태머신이야. '세션에 진행 상태를 저장 → 응답 이벤트에 이어서'가 Part 2 그거거든. C++20 코루틴을 쓰면 이 수동 상태머신을 async-await처럼 자동화할 수 있어 — 콜백/세션 상태 관리를 선형 코드로.

핵심 정리

  • 콜백 지옥 = 비동기 단계를 콜백으로 이어붙여 생기는 중첩 피라미드 + 흩어진 상태 + 에러 지옥.
  • 상태머신 = '몇 단계(state) + 모은 데이터(필드)'를 명시적으로 들고 이벤트마다 switch로 전이 → 중첩을 평탄화.
  • 코루틴/async-await = 그 상태머신을 컴파일러가 자동 생성. 선형 코드로 쓰면 알아서 suspend/resume.
  • await 지점 = state, 지역변수 = 상태머신 필드. 그래서 멈췄다 이어서가 가능.
  • await는 코루틴만 멈추고 스레드는 안 막아 → 그 시간에 다른 요청 처리(한 스레드 수천 요청).
  • 우리 서버는 IOCP+싱글스레드로 '세션 상태=수동 상태머신'. C++20 코루틴으로 자동화 가능.
