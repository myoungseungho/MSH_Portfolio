← AI 활용

개발자 도구를 AI가 100% 만든다면, 어떤 환경이어야 할까?

Internal Tooling의 개념, 종류, 그리고 AI 에이전트가 도구를 만드는 최적 조건

Part 0. 그 "도구"를 뭐라고 불러?

게임 서버 개발하면서 파이썬으로 이것저것 만들잖아. DB 조회 도구, CSV 변환기, 패킷 전송기... 이런 걸 뭐라고 하지?

업계에서는 Internal Tooling 또는 Developer Tooling이라고 불러.

한국어로는 "내부 도구", "개발 도구", "운영 도구" 정도.

[비유: 목수의 연장통] 요리사에게 칼과 도마가 있듯이, 개발자에게도 "코드를 짜기 위한 도구"가 있다. 게임 서버 개발자의 연장통: "이 캐릭터 데이터 좀 봐야 하는데" → DB 조회 도구 "CSV 데이터 형식이 바뀌었네" → 데이터 변환기 "이 패킷을 서버에 보내보자" → 패킷 전송기 "서버 상태 좀 확인하자" → 모니터링 대시보드 "라이브 서버 게이트 잠그자" → GM 도구 이걸 통틀어서 Internal Tooling이라고 한다. 핵심: "유저가 쓰는 게 아니라, 개발자/운영자가 쓰는 도구"
"Internal"이 왜 붙어? 그냥 도구 아니야?

"외부(External)"와 구분하기 위해서야.

[External vs Internal] External (외부용) = 유저가 쓰는 것 → 게임 클라이언트 → 홈페이지 → 앱스토어에 올라가는 앱 → 품질 기준: 매우 높음 (버그 = 매출 손실) Internal (내부용) = 개발자/운영자가 쓰는 것 → DB 조회 도구 → 서버 관리 패널 → 데이터 변환 스크립트 → 빌드 자동화 → 품질 기준: "돌아가면 된다" 차이: External: 디자인, UX, 보안, 성능 전부 중요 Internal: 기능만 되면 됨. UI가 못생겨도 상관없음. 그래서 Internal Tooling은 "빨리 만들고 빨리 고치는" 게 핵심이야. 바로 이 특성 때문에 AI가 만들기에 딱 좋다.

Part 0 핵심

Internal Tooling = 개발자/운영자가 쓰는 내부 도구.

유저가 안 쓰니까 품질 기준이 낮고, 그래서 "빨리 만들고 빨리 고치는" 게 핵심.

이 특성이 AI 에이전트와 궁합이 좋은 이유가 된다.

Part 1. Internal Tooling의 4가지 형태

Internal Tooling에도 종류가 있어?

크게 4가지 형태로 나뉘어. 복잡도 순서대로 볼게.

[4가지 형태 — 단순한 것부터 복잡한 것까지] Level 1. 스크립트 (Script) → 파이썬/배시 파일 하나 → 실행하면 끝. UI 없음. → 예: "CSV를 JSON으로 변환하는 스크립트" → 복잡도: ★☆☆☆☆ Level 2. CLI 도구 (Command Line Interface) → 터미널에서 명령어로 쓰는 도구 → 옵션, 인자, 도움말이 있음 → 예: "python tool.py --input data.csv --output data.json" → 복잡도: ★★☆☆☆ Level 3. Web 대시보드 (Web Dashboard) → 브라우저에서 쓰는 도구 → 버튼, 테이블, 차트가 있음 → 예: "서버 모니터링 페이지, GM 도구 웹" → 복잡도: ★★★☆☆ Level 4. 데스크톱 앱 (Desktop App) → 설치해서 쓰는 독립 프로그램 → Electron, Qt 등으로 제작 → 예: "ChosunToolbox (여러 도구를 하나로 묶은 앱)" → 복잡도: ★★★★☆
실제로 어떤 형태가 제일 많이 쓰여?
형태 실무 사용 빈도 만드는 시간 AI가 만들기
스크립트 ★★★★★ 10분~1시간 매우 쉬움
CLI 도구 ★★★★☆ 1시간~반나절 쉬움
Web 대시보드 ★★★☆☆ 1일~1주 보통
데스크톱 앱 ★★☆☆☆ 1주~수주 어려움
스크립트가 제일 많고, AI도 제일 잘 만든다고?

맞아. 현실에서 Internal Tooling의 80%는 스크립트나 CLI야.

"복잡한 앱"으로 만드는 건 나중에 그 도구가 많은 사람에게 공유될 때.

처음엔 항상 스크립트 하나에서 시작해.

[도구의 진화 과정 — 현실에서 일어나는 일] 1단계: "아 이거 매번 하기 귀찮네" → convert.py 파일 하나 만듦 (스크립트) → 본인만 씀 2단계: "다른 팀원도 쓰고 싶대" → 옵션 추가, README 작성 (CLI 도구) → 팀 내 공유 3단계: "비개발자(기획자)도 써야 해" → 웹 페이지로 감쌈 (Web 대시보드) → 버튼 누르면 실행 4단계: "도구가 10개가 넘으니 하나로 묶자" → Electron 앱 (데스크톱 앱) → ChosunToolbox 같은 통합 도구 핵심: 처음부터 앱을 만들지 않는다. 필요에 의해 "스크립트 → CLI → 웹 → 앱"으로 진화한다.

Part 1 핵심

Internal Tooling은 스크립트 → CLI → Web → 앱 순으로 진화한다.

80%는 스크립트/CLI에서 끝나고, 앱까지 가는 건 소수다.

AI 에이전트가 가장 잘 만드는 것도 스크립트/CLI 영역이다.

Part 2. 인간이 도구를 만드는 방식 vs AI가 만드는 방식

인간이 도구를 만들 때랑 AI가 만들 때, 뭐가 다른 건데?

핵심 차이는 "머릿속에 있는 것"을 어디에 두느냐야.

[비유: 레시피 없는 요리사 vs 레시피 있는 로봇] 인간 개발자: "CSV 변환기 만들어야지" → 머릿속으로 설계 (문서 없음) → 코딩 시작 → 중간에 "아 이것도 필요하네" (설계 변경) → 완성. 본인은 다 알지만 문서는 없음. → 다른 사람: "이거 어떻게 쓰는 거야?" AI 에이전트: "CSV 변환기 만들어야지" → 머릿속? 없음. 뇌가 없으니까. → 대신 "명세서"가 필요함 (입력/출력/규칙이 명확해야 함) → 명세서대로 정확히 만듦 → 명세서에 없는 건 못 만듦 인간: "대충 감으로" 만들 수 있다 → 빠르지만 지식이 머릿속에 갇힘 AI: "정확한 지시로" 만들어야 한다 → 느려 보이지만 지식이 밖에 남음
그러면 AI한테 도구를 시키려면, 그 "명세서"를 잘 써야 한다는 거야?

맞아. 그런데 여기서 재밌는 반전이 있어.

명세서를 쓰는 것 자체가 설계의 80%야.

[명세서 = 설계의 실체] 인간이 도구를 만드는 과정: 1. 머릿속에서 설계 (30분) 2. 코딩 (2시간) 3. 디버깅 (1시간) 4. 합계: 3시간 30분 AI에게 시키는 과정: 1. 명세서 작성 (30분) ← 인간의 "설계"와 같은 시간 2. AI가 코딩 (3분) 3. AI가 디버깅 (5분) 4. 합계: 38분 비밀: 인간이 2시간+1시간 쓰던 "코딩+디버깅"이 8분으로 줄었다. 하지만 "설계(명세서 작성)" 30분은 똑같다. 결론: AI가 빠른 게 아니라, "코딩+디버깅"이 자동화된 것이다. 설계는 여전히 인간의 몫이다.
그러면 좋은 명세서란 뭔데?

AI가 이해할 수 있는 명세서에는 3가지가 꼭 필요해.

[좋은 명세서의 3요소] 1. 입력 (Input) "뭘 받는가?" → 파일? API 응답? DB 쿼리 결과? 사용자 입력? → 형식은? (CSV, JSON, 바이너리?) → 예시 데이터 있으면 최고 2. 출력 (Output) "뭘 내놓는가?" → 변환된 파일? 화면 출력? DB에 저장? → 형식은? 예시는? 3. 규칙 (Rules) "어떤 조건으로 변환하는가?" → 에러 처리는? (파일 없으면? 형식 틀리면?) → 특수한 경우는? (빈 값, 한글 인코딩, 날짜 형식) 나쁜 명세서: "CSV를 JSON으로 바꿔줘" → AI: 어떤 CSV? 구분자가 쉼표야 탭이야? 헤더 있어? 인코딩이 뭐야? 빈 칸은 어떻게 해? 좋은 명세서: "EUC-KR 인코딩의 CSV 파일을 읽어서 UTF-8 JSON으로 변환해줘. 첫 줄은 헤더. 구분자는 탭. 빈 값은 null로. 출력 파일명은 원본파일명.json으로. 예시 입력: data.csv (첨부) 예시 출력: data.json (첨부)"

Part 2 핵심

인간은 "머릿속에서 설계"하고, AI는 "명세서를 읽고 실행"한다.

명세서 쓰기 = 설계의 80%. 코딩은 나머지 20%에 불과하다.

AI가 빠른 게 아니라 "코딩+디버깅 시간이 사라진 것"이다.

Part 3. AI가 도구를 잘 만드는 환경의 조건

그러면 AI 에이전트가 도구를 100% 혼자 만들려면, 환경이 어떻게 되어 있어야 해?

3가지 조건이 갖춰져야 해. 하나라도 없으면 AI가 중간에 멈춰.

[AI가 도구를 만들 수 있는 3가지 조건] 조건 1: 명세가 코드 옆에 있어야 한다 (Spec-as-Code) → 뭘 만들어야 하는지 AI가 읽을 수 있어야 함 → README.md, 주석, 타입 정의 등 조건 2: 실행하고 확인할 수 있어야 한다 (Feedback Loop) → 만든 걸 돌려보고, 맞는지 틀린지 스스로 알 수 있어야 함 → 테스트 코드, 예시 데이터, 실행 환경 조건 3: 인터페이스가 명확해야 한다 (Clear Boundary) → 입구와 출구가 확실해야 함 → "이 함수에 이걸 넣으면 저걸 뱉는다"가 분명해야 함 이 3개가 있으면: AI가 혼자서 만들고 → 테스트하고 → 고칠 수 있다. 이 3개가 없으면: AI가 만들긴 하는데 → 맞는지 모르고 → 인간이 확인해야 한다.
하나씩 더 자세히 설명해줘. 먼저 "명세가 코드 옆에 있다"는 게 뭔데?
[조건 1: Spec-as-Code — 명세가 코드와 함께 산다] 나쁜 환경: 기획서가 컨플루언스(위키)에 있고, 코드는 깃에 있고, 구두로 전달된 요구사항은 슬랙 어딘가에 있다. → AI: "뭘 만들라는 건지 모르겠는데..." 좋은 환경: /tools/csv-converter/ ├── README.md ← "이 도구가 뭘 하는지" 설명 ├── spec.md ← "입력/출력/규칙" 명세 ├── examples/ │ ├── input.csv ← 예시 입력 │ └── expected.json ← 예상 출력 ├── converter.py ← 실제 코드 └── test_converter.py ← 테스트 → AI: "아, spec.md 읽으면 되겠다. 예시도 있네. 이대로 만들면 되겠다." 핵심: 명세가 "코드와 같은 폴더"에 있으면 AI가 바로 읽을 수 있다. 컨플루언스 링크는 AI가 못 열어. 슬랙 대화는 AI가 못 찾아. 파일로 있어야 한다.
두 번째, "실행하고 확인할 수 있다"는 건?
[조건 2: Feedback Loop — 만들고 돌려보고 고치는 루프] 비유: 눈 감고 요리하기 vs 눈 뜨고 요리하기 눈 감고: 소금을 넣었는데, 맛이 어떤지 모른다 → 결과물이 짜든 싱겁든 알 수 없다 → 인간이 맛봐줘야 한다 눈 뜨고: 소금을 넣고, 맛을 보고, 부족하면 더 넣는다 → 스스로 조절 가능 → 인간 없이도 된다 AI 도구 제작에서: "눈 감기" = 테스트 없이 코드만 생성 → AI: 코드 짰습니다! (맞는지 모름) → 인간: 돌려보니 에러남... 고쳐줘 → AI: 고쳤습니다! (또 맞는지 모름) → 무한 반복... "눈 뜨기" = 테스트 코드가 있음 → AI: 코드 짰습니다! 테스트 돌려볼게요. → 테스트: 3개 통과, 1개 실패 (인코딩 에러) → AI: 인코딩 수정했습니다. 테스트 재실행. → 테스트: 4개 전부 통과! → 완료. 인간이 안 봐도 됨. 핵심: 테스트 = AI의 눈. 테스트가 있으면 AI가 스스로 루프를 돌며 고칠 수 있다. 테스트가 없으면 AI는 눈 감고 짜는 것과 같다.
세 번째, "인터페이스가 명확하다"는 건?
[조건 3: Clear Boundary — 입구와 출구가 확실하다] 비유: 자판기 vs 뷔페 자판기: 동전 넣으면 → 음료 나옴 (명확) → AI에게: "동전 받아서 음료 주는 것 만들어" → 바로 만들 수 있음 뷔페: 들어가면 → 뭘 먹을지는 알아서 (불명확) → AI에게: "뷔페 만들어" → "뭘 만들라고요...?" 코드에서: 명확한 인터페이스: def convert(input_path: str, encoding: str) -> dict: """CSV 파일을 읽어서 딕셔너리로 반환""" → 입력: 파일 경로 + 인코딩 → 출력: 딕셔너리 → AI: 이 함수 채우면 되겠다! 불명확한 인터페이스: def process(data): """데이터 처리""" → 입력: data가 뭔데? 문자열? 리스트? 파일? → 출력: 뭘 리턴하는데? 저장하는 건 아니야? → AI: "... 뭘 하라는 건지 모르겠다" 핵심: 타입 힌트 + 독스트링 = AI에게 주는 설계도. 이게 명확하면 AI가 함수 내부를 채울 수 있다. 이게 없으면 AI가 "추측"해서 만드는데, 높은 확률로 틀린다.
3가지를 한눈에 정리하면?
[AI 도구 제작 환경의 3요소] ┌──────────────────────────────────────────────────┐ │ 1. Spec-as-Code (명세) │ │ "뭘 만들어야 하는지" AI가 읽을 수 있게 │ │ → README, spec.md, 예시 데이터 │ │ → 없으면: AI가 추측해서 만듦 (높은 확률로 틀림) │ └──────────────────┬───────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────┐ │ 2. Feedback Loop (확인) │ │ "맞는지 틀린지" AI가 스스로 확인 │ │ → 테스트 코드, 예시 입출력 │ │ → 없으면: 인간이 매번 확인해줘야 함 │ └──────────────────┬───────────────────────────────┘ ↓ ┌──────────────────────────────────────────────────┐ │ 3. Clear Boundary (인터페이스) │ │ "입구/출구가 명확"해서 AI가 헤매지 않음 │ │ → 타입 힌트, 독스트링, 함수 시그니처 │ │ → 없으면: AI가 헤매며 이상한 걸 만듦 │ └──────────────────────────────────────────────────┘ 3개 다 있으면 = AI가 혼자서 만들고 검증까지 가능 2개만 있으면 = AI가 만들지만 인간이 확인 필요 1개만 있으면 = 인간이 반쯤 같이 만드는 것 0개이면 = 인간이 그냥 직접 만드는 게 빠름

Part 3 핵심

명세(Spec) + 피드백(Test) + 인터페이스(Type) = AI 도구 제작의 3요소.

3개 다 갖추면 AI가 혼자서 만들고 → 테스트하고 → 수정까지 가능.

핵심은 "AI를 똑똑하게 만드는 것"이 아니라 "환경을 명확하게 만드는 것"이다.

Part 4. 실전 — 게임 서버 도구를 AI에게 맡긴다면?

실제로 게임 서버 개발하면서 만드는 도구들 있잖아. 그걸 AI에게 맡긴다면?

현실적인 사례 3개로 보여줄게. 쉬운 것부터 어려운 것 순서로.

[사례 1: CSV 변환기 — AI 난이도: 쉬움] 상황: 기획자가 엑셀로 스킬 데이터를 만들면, 서버가 읽을 수 있는 CSV 형식으로 변환해야 한다. 명세: 입력: 기획자 엑셀 (EUC-KR, 탭 구분, 첫 2줄은 헤더) 출력: 서버용 CSV (UTF-8, 쉼표 구분, 첫 1줄 헤더) 규칙: 빈 셀은 0, 날짜는 YYYYMMDD, 한글 컬럼명은 영문으로 환경 준비: /tools/csv-converter/ ├── spec.md ← 위 명세 그대로 ├── examples/ │ ├── skill_raw.xlsx ← 기획자 원본 │ └── skill_expected.csv ← 예상 결과 ├── converter.py ← AI가 채울 파일 └── test_converter.py ← "expected와 같은지" 비교 AI에게: "spec.md 읽고 converter.py 구현해. test 통과하면 완료." → AI가 혼자서 완성 가능 (3요소 모두 충족)
[사례 2: DB 조회 대시보드 — AI 난이도: 보통] 상황: 운영 중에 "이 유저 인벤토리 보여줘" 요청이 자주 온다. 매번 SSMS 열고 쿼리 치는 게 귀찮다. 명세: 입력: 캐릭터 이름 또는 UID 출력: 인벤토리 테이블 (아이템명, 수량, 강화수치) 규칙: 읽기 전용. DB 수정 절대 금지. 라이브 DB 직접 연결. 환경 준비: /tools/inventory-viewer/ ├── spec.md ← 위 명세 ├── schema.sql ← 관련 테이블 DDL (AI가 구조 이해용) ├── examples/ │ └── sample_query.sql ← 예시 쿼리 ├── app.py ← Flask 웹앱 (AI가 구현) └── test_app.py ← API 테스트 AI가 추가로 필요한 것: → DB 접속 정보 (환경변수로 분리) → 테이블 스키마 (schema.sql로 제공) 이건 "규칙"이 좀 더 복잡해서 명세가 더 자세해야 함. → AI가 만들 수 있지만, 인간이 한 번 확인해야 안심
[사례 3: 패킷 전송기 — AI 난이도: 어려움] 상황: 특정 게임 패킷을 서버에 보내서 테스트하고 싶다. 바이너리 프로토콜이라 도구 없이는 어렵다. 명세: 입력: 패킷 타입 + 파라미터 (GUI에서 선택) 출력: 서버에 패킷 전송 + 응답 표시 규칙: C++ 구조체 기반 바이너리 패킷, 리틀엔디안, 암호화 필요 환경의 문제: → 패킷 구조가 C++ 헤더 파일에만 정의되어 있음 → 암호화 로직이 별도 라이브러리에 있음 → 테스트하려면 실제 서버가 떠 있어야 함 → 예시 데이터를 만들기 어려움 (바이너리) → 3요소 중 "명세"와 "피드백"이 부족 → AI 혼자서는 어렵고, 인간이 많이 도와줘야 함 → 또는: C++ 헤더를 파싱해서 JSON 스키마로 변환하는 "사전 작업"을 먼저 해야 함
결국 AI가 잘 만드는 것과 못 만드는 것의 차이가 뭐야?
조건 AI가 잘 만드는 도구 AI가 못 만드는 도구
입출력 텍스트 (CSV, JSON, SQL) 바이너리 (패킷, 구조체)
명세 파일로 존재 (읽을 수 있음) 머릿속/구두 (읽을 수 없음)
테스트 자동화 가능 (비교, 단정) 인간이 눈으로 확인 필요
의존성 독립적 (파일 하나로 동작) 외부 서비스 필요 (서버, DB, 암호화)
규칙 명확한 규칙 (변환, 계산) 애매한 판단 ("적절히", "상황에 따라")

Part 4 핵심

텍스트 기반 + 명세 파일 + 자동 테스트 + 독립 실행 = AI가 혼자 만들 수 있다.

바이너리 + 구두 명세 + 수동 확인 + 외부 의존 = 인간이 많이 도와야 한다.

"AI가 도구를 못 만드는 건 AI 탓이 아니라, 환경이 AI-friendly하지 않은 탓"이다.

Part 5. 이상적인 환경 — "AI 도구 공장"

최종 정리해줘. AI 에이전트가 도구를 알아서 만드는 이상적인 환경이란?

앞에서 본 3가지 조건을 폴더 구조와 워크플로우로 구체화하면 이렇게 돼.

[AI 도구 공장 — 폴더 구조] /tools/ ├── _templates/ ← 도구 템플릿 (뼈대) │ ├── cli_template/ │ │ ├── spec.md # 명세 템플릿 │ │ ├── main.py # 코드 뼈대 │ │ └── test_main.py # 테스트 뼈대 │ └── web_template/ │ ├── spec.md │ ├── app.py │ └── test_app.py │ ├── csv-converter/ ← 도구 1 │ ├── spec.md # 이 도구가 뭘 하는지 │ ├── examples/ # 예시 입출력 │ ├── converter.py # 코드 (AI가 작성) │ └── test_converter.py # 테스트 (AI가 실행) │ ├── db-viewer/ ← 도구 2 │ ├── spec.md │ ├── schema.sql │ ├── app.py │ └── test_app.py │ └── tool-registry.json ← 도구 목록 (메타데이터)
워크플로우는 어떻게 돼?
[AI 도구 공장 — 워크플로우] 인간 AI 에이전트 │ │ │ 1. "CSV 변환 도구 필요해" │ │ ─────────────────────────→ │ │ │ │ 2. 템플릿 복사 │ _templates/cli → tools/csv-converter/ │ │ │ 3. spec.md 작성 │ │ (입력/출력/규칙/예시) │ │ ─────────────────────────→ │ │ │ │ 4. spec.md 읽기 │ 5. 코드 작성 (converter.py) │ 6. 테스트 실행 │ ┌──→ 실패? → 코드 수정 → 재실행 │ └──→ 성공! │ │ │ ←───────────────────────── │ │ 7. "완료. 테스트 전부 통과" │ │ │ │ 8. 인간이 한 번 써보고 확인 │ │ ─────────────────────────→ │ │ "오, 잘 되네" │ └───────────────────────────────┘ 인간이 하는 것: 1(요청) + 3(명세) + 8(확인) = 3단계 AI가 하는 것: 2+4+5+6(+반복) = 나머지 전부 인간의 역할이 "What을 정의"하는 것으로 바뀌었다.
잠깐, 이거 기존 포트폴리오에서 다뤘던 "에이전트 퍼스트 아키텍처"랑 연결되는 거야?

정확히 같은 원리야.

서버 코드든 도구든, AI가 잘 다루는 환경의 조건은 동일해.

[연결: 서버 개발 vs 도구 개발 — 같은 원리] 에이전트 퍼스트 아키텍처 (서버): → 코드가 명시적 (암묵지 최소화) → 테스트 가능한 구조 (ECS 등) → 인터페이스가 명확 (컴포넌트 경계) AI 도구 공장 (도구): → 명세가 파일로 존재 (Spec-as-Code) → 테스트 자동화 (Feedback Loop) → 입출력이 명확 (Clear Boundary) 공통 원리: "AI가 읽을 수 있고, 실행할 수 있고, 확인할 수 있는 환경" 차이점: 서버: 기존 코드가 복잡해서 "구조를 바꿔야" AI가 다룰 수 있다 도구: 새로 만드는 거라서 "처음부터 AI-friendly하게" 만들 수 있다 → 사실 도구가 AI 자동화의 가장 좋은 시작점이다. 기존 서버 코드를 건드리지 않고, 주변 도구부터 AI에게 맡기면 리스크 없이 AI 자동화를 경험할 수 있다.

Part 5 핵심

템플릿 + 명세 + 자동 테스트 = AI가 도구를 찍어내는 공장.

인간은 "What(뭘 만들지)"만 정의하고, AI가 "How(어떻게)"를 실행한다.

기존 서버 코드보다 도구가 AI 자동화의 가장 좋은 시작점이다.

AI가 도구를 만들 때의 함정

명세 없이 "대충 만들어줘"라고 하면, AI가 "대충" 만든다. 결과도 "대충"이다.

테스트 없이 "알아서 해줘"라고 하면, AI는 자기가 맞는지 모른다. 결국 인간이 전부 확인해야 한다.

"도구를 AI가 만드니까 설계 안 해도 되지?" 아니다. 설계(명세)는 여전히 인간 몫이다. 코딩만 사라진 거다.

핵심 정리

  • Internal Tooling — 개발자/운영자가 쓰는 내부 도구. 유저가 안 보니까 "빨리 만들고 빨리 고치는" 게 핵심
  • 4가지 형태 — 스크립트 → CLI → Web → 데스크톱 앱. 80%는 스크립트/CLI에서 끝남
  • 인간 vs AI — 인간은 "머릿속 설계 + 코딩". AI는 "명세서 읽기 + 코딩". 설계 시간은 같고, 코딩 시간만 사라짐
  • AI 도구 제작 3조건 — Spec-as-Code(명세) + Feedback Loop(테스트) + Clear Boundary(인터페이스)
  • AI가 잘 만드는 도구 — 텍스트 기반, 명세 있음, 자동 테스트 가능, 독립 실행
  • AI가 못 만드는 도구 — 바이너리, 구두 명세, 수동 확인 필요, 외부 의존
  • 에이전트 퍼스트와 같은 원리 — "AI가 읽고, 실행하고, 확인할 수 있는 환경"을 만드는 것
  • 도구가 최고의 시작점 — 서버 코드를 안 건드리고, 주변 도구부터 AI에게 맡기면 리스크 없이 경험 가능
