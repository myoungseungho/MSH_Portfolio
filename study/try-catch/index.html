@@error 체크, 왜 구식이 됐을까?

SQL Server 에러 처리의 진화: @@error → TRY-CATCH

Part 1. 우리 프로시저는 어떻게 되어 있어?

에러 처리 코드 보다가 이런 패턴을 봤는데, 이게 뭐야?

우리 프로젝트의 전형적인 에러 처리 패턴이야.

BEGIN TRAN UPDATE TCharacter SET level = @level WHERE charunique = @uid IF @@error <> 0 BEGIN ROLLBACK TRAN RETURN -1 END UPDATE TInventory SET ... WHERE charunique = @uid IF @@error <> 0 BEGIN ROLLBACK TRAN RETURN -2 END COMMIT TRAN
@@error가 에러 코드를 담고 있는 거구나?

맞아. @@error는 "직전 SQL문의 에러 번호"를 담고 있어.

0이면 성공, 0이 아니면 에러.

그럼 뭐가 문제야? 잘 동작하는 것 같은데?

대부분의 경우 잘 동작해. 근데 치명적인 함정이 몇 개 있어.

Part 2. 함정 1: @@error는 휘발성이다

휘발성? 무슨 뜻이야?

@@error 값은 다음 SQL문이 실행되면 즉시 덮어씌워져.

-- 에러 발생! INSERT INTO TCharacter ... -- 중복키 에러 (@@error = 2627) -- 로그 남기려고 PRINT 했는데... PRINT '에러 발생!' -- 이 문장이 성공 (@@error = 0으로 덮어씀!) IF @@error <> 0 -- 이미 0이라서 조건 통과 못함! BEGIN ROLLBACK -- 실행 안 됨 END

시간순 정리:

INSERT 실행 → 중복키 에러 발생 (@@error = 2627)
PRINT 실행 → 성공 (@@error = 0으로 변경!)
IF @@error 체크 → 0이라서 에러 감지 실패
결과 → 에러났는데 롤백 안 됨!
어? 그럼 @@error는 바로 체크해야 하네?

맞아. SQL문 바로 다음 줄에서 체크해야 해.

중간에 다른 문장 하나라도 끼면 안 돼.

-- 올바른 패턴 INSERT INTO TCharacter ... IF @@error <> 0 -- 바로 다음 줄! BEGIN ROLLBACK RETURN -1 END -- 또는 변수에 저장 DECLARE @err int INSERT INTO TCharacter ... SET @err = @@error -- 바로 저장! PRINT '로그...' -- 이제 괜찮음 IF @err <> 0 ROLLBACK

Part 3. 함정 2: 심각한 에러는 @@error로 못 잡아

심각한 에러? 예를 들면?

에러에는 "심각도(Severity)"가 있어.

심각도 설명 @@error로 잡힘?
11~16 일반 에러 (제약조건 위반, 문법 오류 등) O
17~19 리소스/소프트웨어 에러 △ (일부)
20~25 치명적 에러 (연결 끊김, 데이터 손상) X
심각도 20 이상이면 @@error 체크 자체가 안 된다고?

맞아. 심각한 에러가 나면 실행 자체가 중단돼.

IF @@error 줄까지 도달하지 못해.

-- 심각도 20 에러 발생 시 INSERT INTO TCharacter ... -- 💥 심각한 에러 발생! -- 여기서 실행 중단 IF @@error <> 0 -- 이 줄까지 도달 못함 BEGIN ROLLBACK -- 실행 안 됨 END -- 결과: 트랜잭션이 열린 채로 연결이 끊어질 수 있음

Part 4. 함정 3: 코드가 너무 길어진다

매 SQL문마다 IF @@error 체크하면...

코드가 2배로 늘어나.

BEGIN TRAN INSERT INTO TCharacter ... IF @@error <> 0 BEGIN ROLLBACK RETURN -1 END INSERT INTO TInventory ... IF @@error <> 0 BEGIN ROLLBACK RETURN -2 END INSERT INTO TSkill ... IF @@error <> 0 BEGIN ROLLBACK RETURN -3 END INSERT INTO TQuest ... IF @@error <> 0 BEGIN ROLLBACK RETURN -4 END INSERT INTO TTitle ... IF @@error <> 0 BEGIN ROLLBACK RETURN -5 END -- 10개 INSERT면 20줄... COMMIT TRAN

실제 우리 프로젝트의 gp_make_pc는 30개 이상의 INSERT가 있어.

매번 @@error 체크하면 60줄 이상 추가됨.

Part 5. 해결책: TRY-CATCH

그래서 TRY-CATCH가 뭔데?

C++, Java, C# 같은 언어에서 쓰는 그 try-catch랑 같은 개념이야.

SQL Server 2005부터 지원됐어.

BEGIN TRY -- 에러가 발생할 수 있는 코드 INSERT INTO TCharacter ... INSERT INTO TInventory ... INSERT INTO TSkill ... END TRY BEGIN CATCH -- 에러 발생 시 이리로 점프 ROLLBACK RETURN -1 END CATCH
오, 훨씬 깔끔하네?

비교해볼까?

항목 @@error 방식 TRY-CATCH 방식
코드 양 SQL문마다 체크 한 번만 감싸면 됨
심각한 에러 못 잡음 잡을 수 있음
휘발성 문제 있음 없음
에러 정보 @@error만 ERROR_MESSAGE(), ERROR_LINE() 등

Part 6. TRY-CATCH에서 쓸 수 있는 함수들

ERROR_MESSAGE()가 뭐야?

CATCH 블록 안에서 쓸 수 있는 에러 정보 함수들이야.

함수 반환값 예시
ERROR_NUMBER() 에러 번호 2627
ERROR_MESSAGE() 에러 메시지 "중복 키..."
ERROR_SEVERITY() 심각도 14
ERROR_LINE() 에러 발생 줄 15
ERROR_PROCEDURE() 프로시저 이름 "gp_make_pc"
BEGIN TRY INSERT INTO TCharacter ... END TRY BEGIN CATCH PRINT '에러 번호: ' + CAST(ERROR_NUMBER() AS varchar) PRINT '에러 메시지: ' + ERROR_MESSAGE() PRINT '발생 줄: ' + CAST(ERROR_LINE() AS varchar) ROLLBACK RETURN -1 END CATCH

디버깅할 때 어디서 무슨 에러가 났는지 바로 알 수 있어.

Part 7. 실제 변환 예시

Before: @@error 방식 (우리 프로젝트 레거시)

CREATE PROCEDURE gp_make_pc ... AS BEGIN BEGIN TRAN INSERT INTO TCharacter ... IF @@error <> 0 BEGIN ROLLBACK RETURN -2 END INSERT INTO TInventory ... IF @@error <> 0 BEGIN ROLLBACK RETURN -3 END INSERT INTO TSkill ... IF @@error <> 0 BEGIN ROLLBACK RETURN -4 END -- ... 30개 INSERT마다 체크 ... COMMIT TRAN END

After: TRY-CATCH 방식

CREATE PROCEDURE gp_make_pc ... AS BEGIN SET NOCOUNT ON; BEGIN TRY BEGIN TRAN INSERT INTO TCharacter ... INSERT INTO TInventory ... INSERT INTO TSkill ... -- ... 30개 INSERT 깔끔하게 ... COMMIT TRAN END TRY BEGIN CATCH IF @@TRANCOUNT > 0 ROLLBACK TRAN -- 에러 로깅 PRINT ERROR_MESSAGE() RETURN -1 END CATCH END

Part 8. TRY-CATCH 주의사항

⚠️ TRY-CATCH도 만능은 아니야

심각도 10 이하의 "경고"는 CATCH에서 안 잡혀. 심각도 11 이상만 잡힘.

그리고 또 주의할 거 있어?

@@TRANCOUNT 체크가 중요해.

BEGIN CATCH -- 트랜잭션이 열려있을 때만 롤백 IF @@TRANCOUNT > 0 ROLLBACK TRAN -- 그냥 ROLLBACK 하면 트랜잭션 없을 때 에러남 END CATCH

에러가 발생하면 트랜잭션 상태가 "커밋 불가능(uncommittable)"이 될 수 있어.

이때 XACT_STATE()로 상태를 확인하면 더 정확해.

BEGIN CATCH IF XACT_STATE() = -1 -- 커밋 불가능 상태 ROLLBACK TRAN ELSE IF XACT_STATE() = 1 -- 커밋 가능 상태 COMMIT TRAN -- 필요시 커밋 THROW; -- 에러 다시 던지기 (SQL 2012+) END CATCH

Part 9. 우리 프로젝트 현황

우리는 어떤 방식을 쓰고 있어?

분석 결과:

패턴 사용 비율 프로시저 예시
@@error 방식 대다수 gp_save_pc, gp_make_pc
TRY-CATCH 방식 일부 gp_Release_Transaction, gp_COPY_CHARACTER

레거시 코드는 @@error, 최신 코드는 TRY-CATCH

점진적으로 TRY-CATCH로 마이그레이션하는 게 좋아.

마이그레이션할 때 주의할 점?

• 반환 코드 호환성 유지 (게임 서버에서 -1, -2 등을 구분할 수 있으니)

• 테스트 철저히 (에러 발생 시 롤백 확인)

• 점진적으로 (한 번에 다 바꾸지 말고)

핵심 정리

  • @@error = 직전 SQL문의 에러 번호 (0이면 성공)
  • @@error의 함정: 휘발성, 심각한 에러 못 잡음, 코드 길어짐
  • TRY-CATCH = SQL Server 2005+ 에러 처리 (권장)
  • CATCH 블록에서 ERROR_MESSAGE() 등으로 상세 정보 확인
  • @@TRANCOUNT/XACT_STATE() 체크 후 ROLLBACK
  • 마이그레이션: 점진적으로, 반환 코드 호환성 유지
