"지금 상태"를 저장 안 하고 "변경 기록"만 저장한다고?

이벤트 소싱(Event Sourcing) - 모든 변경을 기록하는 새로운 패러다임

Part 1. 지금까지 어떻게 저장했어?

DB에 저장한다는 게 뭐야?

보통은 "현재 상태"만 저장해.

골드가 1000원이면 DB에 "1000"만 저장되어 있어.

💾 일반적인 상태 저장 (State-based): [유저 캐릭터 테이블] ┌────────┬───────┬──────────┐ │ CharID │ Gold │ Level │ ├────────┼───────┼──────────┤ │ 12345 │ 1000 │ 50 │ └────────┴───────┴──────────┘ "현재 골드가 1000원이다" → 어떻게 1000원이 됐는지는 모름
그게 뭐가 문제야?

"어제 500원 있었는데 왜 1000원이에요?"

어디서 500원이 생겼는지 알 수 없어.

버그인지, 핵인지, 정상인지 추적 불가능.

🤔 상태만 저장하면 생기는 문제: 유저: "어제 1만 골드 있었는데 왜 1000원이에요?!" 개발자: DB 확인... "현재 1000원입니다" 유저: "도둑맞은 거 아니에요?!" 개발자: "어... 히스토리가 없어서 모르겠는데..." → 로그 찾으러 여러 테이블 뒤지기 → 로그 없으면 미궁 속으로...

Part 2. 이벤트 소싱이 뭔데?

그럼 어떻게 저장해야 해?

"변경 사건" 자체를 저장하는 거야.

"현재 1000원"이 아니라 "500원 획득, 300원 획득, 200원 사용..." 식으로.

📜 이벤트 소싱 (Event Sourcing): [이벤트 저장소] ┌─────┬────────────────────────┬───────┐ │ Seq │ Event │ Data │ ├─────┼────────────────────────┼───────┤ │ 1 │ CharacterCreated │ {...} │ │ 2 │ GoldEarned │ +500 │ │ 3 │ GoldEarned │ +800 │ │ 4 │ ItemPurchased │ -300 │ │ 5 │ GoldEarned │ +100 │ └─────┴────────────────────────┴───────┘ 현재 골드 = 0 + 500 + 800 - 300 + 100 = 1100 "어떻게 1100원이 됐는지" 완전히 추적 가능!
은행 통장이랑 비슷하네?

정확해! 통장 = 이벤트 소싱이야.

통장에는 "입금 100만원", "출금 50만원" 기록이 있잖아.

잔액은 그 기록들을 다 더하면 나오는 거고.

🏦 은행 통장 = 이벤트 소싱: [통장 내역] 2024-01-01: 입금 +1,000,000원 (월급) 2024-01-05: 출금 -500,000원 (월세) 2024-01-10: 입금 +200,000원 (용돈) 2024-01-15: 출금 -100,000원 (쇼핑) ─────────────────────────────── 현재 잔액: 600,000원 → 잔액이 왜 60만원인지 완벽하게 설명 가능! → "1월 5일에 월세 나갔구나" 추적 가능!

Part 3. 이벤트 소싱의 장점

구체적으로 뭐가 좋아?

게임 서버에서 엄청 유용한 장점들이 있어:

✅ 장점 1: 완벽한 히스토리 "이 유저 골드 이상해요" 문의 들어옴: [이벤트 로그 조회] #1521: 퀘스트 보상 +1000 #1522: 아이템 판매 +500 #1523: ???강화 +999999 ← 🚨 이상한 이벤트 발견! → "강화에서 비정상 골드 획득" 원인 즉시 파악! → 버그인지 핵인지 바로 확인
✅ 장점 2: 시간 여행 (Time Travel) "어제 17시 상태로 돌려주세요" 요청: 이벤트를 어제 17시까지만 재생! #1 → #2 → #3 → ... → #1521 (17:00) └─ 여기까지만 적용 → 어제 17시 상태 완벽 복원! → 롤백이 아니라 "특정 시점 조회"
✅ 장점 3: 버그 재현 "이상한 상황에서 크래시 났어요": 해당 유저의 이벤트를 처음부터 재생! #1: 캐릭터 생성 #2: 아이템 획득 #3: 스킬 사용 ... #150: 특정 스킬 사용 ← 💥 크래시! → 개발 환경에서 정확히 같은 상황 재현 → 버그 원인 분석 용이
상황 상태 저장 이벤트 소싱
골드 이상 문의 로그 뒤지기 이벤트 조회
롤백 요청 백업 복원 시점 재생
버그 재현 추측으로 이벤트 리플레이
핵 탐지 로그 분석 이상 패턴 탐지

Part 4. 현재 상태는 어떻게 알아?

매번 이벤트 다 더해야 해?

그러면 너무 느리지.

스냅샷(Snapshot)을 만들어둬.

📸 스냅샷 (Snapshot): 이벤트가 1000개 쌓임: #1 → #2 → #3 → ... → #1000 매번 1000개 다 더하면 느림! 해결: 중간중간 스냅샷 저장 #1 → ... → #500 → [스냅샷: Gold=5000] → #501 → ... → #1000 현재 상태 계산: = 스냅샷(5000) + #501~#1000 이벤트 = 500개만 계산하면 됨!
스냅샷은 얼마나 자주 만들어?

이벤트 N개마다 또는 시간 간격으로.

예: "이벤트 100개마다" 또는 "1시간마다"

⚡ 스냅샷 전략: [전략 1: 이벤트 개수 기준] 100개마다 스냅샷 생성 → 최대 100개만 재생하면 됨 [전략 2: 시간 기준] 1시간마다 스냅샷 생성 → 시간 기반 조회에 유리 [전략 3: 하이브리드] 100개 또는 1시간 중 먼저 도달하면 생성 → 둘 다 장점 취함

Part 5. 게임에서 어디에 써?

실제 게임에서 이벤트 소싱 쓰는 곳 있어?

모든 곳에 쓰진 않고, 추적이 중요한 곳에 써.

🎮 게임에서 이벤트 소싱 활용: 1️⃣ 재화 시스템 (골드, 캐시) → 모든 획득/소비 기록 → 핵/버그 추적 용이 → 롤백 요청 대응 2️⃣ 거래 시스템 → 모든 거래 이벤트 기록 → 사기 거래 추적 → 분쟁 해결 3️⃣ 전투 리플레이 → 모든 액션을 이벤트로 → 경기 다시보기 → e스포츠 판정 시비 4️⃣ 길드 히스토리 → 가입/탈퇴/강퇴 기록 → 기여도 변경 기록 → 분쟁 시 증거
모든 데이터에 쓰면 안 돼?

저장 공간이 많이 필요해.

위치 정보처럼 자주 바뀌는 건 상태 저장이 나아.

데이터 추천 방식 이유
재화 (골드/캐시) 이벤트 소싱 추적/롤백 필수
인벤토리 이벤트 소싱 아이템 히스토리 중요
캐릭터 위치 상태 저장 변경 빈번, 히스토리 불필요
HP/MP 상태 저장 초당 수십 번 변경

Part 6. 구현할 때 핵심 포인트

직접 구현하려면 뭘 알아야 해?

핵심 개념 3가지:

🔧 이벤트 소싱 핵심 구성: 1️⃣ 이벤트 (Event) - 과거형으로 명명: "GoldEarned", "ItemPurchased" - 불변(Immutable): 한번 저장하면 수정 불가 - 시간순 정렬: Sequence 번호 필수 2️⃣ 이벤트 스토어 (Event Store) - Append-only: 추가만 가능 - 빠른 조회: 집계(Aggregate) ID로 필터 3️⃣ 프로젝션 (Projection) - 이벤트 → 현재 상태 변환 - 읽기 최적화된 뷰 생성
// 이벤트 정의 struct GoldEarnedEvent { int characterId; int amount; string source; // "quest", "trade", "drop" time_t timestamp; }; // 이벤트 적용 (Projection) void Apply(GoldEarnedEvent e) { m_gold += e.amount; // 현재 상태에 반영 } // 리플레이 void Replay(vector<Event> events) { m_gold = 0; // 초기 상태 for (auto& e : events) Apply(e); // 모든 이벤트 재생 }

⚠️ 이벤트 소싱 주의사항

1. 이벤트 스키마 변경 - 과거 이벤트는 수정 불가, 버전 관리 필수

2. 저장 공간 - 이벤트가 계속 쌓임, 아카이빙 전략 필요

3. 복잡성 - 단순 CRUD보다 구현 복잡, 팀 학습 비용

4. 읽기 성능 - 스냅샷/프로젝션 없으면 느림

💡 이벤트 소싱과 잘 맞는 도구

• EventStoreDB - 이벤트 소싱 전용 DB

• Kafka - 이벤트 스트리밍 (대규모)

• Marten - PostgreSQL 기반 (.NET)

📝 핵심 정리

  • 상태 저장 = "현재 1000원", 이벤트 소싱 = "변경 기록 전체"
  • 은행 통장처럼 모든 입출금 기록 → 완벽한 히스토리
  • 시간 여행 가능: 특정 시점 상태 복원
  • 버그 재현: 이벤트 리플레이로 정확히 재현
  • 스냅샷으로 성능 최적화: 중간 상태 저장
