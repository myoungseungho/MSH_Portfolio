행 잠금이 갑자기 테이블 잠금으로?

Lock Escalation - 왜 갑자기 다른 쿼리가 느려지는가

Part 1. 이상한 현상

한 유저가 대량 작업하니까 갑자기 다른 유저들 쿼리가 다 느려졌어. 왜?

Lock Escalation 때문일 가능성이 높아.

Lock Escalation?

"잠금을 더 큰 단위로 업그레이드"하는 것.

행 잠금 → 페이지 잠금 → 테이블 잠금으로.

Row Lock
행 1개
→
Page Lock
8KB 페이지
→
Table Lock
전체 테이블!

Part 2. 왜 에스컬레이션이 일어나?

왜 행 잠금을 테이블 잠금으로 바꿔?

메모리 절약 때문이야.

[잠금도 메모리를 먹는다] 행 잠금 1개 ≈ 96바이트 메모리 5000개 행 잠금 = 96 × 5000 = 480KB 50000개 행 잠금 = 96 × 50000 = 4.8MB SQL Server: "이렇게 많은 잠금 관리 못해! 차라리 테이블 하나 잠그자." (96바이트)

에스컬레이션 발생 조건 (기본값):

• 5000개 이상의 행 잠금

• 또는 메모리 압박 상황

그럼 한 트랜잭션에서 5000행 이상 건드리면?

테이블 전체가 잠겨!

다른 모든 쿼리가 대기 상태가 돼.

Part 3. 게임에서 언제 이런 일이?

5000행 이상 건드리는 경우가 있어?

생각보다 많아:

상황 영향 행 수 위험도
일일 리셋 (전체 유저 접속 기록) 수만~수십만 매우 높음
만료된 메일 일괄 삭제 수천~수만 높음
랭킹 초기화 전체 유저 수 높음
이벤트 보상 일괄 지급 참여 유저 수 중간
단일 캐릭터 저장 1~10 낮음

⚠️ 실제 발생 시나리오

새벽 5시 일일 리셋 → 10만 행 UPDATE

→ Lock Escalation → TCharacter 테이블 잠금

→ 모든 유저 로그인/저장 멈춤!

Part 4. 어떻게 방지해?

에스컬레이션 안 일어나게 할 수 있어?

여러 방법이 있어:

방법 1: 배치 처리 (가장 권장)

-- 나쁜 예: 한 번에 10만 행 DELETE FROM TMail WHERE expiredate < GETDATE() -- 좋은 예: 1000개씩 나눠서 WHILE 1 = 1 BEGIN DELETE TOP (1000) FROM TMail WHERE expiredate < GETDATE() IF @@ROWCOUNT = 0 BREAK -- 잠깐 쉬어주기 (선택) WAITFOR DELAY '00:00:00.100' END

방법 2: ROWLOCK 힌트

-- 행 잠금 강제 (에스컬레이션 방지는 아님) UPDATE TCharacter WITH (ROWLOCK) SET level = @level WHERE charunique = @uid

방법 3: 테이블 옵션으로 에스컬레이션 비활성화

-- 특정 테이블에서 에스컬레이션 비활성화 ALTER TABLE TCharacter SET (LOCK_ESCALATION = DISABLE) -- 또는 파티션 단위로만 에스컬레이션 ALTER TABLE TCharacter SET (LOCK_ESCALATION = AUTO)

주의: 에스컬레이션 비활성화하면 메모리 사용량 급증할 수 있음!

Part 5. 우리 프로젝트 현황

우리는 어떻게 처리하고 있어?

분석 결과:

ROWLOCK 사용 예시

-- 캐릭터 저장 시 ROWLOCK 사용 UPDATE TCharacter WITH (ROWLOCK) SET level = @level, exp = @exp, ... WHERE charunique = @uid

현재 상태:

• 개별 저장: ROWLOCK 사용 ✅

• 배치 작업: 일부는 배치 처리 안 됨 ⚠️

개선이 필요한 부분은?

• 만료 메일 삭제 → 배치 처리 필요

• 랭킹 초기화 → 배치 처리 또는 서비스 중단 시간에

• 대량 UPDATE 프로시저 점검

Part 6. 에스컬레이션 감지하기

에스컬레이션이 일어났는지 어떻게 알아?

DMV(Dynamic Management View)로 확인할 수 있어.

-- 잠금 에스컬레이션 이벤트 확인 SELECT object_name(object_id) AS table_name, lock_escalation_desc, lock_escalation FROM sys.tables WHERE lock_escalation_desc <> 'TABLE' -- 현재 잠금 상태 확인 SELECT resource_type, resource_database_id, request_mode, request_status, COUNT(*) AS lock_count FROM sys.dm_tran_locks GROUP BY resource_type, resource_database_id, request_mode, request_status

핵심 정리

  • Lock Escalation = 행 잠금 → 테이블 잠금 자동 전환
  • 발생 조건: 약 5000개 이상 행 잠금 시
  • 문제: 테이블 전체 잠금 → 다른 모든 쿼리 대기
  • 해결책: 배치 처리 (1000개씩), ROWLOCK 힌트
  • 주의 상황: 일일 리셋, 만료 삭제, 랭킹 초기화
  • 우리 프로젝트: 개별 저장은 OK, 배치 작업 점검 필요
