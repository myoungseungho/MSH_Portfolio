Refactoring #11

Extract Class

클래스 추출 - 책임을 나누는 기술

클래스 추출이 뭐예요? 클래스를 왜 쪼개야 하죠?
하나의 클래스가 너무 많은 일을 할 때 일부 책임을 새 클래스로 분리하는 기법이에요.

예를 들어, 플레이어 클래스가 있는데 여기에 캐릭터 정보, 인벤토리 관리, 스킬 관리, 퀘스트 관리까지 전부 들어있다면? 그 클래스는 수천 줄짜리 괴물이 되겠죠.

🏢 비유: 1인 회사의 성장

처음엔 사장이 영업, 개발, 회계, 마케팅 다 했어요. 하지만 회사가 커지면? 각 부서를 만들어 전문가에게 맡기죠.

클래스도 마찬가지예요. 처음엔 하나로 시작하지만, 역할이 커지면 분리해야 관리가 가능해져요.
어떤 신호가 있으면 클래스를 쪼개야 한다고 알 수 있나요?
다음 신호들을 주의 깊게 봐야 해요:

1. 멤버 변수 그룹
특정 변수들끼리만 같이 사용된다면, 그들은 별도 클래스가 되고 싶어하는 거예요.

2. 메서드 그룹
일부 메서드들이 특정 변수들만 건드린다면? 그 메서드+변수 = 새 클래스 후보.

3. "그리고"로 설명되는 클래스
"이 클래스는 캐릭터 정보를 관리하고, 그리고 인벤토리를 관리하고, 그리고 스킬을 관리해요" → 쪼갤 시간!

4. 파일 크기
한 파일이 1000줄 이상? 거의 확실히 여러 책임이 섞여 있어요.
근데 클래스를 너무 잘게 쪼개면 오히려 복잡해지지 않나요?
좋은 질문이에요! 균형이 중요해요.

쪼개기의 목적은 각 클래스가 하나의 명확한 책임을 갖게 하는 거예요. "단일 책임 원칙(SRP)"이라고 하죠.

⚠️ 과도한 분리의 위험

나쁜 분리: 의미 없이 파일만 늘어남
예: GetName()만 있는 NameManager 클래스 → 과도함

좋은 분리: 각 클래스가 독립적으로 이해 가능
예: Player, Inventory, SkillManager → 각각 명확한 역할
판단 기준: "이 클래스만 보고 뭘 하는지 설명할 수 있는가?"
실무에서 클래스 추출은 어떻게 진행하나요?
단계별로 안전하게 진행해요:

1단계: 분리할 책임 식별
→ "인벤토리 관련 코드를 모두 찾아보자"

2단계: 새 클래스 생성
→ Inventory 클래스를 만들고, 관련 변수/메서드 이동

3단계: 원래 클래스에서 새 클래스 참조
→ Player가 Inventory 객체를 멤버로 가짐

4단계: 기존 호출부 수정
→ player.AddItem() → player.GetInventory().AddItem()

5단계: 테스트
→ 동작이 동일한지 확인

💡 핵심 포인트

한 번에 다 하려 하지 마세요. 하나의 책임씩 천천히 분리하면서 매번 테스트하세요.
추출한 클래스와 원래 클래스의 관계는 어떻게 되나요?
크게 두 가지 패턴이 있어요:

1. 컴포지션 (포함 관계)
Player가 Inventory를 가지고 있음 (has-a 관계)
가장 일반적이고 유연한 방식이에요.

2. 상속 관계로 발전
공통 부분을 부모 클래스로 추출 (is-a 관계)
예: Monster에서 공통 행동을 BaseMonster로 추출

대부분의 경우 컴포지션을 먼저 시도하세요. 상속보다 유연하고, 나중에 변경하기도 쉬워요.

📌 Extract Class 핵심 정리

  • 하나의 클래스가 여러 책임을 지면 분리 신호
  • "그리고"로 설명되는 클래스 = 분리 대상
  • 관련 변수+메서드를 함께 새 클래스로 이동
  • 컴포지션(포함 관계)을 먼저 고려
  • 한 번에 하나씩, 테스트하며 진행
