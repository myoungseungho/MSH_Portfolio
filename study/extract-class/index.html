Extract Class

클래스 추출 - 책임을 나누는 기술

Part 1. 클래스가 너무 커!

클래스 하나가 2000줄인데, 이거 정상이야?

아니, 비정상이야.

그 클래스가 너무 많은 일을 하고 있다는 신호야.

그럼 어떻게 해?

일부 책임을 새 클래스로 분리해.

Player 클래스에 인벤토리, 스킬, 퀘스트가 다 있으면? Inventory, SkillManager, QuestManager로 쪼개는 거야.

1인 회사 비유

처음엔 사장이 영업, 개발, 회계 다 했어.
회사가 커지면? 각 부서 만들어서 전문가 채용하잖아.

클래스도 마찬가지야. 역할이 커지면 분리해야 관리가 돼.

Part 2. 어떤 신호가 있으면 쪼개야 해?

클래스 쪼갤 타이밍을 어떻게 알아?

이런 신호들 봐:

Extract Class 신호들

1. 멤버 변수 그룹 - 특정 변수들끼리만 같이 쓰임
2. 메서드 그룹 - 일부 메서드가 특정 변수만 건드림
3. "그리고"로 설명 - "이 클래스는 A 하고, 그리고 B 하고, 그리고 C 해"
4. 파일 크기 - 1000줄 넘으면 거의 확실히 쪼갤 게 있어
"그리고"가 왜 문제야?

클래스를 한 문장으로 설명할 수 있어야 해.

"Player는 캐릭터 정보를 관리한다" ← Good

"Player는 캐릭터 정보를 관리하고, 그리고 인벤토리도 관리하고, 그리고 스킬도..." ← Bad

Part 3. 너무 잘게 쪼개면?

클래스 쪼개다가 너무 많아지면 오히려 복잡해지지 않아?

맞아, 균형이 필요해.

과도한 분리의 위험

나쁜 분리: GetName()만 있는 NameManager 클래스
→ 의미 없이 파일만 늘어남

좋은 분리: Player, Inventory, SkillManager
→ 각각 독립적으로 이해 가능
판단 기준이 뭐야?

"이 클래스만 보고 뭘 하는지 설명할 수 있어?"

Yes면 적절한 분리, No면 너무 잘게 쪼갠 거야.

Part 4. 실제로 어떻게 해?

클래스 추출 절차가 뭐야?

단계별로 안전하게 진행해:

Extract Class 절차

1단계: 분리할 책임 식별 → "인벤토리 관련 코드 찾기"
2단계: 새 클래스 생성 → Inventory 클래스 만들기
3단계: 관련 변수/메서드 이동
4단계: 원래 클래스에서 새 클래스 참조 → Player가 Inventory 멤버로 보유
5단계: 테스트
한번에 다 옮겨?

절대 아니야!

하나씩 옮기고, 매번 테스트해. 한번에 하면 뭐가 깨졌는지 모르잖아.

Part 5. 추출 후 관계는?

추출한 클래스랑 원래 클래스는 어떤 관계야?

크게 두 가지야:

클래스 관계

1. 컴포지션 (has-a): Player가 Inventory를 가지고 있음
→ 가장 일반적이고 유연한 방식

2. 상속 (is-a): 공통 부분을 부모로 추출
→ Monster에서 BaseMonster를 추출
뭘 먼저 써야 해?

컴포지션 먼저.

상속보다 유연하고, 나중에 바꾸기도 쉬워.

핵심 정리: Extract Class

  • 신호: 클래스가 "그리고"로 설명되면 쪼갤 때
  • 기준: 관련 변수+메서드를 함께 새 클래스로
  • 관계: 컴포지션(has-a)을 먼저 고려
  • 주의: 한 번에 하나씩, 매번 테스트
  • 판단: "클래스만 보고 설명 가능?"
