Refactoring #16

Split Loop

반복문 분리 - 한 루프에서 한 가지 일만

반복문 분리가 뭐예요?
하나의 반복문에서 여러 가지 일을 하고 있다면, 각각을 별도의 반복문으로 나누는 것이에요.

예를 들어, 하나의 for 루프 안에서 "총합 계산", "최댓값 찾기", "특정 조건 필터링"을 동시에 하고 있다면? 이걸 3개의 루프로 분리하는 거예요.
잠깐요, 그러면 루프를 3번 돌잖아요? 성능이 3배 나빠지는 거 아닌가요?
가장 많이 받는 질문이에요! 직관적으로 그렇게 느껴지죠.

하지만 현실은 다릅니다:

1. O(n) × 3 = O(n)
빅오 표기법에서 상수는 무시해요. 3번 돌든 1번 돌든 시간 복잡도는 같아요.

2. 실제 시간 차이는 미미
현대 CPU는 단순 반복에 엄청 최적화되어 있어요. 배열 100개를 3번 도는 건 밀리초도 안 걸려요.

3. 진짜 병목은 다른 곳
DB 조회, 네트워크 호출, 복잡한 계산이 성능의 99%를 잡아먹어요.

🏃 비유: 마라톤과 발걸음

마라톤에서 "발걸음을 1번 더 디뎠다"고 기록이 나빠질까요?

진짜 문제는 페이스 조절, 체력 관리, 코스 선택이에요.

코드도 마찬가지. 단순 루프 횟수보다 복잡한 연산, I/O가 문제예요.
그럼 왜 분리하는 게 좋은 건가요?
각 루프가 한 가지 일만 하면:

1. 이해하기 쉬움
"이 루프는 총합을 구한다"가 한눈에 보여요. 섞여 있으면 "이 루프가 뭘 하는 거지?" 읽어봐야 해요.

2. 테스트하기 쉬움
총합 계산 로직만 따로 검증할 수 있어요.

3. Extract Method 가능
분리된 루프는 바로 메서드로 추출할 수 있어요. CalculateTotal(), FindMax() 같은 명확한 함수로요.

4. 수정 영향 범위 축소
총합 계산 방식을 바꿔도 다른 로직에 영향 없어요.

💡 리팩토링의 목표

성능 최적화가 아니라 이해하기 쉬운 코드예요.

"루프 한 번에 다 한다"는 성급한 최적화의 전형이에요.
정말 성능이 중요한 상황에서는 어떻게 해요?
프로파일링 먼저!

올바른 순서:

1. 먼저 깨끗하고 이해하기 쉬운 코드로 작성
2. 성능 측정 (프로파일링)
3. 병목으로 확인된 곳만 최적화
4. 최적화해도 동작이 같은지 테스트

대부분의 경우, 분리된 루프가 병목이 되지 않아요. 진짜 병목은 DB 쿼리나 복잡한 알고리즘이죠.

⚠️ 예외: 진짜 성능이 중요할 때

- 초당 수백만 건 처리하는 실시간 시스템
- 메모리에 올라오지 않는 거대한 데이터셋
- 이미 프로파일링으로 병목 확인됨

이런 경우엔 주석으로 이유를 설명하고 합친 루프를 유지하세요.
분리 절차는 어떻게 되나요?
단계별로 안전하게:

1단계: 루프 복사
→ 원본 루프를 그대로 복사해서 아래에 붙여넣기

2단계: 각 루프에서 중복 제거
→ 첫 번째 루프에서 "총합 계산" 외의 코드 삭제
→ 두 번째 루프에서 "최댓값" 외의 코드 삭제

3단계: 테스트
→ 결과가 동일한지 확인

4단계: (선택) Extract Method
→ 각 루프를 의미 있는 함수로 추출

핵심은 한 번에 하나씩, 테스트하면서예요.

📌 Split Loop 핵심 정리

  • 하나의 루프가 여러 일을 하면 분리
  • O(n)×3 = O(n), 실제 성능 차이는 미미
  • 이해, 테스트, 수정이 모두 쉬워짐
  • 분리 후 Extract Method로 의미 있는 함수 생성
  • 성능 문제는 프로파일링으로 확인 후 판단
