Split Loop

반복문 분리 - 한 루프에서 한 가지 일만

Part 1. 반복문 분리가 뭐야?

하나의 for 루프에서 여러 가지 일 하면 안 돼?

가능은 하지만, 각각 분리하면 더 좋아.

총합 계산, 최댓값 찾기, 필터링을 한 루프에서? 3개로 나눠.

루프 3번 돌면 느려지지 않아?

가장 흔한 오해야. 현실은 달라:

O(n) × 3 = O(n). 상수는 무시해.

진짜 병목은 DB 조회, 네트워크야. 단순 루프 아니야.

마라톤 비유

마라톤에서 "발걸음 하나 더 디뎠다"고 기록이 나빠져?
진짜 문제는 페이스, 체력, 코스야.

코드도 마찬가지. 단순 루프 횟수보다 복잡한 연산, I/O가 문제야.

Part 2. 왜 분리하는 게 좋아?

성능 차이 없으면 왜 굳이?

가독성과 유지보수 때문이야:

분리의 장점

1. 이해하기 쉬움 - "이 루프는 총합 구한다" 한눈에 보여
2. 테스트 쉬움 - 총합 계산 로직만 따로 검증 가능
3. Extract Method 가능 - CalculateTotal(), FindMax()로 추출
4. 수정 영향 축소 - 총합 로직 바꿔도 다른 건 안 건드려
그냥 한번에 하는 게 효율적이지 않아?

그건 성급한 최적화야.

먼저 읽기 좋은 코드 만들고, 정말 느리면 그때 합쳐.

Part 3. 정말 성능이 중요할 때는?

진짜 느린 경우는 어떻게 해?

프로파일링 먼저!

올바른 순서

1. 깨끗하고 이해하기 쉬운 코드로 작성
2. 성능 측정 (프로파일링)
3. 병목으로 확인된 곳만 최적화
4. 최적화해도 동작 같은지 테스트
예외: 진짜 성능이 중요할 때

- 초당 수백만 건 처리하는 실시간 시스템
- 메모리에 못 올리는 거대한 데이터셋
- 이미 프로파일링으로 병목 확인됨

이런 경우엔 주석으로 이유 설명하고 합쳐.

Part 4. 분리 절차

어떻게 분리해?

단계별로 안전하게:

Split Loop 절차

1단계: 루프 복사 - 원본 그대로 아래에 붙여넣기
2단계: 중복 제거 - 첫 루프에서 총합 외 삭제, 둘째에서 최댓값 외 삭제
3단계: 테스트 - 결과 동일한지 확인
4단계: (선택) Extract Method - 각 루프를 의미 있는 함수로
한번에 막 바꾸면 안 돼?

절대 안 돼.

하나씩 바꾸고, 매번 테스트. 뭐가 깨졌는지 알아야지.

핵심 정리: Split Loop

  • 원칙: 하나의 루프가 여러 일 하면 분리
  • 성능: O(n)×3 = O(n), 실제 차이는 미미
  • 장점: 이해, 테스트, 수정 모두 쉬워짐
  • 후속: 분리 후 Extract Method로 함수화
  • 판단: 성능 문제는 프로파일링으로 확인
