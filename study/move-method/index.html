Refactoring #13

Move Method

메서드 이동 - 책임을 올바른 위치로

메서드 이동이 뭐예요? 왜 메서드 위치를 바꿔야 하죠?
메서드를 다른 클래스로 옮기는 것이에요. 메서드가 현재 클래스보다 다른 클래스의 데이터를 더 많이 사용한다면, 그 클래스로 이동해야 해요.

왜냐하면, 메서드는 자신이 다루는 데이터와 가까이 있어야 코드가 응집력 있고 이해하기 쉬워지거든요.

🏠 비유: 주방 도구의 위치

프라이팬은 주방에 있어야 하잖아요? 거실에 두면 매번 요리할 때마다 거실로 가서 가져와야 하죠.

메서드도 마찬가지예요. 주로 사용하는 데이터가 있는 클래스에 두는 게 자연스러워요.
어떤 신호를 보고 메서드를 이동해야 하는지 알 수 있나요?
"기능 편애(Feature Envy)" 코드 스멜을 찾으세요!

이건 메서드가 자기 클래스보다 다른 클래스에 더 관심을 보이는 상황이에요.

판별 방법:

1. 메서드 안에서 다른 객체의 getter를 여러 번 호출
2. 자기 클래스의 멤버보다 다른 클래스의 멤버를 더 많이 참조
3. 계산에 필요한 데이터가 대부분 다른 클래스에 있음

이런 신호가 보이면? 그 메서드는 이사 가고 싶어하는 거예요!
구체적인 예시로 설명해주세요.
Order 클래스에 있는 메서드가 이렇다고 해봐요:

"주문의 배송비를 계산한다. 이때 고객의 등급, 고객의 지역, 고객의 멤버십 여부를 확인한다."

이 메서드가 Order보다 Customer의 데이터를 더 많이 쓰죠?

그러면 이 메서드는 Customer 클래스로 이동하는 게 자연스러워요.

이동 후: Order가 customer.CalculateShippingFee(this)를 호출하면 됩니다.

💡 핵심 질문

"이 메서드가 주로 누구의 데이터를 다루는가?"

답이 "다른 클래스"라면, 그 클래스로 옮기세요.
메서드 이동은 어떤 순서로 진행하나요?
안전한 이동 절차:

1단계: 대상 클래스 결정
→ 메서드가 가장 많이 사용하는 데이터가 어디 있는지 확인

2단계: 메서드를 대상 클래스에 복사
→ 일단 양쪽 모두에 존재하게 함

3단계: 원본 클래스 참조 처리
→ 원본 클래스의 데이터가 필요하면 파라미터로 전달

4단계: 기존 메서드를 위임으로 변경
→ 원래 위치에서 새 위치의 메서드 호출하도록 수정

5단계: 테스트
6단계: 호출부 수정
→ 모든 호출을 새 위치로 변경

7단계: 원본 메서드 삭제
이동하면 안 되는 경우도 있나요?
네, 몇 가지 상황에서는 주의가 필요해요:

1. 다형성이 필요한 경우
오버라이드되는 메서드라면, 클래스 계층 구조를 고려해야 해요.

2. 순환 의존성 발생
A → B로 메서드를 옮겼는데, B가 다시 A를 참조하게 되면 문제.

3. 캡슐화 위반
이동 후 private 멤버에 접근해야 한다면 설계를 다시 생각해봐야 해요.

⚠️ 이동 전 체크리스트

- 이동 후에도 원래 클래스의 응집력이 유지되는가?
- 순환 참조가 생기지 않는가?
- public 인터페이스만 사용하는가?
Move Method와 Extract Class는 어떤 관계예요?
둘은 자주 함께 사용돼요!

시나리오:

1. 클래스 A에 너무 많은 책임이 있음
2. 일부 메서드들이 특정 변수 그룹만 사용함을 발견
3. Extract Class로 새 클래스 B 생성
4. Move Method로 관련 메서드들을 B로 이동

이 두 기법의 조합으로 책임이 분명한 작은 클래스들을 만들 수 있어요.

💡 리팩토링의 시너지

Extract Class = 새 집을 짓고
Move Method = 그 집에 가구를 배치하는 것

둘을 함께 사용해서 깔끔한 구조를 만드세요.

📌 Move Method 핵심 정리

  • 메서드는 자신이 다루는 데이터와 가까이 있어야 함
  • Feature Envy = 다른 클래스 데이터를 더 많이 사용
  • 이동 전 위임으로 바꾸고, 테스트 후 삭제
  • 순환 의존성과 캡슐화 위반 주의
  • Extract Class와 함께 사용하면 효과적
