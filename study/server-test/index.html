게임 서버 테스트 작성하기

서버 테스트 기초부터 통합 테스트, 병렬 테스트까지

Part 1. 서버 테스트가 뭐야?

서버 테스트? QA가 하는 거 아니야?

서버 테스트는 코드로 서버가 제대로 동작하는지 확인하는 거야.

사람(QA)이 직접 하는 게 아니라, 자동으로 실행돼!

비유: 자동 검수 라인

공장에서 제품 만들면 검수 라인 거치잖아?
- 사람이 하나하나 확인? → 느리고 실수 있음
- 기계가 자동 검수? → 빠르고 정확함

서버 테스트도 똑같아:
- 코드 바꿀 때마다 자동으로 검사
- "아이템 획득이 잘 되나?" 자동 확인!
왜 필요해?

실제 시나리오:

[테스트 없을 때] 개발자: "인벤토리 코드 살짝 수정했어" ↓ 빌드 & 배포 ↓ 라이브 서버 적용 ↓ 유저: "아이템이 사라졌어요!!" ↓ 긴급 점검... 보상... [테스트 있을 때] 개발자: "인벤토리 코드 살짝 수정했어" ↓ 자동 테스트 실행 ↓ 테스트 실패: "아이템 저장 테스트 실패!" ↓ 개발자: "아, 여기 버그 있네. 고치자." ↓ 다시 테스트 → 통과 → 안전하게 배포!

Part 2. 테스트 종류 이해하기

테스트 종류가 여러 개야?

크게 3가지:

[테스트 피라미드] /\ / \ E2E 테스트 / \ (전체 시스템) /------\ / \ 통합 테스트 / \ (여러 모듈 연동) /------------\ / \ 유닛 테스트 /________________\ (함수 하나)
종류 무엇을 테스트? 예시 속도
유닛 테스트 함수 하나 데미지 계산 함수 빠름
통합 테스트 여러 모듈 연동 전투 → 아이템 드롭 → 인벤토리 보통
E2E 테스트 전체 시스템 클라이언트 → 서버 → DB 느림
일반적으로 어떤 비율이야?

보통은 유닛 테스트가 제일 많아. 빠르고 작성하기 쉬우니까.

E2E (적음)
통합 (중간)
유닛 (많음)

Part 3. 게임 서버는 좀 달라!

게임 서버도 유닛 테스트 위주로 하면 돼?

게임 서버는 다를 수 있어!

달빛조각사 사례: 통합 테스트가 90%!

[달빛조각사의 테스트 피라미드] 일반적인 피라미드: 달빛조각사: /\ \------------/ / \ E2E \ 통합 90% / /----\ \--------/ / \ 통합 \ 유닛 / /--------\ \----/ / 유닛 \ \/ 피라미드가 뒤집혔다!
왜 통합 테스트가 많아?

게임 서버의 특성 때문이야:

일반 서버 게임 서버
상태가 단순 상태가 복잡 (캐릭터, 인벤, 퀘스트, 버프...)
기능이 독립적 기능이 연결됨 (전투→드롭→인벤→퀘스트)
함수 단위로 검증 가능 시나리오 단위로 검증해야 함
비유: 자동차 테스트

- 바퀴만 테스트해서 자동차가 잘 달릴까? ❌
- 엔진 + 바퀴 + 핸들 + 브레이크 다 연결해서 테스트해야 함 ✓

게임 서버도 마찬가지:
- "데미지 계산 함수"만 테스트? 부족함
- "공격 → 데미지 → HP 감소 → 사망 → 아이템 드롭" 전체 테스트!
핵심 교훈

"통합 테스트부터 시작해도 괜찮다!"

테스트가 막막하고, 빠르게 효과를 느끼고 싶다면
유저 시나리오 기반의 통합 테스트부터 시작하는 게 좋아.

Part 4. 통합 테스트 작성하기

통합 테스트는 어떻게 작성해?

스토리 기반으로 작성해!

유저가 실제로 하는 행동을 그대로 코드로 옮겨.

[스토리 기반 테스트 예시] 테스트 이름: "캐릭터 보관함 테스트" 시나리오: 1. 캐릭터 보관함 설치 2. 아이템 생성해서 보관함에 넣기 3. 재접속 (DB 저장 확인) 4. 보관함에 아이템이 있는지 확인 ✓ 5. 다른 캐릭터로 접속 6. 보관함이 비어있는지 확인 ✓ (캐릭터별 분리)
# 테스트 코드 예시 (의사 코드) def test_character_storage(): # 1. 보관함 설치 setup_character_storage() # 2. 아이템 넣기 item = create_item(id=1001, count=10) store_item(item) # 3. 검증: 보관함에 있는지 assert item_in_storage(item) # 4. 재접속 (DB 저장 테스트) reconnect() assert item_in_storage(item) # DB에서 잘 불러왔나? # 5. 다른 캐릭터로 접속 switch_to_another_character() # 6. 보관함 비어있어야 함 (캐릭터별 분리) assert storage_is_empty()
버그 발생하면 어떻게 해?

버그 재현 테스트를 먼저 작성해!

[버그 재현 테스트 순서] 1. 버그 신고 들어옴 "존 이동하면 가끔 실패해요" 2. 버그를 재현하는 테스트 작성 (아직 테스트는 실패 상태) 3. 테스트 실행 → 실패 확인! "재현 성공!" 4. 버그 수정 5. 테스트 실행 → 성공! "버그 수정 완료!" 6. 이제 이 테스트가 회귀 테스트가 됨 → 같은 버그 다시 발생하면 테스트가 잡아줌!
# 버그 재현 테스트 예시 def test_zone_transfer_bug(): """ 버그: 채널 파괴 중 캐릭터 입장 시 실패 재현 조건: 채널 유예기간을 0으로 설정 """ # 캐릭터 2개 생성 char1, char2 = create_characters(2) # 채널 즉시 파괴되도록 설정 set_channel_destroy_delay(0) # 100번 반복 시도 (간헐적 버그니까) for _ in range(100): portal(char1, zone2) portal(char2, zone1) # 이동 성공했는지 확인 assert char1.current_zone == zone2 assert char2.current_zone == zone1
달빛조각사 결과

100번 정도 시도하니 버그 재현 성공!
통합 테스트 환경이라 손쉽게 재현 → 빠른 버그 수정!

Part 5. 가끔 깨지는 테스트 (Flaky Test)

테스트가 가끔만 실패해. 왜 그래?

Flaky Test - 같은 코드인데 때때로 성공, 때때로 실패!

제일 짜증나는 유형이야.

[Flaky Test 원인들] 1. 타이밍 이슈 - 비동기 처리가 끝나기 전에 검증 - 네트워크 지연 2. 테스트 간 의존성 - A 테스트 결과가 B 테스트에 영향 3. 랜덤 요소 - 확률 기반 로직 4. 패킷 순서 문제 ← 게임 서버에서 자주 발생! - 예상과 다른 순서로 패킷 도착
패킷 순서 문제가 뭐야?

예시:

[문제 상황] 테스트: 도트 데미지 버프 걸고 공격 기대: 1. 버프 패킷 2. 공격 데미지 패킷 실제 (가끔): 1. 공격 데미지 패킷 ← 순서 바뀜! 2. 버프 패킷 → 테스트가 "버프 패킷 먼저 와야 해!" 라고 했으면 실패!
어떻게 해결해?

패킷 매처를 사용해 순서에 상관없이 처리:

# 나쁜 예 - 순서에 의존 wait_packet(:attack_damage) wait_packet(:dot_damage) # 순서 바뀌면 실패! # 좋은 예 - 패킷 매처 리스트 wait_packets([ :attack_damage, :dot_damage ]) # 순서 상관없이 둘 다 오면 성공!
시간 기다리는 건 어떻게 해?

Eventually 패턴을 사용해:

# 나쁜 예 - 하드코딩된 대기 sleep(5000) # 5초 기다리기 (너무 길면 느림, 짧으면 가끔 실패) assert char.hp < 100 # 좋은 예 - Eventually 패턴 eventually(timeout=5000, interval=100): assert char.hp < 100 # 동작: # - 100ms마다 조건 체크 # - 성공하면 바로 통과 (불필요한 대기 없음!) # - 5초 안에 안 되면 실패
Flaky Test 해결 3가지

1. 패킷 매처 - 순서에 상관없이 패킷 매칭
2. Eventually 패턴 - 조건 만족할 때까지 폴링
3. 테스트 격리 - 테스트 간 상태 공유 제거

Part 6. 병렬 테스트로 속도 높이기

테스트가 1시간 걸려. 어떻게 줄여?

병렬 테스트로 동시에 여러 개 실행!

[순차 vs 병렬] 순차 실행: 테스트A(10초) → 테스트B(10초) → 테스트C(10초) = 30초 병렬 실행: 테스트A(10초) | 테스트B(10초) | = 10초 (동시 실행!) 테스트C(10초) |
달빛조각사는 얼마나 줄였어?

테스트 1,400개 기준:

방식 시간
순차 테스트 1시간
병렬 테스트 30분 (50% 감소)
목표 10분대
병렬로 바꾸면 뭐가 문제야?

공유 자원 충돌!

[문제 상황] 테스트A: 몬스터 HP를 100으로 설정 테스트B: 몬스터 HP를 50으로 설정 동시 실행: 테스트A: HP = 100 설정 → 테스트B: HP = 50 설정 → 테스트A: HP 확인... 50?! 실패! → 같은 데이터를 수정해서 충돌!
절대 하면 안 되는 것!

게임 테이블 데이터를 테스트에서 수정하지 마라!

몬스터 테이블, 아이템 테이블, 스킬 테이블 등은
모든 테스트가 공유하는 읽기 전용이어야 해.

달빛조각사 발표자 曰: "수정하는 건 정말 안 좋은 결정이었습니다"
그럼 어떻게 해?

테스트용 데이터를 새로 추가!

# 나쁜 예 - 기존 데이터 수정 monster_table[1001].hp = 100 # 다른 테스트에 영향! # 좋은 예 - 새로운 데이터 추가 test_monster_id = generate_unique_id() # 테스트용 새 ID create_test_monster(id=test_monster_id, hp=100) # 격리됨!
핵심 조언 3가지 (달빛조각사)

1. 통합 테스트부터 시작해도 괜찮다
게임은 시나리오 검증이 중요하니까

2. 게임 테이블 데이터를 절대 수정하지 마라
추가만 허용, 공유 자원 충돌 방지

3. 처음부터 병렬 테스트로 설계하라
나중에 바꾸기 매우 힘들어!

Part 7. 테스트 문화 정착하기

팀에서 테스트 안 짜려고 해. 어떻게 해?

3가지가 필요해:

[테스트 문화 정착 3요소] 1. 구성원의 동의 └─ "테스트가 버그를 잡는 걸 눈으로 보여주기" └─ 성공 경험이 쌓여야 자발적으로 작성 2. 쉬운 테스트 환경 └─ 브랜치 푸시 → 자동으로 테스트 실행 └─ PR 머지하면 마스터에서도 테스트 실행 3. 자동 알림 └─ Slack 봇으로 실패 즉시 알림 └─ "@홍길동님, test_quest 실패했어요" └─ 이메일은 눈에 안 들어옴!
규칙은 어떻게 정해?

규칙은 딱 하나!

"테스트를 깨면 반드시 고쳐야 한다"

테스트 추가 규칙은 없음. 느슨한 규칙이지만 코드 리뷰가 역할을 함.

결과: 월드 서버 테스트 커버리지 64% 달성!

핵심 정리

  • 서버 테스트 - 코드로 서버 동작을 자동 검증
  • 게임 서버 - 통합 테스트가 더 효과적 (시스템 간 연동이 핵심)
  • 스토리 기반 - 유저 시나리오를 그대로 테스트 코드로
  • 버그 재현 - 버그 발생 → 테스트 작성 → 수정 → 회귀 테스트
  • Flaky Test - 패킷 매처 + Eventually 패턴으로 해결
  • 병렬 테스트 - 처음부터 설계! 공유 자원 수정 금지!
  • 문화 정착 - 성공 경험 + 쉬운 환경 + 자동 알림
