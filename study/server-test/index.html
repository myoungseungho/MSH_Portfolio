1. 달빛조각사 서버 테스트 특징

달빛조각사 서버의 기술 스택은 뭐야?

서버: Elixir (엘릭서) - 함수형 언어, Erlang VM 위에서 동작

클라이언트: Unity

Elixir는 동시성과 분산 처리에 강한 언어야.

왜 Elixir로 게임 서버를 만들었을까?

Erlang VM의 Actor 모델이 게임 서버에 적합해.

  • 각 플레이어가 독립적인 프로세스
  • 한 프로세스가 죽어도 다른 프로세스에 영향 없음
  • 메시지 패싱 기반 통신
서버 테스트를 시작하려면 뭐부터 해야 해?

초반에 필요한 3가지:

  1. 구성원 동의 - 테스트 문화에 대한 팀의 합의
  2. 테스트 환경 구축 - CI/CD 파이프라인
  3. 주요 로직 테스트 - 서버 접속 후 사냥 같은 필수 컨텐츠

Elixir + Unity 조합의 MMORPG

발표자 왈: "혹시나 그림이 불안해 보이신다면 기분 탓이라고 얘기하고 싶네요"

왜 통합 테스트가 90%나 될까?

게임 서버의 특성 때문이야:

  • 상태(State)가 복잡해 - 캐릭터, 인벤토리, 퀘스트, 버프 등
  • 여러 시스템이 상호작용해 - 전투 - 아이템 드롭 - 인벤토리
  • 단위 테스트만으로는 시스템 간 연동을 검증 못해
단위 테스트가 적은 게 문제가 아닐까?

게임 서버에서는 "함수 하나가 잘 동작하는지"보다 "시나리오가 잘 동작하는지"가 더 중요해.

예: "아이템을 장착하면 스탯이 오른다"는 여러 시스템이 연동되어야 검증 가능.

핵심

게임 서버 = 상태 머신의 집합체

단위 테스트로 검증하기 어려운 시스템 간 상호작용이 많음

따라서 통합 테스트 중심이 더 효과적

구성원 동의는 어떻게 얻어?
  • 테스트가 버그를 잡는 걸 눈으로 보여주기
  • "이 테스트 덕분에 라이브 버그를 막았어요"
  • 성공 경험이 쌓여야 자발적으로 작성함
환경 구축은 어떻게 해?

2. 쉽게 테스트 돌릴 수 있는 환경

  1. 피처 브랜치 워크플로 - 마스터에 직접 커밋 안 함
  2. 브랜치 푸시 - 코드 포맷팅 검사 + 정적 분석 자동 실행
  3. 코드 리뷰 - 리뷰어가 머지 버튼을 누름

실패를 숨기지 않고 공개하면 빠르게 대응할 수 있어.

테스트 추가 규칙이 있어?
규칙은 딱 하나

"테스트를 깨면 반드시 고쳐야 한다"

테스트 추가 규칙은 없음. 느슨한 규칙이지만 코드 리뷰가 큰 역할을 함.

  • 코드 리뷰를 통해 테스트 짜는 방법이 자연스럽게 전파됨
  • "리뷰 받으면서 좋은 거라고 약도 많이 쳤다"
  • 결과: 월드 서버 테스트 커버리지 64% 달성
테스트 문화 정착 3요소

1. 구성원 동의 - 성공 경험으로 납득시키기

2. 환경 구축 - 쉽게 돌릴 수 있어야 함

3. 자동 알림 - Slack 봇으로 실패 즉시 공유

4. 통합 테스트 작성 방법

통합 테스트는 어떤 형태로 작성해?

스토리 기반으로 작성해.

유저가 실제로 하는 행동 시나리오를 그대로 테스트 코드로 옮겨.

테스트 경험이 적을 때 "뭘 테스트해야 하지?" 막막함을 느낀다면, 클라이언트를 흉내내서 게임 컨텐츠를 테스트하는 스토리를 작성하면 좋은 가이드라인이 됨.

스토리 기반 테스트 예시는?

캐릭터 보관함 테스트 스토리:

  1. 캐릭터 보관함 설치
  2. 아이템 생성해서 보관함에 넣기
  3. DB 저장 확인을 위해 재접속
  4. 같은 계정 다른 캐릭터로 접속하기
  5. 보관함이 비어 있는 걸 확인하기 (캐릭터별 분리 확인)
# 캐릭터 보관함 설치하고 아이템 보관 setup_character_storage() item = create_storable_item() store_item(item) assert item_in_storage(item) # DB 저장 확인을 위해 재접속 reconnect() assert item_in_storage(item) # 같은 계정 다른 캐릭터로 접속 switch_character() assert storage_is_empty() # 캐릭터별 분리 확인
버그 재현 테스트는 뭐야?

라이브에서 발생한 버그를 테스트로 재현하는 것.

  • 버그 리포트 받으면, 먼저 그 버그를 재현하는 테스트 작성
  • 테스트가 실패하는 걸 확인
  • 버그 수정
  • 테스트가 통과하는 걸 확인

이러면 같은 버그가 다시 발생하면 테스트가 잡아줘.

버그 재현 테스트 예시는?

실제 사례: 존 이동 시 간헐적으로 실패하는 버그

  • 재현 조건 모름, 발생 빈도 낮음 - "환장하는 버그"
  • 가설: 채널 파괴 중에 캐릭터가 입장하면 발생
# 캐릭터 2개 생성 char1, char2 = create_characters(2) # 채널 유예기간을 없애서 즉시 파괴되게 설정 set_channel_destroy_delay(0) # 두 캐릭터가 서로의 존으로 100번 이동 for _ in range(100): portal(char1, zone2) portal(char2, zone1) assert char1.current_zone == zone2 # 여기서 실패하면 버그 재현!
결과

100번 정도 시도하니 재현됨 - 통합 테스트 기반이라 손쉽게 재현해서 버그 수정!

통합 테스트 작성 원칙

1. 스토리 기반 - 유저 시나리오를 그대로 코드로

2. 버그 재현 - 버그 리포트 - 테스트 - 수정 - 회귀 테스트

3. 패킷 주고받으며 테스트 - 실제 클라이언트처럼 동작

4. DB 저장 검증 - 테스트 DB에 직접 접근해서 확인

5. 가끔 깨지는 테스트 해결

"가끔 깨지는 테스트"가 뭐야?

Flaky Test - 같은 코드인데 때때로 성공, 때때로 실패하는 테스트.

가장 짜증나는 유형의 테스트야.

왜 가끔 깨질까?
  • 타이밍 이슈 - 비동기 처리 완료 전에 검증
  • 테스트 간 의존성 - A 테스트가 B 테스트에 영향
  • 랜덤 요소 - 확률 기반 로직
  • 패킷 순서 문제 - 예상과 다른 순서로 패킷이 도착
패킷 순서 문제는 어떻게 해결해?

문제 상황:

  • 도트 데미지 버프를 걸고 - 공격
  • 공격 패킷이 빨리 처리되면: 공격 패킷 먼저
  • 지연이 생기면: 도트 데미지 패킷 먼저
  • - 가끔 깨지는 테스트

해결: 패킷 매처

  • 패킷을 순서에 상관없이 처리하도록 변경
  • 패킷 매처를 리스트로 구성
  • 조합 가능한 패킷 매처 설계
# 나쁜 예 - 순서에 의존 wait_packet(:attack_damage) wait_packet(:dot_damage) # 순서 바뀌면 실패! # 좋은 예 - 패킷 매처 리스트 wait_packets([ :attack_damage, :dot_damage ]) # 순서 상관없이 둘 다 오면 성공
Eventually 패턴이란?

"언젠가는 조건이 만족될 것"을 기다리는 패턴.

문제: 응답 패킷이 따로 없거나 DB 싱크처럼 약간의 지연이 있는 경우

  • 하드코딩된 시간: 넉넉하면 느려지고, 빡빡하면 가끔 깨짐
# Eventually 패턴 eventually(timeout=5000, interval=100): assert char.hp < 100 # HP가 100 미만이 될 때까지 반복 체크 # 장점 # - 총 시간을 넉넉하게 둬서 가끔 깨지는 문제 방지 # - 성공하면 바로 성공 처리 - 불필요한 대기 없음
Flaky Test 해결 방법

1. 패킷 매처 - 순서에 상관없이 패킷 매칭

2. Eventually 패턴 - 조건 만족 시까지 폴링

3. 테스트 격리 - 테스트 간 상태 공유 제거

6. 병렬 테스트 전환 주의점

병렬 테스트가 뭐야?

여러 테스트를 동시에 실행해서 전체 테스트 시간을 줄이는 것.

순차 실행: 테스트A(10초) - 테스트B(10초) - 테스트C(10초) = 30초 병렬 실행: 테스트A | 테스트B | 테스트C = 10초 (동시 실행)
왜 병렬 테스트가 필요했어?

예: 몬스터 테이블, 아이템 테이블, 스킬 테이블 등

이 데이터는 모든 테스트가 공유하는 읽기 전용이어야 해.

"수정하는 건 정말 안 좋은 결정이었습니다"

그러면 어떻게 해야 해?

올바른 방식: 게임 데이터를 추가

  • 타입 ID 자동 발급 - 테스트용 새로운 ID
  • 가장 오래된 데이터를 복사
  • 인자로 받은 값으로 덮어쓰기
# 나쁜 예 - 기존 데이터 수정 monster_table[1001].hp = 100 # 다른 테스트에 영향! # 좋은 예 - 새로운 데이터 추가 test_monster_id = generate_test_id() create_test_monster(id=test_monster_id, hp=100) # 격리됨

총정리: 달빛조각사 서버 테스트

기술 스택

  • 서버: Elixir (Actor 모델, 함수형)
  • 클라이언트: Unity

테스트 비율

통합 테스트: 90% 단위 테스트: 10% 미만 E2E 테스트: 거의 없음 -> 게임 서버는 시스템 간 상호작용이 핵심 -> 단위 테스트보다 통합 테스트가 더 효과적 -> 월드 서버 테스트 커버리지 64% 달성

핵심 조언 3가지
