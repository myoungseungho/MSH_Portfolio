에셋 쿠킹 (Asset Cooking)

에디터 포맷에서 런타임 최적화 포맷으로의 변환 파이프라인

Part 1. 개념 - 에셋 쿠킹이란?

에셋 쿠킹이 정확히 뭐야?

에셋 쿠킹(Asset Cooking)은 개발 중에 사용하는 소스 에셋을 타겟 플랫폼의 런타임에서 최적으로 로드할 수 있는 형태로 변환하는 과정이야.

요리에 비유하면:

  • 소스 에셋 = 재료 (PSD, FBX, WAV 등 원본 포맷)
  • 쿠킹 = 조리 과정 (압축, 변환, 최적화)
  • 쿠킹된 에셋 = 완성된 요리 (DDS, 런타임 메시, OGG 등)

에디터에서 보는 에셋이랑 게임에서 쓰는 에셋이 다르다는 거야?

맞아. 완전히 다른 형태야. 핵심 차이점을 보자:

특성 소스 에셋 (개발용) 쿠킹된 에셋 (런타임용)
포맷 범용 포맷 (PSD, FBX, WAV) 플랫폼 최적화 포맷
크기 크다 (무손실, 고품질) 작다 (압축, 최적화)
로드 속도 느림 (파싱 필요) 빠름 (즉시 사용 가능)
편집 가능 가능 (레이어, 히스토리) 불가능 (평탄화됨)
메타데이터 풍부 (작업 정보) 최소 (런타임 필수만)
// 텍스처 예시: 소스 vs 쿠킹된 에셋 // 소스 에셋 (개발 중) character_diffuse.psd ├── 크기: 256MB ├── 레이어: 47개 ├── 해상도: 8192x8192 ├── 채널: 32비트 RGBA + Alpha └── 압축: 없음 // 쿠킹된 에셋 (PC 빌드) character_diffuse.dds ├── 크기: 16MB ├── 레이어: 1개 (평탄화) ├── 해상도: 4096x4096 (다운스케일) ├── 포맷: BC7 (GPU 압축) └── 밉맵: 13단계 포함 // 쿠킹된 에셋 (모바일 빌드) character_diffuse.astc ├── 크기: 8MB ├── 해상도: 2048x2048 ├── 포맷: ASTC 6x6 └── 밉맵: 12단계 포함
그럼 에디터에서 게임 실행할 때는 어떻게 되는 거야?

에디터에서는 두 가지 방식이 있어:

1. 온디맨드 쿠킹 (On-Demand Cooking)

  • 에셋이 필요할 때 그 순간에 쿠킹
  • 첫 로드 시 느리지만, 캐시되어 이후 빠름
  • Unity의 기본 방식

2. DDC (Derived Data Cache)

  • 미리 쿠킹된 결과를 캐시에 저장
  • 팀 공유 캐시 서버 사용 가능
  • Unreal Engine의 방식

Part 2. 왜 필요해?

그냥 원본 에셋 쓰면 안 돼?

절대 안 돼! 원본 에셋을 그대로 쓰면 발생하는 문제들:

원본 에셋 사용 시 문제점

1. 파일 크기 폭발

  • PSD 하나가 수백 MB
  • AAA 게임 설치 크기가 TB 단위로 증가

2. 로드 시간 급증

  • FBX 파싱에 수 초 소요
  • WAV → PCM 변환 필요

3. GPU 비호환

  • GPU는 PNG를 직접 읽지 못함
  • 런타임에서 변환 → 메모리 2배 + 시간 낭비

4. 플랫폼 비호환

  • 모바일은 ASTC/ETC2만 지원
  • 콘솔마다 최적 포맷이 다름
// 실제 프로젝트 크기 비교 (AAA 타이틀 예시) 소스 에셋 (개발 리포지토리) ├── Textures/ 2.8 TB (PSD, TGA, 16bit) ├── Models/ 800 GB (FBX, Maya) ├── Audio/ 400 GB (WAV, AIFF) ├── Animations/ 200 GB (Maya, MotionBuilder) └── Total: 4.2 TB 쿠킹된 에셋 (PC 빌드) ├── Textures/ 80 GB (BC7, BC5) ├── Models/ 25 GB (최적화 메시) ├── Audio/ 30 GB (Opus, ADPCM) ├── Animations/ 15 GB (압축 커브) └── Total: 150 GB // 압축률: 96.4% (4.2TB → 150GB)
쿠킹의 구체적인 이점이 뭐야?

쿠킹이 제공하는 핵심 이점들:

1. 로드 시간 최소화

  • 바이너리 포맷 → 파싱 불필요
  • GPU 네이티브 포맷 → 직접 업로드
  • 로드 시간 10~100배 감소
// 텍스처 로드 시간 비교 (4K 텍스처) PNG 원본 로드 ├── 파일 읽기: 50ms ├── PNG 디코딩: 200ms ├── RGBA 변환: 30ms ├── GPU 업로드: 80ms └── Total: 360ms DDS (BC7) 로드 ├── 파일 읽기: 20ms (크기 작음) ├── 디코딩: 0ms (불필요) ├── 변환: 0ms (불필요) ├── GPU 업로드: 15ms (압축 상태로) └── Total: 35ms // 개선: 360ms → 35ms (10배 빠름)

2. 메모리 효율성

  • GPU 압축 텍스처 → VRAM 75% 절약
  • 메시 최적화 → 버텍스 버퍼 축소
  • 오디오 스트리밍 포맷 지원

3. 플랫폼 최적화

  • 각 플랫폼의 최적 포맷 자동 선택
  • 하드웨어 특성에 맞춤 최적화
쿠킹 없이 실시간 변환하면 안 되나?

이론적으로 가능하지만, 실용적이지 않아:

// 런타임 변환 vs 쿠킹의 비용 비교 런타임 텍스처 압축 (BC7) ├── CPU 시간: 2~5초 per texture ├── 메모리 피크: 원본 × 3 (소스 + 중간 + 결과) ├── 첫 프레임 딜레이: 불가피 └── 배터리 소모: 심각 (모바일) 쿠킹된 텍스처 로드 ├── CPU 시간: 0ms (이미 압축됨) ├── 메모리 피크: 결과물만 ├── 첫 프레임 딜레이: 없음 └── 배터리: 최소 // 결론: 빌드 타임에 한 번 쿠킹 >> 런타임에 매번 변환

런타임 변환이 허용되는 유일한 경우

UGC(User Generated Content)처럼 빌드 시점에 존재하지 않는 에셋만 런타임 변환 고려

그래도 가능하면 서버에서 미리 쿠킹해서 제공하는 것이 좋음

각 에셋 타입별로 쿠킹이 어떻게 달라?

에셋 타입마다 완전히 다른 쿠킹 프로세스가 적용돼:

// 에셋 타입별 쿠킹 프로세스 ═══ 텍스처 쿠킹 ═══ Input: PSD, PNG, TGA, EXR Process: 1. 색공간 변환 (sRGB ↔ Linear) 2. 채널 분리/병합 (Diffuse, Normal, Mask) 3. 해상도 조정 (POT, NPOT) 4. 밉맵 체인 생성 (Kaiser 필터) 5. GPU 압축 (BC1~BC7, ASTC, ETC2) Output: DDS, KTX, ASTC ═══ 메시 쿠킹 ═══ Input: FBX, OBJ, GLTF Process: 1. 지오메트리 최적화 (중복 버텍스 제거) 2. 인덱스 최적화 (캐시 효율성) 3. LOD 체인 생성 (메시 간략화) 4. 탄젠트/노말 재계산 5. 버텍스 포맷 패킹 (양자화) Output: 런타임 메시 바이너리 ═══ 애니메이션 쿠킹 ═══ Input: FBX, BVH, Maya Process: 1. 키프레임 리샘플링 2. 커브 압축 (오차 임계값 기반) 3. 본 리타겟팅 4. 루트 모션 추출 5. 이벤트 베이킹 Output: 압축된 애니메이션 클립 ═══ 오디오 쿠킹 ═══ Input: WAV, AIFF, FLAC Process: 1. 샘플레이트 리샘플링 2. 채널 다운믹스 (스테레오→모노) 3. 코덱 인코딩 (Opus, Vorbis, ADPCM) 4. 스트리밍 청크 분할 5. 루프 포인트 메타데이터 Output: OGG, OPUS, 플랫폼 네이티브

// 의존성 기반 쿠킹 스케줄러 public class CookingScheduler { private Dictionary<string, AssetCookTask> m_Tasks; private Dictionary<string, HashSet<string>> m_Dependencies; public List<AssetCookTask> GetCookingOrder() { // 위상 정렬로 쿠킹 순서 결정 var result = new List<AssetCookTask>(); var inDegree = new Dictionary<string, int>(); var queue = new Queue<string>(); // 진입 차수 계산 foreach (var task in m_Tasks.Keys) { inDegree[task] = m_Dependencies.ContainsKey(task) ? m_Dependencies[task].Count : 0; if (inDegree[task] == 0) queue.Enqueue(task); } // BFS로 순서 결정 while (queue.Count > 0) { var current = queue.Dequeue(); result.Add(m_Tasks[current]); // 이 에셋을 참조하는 에셋들의 진입차수 감소 foreach (var dependent in GetDependents(current)) { inDegree[dependent]--; if (inDegree[dependent] == 0) queue.Enqueue(dependent); } } // 순환 참조 검출 if (result.Count != m_Tasks.Count) throw new CyclicDependencyException("순환 참조 발견!"); return result; } }

// 인크리멘탈 쿠킹 시스템 public class IncrementalCooker { private Dictionary<string, AssetFingerprint> m_PreviousState; private Dictionary<string, AssetFingerprint> m_CurrentState; public struct AssetFingerprint { public string ContentHash; // 파일 내용 해시 public string SettingsHash; // 임포트 설정 해시 public DateTime LastModified; // 수정 시간 public string[] Dependencies; // 의존 에셋 경로 } public CookingPlan CreateIncrementalPlan() { var plan = new CookingPlan(); foreach (var asset in m_CurrentState) { if (NeedsCooking(asset.Key, asset.Value)) { plan.AddToCook(asset.Key); // 이 에셋에 의존하는 모든 에셋도 재쿠킹 필요 foreach (var dependent in GetDependentAssets(asset.Key)) plan.AddToCook(dependent); } } return plan; } private bool NeedsCooking(string path, AssetFingerprint current) { // 새 에셋 if (!m_PreviousState.TryGetValue(path, out var previous)) return true; // 내용 변경 if (current.ContentHash != previous.ContentHash) return true; // 설정 변경 if (current.SettingsHash != previous.SettingsHash) return true; // 의존성 변경 체크 foreach (var dep in current.Dependencies) { if (NeedsCooking(dep, m_CurrentState[dep])) return true; } return false; } } // 빌드 시간 비교 풀 쿠킹: 4시간 30분 (전체 30,000 에셋) 인크리멘탈 쿠킹: 3분 20초 (변경된 47 에셋 + 의존성 123 에셋)

Part 6. 쿠킹 최적화 전략

쿠킹 시간을 줄이려면 어떻게 해야 해?

쿠킹 최적화는 빌드 파이프라인 효율성의 핵심이야:

쿠킹 시간 최적화 전략

1. DDC (Derived Data Cache) 활용

  • 팀 공유 DDC 서버 구축
  • 한 번 쿠킹된 결과 재사용
  • 캐시 히트율 90%+ 목표

2. 병렬 쿠킹 최대화

  • CPU 코어 수에 맞춰 워커 스레드 설정
  • 의존성 없는 에셋 그룹 병렬 처리
  • I/O 병목 분리 (SSD + RAM 디스크)

3. 스마트 인크리멘탈 빌드

  • 정밀한 의존성 추적
  • 불필요한 재쿠킹 방지
  • 변경 감지 정확도 향상
// DDC 캐시 최적화 설정 public class DDCConfiguration { // 로컬 캐시 (가장 빠름) public string LocalCachePath = @"D:\DDC\Local"; public long LocalCacheMaxSize = 100L * 1024 * 1024 * 1024; // 100GB // 팀 공유 캐시 (네트워크) public string SharedCachePath = @"\\buildserver\DDC\Shared"; public bool AllowWriteToShared = true; // 클라우드 캐시 (원격 팀용) public string CloudCacheUrl = "s3://studio-ddc-cache"; public bool UseCloudCache = true; // 캐시 검색 순서 public CacheSearchOrder Order = CacheSearchOrder.Local | CacheSearchOrder.Shared | CacheSearchOrder.Cloud; } // 캐시 히트율 모니터링 public class DDCMetrics { public void PrintStats() { Console.WriteLine($"DDC 캐시 통계:"); Console.WriteLine($" 로컬 히트: {LocalHits,8} ({LocalHitRate:P1})"); Console.WriteLine($" 공유 히트: {SharedHits,8} ({SharedHitRate:P1})"); Console.WriteLine($" 클라우드 히트: {CloudHits,8} ({CloudHitRate:P1})"); Console.WriteLine($" 미스 (쿠킹): {Misses,8} ({MissRate:P1})"); Console.WriteLine($" 총 히트율: {TotalHitRate:P1}"); } } // 출력 예시 DDC 캐시 통계: 로컬 히트: 23,450 (78.2%) 공유 히트: 4,120 (13.7%) 클라우드 히트: 1,890 (6.3%) 미스 (쿠킹): 540 (1.8%) 총 히트율: 98.2%
쿠킹 품질을 검증하는 방법은?

쿠킹 결과 품질 검증은 자동화해야 해:

// 쿠킹 품질 검증 시스템 public class CookingValidator { public ValidationResult ValidateCookedAsset( string sourcePath, string cookedPath) { var result = new ValidationResult(); // 1. 파일 무결성 검사 if (!File.Exists(cookedPath)) { result.AddError("쿠킹된 파일이 존재하지 않음"); return result; } // 2. 크기 검증 (비정상적으로 작거나 큰 파일) var sourceSize = new FileInfo(sourcePath).Length; var cookedSize = new FileInfo(cookedPath).Length; if (cookedSize > sourceSize * 1.5f) result.AddWarning("쿠킹 후 크기가 원본보다 큼 (압축 실패?)"); if (cookedSize < 100) result.AddError("쿠킹된 파일이 비정상적으로 작음"); // 3. 포맷 검증 if (!ValidateFormat(cookedPath)) result.AddError("잘못된 파일 포맷"); // 4. 텍스처 특화 검증 if (IsTexture(sourcePath)) { var texResult = ValidateTexture(cookedPath); result.Merge(texResult); } return result; } private ValidationResult ValidateTexture(string path) { var result = new ValidationResult(); var header = ReadTextureHeader(path); // 밉맵 체인 검증 var expectedMips = CalculateExpectedMipLevels(header.Width, header.Height); if (header.MipLevels != expectedMips) result.AddWarning($"밉맵 수 불일치: {header.MipLevels} vs {expectedMips}"); // POT (Power of Two) 검증 if (!IsPowerOfTwo(header.Width) || !IsPowerOfTwo(header.Height)) result.AddInfo("NPOT 텍스처 (의도된 것인지 확인 필요)"); // 압축 품질 검증 (SSIM 사용) var ssim = CalculateSSIM(GetSourceImage(path), GetDecompressedImage(path)); if (ssim < 0.95f) result.AddWarning($"압축 품질 저하: SSIM={ssim:F3}"); return result; } }

쿠킹 에러 처리는 어떻게 해야 해?

쿠킹 실패는 빌드 전체를 중단시킬 수 있으므로, 철저한 에러 처리가 필요해:

// 쿠킹 에러 핸들링 시스템 public class CookingErrorHandler { public enum ErrorSeverity { Info, // 정보 (무시 가능) Warning, // 경고 (빌드 계속) Error, // 에러 (에셋 스킵) Fatal // 치명적 (빌드 중단) } public class CookingError { public string AssetPath; public ErrorSeverity Severity; public string Message; public Exception Exception; public string SuggestedFix; } private List<CookingError> m_Errors = new(); public void HandleCookingError(string assetPath, Exception ex) { var error = ClassifyError(assetPath, ex); m_Errors.Add(error); switch (error.Severity) { case ErrorSeverity.Info: LogInfo(error); break; case ErrorSeverity.Warning: LogWarning(error); NotifySlack(error); // 팀에 알림 break; case ErrorSeverity.Error: LogError(error); NotifySlack(error); SkipAsset(assetPath); // 에셋 스킵하고 계속 break; case ErrorSeverity.Fatal: LogFatal(error); NotifyUrgent(error); // 긴급 알림 throw new BuildAbortedException(error.Message); } } private CookingError ClassifyError(string path, Exception ex) { // 에러 패턴 매칭으로 분류 if (ex is FileNotFoundException) { return new CookingError { AssetPath = path, Severity = ErrorSeverity.Error, Message = "소스 파일을 찾을 수 없음", SuggestedFix = "에셋 경로 확인 또는 버전 관리 동기화" }; } if (ex is OutOfMemoryException) { return new CookingError { AssetPath = path, Severity = ErrorSeverity.Fatal, Message = "메모리 부족으로 쿠킹 실패", SuggestedFix = "에셋 크기 축소 또는 빌드 머신 메모리 증설" }; } // 기본값 return new CookingError { AssetPath = path, Severity = ErrorSeverity.Warning, Message = ex.Message, Exception = ex }; } public void GenerateReport() { var report = new StringBuilder(); report.AppendLine("=== 쿠킹 결과 보고서 ==="); report.AppendLine($"총 에러: {m_Errors.Count}"); report.AppendLine(); foreach (var group in m_Errors.GroupBy(e => e.Severity)) { report.AppendLine($"[{group.Key}] {group.Count()}건"); foreach (var error in group) { report.AppendLine($" - {error.AssetPath}: {error.Message}"); if (!string.IsNullOrEmpty(error.SuggestedFix)) report.AppendLine($" → 해결방법: {error.SuggestedFix}"); } } File.WriteAllText("CookingReport.txt", report.ToString()); } }

핵심 요약: 에셋 쿠킹

  • 정의: 소스 에셋 → 런타임 최적화 포맷 변환
  • 핵심 이점: 로드 시간 10~100배 감소, 파일 크기 90%+ 감소
  • 쿠킹 단계: Import → Process → Optimize → Package
  • 플랫폼별 최적화: PC(BC7), Mobile(ASTC/ETC2), Console(네이티브)
  • 인크리멘탈 쿠킹: 변경된 에셋만 재쿠킹 → 빌드 시간 대폭 단축
  • DDC 활용: 팀 공유 캐시로 98%+ 캐시 히트율 달성
  • 분산 쿠킹: 8대 머신으로 7배 속도 향상 가능
