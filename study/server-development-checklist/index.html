2. 기초 구조 보강 - "인프라 준비"

이제 게임 로직 짜면 돼?

아직이야!

생각해보자:

집 짓기: ❌ 바로 벽 세우기 시작? ✅ 먼저 기초 공사 (전기, 수도, 배관)

서버도 마찬가지: 콘텐츠 구현을 도와줄 기초 시스템을 먼저 만들어야 해.

프로토콜을 손으로 하나하나 짜야 해?

질문으로 답해볼게:

기획: "아이템 필드 하나 추가해주세요!" 수동으로 짜면: → 클라 구조체 수정 → 서버 구조체 수정 → 직렬화 코드 수정 → 역직렬화 코드 수정 → 한 곳이라도 빠뜨리면? 버그! 자동화하면: → 정의 파일 한 줄 수정 → 자동 생성 버튼 → 끝!

자동화는 생산성과 정신건강의 문제야.

어떻게 자동화해?

몇 가지 방법:

1. 코드 생성 (Code Generation) → 정의 → 자동 생성 → 코드 확인 가능 2. JSON 인코딩 → 런타임 직렬화/역직렬화 3. Protobuf, FlatBuffers → 성능 필요할 때
DB 접근을 왜 추상화해?

생각해보자:

신입 개발자가 이렇게 짰어: for (유저 in 1000명) { DB.Select("유저 아이템 조회"); // 1000번 DB 조회! } 결과: → 서버 멈춤 → 타임아웃 → 장애!

DB를 잘못 쓰면 서버 전체가 죽어!

추상화 레이어의 목적:

1. 잘못된 사용 패턴 아예 차단 예: N+1 쿼리 방지 2. 기능 자동화 ✅ 샤딩 (여러 DB 분산) ✅ 트랜잭션 로그 ✅ 커넥션 풀 관리
동시성 제어가 뭐야?

일상 비유로 시작:

🏦 은행 계좌 문제

내 계좌: 1000원

나 (ATM): "500원 출금"
아내 (인터넷뱅킹): "500원 출금"

동시에 처리하면?
→ 둘 다 "잔액 1000원" 확인
→ 둘 다 출금 성공
→ 잔액 0원? -500원? ❌

게임도 똑같은 문제야!

어떻게 막아?

두 가지 방법:

1. 낙관적 (Optimistic) "충돌 없을 거야~" → 일단 수정 → 나중에 충돌 체크 → 실패하면 재시도 2. 비관적 (Pessimistic) ⭐ "충돌 날 수도 있어!" → 먼저 잠금 (Lock) → 수정 → 잠금 해제

게임 서버는 비관적을 선호

이유: 대부분 데이터가 "유저 단위" → 유저별로 Lock 잡으면 충돌 거의 없음

서버에서 시간 처리, 뭐가 어려운데?

생각해보자:

상황 1: 장비마다 시간이 조금씩 다름 서버 A: 10:00:01 서버 B: 10:00:03 상황 2: 테스트하려고 서버 시간 앞당김 10:00 → 08:00 (2시간 과거로) → "하루 1번 출석체크" 로직이 꼬임!

시간은 생각보다 훨씬 어려워!

어떻게 해결해?

단조 증가 시계 (Monotonic Clock)

원칙: 시간은 절대 뒤로 가지 않아 현재: 10:00:05 시스템 시간 변경: 10:00:03 (과거로) 단조 증가 시계: → "어? 과거네?" → 10:00:06 반환 (계속 증가) → 로직 안 깨짐!

언어 기본 시간 타입으로는 이런 문제 못 풀어.

3. 콘텐츠 구현 - "실제 게임 만들기"

드디어 게임 로직을 짜는 거야?

응! 하지만 함정이 많아.

단순히 "기능 구현"만 하면 안 돼:

필요한 것: ✅ 테스트 (버그 잡기) ✅ 성능 (느리면 장애) ✅ 보안 (경제 버그 방지)
게임 로직을 어떻게 분류하면 좋아?

두 가지 질문:

질문 1: 누구 정보를 바꿔? A. 내 정보만 B. 남의 정보도 질문 2: 클라이언트에 알려줘야 해? X. 알릴 필요 없음 (DB만 저장) O. 알려야 함 (화면 업데이트)

조합하면 4가지:

타입 예시 난이도
A + X 아이템 획득 (DB만 저장) ⭐
A + O 레벨업 (UI 업데이트) ⭐⭐
B + X 선물 보내기 ⭐⭐⭐
B + O PVP (실시간) ⭐⭐⭐⭐⭐
B + O (PVP)가 왜 제일 어려워?

생각해보자:

서버 1대일 때: A가 B 공격 → 같은 서버니까 쉬움 서버 10대일 때: 서버 1의 A가 서버 5의 B 공격? → 서버끼리 통신 필요 → 트랜잭션 여러 DB 걸침 → 동기화 문제...

이건 4장 (스케일아웃)에서 다룰게.

싱글 프로세스부터? 멀티 프로세스부터?

질문: 기획자가 뭘 먼저 테스트해야 할까?

A안: 분산 서버 먼저 구축 (2개월) → 기획 테스트 시작 B안: 싱글 프로세스 먼저 (1주) → 기획 테스트 시작 → 나중에 분산 전환

B안! 기획 검증이 최우선

순서: 싱글 → 기획 검증 → 멀티 전환

테스트 자동화, 꼭 해야 해?

생각해보자:

클라이언트 버그: → 내 화면만 깨짐 → 재접속하면 고쳐짐 서버 버그: → DB 데이터가 틀어짐 → 모든 유저 영향 → 일일이 수정해야 함 ❌

서버는 테스트 필수!

이유: 1. 버그 파급 효과 큼 (DB까지 깨짐) 2. 동적 타입 언어면 서비스 중 죽음 3. 수정할 때 다른 곳 깨지기 쉬움 4. 자동화 없이 리팩토링? 위험!

🏪 편의점 vs 단골 카페

편의점 (Stateless):
어느 점원한테 가도 OK
점원: "신분증만 보여주세요"
→ 상태 없음, DB만 확인

단골 카페 (Stateful):
특정 점원이 내 취향 기억
→ 같은 점원한테 가야 함
Stateless 서버는 어떻게 만들어?
Stateless: ✅ 서버가 상태 안 갖음 ✅ 모든 상태 → DB/Redis 저장 ✅ 어떤 서버로 접속해도 OK 장점: ✅ 로드 밸런싱 쉬움 ✅ 무중단 업데이트 쉬움 (서버 하나씩 재시작) 단점: ❌ 매번 DB 조회 → 느림 ❌ 실시간 게임 부적합

적합: 턴제, 카드, 캐주얼

Stateless로 못 만들면?

세션 스티키니스 (Session Stickiness)

원칙: 같은 서버로 재접속 구현: 1. 유저ID → 서버 번호 매핑 테이블 2. 로그인 서버가 배정 3. 재접속 시 같은 서버로 라우팅 무중단 업데이트: 1. 새 유저는 다른 서버로 2. 기존 유저 로그아웃 대기 3. 전부 나가면 재시작
다른 서버 유저와 PVP 하려면?

Stateless 서버:

Redis Pub/Sub + HTTP Long Polling 1. 서버 A: PVP 액션 → Redis Publish 2. Redis: 모든 서버에 브로드캐스트 3. 서버 B: Subscribe로 받음 4. 서버 B: Long Polling 클라에 전송

실제: 마비노기 듀얼

Stateful 서버:

방법 1: Dedicated Server (전용 서버) 방법 2: Actor Model (Orleans, Akka) 방법 3: Direct Server-to-Server (TCP/UDP)

실제: 마블 배틀 라인 (Actor Model)

유저 많으면 DB도 여러 대 필요한 거 아냐?

맞아!

수평 분할 (Sharding): 유저 ID로 나누기 예: 유저 1000만 명, DB 10대 → 1-100만: DB 1 → 100-200만: DB 2 → ... 방법 1: Modulo (% 연산) dbNumber = userId % 10 방법 2: Lookup (테이블 조회) dbNumber = LookupTable.Get(userId)
방식 장점 단점
Modulo 구현 쉬움
빠름		 DB 추가 시 재분배
Lookup 유연함
DB 추가 쉬움		 조회 오버헤드
DB 여러 대면 트랜잭션은?

문제 상황:

A (DB1)가 B (DB2)에게 아이템 선물 필요한 원자성: 1. A 아이템 -1 (DB1) 2. B 아이템 +1 (DB2) → 둘 다 성공 or 둘 다 실패 중간에 서버 죽으면? → A만 빠지고 B는 안 받음! ❌

분산 트랜잭션 필요!

해결: ✅ 2PC (Two-Phase Commit) ✅ Saga Pattern ✅ 분산 락 ⚠️ 직접 구현 말고 라이브러리 사용!

📌 핵심 정리: 스케일아웃

  • 봉투 뒷면 계산: 대략적인 서버 대수 추정
  • Stateless: 쉽지만 실시간 부적합 → 턴제 게임용
  • Stateful: 세션 스티키니스 필요 → 실시간 게임용
  • 서버간 통신: Redis Pub/Sub or Actor Model
  • DB 샤딩: 수평 분할 (Modulo or Lookup)
  • 분산 트랜잭션: 직접 구현 금지, 라이브러리 사용

5. 출시 준비 → 운영 도구, 모니터링, 대시보드 6. 보안 → 해킹 방지, 암호화, 인증 7. 로깅 & 분석 → 유저 행동 추적, 데이터 분석 8. 테스트 환경 → QA 환경, 부하 테스트 9. 장애 대응 → 백업, 복구, 롤백 계획 10. 운영 자동화 → 배포 자동화, 오토 스케일링
