넥슨 개발자가 10년 경험으로 정리한 게임 서버 개발 10단계
게임 서버 개발, 뭐부터 시작해야 해?

넥슨의 한 개발자는 신규 프로젝트에서 서버 담당이 되었을 때 이렇게 생각했어:

"일정 안에 필요한 일 다 하면 되겠지?"

그런데 일을 해도 해도 계속 할 일이 생겨나서 후반에는 시간이 너무 부족했어.

문제는 뭐였을까? → 할 일 목록을 몰랐던 거야.

그래서 뭘 만들었는데?

10년 경험을 바탕으로 게임 서버 개발 10단계 체크리스트를 만들었어.

이걸 알았으면 야근 안 했을 텐데...

📋 Phase 1-3: 모든 프로젝트 공통 (필수)

1단계. 최초 의사결정 - "뭘 만들지 정하기"

서버 만들기 전에 뭘 정해야 해?

이런 것들이 서버 구조를 크게 바꿔:

✅ 서버 용도 & 장르 ✅ 사용자 규모 (동접 100명? 10만명?) ✅ 통신 환경 (실시간? 턴제?) ✅ 저장소 (RDB? NoSQL?) ✅ 언어/플랫폼 (C#? Go? Python?)

예를 들어, 유저 수가 적어서 DB 하나, 게임 서버 하나면 끝나는 프로젝트는 서버 구조도 간단해지고 할 일도 크게 줄어들어.

1-1. 통신 환경 선택

어떤 통신 방식을 써야 해?

쉽게 구현하려면 HTTP + Long Polling

장점: ✅ 모바일 환경 잘 커버 ✅ 필요하면 양방향 통신 가능 ✅ 구현 간단 단점: ❌ 지연 시간 큼 ❌ 실시간 액션 게임엔 부적합

FPS, 레이싱 게임처럼 지연에 민감한 장르는 적용 어려워.

실제 사례: 마비노기 듀얼 = HTTP + Long Polling (턴제 게임)

1-2. 저장소 선택

RDB vs NoSQL, 뭘 써야 해?

디폴트는 RDB (MySQL, PostgreSQL 등)

RDB 장점: ✅ ACID 보장 → 안정적인 로직 구현 쉬움 ✅ 잘못 사용해도 위험성 적음 ✅ 트랜잭션 지원 NoSQL (Redis, MongoDB) 장점: ✅ 빠른 속도 ✅ 수평 확장 쉬움 ✅ 특정 용도에 최적화

각 저장소의 장단점을 잘 나열해보고 내 서버 용도에 맞는 걸 골라.

1-3. 언어/플랫폼 선택

개인 개발이면 취향, 팀 개발이면?

생산성의 문제

고려 요소: ✅ 동적 타입 vs 정적 타입 ✅ 빌드 속도 ✅ 클라이언트와 코드 공유 가능 여부

발표자 추천: C# (장점 대부분 커버 + Unity/언리얼 협업 좋음)

💻 Windows vs Linux

Windows 서버:
✅ Visual Studio 사용 가능
✅ 클라우드 배포 편함
✅ 개발 단계에서 편리

Linux 서버:
✅ 서버 비용 쌈
✅ 편리한 툴 많음
✅ 서비스할 때 장점 많음

팁: Windows에서 개발 → Linux 빌드로 서비스
(하지만 나름의 비용 있으니 잘 고려!)

2단계. 기초 구조 보강 - "인프라 준비"

본격적으로 코딩 시작하기 전에 뭘 준비해야 해?

콘텐츠 구현할 때 도움이 될 기초 시스템들을 먼저 만들어놔야 해.

2-1. 프로토콜 자동화

통신 프로토콜을 손으로 하나하나 짜야 해?

절대 아니야!

프로토콜은 생각보다 자주 바뀌어.

자동화를 하는 게 생산성과 정신건강에 좋아.

어떻게 자동화하는데?

몇 가지 방법:

1. 코드 생성 (Code Generation) → 프로토콜 정의하면 필요한 코드 자동 생성 → 생성 결과가 눈에 보여서 고치기 쉬움 2. JSON 인코딩 → 런타임에 직렬화/역직렬화 3. Protobuf, FlatBuffers 등 → 성능 최적화 필요하면 사용

발표자 팀: 예전엔 T4 템플릿 사용 → 지금은 코드 생성 + JSON 인코딩

2-2. DB 접근 추상화

DB 접근을 왜 추상화해?

두 가지 목적:

1. DB를 잘못 사용하는 케이스를 아예 차단 예: N+1 쿼리 문제, 인덱스 없는 조회 등 2. DB 관련 기능들을 자동화 ✅ 수평 샤딩 (여러 DB로 분산) ✅ 트랜잭션 로그 기록 ✅ 커넥션 풀 관리

발표자 팀: 실로바(Siloba) + 바이젠투(Visentou) 사용

(넥슨 서버 엔진 투의 DB 레이어)

2-3. 동시성 제어 (Concurrency Control)

서버에서 데이터 동시 수정, 어떻게 막아?

크게 두 가지 방법:

1. 낙관적 동시성 (Optimistic Concurrency) "충돌 별로 없을 거야~" → 일단 수정하고, 나중에 충돌 체크 → 실패하면 재시도 2. 비관적 동시성 (Pessimistic Concurrency) ⭐ "충돌 날 수도 있으니 미리 잠그자!" → 수정 전에 Lock 획득 → 수정 완료 후 Lock 해제

발표자 팀은 비관적 동시성을 크게 선호

왜 비관적 동시성이 좋아?

게임 서버 데이터의 대다수가 유저에 속해 있어.

유저 단위로 Lock을 잡으면: ✅ 대체로 무난함 ✅ 충돌 거의 없음 ✅ 로직 구현 쉬움 데드락(Deadlock) 문제는? → Lock 순서 규칙을 강제해서 피할 수 있어 (항상 유저ID 오름차순으로 Lock 획득 등)

2-4. 시간 처리 (Time Handling)

서버에서 시간 처리, 뭐가 어려운데?

생각보다 굉장히 어려워!

문제 1: 장비마다 시간이 조금씩 다름 문제 2: 시간 동기화 과정에서... → 시간 역전 발생 가능 → 시간 속도가 달라질 수 있음 문제 3: 서버 시간을 억지로 바꾸는 경우 예: 이벤트 테스트할 때 시간 앞당기기 → 모든 장비 시간 한꺼번에 바꾸기 어려움 → 과거로 돌렸을 때 데이터 꼬임
어떻게 해결해?

단조 증가 시계 (Monotonic Clock)

// 단조 증가 시계 예시 class MonotonicClock { private long lastTick; public long GetNow() { long current = SystemTime.Now(); // 절대 과거로 돌아가지 않음 if (current <= lastTick) { current = lastTick + 1; } lastTick = current; return current; } }

언어가 제공하는 기본 시간 타입으로는 이런 문제들을 잘 풀기 어려워.

세심한 타입을 만들어서 로직 작성하는 것도 방법.

3단계. 콘텐츠 구현 - "실제 게임 만들기"

드디어 게임 로직을 짜는 거야?

응! 하지만 여기도 함정이 많아.

단순히 기능만 구현하면 안 되고, 테스트·성능·보안을 모두 고려해야 해.

3-1. 콘텐츠 로직 분류

게임 서버 로직을 어떻게 분류하면 좋아?

두 가지 기준으로 나눠:

기준 1: 누구 정보를 바꾸는가? A. 내 정보만 B. 내 정보 + 남의 정보 기준 2: 클라이언트에 알려줘야 하는가? X. 알려주지 않아도 됨 (서버 내부 처리) O. 알려줘야 함 (클라에 변경사항 전송)

조합하면 총 4가지:

타입 설명 예시
1. A + X 내 정보만, 알림 불필요 아이템 획득 (DB 저장만)
2. A + O 내 정보만, 알림 필요 레벨업 (클라에 UI 업데이트)
3. B + X 남의 정보도, 알림 불필요 선물 보내기 (받는 사람 접속 안 함)
4. B + O 남의 정보도, 알림 필요 PVP (실시간 동기화)
가장 어려운 건 어떤 타입이야?

4번 (B + O) = PVP 같은 실시간 상호작용

특히 서버가 여러 대라면:

문제: 다른 서버에 접속한 유저와 PVP를 하려면? → 서버 간 통신 (Server-to-Server Communication) 필요 필요한 기능: ✅ 분산 트랜잭션 (여러 DB에 걸친 원자성 보장) ✅ 서버 간 메시지 동기화 ✅ 세션 관리

이 부분은 4장에서 자세히 다룰 거야.

3-2. 개발 순서 전략

싱글 프로세스부터? 멀티 프로세스부터?

싱글 프로세스부터 먼저 개발하는 게 유리!

이유: 1. 콘텐츠 개발은 소규모라도 플레이 가능해야 함 → 기획 테스트 가능해야 함 2. 분산 트랜잭션, 서버간 통신은 준비 시간 오래 걸림 → 나중에 준비되면 하부구조 고쳐서 멀티 프로세스로 전환 순서: 싱글 프로세스 → 기획 검증 → 멀티 프로세스 전환

3-3. 테스트 자동화

테스트 자동화, 꼭 해야 해?

서버는 필수야!

이유 1: 서버 버그는 파급 효과가 큼 클라: 버그 부분만 패치하면 됨 서버: DB 데이터까지 틀어짐 → 일일이 수정해야 함 이유 2: 동적 타입 언어라면 → 테스트 안 하면 서비스 중 서버 죽는 일 비일비재 이유 3: 수정할 때 오류 안 생기게 하기 대단히 어려움 이유 4: 자동화 테스트 없이 리팩토링? → 너무 위험해!

3-4. 로직 레이어링

서버 코드를 어떻게 구조화해야 해?

발표자가 권장하는 레이어링:

하위 레이어: Logic (로직) ↓ 단위 기능 구현 유닛 테스트로 검증 (샌드위치 "재료") ↑ 상위 레이어: Handler (핸들러) ↓ 클라 요청 처리 로직 조합해서 구현 통합 테스트로 검증 (완성된 "샌드위치")
🥪 샌드위치 비유

재료 (로직):
빵, 야채, 고기, 치즈...
→ 각각 단위 테스트

샌드위치 (핸들러):
재료를 조합해서 완성품 만들기
→ 통합 테스트 (테스트 클라이언트)

핸들러는 "조합"만 하고, 실제 기능은 로직에!

3-5. 멀티스레드 프로그래밍

서버라면 멀티스레드 꼭 써야 하는 거 아냐?

알아야 하긴 하지만, 이걸로 서버를 다 짜면 굉장히 힘들어!

멀티스레드가 어려운 이유: ❌ 짜기 어려움 ❌ 버그 찾기 어려움 ❌ 고쳤는지 확인하기 어려움 ❌ 게임 로직은 자주 바뀌는데 다시 짜야 함 "멀티스레드 프로그래밍은 흑마술, 잘못 사용하면 패가망신한다"
그럼 동접 많으면 어떡해?

멀티스레드 대신 다른 대안들을 사용!

대안 1: Actor Model (액터 모델) → 각 액터가 독립적으로 동작 → 메시지로만 통신 → 예: Akka, Orleans 대안 2: Async/Await → 비동기 프로그래밍 → C#, Python, JavaScript 등 대안 3: Coroutine → 협력적 멀티태스킹 → Unity, Lua 등 대안 4: Event Loop → Node.js, Vert.x 등

각 언어마다 멀티스레드 대신 쓸 만한 동시성 기능을 제공해.

3-6. 성능 최적화

서버 코드는 항상 최적화해야 해?

아니!

"성급한 최적화는 악의 근원" (도널드 커누스)

왜 최적화 안 해도 돼?
이유 1: 서버 성능은 대부분 네트워크/DB에서 결정됨 → 로직 코드 최적화해봤자 큰 차이 없음 이유 2: 게임 로직은 자주 바뀜 → 최적화하면 이해하기 어렵고 고치기 어려움 이유 3: 성급한 최적화의 문제 → 열심히 고쳤는데 그 부분이 별로 안 불림 → 다른 부분에 더 큰 병목 있으면 효과 미미 → 이걸 "암달의 법칙"이라고 함

코드는 빠르게 짜는 것보다 명료하게 짜는 게 더 중요!

그럼 최적화는 언제 해?
시기 대상
미리 해도 됨 네트워크, DB 관련 부분
(시스템 로직은 변경 빈도 낮음)
나중에 해야 함 콘텐츠 로직
→ 프로파일링 돌려서 병목 찾고
→ 그 부분만 최적화

3-7. 경제 버그 예방

경제 버그가 뭐야?

돈 복사, 아이템 복사, 재화 증발 같은 버그를 통칭해서 경제 버그라고 불러.

경제 버그의 공통점: ❌ 제대로 수습 못하면 게임 경제 망가짐 ❌ 게임 수명에 지대한 영향 ❌ 버그 고친 뒤에도 후속 작업 대단함 → 잘못 풀린 재화 회수 → 악용한 유저 추적 → 보상 정책 결정
어떻게 예방해?

시스템적인 예방이 중요!

예방 방법: ✅ 재화 변경 로그 철저히 기록 ✅ 트랜잭션으로 원자성 보장 ✅ 재화 증감 API 중앙화 (직접 수정 금지) ✅ 코드 리뷰 필수 ✅ 자동화 테스트로 검증 이미 발생했다면? → 개인을 탓할게 아니라 → 시스템과 절차에 뚫린 구멍을 점검하고 개선

💡 3장까지 정리

  • 1장 의사결정: 서버 용도·규모·통신·저장소·언어 결정
  • 2장 기초 구조: 프로토콜·DB·동시성·시간 처리 자동화
  • 3장 콘텐츠: 로직 분류·테스트·레이어링·성능·보안

🚀 Phase 4-10: 상용 서비스 (안정적 라이브 운영)

4단계. 스케일아웃 - "유저 늘어나면?"

스케일아웃이 뭐야?

서버 처리 성능을 높이는 두 가지 방법:

📈 Scale Out (스케일아웃) → 장비 대수를 늘림 → 서버 10대 → 100대 📊 Scale Up (스케일업) → 개별 장비 성능을 올림 → CPU 4코어 → 16코어

이 장에서는 Scale Out을 다뤄.

4-1. 봉투 뒷면 계산법

서버가 몇 대나 필요한지 어떻게 알아?

봉투 뒷면 계산법 (Back-of-the-envelope Calculation)

→ 봉투 뒷면에 할 수 있을 정도로 간단한 계산

계산 순서: 1. 사업부서에서 최대 동접 추산 "마케팅 예산 ○○원이면 동접 10만명 예상" 2. 필요한 리소스 계산 ✅ 메모리: 유저당 10MB × 10만명 = 1TB ✅ 네트워크: 초당 패킷 수 × 패킷 크기 ✅ DB: 초당 쿼리 수 (QPS) 3. 서버 프로세스 개수 추정 간이 부하 테스트: 1대로 동접 1000명 가능 → 10만명 대비하려면 최소 100대 필요

정밀한 계산은 아니고, 대략적인 범위나 자릿수 확인용

정확한 값은 부하 테스트로 확인!

4-2. 분산 서버의 3가지 문제

게임 서버가 여러 대 필요하면 뭘 해결해야 해?
문제 설명
1. 로드 밸런싱 모든 서버에 유저를 골고루 분산
2. 무중단 업데이트 점검 없이 패치하기
3. 서버간 통신 다른 서버 유저와 실시간 상호작용

4-3. Stateless 서버

분산 서버 만드는 가장 쉬운 방법은?

서버를 Stateless로 만들기!

Stateless 서버: ✅ 서버가 상태를 갖지 않음 ✅ 모든 상태는 DB/Redis에 저장 ✅ 어떤 서버로 접속해도 상관없음 장점: ✅ 로드 밸런싱 쉬움 (아무 서버나 연결) ✅ 무중단 업데이트 쉬움 (서버 하나씩 재시작) 단점: ❌ 지연 시간 큼 (매번 DB 조회) ❌ MMORPG, FPS 같은 실시간 게임 부적합

적합한 장르: 턴제, 카드 게임, 캐주얼 게임

4-4. Stateful 서버

Stateless로 못 만들면?

세션 스티키니스 (Session Stickiness) 필요

세션 스티키니스: → 연결 끊고 다시 접속할 때 → 같은 서버로 재접속 보장 구현 방법: 1. 유저ID → 서버 번호 매핑 테이블 2. 로그인 서버가 어느 게임 서버로 보낼지 결정 3. 재접속 시 같은 서버로 라우팅

무중단 업데이트는?

1. 서버가 세션 전부 종료될 때까지 대기 2. 새로운 유저는 다른 서버로 배정 3. 기존 유저 다 로그아웃하면 재시작 4. 또는 세션 마이그레이션 (고난이도)

4-5. 서버간 통신 (PVP)

다른 서버에 있는 유저와 PVP 하려면?

Stateless vs Stateful로 나눠서 봐야 해.

Stateless 서버에서는?

Redis Pub/Sub + HTTP Long Polling

동작 원리: 1. 서버 A: PVP 액션을 Redis에 Publish 2. Redis: 구독 중인 모든 서버에 브로드캐스트 3. 서버 B: Subscribe해서 메시지 받음 4. 서버 B: Long Polling 대기 중인 클라에 전송

실제 사례: 마비노기 듀얼 (턴제 PVP)

Stateful 서버에서는?

여러 가지 방법 있는데, 컨텐츠마다 달라:

방법 1: Dedicated Server (전용 서버) → PVP 전용 서버 만들기 → 유저들이 PVP 서버로 이동 방법 2: Actor Model (액터 모델) → 각 PVP 룸을 Actor로 구현 → 메시지로 통신 → 예: Orleans, Akka 방법 3: Direct Server-to-Server → 서버끼리 직접 TCP/UDP 통신

실제 사례: 마블 배틀 라인 (Actor Model 사용)

4-6. 저장소 분할 (Sharding)

유저 많으면 DB도 여러 대 필요한 거 아냐?

맞아! 저장소도 분할해야 해.

분할 방식 설명
수직 분할 용도별로 나누기
(유저DB, 아이템DB, 로그DB)
수평 분할 ⭐ 유저 ID로 나누기
(유저 1-10만 → DB1, 10만-20만 → DB2)

RDB는 대부분 수평 분할 사용 (트랜잭션 처리 편함)

수평 분할은 어떻게 구현해?

두 가지 방법:

// 1. Modulo 분할 (% 연산) int dbNumber = userId % dbCount; // 예: 유저 12345, DB 10대 → 12345 % 10 = 5번 DB // 2. Lookup 분할 (테이블 조회) int dbNumber = LookupTable.Get(userId); // 별도 테이블에 "유저 12345 → DB 5번" 저장
방식 장점 단점
Modulo 구현 쉬움
빠름		 DB 추가 시 재분배 필요
Lookup 유연함
DB 추가 쉬움		 조회 오버헤드
Lookup 테이블 관리 필요

4-7. 분산 트랜잭션

DB가 여러 대면 트랜잭션은 어떡해?

분산 트랜잭션 (Distributed Transaction) 필요!

문제 상황: 유저 A (DB1)가 유저 B (DB2)에게 아이템 선물 필요한 원자성: 1. A의 아이템 차감 (DB1) 2. B의 아이템 증가 (DB2) → 둘 다 성공 or 둘 다 실패 보장 해결 방법: ✅ 2PC (Two-Phase Commit) ✅ Saga Pattern ✅ 분산 락 사용

직접 구현하면 너무 복잡! 라이브러리 사용 권장

4-8. Redis 분할

Redis는 어떻게 분할해?

RDB처럼 수직/수평 분할 모두 가능:

Redis 특징: ❌ 트랜잭션 제한적 ✅ 그래서 수직 분할을 RDB보다 적극적으로 사용 가능 수직 분할 예시: ✅ Redis 1: 세션 캐시 ✅ Redis 2: 랭킹 데이터 ✅ Redis 3: 채팅 메시지 데이터 사이즈 너무 크면? → 수평 분할 (유저ID로 샤딩)

📌 핵심 정리: 스케일아웃

  • 봉투 뒷면 계산: 대략적인 서버 대수 추정
  • Stateless 서버: 쉽지만 실시간 게임 부적합
  • Stateful 서버: 세션 스티키니스 필요
  • 서버간 통신: Redis Pub/Sub or Actor Model
  • DB 샤딩: 수평 분할 (Modulo or Lookup)
  • 분산 트랜잭션: 직접 구현 말고 라이브러리 사용
