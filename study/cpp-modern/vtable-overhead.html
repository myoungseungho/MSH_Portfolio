왜 virtual 함수가 많으면 느려질까?

vtable, vptr, 간접 호출의 숨겨진 비용

Part 1. virtual 함수란?

virtual 함수가 뭐야?

런타임에 어떤 함수를 호출할지 결정하는 함수야.

// 일반 함수 - 컴파일 타임에 결정 class Animal { void Speak() { cout << "..."; } }; class Dog : public Animal { void Speak() { cout << "멍멍"; } }; Animal* a = new Dog(); a->Speak(); // "..." 출력 (Animal::Speak 호출) // 컴파일러: "a는 Animal* 타입이니까 Animal::Speak" // virtual 함수 - 런타임에 결정 class Animal { virtual void Speak() { cout << "..."; } }; class Dog : public Animal { void Speak() override { cout << "멍멍"; } }; Animal* a = new Dog(); a->Speak(); // "멍멍" 출력 (Dog::Speak 호출!) // 런타임: "실제 객체가 Dog니까 Dog::Speak"
왜 virtual이 필요해?

다형성(Polymorphism)을 위해서야!

// 다형성의 힘 void MakeNoise(Animal* animal) { animal->Speak(); // 어떤 동물이든 OK! } MakeNoise(new Dog()); // "멍멍" MakeNoise(new Cat()); // "야옹" MakeNoise(new Duck()); // "꽥꽥" // virtual 없으면 전부 "..." 출력됨!

Part 2. vtable과 vptr의 내부 구조

런타임에 어떤 함수를 호출할지 어떻게 알아?

vtable이라는 테이블을 사용해!

[vtable (Virtual Table)] 클래스마다 하나씩 있는 함수 포인터 테이블 class Animal { virtual void Speak(); virtual void Move(); }; class Dog : public Animal { void Speak() override; void Move() override; }; class Cat : public Animal { void Speak() override; // Move()는 오버라이드 안 함 }; [메모리에서의 vtable] Animal vtable: Dog vtable: +------------------+ +------------------+ | 0: Animal::Speak | | 0: Dog::Speak | | 1: Animal::Move | | 1: Dog::Move | +------------------+ +------------------+ Cat vtable: +------------------+ | 0: Cat::Speak | | 1: Animal::Move | ← 오버라이드 안 했으니 부모 함수 +------------------+
그럼 객체는 vtable을 어떻게 찾아?

모든 객체에 vptr이 숨어있어!

[vptr (Virtual Pointer)] virtual 함수가 있는 클래스의 모든 객체에 숨겨진 포인터 Dog dog1, dog2; Cat cat1; [메모리 레이아웃] dog1: dog2: +---------------+ +---------------+ | vptr ---------|--+ | vptr ---------|--+ | (멤버 변수들) | | | (멤버 변수들) | | +---------------+ | +---------------+ | | | v v Dog vtable: <--------------------+--+ +------------------+ | 0: Dog::Speak | | 1: Dog::Move | +------------------+ cat1: +---------------+ | vptr ---------|--→ Cat vtable | (멤버 변수들) | +---------------+ → 같은 클래스의 객체들은 같은 vtable을 공유!
실제 호출 과정을 보여줘.
[virtual 함수 호출 과정] Animal* a = new Dog(); a->Speak(); 단계별로 보면: 1. a 객체에서 vptr 읽기 vptr = a->vptr (8바이트 메모리 접근) 2. vtable에서 Speak 인덱스 찾기 func_ptr = vptr[0] (또 메모리 접근!) 3. 함수 포인터로 점프 call func_ptr 어셈블리로 보면: mov rax, [rcx] ; vptr 읽기 mov rax, [rax] ; vtable[0] 읽기 call rax ; 간접 호출 [일반 함수 호출과 비교] 일반 함수: call Animal::Speak ; 직접 호출 (주소가 코드에 박혀있음) virtual 함수: mov rax, [rcx] ; 메모리 읽기 1 mov rax, [rax] ; 메모리 읽기 2 call rax ; 간접 호출 → 추가 명령어 + 메모리 접근 = 오버헤드!

Part 3. virtual 함수의 성능 문제

정확히 뭐가 느려지는 거야?

크게 3가지 오버헤드가 있어!

[오버헤드 1: 간접 호출 (Indirect Call)] 직접 호출: CPU: "0x401000 번지로 점프!" (주소가 명령어에 있음) 간접 호출: CPU: "메모리에서 주소 읽어서... 거기로 점프!" 왜 느린가? - 분기 예측 어려움 - 파이프라인 스톨 가능성 - 명령어 캐시 미스 가능성 단일 호출: 수 나노초 차이 반복문에서 백만 번: 수 밀리초 차이!
[오버헤드 2: 인라인 불가] 일반 함수는 인라인 가능: // 원래 코드 for (int i = 0; i < 1000000; i++) { obj.GetX(); // return m_x; } // 컴파일러가 인라인하면 for (int i = 0; i < 1000000; i++) { // 함수 호출 없이 직접 m_x 접근! } virtual 함수는 인라인 불가능: for (int i = 0; i < 1000000; i++) { obj->GetX(); // virtual 함수 // 컴파일러: "런타임에 뭐가 호출될지 몰라서 인라인 못 함" } → 매번 함수 호출 오버헤드 발생!
[오버헤드 3: 캐시 미스] vtable 접근 = 메모리 접근 최악의 경우: 1. vptr 읽기 → 캐시 미스 (100ns) 2. vtable 읽기 → 캐시 미스 (100ns) 3. 함수 코드 → 명령어 캐시 미스 다형적 컨테이너가 특히 문제: vector animals; // Dog, Cat, Duck 섞여있음 for (Animal* a : animals) { a->Speak(); // Dog::Speak → Cat::Speak → Duck::Speak → Dog::Speak... // 함수 코드가 계속 바뀜 → 명령어 캐시 스래싱! }
오버헤드 원인 영향
간접 호출 런타임 주소 결정 수 나노초/호출
인라인 불가 호출 대상 불명 최적화 차단
캐시 미스 vtable/함수 분산 100ns+/미스
실제로 얼마나 차이나?

상황에 따라 2~10배 차이날 수 있어!

[벤치마크 예시] // 테스트: 1억 번 호출 일반 함수 (인라인됨): ~0ms (컴파일러가 루프 자체를 최적화) 일반 함수 (인라인 막음): ~100ms virtual 함수 (같은 타입): ~200ms (2배) virtual 함수 (타입 섞임): ~500ms+ (5배+, 캐시 미스 포함) 게임 서버에서: 프레임당 수만 번 호출 × 캐시 미스 → 무시 못 할 성능 차이!

Part 4. 메모리 오버헤드

vptr도 메모리 차지하잖아?

맞아, 객체마다 8바이트(64비트)씩!

[vptr 메모리 오버헤드] class Point { float x, y; // 8바이트 }; sizeof(Point) = 8바이트 class VirtualPoint { virtual void Move(); float x, y; // 8바이트 }; sizeof(VirtualPoint) = 16바이트! (vptr 8 + 데이터 8) → virtual 하나 추가로 객체 크기 2배! [대량 객체에서의 영향] 파티클 100만 개: Point: 100만 × 8 = 8MB VirtualPoint: 100만 × 16 = 16MB → 8MB 추가 메모리 → 캐시 효율 50% 감소!
vtable 자체도 메모리 쓰지?

그건 클래스당 하나라서 별로 안 커.

[vtable 메모리] 클래스당 vtable 하나: virtual 함수 10개 → 80바이트 (포인터 10개) 클래스가 100개여도 → 8KB 객체가 100만 개면: vptr 오버헤드: 100만 × 8 = 8MB vtable: 100 × 80 = 8KB → vtable은 별거 아니고, vptr이 문제!

Part 5. 해결책과 대안

그럼 virtual을 아예 안 쓰면 되나?

그건 아니고, 적재적소에 사용해야 해!

[해결책 1: CRTP (Curiously Recurring Template Pattern)] // 컴파일 타임 다형성! template class Animal { public: void Speak() { static_cast(this)->SpeakImpl(); } }; class Dog : public Animal { public: void SpeakImpl() { cout << "멍멍"; } }; class Cat : public Animal { public: void SpeakImpl() { cout << "야옹"; } }; Dog dog; dog.Speak(); // "멍멍" - 컴파일 타임에 결정! // vtable 없음, 인라인 가능! 단점: 다른 타입을 한 컨테이너에 못 담음 (Animal와 Animal은 다른 타입)
[해결책 2: std::variant + std::visit (C++17)] #include struct Dog { void Speak() { cout << "멍멍"; } }; struct Cat { void Speak() { cout << "야옹"; } }; using Animal = std::variant; vector animals; animals.push_back(Dog{}); animals.push_back(Cat{}); for (auto& a : animals) { std::visit([](auto& animal) { animal.Speak(); }, a); } 장점: - vtable 없음 - 캐시 친화적 (객체가 연속 배치) - 인라인 가능 단점: - 타입 목록이 컴파일 타임에 고정 - variant 크기 = 가장 큰 타입 + 태그
[해결책 3: 타입별 컨테이너 분리] // 나쁜 예 - 타입 섞임 vector entities; // Player, Monster, NPC 섞임 for (Entity* e : entities) { e->Update(); // 매번 다른 vtable → 캐시 스래싱 } // 좋은 예 - 타입별 분리 vector players; vector monsters; vector npcs; // 같은 타입끼리 처리 for (Player& p : players) p.Update(); for (Monster& m : monsters) m.Update(); for (NPC& n : npcs) n.Update(); → 캐시 효율 극대화! → 인라인도 가능해질 수 있음!
[해결책 4: virtual 함수 최소화] // 나쁜 예 - 모든 게 virtual class Entity { virtual int GetX(); virtual int GetY(); virtual int GetHP(); virtual void SetX(int); virtual void SetY(int); virtual void SetHP(int); // ...수십 개 }; // 좋은 예 - 정말 필요한 것만 virtual class Entity { // 데이터 접근은 일반 함수 int GetX() { return m_x; } int GetY() { return m_y; } // 다형성이 필요한 것만 virtual virtual void Update(); virtual void Render(); }; → vtable 크기 감소 → 인라인 가능한 함수 증가
[해결책 5: final 키워드] class Dog final : public Animal { void Speak() override; }; // Dog가 final이면 컴파일러가 알 수 있음: // "Dog를 상속하는 클래스 없음" // → 최적화 가능! Dog* dog = new Dog(); dog->Speak(); // 컴파일러: Dog::Speak 직접 호출 가능! // 또는 함수에만 final class Cat : public Animal { void Speak() override final; // 이 함수는 더 오버라이드 안 됨 };
기법 장점 단점
CRTP vtable 제거, 인라인 타입 혼용 불가
std::variant 캐시 친화적 타입 고정 필요
컨테이너 분리 구현 간단 코드 중복 가능
virtual 최소화 기존 구조 유지 설계 판단 필요
final 쉬운 적용 확장성 제한

Part 6. 실무 가이드라인

그래서 언제 virtual을 쓰고 언제 피해야 해?

Hot Path vs Cold Path를 구분해!

[Hot Path - virtual 피하기] 매 프레임 수만~수십만 번 호출되는 곳: - 물리 연산 - 충돌 검사 - AI 틱 - 파티클 업데이트 - 네트워크 패킷 파싱 → CRTP, variant, 컨테이너 분리 고려 [Cold Path - virtual OK] 가끔 호출되는 곳: - 초기화/종료 - 이벤트 핸들러 - UI 상호작용 - 파일 I/O → 다형성의 유연함 > 약간의 오버헤드
[체크리스트] virtual 쓰기 전에 물어볼 것: 1. 정말 런타임 다형성이 필요한가? → 타입이 컴파일 타임에 알려진다면 CRTP 2. Hot Path에서 호출되나? → 그렇다면 다른 방법 고려 3. 컨테이너에 여러 타입을 섞어야 하나? → 아니라면 타입별 분리 4. 상속 계층이 깊은가? → 깊으면 컴포지션 고려 5. 이 클래스가 상속될 일이 없나? → final 붙이기

핵심 정리

  • vtable = 클래스당 하나, virtual 함수 포인터 테이블
  • vptr = 객체당 하나, vtable을 가리키는 포인터 (8바이트)
  • 간접 호출 = vptr → vtable → 함수, 분기 예측 어려움
  • 인라인 불가 = 컴파일러가 호출 대상을 몰라서 최적화 차단
  • 캐시 미스 = 다형적 컨테이너에서 심각
  • CRTP = 컴파일 타임 다형성, vtable 없음
  • std::variant = 타입 안전한 유니온, 캐시 친화적
  • 컨테이너 분리 = 같은 타입끼리 모아서 처리
  • final = 컴파일러에게 최적화 힌트
  • Hot Path에서는 virtual 피하고, Cold Path에서는 OK
