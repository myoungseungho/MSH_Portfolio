왜 virtual 함수가 많으면 느려질까?

vtable의 비밀과 게임 서버에서 가상 함수를 다루는 법

Part 1. 가상 함수가 뭐야?

virtual 키워드를 왜 붙이는 거야?

다형성(Polymorphism)을 위해서예요. 부모 타입으로 자식을 다룰 때 필요해요.

비유: 리모컨과 가전제품

"전원 켜기" 버튼이 있는 만능 리모컨이 있다고 해봐요.

  • TV를 향하면 → TV 전원이 켜짐
  • 에어컨을 향하면 → 에어컨 전원이 켜짐
  • 선풍기를 향하면 → 선풍기 전원이 켜짐

같은 버튼인데 대상에 따라 다르게 동작해요!

virtual이 이걸 가능하게 합니다.

// virtual 없이 class Monster { public: void Attack() { cout << "기본 공격"; } }; class Dragon : public Monster { public: void Attack() { cout << "불 뿜기!"; } }; Monster* m = new Dragon(); m->Attack(); // 출력: "기본 공격" 😱 // Dragon인데 Monster의 함수가 호출됨!
// virtual 사용 class Monster { public: virtual void Attack() { cout << "기본 공격"; } }; class Dragon : public Monster { public: void Attack() override { cout << "불 뿜기!"; } }; Monster* m = new Dragon(); m->Attack(); // 출력: "불 뿜기!" ✓ // 실제 타입(Dragon)의 함수가 호출됨!
그럼 뭐가 문제야? 항상 virtual 쓰면 안 돼?

공짜가 아닙니다! 편의를 위해 성능 비용을 지불해요.

virtual 함수의 비용
• 메모리: 객체마다 vptr (포인터 하나) 추가
• 속도: 함수 호출 시 간접 참조 필요
• 최적화 제한: 인라인 불가능

Part 2. vtable이 뭐야?

virtual을 쓰면 내부적으로 뭐가 달라지는 거야?

컴파일러가 vtable (가상 함수 테이블)을 만들어요!

비유: 전화번호부

각 클래스가 자기만의 전화번호부를 가지고 있다고 생각해요.

  • Monster 전화번호부: Attack → 기본공격 함수 주소
  • Dragon 전화번호부: Attack → 불뿜기 함수 주소
  • Slime 전화번호부: Attack → 점프공격 함수 주소

객체는 자기 클래스의 전화번호부 위치(vptr)를 기억하고 있어요.

vtable 구조: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [클래스별 vtable - 전역 데이터] │ │ │ │ Monster_vtable: Dragon_vtable: │ │ ┌─────────────────┐ ┌─────────────────┐ │ │ │ Attack() → 0x100│ │ Attack() → 0x200│ │ │ │ Move() → 0x110│ │ Move() → 0x210│ │ │ │ Die() → 0x120│ │ Die() → 0x220│ │ │ └─────────────────┘ └─────────────────┘ │ │ │ │ [객체 인스턴스] │ │ │ │ Monster m1: Dragon d1: │ │ ┌─────────────────┐ ┌─────────────────┐ │ │ │ vptr ──────────────→ │ vptr ──────────────→ │ │ │ Monster_vtable │ Dragon_vtable │ │ ├─────────────────┤ ├─────────────────┤ │ │ │ hp = 100 │ │ hp = 500 │ │ │ │ mp = 50 │ │ mp = 200 │ │ │ └─────────────────┘ └─────────────────┘ │ │ │ │ 호출 과정: m->Attack() │ │ 1. m의 vptr 읽기 │ │ 2. vtable에서 Attack 슬롯 찾기 │ │ 3. 해당 주소로 점프 │ │ │ └─────────────────────────────────────────────────────────────┘
일반 함수 호출이랑 뭐가 달라?
1
일반 함수: 주소가 컴파일 타임에 결정됨 → call 0x12345
2
가상 함수: 런타임에 vtable 조회 필요 → call [vptr + offset]
// 일반 함수 호출 (컴파일 결과) // 직접 점프 - 한 번에 끝! call Monster::Attack ; 주소가 고정되어 있음 // 가상 함수 호출 (컴파일 결과) // 3단계 필요! mov rax, [rcx] ; 1. 객체에서 vptr 읽기 mov rax, [rax + 0] ; 2. vtable에서 함수 주소 읽기 call rax ; 3. 해당 주소로 점프
추가 비용 정리
• 메모리 읽기 2번 추가 (vptr, vtable)
• 캐시 미스 가능성 (vtable이 멀리 있으면)
• 분기 예측 어려움 (어디로 점프할지 모름)

Part 3. 얼마나 느려지는 건데?

진짜 체감될 정도로 느려?

상황에 따라 다릅니다!

상황별 영향: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [영향 거의 없음] │ │ ───────────────────────────────────────────── │ │ • 가끔 호출되는 함수 (이벤트 핸들러) │ │ • 함수 내부 로직이 무거운 경우 (DB 쿼리, 파일 I/O) │ │ • 분기 예측이 잘 맞는 경우 (항상 같은 타입) │ │ │ │ [영향 심각함] ⚠️ │ │ ───────────────────────────────────────────── │ │ • 초당 수백만 번 호출되는 hot path │ │ • 함수 자체가 아주 가벼운 경우 (getter/setter) │ │ • 다양한 타입이 섞여서 분기 예측 실패 │ │ • 캐시 미스가 자주 발생 │ │ │ └─────────────────────────────────────────────────────────────┘
구체적인 숫자로 보여줘!
// 벤치마크 시나리오: 1000만 번 호출 // 테스트 1: 일반 함수 class Normal { int GetValue() { return value; } // 인라인됨! }; // 결과: ~3ms (대부분 최적화로 사라짐) // 테스트 2: 가상 함수 (같은 타입만) class Virtual { virtual int GetValue() { return value; } }; // 결과: ~15ms (분기 예측 성공) // 테스트 3: 가상 함수 (타입 섞임) // monsters = {Dragon, Slime, Goblin, Dragon, Slime...} for (Monster* m : monsters) { m->GetValue(); // 매번 다른 vtable! } // 결과: ~45ms (분기 예측 실패, 캐시 미스)
호출 방식 1000만 회 소요 시간 상대 비용
일반 함수 (인라인) ~3ms 1x
가상 함수 (같은 타입) ~15ms 5x
가상 함수 (타입 혼합) ~45ms 15x
핵심 인사이트
• 단순 비교: 가상 함수가 5~15배 느림
• 하지만! 1000만 번 호출해도 45ms
• 진짜 문제는 다른 타입이 섞일 때 (분기 예측 실패)

Part 4. 인라인이 왜 안 되는 게 문제야?

인라인이 뭔데? 왜 중요해?

인라인은 함수 호출을 함수 본문으로 대체하는 최적화예요.

비유: 전화 vs 직접 말하기

일반 함수 호출 = 전화하기

  • 전화 걸기 → 연결 대기 → 용건 말하기 → 끊기
  • 오버헤드가 있음

인라인 = 옆에 있는 사람한테 바로 말하기

  • 그냥 바로 말함
  • 오버헤드 없음!
// 인라인 전 int GetHP() { return hp; } for (int i = 0; i < 10000; i++) { total += monsters[i].GetHP(); // 함수 호출 10000번! } // 인라인 후 (컴파일러가 자동 변환) for (int i = 0; i < 10000; i++) { total += monsters[i].hp; // 함수 호출 없음! } // 더 나아가면 (벡터화 등 추가 최적화) // SIMD로 한 번에 여러 개 더하기도 가능!
가상 함수는 왜 인라인이 안 돼?

컴파일 시점에 어떤 함수인지 모르니까요!

왜 인라인이 불가능한가: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [일반 함수] │ │ │ │ Monster m; │ │ m.GetHP(); → 컴파일러: "Monster::GetHP()구나!" │ │ "인라인 할게!" │ │ → total += m.hp; │ │ │ │ [가상 함수] │ │ │ │ Monster* m = GetSomeMonster(); // Dragon? Slime? 모름! │ │ m->GetHP(); → 컴파일러: "Monster::GetHP()? 아니면 │ │ Dragon::GetHP()? Slime::GetHP()?│ │ 모르겠다... 인라인 포기 😢" │ │ │ │ → 런타임에 vtable 봐야 알 수 있음 │ │ → 컴파일 타임 최적화 불가 │ │ │ └─────────────────────────────────────────────────────────────┘
인라인 실패의 연쇄 효과
• 인라인 안 됨 → 함수 호출 오버헤드 발생
• 인라인 안 됨 → 후속 최적화도 막힘 (상수 전파, 벡터화 등)
• 인라인 안 됨 → 캐시 효율 저하 (코드가 흩어짐)

Part 5. 그럼 어떻게 해결해?

가상 함수 대신 뭘 쓸 수 있어?

여러 가지 대안이 있어요!

1
CRTP - 컴파일 타임 다형성 (템플릿)
2
enum + switch - 타입 태그 기반
3
함수 포인터 - 직접 저장
4
std::variant - 모던 C++ 방식
CRTP가 뭐야?

Curiously Recurring Template Pattern - 템플릿으로 다형성 구현!

// CRTP 패턴 template<typename Derived> class Monster { public: void Attack() { // 자식 클래스의 함수를 직접 호출! static_cast<Derived*>(this)->AttackImpl(); } }; class Dragon : public Monster<Dragon> { public: void AttackImpl() { cout << "불 뿜기!"; } }; class Slime : public Monster<Slime> { public: void AttackImpl() { cout << "점프 공격!"; } }; // 사용 Dragon d; d.Attack(); // 컴파일 타임에 Dragon::AttackImpl()로 결정! // 인라인 가능! vtable 없음!
CRTP 장점
• vtable 없음 → 메모리 절약
• 인라인 가능 → 성능 향상
• 컴파일 타임 체크

단점
• 이기종 컬렉션 불가 (Dragon과 Slime을 같은 배열에 못 넣음)
• 코드가 복잡해질 수 있음
enum + switch 방식은?
// enum + switch 방식 enum class MonsterType { Dragon, Slime, Goblin }; struct Monster { MonsterType type; int hp; int damage; void Attack() { switch (type) { case MonsterType::Dragon: cout << "불 뿜기! 데미지: " << damage * 2; break; case MonsterType::Slime: cout << "점프 공격! 데미지: " << damage; break; case MonsterType::Goblin: cout << "칼 공격! 데미지: " << damage; break; } } }; // 사용 Monster monsters[1000]; // 같은 배열에 모든 타입! for (auto& m : monsters) { m.Attack(); // switch로 분기 }
장점
• 메모리 연속 배치 가능 (캐시 친화적)
• 분기 예측이 잘 될 수 있음
• 코드가 명확함

단점
• 새 타입 추가 시 모든 switch 수정 필요
• 타입별 데이터 크기가 다르면 복잡해짐
std::variant는?
// std::variant (C++17) struct Dragon { void Attack() { cout << "불!"; } }; struct Slime { void Attack() { cout << "점프!"; } }; struct Goblin { void Attack() { cout << "칼!"; } }; using Monster = std::variant<Dragon, Slime, Goblin>; // 사용 std::vector<Monster> monsters; monsters.push_back(Dragon{}); monsters.push_back(Slime{}); for (auto& m : monsters) { std::visit([](auto& monster) { monster.Attack(); }, m); } // 장점: // - 타입 안전 (컴파일 타임 체크) // - 메모리 연속 배치 // - 모던하고 깔끔한 문법

Part 6. 게임 서버에서는 어떻게 적용해?

실제 게임 서버에서 어떻게 써?

상황에 맞게 선택합니다!

사용 상황별 가이드: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [virtual 써도 되는 경우] │ │ ───────────────────────────────────────────── │ │ • 패킷 핸들러 (가끔 호출) │ │ • 이벤트 시스템 (실행 빈도 낮음) │ │ • 플러그인/모듈 시스템 │ │ • 확장성이 중요한 곳 │ │ │ │ [virtual 피해야 하는 경우] ⚠️ │ │ ───────────────────────────────────────────── │ │ • 매 틱마다 호출되는 Update() │ │ • 수천~수만 객체 순회 │ │ • getter/setter 같은 작은 함수 │ │ • 성능 크리티컬 루프 내부 │ │ │ └─────────────────────────────────────────────────────────────┘
몬스터 시스템 예시를 보여줘!

Part 7. 면접에서 물어보면?

"가상 함수의 오버헤드를 설명하세요"라고 하면?

✅ 핵심 답변 포인트

1. vtable 메커니즘

"가상 함수가 있는 클래스는 vtable을 갖고, 객체는 vptr로 vtable을 가리킵니다. 함수 호출 시 vptr → vtable → 함수 주소 순으로 간접 참조가 필요합니다."

2. 오버헤드 종류

"메모리(vptr), 간접 호출 비용, 캐시 미스 가능성, 그리고 인라인 불가로 인한 최적화 제한이 있습니다."

3. 실제 영향

"단순 호출은 5배, 타입이 섞이면 15배까지 느려질 수 있지만, 호출 빈도와 함수 무게에 따라 영향이 달라집니다."

4. 대안

"CRTP로 컴파일 타임 다형성, enum+switch, std::variant 등이 있고, 게임 서버에서는 hot path에만 선별 적용합니다."

핵심 숫자는?
핵심 숫자 정리: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [메모리 오버헤드] │ │ • vptr 크기: 8바이트 (64비트) │ │ • 100만 객체 × 8바이트 = 8MB │ │ │ │ [호출 오버헤드] │ │ • 일반 함수: ~1 cycle (인라인 시 0) │ │ • 가상 함수: ~10-25 cycles │ │ • 캐시 미스 시: +100 cycles │ │ │ │ [벤치마크 결과] │ │ • 같은 타입: ~5배 느림 │ │ • 타입 혼합: ~15배 느림 │ │ │ │ [게임 서버 기준] │ │ • 60fps = 16.6ms/frame │ │ • 1만 몬스터 × 가상함수 Update = ~0.5ms (허용 범위) │ │ • 1만 몬스터 × 10개 가상함수 = ~5ms (문제!) │ │ │ └─────────────────────────────────────────────────────────────┘

핵심 정리

  • vtable: 클래스별 가상 함수 주소 테이블, 객체는 vptr로 가리킴
  • 오버헤드: 메모리(8B/객체), 간접 호출, 캐시 미스, 인라인 불가
  • 인라인 불가가 가장 큰 성능 손실 원인 (후속 최적화도 막힘)
  • 타입 혼합 시 분기 예측 실패로 15배까지 느려질 수 있음
  • CRTP: 컴파일 타임 다형성으로 인라인 가능
  • enum+switch: 간단하고 캐시 친화적
  • 하이브리드: 데이터는 연속 배치, 복잡한 로직만 virtual
  • hot path에만 최적화 적용, 나머지는 virtual 사용 OK
