Rust

Systems Programming Memory Safety
Rust Ownership Borrow Checker unsafe

개요

C++의 성능을 유지하면서, 메모리 버그를 컴파일 타임에 잡아주는 언어. GC 없이, 런타임 오버헤드 없이, 안전성 확보.

1C++의 문제점

질문
C++이 빠른데, 왜 위험하다고 하지? 
// C++ - 이런 코드가 컴파일 됨
int* ptr = new int(42);
delete ptr;
std::cout << *ptr;  // 💥 Use-after-free (컴파일 OK, 런타임에 터짐)

int* p = nullptr;
*p = 5;             // 💥 Null pointer dereference

int arr[5];
arr[10] = 1;        // 💥 Buffer overflow
문제

C++은 이런 메모리 버그를 컴파일러가 안 잡아줌. 프로그래머 책임. 런타임에 터지거나, 더 무서운 건 조용히 잘못된 동작.

질문
그럼 Java, C#처럼 GC 쓰면 되지 않아?
트레이드오프

GC는 안전하지만 느려. 런타임 오버헤드, JIT 컴파일, VM... 성능이 중요한 곳에서는 못 씀.

C++ Java/C#
성능 빠름 (네이티브) 느림 (GC, VM)
안전성 위험 (수동 관리) 안전 (GC)
핵심 질문
성능도 잡고 안전성도 잡을 수는 없을까?

2해결책: 컴파일 타임 검사

생각해보면...

컴파일 때 메모리 시뮬레이션 돌려보면 안 될까?

int* ptr = new int(42);

if (userInput > 0) {   // 사용자가 뭘 입력할지 모름
    delete ptr;
}

*ptr = 10;  // 위험한가? → 입력값에 따라 다름!
시뮬레이션은 불가능

모든 경우의 수가 무한대 (조합 폭발). 런타임 입력, 루프, 재귀...

Rust의 접근

시뮬레이션이 아니라, "이 규칙만 따르면 메모리 버그가 원천적으로 불가능"하게 만드는 것!

  • 시뮬레이션 = 모든 도로를 달려보며 사고 날 곳 찾기 (불가능)
  • 규칙 기반 = "빨간불에 못 가게 막으면 사고 안 남" (원천 차단)

3Ownership (소유권)

질문
C++에서 메모리 버그가 나는 근본 원인이 뭘까? 
// C++ - 누가 주인인지 불명확
int* ptr = new int(42);
int* ptr2 = ptr;      // 둘 다 같은 메모리를 가리킴
delete ptr;           // ptr이 해제
*ptr2 = 10;           // ptr2는 몰라... 💥
생각해보면...

주인을 하나로 정하면 되지 않을까?

정확해! 그게 Rust의 Ownership 규칙

Rust의 Ownership 규칙

  1. 모든 값은 "주인(owner)"이 딱 하나
  2. 주인이 스코프를 벗어나면 자동으로 메모리 해제
  3. 소유권은 "이동(move)"할 수 있음
// Rust - 소유권 이동
let s1 = String::from("hello");
let s2 = s1;          // 소유권이 s2로 "이동"

println!("{}", s1);   // ❌ 컴파일 에러! "s1은 더 이상 주인 아님"
println!("{}", s2);   // ✅ OK
// 컴파일러 에러 메시지
error: value borrowed after move
 --> src/main.rs:4:20
  |
2 |     let s2 = s1;
  |              -- value moved here
4 |     println!("{}", s1);
  |                    ^^ value used after move

4Borrowing (빌려쓰기)

질문
소유권을 넘기지 않고 "잠깐 빌려쓰기"는 어떻게 해?
생각해보면...

스마트 포인터처럼 shared_ptr, unique_ptr 같은 거?

비슷하지만 결정적 차이

C++ 스마트 포인터는 선택, Rust는 강제

C++ Rust
unique_ptr 쓰면 좋음 (선택) 기본 동작 (강제)
shared_ptr 참조 카운팅 (런타임 비용) Rc<T> 있음 (명시적 선택)
raw 포인터 아무때나 사용 가능 unsafe 블록에서만
컴파일러 체크 안 함 강제로 함 
// Rust 빌려쓰기

// 읽기 전용 빌려쓰기: 여러 개 OK
let s = String::from("hello");
let r1 = &s;   // 읽기 전용 빌림
let r2 = &s;   // 읽기 전용 빌림 (여러 개 가능)
println!("{}, {}", r1, r2);  // ✅ OK

// 쓰기 빌려쓰기: 하나만!
let mut s = String::from("hello");
let r1 = &mut s;  // 쓰기 빌림
let r2 = &mut s;  // ❌ 컴파일 에러! "동시에 두 개가 수정하면 안 돼"

빌려쓰기 규칙

  • 읽기(&) 여러 개 OK
  • 쓰기(&mut) 하나만
  • 읽기와 쓰기 동시에 X

이 규칙 덕분에 데이터 레이스가 컴파일 타임에 차단됨!

5unsafe - 안전벨트 풀기

질문
항상 안전한 코드만 쓸 수 있어?
아니, 때로는 위험한 짓이 필요

하드웨어 직접 제어, FFI(다른 언어 연동) 등.

// unsafe 블록 - "여기는 내가 책임질게"
unsafe {
    // raw 포인터 역참조
    let ptr = 0x12345 as *const i32;
    println!("Value: {}", *ptr);

    // C 함수 호출
    libc::printf("Hello from C!\n");
}

unsafe의 의미

"컴파일러야, 여기는 네가 검사 못해. 내가 안전하다고 보장할게."

언어 unsafe 개념
C++ 기본이 전부 unsafe (키워드 없음)
C# unsafe 블록 = 포인터 쓸 때 (거의 안 씀)
Rust unsafe 블록 = "여기만 위험해" 명시

unsafe에서만 가능한 것들

  1. raw 포인터 역참조
  2. unsafe 함수 호출
  3. 가변 정적 변수 접근
  4. unsafe 트레이트 구현
  5. union 필드 접근

주의!

unsafe는 "Rust의 안전성 보장이 없다"는 뜻. 버그 나면 C++처럼 런타임에 터짐. 최소한으로 사용!

6Rust의 현실

장점

  • C++ 수준 성능
  • 메모리 안전성 (컴파일 타임)
  • 데이터 레이스 방지
  • GC 없음 (예측 가능한 성능)
  • 현대적 도구 (cargo, rustfmt)

단점

  • 학습 곡선 가파름
  • 개발 속도 느림 (컴파일러와 싸움)
  • 컴파일 시간 김
  • 생태계가 C++보다 작음
  • 레거시 코드 없음
질문
그럼 Rust가 이렇게 좋으면 왜 아직 C++을 많이 쓸까?
상황 선택
새 프로젝트, 안전성 중요 Rust 고려
기존 C++ 코드베이스 C++ 유지
게임 엔진, 기존 생태계 C++
시스템 프로그래밍, 보안 중요 Rust 떠오르는 중

결론

Rust는 C++을 "대체"하기보다 "새로운 선택지"로 공존 중.

C++ 개발자라면 Rust 배워볼 만한 가치 있음.

핵심 정리

개념 설명
Ownership 모든 값은 주인이 하나. 주인이 스코프 벗어나면 해제.
Move 소유권 이동. 원래 변수는 더 이상 사용 불가.
Borrow (&) 읽기 전용 빌림. 여러 개 가능.
Mutable Borrow (&mut) 쓰기 빌림. 하나만 가능.
unsafe 컴파일러 검사 비활성화. 위험한 작업용. 
// Rust 한눈에 보기
fn main() {
    // Ownership
    let s1 = String::from("hello");
    let s2 = s1;  // move
    // s1 사용 불가

    // Borrowing
    let s = String::from("world");
    let r = &s;   // borrow
    println!("{}, {}", s, r);  // 둘 다 사용 가능

    // Mutable borrow
    let mut v = vec![1, 2, 3];
    let r = &mut v;
    r.push(4);  // 수정 가능
}
