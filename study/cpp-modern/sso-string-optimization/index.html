왜 string 복사가 그렇게 비쌀까?

SSO, Move Semantics, 그리고 게임 서버 문자열 최적화

Part 1. 문자열 복사가 왜 비싸?

std::string 복사가 느리다고?

네, 특히 긴 문자열은요! 내부적으로 무슨 일이 일어나는지 봐요.

비유: 책 복사하기

int 복사 = 메모장에 숫자 하나 적기

  • 4바이트 그냥 복사 끝!

string 복사 = 책 전체를 복사기로 복사

  • 새 종이 준비 (메모리 할당)
  • 한 글자씩 복사 (데이터 복사)
  • 원본이 100페이지면 100페이지 다 복사!
// string 복사 시 내부 동작 std::string original = "Hello, World! This is a test string."; std::string copy = original; // 여기서 무슨 일이? // 1단계: 메모리 할당 (malloc 호출!) // - 시스템 콜 가능성 // - 힙 탐색 오버헤드 // - 락 경합 가능 (멀티스레드) // 2단계: 데이터 복사 (memcpy) // - 36바이트 복사 // - 캐시 라인 오염 // 3단계: null terminator 처리 // 만약 소멸되면? // 4단계: 메모리 해제 (free 호출!)
메모리 할당이 왜 그렇게 느려?

힙 할당은 복잡한 작업입니다!

메모리 할당 과정: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [스택 할당 - int a = 5;] │ │ ───────────────────────────────────────────── │ │ 스택 포인터 이동 끝! (1 CPU 명령어) │ │ │ │ [힙 할당 - new char[100]] │ │ ───────────────────────────────────────────── │ │ 1. 힙 자료구조 탐색 (빈 공간 찾기) │ │ 2. 적절한 크기의 블록 선택 │ │ 3. 블록 분할 (필요시) │ │ 4. 메타데이터 업데이트 │ │ 5. 멀티스레드면 락 획득/해제! │ │ │ │ 비용 비교: │ │ • 스택 할당: ~1 cycle │ │ • 힙 할당: ~100-1000 cycles │ │ • 락 경합 시: ~10,000+ cycles │ │ │ └─────────────────────────────────────────────────────────────┘
그럼 string 쓰지 말라는 거야?

아뇨! 최적화 기법들이 있어요. 첫 번째가 SSO입니다!

Part 2. SSO (Small String Optimization)

SSO가 뭐야?

짧은 문자열은 힙 할당 없이 객체 안에 직접 저장!

비유: 지갑 vs 가방

긴 문자열 = 큰 짐 → 가방(힙)에 넣어야 함

짧은 문자열 = 동전 몇 개 → 지갑(객체 내부)에 그냥 넣음

굳이 가방 꺼내지 않고 지갑에서 바로 꺼내는 게 빠르잖아요!

SSO 메모리 구조: ┌─────────────────────────────────────────────────────────────┐ │ │ │ std::string 객체 (보통 24~32바이트) │ │ │ │ [긴 문자열 모드] │ │ ┌────────────────────────────────┐ │ │ │ ptr ──────────────────────→ [힙: "Hello, World!..."] │ │ │ size = 100 │ │ │ │ capacity = 128 │ │ │ └────────────────────────────────┘ │ │ │ │ [SSO 모드 - 짧은 문자열] │ │ ┌────────────────────────────────┐ │ │ │ buffer: "Hello" │ ← 힙 할당 없이 │ │ │ (내부 버퍼에 직접!) │ 객체 안에 저장! │ │ │ size = 5 │ │ │ └────────────────────────────────┘ │ │ │ │ SSO 임계값 (구현마다 다름): │ │ • MSVC: 15자 │ │ • GCC: 15자 │ │ • Clang/libc++: 22자 │ │ │ └─────────────────────────────────────────────────────────────┘
SSO면 복사도 빠른 거야?

네! 힙 할당 없이 그냥 객체만 복사하면 됩니다!

// SSO가 적용되는 경우 std::string name = "Player"; // 6자 → SSO! std::string copy = name; // 힙 할당 없이 복사! // 내부적으로: // memcpy(©, &name, sizeof(string)); // 24~32바이트만! // 힙 할당 없음, free도 필요 없음! // SSO가 적용 안 되는 경우 std::string message = "This is a very long message that exceeds SSO limit"; std::string copy2 = message; // 힙 할당 발생! 😢
문자열 길이 SSO 적용 복사 비용
1~15자 ✓ 적용 ~20 cycles
16~100자 ✗ 미적용 ~200 cycles
100자 이상 ✗ 미적용 ~500+ cycles

Part 3. Move Semantics (이동 의미론)

긴 문자열은 방법이 없어?

Move! 복사 대신 소유권을 넘기는 방법이 있어요!

비유: 이사

복사 (Copy) = 집에 있는 물건 다 똑같이 새로 사기

  • 돈도 많이 들고, 시간도 오래 걸림

이동 (Move) = 물건을 그냥 새 집으로 옮기기

  • 원래 집은 빈 집이 됨
  • 물건은 그대로, 주소만 바뀜!
// 복사 vs 이동 std::string original = "This is a very long string..."; // 복사: 새 메모리 할당 + 전체 복사 std::string copy = original; // original: "This is a very long string..." // copy: "This is a very long string..." (새로 할당!) // 이동: 포인터만 옮김! std::string moved = std::move(original); // original: "" (빈 문자열이 됨!) // moved: "This is a very long string..." (원래 메모리 그대로!)
Move의 내부 동작: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [복사 전] │ │ │ │ original: │ │ ┌──────────────────┐ ┌─────────────────────────────┐ │ │ │ ptr ─────────────│────→│ "This is a very long..." │ │ │ │ size = 50 │ └─────────────────────────────┘ │ │ └──────────────────┘ │ │ │ │ [복사 후 - copy = original] │ │ │ │ original: copy: │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ ptr ────────│──→ [A] │ ptr ────────│──→ [B] (새 할당!)│ │ └─────────────┘ └─────────────┘ │ │ │ │ [이동 후 - moved = std::move(original)] │ │ │ │ original: moved: │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ ptr → null │ │ ptr ────────│──→ [A] (같은 메모리!)│ │ │ size = 0 │ │ size = 50 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ Move = 포인터 3개 복사 끝! (힙 할당 없음) │ │ │ └─────────────────────────────────────────────────────────────┘
언제 Move가 자동으로 일어나?
자동 Move 발생 조건
• 함수에서 지역 변수 return 할 때 (NRVO/RVO)
• 임시 객체 (rvalue) 대입할 때
• std::move() 명시적 호출
• STL 컨테이너 재할당 시
// 자동 Move 예시 // 1. 함수 반환 (RVO/NRVO) std::string CreateMessage() { std::string msg = "Hello"; return msg; // 자동으로 Move! } // 2. 임시 객체 std::string name = std::string("Player") + "_001"; // 임시 객체가 Move됨! // 3. 명시적 Move std::vector names; std::string temp = "LongName..."; names.push_back(std::move(temp)); // temp는 이제 빈 문자열

Part 4. string_view - 복사 자체를 피하기

복사도, 이동도 없이 문자열 다루는 방법은?

std::string_view! 읽기 전용 "창문" 같은 거예요.

비유: 전시장 유리창

string 복사 = 그림을 통째로 복제해서 가져가기

string_view = 유리창 너머로 그림 보기

  • 그림(원본)은 그대로
  • 나는 포인터(유리창 위치)만 기억
  • 비용: 거의 0!
// string_view 사용 void ProcessName(const std::string& name); // 참조 전달 void ProcessName(std::string_view name); // 더 좋음! // 왜 string_view가 더 좋아? // Case 1: string 전달 std::string s = "Hello"; ProcessName(s); // 둘 다 OK // Case 2: 문자열 리터럴 전달 ProcessName("Hello"); // const string& 버전: // "Hello" → 임시 std::string 생성 (힙 할당 가능!) // → 함수 호출 // → 임시 객체 파괴 // string_view 버전: // "Hello"의 포인터 + 길이만 전달 // → 힙 할당 없음!
string_view 내부 구조: ┌─────────────────────────────────────────────────────────────┐ │ │ │ string_view = 포인터 + 길이 (16바이트!) │ │ │ │ ┌──────────────────┐ │ │ │ ptr ─────────────│────→ "Hello, World!" │ │ │ length = 13 │ (어딘가에 있는 원본) │ │ └──────────────────┘ │ │ │ │ 원본이 string이든, char[]이든, 리터럴이든 상관없음! │ │ │ │ 주의: 원본이 사라지면 dangling pointer! │ │ │ │ // 위험한 코드! │ │ std::string_view GetView() { │ │ std::string temp = "Hello"; │ │ return temp; // temp가 사라짐! │ │ } // 반환된 view는 dangling! │ │ │ └─────────────────────────────────────────────────────────────┘
string_view 주의사항은?
⚠️ string_view 주의사항
• 소유권 없음: 원본이 사라지면 dangling!
• null-terminated 아님: C 함수에 직접 전달 불가
• 저장하지 말 것: 멤버 변수로 저장 위험

✓ 안전한 사용
• 함수 매개변수로 사용
• 지역 범위에서만 사용
• 원본 수명이 확실할 때만 사용

Part 5. 게임 서버 실전 최적화

게임 서버에서 문자열 어떻게 다뤄?

여러 기법을 조합합니다!

게임 서버 문자열 최적화 전략: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [1] 고정 크기 버퍼 사용 │ │ ───────────────────────────────────────────── │ │ struct PlayerName { │ │ char name[16]; // 힙 할당 없음! │ │ }; │ │ │ │ [2] 문자열 인터닝 (Interning) │ │ ───────────────────────────────────────────── │ │ 같은 문자열은 하나만 저장하고 ID로 참조 │ │ "Warrior" → ID: 1001 │ │ "Mage" → ID: 1002 │ │ │ │ [3] 문자열 풀 (String Pool) │ │ ───────────────────────────────────────────── │ │ 미리 할당된 버퍼에서 문자열 관리 │ │ 힙 단편화 방지, 할당 속도 향상 │ │ │ │ [4] 포맷 문자열 최소화 │ │ ───────────────────────────────────────────── │ │ sprintf보다 미리 만들어둔 템플릿 사용 │ │ │ └─────────────────────────────────────────────────────────────┘
실제 코드로 보여줘!
// 1. 고정 크기 버퍼 struct ChatMessage { uint32_t senderId; char content[256]; // 힙 할당 없음! uint8_t contentLength; }; // 2. 문자열 ID 매핑 (인터닝) class StringTable { std::unordered_mapuint32_t> stringToId; std::vector idToString; public: uint32_t GetId(const std::string& str) { auto it = stringToId.find(str); if (it != stringToId.end()) return it->second; uint32_t newId = idToString.size(); stringToId[str] = newId; idToString.push_back(str); return newId; } }; // 캐릭터 이름을 ID로 저장 struct Player { uint32_t nameId; // 4바이트! (vs string 32바이트) // ... }; // 3. 로그 메시지 최적화 // Bad: 매번 포맷 Log("Player %s joined channel %d", name, channelId); // Good: 구조화된 로그 struct JoinChannelLog { uint32_t playerId; uint16_t channelId; uint64_t timestamp; }; LogStruct(JoinChannelLog{playerId, channelId, Now()});

Part 7. 면접에서 물어보면?

"string 최적화 방법을 설명하세요"라고 하면?

✅ 핵심 답변 포인트

1. 문제 인식

"string 복사는 힙 할당 + 데이터 복사가 필요해서 비용이 큽니다. 특히 멀티스레드 환경에서 할당자 락 경합도 발생합니다."

2. SSO

"15자 이하 문자열은 SSO로 객체 내부 버퍼에 저장되어 힙 할당이 없습니다."

3. Move Semantics

"긴 문자열은 std::move로 소유권만 이전하면 포인터 복사로 끝납니다."

4. string_view

"읽기 전용이면 string_view로 포인터+길이만 전달합니다. 다만 원본 수명에 주의해야 합니다."

5. 게임 서버 특화

"고정 크기 버퍼, 문자열 인터닝, 구조화된 로그 등으로 힙 할당 자체를 최소화합니다."

핵심 숫자는?
핵심 숫자 정리: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [SSO 임계값] │ │ • MSVC/GCC: 15자 │ │ • libc++: 22자 │ │ │ │ [string 객체 크기] │ │ • 보통 24~32바이트 (구현마다 다름) │ │ │ │ [비용 비교] │ │ • 스택 할당: ~1 cycle │ │ • 힙 할당: ~100-1000 cycles │ │ • Move: ~5 cycles (포인터 3개 복사) │ │ • string_view: ~2 cycles (포인터+길이) │ │ │ │ [100만 회 벤치마크] │ │ • SSO 복사: ~15ms │ │ • 긴 문자열 복사: ~120ms (8배 느림) │ │ • Move: ~10ms │ │ • string_view: ~5ms │ │ │ └─────────────────────────────────────────────────────────────┘

핵심 정리

  • string 복사가 비싼 이유: 힙 할당 + 데이터 복사 + 해제
  • SSO: 15자 이하는 객체 내부 버퍼에 저장 (힙 할당 없음)
  • Move: 소유권 이전으로 포인터만 복사 (원본은 빈 상태)
  • string_view: 읽기 전용, 포인터+길이만 전달 (원본 수명 주의!)
  • 게임 서버: 고정 버퍼, 인터닝, 구조화 로그로 할당 최소화
  • 측정 결과: 긴 문자열 복사는 SSO 대비 ~8배 느림
  • 실전 가이드: SSO면 복사 OK, 길면 Move/참조, 읽기만 string_view
