예외 처리 vs 에러 코드

게임 서버에서 에러를 다루는 두 가지 철학

Part 1. 에러 처리가 왜 중요해?

에러 처리를 왜 그렇게 신경 써?

게임 서버에서 에러 = 유저 이탈이기 때문이에요!

비유: 놀이공원 운영

에러가 발생했을 때...

  • 무시: 롤러코스터가 고장났는데 계속 운영 → 사고!
  • 모두 정지: 한 기구 고장에 전체 놀이공원 폐쇄 → 과잉 대응
  • 적절한 처리: 해당 기구만 정지, 대기열 안내, 나머지 정상 운영

게임 서버도 마찬가지! 어떤 에러를 어떻게 처리할지가 중요해요.

에러 처리 실패의 결과: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [에러 무시] │ │ • 데이터 손상 │ │ • 보안 취약점 │ │ • 유저 불만 폭발 │ │ │ │ [과잉 대응 - 서버 크래시] │ │ • 모든 유저 강제 종료 │ │ • 매출 손실 │ │ • 유저 이탈 │ │ │ │ [적절한 처리] │ │ • 문제 있는 요청만 거절 │ │ • 에러 로깅 │ │ • 다른 유저는 정상 플레이 │ │ │ └─────────────────────────────────────────────────────────────┘
에러 처리 방법이 뭐가 있어?

크게 두 가지 철학이 있어요.

방식 특징 예시 언어
예외 (Exception) 에러 발생 시 특별한 경로로 탈출 Java, C#, Python, C++
에러 코드 반환값으로 성공/실패 전달 C, Go, Rust (Result)

Part 2. 예외(Exception)란?

예외가 정확히 뭐야?

"정상적인 흐름"을 벗어난 상황을 처리하는 메커니즘이에요.

비유: 긴급 탈출구

일반 코드 = 건물의 복도 (정상 이동)

예외 = 비상구로 바로 탈출!

  • 복도(일반 코드)를 따라가지 않고
  • 바로 비상구(catch 블록)로 점프!
// 예외 기본 사용법 void ProcessPayment(int amount) { if (amount <= 0) { throw std::invalid_argument("금액이 잘못됨!"); } if (amount > userBalance) { throw std::runtime_error("잔액 부족!"); } // 정상 처리... } // 호출 측 try { ProcessPayment(1000); SendItem(); SaveToDB(); } catch (const std::invalid_argument& e) { Log("입력 에러: %s", e.what()); } catch (const std::exception& e) { Log("에러 발생: %s", e.what()); }
예외 발생 시 스택 언와인딩: ┌─────────────────────────────────────────────────────────────┐ │ │ │ 호출 스택: │ │ │ │ ┌─────────────────────┐ │ │ │ ProcessPayment() │ ← throw! 예외 발생! │ │ └─────────────────────┘ │ │ ↑ │ │ ┌─────────────────────┐ │ │ │ SendItem() │ ← 건너뜀! │ │ └─────────────────────┘ │ │ ↑ │ │ ┌─────────────────────┐ │ │ │ SaveToDB() │ ← 건너뜀! │ │ └─────────────────────┘ │ │ ↑ │ │ ┌─────────────────────┐ │ │ │ try { ... } │ │ │ │ catch (exception) │ ← 여기로 바로 점프! │ │ └─────────────────────┘ │ │ │ │ 스택 언와인딩 중: │ │ • 각 함수의 지역 변수 소멸자 호출 │ │ • RAII 객체 정리 (파일 닫기, 락 해제 등) │ │ │ └─────────────────────────────────────────────────────────────┘

Part 3. 예외의 비용

예외가 느리다고 하던데?

"예외를 던지면" 느려요. 그냥 try-catch는 거의 공짜!

예외 비용 분석 (Zero-Cost Exception Model): ┌─────────────────────────────────────────────────────────────┐ │ │ │ [예외가 발생하지 않을 때] │ │ ───────────────────────────────────────────── │ │ try { │ │ NormalCode(); // 추가 비용 거의 0! │ │ } catch (...) { } │ │ │ │ 컴파일러가 정상 경로는 최적화 │ │ 테이블 기반으로 예외 처리 정보만 저장 │ │ → 정상 경로 비용: ~0 │ │ │ │ [예외가 발생했을 때] │ │ ───────────────────────────────────────────── │ │ throw exception; │ │ │ │ 1. 예외 객체 생성 (힙 할당 가능) │ │ 2. 스택 언와인딩 (각 프레임 정리) │ │ 3. catch 블록 탐색 │ │ 4. 핸들러 실행 │ │ → 비용: 수천~수만 cycles │ │ │ └─────────────────────────────────────────────────────────────┘
구체적으로 얼마나 느려?
상황 비용 비고
try 블록 (예외 없음) ~0 cycles Zero-cost
예외 throw ~10,000 cycles 스택 언와인딩
에러 코드 반환 ~1-5 cycles 그냥 return
에러 코드 검사 ~2 cycles 조건문
핵심 결론
• 예외가 "예외적"일 때: 예외 사용 OK (더 깔끔한 코드)
• 예외가 "자주 발생"할 때: 에러 코드가 낫다
• 게임 서버: 대부분 에러는 예상 가능해서 에러 코드 선호

Part 4. 에러 코드 방식

에러 코드가 뭐야?

함수 반환값으로 성공/실패를 알려주는 방식이에요!

// 에러 코드 정의 enum class ErrorCode { Success = 0, InvalidAmount, InsufficientBalance, ItemNotFound, InventoryFull, NetworkError, DatabaseError }; // 함수에서 에러 코드 반환 ErrorCode ProcessPayment(int amount) { if (amount <= 0) return ErrorCode::InvalidAmount; if (amount > userBalance) return ErrorCode::InsufficientBalance; // 처리... return ErrorCode::Success; } // 호출 측 ErrorCode result = ProcessPayment(1000); if (result != ErrorCode::Success) { HandleError(result); return; } // 성공 시 다음 로직...
에러 코드의 문제점은?

무시하기 쉽고, 코드가 지저분해질 수 있어요!

// 에러 코드의 문제점 // 1. 에러 무시 가능 😱 ProcessPayment(1000); // 반환값 무시! SendItem(); // 결제 실패했는데 아이템 지급?! // 2. 에러 체크 지옥 (Error Checking Hell) ErrorCode err; err = Step1(); if (err != ErrorCode::Success) { return err; } err = Step2(); if (err != ErrorCode::Success) { return err; } err = Step3(); if (err != ErrorCode::Success) { return err; } err = Step4(); if (err != ErrorCode::Success) { return err; } // 비즈니스 로직이 에러 체크에 묻힘...
예외 vs 에러 코드 코드 비교: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [예외 방식] - 깔끔한 정상 경로 │ │ ───────────────────────────────────────────── │ │ try { │ │ Step1(); │ │ Step2(); │ │ Step3(); │ │ Step4(); │ │ // 비즈니스 로직이 명확! │ │ } catch (const Error& e) { │ │ HandleError(e); │ │ } │ │ │ │ [에러 코드 방식] - 에러 체크가 끼어듦 │ │ ───────────────────────────────────────────── │ │ if (Step1() != OK) return err; │ │ if (Step2() != OK) return err; │ │ if (Step3() != OK) return err; │ │ if (Step4() != OK) return err; │ │ // 에러 체크와 로직이 섞임... │ │ │ └─────────────────────────────────────────────────────────────┘

Part 5. 모던 C++ 대안들

더 좋은 방법 없어?

std::optional, std::expected! 두 방식의 장점을 결합해요.

// std::optional - "값이 있거나 없거나" #include std::optional<Item> FindItem(int itemId) { auto it = items.find(itemId); if (it == items.end()) return std::nullopt; // 없음! return it->second; // 있음! } // 사용 auto item = FindItem(1001); if (item) { UseItem(*item); // 값 사용 } else { // 아이템 없음 처리 } // 또는 auto item = FindItem(1001).value_or(defaultItem);
// std::expected (C++23) - "값 또는 에러" #include std::expected<int, ErrorCode> ProcessPayment(int amount) { if (amount <= 0) return std::unexpected(ErrorCode::InvalidAmount); if (amount > balance) return std::unexpected(ErrorCode::InsufficientBalance); balance -= amount; return amount; // 성공 시 처리된 금액 반환 } // 사용 auto result = ProcessPayment(1000); if (result) { Log("결제 완료: %d", *result); } else { HandleError(result.error()); // 에러 코드 접근 } // 체이닝도 가능! (모나딕 연산) auto final = ProcessPayment(1000) .and_then([](int amount) { return SendItem(amount); }) .and_then([](Item item) { return SaveToDB(item); });
모던 C++ 에러 처리 장점
• 컴파일 타임 체크: 결과 무시 시 경고
• 값과 에러 동시 표현: 타입 시스템으로 강제
• 함수형 체이닝: 에러 체크 지옥 탈출
• 예외만큼 표현력 + 에러 코드만큼 빠름

Part 7. 면접에서 물어보면?

"예외와 에러 코드 중 뭘 선택하시겠습니까?"

✅ 핵심 답변 포인트

1. 트레이드오프 설명

"예외는 정상 경로가 깔끔하고 에러 전파가 자동이지만, throw 시 비용이 큽니다. 에러 코드는 빠르지만 무시될 수 있고 코드가 복잡해집니다."

2. 상황별 선택 기준

"예외적 상황(설정 파일 없음, 복구 불가 오류)에는 예외를, 예상 가능한 실패(입력 검증, 비즈니스 로직)에는 에러 코드를 사용합니다."

3. 게임 서버 특성

"게임 서버는 패킷 처리가 hot path이고 실패가 흔해서 에러 코드를 주로 사용합니다. 초기화나 설정 로딩에만 예외를 씁니다."

4. 모던 C++ 언급

"C++17의 optional, C++23의 expected 같은 타입으로 에러 코드의 단점을 보완할 수 있습니다."

핵심 숫자는?
핵심 숫자 정리: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [비용 비교] │ │ • try 블록 (예외 없음): ~0 cycles │ │ • throw 발생: ~10,000+ cycles │ │ • 에러 코드 반환: ~1-5 cycles │ │ • if 검사: ~2 cycles │ │ │ │ [벤치마크 (100만 회)] │ │ • 예외 0% 발생: 에러 코드와 비슷 │ │ • 예외 1% 발생: 에러 코드보다 ~10배 느림 │ │ • 예외 10% 발생: 에러 코드보다 ~100배 느림 │ │ │ │ [게임 서버 기준] │ │ • 패킷 처리: 초당 수만~수십만 건 │ │ • 검증 실패율: 1~10% (해킹 시도, 잘못된 요청) │ │ • → 예외 사용 시 심각한 성능 저하 │ │ │ └─────────────────────────────────────────────────────────────┘

핵심 정리

  • 예외: 정상 경로 깔끔, throw 비용 큼 (~10,000 cycles)
  • 에러 코드: 빠름 (~5 cycles), 무시 가능, 코드 복잡
  • Zero-cost Exception: 예외 안 터지면 비용 0
  • 게임 서버: 대부분 에러 코드, 초기화만 예외
  • std::optional: 값이 있거나 없거나
  • std::expected (C++23): 값 또는 에러, 체이닝 가능
  • 실전 기준: "예외적"이면 예외, "예상 가능"하면 에러 코드
  • 모든 에러는 로깅: 디버깅과 모니터링을 위해
