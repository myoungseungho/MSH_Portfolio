예외 처리 vs 에러 코드, 게임에선 뭐가 좋을까?

C++ 예외의 숨겨진 비용과 게임 업계의 선택

Part 1. C++ 예외란?

C++ 예외가 뭐야?

에러 상황에서 정상 흐름을 벗어나 처리하는 메커니즘이야.

[예외 기본 문법] // 예외 던지기 void Divide(int a, int b) { if (b == 0) { throw std::runtime_error("0으로 나눌 수 없음!"); } return a / b; } // 예외 받기 try { int result = Divide(10, 0); cout << result; } catch (const std::exception& e) { cout << "에러: " << e.what(); } // 출력: "에러: 0으로 나눌 수 없음!"
왜 예외를 쓰는 거야? 그냥 if문으로 체크하면 안 돼?

예외의 장점이 있어!

[예외의 장점] 1. 에러 무시 방지 // 에러 코드 - 무시 가능! int result = Divide(10, 0); // 에러 코드 무시하고 사용 // → 버그! // 예외 - 무시 불가능! int result = Divide(10, 0); // 예외 발생 시 여기서 멈춤 // → 반드시 처리해야 함 2. 코드 깔끔함 // 에러 코드 - if 지옥 int err = Step1(); if (err) return err; err = Step2(); if (err) return err; err = Step3(); if (err) return err; // 예외 - 깔끔 try { Step1(); Step2(); Step3(); } catch (...) { // 한 곳에서 처리 } 3. 생성자에서 에러 보고 class File { File(const char* path) { if (!open(path)) { throw FileNotFound(path); // 생성자는 반환값 없음! } } };

Part 2. 예외의 숨겨진 비용

예외가 왜 느리다고 해?

예외가 발생했을 때의 비용이 어마어마해!

[예외 발생 시 일어나는 일] throw std::runtime_error("에러!"); 1. 예외 객체 생성 - 힙 할당 (문자열 저장) - 타입 정보 기록 2. 스택 되감기 (Stack Unwinding) - 호출 스택을 거슬러 올라가며 - 각 함수의 지역 변수 소멸자 호출! 3. 예외 핸들러 탐색 - catch 블록 찾을 때까지 스택 탐색 - RTTI(런타임 타입 정보) 사용 4. 점프 - catch 블록으로 이동 [비용] 함수 호출 스택이 깊으면: main() → Process() → Update() → Calculate() → Error() Calculate에서 예외 발생: 1. Calculate의 소멸자들 호출 2. Update의 소멸자들 호출 3. Process의 소멸자들 호출 4. main의 catch로 도착 → 수천~수만 사이클 소요! → 일반 함수 반환의 1000배 이상
예외 안 던지면 비용 없어?

"제로 코스트 예외"라고 하지만... 완전히 공짜는 아니야.

[제로 코스트 예외?] 현대 컴파일러 (LLVM, GCC): - 예외 안 던지면 런타임 오버헤드 거의 0 하지만... 1. 코드 크기 증가 - 예외 처리 테이블 (unwind table) - 소멸자 호출 코드 - 바이너리 5-15% 증가 2. 최적화 제한 - 컴파일러가 코드 이동 제한 - 인라인 어려워짐 - noexcept 없으면 최적화 포기 3. 캐시 효율 감소 - 더 큰 코드 = 더 많은 캐시 미스 [벤치마크] 예외 던지기: 성공 경로: ~0ns (거의 공짜) 실패 경로: ~10,000ns (엄청 비쌈!) 에러 코드: 성공 경로: ~1ns (분기 비용) 실패 경로: ~1ns (분기 비용) → 예외는 "실패가 드물 때" 최적화된 전략

Part 3. 에러 코드의 문제점

그럼 에러 코드가 완벽해?

에러 코드도 심각한 문제가 있어!

[에러 코드의 문제점] 1. 무시하기 쉬움 int result = ParseConfig(path); // 에러 코드 무시! UseConfig(); // 💥 크래시 2. 반환값 오염 // 에러 코드가 반환값을 차지 int GetValue(); // 음수면 에러? 0이 에러? // 값과 에러 분리 필요 bool GetValue(int& out); pair GetValue(); // 귀찮음 3. 에러 전파 지옥 int ProcessA() { int err = StepA1(); if (err) return err; // 전파 err = StepA2(); if (err) return err; // 전파 err = StepA3(); if (err) return err; // 전파 return 0; } // 모든 함수에서 이런 보일러플레이트 4. 에러 정보 부족 return -1; // 왜 실패? 어디서 실패? // vs throw DetailedError("파일 열기 실패", path, errno);
에러 코드를 잘 쓰는 방법은?

현대적인 패턴들이 있어!

[에러 코드 개선 패턴] 1. enum class로 타입 안전성 enum class ErrorCode { Success = 0, FileNotFound, PermissionDenied, InvalidFormat }; ErrorCode OpenFile(const char* path); // → 정수와 혼동 없음 2. [[nodiscard]]로 무시 방지 (C++17) [[nodiscard]] ErrorCode DoSomething(); DoSomething(); // 경고! 반환값 무시됨 3. Result 타입 패턴 template struct Result { T value; ErrorCode error; bool ok() const { return error == ErrorCode::Success; } }; Result GetValue() { return { 42, ErrorCode::Success }; // 또는 return { 0, ErrorCode::FileNotFound }; } auto result = GetValue(); if (result.ok()) { Use(result.value); }

Part 4. 게임 업계의 선택

실제 게임 회사들은 뭘 써?

대부분 예외를 끈다!

[게임 업계 현실] 언리얼 엔진: - 예외 비활성화 (-fno-exceptions) - 자체 에러 처리 (check, verify, ensure 매크로) EA (EASTL): - 예외 없는 STL 대체 라이브러리 구글 (C++ 스타일 가이드): - "예외 사용하지 마라" 블리자드, 라이엇: - 예외 비활성화가 일반적 [이유] 1. 일관된 성능 → 예외 발생 시 성능 절벽 방지 2. 바이너리 크기 → 콘솔 게임은 메모리 제한 빡빡 3. 디버깅 → 예외보다 assert가 디버깅하기 쉬움 4. 레거시 → 오래된 코드베이스가 예외 없이 설계됨
[언리얼 엔진 스타일] // 예외 대신 매크로 void LoadAsset(const char* path) { UAsset* asset = FindAsset(path); check(asset); // 실패 시 크래시 (릴리즈에서도) checkf(asset, TEXT("Asset not found: %s"), path); verify(asset); // 실패 시 크래시, 조건은 항상 평가 ensure(asset); // 실패해도 계속, 로그만 (릴리즈에서 제거) ensureMsgf(asset, TEXT("Missing: %s"), path); } // 치명적 에러 if (!CriticalResource) { UE_LOG(LogCore, Fatal, TEXT("Critical failure!")); // Fatal은 에디터/게임 종료 } // 에러 반환 ELoadResult LoadConfig(FString& OutData) { if (!FileExists()) return ELoadResult::FileNotFound; if (!Parse()) return ELoadResult::ParseError; OutData = parsed; return ELoadResult::Success; }
그럼 예외는 절대 안 써?

상황에 따라 선택적으로 사용하기도 해.

[예외를 쓰는 경우] 1. 초기화/로딩 - 게임 시작 시 설정 파일 로드 - 리소스 초기화 → 이때는 성능보다 안정성 → 실패하면 어차피 게임 시작 불가 2. 도구 / 에디터 - 실시간 성능 덜 중요 - 에러 정보 상세하게 필요 - 사용자에게 친절한 메시지 3. 테스트 코드 - 테스트 실패 = 예외로 깔끔하게 4. 외부 라이브러리 경계 - 예외 쓰는 라이브러리 호출 시 - 경계에서 catch 후 에러 코드로 변환 [하이브리드 접근] // 외부 라이브러리 래퍼 ErrorCode LoadJson(const char* path, Json& out) { try { out = json::parse(ReadFile(path)); // 라이브러리가 예외 던짐 return ErrorCode::Success; } catch (const json::parse_error& e) { LogError("JSON parse failed: %s", e.what()); return ErrorCode::ParseError; } catch (...) { return ErrorCode::Unknown; } }
예외 에러 코드
성공 시 비용 거의 0 분기 1회
실패 시 비용 매우 높음 낮음
코드 크기 증가 작음
무시 방지 강제 쉽게 무시
에러 정보 풍부 제한적
게임 업계 대부분 비활성화 선호

Part 5. std::expected (C++23)

더 좋은 방법은 없어?

C++23의 std::expected가 답이야!

[std::expected란?] #include // 성공 시 값, 실패 시 에러 - 타입 안전하게! std::expected Divide(int a, int b) { if (b == 0) { return std::unexpected(ErrorCode::DivideByZero); } return a / b; // 암시적으로 expected 생성 } [사용법] auto result = Divide(10, 2); if (result) { // 또는 result.has_value() cout << "결과: " << *result; // 또는 result.value() } else { cout << "에러: " << result.error(); } // value_or로 기본값 int val = Divide(10, 0).value_or(-1); // -1 // monadic 연산 (C++23) auto final = Divide(100, 10) .and_then([](int v) { return Divide(v, 2); }) // 성공 시 체이닝 .transform([](int v) { return v * 2; }) // 값 변환 .or_else([](auto e) { return 0; }); // 에러 시 대체
예외랑 에러 코드의 장점을 합친 거야?

정확해!

[std::expected의 장점] 1. 무시 방지 (예외처럼) auto result = Divide(10, 0); // result 안 쓰면 컴파일러 경고 // [[nodiscard]] 기본 적용 2. 일정한 성능 (에러 코드처럼) - 예외 테이블 없음 - 스택 되감기 없음 - 분기 비용만 3. 타입 안전 - 값 타입과 에러 타입이 명확 - 실수로 에러를 값으로 쓸 수 없음 4. 풍부한 에러 정보 std::expected result; // DetailedError에 원하는 정보 담기 5. Monadic 연산 - 함수형 스타일로 체이닝 - 에러 전파 보일러플레이트 제거
[C++23 이전이라면?] // tl::expected (헤더만) #include "tl/expected.hpp" tl::expected Divide(int a, int b); // 직접 구현 template class Expected { union { T m_value; E m_error; }; bool m_hasValue; public: // ... }; // std::variant 활용 using Result = std::variant, Error>; Result Divide(int a, int b) { if (b == 0) return Error{"divide by zero"}; return Success{a / b}; }

Part 6. 실무 가이드라인

그래서 뭘 쓰라는 거야?

상황에 맞게 선택해!

[권장 사항] Hot Path (매 프레임): → 에러 코드 또는 expected → 예외 절대 금지 Cold Path (초기화, 로딩): → 예외 OK, 또는 expected → 안정성 > 성능 외부 라이브러리 경계: → catch 후 변환 → 내부 코드에 예외 전파 방지 새 프로젝트: → std::expected (C++23) 추천 → 못 쓰면 tl::expected 레거시 프로젝트: → 기존 컨벤션 따라가기 → 일관성이 더 중요
[체크리스트] 예외를 쓸지 말지 결정: [ ] 프로젝트에서 예외가 활성화되어 있나? [ ] 이 코드가 Hot Path인가? [ ] 에러가 자주 발생하는가? [ ] 팀 컨벤션은 뭔가? → Hot Path + 빈번한 에러 → 에러 코드/expected → Cold Path + 드문 에러 → 예외 가능 → 모르겠으면 → expected가 안전

핵심 정리

  • 예외 장점 = 무시 불가, 깔끔한 코드, 풍부한 정보
  • 예외 비용 = 던질 때 수천~수만 사이클, 코드 크기 증가
  • 에러 코드 장점 = 일정한 성능, 작은 바이너리
  • 에러 코드 단점 = 무시 쉬움, 전파 보일러플레이트
  • 게임 업계 = 대부분 예외 비활성화, 에러 코드 선호
  • std::expected (C++23) = 예외 + 에러 코드 장점 결합
  • Hot Path = 에러 코드 또는 expected 필수
  • Cold Path = 예외 사용 가능
  • 하이브리드 = 외부 라이브러리 경계에서 예외 → 에러 코드 변환
  • 새 프로젝트 = std::expected 적극 활용 권장
