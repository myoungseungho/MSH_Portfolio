왜 게임 서버는 아직도 C++을 쓸까?

Java, C#, Go, Rust가 있는데 왜 아직도 C++을 고집할까?

Part 1. 게임 서버는 뭐가 다른데?

웹 서버랑 게임 서버가 많이 달라?

완전히 다릅니다! 요구사항 자체가 달라요.

비유: 우체국 vs 응급실

웹 서버 = 우체국

  • 편지가 1분 늦게 가도 괜찮음
  • 바쁘면 "잠시 기다려주세요" 해도 됨
  • 하루에 100만 통 처리하는 게 중요 (처리량)

게임 서버 = 응급실

  • 환자가 1분 기다리면 안 됨!
  • "잠시 기다려주세요"가 허용 안 됨
  • 매 순간 빠른 응답이 중요 (지연시간)
웹 서버 vs 게임 서버 비교: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [웹 서버] [게임 서버] │ │ │ │ 요청 → 처리 → 응답 프레임 1 → 프레임 2 → ... │ │ │ │ • 요청-응답 모델 • 실시간 상태 유지 │ │ • 상태 없음 (Stateless) • 상태 있음 (Stateful) │ │ • 100ms 응답도 OK • 50ms도 느림! │ │ • 가끔 느려도 OK • 항상 일정해야 함 │ │ │ │ 측정 기준: 측정 기준: │ │ "1초에 몇 개 처리?" (TPS) "최악의 응답 시간?" (Tail) │ │ │ └─────────────────────────────────────────────────────────────┘
게임에서 느리면 어떻게 체감돼?

유저가 바로 알아챕니다!

지연 시간과 유저 체감: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [웹 서비스] │ │ │ │ 클릭 → 100ms 로딩 → 페이지 표시 │ │ "이 정도는 괜찮지" │ │ │ │ 클릭 → 500ms 로딩 → 페이지 표시 │ │ "좀 느리네..." │ │ │ │ [게임 - MMORPG] │ │ │ │ 스킬 버튼 → 50ms → 스킬 발동 │ │ "반응 좋은데?" ✓ │ │ │ │ 스킬 버튼 → 200ms → 스킬 발동 │ │ "어? 렉인가?" │ │ │ │ 스킬 버튼 → 500ms → 스킬 발동 │ │ "게임 터졌나?!" 😡 │ │ │ │ [게임 - FPS] │ │ │ │ 샷 → 30ms → 피격 판정 │ │ "정상" ✓ │ │ │ │ 샷 → 150ms → 피격 판정 │ │ "분명 맞췄는데!!" 🤬 │ │ │ └─────────────────────────────────────────────────────────────┘
핵심 차이
• 웹: 평균 성능이 중요 (1초에 몇 개 처리하나?)
• 게임: 최악 성능이 중요 (가장 느린 응답이 얼마나 느린가?)

Part 2. 평균 성능 vs 최악 성능

평균 성능이 좋으면 되는 거 아니야?

게임에서는 최악 성능이 더 중요합니다!

비유: 버스 배차 간격

A 노선: 평균 10분 간격, 가끔 30분 기다림

B 노선: 항상 12분 간격

평균은 A가 좋지만, 실제로는 B가 더 편함!

"30분 기다리기 싫어서 B 노선 타요" → 예측 가능성이 중요

언어 평균 성능 최악 성능 예측 가능성
C++ 100% 안정적 높음
Rust 95-100% 안정적 높음
Go 80-90% 가끔 GC 중간
Java 85-95% GC 스파이크 낮음
C# 85-95% GC 스파이크 낮음
왜 Java, C#은 최악 성능이 안 좋아?

GC(Garbage Collection) 때문이에요!

GC가 있는 언어의 성능 그래프: ┌─────────────────────────────────────────────────────────────┐ │ │ │ 응답 시간 │ │ (ms) │ │ │ │ │ │ ┃ ← GC 발생! (150ms) │ │ 150├─────────┃────────────────────────────────────────── │ │ │ ┃ │ │ 100├─────────┃────────────────────────────────────────── │ │ │ ┃ │ │ 50├─●─●─●─●─┃─●─●─●─●─●─●─●─┃─●─●─●─●─●─●─●─●─● 평균 20ms │ │ │ ┃ ┃ │ │ 20├─────────┃──────────────┃─────────────────────────── │ │ │ │ │ └───────────────────────────────────────────→ 시간 │ │ │ │ 평균: 20ms (좋아 보임) │ │ 최악: 150ms (문제!) │ │ │ │ → GC가 발생하면 순간적으로 모든 유저가 렉을 경험 │ │ │ └─────────────────────────────────────────────────────────────┘

Part 3. GC가 왜 문제야?

GC가 정확히 뭐고, 왜 게임에서 문제야?

Garbage Collection은 자동 메모리 관리 시스템이에요.

비유: 방 청소하는 엄마

GC가 없는 언어 (C++) = 네가 직접 정리

  • 쓴 물건은 네가 바로 치움
  • 언제 치울지 네가 결정
  • 귀찮지만 방해받지 않음

GC가 있는 언어 (Java, C#) = 엄마가 가끔 청소

  • 쓴 물건 그냥 두면 됨 (편함!)
  • 엄마가 알아서 치워줌
  • 근데... 청소할 때 모든 활동 중단!
Stop-the-World 현상: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [정상 상태] │ │ │ │ 프레임 1 프레임 2 프레임 3 프레임 4 │ │ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │게임 │ │게임 │ │게임 │ │게임 │ │ │ │로직 │ │로직 │ │로직 │ │로직 │ │ │ └──────┘ └──────┘ └──────┘ └──────┘ │ │ ↓ ↓ ↓ ↓ │ │ 16ms 16ms 16ms 16ms ← 일정함 │ │ │ │ [GC 발생!] │ │ │ │ 프레임 1 프레임 2 GC 청소 프레임 3 │ │ ┌──────┐ ┌──────┐ ┌──────────────────┐ ┌──────┐ │ │ │게임 │ │게임 │ │ 메모리 정리 │ │게임 │ │ │ │로직 │ │로직 │ │ (전부 멈춤!) │ │로직 │ │ │ └──────┘ └──────┘ └──────────────────┘ └──────┘ │ │ ↓ ↓ ↓ ↓ │ │ 16ms 16ms 150ms! 16ms │ │ ↑ │ │ 이 동안 모든 유저가 렉! │ │ │ └─────────────────────────────────────────────────────────────┘
요즘 GC는 많이 좋아지지 않았어?

맞아요, 많이 발전했습니다. 근데 완벽하진 않아요.

1
1세대 GC: Stop-the-World (전체 멈춤) → 수백ms 멈춤
↓
2
2세대 GC: Generational (세대별) → 젊은 객체 위주 검사
↓
3
3세대 GC: Concurrent (동시성) → 조금씩 나눠서 청소
↓
4
최신 GC: ZGC, Shenandoah → 1-10ms까지 감소... 근데!
여전한 문제점
• 게임은 16ms (60fps) 안에 처리해야 함
• 1-10ms도 프레임 하나 날릴 수 있음
• 동접 만 명, 객체 수백만 개 → GC 스캔 양이 어마어마
• 여전히 예측 불가능한 스파이크 발생
C++은 어떻게 이 문제를 피해?

메모리 해제 시점을 개발자가 결정합니다!

// C++ - 개발자가 해제 시점 결정 void ProcessPacket(Packet* pkt) { // 패킷 처리... delete pkt; // 여기서 바로 해제! 예측 가능! } // 더 좋은 방법: 오브젝트 풀 void ProcessPacket(Packet* pkt) { // 패킷 처리... packetPool.Free(pkt); // 풀에 반납, 실제 해제 없음! } // 결과: // - 언제 메모리 작업이 일어나는지 개발자가 알고 있음 // - Stop-the-World 없음! // - 성능 예측 가능!

Part 4. 메모리를 직접 만질 수 있다는 것

메모리 직접 관리가 왜 장점이야? 귀찮기만 한 거 아니야?

게임 서버는 메모리 레이아웃이 성능에 직결됩니다!

비유: 도서관 책 배치

GC 언어 = 도서관 아무데나 책 꽂음

  • 1권 찾으러 1층 → 5권 찾으러 3층 → 2권 찾으러 지하
  • 왔다갔다 시간 낭비!

C++ = 관련 책을 한 선반에 모아둠

  • 한 번에 쭉 훑으면서 다 찾음
  • 이동 시간 최소화!
캐시 친화적 메모리 배치: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [GC 언어 - Java, C#] │ │ │ │ 객체들이 힙에 흩어져 있음: │ │ │ │ [ A ] . . . . [ B ] . . . . [ C ] . . . . [ D ] │ │ ↑ ↑ ↑ ↑ │ │ 메모리 여기저기 (Cache Miss 많음!) │ │ │ │ CPU: "A 읽었는데 B가 어디지? 찾아야 해..." │ │ │ │ ───────────────────────────────────────────────────────── │ │ │ │ [C++] │ │ │ │ 객체들을 연속으로 배치 가능: │ │ │ │ [ A ][ B ][ C ][ D ] │ │ ↑ │ │ CPU가 한 번에 캐시로 읽어옴 (Cache Hit!) │ │ │ │ CPU: "A 읽었더니 B, C, D도 같이 왔네! 빠르다!" │ │ │ └─────────────────────────────────────────────────────────────┘
캐시 미스가 얼마나 느린 건데?

100배 이상 차이날 수 있어요!

메모리 접근 대략적 시간 비유
L1 캐시 ~1ns 책상 위 메모장
L2 캐시 ~4ns 서랍 속 파일
L3 캐시 ~10ns 옆 책장
RAM (캐시 미스) ~100ns 창고까지 걸어감
10,000명 플레이어 업데이트 비교: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [Java/C# - 흩어진 객체] │ │ │ │ for (Player p : players) { │ │ p.Update(); // 매번 캐시 미스 가능 │ │ } │ │ │ │ → 10,000 × 100ns = 1,000,000ns = 1ms │ │ │ │ ───────────────────────────────────────────────────────── │ │ │ │ [C++ - 연속 배치] │ │ │ │ for (int i = 0; i < count; i++) { │ │ players[i].Update(); // 캐시 히트! │ │ } │ │ │ │ → 10,000 × 4ns = 40,000ns = 0.04ms │ │ │ │ → 같은 작업인데 25배 차이! │ │ │ └─────────────────────────────────────────────────────────────┘
커스텀 메모리 할당자도 쓸 수 있어?

네! 용도별로 최적화된 할당자를 직접 만들 수 있어요.

커스텀 할당자 종류: ┌─────────────────────────────────────────────────────────────┐ │ │ │ [1] 오브젝트 풀 (Object Pool) │ │ ┌─────────────────────────────────────────┐ │ │ │ [사용중] [비어있음] [사용중] [비어있음] │ │ │ └─────────────────────────────────────────┘ │ │ • 미리 만들어 놓고 재사용 │ │ • 할당/해제 시간 = O(1) │ │ • 용도: 패킷, 몬스터, 이펙트 등 │ │ │ │ [2] 스택 할당자 (Stack Allocator) │ │ ┌─────────────────────────────────────────┐ │ │ │ ████████████░░░░░░░░░░░░░░░░░░░░░░░░░░░ │ ← 여기까지 사용│ │ └─────────────────────────────────────────┘ │ │ • 프레임 시작 시 사용, 끝나면 한 번에 리셋 │ │ • 해제 비용 = 0! │ │ • 용도: 프레임 내 임시 계산 │ │ │ │ [3] 링 버퍼 (Ring Buffer) │ │ ┌─────────────────────────────────────────┐ │ │ │ ███░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░███ │ ← 원형 사용 │ │ └─────────────────────────────────────────┘ │ │ • 패킷 버퍼용 │ │ • 단편화 없음 │ │ │ │ → GC 언어에서는 이런 제어가 어렵거나 불가능! │ │ │ └─────────────────────────────────────────────────────────────┘

Part 5. 다른 언어들은 어때?

Rust는 어때? GC 없고 안전하다던데?

Rust는 미래의 강력한 대안입니다!

Rust 장단점: ┌─────────────────────────────────────────────────────────────┐ │ │ │ ✅ 장점 │ │ ───────────────────────────────────────────── │ │ • C++ 수준 성능 │ │ • GC 없음 → Stop-the-World 없음 │ │ • 메모리 안전성 보장 (컴파일 타임 체크) │ │ • 데이터 레이스 방지 (안전한 동시성) │ │ │ │ ❌ 단점 │ │ ───────────────────────────────────────────── │ │ • 게임 업계 생태계 부족 (라이브러리, 엔진) │ │ • 기존 C++ 코드베이스와 호환 어려움 │ │ • 러닝 커브 높음 (소유권 개념) │ │ │ │ 🎯 현실 │ │ ───────────────────────────────────────────── │ │ • 새 프로젝트에서 고려 가치 있음 │ │ • 기존 C++ 서버를 Rust로 재작성? → 비용 막대함 │ │ • 아직은 "미래" 단계 │ │ │ └─────────────────────────────────────────────────────────────┘
Go는? 고루틴이 좋다던데.

Go는 웹 서버에는 좋은데 게임 서버에는 애매해요.

Go 특징
✅ 장점: 고루틴 (경량 스레드), 빠른 컴파일, 단순한 문법
❌ 단점: GC 있음, 메모리 레이아웃 제어 어려움

적합한 곳: 로비 서버, 매치메이킹, API 게이트웨이
부적합한 곳: 실시간 전투, MMORPG 월드 서버
C#은? Unity 서버 같은 거 있잖아.

C#도 게임 서버에서 많이 쓰여요. 특히 모바일!

C# 특징
✅ 장점: 개발 생산성 높음, 안전한 메모리 관리, 풍부한 라이브러리
❌ 단점: GC 존재 (성능 상한선), 최적화 한계

적합한 곳: 모바일 게임, 턴제 게임, 소규모 동접
부적합한 곳: 대규모 MMORPG, 고성능 FPS 서버
언어 성능 생산성 안전성 게임 서버 적합도
C++ 최고 낮음 낮음 AAA급
Rust 최고 중간 높음 미래 유망
Go 양호 높음 높음 보조 서버용
C# 양호 높음 높음 모바일/소규모
Java 양호 높음 높음 부적합

기술적인 이유 말고 다른 이유도 있어?

그럼 C++은 앞으로도 계속 쓰일까?

당분간은 확실히! 하지만 변화도 있어요.

Part 7. 면접에서 물어보면?

"왜 게임 서버는 C++을 쓰나요?"라고 물어보면?

✅ 핵심 답변 포인트

1. 성능 특성 설명

"게임 서버는 평균 성능보다 최악 성능이 중요합니다. GC가 있는 언어는 Stop-the-World로 인해 예측 불가능한 지연이 발생합니다."

2. 메모리 제어

"C++은 메모리 레이아웃을 직접 제어할 수 있어 캐시 친화적 코드를 작성할 수 있고, 커스텀 할당자로 특정 상황에 최적화할 수 있습니다."

3. 현실적 이유

"기존 코드베이스, 검증된 라이브러리, 경험 있는 인력 풀도 중요한 이유입니다. 엔진(Unreal)과의 호환성도 있습니다."

4. 미래 전망

"Rust가 유망하지만 생태계가 아직 부족하고, 영역별로 적합한 언어를 혼용하는 하이브리드 접근이 늘어나는 추세입니다."

핵심 정리

  • 평균 성능보다 최악 성능이 게임 서버에서 중요
  • GC의 Stop-the-World가 실시간 게임에서 치명적
  • C++은 메모리 레이아웃 제어로 캐시 효율 극대화
  • 커스텀 할당자로 할당/해제 비용 최소화
  • Rust는 미래의 강력한 대안, 하지만 아직 생태계 부족
  • Go, C#은 보조 서버나 모바일에 적합
  • 레거시, 인력, 생태계도 C++ 선택의 현실적 이유
