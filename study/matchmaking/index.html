왜 내 팀은 다 초보만 있을까?

게임 디자인부터 서버 구현까지: 매치메이킹 시스템 완전 정복

던전에 들어갔는데...

• 나만 열심히 뛰고 다른 팀원들은 계속 죽어

• 보스 잡다가 누가 자꾸 실수해서 전멸

• "마랭 100 이상만 오세요" 방 제목에 쓰는데도 초보가 와


왜 이럴까? 매치메이킹은 어떻게 작동하는 걸까?

이 문서는 게임 디자인 관점과 기술 구현 관점 모두에서 매치메이킹 시스템을 다룹니다.

Part 1: 게임 디자인 관점

PVE 매치메이킹은 어떻게 설계할까? (퍼스트 디센던트 사례)

1. 매칭이 뭔데?

매칭이 뭐야? 그냥 사람 아무나 4명 모으면 되는 거 아니야?

그게 아니야. 매칭 = 대상을 적절히 연결하는 것

저울로 비교하듯이, 비슷한 사람들을 찾아서 연결해주는 거지.

PVP에서는 "실력 비슷한 적"을 찾아주지만, PVE에서는 "목표를 함께 달성할 동료"를 찾아줘야 해.

퍼스트 디센던트 유저들의 목표가 뭐야?

던전 클리어 → 다음 지역 열기 → 또 던전 클리어...

끝없는 마라톤이야. 특정 보스 잡고 → 다음 지역 열고 → 또 보스 잡고...

그래서 매칭의 목표는: "적절한 동료를 찾아서 유저들이 앞으로 나아가게 하는 것"

2. 비슷한 실력끼리 매칭하면 되잖아?

왜 비슷한 실력의 유저를 만나게 해야 해?

보이드 요격전(보스레이드) 같은 콘텐츠는 비숙련 유저가 다른 유저의 발목을 잡아

당시에는 데스카운트가 공유됐어. 가장 취약한 유저가 자주 죽으면 → 전체 실패

게다가 인원수에 비례해서 보스 스펙이 증가했어. 약한 사람이 들어오면 → 난이도만 올라가고 → 기여는 못해

실제로 그런 문제가 있었어?

데이터를 보니까:

실력 점수 격차가 큰 그룹에서 매치 탈출 비율이 증가했어.

유저들이 직접 방 제목에 "마랭 100 이상", "보스 기믹 숙지" 같은 조건을 쓰기 시작했지.

그래서 어떻게 했어?

실력 점수(Skill Score)를 도입했어.

방법은 이렇게:

1. 유저 실력에 반영될 변수 선별 - 클리어 여부 - 캐릭터 레벨 - 마스터리 랭크 - 보스 기믹 숙지 여부 2. 던전 결과를 예측값으로 설정 3. 머신러닝 모델로 실력 측정 4. PVP의 MMR처럼 활용
🎮 비유: 롤 랭크 게임

롤에서 브론즈랑 다이아를 같은 팀에 넣으면 어떻게 될까?
브론즈는 실력이 안 되니까 죽고, 다이아는 혼자 캐리하려다 지쳐.

PVE도 마찬가지야. 비슷한 실력끼리 모아야 각자 1인분을 해.
✅ 결과:
  • 실력 차이 나는 매치 비중 ↓
  • 탈주율 ↓
  • 던전 성공률 ↑

충분히 클리어할 수 있는 유저들끼리 만나면 각자 비슷하게 1인분 수행 → 수월하게 진행

3. 그런데 초보는 계속 못 깨잖아?

실력 점수로 비슷한 사람끼리 모았는데 뭐가 문제야?

저실력 초보 유저들끼리 모이면 → 반복된 실패 → 좌절 → 게임 이탈

소위 "달리기에서 넘어지는 유저"들이야.

데이터로 확인할 수 있었어?

특정 구간에서 유저 잔존율이 하락했어:

A 단계에서 이탈한 유저: 3회 이상 실패 비율 8%

B, C, D 단계: 수차례 실패 경험 끝에 이탈 → 급증

즉, 클리어하고 싶어서 여러 번 시도 → 목표 달성 못함 → 이탈

그냥 스펙을 높이라고 하면 되잖아?

맞아. 정석은 모듈 강화, 무기 장착, 반응로 업그레이드야.

근데 문제는: 배우고 경험할 기회 이전에 맨땅에 헤딩 → 실패 경험 쌓임 → 포기

게임을 배울 기회조차 못 가지고 떠나는 거지.

그래서 어떻게 했어?

"버스 태우기"

넘어진 유저 일부를 강한 팀원과 매칭시켜.

조건: 1. 누적 실패 횟수가 많은 유저 선별 2. 고실력 유저 풀에 소수만 투입 3. 민폐 안 되도록 1명만 넣기 이유: - 아무리 잘하는 최고실력 유저라도 - 저실력 유저가 늘어날수록 클리어 못함 - 그래서 소수만 "월반"시켜
🚌 비유: 학교 버스

학교 가는 길을 모르는 1학년이 있어.
혼자 가면 길 잃고 학교 못 가.

근데 6학년 형들이 타는 버스에 1명만 태우면?
형들은 원래 가던 대로 가고, 1학년은 학교 도착.

단, 버스에 1학년을 10명 태우면? 형들도 못 가.
✅ 결과:
  • 특정 보스에서 클리어율 최대 50% 포인트 ↑
  • 매치 탈주율 11% 포인트 ↓

예상 못한 효과:

케어 받지 않은 저숙련 유저도 경험 개선 → 확실한 저실력 유저들이 풀에서 빠져나가니까 나머지끼리는 클리어 가능

4. 새벽에는 사람이 없는데?

게임 초기에는 사람이 많았는데, 시간 지나니까 사람 줄었어. 어떡해?

RPG나 루트슈터 게임의 보편적인 현상이야:

초반 콘텐츠: 오픈 직후 몰림 → 시간 지나면 사람 없음

후반 콘텐츠: 사람들이 점점 이동 → 나중에는 여기만 붐빔

그리고 시간대, 지역에 따라서도 요청량 달라.

사람 적으면 뭐가 문제야?

사람 많으면: 짝 쉽게 찾음 → 대기 시간 짧음

사람 적으면: 짝 찾기 어려움 → 대기 시간 길어짐

같은 로직으로 판단하면 초반 콘텐츠 대기 시간만 계속 늘어나.

그래서 어떻게 해야 해?

동적 최적화 (Dynamic Optimization)

풀 상황에 따라 탐색 조건을 유연하게 맞추고, 이를 자동화

동적 최적화 과정

어떻게 동작하는데?
예시: 실력 탐색 범위 조정 1단계: 요청량과 대기 시간 관계 파악 - 1500개 요청 → 티어별 500개 → 대기 30초 - 900개 요청 → 티어별 300개 → 대기 60초 → 요청량 적으면 대기 시간 증가하는 패턴 발견 2단계: 미래 요청량 예측 - 직전 시간 데이터 - 전주 동기간 데이터 - 시계열 패턴 반영 3단계: 탐색 범위 조정 - 목표 대기 시간: 30초 - 예측 요청량: 900개 - 탐색 티어를 3등분 → 2등분으로 넓힘 → 덜 꼼꼼하게 탐색하지만 대기 시간 유지
🍕 비유: 피자 배달

손님이 많을 때: "30분 안에 배달합니다!" → 근처만 배달
손님이 적을 때: "30분 안에 배달합니다!" → 좀 먼 곳도 배달

같은 시간 약속하지만, 배달 범위를 상황에 맞춰 조절하는 거야.
✅ 결과:
  • 목표 대기 시간을 모든 풀에 걸쳐 동일하게 경험
  • 풀이 부족한 경우: 불필요한 대기 시간 제거
  • 풀이 충분한 경우: 더 품질 높은 매치 제공

5. 특정 캐릭터 없으면 다 나가버려

비슷한 실력끼리 모였는데도 탈주가 많아. 왜?

특정 캐릭터(계승자)가 없으면 → 시작도 안 하고 탈출

"이 캐릭터 없으면 어차피 못 깨" 이런 인식이 생긴 거지.

실제 데이터는?

인기 캐릭터 1명 이상 포함:

  • 임무 성공률 ↑
  • 탈주율 ↓

심지어:

저실력 팀 + 인기 캐릭터 > 고실력 팀 + 인기 캐릭터 없음

실력으로는 충분히 클리어 가능한데도 탈주율이 더 높았어.

그래서 어떻게 했어?
로직: 1. 일정 시간 동안 인기 캐릭터 1명은 무조건 포함 2. 인기 캐릭터가 너무 많이 포함된 매치는 줄임 (한 팀에 4명 다 인기 캐릭터 → 낭비) 3. 유저들이 자유롭게 매칭하되 최대한 많은 매치에서 인기 캐릭터 포함되도록 주의: - 대기 시간 변화 없도록 시간 제한 설정
⚽ 비유: 축구팀

골키퍼 없는 축구팀 vs 골키퍼 있는 축구팀
당연히 골키퍼 있는 팀이 이겨.

근데 골키퍼 4명인 팀은? 공격수가 없어서 득점 못 해.
골키퍼 1명씩 골고루 분배하는 게 최선이야.
✅ 결과:
  • 대기 시간 변화 없음
  • 인기 캐릭터 없는 매치 비중 ↓
  • 전체 탈주율 ↓
  • 성공률 ↑

6. PC 유저들이 콘솔이랑 안 하고 싶대

PC 유저들이 왜 분리를 요청해?

최적화 문제 등의 이유로 PC 유저들이 "콘솔이랑 안 하고 싶다"고 요청

콘솔 유저들은 원래 크로스플레이 선택권이 있는데, PC는 없었어.

그냥 분리해주면 되잖아?

풀을 나누면 나눌수록 대기 시간 증가

게다가 지역마다 플랫폼 분포가 달라

예: 북미는 PC 50%, 콘솔 50% → 분리하면 각각 50% 풀만 사용

최악의 경우: 절반이 분리 선택하면 → 14% 유저 풀만 활용

두 가지 방법 검토

하드 분리 소프트 분리
완전히 다른 플랫폼과 분리 동일 플랫폼 우선 지원 + 일정 시간 후 합침
✅ 유저 요구 사항 100% 충족 ⚠️ 완벽한 분리는 보장 못함
❌ 지역/선택 비중에 따라 고립 가능 ✅ 풀 충분하면 동일 플랫폼끼리
✅ 풀 부족하면 다른 플랫폼이라도 매칭
❌ 일부 지역 필연적 고립 ✅ 고립 상황에 강건함
뭘 선택했어?

고민이 많았어. 근데 시뮬레이션으로 미리 테스트했어.

시뮬레이션 시스템

시뮬레이션이 뭐야?
동작 원리: 1. 실제 라이브 요청만 따로 저장 2. 다른 설정의 매치 서버에 재생 3. "그때 이랬으면 어땠을까?" 확인 예: - 실제: A 유저 + B 유저 매칭 → 결과 O - 시뮬: A 유저 + C 유저 매칭 → 결과 X 매치 구성과 대기 시간은 정확히 확인 가능
시뮬레이션 결과는?

하드 분리 (0~100% 선택 비중 테스트):

→ 모든 경우에 평균 16초 이상 대기 시간 증가

→ PC 유저뿐만 아니라 콘솔 유저도 대기 시간 증가


소프트 분리:

→ 다른 플랫폼 섞이는 비중 완화

→ 대기 시간 크게 증가하지 않음

🚇 비유: 지하철 노선

하드 분리: 1호선만 타는 사람 / 2호선만 타는 사람 완전 분리
→ 환승 불가 → 목적지 못 가는 사람 생김

소프트 분리: 같은 노선 우선 이용, 필요하면 환승 가능
→ 조금 돌아가지만 모두 목적지 도착
✅ 결과:

소프트 로직 선택 → 실제 적용 후에도 대기 시간 변화 없이 비중 낮춤 성공

Part 2: 기술 구현 관점

매치메이킹 서버는 어떻게 구현할까?

7. 매칭 요청이 들어오면?

"대전 찾기" 버튼을 누른 순간부터 상대를 만나기까지, 서버에서 어떤 일이 일어나야 할까?

대전 찾기에도 종류가 있어. 레벨별, 지역별, 랭크별 등등.

내 세션 정보를 기반으로 어딘가 큐(Queue)에 넣어야 해.

플레이어 → [내 정보: 레벨30, 한국, 골드랭크] → 큐에 등록

8. 큐는 어떻게 설계할까?

큐를 여러 개로 나눌까, 하나로 합칠까? 각각의 장단점은?

두 가지 방법이 있어:

방법 A: 조건별로 큐 분리 방법 B: 하나의 큐
[레벨1~10 큐] [레벨11~20 큐] [레벨21~30 큐] ... → 이미 분류됨
[전체 대기열] ↓ 꺼낼 때 조건 맞는 사람끼리 묶음
✅ 동접자 많으면 검색 빠름
✅ 이미 분류되어 있어서 바로 매칭		 ✅ 동접자 적어도 유연함
✅ 큐 관리가 간단함
❌ 조건 조합하면 큐가 너무 많아짐
❌ 특정 큐에 사람 없으면 영원히 대기		 ❌ 검색 시간이 조금 더 걸림
동접자 많으면 A가 빠르다는 건 알겠어. 근데 문제가 뭐야?

조건이 여러 개면 큐가 폭발적으로 증가해:

조건 1: 레벨 (1~10, 11~20, 21~30...) → 10가지 조건 2: 지역 (한국, 일본, 미국...) → 5가지 조건 3: 랭크 (브론즈, 실버, 골드...) → 6가지 조건 4: 모드 (솔로, 듀오, 스쿼드) → 3가지 총 큐 개수 = 10 × 5 × 6 × 3 = 900개!

🚨 문제 발생!

만약 [레벨21~30 + 일본 + 다이아 + 스쿼드] 큐에 사람이 1명뿐이라면?

→ 이 플레이어는 영원히 대기할 수도 있어!

9. 오래 기다리는 문제를 어떻게 해결할까?

특정 조건에 사람이 없어서 계속 기다리는 문제를 어떻게 해결할까?

대기 시간이 길어지면 탐색 범위를 넓혀

1. 처음 30초: 레벨 20~30, 한국, 다이아만 찾기 2. 30초 경과: 레벨 15~35, 한국, 플래티넘~다이아 범위 확대 3. 60초 경과: 레벨 10~40, 아시아 전체, 골드~다이아 범위 더 확대 4. 90초 경과: 조건 무시하고 누구든 매칭

10. 대기열이 1만 명이면 어떻게 찾지?

대기열에 1만 명이 있는데, 나랑 비슷한 실력의 상대를 어떻게 빠르게 찾아?

1만 명을 전부 비교하면 너무 느려. O(n²) 복잡도

그래서 자료구조를 활용해야 해:

해결 방법

방법 1: 범위 기반 인덱스 - 실력 점수별로 범위 인덱스 생성 - 예: 1000~1100 점수 → Bucket A 1100~1200 점수 → Bucket B - 내 점수가 1050이면 Bucket A에서만 검색 방법 2: K-D Tree / R-Tree 활용 - 다차원 데이터 (실력, 레벨, 지역)를 트리 구조로 저장 - 범위 검색 O(log n)으로 최적화 방법 3: Redis Sorted Set 활용 - 실력 점수를 score로 저장 - ZRANGEBYSCORE 명령으로 범위 검색 - 매우 빠른 검색 (Redis는 메모리 기반)
✅ 실전 팁:

대부분의 게임은 Redis Sorted Set을 활용합니다.

이유: 빠르고, 분산 환경에서도 동작하며, 구현이 간단하기 때문

11. 모든 조건을 하나의 점수로 합칠 수 있을까?

레벨, 실력, 지역, 랭크... 여러 조건을 어떻게 하나의 점수로 만들어?

가중치(Weight)를 활용한 점수 계산

최종 점수 = (실력 × 0.5) + (레벨 × 0.3) + (승률 × 0.2) 예시: - 플레이어 A: (1500 × 0.5) + (30 × 0.3) + (60 × 0.2) = 771 - 플레이어 B: (1520 × 0.5) + (28 × 0.3) + (58 × 0.2) = 779.6 두 플레이어의 점수 차이 = 8.6 → 비슷함! 매칭 가능

이렇게 하면 여러 조건을 하나의 숫자로 표현할 수 있어.

그런데 가중치는 누가 정해?

이건 게임 디자인 영역이야.

실력을 가장 중요하게 볼 거면 가중치를 0.7로, 레벨을 중요하게 볼 거면 0.5로 설정.

실제로는 A/B 테스트나 시뮬레이션으로 최적의 가중치를 찾아.

12. 서버 구조는 어떻게?

매치메이킹 서버는 어떤 구조로 만들어야 해?

기본적인 구조는 이렇게:

┌─────────────┐ │ 클라이언트 │ → "매칭 시작" 요청 └─────────────┘ ↓ ┌─────────────┐ │ 게임 서버 │ → 세션 정보 검증 └─────────────┘ ↓ ┌─────────────┐ │ 매치메이킹 │ → 큐에 등록 │ 서버 │ 적합한 상대 찾기 └─────────────┘ 매치 구성 ↓ ┌─────────────┐ │ Redis/DB │ → 대기열 저장 └─────────────┘ 실시간 조회 ↓ 매치 완료! ↓ ┌─────────────┐ │ 게임 방 생성 │ → 플레이어들을 방에 입장 └─────────────┘

주요 컴포넌트

1. API Gateway - 클라이언트 요청 수신 - 인증/인가 처리 2. Matchmaking Service - 핵심 로직 실행 - 매칭 알고리즘 수행 - 큐 관리 3. Queue Storage (Redis) - 대기열 저장 - 빠른 조회/수정 4. Match Result DB - 매칭 이력 저장 - 통계 분석 5. Notification Service - 매칭 완료 알림 - WebSocket/Long Polling
✅ 확장성 고려사항:
  • 수평 확장: Matchmaking Service를 여러 인스턴스로 분산
  • 지역별 분리: 지역마다 별도의 매칭 서버 운영
  • Redis Cluster: 대용량 처리를 위한 Redis 클러스터링
  • 비동기 처리: 매칭 결과를 비동기로 통보 (WebSocket)

📌 핵심 정리

Part 1: 게임 디자인 관점

  • PVE vs PVP 매칭 - PVE는 "함께 목표 달성할 동료"를 찾는 것
  • 실력 점수 시스템 - 비슷한 실력의 유저끼리 매칭하여 각자 1인분 수행
  • 넘어지는 유저 케어 - 저숙련 유저를 소수만 고숙련 팀에 투입 (버스 태우기)
  • 동적 최적화 - 풀 상황에 따라 탐색 범위를 자동으로 조정
  • 인기 캐릭터 분산 - 특정 캐릭터를 골고루 분배하여 탈주율 감소
  • 소프트 크로스플랫폼 - 동일 플랫폼 우선 + 필요 시 합침
  • 시뮬레이션 - 라이브 적용 전에 미리 테스트하여 부작용 검증

Part 2: 기술 구현 관점

  • 큐 설계 - 단일 큐 vs 분리 큐, 트레이드오프 고려
  • 탐색 범위 확대 - 대기 시간 길어지면 조건 완화
  • 대규모 처리 - Redis Sorted Set으로 빠른 범위 검색
  • 점수 기반 매칭 - 가중치 활용한 단일 점수 계산
  • 서버 구조 - API Gateway, Matchmaking Service, Redis, Notification
  • 확장성 - 수평 확장, 지역별 분리, 비동기 처리


가장 중요한 것: 유저의 목표는 "게임을 즐기는 것"이다. 매칭은 그 경험을 극대화하기 위한 수단이다.

💡 배운 점

1. 데이터 기반 의사결정

막연한 추측이 아니라, 실제 데이터와 시뮬레이션으로 검증한다.


2. 완벽한 해결책은 없다

모든 것을 만족시킬 수 없으니, 상황에 맞는 "차선"을 자동으로 선택하게 한다.


3. 게임 디자인과 기술 구현의 조화

좋은 매칭 시스템은 게임 디자이너의 의도를 기술로 정확히 구현한 것이다.


4. 확장성과 유연성

게임이 성장하고 유저가 늘어날 때를 대비해 처음부터 확장 가능하게 설계한다.
