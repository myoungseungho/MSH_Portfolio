ELK Stack

로그 10TB를 검색 가능하게 저장하는 법

1. 로그 파일로 충분하지 않아?

그냥 서버에 로그 파일 쌓아두면 안 돼?

서버 100대면?

상황: 유저 민원 "2시에 아이템이 사라졌어요!" 로그 파일 방식: 1. 서버 100대 중 어디서 플레이했는지 찾기 2. SSH로 각 서버 접속 3. grep으로 유저 ID 검색 4. 로그 파일 10GB씩... 검색 30분 5. 찾았다! game-server-42에서 발생 결과: 원인 파악까지 2시간
ELK 있으면?
ELK 방식: 1. Kibana 접속 2. 검색창에 "user_id: 12345 AND action: item_lost" 3. 엔터! 4. 결과: game-server-42, 02:15:32, 아이템 ID 9999 결과: 원인 파악까지 10초

2시간 vs 10초 차이야!

2. ELK가 뭐야?

Elasticsearch, Logstash, Kibana?
ELK 스택 구조: [Game Server 1] --로그--> [Filebeat] [Game Server 2] --로그--> [Filebeat] --> [Logstash] --> [Elasticsearch] [Game Server N] --로그--> [Filebeat] | v [Kibana] 대시보드/검색
구성요소 역할 비유
Filebeat 로그 파일 수집 배달 기사
Logstash 로그 파싱/변환 물류 센터
Elasticsearch 저장/검색 엔진 도서관
Kibana 시각화/대시보드 사서 + 검색창

3. 로그는 어떻게 흘러가?

게임 서버에서 로그를 어떻게 보내?

Filebeat 설정:

# filebeat.yml filebeat.inputs: - type: log enabled: true paths: - /var/log/game-server/*.log fields: server_type: game environment: production multiline: pattern: '^[0-9]{4}-[0-9]{2}-[0-9]{2}' negate: true match: after output.logstash: hosts: ["logstash.example.com:5044"]
Logstash에서는 뭘 해?

로그 파싱 + 변환:

# logstash.conf input { beats { port => 5044 } } filter { # 게임 로그 파싱 grok { match => { "message" => "%{TIMESTAMP_ISO8601:timestamp} \[%{WORD:level}\] \[%{DATA:server}\] %{GREEDYDATA:log_message}" } } # JSON 필드 파싱 (아이템 로그) if [log_message] =~ /^\{/ { json { source => "log_message" target => "data" } } # 시간 변환 date { match => ["timestamp", "ISO8601"] target => "@timestamp" } # 불필요한 필드 제거 mutate { remove_field => ["message", "timestamp"] } } output { elasticsearch { hosts => ["elasticsearch:9200"] index => "game-logs-%{+YYYY.MM.dd}" } }

4. 10TB를 어떻게 저장해?

데이터가 너무 많지 않아?

인덱스 분리가 핵심이야:

인덱스 설계 전략: 1. 날짜별 인덱스 game-logs-2025.02.01 game-logs-2025.02.02 game-logs-2025.02.03 2. 타입별 분리 game-logs-combat-2025.02.03 game-logs-economy-2025.02.03 game-logs-login-2025.02.03 3. Hot-Warm-Cold 아키텍처 Hot (SSD): 최근 3일 로그 (빠른 검색) Warm (HDD): 3일~30일 로그 (일반 검색) Cold (저장): 30일~1년 (아카이브)
오래된 로그는 어떻게 해?

ILM (Index Lifecycle Management):

# elasticsearch ILM 정책 PUT _ilm/policy/game-logs-policy { "policy": { "phases": { "hot": { "min_age": "0ms", "actions": { "rollover": { "max_size": "50gb", "max_age": "1d" } } }, "warm": { "min_age": "3d", "actions": { "shrink": { "number_of_shards": 1 }, "forcemerge": { "max_num_segments": 1 } } }, "cold": { "min_age": "30d", "actions": { "freeze": {} } }, "delete": { "min_age": "365d", "actions": { "delete": {} } } } } }

5. 게임 로그로 뭘 볼 수 있어?

실제로 어떤 분석을 해?
게임 로그 분석 예시: 1. 유저 민원 대응 "02:15에 아이템 사라졌어요!" -> 해당 시간대 아이템 로그 검색 -> 원인: 버그로 인한 아이템 소실 확인 -> 복구 조치 2. 핵 유저 탐지 -> 비정상적인 골드 획득량 검색 -> 1시간에 1억 골드? 핵 의심! -> 계정 제재 3. 밸런스 분석 -> 보스 레이드 클리어율 분석 -> 1% 클리어? 너무 어려움 -> 난이도 조정 4. 버그 추적 -> 에러 로그 패턴 분석 -> "NullPointerException" 급증 -> 특정 맵에서만 발생 확인
검색 쿼리 예시는?
# Kibana 검색 예시 # 특정 유저의 아이템 로그 user_id: 12345 AND action: (item_acquire OR item_lose) # 에러 로그 (최근 1시간) level: ERROR AND @timestamp >= now-1h # 골드 1억 이상 획득 action: gold_acquire AND data.amount >= 100000000 # 특정 맵에서 발생한 로그 server: game-server-* AND data.map_id: "dungeon_01" # 레벨업 로그 집계 (시간대별) action: level_up | histogram(@timestamp, interval: 1h)

Kibana Alerting:

# Kibana Alert 설정 예시 { "name": "High Error Rate Alert", "trigger": { "schedule": { "interval": "1m" } }, "input": { "search": { "request": { "indices": ["game-logs-*"], "body": { "query": { "bool": { "must": [ { "term": { "level": "ERROR" } }, { "range": { "@timestamp": { "gte": "now-5m" } } } ] } } } } } }, "condition": { "compare": { "ctx.payload.hits.total.value": { "gt": 100 } } }, "actions": { "slack": { "message": "5분간 에러 로그 100건 이상 발생!" } } }

비용 줄이는 팁은?
비용 최적화 전략: 1. 로그 레벨 필터링 - DEBUG 로그는 저장 안 함 - 프로덕션: INFO 이상만 수집 - 용량 70% 절감 2. 샘플링 - 정상 로그는 10%만 저장 - 에러 로그는 100% 저장 - 용량 50% 절감 3. Hot-Warm-Cold 분리 - 최근 데이터만 SSD - 오래된 데이터는 HDD - 비용 60% 절감 4. 압축 - best_compression 설정 - 용량 30% 절감

핵심 정리: ELK Stack

  • 구성 - Filebeat(수집) + Logstash(파싱) + Elasticsearch(저장) + Kibana(검색)
  • 인덱스 - 날짜별/타입별 분리 + ILM으로 자동 관리
  • 활용 - 민원 대응, 핵 탐지, 밸런스 분석, 버그 추적
  • 대시보드 - 실시간 현황 + 자동 알람
  • 비용 - 로그 필터링 + Hot-Warm-Cold로 최적화
