번들 버전 관리

라이브 서비스의 무중단 업데이트를 위한 버전 전략

Part 1. 번들 버전 관리란?

번들 버전 관리가 왜 필요해?

라이브 서비스 게임에서는 클라이언트 버전과 서버 버전이 공존하는 상황이 발생합니다. 앱스토어 업데이트가 완료되지 않은 유저, 업데이트를 미룬 유저, 새로 업데이트한 유저가 동시에 접속합니다.

번들 버전 관리가 없다면:

  • 구버전 클라이언트가 신버전 번들을 받으면 크래시
  • 신버전 클라이언트가 구버전 번들과 호환 안 되면 기능 오작동
  • 강제 업데이트 시 유저 이탈 급증
버전 관리의 핵심 목표가 뭐야?

번들 버전 관리는 세 가지 핵심 목표를 달성해야 합니다:

Part 2. 버전 스키마 선택

버전 번호는 어떤 형식으로 매겨야 해?

게임 번들에 사용되는 주요 버전 스키마입니다:

┌─────────────────────────────────────────────────────────────────┐
│                       버전 스키마 종류                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  1. Semantic Versioning (SemVer)                               │
│  ─────────────────────────────────                              │
│  형식: MAJOR.MINOR.PATCH                                       │
│  예시: 2.1.3                                                   │
│                                                                 │
│      MAJOR: 호환 안 되는 변경 (클라이언트 업데이트 필수)          │
│      MINOR: 하위 호환되는 기능 추가                              │
│      PATCH: 버그 수정                                           │
│                                                                 │
│  장점: 호환성 의도가 버전에 명시됨                               │
│  단점: 번들별 개별 관리 복잡                                     │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  2. 날짜 기반 (CalVer)                                          │
│  ─────────────────────                                          │
│  형식: YYYY.MM.DD.BUILD                                        │
│  예시: 2024.01.15.001                                          │
│                                                                 │
│  장점: 언제 만들어졌는지 즉시 파악                               │
│  단점: 호환성 정보 없음                                          │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  3. 해시 기반                                                   │
│  ─────────────                                                  │
│  형식: 콘텐츠 해시 (MD5, SHA-1)                                 │
│  예시: a3f2e1b8c4d7                                            │
│                                                                 │
│  장점: 변경 여부 100% 정확, 중복 방지                            │
│  단점: 사람이 읽기 어려움, 순서 파악 불가                         │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  4. 하이브리드 (권장)                                            │
│  ─────────────────                                              │
│  형식: MAJOR.MINOR_YYYYMMDD_HASH                               │
│  예시: 2.1_20240115_a3f2e1                                     │
│                                                                 │
│  장점: 호환성 + 날짜 + 무결성 모두 포함                          │
│  단점: 다소 긴 버전 문자열                                       │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
실제 프로젝트에서 버전 스키마는 어떻게 구현해?

번들 버전 정보를 관리하는 구조체와 비교 로직입니다:

// BundleVersion.cs - 하이브리드 버전 스키마 using System; public struct BundleVersion : IComparable<BundleVersion> { public int Major; // 호환성 파괴 변경 public int Minor; // 기능 추가 public int Patch; // 버그 수정 public string BuildDate; // YYYYMMDD public string Hash; // 콘텐츠 해시 (6자리) // 문자열 파싱: "2.1.3_20240115_a3f2e1" public static BundleVersion Parse(string versionString) { var parts = versionString.Split('_'); var semver = parts[0].Split('.'); return new BundleVersion { Major = int.Parse(semver[0]), Minor = int.Parse(semver[1]), Patch = int.Parse(semver[2]), BuildDate = parts[1], Hash = parts[2] }; } // 호환성 검사 public bool IsCompatibleWith(BundleVersion clientVersion) { // Major가 다르면 무조건 비호환 if (Major != clientVersion.Major) return false; // 서버 Minor가 클라이언트보다 높으면: 하위 호환 (OK) // 서버 Minor가 클라이언트보다 낮으면: 상위 호환 필요 if (Minor < clientVersion.Minor) return false; return true; } // 정렬용 비교 public int CompareTo(BundleVersion other) { if (Major != other.Major) return Major.CompareTo(other.Major); if (Minor != other.Minor) return Minor.CompareTo(other.Minor); if (Patch != other.Patch) return Patch.CompareTo(other.Patch); return string.Compare(BuildDate, other.BuildDate); } public override string ToString() => $"{Major}.{Minor}.{Patch}_{BuildDate}_{Hash}"; }

Part 3. 호환성 관리 전략

하위 호환성이랑 상위 호환성이 뭐야?

호환성 방향에 따라 두 가지로 구분합니다:

┌─────────────────────────────────────────────────────────────────┐
│                     호환성 방향 이해하기                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [하위 호환성 (Backward Compatibility)]                          │
│  ─────────────────────────────────────                          │
│                                                                 │
│    신버전 서버 ──→ 구버전 클라이언트                              │
│         ↓                                                       │
│    "새로 배포한 번들을 옛날 앱에서도 읽을 수 있어?"              │
│                                                                 │
│    예: 서버 v2.1 번들 → 클라이언트 v2.0 앱                       │
│        새 필드 추가했지만, 기존 앱이 무시하면 OK                  │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [상위 호환성 (Forward Compatibility)]                           │
│  ────────────────────────────────────                           │
│                                                                 │
│    구버전 서버 ──→ 신버전 클라이언트                              │
│         ↓                                                       │
│    "옛날 번들을 새 앱에서도 읽을 수 있어?"                       │
│                                                                 │
│    예: 서버 v2.0 번들 → 클라이언트 v2.1 앱                       │
│        새 앱이 없는 필드에 대해 기본값 처리 필요                  │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [실제 상황]                                                    │
│                                                                 │
│    패치 배포 시간축:                                            │
│    ─────────────────────────────────────────────────────        │
│    00:00          06:00          12:00          24:00           │
│      │              │              │              │             │
│      ▼              ▼              ▼              ▼             │
│    서버 v2.1      CDN 전파      iOS 승인       Android 롤아웃    │
│    배포 완료      70% 완료      완료           100%              │
│                                                                 │
│    이 24시간 동안:                                              │
│    - v2.0 앱 + v2.1 번들 조합 발생 (하위 호환 필요)              │
│    - v2.1 앱 + v2.0 번들 조합 발생 (상위 호환 필요)              │
│                                                                 │
│    ∴ 양방향 호환성이 모두 필요!                                 │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
양방향 호환성을 보장하려면 어떻게 해야 해?

데이터 구조 변경 시 호환성을 유지하는 규칙입니다:

호환성 유지 규칙

  • 필드 추가: 항상 optional로, 기본값 필수
  • 필드 삭제: deprecated 마킹 → 2버전 후 삭제
  • 필드 타입 변경: 절대 금지 → 새 필드로 대체
  • 필드 이름 변경: 금지 → alias 유지 또는 새 필드
// 호환성 있는 데이터 진화 예시 // v1.0 - 최초 릴리스 public class CharacterData_v1 { public int id; public string name; public int level; } // v1.1 - 새 필드 추가 (하위 호환 O) public class CharacterData_v1_1 { public int id; public string name; public int level; // 새 필드: optional + 기본값 public int rarity = 1; // v1.0 클라이언트는 이 필드 무시 } // v1.2 - 타입 변경이 필요한 경우 (호환성 유지) public class CharacterData_v1_2 { public int id; public string name; public int level; public int rarity = 1; // ❌ 잘못된 방법: 기존 필드 타입 변경 // public float level; // int → float 변경 = 호환성 파괴! // ✅ 올바른 방법: 새 필드 추가 public float levelProgress = 0f; // 경험치 진행률을 별도로 } // v2.0 - 호환성 파괴 변경 (Major 버전 업) public class CharacterData_v2 { public long characterId; // int → long (ID 체계 전면 개편) public string displayName; public CharacterStats stats; // level을 stats 객체로 통합 // Major 버전 변경 = 클라이언트 강제 업데이트 필요 }
직렬화 포맷도 호환성에 영향을 줘?

직렬화 포맷에 따라 호환성 유지 난이도가 다릅니다:

┌─────────────────────────────────────────────────────────────────┐
│                직렬화 포맷별 호환성 특성                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [JSON]                                                         │
│  ───────────────────────────────────────────────────            │
│  호환성: ★★★★★                                                  │
│  - 필드 추가: 자동 무시 (하위 호환 ✓)                            │
│  - 필드 누락: null/기본값 (상위 호환 ✓)                          │
│  - 단점: 파싱 느림, 용량 큼                                      │
│                                                                 │
│  {"id": 1, "name": "hero", "newField": "ignored by v1"}         │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [Protocol Buffers (Protobuf)]                                  │
│  ───────────────────────────────────────────────────            │
│  호환성: ★★★★☆                                                  │
│  - 필드 번호 기반 → 번호만 유지하면 이름 변경 가능               │
│  - optional 기본 → 추가/삭제 유연                               │
│  - 단점: 스키마 파일(.proto) 관리 필요                          │
│                                                                 │
│  message Character {                                            │
│    int32 id = 1;                                               │
│    string name = 2;                                            │
│    int32 new_field = 100; // 번호만 안 겹치면 OK               │
│  }                                                              │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [MessagePack]                                                  │
│  ───────────────────────────────────────────────────            │
│  호환성: ★★★☆☆                                                  │
│  - 배열 기반: 순서 변경 시 호환성 파괴                           │
│  - 맵 기반: JSON과 유사한 유연성                                 │
│  - 장점: JSON보다 빠르고 작음                                    │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [Binary (자체 포맷)]                                            │
│  ───────────────────────────────────────────────────            │
│  호환성: ★☆☆☆☆                                                  │
│  - 고정 크기 구조체: 필드 추가 = 호환성 파괴                     │
│  - 수동으로 버전 분기 코드 작성 필요                             │
│  - 장점: 가장 빠름, 가장 작음                                    │
│                                                                 │
│  [header:4][version:2][data_size:4][data:N]                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

권장: 설정/테이블 데이터 → JSON 또는 Protobuf
     실시간 패킷 → MessagePack 또는 Binary

Part 4. 매니페스트와 버전 추적

매니페스트가 버전 관리에서 어떤 역할을 해?

매니페스트는 모든 번들의 버전 상태를 담은 메타데이터 파일입니다. 클라이언트가 어떤 번들을 다운로드해야 하는지 결정하는 핵심 정보입니다.

┌─────────────────────────────────────────────────────────────────┐
│                    매니페스트 구조와 역할                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  manifest.json                                                  │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │ {                                                       │    │
│  │   "manifestVersion": "2024.01.15.003",                  │    │
│  │   "minClientVersion": "2.0.0",                          │    │
│  │   "bundles": {                                          │    │

│  │       "version": "2.1.3_20240115_a3f2e1",              │    │

│  │     "effects": {                                        │    │

│  │       "crc": 1927364851,                               │    │

│  │ }                                                       │    │
│  └─────────────────────────────────────────────────────────┘    │

│  ┌─────────────────────────────────────────────────────────┐    │
│  │              매니페스트 활용 흐름                         │    │
│  │                                                         │    │
│  │  1. 앱 시작 → CDN에서 최신 manifest.json 다운로드       │    │

│  │  5. 성공 시 로컬 manifest 업데이트                      │    │

│                                                                 │
└─────────────────────────────────────────────────────────────────┘
매니페스트 기반 업데이트 시스템 코드는 어떻게 짜?
// ManifestManager.cs - 매니페스트 기반 버전 관리 using System; using System.Collections.Generic; using UnityEngine; using UnityEngine.Networking; public class ManifestManager : MonoBehaviour { [System.Serializable] public class BundleInfo { public string version; ShowUpdateConfirmPopup(updatesNeeded.Count, totalSize); } } private List<string> GetUpdatedBundles() { var updates = new List<string>(); foreach (var kvp in m_RemoteManifest.bundles) { string bundleName = kvp.Key; BundleInfo remoteInfo = kvp.Value; // 로컬에 없거나 버전이 다르면 업데이트 필요 if (!m_LocalManifest.bundles.TryGetValue(bundleName, out var localInfo) || localInfo.version != remoteInfo.version) { updates.Add(bundleName); } } return updates; } public IEnumerator DownloadBundles(List<string> bundleNames) { foreach (var bundleName in bundleNames) { var info = m_RemoteManifest.bundles[bundleName]; string url = $"{CDN_URL}{bundleName}_{info.version}"; var request = UnityWebRequest.Get(url); yield return request.SendWebRequest(); // CRC 검증 if (!VerifyCRC(request.downloadHandler.data, info.crc)) { Debug.LogError($"CRC 불일치: {bundleName}"); continue; } // 로컬 저장 SaveBundleToLocal(bundleName, request.downloadHandler.data); // 로컬 매니페스트 업데이트 m_LocalManifest.bundles[bundleName] = info; } // 최종 매니페스트 저장 SaveLocalManifest(m_LocalManifest); } }

// BundleRollbackSystem.cs - 종합 롤백 시스템 public class BundleRollbackSystem { private const int MAX_BUNDLE_HISTORY = 5; private Dictionary<string, Queue<BundleSnapshot>> m_BundleHistory; public struct BundleSnapshot { public string Version; public string LocalPath; public DateTime DeployedAt; public string ManifestHash; } // 번들 업데이트 전 스냅샷 저장 public void SaveSnapshot(string bundleName, string version, string path) { if (!m_BundleHistory.ContainsKey(bundleName)) { m_BundleHistory[bundleName] = new Queue<BundleSnapshot>(); } var queue = m_BundleHistory[bundleName]; // 히스토리 개수 제한 while (queue.Count >= MAX_BUNDLE_HISTORY) { var oldest = queue.Dequeue(); DeleteBundleFile(oldest.LocalPath); } // 현재 상태 백업 string backupPath = CreateBackup(bundleName, path); queue.Enqueue(new BundleSnapshot { Version = version, LocalPath = backupPath, DeployedAt = DateTime.UtcNow, ManifestHash = GetCurrentManifestHash() }); } // 특정 버전으로 롤백 public bool RollbackTo(string bundleName, string targetVersion) { if (!m_BundleHistory.TryGetValue(bundleName, out var queue)) { Debug.LogError($"번들 히스토리 없음: {bundleName}"); return false; } // 대상 버전 찾기 BundleSnapshot? target = null; foreach (var snapshot in queue) { if (snapshot.Version == targetVersion) { target = snapshot; break; } } if (!target.HasValue) { Debug.LogError($"대상 버전 없음: {targetVersion}"); return false; } // 백업에서 복원 RestoreFromBackup(bundleName, target.Value.LocalPath); // 로컬 매니페스트 업데이트 UpdateLocalManifestVersion(bundleName, targetVersion); Debug.Log($"롤백 완료: {bundleName} → {targetVersion}"); return true; } // 직전 버전으로 빠른 롤백 public bool RollbackToPrevious(string bundleName) { if (!m_BundleHistory.TryGetValue(bundleName, out var queue) || queue.Count < 2) { return false; } // 현재 버전 스킵, 직전 버전으로 var snapshots = queue.ToArray(); var previous = snapshots[snapshots.Length - 2]; return RollbackTo(bundleName, previous.Version); } }

// FeatureFlagManager.cs - 서버 제어 기능 플래그 public class FeatureFlagManager : MonoBehaviour { private Dictionary<string, bool> m_Flags = new(); private Dictionary<string, string> m_FallbackAssets = new(); // 서버에서 플래그 동기화 (주기적 호출) public IEnumerator SyncFlags() { var request = UnityWebRequest.Get("https://api.game.com/feature-flags"); yield return request.SendWebRequest(); if (request.result == UnityWebRequest.Result.Success) { var response = JsonUtility.FromJson<FeatureFlagResponse>( request.downloadHandler.text); foreach (var flag in response.flags) { m_Flags[flag.name] = flag.enabled; m_FallbackAssets[flag.name] = flag.fallbackAsset; } } } // 기능 활성화 여부 확인 public bool IsEnabled(string featureName) { return m_Flags.TryGetValue(featureName, out var enabled) && enabled; } // 에셋 로드 시 플래그 체크 public T LoadAssetWithFlag<T>(string featureName, string newAsset) where T : UnityEngine.Object { if (IsEnabled(featureName)) { // 새 기능 활성화 → 새 에셋 사용 return Resources.Load<T>(newAsset); } else { // 기능 비활성화 → 폴백 에셋 사용 if (m_FallbackAssets.TryGetValue(featureName, out var fallback)) { return Resources.Load<T>(fallback); } return null; } } } // 사용 예시: 새 스킬 이펙트 (문제 발생 시 서버에서 OFF) public class SkillEffectLoader { public GameObject LoadSkillEffect(int skillId) { var flagManager = FeatureFlagManager.Instance; // 서버에서 "new_skill_effects_v2"를 false로 설정하면 // → 자동으로 구버전 이펙트(v1) 사용 return flagManager.LoadAssetWithFlag<GameObject>( "new_skill_effects_v2", $"Effects/Skills/{skillId}_v2" ); } }

⚠️ 기능 플래그 설계 주의점

  • 플래그가 너무 많으면 조합 폭발 → 테스트 불가능
  • 플래그 ON/OFF 시 상태 불일치 위험
  • 임시 플래그는 일정 기간 후 반드시 제거
  • 플래그 변경 로그 필수 기록

핵심 정리: 번들 버전 관리

  • 버전 스키마: SemVer + 날짜 + 해시 조합 권장
  • 호환성: 양방향(하위/상위) 모두 고려, 필드 추가는 optional
  • 매니페스트: 모든 번들 상태의 단일 진실 공급원
  • 롤아웃: 단계적 배포(1%→10%→50%→100%)로 리스크 최소화
  • 롤백: 매니페스트 교체, 핫픽스, 기능 플래그 중 선택
  • 모니터링: 크래시율/로딩시간 실시간 추적으로 자동 롤백 트리거
