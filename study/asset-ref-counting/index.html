Reference Counting

아무도 안 쓰면 해제 - 리소스 수명 관리의 핵심 패턴

Part 1. Reference Counting이란?

레퍼런스 카운팅이 뭐야?

리소스를 몇 군데서 사용하는지 세는 것

카운트가 0이 되면 → 아무도 안 쓰니까 → 메모리 해제!

핵심 원칙: "마지막으로 사용 끝낸 놈이 불 끄고 나가라"

Reference Counting의 핵심 아이디어

    ┌─────────────────────────────────────────────────────────────┐
    │                      Texture (hero.png)                      │
    │                      ┌─────────────────┐                     │
    │                      │  RefCount: 3    │                     │
    │                      └────────┬────────┘                     │
    │                               │                              │
    │              ┌────────────────┼────────────────┐             │
    │              │                │                │             │
    │              ▼                ▼                ▼             │
    │        ┌──────────┐    ┌──────────┐    ┌──────────┐         │
    │        │ Player   │    │ NPC_A    │    │ Portrait │         │
    │        │ Object   │    │ Object   │    │ UI       │         │
    │        └──────────┘    └──────────┘    └──────────┘         │
    │                                                              │
    │   같은 텍스처를 3군데서 공유 중 → 메모리 1개만 사용!          │
    └─────────────────────────────────────────────────────────────┘


    RefCount 변화 과정:

    LoadTexture()     → RefCount = 1  (생성)
    Player 사용       → RefCount = 2  (AddRef)
    NPC 사용          → RefCount = 3  (AddRef)
    Player 삭제       → RefCount = 2  (Release)
    Portrait UI 삭제  → RefCount = 1  (Release)
    NPC 삭제          → RefCount = 0  → 💥 DELETE!
왜 게임에서 중요해?

게임에서는 같은 리소스를 수백 개가 공유하거든!

게임에서 Reference Counting이 필요한 이유

[예시: 병사 100명이 같은 모델/텍스처 사용]

Without Reference Counting:
━━━━━━━━━━━━━━━━━━━━━━━━━━

  병사1 → Model 복사본 (50MB)
  병사2 → Model 복사본 (50MB)
  병사3 → Model 복사본 (50MB)
  ...
  병사100 → Model 복사본 (50MB)
  ─────────────────────────────
  총 메모리: 5GB  💀 메모리 폭발!


With Reference Counting:
━━━━━━━━━━━━━━━━━━━━━━━

  병사1   ──┐
  병사2   ──┼──→ Model (RefCount: 100)  ← 50MB 1개만!
  병사3   ──┤
  ...      │
  병사100 ──┘
  ─────────────────────────────
  총 메모리: 50MB  ✅ 100배 절약!


해제 문제도 해결:
━━━━━━━━━━━━━━━

  Q: 병사 50명이 죽었다. 모델을 해제해야 할까?
  A: RefCount가 50이니까 NO! 아직 50명이 쓰고 있음.

  Q: 마지막 병사가 죽었다. 이제 해제?
  A: RefCount가 0이 되었으니 YES! 이제 진짜 해제.

Part 2. Reference Counting 기본 구현

어떻게 만들어?

핵심 3가지: 카운터 변수 + AddRef() + Release()

// 가장 단순한 Reference Counting 구현 class RefCounted { private: int m_RefCount; public: RefCounted() : m_RefCount(1) // 생성 시 1로 시작! {} // 참조 추가 void AddRef() { m_RefCount++; } // 참조 해제 void Release() { m_RefCount--; if (m_RefCount == 0) { delete this; // 💀 자기 자신 삭제 } } int GetRefCount() const { return m_RefCount; } protected: // 직접 delete 방지 - 반드시 Release()로만 삭제 virtual ~RefCounted() = default; };
AddRef / Release 호출 시점

┌─────────────────────────────────────────────────────────────────┐
│                         AddRef() 호출                            │
├─────────────────────────────────────────────────────────────────┤
│  • 포인터를 다른 변수에 복사할 때                                 │
│  • 컨테이너에 추가할 때                                          │
│  • 함수 인자로 전달받을 때 (소유권 가질 때)                       │
│  • 콜백/이벤트 핸들러에 등록할 때                                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                        Release() 호출                            │
├─────────────────────────────────────────────────────────────────┤
│  • 포인터 변수가 스코프를 벗어날 때                               │
│  • 다른 객체로 교체할 때                                         │
│  • 컨테이너에서 제거할 때                                        │
│  • 객체가 소멸할 때 (소유하던 리소스 정리)                        │
└─────────────────────────────────────────────────────────────────┘


코드 예시:
━━━━━━━━━

void UseTexture(Texture* tex)
{
    tex->AddRef();      // ← 이 함수에서 사용할 거니까 AddRef

    // ... 텍스처 사용 ...

    tex->Release();     // ← 다 썼으니 Release
}
이거 불편하지 않아? 매번 AddRef/Release 호출해야 해?

그래서 스마트 포인터를 쓰는 거야!

포인터를 감싸서 자동으로 AddRef/Release 호출해줌.

// 간단한 스마트 포인터 구현 template<typename T> class RefPtr { private: T* m_Ptr; public: // 생성자 - 포인터 받으면 AddRef RefPtr(T* ptr = nullptr) : m_Ptr(ptr) { if (m_Ptr) { m_Ptr->AddRef(); } } // 복사 생성자 - 복사하면 AddRef RefPtr(const RefPtr& other) : m_Ptr(other.m_Ptr) { if (m_Ptr) { m_Ptr->AddRef(); } } // 소멸자 - 범위 벗어나면 Release ~RefPtr() { if (m_Ptr) { m_Ptr->Release(); } } // 대입 연산자 RefPtr& operator=(const RefPtr& other) { if (this != &other) { // 기존 것 Release if (m_Ptr) { m_Ptr->Release(); } // 새 것 AddRef m_Ptr = other.m_Ptr; if (m_Ptr) { m_Ptr->AddRef(); } } return *this; } // 포인터처럼 사용 T* operator->() const { return m_Ptr; } T& operator*() const { return *m_Ptr; } operator bool() const { return m_Ptr != nullptr; } };
스마트 포인터의 자동 관리

[수동 관리 (위험!)]
━━━━━━━━━━━━━━━━━

Texture* tex = LoadTexture("hero.png");  // RefCount = 1
tex->AddRef();                           // RefCount = 2

// ... 여기서 예외 발생하면? Release 누락! 💀

tex->Release();                          // 호출 안 됨 → 메모리 누수!


[스마트 포인터 (안전!)]
━━━━━━━━━━━━━━━━━━━━

{
    RefPtr tex = LoadTexture("hero.png");  // RefCount = 1
    RefPtr copy = tex;                     // RefCount = 2

    // 예외가 발생해도...
    throw std::exception();

}   // 스코프 끝 → 소멸자 자동 호출
    // copy 소멸 → Release() → RefCount = 1
    // tex 소멸 → Release() → RefCount = 0 → DELETE!
    // ✅ 메모리 누수 없음!

Part 3. std::shared_ptr 심층 분석

C++ 표준의 shared_ptr은 어떻게 동작해?

shared_ptr은 Control Block이라는 별도 메모리를 사용해.

Control Block에 RefCount가 저장돼 있어.

std::shared_ptr의 내부 구조

┌─────────────────────────────────────────────────────────────────┐
│                        shared_ptr A                              │
│  ┌─────────────────────────────────────────────────────────┐    │
│  │  T* ptr       ────────────────────────┐                  │    │
│  │  ControlBlock* ctrl ──────────┐       │                  │    │
│  └───────────────────────────────┼───────┼──────────────────┘    │
│                                  │       │                       │
│                                  ▼       ▼                       │
│                        ┌──────────────────────────────┐          │
│                        │      Control Block           │          │
│                        ├──────────────────────────────┤          │
│                        │  strong_count: 2             │          │
│                        │  weak_count: 1               │          │
│                        │  deleter: default_delete  │          │
│                        │  allocator: ...              │          │
│                        └──────────────────────────────┘          │
│                                  │                               │
│                                  ▼                               │
│                        ┌──────────────────────────────┐          │
│                        │      실제 객체 (T)           │          │
│                        │  ┌────────────────────────┐  │          │
│                        │  │  Texture 데이터        │  │          │
│                        │  │  (픽셀, 메타데이터 등)  │  │          │
│                        │  └────────────────────────┘  │          │
│                        └──────────────────────────────┘          │
└─────────────────────────────────────────────────────────────────┘


shared_ptr 복사 시:
━━━━━━━━━━━━━━━━━━

auto a = std::make_shared();  // strong_count = 1
auto b = a;                            // strong_count = 2, 같은 Control Block 공유
auto c = a;                            // strong_count = 3

c.reset();                             // strong_count = 2
b.reset();                             // strong_count = 1
a.reset();                             // strong_count = 0 → 객체 삭제!
make_shared랑 new의 차이는?

make_shared가 훨씬 효율적이야!

// 방법 1: new 사용 (비추천) std::shared_ptr<Texture> tex1(new Texture()); // 메모리 할당 2번: // 1. new Texture() → 객체 메모리 // 2. shared_ptr 내부 → Control Block 메모리 // 방법 2: make_shared 사용 (추천!) auto tex2 = std::make_shared<Texture>(); // 메모리 할당 1번: // 객체 + Control Block을 한 덩어리로 할당!
new vs make_shared 메모리 레이아웃

[new Texture() 방식]
━━━━━━━━━━━━━━━━━━━

  할당 1:                    할당 2:
  ┌──────────────────┐      ┌──────────────────┐
  │  Texture 객체    │      │  Control Block   │
  │  (실제 데이터)    │      │  (RefCount 등)   │
  └──────────────────┘      └──────────────────┘
        ↑                          ↑
        └──────────── 서로 다른 메모리 위치


[make_shared 방식]
━━━━━━━━━━━━━━━━━━

  할당 1 (한 덩어리):
  ┌────────────────────────────────────────┐
  │  Control Block  │  Texture 객체        │
  │  (RefCount 등)  │  (실제 데이터)        │
  └────────────────────────────────────────┘
        연속된 메모리 → 캐시 효율 ↑


장점 비교:
┌────────────────────┬────────────────┬────────────────────┐
│       항목         │  new 방식      │  make_shared 방식  │

Part 4. 순환 참조 문제와 weak_ptr

Reference Counting의 치명적 약점이 있다며?

순환 참조(Circular Reference)가 발생하면 영원히 해제 안 돼!

순환 참조 문제

[정상 참조]
━━━━━━━━━━━

Parent ──────────────→ Child
  ↑                      │
  │       (참조 없음)      │
  └───────────────────────┘

Parent 삭제 → Child RefCount 감소 → Child 삭제  ✅


[순환 참조 - 메모리 누수!]
━━━━━━━━━━━━━━━━━━━━━━━━

Parent ──────────────→ Child
  ↑                      │
  │      (부모 참조)       │
  └───────────────────────┘

  Parent.refCount = 1 (Child가 참조)
  Child.refCount = 1 (Parent가 참조)

  아무도 해제 못 함!  → 💀 메모리 누수!


게임에서 흔한 순환 참조 예시:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

• GameObject ↔ Component
• Entity ↔ Entity (상호 참조)
• UI Widget ↔ Data Binding
• Event Emitter ↔ Event Listener
어떻게 해결해?

weak_ptr을 사용해!

weak_ptr은 RefCount를 증가시키지 않는 참조야.

// 순환 참조가 발생하는 코드 (잘못된 예) class Parent { std::shared_ptr<Child> m_Child; // 자식 소유 }; class Child { std::shared_ptr<Parent> m_Parent; // 💀 순환 참조! }; // 해결: weak_ptr 사용 class Parent { std::shared_ptr<Child> m_Child; // 자식 소유 (strong) }; class Child { std::weak_ptr<Parent> m_Parent; // ✅ 부모 참조 (weak) void DoSomethingWithParent() { // weak_ptr은 직접 접근 불가 // lock()으로 shared_ptr 획득 시도 if (auto parent = m_Parent.lock()) { // 부모가 아직 살아있음 - 사용 가능 parent->DoSomething(); } else { // 부모가 이미 삭제됨 } } };
weak_ptr의 동작 원리

Control Block 구조:
━━━━━━━━━━━━━━━━━━

┌────────────────────────────────────┐
│         Control Block              │
├────────────────────────────────────┤
│  strong_count: 2  ← shared_ptr 수  │
│  weak_count: 1    ← weak_ptr 수    │
└────────────────────────────────────┘

• strong_count가 0 → 객체 삭제
• weak_count가 0 → Control Block도 삭제


weak_ptr.lock() 동작:
━━━━━━━━━━━━━━━━━━━━━

                    weak_ptr
                       │
                       ▼
           ┌─────────────────────┐
           │   strong_count > 0? │
           └──────────┬──────────┘
                      │
           ┌──────────┴──────────┐
           │ YES                  │ NO
           ▼                      ▼
    ┌─────────────────┐    ┌─────────────────┐
    │ shared_ptr 반환  │    │ 빈 shared_ptr   │
    │ strong_count++  │    │ (nullptr)       │
    └─────────────────┘    └─────────────────┘
// 게임에서의 실제 사용 예시: 컴포넌트 시스템 class GameObject { std::vector<std::shared_ptr<Component>> m_Components; public: template<typename T> std::shared_ptr<T> AddComponent() { auto comp = std::make_shared<T>(); comp->SetOwner(weak_from_this()); // weak_ptr로 전달! m_Components.push_back(comp); return comp; } }; class Component { std::weak_ptr<GameObject> m_Owner; // weak로 소유자 참조 public: void SetOwner(std::weak_ptr<GameObject> owner) { m_Owner = owner; } std::shared_ptr<GameObject> GetOwner() const { return m_Owner.lock(); // 안전하게 접근 } };

Part 5. Thread Safety - 멀티스레드 환경

멀티스레드에서 RefCount 관리하면 문제 없어?

Race Condition 발생 가능!

두 스레드가 동시에 RefCount를 수정하면 값이 꼬여.

Race Condition 문제

[Thread A]                    [Thread B]
    │                             │
    ▼                             ▼
refCount 읽기 (1)            refCount 읽기 (1)
    │                             │
    ▼                             ▼
refCount + 1 = 2             refCount + 1 = 2
    │                             │
    ▼                             ▼
refCount 쓰기 (2)            refCount 쓰기 (2)

결과: refCount = 2  💥 (기대값: 3)


해결책: Atomic 연산
━━━━━━━━━━━━━━━━━━━

std::atomic refCount;

refCount.fetch_add(1);  // 원자적 증가 (한 번에 읽고-수정하고-쓰기)

Thread A와 B가 동시에 해도:
refCount = 3  ✅
// Thread-Safe Reference Counting class ThreadSafeRefCounted { private: std::atomic<int> m_RefCount; // 원자적 카운터 public: ThreadSafeRefCounted() : m_RefCount(1) {} void AddRef() { // memory_order_relaxed: 순서 보장 불필요 m_RefCount.fetch_add(1, std::memory_order_relaxed); } void Release() { // memory_order_acq_rel: 해제 전 모든 쓰기가 완료되어야 함 if (m_RefCount.fetch_sub(1, std::memory_order_acq_rel) == 1) { delete this; } } }; // std::shared_ptr은 기본적으로 Thread-Safe! // Control Block의 카운터가 atomic으로 구현됨 // 하지만 주의! std::shared_ptr<Texture> globalTex; // Thread A globalTex = tex1; // ❌ 위험! shared_ptr 자체의 대입은 atomic이 아님 // Thread B globalTex = tex2; // ❌ 동시 대입 시 미정의 동작! // 해결: mutex 사용 또는 atomic_store std::atomic<std::shared_ptr<Texture>> atomicTex; // C++20 // 또는 std::atomic_store(&globalTex, tex1); // C++11
Memory Order 이해하기

┌────────────────────────────────────────────────────────────────┐
│  memory_order_relaxed                                          │
│  • 가장 빠름                                                    │
│  • 순서 보장 없음                                               │
│  • AddRef에 적합 (증가만 하면 됨)                               │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│  memory_order_acquire                                          │
│  • 이 연산 이후의 읽기/쓰기가 이 연산 이전으로 재배치 안 됨     │
│  • 데이터 읽기 시작점에 사용                                    │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│  memory_order_release                                          │
│  • 이 연산 이전의 읽기/쓰기가 이 연산 이후로 재배치 안 됨       │
│  • 데이터 쓰기 완료점에 사용                                    │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│  memory_order_acq_rel                                          │
│  • acquire + release 결합                                      │
│  • Release()에 적합 (객체 삭제 전 모든 쓰기 완료 보장)          │
└────────────────────────────────────────────────────────────────┘

Part 6. 에셋 매니저에서의 Reference Counting

에셋 매니저는 RefCount를 어떻게 활용해?

캐시 + RefCount 조합으로 에셋 수명 관리!

class AssetManager { private: // 캐시: 에셋 경로 → weak_ptr std::unordered_map<std::string, std::weak_ptr<Asset>> m_Cache; std::mutex m_Mutex; public: template<typename T> std::shared_ptr<T> Load(const std::string& path) { std::lock_guard<std::mutex> lock(m_Mutex); // 1. 캐시에서 찾기 auto it = m_Cache.find(path); if (it != m_Cache.end()) { // weak_ptr → shared_ptr 변환 시도 if (auto asset = it->second.lock()) { // 아직 살아있음! 재사용 return std::static_pointer_cast<T>(asset); } // 이미 삭제됨 - 캐시 항목 제거 m_Cache.erase(it); } // 2. 새로 로드 auto asset = LoadFromDisk<T>(path); // 3. 캐시에 등록 (weak_ptr로!) m_Cache[path] = asset; return asset; } private: template<typename T> std::shared_ptr<T> LoadFromDisk(const std::string& path) { // 실제 디스크에서 로드 auto data = ReadFile(path); return std::make_shared<T>(data); } };
에셋 매니저의 캐시 전략

왜 weak_ptr을 쓸까?
━━━━━━━━━━━━━━━━━━━

[shared_ptr로 캐시하면]
• 캐시가 RefCount를 유지 → 영원히 해제 안 됨
• 메모리 누수!

[weak_ptr로 캐시하면]
• 캐시는 RefCount에 영향 없음
• 사용처가 없으면 자동 삭제
• 다음 Load() 시 expired 확인 → 재로드

Part 7. Unity와 Unreal의 Reference Counting

Unity는 어떻게 해?

Unity는 Garbage Collection을 사용해.

C#의 GC가 참조 없는 객체를 자동 수집해.

// Unity (C#) - GC 기반 public class TextureManager : MonoBehaviour { // 참조가 있으면 유지, 없으면 GC가 수집 private Dictionary<string, WeakReference<Texture>> _cache; public Texture Load(string path) { if (_cache.TryGetValue(path, out var weakRef)) { if (weakRef.TryGetTarget(out var tex)) { return tex; // 캐시 히트 } } // 새로 로드 var newTex = Resources.Load<Texture>(path); _cache[path] = new WeakReference<Texture>(newTex); return newTex; } } // Addressables는 명시적 Release 필요! public async Task UseTexture() { var handle = Addressables.LoadAssetAsync<Texture>("hero"); await handle.Task; // 사용... // 반드시 Release 호출! (Reference Counting) Addressables.Release(handle); }
Unreal은?

Unreal은 TSharedPtr / TWeakPtr을 자체 구현해서 사용해.

UObject는 별도의 GC 시스템이 있어.

// Unreal Engine - TSharedPtr 사용 class FMyAssetManager { private: TMap<FString, TWeakPtr<FMyAsset>> Cache; public: TSharedPtr<FMyAsset> LoadAsset(const FString& Path) { // 캐시 확인 if (TWeakPtr<FMyAsset>* Found = Cache.Find(Path)) { if (TSharedPtr<FMyAsset> Pinned = Found->Pin()) { return Pinned; } } // 새로 로드 TSharedPtr<FMyAsset> NewAsset = MakeShared<FMyAsset>(); Cache.Add(Path, NewAsset); return NewAsset; } }; // UObject는 다름! - Unreal GC 사용 UCLASS() class UMyObject : public UObject { GENERATED_BODY() // UPROPERTY가 붙은 참조는 GC가 추적 UPROPERTY() UTexture2D* Texture; // GC가 관리 // UPROPERTY 없으면 GC가 모름! UObject* DangerousRef; // ⚠️ GC가 수집할 수 있음 };

Part 8. 디버깅과 메모리 누수 감지

RefCount 관련 버그는 어떻게 찾아?

대표적인 문제와 디버깅 방법:

// 1. 메모리 누수 감지용 RefCounted 클래스 class DebugRefCounted { private: std::atomic<int> m_RefCount; std::string m_DebugName; // 전역 추적 static std::unordered_set<DebugRefCounted*> s_AllInstances; static std::mutex s_Mutex; public: DebugRefCounted(const std::string& name) : m_RefCount(1) , m_DebugName(name) { std::lock_guard<std::mutex> lock(s_Mutex); s_AllInstances.insert(this); #if _DEBUG printf("[RefCount] Created: %s (count: %d)\n", m_DebugName.c_str(), m_RefCount.load()); #endif } void AddRef() { int oldCount = m_RefCount.fetch_add(1); #if _DEBUG printf("[RefCount] AddRef: %s (%d → %d)\n", m_DebugName.c_str(), oldCount, oldCount + 1); #endif } void Release() { int oldCount = m_RefCount.fetch_sub(1); #if _DEBUG printf("[RefCount] Release: %s (%d → %d)\n", m_DebugName.c_str(), oldCount, oldCount - 1); #endif if (oldCount == 1) { { std::lock_guard<std::mutex> lock(s_Mutex); s_AllInstances.erase(this); } delete this; } } // 메모리 누수 체크 static void ReportLeaks() { std::lock_guard<std::mutex> lock(s_Mutex); if (!s_AllInstances.empty()) { printf("=== MEMORY LEAKS DETECTED ===\n"); for (auto* obj : s_AllInstances) { printf(" Leaked: %s (refCount: %d)\n", obj->m_DebugName.c_str(), obj->m_RefCount.load()); } } else { printf("=== No memory leaks! ===\n"); } } };

Part 9. 성능 고려사항

Reference Counting의 성능 오버헤드는?

의외로 Atomic 연산 비용이 있어!

Reference Counting 성능 비용

┌─────────────────────────────────────────────────────────────────┐
│  연산                    │  대략적 비용                          │
├─────────────────────────────────────────────────────────────────┤
│  일반 정수 증가 (i++)    │  ~1 cycle                             │
│  Atomic 증가             │  ~10-100 cycles (캐시 상태에 따라)     │
│  메모리 할당 (new)       │  ~100-1000 cycles                     │
│  디스크 I/O              │  ~1,000,000+ cycles                   │
└─────────────────────────────────────────────────────────────────┘

상대적으로 보면:
• 디스크 로드 1번 >> Atomic 연산 10,000번
• 걱정할 필요 거의 없음!


하지만 주의할 경우:
━━━━━━━━━━━━━━━━━━

1. 핫 루프에서 shared_ptr 복사가 수천 번 일어날 때
   → 참조로 전달하거나 raw pointer 사용 고려

2. 캐시 라인 경합 (False Sharing)
   → RefCount와 다른 데이터가 같은 캐시 라인에 있으면 성능 저하
// 성능 최적화 팁 // 1. 복사 대신 참조로 전달 void Bad(std::shared_ptr<Texture> tex) // 복사 → AddRef + Release { tex->Use(); } void Good(const std::shared_ptr<Texture>& tex) // 참조 → 카운터 변경 없음 { tex->Use(); } // 2. 로컬에서만 사용할 땐 raw pointer void ProcessTextures(const std::vector<std::shared_ptr<Texture>>& textures) { for (const auto& tex : textures) { // 이 함수 내에서만 사용 → raw pointer도 안전 Texture* raw = tex.get(); raw->Process(); // Atomic 연산 없음! } } // 3. 캐시 라인 정렬로 False Sharing 방지 struct alignas(64) CacheAlignedRefCount // 64바이트 정렬 { std::atomic<int> RefCount; char Padding[60]; // 다른 데이터와 분리 };

핵심 정리

  • Reference Counting - 참조 횟수를 세고, 0이면 삭제
  • 스마트 포인터 - AddRef/Release를 자동 호출 (RAII)
  • shared_ptr - Control Block에 카운터 저장
  • weak_ptr - 순환 참조 해결, RefCount 증가 안 함
  • Thread Safety - Atomic 카운터 필수
  • 에셋 매니저 - weak_ptr 캐시 + Pin 시스템
  • 디버깅 - 전역 추적, 콜 스택 기록
