Environment Separation

개발/스테이징/프로덕션 환경 분리하는 법

1. 왜 환경을 분리해야 해?

개발 서버에서 테스트하면 안 돼?

실제 사고 사례:

사고 재현: 신입 개발자 A: "이 쿼리 테스트해볼게요..." DELETE FROM users; -- WHERE 빼먹음 결과: - 개발 DB? NO, 라이브 DB였음! - 50만 유저 데이터 삭제 - 백업에서 복구까지 8시간 - 보상 비용: ???
그래서 환경을 분리한다고?
환경 분리 구조: [개발자 PC] --> [Development] --> [Staging] --> [Production] 로컬 개발 서버 테스트 라이브 역할: - Development: 개발자 맘대로 - Staging: 라이브 미리보기 - Production: 실제 서비스 (신중!) 접근 권한: - Dev: 모든 개발자 - Staging: 개발자 + QA - Prod: 제한된 인원 (승인 필요)

2. 각 환경은 뭘 해?

Development는 뭐야?
환경 목적 특징
Local 개발자 PC - Docker Compose
- 빠른 반복 개발
- 독립적
Development 통합 개발 - 최신 코드 반영
- 불안정 허용
- 자유로운 테스트
Staging 출시 전 검증 - Prod와 동일 구성
- QA 테스트
- 실제 데이터 복제
Production 실제 서비스 - 최고 안정성
- 변경 승인 필요
- 모니터링 강화
게임 서버는 더 많은 환경이 필요하지 않아?
게임 서버 환경 구성: [Local] - 개발자 PC (Docker) | [Dev] - 개발 서버 (최신 빌드) | [QA] - QA팀 테스트 (스프린트 빌드) | [Staging] - 출시 전 최종 검증 | [CBT] - 클로즈 베타 테스트 | [Live] - 실제 서비스 특수 환경: - [Sandbox] - 기획팀 밸런스 테스트 - [Review] - 앱스토어 심사용 - [Event] - 이벤트 서버 (격리)

3. 환경별 설정은 어떻게 관리해?

DB 주소가 환경마다 다르잖아?

환경 변수로 분리:

# .env.development DB_HOST=dev-db.internal DB_NAME=game_dev REDIS_HOST=dev-redis.internal LOG_LEVEL=DEBUG FEATURE_NEW_DUNGEON=true # .env.staging DB_HOST=staging-db.internal DB_NAME=game_staging REDIS_HOST=staging-redis.internal LOG_LEVEL=INFO FEATURE_NEW_DUNGEON=true # .env.production DB_HOST=prod-db.internal DB_NAME=game_prod REDIS_HOST=prod-redis.internal LOG_LEVEL=WARN FEATURE_NEW_DUNGEON=false # 아직 출시 전
비밀번호는 어떻게 해?

환경 변수 파일에 넣으면 안 돼!

# Secret Manager 사용 (AWS) aws secretsmanager get-secret-value \ --secret-id game-server/production/db-password # 쿠버네티스 Secret kubectl create secret generic db-credentials \ --from-literal=password='super-secret-password' # 코드에서 사용 apiVersion: v1 kind: Pod spec: containers: - name: game-server env: - name: DB_PASSWORD valueFrom: secretKeyRef: name: db-credentials key: password
코드에서는 어떻게 읽어?
// C++ 게임 서버 예시 class Config { public: static Config& Instance() { static Config instance; return instance; } void Load() { // 환경 변수에서 읽기 m_dbHost = GetEnvOrDefault("DB_HOST", "localhost"); m_dbPort = std::stoi(GetEnvOrDefault("DB_PORT", "5432")); m_logLevel = GetEnvOrDefault("LOG_LEVEL", "DEBUG"); // 환경별 설정 파일 std::string env = GetEnvOrDefault("GAME_ENV", "development"); LoadConfigFile("config." + env + ".json"); } private: std::string GetEnvOrDefault(const char* name, const char* def) { const char* value = std::getenv(name); return value ? value : def; } std::string m_dbHost; int m_dbPort; std::string m_logLevel; };

4. 테스트 데이터는 어떻게 해?

Staging에서 실제 유저 데이터로 테스트하고 싶은데?

개인정보 주의!

데이터 복제 전략: 1. 익명화 (Anonymization) - 이름: "김철수" -> "User_12345" - 이메일: "kim@gmail.com" -> "test_12345@example.com" - 전화번호: "010-1234-5678" -> "010-0000-0000" 2. 마스킹 (Masking) - 이름: "김철수" -> "김**" - 이메일: "kim@gmail.com" -> "k**@g****.com" 3. 합성 데이터 (Synthetic) - 실제 데이터 통계로 가짜 데이터 생성 - 패턴은 같지만 실제 유저 없음
DB 복제 스크립트는?
#!/bin/bash # sync_staging_db.sh - Production -> Staging 데이터 복제 # 1. Production 백업 (익명화된 버전) pg_dump -h prod-db -d game_prod \ --exclude-table=user_payments \ --exclude-table=user_logs \ > /tmp/prod_backup.sql # 2. 익명화 처리 python anonymize.py /tmp/prod_backup.sql > /tmp/anonymous.sql # 3. Staging에 복원 psql -h staging-db -d game_staging < /tmp/anonymous.sql # 4. 테스트 계정 추가 psql -h staging-db -d game_staging << EOF INSERT INTO users (id, name, email, role) VALUES (999901, 'QA_User_1', 'qa1@test.com', 'tester'), (999902, 'QA_User_2', 'qa2@test.com', 'tester'), (999903, 'QA_Admin', 'qa_admin@test.com', 'admin'); EOF echo "Staging DB sync completed!"

5. 코드는 어떻게 올려?

Dev에서 바로 Prod로 배포하면 안 돼?

단계별 프로모션 필수:

배포 파이프라인: [Git Push] --> [CI Build] --> [Dev 배포] --> [Auto Test] | v (통과) [Staging 배포] --> [QA Test] | v (승인) [Production 배포] 시간: - Dev 배포: 자동 (커밋 즉시) - Staging 배포: 수동 or 스케줄 - Prod 배포: 승인 필요
승인 프로세스는?
# GitHub Actions 배포 워크플로우 name: Deploy to Production on: push: branches: [release/*] jobs: deploy-staging: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: Deploy to Staging run: ./deploy.sh staging deploy-production: needs: deploy-staging runs-on: ubuntu-latest environment: name: production # 수동 승인 필요! steps: - uses: actions/checkout@v3 - name: Deploy to Production run: ./deploy.sh production
승인 프로세스: 1. Staging 배포 완료 2. QA 테스트 통과 3. 배포 요청 생성 (Slack 알림) 4. 리뷰어 2명 승인 5. 배포 시간 확인 (피크 시간 피하기) 6. Production 배포 실행 7. 모니터링 (30분) 8. 완료 보고

6. 네트워크도 분리해야 해?

Dev에서 Prod DB에 실수로 접속할 수도 있잖아?

네트워크 격리로 원천 차단:

VPC 분리: [VPC: Development] [VPC: Production] +------------------+ +------------------+ | Dev Server | | Prod Server | | Dev DB | X | Prod DB | | Dev Redis | <----> | Prod Redis | +------------------+ 차단 +------------------+ 10.0.0.0/16 10.1.0.0/16 - Dev에서 Prod로 접근 불가 - Prod는 완전히 격리된 네트워크 - VPN/Bastion으로만 접근
AWS에서는 어떻게 설정해?
# Terraform VPC 분리 resource "aws_vpc" "development" { cidr_block = "10.0.0.0/16" tags = { Environment = "development" } } resource "aws_vpc" "production" { cidr_block = "10.1.0.0/16" tags = { Environment = "production" } } # Security Group - Dev에서 Prod 접근 차단 resource "aws_security_group" "prod_db" { vpc_id = aws_vpc.production.id ingress { from_port = 5432 to_port = 5432 protocol = "tcp" # Production VPC 내부에서만 접근 cidr_blocks = ["10.1.0.0/16"] } # Development VPC (10.0.0.0/16)는 허용 안 함! }

핵심 정리: 환경 분리

  • 환경 구분 - Local / Dev / Staging / Production (+ QA, CBT 등)
  • 설정 분리 - 환경 변수 + Secret Manager
  • 데이터 격리 - 익명화, 마스킹, 합성 데이터
  • 배포 프로모션 - 단계별 승인 프로세스
  • 네트워크 격리 - VPC 분리, Security Group
  • 핵심 - Production은 최고 수준의 보호!
