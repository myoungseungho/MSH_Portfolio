Monitoring & Alerting

서버 장애를 30초 만에 알아채는 법

1. 모니터링 없으면 어떻게 돼?

장애 나면 유저가 신고하지 않아?

그때는 이미 늦었어!

모니터링 없는 회사의 장애 대응: 02:00 - 서버 다운 (아무도 모름) 02:30 - 유저: "게임 안 돼요" (디시인사이드) 03:00 - 커뮤니티: "서버 터졌대" (루머 확산) 03:15 - CS팀: "문의 폭주 중..." (출근 요청) 03:30 - 개발팀 도착, 원인 파악 시작 04:00 - 복구 완료 결과: - 장애 인지까지: 1시간 30분 - 총 장애 시간: 2시간 - SNS 악플: 폭발
모니터링이 있으면?
모니터링 있는 회사의 장애 대응: 02:00:00 - 서버 다운 02:00:30 - 알람 발생 "CPU 100%, 응답시간 급증" 02:00:35 - 온콜 담당자 알림 (자동 전화) 02:01:00 - 담당자 확인, 자동 롤백 시작 02:02:00 - 복구 완료 결과: - 장애 인지까지: 30초 - 총 장애 시간: 2분 - 유저: "어? 잠깐 끊겼나? 됐네"

30초 vs 1시간 30분 차이야!

2. 뭘 모니터링해야 해?

CPU 사용량만 보면 되지 않아?

4가지 골든 시그널을 봐야 해:

시그널 설명 게임 서버 예시
Latency 응답 시간 패킷 처리 시간
DB 쿼리 시간
Traffic 처리량 동시 접속자
초당 패킷 수
Errors 에러율 접속 실패율
5xx 응답률
Saturation 포화도 CPU/메모리 사용률
커넥션풀 사용률
게임 서버 전용 메트릭은?
게임 서버 필수 메트릭: [접속자] - 동시 접속자 (CCU) - 분당 접속/퇴장 수 - 채널별 인원 [게임 로직] - 전투 시작/종료 수 - 던전 입장/클리어 수 - 아이템 드롭 수 - 거래 건수 [경제] - 골드 생성/소멸량 - 캐시 결제 건수 - 캐시 사용량 [성능] - 게임 루프 틱 시간 - 패킷 처리 지연 - DB 쿼리 시간 - 월드 시뮬레이션 부하

3. 어떻게 수집해?

Prometheus가 유명하던데?

맞아! 구조는 이래:

모니터링 아키텍처: [Game Server] --메트릭--> [Prometheus] --> [Grafana] | | | v v v /metrics 시계열 저장 대시보드 엔드포인트 쿼리 엔진 시각화 [Alertmanager] <-- 알람 규칙 -- [Prometheus] | v [Slack/PagerDuty/전화]
게임 서버에서 메트릭을 어떻게 내보내?
// C++ 게임 서버 메트릭 예시 #include #include // 메트릭 정의 prometheus::Counter& login_total = prometheus::BuildCounter() .Name("game_login_total") .Help("Total login attempts") .Register(*registry); prometheus::Histogram& packet_latency = prometheus::BuildHistogram() .Name("game_packet_latency_ms") .Help("Packet processing latency") .Buckets({1, 5, 10, 25, 50, 100, 250, 500}) .Register(*registry); // 로그인 시 void OnLogin(Player* player) { login_total.Increment(); // ... } // 패킷 처리 시 void ProcessPacket(Packet* packet) { auto start = std::chrono::high_resolution_clock::now(); // 패킷 처리... auto end = std::chrono::high_resolution_clock::now(); auto duration_ms = std::chrono::duration_cast< std::chrono::milliseconds>(end - start).count(); packet_latency.Observe(duration_ms); }
Node.js 서버는?
// Node.js 메트릭 예시 const client = require('prom-client'); // 기본 메트릭 수집 client.collectDefaultMetrics(); // 커스텀 메트릭 const loginCounter = new client.Counter({ name: 'game_login_total', help: 'Total login attempts', labelNames: ['status'] }); const packetHistogram = new client.Histogram({ name: 'game_packet_latency_ms', help: 'Packet processing latency', buckets: [1, 5, 10, 25, 50, 100, 250, 500] }); // 사용 app.post('/login', async (req, res) => { const timer = packetHistogram.startTimer(); try { await processLogin(req); loginCounter.inc({ status: 'success' }); } catch (e) { loginCounter.inc({ status: 'failure' }); } finally { timer(); // 시간 기록 } }); // /metrics 엔드포인트 app.get('/metrics', async (req, res) => { res.set('Content-Type', client.register.contentType); res.end(await client.register.metrics()); });

4. 알람은 어떻게 설정해?

CPU 80%면 알람이 오게?

단순 임계값은 위험해!

잘못된 알람 설정: - CPU > 80% -> 알람 - 결과: 배포할 때마다 알람 (잠깐 올라감) - 담당자: 알람 무시하기 시작 - 진짜 장애 시: "또 거짓 알람이겠지"

지속 시간을 함께 봐야 해:

좋은 알람 설정은?
# prometheus/alerts.yml groups: - name: game-server-alerts rules: # CPU 알람 - 5분 이상 지속될 때만 - alert: HighCPU expr: avg(rate(process_cpu_seconds_total[5m])) > 0.8 for: 5m # 5분 지속 labels: severity: warning annotations: summary: "High CPU usage on {{ $labels.instance }}" # 에러율 알람 - 즉시 - alert: HighErrorRate expr: | sum(rate(http_requests_total{status=~"5.."}[1m])) / sum(rate(http_requests_total[1m])) > 0.05 for: 1m labels: severity: critical annotations: summary: "Error rate > 5%" # 동접자 급감 알람 - alert: CCUDrop expr: | (game_ccu - game_ccu offset 5m) / game_ccu offset 5m < -0.3 for: 2m labels: severity: critical annotations: summary: "CCU dropped by 30% in 5 minutes"

5. 새벽에 알람 오면?

Slack 알람은 안 볼 수도 있잖아?

에스컬레이션 체계를 만들어:

알람 에스컬레이션: Level 1 (0분): Slack 알림 | v (5분 무응답) Level 2 (5분): 온콜 담당자 SMS + 전화 | v (10분 무응답) Level 3 (15분): 백업 담당자 전화 | v (15분 무응답) Level 4 (30분): 팀 리더 전화 | v (15분 무응답) Level 5 (45분): CTO 전화
PagerDuty 같은 거?
# alertmanager.yml global: resolve_timeout: 5m route: receiver: 'slack-notifications' routes: # Critical 알람은 PagerDuty로 - match: severity: critical receiver: 'pagerduty-critical' continue: true # Warning은 Slack만 - match: severity: warning receiver: 'slack-notifications' receivers: - name: 'slack-notifications' slack_configs: - channel: '#alerts' send_resolved: true title: '{{ .Status | toUpper }}' text: '{{ .CommonAnnotations.summary }}' - name: 'pagerduty-critical' pagerduty_configs: - service_key: $PAGERDUTY_KEY severity: critical description: '{{ .CommonAnnotations.summary }}'
온콜 로테이션은?
온콜 로테이션 예시: 주차별 담당: Week 1: 김개발 (1차), 이서버 (백업) Week 2: 이서버 (1차), 박운영 (백업) Week 3: 박운영 (1차), 최디비 (백업) Week 4: 최디비 (1차), 김개발 (백업) 온콜 규칙: - 주 1회 로테이션 - 1차 담당 10분 무응답 시 백업 호출 - 연휴 전 인수인계 필수 - 온콜 수당 별도 지급

7. 실제 장애 대응 사례

모니터링으로 장애 잡은 실제 사례는?
사례: 메모리 누수 조기 발견 Day 1 (월요일): - 메모리 사용률 그래프: 완만한 상승 시작 - 55% -> 58% (하루 3% 증가) - 알람 없음 (임계값 80%) Day 2 (화요일): - 58% -> 62% - 트렌드 알람 발생: "메모리 증가 추세 감지" - 담당자: 로그 확인, 메모리 프로파일링 시작 Day 3 (수요일): - 원인 발견: 캐시 만료 미처리 - 핫픽스 배포 - 메모리 정상화: 62% -> 45% 만약 모니터링 없었다면? - Day 6: 메모리 80% 초과, 성능 저하 - Day 7: OOM으로 서버 크래시 - 장애 시간: 수 시간

핵심 정리: 모니터링 & 알람

  • 4가지 골든 시그널 - Latency, Traffic, Errors, Saturation
  • 메트릭 수집 - Prometheus + 게임 전용 메트릭
  • 알람 설정 - 임계값 + 지속 시간 조합
  • 온콜 시스템 - 에스컬레이션 + 로테이션
  • 대시보드 - 핵심 지표 + 트렌드 시각화
  • 목표 - 장애 인지 30초 이내
