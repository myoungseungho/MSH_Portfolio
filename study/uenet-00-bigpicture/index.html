언리얼 네트워크는 어떻게 돌아갈까? — 한 장의 그림

서버가 진실, 클라는 복제본을 본다 + RPC. 이 두 개가 거의 전부야

이 섹션은 이렇게 진행돼

가장 추상적인 질문 '언리얼 네트워크는 어떻게 돌아갈까?'에서 시작해, 시스템을 하나씩 파고들어.

매 챕터마다: 질문으로 예측 → 비유로 그림 → 인터랙티브로 직접 확인 → 우리 서버(조선협객전)와 비교 → 실제 UE 소스 클래스까지.

목표: 초보자도 '언리얼 네트워크가 어떻게 도는지' 머릿속에 그림을 그리고, 동시에 실제로 어떻게 동작하는지 안다.

Part 1. 한마디로 뭐야?

온라인 게임에서, 내 화면 속 저 적은 '진짜' 거기 있는 걸까?

아니야. 네 화면 속 적은 '복제본'이야.

진짜 적의 위치·체력은 서버에 있고, 네 화면은 그걸 베껴 그린 그림이야.

그래서 핵심 명제 하나만 기억하면 돼: 서버가 진실, 클라는 복제본을 본다.

그럼 언리얼 네트워크를 한 문장으로?

서버가 권위(진실)를 갖고, 상태는 '복제(Replication)'로 클라에 자동 동기화, 행동은 'RPC'로 호출한다.

복제 + RPC — 이 두 개가 거의 전부야. 나머지 챕터는 전부 '이걸 어떻게 효율적으로·정확하게 하느냐'의 디테일이야.

비유로?

스포츠 중계로 보면 — 실제 경기(서버)는 경기장에서 딱 한 번 벌어져. 집집마다 TV(클라)는 그 경기를 '중계 화면'으로 봐.

시청자가 '리플레이 보여줘' 버튼을 누르면(RPC) 방송국(서버)이 받아서 모두에게 같은 리플레이를 송출해. 시청자가 경기 결과를 바꿀 순 없어 — 경기장이 진실이니까.

Part 2. 직접 봐 — 복제와 RPC

두 메커니즘을 눈으로 보자.

탭으로 ① 상태 복제 / ② RPC 를 바꿔봐.

① 서버 액터가 움직이면 상태가 클라들로 흘러가 복제본이 따라오는 것, ② 클라 이벤트가 서버로 올라갔다가 모든 클라로 뿌려지는 것을 비교해봐.

Part 3. 복제 vs RPC — 언제 뭘 써?

둘 다 서버-클라 통신인데 뭐가 달라?

복제(Replication)는 '상태'를 동기화해. 체력, 위치 같은 값이 바뀌면 엔진이 알아서 보내. '지금 상태가 이래'를 계속 맞추는 거야.

RPC는 '이벤트/행동'을 호출해. '점프해라', '폭발 이펙트 터뜨려라' 같은 일회성 신호야.

예를 들면?

캐릭터 체력 70 → 복제(값이라 계속 동기화).

'스킬 시전 이펙트' → Multicast RPC(한 번 터지고 끝, 값으로 들고 있을 필요 없음).

둘을 섞어 써. 대부분의 게임 상태는 복제, 순간 이벤트는 RPC.

Part 4. 우리 서버(조선협객전)랑 뭐가 같고 달라

한 줄로?

둘 다 '서버가 진실'은 같아. 차이는 — 언리얼은 '객체 단위 자동 복제'를 엔진이 내장해서 편하지만 세션형(한 판)에 맞춰져 있고, 우리는 패킷을 손으로 짜지만 영속 MMO(수천 명·DB·서버간)에 맞춰 만든 거야.

이 차이가 마지막 챕터의 결론으로 이어져: 'UE 데디서버가 왜 MMO를 그대로 못 하나.'

Part 5. 실제로는? (UE 소스 첫걸음)

코드에서 '서버냐 클라냐'는 어떻게 구분해?

UE는 NetMode로 구분해: Standalone(혼자), ListenServer(호스트가 서버+클라 겸함), DedicatedServer(서버 전용), Client.

같은 코드가 NetMode에 따라 다르게 동작해. 'HasAuthority()'가 true면 '나는 서버다'라는 뜻.

그럼 '이 액터를 복제해'는 어디서?

AActor의 bReplicates = true 한 줄. 그러면 서버가 그 액터를 만들면 클라들에도 자동으로 생겨.

실제 송수신은 UNetDriver / UNetConnection / UChannel이 담당하는데, 그건 다음 챕터들에서 하나씩 뜯어봐.

[UE 핵심 클래스 지도 — 이 섹션에서 차차 만남] ENetMode 서버/클라 구분 (HasAuthority) UWorld / AGameMode 월드, 게임 규칙(서버에만 존재) AActor::bReplicates 이 객체를 복제할까? └ UNetDriver 실제 네트워크 송수신 엔진 (Ch5) └ UNetConnection 클라 1명과의 연결 (Ch5) └ UChannel / Bunch 데이터 단위 (Ch6)

핵심 정리

  • 한 문장: 서버가 진실(권위), 클라는 복제본을 본다
  • 두 메커니즘: 상태는 복제(Replication, 값 동기화), 행동은 RPC(이벤트 호출)
  • 우리와 같은 점: 서버 권위. 다른 점: UE는 객체 자동 복제 내장(세션형), 우리는 패킷 수동(영속 MMO)
  • NetMode로 서버/클라 구분, HasAuthority() = 내가 서버인가, bReplicates = 이 액터를 복제할까
  • 다음부터: 소켓 → TCP/UDP → 우리 서버 한 바퀴 → NetDriver/Channel → 복제 → 이동예측 → 대규모/Iris

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 서버가 버그로 틀린 상태를 보내면 클라는 그냥 믿어야 해?
응, 클라는 서버를 믿을 수밖에 없어 — 그래서 서버 코드의 정확성이 생명이야. 클라가 서버를 의심해 멋대로 고치기 시작하면 그게 또 보안 구멍이 돼. 대신 서버는 테스트·로그로 버그를 잡고, 심하면 상태 롤백으로 되돌려.
Q. 체력처럼 복제로도 RPC로도 보낼 수 있으면 뭘 기준으로 골라?
'계속 유지되는 값'이면 복제(체력=값), '그 순간의 사건'이면 RPC(폭발 이펙트). 새로 접속한 사람도 알아야 하면 복제, 한 번 보고 끝이면 RPC야.
Q. 서버 1대가 죽으면 다 끊기는 거야?
세션형은 그 판이 종료돼. 그래서 인스턴스를 여러 개 띄워 죽으면 재배치하고, MMO는 채널·DB로 상태를 살려둬. 단일 권위의 대가야.
Q. P2P(서버 없이 클라끼리)는 왜 안 써?
호스트가 곧 권위라 치트·호스트 이탈에 약해. 경쟁·거래 게임은 중립 전용 서버에 권위를 둬. 대신 캐주얼은 서버비를 아끼려 P2P도 써.
