CPU 0%인데 프로그램이 안 움직여요

Deadlock 분석 — 서로 기다리며 영원히 멈춘 스레드들

Part 1. Deadlock이 뭐야?

프로그램이 멈췄는데 CPU 사용량이 0%야

무한 루프면 CPU 100%가 된다. 0%면 Deadlock(교착 상태)일 가능성이 높다.

Deadlock = 두 개 이상의 스레드가 서로 상대방이 가진 락을 기다리며 영원히 멈춘 상태

// 클래식 Deadlock 예시 // Thread A // Thread B LockA.Lock(); LockB.Lock(); // A를 획득 // B를 획득 LockB.Lock(); // B 대기... LockA.Lock(); // A 대기... // 영원히 안 옴 // 영원히 안 옴 // Thread A: "B 내놔!" → Thread B가 들고 있음 // Thread B: "A 내놔!" → Thread A가 들고 있음 // → 서로 기다리며 영원히 멈춤

Part 2. Deadlock 진단하기

1 Debug → Break All (Ctrl+Alt+Break)

멈춘 프로그램을 강제로 중단

2 Threads 창 열기 (Ctrl+Alt+H)

각 스레드가 어디서 멈춰있는지 확인

3 Location 컬럼 확인

여러 스레드가 EnterCriticalSection, WaitForSingleObject 등에서 멈춰있다면 의심

4 각 스레드 콜스택 확인

어떤 락을 기다리는지, 어떤 락을 이미 들고 있는지 추적

// Threads 창 예시 (Deadlock 상황) ID Location ────────────────────────────────────────── 1234 ntdll!NtWaitForSingleObject ← 락 대기 중 5678 ntdll!NtWaitForSingleObject ← 락 대기 중 9012 ntdll!NtWaitForSingleObject ← 락 대기 중 // 모든 스레드가 뭔가를 기다리고 있다 = Deadlock!

Part 3. Parallel Stacks로 한눈에 보기

스레드가 많은데 일일이 확인하기 힘들어

Parallel Stacks 창을 쓴다. Debug → Windows → Parallel Stacks (Ctrl+Shift+D, S)

모든 스레드의 콜스택을 그래프로 시각화해서 보여준다.

// Parallel Stacks 시각화 예시 ┌─ Thread 1234: WaitForCriticalSection(g_csA) │ main() ─────────┼─ Thread 5678: WaitForCriticalSection(g_csB) │ └─ Thread 9012: WaitForCriticalSection(g_csA) // 같은 락을 기다리는 스레드들이 그룹핑됨 // → Deadlock 관계를 한눈에 파악 가능

Part 4. 락 소유자 찾기

누가 락을 들고 있는지 어떻게 알아?

CRITICAL_SECTION 구조체를 직접 확인한다.

// Watch 창에서 CRITICAL_SECTION 내용 확인 g_csPlayer ├─ LockCount: -2 // 락 상태 (-1이면 unlock, -2 이하면 lock) ├─ RecursionCount: 1 // 재귀 횟수 ├─ OwningThread: 0x1234 // ← 락을 소유한 스레드 ID! └─ LockSemaphore: ... // OwningThread를 Threads 창에서 찾으면 → 락 소유자 확인
Deadlock 구조를 파악했으면?

순환 대기 관계를 그려본다:

// Deadlock 순환 구조 Thread 1234: - 소유: g_csPlayer - 대기: g_csWorld ←──────┐ │ Thread 5678: │ - 소유: g_csWorld │ - 대기: g_csPlayer ──────┘ // 1234 → g_csWorld 대기 → 5678이 소유 // 5678 → g_csPlayer 대기 → 1234가 소유 // → 순환! = Deadlock

Part 5. Deadlock 예방 패턴

패턴 설명 예시
락 순서 통일 항상 같은 순서로 락 획득 A→B→C 순서 고정
TryLock 사용 락 획득 실패 시 이미 가진 락도 해제 TryEnterCriticalSection
타임아웃 일정 시간 대기 후 포기 WaitForSingleObject + timeout
락 계층화 레벨 낮은 락만 추가 획득 가능 Level 1 → Level 2 만 허용
// 락 순서 통일 예시 // ❌ 나쁜 코드 (순서가 제각각) void ThreadA() { LockA(); LockB(); ... // A → B } void ThreadB() { LockB(); LockA(); ... // B → A ← 순서 다름! } // ✅ 좋은 코드 (순서 통일) void ThreadA() { LockA(); LockB(); ... // A → B } void ThreadB() { LockA(); LockB(); ... // A → B ← 순서 같음!

Part 6. Deadlock vs 다른 멈춤 현상

현상 CPU 사용량 원인
Deadlock 0% 서로 락 대기
무한 루프 100% 조건이 안 바뀜
정상 대기 0% I/O, Sleep 등
Livelock 높음 락 포기→재시도 반복

핵심 정리

  • Deadlock = 서로 상대방 락을 기다리며 영원히 멈춤
  • 증상: CPU 0%, 프로그램 무응답
  • 진단: Break All → Threads 창 → 락 대기 스레드 확인
  • Parallel Stacks: 모든 스레드 상태를 그래프로 시각화
  • 예방: 락 순서 통일, TryLock, 타임아웃
