동기 로딩 - 멈추고 기다려

Load() 호출하면 프레임이 멈추는 이유와 올바른 사용법

Part 1. 동기 로딩의 기본 개념

동기 로딩이 정확히 뭐야?

동기(Synchronous)란 "동시에 진행"이라는 의미가 아니라, "순서대로 진행"이라는 뜻입니다. 로딩 함수를 호출하면 작업이 완료될 때까지 호출자가 기다립니다.

가장 직관적이고 단순한 프로그래밍 모델입니다. 코드 한 줄이 끝나야 다음 줄이 실행되는 일반적인 흐름과 동일합니다.

// 동기 로딩의 가장 기본적인 형태 void GameStartup() { // 1. 이 줄에서 파일 읽기 완료까지 대기 Texture* playerTex = LoadTexture("player.dds"); // 2. 텍스처 로딩 끝나야 여기로 옴 Mesh* playerMesh = LoadMesh("player.fbx"); // 3. 메시 로딩 끝나야 여기로 옴 Sound* bgm = LoadSound("bgm.ogg"); // 4. 모든 로딩이 순차적으로 완료된 후 실행 StartGame(); }
왜 "동기"라고 부르는 거야?

호출자(Caller)와 피호출자(Callee)의 실행 흐름이 동기화되어 있기 때문입니다. 호출한 쪽은 작업이 끝날 때까지 함께 기다립니다.

Part 2. 동기 로딩의 내부 동작

LoadTexture 내부에서는 뭐가 일어나?

동기 로딩 함수 내부에서는 여러 단계의 작업이 순차적으로 진행됩니다. 각 단계가 완료되어야 다음 단계로 넘어갑니다.

// 동기 텍스처 로딩의 내부 구현 Texture* LoadTextureSync(const char* path) { // 1단계: 파일 열기 (블로킹) FILE* file = fopen(path, "rb"); if (!file) return nullptr; // 2단계: 파일 크기 확인 fseek(file, 0, SEEK_END); size_t fileSize = ftell(file); fseek(file, 0, SEEK_SET); // 3단계: 메모리 할당 uint8_t* rawData = new uint8_t[fileSize]; // 4단계: 파일 읽기 (블로킹 - 가장 오래 걸림) size_t bytesRead = fread(rawData, 1, fileSize, file); fclose(file); // 5단계: 헤더 파싱 DDSHeader* header = ParseDDSHeader(rawData); // 6단계: 압축 해제 (CPU 집약적) uint8_t* decompressed = nullptr; if (header->compressionType == ZSTD) { decompressed = DecompressZSTD( rawData + sizeof(DDSHeader), fileSize - sizeof(DDSHeader) ); } // 7단계: GPU 텍스처 생성 (GPU 블로킹) Texture* texture = CreateGPUTexture( header->width, header->height, header->format, decompressed ? decompressed : rawData + sizeof(DDSHeader) ); // 8단계: 정리 delete[] rawData; delete[] decompressed; return texture; // 모든 작업 완료 후 반환 }
각 단계별로 얼마나 걸려?

에셋의 종류와 크기, 저장 장치에 따라 다르지만, 일반적인 4K 텍스처(~20MB) 기준으로 각 단계의 소요 시간을 살펴보겠습니다.

Part 3. 블로킹의 실제 비용

게임 중 동기 로딩하면 무슨 일이 일어나?

게임 루프가 완전히 정지합니다. 이 동안 물리 시뮬레이션, AI 업데이트, 입력 처리, 렌더링 모두 멈춥니다.

플레이어는 "프레임 드랍" 또는 "렉"으로 인식하고, 심한 경우 게임이 "프리징"된 것으로 오해합니다.

문제 1: 델타 타임 폭발
  - deltaTime = 0.5초 (정상은 0.016초)
  - 물리: 캐릭터가 벽 뚫고 이동
  - AI: 0.5초치 행동을 한 프레임에 실행

문제 2: 입력 누적
  - 로딩 중 누른 키가 한꺼번에 처리됨
  - 점프 10번 누름 → 10단 점프?

문제 3: 애니메이션 점프
  - 걷기 5% → 갑자기 35% (중간 건너뜀)
// 동기 로딩 후 델타 타임 문제 예시 void GameLoop() { float lastTime = GetTime(); while (running) { float currentTime = GetTime(); float deltaTime = currentTime - lastTime; lastTime = currentTime; // 동기 로딩이 여기서 발생하면... if (NeedNewAsset()) { LoadAssetSync("big_asset.pak"); // 500ms 블로킹! } // deltaTime이 0.5초가 됨! UpdatePhysics(deltaTime); // 캐릭터가 순간이동? UpdateAI(deltaTime); // AI가 0.5초치 행동 한번에 Render(); } } // 델타 타임 클램핑으로 완화 (완전한 해결책 아님) void SafeGameLoop() { const float MAX_DELTA_TIME = 0.1f; // 최대 100ms로 제한 while (running) { float rawDelta = CalculateDeltaTime(); float deltaTime = min(rawDelta, MAX_DELTA_TIME); if (rawDelta > MAX_DELTA_TIME) { // 긴 프레임 감지 - 로그 남기기 LogWarning("Long frame: %.2fms (clamped to %.2fms)", rawDelta * 1000.0f, MAX_DELTA_TIME * 1000.0f); } Update(deltaTime); Render(); } }
멀티스레드 게임에서도 문제야?

동기 로딩이 메인 스레드(게임 스레드)에서 발생하면 여전히 문제입니다. 렌더 스레드, 오디오 스레드가 분리되어 있어도 게임 로직이 멈추면 화면 업데이트가 없습니다.

Part 4. 동기 vs 비동기 구현 비교

코드로 보면 얼마나 달라?

동기 로딩은 코드가 단순합니다. 호출하고 결과 받고 끝. 비동기는 콜백, 상태 관리, 스레드 안전성 등 고려할 게 많습니다.

//═══════════════════════════════════════════════════════════════ // 동기 로딩 - 가장 단순한 형태 //═══════════════════════════════════════════════════════════════ void SyncApproach() { // 한 줄로 끝. 결과가 바로 반환됨. Texture* tex = LoadTexture("player.dds"); // 바로 사용 가능 player->SetTexture(tex); } //═══════════════════════════════════════════════════════════════ // 비동기 로딩 - 콜백 방식 //═══════════════════════════════════════════════════════════════ void AsyncCallbackApproach() { // 요청만 하고 바로 반환 LoadTextureAsync("player.dds", [this](Texture* tex) { // 로딩 완료 시 콜백 호출 // 주의: 이 시점에 player가 유효한가? if (player) player->SetTexture(tex); } ); // 여기서 tex를 사용할 수 없음! } //═══════════════════════════════════════════════════════════════ // 비동기 로딩 - Future/Promise 방식 //═══════════════════════════════════════════════════════════════ void AsyncFutureApproach() { // Future 받아서 저장 Future<Texture*> textureFuture = LoadTextureAsync("player.dds"); // 매 프레임 체크 if (textureFuture.IsReady()) { Texture* tex = textureFuture.Get(); player->SetTexture(tex); } } //═══════════════════════════════════════════════════════════════ // 비동기 로딩 - 상태 머신 방식 //═══════════════════════════════════════════════════════════════ class PlayerLoader { enum State { Idle, LoadingTexture, LoadingMesh, Complete, Error }; State m_state = Idle; LoadHandle m_currentLoad; public: void StartLoading() { m_state = LoadingTexture; m_currentLoad = LoadTextureAsync("player.dds"); } void Update() { switch (m_state) { case LoadingTexture: if (m_currentLoad.IsComplete()) { if (m_currentLoad.HasError()) { m_state = Error; return; } m_texture = m_currentLoad.GetResult<Texture*>(); m_state = LoadingMesh; m_currentLoad = LoadMeshAsync("player.fbx"); } break; case LoadingMesh: if (m_currentLoad.IsComplete()) { // ... 유사한 패턴 m_state = Complete; } break; } } };
코드 복잡도 차이가 얼마나 나?

일반적으로 비동기 코드는 동기 코드보다 2~5배 더 복잡합니다. 에러 처리, 취소 로직, 스레드 안전성까지 고려하면 더 늘어납니다.

              동기               비동기
            ─────────         ─────────
기본 로딩      5줄              15줄
에러 처리     +3줄             +10줄
취소 로직      N/A             +15줄
진행률 표시    N/A             +10줄
의존성 체인   순차 호출         상태 머신
            ─────────         ─────────
총 LOC       ~10줄            ~50줄+


복잡도 요인
─────────────────────────────────────────────────────────────────
동기:
  • 제어 흐름이 선형적
  • 에러 발생 시점이 명확
  • 디버깅 쉬움 (스택 트레이스)
  • 리소스 정리가 간단

비동기:
  • 제어 흐름이 분산됨
  • 에러 전파 경로가 복잡
  • 디버깅 어려움 (콜백 지옥)
  • 리소스 수명 관리 복잡
  • 경쟁 조건 가능성
  • 취소 시 부분 상태 처리

Part 5. 동기 로딩이 적합한 경우

언제 동기 로딩을 써도 괜찮아?

동기 로딩도 올바른 상황에서는 최선의 선택입니다. 핵심은 "사용자가 대기를 기대하는 상황"인지 여부입니다.

//═══════════════════════════════════════════════════════════════ // 적합한 경우 1: 로딩 화면 //═══════════════════════════════════════════════════════════════ void LoadingScreen() { ShowLoadingUI(); // 사용자가 이미 대기 중 - 동기 로딩 OK const char* essentialAssets[] = { "player.dds", "player.fbx", "ui_atlas.dds", "terrain.pak", "shader_cache.bin" }; for (int i = 0; i < ARRAYSIZE(essentialAssets); i++) { UpdateProgress(i, ARRAYSIZE(essentialAssets)); LoadAssetSync(essentialAssets[i]); } HideLoadingUI(); StartGame(); } //═══════════════════════════════════════════════════════════════ // 적합한 경우 2: 게임 초기화 (메인 메뉴 전) //═══════════════════════════════════════════════════════════════ void EngineStartup() { // 스플래시 화면 표시 중 ShowSplashScreen(); // 엔진 필수 리소스 - 이것 없으면 아무것도 못함 g_DefaultShader = LoadShaderSync("default.hlsl"); g_ErrorTexture = LoadTextureSync("error.dds"); g_DefaultFont = LoadFontSync("default.ttf"); HideSplashScreen(); } //═══════════════════════════════════════════════════════════════ // 적합한 경우 3: 에디터/도구 //═══════════════════════════════════════════════════════════════ void EditorImportAsset(const char* path) { // 에디터에서는 UX보다 정확성이 중요 // 동기 로딩으로 즉시 결과 확인 가능 ShowBusyCursor(); Asset* imported = ImportAssetSync(path); if (imported) { AddToAssetDatabase(imported); RefreshAssetBrowser(); ShowMessage("Import successful"); } else { ShowError("Import failed"); } HideBusyCursor(); } //═══════════════════════════════════════════════════════════════ // 적합한 경우 4: 디버그/테스트 //═══════════════════════════════════════════════════════════════ void DebugLoadSingleAsset(const char* path) { // 테스트 코드에서는 단순함이 중요 // 비동기 테스트는 타이밍 문제로 불안정 Timer timer; timer.Start(); Asset* asset = LoadAssetSync(path); double loadTime = timer.ElapsedMs(); printf("Loaded %s in %.2fms\n", path, loadTime); ASSERT(asset != nullptr); ASSERT(asset->IsValid()); }
작은 파일도 동기 로딩해도 돼?

"작은 파일"의 기준이 중요합니다. 1프레임(16ms) 이내에 로딩이 끝나면 사용자가 인지하기 어렵습니다. 하지만 누적되면 문제가 됩니다.

파일 크기별 로딩 시간 가이드 (NVMe SSD 기준)
═══════════════════════════════════════════════════════════════════

파일 크기    예상 시간     프레임 손실   동기 로딩 적합도
─────────   ──────────   ───────────   ─────────────────
1 KB        < 0.1ms       0             ✅ 안전
10 KB       < 0.5ms       0             ✅ 안전
100 KB      ~ 2ms         0             ✅ 안전
1 MB        ~ 5ms         0             ⚠️ 주의 (누적 시 문제)
10 MB       ~ 20ms        1             ❌ 비동기 권장
100 MB      ~ 150ms       9             ❌ 반드시 비동기


"1프레임 규칙"
─────────────────────────────────────────────────────────────────
• 16ms 이하: 단일 호출은 OK
• 16ms 초과: 반드시 비동기

누적 효과 예시
─────────────────────────────────────────────────────────────────
100KB 파일 10개를 연속 동기 로딩:
  → 개별: 2ms × 10 = 20ms
  → 실제: 파일 시스템 오버헤드 추가 → 30~40ms
  → 결과: 2프레임 스터터

권장: 작은 파일도 배치(batch)로 묶어서 비동기 처리

Part 6. 동기 로딩의 위험한 패턴

절대 피해야 하는 동기 로딩 패턴이 있어?

게임플레이 중 트리거되는 동기 로딩은 최악의 패턴입니다. 특히 전투 중, 컷신 중, 이동 중에 발생하면 치명적입니다.

//═══════════════════════════════════════════════════════════════ // ❌ 위험 패턴 1: 전투 중 스킬 이펙트 로딩 //═══════════════════════════════════════════════════════════════ void UseSkill_BAD(int skillId) { Skill* skill = GetSkill(skillId); // ❌ 스킬 사용 시점에 이펙트 로딩? // 보스전 중 0.5초 멈추면 죽음! if (!skill->effectLoaded) { skill->effect = LoadEffectSync(skill->effectPath); skill->effectLoaded = true; } PlayEffect(skill->effect); } //═══════════════════════════════════════════════════════════════ // ❌ 위험 패턴 2: 시야에 들어올 때 로딩 //═══════════════════════════════════════════════════════════════ void OnBecameVisible_BAD(GameObject* obj) { // ❌ 카메라 이동할 때마다 스터터! if (!obj->meshLoaded) { obj->mesh = LoadMeshSync(obj->meshPath); obj->meshLoaded = true; } } //═══════════════════════════════════════════════════════════════ // ❌ 위험 패턴 3: 물리 콜백 안에서 로딩 //═══════════════════════════════════════════════════════════════ void OnCollisionEnter_BAD(Collision* col) { // ❌ 물리 엔진 콜백은 시간에 민감! // 여기서 블로킹하면 시뮬레이션 꼬임 if (col->other->IsBreakable()) { Sound* breakSound = LoadSoundSync("break.wav"); PlaySound(breakSound); } } //═══════════════════════════════════════════════════════════════ // ❌ 위험 패턴 4: 네트워크 콜백 안에서 로딩 //═══════════════════════════════════════════════════════════════ void OnPlayerJoined_BAD(NetworkPlayer* player) { // ❌ 네트워크 스레드 블로킹! // 다른 플레이어 패킷 처리 지연 Texture* customSkin = LoadTextureSync(player->skinUrl); player->SetSkin(customSkin); } //═══════════════════════════════════════════════════════════════ // ❌ 위험 패턴 5: Update()에서 조건부 로딩 //═══════════════════════════════════════════════════════════════ void Enemy::Update_BAD() { // ❌ 상태 전이마다 로딩? if (m_state == State::Angry && !m_angryEffectLoaded) { m_angryEffect = LoadEffectSync("angry_aura.vfx"); m_angryEffectLoaded = true; // 적 100마리가 동시에 화나면 100번 스터터! } }
이런 패턴들은 어떻게 고쳐?

기본 원칙: 예측 가능한 시점에 미리 로딩. 필요할 때가 아니라, 필요해지기 전에 비동기로 준비합니다.

//═══════════════════════════════════════════════════════════════ // ✅ 해결책 1: 스킬 획득 시점에 미리 로딩 //═══════════════════════════════════════════════════════════════ void LearnSkill(int skillId) { Skill* skill = GetSkillData(skillId); m_learnedSkills.push_back(skill); // ✅ 스킬 배우는 순간 이펙트 비동기 로딩 시작 PreloadEffectAsync(skill->effectPath); } void UseSkill_GOOD(int skillId) { Skill* skill = GetSkill(skillId); // ✅ 이미 로딩되어 있음 (스킬 배울 때 시작) Effect* effect = GetPreloadedEffect(skill->effectPath); if (effect) PlayEffect(effect); else PlayFallbackEffect(); // 아직 로딩 중이면 대체 이펙트 } //═══════════════════════════════════════════════════════════════ // ✅ 해결책 2: 거리 기반 스트리밍 //═══════════════════════════════════════════════════════════════ void StreamingSystem::Update() { Vector3 playerPos = player->GetPosition(); for (auto& obj : m_streamableObjects) { float distance = Distance(playerPos, obj.position); // ✅ 시야에 들어오기 전에 미리 로딩 if (distance < PRELOAD_DISTANCE && !obj.loadStarted) { LoadMeshAsync(obj.meshPath, [&obj](Mesh* m) { obj.mesh = m; }); obj.loadStarted = true; } // 시야 밖으로 나가면 언로드 if (distance > UNLOAD_DISTANCE && obj.mesh) { UnloadMesh(obj.mesh); obj.mesh = nullptr; obj.loadStarted = false; } } } //═══════════════════════════════════════════════════════════════ // ✅ 해결책 3: 이벤트 큐로 분리 //═══════════════════════════════════════════════════════════════ void OnCollisionEnter_GOOD(Collision* col) { if (col->other->IsBreakable()) { // ✅ 물리 콜백에서는 요청만 QueueSoundRequest("break.wav", col->point); } } // 메인 루프에서 사운드 요청 처리 void ProcessSoundQueue() { while (SoundRequest* req = PopSoundRequest()) { // ✅ 캐시에서 가져오거나 비동기 로딩 Sound* sound = GetCachedSound(req->path); if (sound) PlaySoundAt(sound, req->position); else LoadSoundAsync(req->path, req->position); } }

Part 7. 하이브리드 접근법

동기와 비동기를 섞어 쓸 수 있어?

네, 실제 게임에서는 하이브리드 접근이 일반적입니다. 상황에 따라 적절한 방식을 선택합니다.

//═══════════════════════════════════════════════════════════════ // 하이브리드 에셋 로더 //═══════════════════════════════════════════════════════════════ class HybridAssetLoader { public: enum LoadMode { Sync, // 즉시 로딩 (블로킹) Async, // 백그라운드 로딩 AsyncPriority, // 우선순위 백그라운드 로딩 SyncIfCached // 캐시 있으면 동기, 없으면 비동기 }; Asset* Load(const char* path, LoadMode mode) { // 캐시 확인 (모든 모드에서) Asset* cached = m_cache.Get(path); if (cached) return cached; switch (mode) { case Sync: return LoadSync(path); case Async: LoadAsync(path, Priority::Normal); return nullptr; // 나중에 가져가야 함 case AsyncPriority: LoadAsync(path, Priority::High); return nullptr; case SyncIfCached: // 이미 위에서 캐시 확인함 → 비동기로 LoadAsync(path, Priority::Normal); return nullptr; } return nullptr; } // 상황에 맞는 모드 자동 선택 Asset* LoadSmart(const char* path, LoadContext context) { LoadMode mode = DetermineMode(path, context); return Load(path, mode); } private: LoadMode DetermineMode(const char* path, LoadContext context) { // 로딩 화면 → 동기 OK if (context.isLoadingScreen) return Sync; // 게임플레이 중 → 무조건 비동기 if (context.isGameplay) return context.isUrgent ? AsyncPriority : Async; // 메뉴/로비 → 캐시 있으면 동기 if (context.isMenu) return SyncIfCached; // 기본값 return Async; } };
타임아웃 동기 로딩이라는 것도 있어?

네, "제한된 시간만 동기로 기다리고 넘기면 비동기로 전환"하는 패턴입니다. 하지만 이것도 일정 시간 블로킹이 발생하므로 신중하게 사용해야 합니다.

//═══════════════════════════════════════════════════════════════ // 타임아웃 기반 하이브리드 로딩 //═══════════════════════════════════════════════════════════════ class TimedLoader { public: // maxWaitMs 동안 동기 대기, 넘으면 비동기 전환 Asset* LoadWithTimeout(const char* path, float maxWaitMs) { // 먼저 비동기 요청 시작 LoadHandle handle = StartAsyncLoad(path); // 지정된 시간만큼 대기 Timer timer; timer.Start(); while (!handle.IsComplete()) { if (timer.ElapsedMs() >= maxWaitMs) { // 타임아웃! 비동기로 전환 StoreForLaterRetrieval(path, handle); return nullptr; // 아직 없음 } // 짧게 sleep (CPU 양보) Sleep(1); } // 타임아웃 전에 완료됨! return handle.GetResult(); } }; // 사용 예 void TryLoadImmediate() { TimedLoader loader; // 5ms까지는 기다려봄 (1프레임의 1/3) Asset* asset = loader.LoadWithTimeout("item.dds", 5.0f); if (asset) { // 5ms 안에 로딩됨 - 바로 사용 UseAsset(asset); } else { // 5ms 초과 - 대체 에셋 사용 UseAsset(g_PlaceholderAsset); // 백그라운드에서 계속 로딩 중 } }

Part 9. 디버깅과 프로파일링

동기 로딩 문제를 어떻게 찾아?

동기 로딩으로 인한 스터터는 프레임 타임 스파이크로 나타납니다. 프로파일러에서 긴 프레임을 찾아 콜스택을 확인하면 됩니다.

//═══════════════════════════════════════════════════════════════ // 동기 로딩 감지 래퍼 //═══════════════════════════════════════════════════════════════ class SyncLoadDetector { public: // 모든 동기 로딩을 감싸는 래퍼 template<typename T> T WrapSyncLoad(const char* path, T (*loadFunc)(const char*)) { // 게임플레이 중 동기 로딩 경고 if (g_GameState == GameState::Playing) { LogWarning("SYNC LOAD DURING GAMEPLAY: %s", path); LogCallStack(); // 호출 스택 기록 #if DEBUG_BUILD // 디버그 빌드에서는 브레이크포인트 __debugbreak(); #endif } // 시간 측정 Timer timer; timer.Start(); T result = loadFunc(path); double elapsed = timer.ElapsedMs(); // 긴 로딩 기록 if (elapsed > 16.0) // 1프레임 초과 { LogPerformance("LONG SYNC LOAD: %s took %.2fms", path, elapsed); m_longLoads.push_back({path, elapsed, GetCurrentFrame()}); } // 통계 업데이트 m_totalSyncLoads++; m_totalSyncTime += elapsed; return result; } // 세션 종료 시 리포트 void GenerateReport() { printf("=== Sync Load Report ===\n"); printf("Total sync loads: %d\n", m_totalSyncLoads); printf("Total sync time: %.2f ms\n", m_totalSyncTime); printf("Average per load: %.2f ms\n", m_totalSyncTime / m_totalSyncLoads); printf("\n--- Long Loads (>16ms) ---\n"); for (const auto& load : m_longLoads) { printf("Frame %d: %s (%.2fms)\n", load.frame, load.path, load.time); } } private: int m_totalSyncLoads = 0; double m_totalSyncTime = 0; std::vector<LoadRecord> m_longLoads; }; // 매크로로 모든 동기 로딩 래핑 #define LOAD_TEXTURE_SYNC(path) \ g_SyncDetector.WrapSyncLoad(path, LoadTextureImpl) #define LOAD_MESH_SYNC(path) \ g_SyncDetector.WrapSyncLoad(path, LoadMeshImpl)
프로파일러에서 뭘 봐야 해?

//═══════════════════════════════════════════════════════════════ // 인게임 프레임 타임 모니터 //═══════════════════════════════════════════════════════════════ class FrameTimeMonitor { public: void BeginFrame() { m_frameTimer.Start(); } void EndFrame() { double frameTime = m_frameTimer.ElapsedMs(); // 히스토리 기록 m_frameHistory[m_historyIndex] = frameTime; m_historyIndex = (m_historyIndex + 1) % HISTORY_SIZE; // 스파이크 감지 if (frameTime > m_spikeThreshold) { FrameSpike spike; spike.frameNumber = m_frameCount; spike.time = frameTime; spike.timestamp = GetTimestamp(); // 마지막 로딩 작업 기록 spike.lastLoadOp = g_LastLoadOperation; m_spikes.push_back(spike); if (m_debugOverlay) { ShowSpikeWarning(frameTime, g_LastLoadOperation); } } m_frameCount++; } // 화면에 프레임 그래프 표시 void DrawDebugOverlay() { // 최근 120프레임의 타임 그래프 for (int i = 0; i < HISTORY_SIZE; i++) { int idx = (m_historyIndex + i) % HISTORY_SIZE; float height = m_frameHistory[idx] / 50.0f; // 50ms를 최대로 Color color = m_frameHistory[idx] > 16.67f ? RED : GREEN; DrawBar(i * 4, 100, 3, height * 100, color); } // 16ms 라인 표시 DrawLine(0, 66, HISTORY_SIZE * 4, 66, YELLOW); } private: static const int HISTORY_SIZE = 120; double m_frameHistory[HISTORY_SIZE] = {}; int m_historyIndex = 0; int m_frameCount = 0; double m_spikeThreshold = 33.33; // 30FPS 이하면 스파이크 bool m_debugOverlay = true; };

Part 10. 실전 가이드라인

동기 로딩에 대한 실전 규칙을 정리해줘.

동기 로딩 사용에 대한 명확한 규칙을 팀 내에서 공유하면 실수를 줄일 수 있습니다.

동기 로딩 사용 규칙 (팀 가이드라인)
═══════════════════════════════════════════════════════════════════

✅ 허용되는 경우
─────────────────────────────────────────────────────────────────
1. 로딩 화면 (Loading Screen)
   - 진행률 표시 권장
   - 사용자가 대기를 기대하는 상황

2. 게임 초기화 (Startup)
   - 스플래시 화면 중
   - 엔진 필수 리소스만

3. 에디터/도구 (Editor/Tools)
   - 개발자 도구는 UX 덜 중요
   - 단, 대용량은 비동기 권장

4. 단위 테스트 (Unit Tests)
   - 테스트 안정성 우선
   - 타이밍 의존성 제거


❌ 금지되는 경우
─────────────────────────────────────────────────────────────────
1. 게임플레이 중 (During Gameplay)
   - 전투, 이동, 탐험 중 절대 금지
   - 예외 없음!

2. 이벤트 콜백 내부
   - OnCollision, OnTrigger
   - OnNetworkMessage
   - OnInputEvent

3. Update()/Tick() 함수
   - 매 프레임 호출되는 함수 내부

4. 조건부 로딩
   - if (첫 사용) LoadSync() 패턴 금지


⚠️ 주의가 필요한 경우
─────────────────────────────────────────────────────────────────
1. 메뉴/로비
   - 캐시 히트 시만 동기 허용
   - 미스 시 비동기 전환

2. 컷신 시작
   - 첫 프레임 전에만 허용
   - 재생 중 금지

3. 씬 전환
   - 페이드 아웃 중에만
   - 완전 블랙 화면에서
//═══════════════════════════════════════════════════════════════ // 동기 로딩 정책 검사기 (CI/코드 리뷰용) //═══════════════════════════════════════════════════════════════ class SyncLoadPolicy { public: // 동기 로딩 허용 여부 검사 static bool IsAllowed(LoadContext context) { // 게임플레이 중 = 절대 금지 if (context.gameState == GameState::Playing) return false; // 물리/네트워크 콜백 = 절대 금지 if (context.isPhysicsCallback || context.isNetworkCallback) return false; // Update 함수 = 절대 금지 if (context.isUpdateFunction) return false; // 로딩 화면 = 허용 if (context.gameState == GameState::Loading) return true; // 초기화 = 허용 if (context.gameState == GameState::Initializing) return true; // 에디터 = 허용 if (context.isEditor) return true; // 기본: 불허 return false; } // 동기 로딩 호출 시 강제 검사 static void Enforce(LoadContext context, const char* path) { if (!IsAllowed(context)) { // 위반 로그 LogError("SYNC LOAD POLICY VIOLATION: %s", path); LogError("Context: %s", context.ToString()); LogCallStack(); #if DEBUG_BUILD // 디버그 빌드: 중단 assert(false && "Sync load policy violation!"); #else // 릴리즈 빌드: 비동기로 자동 전환 LogWarning("Falling back to async load"); g_ForcedAsyncCount++; #endif } } }; // 매크로로 모든 동기 로딩에 정책 검사 추가 #define LOAD_SYNC(Type, path) \ ([&]() -> Type* { \ LoadContext ctx = GetCurrentLoadContext(); \ SyncLoadPolicy::Enforce(ctx, path); \ return Load##Type##Impl(path); \ })()
마지막으로 정리해줘.

동기 로딩은 도구입니다. 적절히 사용하면 코드가 단순해지고, 잘못 사용하면 게임을 망칩니다. 핵심은 언제 사용하면 안 되는지를 아는 것입니다.

동기 로딩 최종 체크리스트
═══════════════════════════════════════════════════════════════════

동기 로딩 코드를 작성하기 전에:

□ 지금 게임플레이 중인가?
  → YES: 절대 금지. 비동기 사용.

□ 이 코드가 Update()나 콜백 안에 있는가?
  → YES: 절대 금지. 다른 시점으로 이동.

□ 로딩 화면이나 초기화 단계인가?
  → YES: 동기 로딩 OK.

□ 파일 크기가 플랫폼 임계값 이하인가?
  → YES: 동기 고려 가능. (그래도 비동기 권장)
  → NO: 반드시 비동기.

□ 에디터/도구 코드인가?
  → YES: 동기 로딩 OK. (대용량은 비동기 권장)


기억할 것
─────────────────────────────────────────────────────────────────
• 동기 로딩 = 단순함의 대가로 반응성 희생
• "1프레임(16ms) 규칙" - 이 이상 걸리면 비동기
• 의심될 때는 비동기를 선택
• 프로파일링으로 실제 영향 확인
• 팀 가이드라인 만들고 공유하기

핵심 정리

  • 동기 로딩은 호출자가 완료까지 기다리는 가장 단순한 방식
  • 게임 루프가 멈추면 물리, AI, 렌더링 모두 정지
  • 로딩 화면, 초기화에서는 적합 - 게임플레이 중에는 금지
  • 파일 I/O가 가장 큰 병목 - 플랫폼마다 속도 차이 큼
  • 하이브리드 접근: 상황에 맞게 동기/비동기 선택
  • 프로파일러로 프레임 스파이크 찾아 원인 분석
  • 팀 내 명확한 규칙 공유가 중요
