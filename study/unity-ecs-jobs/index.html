1. 발표 배경과 동기

프로젝트 배경은 무엇인가?

발표자는 넥슨 모다스튜디오에서 도미네이션즈 중국버전 개발 후, 신규 모바일 시뮬레이션 게임을 개발 중이었다.

프로젝트 특성:
  • 1600 x 1600 타일 기반의 광활한 맵
  • 멀티플레이어 게임 (유저 증가에 따라 유닛 수 증가)
  • 기병 유닛 등 다수의 오브젝트가 동시 존재
기존 방식으로 개발했을 때 어떤 문제가 발생했는가?

도미네이션즈처럼 기존 유니티 방식으로 개발하니 악순환이 반복되었다:

CPU 쓰로틀링 → 프레임 저하 → 최적화 시도 → 일시적 개선 → 다시 저하

구글 검색, PPT 자료, 책까지 참고했지만 근본적인 한계를 느꼈다.

근본적인 한계란 무엇이었나?

두 가지 관점에서 고민:

  1. 하드웨어 활용: 모바일 기기 성능이 좋아지는데, 우리가 그 성능을 최대한 사용하고 있는가?
  2. 설계 패러다임: OOP 외에 다른 방법은 없는가?

2. Data Oriented Design (DOD)

DOD(데이터 기반 디자인)를 어떻�게 알게 되었나?

인디 게임 개발자 Tol의 블로그 글을 발견했다. 게임 개발 관점에서 DOD를 설명한 글이었다.

핵심 주장 2가지:
  1. "게임이 하는 일은 어떤 데이터를 다른 데이터로 변환하는 것이 전부다"
  2. "게임 속도 저하의 원인은 메모리에 랜덤하게 접근하는 패턴과 캐시 미스(적중률 저하)다"
DOD를 적용하면 어떤 장점이 있나?
  • 병렬화 용이: 멀티코어 CPU 활용 가능
  • 캐시 적중률 향상: 메모리 접근 패턴 최적화
  • 보너스: 모듈화, 테스트 용이성
유니티에서 DOD를 어떻게 적용할 수 있나?

유니티 CTO이자 공동 창립자인 Joachim Ante의 GDC 발표를 발견했다.

주제: "ECS를 통한 성능 향상과 데이터 기반 디자인을 유니티에 적용"

비슷한 시기에 ECS 데모 프로젝트도 공개되어 검토 후 적용을 결정했다.

3. 기존 유니티 개발 방식의 한계

기존 방식(클래식)의 가장 큰 문제점은?

비효율적이고 비대한 GameObject가 문제다.

DOD 관점에서 보면:

  • 데이터가 메모리 공간 여기저기에 흩어져 있음
  • 랜덤 메모리 접근으로 인한 캐시 적중률 저하
캐시(Cache)가 왜 중요한가?

CPU vs 메모리 발전 속도 격차가 핵심이다.

CPU 발전 ████████████████████████████ (빠름) 메모리 발전 ████████ (느림)

느린 메모리에서 데이터를 가져오는 시간 = 병목(Bottleneck)

  • 메모리: 크고 느림
  • 캐시: 작고 매우 빠름

따라서 캐시 접근 확률을 높이고 메모리 접근을 줄이는 것이 핵심이다.

캐시 적중률을 높이려면 어떻게 해야 하나?

캐시는 데이터 지역성(Locality) 원리로 작동한다:

지역성 종류 설명
시간 지역성 최근 접근한 데이터에 다시 접근할 가능성이 높음
공간 지역성 접근한 데이터 주변 공간에 다시 접근할 가능성이 높음
결론: 메모리상에 데이터를 촘촘하게(연속적으로) 배치해야 한다.
이것이 바로 Unity ECS가 추구하는 방향이다.

4. ECS (Entity-Component-System) 구조

Component란 무엇인가?

데이터만 보관하는 역할. 로직이 전혀 없다.

제약사항:
  • 클래스가 아닌 구조체(struct)로만 구현
  • 멤버는 참조 형식이 아닌 값 타입(value type)만 가능

장점: 가비지 컬렉터(GC)에 의해 관리되지 않음 → "가비지 딸꾹질" 없음

public struct TroopMove : IComponentData
{
    public float speed;
    public float3 targetPosition;
}
Shared Component는 무엇인가?

여러 Entity가 공유하는 컴포넌트. 인스턴스가 1개만 생성된다.

예: RenderMesh - Material, Mesh 같은 렌더링 데이터 공유

Entity A ─┐ Entity B ─┼─→ [ Shared Component (1개 인스턴스) ] Entity C ─┘
System이란 무엇인가?

로직 담당. "어떤 데이터를 다른 데이터로 변환"하는 처리를 수행.

  • Entity가 뭔지 모름
  • Entity 타입에 상관없이, 어떤 Component를 가지고 있는지에 따라 작동
  • Component 조합으로 쿼리를 던져서 처리 대상 선택
// Translation과 TroopMove 컴포넌트를 가진 Entity에 대해 처리
Entities.ForEach((ref Translation pos, in TroopMove move) => {
    // 이동 로직
}).Schedule();
Entity란 무엇인가?

극단적으로 말하면:

클래식 ECS
GameObject = 거의 모든 것 (Everything) Entity = 거의 아무것도 아님 (Nothing)

Entity는 내부적으로 그냥 int 타입 하나일 뿐이다.

Component들을 논리적으로 묶어주는 식별자 역할만 한다.

5. Archetype과 Chunk - 데이터 저장 구조

Archetype이란 무엇인가?

ECS 데이터 저장 방식의 핵심 개념. Component 배열을 모아놓은 형태.

Archetype (Position, Rotation, Renderer, Rigidbody를 가진 Entity들) ┌─────────────────────────────────────────────────────┐ │ Position[] │ [pos0] [pos1] [pos2] [pos3] ... │ │ Rotation[] │ [rot0] [rot1] [rot2] [rot3] ... │ │ Renderer[] │ [ren0] [ren1] [ren2] [ren3] ... │ │ Rigidbody[] │ [rig0] [rig1] [rig2] [rig3] ... │ └─────────────────────────────────────────────────────┘ ↑ ↑ ↑ ↑ ↑ Entity = E0 E1 E2 E3

세로 방향 같은 인덱스가 하나의 Entity를 구성한다.

Archetype의 장점은?
  • 배열 형태 저장 → 인접한 메모리 공간에 촘촘하게 저장
  • 효과적인 반복 처리 (Iteration)
  • 메모리 공간 최적화
  • 캐시 적중률 향상 (공간 지역성 활용)
Entity 구조를 변경하면 어떤 일이 발생하나?
주의: Component를 추가/삭제하면 메모리 이동이 발생한다.

예: Entity에서 Rigidbody를 제거하면 → 다른 Archetype으로 이동

이는 성능 저하를 유발하므로, 설계 시 구조 변경을 최소화해야 한다.

Chunk란 무엇인가?

Archetype을 쪼개면 Chunk로 구성되어 있다.

  • 크기: 고정 16KB
  • Chunk 내부는 배열 → 캐시 적중률 높음
  • Chunk 간은 연결 리스트 → 삽입/삭제 비용 최소화
Archetype ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Chunk 1 │ ←→ │ Chunk 2 │ ←→ │ Chunk 3 │ (연결 리스트) │ 16KB │ │ 16KB │ │ 16KB │ └─────────┘ └─────────┘ └─────────┘ (배열) (배열) (배열)
Chunk 설계 시 주의할 점은?

하나의 Chunk(16KB)에 최대한 많은 Entity를 넣는 것이 메모리 효율적.

Component 수가 많아지면:
  • 가로(Component)가 길어짐
  • Chunk당 들어갈 수 있는 Entity 수 감소
설계 원칙: "이 Entity에 이 Component가 정말 필요한가?" 항상 고민

6. Job System - 병렬 처리

Job System이란?

멀티스레딩을 쉽게 해주는 시스템.

  • Deadlock, Race Condition 등을 컴파일 타임에 방지
  • Job = Thread (정확히 같진 않지만 개념적으로 유사)
ECS와 Job System의 관계는?
  • Job System: 이미 릴리즈됨, ECS 없이도 사용 가능
  • ECS: 아직 프리뷰 단계 (발표 당시)

JobComponentSystem을 사용하면 쉽게 병렬 프로그래밍 가능:

public class TroopMoveSystem : JobComponentSystem
{
    struct TroopMoveJob : IJobForEach
    {
        public void Execute(ref Translation pos, ref TroopMove move)
        {
            pos.Value.x += move.speed * deltaTime;
        }
    }
}
DOTS란 무엇인가?

Data-Oriented Technology Stack - 유니티의 마케팅 용어.

DOTS = ECS + Job System + Burst Compiler
  • ECS: Entity-Component-System 아키텍처
  • Job System: 멀티스레딩
  • Burst Compiler: 네이티브 코드 최적화 컴파일러

7. Entity Debugger - 디버깅 도구

Entity Debugger는 왜 필요한가?

ECS로 개발하면 기존 에디터에서 Entity를 볼 수 없다.

GameObject처럼 Hierarchy에서 눈으로 확인할 수 없기 때문에, 유일하게 Entity Debugger를 통해서만 실행 중인 Entity를 확인할 수 있다.

Entity Debugger에서 무엇을 확인할 수 있나?

화면이 3개 부분으로 구성:

  1. 왼쪽: System 리스트 (체크박스로 On/Off 가능, 프레임당 수행시간 표시)
  2. 가운데: 선택한 System의 쿼리 조건 (어떤 Component 조합을 처리하는지)
  3. 오른쪽: Chunk Info - Entity가 Chunk에 어떻게 보관되어 있는지 히스토그램으로 표시
Chunk Info 해석:
히스토그램 막대가 오른쪽에 가까울수록 메모리 배치가 잘 되어 있음 (Chunk가 꽉 차있음)

8. 프로젝트 적용 사례

타일맵에 ECS를 어떻게 적용했나?

모든 것을 새로 만들 필요 없음! 기존 것을 대부분 재활용 가능.

변경한 부분:
  • SpriteRenderer → Mesh Renderer (ECS 미지원)
  • Hybrid 방식으로 풀링 적용

자동 변환 도구:

GameObjectConversionUtility.ConvertGameObjectHierarchy(
    gameObject,           // 기존 GameObject
    conversionSettings    // 설정
);
// 결과: ECS Entity 반환
타일맵 적용 결과는?
타일 수 결과
15,000개 무난하게 60fps 이상
55,000개 프레임 저하 있지만 클래식 방식보다 훨씬 양호
62,000개 5.38ms로 렌더링 처리 (Entity Debugger 확인)
의미: 렌더링 부분만 ECS 적용해도 큰 속도 향상!
유닛 생성/이동에 ECS를 어떻게 적용했나?

Hybrid 방식 사용 - 클래식과 ECS 혼합 가능!

작성한 코드:

  1. TroopMove - Component (데이터)
  2. TroopMoveSystem - System (로직)
  3. TroopMoveProxy - MonoBehaviour 헬퍼 (에디터 연동)
  4. UnitSpawnMonoBehaviour - 기존 클래식 스폰 로직
// TroopMove Component
public struct TroopMove : IComponentData
{
    public float speed;
}

// Proxy - 에디터에서 값 설정 가능
public class TroopMoveProxy : MonoBehaviour, IConvertGameObjectToEntity
{
    [SerializeField] float speed;

    public void Convert(Entity entity, EntityManager manager, ...)
    {
        manager.AddComponentData(entity, new TroopMove { speed = speed });
    }
}
유닛 이동 적용 결과는?
방식 10,000 유닛
클래식 (MonoBehaviour.Update) 약 8fps
ECS + Job System 60fps 이상 유지

Profiler로 확인: Main Thread 외에 Worker Thread들이 활성화되어 멀티코어 활용

유닛 수를 늘려도 프레임 저하가 크지 않음 - 일괄 처리 + 높은 캐시 적중률 효과

9. ECS 적용 팁 및 주의사항

ECS가 효과적인 경우는?
조건:
  1. 같은 타입의 오브젝트가
  2. 엄청 많이 (수만 단위)
  3. 매 프레임 업데이트되는 경우

기계적 판단: MonoBehaviour.Update()가 있다면 → ECS System으로 대체 검토

ECS가 효과적이지 않은 경우는?
  • 오브젝트 수가 적은 경우
  • 서로 다른 타입이 많은 경우
  • 구조 변경(Component 추가/삭제)이 빈번한 경우
ECS의 단점은?
  • 디버깅: Entity Debugger만 가능, 기존처럼 에디터에서 눈으로 확인 어려움
  • 학습 곡선: DOD 패러다임이 익숙하지 않으면 어려움
  • 프리뷰 단계: 잦은 업데이트, API 변경 (Deprecated 다수)
팁: Unity Forum의 ECS 섹션을 즐겨찾기하고 수시로 확인하세요!

핵심 정리

DOD 캐시 적중률 메모리 연속 배치

  1. 문제: 기존 GameObject 방식은 메모리 랜덤 접근 → 캐시 미스 → 성능 저하
  2. 해결: ECS로 데이터를 촘촘하게 배치 → 캐시 적중률 향상
  3. 병렬화: Job System으로 멀티코어 활용 → 하드웨어 성능 최대 활용
  4. 적용 기준: 같은 타입 + 대량 + 매 프레임 업데이트 = ECS 적합
  5. Hybrid 가능: 기존 프리팹/코드 재활용, 점진적 적용

발표자 소감: "설계 단계부터 생각하게 되고, 하드웨어 단계에서도 고민하게 됐다. 더 이상 단순히 응용 프로그래머가 아닌 엔지니어가 된 느낌."
