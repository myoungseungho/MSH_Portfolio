왜 유니티가 느려? ECS와 Job System

데이터 기반 설계로 성능 10배 향상시키기 - NDC 발표 기반

Part 1. 왜 유니티가 이렇게 느려?

모바일 게임 만들고 있는데, 유닛이 많아지면 프레임이 뚝뚝 떨어져. 최적화 해봤는데 한계가 있어...

넥슨 모다스튜디오에서 1600x1600 타일 기반 시뮬레이션 게임 만들 때 같은 문제 겪었어.

기존 방식으로 개발하니까 이런 악순환이 반복됐대:

CPU 쓰로틀링 → 프레임 저하 → 최적화 시도 → 일시적 개선 → 다시 저하 → 구글 검색, PPT 자료, 책까지 참고했지만 근본적인 한계!
근본적인 한계가 뭔데?

두 가지 질문을 던져봤대:

1. 요즘 모바일 성능 좋아졌는데, 그 성능을 제대로 쓰고 있나?

2. OOP 말고 다른 설계 방법은 없나?

Part 2. DOD가 뭐야?

DOD(Data Oriented Design)가 뭐야? 처음 들어보는데...

인디 게임 개발자 Tol의 블로그에서 발견한 개념인데, 핵심 주장이 2가지야:

DOD 핵심 주장
  • "게임이 하는 일은 어떤 데이터를 다른 데이터로 변환하는 것이 전부다"
  • "게임 속도 저하의 원인은 메모리에 랜덤하게 접근하는 패턴과 캐시 미스다"
캐시 미스? 그게 성능이랑 무슨 상관이야?

CPU와 메모리의 발전 속도 차이가 핵심이야.

CPU 발전 속도: ████████████████████████████ (엄청 빠름) 메모리 발전 속도: ████████ (상대적으로 느림) → 느린 메모리에서 데이터 가져오는 시간 = 병목(Bottleneck)!
창고 비유

CPU = 엄청 빠른 계산원
메모리 = 멀리 있는 큰 창고
캐시 = 계산대 바로 옆 작은 선반

창고까지 왔다갔다 하면 느림 → 선반에 미리 올려두면 빠름!

Part 3. 캐시 적중률을 높이려면?

그럼 캐시를 잘 쓰려면 어떻게 해야 해?

캐시는 데이터 지역성(Locality) 원리로 작동해.

지역성 종류 설명
시간 지역성 최근 접근한 데이터에 다시 접근할 가능성이 높음
공간 지역성 접근한 데이터 주변 공간에 다시 접근할 가능성이 높음
기존 유니티 GameObject는 왜 캐시를 못 써?

데이터가 메모리 여기저기 흩어져 있어서 그래.

기존 GameObject 방식: [GameObject A] ... [GameObject B] ... [GameObject C] ↑ 여기 ↑ 저기 ↑ 또 저기 → 랜덤하게 접근 → 캐시 미스 → 느림!
해결책

메모리상에 데이터를 촘촘하게(연속적으로) 배치해야 해.
이게 바로 Unity ECS가 추구하는 방향이야!

Part 4. ECS가 뭐야?

ECS가 정확히 뭐야? Entity, Component, System?

각각 역할이 다른 3가지를 분리한 구조야.

구성요소 역할 특징
Entity 식별자 그냥 int 하나일 뿐! (거의 Nothing)
Component 데이터만 보관 로직 없음, 구조체(struct)만
System 로직 담당 데이터 → 다른 데이터 변환
Component가 구조체(struct)여야 하는 이유가 뭐야?

가비지 컬렉터(GC)에 의해 관리되지 않아!

"가비지 딸꾹질" 현상이 없어지는 거야.

// Component 예시 - 데이터만! public struct TroopMove : IComponentData { public float speed; public float3 targetPosition; } // System 예시 - 로직만! Entities.ForEach((ref Translation pos, in TroopMove move) => { // 이동 로직 }).Schedule();
기존 GameObject와 Entity 차이가 뭐야?

극단적으로 말하면:

클래식 ECS
GameObject = 거의 모든 것 (Everything) Entity = 거의 아무것도 아님 (Nothing)
주민등록번호 비유

Entity = 주민등록번호 (그냥 식별용 숫자)
Component들 = 실제 개인 정보 (이름, 주소, 전화번호...)

번호 자체는 의미 없고, 그걸로 정보를 찾는 거야!

Part 5. Archetype이랑 Chunk가 뭐야?

ECS가 데이터를 어떻게 저장하길래 빨라?

Archetype이라는 구조로 저장해.

같은 Component 조합을 가진 Entity들을 배열로 모아놓는 거야.

Archetype (Position, Rotation, Renderer를 가진 Entity들) ┌─────────────────────────────────────────────────────┐ │ Position[] │ [pos0] [pos1] [pos2] [pos3] ... │ │ Rotation[] │ [rot0] [rot1] [rot2] [rot3] ... │ │ Renderer[] │ [ren0] [ren1] [ren2] [ren3] ... │ └─────────────────────────────────────────────────────┘ ↑ ↑ ↑ ↑ ↑ Entity = E0 E1 E2 E3 → 세로 방향 같은 인덱스 = 하나의 Entity!
이게 왜 빠른 거야?

배열이니까 메모리에 촘촘하게 저장돼!

Position 처리할 때 pos0, pos1, pos2... 쭉 읽으면 캐시 적중률 최고!

Chunk는 또 뭐야?

Archetype을 16KB 단위로 쪼갠 거야.

Archetype ┌─────────┐ ┌─────────┐ ┌─────────┐ │ Chunk 1 │ ←→ │ Chunk 2 │ ←→ │ Chunk 3 │ (연결 리스트) │ 16KB │ │ 16KB │ │ 16KB │ └─────────┘ └─────────┘ └─────────┘ (배열) (배열) (배열) → Chunk 내부는 배열 (빠름) → Chunk 간은 연결 리스트 (삽입/삭제 비용 최소)
주의사항

Component를 추가/삭제하면 다른 Archetype으로 이동해야 함!
→ 메모리 이동 발생 → 성능 저하

설계 원칙: "이 Entity에 이 Component가 정말 필요한가?" 항상 고민!

Part 6. Job System이 뭐야?

멀티스레딩 하면 Deadlock이나 Race Condition 걱정되는데...

Job System이 컴파일 타임에 그런 문제들을 방지해줘!

Job System 특징
  • Deadlock 방지: 컴파일 시점에 감지
  • Race Condition 방지: 데이터 접근 규칙 강제
  • 쉬운 병렬화: Schedule() 한 번이면 끝
public class TroopMoveSystem : JobComponentSystem { struct TroopMoveJob : IJobForEach { public void Execute(ref Translation pos, ref TroopMove move) { pos.Value.x += move.speed * deltaTime; } } } // .Schedule() 호출하면 자동으로 멀티스레딩!
DOTS는 또 뭐야?

유니티의 마케팅 용어야. 3가지를 합친 거:

DOTS = Data-Oriented Technology Stack

ECS + Job System + Burst Compiler

Burst Compiler = 네이티브 코드로 최적화해주는 컴파일러

Part 7. 실제로 얼마나 빨라져?

실제 프로젝트에 적용하면 얼마나 차이 나?

넥슨 모다스튜디오 타일맵 게임 적용 결과야:

타일 수 결과
15,000개 무난하게 60fps 이상
55,000개 프레임 저하 있지만 클래식보다 훨씬 양호
62,000개 5.38ms로 렌더링 처리
유닛 이동은 어때?

10,000 유닛 기준으로 비교해볼게:

방식 10,000 유닛 결과
클래식 (MonoBehaviour.Update) 약 8fps
ECS + Job System 60fps 이상 유지
성능 차이

8fps → 60fps 이상

Profiler로 확인: Worker Thread들이 활성화되어 멀티코어 활용!

Part 8. 디버깅은 어떻게 해?

ECS 쓰면 Hierarchy에서 안 보이는데, 디버깅은 어떻게 해?

Entity Debugger라는 전용 도구를 써야 해.

Entity Debugger 구성
  • 왼쪽: System 리스트 (On/Off, 프레임당 수행시간)
  • 가운데: 쿼리 조건 (어떤 Component 조합 처리하는지)
  • 오른쪽: Chunk Info 히스토그램
Chunk Info는 어떻게 읽어?

히스토그램 막대가 오른쪽에 가까울수록 좋아!

Chunk가 꽉 차있다는 뜻이거든.

ECS 디버깅의 어려움

기존처럼 에디터에서 눈으로 확인하기 어려움
Entity Debugger가 유일한 확인 방법이야!

Part 9. 기존 코드 다 버려야 해?

ECS 쓰려면 기존 코드 다 새로 짜야 해?

아니! Hybrid 방식으로 기존 것 대부분 재활용 가능해!

// 기존 GameObject를 ECS Entity로 자동 변환! GameObjectConversionUtility.ConvertGameObjectHierarchy( gameObject, // 기존 GameObject conversionSettings // 설정 ); // 결과: ECS Entity 반환
Hybrid 방식으로 어떻게 개발해?

이런 구조로 만들어:

// 1. Component (데이터) public struct TroopMove : IComponentData { public float speed; } // 2. Proxy (에디터에서 값 설정 가능) public class TroopMoveProxy : MonoBehaviour, IConvertGameObjectToEntity { [SerializeField] float speed; public void Convert(Entity entity, EntityManager manager, ...) { manager.AddComponentData(entity, new TroopMove { speed = speed }); } } // 3. System (로직) // 4. 기존 MonoBehaviour 스폰 로직 그대로 사용!
Hybrid의 장점

기존 프리팹/코드 재활용 가능!
점진적으로 ECS 적용할 수 있어!

Part 10. 언제 ECS를 써야 해?

모든 걸 ECS로 바꿔야 해?

아니! ECS가 효과적인 조건이 있어:

ECS가 효과적인 경우

  1. 같은 타입의 오브젝트가
  2. 엄청 많이 (수만 단위)
  3. 매 프레임 업데이트되는 경우

기계적 판단: MonoBehaviour.Update()가 있다면 → ECS System으로 대체 검토!
ECS가 오히려 안 좋은 경우는?

이런 경우에는 기존 방식이 나아:

상황 ECS 효과
오브젝트 수가 적음 효과 없음
서로 다른 타입이 많음 Archetype이 많아져서 비효율
Component 추가/삭제 빈번 메모리 이동 비용
ECS 단점
  • 디버깅 어려움: Entity Debugger만 가능
  • 학습 곡선: DOD 패러다임이 익숙하지 않으면 어려움
  • API 변경: 아직 프리뷰라 자주 바뀜

핵심 정리: Unity ECS와 Job System

  • 문제 - 기존 GameObject는 메모리 랜덤 접근 → 캐시 미스 → 성능 저하
  • DOD - 데이터를 촘촘하게 배치해서 캐시 적중률 향상
  • ECS - Entity(식별자) + Component(데이터) + System(로직) 분리
  • Archetype - 같은 Component 조합을 배열로 저장 → 캐시 효율적
  • Job System - 멀티스레딩 쉽게, Deadlock/Race Condition 컴파일 타임 방지
  • 적용 기준 - 같은 타입 + 대량 + 매 프레임 업데이트 = ECS 적합
  • Hybrid - 기존 코드 재활용하면서 점진적 적용 가능
발표자 소감

"설계 단계부터 생각하게 되고, 하드웨어 단계에서도 고민하게 됐다.
더 이상 단순히 응용 프로그래머가 아닌 엔지니어가 된 느낌."
