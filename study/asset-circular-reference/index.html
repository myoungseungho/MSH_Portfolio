순환 참조의 지옥

A→B→C→A 고리가 만드는 메모리 누수와 해결 전략

Part 1. 순환 참조란?

순환 참조가 뭐야?

순환 참조(Circular Reference)는 에셋들이 서로를 참조하여 닫힌 고리를 형성하는 상태입니다. A가 B를 참조하고, B가 C를 참조하고, C가 다시 A를 참조하면 순환이 발생합니다.

┌─────────────────────────────────────────────────────────────────┐
│                      순환 참조 기본 패턴                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [직접 순환 참조]                                                │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      A ─────────→ B                                             │
│      ↑             │                                            │
│      └─────────────┘                                            │
│                                                                 │
│      예: Player 프리팹이 Weapon 프리팹 참조                      │
│          Weapon 프리팹이 Player 프리팹 참조 (소유자 표시용)       │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [간접 순환 참조]                                                │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      A ──→ B ──→ C ──→ D                                       │
│      ↑                   │                                      │
│      └───────────────────┘                                      │
│                                                                 │
│      예: UI 시스템                                               │
│          MainUI → GameUI → Inventory → ItemPopup → MainUI       │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [자기 참조 (Self-Reference)]                                    │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│           ┌────┐                                                │
│           │    │                                                │
│           ▼    │                                                │
│           A ───┘                                                │
│                                                                 │
│      예: 트리 구조의 노드가 자신의 프리팹을 자식으로 참조         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
순환 참조가 왜 문제야?

순환 참조는 여러 심각한 문제를 일으킵니다:

┌─────────────────────────────────────────────────────────────────┐
│                    순환 참조의 문제점                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [1. 메모리 누수 (Memory Leak)]                                  │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  번들 A 언로드 시도:                                             │
│  ─────────────────                                              │
│  "B가 아직 A를 참조 중 → 언로드 불가"                            │
│                                                                 │
│  번들 B 언로드 시도:                                             │
│  ─────────────────                                              │
│  "A가 아직 B를 참조 중 → 언로드 불가"                            │
│                                                                 │
│  결과: A도 B도 영원히 메모리에 남음 → 누수!                      │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [2. 빌드 크기 폭발]                                             │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  번들 빌드 시:                                                   │
│                                                                 │
│  Bundle_A를 빌드 → B가 필요 → B를 A에 포함                      │
│  Bundle_B를 빌드 → A가 필요 → A를 B에 포함                      │
│                                                                 │
│  결과: A와 B 모두에 중복 에셋 포함 → 용량 2배!                   │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [3. 로딩 순서 교착 (Deadlock)]                                  │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  동기 로딩 시:                                                   │
│                                                                 │
│  Load(A) → A가 B 필요 → Load(B)                                 │
│            → B가 A 필요 → Load(A) ← 이미 로딩 중!               │
│                                                                 │
│  결과: 무한 대기 또는 스택 오버플로우                             │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [4. 가비지 컬렉션 문제]                                         │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  참조 카운팅 방식 GC에서:                                        │
│                                                                 │
│  A.refCount = 1 (B가 참조)                                      │
│  B.refCount = 1 (A가 참조)                                      │
│                                                                 │
│  외부 참조 없어도 서로 참조 → refCount > 0 → 수집 안 됨          │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Part 2. 순환 참조 유형

실제로 어떤 상황에서 순환 참조가 발생해?

게임 개발에서 흔히 발생하는 순환 참조 패턴들입니다:

┌─────────────────────────────────────────────────────────────────┐
│                 게임에서 흔한 순환 참조 패턴                       │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [패턴 1: 양방향 소유 관계]                                      │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      ┌────────────┐          ┌────────────┐                     │
│      │   Player   │──owns──→│   Weapon   │                     │
│      │  프리팹    │←─owner──│   프리팹   │                     │
│      └────────────┘          └────────────┘                     │
│                                                                 │
│  원인: Weapon이 소유자(Player)를 알아야 하는 상황                │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [패턴 2: UI 네비게이션]                                         │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      ┌──────────┐    ┌──────────┐    ┌──────────┐              │
│      │  메인UI  │───→│  상점UI  │───→│ 아이템UI │              │
│      └──────────┘    └──────────┘    └──────────┘              │
│           ↑                               │                     │
│           └───────────────────────────────┘                     │
│                    (메인으로 돌아가기)                           │
│                                                                 │
│  원인: 모든 UI가 메인 UI 참조를 직접 가지고 있음                 │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [패턴 3: 컴포넌트 상호 의존]                                    │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      ┌──────────────┐        ┌──────────────┐                   │
│      │ AudioManager │───────→│ GameManager  │                   │
│      │   (사운드)   │←───────│   (게임)     │                   │
│      └──────────────┘        └──────────────┘                   │
│                                                                 │
│  원인: 매니저 클래스들이 서로 직접 참조                          │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [패턴 4: 번들 간 공유 에셋]                                     │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│      Bundle_Characters                  Bundle_Enemies          │
│      ┌──────────────────┐              ┌──────────────────┐     │
│      │ PlayerPrefab     │              │ EnemyPrefab      │     │
│      │   └─ CommonVFX ──┼──────────────┼→ CommonVFX       │     │
│      │   └─ SharedMat ──┼──────────────┼→ SharedMat       │     │
│      └──────────────────┘              └──────────────────┘     │
│                │                               │                │
│                └───────────────┬───────────────┘                │
│                                ▼                                │
│                    두 번들이 같은 에셋 참조                      │
│                    → 중복 포함 또는 암묵적 의존성                │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Part 3. 순환 참조 감지 방법

순환 참조를 어떻게 찾아내?

순환 참조 감지는 그래프 이론의 사이클 탐지 알고리즘을 사용합니다:

┌─────────────────────────────────────────────────────────────────┐
│                    순환 참조 감지 알고리즘                         │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [1. DFS (깊이 우선 탐색) 기반 사이클 감지]                       │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  상태 정의:                                                     │
│  - WHITE (미방문)                                               │
│  - GRAY  (현재 탐색 중 - 스택에 있음)                           │
│  - BLACK (탐색 완료)                                            │
│                                                                 │
│  알고리즘:                                                       │
│  1. 노드 방문 시 GRAY로 마킹                                     │
│  2. 인접 노드가 GRAY면 → 사이클 발견!                           │
│  3. 모든 인접 노드 탐색 후 BLACK으로 마킹                        │
│                                                                 │
│     A ──→ B ──→ C                                               │
│     ↑           │                                               │
│     └───────────┘                                               │
│                                                                 │
│  탐색: A(GRAY) → B(GRAY) → C(GRAY) → A(이미 GRAY!) → 사이클!    │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [2. 위상 정렬 (Topological Sort) 활용]                          │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  원리: DAG(방향 비순환 그래프)만 위상 정렬 가능                   │
│                                                                 │
│  알고리즘:                                                       │
│  1. 모든 노드의 진입 차수(in-degree) 계산                        │
│  2. 진입 차수 0인 노드부터 제거                                  │
│  3. 제거된 노드의 간선 삭제, 인접 노드 진입 차수 감소            │
│  4. 모든 노드 제거 가능 → 사이클 없음                           │
│     제거 불가 노드 존재 → 사이클 있음!                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
Unity에서 순환 참조를 감지하는 코드는?
// CircularReferenceDetector.cs - 에디터용 순환 참조 감지 using System.Collections.Generic; using UnityEngine; using UnityEditor; public class CircularReferenceDetector { private enum NodeState { White, Gray, Black } private Dictionary<string, HashSet<string>> m_Graph; private Dictionary<string, NodeState> m_States; private List<string> m_CurrentPath; private List<List<string>> m_Cycles; // 프리팹의 참조 관계로 그래프 구축 public void BuildGraphFromPrefabs(string folderPath) { m_Graph = new Dictionary<string, HashSet<string>>(); string[] guids = AssetDatabase.FindAssets("t:Prefab", new[] { folderPath }); foreach (string guid in guids) { string path = AssetDatabase.GUIDToAssetPath(guid); string[] dependencies = AssetDatabase.GetDependencies(path, false); if (!m_Graph.ContainsKey(path)) { m_Graph[path] = new HashSet<string>(); } foreach (string dep in dependencies) { if (dep.EndsWith(".prefab") && dep != path) { m_Graph[path].Add(dep); if (!m_Graph.ContainsKey(dep)) { m_Graph[dep] = new HashSet<string>(); } } } } } // DFS로 사이클 감지 public List<List<string>> FindCycles() { m_States = new Dictionary<string, NodeState>(); m_Cycles = new List<List<string>>(); m_CurrentPath = new List<string>(); foreach (var node in m_Graph.Keys) { m_States[node] = NodeState.White; } foreach (var node in m_Graph.Keys) { if (m_States[node] == NodeState.White) { DFS(node); } } return m_Cycles; } private void DFS(string node) { m_States[node] = NodeState.Gray; m_CurrentPath.Add(node); foreach (string neighbor in m_Graph[node]) { if (m_States[neighbor] == NodeState.Gray) { // 사이클 발견! int cycleStart = m_CurrentPath.IndexOf(neighbor); var cycle = m_CurrentPath.GetRange(cycleStart, m_CurrentPath.Count - cycleStart); cycle.Add(neighbor); // 시작점 다시 추가로 순환 표시 m_Cycles.Add(cycle); } else if (m_States[neighbor] == NodeState.White) { DFS(neighbor); } } m_States[node] = NodeState.Black; m_CurrentPath.RemoveAt(m_CurrentPath.Count - 1); } } // 에디터 메뉴에서 실행 public class CircularRefMenu { [MenuItem("Tools/Detect Circular References")] static void DetectCircularReferences() { var detector = new CircularReferenceDetector(); detector.BuildGraphFromPrefabs("Assets/Prefabs"); var cycles = detector.FindCycles(); if (cycles.Count == 0) { Debug.Log("순환 참조 없음!"); } else { foreach (var cycle in cycles) { Debug.LogWarning($"순환 발견: {string.Join(" → ", cycle)}"); } } } }

Part 4. 순환 참조 해결 전략

순환 참조를 어떻게 끊어?

주요 해결 전략들입니다:

┌─────────────────────────────────────────────────────────────────┐
│                    순환 참조 해결 전략 개요                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [전략 1: 약한 참조 (Weak Reference)]                            │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  Before:  A ←──────→ B  (양방향 강한 참조)                      │
│  After:   A ─────────→ B  (강한 참조)                           │
│           A ←─ ─ ─ ─ ─ B  (약한 참조)                           │
│                                                                 │
│  약한 참조는 GC 대상에서 제외 안 됨                              │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [전략 2: 이벤트/콜백 패턴]                                       │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  Before:  Player ←──────→ Weapon                                │
│                                                                 │
│  After:   Player ──────→ Weapon                                 │
│           Player ←─event─ (OnDamageDealt 이벤트)                │
│                                                                 │
│  Weapon이 Player를 직접 참조하지 않고 이벤트로 통신              │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [전략 3: 인터페이스 분리]                                        │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  Before:  A ←──────→ B (구체 클래스 참조)                       │
│                                                                 │
│  After:   A ──────→ IB (인터페이스)                             │
│           B implements IB                                       │
│           B ──────→ IA (인터페이스)                             │
│           A implements IA                                       │
│                                                                 │
│  서로 인터페이스만 알고, 구체 구현 모름 → 의존성 역전            │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [전략 4: 공유 번들 분리]                                        │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  Before:                                                        │
│    Bundle_A ────→ SharedAsset ←──── Bundle_B                   │
│         ↑____________________________↓                          │
│         (암묵적 순환 의존)                                       │
│                                                                 │
│  After:                                                         │
│    Bundle_A ────┐              ┌──── Bundle_B                  │
│                 ↓              ↓                                │
│              Bundle_Shared (SharedAsset)                        │
│                                                                 │
│  공유 에셋을 별도 번들로 분리하여 의존 방향 단일화               │
│                                                                 │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  [전략 5: 런타임 동적 참조]                                       │
│  ─────────────────────────────────────────────────────          │
│                                                                 │
│  Before:  [SerializeField] Player m_Player; (에디터 참조)       │
│                                                                 │
│  After:   Player m_Player;                                      │
│           void Start() {                                        │
│               m_Player = FindObjectOfType();            │
│           }                                                     │
│                                                                 │
│  에셋 참조 대신 런타임에 찾아서 연결                             │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
실제 코드로 해결 방법을 보여줘
// ===== 해결 전략 1: 이벤트/콜백 패턴 ===== // Before: 순환 참조 public class Player_Bad : MonoBehaviour { [SerializeField] private Weapon_Bad m_Weapon; } public class Weapon_Bad : MonoBehaviour { [SerializeField] private Player_Bad m_Owner; // 순환! void OnDealDamage(int damage) { m_Owner.AddKillCount(); } } // After: 이벤트로 분리 public class Player_Good : MonoBehaviour { [SerializeField] private Weapon_Good m_Weapon; void Awake() { m_Weapon.OnDamageDealt += HandleDamageDealt; } void OnDestroy() { m_Weapon.OnDamageDealt -= HandleDamageDealt; } private void HandleDamageDealt(int damage) { AddKillCount(); } } public class Weapon_Good : MonoBehaviour { // Player를 직접 참조하지 않음! public System.Action<int> OnDamageDealt; void DealDamage(int damage) { OnDamageDealt?.Invoke(damage); } } // ===== 해결 전략 2: 인터페이스 분리 ===== // 인터페이스 정의 public interface IDamageable { void TakeDamage(int amount); } public interface IWeaponHolder { void OnWeaponFired(); } // 구현 - 서로 인터페이스만 알고 있음 public class Player_Interface : MonoBehaviour, IWeaponHolder, IDamageable { private IWeapon m_Weapon; // 인터페이스로 참조 public void TakeDamage(int amount) { ... } public void OnWeaponFired() { ... } } public interface IWeapon { void Fire(); void SetHolder(IWeaponHolder holder); } public class Weapon_Interface : MonoBehaviour, IWeapon { private IWeaponHolder m_Holder; // 인터페이스로 참조 public void SetHolder(IWeaponHolder holder) { m_Holder = holder; } public void Fire() { m_Holder?.OnWeaponFired(); } } // ===== 해결 전략 3: 약한 참조 (WeakReference) ===== using System; public class Weapon_WeakRef : MonoBehaviour { // WeakReference: GC가 Player를 수집하는 것을 막지 않음 private WeakReference<Player> m_OwnerRef; public void SetOwner(Player owner) { m_OwnerRef = new WeakReference<Player>(owner); } void OnDealDamage() { // TryGetTarget: 참조가 아직 유효한지 확인 if (m_OwnerRef != null && m_OwnerRef.TryGetTarget(out var owner)) { owner.AddKillCount(); } } }

Part 5. 번들 간 순환 참조

Asset Bundle 간 순환 참조는 어떻게 처리해?

번들 의존성을 분석하는 코드는?
// BundleDependencyAnalyzer.cs - 번들 간 의존성 분석 using System.Collections.Generic; using UnityEngine; using UnityEditor; public class BundleDependencyAnalyzer { public struct BundleInfo { public string Name; public HashSet<string> Dependencies; public HashSet<string> Dependents; public int Layer; // 계산된 레이어 } private Dictionary<string, BundleInfo> m_Bundles; // 번들 의존성 그래프 구축 public void BuildDependencyGraph() { m_Bundles = new Dictionary<string, BundleInfo>(); foreach (string bundleName in AssetDatabase.GetAllAssetBundleNames()) { var info = new BundleInfo { Name = bundleName, Dependencies = new HashSet<string>(), Dependents = new HashSet<string>(), Layer = -1 }; // 이 번들이 의존하는 다른 번들들 string[] deps = AssetDatabase.GetAssetBundleDependencies(bundleName, false); foreach (string dep in deps) { info.Dependencies.Add(dep); } m_Bundles[bundleName] = info; } // 역방향 관계 구축 (누가 나를 의존하는가) foreach (var kvp in m_Bundles) { foreach (string dep in kvp.Value.Dependencies) { if (m_Bundles.ContainsKey(dep)) { var depInfo = m_Bundles[dep]; depInfo.Dependents.Add(kvp.Key); m_Bundles[dep] = depInfo; } } } } // 순환 참조 검사 public List<List<string>> FindBundleCycles() { var cycles = new List<List<string>>(); var visited = new HashSet<string>(); var recStack = new HashSet<string>(); var path = new List<string>(); foreach (string bundle in m_Bundles.Keys) { if (!visited.Contains(bundle)) { DFSFindCycle(bundle, visited, recStack, path, cycles); } } return cycles; } private void DFSFindCycle(string node, HashSet<string> visited, HashSet<string> recStack, List<string> path, List<List<string>> cycles) { visited.Add(node); recStack.Add(node); path.Add(node); foreach (string dep in m_Bundles[node].Dependencies) { if (!visited.Contains(dep)) { DFSFindCycle(dep, visited, recStack, path, cycles); } else if (recStack.Contains(dep)) { // 사이클 발견 int start = path.IndexOf(dep); var cycle = path.GetRange(start, path.Count - start); cycle.Add(dep); cycles.Add(cycle); } } recStack.Remove(node); path.RemoveAt(path.Count - 1); } // 레이어 계산 (위상 정렬) public void CalculateLayers() { var inDegree = new Dictionary<string, int>(); foreach (var kvp in m_Bundles) { inDegree[kvp.Key] = kvp.Value.Dependencies.Count; } var queue = new Queue<string>(); int currentLayer = 0; // 의존성이 없는 번들 = Layer 0 foreach (var kvp in inDegree) { if (kvp.Value == 0) { queue.Enqueue(kvp.Key); var info = m_Bundles[kvp.Key]; info.Layer = currentLayer; m_Bundles[kvp.Key] = info; } } while (queue.Count > 0) { int levelSize = queue.Count; currentLayer++; for (int i = 0; i < levelSize; i++) { string current = queue.Dequeue(); foreach (string dependent in m_Bundles[current].Dependents) { inDegree[dependent]--; if (inDegree[dependent] == 0) { queue.Enqueue(dependent); var info = m_Bundles[dependent]; info.Layer = currentLayer; m_Bundles[dependent] = info; } } } } } }

Part 7. 순환 참조 해결 체크리스트

순환 참조 문제를 발견했을 때 어떤 순서로 해결해야 해?

순환 참조 해결 단계

  1. 식별: 어떤 에셋들이 순환에 포함되어 있는지 파악
  2. 분류: 순환 유형 판단 (프리팹/번들/코드)
  3. 우선순위: 끊어야 할 연결 선택 (가장 약한 의존성)
  4. 리팩토링: 이벤트/인터페이스/Soft Reference로 대체
  5. 검증: 순환 참조 감지 도구로 재확인
  6. 예방: CI 검사 추가

⚠️ 순환 참조 해결 시 주의사항

  • 한 번에 모든 순환을 끊으려 하지 말 것 → 점진적 리팩토링
  • WeakReference는 null 체크 필수 → 참조 대상이 GC될 수 있음
  • 이벤트 구독 해제 잊지 않기 → 메모리 누수 원인
  • 런타임 참조 해결은 성능 비용 고려
  • 팀 전체가 의존성 규칙을 이해해야 함

핵심 정리: 순환 참조

  • 순환 참조: A→B→C→A 형태의 닫힌 의존성 고리
  • 문제점: 메모리 누수, 빌드 크기 증가, 로딩 교착
  • 감지: DFS 사이클 탐지, 위상 정렬
  • 해결: 약한 참조, 이벤트, 인터페이스, 공유 번들 분리
  • 예방: 레이어 아키텍처, 의존성 방향 규칙, CI 검사
