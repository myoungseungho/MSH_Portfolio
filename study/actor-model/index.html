우리 게임 서버, 알고 보면 '액터가 1마리뿐인' 액터 모델이야

IOCP → 큐 → 게임로직 스레드 1개 vs 진짜 액터 모델, 직접 움직여보며 비교

30초 요약

우리 서버의 'IOCP 스레드 → 큐 → 게임로직 스레드 1개'는 액터 모델과 메커니즘이 똑같아 — 큐에 줄 세워 하나씩 처리해서 락을 없애는 것.

결정적 차이는 딱 하나, '액터 수'. 우리는 1마리(월드 전체를 스레드 1개가 처리), 진짜 액터 모델은 N마리(유저·방·NPC마다).

아래 시뮬레이터를 직접 만져보면 그 차이가 눈에 보여.

Part 1. 우리 서버, 사실 이렇게 돌아가

우리 게임 서버, 네트워크 패킷이 들어오면 누가 처리해?

IOCP 스레드(보통 여러 개)가 소켓에서 패킷을 꺼내.

근데 걔네가 게임 로직을 직접 돌리진 않아.

그냥 패킷을 큐 하나에 차곡차곡 넣어두기만 해.

그 다음은?

게임로직 스레드가 그 큐에서 메시지를 하나씩 꺼내서 처리해.

공격, 이동, 거래... 전부 이 스레드 1개가 순서대로 처리하지.

그래서 우리 서버 로직엔 락이 거의 없어. 혼자 다 하니까 동시에 꼬일 일이 없거든.

[우리 게임 서버] IOCP #1 ┐ IOCP #2 ┼──▶ 큐 1개 ──▶ 게임로직 스레드 ×1 ──▶ (순차 처리) IOCP #3 ┘ 받아서 쌓기만 한 번에 딱 하나씩

Part 2. 직접 만져봐 (어디서 본 구조 같지 않아?)

'큐에 넣고 하나씩 처리'... 이거 어디서 많이 들어본 느낌 아냐?

맞아, 액터 모델이랑 똑 닮았어.

근데 '닮았다'랑 '같다'는 달라. 결정적인 차이가 딱 하나 있는데 — 맞춰봐. 뭘까?

아래에서 ① 우리 서버와 ② 진짜 액터 모델을 번갈아 보면서, '패킷 유입량'을 올리거나 '공성전' 버튼을 눌러봐. 큐 적체 숫자를 비교해보면 차이가 보일 거야.

0큐 적체
0처리 완료
1동시 처리 코어

Part 3. 그래서, 같은 거 맞아?

① 우리 서버는 큐가 막 쌓이는데 ② 액터 모델은 잘 안 쌓이더라. 왜 그래?

①은 처리하는 스레드가 딱 1개거든. 아무리 쌓여도 한 번에 하나씩.

②는 코어 4개가 서로 다른 액터를 동시에 처리해. 같은 양이 들어와도 4배 빨리 비워내지.

그럼 둘이 메커니즘은 같은 거네?

락을 없애는 원리는 같아. 둘 다 '큐에 줄 세워서 하나씩' 처리하니까, 같은 데이터를 동시에 건드릴 일이 구조적으로 없어.

근데 '몇 개를 동시에 굴리느냐'가 완전히 달라. 바로 이게 핵심.

Part 4. 결정적 차이 = 액터가 몇 마리야?

그 결정적 차이가 뭔데?

액터 수.

우리 서버 = 액터 1마리. 게임로직 스레드 1개가 온 세상(모든 유저·몬스터·방)을 혼자 맡아.

진짜 액터 모델 = 액터 N마리. 유저마다, 방마다, NPC마다 따로 존재하고, 각자 자기 메일박스를 가져.

[우리 = 거대한 액터 1마리] [액터 모델 = 작은 액터 N마리] ┌──────────────────┐ ┌─유저A─┐ ┌─유저B─┐ ┌─방1─┐ │ 게임로직 스레드 │ │메일박스│ │메일박스│ │메일박스│ │ (월드 전체 담당) │ └───┬──┘ └───┬──┘ └──┬─┘ │ 메일박스 1개 │ └──── 코어풀이 동시에 ────┘ └──────────────────┘ (멀티코어 병렬)

Part 5. IOCP 스레드는 액터가 아니야 (흔한 오해)

잠깐, IOCP 스레드도 여러 개잖아. 걔네가 액터들 아냐?

아니, 그게 제일 흔한 오해야.

IOCP 스레드는 게임 판단을 1도 안 해. 소켓에서 바이트 꺼내서 큐에 넣는 게 전부인 우편배달부거든.

액터의 핵심은 '자기 상태를 갖고 스스로 판단'하는 건데, IOCP 스레드는 상태도 없고 판단도 안 해.

비유로 들면?

식당으로 보면 — IOCP 스레드는 손님 주문을 받아 적어서 주방에 거는 '서빙 직원'이야. 요리는 안 해.

게임로직 스레드는 그 주문표를 하나씩 떼어 요리하는 '주방장 1명'이고.

진짜 액터 모델은 주방장이 여러 명이라 동시에 여러 요리를 해. 그게 차이야.

IOCP 스레드 = 우편배달부 / 서빙 직원 - 상태 없음, 판단 없음 - 받아서 큐(메일박스)에 넣기만 게임로직 스레드 = 액터 (단 1마리) - 월드 상태를 들고 있음 - 메시지를 보고 스스로 판단·처리

Part 6. '서버가 곧 액터다'는 반만 맞아

예전엔 '게임 서버 11, 12가 패킷으로 통신하니까 그게 액터 모델이다'라고 들었는데?

그건 '서버끼리' 봤을 때 얘기야. 서버 하나하나를 액터로 보면 — 맞아, 여러 서버 = 여러 액터.

근데 서버 '안'을 들여다보면? 그 안엔 게임로직 스레드가 1개뿐이야. 즉 액터 1마리.

그래서 똑같은 시스템이 보는 각도에 따라 'N 액터'도 되고 '1 액터'도 돼.

[멀리서 보면 = N 액터] [가까이서 보면 = 1 액터] 서버11 ⇄ 서버12 ⇄ 서버13 서버11 내부: (패킷으로만 통신) IOCP들 ─▶ 큐 ─▶ 게임로직 ×1 서버 = 액터 N개 = 액터 1마리
그럼 진짜 액터 모델이라고 부르려면?

한 프로세스 '안'에서 액터가 여러 마리여야 해. 유저A 액터, 유저B 액터가 각자 메일박스를 갖고 멀티코어로 동시에 도는 구조.

우리는 그걸 프로세스 단위(채널·존)로 쪼개서 비슷한 효과를 내는 거고.

Part 7. 왜 우리는 굳이 액터 1마리로?

멀티코어로 N 액터 굴리면 더 빠른데, 왜 굳이 1개로 해?

단순함 때문이야.

싱글스레드면 락이 0개, 레이스컨디션이 0개. 새벽 3시에 '데드락 터졌어요' 전화 올 일이 없거든.

게다가 게임 로직은 한 스킬이 여러 유저·몬스터를 동시에 건드리는 거미줄이라, 액터로 잘게 쪼개면 메시지 폭발 + 분산 트랜잭션 지옥이 돼.

그럼 1코어 천장은 어떻게 넘어?

수직(스레드 늘리기) 대신 수평으로 쪼개.

한 프로세스 안에서 스레드를 늘리는 대신, 채널·존(맵) 단위로 프로세스 자체를 여러 개 띄우는 거야.

공성전에 한 채널로 3,000명이 몰리면? 그 채널의 게임로직 1코어가 밀려서 렉이 걸려. 그래서 채널 정원을 두고, 맵을 쪼개는 거지.

한 줄로 정리하면?

구체: 우리는 채널 하나당 게임로직 스레드 1개 = 액터 1마리로 묶어서 락 없는 단순함을 샀어.

추상: 동시성을 '한 단위 안에선 순차, 단위 사이는 분리'로 푼 거야.

구체: 그래서 동접이 늘면 코어를 늘리는 게 아니라 채널·서버를 늘려. WoW가 대륙별로 서버를 쪼개는 거랑 같은 원리.

핵심 정리

  • 우리 서버 = IOCP(우편배달부) → 큐 1개 → 게임로직 스레드 1개 = 액터가 1마리뿐인 액터 모델
  • 메커니즘은 동일 — 큐에 줄 세워 순차 처리해서 락을 없애는 방식
  • 결정적 차이 = 액터 수. 우리는 1개(월드 전체), 진짜 액터 모델은 N개(유저·방·NPC)
  • IOCP 스레드는 액터가 아님 — 상태도 판단도 없는 I/O 전담
  • '서버=액터'는 서버 간에서만 성립 — 서버 안은 액터 1마리
  • 왜 1마리? 락 0개의 단순함을 얻고, 1코어 천장은 채널·존 샤딩으로 수평 확장

더 생각해볼 거리

만약 우리 서버를 진짜 멀티 액터로 바꾼다면, 1:1 골드 거래(한쪽 빼고 한쪽 더하기)는 어떻게 처리해야 중간에 서버가 죽어도 안전할까?

채팅 서버는 게임 서버랑 달리 상태 의존성이 약해. 그럼 채팅은 액터 N개로 쪼개는 게 유리할까, 1개가 나을까?
