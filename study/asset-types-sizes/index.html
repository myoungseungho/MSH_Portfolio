Part 1. 게임 에셋의 대분류

게임에는 어떤 종류의 에셋이 있어?

게임 에셋은 크게 렌더링 에셋, 오디오 에셋, 데이터 에셋으로 나눌 수 있어.

각 에셋 타입의 특징은?

각 에셋은 용량, 로딩 속도, 압축률이 다 달라.

에셋 타입별 특성 비교:

┌────────────────┬─────────────┬─────────────┬─────────────┬─────────────┐
│   에셋 타입    │ 평균 크기   │  압축률     │  로딩 비용  │ 메모리 상주 │
├────────────────┼─────────────┼─────────────┼─────────────┼─────────────┤
│ 텍스처         │   큼        │  좋음       │   보통      │ GPU 메모리  │
│ 메시           │   보통      │  보통       │   보통      │ GPU 메모리  │
│ 애니메이션     │   작음      │  좋음       │   빠름      │ CPU 메모리  │
│ 오디오 (BGM)   │   큼        │  좋음       │   스트리밍  │ 버퍼만      │
│ 오디오 (SFX)   │   작음      │  보통       │   빠름      │ CPU 메모리  │
│ 비디오         │   매우 큼   │  매우 좋음  │   스트리밍  │ 버퍼만      │
│ 스크립트       │   매우 작음 │  좋음       │   빠름      │ CPU 메모리  │
│ 설정 파일      │   매우 작음 │  좋음       │   빠름      │ CPU 메모리  │
└────────────────┴─────────────┴─────────────┴─────────────┴─────────────┘

※ GPU 메모리: VRAM에 상주, CPU에서 직접 접근 어려움
※ 스트리밍: 전체를 메모리에 올리지 않고 조금씩 읽어서 재생

Part 2. 에셋 용량 비율 - 뭐가 제일 무거워?

게임 전체에서 어떤 에셋이 제일 용량을 많이 차지해?

대부분의 게임에서 텍스처가 50~70%를 차지해. 압도적으로 1등이야.

그 다음이 오디오(15~25%), 메시(5~15%), 애니메이션(3~8%) 순이야.

일반적인 AAA 게임 에셋 용량 비율:

텍스처       ████████████████████████████████████████████████████████ 55%
오디오       ████████████████████████ 22%
메시         ████████████ 11%
애니메이션   ██████ 5%
비디오       ████ 4%
기타         ██ 3%
            ├────────────────────────────────────────────────────────┤
            0%                                                    100%

실제 게임 사례 (설치 용량 기준):
┌────────────────────────────────────────────────────────────────────┐
│  콜 오브 듀티 MW (2019)         │   텍스처 60%  │  오디오 25%     │
│  사이버펑크 2077               │   텍스처 55%  │  보이스 20%     │
│  파이널 판타지 XV              │   텍스처 50%  │  영상 15%       │
│  인디 2D 게임                  │   스프라이트 40%  │  오디오 30%  │
└────────────────────────────────────────────────────────────────────┘

→ 용량 최적화 = 텍스처 최적화가 핵심!
왜 텍스처가 그렇게 큰 거야?

현대 게임은 4K 텍스처를 기본으로 사용하고, 하나의 오브젝트에 여러 텍스처가 필요해:

- Albedo(색상): 기본 색상 맵

- Normal(노말): 표면 요철 정보

- Roughness/Metallic: PBR 파라미터

- AO(Ambient Occlusion): 구석 그림자

- Emissive: 발광 맵

캐릭터 하나에 5~8장의 텍스처가 붙어!

PBR 캐릭터 텍스처 구성 예시:

    캐릭터 "철갑 기사"
    ├── Body_Albedo.tga      (4096x4096, RGBA) → 64MB
    ├── Body_Normal.tga      (4096x4096, RGB)  → 48MB
    ├── Body_Roughness.tga   (2048x2048, R)    → 4MB
    ├── Body_Metallic.tga    (2048x2048, R)    → 4MB
    ├── Body_AO.tga          (2048x2048, R)    → 4MB
    ├── Armor_Albedo.tga     (4096x4096, RGBA) → 64MB
    ├── Armor_Normal.tga     (4096x4096, RGB)  → 48MB
    ├── Armor_RoughMetal.tga (2048x2048, RG)   → 8MB
    └── Face_Subsurface.tga  (2048x2048, RGB)  → 12MB
                                               ─────────
                                    원본 합계: 약 256MB
                                    압축 후:   약 40MB (BC7 기준)

→ 캐릭터 1명 = 원본 256MB, 압축 후에도 40MB!
→ NPC 10명만 있어도 400MB!

Part 3. 텍스처 크기 계산법

텍스처 메모리 크기는 어떻게 계산해?

공식: 가로 × 세로 × 채널당 바이트 × 채널 수

// 텍스처 메모리 크기 계산 // 채널별 비트 깊이 // R8G8B8A8: 각 채널 8비트 = 4바이트/픽셀 // R16G16B16A16: 각 채널 16비트 = 8바이트/픽셀 (HDR용) // R32G32B32A32: 각 채널 32비트 = 16바이트/픽셀 (float) size_t CalculateTextureSize(int width, int height, int bytesPerPixel) { return width * height * bytesPerPixel; } // 예시 계산 // 512x512 RGBA8: 512 * 512 * 4 = 1,048,576 bytes = 1 MB // 1024x1024 RGBA8: 1024 * 1024 * 4 = 4,194,304 bytes = 4 MB // 2048x2048 RGBA8: 2048 * 2048 * 4 = 16,777,216 bytes = 16 MB // 4096x4096 RGBA8: 4096 * 4096 * 4 = 67,108,864 bytes = 64 MB // 8192x8192 RGBA8: 8192 * 8192 * 4 = 268,435,456 bytes = 256 MB // Mipmap이 있으면 약 1.33배 size_t CalculateWithMipmaps(int width, int height, int bytesPerPixel) { size_t total = 0; while (width >= 1 && height >= 1) { total += width * height * bytesPerPixel; width /= 2; height /= 2; } return total; // 원본의 약 1.33배 }
압축 포맷별로 얼마나 줄어들어?

GPU에서 바로 읽을 수 있는 블록 압축(Block Compression)을 사용하면 크게 줄어들어!

텍스처 압축 포맷 비교 (4096x4096 기준):

┌─────────────────┬───────────────┬────────────┬────────────────────────┐
│    포맷         │  비트/픽셀    │   크기     │        용도            │
├─────────────────┼───────────────┼────────────┼────────────────────────┤
│ RGBA8 (무압축)  │    32 bpp     │   64 MB    │ 원본/편집용            │
│ BC1 (DXT1)      │     4 bpp     │    8 MB    │ 알파 없는 색상         │
│ BC3 (DXT5)      │     8 bpp     │   16 MB    │ 알파 있는 색상         │
│ BC5             │     8 bpp     │   16 MB    │ 노말맵 (RG만)          │
│ BC7             │     8 bpp     │   16 MB    │ 고품질 색상 (최신)     │
│ ASTC 4x4        │     8 bpp     │   16 MB    │ 모바일 (고품질)        │
│ ASTC 8x8        │     2 bpp     │    4 MB    │ 모바일 (저용량)        │
│ ETC2            │     8 bpp     │   16 MB    │ 모바일 (Android)       │
└─────────────────┴───────────────┴────────────┴────────────────────────┘

압축률 시각화 (4096x4096 텍스처):

무압축 RGBA8   ████████████████████████████████████████████████████████████████  64MB
BC7/BC3        ████████████████  16MB (75% 절약)
BC1 (DXT1)     ████████  8MB (87.5% 절약)
ASTC 8x8       ████  4MB (93.75% 절약)

※ BC = Block Compression (DirectX)
※ ASTC = Adaptive Scalable Texture Compression (OpenGL/Vulkan/Metal)
※ 압축/해제는 GPU 하드웨어에서 실시간 처리 (CPU 부담 없음)
Mipmap은 뭐고 왜 쓰는 거야?

Mipmap은 텍스처의 축소 버전들을 미리 만들어둔 것이야.

멀리 있는 오브젝트에 4K 텍스처를 쓰면 앨리어싱도 생기고 대역폭 낭비야.

Mipmap이 있으면 거리에 맞는 작은 버전을 써서 효율적이지!

Mipmap 레벨 구조:

Level 0: 4096x4096 = 64 MB    (원본)
         ┌────────────────────────────────────────────────────────────┐
         │                                                            │
         │                        원본 텍스처                          │
         │                                                            │
         └────────────────────────────────────────────────────────────┘

Level 1: 2048x2048 = 16 MB    (1/4)
         ┌──────────────────────────────────┐
         │                                  │
         └──────────────────────────────────┘

Level 2: 1024x1024 = 4 MB     (1/16)
         ┌────────────────┐
         │                │
         └────────────────┘

Level 3: 512x512 = 1 MB       (1/64)
         ┌────────┐
         │        │
         └────────┘

Level 4~11: 256→128→64→32→16→8→4→2→1 픽셀

총 메모리 = 64 + 16 + 4 + 1 + ... ≈ 85.3 MB (원본의 약 1.33배)

거리별 Mipmap 선택:
┌────────────────────────────────────────────────────────────────────┐
│  카메라 [📷]──────────────────────────────────────────────→        │
│                                                                    │
│   [물체]     [물체]         [물체]             [물체]              │
│   Level 0   Level 1-2      Level 3-4          Level 5+            │
│   (가까움)  (중간)         (멀리)             (아주 멀리)          │
└────────────────────────────────────────────────────────────────────┘

Part 4. 메시 크기 분석

3D 메시는 메모리를 얼마나 쓰는 거야?

메시 크기 = 버텍스 수 × 버텍스당 바이트 + 인덱스 수 × 인덱스당 바이트

// 일반적인 버텍스 구조체 struct StandardVertex { Vector3 position; // 12 bytes (float x 3) Vector3 normal; // 12 bytes Vector2 uv0; // 8 bytes Vector4 tangent; // 16 bytes (w = bitangent sign) // 총: 48 bytes per vertex }; // 스킨드 메시 (캐릭터용) struct SkinnedVertex { Vector3 position; // 12 bytes Vector3 normal; // 12 bytes Vector2 uv0; // 8 bytes Vector4 tangent; // 16 bytes uint8_t boneIndices[4]; // 4 bytes (최대 4개 본 영향) float boneWeights[4]; // 16 bytes (각 본의 가중치) // 총: 68 bytes per vertex }; // 인덱스 버퍼 // 65536개 미만: uint16 (2 bytes) // 65536개 이상: uint32 (4 bytes) // 메시 크기 계산 예시 // 10만 삼각형 캐릭터 (약 6만 버텍스) // 버텍스: 60,000 × 68 = 4,080,000 bytes ≈ 3.9 MB // 인덱스: 300,000 × 4 = 1,200,000 bytes ≈ 1.1 MB // 총: 약 5 MB per LOD
LOD별로 얼마나 줄어들어?

LOD(Level of Detail)는 거리에 따라 다른 디테일의 메시를 사용하는 기법이야.

LOD 레벨별 폴리곤 수와 메모리:

AAA 게임 주인공 캐릭터 예시:
┌─────────┬───────────────┬───────────────┬────────────┬─────────────┐
│  LOD    │  삼각형 수    │  버텍스 수    │  메모리    │   사용 거리 │
├─────────┼───────────────┼───────────────┼────────────┼─────────────┤
│  LOD 0  │  100,000      │  60,000       │  5.0 MB    │   0~5m      │
│  LOD 1  │   40,000      │  25,000       │  2.1 MB    │   5~15m     │
│  LOD 2  │   15,000      │  10,000       │  0.9 MB    │   15~30m    │
│  LOD 3  │    5,000      │   3,500       │  0.3 MB    │   30~60m    │
│  LOD 4  │    1,000      │     800       │  0.07 MB   │   60m+      │
└─────────┴───────────────┴───────────────┴────────────┴─────────────┘
                                           총: 8.37 MB

시각화:
LOD 0 ████████████████████████████████████████████████████████████ 100K
LOD 1 ████████████████████████  40K
LOD 2 █████████  15K
LOD 3 ███  5K
LOD 4 █  1K

※ 멀리 있으면 화면에서 작게 보이므로 LOD 4로도 충분!
※ 가까운 캐릭터만 LOD 0, 나머지는 LOD 1~3 → 메모리 대폭 절약
버텍스 압축은 없어?

있어! 버텍스 압축으로 메모리를 더 줄일 수 있어:

// 버텍스 압축 기법들 // 1. 노말/탄젠트 압축 (12+16 bytes → 4 bytes) // Octahedron encoding: Vector3 → 2x snorm16 struct CompressedNormal { int16_t x, y; // 4 bytes (z는 sqrt(1-x²-y²)로 복원) }; // 2. UV 압축 (8 bytes → 4 bytes) struct CompressedUV { uint16_t u, v; // 4 bytes (0~65535 → 0.0~1.0) }; // 3. 포지션 양자화 (12 bytes → 6 bytes) // 바운딩 박스 기준 상대 좌표로 변환 struct QuantizedPosition { uint16_t x, y, z; // 6 bytes }; // 압축된 버텍스 (48 bytes → 20 bytes로 58% 절약) struct CompressedVertex { QuantizedPosition position; // 6 bytes CompressedNormal normal; // 4 bytes CompressedNormal tangent; // 4 bytes int8_t tangentSign; // 1 byte uint8_t padding; // 1 byte CompressedUV uv; // 4 bytes // 총: 20 bytes (기존 48의 42%) };

Part 5. 애니메이션 크기 분석

애니메이션 데이터는 어떻게 구성되어 있어?

애니메이션은 본(Bone)의 트랜스폼(위치/회전/스케일)을 시간에 따라 저장한 데이터야.

애니메이션 데이터 구조:

┌─────────────────────────────────────────────────────────────────────┐
│  "달리기" 애니메이션 (1초, 30fps)                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  본: Hips                                                           │
│  ├── Frame 0:  pos(0,0.9,0)   rot(0,0,0,1)   scale(1,1,1)         │
│  ├── Frame 1:  pos(0,0.92,0.1) rot(...)      scale(1,1,1)         │
│  ├── Frame 2:  pos(0,0.91,0.2) rot(...)      scale(1,1,1)         │
│  │   ... (총 30프레임)                                              │
│  └── Frame 29: pos(0,0.9,1.0)  rot(...)      scale(1,1,1)         │
│                                                                     │
│  본: Spine                                                          │
│  ├── Frame 0~29 (30프레임)                                          │
│                                                                     │
│  본: LeftUpLeg, RightUpLeg, ... (총 60~100개 본)                    │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
애니메이션 하나가 메모리를 얼마나 차지해?

본 개수, 프레임 수, 압축 여부에 따라 크게 달라져.

// 애니메이션 메모리 계산 // 무압축 기준 // 본당 트랜스폼: position(12) + rotation(16) + scale(12) = 40 bytes // 프레임당 크기: 본 수 × 40 bytes // 전체 크기: 프레임 수 × 프레임당 크기 struct BoneTransform { Vector3 position; // 12 bytes Quaternion rotation; // 16 bytes Vector3 scale; // 12 bytes // 총: 40 bytes per bone per frame }; // 예시: 일반적인 캐릭터 애니메이션 // 본: 70개 // 초당 프레임: 30fps // 애니메이션 길이: 2초 // 총 프레임: 60 // 무압축 크기: 70 × 40 × 60 = 168,000 bytes ≈ 164 KB // 캐릭터 전체 애니메이션 세트 (RPG 기준) // Idle: 2초 × 2종 = 328 KB // Walk: 1초 × 8방향 = 656 KB // Run: 1초 × 8방향 = 656 KB // Attack: 평균 1.5초 × 20종 = 4.9 MB // Skill: 평균 2초 × 30종 = 9.8 MB // Hit/Death/etc: 약 3 MB // 총: 약 20 MB (무압축 기준)
애니메이션 압축은 어떻게 해?

애니메이션은 키프레임 리덕션과 양자화로 크게 압축할 수 있어!

애니메이션 압축 기법:

1. 키프레임 리덕션 (Keyframe Reduction)
   변화가 없거나 선형 보간 가능한 프레임 제거

   Before: [■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■ ■] 30 frames
   After:  [■     ■         ■     ■     ■ ] 5 keyframes + 보간
   → 30 → 5개로 줄이면 83% 절약!

2. 쿼터니언 압축 (Quaternion Compression)
   4 floats (16 bytes) → 3 shorts (6 bytes)

   "Smallest Three" 방식:
   - 쿼터니언은 |q| = 1 이므로 가장 큰 성분 생략 가능
   - 나머지 3개를 15비트로 양자화
   - 2비트로 생략된 성분 인덱스 저장

   16 bytes → 6 bytes (62.5% 절약)

3. 포지션 양자화 (Position Quantization)
   바운딩 박스 기준 상대 좌표 + 16비트 양자화

   12 bytes → 6 bytes (50% 절약)

4. 커브 피팅 (Curve Fitting)
   키프레임 대신 베지어/에르미트 커브로 표현

   [키프레임 데이터] → [커브 컨트롤 포인트]
   데이터량 대폭 감소 + 부드러운 재생

압축 결과 비교:
┌────────────────────┬────────────────┬────────────────┐
│    압축 방식       │  20MB 원본     │   압축 비율    │
├────────────────────┼────────────────┼────────────────┤
│  키프레임 리덕션   │    5 MB        │     75%        │
│  쿼터니언 압축     │    3 MB        │     85%        │
│  포지션 양자화     │    2.5 MB      │     87.5%      │
│  전체 적용         │    1~2 MB      │     90~95%     │
└────────────────────┴────────────────┴────────────────┘

Part 6. 오디오 크기 분석

오디오 파일은 얼마나 커?

오디오는 샘플레이트, 비트뎁스, 채널 수, 길이로 크기가 결정돼.

// 오디오 PCM(무압축) 크기 계산 // 크기 = 샘플레이트 × 비트뎁스/8 × 채널 수 × 초 // CD 품질 (44.1kHz, 16bit, Stereo) // 1초: 44100 × 2 × 2 = 176,400 bytes ≈ 172 KB/sec // 1분: 172 KB × 60 ≈ 10.3 MB // 고품질 (48kHz, 24bit, Stereo) // 1초: 48000 × 3 × 2 = 288,000 bytes ≈ 281 KB/sec // 1분: 281 KB × 60 ≈ 16.9 MB // 모바일 최적화 (22kHz, 16bit, Mono) // 1초: 22050 × 2 × 1 = 44,100 bytes ≈ 43 KB/sec // 1분: 43 KB × 60 ≈ 2.6 MB size_t CalculateAudioSize( int sampleRate, // 44100, 48000, 22050 등 int bitDepth, // 16, 24, 32 int channels, // 1=mono, 2=stereo float seconds ) { return sampleRate * (bitDepth / 8) * channels * seconds; }
오디오 압축은 어떻게 해?

오디오 압축은 손실(Lossy)과 무손실(Lossless)로 나뉘어.

게임에서 BGM과 SFX를 다르게 처리하는 이유는?

BGM은 길고 한 번에 하나만 재생해서 스트리밍으로 처리하고,

SFX는 짧고 동시에 여러 개 재생해야 해서 메모리에 미리 로드해둬.

BGM vs SFX 처리 방식:

┌──────────────────────────────────────────────────────────────────┐
│  BGM (스트리밍 방식)                                              │
│                                                                  │
│  파일 [====================================]  크기: 5MB          │
│           ↓ 실시간으로 조금씩 읽음                               │
│  버퍼 [==]  ← 64KB~256KB 버퍼만 메모리 사용                     │
│           ↓ 디코딩 후 재생                                       │
│  출력 [♪♪♪]                                                      │
│                                                                  │
│  장점: 메모리 적게 사용 (수 KB~수백 KB)                          │
│  단점: 디스크 I/O 지속 발생, 약간의 지연                         │
└──────────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────────┐
│  SFX (프리로드 방식)                                              │
│                                                                  │
│  파일들:                                                         │
│  sword_hit.wav  [=]     10KB    →  메모리 [=]                   │
│  explosion.wav  [==]    50KB    →  메모리 [==]                  │
│  footstep.wav   [=]     5KB     →  메모리 [=]                   │
│                                                                  │
│  전부 메모리에 디코딩된 PCM으로 로드                             │
│  → 즉시 재생 가능, 동시 재생 가능                                │
│                                                                  │
│  장점: 지연 없음, 동시 다중 재생                                 │
│  단점: 메모리 많이 사용                                          │
└──────────────────────────────────────────────────────────────────┘

일반적인 메모리 사용량:
- BGM 스트리밍 버퍼: 64KB ~ 512KB
- SFX 풀 전체: 20MB ~ 100MB (게임 규모에 따라)
- 보이스 (스트리밍): 256KB ~ 1MB 버퍼

셰이더는 어때?

셰이더는 소스 코드는 작지만 컴파일된 바이너리가 플랫폼마다 다르게 필요해.

Part 10. 에셋 버짓(Budget) 설계

게임 개발할 때 에셋 용량을 어떻게 계획해?

에셋 버짓을 정해서 각 팀(캐릭터, 배경, UI 등)에 할당량을 배분해야 해.

// 에셋 검증 시스템 class AssetBudgetValidator { public: struct BudgetRule { AssetType type; size_t maxSizeBytes; int maxTextureSize; int maxPolyCount; }; std::vector<BudgetRule> rules = { // 캐릭터 텍스처: 최대 2048, 총 50MB { CHARACTER_TEXTURE, 50 * 1024 * 1024, 2048, 0 }, // 배경 텍스처: 최대 1024, 총 20MB { ENVIRONMENT_TEXTURE, 20 * 1024 * 1024, 1024, 0 }, // 캐릭터 메시: 최대 50K 폴리곤 { CHARACTER_MESH, 0, 0, 50000 }, // 배경 메시: 최대 10K 폴리곤 { ENVIRONMENT_MESH, 0, 0, 10000 }, }; ValidationResult Validate(const Asset& asset) { for (const auto& rule : rules) { if (asset.type == rule.type) { if (asset.sizeBytes > rule.maxSizeBytes) return { false, "Size budget exceeded" }; if (asset.textureSize > rule.maxTextureSize) return { false, "Texture too large" }; if (asset.polyCount > rule.maxPolyCount) return { false, "Too many polygons" }; } } return { true, "OK" }; } // CI/CD에서 자동 검사 void ValidateOnCommit(const std::vector<Asset>& changedAssets) { for (const auto& asset : changedAssets) { auto result = Validate(asset); if (!result.passed) { RejectCommit(asset.path, result.message); } } } };

Part 11. 실전 최적화 체크리스트

에셋 최적화할 때 뭘 확인해야 해?

에셋 타입별로 체크리스트를 만들어서 검토해야 해!

에셋 최적화 체크리스트:

☑ 텍스처 체크리스트
  □ 필요 이상으로 크지 않은가? (멀리서만 보이는데 4K?)
  □ 적절한 압축 포맷 사용? (BC7/ASTC)
  □ Mipmap 생성됨?
  □ 알파 채널 꼭 필요? (BC1이면 절반 용량)
  □ 중복 텍스처 없음? (틴팅으로 대체 가능?)
  □ Power of 2 크기? (512, 1024, 2048...)
  □ 아틀라스로 합칠 수 있음?

☑ 메시 체크리스트
  □ LOD 세팅 적절? (거리별 폴리곤 감소)
  □ 보이지 않는 면 제거됨? (바닥에 붙은 면 등)
  □ 버텍스 압축 적용?
  □ 중복 버텍스 병합됨?
  □ 배칭 가능한 오브젝트 합쳐짐?
  □ 오클루전 컬링 설정됨?

☑ 애니메이션 체크리스트
  □ 키프레임 최소화됨?
  □ 필요 없는 본 애니메이션 제거?
  □ 압축 적용됨?
  □ 블렌딩으로 재사용 가능한 부분 분리?
  □ 프레임레이트 적절? (모든게 60fps일 필요 없음)

☑ 오디오 체크리스트
  □ BGM은 스트리밍 설정?
  □ SFX는 적절한 길이? (3초 이상 필요?)
  □ 모노로 충분한 것에 스테레오 사용 안함?
  □ 샘플레이트 적절? (효과음에 48kHz 불필요)
  □ 압축률 적절? (OGG 128~192kbps)
  □ 불필요한 침묵 구간 제거?

☑ 공통 체크리스트
  □ 사용하지 않는 에셋 정리?
  □ 개발용 고해상도 원본 정리?
  □ 플랫폼별 최적화 버전 준비?
  □ 에셋 번들링 전략 검토?

핵심 정리

  • 텍스처가 50~70%로 가장 큰 비중 → 최적화 1순위
  • 4K 텍스처 = 64MB (RGBA), BC7 압축 후 16MB
  • 텍스처 크기 공식: 가로 × 세로 × 채널 × 바이트
  • Mipmap은 1.33배 메모리 사용하지만 성능+품질 향상
  • 메시: 버텍스당 32~68 bytes, LOD로 90% 이상 절약 가능
  • 애니메이션: 압축으로 90~95% 절약 가능
  • 오디오 BGM은 스트리밍, SFX는 프리로드
  • 비디오는 반드시 스트리밍 (메모리는 버퍼만 사용)
  • 플랫폼별 에셋 크기가 4~10배 차이날 수 있음
  • 에셋 버짓을 정하고 CI/CD에서 자동 검증하기
