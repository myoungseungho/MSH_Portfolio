이동 복제 & 클라 예측 — UE에서 가장 어려운 곳

CharacterMovementComponent: 우리가 #1에서 본 예측/보정의 실제 구현

30초 요약

캐릭터 이동은 '고빈도 + 물리 + 예측'이라 UE 네트워크에서 가장 까다로워.

클라가 입력을 즉시 예측 적용 + SavedMoves에 저장 → 서버에 보냄(ServerMove) → 서버가 권위로 시뮬 → 어긋나면 ClientAdjustPosition으로 보정.

이게 우리가 Ch(#1) '클라 예측 & 서버 보정'에서 본 것의 UE 실제 구현이야.

Part 1. 왜 이동이 제일 어렵나

체력 복제는 쉬웠는데 이동은 왜 어려워?

세 가지가 겹쳐. ① 고빈도(매 프레임 바뀜) ② 물리(충돌·중력·경사) ③ 예측(핑을 숨기려 클라가 미리 움직임).

체력은 가끔 바뀌는 숫자지만, 이동은 매 순간 바뀌고 서버·클라가 같은 물리를 따로 굴려야 해 — 그래서 어긋남이 필연이고, 보정이 필수야.

복습: 예측 + 보정이 뭐였지?

클라가 서버 응답을 안 기다리고 내 화면에서 먼저 움직이고(예측), 서버 확정과 어긋나면 그 위치로 되돌린 뒤 그 사이 입력을 다시 적용(보정/replay).

아래 위젯은 #1과 같은 거야 — 핑을 올리며 ① 예측없음 ② 예측만 ③ 예측+보정을 비교해봐.

💭 잠깐, 이런 생각 들지 않아?
이동을 클라가 100% 결정하면 안 돼? 어차피 화면은 클라잖아
클라가 결정 = 스피드핵·텔레포트핵 즉시 통함. 서버 권위가 깨지면 게임 전체 권위가 깨져 — 데미지·아이템 위치 다 클라 말 듣게 됨. 그래서 "화면은 클라가 그려도 결정은 서버가"라는 분리가 필수. 단일 플레이어 게임은 클라가 다 결정해도 OK, 멀티는 절대 안 됨.

💭 잠깐, 이런 생각 들지 않아?
예측은 내 캐릭만? 다른 사람 캐릭은 어떻게?
내 캐릭만 예측, 남 캐릭은 보간(Ch3 영역). 받은 위치를 부드럽게 이어 그리지 예측 안 함 — 남의 입력을 모르니까. 그래서 내 건 즉각, 남은 약간 과거지만 부드러움. "내가 본 적 위치"와 "서버의 적 위치"가 다른 게 그래서, 지연 보상(히트 되감기)이 그 차이를 메워.

Part 3. UE의 이동 사이클 — SavedMoves

UE는 이걸 정확히 어떻게 해?

클라가 입력으로 캐릭터를 움직일 때마다, 그 '입력(SavedMove)'을 버퍼에 저장하고 동시에 서버에 ServerMove로 보내.

서버는 받은 입력으로 권위 있게 시뮬한 뒤, 결과가 클라 예측과 맞으면 'ACK'(여기까지 OK), 어긋나면 ClientAdjustPosition으로 '진짜 위치는 여기야'를 보내.

보정 받으면 클라는?

그 확정 위치로 되돌리고(롤백), 아직 서버가 ACK 안 한 SavedMoves를 그 위에서 다시 적용(replay)해. 그래서 보정이 와도 '최근 입력'은 살아남아 — 그냥 옛 위치로 뚝 떨어지지 않아.

ACK된 SavedMove는 버퍼에서 지워. 이 버퍼가 곧 '되돌릴 수 있는 입력 기록'이야.

[UE 이동 사이클] 클라: 입력 → 즉시 이동(예측) + SavedMoves에 저장 ──ServerMove──▶ 서버 서버: 권위 시뮬 → 맞으면 ACK / 틀리면 ClientAdjustPosition ──▶ 클라 클라: (보정 시) 확정 위치로 롤백 → 미ACK SavedMoves replay ACK된 move는 버퍼에서 제거
SavedMoves Replay — 보정 받으면 안에서 일어나는 일

"보정이 와도 최근 입력은 살아남는다"는 어떻게 가능한지, 클라 버퍼 상태를 시간순으로 펴봐. 예: 핑 100ms, 클라가 t=0에 입력 #100을 보냈는데 서버가 t=100에 시뮬해보니 다른 결과를 내고 ClientAdjustPosition을 보냄 (t=200에 클라 도착).

시각클라 SavedMoves 버퍼화면 위치일어난 일
t=0[#100](예측) x=10입력 #100 발생 → 즉시 적용 + ServerMove 송신
t=50[#100, #101]x=20입력 #101 추가, 예측 계속
t=100[#100, #101, #102]x=30입력 #102, 서버는 이제 #100 처리 시작
t=200[#100, #101, #102, #103]x=40서버에서 ClientAdjustPosition(after #100, x=5) 도착!
t=200
(직후)		[#101, #102, #103]
(#100 제거)		x=5로 롤백 → replay
#101 적용 → x=15
#102 적용 → x=25
#103 적용 → x=35		되돌리고 미ACK 입력 재적용

핵심: 보정 받았지만 "그 사이 사용자가 한 행동(#101~#103)"은 다 살아남아. 사용자 입장에선 한순간 위치가 살짝 튀는 정도로 보이고, 누른 키는 다 반영됐어.

이게 안 되면 보정 = 옛 위치로 뚝 떨어짐 + 그 사이 입력 무효 → "고무줄(러버밴드)"이 심해. SavedMoves 덕분에 그 사이 행동이 손실되지 않아.

💭 잠깐, 이런 생각 들지 않아?
이 사이클이 매 프레임 다 도는 거야? 너무 비싸지 않아?
응 매 프레임 도는데 — 각 단계가 짧아서 60fps 안에 다 들어가. SavedMoves 추가는 O(1), ServerMove 전송은 한 패킷에 묶임, replay도 보통 1~10개 입력만 다시 적용. 보정이 자주 일어나면 비용 누적되지만 그땐 다른 문제(네트워크 불안정)가 먼저야.

Part 4. 우리 클릭 이동 vs UE 물리 이동

항목조선협객전 (우리)언리얼
이동 방식클릭 목적지 → 서버 경로 이동물리 기반(가속·충돌) 실시간
예측 필요성낮음(목적지 방식이라 덜 민감)필수(매 프레임 입력)
보정서버 위치로 스냅(가끔)ClientAdjustPosition + replay
입력 기록거의 불필요SavedMoves 버퍼
왜 우리는 예측이 덜 절박했지?

클릭 이동은 '목적지'를 보내고 서버가 경로를 도는 구조라, 입력이 연속적이지 않아 약간의 지연을 덜 느껴. 그래서 우리는 무거운 예측/SavedMoves 없이도 버텼어.

반대로 UE의 주 무대인 액션·FPS는 매 프레임 입력이라 예측이 없으면 게임이 안 돼 — 그래서 CharacterMovement가 이 복잡한 사이클을 엔진에 내장한 거야.

UE 사이클SavedMoves / ServerMove / ClientAdjustPosition

UE 이동 사이클의 세 주역. SavedMoves는 클라의 미ACK 입력 버퍼, ServerMove는 입력을 서버로 보내는 RPC, ClientAdjustPosition은 서버가 보내는 보정 RPC야.

// 클라: 입력 발생 시 FSavedMove_Character NewMove; NewMove.SetMoveFor(this, DeltaTime, Acceleration, ClientData); ClientData->SavedMoves.Add(MakeShared<FSavedMove_Character>(NewMove)); // 클라 → 서버 (자동) ServerMove(TimeStamp, NewAccel, ClientLoc, ...); // 서버: 시뮬 후 결과가 클라 예측과 다르면 ClientAdjustPosition(TimeStamp, NewLoc, NewVel, ...); // 클라: 받으면 롤백 → 미ACK SavedMoves replay ClientUpdatePositionAfterServerUpdate();
우리 서버

클릭 목적지 한 번 보내고 서버가 경로 계산. 입력 기록 거의 불필요.

언리얼

매 프레임 입력을 SavedMoves에 쌓고 ServerMove로 전송. 어긋나면 ClientAdjustPosition으로 롤백·replay.

이 사이클이 UE 네트워크의 가장 복잡한 부분. UCharacterMovementComponent가 다 해줘서 보통은 신경 안 써도 되지만, 커스텀 이동(벽 타기 등) 만들면 직접 다뤄야 함.

💭 잠깐, 이런 생각 들지 않아?
SavedMoves가 끝없이 쌓이면 메모리 터지는 거 아냐?
일정 상한(예: 256개)을 두고 넘으면 오래된 것부터 강제 폐기 + 클라 위치를 서버 상태로 재동기. 평소 정상 핑이면 ACK가 빨라 버퍼는 ~10개 안정 상태. 문제는 심한 랙·끊김 — 그땐 차라리 연결을 끊고 다시 붙는 게 안전해.
서버랑 어긋날 때 무조건 서버가 맞아? 클라가 옳을 수도 있잖아
무조건 서버 권위. 클라는 핑·물리 오차·심지어 조작 가능성까지 있어서, 서버가 진실로 통일. 그래서 가끔 사용자가 "분명 점프했는데 안 점프해진" 답답함이 생기는 거야 — 그게 서버 권위의 대가야. 정 답답하면 클라 예측을 더 정교히 해서 어긋남 자체를 줄이는 게 답.

Part 5. 실제로는? (클래스)

핵심 클래스/함수는?

UCharacterMovementComponent가 전부 담당해. 클라에서 FSavedMove_Character에 입력을 저장하고, ServerMove(또는 압축된 ServerMoveDual 등)로 서버에 전송.

서버는 시뮬 후 ClientAckGoodMove(맞음) 또는 ClientAdjustPosition(보정)을 보내고, 클라는 ClientUpdatePositionAfterServerUpdate에서 롤백+replay를 수행해.

남의 캐릭터는?

내 캐릭터는 이렇게 예측/보정하지만, 남의 캐릭터는 '받은 위치'를 부드럽게 보간(NetworkSmoothing)해서 그려. 내 것은 예측, 남은 보간 — 이 분리가 핵심이야 (보간은 틱레이트 챕터 영역).

💭 잠깐, 이런 생각 들지 않아?
커스텀 이동(벽 타기, 그래플링) 만들면 다 다시 짜야 해?
CharacterMovementComponent를 상속해서 새 MovementMode 추가하는 게 정석. SavedMoves에 추가 데이터(예: 그래플 타깃) 직렬화하고, 서버 검증 로직도 같이. UE 액션·플랫포머 게임이 다 이런 식 — 엔진 골격은 유지하고 모드만 확장.

핵심 정리

  • 이동이 제일 어려움 = 고빈도 + 물리 + 예측이 겹침
  • 사이클: 예측 이동 + SavedMoves 저장 → ServerMove → 서버 권위 시뮬 → ACK / ClientAdjustPosition
  • 보정 = 확정 위치로 롤백 후 미ACK SavedMoves replay → 최근 입력 보존
  • 우리(클릭이동)는 예측 덜 절박, UE(물리이동)는 필수 → CharacterMovement에 내장
  • 내 캐릭터=예측/보정, 남의 캐릭터=보간(NetworkSmoothing)

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 서버 ACK가 느리면 SavedMoves가 무한히 쌓여?

서버가 ACK한 move는 즉시 버퍼에서 지워서 평소엔 안 쌓여. 문제는 심한 랙 상황.

[정상 vs 랙 상황] 정상: 클라 입력 → SavedMoves[100, 101, 102, ...] 서버 ACK("100 OK") → SavedMoves 정리 버퍼 크기: ~10개 안정 랙 (3초 멈춤): 서버 ACK 안 옴, 입력은 계속 SavedMoves: [100..280] (180개) 메모리 슬금슬금 증가

대응:

  • 상한 설정: 버퍼가 일정 크기(예: 256) 넘으면 가장 오래된 것부터 강제 폐기 + 클라 로컬을 서버 상태로 재동기.
  • 타임아웃: ACK 없이 N초 지나면 연결 끊김 처리. SavedMoves도 같이 정리.
Q. 보정 잦으면 차라리 예측을 끄는 게 나아?

아니. 예측이 자주 틀린다면 그건 예측 로직이 서버와 안 맞는 거지 예측 자체가 나쁜 게 아냐. 끄는 건 마지막 카드.

먼저 점검:

  • 물리 일치: 클라·서버가 같은 가속도·마찰·중력을 쓰나? 데이터 차이가 흔한 원인.
  • 입력 타이밍: SavedMove에 정확한 타임스탬프가 실리나? 시간이 어긋나면 같은 입력도 결과가 다름.
  • 비결정적 요소: 랜덤·물리 충돌이 양쪽에서 다르게 풀리면 어긋남.
예측 끄면 답답함이 핑만큼 직격 — 핑 100ms면 매번 100ms 늦게 반응. FPS는 사실상 불가능. 보정이 잦아도 끄는 것보단 보정을 부드럽게(smoothing) 하는 게 나아.
Q. 내가 본 남의 위치와 서버 위치가 다른데 밀치기는 누구 기준?

서버 기준이야. 내가 보는 남은 "보간된 과거 위치"라, 진짜 충돌은 서버가 자기 시간의 두 액터 상태로 판정해.

[밀치기 어긋남] 클라: 내 화면 — 남이 여기 있음 (RTT 전 위치) → "지금 밀쳤어!" RPC 전송 서버: 받았을 때 — 남이 이미 옆으로 이동 → 충돌 박스 안 닿음 → 안 밀침 클라: 화면엔 분명 밀쳤는데... ?

해결책 (지연 보상의 확장):

  • 되감기 판정: 서버가 클라가 본 시점으로 두 액터를 모두 되감아 충돌 판정. FPS의 히트 판정과 같은 원리.
  • 관용: 충돌 박스를 조금 키워 핑 차이를 흡수.
Q. 물리(넉백)도 서버·클라가 100% 똑같이 계산돼?

완벽히 같긴 어려워.

  • 부동소수점: CPU·컴파일러마다 미세하게 다른 결과.
  • 실행 순서: 서버는 30Hz, 클라는 60fps. 같은 입력도 시뮬 횟수가 달라 결과 미세 차.
  • 충돌 정렬: 동시 충돌 처리 순서가 다르면 결과 다름.

대처:

  • 결정적 물리: 고정 소수점·고정 틱·정해진 순서로 강제 일치. 비싸고 까다로움.
  • 서버 권위 + 보정: 다르면 서버가 옳고 클라를 끌어옴. 대부분 게임의 선택.
완전 일치를 노리는 게 아니라 "어긋남을 빠르게 흡수하는" 게 실전. 작은 어긋남은 보정으로 처리하고 큰 어긋남은 스냅으로.
