RPC — 함수처럼 보이는 원격 호출

호출은 한 쪽에서, 실행은 다른 쪽에서. Server / Client / Multicast

30초 요약

RPC = 함수를 호출하면 그 본문이 '다른 컴퓨터에서' 실행되는 것. 호출과 실행 위치가 다름.

3종: Server RPC(클라→서버 실행), Client RPC(서버→대상 클라 실행), Multicast(서버→모든 클라 실행).

우리 CM_/SM_ 핸들러가 곧 RPC. Server RPC는 반드시 검증(WithValidation) — 서버 권위.

Part 1. '함수처럼 보인다'는 게 뭐야

RPC가 패킷이랑 뭐가 달라?

본질은 같아 — 결국 패킷이 오가. 근데 코드에선 그냥 함수 호출처럼 보이게 감싼 거야. ServerFire() 하면 마치 로컬 함수 부르듯 쓰지만, 실제론 그게 네트워크 타고 서버에서 실행돼.

핵심 질문은 항상 '이 함수 본문이 어느 컴퓨터에서 도느냐'야.

어떻게 표시해?

UFUNCTION 매크로로: UFUNCTION(Server, Reliable, WithValidation) 같은 식. Server/Client/NetMulticast로 '어디서 실행'을, Reliable/Unreliable로 '꼭 도착 여부'를 정해.

RPC 한 줄 호출이 실제로 일어나는 일

코드에선 그냥 ServerFire(AimDir) 한 줄. 그런데 그 줄이 실행되는 머신은 따로 있어 — 그 사이에 일어나는 일을 5단계로 펴봐:

코드에선 안 보이는 단계들: 2(직렬화), 3(전송), 4(역직렬화)는 엔진이 자동. 개발자는 1(호출)과 5(실행)만 짜면 됨. 우리 서버는 이걸 손으로 다 짜야 함 — 패킷 구조 정의 + 송수신 + 핸들러 switch.

그래서 RPC가 "함수처럼 보인다"고 하는 거야 — 1과 5만 보이고 사이는 마법처럼 사라져 있어.

Part 2. 3종 RPC를 봐

방향을 직접 보자.

탭으로 ① Server ② Client ③ Multicast 를 바꿔봐. 호출이 출발하는 쪽과, '▶ 여기서 실행' 배지가 켜지는 쪽(=실제 실행 위치)을 비교해봐.

Server는 클라가 쏘지만 서버에서, Client는 서버가 쏘면 대상 클라에서, Multicast는 모든 클라에서 실행돼.

Part 3. Reliable / Validation

Reliable이랑 Unreliable은 언제 써?

Reliable = 꼭 도착(ACK·재전송). 결제·중요 이벤트. Unreliable = 잃어도 되는 잦은 것(이펙트 한 번).

Unreliable을 남발하면 빠지고, Reliable을 남발하면 큐가 막혀. 적재적소가 실력.

Server RPC에 검증이 왜 꼭 필요해?

클라가 호출하는 거라 '클라가 보낸 값'이 들어와. 그걸 그대로 믿으면 핵이 뚫려.

그래서 WithValidation으로 _Validate 함수에서 범위·소유권·상태를 검사하고, 실패면 연결을 끊어. 우리 CM_ 핸들러에서 클라 값 검증하는 것과 똑같아 (Ch15에서 더).

UE 매크로UFUNCTION(Server, Reliable, WithValidation)

함수 위에 한 줄 매크로만 박으면 그 함수가 RPC가 돼. Server=서버에서 실행, Reliable=재전송 보장, WithValidation=서버 진입 전 검증 함수 자동 호출.

UFUNCTION(Server, Reliable, WithValidation) void ServerFire(FVector AimDir); bool ServerFire_Validate(FVector AimDir) { // 범위·소유권·빈도 체크 return AimDir.IsNormalized(); } void ServerFire_Implementation(FVector AimDir) { // 실제 서버 로직 (검증 통과 시만 호출됨) }
우리 서버

switch(packetID) { case CM_FIRE: ... } 핸들러에서 직접 검증·실행.

언리얼

매크로 한 줄로 '함수 호출'처럼 보이게. _Validate 분리로 검증 강제.

Part 4. 우리와 대응

RPC실행 위치우리 대응
Server RPC서버CM_ 핸들러 (+ 검증)
Client RPC대상 클라 1명특정 클라에게 SM_
Multicast모든 클라BroadCast (SM_ 뿌리기)
한 줄로?

우리가 'CM_/SM_ + 핸들러 switch'로 손수 하는 걸, UE는 'UFUNCTION(Server/Client/Multicast)'로 함수처럼 보이게 추상화했어. 검증·신뢰성·서버 권위라는 본질은 완전히 같아.

핵심 정리

  • RPC = 함수 호출처럼 보이지만 본문은 '다른 컴퓨터'에서 실행 (호출 ≠ 실행 위치)
  • Server(클라→서버 실행) · Client(서버→대상 클라) · Multicast(서버→모든 클라)
  • Reliable/Unreliable = 꼭 도착 여부. 적재적소
  • Server RPC는 WithValidation 필수 — 클라 값 불신, 서버 권위
  • 우리 CM_(서버 실행)·SM_(클라 실행)·BroadCast(멀티캐스트)와 1:1

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 클라가 Server RPC를 초당 1000번 스팸하면?

두 단계로 막아.

  • 레이트 리밋: 한 RPC 함수마다 호출 빈도 상한. 예: "공격은 초당 5회까지". 초과는 무시.
  • 이상 행동 감지 + 끊기: 초당 1000번처럼 명백한 봇 행동은 즉시 연결 종료 + IP 블랙리스트.
[레이트 리밋 체크] UFUNCTION(Server, Reliable, WithValidation) void ServerFire(); bool ServerFire_Validate() { if (Now - LastFireTime < 0.2f) return false; // 5/s 상한 LastFireTime = Now; return true; // 통과 } // false → 검증 실패 → 연결 끊김
우리 서버 CLAUDE.md 안정성 9번이 정확히 이걸 강조 — "범위·소유권·상태·빈도" 4축 검증. 빈도 체크가 없으면 합법적인 RPC를 무한히 호출해서도 서버를 죽일 수 있어.
Q. Multicast가 unreliable이면 일부만 이펙트를 못 보잖아?

응, 그게 트레이드오프야. 보통은 그래도 unreliable이 맞아:

  • 이펙트는 "그 순간만" 의미. 1초 뒤 재전송돼 봐야 이미 늦음.
  • 한두 명 못 보는 비율이 게임 체감에 큰 영향 X.
  • reliable로 다 보내면 폭주 시 큐 폭발·HOL 위험.

예외:

  • 사망 연출·매치 종료 → reliable. 못 보면 게임 진행 자체에 문제.
  • 스킬 시전 시작 알림 → reliable(이걸 봐야 회피 가능).
  • 피격 이펙트·발자국·잎사귀 흔들림 → unreliable.
규칙: "이 이벤트를 놓치면 게임이 이상해지나?" Yes면 reliable, No면 unreliable. 의심되면 unreliable로 가는 게 안전(부하 적음).
Q. 큰 배열 파라미터는 매번 직렬화돼서 가? 비싸지 않아?

비싸. RPC 호출마다 인자가 매번 직렬화돼 패킷에 실려.

[큰 인자 RPC의 함정] ServerSendInventory(TArray Inventory); // 인벤 100칸 × 32B = 3200B // 호출마다 매번 3200B 송신 // 1초 10번 호출 → 32KB/s 한 명에서만

대안:

  • 복제로: 인벤토리 자체를 Replicated 상태로 두면 변경분만 전송(Push Model + Delta).
  • 참조만: 큰 데이터는 ID로 보내고 본체는 서버·DB에 두기. 클라는 ID로 조회.
  • 일부만: 정말 RPC로 가야 하면 변경된 슬롯만 인자에 담기.
RPC는 "이벤트 알림"에 적합하지 "상태 묶음 전송"엔 부적합. 큰 상태는 복제로 보내는 게 엔진이 기대하는 패턴.
Q. 대상 클라가 그 액터를 아직 복제 안 받았는데 Client RPC가 오면?

그 RPC는 버려지거나 보류돼. 액터가 클라에 없으면 어디서 함수를 실행할지 모르니까.

UE의 처리:

  • 그 액터가 아직 복제 큐에 있으면 RPC를 잠깐 보류하다 액터 도착 후 호출.
  • 관련성이 없어 영영 안 올 액터면 RPC는 그냥 폐기.
설계 교훈: 중요한 통지는 "그 클라가 보는 액터"에서만 보내. 안 보이는 적이 "맞았어!" RPC를 보내봐야 받는 사람이 처리 못 함. 그래서 Multicast는 "관련 있는 클라들"에만 가게 엔진이 알아서 추려.

실수 패턴: 매치 종료 알림을 "임의의 액터"에서 Multicast로 보냈는데 그 액터가 일부 클라에 관련 없어 RPC가 누락 — "왜 한 명만 매치 종료를 못 받지?"의 원인. 매치 상태는 bAlwaysRelevant 액터(GameState)에서 보내는 게 정석.
