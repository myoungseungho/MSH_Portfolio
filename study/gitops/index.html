GitOps

Git 저장소가 곧 인프라의 진실이 되는 운영 방식

Part 1: GitOps가 뭐야?

GitOps를 쉽게 설명해줘
비유: 레고 설명서

레고 설명서(Git): "1번 블록은 여기, 2번 블록은 저기"
실제 레고(인프라): 설명서대로 조립된 상태

GitOps = "설명서(Git)가 바뀌면 레고(인프라)도 자동으로 바뀐다"

설명서를 수정하면 → 누군가가 자동으로 레고를 재조립해줌!

GitOps의 핵심 아이디어: Git 저장소 실제 인프라 ┌─────────────┐ ┌─────────────┐ │ deployment │ │ 서버 3대 │ │ .yaml │ ═══════> │ 실행 중 │ │ replicas: 3 │ (자동 동기화) │ │ └─────────────┘ └─────────────┘ Git에 적힌 대로 = 실제 인프라 상태 Git을 수정하면 = 인프라가 자동으로 바뀜
Infrastructure as Code (IaC)랑 뭐가 달라?
구분 IaC GitOps
정의 인프라를 코드로 정의 Git이 유일한 진실의 원천
배포 방식 Push (명령어로 밀어넣기) Pull (에이전트가 가져감)
상태 관리 코드만 관리 코드 = 실제 상태
드리프트 수동 확인 자동 감지 & 복구
드리프트(Drift)란?
코드에는 "서버 3대"라고 적혀있는데, 누군가 콘솔에서 수동으로 4대로 늘림
→ 코드 ≠ 실제 상태 = "드리프트 발생!"
GitOps는 이런 드리프트를 자동으로 감지하고 원래대로 복구함

Part 2: 왜 GitOps가 필요해?

콘솔에서 클릭클릭하면 안 돼?
3개월 후의 비극

신입: "이 서버 설정 어떻게 되어 있어요?"
선배: "음... 그때 내가 했는데... 기억 안 나네"
신입: "문서 없어요?"
선배: "바빠서 못 적었어"
신입: "재현하려면요?"
선배: "콘솔 들어가서... 어디 클릭하고... 뭐였지?"

결과: 설정 재현 불가, 담당자 퇴사 시 지식 손실
GitOps가 있다면

신입: "이 서버 설정 어떻게 되어 있어요?"
선배: "Git 저장소 보면 돼. 전부 거기 있어"
신입: (Git 확인) "아 이렇게 되어 있네요!"
신입: "누가 왜 바꿨는지도 보여요!"

결과: 완벽한 이력 추적, 언제든 재현 가능
GitOps의 핵심 이점은?

1. 버전 관리

모든 변경 이력이 Git에 남음. 누가, 언제, 왜 바꿨는지 추적 가능

2. 코드 리뷰

인프라 변경도 PR(Pull Request)로! 동료가 검토한 후 머지

3. 롤백

문제 생기면 Git revert 한 번으로 이전 상태로 복구

4. 감사 로그

Git 커밋 이력 = 완벽한 감사 추적(Audit Trail)

Part 3: GitOps의 4가지 원칙

GitOps의 핵심 원칙이 뭐야?
GitOps 4대 원칙: 1. 선언적 (Declarative) ───────────────────── "서버 3대 실행해" (O) "서버 1대 추가해" (X) → 원하는 최종 상태를 선언. "어떻게"가 아니라 "무엇을" 2. Git = 진실의 원천 (Single Source of Truth) ─────────────────────────────────────────── Git에 있는 설정 = 실제로 있어야 할 상태 수동 변경 금지! 모든 변경은 Git을 통해서 3. 자동 동기화 (Automated Sync) ───────────────────────────── Git 변경 감지 → 자동으로 인프라에 반영 드리프트 발생 → 자동으로 복구 4. 풀 기반 (Pull-based) ───────────────────── 에이전트가 Git을 주기적으로 감시 변경 감지하면 Pull해서 적용
Push 방식이랑 Pull 방식이 뭐가 달라?
Push 방식 (전통적 CI/CD): ──────────────────────────── [개발자] → [CI 서버] ──push──> [쿠버네티스] │ CI가 클러스터 접근 권한 필요 보안 위험! Pull 방식 (GitOps): ───────────────────────────── [개발자] → [Git] <──pull── [ArgoCD] │ ↓ [쿠버네티스] 에이전트만 클러스터 내부에서 동작 외부 접근 권한 불필요 → 보안 강화!
구분 Push 방식 Pull 방식
누가 배포? CI 서버가 밀어넣음 에이전트가 당겨감
인증 CI에 클러스터 접근 권한 에이전트만 내부 접근
보안 외부 노출 위험 더 안전
드리프트 감지 어려움 자동 감지/복구

Part 4: ArgoCD로 GitOps 시작하기

ArgoCD가 뭐야?

ArgoCD는 가장 인기 있는 GitOps 도구입니다. 쿠버네티스 전용!

ArgoCD 동작 방식: ┌─────────────┐ │ Git Repo │ ← 여기에 K8s 설정 파일들 │ (YAML 파일) │ └──────┬──────┘ │ │ 주기적으로 감시 (3분마다) ↓ ┌─────────────┐ │ ArgoCD │ ← 쿠버네티스 안에서 실행 │ (에이전트) │ └──────┬──────┘ │ │ 변경 감지하면 자동 적용 ↓ ┌─────────────┐ │ Kubernetes │ ← 실제 서비스 실행 │ Cluster │ └─────────────┘
ArgoCD 설정 예시 보여줘
# argocd-application.yaml apiVersion: argoproj.io/v1alpha1 kind: Application metadata: name: my-game-server namespace: argocd spec: project: default # 어디서 가져올지 source: repoURL: https://github.com/company/game-server-k8s.git targetRevision: HEAD # 최신 커밋 path: k8s/production # 설정 파일 경로 # 어디에 배포할지 destination: server: https://kubernetes.default.svc namespace: game # 동기화 정책 syncPolicy: automated: prune: true # Git에서 삭제되면 클러스터에서도 삭제 selfHeal: true # 드리프트 발생하면 자동 복구 syncOptions: - CreateNamespace=true
주요 옵션 설명
- prune: true: Git에서 파일 삭제하면 클러스터에서도 삭제
- selfHeal: true: 누군가 수동으로 바꾸면 자동으로 원복
- targetRevision: HEAD(최신), 특정 태그, 브랜치 지정 가능

Part 5: GitOps 저장소 구조

Git 저장소는 어떻게 구성해?
# 추천 디렉토리 구조 game-server-k8s/ ├── base/ # 공통 설정 (모든 환경에서 공유) │ ├── deployment.yaml # 기본 Deployment │ ├── service.yaml # 기본 Service │ └── kustomization.yaml # Kustomize 설정 │ ├── overlays/ # 환경별 설정 (base를 오버라이드) │ ├── development/ # 개발 환경 │ │ ├── kustomization.yaml │ │ └── patch-replicas.yaml # replicas: 1 │ │ │ ├── staging/ # 스테이징 환경 │ │ ├── kustomization.yaml │ │ └── patch-replicas.yaml # replicas: 3 │ │ │ └── production/ # 프로덕션 환경 │ ├── kustomization.yaml │ ├── patch-replicas.yaml # replicas: 10 │ └── patch-resources.yaml # CPU, 메모리 더 많이 │ └── README.md
Kustomize가 뭐야?

Kustomize는 기본 YAML을 환경별로 "패치"하는 도구입니다.

# base/deployment.yaml (기본 설정) apiVersion: apps/v1 kind: Deployment metadata: name: game-server spec: replicas: 1 # 기본값은 1대 template: spec: containers: - name: game-server image: game-server:latest resources: requests: memory: "256Mi" cpu: "200m"
# overlays/production/patch-replicas.yaml (프로덕션 패치) apiVersion: apps/v1 kind: Deployment metadata: name: game-server spec: replicas: 10 # 프로덕션은 10대로!
Kustomize 동작: base/deployment.yaml (replicas: 1) + overlays/production/patch-replicas.yaml (replicas: 10) ↓ 최종 결과: replicas: 10 "기본 설정 + 환경별 패치 = 최종 설정"

Part 6: 실전 GitOps 워크플로우

실제로 어떻게 사용해?
일반적인 GitOps 워크플로우: 1. 개발자가 코드 수정 └─> 애플리케이션 Git 저장소에 푸시 2. CI 파이프라인 실행 └─> 빌드 → 테스트 → Docker 이미지 생성 └─> 이미지를 레지스트리에 푸시 (v1.2.3) 3. GitOps 저장소 업데이트 (자동 또는 수동) └─> deployment.yaml의 image 태그를 v1.2.3으로 변경 └─> PR 생성 → 리뷰 → 머지 4. ArgoCD가 변경 감지 └─> Git과 클러스터 비교 └─> 차이 발견! → 자동 동기화 5. 쿠버네티스에 배포 완료!
이미지 태그 업데이트는 어떻게 해?
# CI에서 자동으로 GitOps 저장소 업데이트 # .github/workflows/ci.yml jobs: build: runs-on: ubuntu-latest steps: - name: Build & Push Docker Image run: | docker build -t game-server:${{ github.sha }} . docker push registry/game-server:${{ github.sha }} - name: Update GitOps Repository run: | # GitOps 저장소 클론 git clone https://github.com/company/game-server-k8s.git cd game-server-k8s # 이미지 태그 업데이트 sed -i "s|image: game-server:.*|image: game-server:${{ github.sha }}|" \ overlays/production/deployment.yaml # 커밋 & 푸시 git commit -am "Update image to ${{ github.sha }}" git push
Image Updater 자동화
ArgoCD Image Updater를 사용하면 이미지 태그 업데이트도 자동화 가능!
새 이미지가 레지스트리에 푸시되면 자동으로 GitOps 저장소 업데이트

Part 7: GitOps 베스트 프랙티스

GitOps 잘 운영하는 팁 알려줘

1. 애플리케이션 코드와 인프라 코드 분리

app-repo: 애플리케이션 소스 코드
infra-repo: K8s 설정 파일 (GitOps 저장소)
→ 배포 주기가 다르고, 권한 관리도 따로

2. 환경별 브랜치 또는 디렉토리

main 브랜치 = production
또는 overlays/dev, overlays/staging, overlays/prod
→ 환경별 설정 명확히 분리

3. Sealed Secrets 사용

비밀번호, API 키를 Git에 넣으면 안 됨!
Sealed Secrets: 암호화된 시크릿만 Git에 저장
→ 클러스터 내부에서만 복호화

4. PR 리뷰 필수

인프라 변경도 코드 리뷰 대상!
main 브랜치 직접 푸시 금지
→ 실수 방지, 지식 공유

피해야 할 안티패턴은?
GitOps 안티패턴 TOP 4

1. kubectl로 직접 수정: "급해서 콘솔에서 바꿨어요" → 드리프트 발생, 추적 불가

2. 시크릿을 평문으로 커밋: 비밀번호가 Git 이력에 영원히 남음!

3. 하나의 저장소에 모든 환경: 개발 변경이 프로덕션에 영향 줄 수 있음

4. 자동 동기화 없이 수동 배포: GitOps의 핵심 이점을 포기하는 것

핵심 정리: GitOps

  • GitOps 정의: Git 저장소가 인프라의 유일한 진실의 원천
  • 4대 원칙: 선언적, Git = 진실, 자동 동기화, Pull 기반
  • 핵심 도구: ArgoCD (쿠버네티스용 GitOps 에이전트)
  • 저장소 구조: base + overlays (환경별 패치)
  • 이점: 버전 관리, 코드 리뷰, 쉬운 롤백, 감사 추적
  • 핵심: "Git을 바꾸면 인프라가 바뀐다" - 수동 변경 금지!
