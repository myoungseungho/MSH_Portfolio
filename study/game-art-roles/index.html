로아급 MMO에 아트 직군이 왜 이렇게 많아?

게임 회사의 아트 조직도 해부 — 10개 직군이 각각 뭘 하고, 왜 필요하고, AI는 어디까지 대체하나

Part 0. "그림 잘 그리는 사람 한 명이면 되는 거 아니야?"

나 서버 개발자인데, 아트 쪽은 진짜 하나도 몰라. 솔직히 "그림 잘 그리는 사람" 한 명 데려오면 캐릭터도 그리고 배경도 그리고 다 하는 거 아냐?

서버로 비유하면 이런 거야:

"코딩 잘하는 사람 한 명이면 DB도 짜고 네트워크도 짜고 보안도 하고 인프라도 하잖아?"

기술적으로 불가능하진 않지만, 전문성이 완전히 다른 영역이야.

[서버 조직과 아트 조직의 1:1 대응] 서버 팀 아트 팀 ────────────── ────────────── 아키텍트 (설계) ↔ 원화가 (설계) 서버 개발자 (구현) ↔ 3D 모델러 (구현) DBA (데이터 최적화) ↔ 텍스처 아티스트 (표면) 네트워크 엔지니어 ↔ 리거 (구조) DevOps (배포/운영) ↔ 테크니컬 아티스트 (최적화) 서버 개발자 1명이 DBA + DevOps 다 하면? → 할 수는 있는데, 품질이 떨어지고, 속도가 느려짐 아트도 마찬가지야.
그래도 인디 게임은 한 명이 다 하잖아. 왜 로아 같은 데는 팀이 이렇게 커?

규모의 문제야. 로아급 MMO에 들어가는 에셋 수를 보면:

[로아급 MMO의 아트 에셋 규모 (추정)] 캐릭터: · 플레이어블 클래스 20+개 (각각 고유 모델) · 클래스당 스킨/코스튬 10+벌 · NPC 500+명 · 몬스터/보스 300+종 배경: · 월드 맵 지역 30+개 · 던전 50+개 · 건물/구조물 1,000+개 · 소품 (나무, 돌, 통) 5,000+개 이펙트: · 스킬 이펙트 클래스당 20개 × 20클래스 = 400+개 · 환경 이펙트 200+개 UI: · 화면/패널 100+개 · 아이콘 2,000+개 애니메이션: · 캐릭터 동작 클래스당 50+ × 20 = 1,000+개 · 몬스터 동작 종당 10+ × 300 = 3,000+개 합계: 에셋 10,000개+ 한 사람이 하면? 에셋 하나에 평균 2일 → 20,000일 = 55년
55년... 그러니까 분업이 필요한 거구나. 그러면 구체적으로 어떤 직군들이 있어?

대형 게임 회사의 아트팀은 보통 10개 전문 직군으로 나뉘어. 하나씩 볼 건데, 각각 "이게 없으면 어떻게 되는데?"부터 시작할게.

Part 1. 검 하나가 화면에 나오기까지 — 7명이 손을 댄다

직군을 하나씩 보기 전에, 전체 흐름을 먼저 보여줄 수 있어? 에셋 하나가 만들어지는 과정?

좋은 순서야. 한 자루의 검이 게임 화면에 나타나기까지 누구의 손을 거치는지 따라가 보자.

[로아의 "마법사의 지팡이" 하나가 화면에 나오기까지] Step 1. 원화가 (Concept Artist) "이런 느낌의 지팡이를 만들 거야" → 산출물: 컨셉 이미지 + 3면도 (정면/측면/후면) → 다음 사람에게 "설계도"를 넘김 Step 2. 3D 모델러 (3D Modeler) "설계도 보고 입체로 만들게" → 산출물: 폴리곤으로 이루어진 3D 형상 (.fbx) → 이 시점에서는 회색 점토 덩어리처럼 보임 Step 3. 텍스처 아티스트 (Texture Artist) "표면에 색과 질감을 입힐게" → 산출물: PBR 텍스처 6장 (색상, 요철, 거칠기, 금속성, 그림자, 발광) → 이제 "보석이 박힌 금속 지팡이"처럼 보임 Step 4. 리거 (Rigger) ※ 지팡이 자체는 리깅 불필요 (정적 소품) ※ 하지만 캐릭터 손에 "부착 포인트" 설정은 필요 → 산출물: 캐릭터 본에 소켓(Socket) 추가 Step 5. 애니메이터 (Animator) "지팡이를 휘두르는 공격 동작 만들게" → 산출물: 시전 모션, 휘두르기 모션 (.anim) Step 6. 이펙트 아티스트 (VFX Artist) "지팡이 끝에서 마법 이펙트 나가게 할게" → 산출물: 파티클 시스템, 궤적 효과, 폭발 이펙트 Step 7. 테크니컬 아티스트 (TA) "이거 폴리곤 너무 많아서 프레임 떨어져. 최적화할게" → 산출물: LOD 설정, 셰이더 최적화, 드로우콜 절감
지팡이 하나에 7명이나? 진짜 그 정도야?

실제로는 더 많아. 라이팅 아티스트가 지팡이의 발광 효과가 주변 환경에 미치는 빛을 조정하고, UI 아티스트가 인벤토리에 표시될 아이콘을 만들고, 사운드 디자이너가 휘두르는 소리를 넣어.

이제 각 직군이 왜 필요한지 하나씩 뜯어보자.

Part 2. 원화가 (Concept Artist) — "설계도 없이 집을 지을 수 있어?"

원화가가 뭐야? 그냥 그림 그리는 사람 아니야?

서버로 비유하면 아키텍트야. 코드를 직접 짜는 게 아니라, "이런 구조로 만들 거야"라는 청사진을 그리는 사람.

원화 없이 바로 3D 모델 만들면 안 돼? 더 빠르잖아.

해보면 이렇게 돼:

[원화 없이 3D 모델 만들기 — 실제 상황] PM: "중세 기사 만들어주세요" 모델러 A: (머릿속 중세 기사) → 판금 갑옷 + 대검 모델러 B: (머릿속 중세 기사) → 사슬 갑옷 + 방패 모델러 C: (머릿속 중세 기사) → 가죽 갑옷 + 창 → 3명이 전혀 다른 걸 만듦 → 3개 다 "중세 기사"는 맞음 → 하지만 같은 게임에 넣으면? 통일감 제로 비유: 설계도 없이 건축업자 3명에게 "한옥 지어주세요" → 한 명은 전통 한옥, 한 명은 퓨전 한옥, 한 명은 한옥 카페 → 마을이 아니라 전시회가 됨
아... 그러니까 원화는 "이렇게 만들어라"라는 기준을 세우는 거구나?

정확해. 원화가의 핵심 역할은 "아직 존재하지 않는 것의 생김새를 결정하는 것"이야.

[원화가가 만드는 산출물] 1. 캐릭터 원화 → 정면/측면/후면 3면도 (3D 모델러의 설계도) → 표정 시트 (감정별 얼굴 변화) → 의상 변형 (계절별, 진화별) → 컬러 팔레트 (이 캐릭터에 쓸 색상 세트) 2. 배경 원화 → 지역 분위기 컨셉 ("이 던전은 이런 느낌") → 핵심 랜드마크 스케치 → 색감/분위기 가이드 3. 소품 원화 → 무기, 방어구, 탈것 디자인 → 소품의 소재감 지정 ("이건 금속", "이건 뼈") 4. 아트 바이블 (Art Bible) → 게임 전체의 비주얼 규칙서 → "우리 게임은 이런 색감, 이런 비율, 이런 분위기" → 모든 아트 직군이 이걸 기준으로 작업
서버의 API 스펙 문서 같은 거네? "이 규격대로 만들어라"

완벽한 비유야. 아트 바이블 = API 스펙 문서. 모든 에셋이 이 규격에 맞춰야 "한 게임"처럼 보이는 거야.

AI 관점에서 원화가

AI가 대체 가능한 부분: 컨셉 이미지 생성 자체는 Midjourney/Stable Diffusion이 매우 잘함. "중세 판타지 여전사, 붉은 망토, 은 갑옷" → 5초면 나옴.

AI가 대체 못하는 부분: "우리 게임의 20개 캐릭터가 전부 같은 세계관에 속해 보이게" 하는 일관성 유지. 이건 LoRA/ControlNet + 프롬프트 템플릿으로 접근해야 함.

서버 개발자가 챙겨야 할 것: 아트 바이블 = 프롬프트 템플릿. 이걸 먼저 정의해야 AI에게 일관된 지시를 내릴 수 있다.

Part 3. 3D 모델러 — "설계도를 입체로 만드는 사람"

원화가 그린 2D 그림을 3D로 만드는 사람이지? 그건 좀 직관적이네.

맞아. 근데 실제로는 3종류로 나뉘어. 캐릭터/배경/소품을 같은 사람이 잘 못 해.

왜? 3D 모델링이면 다 같은 기술 아니야?

서버로 비유하면: "코딩이면 다 같은 거 아니야?" 라고 하는 거랑 같아. DB 최적화하는 사람과 네트워크 코드 짜는 사람의 전문성이 다른 것처럼.

[3D 모델러가 3종류인 이유] 1. 캐릭터 모델러 만드는 것: 사람, 몬스터 등 "움직이는" 존재 핵심 기술: 인체 비율, 얼굴 디테일, 관절 부위 토폴로지 왜 어려운가: → 관절이 접힐 때 폴리곤이 찌그러지면 안 됨 → 팔꿈치 안쪽, 무릎 뒤쪽에 "에지 루프"를 넣어야 함 → 에지 루프 = 관절 주변에 폴리곤을 촘촘히 배치하는 것 → 이걸 모르면 팔 구부릴 때 팔꿈치가 뾰족하게 튀어나옴 비유: 관절이 움직이는 피규어를 만드는 것 vs 관절 없는 석고상을 만드는 것 → 완전히 다른 기술 2. 배경 모델러 (환경 아티스트) 만드는 것: 건물, 지형, 던전 구조 핵심 기술: 모듈러 디자인, 타일링, 대규모 스케일 왜 다른가: → 건물은 움직이지 않아서 관절 걱정 없음 → 대신 "모듈러"가 핵심 — 벽 조각 10개로 건물 100채를 만듦 → 레고 블록처럼 조합 가능한 조각을 만드는 기술 비유: 레고 블록 설계자 벽 블록 + 지붕 블록 + 창문 블록 = 무한 조합 3. 소품 모델러 (하드서피스 모델러) 만드는 것: 무기, 방어구, 가구, 물약 등 핵심 기술: 디테일, 소재 표현, 심미성 왜 다른가: → 움직이지도 않고, 모듈러도 아닌, "한 덩어리" 작품 → 대신 가까이서 볼 일이 많아서 디테일이 중요 → 보석의 커팅, 칼날의 날카로움, 가죽 끈의 꼬임 비유: 미니어처 피규어 장인
캐릭터 모델러가 가장 어렵겠네. "움직일 때 안 깨져야" 하니까.

맞아. 그래서 캐릭터 모델러가 가장 몸값이 비싸고, AI가 가장 못하는 영역이기도 해.

[3D 모델러의 핵심 작업 — 하이폴리 → 로우폴리 워크플로우] "왜 모델을 두 번 만들어?" Step 1: 하이폴리 (High-Poly) 모델 만들기 → 수백만 폴리곤 → 주름, 흉터, 실밥까지 다 표현 → 조각(Sculpting)이라고 부름 (ZBrush 사용) → 이대로 게임에 넣으면? GPU가 폭발 Step 2: 로우폴리 (Low-Poly) 모델 만들기 → 수천~수만 폴리곤 → 하이폴리의 "실루엣"만 유지 → 게임에서 실제로 쓰는 모델 Step 3: 노말맵 베이킹 → 하이폴리의 디테일을 "사진 찍어서" 로우폴리에 붙이기 → 로우폴리인데 하이폴리처럼 "보이게" 하는 트릭 → 빛을 속이는 것 (노말 = 표면의 방향 정보) 비유: 하이폴리 = 진짜 조각상 (100kg) 로우폴리 = 조각상 모양의 빈 틀 (2kg) 노말맵 = 틀 위에 붙인 조각상 사진 (빛에 따라 입체적으로 보임) 왜 이렇게 하나: 게임은 초당 60번 화면을 그려야 함 100만 폴리곤 캐릭터 100명 = 1억 폴리곤/프레임 GPU: "못 해" → 프레임 10 → 슬라이드쇼 1만 폴리곤 캐릭터 100명 + 노말맵 = 100만 폴리곤/프레임 GPU: "가능" → 프레임 60 → 스무스

AI 관점에서 3D 모델러

소품: Meshy AI, Tripo3D가 꽤 잘 만듦 (75%). 정적이라 토폴로지 문제가 덜 중요.

배경: 모듈러 조각은 AI가 만들 수 있지만, "조합 규칙"은 인간이 정해야 함. 프로시저럴 생성(Houdini)과 결합하면 강력.

캐릭터: AI가 가장 약한 영역. 관절 토폴로지가 지저분하면 애니메이션에서 터짐. 스타일라이즈(만화풍)면 그나마 괜찮.

서버 개발자 포인트: "하이폴리 → 로우폴리 → 노말맵 베이킹" 이 3단계를 알아야 AI 에이전트에게 올바른 포맷으로 지시할 수 있다.

Part 4. 텍스처/머티리얼 아티스트 — "민낯에 화장을 하는 사람"

3D 모델이 만들어졌으면 끝 아니야? 왜 따로 "색칠하는 사람"이 필요해?

3D 모델러가 만든 건 이거야:

[3D 모델의 실제 상태] 모델러가 넘겨주는 것: → 회색 점토 덩어리 (형태만 있음) → 색상 없음, 질감 없음, 반사 없음 → 금속 갑옷인지 가죽 갑옷인지 구분 불가 텍스처 아티스트가 해야 하는 것: → "이 부분은 녹슨 금속" → "이 부분은 낡은 가죽" → "보석 부분은 빛이 투과" → "이 문양은 마법으로 빛남" 비유: 모델러 = 흰색 마네킹을 만든 사람 텍스처 아티스트 = 마네킹에 피부, 옷 질감, 색상을 입히는 사람
그냥 색칠하면 되는 거 아니야? 왜 전문 직군이 필요해?

현대 게임은 "그냥 색칠"이 아니라 물리 법칙에 따라 칠해야 해. 이게 PBR이야.

[PBR 텍스처 — 왜 그림 1장이 아니라 6장이 필요한가] PBR = Physically Based Rendering (물리 기반 렌더링) "현실의 빛이 물체에 반응하는 원리를 그대로 시뮬레이션" 1. Albedo Map (색상) → 순수한 색상만. 빛/그림자 정보 없음 → "금속 원래 색은 회색, 가죽 원래 색은 갈색" → 옛날 게임: 이것만 있었음 (2000년대) 2. Normal Map (요철) → 표면의 울퉁불퉁함 정보 → 실제로 폴리곤을 추가하지 않고 "울퉁불퉁해 보이게" → 보라색/파란색 이미지 (방향 정보를 색으로 인코딩) 3. Roughness Map (거칠기) → 표면이 얼마나 매끄러운지 → 검은색 = 매끈 (거울처럼 반사) → 흰색 = 거침 (빛이 흩어짐) → "금속 갑옷의 광택" vs "가죽의 무광" 차이를 만듦 4. Metallic Map (금속성) → 금속인가 비금속인가 (0 또는 1) → 금속: 반사에 자기 색이 묻음 (금은 노란 반사) → 비금속: 반사가 하얀색 (플라스틱, 나무, 피부) 5. Ambient Occlusion Map (차폐) → 빛이 못 들어가는 틈새의 어두움 → 갑옷 이음새, 벨트 아래, 주름 안쪽 → "디테일의 깊이감"을 더해줌 6. Emissive Map (발광) → 스스로 빛나는 부분 → 마법 문양, 룬 문자, 눈동자 → 이게 있어야 "마법 무기"처럼 보임 왜 6장인가: 엔진의 셰이더가 이 6장을 조합해서 "모든 각도, 모든 조명"에서 올바르게 보이게 계산함 낮에 보면 금속이 번쩍이고, 밤에 보면 룬 문자만 빛나고, 비 오면 표면이 젖어서 반사율이 올라감 → 이게 전부 6장 텍스처의 조합으로 나오는 결과
와, 그냥 "색칠"이 아니라 물리 시뮬레이션용 데이터를 만드는 거네.

정확해. 텍스처 아티스트는 "그림쟁이"가 아니라 "물리 데이터 제작자"야. Substance Painter라는 도구로 3D 모델 위에 직접 칠하면서 6장의 맵을 동시에 만들어.

AI 관점에서 텍스처 아티스트

AI가 가장 잘하는 아트 영역 (90%). Midjourney/SD로 Albedo 생성 → Materialize 같은 도구로 나머지 5장 자동 생성 가능.

왜 잘하나: 텍스처는 결국 "2D 이미지"야. AI 이미지 생성이 가장 성숙한 분야.

서버 개발자 포인트: PBR의 6장 구조를 이해하면, AI에게 "seamless PBR stone wall, 4K, roughness 0.7" 같은 정확한 프롬프트를 줄 수 있다. "돌벽 텍스처 만들어줘"보다 10배 좋은 결과가 나옴.

Part 5. 리거 (Rigger) — "인형에 뼈를 심는 사람"

리깅이 뭔지는 대충 알아. 3D 모델에 뼈대 넣는 거지? 근데 왜 전문 직군이야?

질문을 바꿔볼게. "뼈대를 넣는 것"과 "잘 움직이는 뼈대를 넣는 것"의 차이가 뭘까?

[리깅의 3단계 — 뼈 심기가 전부가 아닌 이유] Step 1: 스켈레톤 생성 (Skeleton) → 뼈대 구조를 배치 (어깨-팔꿈치-손목-손가락) → 관절의 회전 축 설정 (팔꿈치는 한 방향으로만 접힘) → 이건 비교적 단순 (인간형은 표준 구조) Step 2: 스키닝 (Skinning) → 각 폴리곤이 "어떤 뼈에 얼마나 영향받는지" 설정 → 문제가 되는 곳: 관절 경계 예시 — 팔꿈치를 구부릴 때: 팔꿈치 근처 폴리곤은 "윗팔 뼈"와 "아랫팔 뼈" 둘 다 영향 윗팔 뼈 영향 70% + 아랫팔 뼈 영향 30% → 자연스럽게 구부러짐 ✅ 윗팔 뼈 영향 100% + 아랫팔 뼈 영향 0% → 접히는 부분이 칼로 자른 것처럼 꺾임 ❌ 이 비율을 정하는 게 "웨이트 페인팅" (Weight Painting) Step 3: 웨이트 페인팅 (Weight Painting) → 3D 모델 위에 "빨간색~파란색"으로 칠하기 → 빨간색 = 이 뼈에 100% 영향 → 파란색 = 이 뼈에 0% 영향 → 모든 관절마다 이걸 수작업으로 조정 이게 왜 전문 직군인 이유: 캐릭터 하나의 뼈 = 50~100개 각 뼈마다 웨이트 조정 = 수천 개의 폴리곤을 일일이 한 곳이라도 틀리면? 특정 동작에서 살이 뚫고 나옴
"살이 뚫고 나온다"는 게 뭐야?

캐릭터가 쪼그려 앉을 때 허벅지가 갑옷을 뚫고 나오거나, 팔을 올릴 때 어깨 옷이 몸 안으로 파고드는 거야. 웨이트가 잘못되면 발생하는 대표적인 버그. 게임에서 보면 진짜 무서워 보여.

[리거가 추가로 하는 것들] 4. IK 체인 (Inverse Kinematics) → "발이 바닥에 붙어있으면 다리가 자동으로 따라가게" → 계단을 올라갈 때 발이 바닥을 뚫지 않게 하는 기술 → 검을 집으면 손가락이 자동으로 감싸지게 하는 기술 5. 페이셜 리그 (Facial Rig) → 얼굴 표정을 위한 별도의 뼈대/컨트롤러 → 눈썹 올리기, 입꼬리 올리기, 눈 감기 등 → 블렌드쉐이프: 미리 만든 표정 사이를 섞는 방식 → "웃는 얼굴 50% + 놀란 얼굴 30%" = 살짝 놀라면서 웃는 표정 → AAA 게임은 표정 컨트롤러가 40개+ (얼굴 근육 하나하나) 6. 보조 본 (Helper Bone) → 실제 인체에 없는 가상의 뼈 → 근육이 불룩해지는 효과 (이두근) → 옷자락이 따라 움직이는 효과 → 가슴, 머리카락의 물리 시뮬레이션용
어... 생각보다 엔지니어링이네. "그림 그리는 사람"이랑은 완전 다른 스킬이잖아.

리거는 아트팀에서 가장 엔지니어링에 가까운 직군이야. 실제로 프로그래밍을 하는 리거도 많아 (MEL/Python으로 자동화 스크립트를 짜거든).

AI 관점에서 리거

인간형 = 거의 해결 (80%). Mixamo가 자동 리깅 + 스키닝 + 기본 웨이트를 해줌. 5개 관절 위치만 찍으면 30초 만에 완성.

비인간형 = 거의 불가 (20%). 드래곤 날개, 거미 8개 다리, 촉수 같은 건 학습 데이터 자체가 부족.

서버 개발자 포인트: 리거는 프로그래밍에 가까워서, Blender Python API(bpy)로 리깅 자동화 스크립트를 짤 수 있다. AI 에이전트가 가장 직접적으로 제어 가능한 아트 직군.

Part 6. 애니메이터 — "기술이 아니라 감각의 영역"

뼈대를 심었으니 이제 움직이면 되잖아. 애니메이터는 뭘 하는 거야?

질문을 하나 해볼게. "걷기"랑 "성큼성큼 걷기"의 차이를 코드로 어떻게 표현해?

[애니메이터가 하는 것 — "움직임"이 아니라 "감정"] 같은 "걷기"라도: 자신감 있는 기사: 보폭 크고, 상체 약간 뒤로, 무게감 있게 도둑: 보폭 작고, 상체 앞으로 숙이고, 가볍게 지친 전사: 다리를 끌고, 어깨 처지고, 간헐적으로 비틀거림 권위적인 왕: 느리고, 목을 세우고, 팔을 거의 안 흔듦 기술적으로는 전부 "걷기 애니메이션"이야. 하지만 캐릭터의 성격을 전달하는 건 이 미세한 차이. 이걸 만드는 사람이 애니메이터야. "정확하게 움직이게" 하는 건 리거. "느낌 있게 움직이게" 하는 건 애니메이터.
구체적으로 어떻게 만들어? 프레임 하나하나 손으로?

크게 3가지 방법이 있어:

[애니메이션 제작 방법 3가지] 방법 1: 키프레임 애니메이션 (전통) 0프레임: 팔이 내려간 상태 (키프레임 1) 10프레임: 팔이 올라간 상태 (키프레임 2) 20프레임: 팔이 다시 내려간 상태 (키프레임 3) → 중간 프레임은 소프트웨어가 자동 보간 (선형/곡선) → 핵심 포즈만 잡고 사이를 채우는 방식 장점: 정밀한 제어. 1프레임 단위로 타이밍 조정 가능 단점: 느림. 숙련 애니메이터가 "걷기" 하나에 1~2일 방법 2: 모션 캡처 (모캡) 배우가 센서 슈트를 입고 실제로 동작 수행 → 센서가 관절 위치를 초당 120번 기록 → 그 데이터를 3D 캐릭터에 적용 장점: 자연스러움. 실제 인간 동작이니까 단점: 장비 비쌈 (수천만~수억). 클린업 필요. 판타지 동작은 배우가 하기 어려움 (3m 점프를 어떻게?) 방법 3: 절차적 애니메이션 (Procedural) 코드로 실시간 생성 → "발이 바닥에 닿으면 다리 각도를 자동 계산" (IK) → "피격 방향으로 몸이 밀려남" (물리 반응) → "바람이 불면 머리카락이 흔들림" (시뮬레이션) 장점: 상황에 반응하는 동적 애니메이션 단점: "느낌"을 주기 어려움. 물리적으로 맞지만 "멋"이 없음 실제 게임은 3가지를 섞어 씀: 기본 동작: 모캡 (자연스러움) 또는 키프레임 (정밀함) 상호작용: 절차적 (발 IK, 시선 추적) 특수 동작: 키프레임 (스킬 모션, 과장된 연출)
전투 게임에서 애니메이션이 특히 중요한 이유가 있어?

"손맛"의 비밀이 여기 있어.

[전투 애니메이션의 비밀 — 프레임 경제학] 공격 하나를 분해하면: 선딜 (Anticipation): 3~5프레임 "때리기 전 준비 동작" 활성 (Active): 2~3프레임 "실제로 타격하는 순간" 후딜 (Recovery): 5~8프레임 "때린 후 자세 복귀" 이 비율이 "게임의 성격"을 결정함: 선딜 짧음 → 속전속결 느낌 (데빌 메이 크라이) 선딜 길음 → 묵직한 느낌 (다크 소울) 후딜 짧음 → 콤보 연결 가능 (격투 게임) 후딜 길음 → 신중한 플레이 유도 (몬스터 헌터) 로아의 경우: 스킬 시전 모션이 화려하면서도 빠름 → 선딜 3프레임 + 이펙트로 "시전 느낌" 보완 → 활성 프레임에 히트스톱(순간 정지) 0.05초 → 이 0.05초가 "때리는 느낌"을 만듦 핵심: 1프레임 = 1/60초 = 0.016초 이 0.016초 차이를 가지고 수십 번 조정하는 게 애니메이터의 일 "기술적으로 맞는 동작"과 "기분 좋은 동작"은 완전히 다른 것

AI 관점에서 애니메이터

기본 동작 (70%): Mixamo에 2,000개+ 무료 애니메이션. 걷기, 뛰기, 기본 공격은 즉시 사용 가능.

커스텀 동작 (40%): 폰 모캡(Move.ai)으로 직접 촬영 가능하지만, 클린업 필요. Cascadeur로 AI 보조 키프레임도 가능.

전투 감각 (10%): "기분 좋은 타격감"은 AI가 가장 못하는 영역. 프레임 단위 조정은 결국 수작업. 하지만 코드로 히트스톱/카메라 쉐이크를 넣는 건 프로그래머가 유리.

서버 개발자 포인트: 애니메이션 자체보다 "애니메이션 시스템"(스테이트 머신, 블렌딩, 리타겟팅)이 코드 영역. 여기서 에이전트 활용도가 높다.

Part 7. 이펙트 아티스트 (VFX) — "로아가 로아인 이유"

이펙트? 스킬 쓸 때 나오는 불꽃이나 번개 같은 거?

맞아. 근데 한 번 생각해봐. 로아에서 이펙트를 전부 끄면 어떻게 될까?

[이펙트 ON vs OFF — 같은 게임인가?] 이펙트 ON: 스킬 사용 → 화려한 빛줄기 + 폭발 + 잔상 + 화면 흔들림 → "와, 강해 보인다!" → 쾌감 → 계속 하고 싶음 이펙트 OFF: 스킬 사용 → 캐릭터가 칼을 휘두름 → 몬스터 HP가 줄어듦 → "...때린 건가?" → 밋밋함 → 5분 후 종료 이펙트가 담당하는 것: 1. 타격감 (피드백) : "때렸다"는 시각적 확인 2. 위력감 (파워 판타지) : "나 이렇게 강하다" 느낌 3. 가독성 (정보 전달) : "여기 위험 범위" "여기 안전 범위" 4. 분위기 (세계관) : 마법 세계라는 느낌 로아가 "로아"인 이유의 절반은 이펙트야. 스킬 시스템이 같아도 이펙트가 다르면 완전히 다른 게임이 됨.
이펙트 아티스트는 구체적으로 뭘 만들어?
[이펙트 아티스트의 산출물] 1. 스킬 이펙트 → 시전 이펙트: 손에서 마법진이 생기는 효과 → 발사체: 날아가는 화염구, 화살의 궤적 → 적중 이펙트: 적에게 맞았을 때의 폭발/스파크 → 지속 이펙트: 바닥에 깔리는 장판, 버프 오라 2. 환경 이펙트 → 날씨: 비, 눈, 안개, 모래 바람 → 자연: 물결, 풀 흔들림, 먼지, 나뭇잎 날림 → 건축: 횃불, 용광로, 연기, 수증기 3. UI 이펙트 → 레벨업 이펙트, 아이템 획득 빛줄기 → 대미지 숫자가 튀어나오는 효과 → 화면 전환 효과 4. 포스트 프로세싱 (화면 전체 효과) → 블룸: 밝은 부분이 번지는 효과 (빛이 눈부신 느낌) → 모션 블러: 빠른 동작에 잔상 → 컬러 그레이딩: 전체 색감 톤 조정 → 비네팅: 화면 가장자리 어둡게 (집중 효과) 이펙트 아티스트의 도구: → 파티클 시스템 (수천 개의 작은 이미지를 뿌림) → 셰이더 (수학으로 시각 효과를 만듦) → 메시 이펙트 (3D 오브젝트를 변형시키는 효과) → 이 3가지를 조합해서 하나의 스킬 이펙트를 완성
파티클이랑 셰이더가 뭔지 간단하게 설명해줘.
[파티클 vs 셰이더 — 이펙트의 두 기둥] 파티클 (Particle): "작은 이미지 수천 개를 흩뿌리는 것" 불꽃 이펙트 예시: 1. 불꽃 이미지(32x32 픽셀) 1장 준비 2. 이걸 초당 500개씩 발사 3. 각각 위로 올라가면서 작아지고 투명해짐 4. 수명 0.5초 후 사라짐 → 눈에는 "활활 타오르는 불꽃"으로 보임 서버 개발자 비유: 네트워크 패킷을 브로드캐스트하는 것과 비슷 각 파티클 = 패킷 (위치, 속도, 수명을 가짐) 파티클 시스템 = 패킷 스폰/관리 시스템 셰이더 (Shader): "픽셀 하나하나의 색을 수학 공식으로 계산하는 것" 디스토션(왜곡) 이펙트 예시: 1. 화면의 각 픽셀 좌표를 받음 2. sin(좌표 + 시간) 으로 좌표를 살짝 비틀어줌 3. 비틀어진 좌표의 색을 가져옴 → 눈에는 "아지랑이"나 "열기 왜곡"으로 보임 서버 개발자 비유: 데이터 변환 파이프라인과 비슷 입력(좌표) → 변환 함수(수학) → 출력(색상) GPU에서 수백만 픽셀을 병렬 처리

AI 관점에서 이펙트 아티스트

파티클: 텍스처 이미지 자체는 AI가 생성 가능 (불꽃, 연기 텍스처). 하지만 파티클 시스템의 파라미터 설정(속도, 수명, 곡선)은 수작업/코드.

셰이더: 코드(HLSL/GLSL)로 작성하므로 AI 에이전트가 직접 작성 가능! 서버 개발자에게 가장 유리한 영역.

포스트 프로세싱: 엔진 설정값(블룸 강도, 색온도 등)을 코드로 제어 가능. 에이전트 자동화 적합.

핵심 인사이트: 이펙트 = 파티클 텍스처(AI) + 파라미터 설정(코드) + 셰이더(코드). 3가지 중 2가지가 코드. 프로그래머가 가장 잘 커버할 수 있는 아트 직군.

Part 8. 라이팅 아티스트 — "같은 방인데 분위기가 다른 이유"

조명? 그냥 밝게 하면 되는 거 아니야?

사진 찍을 때 "셀카 조명"이 왜 있는지 알아? 같은 얼굴인데 조명만 바꾸면 완전히 다른 인상이 돼. 게임도 마찬가지야.

[라이팅이 게임 분위기에 미치는 영향] 같은 던전 모델에 조명만 다르게 설정하면: 설정 1: 따뜻한 주황 조명 + 부드러운 그림자 → "안전한 마을 느낌" (거점, 쉼터) 설정 2: 차가운 파랑 조명 + 날카로운 그림자 → "위험한 던전 느낌" (얼음 동굴) 설정 3: 붉은 조명 + 안개 + 깜빡임 → "보스방 느낌" (긴장감 극대화) 설정 4: 조명 거의 없음 + 캐릭터 발광만 → "공포 던전 느낌" (시야 제한) 모델, 텍스처, 모든 에셋이 동일함. 조명만 바꿨는데 완전히 다른 게임이 됨. 이게 라이팅 아티스트의 힘.
[라이팅 아티스트가 다루는 것들] 1. 직접 조명 (Direct Light) → 태양, 횃불, 마법 빛 등 "광원"을 배치 → 방향, 색상, 강도, 감쇠 범위 설정 2. 간접 조명 (Global Illumination / GI) → 빛이 벽에 반사되어 다른 면을 비추는 효과 → 빨간 벽 옆에 서면 얼굴에 붉은 빛이 은은하게 → 라이트맵: 이 반사광을 미리 계산해서 텍스처로 저장 → 계산 비용이 매우 크기 때문에 미리 "굽는" 것 3. 대기 효과 (Atmospheric) → 안개: 먼 거리의 물체가 뿌옇게 (깊이감) → 볼류메트릭 라이팅: 빛줄기가 보이는 효과 (성당 스테인드글라스) → 대기 산란: 하늘이 파란 이유, 석양이 붉은 이유를 시뮬레이션 4. 시간대 시스템 (Time of Day) → 아침/낮/저녁/밤에 따라 조명 자동 변화 → 태양 각도, 색온도, 별/달 전환 → 로아는 지역마다 시간대가 고정 (설계 선택) 5. 색감 연출 (Color Grading) → 전체 화면의 색조를 조정 → 따뜻한 톤 (마을) vs 차가운 톤 (던전) → 영화의 "색보정"과 같은 개념

AI 관점에서 라이팅 아티스트

설정값 기반: 라이팅의 대부분은 "숫자 파라미터"야. 위치(x,y,z), 색상(RGB), 강도(float), 감쇠(float). 전부 코드로 제어 가능.

자동화 가능: "이 지역은 던전이니까 차가운 파란 톤, GI 약하게" 같은 규칙을 정하면 에이전트가 일괄 적용 가능.

라이트맵 베이킹: 시간이 오래 걸리는 작업(수 시간). 배치로 돌려놓는 CI/CD 개념과 비슷. 자동화 적합.

서버 개발자 포인트: 라이팅 = 파라미터 + 규칙. 프로그래머 사고방식에 딱 맞는 영역. "분위기 감각"만 레퍼런스로 보완하면 됨.

Part 9. UI 아티스트 — "로아에 UI 화면이 몇 개인지 알아?"

UI는 프로그래머가 그냥 코드로 만들면 되는 거 아니야?

프로그래머가 만든 UI를 본 적 있어? 기능은 되는데 못 생겼어. 그게 왜 문제냐면:

[UI가 게임에서 차지하는 비중 — 생각보다 크다] 플레이어가 게임에서 보내는 시간: 전투 중 (3D 월드를 봄): 40% UI를 보고 있는 시간: 60% ← 더 많음! 왜?: 인벤토리 정리, 스킬 세팅, 장비 비교, 퀘스트 확인, 강화, 제작, 경매장, 우편, 길드 관리, 도감, 업적, 설정, 채팅, 파티 구성, 던전 매칭... MMORPG는 "UI 게임"이라고 할 정도로 UI가 많음. 로아급 MMO의 UI 화면 수 (추정): 메인 HUD: 1개 (체력바, 스킬바, 미니맵, 퀘스트) 인벤토리 계열: 5+개 (가방, 장비, 코스메틱, 보관함, 분해) 강화/제작: 5+개 (강화, 초월, 보석, 각인, 제작) 소셜: 5+개 (채팅, 파티, 길드, 친구, 우편) 컨텐츠: 10+개 (던전, 레이드, PvP, 항해, 모험) 상점: 5+개 (일반, 캐시, 경매장, 거래소) 시스템: 5+개 (설정, 키바인딩, 그래픽, 캐릭터 정보) 기타: 10+개 (도감, 업적, 카드, 수집, 이벤트...) 합계: 50+ 개의 고유 UI 화면 각 화면의 아이콘: 평균 20개 → 아이콘 1,000개+
[UI 아티스트가 하는 일] 1. 레이아웃 디자인 → 각 화면의 요소 배치 (어디에 뭘 놓을지) → 정보 계층 (중요한 것이 먼저 눈에 들어오게) → 반복 사용 패턴 (닫기 버튼은 항상 오른쪽 위) 2. 비주얼 디자인 → 프레임, 버튼, 슬롯의 "스킨" → 게임 세계관과 일치하는 UI 테마 → 로아: 금속 + 마법 느낌의 UI 프레임 3. 아이콘 디자인 → 스킬 아이콘, 아이템 아이콘, 버프 아이콘 → 작은 크기(64x64)에서도 구분 가능해야 함 → 등급별 색상 코딩 (일반=회, 고급=파, 영웅=보라, 전설=주황) 4. UI 애니메이션 → 버튼 호버 효과, 창 열림/닫힘 트랜지션 → 레벨업 연출, 아이템 획득 연출 → "기분 좋은 UI"는 이 미세한 애니메이션에서 옴 5. HUD (Heads-Up Display) → 전투 중 화면에 항상 보이는 정보 → 체력바, 마나바, 스킬 쿨다운, 미니맵 → "정보는 많되 시야를 가리지 않게" = 핵심 과제

AI 관점에서 UI 아티스트

아이콘 생성 (85%): Midjourney "fantasy sword icon, game UI, 64x64, transparent background" → 대량 생성 가능. 스타일 일관성만 잡으면 됨.

레이아웃 (코드 영역): UI 배치는 대부분 코드나 XML/JSON으로 정의. 에이전트가 직접 레이아웃 코드를 짤 수 있음.

UI 프레임/테마: 9-슬라이스(나인패치) 기법으로 프레임 이미지 몇 장이면 전체 UI 커버. AI로 기본 프레임 생성 가능.

서버 개발자 포인트: UI는 "코드 + 이미지"의 조합. 코드 비중이 높아서 프로그래머가 커버하기 가장 쉬운 아트 영역 중 하나.

Part 10. 테크니컬 아티스트 (TA) — "아트팀과 개발팀 사이의 통역사"

TA가 뭐야? 이름이 좀 모호한데.

서버 팀에 DevOps가 있지? 개발과 운영 사이를 잇는 사람. TA는 아트와 엔지니어링 사이를 잇는 사람이야.

[TA가 없으면 생기는 일] 아티스트: "캐릭터 만들었어요! 100만 폴리곤에 4K 텍스처 8장이요!" 프로그래머: "...그거 넣으면 프레임 5 나와요." 아티스트: "그럼 어떡해요? 저는 최적화를 모르는데." 프로그래머: "저는 어떤 폴리곤을 줄여야 할지 모르는데." (둘 다 멍하니 서로 쳐다봄) TA가 있으면: TA: "제가 이 모델의 등 뒤쪽 폴리곤을 50% 줄여도 안 보여요. 텍스처 3장은 아틀라스로 합치면 드로우콜 2개 줄일 수 있고요. LOD 3단계 만들면 멀리서 볼 때 자동으로 간단한 모델로 바뀌어요." 아티스트: "그렇게 하면 퀄리티 괜찮아요?" TA: "거의 차이 안 나요. 여기 비교 캡처요." → 아티스트의 퀄리티를 지키면서 프로그래머의 성능 요구를 충족
[TA가 하는 일 — 범위가 넓다] 1. 셰이더 개발 → 커스텀 머티리얼 제작 (물, 용암, 얼음, 홀로그램) → 아티스트가 "이런 느낌 원해요"라고 하면 → TA가 셰이더 코드로 구현 2. 에셋 최적화 → LOD 자동 생성 파이프라인 → 텍스처 압축 설정 → 드로우콜 최적화 (배칭, 인스턴싱) → 메모리 버짓 관리 ("이 지역은 VRAM 2GB까지") 3. 파이프라인 자동화 → DCC 도구(Maya/Blender)에서 엔진으로 에셋 전달 자동화 → 네이밍 규칙 검증 스크립트 → 텍스처 크기/포맷 자동 검증 → 파이프라인 = "아트 CI/CD" 4. 리깅/애니메이션 기술 지원 → 복잡한 리그 시스템 구축 → 천, 머리카락 물리 시뮬레이션 설정 → 절차적 애니메이션 시스템 5. 프로파일링 & 성능 모니터링 → GPU/CPU 병목 분석 → "이 씬에서 프레임 드랍이 왜 생기나?" → 서버의 쿼리 최적화와 완전히 같은 개념 한 줄 정리: TA = "아트 에셋이 엔진에서 잘 돌아가게 하는 엔지니어"
TA는 프로그래머에 가깝네. 아트팀인데 코딩을 하는 거잖아.

맞아. 그래서 서버 개발자인 너에게 TA 역할이 가장 자연스러워.

TA가 쓰는 도구: Python(Maya/Blender 스크립팅), HLSL/GLSL(셰이더), 프로파일링 도구. 전부 프로그래밍이야.

AI 관점에서 테크니컬 아티스트

가장 AI 에이전트 친화적인 직군. TA의 업무 80%가 코드/스크립트.

파이프라인 자동화: 에셋 검증, 포맷 변환, LOD 생성 — 전부 스크립트. AI 에이전트가 즉시 가능.

셰이더: HLSL/GLSL은 코드. AI 코딩 에이전트의 직접 영역.

프로파일링: 데이터 분석 + 원인 추적. 서버 디버깅과 동일한 사고 방식.

서버 개발자 포인트: 1인 개발에서 TA 역할은 "너 자신 + AI 에이전트"로 완전히 커버 가능. 오히려 가장 강점인 영역.

Part 11. 사운드 디자이너 — "눈을 감아도 게임이 보여야 한다"

사운드도 아트에 포함돼?

엄밀히는 별도 팀인 경우가 많지만, "감각적 경험"이라는 점에서 아트의 인접 영역이야. 그리고 1인 개발이면 어차피 너가 다 해야 하니까.

[사운드가 없는 게임 vs 있는 게임] 사운드 OFF: 검을 휘두름 → (무음) → 몬스터 HP 줄어듦 → "때린 건가?" (이펙트 없을 때와 같은 문제) 사운드 ON: 검을 휘두름 → "슈웅" + "퍽!" → 몬스터가 비틀거리며 "윽" → 타격감 200% 증가 사운드의 역할: 1. BGM (배경 음악) → 분위기 설정. 마을은 평화롭게, 보스전은 긴장감 있게 → 감정 유도. 슬픈 스토리에 슬픈 음악 2. SFX (효과음) → 피드백. 모든 행동에 청각적 확인 → 검 소리, 마법 소리, 발소리, 문 열리는 소리 3. Ambient (환경음) → 공간감. 숲에서 새소리, 던전에서 물방울 소리 → 이게 없으면 세계가 "죽어있는" 느낌 4. Voice (음성) → NPC 대사, 스킬 시전 보이스, 시스템 안내 → 캐릭터에 "인격"을 부여

AI 관점에서 사운드 디자이너

BGM (85%): Suno AI, AIVA가 장르/분위기별 음악 생성. 루프 가능한 게임 BGM도 가능.

SFX (70%): 기본 효과음은 라이브러리(freesound.org)에서 구하고, AI 오디오 생성 도구로 변형 가능.

Voice (80%): ElevenLabs, OpenAI TTS로 NPC 음성 생성. 감정 조절도 가능.

서버 개발자 포인트: 사운드는 "파일 재생 타이밍"이 핵심. 타이밍 제어는 코드 영역. 파일 자체는 AI가 생성하고, 언제 재생할지는 코드로.

Part 13. 결론 — "직군을 알면 에이전트가 보인다"

이 많은 직군을 알아서 뭐가 달라지는 건데?

각 직군의 "산출물"을 알면, AI에게 뭘 시켜야 하는지가 명확해져.

[Before vs After — 직군을 모를 때 vs 알 때] Before (직군을 모를 때): "AI야, 게임에 쓸 캐릭터 만들어줘" → AI가 2D 이미지를 줌 → "이걸 어떻게 게임에 넣지...?" After (직군을 알고 나서): Step 1: "원화 에이전트, 여전사 컨셉 3면도 만들어줘. 아트 바이블 기준: 셀 셰이딩, 따뜻한 색감, 판타지" Step 2: "모델링 에이전트, 이 3면도 기반으로 로우폴리 모델 생성. 폴리곤 15K, 인간형 표준 토폴로지" Step 3: "텍스처 에이전트, PBR 6장 생성. Albedo/Normal/Roughness/Metallic/AO/Emissive" Step 4: "리깅 에이전트, Mixamo 자동 리깅 적용. IK 체인: 발, 손" Step 5: "애니메이션 에이전트, Mixamo에서 기본 모션 세트 다운로드. 걷기/뛰기/공격/피격/사망" Step 6: "이펙트 에이전트, 공격 스킬 3개 이펙트 생성. 파티클 텍스처 + 셰이더 코드" Step 7: "TA 에이전트, LOD 3단계 생성 + 텍스처 아틀라스 최적화" → 각 단계가 명확하고, AI에게 구체적으로 지시 가능 → 서버 에이전트 시스템의 분석팀/구현팀처럼 "역할 분리"
서버 에이전트에서 "분석팀은 opus, 구현팀은 sonnet"처럼 나눈 거랑 같은 구조네?

정확해. 서버에서 했던 걸 아트에도 똑같이 적용하는 거야:

[서버 에이전트 ↔ 아트 에이전트 대응] 서버 에이전트 시스템 아트 에이전트 시스템 ───────────────── ────────────────── 분석팀 (opus) ↔ 원화 에이전트 (Midjourney) → 코드 흐름 분석 → 컨셉 이미지 생성 구현팀 (sonnet) ↔ 모델링 에이전트 (Meshy AI) → 코드 작성 → 3D 메시 생성 빌드/배포 (haiku) ↔ 파이프라인 에이전트 (Blender Python) → 빌드 실행 → 포맷 변환, 최적화, 엔진 임포트 도메인가드 (opus) ↔ 아트 디렉션 에이전트 → 사이드이펙트 검토 → 스타일 일관성 검증 핵심: 서버: 분석 → 구현 → 빌드 → 검증 아트: 원화 → 모델링 → 텍스처링 → 리깅 → 애니 → 이펙트 → 최적화 구조가 동일해. 파이프라인이 있고, 각 단계에 전문가(에이전트)가 있고, 핸드오프 프로토콜(산출물 포맷)이 있어. "어떤 에이전트에게 뭘 시킬지"를 알려면 "어떤 직군이 뭘 하는지"부터 알아야 해. 그래서 이 문서가 첫 번째인 거야.

규모의 함정 — "로아급"을 처음부터 노리면 안 된다

이 문서에서 로아를 예시로 든 건 "어떤 직군이 필요한지" 보여주기 위해서야.

실제로 1인 AI 개발을 시작할 때는: 에셋 100개짜리 게임 → 500개 → 1,000개 순서로 키워야 해.

10,000개 에셋을 Day 1부터 목표하면? 완성 못하고 번아웃됨. 서버도 마이크로서비스를 모놀리스부터 시작하는 것처럼.

서버 개발자의 숨은 강점

10개 직군 중 "코드가 핵심인 직군"이 몇 개인지 세어봐:

이펙트 (파티클+셰이더=코드), TA (전부 코드), UI (코드+이미지), 라이팅 (파라미터=코드), 사운드 (재생 로직=코드)

10개 중 5개가 코드 중심. 서버 개발자가 아트 직군의 절반을 자연스럽게 커버할 수 있다는 뜻.

나머지 5개(원화, 모델링, 텍스처, 리깅, 애니메이션)는 AI 도구가 커버하고.

결론: 서버 개발자 + AI = 10개 직군 대부분 커버 가능. "그림을 못 그린다"는 문제가 아니야.

핵심 정리 — 10개 아트 직군과 AI 전략

  • 원화가 — 설계도를 그리는 사람. AI 이미지 생성 + 아트 바이블(프롬프트 템플릿)으로 대체
  • 3D 모델러 — 설계도를 입체로 만드는 사람. 캐릭터/배경/소품 3종류. 토폴로지가 핵심 기술
  • 텍스처 아티스트 — 물리 데이터 제작자. PBR 6장. AI가 가장 잘하는 영역 (90%)
  • 리거 — 뼈를 심고 스키닝하는 사람. 인간형은 Mixamo로 거의 해결
  • 애니메이터 — "감각"의 영역. 기본 동작은 라이브러리, 전투 감각은 코드로 보정
  • 이펙트 아티스트 — 게임의 화려함. 파티클+셰이더 = 코드. 프로그래머가 가장 유리
  • 라이팅 아티스트 — 분위기 결정자. 전부 파라미터 기반. 코드로 자동화 가능
  • UI 아티스트 — 코드 UI + AI 아이콘. MMORPG는 "UI 게임"
  • TA — 아트와 엔지니어링 사이의 통역사. 서버 개발자의 최강 동맹
  • 사운드 — Suno AI + ElevenLabs로 80% 커버. 재생 타이밍은 코드
  • 핵심 전략 — 직군을 알면 에이전트를 설계할 수 있다. "뭘 시킬지"가 명확해진다
