할당 없이 무한히 돌려 쓰는 큐 — 링버퍼

고정 배열을 원처럼 돌려 쓰는 IOCP·로그·오디오의 단골 자료구조

30초 요약

링버퍼 = 고정 크기 배열을 '원'처럼 돌려 쓰는 큐. 끝에 닿으면 처음으로(wrap).

쓰기(W)·읽기(R) 포인터가 따로 돌고, 둘 사이가 쌓인 데이터. W가 R을 따라잡으면 가득참, R이 W를 따라잡으면 빔.

메모리 할당/해제 없이 재활용해 빠름 — IOCP 수신 버퍼·로그·오디오 스트림에 단골.

Part 1. 왜 '원'으로?

그냥 일반 큐 쓰면 안 돼?

일반 큐는 넣고 뺄 때 메모리 할당/해제나 원소 이동이 생겨. 초당 수만 번이면 그 비용이 커.

링버퍼는 고정 배열을 미리 잡아두고 포인터만 돌려 — 할당 0, 이동 0. 그래서 고빈도 입출력에 딱이야.

포인터 두 개로 어떻게?

쓰기 포인터(W)는 '다음에 쓸 칸', 읽기 포인터(R)는 '다음에 읽을 칸'. 생산자가 쓰면 W가 한 칸 전진, 소비자가 읽으면 R이 전진. 끝 칸 다음은 0번으로 돌아와.

W와 R 사이 구간이 '아직 안 읽은 데이터'야.

Part 2. 가득참 / 빔을 봐

포인터가 만나는 두 경우를 봐.

탭으로 생산/소비 속도를 바꿔봐. 초록 W, 주황 R.

생산이 빠르면 W가 R을 따라잡아 '가득참'(더 못 씀), 소비가 빠르면 R이 W를 따라잡아 '빔'(읽을 것 없음)이 돼.

정상상태

Part 3. 빈/참 구분과 단일 생산자-소비자

W==R이면 빈 거야 가득 찬 거야?

헷갈리는 지점이야. 'W==R = 빈 상태'로 정의하면, 가득 찬 걸 표현하려면 한 칸을 비워두거나(용량 N-1), 별도 count 변수를 둬.

이 시뮬은 count를 따로 세서 N까지 꽉 채워. 구현마다 '한 칸 희생 vs count 변수' 중 골라.

락 없이 쓸 수 있어?

생산자 1 + 소비자 1(SPSC)이면 락 없이도 안전하게 만들 수 있어 — W는 생산자만, R은 소비자만 건드리니까(메모리 배리어만 신경). 그래서 IOCP 워커↔로직 스레드 같은 1:1 전달에 락프리 링버퍼가 인기야.

생산자/소비자가 여럿(MPMC)이면 더 복잡한 동기화가 필요해.

핵심 정리

  • 링버퍼 = 고정 배열을 원처럼 돌려 씀(wrap). 할당/이동 0 → 빠름
  • W(쓰기)·R(읽기) 포인터가 따로 전진, 둘 사이가 데이터
  • 가득참 = W가 R 따라잡음, 빔 = R이 W 따라잡음
  • 빈/참 구분 = 한 칸 비우기 또는 count 변수
  • SPSC(1:1)는 락프리 가능 → IOCP·로그·오디오 단골
