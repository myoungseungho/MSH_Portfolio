NOLOCK은 만능이 아니다

WITH (NOLOCK)의 진짜 의미와 Dirty Read의 위험

Part 1. 자주 보는 코드

프로시저에서 이런 코드 자주 보이는데, NOLOCK이 뭐야?

우리 프로젝트에서 흔히 볼 수 있는 패턴이야.

SELECT level, exp, gold FROM TCharacter WITH (NOLOCK) WHERE charunique = @uid
"잠금 없이" 읽는다는 거야?

맞아. 다른 트랜잭션이 잠금을 걸어도 무시하고 읽겠다는 뜻이야.

그래서 빠르지. 대기 없이 바로 읽으니까.

그럼 항상 NOLOCK 붙이면 빨라지는 거 아니야?

거기에 함정이 있어.

Part 2. 잠깐, 잠금(Lock)이 뭐야?

왜 DB는 잠금을 걸어?

동시에 여러 명이 같은 데이터를 건드리면 문제가 생기니까.

[상황: 유저 A가 골드를 인출 중] 시간 →→→→→→→→→→→→→→→→→→→→→→→→→ 트랜잭션 A: BEGIN → 골드 읽기(1000) → 골드 차감(-500) → COMMIT ↑ 여기서 다른 사람이 읽으면? 트랜잭션 B: SELECT 골드 → ???
A가 아직 커밋 안 했는데 B가 읽으면?

두 가지 가능성이 있어:

1. 잠금 있음: B는 A가 끝날 때까지 대기

2. NOLOCK: B는 A의 "작업 중인 데이터"를 읽음

Part 3. Dirty Read가 뭐야?

"작업 중인 데이터"를 읽는 게 왜 문제야?

그 트랜잭션이 롤백되면?

[Dirty Read 시나리오] 트랜잭션 A: 골드 1000 → 500으로 UPDATE → 💥 에러! ROLLBACK! ↑ 트랜잭션 B (NOLOCK): SELECT 골드 = 500 ← 이 값을 읽음 결과: - 실제 골드: 1000 (롤백됨) - B가 읽은 값: 500 (존재한 적 없는 값!) - B: "어? 골드가 500인데 왜 아이템을 못 사?"

Dirty Read = 커밋되지 않은 (더러운) 데이터를 읽는 것

그 데이터는 결국 롤백되어 존재한 적 없는 값이 될 수 있어.

게임에서 실제로 문제가 될 수 있어?

예시 1: 골드 잔액 확인

• 실제 골드: 1000

• A가 500 차감 중 (아직 커밋 안 함)

• B가 NOLOCK으로 읽음: 500

• "잔액 부족" 오표시 또는 이상한 계산

예시 2: 랭킹 조회

• 레벨 업 트랜잭션 진행 중

• NOLOCK으로 랭킹 조회

• 잘못된 레벨 값으로 랭킹 계산

Part 4. Dirty Read만 문제야?

NOLOCK 쓰면 Dirty Read만 조심하면 돼?

아니, 더 심각한 문제들이 있어.

문제 설명 심각도
Dirty Read 커밋 안 된 데이터 읽음 중간
행 누락 페이지 분할 중 일부 행 못 읽음 높음
중복 읽기 같은 행을 두 번 읽음 높음
데이터 손상 UPDATE 중인 행의 일부만 읽음 매우 높음
행 누락? 중복 읽기? 그게 뭐야?

인덱스 페이지 분할(Page Split) 때문이야.

[페이지 분할 중 NOLOCK 읽기] Before: [Page A: 행1, 행2, 행3, 행4] INSERT 발생 → 페이지 분할 시작 During: [Page A: 행1, 행2] → [Page B: 행3, 행4, 새행] ↑ NOLOCK SELECT가 여기서 읽으면: - Page A 읽음 (행1, 행2) - Page B로 이동 중 행3이 옮겨짐 - 행3을 못 읽거나 두 번 읽음!

⚠️ 실제 발생 사례

• SUM(골드)가 실제보다 적거나 많게 나옴

• COUNT(*)가 부정확함

• 집계 쿼리 결과가 매번 다름

Part 5. 그럼 NOLOCK 언제 써도 돼?

NOLOCK이 이렇게 위험하면 왜 쓰는 거야?

적절한 상황에서는 성능 향상 효과가 크기 때문이야.

상황 NOLOCK 이유
실시간 정확성 필요 ❌ 금지 골드/아이템 수량 등
집계 쿼리 (정확해야 함) ❌ 금지 SUM, COUNT 등
거래/결제 관련 ❌ 금지 데이터 정합성 필수
대략적인 조회 (UI용) ✅ 가능 리스트 미리보기 등
로그/히스토리 조회 ✅ 가능 INSERT만 되는 테이블
마스터 데이터 조회 ✅ 가능 변경 안 되는 데이터

핵심 원칙:

• 변경이 거의 없는 테이블: NOLOCK OK

• INSERT만 되는 테이블: NOLOCK OK

• UPDATE/DELETE가 빈번한 테이블: NOLOCK 위험

Part 6. 우리 프로젝트 현황

우리 프로젝트는 NOLOCK 어떻게 쓰고 있어?

분석 결과:

실제 코드 - gp_LoadCharacter

SELECT ... FROM TCharacter WITH (NOLOCK) WHERE charunique = @uid SELECT ... FROM TMail WITH (NOLOCK) WHERE receiver = @uid

현재 사용 패턴:

• 캐릭터 로드: WITH (NOLOCK) 사용 ← 괜찮음 (로그인 시점)

• 메일 조회: WITH (NOLOCK) 사용 ← 괜찮음

• 랭킹 조회: WITH (NOLOCK) 사용 ← 주의 필요

저장 프로시저에서는?

저장 시에는 NOLOCK을 안 써야 해. 정합성이 중요하니까.

대신 ROWLOCK을 쓰는 경우가 있어.

-- 저장 시: 행 단위 잠금으로 동시성 확보 UPDATE TCharacter WITH (ROWLOCK) SET level = @level WHERE charunique = @uid

Part 7. NOLOCK 대신 쓸 수 있는 것

NOLOCK 말고 다른 방법 없어?

있어. READ COMMITTED SNAPSHOT이라는 옵션이 있어.

방식 Dirty Read 블로킹 설정
기본 (READ COMMITTED) 없음 있음 기본값
NOLOCK 있음 없음 쿼리 힌트
RCSI (스냅샷) 없음 없음 DB 옵션
RCSI가 좋아 보이는데?

맞아. 근데 tempdb 부담이 커져.

버전 정보를 tempdb에 저장하거든.

기존 시스템에 적용하려면 충분한 테스트 필요해.

핵심 정리

  • NOLOCK = 잠금 무시하고 읽기 (빠르지만 위험)
  • Dirty Read = 커밋 안 된 데이터 읽기 (롤백되면 문제)
  • 페이지 분할 중에는 행 누락/중복 읽기 발생 가능
  • 사용 OK: 변경 없는 테이블, INSERT만 되는 테이블, 대략적 조회
  • 사용 금지: 정확한 집계, 거래/결제, 실시간 정합성 필요한 곳
  • 대안: RCSI (READ COMMITTED SNAPSHOT) - tempdb 부담 있음
