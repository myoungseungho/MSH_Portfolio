Server Rollback

서버 롤백을 5분 만에 하는 법

1. 롤백이 왜 중요해?

배포하면 끝 아니야?

배포 후가 진짜 시작이야!

실제 사례 (가상 시나리오): 14:00 - 새 버전 배포 완료 14:05 - "레이드 보상이 안 들어와요" 신고 14:10 - 원인 파악 중... DB 쿼리 버그! 14:30 - 핫픽스 개발 중... 14:45 - 테스트 중... 15:00 - 핫픽스 배포 결과: - 1시간 동안 레이드 보상 미지급 - 영향받은 유저: 5,000명 - 보상 비용: ???

만약 즉시 롤백했다면?

14:00 - 새 버전 배포 완료 14:05 - "레이드 보상이 안 들어와요" 신고 14:06 - 롤백 시작 14:07 - 롤백 완료, 이전 버전 복구 결과: - 영향 시간: 7분 - 영향받은 유저: 500명 - 보상 비용: 최소화

2. 버전 관리는 어떻게 해?

롤백하려면 이전 버전이 있어야 하잖아?

버전 관리 전략이 핵심이야:

버전 관리 구조: /releases/ ├── v1.0.0/ │ ├── server.exe │ ├── config.json │ └── checksum.md5 ├── v1.0.1/ ├── v1.0.2/ ├── v1.1.0/ <- 현재 배포 └── latest -> v1.1.0 (심볼릭 링크) 유지 정책: - 최근 10개 버전 유지 - 7일 이상 된 버전 자동 삭제 - Major 버전은 영구 보관
도커 이미지로는?

태그로 버전 관리:

# 이미지 빌드 시 태그 docker build -t game-server:v1.1.0 . docker build -t game-server:v1.1.0-20250203 . # 날짜 포함 # 레지스트리에 푸시 docker push registry.example.com/game-server:v1.1.0 # 현재 배포 버전 확인 docker ps --format "{{.Image}}" # 출력: registry.example.com/game-server:v1.1.0 # 롤백 (이전 버전으로) docker pull registry.example.com/game-server:v1.0.2 docker stop game-server docker run -d --name game-server \ registry.example.com/game-server:v1.0.2

3. 이미지 기반 롤백

컨테이너 환경에서 롤백은?

쿠버네티스 롤백이 가장 빨라:

# 현재 배포 상태 확인 kubectl rollout history deployment/game-server # 출력: # REVISION CHANGE-CAUSE # 1 Initial deployment # 2 Update to v1.0.1 # 3 Update to v1.1.0 <- 현재 # 이전 버전으로 롤백 (1초!) kubectl rollout undo deployment/game-server # 특정 버전으로 롤백 kubectl rollout undo deployment/game-server --to-revision=1 # 롤백 상태 확인 kubectl rollout status deployment/game-server
실제로 얼마나 걸려?
쿠버네티스 롤백 타임라인: 0초: kubectl rollout undo 실행 1초: 이전 이미지 선택 2초: 새 Pod 생성 시작 30초: Pod Ready (헬스체크 통과) 31초: 트래픽 전환 총 소요: 약 30초 ~ 1분

미리 이미지가 캐시되어 있으면 더 빨라!

4. DB 롤백이 진짜 어렵지 않아?

코드는 롤백해도 DB는?

이게 가장 어려운 부분이야!

문제 상황: v1.0: users 테이블 - id, name, email v1.1: users 테이블 (마이그레이션) - id, first_name, last_name, email - name 컬럼 삭제됨! 롤백하면? - 코드: v1.0 (name 컬럼 사용) - DB: v1.1 스키마 (name 컬럼 없음!) - 결과: 에러!
그럼 어떻게 해야 해?

3단계 마이그레이션 원칙:

안전한 DB 변경 방법: Step 1: 확장 (Expand) - 새 컬럼 추가 (기존 유지) - v1.0.5: name, first_name, last_name 모두 존재 - 코드: name 사용 + first_name/last_name 동시 기록 Step 2: 전환 (Migrate) - 데이터 마이그레이션 완료 - v1.1.0: first_name, last_name 사용 - 코드: first_name/last_name 사용 (name은 읽기만) Step 3: 축소 (Contract) - 이전 컬럼 삭제 - v1.2.0: name 컬럼 삭제 - 이 시점부터 v1.0으로 롤백 불가 핵심: 각 단계가 안정화된 후 다음 단계!
마이그레이션 스크립트는?
-- migrations/001_expand_user_name.sql -- UP (적용) ALTER TABLE users ADD COLUMN first_name VARCHAR(50); ALTER TABLE users ADD COLUMN last_name VARCHAR(50); -- 기존 데이터 마이그레이션 UPDATE users SET first_name = SUBSTRING_INDEX(name, ' ', 1), last_name = SUBSTRING_INDEX(name, ' ', -1) WHERE first_name IS NULL; -- DOWN (롤백) ALTER TABLE users DROP COLUMN first_name; ALTER TABLE users DROP COLUMN last_name;
# 마이그레이션 실행 python manage.py migrate # 롤백 (이전 버전으로) python manage.py migrate 001_expand_user_name --reverse # 또는 Flyway flyway migrate flyway undo

5. 롤백 자동화

새벽에 장애 나면 어떡해?

자동 롤백을 설정해둬:

#!/bin/bash # auto_rollback.sh - 자동 롤백 스크립트 # 설정 ERROR_THRESHOLD=5 # 5% 에러율 CHECK_INTERVAL=30 # 30초마다 체크 ROLLBACK_COOLDOWN=300 # 롤백 후 5분 대기 check_health() { # Prometheus에서 에러율 조회 ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query?query=\ rate(http_requests_total{status=~'5..'}[1m])/\ rate(http_requests_total[1m])*100" | jq '.data.result[0].value[1]') echo "Current error rate: ${ERROR_RATE}%" if (( $(echo "$ERROR_RATE > $ERROR_THRESHOLD" | bc -l) )); then return 1 # 비정상 fi return 0 # 정상 } rollback() { echo "[$(date)] Starting auto-rollback..." # Slack 알림 curl -X POST $SLACK_WEBHOOK -d '{ "text": "Auto-rollback triggered! Error rate exceeded threshold." }' # 쿠버네티스 롤백 kubectl rollout undo deployment/game-server # 롤백 결과 대기 kubectl rollout status deployment/game-server echo "[$(date)] Rollback completed" } # 메인 루프 while true; do if ! check_health; then rollback sleep $ROLLBACK_COOLDOWN fi sleep $CHECK_INTERVAL done
수동 롤백은?

원클릭 롤백 스크립트:

#!/bin/bash # rollback.sh - 수동 롤백 스크립트 VERSION=${1:-"previous"} echo "======================================" echo " Game Server Rollback Script" echo "======================================" echo "" # 현재 버전 확인 CURRENT=$(kubectl get deployment game-server \ -o jsonpath='{.spec.template.spec.containers[0].image}') echo "Current version: $CURRENT" # 롤백 대상 확인 if [ "$VERSION" = "previous" ]; then TARGET=$(kubectl rollout history deployment/game-server \ --revision=$(kubectl rollout history deployment/game-server \ | tail -2 | head -1 | awk '{print $1}')) else TARGET="registry.example.com/game-server:$VERSION" fi echo "Target version: $TARGET" # 확인 read -p "Proceed with rollback? (y/n): " CONFIRM if [ "$CONFIRM" != "y" ]; then echo "Rollback cancelled." exit 0 fi # 롤백 실행 echo "" echo "Starting rollback..." START_TIME=$(date +%s) if [ "$VERSION" = "previous" ]; then kubectl rollout undo deployment/game-server else kubectl set image deployment/game-server \ game-server=$TARGET fi # 완료 대기 kubectl rollout status deployment/game-server END_TIME=$(date +%s) DURATION=$((END_TIME - START_TIME)) echo "" echo "======================================" echo " Rollback completed in ${DURATION}s" echo "======================================" # Slack 알림 curl -X POST $SLACK_WEBHOOK -d "{ \"text\": \"Manual rollback completed\nFrom: $CURRENT\nTo: $TARGET\nDuration: ${DURATION}s\" }"

6. 롤백 체크리스트

롤백할 때 뭘 확인해야 해?
단계 확인 항목 담당
롤백 전 - 현재 버전 기록
- 롤백 대상 버전 확인
- DB 호환성 검증
- 팀 공유 		DevOps
롤백 중 - 진행 상태 모니터링
- 에러 로그 확인
- 헬스체크 상태 		DevOps
롤백 후 - 서비스 정상 확인
- 에러율 모니터링
- 유저 피드백 확인 		QA/CS
사후 - 장애 보고서 작성
- 원인 분석
- 재발 방지 대책 		전체

7. 롤백이 안 되는 경우

롤백이 불가능한 상황도 있어?

있어! 이런 경우는 핫픽스가 필수:

롤백 불가 상황: 1. 비가역적 DB 변경 - 컬럼 삭제 + 데이터 손실 - 테이블 드롭 2. 외부 API 버전 변경 - 결제 API v1 -> v2 (v1 종료) - 소셜 로그인 프로토콜 변경 3. 클라이언트 강제 업데이트 - 앱스토어에 신버전만 존재 - 프로토콜 호환성 없음 4. 데이터 마이그레이션 완료 - 1000만 유저 데이터 변환 완료 - 롤백 = 데이터 불일치
그럼 어떻게 대비해?

Feature Flag로 코드 레벨 롤백:

// 기능 플래그로 새 기능 제어 void ProcessReward(Player* player) { if (FeatureFlag::IsEnabled("new_reward_system")) { // 새 보상 시스템 NewRewardSystem::Process(player); } else { // 기존 보상 시스템 LegacyRewardSystem::Process(player); } } // 문제 발생 시 플래그만 끄면 됨 // 서버 재배포 없이 즉시 적용! FeatureFlag::Disable("new_reward_system");
비유: 비상 스위치

- 새 기능 = 새 전구
- Feature Flag = 전등 스위치

전구가 고장나면?
-> 스위치만 끄면 됨! (전구 교체 없이)

핵심 정리: 서버 롤백

  • 버전 관리 - 최근 N개 버전 항상 보관
  • 이미지 롤백 - 쿠버네티스로 30초 내 롤백
  • DB 롤백 - Expand-Migrate-Contract 3단계 원칙
  • 자동화 - 에러율 초과 시 자동 롤백
  • Feature Flag - 코드 레벨 즉시 롤백
  • 목표 - 5분 이내 서비스 복구
