서버 롤백

배포 실패 시 빠르게 복구하는 방법

Part 1. 롤백이 뭐야?

롤백? 그게 뭔데?

롤백(Rollback)은 새 버전에 문제가 생겼을 때 이전 버전으로 되돌리는 것이야.

비유: 게임 세이브 포인트

게임할 때 어려운 구간 전에 세이브하잖아?
- 죽으면? 세이브 포인트로 복귀!

서버 롤백도 똑같아:
- 배포 전 = 세이브 포인트
- 버그 발생 = 게임 오버
- 롤백 = 세이브 포인트 로드!
왜 중요해?

실제 시나리오를 비교해보자:

[롤백 없을 때] 14:00 - 새 버전 배포 완료 14:05 - "레이드 보상이 안 들어와요" 신고 14:10 - 원인 파악 중... DB 쿼리 버그! 14:30 - 핫픽스 개발 중... 14:45 - 테스트 중... 15:00 - 핫픽스 배포 결과: - 장애 시간: 1시간 - 영향받은 유저: 5,000명 - 보상 비용: ??? [롤백 있을 때] 14:00 - 새 버전 배포 완료 14:05 - "레이드 보상이 안 들어와요" 신고 14:06 - 롤백 시작! 14:07 - 롤백 완료, 이전 버전 복구 결과: - 장애 시간: 7분 - 영향받은 유저: 500명 - 보상 비용: 최소화
핵심 원칙

문제가 발생하면 "고치지 말고 일단 롤백!"

고치는 건 롤백 후에 여유롭게 하면 됨.

Part 2. 롤백하려면 버전 관리가 필수!

롤백하려면 뭐가 필요해?

이전 버전이 보관되어 있어야 해!

[버전 관리 구조 예시] /releases/ ├── v1.0.0/ │ ├── server.exe │ └── config.json ├── v1.0.1/ ├── v1.0.2/ ├── v1.1.0/ ← 현재 배포 (문제 발생!) └── latest → v1.1.0 (심볼릭 링크) 유지 정책: - 최근 10개 버전 유지 - 7일 이상 된 버전 자동 삭제 - Major 버전은 영구 보관
도커를 쓰면?

태그로 버전 관리하면 돼:

# 이미지 빌드 시 태그 붙이기 docker build -t game-server:v1.1.0 . docker build -t game-server:v1.1.0-20250203 . # 날짜 포함 # 레지스트리에 푸시 docker push registry.example.com/game-server:v1.1.0 # 현재 버전 확인 docker ps --format "{{.Image}}" # 출력: registry.example.com/game-server:v1.1.0 # 롤백! 이전 버전으로 docker pull registry.example.com/game-server:v1.0.2 docker stop game-server docker run -d --name game-server registry.example.com/game-server:v1.0.2

Part 3. 쿠버네티스에서 롤백하기

쿠버네티스를 쓰면 롤백이 쉬워?

명령어 하나로 즉시 롤백!

# 배포 히스토리 확인 kubectl rollout history deployment/game-server # 출력: # REVISION CHANGE-CAUSE # 1 v1.0 initial # 2 v1.0.1 bug fix # 3 v1.1.0 new feature ← 현재 (버그 있음!) # 이전 버전으로 롤백 (1초!) kubectl rollout undo deployment/game-server # 또는 특정 버전으로 롤백 kubectl rollout undo deployment/game-server --to-revision=1 # 롤백 상태 확인 kubectl rollout status deployment/game-server
실제로 얼마나 걸려?

쿠버네티스 롤백 타임라인:

[쿠버네티스 롤백 과정] 0초: kubectl rollout undo 실행 1초: 이전 이미지 선택 2초: 새 Pod 생성 시작 30초: Pod Ready (헬스체크 통과) 31초: 트래픽 전환 완료 총 소요: 약 30초 ~ 1분! (이미지가 미리 캐시되어 있으면 더 빠름)
쿠버네티스 롤백의 장점

1. 명령어 하나로 실행
2. 자동으로 롤링 방식 적용 (서비스 중단 없음)
3. 히스토리 자동 관리
4. 실패 시 자동 롤백 설정 가능

Part 4. DB 롤백은 왜 어려워?

코드는 롤백하면 되는데, DB는?

이게 가장 어려운 부분이야!

[문제 상황] v1.0: users 테이블 - id, name, email v1.1: users 테이블 변경 (마이그레이션) - id, first_name, last_name, email - name 컬럼 삭제됨! 롤백하면? - 코드: v1.0 (name 컬럼 사용) - DB: v1.1 스키마 (name 컬럼 없음!) - 결과: 에러!! 💥
그럼 어떻게 해야 해?

3단계 마이그레이션 원칙을 따라!

[안전한 DB 변경: Expand-Migrate-Contract] Step 1: 확장 (Expand) ───────────────────────────────────── - 새 컬럼 추가 (기존 컬럼 유지!) - v1.0.5: name, first_name, last_name 모두 존재 - 코드: name 사용 + first_name/last_name 동시 기록 → 이 시점에 롤백해도 안전! Step 2: 전환 (Migrate) ───────────────────────────────────── - 데이터 마이그레이션 - v1.1.0: first_name, last_name 사용 - 코드: first_name/last_name 사용 (name은 읽기만) → 아직 name 컬럼 있으니 롤백 가능! Step 3: 축소 (Contract) ───────────────────────────────────── - 이전 컬럼 삭제 - v1.2.0: name 컬럼 삭제 → 이 시점부터 v1.0으로 롤백 불가! 핵심: 각 단계가 충분히 안정화된 후 다음 단계!
# 마이그레이션 스크립트 예시 -- migrations/001_expand_user_name.sql -- UP (적용) ALTER TABLE users ADD COLUMN first_name VARCHAR(50); ALTER TABLE users ADD COLUMN last_name VARCHAR(50); -- 기존 데이터 마이그레이션 UPDATE users SET first_name = SUBSTRING_INDEX(name, ' ', 1), last_name = SUBSTRING_INDEX(name, ' ', -1) WHERE first_name IS NULL; -- DOWN (롤백) ALTER TABLE users DROP COLUMN first_name; ALTER TABLE users DROP COLUMN last_name;
중요

DB 스키마 변경은 신중하게!
한 번에 바꾸지 말고 단계별로 진행해야 안전하게 롤백 가능!

Part 5. 자동 롤백 설정하기

새벽에 장애 나면 어떡해?

자동 롤백을 설정해두면 돼!

[자동 롤백 조건 예시] 조건 1: 에러율 5% 초과 조건 2: 응답 시간 3초 초과 조건 3: 헬스체크 3번 연속 실패 → 조건 충족 시 자동으로 이전 버전으로 롤백!
# 쿠버네티스 자동 롤백 설정 apiVersion: apps/v1 kind: Deployment metadata: name: game-server spec: strategy: type: RollingUpdate rollingUpdate: maxSurge: 1 maxUnavailable: 0 template: spec: containers: - name: game-server livenessProbe: httpGet: path: /health port: 8080 initialDelaySeconds: 30 periodSeconds: 10 failureThreshold: 3 # 3번 실패하면 재시작 readinessProbe: httpGet: path: /ready port: 8080 initialDelaySeconds: 5 periodSeconds: 5
수동 롤백 스크립트는?

원클릭 롤백 스크립트를 준비해두면 좋아:

#!/bin/bash # rollback.sh - 원클릭 롤백 스크립트 VERSION=${1:-"previous"} echo "================================" echo " Game Server Rollback Script" echo "================================" # 현재 버전 확인 CURRENT=$(kubectl get deployment game-server \ -o jsonpath='{.spec.template.spec.containers[0].image}') echo "현재 버전: $CURRENT" echo "롤백 대상: $VERSION" # 확인 read -p "롤백 진행할까요? (y/n): " CONFIRM if [ "$CONFIRM" != "y" ]; then echo "취소됨" exit 0 fi # 롤백 실행 START=$(date +%s) if [ "$VERSION" = "previous" ]; then kubectl rollout undo deployment/game-server else kubectl set image deployment/game-server \ game-server=registry.example.com/game-server:$VERSION fi # 완료 대기 kubectl rollout status deployment/game-server END=$(date +%s) echo "================================" echo " 롤백 완료! 소요: $((END-START))초" echo "================================" # Slack 알림 curl -X POST $SLACK_WEBHOOK -d "{ \"text\": \"롤백 완료! $CURRENT → $VERSION\" }"

Part 6. 롤백이 안 되는 경우

롤백이 불가능한 상황도 있어?

있어! 이런 경우는 핫픽스가 필수:

[롤백 불가 상황들] 1. 비가역적 DB 변경 - 컬럼 삭제 + 데이터 손실 - 테이블 DROP 2. 외부 API 버전 변경 - 결제 API v1 → v2 (v1 종료됨) - 소셜 로그인 프로토콜 변경 3. 클라이언트 강제 업데이트 - 앱스토어에 신버전만 존재 - 프로토콜 호환성 없음 4. 대규모 데이터 마이그레이션 완료 - 1000만 유저 데이터 변환 완료 - 롤백 = 데이터 불일치
그럼 어떻게 대비해?

Feature Flag로 코드 레벨 롤백!

// Feature Flag 사용 예시 void ProcessReward(Player* player) { // 새 기능을 플래그로 제어 if (FeatureFlag::IsEnabled("new_reward_system")) { // 새 보상 시스템 NewRewardSystem::Process(player); } else { // 기존 보상 시스템 (폴백) LegacyRewardSystem::Process(player); } } // 문제 발생 시? // 서버 재배포 없이 플래그만 끄면 됨! FeatureFlag::Disable("new_reward_system");
비유: 전등 스위치

- 새 기능 = 새 전구
- Feature Flag = 전등 스위치

전구가 고장나면?
→ 스위치만 끄면 됨!
→ 전구 교체(재배포) 없이 즉시 해결!

Part 7. 롤백 체크리스트

롤백할 때 뭘 확인해야 해?

단계별 체크리스트:

단계 확인 항목
롤백 전 □ 현재 버전 기록
□ 롤백 대상 버전 확인
□ DB 호환성 검증
□ 팀 공유
롤백 중 □ 진행 상태 모니터링
□ 에러 로그 확인
□ 헬스체크 상태
롤백 후 □ 서비스 정상 확인
□ 에러율 모니터링
□ 유저 피드백 확인
사후 □ 장애 보고서 작성
□ 원인 분석
□ 재발 방지 대책
롤백 골든 타임

목표: 5분 이내 서비스 복구

- 장애 감지: 1분 이내
- 의사결정: 2분 이내
- 롤백 실행: 2분 이내

이를 위해 평소에 롤백 스크립트와 프로세스를 준비해둬야 함!

핵심 정리

  • 롤백 - 문제 발생 시 이전 버전으로 빠르게 복구
  • 버전 관리 - 최근 N개 버전 항상 보관
  • 쿠버네티스 - 명령어 하나로 30초 내 롤백
  • DB 롤백 - Expand-Migrate-Contract 3단계 원칙
  • 자동 롤백 - 에러율 초과 시 자동 실행
  • Feature Flag - 재배포 없이 기능 끄기
  • 목표 - 5분 이내 서비스 복구
