에셋 파이프라인 전체 그림

DCC 툴부터 최종 빌드까지, 에셋이 거치는 모든 단계

Part 1. 개념

에셋 파이프라인이 뭐야?

에셋 파이프라인은 게임 에셋이 제작(DCC) → 엔진 Import → 처리/최적화 → 빌드 → 배포까지 거치는 전체 흐름을 의미합니다.

잘 설계된 파이프라인은 아티스트의 생산성을 높이고, 에셋 품질을 일관되게 유지하며, 최종 빌드 크기와 로딩 시간을 최적화합니다.

Part 2. DCC 단계

DCC 툴에서 내보낼 때 주의할 점은?

DCC에서 내보내는 방식이 이후 모든 단계에 영향을 미칩니다. 표준화된 내보내기 규칙이 중요합니다.

DCC와 엔진 사이 자동화는 어떻게 해?

스크립트를 통해 DCC 내보내기와 엔진 Import를 자동화할 수 있습니다.

# Maya - 배치 FBX 내보내기 스크립트 (Python) import maya.cmds as cmds import os def batch_export_fbx(output_dir, scale_factor=0.01): """선택된 오브젝트들을 개별 FBX로 내보내기""" selection = cmds.ls(selection=True) for obj in selection: # 이름에서 파일명 생성 file_name = f"{obj}.fbx" file_path = os.path.join(output_dir, file_name) # 해당 오브젝트만 선택 cmds.select(obj) # FBX Export 옵션 설정 cmds.FBXExportSmoothingGroups("-v", True) cmds.FBXExportTriangulate("-v", True) cmds.FBXExportScaleFactor(scale_factor) cmds.FBXExportUpAxis("y") # 내보내기 cmds.FBXExport("-f", file_path, "-s") print(f"Exported: {file_path}") # 사용 예시 batch_export_fbx("C:/Project/Assets/Art/Characters")
# Photoshop - 텍스처 내보내기 자동화 (JavaScript) // 레이어별 PNG 내보내기 function exportLayersAsPNG(outputFolder, baseName) { var doc = app.activeDocument; var layers = doc.artLayers; // 각 레이어를 순회 for (var i = 0; i < layers.length; i++) { var layer = layers[i]; // 모든 레이어 숨기기 for (var j = 0; j < layers.length; j++) { layers[j].visible = false; } // 현재 레이어만 보이기 layer.visible = true; // 파일명 생성 (예: T_Character_Base_D.png) var suffix = getSuffixFromLayerName(layer.name); var fileName = baseName + suffix + ".png"; // PNG로 저장 var file = new File(outputFolder + "/" + fileName); var options = new PNGSaveOptions(); options.compression = 9; doc.saveAs(file, options, true); } } function getSuffixFromLayerName(name) { var mapping = { "Diffuse": "_D", "Normal": "_N", "Metallic": "_M", "Roughness": "_R", "AO": "_AO" }; return mapping[name] || "_D"; }

Part 3. Import 단계

.meta 파일이 왜 그렇게 중요해?

.meta 파일은 에셋의 Import 설정, GUID, 참조 정보를 저장합니다. 없으면 참조가 깨지고 설정이 초기화됩니다.

Part 4. Build 단계

빌드 과정에서 에셋은 어떻게 처리돼?

빌드 시 에셋은 씬 참조 분석 → 번들링 → 직렬화 → 압축 과정을 거칩니다.

┌─────────────────────────────────────────────────────────────────────────────┐
│                        Unity Build Pipeline                                 │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  ┌─────────────────────────────────────────────────────────────────────┐   │
│  │  1. Scene Dependency Analysis                                       │   │

Resources vs StreamingAssets vs AssetBundles 차이는?

에셋 배포 방식에 따라 로딩 시점, 크기, 업데이트 유연성이 달라집니다.

┌─────────────────────────────────────────────────────────────────────────────┐
│                    에셋 배포 방식 비교                                       │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  방식          │ 빌드 포함 │ 로딩 API          │ 업데이트 │ 용도             │
│  ──────────────┼──────────┼──────────────────┼─────────┼─────────────────│
│  Resources/    │ O (항상) │ Resources.Load() │ 불가능  │ 코어 에셋        │
│                │          │ 경로 문자열 기반  │ 앱 재빌드│ 프리팹, 설정     │
│  ──────────────┼──────────┼──────────────────┼─────────┼─────────────────│
│  Streaming     │ O (원본) │ File.Read*       │ 불가능  │ 원본 파일 필요   │
│  Assets/       │ 압축 안됨│ WWW/UnityWebReq  │ 앱 재빌드│ 비디오, JSON     │
│  ──────────────┼──────────┼──────────────────┼─────────┼─────────────────│
│  AssetBundles  │ X (별도) │ AssetBundle.Load │ 가능    │ 대용량, DLC      │
│                │ CDN 배포 │ Addressables     │ 다운로드│ 라이브 업데이트  │
│  ──────────────┼──────────┼──────────────────┼─────────┼─────────────────│
│  Addressables  │ 선택적   │ Addressables API │ 가능    │ 현대적 권장 방식 │
│                │ 로컬/원격│ 비동기, 참조카운팅│ 자동관리│ 모든 에셋        │
│                                                                             │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  📌 Resources 폴더 주의사항                                                  │
│  ├─ 모든 에셋이 빌드에 포함 (사용 안 해도)                                  │
│  ├─ 문자열 기반 로딩 → 오타 런타임 에러                                    │
│  ├─ 앱 시작 시 전체 인덱싱 → 시작 시간 증가                                │
│  └─ 권장: 꼭 필요한 핵심 에셋만 (시스템 프리팹, 기본 설정)                  │
│                                                                             │
│  📌 StreamingAssets 폴더                                                     │
│  ├─ 빌드 시 압축/변환 없이 원본 그대로 복사                                │
│  ├─ 경로: Application.streamingAssetsPath                                  │
│  ├─ 플랫폼별 접근 방식 다름 (Android는 압축된 APK 내부)                     │
│  └─ 용도: 비디오, 로컬 DB, 설정 JSON, 커스텀 포맷                          │
│                                                                             │
│  📌 AssetBundles / Addressables                                              │
│  ├─ 빌드에서 분리, CDN 배포 가능                                           │
│  ├─ 라이브 업데이트, 부분 다운로드 가능                                    │
│  ├─ 의존성 관리 필요 (중복 방지)                                           │
│  └─ Addressables = AssetBundles의 고수준 래퍼 (권장)                       │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

빌드 크기를 줄이려면?

빌드 크기 분석 후 가장 큰 원인을 찾아 해결합니다.

// Build Report 분석 (에디터 로그) // Edit → Preferences → General → Editor Log // 빌드 후 Console 로그에서 확인 // 또는 Build Report API 사용 using UnityEditor.Build.Reporting; public class BuildAnalyzer { [MenuItem("Tools/Analyze Last Build")] public static void AnalyzeLastBuild() { // 마지막 빌드 리포트 경로 string reportPath = "Library/LastBuild.buildreport"; BuildReport report = AssetDatabase.LoadAssetAtPath<BuildReport>(reportPath); if (report == null) { Debug.LogError("No build report found. Build first."); return; } // 크기별 정렬 var sortedAssets = report.packedAssets .SelectMany(pa => pa.contents) .OrderByDescending(c => c.packedSize) .Take(50); Debug.Log("=== Top 50 Largest Assets ==="); foreach (var asset in sortedAssets) { float sizeMB = asset.packedSize / (1024f * 1024f); Debug.Log($"{sizeMB:F2} MB - {asset.sourceAssetPath}"); } // 타입별 합계 var byType = report.packedAssets .SelectMany(pa => pa.contents) .GroupBy(c => c.type) .Select(g => new { Type = g.Key, Size = g.Sum(c => c.packedSize) }) .OrderByDescending(x => x.Size); Debug.Log("\n=== Size by Asset Type ==="); foreach (var type in byType) { float sizeMB = type.Size / (1024f * 1024f); Debug.Log($"{sizeMB:F2} MB - {type.Type}"); } } }

Part 7. 핵심 정리

에셋 파이프라인 핵심만 정리해줘
┌─────────────────────────────────────────────────────────────────────────────┐
│                      에셋 파이프라인 핵심 정리                               │
├─────────────────────────────────────────────────────────────────────────────┤
│                                                                             │
│  📌 전체 흐름                                                                │
│  DCC (Maya 등) → Export → VCS → Import → PostProcess → Build → Deploy      │
│                                                                             │
│  📌 각 단계 핵심                                                             │
│  ├─ DCC: 네이밍 규칙, 스케일 통일, POT 해상도                               │
│  ├─ Import: .meta 관리, 플랫폼별 설정, 캐시 활용                            │
│  ├─ PostProcess: AssetPostprocessor로 자동화                                │
│  ├─ Build: Resources 최소화, 번들 분리                                      │
│  └─ Deploy: CDN, 증분 업데이트                                              │
│                                                                             │
│  📌 에셋 배포 방식 선택                                                      │
│  ├─ Resources: 핵심만 (시작 시 인덱싱 비용)                                 │
│  ├─ StreamingAssets: 원본 필요시 (비디오, JSON)                             │
│  ├─ AssetBundles: 업데이트 필요시                                           │
│  └─ Addressables: 권장 (모던 워크플로우)                                    │
│                                                                             │
│  📌 최적화 우선순위                                                          │
│  ├─ 1순위: 텍스처 (해상도, 압축, 밉맵)                                      │
│  ├─ 2순위: 오디오 (압축, 채널, 샘플레이트)                                  │
│  ├─ 3순위: 메시 (폴리곤, LOD, 압축)                                         │
│  └─ 4순위: 코드/쉐이더 (스트리핑)                                           │
│                                                                             │
│  📌 팀 협업 핵심                                                             │
│  ├─ 명확한 네이밍/폴더 규칙 문서화                                          │
│  ├─ .meta 파일 버전 관리 필수                                               │
│  ├─ CI에서 자동 검증                                                        │
│  └─ 역할 분리 (아티스트 ↔ TA ↔ 프로그래머)                                 │
│                                                                             │
└─────────────────────────────────────────────────────────────────────────────┘

핵심 요약

  • DCC → Import → PostProcess → Build → Deploy 전체 흐름 이해
  • .meta 파일은 GUID와 설정 저장, 반드시 버전 관리
  • 플랫폼별 Import 설정으로 에셋 최적화
  • Resources 최소화, Addressables 권장
  • 텍스처가 크기의 50-70% - 압축/해상도 최적화 우선
  • 자동화와 팀 규칙으로 일관성 유지
