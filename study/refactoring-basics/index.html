리팩토링이란 무엇인가

외부 동작 유지 + 내부 구조 개선 - 왜 필요한가?

Part 1. 리팩토링이 뭐야?

코드가 더러운데, 그냥 다시 짜면 안 돼?

다시 짜면 기존에 되던 것도 안 될 수 있어.

그래서 "동작은 그대로 두고, 구조만 개선"하는 게 리팩토링이야.

집 리모델링 비유

집을 부수고 새로 짓기 vs 살면서 한 방씩 고치기

새로 짓기: 6개월간 다른 데서 살아야 함, 비용 큼
리모델링: 살면서 조금씩 개선, 바로 효과 확인 가능

리팩토링은 "살면서 고치기"야.
정확히 어떤 규칙이 있어?

Martin Fowler의 정의:

리팩토링의 정의

"소프트웨어의 겉보기 동작(external behavior)은 그대로 유지한 채,
코드의 내부 구조(internal structure)를 개선하는 것"
"겉보기 동작이 그대로"라는 게 뭔데?

리팩토링 전후로 같은 입력 → 같은 출력이 나와야 해.

유저 입장에서 변화가 없어야 한다는 거야.

// 리팩토링 전 int result = a + b + c + d + e; // 리팩토링 후 int CalculateTotal(int a, int b, int c, int d, int e) { return a + b + c + d + e; } int result = CalculateTotal(a, b, c, d, e); // → 결과는 똑같음! 구조만 바뀜

Part 2. 왜 리팩토링이 필요해?

일단 돌아가면 됐지, 왜 고쳐?

지금은 괜찮아. 근데 6개월 뒤에 이 코드 다시 보면?

// 실제 프로젝트 예시 (조선협객전 서버) // ServerMsgProcess.cpp - 1019줄짜리 파일 void CServerMsgProcess::HandleServerMsg(int iClient, BYTE* pPacket) { switch (*pwHeader) { case SSM_SERVER_CONNECTED: // ... 100줄 ... break; case SSM_SERVER_DISCONNECTED: // ... 50줄 ... break; // ... 30개 이상의 case문 ... } } // 질문: 새 기능 추가하려면 어디를 봐야 해? // 답: 1019줄 전부 읽어야 함 😱
진짜 문제가 뭔데?

기술 부채(Technical Debt)가 쌓이는 거야.

부채니까 이자가 붙어. 시간이 갈수록 수정 비용이 올라가.

시점 기능 추가 비용 버그 수정 비용
출시 직후 1시간 30분
6개월 후 (안 고침) 3시간 2시간
2년 후 (계속 안 고침) 2일 1일
리팩토링하면 이자를 안 내도 돼?

이자율을 낮추는 거야.

부채 자체를 없애는 건 리라이트(다시 짜기)고.

Part 3. 리팩토링 vs 리라이트, 어떻게 선택해?

그냥 다 새로 짜는 게 깔끔하지 않아?

유혹되지? 근데 리라이트의 함정이 있어.

리라이트의 함정

1. 보이지 않는 지식 - 기존 코드엔 수많은 버그 수정의 흔적이 있음
2. 범위 확대 - "이왕 새로 짜는 김에 이것도..." 끝없이 늘어남
3. 동시 개발 - 기존 코드도 계속 수정되는데, 새 코드는 따라가야 함
4. 일정 폭파 - 예상보다 2~3배 오래 걸림
그럼 언제 리라이트해?

이런 조건일 때만:

조건 리팩토링 리라이트
코드 이해 가능? 읽으면 이해됨 아무도 모름
테스트 있음? 있음 (검증 가능) 없음
기술 스택 현재도 유효 완전히 구식
비즈니스 압박 계속 운영 중 여유 있음
실무 판단 기준

80% 이상: 리팩토링 (대부분의 경우)
20% 미만: 리라이트 (기술 스택 변경, 아키텍처 전면 교체)

우리 프로젝트(조선협객전)? → 당연히 리팩토링

Part 4. 언제 리팩토링해야 해?

따로 시간 내서 해야 해?

아니. 기능 개발하면서 같이 해.

"리팩토링 스프린트"는 안티패턴이야.

보이스카웃 규칙

"캠핑장을 떠날 때는 왔을 때보다 더 깨끗하게"

코드도 마찬가지. 내가 건드린 부분은 조금이라도 나아지게 두고 떠나.
구체적으로 어떤 타이밍?

Rule of Three (3의 법칙)

// 3의 법칙 1번째: 그냥 한다 2번째: 중복이네? 일단 참는다 3번째: 이제 리팩토링! // 예시: 비슷한 유효성 검사 코드 // 1번째 - 던전 입장 if (player->GetLevel() < 10) return FAIL; // 2번째 - PvP 입장 if (player->GetLevel() < 10) return FAIL; // 3번째 - 레이드 입장 // "또 같은 코드?" → 이제 함수로 빼자! bool CheckMinLevel(Player* p, int minLv) { return p->GetLevel() >= minLv; }
TDD에서 말하는 리팩토링은?

Red → Green → Refactor

테스트 통과(Green) 후, 바로 리팩토링!

Part 5. 우리 프로젝트에서 리팩토링 대상은?

조선협객전 서버에서 어떤 게 리팩토링 대상이야?

여러 가지가 있어:

// 1. 거대한 switch문 (ServerMsgProcess.cpp) switch (*pwHeader) { case SSM_SERVER_CONNECTED: // 100줄 case SSM_SERVER_DISCONNECTED: // 50줄 case DCM_LOAD_CHARACTER: // 200줄 // ... 30개 이상 ... } // → 각 case를 별도 함수로 분리 가능 // 2. 중복된 프로시저 구조 (Procedure_*.h 파일들) // Procedure_LoadCharacter.h, Procedure_SavePC.h, ... // 모두 비슷한 구조 → 템플릿화 가능 // 3. 헝가리안 표기법 (의미없는 접두사) int m_i32OsType; // i32가 뭔지 모름 DWORD m_dwAccunique; // dw가 뭔지 모름 // → 의미있는 이름으로 변경
전부 한번에 바꿔야 해?

절대 아니야!

한 번에 하나씩, 작게 바꿔야 해.

핵심 정리: 리팩토링이란

  • 정의: 외부 동작 유지 + 내부 구조 개선
  • 목적: 기술 부채의 이자율 낮추기
  • 리팩토링 vs 리라이트: 80% 이상은 리팩토링이 정답
  • 타이밍: 기능 개발하면서 함께, 3의 법칙
  • 보이스카웃: 왔을 때보다 깨끗하게 두고 떠나기
  • 핵심: 한 번에 하나씩, 작게
