부팅 과정 (Boot Process)

전원 버튼 누르면 무슨 일이 일어날까?

전원 ON → BIOS/UEFI → 부트로더 → 커널 → init

Part 1. 전원 버튼을 누르면?

컴퓨터 전원 버튼 누르면 바로 Windows가 뜨는 거 아니야?

아니! 그 전에 엄청 많은 일이 일어나.

[전원 버튼 누른 직후] CPU: "...?" (아무것도 모름) RAM: "...?" (텅 비어있음) SSD: "...?" (OS가 여기 있긴 한데...) 문제: CPU는 뭘 실행해야 할지 모름! OS는 SSD에 있는데, 어떻게 불러오지?
닭이 먼저냐 달걀이 먼저냐 같은 문제네?

정확해! 이걸 부트스트랩 문제라고 해.

[부트스트랩 문제 (Bootstrap Problem)] - OS를 실행하려면 메모리에 올려야 함 - 메모리에 올리려면 프로그램이 필요함 - 프로그램을 실행하려면 OS가 필요함 - ...무한 루프! 해결책: 아주 작은 프로그램을 하드웨어에 박아두자! → 이게 BIOS / UEFI

Part 2. BIOS가 뭐야?

BIOS가 뭐야?

Basic Input/Output System

메인보드에 박혀있는 최초의 프로그램이야.

[BIOS의 위치] ┌─────────────────────────────┐ │ 메인보드 │ │ │ │ [CPU] [RAM 슬롯] │ │ │ │ [BIOS 칩] ← 여기에 프로그램이 박혀있음! │ (ROM/Flash) │ │ │ └─────────────────────────────┘ 특징: - 전원 꺼져도 내용 유지 (비휘발성) - 메인보드에 물리적으로 붙어있음 - 컴퓨터 켜지면 CPU가 제일 먼저 실행
CPU가 어떻게 BIOS를 찾아?

약속된 주소가 있어!

[CPU의 첫 동작] 전원 ON! ↓ CPU: "리셋 벡터(Reset Vector) 주소로 점프!" (x86: 0xFFFFFFF0) ↓ 이 주소에 BIOS 코드가 매핑되어 있음 ↓ BIOS 실행 시작! → CPU는 무조건 정해진 주소부터 시작 → 메인보드 설계 시 그 주소에 BIOS를 연결해둠
BIOS는 뭘 해?

크게 두 가지: POST와 부트로더 찾기

[BIOS가 하는 일] 1. POST (Power-On Self-Test) - 하드웨어 점검 ├─ CPU 정상? ✓ ├─ RAM 정상? ✓ (메모리 테스트) ├─ 키보드 연결? ✓ ├─ 그래픽카드? ✓ └─ 문제 있으면 → 삐~~~! (비프음) 2. 부팅 장치 찾기 ├─ 설정된 부팅 순서 확인 (SSD → USB → CD) ├─ 첫 번째 장치의 부트 섹터 읽기 └─ 부트로더에게 제어권 넘김 → BIOS는 "하드웨어 점검 + 다음 단계 찾기" 담당
POST에서 문제 생기면?

아직 화면 출력이 안 될 수도 있어서 비프음으로 알려줘!

[비프음 코드 예시] 삐- (짧게 1번): 정상 삐- 삐- 삐- (짧게 3번): 메모리 문제 삐----- (길게 1번): 메모리 없음 삐- 삐----- (짧게+길게): 그래픽카드 문제 → 모니터 안 켜져도 문제 원인 파악 가능! → 메인보드 제조사마다 코드가 다름

Part 3. UEFI는 뭐야?

요즘은 BIOS 말고 UEFI라던데?

Unified Extensible Firmware Interface

BIOS의 현대판 후계자야.

[BIOS의 한계] 1. 16비트 모드로 동작 → 1MB 메모리만 접근 가능 2. 2TB 이상 디스크 부팅 불가 (MBR 한계) 3. 텍스트 기반 UI만 가능 4. 부팅 느림 5. 보안 기능 없음 → 1975년 설계... 너무 오래됨!
[UEFI의 장점] 1. 32/64비트 모드 → 더 많은 메모리 접근 2. GPT 지원 → 9.4ZB까지 (사실상 무제한) 3. 그래픽 UI 가능 (마우스도!) 4. 빠른 부팅 5. Secure Boot → 악성코드 차단 → BIOS를 대체하는 현대 표준
BIOS (레거시) UEFI
등장 1975년 2007년
모드 16비트 32/64비트
디스크 한계 2TB (MBR) 9.4ZB (GPT)
UI 텍스트 그래픽
부팅 속도 느림 빠름
보안 없음 Secure Boot
Secure Boot가 뭐야?

부팅 과정에서 서명된 코드만 실행하는 보안 기능!

[Secure Boot] 문제: 부팅 과정에 악성코드 끼어들면? → 백신보다 먼저 실행됨 → 탐지 불가! → 이런 걸 "부트킷(Bootkit)"이라 함 해결: 서명 검증! UEFI: "이 부트로더, 서명 있어?" 부트로더: "마이크로소프트 서명이요!" UEFI: (검증) "OK, 실행 허가" UEFI: "이건?" 악성코드: "..." UEFI: "서명 없네? 차단!" → 신뢰할 수 있는 코드만 부팅 허용

Part 4. 부트로더는 뭐야?

BIOS/UEFI가 OS 바로 실행하면 안 돼?

안 돼! BIOS/UEFI는 너무 작고 단순해.

[왜 부트로더가 필요해?] BIOS/UEFI가 직접 OS 로드하면? 1. 파일 시스템을 이해해야 함 (NTFS, ext4...) 2. OS 커널 위치를 알아야 함 3. 커널 압축 해제 4. 다양한 OS 지원 (Windows, Linux, macOS...) → BIOS/UEFI가 이걸 다 하면 너무 복잡해짐 → 중간 단계가 필요! = 부트로더
부트로더가 뭔데?

OS 커널을 메모리에 올려주는 프로그램

[부트로더의 역할] BIOS/UEFI: "부트로더야, 이제 네 차례!" 부트로더: 1. 어떤 OS 부팅할지 선택 (듀얼부팅이면) 2. 파일 시스템 읽기 (커널 파일 찾기) 3. 커널을 메모리에 로드 4. 부팅 파라미터 전달 5. 커널에게 제어권 넘김 → BIOS/UEFI와 커널 사이의 다리 역할
부트로더 예시?
부트로더 OS 특징
Windows Boot Manager Windows bootmgr, BCD 설정
GRUB Linux 가장 유명, 멀티부팅 지원
systemd-boot Linux UEFI 전용, 심플
boot.efi macOS Apple 전용
[GRUB 메뉴 예시] ┌────────────────────────────────────┐ │ GNU GRUB │ ├────────────────────────────────────┤ │ ▶ Ubuntu 22.04 │ │ Windows 11 │ │ Advanced options │ │ │ │ Use ↑↓ to select, Enter to boot │ └────────────────────────────────────┘ → 여러 OS 중 선택 가능 (듀얼부팅) → 선택한 OS의 커널을 로드
부트 섹터가 뭐야?

디스크의 맨 첫 번째 섹터. 부트로더가 여기 있어.

[디스크 구조 - MBR 방식] 섹터 0 (512 bytes) ┌──────────────────────────────────────┐ │ 부트 코드 (446 bytes) │ ← 부트로더 1단계 ├──────────────────────────────────────┤ │ 파티션 테이블 (64 bytes) │ ← 파티션 정보 ├──────────────────────────────────────┤ │ 0x55AA (2 bytes) │ ← 부팅 가능 표시 └──────────────────────────────────────┘ BIOS가 이 512바이트를 메모리에 올리고 실행! → 446바이트로 할 수 있는 게 제한적 → 그래서 2단계 부트로더로 넘어감

Part 5. 커널 로딩

부트로더 다음은?

드디어 커널(Kernel)이 로드돼!

[커널이란?] 운영체제의 핵심! 하드웨어와 소프트웨어 사이의 중재자 ┌─────────────────────────────────┐ │ 응용 프로그램 │ ├─────────────────────────────────┤ │ 커널 │ ← OS의 핵심 ├─────────────────────────────────┤ │ 하드웨어 │ └─────────────────────────────────┘ 역할: - 메모리 관리 - 프로세스 관리 - 파일 시스템 - 하드웨어 드라이버 - 보안
커널 로딩할 때 뭐가 일어나?
[커널 부팅 과정] 1. 압축 해제 - 커널은 보통 압축되어 있음 (vmlinuz) - 메모리에서 압축 해제 2. 커널 초기화 ├─ CPU 설정 (보호 모드 → 롱 모드) ├─ 메모리 맵 설정 ├─ 인터럽트 테이블 설정 └─ 기본 하드웨어 초기화 3. 드라이버 로드 ├─ 디스크 드라이버 ├─ 파일 시스템 드라이버 └─ 기타 필수 드라이버 4. 루트 파일 시스템 마운트 - "/" 디렉토리를 실제 디스크에 연결 5. init 프로세스 실행 - PID 1번, 모든 프로세스의 조상!
initrd/initramfs가 뭐야?

임시 루트 파일 시스템이야!

[initrd/initramfs] 문제: - 커널이 디스크를 읽으려면 드라이버 필요 - 드라이버는 디스크에 있음 - 디스크 읽으려면 드라이버... (닭과 달걀!) 해결: 필수 드라이버를 RAM에 미리 올려두자! 부트로더가: 1. 커널 로드 2. initramfs도 같이 로드 (RAM에) 커널이: 1. initramfs를 임시 루트로 사용 2. 필요한 드라이버 로드 3. 진짜 루트 파일 시스템 마운트 4. initramfs 버리고 진짜 루트로 전환

Part 6. init - 첫 번째 프로세스

init이 뭐야?

PID 1번, 모든 프로세스의 조상!

[init 프로세스] 커널: "하드웨어 준비 완료!" 커널: "이제 첫 번째 프로세스 실행!" 커널: → init 실행 (PID = 1) init의 역할: 1. 시스템 서비스 시작 (네트워크, 로그, 스케줄러...) 2. 사용자 로그인 화면 띄우기 3. 고아 프로세스 수거 (부모 없는 프로세스) 4. 시스템 종료 처리 → 커널 다음으로 계속 실행되는 프로세스 → init이 죽으면 시스템 패닉!
init 종류가 여러 개야?
init 시스템 사용 특징
SysVinit 구형 Linux 스크립트 순차 실행, 느림
Upstart Ubuntu (과거) 이벤트 기반, 병렬 실행
systemd 현대 Linux 병렬 실행, 의존성 관리, 빠름
launchd macOS Apple 전용
Service Control Manager Windows services.msc
[SysVinit vs systemd] SysVinit (전통 방식): 서비스A 시작... 완료 서비스B 시작... 완료 서비스C 시작... 완료 → 순차 실행, 느림 systemd (현대 방식): 서비스A 시작 ─┐ 서비스B 시작 ─┼─→ 동시에! 서비스C 시작 ─┘ → 병렬 실행, 빠름 → 의존성 있으면 자동으로 순서 조절
그래서 init 끝나면?

로그인 화면! 드디어 사용자 차례.

[부팅 완료!] init/systemd가: 1. 모든 시스템 서비스 시작 2. 그래픽 환경 로드 (X11/Wayland, Windows DWM) 3. 로그인 매니저 실행 ┌─────────────────────────────────┐ │ │ │ 사용자 이름: _ │ │ 비밀번호: _ │ │ │ │ [ 로그인 ] │ │ │ └─────────────────────────────────┘ → 전원 버튼 → 로그인 화면까지 완료!

Part 7. 전체 흐름 정리

[전원 ON → 로그인까지] ┌─────────────────────────────────────────────────────────┐ │ 1. 전원 ON │ │ └─ 전기 공급, CPU 리셋 │ ├─────────────────────────────────────────────────────────┤ │ 2. BIOS/UEFI (펌웨어) │ │ ├─ POST: 하드웨어 점검 │ │ ├─ 부팅 장치 찾기 │ │ └─ 부트로더 실행 │ ├─────────────────────────────────────────────────────────┤ │ 3. 부트로더 (GRUB, Windows Boot Manager) │ │ ├─ OS 선택 (듀얼부팅 시) │ │ ├─ 커널 + initramfs 로드 │ │ └─ 커널에게 제어권 넘김 │ ├─────────────────────────────────────────────────────────┤ │ 4. 커널 (OS 핵심) │ │ ├─ 압축 해제, 초기화 │ │ ├─ 드라이버 로드 │ │ ├─ 루트 파일 시스템 마운트 │ │ └─ init 프로세스 실행 (PID 1) │ ├─────────────────────────────────────────────────────────┤ │ 5. init/systemd │ │ ├─ 시스템 서비스 시작 │ │ ├─ 그래픽 환경 로드 │ │ └─ 로그인 화면 표시 │ ├─────────────────────────────────────────────────────────┤ │ 6. 로그인! │ │ └─ 사용자 환경 시작 │ └─────────────────────────────────────────────────────────┘
각 단계의 역할을 한 줄로?
단계 역할 핵심
BIOS/UEFI 하드웨어 점검, 부트로더 찾기 전원 → 소프트웨어
부트로더 커널을 메모리에 로드 펌웨어 → OS
커널 하드웨어 관리, init 실행 OS의 심장
init 서비스 시작, 사용자 환경 시스템 → 사용자

Part 8. 실전에서 알면 좋은 것

부팅 안 되면 어떻게 해?

어디서 멈췄는지가 힌트야!

[부팅 문제 진단] 증상 → 원인 아무것도 안 뜸, 비프음 → POST 실패 → 하드웨어 문제 (RAM, 그래픽카드) "No bootable device" → 부팅 장치 못 찾음 → BIOS 설정, 디스크 연결 확인 GRUB 메뉴 후 멈춤 → 커널 로드 실패 → 커널 손상, initramfs 문제 로고 나오고 멈춤 → 드라이버/서비스 문제 → 안전 모드로 부팅
게임 개발에서 부팅이 왜 중요해?

콘솔 게임, 임베디드 시스템에서는 부트 시간 최적화가 중요!

[게임/임베디드에서의 부팅] 콘솔 게임기: - 전원 켜면 빠르게 게임 시작해야 함 - 커스텀 부트로더 사용 - 불필요한 서비스 제거 아케이드 기계: - 전원 = 바로 게임 - OS 최소화, 부팅 최적화 필수 자동차, IoT: - 부팅 중 사고나면? - 초고속 부팅 필수 (1-2초 내)
[Windows 빠른 부팅 (Fast Startup)] 원리: - 종료 시 커널 상태를 디스크에 저장 (최대 절전 비슷) - 다음 부팅 시 저장된 상태 복원 - 콜드 부팅 vs 웜 부팅 → 부팅 시간 단축 → 단, 듀얼부팅이나 드라이버 업데이트 시 문제 가능

핵심 정리

  • 부트스트랩 문제 = OS 로드하려면 OS가 필요한 모순 → BIOS로 해결
  • BIOS/UEFI = 하드웨어에 박힌 최초 프로그램, POST + 부트로더 찾기
  • UEFI = BIOS의 현대판, GPT 지원, Secure Boot
  • 부트로더 = 커널을 메모리에 올리는 프로그램 (GRUB, bootmgr)
  • 커널 = OS의 핵심, 하드웨어 관리, init 실행
  • initramfs = 임시 루트 파일 시스템, 드라이버 로드용
  • init (PID 1) = 모든 프로세스의 조상, 서비스 관리
  • systemd = 현대 Linux init, 병렬 실행, 빠른 부팅
