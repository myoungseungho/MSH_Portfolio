조건문을 다형성으로

리팩토링 #10 고급 기법 Replace Conditional with Polymorphism

switch문이 계속 커지는데 어떻게 해?

타입별로 다른 동작을 하는 switch/if-else가 여러 곳에 반복되면, 다형성(Polymorphism)으로 교체하는 것이 좋습니다.

❌ 전형적인 문제 패턴 
// 몬스터 타입별 처리가 여러 곳에 흩어져 있음
int GetMonsterDamage(CMonster* pMon)
{
    switch (pMon->GetType())
    {
        case MONSTER_NORMAL:
            return pMon->GetAtk() * 1;
        case MONSTER_ELITE:
            return pMon->GetAtk() * 2;
        case MONSTER_BOSS:
            return pMon->GetAtk() * 5;
    }
    return 0;
}

int GetMonsterExp(CMonster* pMon)
{
    switch (pMon->GetType())  // 또 같은 switch!
    {
        case MONSTER_NORMAL:
            return 100;
        case MONSTER_ELITE:
            return 500;
        case MONSTER_BOSS:
            return 5000;
    }
    return 0;
}

const char* GetMonsterName(CMonster* pMon)
{
    switch (pMon->GetType())  // 또 또!
    {
        case MONSTER_NORMAL:
            return "일반 몬스터";
        case MONSTER_ELITE:
            return "정예 몬스터";
        case MONSTER_BOSS:
            return "보스";
    }
    return "알 수 없음";
}

⚠️ 문제점

  • 새 몬스터 타입 추가 시 모든 switch를 수정해야 함
  • 수정 위치를 놓치기 쉬움 (버그 발생)
  • 타입별 로직이 여러 곳에 흩어짐

다형성으로 어떻게 바꿔?

각 타입을 별도 클래스로 만들고, switch 분기를 가상 함수로 대체합니다:

    ┌─────────────────┐
    │   CMonster      │ ◀── 기반 클래스 (순수 가상 함수)
    │  + GetDamage()  │
    │  + GetExp()     │
    │  + GetName()    │
    └────────┬────────┘
             │
    ┌────────┼────────┬────────────────┐
    │        │        │                │
    ▼        ▼        ▼                ▼
┌────────┐┌────────┐┌────────┐    ┌────────┐
│ Normal ││ Elite  ││  Boss  │    │  New?  │
│Monster ││Monster ││Monster │    │ 추가만 │
└────────┘└────────┘└────────┘    │ 하면됨 │
                                  └────────┘
✅ 다형성으로 리팩토링 
// 기반 클래스
class CMonster
{
public:
    virtual ~CMonster() {}
    virtual int GetDamage() const = 0;
    virtual int GetExp() const = 0;
    virtual const char* GetName() const = 0;

protected:
    int m_nAtk;
};

// 일반 몬스터
class CNormalMonster : public CMonster
{
public:
    int GetDamage() const override { return m_nAtk * 1; }
    int GetExp() const override { return 100; }
    const char* GetName() const override { return "일반 몬스터"; }
};

// 정예 몬스터
class CEliteMonster : public CMonster
{
public:
    int GetDamage() const override { return m_nAtk * 2; }
    int GetExp() const override { return 500; }
    const char* GetName() const override { return "정예 몬스터"; }
};

// 보스 몬스터
class CBossMonster : public CMonster
{
public:
    int GetDamage() const override { return m_nAtk * 5; }
    int GetExp() const override { return 5000; }
    const char* GetName() const override { return "보스"; }
};
✅ 사용하는 곳 
// switch 없이 깔끔하게 호출
void ProcessDamage(CMonster* pMon, CGamePC* pPC)
{
    int damage = pMon->GetDamage();  // 타입에 맞는 함수가 자동 호출
    pPC->TakeDamage(damage);
}

void GiveReward(CMonster* pMon, CGamePC* pPC)
{
    int exp = pMon->GetExp();        // switch 불필요!
    pPC->AddExp(exp);
}

새 타입 추가할 때 어떻게 달라져?

✅ Before: switch 방식

새 몬스터 타입 추가 시: GetDamage(), GetExp(), GetName(), 그 외 모든 switch문 수정 필요 (10곳 이상)

✅ After: 다형성 방식

새 클래스 파일 1개 추가 + Factory에 생성 코드 1줄 추가. 끝!

새 타입 추가 예시: 레이드 보스 
// 새 파일: RaidBossMonster.h
class CRaidBossMonster : public CMonster
{
public:
    int GetDamage() const override { return m_nAtk * 10; }
    int GetExp() const override { return 50000; }
    const char* GetName() const override { return "레이드 보스"; }

    // 레이드 보스만의 특수 기능도 추가 가능
    void EnrageMode() { m_nAtk *= 2; }
};

// MonsterFactory.cpp에 1줄 추가
case MONSTER_RAID_BOSS:
    return new CRaidBossMonster();

🎯 핵심: 개방-폐쇄 원칙 (OCP)

"확장에는 열려있고, 수정에는 닫혀있다." 새 타입을 추가할 때 기존 코드를 수정하지 않아도 됩니다.

우리 프로젝트에 적용할 곳은?

게임 서버에서 다형성이 유용한 패턴들:

switch 패턴 다형성 클래스
몬스터 타입별 처리 CMonster → CNormal, CElite, CBoss
스킬 타입별 효과 CSkill → CAttackSkill, CBuffSkill, CHealSkill
아이템 타입별 사용 CItem → CWeapon, CArmor, CConsumable
퀘스트 타입별 완료조건 CQuest → CKillQuest, CCollectQuest, CTalkQuest

리팩토링 절차는?

  1. 1

    타입 코드 식별

    switch/if-else에서 분기하는 타입 코드(enum, int)를 찾습니다.

  2. 2

    기반 클래스 생성

    공통 인터페이스(순수 가상 함수)를 정의하는 기반 클래스를 만듭니다.

  3. 3

    각 타입을 서브클래스로

    switch의 각 case를 별도 클래스로 분리하고, 가상 함수를 구현합니다.

  4. 4

    Factory 패턴 도입

    타입 코드를 받아 적절한 서브클래스 인스턴스를 생성하는 Factory를 만듭니다.

  5. 5

    switch문 제거

    호출부에서 switch 대신 가상 함수 호출로 교체합니다.

언제 다형성을 쓰면 안 돼?

⚠️ 과도한 적용 주의

  • switch가 1곳뿐이면 굳이 클래스 계층 불필요
  • 분기가 2-3개뿐이고 확장 가능성 낮으면 switch가 나음
  • 단순 값 반환만 하는 경우 맵/테이블이 더 적합
  • 레거시 코드에서 대규모 변경이 필요하면 위험
맵으로 충분한 경우 
// 단순 값 매핑은 테이블이 더 간단
std::map MonsterExpTable = {
    {MONSTER_NORMAL, 100},
    {MONSTER_ELITE, 500},
    {MONSTER_BOSS, 5000}
};

int GetExp(int type) {
    return MonsterExpTable[type];
}

핵심 요약

📌 조건문→다형성 핵심

  • 같은 switch가 여러 곳에 반복되면 다형성 고려
  • 각 타입을 별도 클래스로 분리
  • switch 분기를 가상 함수 오버라이드로 대체
  • 새 타입 추가 = 새 클래스 추가 (기존 코드 수정 X)
  • switch 1곳, 분기 2-3개면 그냥 switch 사용
