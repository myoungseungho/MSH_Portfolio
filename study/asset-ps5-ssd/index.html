PS5 SSD의 혁명

I/O Complex가 게임 설계를 어떻게 바꿨는가

Part 1. PS5 스토리지의 진짜 혁신

PS5 SSD가 5.5GB/s라는데, PC NVMe도 그 정도 나오잖아. 뭐가 그렇게 특별해?

숫자만 보면 비슷해 보이지만, 병목 지점이 완전히 다릅니다.

기존 PC 아키텍처 (PS4, PC)
═══════════════════════════════════════════════════════════

SSD (3-5GB/s) → PCIe → CPU → RAM → GPU VRAM

문제점:
1. CPU가 I/O 요청 처리에 개입 (인터럽트, 스케줄링)
2. 압축 해제를 CPU가 담당 (코어 1개가 2-3GB/s 한계)
3. 데이터가 RAM을 거쳐야 GPU에 도달
4. 실제 사용 가능 대역폭: 50-100MB/s

┌─────────────────────────────────────────────────────────┐
│  SSD → [PCIe 오버헤드] → [CPU 처리] → [RAM 복사]       │
│        → [압축 해제] → [GPU 복사] → [사용 가능]        │
│                                                         │
│  실제 대역폭: ~100MB/s (이론 3GB/s의 3%)               │
└─────────────────────────────────────────────────────────┘

PC에서 NVMe가 5GB/s라고 해도, 실제로 게임이 쓸 수 있는 건 100MB/s 수준입니다. CPU가 모든 과정에 끼어들기 때문이죠.

PS5는 뭐가 다른 거야?

PS5는 I/O Complex라는 전용 하드웨어가 모든 과정을 담당합니다. CPU는 "이 파일 로드해"라고만 말하면 끝입니다.

      (PC의 80배 이상!)
CPU가 아예 관여 안 해?

거의요. CPU는 "이 파일을 저 주소로 로드해"라는 명령만 내리면, 나머지는 I/O Complex가 알아서 합니다.

// PS5 파일 로드 (개념적 코드) // 실제 PS5 SDK는 NDA 보호됨 // 기존 방식 (PS4, PC) void OldStyleLoad(const char* filename, void* dest) { // 1. 파일 시스템에서 위치 찾기 (CPU) FileHandle file = OpenFile(filename); // 2. I/O 요청 제출 (CPU) void* tempBuffer = AllocTemp(file.size); ReadFile(file, tempBuffer, file.size); // CPU가 대기하거나 스레드 스위칭 // 3. 압축 해제 (CPU - 여기서 병목!) size_t decompSize = LZ4_decompress(tempBuffer, dest, file.size); // 4. GPU로 복사 (CPU + DMA) UploadToGPU(dest, decompSize); FreeTemp(tempBuffer); } // PS5 방식 void PS5StyleLoad(const char* filename, void* gpuDest) { // 1. I/O Complex에 요청 제출 (CPU 개입 최소) IORequest req = { .filename = filename, .destination = gpuDest, // GPU 메모리 직접 지정! .priority = Priority::High, .decompressor = Decompressor::Kraken // 하드웨어 해제 }; // 2. 비동기 요청 - CPU는 바로 다른 일 가능 IOHandle handle = SubmitIORequest(&req); // 3. 나머지는 I/O Complex가 알아서: // - SSD에서 읽기 // - Kraken 하드웨어로 압축 해제 // - DMA로 GPU 메모리에 직접 전송 // - 캐시 일관성 자동 관리 // 4. 필요하면 완료 대기 (보통 다음 프레임쯤) WaitForIO(handle); }

Part 2. Kraken 하드웨어 디컴프레서

Kraken이 정확히 뭐야?

Kraken은 RAD Game Tools가 만든 고성능 압축 알고리즘입니다. Oodle 압축 라이브러리의 일부예요.

Kraken의 특징

  • 높은 압축률: 일반적으로 1.5~2배 (텍스처는 더 낮음)
  • 빠른 해제 속도: CPU에서도 초당 1-2GB 가능
  • PS5 전용 하드웨어: 22GB/s 처리, CPU 부담 0
  • 스트리밍 최적화: 청크 단위 해제 가능
왜 압축을 하드웨어로 해?

CPU로 압축 해제하면 심각한 병목이 됩니다.

압축 해제 성능 비교
═══════════════════════════════════════════════════════════

               처리 속도       CPU 사용률    지연 시간
───────────────────────────────────────────────────────────
CPU (1코어)    ~2 GB/s         100%          높음
CPU (8코어)    ~10 GB/s        800%          높음
PS5 하드웨어   22 GB/s         0%            매우 낮음
───────────────────────────────────────────────────────────

문제: SSD가 5.5GB/s 읽어도, CPU가 2GB/s밖에 해제 못 하면?
→ SSD 대역폭의 36%만 활용 가능
→ 나머지 CPU 코어가 게임 로직 못 돌림

해결: 하드웨어 디컴프레서
→ SSD 풀 속도 활용
→ CPU는 게임 로직에 전념
하드웨어 디컴프레서는 어떻게 동작해?

데이터가 SSD에서 나오자마자 파이프라인으로 바로 해제됩니다.

// 하드웨어 디컴프레서 동작 개념 // SSD에서 읽은 데이터 스트림 // ↓ // ┌─────────────────────────────────────────────┐ // │ Kraken 하드웨어 디컴프레서 │ // │ │ // │ ┌─────────┐ ┌─────────┐ ┌─────────┐ │ // │ │ 파서 │→│ LZ 매칭 │→│ 출력 │ │ // │ │ (헤더) │ │ (사전) │ │ (DMA) │ │ // │ └─────────┘ └─────────┘ └─────────┘ │ // │ │ // │ - 스트리밍 처리 (버퍼 최소화) │ // │ - 고정 지연 시간 (예측 가능) │ // │ - 다중 스트림 병렬 처리 │ // └─────────────────────────────────────────────┘ // ↓ // 해제된 데이터 → DMA → GPU 메모리 // 게임에서 활용 struct StreamingChunk { uint64_t compressedOffset; // SSD 상 위치 uint32_t compressedSize; // 압축 크기 uint32_t uncompressedSize; // 해제 후 크기 void* destAddress; // 목적지 (GPU 메모리) }; // 청크 단위로 요청 void StreamTexture(const StreamingChunk* chunks, int count) { for (int i = 0; i < count; i++) { IORequest req = { .offset = chunks[i].compressedOffset, .size = chunks[i].compressedSize, .dest = chunks[i].destAddress, .decompressor = Decompressor::Kraken }; SubmitAsync(&req); } // 모든 청크가 병렬로 처리됨 }

Part 3. DMA와 직접 GPU 전송

DMA가 뭐야? 왜 중요해?

DMA (Direct Memory Access)는 CPU를 거치지 않고 장치가 메모리에 직접 접근하는 방식입니다.

기존 방식 (CPU 경유)
═══════════════════════════════════════════════════════════

SSD → [PCIe] → [CPU] → [시스템 RAM] → [CPU] → [GPU VRAM]
                 ↑          ↑            ↑
              복사1       복사2        복사3

- CPU가 3번 개입
- 메모리 대역폭 3배 낭비
- CPU 캐시 오염


PS5 DMA 방식
═══════════════════════════════════════════════════════════

SSD → [I/O Complex] ──────────────────→ [통합 메모리]
         │                                    │
         └─ Kraken 해제                       └─ GPU 직접 접근
         └─ DMA 전송

- CPU 개입 0
- 복사 1회
- 캐시 영향 없음
PS5는 통합 메모리라면서? GPU VRAM이 따로 없어?

맞습니다. PS5는 16GB GDDR6를 CPU와 GPU가 공유합니다. 덕분에 데이터 전송이 필요 없어요.

// 통합 메모리의 장점 // 기존 PC 방식 void LoadTextureOld(const char* file, Texture* tex) { // 1. 시스템 RAM에 로드 void* cpuBuffer = SystemAlloc(tex->size); LoadFromDisk(file, cpuBuffer); // 2. GPU VRAM으로 복사 (CPU + PCIe 대역폭 사용) tex->gpuHandle = CreateGPUTexture(tex->width, tex->height, tex->format); UploadToGPU(tex->gpuHandle, cpuBuffer, tex->size); // 느림! // 3. CPU 버퍼 해제 SystemFree(cpuBuffer); } // PS5 통합 메모리 방식 void LoadTexturePS5(const char* file, Texture* tex) { // 1. GPU 메모리에 직접 로드 (복사 없음!) tex->gpuHandle = CreateGPUTexture(tex->width, tex->height, tex->format); void* gpuAddress = GetGPUAddress(tex->gpuHandle); // 2. SSD → I/O Complex → GPU 메모리 (직접!) IORequest req = { .filename = file, .destination = gpuAddress, // GPU 주소 직접 지정 .decompressor = Decompressor::Kraken }; SubmitIORequest(&req); // 끝! 복사가 없으므로 훨씬 빠름 }
캐시 일관성은 어떻게 관리해?

I/O Complex 안의 Coherency Engine이 자동으로 처리합니다.

Coherency Engine의 역할

  • 캐시 무효화: DMA 전송 후 해당 메모리 영역의 CPU 캐시 자동 무효화
  • 메모리 배리어: GPU가 데이터를 안전하게 읽을 수 있도록 보장
  • 순서 보장: I/O 요청의 완료 순서 관리
  • CPU 개입 불필요: 수동 캐시 플러시/무효화 필요 없음

개발자가 캐시 일관성을 신경 쓸 필요가 없어서, 코드가 단순해지고 버그도 줄어듭니다.

Part 4. 게임 설계 패러다임의 변화

이렇게 빠른 SSD가 게임 설계를 어떻게 바꿔?

완전히 다른 접근이 가능해집니다.

HDD/느린 SSD 시대의 설계 제약
═══════════════════════════════════════════════════════════

문제: 스토리지가 느리므로...

1. 모든 에셋을 메모리에 미리 로드
   └─ 로딩 화면 필수 (30초~2분)

2. 오픈월드에서 스트리밍 어려움
   └─ 플레이어 이동 속도 제한
   └─ "이 문은 아직 열 수 없습니다"
   └─ 좁은 통로로 로딩 숨기기

3. 에셋 중복 저장
   └─ 여러 레벨에서 쓰는 에셋을 각 레벨마다 복사
   └─ 설치 용량 비대 (100GB+)

4. 텍스처 품질 타협
   └─ 고해상도 텍스처를 실시간 로드 불가
   └─ 낮은 밉맵 레벨 사용


PS5 시대의 새로운 가능성
═══════════════════════════════════════════════════════════

해결: 스토리지가 메모리처럼 빠르므로...

1. 필요한 에셋만 즉시 로드
   └─ 로딩 화면 1-2초 또는 없음

2. 어디든 순간이동 가능
   └─ 플레이어 제한 없음
   └─ 차원 이동, 텔레포트 자유롭게

3. 에셋 중복 불필요
   └─ 필요할 때 바로 로드
   └─ 설치 용량 감소

4. 최고 품질 텍스처 항상 사용
   └─ 4K 텍스처 실시간 스트리밍
   └─ 팝인(pop-in) 현상 감소
실제 게임 예시 좀 보여줘

래칫 & 클랭크: 리프트 어파트가 대표적입니다.

// 래칫 & 클랭크: 차원 이동 시스템 (개념) class DimensionRiftSystem { private: World* m_CurrentWorld; World* m_TargetWorld; public: void TriggerDimensionRift(RiftPortal* portal) { m_TargetWorld = portal->GetTargetWorld(); // 1. 타겟 월드의 필수 에셋만 로드 (1-2초) // - PS5: 5.5GB/s × 2초 = 11GB 로드 가능! std::vector<AssetID> criticalAssets = { m_TargetWorld->GetTerrain(), m_TargetWorld->GetSkybox(), m_TargetWorld->GetPlayerSpawnPoint() }; IOBatch batch; for (auto id : criticalAssets) { batch.Add(id, Priority::Critical); } SubmitAndWait(batch); // ~0.5초 // 2. 차원 이동 애니메이션 재생 (0.5초) PlayRiftAnimation(); // 3. 월드 스왑 SwapWorlds(m_CurrentWorld, m_TargetWorld); // 4. 백그라운드에서 나머지 로드 StreamRemainingAssets(m_TargetWorld); } // HDD 시대였다면? // - 차원 이동 전 30초 로딩 화면 // - 또는 차원 이동 자체가 불가능 // - 두 월드를 동시에 메모리에 올릴 수 없음 };
Returnal은 어떻게 빠른 SSD를 활용해?

Returnal은 절차적 생성 + 즉시 로딩을 결합했습니다.

Returnal의 SSD 활용

  • 즉시 부활: 죽으면 2초 내에 게임 재시작 (로딩 화면 없음)
  • 절차적 방 생성: 다음 방을 실시간으로 생성하고 에셋 로드
  • 빠른 전환: 바이옴(Biome) 간 이동이 거의 즉각적
  • 고품질 유지: 60fps에서 고해상도 텍스처 항상 사용
// Returnal 스타일 절차적 룸 스트리밍 class ProceduralRoomStreamer { private: std::queue<RoomTemplate*> m_UpcomingRooms; std::unordered_set<AssetID> m_PreloadedAssets; public: void OnPlayerEnterRoom(Room* currentRoom) { // 1. 다음 방들 결정 (절차적 생성) std::vector<RoomTemplate*> possibleNextRooms = GeneratePossibleRooms(currentRoom); // 2. 가장 가능성 높은 방들의 에셋 프리로드 for (auto* room : possibleNextRooms) { PreloadRoomAssets(room); } } void PreloadRoomAssets(RoomTemplate* room) { for (auto assetId : room->GetRequiredAssets()) { if (m_PreloadedAssets.count(assetId) == 0) { // 비동기로 로드 시작 IORequest req = { .assetId = assetId, .priority = Priority::Background }; SubmitAsync(&req); m_PreloadedAssets.insert(assetId); } } } void OnPlayerDeath() { // PS5: 죽음 → 부활까지 ~2초 // 1. 시작 위치 에셋은 항상 메모리에 // 2. 절차적으로 새 레벨 생성 (0.5초) // 3. 필수 에셋 로드 (1초) // 4. 바로 플레이! } };

SFS (Sampler Feedback Streaming)가 뭐야?

SFS는 GPU가 실제로 샘플링하는 텍스처 영역만 로드하는 기술입니다.

// SFS 개념 (Xbox) // 기존 방식: 텍스처 전체 로드 // - 4K 텍스처 = 16MB // - 화면에 5%만 보여도 16MB 전부 로드 // SFS 방식: 필요한 영역만 로드 // - GPU가 "이 텍스처의 이 영역 필요해" 피드백 // - 해당 영역만 로드 (예: 0.8MB) // - 메모리 95% 절약 struct SFSFeedback { TextureID texture; uint8_t mipLevel; // 필요한 밉맵 레벨 uint16_t tileX, tileY; // 필요한 타일 좌표 }; // GPU가 렌더링하면서 피드백 생성 // → CPU/스토리지가 필요한 타일만 로드 // → 메모리 효율 극대화 // PS5도 유사한 기술 사용 가능하지만, // Xbox는 하드웨어 수준에서 더 깊이 통합됨

PS5는 빠른 속도로 전체를 로드하고, Xbox는 필요한 부분만 선별해서 로드하는 접근입니다. 둘 다 유효한 전략이에요.

DirectStorage는?

DirectStorage는 Windows PC에서 PS5/Xbox 스타일 I/O를 구현하는 API입니다.

DirectStorage 특징

  • GPU 직접 로드: SSD → GPU VRAM 직접 전송
  • GPU 압축 해제: GPU의 컴퓨트 셰이더로 BCPack 해제
  • 배치 처리: 수천 개 I/O 요청을 한 번에 제출
  • Windows 11 + NVMe: 하드웨어/OS 조합 필요
// DirectStorage 코드 예시 (Windows) #include <dstorage.h> void LoadAssetsDirectStorage() { // DirectStorage 팩토리 생성 IDStorageFactory* factory; DStorageGetFactory(IID_PPV_ARGS(&factory)); // 큐 생성 (GPU 메모리 타겟) DSTORAGE_QUEUE_DESC queueDesc = {}; queueDesc.SourceType = DSTORAGE_REQUEST_SOURCE_FILE; queueDesc.Capacity = DSTORAGE_MAX_QUEUE_CAPACITY; queueDesc.Priority = DSTORAGE_PRIORITY_NORMAL; queueDesc.Device = d3d12Device; // GPU 장치 IDStorageQueue* queue; factory->CreateQueue(&queueDesc, IID_PPV_ARGS(&queue)); // 파일 열기 IDStorageFile* file; factory->OpenFile(L"Assets/Textures.pak", IID_PPV_ARGS(&file)); // 배치 요청 제출 for (auto& asset : assetList) { DSTORAGE_REQUEST request = {}; request.Options.SourceType = DSTORAGE_REQUEST_SOURCE_FILE; request.Options.DestinationType = DSTORAGE_REQUEST_DESTINATION_BUFFER; request.Source.File.Source = file; request.Source.File.Offset = asset.offset; request.Source.File.Size = asset.compressedSize; request.Destination.Buffer.Resource = gpuBuffer; request.Destination.Buffer.Offset = asset.gpuOffset; request.Destination.Buffer.Size = asset.uncompressedSize; request.UncompressedSize = asset.uncompressedSize; request.Options.CompressionFormat = DSTORAGE_COMPRESSION_FORMAT_GDEFLATE; queue->EnqueueRequest(&request); } // 제출 및 완료 대기 queue->Submit(); IDStorageStatusArray* statusArray; factory->CreateStatusArray(1, nullptr, IID_PPV_ARGS(&statusArray)); queue->EnqueueStatus(statusArray, 0); queue->Submit(); // GPU 펜스로 완료 대기 statusArray->GetHRESULT(0); // 에러 체크 }

Part 6. 개발자 관점의 활용법

PS5에서 개발할 때 SSD를 최대한 활용하려면?

몇 가지 핵심 원칙이 있습니다.

PS5 SSD 최적화 원칙

  1. 크게 읽어라: 작은 I/O 여러 개보다 큰 I/O 하나가 효율적
  2. 순차 접근 우선: SSD도 순차 읽기가 랜덤보다 빠름
  3. 압축률 높은 포맷: Kraken에 최적화된 에셋 포맷 사용
  4. I/O 배치: 여러 요청을 모아서 한 번에 제출
  5. 우선순위 활용: 필수 에셋은 높은 우선순위로
// 최적화된 에셋 배치 // 나쁜 예: 작은 파일 수천 개 // /Assets/Textures/wood_001.dds // /Assets/Textures/wood_002.dds // ... 5000개 // → 파일 시스템 오버헤드, 작은 I/O 수천 번 // 좋은 예: 큰 번들 파일 // /Assets/Level1_Textures.pak (2GB) // /Assets/Level1_Meshes.pak (1GB) // → 순차 읽기, 큰 I/O 몇 번 struct OptimizedAssetPack { // 헤더 (파일 앞부분) struct Header { uint32_t magic; uint32_t assetCount; uint64_t tocOffset; // 목차 위치 }; // 목차 (TOC - Table of Contents) struct TOCEntry { uint64_t hash; // 에셋 ID uint64_t offset; // 데이터 시작 위치 uint32_t compressedSize; uint32_t uncompressedSize; }; // 데이터는 사용 순서대로 배치 // → 플레이어가 레벨을 진행하는 순서로 정렬 // → 순차 읽기 최대화 }; // I/O 배치 예시 void LoadLevelOptimized(const char* levelPak) { // 1. 헤더와 TOC 먼저 로드 Header header; std::vector<TOCEntry> toc; LoadHeaderAndTOC(levelPak, &header, &toc); // 2. 연속된 에셋들을 하나의 큰 I/O로 배치 IOBatch batch; uint64_t currentOffset = toc[0].offset; uint64_t batchStart = currentOffset; uint64_t batchSize = 0; for (const auto& entry : toc) { if (entry.offset == currentOffset + batchSize) { // 연속 → 배치에 추가 batchSize += entry.compressedSize; } else { // 불연속 → 이전 배치 제출, 새 배치 시작 batch.Add(levelPak, batchStart, batchSize); batchStart = entry.offset; batchSize = entry.compressedSize; } currentOffset = entry.offset + entry.compressedSize; } batch.Add(levelPak, batchStart, batchSize); // 3. 한 번에 제출 SubmitBatch(batch); }
크로스 플랫폼 게임에서는 어떻게 해?

PS5의 속도에 맞춰 설계하고, 다른 플랫폼에서는 대체 전략을 사용합니다.

// 크로스 플랫폼 로딩 추상화 class CrossPlatformLoader { public: virtual void LoadLevel(const char* levelId) = 0; virtual bool CanInstantTravel() const = 0; }; // PS5 구현 class PS5Loader : public CrossPlatformLoader { public: void LoadLevel(const char* levelId) override { // SSD에서 직접 로드 (1-2초) IORequest req = { levelId, Priority::Critical }; SubmitAndWait(req); } bool CanInstantTravel() const override { return true; } }; // PS4/HDD PC 구현 class LegacyLoader : public CrossPlatformLoader { public: void LoadLevel(const char* levelId) override { // 로딩 화면 표시 ShowLoadingScreen(); // 느린 로드 (30초+) LoadFromDiskSync(levelId); HideLoadingScreen(); } bool CanInstantTravel() const override { return false; } }; // 게임 로직에서 분기 void OnPlayerEnterPortal(Portal* portal) { if (g_Loader->CanInstantTravel()) { // PS5: 바로 이동 TeleportPlayer(portal->GetDestination()); } else { // 레거시: "포탈 활성화 중..." 메시지 표시 ShowPortalChargingAnimation(); // 또는 좁은 통로로 이동하면서 로딩 } }

Part 7. 미래 전망

앞으로 스토리지 기술은 어떻게 발전할까?

몇 가지 방향이 예상됩니다.

스토리지 기술 발전 방향
═══════════════════════════════════════════════════════════

현재 (2020-2024)
├─ PS5: 5.5GB/s + 하드웨어 디컴프레서
├─ Xbox: 2.4GB/s + SFS + Velocity
├─ PC: DirectStorage + GPU 압축 해제
└─ 모바일: UFS 3.1 (~2GB/s)

가까운 미래 (2025-2027)
├─ PCIe 5.0 SSD: 12-14GB/s
├─ 차세대 압축 (Oodle Data 2.0)
├─ DirectStorage 2.0 (더 깊은 GPU 통합)
└─ CXL 메모리 확장

먼 미래 (2028+)
├─ PCIe 6.0+: 30GB/s+
├─ 스토리지 = 메모리 계층 통합
├─ 압축 데이터 직접 연산 (Computational Storage)
└─ 로딩이라는 개념 자체가 사라질 수도?
게임 개발자는 어떻게 준비해야 해?

핵심은 "스토리지가 제약이 아닌 시대"를 염두에 둔 설계입니다.

미래를 대비한 설계 원칙

  • 로딩을 숨기지 말고 없애라: 좁은 통로, 엘리베이터 트릭보다 실제 빠른 로드
  • 메모리 예산보다 스트리밍 예산: 얼마나 빨리 데이터를 갈아치울 수 있는가
  • 압축 최적화: 에셋 파이프라인에서 압축률과 해제 속도 고려
  • 비동기 우선: 모든 I/O는 비동기로, 동기 로딩은 최소화
  • 플랫폼 추상화: 빠른 스토리지와 느린 스토리지 모두 지원

핵심 정리

  • I/O Complex: CPU 개입 없이 SSD → GPU 직접 전송
  • Kraken 하드웨어: 22GB/s 압축 해제, CPU 부담 0
  • DMA + 통합 메모리: 데이터 복사 없이 즉시 사용
  • 게임 설계 혁신: 로딩 화면 제거, 순간이동, 무제한 스트리밍
  • Xbox Velocity: SFS로 필요한 텍스처만 선별 로드
  • DirectStorage: PC에서 콘솔 수준 I/O 구현
  • 미래 대비: 스토리지 제약 없는 설계, 비동기 I/O 우선
