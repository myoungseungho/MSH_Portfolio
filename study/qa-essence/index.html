QA의 본질 — "기본은 되네"가 왜 함정인가

개발자가 코드를 짠 뒤, 테스트를 어떤 기준으로 리스트업해야 버그가 안 새는가

용어부터 — QA / 테스트 / 품질보증

QA(Quality Assurance, 品質保證) = 품질을 "보증"하는 일. 버그를 우연히 발견하는 게 아니라, "이 정도로 확인했으니 괜찮다"를 증명하는 활동.

테스트(Test) = 그 보증을 위해 실제로 돌려보는 행위. QA의 수단이지 QA 그 자체는 아니다.

핵심 한 줄 — "동작한다"는 보증이 아니다. "어떤 상황에서도 동작한다"가 보증이다.

Part 1. QA가 그냥 "테스트해보는 거" 아냐?

코드 짜고 한 번 돌려보면 그게 테스트고 QA 아냐?

"한 번 돌려보기"는 데모지 QA가 아닙니다. QA는 "이 코드가 망가질 수 있는 모든 상황을 미리 적어두고, 그게 다 괜찮은지 증명"하는 일입니다.

차이는 "증거의 범위"입니다. 데모는 "내가 해본 한 경우"가 전부지만, QA는 "안 해본 경우까지 목록으로 만들어 덮는다"는 점이 다릅니다.

데모 = 자전거 타고 평지 한 바퀴 돌고 "잘 굴러가네!" 하는 것.

QA = 오르막·내리막·빗길·짐 싣고·비 맞고·브레이크 젖었을 때까지 목록을 만들어 하나하나 타보는 것. "평지만 됐다"는 자전거가 안전하다는 증거가 아니다.

데모(한 번 해봄)QA(보증)
목표"되네""어떤 상황에서도 되네"
범위내가 해본 1~2 경우상황 목록 전수
판정화면에 떴다정확한 값/상태가 맞다

Part 2. 왜 "기본은 되네"가 함정인가 — 문제의식

기본 동작 확인했고 잘 됐어. 근데 왜 라이브에서 자꾸 터지지?

버그는 "기본 동작"에 숨지 않습니다. 버그는 "특정 상황 × 한 칸 더 깊은 속성"에 숨습니다. 기본 경로는 누구나 확인하니까 오히려 거의 안 터집니다.

두 가지 사각지대가 거의 모든 사고의 원인입니다:

① 숨은 전제조건 — "깨끗한 상태"로만 테스트하면, "이미 갖고 있을 때 / 2개일 때 / 가득 찼을 때"의 다른 코드 분기는 한 번도 안 타집니다.

② 얕은 확인 — "아이템이 바뀌었다"까지만 보고, 그 안에 든 강화 수치·각성 단계가 보존됐는지는 안 봅니다.

펫을 새 펫으로 바꾸는 기능을 테스트하는데, 새 펫이 없는 깨끗한 캐릭으로만 해봄 → "잘 바뀌네!" 통과.

그런데 실제 유저는 이미 그 펫을 갖고 있었음. 그러면 게임이 "어 있네? 개수만 +1" 하고 별(각성)·보석(투자)을 버림. → 라이브에서 "각성이 초기화됐어요" CS. 기본 테스트로는 영원히 안 보인다.

Part 3. ★ 그럼 테스트 리스트를 어떤 기준으로 만드나 — 행동 × 8축

꼼꼼한 테스트 목록은 어떤 기준으로 뽑아야 100개씩 나오지?

공식은 단순합니다. 플레이어 행동(함수) × 상황축 8종을 전부 곱합니다. 행동이 5개고 축이 8개면 그것만으로 40칸, 각 칸에 2~3개씩 = 100개+.

먼저 행동을 쪼갠다: 배우기 / 시전 / 강화 / 변환 / 소모 / 저장... 그 다음 각 행동에 아래 8축을 곱한다.

1. 정상 기준선

깨끗한 상태에서 정상 동작. 단, 정확한 기대값(N)으로. "소모됨"이 아니라 "딱 30개 소모".
예: 강화 0→1, 재료 정확히 5개 소모 + 엽전 1000 차감 + 단계 1

2. 상태 전제조건 변형

대상 보유 0 / 1 / 중복 2개+ / 최대치 / 이미 보유한 도착지. 직업·성별·레벨·문파·채널/서버·온라인↔오프라인이 다를 때.
예: 바꿀 펫을 이미 갖고 있을 때 변환 → 별·보석 보존되나

3. 수량 / 경계

0, 1, 2, 최대, 최대+1, 음수, 잘못된 인덱스. 재화가 정확히 부족 / 딱 맞음 / 초과.
예: 재료 1개 부족 → 실패코드 뜨고 재화 변화 0

4. 머지 / 스택 / 변환 보존

변환·합치기·획득 시 도착 대상을 이미 보유 + 투자(강화/각성/보석)까지 해둔 상태에서 그 깊은 속성이 정확 단계로 보존되나.
예: 각성3 둔갑을 변환했는데 도착에 각성0 둔갑이 이미 있음 → 각성3 유지되나(다운그레이드 금지)

5. 교차 시스템

다른 컨텐츠와 동시/연계 — 거래·창고·우편·점령전·이벤트·파티 진행 중일 때. 한 시스템 변경이 다른 시트/상태도 건드리나.
예: 거래창 열어둔 채 강화 시도 → 거부/정상 중 의도대로

6. 타이밍 / 중단

행동 도중 이동·채널변경·로그아웃·강제종료·동시 2클릭. 행동 후 재접속해도 유지되나(인메모리 vs DB 저장).
예: 강화 직후 즉시 재접속 → 단계 유지되나

7. 회귀 (리뉴얼/수정이면 필수)

옛 동작과 1:1 대조. 삭제·변경된 비용/지급/위치가 의도대로인가. 옛 기능이 조용히 죽지 않았나.
예: 예전엔 증표 400개 받던 비용이 30으로 — 의도된 변경인가, 누락인가

8. 부작용 / 짝꿍 상태

원본이 사라지면 그를 가리키던 장착/소환/퀵슬롯 포인터가 댕글링(없는 걸 장착·이중 적용)되지 않나. 다른 캐릭/계정/문파원에 영향 없나.
예: 장착 중이던 말을 변환 → 장착 슬롯이 사라진 옛 말을 가리켜 이중 능력치

이 8축이 핵심인 이유: 실제 라이브 사고가 전부 1번(기본)은 통과하고 2·4·7·8번에서 터졌기 때문입니다.

Part 4. 우리가 실제로 놓친 것들 — 사고 회고

실무에서 이 축들을 안 봐서 터진 사고가 진짜 있었어?

전부 "기본은 됐는데" 라이브에서 터진 것들입니다. 어느 축을 빼먹었는지 보면 정확히 보입니다.

사고현상빠뜨린 축
둔갑/신수 각성 초기화변환 시 도착을 이미 보유하면 각성·보석 증발4 머지 보존
용맹의 증표 400→30리뉴얼이 비용을 조용히 삭제7 회귀 + 정확값
둔갑 중복 변환같은 둔갑 2개면 전부 변환됨3 수량 경계
마패 장착 댕글링변환 후 없는 말이 장착된 채 이중 능력치8 부작용
직변 주말 차단 잔존구현이 분산돼 일부만 제거됨전역 변형 확인

100가지 케이스를 만들어도 전부 같은 모양(깨끗한 상태 + "됐다")이면, 같은 사각지대를 100번 반복한 것일 뿐이다. 양(개수)이 아니라 축의 다양성이 커버리지를 만든다.

Part 5. 좋은 테스트 케이스 한 줄의 모양

그래서 한 줄을 어떻게 적어야 "좋은" 케이스야?

케이스 한 줄에는 4가지가 반드시 들어가야 합니다. 하나라도 빠지면 "확인했다"고 못 합니다.

[ID] [축] 상황 세팅 → 행동 → 정상 기대결과(정확 N) | 확인: 어디서 보나 ───────────────────────────────────────────── P-004 [머지보존] 각성3 둔갑 보유 + 도착에 각성0 동일 둔갑 이미 보유 → 직업변경으로 변환 → 도착 둔갑 각성 == 3 (다운그레이드 금지) | 확인: 변환 후 DB 둔갑 각성 == 3, 변환로그 {before3 after3}

① 상황 세팅(어떻게 만드나) ② 행동 ③ 정상 기대값(정확 N) ④ 확인 포인트(화면/로그/DB).

특히 ">0", "바뀜", "됐음"으로 끝나는 오라클은 금지입니다. 보상·재화·아이템은 종착 자산(우편함 행 / 인벤 / 잔액 / DB 컬럼)의 실제 변화로만 판정합니다. 중간 로그(eligible/OK)는 합격 증거가 아닙니다.

한 줄 정리

  • QA의 본질 = "동작한다"가 아니라 "어떤 상황에서도 동작한다"를 증명하는 것.
  • 버그는 기본 경로가 아니라 "특정 상황 × 한 칸 더 깊은 속성"에 숨는다.
  • 테스트 리스트는 플레이어 행동 × 8축(기준선·전제조건·수량·머지보존·교차·타이밍·회귀·부작용)을 전수 교차해 뽑는다.
  • 케이스 한 줄 = 상황 세팅 + 행동 + 정확 기대값 + 확인 포인트. ">0/바뀜"은 합격 아님.
  • 케이스 개수가 아니라 축의 다양성이 진짜 커버리지다.
