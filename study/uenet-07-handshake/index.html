핸드셰이크 — 연결은 어떻게 맺어지나

Hello부터 복제 시작까지, 그리고 가짜 연결을 막는 쿠키

30초 요약

연결은 Hello → Challenge(쿠키) → 응답 → 검증 → Welcome → 준비 → 복제 시작 순으로 맺어져.

쿠키(Challenge-Response)는 가짜 연결 폭주(DoS)를 막는 장치 — 상태를 만들기 전에 먼저 검증.

우리로 치면 Login 인증 + Gate 입장 흐름이야.

Part 1. 왜 바로 게임에 못 들어가나

접속하면 그냥 바로 플레이하면 안 돼?

서로 모르는 사이라 먼저 '신원 확인 + 합의'가 필요해. 버전이 맞나, 진짜 클라가 맞나, 어떤 맵으로 갈까...

이 합의 과정이 핸드셰이크야. 끝나야 비로소 PlayerController가 생기고 복제가 시작돼.

쿠키는 왜 줘?

공격자가 가짜 주소로 연결 요청만 폭주시키면(SYN flood류) 서버가 연결 상태를 잔뜩 만들다 죽어.

그래서 서버는 처음엔 상태를 안 만들고 쿠키만 던져 — 진짜 클라면 그 쿠키를 돌려보내. 못 돌려보내면 무시. 이게 stateless 핸드셰이크.

실제 클래스/흐름은?

PacketHandler(특히 StatelessConnectHandlerComponent)가 쿠키 핸드셰이크를 담당하고, 그 위에서 UControlChannel이 NMT_Hello / NMT_Challenge / NMT_Login / NMT_Welcome 같은 제어 메시지를 주고받아.

끝나면 서버가 그 연결에 PlayerController를 스폰하고, 관련 액터들의 복제(ActorChannel 개설)가 시작돼.

UE 클래스PacketHandler / UControlChannel

PacketHandler는 패킷 수신 직후 첫 관문 — 쿠키 핸드셰이크·암호화·압축 같은 '저수준 변환'을 컴포넌트 체인으로 처리. 그 위에 UControlChannel이 NMT_Hello / NMT_Challenge / NMT_Login 같은 제어 메시지를 주고받아.

// 핸드셰이크 메시지 종류 (Engine/Net/DataChannel.h) NMT_Hello // 클라 첫 인사 NMT_Challenge // 서버 쿠키 NMT_Login // 로그인 정보 NMT_Welcome // 환영 + 맵 정보 NMT_Join // 게임 참여 요청 // PacketHandler 컴포넌트 예 (DefaultEngine.ini) [PacketHandlerComponents] +Components=StatelessConnectHandlerComponent // 쿠키 핸드셰이크 +Components=AESHandlerComponent // 암호화 (선택)

이 핸드셰이크 다 끝나는 데 얼마나 걸려?
정상 핑(50ms)이면 보통 100~300ms. Hello/Challenge 왕복(50~100ms) + 인증 부가 왕복 + Welcome + PlayerController 스폰까지 합쳐. "접속 중..." 로딩 화면이 도는 게 바로 이 시간이야. 핑이 300ms 넘는 해외 서버면 1초 이상도 흔하고. 모바일에서 자주 끊겼다 붙는 경우 이 시간이 누적돼서 체감이 커.

핵심 정리

  • 핸드셰이크 = Hello → Challenge(쿠키) → 응답 → 검증 → Welcome → 준비 → 복제 시작
  • 쿠키(Challenge-Response) = 상태 만들기 전 검증 → 가짜 연결 폭주(DoS) 방어
  • 버전 불일치 = 즉시 거부 (패킷 구조 안 맞으면 가비지)
  • 우리 = Login 인증 + Gate 입장, UE = PacketHandler + Control 채널(NMT_*)
  • 끝나야 PlayerController 스폰 + ActorChannel 복제 시작

Q. 쿠키도 공격자가 받아서 그대로 돌려보내면 되는 거 아냐?

여기가 미묘해. 진짜 클라는 자기 IP로 쿠키를 받아 그대로 돌려줄 수 있어. 근데 공격자가 IP를 위조해서 폭주 공격을 하면 — 응답(쿠키)이 가짜 IP로 가니까 공격자는 못 받아. 그래서 쿠키를 모르고, 다음 단계로 못 넘어가.

[IP 위조 공격 vs 쿠키 방어] 공격자(실제 IP X) → "Hello" with 위조 src=Y 서버 → "쿠키 = abc123" 응답을 Y로 보냄 공격자: 응답을 못 받음 (Y는 자기 IP가 아니라서) 공격자가 다음 단계 못 감 ✓ 방어 성공

핵심은 응답이 진짜 출발지로 가게 한 거야. 응답을 받을 수 있는 = 그 주소를 진짜 가진 = 추적 가능. 그래서 "DDoS 증폭 공격"(IP 위조로 폭주)을 막아. 단 공격자가 자기 진짜 IP로 정상 핸드셰이크를 진행하면 이건 다른 방어(레이트리밋·블랙리스트)가 막아야 해.

Q. 핸드셰이크 중 패킷이 유실되면(UDP니까) 어떻게 돼?

각 단계마다 응답을 기다리다 일정 시간 안 오면 재시도해.

[재시도 흐름] t=0 Hello 전송 t=0.5s 응답 없음 → Hello 재전송 t=1.0s 응답 없음 → 재전송 (지수 백오프) t=5.0s 여러 번 실패 → "연결 실패" 클라에 알림

대부분의 클라는 "서버 연결 중..." 화면을 보여주고, 몇 초 내 응답 없으면 사용자에게 "다시 시도" 옵션을 줘. 사용자 입장에선 그냥 "접속이 느리네"로 느껴지고 자동 복구되는 케이스가 많아.

한 가지 함정: 재시도 간격이 너무 짧으면 자기가 자기 트래픽을 폭주시켜. 그래서 지수 백오프(0.5s → 1s → 2s → 4s)로 점점 늘려.
Q. 패치 중 옛 버전 클라가 붙으면 어떻게 막아?

핸드셰이크 첫 단계(Hello)에 클라 버전을 실어 보내. 서버가 자기 버전과 다르면 즉시 거부하고 "업데이트 필요" 메시지.

[버전 체크] Client → "Hello, version=5.4.2" Server: my version=5.4.3 ↓ 다름 → "REJECT: please update to 5.4.3" Client: 자동 패치 다운로드 또는 에러 화면

왜 즉시 거부해야 하나: 버전이 다르면 패킷 구조·NetGUID·복제 속성이 다를 수 있어. 그대로 진행하면 가비지 데이터가 흐르고 양쪽이 이상한 상태가 돼 — 차라리 빠르게 끊는 게 안전.

패치 운영 팁: 새 버전 배포 시 서버 먼저 → 그 다음 클라. 그 사이 옛 클라가 붙으면 거부 메시지로 패치 유도. 또는 잠시 양쪽 버전 동시 지원(다중 버전) 후 옛 버전 차단.
Q. 재접속할 때도 매번 풀 핸드셰이크를 해?

기본은 그래. 안전을 위해 매번 처음부터.

빠른 복구가 중요한 게임은 세션 복구 기법을 써:

  • 세션 토큰: 연결 끊기기 전 서버가 발급한 토큰을 클라가 저장. 재접속 시 토큰만 보내면 검증 후 짧게 복구. 1~2초 안에 게임 복귀.
  • 0-RTT 핸드셰이크(QUIC): 처음 접속 시 받은 키를 캐시해, 다음엔 첫 패킷부터 암호화 데이터를 보냄. 거의 즉시 통신 가능.
트레이드오프: 빠른 재접속은 보안이 살짝 약해져(토큰이 유출되면 가로채기 가능). 그래서 "방금까지 정상이었던 같은 클라"에만 적용하고, 일정 시간 지나면 풀 핸드셰이크로 강등.
