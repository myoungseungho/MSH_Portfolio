핸드셰이크 — 연결은 어떻게 맺어지나

Hello부터 복제 시작까지, 그리고 가짜 연결을 막는 쿠키

30초 요약

연결은 Hello → Challenge(쿠키) → 응답 → 검증 → Welcome → 준비 → 복제 시작 순으로 맺어져.

쿠키(Challenge-Response)는 가짜 연결 폭주(DoS)를 막는 장치 — 상태를 만들기 전에 먼저 검증.

우리로 치면 Login 인증 + Gate 입장 흐름이야.

Part 1. 왜 바로 게임에 못 들어가나

접속하면 그냥 바로 플레이하면 안 돼?

서로 모르는 사이라 먼저 '신원 확인 + 합의'가 필요해. 버전이 맞나, 진짜 클라가 맞나, 어떤 맵으로 갈까...

이 합의 과정이 핸드셰이크야. 끝나야 비로소 PlayerController가 생기고 복제가 시작돼.

쿠키는 왜 줘?

공격자가 가짜 주소로 연결 요청만 폭주시키면(SYN flood류) 서버가 연결 상태를 잔뜩 만들다 죽어.

그래서 서버는 처음엔 상태를 안 만들고 쿠키만 던져 — 진짜 클라면 그 쿠키를 돌려보내. 못 돌려보내면 무시. 이게 stateless 핸드셰이크.

Part 2. 연결이 맺어지는 순서

정상/실패 시나리오를 보자.

탭으로 ① 정상 ② 버전 불일치 ③ 쿠키 위조 를 바꿔봐.

정상은 끝까지 가서 '복제 시작', 버전 불일치는 첫 단계에서 거부, 쿠키 위조는 검증에서 무시되는 걸 단계별로 따라가봐.

실제 클래스/흐름은?

PacketHandler(특히 StatelessConnectHandlerComponent)가 쿠키 핸드셰이크를 담당하고, 그 위에서 UControlChannel이 NMT_Hello / NMT_Challenge / NMT_Login / NMT_Welcome 같은 제어 메시지를 주고받아.

끝나면 서버가 그 연결에 PlayerController를 스폰하고, 관련 액터들의 복제(ActorChannel 개설)가 시작돼.

핵심 정리

  • 핸드셰이크 = Hello → Challenge(쿠키) → 응답 → 검증 → Welcome → 준비 → 복제 시작
  • 쿠키(Challenge-Response) = 상태 만들기 전 검증 → 가짜 연결 폭주(DoS) 방어
  • 버전 불일치 = 즉시 거부 (패킷 구조 안 맞으면 가비지)
  • 우리 = Login 인증 + Gate 입장, UE = PacketHandler + Control 채널(NMT_*)
  • 끝나야 PlayerController 스폰 + ActorChannel 복제 시작

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 쿠키도 공격자가 받아서 그대로 돌려보내면 되는 거 아냐?
진짜 클라는 자기 주소로 받은 쿠키를 돌려줄 수 있지만, 출발지 IP를 위조한 공격자는 응답을 못 받아 쿠키를 몰라. 그래서 주소를 진짜 가진 클라만 통과해 — 위조 폭주를 막아.
Q. 핸드셰이크 중 패킷이 유실되면(UDP니까) 어떻게 돼?
일정 시간 응답이 없으면 재시도해(타임아웃·재전송). 몇 번 실패하면 연결을 포기하고 클라가 다시 시도해.
Q. 패치 중 옛 버전 클라가 붙으면 어떻게 막아?
Hello에 버전을 실어 보내 서버가 다르면 즉시 거부하고 「업데이트 필요」를 줘. 그래서 패치 후 옛 클라는 못 붙어.
Q. 재접속할 때도 매번 풀 핸드셰이크를 해?
보통은 그래. 단 빠른 복구가 필요하면 세션 토큰·티켓을 발급해 다음 접속을 짧게 만드는 기법(0-RTT 등)을 써.
