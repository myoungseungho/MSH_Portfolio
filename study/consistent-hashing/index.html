서버 한 대 늘렸더니 캐시가 전부 날아갔다 — 일관성 해싱

노드를 추가/제거해도 데이터 재배치를 최소로 만드는 해시 링

30초 요약

단순 'key % N'으로 서버를 고르면, N(서버 수)이 바뀌는 순간 거의 모든 키가 다른 서버로 옮겨가.

일관성 해싱 = 노드·키를 같은 해시 링에 올리고 '시계방향 다음 노드'가 맡음.

노드를 추가/제거해도 근처 키만 옮겨가고 나머지는 그대로 — 재배치 최소.

Part 1. modulo의 재앙

캐시 서버 3대에 key % 3으로 분산했어. 1대 추가하면?

key % 3 → key % 4로 바뀌어. 거의 모든 키의 나머지가 달라져서 — 대부분의 데이터가 '다른 서버 담당'이 돼.

캐시라면 전부 미스 나서 한순간에 DB로 요청이 폭주해(thundering herd). 서버 늘리려다 서비스를 죽이는 거지.

어떻게 줄여?

서버 수를 나눗셈에 직접 안 쓰면 돼. 노드와 키를 같은 '원(해시 링)'에 올리고, 키는 자기 위치에서 시계방향으로 만나는 첫 노드가 맡게 해.

그럼 노드 하나가 빠져도 그 노드가 맡던 키만 다음 노드로 넘어가고, 나머지는 그대로야.

Part 2. 직접 노드를 넣고 빼봐

재배치 수를 비교해봐.

탭으로 ① 해시 링 ② 단순 modulo 를 고르고, '노드 추가/제거'를 눌러봐.

해시 링은 변경 시 재배치가 소수(근처 키만), modulo는 거의 전부 재배치되는 걸 '재배치 수'로 비교해.

Part 3. 가상 노드와 쓰임

노드가 링에 몰리면 한쪽만 부하 받는 거 아냐?

맞아. 그래서 실제론 노드 하나를 링 위 여러 지점에 '가상 노드(vnode)'로 흩뿌려. 그럼 키가 더 고르게 나뉘고, 노드 제거 시 그 부하가 여러 노드로 분산돼.

노드 수가 적을 때 쏠림을 막는 핵심 기법이야.

어디 쓰여?

분산 캐시(Memcached 클라이언트), 분산 DB(Cassandra, DynamoDB), 로드밸런서의 세션 고정 등. '서버 풀이 동적으로 늘었다 줄었다 하는데 데이터 이동을 줄이고 싶을 때' 단골이야.

게임이라면 유저/방을 서버 풀에 분산할 때, 서버를 증설해도 대부분의 세션이 안 옮겨가게 할 수 있어.

핵심 정리

  • key % N = N 바뀌면 거의 전부 재배치 → 캐시 전멸(thundering herd)
  • 일관성 해싱 = 해시 링 + '시계방향 다음 노드' → 변경 시 근처 키만 이동
  • 재배치량 ≈ 1/N (노드 하나 몫만) — 규모 변화에 강함
  • 가상 노드(vnode)로 쏠림 방지 + 부하 고르게
  • 쓰임: 분산 캐시·DB(Cassandra/Dynamo)·LB 세션 분산
