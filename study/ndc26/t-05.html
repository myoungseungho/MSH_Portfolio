[마비노기 모바일]의 카메라 시스템 설계도

독자적인 컴포넌트 시스템 위에서 다시 구현하는 3D 게임 카메라 시스템 설계 · 발표 영상 보기 ↗

1. 카메라를 “찍는 물건”이 아니라 “결정의 흐름”으로 보기

플레이어가 걷다가 전투에 들어가고, 대화를 시작하고, 컷신을 본다고 해 보자. 화면은 매 순간 하나뿐이다. 그런데 그 한 화면은 캐릭터를 따라가기도 하고, 적을 함께 보여 주기도 하고, 연출을 위해 가까워지기도 해야 한다. 카메라 하나에 이 모든 경우를 이어 붙이면, 다음 요구가 들어올 때마다 어디를 고쳐야 할지 찾기 어려워진다.

발표는 화면의 색을 바꾸는 셰이더가 아니라 카메라의 위치와 바라보는 방향을 정하는 시스템을 다룬다. 이 게임에는 자동 이동·수동 이동·궁극기·빠른 이동·전투·컷신처럼 여러 카메라 타입이 필요했다.

🔤 트랜스폼(Transform) — 물체가 어디에 있고 어느 방향을 보는지를 담은 값이다. 카메라라면 “어디에서 어느 쪽을 촬영하는가”가 된다. 발표에서는 위치(Position)와 회전(Rotation)을 말한다.
[게임 속 상황] → [지금 필요한 구도 판단] → [위치·방향 계산] → [Unity 카메라에 적용] 자동 이동 / 전투 / 대화 / 컷신
🎤 발표자는 이 세션을 카메라 트랜스폼을 결정하는 시스템의 오버뷰라고 설명한다. 깊은 수학과 세부 알고리즘 구현은 범위에서 제외했다.

2. 왜 시네머신을 그대로 쓰지 않았나

새 기능을 만들 때 외부 도구를 쓰는 선택은 자연스럽다. 여기서도 Unity가 제공하는 시네머신(Cinemachine)을 검토했다. 하지만 이 프로젝트의 게임 로직은 Unity 컴포넌트가 아니라 자체 C# 컴포넌트들 안에서 움직이고 있었다.

예를 들어 A가 캐릭터 위치를 갱신하고, B가 그 위치를 읽어 카메라 값을 만든다고 하자. 이 프로젝트의 코드 생성 프로그램은 B가 A를 참조한 사실을 분석한다. 그리고 같은 프레임 안에서 A 다음에 B가 실행되도록 순서를 고정한다. 이 흐름 한가운데에 시네머신을 넣으면 값을 밖으로 꺼내고 다시 넣는 다리 코드가 필요하다.

🔤 컴포넌트 — 게임 물체에 붙어 자기 몫의 일을 하는 작은 코드 단위다. 여기서는 Unity와 별개로 만든 C# 클래스들을 뜻한다.
Before · 다리 코드
[자체 컴포넌트] → [브리지 레이어] → [시네머신] ↑ 카메라 결과를 다시 읽어야 함
After · 내부에서 끝내기
[자체 컴포넌트 안의 카메라 로직] ↓ [끝단의 특수 컴포넌트] → [Unity 카메라]

또 하나는 디렉션의 밀도였다. “마지막 수동 조작 뒤 몇 초”, “패드를 어떤 각도로 움직이면 어떻게 멈출지”처럼 조건이 아주 구체적이었다. 그 판단 코드는 어느 쪽을 써도 사라지지 않는다. 그래서 팀은 카메라 코드를 자기 컴포넌트 시스템 안에 두고 조절 지점을 늘리는 쪽을 택했다.

🎤 다만 컷신은 예외다. 인게임 상태를 참조하지 않고 Playable 기반 타임라인 제작 공정의 사용성이 좋아서, 컷신 구성에는 시네머신을 적극적으로 사용한다고 발표에서 밝혔다.

3. 한 장의 화면이 만들어지는 네 겹

주인공 ‘루나’가 평소에는 혼자 달리다가 전투 중인 동료에게 다가간다고 하자. 카메라는 “루나 뒤 3m” 같은 최종 좌표를 처음부터 만지지 않는다. 먼저 타깃에서 얼마나 떨어질지, 어느 각도에서 볼지처럼 사람이 조절하기 쉬운 조각으로 나눈다.

🔤 CameraRigProperty — 발표에서 카메라 트랜스폼을 계산하는 데 쓰는 값 묶음(struct) 이름이다. 타깃 좌표, 각도, 거리, 오프셋 등을 담고, 이 값들을 다시 조립해 카메라 트랜스폼을 만든다.
[루나의 위치] + [각도] + [거리] + [오프셋] │ ▼ [CameraRigProperty] │ 재조립 ▼ [카메라 위치 + 바라보는 방향]

카메라 동작을 하나의 거대한 클래스에 몰아넣지 않는다. 기본 추적, 전투, 대화처럼 상황별로 비헤이비어를 두고, 각 비헤이비어가 자기 구도를 낸다. 그 다음 현재 화면은 하나여야 하므로 디렉터 역할의 카메라 컴포넌트가 고르거나 섞는다.

🔤 블렌딩(Blending) — 두 구도 사이의 중간값을 차례로 만들어, 한 화면에서 다른 화면으로 부드럽게 넘어가게 하는 일이다. 발표에서는 파라미터들이 float 묶음이므로 내분점을 구하는 방식으로 설명한다.
체험 1 · 디렉터가 고르는 한 장면
[팔로우 비헤이비어] → [카메라 컴포넌트] → [화면]
루나가 평소처럼 움직인다. 팔로우 카메라가 구도를 내고, 카메라 컴포넌트가 그 값을 화면에 보낸다.
🎤 발표에서는 비헤이비어의 값이 연속적이라고 보장할 수 없으므로, 목표값을 부드럽게 따라가게 하는 SmoothDamp도 사용한다고 설명한다.

4. “기능 조각”과 “상황 기억”을 분리하기

루나가 게임패드로 카메라를 돌린 직후, 카메라가 언덕에 파고들지 않게 해야 한다고 해 보자. 회전 입력 처리와 지형 충돌 처리는 다른 상황에서도 쓸 수 있다. 그래서 발표의 시스템은 RigProperty를 받아 조금 고친 새 RigProperty를 돌려주는 작은 기능 조각을 둔다.

🔤 모디파이어(Modifier) — CameraRigProperty를 입력으로 받아 기능에 맞게 수정한 새 CameraRigProperty를 반환하는 최소 기능 단위다. 내부 상태를 갖지 않는 static 메서드로 만든다.
[RigProperty 1] └─ OrbitModifier: 이번 프레임의 회전 입력 반영 → [RigProperty 2] └─ CollisionModifier: 지형 충돌 검사 → [RigProperty 3]

발표에 나온 조각은 OrbitModifier, AutoMove, ManualMove, CollisionModifier, TwoShotModifier다. TwoShot은 한 대상만 보던 구도에 다른 대상을 함께 넣을 때 쓴다.

반면 “루나가 수동 이동을 마지막으로 한 시각”, “자동 이동이 언제 끝나는가”, “전투 대상은 어디 있는가”는 매번 들고 다니는 설정 조각이 아니다. 이런 기억은 비헤이비어가 맡는다.

🔤 비헤이비어(Behavior) — 특정 상황의 카메라 구도를 만드는 클래스다. 액터 상태·게임 내부 상태·레플리케이션 상태를 가져와, 그 상황에 필요한 맥락을 보관한다.
🧩 모디파이어를 ‘누구나 빌려 쓰는 렌즈 조절 도구’, 비헤이비어를 ‘현재 장면의 사정을 기억하는 촬영 감독’으로 나누면, 어느 쪽을 고쳐야 할지가 명확해진다. 이는 발표의 역할 분리를 풀어 쓴 해석이다.

5. 새 연출 요청이 들어온 날: 어프로칭 카메라

루나가 자동 이동으로 상호작용 대상에게 다가간다. 너무 가까워졌을 때 루나만 화면에 있으면, 무엇에게 다가가는지 놓치기 쉽다. 이때 “루나와 대상이 함께 보이게 하자”는 요청이 들어왔다.

발표의 답은 기존 코드 한 곳에 조건을 끼워 넣는 일이 아니었다. 어프로칭 카메라라는 새 비헤이비어를 만든다. 그 비헤이비어 안에서 자동 이동 중인지와 거리가 어떤지를 보고, 조건이 맞으면 스스로 활성 상태가 된다. 내부에서는 이미 있던 TwoShotModifier와 CollisionModifier를 재사용한다.

[자동 이동 중인가?] ─아니오→ [팔로우 카메라] │ 예 ▼ [상호작용 대상과의 거리 확인] ─조건 충족→ [어프로칭 비헤이비어 활성] │ [TwoShot] + [지형 충돌 검사] ▼ [루나 + 대상이 함께 보이는 구도]
문제가 생긴 곳먼저 볼 곳
새로운 상황의 카메라가 필요하다새 비헤이비어
상황을 판단하는 기억이 이상하다비헤이비어 내부
여러 카메라가 공통으로 쓰는 계산이 이상하다모디파이어
우선순위 전환·블렌딩이 어색하다카메라 컴포넌트
🎤 발표에는 팔로우 카메라에서 어프로칭 카메라로, 다시 게더링 카메라라는 다른 비헤이비어로 전환되는 사례가 나온다.

6. 값 하나를 바꾸고 확인하는 시간이 설계를 바꾼다

카메라를 조정하는 사람은 “이 FOV가 맞나?”를 한 번만 묻지 않는다. 100으로 보고, 30으로 보고, 다시 비교한다. 게임을 껐다 켜야만 값이 바뀐다면 생각의 흐름도 끊긴다. 발표자는 가장 오래 걸리는 경우 게임을 한 번 껐다 켜는 데 약 20분이 걸리기도 했다고 말한다.

🔤 FOV(Field of View, 화각) — 카메라가 한 번에 담는 시야의 넓이다. 값이 바뀌면 화면에서 보이는 범위의 느낌이 달라진다.
Before · 재시작을 기다리는 흐름
값 수정 → 게임 종료 → 게임 시작 → 장면 재현 → 기억으로 비교
After · 실행 중 적용
값 수정 → Apply → 현재 장면에서 즉시 비교 → 채택 또는 폐기
체험 2 · 실행 중 값 적용이라는 작업 감각
현재 편집 값60
슬라이더는 편집 중인 값이다. Apply를 누르면 현재 실행 중인 카메라에 적용하는 상황을 흉내 낸다.

이 프로젝트는 인스펙터를 따로 만들어, 여러 변수를 한 번에 바꾸고 빠르게 적용하거나 버릴 수 있게 했다. UI의 문장도 “몇 초 동안 움직이지 않으면 몇 초에 걸쳐 기본 거리로 돌아간다”처럼 디렉션 문장에 가깝게 썼다. 구현자와 요청자가 같은 의도를 읽게 하기 위해서다.

🎤 발표에서는 카메라 설정값을 캐싱하지 말고 사용 직전에 읽어야 한다고 강조한다. 값을 캐싱하면 실행 중 변경이 바로 적용되지 않는다.

7. 마지막 한 끗: 흔들림, 타임라인, 화면 중심 옮기기

기본 구도는 비헤이비어가 만든다. 그 뒤 디렉터 단계에서 순간의 느낌을 더할 수 있다. 여기서 말하는 포스트 이펙트는 화면 색을 바꾸는 셰이더가 아니라, 카메라 트랜스폼에 더하는 변화다.

프레임이 달라도 타격감을 놓치지 않기

카메라 셰이크는 최종 카메라 위치에 사인 그래프를 샘플링한 값을 더한다. magnitude(크기), frequency(빈도), duration(지속 시간)을 다르게 주어 느낌을 조절한다. 그런데 프레임 타이밍에 따라 사인파의 꼭대기를 건너뛰면 흔들림이 약해 보일 수 있다. 발표에서는 극값을 강제로 만들거나, 크기를 보정하거나, 사인을 뒤집는 트릭을 소개했다.

체험 3 · 샘플 하나가 0 근처에 걸리면
●
사인파의 가운데를 읽으면 움직임이 작아 보인다. 프레임마다 읽는 지점이 달라질 수 있다는 발표의 문제를 단순화해 보여 준다.

카메라는 움직이지 않고 화면의 중심만 바꿀 수 있다

타임라인 이펙트는 Unity Timeline의 Playable로 타이밍을 조절하며 트랜스폼을 살짝 바꾼다. 궁수의 매그넘 샷에서는 차징 타이밍에 FOV와 거리를 조절한 사례가 나온다. 오프센터 프로젝션은 투영 중심축을 화면 X/Y 방향으로 옮긴다. 가상 키보드나 UI가 화면 일부를 가릴 때, 남은 화면의 중심에 캐릭터를 두는 데 쓸 수 있다.

🔤 오프센터 프로젝션(Off-center projection) — 카메라 자체의 월드 공간 위치는 그대로 두고, 화면이 투영되는 중심축만 평행 이동시키는 방식이다. 그래서 카메라가 벽이나 땅에 닿을 걱정을 늘리지 않는 장점이 있다.

8. 처음 만드는 개발자가 가져갈 5가지

카메라가 이상할 때는 대개 오류 메시지 대신 “툭 끊긴다”, “덜거덕거린다”는 느낌으로 나타난다. 발표자는 그래서 시각화가 언제나 제값을 한다고 말한다. 그래프와 기즈모로 후보값, 충돌 거리, 가속도, 한 프레임의 튀는 값을 보이면 문제의 순간을 먼저 잡을 수 있다.

🔤 기즈모(Gizmo) — 게임 화면이나 편집 화면 위에 선·점·도형으로 내부 값을 그려 보는 디버그 표시다. 숫자만 읽을 때보다 카메라가 무엇을 계산했는지 눈으로 확인하기 쉽다.

수학 공간도 조심해야 한다. 발표자는 로직을 가능한 월드 스페이스와 뷰 스페이스에서 다루고, 스크린 스페이스 계산은 피하자고 조언한다. 또한 외부 수학 라이브러리를 쓸 때 행렬의 로우/컬럼 메이저와 왼손/오른손 좌표계 차이를 확인해야 한다. 실제로 투영 행렬을 잘못 계산해 섀도우 캐스케이드가 잘려 보인 사례도 소개했다.

  1. 도구의 이름보다 흐름을 먼저 보자. 자체 컴포넌트의 실행 순서와 카메라가 강하게 얽혀 있다면, 연결 비용까지 설계 대상이다.
  2. 값·기능·상황·선택을 분리하자. RigProperty, 모디파이어, 비헤이비어, 디렉터라는 나눔이 수정 위치를 알려 준다.
  3. 새 장면은 새 비헤이비어로 표현하자. 어프로칭 카메라처럼 조건과 맥락이 새로 생긴다면 한 덩어리로 격리한다.
  4. 반복 확인을 빠르게 하자. 실행 중 적용, 설명식 UI, 사용 직전 설정값 읽기가 디렉션 수정 속도를 지킨다.
  5. 느낌 문제는 먼저 그려 보자. 값의 그래프와 기즈모가 “어느 프레임에서 무엇이 튀었나”를 드러낸다.
