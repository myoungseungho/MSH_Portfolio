GPU Profiling and Crash Debugging in the Latest Unreal Engine

최신 언리얼 엔진에서 GPU가 무엇을 기다리고 어디에서 멈췄는지 추적하는 법. 발표 영상 보기 ↗

1. 화면이 멈춘 날, 무엇부터 봐야 할까

지수의 게임 화면이 멈췄습니다. CPU 프로파일러에는 대기 시간이 보입니다. 그러나 그 시간에 GPU가 그림을 그리느라 바빴는지, 다음 일을 받지 못해 놀았는지는 알 수 없습니다. GPU 오류는 난 뒤에도 다른 작업이 진행될 수 있습니다. CPU에 리포트가 도착했을 때는 범인 패스가 이미 지나간 뒤일 수 있습니다.

🔤 GPU — 화면의 픽셀을 계산하는 전용 장치다. CPU가 작업 목록을 건네면, GPU는 여러 일을 한꺼번에 처리한다.
🔤 RHI(Render Hardware Interface) — 기기마다 다른 그래픽스 API 사이의 번역 창구다. 렌더러의 요청을 각 기기의 GPU 명령으로 바꾼다.
[CPU가 작업 목록을 보냄] → [RHI가 번역] → [GPU의 여러 큐가 실행] ↘ 오류 보고는 나중에 도착
🎤 발표에서는 GPU 오류와 CPU 측 리포트 사이에 최대 2초 정도 차이가 날 수 있고, 기존에는 컴퓨트 큐의 동작이나 CPU 대기의 원인을 파악하기 어려웠다고 설명한다.
🧩 CPU에서 ‘대기’ 하나만 보이면 서로 다른 원인이 같은 모양으로 뭉개진다. 이 발표의 개선은 GPU를 빠르게 하는 일에 앞서, 그 대기의 정체를 구분하게 하는 관측 장치다.

2. 숲길의 빵 부스러기, 브레드크럼

렌더 패스를 택배 상자라고 생각해 보겠습니다. 상자가 GPU 작업대에 들어갈 때 ‘진행 중’ 도장을 찍고, 나올 때 ‘완료’ 도장을 찍습니다. 중간에 GPU가 멈추면 마지막 도장을 읽습니다. 긴 작업 목록 속에서도 어느 상자 근처였는지 찾을 수 있습니다. 이 흔적이 RHI 브레드크럼입니다.

🔤 렌더 패스 — 화면을 만들기 위해 나눈 작업 한 덩어리다. 그림자 계산이나 가려진 물체를 거르는 일이 각각 한 패스가 될 수 있다.
패스 시작: [공유 메모리의 정수값 = 진행 중] ↓ GPU 작업 패스 끝: [같은 값 = 완료] ↓ 크래시 로그: [마지막 값] → 멈춘 위치의 단서
🎤 발표에 따르면 브레드크럼은 GPU와 공유하는 메모리 버퍼에 정수값을 기록한다. Render Graph Event Scope는 r.RDG.Event=1, RDG 패스 자동 마커는 r.RDG.Event=3에서 활용할 수 있다.
🧩 브레드크럼은 원인을 고쳐 주지는 않는다. 대신 ‘보고가 왔을 때의 풍경’이 아니라 ‘마지막으로 통과하지 못한 문’을 남긴다. 병렬 작업이 많을수록 조사 범위를 크게 줄인다.

3. 세 도구가 같은 장부를 보게 되다

예전에는 Stat GPU에서 이상을 본 뒤 Unreal Insights를 열면 서로 다른 숫자 때문에 다시 출발할 수 있었습니다. 새 구조에서는 세 도구가 RHI 브레드크럼이라는 같은 장부를 봅니다. 패스 이름도 렌더 스레드에서 시작해 워커 스레드에서 변환되고 GPU에서 실행될 때까지 유지됩니다.

🔤 프로파일링 — 프로그램이 어느 일을 얼마나 오래 했는지 시간을 재어 병목을 찾는 과정이다. 병목은 줄이 길게 선 좁은 계산대처럼 전체를 늦춘다.

🎤 발표는 Stat GPU, ProfileGPU, Unreal Insights가 단일 브레드크럼 데이터를 사용하도록 바뀌었고, GPU Profiler 2.0은 언리얼 엔진 5.6부터 도입됐다고 말한다.
🧩 같은 데이터는 도구를 하나로 만들지 않는다. 표는 빠르게 훑고, 덤프는 한 프레임을 남기고, 타임라인은 시간 관계를 보여 준다. 같은 사건을 다른 거리에서 보는 구성이다.

4. 여러 줄이 만나는 곳: 큐와 펜스

GPU에는 그래픽스 큐와 컴퓨트 큐처럼 여러 작업 줄이 있을 수 있습니다. 컴퓨트 큐가 계산을 끝내야 그래픽스 큐가 다음 장면을 시작할 수 있다면, 완료 신호가 필요합니다. 한쪽이 신호를 남기고 다른 쪽이 기다리는 약속이 펜스입니다.

🔤 큐(queue) — GPU에 들어갈 작업이 줄 서 있는 통로다. 그래픽스 큐는 화면 그리기, 컴퓨트 큐는 별도 계산을 처리할 수 있다.
🔤 펜스(fence) — 한 큐의 일이 끝났다는 신호와 그 신호를 기다리는 규칙이다. ‘다음 사람이 넘어가도 된다’는 표지판에 가깝다.
[컴퓨트 큐: 계산] --완료 신호--> [펜스 B] ↓ [그래픽스 큐: 펜스 B를 받을 때까지 Wait]
🎤 발표에서는 Busy를 셰이더 실행, Wait를 GPU 큐 대기, Idle을 CPU 제출 대기로 설명한다. 컴퓨트 큐의 Wait는 정상 패턴일 수 있지만, 그래픽스 큐의 Wait는 설계·완료 시점·리소스 전환을 살필 신호다. Idle이 0보다 크면 CPU 바운드의 단서다.

🧩 Wait가 있다는 사실만으로 버그라고 할 수 없다. 누가 누구를 기다리는지, 그 기다림이 다음 일을 앞당기기 위한 것인지까지 연결해야 한다. 펜스 화살표가 원인을 향한 방향표가 되는 이유다.

5. 한 작업자에게 몰린 일을 나누다

기존 RHI 스레드는 주문서를 번역하고, GPU에 제출하고, 완료 여부도 계속 물어보는 계산대였습니다. GPU가 끝났는지 반복해서 확인하는 방식을 폴링이라고 합니다. 확인 주기 사이에는 끝난 일을 늦게 알아챌 수 있습니다.

🔤 스레드 — 한 프로그램 안에서 일을 진행하는 작업자 한 명의 흐름이다. 독립적인 일은 여러 스레드에서 동시에 할 수 있다.
Before [렌더 스레드] → [RHI: 번역 + 제출 + 폴링] → [GPU] After [렌더 스레드] → [여러 워커: 병렬 번역] → [서브미션: 제출·배칭·펜스] → [GPU] ↓ 완료 알림 [인터럽트 스레드]
🔤 인터럽트 — 계속 물어보지 않아도, 일이 끝난 쪽이 먼저 ‘끝났다’고 알리는 방식이다. 초인종이 울릴 때만 문으로 가는 장면이다.
🎤 발표는 Parallel Translate로 여러 워커가 변환하고, 서브미션 스레드가 제출·배칭·펜스 신호를 맡으며, 인터럽트 스레드가 완료를 수신한다고 설명한다.
🧩 분리의 핵심은 작업자를 무작정 늘리는 데 있지 않다. 순서가 필요한 제출은 한곳에 두고, 독립적인 번역만 나눴다. ‘먼저여야 하는 일’과 ‘동시에 해도 되는 일’을 다른 자리에서 다룬 설계다.

6. 타임라인에서 GPU 버블 읽기

Insights에서 지수는 한 프레임의 그래픽스 큐와 컴퓨트 큐를 같은 시간축에 놓습니다. 둘 다 유휴 구간이면 GPU가 일을 못 받은 장면입니다. 컴퓨트의 Wait에서 그래픽스 쪽으로 펜스 화살표가 가면, 지수는 누구를 기다렸는지 따라갑니다.

🔤 파이프라인 버블 — GPU의 계산 능력이 있는데도 작업 줄이 비어 실제로 노는 구간이다. 공장 기계가 다음 부품을 기다리는 빈 시간과 같다.
[그래픽스 Busy] ────┐ └─ 펜스 번호 19959 이후의 준비 지연 → [컴퓨트 시작] [컴퓨트 Wait] ────────┘ [그래픽스 Idle] + [컴퓨트 Idle] → CPU 제출 지연을 의심
🎤 발표는 Insights가 펜스 화살표와 고유 번호를 보여 주며, 펜스 번호 19959 뒤 검은 영역을 새 셰이더 실행 준비의 레이턴시로 설명한다. 모든 큐가 유휴이면 CPU 측 문제를 바로 파악할 수 있다고 했다.

7. 크래시를 한 번에 맞히지 말고 좁힌다

‘맵을 열었더니 멈췄다’는 제보를 받으면 먼저 깨끗한 재현 환경부터 만듭니다. 드라이버를 최신으로 바꾸고, 무거운 백그라운드 작업과 GPU 메모리 사용량을 확인합니다. 그 뒤 브레드크럼으로 마지막 위치를 잡고 조건을 하나씩 꺼 봅니다.

🔤 TDR — GPU 작업이 OS가 정한 시간 안에 끝나지 않을 때 운영체제가 문제로 판단하는 타임아웃이다. 발표에서는 윈도우 기준 보통 2초라고 설명한다.
🔤 페이지 폴트 — 이미 해제했거나 아직 메모리에 올라오지 않은 자원, 또는 접근하면 안 되는 메모리 영역을 읽으려 할 때 생길 수 있는 오류다.
1. 재현 환경 점검 → 2. -gpucrashdebugging / -gpu breadcrumbs로 흔적 수집 → 3. 기능을 켜고 끄며 조건 축소 → 4. -onethread / r.RDG.ImmediateMode / r.RDG.AsyncCompute 0으로 병렬성 확인 → 5. 밴더 도구와 라이브러리로 세부 원인 확인
🎤 발표 사례에서는 Nanite Virtual Shadow Map Culling의 Occlusion Culling 뒤 크래시를 브레드크럼으로 좁힌 뒤 Aftermath 덤프로 셰이더를 확인했다. 또 스킨 캐시 Read 대기와 동시에 펜스가 걸린 Async Compute 큐를 보며 데드락을 찾았고, D3D Residency Manager로 존재하지 않는 Mip 3 샘플링도 확인했다.
🧩 끄기 스위치는 해결책 후보이기 전에 질문 도구다. Async Compute를 껐더니 사라진다면 비동기가 나쁘다는 뜻이 아니라, 그 경로의 순서·자원 준비·동기화 중 어디를 볼지 정하는 실험 결과다.

8. 처음 GPU를 분석하는 개발자가 가져갈 5가지

이 발표는 한 번의 측정으로 판결하는 법보다, 패스 이름·큐 상태·펜스 방향·재현 조건을 같은 사건의 흔적으로 연결하는 법을 보여 준다.

  1. CPU의 대기만 보고 GPU 병목이라고 단정하지 않는다.
  2. 크래시 뒤에는 마지막 ‘진행 중’ 브레드크럼부터 찾는다.
  3. Stat GPU, ProfileGPU, Insights를 질문에 맞춰 고른다.
  4. 펜스 화살표로 누가 누구를 기다렸는지 따라간다.
  5. 재현 조건을 줄이고 엔진 정보와 밴더 도구를 함께 쓴다.
