코드 리뷰부터 지식 자산화까지 게임 코드베이스를 위한 AI - CodeOnBoard

AI가 빨리 만든 코드를, 팀이 끝까지 이해할 수 있게 만드는 여정. 발표 영상 보기 ↗

코드는 빨라졌는데, 왜 리뷰 줄은 더 길어졌을까

지수는 게임의 아이템 기능을 고친다. AI가 몇 분 만에 바꾼 코드를 내놓는다. 그런데 지수는 그 코드가 기존 보상 화면까지 건드리는지 혼자 판단할 수 없다. 선배에게 리뷰를 부탁하고, 선배는 하던 일을 멈춰 코드를 읽는다. 만드는 속도와 이해하는 속도가 갈라지는 장면이다.

🔤 이해 부채 — 코드는 저장소에 있지만, 왜 그렇게 동작하는지 아는 사람이 부족한 상태가 쌓이는 문제다. 나중에 고치거나 연결하려 할 때 읽는 시간이 이자로 붙는다.
[AI가 변경 코드 생성] → [개발자가 제출] → [리뷰어가 맥락을 찾음] ↓ 이해 시간이 병목이 됨
🎤 발표에서 인용한 Cortex 2026 엔지니어링 벤치마크는 PR 볼륨 20% 증가, 리뷰 시간 91% 증가를 보여 준다. PR당 문제 건수도 23.5% 더 늘었다고 설명한다.

게임 프로젝트에는 이미 오래된 코드와 떠난 원작자의 빈자리가 있다. 여기에 AI가 만든 코드까지 빠르게 들어온다. CodeOnBoard는 이 빈자리를 “코드를 더 만들기”가 아니라 “변경을 이해하고, 그 이해를 남기기”로 다룬다.

🧩 리뷰어 수만 늘리면 대기 줄은 잠시 줄 수 있다. 하지만 같은 맥락을 매번 처음부터 찾는다면 팀 전체의 읽기 비용은 계속 반복된다. 발표의 접근은 이 반복을 시스템 쪽으로 옮기는 선택으로 볼 수 있다.

첫 출발점: 한 줄의 변경만 보면 놓치는 장면

아이템 서비스의 AddItem 함수가 있다. 원래는 수량 0을 받지 않았다. 누군가 조건을 완화해서 0도 받게 바꾼다. 바뀐 줄만 보면 “입력 조건 하나를 느슨하게 했다”로 끝난다.

하지만 지수는 호출하는 쪽까지 따라간다. 그곳에는 AddItem이 성공하면 보상 획득 팝업을 띄우는 코드가 있다. 수량이 0인데도 성공으로 돌아오면, 아이템 없이 팝업만 뜰 수 있다. 이 연결은 변경된 줄 밖에 있다.

🔤 디프(diff) — 파일 전체가 아니라, 이번 제출에서 추가·삭제·수정된 줄만 모아 보여 주는 비교 화면이다.
Before: [수정된 AddItem 조건] → AI가 그 줄만 읽음 → 팝업 호출부를 못 봄 After: [수정된 함수 전체] → [호출한 곳] + [호출되는 곳] → 함께 읽고 리뷰
A · 리뷰 범위 바꾸기
지수는 “0을 허용”으로 바뀐 한 줄만 본다. 이 화면에는 보상 팝업을 띄우는 호출부가 없다.
🎤 CodeOnBoard는 변경 함수의 전체 내용과 호출자·피호출자를 코드베이스에서 검색한 뒤 리뷰하도록 구성했다고 발표에서 설명한다.
🧩 이 방식은 AI에게 정답을 미리 주는 일이 아니다. 사람이 옆 파일과 호출부를 펼쳐 보는 행동을 먼저 시키는 일이다. 그래서 리뷰 결과도 “변경 줄”이 아니라 “변경이 닿는 장면”을 근거로 말할 여지가 생긴다.

검색은 한 번의 정답이 아니라, 다음 리뷰의 힌트가 된다

코드에서 호출부를 찾으려면 검색식이 필요하다. 그런데 프로젝트마다 함수 호출을 쓰는 버릇이 다르다. 고정된 예시만 보고 검색식을 만들면, 어느 프로젝트에서는 맞고 다른 프로젝트에서는 헛돈다.

🔤 퓨샷(few-shot) — AI에게 작업 예시를 몇 개 보여 주고, 그 예시의 모양을 따라 다음 답을 만들게 하는 방법이다.
[이번 리뷰에서 검색 성공] → [성공한 검색 패턴 저장] ↓ [다음 리뷰] ← [저장된 패턴을 동적 퓨샷으로 넣음] ← 검색식 생성
시도장면대본의 결과
고정 퓨샷모든 코드베이스에 같은 예시를 건넴매칭률 43%, 완전 실패 35%
최대 3회 재생성실패할 때 AI에게 다시 요청매칭률은 회복, 재생성 비용으로 지연 증가
자기 개선 루프성공 패턴을 캐싱하고 다음 검색에 주입평균 매칭률 92%, 완전 성공 77%
🔤 캐시(cache) — 방금 얻은 결과를 가까운 저장소에 보관했다가, 같은 종류의 일이 다시 오면 빨리 꺼내 쓰는 메모다.
B · 자기 개선 검색 루프
버튼을 누르면 한 번의 검색이 다음 리뷰의 힌트가 되는 순서를 따라간다.
🎤 발표는 성공한 패턴을 Redis와 같은 저장소에 기억해 퓨샷으로 재활용하며, 재생성 비용과 지연도 감소했다고 말한다.
🧩 이 구조는 모델 자체가 매번 새로 학습한다는 뜻은 아니다. 발표에서 말한 것은 성공한 “검색 패턴”을 업무 흐름 안에 남기는 것이다. 같은 팀의 반복 작업일수록 그 기억이 더 가치 있어진다.

게임 개발 현장에 들어가려면, 이미 쓰는 문을 통과해야 한다

리뷰 엔진이 좋아도 개발자가 평소 쓰는 도구 밖에 있으면 결국 따로 열어 봐야 한다. CodeOnBoard는 팀이 이미 제출하고 검토하는 자리에서 결과가 보이도록 통합을 고려했다.

🔤 VCS(버전 관리 시스템) — 파일의 변경 이력을 기록하고, 여러 사람이 같은 프로젝트를 함께 고치게 돕는 도구다. 발표에는 GitLab, SVN, Perforce가 나온다.
[개발자가 기존 워크플로에서 변경 제출] ↓ [CodeOnBoard가 리뷰] → [리포트: 변경 의도·품질] → [줄 단위 코멘트: 컨벤션·보안·품질] → [기획서와 구현의 준수 여부 확인]

게임 코드는 일반적인 프로그래밍 언어만 쓰지 않는다. 프로젝트 안에서 만든 스크립트 언어도 있다. 발표에서는 Tree-sitter 같은 도구로 이런 언어를 직접 파싱해 지원한다고 말한다.

🔤 파싱(parsing) — 글자로 된 코드를 컴퓨터가 “함수 이름”, “조건”, “호출”처럼 구조를 나눠 읽는 일이다. 문장을 단어와 문장 성분으로 나누는 것에 가깝다.
🧩 통합과 파싱은 화면 꾸미기 문제가 아니다. 리뷰 대상이 저장소의 실제 변경과 언어의 실제 구조를 가리켜야, 앞에서 말한 호출자·피호출자 검색도 이어질 수 있다.

AI 리뷰를 먼저 세우면, 사람 리뷰의 자리가 바뀐다

기존에는 준호가 코드를 고치면 선배 한 명과 마주 앉아 리뷰할 시간을 기다렸다. 선배는 리뷰 요청이 들어올 때마다 하던 작업의 맥락을 끊었다. CodeOnBoard를 도입한 팀에서는 준호가 개발 뒤 실시간 AI 리뷰를 먼저 받고, 마지막 단계에서 팀 리뷰를 한다.

Before [개발자] ─대기→ [시니어 대면 리뷰] ─→ 수정 After [개발자] → [실시간 AI 리뷰] → [팀이 최종 검토] → 수정
🎤 발표에서 소개한 넥슨의 한 클래식 게임 개발팀은 리뷰 시간이 95% 절감됐다. 건당 한두 시간이던 시간이 5분~20분이 됐고, 연간 단순 환산은 670시간에서 33시간으로 줄었다.

리콜(recall)은 실제 이슈와 버그 가운데 도구가 찾아낸 비율이다. 발표의 오픈소스 기반 오프라인 테스트에서는 Python과 Java 리콜 수치를 제시하며, 같은 기준에서 글로벌 주요 도구 대비 1.5배 이상의 리콜을 기록했다고 설명한다. 자동자막의 Python 수치는 불명확하므로 여기서는 인용하지 않는다.

🧩 95%는 “사람이 더 이상 리뷰하지 않는다”는 수치가 아니다. 대본의 바뀐 순서에는 최종 팀 리뷰가 남아 있다. 먼저 넓은 범위를 빠르게 훑고, 사람은 더 판단이 필요한 곳에 시간을 쓰도록 재배치한 구조다.

창고 같은 코드베이스를, 찾을 수 있는 도서관으로

새로 온 개발자 민지는 “데미지 계산이 어디 있지?”를 묻는다. 파일은 수백 곳에 있고 문서는 낡았다. 코드 전체를 AI에게 다시 건네도, 다음 대화에서는 그 맥락이 사라질 수 있다. 발표는 이 상태를 책은 쌓였지만 분류표가 없는 창고에 비유한다.

🔤 코드베이스 자산화 — 코드를 단순 파일 모음으로 두지 않고, 구조·의미·관계를 쌓아 반복해서 찾고 설명할 수 있게 만드는 일이다.
창고: [파일이 쌓임] → “어디에 무엇이 있지?” 도서관: [분류표] + [비슷한 책장] + [책 사이 연결] → 질문으로 찾고 맥락까지 봄

발표의 목표는 이 축적물을 하나의 컨텍스트 레이어로 만드는 것이다. AI가 리뷰·문서·질의에 답할 때 필요한 부분을 이 기반에서 꺼내 쓰는 그림이다.

🔤 인덱싱(indexing) — 많은 파일을 나중에 빨리 찾도록 미리 정리해 두는 일이다. 책 제목과 위치를 목록에 적어 두는 것과 같다.
🧩 전체 코드를 매 세션마다 다시 읽는 방식은 질문 하나마다 창고를 처음부터 뒤지는 모습에 가깝다. 자산화는 답을 고정해 두기보다, 다음 질문을 위한 길과 연결을 남기려는 설계로 해석할 수 있다.

같은 코드를 세 개의 서랍에서 본다

민지가 데미지 함수를 찾을 때 이름을 알고 있다면 분류표가 유용하다. 이름은 몰라도 “피해량을 계산하는 곳”이라는 뜻을 알고 있다면 비슷한 책장으로 가야 한다. 또 그 함수가 무엇을 부르고 누가 부르는지 보려면 책 사이의 인용선을 따라가야 한다.

저장소도서관 비유CodeOnBoard가 담는 것
RDB카탈로그함수·클래스 이름, 경로, 언어 같은 구조화된 정보
벡터 DB비슷한 주제의 책장함수·클래스 요약을 인베딩해 의미가 비슷한 코드 검색
지식 그래프참고문헌과 인용 관계함수·클래스 사이 관계를 쌓아 영향 추적
🔤 인베딩(embedding) — 글의 뜻이 비슷한지 계산할 수 있도록, 요약을 숫자 묶음으로 바꿔 저장하는 방법이다. 같은 주제의 책을 가까이 놓을 수 있게 하는 좌표표처럼 생각하면 된다.
🔤 지식 그래프 — 대상들을 점으로, 그 사이의 호출·의존·상속 같은 연결을 선으로 그려 저장하는 구조다.
1단계: [언어별 정적 분석] → [RDB에 구조 저장] + [요약·인베딩 → 벡터 DB] 2단계: [코드 관계 분석·분류·정제] → [AI가 의미 부여] → [지식 그래프]
C · 문서에 필요한 맥락 고르기
서랍 하나를 눌러, 민지가 어떤 단서를 얻는지 확인해 보자.

처음 문서 생성은 벡터 DB만으로 시작했다. 하지만 호출·의존·상속 관계의 맥락이 끊겨 요약의 요약 같은 문서가 나왔다. 관계를 더한 뒤에는 영향도 설명하고 함수·클래스를 추적할 수 있게 됐다고 발표는 설명한다.

🧩 의미 검색은 “무슨 일을 하는가”에 강하고, 그래프는 “무엇과 이어지는가”에 강하다. 발표가 두 가지를 함께 둔 이유는 함수 설명만으로는 변경의 파장을 말하기 어렵기 때문으로 읽을 수 있다.

문서 자동 생성의 마지막 판단은 사람이 한다

AI가 코드 관계 위에서 목차 초안을 만들었다고 하자. 자주 참조되는 로깅, 이벤트 처리, 데이터 직렬화 도구가 앞쪽 목차를 차지할 수 있다. 하지만 게임의 핵심이 보상 시스템이라면, 이 목차는 새 입사자에게 잘못된 출발점을 준다.

🔤 휴먼 인 더 루프(human-in-the-loop) — AI가 초안을 만들되, 사람이 중간에 보고 선택·수정·승인하는 방식이다.
[지식 그래프] → [AI가 목차 초안] ↓ [사람이 추가·삭제·순서 편집] ↓ [확인] → [AI 본문 생성] → [다이어그램 생성] → [기술 문서]
🎤 발표는 완전 자동 목차에서 로깅·이벤트 처리·데이터 직렬화 유틸이 주요 목차가 되는 문제를 겪었다고 말한다. 그래서 사람이 목차를 편집하고 최종 컨펌한 뒤 문서를 생성하는 흐름으로 바꿨다.

이 문서는 신규 합류자에게는 온보딩의 시작점을, 개발자에게는 문서 작성·갱신 부담을 줄이는 길을, PM과 기획자에게는 코드를 읽지 않고도 구조를 보는 길을 제공한다. 또한 에이전트와 CLI에서는 “데미지 계산 로직 어디?”처럼 질문해 자산화된 지식 위의 답을 받을 수 있다.

🧩 자동 생성의 품질은 문장만 그럴듯한지로 끝나지 않는다. “무엇을 먼저 설명할지”는 도메인 판단이다. 발표의 사람 편집 단계는 AI의 생산성과 사람이 가진 우선순위 판단을 서로 다른 자리에서 쓰게 한다.

처음 접하는 개발자가 가져갈 5가지

  1. 리뷰의 단위는 바뀐 줄이 아니다. 호출자와 피호출자까지 따라가야 변경이 만든 장면을 볼 수 있다.
  2. 검색 성공은 다음 검색의 자산이 될 수 있다. 성공 패턴을 남기면 팀의 반복 작업이 조금씩 덜 낯설어진다.
  3. 코드 자산화는 파일을 복제하는 일이 아니다. 구조, 의미, 관계를 각각 보관해 질문에 맞는 길을 만드는 일이다.
  4. 문서 생성에도 사람의 판단이 필요하다. AI는 초안을 빠르게 만들고, 사람은 무엇이 핵심인지 결정한다.
  5. 자율화가 가까워져도 검수와 의사결정은 남는다. 발표의 로드맵도 AI가 테스트·분석·변경을 돕고 최종 결과는 사람이 검토하는 그림이다.
🎤 발표는 자율 테스트 생성의 Python 기반 POC를 진행했고, 앞으로는 이슈 등록부터 분석·계획·코드 변경·리뷰·자동 테스트까지 이어지는 엔드투엔드 자동화를 제시한다. 동시에 할루시네이션과 검색 품질·정확도를 남은 과제로 언급한다.
