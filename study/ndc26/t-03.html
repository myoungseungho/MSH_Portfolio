How we track and analyze every bullet fired

한 발의 총알부터 경기 한 판까지: Embark의 이벤트 수집, 요약, 분석 도구. 발표 영상 보기 ↗

총알 한 발 뒤에는 어떤 질문이 남을까

지수와 준호가 한 판에 들어갔다고 하자. 지수가 먼저 총을 쏜다. 운영팀은 단순히 “총을 쐈다”에서 멈추지 않는다. 이 탄환이 맞았는지, 누가 먼저 싸움을 시작했는지, 피해량이 이상하지 않은지를 나중에 물을 수 있어야 한다.

미니건처럼 짧은 시간에 많은 탄환을 쏘는 무기도 있다. 이런 장면을 재현하려면 플레이어 위치와 명중도 함께 남겨야 한다.

🎤 Embark는 1,000종이 넘는 이벤트를 추적한다. ARC Raiders가 가장 활발했을 때 하루 1,000억 건이 넘는 이벤트, 하루 30TB의 데이터를 추적했다. 발사 뒤 BigQuery에서 명중 여부를 조회할 수 있기까지 지연 시간은 2초 미만이다.
🔤 이벤트(event) — 게임이나 운영 도구에서 실제로 일어난 일 한 건을 적은 기록이다. “지수가 총을 쐈다”, “준호의 체력이 줄었다”처럼 누가 무엇을 했는지 담는다. 발표에서는 한 번 정한 이벤트 정의를 바꾸지 않는다고 설명한다.
[지수의 발사] → [발사 이벤트] ├→ 명중·피해량을 살펴 밸런스 확인 ├→ 비정상 행동을 살펴 치터 조사 └→ 누가 먼저 쐈는지 계산해 매칭 분류

ARC Raiders에서는 먼저 공격하는 정도로 플레이어를 나눈다. 싸움을 자주 여는 사람은 비슷한 사람과, 먼저 싸우지 않는 친화적인 사람은 비슷한 사람과 만나게 하려는 목적이다.

기록을 데이터팀의 서랍에 넣지 않기

데이터를 모아도 분석가에게 요청서를 보내고 며칠을 기다려야 한다면, 맵을 고치는 디자이너는 지금 본 문제를 확인하기 어렵다. 발표자는 데이터를 데이터팀이 대신 해석하는 물건이 아니라, 개발자와 맵 디자이너가 직접 쓰는 물건으로 만들려 한다고 말한다.

🔤 대시보드 — 자동차 계기판처럼 숫자와 그래프를 한 화면에 모아 보는 화면이다. 반복해서 확인할 상태를 빠르게 보는 첫 관문이다.
[대시보드] 반복해서 보는 전체 상태 ↓ “이 이상한 경기 한 판은 무엇이지?” [Round Viewer] 경기 한 판을 한 행으로 찾아냄 ↓ [Map Replay] 그 경기 안에서 이동·사망·체력을 다시 봄

Embark의 내부 운영 도구는 Game Tools다. 대부분의 대시보드는 전 직원에게 열려 있다. Round Viewer는 BigQuery에 매개변수를 넣어 실행하는 질의로 만든 도구다. 서버 크래시 탐색, 로그 연결, 플레이어가 오늘 한 경기 확인에 쓰인다.

🎤 Map Replay는 한 경기의 이벤트를 재생해 이동·사망·체력 등을 보여 준다. 맵 디자이너, 안티치트 담당자는 이 요약 화면으로 플레이어가 너무 빨리 움직였는지 또는 금지된 곳에 먼저 갔는지 살핀다.

한 판을 지도로 펴면 보이는 것

맵 디자이너가 밀어내기 목표가 있는 맵을 고친다고 하자. 여러 경기의 위치 기록을 한 장의 지도에 겹친다. 사람이 많이 지나간 곳은 진하게 보이고, 저격하기 좋은 탑처럼 따로 모이는 장소도 드러난다.

🔤 히트맵(heat map) — 여러 기록을 지도 칸마다 세어, 많이 나온 칸을 더 진하게 색칠한 그림이다. 온도가 아니라 기록의 밀도를 색으로 표현한다.
[경기 1의 위치] + [경기 2의 위치] + [경기 3의 위치] ↓ 칸별로 횟수 세기 [2D 히트맵] ↓ 게임 엔진 안에서는 [복셀 히트맵]으로 보기
🔤 복셀(voxel) — 3차원 공간을 작은 블록으로 나눈 한 칸이다. 2D 그림의 픽셀을 입체 공간으로 늘렸다고 생각하면 된다.
🎤 발표에는 경기 여러 판을 합친 히트맵과 Unreal Engine 안의 복셀 히트맵이 소개된다. 밀도와 시점을 조절하는 필터도 추가했다. 해크데이에는 최근 며칠의 GeoIP 데이터를 세계 지도 위에 보이는 도구도 만들었다.

새 이벤트를 만들면, 통로도 함께 만들어진다

“새 무기의 명중 이벤트를 추가하자”라고 결정했다고 하자. 표를 만들고, 메시지 통로를 만들고, 실패한 메시지를 모을 상자를 준비해야 한다. 이 일을 매번 손으로 맞추면 빠진 부품이 생긴다.

발표의 이벤트 생성 서비스에서는 웹 화면에서 새 이벤트를 만들 때 이 준비물을 함께 만든다. 각 이벤트는 자기만의 형태를 가진다.

🔤 스키마(schema) — 종이 양식의 빈칸 규칙이다. 어느 칸이 있고, 각 칸에 숫자·글자 중 무엇을 적어야 하는지 정한다. 강한 타입은 그 칸에 엉뚱한 종류의 값을 넣지 못하게 하는 규칙이다.
[이벤트 정의를 생성] ├→ [Pub/Sub 스키마] 사건 기록 양식 ├→ [Pub/Sub 토픽] 메시지를 넣는 전용 우체통 ├→ [구독·Dead letter queue] 받기 / 못 받은 편지 보관 ├→ [BigQuery 테이블] 분석용 보관함 └→ (선택) [NX log 구독]
🔤 Pub/Sub — 발신자가 우체통(토픽)에 편지를 넣고, 구독자가 그 우체통을 받아 가는 메시지 전달 방식이다. Dead letter queue는 처리하지 못한 편지를 따로 모아 두는 상자다.
🎤 이벤트를 만들면 Pub/Sub 스키마·토픽·구독·dead letter queue·BigQuery 테이블이 생성된다. 선택적으로 NX log 구독도 만든다. Pub/Sub에 들어온 이벤트는 보통 1초 안에 BigQuery 테이블에 도착한다.

발사 이벤트는 어느 길로 BigQuery에 갈까

기록을 보내는 곳은 하나가 아니다. 관리 화면과 백엔드는 바로 보낼 수 있다. 게임 클라이언트는 플레이어 PC에서 보낸다. 경기 서버는 한 판이 끝나면 사라졌다가 다음 매치에 새로 켜진다. 그래서 서버 옆에는 별도 작은 프로그램을 붙였다.

🔤 사이드카(sidecar) — 큰 프로그램 옆에서 함께 실행하며 보조 일을 맡는 작은 프로그램이다. 게임 서버 본체를 바꾸지 않고도 기록 처리를 붙일 수 있다.
관리 화면·백엔드 ──직접──→ [Pub/Sub] → [BigQuery] 게임 클라이언트 ─HTTPS→ [Client to Pub/Sub] → [Pub/Sub] → [BigQuery] 게임 서버 ─Unix domain socket→ [Event Reactor] → [Pub/Sub] → [BigQuery]
🔤 Unix domain socket — 같은 컴퓨터에서 실행 중인 두 프로그램이 짧은 통로로 데이터를 주고받는 방법이다. 여기서는 게임 서버와 바로 옆 Event Reactor가 쓴다.
🎤 매치메이킹이 끝나면 Unreal Engine 게임 서버가 클라우드 또는 사내 가상 머신에서 켜진다. 게임 서버는 서버 틱마다 이벤트를 모아 Event Reactor로 보낸다. 초당 30번, 즉 1/30초 동안 일어난 일을 마이크로 배치로 보내며 Event Reactor는 이를 Unix domain socket으로 받는다.

발표에 나온 실제 구성요소를 순서대로 보여 주는 학습용 흐름이다.

Event Reactor는 왜 단순 전달자가 아닐까

준호가 맵을 달린다고 하자. 위치 이벤트가 여러 번 들어온다. 나중에 “이번 판에서 준호가 얼마나 달렸나?”를 알고 싶다면 모든 위치를 다시 꺼내 차례로 빼고 더할 수 있다. 하지만 경기 중에 바로 요약을 만들면 끝날 때 답을 손에 들고 있을 수 있다.

🔤 상태 기계(state machine) — 들어오는 사건을 보고, 지금까지 기억한 값을 바꾸는 프로그램이다. 여기서는 “준호의 마지막 위치”를 기억해 두었다가 다음 위치가 오면 이동 거리를 더한다.
[준호 위치 A] → 마지막 위치를 A로 기억 [준호 위치 B] → A와 B의 거리 계산 → 누적 이동 거리 더하기 → 마지막 위치를 B로 교체 [경기 종료] → 누적값을 요약 통계로 보냄

Event Reactor는 피해량, 접속 시간, 마지막 위치 같은 값을 경기 도중 쌓는다. 경기 종료 뒤에는 실시간으로 Pub/Sub에 보내던 이벤트와 별도로, 그 경기 전체 이벤트가 든 파일 하나를 GCS에 보낸다.

🔤 GCS — Google Cloud Storage. 파일을 보관하는 클라우드 저장소다. ETL은 데이터를 꺼내고, 필요한 모양으로 바꾸고, 다른 곳에 넣는 작업을 묶어 부르는 말이다.
🎤 경기 종료 시 Event Reactor는 그 라운드의 모든 이벤트가 담긴 GCS 파일 하나를 보낸다. 한 경기에는 수십만 건, 경우에 따라 10만 건이 넘는 이벤트가 들어갈 수 있다. 발표자는 이 방식으로 ETL을 자주 돌리지 않아도 지연이 낮은 요약 통계를 만들 수 있다고 설명한다.
Before: [BigQuery의 위치 행들] → 나중에 SQL로 이전 위치를 찾아 거리 계산 After: [Event Reactor가 위치를 받을 때마다] → 즉시 거리 누적 → [경기 끝 요약]
🧩 발표자가 SQL의 window function과 세션 시작·종료 처리가 복잡해진다고 말한 까닭은, “바로 전 위치”를 매 행마다 다시 찾아야 하기 때문이다. 옆에서 상태를 기억하는 코드는 그 순서를 자연스럽게 가진다.

저장용 BigQuery와 빠른 화면용 DuckDB를 나누기

같은 “피해”라도 무기가 바뀌며 이벤트 이름이 여러 번 생길 수 있다. 분석가가 매번 모든 이름을 기억하게 하면 질문을 시작하기 어렵다. 원본 표는 그대로 두고, 분석할 때만 여러 원본을 하나의 이름으로 보게 한다.

🔤 semantic class — 여러 이벤트를 분석할 때 하나로 묶어 보여 주는 보기(view)다. 예를 들어 버전이 다른 적 피해 이벤트들을 ‘적 피해’라는 한 창구로 모은다. UNION ALL은 여러 표의 행을 위아래로 이어 붙이는 SQL 연산이다.
[변경하지 않는 이벤트 표들] ─UNION ALL→ [바꿀 수 있는 semantic class 보기] ↓ [스케줄러] → [Parquet 파일] → [Analytics Data Service] → [DuckDB] → [대시보드]
🔤 Parquet — 표 데이터를 파일로 저장하는 형식이다. DuckDB — 한 인스턴스에서 실행하는 오픈 소스 분석용 데이터베이스다. 발표에서는 데이터 양이 낮을 때 BigQuery보다 응답이 빠르다고 소개한다.
🎤 자체 스케줄러는 날짜 범위 SQL, 그래프 형태의 의존성, 사용자 정의 함수, 품질 검사, backfill을 지원한다. 새 Parquet 파일이 생기면 Pub/Sub 이벤트가 나가고 Analytics Data Service가 이를 받아 DuckDB에 넣는다. 대시보드는 DuckDB에 매개변수를 넣어 실행하는 SQL 질의다.
B · 원본을 고치지 않는 분석 창구
[enemy_damage_v3 표] 변경하지 않음 [enemy_damage_v4 표] 변경하지 않음 분석가는 표 이름을 각각 알아야 한다.
원본 기록을 보존한 채, 분석할 때 쓰기 쉬운 창구를 따로 둔다.

빠르되, 전송량만큼만 비용이 든다

발사 직후 기록을 보내면 즉시 하나씩 전송할 수도 있다. 그러나 Pub/Sub의 최소 과금 단위는 1KB다. 아주 작은 편지를 자주 보내면 빈 봉투에도 같은 최소 비용이 붙는다. 그래서 발표의 SDK는 최대 1초까지 이벤트를 모아 보낸다.

Before: [작은 이벤트 1건] [1건] [1건] [1건] → 각각 전송 After: [최대 1초 동안 사건을 모음] → [한 묶음 전송]
🎤 SDK는 비용을 줄이기 위해 이벤트를 최대 1초까지 배치한다. Pub/Sub의 최소 과금은 1KB다. 발표자는 Pub/Sub과 BigQuery가 전송량에 따라 비용과 규모가 함께 변하고, 적은 데이터에서는 하루 몇 센트 수준부터 시작한다고 설명한다.

비용을 계산하는 도구가 아니다. 최소 과금 단위가 있을 때 묶음 전송이 왜 등장하는지 보여 주는 모형이다.

🎤 발표자는 현재 수집 구조가 일관되게 1초 미만 또는 1초 수준의 지연 시간을 보이며, 출시 후 이벤트 수집 문제는 없었다고 말한다. 이전 Dataflow 기반 수집과 비교해 Pub/Sub의 BigQuery destination subscription이 비용을 크게 줄였다고 평가한다.

처음 접하는 개발자가 가져갈 5가지

  1. 관찰할 질문부터 잡는다. 총알 하나를 남기는 일은 치터 탐지, 밸런싱, 매칭이라는 실제 질문으로 이어진다.
  2. 이벤트는 재사용 가능한 사실 기록이다. 한 사건의 시간순 기록은 지표, 모니터링, 버그 조사에 서로 다른 모습으로 쓰인다.
  3. 경기 서버 옆에서 요약하면 경기 중 문맥을 잃지 않는다. Event Reactor는 이전 위치처럼 바로 전 상태를 기억하며 요약을 만든다.
  4. 원본과 분석 창구를 분리한다. 변경하지 않는 이벤트 표 위에 semantic class 보기를 얹어 분석의 이름을 단순하게 한다.
  5. 도구는 사용자와 질문에 맞춘다. 대시보드만으로 끝내지 않고 Round Viewer, Map Replay, 엔진 안의 히트맵처럼 각 직군의 화면을 만든다.
