[메이플스토리M] DevSecOps 전환기
라이브 게임을 멈추지 않고 바꾸는 비법

사람의 기억에 쌓인 인프라를 코드와 안전장치 위로 옮긴 전환기. 발표 영상 보기 ↗

1. “잘 돌아가는데”가 가장 위험한 순간

새 서버를 늘려야 하는 날, 운영자가 콘솔을 열고 예전에 들은 규칙을 떠올린다. 어느 월드는 사설 IP 끝자리가 10~40번이고, 다른 월드는 50~70번이다. 작업을 마친 뒤 왜 그렇게 했는지는 메모에 남지 않을 수 있다. 다음 담당자는 다시 사람을 찾아야 한다.

발표팀은 이 문제를 도구 하나의 부족이 아니라, 변경이 기록·검증·승인되는 운영 방식의 부재로 보았다.

🎤 메이플스토리M은 2016년부터 서비스 중이며, 동시 접속 20만 명의 유저가 즐기는 모바일 라이브 게임이다. 국내·글로벌·일본을 운영하고, 관리 리소스는 1,000대 이상이며 다수 리전과 월드 구조를 가진다.
🔤 DevSecOps — 서비스를 만드는 사람, 운영하는 사람, 보안을 확인하는 사람이 같은 흐름에서 함께 일하는 방식이다. 처음 설계할 때부터 보안 확인을 넣고, 변경은 빠르게 하되 위험한 변경은 멈추게 한다.
예전: [운영자 기억] → [콘솔에서 직접 클릭] → [변경 이유가 흩어짐] 바꾼 뒤: [변경 의도] → [코드와 기록] → [검증·승인] → [안전하게 적용]
🧩 “안 건드리는 것”은 위험을 없애는 선택이 아니다. 타이어가 닳은 채로 차를 계속 모는 것처럼, 지식 의존과 수동 변경이라는 위험을 미래로 미루는 선택으로 볼 수 있다.

2. 도구보다 먼저, 함께 같은 말을 쓰는 팀

Terraform과 Git을 깔아도 팀마다 쓰는 방식이 다르면 새 혼란이 생긴다. 한 팀은 바로 배포하고 다른 팀은 검토를 먼저 한다면, “배포했다”라는 말조차 서로 다른 행동을 가리킨다.

일곱 팀의 구성원이 모인 TF에서 SE와 DBA는 실제 장애가 날 수 있는 지점과 운영자의 부담을 전했다. 아키텍트는 공통 구조를 설계했고, 개발자는 반복 작업과 검토 단계를 자동화했다. 먼저 각자의 방식을 드러내고 맞추는 시간이 필요했다.

🔤 Git — 파일의 바뀐 기록을 남기고 여러 사람이 바꾼 내용을 비교하게 하는 저장소 도구다. 여기서는 ‘누가 언제 무엇을 왜 바꿨는가’를 다시 찾는 장부 역할을 한다.
🎤 발표자는 Git을 처음에는 저장소로만 썼고, 브랜치 전략과 CI/CD 파이프라인은 익숙하지 않았다고 말했다. 데일리 스크럼과 2주 회고를 거치며 변경이 기록되고 리뷰되어야 한다는 사고방식을 팀이 공유하게 되었다고 설명했다.
[현장: 장애와 운영 규칙] ─┐ [설계: 공통 구조와 표준] ──┼→ [공통 언어] → [같은 변경 절차] [개발: 자동화 장치] ──────┘
🧩 표준은 문서로 선언하는 순간 작동하지 않는다. 바쁜 날에도 팀원이 그 절차를 선택할 만큼 현장의 불편과 위험을 함께 줄여야 기본값이 된다.

3. 한 장의 의도를, 세 층의 코드로 번역하기

서버 다섯 대를 더 늘린다고 해 보자. 단층 구조에서는 엔지니어가 역할별 폴더를 찾아 서버 수량과 타입을 고치고, 또 다른 폴더에서 설정을 고친다. 파일을 하나 놓치면 사람의 기억이 다시 안전장치가 된다.

발표팀은 운영자가 YAML 파일에 의도만 적는 첫 층을 두었다. 가운데 층은 IP, 호스트명, AMI, 보안 규칙을 계산한다. 마지막 층이 AWS 리소스를 만든다. 이것이 모듈 인 모듈 3단 계층이다.

🔤 YAML — 들여쓰기와 짧은 항목으로 정보를 적는 텍스트 형식이다. 여기서는 “어느 리전에 어떤 역할의 서버를 몇 대 둘지”를 적는 종이로 생각하면 된다.
🔤 인프라 매니페스트 — 여러 리전·월드·역할의 서버 수량과 타입을 한곳에 적어 둔 목록이다. 코드를 어디서 고칠지 기억하는 대신 무엇을 바꿀지만 적게 한다.
[L1: YAML에 ‘서버 5대 추가’] → [L2: IP·호스트명·AMI·보안 규칙 계산] → [L3: AWS 리소스 생성]
원래는바꾼 뒤에는
여러 폴더와 파일을 찾아 수정매니페스트 한 장에서 의도를 수정
운영 규칙이 코드 곳곳에 섞임가운데 계층이 복잡한 규칙을 계산
🎤 당시 운영 규칙에는 월드별 사설 IP 범위를 지키는 조건이 있었고, 대만 일부 통신사의 지연 문제를 위한 라우팅 때문에 기존 공인 IP를 계속 재사용해야 하는 제약도 있었다.
🧩 세 층은 복잡함을 없애기보다 자리를 정해 준다. 운영자는 ‘무엇을 바꿀지’에, 로직 담당자는 ‘어떻게 계산할지’에 집중할 수 있어 여러 서비스로 넓힐 때 규칙을 다시 흩뿌리지 않게 된다.

4. 이미 살아 있는 서버를 코드의 기억에 연결하기

한 달 전 콘솔에서 만든 EC2를 코드가 바꾸려면, 코드 속 이름과 AWS의 실제 서버가 같은 대상이라는 연결이 필요하다. 그 연결을 잃은 Terraform은 무엇을 바꿔야 하는지 알 수 없다.

🔤 Terraform — 서버와 네트워크 같은 인프라의 원하는 모양을 파일로 적고, 그 파일을 바탕으로 만들거나 바꾸는 도구다.
🔤 스테이트(tfstate) — Terraform이 코드와 실제 AWS 리소스의 짝을 기억하는 기록 파일이다. 주소록에서 ‘코드의 이 항목’과 ‘AWS의 이 실제 리소스’를 연결하는 장부에 가깝다.
[코드의 리소스 이름] ── 짝 기록 ── [tfstate] ── 실제 ID ── [AWS의 이미 있는 리소스]

스테이트에는 코드 쪽 식별자인 타입과 네임, AWS에 실제로 있는 리소스의 아이디가 맞물려야 한다. 셋 중 하나가 어긋나면 Terraform이 기존 것을 새로 만들거나 없애거나 교체해야 한다고 판단할 수 있다.

🎤 발표에서는 타입·네임·아이디를 스테이트의 세 핵심 필드로 설명했다. EC2 한 대에도 시큐리티 그룹, Elastic IP, EBS 등 연관 리소스를 연결해야 하므로 수동 작업에는 최소 12개 값을 넣어야 한다고 말했다.
🧩 스테이트가 ‘최종 보스’가 된 이유는 파일 형식 때문만이 아니다. 라이브 환경에서는 매핑 실수 하나가 실제 리소스의 삭제·재생성 판단으로 이어져 작은 장부 오류가 서비스 중단 위험으로 커진다.

5. 임포트 자동화: 가장 닮은 짝부터 찾기

사람이 AWS 콘솔에서 ID를 찾아 하나씩 넣을 수는 있다. 하지만 서버 한 대와 주변 리소스를 수천·수만 번 연결해야 하는 상황에서는 지치지 않고 똑같이 정확한 사람이 필요하다. 발표팀은 그 반복을 도구로 옮겼다.

🔤 import — AWS에 이미 존재하는 리소스를 새로 만드는 기능이 아니다. 그 리소스를 Terraform이 관리하도록 스테이트 장부에 기록하는 기능이다.
[AWS 리소스를 발견] → [이름 태그로 후보 비교] → [타입·네임·아이디 생성] → [스테이트 편입 준비]

이름 태그를 바탕으로 네 단계 우선순위로 후보를 비교했다. 모듈명과 리소스명이 정확히 같은 후보부터 찾고, 맞지 않으면 둘을 포함한 후보, 모듈명만 포함한 후보처럼 점차 느슨하게 시도한다.

A · 스마트 매칭 우선순위 따라가기
1단계: 모듈명과 리소스명이 정확히 일치하는 이름 태그를 먼저 찾는다.

발표의 4단계 우선순위와, 실패 시 점진적으로 느슨한 매칭을 시도한다는 설명을 따라 만든 학습용 흐름입니다.

🎤 자동화 도구는 Terraform import 기능과 Python 등을 사용했다. 수동 반복 검증 시 인력 한 명 기준 최소 3개월에서 최대 1년이 걸릴 수 있는 작업에서 약 99% 수준의 작업 시간 절감 효과를 얻었다고 밝혔다.
🧩 이 자동화의 핵심은 ‘빠르게 편입’이 아니라 ‘매칭을 설명 가능한 순서로 좁히기’다. 후보가 적을수록 검증해야 할 장면도 선명해지고 스테이트 오염을 줄일 여지가 생긴다.

6. 코드는 바로 배포되지 않는다: 여러 번 멈춰 보는 길

운영자가 제니스 월드 게임 서버 수량을 23대에서 28대로 바꿨다고 해 보자. Git에 올린 변경은 곧바로 라이브에 닿지 않는다. AI 코드 리뷰가 새 코드와 기존 코드의 차이를 읽기 쉬운 말로 요약하고, 위험한 보안 변경을 살핀 뒤 문제가 있으면 머지를 막는다.

🔤 diff — 바꾸기 전 파일과 바꾼 뒤 파일을 나란히 놓고 다른 줄을 찾는 비교 결과다. 긴 코드를 다 읽기 전에 ‘서버가 5대 늘었다’ 같은 변화를 확인하는 재료가 된다.
🔤 파이프라인 — 변경이 통과해야 하는 정해진 작업 순서다. 공장에서 제품이 검사대를 차례로 지나가는 것처럼 각 단계가 앞 단계 결과를 받아 검사한다.
B · 변경 한 건이 지나가는 검사대
AI 코드 리뷰: diff를 비교하고 사람이 읽을 수 있게 변경을 요약한다.
[Git push] → [AI 코드 리뷰] → [merge] → [check] → [plan] → [AI assist] → [tag] → [사람이 수동 apply]
🎤 발표의 AI 코드 리뷰는 제니스 월드 게임 서버가 23대에서 28대로 증가한 변화를 요약하는 예를 들었다. 플랜에서 destroy나 replace가 감지되면 파이프라인은 자동 정지하고, 마지막 apply는 사람이 직접 눌러야 한다.
🧩 AI의 역할은 결정을 대신하는 사람이 아니라, 사람이 결정하기 전에 변화와 위험을 보이게 하는 검사대에 가깝다. 마지막 apply를 수동으로 둔 것은 속도보다 라이브 환경의 확인 가능성을 우선한 선택으로 해석할 수 있다.

7. 사고 뒤에 한 겹 더: 우회로까지 막기

발표팀은 전환 자체는 무장애로 마쳤지만 운영 중 사고를 겪었다. 파이프라인이 없어서가 아니라 파이프라인 밖으로 빠져나가는 길이 남아 있었기 때문이다. 안전장치를 거치지 않은 변경이 라이브에 적용되어 서비스 장애로 이어졌다.

그래서 플랜에는 인플레이스 업데이트처럼 보여도 실제 적용 때 내부적으로 리부팅이나 스톱이 일어나는 API가 있다면, 시스템이 그 위험을 감지해 차단하고 작업자에게 알리도록 보강했다.

처음: [안전한 파이프라인] → [사람이 우회로를 택하면?] → [라이브 변경] 보강: [변경] → [플랜 검사] → [재시작·중지 위험 감지] → [자동 차단] → [확인 후 재진행]
C · 적용 전, 시스템이 멈춰 세우는 장면
플랜 결과 확인
→
적용 대기
버튼을 눌러 시스템이 어떤 장면에서 진행을 멈추는지 확인해 보자.
🎤 발표팀은 전환 후 위험한 destroy·replace 변경을 감지하고 restart·stop API도 시스템이 감지할 수 있게 한 것을 안전성 성과로 제시했다.
🧩 안전한 절차는 ‘사람이 항상 지킨다’는 가정에 기대면 약해진다. 우회 경로와 실제 적용 시점의 행동까지 확인해야 절차가 조언이 아니라 시스템의 경계가 된다.

8. 처음 접하는 개발자가 가져갈 4가지

입력의 의도, 코드의 계산, 스테이트의 기억, 검증 파이프라인, 사람의 승인이 하나의 길로 이어졌다. 그래서 AI가 자연어를 해석하더라도 그 명령은 검증된 길을 반드시 지나게 할 수 있다.

🎤 발표팀은 운영 리소스 100%를 Terraform으로 코드화하고 모든 변경을 GitOps 파이프라인으로 처리할 수 있게 된 점, import 시간 99% 절감과 Git을 통한 변경 이력 100% 추적을 성과로 밝혔다. 자연어 한 줄로 다루는 Deploy Portal은 아직 상용 라이브가 아닌 데모 버전이라고 설명했다.
  1. DevSecOps는 도구가 아니라 사람에서 시작한다. 현장의 위험을 아는 사람과 공통 언어가 먼저 필요하다.
  2. 레거시는 안전장치를 쌓으며 옮길 수 있다. 의도, 계산, 리소스 생성을 나누고 하나씩 연결한다.
  3. 코드화에는 기억이 필요하다. 이미 살아 있는 리소스를 옮길 때 스테이트의 매핑은 코드만큼 중요하다.
  4. 안전은 승인 화면 하나로 끝나지 않는다. 위험한 결과와 우회로, 실제 적용 때의 재시작·중지까지 시스템이 확인해야 한다.
