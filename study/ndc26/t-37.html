메이플스토리 월드 자체 LLM 단풍 개발기

메이플스토리 월드 제작을 돕는 도메인 특화 LLM을, 데이터 생성부터 학습·검증·개선까지 따라간다. 발표 영상 보기 →

먼저, “코드 좀 짜 줘”가 막히는 장면

처음 월드를 만드는 유진은 일반 루아를 조금 안다. AI에게 “더블 점프 스크립트”를 부탁한다. 하지만 월드에서는 루아 문법만 맞아도 충분하지 않다. 스크립트 유형, 값의 형태, 서버와 클라이언트 중 실행할 곳까지 정해야 한다.

🔤 도메인 특화 모델 — 특정 현장에서 쓰는 말, 규칙, 도구를 따로 익힌 모델이다. 여기서는 메이플스토리 월드 제작에 필요한 M Lua와 API를 아는 챗봇을 뜻한다.
[유진: “더블 점프 만들어 줘”] → [일반 AI: 일반 루아식 코드 / 존재하지 않는 이벤트] → [에디터: 그대로 붙여도 동작을 보장할 수 없음] [같은 질문] → [월드 규칙·API를 아는 단풍] → [M Lua 형식 + 구현 설명]
🎤 발표에서는 ChatGPT·Claude·Gemini에 같은 질문을 했을 때, 프로퍼티·method·라이프사이클·이벤트가 메이플스토리 월드 방식과 다른 답변이 나왔다고 설명했다. 개발에는 500여 개 이상의 네이티브 API도 알아야 한다.
🧩 필요한 것은 코드를 길게 생성하는 능력만이 아니다. 붙여 넣을 환경의 규칙을 빠뜨리지 않는 능력이 먼저다. 규칙 하나가 틀리면 보기 좋은 코드도 출발선에서 멈춘다.

월드의 문법은 무엇이 다른가

유진의 첫 줄에는 단순 함수가 아니라 스크립트 유형이 들어간다. 값의 종류와 서버에 맞출지도 적는다. 게임 시작, 반복 실행, 끝나는 시점도 각자 다른 자리에 코드를 둔다.

🔤 라이프사이클 — 스크립트가 태어나고, 계속 움직이고, 끝나는 순서다. 가게의 개점 준비·영업·마감처럼 각 시점의 일이 다르다.
🔤 네이티브 API — 플랫폼이 미리 만든 기능의 손잡이다. 물리나 입력 같은 기능을 정해진 이름과 사용법으로 부른다.
알아야 할 것왜 코드에 남는가
유형·프로퍼티어떤 물건과 값을 만들지 에디터가 안다.
동기화·실행 공간값을 서버와 맞출지, 어디서 돌릴지 정한다.
라이프사이클·핸들러언제 실행하고 누가 보낸 사건을 받을지 적는다.
🎤 단풍은 API 사용법, 특정 기능 구현, 월드 제작 질의응답을 돕는 챗봇으로 소개됐다. 에디터 AI 어시스턴트에서 RAG 기반 AI와 LLM 단풍 모델을 선택하며, 현재 사용 가능한 것은 RAG 기반 AI라고 발표했다.

커뮤니티 데이터가 없을 때, 질문을 만드는 공장

챗봇에는 질문과 답의 짝이 필요하다. 공개된 대규모 월드 개발 커뮤니티가 없어, 팀은 API 문서·크리에이터 센터 가이드·공식 가이드 영상을 재료로 삼았다.

🔤 합성 데이터 — 사람이 쓴 문장을 그대로 모은 것이 아니라, 가진 자료를 바탕으로 새로 만든 학습용 질문·답변이다.
[API 문서 · 가이드 · 영상] → [토픽] → [서브토픽] → [구체 질문]

TransformComponent 문서에서 “사용법”을 고른다. 이어 ZRotation을 고른다. 그러고 나서 회전과 좌표 이동을 함께 묻는 질문을 만든다.

🧩 이 순서는 다양성과 구체성을 함께 잡는 장치다. 자료 없이 넓게 만들면 월드와 무관한 질문이 섞이고, 처음부터 너무 좁히면 비슷한 질문만 쌓일 수 있다.

답변 하나를 여러 역할로 조립하다

“더블 점프” 요청에서 누군가는 API를 찾고, 다른 역할은 M Lua 문법을 고치며, 또 다른 역할은 실행 위치를 살핀다. 답변 데이터를 한 번에 만들지 않은 이유다.

🔤 Expert Orchestration — 복잡한 일을 역할별 작업자가 순서대로 넘겨받는 방식이다. 식당의 재료·조리·검수 담당처럼 나눈다.
[질문] → [API Expert: Component·Service·Context 검색] → [M Lua Expert] → [Execute Space Expert] → [Output Expert] → [린터·필터링] → [학습 데이터]
🔤 린터 — 실행 전에 코드 문법 모양을 검사하는 도구다. 괄호와 철자를 먼저 살피는 단계이며, 실제 게임 동작까지 증명하지는 않는다.
🎤 자동 필터는 린터 기반 문법 오류와 유사도 기반 중복 질문을 제거했다. 이후 LLM이 자주 틀리는 패턴을 분석해 규칙 기반으로 수정하거나 제거하는 수동 필터링도 수행했다.
🧩 역할을 쪼개면 어디에서 틀렸는지 찾기 쉽다. 그러나 린터 통과는 “문장 모양”의 합격일 뿐, 월드 실행의 합격은 아니다.

모델에게 월드의 말을 먼저 가르치다: CPT와 FIM

가벼운 오픈소스 모델은 처음에는 월드를 모른다. 팀은 먼저 문서와 M Lua로 월드의 말과 문법을 익히게 했다.

🔤 Continual Pretraining (CPT, 추가 사전학습) — 기본 언어를 배운 모델에게 새 분야의 책을 더 읽히는 단계다.
🔤 Fill-in-the-Middle (FIM, 중간 채우기) — 코드 앞과 뒤를 보여 주고 가운데 빈 자리를 채우게 하는 학습이다.
Before: [코드 앞] → [그럴듯하지만 맞지 않는 다음 코드] After: [코드 앞] + [빈칸] + [코드 뒤] → [문맥에 맞는 가운데 코드]
B · 코드 빈칸 관점 전환
다음만 예측: 이미 쓴 코드 뒤를 맞힌다. 중간을 고칠 때는 뒤쪽 조건을 바로 쓰기 어렵다.
🎤 CPT에는 크리에이터 센터 문서를 증강한 API·튜토리얼 데이터, 논리 추론 능력 보존을 위한 수학 문제 풀이 데이터, FIM이 포함된 M Lua 데이터를 사용했다. 학습 뒤에는 RigidbodyComponent와 이벤트 센더·핸들러를 쓰는 예시가 제시됐다.
🧩 수학 데이터를 함께 넣은 선택은 새 문법만 반복하다 기존 문제 풀이 감각이 약해지는 위험을 줄이려는 균형으로 해석할 수 있다.

문법을 안다고, 질문을 이해하는 것은 아니다: SFT

유진이 다시 더블 점프를 묻는다. CPT만 거친 모델은 API 이름을 알면서도 바닥에서 멈추는 이야기를 할 수 있다. 질문 목적을 읽지 못한 것이다.

🔤 Supervised Fine-Tuning (SFT, 지도 미세조정) — 문제와 모범 답을 나란히 보여 주며 답변 습관을 다듬는 학습이다.
Before / CPT 뒤: [“더블 점프”] → [다른 기능을 설명] After / SFT 뒤: [“더블 점프”] → [의도 파악] → [RigidbodyComponent·IsOnGround·AddForce]
🎤 SFT에는 합성 데이터, 추론 단계를 위한 thinking 데이터, 월드 밖 질문을 거절하는 세이프티 데이터를 썼다. 발표에서는 SFT 뒤 InputService로 Alt 키 입력을 연결하는 팁까지 답변하는 예시를 보였다.

틀린 API를 그럴듯하게 말하지 않게: GRPO

문법과 의도를 배운 뒤에도 “스킬 컴포넌트가 있어?”에 없는 API를 있는 것처럼 답할 수 있다. 그래서 중요한 기준을 먼저 통과해야 하는 채점표가 필요했다.

🔤 GRPO — 같은 질문에서 여러 답을 만든 뒤, 답들 사이의 상대 보상을 이용해 더 나은 답 쪽으로 학습시키는 강화학습 알고리즘이다.
[하나의 질문] → [여러 답변] → [각 답변 채점] → [상대적 점수] → [학습] 채점문: [린터] → [네이티브 API] → [다음 항목]
C · 계층 보상 게이트
1. 린터
→
2. API
→
3. 다음 평가
먼저 린터 문을 통과해야 한다.
🎤 린터와 네이티브 API에 가장 높은 가중치를 두고, 앞 항목을 통과하지 못하면 다음 보상을 받지 못하게 평가했다. GRPO 뒤에는 월드와 무관한 NDC·김치찌개 질문을 거절하고 월드 질문을 유도하는 예시가 제시됐다.
🧩 계층형 채점은 문장이 매끄러워도 존재하지 않는 API를 말하는 답을 초기에 멈춰 세우려는 설계다.

배포 뒤에 발견한 진짜 질문의 모양

팀은 사용자가 길고 구체적으로 묻는다고 예상했다. 실제 입력은 “디펜스 게임 만들어 줘”, “그 UI 만들어 줘”, “캐릭터 이동 방법”처럼 짧았다. 세이프티 가중치가 너무 크자 월드 질문도 거절했다.

처음: [짧은 월드 질문] → [큰 세이프티 가중치] → [과도한 거절] 개선: [실제 질문 분류] → [데이터 재생성·보상 점검] → [의도에 맞는 안내]
🎤 실제 질문의 약 70%가 “이거 왜 안 돼?”, “이거 어떻게 써?” 같은 사용법 또는 디버깅 관련 질문이었다. 분석 뒤 데이터와 보상 체계를 점검해 재학습했고, 캐릭터 이동과 TransformComponent 질문에 답하는 모습이 제시됐다.
🧩 거절은 안전장치지만 문 앞이 너무 좁으면 들어와야 할 질문도 막는다. 실제 사용자 질문은 학습 때 상상한 사용자 모습을 검증하는 시험지다.

발표자는 린터로 검증해도 실제 월드에서 실행되는지는 별도 문제였고, 워크스페이스 분석이 불가능해 기본 문법·API 답변에 치우쳤다고 회고했다.

🧩 다음 단계의 핵심은 더 많은 코드보다 실행 가능한 검증 환경과 현재 작업 공간의 맥락일 수 있다. 그래야 문법이 맞는 답에서, 지금 월드에 붙일 수 있는 답으로 가까워진다.

처음 만드는 개발자가 가져갈 5가지

  1. 도메인 챗봇의 첫 과제는 말솜씨보다 환경 규칙과 도구를 아는 일이다.
  2. 데이터가 부족하면 문서에서 주제를 단계적으로 좁혀 합성 질문을 만들 수 있다.
  3. API·문법·실행 공간·표현을 나누면 답변 과정을 점검하기 쉽다.
  4. CPT는 분야의 말을, SFT는 질문 의도를, GRPO는 틀린 답을 피할 기준을 다듬는다.
  5. 배포 뒤 실제 사용자가 무엇을 어떻게 묻는지가 다음 학습의 출발점이다.
