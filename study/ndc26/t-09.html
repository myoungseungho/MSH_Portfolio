AI가 답을 내게 하는 환경은 어떻게 만드는가. 발표 영상 보기 ↗

AI 답변을 두고 팀원이 갈라지는 순간

지현은 새 데이터 도구가 가능한지 직접 테스트했다. 결과는 실패였다. 옆자리 동료는 AI에게 같은 질문을 했고, “가능하다”는 답을 가져왔다. 둘 다 빈말을 한 것은 아니다. 한쪽에는 실행 결과가 있고, 다른 쪽에는 그럴듯한 설명이 있다.

[지현] --직접 실행--> [안 됨] ↘ [동료] --AI에 질문--> [된다는데요?] → 무엇을 믿을까?

이 발표는 어느 쪽이 이긴다는 이야기가 아니다. AI가 낸 결과를 검증할 수 있는 일의 흐름을 만드는 이야기다.

🎤 발표자는 개발자 중 84%가 AI를 사용 중이거나 사용할 계획이라고 답한 Stack Overflow 설문을 언급했다. 동시에 AI 결과를 신뢰하지 않는 응답은 46%, 신뢰한다는 응답은 33%였다.
🧩 사용 여부와 신뢰 여부가 갈린다는 것은, AI를 도입하는 일과 결과를 받아들일 규칙을 만드는 일이 별개라는 뜻으로 읽을 수 있다.

데이터 엔지니어에게 AI가 특히 가까운 이유

처음 보는 오픈소스 문서가 쌓인다. SQL 문장을 써야 한다. 클라우드의 많은 설정도 고른다. 데이터 엔지니어의 하루에는 “무엇을 찾아야 하지?”라는 탐색이 많다. AI는 이 출발을 빠르게 할 수 있다.

🔤 SQL — 데이터 표에서 원하는 행을 찾거나, 묶거나, 계산하라고 데이터베이스에 말하는 언어다. “지난달 구매 금액을 사람별로 더해 줘” 같은 요청을 적는다.

하지만 AI가 만든 명령을 붙여 넣는 장면에서 일은 끝나지 않는다. 무엇을 확인할지, 어떤 두 결과를 비교할지, 어느 조건을 같게 둘지는 사람이 결정한다.

예전의 초점 [코드를 직접 쓰는 힘] AI와 일할 때 [문제를 고르는 사람] → [측정할 것을 정함] → [AI가 실행을 보조]
🎤 발표자는 오픈소스 기반, SQL 중심, 클라우드 환경이라는 세 이유 때문에 데이터 엔지니어링이 AI의 도움을 크게 받는 분야라고 보았다. 또한 문제 정의·측정·비교의 결정은 사람이 해야 한다고 말했다.

들쭉날쭉한 답을 줄이는 0단계~4단계

처음에는 “벤치마크 환경을 만들어 줘”처럼 넓게 부탁했다. 그러면 AI는 선택할 길이 너무 많다. 이제는 출발점부터 마지막 확인까지 다섯 칸을 먼저 만든다. 이 다섯 칸이 AI에게 줄 작업의 울타리다.

🔤 가드레일 — 기차가 선로를 벗어나지 않도록 막는 난간처럼, 탐색해도 되는 범위를 미리 정한 조건이다.
🔤 컨텍스트 — 지금 일을 이해하는 데 필요한 배경과 재료다. 이미 만든 설정, 파일, 실패 기록, 확인 방법이 여기에 들어간다.
🔤 스캐폴딩 — 건물을 지을 때 바깥에 세우는 작업 발판처럼, AI와 반복해 만든 템플릿·스크립트·기록을 다음 작업의 발판으로 쓰는 것을 발표자가 부른 이름이다.
[0 요구 사항] → [1 문제 정의] → [2 가드레일] → [3 스캐폴딩] → [4 검증] “무엇이 필요?” “정확히 뭘?” “어디까지?” “다음에도 쓸 발판” “정말 맞나?”
A · 다섯 칸을 한 장면으로 따라가기
0 요구
1 정의
2 난간
3 발판
4 검증
지현이 “빠르게 조회하고 싶다”는 말을 적는다. 아직 방법은 정하지 않았다.
🎤 발표자는 요구 사항에서 출발해 문제 정의, 가드레일, 컨텍스트(스캐폴딩), 결과 검증으로 이어지는 0~4단계 흐름이 여러 문제를 풀면서 자연스럽게 정착했다고 설명했다.
🧩 이 흐름은 프롬프트를 길게 쓰는 요령보다 앞선다. 먼저 사람이 선택지를 줄여 두어야, AI의 다음 행동도 비교 가능한 범위 안에 남는다.

사례 1: 빠른 조회와 싼 저장을 한 장면에 놓기

대시보드에서 막 들어온 대규모 데이터를 보고 싶다. 그런데 데이터는 비용과 확장 면에서 유리한 S3 같은 클라우드 저장소에 쌓고 싶다. 문제는 저장소에 한 번 쌓인 뒤 다시 읽으려면 시간이 든다는 점이다.

🔤 스트리밍 — 물을 한꺼번에 붓지 않고 계속 흘려보내듯, 새 데이터가 들어오는 대로 이어서 처리하는 방식이다.
🔤 레이턴시 — 버튼을 누른 뒤 화면에 결과가 오기까지 걸리는 기다림이다. 여기서는 조회 요청 뒤 답이 나올 때까지의 시간이다.
Before [Kafka: 데이터 수집] → [Flink: 처리] → [저장소] → [대시보드 조회] 질문 [처리]와 [저장]을 한곳에 두고 → 저장소를 한 번 더 거치지 않고 조회할 수 있을까?
🎤 첫 요구 사항은 실시간 처리, S3 저장, 수백 밀리세컨드 이내 조회였다. 기존 구조는 Kafka로 수집하고 Flink로 처리한 뒤 저장소를 거쳐 대시보드에서 조회했다.
🧩 이 사례의 핵심은 “새 제품이 좋은가”가 아니다. 저장을 포기하지 않은 채, 조회 경로에서 한 번의 경유를 줄일 수 있는지 확인하는 질문으로 좁혔다는 데 있다.

같은 시험지를 만들기: 가드레일과 스캐폴딩

두 엔진을 비교하려는데 한쪽은 큰 컴퓨터, 다른 쪽은 작은 컴퓨터에서 돌리면 결과가 공정하지 않다. 그래서 AI에게 일을 맡기기 전에 시험장부터 고정했다. 전용 EKS 클러스터, Nexmark 벤치마크, 검증된 배포 레퍼런스라는 세 조건이다.

🔤 벤치마크 — 같은 문제를 같은 조건에서 풀게 하고 결과를 재는 시험이다. 컴퓨터의 성능이나 프로그램의 처리 능력을 비교할 때 쓴다.
🔤 클러스터 — 여러 컴퓨터를 한 팀처럼 묶어 일을 나눠 하는 구성이다. EKS는 발표에서 전용으로 사용한 클러스터 환경의 이름이다.
[AI에게 넓은 요청] → 경로·버전·자원이 제각각 → 비교하기 어려움 [전용 EKS] + [Nexmark] + [검증된 배포 레퍼런스] ↓ [같은 시험장] → [비교할 수 있는 결과]

그 다음에는 한 번에 완성하려 하지 않았다. 템플릿을 만들고, 오류를 고치고, 프롬프트를 다듬었다. 그 흔적을 버리지 않고 다음 요청의 재료로 남겼다.

🎤 발표자가 제시한 첫 사례의 가드레일은 전용 EKS 클러스터, 스트리밍 업계 표준 벤치마크 Nexmark, 검증된 레퍼런스를 따른 클러스터 배포였다. 구축 과정에서는 공식 오퍼레이터 예시, S3 스테이트, 컴팩터 2개와 나머지 1개라는 조건을 프롬프트에 넣었다.
🧩 오류 기록은 단순한 일지가 아니다. 다음 사람이나 다음의 나 자신이 같은 막다른 길을 다시 찾지 않게 하는, 검증 환경의 일부가 된다.

결과를 읽되, 측정의 주도권은 놓지 않기

준비된 환경에서 22개 쿼리를 실행했다. 그래프의 세로축은 처리량이다. 높을수록 같은 시간에 더 많은 일을 한 것이다. 발표에서는 Flink보다 두 스트리밍 데이터베이스 버전의 막대가 대체로 높게 보였다.

B · 22개 쿼리에서 한 결과를 읽는 법
Flink기준
스트리밍 데이터베이스대체로 더 높음

발표 그래프의 개별 쿼리 값을 재현한 것이 아니다. 22개 쿼리를 비교했고, 일부에서 최대 1.7배가 나왔다는 사실을 읽는 연습용 도식이다.

🎤 발표에서는 22개 쿼리의 처리량을 비교했으며, 쿼리에 따라 스트리밍 데이터베이스가 Flink 대비 최대 1.7배 높았다. 단순 쿼리의 레이턴시로 환산하면 약 200~350ms였고, 수백 밀리세컨드 이내라는 목표를 충족했다고 설명했다.

여기서 중요한 장면이 하나 더 있다. “수백 밀리세컨드”를 말하려면 원래는 레이턴시를 직접 재는 편이 더 맞다. 그러나 이를 위해 스키마와 입력을 바꾸면 이미 만든 시험장이 흔들린다. 발표자는 처리량만으로도 요구 충족을 확인할 수 있다고 판단해, 측정 기준을 바꾸지 않았다.

🧩 AI는 시험을 실행하고 결과 표를 만들 수 있다. 하지만 지금의 질문에 필요한 측정이 무엇인지, 이미 만든 비교 조건을 바꿀지는 사람이 책임져야 한다.

사례 2: 파이프라인을 줄여도 원본과 같을까

운영 중인 PostgreSQL의 데이터를 분석 화면에서 보고 싶다. 보통은 데이터를 옮기는 여러 단계가 붙는다. 각각은 할 일을 하지만, 운영할 상자도 늘어난다. 발표자는 그 길을 줄이되, 원본과 값이 다르면 소용없다는 문제를 붙잡았다.

🔤 ETL — 데이터를 꺼내고(Extract), 모양을 바꾸고(Transform), 다른 곳에 넣는(Load) 작업이다. 택배 상자를 꺼내고, 분류해, 다른 창고로 옮기는 일에 가깝다.
🔤 정합성 — 두 곳에서 본 데이터가 서로 모순되지 않는 상태다. 주문이 취소됐는데 분석 화면에는 남아 있다면 정합성이 맞지 않는다.
Before [PostgreSQL 원본] → [CDC] → [Kafka] → [ETL] → [분석] After로 검토한 길 [PostgreSQL 원본] → [PG Lake] → [Iceberg] → [Spark 조회] ↓ “원본과 정말 같나?”
🎤 발표는 PostgreSQL 분석에 보통 CDC·Kafka·ETL 같은 별도 파이프라인이 필요하다고 설명했다. Snowflake가 공개한 오픈소스 PG Lake를 검토했고, PG Lake는 PostgreSQL 데이터를 별도 ETL 없이 Iceberg로 노출한다.
🧩 단계를 줄이는 설계에서는 편리함만 확인하면 부족하다. 중간 상자가 사라진 만큼, 데이터가 사라지거나 뒤섞이지 않았음을 별도 장면으로 확인해야 한다.

커밋·롤백·동시성: 신뢰를 세 장면으로 시험하기

이번에는 최적의 조합을 찾는 것이 목표가 아니었다. Docker로 구성하고, JDBC 카탈로그를 쓰고, Spark로 조회하는 한 경로만 잡았다. 가장 짧은 길로 “ETL 없이도 정합성 있는 분석이 가능한가”를 확인하려는 선택이다.

🔤 커밋 — 장부에 적어 둔 변경을 “이제 확정”이라고 저장하는 순간이다. 롤백은 그 변경을 없던 일로 되돌리는 일이다. 동시성은 여러 작업이 거의 같은 때에 겹쳐 일어나는 상황이다.
[데이터 적재] → [원본과 분석 데이터를 비교] ├─ 커밋한 주문: 확정된 값이 같은가? ├─ 롤백한 주문: 되돌린 흔적을 어떻게 다루는가? └─ 동시에 쓴 주문: 빠진 값은 없는가?
C · 정합성 확인 장면
커밋한 시점의 스냅샷을 원본과 나란히 놓는다. 발표에서는 정확히 일치했다.
🎤 두 번째 사례의 가드레일은 Docker 기반 구성, JDBC 카탈로그, Spark 조회였다. 커밋·롤백·동시성 시나리오를 검증한 결과, 커밋 시점 스냅샷은 정확히 일치했고 동시성에서도 데이터 유실은 없었다. 롤백 때 S3에 orphan 파일이 남는 주의점이 발견됐다. 발표자는 통과 둘, 주의 하나, 실패는 없었다고 정리했다.
🔤 orphan 파일 — 데이터에서 더는 참조하지 않지만 저장소에는 남아 있는 파일이다. 책장 목록에는 없는 책이 창고 한쪽에 남아 있는 모습으로 생각하면 된다.
🧩 이 결과는 “문제 없음”이라는 도장보다 더 유용하다. 안전한 장면 둘과 주의할 장면 하나를 구분해 두면, 다음 운영 판단에서 무엇을 계속 감시해야 할지가 보인다.

처음 접하는 데이터 엔지니어가 가져갈 5가지

  1. AI의 답과 실행 결과를 같은 자리에 놓아라. 믿음은 답변의 말투가 아니라 확인 과정에서 생긴다.
  2. 문제는 방법보다 먼저 적어라. “무엇을 만들까”보다 “무엇이 되면 성공인가”를 먼저 정한다.
  3. 가드레일로 시험장을 고정하라. 조건이 달라지면 빠른 답도 비교할 수 없다.
  4. 오류와 해결을 스캐폴딩으로 남겨라. 다음 요청이 빨라지는 이유는 같은 시행착오를 덜 겪기 때문이다.
  5. AI에게 맡길 곳과 사람이 정할 곳을 나눠라. 실행은 도움받되, 측정·비교·비용의 판단은 계속 엔지니어의 일이다.

문제 정의 가드레일 스캐폴딩 검증 정합성

🎤 발표자는 AI가 실력을 대체하는 도구가 아니라 실력을 증폭시키는 도구라고 보았다. 모델은 계속 좋아지지만, 엔지니어가 만들 수 있는 것은 모델이 일할 환경이며, 그 환경도 시간이 지나면 부채가 되어 계속 다듬어야 한다고 마무리했다.
