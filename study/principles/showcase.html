Cognitive Load - 발생적 부하 극대화

읽기만 하면 발생적 부하가 낮다. "잠깐, 생각해보세요" 장치가 필요.
구조 ▾
섹션 사이에 들어갈 사고 유도 컴포넌트

...셀룰러 오토마타에서 각 픽셀은 주변 8개 이웃의 상태를 확인하고 규칙에 따라 변합니다. 물은 아래로, 모래는 대각선으로, 불은 위로 퍼집니다...

잠깐 - 만약 "모래" 위에 "물"이 있으면 어떻게 될까요?
두 규칙이 충돌할 때 어떤 순서로 처리해야 할지 생각해보세요.
Noita의 해결책: 물질마다 밀도(density) 값이 있습니다. 물(밀도 1.0)이 모래(밀도 2.5) 위에 있으면, 밀도가 높은 모래가 아래로 가라앉고 물이 위로 올라옵니다. 이것은 실제 물리의 부력(buoyancy)과 같은 원리입니다. 처리 순서는 밀도 높은 물질부터 — 이래야 한 프레임에 교차가 완료됩니다.

09

Productive Failure - "먼저 실패해보세요"

정답을 먼저 주는 것보다 실패 후 가르치면 전이 능력이 급상승.
참여 ▾
"ECS를 배우기 전" 챌린지 - 실패를 체험하게 하는 컴포넌트
챌린지: 100만 개 Entity의 Position을 업데이트하는 코드를 OOP로 짜보세요.
각 Entity는 Position, Velocity, HP, Inventory, AI State를 가집니다.
힌트 없이 성능 문제를 해결해보세요.
당신의 코드가 느린 이유:

Entity 배열을 순회할 때, 각 Entity 객체에는 Position뿐 아니라 HP, Inventory, AI State 등 사용하지 않는 데이터도 캐시 라인에 올라옵니다.

64바이트 캐시 라인 중 Position 12바이트만 쓰고 나머지 52바이트는 낭비. 이것이 캐시 미스입니다.

ECS의 해결책: Position만 따로 모은 배열을 만들면 캐시 라인 하나에 Position 5개가 들어갑니다. → 이제 ECS를 배울 준비가 됐습니다.

Cognitive Conflict - "모두가 이렇게 생각합니다... 하지만"

기존 믿음과 모순되는 증거를 만나야 깊은 학습이 시작된다.
트리거 ▾
오해를 심고 부수는 "인지 갈등" 컴포넌트
✅
대부분 이렇게 생각합니다
"멀티스레딩을 쓰면 당연히 더 빠르다. 코어가 많으니까."
❌
하지만 Factorio는 싱글스레드로 더 빠릅니다. 왜?
클릭해서 확인
이유: 벨트 시뮬레이션은 순차 의존성이 있습니다. A 벨트의 출력이 B 벨트의 입력이 되기 때문에, 병렬 처리하면 동기화 비용이 단일 스레드 이득을 초과합니다.

교훈: 병렬화는 "작업 간 의존성이 없을 때"만 유효합니다. 이것이 Amdahl의 법칙 — 병렬화할 수 없는 부분이 전체 성능을 제한합니다.

💡 지금 느낀 "어?!" — 그것이 학습입니다.

Narrative Structure - 개발 스토리 3막 구조

이야기 속 사실 = 22배 기억. 문제 → 시행착오 → 해결의 서사.
표현 ▾
기술의 탄생 맥락을 서사로 풀어내는 타임라인 컴포넌트

Portal의 공간 렌더링은 어떻게 탄생했나

문제
DigiPen 학생 프로젝트 Narbacular Drop. "벽에 구멍을 뚫어서 다른 곳으로 나간다"는 아이디어는 있었지만, 포탈 너머 세계를 실시간으로 보여주는 방법이 없었다.
시행착오
시도 1: 렌더 텍스처 — 포탈 반대편 카메라로 찍어서 텍스처로 붙임. 작동했지만, 포탈 안에 포탈이 보이는 "재귀" 상황에서 무한 렌더링 발생.

시도 2: 레이트레이싱 — 물리적으로 정확하지만, 2005년 하드웨어에서 실시간 불가. 포기.
해결
스텐실 버퍼: 화면에서 "포탈 영역"만 마스킹하고, 그 영역에만 반대편 카메라의 렌더링 결과를 그린다. 재귀? 깊이 제한을 두면 된다 (보통 4~8단계). GPU 부담 최소화 + 재귀 가능. Valve가 인수하여 Portal이 탄생.
