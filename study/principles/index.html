같은 원리가 여러 기술에서 반복된다는 걸 보면, 그때 원리를 진짜 이해하게 됩니다.

GPU / 그래픽스 — 주제 목록

Unity DOTS (ECS + Jobs + Burst) GPU
Compute Shader 개념과 구현 GPU
GPU 아키텍처 기초 GPU
Anti-Aliasing GPU
Clustered Deferred Rendering GPU

각 글이 독립적. DOTS의 "캐시 지역성"과 AOI의 "그리드 탐색"이
같은 원리라는 걸 알 방법이 없음.

📐
공간 지역성 (Spatial Locality) 5개 글
가까이 있는 데이터를 연속으로 접근하면 빠르다
캐시 라인 연속 메모리 프리페칭
▼
CPU는 메모리를 1바이트씩이 아니라 64바이트 캐시 라인 단위로 읽어온다.
연속 배치된 데이터는 한 번에 여러 개가 캐시에 올라오고,
흩어진 데이터는 매번 RAM까지 왕복한다 (1ns vs 100ns).

이 원리는 게임 기술 곳곳에서 반복된다:
이 원리가 나타나는 곳
Unity DOTS
ECS가 Component를 struct 배열로 연속 배치 → 캐시 히트율 극대화 → 20fps → 250fps
GPU / 그래픽스
AOI (Area of Interest)
같은 그리드 셀의 엔티티를 연속 배열에 저장 → 주변 탐색 시 캐시 친화적
네트워크
패킷 구조 최적화
패킷 필드를 연속된 바이트로 직렬화 → memcpy 한 방, 파싱 오버헤드 최소화
네트워크
GPU 아키텍처
Warp 내 스레드가 인접 주소를 접근해야 코얼레싱 → 메모리 대역폭 최대 활용
GPU / 그래픽스
Factorio 시뮬레이션
같은 청크의 벨트를 연속 배열로 처리 → 수만 개 기계를 60fps로
게임에 적용된 기술
이 원리가 안 통할 때: 접근 패턴이 완전히 랜덤일 때 (해시맵 체이닝, 포인터 그래프 순회). 이 경우 연속 배치해도 캐시 히트가 보장되지 않는다.
🔀
분할 정복 (Divide & Conquer) 5개 글
큰 문제를 작은 단위로 쪼개서 독립적으로 처리하면 병렬화·관리가 된다
파티셔닝 병렬 처리 청크
▼
50,000개를 한꺼번에 처리하면 느리다.
8등분해서 8코어에 나눠주면 8배 빠르다.
월드를 존(Zone)으로 나누면 각 서버가 독립적으로 관리한다.

핵심은 "쪼갠 조각 사이에 의존성이 없어야 한다"는 것.
이 원리가 나타나는 곳
Unity Jobs System
50,000개 엔티티를 8등분 → 각 코어가 독립 처리 → 레이스 컨디션 원천 차단
GPU / 그래픽스
Seamless World
월드를 존(Zone)으로 분할 → 각 서버가 담당 영역만 처리 → 수평 확장
네트워크
Minecraft 청크
무한 월드를 16×16 청크로 분할 → 플레이어 주변만 로드 → 메모리 관리 가능
게임에 적용된 기술
Quadtree / Octree
공간을 재귀적으로 4/8분할 → 탐색 O(n) → O(log n)
CS 기초
Compute Shader
파티클 연산을 Thread Group으로 분할 → GPU 수천 코어가 병렬 처리
GPU / 그래픽스
이 원리가 안 통할 때: 조각 사이에 강한 의존성이 있을 때 (전역 상태 공유, 순차 의존성). Seamless World의 "오버랩 존"은 이 한계를 우회하는 해법.
📸
상태 스냅샷 + 델타 (Snapshot + Delta) 4개 글
전체를 매번 저장/전송하지 말고, 변한 부분만 기록하면 된다
델타 압축 변경 감지 되감기
▼
매 프레임 모든 상태를 보내면 42KB/s.
변한 필드만 보내면 3.9KB/s.
같은 원리로 시간을 되감을 수도 있고, 네트워크 지연을 보상할 수도 있다.
이 원리가 나타나는 곳
델타 압축
이전 프레임 대비 변한 필드만 전송 → 트래픽 10.8배 절약
네트워크
Braid 시간 역행
매 프레임 스냅샷 저장 + 델타로 압축 → 되감기 시 역재생
게임에 적용된 기술
Lag Compensation
서버가 과거 상태 스냅샷을 버퍼링 → 클라이언트 시점으로 되감아서 판정
네트워크
클라이언트 예측
서버 확정 스냅샷과 클라이언트 예측 사이의 차이(델타)를 보정
네트워크
이 원리가 안 통할 때: 상태 대부분이 매 프레임 바뀔 때 (파티클 시스템 전체 갱신). 이 경우 델타가 풀 스테이트와 거의 같아져서 오버헤드만 늘어남.
🔮
예측과 보정 (Predict & Correct) 4개 글
정확한 답을 기다리지 말고, 먼저 예측하고 나중에 보정한다
외삽 보간 롤백
▼
서버 응답을 기다리면 0.1초 멈춘다. 사용자는 0.05초만 멈춰도 알아챈다.
해법: 일단 예측하고, 정답이 오면 보정한다.
네트워크에서도, 애니메이션에서도, 물리에서도 같은 원리.
이 원리가 나타나는 곳
카트라이더 네트워크 동기화
클라이언트가 입력 즉시 예측 이동 → 서버 결과 도착 시 부드럽게 보정
네트워크
Lag Compensation
다른 플레이어 위치를 외삽(Extrapolation)으로 예측 → 패킷 도착 시 보정
네트워크
애니메이션 블렌딩
걷기→뛰기 전환 시 보간(Lerp)으로 중간 상태 예측 → 부드러운 전환
애니메이션
SUPERHOT 시간 동기화
입력 크기로 시간 흐름을 예측 → timeScale로 물리/애니 동기 보정
게임에 적용된 기술
이 원리가 안 통할 때: 예측이 크게 빗나갈 때 (급격한 방향 전환, 텔레포트). 빗나간 예측의 보정이 눈에 보이면 (Hard Snap) 오히려 부자연스러워짐.
⚖️
정밀도 트레이드오프 (Precision Trade-off) 4개 글
눈에 안 보이는 정밀도를 버리면 성능이나 대역폭을 크게 얻는다
양자화 LOD 디더링
▼
float는 32비트지만, 체력을 0~100 범위로 보내는데 32비트가 필요한가?
7비트면 된다. 25비트를 "버렸지만" 사용자는 차이를 모른다.
인간의 인지 한계 안에서 정밀도를 교환하는 것이 핵심.
이 원리가 나타나는 곳
양자화 (Quantization)
float 4바이트 → 1바이트로 압축. 정밀도 손실 ≤ 0.4% → 대역폭 75% 절약
네트워크
Bit Packing
바이트 경계를 무시하고 필요한 비트만 전송 → 2.75바이트 패킷
네트워크
Obra Dinn 1-bit 렌더링
색상을 흑/백 2값으로 줄이되, 디더링 패턴으로 입체감 보존
게임에 적용된 기술
Anti-Aliasing
FXAA는 정확한 기하 정보를 포기하고 픽셀 색상만으로 근사 → 빠름
GPU / 그래픽스
이 원리가 안 통할 때: 금융 데이터, 물리 시뮬레이션 정밀 계산 등 정밀도가 결과에 직접 영향을 주는 경우. 게임에서도 충돌 판정은 정밀도를 함부로 줄이면 관통 버그 발생.
