200명 팀이 거대한 월드를 채우는 법

붉은사막 개발 프로세스에서 배우는 빠른 반복, 절차적 배치, XML 데이터 주도 제작

30초 요약

이 문서는 “C++ 엔진인데 디자이너가 XML을 만진다”, “후디니로 자동 배치한다”가 실제로 무슨 뜻인지 풀어 쓴 학습 노트야.

핵심은 프로그래머가 모든 콘텐츠를 대신 만들지 않고, 안전한 부품과 규칙을 만들며, 기획·아트가 그 부품을 조합해 빠르게 검증하게 하는 것이야.

Part 1. 이 발표가 말한 문제는 “사람이 부족하다”가 아니야

맵이 크면 사람을 더 붙이면 되는 것 아닌가?

처음에는 그렇게 보이지만, 팀원이 늘수록 “A팀 완료를 기다려야 B팀이 시작”하는 시간이 같이 늘어. 퀘스트 목표 하나가 바뀌었는데 환경, NPC, 보상, 스크립트까지 줄줄이 고쳐야 하면 제작자는 일을 하는 시간보다 기다리고 맞추는 시간을 더 쓰게 돼.

붉은사막 팀이 붙든 세 원칙은 뭐야?

빠른 반복(Fast Iteration)은 바꾼 뒤 결과를 보는 피드백 고리를 짧게 만드는 것. 숫자 하나를 고치고 빌드가 2시간 걸리면 실험은 줄어들어.

유지보수성(Maintainability)은 나중에 바꿀 수 있게 만드는 것. 요구사항 변경이 실패가 아니라 정상이라는 전제야.

병렬 워크플로우(Parallel Workflows)는 팀 간 순차 의존을 줄이는 것. 서로의 산출물을 기다리지 않고 같은 공통 기반 위에서 함께 움직이는 구조야.

전형적인 순차 제작 기획서 확정 → 환경 제작 → 오브젝트 배치 → 로직 구현 → 테스트 ↑ 목표 변경 시 앞 단계까지 되감기 공통 기반을 먼저 만든 병렬 제작 지형/POI/규칙 ─┬→ 환경팀: 공간·에셋 ├→ 콘텐츠팀: NPC·전투·보상 └→ 퀘스트팀: 목표·대사·연출 → 통합 플레이 테스트

발표에서 말한 월드 우선 접근은 퀘스트가 지역의 유일한 출발점이 되지 않게 하여, 환경·콘텐츠·퀘스트를 겹쳐 진행하게 한 사례다. 다만 기사도 내러티브가 이미 만들어진 공간에 맞춰질 수 있다는 트레이드오프를 함께 언급한다.

Part 2. 후디니 자동 배치 + 수작업 스팟 배치가 뭐야?

후디니(Houdini)는 게임 엔진인가?

아니. 후디니는 노드로 규칙을 조합해 지형·도로·식생 같은 결과를 만들어 내는 절차적 생성(Procedural Generation) 도구야. 여기서 절차적이란 “아티스트가 돌 하나씩 찍는다” 대신 “강 주변 10m에는 갈대, 경사 30도 이상에는 바위, 도로 양옆에는 나무를 피한다”처럼 규칙과 입력 데이터로 결과를 만드는 방식을 뜻해.

왜 필요해? 같은 규칙이 수 km²에 반복될 때, 지형을 조금 바꿔도 규칙을 다시 실행하면 전체 결과가 따라 바뀌기 때문이야. 안 쓰면? 강의 선형이 바뀔 때 도로·식생·장식물을 사람이 다시 만져야 해.

🏞️ 비유: 조경 설계도와 화분

후디니는 “햇빛 드는 길가에는 이 간격으로 가로수를 심어라”는 조경 규칙이야. 수작업 스팟 배치는 “이 벤치 옆에는 편지 읽는 NPC와 떨어진 모자를 둬서 기억에 남게 하자”는 연출이야. 전자는 넓이를 감당하게 하고, 후자는 장소의 뜻을 만든다.
그럼 자동 배치만 하면 더 싸고 빠른 것 아닌가?

자동 배치는 기본 밀도를 만들기 좋지만, 플레이어의 시선·동선·서사적 타이밍까지 스스로 판단하지는 못해. 그래서 “숲에는 작은 동물, 물에는 물고기, 길에는 방황 NPC” 같은 넓은 범위는 자동화하고, 보스 입구·퀘스트 전환점·NPC 일상 장면처럼 의도가 중요한 곳은 사람이 스팟 배치해.

작업생노가다 배치규칙 기반 자동 배치수작업 스팟 배치
숲 20km²의 나무나무마다 위치·회전·밀도를 직접 결정바이옴·경사·거리 규칙을 실행랜드마크 주변만 미세 조정
강이 100m 이동주변 소품을 찾아 옮김강 입력을 바꾸고 재생성다리·낚시터·연출 지점만 확인
기억에 남는 만남가능하지만 넓은 범위와 같은 비용평균적인 밀도까지만 잘함NPC 위치·행동·카메라·보상을 의도대로 설계

자동화의 함정: “자동”은 “검수 불필요”가 아니야

기사에서도 배치 겹침은 조건에 따라 정상일 수 있어 완전 자동 판정이 쉽지 않다고 했다. 자동 배치는 후보를 빠르게 만들고, 디자이너는 플레이 흐름·시야·충돌·퀘스트 조건을 실제 레벨에서 확인하는 역할로 바뀐다.

Part 3. C++ 엔진인데 XML 스크립트? 역할을 나눈 거야

XML이 C++ 코드를 대신 실행한다는 뜻이야?

아니야. XML은 보통 데이터 파일이고, 그 데이터를 읽어 실제 동작을 실행하는 프로그램은 C++ 엔진이야. 엔진이 “문 열기”, “애니메이션 재생”, “범위 안 플레이어 확인”, “보상 지급” 같은 검증된 기능을 C++로 제공해 두고, XML은 그 기능을 언제, 어떤 순서와 조건으로 조합할지 적는 설계도에 가깝다.

[C++ 엔진: 한 번 만들어 검증하는 도구 상자] OpenDoor(id) / PlayAnimation(id) / CheckCondition(id) SpawnNPC(id) / GiveReward(id) / ChangePhase(id) ▲ XML을 읽고 호출 │ <Trigger when="boss_dead"> <OpenDoor id="north_gate" /> <SpawnNPC group="villagers" /> <GiveReward table="boss_reward_A" /> </Trigger> ▲ [디자이너: 이미 허용된 부품을 조합]
그럼 디자이너도 로직에 관여하는 거네?

맞아. 단, “아무 C++나 고칠 수 있다”가 아니라 콘텐츠 로직의 조합과 파라미터에 관여하는 거야. 예를 들어 기믹의 상태 전환, 발동 조건, 타이밍, 등장 NPC, 보상 테이블을 바꾸고 게임에서 바로 테스트할 수 있어.

새로운 물리 기능, 네트워크 권한 검증, 저장 방식, 성능이 민감한 AI 알고리즘처럼 새 능력 자체가 필요하면 프로그래머가 C++ 도구 상자에 새 기능을 추가해야 해.

변경 요청XML로 가능한 쪽C++ 작업이 필요한 쪽
상자 열기 뒤 2초 후 몬스터 등장기존 이벤트·대기·스폰 노드 조합그 노드들이 이미 존재한다는 전제
보스가 체력 30%에 광폭화조건값·행동 차트·이펙트 연결광폭화 전용 전투 시스템이 없으면 구현 필요
“물체를 들어 던져 다리를 무너뜨리는” 새 상호작용기존 물리/파괴 부품이 있으면 조합 가능새 런타임 규칙·동기화·검증을 엔진에 추가
🧱 비유: 레고와 레고 공장

XML은 레고 조립 설명서, C++는 레고 블록과 결합 규칙을 만드는 공장이야. 설명서를 바꾸면 성문을 열고 NPC를 등장시키는 순서는 바로 바꿀 수 있어. 하지만 “전기로 움직이는 새 블록”이 없으면 공장(C++ 팀)이 먼저 만들어야 해.

Part 4. 기믹 교체와 병렬 작업은 실제로 어떻게 가능해?

“일반 오브젝트를 기믹으로 한 번에 교체”한다는 건 뭐야?

환경팀은 우선 일반 상자·문·크레인 모델을 월드에 배치해 화면과 동선을 만든다. 동시에 디자인팀은 같은 규격의 “열 수 있는 상자”, “파괴되는 문”, “작동하는 크레인” 정의를 XML과 에셋 규칙으로 만든다. 준비가 끝나면 배치된 일반 모델의 참조를 상호작용 버전으로 바꾸거나, 같은 ID의 프리팹/구성으로 교체하는 식이야.

중요한 것은 교체 기술 자체보다 공통 계약이야. 예를 들어 `MarketCrate_A`라는 배치 ID, 피벗 위치, 충돌 범위, 애니메이션 슬롯을 미리 약속해 두면 환경팀이 멈춰서 기믹팀을 기다릴 이유가 줄어.

환경팀 디자인/프로그래밍팀 일반 문 Mesh 배치 ───────┐ Door_01 상태/조건 정의 피벗·크기·ID 규약 준수 │ Open / Locked / Broken 동작 구현 └──→ 검증 후 같은 배치 ID에 기믹 버전 연결 ↓ 월드는 다시 배치하지 않고 상호작용만 추가
MMORPG 팀에서는 이 생각을 어디에 써볼 수 있어?

맵 오브젝트만의 이야기가 아니야. 예를 들면 이벤트 보상, 몬스터 스폰, 던전 기믹, NPC 스케줄도 “코드 수정 없이 조정 가능한 범위”를 정해 둘 수 있어.

작게 시작하는 실무 실험: 다음 콘텐츠 하나를 골라 “매번 개발자에게 요청하는 변경 5개”를 적어 봐. 그중 반복되고 위험이 낮은 항목(숫자, 조건, 등장 풀, 시간표)을 데이터화 후보로 삼아. 한 번에 범용 XML 엔진을 만들려 하면 실패하기 쉬워.

Part 5. 기획 CSV/엑셀은 왜 커질수록 답답해질까?

우리는 기획이 엑셀(CSV)로 주는데, 그게 잘못된 거야?

아니. 표 형태의 수치 데이터에는 엑셀이 아주 훌륭해. 아이템 가격 500개, 몬스터 HP 1,000개처럼 모든 행이 같은 열을 가지면 입력·정렬·필터가 빠르지. 문제는 데이터가 표가 아니라 트리와 관계가 될 때 생겨.

엑셀이 힘들어지는 순간은 언제야?

예를 들어 보스 하나에 기본 능력치, 페이즈 3개, 각 페이즈의 패턴 4개, 패턴마다 조건·타이밍·이펙트·예외가 붙는다면? 열을 계속 추가하거나 여러 시트로 쪼개고 ID로 연결해야 해. 한 행만 봐서는 전체가 안 보이고, 열 삽입·복사·필터 실수도 늘어.

또 CSV/XLSX는 파일 단위 변경이라, A가 12행을 고치고 B가 83행을 고쳐도 병합 도구가 의미를 이해하기 어렵다. 결국 한 명이 파일을 잡고 다른 사람이 기다리는 일이 생겨.

상황CSV/엑셀에 잘 맞음텍스트 XML/JSON에 유리함
모든 데이터가 같은 필드아이템 ID / 가격 / 등급 / 판매 여부가능하지만 표가 더 읽기 쉬울 수 있음
계층과 선택적 항목시트 분리·참조 ID·빈 열이 늘어남보스 → 페이즈 → 패턴 → 조건을 중첩해 표현
동시 변경·코드 리뷰바이너리 XLSX는 줄 단위 차이를 보기 어려움Git diff가 바뀐 노드·속성을 보여 줌
일괄 수정엑셀 기능/매크로에 강점검색·정규식·스크립트로 파일 전체 변경
XML의 원리는 결국 뭐야?

태그로 “이 값은 무엇에 속하는가”를 직접 적는 텍스트 구조야. 엑셀의 열 이름이 관계를 알려 준다면, XML은 부모-자식 구조가 관계를 알려 줘. 엔진은 정해진 스키마(허용되는 태그·속성·형식 규칙)에 맞는지 검사한 뒤 메모리 데이터로 읽어 실행한다.

<Boss id="ice_king" level="80"> <Phase hpBelow="70"> <Pattern name="ice_storm" cooldown="12" /> </Phase> <Phase hpBelow="30"> <Pattern name="summon_guard" count="4" /> </Phase> </Boss> 위 구조만 봐도 “빙왕 → 2개 페이즈 → 각 패턴” 관계가 보인다.

XML이 엑셀을 무조건 대체한다는 뜻은 아니야

복잡한 계층형 콘텐츠에는 텍스트 데이터가 유리할 수 있지만, 대량 수치 밸런싱·기획 검토에는 스프레드시트가 편하다. 좋은 팀은 형식의 유행을 따르지 않고 “누가 무엇을 얼마나 자주, 어떻게 바꿔야 하는가”로 형식을 고른다. 스프레드시트로 편집하고 빌드 때 검증된 XML/바이너리로 변환하는 혼합형도 흔하다.

Part 6. 내 실무에 가져갈 수 있는 질문

당장 대형 도구를 도입해야 해?

아니. 이 발표에서 더 일반적인 원리는 변경 비용을 측정하고, 자주 바뀌는 부분의 손잡이를 현업 가까이 가져가는 것이야. “XML을 쓴다”는 한 가지 해법일 뿐 목적은 아니야.

다음 회의나 회고에서 써볼 체크 질문

1. 이 변경은 실제 제작 10분보다 대기·전달·재검수에 2일을 쓰고 있나?

2. 매주 반복되는 조정 중, 권한·보안·성능 위험이 낮아 데이터로 열어도 되는 것은 무엇인가?

3. 두 팀이 같은 곳을 만질 때, 충돌을 피할 공통 ID·영역·버전 규약은 있는가?

4. 자동화가 만든 결과를 사람이 판단해야 하는 품질 기준은 무엇인가?

5. 이 구조가 서사·품질·안전성을 희생하고 있지는 않은가?

📌 핵심 정리

  • 빠른 반복은 코딩 속도만이 아니라 수정→확인의 전체 대기 시간을 줄이는 일이다.
  • 후디니/절차적 배치는 넓은 범위의 규칙을 재실행해 기본 밀도를 만들고, 사람은 의도가 필요한 스팟에 집중하게 한다.
  • C++ + XML은 경쟁 관계가 아니다. C++가 안전한 능력을 만들고 XML이 그 능력을 콘텐츠로 조합한다.
  • 엑셀은 균일한 표 데이터에 강하고, XML은 계층·조건·관계·텍스트 병합에 강하다.
