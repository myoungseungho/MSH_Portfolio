1단계: 공용 공간의 원칙

식당 문지기가 "이미 홍길동이 안에 있다"고 판단하려면, 표식을 어디에 두어야 할까?

문지기가 알 수 있으려면, 누구나 볼 수 있는 공용 공간에 표식이 있어야 해.

예를 들어:

- 입구 옆 게시판에 "홍길동 입장 중" 표시
- 로비의 출석부에 이름 적기
- 문지기가 직접 관리하는 명단

🖥️ 컴퓨터에서는?

프로그램들은 각자 격리된 공간(프로세스)에서 실행돼.
하지만 운영체제(OS)가 관리하는 커널(Kernel)이라는 공용 공간을 통해
서로의 존재를 확인할 수 있어.
게임 A
게임 B
메모장
↓ ↓ ↓
커널 (Kernel) - 공용 게시판
💡 핵심 개념
프로그램들은 격리되어 있지만, OS가 관리하는 커널이라는 공용 공간을 통해
서로의 존재를 확인한다.

2단계: 선점과 확인

두 번째 프로그램이 실행될 때 가장 먼저 해야 할 일은?

공용 공간을 먼저 살펴서 이미 실행 중인 표시가 있는지 확인해야 해.

무작정 실행하는 게 아니라, "체크 후 실행" 프로세스가 선행되어야 해.

// 게임 시작 시 실행되는 코드 if (공용_게시판에_이미_표시가_있나()) { MessageBox("이미 게임이 실행 중입니다!"); return; // 실행 중단 } 공용_게시판에_내_표시를_남긴다(); 게임_시작();
💡 핵심 개념
무작정 실행하는 것이 아니라, '체크 후 실행' 프로세스가 선행되어야 한다.

3단계: 뮤텍스(Mutex)라는 열쇠

"공용 게시판에 표시"를 구체적으로 어떻게 구현해?

Windows에서는 뮤텍스(Mutex)라는 걸 써.

Mutex = Mutual Exclusion (상호 배제)

"나 외엔 아무도 이 열쇠를 가질 수 없어!" 라는 개념이야.

// 실제 Windows API 코드 HANDLE hMutex = CreateMutex( NULL, // 보안 속성 TRUE, // 즉시 소유권 획득 "MyGame_ChosunHyupkyuk_GUID" // 고유한 이름! ); if (GetLastError() == ERROR_ALREADY_EXISTS) { // 이미 같은 이름의 뮤텍스가 존재함 = 게임이 이미 실행 중 MessageBox("이미 게임이 실행 중입니다!"); return; }
게임 A와 게임 B가 실수로 똑같은 이름의 열쇠를 사용하면 어떻게 돼?

충돌 발생!

한 게임이 켜져 있으면 다른 게임은 켜지지 않아.

그래서 개발자는 게임마다 고유한 이름(GUID)의 뮤텍스를 만들어야 해.

// 나쁜 예: 흔한 이름 사용 CreateMutex(NULL, TRUE, "GameMutex"); // 다른 게임과 충돌 가능! // 좋은 예: GUID(Globally Unique ID) 사용 CreateMutex(NULL, TRUE, "{A1B2C3D4-E5F6-7890-ABCD-EF1234567890}");
💡 핵심 개념
개발자는 게임마다 고유한 이름(GUID/String)의 뮤텍스를 만들어 중복을 방지한다.

4단계: 프로그램의 자발적 종료

열쇠를 얻지 못한 두 번째 프로그램은 어떻게 행동해야 할까?

두 가지 선택지가 있어:

1. 기다린다 - 첫 번째가 끝날 때까지 대기 (WaitForSingleObject)
2. 포기한다 - 유저에게 안내를 띄우고 스스로 종료(Exit)

대부분의 게임은 2번을 선택해.

if (GetLastError() == ERROR_ALREADY_EXISTS) { MessageBox( NULL, "이미 게임이 실행 중입니다.\n기존 게임을 종료 후 다시 시도해주세요.", "실행 오류", MB_OK | MB_ICONWARNING ); return 0; // 프로그램 스스로 종료 }
💡 핵심 개념
다중 클라 방지는 프로그램이 스스로 "난 두 번째구나"를 깨닫고 물러나게 만드는 설계다.

⚔️ 여기서부터 전쟁이 시작된다

위의 1~4단계는 "정상적인 유저"를 위한 설계야.

하지만 해커들은 다르게 생각해:

"두 번째 프로그램이 스스로 종료하게 만드는 거잖아?
그럼 그 '종료 조건'을 무력화하면 되겠네!"

5단계: 해커의 첫 번째 수법 (핸들 닫기)

첫 번째 게임을 끄지 않고 '열쇠(표식)'만 없애려면 어떻게 해야 할까?

공용 공간(게시판)에 붙은 포스트잇(핸들)만 몰래 떼어내면 돼.

첫 번째 게임은 계속 돌아가지만, 게시판에는 아무 표시도 없어지는 거지.

게임 1 (실행 중)
→
뮤텍스 핸들
Process Hacker
→ 핸들 강제 닫기!
게임 1 (실행 중)
...
뮤텍스 사라짐
그걸 어떻게 해?

Process Hacker 같은 외부 도구를 이용해.

1. 실행 중인 게임 프로세스를 찾는다
2. 그 프로세스가 들고 있는 핸들 목록을 본다
3. 뮤텍스 핸들을 찾아서 "Close Handle" 클릭!

이제 두 번째 게임을 켜면?
→ "어? 뮤텍스가 없네? 내가 첫 번째구나!" → 실행 성공

💡 핵심 개념
외부 도구(Process Hacker 등)를 이용해 첫 번째 게임이 쥐고 있는
뮤텍스 핸들(Handle)을 강제로 닫아버린다.

6단계: 방어자의 대응 (주기적 검사)

해커가 열쇠를 뺏어갔는지 게임 중에 어떻게 확인할까?

게임 시작할 때만 체크하면 안 돼.
실행 중에도 가끔씩(Polling) OS에게 물어봐야 해.

"내 번호표가 아직 유효한가?"

// 게임 메인 루프에서 주기적으로 체크 void GameLoop() { while (gameRunning) { UpdateGame(); RenderFrame(); // 5초마다 뮤텍스 유효성 체크 if (currentTime - lastCheckTime > 5000) { if (!ValidateMutexHandle(hMutex)) { // 뮤텍스가 사라졌다! 해킹 감지! LogSuspiciousActivity(); ForceShutdown(); // 게임 강제 종료 } lastCheckTime = currentTime; } } }
ValidateMutexHandle()은 어떻게 구현해?

몇 가지 방법이 있어:

// 방법 1: WaitForSingleObject로 상태 확인 DWORD result = WaitForSingleObject(hMutex, 0); // 즉시 반환 if (result == WAIT_ABANDONED || result == WAIT_FAILED) { // 뮤텍스가 비정상! } // 방법 2: 핸들 정보 조회 if (!GetHandleInformation(hMutex, &flags)) { // 핸들이 유효하지 않음! }
💡 핵심 개념
실행 시점뿐만 아니라, 실행 중에도 핸들의 유효성을 체크하여
해커의 기습을 막는다.

7단계: 고차원 기만 (API 후킹)

게임이 주기적으로 체크하면 해커는 어떻게 대응해?

해커: "게임이 OS한테 물어보는 걸 가로채면 되겠네!"

OS가 "열쇠 없어졌어"라고 대답하려는데,
해커가 그 대답을 가로채서 "아직 있어!"라고 거짓말을 해.

정상적인 경우

게임
→
WaitForSingleObject()
→
커널
→
"실패!"

API 후킹된 경우

게임
→
가짜 함수
→
"성공!"
(커널까지 안 가고 바로 거짓 응답)
그게 가능해?

가능해. 이걸 API 후킹(Hooking)이라고 해.

게임이 호출하는 Windows API 함수의 주소를 해커가 만든 가짜 함수로 바꿔치기하는 거야.

// 해커의 가짜 함수 DWORD WINAPI Fake_WaitForSingleObject(HANDLE hHandle, DWORD dwMilliseconds) { if (IsMutexHandle(hHandle)) { return WAIT_OBJECT_0; // 무조건 "성공!" 반환 } return Original_WaitForSingleObject(hHandle, dwMilliseconds); }
💡 핵심 개념
API 후킹(Hooking)을 통해 게임과 OS 사이의 통신을 조작하여
방어 시스템을 무력화한다.

8단계: 최후의 전쟁터 (커널과 Syscall)

공식 통로(API)가 오염되었다면 어떻게 해야 할까?

논리적 결론:

공식 창구를 거치지 않고 OS의 심장부(커널)로 직접 통하는 비밀 통로를 이용해야 해.

이걸 Direct Syscall이라고 해.

// 일반적인 방식 (후킹 가능) WaitForSingleObject(hMutex, 0); // → ntdll.dll → 커널 // Direct Syscall (후킹 우회) __asm { mov eax, 0x0004 // NtWaitForSingleObject의 시스템 콜 번호 mov edx, esp syscall // 직접 커널로! }
그럼 이것도 막을 수 있어?

여기서부터는 커널 레벨 전쟁이야.

방어 측: 커널 드라이버를 설치해서 커널에서 직접 감시
공격 측: 커널 드라이버를 우회하거나, 취약점을 찾아 공격

결국 싸움은 "누가 더 컴퓨터의 깊은 곳(바닥)을 점령하느냐"의 전쟁으로 이어져.

컴퓨터의 계층 구조

유저 모드 (게임, Cheat Engine)
↕ API (후킹 가능)
커널 모드 (안티치트 드라이버 vs 커널 해킹)
↕
하드웨어 (CPU, RAM)

📌 핵심 정리: 다중 클라 방지의 공방전

  • 뮤텍스(Mutex) - OS의 공용 공간에 "나 실행 중!" 표식을 남기는 것
  • 체크 후 실행 - 두 번째 프로그램은 표식을 확인하고 스스로 물러남
  • 핸들 닫기 - 해커가 외부 도구로 뮤텍스 핸들을 강제 해제
  • 주기적 검사 - 방어자가 실행 중에도 뮤텍스 유효성을 확인
  • API 후킹 - 해커가 검사 결과를 가로채서 거짓말
  • Direct Syscall - API를 우회해 커널에 직접 접근
  • 커널 레벨 전쟁 - 결국 더 깊은 곳을 점령하려는 싸움

🎮 실제 게임들은 어떻게 해?

현업에서는 어떤 방법을 쓰고 있어?

대부분의 온라인 게임은 여러 방어층을 조합해:

1. 뮤텍스 기본 체크 - 일반 유저 대응
2. 주기적 유효성 검사 - 단순 해킹 도구 대응
3. 안티치트 엔진 - API 후킹 탐지, 커널 드라이버 설치
4. 서버 측 검증 - 같은 계정의 다중 접속 감지

🏰 비유: 성을 지키는 여러 겹의 방벽

- 1겹 (뮤텍스): 성문 앞 번호표 시스템
- 2겹 (주기적 검사): 순찰병의 정기 점검
- 3겹 (안티치트): 성벽 위 감시탑
- 4겹 (서버 검증): 왕이 직접 명단 확인

이 문서는 교육 목적으로 작성되었습니다.
실제 온라인 게임에서 다중 클라이언트 제한을 우회하면:
- 계정 영구 정지
- 이용약관 위반으로 법적 분쟁 가능
- 게임사에 손해배상 청구 가능
