왜 같은 프로시저가 어제는 빠르고 오늘은 느릴까?

Parameter Sniffing - 첫 번째 파라미터가 운명을 결정한다

Part 1. 이상한 현상

프로시저가 어제는 0.1초 걸렸는데 오늘 갑자기 5초 걸려. 코드 안 바꿨는데?

Parameter Sniffing 문제일 가능성이 높아.

파라미터 스니핑?

"첫 실행 때 들어온 파라미터"로 실행 계획을 만들고 캐싱하는 것.

그 계획이 다른 파라미터에는 안 맞을 수 있어.

Part 2. 어떻게 발생해?

자세히 설명해줘.

프로시저 실행 과정을 보자.

[프로시저 첫 실행 시] 1. gp_LoadCharacter(charunique=1) 호출 2. SQL Server: "처음 보는 프로시저네, 실행 계획 만들자" 3. 파라미터 1로 최적의 계획 생성 (Index Seek) 4. 이 계획을 캐시에 저장 5. 실행: 0.1초 [이후 실행들] 6. gp_LoadCharacter(charunique=999999) 호출 7. SQL Server: "아, 이미 계획 있네. 그거 쓰자" 8. 캐시된 계획 사용 (Index Seek) 9. 실행: 0.1초 ← 여기까진 OK
뭐가 문제인 거야? 잘 동작하는데?

문제는 "첫 파라미터가 특이한 경우"야.

[문제 시나리오] 서버 재시작 후 첫 호출: gp_GetCharacterByGuild(guildID=1) ← 길드 1 = 회원 5만 명! SQL Server: "guildID=1이면 5만 행이네. Table Scan이 낫겠다" 계획 생성: Table Scan 계획 캐시 저장 이후 호출: gp_GetCharacterByGuild(guildID=12345) ← 길드 12345 = 회원 10명 SQL Server: "이미 계획 있네. Table Scan으로 실행" 결과: 10명 찾는데 Table Scan?? → 느림!

5만 명용 계획으로 10명을 찾는 꼴이야.

반대의 경우도 마찬가지.

Part 3. 게임에서 실제 예시

프로시저 위험 파라미터 문제 상황
gp_GetGuildMembers guildID 첫 호출이 대형 길드면 소형 길드 느림
gp_GetMailByDate startDate 첫 호출이 1년치면 하루치도 느림
gp_GetRankByLevel minLevel 첫 호출이 level>1이면 모든 호출 느림

⚠️ 특히 위험한 상황

서버 재시작/DB 재시작 직후

→ 모든 계획 캐시 초기화

→ 첫 호출의 파라미터가 모든 것을 결정

Part 4. 해결책

어떻게 해결해?

여러 방법이 있어.

방법 1: OPTION (RECOMPILE)

CREATE PROCEDURE gp_GetGuildMembers @guildID int AS BEGIN SELECT * FROM TCharacter WHERE guildID = @guildID OPTION (RECOMPILE) -- 매번 새로 컴파일! END

장점: 항상 최적의 계획

단점: 매번 컴파일 비용 발생

방법 2: OPTIMIZE FOR

-- 특정 값으로 최적화 SELECT * FROM TCharacter WHERE guildID = @guildID OPTION (OPTIMIZE FOR (@guildID = 100)) -- 100명 길드 기준 -- 또는 "알 수 없는 값"으로 OPTION (OPTIMIZE FOR UNKNOWN) -- 평균적인 분포 가정

방법 3: 로컬 변수 사용

CREATE PROCEDURE gp_GetGuildMembers @guildID int AS BEGIN DECLARE @localGuildID int = @guildID -- 로컬 변수로 복사 SELECT * FROM TCharacter WHERE guildID = @localGuildID -- 로컬 변수 사용 END

로컬 변수는 sniffing이 안 돼서 평균적인 계획이 생성됨.

Part 5. 언제 어떤 방법을 써?

상황 권장 방법 이유
파라미터에 따라 행 수 차이 큼 RECOMPILE 매번 최적 계획 필요
대부분 비슷한 행 수 OPTIMIZE FOR 대표값으로 충분
자주 호출되는 프로시저 로컬 변수 컴파일 비용 절약
간헐적 호출 RECOMPILE 컴파일 비용 감수 가능

Part 6. Parameter Sniffing 진단

이 문제인지 어떻게 알아?

실행 계획을 확인해봐.

-- 캐시된 계획의 파라미터 확인 SELECT cp.objtype, st.text AS query, qp.query_plan, qs.execution_count, qs.total_elapsed_time / qs.execution_count AS avg_time FROM sys.dm_exec_cached_plans cp CROSS APPLY sys.dm_exec_query_plan(cp.plan_handle) qp CROSS APPLY sys.dm_exec_sql_text(cp.plan_handle) st INNER JOIN sys.dm_exec_query_stats qs ON cp.plan_handle = qs.plan_handle WHERE st.text LIKE '%gp_GetGuildMembers%'

의심 신호:

• 같은 프로시저인데 실행 시간이 천차만별

• 서버 재시작 후 성능 변화

• 예상 행 수와 실제 행 수 차이가 큼

핵심 정리

  • Parameter Sniffing = 첫 파라미터로 실행 계획 결정
  • 문제: 첫 파라미터가 특이하면 다른 호출 전부 느림
  • RECOMPILE: 매번 새 계획 (비용↑, 정확도↑)
  • OPTIMIZE FOR: 대표값으로 계획 (균형)
  • 로컬 변수: sniffing 회피 (평균 계획)
  • 위험 시점: 서버 재시작 직후, 캐시 초기화 후
