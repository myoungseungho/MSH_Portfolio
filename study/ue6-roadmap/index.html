언리얼6를 왜 새로 만든다고? — UE5의 고민과 UE6의 답

셰이더 버벅임, 100명 천장, UE5/UEFN 분리 — 무엇이 불편했고, Verse·Iris·통합으로 뭘 바꾸나 (초딩도 이해하는 비유 중심)

30초 결론

2026년 6월 17일, Epic이 "언리얼6(UE6) 개발 시작"을 발표했어. 핵심 공식: UE5 + UEFN = UE6 (게임 만드는 도구 + 포트나이트 만드는 도구를 하나로 합침).

UE5의 3대 불편: ① 화면이 뚝뚝 끊기는 셰이더 컴파일 스터터링 ② 도구가 UE5·UEFN로 두 동강 ③ 세션형 ~100명 천장(수천 명 영속 세계가 안 됨).

UE6의 답: 도구 통합 + Verse 언어로 대규모 영속 월드 + Scene Graph + AI(Claude·Gemini) 통합 + 스터터링/쿡타임 제거.

단, 발표지 출시가 아니야 — 얼리액세스 2027년, 정식은 그로부터 12~18개월 뒤. 그리고 Verse가 와도 'UE로 MMO 끝'은 아님(뒤에서 설명).

Part 1. 언리얼5는 뭐가 불편했길래?

그래픽 좋다고 소문난 UE5인데, 개발자들이 왜 불만이었어?

게임 하다가 화면이 갑자기 뚝… 뚝… 끊긴 적 있지? 그게 제일 큰 원흉이야.

이름이 셰이더 컴파일 스터터링(shader compilation stuttering) 인데, 풀어보면 이래.

• 셰이더(shader) = 화면을 색칠하고 빛 반사를 그려주는 '작은 그림 프로그램'

• 컴파일(compile) = 컴퓨터가 알아듣게 '번역하는 작업'

게임이 처음 보는 효과를 만나면 "어 이거 번역 좀 하고 올게" 하면서 그 순간 멈추는 거야.

🍳 식당 비유로 보는 스터터링 [UE5 = 주문 받고 그때 썰기] 손님: "불꽃 효과 주세요!" 주방: 재료 꺼내 → 썰고 → 익히고... ⏳ (화면 뚝!) → 음식 늦게 나옴 = 게임 끊김 [UE6 목표 = 미리 다 썰어둠] 개점 전: 모든 재료 손질 완료 ✅ 손님: "불꽃 효과 주세요!" 주방: 바로 접시에 → (화면 안 끊김)
끊김 말고 또?

도구가 두 개로 쪼개져 있었어.

• UE5 = 진짜 게임 만드는 전문가용 공장

• UEFN(Unreal Editor for Fortnite) = 포트나이트 안에 들어갈 미니게임 만드는 도구

가위랑 칼을 따로 들고 다니는 셈이라, 한쪽에서 만든 걸 다른 쪽으로 옮기기가 번거로웠어. 그래서 UE6에서 하나로 합치는 게 1번 목표야.

💭 잠깐, 이런 생각 들지 않아?
미리 다 번역해두면 끝 아냐? 왜 지금까지 안 했어?
셰이더 조합이 수만~수십만 가지라서 그래. 재질 × 조명 × 그림자 × 플랫폼이 곱해지면 폭발하거든. 다 미리 굽자니 빌드(쿡) 시간이 몇 시간씩 늘고, 안 굽자니 게임 중에 끊겨. UE6는 "필요한 것만 똑똑하게 미리" + "굽는 시간 자체를 줄이기"로 이 줄다리기를 푸는 쪽이야.
합치면 UE5 쓰던 사람은 다 새로 배워야 해?
Epic 말로는 "UE5 + UEFN + 추가"라 기존 UE5 기반을 버리는 게 아니라 흡수·확장이래. 다만 게임 로직을 Verse로 옮기는 건 새 언어 학습이 필요 — 공짜는 아니야.

Part 2. "언리얼은 100명이 한계"라는 그 말, 맞아?

포트나이트는 100명이 같이 하던데? 그게 한계야?

맞아, 그게 유명한 구조적 한계야. 이유는 UE 네트워크의 태생 때문이야.

UE는 데디케이티드 서버(전용 서버) 1대 = 한 판(세션) 구조로 태어났어. 서버 한 대가 모든 플레이어와 물건을 머릿속에 다 들고 돌려.

사람이 늘면? 한 명 움직일 때마다 주변 모두에게 알려줘야 해서 일이 N×N로 폭발해. 그래서 보통 수십~100명 선에서 한 대가 버티는 천장이 와.

그럼 100명 들어가는 매치는 어떻게 되는 거야? 한번 맞춰봐.

"UE면 다 100명 되는 거 아냐?"라고 생각했지? 아니야.

포트나이트 100명은 Epic이 엔진을 직접 갈아서 만든 특별 케이스고, 평범한 UE 프로젝트를 그대로 쓰면 보통 32~64명이 안정선이야. "박스 그대로의 UE"는 100명도 빠듯해. 수천 명 영속 세계(MMORPG)는 한 월드로는 아예 불가능하고.

🏟️ 왜 사람 늘면 폭발할까 (서로에게 알려주기) 2명: A↔B = 1쌍 4명: A↔B A↔C A↔D B↔C ... = 6쌍 100명: ............ = 4,950쌍 1000명: ................... = 약 50만 쌍 💥 → 인원이 10배면 일은 약 100배 → 이래서 '한 서버 = 한 판'은 천장이 낮다
그럼 MMO들은 어떻게 수천 명을 굴려?

두 가지로 우회해.

① 샤딩/채널 — 한 세상을 여러 서버로 쪼개 '1채널, 2채널'로 나눠. 100명 한계를 여러 개 복사해서 푸는 거야. (조선협객전도 한양1·한양2처럼 채널·존을 나눠.)

② 자체 네트워크 — UE 기본 동기화를 버리고 회사가 직접 만든 서버 통신을 붙여.

즉 지금까진 "UE가 MMO를 해준 게 아니라, 개발사가 억지로 우회해서" 한 거야. 이 부분은 Ch15에서 더 깊게 다뤘어.

Part 3. UE6의 핵심 무기 ① — Verse 언어

그래서 UE6는 그 100명 천장을 어떻게 깨겠다는 거야?

게임을 만드는 '말투(언어)'를 통째로 바꿔. 그 새 언어가 Verse(버스)야.

• 프로그래밍 언어 = 컴퓨터한테 시키는 명령어 말투 (사람으로 치면 한국어·영어)

Epic이 Verse를 만든 목적을 그대로 옮기면: "대규모의, 계속 살아있는 세계를 떠받치고, 전역 상태(global state)가 그냥 알아서 작동하며, 동시성을 런타임이 알아서 정확히 처리한다"는 거야.

🔐 Verse = 안 꼬이는 똑똑한 사물함 [지금까지] 친구 3명이 같은 사물함 동시에 열기 → 물건이 섞이거나 사라짐 (개발자가 직접 자물쇠 채워야) [Verse] 여러 명이 동시에 와도 런타임이 자동으로 줄 세워 처리 → 절대 안 섞임 (= transactionally correct concurrency)
"전역 상태가 그냥 작동한다"가 왜 그렇게 대단한 거야?

MMO에서 제일 어려운 사고가 바로 "여러 명이 동시에 같은 돈·아이템·상자를 건드릴 때 꼬이는 것"이거든. 복제(아이템 뻥튀기) 버그가 다 여기서 나와.

지금은 개발자가 일일이 자물쇠(락)를 채우고 검증해야 하는데, Verse는 그걸 언어 런타임이 자동으로 보장하겠다는 거야. 잘 되면 MMO 만들기의 난이도가 확 내려가.

💭 잠깐, 이런 생각 들지 않아?
자동으로 다 처리하면 우리 같은 서버 개발자는 필요 없어지는 거 아냐?
자동화는 천장이 높아질 뿐, 공짜는 아니야. 런타임이 "안 꼬이게" 보장하려면 내부적으로 비용(메모리·지연)을 치러. 대규모일수록 "자동이 만든 부하"를 이해하고 조율하는 사람이 더 중요해져. 도구가 좋아질수록 "무엇을·왜"를 판단하는 사람의 값이 올라가는 거지.
C++ 안 쓰고 Verse만 쓰면 느려지지 않아?
트레이드오프 맞아. 안전·편의를 얻는 대신 저수준 제어를 일부 내려놓는 구조라, 극한 성능이 필요한 부분은 여전히 C++가 남을 가능성이 커. "전부 Verse"가 아니라 "게임플레이는 Verse, 엔진 코어는 C++" 분업이 현실적.

Part 4. UE6의 핵심 무기 ② — Iris와 Scene Graph

'아이리스(Iris)'라는 것도 그 한계랑 관련 있다던데, 맞아?

정확해. Iris = 언리얼의 차세대 리플리케이션 시스템(새 네트워크 동기화 엔진)이야. UE 5.1쯤 실험 기능으로 등장했고, 포트나이트 네트워크를 굴리던 팀이 만들었어.

• 리플리케이션 = 서버가 가진 정보를 모든 클라에게 복사해 뿌리는 것

Part 2에서 본 그 '폭발하는 부분'을 새로 짠 게 Iris야. 같은 CPU로 더 많은 오브젝트·연결을 동기화하는 게 목표지.

항목옛 방식 (레거시 복제)Iris
처리 방식오브젝트마다 일일이 비교묶어서 한 번에(batch)
CPU 부담인원·물건 늘면 급증훨씬 덜 먹게 설계
구조게임 로직과 엉킴동기화만 따로 떼냄(모듈화)
확장성수십~100명대 천장더 많은 액터·연결 지향
그럼 Iris 깔면 UE로 MMO 되는 거네?

아니, 여기가 중요해. Iris ≠ MMO 만능 해결책이야.

• Iris가 푸는 것 = "한 서버 안에서 동기화를 더 효율적으로" → 한 판의 천장을 높여줌 (100명 → 더 많이)

• Iris가 안 푸는 것 = "수천 명을 여러 서버에 어떻게 나눠 담나(샤딩·심리스 월드)" + "영속 상태·DB" → 여전히 별개 문제

진짜 대규모는 Iris(동기화) + Verse(정합성) + 서버 분산, 이 셋이 다 모여야 돼.

Scene Graph는 또 뭐야?

Scene Graph(씬 그래프)는 게임의 핵심 부품(애니메이션·아이템·플레이어 능력 같은 거)을 레고 블록처럼 끼워서 Verse로 쉽게 짜게 해주는 새 구조야.

• 씬(scene) = 게임 장면 / 그래프(graph) = 부품들이 어떻게 연결됐는지 보여주는 지도

쉽게 말하면 "코딩을 덜 하고도 게임 메커닉을 조립"하게 만드는 도구야.

Part 5. 나머지 변화 — AI, 오픈 표준, 쿡타임

요즘 다 AI라던데 UE6도?

맞아. Claude(클로드)와 Gemini(제미나이) 같은 AI가 개발 파이프라인에 붙어. "이 코드 이렇게 하면 돼" 하고 옆에서 도와주는 보조 요리사처럼. 창의성·생산성을 곱하기로 늘리는 도구로 본대.

'오픈 표준', '쿡타임'은?

• 오픈 스탠다드(open standards) = 누구나 쓰는 공통 규격(USB 케이블처럼 어디 꽂아도 됨). 내가 만든 캐릭터·아이템·경제를 다른 게임·생태계로 옮길 수 있게 하겠다는 야심이야.

• 쿡(cook) = 게임 재료를 기기에서 돌아가게 미리 '익혀두는' 작업. 이 쿡 타임을 줄여서 개발자가 수정→확인을 빨리 반복하게(=이터레이션 루프를 짧게) 만들어.

💭 잠깐, 이런 생각 들지 않아?
아이템을 다른 게임으로 옮긴다고? 그게 진짜 돼?
기술보다 이해관계가 더 어려운 문제야. A게임에서 산 칼을 B게임이 받아주려면, 밸런스·저작권·매출 배분을 회사들이 합의해야 해. Epic이 노리는 건 "포트나이트 생태계" 안에서 먼저 통하게 만드는 것 — 전 우주적 호환은 아직 꿈에 가까워.

Part 6. 언제 나오는데? (일정과 현실)

시점무슨 일
2026.06.17"UE6 개발 시작" 발표 (Unreal Fest Chicago, State of Unreal)
2027년얼리 액세스(Early Access) = 미리 맛보기 (완성품 아님)
+12~18개월그 뒤 정식 출시
2026~2027포트나이트 콜라보 30개+ 예정
그럼 곧 게임 만들 때 UE6 쓰면 되겠네?

서두르면 안 돼. 발표는 "되게 하겠다"는 선언이지 "됐다"가 아니야. 얼리액세스가 2027년이고, 실제 MMO급 스케일이 검증되는 건 한참 뒤야.

참고로 그동안 UEFN로 창작자들에게 10억 달러(약 1.3조 원)+를 지급했고 제작 속도가 40% 빨라졌다고 해. 발표대로 되면 게임 서버 업계에도 꽤 큰 변화겠지.

현재 우리(C++ IOCP MMO 서버) 입장에서 한 줄로?

비교 대상 = 우리는 지금 채널·존 샤딩 + 자체 패킷 + DB 영속으로 수천 명을 굴려.

나은 점 = UE6/Verse가 약속대로면 "동시성 정합성"을 언어가 보장해줘 복제 버그 류가 줄어.

잃는 것 = 대신 엔진·언어 생태계에 종속되고, 저수준 제어와 검증된 안정성(우리가 수년간 다진 것)을 새 플랫폼에서 다시 쌓아야 해. "성숙한 자체 구조" vs "미래의 편의"의 줄다리기인 거지.

핵심 정리

  • 한 줄 공식: UE5 + UEFN = UE6 (게임 도구 + 포트나이트 도구 통합) + 추가 기능
  • UE5 불편: ① 셰이더 스터터링(화면 뚝) ② 도구 두 동강 ③ 세션형 ~100명 천장(박스 그대로면 32~64명)
  • Verse: 대규모 영속 세계용 새 언어 — 동시에 같은 데이터 건드려도 런타임이 자동으로 안 꼬이게(transactional concurrency)
  • Iris: 차세대 복제로 한 서버 동기화 효율↑ = 천장 높이기. 단 Iris 혼자선 MMO 안 됨(샤딩·DB는 별개)
  • Scene Graph: 게임 메커닉을 레고처럼 조립 / AI(Claude·Gemini)·오픈표준·쿡타임 단축도 함께
  • 일정·현실: 2026.6.17 발표 → 2027 얼리액세스 → +12~18개월 정식. '발표=출시' 아님, MMO 스케일 검증은 한참 뒤

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. UE5로 만들던 내 프로젝트는 UE6로 그냥 넘어가?

Epic은 "UE5 + UEFN을 흡수·확장"이라 호환을 강조하지만, 게임 로직을 Verse로 옮기는 건 별개 작업이야.

렌더링·에셋 같은 자산은 대체로 이어지되, 게임플레이 코드(특히 Blueprint/C++ 로직)는 점진적 마이그레이션이 현실적. "버튼 한 번에 변환"은 기대 안 하는 게 좋아.
Q. Verse가 안 꼬이게 자동 처리하면, 락(Lock) 공부는 이제 필요 없어?

오히려 더 알아야 해 — 자동화가 "왜·어떻게" 안 꼬이게 하는지 모르면 성능 문제를 못 잡아.

  • Verse의 트랜잭션은 충돌 시 재시도(rollback & retry)로 푸는 방식일 가능성이 커. 충돌이 잦으면 보이지 않게 느려져.
  • "왜 느리지?"를 디버깅하려면 결국 동시성 원리를 알아야 함.
도구가 좋아질수록 "도구가 뭘 대신 해주는지" 아는 사람의 값이 올라간다 — 우리 섹션 Ch15의 결론과 같아.
Q. 그럼 우리 같은 자체 서버는 UE6 나오면 갈아타야 해?

당장은 아니야. 이유:

  • 검증 시간: 정식 + MMO 스케일 검증까지 최소 2~3년. 그 전엔 도박.
  • 성숙도: 우리가 수년간 다진 영속·샤딩·DB·서버간 메시징을 새 플랫폼에서 다시 쌓아야 함.
  • 현실적 길: 많은 한국 MMO가 클라는 UE, 서버는 자체 두 트랙. UE6도 "클라엔진으로 먼저 흡수, 서버는 관망"이 안전.
Q. "전역 상태가 그냥 작동"이면, DB는 이제 필요 없어지나?

열린 질문이야 — 아직 누구도 확답 못 해. Verse의 영속 상태가 어디까지 "진짜 DB급 영속(백업·정산·감사)"을 대체할지는 미지수.

한번 생각해봐: 게임 안 상태가 자동 영속된다 쳐도, 매출 정산·환불·로그 감사 같은 건 여전히 별도 신뢰 가능한 저장소가 필요하지 않을까? 정답은 안 줄게 — 직접 굴려봐.
