nullptr 역참조 크래시

가장 흔한 버그 — 주소 0x00000000 읽기 실패

Part 1. 증상

주소 0x00000000을(를) 읽는 동안 액세스 위반이 발생했습니다

nullptr 포인터를 역참조한 것이다.

즉, 가리키는 게 없는 포인터로 접근하려고 함.

// 크래시 발생 코드 CPlayer* pPlayer = nullptr; pPlayer->TakeDamage(10); // 💥 크래시! // 또는 CPlayer* pPlayer = FindPlayer(nID); // null 반환됨 pPlayer->m_nHP -= 10; // 💥 크래시!

Part 2. 주소가 0이 아닌 작은 값일 때

주소 0x00000008을(를) 읽는 동안...

nullptr인 객체 포인터로 멤버 변수에 접근한 것.

0 + 멤버 오프셋 = 작은 주소

class CPlayer { int m_nType; // offset 0 int m_nHP; // offset 4 int m_nMP; // offset 8 ← 여기! }; CPlayer* p = nullptr; p->m_nMP = 100; // 주소 0x00000008 접근 시도 → 크래시

Part 3. 디버깅 방법

어디서 nullptr이 된 거야?

1. Call Stack에서 호출 경로 확인

2. 해당 포인터에 데이터 중단점 설정

3. 포인터가 nullptr로 바뀌는 순간 잡기

// 데이터 중단점으로 추적 1. 크래시 난 줄에서 pPlayer 주소 확인 (예: &pPlayer = 0x12345678) 2. Debug → New Breakpoint → Data Breakpoint 3. 주소: 0x12345678, 크기: 8 (64비트 포인터) 4. 조건: (*(void**)0x12345678) == 0 5. 실행 → nullptr로 바뀌는 순간 멈춤!

Part 4. 예방

어떻게 방지해?

1. 포인터 사용 전 null 체크

2. 함수가 null을 반환할 수 있으면 문서화

3. 가능하면 참조(&)나 스마트 포인터 사용

// 나쁜 코드 pPlayer->TakeDamage(10); // 좋은 코드 if (pPlayer) { pPlayer->TakeDamage(10); } // 더 좋은 코드 (early return) if (!pPlayer) { LOG_ERROR("Player is null!"); return; } pPlayer->TakeDamage(10);

핵심 정리

  • 0x00000000 = nullptr 직접 역참조
  • 작은 주소 (0x8, 0x10 등) = nullptr + 멤버 오프셋
  • 데이터 중단점으로 nullptr 되는 순간 추적
  • null 체크로 예방
