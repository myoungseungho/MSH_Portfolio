번들 단위 설계

씬별? 기능별? 캐릭터별? - 프로젝트에 맞는 최적의 번들 전략 선택하기

Part 1. 번들 설계의 중요성

번들 단위 설계가 왜 중요해?

번들 설계는 에셋 번들 시스템의 성패를 좌우하는 핵심 결정입니다. 잘못된 설계는 나중에 수정하기 매우 어렵습니다.

번들 설계가 영향을 미치는 요소:

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  초기 다운로드 크기                                              │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 너무 큰 번들 → 초기 설치 오래 걸림                        │  │
│  │ 너무 작은 번들 → 많은 HTTP 요청, 오버헤드                 │  │
│  └──────────────────────────────────────────────────────────┘  │
│                           ↓                                     │
│  패치/업데이트 크기                                              │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 잘못된 그룹핑 → 작은 수정에도 큰 번들 재다운로드          │  │
│  │ 좋은 그룹핑 → 변경된 에셋이 있는 번들만 업데이트          │  │
│  └──────────────────────────────────────────────────────────┘  │
│                           ↓                                     │
│  런타임 메모리 사용량                                            │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 필요한 것만 로드 vs 불필요한 에셋까지 함께 로드           │  │
│  └──────────────────────────────────────────────────────────┘  │
│                           ↓                                     │
│  로딩 시간                                                       │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ 동시 사용 에셋이 같은 번들 → 빠른 로드                    │  │
│  │ 동시 사용 에셋이 여러 번들에 분산 → 느린 로드             │  │
│  └──────────────────────────────────────────────────────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
잘못된 번들 설계의 결과는 어때?

실제 프로젝트 실패 사례

사례 1: 모든 에셋을 1개 번들에
┌─────────────────────────────────────────────────────────────┐
│ 설계: all_assets.bundle (5GB)                                │
│                                                             │
│ 결과:                                                        │
│ - 초기 다운로드: 5GB (사용자 이탈률 80%)                     │
│ - 메모리 사용: 전체 로드 불가 (Out of Memory)                │
│ - 패치: 텍스처 1개 수정 → 5GB 재다운로드                    │
│ - 로딩: 한 번에 로드 불가                                    │
│                                                             │
│ 교훈: "번들 1개는 번들이 없는 것과 같다"                     │
└─────────────────────────────────────────────────────────────┘

사례 2: 모든 에셋을 개별 번들에
┌─────────────────────────────────────────────────────────────┐
│ 설계: 에셋 10,000개 → 번들 10,000개                          │
│                                                             │
│ 결과:                                                        │
│ - 번들 매니페스트: 50MB (헤더/메타데이터 오버헤드)          │
│ - 의존성 그래프: 너무 복잡, 분석 시간 30초+                 │
│ - HTTP 요청: 씬 하나에 수백 개 요청                         │
│ - 로딩 시간: 요청 오버헤드로 오히려 느림                    │
│                                                             │
│ 교훈: "번들이 너무 많으면 관리가 불가능하다"                 │
└─────────────────────────────────────────────────────────────┘

사례 3: 잘못된 그룹핑 (업데이트 관점 무시)
┌─────────────────────────────────────────────────────────────┐
│ 설계: 알파벳 순서로 그룹핑                                    │
│ - bundle_a: Apple.png, Armor.fbx, Attack.anim                │
│ - bundle_b: Background.png, Boss.prefab, Button.png          │
│                                                             │
│ 결과:                                                        │
│ - 패치: Attack.anim 버그 수정 → bundle_a 전체 재다운로드    │
│        (관련 없는 Apple.png, Armor.fbx도 함께)              │
│ - 로딩: 캐릭터 로드에 필요한 에셋이 10개 번들에 분산        │
│                                                             │
│ 교훈: "그룹핑 기준은 논리적 연관성이어야 한다"               │
└─────────────────────────────────────────────────────────────┘
좋은 번들 설계의 기준이 뭐야?

번들 설계 원칙

  • 함께 쓰이는 것은 함께 묶기: 동시에 로드되는 에셋은 같은 번들에
  • 함께 바뀌는 것은 함께 묶기: 같이 업데이트되는 에셋은 같은 번들에
  • 적절한 크기 유지: 모바일 2~10MB, PC/콘솔 5~50MB
  • 의존성 최소화: 공유 에셋은 별도 Shared 번들로
  • 로드 경계 고려: 언로드 가능한 단위로 설계

Part 3. 씬 기반 설계 (Scene-based)

씬 기반 설계는 어떻게 하는 거야?

씬 기반 설계는 게임의 레벨/맵 단위로 번들을 구성합니다. 가장 직관적이고 구현하기 쉬운 방식입니다.

씬 기반 번들 구조 예시:

게임: 판타지 RPG (5개 지역)
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  core.bundle (항상 로드)                                        │
│  ├── 플레이어 캐릭터                                             │
│  ├── 기본 UI                                                     │
│  └── 공통 이펙트                                                 │
│                                                                 │
│  scene_tutorial.bundle (튜토리얼 섬)                            │
│  ├── 튜토리얼 지형                                               │
│  ├── 튜토리얼 NPC                                                │
│  └── 튜토리얼 전용 UI                                            │
│                                                                 │
│  scene_forest.bundle (숲 지역)                                   │
│  ├── 숲 지형/배경                                                │
│  ├── 숲 몬스터 (고블린, 늑대)                                    │
│  ├── 숲 NPC                                                      │
│  └── 숲 배경음악                                                 │
│                                                                 │
│  scene_dungeon.bundle (던전)                                     │
│  scene_castle.bundle (성)                                        │
│  scene_boss.bundle (보스방)                                      │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

메모리 흐름:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  게임 시작   →   [core] 상주                                    │
│       ↓                                                         │
│  튜토리얼    →   [core] + [scene_tutorial]                      │
│       ↓                                                         │
│  숲 입장     →   [core] + [scene_forest]                        │
│              →   scene_tutorial 언로드!                         │
│       ↓                                                         │
│  던전 입장   →   [core] + [scene_dungeon]                       │
│              →   scene_forest 언로드!                           │
│                                                                 │
│  메모리 = core(상주) + 현재 씬(1개만)                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
씬 기반의 장점과 단점은?
장점:
┌─────────────────────────────────────────────────────────────────┐
│ ✓ 직관적: 맵 = 번들, 이해하기 쉬움                              │
│ ✓ 메모리 효율: 현재 맵 에셋만 메모리에                          │
│ ✓ 로딩 로컬리티: 동시에 필요한 에셋이 한 번들에                 │
│ ✓ 언로드 명확: 맵 전환 시 이전 맵 번들 전체 언로드              │
│ ✓ 테스트 용이: 맵 단위로 독립적 테스트 가능                     │
└─────────────────────────────────────────────────────────────────┘

단점:
┌─────────────────────────────────────────────────────────────────┐
│ ✗ 에셋 중복: 여러 맵에서 쓰이는 에셋 중복                       │
│   예: 고블린이 숲, 던전 둘 다 등장 → 중복!                      │
│                                                                 │
│ ✗ 큰 번들 크기: 맵이 크면 번들도 거대해짐                       │
│   예: 오픈월드 맵 1개 = 1GB+                                    │
│                                                                 │
│ ✗ 부분 로드 어려움: 맵의 일부만 로드하기 어려움                 │
│   예: 넓은 맵에서 현재 위치 주변만 로드하고 싶을 때             │
│                                                                 │
│ ✗ DLC 복잡: 새 캐릭터가 여러 맵에 등장하면?                     │
│   → 모든 맵 번들 수정 필요                                       │
└─────────────────────────────────────────────────────────────────┘
// 씬 기반 번들 로더 예시 public class SceneBasedLoader : MonoBehaviour { private AssetBundle m_CoreBundle; private AssetBundle m_CurrentSceneBundle; private string m_CurrentSceneName; private void Awake() { // Core는 앱 시작 시 로드, 절대 언로드하지 않음 m_CoreBundle = AssetBundle.LoadFromFile( GetBundlePath("core") ); } public IEnumerator LoadScene(string sceneName) { // 이전 씬 번들 언로드 if (m_CurrentSceneBundle != null) { m_CurrentSceneBundle.Unload(true); // 에셋까지 해제 m_CurrentSceneBundle = null; } // 새 씬 번들 로드 string bundleName = $"scene_{sceneName}"; var request = AssetBundle.LoadFromFileAsync( GetBundlePath(bundleName) ); yield return request; m_CurrentSceneBundle = request.assetBundle; m_CurrentSceneName = sceneName; // 씬 로드 yield return SceneManager.LoadSceneAsync(sceneName); } }
씬 기반에서 에셋 중복은 어떻게 해결해?

Shared 번들을 도입하여 공유 에셋을 분리합니다:

개선된 씬 기반 구조 (Shared 추가):

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  shared_enemies.bundle (공유 몬스터)                            │
│  ├── 고블린 (여러 맵에서 등장)                                   │
│  ├── 슬라임                                                      │
│  └── 해골병사                                                    │
│                     ↑                                            │
│           ┌────────┴────────┐                                    │
│           ↓                 ↓                                    │
│  scene_forest.bundle   scene_dungeon.bundle                     │
│  ├── 숲 지형            ├── 던전 지형                            │
│  ├── 숲 전용 NPC        ├── 던전 전용 NPC                        │
│  └── (고블린 참조)      └── (고블린, 해골 참조)                  │
│                                                                 │
│  장점:                                                           │
│  - 고블린이 1번만 존재 (중복 제거)                               │
│  - 고블린 수정 시 shared_enemies만 업데이트                      │
│                                                                 │
│  단점:                                                           │
│  - 의존성 복잡해짐                                               │
│  - 로딩 시 shared도 함께 로드 필요                               │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

Part 4. 기능 기반 설계 (Feature-based)

기능 기반 설계는 어떻게 하는 거야?

기능 기반 설계는 게임의 시스템/기능 단위로 번들을 구성합니다. 라이브 서비스 게임에서 유용합니다.

기능 기반 번들 구조 예시:

게임: 라이브 서비스 모바일 RPG
┌─────────────────────────────────────────────────────────────────┐

│  core.bundle (필수 시스템)                                       │
│  ├── 게임 매니저                                                 │

│                                                                 │
│  feature_combat.bundle (전투 시스템)                             │
│  ├── 전투 UI (HP바, 스킬 버튼)                                   │
│  ├── 데미지 텍스트                                               │
│  ├── 스킬 이펙트                                                 │
│  └── 전투 사운드                                                 │
│                                                                 │
│  feature_gacha.bundle (가챠 시스템)                              │
│  ├── 가챠 UI                                                     │
│  ├── 뽑기 연출                                                   │
│  ├── 캐릭터 획득 이펙트                                          │
│  └── 확률 표시 UI                                                │
│                                                                 │
│  feature_guild.bundle (길드 시스템)                              │
│  ├── 길드 UI                                                     │
│  ├── 길드 홀 배경                                                │
│  ├── 길드 아이콘/엠블럼                                          │
│  └── 길드 채팅 UI                                                │
│                                                                 │
│  feature_pvp.bundle (PvP 시스템)                                 │
│  feature_raid.bundle (레이드 시스템)                             │
│  feature_crafting.bundle (제작 시스템)                           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

메모리 흐름:
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  게임 시작     →  [core]                                        │
│       ↓                                                         │
│  로비 입장     →  [core] + [feature_gacha]                      │
│                   (길드 버튼만 있고 길드 시스템은 미로드)        │
│       ↓                                                         │
│  전투 시작     →  [core] + [feature_combat]                     │
│                →  feature_gacha 언로드                          │
│       ↓                                                         │
│  길드홀 방문   →  [core] + [feature_guild]                      │
│                →  feature_combat 언로드                         │
│                                                                 │
│  필요한 기능만 로드 → 메모리 효율적!                            │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
기능 기반의 장점과 단점은?
장점:
┌─────────────────────────────────────────────────────────────────┐
│ ✓ 모듈화: 기능 단위로 독립적 개발/배포 가능                     │
│   예: 길드 팀이 feature_guild만 수정, 다른 팀에 영향 없음       │
│                                                                 │
│ ✓ 패치 효율: 특정 기능 수정 시 해당 번들만 업데이트             │
│   예: PvP 밸런스 패치 → feature_pvp만 재다운로드                │
│                                                                 │
│ ✓ A/B 테스트: 기능별 번들 교체로 테스트 용이                    │
│   예: 새 가챠 UI 테스트 → feature_gacha_v2 로드                 │
│                                                                 │
│ ✓ 점진적 출시: 기능을 하나씩 추가 가능                          │
│   예: v1.0 전투만, v1.1 길드 추가, v1.2 PvP 추가                │
└─────────────────────────────────────────────────────────────────┘

단점:
┌─────────────────────────────────────────────────────────────────┐
│ ✗ 기능 경계 모호: "이 에셋은 어느 기능에 속하지?"               │
│   예: 캐릭터 모델은 전투? 가챠? 로비? → 판단 어려움             │
│                                                                 │
│ ✗ 교차 의존성: 기능 간 공유 에셋 많으면 복잡                    │
│   예: 캐릭터가 전투, 가챠, 길드 모두에서 사용                   │
│                                                                 │
│ ✗ 씬 로딩 복잡: 하나의 씬에 여러 기능 번들 필요                 │
│   예: 로비 = UI기본 + 가챠 + 우편 + 상점 + ...                  │
│                                                                 │
│ ✗ 설계 오버헤드: 기능 분류와 의존성 설계에 시간 필요            │
└─────────────────────────────────────────────────────────────────┘
// 기능 기반 번들 매니저 예시 public class FeatureBundleManager { private Dictionary<string, FeatureBundle> m_Features = new(); public enum Feature { Combat, Gacha, Guild, PvP, Raid, Crafting } // 기능 활성화 (필요 시 로드) public IEnumerator EnableFeature(Feature feature) { string bundleName = $"feature_{feature.ToString().ToLower()}"; if (m_Features.ContainsKey(bundleName)) { m_Features[bundleName].RefCount++; yield break; } // 번들 로드 var bundle = new FeatureBundle(); yield return bundle.LoadAsync(bundleName); m_Features[bundleName] = bundle; } // 기능 비활성화 public void DisableFeature(Feature feature) { string bundleName = $"feature_{feature.ToString().ToLower()}"; if (!m_Features.TryGetValue(bundleName, out var bundle)) return; bundle.RefCount--; if (bundle.RefCount <= 0) { bundle.Unload(); m_Features.Remove(bundleName); } } } // 사용 예시 public class BattleManager { public IEnumerator StartBattle() { // 전투 시작 전 기능 활성화 yield return FeatureBundleManager.EnableFeature(Feature.Combat); // 전투 진행... } public void EndBattle() { // 전투 종료 시 비활성화 FeatureBundleManager.DisableFeature(Feature.Combat); } }

Part 5. 콘텐츠 기반 설계 (Content-based)

콘텐츠 기반 설계는 어떻게 하는 거야?

콘텐츠 기반 설계는 게임의 콘텐츠(캐릭터, 무기, 스킨 등) 단위로 번들을 구성합니다. 수집형 게임에 적합합니다.

콘텐츠 기반 번들 구조 예시:

게임: 캐릭터 수집형 RPG (100+ 캐릭터)

│                                                                 │
│  shared_characters.bundle (캐릭터 공통)                         │

│                                                                 │
│  char_001_warrior.bundle (전사 캐릭터)                          │
│  ├── 전사 메시                                                   │

│  ├── 전사 전용 스킬 이펙트                                       │
│  └── 전사 음성                                                   │
│                                                                 │
│  char_002_mage.bundle (마법사 캐릭터)                            │
│  char_003_archer.bundle (궁수 캐릭터)                            │
│  char_004_healer.bundle (힐러 캐릭터)                            │

메모리 흐름:
┌─────────────────────────────────────────────────────────────────┐

│  로드 상태:                                                      │

│  가챠에서 힐러 획득 → char_004_healer.bundle 다운로드           │

콘텐츠 기반의 장점과 단점은?
장점:
┌─────────────────────────────────────────────────────────────────┐
│ ✓ DLC 완벽 지원: 새 캐릭터 = 새 번들 추가, 기존 수정 없음       │
│                                                                 │
│ ✓ 온디맨드 다운로드: 보유/필요한 콘텐츠만 다운로드              │
│   예: 가챠 획득 시 해당 캐릭터 번들만 다운로드                  │
│                                                                 │
│ ✓ 메모리 최적화: 사용 중인 콘텐츠만 메모리에                    │
│   예: 전투에 출전한 4캐릭터만 로드                              │
│                                                                 │
│ ✓ 패치 독립성: 특정 캐릭터 수정 시 해당 번들만 업데이트         │
│   예: 전사 밸런스 패치 → char_001_warrior만 재다운로드          │
│                                                                 │
│ ✓ 확장성: 캐릭터가 100개든 1000개든 구조 동일                   │
└─────────────────────────────────────────────────────────────────┘

단점:
┌─────────────────────────────────────────────────────────────────┐
│ ✗ 번들 수 폭발: 콘텐츠 100개 = 번들 100개+                      │
│   → 매니페스트 관리, 의존성 추적 복잡                           │
│                                                                 │
│ ✗ 작은 번들 오버헤드: 각 번들의 헤더/메타데이터 누적            │
│   예: 1KB 에셋도 번들화하면 ~10KB 오버헤드                      │
│                                                                 │
│ ✗ 공유 에셋 관리: 여러 콘텐츠가 공유하는 에셋 처리 복잡         │
│   예: "불 이펙트"를 전사, 마법사, 드래곤이 공유                 │
│                                                                 │
│ ✗ 일괄 업데이트 어려움: 전체 캐릭터 수정 시 100개 번들 업데이트 │
└─────────────────────────────────────────────────────────────────┘
// 콘텐츠 기반 캐릭터 로더 public class CharacterLoader { private Dictionary<int, LoadedCharacter> m_LoadedCharacters = new(); // 캐릭터 프리로드 (보유 캐릭터 목록) public IEnumerator PreloadOwnedCharacters(List<int> ownedIds) { // 공유 번들 먼저 로드 yield return LoadBundle("shared_characters"); // 보유 캐릭터만 병렬 로드 var requests = new List<AssetBundleCreateRequest>(); foreach (int charId in ownedIds) { string bundleName = $"char_{charId:D3}"; // char_001, char_002, ... var request = AssetBundle.LoadFromFileAsync(GetPath(bundleName)); requests.Add(request); } // 모든 로드 완료 대기 foreach (var request in requests) { yield return request; } } // 새 캐릭터 획득 시 다운로드 public IEnumerator OnCharacterAcquired(int charId) { string bundleName = $"char_{charId:D3}"; // 서버에서 다운로드 using (var request = UnityWebRequestAssetBundle.GetAssetBundle( GetBundleUrl(bundleName), GetBundleHash(bundleName) )) { yield return request.SendWebRequest(); if (request.result == UnityWebRequest.Result.Success) { var bundle = DownloadHandlerAssetBundle.GetContent(request); CacheCharacter(charId, bundle); } } } }

Part 6. 하이브리드 설계

실제 프로젝트에서는 어떤 전략을 써?

실제 프로젝트는 대부분 하이브리드 설계를 사용합니다. 여러 전략을 계층적으로 조합합니다.

하이브리드 설계 예시: 대규모 모바일 RPG

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  Layer 0: Core (앱 시작 시 로드, 절대 언로드 안 함)             │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ core_essential.bundle                                     │  │
│  │ ├── 기본 셰이더, 폰트                                      │  │
│  │ ├── 네트워크 매니저                                        │  │
│  │ └── 공통 UI 프레임워크                                     │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                     │
│  Layer 1: Shared (타입 기반 - 공유 에셋)                        │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ shared_ui.bundle        - UI 아틀라스, 위젯               │  │
│  │ shared_characters.bundle - 캐릭터 공통 (본, 기본 애니)    │  │
│  │ shared_effects.bundle   - 공통 이펙트                     │  │
│  │ shared_audio.bundle     - BGM, 공통 SFX                   │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                     │
│  Layer 2: Feature (기능 기반)                                   │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ feature_battle.bundle   - 전투 시스템                     │  │
│  │ feature_gacha.bundle    - 가챠 시스템                     │  │
│  │ feature_guild.bundle    - 길드 시스템                     │  │
│  │ feature_pvp.bundle      - PvP 시스템                      │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                     │
│  Layer 3: Content (콘텐츠 기반)                                 │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ char_001.bundle ~ char_100.bundle  - 개별 캐릭터          │  │
│  │ weapon_001.bundle ~ weapon_050.bundle - 개별 무기         │  │
│  │ skin_001.bundle ~ skin_200.bundle  - 개별 스킨            │  │
│  └───────────────────────────────────────────────────────────┘  │
│                           ↑                                     │
│  Layer 4: Scene (씬 기반 - 맵 전용)                             │
│  ┌───────────────────────────────────────────────────────────┐  │
│  │ scene_lobby.bundle      - 로비 전용 에셋                  │  │
│  │ scene_chapter1.bundle   - 챕터1 전용 에셋                 │  │
│  │ scene_raid_dragon.bundle - 드래곤 레이드 전용             │  │
│  └───────────────────────────────────────────────────────────┘  │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

의존성 방향: Layer 4 → 3 → 2 → 1 → 0 (위로만)
하이브리드 설계의 로딩 흐름은 어때?
하이브리드 설계 로딩 시나리오:

시나리오: 전투 씬 입장 (파티: 전사, 마법사, 궁수)

┌─────────────────────────────────────────────────────────────────┐
│ 1단계: Core 확인 (앱 시작 시 이미 로드됨)                        │
│ [core_essential] ✓                                              │
├─────────────────────────────────────────────────────────────────┤
│ 2단계: Shared 로드 (없으면 로드)                                 │
│ [shared_characters] ✓ (캐릭터 공통)                             │
│ [shared_effects] ✓ (이펙트 공통)                                │
│ [shared_audio] ✓ (전투 BGM)                                     │
├─────────────────────────────────────────────────────────────────┤
│ 3단계: Feature 로드                                              │
│ [feature_battle] ← 전투 시스템                                  │
├─────────────────────────────────────────────────────────────────┤
│ 4단계: Content 로드 (파티원만)                                   │
│ [char_001_warrior] ← 전사                                       │
│ [char_002_mage] ← 마법사                                        │
│ [char_003_archer] ← 궁수                                        │
│ [weapon_sword_01] ← 전사 무기                                   │
│ [weapon_staff_01] ← 마법사 무기                                 │
│ [weapon_bow_01] ← 궁수 무기                                     │
├─────────────────────────────────────────────────────────────────┤
│ 5단계: Scene 로드 (현재 맵)                                      │
│ [scene_chapter1_forest] ← 숲 맵                                 │
└─────────────────────────────────────────────────────────────────┘

전투 종료 후:
- scene_chapter1_forest 언로드
- feature_battle 언로드
- Content (캐릭터, 무기)는 유지 (다음 전투에서 재사용)
- Shared, Core는 항상 유지
// 하이브리드 번들 매니저 public class HybridBundleManager { public enum Layer { Core, Shared, Feature, Content, Scene } private Dictionary<Layer, HashSet<string>> m_LayerBundles = new(); // 전투 씬 로드 예시 public IEnumerator LoadBattleScene( string sceneName, List<int> partyCharIds, List<int> weaponIds) { // 1. Shared 확인/로드 yield return EnsureLayerLoaded(Layer.Shared, new[] { "shared_characters", "shared_effects", "shared_audio" }); // 2. Feature 로드 yield return LoadBundle(Layer.Feature, "feature_battle"); // 3. Content 로드 (병렬) var contentTasks = new List<Coroutine>(); foreach (var charId in partyCharIds) { contentTasks.Add(StartCoroutine( LoadBundle(Layer.Content, $"char_{charId:D3}") )); } foreach (var weaponId in weaponIds) { contentTasks.Add(StartCoroutine( LoadBundle(Layer.Content, $"weapon_{weaponId:D3}") )); } foreach (var task in contentTasks) yield return task; // 4. Scene 로드 yield return LoadBundle(Layer.Scene, $"scene_{sceneName}"); } // 전투 종료 public void UnloadBattleScene() { // Scene, Feature만 언로드 (Content는 유지) UnloadLayer(Layer.Scene); UnloadLayer(Layer.Feature); // Shared, Core는 유지 } }

번들 설계 체크리스트

1. 초기 계획

  • [ ] 게임 장르와 특성 파악
  • [ ] 예상 콘텐츠 규모 (캐릭터 수, 맵 수, 아이템 수)
  • [ ] 타겟 플랫폼 (모바일/PC/콘솔) 메모리 제약
  • [ ] DLC/패치 빈도 예상

2. 전략 선택

  • [ ] 주 전략 결정 (씬/기능/콘텐츠 중 1개)
  • [ ] Shared 번들 범위 정의
  • [ ] 번들 네이밍 컨벤션 확립

3. 크기 가이드라인

  • [ ] 목표 번들 크기 설정 (모바일: 2~10MB)
  • [ ] 최대 번들 수 제한 (관리 가능한 수준)
  • [ ] 의존성 깊이 제한 (보통 3단계 이하)

4. 검증

  • [ ] 중복 에셋 검사 도구 구축
  • [ ] 순환 의존성 검사
  • [ ] 로딩 시간 프로파일링
  • [ ] 메모리 사용량 모니터링

핵심 정리

  • 번들 설계 원칙: 함께 쓰이고, 함께 바뀌는 에셋을 함께 묶기
  • 씬 기반: 맵 단위, 직관적, 레벨 기반 게임에 적합
  • 기능 기반: 시스템 단위, 모듈화, 라이브 서비스에 적합
  • 콘텐츠 기반: 캐릭터/아이템 단위, DLC 최적, 수집형 게임에 적합
  • 타입 기반: 에셋 타입 단위, Shared 번들로 주로 사용
  • 하이브리드: 실제 프로젝트는 여러 전략을 계층적으로 조합
  • 적절한 크기: 모바일 2~10MB, PC/콘솔 5~50MB 권장
