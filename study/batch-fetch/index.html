50개씩 vs 100개씩 - 최적의 배치 크기 찾기

Batch Fetch 튜닝 - 한 번에 몇 개씩 가져오는 게 좋을까?

Part 1. 왜 Batch로 가져와야 해?

인벤토리 아이템 200개를 불러와야 해. 어떻게 하지?

두 가지 방법이 있어:

1. 한 번에 200개 다 가져오기

2. 50개씩 4번 나눠 가져오기

한 번에 200개 다 가져오면 안 돼?

양이 적으면 괜찮아. 하지만...

❌ 한 번에 다 가져오기의 문제: 1. 메모리 부담 └─ 200개 아이템 × 500바이트 = 100KB 한번에 할당 2. 네트워크 패킷 크기 └─ 큰 패킷 하나 > 작은 패킷 여러 개 (MTU 초과 시 분할) 3. DB 락 점유 시간 └─ 200개 처리하는 동안 다른 요청 대기 4. 타임아웃 위험 └─ 데이터 많으면 처리 시간 증가 → 클라이언트 타임아웃

Part 2. Batch(배치)가 뭐야?

배치가 정확히 뭐야?

일정 개수씩 묶어서 처리하는 것.

📦 택배 비유: ❌ 비효율적: 물건 200개를 1개씩 200번 배송 → 배송비 200배, 시간 200배 ❌ 역시 비효율: 물건 200개를 한 트럭에 다 싣기 → 트럭 과적, 중간에 고장 위험 ✅ 효율적: 물건 50개씩 4대 트럭으로 배송 → 적정 용량, 빠른 배송, 안전
DB에서도 같은 원리야?

맞아. 적정 크기로 나눠서 가져오면

메모리, 네트워크, 락 점유 시간 모두 최적화돼.

Part 3. 현재 우리 코드는?

우리 서버에서는 어떻게 하고 있어?

인벤토리 로드를 보자.

// gp_LoadPCInventory 호출 구조 // 현재: 슬롯 범위를 지정해서 호출 void LoadInventory(i32CharSID) { // 0~49번 슬롯 CallProcedure("gp_LoadPCInventory", CharSID, 0, 49); // 50~99번 슬롯 CallProcedure("gp_LoadPCInventory", CharSID, 50, 99); // 100~149번 슬롯 CallProcedure("gp_LoadPCInventory", CharSID, 100, 149); // ... 계속 }
그럼 배치 크기가 50이네?

그래. 하지만 이 50이 최적인지는 모르는 거야.

Part 4. 최적 배치 크기 결정 요소

배치 크기를 어떻게 정해?

여러 요소를 고려해야 해:

요소 작은 배치 (20개) 큰 배치 (200개)
DB 호출 횟수 많음 (오버헤드 큼) 적음
메모리 사용 적음 많음
락 점유 시간 짧음 길음
네트워크 효율 패킷 오버헤드 큼 패킷당 데이터 많음
에러 복구 영향 범위 작음 영향 범위 큼
그럼 정답이 없는 거야?

일반적으로 50~200 사이가 적정.

데이터 크기, 네트워크 상황에 따라 조정.

Part 5. 배치 크기 계산 가이드

대략적인 기준이 있어?

네트워크 패킷 크기 기준으로 계산할 수 있어.

📐 배치 크기 계산: 목표 패킷 크기: 8KB~64KB (네트워크 효율 영역) 예: 인벤토리 아이템 1개 = 200바이트 최소 배치: 8,192 ÷ 200 ≈ 40개 최대 배치: 65,536 ÷ 200 ≈ 320개 💡 권장 범위: 50~200개
왜 8KB~64KB야?

네트워크 MTU(1500바이트)의 배수이면서,

TCP 윈도우 크기를 효율적으로 활용하는 범위야.

🌐 네트워크 효율: 너무 작은 패킷 (1KB): ├── 헤더 오버헤드 비율 높음 ├── TCP ACK 빈번 └── 실제 데이터 전송률 낮음 너무 큰 패킷 (1MB): ├── 메모리 버퍼 부담 ├── 분할/재조립 오버헤드 └── 재전송 시 비용 큼 적정 크기 (8KB~64KB): ├── 헤더 오버헤드 최소화 ├── TCP 효율적 전송 └── 빠른 응답 가능

Part 6. 동적 배치 크기 조절

상황에 따라 배치 크기를 바꿀 수도 있어?

고급 최적화로 적응형 배치 크기를 쓸 수 있어.

// 적응형 배치 크기 (개념 코드) int CalculateBatchSize(int totalItems, int itemSize) { // 목표: 16KB 패킷 const int TARGET_PACKET_SIZE = 16384; int batchSize = TARGET_PACKET_SIZE / itemSize; // 최소 20개, 최대 200개로 제한 batchSize = max(20, min(batchSize, 200)); // 전체 개수가 적으면 한 번에 if (totalItems <= batchSize) return totalItems; return batchSize; }
이렇게 하면 뭐가 좋아?

아이템 크기가 다른 테이블에서도 최적 성능.

예: 장비(500B)와 소비템(100B)이 다른 배치 크기.

Part 7. 최적 배치 크기 찾기 (테스트)

실제로 최적값을 어떻게 찾아?

배치 크기별로 테스트하고 측정해.

-- SQL Server에서 측정 SET STATISTICS IO ON SET STATISTICS TIME ON -- 배치 50 EXEC gp_LoadPCInventory @CharSID, 0, 49 -- 배치 100 EXEC gp_LoadPCInventory @CharSID, 0, 99 -- 배치 200 EXEC gp_LoadPCInventory @CharSID, 0, 199 -- 각각의 실행 시간, I/O 비교
📊 테스트 결과 예시: 배치 크기 | 총 호출 | 호출당 시간 | 전체 시간 ---------|--------|-----------|---------- 20 | 10회 | 3ms | 30ms + 오버헤드 50 | 4회 | 6ms | 24ms 100 | 2회 | 11ms | 22ms ← 최적 200 | 1회 | 25ms | 25ms (락 점유 ↑) 💡 이 경우 배치 100이 최적!

Part 8. 병렬 배치 처리

배치를 병렬로 처리할 수 있어?

가능하지만 우리 서버는 동기 호출이라 어려워.

다른 아키텍처에서는 효과적이야.

🔄 병렬 배치 (비동기 아키텍처): 순차 처리: Batch1 ─────→ Batch2 ─────→ Batch3 ─────→ 완료 50ms 50ms 50ms = 150ms 병렬 처리: Batch1 ─────→ ┐ Batch2 ─────→ ├──→ 완료 Batch3 ─────→ ┘ 50ms = 50ms ⚠️ 단, 동기 OLE DB 호출에서는 불가능 비동기 드라이버나 멀티스레드 필요
우리 서버에서는 어떻게 해?

싱글스레드 동기 호출이라 순차 처리만 가능.

대신 배치 크기 최적화에 집중해.

실전 가이드: 배치 크기 권장값

데이터 종류 레코드 크기 권장 배치
인벤토리 아이템 ~200B 50~100개
스킬 목록 ~100B 100~150개
퀘스트 정보 ~300B 40~80개
로그 기록 (INSERT) ~500B 30~50개
우편함 (텍스트 포함) ~1KB 15~30개

⚠️ 배치 튜닝 주의사항

1. 배치 크기 변경 시 테스트 필수 - 서버 환경마다 최적값 다름

2. INSERT/UPDATE는 더 작게 - 락 점유 시간 고려

3. 트랜잭션 범위 고려 - 배치 중간 실패 시 롤백 범위

4. 메모리 모니터링 - 큰 배치는 메모리 스파이크 유발

📝 핵심 정리

  • 배치 = 적정 개수씩 묶어서 처리 (한 번에 다 X, 하나씩 X)
  • 일반적인 최적 범위: 50~200개
  • 목표 패킷 크기: 8KB~64KB
  • 계산: (목표 패킷) ÷ (레코드 크기) = 배치 크기
  • 실제 테스트로 최적값 검증 필요
