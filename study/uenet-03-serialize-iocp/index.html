직렬화 & IOCP — 비트로 만들고, 한 줌의 스레드로 받는다

보낼 데이터를 어떻게 바이트로 만들고, 수천 연결을 어떻게 소수 스레드가 감당하나

30초 요약

직렬화 = 메모리 속 구조체(객체)를 네트워크로 보낼 '바이트 줄'로 펴는 것. 비트 팩킹으로 크기를 확 줄여.

IOCP = 윈도우의 '완료된 I/O만 큐에 올려주는' 방식. 소수 워커 스레드로 수천 연결을 감당.

우리 서버는 IOCP로 받고 직접 직렬화. UE는 비슷한 비동기 I/O 위에서 FArchive/NetSerialize로 직렬화.

Part 1. 직렬화 — 데이터를 어떻게 '비트'로?

구조체 { id, x, y, hp } 를 그대로 네트워크에 보낼 수 있어?

메모리 속 객체는 포인터·정렬·패딩이 섞여 있어서 그대로는 못 보내. '바이트 줄'로 펴야 해 — 이게 직렬화(serialization).

받는 쪽은 그 바이트를 다시 구조체로 복원(역직렬화)해.

그냥 통째로 보내면 되잖아?

크기가 문제야. 수천 명 × 초당 수십 번이면 1바이트도 아껴야 해.

hp가 0~100이면 32비트(4바이트) 정수로 보낼 필요 없어 — 7비트면 충분하거든. 좌표도 적당히 양자화(quantize)해서 줄여. 이게 비트 팩킹.

[그냥 보내면] id:4B x:4B y:4B hp:4B = 16바이트 [비트 팩킹] hp 0~100 → 7비트면 충분 좌표 → 양자화(소수점 버림) → 6바이트로 (62% 절감) 수천 명 × 60fps 면 이 차이가 대역폭을 좌우
💭 잠깐, 이런 생각 들지 않아?
JSON이나 Protobuf 쓰면 안 돼? 왜 직접 짜?
게임은 1바이트도 중요. JSON은 텍스트라 같은 데이터가 5~10배 큼. Protobuf는 좋은 옵션이고 일부 게임이 쓰지만(특히 gRPC 백엔드), 게임 트래픽은 비트 단위 패킹·고정 크기·결정적 직렬화가 더 중요해서 자체 형식이 흔해. 또 Protobuf도 결국 직렬화 라이브러리 — 비트 절감은 직접 설계해야 함.

Part 2. 받는 구조 — IOCP

연결이 수천 개인데 어떻게 다 받아?

워커 스레드 수를 바꿔보며 봐. 핵심은 — OS가 '완료된 I/O만' 큐에 올려주고, 소수 워커가 거기서 꺼내 처리해.

워커를 1개로 줄이면 부하 시 큐가 쌓이고(빨강), 늘리면 잘 비워. 그래도 '연결 수'만큼 스레드가 필요한 건 아니라는 게 포인트.

수천연결 수
0완료 큐 대기
2워커 스레드

Part 3. 왜 IOCP? — thread-per-connection의 함정

연결마다 스레드 하나 주면 안 돼?

1,000 연결 = 1,000 스레드면 메모리·문맥전환 비용이 폭발해. 대부분 스레드는 '데이터 올 때까지' 그냥 잠들어 있어 — 낭비야.

IOCP는 뒤집어. 연결은 수천이어도 '실제로 처리할 게 생긴 것만' 큐에 올리고, 소수 워커가 그것만 처리해. (Ch12의 액터≠스레드와 같은 사고방식)

리눅스는?

같은 발상의 epoll이 있어. '관심 있는 소켓들 중 준비된 것만 알려줘' 하는 방식. IOCP(윈도우) ↔ epoll(리눅스)은 사실상 같은 목적이야.

💭 잠깐, 이런 생각 들지 않아?
epoll이랑 IOCP 차이가 뭐야?
둘 다 "수많은 연결을 적은 스레드로" 푸는 도구. epoll(리눅스)은 "준비된 소켓만 알려줘"(레벨/엣지 트리거), IOCP(윈도우)는 "완료된 I/O를 큐에 올려놔"(완료 이벤트). 목적은 같지만 API 철학이 달라. epoll은 폴링 친화적, IOCP는 비동기 콜백 친화적. 게임은 어차피 매 틱 처리라 epoll 스타일이 더 자연스럽고 — 그래서 UE도 비슷하게 동작.
Node.js처럼 싱글스레드면 IOCP 같은 게 필요해?
응 — 싱글스레드여도 "I/O 대기에 묶이지 않기 위해" 비동기 I/O가 필수. Node.js도 내부적으로 libuv가 IOCP/epoll/kqueue를 씀. "스레드 수"가 아니라 "I/O를 어떻게 다루느냐"의 문제야. 만약 단일 스레드가 blocking I/O를 하면 그 동안 아무 일도 못 함.

Part 4. 우리 vs UE

항목조선협객전 (우리)언리얼
받는 구조IOCP (완료 포트)비동기 소켓 (플랫폼별)
직렬화구조체 + AddParamBinding 등 직접FArchive / NetSerialize
비트 절감구조체 설계로FVector_NetQuantize 등 내장
처리 흐름워커가 받아 단일 게임로직 스레드로NetDriver가 모아 틱에 처리
한 줄로?

받는 방식(소수 스레드로 다수 연결)도, 보내는 방식(바이트로 펴서 비트 아끼기)도 둘 다 비슷한 원리를 써. UE는 그걸 엔진이 추상화(FArchive·NetQuantize)했고, 우리는 직접 구조체로 다룬다는 게 차이야.

💭 잠깐, 이런 생각 들지 않아?
우리는 IOCP를 쓰는데, UE는 "비동기 소켓"? UE는 IOCP 안 써?
정확히는 — UE는 IOCP를 직접 쓰진 않아. UE의 ISocketSubsystem이 플랫폼 추상화를 거쳐서, Windows에서도 보통 non-blocking UDP + 매 틱 폴링(TickDispatch에서 들어온 패킷 일괄 처리)으로 동작해. 즉 "OS가 콜백으로 알려주는 IOCP" 방식이 아니라 "내가 매 틱 가서 가져오는" 방식.

왜 그렇게? 게임은 어차피 매 틱(예: 30Hz) 처리하니까 IOCP의 콜백 비동기성이 큰 이득이 안 돼. 우리는 TCP라 연결당 들어오는 시점이 제각각이라 IOCP의 "완료된 것만 알려줘"가 잘 맞고, UE는 UDP라 단순 폴링도 충분.
AddParamBinding이 뭐야? 못 들어봤어
우리 서버에서 DB 호출 시 매개변수를 바인딩하는 헬퍼야 — OLEDB로 프로시저 부를 때 SQL의 ? 자리에 메모리 값을 끼우는 도구. 직렬화의 한 형태인데 "네트워크 전송"이 아니라 "DB 호출 형식"으로 펴내는 거. UE의 FArchive가 "네트워크용 직렬화 헬퍼"라면, 우리 AddParamBinding은 "DB용 직렬화 헬퍼"인 셈. 둘 다 "메모리 구조 → 외부 형식"을 도와주는 도구.
"구조체 설계로 비트 절감"이라는데, 손으로 구조체만 짜서 어떻게 비트를 줄여?
필드 타입·순서를 직접 골라서. 예: int32 hp(4B) → uint8 hp(1B, 0~100이면 충분). 좌표를 그리드 셀 인덱스로 압축(2B → 1B). 자주 같이 변하는 필드끼리 묶어 한 패킷에 모으면 헤더 오버헤드 분담. UE는 FVector_NetQuantize 같은 내장 타입이 이걸 자동으로, 우리는 매번 손으로 설계 결정 — 그만큼 미세 제어는 가능하지만 손이 많이 가.

Part 5. 실제로는? (클래스)

UE에서 직렬화는 어떤 클래스?

FArchive가 직렬화의 기반이야 (<< 연산자로 읽기/쓰기 양방향). 네트워크 전용 최적화는 NetSerialize()를 오버라이드해서 직접 비트를 패킹해.

좌표는 FVector_NetQuantize / FVector_NetQuantize10 같은 타입으로 정밀도를 낮춰 비트를 아껴.

받는 쪽 엔진은?

UNetDriver가 소켓에서 데이터를 받아 연결(UNetConnection)별로 나누고, 그걸 다음 챕터에서 볼 Channel/Bunch로 푼다. 우리의 'IOCP 워커 → 게임로직 스레드'에 대응하는 자리야.

핵심 정리

  • 직렬화 = 구조체 → 바이트 줄. 비트 팩킹으로 크기 확 절감(hp 7비트, 좌표 양자화)
  • IOCP = '완료된 I/O만' 큐로. 소수 워커가 수천 연결 감당
  • thread-per-connection은 함정(1000 연결=1000 스레드 낭비) — 액터≠스레드와 같은 사고
  • 우리 = IOCP + 구조체 직접, UE = 비동기 I/O + FArchive/NetSerialize/NetQuantize
  • 받기(소수 스레드)·보내기(비트 절감) 둘 다 같은 원리, 추상화 수준만 다름

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 비트로 줄이면 멀리 있는 적이 미세하게 떨리는 거 아냐?

맞아, 그게 양자화 오차(quantization error)야. 좌표를 16비트로 줄이면 표현 가능한 위치가 듬성듬성해져 — 보내는 쪽과 받는 쪽이 같은 격자에 "스냅"되면서 미세하게 떨려 보일 수 있어.

실전 완화책:

  • 거리별 정밀도 차등: 가까운 액터는 32비트, 멀리는 16비트. FVector_NetQuantize10/100처럼 단계 선택.
  • 클라 보간으로 가리기: 받은 위치를 즉시 스냅하지 않고 부드럽게 보간해서 떨림을 흡수.
  • 눈에 띄는 임계까지만: 게임 카메라 거리·픽셀 해상도 기준으로 "이 이상은 사람이 못 알아채는 정밀도"까지만 줄여.
FPS는 조준선이 정밀해야 하니 그 축은 비트를 많이 주고, MMO처럼 멀리서 보는 적은 거칠게 줘도 안 보여. 정밀도는 게임 장르가 정해줘.
Q. 서버·클라 CPU가 다르면 직렬화가 깨지지 않아?

구조체를 그대로 memcpy해 보내면 두 가지 함정에 빠져:

  • 엔디언(byte order): x86은 little-endian, 일부 ARM·옛 PowerPC는 big-endian. int 0x12345678이 메모리에선 다르게 배치돼.
  • 패딩: 컴파일러가 정렬을 위해 구조체 사이에 빈 바이트를 넣어. 컴파일러·옵션마다 패딩이 달라.
[같은 구조체 다른 메모리] struct { uint8 a; uint32 b; } x86 (4B 정렬): [a][P][P][P] [b0][b1][b2][b3] ← 패딩 3바이트 팩킹 1: [a][b0][b1][b2][b3] ← 5바이트

해법: 필드 단위로 직접 쓰는 직렬화 코드(예: FArchive::Serialize)를 둬. 엔디언은 "네트워크 바이트 오더(big-endian)"로 통일하거나 명시적 변환을 박아. htonl/ntohl이 그래서 있는 거.

Q. IOCP 워커→게임로직 스레드 큐는 결국 락 아냐?

맞아, 그 경계엔 동기화가 필요해. 락이 아예 0은 아니야.

다만 어떻게 만드느냐가 핵심:

  • SPSC 락프리 큐(링버퍼): 생산자 1·소비자 1이면 메모리 배리어만으로 락 없이 안전. IOCP 워커→로직 1:1이면 이 패턴이 인기.
  • 짧은 락: 큐 push/pop 구간만 잠깐 잡고 즉시 풀어. 락 안에서 무거운 일을 안 하면 경합이 거의 없어.
  • 이중 버퍼링: 워커는 "쓰기 버퍼"에 쌓고, 로직 스레드가 틱마다 두 버퍼를 swap해서 한꺼번에 처리. 락이 1초당 수회로 줄어.
핵심: 큐에서 꺼낸 뒤의 게임 로직은 여전히 싱글스레드라 락이 0. 락은 "경계"에만 존재하고, 그것도 락프리·짧은 락·이중버퍼링으로 최소화해.
Q. 패킷을 중간에서 까보면(스니핑) 다 보이는 거 아냐?

응, 평문 UDP면 다 보여. Wireshark 같은 도구로 쉽게 볼 수 있어 — 자기 캐릭 위치는 물론 다른 사람 위치까지 다 노출.

대응:

  • TLS/DTLS를 얹어 암호화. UE도 옵션으로 패킷 핸들러에 암호화 컴포넌트를 끼울 수 있어.
  • 자체 암호화: 가벼운 XOR + 키 교환부터 AES-128까지 게임에 맞게. 무거우면 안 쓰니까 균형이 중요해.
  • "보이는 건 막지 않되 조작은 막는다": 핵심 판정·재화는 서버 권위라, 패킷을 봐도 조작할 수 없게. 보는 것 자체는 일부 정보 노출(맵핵)이지만 최소화 노력.
완벽한 비밀은 불가능. "다른 사람 위치"가 패킷에 있으면 누군가는 결국 본다(월핵). 그래서 진짜 방어는 안 보이는 적은 패킷에 안 싣는 것 — 가시성 컬링(Ch11). 암호화는 캐주얼 핵 방지·재화 보호용 기본기.
