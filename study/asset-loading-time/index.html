게임 시작에 5분 걸리는 이유

시작 시 모든 리소스 로딩의 문제점과 로딩 시간 분석 - 왜 이렇게 오래 걸리고 어떻게 줄일 수 있나

Part 1. 가장 단순한 로딩 방식

게임 시작할 때 왜 이렇게 오래 기다려야 해?

가장 단순한 에셋 로딩 방식은 게임 시작 시 모든 리소스를 한 번에 로딩하는 것이야.

이 방식은 구현이 쉽지만, 현대 게임에서는 치명적인 문제가 돼.

// 가장 단순하고 무식한 로딩 방식 void GameStart() { ShowLoadingScreen(); // 모든 것을 한 번에 로딩 LoadAllTextures(); // 4GB → 60초 LoadAllMeshes(); // 2GB → 30초 LoadAllAnimations(); // 1GB → 15초 LoadAllSounds(); // 1GB → 15초 LoadAllShaders(); // 컴파일 → 20초 LoadAllScripts(); // 초기화 → 10초 InitializeWorld(); // 레벨 생성 → 30초 HideLoadingScreen(); StartGame(); // 총 3분 후 시작! } // 장점: 한 번 로딩하면 플레이 중 끊김 없음 // 단점: 플레이어가 3분 동안 멍하니 기다려야 함
왜 이렇게 단순한 방식을 쓰는 거야?

이 방식에는 분명한 장점이 있어:

- 구현이 매우 단순: 복잡한 스트리밍 로직 불필요

- 메모리 관리 쉬움: 해제 타이밍 고민 안 해도 됨

- 플레이 중 로딩 없음: 한 번 시작하면 끊김 없이 플레이

- 디버깅 쉬움: 모든 에셋이 항상 메모리에 있음

시작 시 전체 로딩 방식:

┌─────────────────────────────────────────────────────────────────────┐
│                         게임 실행                                    │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  [게임 시작] ─────────────────────────────────────────▶ [플레이]    │
│       │                                                    │        │
│       ▼                                                    │        │
│  ┌─────────────────────────────────────────────────────┐   │        │
│  │              긴~~ 로딩 화면                          │   │        │
│  │                                                     │   │        │
│  │  텍스처 로딩... ████████████████████████████████    │   │        │
│  │  메시 로딩...   ████████████████████               │   │        │

│  │                                                     │   │        │

※ 현대 게임: 로딩 3~10분, 용량 50~150GB

Part 2. 로딩 시간의 구성 요소

로딩 시간은 정확히 어디서 소비되는 거야?

로딩 시간 = 디스크 읽기 + 압축 해제 + GPU 업로드 + 초기화

각 단계가 병목이 될 수 있어!

로딩 파이프라인 단계별 소요 시간:

┌──────────────────────────────────────────────────────────────────────┐
│   1. 디스크 읽기 (I/O Bound)                                         │
│   ─────────────────────────────────────────────────────────────────  │
│   HDD: 100~200 MB/s  → 10GB 읽기 = 50~100초                         │
│   SATA SSD: 500 MB/s → 10GB 읽기 = 20초                             │
│   NVMe SSD: 3500 MB/s → 10GB 읽기 = 3초                             │
│   PS5 SSD: 5500 MB/s → 10GB 읽기 = 2초                              │
└──────────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│   2. 압축 해제 (CPU Bound)                                           │
│   ─────────────────────────────────────────────────────────────────  │
│   LZ4: 4~5 GB/s (빠름, 압축률 낮음)                                  │
│   Zstd: 1~2 GB/s (밸런스)                                            │
│   LZMA: 100~300 MB/s (느림, 압축률 높음)                             │
│   Oodle Kraken: 2~4 GB/s (게임 최적화)                               │
└──────────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│   3. 데이터 가공 (CPU Bound)                                         │
│   ─────────────────────────────────────────────────────────────────  │
│   - 텍스처 포맷 변환 (DDS → GPU 포맷)                                │
│   - 메시 버텍스 버퍼 생성                                            │
│   - 애니메이션 커브 평가                                             │
│   - 셰이더 컴파일/링킹                                               │
└──────────────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌──────────────────────────────────────────────────────────────────────┐
│   4. GPU 업로드 (Transfer Bound)                                     │
│   ─────────────────────────────────────────────────────────────────  │
│   PCIe 3.0 x16: 15 GB/s                                              │
│   PCIe 4.0 x16: 32 GB/s                                              │
│   실제 유효 대역폭: 이론치의 50~70%                                   │
│   → 4GB 텍스처 업로드 = 0.3~0.5초                                   │
└──────────────────────────────────────────────────────────────────────┘
어느 단계가 제일 느린 거야?

보통 디스크 읽기가 가장 큰 병목이야. 특히 HDD에서!

NVMe SSD가 보급되면서 이제는 압축 해제와 초기화가 병목이 되기도 해.

// 로딩 시간 프로파일링 struct LoadingProfile { double diskReadTime; // 디스크에서 읽기 double decompressionTime; // 압축 해제 double processingTime; // 데이터 가공 double gpuUploadTime; // GPU로 전송 double initializationTime; // 객체 초기화 }; // 실제 측정 예시 (10GB 게임 데이터) LoadingProfile hddProfile = { .diskReadTime = 60.0, // 100 MB/s HDD .decompressionTime = 5.0, // Zstd 2 GB/s .processingTime = 10.0, // 포맷 변환 등 .gpuUploadTime = 2.0, // PCIe 전송 .initializationTime = 8.0, // 월드 빌드 등 // 총: 85초 → 디스크가 70% 차지! }; LoadingProfile nvmeProfile = { .diskReadTime = 3.0, // 3500 MB/s NVMe .decompressionTime = 5.0, // Zstd 2 GB/s .processingTime = 10.0, // 포맷 변환 등 .gpuUploadTime = 2.0, // PCIe 전송 .initializationTime = 8.0, // 월드 빌드 등 // 총: 28초 → 이제 처리 시간이 병목! };

Part 3. 디스크 I/O 병목 이해하기

HDD와 SSD는 뭐가 그렇게 다른 거야?

HDD는 물리적인 디스크와 헤드가 움직여야 해서 탐색 시간(Seek Time)이 발생해.

SSD는 전자적으로 접근해서 탐색 시간이 거의 없어!

HDD vs SSD 접근 패턴:

┌─────────────────────────────────────────────────────────────────────┐
│  HDD (Hard Disk Drive) - 기계식 저장장치                            │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│       [=====] ← 헤드가 물리적으로 이동                              │
│    ╭──────────╮                                                     │
│   │  ○ ○ ○ ○  │  ← 플래터(원판)가 회전                              │
│   │  ○ ○ ○ ○  │     7200 RPM = 초당 120회                          │
│    ╰──────────╯                                                     │
│                                                                     │
│   탐색 시간: 5~15ms (헤드 이동)                                     │
│   회전 지연: 평균 4ms (7200 RPM)                                    │
│   순차 읽기: 100~200 MB/s                                           │
│   랜덤 읽기: 0.5~2 MB/s ← ⚠️ 100배 느림!                            │
│                                                                     │
│   작은 파일 1000개 읽기:                                            │
│   1000 × (10ms 탐색 + 4ms 회전) = 14초!                            │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────────┐
│  SSD (Solid State Drive) - 전자식 저장장치                          │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│   ┌─────────────────────────────────────────┐                       │
│   │ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ │ ← NAND 플래시 칩      │
│   │ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ █ │   물리적 이동 없음    │
│   └─────────────────────────────────────────┘                       │
│                                                                     │
│   SATA SSD:                                                         │
│   - 탐색 시간: 0.1ms                                                │
│   - 순차 읽기: 500~550 MB/s (SATA 한계)                            │
│   - 랜덤 읽기: 50~100 MB/s                                          │
│                                                                     │
│   NVMe SSD:                                                         │
│   - 탐색 시간: 0.02ms                                               │
│   - 순차 읽기: 3000~7000 MB/s                                       │
│   - 랜덤 읽기: 500~1000 MB/s                                        │
│                                                                     │
│   작은 파일 1000개 읽기:                                            │
│   NVMe: 1000 × 0.02ms = 0.02초 (HDD의 1/700)                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
그럼 파일 구조가 로딩 속도에 영향을 미쳐?

맞아! 작은 파일 많음 vs 큰 파일 적음은 로딩 속도에 큰 차이를 만들어.

// 파일 구조가 로딩 속도에 미치는 영향 // 방식 1: 개별 파일 (나쁜 예) // textures/ // hero_diffuse.dds (4MB) // hero_normal.dds (4MB) // enemy_diffuse.dds (2MB) // ... 5000개 파일 // HDD에서 5000개 파일 열기: // 5000 × 10ms = 50초 (탐색만으로!) // 방식 2: 패킹된 아카이브 (좋은 예) // data/ // textures.pak (10GB, 단일 파일) // 1개 파일 열기 + 순차 읽기: // 0.01초 + 100초(HDD 순차) = 100초 class AssetArchive { public: // 아카이브 파일 구조 // [헤더][목차(TOC)][데이터1][데이터2]...[데이터N] struct ArchiveHeader { uint32_t magic; // 'PAK1' uint32_t version; uint32_t entryCount; uint64_t tocOffset; // 목차 위치 }; struct TOCEntry { uint64_t nameHash; // 파일명 해시 uint64_t offset; // 데이터 시작 위치 uint64_t compressedSize; uint64_t uncompressedSize; }; // 단일 파일 열기 → 목차 읽기 → 필요한 오프셋으로 점프 // 랜덤 접근 최소화! };

Part 4. 압축과 해제의 트레이드오프

파일을 압축하면 더 빨라져?

상황에 따라 달라! 디스크 속도 < CPU 해제 속도면 압축이 유리해.

압축의 트레이드오프:

HDD (100 MB/s)에서 10GB 로딩:
┌──────────────────────────────────────────────────────────────────────┐
│  무압축:                                                             │
│  - 디스크 읽기: 10GB ÷ 100 MB/s = 100초                             │
│  - 해제: 0초                                                         │
│  - 총: 100초                                                         │
│                                                                      │
│  Zstd 압축 (50% 압축률, 2 GB/s 해제):                               │
│  - 디스크 읽기: 5GB ÷ 100 MB/s = 50초                               │
│  - 해제: 10GB ÷ 2 GB/s = 5초                                        │
│  - 총: 55초 ✓ (45초 절약!)                                          │
│                                                                      │
│  LZMA 압축 (30% 압축률, 200 MB/s 해제):                             │
│  - 디스크 읽기: 3GB ÷ 100 MB/s = 30초                               │
│  - 해제: 10GB ÷ 200 MB/s = 50초                                     │
│  - 총: 80초 (압축률 좋지만 해제가 느림)                              │
└──────────────────────────────────────────────────────────────────────┘

NVMe SSD (3500 MB/s)에서 10GB 로딩:
┌──────────────────────────────────────────────────────────────────────┐
│  무압축:                                                             │
│  - 디스크 읽기: 10GB ÷ 3500 MB/s = 2.9초                            │
│  - 해제: 0초                                                         │
│  - 총: 2.9초 ✓                                                       │
│                                                                      │
│  Zstd 압축 (50% 압축률, 2 GB/s 해제):                               │
│  - 디스크 읽기: 5GB ÷ 3500 MB/s = 1.4초                             │
│  - 해제: 10GB ÷ 2 GB/s = 5초                                        │
│  - 총: 6.4초 (오히려 느림!)                                          │
│                                                                      │
│  LZ4 압축 (60% 압축률, 5 GB/s 해제):                                │
│  - 디스크 읽기: 6GB ÷ 3500 MB/s = 1.7초                             │
│  - 해제: 10GB ÷ 5 GB/s = 2초                                        │
│  - 총: 3.7초 (비슷하지만 용량 절약)                                  │
└──────────────────────────────────────────────────────────────────────┘

결론:
- HDD → 높은 압축률 선호 (Zstd, Oodle)
- NVMe SSD → 빠른 해제 선호 (LZ4) 또는 무압축
- 설치 용량이 중요하면 → 압축 필수
압축 알고리즘마다 뭐가 다른 거야?

각 알고리즘은 압축률과 속도 사이에서 다른 선택을 해.

// 게임에서 자주 쓰는 압축 알고리즘 비교 enum class CompressionType { LZ4, // 가장 빠른 해제, 낮은 압축률 LZ4_HC, // LZ4보다 느린 압축, 비슷한 해제, 더 나은 압축률 ZSTD, // 밸런스형, 레벨 조절 가능 LZMA, // 최고 압축률, 느린 해제 (7-Zip) OODLE_KRAKEN, // 게임 최적화, 빠른 해제 + 좋은 압축률 OODLE_LEVIATHAN,// Kraken보다 높은 압축률 }; // 벤치마크 (Silesia 코퍼스 기준) struct CompressionBenchmark { const char* name; float compressionRatio; // 원본 대비 % float compressSpeed; // MB/s float decompressSpeed; // MB/s }; CompressionBenchmark benchmarks[] = { { "LZ4", 47.6, 780, 4970 }, // 초고속 해제 { "LZ4 HC", 40.5, 110, 4970 }, // 더 나은 압축 { "Zstd (level 1)", 42.2, 515, 1850 }, // 빠른 모드 { "Zstd (level 9)", 36.4, 85, 1600 }, // 밸런스 { "Zstd (level 19)", 32.7, 5, 1400 }, // 최대 압축 { "LZMA", 30.0, 2, 270 }, // 최고 압축, 느림 { "Oodle Kraken", 35.1, 45, 3200 }, // 게임 최적! { "Oodle Leviathan",33.5, 25, 2900 }, // 더 높은 압축 }; // PS5, Xbox Series X|S는 하드웨어 Kraken 해제 지원 // → CPU 부담 없이 초고속 해제 가능!

Part 5. 셰이더 컴파일 지옥

셰이더 컴파일이 왜 그렇게 오래 걸려?

현대 게임은 수천 개의 셰이더 변형(Variant)이 있어. 각각 컴파일해야 해!

이게 바로 "최초 실행 시 셰이더 컴파일" 화면의 정체야.

셰이더 변형 폭발 문제:

기본 PBR 셰이더의 옵션들:
┌────────────────────────────────────────────────────────────────────┐
│  □ 노말맵 사용            (ON/OFF)  → 2가지                       │
│  □ 스페큘러맵 사용        (ON/OFF)  → 2가지                       │
│  □ 이미션맵 사용          (ON/OFF)  → 2가지                       │
│  □ AO맵 사용              (ON/OFF)  → 2가지                       │
│  □ 버텍스 컬러 사용       (ON/OFF)  → 2가지                       │
│  □ 스키닝 (본 수)         (0/4/8)   → 3가지                       │
│  □ 인스턴싱               (ON/OFF)  → 2가지                       │
│  □ 그림자 품질            (LOW/MED/HIGH/OFF) → 4가지              │
│  □ 포그 타입              (LINEAR/EXP/EXP2/NONE) → 4가지          │
│  □ 라이트 수              (1/2/4/8) → 4가지                       │
└────────────────────────────────────────────────────────────────────┘

총 변형 수: 2×2×2×2×2×3×2×4×4×4 = 12,288개!

각 변형을 컴파일하는 시간:
- DX11 HLSL → DXBC: 0.1초/개 × 12,288 = 20분
- DX12 HLSL → DXIL: 0.05초/개 × 12,288 = 10분
- Vulkan SPIR-V: 0.05초/개 × 12,288 = 10분

※ 이래서 게임 첫 실행 시 "셰이더 컴파일 중..." 표시가 나옴
※ 컴파일된 결과는 캐시에 저장 → 다음 실행부터 빠름
셰이더 컴파일을 빨리 할 방법은 없어?

여러 최적화 전략이 있어:

// 셰이더 컴파일 최적화 전략들 // 1. 사전 컴파일 (PSO 캐시) // 설치 시 또는 업데이트 시 미리 컴파일 void PrecompileShaders() { auto targetGPU = DetectGPU(); auto cacheFile = GetPSOCachePath(targetGPU); if (!FileExists(cacheFile)) { ShowProgress("Compiling shaders for your GPU..."); CompileAllVariants(cacheFile); // 오래 걸림 } } // 2. 지연 컴파일 (Lazy Compilation) // 실제로 필요할 때만 컴파일 class ShaderCache { std::unordered_map<ShaderKey, CompiledShader*> m_cache; CompiledShader* GetShader(const ShaderKey& key) { auto it = m_cache.find(key); if (it != m_cache.end()) { return it->second; } // 없으면 즉시 컴파일 (첫 사용 시 히칭 발생 가능) auto shader = CompileShader(key); m_cache[key] = shader; return shader; } }; // 3. 백그라운드 컴파일 // 로딩 중 또는 게임 중에 백그라운드 스레드에서 컴파일 void BackgroundShaderCompilation() { while (m_running) { ShaderKey key; if (m_compileQueue.TryPop(key)) { auto shader = CompileShader(key); m_cache.Insert(key, shader); } std::this_thread::sleep_for(1ms); } } // 4. 변형 수 줄이기 // Uber 셰이더: 모든 기능을 하나에 넣고 런타임에 분기 // if/else 대신 곱셈으로 기능 끄기 // color *= hasNormalMap ? normalMapColor : 1.0;

Part 6. 메모리 한계와 로딩

메모리가 로딩 시간에 어떻게 영향을 미쳐?

메모리가 부족하면 스왑(Swap)이 발생해서 엄청 느려져!

그래서 "모든 것을 로딩"하려면 충분한 메모리가 필수야.

메모리 부족 시 발생하는 일:

게임이 로딩하려는 양: 20GB
사용 가능한 RAM: 16GB

※ 스래싱(Thrashing): 스왑이 너무 잦아서 실제 작업보다
   스왑 I/O가 더 많은 상태 → 시스템 거의 멈춤
그럼 16GB RAM으로 100GB 게임을 어떻게 돌려?

바로 모든 것을 로딩하지 않는 것이 답이야!

이것이 스트리밍과 온디맨드 로딩이 필요한 이유야.

// 메모리 효율적인 로딩 전략 class SmartLoader { private: const size_t m_memoryBudget; // 사용 가능한 메모리 size_t m_currentUsage = 0; public: SmartLoader(size_t budget) : m_memoryBudget(budget) {} void LoadLevel(const Level& level) { // 1. 필수 에셋만 먼저 로딩 LoadEssentialAssets(level); // 플레이어, UI, 코어 셰이더 // 2. 시작 지점 주변만 로딩 auto spawnPos = level.GetSpawnPosition(); LoadAreaAssets(spawnPos, 100.0f); // 반경 100m // 3. 나머지는 백그라운드 스트리밍 m_streamingQueue.EnqueueSurroundingAreas(spawnPos); // 플레이 시작 가능! 나머지는 플레이 중 로딩 } void LoadAsset(const Asset& asset) { // 메모리 한도 체크 if (m_currentUsage + asset.size > m_memoryBudget) { // 오래된 에셋 해제 EvictLeastRecentlyUsed(asset.size); } // 이제 로딩 가능 DoLoadAsset(asset); m_currentUsage += asset.size; } };

PS5가 로딩이 엄청 빠른 이유는?

- CPU/GPU로 직접 스트리밍 (메모리 카피 최소화)

- I/O 코프로세서가 별도 처리

Part 8. DirectStorage와 미래

PC에서도 PS5처럼 빨라질 수 있어?

DirectStorage가 그 해답이야! GPU가 직접 SSD에서 읽고 압축 해제해.

// DirectStorage 개념 // 기존 방식: CPU가 모든 것을 중개 // SSD → CPU(압축해제) → RAM → CPU(복사) → VRAM // DirectStorage 방식: GPU가 직접 처리 // SSD → GPU(압축해제) → VRAM // CPU 개입 최소화! class DirectStorageLoader { public: void LoadTextureGPUDirect(const char* path, GPUTexture* dest) { // 1. GPU 메모리에 목적지 할당 ID3D12Resource* gpuBuffer = AllocateGPUMemory(dest->size); // 2. DirectStorage 요청 생성 DSTORAGE_REQUEST request = {}; request.Options.CompressionFormat = DSTORAGE_COMPRESSION_FORMAT_GDEFLATE; request.Options.SourceType = DSTORAGE_REQUEST_SOURCE_FILE; request.Source.File.Source = m_file; request.Source.File.Offset = fileOffset; request.Source.File.Size = compressedSize; request.Destination.Buffer.Resource = gpuBuffer; request.Destination.Buffer.Size = uncompressedSize; // 3. 큐에 제출 (비동기) m_queue->EnqueueRequest(&request); m_queue->Submit(); // 4. GPU가 알아서 처리 // - SSD에서 직접 읽기 // - GPU에서 GDeflate 압축 해제 // - VRAM에 바로 쓰기 // - CPU는 거의 개입하지 않음! } };
DirectStorage 성능 향상:

┌────────────────────────────────────────────────────────────────────┐
│  로딩 시나리오: 4K 텍스처 100장 (4GB, 압축 시 1GB)                 │
├────────────────────────────────────────────────────────────────────┤
│                                                                    │
│  기존 방식 (Win32 API):                                            │
│  ├── SSD 읽기: 1GB ÷ 3.5GB/s = 0.29초                             │
│  ├── CPU 압축 해제: 4GB ÷ 2GB/s = 2초                             │
│  ├── RAM → VRAM 복사: 4GB ÷ 10GB/s = 0.4초                        │
│  └── 총: 약 2.7초                                                  │
│                                                                    │
│  DirectStorage + GPU 압축 해제:                                    │

│  ├── GPU 압축 해제: 4GB ÷ 24GB/s = 0.17초                         │
│  ├── 메모리 복사: 없음 (직접 VRAM에 쓰기)                          │
│  └── 총: 약 0.3초                                                  │
│                                                                    │
│  * NVMe SSD + PCIe 4.0 기준                                        │
│                                                                    │

│                                                                    │
└────────────────────────────────────────────────────────────────────┘

- Windows 11

- 게임이 DirectStorage API 사용

📁 파일 구조 최적화

🎯 선택적 로딩

// 병렬 로딩 파이프라인 class ParallelLoadingPipeline { private: ThreadSafeQueue<FileReadJob> m_readQueue; ThreadSafeQueue<DecompressJob> m_decompressQueue; ThreadSafeQueue<ProcessJob> m_processQueue; ThreadSafeQueue<UploadJob> m_uploadQueue; // 각 단계를 별도 스레드(들)가 처리 std::vector<std::thread> m_ioThreads; // 파일 읽기 std::vector<std::thread> m_decompressThreads; // 압축 해제 std::vector<std::thread> m_processThreads; // 데이터 가공 std::thread m_uploadThread; // GPU 업로드 public: void Initialize() { // I/O 스레드: 보통 1~2개 (디스크 수) for (int i = 0; i < 2; i++) { m_ioThreads.emplace_back([this]() { IOThreadFunc(); }); } // 압축 해제: CPU 코어 수에 비례 int decompressThreads = std::thread::hardware_concurrency() - 2; for (int i = 0; i < decompressThreads; i++) { m_decompressThreads.emplace_back([this]() { DecompressThreadFunc(); }); } // 처리 스레드: 남은 코어 m_processThreads.emplace_back([this]() { ProcessThreadFunc(); }); // GPU 업로드: 단일 스레드 (GPU 명령 직렬화) m_uploadThread = std::thread([this]() { UploadThreadFunc(); }); } // 결과: 모든 단계가 동시에 진행! // 파일 A 읽는 동안, 파일 B 압축 해제, 파일 C 처리, 파일 D 업로드 };

   □ 대화/이벤트 중 백그라운드 로딩

   □ 첫 프레임 빨리 보여주기 (저품질이라도)

// 체감 로딩 시간 최적화 class PerceivedLoadingOptimizer { public: // 1. 점진적 로딩 (Progressive Loading) // 저품질 먼저 → 고품질 나중 void LoadTextureProgressive(const char* path) { // 64x64 썸네일 먼저 (0.01초) LoadAndDisplay(path, MIP_LEVEL_6); // 즉시 뭔가 보임! // 256x256 로딩 (0.1초) LoadAndUpgrade(path, MIP_LEVEL_4); // 1024x1024 로딩 (0.5초) LoadAndUpgrade(path, MIP_LEVEL_2); // 전체 4K 로딩 (2초) LoadAndUpgrade(path, MIP_LEVEL_0); } // 2. 프로그레스바 트릭 float AdjustProgressForPerception(float actualProgress) { // 처음 50% → 화면에 80% 표시 (빠르게 느껴짐) // 마지막 50% → 화면에 20% 표시 // 실제로는 일정하게 로딩되지만, 체감상 빨라 보임 if (actualProgress < 0.5f) { return actualProgress * 1.6f; // 0~0.5 → 0~0.8 } else { return 0.8f + (actualProgress - 0.5f) * 0.4f; // 0.5~1 → 0.8~1 } } };

핵심 정리

  • 로딩 시간 = 디스크 읽기 + 압축 해제 + 처리 + GPU 업로드
  • HDD는 탐색 시간이 병목, NVMe는 처리가 병목
  • 파일 패킹으로 랜덤 접근 최소화 (HDD에서 중요)
  • 압축은 디스크 < CPU일 때만 이득
  • 셰이더 컴파일은 PSO 캐시로 최적화
  • 메모리 부족 → 스왑 → 10배 느림
  • DirectStorage: GPU가 직접 SSD에서 읽고 압축 해제
  • 병렬 파이프라인으로 모든 단계 동시 진행
  • 체감 시간 줄이기: 점진적 로딩, 진행 피드백, 흥미 콘텐츠
  • 궁극의 해결책: 필요한 것만 필요할 때 로딩 (스트리밍)
