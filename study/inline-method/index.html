Refactoring #12

Inline Method

메서드 인라인 - 불필요한 간접 계층 제거

인라인이 뭐예요? 메서드를 왜 없애야 하죠?
메서드의 본문을 호출하는 곳에 직접 넣고, 그 메서드를 삭제하는 거예요. Extract Method의 정반대 기법이죠.

왜 필요할까요? 때로는 메서드가 오히려 코드를 복잡하게 만들어요.

예를 들어, 딱 한 줄짜리 메서드인데 이름이 본문만큼이나 명확하지 않다면? 그냥 본문을 직접 쓰는 게 더 읽기 쉬워요.
언제 메서드를 인라인해야 하나요?
다음 경우들을 보세요:

1. 메서드 본문이 이름만큼 명확할 때
IsEmpty()가 단순히 count == 0을 반환한다면? 문맥에 따라 그냥 count == 0을 쓰는 게 나을 수도 있어요.

2. 위임만 하는 메서드
다른 메서드를 그냥 호출만 하고 끝나는 메서드. 중간 계층이 의미 없이 늘어난 거예요.

3. 리팩토링 과정에서
여러 작은 메서드들을 정리하고 다시 재구성할 때, 일단 인라인해서 전체 그림을 본 뒤 다시 추출하기도 해요.

🎭 비유: 불필요한 중간 관리자

부장에게 보고 → 부장이 그대로 팀장에게 전달 → 팀장이 처리
부장이 아무것도 안 하고 그냥 전달만 한다면? 직접 팀장에게 가는 게 빨라요.

메서드도 마찬가지. 가치 없는 중간 계층은 제거하세요.
그런데 Extract Method가 좋다고 했잖아요. 왜 거꾸로 인라인해요?
둘 다 도구예요. 상황에 맞게 쓰는 거죠.

Extract Method가 좋은 경우:
- 코드 블록에 "이름"을 붙여 의도를 드러낼 때
- 같은 로직이 여러 곳에서 쓰일 때
- 복잡한 로직을 단계별로 나눌 때

Inline Method가 좋은 경우:
- 메서드가 너무 잘게 쪼개져서 흐름 파악이 어려울 때
- 이름보다 본문이 더 명확할 때
- 한 곳에서만 쓰이는 사소한 메서드일 때

⚠️ 균형의 기술

"추출이 항상 좋다"도, "인라인이 항상 좋다"도 틀린 말이에요.

기준은 가독성입니다. "이 코드를 처음 보는 동료가 더 쉽게 이해할 수 있는 형태는?"
인라인하면 안 되는 경우는요?
절대 인라인하면 안 되는 경우가 있어요:

1. 여러 곳에서 호출되는 메서드
3군데에서 쓰이는 메서드를 인라인하면? 같은 코드가 3번 복사되죠. 나중에 수정할 때 3곳 다 바꿔야 해요.

2. 재귀 메서드
자기 자신을 호출하는 메서드는 인라인 불가능.

3. 복잡한 로직을 담은 메서드
10줄짜리 복잡한 계산 로직을 인라인하면? 호출하는 쪽 코드가 엉망이 돼요.

4. 의미 있는 추상화
CalculateDamage()처럼 중요한 개념을 담은 메서드는 유지하세요.
실제로 어떻게 진행하나요?
단계별 진행:

1단계: 호출 위치 확인
이 메서드를 호출하는 곳이 몇 군데인지 파악

2단계: 각 호출부에 본문 복사
메서드 본문을 호출하는 곳에 붙여넣기 (파라미터가 있다면 적절히 치환)

3단계: 테스트
동작이 동일한지 확인

4단계: 메서드 삭제
원래 메서드 제거

💡 IDE 활용

대부분의 IDE에서 "Inline Method" 기능을 제공해요.

Visual Studio: Ctrl+R, Ctrl+I
자동으로 모든 호출부를 찾아서 치환해줍니다.

📌 Inline Method 핵심 정리

  • 메서드 본문을 호출부에 직접 넣고 메서드 삭제
  • 이름보다 본문이 명확할 때 사용
  • 가치 없는 중간 계층 제거가 목적
  • 여러 곳에서 호출되는 메서드는 인라인하지 않음
  • Extract Method와 상황에 맞게 균형 있게 사용
