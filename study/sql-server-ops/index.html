넥슨 게임DB팀 NDC 발표 - 실무 협업 노하우

Part 1. 게임 DB의 두 가지 성격

게임 서비스에서 DB는 어떻게 구분돼?

크게 게임 DB와 로그 DB로 나눠.

구분 게임 DB 로그 DB
용도 실시간 요청 처리 기록 저장/분석
성능 고성능 필수 상대적으로 낮아도 OK
용량 작게 유지 크고 계속 증가
장애 영향 서비스 중단 분석 지연 정도
데이터 증가 vs 동접자 증가, 뭐가 더 중요해?

동접자 증가가 훨씬 위험해!

데이터가 1테라인데 동접 100명이면? 실제 처리하는 건 기가 단위야.

근데 동접자가 늘면? 요청량 자체가 폭증하고, 액티브 데이터도 커져.

창고 vs 매장 비유

데이터 증가 = 창고에 물건 쌓임 (찾는 건 당장 쓸 것만)
동접자 증가 = 매장에 손님 폭주 (전부 당장 서비스해야 함!)

손님이 많으면 창고도 더 자주 뒤져야 해 → 전체적으로 힘들어짐

Part 2. 액티브 데이터와 메모리 관계

DB 서버의 병목은 어디서 생겨?

일반적으로 CPU - 메모리 - 디스크 구조야.

유저가 요청한 데이터를 액티브 데이터라고 부르는데...

액티브 데이터 < 메모리 용량 → 메모리에서 바로 처리 (빠름!) 액티브 데이터 > 메모리 용량 → 디스크에서 읽어와야 함 (느림!) → 캐시 히트율 떨어짐 → 전체 성능 저하
그러면 메모리만 늘리면 해결이야?

기본적으로는 그래. 메모리 늘려서 캐시 히트율을 높이는 게 핵심이야.

근데 메모리 더 못 늘리면? 그때 디스크를 빠른 걸로 교체하거나 분산해야지.

일반적인 게임 DB 특성

CPU 사용률은 보통 20~30% 수준
→ CPU보다는 메모리와 디스크 I/O가 병목 포인트!

Part 3. DB 간 연관관계는 끊어라

게임 DB랑 마켓 DB 데이터를 조인해서 보여주고 싶어

나중에 큰 문제가 될 수 있어!

나쁜 예: DB 간 조인 게임DB와 마켓DB를 Linked Server로 연결해서 조인 → 성능 한계 (초당 3,000~4,000건) → 분산 트랜잭션 발생 → 나중에 스케일아웃 불가능!
그러면 어떻게 해야 돼?

연관관계를 끊는 방법을 써!

좋은 예: 연관관계 제거 방법 1: 순차 조회 1. 게임 DB에서 유저 데이터 조회 2. 그 결과로 마켓 DB에서 추가 조회 3. 애플리케이션에서 합쳐서 표시 방법 2: 데이터 복제 마켓 DB의 변경 데이터를 게임 DB에도 반영 → 조인 없이 게임 DB만으로 처리
왜 이렇게까지 해야 하나?

DB 장비는 스케일업(좋은 장비로 교체)은 쉽지만,
스케일아웃(분산)은 매우 어려워.

연관관계가 모두 끊어져 있으면 → 장비별로 분산 가능!
개발 코드에서는 커넥션 스트링만 바꾸면 분산 완료.

Part 4. 데이터 유실 1초, 허용할 수 있어?

DB가 갑자기 죽으면 마지막 1초 데이터가 날아갈 수 있대. 괜찮아?

이건 서비스 성격에 따라 달라. 하지만 성능 5배 향상을 얻을 수 있어!

Delayed Durability (지연 영속성) 일반 모드: 데이터 변경 → 로그에 기록 → 디스크에 즉시 반영 (안전하지만 느림) 지연 모드: 데이터 변경 → 로그에 기록 → 캐시에 모아둠 → 나중에 디스크 반영 (빠름!) 트레이드오프: 300ms~1초 내 장애 시 데이터 유실 가능
게임에서 써도 될까?

게임 서비스는 성능이 매우 중요해서 이미 캐시를 많이 써.

1초 정도 유실은 보통 크게 문제 안 됐어.

개발자-DBA 협업 포인트

"데이터 유실 허용 범위"를 협의해야 해!

예시: 레어 아이템 획득은 즉시 반영, 일반 아이템은 지연 처리
→ 쿼리별로 다르게 적용 가능 (하지만 관리 복잡)
유실 대비책

로그 DB에도 같이 기록해두면 → 나중에 복구 작업 가능!

Part 5. 대량 데이터는 나눠서 처리해라

크리스마스 이벤트로 접속한 10만 명한테 산타모자 지급해야 해

한 번에 처리하면 DB가 멈칫해!

나쁜 예: 한 번에 10만 건 INSERT → 트랜잭션 커짐 → 순간적 지연 발생 → 다른 유저 영향 좋은 예: 500건씩 나눠서 처리 10만명 / 500건 = 200회 반복 → 안정적으로 분산 처리 (약 200초 소요)
왜 500건이야?

DB 묶음 처리 단위가 커지면 지연이 생길 수 있어.

일반적으로 1,000건 이하가 안전해. 500건은 여유 있는 수치야.

이벤트 지급 패턴
  • 접속 시 지급 - 유저가 접속할 때마다 아이템 지급 → 자연스럽게 분산
  • 정시 지급 - 3시 정각에 접속 중인 10만 명 지급 → 500건씩 배치로 처리

Part 6. 압축은 무조건 쓰자

SQL Server 압축 기능, 장단점이 뭐야?

거의 장점만 있어!

항목 효과
CPU 사용 약 15% 증가 (게임 DB는 원래 CPU 여유 있음)
데이터 크기 대폭 감소
캐시 히트율 향상 (메모리에 더 많이 올림)
디스크 I/O 감소
비용 더 작은 장비로 가능
압축 적용 시간 (100GB 기준): 약 2~3시간 (장비 성능에 따라 다름) 팁: 로그 테이블처럼 매일 새로 생성되는 경우 → 기존 데이터 말고 새 테이블에만 압축 옵션 걸기 → 시간 지나면서 자연스럽게 전체 압축 완료!
권장

처음 DB 스펙 산정할 때부터 압축 한다고 가정하고 설계하자!

Part 7. 주요 테이블은 신중하게

게임에서 주요 테이블이 뭐야?

캐릭터, 아이템, 퀘스트, 스킬 같은 테이블이야.

이런 테이블은 요청도 많고 데이터도 많이 쌓여.

나중에 바꾸기 거의 불가능한 것들

Clustered Index 변경
→ 똑같은 크기만큼 디스크 필요 + 전체 데이터 재처리
→ 테이블이 커지면 사실상 불가능

Primary Key 변경
→ 연관된 모든 테이블의 FK까지 같이 바꿔야 함
→ 거의 대부분의 테이블을 손봐야 할 수도
INT형 vs BIGINT형, 뭘 써야 해?

INT는 21억까지야. 아이템 같은 건 생각보다 빨리 찰 수 있어.

처음부터 BIGINT 쓰는 게 안전해! (4바이트 더 드는 정도)

순차 증가 컬럼에 인덱스 걸면 안 돼?

아이템 번호나 ModifyDate 같은 순차 증가 컬럼에 인덱스 걸면...

핫스팟(Hot Spot) 발생! 한 곳에 요청이 몰려.

핫스팟 문제: ModifyDate가 항상 현재 시간으로 업데이트 → 인덱스의 맨 끝에만 모든 변경 집중 → 아무리 좋은 장비도 초당 8,000~20,000건이 한계 해결: 분산 처리 구조 필요 (별도 세션 주제)

Part 8. 로그 DB는 게임 DB와 분리해라

게임 DB 프로시저 안에서 로그도 같이 쌓으면 편하잖아?

절대 안 돼!

로그 DB 지연 → 게임 DB 쿼리도 지연 → 게임 서비스 장애!

나쁜 구조: 게임 DB SP 안에서 → 로그 DB INSERT → 로그 DB 장애가 게임 장애로 전파! 좋은 구조: 게임 서버 → 게임 DB (게임 로직만) 게임 서버 → 로그 DB (별도 처리) → 로그 DB 문제가 게임에 영향 X
개발자-DBA 협업 포인트

로그 기록을 어떻게 할지 협의가 필요해!

예시: 먼저 파일/Redis에 기록 → 5분마다 DB에 적재
→ "5분 이내 데이터는 조회 안 될 수 있다"는 합의 필요
로그 테이블 관리 팁
  • 파티션 테이블 사용 - 오래된 파티션은 DROP으로 빠르게 삭제
  • 수동 구현 - 날짜별 테이블 생성 → 뷰로 묶어서 사용 → 오래된 테이블 DROP
  • 압축 적극 활용 - 로그는 비슷한 데이터가 많아서 압축 효과 좋음

Part 9. 장애 복구 시간, 목표를 정해라

장애 나면 "최대한 빨리 복구해주세요"라고 하면 되는 거 아냐?

그러면 계획을 세울 수가 없어!

명확한 수치가 있어야 판단하고 훈련할 수 있어.

장애 복구 시간 구성 예시: DB 장애 조치: 10분 개발팀 작업: 5분 QA 검증: 2시간 (검증이 오래 걸림!) → 전체 유저 체감 장애 시간은 이보다 더 길 수 있음
게임 서버가 DB 오류 나면 어떻게 해야 해?

많은 게임 서버가 DB 오류 시 의도적으로 크래시시키더라.

리트라이 하다가 데이터 불일치 나면 더 큰 문제니까...

리트라이를 넣으면?

DB가 30초 만에 복구되면 → 대부분 유저는 지연 못 느끼고 플레이 계속!
크래시 시키면 → 장애 프로세스 시작 → 최소 1~2시간 소요
리트라이 구현 위치: 게임 서버 내 DB 함수 영역에 리트라이 로직 → 각 비즈니스 로직에는 영향 없이 처리 가능 클라우드 환경에서는 더 중요! → 자동 장애 조치 제공하는 서비스들이 많음 → 리트라이만 있으면 서비스 가용성 크게 향상

Part 10. 저장 프로시저 vs 쿼리 직접 실행

쿼리를 게임 서버에 직접 넣으면 안 돼?

가능은 하지만, 저장 프로시저가 운영에 유리해!

상황 저장 프로시저 쿼리 직접
쿼리 문제 발생 시 즉시 수정 가능 빌드/배포/점검 필요
DB 업그레이드 호환성 미리 검증 가능 실행 전까지 모름
쿼리 플랜 문제 DBA가 바로 확인 가능 개발자 연락 필요
게임 서버에서 DB 로그도 남겨야 해?

네트워크 문제는 DB 로그에 안 남아!

게임 서버에서도 DB 관련 로그를 남기면 문제 지점 찾기 쉬워.

DB 오류 로그에 포함할 것
  • 시간 - 최소 초 단위, 가능하면 밀리초까지
  • 쿼리/SP명 - 어떤 쿼리가 문제였는지
  • 파라미터 - 특정 값일 때만 느려지는 경우 있음
  • 호출 함수명 - 어디서 요청했는지
  • 수행 시간 - DB에서 0.1초인데 애플리케이션에서 3초면 네트워크 문제
  • 오류 메시지 - DB가 반환한 에러

Part 11. 기타 운영 팁

SQL Server 버전은 언제 올려야 해?

DBA가 버전 올리자고 하면 개발자가 부담스러워하는 경우가 많아.

근데 쿼리 부분은 거의 안 바뀌어! 안심해도 돼.

SQL Server 안정성: - 20년간 쿼리 플랜 방식 변경 딱 1번 (2014년) - 그때도 호환성 플래그로 끄고 켤 수 있었음 - 버그 픽스 받으려면 기술지원 기간 내 버전 필요 참고: 2012 이하는 메인스트림 지원 종료 → 버그 발생 시 해결 방법 없을 수 있음
글로벌 서비스 할 수도 있으면?

처음부터 유니코드(nvarchar) 쓰세요!

나중에 바꾸려면 DB만 아니라 개발 코드 전체를 손봐야 해.

아이템 정보 같은 메타데이터는 어디서 관리해?

보통 파일로 관리하는데, DB에도 같이 넣어두면 좋아!

운영툴, 분석 시스템 등 연결된 시스템에서도 필요하거든.

실시간 랭킹은 어떻게 해?

SQL Server에서 배치로 계산해도 되지만...

Redis 같은 인메모리 DB를 쓰면 진짜 실시간으로 가능해!

메이플에서 "이 월드에서 몇 등입니다" 같은 기능도 Redis로 구현.

핵심 정리: 개발자-DBA 협업 포인트

  • 게임 DB vs 로그 DB - 성격이 다르므로 완전히 분리 설계
  • 동접자 증가 - 데이터 증가보다 훨씬 위험, 미리 대비
  • DB 간 연관관계 - 처음부터 끊어서 스케일아웃 가능하게
  • 지연 영속성 - 성능 5배 향상, 1초 유실 허용 협의 필요
  • 대량 처리 - 500건씩 나눠서 처리, 한 번에 하면 멈춤
  • 압축 - CPU 여유 있으면 무조건 적용, 장점만 있음
  • 장애 복구 - 명확한 시간 목표 설정, 리트라이 구현
  • 저장 프로시저 - 운영 시 즉각 대응 가능, 권장
