의도를 드러내는 이름

이름이 곧 문서다 - 주석 없이도 이해되는 코드

Part 1. 왜 이름이 중요해?

변수 이름이 뭐가 그렇게 중요해?

코드 읽는 시간의 70%가 "이해"하는 데 쓰여.

좋은 이름은 그 시간을 확 줄여줘.

지도 비유

지명이 "A구역", "B구역", "C구역"인 지도 vs
"서울역", "명동", "강남역"인 지도

어떤 게 찾기 쉬워? 의미있는 이름이 있어야 탐색이 쉬워.
주석 달면 되잖아?

주석은 거짓말할 수 있어.

코드는 바꿨는데 주석 안 바꾸면? 혼란만 가중.

// 유저 레벨을 체크한다 ← 거짓말! 실제론 HP 체크 if (user->hp > 100) { ... }
좋은 이름의 효과

✅ 주석 없이도 코드가 설명됨
✅ 거짓 주석 문제 없음
✅ 검색이 쉬움 (Ctrl+F)
✅ 코드 리뷰가 빨라짐

Part 2. 헝가리안 표기법, 쓰면 안 돼?

우리 프로젝트에 i32, dw, m_ 이런 거 많던데?

그게 헝가리안 표기법이야.

타입을 접두사로 붙이는 오래된 방식.

// 실제 프로젝트 예시 struct _PROCEDURE_LOAD_CHARACTER_PARAM { int out_iResult; // i = int INT32 m_i32OsType; // m_ = member, i32 = int32 DWORD m_dwAccunique; // dw = DWORD BYTE m_bBujeogAuto; // b = BYTE WCHAR m_munpaName[32]; // 얘는 접두사 없네? }; // 질문: m_i32OsType이 뭔지 알겠어? // "int32 타입의 멤버 변수"... 근데 뭘 담는 건데?

헝가리안 표기법 논쟁

찬성: 타입이 바로 보임, IDE 없던 시절엔 유용했음

반대: 현대 IDE가 타입 보여줌, 의미가 안 보임, 리팩토링 시 이름도 바꿔야 함

그럼 어떻게 바꿔?

타입 대신 의미를 담아.

헝가리안 의미있는 이름 개선점
m_i32OsType osType OS 타입이라는 게 명확
m_dwAccunique accountId 계정 ID라는 게 명확
m_bBujeogAuto isAutoBujeog bool이고 자동 부적인지
m_dwPK_Score pkScore PK 점수라는 게 명확
레거시 코드에서의 현실적 조언

기존 코드를 한번에 다 바꿀 순 없어.
새로 만드는 코드부터 의미있는 이름 쓰고,
기존 코드는 건드릴 때마다 조금씩 개선해.

Part 3. 좋은 이름의 4가지 조건

좋은 이름은 어떻게 만들어?

4가지 조건을 체크해봐:

// 조건 1: 의도를 드러낸다 int d; // d가 뭐야? int elapsedDays; // 경과 일수! // 조건 2: 발음할 수 있다 int ymdhms; // 읽을 수가 없어 int timestamp; // "타임스탬프" // 조건 3: 검색할 수 있다 if (status == 4) // 4가 뭐야? 검색해도 4만 나옴 if (status == STATUS_DEAD) // "STATUS_DEAD" 검색 가능! // 조건 4: 한 개념에 한 단어 GetPlayer() / FetchUser() / RetrieveCharacter() // 다 같은 건데 다른 이름 GetPlayer() / GetUser() / GetCharacter() // 일관되게 Get 사용
이름이 너무 길어지면?

길어도 명확한 게 낫다.

자동완성 있잖아!

// 길이 vs 명확성 int pdc; // 2글자, 의미 모름 int partyDungeonClearCount; // 22글자, 의미 명확! // 타이핑? 자동완성이 해결해줌 // "par" 치면 partyDungeonClearCount 자동완성

Part 4. 함수 이름은 동사로

함수 이름은 어떻게?

함수는 "행동"이니까 동사로 시작해.

// 함수 이름 패턴 // 동사 + 명사 SaveCharacter() // 캐릭터를 저장 LoadInventory() // 인벤토리를 로드 CalculateDamage() // 데미지를 계산 // bool 반환은 is/has/can IsPlayerDead() // 죽었는지? HasEnoughMoney() // 돈 충분한지? CanEnterDungeon() // 던전 입장 가능한지? // 생성/변환 CreateParty() // 파티 생성 ToJson() // JSON으로 변환
피해야 할 함수 이름

❌ Do() - 뭘 하는데?
❌ Process() - 어떤 처리?
❌ Handle() - 뭘 핸들?
❌ Manager() - 관리한다는 건 알겠는데...

이런 이름은 구체적인 동작으로 바꿔야 해.
// 모호한 이름 → 구체적인 이름 void ProcessData(); void ParsePacketAndUpdateState(); // 패킷 파싱하고 상태 업데이트 void HandleMessage(); void RouteMessageToHandler(); // 메시지를 핸들러로 라우팅 void DoTask(); void ExecuteScheduledSave(); // 예약된 저장 실행

Part 5. 실제 프로젝트에 적용

우리 프로젝트 코드를 실제로 바꿔보면?

Procedure_LoadCharacter.h를 예로 들어볼게:

// Before: 헝가리안 + 의미 불명확 struct _PROCEDURE_LOAD_CHARACTER_PARAM { int out_iResult; INT32 m_i32OsType; DWORD m_dwAccunique; DWORD m_dwPK_Score; int m_iPK_Kill; int m_iPK_Death; INT32 _i32PKCooltime; int m_iUpdateFlag; };
// After: 의도가 드러나는 이름 struct CharacterLoadParams { DBResult result; // 명확한 타입 OSType osType; // enum class AccountID accountId; // 전용 타입 // PK 관련은 묶음 struct PKStats { int score; int kills; int deaths; int cooldownSeconds; } pkStats; CharacterUpdateFlags updateFlags; // 비트 플래그용 타입 };
변경 효과

✅ 타입 정보 → 컴파일러가 체크
✅ 관련 데이터 → 구조체로 묶음
✅ 접두사 제거 → 의미가 직접 보임
✅ 주석 필요 없음 → 이름이 문서

Part 6. 레거시에서 점진적 적용

기존 코드 전부 바꾸긴 힘든데?

맞아. 보이스카웃 규칙 적용해.

// 1. 새 코드는 좋은 이름으로 int partyMemberCount = GetPartyMemberCount(); // 새로 추가 // 2. 기존 코드 건드릴 때 조금씩 개선 // 수정 전 if (m_i32Flag & 0x04) { ... } // 수정 후 (플래그에 의미 부여) const int FLAG_PARTY_LEADER = 0x04; if (m_i32Flag & FLAG_PARTY_LEADER) { ... } // 3. IDE 리팩토링 기능 활용 (Rename Symbol) // m_dwPK_Score 선택 → F2 → pkScore로 변경 // → 모든 참조가 자동으로 바뀜!
IDE 단축키: Rename Symbol

Visual Studio: F2 또는 Ctrl + R, R
VS Code: F2
JetBrains: Shift + F6

변수/함수 이름 바꾸면 모든 참조가 자동으로 바뀜!

핵심 정리: 의도를 드러내는 이름

  • 이름 = 문서: 주석 없이도 이해되게
  • 4가지 조건: 의도, 발음, 검색, 일관성
  • 헝가리안: 새 코드에선 지양, 의미를 담아
  • 함수는 동사: Save, Load, Calculate, Is, Has
  • 길어도 OK: 명확한 게 짧고 모호한 것보다 나음
  • 점진적: 건드릴 때마다 조금씩 개선
