머티리얼 그래프는 어떻게 HLSL이 되는가

언리얼 렌더링 · 36 / 42

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "아티스트가 연결한 노드가 HLSLMaterialTranslator를 거쳐 MaterialTemplate.ush의 빈칸을 채우고, 그게 basepass-shader에서 우리가 그냥 받아 쓰던 GetMaterialBaseColor()가 되는 길"이 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX로 직접 뭘 그려봤으면 이 순서가 몸에 배어 있을 거야. HLSL 파일을 손으로 연다. float4 PS(...) : SV_Target을 손으로 짠다. 상수버퍼 구조체를 C++에도 똑같이 하나 만든다. map 해서 값을 채우고, 셰이더를 컴파일해서 PSO에 꽂는다. 재질이 하나 늘면? 사람이 코드를 하나 더 짠다.

그런데 언리얼 에디터를 열면 아티스트가 마우스로 노드를 끌어다 붙이고 있어. 텍스처 샘플 노드 하나, 곱하기 노드 하나, 그 결과를 Base Color 핀에 꽂는다. 저장을 누르면 잠깐 "Compiling Shaders"가 뜨고, 뷰포트의 구체가 바뀐다. 코드를 아무도 안 짰는데 GPU에서 픽셀 셰이더가 돌고 있어.

그럼 그 셰이더는 누가 짰나?

지난 basepass-shader에서 우리는 GetMaterialBaseColor(PixelMaterialInputs), GetMaterialRoughness(...) 같은 함수를 그냥 있는 셈 치고 받아 썼어. FPixelMaterialInputs라는 구조체가 어디선가 뚝 떨어져서 채워져 있었지. 사실 그게 이 챕터의 정체야. 그 함수들은 언리얼이 미리 짜둔 게 아니라, 네 머티리얼 그래프를 보고 그때그때 만들어낸 코드다.

이걸 모르면 뭐가 터질까? 세 가지가 계속 미스터리로 남아.

  1. 머티리얼 인스턴스에서 색깔 파라미터를 슬라이더로 드르륵 움직이면 즉시 바뀌는데, Static Switch 체크박스 하나 누르면 다시 컴파일이 돈다. 왜 어떤 건 공짜고 어떤 건 비싼가?
  2. 블렌드 모드를 Opaque에서 Translucent로 바꿨더니 GBuffer에 안 찍힌다. 왜?
  3. 머티리얼 하나 고쳤는데 셰이더가 수백 벌 컴파일된다. 뭐가 곱해지는 건가?

이 셋 다 "그래프가 코드가 되는 그 순간"에 답이 있어. 그러니까 이번 장은 shader-compile(어떻게 굽는가)과 shader-permutation(왜 여러 벌 굽는가) 사이에 빠져 있던 조각, "애초에 그 셰이더 원본을 누가 썼는가"를 채우는 장이다.

🧱 먼저 알아야 할 것 — 그림으로 그린 계산도 결국 계산 순서다
• 선으로 이은 상자: 상자에서 상자로 선을 그으면, 앞 상자의 결과가 뒤 상자의 재료가 된다는 뜻이야. 왼쪽에서 오른쪽으로 물이 흐르는 관이라고 봐도 돼.
• 순서가 정해진다: "A와 B를 곱해서 C에 넣는다"를 상자 그림으로 그리든 글로 쓰든, 실제로 해야 할 일의 순서는 똑같다. 그림은 표현 방식일 뿐이야.
• 끝에는 목적지가 있다: 관을 따라가면 마지막엔 "이 값을 어디에 쓸 건가"가 나온다. 색인지, 거칠기인지, 표면 방향인지.
이게 잡히면 아래 "노드 그래프를 코드로 번역한다"는 말이 얹힌다.

0. 비유부터 — 콘티는 있는데 대본이 없다

영화 촬영장으로 가보자. 감독이 콘티를 그렸어. 그림으로. "여기서 카메라가 이렇게 돌고, 배우가 저쪽에서 나오고, 조명은 파랗게."

근데 조명팀은 그림을 못 읽어. 조명팀이 읽는 건 큐시트야. "3번 조명, 청색 필터, 40% 밝기, 12초부터." 아주 딱딱한 형식.

그러면 누군가는 콘티(그림)를 큐시트(글)로 옮겨 적어야 해. 그 사람이 스크립터야. 스크립터는 콘티를 보고, 이미 정해진 큐시트 양식지의 빈칸을 채운다. 양식지는 원래 있던 거고 — "3번 조명: ______, 밝기: ______" — 스크립터는 그 빈칸만 채우는 거지.

머티리얼도 똑같아.

  • 콘티(그림) = 아티스트가 연결한 머티리얼 노드 그래프
  • 스크립터 = HLSLMaterialTranslator (그래프 → HLSL 번역기)
  • 큐시트 양식지 = MaterialTemplate.ush (빈칸이 뚫린 셰이더 틀)
  • 채워진 큐시트 = 완성된 .usf 소스
  • 조명팀 = GPU

중요한 건 이거야. 양식지는 언리얼이 미리 만들어놨고, 빈칸만 네 그래프로 채운다. 그러니까 basepass-shader의 BasePass 코드는 절대 안 바뀐다. 걔는 항상 GetMaterialBaseColor()를 부를 뿐이야. 바뀌는 건 그 함수 안쪽, 즉 빈칸이지.

이번 장은 그 스크립터의 손을 따라간다.

🌱 이 개념은 왜 생겼나 — 머티리얼 그래프
• 원래 구조: 재질마다 프로그래머가 HLSL을 하나씩 손으로 짠다. 우리가 DirectX 샘플 짤 때 하던 그거야. 재질 3개면 셰이더 3개.
• 그런데 문제: 게임 하나에 재질이 수천 개다. 아티스트는 "이 벽돌을 조금 더 젖게" 만들고 싶은데 그때마다 프로그래머한테 가서 HLSL을 고쳐달라고 해야 해. 병목이 사람이 돼버려.
• 그래서 필요한 것: 아티스트가 코드 없이 재질을 조립할 수 있는 그림 언어가 필요해. 그게 노드 그래프고, 대신 그 그림을 코드로 옮기는 번역기가 엔진 쪽에 하나 있어야 한다. 그 번역기가 HLSLMaterialTranslator야.

1. 노드 하나는 코드 한 줄이 된다

제일 밑바닥부터 보자. 노드 하나가 코드로 바뀌는 순간.

모든 머티리얼 노드는 C++에서 UMaterialExpression을 상속한 클래스야. 그리고 각자 자기를 어떻게 코드로 옮길지 아는 Compile() 함수를 하나씩 갖고 있어. 곱하기 노드를 보자.

A.Compile(Compiler) : Compiler->Constant(ConstA); // if the input is hooked up, use it, otherwise use the internal constant int32 Arg2 = B.GetTracedInput().Expression ? B.Compile(Compiler) : Compiler->Constant(ConstB); return Compiler->Mul(Arg1, Arg2); }
🔤 기호 사전 — 노드의 자기소개서
• UMaterialExpression = 머티리얼 그래프의 노드 한 개를 나타내는 C++ 클래스야. Multiply, TextureSample, ScalarParameter 전부 이걸 상속해.
• FMaterialCompiler* Compiler = 번역기 손잡이야. 노드는 "나를 코드로 만들어줘"라고 이 손잡이에 부탁한다. 실제 구현체가 FHLSLMaterialTranslator야.
• int32 리턴 = 놀랍게도 값이 아니라 번호표를 돌려줘. "네가 부탁한 계산은 몇 번 코드 조각(chunk)이야"라는 인덱스다.
• A, B = 노드의 입력 핀. 그래프에서 왼쪽에 달린 그 구멍이야.
• A.GetTracedInput().Expression = 그 핀에 연결된 노드가 실제로 있는지 확인한다. 없으면 nullptr.
• ? : = 조건이 참이면 앞, 거짓이면 뒤를 고르는 삼항 연산자야.
• A.Compile(Compiler) = 연결된 앞 노드를 재귀적으로 컴파일한다. 그래프를 거슬러 올라가는 거야.
• Compiler->Constant(ConstA) = 핀이 비어 있으면 노드에 손으로 적어둔 상수를 코드 조각으로 만든다.
• Compiler->Mul(Arg1, Arg2) = "이 두 번호표를 곱하는 코드 한 줄 만들어줘"라는 요청. 새 번호표가 나온다.
🔁 이제 다시 보자. 곱하기 노드는 자기 왼쪽 핀 두 개를 먼저 컴파일해서 번호표 두 장을 받고 → 번역기에게 "이 둘을 곱해라"고 시켜 새 번호표 한 장을 받아 → 그걸 자기를 부른 쪽에 돌려준다. 이게 그래프 전체에서 재귀로 일어나. 결과 핀에서 시작해 거꾸로 거슬러 올라가면서, 노드마다 코드 조각이 하나씩 쌓이는 거야.

여기서 감이 와야 해. 번역기는 그래프를 "그림"으로 안 봐. 결과 핀에서 거꾸로 타고 올라가면서 계산 순서를 뽑아내. 서버로 치면 스크립트 표현식 트리를 후위 순회하면서 바이트코드를 뱉는 거랑 똑같은 짓이야.

그럼 그 "코드 조각"이 실제로 어떻게 생겼냐? 번역기는 조각마다 지역변수 한 줄을 뱉어. 텍스처 샘플 하나를 곱해서 Base Color에 꽂은 그래프는 대충 이런 HLSL이 된다.

// 노드 그래프 // // [Texture Sample] ──┐ // ├──▶ [Multiply] ──▶ ● Base Color // [Scalar "Tint"] ──┘ // // ↓ 번역 결과 (모양만 보자. 정확한 표기는 엔진 버전마다 다르다) MaterialFloat4 Local0 = ProcessMaterialColorTextureLookup(Texture2DSample(...)); MaterialFloat Local1 = <Material 유니폼 버퍼의 N번 칸>; // ScalarParameter "Tint" MaterialFloat3 Local2 = (Local0.rgb * Local1); // Multiply 노드 PixelMaterialInputs.BaseColor = Local2; // 결과 핀에 대입

Local0, Local1, Local2. 노드 하나당 지역변수 하나. 아까 Compile()이 돌려준 int32 번호표가 바로 이 LocalN의 N이야. 번호표를 코드로 펼치면 Local2가 되는 거지.

그리고 마지막 줄을 잘 봐둬. PixelMaterialInputs.BaseColor = Local2; — 여기가 그래프와 basepass-shader가 만나는 지점이다.

🌱 이 개념은 왜 생겼나 — MaterialTemplate.ush (빈칸 뚫린 양식지)
• 원래 구조: 번역기가 셰이더 파일 전체를 통째로 생성하면 되지 않나? 노드 그래프를 보고 .usf 한 벌을 처음부터 끝까지 찍어내는 거야.
• 그런데 문제: 그러면 FMaterialPixelParameters 구조체 선언, 텍스처 좌표 처리, 노멀 공간 변환 같은 모든 머티리얼이 똑같이 쓰는 뼈대까지 매번 생성해야 해. 뼈대를 고치려면 생성기 C++ 코드를 고쳐야 하고, 셰이더 프로그래머가 HLSL을 못 만지게 돼.
• 그래서 필요한 것: 뼈대는 사람이 쓴 HLSL 파일로 두고, 그래프마다 달라지는 부분만 빈칸으로 뚫어두면 돼. 그 빈칸 뚫린 양식지가 MaterialTemplate.ush고, 빈칸 기호가 %{이름}이야.

2. 양식지의 빈칸 — MaterialTemplate.ush

이제 양식지를 열어보자. Engine/Shaders/Private/MaterialTemplate.ush. 이건 그냥 HLSL이 아니야. 중간중간 %{이름}이 박혀 있는, 컴파일 안 되는 반쪽짜리 파일이다.

먼저 머티리얼이 내놓는 값들의 상자를 보자. 놀랍게도 구조체 몸통 자체가 빈칸이야.

🔤 기호 사전 — 양식지 읽는 법
• .ush = Unreal Shader Header. .usf가 셰이더 본문이면 .ush는 include 되는 조각이야.
• %{pixel_material_inputs} = 여기가 빈칸이다. C++ 번역기가 나중에 이 자리에 생성한 HLSL 문자열을 꽂는다. UE5.6은 printf의 %s가 아니라 이름표 달린 빈칸(%{이름})을 쓴다.
• struct FPixelMaterialInputs { %{pixel_material_inputs} }; = ⭐ 구조체의 필드 목록조차 생성물이라는 뜻이야. 이 머티리얼이 실제로 쓰는 칸만 들어간다.
• #if TEMPLATE_USES_SUBSTRATE = UE5의 새 재질 시스템(Substrate)을 쓸 때만 켜지는 갈래.
• FMaterialPixelParameters Parameters = 머티리얼이 받는 재료들의 상자. 이 픽셀의 UV, 월드 위치, 카메라 방향 같은 것.
• in out = 들어오기도 하고 나가기도 하는 값. 함수 안에서 고쳐서 바깥으로 넘긴다.
• SHADER_PUSH_WARNINGS_STATE / SHADER_DISABLE_WARNINGS = 생성된 코드는 사람이 안 쓴 코드라 경고가 잔뜩 뜰 수 있어서, 빈칸 구간만 경고를 꺼두는 장치야. 빈칸이 어디부터 어디까지인지 알려주는 표시이기도 해.
• CalcPixelMaterialInputs(...) = 이 픽셀의 머티리얼 값을 전부 계산해서 PixelMaterialInputs를 채우는 함수. 이 함수의 몸통이 곧 네 그래프다.
• GetMaterialBaseColor(...) = 채워진 상자에서 BaseColor 칸을 꺼내주는 창구. saturate(0~1로 자르기) 하나 얹은 게 전부야.
🔁 이제 다시 보자. 양식지에서 안 바뀌는 부분은 struct FPixelMaterialInputs라는 껍데기와 GetMaterialBaseColor 같은 창구 함수들이야. 바뀌는 부분은 %{pixel_material_inputs}(어떤 칸이 있는지)와 CalcPixelMaterialInputs 몸통의 %{calc_pixel_material_inputs_*} 세 칸(그 칸을 어떻게 채우는지)이고, 거기에 Local0 = ...; Local1 = ...; PixelMaterialInputs.BaseColor = Local2;가 들어간다. 그래서 BasePass는 어떤 머티리얼이든 항상 같은 함수를 부를 수 있어.
⚠️ 여기서 basepass-shader의 오해 하나가 풀려. GetMaterialBaseColor()는 무거운 계산을 하는 함수가 아니야. 계산은 이미 CalcPixelMaterialInputs에서 다 끝났고, 얘는 구조체 필드 하나 꺼내주는 게 전부다. BasePass가 GetMaterialRoughness()를 부른다고 해서 러프니스 그래프가 그때 도는 게 아니야 — 픽셀당 한 번, 맨 앞에서 이미 다 돌았어.

🔁 이제 다시 보자. 번역기는 PrepareMaterialSourceStringParameters()에서 (이름표 → 문자열) 짝을 수십 개 쌓아두고(개수 define부터 노드 그래프 번역 결과까지) → GetMaterialShaderCode()가 MaterialTemplate.ush를 리졸버에 물리고 그 목록을 넘겨 → Finalize()로 완성된 .usf 소스 한 벌을 만든다. 이 문자열이 그대로 shader-compile의 입구로 들어가. 거기서 전처리되고, 백엔드가 굽고, DDC에 박히는 거야.

이제 두 챕터가 이어졌지. 이 장이 "셰이더 소스를 만드는 곳"이고, shader-compile이 "그 소스를 굽는 곳"이야. DirectX로 치면, 우리가 손으로 .hlsl 파일을 저장하는 그 순간을 언리얼은 C++ 문자열 조립으로 대신하는 거다.

3. 역할 분담 — FMaterial / FMaterialShaderMap / FMaterialRenderProxy

이름이 비슷해서 제일 헷갈리는 3형제야. 근데 하는 일은 완전히 달라. 촬영장 비유로 먼저 나누자.

  • FMaterial = 대본 담당. "이 재질은 어떤 셰이딩 모델이고, 블렌드 모드가 뭐고, 그래프가 이렇게 생겼다"는 레시피를 안다. 렌더 스레드가 보는 머티리얼의 정체. (UMaterial은 에디터/게임 스레드 쪽 에셋이고, 렌더링이 실제로 보는 건 FMaterial 쪽이야.)
  • FMaterialShaderMap = 구워진 필름 창고. 그 레시피로 실제 컴파일된 셰이더 바이트코드 묶음. 버텍스 팩토리별 × 셰이더 타입별 × 순열별로 여러 벌 들어 있다.
  • FMaterialRenderProxy = 현장 소품 담당. "이번 촬영에서 이 벽돌의 색은 빨강, 거칠기 0.7" 같은 파라미터 값을 대준다. 대본은 안 건드리고 값만 대준다.

표로 보면 더 깔끔해.

클래스뭘 들고 있나바뀌면?
FMaterial셰이딩 모델, 블렌드 모드, 도메인, 그래프 → 레시피셰이더 소스가 달라짐 → 재컴파일
FMaterialShaderMap컴파일된 셰이더들 → 결과물(레시피가 바뀌면 통째로 새로 생김)
FMaterialRenderProxy스칼라/벡터/텍스처 파라미터 값유니폼 버퍼만 다시 채움 → 공짜

연결 관계는 이래. 드로우콜을 만들 때(mesh-draw-command) 렌더러는 메시에 붙은 FMaterialRenderProxy를 잡는다. 프록시한테 "네 FMaterial 줘" 하면 레시피가 나오고, 레시피의 FMaterialShaderMap에서 이 버텍스 팩토리 × 이 패스에 맞는 셰이더를 꺼낸다. 그리고 프록시가 들고 있는 유니폼 버퍼를 그 셰이더에 꽂는다.

🧱 먼저 알아야 할 것 — 틀과 채우는 값은 다른 층이다
• 도장과 잉크: 도장은 모양을 정하고, 잉크는 색을 정한다. 도장을 깎는 건 오래 걸리지만 잉크를 바꾸는 건 순식간이야.
• 같은 도장, 다른 잉크: 도장 하나로 빨강도 찍고 파랑도 찍을 수 있다. 굳이 도장을 새로 깎지 않아도 돼.
• 모양을 바꾸려면: 글자 하나를 빼고 싶으면? 그건 잉크로 못 한다. 도장을 다시 깎아야 해.
이게 잡히면 아래 "머티리얼 인스턴스 vs 스태틱 스위치" 설명이 얹힌다.

4. ⭐ 왜 파라미터는 공짜고, 스태틱 스위치는 비싼가

이번 장의 심장이다. 아티스트가 제일 자주 묻고, 면접에서도 제일 자주 나오는 질문이야.

머티리얼 인스턴스에서 색 슬라이더를 움직이면 즉시 반영된다. 근데 Static Switch 체크박스 하나 누르면 셰이더가 다시 컴파일된다. 왜?

스칼라/벡터 파라미터 — 잉크만 바꾼다

ScalarParameter 노드의 Compile()을 보자. 허무할 만큼 짧아.

MaterialExpressions.cpp:8620

int32 UMaterialExpressionScalarParameter::Compile(class FMaterialCompiler* Compiler, int32 OutputIndex) { if (bUseCustomPrimitiveData) { if (Material && Material->MaterialDomain == MD_UI) { return CompilerError(Compiler, CPD_UI_ErrorMessage); } return Compiler->CustomPrimitiveData(PrimitiveDataIndex, MCT_Float); } else { return Compiler->ScalarParameter(ParameterName,DefaultValue); } }

본줄기는 맨 아래 return Compiler->ScalarParameter(ParameterName, DefaultValue); 한 줄이야. 여기서 핵심은 DefaultValue를 상수로 박지 않는다는 거야. Compiler->ScalarParameter(...)는 "이 머티리얼의 유니폼 버퍼에 Tint라는 칸을 하나 잡아라"라고 등록하고, 생성되는 HLSL은 상수 대신 그 칸을 읽는 코드가 된다.

// ScalarParameter "Tint" = 0.5 로 만든 그래프의 번역 결과 // ❌ 이렇게 안 됨 (상수로 굳어버림) MaterialFloat Local1 = 0.5f; // ✅ 실제로는 이렇게 (유니폼 버퍼를 읽음) MaterialFloat Local1 = <Material 유니폼 버퍼의 N번 칸>; // → 0.5든 0.9든 셰이더 코드는 똑같다. 버퍼에 든 숫자만 다르다.
🔤 기호 사전 — 유니폼 버퍼로 빠지는 값
• 유니폼 버퍼(uniform buffer) = 한 드로우콜 동안 모든 픽셀에 똑같이 적용되는 값을 담는 GPU 메모리 덩어리. DirectX의 상수 버퍼(constant buffer, cbuffer)랑 같은 물건이야. 우리가 ID3D11Buffer 만들어서 Map/memcpy 하던 그거.
• bUseCustomPrimitiveData = 곁가지 갈래야. 이걸 켜면 값을 머티리얼 유니폼 버퍼가 아니라 프리미티브(오브젝트)마다 따로 들고 있는 칸에서 읽는다. 같은 머티리얼을 쓰는 물체마다 값을 다르게 주고 싶을 때 쓰는 길이고, 이번 절의 본줄기는 아니야.
• ParameterName = 아티스트가 노드에 적어둔 이름(Tint). 나중에 인스턴스가 이 이름으로 값을 덮어쓴다.
• DefaultValue = 아무도 안 덮어썼을 때 쓸 기본값. 코드에 박히는 게 아니라 버퍼의 초기값이 될 뿐이다.
• FMaterialUniformExpressionSet = "이 머티리얼의 유니폼 버퍼에는 몇 번 칸에 뭐가 들어간다"는 배치표. 번역할 때 같이 만들어진다.
• FUniformExpressionCache = 렌더 프록시가 들고 있는 실제로 채워진 유니폼 버퍼. 값이 바뀌면 이것만 다시 채운다.
🔁 이제 다시 보자. 스칼라/벡터 파라미터는 셰이더 코드에 흔적을 남기지 않아. 코드에는 "유니폼 버퍼 N번 칸을 읽어라"만 남고, 그 칸에 0.5를 넣든 0.9를 넣든 바이트코드는 글자 하나 안 바뀐다. 그래서 머티리얼 인스턴스를 100개 만들어도 FMaterialShaderMap은 부모 것 하나를 공유하고, 인스턴스마다 다른 건 FMaterialRenderProxy가 채우는 유니폼 버퍼뿐이야. 슬라이더를 움직이면 FUniformExpressionCache만 다시 채워진다. 셰이더는 손도 안 대.

이게 머티리얼 인스턴스(Material Instance)의 존재 이유 전부야. 같은 도장, 다른 잉크. 텍스처 파라미터도 마찬가지 — 셰이더는 "0번 텍스처 슬롯에서 샘플링해"라고만 적혀 있고, 그 슬롯에 어떤 텍스처를 바인딩하는지는 프록시가 정하니까.

스태틱 스위치 — 도장을 다시 깎는다

이제 StaticSwitchParameter를 보자. 이름은 비슷한데 Compile()이 완전히 다른 짓을 해.

UE5.6에서는 "어느 쪽 핀을 쓸지 고르는" 일이 GetEffectiveInput()으로 빠져 있어. 여기가 진짜 핵심이야.

🔤 기호 사전 — 번역 시점에 갈라지는 스위치
• bool bValue = 이 스위치가 켜졌는지 꺼졌는지. 런타임이 아니라 번역 중에 정해지는 값이야.
• GetStaticBoolValue(...) = "이 머티리얼(인스턴스)에서 이 스위치는 켜져 있나?"를 번역기에게 물어본다. 답은 컴파일 전에 이미 나와 있다.
• StaticBoolParameter(...) = 이 스위치를 스태틱 파라미터 목록에 등록한다. 이 목록이 나중에 셰이더맵을 찾는 열쇠의 일부가 돼.
• FExpressionInput* = 입력 핀을 가리키는 포인터야. return bValue ? &A : &B; — ⭐ 이 한 줄이 전부다. 켜졌으면 A 핀 주소를, 꺼졌으면 B 핀 주소를 돌려준다.
• EffectiveInput->Compile(Compiler) = 고른 쪽 하나만 컴파일한다. 안 불린 쪽 서브그래프는 코드 조각이 아예 안 만들어져. HLSL 파일에 존재하지 않는다.
• INDEX_NONE = 언리얼의 "없음" 인덱스(-1). 번역 실패를 뜻해.
• DynamicBranch = 최근에 추가된 예외 갈래야. 이걸 켜면 스태틱 스위치인데도 A와 B를 둘 다 컴파일하고 런타임 분기를 남긴다. 즉 재컴파일은 안 하지만 셰이더가 무거워져. 정확히 "도장 vs 잉크"의 절충안이고, 기본값은 꺼져 있어.
• FStaticParameterSet = 이 머티리얼의 모든 스태틱 스위치 값 모음. 셰이더맵 ID의 재료야.
🔁 이제 다시 보자. 스태틱 스위치는 (DynamicBranch를 안 켠 기본 상태에서) if 문을 셰이더에 남기지 않아. GetEffectiveInput()이 번역 중에 GetStaticBoolValue로 값을 확정하고 A 핀이냐 B 핀이냐를 골라서 그 하나만 Compile()에 넘긴다. 안 쓰는 쪽 노드들은 코드로 번역조차 안 된다. 그러니까 스위치를 켜고 끄면 생성되는 HLSL 소스 자체가 달라진다. 소스가 다르면? 다른 셰이더다. 다시 구워야 해. 도장을 다시 깎는 거야.

그래서 셰이더맵이 갈린다 — shader-permutation과 만나는 지점

언리얼이 컴파일된 셰이더맵을 찾을 때 쓰는 열쇠가 FMaterialShaderMapId야. 그 안에 뭐가 들었냐면:

FMaterialShaderMapId (열쇠 구성 — 개념) ├─ BaseMaterialId (어느 머티리얼 에셋인가) ├─ FStaticParameterSet ★ 스태틱 스위치 값들 ├─ QualityLevel (Low / Medium / High / Epic) ├─ FeatureLevel (SM5 / SM6 / ES3_1 ...) └─ ShaderTypeDependencies / VertexFactoryTypeDependencies

보이지? FStaticParameterSet이 열쇠 안에 들어 있다. 스위치 하나 켜면 열쇠가 달라지고, 열쇠가 달라지면 창고에서 기존 셰이더맵을 못 꺼내. 새로 구워야 한다. shader-compile에서 봤던 "define 하나 바뀌면 캐시 키가 달라진다"의 머티리얼 버전이야.

그리고 여기서 순열 폭발이 시작돼. shader-permutation에서 배운 곱셈이 그대로 돌아온다.

스태틱 스위치 3개 = 2 × 2 × 2 = 8 벌 × 퀄리티 4단계 = 32 벌 × 버텍스 팩토리 (Static/Skeletal/Instanced ...) ← ch-37에서 다룬다 × 패스별 셰이더 타입 (BasePass / Depth / Shadow / Velocity ...) ───────────────────────────────────────────── = 머티리얼 하나에서 수백~수천 벌

"머티리얼 하나 저장했는데 왜 셰이더 400개를 굽지?"의 답이 이거야. 스태틱 스위치 하나 추가는 코드 한 줄이 아니라, 구워야 할 셰이더 수를 두 배로 만드는 결정이다.

⚠️ 그래서 실무 원칙이 하나 나와. 런타임에 자주 바뀌는 건 스칼라/벡터 파라미터로, 에셋마다 고정인 건 스태틱 스위치로. "이 벽돌은 젖었나?"를 스태틱 스위치로 하면 젖음/마름 두 벌이 구워지지만 셰이더가 최적이고, 스칼라 WetAmount로 하면 한 벌만 굽지만 안 젖은 픽셀도 젖음 계산 코드를 지나간다. 컴파일 시간 vs GPU 시간의 거래야.
🌱 이 개념은 왜 생겼나 — 머티리얼 인스턴스
• 원래 구조: 색깔만 다른 벽돌 재질 20개가 필요하면 머티리얼 에셋 20개를 만든다. 그래프를 복사-붙여넣기 하면 되잖아.
• 그런데 문제: 그래프가 같으니 셰이더 코드도 완전히 똑같은데, 에셋이 20개니까 셰이더맵도 20벌 구워진다. 컴파일 시간 20배, 메모리 20배, PSO 20배. 게다가 그래프를 고치려면 20개를 다 고쳐야 해.
• 그래서 필요한 것: 코드는 부모 것을 그대로 쓰고, 유니폼 버퍼 값만 다른 가벼운 자식이 필요해. 그게 머티리얼 인스턴스(UMaterialInstance → 렌더 쪽 FMaterialInstanceResource)야. 자기 셰이더맵을 안 갖고 부모의 FMaterial을 가리키기만 한다. 단, 스태틱 파라미터를 하나라도 덮어쓰면 그 순간 자기만의 셰이더맵을 갖게 된다.

5. 블렌드 모드 · 셰이딩 모델 · 도메인은 define이 된다

머티리얼 에디터 왼쪽 디테일 패널의 드롭다운 세 개. 이것들도 결국 셰이더 컴파일 환경의 define으로 번역돼. shader-compile에서 봤던 FShaderCompilerEnvironment에 값을 박는 거야.

🔤 기호 사전 — 드롭다운이 define으로
• GetBlendMode() = 이 머티리얼이 Opaque인지 Translucent인지 돌려준다. 에디터 드롭다운 값 그대로야.
• WritesEveryPixel() = 이 재질이 픽셀을 하나도 안 버리는지 확인. 마스크가 없으면 Masked로 설정돼 있어도 사실상 Solid로 취급해서 공짜로 최적화한다.
• SET_SHADER_DEFINE(OutEnvironment, NAME, 1) = 셰이더 컴파일 환경에 #define NAME 1을 박는 매크로. shader-permutation의 "도장 찍기"랑 똑같은 동작이야.
• SET_SHADER_DEFINE_AND_COMPILE_ARGUMENT(...) = define을 박는 동시에 컴파일 인자로도 넘긴다. define은 셰이더 소스가 읽고, 컴파일 인자는 엔진의 컴파일 로직이 읽는다.
• MATERIALBLENDING_SOLID = .usf 안의 #if MATERIALBLENDING_SOLID를 켜는 스위치.
• case BLEND_AlphaComposite: 가 MATERIALBLENDING_TRANSLUCENT도 켠다 = 주석 그대로 "블렌드 모드가 TRANSLUCENT를 재사용한다"는 뜻. 반투명 계열은 결국 같은 셰이더 경로를 탄다.
• MATERIAL_DOMAIN_SURFACE = 이 머티리얼이 일반 표면용인지, 포스트프로세스용인지, UI용인지 가른다. 도메인이 다르면 아예 다른 패스에서 다른 셰이더로 돈다.
• default: UE_LOG(...) = 모르는 값이 오면 경고를 찍고 안전한 기본값(Opaque / Surface)으로 되돌린다.
🔁 이제 다시 보자. 에디터의 드롭다운 하나 → FMaterial::SetupMaterialEnvironment가 SET_SHADER_DEFINE으로 번역 → .usf의 #if가 켜지고 꺼짐 → 다른 셰이더가 나온다. 이게 shader-permutation에서 본 "도장 → define → #if" 흐름 그대로야. 차이는 도장을 C++ 프로그래머가 아니라 아티스트가 드롭다운으로 찍는다는 것뿐이지.

이 챕터에서 딱 이것만

  • 머티리얼 노드 그래프는 UMaterialExpression::Compile()이 결과 핀에서 거꾸로 재귀하면서 코드 조각(LocalN)으로 번역된다.
  • MaterialTemplate.ush는 %{이름} 빈칸이 뚫린 양식지고, FHLSLMaterialTranslator::GetMaterialShaderCode()가 그 빈칸을 채워 완성된 셰이더 소스를 만든다. FPixelMaterialInputs는 구조체 몸통(%{pixel_material_inputs})조차 생성물이다.
  • ch-21의 GetMaterialBaseColor()는 구조체 필드를 꺼내는 창구일 뿐이고, 진짜 그래프는 CalcPixelMaterialInputs() 몸통이다.
  • FMaterial=레시피 / FMaterialShaderMap=구워진 셰이더 / FMaterialRenderProxy=파라미터 값. 셋은 다른 층이다.
  • 스칼라/벡터/텍스처 파라미터는 유니폼 버퍼 값일 뿐이라 재컴파일이 없다. 머티리얼 인스턴스는 부모의 셰이더맵을 공유한다.
  • 스태틱 스위치는 번역 시점에 갈래를 확정해 한쪽만 코드로 만든다. 소스가 달라지므로 FMaterialShaderMapId가 갈리고 재컴파일된다.
  • Blend Mode / Shading Model / Domain은 SET_SHADER_DEFINE으로 번역되어 USES_GBUFFER, SHADINGMODELID_* 같은 ch-20/21의 갈림길을 만든다.

Q1. 아티스트가 노드를 연결하면 그게 어떻게 GPU에서 도는 픽셀 셰이더가 되나요?

답 보기
노드마다 UMaterialExpression::Compile()이 있어서, 결과 핀에서부터 거꾸로 재귀하며 자기를 코드 조각으로 번역해. 곱하기 노드면 왼쪽 핀 두 개를 먼저 컴파일해서 번호표를 받고, Compiler->Mul(...)로 새 번호표를 받는 식이야. 그 번호표가 결국 MaterialFloat3 Local2 = (Local0.rgb * Local1); 같은 지역변수 한 줄이 돼. 그렇게 쌓인 조각들을 FHLSLMaterialTranslator가 MaterialTemplate.ush의 %{이름} 빈칸에 꽂으면 완성된 셰이더 소스 문자열이 나오고, 그게 shader-compile 파이프라인으로 들어가서 구워져. 감독이 그린 콘티를 스크립터가 큐시트 양식지에 옮겨 적는 거야 — DirectX에서 우리가 손으로 .hlsl 파일을 저장하던 그 순간을 C++ 문자열 조립이 대신하는 거지.

↳ 그럼 ch-21에서 봤던 GetMaterialBaseColor()는 어디서 온 함수인가요?

답 보기
MaterialTemplate.ush에 미리 사람이 써둔 함수야. 그리고 하는 일은 return PixelMaterialInputs.BaseColor;가 전부 — 구조체 필드 하나 꺼내주는 창구일 뿐이야. 무거운 계산을 하는 함수가 아니라는 게 중요해. 진짜 네 그래프는 그 위쪽 CalcPixelMaterialInputs() 몸통에 들어 있고, 거기서 픽셀당 한 번 다 계산해서 PixelMaterialInputs 칸들을 채워놔. 그래서 BasePass 코드는 어떤 머티리얼이든 절대 안 바뀌어. 양식지의 창구는 고정이고, 빈칸만 그래프마다 다른 거지.

↳ 그럼 MaterialTemplate.ush를 열면 컴파일 가능한 HLSL인가요?

답 보기
아니야. 중간에 %{pixel_material_inputs}, %{calc_pixel_material_inputs_normal} 같은 이름표 달린 빈칸이 박혀 있는 반쪽짜리 파일이야. 그대로는 컴파일 안 돼. FHLSLMaterialTranslator::PrepareMaterialSourceStringParameters()가 (이름표 → 문자열) 짝을 수십 개 쌓아두고, GetMaterialShaderCode()가 FStringTemplateResolver로 그 빈칸들을 이름을 보고 채워야 비로소 진짜 HLSL이 돼. 심지어 struct FPixelMaterialInputs의 필드 목록조차 빈칸이라, 이 머티리얼이 실제로 쓰는 칸만 생성된다.

Q2. FMaterial, FMaterialShaderMap, FMaterialRenderProxy는 각각 뭘 하나요?

답 보기
촬영장으로 나누면 딱 떨어져. FMaterial은 대본 담당 — 셰이딩 모델, 블렌드 모드, 도메인, 그래프 같은 레시피를 안다. FMaterialShaderMap은 구워진 필름 창고 — 그 레시피로 실제 컴파일된 셰이더 바이트코드 묶음이야(버텍스 팩토리 × 셰이더 타입 × 순열별로 여러 벌). FMaterialRenderProxy는 현장 소품 담당 — "이 벽돌 색은 빨강, 거칠기 0.7" 같은 파라미터 값만 대준다. 드로우콜을 만들 땐 프록시에서 시작해서 → FMaterial(레시피) → FMaterialShaderMap(셰이더)을 꺼내고, 프록시가 들고 있는 유니폼 버퍼를 그 셰이더에 꽂아.

↳ 왜 굳이 FMaterialRenderProxy를 따로 두나요? FMaterial이 값도 같이 들고 있으면 안 되나요?

답 보기
그러면 머티리얼 인스턴스가 성립을 안 해. 색만 다른 벽돌 20종을 만들 때, 레시피(코드)는 하나면 충분하고 값만 20벌 있으면 되잖아. 값을 FMaterial에 붙여버리면 값이 다른 만큼 FMaterial도 20개가 되고, 셰이더맵도 20벌 구워져 — 코드가 똑같은데도. 그래서 레시피 층(FMaterial + 셰이더맵)과 값 층(FMaterialRenderProxy)을 분리한 거야. 도장과 잉크를 분리하는 거지. 덕분에 인스턴스 100개가 부모의 셰이더맵 하나를 공유할 수 있어.

Q3. ⭐ 머티리얼 인스턴스에서 색 파라미터를 바꾸면 즉시 되는데, 스태틱 스위치를 켜면 왜 재컴파일되나요?

답 보기
스칼라/벡터 파라미터는 셰이더 코드에 흔적을 안 남기기 때문이야. UMaterialExpressionScalarParameter::Compile()은 DefaultValue를 상수로 박지 않고 Compiler->ScalarParameter(...)를 불러서 유니폼 버퍼에 칸을 하나 예약해. 생성된 HLSL에는 "유니폼 버퍼 N번 칸을 읽어라"만 남지. 그러니까 그 칸에 0.5를 넣든 0.9를 넣든 바이트코드는 글자 하나 안 바뀐다. 값만 FUniformExpressionCache에 다시 채우면 끝 — DirectX로 치면 cbuffer에 memcpy 한 줄이야.

반대로 UMaterialExpressionStaticSwitchParameter::Compile()은 번역 시점에 GetStaticBoolValue()로 값을 확정하고 A 아니면 B 한쪽만 컴파일해. 안 쓰는 쪽 서브그래프는 HLSL에 아예 안 실려. 그러니까 스위치를 바꾸면 생성되는 소스 자체가 달라지고, 그건 정의상 다른 셰이더야. 다시 구울 수밖에 없어. 파라미터는 잉크, 스태틱 스위치는 도장이야.

↳ 엔진은 "다시 구워야 한다"는 걸 어디서 알아채나요?

답 보기
셰이더맵을 찾는 열쇠인 FMaterialShaderMapId 안에 FStaticParameterSet이 들어 있어서야. 스태틱 스위치 값들이 열쇠의 일부인 거지. 스위치 하나를 켜면 열쇠가 달라지고, 열쇠가 달라지면 창고에서 기존 FMaterialShaderMap을 못 꺼내니까 새로 굽는다. shader-compile에서 본 "define 하나 바뀌면 캐시 키(입력 지문)가 달라진다"의 머티리얼 버전이야. 열쇠엔 그 외에 퀄리티 레벨, 피처 레벨, 셰이더/버텍스팩토리 타입 의존성도 들어가.

↳ 그럼 실무에서 스태틱 스위치를 언제 쓰고 언제 피해야 하나요?

답 보기
런타임에 자주 바뀌는 건 스칼라/벡터로, 에셋마다 고정인 건 스태틱 스위치로. 스태틱 스위치는 조합이 곱셈으로 늘어(shader-permutation). 스위치 3개면 8벌, 거기에 퀄리티 4단계 × 버텍스 팩토리 × 패스별 셰이더 타입까지 곱하면 머티리얼 하나에서 수백~수천 벌이 나와. "머티리얼 하나 저장했는데 왜 셰이더 400개를 굽지?"의 답이 이거야. 대신 스위치를 쓰면 안 쓰는 코드가 셰이더에 아예 없어서 GPU에선 제일 빨라. 컴파일 시간·메모리 vs GPU 시간의 거래고, 이걸 이해하고 고르는 게 핵심이야. 참고로 스태틱 스위치를 하나라도 덮어쓴 머티리얼 인스턴스는 그 순간 자기만의 셰이더맵을 갖게 돼 — 더 이상 가벼운 인스턴스가 아니야.

Q4. Blend Mode를 Translucent로 바꾸면 왜 GBuffer에 안 찍히나요?

답 보기
에디터 드롭다운이 셰이더 컴파일 환경의 define으로 번역되기 때문이야. FMaterial::SetupMaterialEnvironment()가 블렌드 모드를 보고 MATERIALBLENDING_SOLID나 MATERIALBLENDING_TRANSLUCENT를 SET_SHADER_DEFINE으로 박아. 그러면 .usf의 #if들이 갈리면서 불투명 재질만 USES_GBUFFER 경로를 타고 basepass-shader의 EncodeGBufferToMRT까지 가. 반투명은 GBuffer 한 칸에 표면 하나만 적을 수 있다는 디퍼드의 근본 한계 때문에 애초에 그 길로 못 가고, translucency의 포워드 경로로 빠져. 셰이딩 모델도 똑같아 — Unlit을 고르면 MATERIAL_SHADINGMODEL_UNLIT이 박히고, ch-21에서 봤던 SetGBufferForUnlit 갈림길이 켜지는 거야.

↳ 이건 결국 shader-permutation에서 배운 거랑 같은 얘기 아닌가요?

답 보기
맞아, 메커니즘은 완전히 똑같아. "도장(define) → #if → 다른 셰이더"라는 흐름 그대로야. 차이는 도장을 누가 찍느냐뿐이야. ch-27에서는 C++ 프로그래머가 SHADER_PERMUTATION_BOOL("TONEMAP")으로 차원을 선언했지. 여기서는 아티스트가 드롭다운을 고르고 스태틱 스위치를 체크하면 그게 define이 돼. 그래서 머티리얼 순열 폭발은 프로그래머가 통제하기 더 어려워 — 아티스트가 스위치를 하나 추가할 때마다 빌드팜 시간이 두 배가 되는데, 그 사람은 그걸 모를 수도 있거든. 순열 예산 관리가 팀 문제가 되는 이유야.
