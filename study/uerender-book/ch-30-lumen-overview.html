Lumen — 실시간 전역 조명

언리얼 렌더링 · 30 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "Lumen이 왜 bake를 대신하려고 나왔는지, 어떤 조건을 통과해야 실제로 켜지는지"가 잡힌다.

왜 이걸 배워? — 문제의식부터

너는 서버에서 캐시가 왜 필요한지 알아. 매번 DB를 깊게 긁으면 느리니까, 자주 쓰는 값은 메모리에 잡아두고 상황이 바뀌면 갱신하지.

간접광도 똑같은 압박을 받아. 빛이 벽에 맞고 바닥에 맞고 다시 캐릭터 얼굴에 닿는 걸 200만 픽셀마다 정직하게 여러 번 추적하면, 한 프레임 16.6ms 안에 끝내기 어렵다. 그래서 예전엔 많이 굽기, 즉 bake를 했어. 맵이 고정돼 있으면 에디터에서 미리 빛 튐 결과를 계산해 텍스처로 저장하고, 게임 중에는 읽기만 하는 방식이야.

근데 문이 열리고, 벽이 부서지고, 시간이 낮에서 밤으로 바뀌고, 손전등 든 플레이어가 뛰면 미리 구운 지도는 금방 거짓말이 돼. 언리얼도 같은 문제를 만났고, 그 답이 Lumen이야. Lumen은 간접광을 런타임 장면 데이터와 트레이싱으로 계속 갱신하려는 시스템이야.

왜 지금 보냐면, 앞에서 GBuffer, deferred lighting, shadow, Nanite까지 봤기 때문이야. 이제 "표면에 직접 빛을 때리는 것"을 넘어서 그 빛이 주변으로 번지는 문제를 볼 차례야. 다음 lumen-diffuse는 실제 diffuse indirect 경로를 더 팔고, 이번 챕터는 먼저 Lumen의 입구 조건과 필요한 재료를 잡는다.

0. 비유부터 — 빛 배달 관제센터

도시에 피자 배달원이 있다고 해보자.

직접광은 쉽다. 가게에서 손님 집까지 바로 가면 돼. 태양이 바닥을 바로 때리는 것, 램프가 벽을 바로 밝히는 것, 이건 "직배송"이야.

간접광은 어렵다. 피자가 한 번에 안 가고, A 건물 로비, B 복도, C 방 안으로 옮겨가는 느낌이야. 빛도 그래. 빨간 벽에 닿은 빛이 바닥에 붉은 기운을 묻히고, 밝은 바닥이 다시 캐릭터 턱 밑을 살짝 밝힌다.

예전 bake는 "내일 배달 경로는 다 고정이니까 오늘 밤에 지도에 색칠해두자"야. 건물이 안 바뀌면 빠르고 좋다. 하지만 실시간 게임 도시는 움직여. 그러면 어제 색칠한 지도는 낡아.

Lumen은 "배달 관제센터"야. 매 프레임 도시 전체를 완전 시뮬레이션하진 못하지만, 지금 필요한 경로를 추적하고, 쓸 수 있는 지도 조각을 캐시하고, 하드웨어 레이 트레이싱이 있으면 그 길을 쓰고, 없으면 distance field 같은 대체 지도를 써.

이번 챕터의 비유는 이렇게 간다.

  • Lumen.cpp = 관제센터 입구와 안전문
  • ShouldRenderLumenDiffuseGI = 간접광 배달 접수대
  • Hardware Ray Tracing = 실제 도로를 레이로 훑는 특수 차량
  • Software Distance Field = 건물 모양을 압축한 거리 지도
  • Warning = "지도 없어서 배달 못 해" 안내문

1. 큰 전원 — 프로젝트가 Lumen을 허용하나

관제센터가 아무리 똑똑해도 프로젝트 설정에서 "Lumen 쓰지 마"라고 하면 시작도 못 해. Lumen.cpp 맨 앞은 그런 큰 스위치들부터 둔다.

• TAutoConsoleVariable<int32> = 콘솔 변수로 읽을 수 있는 정수 설정 상자야.
• TEXT("...") = 언리얼 문자열을 감싸는 표기야.
• r.Lumen.Supported = 프로젝트가 Lumen 자체를 지원할지 보는 큰 문패야.
• ECVF_ReadOnly = 실행 중 막 바꾸는 값이 아니라는 뜻이야.

🔁 이제 다시 보자. CVarLumenSupported는 관제센터 전원이고 → CVarLumenSupportedSM5는 낡은 길을 허용할지 보는 문이고 → CVarLumenAsyncCompute는 가능하면 compute 차선을 쓸지 보는 스위치야. Lumen은 "그냥 항상 켜짐"이 아니라 프로젝트와 품질 설정을 먼저 통과해.

여기서 중요한 건 설명 문자열이야. Lumen을 끄면 shader compile과 load time overhead도 피할 수 있다고 적혀 있지. 즉 Lumen은 후처리 필터 하나가 아니라, 셰이더와 장면 데이터와 추적 리소스가 줄줄이 따라오는 큰 기능 묶음이야.

서버로 치면 기능 플래그 하나 켰더니 DB 테이블, 메모리 캐시, 백그라운드 잡, 패킷 핸들러가 같이 붙는 상황이야. 그래서 입구에 큰 차단기가 있어야 해.

2. 뷰 하나가 Lumen을 받을 자격이 있나

프로젝트가 허용해도 모든 카메라 뷰가 Lumen을 받는 건 아니야. 평면 반사용 뷰, 리플렉션 캡처용 뷰, 뷰 상태가 없는 특수 뷰는 빠진다. 관제센터가 모든 CCTV에 배달 경로를 계산하지 않는 거야.

• Scene->DefaultLumenSceneData = Lumen이 쓸 장면 데이터가 준비돼 있는지 보는 칸이야.
• nullptr = 아무것도 없다는 뜻이야.
• ViewFamily.Views.Num() = 이 렌더링 묶음 안의 뷰 개수야.
• LUMEN_MAX_VIEWS = Lumen이 처리하겠다고 정한 최대 뷰 수야.
• *View.Family = 포인터가 가리키는 실제 ViewFamily를 꺼내 넘기는 표기야.
• !View.bIsPlanarReflection = 평면 반사용 뷰가 아니어야 한다는 뜻이야.
• DoesProjectSupportDistanceFields() = 프로젝트가 distance field 데이터를 만들 수 있는지 묻는 함수야.
🔁 이제 다시 보자. ShouldRenderLumenForViewFamily는 장면, Lumen scene data, 뷰 개수, 플랫폼을 보고 → IsSoftwareRayTracingSupported는 distance field 지원을 보고 → IsLumenFeatureAllowedForView는 이 뷰가 진짜 Lumen 대상인지 마지막으로 거른다. 관제센터가 "도시 지도 있음, 화면 수 감당 가능, 진짜 플레이어 화면, 추적용 도로 정보 있음"을 확인하는 장면이야.

이 토막이 Lumen 입구의 핵심이야. PostProcessSettings에서 Lumen을 골랐다고 무조건 도는 게 아니다. Scene에 DefaultLumenSceneData가 있어야 하고, 플랫폼이 지원해야 하고, View가 적절해야 하고, 마지막으로 tracing data가 있어야 해.

여기서 bSkipTracingDataCheck는 뒤의 경고 코드에서 다시 나온다. "설정상 켜고 싶었는데 추적 데이터가 없어서 실제론 못 켜는 상황"을 구분하려고 일부 조건을 잠깐 건너뛰는 검사 스위치야.

3. 간접광 접수대 — Diffuse GI가 켜지는 조건

이제 Lumen 공통 문을 통과했으니 진짜 간접광 접수대로 내려가 보자. 파일은 LumenDiffuseIndirect.cpp야. 여기서 "이 뷰에 Lumen diffuse global illumination을 렌더할까?"를 결정한다.

LumenDiffuseIndirect.cpp:291

bool ShouldRenderLumenDiffuseGI(const FScene* Scene, const FSceneView& View, bool bSkipTracingDataCheck, bool bSkipProjectCheck) { return Lumen::IsLumenFeatureAllowedForView(Scene, View, bSkipTracingDataCheck, bSkipProjectCheck) && View.FinalPostProcessSettings.DynamicGlobalIlluminationMethod == EDynamicGlobalIlluminationMethod::Lumen && CVarLumenGlobalIllumination.GetValueOnAnyThread() && View.Family->EngineShowFlags.GlobalIllumination && View.Family->EngineShowFlags.LumenGlobalIllumination && !View.Family->EngineShowFlags.PathTracing && !View.Family->EngineShowFlags.RayTracingDebug && (bSkipTracingDataCheck || Lumen::UseHardwareRayTracedScreenProbeGather(*View.Family) || Lumen::IsSoftwareRayTracingSupported()); }
🔤 기호 사전 — Diffuse GI 접수대
• ShouldRenderLumenDiffuseGI = 이 뷰에 Lumen 간접광을 그릴지 묻는 함수야.
• DynamicGlobalIlluminationMethod = 최종 설정에서 동적 전역 조명 방식을 뭘로 골랐는지 보는 칸이야.
• EDynamicGlobalIlluminationMethod::Lumen = GI 방식이 Lumen이어야 한다는 enum 값이야.
• CVarLumenGlobalIllumination.GetValueOnAnyThread() = Lumen GI 콘솔 스위치가 켜져 있는지 읽는 호출이야.
• EngineShowFlags.GlobalIllumination = 전역 조명 자체가 show flag에서 켜져 있어야 한다는 뜻이야.
• PathTracing = 별도 패스 트레이싱 모드라 Lumen GI가 끼어들지 않는다.
• UseHardwareRayTracedScreenProbeGather = 하드웨어 레이 트레이싱으로 screen probe gather를 할 수 있는지 보는 함수야.
🔁 이제 다시 보자. 공통 허가증을 보고 → 포스트프로세스 설정이 Lumen GI인지 보고 → 콘솔 변수와 show flag가 켜졌는지 보고 → path tracing/debug 같은 특수 모드를 빼고 → 하드웨어 트레이싱이나 software distance field 중 하나가 있는지 본다. "배달 신청함, 관제센터 켜짐, 도시 지도 있음"이어야 간접광 배달이 출발해.

DynamicGlobalIlluminationMethod라는 이름 자체가 bake와의 차이를 보여준다. 정적인 라이트맵을 읽는 게 아니라, 동적으로 GI를 만드는 경로 중 하나로 Lumen을 고르는 거야.

물론 매번 완전 정답을 계산하진 못해. 그래서 screen probe, radiance cache, surface cache, distance field, hardware ray tracing 같은 장치를 섞는다. 이번 챕터에서는 이름만 잡고, 다음 lumen-diffuse에서 실제 diffuse indirect 경로를 더 본다.

4. 움직이는 지도 재료 — Software Distance Field

실시간 간접광은 장면을 추적할 재료가 필요해. 벽이 어디 있는지, 메시가 어디 있는지, 빛이 어느 방향으로 막히는지 모르면 배달 경로를 못 짜.

하드웨어 레이 트레이싱이 있으면 실제 ray tracing scene을 쓸 수 있어. 없으면 Lumen은 software distance field 경로를 쓴다. 아주 거칠게 말하면, 메시를 "이 지점에서 표면까지 얼마나 떨어졌나"를 알려주는 거리 지도처럼 바꿔서 추적하는 방식이야.

Lumen.cpp:260

bool Lumen::UseGlobalSDFObjectGrid(const FSceneViewFamily& ViewFamily) { if (!Lumen::IsSoftwareRayTracingSupported()) { return false; } // All features use Hardware RayTracing, no need to update voxel lighting if (Lumen::UseHardwareRayTracedSceneLighting(ViewFamily) && Lumen::UseHardwareRayTracedScreenProbeGather(ViewFamily) && Lumen::UseHardwareRayTracedReflections(ViewFamily) && Lumen::UseHardwareRayTracedRadianceCache(ViewFamily) && Lumen::UseHardwareRayTracedTranslucencyVolume(ViewFamily) && Lumen::UseHardwareRayTracedVisualize(ViewFamily)) { return false; } return true; }
🔤 기호 사전 — 소프트웨어 추적 지도
• UseGlobalSDFObjectGrid = global signed distance field 오브젝트 격자를 쓸지 묻는 함수야.
• if (...) = 조건이 맞으면 안쪽으로 들어가라는 뜻이야.
• return false = 이 기능을 쓰지 않겠다고 바로 답하고 끝내는 거야.
• IsSoftwareRayTracingSupported() = software tracing용 distance field가 가능한지 보는 함수야.
• UseHardwareRayTracedSceneLighting = 장면 조명 추적을 hardware ray tracing으로 하는지 보는 함수야.
• UseHardwareRayTracedReflections = 반사 추적도 hardware ray tracing 경로인지 보는 함수야.
• return true = 위에서 빠지지 않았으니 grid를 업데이트하겠다는 뜻이야.
🔁 이제 다시 보자. software tracing이 불가능하면 false → 모든 관련 기능이 hardware ray tracing을 쓰면 voxel lighting 지도를 업데이트할 필요가 없으니 false → 그 외에는 global SDF object grid가 필요하니 true야. 특수 차량이 모든 길을 직접 훑으면 종이 지도 갱신이 덜 필요하고, 아니면 거리 지도가 계속 필요한 셈이야.

이게 bake와 결정적으로 달라. bake는 정해진 지도를 한 번 만들고 끝내는 쪽에 가깝다. Lumen은 런타임에 쓸 장면 표현을 계속 보며, hardware 경로가 충분하면 그쪽을 쓰고, 아니면 software용 압축 지도를 유지한다.

우리 서버로 치면 bake는 서버 시작 전에 몬스터 스폰 테이블을 전부 파일로 저장하는 방식이고, Lumen은 라이브 서버에서 필드 상황을 보고 필요한 지역 캐시를 갱신하는 방식에 가깝다.

5. 데이터가 없으면 못 한다 — 경고까지 코드에 있다

사용자 입장에서는 "프로젝트에서 Lumen 켰는데 왜 화면이 이상하지?"가 흔해. 언리얼은 이 상황도 코드로 구분한다. 설정상으로는 Lumen을 원하지만 하드웨어 레이 트레이싱도 없고 software distance field도 없으면, 관제센터는 배달 지도가 없는 상태야.

• Writer->DrawLine(Message) = 화면에 메시지 한 줄을 그리라는 호출이야.

여기서 진짜 중요한 문장이 나온다. "Lumen is enabled, but has no ray tracing data..." 즉 Lumen은 빛을 실시간으로 계산하려면 반드시 추적할 데이터가 있어야 해.

그 데이터는 둘 중 하나야. 프로젝트에서 Mesh Distance Fields를 생성해서 software distance field tracing을 쓰거나, hardware ray tracing 지원을 켜서 ray tracing scene을 쓰거나. 이걸 모르면 Lumen을 "켜면 예쁜 간접광이 나오는 옵션"으로 오해해. 실제로는 관제센터와 지도와 차량이 같이 있어야 움직이는 시스템이야.

6. 그래서 Lumen은 무엇을 실시간으로 바꾸나

빛에는 직접광과 간접광이 있어. 직접광은 태양이나 램프에서 표면까지 바로 오는 빛이고, 앞에서 본 shadow map이나 deferred lighting이 주로 이 감각을 잡아줬어.

간접광은 한 번 이상 튄 빛이야. 바닥 색이 천장에 묻고, 벽 색이 캐릭터 그림자 속에 섞이고, 창문으로 들어온 빛이 방 안 전체에 퍼지는 것. 예전 bake는 이 결과를 정적 맵에 미리 저장했어. 빠르지만 못 움직인다.

Lumen은 이 문제를 런타임 시스템으로 바꾼다. 완전한 정답을 매번 계산하는 대신 화면 정보, Lumen scene data, surface cache, screen probe, radiance cache, hardware ray tracing, software distance field를 섞어 지금 화면에 필요한 간접광을 갱신한다.

이번 코드에서 확인한 건 계산 공식이 아니라 시작 조건이야.

  • 프로젝트가 r.Lumen.Supported로 Lumen을 허용해야 해.
  • Scene에 DefaultLumenSceneData가 있어야 해.
  • View가 planar reflection이나 reflection capture 같은 보조 뷰가 아니어야 해.
  • GI 설정이 EDynamicGlobalIlluminationMethod::Lumen이어야 해.
  • hardware ray tracing 또는 software distance field tracing 데이터가 있어야 해.

이 입구를 통과하면 다음 단계에서 diffuse indirect 계산이 시작된다.

콜/데이터 흐름 한눈에

줄번호는 실제 인용 기준이야.

프로젝트 큰 스위치 Lumen.cpp :16 | v 뷰 패밀리 공통 허가 ShouldRenderLumenForViewFamily :235 | v 뷰 하나 허가 IsLumenFeatureAllowedForView :248 | v Diffuse GI 접수 ShouldRenderLumenDiffuseGI :291 | v 추적 데이터 선택 Hardware ray tracing path Software distance field path | v 데이터 없으면 화면 경고 WriteWarnings :288

배달 비유로 다시 읽으면, 관제센터 전원을 켜고, 오늘 처리할 화면이 진짜 대상인지 보고, 간접광 배달 요청인지 확인하고, 실제 도로 지도나 거리 지도가 있는지 본 다음, 지도 없으면 안내문을 띄우는 흐름이야.

우리 서버·DirectX 랑 비교

서버 쪽 감각으로 보면 Lumen은 "패킷 핸들러 하나"가 아니라 큰 기능 묶음이야. 실시간 전장 매칭을 켜면 설정 플래그만 보는 게 아니라 DB 테이블, 메모리 캐시, 매칭 큐, 타이머, 클라 알림 패킷까지 준비돼야 하잖아. Lumen도 r.Lumen.Supported, DefaultLumenSceneData, tracing data가 같이 있어야 해.

DirectX 감각으로 보면 픽셀 셰이더 하나가 아니라 여러 pass와 리소스 조합이야. async compute를 쓸 수 있으면 일부 일을 겹칠 수 있지만, 하드웨어 레이 트레이싱 경로는 별도 지원 조건이 붙는다.

bake와 Lumen의 차이는 서버의 "오프라인 프리컴퓨트"와 "라이브 캐시" 차이랑 비슷해. 오프라인 프리컴퓨트는 빠르지만 세상이 바뀌면 낡고, 라이브 캐시는 비용이 들지만 현재 상태를 따라온다.

이 챕터에서 딱 이것만

  • Lumen은 간접광을 실시간으로 다루려는 관제센터야.
  • 예전 bake는 빠르지만 정적인 지도라 움직이는 장면을 잘 못 따라온다.
  • Lumen이 켜지려면 프로젝트, Scene, View, GI 설정, tracing data를 전부 통과해야 해.
  • tracing data는 hardware ray tracing 또는 software distance field 쪽으로 준비돼야 한다.
  • "설정상 켜짐"과 "실제로 렌더 가능"은 다른 문제야.
