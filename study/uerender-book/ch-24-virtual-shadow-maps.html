Virtual Shadow Maps — 그림자를 가상 메모리처럼

언리얼 렌더링 · 24 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "VSM이 왜 거대한 그림자 텍스처를 통째로 만들지 않고, 필요한 페이지만 빌려 쓰는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

너는 이미 서버에서 이런 문제를 봤어. 유저 10만 명이 있을 수 있다고 해서, 접속도 안 한 10만 명 전부의 인벤토리 버퍼를 매 프레임 꽉 채워 만들진 않잖아. 실제 접속자, 실제 이동한 유저, 실제 필요한 패킷만 잡아서 처리해.

그림자도 똑같이 터져. 앞 챕터 shadow-maps에서 배운 방식은 "빛의 눈으로 깊이를 한 번 더 그린다"였지. 그런데 월드가 커지고, 카메라 가까이엔 고해상도 그림자가 필요하고, Nanite처럼 미세한 지오메트리가 늘어나면 그냥 큰 섀도맵 하나로는 답이 안 나와. 16K 텍스처를 빛마다 통째로 만들면 메모리도, 렌더링도, 캐시도 터져.

그래서 언리얼도 같은 문제를 만났고, 답이 Virtual Shadow Maps야. 이름 그대로 그림자 지도를 가상 메모리처럼 본다. 주소 공간은 크게 잡아두되, 실제 물리 메모리 페이지는 화면에서 필요한 타일만 빌려준다.

지금 이 챕터가 shadow-maps 바로 다음인 이유도 그거야. "빛의 눈으로 한 번 더 그린다"는 원리는 이미 배웠고, 이제 현대 UE가 그 비용을 어떻게 버티는지 볼 차례야. 다음 translucency로 가면 반투명처럼 또 다른 예외가 나오니까, 여기서 먼저 그림자 메모리 문제를 잡고 가자.

0. 비유부터 — 학교 사물함을 전교생 명부처럼 쓰기

전교생이 10,000명인 학교가 있다고 해보자.

교장 선생님이 이렇게 말하면 망해:

  • 학생 10,000명 전부에게 매일 새 사물함을 하나씩 준다.
  • 안 온 학생 사물함도 청소한다.
  • 비어 있는 사물함도 이름표를 새로 붙인다.
  • 복도 끝 창고까지 전부 매일 검사한다.

이러면 사물함이 몇 개가 있어도 부족하고, 청소하는 애들이 지쳐 쓰러져.

똑똑한 방식은 이거야:

  • 명부에는 전교생 10,000명 이름을 다 적어둔다.
  • 진짜 사물함은 오늘 필요한 만큼만 둔다.
  • 등교한 학생만 "사물함 필요" 표시를 한다.
  • 빈 사물함 하나를 꺼내 그 학생 이름과 연결한다.
  • 내일도 같은 학생이 오면 어제 사물함을 재사용한다.
  • 자리가 부족하면 오래 안 쓴 사물함을 회수한다.

VSM도 이 구조야.

  • 전교생 명부 = 거대한 가상 섀도맵 주소 공간
  • 진짜 사물함 = PhysicalPagePool
  • 이름표 표 = PageTable
  • "오늘 필요함" 체크 = PageRequestFlags
  • 사물함 속 쪽지 = PhysicalPageMetaData
  • 어제 사물함 재사용 = 캐시

앞으로도 계속 이 비유로 갈 거야. "그림자 타일"이라고 어렵게 들리면 그냥 "오늘 필요한 학생에게만 사물함 빌려주기"라고 읽으면 된다.

1. 큰 그림 — 큰 지도는 가짜고, 진짜 창고는 작다

일반 섀도맵은 커다란 종이 한 장이야. 빛 하나가 8192x8192 깊이 텍스처를 갖고 있으면, 그 텍스처 전체가 진짜 메모리야.

VSM은 반대로 생각해. "가상으로는 큰 지도처럼 보이게 하자. 하지만 실제 메모리는 작은 페이지 창고만 두자." 그래서 첫 번째 핵심은 물리 페이지 풀 크기를 정하는 코드야.

FVirtualShadowMapArray::Initialize 안에서 실제 물리 페이지 풀의 폭/높이를 계산해. 줄을 보면 PhysicalPagesX, PhysicalPagesY, MaxPhysicalPages, PhysicalPageRowMask, PhysicalPageRowShift 같은 말이 나온다. 이게 전부 "사물함 창고를 몇 칸으로 둘까" 계산이야.

const uint32 PhysicalPagesX = FMath::DivideAndRoundDown(CacheManager->GetPhysicalMaxWidth(), FVirtualShadowMap::PageSize); check(FMath::IsPowerOfTwo(PhysicalPagesX)); const int32 MaxPhysicalPages = CVarMaxPhysicalPages.GetValueOnRenderThread(); uint32 PhysicalPagesY = FMath::DivideAndRoundUp((uint32)FMath::Max(1, MaxPhysicalPages), PhysicalPagesX); UniformParameters.MaxPhysicalPages = PhysicalPagesX * PhysicalPagesY; if (CacheManager->IsCacheEnabled()) { // Only set up the dynamic separate HZB build allocation if // 1. caching is enabled & we cache static separate (otherwise they are combined anyway) // 2. the cvar is enabled if (CVarBuildDynamicHZB.GetValueOnRenderThread() != 0) { UniformParameters.StaticHZBArrayIndex = 1; } // Enable separate static caching in the second texture array element UniformParameters.StaticCachedArrayIndex = 1; } uint32 PhysicalX = PhysicalPagesX * FVirtualShadowMap::PageSize; uint32 PhysicalY = PhysicalPagesY * FVirtualShadowMap::PageSize; // TODO: Some sort of better fallback with warning? // All supported platforms support at least 16384 texture dimensions which translates to 16384 max pages with default 128x128 page size check(PhysicalX <= GetMax2DTextureDimension()); check(PhysicalY <= GetMax2DTextureDimension()); UniformParameters.PhysicalPageRowMask = (PhysicalPagesX - 1); UniformParameters.PhysicalPageRowShift = FMath::FloorLog2( PhysicalPagesX ); UniformParameters.RecPhysicalPoolSize = FVector4f( 1.0f / PhysicalX, 1.0f / PhysicalY, 1.0f, 1.0f ); UniformParameters.PhysicalPoolSize = FIntPoint( PhysicalX, PhysicalY ); UniformParameters.PhysicalPoolSizePages = FIntPoint( PhysicalPagesX, PhysicalPagesY );
🔤 기호 사전 — 물리 페이지 풀 만들기
• const uint32 = 바뀌지 않는 32비트 양수. 사물함 개수처럼 음수가 되면 이상한 값에 쓴다.
• FMath::DivideAndRoundDown = 나누고 버림. 창고 폭에 페이지가 몇 개 들어가나 세는 계산이야.
• check(...) = 조건이 깨지면 개발 중 바로 터뜨리는 안전핀.
• CVarMaxPhysicalPages.GetValueOnRenderThread() = 콘솔 변수에서 "최대 물리 페이지 수" 설정을 렌더 스레드에서 읽는다.
• UniformParameters = 나중에 셰이더가 볼 공통 설정 묶음. GPU에게 넘기는 안내문이라고 보면 돼.
• PhysicalPageRowMask / PhysicalPageRowShift = 페이지 번호를 x/y 좌표로 빠르게 바꾸기 위한 비트 계산 도구.
• FIntPoint = 정수 x/y 한 쌍. 여기서는 풀의 크기를 픽셀 또는 페이지 단위로 담는다.
🔁 이제 다시 보자. PhysicalPagesX로 한 줄에 들어갈 사물함 수를 정하고 → MaxPhysicalPages로 전체 예산을 읽고 → PhysicalPagesY로 줄 수를 만든다. 그 다음 UniformParameters에 "총 사물함 수, 창고 크기, 줄 번호 계산법"을 적어 GPU에게 넘겨. 큰 그림자 지도를 통째로 산 게 아니라, 작은 사물함 창고 규격만 먼저 정한 거야.

여기서 중요한 건 VirtualMaxResolutionXY 같은 가상 해상도랑 PhysicalPoolSize가 다르다는 점이야.

가상 섀도맵은 크게 보인다.

하지만 실제 깊이 값이 저장되는 곳은 PhysicalPagePool이야.

서버로 치면 "전체 유저 ID 공간은 64비트로 넓게 잡지만, 실제 세션 객체는 접속자 수만큼만 만든다"와 같아.

2. 누가 사물함을 달라고 하나 — 화면 픽셀이 페이지를 표시한다

그럼 누가 "이 페이지 필요해"라고 표시할까?

정답은 화면 픽셀이야. 지금 화면에 보이는 픽셀마다 "이 픽셀이 그림자를 계산하려면 어느 섀도맵 페이지가 필요하지?"를 거꾸로 계산한다.

이 계산은 VirtualShadowMapPageMarking.ush의 MarkPage가 딱 보여준다. 월드 위치를 빛의 섀도 좌표로 바꾸고, 그 좌표가 어떤 가상 페이지에 속하는지 계산하고, 마지막에 MarkPageAddress로 요청 플래그를 찍어.

VirtualShadowMapPageMarking.ush:82

void MarkPage(FVirtualShadowMapHandle VirtualShadowMapHandle, uint MipLevel, float3 TranslatedWorldPosition, bool bUsePageDilation, float2 PageDilationOffset) { FVirtualShadowMapProjectionShaderData ProjectionData = GetVirtualShadowMapProjectionData(VirtualShadowMapHandle); // MarkPage (or mark pixel pages) should never run for a distant light. checkSlow(!VirtualShadowMapHandle.IsSinglePage()); float3 ViewToShadowTranslation = DFFastLocalSubtractDemote(ProjectionData.PreViewTranslation, PrimaryView.PreViewTranslation); float3 ShadowTranslatedWorldPosition = TranslatedWorldPosition + ViewToShadowTranslation; float4 ShadowUVz = mul(float4(ShadowTranslatedWorldPosition, 1.0f), ProjectionData.TranslatedWorldToShadowUVMatrix); ShadowUVz.xyz /= ShadowUVz.w; // Check overlap vs the shadow map space // NOTE: XY test not really needed anymore with the precise cone test in the caller, but we'll leave it for the moment bool bInClip = ShadowUVz.w > 0.0f && all(and(ShadowUVz.xyz <= ShadowUVz.w, ShadowUVz.xyz >= float3(-ShadowUVz.ww, 0.0f))); if (!bInClip) { return; } // Normal pages marked through pixel processing are not "coarse" and should include "detail geometry" - i.e., all geometry uint Flags = VSM_FLAG_ALLOCATED | VSM_FLAG_DETAIL_GEOMETRY; uint MaxVirtualAddress = CalcLevelDimsTexels(MipLevel) - 1U; float2 VirtualAddressFloat = ShadowUVz.xy * CalcLevelDimsTexels(MipLevel); uint2 VirtualAddress = clamp(uint2(VirtualAddressFloat), 0U, MaxVirtualAddress); uint2 PageAddress = VirtualAddress >> VSM_LOG2_PAGE_SIZE; FVSMPageOffset PageOffset = CalcPageOffset(VirtualShadowMapHandle, MipLevel, PageAddress); MarkPageAddress(PageOffset, Flags); BRANCH if (ProjectionData.bUseReceiverMask) { MarkPageReceiverMask(PageOffset, VirtualAddress); }
🔤 기호 사전 — 필요한 페이지 표시
• float3 / float4 = GPU 셰이더의 실수 벡터. 위치나 좌표를 x/y/z/w로 들고 다닌다.
• mul(...) = 행렬 곱. 월드 위치를 섀도맵 좌표로 바꾸는 변환이다.
• ShadowUVz.xyz /= ShadowUVz.w = 동차좌표 나누기. 투영 뒤 진짜 uv/z로 펴는 단계야.
• if (!bInClip) return; = 빛의 지도 안에 없으면 사물함 요청을 하지 않고 바로 나간다.
• uint Flags = ... | ... = 비트 깃발을 합친다. "할당 필요"와 "디테일 지오메트리 필요" 표식을 같이 켠다.
• >> VSM_LOG2_PAGE_SIZE = 텍셀 주소를 페이지 주소로 바꾸는 빠른 나누기. 페이지 크기만큼 오른쪽으로 접는 느낌이야.
• MarkPageAddress(PageOffset, Flags) = 이 가상 페이지가 필요하다고 요청표에 표시한다.
• BRANCH = GPU에게 "여기 조건 분기 있어"라고 힌트를 주는 매크로.
🔁 이제 다시 보자. TranslatedWorldPosition을 ShadowUVz로 바꾸고 → 빛의 범위 밖이면 return하고 → 안쪽이면 VirtualAddress와 PageAddress를 계산한다. 마지막 MarkPageAddress(PageOffset, Flags)가 "이 학생 오늘 사물함 필요함" 도장이다. 아직 그림자를 그린 게 아니야. 필요한 페이지 목록만 만든 거야.

이 지점이 VSM의 첫 번째 반전이야.

일반 섀도맵은 먼저 그림자 텍스처를 통째로 렌더하고 나중에 화면에서 샘플링한다.

VSM은 화면을 먼저 보면서 "필요한 페이지"를 표시한다.

서버로 치면 모든 유저에게 매 프레임 패킷을 만들지 않고, 이번 틱에 실제로 관심 영역에 들어온 대상만 send queue에 올리는 거랑 비슷해.

3. 요청표를 보고 진짜 사물함을 빌려준다

이제 PageRequestFlags에 필요한 가상 페이지들이 표시됐어.

다음 단계는 실제 물리 페이지를 배정하는 거야. 이름표 표인 PageTable에 "이 가상 페이지는 물리 페이지 몇 번으로 가라"를 적는다.

VirtualShadowMapPhysicalPageManagement.usf의 AllocateNewPageMappings가 그 장면이다. 이미 캐시된 페이지가 없고, 요청 플래그가 있으면, 사용 가능한 물리 페이지 목록에서 하나를 꺼내서 연결한다.

🔁 이제 다시 보자. RequestFlags가 0이 아니면 요청이 있다는 뜻이고 → PageFlags가 0이면 아직 연결된 페이지가 없다는 뜻이야. 그러면 PopPhysicalPageList로 빈 사물함을 꺼내고 → OutPageTable에 가상 주소와 물리 주소를 연결하고 → OutPhysicalPageMetaData에 "이 사물함은 누구 것"인지 적는다. 이게 VSM의 심장이다.

여기서 가상 메모리 냄새가 확 나지?

CPU 가상 메모리도 "가상 주소 → 페이지 테이블 → 물리 프레임"으로 간다.

VSM도 "가상 섀도 페이지 → PageTable → PhysicalPagePool"로 간다.

차이는 목적이야. CPU는 프로세스 메모리를 보호하고 크게 보이게 하려고 쓰고, VSM은 그림자 텍스처를 크게 보이게 하되 실제 렌더링은 필요한 타일만 하려고 쓴다.

4. 이제 그릴 때도 전체 지도가 아니라 물리 창고에 그린다

페이지를 배정했으면 진짜 그림자를 그려야 해.

그런데 여기서도 VSM은 큰 가상 텍스처에 직접 그리지 않는다. 실제 출력 대상은 PhysicalPagePoolRDG야. 렌더 패스 파라미터를 만들 때 bRenderToVirtualShadowMap을 켜고, 페이지 테이블과 물리 페이지 풀 UAV를 넘긴다.

🔤 기호 사전 — VSM 렌더 패스 준비
• auto ... = [...] (...) { ... }; = 람다. 작은 함수를 변수처럼 만들어두는 C++ 문법이야.
• GraphBuilder.AllocParameters = RDG 패스에 넘길 파라미터 구조체를 그래프 안에서 할당한다.

• VirtualSmPageTable = PageTableRDG = 셰이더가 가상 페이지를 물리 페이지로 찾을 표를 넘긴다.
• GraphBuilder.CreateSRV = 읽기용 뷰를 만든다. "이 버퍼를 읽을 수 있게 해줘"라는 손잡이다.
• GraphBuilder.CreateUAV = 쓰기용 뷰를 만든다. OutDepthBufferArray는 물리 페이지 풀에 깊이를 쓸 수 있게 한다.
• ERDGUnorderedAccessViewFlags::SkipBarrier = RDG 배리어 처리를 일부 건너뛰겠다는 플래그. 이미 흐름을 알고 있을 때 쓰는 저수준 옵션이야.
🔁 이제 다시 보자. bRenderToVirtualShadowMap을 켜고 → VirtualSmPageTable로 이름표 표를 넘기고 → OutDepthBufferArray를 PhysicalPagePoolRDG의 UAV로 만든다. 그러니까 렌더러는 큰 가상 종이에 그리는 게 아니라, 페이지 테이블을 보며 실제 사물함 칸에 깊이를 써 넣는 거야.

이게 "필요한 타일만 렌더"의 두 번째 절반이야.

앞에서 필요한 페이지를 표시했고, 중간에서 물리 페이지를 배정했고, 이제 그 배정된 물리 칸에만 깊이를 써.

전체 월드 전체 그림자 텍스처를 싹 칠하는 게 아니다.

5. 샘플링할 때도 주소 번역부터 한다

마지막으로 화면에 빛을 얹을 때는 그림자를 샘플링해야 해.

일반 섀도맵이면 "uv로 텍스처 찍고 깊이 비교"가 끝이야.

VSM은 한 단계가 더 있다. 가상 uv가 어느 페이지인지 찾고, PageTable에서 물리 주소를 꺼내고, 진짜 물리 텍셀 주소로 바꾼 다음 샘플링한다.

VirtualShadowMapPageAccessCommon.ush의 ShadowVirtualToPhysicalUV가 그 번역기를 보여준다.

VirtualShadowMapPageAccessCommon.ush:330

// Finds the best-resolution mapped page at the given UV FShadowPageTranslationResult ShadowVirtualToPhysicalUV(FVirtualShadowMapHandle VirtualShadowMapHandle, float2 ShadowMapUV, uint MinMipLevel) { uint2 vPage = uint2(ShadowMapUV * VSM_LEVEL0_DIM_PAGES_XY); FShadowPhysicalPage PhysicalPageEntry = ShadowGetPhysicalPage(CalcPageOffset(VirtualShadowMapHandle, MinMipLevel, vPage >> MinMipLevel)); FShadowPageTranslationResult Result; Result.bValid = PhysicalPageEntry.bAnyLODValid; Result.LODOffset = VirtualShadowMapHandle.IsSinglePage() ? (VSM_MAX_MIP_LEVELS - 1U) : (PhysicalPageEntry.LODOffset + MinMipLevel); // TODO: Can optimize this slightly based on relative offset Result.VirtualTexelAddressFloat = ShadowMapUV * float(CalcLevelDimsTexels(Result.LODOffset)); Result.VirtualTexelAddress = uint2(Result.VirtualTexelAddressFloat); Result.PhysicalTexelAddress = PhysicalPageEntry.PhysicalAddress * VSM_PAGE_SIZE + (Result.VirtualTexelAddress & VSM_PAGE_SIZE_MASK); return Result; }
🔤 기호 사전 — 가상 uv를 물리 텍셀로 번역
• ShadowMapUV = 섀도맵 안에서의 0~1 좌표. 종이 지도 위 위치라고 보면 돼.
• uint2 vPage = uv가 속한 가상 페이지 좌표.
• ShadowGetPhysicalPage(...) = 페이지 테이블을 읽어 실제 물리 페이지 정보를 가져온다.
• Result.bValid = 이 페이지가 실제로 유효한지 여부.
• LODOffset = 원하는 해상도 페이지가 없으면 더 거친 mip을 볼 때 쓰는 단계 차이.
• PhysicalPageEntry.PhysicalAddress * VSM_PAGE_SIZE = 물리 페이지 시작 텍셀 주소.
• Result.VirtualTexelAddress & VSM_PAGE_SIZE_MASK = 페이지 안쪽에서 몇 번째 칸인지 구한다.
• return Result = 번역 결과를 호출한 셰이더에게 돌려준다.
🔁 이제 다시 보자. ShadowMapUV로 가상 페이지 vPage를 찾고 → ShadowGetPhysicalPage로 사물함 번호를 읽고 → VirtualTexelAddress로 페이지 안쪽 위치를 계산하고 → PhysicalTexelAddress로 진짜 창고 좌표를 만든다. 이걸 끝내야 비로소 깊이 값을 읽을 수 있어.

이 코드가 VSM의 이름값을 한다.

가상 주소를 그대로 쓰지 않고, 페이지 테이블을 통해 물리 주소로 바꾼다.

그래서 "Virtual Shadow Map"이 단순한 마케팅 이름이 아니야. 코드가 진짜로 페이지 테이블과 물리 페이지 풀을 들고 움직인다.

6. 캐시는 왜 중요하나

사물함을 매일 전부 비우면 여전히 비싸. 그래서 VSM은 "어제 그린 페이지가 오늘도 쓸 수 있나?"를 계속 본다. 정적인 벽, 바닥, 큰 건물 그림자는 카메라가 조금 움직여도 같은 물리 페이지를 재사용할 수 있다.

반대로 움직인 프리미티브, WPO로 흔들리는 메시, 새로 드러난 물체는 캐시를 깨야 한다. VirtualShadowMapCacheManager.cpp가 그 기록부 역할을 하고, VirtualShadowMapPhysicalPageManagement.usf가 실제 사물함 배정을 한다.

그래서 VSM의 어려움은 "페이지를 적게 렌더하자"에서 끝나지 않는다. 안 바뀐 페이지는 살리고, 바뀐 페이지만 죽이는 것까지 해야 진짜 성능이 나온다. 우리 서버의 관심 영역 캐시처럼, 무효화를 놓치면 클라 상태가 틀리듯 VSM도 그림자가 남거나 빠진다.

보이는 픽셀 → 필요한 페이지 표시 → 물리 페이지 배정 → 그 페이지만 그림자 렌더 → 샘플링 때 주소 번역

우리 서버·DirectX 랑 비교

서버 감각으로 보면 VSM은 세션 객체를 전 유저 수만큼 만들지 않는 설계야. 유저 ID 공간은 넓지만 실제 접속 세션만 만들듯, 가상 섀도맵은 크지만 필요한 물리 페이지만 할당한다. 관심 영역에 들어온 객체만 패킷을 만들듯, 화면 픽셀이 참조하는 페이지에만 요청 플래그를 찍는다.

DirectX 감각으로 보면 VSM은 타일드 리소스 사고방식에 가깝다. 셰이더에서 큰 텍스처를 보는 척하지만, 실제로는 페이지 테이블을 통해 물리 텍스처 배열의 어느 부분을 볼지 결정한다. SRV로 표를 읽고, UAV로 물리 풀에 쓰고, RDG가 패스 사이 의존성을 묶는다. 앞에서 배운 rdg, rhi-resources, shadow-maps가 여기서 한꺼번에 만난다.

단, VSM은 OS 가상 메모리처럼 페이지 폴트가 자동으로 나서 CPU가 처리해주는 구조가 아니야. 화면에서 필요한 페이지 표시, 물리 페이지 배정, 물리 풀 렌더, 페이지 테이블 샘플링을 렌더러가 직접 한다. 운영체제가 아니라 렌더러가 사물함 담당 선생님 역할을 하는 거야.

이 챕터에서 딱 이것만

  • VSM은 큰 섀도맵을 통째로 만드는 기술이 아니라, 큰 가상 주소 공간과 작은 물리 페이지 풀을 연결하는 기술이야.
  • 화면 픽셀이 먼저 PageRequestFlags에 필요한 페이지를 표시한다.
  • AllocateNewPageMappings가 빈 물리 페이지를 꺼내 PageTable에 가상→물리 연결을 적는다.
  • 실제 깊이 렌더링은 PhysicalPagePoolRDG에 쓴다.
  • 샘플링할 때는 ShadowVirtualToPhysicalUV가 가상 uv를 물리 텍셀 주소로 번역한다.
