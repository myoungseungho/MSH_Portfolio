BasePassPixelShader.usf 안으로

언리얼 렌더링 · 21 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "BasePass 픽셀 셰이더가 재질 값을 FGBufferData에 모은 뒤, GBuffer 렌더타깃으로 쓰는 지점"이 잡힌다.

왜 이걸 배워? — 문제의식부터

지난 장에서 우리는 BasePass가 GBuffer에 재질 정보를 눕힌다고 배웠어. 서버로 치면 "클라가 보낸 패킷을 파싱해서 구조체에 담는다"까지 본 거야. 그런데 아직 제일 중요한 질문이 남았지. 진짜로 어느 코드가 화면의 GBuffer 칸에 값을 쓰냐?

DirectX를 조금 해봤으면 SV_Target0, SV_Target1 같은 걸 기억할 거야. 픽셀 셰이더가 여러 렌더타깃에 동시에 값을 뱉으면, GPU가 그 픽셀 위치의 여러 텍스처 칸을 한 번에 채워. 디퍼드 렌더링은 이걸 크게 써먹는다. 한 픽셀에 색 하나만 쓰는 게 아니라 노멀, 베이스컬러, 러프니스, 셰이딩 모델, 그림자 마스크 같은 표를 여러 장 써두는 거야.

이걸 모르면 뭐가 터질까? 라이팅 장에서 GBuffer.WorldNormal이나 GBuffer.Roughness를 읽는 코드를 봐도 "이 값이 대체 어디서 왔지?" 하고 길을 잃어. 렌더독에서 GBufferA/B/C를 열어봐도 A가 노멀인지, B가 러프니스인지, C가 베이스컬러인지 감이 안 와. 그러면 디버깅은 색깔 맞추기 놀이가 아니라 점쟁이 놀이가 돼.

언리얼도 같은 문제를 만났고, 답은 BasePassPixelShader.usf 안의 FGBufferData와 Out.MRT[] 흐름이야. 재질 그래프에서 나온 값은 먼저 PixelMaterialInputs와 MaterialParameters로 정리되고, 그 다음 FGBufferData GBuffer라는 운송장에 적히고, 마지막에 EncodeGBufferToMRT(Out, GBuffer, ...)로 여러 렌더타깃 칸에 들어간다.

왜 지금 배우냐면 순서가 딱 여기야. 앞 장 basepass-gbuffer는 "BasePass가 GBuffer를 만든다"는 C++ 쪽 지도였고, 이번 장은 그 지도의 가장 안쪽 방, 실제 픽셀 셰이더 쓰기 지점이야. 다음 장 deferred-lighting에서 빛은 이 표를 읽기만 해. 그러니까 지금 여기서 "누가 표를 썼는지"를 잡고 가야 다음 장이 읽힌다.

0. 비유부터 — 택배 분류장 송장 쓰기

택배 분류장을 떠올려보자. 상자 하나가 들어오면 직원이 눈으로 보고 바로 트럭에 싣지 않아. 먼저 송장을 붙여.

송장에는 이런 게 적혀:

  1. 받는 지역
  2. 깨지기 쉬운 물건인지
  3. 냉장인지
  4. 무게가 얼마인지
  5. 어느 컨베이어 벨트로 보내야 하는지

렌더링도 비슷해. 픽셀 하나가 들어오면 바로 "최종 색"을 계산하지 않아. BasePass 직원이 먼저 송장을 써. 이 송장이 GBuffer야.

택배 상자 = 픽셀. 상자 재질과 상태 = 머티리얼 결과. 송장 = FGBufferData. 컨베이어 벨트 여러 개 = Out.MRT[0], Out.MRT[1], Out.MRT[2] 같은 렌더타깃. 나중에 배송 계획 짜는 직원 = 디퍼드 라이팅.

중요한 건 이거야. BasePass는 빛을 전부 계산하는 장면이 아니야. BasePass는 "나중에 빛 계산할 사람이 읽을 수 있게 픽셀 송장을 정리해서 여러 장부에 쓰는 장면"이야.

이번 장은 그 송장 쓰는 손을 따라간다.

🌱 이 개념은 왜 생겼나 — 픽셀 셰이더 출력 상자(Out)
• 원래 구조: 작은 셰이더는 그냥 return float4(color, 1) 하나만 하면 됐어. 상자 하나 보고 최종 색 스티커 하나만 붙이는 구조야.
• 그런데 문제: 디퍼드 렌더링은 한 픽셀에 색만 쓰면 안 돼. 노멀, 러프니스, 셰이딩 모델, 속도 같은 송장 칸을 여러 장부에 같이 써야 다음 직원이 안 헤매.
• 그래서 필요한 것: 함수 밖으로 여러 칸을 들고 나가는 출력 상자가 필요해. 그게 FPixelShaderOut Out이고, 이름 그대로 "밖으로 나갈 값들"을 담는 상자야.

1. 셰이더의 작업대 — FPixelShaderInOut_MainPS

먼저 BasePass 픽셀 셰이더의 실제 몸통으로 들어가자. 여기서 Out이 나와. 나중에 GBuffer 렌더타깃으로 연결되는 출력 상자야.

BasePassPixelShader.usf:890

void FPixelShaderInOut_MainPS( FVertexFactoryInterpolantsVSToPS Interpolants, FBasePassInterpolantsVSToPS BasePassInterpolants, in FPixelShaderIn In, inout FPixelShaderOut Out, const uint EyeIndex, uint QuadPixelWriteMask=1, uint2 QuadPixelPos=0, bool bQuadShadingEnabled=false) { // Velocity float4 OutVelocity = 0; // CustomData float4 OutGBufferD = 0; // PreShadowFactor float4 OutGBufferE = 0; FMaterialPixelParameters MaterialParameters = GetMaterialPixelParameters(Interpolants, In.SvPosition); FPixelMaterialInputs PixelMaterialInputs;
🔤 기호 사전 — 픽셀 셰이더 작업대
• void = 이 함수는 호출한 쪽에 값을 return하지 않는다는 뜻이야. 대신 Out 같은 출력 상자를 바꿔.
• in = 입력으로 받는 값. "읽는 쪽"이라고 보면 돼.
• inout = 들어오기도 하고 나가기도 하는 값. 함수 안에서 고쳐서 바깥으로 넘긴다.
• FPixelShaderOut Out = 픽셀 셰이더가 여러 렌더타깃에 쓸 출력 상자.
• uint = 음수 없는 정수. 비트마스크나 인덱스에 자주 쓴다.
• uint2 = 정수 두 개짜리 묶음. 여기서는 픽셀 좌표 같은 데 쓴다.
• float4 = 실수 네 개 묶음. 보통 RGBA처럼 네 칸짜리 값을 담는다.
• = 0 = 일단 전부 0으로 비워두고 시작한다는 뜻.
• GetMaterialPixelParameters(...) = 이 픽셀의 위치, 노멀, 카메라 방향 같은 재질 계산 재료를 만든다.
🔁 이제 다시 보자. FPixelShaderInOut_MainPS는 BasePass 픽셀 셰이더의 작업대야. Interpolants와 In으로 픽셀 정보를 받고 → OutVelocity, OutGBufferD, OutGBufferE 같은 보조 출력 칸을 비워두고 → MaterialParameters와 PixelMaterialInputs라는 재료 계산 상자를 준비한다. 택배 분류장으로 치면 상자가 들어오자마자 빈 송장과 빈 보조 스티커를 꺼내는 장면이야.

여기서 아직 GBuffer에 뭘 쓴 건 아니야. 그냥 작업대가 열렸고, 출력 상자인 Out이 함수 안으로 들어왔어. 서버 코드로 치면 HandlePacket(Session&, PacketReader&)가 시작되면서 세션과 리더를 받아온 상태랑 비슷해.

OutGBufferD, OutGBufferE 이름도 잘 봐둬. 뒤에서 CustomData, PreShadowFactor 같은 별도 송장 칸으로 이어진다. 하지만 진짜 중심은 아직 안 나왔어. 바로 FGBufferData야.

🌱 이 개념은 왜 생겼나 — FGBufferData
• 원래 구조: 재질에서 나온 값을 바로 렌더타깃 칸에 써도 될 것 같아. 베이스컬러는 여기, 러프니스는 저기, 이렇게 손으로 적는 식이야.
• 그런데 문제: 픽셀마다 적을 항목이 10개 넘게 늘어나면 금방 헷갈려. 어떤 길은 노멀을 쓰고 어떤 길은 셰이딩 모델을 빼먹으면, 나중에 라이팅 직원은 찢어진 송장을 받는 셈이야.
• 그래서 필요한 것: 먼저 한 장짜리 임시 송장에 전부 모아야 해. FGBufferData는 이름 그대로 GBuffer에 들어갈 데이터를 담는 송장 양식이야.
🧱 먼저 알아야 할 것 — 표면의 성질을 숫자로 적는다
• 표면이 바라보는 쪽(노멀): 물체 겉면의 한 점이 어느 쪽을 향하는지야. 바닥에 연필을 수직으로 꽂으면 그 연필이 가리키는 방향이 그 자리의 바라보는 쪽이야. 빛이 어느 각도로 닿는지 따질 때 이게 필요해.
• 매끈한가 거친가 / 쇠붙이인가: 같은 모양이라도 젖은 유리, 마른 나무, 쇠는 빛을 다르게 되돌려. 그래서 "얼마나 거친지", "쇠붙이인지" 같은 성질도 숫자로 적어둬.
• 그래서 한 점마다 색만이 아니라 성질표를 적어둔다: 나중에 빛을 계산할 사람이 "이 점은 이쪽을 보고, 이만큼 거칠고, 쇠붙이"라고 읽을 수 있게.
이게 잡히면 아래 송장 양식(FGBufferData) 칸 설명이 얹힌다.

2. 송장 양식 — FGBufferData

GBuffer는 그냥 텍스처 몇 장이 아니야. 셰이더 안에서는 먼저 구조체 하나로 다룬다. 그 구조체가 FGBufferData야.

DeferredShadingCommon.ush:335

struct FGBufferData { // normalized half3 WorldNormal; // normalized, only valid if HAS_ANISOTROPY_MASK in SelectiveOutputMask half3 WorldTangent; // 0..1 (derived from BaseColor, Metalness, Specular) half3 DiffuseColor; // 0..1 (derived from BaseColor, Metalness, Specular) half3 SpecularColor; // 0..1, white for SHADINGMODELID_SUBSURFACE_PROFILE and SHADINGMODELID_EYE (apply BaseColor after scattering is more correct and less blurry) half3 BaseColor; // 0..1 half Metallic; // 0..1 half Specular; // 0..1 float4 CustomData; // AO utility value half GenericAO; // Indirect irradiance luma half IndirectIrradiance; // Static shadow factors for channels assigned by Lightmass // Lights using static shadowing will pick up the appropriate channel in their deferred pass half4 PrecomputedShadowFactors; // 0..1 half Roughness; // -1..1, only valid if only valid if HAS_ANISOTROPY_MASK in SelectiveOutputMask half Anisotropy; // 0..1 ambient occlusion e.g.SSAO, wet surface mask, skylight mask, ... half GBufferAO; // Bit mask for occlusion of the diffuse indirect samples uint DiffuseIndirectSampleOcclusion; // 0..255 uint ShadingModelID;
🔤 기호 사전 — GBuffer 송장 양식
• struct = 여러 값을 한 상자에 묶는 양식. 택배 송장 양식지라고 보면 돼.
• half3 = 절반 정밀도 실수 세 개. 색이나 방향처럼 세 칸짜리 값을 싸게 담는다.
• half = float보다 가벼운 실수. GPU 메모리와 대역폭을 아끼려고 쓴다.
• float4 = 실수 네 개. 커스텀 데이터처럼 네 칸을 한 번에 담을 때 편해.
• uint = 음수 없는 정수. ShadingModelID 같은 번호표에 쓴다.
• WorldNormal = 월드 공간 노멀. 빛이 어느 방향에서 때리는지 계산할 때 핵심이야.
• BaseColor = 머티리얼의 기본 색.
• Metallic, Specular, Roughness = PBR 재질의 대표 속성. 다음 빛 계산의 재료야.
• ShadingModelID = 이 픽셀이 기본 조명인지, 헤어인지, 클리어코트인지 알려주는 번호표.

이 구조체를 보면 BasePass가 뭘 저장하려는지 딱 보인다. 최종 색 하나가 아니라 "나중에 빛 계산자가 필요한 재질 신분증"을 저장한다. 택배 비유로 치면 WorldNormal은 상자의 방향, Roughness는 포장 표면의 거칠기, ShadingModelID는 취급주의 종류야.

중요한 건 FGBufferData 자체는 아직 렌더타깃이 아니라는 거야. 이건 셰이더 내부의 임시 송장 상자다. 나중에 이 상자를 Out.MRT[]라는 실제 장부 칸에 포장해서 쓴다.

🌱 이 개념은 왜 생겼나 — 셰이딩 모델
• 원래 구조: 모든 재질을 같은 방식으로 빛낸다고 생각하면 단순해. 상자는 전부 같은 배송 규칙으로 처리하는 거야.
• 그런데 문제: 언릿은 빛을 얹으면 안 되고, 클리어코트는 겉 코팅 반사가 따로 있고, 피부 같은 재질도 규칙이 달라. 다 같은 규칙이면 물건 종류 스티커를 무시한 배송이 돼.
• 그래서 필요한 것: "이 픽셀은 어떤 빛 계산법을 써야 해"라는 번호표가 필요해. 그게 셰이딩 모델이고, SetGBufferForShadingModel은 송장에 그 취급 종류를 찍어주는 단계야.

3. 빈 송장을 만들고, 셰이딩 모델로 기본 칸을 채운다

이제 BasePass 몸통으로 돌아오자. FGBufferData는 여기서 0으로 초기화된다. 그리고 몇 개 기본 칸이 바로 채워져.

BasePassPixelShader.usf:1129

FGBufferData GBuffer = (FGBufferData)0; GBuffer.GBufferAO = MaterialAO; GBuffer.PerObjectGBufferData = GetPrimitive_PerObjectGBufferData(MaterialParameters.PrimitiveId); GBuffer.Depth = MaterialParameters.ScreenPosition.w; GBuffer.PrecomputedShadowFactors = GetPrecomputedShadowMasks(LightmapVTPageTableResult, Interpolants, MaterialParameters, VolumetricLightmapBrickTextureUVs); #if !SUBSTRATE_ENABLED || SUBSTRATE_INLINE_SINGLELAYERWATER // Use GBuffer.ShadingModelID after SetGBufferForShadingModel(..) because the ShadingModel input might not be the same as the output SetGBufferForShadingModel( GBuffer, MaterialParameters, PixelMaterialInputs, Opacity, BaseColor, Metallic, Specular, Roughness, Anisotropy, SubsurfaceColor, SubsurfaceProfile, Dither, ShadingModel );
🔤 기호 사전 — 빈 송장과 기본 입력
• (FGBufferData)0 = FGBufferData 모양의 상자를 만들고 모든 칸을 0으로 비운다.
• . = 구조체 안의 칸을 찍어서 고르는 표시. GBuffer.Depth는 GBuffer 안의 Depth 칸.
• MaterialAO = 머티리얼 쪽 앰비언트 오클루전 값.
• PrimitiveId = 지금 그려지는 프리미티브의 번호표.
• ScreenPosition.w = 화면 위치 정보 중 깊이 복원에 쓰이는 값.
• #if = 컴파일할 때 조건에 따라 이 코드 조각을 넣거나 뺀다.
• SetGBufferForShadingModel(...) = 셰이딩 모델에 맞게 GBuffer 칸들을 채우는 함수.
• GBuffer, = 여기서는 함수에 송장 상자를 넘겨서 안쪽 칸을 채우게 한다.
🔁 이제 다시 보자. FGBufferData GBuffer = (FGBufferData)0으로 빈 송장을 만들고 → AO, 오브젝트 데이터, 깊이, 정적 그림자 마스크를 먼저 적고 → SetGBufferForShadingModel(...)에 베이스컬러, 메탈릭, 스페큘러, 러프니스, 셰이딩 모델을 넘긴다. 택배 직원이 빈 송장에 "지역, 무게, 취급 종류"를 먼저 적는 장면이야.

여기서 한 가지 조심해야 해. ShadingModel 입력값이 곧바로 최종 GBuffer.ShadingModelID라고 단정하면 안 돼. 코드 주석도 말하잖아. SetGBufferForShadingModel(..) 뒤의 GBuffer.ShadingModelID를 쓰라고. 재질 입력과 최종 저장 모델이 중간에서 바뀔 수 있다는 뜻이야.

서버로 치면 클라가 보낸 CM_ATTACK 원문을 그대로 믿지 않고, 서버 검증 뒤에 내부 명령 타입으로 다시 정규화하는 느낌이야. BasePass도 재질 입력을 바로 렌더타깃에 쓰지 않고 GBuffer라는 내부 송장으로 한 번 정리한다.

4. 재질 값을 빛 계산용 값으로 다듬는다

SetGBufferForShadingModel이 기본 칸을 채운 뒤에도 끝이 아니야. BasePass는 빛 계산용으로 SpecularColor, Roughness, DiffuseColor 같은 값을 다시 다듬는다.

BasePassPixelShader.usf:1223

// So that the following code can still use DiffuseColor and SpecularColor. GBuffer.SpecularColor = ComputeF0(Specular, BaseColor, Metallic); #if MATERIAL_NORMAL_CURVATURE_TO_ROUGHNESS const float GeometricAARoughness = GetRoughnessFromNormalCurvature(MaterialParameters); GBuffer.Roughness = max(GBuffer.Roughness, GeometricAARoughness); #if MATERIAL_SHADINGMODEL_CLEAR_COAT if (GBuffer.ShadingModelID == SHADINGMODELID_CLEAR_COAT) { GBuffer.CustomData.y = max(GBuffer.CustomData.y, GeometricAARoughness); } #endif #endif #if POST_PROCESS_SUBSURFACE // SubsurfaceProfile applies the BaseColor in a later pass. Any lighting output in the base pass needs // to separate specular and diffuse lighting in a checkerboard pattern if (UseSubsurfaceProfile(GBuffer.ShadingModelID)) { AdjustBaseColorAndSpecularColorForSubsurfaceProfileLighting(BaseColor, GBuffer.SpecularColor, Specular, bChecker); } #endif GBuffer.DiffuseColor = BaseColor - BaseColor * Metallic;
🔤 기호 사전 — 재질값 다듬기
• ComputeF0(...) = PBR에서 정면 반사율을 계산하는 함수. 스페큘러 색의 출발점이야.
• const = 한 번 정하면 아래에서 바꾸지 않는 값.
• max(a, b) = 둘 중 큰 값을 고른다. 러프니스를 너무 낮게 두지 않게 막는다.
• if (...) = 조건이 참일 때만 안쪽을 실행한다.
• == = 두 값이 같은지 비교한다.
• && = 두 조건이 둘 다 참이어야 한다는 뜻.
• BaseColor - BaseColor * Metallic = 금속일수록 diffuse 몫을 줄이는 계산.
🔁 이제 다시 보자. 이 토막은 ComputeF0로 스페큘러 색을 만들고 → 노멀 곡률 때문에 필요한 러프니스 보정을 하고 → 서브서피스 예외를 처리하고 → DiffuseColor = BaseColor - BaseColor * Metallic으로 diffuse 몫을 확정한다. 택배 송장에 "색"만 적는 게 아니라 실제 배송 규칙에 맞는 취급 등급으로 바꾸는 과정이야.

여기서 핵심은 BaseColor와 DiffuseColor가 같은 말이 아니라는 점이야. BaseColor는 재질의 원래 색에 가깝고, DiffuseColor는 메탈릭 같은 물리 규칙을 반영한 뒤 빛 계산에 쓸 확산색이야. 금속은 확산 반사가 거의 없으니까 BaseColor - BaseColor * Metallic 같은 계산이 들어간다.

Roughness도 그냥 머티리얼 입력을 믿고 끝내지 않아. 노멀 곡률 aliasing을 줄이려고 GeometricAARoughness를 써서 올릴 수 있어. 즉 BasePass는 단순 저장소가 아니라 "나중에 읽기 좋은 형태로 재질을 가공하는 접수대"야.

🌱 이 개념은 왜 생겼나 — MRT와 EncodeGBufferToMRT
• 원래 구조: 픽셀 셰이더가 렌더타깃 하나에 색 하나만 쓰면 돼. 컨베이어 벨트가 하나뿐인 분류장이야.
• 그런데 문제: GBuffer는 같은 픽셀 위치에 노멀, 베이스컬러, 러프니스 같은 장부를 여러 장 써야 해. 1920×1080 픽셀을 장부마다 따로 돌리면 손이 너무 많이 가고, 서로 맞물린 송장도 어긋나기 쉬워.
• 그래서 필요한 것: 한 번 분류할 때 여러 렌더타깃에 동시에 쓰는 길이 필요해. MRT는 Multiple Render Targets, 여러 장부 출력이고 EncodeGBufferToMRT는 송장을 그 장부 칸들에 압축해서 베껴 쓰는 호출이야.

5. 진짜 기록 지점 — EncodeGBufferToMRT

이제 드디어 송장을 장부에 쓰는 장면이다. BasePass는 GBuffer 구조체를 다 채운 뒤, USES_GBUFFER 경로에서 인코딩한다. 현재 활성 경로는 #if 1 아래의 EncodeGBufferToMRT 호출이야.

BasePassPixelShader.usf:2299

#if USES_GBUFFER // -0.5 .. 0.5, could be optimzed as lower quality noise would be sufficient float QuantizationBias = PseudoRandom( MaterialParameters.SvPosition.xy ) - 0.5f; GBuffer.IndirectIrradiance = IndirectIrradiance; GBuffer.NormalDistribution = 0.0f; // this is the new encode, the older encode is the #else, keeping it around briefly until the new version is confirmed stable. #if 1 { // change this so that we can pack everything into the gbuffer, but leave this for now #if GBUFFER_HAS_DIFFUSE_SAMPLE_OCCLUSION GBuffer.GenericAO = float(GBuffer.DiffuseIndirectSampleOcclusion) * (1.0f / 255.0f); #elif ALLOW_STATIC_LIGHTING // No space for AO. Multiply IndirectIrradiance by AO instead of storing. GBuffer.GenericAO = EncodeIndirectIrradiance(GBuffer.IndirectIrradiance * GBuffer.GBufferAO) + QuantizationBias * (1.0 / 255.0); // Stationary sky light path #else GBuffer.GenericAO = GBuffer.GBufferAO; // Movable sky light path #endif EncodeGBufferToMRT(Out, GBuffer, QuantizationBias); if (GBuffer.ShadingModelID == SHADINGMODELID_UNLIT && (!SUBSTRATE_ENABLED || SUBSTRATE_GBUFFER_FORMAT==0)) // Do not touch what Substrate outputs with Format=1 { Out.MRT[1] = 0; SetGBufferForUnlit(Out.MRT[2]);
🔤 기호 사전 — GBuffer 기록 출구
• USES_GBUFFER = 이번 셰이더 변형이 GBuffer를 쓰는 경로인지 나타내는 컴파일 조건.
• QuantizationBias = 값을 적은 비트 수에 구겨 넣을 때 생기는 계단 현상을 줄이려고 넣는 작은 랜덤 흔들림.
• PseudoRandom(...) = 픽셀 위치에서 가짜 랜덤 값을 만든다.
• #elif, #else, #endif = 컴파일 조건 분기의 다른 갈래와 끝.
• GenericAO = 상황에 따라 AO나 간접광 정보를 압축해서 담는 공용 칸.
• EncodeIndirectIrradiance(...) = 간접광 밝기를 저장 가능한 형태로 바꾸는 함수.
• EncodeGBufferToMRT(Out, GBuffer, QuantizationBias) = 채워진 GBuffer 송장을 Out.MRT[] 렌더타깃 출력으로 포장해서 쓰는 핵심 호출.
• Out.MRT[1] = 픽셀 셰이더 출력 배열의 1번 칸. 실제 렌더타깃 하나로 이어진다.
• SHADINGMODELID_UNLIT = 빛 계산이 필요 없는 언릿 재질 번호.
🔁 이제 다시 보자. USES_GBUFFER 경로에 들어오면 → 픽셀 위치 기반 QuantizationBias를 만들고 → 간접광과 AO를 저장 가능한 GenericAO로 정리하고 → EncodeGBufferToMRT(Out, GBuffer, QuantizationBias)를 호출한다. 이 한 줄이 이번 챕터의 목적지야. 송장(GBuffer)을 실제 장부 묶음(Out.MRT[])에 베껴 쓰는 순간이지.

이 코드에서 제일 중요한 줄은 딱 하나야.

EncodeGBufferToMRT(Out, GBuffer, QuantizationBias);

이 줄 이전까지는 "송장 작성"이고, 이 줄부터는 "장부 기록"이야. 렌더독에서 보이는 GBuffer 텍스처들은 이 출력 경로의 결과물이라고 보면 된다.

그리고 바로 아래 언릿 예외를 보자. GBuffer.ShadingModelID == SHADINGMODELID_UNLIT이면 일부 GBuffer 칸을 0으로 밀거나 SetGBufferForUnlit을 써. 왜냐면 언릿은 나중에 디퍼드 라이팅이 보통 재질처럼 빛을 얹으면 안 되거든. 송장에 "이 상자는 배송 계획에서 빼라"는 특별 스티커를 붙이는 셈이야.

Out.MRT[]는 여기서 끝나는 임시 배열이 아니야. 공통 출력 래퍼가 PixelShaderOut.MRT[n]을 OutTargetN으로 옮기고, 그 OutTargetN이 DirectX의 SV_TargetN 렌더타깃 출력으로 나간다.

이제 렌더독에서 GBuffer를 보면 다르게 보여야 해. 그건 마법 텍스처가 아니야. BasePass 직원이 픽셀마다 손으로 쓴 송장 묶음이야. 나중에 라이팅 패스는 그 송장을 읽고 "이 픽셀은 노멀이 이쪽이고, 거칠기는 이 정도고, 셰이딩 모델은 이거니까 빛을 이렇게 얹자"라고 판단한다.

7. 우리 서버·DirectX 랑 비교

서버 쪽 감각으로 보면 이 흐름은 패킷 파싱이랑 꽤 닮았어.

클라가 날 바이트를 보내면 우리 서버는 바로 게임 로직을 실행하지 않아. 먼저 헤더를 읽고, 길이를 확인하고, CM_* 구조체로 정리하고, 세션 상태와 권한을 붙여. 그 다음에야 게임 로직 큐로 넘긴다.

BasePass도 같아.

머티리얼에서 나온 값이 바로 최종 라이팅으로 가지 않아. 먼저 FGBufferData로 정리하고, 셰이딩 모델별 예외를 반영하고, AO와 러프니스 같은 값을 보정하고, 그 다음 Out.MRT[]로 내보낸다.

DirectX 감각으로 보면 In.SvPosition은 SV_Position, Out.MRT[n]은 결국 SV_TargetN으로 이어지는 출력 묶음이야. 우리가 손으로 짠 샘플은 보통 return float4(color, 1) 하나로 끝나지만, 언리얼 BasePass는 픽셀 하나에 대해 BaseColor, Roughness, ShadingModelID, Velocity 같은 정보를 여러 장으로 나눠 쓴다.

그리고 서버와 달리 여기서는 락이 문제가 아니야. GPU는 픽셀 수만큼 엄청 많이 병렬로 이 함수를 돌린다. 각 픽셀은 자기 위치의 렌더타깃 칸만 쓴다. 그러니까 공유 객체 락이 아니라 "어떤 값을 어느 렌더타깃 포맷에 어떻게 압축하냐"가 핵심 비용이야.

8. 이 챕터에서 딱 이것만

  • FPixelShaderInOut_MainPS는 BasePass 픽셀 셰이더의 실제 작업대다.
  • FGBufferData는 나중 라이팅이 읽을 픽셀 송장이다.
  • SetGBufferForShadingModel 뒤에야 최종 셰이딩 모델 기준 GBuffer 값을 믿을 수 있다.
  • ComputeF0, DiffuseColor, GBufferAO 같은 보정은 렌더타깃에 쓰기 전 단계에서 일어난다.
  • 진짜 기록 지점은 EncodeGBufferToMRT(Out, GBuffer, QuantizationBias)다.
