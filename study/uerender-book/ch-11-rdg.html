RDG(RenderGraph) — 왜 그래프로 짜나

언리얼 렌더링 · 11 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "렌더 패스를 왜 그냥 순서대로 호출하지 않고 그래프로 모아 실행하는가"가 잡힌다.
🧱 먼저 알아야 할 것 — 순서를 지켜야 하는 일
• 먼저 할 일과 나중 할 일: 밥을 안 지었는데 덮밥을 담을 수 없고, 라면 물을 안 끓였는데 면을 넣을 수 없어. 어떤 일은 다른 일이 끝나야만 시작할 수 있어서, 순서를 안 지키면 망가져.
이게 잡히면 아래 일의 순서를 그래프로 짜는 설명이 얹힌다.

왜 이걸 배워? — 문제의식부터

서버에서 패킷 처리 순서를 많이 봤을 거야. CM_MOVE가 와야 위치를 갱신하고, 그 뒤에야 주변 유저에게 SP_MOVE를 뿌릴 수 있지. DirectX도 처음엔 비슷해 보여. "렌더타깃 만들고, 패스 A 그리고, 패스 B 그리고, Present 하면 되지 않나?" 작은 예제면 맞아.

그런데 UE 한 프레임은 깊이 PrePass, BasePass, Shadow, Lumen, Translucency, PostProcess가 줄줄이 붙어. 패스 수가 수십 개를 넘고, 임시 텍스처도 수백 개가 오가면 사람이 모든 읽기/쓰기 순서와 barrier를 기억할 수 없어. 너무 오래 붙잡으면 GPU 메모리가 터지고, 너무 일찍 반납하면 다음 패스가 죽은 텍스처를 읽는다.

언리얼도 같은 문제를 만났고, 답이 RDG야. Render Dependency Graph, 즉 렌더 패스 사이의 의존성 그래프를 먼저 만들고 실행 순서, barrier, 리소스 수명을 엔진이 계산한다.

그래서 지금 배워야 해. 앞에서 RHI 명령, 리소스, PSO, 셰이더 파라미터를 봤고, 다음 권부터는 GraphBuilder.AddPass가 계속 나온다. RDG를 모르면 "람다 안에서 뭔가 그리네"에서 멈춘다.

0. 비유부터 — 주방 전체 주문 보드

식당 주방을 떠올려봐. 밥을 안 지었는데 덮밥을 완성할 수 없고, 팬을 안 씻었는데 다음 소스를 부으면 맛이 섞인다. 그래서 큰 주방에는 주문 보드가 있어.

RDG가 딱 그 주문 보드야. 패스는 요리 단계고, 텍스처/버퍼는 팬과 접시야. barrier는 "이 팬 씻고 넘겨"라는 표지판이고, lifetime은 "이 접시는 3번부터 5번 요리까지만 필요"라는 대여표야.

중요한 건 하나야. RDG는 패스를 등록할 때 바로 실행하지 않는다. 먼저 보드에 다 적고, 전체를 본 뒤 순서와 barrier와 반납 시점을 정한다.

소스 위치 (이 챕터 코드는 전부 이 파일에서 그대로 뽑음)
• 구현: Engine/Source/Runtime/RenderCore/Private/RenderGraphBuilder.cpp
🌱 이 개념은 왜 생겼나 — RDG(RenderGraph)
• 원래 구조: 작은 DirectX 예제처럼 패스 A 실행하고, 패스 B 실행하고, 마지막에 Present 하면 돼. 팬과 접시는 개발자가 손으로 챙기는 구조야.
• 그런데 문제: UE 한 프레임은 요리가 수십 개고 임시 접시가 수백 개야. 8번 요리가 만든 접시를 12번이 읽는데 10번에서 반납하면 바로 깨져.
• 그래서 필요한 것: 한 프레임 주문을 먼저 보드에 다 붙이고, 누가 누구 뒤에 와야 하는지 전체를 본 뒤 실행해야 해. 그래서 Render Dependency Graph, 줄여서 RDG야.
🧱 먼저 알아야 할 것 — 적어만 두고 나중에 한다
• 주문 적어두기: 식당에서 주문을 받을 때 요리사가 바로 불 앞으로 뛰지 않아. 주문서에 먼저 다 적어두고, 주문이 모이면 그때 순서를 정해 요리해. 적는 것과 실제로 하는 것은 다른 시점이야.
이게 잡히면 아래 패스를 바로 실행하지 않고 등록만 해두는 설명이 얹힌다.

1. 패스 등록 — 주문을 바로 만들지 않고 보드에 붙인다

렌더러 코드에서 GraphBuilder에 패스를 추가하면 GPU 명령이 바로 나가지 않아. RenderGraphBuilder.cpp 쪽 핵심 관문인 SetupParameterPass에서 패스 내부 정보와 리소스 분석이 붙는다.

RenderGraphBuilder.cpp:2624

FRDGPass* FRDGBuilder::SetupParameterPass(FRDGPass* Pass) { IF_RDG_ENABLE_DEBUG(UserValidation.ValidateAddPass(Pass)); CSV_SCOPED_TIMING_STAT_EXCLUSIVE_CONDITIONAL(RDGBuilder_SetupPass, GRDGVerboseCSVStats != 0); RDG_EVENT_SCOPE_CONDITIONAL_NAME(*this, ScopeState.ScopeMode == ERDGScopeMode::AllEventsAndPassNames, Pass->GetEventName()); SetupPassInternals(Pass); if (AsyncSetupQueue.bEnabled) { MarkResourcesAsProduced(Pass); AsyncSetupQueue.Push(FAsyncSetupOp::SetupPassResources(Pass)); } else { SetupPassResources(Pass); } SetupAuxiliaryPasses(Pass); return Pass; }
🔤 기호 사전 — 패스 등록 관문
• FRDGPass* = RDG 패스 객체를 가리키는 손잡이야.
• IF_RDG_ENABLE_DEBUG(...) = RDG 디버그 기능이 켜졌을 때만 안쪽 검사를 실행하는 매크로야.
• *this = 지금 이 FRDGBuilder 자기 자신을 값처럼 넘기는 표현이야.
• SetupPassInternals(Pass) = 패스 번호, 파이프라인, 스코프 같은 내부 표찰을 붙이는 단계야.
• AsyncSetupQueue.bEnabled = 리소스 분석을 비동기 큐에 밀어도 되는지 보는 참/거짓 스위치야.
• SetupPassResources(Pass) = 이 패스가 어떤 텍스처/버퍼를 읽고 쓰는지 훑는 핵심 단계야.
• return Pass = 준비된 패스 손잡이를 호출한 쪽에 돌려준다.
🔁 이제 다시 보자. ValidateAddPass로 주문표가 이상하지 않은지 보고 → SetupPassInternals로 주문 번호를 붙이고 → SetupPassResources를 직접 하거나 큐에 밀고 → SetupAuxiliaryPasses까지 붙인 뒤 패스를 돌려준다. 즉 요리를 만든 게 아니라, 주문 보드에 붙일 준비를 끝낸 거야.

패스 람다를 썼다고 바로 GPU가 도는 게 아니야. 먼저 주문표를 만들고, 그 주문표에 "무슨 접시를 읽고 무슨 팬에 쓰는지"를 적는다.

2. 리소스 분석 — 주문표에서 팬과 접시를 읽는다

RDG는 패스 파라미터를 주문표로 읽는다. 셰이더 파라미터 구조체 안의 RDG 텍스처, SRV, UAV, 렌더타깃을 SetupPassResources가 순회한다. 주문표에 안 적힌 팬을 몰래 쓰면 주방장이 알 수 없듯, 패스가 실제로 쓰는 리소스는 파라미터에 들어가야 해.

RenderGraphBuilder.cpp:2394

EnumerateTextureAccess(PassParameters, PassFlags, [&](FRDGViewRef TextureView, FRDGTextureRef Texture, ERHIAccess Access, ERDGTextureAccessFlags AccessFlags, FRDGTextureSubresourceRange Range) { TryAddView(TextureView); if (Texture->AccessModeState.IsExternalAccess() && !Pass->bExternalAccessPass) { // Resources in external access mode are expected to remain in the same state and are ignored by the graph. // As only External | Extracted resources can be set as external by the user, the graph doesn't need to track // them any more for culling / transition purposes. Validation checks that these invariants are true. IF_RDG_ENABLE_DEBUG(UserValidation.ValidateExternalAccess(Texture, Access, Pass)); return; } const FRDGViewHandle NoUAVBarrierHandle = GetHandleIfNoUAVBarrier(TextureView); const EResourceTransitionFlags TransitionFlags = GetTextureViewTransitionFlags(TextureView, Texture); FRDGPass::FTextureState* PassState; if (Texture->LastPasses[PassPipeline] != PassHandle) { Texture->LastPasses[PassPipeline] = PassHandle; Texture->PassStateIndex = Pass->TextureStates.Num(); PassState = &Pass->TextureStates.Emplace_GetRef(Texture); } else { PassState = &Pass->TextureStates[Texture->PassStateIndex]; } PassState->ReferenceCount++; EnumerateSubresourceRange(PassState->State, Texture->Layout, Range, [&](FRDGSubresourceState*& State) { if (!State) { State = AllocSubresource(); } IF_RDG_ENABLE_DEBUG(UserValidation.ValidateAddSubresourceAccess(Texture, *State, Access)); State->Access = MakeValidAccess(State->Access, Access); State->Flags |= TransitionFlags; State->NoUAVBarrierFilter.AddHandle(NoUAVBarrierHandle); State->SetPass(PassPipeline, PassHandle); });
🔤 기호 사전 — 텍스처 접근 분석
• EnumerateTextureAccess(...) = 패스 파라미터 안의 텍스처 접근을 하나씩 꺼내보는 순회 함수야.
• [&](...) = 람다야. 주변 변수를 빌려 쓰면서, 각 텍스처마다 이 안쪽 코드를 실행한다.
• ERHIAccess Access = 이 리소스를 읽는지, 쓰는지, UAV인지, 렌더타깃인지 같은 GPU 접근 상태야.
• Texture->LastPasses[PassPipeline] = 이 텍스처를 이 파이프라인에서 마지막으로 만진 패스 번호야.
• PassState->ReferenceCount++ = 이 패스가 이 텍스처를 한 번 더 붙잡는다고 카운트를 올린다.
• State->Access = MakeValidAccess(...) = 여러 접근 상태를 RDG가 이해할 수 있는 유효한 상태로 합친다.
• State->Flags |= TransitionFlags = 기존 플래그에 transition 관련 표시를 덧붙인다. |=는 "합쳐서 다시 넣기"야.
🔁 이제 다시 보자. EnumerateTextureAccess가 주문표의 텍스처 칸을 하나씩 읽고 → PassState에 이 패스의 사용 기록을 만들고 → ReferenceCount를 올리고 → subresource마다 Access와 PassHandle을 박는다. 이게 있어야 나중에 "누가 먼저고 누가 나중인지" 계산할 수 있어.

PassParameters는 그냥 C++ 인자 묶음이 아니야. 주방장이 보는 주문표야. DirectX 12에서 직접 상태 전환을 넣던 일을 RDG는 이 주문표의 "읽음/씀" 기록으로 계산한다.

🌱 이 개념은 왜 생겼나 — 의존성 그래프와 culling
• 원래 구조: 주문 보드에 적힌 요리를 그냥 전부 순서대로 만들면 돼. 안 쓰일지도 모르지만 일단 다 해보는 거야.
• 그런데 문제: 마지막 화면에 안 올라가는 중간 요리까지 만들면 GPU 시간이 새고, 임시 접시도 계속 붙잡혀. 손님에게 안 나갈 소스를 20그릇 끓이는 셈이야.
• 그래서 필요한 것: "이 접시는 누가 만들고 누가 먹나"를 선으로 잇고, 최종 접시에서 거꾸로 따라가 필요한 주문만 살려야 해. 안 쓰는 주문을 잘라내는 게 culling이야.

3. 의존성 그래프와 culling — 안 필요한 주문은 만들지 않는다

패스마다 리소스 사용 기록이 생기면 RDG는 "누가 누구 뒤에 와야 하는지"를 계산한다. 어떤 패스가 텍스처를 쓰고 다음 패스가 그 텍스처를 읽으면, 뒤 패스는 앞 패스 뒤에 와야 해. SetupPassDependencies는 텍스처/버퍼 상태를 보면서 reference count를 더하고 producer와 consumer를 잇는다.

RenderGraphBuilder.cpp:2319

void FRDGBuilder::SetupPassDependencies(FRDGPass* Pass) { bool bIsCullRootProducer = false; for (auto& PassState : Pass->TextureStates) { FRDGTextureRef Texture = PassState.Texture; auto& LastProducers = Texture->LastProducers; Texture->ReferenceCount += PassState.ReferenceCount; for (uint32 Index = 0, Count = LastProducers.Num(); Index < Count; ++Index) { const FRDGSubresourceState* SubresourceState = PassState.State[Index]; if (!SubresourceState) { continue; } FRDGProducerState ProducerState; ProducerState.Pass = Pass; ProducerState.Access = SubresourceState->Access; ProducerState.NoUAVBarrierHandle = SubresourceState->NoUAVBarrierFilter.GetUniqueHandle(); bIsCullRootProducer |= AddCullingDependency(LastProducers[Index], ProducerState, Pass->Pipeline) && Texture->IsCullRoot(); } }
🔤 기호 사전 — 의존성 만들기
• bIsCullRootProducer = 이 패스가 culling 탐색의 시작점이 되는 결과를 만드는지 표시하는 bool이야.
• for (auto& PassState : ...) = 배열 원소를 복사하지 않고 참조로 하나씩 만진다.
• LastProducers = 이 리소스를 마지막으로 쓴 패스들 목록이야.
• Texture->ReferenceCount += ... = 이 텍스처가 앞으로 몇 번 더 필요한지 누적한다.
• FRDGProducerState = "이 패스가 이 접근 상태로 리소스를 만들었다"는 기록 상자야.
• AddCullingDependency(...) = 앞 producer와 지금 패스 사이의 의존성을 연결한다.
🔁 이제 다시 보자. 텍스처마다 ReferenceCount를 더하고 → 마지막 producer와 현재 pass를 AddCullingDependency로 잇는다. 같은 함수 아래쪽에서는 버퍼도 같은 식으로 처리하고, culling root만 살려서 손님에게 안 나가는 중간 요리는 만들지 않게 한다.

그래프면 최종 back buffer나 extraction 되는 history texture에서 거꾸로 따라가 필요한 producer만 살릴 수 있다. 서버에서 아무한테도 안 보낼 로그 문자열 작업을 지워도 되는 것과 비슷해. 단, DB 저장처럼 부작용이 있으면 NeverCull 같은 표시가 필요하다.

4. Execute — 이제서야 보드를 컴파일한다

패스를 다 등록했다고 GPU가 바로 돌지는 않는다. FRDGBuilder::Execute()가 주문 보드를 닫고, 먼저 Compile()과 barrier 수집을 건다.

RenderGraphBuilder.cpp:1891

Compile(); CollectPassBarriersTask = AddSetupTask([this] { CompilePassBarriers(); CollectPassBarriers(); }, TaskPriority, bParallelCompileResources);
🔤 기호 사전 — 실행 전 컴파일
• Compile() = 지금까지 모은 패스와 리소스 정보를 보고 그래프를 정리하는 단계야.
• CollectPassBarriersTask = barrier 수집 작업을 담는 task 손잡이야.
• AddSetupTask([this] { ... }) = setup 일을 task로 등록한다. [this]는 빌더 자기 자신을 람다 안에서 쓰겠다는 뜻이야.
• CompilePassBarriers() = 리소스 상태들을 합치고 transition 후보를 준비한다.
• CollectPassBarriers() = 각 패스 앞뒤에 붙을 barrier 묶음을 수집한다.
• TaskPriority = 작업 우선순도야. 렌더 프레임 안에서는 이런 준비 작업도 시간 싸움이다.

Compile()은 reference count, culling, render pass merge, async compute fork/join을 정리한다. 주방장이 주문 접수를 마감하고 "취소할 요리, 이어서 쓸 팬, 씻을 타이밍"을 계산하는 단계야.

등록 단계: AddPass, CreateTexture, RegisterExternalTexture, QueueExtraction 컴파일 단계: dependency, culling, lifetime, barrier 계산 실행 단계: 살아남은 pass의 lambda 실행

이걸 모르면 "왜 텍스처를 만들었는데 아직 RHI texture가 없지?" 같은 질문에서 막힌다. 답은 간단해. 아직 보드에 적는 중이기 때문이야.

🌱 이 개념은 왜 생겼나 — 리소스 수명(lifetime)
• 원래 구조: 텍스처나 버퍼를 만들면 프레임 끝까지 들고 있으면 돼. 접시를 한 번 빌리면 장사 끝날 때까지 안 돌려주는 식이야.
• 그런데 문제: 임시 텍스처가 수백 개면 GPU 메모리가 금방 찬다. 반대로 7번 요리가 아직 읽는 접시를 6번 끝났다고 반납하면 다음 요리가 빈 접시를 읽게 돼.
• 그래서 필요한 것: 각 접시가 몇 번 요리부터 몇 번 요리까지 필요한지 세는 대여표가 필요해. 그 필요한 기간이 바로 lifetime, 리소스 수명이야.
🧱 먼저 알아야 할 것 — 필요할 때만 빌리고 바로 돌려주기
• 빌려 쓰기: 캠핑장 그릇은 내 것이 아니라 빌리는 거야. 쓸 동안만 갖고 있다가 다 쓰면 바로 돌려주면, 같은 그릇을 다음 사람이 또 써. 개수가 적어도 돌려쓰면 충분해.
이게 잡히면 아래 리소스를 필요한 구간에만 빌려 쓰는 설명이 얹힌다.

5. 리소스 수명 — 접시는 필요한 동안만 빌린다

RDG의 큰 이득 중 하나가 임시 리소스 수명이야. CreateTexture로 RDG 텍스처를 만들었다고 즉시 GPU 메모리가 잡히는 게 아니다. 일단 설명서와 이름이 그래프에 들어간다. 실제 allocation은 "이 패스부터 필요하다"가 확정될 때 이뤄진다. 마지막 참조가 끝나면 deallocation 후보로 들어간다.

아래는 텍스처 reference count가 줄다가 0이 되는 순간이야. 0이 되면 transient 또는 pooled 자원 반납 목록에 넣고, DeallocatedReferenceCount로 표시한다.

RenderGraphBuilder.cpp:3656

void FRDGBuilder::CollectDeallocateTexture(FCollectResourceContext& Context, ERHIPipeline PassPipeline, FRDGPassHandle PassHandle, FRDGTexture* Texture, uint32 ReferenceCount) { check(!IsImmediateMode()); check(Texture->ReferenceCount != FRDGViewableResource::DeallocatedReferenceCount); check(Texture->ReferenceCount >= ReferenceCount); Texture->ReferenceCount -= ReferenceCount; Texture->LastPasses[PassPipeline] = PassHandle; if (Texture->ReferenceCount == 0) { check(!Texture->bCollectForAllocate); const FCollectResourceOp DeallocateOp = FCollectResourceOp::Deallocate(Texture->Handle); if (Texture->bTransient) { Context.TransientResources.Emplace(DeallocateOp); } else { Context.PooledTextures.Emplace(DeallocateOp); } Texture->ReferenceCount = FRDGViewableResource::DeallocatedReferenceCount; } }
🔤 기호 사전 — 텍스처 반납
• FCollectResourceContext& Context = allocation/deallocation 작업을 모아두는 장부를 참조로 받는다.
• ERHIPipeline PassPipeline = graphics인지 async compute인지 같은 GPU 파이프라인 표시야.
• FRDGPassHandle PassHandle = 패스를 숫자로 가리키는 손잡이야.
• check(...) = 조건이 깨지면 개발 중에 바로 잡아내는 검사야.
• Texture->ReferenceCount -= ReferenceCount = 이 패스가 끝나면서 필요한 횟수를 줄인다.
• Texture->LastPasses[PassPipeline] = PassHandle = 이 파이프라인에서 이 텍스처를 마지막으로 만진 패스를 기록한다.
• FCollectResourceOp::Deallocate(...) = "이 리소스를 반납하라"는 작업 표를 만든다.
• Context.TransientResources.Emplace(...) = transient allocator 쪽 반납 목록에 넣는다.
• Context.PooledTextures.Emplace(...) = render target pool 쪽 반납 목록에 넣는다.
🔁 이제 다시 보자. ReferenceCount를 줄이고 → 0이 되면 deallocate 작업표를 만들고 → transient면 transient 장부에, 아니면 pooled texture 장부에 넣고 → 마지막에 이미 반납된 상태로 표시한다. 접시를 마지막 요리가 다 쓰자마자 반납 목록에 올리는 거야.

이게 사람이 직접 하면 정말 잘 터지는 부분이다. 렌더러 개발자가 "이 텍스처는 8번 패스까지만 쓰이니까 9번에서 풀어도 됨"을 매번 손으로 세면, 기능 하나 추가될 때마다 수명이 바뀐다. RDG는 pass parameter를 보고 reference count를 세니까, 패스가 추가되거나 빠져도 수명 장부를 다시 계산할 수 있어.

DirectX 12에서 aliasing heap을 직접 굴려봤다면 더 와닿을 거야. 메모리를 재사용하려면 이전 리소스가 끝난 걸 확실히 알아야 한다. RDG는 그 "끝난 시점"을 LastPasses, ReferenceCount, barrier 정보로 잡는다.

🌱 이 개념은 왜 생겼나 — 자동 barrier
• 원래 구조: 개발자가 패스 사이마다 "이 팬은 이제 렌더타깃에서 셰이더 읽기용으로 바꿔"라고 손으로 표지판을 세우면 돼.
• 그런데 문제: 패스가 수십 개로 늘면 표지판 하나만 빠져도 GPU는 아직 더러운 팬을 읽어. 반대로 너무 많이 세우면 주방 동선이 막혀서 프레임 시간이 늘어.
• 그래서 필요한 것: 주문표의 읽음/씀 기록을 보고 RDG가 필요한 위치에 표지판을 붙여야 해. 그게 사람이 박던 barrier를 자동으로 계산하는 자동 barrier야.
🧱 먼저 알아야 할 것 — 용도를 바꾸려면 먼저 준비가 필요
• 쓰임을 바꿀 때: 튀김을 볶던 팬에 곧바로 국을 끓이면 기름 맛이 섞여. 같은 팬이라도 하던 일과 다른 일을 시키려면, 그 사이에 씻어서 준비하는 단계가 꼭 있어야 해.
이게 잡히면 아래 리소스 용도가 바뀔 때 자동으로 barrier를 거는 설명이 얹힌다.

6. 자동 barrier — 팬을 씻는 표지판을 붙인다

리소스 수명만큼 중요한 게 barrier야. GPU 리소스는 방금 렌더타깃으로 쓴 상태와, 다음 패스에서 셰이더 리소스로 읽는 상태가 다르다. 상태가 다르면 transition이 필요하다.

RDG는 패스 파라미터에서 수집한 Access를 보고, 어떤 패스의 epilogue에서 barrier를 시작하고, 어떤 패스의 prologue에서 끝낼지 계산한다. 그리고 실제 패스 실행 전후에 그 barrier batch를 제출한다.

아래는 패스 epilogue에서 barrier begin들을 제출하고, 필요하면 BeginTransitions를 호출하는 장면이야.

RenderGraphBuilder.cpp:3443

FRDGTransitionQueue Transitions; if (Pass->EpilogueBarriersToBeginForGraphics) { Pass->EpilogueBarriersToBeginForGraphics->Submit(RHICmdListPass, PassPipeline, Transitions); } if (Pass->EpilogueBarriersToBeginForAsyncCompute) { Pass->EpilogueBarriersToBeginForAsyncCompute->Submit(RHICmdListPass, PassPipeline, Transitions); } if (Pass->EpilogueBarriersToBeginForAll) { Pass->EpilogueBarriersToBeginForAll->Submit(RHICmdListPass, PassPipeline, Transitions); } for (FRDGBarrierBatchBegin* BarriersToBegin : Pass->SharedEpilogueBarriersToBegin) { BarriersToBegin->Submit(RHICmdListPass, PassPipeline, Transitions); } if (!Transitions.IsEmpty()) { RHICmdListPass.BeginTransitions(Transitions); } if (Pass->EpilogueBarriersToEnd) { Pass->EpilogueBarriersToEnd->Submit(RHICmdListPass, PassPipeline); }
🔤 기호 사전 — epilogue barrier 제출
• FRDGTransitionQueue Transitions = 지금 제출할 RHI transition들을 담는 임시 줄이야.
• EpilogueBarriersToBeginForGraphics = graphics 파이프라인 쪽에서 시작해야 하는 barrier 묶음이야.
• Submit(...) = RDG barrier batch를 실제 RHI transition 정보로 제출한다.
• BeginTransitions(Transitions) = 모인 transition들을 RHI command list에 시작하라고 명령한다.
🔁 이제 다시 보자. graphics/async/all용 epilogue barrier 묶음을 Submit하고 → 모인 transition이 있으면 BeginTransitions를 호출하고 → 끝내야 할 epilogue barrier도 제출한다. 사람이 ResourceBarrier를 손으로 여기저기 박는 대신, RDG가 주문 보드를 보고 자동 표지판을 붙이는 거야.

여기서 "자동"이라는 말이 마법은 아니야. 앞에서 SetupPassResources가 access를 모았고, SetupPassDependencies가 producer/consumer를 이었고, CompilePassBarriers와 CollectPassBarriers가 그 사이를 transition으로 바꿨다. 이 epilogue는 그 결과를 실제 RHI command list에 적는 자리야.

그러니까 RDG를 믿으려면 규칙을 지켜야 해. 패스가 쓰는 리소스는 파라미터에 넣어야 하고, 람다 안에서 몰래 다른 RDG 리소스를 만지면 안 돼. 주문표에 안 적힌 팬을 몰래 쓰면 주방장이 씻을 타이밍을 모르는 것과 같아.

콜/데이터 흐름 한눈에

한 프레임 안에서 RDG 흐름을 줄이면 이렇게 봐도 돼.

렌더러 코드 → GraphBuilder.CreateTexture / RegisterExternalTexture → GraphBuilder.AllocParameters → GraphBuilder.AddPass → FRDGBuilder::SetupParameterPass (:2624) → SetupPassInternals → SetupPassResources (:2374) → EnumerateTextureAccess / EnumerateBufferAccess → PassState.ReferenceCount++ → State.Access / State.SetPass → SetupAuxiliaryPasses → GraphBuilder.Execute (:1755) → Compile (:1316) → SetupPassDependencies (:2319) → culling / render pass merge / async fork-join → CompilePassBarriers (:3750) → CollectPassBarriers (:3839) → CollectAllocations / CollectDeallocations (:3557, :3599) → ExecuteSerialPass / parallel execute → ExecutePassPrologue (:3395) → Pass->Execute → ExecutePassEpilogue (:3428)

RDG 코드를 읽을 때는 함수 이름보다 시점을 먼저 봐야 해. 주문표를 적는 중인지, 보드를 컴파일하는 중인지, 진짜 GPU 명령을 쓰는 중인지 구분하면 길을 잃지 않아.

우리 서버·DirectX 랑 비교

서버에서 IOCP 워커가 패킷을 받으면 바로 모든 게임 로직을 락 잡고 처리하지 않고, 세션/액터 큐에 넣어 순서를 정리하잖아. RDG도 렌더러 곳곳의 패스 주문을 즉시 GPU에 때리지 않고 그래프에 모아 "누가 만들고, 누가 읽고, 누가 마지막으로 쓰는지"를 선명하게 만든다.

DirectX 12로 치면 render target 상태, shader resource 상태, UAV barrier, aliasing acquire/discard를 손으로 맞추던 일을 RDG가 패스 파라미터에서 모은 정보로 자동화하는 거야. 단, 주문표에 안 쓴 리소스를 람다 안에서 몰래 만지면 RDG는 모른다. 서버에서 락 규칙 밖으로 전역 상태를 몰래 바꾸는 것과 같다.

이 챕터에서 딱 이것만

  • RDG는 패스를 바로 실행하지 않고 먼저 그래프에 등록한다.
  • 패스 파라미터는 RDG가 리소스 읽기/쓰기를 아는 주문표다.
  • SetupPassResources가 access와 reference count를 모으고, SetupPassDependencies가 producer/consumer 관계를 만든다.
  • Compile() 뒤에 culling, 리소스 수명, barrier가 계산된다.
  • 실제 실행 때는 prologue/epilogue에서 RDG가 만든 barrier batch가 RHI command list에 제출된다.
