이 챕터가 끝나면 "RHI 호출이 왜 바로 GPU로 가지 않고, 명령으로 기록됐다가 제출되는가"가 잡힌다.

• 시간 약속: 종이 울리기 전까지 숙제를 내야 하면, 한 문제에 오래 붙잡힐수록 뒤 문제를 못 푼다.

• 한꺼번에 몰린 일: 작은 심부름도 수백 개가 한꺼번에 오면, 왔다 갔다 하는 시간만으로 하루가 찬다.

왜 이걸 배워? — 문제의식부터

DirectX를 조금 써봤으면 이런 코드를 떠올릴 거야. DrawIndexedInstanced 부르고, ResourceBarrier 치고, ExecuteCommandLists로 제출하지. 게임 서버 쪽으로 치면 워커가 패킷을 받았다고 그 자리에서 바로 게임 로직을 다 실행하지 않고, 큐에 넣었다가 메인 로직 스레드가 순서대로 처리하는 구조랑 비슷해.

그런데 렌더러가 수천 개 드로우콜을 매 프레임 즉석에서 다 처리하면 어떻게 될까. 렌더 스레드 하나가 "상태 세팅 → 드로우 → 배리어 → 복사"를 전부 직접 때리느라 막혀. 60fps면 한 프레임에 16.6ms뿐인데, 그중 몇 ms를 명령 포장에만 태우면 GPU는 놀고 CPU는 줄 서는 이상한 상황이 나온다.

그래서 언리얼도 같은 문제를 만났고, 답이 RHICommandList야. RHI 함수를 부르면 대부분 바로 실행하지 않고 명령 객체를 리스트에 쌓아둔다. 나중에 그 리스트를 실행하면서 RHI context로 번역하고, 마지막에 플랫폼 GPU command list로 제출한다.

왜 지금 배우냐면, 앞 장 RHI가 "CPU가 GPU에게 말 거는 공용 언어"였다면, 이번 장은 그 말을 어떤 종이에 적고, 누가 들고 가고, 언제 주방에 넘기는지를 보는 장이야. 다음 장 D3D12RHI는 이 종이가 진짜 D3D12 명령으로 내려가는 지점이다. → rhi-overview → d3d12-backend

0. 비유부터 — 주방에 바로 소리치지 말고 주문서를 쌓아라

식당에서 웨이터가 손님 주문을 받는다고 치자.

손님이 "파스타 하나"라고 말할 때마다 웨이터가 주방으로 뛰어가서 "파스타!" 하고 외치고, 다시 와서 "샐러드 하나" 받고, 또 뛰어가면 어떻게 될까.

걷는 시간만 낭비야. 주방도 정신없어. 누가 먼저 들어온 주문인지 헷갈리고, 여러 웨이터가 동시에 외치면 순서도 꼬인다.

그래서 보통은 이렇게 해:

  1. 웨이터가 손님 주문을 주문서에 적는다.
  2. 여러 주문서를 모아 접수대에 넘긴다.
  3. 접수대는 순서를 맞추고, 필요한 건 주방 파트별로 나눈다.
  4. 주방은 자기 도구에 맞게 조리하고, 마지막에 음식이 나간다.

RHICommandList가 바로 그 주문서야.

DrawPrimitive는 "파스타 하나" 같은 주문이고, ALLOC_COMMAND는 그 주문을 종이에 적는 동작이야. Execute()는 주문서를 처음부터 끝까지 읽는 동작이고, Submit()은 주방 접수대에 넘기는 동작이다. 병렬 translate는 웨이터 여러 명이 주문서를 나눠 정리하는 장면으로 보면 돼.

이번 장 내내 이 비유를 끌고 갈게. 바로 소리치지 않는다. 적고, 모으고, 번역하고, 제출한다.

🌱 이 개념은 왜 생겼나 — RHICommandList
• 원래 구조: 렌더 코드가 DrawPrimitive 같은 RHI 함수를 부르면 그 자리에서 바로 GPU 쪽으로 소리치는 거야. 웨이터가 주문 받을 때마다 주방 문 앞까지 뛰어가는 구조지.
• 그런데 문제: 한 프레임에 드로우, 배리어, 복사가 수천 줄이면 웨이터가 계속 뛰어다녀. 16.6ms 안에 주문도 받고 전달도 해야 하는데, CPU는 발이 묶이고 GPU는 주문이 늦게 와서 놀 수 있어.
• 그래서 필요한 것: 먼저 주문서를 쌓아두고, 나중에 읽고, 번역하고, 제출하는 기록장이 필요해. 명령(Command)을 줄줄이 담은 목록(List)이라서 RHICommandList야.

1. 전체 지도 — 기록, 완료, 번역, 제출

먼저 큰 흐름부터 잡자.

RHICommandList 흐름은 이렇게 생겼다.

렌더 코드가 RHI 함수 호출 │ ▼ FRHICommandList에 명령 객체 기록 │ ▼ FinishRecording()으로 "주문서 작성 끝" 신호 │ ▼ Submit()이 command list들을 dispatch task로 넘김 │ ▼ translate task가 Execute()로 기록 명령을 RHI context에 재생 │ ▼ Finalize 후 RHISubmitCommandLists()로 플랫폼 RHI에 제출

여기서 헷갈리면 안 되는 말이 두 개 있어.

  • recording = 명령을 리스트에 쌓는 단계.
  • execute/translate = 쌓아둔 명령을 꺼내서 RHI context에 실제 호출로 재생하는 단계.
  • submit = 그렇게 만들어진 플랫폼 command list를 GPU 쪽으로 넘기는 단계.

DirectX 12로 치면 command list에 DrawIndexedInstanced를 기록하고, close하고, queue에 submit하는 흐름과 닮았다. 언리얼은 그 위에 "엔진 공용 RHI 명령 리스트"를 하나 더 둔 셈이야.

🧱 먼저 알아야 할 것 — 줄마다 다음 줄을 알려 주기
• 이어 붙인 줄: 기차 칸처럼 한 칸이 다음 칸을 물고 있으면, 첫 칸부터 따라가며 끝까지 갈 수 있다.
• 마지막의 빈 고리: 새 칸을 붙일 자리를 늘 기억해 두면, 뒤쪽에 빠르게 하나 더 달 수 있다.
• 크기가 다른 칸: 어떤 칸은 작고 어떤 칸은 커도, "다음 칸은 여기"라는 표시만 같으면 한 줄로 이을 수 있다.
이게 잡히면 아래 설명이 얹힌다.

2. 기록의 핵심 — 명령 하나는 링크드 리스트에 꽂힌다

먼저 주문서에 줄 하나를 쓰는 코드부터 보자. AllocCommand는 새 명령 객체가 들어갈 메모리를 잡고, 현재 리스트 뒤에 붙인다.

RHICommandList.h:567

inline void* AllocCommand(int32 AllocSize, int32 Alignment) { checkSlow(!IsExecuting()); checkfSlow(!Bypass(), TEXT("Invalid attempt to record commands in bypass mode.")); FRHICommandBase* Result = (FRHICommandBase*) MemManager.Alloc(AllocSize, Alignment); ++NumCommands; *CommandLink = Result; CommandLink = &Result->Next; return Result; }
🔤 기호 사전 — 명령을 리스트에 꽂는 코드
• void* = 어떤 타입이든 가리킬 수 있는 아주 날것의 포인터야.
• int32 = 32비트 정수. 크기나 정렬 값을 담는다.
• checkSlow(...) = 느린 검사지만 디버그 때 잡아내려고 넣은 안전장치야.
• Bypass() = 명령 기록을 건너뛰고 바로 실행하는 특수 모드인지 묻는 함수야.
• FRHICommandBase* Result = 새로 만든 명령 객체를 가리키는 손잡이야.
• MemManager.Alloc(...) = 명령을 넣을 메모리 조각을 빌리는 동작이야.
• ++NumCommands = 명령 개수를 하나 늘린다. 주문서 줄 수를 세는 거야.
• *CommandLink = Result = 지금 리스트의 빈 꼬리 칸에 새 명령을 꽂는다.
• CommandLink = &Result->Next = 다음 명령이 붙을 자리를 새 명령의 Next 칸으로 옮긴다.

이 코드의 핵심은 *CommandLink = Result와 CommandLink = &Result->Next야.

주문서 맨 아래에 새 줄을 쓰고, 펜 끝을 다음 빈 줄로 내려놓는 장면이라고 보면 된다.

여기서 GPU 호출이 일어나지 않는다. RHIDrawPrimitive도, D3D12도 아직 안 나와. 그냥 "나중에 실행할 명령 객체"를 메모리에 만들고 리스트에 이어 붙인다.

🔁 이제 다시 보자. MemManager.Alloc으로 명령 종이 한 칸을 얻고 → ++NumCommands로 줄 수를 세고 → *CommandLink = Result로 리스트 꼬리에 붙이고 → CommandLink = &Result->Next로 다음 빈칸을 준비한다. 읽으면 "명령을 실행했다"가 아니라 "명령을 적었다"야.

이게 이 장의 첫 번째 못이야.

RHICommandList는 기본적으로 실행기가 아니라 기록장이다.

🌱 이 개념은 왜 생겼나 — 명령 객체와 링크드 리스트
• 원래 구조: 주문을 그냥 함수 호출로 바로 처리하거나, 커다란 배열에 차례대로 넣으면 단순해 보여. 주문서 줄을 한 칸씩 쓰는 느낌이야.
• 그런데 문제: RHI 명령은 드로우, 복사, 배리어처럼 종류도 크기도 달라. 매 프레임 수천 줄을 빠르게 붙여야 하는데, 중간마다 큰 배열을 옮기면 접수대가 종이 정리만 하다 끝나.
• 그래서 필요한 것: 명령마다 자기 크기만큼 메모리를 받고, Next로 다음 줄을 가리키게 잇는 구조가 필요해. ALLOC_COMMAND는 새 주문 줄을 만들고 리스트 꼬리에 꽂는 동작이야.

3. DrawPrimitive도 바로 그리지 않는다

그럼 실제 드로우 호출은 어떻게 기록될까. DrawPrimitive를 보자.

RHICommandList.h:3962

inline void DrawPrimitive(uint32 BaseVertexIndex, uint32 NumPrimitives, uint32 NumInstances) { //check(IsOutsideRenderPass()); if (Bypass()) { GetContext().RHIDrawPrimitive(BaseVertexIndex, NumPrimitives, NumInstances); return; } ALLOC_COMMAND(FRHICommandDrawPrimitive)(BaseVertexIndex, NumPrimitives, NumInstances); }
🔤 기호 사전 — 드로우 호출 기록 코드
• inline = 함수 호출 비용을 줄이려고 본문을 가까이 펼칠 수 있다는 힌트야.
• uint32 = 32비트 양수 정수. 정점 시작 위치, 삼각형 개수 같은 숫자에 쓴다.
• if (Bypass()) = 특수 모드면 기록하지 않고 바로 실행하겠다는 갈림길이야.
• GetContext().RHIDrawPrimitive(...) = 실제 RHI context에 드로우를 바로 호출하는 길이야.
• return = 여기서 함수 끝. 아래 기록 코드는 안 간다.
• ALLOC_COMMAND(...) = 방금 본 AllocCommand를 써서 명령 객체를 리스트에 쌓는 매크로야.
• FRHICommandDrawPrimitive = "나중에 DrawPrimitive를 실행해"라는 주문서 줄의 타입이야.

이 코드가 진짜 중요해.

Bypass()가 켜져 있으면 바로 GetContext().RHIDrawPrimitive(...)로 간다. 그런데 평소 경로는 아래 한 줄이야.

ALLOC_COMMAND(FRHICommandDrawPrimitive)(...)

즉 DrawPrimitive()라는 이름 때문에 바로 그릴 것 같지만, 실제로는 FRHICommandDrawPrimitive라는 명령 객체를 쌓는다.

웨이터가 주방에 바로 뛰어가는 모드가 Bypass()고, 정상 영업 모드는 주문서에 적는 모드야.

🔁 이제 다시 보자. DrawPrimitive는 먼저 Bypass()인지 보고, 맞으면 즉시 RHIDrawPrimitive를 때린다. 아니면 ALLOC_COMMAND(FRHICommandDrawPrimitive)로 주문서에 드로우 명령을 쓴다. 그러니까 이름은 "그려"지만, 보통 의미는 "나중에 그릴 명령을 기록해"야.

이 차이를 못 잡으면 앞으로 렌더러 코드가 이상해 보여.

"분명 RHICmdList.DrawPrimitive()를 불렀는데 왜 GPU가 바로 움직이지 않지?"

답은 간단해. 아직 주문서에 적은 단계라서 그래.

🧱 먼저 알아야 할 것 — 끝났다는 신호
• 기다림: 친구가 준비를 마쳐야 같이 출발할 수 있으면, 끝났다는 말을 듣기 전에는 움직이면 안 된다.
• 신호: 손을 들거나 종을 치는 것처럼, 다음 사람이 시작해도 되는 순간을 알려 주는 표시가 필요하다.
• 먼저 할 일: 빠진 물건이 없는지 확인한 뒤 신호를 보내야, 다음 사람이 헛걸음하지 않는다.
이게 잡히면 아래 설명이 얹힌다.

4. 기록 완료 — 주문서 작성 끝 신호

명령을 쌓았으면 어느 순간 "이 주문서 이제 다 썼다"는 신호가 필요해. 언리얼은 FinishRecording()에서 그 신호를 준다.

RHICommandList.cpp:286

// "Complete" the dispatch event. DispatchEvent->DispatchSubsequents(); }
🔤 기호 사전 — 기록 완료 코드
• // = 사람한테 남기는 주석이야. 실행되는 명령은 아니다.
• DispatchEvent->DispatchSubsequents() = 이 이벤트를 기다리던 다음 작업들을 깨운다.
• -> = 포인터가 가리키는 물건의 함수를 부르는 화살표야.

이게 "주문서 작성 끝났어. 이제 접수대가 가져가도 돼"라는 호출이다. FinishRecording()의 앞부분은 fence scope와 pending upload를 검사하고, 마지막에 이 dispatch event를 완료시킨다.

서버로 치면 패킷을 큐에 넣기 전에 길이, 상태, 세션 생존 여부를 확인하고, 마지막에 큐 이벤트를 깨우는 장면이랑 닮았다.

5. 실행 — 기록된 명령을 처음부터 끝까지 재생한다

이제 주문서가 접수대로 넘어갔다고 치자. 누군가는 주문서 줄들을 처음부터 끝까지 읽어야 해.

그 역할이 FRHICommandListBase::Execute()다.

RHICommandList.cpp:518

void FRHICommandListBase::Execute() { check(!IsExecuting()); bExecuting = true; PersistentState.CurrentGPUMask = PersistentState.InitialGPUMask; #if WITH_RHI_BREADCRUMBS && WITH_ADDITIONAL_CRASH_CONTEXTS FScopedAdditionalCrashContextProvider CrashContext( [ this, ThreadName = IsInRHIThread() ? TEXT("RHIThread") : IsInActualRenderingThread() ? TEXT("RenderingThread") : IsInGameThread() ? TEXT("GameThread") : TEXT("Parallel") ](FCrashContextExtendedWriter& Writer) { if (PersistentState.LocalBreadcrumb) { PersistentState.LocalBreadcrumb->WriteCrashData(Writer, ThreadName); } }); #endif // WITH_ADDITIONAL_CRASH_CONTEXTS FRHICommandListIterator Iter(*this); while (Iter.HasCommandsLeft()) { FRHICommandBase* Cmd = Iter.NextCommand(); Cmd->ExecuteAndDestruct(*this); } }
🔤 기호 사전 — 명령 재생 코드
• check(!IsExecuting()) = 이미 실행 중이면 또 실행하면 안 된다는 검사야. !는 참/거짓 뒤집기야.
• bExecuting = true = 지금부터 실행 중이라고 표시한다. b로 시작하면 보통 bool이야.
• #if ... #endif = 빌드 옵션에 따라 들어가거나 빠지는 컴파일 조건문이야.
• FScopedAdditionalCrashContextProvider = 크래시가 났을 때 추가 정보를 남기기 위한 범위 객체야.
• FRHICommandListIterator Iter(*this) = 지금 command list를 훑는 반복자를 만든다.
• while (Iter.HasCommandsLeft()) = 남은 명령이 있는 동안 계속 돈다.
• FRHICommandBase* Cmd = 현재 꺼낸 명령을 가리키는 포인터야.
• Cmd->ExecuteAndDestruct(*this) = 명령을 실행하고, 끝나면 그 명령 객체를 파괴한다.

여기가 주문서를 실제로 읽는 장면이야.

FRHICommandListIterator가 첫 줄부터 따라가고, 각 줄마다 ExecuteAndDestruct를 부른다.

아까 DrawPrimitive에서 쌓았던 FRHICommandDrawPrimitive도 결국 이 루프 안에서 자기 차례가 오면 실행된다.

그리고 이름에 Destruct가 붙어 있지. 실행하고 버린다는 뜻이야. 주문서 줄을 처리했으면 그 줄은 다시 쓸 필요가 없다.

🔁 이제 다시 보자. Execute()는 실행 중 플래그를 세우고 → iterator로 command list를 훑고 → NextCommand()로 명령 하나를 꺼내고 → ExecuteAndDestruct(*this)로 실행 후 파괴한다. 아까 기록한 주문이 여기서 주방 말로 읽히는 거야.

여기까지 보면 기록과 실행이 분리된 이유가 보인다.

기록은 여러 곳에서 빠르게 할 수 있다. 실행은 정해진 순서로 밀어 넣을 수 있다. 이 분리가 있어야 병렬 기록과 순서 보장이 같이 가능해진다.

🌱 이 개념은 왜 생겼나 — 병렬 번역(translate task)
• 원래 구조: 주문서를 한 접수대 직원이 처음부터 끝까지 읽고, 주방 말로 바꿔서 넘기면 돼. 한 줄이라서 순서는 확실해.
• 그런데 문제: 드로우콜이 수천 개면 그 한 명이 병목이 돼. CPU 코어가 여러 개 있어도 접수대 한 명만 일하면 나머지는 구경하고, GPU는 번역 끝나길 기다려.
• 그래서 필요한 것: 기록은 이미 끝났으니, 나중에 안전한 주문서는 여러 작업 스레드가 나눠 번역하면 돼. 이게 병렬 번역이고, TranslatePipe는 그 주문서를 흘려보내는 접수대 레일이야.
🧱 먼저 알아야 할 것 — 여럿이 나눠 일할 때
• 나눌 수 있는 일: 시험지를 여러 묶음으로 나눠 채점하면, 선생님 여러 명이 동시에 빨리 끝낼 수 있다.
• 순서가 중요한 일: 번호표 순서대로 해야 하는 일은 아무에게나 흩어 주면 앞뒤가 꼬인다.
• 줄 고르기: 빨리 처리해도 되는 줄과 차례를 지켜야 하는 줄을 나눠 보내면 덜 기다린다.
이게 잡히면 아래 설명이 얹힌다.

6. 병렬 번역 — 어떤 스레드가 주문서를 정리할까

이제 핵심 질문으로 가자.

왜 굳이 이렇게 복잡하게 쌓고 나중에 실행할까?

답은 병렬성 때문이야.

렌더러는 어떤 command list는 병렬로 RHI context에 번역해도 되고, 어떤 command list는 RHI thread에서 한 줄로 처리해야 한다. 언리얼은 translate task를 어느 pipe에 넣을지 고른다.

RHICommandList.cpp:785

FRHICommandListExecutor::FTaskPipe* FRHICommandListExecutor::FTranslateState::GetTranslateTaskPipe(ENamedThreads::Type& NamedThread) { NamedThread = ENamedThreads::AnyHiPriThreadHiPriTask; FTaskPipe* Pipe = &TranslatePipe; if (!GRHICommandList.AllowParallel()) { NamedThread = ENamedThreads::GetRenderThread_Local(); Pipe = &GRHICommandList.RHIThreadPipe; } else if (!bParallel) { NamedThread = ENamedThreads::RHIThread; Pipe = &GRHICommandList.RHIThreadPipe; } return Pipe; } FRHICommandListExecutor::FTaskPipe* FRHICommandListExecutor::FTranslateState::EnqueueTranslateTask(FGraphEventArray&& Prereqs, TFunction<void()>&& Lambda) { // This is called on the dispatch thread ENamedThreads::Type NamedThread = ENamedThreads::AnyHiPriThreadHiPriTask; FTaskPipe* Pipe = GetTranslateTaskPipe(NamedThread); Pipe->Enqueue(NamedThread, MoveTemp(Prereqs), MoveTemp(Lambda)); return Pipe; }
🔤 기호 사전 — 병렬 translate 선택 코드
• FTaskPipe* = task를 순서대로 흘려보내는 pipe를 가리키는 포인터야.
• ENamedThreads::Type& NamedThread = 어떤 이름 붙은 스레드에서 돌릴지 결과를 받아갈 변수야. &는 참조야.
• AnyHiPriThreadHiPriTask = 아무 고우선순위 작업 스레드에 넣을 수 있다는 뜻이야.
• TranslatePipe = 병렬 translate용 작업 pipe야.
• GRHICommandList.AllowParallel() = RHI 작업을 병렬로 돌려도 되는지 묻는다.
• RHIThreadPipe = RHI thread 쪽으로 보내는 pipe야.
• else if (!bParallel) = 병렬 실행 대상이 아니면 RHI thread로 보내겠다는 갈림길이야.
• MoveTemp(Prereqs) = 선행 조건 목록을 복사하지 말고 옮겨 넣는다.
• Lambda = 나중에 실행할 작은 함수 덩어리야.

이 코드는 세 갈래야.

  1. 병렬 자체가 안 되면 render thread local queue로 간다.
  2. 병렬은 되지만 이 job이 병렬 대상이 아니면 RHI thread로 간다.
  3. 병렬 가능하고 병렬 대상이면 AnyHiPriThreadHiPriTask와 TranslatePipe를 쓴다.

웨이터 비유로 돌아가면, 주문서를 접수대 한 명이 다 정리할 수도 있고, 파트별 담당자가 병렬로 정리할 수도 있다. 단, 순서가 중요한 주문은 한 줄 접수대로 보내야 해.

🔁 이제 다시 보자. GetTranslateTaskPipe는 기본값을 병렬 작업 스레드와 TranslatePipe로 잡고 → 병렬이 금지되면 render thread/RHI pipe로 바꾸고 → 이 job만 병렬 불가면 RHI thread로 바꾼다. 즉 command list를 기록해뒀기 때문에, 나중에 상황을 보고 "누가 번역할지" 고를 수 있는 거야.

이게 이번 장의 핵심 답이다.

즉시 실행이면 호출한 그 스레드가 그 자리에서 묶인다. 기록 후 제출이면 나중에 더 좋은 스레드 배치로 처리할 수 있다.

🌱 이 개념은 왜 생겼나 — 최종 제출(Submit)
• 원래 구조: 주문서를 읽고 주방 말로 번역했으면 끝난 것처럼 보여. 접수대 직원이 "파스타, 샐러드"로 정리해둔 상태야.
• 그런데 문제: 정리만 해놓고 주방장에게 안 넘기면 음식은 안 나와. 엔진 공용 명령을 플랫폼 command list로 만들었어도, 마지막 제출이 없으면 D3D12나 Vulkan 쪽 큐는 일을 못 받아.
• 그래서 필요한 것: 완성된 command list들을 모아서 실제 플랫폼 RHI에 넘기는 마지막 손길이 필요해. 그래서 Submit, 말 그대로 "접수대에 제출"하는 단계가 있어.

7. 최종 제출 — 플랫폼 command list를 RHI로 넘긴다

마지막 단계는 진짜 제출이야.

여기서는 translate가 끝난 플랫폼 command list들을 모아서 GDynamicRHI->RHISubmitCommandLists(...)로 넘긴다.

🔤 기호 사전 — 최종 제출 코드
• FinalizedCmdLists.Add(...) = 최종 제출 배열에 완성된 command list를 넣는다.
• FrameDrawStats.Accumulate(...) = 여러 translate job의 드로우 통계를 한 프레임 통계로 합친다.
• GDynamicRHI = 현재 플랫폼 RHI 구현체로 가는 전역 손잡이야.
• RHISubmitCommandLists(...) = 이제 진짜 플랫폼 RHI로 command list들을 넘기는 호출이야.

이 줄이 종착지야. RHICommandList 안에 쌓였던 엔진 공용 명령들은 translate를 거쳐 플랫폼 command list가 됐고, 이제 DynamicRHI 아래 구현체로 내려간다.

D3D12라면 다음 장에서 이 아래가 D3D12 command queue와 command list 쪽으로 이어진다. Vulkan이면 Vulkan식으로 이어지고. RHI가 추상화 계층인 이유가 여기서 다시 나온다.

8. 콜/데이터 흐름 한눈에

이제 전체를 주문서 흐름으로 다시 그려보자.

9. 우리 서버·DirectX랑 비교

우리 조선 서버 관점으로 보면 RHICommandList는 작업 큐에 가깝다.

IOCP 워커가 클라 패킷을 받자마자 게임 로직을 다 실행하면 락도 많아지고 순서도 꼬이지. 그래서 세션별 버퍼, 패킷 큐, 싱글스레드 액터 큐 같은 구조를 둔다. 기록과 처리 시점을 분리하면, 받은 스레드와 처리 스레드를 나눌 수 있어.

렌더링도 마찬가지야.

렌더 코드가 DrawPrimitive를 부른 스레드에서 바로 하드웨어 API까지 내려가면, 병렬 기록이 어렵고 순서 보장이 힘들어진다. 그래서 RHICommandList가 중간 주문서가 된다.

DirectX 12 경험으로 보면 더 직관적이야.

DirectX 12 감각언리얼 RHICommandList 감각
command list에 draw/barrier 기록ALLOC_COMMAND로 FRHICommand... 기록
command list closeFinishRecording()으로 dispatch event 완료
여러 command list를 worker에서 만들 수 있음parallel translate task로 여러 RHI context 정리
command queue executeGDynamicRHI->RHISubmitCommandLists(...)
즉시 context식 사고는 병목Bypass()는 특수 경로

서버의 큐와 DirectX의 command list를 합쳐서 생각하면 된다.

패킷을 받는 것과 처리하는 것을 분리하듯, RHI 호출도 기록과 제출을 분리한다.

10. 이 챕터에서 딱 이것만

  • RHICommandList는 RHI 호출을 바로 실행하는 물건이 아니라, 보통 명령 객체를 쌓는 주문서야.
  • ALLOC_COMMAND는 명령 객체를 만들고 CommandLink/Next로 리스트에 붙인다.
  • Bypass()가 켜지면 바로 GetContext().RHI...로 가지만, 정상 경로는 기록이다.
  • Execute()는 기록된 명령을 iterator로 훑으며 ExecuteAndDestruct를 부른다.
  • 제출 끝에는 GDynamicRHI->RHISubmitCommandLists(...)가 있고, 그 아래가 D3D12/Vulkan 같은 실제 백엔드다.

🎯 원리 한 줄 요약

RHICommandList는 "GPU에게 바로 소리치는 코드"가 아니라, 렌더 명령을 주문서처럼 쌓고 병렬로 정리한 뒤 플랫폼 RHI에 제출하게 해주는 기록·번역·제출 파이프라인이다.
