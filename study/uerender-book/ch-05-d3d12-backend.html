D3D12RHI — 진짜 하드웨어로 내려가는 지점

언리얼 렌더링 · 05 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "RHI 명령이 어디서 진짜 D3D12 API 호출로 바뀌는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX 12를 조금이라도 만져봤으면 ID3D12GraphicsCommandList가 낯설진 않을 거야. 결국 네이티브 DX에서는 SetPipelineState, ResourceBarrier, DrawInstanced, Dispatch, CopyResource 같은 호출이 명령 리스트에 찍히지. 게임 서버로 치면 CM_MOVE 같은 패킷이 마지막엔 진짜 핸들러 함수 하나를 타고 캐릭터 좌표를 바꾸는 지점이 있어야 하는 것과 같아.

그런데 앞 장까지만 보면 언리얼은 일부러 그 지점을 숨겨. 렌더러는 RHIDrawPrimitive라고 말하고, RHICommandList는 그걸 주문서처럼 쌓아. 여기서 멈추면 RenderDoc에 찍힌 DrawIndexedInstanced와 엔진 코드의 RHI 호출이 서로 안 이어져. GPU 크래시가 나도 "어느 RHI 명령이 실제 D3D12 호출이 됐지?"를 못 찾게 된다.

그래서 언리얼도 같은 문제를 만났고, 답이 D3D12RHI야. 공용 언어였던 RHI를 윈도우/D3D12용 방언으로 번역해서, 진짜 ID3D12GraphicsCommandList 버튼을 누르는 층. 그 중심에 FD3D12CommandContext와 FD3D12StateCache가 있어.

왜 지금 배우냐면, 앞 장 rhi-commandlist가 "명령을 적고 제출하는 주문서"였다면 이번 장은 그 주문서가 주방 안쪽의 실제 화구 버튼으로 바뀌는 순간이야. 다음 장 rhi-resources와 pso에서 버퍼, 텍스처, PSO를 보려면 "얘들이 결국 어떤 D3D12 호출에 꽂히는지"를 먼저 알아야 해.

0. 비유부터 — 주문서가 주방 기계 버튼으로 바뀌는 순간

이번에도 식당으로 가자.

앞 장의 RHICommandList는 웨이터가 적어둔 주문서였어. "파스타 하나", "스테이크 하나", "접시 비워", "냉장고에서 재료 꺼내" 같은 줄들이 쌓였지.

그런데 주문서만 있으면 음식은 안 나와. 누군가는 주방 안으로 들어가서 실제 기계를 만져야 해.

  1. 주문서의 "파스타"를 읽는다.
  2. 파스타용 화구를 켠다.
  3. 팬을 올린다.
  4. 소스를 붓는다.
  5. 접시에 담는다.

D3D12RHI가 이 주방 안쪽 사람이야. RHI 주문을 읽고, D3D12 기계의 실제 버튼을 누른다.

이 챕터에서 계속 이렇게 부를게.

  • RHICommandList = 손님 주문서.
  • FD3D12CommandContext = 주문서를 읽고 주방 기계를 누르는 사람.
  • FD3D12StateCache = 지금 켜진 화구, 팬, 접시 상태를 기억하는 칠판.
  • ID3D12GraphicsCommandList = 진짜 주방 기계 버튼판.
  • DrawInstanced / Dispatch / ClearRenderTargetView = 실제 버튼 이름.

중요한 건 하나야. 언리얼 렌더러 대부분은 "D3D12 버튼 이름"을 직접 부르지 않아. 대신 RHI로 말하고, D3D12RHI가 마지막에 버튼을 눌러.

🌱 이 개념은 왜 생겼나 — D3D12RHI 백엔드
• 원래 구조: 엔진 코드가 그냥 D3D12 버튼을 직접 누르면 제일 단순해. 주문서 없이 주방 기계 앞에서 바로 DrawInstanced를 누르는 거야.
• 그런데 문제: 그러면 윈도우/D3D12 말이 렌더러 전체에 퍼져. 다른 그래픽 API나 플랫폼으로 가려면 주문서를 전부 다시 써야 해.
• 그래서 필요한 것: 위쪽은 공용 RHI 말만 쓰고, 맨 아래에서만 D3D12 말로 번역하는 층이 필요해. 그 D3D12 전용 뒷문이 D3D12RHI 백엔드야.

1. 전체 지도 — 추상 명령에서 네이티브 호출까지

큰 길은 이렇게 생겼어.

렌더러 / RenderCore | | RHI 명령 호출 v FRHICommandList | | 기록된 명령 실행 v FD3D12CommandContext | | 상태 정리 + 리소스 바인딩 + 배리어 v FD3D12StateCache / DescriptorCache | | 실제 D3D12 메서드 호출 v ID3D12GraphicsCommandList

이 그림에서 이번 장의 주인공은 아래쪽 세 칸이야. 특히 FD3D12CommandContext는 "RHI 함수 이름이 붙은 메서드"를 많이 들고 있어.

예를 들면 이런 식이야.

RHI 쪽 말D3D12RHI 안쪽마지막 D3D12 버튼
RHISetGraphicsPipelineStateStateCache.SetGraphicsPipelineStateSetPipelineState
RHIDispatchComputeShaderSetupDispatch 후 실행Dispatch
RHIDrawPrimitiveSetupDraw 후 실행DrawInstanced
RHIClearMRTImplRTV/DSV 찾고 실행ClearRenderTargetView / ClearDepthStencilView
텍스처/버퍼 전송copy context 선택CopyResource / CopyTextureRegion

여기서 조심할 점이 있어. 모든 함수가 D3D12CommandContext.cpp 한 파일에 있진 않아. 이 클론에서는 명령별 몸통이 D3D12Commands.cpp, 상태 캐시는 D3D12StateCache.cpp, 복사 일부와 명령 리스트 관리는 D3D12CommandContext.cpp에 나뉘어 있어. 그래도 전부 같은 D3D12RHI/Private 주방 안쪽 코드야.

🌱 이 개념은 왜 생겼나 — 리소스 배리어(Resource Barrier)
• 원래 구조: 텍스처나 버퍼를 그냥 물건 이름으로 쓰면 편해. 방금 접시로 썼던 걸 바로 재료통으로 읽는 식이야.
• 그런데 문제: D3D12는 "지금 이 리소스가 렌더 타깃인지, 셰이더가 읽는지, 복사용인지"를 GPU에게 알려줘야 해. 표지판 없이 바꾸면 validation이 화내거나 화면이 깨져.
• 그래서 필요한 것: 쓰임새가 바뀌는 경계마다 "이제 상태 바뀜" 표지판을 명령 리스트에 꽂아야 해. 그 표지판이 리소스 배리어고, 모아뒀다 밀어내는 게 FlushResourceBarriers()야.

2. 명령 리스트 닫기 — 주방에 넘기기 전 배리어부터 비운다

먼저 주요 소스인 D3D12CommandContext.cpp에서 명령 리스트를 닫는 장면을 보자. 주문서가 다 실행됐다고 바로 닫지 않아. 닫기 직전에 "아직 밀린 배리어가 있나?"부터 털어.

D3D12CommandContext.cpp:378

void FD3D12ContextCommon::CloseCommandList() { checkf(IsPendingCommands(), TEXT("The command list is empty.")); // Do this before we insert the final timestamp to ensure we're timing all the work on the command list. // If the command list only has barrier work to do, this will open the command list for the first time FlushResourceBarriers(); checkf(IsOpen(), TEXT("Command list is not open.")); checkf(Payloads.Num() && CurrentPhase == EPhase::Execute, TEXT("Expected the current payload to be in the execute phase.")); checkf(ActiveQueries == 0, TEXT("All queries must be completed before the command list is closed.")); FD3D12Payload* Payload = GetPayload(EPhase::Execute); CommandList->Close(); CommandList = nullptr; TimestampQueries .CloseAndReset(Payload->BatchedObjects.QueryRanges); OcclusionQueries .CloseAndReset(Payload->BatchedObjects.QueryRanges);
🔤 기호 사전 — 명령 리스트 닫기
• FD3D12ContextCommon::CloseCommandList = D3D12 공통 컨텍스트 안의 명령 리스트 닫기 함수야. ::는 "이 묶음 안에 있는 함수"라는 뜻.
• checkf(...) = 조건이 틀리면 바로 잡아내는 검사야. 뒤의 TEXT(...)는 터질 때 보여줄 말.
• FlushResourceBarriers() = 미뤄둔 리소스 상태 전환을 실제 명령 리스트에 밀어 넣는 함수야.
• Payloads.Num() = Payloads 안에 몇 개 들어 있는지 세는 호출이야.
• && = 둘 다 참이어야 한다는 "그리고".
• FD3D12Payload* Payload = FD3D12Payload를 가리키는 손잡이야. *는 포인터.
• CommandList->Close() = D3D12 명령 리스트한테 "이제 기록 끝"이라고 닫는 호출이야.
• nullptr = 이제 가리키는 대상이 없다는 빈 손잡이야.
🔁 이제 다시 보자. CloseCommandList()는 먼저 빈 명령 리스트가 아닌지 확인하고 → FlushResourceBarriers()로 밀린 안전 표지판을 붙이고 → 실제 CommandList->Close()를 부른다. 주방 비유로 치면 주문서를 주방장에게 넘기기 전에 "이 재료는 냉장, 이 팬은 뜨거움" 같은 표시를 마지막으로 붙이는 거야.

여기서 CommandList->Close()는 DirectX 12에서 익숙한 그 닫기 단계야. 언리얼의 RHI 주문서가 D3D12 명령 리스트에 다 기록된 다음, 제출 가능한 상태로 바뀌는 관문이지.

다만 초보가 자주 놓치는 건 FlushResourceBarriers()야. D3D12는 리소스 상태를 개발자가 직접 맞춰야 해. "이 텍스처를 방금 렌더 타깃으로 썼는데 이제 셰이더에서 읽을 거야" 같은 말을 빼먹으면 GPU validation이 바로 화낸다. 그래서 D3D12RHI는 배리어를 모아뒀다가 적당한 순간에 명령 리스트로 흘려보내.

🌱 이 개념은 왜 생겼나 — 상태 캐시와 PSO
• 원래 구조: 드로우할 때마다 셰이더, 블렌드, 깊이, 래스터라이저 버튼을 전부 다시 눌러도 돼. 주문마다 주방 세팅을 처음부터 맞추는 거야.
• 그런데 문제: 한 프레임에 드로우콜이 수천 번이면 같은 버튼을 수천 번 다시 누르게 돼. 그래픽/컴퓨트 전환 때 세팅이 틀리면 엉뚱한 화구로 요리해.
• 그래서 필요한 것: 지금 버튼판에 꽂힌 세팅을 칠판에 적어두고, 바뀔 때만 SetPipelineState를 눌러야 해. 그 기억장이 FD3D12StateCache고, 묶인 파이프라인 상태 객체가 PSO야.

3. PSO 세팅 — 상태 캐시가 SetPipelineState 버튼을 누른다

DirectX 12에서는 드로우 전에 PSO가 맞아야 해. 셰이더, 블렌드, 깊이, 래스터라이저 상태가 묶인 그 덩어리 말이야.

언리얼 렌더러는 매번 ID3D12GraphicsCommandList::SetPipelineState를 직접 부르지 않아. 먼저 RHISetGraphicsPipelineState 같은 RHI 함수를 타고, 그 안에서 StateCache가 상태를 기억해. 그리고 실제로 바뀌어야 할 때만 D3D12 버튼을 누른다.

D3D12StateCache.cpp:413

void FD3D12StateCache::InternalSetPipelineState(FD3D12PipelineState* InPipelineState) { // See if we need to set our PSO: // In D3D11, you could Set dispatch arguments, then set Draw arguments, then call Draw/Dispatch/Draw/Dispatch without setting arguments again. // In D3D12, we need to understand when the app switches between Draw/Dispatch and make sure the correct PSO is set. ID3D12PipelineState* const CurrentD3DPipelineState = PipelineState.Common.CurrentPipelineStateObject; ID3D12PipelineState* const PendingD3DPipelineState = InPipelineState->GetPipelineState(); if (PipelineState.Common.bNeedSetPSO || CurrentD3DPipelineState == nullptr || CurrentD3DPipelineState != PendingD3DPipelineState) { PipelineState.Common.CurrentPipelineStateObject = PendingD3DPipelineState; CmdContext.GraphicsCommandList()->SetPipelineState(PendingD3DPipelineState); PipelineState.Common.bNeedSetPSO = false; } }
🔤 기호 사전 — PSO 세팅
• FD3D12StateCache = D3D12 상태를 기억하는 캐시야. 같은 상태를 반복해서 누르지 않게 해.
• FD3D12PipelineState* = 언리얼이 감싼 D3D12 PSO 손잡이야.
• ID3D12PipelineState* const = 진짜 D3D12 PSO 포인터인데, 이 변수 자체는 다른 걸 가리키도록 못 바꾼다는 뜻이야.
• InPipelineState->GetPipelineState() = 언리얼 래퍼에서 실제 D3D12 PSO를 꺼내는 호출이야.
• || = 조건 중 하나라도 맞으면 된다는 "또는".
• CurrentD3DPipelineState != PendingD3DPipelineState = 지금 GPU에 박힌 PSO와 새로 박아야 할 PSO가 다른지 비교하는 거야.
• CmdContext.GraphicsCommandList()->SetPipelineState(...) = 드디어 진짜 D3D12 명령 리스트에 PSO를 세팅하는 버튼이야.
• bNeedSetPSO = false = 이제 세팅했으니 "다시 세팅 필요" 표시를 끄는 거야.
🔁 이제 다시 보자. 이 함수는 현재 PSO와 새 PSO를 비교하고 → 필요할 때만 SetPipelineState를 호출하고 → bNeedSetPSO를 꺼. 주방 칠판에 "지금 파스타 팬 세팅임"이라고 적어둬서, 같은 팬이면 다시 꺼내지 않는 장면이야.

이 코드가 중요한 이유는 "RHI 함수 하나 = D3D12 호출 하나"가 항상 아니라는 걸 보여줘. 언리얼은 상태를 캐시하고 더러운 것만 밀어. 서버에서도 똑같지. 매 패킷마다 플레이어 전체 상태를 DB에 다 쓰지 않고, 바뀐 필드만 dirty로 잡아 반영하잖아.

D3D12RHI도 비슷해. StateCache는 지금 GPU 명령 리스트에 어떤 상태가 걸렸는지 기억하고, 바뀐 것만 실제 D3D12 호출로 내려보낸다.

4. 컴퓨트 — RHIDispatchComputeShader가 Dispatch로 떨어진다

이제 진짜 명령다운 장면을 보자. 컴퓨트 셰이더는 "몇 개 스레드 그룹을 돌려라"라는 명령이야. RHI 이름은 RHIDispatchComputeShader지만, 마지막 버튼은 D3D12의 Dispatch다.

D3D12Commands.cpp:140

void FD3D12CommandContext::RHIDispatchComputeShader(uint32 ThreadGroupCountX, uint32 ThreadGroupCountY, uint32 ThreadGroupCountZ) { RHI_DISPATCH_CALL_INC(); SetupDispatch(ThreadGroupCountX, ThreadGroupCountY, ThreadGroupCountZ); GraphicsCommandList()->Dispatch(ThreadGroupCountX, ThreadGroupCountY, ThreadGroupCountZ); PostGpuEvent(); }
🔤 기호 사전 — 컴퓨트 디스패치
• RHIDispatchComputeShader = RHI 공용 이름으로 "컴퓨트 셰이더 실행해"라는 함수야.
• uint32 = 부호 없는 32비트 정수야. 스레드 그룹 개수를 담는다.
• ThreadGroupCountX/Y/Z = X, Y, Z 방향으로 몇 묶음의 스레드를 돌릴지 나타내는 값이야.
• RHI_DISPATCH_CALL_INC() = 디스패치 호출 통계를 하나 올리는 매크로야.
• SetupDispatch(...) = 디스패치 전에 디스크립터, 상수, 상태를 맞추는 준비 단계야.
• GraphicsCommandList()->Dispatch(...) = 실제 D3D12 명령 리스트에 컴퓨트 실행 명령을 찍는 버튼이야.
• PostGpuEvent() = GPU 이벤트 뒤처리, 명령 리스트 분할 같은 후처리를 하는 함수야.
🔁 이제 다시 보자. RHIDispatchComputeShader는 통계를 올리고 → SetupDispatch로 주방 세팅을 맞춘 뒤 → GraphicsCommandList()->Dispatch(...)를 누른다. 앞의 이름은 언리얼 말이고, 가운데 준비가 번역이고, 마지막 줄이 진짜 D3D12 말이야.

여기서 GraphicsCommandList()라는 이름이 살짝 헷갈릴 수 있지만, D3D12의 direct command list는 그래픽스와 컴퓨트 명령을 둘 다 받을 수 있어. 여기서는 D3D12 명령을 기록하는 direct command list 손잡이라고 보면 돼.

SetupDispatch 안에서는 디스크립터 업데이트, compute shader constants, resource table, StateCache.ApplyState(...Compute)가 먼저 맞춰진다. 즉 Dispatch 한 줄 앞에 이미 "어떤 셰이더, 어떤 버퍼, 어떤 UAV를 물고 돌 건지"가 정해져 있어.

5. 드로우 — RHIDrawPrimitive가 DrawInstanced로 떨어진다

렌더링에서 제일 익숙한 버튼은 드로우콜이지. 언리얼 쪽 이름은 RHIDrawPrimitive야. 하지만 D3D12로 내려가면 네가 아는 DrawInstanced가 나온다.

D3D12Commands.cpp:1216

void FD3D12CommandContext::RHIDrawPrimitive(uint32 BaseVertexIndex, uint32 NumPrimitives, uint32 NumInstances) { uint32 VertexCount = StateCache.GetVertexCount(NumPrimitives); NumInstances = FMath::Max<uint32>(1, NumInstances); RHI_DRAW_CALL_STATS(StateCache.GetGraphicsPipelinePrimitiveType(), VertexCount, NumPrimitives, NumInstances); SetupDraw(nullptr, NumPrimitives * NumInstances, VertexCount * NumInstances); GraphicsCommandList()->DrawInstanced(VertexCount, NumInstances, BaseVertexIndex, 0); PostGpuEvent(); }
🔤 기호 사전 — 기본 드로우
• BaseVertexIndex = 정점 버퍼에서 어디부터 읽을지 시작 위치야.
• NumPrimitives = 삼각형 같은 primitive가 몇 개인지 나타내는 수야.
• NumInstances = 같은 메시를 몇 번 반복해서 그릴지 나타내는 수야.
• StateCache.GetVertexCount(...) = primitive 개수를 실제 정점 개수로 바꿔주는 계산이야. 삼각형이면 보통 primitive 하나에 정점 셋이지.
• FMath::Max<uint32>(1, NumInstances) = 인스턴스 개수가 0이면 최소 1로 맞추는 안전장치야.
• RHI_DRAW_CALL_STATS(...) = 드로우콜 통계를 기록하는 매크로야.
• SetupDraw(nullptr, ...) = indexed draw가 아니니 index buffer 자리에 nullptr을 넘기고 드로우 준비를 한다는 뜻이야.
• DrawInstanced(...) = 진짜 D3D12 드로우 버튼이야.
🔁 이제 다시 보자. RHIDrawPrimitive는 primitive 개수를 정점 개수로 바꾸고 → 인스턴스 수를 최소 1로 맞추고 → SetupDraw로 상태와 리소스를 준비하고 → DrawInstanced를 찍는다. 주문서에는 "기본 도형 그려"라고 적혀 있었는데, 주방 안쪽 버튼판에서는 DrawInstanced라는 정확한 버튼을 누르는 거야.

SetupDraw가 별거 아닌 것처럼 보이면 안 돼. 그 안에서 그래픽스 리소스 테이블을 commit하고, 상수 버퍼를 commit하고, 인덱스 버퍼가 있으면 StateCache.SetIndexBuffer까지 해. 마지막엔 StateCache.ApplyState(...Graphics)로 PSO, root signature, descriptor table 같은 걸 실제 D3D12 상태로 맞춘다.

indexed draw는 같은 파일 D3D12Commands.cpp:1270의 RHIDrawIndexedPrimitive로 가고, 마지막 줄에서 DrawIndexedInstanced를 호출해. 이번 챕터에선 하나만 기억하면 돼. RHI의 드로우 함수는 마지막에 D3D12의 draw 계열 함수로 떨어진다.

🌱 이 개념은 왜 생겼나 — RTV/DSV 디스크립터 핸들
• 원래 구조: 렌더 타깃 텍스처를 지울 때 "이 텍스처 지워"라고 객체만 넘기면 단순해. 접시 이름만 부르는 거지.
• 그런데 문제: D3D12 버튼판은 그냥 텍스처보다 "어떤 방식으로 볼 건지"가 적힌 손잡이를 원해. 색 접시인지 깊이 접시인지 모르면 어떤 버튼을 눌러야 할지 애매해.
• 그래서 필요한 것: 리소스를 D3D12가 읽을 수 있는 뷰로 포장한 표찰이 필요해. 색은 RTV, 깊이/스텐실은 DSV고, 그 표찰 주소가 descriptor handle이야.

6. 클리어 — 렌더 타깃과 깊이 버퍼도 D3D12 뷰 핸들로 지운다

화면을 그리기 전에 렌더 타깃을 특정 색으로 지우거나 깊이 버퍼를 1로 초기화하는 건 흔한 일이야. RHI에서는 "MRT를 clear해"라고 말하지만, D3D12에서는 RTV/DSV 핸들을 들고 ClearRenderTargetView, ClearDepthStencilView를 호출해야 해.

D3D12Commands.cpp:1466

if (ClearRTV || ClearDSV) { FlushResourceBarriers(); if (ClearRTV) { for (int32 TargetIndex = 0; TargetIndex < BoundRenderTargets.GetNumActiveTargets(); TargetIndex++) { FD3D12RenderTargetView* RTView = BoundRenderTargets.GetRenderTargetView(TargetIndex); if (RTView != nullptr && bClearColorArray[TargetIndex]) { GraphicsCommandList()->ClearRenderTargetView(RTView->GetOfflineCpuHandle(), (float*)&ClearColorArray[TargetIndex], ClearRectCount, pClearRects); UpdateResidency(RTView->GetResource()); } } } if (ClearDSV) { GraphicsCommandList()->ClearDepthStencilView(DepthStencilView->GetOfflineCpuHandle(), (D3D12_CLEAR_FLAGS)ClearFlags, Depth, Stencil, ClearRectCount, pClearRects); UpdateResidency(DepthStencilView->GetResource()); }
🔤 기호 사전 — 렌더 타깃 클리어
• ClearRTV || ClearDSV = 색 렌더 타깃이나 깊이/스텐실 중 하나라도 지울 게 있으면 들어간다는 뜻이야.
• FlushResourceBarriers() = 지우기 전에 리소스 상태를 clear 가능한 상태로 맞추는 단계야.
• for (int32 TargetIndex = 0; ...; TargetIndex++) = 활성 렌더 타깃을 0번부터 끝까지 하나씩 도는 반복문이야.
• FD3D12RenderTargetView* RTView = D3D12 렌더 타깃 뷰를 언리얼이 감싼 손잡이야.
• RTView != nullptr = 실제 뷰가 있는지 확인하는 조건이야.
• GetOfflineCpuHandle() = D3D12가 알아먹는 CPU descriptor handle을 꺼내는 호출이야.
• ClearRenderTargetView(...) = 색 렌더 타깃을 지우는 D3D12 버튼이야.
• ClearDepthStencilView(...) = 깊이/스텐실을 지우는 D3D12 버튼이야.
• UpdateResidency(...) = 이 리소스를 GPU가 쓸 예정이라고 residency 추적에 알려주는 호출이야.
🔁 이제 다시 보자. 클리어는 먼저 FlushResourceBarriers()로 상태를 맞추고 → 색 타깃이면 RTV 핸들을 꺼내 ClearRenderTargetView를 누르고 → 깊이/스텐실이면 DSV 핸들을 꺼내 ClearDepthStencilView를 누른다. "접시 닦아"라는 주문이 실제로는 색 접시 버튼과 깊이 접시 버튼으로 갈라지는 거야.

여기서 GetOfflineCpuHandle()이 핵심이야. D3D12는 리소스를 그냥 "텍스처 객체"로만 지우지 않아. RTV나 DSV descriptor handle을 줘야 해. 언리얼의 FD3D12RenderTargetView, FD3D12DepthStencilView 같은 래퍼는 바로 그 손잡이를 관리하는 포장지야.

7. 복사 — 전체 리소스는 CopyResource로 간다

이번 장의 주요 파일 D3D12CommandContext.cpp에는 GPU 간 리소스 전송도 들어 있다. 텍스처 전체를 복사할 수도 있고, 버퍼 전체를 복사할 수도 있어. 핵심은 언리얼 리소스 래퍼에서 진짜 D3D12 리소스를 꺼낸 뒤 CopyResource를 누른다는 점이야.

D3D12CommandContext.cpp:953

FD3D12CommandContext* CopyContext = Param.bPullData ? DstContext : SrcContext; if (Param.Texture) { FD3D12Texture* SrcTexture = FD3D12CommandContext::RetrieveTexture(Param.Texture, Param.SrcGPUIndex); FD3D12Texture* DstTexture = FD3D12CommandContext::RetrieveTexture(Param.Texture, Param.DestGPUIndex); // If the texture size is zero (Max.Z == 0, set in the constructor), copy the whole resource if (Param.Max.Z == 0) { CopyContext->GraphicsCommandList()->CopyResource(DstTexture->GetResource()->GetResource(), SrcTexture->GetResource()->GetResource()); }
🔤 기호 사전 — 리소스 복사
• Param.bPullData ? DstContext : SrcContext = 데이터를 당기는 방식이면 목적지 컨텍스트를, 아니면 출발지 컨텍스트를 고르는 짧은 if야.
• Param.Texture = 이번 복사 대상이 텍스처인지 보는 값이야. 없으면 아래 else에서 버퍼로 본다.
• RetrieveTexture(...) = RHI 텍스처에서 해당 GPU 인덱스의 D3D12 텍스처를 꺼내는 함수야.
• Param.Max.Z == 0 = 복사 영역이 따로 지정되지 않았으니 전체 리소스를 복사한다는 약속으로 쓰는 조건이야.
• CopyResource(...) = D3D12 전체 리소스 복사 버튼이야.
🔁 이제 다시 보자. 이 코드는 복사를 어느 컨텍스트에서 할지 고르고 → 텍스처 래퍼에서 출발지와 목적지 D3D12 리소스를 꺼내고 → 전체 복사면 CopyResource를 호출한다. 주문서의 "재료 통째로 옮겨"가 실제 주방에선 D3D12 복사 버튼 하나로 떨어지는 거야.

이 장면이 좋은 이유는 추상화의 양쪽을 한 번에 보여줘서야. 겉에서는 Param.Texture, Param.Buffer, Param.SrcGPUIndex 같은 언리얼 구조로 말해. 안쪽에서는 CopyResource 같은 D3D12 호출로 말하지. 영역 복사는 같은 함수 아래쪽에서 CopyTextureRegionChecked 경로로 갈라진다.

즉 D3D12RHI는 단순히 함수 이름만 바꾸는 번역기가 아니야. 언리얼 리소스 래퍼에서 네이티브 D3D12 리소스와 핸들을 꺼내고, 필요한 상태와 영역 정보를 맞춘 다음, 진짜 API를 호출하는 계층이야.

9. 우리 서버·DirectX 랑 비교

게임 서버로 치면 CM_* 패킷 핸들러가 세션 상태를 검증하고 마지막에 캐릭터 상태를 바꾸는 것과 같아. D3D12RHI도 RHI... 함수에 도착한 뒤 SetupDraw, SetupDispatch, StateCache.ApplyState로 상태를 맞추고 마지막에 DrawInstanced, Dispatch, CopyResource를 누른다.

dirty 필드만 DB에 쓰듯이 StateCache도 바뀐 PSO/루트서명/디스크립터만 밀어 넣어. 락이나 순서 보장을 빼먹으면 서버가 터지듯, 배리어나 리소스 상태를 빼먹으면 GPU validation이 터진다.

DirectX 12 경험으로 보면 더 직접적이야. 손으로 DX12 샘플을 짤 때 SetPipelineState → ResourceBarrier → DrawInstanced → Close → ExecuteCommandLists로 가던 그 길을 언리얼도 간다. 다만 중간에 RHI 추상화, command list 기록, state cache, descriptor cache가 들어가 있을 뿐이야.

그래서 RenderDoc이나 PIX에서 DrawInstanced를 봤다면 D3D12Commands.cpp:1216의 RHIDrawPrimitive 쪽으로 거슬러 올라갈 수 있어. 반대로 엔진 코드에서 RHIDispatchComputeShader를 봤다면 최종적으로 PIX에는 Dispatch가 찍힌다고 예상하면 된다.

10. 이번 챕터에서 딱 이것만

  • D3D12RHI는 RHI 추상 명령을 D3D12 네이티브 호출로 바꾸는 마지막 백엔드야.
  • FD3D12CommandContext는 주문서를 읽고 GraphicsCommandList()->... 버튼을 누르는 사람이다.
  • FD3D12StateCache는 PSO, 루트서명, 디스크립터 같은 상태를 기억해서 필요한 것만 D3D12에 세팅한다.
  • RHIDispatchComputeShader는 Dispatch, RHIDrawPrimitive는 DrawInstanced, clear는 ClearRenderTargetView/ClearDepthStencilView로 내려간다.
  • D3D12에서는 실제 호출 전에 descriptor commit, shader constants commit, resource barrier flush가 같이 따라온다.
