GPU 프로파일링과 디버깅

언리얼 렌더링 · 34 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "GPU 병목을 숫자, 이름표, 캡처 화면 중 어디서 봐야 하는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

서버를 짜봤으면 이런 순간을 알 거야. 동접이 늘었는데 랙이 나. 그런데 막상 CPU는 40%고, DB도 멀쩡하고, 네트워크 패킷도 밀리지 않아. 그럼 다음 질문은 이거지. 어느 구간이 진짜 오래 걸렸지?

렌더링도 똑같아. 프레임이 16.6ms 안에 끝나야 60fps인데, 화면은 24ms, 31ms, 48ms로 튄다. CPU에서 Render() 함수가 빨리 끝났다고 안심하면 안 돼. GPU는 뒤에서 따로 줄 서서 일을 하고 있으니까. CPU 로그만 보면 "명령은 빨리 냈는데요?"가 전부야. 정작 GPU가 BasePass에서 막혔는지, Shadow에서 막혔는지, PostProcess에서 막혔는지는 안 보여.

그래서 언리얼도 같은 문제를 만났고, 답이 GPU 프로파일링 이름표 + GPU 타임스탬프 쿼리 + 캡처 도구(RenderDoc/PIX)야. 패스마다 "나는 Prepass야", "나는 TAA야" 같은 이름표를 붙이고, GPU가 그 구간을 시작/끝낸 시각을 쿼리로 찍어. 그리고 필요하면 RenderDoc 같은 도구로 프레임 하나를 통째로 열어본다.

왜 지금 배우냐면, 앞 장까지 우리는 실제 렌더링 패스들을 봤어. PrePass, BasePass, Deferred Lighting, Shadow, Lumen, TAA, PostProcess. 이제 남은 질문은 "그중 뭐가 느린데?"야. 이 장은 앞에서 배운 패스 이름들을 성능 지도로 바꾸는 장이야. 막히면 → postprocess-chain, rdg, deferred-overview를 다시 보면 된다.

0. 비유부터 — 공장 라인에 초시계 붙이기

렌더링 프레임을 공장 라인이라고 치자. 상자 하나가 지나가면서 여러 작업대를 거쳐:

  1. 깊이 검사 작업대
  2. 재질 칠하기 작업대
  3. 그림자 작업대
  4. 조명 작업대
  5. 후처리 작업대
  6. 포장 작업대

프레임이 늦으면 사장이 묻겠지. "누가 늦었어?"

감으로 보면 망해. "아마 조명?" "아마 후처리?" 이러면 서버에서 락 병목을 느낌으로 찍는 거랑 같아.

공장에서는 작업대마다 초시계를 붙여야 해. 작업대에 이름표도 붙여야 해. 그리고 정말 이상하면 CCTV를 돌려서, 그 순간 어떤 작업자가 어떤 물건을 잡고 있었는지 봐야 해.

언리얼에서 이 셋이 이렇게 대응돼:

  • 이름표 = SCOPED_GPU_STAT, RDG_GPU_STAT_SCOPE, breadcrumb/event
  • 초시계 = GPU timestamp render query
  • CCTV = ProfileGPU, Unreal Insights, RenderDoc/PIX 캡처

이 비유를 끝까지 끌고 갈 거야. 우리는 지금 "공장 라인 어디가 막혔는지 찾는 법"을 배우는 중이야.

🌱 이 개념은 왜 생겼나 — GPU 프로파일링 이름표
• 원래 구조: 그냥 GPU 전체 시간이 24ms라고만 알면 돼 보였어. 공장 전체 퇴근 시간이 늦었다는 숫자 하나만 보는 거야.
• 그런데 문제: 작업대가 6개인데 숫자 하나만 있으면 누가 늦었는지 몰라. 서버 로그에 CM_ATTACK 이름 없이 "0.21ms"만 찍힌 느낌이야.
• 그래서 필요한 것: 각 패스가 자기 앞에 "나는 Prepass야" 같은 간판을 붙여야 해. 그게 SCOPED_GPU_STAT 같은 GPU 프로파일링 이름표야.

1. 먼저 이름표가 붙는다 — 패스 코드가 직접 "나 Prepass야"라고 말함

프로파일러가 렌더러 안을 저절로 읽는 게 아니야. 각 패스 코드가 자기 구간에 이름표를 붙여준다. 예를 들어 깊이 프리패스 쪽 코드를 보면, GPU stat과 breadcrumb가 같이 박혀 있어.

DepthRendering.cpp:692

SCOPED_NAMED_EVENT(FMobileSceneRenderer_RenderPrePass, FColor::Emerald); RHI_BREADCRUMB_EVENT_STAT(RHICmdList, Prepass, "MobileRenderPrePass"); SCOPED_GPU_STAT(RHICmdList, Prepass);
🔤 기호 사전 — 패스 이름표 토막
• SCOPED_NAMED_EVENT = CPU/툴에서 볼 이름표를 현재 스코프에 붙이는 매크로야.
• RHI_BREADCRUMB_EVENT_STAT = GPU 명령줄에 빵 부스러기처럼 추적 이름을 남기는 장치야.
• RHICmdList = GPU에게 보낼 명령을 적어두는 공책이야.
• Prepass = 이 구간의 stat 이름이야. 나중에 stat gpu나 캡처에서 이 이름으로 보인다.
• SCOPED_GPU_STAT = 여기부터 이 스코프가 끝날 때까지 GPU 시간을 재겠다는 표시야.
• ; = C++에서 "이 명령 끝"이라는 마침표야.
🔁 이제 다시 보자. SCOPED_NAMED_EVENT는 사람 눈에 보일 이름표를 달고 → RHI_BREADCRUMB_EVENT_STAT은 GPU 명령 흐름에 흔적을 남기고 → SCOPED_GPU_STAT은 실제 GPU 시간을 잴 계측 스코프를 연다. 공장 작업대 앞에 "Prepass 작업대" 간판과 초시계를 같이 붙이는 장면이야.

여기서 중요한 건 이거야. 병목 표에 Prepass가 보이면, 그 이름은 하늘에서 떨어진 게 아니야. 렌더링 코드가 직접 붙인 이름이야.

서버에서도 SP_LOGIN, SP_MOVE, CM_ATTACK 같은 패킷 이름을 로그에 붙여야 "어느 패킷이 느린지" 볼 수 있잖아. 렌더링도 똑같다. 이름표가 없으면 숫자가 떠도 어디 숫자인지 몰라.

2. 스코프 객체가 생성될 때 시작, 사라질 때 끝

SCOPED_GPU_STAT 같은 매크로는 결국 스코프 객체를 만든다. C++에서 지역 객체는 생성자에서 시작하고, 스코프를 벗어나면 소멸자에서 끝난다. 이 패턴은 서버에서 ScopedLock 쓰는 감각이랑 거의 같아.

FScopedGPUStatEvent를 보면 생성자에서 PushStat, 소멸자에서 PopStat을 호출한다.

RealtimeGPUProfiler.cpp:1019

FScopedGPUStatEvent::FScopedGPUStatEvent(FRHICommandListBase& InRHICmdList, const FName& Name, const TStatId& StatId, const TCHAR* Description) { if (!AreGPUStatsEnabled()) { return; } if (InRHICmdList.IsImmediate() && EnumHasAnyFlags(InRHICmdList.GetPipeline(), ERHIPipeline::Graphics)) { RHICmdList = &InRHICmdList; FRealtimeGPUProfiler::Get()->PushStat(InRHICmdList.GetAsImmediate(), Name, StatId, Description); } } FScopedGPUStatEvent::~FScopedGPUStatEvent() { if (!RHICmdList) { return; } if (RHICmdList != nullptr) { // Command list is initialized only if it is immediate during Begin() and GetAsImmediate() also internally checks this. FRealtimeGPUProfiler::Get()->PopStat(RHICmdList->GetAsImmediate()); } }
🔤 기호 사전 — 스코프 객체 토막
• FScopedGPUStatEvent::FScopedGPUStatEvent = 생성자야. 물건이 만들어질 때 자동으로 불린다.
• ~FScopedGPUStatEvent = 소멸자야. 물건이 사라질 때 자동으로 불린다.
• if (!AreGPUStatsEnabled()) = GPU stat이 꺼져 있으면 아무것도 하지 말라는 뜻이야.
• && = 둘 다 참이어야 한다는 "그리고"야.
• EnumHasAnyFlags = 플래그 묶음 안에 원하는 표시가 들어 있는지 보는 함수야.
• ERHIPipeline::Graphics = 그래픽스 파이프라인 쪽 명령인지 보는 이름표야.
• &InRHICmdList = 이 명령 공책의 주소를 저장한다는 뜻이야.
• FRealtimeGPUProfiler::Get() = 싱글턴 프로파일러를 꺼내오는 호출이야.
• -> = 포인터가 가리키는 대상의 기능을 부를 때 쓰는 화살표야.

여기서 감을 잡아야 해. SCOPED_GPU_STAT은 "지금 당장 결과를 계산해줘"가 아니야. "여기서부터 시작이야" 하고 Push하고, 스코프 끝에서 "여기서 끝이야" 하고 Pop하는 구조야.

서버로 치면 이거랑 같아: 패킷 핸들러 입구에서 StartTick = Now(), 함수 끝에서 EndTick = Now(), 그 차이를 누적해서 CM_ATTACK = 0.21ms 같은 표를 만드는 거야. 차이는 하나뿐이야. CPU 시간은 바로 읽을 수 있지만, GPU 시간은 GPU가 명령을 실제로 끝낼 때까지 기다려야 한다.

3. 이벤트 하나는 시작 쿼리와 끝 쿼리 두 장을 가진다

이제 초시계의 실물을 보자. FRealtimeGPUProfilerEvent는 이벤트 하나마다 start query와 end query를 가진다. 작업대 입구와 출구에 각각 도장 기계를 둔 셈이야.

RealtimeGPUProfiler.cpp:46

FRealtimeGPUProfilerEvent(FRHIRenderQueryPool& RenderQueryPool) : StartResultMicroseconds(InPlace, InvalidQueryResult) , EndResultMicroseconds(InPlace, InvalidQueryResult) , StartQuery(RenderQueryPool.AllocateQuery()) , EndQuery(RenderQueryPool.AllocateQuery()) , FrameNumber(-1) , DescriptionLength(0) #if DO_CHECK || USING_CODE_ANALYSIS , bInsideQuery(false) #endif { check(StartQuery.IsValid() && EndQuery.IsValid()); }
🔤 기호 사전 — 시작/끝 쿼리 토막
• FRealtimeGPUProfilerEvent(...) = 이벤트 하나를 만들 때 도는 생성자야.
• FRHIRenderQueryPool& = query를 빌려오는 풀을 원본 그대로 참조한다는 뜻이야.
• StartResultMicroseconds = 시작 시각 결과를 담을 칸이야.
• EndResultMicroseconds = 끝 시각 결과를 담을 칸이야.
• AllocateQuery() = GPU timestamp query 한 장을 풀에서 꺼내는 호출이야.
• InvalidQueryResult = 아직 결과가 없다는 표시값이야.
• FrameNumber(-1) = 아직 프레임 번호가 정해지지 않았다는 초기값이야.
• check(...) = 개발 중 조건이 틀리면 바로 잡아내는 안전 검사야.
🔁 이제 다시 보자. 생성자에서 StartQuery와 EndQuery를 둘 다 할당하고 → 결과 칸은 InvalidQueryResult로 비워두고 → 마지막에 두 query가 유효한지 검사한다. 이벤트 하나가 입구 도장과 출구 도장을 한 쌍으로 들고 태어나는 장면이야.

아까 비유로 돌아가자. 작업대에 작업자가 들어올 때 카드 찍고, 나갈 때 카드 찍는 거야. Begin이 입구 카드, End가 출구 카드야.

여기서는 아직 시간이 나온 게 아니야. "찍을 쿼리 객체"만 준비한 거고, 실제로 GPU 명령줄에 쿼리를 끼워 넣는 건 다음 단계야.

🌱 이 개념은 왜 생겼나 — GPU 타임스탬프 쿼리
• 원래 구조: CPU처럼 작업 시작할 때 Now(), 끝날 때 Now()를 바로 읽으면 될 것 같아.
• 그런데 문제: GPU는 뒤쪽 공장 라인에서 나중에 일해. CPU가 지금 시간을 읽어도 GPU가 그 작업대를 아직 지나가지 않았을 수 있어.
• 그래서 필요한 것: GPU 명령줄에 "여기 지나갈 때 시간 찍어줘"라는 도장 카드를 꽂아야 해. 그게 timestamp query야. query는 나중에 답을 받는 질문표라고 보면 돼.

4. 쿼리는 RHI 명령 리스트에 제출된다

준비한 쿼리는 Submit에서 RHI 명령 리스트에 들어간다. 코드를 보면 이상하게도 시작과 끝 둘 다 EndRenderQuery를 호출해. 이 이름은 헷갈릴 수 있는데, 여기서는 "timestamp query를 명령 스트림에 기록한다"는 쪽으로 보면 돼.

RealtimeGPUProfiler.cpp:264

void FRealtimeGPUProfilerQuery::Submit(FRHICommandList& RHICmdList, bool bBegin) const { if (Query) { SCOPED_GPU_MASK(RHICmdList, GPUMask); RHICmdList.EndRenderQuery(Query); if (bBegin) { Parent->bStarted = true; } else { Parent->bEnded = true; } } }
🔤 기호 사전 — 쿼리 제출 토막
• Submit = 준비한 query를 실제 RHI 명령 리스트에 넣는 함수야.
• FRHICommandList& = GPU 명령 공책을 빌려 쓰는 참조야. &는 복사하지 않고 원본을 가리킨다는 뜻이야.
• bool bBegin = 시작 쿼리인지 끝 쿼리인지 알려주는 참/거짓 값이야.
• if (Query) = query 손잡이가 비어 있지 않으면 실행한다는 뜻이야.
• SCOPED_GPU_MASK = 어느 GPU에 쿼리를 찍을지 잠깐 범위를 잡는 매크로야.
• RHICmdList.EndRenderQuery(Query) = RHI 명령줄에 query 지점을 기록하는 호출이야.
• Parent->bStarted = 부모 이벤트에 "시작점은 제출됨" 표시를 남긴다.
• Parent->bEnded = 부모 이벤트에 "끝점은 제출됨" 표시를 남긴다.
🔁 이제 다시 보자. Submit은 query가 있으면 → GPU 마스크를 맞추고 → EndRenderQuery(Query)로 명령 리스트에 타임스탬프를 찍고 → bBegin이면 시작 완료, 아니면 종료 완료 표시를 남긴다. 공장 라인에 "여기서 카드 찍어"라는 명령을 실제로 꽂는 장면이야.

여기서 CPU/GPU 분리를 다시 떠올려야 해. CPU는 명령 리스트에 "여기서 시간 찍어"라고 적어. GPU는 나중에 그 명령을 실행하다가 실제 시간을 찍어. 그래서 결과를 바로 읽으면 아직 없을 수 있어.

이게 서버의 async IO랑 닮았어. IOCP에서 WSARecv를 걸었다고 그 순간 패킷이 온 게 아니잖아. 완료 통지가 나중에 오지. GPU timestamp query도 비슷해. 명령을 걸어두고, 나중에 결과가 준비됐을 때 읽는다.

🌱 이 개념은 왜 생겼나 — inclusive/exclusive 시간
• 원래 구조: 작업대 하나가 8ms 걸렸다고 표에 쓰면 끝인 것 같아.
• 그런데 문제: 그 8ms 안에 TAA 3ms, Bloom 1ms처럼 작은 작업대들이 들어 있으면 누가 진짜 늦었는지 헷갈려. 부모 작업대를 억울하게 범인으로 찍을 수 있어.
• 그래서 필요한 것: 자식까지 포함한 시간과 자기 혼자 먹은 시간을 나눠 봐야 해. 포함한 게 inclusive, 자기 몫만 남긴 게 exclusive야.

5. 프레임 끝에서 결과를 모으고, inclusive/exclusive 시간을 만든다

프레임이 끝나면 이제 결과를 모아야 해. 언리얼은 pending event들을 돌면서 query 결과가 준비됐는지 확인한다. 아직 안 됐으면 이번 프레임 stat 업데이트를 미루고, 준비됐으면 inclusive/exclusive 시간을 계산한다.

• #if GPUPROFILERTRACE_ENABLED = 빌드 옵션이 켜졌을 때만 이 코드를 넣는 전처리 조건이야.
• for (; ...; ++...) = 앞 초기식 없이 조건과 증가식만 있는 반복문이야.
• GatherQueryResults = GPU가 찍은 timestamp query 결과를 읽어오는 함수야.
• return false = 아직 결과가 준비 안 됐으니 이번엔 실패라고 알려준다.
• InclusiveTimeUs = 자식 작업까지 포함한 전체 시간, 마이크로초 단위야.
• ExclusiveTimeUs = 자식 작업 시간을 뺀 자기 순수 시간이야.
• ParentIdx = 이벤트 트리에서 부모 이벤트의 번호야.
• -= = 왼쪽 값에서 오른쪽 값을 빼서 다시 왼쪽에 저장한다는 뜻이야.
🔁 이제 다시 보자. UpdateStats는 이벤트마다 GatherQueryResults로 결과를 읽고 → 준비 안 됐으면 다음 프레임으로 미루고 → 준비됐으면 inclusive 시간을 만든다. 그다음 부모의 exclusive 시간에서 자식 inclusive 시간을 빼. 즉 "작업대 전체 체류 시간"과 "이 작업대가 순수하게 잡아먹은 시간"을 나누는 장면이야.

이 차이가 병목 분석에서 진짜 중요해.

PostProcess = 8ms라고 해보자. 그 안에 TAA = 3ms, Bloom = 1ms, Tonemap = 0.5ms가 들어 있으면, PostProcess의 inclusive는 8ms야. 하지만 exclusive는 자식 시간을 뺀 나머지야.

서버에서도 똑같아. ProcessPacket()이 10ms라고 해서 그 함수 자체가 느린 게 아닐 수 있어. 안에서 DBQuery()가 9ms면 병목은 DB지, 패킷 디스패처가 아니잖아.

GPU stat 표를 볼 때도 그래서 물어야 해.

  • inclusive가 큰가?
  • exclusive가 큰가?
  • 자식 중 하나가 독식하나?
  • [unaccounted] 같은 빈 시간이 큰가?
  • VSync나 캡처 오버헤드가 섞였나?
🌱 이 개념은 왜 생겼나 — RenderDoc/PIX 캡처
• 원래 구조: stat gpu 표만 보고 제일 큰 숫자부터 줄이면 될 것 같아.
• 그런데 문제: TAA 4ms라는 숫자는 "늦다"만 말해. 텍스처가 큰지, dispatch가 많은지, 배리어에서 막혔는지는 안 보여.
• 그래서 필요한 것: 프레임 하나를 CCTV처럼 열어서 draw/dispatch와 리소스를 직접 봐야 해. 그 역할을 하는 캡처 도구가 RenderDoc/PIX야.

6. RenderDoc/PIX는 CCTV다 — 캡처 모드에서는 이벤트 이름을 더 잘 보이게 켠다

숫자만으로 안 풀리는 문제가 있어. 예를 들어 TAA가 4ms인데 왜 4ms인지 알고 싶어. 샘플 수 때문인지, 해상도 때문인지, 리소스 배리어 때문인지, 특정 텍스처가 비정상인지, 숫자 표만으로는 부족해.

그때 ProfileGPU로 한 프레임 보고서를 뽑거나, RenderDoc/PIX로 프레임을 연다. 언리얼 D3D12RHI는 RenderDoc 아래에서 실행 중인지 감지하는 코드도 가지고 있어.

D3D12Device.cpp:297

#if PLATFORM_WINDOWS // Check if we're running under GPU capture bool bUnderGPUCapture = false; // RenderDoc if (D3D12RHI_IsRenderDocPresent(Direct3DDevice)) { // Running under RenderDoc, so enable capturing mode bUnderGPUCapture = true; }
🔤 기호 사전 — RenderDoc 감지 토막
• #if PLATFORM_WINDOWS = 윈도우 빌드에서만 이 코드를 넣는 조건이야.
• bUnderGPUCapture = GPU 캡처 도구 아래에서 실행 중인지 나타내는 참/거짓 값이야.
• D3D12RHI_IsRenderDocPresent = D3D12 장치에 RenderDoc이 붙어 있는지 확인하는 함수야.
• Direct3DDevice = 실제 D3D12 디바이스 객체야.
• true = 맞다, 켜짐, 참이라는 값이야.
• // RenderDoc = 이 아래 블록이 RenderDoc 감지용이라는 사람용 메모야.

이렇게 감지되면 언리얼은 캡처 도구가 읽기 좋은 이벤트 이름을 살리려 한다. RenderDoc 화면에서 DrawIndexed만 수천 줄 보이면 길을 잃지만, Prepass, ShadowProjection, TemporalSuperResolution 같은 이름표가 보이면 stat gpu에서 본 병목과 캡처 안의 draw/dispatch 묶음이 이어진다.

7. 병목을 어디서 보나 — 읽는 순서

실전 순서는 단순해. 먼저 GPU total을 본다. 16.6ms를 넘으면 60fps가 안 나오고, CPU가 빠른데 GPU total만 크면 GPU 병목이다.

그다음 큰 이름표를 본다. ShadowProjection, Basepass, RenderDeferredLighting, Postprocessing, TemporalSuperResolution, LumenSceneLighting처럼 큰 작업대부터 봐. inclusive가 큰데 exclusive가 작으면 자식 중에 범인이 있고, exclusive도 크면 그 작업대 자체가 오래 잡아먹는 거야.

마지막으로 캡처 도구로 넘어간다. "TAA가 크다"까지는 stat이 알려주고, "왜 이 dispatch가 느린가"는 RenderDoc/PIX에서 스레드 그룹, 텍스처 크기, UAV/SRV, 배리어를 봐야 한다. 단, 캡처를 켜면 이벤트와 동기화가 늘 수 있으니 숫자 절대값은 다시 확인해야 해.

콜/데이터 흐름 한눈에

공장 라인 초시계 흐름은 이렇게 읽으면 돼.

렌더 패스 코드 -> SCOPED_GPU_STAT(..., Prepass) DepthRendering.cpp:694 -> FScopedGPUStatEvent 생성자 RealtimeGPUProfiler.cpp:1019 -> FRealtimeGPUProfilerQuery::Submit(begin=true) RealtimeGPUProfiler.cpp:264 -> GPU 명령줄에 start timestamp query 기록 -> 스코프 종료 -> FScopedGPUStatEvent 소멸자 RealtimeGPUProfiler.cpp:1033 -> FRealtimeGPUProfilerQuery::Submit(begin=false) RealtimeGPUProfiler.cpp:264 -> GPU 명령줄에 end timestamp query 기록 -> 프레임 끝 UpdateStats RealtimeGPUProfiler.cpp:437 -> stat gpu / CSV / trace / history로 노출

ProfileGPU는 한 프레임 보고서 버튼이고, RenderDoc/PIX는 그 보고서로도 이유가 안 보일 때 여는 CCTV야.

우리 서버·DirectX 랑 비교

서버 감각으로 보면 GPU profiler는 패킷 처리 시간표야. CM_ATTACK 핸들러 이름이 Prepass/TAA 같은 GPU stat 이름이고, 핸들러 입구·출구 Now()가 start/end timestamp query야. 핸들러별 평균/최대 시간이 stat gpu, CSV, Insights로 나오고, 특정 요청 하나를 추적하는 게 ProfileGPU 한 프레임 보고서야. 패킷 바이트 덤프처럼 더 깊게 보는 도구가 RenderDoc/PIX고.

DirectX 감각으로 보면 timestamp query heap에 시간을 찍고 readback하는 흐름과 같다. 언리얼은 그걸 RHI와 stat 시스템으로 감싸고, 이름표 계층을 얹어서 draw/dispatch 수천 개를 사람이 읽을 수 있게 만든다. GPU query 결과가 늦게 오는 점은 IOCP 완료 통지 기다리는 감각으로 읽으면 된다.

이 챕터에서 딱 이것만

  • SCOPED_GPU_STAT은 패스에 GPU 시간 이름표를 붙이는 입구야.
  • FScopedGPUStatEvent는 생성자 Push, 소멸자 Pop으로 스코프 시간을 잰다.
  • 실제 GPU 시간은 start/end timestamp query를 RHI 명령 리스트에 제출해서 얻는다.
  • UpdateStats는 늦게 도착한 query 결과를 모아 inclusive/exclusive 시간으로 바꾼다.
  • ProfileGPU는 한 프레임 보고서, RenderDoc/PIX는 그 프레임의 CCTV야.

🎯 원리 한 줄 요약

GPU 프로파일링은 패스마다 이름표를 붙이고, GPU 명령줄에 start/end 초시계를 꽂고, 나중에 그 결과를 트리와 캡처로 읽어서 "어느 작업대가 늦었는지" 찾는 장치다.
