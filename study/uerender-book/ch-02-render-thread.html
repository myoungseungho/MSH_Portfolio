게임 스레드 vs 렌더 스레드 — 왜 나눴나

언리얼 렌더링 · 02 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "게임 로직과 렌더링이 왜 한 줄로 서지 않고, 명령 큐와 펜스로 느슨하게 이어지는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

잠깐. "렌더 스레드"라고 하면 이름부터 좀 멀게 느껴져. 하지만 네가 서버를 해봤으면 이미 같은 문제를 겪었어.

IOCP 워커가 패킷을 받았다고 해서, 그 자리에서 바로 게임 로직을 다 돌리진 않잖아. 워커는 바이트를 줍고, 세션에 붙이고, 게임 로직 쪽 큐로 넘겨. 그리고 월드 상태는 보통 한 스레드에서 순서대로 만져.

렌더링도 똑같은 압박을 받아. 게임 스레드가 액터 이동, 애니메이션, 물리, 입력을 처리하는데, 그 자리에서 "좋아, 이제 GPU 명령까지 전부 만들어서 제출하고, 끝날 때까지 기다리자"를 해버리면 어떻게 될까?

60FPS면 한 프레임 예산은 약 16.6ms야. 게임 로직 8ms, 렌더 준비 7ms, GPU 제출 기다림 4ms가 한 줄로 붙으면 벌써 19ms야. 한 번만 삐끗해도 프레임이 밀려. 입력도 늦게 먹고, 카메라 회전도 끊겨.

그래서 언리얼도 같은 문제를 만났고, 답이 게임 스레드와 렌더 스레드 분리야. 게임 스레드는 "이번 프레임에 그려야 할 일"을 명령으로 포장해서 넘기고, 렌더 스레드는 그 명령을 자기 줄에서 처리해. 둘은 매 순간 붙어 있지 않고, 필요할 때만 펜스로 기다려.

왜 지금 배우냐면, 바로 앞 cpu-vs-gpu에서 CPU와 GPU가 다른 세계라는 걸 봤지. 이번 장은 그 CPU 안에서도 다시 한 번 갈라지는 지점이야. 여기를 잡아야 다음 rhi-overview에서 "렌더 스레드가 RHI로 내려간다"는 말이 허공에 안 뜬다.

0. 비유부터 — 주문 받는 홀과 요리하는 주방

식당을 하나 떠올려봐. 홀 직원은 손님을 보고 주문을 받아. 주방 직원은 주문서를 보고 요리를 만들어.

홀 직원이 주문 받을 때마다 주방까지 뛰어가서 직접 요리하고 돌아오면? 손님 줄은 바로 막혀. 물 달라는 손님, 계산하려는 손님, 새로 들어온 손님이 전부 기다려.

그래서 보통은 이렇게 나눠.

  1. 홀 직원이 주문을 받는다. (게임 스레드)
  2. 주문서를 레일에 올린다. (렌더 명령 enqueue)
  3. 주방이 자기 속도로 주문서를 꺼내 요리한다. (렌더 스레드)
  4. 정말 꼭 필요할 때만 홀 직원이 "저 주문 끝났어?" 하고 기다린다. (펜스/Flush)
  5. 장사가 너무 앞서가면 홀과 주방 사이 간격을 조절한다. (프레임 지연 제한)

이 챕터의 비유는 끝까지 이거야. 게임 스레드 = 홀, 렌더 스레드 = 주방, 렌더 명령 = 주문서, 펜스 = 주문 완료 확인표.

언리얼의 RenderingThread.cpp와 RenderingThread.h는 이 식당의 레일, 주방, 확인표가 어떻게 생겼는지 보여주는 파일이야.

🌱 이 개념은 왜 생겼나 — 명령 큐(렌더 커맨드)
• 원래 구조: 제일 단순한 게임은 한 스레드가 다 해. 입력 받고 → 로직 굴리고 → 그리고 → 화면에 띄우고. 순서대로 한 줄.
• 그런데 문제: 그리는 일(GPU에 명령 보내기)은 기다리는 시간이 많아. 그 동안 CPU는 놀아. 게다가 요즘 CPU는 코어가 8개 16개인데 한 줄로 서면 한 코어만 일해. 나머지는 구경만 해.
• 그래서 필요한 것: 게임 로직과 그리기를 다른 사람에게 맡기자. 근데 두 사람이 같은 물건을 동시에 만지면 싸워. 그러니 직접 만지지 말고 "주문서"를 던져주자. → 이게 렌더 명령 큐야. 홀은 주문서만 던지고 바로 다음 손님을 받아.
🧱 먼저 알아야 할 것 — 줄서기와 차례
• 줄서기: 사람들이 매표소 앞에 서면 먼저 온 사람이 먼저 일을 본다.
• 차례 유지: 종이를 줄 끝에 꽂아두면 앞 종이가 끝난 뒤에 다음 종이를 꺼낼 수 있다.
• 맡기고 떠나기: 종이를 맡긴 사람은 그 일이 끝날 때까지 옆에 붙어 있지 않아도 된다.
이게 잡히면 아래 설명이 얹힌다.

1. 홀에서 바로 요리하지 않는다 — 먼저 주문서로 넘긴다

렌더 명령을 넣는 입구부터 보자. ENQUEUE_RENDER_COMMAND(...)라는 매크로를 많이 보게 될 텐데, 그 끝은 FRenderCommandDispatcher::Enqueue 쪽으로 간다.

핵심은 이 조건이야. 지금 렌더 스레드가 아니고, 렌더 스레드에서 실행해야 하는 상황이면 큐에 넣는다. 그게 아니면 바로 실행한다.

RenderingThread.h:593

template <typename RenderCommandTag, typename LambdaType> static void Enqueue(LambdaType&& Lambda) { const FRenderCommandTag& Tag = RenderCommandTag::Get(); TRACE_CPUPROFILER_EVENT_SCOPE_USE_ON_CHANNEL(Tag.GetSpecId(), Tag.GetName(), EventScope, RenderCommandsChannel, true); if (!IsInRenderingThread() && ShouldExecuteOnRenderThread()) { CheckNotBlockedOnRenderThread(); if (GRenderCommandPipeMode != ERenderCommandPipeMode::None) { Instance.EnqueueAndLaunch(MoveTemp(Lambda), Tag); } else { TGraphTask<TRenderCommandTask<LambdaType>>::CreateTask().ConstructAndDispatchWhenReady(MoveTemp(Lambda), Tag); } } else { FScopeCycleCounter CycleScope(Tag.GetStatId()); Lambda(GetImmediateCommandList_ForRenderCommand()); } }
🔤 기호 사전 — 렌더 명령 넣는 입구
• template <typename ...> = 어떤 람다/태그가 오든 같은 틀로 처리하겠다는 C++ 틀 문법이야.
• LambdaType&& Lambda = 실행할 작은 함수 덩어리를 받는다. &&는 여기서 "넘겨받아 옮길 수 있음"에 가까워.
• const FRenderCommandTag& Tag = 렌더 명령 이름표를 읽기 전용 참조로 잡는다. &는 복사하지 말고 원본을 보겠다는 뜻이야.
• !IsInRenderingThread() = 지금 렌더 스레드가 아니라는 뜻. !는 참/거짓을 뒤집어.
• ShouldExecuteOnRenderThread() = 이 명령을 렌더 스레드에서 실행해야 하는지 묻는 스위치야.
• Instance.EnqueueAndLaunch(...) = 명령 파이프에 넣고 실행되게 만든다. 홀 직원이 주문서를 레일에 올리는 장면이야.
• TGraphTask<...>::CreateTask() = 태스크 그래프에 일을 하나 만들어 넣는다. 파이프를 안 쓰는 경로야.
• MoveTemp(Lambda) = 람다를 복사하지 말고 "이쪽으로 옮겨"라는 표시야.
• Lambda(GetImmediateCommandList_ForRenderCommand()) = 큐에 안 넣고 지금 바로 실행하는 길. 이미 주방 안에 있으면 주문서를 또 레일에 올릴 필요가 없지.
🔁 이제 다시 보자. !IsInRenderingThread()는 "지금 홀에 있나?"를 묻고, ShouldExecuteOnRenderThread()는 "이 주문은 주방 일이 맞나?"를 묻는다. 둘 다 맞으면 EnqueueAndLaunch나 TGraphTask로 주문서를 넘기고, 아니면 Lambda(...)로 바로 처리해. 그러니까 렌더 명령의 기본 자세는 "게임 스레드에서 직접 그리지 말고, 렌더 스레드 줄에 세우자"야.

여기서 중요한 건 Lambda야. 게임 스레드는 보통 "나중에 렌더 스레드가 실행할 작은 함수"를 만들어 넘겨. 즉 렌더 스레드는 게임 오브젝트를 막 만지는 게 아니라, 게임 스레드가 포장해준 렌더용 작업을 받는다.

서버로 치면 IOCP 워커가 CSession을 직접 마음대로 바꾸는 게 아니라, 액터 큐에 SP_MOVE_REQ 처리해 같은 일을 넣는 느낌이야. 그 큐가 있어야 락 지옥을 피하고 순서를 만들 수 있지.

2. 주방은 따로 돌고, 주문서를 계속 꺼내 먹는다

그럼 렌더 스레드는 어디서 기다리고 있을까? RenderingThreadMain이 주방의 메인 루프야.

초반에 태스크 그래프에 붙고 준비 이벤트를 게임 스레드에 알려준 뒤, 핵심 루프로 들어간다. 그 핵심은 ProcessThreadUntilRequestReturn(RenderThread)야. 이 줄이 렌더 스레드가 자기 큐를 계속 처리하는 자리다.

🔤 기호 사전 — 렌더 스레드 메인 루프
• Broadcast() = 등록된 구독자들에게 이벤트를 뿌린다.
• check(GIsThreadedRendering) = 렌더 스레드 모드가 켜져 있어야 한다는 검사야.
• FScopedRHIThreadOwnership = 현재 스레드가 RHI 쪽 소유권을 잡을지 정하는 작은 RAII 상자야.
• ProcessThreadUntilRequestReturn(RenderThread) = "돌아가라는 요청이 올 때까지 렌더 스레드 태스크를 계속 처리해"라는 핵심 루프야.
🔁 이제 다시 보자. 렌더 스레드는 생성 알림을 뿌린 뒤 check(GIsThreadedRendering)로 모드를 확인하고, ProcessThreadUntilRequestReturn(RenderThread)에서 주문서를 계속 꺼내 처리해. 주방이 열린 뒤 레일을 바라보고 계속 요리하는 그림이지.

이 구조 덕분에 게임 스레드는 렌더 일을 "함수 호출"로 바로 끝내지 않아도 돼. 작업을 큐에 올리고 자기 일을 이어갈 수 있어. 렌더 스레드는 자기 차례대로 명령을 먹는다.

물론 아무 데이터나 공유하면 위험해. 그래서 이후 챕터 scene-proxy에서 게임 오브젝트의 렌더용 사본이 왜 필요한지 보게 된다. 이번 장에서는 일단 "직접 만지는 대신 명령을 넘긴다"만 잡으면 돼.

🧱 먼저 알아야 할 것 — 신호와 기다림
• 신호: 멀리 있는 사람이 일을 끝내면 손을 들거나 종을 쳐서 알려줄 수 있다.
• 기다림: 아직 신호가 안 왔으면 다음 일을 시작하지 않고 그 자리에서 멈춰 선다.
• 확인표: 여기까지 끝났다는 표시를 남기면 나중에 끝났는지 다시 물어볼 수 있다.
이게 잡히면 아래 설명이 얹힌다.

3. 렌더 스레드 시작은 그냥 스레드 하나 만드는 게 아니다

이제 식당 오픈 장면을 보자. StartRenderingThread는 게임 스레드에서 호출된다. 실제로 파일에는 check(IsInGameThread())도 있다.

아래 토막은 중간 핵심부야. 렌더 스레드 플래그를 켜고, FRenderingThread 러너를 만들고, OS 스레드를 생성한 뒤, 렌더 스레드가 태스크 그래프에 붙을 때까지 기다린다.

// Turn on the threaded rendering flag. GIsThreadedRendering = true; // Create the rendering thread. ((FRenderingThread*)GRenderingThreadRunnable)->TaskGraphBoundSyncEvent->Wait();
🔤 기호 사전 — 렌더 스레드 시작
• GIsThreadedRendering = true = 이제 렌더링을 별도 스레드로 돌린다는 전역 깃발을 세운다.
• new FRenderingThread() = 렌더 스레드에서 실행될 러너 객체를 만든다.
• FRunnableThread::Create(...) = 실제 OS 스레드를 만든다. 주방 직원을 고용하는 줄이야.
• BuildRenderingThreadName(ThreadCount) = 스레드 이름을 만든다. 디버거나 프로파일러에서 보려고 붙이는 이름표야.
• TaskGraphBoundSyncEvent->Wait() = 렌더 스레드가 태스크 그래프에 붙을 때까지 게임 스레드가 기다린다.
🔁 이제 다시 보자. GIsThreadedRendering으로 식당을 스레드 모드로 바꾸고 → FRunnableThread::Create로 주방 직원을 만들고 → TaskGraphBoundSyncEvent->Wait()로 주방이 레일에 붙을 때까지 기다려. 주방이 레일에 붙기 전에는 주문서를 던지지 않겠다는 안전장치야.

여기서 Wait()가 무조건 나쁜 건 아니야. 시작할 때는 기다려야 해. 주방이 레일에 붙기도 전에 주문서를 던지면 주문서가 어디로 가겠어.

중요한 건 매 프레임 모든 작업마다 기다리지 않는다는 거야. 시작/종료/리소스 파괴처럼 경계가 필요한 지점에서만 기다린다. 평소에는 홀과 주방이 겹쳐서 움직인다.

🌱 이 개념은 왜 생겼나 — 펜스(Fence)
• 원래 구조: 홀(게임 스레드)은 주문서를 큐에 던지고 곧장 다음 프레임 일을 시작해. 주방(렌더 스레드)은 뒤에서 알아서 따라와. 서로 안 기다리니까 둘 다 쉬지 않고 돌아 — 빨라진 이유가 이거야.
• 그런데 문제: 홀이 주방보다 너무 멀리 앞서가면? ① 주방이 아직 읽고 있는 재료(액터 데이터)를 홀이 덮어써 버려 → 화면이 깨지거나 크래시. ② 주문이 계속 쌓여 열 장이 밀리면, 내가 마우스를 움직여도 화면은 열 프레임 뒤에 반응해 → 조작이 굼떠져.
• 그래서 필요한 것: "여기까지는 주방이 진짜 다 처리했다"를 확인할 수단. 홀은 그 지점보다 더 앞서가지 않기로 약속해. → 이게 펜스야. 이름 그대로 울타리 — "여기 넘어오지 마"를 세워두는 것.

4. 펜스는 "여기까지 했어?" 확인표다

펜스는 이름이 멋있지만, 식당 비유로는 확인표야. "이 주문서까지 처리하면 이 이벤트를 켜줘." 게임 스레드는 그 이벤트를 기다리면 된다.

FRenderCommandFence::BeginFence의 핵심은 렌더 명령 하나를 큐에 넣고, 그 명령이 렌더 스레드에서 실행될 때 Event.Trigger()를 호출하게 만드는 거야.

🔁 이제 다시 보자. ENQUEUE_RENDER_COMMAND(BeginFence)는 확인표 자체도 렌더 명령으로 넣어. 렌더 스레드가 그 지점까지 오면 Event.Trigger()가 찍히고, 게임 스레드는 CompletionTask를 보고 기다릴 수 있어. 더 깊게 기다려야 하면 Swapchain이나 RHIThread 선행조건을 붙여서 "주방 조리 완료"보다 더 뒤까지 확인한다.

그 확인표를 실제로 기다리는 쪽은 짧다.

🔁 이제 다시 보자. BeginFence는 확인표를 렌더 스레드 큐에 넣고, Wait는 그 확인표가 끝날 때까지 게임 스레드를 세운다. 그래서 펜스는 "락"이라기보다 "주문 레일 위 특정 위치까지 주방이 왔는지 확인하는 번호표"에 가깝다.

이게 동기화 지점이야. 평소에는 주문서를 계속 넘기지만, 리소스를 지우거나 종료하거나 프레임 간격을 맞출 때는 "여기까지는 끝났어야 해"라고 선을 긋는다.

서버에서도 비슷한 게 있어. 세션을 삭제하려는데 IOCP 워커가 아직 그 세션 버퍼를 만질 수 있으면 바로 free 하면 터지잖아. 그래서 참조 카운트, 완료 이벤트, 큐 drain 같은 걸 둔다. 렌더 스레드의 펜스도 같은 감각으로 읽으면 된다.

🌱 이 개념은 왜 생겼나 — 프레임 지연(frame lag)
• 원래 구조: 펜스로 "너무 앞서가지 마"를 막았어. 그럼 딱 한 프레임만 앞서게 할까? 아니면 두 프레임?
• 그런데 문제: 너무 바짝 붙이면(0프레임) 홀이 매번 주방을 기다려서 분업한 의미가 사라져 — 다시 한 줄 서기가 돼. 반대로 너무 떨어뜨리면 조작이 굼떠져(위 ②).
• 그래서 필요한 것: "몇 프레임까지 앞서도 되는가"라는 다이얼. 보통 1프레임을 허용해 — 성능(분업 유지)과 반응성(입력 지연) 사이의 타협점이야. 공짜 점심은 없어.
🧱 먼저 알아야 할 것 — 앞서감과 시간차
• 앞서감: 두 사람이 이어달리기처럼 일할 때 앞사람이 너무 멀리 가면 뒷사람 상태를 보고 맞추기 어렵다.
• 시간차: 지금 한 행동의 결과가 조금 뒤에 보이면 몸이 둔하게 느껴진다.
• 간격 조절: 너무 붙으면 서로 기다리고, 너무 벌어지면 늦게 맞아떨어진다.
이게 잡히면 아래 설명이 얹힌다.

5. 프레임 지연 — 홀은 주방보다 너무 멀리 앞서가면 안 된다

이제 이 챕터의 핵심 질문으로 돌아오자. 왜 나눴냐? 겹쳐서 돌리려고.

하지만 너무 많이 겹치면 또 문제가 생겨. 게임 스레드가 3프레임, 4프레임 앞서가면 입력 지연이 커진다. 화면은 아직 옛날 주문을 요리 중인데, 홀은 이미 새 주문을 산더미처럼 쌓아둔 상태가 돼.

그래서 언리얼은 프레임 끝에서 간격을 조절한다. r.OneFrameThreadLag라는 CVar 이름 그대로, 렌더 스레드가 게임 스레드보다 한 프레임 정도 뒤처지는 걸 허용할지 정한다.

• r.OneFrameThreadLag = 게임 스레드가 렌더 스레드보다 한 프레임 앞서가는 걸 허용할지 정하는 콘솔 변수야.
• bFullSync = 완전히 맞춰 기다릴지 나타내는 참/거짓 값이야.
• CVarAllowOneFrameThreadLag.GetValueOnAnyThread() = 어느 스레드에서든 현재 설정값을 읽는다.
• RenderThreadFences.Emplace() = 렌더 스레드 확인표를 배열 끝에 새로 만든다.
• RenderThreadFences.Num() > (bFullSync ? 0 : 1) = 완전 동기면 남길 펜스가 0개, 한 프레임 지연 허용이면 1개까지만 남긴다는 뜻이야.
🔁 이제 다시 보자. bFullSync가 참이면 홀은 주방 일이 끝나기 전까지 다음 일을 시작하지 않아. 거짓이면 RenderThreadFences를 1개 남겨서 한 프레임 정도 겹치게 둔다. 성능을 위해 겹치되, 줄이 무한히 길어지지 않게 제한하는 장치야.

이게 "프레임 지연"의 정체야. 렌더 스레드가 뒤처지는 건 버그가 아니라 설계일 수 있어. 게임 스레드가 N프레임 명령을 만들 때, 렌더 스레드는 N-1프레임 명령을 처리할 수 있다. 그 사이 GPU는 더 아래에서 N-2 같은 일을 하고 있을 수도 있어.

파이프라이닝은 공짜가 아니야. 겹치면 처리량은 좋아지지만 지연이 늘 수 있어. 그래서 SyncDepth, NumFramesOverlap, r.OneFrameThreadLag, r.GTSyncType 같은 조절 장치가 있다.

7. 우리 서버·DirectX 랑 비교

우리 서버 감각으로 보면 제일 가까운 건 IOCP 워커와 게임 로직 큐 분리야.

개념우리 서버언리얼 렌더링
빠르게 받아 넘기는 쪽IOCP 워커가 완료 통지 받음게임 스레드가 렌더 명령 생성
순서대로 처리하는 쪽단일 게임 로직 스레드/액터 큐렌더 스레드

기다리는 지점세션 삭제 전 drain, 작업 완료 이벤트FRenderCommandFence::Wait

락으로 다 해결하려고 하면 망한다는 것도 똑같아. 게임 스레드와 렌더 스레드가 같은 UObject를 마구 같이 만지면 락이 필요하고, 락을 많이 걸면 프레임 시간은 흔들려. 그래서 언리얼은 렌더 명령, 프록시, 펜스 같은 구조로 "공유를 줄이고 순서를 만든다".

DirectX 경험으로 보면 커맨드 리스트와 비슷해. CPU가 GPU에게 바로 "지금 당장 이 삼각형 그려"라고 말하는 게 아니라, 명령을 기록하고 제출하잖아. 언리얼의 렌더 스레드는 그 CPU 쪽 기록/제출을 맡는 주방에 가깝다.

단, 여기서 조심할 점이 있어. 렌더 스레드와 GPU는 같은 게 아니야. 렌더 스레드는 CPU 스레드고, GPU는 더 아래 하드웨어야. 렌더 스레드가 RHI 명령을 만들고 제출하면, RHI 스레드나 GPU 큐가 또 따로 움직일 수 있다. 그 다음 층은 rhi-overview에서 본다.

8. 이 챕터에서 딱 이것만

  • 게임 스레드는 렌더 일을 직접 끝내기보다 ENQUEUE_RENDER_COMMAND로 렌더 스레드에 주문서를 넘긴다.
  • 렌더 스레드는 RenderingThreadMain에서 태스크 그래프에 붙고, ProcessThreadUntilRequestReturn으로 자기 큐를 계속 처리한다.
  • FRenderCommandFence는 "여기까지 처리했는지" 확인하는 번호표다. 필요할 때만 게임 스레드가 기다린다.
  • r.OneFrameThreadLag와 FFrameEndSync::Sync는 게임 스레드가 렌더/RHI/GPU보다 너무 앞서가지 않게 간격을 조절한다.
  • 스레드를 나누는 이유는 병렬 처리량을 얻기 위해서고, 펜스가 필요한 이유는 그 병렬성이 무한히 벌어지면 안 되기 때문이다.

Q1. 게임 스레드랑 렌더 스레드를 왜 나눴나요?

답 보기
한 스레드가 입력 받고 → 로직 굴리고 → 그리고 → 화면에 띄우기를 한 줄로 다 하면, 60fps 기준 16.6ms 예산이 금방 터져. 게임 로직 8ms + 렌더 준비 7ms + GPU 제출 대기 4ms가 붙으면 벌써 19ms야. 게다가 그리는 일은 기다리는 시간이 많은데 그 동안 CPU가 놀고, 코어가 8개 16개여도 한 줄로 서면 한 코어만 일해. 그래서 게임 스레드는 "이번 프레임 그릴 일"을 명령으로 포장해 넘기고, 렌더 스레드가 자기 줄에서 처리하게 겹쳐 돌리려고 나눈 거야. 식당으로 치면 홀 직원(게임)과 주방(렌더)을 나눈 거지.

↳ 나눴으면 게임 스레드가 렌더 스레드한테 데이터를 그냥 같이 만지면 되지 않나요?

답 보기
그게 제일 위험한 거야. 두 스레드가 같은 UObject를 동시에 만지면 락이 필요하고, 락을 많이 걸면 프레임 시간이 흔들려. 그래서 직접 만지는 대신 "주문서"를 던져. 게임 스레드는 ENQUEUE_RENDER_COMMAND로 "나중에 렌더 스레드가 실행할 작은 함수(람다)"를 넘기고, 렌더 스레드는 그 포장된 작업만 받아. 우리 서버로 치면 IOCP 워커가 CSession을 직접 마음대로 바꾸는 게 아니라 액터 큐에 처리 요청을 넣는 느낌이야.

Q2. 렌더 명령을 큐에 넣는다는데, 큰 흐름에서 어떻게 도나요?

답 보기
게임 스레드가 ENQUEUE_RENDER_COMMAND로 람다를 만들어 던지면, 지금 렌더 스레드가 아니고 렌더 스레드에서 실행해야 하는 상황이면 큐에 올리고 게임 스레드는 자기 일을 이어가. 렌더 스레드는 메인 루프에서 자기 큐를 계속 꺼내 처리하고. 홀은 주문서를 레일에 올리고 바로 다음 손님을 받고, 주방은 자기 속도로 주문서를 꺼내 요리하는 그림이야. 이 분리 덕분에 게임 스레드가 렌더 일을 "함수 호출"로 그 자리에서 끝내지 않아도 돼.

↳ 그럼 이미 렌더 스레드 안에서 렌더 명령을 부르면요?

답 보기
그땐 큐에 넣을 이유가 없어서 바로 실행해. 이미 주방 안에 있는 사람이 주문서를 또 레일에 올려서 자기가 다시 꺼낼 필요가 없잖아. 그래서 코드가 "지금 렌더 스레드냐"를 먼저 묻는 거야 — 아니면 큐에, 맞으면 즉시 실행.

Q3. 펜스(fence)는 왜 필요하고, 큰 그림에서 뭘 하나요?

답 보기
겹쳐 돌리면 빨라지는데, 홀이 주방보다 너무 멀리 앞서가면 문제가 생겨. ① 주방이 아직 읽고 있는 재료(액터 데이터)를 홀이 덮어써서 화면이 깨지거나 크래시, ② 주문이 열 장씩 밀리면 마우스를 움직여도 화면은 열 프레임 뒤에 반응해서 조작이 굼떠져. 펜스는 "여기까지는 주방이 진짜 다 처리했다"를 확인하는 번호표야. 이름 그대로 울타리 — "여기 넘어오지 마"를 세워두는 거지. 락이라기보다 "특정 지점까지 왔는지 확인표"에 가까워.

↳ 그럼 매 프레임 모든 작업마다 펜스로 기다리나요?

답 보기
아니, 그러면 분업한 의미가 사라져 — 다시 한 줄 서기가 돼. 평소엔 주문서를 계속 넘기고, 리소스를 지우거나 종료하거나 프레임 간격을 맞출 때처럼 경계가 필요한 지점에서만 기다려. 우리 서버에서 세션 삭제 전에 IOCP 워커가 그 버퍼를 아직 만질 수 있으면 바로 free하면 터지니까 참조 카운트·완료 이벤트·큐 drain을 두잖아. 렌더 스레드 펜스도 딱 그 감각이야.

Q4. 그럼 렌더 스레드가 게임 스레드보다 뒤처지는 건 버그 아닌가요?

답 보기
버그가 아니라 설계일 수 있어. 게임 스레드가 N프레임 명령을 만들 때 렌더 스레드는 N-1프레임을 처리하고, GPU는 더 아래에서 N-2를 처리할 수 있어. 이게 파이프라이닝이야. r.OneFrameThreadLag가 그걸 조절하는 다이얼인데, 값이 0이면 홀이 매번 주방을 기다려(완전 동기), 아니면 펜스를 한 개 남겨서 한 프레임 정도만 겹치게 둬.

↳ 그럼 많이 겹칠수록 좋은 거 아닌가요? 왜 1프레임으로 제한해요?

답 보기
파이프라이닝은 공짜가 아니거든. 겹치면 처리량(throughput)은 좋아지지만 지연(latency)이 늘어. 너무 바짝 붙이면(0프레임) 서로 기다려서 분업이 무의미해지고, 너무 벌리면 조작이 굼떠져. 그래서 보통 1프레임을 허용해 — 성능과 반응성 사이의 타협점이야. 공짜 점심은 없어.

↳ 렌더 스레드랑 GPU는 같은 건가요?

답 보기
아니, 헷갈리기 쉬운 지점이야. 렌더 스레드는 CPU 스레드고, GPU는 더 아래 하드웨어야. 렌더 스레드가 RHI 명령을 만들고 제출하면, 그 아래에서 RHI 스레드나 GPU 큐가 또 따로 움직여. 그러니까 층이 홀(게임 스레드) → 주방(렌더 스레드) → 실제 화구(RHI/GPU)로 한 단계 더 있는 셈이야. 그 아래 층은 rhi-overview에서 봐.
