셰이더 순열 — 하나의 셰이더, 수천 가지 변형

언리얼 렌더링 · 27 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "하나의 셰이더가 여러 변형으로 컴파일되는 이유와, 언리얼이 그 폭발을 어디서 세고 거르는지"가 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX를 해봤으면 #define 하나로 HLSL 컴파일 결과가 달라진다는 건 알아. 서버로 치면 같은 CM_ATTACK이라도 시즌, 직업, 이벤트 플래그에 따라 처리 경로가 갈라지는 느낌이야.

문제는 셰이더 쪽 조합이 훨씬 빨리 터진다는 거야. bool 옵션 10개면 2^10 = 1024벌이고, 품질 4단계와 플랫폼 5개를 곱하면 2만 벌이 넘어간다.

이걸 다 구우면 에디터 아래에 "Compiling Shaders 12000"이 뜨고, 작은 옵션 변경 하나로 몇 분이 사라져.

언리얼도 같은 문제를 만났고, 답이 셰이더 순열(permutation) 이야. 차원을 선언하고, 차원 값을 PermutationId 하나로 접고, 필요 없는 조합은 ShouldCompilePermutation에서 잘라낸다.

왜 지금 보냐면 앞 장 pbr-brdf에서는 빛 수식 자체를 봤고, 뒤의 nanite-overview, lumen-overview에서도 FPermutationDomain이 계속 나오기 때문이야.

0. 비유부터 — 주문표 도장 찍는 분식집

이번 장은 분식집으로 보자. 메뉴는 김밥 하나인데 옵션 도장이 붙어.

  • 참치 넣을까?
  • 매운 소스 넣을까?
  • 치즈 넣을까?
  • 포장할까?

옵션 4개가 전부 참/거짓이면 벌써 16가지 김밥이야. 레시피 원본은 하나지만, 주방 입장에서는 도장 조합마다 다른 작업지시서가 된다.

셰이더도 똑같아. .usf 원본은 하나인데, C++ 주문표가 ALPHA, TONEMAP, ST2084 같은 도장을 찍고 HLSL 안의 #if ALPHA, #if TONEMAP을 켜고 끈다.

셰이더 원본 = 김밥 레시피.

순열 차원 = 옵션 도장.

PermutationId = 주문번호 한 줄.

컴파일 결과 = 실제로 말아둔 김밥 한 줄.

문제는 도장이 늘수록 주문번호가 곱셈으로 폭발한다는 점이고, 언리얼은 그걸 세고, 접고, 거르고, 도장 찍어서 주방에 넘긴다.

🌱 이 개념은 왜 생겼나 — 순열 차원
• 원래 구조: 셰이더 원본 하나에 #if를 몇 개 두고, 컴파일할 때 매크로를 손으로 켜고 끄면 될 것 같아. 분식집이면 주문표에 도장 하나씩 찍는 거야.
• 그런데 문제: ALPHA, TONEMAP, ST2084처럼 도장이 3개만 돼도 8장이고, 도장 이름을 손으로 맞추면 C++ 주문표와 .usf 레시피가 쉽게 엇갈려.
• 그래서 필요한 것: 각 도장을 C++에서 차원으로 선언해두는 틀이 필요해. SHADER_PERMUTATION_BOOL은 "이 도장은 켜짐/꺼짐 두 칸짜리야"라고 장부에 올리는 이름표야.

1. 실제 예시 — bool 3개면 8벌이다

작은 예시부터 보자. BinkShaders.h의 Bink 동영상 픽셀 셰이더는 ALPHA, TONEMAP, ST2084 세 도장을 선언한다.

각각 bool이니까 켜짐/꺼짐 두 가지이고, 조합은 2 × 2 × 2 = 8개야.

BinkShaders.h:92

struct FBinkDrawICtCpPS : FGlobalShader { DECLARE_EXPORTED_SHADER_TYPE(FBinkDrawICtCpPS, Global, RENDERCORE_API); SHADER_USE_PARAMETER_STRUCT(FBinkDrawICtCpPS, FGlobalShader); class FALPHA : SHADER_PERMUTATION_BOOL("ALPHA"); class FTONEMAP : SHADER_PERMUTATION_BOOL("TONEMAP"); class FST2084 : SHADER_PERMUTATION_BOOL("ST2084"); using FPermutationDomain = TShaderPermutationDomain<FALPHA, FTONEMAP, FST2084>; static bool ShouldCompilePermutation(const FGlobalShaderPermutationParameters& Parameters) { return true; } static void ModifyCompilationEnvironment(const FGlobalShaderPermutationParameters& Parameters, FShaderCompilerEnvironment& OutEnvironment) { }
🔤 기호 사전 — Bink 순열 선언
• struct FBinkDrawICtCpPS : FGlobalShader = 전역 픽셀 셰이더 주문표 하나야.
• SHADER_PERMUTATION_BOOL("ALPHA") = ALPHA라는 참/거짓 옵션 도장을 만든다.
• class FTONEMAP = 톤매핑을 켤지 말지 나타내는 차원 하나야.
• using FPermutationDomain = ... = 여러 도장을 한 주문표 묶음으로 합친다.
• TShaderPermutationDomain<FALPHA, FTONEMAP, FST2084> = 세 차원의 모든 조합을 다룬다는 뜻이야.
• ShouldCompilePermutation = 이 조합을 진짜 컴파일할지 묻는 문지기 함수야.
• return true = 여기서는 모든 조합을 허용한다는 뜻이야.

이제 같은 이름이 .usf에서 어떻게 쓰이는지 보자.

Bink.usf:92

#if TONEMAP // Simplified Reinhard p.xyz /= p.xyz+1; p.xyz *= hdr.z; #endif #if ST2084 // Convert into PQ space float3 Lm1 = pow(max(p.xyz*(1.0/125),0), 0.159301758125); float3 X = (0.8359375 + 18.8515625 * Lm1) / (1 + 18.6875 * Lm1); p.xyz = pow(X, 78.84375); #endif #if ALPHA p.w = tex3.Sample( samp3, UV.xy ).r; #endif
🔤 기호 사전 — HLSL #if 분기
• #if TONEMAP = 컴파일할 때 TONEMAP 도장이 켜져 있으면 아래 줄을 포함한다.
• #endif = 조건부 코드 구간이 여기서 끝난다는 표시야.
• p.xyz = 색의 RGB 세 성분만 가리킨다.
• p.w = 색의 알파 성분이야.
• pow(...) = 거듭제곱 함수야.
• tex3.Sample(...) = 네 번째 텍스처에서 값을 읽는다.
🔁 이제 다시 보자. C++의 class FTONEMAP : SHADER_PERMUTATION_BOOL("TONEMAP")가 도장을 만들고 → 컴파일 환경에 TONEMAP define이 들어가고 → .usf의 #if TONEMAP이 켜지거나 꺼진다. 도장 하나가 레시피 줄 하나를 살리거나 죽이는 거야.

분식집으로 말하면 FALPHA는 "알파 토핑", FTONEMAP은 "톤매핑 소스", FST2084는 "PQ 포장지" 도장이야.

세 도장을 찍는 모든 경우를 만들면 주문표는 8장이 된다.

렌더러 본체로 가면 차원이 훨씬 많아져서 이 숫자가 바로 컴파일 시간으로 돌아온다.

🌱 이 개념은 왜 생겼나 — PermutationId
• 원래 구조: 도장 조합을 매번 "알파 켜짐, 톤매핑 꺼짐, ST2084 켜짐"처럼 주문표 그대로 들고 다니면 돼.
• 그런데 문제: 컴파일 큐, 캐시, 로그가 수천 장을 돌면 긴 주문표를 계속 비교하고 저장해야 해. 주문이 16000장이면 이름표만 봐도 정신없어.
• 그래서 필요한 것: 도장 조합을 주문번호 하나로 접어두는 방식이 필요해. 그 번호가 PermutationId야. 숫자 하나면 큐에 넣고, 저장하고, 다시 펼치기 쉬워.

2. PermutationId — 여러 도장을 주문번호 하나로 접는다

옵션 세 개를 매번 구조체째로 들고 다니면 번거롭다.

언리얼은 순열 벡터를 정수 하나로 접는다.

분식집으로 치면 "알파=true, 톤매핑=false, ST2084=true"를 주문번호 5번으로 접어두는 거야.

핵심 구조는 TShaderPermutationDomain에 있다.

총 개수는 곱셈으로 계산되고, PermutationId는 %와 /로 다시 풀린다.

ShaderPermutation.h:378

/** Total number of permutation within the domain. */ static constexpr int32 PermutationCount = Super::PermutationCount * TDimension::PermutationCount; /** Constructors. */ TShaderPermutationDomain<TDimension, Ts...>() : DimensionValue(TDimension::FromDimensionValueId(0)) { } explicit TShaderPermutationDomain<TDimension, Ts...>(int32 PermutationId) : DimensionValue(TDimension::FromDimensionValueId(PermutationId % TDimension::PermutationCount)) , Tail(PermutationId / TDimension::PermutationCount) { checkf(PermutationId >= 0 && PermutationId < PermutationCount, TEXT("Invalid shader permutation id %i."), PermutationId); } /** Set dimension's value. */ template<class DimensionToSet> void Set(typename DimensionToSet::Type Value) { return TShaderPermutationDomainSpetialization<std::is_same_v<TDimension, DimensionToSet>>::template SetDimension<Type, DimensionToSet>(*this, Value); } /** Get dimension's value. */ template<class DimensionToGet> const typename DimensionToGet::Type& Get() const { return TShaderPermutationDomainSpetialization<std::is_same_v<TDimension, DimensionToGet>>::template GetDimension<Type, DimensionToGet>(*this); } /** Get the tail of the dimensions. */ inline const typename Super::Type& GetTail() const { return Tail; } /** Modify the shader's compilation environment. */ void ModifyCompilationEnvironment(FShaderCompilerEnvironment& OutEnvironment) const { TShaderPermutationDomainSpetialization<TDimension::IsMultiDimensional>::template ModifyCompilationEnvironment<Type, TDimension>(*this, OutEnvironment); } /** Converts domain permutation vector to domain's value id. */ static int32 ToDimensionValueId(const Type& PermutationVector) { return PermutationVector.ToDimensionValueId(); } int32 ToDimensionValueId() const { return TDimension::ToDimensionValueId(DimensionValue) + TDimension::PermutationCount * Tail.ToDimensionValueId(); }
🔤 기호 사전 — 순열 ID 접기와 풀기
• static constexpr int32 PermutationCount = 컴파일 시간에 정해지는 총 순열 개수야.
• Super::PermutationCount * TDimension::PermutationCount = 뒤쪽 차원 수와 이번 차원 수를 곱한다.
• explicit ... (int32 PermutationId) = 정수 주문번호 하나로 순열 벡터를 다시 만드는 생성자야.
• PermutationId % TDimension::PermutationCount = 이번 차원의 값 번호만 뽑는 나머지 계산이야.
• PermutationId / TDimension::PermutationCount = 남은 주문번호를 뒤쪽 차원에게 넘기는 나눗셈이야.
• Tail = 이번 차원 뒤에 남은 차원 묶음이야.
• Set<...> / Get<...> = 특정 도장 값을 바꾸거나 읽는 함수야.
• ModifyCompilationEnvironment = 이 순열 값을 컴파일 환경 define으로 내려보내는 함수야.
🔁 이제 다시 보자. PermutationCount는 차원 개수를 계속 곱해서 총 주문표 수를 만들고, 생성자는 PermutationId % Count로 이번 도장을 풀고, PermutationId / Count로 남은 도장을 Tail에게 넘긴다. 반대로 ToDimensionValueId()는 도장 묶음을 정수 주문번호 하나로 다시 접는다.

컴파일 작업 큐는 결국 0, 1, 2 같은 정수 범위를 돈다.

각 번호를 다시 벡터로 풀면 옵션 조합이 된다.

서버에서 SP_* 번호 하나로 실제 프로시저와 파라미터 모양을 찾아가는 것과 비슷해.

정수 하나로 접으면 저장, 캐시, 로그가 쉬워진다.

대신 숫자를 도장 조합으로 푸는 규칙은 반드시 정확해야 한다.

🌱 이 개념은 왜 생겼나 — 컴파일 환경 define
• 원래 구조: C++이 주문번호만 주면 HLSL도 알아서 5번 주문이 뭔지 알 것 같아.
• 그런데 문제: .usf 레시피는 PermutationId 숫자를 몰라. #if TONEMAP처럼 도장 이름만 보니까, 번호 5번만 던지면 어느 줄을 켤지 못 정해.
• 그래서 필요한 것: 주문번호를 다시 도장으로 펼쳐서 TONEMAP=0/1 같은 define 메모로 붙여줘야 해. 그 메모판이 FShaderCompilerEnvironment 쪽 컴파일 환경이야.

3. 주문번호가 define으로 내려간다

PermutationId는 정수 하나일 뿐이야.

그런데 HLSL의 #if TONEMAP은 정수를 직접 모른다.

중간에서 누가 TONEMAP=0 또는 TONEMAP=1 define을 박아줘야 해.

그 연결부가 셰이더 선언 매크로 안에 있다.

Parameters.PermutationId로 FPermutationDomain을 만들고, 그 벡터가 환경을 수정한다.

분식집으로 치면 주문번호 5번을 보고 주문표를 다시 펼친다.

그 다음 주방 벽에 "ALPHA 켜짐, TONEMAP 꺼짐, ST2084 켜짐"이라고 붙인다.

요리사는 그 메모를 보고 레시피의 어느 줄을 읽을지 결정한다.

HLSL 전처리기가 하는 일이 딱 그거야.

🌱 이 개념은 왜 생겼나 — ShouldCompilePermutation
• 원래 구조: 만들 수 있는 김밥 주문표는 전부 굽자. bool 3개면 8장이라 아직 참을 만해.
• 그런데 문제: bool 10개면 1024장이고, 품질 4단계와 플랫폼 5개가 붙으면 2만 장이 넘어가. 필요 없는 조합까지 구우면 에디터가 몇 분씩 멈춰.
• 그래서 필요한 것: 주방 입구에서 "이 주문 진짜 만들까?"를 자르는 문지기가 필요해. 그게 ShouldCompilePermutation이야. 너무 넓으면 낭비고, 너무 좁으면 필요한 김밥이 없어져.

4. Shader.cpp의 문지기 — 컴파일할 조합만 통과

이제 주요 소스인 Shader.cpp로 내려가자.

순열 폭발을 줄이는 첫 안전장치는 문지기 함수다.

모든 순열 번호가 실제로 컴파일되는 건 아니야.

플랫폼이 그 셰이더 스테이지를 지원하지 않을 수 있고, 셰이더 타입 자체가 "이 조합은 필요 없다"고 말할 수도 있다.

그 판단이 FShaderType::ShouldCompilePermutation으로 모인다.

• Parameters.Platform = 지금 목표 플랫폼이야.
• && = 앞 검사도 통과하고 뒤 검사도 통과해야 한다는 뜻이야.
• (*ShouldCompilePermutationRef)(Parameters) = 셰이더 클래스가 넘겨준 판단 함수를 호출한다.
• (*ModifyCompilationEnvironmentRef) = 타입별 컴파일 환경 수정 함수를 호출하는 함수 포인터야.
🔁 이제 다시 보자. ShouldCompileShaderFrequency가 플랫폼/스테이지 기본 문지기고, ShouldCompilePermutationRef가 셰이더 클래스별 문지기야. 둘 다 통과해야 컴파일된다. 아래 ModifyCompilationEnvironmentRef는 통과한 주문표에 실제 도장 define과 추가 환경을 붙이는 단계로 이어진다.

여기서 컴파일 시간과의 싸움이 시작돼.

ShouldCompilePermutation이 느슨하면 너무 많이 굽는다.

반대로 너무 세게 막으면 필요한 플랫폼에서 셰이더가 없어서 렌더링이 깨진다.

서버로 치면 모든 CM_*를 모든 월드, 모든 이벤트에 다 등록하면 낭비고, 필요한 핸들러를 빼먹으면 런타임에서 "처리 불가 패킷"이 나는 것과 같아.

순열 문지기는 성능 최적화이면서 정확성 계약이다.

5. 조합 폭발을 숫자로 느껴보자

Bink 예시는 bool 3개라 8개였어.

FALPHA = 2 FTONEMAP = 2 FST2084 = 2 총 순열 = 2 * 2 * 2 = 8 PermutationId 범위 = 0..7

품질 4단계가 붙으면 바로 32개가 된다.

FQUALITY = 4 총 순열 = 2 * 2 * 2 * 4 = 32

플랫폼 5개면 160개고, 이런 셰이더 타입이 100개면 16000개야.

그래서 순열은 그냥 "깔끔한 코드 구조" 문제가 아니다.

에디터 대기 시간, 빌드팜 시간, DDC 크기, 패치 용량까지 건드린다.

옵션 도장 하나는 코드 한 줄처럼 보이지만, 실제로는 컴파일해야 할 주문표를 두 배로 늘릴 수 있다.

콜/데이터 흐름 한눈에

BinkShaders.h:97 class FALPHA / FTONEMAP / FST2084 | v BinkShaders.h:101 using FPermutationDomain = TShaderPermutationDomain<...> | v ShaderPermutation.h:379 PermutationCount = Super::PermutationCount * TDimension::PermutationCount | v ShaderPermutation.h:388 FPermutationDomain(PermutationId) -> % 와 / 로 각 차원 값 복원 | v Shader.h:1641 PermutationVector(Parameters.PermutationId) | v Shader.h:1642 PermutationVector.ModifyCompilationEnvironment(OutEnvironment) | v Shader.cpp:462 ShouldCompilePermutation(...) 문지기 | v Bink.usf:92 #if TONEMAP / #if ST2084 / #if ALPHA | v 컴파일 결과 한 벌

흐름을 말로 읽으면, 셰이더 클래스가 도장 차원을 선언하고 그 차원들이 총 주문표 수를 만든다.

컴파일 작업은 PermutationId 하나를 들고 오고, 그 숫자가 FPermutationDomain으로 풀려 define이 되며, 문지기를 통과한 조합만 최종 결과가 된다.

우리 서버·DirectX 랑 비교

DirectX만 놓고 보면 순열은 "다른 매크로 값으로 HLSL을 여러 번 컴파일한다"야.

언리얼은 그걸 엔진 규모로 관리해야 하니까 장부가 붙는다.

DirectX 감각언리얼 이름
D3DCompile에 넘기는 매크로 배열FShaderCompilerEnvironment
#if USE_FOO.usf의 #if ALPHA, #if TONEMAP
매크로 조합 하나PermutationId 하나
조합을 손으로 관리TShaderPermutationDomain
필요 없는 조합 스킵ShouldCompilePermutation

서버랑도 비슷하다.

우리 서버에서 CM_* 핸들러를 모든 상황에 다 열어두면 관리가 힘들어.

월드, 이벤트, 직업, 레벨 제한에 따라 어떤 핸들러는 아예 등록하지 않거나 입구에서 잘라야 한다.

셰이더도 모든 플랫폼, 모든 품질, 모든 머티리얼 옵션을 다 굽는 건 비싸다.

그래서 ShouldCompilePermutation은 서버의 "패킷 라우팅 허용표" 같은 역할을 한다.

허용표가 너무 넓으면 컴파일 시간이 터지고, 너무 좁으면 런타임에 필요한 셰이더가 없다.

이 챕터에서 딱 이것만

  • 순열은 하나의 셰이더 원본에 붙는 컴파일 타임 옵션 조합이다.
  • SHADER_PERMUTATION_BOOL 같은 작은 class 하나가 HLSL #if define 하나로 내려간다.
  • TShaderPermutationDomain은 여러 차원을 곱해서 PermutationCount를 만들고, PermutationId 하나로 접고 푼다.
  • Shader.cpp의 ShouldCompilePermutation은 플랫폼/셰이더별 문지기로 불필요한 조합을 줄인다.
  • 순열 차원 하나는 코드 한 줄처럼 보여도 컴파일 결과 수를 곱셈으로 늘릴 수 있다.

🎯 원리 한 줄 요약

셰이더 순열은 "옵션 도장을 찍은 셰이더 주문표"다 — 언리얼은 여러 도장을 PermutationId 하나로 접고, 필요한 조합만 컴파일해 HLSL #if를 켜고 끈다.
