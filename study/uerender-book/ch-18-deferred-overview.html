DeferredShadingRenderer — 한 프레임 한 바퀴

언리얼 렌더링 · 18 / 42

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "FDeferredShadingSceneRenderer::Render() 안에서 한 프레임이 어떤 순서로 지나가는가"의 큰 지도가 잡힌다.

왜 이걸 배워? — 문제의식부터

잠깐. 우리는 앞에서 프러스텀 컬링, 오클루전 컬링, MeshDrawCommand까지 봤어. 그러면 이제 이런 질문이 남아. 그래서 그 재료들이 한 프레임 안에서 대체 어떤 순서로 쓰이는데? 게임 서버로 치면 SP_* 핸들러 하나하나는 봤는데, 메인 루프가 언제 recv를 털고, 언제 DB 결과를 반영하고, 언제 월드 tick을 돌리고, 언제 send queue를 flush하는지 모르는 상태랑 같아. 조각 함수만 알면 디버깅할 때 바로 막혀. 예를 들어 화면에 그림자는 있는데 물체가 안 보인다? BasePass 문제인지, PrePass에서 깊이가 잘못 깔린 건지, 후처리에서 날아간 건지 모르면 RenderDoc을 열어도 그냥 검은 상자야. 패스가 20개 넘게 보이는데 순서 감각이 없으면 "어디서부터 봐야 하는지"가 안 잡히거든. 언리얼도 같은 문제를 만났고, 답이 FDeferredShadingSceneRenderer::Render()라는 한 바퀴짜리 진행표야. 이 함수는 모든 세부 구현을 다 품은 작은 함수가 아니야. 오히려 반대야. RenderPrePass, RenderBasePass, RenderLights, RenderTranslucency, AddPostProcessingPasses 같은 큰 패스들을 정해진 순서로 호출하는 지휘자에 가까워. 그래서 지금 이 챕터가 필요해. 앞 챕터 mesh-draw-command까지는 "무엇을 그릴지 준비하는 법"을 봤고, 다음 챕터 prepass-depth부터는 각 패스를 하나씩 파고들 거야. 그 사이에 이 장이 없으면, 다음 장들이 전부 흩어진 골목처럼 보여. 이번 장은 골목 이름을 외우는 게 아니라 동네 지도를 그리는 장이야.

0. 비유부터 — 코스 요리 주방의 총괄 셰프

식당 주방을 떠올려봐. 손님이 코스 요리를 주문했어. 주방장은 직접 양파도 썰고 스테이크도 굽고 디저트도 꾸미는 사람이 아니야. 대신 순서를 지휘하지.

  1. 접시를 먼저 데운다.
  2. 전채 준비를 끝낸다.
  3. 메인 재료를 팬에 올린다.
  4. 소스를 얹는다.
  5. 투명한 장식과 가니시를 올린다.
  6. 마지막으로 플레이팅하고 손님 테이블에 보낸다.

FDeferredShadingSceneRenderer::Render()가 이 주방장이야. 여기서 접시 데우기는 PrePass, 메인 재료는 BasePass, 소스는 Lighting, 투명한 장식은 Translucency, 마지막 플레이팅은 PostProcessing이야. 각 요리사는 다음 챕터들이 따로 파고든다. 이번 장은 주방장이 어떤 순서로 벨을 치는지만 본다.

소스 위치 (이 클론에 실제로 있음. 아래 코드는 전부 여기서 그대로 뽑음)
• 구현: _study/UE_Graphics/Engine/Source/Runtime/Renderer/Private/DeferredShadingRenderer.cpp

1. Render()는 한 프레임 주문표의 시작점이야

먼저 함수 입구부터 보자. 이름이 길지만 겁먹지 마. FDeferredShadingSceneRenderer라는 렌더러 객체가 있고, 그 객체의 Render 함수가 FRDGBuilder를 들고 한 프레임 패스들을 쌓는 장면이야. DeferredShadingRenderer.cpp:1736

void FDeferredShadingSceneRenderer::Render(FRDGBuilder& GraphBuilder, const FSceneRenderUpdateInputs* SceneUpdateInputs) { { FRayTracingVisualizationData& RayTracingVisualizationData = GetRayTracingVisualizationData(); if (RayTracingVisualizationData.HasOverrides()) { // When activating the view modes from the command line, automatically enable the RayTracingDebug show flag for convenience. ViewFamily.EngineShowFlags.SetRayTracingDebug(true); } } // If this is scene capture rendering depth pre-pass, we'll take the shortcut function RenderSceneCaptureDepth if optimization switch is on. const ERendererOutput RendererOutput = GetRendererOutput(); const bool bNaniteEnabled = ShouldRenderNanite(); const bool bHasRayTracedOverlay = HasRayTracedOverlay(ViewFamily);
🔤 기호 사전 — Render() 입구
• void = 이 함수가 값을 돌려주지 않는다는 뜻이야. 그냥 일을 하고 끝난다.
• FDeferredShadingSceneRenderer::Render = FDeferredShadingSceneRenderer라는 집 안에 있는 Render 함수라는 뜻. ::는 소속 표시야.
• FRDGBuilder& GraphBuilder = 이번 프레임의 렌더 패스들을 적어 넣는 장부야. &는 복사본 말고 원본을 같이 쓴다는 뜻으로 보면 돼.
• const FSceneRenderUpdateInputs* = 바꾸지 않을 입력 손잡이야. const는 "건드리지 마", *는 포인터 손잡이.
• if (...) = 조건이 맞으면 안쪽을 실행한다.
• RendererOutput = 이번 렌더가 최종 화면인지, depth prepass 전용인지 같은 출력 모드야.
• bNaniteEnabled = Nanite를 쓸지 말지 보는 참/거짓 값. b로 시작하면 보통 bool이야.
• bHasRayTracedOverlay = 레이트레이싱 오버레이가 켜져서 일반 패스를 건너뛸 상황인지 보는 깃발이야.

입구에서 벌써 중요한 게 보여. 주방장이 바로 "고기 굽자" 하지 않아. 먼저 이번 주문이 어떤 종류인지 본다. 최종 장면을 뽑는 주문인지, depth만 뽑는 특수 주문인지, Nanite를 쓸지, 레이트레이싱 오버레이 때문에 평소 동선을 건너뛸지 확인해. 서버로 치면 tick 시작하자마자 is_shutdown, maintenance_mode, channel_ready 같은 전역 상태를 먼저 보는 것과 같아. 이 상태 깃발이 뒤에서 계속 분기 기준이 된다.

🌱 이 개념은 왜 생겼나 — 디퍼드 렌더링
• 원래 구조: 물체를 하나 그릴 때마다 그 자리에서 재질 보고, 빛 계산하고, 최종 색까지 바로 접시에 올렸어.
• 그런데 문제: 라이트가 10개, 100개로 늘면 같은 재료를 보면서 빛 계산을 계속 반복해. 주방에서 소스가 바뀔 때마다 재료 손질부터 다시 하는 꼴이야.
• 그래서 필요한 것: 재료 정보는 먼저 GBuffer 접시에 눕혀두고, 빛은 뒤에서 한꺼번에 붓자. 계산을 뒤로 미룬다고 해서 Deferred야.

2. 큰 지도 먼저 — 한 프레임의 코스 순서

이 장 전체를 한 장으로 줄이면 이렇게야.

Render -> 상태 깃발 확인 -> visibility / scene uniform / task 준비 -> PrePass -> BasePass -> AfterBasePass 작업 -> DeferredLighting -> Translucency -> PostProcessing -> RenderFinish

이건 너무 단순화한 지도야. 실제 함수 안에는 Nanite, Lumen, Virtual Shadow Map, Hair, Water, Cloud, Path Tracing 같은 갈림길이 엄청 많아. 하지만 초보가 처음 잡아야 할 뼈대는 저 순서야. 깊이를 먼저 깔고, 재질 정보를 깔고, 빛을 얹고, 반투명을 따로 얹고, 후처리로 마감한다. 디퍼드 렌더링이라는 이름도 여기서 나온다. BasePass 때 바로 최종 색을 끝내지 않고, GBuffer에 재질 재료를 먼저 적어둔 다음, 나중에 Lighting 단계에서 빛을 계산해. 요리로 치면 접시에 재료를 먼저 깔아두고, 소스는 뒤에 한꺼번에 붓는 방식이야.

🌱 이 개념은 왜 생겼나 — PrePass
• 원래 구조: 그냥 BasePass에서 색도 칠하고 깊이도 쓰면 돼. 한 번에 요리하면 제일 단순해 보여.
• 그런데 문제: 앞 건물에 가려질 픽셀도 비싼 머티리얼 셰이더를 돌린 뒤 버리면 헛일이 커져. 접시 뒤에 숨을 재료까지 정성껏 굽는 셈이야.
• 그래서 필요한 것: 먼저 깊이만 싸게 깔아서 "뒤에 숨은 애는 패스"라고 빨리 판정하자. 먼저 도는 패스라서 PrePass, GPU 쪽 말로는 Early Z 감각이야.
🧱 먼저 알아야 할 것 — 앞뒤(깊이)를 숫자로 적어둔다
• 깊이 = 얼마나 앞이냐: 화면의 한 점을 보면 벽도 있고 그 앞에 사람도 있어. "카메라에서 얼마나 가까운가"를 점마다 숫자로 적어둔 게 깊이야.
• 가까운 게 먼 걸 가린다: 같은 자리에 두 물체가 겹치면, 더 가까운 쪽만 눈에 보이고 뒤엣것은 안 보여.
이게 잡히면 아래 PrePass 설명이 얹힌다.

3. PrePass — 접시 바닥부터 깐다

첫 번째 큰 관문은 PrePass야. 아직 색을 칠하지 않는다. 깊이 버퍼를 먼저 정리하고, 필요하면 Early Z를 채운다. 이걸 해두면 뒤에서 픽셀 셰이더가 헛일을 덜 해. 앞에 가려진 픽셀은 "이미 더 가까운 물체가 있어" 하고 빨리 버릴 수 있거든. DeferredShadingRenderer.cpp:2369

auto RenderPrepassAndVelocity = [&](auto& InViews, auto& InNaniteBasePassVisibility, auto& NaniteRasterResults, auto& PrimaryNaniteViews, FSceneTextures& LocalSceneTextures) { FRDGTextureRef FirstStageDepthBuffer = nullptr; { // Both compute approaches run earlier, so skip clearing stencil here, just load existing. const ERenderTargetLoadAction StencilLoadAction = DepthPass.IsComputeStencilDitherEnabled() ? ERenderTargetLoadAction::ELoad : ERenderTargetLoadAction::EClear; const ERenderTargetLoadAction DepthLoadAction = ERenderTargetLoadAction::EClear; AddClearDepthStencilPass(GraphBuilder, LocalSceneTextures.Depth.Target, DepthLoadAction, StencilLoadAction); // Draw the scene pre-pass / early z pass, populating the scene depth buffer and HiZ if (bNeedsPrePass) { RenderPrePass(GraphBuilder, InViews, LocalSceneTextures.Depth.Target, InstanceCullingManager, &FirstStageDepthBuffer); } else { // We didn't do the prepass, but we still want the HMD mask if there is one RenderPrePassHMD(GraphBuilder, InViews, LocalSceneTextures.Depth.Target); } // special pass for DDM_AllOpaqueNoVelocity, which uses the velocity pass to finish the early depth pass write if (bShouldRenderVelocities && Scene->EarlyZPassMode == DDM_AllOpaqueNoVelocity && RendererOutput == ERendererOutput::FinalSceneColor) { // Render the velocities of movable objects. Don't bind the velocity render target for custom render passes (it's not used downstream), to avoid needing to clear it again. RenderVelocities(GraphBuilder, InViews, LocalSceneTextures, EVelocityPass::Opaque, bForceVelocityOutput, /*bBindRenderTarget=*/ InViews[0].CustomRenderPass == nullptr); }
🔤 기호 사전 — PrePass 토막
• auto RenderPrepassAndVelocity = [&] = 이름 없는 작은 함수를 변수에 담는 람다야. [&]는 주변 변수를 원본으로 붙잡아 쓴다는 뜻이야.
• FRDGTextureRef = RDG 안에서 쓰는 텍스처 손잡이야. 실제 GPU 리소스를 직접 들고 있는 게 아니라 그래프용 이름표에 가까워.
• nullptr = 아직 가리키는 게 없다는 뜻.
• ERenderTargetLoadAction::EClear = 렌더 타깃을 시작할 때 깨끗이 지우겠다는 선택지야.
• AddClearDepthStencilPass = depth/stencil 접시를 먼저 비우는 패스를 그래프에 추가한다.
• bNeedsPrePass = 진짜 PrePass를 해야 하는지 보는 깃발이야.
• RenderPrePass(...) = 깊이만 먼저 그리는 본 패스야.
• RenderPrePassHMD(...) = PrePass는 안 해도 VR HMD 마스크 같은 최소 처리는 하겠다는 갈림길이야.
• RenderVelocities(...) = 움직임 벡터를 따로 기록하는 패스야. TAA나 모션블러에서 필요해.
🔁 이제 다시 보자. 이 토막은 AddClearDepthStencilPass로 접시 바닥을 비우고 → bNeedsPrePass면 RenderPrePass로 깊이를 깔고 → 아니면 RenderPrePassHMD로 필요한 마스크만 처리하고 → 특수 EarlyZ 모드면 RenderVelocities까지 이어 붙여. 색칠 전에 바닥 공사를 끝내는 장면이야.

여기서 중요한 건 PrePass가 "그림을 예쁘게 만드는 패스"가 아니라는 점이야. PrePass는 뒤 패스가 덜 고생하게 만드는 교통정리 패스야. DirectX로 직접 엔진을 짜봤으면 depth-only pass를 먼저 돌리는 최적화를 떠올리면 돼. 서버로 치면 게임 로직 tick 전에 접속 끊긴 세션, 죽은 액터, 유효하지 않은 작업을 먼저 걷어내는 단계와 비슷해. 나중에 무거운 로직을 덜 돌리려고 앞에서 싼 검사를 하는 거지. PrePass의 세부 구현은 다음 장 prepass-depth에서 따로 내려간다.

🌱 이 개념은 왜 생겼나 — GBuffer
• 원래 구조: 픽셀에 최종 색만 써두면 화면은 일단 나와. 접시에 완성 요리만 올리는 방식이야.
• 그런데 문제: 나중에 빛을 다시 계산하려면 그 픽셀의 노멀, roughness, metallic 같은 재료표가 필요해. 최종 색만 있으면 "이게 무슨 재료였지?"가 돼.
• 그래서 필요한 것: 화면 픽셀마다 재료 정보를 여러 접시에 나눠 저장하자. Geometry 정보를 담는 버퍼라서 GBuffer라고 부르는 거야.

4. BasePass — GBuffer 접시에 재료를 눕힌다

PrePass가 깊이 바닥이라면, BasePass는 진짜 재료를 접시에 올리는 단계야. 하지만 디퍼드에서는 여기서 최종 조명을 끝내지 않아. 대신 GBuffer라는 여러 장의 렌더 타깃에 색, 노멀, roughness, metallic 같은 재질 정보를 기록해. 이게 디퍼드의 핵심이야. 빛은 나중에 GBuffer를 읽어서 계산한다. DeferredShadingRenderer.cpp:2902

{ if (!bHasRayTracedOverlay) { RenderBasePass(*this, GraphBuilder, Views, SceneTextures, DBufferTextures, BasePassDepthStencilAccess, ForwardScreenSpaceShadowMaskTexture, InstanceCullingManager, bNaniteEnabled, Scene->NaniteShadingCommands[ENaniteMeshPass::BasePass], NaniteRasterResults); } if (!bAllowReadOnlyDepthBasePass) { AddResolveSceneDepthPass(GraphBuilder, Views, SceneTextures.Depth); }
🔤 기호 사전 — BasePass 토막
• if (!bHasRayTracedOverlay) = 레이트레이싱 오버레이가 없을 때만 일반 BasePass를 실행한다. !는 참/거짓을 뒤집는 표시야.
• RenderBasePass(*this, ...) = 지금 렌더러 자신을 넘겨 BasePass를 실행한다. 여기서 *this는 "내 실물"을 넘긴다는 뜻이야.
• Views = 카메라별 뷰 목록이야. 분할 화면이나 VR이면 여러 개일 수 있어.
• SceneTextures = 이번 프레임에서 쓰는 장면 텍스처 묶음이야. depth, color, GBuffer 같은 접시 묶음으로 보면 돼.
• DBufferTextures = deferred decal 쪽에서 쓰는 별도 버퍼 묶음이야.
• Scene->NaniteShadingCommands[...] = Nanite BasePass용으로 준비된 그리기 명령 묶음이야.
• AddResolveSceneDepthPass = depth를 뒤에서 읽기 좋은 상태로 정리하는 패스야.
🔁 이제 다시 보자. !bHasRayTracedOverlay면 일반 렌더 길로 가서 RenderBasePass가 GBuffer 재료를 깔고 → depth를 읽기 전용으로 못 쓰는 상황이면 AddResolveSceneDepthPass로 깊이 접시를 정리해. PrePass가 바닥, BasePass가 재료, resolve가 접시 정리야.

여기서 RenderBasePass 호출 하나 안에 엄청 많은 일이 숨어 있어. MeshDrawCommand가 실제 draw로 내려가고, 머티리얼 셰이더가 돌고, GBuffer에 값이 기록돼. 하지만 이번 장에서는 BasePass가 Lighting보다 먼저 온다는 것만 박아두면 돼. 이 순서가 디퍼드 렌더링을 디퍼드답게 만든다. BasePass 세부는 basepass-gbuffer와 basepass-shader에서 다시 볼 거야.

5. Lighting — 재료 위에 빛 소스를 붓는다

BasePass가 끝나면 접시 위에는 "빛 없는 재료 정보"가 누워 있어. 이제 조명 차례야. 여기서 디퍼드 렌더러는 정렬된 라이트 목록을 가져와서 RenderLights를 돌리고, 투명 조명 볼륨과 Lumen 간접광, 반사/스카이라이트까지 이어 붙인다. DeferredShadingRenderer.cpp:3310

GatherTranslucencyVolumeMarkedVoxels(GraphBuilder); const FSortedLightSetSceneInfo& SortedLightSet = *GatherAndSortLightsTask.GetResult(); RenderLights(GraphBuilder, SceneTextures, LightingChannelsTexture, SortedLightSet); if (MegaLightsContext.IsValid()) { RenderMegaLights( GraphBuilder, MegaLightsContext, SceneTextures, NaniteShadingMask, LightingChannelsTexture); } RenderTranslucencyLightingVolume(GraphBuilder, TranslucencyLightingVolumeTextures, SortedLightSet); // Do DiffuseIndirectComposite after Lights so that async Lumen work can overlap RenderDiffuseIndirectAndAmbientOcclusion( GraphBuilder, SceneTextures, LumenFrameTemporaries, LightingChannelsTexture, /* bCompositeRegularLumenOnly = */ true, /* bIsVisualizePass = */ false, AsyncLumenIndirectLightingOutputs); // Render diffuse sky lighting and reflections that only operate on opaque pixels RenderDeferredReflectionsAndSkyLighting(GraphBuilder, SceneTextures, LumenFrameTemporaries, DynamicBentNormalAOTextures);
🔤 기호 사전 — Lighting 토막
• GatherAndSortLightsTask.GetResult() = 미리 돌려둔 라이트 정렬 작업의 결과를 가져온다.
• FSortedLightSetSceneInfo& = 정렬된 라이트 묶음을 원본 참조로 받는다는 뜻이야.
• RenderLights(...) = GBuffer를 읽고 장면 색에 직접광을 얹는 큰 패스야.
• MegaLightsContext.IsValid() = MegaLights 쪽 자료가 쓸 수 있는 상태인지 확인한다.
• RenderTranslucencyLightingVolume(...) = 반투명 물체가 나중에 참고할 조명 볼륨을 준비한다.
• RenderDiffuseIndirectAndAmbientOcclusion(...) = 간접광과 AO를 합성한다.
• /* ... */ = 인자 설명 주석이야. 실행되는 값은 바로 뒤의 true, false야.
• RenderDeferredReflectionsAndSkyLighting(...) = 불투명 픽셀에 반사와 하늘빛을 더한다.
🔁 이제 다시 보자. SortedLightSet을 가져오고 → RenderLights로 직접광 소스를 붓고 → RenderTranslucencyLightingVolume로 투명용 조명 재료를 따로 준비하고 → RenderDiffuseIndirectAndAmbientOcclusion과 RenderDeferredReflectionsAndSkyLighting으로 간접광, AO, 반사, 하늘빛을 얹어. BasePass가 재료라면 이 블록은 소스와 향을 붓는 구간이야.

이 코드에서 RenderLights 하나만 보지 마. 그 주변 순서가 더 중요해. 투명 물체는 GBuffer에 완전히 들어가지 못하니까 투명용 조명 볼륨을 따로 준비한다. Lumen은 async로 돌 수 있어서 주석처럼 overlap을 고려한다. 반사와 스카이라이트는 "opaque pixels"라고 주석에 박혀 있어. 즉 불투명 세계를 먼저 완성하고, 반투명은 뒤에서 따로 얹는 구조야. 조명 세부는 deferred-lighting, Lumen은 lumen-overview로 이어진다.

🌱 이 개념은 왜 생겼나 — Translucency
• 원래 구조: 모든 물체를 GBuffer에 넣고 Lighting에서 한 번에 빛을 붓자. 접시 하나에 재료를 쭉 깔면 편해 보여.
• 그런데 문제: 유리, 물, 연기는 뒤가 비쳐서 "가장 앞 픽셀 하나"만 저장하면 부족해. 어떤 순서로 섞느냐에 따라 색이 달라져.
• 그래서 필요한 것: 불투명 접시는 먼저 끝내고, 투명 장식은 깊이와 순서를 보며 따로 올리자. 그래서 Translucency는 별도 코스로 빠지는 거야.

6. Translucency — 투명 장식은 따로 올린다

반투명은 디퍼드 렌더러에서 늘 골치 아픈 손님이야. 왜냐하면 GBuffer에는 "한 픽셀에 제일 앞 물체 하나"의 정보만 안정적으로 넣기 쉽거든. 유리창, 물, 연기처럼 뒤가 비쳐야 하는 물체는 순서와 blending이 중요해. 그래서 불투명 조명까지 끝낸 뒤 별도 패스로 온다. DeferredShadingRenderer.cpp:3608

7. PostProcessing — 마지막 플레이팅과 사진 보정

이제 장면은 거의 완성됐어. 하지만 아직 화면에 바로 내보낼 상태는 아니야. HDR 색을 LDR로 바꾸고, 노출을 맞추고, TAA, bloom, tone mapping, debug view 같은 후처리 체인을 타야 해. 코드에서는 AddPostProcessingPasses가 그 큰 입구야. DeferredShadingRenderer.cpp:3943

AddPostProcessingPasses( GraphBuilder, View, ViewIndex, GetSceneUniforms(), ViewPipelineState.DiffuseIndirectMethod, ViewPipelineState.ReflectionsMethod, PostProcessingInputs, NaniteResults, InstanceCullingManager, &VirtualShadowMapArray, LumenFrameTemporaries, SceneWithoutWaterTextures, TSRFlickeringInput, InstancedEditorDepthTexture);
🔤 기호 사전 — PostProcessing 토막
• AddPostProcessingPasses = 후처리 패스들을 RDG에 줄줄이 추가하는 큰 함수야.
• View, ViewIndex = 지금 처리 중인 카메라와 그 번호야.
• GetSceneUniforms() = 여러 셰이더가 공통으로 읽을 장면 상수 묶음을 가져온다.
• ViewPipelineState.DiffuseIndirectMethod = 이 뷰가 어떤 간접광 방식을 쓰는지 알려주는 값이야.
• PostProcessingInputs = 후처리에 필요한 장면 색, depth, custom depth, 노출 같은 입력 묶음이야.
• NaniteResults = Nanite 시각화나 후처리에 참고할 수 있는 결과 손잡이야.
• &VirtualShadowMapArray = VSM 배열 원본의 주소를 넘긴다. &는 주소를 꺼내는 표시이기도 해.
• TSRFlickeringInput = TSR 깜빡임 분석/완화 쪽 입력 텍스처야.
🔁 이제 다시 보자. AddPostProcessingPasses는 GraphBuilder 장부에 후처리 코스를 추가하고 → 현재 View와 파이프라인 상태를 보고 → PostProcessingInputs에 담긴 장면 텍스처들을 재료로 써서 → 최종 화면에 가까운 결과로 다듬는다. 주방 비유로는 접시가 나가기 전 조명 아래에서 마지막 플레이팅을 하는 장면이야.

PostProcess는 "예쁜 효과"만이 아니야. 현대 렌더러에서는 최종 가독성을 만드는 필수 단계야. 노출, tone mapping, TAA, upscaling이 여기로 들어오니까, 실제 플레이어가 보는 화면 품질은 여기서 크게 갈린다. 세부 체인은 postprocess-chain에서 따로 보자.

9. 우리 서버·DirectX 랑 비교

우리 서버 메인 루프랑 놓고 보면 감이 더 빨라.

서버 루프 감각렌더러 감각
세션/월드 상태 확인RendererOutput, bNaniteEnabled, bHasRayTracedOverlay 확인
죽은 세션, 무효 작업 먼저 걷기PrePass로 depth를 먼저 깔아 낭비 줄이기
패킷 핸들러가 월드 상태를 갱신BasePass가 GBuffer에 재질 상태 기록
월드 tick 뒤 이벤트/효과 계산Lighting이 GBuffer 위에 빛 계산
특수 패킷이나 보조 큐 처리Translucency, Hair, Water 같은 별도 패스
send queue flushPostProcess 뒤 최종 화면으로 마감

DirectX 경험으로 보면 더 직접적이야. PrePass는 depth-only draw. BasePass는 MRT에 GBuffer를 쓰는 draw. Lighting은 GBuffer SRV를 읽고 scene color RTV에 더하는 pass. Translucency는 depth를 참고하며 alpha blending하는 별도 draw. PostProcess는 scene color를 입력 텍스처로 읽어서 다음 render target으로 넘기는 screen pass 체인. FDeferredShadingSceneRenderer::Render()는 이 모든 DirectX 작업을 직접 API 호출로 줄줄 쓰는 곳이 아니라, RDG 위에 패스 이름표를 붙여 쌓는 곳이야. 그래서 rdg를 알고 읽으면 훨씬 편해. GraphBuilder는 주방장이 칠판에 "이 순서로 요리해"라고 적는 장부고, 실제 실행 순서와 리소스 배리어는 RDG가 정리해준다.

10. 이 챕터에서 딱 이것만

  • FDeferredShadingSceneRenderer::Render()는 한 프레임의 총괄 진행표야.
  • 큰 순서는 PrePass → BasePass → Lighting → Translucency → PostProcess야.
  • PrePass는 깊이 바닥, BasePass는 GBuffer 재료, Lighting은 빛 소스, Translucency는 투명 장식, PostProcess는 마지막 보정이야.
  • 세부 구현은 다른 파일에 흩어져 있고, 이 함수는 그 패스들을 RDG에 올리는 지휘자 역할을 해.
  • 디버깅할 때는 문제가 어느 코스에서 생겼는지 먼저 나눠야 해.

Q1. FDeferredShadingSceneRenderer::Render()는 큰 그림에서 무슨 역할인가요?

답 보기
이 함수는 세부 구현을 다 품은 거대 함수가 아니야. 오히려 반대로, RenderPrePass·RenderBasePass·RenderLights·RenderTranslucency·AddPostProcessingPasses 같은 큰 패스들을 정해진 순서로 호출하는 지휘자야. 코스 요리 총괄 셰프가 직접 썰고 굽는 게 아니라 "접시 데워 → 전채 → 메인 → 소스 → 장식 → 플레이팅" 순서로 벨만 치는 거랑 같아. 세부 요리사(각 패스)는 다음 챕터들이 따로 파고들고, 이 장은 동네 지도만 그려.

↳ 그 순서를 못 잡으면 실무에서 뭐가 곤란해지나요?

답 보기
디버깅할 때 바로 막혀. "그림자는 있는데 물체가 안 보인다"는 증상이 떴을 때, BasePass 문제인지 PrePass에서 깊이가 잘못 깔린 건지 후처리에서 날아간 건지 어느 코스에서 터졌는지 나눌 줄 알아야 RenderDoc을 열어도 의미가 있어. 패스가 20개 넘게 보이는데 순서 감각이 없으면 그냥 검은 상자야. 서버로 치면 SP_* 핸들러 하나하나는 아는데, 메인 루프가 언제 recv 털고 언제 DB 반영하고 언제 send flush하는지 모르면 디버깅이 안 되는 거랑 같지.

Q2. 디퍼드 렌더러의 큰 순서를 말해보세요. 왜 그 순서인가요?

답 보기
뼈대는 PrePass → BasePass → Lighting → Translucency → PostProcess야. 깊이를 먼저 깔고, GBuffer에 재질 정보를 눕히고, 빛을 얹고, 반투명을 따로 올리고, 후처리로 마감해. 이 순서가 디퍼드를 디퍼드답게 만드는 이유는 BasePass에서 최종 색을 끝내지 않기 때문이야. 재료를 GBuffer 접시에 먼저 깔아두고, 빛은 뒤에서 한꺼번에 부어. 요리로 치면 접시에 재료 먼저 깔고 소스는 나중에 붓는 방식이지. 계산을 뒤로 미룬다고 해서 Deferred야.

↳ 그럼 빛을 물체 그릴 때 바로 계산하면 왜 안 되나요?

답 보기
라이트가 10개, 100개로 늘면 같은 재료를 보면서 빛 계산을 계속 반복하게 돼. 물체 하나 그릴 때마다 그 자리에서 조명 다 계산하면, 주방에서 소스 바뀔 때마다 재료 손질부터 다시 하는 꼴이야. 그래서 재질 정보(노멀·러프니스·metallic 등)를 GBuffer에 먼저 적어두고, Lighting 단계에서 그 GBuffer를 읽어 빛을 한 번에 계산해. 라이트 수가 늘어도 재료 손질은 한 번만 하는 거지.

Q3. PrePass는 왜 있나요? BasePass에서 깊이도 같이 쓰면 안 되나요?

답 보기
그냥 BasePass에서 색도 칠하고 깊이도 쓰면 단순하긴 해. 근데 앞 건물에 가려질 픽셀도 비싼 머티리얼 셰이더를 돌린 뒤 버리면 헛일이 커져. 접시 뒤에 숨을 재료까지 정성껏 굽는 셈이지. 그래서 PrePass에서 깊이만 싸게 먼저 깔아서 "뒤에 숨은 애는 패스"라고 빨리 판정해. PrePass는 예쁜 그림 만드는 패스가 아니라, 뒤 패스가 덜 고생하게 하는 교통정리 패스야. GPU 말로는 Early Z 감각이고.

↳ 서버 메인 루프로 비유하면 PrePass가 뭐랑 대응돼요?

답 보기
게임 로직 tick 돌리기 전에 접속 끊긴 세션·죽은 액터·유효하지 않은 작업을 먼저 걷어내는 단계랑 같아. 나중에 무거운 로직을 덜 돌리려고 앞에서 싼 검사를 하는 거지. PrePass도 똑같이, 비싼 BasePass 픽셀 셰이더를 덜 돌리려고 앞에서 싼 깊이 검사를 먼저 하는 거야. "비싼 일 하기 전에 싼 정보로 버릴 거 버린다"는 구조가 완전히 같아.

Q4. 반투명(Translucency)은 왜 불투명 조명 다 끝난 뒤에 따로 오나요?

답 보기
GBuffer는 한 픽셀에 "제일 앞 물체 하나"의 정보만 안정적으로 넣기 쉬워. 근데 유리·물·연기는 뒤가 비쳐야 하니까 그 픽셀에 여러 겹이 겹쳐. 앞 하나만 저장하는 GBuffer 구조에 안 맞는 거지. 게다가 어떤 순서로 섞느냐(blending)에 따라 색이 달라져서 순서가 중요해. 그래서 불투명 세계를 GBuffer로 먼저 완성하고, 반투명은 깊이와 순서를 보며 뒤에서 별도 패스로 얹어. 투명 젤리 장식을 소스 붓기 전에 올리면 망가지니까 메인 접시 거의 완성된 뒤 올리는 거야.

↳ 그럼 이 Render()가 실제 DirectX 호출을 직접 줄줄 부르는 건가요?

답 보기
아니야. Render()는 GraphBuilder(RDG) 위에 패스 이름표를 붙여 쌓는 곳이지, D3D API를 직접 호출하는 데가 아니야. 주방장이 칠판에 "이 순서로 요리해"라고 적는 장부라고 보면 돼. 실제 실행 순서와 리소스 배리어는 RDG가 정리해줘. 그래서 이 함수를 읽을 땐 "PrePass는 depth-only draw, BasePass는 MRT에 GBuffer 쓰는 draw, Lighting은 GBuffer 읽어 scene color에 더하는 pass"처럼 역할로 읽으면 되고, 실제 호출 릴레이는 RDG가 맡아.

↳ Nanite나 Lumen 같은 것들은 이 순서 어디에 끼나요?

답 보기
큰 코스는 안 무너지고, 그 뼈대 주변에 붙어. Nanite는 PrePass/BasePass 주변을 바꾸고(지오메트리 래스터 방식이 달라지니까), Lumen은 Lighting 주변에 붙어(간접광·반사), Virtual Shadow Map은 shadow와 lighting 사이에 끼어들고, Hair·Water·Cloud는 자기 전용 보조 패스를 둬. 실제 함수 안엔 이런 갈림길이 엄청 많지만, 처음엔 PrePass → BasePass → Lighting → Translucency → PostProcess 뼈대에 다 걸어두면 돼. 골목이 아무리 많아도 큰길은 이 다섯이야.
