대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "왜 언리얼에 렌더러가 여러 개고, ShadingPath가 갈리는 그 else가 무슨 세계인가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

이 책은 지금까지 계속 한 갈래만 팠어. FDeferredShadingSceneRenderer. PrePass로 깊이 깔고, BasePass로 GBuffer에 재질 눕히고, Lighting에서 빛 얹고, 후처리로 마감하고. 40장을 거쳐오는 동안 이게 "렌더링이란 원래 이런 것"처럼 보였을 거야.

근데 잠깐. bigpicture에서 우리가 본 그 코드 기억나? 3절에서 딱 이렇게 찍혀 있었어.

if (ShadingPath == EShadingPath::Deferred) { OutRenderers.Add(new FDeferredShadingSceneRenderer(...)); } else { ... ← 이게 뭐야? }

그때는 "모바일은 다른 감독도 있다까지만 기억하고 지나가자"고 하고 넘어갔지. 이번 장이 그 else를 펼치는 장이야.

왜 이게 중요하냐면, 이걸 모르면 실무에서 정확히 두 가지가 터져. 첫째, 모바일이나 VR 프로젝트에 투입되는 순간 이 책의 지도가 통째로 안 맞아. RenderDoc을 열었는데 GBufferA/B/C가 아예 없어. 라이팅 패스도 없어. BasePass 하나에서 최종 색이 다 나와버려. "내가 배운 디퍼드는 어디 갔지?" 하고 멘붕이 와. 둘째, 왜 어떤 기능은 되고 어떤 기능은 안 되는지를 설명 못 해. 아티스트가 "왜 모바일에선 클리어코트가 안 먹어요?", "왜 포워드에선 데칼이 이상해요?"라고 물으면 답이 안 나와.

더 근본적인 질문은 이거야. 디퍼드가 그렇게 좋으면 왜 언리얼은 렌더러를 하나로 안 통일했을까? 코드를 두 벌 유지하는 건 엄청난 비용이야. 그런데도 안 합쳤다는 건, 디퍼드가 죽어도 못 하는 일이 있다는 뜻이거든. MSAA, 다양한 셰이딩 모델, 반투명, 그리고 무엇보다 대역폭.

서버로 치면 이런 거야. 너는 지금까지 "IOCP + 싱글스레드 게임 로직"이라는 한 아키텍처만 팠어. 근데 실무에 나가면 채팅 서버는 그렇게 안 짜. 매칭 서버도 그렇게 안 짜. "왜 이 구조를 안 쓰는가"를 설명할 수 있어야 그 구조를 진짜 이해한 거야. 디퍼드도 똑같아. 디퍼드의 한계를 모르면 디퍼드를 아는 게 아니야.

그래서 이 장은 마지막 정리이자, 지금까지 배운 걸 뒤집어보는 장이야. 렌더러는 하나가 아니고, 정답도 하나가 아니다.

🧱 먼저 알아야 할 것 — 계산을 "지금" 하느냐 "나중에" 하느냐
• 지금 하기: 물건을 하나 볼 때마다 그 자리에서 답까지 다 내는 방식. 물건 하나만 있으면 제일 빠르고 간단해.
• 나중에 하기: 일단 물건 정보만 표에 적어두고, 표가 다 차면 그때 몰아서 답을 낸다. 물건이 많고 계산이 반복될 때 이득이야.
• 공짜는 없다: 나중에 하려면 표를 어딘가에 적어둬야 해. 그 표 자체가 자리를 차지하고, 표를 쓰고 읽는 데도 시간이 든다.
이게 잡히면 아래 "디퍼드 vs 포워드" 설명이 통째로 얹힌다.

0. 비유부터 — 대형 스튜디오와 게릴라 촬영팀

우리 촬영장 비유를 마지막으로 한 번 더 굴리자.

디퍼드는 대형 스튜디오 촬영이야. 배우 200명이 있어. 감독은 배우를 하나씩 붙잡고 조명을 켜지 않아. 대신 배우 전원의 재료표(옷 색, 얼굴 방향, 피부 재질)를 커다란 게시판(GBuffer)에 먼저 다 적어. 그 다음 조명팀이 들어와서 게시판만 보고 조명 50개를 한 번에 쏜다. 배우가 몇 명이든 조명팀은 게시판 한 장만 보면 돼.

포워드는 게릴라 야외 촬영이야. 게시판 같은 거 없어. 배우 한 명을 카메라에 잡는 그 순간, 그 자리에서 조명을 켜고 색을 확정하고 찍어버려. 다음 배우로 넘어가면 조명을 다시 켠다. 게시판을 안 만드니까 장비도 가볍고 준비도 빨라. 대신 배우 200명 × 조명 50개면 조명을 만 번 켜야 해.

모바일은 배터리로 도는 소형 촬영팀이야. 여기가 진짜 핵심인데 — 이 팀엔 게시판을 놓을 자리 자체가 없어. 게시판을 쓰려면 촬영장에서 장비 트럭까지 매번 걸어갔다 와야 해. 그 왕복이 배터리를 다 잡아먹어. 그래서 모바일은 기본이 게릴라 촬영이야.

이번 장의 전부는 이 한 문장이야. 게시판(GBuffer)은 공짜가 아니다. 게시판을 만드는 게 이득인 촬영장이 있고, 게시판이 오히려 촬영을 망치는 촬영장이 있다.

🌱 이 개념은 왜 생겼나 — 포워드 렌더러
• 원래 구조: 사실 포워드가 원조야. 디퍼드가 나오기 전엔 다 이랬어. 물체를 그릴 때 그 자리에서 조명까지 계산해서 최종 색을 뱉는다. 제일 자연스럽고, 제일 단순하다.
• 그런데 문제: 라이트가 늘면 물체 × 라이트로 곱셈 폭발이 나. 그래서 디퍼드가 나왔지(deferred-overview).
• 그래서 필요한 것: 근데 디퍼드로 다 갈아탄 뒤에 보니, GBuffer 때문에 MSAA도 못 쓰고 대역폭도 터지더라고. 그래서 "라이트를 미리 화면 격자에 나눠 담아두고, 포워드로 그리되 그 픽셀에 닿는 라이트만 도는" 개량 포워드가 돌아왔어. 그게 지금 언리얼의 Forward / Mobile 렌더러야.

1. 갈림길 — ShadingPath가 감독을 고른다

먼저 그 else를 정면으로 보자. bigpicture에서 잘려 있던 코드의 전문이야.

SceneRenderBuilder.cpp:511

if (ShadingPath == EShadingPath::Deferred) { OutRenderers.Add(new FDeferredShadingSceneRenderer(ViewFamily, HitProxyConsumer)); } else { check(ShadingPath == EShadingPath::Mobile); OutRenderers.Add(new FMobileSceneRenderer(ViewFamily, HitProxyConsumer)); }
🔤 기호 사전 — 감독 선택 분기
• EShadingPath = 이 씬을 어떤 셰이딩 경로로 그릴지 정하는 enum이야. 값은 Deferred와 Mobile 둘뿐이야.
• FDeferredShadingSceneRenderer = 우리가 40장 내내 판 그 감독. PC/콘솔의 큰 줄기.
• FMobileSceneRenderer = 이 장의 주인공. 완전히 별개의 렌더러 클래스야. 같은 클래스의 다른 모드가 아니라 다른 클래스야.
• check(...) = "여기 왔으면 반드시 Mobile이어야 한다"는 안전 검사. 즉 경로는 딱 두 개라는 선언이야.
• OutRenderers.Add(...) = 이번 프레임을 맡을 렌더러를 목록에 올린다.
• new = 객체를 새로 만든다. 프레임마다 렌더러 객체가 만들어진다는 뜻이야.
🔁 이제 다시 보자. ShadingPath를 보고 → 디퍼드면 FDeferredShadingSceneRenderer를, 아니면 FMobileSceneRenderer를 만든다. check가 말하듯 경로는 딱 둘이야. 촬영장으로 치면 "오늘 촬영은 스튜디오 감독한테 맡길래, 게릴라 감독한테 맡길래"를 프레임 시작 시점에 정하는 장면이야.

여기서 중요한 걸 하나 짚고 가자. EShadingPath는 두 값밖에 없어. Deferred랑 Mobile. 그런데 언리얼엔 분명히 "Forward Shading"이라는 옵션도 있잖아? 이게 초보를 제일 헷갈리게 하는 지점이야.

정리하면 이래. 렌더러 클래스는 2개, 셰이딩 방식은 3가지야.

  • FDeferredShadingSceneRenderer + GBuffer 씀 → Deferred (PC/콘솔 기본, 우리가 40장 판 그거)
  • FDeferredShadingSceneRenderer + GBuffer 안 씀 → Desktop Forward (VR/MSAA용. 같은 렌더러 클래스인데 라이팅 방식이 다름)
  • FMobileSceneRenderer → Mobile (얘는 또 안에서 forward/deferred가 갈림. 뒤에서 봄)

그러니까 "포워드 렌더러"는 별도 클래스가 아니야. 같은 FDeferredShadingSceneRenderer 안에서 "GBuffer 쓰지 마"라는 스위치가 켜진 상태에 가까워. 이름이 참 얄궂지. 서버로 치면 GameServer 클래스는 하나인데 bUseDbCache 깃발 하나로 내부 동작이 통째로 갈리는 거랑 비슷해.

2. 포워드의 정의 — "GBuffer를 안 쓴다"

그럼 그 스위치가 코드 어디에 있냐. 놀랍도록 짧아. 이 두 함수가 이 장 전체의 뼈대야.

RenderUtils.cpp:1557

bool IsForwardShadingEnabled(const FStaticShaderPlatform Platform) { return (GForwardShadingPlatformMask[(int)Platform]) // Culling uses compute shader && GetMaxSupportedFeatureLevel(Platform) >= ERHIFeatureLevel::SM5; } bool IsUsingGBuffers(const FStaticShaderPlatform Platform) { if (IsMobilePlatform(Platform)) { return IsMobileDeferredShadingEnabled(Platform); } else { return !IsForwardShadingEnabled(Platform); } }
🔤 기호 사전 — 포워드 판정
• FStaticShaderPlatform Platform = "어느 셰이더 플랫폼이냐"(PC D3D12냐, 안드로이드 Vulkan이냐 등). 플랫폼이 인자라는 게 핵심이야 — 판정 기준이 플랫폼이라는 뜻.
• GForwardShadingPlatformMask = 플랫폼별로 "포워드 켰냐"를 비트로 담은 전역 마스크. 프로젝트 설정의 Forward Shading 체크박스가 여기로 흘러들어와.
• GetMaxSupportedFeatureLevel(Platform) >= ERHIFeatureLevel::SM5 = 이 플랫폼이 SM5 이상이어야 한다는 조건. 주석이 이유를 대놓고 말해 — 라이트 컬링에 컴퓨트 셰이더를 쓰거든.
• IsUsingGBuffers(...) = "이 플랫폼에서 GBuffer를 쓰냐"를 묻는 함수.
• !IsForwardShadingEnabled(Platform) = !는 뒤집기. 포워드가 아니면 GBuffer를 쓴다는 뜻이야.
• IsMobilePlatform(Platform) = 모바일이냐. 모바일은 판정 규칙 자체가 달라서 먼저 갈라낸다.
🔁 이제 다시 보자. IsUsingGBuffers는 모바일이면 IsMobileDeferredShadingEnabled를 묻고, 아니면 !IsForwardShadingEnabled를 돌려줘. 이 한 줄이 이번 장의 정의야. 포워드 = GBuffer를 안 쓰는 것. 반대로 디퍼드 = GBuffer를 쓰는 것. 촬영장으로 치면 "게시판을 세우냐 마냐"가 두 감독을 가르는 유일한 기준이라는 소리야.

이걸 보면 basepass-shader에서 봤던 그 #if USES_GBUFFER가 갑자기 다르게 읽혀. 그때 우리는 "GBuffer를 쓰는 경로인지 나타내는 컴파일 조건"이라고만 하고 넘어갔지. 그 조건이 여기서 결정되는 거야. 포워드로 빌드하면 USES_GBUFFER가 꺼지고, EncodeGBufferToMRT 호출 자체가 셰이더에서 사라져. 그럼 그 자리에 뭐가 들어오냐? 그게 다음 절이야.

그리고 >= ERHIFeatureLevel::SM5도 그냥 지나치지 마. 포워드가 "옛날 방식"이라 아무 데서나 도는 게 아니야. 지금의 포워드는 컴퓨트 셰이더로 라이트를 미리 컬링해두는 개량형이라서, 오히려 SM5 이상을 요구해. 원조 포워드가 아니라 Forward+인 거지.

🌱 이 개념은 왜 생겼나 — 라이트 그리드(Light Grid)
• 원래 구조: 옛날 포워드는 물체를 그릴 때 씬의 모든 라이트를 다 돌았어. 배우 한 명 찍는데 촬영장 조명 50개를 전부 확인하는 거야.
• 그런데 문제: 화면 왼쪽 끝 픽셀이 오른쪽 끝 전구를 왜 확인해? 어차피 안 닿는데. 낭비가 물체 수만큼 곱해져서 커져.
• 그래서 필요한 것: 화면을 격자(cell)로 쪼개고, 격자 칸마다 "여기 닿는 라이트 목록"을 미리 적어두자. 그럼 픽셀은 자기 칸의 짧은 목록만 돌면 돼. 그 격자가 라이트 그리드고, 이걸 채우는 게 LightGridInjection.usf야.

3. 그럼 라이트는 어떻게 하냐 — 픽셀이 직접 라이트를 돈다

디퍼드는 라이팅이 별도 패스였어(deferred-lighting). GBuffer 다 채운 다음, 라이트마다 화면을 한 번씩 훑으면서 빛을 더했지.

포워드엔 그런 패스가 아예 없어. 라이팅이 BasePass 픽셀 셰이더 안에서 끝나. 픽셀 하나가 자기 격자 칸의 라이트 목록을 직접 for문으로 돈다.

🔤 기호 사전 — 픽셀 안의 라이트 루프
• GridIndex = 이 픽셀이 속한 격자 칸 번호. 화면 x/y와 깊이로 계산해서 나온다.
• GetCulledLightsGridHeader(GridIndex) = 그 칸의 머리말을 가져온다. "이 칸엔 라이트 몇 개, 목록은 어디서부터"가 적혀 있어.
• NumLights = 이 칸에 닿는 라이트 개수. 씬 전체 라이트 수가 아니라 이 칸에만 닿는 수야.
• min(..., GetMaxLightsPerCell()) = 칸당 라이트 수에 상한을 건다. 주석이 이유를 말해 — 안 막으면 초기화 안 된 버퍼를 읽다가 GPU가 멈출(hang) 수 있어.
• LOOP = 이 for문을 펼치지(unroll) 말고 진짜 루프로 돌라는 컴파일러 힌트야.
• for (uint GridLightListIndex = 0; ... ++) = 이 장의 심장. 픽셀 셰이더 안에서 라이트를 하나씩 도는 반복문이야.
• GetLocalLightDataFromGrid(...) = 목록에서 i번째 라이트의 실제 데이터를 꺼낸다.
• DataStartIndex + GridLightListIndex = 이 칸 목록의 시작 위치 + 몇 번째. 서버의 버퍼시작 + 오프셋이랑 똑같은 감각이야.
🔁 이제 다시 보자. 픽셀이 자기 GridIndex를 구하고 → 그 칸의 헤더에서 NumLights를 읽고 → 상한을 씌운 뒤 → for문으로 그 칸의 라이트만 하나씩 돌면서 빛을 더한다. 디퍼드처럼 "라이트마다 화면 한 번씩"이 아니라, "픽셀마다 자기 라이트 목록 한 번씩"이야. 방향이 통째로 뒤집힌 거지.

이게 왜 성립하냐면, 그리기 전에 컴퓨트 셰이더(LightGridInjection.usf)가 라이트를 격자 칸에 미리 뿌려뒀기 때문이야. 씬에 라이트가 500개여도, 한 격자 칸에 실제로 닿는 건 3~4개뿐이거든. 그래서 픽셀당 for문이 3~4바퀴로 끝나.

서버 감각으로 보면 이거 완전히 공간 분할이야. AOI(Area of Interest)랑 똑같아. 유저 한 명한테 월드의 모든 유저를 브로드캐스트하지 않고, 같은 섹터에 있는 유저만 골라 보내잖아. 라이트 그리드는 화면판 AOI야. 픽셀은 자기 섹터의 라이트만 본다.

🧱 먼저 알아야 할 것 — 격자로 나누면 왜 싸지나
• 전수 검사: 사람 1000명과 전구 500개가 있을 때, "누가 어느 전구에 비치나"를 다 확인하면 1000 × 500 = 50만 번이야.
• 칸으로 나누기: 방을 100칸으로 쪼개고, 전구마다 "내 빛이 닿는 칸"을 먼저 표시해두면, 한 칸엔 전구가 서너 개뿐이야.
• 결과: 사람은 자기 칸의 전구 서너 개만 보면 돼. 1000 × 4 = 4천 번. 곱셈의 한쪽 항을 500에서 4로 줄인 거야.
이게 잡히면 아래 "그럼 포워드가 라이트 수에 강한 거 아니냐" 논쟁이 얹힌다.

5. ⭐ 디퍼드가 못 하는 것 — GBuffer의 청구서

자, 이제 이 장의 진짜 알맹이. 디퍼드가 그렇게 좋은데 왜 안 통일했나. 네 가지 청구서가 있어.

(1) MSAA — 픽셀당 샘플이 GBuffer 장수만큼 곱해진다

MSAA(Multi-Sample Anti-Aliasing)는 계단 현상을 없애려고 픽셀 하나를 여러 샘플로 쪼개는 기법이야. 4x MSAA면 픽셀마다 샘플 4개.

포워드에선 이게 싸. 렌더타깃이 색 하나뿐이니까 색 버퍼만 4배가 돼. 근데 디퍼드는? GBuffer가 A/B/C/D/E 다섯 장이야. 그 다섯 장이 전부 4배가 돼. 게다가 라이팅 패스는 그 4배짜리 GBuffer를 샘플마다 다시 읽어서 조명 계산을 4번 해야 해. 메모리도 4배, 대역폭도 4배, 라이팅 비용도 4배야.

그래서 언리얼은 MSAA를 아예 포워드 전용 기능으로 못 박아뒀어. CVar 설명문이 대놓고 말한다.

(2) 셰이딩 모델 — 다 담으려면 GBuffer가 무한히 넓어져야 한다

basepass-shader에서 ShadingModelID를 봤지. 클리어코트, 헤어, 피부, 눈, 천... 근데 문제가 있어. 재질마다 필요한 데이터가 다르다. 클리어코트는 코팅 러프니스가 필요하고, 헤어는 산란 값이 필요하고, 피부는 서브서피스 프로파일이 필요해.

디퍼드는 이걸 고정된 GBuffer 칸에 다 우겨넣어야 해. 그래서 CustomData라는 만능 칸을 하나 만들어놓고, 셰이딩 모델마다 다른 의미로 재활용해. 재질 종류가 늘수록 이 압축이 더러워지고, 정밀도가 깎이고, 결국 새 셰이딩 모델을 추가하려면 GBuffer 포맷을 건드려야 해.

포워드는 이 문제가 없어. 픽셀 안에서 라이팅을 끝내니까, 중간 데이터를 어디 저장할 필요가 없거든. 재질이 뭘 얼마나 쓰든 그건 그 셰이더 안의 지역 변수 문제야. 대신 셰이더 순열이 폭발해(→ shader-permutation). 디퍼드는 "GBuffer 포맷 압박"을, 포워드는 "순열 압박"을 받는 구조야.

(3) 반투명 — 디퍼드는 애초에 손도 못 댄다

이건 translucency에서 이미 통째로 판 얘기야. 근데 그때 우리가 뭐라고 결론 냈는지 기억나? "반투명은 별도 포워드식 패스로 간다."

그때는 그게 무슨 뜻인지 애매했을 거야. 이제 정확히 말할 수 있어. 디퍼드 렌더러 안에 이미 포워드 렌더러가 들어 있다. 유리창을 그릴 때 언리얼은 GBuffer에 안 눕히고, 그 자리에서 라이트 그리드를 돌아 라이팅을 끝내고 scene color에 블렌드해. 방금 3절에서 본 그 for문을 반투명 픽셀도 똑같이 돈다. ForwardLightingCommon.ush에 MATERIALBLENDING_ANY_TRANSLUCENT 갈래가 있는 게 그 증거야.

그러니까 이건 이렇게 읽어야 해. 순수한 디퍼드 엔진은 없다. 디퍼드 엔진도 반투명은 포워드로 처리해. 디퍼드는 "불투명 전용 최적화"에 가깝고, 포워드는 그 최적화를 못 받는 나머지를 다 떠맡는 만능 백업이야.

(4) 대역폭 — 모바일에선 이게 사형선고다

앞의 셋은 "불편"이야. 이건 급이 달라. 모바일에선 GBuffer가 성립 자체를 못 한다. 절을 따로 뺄게.

6. 모바일 타일 GPU에서 GBuffer가 왜 비싼가 — 대역폭

🧱 먼저 알아야 할 것 — 작업대와 창고는 다르다
• 가까운 작업대: 손 닿는 곳에 있는 작은 책상. 꺼내고 넣는 게 거의 공짜야. 대신 아주 좁다.
• 먼 창고: 크지만 멀다. 물건 하나 가지러 갈 때마다 걸어갔다 와야 해. 시간도 들고, 힘(전력)도 든다.
• 왕복 횟수가 비용: 창고를 몇 번 왕복하느냐가 곧 비용이야. 물건 크기보다 왕복 횟수가 중요해.
이게 잡히면 아래 "타일 메모리 vs 메인 메모리" 설명이 그대로 얹힌다.

모바일 GPU는 타일 기반(Tile-Based)이야. 데스크톱 GPU랑 작동 방식이 근본적으로 달라.

데스크톱 GPU는 화면 전체 버퍼를 메인 메모리(VRAM)에 놓고, 픽셀을 그릴 때마다 그리로 쓴다. VRAM 대역폭이 초당 수백 GB니까 그래도 돼.

모바일 GPU는 그럴 수가 없어. 메모리 대역폭이 데스크톱의 몇십 분의 일이고, 메모리를 왕복할 때마다 배터리가 닳아. 그래서 화면을 작은 타일(예: 32×32)로 쪼개고, 타일 하나를 칩 안의 초고속 작은 메모리(타일 메모리)에 올려놓고 거기서만 작업해. 타일이 다 그려지면 그때 한 번만 메인 메모리로 내보낸다.

데스크톱 GPU (Immediate Mode) 픽셀 그릴 때마다 → VRAM에 직접 쓰기 대역폭이 넉넉하니까 GBuffer 5장도 그냥 씀 모바일 GPU (Tile-Based) 화면을 32x32 타일로 쪼갬 타일 하나를 칩 안 작은 메모리에 올림 ← 여기선 공짜 타일 안에서 다 그림 끝나면 메인 메모리로 1회 내보냄 ← 여기가 비싸다 그런데 GBuffer 5장을 쓰면? 타일 메모리에 5장이 안 들어감 → 매번 메인 메모리로 내보내고 다시 읽어옴 → 왕복 폭발 → 대역폭 폭발 → 발열 → 스로틀링

바로 이 지점이 bRequiresMultiPass야. 아까 4절에서 본 그 깃발. 이 함수가 그 판정을 해.

• GSupportsShaderFramebufferFetch = 이 기기가 framebuffer fetch를 실제로 지원하는지 알려주는 전역 깃발.
• IsMetalMobilePlatform(...) = iOS(Metal)냐. 주석대로 iOS는 전부 지원해서 false.
🔁 이제 다시 보자. 이 함수는 "GBuffer를 타일 안에 가둬둘 수 있냐"를 기기별로 묻는다. framebuffer fetch가 없으면 → true(왕복해야 함, 비쌈). Vulkan은 subpass가 있으니 → false. iOS는 다 지원하니 → false. 모바일 디퍼드가 성립하려면 "GBuffer를 메모리에 안 내보내고 타일 안에서 즉시 소비"가 가능해야 한다는 뜻이야. 촬영장으로 치면 "게시판을 촬영장 안에 세울 수 있냐, 아니면 장비 트럭까지 매번 갔다 와야 하냐"를 묻는 거지.

이제 RenderDeferredSinglePass와 RenderDeferredMultiPass가 왜 나뉘는지 완전히 보여. SinglePass는 "GBuffer를 만들고 타일 안에서 바로 소비"고, MultiPass는 "GBuffer를 메모리에 진짜로 쓰고, 다시 읽어옴"이야. 같은 디퍼드인데 비용이 몇 배 차이가 나.

그래서 모바일의 기본값이 포워드인 거야. 포워드는 애초에 GBuffer가 없으니 이 고민 자체가 없어. 타일 안에서 색 하나 만들고 한 번 내보내면 끝.

🌱 이 개념은 왜 생겼나 — Framebuffer Fetch / Subpass
• 원래 구조: 픽셀 셰이더는 "쓰기 전용"이었어. 자기가 방금 쓴 렌더타깃 값을 다시 읽으려면 패스를 끊고, 메모리에 쓰고, 텍스처로 다시 바인딩해야 했지.
• 그런데 문제: 모바일에선 그 "메모리에 쓰고 다시 읽기"가 가장 비싼 동작이야. 타일 안에 이미 값이 있는데 굳이 창고까지 왕복하는 꼴이니까.
• 그래서 필요한 것: "방금 이 타일에 쓴 값을 그 자리에서 읽게 해줘"가 필요해. 그게 framebuffer fetch(GL/Metal)이고, Vulkan에선 subpass의 input attachment야. 이게 있어야 모바일 디퍼드가 단일 패스로 성립한다.

7. ⭐ 포워드가 못 하는 것 — 곱셈 폭발

여기까지 읽으면 이런 생각이 들 거야. "어? 포워드가 다 나은데? 그럼 디퍼드는 왜 나온 거야?"

바로 이 질문이 deferred-overview의 출발점이었어. 거기서 우리가 뭐라고 했지?

"라이트가 10개, 100개로 늘면 같은 재료를 보면서 빛 계산을 계속 반복해. 주방에서 소스가 바뀔 때마다 재료 손질부터 다시 하는 꼴이야." — deferred-overview

이게 포워드의 사형선고야. 숫자로 보자.

포워드 (그리드 없는 원조) 물체 1000개 × 라이트 100개 = 라이팅 계산 100,000회 게다가 오버드로우까지 곱해짐 → 라이트를 하나 더 놓을 때마다 물체 수만큼 비용 증가 디퍼드 BasePass: 물체 1000개 = GBuffer 쓰기 1000회 Lighting: 라이트 100개 × 그 라이트가 덮는 화면 영역 → 물체 수와 라이트 수가 곱해지지 않고 "분리"됨 → 라이트를 하나 더 놓아도 물체 수와 무관

디퍼드의 본질은 "물체 × 라이트"를 "물체 + 라이트"로 바꾼 것이야. 곱셈을 덧셈으로 바꾼 거지. GBuffer는 그 덧셈을 가능하게 하는 중간 장부일 뿐이고.

서버로 치면 완전히 O(N×M) → O(N+M) 최적화야. 유저 N명의 상태를 M개 시스템에 각각 전파하지 말고, 공유 스냅샷에 한 번 쓰고 시스템들이 그걸 읽게 하는 거. 스냅샷이 GBuffer야.

"근데 라이트 그리드 있으면 해결된 거 아니에요?"

날카로운 질문이야. 그리고 부분적으로만 맞아.

라이트 그리드는 "픽셀당 라이트 수"를 줄여줘. 씬에 라이트 500개여도 한 칸엔 3~4개니까 for문이 3~4바퀴로 끝나지. 이건 진짜 큰 개선이야. 그래서 지금의 Forward+는 옛날 포워드처럼 무기력하지 않아.

근데 안 풀리는 게 남아.

  • 겹치는 라이트(overlap): 한 격자 칸에 라이트 20개가 겹치는 구역이 생기면? 그 칸의 모든 픽셀이 20바퀴를 돈다. 디퍼드는 이런 경우에도 라이트별로 화면 영역만 처리하면 되지만, 포워드는 픽셀이 다 뒤집어써. 게다가 코드에 GetMaxLightsPerCell() 상한이 있잖아 — 칸당 라이트 수엔 하드 리밋이 있어. 넘치면 그냥 잘려서 안 그려진다.
  • 오버드로우: 포워드는 픽셀이 여러 번 그려지면(앞뒤로 겹친 물체) 라이팅도 그만큼 반복돼. 디퍼드는 GBuffer에 최종 표면 하나만 남으니 라이팅은 딱 한 번이야. Early-Z로 어느 정도 막지만 완벽하진 않아.
  • 화면 공간 효과: SSAO, SSR, 데칼, Lumen 같은 건 "화면 전체의 노멀·러프니스 맵"을 읽어야 돌아가. 그게 바로 GBuffer야. 포워드엔 그 맵이 없으니 이런 기능이 통째로 제한되거나, 노멀만 따로 뽑는 별도 패스를 붙여야 해. 현대 렌더링의 화려한 기능 대부분이 GBuffer를 전제로 깔고 있어.

그래서 최종 결론은 "라이트를 많이, 화면 공간 효과를 화려하게" → 디퍼드, "MSAA가 필요하거나(VR), 대역폭이 목숨이거나(모바일), 재질이 특이하거나(반투명)" → 포워드야.

DirectX로 직접 짜던 때

이건 네가 몸으로 겪은 얘기일 거야. 처음 DirectX로 렌더러를 짜면 누구나 포워드로 시작해. 당연하지 — 그게 자연스럽거든. 버텍스 셰이더로 변환하고, 픽셀 셰이더에서 N·L 계산해서 return float4(color, 1). 라이트 하나면 완벽하게 돌아가.

라이트 2개도 괜찮아. 상수 버퍼에 배열로 넣고 for문 두 바퀴 돌리면 돼. 5개도 어찌어찌 돼.

그런데 20개쯤에서 벽을 만나. 프레임이 뚝 떨어져. 프로파일러를 켜보면 픽셀 셰이더가 다 잡아먹고 있어. 당연하지 — 물체 하나 그릴 때마다 라이트 20개를 다 돌고 있고, 화면 왼쪽 끝 벽이 오른쪽 끝 전구까지 계산하고 있으니까. 게다가 셰이더 상수 버퍼에 라이트 배열 크기를 고정해놨는데 라이트 수가 그걸 넘어가면? 셰이더를 라이트 개수별로 여러 벌 컴파일하고 있는 자신을 발견해. (이게 셰이더 순열의 첫 경험이지.)

그래서 디퍼드로 갈아탄다. 렌더타깃 여러 장 만들고, SV_Target0~3에 노멀/알베도/러프니스를 뱉고, 풀스크린 쿼드 하나로 라이트마다 조명을 더해. 그 순간 라이트 100개를 켜도 프레임이 안 떨어져. 감동적이지. "이래서 디퍼드구나."

그리고 정확히 이 순간 다음 벽을 만나. 유리창을 그리려니 안 돼. MSAA를 켜려니 렌더타깃이 5장이라 메모리가 터져. 캐릭터 피부를 특별하게 처리하려니 GBuffer에 넣을 칸이 없어. 네가 겪은 그 순서가 그대로 렌더링 역사이고, 그대로 이 장의 내용이야. 언리얼은 그 두 벽을 다 만났고, 그래서 렌더러를 하나로 안 합친 거야.

요청 적으면 즉시 처리가 이김라이트 적으면 포워드가 이김
요청 많으면 배치가 이김 (N×M → N+M)라이트 많으면 디퍼드가 이김
임베디드/저사양 서버는 큐를 못 감당모바일 타일 GPU는 GBuffer를 못 감당
순서가 중요한 요청은 배치가 어려움반투명은 디퍼드가 못 다룸

핵심은 "중간 장부를 만드는 게 이득이냐"야. 서버에서도 캐시나 큐 같은 중간 계층은 공짜가 아니잖아. 트래픽이 적으면 오히려 손해야. GBuffer도 똑같아. 라이트가 적고 대역폭이 귀하면, 중간 장부는 순손실이야.

10. 이 챕터에서 딱 이것만

  • SceneRenderBuilder.cpp:511의 else는 FMobileSceneRenderer다. 렌더러 클래스는 2개, 셰이딩 방식은 3가지(Deferred / Desktop Forward / Mobile).
  • 포워드의 정의는 딱 하나 — GBuffer를 안 쓴다(IsUsingGBuffers는 !IsForwardShadingEnabled).
  • 포워드는 BasePass 픽셀 셰이더 안에서 라이트 그리드를 for문으로 돌아 라이팅을 끝낸다. 별도 라이팅 패스가 없다.
  • 디퍼드가 못 하는 것 — MSAA(GBuffer × 샘플수 폭발), 다양한 셰이딩 모델(GBuffer 포맷에 갇힘), 반투명(어차피 포워드로 처리), 대역폭(모바일에선 치명적).
  • 모바일 타일 GPU는 GBuffer를 타일 메모리에 못 담는다. framebuffer fetch/subpass가 없으면 RequiresMultiPass가 true가 되고 메인 메모리 왕복이 폭발한다.
  • 포워드가 못 하는 것 — 라이트 수 확장(칸당 상한, 오버드로우), 화면공간 효과(SSR/SSAO/데칼/Lumen이 GBuffer를 전제로 한다).
  • ERHIFeatureLevel(능력 등급) + EShaderPlatform(구체적 대상) → USES_GBUFFER 같은 셰이더 매크로 → 순열(ch-27) → PSO(ch-07)로 내려간다.
  • 정답은 하나가 아니다. "GBuffer라는 중간 장부가 이 플랫폼에서 이득이냐"가 모든 걸 가른다.

Q1. 언리얼에 렌더러가 왜 여러 개인가요? 디퍼드 하나로 통일하면 안 되나요?

답 보기
디퍼드가 죽어도 못 하는 게 있어서야. 코드 두 벌 유지가 엄청난 비용인데도 안 합쳤다는 게 그 증거지. SceneRenderBuilder.cpp:511에서 ShadingPath가 Deferred면 FDeferredShadingSceneRenderer, 아니면 FMobileSceneRenderer로 갈려. 디퍼드가 못 하는 건 크게 넷이야 — MSAA(GBuffer 장수 × 샘플 수로 폭발), 다양한 셰이딩 모델(고정 GBuffer 포맷에 다 못 우겨넣음), 반투명(픽셀당 표면 하나만 저장되니 애초에 불가), 대역폭(모바일 타일 GPU엔 사형선고). 그래서 "라이트 많고 화려한 화면 → 디퍼드", "MSAA/대역폭/특이 재질 → 포워드"로 갈라놓은 거야.

↳ 그럼 "Forward Shading"이라는 설정은 세 번째 렌더러 클래스인가요?

답 보기
아니야, 여기가 제일 헷갈리는 지점이야. 렌더러 클래스는 2개, 셰이딩 방식은 3가지야. Desktop Forward는 여전히 FDeferredShadingSceneRenderer인데 "GBuffer 쓰지 마" 스위치가 켜진 상태야. EShadingPath엔 Deferred랑 Mobile 두 값밖에 없고 check가 그걸 강제해. 포워드 여부는 별도 함수로 판정돼 — IsUsingGBuffers()가 !IsForwardShadingEnabled()를 돌려주거든. 즉 포워드의 정의는 "GBuffer를 안 쓴다" 딱 하나야. 클래스 이름이 얄궂을 뿐이지.

Q2. 포워드엔 라이팅 패스가 없다는데, 그럼 빛은 언제 계산되나요?

답 보기
BasePass 픽셀 셰이더 안에서 다 끝나. basepass-shader에서 EncodeGBufferToMRT가 있던 그 자리에, 포워드는 라이팅 루프가 들어와 있어. 픽셀이 자기 GridIndex(화면 격자 칸 번호)를 구하고 → 그 칸의 라이트 목록 헤더를 읽고 → for (GridLightListIndex = 0; ... < NumLightsInGridCell; ...)로 자기 칸에 닿는 라이트만 하나씩 돌면서 빛을 더해. 디퍼드가 "라이트마다 화면 한 번씩"이라면, 포워드는 "픽셀마다 자기 라이트 목록 한 번씩"이야 — 루프 방향이 통째로 뒤집힌 거지.

↳ 씬에 라이트 500개면 픽셀마다 500바퀴를 도나요?

답 보기
아니야, 그게 라이트 그리드가 있는 이유야. 그리기 전에 컴퓨트 셰이더(LightGridInjection.usf)가 화면을 격자로 쪼개고 칸마다 "여기 닿는 라이트 목록"을 미리 뿌려둬. 그래서 한 칸엔 실제로 3~4개뿐이고, 픽셀은 NumLightsInGridCell만큼만 돌면 돼. 서버의 AOI랑 똑같아 — 유저한테 월드 전체를 브로드캐스트 안 하고 같은 섹터 유저만 보내잖아. 라이트 그리드는 화면판 AOI야. 참고로 이 컬링이 컴퓨트 셰이더를 쓰기 때문에 IsForwardShadingEnabled가 >= ERHIFeatureLevel::SM5를 요구해 — 지금의 포워드는 원조가 아니라 Forward+인 거지.

↳ 그럼 라이트 그리드 덕분에 포워드가 라이트 수 문제를 해결한 건가요?

답 보기
부분적으로만. 픽셀당 라이트 수는 확 줄었지만 셋이 안 풀려. (1) 겹치는 라이트 — 한 칸에 라이트 20개가 겹치면 그 칸의 모든 픽셀이 20바퀴를 돌아. 게다가 GetMaxLightsPerCell()이라는 하드 리밋이 있어서 넘치면 그냥 잘려 나가. (2) 오버드로우 — 앞뒤로 겹친 물체는 픽셀이 여러 번 그려지고 라이팅도 그만큼 반복돼. 디퍼드는 GBuffer에 최종 표면 하나만 남으니 라이팅이 딱 한 번이지. (3) 화면공간 효과 — SSR·SSAO·데칼·Lumen은 "화면 전체의 노멀·러프니스 맵"을 읽어야 도는데, 그게 바로 GBuffer야. 포워드엔 없으니 이 기능들이 통째로 제한돼. 현대 렌더링의 화려한 기능 대부분이 GBuffer를 전제로 깔고 있어.

Q3. 모바일 타일 GPU에서 GBuffer가 왜 그렇게 비싼가요?

답 보기
대역폭 때문이야. 모바일 GPU는 타일 기반이라 화면을 32×32 같은 작은 타일로 쪼개고, 타일 하나를 칩 안의 초고속 작은 메모리에 올려서 거기서만 작업해. 다 그리면 메인 메모리로 한 번만 내보내지. 메모리 왕복이 배터리를 직접 태우니까 이렇게 설계된 거야. 그런데 GBuffer는 A~E 다섯 장이잖아 — 타일 메모리에 안 들어가. 그럼 매번 메인 메모리에 쓰고 다시 읽어야 하고, 왕복이 폭발하고, 발열로 스로틀링까지 와. 창고 비유로 "작업대에 안 올라가는 게시판을 쓰려고 장비 트럭까지 매번 왕복하는 꼴"이야. 그래서 모바일의 기본값은 포워드고, GBuffer 자체가 없으니 이 고민이 아예 없어.

↳ 근데 모바일에도 디퍼드 옵션이 있던데, 그건 어떻게 성립하나요?

답 보기
GBuffer를 타일 안에서 만들고 타일 안에서 바로 소비하면 성립해. 그러려면 "방금 이 타일에 쓴 값을 메모리 안 거치고 셰이더에서 바로 다시 읽는" 기능이 필요한데, 그게 framebuffer fetch(GL/Metal)와 subpass input attachment(Vulkan)야. FMobileSceneRenderer::RequiresMultiPass가 정확히 이걸 판정해 — MobileAllowFramebufferFetch가 안 되면 무조건 true(왕복 필요, 비쌈), Vulkan은 subpass가 있으니 false, iOS는 다 지원하니 false. 그 결과가 RenderDeferredSinglePass(타일에서 끝, 쌈)냐 RenderDeferredMultiPass(메모리 왕복, 비쌈)냐를 가른다. 같은 디퍼드인데 비용이 몇 배 차이가 나는 거야.

↳ 반투명이 "포워드로 처리된다"는 게 이제 무슨 뜻인지 설명해보세요.

답 보기
translucency에서 애매하게 넘어갔던 그 문장을 이제 정확히 말할 수 있어. 디퍼드 렌더러 안에 이미 포워드 렌더러가 들어 있다는 뜻이야. 유리창을 그릴 때 GBuffer에 안 눕히고, 그 자리에서 라이트 그리드 for문을 돌아 라이팅을 끝내고 scene color에 블렌드해. ForwardLightingCommon.ush에 MATERIALBLENDING_ANY_TRANSLUCENT 갈래가 있는 게 증거고, USES_GBUFFER 조건에 MATERIALBLENDING_SOLID || MATERIALBLENDING_MASKED가 박혀 있는 것도 같은 얘기야(반투명이면 GBuffer 안 씀). 결론: 순수한 디퍼드 엔진은 없다. 디퍼드는 "불투명 전용 최적화"고, 포워드는 그 최적화를 못 받는 나머지를 다 떠맡는 만능 백업이야.

Q4. ERHIFeatureLevel이 셰이더 순열이랑 PSO에 어떻게 연결되나요?

답 보기
연쇄가 이래. 프로젝트 설정 + 타깃 플랫폼 → EShaderPlatform/ERHIFeatureLevel → IsForwardShadingEnabled/IsUsingGBuffers → 셰이더 매크로 → 순열 → PSO. 결정적인 한 줄이 ShaderMaterialDerivedHelpers.cpp:46이야 — USES_GBUFFER = (FEATURE_LEVEL >= ... && (SOLID || MASKED) && !FORWARD_SHADING). 이 값이 셰이더 컴파일 환경에 매크로로 꽂히고, basepass-shader에서 본 #if USES_GBUFFER 블록이 살거나 죽어. 살면 EncodeGBufferToMRT가 돌고, 죽으면 그 자리에 라이팅 루프가 들어와. 그리고 렌더타깃 개수 자체가 달라지니(MRT 5장 vs 1장) PSO도 다른 걸로 구워져(→ pso). 즉 ERHIFeatureLevel은 "이 GPU가 뭘 할 수 있냐"라는 능력 등급표인데, 그게 컴파일 시점에 셰이더 코드를 통째로 갈아끼우는 스위치로 내려가는 거야.

↳ ERHIFeatureLevel이랑 EShaderPlatform은 뭐가 달라요?

답 보기
ERHIFeatureLevel은 "능력 등급"이야 — ES3_1, SM5, SM6. "이 GPU가 컴퓨트 셰이더 되냐, 레이트레이싱 되냐" 같은 할 수 있는 일을 나타내. EShaderPlatform은 "구체적 대상"이야 — SP_PCD3D_SM6, SP_VULKAN_ES3_1_ANDROID 같은 실제 API/기기 조합이고 수십 개야. 서버로 치면 FeatureLevel은 "4코어급이냐 32코어급이냐", ShaderPlatform은 "Windows/Intel이냐 Linux/ARM이냐". 이 장에서 둘의 역할도 갈려 — 포워드 가능 여부는 FeatureLevel(>= SM5)이 정하고, framebuffer fetch 되냐 모바일이냐는 ShaderPlatform이 정해. 참고로 파일 주석이 경고하듯 이름이 API를 따서 지어졌을 뿐 API와 등급은 별개야 — D3D11에서 ES3_1 등급으로 돌 수도 있어(모바일 프리뷰).

↳ 이 장을 한 문장으로 정리하면요?

답 보기
"GBuffer라는 중간 장부는 공짜가 아니다." 디퍼드의 본질은 "물체 × 라이트"를 "물체 + 라이트"로 바꾼 것이고, GBuffer는 그 곱셈을 덧셈으로 만드는 대가로 메모리·대역폭·MSAA·재질 자유도·반투명을 지불한 거야. 라이트가 많고 VRAM이 넉넉하면 그 거래가 남는 장사고, 라이트가 적고 대역폭이 목숨이면 순손실이야. 서버로 치면 캐시나 큐 같은 중간 계층은 트래픽이 많을 때만 이득인 거랑 똑같아. 그래서 언리얼은 렌더러를 하나로 안 합쳤고, 플랫폼마다 다른 거래를 고르게 놔둔 거야.
