PrimitiveSceneProxy — 게임↔렌더 경계

언리얼 렌더링 · 13 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "UPrimitiveComponent 원본을 렌더 스레드가 직접 만지지 않고, FPrimitiveSceneProxy라는 렌더용 대리 사본을 넘기는 이유"가 잡힌다.

왜 이걸 배워? — 문제의식부터

서버를 짜봤으면 이 감각은 이미 있어. IOCP 워커가 받은 패킷을 바로 게임 객체 여기저기에 꽂지 않고, 게임 로직 스레드로 넘길 작은 메시지나 스냅샷을 만들잖아. 락 없이 원본 객체를 여러 스레드가 동시에 만지면 언젠가 터지니까.

렌더링도 똑같아. 게임 스레드에는 UPrimitiveComponent가 있어. 이건 액터 소유, 월드 소속, UObject 생명주기, 에디터 상태, 게임 로직 상태까지 품고 있는 원본이야. 반면 렌더 스레드는 매 프레임 컬링하고, 메시를 모으고, GPU 리소스를 건드려야 해. 렌더 스레드가 그때마다 UPrimitiveComponent 원본을 뒤지면 어떻게 될까? 한쪽에서는 컴포넌트 위치를 바꾸고, 다른 쪽에서는 예전 bounds로 그림자를 만들고, 또 다른 순간에는 컴포넌트가 unregister 되면서 포인터가 풀릴 수 있어. 이건 서버에서 유저 객체를 워커 스레드와 게임 스레드가 동시에 만지는 거랑 같은 사고야.

그래서 언리얼도 같은 문제를 만났고, 답이 FPrimitiveSceneProxy야. 이건 게임 객체 그 자체가 아니라 렌더 스레드가 봐도 되는 그림자 사본이야. 게임 스레드가 원본에서 렌더에 필요한 값을 뽑아 프록시를 만들고, 렌더 스레드는 그 프록시와 FPrimitiveSceneInfo만 보고 일한다. 원본 배우를 무대감독 책상에 앉히는 게 아니라, 공연용 대리 카드를 만들어 넘기는 거야.

지금 이걸 배우는 이유도 분명해. 앞 장 fscene에서 FScene이라는 렌더러 장부를 봤어. 이번 장은 그 장부에 들어가는 핵심 인물, FPrimitiveSceneProxy가 어디서 만들어지고, 어떻게 렌더 스레드로 넘어가고, 갱신과 삭제 때 어떤 안전선이 지켜지는지 보는 장이야. 다음 view-family와 frustum-culling은 이 프록시들이 모인 뒤 카메라가 무엇을 볼지 고르는 이야기로 이어진다.

0. 비유부터 — 배우 원본 대신 무대감독용 대리 카드

공연장을 떠올려봐. 배우 원본은 대기실에 있어. 의상 갈아입고, 물 마시고, 휴대폰 보고, 감독이랑 얘기하고, 공연 중에도 여러 사람이 계속 상태를 바꿔.

그런데 무대감독은 공연 중에 배우 원본 전체가 필요하지 않아. 필요한 건 딱 이런 대리 카드야.

  • 무대에 올라오는가
  • 어느 위치에 서는가
  • 어떤 의상과 소품을 쓰는가
  • 조명을 받는가
  • 그림자를 만들까
  • 무대에서 내려갈 때 어떤 자원을 치워야 하나

이 대리 카드가 FPrimitiveSceneProxy라고 보면 돼. 배우 원본이 UPrimitiveComponent라면, 프록시는 무대감독, 즉 렌더 스레드가 들고 보는 공연용 카드야.

중요한 건 카드가 원본과 같은 사람이 아니라는 점이야. 카드는 원본에서 뽑은 렌더용 정보만 담아. 그래서 무대감독은 대기실을 뒤지지 않아도 공연을 진행할 수 있고, 대기실에서 배우 상태가 바뀌어도 정해진 통로로 새 카드나 수정 메모만 받으면 된다.

이번 장의 질문은 하나야. 언리얼은 이 대리 카드를 어느 순간 만들고, 어느 순간부터 렌더 스레드 소유로 넘길까?

• 등록·갱신·해제: Engine/Source/Runtime/Renderer/Private/RendererScene.cpp
• 렌더 장부 항목: Engine/Source/Runtime/Renderer/Public/PrimitiveSceneInfo.h
🌱 이 개념은 왜 생겼나 — FPrimitiveSceneProxy
• 원래 구조: 배우 원본인 UPrimitiveComponent를 무대감독도 같이 보면 제일 쉬워. 위치, 메시, 머티리얼을 원본에서 바로 읽으면 돼.
• 그런데 문제: 공연 중 배우가 대기실에서 옷 갈아입는데 무대감독이 동시에 가방을 뒤지면 싸움 나. 위치 변경, unregister, 그림자 계산이 한 프레임 안에 겹치면 포인터도 흔들려.
• 그래서 필요한 것: 무대감독 책상에 둘 렌더용 대리 카드가 필요해. 원본 대신 필요한 값만 뽑은 Proxy, 말 그대로 대리자가 FPrimitiveSceneProxy야.

1. 프록시는 게임 스레드에서 태어난다

프리미티브가 씬에 들어올 때 시작점은 FScene::BatchAddPrimitivesInternal이야. 여기는 이름 그대로 여러 프리미티브를 한 번에 장부에 넣는 길목이지.

처음 하는 일은 원본 Primitive에서 FPrimitiveSceneProxy를 얻는 거야. 컴포넌트 인터페이스가 있으면 CreateSceneProxy()를 호출하고, 이미 만들어진 경로라면 GetSceneProxy()를 가져온다. 프록시가 없으면 렌더러 입장에서는 볼 일이 없는 물건이라 건너뛰어.

RendererScene.cpp:1402

FPrimitiveSceneProxy* PrimitiveSceneProxy = nullptr; if (Primitive->GetPrimitiveComponentInterface()) { checkf(!Primitive->GetSceneProxy(), TEXT("Primitive has already been added to the scene!")); PrimitiveSceneProxy = Primitive->GetPrimitiveComponentInterface()->CreateSceneProxy(); check(SceneData.SceneProxy == PrimitiveSceneProxy); // CreateSceneProxy has access to the shared SceneData and should set it properly } else { check(!Primitive->ShouldRecreateProxyOnUpdateTransform()); // recreating proxies when updating the transform requires a IPrimitiveComponentInterface PrimitiveSceneProxy = Primitive->GetSceneProxy(); } if(!PrimitiveSceneProxy) { // Primitives which don't have a proxy are irrelevant to the scene manager. continue; } // Create the primitive scene info. FPrimitiveSceneInfo* PrimitiveSceneInfo = new FPrimitiveSceneInfo(Primitive, this); PrimitiveSceneProxy->PrimitiveSceneInfo = PrimitiveSceneInfo; // Cache the primitives initial transform. FMatrix RenderMatrix = Primitive->GetRenderMatrix(); FVector AttachmentRootPosition = Primitive->GetActorPositionForRenderer(); FBoxSphereBounds WorldBounds = Primitive->Bounds; CheckAndSanitizePrimitiveBounds(WorldBounds, Primitive); CreateCommands.Emplace( PrimitiveSceneInfo, PrimitiveSceneProxy, // If this primitive has a simulated previous transform, ensure that the velocity data for the scene representation is correct. FMotionVectorSimulation::Get().GetPreviousTransform(ToUObject(Primitive)), RenderMatrix, WorldBounds, AttachmentRootPosition, Primitive->GetLocalBounds() );
🔤 기호 사전 — 프록시 생성과 첫 스냅샷
• FPrimitiveSceneProxy* = 렌더용 대리 카드를 가리키는 포인터야. 실물 원본 컴포넌트가 아니라 렌더용 카드 주소야.
• Primitive->GetPrimitiveComponentInterface() = 원본 프리미티브에게 "컴포넌트 인터페이스 있니?" 하고 물어보는 호출이야.
• CreateSceneProxy() = 렌더 스레드가 볼 대리 카드를 새로 만드는 함수야.
• checkf / check = 조건이 깨지면 개발 중 바로 터뜨리는 안전 검사야.
• if(!PrimitiveSceneProxy) = 대리 카드가 없으면 씬 매니저가 볼 일이 없다는 뜻이야. !는 참거짓을 뒤집어.
• new FPrimitiveSceneInfo(Primitive, this) = 렌더 장부의 한 줄을 새로 만든다. this는 지금 이 FScene이야.
• PrimitiveSceneProxy->PrimitiveSceneInfo = 대리 카드가 자기 장부 줄을 알게 연결하는 화살표야.
• FMatrix RenderMatrix = 렌더용 위치·회전·스케일 표야.
• FBoxSphereBounds = 박스와 구를 합친 빠른 범위 정보야. 컬링할 때 먼저 보는 울타리라고 생각하면 돼.
• CreateCommands.Emplace(...) = 나중에 렌더 스레드로 보낼 등록 명령 상자에 값을 바로 넣는 거야.

여기서 첫 번째 핵심이 보여. UPrimitiveComponent 원본을 그대로 렌더 스레드에 던지지 않아. 먼저 PrimitiveSceneProxy를 만들고, 그 프록시에 대응하는 PrimitiveSceneInfo를 만들고, 초기 RenderMatrix, WorldBounds, LocalBounds 같은 값도 같이 뽑아 CreateCommands에 담아.

공연장 비유로 읽으면 이렇다. 배우 원본을 무대감독에게 보내지 않고, 배우의 공연용 대리 카드와 첫 위치표를 만든 다음, "이 카드 등록해줘"라는 봉투에 넣는 거야.

🔁 이제 다시 보자. CreateSceneProxy()는 배우 원본에서 대리 카드를 만들고 → new FPrimitiveSceneInfo는 무대감독 장부 한 줄을 만들고 → PrimitiveSceneProxy->PrimitiveSceneInfo는 카드와 장부 줄을 묶고 → CreateCommands.Emplace는 렌더 스레드로 넘길 봉투를 만든다. 아까는 포인터 덩어리였는데 이제 "원본 대신 카드 만들기"로 읽히지?
🧱 먼저 알아야 할 것 — 그림 담당의 '따로 있는 준비물'
• 작업대가 따로 있다: 그림을 실제로 그리는 담당은 자기만 쓰는 작업대가 따로 있어서, 그릴 물건의 모양 데이터를 그 작업대에 미리 옮겨 갖춰둬야 그릴 수 있어. 게임 로직이 쓰는 살림과 그림 담당이 쓰는 살림은 서로 다른 칸이야.
• 갖추기와 치우기가 따로: 그래서 "이 물건 그릴 준비물 갖춰둬"와 "이제 안 쓰니 치워"를 따로 챙겨야 해. 아무 때나 원본을 다시 뒤지는 게 아니라, 준비물을 갖출 때와 치울 때가 정해져 있어.
이게 잡히면 아래 '렌더 쪽에서 준비물을 만들고 치운다' 설명이 얹힌다.

2. 경계선은 ENQUEUE_RENDER_COMMAND다

방금 만든 CreateCommands는 아직 게임 스레드 쪽 준비물이야. 렌더 스레드에서 GPU 리소스를 만들고 씬 장부에 꽂으려면 명령 큐를 타야 해. 그 경계선이 ENQUEUE_RENDER_COMMAND야.

RendererScene.cpp:1459

if (!CreateCommands.IsEmpty()) { // Must enqueue RT commands to ensure SetTransform & CreateRenderThreadResources are executed in-order. ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand)( [this, CreateCommands = MoveTemp(CreateCommands)](FRHICommandListBase& RHICmdList) { for (const FCreateCommand& Command : CreateCommands) { FScopeCycleCounter Context(Command.PrimitiveSceneProxy->GetStatId()); Command.PrimitiveSceneProxy->SetTransform(RHICmdList, Command.RenderMatrix, Command.WorldBounds, Command.LocalBounds, Command.AttachmentRootPosition); Command.PrimitiveSceneProxy->CreateRenderThreadResources(RHICmdList); AddPrimitiveSceneInfo_RenderThread(Command.PrimitiveSceneInfo, Command.PreviousTransform); }
🔤 기호 사전 — 렌더 스레드로 넘기는 문
• CreateCommands.IsEmpty() = 보낼 등록 명령이 하나도 없는지 확인해.
• ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand) = 렌더 스레드가 나중에 실행할 명령을 큐에 넣는 언리얼 매크로야.
• [this, CreateCommands = MoveTemp(CreateCommands)] = 람다가 쓸 값을 잡아가는 부분이야. MoveTemp는 봉투 내용물을 복사하지 말고 옮겨 담는 느낌이야.
• FRHICommandListBase& RHICmdList = 렌더 스레드 쪽에서 GPU 명령을 쌓을 때 쓰는 명령 리스트야. &는 참조, 즉 같은 물건을 별명으로 받는다는 뜻이야.
• FScopeCycleCounter = 이 구간 시간이 얼마나 걸리는지 재는 계측 도구야.
• SetTransform(...) = 대리 카드에 렌더용 위치와 bounds를 박는 호출이야.
• CreateRenderThreadResources(...) = 렌더 스레드에서 필요한 GPU/렌더 리소스를 만드는 호출이야.
• AddPrimitiveSceneInfo_RenderThread(...) = 장부 줄을 렌더 스레드의 씬 업데이트 큐에 추가하는 호출이야.

주석이 아주 노골적이야. SetTransform과 CreateRenderThreadResources가 순서대로 실행되도록 RT 명령을 큐에 넣어야 한다고 말하지. 여기서 RT는 Render Thread야.

이 한 토막이 게임↔렌더 경계의 정체야. 게임 스레드는 대리 카드와 첫 위치표를 만든다. 렌더 스레드는 그 카드에 transform을 세팅하고, 렌더 스레드 리소스를 만들고, FScene 장부에 등록한다.

서버로 치면 IOCP 워커가 패킷 바이트를 직접 플레이어 객체에 꽂지 않고, 게임 스레드 큐에 CM_MOVE 같은 명령을 넣는 것과 비슷해. 큐를 타는 순간 소유권과 실행 스레드가 바뀐다.

🔁 이제 다시 보자. ENQUEUE_RENDER_COMMAND는 무대감독 책상으로 가는 전달함이고 → 람다는 전달함 안의 작업지시서고 → SetTransform은 대리 카드에 위치를 쓰고 → CreateRenderThreadResources는 무대용 장비를 준비하고 → AddPrimitiveSceneInfo_RenderThread는 장부에 꽂는다. 프록시는 이 지점부터 렌더 쪽 세계의 물건으로 굴러간다.
🌱 이 개념은 왜 생겼나 — 원본 역참조 금지
• 원래 구조: 프록시에 원본 포인터가 있으면 "필요할 때 따라가서 읽자"가 쉬워 보여. 대기실 문을 열면 배우 정보가 다 있잖아.
• 그런데 문제: 게임 스레드가 UObject 멤버를 바꾸는 바로 그 순간 렌더 스레드가 읽으면, 두 사람이 같은 서랍을 동시에 잡아당기는 꼴이야.
• 그래서 필요한 것: 렌더 스레드는 원본 문을 열지 않고 카드와 ID만 봐야 해. 그래서 ForDebuggingOnly, PrimitiveComponentId 같은 안전 표지판이 붙어 있어.

3. 렌더 스레드는 원본 컴포넌트를 뒤지면 안 된다

여기서 제일 중요한 안전선이 나온다. FPrimitiveSceneInfo 안에는 디버깅용으로 컴포넌트 인터페이스 포인터가 있긴 해. 하지만 렌더 스레드에서 그걸 역참조하지 말라고 소스 주석이 못을 박아놨다.

PrimitiveSceneInfo.h:588

/** * The IPrimitiveComponentInterface this scene info is for, useful for quickly inspecting properties on the corresponding component while debugging. * This should not be dereferenced on the rendering thread. The game thread can be modifying UObject members at any time. * Use PrimitiveComponentId instead when a component identifier is needed. * */ IPrimitiveComponent* PrimitiveComponentInterfaceForDebuggingOnly; /** * Ptr to the FPrimitiveSceneInfoData for this prim, this is used for shared data between the primitive and the component that created the primitive. */ FPrimitiveSceneInfoData* SceneData;
🔤 기호 사전 — 원본을 건드리지 말라는 경고
• /** ... */ = 여러 줄짜리 주석이야. 실행은 안 되지만 개발자에게 규칙을 알려줘.
• IPrimitiveComponentInterface* = 원본 컴포넌트 쪽 인터페이스를 가리키는 포인터야.
• ForDebuggingOnly = 이름 그대로 디버깅용이라는 경고표지야.
• should not be dereferenced = 포인터가 가리키는 원본을 따라 들어가서 읽지 말라는 뜻이야.
• rendering thread = 렌더 스레드야. 게임 스레드와 따로 돈다.
• UObject members = 게임 객체 안의 멤버들이야. 게임 스레드가 언제든 바꿀 수 있어.
• PrimitiveComponentId = 포인터 대신 쓰는 안정적인 식별자야. 주민번호처럼 "누구인지"만 나타낸다.
• FPrimitiveSceneInfoData* SceneData = 프리미티브와 만든 쪽이 공유하는 별도 데이터 손잡이야.

이 주석은 이 장의 중심 문장이야. "렌더 스레드에서 컴포넌트 포인터를 따라가지 마라. 게임 스레드가 언제든 UObject 멤버를 바꿀 수 있다."

그러니까 프록시는 성능 최적화만이 아니야. 스레드 안전을 위한 경계선이야. 렌더 스레드가 원본 배우 대기실을 마음대로 열고 들어가면 안 된다. 무대감독은 자기 책상 위의 대리 카드와 장부 번호만 봐야 한다.

🔁 이제 다시 보자. PrimitiveComponentInterfaceForDebuggingOnly는 "원본 배우로 가는 문"처럼 보이지만 → 주석은 렌더 스레드에서 그 문을 열지 말라고 해 → 대신 PrimitiveComponentId 같은 식별자를 쓰라고 한다. 그래서 프록시가 필요한 이유가 "편해서"가 아니라 "원본을 동시에 만지면 위험해서"라는 게 보인다.
🌱 이 개념은 왜 생겼나 — 수정 메모(UpdateParams)
• 원래 구조: 배우가 움직일 때마다 무대감독이 대기실 원본을 다시 읽으면 간단해 보여. "지금 어디야?" 하고 매번 물어보는 거지.
• 그런데 문제: 한 프레임에 컴포넌트 1,000개가 움직이면 원본 뒤지기가 1,000번 생겨. 그 사이 게임 스레드는 또 위치를 바꿀 수 있어.
• 그래서 필요한 것: 새 위치, bounds, 이전 transform만 적은 수정 메모가 필요해. 그 봉투가 UpdateParams고, 렌더 스레드는 메모만 보고 대리 카드를 고쳐.

4. 위치가 바뀌면 원본을 다시 뒤지지 않고 수정 메모를 보낸다

배우가 무대 위에서 이동하면 어떻게 할까? 무대감독이 대기실까지 뛰어가서 배우 원본을 다시 훑으면 안 돼. 게임 스레드가 새 위치표를 만들어 렌더 스레드에 수정 메모를 보내야 해.

UpdatePrimitiveTransformInternal이 그 길목이야. 이미 프록시가 있으면 새 bounds, 새 render matrix, attachment root, previous transform을 UpdateParams에 담는다. 그 다음 렌더 명령으로 넘겨서 렌더 스레드가 프록시를 갱신하게 한다.

🔤 기호 사전 — transform 수정 메모
• bNeedsTransformCommand = 렌더 스레드에 transform 갱신 명령을 따로 보내야 하는지 나타내는 참거짓 값이야.
• UpdateTransformCommand = 위치 수정용 렌더 명령 이름이야.
• [UpdateParams] = 위치 수정에 필요한 값을 람다 안으로 복사해 들고 간다는 뜻이야.
• UpdateParams.PrimitiveSceneProxy = 갱신할 대리 카드야. 원본 컴포넌트가 아니라 프록시다.
• WorldBounds / LocalBounds = 월드 기준 울타리와 로컬 기준 울타리야.
• LocalToWorld = 로컬 좌표를 월드 좌표로 바꾸는 행렬이야.
• AttachmentRootPosition = 붙어 있는 루트의 위치야. 조명이나 attachment 계산에 필요해.
• PreviousTransform = 이전 transform이야. 모션 벡터 같은 "얼마나 움직였나" 계산에 쓰인다.

여기서 다시 원칙이 보여. 갱신 명령은 PrimitiveSceneProxy와 숫자 데이터만 들고 간다. 렌더 스레드가 UPrimitiveComponent 원본을 다시 열어보지 않아도 되게, 게임 스레드가 필요한 값을 UpdateParams에 싸서 보낸다.

서버로 치면 CPlayer 포인터를 워커에게 넘기는 게 아니라, { playerId, x, y, dir, tick } 같은 작은 갱신 메시지를 큐에 넣는 거야. 워커나 렌더 쪽은 그 메시지를 보고 자기 쪽 상태만 바꾼다.

🌱 이 개념은 왜 생겼나 — 두 단계 삭제
• 원래 구조: 배우가 나가면 원본, 대리 카드, 조명 장비를 그 자리에서 한 번에 지우면 쉬워 보여.
• 그런데 문제: 무대감독이 아직 그 카드로 그림자나 리소스를 정리 중인데 게임 쪽이 바로 free하면, 워커가 쓰는 세션 버퍼를 먼저 해제한 사고랑 같아.
• 그래서 필요한 것: 게임 스레드는 연결만 끊고, 렌더 스레드는 자기 장부와 장비를 자기 줄에서 치워야 해. 그래서 삭제도 회수 명령과 철거 명령으로 나뉘어.

5. 삭제도 두 단계다

등록과 갱신만 경계가 있는 게 아니야. 삭제도 똑같이 조심스럽게 나뉜다.

게임 스레드 쪽에서는 먼저 원본 프리미티브에서 씬 프록시 연결을 끊어. 그 다음 렌더 스레드 명령으로 장부 줄 제거와 렌더 리소스 파괴를 보낸다. 즉 "배우 카드 회수"와 "무대 장비 철거"가 같은 스레드에서 막 섞이지 않는다.

• Primitive->GetSceneProxy() = 원본 프리미티브에 붙어 있는 대리 카드를 가져온다.
• FSimpleStreamableAssetManager::Unregister(...) = 스트리밍 관리에서 이 프록시를 빼는 호출이야.
• PrimitiveSceneProxy->GetPrimitiveSceneInfo() = 대리 카드가 연결된 장부 줄을 꺼낸다.
• Primitive->ReleaseSceneProxy() = 원본 프리미티브와 대리 카드의 연결을 끊는다.
• DestroyCommands.Add(...) = 렌더 스레드에서 처리할 철거 명령을 모은다.
• FRemovePrimitiveCommand = 프리미티브 제거용 렌더 명령이야.
• RemovePrimitiveSceneInfo_RenderThread(...) = 렌더 스레드 장부에서 프리미티브 줄을 제거 큐에 넣는다.
• DestroyRenderThreadResources() = 렌더 스레드에서 만든 리소스를 파괴한다.
• AttachmentCounter->Decrement() = scene에 붙어 있는 카운터를 하나 줄인다.

삭제에서도 같은 패턴이 반복돼. 게임 스레드는 원본에서 프록시 연결을 끊고, 렌더 스레드는 자기 장부와 자기 리소스를 정리한다. 원본 컴포넌트를 렌더 스레드가 붙잡고 있다가 직접 지우는 모양이 아니야.

공연장으로 보면, 배우가 퇴장하면 대기실 쪽에서는 "이 배우 카드는 이제 회수됨"이라고 표시하고, 무대감독 쪽에서는 조명 큐, 소품, 장부 줄을 순서대로 치운다. 퇴장 중에 대기실 문을 열고 배우 상태를 다시 캐묻지 않는다.

🔁 이제 다시 보자. GetSceneProxy()로 회수할 대리 카드를 찾고 → ReleaseSceneProxy()로 원본과 카드 연결을 끊고 → DestroyCommands에 철거 봉투를 넣고 → 렌더 명령 안에서 RemovePrimitiveSceneInfo_RenderThread와 DestroyRenderThreadResources를 실행한다. 태어날 때도 큐, 죽을 때도 큐야.

6. 전체 흐름 한눈에

프록시의 삶을 한 줄로 그리면 이거야.

여기서 세 단어만 외우면 돼.

  • Proxy = 렌더 스레드가 보는 대리 카드
  • SceneInfo = FScene 장부의 한 줄
  • ENQUEUE = 게임 스레드에서 렌더 스레드로 넘어가는 전달함

FScene은 배우 원본을 들고 있지 않아. 무대감독 장부에는 대리 카드와 카드 번호, 위치표, bounds, 리소스 상태가 들어간다. 이게 앞 장 fscene에서 봤던 프리미티브 packed array와 이어지는 지점이야.

7. 우리 서버·DirectX랑 비교

게임 서버 기준으로 보면 FPrimitiveSceneProxy는 송신용 DTO에 가깝다. 원본 CPlayer 객체에는 퀘스트, 인벤토리, DB dirty flag, AI 상태까지 많아. 하지만 클라에 보낼 이동 패킷에는 id, pos, rot, state만 뽑아 담지. 그 패킷을 IOCP 워커가 들고 있어도 원본 CPlayer를 직접 만지지 않아도 돼.

UPrimitiveComponent와 FPrimitiveSceneProxy도 비슷해. 컴포넌트 원본에는 UObject 생명주기와 게임 상태가 있고, 프록시에는 렌더링에 필요한 상태가 있다. 렌더 스레드는 프록시를 보고 메시, 머티리얼, transform, bounds, visibility를 판단한다.

DirectX 경험으로 보면 더 직관적이야. 게임 로직의 TransformComponent를 GPU가 직접 읽지 않잖아. CPU가 월드 행렬을 상수 버퍼나 인스턴스 버퍼에 복사해서 올리고, GPU는 그 렌더용 복사본을 읽어. 프록시는 그 CPU 렌더러 버전의 복사본이라고 보면 된다.

차이도 있어. 단순 DirectX 샘플에서는 네가 한 스레드에서 전부 처리할 수 있어. 그러면 원본 구조체를 바로 읽어도 큰 문제가 안 보일 수 있지. 하지만 UE는 게임 스레드와 렌더 스레드가 파이프라인처럼 겹쳐 돈다. 그래서 "원본 바로 읽기"가 아니라 "프록시와 렌더 명령으로 넘기기"가 기본 구조가 된다.

서버에서 락을 잔뜩 걸고 원본 객체를 공유하면 일단 돌아갈 수는 있어. 하지만 성능과 복잡도가 망가지지. 언리얼 렌더러도 같은 선택을 피해 간다. 락으로 원본을 공유하는 대신, 프록시와 명령 큐로 소유권 경계를 만든다.

8. 이 챕터에서 딱 이것만

  • FPrimitiveSceneProxy는 UPrimitiveComponent 원본이 아니라 렌더 스레드용 대리 카드야.
  • 등록 때 게임 스레드는 CreateSceneProxy()로 프록시를 만들고 FPrimitiveSceneInfo와 묶는다.
  • 렌더 스레드로 넘어가는 문은 ENQUEUE_RENDER_COMMAND야.
  • 렌더 스레드는 원본 컴포넌트 포인터를 역참조하면 안 된다. 소스 주석이 직접 경고한다.
  • 위치 변경과 삭제도 원본 직접 접근이 아니라 수정/철거 명령으로 전달된다.

Q1. FPrimitiveSceneProxy는 왜 있나요? 렌더 스레드가 그냥 UPrimitiveComponent를 읽으면 안 되나요?

답 보기
UPrimitiveComponent는 액터 소유, UObject 생명주기, 에디터 상태, 게임 로직까지 품은 원본이야. 근데 렌더 스레드는 매 프레임 컬링하고, 메시 모으고, GPU 리소스를 건드려. 렌더 스레드가 그때마다 원본을 뒤지면, 게임 스레드가 위치를 바꾸는 순간 예전 bounds로 그림자를 만들거나, unregister 되면서 포인터가 풀릴 수 있어. FPrimitiveSceneProxy는 렌더 스레드가 봐도 되는 그림자 사본이야 — 원본에서 렌더에 필요한 값만 뽑은 대리 카드. 원본 배우를 무대감독 책상에 앉히는 대신, 공연용 대리 카드를 넘기는 거지.

↳ 그거 성능 최적화 아니에요? 그냥 복사본 두는 거잖아요.

답 보기
최적화도 되지만 본질은 스레드 안전 경계야. 실제로 FPrimitiveSceneInfo 안엔 디버깅용 컴포넌트 포인터(...ForDebuggingOnly)가 있긴 한데, 소스 주석이 "렌더 스레드에서 이걸 역참조하지 마라, 게임 스레드가 언제든 UObject 멤버를 바꾼다"라고 못을 박아놨어. 그래서 컴포넌트를 가리킬 땐 포인터 대신 PrimitiveComponentId 같은 안정적 식별자를 써. 두 사람이 같은 서랍을 동시에 잡아당기는 걸 막는 게 프록시의 진짜 존재 이유야.

↳ 우리 서버로 치면 뭐랑 같나요?

답 보기
송신용 DTO야. 원본 CPlayer엔 퀘스트, 인벤토리, DB dirty flag, AI 상태까지 많지만, 클라에 보낼 이동 패킷엔 id, pos, rot, state만 뽑아 담잖아. 그 패킷을 워커가 들고 있어도 원본 CPlayer를 직접 안 만져. 프록시도 컴포넌트에서 렌더링에 필요한 값(메시, 머티리얼, transform, bounds)만 뽑은 렌더 스레드용 사본이야.

Q2. 게임 스레드에서 만든 프록시가 어느 순간부터 렌더 스레드 소유가 되나요?

답 보기
경계선이 정확히 ENQUEUE_RENDER_COMMAND야. 게임 스레드는 CreateSceneProxy()로 대리 카드를 만들고 첫 위치표(RenderMatrix, WorldBounds)를 뽑아서 봉투(CreateCommands)에 담기까지만 해. 그 봉투가 ENQUEUE_RENDER_COMMAND라는 전달함을 타는 순간부터, 렌더 스레드가 SetTransform으로 위치 박고, CreateRenderThreadResources로 GPU 리소스 만들고, FScene 장부에 꽂아. 큐를 타는 순간 소유권과 실행 스레드가 바뀐다는 게 핵심이야.

↳ 서버에서 비슷한 경계가 있나요?

답 보기
IOCP 워커가 패킷 바이트를 직접 플레이어 객체에 꽂지 않고, 게임 스레드 큐에 CM_MOVE 같은 명령을 넣는 거랑 같아. 큐에 넣기 전엔 워커 소유, 큐를 타면 게임 스레드 소유로 넘어가지. 소유권 경계를 락이 아니라 명령 큐로 긋는다는 발상이 똑같아.

Q3. 프리미티브 위치가 매 프레임 바뀌면 렌더 스레드가 원본을 다시 읽나요?

답 보기
아니, 그러면 안 돼. 무대감독이 배우 이동할 때마다 대기실까지 뛰어가 원본을 훑으면, 한 프레임에 컴포넌트 1,000개가 움직이면 원본 뒤지기가 1,000번 생기고 그 사이 게임 스레드가 또 위치를 바꿔. 대신 게임 스레드가 새 bounds·render matrix·이전 transform만 UpdateParams라는 수정 메모에 담아서 렌더 명령으로 보내. 렌더 스레드는 그 메모만 보고 프록시를 고쳐. 서버로 치면 CPlayer 포인터를 넘기는 게 아니라 { id, x, y, dir, tick } 작은 갱신 메시지를 큐에 넣는 거야.

↳ 삭제할 때도 같은 원칙인가요?

답 보기
응, 삭제도 두 단계야. 게임 스레드는 원본에서 프록시 연결만 끊어(ReleaseSceneProxy). 그다음 렌더 명령으로 장부 줄 제거(RemovePrimitiveSceneInfo_RenderThread)랑 렌더 리소스 파괴(DestroyRenderThreadResources)를 보내. "배우 카드 회수"랑 "무대 장비 철거"를 같은 스레드에서 막 섞지 않는 거지. 무대감독이 아직 그 카드로 그림자를 정리 중인데 게임 쪽이 바로 free하면, 워커가 쓰는 세션 버퍼를 먼저 해제한 사고랑 같으니까.

Q4. 그럼 프록시 하나 요약하면 뭐라고 설명하나요? 태어나서 죽을 때까지.

답 보기
세 단어면 돼. Proxy(렌더 스레드가 보는 대리 카드), SceneInfo(FScene 장부의 한 줄), ENQUEUE(게임→렌더 넘어가는 전달함). 태어날 때 CreateSceneProxy()로 카드 만들어 큐로 넘기고, 움직이면 수정 메모를 큐로 보내고, 죽을 때 연결 끊고 철거 명령을 큐로 보내. 태어날 때도 큐, 죽을 때도 큐야. 원본 UObject랑 렌더 장부 사이에 명령 큐로 스레드 안전 경계를 긋는 게 전부야.

↳ 단순 DirectX 샘플에선 이런 게 없잖아요. 왜 UE만 이렇게 복잡한가요?

답 보기
단순 DX 샘플은 한 스레드에서 다 처리하니까 원본 구조체를 바로 읽어도 문제가 안 보여. 근데 그때도 GPU가 TransformComponent를 직접 읽진 않아 — CPU가 월드 행렬을 상수/인스턴스 버퍼에 복사해 올리고 GPU는 그 복사본을 읽지. 프록시가 딱 그 CPU 렌더러 버전 복사본이야. UE는 게임 스레드랑 렌더 스레드가 파이프라인처럼 겹쳐 도니까, "원본 바로 읽기"가 아니라 "프록시+렌더 명령으로 넘기기"가 기본 구조가 될 수밖에 없어. 락으로 원본 공유하면 돌긴 하지만 성능·복잡도가 망가지거든.

🎯 원리 한 줄 요약

FPrimitiveSceneProxy는 게임 객체 원본을 렌더 스레드에 공유하지 않기 위한 "렌더용 대리 카드"다 — 생성, 갱신, 삭제 모두 명령 큐를 타고 넘어가며 원본 UObject와 렌더 장부 사이의 스레드 안전 경계를 만든다.

막히면(선행 개념) → fscene · render-thread
다음(카메라가 이 프록시들을 어떻게 보나) → view-family
← 이전FScene — 렌더러가 보는 세계다음 →View / ViewFamily - 카메라 한 대의 모든 것
