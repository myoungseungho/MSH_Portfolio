Nanite — 삼각형 수 제한을 깨다

언리얼 렌더링 · 28 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "Nanite가 삼각형을 몽땅 CPU로 보내서 그리는 기술이 아니라, 클러스터 후보를 GPU에서 고르고 작은 조각만 래스터라이즈하는 흐름"이라는 큰 그림이 잡힌다.
🧱 먼저 알아야 할 것 — 물체는 삼각형 껍데기, 그걸 화면 칸에 칠하기
• 3D 물체 = 삼각형 덩어리: 게임 속 바위나 사람은 속이 꽉 찬 게 아니라, 수천~수백만 개의 작은 삼각형을 이어 붙여 만든 껍데기야. 삼각형이 많을수록 매끈하고, 적으면 각져 보여.
• 화면에 칠하기(래스터화): 그 삼각형 하나하나를, 화면을 잘게 나눈 작은 네모칸(픽셀)들 중 어느 칸을 덮는지 따져서 그 칸에 색을 써넣는 일이야. 삼각형이 많으면 이 칠하기 일도 그만큼 늘어나.
이게 잡히면 "삼각형 수가 터진다"는 아래 이야기가 얹힌다.

왜 이걸 배워? — 문제의식부터

1. 네가 아는 것에서 출발하자. 서버에서 유저 1만 명이 접속했는데, 매 틱마다 모든 유저의 모든 아이템, 모든 몬스터, 모든 로그를 처음부터 끝까지 훑으면 서버가 버티겠어? 당연히 안 버틴다. 그래서 우리는 공간 분할, 관심 영역, 더티 플래그, 큐, 배치 같은 걸 써. "지금 필요한 것만" 고르는 장치가 있어야 해.

2. 렌더링도 똑같이 터진다. 영화급 메시 하나가 수천만 삼각형을 들고 오면, 전통 파이프라인처럼 CPU가 메시 섹션을 나누고, 드로우콜을 쌓고, 정점 셰이더가 삼각형을 다 밀어 넣는 방식으로는 금방 벽에 닿아. 화면에 쌀알보다 작게 보이는 삼각형까지 똑같은 손님처럼 줄 세우면, GPU도 "이걸 왜 다 세지?"가 된다.

3. 그래서 필요한 통이 Nanite다. Nanite는 "모든 삼각형을 그대로 그리자"가 아니야. 원본 메시를 작은 클러스터 묶음으로 쪼개 두고, 화면에서 필요한 LOD 조각만 고른 뒤, 그 조각을 GPU 쪽 큐와 버퍼로 흘려보내. 서버로 치면 모든 유저를 매번 풀스캔하지 않고, 지금 AOI에 걸린 엔티티 묶음만 워커 큐에 올리는 느낌이야.

4. 지금 여기서 배울 위치. 앞에서 우리는 GPU와 CPU의 역할 cpu-vs-gpu, RDG 패스 rdg, 드로우 명령 mesh-draw-command, 셰이더 퍼뮤테이션 shader-permutation을 봤어. Nanite는 그걸 한꺼번에 써먹는 장이야. 이번엔 큰 그림만 잡고, 다음 장 nanite-cull-raster에서 컬링/래스터 세부를 더 파고들 거야.

0. 비유부터 — 놀이공원 줄을 삼각형 줄로 바꿔 보자

놀이공원에 손님이 천만 명 왔다고 하자.

입구 직원이 손님 한 명 한 명을 전부 불러서 "너는 바이킹, 너는 회전목마, 너는 매점" 하고 분류하면 하루가 끝나.

그래서 진짜 운영은 이렇게 해야 해.

  1. 손님을 가족/단체 같은 묶음으로 본다.
  2. 멀리 있는 단체는 대충 큰 표지판만 보고 보낸다.
  3. 가까이 온 단체만 자세히 쪼갠다.
  4. 키 작은 애들은 작은 놀이기구 줄로, 키 큰 애들은 큰 놀이기구 줄로 보낸다.
  5. 매번 직원이 다 판단하지 않고, 자동 게이트가 사람을 세고 보낸다.

Nanite의 클러스터가 바로 그 "단체"야.

LOD는 "멀리 있으면 큰 묶음으로 충분하고, 가까우면 더 잘게 보자"는 규칙이야.

GPU 주도는 "입구 직원(CPU)이 모든 손님을 한 명씩 판정하지 말고, 자동 게이트(GPU)가 직접 후보를 세고 줄을 나누자"는 뜻이야.

🌱 이 개념은 왜 생겼나 — 클러스터 LOD
• 원래 구조: 메시 하나에 LOD0, LOD1, LOD2 같은 큰 단체 표를 몇 장 만들어 두고, CPU가 거리 보고 하나 골라.
• 그런데 문제: 천만 손님 놀이공원에서 멀리 보이는 단체까지 한 명씩 자세히 세우면 입구가 터져. 화면에 쌀알만 한 바위도 큰 덩어리로 처리하면 너무 낭비야.
• 그래서 필요한 것: 메시를 작은 클러스터 단체로 쪼개고, 화면 크기와 오차로 지금 필요한 단계만 고르는 규칙이 필요해. 그게 클러스터 LOD야.
🧱 먼저 알아야 할 것 — 멀면 대충, 가까우면 자세히(LOD)
• 거리에 따라 정성을 다르게: 멀리 있는 물건은 눈에 작게 보이니 대충 만들어도 티가 안 나고, 가까이 오면 자세히 보여야 해. 종이지도를 축소하면 골목은 사라지고 큰길만 남듯, 멀수록 덜어내는 게 이득이야.
• LOD: 그래서 같은 물체를 "자세한 판 / 적당한 판 / 대충한 판"으로 여러 개 두고, 지금 거리에 맞는 걸 고르는 걸 LOD(자세함 단계)라고 불러.
이게 잡히면 아래 화면 크기로 단계를 고르는 계산이 얹힌다.

1. LOD는 감이 아니라 화면 크기 계산이야

Nanite의 LOD를 "가까우면 고해상도, 멀면 저해상도"라고 말하면 맞긴 한데 너무 흐릿해.

실제 셰이더는 노드/클러스터의 경계 구를 화면에 투영해서, 지금 더 내려가야 하는지 아니면 이 클러스터를 그려도 되는지 계산한다.

아래는 NaniteClusterCulling.usf 안의 핵심 판정이야.

NaniteClusterCulling.usf:281

bool ShouldVisitChildInternal( FNaniteView NaniteView, FInstanceSceneData InstanceData, FInstanceDynamicData DynamicData, FNodeCullingBounds Bounds, FHierarchyNodeSlice HierarchyNodeSlice, inout float Priority ) { float2 ProjectedEdgeScales = GetProjectedEdgeScales(NaniteView, InstanceData, DynamicData, Bounds.Sphere); float UniformScale = Bounds.MeshMinDeformScale * min3( InstanceData.NonUniformScale.x, InstanceData.NonUniformScale.y, InstanceData.NonUniformScale.z ); float Threshold = NaniteView.LODScale * UniformScale * HierarchyNodeSlice.MaxParentLODError; if( ProjectedEdgeScales.x <= Threshold ) { Priority = Threshold / ProjectedEdgeScales.x; // TODO: Experiment with better priority bool bSkipMinLODCulling = false; #if DEBUG_FLAGS bSkipMinLODCulling |= (DebugFlags & (NANITE_DEBUG_FLAG_DISABLE_CULL_MIN_LOD | NANITE_DEBUG_FLAG_DRAW_ONLY_ROOT_DATA)) != 0u; #endif return bSkipMinLODCulling || !HierarchyNodeSlice.bLeaf || (ProjectedEdgeScales.y >= NaniteView.LODScale * UniformScale * HierarchyNodeSlice.MinLODError); } else { return false; } } bool SmallEnoughToDraw( FNaniteView NaniteView, FInstanceSceneData InstanceData, FInstanceDynamicData DynamicData, FNodeCullingBounds Bounds, float LODError, float EdgeLength, inout bool bUseHWRaster ) { float ProjectedEdgeScale = GetProjectedEdgeScales( NaniteView, InstanceData, DynamicData, Bounds.Sphere ).x; float UniformScale = Bounds.MeshMinDeformScale * min3( InstanceData.NonUniformScale.x, InstanceData.NonUniformScale.y, InstanceData.NonUniformScale.z ); bool bVisible = ProjectedEdgeScale > UniformScale * LODError * NaniteView.LODScale; if (RenderFlags & NANITE_RENDER_FLAG_FORCE_HW_RASTER) { bUseHWRaster = true; } else { float HWEdgeScale = InstanceData.NonUniformScale.w * Bounds.NodeMaxDeformScale; bUseHWRaster |= ProjectedEdgeScale < HWEdgeScale * abs( EdgeLength ) * NaniteView.LODScaleHW; // TODO: EdgeLength shouldn't have sign } return bVisible; }
🔤 기호 사전 — LOD 판정
• ProjectedEdgeScales = 이 묶음이 화면에서 얼마나 크게 보이는지 재는 자.
• LODScale = "얼마나 빡세게 쪼갤까"를 조절하는 배율.
• MaxParentLODError / MinLODError = 부모 묶음과 자식 묶음의 허용 오차. 오차가 크면 더 내려가야 해.
• ShouldVisitChildInternal = "자식 노드로 더 들어갈까?"를 묻는 문.
• SmallEnoughToDraw = "이 클러스터는 이제 그려도 될 만큼 작나?"를 묻는 문.
• bUseHWRaster = 하드웨어 래스터 길로 보낼지 표시하는 깃발.
🔁 이제 다시 보자. ShouldVisitChildInternal은 놀이공원 단체를 더 쪼갤지 보는 단계야. SmallEnoughToDraw는 "이 단체는 이제 줄에 세워도 된다"를 결정하는 단계고. Nanite의 LOD는 감으로 바뀌는 게 아니라, 화면 크기와 오차 기준을 놓고 GPU 셰이더가 직접 판단한다.

여기서 중요한 건 CPU가 "이 메시의 3번 LOD를 그려" 하고 딱 정해 주는 그림이 아니라는 거야.

GPU 안에서 노드와 클러스터를 보며 더 내려갈지, 멈출지, 그릴지를 판단한다.

기존 StaticMesh LOD처럼 메시 단위로 큰 덩어리 하나를 고르는 방식과 감각이 달라.

Nanite는 훨씬 작은 클러스터 단위로 "이번 화면에 필요한 컷"을 만든다.

🌱 이 개념은 왜 생겼나 — SW/HW 래스터 경로
• 원래 구조: 삼각형은 전부 GPU의 하드웨어 래스터라이저 한 줄로 보내면 돼. 큰 놀이기구 줄 하나만 있는 셈이야.
• 그런데 문제: 픽셀보다 작은 삼각형이 모래알처럼 쏟아지면, 그 큰 줄에 전부 태우는 준비가 더 부담돼.
• 그래서 필요한 것: 큰 삼각형은 하드웨어 길로, 작은 삼각형은 compute 셰이더 길로 나눠 보내야 해. 그래서 SW/HW 래스터 경로가 필요해.
🧱 먼저 알아야 할 것 — GPU에게 시키는 자유 계산 프로그램(컴퓨트 셰이더)
• 정해진 조립 라인 vs 자유 계산: GPU에는 원래 "삼각형을 픽셀로 칠하는" 전용 조립 라인이 붙어 있어. 빠르지만 하는 일이 정해져 있지.
• 컴퓨트 셰이더: 그 전용 라인 말고, GPU의 수천 일꾼에게 "이 숫자들을 가져다 이렇게 계산해서 여기다 써라"라고 자유롭게 시키는 프로그램이야. 조립 라인이 안 맞는 일은 이 자유 계산으로 대신 처리할 수 있어.
이게 잡히면 "작은 삼각형은 컴퓨트로 칠한다"는 아래 갈림길이 얹힌다.

2. 왜 하드웨어 래스터만으로는 부족해?

기존 파이프라인은 대충 이래.

CPU가 드로우콜을 만들고, GPU 고정 기능 래스터라이저가 삼각형을 화면 픽셀로 바꾼다.

큰 삼각형이 많을 땐 이 길이 아주 좋다.

문제는 Nanite가 상대하는 삼각형이 너무 작다는 거야.

픽셀보다 작은 삼각형이 산더미처럼 있으면, 고정 기능 래스터만 믿고 전부 밀어 넣는 게 항상 최선이 아니게 된다.

그래서 코드에 아예 래스터 스케줄링 모드가 있다.

NaniteCullRaster.h:25

enum class ERasterScheduling : uint8 { // Only rasterize using fixed function hardware. HardwareOnly = 0, // Rasterize large triangles with hardware, small triangles with software (compute). HardwareThenSoftware = 1, // Rasterize large triangles with hardware, overlapped with rasterizing small triangles with software (compute). HardwareAndSoftwareOverlap = 2, };
🔤 기호 사전 — 래스터 길 나누기
• enum class = 정해진 선택지 상자. 여기서는 래스터 방식 3개만 고를 수 있어.
• HardwareOnly = 고정 기능 하드웨어 래스터만 쓴다.
• HardwareThenSoftware = 큰 삼각형은 하드웨어, 작은 삼각형은 compute 소프트웨어 길로 보낸다.
• HardwareAndSoftwareOverlap = 두 길을 겹쳐서 돌린다. 한 줄 끝나고 다음 줄이 아니라 동시에 밀어붙이는 느낌.
• uint8 = 아주 작은 정수 타입. 선택지 번호를 작게 저장한다.
🔁 이제 다시 보자. 여기서 "software"는 CPU 소프트웨어가 아니야. compute shader로 도는 GPU 쪽 소프트웨어 래스터야. 그러니까 Nanite는 GPU 안에서도 고정 기능 길과 compute 길을 나눠서 쓴다. 큰 차는 고속도로, 킥보드는 골목길로 보내는 식이야.

이 줄 하나만 봐도 "Nanite = 그냥 삼각형을 많이 넣는 기술"이 아니라는 게 보인다.

삼각형이 작아질수록 파이프라인의 병목 모양이 바뀌니까, 래스터 경로 자체를 나눈다.

🌱 이 개념은 왜 생겼나 — GPU 작업판
• 원래 구조: CPU가 "이 클러스터 그려, 저 클러스터 버려"를 전부 정해서 GPU에 목록을 넘겨.
• 그런데 문제: 후보가 산더미가 되면 입구 직원 혼자 손님 이름표를 다 쓰는 꼴이야. 자동 게이트는 빠른데, 게이트 앞 종이가 늦게 와서 놀게 돼.
• 그래서 필요한 것: GPU가 직접 후보 큐를 읽고, 새 후보와 visible 결과를 써 넣을 작업판이 필요해. CandidateNodes, CandidateClusters, OutVisibleClustersSWHW가 그런 판이야.

3. CPU가 넘기는 건 삼각형 목록이 아니라 작업판이야

Nanite C++ 쪽은 GPU 셰이더가 일할 버퍼를 준비한다.

중요한 이름은 CandidateNodes, CandidateClusters, OutVisibleClustersSWHW야.

서버식으로 말하면, 아직 판정 중인 후보 큐와 최종 처리 큐가 따로 있는 셈이야.

🔤 기호 사전 — GPU 작업판
• SRV = 읽기용 창구. 셰이더가 ClusterPageData, HierarchyBuffer를 읽는다.
• UAV = 읽고 쓰는 창구. 셰이더가 후보와 결과를 직접 써 넣는다.
• CandidateNodes = 아직 더 내려가 봐야 할 계층 노드 후보.
• CandidateClusters = 그릴지 말지 판정할 클러스터 후보.
• OutVisibleClustersSWHW = 최종으로 보이는 클러스터 목록. SW/HW 두 길이 같이 들어간다.
• OutStreamingRequests = 필요한 클러스터 페이지가 없으면 스트리밍 요청도 남긴다.
🔁 이제 다시 보자. CPU가 "삼각형 1번부터 1억 번까지 그려"라고 보내는 게 아니야. CPU는 ClusterPageData와 HierarchyBuffer 같은 재료, 그리고 CandidateNodes 같은 작업 큐를 GPU에 넘긴다. 그 뒤 후보를 늘리고 줄이고 최종 visible 목록을 쓰는 건 GPU 쪽 일이다.

여기서 HierarchyBuffer가 핵심이야.

Nanite 메시가 그냥 납작한 삼각형 배열이면 GPU가 똑똑하게 내려갈 수 없어.

계층이 있어야 "부모가 충분하면 멈추고, 부족하면 자식으로 내려간다"가 가능해.

그래서 클러스터 LOD는 데이터 구조와 셰이더가 한 몸이야.

🌱 이 개념은 왜 생겼나 — Main/Post 패스
• 원래 구조: 한 번 검사해서 "보임/가려짐"을 정하고 바로 끝내면 제일 단순해.
• 그런데 문제: 놀이공원 줄이 움직이듯 카메라도 움직여. 지난 프레임엔 기둥 뒤라 안 보이던 단체가 이번 프레임엔 옆으로 삐져나올 수 있어.
• 그래서 필요한 것: 먼저 MainPass로 큰 줄을 처리하고, HZB 같은 깊이 표를 만든 뒤 PostPass에서 의심스러운 애들을 다시 봐야 해. 이름도 그대로 먼저/나중 패스야.

4. 한 번만 그리는 게 아니라 Main/Post로 다시 본다

Nanite는 보이는 후보를 한 번에 끝내지 않아.

오클루전까지 생각하면 "지난 프레임 기준으로 가려졌던 것"이 이번 프레임엔 보일 수 있다.

그래서 메인 패스와 포스트 패스 흐름이 있다.

아래 C++ 흐름에서 MainPass 뒤에 HZB를 만들고, PostPass에서 다시 컬링/래스터를 건다.

NaniteCullRaster.cpp:6568

// No Occlusion Pass / Occlusion Main Pass { RDG_EVENT_SCOPE_CONDITIONAL(GraphBuilder, !Configuration.bTwoPassOcclusion, "NoOcclusionPass"); RDG_EVENT_SCOPE_CONDITIONAL(GraphBuilder, Configuration.bTwoPassOcclusion, "MainPass"); AddPass_InstanceHierarchyAndClusterCull( Configuration.bTwoPassOcclusion ? 🔤 기호 사전 — 두 번 보는 이유
• MainPass = 먼저 보이는 것들을 컬링하고 래스터하는 1차 검사.
• PostPass = 지난번에 가려졌다고 생각한 것들을 다시 시험하는 2차 검사.
• HZB = 깊이 버퍼를 계층으로 줄인 것. 멀리서 "저 상자 뒤에 숨었나?"를 빨리 본다.
• AddPass_InstanceHierarchyAndClusterCull = 인스턴스/계층/클러스터 후보를 GPU 패스로 줄이는 단계.
• AddPass_Rasterize = 남은 클러스터를 실제 래스터 단계로 넘기는 단계.
• SplitWorkQueue = 다음 단계로 넘길 작업 묶음. 서버의 워커 큐처럼 읽으면 된다.
🔁 이제 다시 보자. MainPass는 "일단 보이는 것부터 처리"야. PostPass는 "아까 가려졌다고 넘긴 것 중 지금은 보여야 하는 것 다시 확인"이고. Nanite는 클러스터를 고르는 일도, 다시 확인하는 일도 RDG 패스로 쪼개 GPU에 던진다.

이 구조 때문에 Nanite는 화면 변화에 따라 후보를 계속 재평가할 수 있어.

서버에서 지연 처리 큐를 한 번 더 확인하는 것과 비슷해.

한 틱 전에 관심 영역 밖이던 엔티티가 지금 들어왔으면 다시 잡아야 하잖아.

렌더링도 "지난 프레임엔 가려짐"이 영원한 진실이 아니야.

5. 최종 visible 클러스터는 SW/HW 양쪽 끝에서 쌓인다

이제 GPU가 클러스터를 골랐다고 하자.

그 다음엔 이 클러스터를 하드웨어 래스터로 보낼지, 소프트웨어 compute 래스터로 보낼지 나눠야 해.

셰이더는 같은 OutVisibleClustersSWHW 버퍼에 쓰되, 하드웨어 클러스터는 뒤쪽에서, 소프트웨어 클러스터는 앞쪽에서 쌓는다.

NaniteClusterCulling.usf:709

void EmitVisibleCluster(bool bUseHWRaster, uint2 TotalPrevDrawClusters, uint HWClusterCounterIndex, FVisibleCluster VisibleCluster) { if (bUseHWRaster) { uint ClusterOffsetHW = 0; WaveInterlockedAddScalar_(VisibleClustersArgsSWHW[HWClusterCounterIndex], 1, ClusterOffsetHW); uint VisibleClusterOffsetHW = ClusterOffsetHW; VisibleClusterOffsetHW += TotalPrevDrawClusters.y; #if CULLING_PASS == CULLING_PASS_OCCLUSION_POST VisibleClusterOffsetHW += OffsetClustersArgsSWHW[HWClusterCounterIndex]; #endif if (VisibleClusterOffsetHW < MaxVisibleClusters) { StoreVisibleCluster(OutVisibleClustersSWHW, (MaxVisibleClusters - 1) - VisibleClusterOffsetHW, VisibleCluster, VIRTUAL_TEXTURE_TARGET); // HW clusters written from the top } } else { uint ClusterOffsetSW = 0; WaveInterlockedAddScalar_(VisibleClustersArgsSWHW[0], 1, ClusterOffsetSW); uint VisibleClusterOffsetSW = ClusterOffsetSW; VisibleClusterOffsetSW += TotalPrevDrawClusters.x; #if CULLING_PASS == CULLING_PASS_OCCLUSION_POST VisibleClusterOffsetSW += OffsetClustersArgsSWHW[0]; #endif if (VisibleClusterOffsetSW < MaxVisibleClusters) { StoreVisibleCluster(OutVisibleClustersSWHW, VisibleClusterOffsetSW, VisibleCluster, VIRTUAL_TEXTURE_TARGET); // SW clusters written from the bottom } } }
🔤 기호 사전 — visible 클러스터 쌓기
• EmitVisibleCluster = "이 클러스터는 그릴 목록에 넣어" 함수.
• bUseHWRaster = 하드웨어 길이면 참, compute 소프트웨어 길이면 거짓.
• WaveInterlockedAddScalar_ = 여러 GPU 스레드가 동시에 숫자를 올릴 때 겹치지 않게 더하는 장치.
• MaxVisibleClusters = 이번 패스에서 담을 수 있는 visible 클러스터 최대치.
• StoreVisibleCluster = 버퍼에 클러스터 정보를 실제로 써 넣는다.
• top / bottom 주석 = HW는 버퍼 뒤쪽, SW는 앞쪽에서 채운다는 힌트.
🔁 이제 다시 보자. 버퍼 하나를 두 팀이 같이 쓰는데, 한 팀은 앞에서부터, 한 팀은 뒤에서부터 채워. 이렇게 하면 SW/HW 목록이 서로 밟지 않고 같은 결과판에 모일 수 있어. 이건 CPU가 예쁘게 배열을 만들어 주는 게 아니라 GPU 스레드들이 원자 연산으로 직접 자리표를 뽑는 구조야.

여기서 "GPU 주도"라는 말이 진짜 의미를 가진다.

CPU가 최종 배열 인덱스를 하나하나 정해 주는 게 아니야.

GPU 웨이브가 카운터를 올리고, 자기 자리를 얻고, visible 클러스터를 쓴다.

서버로 치면 IOCP 워커들이 완료 패킷을 꺼내서 락 없는 카운터로 결과 슬롯을 잡는 그림에 가깝다.

6. Nanite.cpp는 이 결과를 통계로도 다시 본다

이번 장의 주요 소스인 Nanite.cpp에는 전체 컬링 공식보다, Nanite 결과를 화면에 출력하고 통계로 보는 접점이 많이 나온다.

특히 PrintStats는 MainPass/PostPass 버퍼를 꺼내고, FPackedCluster 크기와 두 패스 여부를 셰이더 파라미터로 넘긴다.

🔤 기호 사전 — 통계도 패스를 안다
• MainPassBuffers = 1차 컬링/래스터 통계 버퍼.
• PostPassBuffers = 2차 오클루전 재검사용 통계 버퍼.
• PackedClusterSize = packed cluster 하나의 바이트 크기. 내부 필드는 여기서 꾸며내면 안 되고, 이 코드에선 크기만 넘긴다.
• bTwoPass = PostPass 버퍼가 있으면 두 패스 컬링으로 본다.
• PermutationVector.Set = 셰이더 변형을 고르는 스위치. shader-permutation에서 본 그 구조야.
• GraphBuilder.RegisterExternalBuffer = RDG 밖에 있던 버퍼를 그래프 패스에서 읽을 수 있게 등록한다.
🔁 이제 다시 보자. Nanite.cpp는 "Nanite가 방금 몇 개의 클러스터를 어떤 패스로 보냈는지"를 출력용 셰이더에 넘긴다. bTwoPass가 켜지면 통계 셰이더도 Main/Post를 다르게 본다. 그러니까 Nanite의 두 패스 구조는 디버그 출력에서도 그대로 드러난다.

여기서 FPackedCluster 내부를 억지로 설명하지 않는 게 중요해.

이 저장소에서 이 장이 직접 인용한 C++ 줄은 sizeof(Nanite::FPackedCluster)만 보여 준다.

그래서 우리는 "클러스터 단위로 통계를 본다"까지만 말하면 돼.

구조체 내부 필드 이야기는 실제 정의를 찾은 장에서 해야 한다.

코드 데이터 흐름 한눈에

원본 Nanite 메시 -> ClusterPageData + HierarchyBuffer -> CandidateNodes / CandidateClusters (NaniteCullRaster.cpp:983) -> ShouldVisitChildInternal / SmallEnoughToDraw (NaniteClusterCulling.usf:281) -> AddPass_InstanceHierarchyAndClusterCull (NaniteCullRaster.cpp:6573) -> AddPass_Rasterize (NaniteCullRaster.cpp:6575) -> EmitVisibleCluster (NaniteClusterCulling.usf:709) -> OutVisibleClustersSWHW 앞쪽: SW compute raster clusters 뒤쪽: HW raster clusters -> VisBuffer / Depth / Shading / Stats

이 그림에서 핵심은 "삼각형 전체 목록"이 중간에 없다는 거야.

계층, 후보, visible 클러스터, 래스터 인자만 계속 흐른다.

클러스터가 최종 단위고, 그 클러스터를 어느 길로 보낼지가 GPU 안에서 결정된다.

우리 서버·DirectX 경험과 비교

게임 서버에서 제일 무서운 코드는 대체로 이런 거야.

모든 유저를 돌고, 모든 몬스터를 돌고, 모든 아이템을 돌고, 그 안에서 또 모든 스킬을 돈다.

작을 땐 괜찮지만 숫자가 커지면 끝장이야.

렌더링의 전통 메시 파이프라인도 비슷한 한계가 있어.

모든 삼각형을 정직하게 드로우 경로에 밀어 넣는 구조는, 삼각형 수가 폭발할 때 병목이 선명해진다.

Nanite는 서버식으로 말하면 전체 유저 풀스캔 대신 AOI 후보 큐를 만들고, 워커가 원자 카운터로 결과 슬롯을 잡는 설계에 가깝다.

렌더링 쪽 이름으로 바꾸면 계층 노드와 클러스터가 AOI 후보이고, CandidateNodes, CandidateClusters, OutVisibleClustersSWHW가 작업 큐와 결과 큐다.

DirectX 기본 파이프라인만 보면 "버텍스 넣고 래스터라이저가 삼각형을 그린다"가 중심이야.

Nanite는 그 앞에 거대한 GPU 작업 관리층을 세운다.

어떤 클러스터가 필요한지, 얼마나 잘게 내려갈지, 어떤 래스터 길로 보낼지부터 GPU가 계산한다.

그래서 Nanite를 이해하려면 "삼각형을 많이 그린다"보다 "삼각형이 되기 전 클러스터 후보를 GPU가 관리한다"가 먼저야.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. Nanite가 왜 필요한가요? 기존 파이프라인은 뭐가 문제였나요?

답 보기
영화급 메시가 수천만 삼각형을 들고 오면, 전통 방식은 CPU가 드로우콜 쌓고 정점 셰이더가 삼각형을 다 밀어 넣다가 금방 벽에 닿아. 화면에 쌀알보다 작게 보이는 삼각형까지 똑같이 줄 세우니까 낭비가 심하지. 서버로 치면 유저 1만 명 접속했는데 매 틱마다 모든 유저·아이템·몬스터를 처음부터 끝까지 풀스캔하는 꼴이야. Nanite는 "모든 삼각형을 그대로 그리자"가 아니라, 메시를 클러스터 묶음으로 쪼개두고 화면에 필요한 조각만 고르는 장치야. AOI에 걸린 엔티티만 워커 큐에 올리는 감각.

↳ 그럼 Nanite의 기본 처리 단위는 삼각형인가요?

답 보기
아니, 클러스터야. 이게 핵심 착각 포인트인데, Nanite는 삼각형 1억 개를 낱개로 다루지 않아. 원본 메시를 작은 클러스터 단체로 쪼개 HierarchyBuffer라는 계층으로 묶어두고, GPU가 "이 부모 묶음이면 충분한가, 아니면 자식으로 더 내려가야 하나"를 판단해. 그래서 중간에 "삼각형 전체 목록"이 아예 없어 — 계층·후보·visible 클러스터만 계속 흐른다.

Q2. Nanite에서 LOD는 큰 그림에서 어떻게 정해지나요?

답 보기
"가까우면 고해상도, 멀면 저해상도"는 맞는데 너무 흐릿한 표현이야. 실제로는 클러스터의 경계 구를 화면에 투영해서, 화면에서 얼마나 크게 보이는지와 허용 오차를 놓고 계산해. ShouldVisitChildInternal이 "더 쪼갤까"를 보고, SmallEnoughToDraw가 "이제 그려도 될 만큼 작나"를 봐. 기존 StaticMesh LOD가 메시 단위로 큰 덩어리 하나를 고르는 거였다면, Nanite는 훨씬 작은 클러스터 단위로 "이번 화면에 필요한 컷"을 만든다.

↳ 이 LOD 판정을 CPU가 하나요 GPU가 하나요?

답 보기
GPU 셰이더 안에서 해. CPU가 "이 메시의 3번 LOD 그려" 하고 딱 정해주는 그림이 아니야. GPU가 노드와 클러스터를 보며 더 내려갈지·멈출지·그릴지를 직접 판단하지. 이게 "GPU 주도(GPU-driven)"의 핵심이야 — 입구 직원(CPU) 혼자 손님을 다 판정하는 게 아니라, 자동 게이트(GPU)가 직접 후보를 세고 줄을 나눈다.

Q3. 그럼 CPU는 Nanite한테 뭘 넘기나요?

답 보기
삼각형 목록이 아니라 작업판(버퍼)을 넘겨. ClusterPageData·HierarchyBuffer 같은 재료와, CandidateNodes·CandidateClusters 같은 후보 큐, 그리고 결과를 쓸 OutVisibleClustersSWHW를 RDG 버퍼로 준비해줘. 그 뒤 후보를 늘리고 줄이고 최종 visible 목록을 채우는 건 GPU 일이야. 서버식으로 말하면 아직 판정 중인 후보 큐와 최종 처리 큐를 따로 만들어 워커한테 넘기는 셈.

↳ 왜 HierarchyBuffer가 핵심인가요?

답 보기
Nanite 메시가 그냥 납작한 삼각형 배열이면 GPU가 똑똑하게 내려갈 수가 없어. 계층이 있어야 "부모 묶음이 충분하면 멈추고, 부족하면 자식으로 내려간다"가 가능해지거든. 그래서 클러스터 LOD는 데이터 구조(계층)와 셰이더(판정)가 한 몸이야. 계층이 없으면 화면 크기로 필요한 만큼만 쪼갠다는 아이디어 자체가 성립을 안 해.

Q4. Nanite는 왜 한 번에 안 끝내고 Main/Post 두 패스로 도나요?

답 보기
오클루전 때문이야. 지난 프레임 기준으로 가려졌던 게 이번 프레임엔 보일 수 있거든. 카메라가 움직이면 기둥 뒤에 숨었던 단체가 옆으로 삐져나오잖아. 그래서 MainPass로 일단 보이는 것부터 처리하고 HZB(계층 깊이 표)를 만든 뒤, PostPass에서 "아까 가려졌다고 넘긴 것 중 지금은 보여야 하는 것"을 다시 확인해. "지난 프레임엔 가려짐"이 영원한 진실이 아니라는 거지. 서버에서 지연 처리 큐를 한 틱 뒤 다시 확인하는 것과 비슷해.

↳ 최종 visible 클러스터를 SW/HW로 나누는 건 왜죠?

답 보기
삼각형이 픽셀보다 작아지면 고정 기능 하드웨어 래스터에 전부 태우는 준비 비용이 오히려 부담이 돼. 그래서 큰 삼각형은 하드웨어 길로, 작은 삼각형은 compute 셰이더(소프트웨어) 길로 나눠. 재밌는 건 둘이 같은 OutVisibleClustersSWHW 버퍼를 쓰는데, HW는 뒤쪽에서 SW는 앞쪽에서 채워서 서로 안 밟아. CPU가 배열을 예쁘게 만들어주는 게 아니라 GPU 웨이브가 원자 연산으로 자기 자리를 직접 뽑는 구조야 — 세부는 다음 장 컬링/래스터에서 더 판다.

이 챕터에서 챙길 말

  1. Nanite의 기본 단위는 원본 메시 전체가 아니라 클러스터다.
  2. LOD 선택은 CPU 감이 아니라 GPU 셰이더의 화면 크기/오차 계산이다.
  3. C++은 GPU가 일할 RDG 버퍼와 패스를 준비한다.
  4. MainPass와 PostPass가 있고, PostPass는 오클루전 결과를 다시 확인한다.
  5. 최종 visible 클러스터는 SW/HW 래스터 경로로 나뉜다.

이 다섯 개가 잡히면 다음 장 nanite-cull-raster에서 NodeCull, ClusterCull, raster binning을 읽을 준비가 된다.

🧠 머리 속 한 줄 요약

Nanite는 수많은 삼각형을 CPU가 전부 줄 세우는 방식이 아니라, 메시를 클러스터 계층으로 쪼개 두고 GPU가 화면 기준 LOD·컬링·SW/HW 래스터 경로를 직접 고르게 해서 삼각형 수 제한을 우회하는 렌더링 파이프라인이다.
