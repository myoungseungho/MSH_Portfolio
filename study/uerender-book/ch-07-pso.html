PSO — GPU의 설정 묶음

언리얼 렌더링 · 07 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "GPU에 넘기는 거대한 렌더 상태 묶음이 왜 PSO라는 손잡이 하나가 되는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX를 조금 만져봤으면 셰이더 바꾸고, 블렌드 상태 바꾸고, 래스터라이저 상태 바꾸고, 뎁스 스텐실 상태 바꾸고, 렌더타깃 포맷 맞추던 기억이 있을 거야. 서버로 치면 패킷 하나 처리할 때마다 "이 유저 락은 뭐고, DB 트랜잭션 옵션은 뭐고, 라우팅 테이블은 뭐고, 권한 검사는 뭐고"를 매번 새로 조립하는 느낌이지.

한두 번이면 괜찮아. 그런데 렌더링은 한 프레임에 드로우가 수천 번 나와. 16.6ms 안에 끝내야 하는데, 드로우마다 GPU 설정을 낱개로 검증하고 조합하면 그 자체가 병목이 돼. 처음 보는 조합이면 드라이버가 "이 셰이더랑 이 렌더타깃 포맷이랑 이 뎁스 상태가 같이 되는지"를 만들고 검사하느라 40ms, 80ms 히치를 만들 수도 있어.

언리얼도 같은 문제를 만났고, 답이 PSO(Pipeline State Object) 야. 여러 렌더 상태를 매번 낱개로 외치지 말고, "이 조합은 이 카드"라고 미리 묶어둔 다음, 드로우 직전엔 카드 손잡이만 GPU에 꽂는 거지.

그래서 지금 배워야 해. 앞에서 RHI가 하드웨어를 가리는 층이라는 것과 → rhi-overview, RHICommandList가 명령을 쌓았다가 제출한다는 걸 봤어 → rhi-commandlist. 바로 다음 장은 셰이더야 → shader-basics. 셰이더를 배우기 전에, 그 셰이더가 블렌드·뎁스·렌더타깃 포맷과 어떻게 한 묶음으로 GPU에 들어가는지 알아야 해. 그 묶음이 PSO야.

0. 비유부터 — 주방의 코팅된 조리법 카드

식당 주방을 떠올려봐. 주문이 들어올 때마다 홀 직원이 "팬은 28cm, 불은 중강불, 소스는 간장 베이스, 접시는 검은 접시, 마지막에 깨"를 매번 외치면 주방이 미쳐. 듣는 사람도 헷갈리고, 빠진 설정도 생기고, 새 알바는 계속 "이 조합 되는 거 맞아요?" 하고 물어봐.

그래서 식당은 조리법 카드를 만들어. "7번 카드 = 불 중강불 + 28cm 팬 + 간장 소스 + 검은 접시 + 깨 마무리." 주문이 들어오면 이제 긴 설명 대신 "7번 카드로"라고 말하면 돼. PSO가 딱 이 카드야.

셰이더, 블렌드, 래스터라이저, 뎁스 스텐실, 렌더타깃 포맷, 샘플 수, 토폴로지까지 한 장에 적어둔 카드. FGraphicsPipelineStateInitializer는 카드에 적을 원재료 목록이고, PipelineStateCache는 카드 보관함이고, FRHICommandList는 그 카드를 주방으로 들고 가는 웨이터고, D3D12의 SetPipelineState는 주방 라인에 "이 카드로 세팅해" 하고 꽂는 순간이야.

이 비유를 끝까지 끌고 갈 거야. PSO를 보면 계속 "조리법 카드"라고 읽어.

🌱 이 개념은 왜 생겼나 — PSO(Pipeline State Object)
• 원래 구조: 드로우할 때마다 셰이더, 블렌드, 뎁스, 접시 포맷을 하나씩 말하면 돼. 주문마다 "팬, 불, 소스, 접시"를 다시 외치는 식이야.
• 그런데 문제: 드로우가 한 프레임에 수천 번이면 16.6ms 안에 그 긴 설정 확인을 계속 해야 해. 빠진 항목 하나나 안 맞는 포맷 하나가 나오면 주방이 멈춰서 "이 조합 돼?"를 다시 묻지.
• 그래서 필요한 것: 자주 쓰는 설정 묶음을 카드 한 장으로 굳혀두는 거야. 파이프라인 상태를 담은 객체라서 Pipeline State Object, 줄여서 PSO야.

1. PSO 카드에는 뭐가 적히나

먼저 카드 내용부터 보자. 언리얼의 그래픽 PSO 주문서는 FGraphicsPipelineStateInitializer야. 아래 멤버들이 "이 드로우를 어떤 GPU 상태로 그릴지"를 한곳에 모아둔다.

🔤 기호 사전 — PSO 카드의 항목들
• FBoundShaderStateInput = 어떤 셰이더들을 묶어 쓸지 담는 칸. 정점/픽셀/메시 셰이더 손잡이가 여기 들어가.
• FRHIBlendState* = 색을 덮어쓸지, 섞을지 정하는 블렌드 상태 손잡이.
• FRHIRasterizerState* = 삼각형 앞뒷면, 와이어프레임 같은 래스터라이저 규칙 손잡이.
• FRHIDepthStencilState* = 깊이 테스트와 스텐실 테스트 규칙 손잡이.
• EPrimitiveType = 점, 선, 삼각형 중 어떤 모양으로 해석할지 고르는 값.
• RenderTargetFormats = 결과를 쓸 색 버퍼들의 포맷 목록. 접시 모양이라고 보면 돼.
• DepthStencilTargetFormat = 깊이/스텐실 접시의 포맷.
• uint16 / uint8 = 작은 정수 타입. 필요한 크기만큼만 쓰는 번호칸이야.
• bool = 참/거짓 스위치. b로 시작하면 보통 이런 스위치야.
🔁 이제 다시 보자. 이 구조체는 BoundShaderState로 "누가 요리하나"를 적고 → BlendState, RasterizerState, DepthStencilState로 "어떤 조리 규칙인가"를 적고 → RenderTargetFormats, DepthStencilTargetFormat, NumSamples로 "어떤 접시에 담나"를 적어. 이어 읽으면 "GPU 조리법 카드 한 장"이야. 아까는 이름이 길었는데 이제 묶음으로 보이지?

여기서 중요한 건 셰이더만 PSO가 아니라는 거야. 셰이더는 카드의 큰 항목일 뿐이고, 렌더타깃 포맷도 카드에 들어가고, 뎁스 포맷도 들어가고, 샘플 수도 들어가. 그러니까 "같은 픽셀 셰이더인데 렌더타깃 포맷이 다르면 같은 PSO인가?"라고 물으면 답은 보통 아니야. 접시가 바뀌면 주방 카드도 바뀐다.

🌱 이 개념은 왜 생겼나 — 해시 이름표
• 원래 구조: 카드 보관함에서 찾을 때 조리법 전체를 줄줄이 비교하면 돼. 셰이더, 블렌드, 뎁스, 접시 포맷을 하나씩 대조하는 거야.
• 그런데 문제: 카드가 수천 장이고 드로우도 수천 번이면, 요리보다 카드 찾기가 길어져. "7번 카드 있어?" 대신 매번 긴 조리법을 읽는 셈이지.
• 그래서 필요한 것: 긴 조리법을 짧은 숫자 이름표로 접어두는 거야. 값을 잘게 섞어 만든 이름표라서 해시고, 보관함에서 빨리 찾는 손잡이가 돼.

2. 카드 이름표는 해시로 만든다

카드를 보관하려면 이름표가 필요해. 언리얼은 PSO 주문서의 핵심 항목들을 해시로 섞어 캐시 키를 만든다. 주방 카드 보관함에서 "이 조합 카드 이미 있나?"를 빨리 찾으려면 긴 설명 대신 짧은 번호가 필요하잖아.

• uint32 Hash = 32비트짜리 숫자 이름표.

• HashCombineFast = 기존 이름표에 새 항목의 이름표를 빠르게 섞는 함수.
• for (...) = 같은 일을 여러 번 반복하는 문법.
• Initializer.RenderTargetFlags[Index] = 렌더타깃 플래그 배열에서 Index번째 칸을 꺼낸다는 뜻.

🔁 이제 다시 보자. BoundShaderState 해시에서 시작해서 → 블렌드, 래스터라이저, 뎁스, 렌더타깃 포맷을 하나씩 HashCombineFast로 섞고 → 마지막에 return Hash로 카드 번호를 만든다. 긴 조리법을 매번 비교하지 않으려고 "7번 카드" 번호표를 붙이는 거지.

이 코드가 말해주는 게 있어. PSO는 성능용 캐시이면서 동시에 정확성용 키야. 상태 하나라도 바뀌면 해시가 달라질 수 있고, 해시가 달라지면 보관함에서 다른 카드를 찾게 돼. GPU 입장에서는 셰이더뿐 아니라 출력 포맷, 샘플 수, 뎁스 규칙까지 같이 맞아야 한다.

🌱 이 개념은 왜 생겼나 — PSO 캐시/프리캐시
• 원래 구조: 주문이 들어온 순간 카드가 없으면 그때 새로 쓰고 코팅하면 돼. 한두 장이면 주방이 잠깐 멈춰도 티가 안 나.
• 그런데 문제: 전투 첫 폭발처럼 처음 보는 조합이 몰리면 새 카드를 한꺼번에 굽게 돼. 앞에서 말한 40ms, 80ms 히치가 여기서 튀어나와.
• 그래서 필요한 것: 이미 만든 카드는 캐시 보관함에 넣고, 올 것 같은 카드는 미리 굽는 프리캐시가 필요해. 피크 시간에 조리법을 쓰지 말고, 준비 시간에 카드부터 만들어두자는 거야.

3. 카드 보관함에서 찾고, 없으면 만든다

이제 주문서가 들어왔어. 언리얼은 먼저 보관함을 뒤져. 이미 카드가 있으면 그걸 쓰고, 없으면 새 카드를 만든다. 여기가 런타임 히치가 생길 수 있는 지점이라 중요해.

• GGraphicsPipelineCache.Find(...) = 전역 그래픽 PSO 보관함에서 이 주문서 카드를 찾아본다.

• GraphicsPipelineCacheMisses++ = 캐시 미스 카운터를 하나 올린다.
• InternalCreateGraphicsPipelineState(...) = 실제 RHI PSO 생성을 시작하는 내부 함수.
• AddDispatchPrerequisite(GraphEvent) = 비동기 생성이 끝나야 이 명령을 제출할 수 있다고 의존성을 건다.

🔁 이제 다시 보자. GGraphicsPipelineCache.Find로 카드 보관함을 뒤지고 → 없으면 new FGraphicsPipelineState()로 빈 카드를 만들고 → InternalCreateGraphicsPipelineState로 실제 GPU용 카드를 굽고 → 필요하면 AddDispatchPrerequisite로 "다 구워질 때까지 기다려"를 걸고 → GGraphicsPipelineCache.Add로 보관함에 꽂는다. 이게 PSO 캐시의 핵심 동선이야.

여기서 "왜 미리 묶어두나"가 보이지? 새 카드 만들기는 싸지 않을 수 있어. 그래서 언리얼은 PSOPrecacheResult를 보고, DoAsyncCompile을 보고, GraphicsPipelineCacheMisses까지 센다. 실행 중에 카드가 없어서 새로 굽는 건 위험 신호야. 점심 피크에 코팅 카드가 없어서 그 자리에서 조리법을 새로 쓰고 검수하는 꼴이고, 게임에서는 그게 히치로 보인다.

4. 커맨드 리스트는 카드 손잡이를 명령으로 쌓는다

카드가 생겼다고 해보자. 그 카드를 바로 GPU에 꽂을 수도 있고, RHICommandList에 "나중에 이 카드 꽂아"라는 명령으로 쌓을 수도 있어. 이전 장에서 본 명령 기록 구조가 여기서 다시 나온다.

RHICommandList.h:4100

inline void SetGraphicsPipelineState(class FGraphicsPipelineState* GraphicsPipelineState, const FBoundShaderStateInput& ShaderInput, uint32 StencilRef, bool bApplyAdditionalState) { //check(IsOutsideRenderPass()); OnBoundShaderChanged(ShaderInput); if (Bypass()) { FRHIGraphicsPipelineState* RHIGraphicsPipelineState = ExecuteSetGraphicsPipelineState(GraphicsPipelineState); GetContext().RHISetGraphicsPipelineState(RHIGraphicsPipelineState, StencilRef, bApplyAdditionalState); return; } ALLOC_COMMAND(FRHICommandSetGraphicsPipelineState)(GraphicsPipelineState, StencilRef, bApplyAdditionalState); }
🔤 기호 사전 — PSO 설정 명령 쌓기
• inline void = 반환값 없이 바로 펼쳐 쓰기 좋은 작은 함수라는 뜻.
• FGraphicsPipelineState* = 언리얼 캐시가 들고 있는 그래픽 PSO 카드 손잡이.
• const FBoundShaderStateInput& = 셰이더 묶음 정보를 복사하지 않고 읽기 전용으로 받는다.
• OnBoundShaderChanged(ShaderInput) = 지금 바인딩된 셰이더 정보가 바뀌었다고 커맨드 리스트 내부 상태를 갱신한다.
• Bypass() = 명령을 쌓지 않고 즉시 실행하는 경로인지 확인한다.
• ExecuteSetGraphicsPipelineState(...) = 캐시 카드에서 실제 RHI PSO 손잡이를 꺼낸다.
• GetContext().RHISetGraphicsPipelineState(...) = RHI 컨텍스트에 바로 PSO를 꽂는다.
• ALLOC_COMMAND(...) = 지금 실행하지 말고 커맨드 리스트에 명령 객체를 할당해 쌓는다.
🔁 이제 다시 보자. OnBoundShaderChanged로 셰이더 상태를 갱신하고 → Bypass()면 즉시 RHISetGraphicsPipelineState를 호출하고 → 아니면 ALLOC_COMMAND로 "나중에 이 PSO 꽂아" 명령을 쌓는다. 웨이터가 주방에 바로 뛰어갈지, 주문표에 적어뒀다가 한 번에 넘길지의 차이야.

PSO는 "그리기 명령" 자체가 아니야. 그리기 전에 주방 라인을 어떤 카드로 맞출지 정하는 명령이야. 그 다음에 Draw가 와야 실제 픽셀이 찍혀. 서버로 치면 CM_ATTACK 패킷 처리 전에 "이 세션의 권한/상태/락 컨텍스트를 이걸로 세팅한다"에 가깝고, 세팅만 했다고 몬스터가 맞는 건 아니야.

5. RHICommandList.cpp에서는 쌓인 명령을 재생한다

사용자가 지정한 주요 소스인 RHICommandList.cpp도 여기서 이어져. 커맨드 리스트는 명령을 품고 있다가, 번역 단계에서 실제로 실행한다. PSO 설정 명령도 이 흐름 속에서 재생된다.

RHICommandList.cpp:1095

// Replay the recorded commands. The Contexts array accumulates any used // contexts depending on the ActivatePipeline commands that were recorded. CmdList->Execute(); #if WITH_RHI_BREADCRUMBS // Walk back out of the breadcrumb tree FRHIBreadcrumbNode::WalkOut(CmdList->CPUBreadcrumbState.Current); #endif // Extract the contexts from the command list, so we can reuse them for future command lists. for (ERHIPipeline Pipeline : MakeFlagsRange(ERHIPipeline::All)) { auto& TranslateContext = PipelineStates[Pipeline].Context; check(!TranslateContext || TranslateContext == CmdList->Contexts[Pipeline]); if (!TranslateContext) { TranslateContext = CmdList->Contexts[Pipeline]; }
🔤 기호 사전 — 기록된 RHI 명령 재생
• CmdList->Execute() = 커맨드 리스트에 쌓인 명령들을 실제로 실행한다.
• #if WITH_RHI_BREADCRUMBS = 디버깅용 빵부스러기 기능이 켜졌을 때만 컴파일되는 구간.
• for (ERHIPipeline Pipeline : MakeFlagsRange(...)) = 그래픽/컴퓨트 같은 RHI 파이프라인들을 하나씩 돈다.
• auto& TranslateContext = 타입은 컴파일러가 알아서 잡고, 원본을 직접 가리키는 별명으로 쓴다.
• check(...) = 조건이 틀리면 개발 중 바로 터뜨리는 검증.
• CmdList->Contexts[Pipeline] = 이 커맨드 리스트가 실제로 사용한 RHI 컨텍스트 칸.
🔁 이제 다시 보자. CmdList->Execute()가 주문표에 적어둔 명령을 재생하고 → 그 실행 중에 PSO 설정 명령도 RHI 컨텍스트로 내려가고 → 끝나면 CmdList->Contexts에서 사용한 컨텍스트를 꺼내 다음 번역 작업에 재사용한다. 웨이터가 주문표를 주방에 전달하고, 주방 라인 담당자를 다음 주문에도 이어 쓰는 흐름이야.

이 장의 핵심은 여기야. RHICommandList.h에서는 PSO 설정을 명령으로 쌓고, RHICommandList.cpp에서는 쌓인 명령 전체를 재생해. PSO는 따로 떠다니는 개념이 아니라, RHI 명령 재생 흐름 안에서 "GPU 상태 카드를 꽂는 명령"으로 살아 있어.

🌱 이 개념은 왜 생겼나 — D3D12 SetPipelineState
• 원래 구조: 드로우할 때마다 셰이더, 블렌드, 뎁스 같은 상태를 낱개로 다시 꽂으면 돼. 주방 라인을 주문마다 전부 새로 세팅하는 방식이야.
• 그런데 문제: 같은 카드로 100번 그릴 때도 매번 전부 다시 꽂으면 손이 너무 많이 가. 반대로 Draw/Dispatch가 바뀌는데 카드가 안 맞으면 엉뚱한 라인 세팅으로 요리하는 꼴이 돼.
• 그래서 필요한 것: 지금 꽂힌 카드와 다음 카드를 비교해서, 달라질 때만 파이프라인 상태를 새로 Set하는 호출이 필요해. 그 끝단 명령이 D3D12의 SetPipelineState야.

6. D3D12 끝단에서는 진짜 SetPipelineState가 호출된다

마지막으로 주방 라인 끝을 보자. RHI가 D3D12 백엔드로 내려가면, 상태 캐시는 현재 꽂힌 D3D12 PSO와 새로 꽂을 PSO를 비교한다. 다르면 진짜 DirectX 명령 리스트에 SetPipelineState를 호출한다.

D3D12StateCache.cpp:413

void FD3D12StateCache::InternalSetPipelineState(FD3D12PipelineState* InPipelineState) { // See if we need to set our PSO: // In D3D11, you could Set dispatch arguments, then set Draw arguments, then call Draw/Dispatch/Draw/Dispatch without setting arguments again. // In D3D12, we need to understand when the app switches between Draw/Dispatch and make sure the correct PSO is set. ID3D12PipelineState* const CurrentD3DPipelineState = PipelineState.Common.CurrentPipelineStateObject; ID3D12PipelineState* const PendingD3DPipelineState = InPipelineState->GetPipelineState(); if (PipelineState.Common.bNeedSetPSO || CurrentD3DPipelineState == nullptr || CurrentD3DPipelineState != PendingD3DPipelineState) { PipelineState.Common.CurrentPipelineStateObject = PendingD3DPipelineState; CmdContext.GraphicsCommandList()->SetPipelineState(PendingD3DPipelineState); PipelineState.Common.bNeedSetPSO = false; } }
🔤 기호 사전 — D3D12에 카드 꽂기
• FD3D12StateCache = D3D12 백엔드가 현재 GPU 상태를 기억해두는 캐시.
• FD3D12PipelineState* = D3D12 쪽 PSO 카드 손잡이.
• ID3D12PipelineState* const = DirectX 12의 실제 PSO 인터페이스 손잡이.
• CurrentD3DPipelineState = 지금 주방 라인에 꽂혀 있는 카드.
• PendingD3DPipelineState = 새로 꽂으려는 카드.
• CurrentD3DPipelineState != PendingD3DPipelineState = 카드가 다르면 바꿔야 한다는 조건.
• SetPipelineState(...) = D3D12 명령 리스트에 진짜 PSO를 설정하는 호출.
• bNeedSetPSO = false = 이제 카드 꽂았으니 다시 꽂을 필요 표시를 끈다.
🔁 이제 다시 보자. CurrentD3DPipelineState와 PendingD3DPipelineState를 비교하고 → 비어 있거나 다르면 SetPipelineState를 호출하고 → 끝나면 bNeedSetPSO를 끈다. 즉 PSO는 "매번 모든 상태를 다시 말하기"가 아니라 "카드가 달라질 때만 새 카드 꽂기"야.

GPU는 상태가 필요하고, 언리얼은 그 상태를 PSO 카드로 묶고, 캐시는 같은 카드를 재사용하고, D3D12는 카드가 바뀔 때만 실제 SetPipelineState를 호출한다. 카드를 미리 잘 구워두면 주방이 빠르게 돌고, 카드가 없으면 점심 피크에 새 카드 만들다가 멈칫한다.

우리 서버·DirectX 랑 비교

우리 조선 서버 쪽 감각으로 보면 PSO는 "패킷 핸들러 실행 컨텍스트를 미리 조립한 것"에 가까워. 매 패킷마다 DB 커넥션 옵션, 권한 정책, 락 순서, 라우팅 테이블을 새로 계산하면 서버가 느려질 거야. 그래서 세션 상태나 액터 상태, 핸들러 테이블을 미리 잡아두고, 패킷이 오면 손잡이로 빠르게 들어가잖아.

PSO도 비슷해. 드로우가 올 때마다 전체 렌더 상태를 낱개로 검증하지 않고, 이미 검증되고 생성된 상태 묶음을 재사용한다. 다만 서버의 핸들러 테이블은 보통 CPU 포인터 찾기라 비교적 싸고, PSO 생성은 드라이버와 GPU 백엔드가 끼는 일이라 훨씬 무겁다.

DirectX 11에 익숙하면 처음엔 낯설 수 있어. D3D11은 OMSetBlendState, RSSetState, OMSetDepthStencilState처럼 낱개 상태를 자주 바꾸는 느낌이 강했어. D3D12는 더 노골적으로 "파이프라인 상태를 큰 덩어리로 만들어라" 쪽이야. 언리얼의 RHI PSO 캐시는 그 D3D12식 사고방식을 엔진 전체에 맞게 감싼 층이라고 보면 돼.

그래서 언리얼은 PSOPrecacheResult, DoAsyncCompile, AddDispatchPrerequisite 같은 장치를 둬. "없으면 그때 만들지 뭐"가 아니라, 가능하면 미리 만들고, 늦었으면 추적하고, 비동기면 기다릴 조건을 붙인다. 락으로 치면 "전투 중에 큰 전역 락 잡지 말고, 로딩이나 준비 단계에서 필요한 테이블을 만들어둬"에 가까워.

이 챕터에서 딱 이것만

  • PSO는 셰이더 하나가 아니라, 셰이더·블렌드·래스터·뎁스·렌더타깃 포맷까지 묶은 GPU 설정 카드야.
  • FGraphicsPipelineStateInitializer는 그 카드에 적을 주문서고, GetTypeHash는 보관함에서 찾기 위한 카드 번호야.
  • PipelineStateCache는 먼저 찾고, 없으면 만들고, 필요하면 비동기 생성 완료를 RHICommandList 제출 조건으로 걸어.
  • FRHICommandList는 PSO 설정을 즉시 실행하거나 명령으로 쌓고, RHICommandList.cpp의 CmdList->Execute() 흐름에서 재생해.
  • D3D12 끝단에서는 현재 카드와 새 카드를 비교해서, 다를 때만 SetPipelineState를 호출해.

🎯 원리 한 줄 요약

PSO는 GPU에게 매번 긴 설정을 다시 설명하지 않으려고 만든 "조리법 카드"다 — 언리얼은 그 카드를 해시로 찾고 캐시하며, RHICommandList를 통해 필요할 때만 D3D12 SetPipelineState까지 내려보낸다.
