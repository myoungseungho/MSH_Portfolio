버퍼·텍스처·뷰 — GPU 메모리에 올리기

언리얼 렌더링 · 06 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "CPU 메모리의 데이터를 GPU 리소스로 올리고, SRV/UAV/RTV 같은 뷰로 쓰게 만드는 흐름"이 잡힌다.
🧱 먼저 알아야 할 것 — 물건과 이름표
• 물건: 실제로 만질 대상과 그 대상을 부르는 이름은 서로 다르다.
• 이름표: 같은 물건에도 "읽기만", "고치기 가능", "여기에 담기"처럼 다른 이름표를 붙일 수 있다.
• 허락: 이름표가 다르면 할 수 있는 행동도 달라진다.
이게 잡히면 아래 설명이 얹힌다.

왜 이걸 배워? — 문제의식부터

지난 장에서 RHI 명령이 D3D12 백엔드로 내려가는 걸 봤어. 이제 질문은 이거야. "GPU가 그릴 데이터는 어디 있어?" 서버로 치면 CM_ATTACK 패킷 핸들러만 있어서는 아무것도 못 해. 플레이어 위치, 인벤토리, 몬스터 테이블 같은 상태 저장소가 있어야 로직이 돌잖아. 렌더링도 똑같아. Draw 명령만 있다고 삼각형이 생기는 게 아니야. 정점 버퍼, 인덱스 버퍼, 텍스처, 렌더타깃이 먼저 GPU 쪽에 있어야 해.

이게 없으면 뭐가 터질까? 매 프레임 CPU 배열을 들고 있다가 Draw 직전에 GPU로 100MB씩 밀어 넣는다고 생각해봐. PCIe 전송이 병목이 되고, RHI 스레드가 기다리고, GPU는 "밥이 아직 안 왔는데 뭘 그려?" 하고 멈춘다. 텍스처 한 장을 잘못된 크기로 업데이트하면 out-of-bounds 검사에 걸리고, 렌더타깃 플래그 없이 만든 텍스처를 화면에 쓰려 하면 RTV가 없어서 백엔드에서 막힌다.

그래서 언리얼도 같은 문제를 만났고, 답이 RHI 리소스야. FRHIBuffer, FRHITexture가 GPU 창고의 물건이고, FRHICommandList는 그 물건을 만들고 채우고 갱신하는 주문서야. 그리고 SRV/UAV/RTV는 같은 물건을 "읽기용 창", "읽고쓰기용 창", "렌더타깃용 도장판"으로 보는 뷰야.

왜 지금 배우냐면 순서가 딱 여기야. 앞에서 RHICommandList가 명령을 쌓는 법을 봤고 → rhi-commandlist, D3D12 백엔드가 진짜 API를 부르는 것도 봤어 → d3d12-backend. 이제 PSO와 셰이더로 넘어가기 전에, 셰이더가 읽을 재료가 GPU 메모리에 어떻게 올라가는지 알아야 해. 안 그러면 다음 장 PSO의 "입력 레이아웃"도, 뒤의 GBuffer도 다 허공에 뜬다.

0. 비유부터 — 주방 창고, 식재료, 라벨

이번 챕터는 식당 주방으로 가자.

주방에는 커다란 냉장 창고가 있어. 거기에 고기, 채소, 소스가 들어간다. GPU 메모리가 그 창고야.

  • 버퍼는 길게 쌓은 식재료 박스야. 정점 목록, 인덱스 목록, 구조화 데이터 같은 "줄 세운 데이터"가 들어가.
  • 텍스처는 칸이 있는 재료 트레이야. 가로·세로 픽셀 칸이 있고, 밉맵이라는 작은 트레이도 붙을 수 있어.
  • 업로드는 CPU 쪽 배달 트럭이 주방 창고로 재료를 나르는 일이야.
  • SRV는 "요리사가 읽어도 되는 라벨"이야. 셰이더가 이 재료를 읽는다.
  • UAV는 "읽고 쓰는 작업대 라벨"이야. 컴퓨트 셰이더가 결과를 다시 써넣을 수 있다.
  • RTV는 "여기에 완성 요리를 담아라"라는 접시 라벨이야. 픽셀 셰이더 출력이 이 텍스처로 들어간다.

중요한 건 창고 물건과 라벨이 같은 게 아니라는 거야.

고기 박스 하나가 있어도, "얇게 썰어 읽기", "다져서 쓰기", "오늘 메인 접시로 쓰기"처럼 보는 법이 달라질 수 있지. GPU도 그래. 같은 FRHITexture라도 SRV로 읽을 수도 있고, UAV로 쓸 수도 있고, 렌더타깃 플래그가 있으면 RTV로 색을 찍을 수도 있어.

그리고 배달은 공짜가 아니야. CPU에서 GPU로 보내는 순간 비용이 든다. 작게 자주 보내면 택배비가 계속 붙고, 크게 한 번에 보내면 대기 시간이 생긴다. 이 장은 "언리얼이 그 배달 주문서를 어떻게 적는가"를 보는 장이야.

소스 위치 (이 클론에 실제로 있음, 아래 코드는 전부 원문 그대로 뽑음)
• 주요 파일: Engine/Source/Runtime/RHI/Public/RHICommandList.h
• 리소스 설명자: Engine/Source/Runtime/RHI/Public/RHIResources.h
• D3D12 RTV 실물: Engine/Source/Runtime/D3D12RHI/Private/D3D12View.cpp
🌱 이 개념은 왜 생겼나 — 버퍼
• 원래 구조: 작은 그림이면 CPU 배열을 들고 있다가 그릴 때마다 GPU에 던지면 될 것 같아.
• 그런데 문제: 정점 100만 개짜리 맵을 매 프레임 다시 배달하면 창고 앞에 트럭 줄이 생겨. 60FPS면 16.6ms 안에 로직, 배달, 그림까지 다 해야 해.
• 그래서 필요한 것: 자주 읽을 줄 세운 데이터를 GPU 창고에 박스로 미리 넣어두자. 그 긴 박스가 버퍼야.
🧱 먼저 알아야 할 것 — 크기와 처음 내용
• 크기: 상자나 공책은 얼마나 큰지 정해야 안에 넣을 양을 알 수 있다.
• 처음 내용: 새 공책은 빈칸일 수도 있고, 0으로 채워져 있을 수도 있고, 처음부터 글이 적혀 있을 수도 있다.
• 주문서: 만들 사람에게는 "얼마나 크게, 처음엔 무엇이 들어 있게"를 한꺼번에 알려줘야 한다.
이게 잡히면 아래 설명이 얹힌다.

1. 버퍼 만들기 — 창고에 긴 박스 하나 들여놓기

버퍼는 GPU가 읽을 "길게 이어진 데이터"야. 정점 버퍼, 인덱스 버퍼, 구조화 버퍼, 유니폼 버퍼가 전부 이 계열이야.

언리얼은 요즘 FRHIBufferCreateDesc라는 주문서로 버퍼를 만든다. 이름, 크기, stride, usage, 초기 상태, 초기화 방식 같은 걸 한 덩어리로 들고 가는 구조야.

실제 생성 함수는 FRHICommandListBase::CreateBuffer에 있어.

RHICommandList.h:800

inline FBufferRHIRef CreateBuffer(const FRHIBufferCreateDesc& CreateDesc) { if (CreateDesc.Size == 0 && !CreateDesc.IsNull()) { InvalidBufferFatalError(CreateDesc); } checkf(CreateDesc.InitAction != ERHIBufferInitAction::Initializer, TEXT("Buffer InitAction set to Initializer when calling CreateBuffer which doesn't write to its initializer")); FRHICommandListScopedPipelineGuard ScopedPipeline(*this); FRHIBufferInitializer Initializer = GDynamicRHI->RHICreateBufferInitializer(*this, CreateDesc); return Initializer.Finalize(); }
🔤 기호 사전 — 버퍼 생성 토막
• FBufferRHIRef = RHI 버퍼를 가리키는 참조 손잡이야. "GPU 창고 안 박스 번호표"라고 보면 돼.
• const FRHIBufferCreateDesc& = 버퍼 주문서를 복사하지 않고 읽기 전용으로 빌려 받는다는 뜻이야.
• CreateDesc.Size == 0 = 주문한 버퍼 크기가 0인지 확인한다.
• !CreateDesc.IsNull() = null placeholder 버퍼가 아니면이라는 뜻. !는 참/거짓 뒤집기야.
• checkf(...) = 조건이 틀리면 메시지를 붙여 터뜨리는 개발용 안전 검사야.
• ERHIBufferInitAction::Initializer = "초기 데이터를 Initializer로 직접 채우겠다"는 선택지야.
• FRHICommandListScopedPipelineGuard ScopedPipeline(*this) = 이 함수 안에서 RHI 파이프라인 접근을 안전하게 감싸는 작은 경비원 같은 객체야.
• GDynamicRHI->RHICreateBufferInitializer(*this, CreateDesc) = 실제 플랫폼 RHI한테 "이 주문서로 버퍼 초기화기를 만들어줘"라고 넘기는 호출이야.
• Initializer.Finalize() = 초기화기를 끝내고 진짜 FBufferRHIRef를 돌려받는 마지막 도장이다.
🔁 이제 다시 보자. 이 코드는 CreateDesc를 검사하고 → RHICreateBufferInitializer로 플랫폼 RHI에 넘기고 → Finalize()로 진짜 버퍼 손잡이를 받는다. 창고 직원한테 "이 크기 박스 하나 만들어" 주문하고, 박스 번호표를 받아오는 장면이야.

여기서 중요한 건 "만들기"와 "채우기"가 분리돼 있다는 점이야. CreateBuffer는 바로 Finalize()를 해버리니까, Initializer 방식으로 데이터를 써넣으려는 주문서는 거절한다. 그래서 코드에 CreateDesc.InitAction != ERHIBufferInitAction::Initializer 검사가 있는 거야.

초보가 헷갈리는 지점은 여기야. "버퍼 만들기"가 항상 CPU 데이터를 같이 올린다는 뜻은 아니야. 빈 박스를 만들 수도 있고, 0으로 채울 수도 있고, 외부 ResourceArray를 업로드할 수도 있고, 초기화기를 받아 직접 채울 수도 있어.

RHIResources.h에는 그 초기화 선택지가 딱 enum으로 박혀 있다.

RHIResources.h:1401

enum class ERHIBufferInitAction { // Default for the RHI, data can be "undefined" Default, // Zero all buffer data Zeroed, // Upload data from a provided FResourceArrayUploadInterface. This data will be discarded after it's used. ResourceArray, // Caller will use FRHIBufferInitializer to set the initial buffer contents. Initializer, };
🔤 기호 사전 — 버퍼 초기화 방식
• enum class = 정해진 보기 몇 개 중 하나만 고르게 하는 안전한 목록이야.
• Default = RHI 기본값. 내용물은 정해지지 않았을 수 있어.
• Zeroed = 버퍼 전체를 0으로 채운다.
• ResourceArray = CPU 쪽 FResourceArrayUploadInterface 데이터를 업로드하고, 사용 후 버릴 수 있다는 뜻이야.
• Initializer = 호출자가 FRHIBufferInitializer로 직접 초기 내용을 채운다는 선택지야.
• // = 사람한테 남기는 설명 주석이고, 실행되진 않아.

이 enum이 바로 "배달 방식" 표야. 냉장고에 박스만 놓을지, 빈 박스를 0으로 닦을지, CPU 트럭에서 물건을 싣고 올지, 직접 포장대에서 채울지를 고르는 거지.

🌱 이 개념은 왜 생겼나 — lock/unlock
• 원래 구조: CPU가 버퍼 포인터를 그냥 들고 아무 때나 고치면 될 것 같아.
• 그런데 문제: GPU가 그 박스를 읽는 중에 CPU가 내용을 갈아 끼우면, 주방 요리사가 재료 쓰는 중에 창고 직원이 박스를 바꿔치기하는 꼴이야.
• 그래서 필요한 것: "잠깐 열게, 다 쓰면 닫을게"라는 출입 절차가 필요해. 그게 lock/unlock이야. 서버 recv buffer도 누가 쓰는 중인지 안 보고 덮으면 터지잖아.
🧱 먼저 알아야 할 것 — 같이 쓰는 물건의 차례
• 차례: 한 사람이 공책을 읽는 동안 다른 사람이 같은 줄을 지우면 내용이 꼬인다.
• 열기와 닫기: 고칠 때는 "지금 내가 쓸게" 하고 열고, 끝나면 "다 썼어" 하고 닫아야 한다.
• 약속: 누가 언제 만질 수 있는지 정해 두면 서로 덮어쓰는 일을 막을 수 있다.
이게 잡히면 아래 설명이 얹힌다.

2. 버퍼를 잠그고 풀기 — CPU가 박스 안에 손 넣는 순간

버퍼를 이미 만들었는데 CPU가 내용을 고쳐야 할 때가 있어. 동적 vertex buffer, staging buffer, readback buffer 같은 상황이지.

그때 나오는 말이 lock/unlock이야. CPU가 잠깐 "이 박스 좀 열어볼게" 하고 포인터를 받고, 다 쓰면 "닫았어" 하고 돌려주는 흐름이야.

RHICommandList.h:747

inline void* LockBuffer(FRHIBuffer* Buffer, uint32 Offset, uint32 SizeRHI, EResourceLockMode LockMode) { checkf(IsTopOfPipe() || Bypass(), TEXT("Buffers may only be locked while recording RHI command lists, not during RHI command list execution.")); FRHICommandListScopedPipelineGuard ScopedPipeline(*this); return GDynamicRHI->RHILockBuffer(*this, Buffer, Offset, SizeRHI, LockMode); } inline void UnlockBuffer(FRHIBuffer* Buffer) { checkf(IsTopOfPipe() || Bypass(), TEXT("Buffers may only be unlocked while recording RHI command lists, not during RHI command list execution.")); FRHICommandListScopedPipelineGuard ScopedPipeline(*this); GDynamicRHI->RHIUnlockBuffer(*this, Buffer); }
🔤 기호 사전 — 버퍼 lock/unlock
• void* = 타입을 아직 모르는 메모리 주소야. "여기부터 네가 해석해"라는 날 포인터에 가까워.
• FRHIBuffer* Buffer = 실제 RHI 버퍼를 가리키는 포인터야.
• uint32 Offset = 버퍼 시작부터 몇 바이트 떨어진 지점부터 열지 정한다.
• uint32 SizeRHI = 얼마나 많은 바이트를 열지 정한다.
• EResourceLockMode LockMode = 읽기인지 쓰기인지 같은 lock 방식이다.
• IsTopOfPipe() || Bypass() = 지금 command list 기록 단계이거나 우회 실행이면 허용한다는 조건이야.
• RHILockBuffer / RHIUnlockBuffer = 실제 플랫폼 RHI로 내려가는 lock/unlock 호출이다.
🔁 이제 다시 보자. LockBuffer는 기록 중인지 검사하고 → 플랫폼 RHI에서 CPU가 만질 주소를 받아온다. UnlockBuffer는 같은 안전 검사를 한 뒤 → "이제 다 썼어"를 플랫폼 RHI에 알려준다. 박스를 연 채로 요리하면 안 되니까, 열었으면 반드시 닫는 흐름이야.

여기서 경고 문구가 중요해. "RHI command list 실행 중"에는 lock하지 말라고 한다. 즉 CPU가 아무 때나 GPU 리소스에 손을 넣을 수 있는 게 아니야. 명령을 기록하는 시점과 명령이 실행되는 시점을 나눴던 전 장 내용이 여기서 다시 나온다 → rhi-commandlist.

서버로 치면 이거야. IOCP 워커가 쓰는 recv buffer를 게임 로직 스레드가 아무 락 없이 바로 고치면 터지잖아. GPU 리소스도 마찬가지야. CPU와 GPU가 같은 물건을 서로 다른 시간축에서 보니까, lock/unlock과 상태 전환이 필요해.

🌱 이 개념은 왜 생겼나 — 텍스처
• 원래 구조: 색이나 깊이도 그냥 긴 버퍼 하나에 줄줄이 담으면 될 것 같아.
• 그런데 문제: 화면 재료는 가로·세로 칸, mip, depth, array, format이 있어. 1024x1024 트레이를 긴 줄로만 보면 "몇 번째 칸"인지 매번 따져야 해.
• 그래서 필요한 것: 칸 모양과 형식과 용도를 함께 들고 있는 GPU 트레이가 필요해. 그게 텍스처야.

3. 텍스처 만들기 — 칸이 있는 재료 트레이 들여놓기

버퍼가 긴 박스라면 텍스처는 가로·세로 칸이 있는 트레이야. 색, 노멀, 깊이, GBuffer, shadow map 같은 것들이 여기 들어간다.

텍스처 생성에서 제일 중요한 주문 항목은 네 가지야.

  1. 크기: Extent, Depth, ArraySize.
  2. 형식: Format.
  3. 용도 플래그: TexCreate_RenderTargetable, TexCreate_ShaderResource, TexCreate_UAV 같은 것.
  4. 초기 상태와 초기 데이터: InitialState, BulkData.

FRHICommandList의 생성 함수는 텍스처 주문서에 초기 상태가 비어 있으면 기본 상태를 계산해 넣는다.

• ERHIAccess::Unknown = 아직 리소스 접근 상태가 정해지지 않았다는 뜻이야.
• RHIGetDefaultResourceState(...) = 플래그와 초기 데이터 유무를 보고 기본 GPU 상태를 고른다.

🔁 이제 다시 보자. CreateTextureInitializer는 메모리 태그를 잡고 → InitialState가 Unknown이면 주문서를 복사해서 기본 상태를 채운 뒤 → 플랫폼 RHI에 넘긴다. CreateTexture는 그 초기화기를 받아 Finalize()로 완성한다. 트레이를 만들 때 "이건 읽기용인지, 렌더타깃용인지, 초기 재료가 실려 오는지"까지 같이 정하는 장면이야.

여기서 InitialState가 왜 중요하냐면 GPU는 리소스를 아무 상태로나 못 써. 방금 렌더타깃으로 썼던 텍스처를 곧바로 셰이더에서 읽으려면 상태 전환이 필요해. 이 장에서는 깊게 안 파지만, "처음 태어날 때 어느 상태냐"가 이후 barrier 비용의 출발점이 된다.

텍스처는 보통 정적 리소스면 생성 시 bulk data를 같이 올리고, 동적 리소스면 이후 update나 copy 명령으로 갱신한다. 여기서도 배달비를 생각해야 해.

🧱 먼저 알아야 할 것 — 칸 안의 사각형 범위
• 자리: 바둑판에서 어느 칸부터 시작하는지 알아야 바꿀 곳을 찾을 수 있다.
• 가로와 세로: 시작 칸에서 몇 칸 넓이와 몇 칸 높이를 바꿀지 정하면 작은 사각형이 된다.
• 줄 길이: 한 줄에 몇 칸이 있는지 알아야 다음 줄의 시작 자리를 헷갈리지 않는다.
이게 잡히면 아래 설명이 얹힌다.

4. 텍스처 업데이트 — CPU 트럭이 일부 칸만 갈아 끼우기

이미 만든 텍스처의 일부 영역만 바꾸는 함수가 UpdateTexture2D야. UI atlas, 동적 데이터 텍스처, 스트리밍 mip 업데이트 같은 데서 감이 온다.

코드를 보면 제일 먼저 경계 검사를 한다. "트레이 밖으로 재료를 흘리지 마"야.

• uint32 MipIndex = 몇 번째 mip level을 바꿀지 정한다.

• RHIUpdateTexture2D = 실제 플랫폼 RHI가 CPU 데이터를 GPU 텍스처에 반영하게 하는 호출이야.
🔁 이제 다시 보자. UpdateTexture2D는 업데이트할 사각형이 텍스처 안에 들어오는지 X/Y로 검사하고 → 메모리 추적 태그를 잡고 → 플랫폼 RHI의 RHIUpdateTexture2D로 CPU 바이트를 넘긴다. 배달 트럭이 트레이의 몇 칸만 갈아 끼우는 흐름이야.

여기서 성능 감각을 잡아야 해. SourceData는 CPU 메모리야. 이 호출은 결국 GPU 쪽으로 데이터를 보내야 한다. 작고 드문 업데이트는 괜찮아. 하지만 큰 텍스처를 매 프레임 업데이트하면, 렌더링 병목이 셰이더가 아니라 업로드가 될 수 있다.

우리 서버로 치면 매 tick마다 DB에서 전체 인벤토리를 다시 긁어와서 클라에 통째로 보내는 느낌이야. 바뀐 슬롯 몇 개만 보내면 되는데 매번 전체를 보내면 네트워크가 막히잖아. 텍스처도 똑같아. 필요한 영역만, 필요한 타이밍에, 가능하면 GPU 내부 copy로 처리하는 게 좋다.

🌱 이 개념은 왜 생겼나 — 뷰(SRV/UAV/RTV)
• 원래 구조: GPU 물건 하나를 만들었으면 그냥 읽고, 쓰고, 출력까지 다 하면 될 것 같아.
• 그런데 문제: 같은 고기 박스라도 읽기만 할지, 작업대에서 다시 다질지, 접시에 담을지 권한이 달라. 렌더타깃 아닌 텍스처에 색을 찍으려 하면 막혀.
• 그래서 필요한 것: 실물은 그대로 두고 "어떻게 볼지(View)" 라벨을 따로 붙여야 해. 읽기 SRV, 읽고쓰기 UAV, 출력 RTV가 그 라벨이야.

5. SRV와 UAV — 같은 물건에 붙는 읽기/쓰기 라벨

이제 뷰로 넘어가자.

리소스는 창고 물건이고, 뷰는 그 물건을 어떻게 볼지 정한 라벨이야.

SRV는 Shader Resource View야. 셰이더가 읽는 라벨이다. Texture2D, StructuredBuffer, ByteAddressBuffer 같은 셰이더 파라미터에 꽂힌다.

UAV는 Unordered Access View야. 셰이더가 읽고 쓸 수 있는 라벨이다. 보통 compute shader의 RWTexture2D, RWStructuredBuffer 같은 곳에 꽂힌다.

언리얼 공개 RHI에서는 CreateShaderResourceView, CreateUnorderedAccessView가 버퍼용과 텍스처용으로 나뉘어 있다.

RHICommandList.h:975

• FUnorderedAccessViewRHIRef = 셰이더가 읽고 쓸 수 있는 뷰 손잡이야. 작업대 라벨 번호표다.
• FRHIViewDesc::FBufferSRV::FInitializer = 버퍼 SRV 라벨 주문서야. 어떤 형식, offset, element 수로 볼지 담는다.
• FRHIViewDesc::FTextureSRV::FInitializer = 텍스처 SRV 라벨 주문서야. mip 범위, array 범위, sRGB 여부 같은 걸 담는다.

• FRHIViewDesc::FTextureUAV::FInitializer = 텍스처 UAV 라벨 주문서야.

🔁 이제 다시 보자. 버퍼든 텍스처든 SRV는 RHICreateShaderResourceView로 내려가고, UAV는 RHICreateUnorderedAccessView로 내려간다. 리소스 실물은 그대로 두고, "읽기 라벨" 또는 "읽고쓰기 라벨"을 따로 붙이는 구조야.

여기서 DirectX 경험이 있으면 바로 매핑돼.

  • FShaderResourceViewRHIRef는 D3D12의 SRV descriptor 쪽 감각이야.
  • FUnorderedAccessViewRHIRef는 D3D12의 UAV descriptor 쪽 감각이야.
  • FRHIViewDesc는 그 descriptor를 만들기 위한 엔진 공통 주문서야.

중요한 차이는 언리얼이 D3D12 전용 구조체를 바로 노출하지 않는다는 거야. FRHIViewDesc라는 공통 말로 적어두고, D3D12/Vulkan/Metal 백엔드가 자기 말로 번역한다. 앞 장에서 본 RHI 추상화가 리소스 뷰에도 그대로 적용되는 거지 → rhi-overview.

6. RTV — 렌더타깃으로 찍는 접시 라벨

SRV/UAV는 공개 RHI command list에 생성 함수가 바로 보였지. 그런데 RTV는 조금 달라. "CreateRenderTargetView"라는 RHI 공개 함수가 앞에 튀어나오기보다, 텍스처를 만들 때 TexCreate_RenderTargetable 같은 플래그가 붙고, D3D12 텍스처 쪽에서 필요한 RTV descriptor를 만들어 둔다.

그래서 D3D12 백엔드 코드를 봐야 실물이 보인다.

RTV는 D3D12에서 진짜 CreateRenderTargetView 호출로 만들어진다.

D3D12View.cpp:382

void FD3D12RenderTargetView::UpdateDescriptor() { GetParentDevice()->GetDevice()->CreateRenderTargetView( ResourceInfo.Resource->GetResource(), &D3DViewDesc, OfflineCpuHandle ); OfflineCpuHandle.IncrementVersion(); }
🔤 기호 사전 — D3D12 RTV 실물 토막
• FD3D12RenderTargetView = D3D12 백엔드가 들고 있는 렌더타깃 뷰 객체야.
• UpdateDescriptor() = 뷰의 descriptor 내용을 다시 써주는 함수야.
• GetParentDevice()->GetDevice() = 언리얼 D3D12 장치 래퍼를 타고 실제 ID3D12Device까지 내려간다.
• CreateRenderTargetView = D3D12가 RTV descriptor를 만드는 실제 API 호출이다.
• ResourceInfo.Resource->GetResource() = 뷰가 가리킬 실제 D3D12 resource를 꺼낸다.
• &D3DViewDesc = D3D12가 읽을 RTV 설명서를 주소로 넘긴다.
• OfflineCpuHandle = CPU descriptor heap 안의 RTV 칸 손잡이야.
• IncrementVersion() = descriptor 내용이 바뀌었음을 버전으로 표시한다.
🔁 이제 다시 보자. FD3D12RenderTargetView는 실제 D3D12 resource와 RTV 설명서와 descriptor heap 칸을 들고 있다가 → CreateRenderTargetView로 RTV를 만든다. 언리얼 RHI의 "렌더타깃 가능 텍스처"가 D3D12에서는 "RTV descriptor 한 칸"으로 내려가는 순간이야.

식당 비유로 돌아오면, RTV는 재료가 아니라 접시야. 셰이더가 계산한 색을 여기에 담는다. GBuffer의 여러 렌더타깃, shadow depth target, 후처리 intermediate texture가 다 이런 식으로 "출력 접시"가 된다.

여기서 많이 하는 실수는 "텍스처니까 읽을 수도 있고 쓸 수도 있고 렌더타깃도 되겠지"라고 생각하는 거야. 아니야. 만들 때 플래그가 중요하다. 렌더타깃으로 쓸 텍스처는 그 용도에 맞게 만들어져야 하고, 백엔드는 거기에 맞는 RTV를 만들어 둔다.

7. CPU→GPU 전송 비용 — 배달 트럭을 너무 자주 부르지 마

이제 비용 얘기를 하자.

CPU 메모리에서 GPU 메모리로 데이터를 보내는 건 그냥 memcpy 감각이 아니야. CPU와 GPU는 다른 세계에 있고, 중간에 드라이버, command queue, upload heap, synchronization이 낀다.

이 장에서 본 비용 지점은 세 군데야.

  1. CreateBuffer / CreateTexture 때 초기 데이터가 있으면 생성과 함께 업로드될 수 있다.
  2. LockBuffer / UnlockBuffer는 CPU가 버퍼를 만지는 동기화 지점이 될 수 있다.
  3. UpdateTexture2D는 CPU 바이트를 텍스처로 보내는 직접 갱신이다.

정적 mesh vertex/index buffer처럼 한 번 만들고 오래 쓰는 건 생성 시 초기 데이터로 올리는 게 자연스럽다. 매 프레임 조금씩 바뀌는 데이터는 작은 동적 버퍼나 uniform buffer로 잘라서 올리는 게 낫다. 큰 텍스처 전체를 자주 바꿔야 한다면 "정말 CPU에서 매번 만들어야 하나? 작은 region만 갱신하면 안 되나?"부터 의심해야 해.

서버 감각으로 말하면, "변경분만 보내라"야. 위치 패킷 하나 바뀌었는데 캐릭터 전체 스냅샷 10KB를 매 tick 보내면 대역폭이 터지잖아. 렌더링도 바뀐 영역, 바뀐 mip, 바뀐 버퍼 구간만 건드리는 습관이 중요해.

콜/데이터 흐름 한눈에

아래 흐름만 잡으면 이번 장은 거의 끝이야.

CPU 데이터 | | 1) 생성 시 초기화 v FRHIBufferCreateDesc / FRHITextureCreateDesc | | RHICommandList.h:800 CreateBuffer | RHICommandList.h:925 CreateTextureInitializer v FRHIBuffer / FRHITexture = GPU 창고 물건 | | 2) 이후 갱신 | RHICommandList.h:747 LockBuffer / UnlockBuffer | RHICommandList.h:914 UpdateTexture2D v 같은 GPU 물건의 내용 변경 | | 3) 보는 법 붙이기 | RHICommandList.h:975 CreateShaderResourceView = SRV | RHICommandList.h:989 CreateUnorderedAccessView = UAV | D3D12View.cpp:382 CreateRenderTargetView = RTV v 셰이더가 읽음 / 컴퓨트가 씀 / 렌더패스가 색을 찍음

흐름을 한 문장으로 줄이면 이거야.

CPU가 주문서를 적고, RHI가 GPU 창고에 물건을 만들고, 필요한 순간 뷰 라벨을 붙여 셰이더와 렌더패스에 넘긴다.

우리 서버·DirectX 랑 비교

서버 개발자 관점으로 보면 RHI 리소스는 "세션별 버퍼"보다 더 엄격한 공유 자원이야.

우리 서버에서 recv buffer를 재사용할 때도 규칙이 있지. 워커가 쓰는 중인 버퍼를 게임 로직이 덮어쓰면 터진다. 패킷 큐에 넣은 뒤에는 소유권이 넘어간다. 락을 걸거나, 복사하거나, 단일 스레드 큐에서 순서대로 처리한다.

GPU 리소스도 똑같이 소유권과 시점이 중요해.

LockBuffer가 기록 시점인지 검사하는 건 "지금 손대도 되는 시점이냐"를 보는 거야.

UpdateTexture2D가 region bounds를 검사하는 건 "네가 쓰려는 칸이 진짜 트레이 안이냐"를 보는 거야.

SRV/UAV/RTV가 따로 있는 건 "같은 물건이라도 읽기, 쓰기, 출력은 권한이 다르다"는 뜻이야.

DirectX 경험으로 보면 더 직접적이야.

언리얼 RHIDirectX 감각한 줄 느낌
FRHIBufferID3D12Resource buffer긴 데이터 박스
FRHITextureID3D12Resource texture2D/3D 픽셀 트레이
FShaderResourceViewRHIRefSRV descriptor셰이더 읽기 라벨
FUnorderedAccessViewRHIRefUAV descriptor읽고쓰기 라벨
FD3D12RenderTargetViewRTV descriptor렌더 출력 접시
UpdateTexture2Dupload/copy/update 경로CPU 배달 트럭

차이는 언리얼이 그걸 바로 D3D12 이름으로 들이밀지 않는다는 점이야. RHI 이름으로 한 번 감싸고, D3D12 백엔드가 CreateRenderTargetView 같은 진짜 API를 부른다. 그래서 엔진 상위 코드는 D3D12/Vulkan/Metal 차이를 덜 보게 된다.

이 챕터에서 딱 이것만

  1. 버퍼와 텍스처는 GPU 창고의 실물이야. FRHIBuffer, FRHITexture가 그 손잡이다.
  2. 생성 주문서는 용도와 초기 상태를 같이 담는다. 크기만 맞으면 끝이 아니라 usage/flags/state가 중요하다.
  3. CPU→GPU 업로드는 공짜가 아니다. lock, update, bulk data는 전송과 동기화 비용을 만든다.
  4. 뷰는 실물이 아니라 라벨이다. SRV는 읽기, UAV는 읽고쓰기, RTV는 렌더 출력용이다.
  5. RHI는 공통 언어고 백엔드는 번역기다. D3D12에서는 결국 descriptor와 CreateRenderTargetView 같은 실제 API로 내려간다.

이 다섯 개만 잡으면 다음 장 PSO가 훨씬 잘 읽힌다. PSO는 "어떤 셰이더와 상태로 그릴까"이고, 이 장은 "그 셰이더가 읽고 쓸 물건이 어디 있나"니까.

🎯 원리 한 줄 요약

RHI 리소스는 GPU 창고의 물건이고, 업로드는 CPU 배달이며, SRV/UAV/RTV는 같은 물건에 붙이는 읽기·쓰기·출력 라벨이다.
