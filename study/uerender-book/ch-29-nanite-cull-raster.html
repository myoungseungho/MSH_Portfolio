Nanite 컬링과 소프트웨어 래스터

언리얼 렌더링 · 29 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "Nanite가 보이는 클러스터를 GPU에서 고르고, 작은 삼각형은 컴퓨트 셰이더 소프트웨어 래스터 길로 직접 칠한다"는 흐름이 잡힌다.

왜 이걸 배워? — 문제의식부터

1. 네가 아는 것에서 출발하자. 서버에서 접속자 1만 명이 있다고 해보자. 모든 유저에게 모든 몬스터를 매 틱 전부 검사하지 않지? AOI로 먼저 줄이고, 보낼 패킷만 큐에 넣고, 어떤 건 배치하고, 어떤 건 바로 보낸다. 핵심은 "일단 후보를 줄이고, 남은 일을 맞는 처리 라인으로 보낸다"야.

2. 렌더링도 안 줄이면 터진다. Nanite 메시에는 삼각형이 너무 많아. 화면에 1픽셀도 안 되는 작은 삼각형까지 전통적인 고정 기능 래스터 길로 전부 밀면, 드로우콜 문제가 사라져도 다른 병목이 생긴다. 큰 삼각형은 하드웨어 래스터가 잘 먹히지만, 미세 삼각형은 컴퓨트 셰이더가 직접 처리하는 길이 더 맞을 때가 있어.

3. 그래서 답이 Nanite 컬링과 소프트웨어 래스터야. 언리얼은 GPU에서 인스턴스, 노드, 클러스터를 줄이고, 최종 visible 클러스터를 SW/HW 두 줄로 나눠. 여기서 "소프트웨어"는 CPU가 아니라 GPU 컴퓨트 셰이더야. 작은 삼각형을 GPU 안의 일반 계산 셰이더가 직접 픽셀 후보로 찍는 거지.

4. 왜 지금 배우냐. 앞 장 nanite-overview에서 Nanite가 클러스터 계층을 GPU 주도로 고른다는 큰 그림을 봤어. 이번 장은 그 다음 칸이야. 후보가 보이는 클러스터가 된 뒤, 그걸 어떤 래스터 길로 보내고, 실제로 어떻게 컴퓨트 디스패치까지 내려가는지 본다. 다음 장 lumen-overview로 가기 전에 현대 렌더러의 "GPU가 일감을 직접 배정한다"는 감각을 확실히 잡아야 해.

0. 비유부터 — 물류센터 자동 분류기

이번 장은 물류센터로 보자.

트럭에 상자가 산더미처럼 들어온다.

센터장이 사람 손으로 모든 상자를 열어 보며 분류하면 망해.

그래서 센터에는 자동 분류기가 있어.

  1. 먼저 안 보낼 상자는 버린다. 이게 컬링이야.
  2. 남은 상자는 큰 박스와 작은 봉투로 나눈다.
  3. 큰 박스는 컨베이어 벨트로 보낸다. 이게 하드웨어 래스터야.
  4. 작은 봉투는 빠른 분류 직원들이 직접 칸에 꽂는다. 이게 컴퓨트 셰이더 소프트웨어 래스터야.
  5. 두 줄의 결과는 같은 출고판에 모인다.

중요한 건 "소프트웨어"라는 단어에 속지 않는 거야.

여기서 직원은 CPU 직원이 아니야.

GPU 안에서 도는 컴퓨트 셰이더 직원이야.

Nanite는 트럭 안의 모든 삼각형을 CPU가 만지는 구조가 아니라, GPU 물류센터가 직접 후보를 줄이고 줄을 나누는 구조야.

🌱 이 개념은 왜 생겼나 — 래스터 스케줄러
• 원래 구조: 보이는 삼각형은 그냥 한 줄 컨베이어에 다 올리면 돼. GPU의 하드웨어 래스터가 알아서 픽셀로 바꿔 주는 구조야.
• 그런데 문제: Nanite 상자는 너무 잘게 쪼개져 있어. 1픽셀도 안 되는 작은 봉투까지 같은 컨베이어에 태우면, 큰 박스엔 빠른 설비가 작은 봉투 앞에서 버벅여.
• 그래서 필요한 것: 큰 박스는 HW 줄, 작은 봉투는 SW 줄로 보낼지 정하는 센터장 다이얼이 필요해. 그게 래스터 스케줄러야.

1. 먼저 스케줄러부터 — HW만 쓸지, SW도 쓸지

물류센터에 작은 봉투 분류 라인을 켤지 말지부터 정해야 해.

언리얼은 InitRasterContext에서 래스터 스케줄링을 정한다.

r.Nanite.ComputeRasterization이 켜져 있으면 컴퓨트 래스터를 쓸 수 있고, 플랫폼이 async compute까지 받쳐주면 HW와 SW를 겹쳐 돌릴 수도 있어.

반대로 이 옵션이 꺼지면 하드웨어 전용으로 강제한다.

NaniteCullRaster.cpp:6154

// Set rasterizer scheduling based on config and platform capabilities. if (CVarNaniteComputeRasterization.GetValueOnRenderThread() != 0) { bAsyncCompute = bAsyncCompute && GSupportsEfficientAsyncCompute && (CVarNaniteEnableAsyncRasterization.GetValueOnRenderThread() != 0) && EnumHasAnyFlags(GRHIMultiPipelineMergeableAccessMask, ERHIAccess::UAVMask) && !(bCustomPass && !UseAsyncComputeForCustomPass(ViewFamily)); RasterContext.RasterScheduling = bAsyncCompute ? ERasterScheduling::HardwareAndSoftwareOverlap : ERasterScheduling::HardwareThenSoftware; } else { // Force hardware-only rasterization. RasterContext.RasterScheduling = ERasterScheduling::HardwareOnly; }
🔤 기호 사전 — 래스터 스케줄러
• CVarNaniteComputeRasterization = Nanite 컴퓨트 래스터 라인을 켤지 보는 콘솔 변수.
• GetValueOnRenderThread() = 렌더 스레드에서 현재 설정값을 읽는다.
• bAsyncCompute = 그래픽 파이프와 컴퓨트 파이프를 겹쳐 돌릴 수 있는지의 깃발.
• && = 조건이 전부 맞아야 통과한다는 "그리고".
• EnumHasAnyFlags = 플래그 묶음 안에 원하는 기능이 하나라도 있는지 검사한다.
• ERasterScheduling::HardwareAndSoftwareOverlap = 큰 박스 컨베이어와 작은 봉투 분류를 겹쳐 돌리는 모드.
• ERasterScheduling::HardwareThenSoftware = 하드웨어 일을 먼저 하고, 그 다음 소프트웨어 래스터를 도는 모드.
• ERasterScheduling::HardwareOnly = 작은 봉투 라인을 닫고 컨베이어만 쓰는 모드.
🔁 이제 다시 보자. CVarNaniteComputeRasterization이 켜져 있으면 작은 봉투 라인을 열 수 있어. 거기에 async compute 조건까지 맞으면 HardwareAndSoftwareOverlap, 아니면 HardwareThenSoftware야. 옵션이 꺼지면 HardwareOnly로 고정된다. 즉 Nanite는 처음부터 HW/SW 두 라인을 스케줄러에 넣고 시작해.

이 코드에서 "소프트웨어"는 CPU 루프가 아니야.

이 장에서 계속 나오는 SW는 GPU 컴퓨트 파이프 쪽이야.

서버로 치면 메인 게임 루프가 다 하는 게 아니라, 워커 큐를 따로 열어 병렬로 처리하는 느낌에 더 가까워.

🌱 이 개념은 왜 생겼나 — 소프트웨어 래스터
• 원래 구조: 삼각형을 픽셀로 바꾸는 일은 GPU의 고정 기능 래스터 장치가 맡아. 우리는 draw만 던지고 컨베이어가 알아서 찍어.
• 그런데 문제: 아주 작은 삼각형이 화면에 먼지처럼 많아지면, 컨베이어에 올리고 내리는 준비 비용이 더 크게 느껴져. 작은 봉투를 큰 박스 설비에 태우는 셈이야.
• 그래서 필요한 것: GPU 컴퓨트 셰이더가 직접 작은 봉투를 집어 칸에 꽂는 길이 필요해. 고정 장치 대신 프로그램이 래스터를 하니까 소프트웨어 래스터라고 부르는 거야.

2. SW 라인의 정체 — FMicropolyRasterizeCS

작은 봉투 라인이 실제로 어떤 프로그램으로 도는지 보자.

FMicropolyRasterizeCS는 Nanite 소프트웨어 래스터용 material shader 클래스야.

컴파일 환경에 SOFTWARE_RASTER를 박고, 실제 엔트리 포인트는 NaniteRasterizer.usf의 MicropolyRasterize로 연결한다.

NaniteCullRaster.cpp:1737

static void ModifyCompilationEnvironment(const FMaterialShaderPermutationParameters& Parameters, FShaderCompilerEnvironment& OutEnvironment) { FPermutationDomain PermutationVector(Parameters.PermutationId); FNaniteMaterialShader::ModifyCompilationEnvironment(Parameters, OutEnvironment); OutEnvironment.SetDefine(TEXT("SOFTWARE_RASTER"), 1); OutEnvironment.SetDefine(TEXT("USE_ANALYTIC_DERIVATIVES"), 1); OutEnvironment.SetDefine(TEXT("NANITE_MULTI_VIEW"), 1); if (PermutationVector.Get<FPixelProgrammableDim>() || PermutationVector.Get<FTessellationDim>()) { OutEnvironment.SetDefine(TEXT("NANITE_VERT_REUSE_BATCH"), 1); } if (PermutationVector.Get<FPixelProgrammableDim>() || PermutationVector.Get<FTessellationDim>() || PermutationVector.Get<FVoxelsDim>()) { OutEnvironment.CompilerFlags.Add(CFLAG_Wave32); } if (PermutationVector.Get<FTessellationDim>()) { OutEnvironment.SetDefine(TEXT("VIRTUAL_TEXTURE_FORCE_BILINEAR_FILTERING"), 1); } OutEnvironment.CompilerFlags.Add(CFLAG_CheckForDerivativeOps); FVirtualShadowMapArray::SetShaderDefines(OutEnvironment); } void SetParameters(FRHIBatchedShaderParameters& BatchedParameters, const FViewInfo& View, const FMaterialRenderProxy* MaterialProxy, const FMaterial& Material) { FMaterialShader::SetViewParameters(BatchedParameters, View, View.ViewUniformBuffer); FMaterialShader::SetParameters(BatchedParameters, MaterialProxy, Material, View); } }; IMPLEMENT_MATERIAL_SHADER_TYPE(, FMicropolyRasterizeCS, TEXT("/Engine/Private/Nanite/NaniteRasterizer.usf"), TEXT("MicropolyRasterize"), SF_Compute);
🔤 기호 사전 — 소프트웨어 래스터 셰이더
• ModifyCompilationEnvironment = 셰이더를 컴파일할 때 켤 스위치를 넣는 함수.
• OutEnvironment.SetDefine = HLSL 쪽 #if에서 볼 수 있는 이름을 켠다.
• SOFTWARE_RASTER = 이 셰이더가 소프트웨어 래스터 길이라는 표시.
• CFLAG_Wave32 = GPU wave 크기 32를 요구하는 컴파일 플래그.
• CFLAG_CheckForDerivativeOps = derivative 연산 사용을 검사하라는 플래그.
• IMPLEMENT_MATERIAL_SHADER_TYPE = C++ 셰이더 클래스와 .usf 엔트리 포인트를 묶는 매크로.
• SF_Compute = 이 엔트리 포인트가 컴퓨트 셰이더로 돈다는 뜻.

여기서 중요한 줄은 둘이야.

SOFTWARE_RASTER가 켜지고, SF_Compute로 등록된다.

그러니까 작은 삼각형을 "CPU에서 소프트웨어 렌더링" 하는 게 아니다.

GPU 컴퓨트 셰이더가 고정 기능 래스터라이저 대신 픽셀 후보를 직접 쓰는 거야.

DirectX로 치면 IA/VS/RS/PS 고정 흐름만 생각하면 안 돼.

Compute Shader가 UAV에 직접 쓰는 길을 같이 떠올려야 한다.

3. 큰 흐름 — 컬링하고 바로 래스터한다

이제 물류센터 전체 흐름을 보자.

FRenderer는 먼저 래스터 패스에 쓸 셰이더와 자료를 준비하고, 그 다음 MainPass에서 컬링을 건 뒤 곧바로 래스터 패스를 붙인다.

two-pass occlusion이 켜져 있으면 PostPass에서도 같은 조합이 한 번 더 돈다.

아래 토막은 MainPass의 핵심이야.

NaniteCullRaster.cpp:6568

// No Occlusion Pass / Occlusion Main Pass { RDG_EVENT_SCOPE_CONDITIONAL(GraphBuilder, !Configuration.bTwoPassOcclusion, "NoOcclusionPass"); RDG_EVENT_SCOPE_CONDITIONAL(GraphBuilder, Configuration.bTwoPassOcclusion, "MainPass"); AddPass_InstanceHierarchyAndClusterCull( Configuration.bTwoPassOcclusion ? CULLING_PASS_OCCLUSION_MAIN : CULLING_PASS_NO_OCCLUSION ); MainPassBinning = AddPass_Rasterize( DispatchContext, SafeMainRasterizeArgsSWHW, VisiblePatches, VisiblePatchesMainArgs, SplitWorkQueue, OccludedPatches, true ); }
🔤 기호 사전 — MainPass 연결
• RDG_EVENT_SCOPE_CONDITIONAL = RDG 이벤트 이름을 조건에 따라 붙이는 디버그 표식.
• Configuration.bTwoPassOcclusion = 오클루전을 두 번에 나눠 검사할지 보는 깃발.
• AddPass_InstanceHierarchyAndClusterCull = 인스턴스, 계층 노드, 클러스터 후보를 줄이는 GPU 패스를 추가한다.
• CULLING_PASS_OCCLUSION_MAIN = two-pass일 때 첫 번째 오클루전 컬링 패스.
• CULLING_PASS_NO_OCCLUSION = previous HZB 없이 한 번에 가는 컬링 패스.
• AddPass_Rasterize = visible 클러스터를 HW/SW 래스터 패스로 보내는 함수.
• SafeMainRasterizeArgsSWHW = SW/HW 래스터 인자를 안전하게 정리한 버퍼.
🔁 이제 다시 보자. MainPass는 AddPass_InstanceHierarchyAndClusterCull로 안 보이는 상자를 버리고, 바로 AddPass_Rasterize로 남은 상자를 출고 라인에 올려. 컬링과 래스터가 따로 떨어진 장식이 아니라, RDG 그래프에서 바로 이어지는 두 단계야.

SafeMainRasterizeArgsSWHW라는 이름도 잘 봐.

끝의 SWHW가 이번 장의 핵심 힌트야.

하나의 패스 결과가 소프트웨어 래스터용 인자와 하드웨어 래스터용 인자를 같이 들고 간다.

🌱 이 개념은 왜 생겼나 — SW/HW visible 결과판
• 원래 구조: 컬링이 끝나면 "보이는 클러스터 목록" 하나만 만들고, CPU나 다음 단계가 다시 훑어서 어느 줄로 보낼지 나누면 돼.
• 그런데 문제: 보이는 상자가 수천, 수만 개면 다시 훑는 것도 일이야. 물류센터가 분류해 놓고 사무실에 다시 들고 가서 재분류하는 꼴이 돼.
• 그래서 필요한 것: 보인다고 판정하는 순간, SW 줄과 HW 줄의 자리까지 바로 잡는 결과판이 필요해. 그래서 OutVisibleClustersSWHW에 양쪽 끝에서 쌓는 거야.

4. visible 결과판 — SW는 앞에서, HW는 뒤에서 쌓는다

컬링 셰이더가 "이 클러스터는 보인다"라고 결정하면, 그 클러스터를 visible 목록에 넣어야 해.

그런데 이 목록은 두 팀이 같이 쓴다.

하드웨어 래스터 팀과 소프트웨어 래스터 팀.

언리얼은 같은 OutVisibleClustersSWHW 버퍼를 쓰되, HW 클러스터는 뒤쪽에서, SW 클러스터는 앞쪽에서 채운다.

NaniteClusterCulling.usf:709

void EmitVisibleCluster(bool bUseHWRaster, uint2 TotalPrevDrawClusters, uint HWClusterCounterIndex, FVisibleCluster VisibleCluster) { if (bUseHWRaster) { uint ClusterOffsetHW = 0; WaveInterlockedAddScalar_(VisibleClustersArgsSWHW[HWClusterCounterIndex], 1, ClusterOffsetHW); uint VisibleClusterOffsetHW = ClusterOffsetHW; VisibleClusterOffsetHW += TotalPrevDrawClusters.y; #if CULLING_PASS == CULLING_PASS_OCCLUSION_POST VisibleClusterOffsetHW += OffsetClustersArgsSWHW[HWClusterCounterIndex]; #endif if (VisibleClusterOffsetHW < MaxVisibleClusters) { StoreVisibleCluster(OutVisibleClustersSWHW, (MaxVisibleClusters - 1) - VisibleClusterOffsetHW, VisibleCluster, VIRTUAL_TEXTURE_TARGET); // HW clusters written from the top } } else { uint ClusterOffsetSW = 0; WaveInterlockedAddScalar_(VisibleClustersArgsSWHW[0], 1, ClusterOffsetSW); uint VisibleClusterOffsetSW = ClusterOffsetSW; VisibleClusterOffsetSW += TotalPrevDrawClusters.x; #if CULLING_PASS == CULLING_PASS_OCCLUSION_POST VisibleClusterOffsetSW += OffsetClustersArgsSWHW[0]; #endif if (VisibleClusterOffsetSW < MaxVisibleClusters) { StoreVisibleCluster(OutVisibleClustersSWHW, VisibleClusterOffsetSW, VisibleCluster, VIRTUAL_TEXTURE_TARGET); // SW clusters written from the bottom } } }
🔤 기호 사전 — SW/HW 결과판
• EmitVisibleCluster = 보이는 클러스터를 결과판에 넣는 함수.
• bUseHWRaster = 이 클러스터를 하드웨어 래스터 길로 보낼지의 깃발.
• WaveInterlockedAddScalar_ = GPU 스레드들이 동시에 카운터를 올려도 충돌하지 않게 하는 원자 덧셈.
• VisibleClustersArgsSWHW = SW/HW 각각 몇 개가 쌓였는지 세는 인자 버퍼.
• HWClusterCounterIndex = HW 쪽 카운터가 있는 칸.
• StoreVisibleCluster = visible 클러스터 정보를 버퍼에 쓴다.
• top / bottom = 주석 그대로, HW는 위쪽 끝에서, SW는 아래쪽 시작에서 쌓는다.
🔁 이제 다시 보자. 하드웨어 팀은 MaxVisibleClusters - 1 쪽에서 내려오고, 소프트웨어 팀은 0번 쪽에서 올라가. 둘이 같은 창고를 쓰지만 서로 다른 문으로 들어와서 충돌을 줄이는 거야. CPU가 배열을 정리해서 넘기는 게 아니라, GPU wave가 카운터를 올리고 자기 자리를 직접 잡는다.

서버식으로 보면 atomic counter로 결과 슬롯을 잡는 구조야.

락 하나 잡고 전체 배열을 정렬하는 그림이 아니다.

그래서 Nanite의 컬링 결과는 그냥 "보이는 것 목록"이 아니라, 이미 다음 래스터 라인까지 생각한 목록이야.

5. 래스터 패스 — 큰 박스는 HW, 작은 봉투는 SW

이제 visible 결과판을 실제 출고 라인으로 보낸다.

AddPass_Rasterize 안에는 하드웨어 래스터 패스와 소프트웨어 래스터 패스가 둘 다 보인다.

하드웨어는 DispatchHW, 소프트웨어는 DispatchSW야.

스케줄이 HardwareOnly가 아니면 SW triangle pass가 RDG에 추가된다.

NaniteCullRaster.cpp:5781

FRDGPass* HWTrianglesPass = GraphBuilder.AddPass( RDG_EVENT_NAME("HW Rasterize (Triangles)"), ClusterPassParameters, ERDGPassFlags::Raster | ERDGPassFlags::SkipRenderPass, [ClusterPassParameters, &DispatchContext, ViewRect, &SceneView = SceneView, bMainPass, HardwarePath, PSOCollectorIndex, RenderFlags = RenderFlags](FRDGAsyncTask, FRHICommandList& RHICmdList) { DispatchContext.DispatchHW( RHICmdList, DispatchContext.Dispatches_HW_Triangles, SceneView, ViewRect, HardwarePath, PSOCollectorIndex, *ClusterPassParameters ); } ); GraphBuilder.SetPassWorkload(HWTrianglesPass, PassWorkload); if (Scheduling != ERasterScheduling::HardwareOnly) { FRDGPass* SWTrianglesPass = GraphBuilder.AddPass( RDG_EVENT_NAME("SW Rasterize (Triangles)"), ClusterPassParameters, AsyncComputeFlag, [ClusterPassParameters, &DispatchContext, &SceneView = SceneView, RenderFlags = RenderFlags, PSOCollectorIndex](FRDGAsyncTask, FRHIComputeCommandList& RHICmdList) { DispatchContext.DispatchSW( RHICmdList, DispatchContext.Dispatches_SW_Triangles, SceneView, PSOCollectorIndex, *ClusterPassParameters, false /* Patches */ ); } ); GraphBuilder.SetPassWorkload(SWTrianglesPass, PassWorkload); }
🔤 기호 사전 — 래스터 패스 두 줄
• GraphBuilder.AddPass = RDG 그래프에 실행할 작업 하나를 올린다.
• RDG_EVENT_NAME("HW Rasterize (Triangles)") = GPU 디버거에서 보일 하드웨어 래스터 패스 이름.
• ERDGPassFlags::Raster = 그래픽 래스터 파이프를 쓰는 패스라는 표시.
• DispatchContext.DispatchHW = HW 래스터 목록을 실제 draw/mesh shader 길로 보낸다.
• Scheduling != ERasterScheduling::HardwareOnly = 하드웨어 전용이 아니면 SW 패스도 추가한다.
• AsyncComputeFlag = SW 패스를 async compute로 돌릴지, 일반 compute로 돌릴지 정한 플래그.
• FRHIComputeCommandList = 컴퓨트 명령을 기록하는 RHI 커맨드 리스트.
• DispatchContext.DispatchSW = SW 래스터 목록을 컴퓨트 셰이더 길로 보낸다.
🔁 이제 다시 보자. 같은 ClusterPassParameters를 들고 HW 패스와 SW 패스가 나뉜다. HW는 ERDGPassFlags::Raster와 DispatchHW, SW는 AsyncComputeFlag와 DispatchSW야. 물류센터로 치면 큰 박스 컨베이어와 작은 봉투 분류대가 같은 출고 지시서를 보고 각자 자기 줄을 처리하는 장면이다.

여기서 "작은 삼각형"을 누가 작은지 판단했냐는 앞 단계의 일이다.

컬링/비닝 셰이더가 visible 목록과 인자 버퍼를 만들어 놨고, AddPass_Rasterize는 그 결과를 실제 실행 라인에 꽂는다.

그래서 Nanite를 읽을 때는 Cull과 Raster를 따로 외우면 안 돼.

컬링 결과가 래스터 인자로 바로 이어진다.

🌱 이 개념은 왜 생겼나 — 간접 컴퓨트 디스패치
• 원래 구조: CPU가 "이번엔 클러스터 183개니까 컴퓨트 그룹 몇 개" 하고 세어서 GPU에 실행 수를 넣어 주면 돼.
• 그런데 문제: Nanite는 GPU가 이미 컬링하고 비닝했어. 그걸 CPU가 다시 읽어 오면 왕복 시간이 생기고, 물류센터 자동 분류기를 멈춰 세우는 꼴이야.
• 그래서 필요한 것: GPU가 만든 실행 인자를 GPU가 바로 먹는 방식이 필요해. CPU가 직접 숫자를 넣지 않아서 indirect, 그래서 간접 컴퓨트 디스패치야.

6. SW 라인의 마지막 — 간접 컴퓨트 디스패치

마지막으로 DispatchSW 안쪽을 보자.

여기서 진짜로 컴퓨트 셰이더 RHI를 잡고, 파라미터를 묶고, indirect compute dispatch를 날린다.

이게 "작은 삼각형은 컴퓨트 셰이더로 직접 칠한다"의 C++ 쪽 끝단이야.

NaniteCullRaster.cpp:3578

Parameters.PassData = FUintVector4(RasterizerPass.RasterBin, 0u, 0u, 0u); const TShaderRef<FMicropolyRasterizeCS>* ComputeShader = bPatches ? &RasterizerPass.PatchComputeShader : &RasterizerPass.ClusterComputeShader; FRHIBuffer* IndirectArgsBuffer = Parameters.IndirectArgs->GetIndirectRHICallBuffer(); FRHIComputeShader* ShaderRHI = ComputeShader->GetComputeShader(); // TODO: Implement support for testing precache and skipping if needed FComputeShaderUtils::ValidateIndirectArgsBuffer(IndirectArgsBuffer->GetSize(), RasterizerPass.IndirectOffset); SetComputePipelineState(RHICmdList, ShaderRHI); #if PSO_PRECACHING_VALIDATE EPSOPrecacheResult PSOPrecacheResult = PipelineStateCache::CheckPipelineStateInCache(ShaderRHI); PSOCollectorStats::CheckComputePipelineStateInCache(*ShaderRHI, PSOPrecacheResult, RasterizerPass.ComputeMaterialProxy, PSOCollectorIndex); #endif if (GRHISupportsShaderRootConstants) { RHICmdList.SetComputeShaderRootConstants(Parameters.PassData); } SetShaderParametersMixedCS( RHICmdList, *ComputeShader, Parameters, ViewInfo, RasterizerPass.ComputeMaterialProxy, *RasterizerPass.ComputeMaterial ); RHICmdList.DispatchIndirectComputeShader(IndirectArgsBuffer, RasterizerPass.IndirectOffset);
🔤 기호 사전 — 컴퓨트 디스패치 끝단
• Parameters.PassData = 이번 패스가 어떤 raster bin을 처리하는지 넘기는 작은 상자.
• TShaderRef<FMicropolyRasterizeCS> = 소프트웨어 래스터 컴퓨트 셰이더를 가리키는 참조.
• bPatches ? ... : ... = 패치 래스터면 patch shader, 아니면 cluster shader를 고르는 짧은 if.
• IndirectArgsBuffer = GPU가 만들어 둔 실행 인자 버퍼. 몇 그룹을 돌릴지 여기에 있다.
• FRHIComputeShader = RHI가 보는 컴퓨트 셰이더 핸들.
• SetComputePipelineState = 지금부터 이 컴퓨트 셰이더를 실행할 준비를 한다.
• SetShaderParametersMixedCS = 셰이더가 읽을 버퍼, 머티리얼, 뷰 정보를 바인딩한다.
• DispatchIndirectComputeShader = CPU가 그룹 수를 직접 넣지 않고, GPU 버퍼에 적힌 인자로 컴퓨트 셰이더를 실행한다.
🔁 이제 다시 보자. FMicropolyRasterizeCS를 고르고, IndirectArgsBuffer를 꺼내고, compute pipeline을 맞춘 뒤, DispatchIndirectComputeShader로 실행한다. 그룹 수는 CPU가 다시 세지 않아. 앞 단계 GPU 컬링/비닝이 써 둔 인자를 보고 GPU가 자기 일을 이어서 한다.

이 줄이 중요해.

CPU가 "클러스터가 183개니까 x=3 그룹" 하고 계산해서 직접 넣는 그림이 아니야.

GPU가 만든 indirect args를 GPU가 다시 소비한다.

서버로 치면 워커가 만든 큐 길이를 메인 스레드가 매번 풀스캔하지 않고, 다음 워커 단계가 그 큐 메타데이터를 그대로 읽는 구조야.

그래서 Nanite는 GPU-driven이라고 부를 만해.

7. 소프트웨어 래스터가 실제로 칠하는 방식

FMicropolyRasterizeCS의 엔트리 포인트는 NaniteRasterizer.usf의 MicropolyRasterize야.

그 안쪽에서는 클러스터 래스터와 패치 래스터로 갈라지고, 클러스터 쪽은 삼각형을 만들고 RasterizeTri_Adaptive 같은 소프트웨어 래스터 함수를 부른다.

이 장에서는 C++ 경로가 목표라 셰이더 내부를 깊게 파지는 않을게.

그래도 감은 잡자.

고정 기능 rasterizer가 삼각형을 픽셀로 바꾸는 대신, compute shader 코드가 삼각형 범위를 훑고 UAV에 depth/visibility 값을 써 넣는 구조야.

물류센터 비유로 돌아가면 이렇다.

컨베이어 벨트는 박스를 자동으로 스캔해서 출고한다.

작은 봉투 라인은 직원들이 봉투 하나씩 집어서 칸에 직접 꽂는다.

둘 다 GPU 안에서 일하지만, 쓰는 길이 다르다.

Nanite는 이 두 길을 같은 프레임 안에 같이 쓴다.

콜/데이터 흐름 한눈에

FRenderer::Draw / Raster 준비 -> InitRasterContext (NaniteCullRaster.cpp:6121) RasterScheduling = HardwareOnly / HardwareThenSoftware / HardwareAndSoftwareOverlap -> PrepareRasterizerPasses (NaniteCullRaster.cpp:6543) Raster bin별 HW shader / SW compute shader 준비 -> AddPass_InstanceHierarchyAndClusterCull (NaniteCullRaster.cpp:6573) InstanceCull -> NodeCull -> ClusterCull EmitVisibleCluster (NaniteClusterCulling.usf:709) SW cluster: OutVisibleClustersSWHW 앞쪽 HW cluster: OutVisibleClustersSWHW 뒤쪽 -> AddPass_Rasterize (NaniteCullRaster.cpp:6575) HWTrianglesPass -> DispatchHW SWTrianglesPass -> DispatchSW -> DispatchSW (NaniteCullRaster.cpp:3578) FMicropolyRasterizeCS DispatchIndirectComputeShader -> NaniteRasterizer.usf / MicropolyRasterize Cluster/Patch를 compute shader로 rasterize

이 흐름에서 CPU가 하는 일은 "물류센터 설비를 RDG에 등록"하는 쪽이야.

어떤 상자가 보이는지, 몇 개를 어느 줄로 보낼지는 GPU 버퍼와 셰이더가 계속 이어받는다.

우리 서버·DirectX 랑 비교

우리 서버의 AOI와 비교하면 꽤 닮았어.

AOI 후보를 줄이고, 보낼 패킷을 큐에 쌓고, 큐 길이에 따라 워커가 처리하지.

Nanite도 인스턴스/노드/클러스터 후보를 줄이고, visible 클러스터를 OutVisibleClustersSWHW에 쌓고, SW/HW 인자 버퍼로 다음 패스를 돌린다.

차이는 실행 위치야.

서버는 CPU 스레드와 락, 큐가 중심이지만, Nanite는 GPU wave, UAV, indirect args가 중심이야.

DirectX 기본 파이프라인과 비교하면 더 선명해.

전통 흐름은 draw call이 정점 셰이더를 지나 고정 기능 래스터라이저로 간다.

Nanite HW 라인은 그 감각과 가까워.

하지만 SW 라인은 compute shader가 직접 raster work를 먹는다.

그래서 ERDGPassFlags::Raster와 FRHIComputeCommandList가 한 함수 안에 같이 보이는 거야.

큰 박스 컨베이어와 작은 봉투 분류대가 같은 출고판을 쓰는 셈이지.

이 챕터에서 딱 이것만

  1. Nanite의 "software raster"는 CPU 렌더러가 아니라 GPU 컴퓨트 셰이더 길이다.
  2. InitRasterContext가 HW only, HW then SW, HW/SW overlap 스케줄을 정한다.
  3. 컬링 셰이더는 visible 클러스터를 OutVisibleClustersSWHW에 SW/HW 양쪽으로 나눠 쌓는다.
  4. AddPass_Rasterize는 HW triangle pass와 SW triangle pass를 RDG에 같이 올린다.
  5. SW 패스 끝은 FMicropolyRasterizeCS와 DispatchIndirectComputeShader다.

이 다섯 개면 이번 장은 통과야.

작은 삼각형을 왜 따로 보내는지, 그 길이 어디서 켜지고 어디서 실행되는지 설명할 수 있어야 해.

🎯 원리 한 줄 요약

Nanite는 GPU에서 visible 클러스터를 고른 뒤, 큰 삼각형은 하드웨어 래스터 길로, 작은 삼각형은 FMicropolyRasterizeCS 컴퓨트 셰이더 길로 보내 같은 visibility/depth 결과판을 채우는 GPU 주도 물류센터다.
