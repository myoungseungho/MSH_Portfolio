PrePass — 깊이부터 그리는 이유

언리얼 렌더링 · 19 / 36

대상 독자: 게임 서버는 아는, 렌더링은 처음 보는 사람.
이 챕터가 끝나면 "PrePass가 왜 색칠보다 먼저 깊이만 그리는지"가 머릿속에 잡힘.
🧱 먼저 알아야 할 것 — 화면 한 칸의 색을 정하는 작은 계산
• 화면 = 아주 많은 작은 칸: 화면은 가로세로로 촘촘히 나뉜 수백만 개의 작은 칸으로 되어 있어.
• 칸마다 작은 계산이 한 번씩 돈다(픽셀 셰이더): 각 칸의 색을 정하려고 GPU가 작은 계산을 칸마다 한 번씩 돌려. 칸이 수백만이면 그 계산도 수백만 번이야.
• 그 계산은 은근히 무겁다: 한 칸 색을 정하려고 그림 조각을 여러 장 들춰보고 이것저것 따져. 그래서 어차피 가려져 안 보일 칸까지 계산하면 그만큼 통째로 헛일이 돼.
이게 잡히면 아래 "왜 색칠 전에 깊이부터 그리나" 이야기가 얹힌다.

왜 이걸 배워? — 문제의식부터

너가 DirectX로 큐브 여러 개를 그려 봤다고 치자. 삼각형을 보내고, 버텍스 셰이더가 돌고, 픽셀 셰이더가 색을 계산해서 화면에 찍는다. 여기까지는 자연스러워. 그런데 실제 게임 화면은 큐브 몇 개가 아니야. 벽, 캐릭터, 나무, 풀, 무기, 이펙트, 건물 조각이 한 픽셀 위에 여러 번 겹쳐.

문제는 뒤에 가려져서 어차피 안 보일 픽셀도 픽셀 셰이더를 태울 수 있다는 거야. 픽셀 셰이더는 싸지 않아. 텍스처를 여러 장 읽고, 노멀을 풀고, 머티리얼 분기를 타고, GBuffer 여러 장에 값을 써. 화면에 보이는 건 맨 앞 표면 하나인데, 뒤쪽 표면 5개가 먼저 비싼 계산을 끝내고 나중에 깊이 테스트에서 버려지면 낭비야.

우리도 같은 문제를 많이 만나. 서버에서 CM_ATTACK 하나가 왔을 때, 대상이 죽었는지, 거리가 맞는지, 맵이 같은지 확인도 안 하고 비싼 스킬 공식, DB 기록, 드랍 계산부터 돌리면 손해야. 먼저 싼 검사로 "이 요청은 처리 대상인가?"를 걸러야 해. 렌더링에서 그 싼 검사의 대표가 깊이 버퍼고, 그걸 색칠보다 먼저 채워 두는 패스가 PrePass / Early-Z pass야.

그래서 지금 배우는 건 "그림을 두 번 그리네?"가 아니야. 비싼 색칠을 줄이기 위해, 싼 깊이 번호표를 먼저 붙이는 방법이야. 이번 흐름은 deferred-overview 다음, basepass-gbuffer 바로 앞에 놓여. PrePass가 깊이 장부를 먼저 만들고, BasePass는 그 장부를 보고 진짜 보이는 픽셀 위주로 GBuffer를 채운다.

0. 비유부터 — 색칠하기 전에 앞자리 번호표 붙이기

도화지에 종이 인형을 여러 겹 붙이고 색칠한다고 해 보자. 앞에는 기사, 그 뒤에는 나무, 더 뒤에는 성벽이 있어. 선생님이 "모든 종이 인형을 예쁘게 색칠해"라고 하면 뒤에 가려진 성벽까지 열심히 색칠할 수 있어. 하지만 완성된 그림에서는 기사 뒤의 성벽이 안 보여.

똑똑한 방법은 이거야. 먼저 색칠하지 말고, 도화지 칸마다 제일 앞에 있는 종이가 몇 번째 깊이인지 숫자만 적어. 예를 들어 어떤 칸에는 기사 깊이 3, 다른 칸에는 나무 깊이 7, 하늘 칸에는 아무것도 없음. 이 숫자 장부가 깊이 버퍼야.

그다음 진짜 색칠을 시작해. 성벽을 색칠하려고 어떤 칸에 갔는데, 이미 깊이 장부에 "여기는 기사 깊이 3이 제일 앞"이라고 적혀 있어. 성벽 깊이 10은 뒤쪽이지. 그러면 물감도 안 묻히고 지나가. 이게 Early-Z 감각이야. 픽셀 셰이더라는 비싼 색칠공을 부르기 전에, 깊이 문지기가 먼저 잘라내는 것.

이번 챕터의 비유는 끝까지 이걸로 간다. PrePass는 연필로 앞자리 번호표만 적는 시간. SceneDepthTexture는 칸마다 적힌 깊이 장부. BasePass는 물감으로 진짜 색칠하는 시간. Early-Z는 장부 보고 뒤쪽이면 색칠공을 돌려보내는 문지기야.

🌱 이 개념은 왜 생겼나 — Early-Z 모드(EDepthDrawingMode)
• 원래 구조: 번호표를 붙일 거면 그냥 모든 종이 인형에 다 붙이면 쉬워 보여.
• 그런데 문제: 작은 풀잎 5만 개까지 먼저 훑으면, 물감 아끼려다 연필 시간이 더 비싸질 수 있어.
• 그래서 필요한 것: "안 함/가림막만/불투명 전부"처럼 번호표 범위를 고르는 손잡이가 필요해. 그 선택지 묶음이 EDepthDrawingMode야.

1. 먼저 모드부터 보자 — 깊이를 얼마나 먼저 그릴 건가

PrePass는 항상 같은 양을 그리지 않아. 어떤 프로젝트는 아예 안 할 수 있고, 어떤 경우는 불투명 전체를 다 그리고, 어떤 경우는 가림막 역할을 하는 물체만 그려. 언리얼은 이 결정을 EDepthDrawingMode로 들고 있어.

DepthRendering.h:20

enum EDepthDrawingMode { // tested at a higher level DDM_None = 0, // Opaque materials only DDM_NonMaskedOnly = 1, // Opaque and masked materials, but no objects with bUseAsOccluder disabled DDM_AllOccluders = 2, // Full prepass, every object must be drawn and every pixel must match the base pass depth DDM_AllOpaque = 3, // Masked materials only DDM_MaskedOnly = 4, // Full prepass, every object must be drawn and every pixel must match the base pass depth, except dynamic geometry which will render in the Velocity pass DDM_AllOpaqueNoVelocity = 5, };
🔤 기호 사전 — 깊이 모드 표
• enum = 정해진 선택지 목록. "이 중 하나만 골라" 상자야.
• EDepthDrawingMode = 깊이 먼저 그리기를 어떤 방식으로 할지 정하는 이름.
• DDM_None = 깊이 먼저 그리기를 안 함.
• DDM_AllOccluders = 가림막으로 쓸 수 있는 물체 위주로 먼저 그림.
• DDM_AllOpaque = 불투명 물체 전체를 먼저 깊이에 그림.
• DDM_MaskedOnly = 잎사귀, 철망처럼 구멍이 있는 마스크 재질만 먼저 그림.
• DDM_AllOpaqueNoVelocity = 대부분은 먼저 깊이에 그리고, 속도 패스가 맡을 동적 물체는 남김.
🔁 이제 다시 보자.
DDM_None이면 번호표 붙이기 시간이 없어.
DDM_AllOpaque면 불투명 종이 인형은 거의 다 먼저 번호표를 붙여.
DDM_AllOccluders는 "뒤를 많이 가리는 큰 물체만 먼저 하자"는 절충이야.
즉 PrePass는 한 가지 버튼이 아니라, 비용과 절약을 맞추는 손잡이야.

이 모드가 중요한 이유는 간단해. PrePass도 공짜는 아니거든. 깊이만 쓴다고 해도 버텍스는 돌고, 래스터라이즈도 하고, 드로우 명령도 쌓아야 해. 작은 소품이 많고 픽셀 셰이더가 가벼우면 깊이만 먼저 한 번 더 그리는 비용이 더 클 수 있어. 반대로 벽, 산, 건물처럼 큰 가림막이 많고 머티리얼이 비싸면 PrePass가 크게 이긴다. 서버로 치면 모든 패킷에 대해 사전 검사를 엄청 많이 넣으면 검사 자체가 병목이 될 수 있는 것과 같아.

🌱 이 개념은 왜 생겼나 — SceneDepthTexture와 HiZ
• 원래 구조: 칸마다 제일 앞 깊이 하나만 적은 장부만 있으면 BasePass가 뒤쪽 픽셀을 버릴 수 있어.
• 그런데 문제: 멀리 있는 건물 하나가 화면 800x600칸을 전부 가리는지 매번 작은 칸으로만 보면, 큰 물체 검사도 너무 잘게 쪼개져.
• 그래서 필요한 것: 먼저 만든 깊이 장부를 텍스처로 들고 있고, 큰 칸부터 작은 칸까지 묶어 본 요약본이 필요해. 장면 깊이 장부가 SceneDepthTexture, 계단식 요약 장부가 HiZ야.

2. 프레임 본줄에서 PrePass가 진짜 BasePass 앞에 온다

DeferredShadingRenderer의 큰 흐름 안에서 먼저 ShouldRenderPrePass()로 필요 여부를 잡고, 깊이 버퍼를 지운 뒤, PrePass를 호출한다. 주석도 아주 직접적이야. scene pre-pass / early z pass라고 부른다.

DeferredShadingRenderer.cpp:2378

const ERenderTargetLoadAction DepthLoadAction = ERenderTargetLoadAction::EClear; AddClearDepthStencilPass(GraphBuilder, LocalSceneTextures.Depth.Target, DepthLoadAction, StencilLoadAction); // Draw the scene pre-pass / early z pass, populating the scene depth buffer and HiZ if (bNeedsPrePass) { RenderPrePass(GraphBuilder, InViews, LocalSceneTextures.Depth.Target, InstanceCullingManager, &FirstStageDepthBuffer); }
🔤 기호 사전 — 프레임 안의 호출 지점
• ERenderTargetLoadAction::EClear = 예전 내용을 버리고 깨끗이 지운다는 뜻.
• AddClearDepthStencilPass = 깊이/스텐실 장부를 먼저 비우는 RDG 패스.
• LocalSceneTextures.Depth.Target = 이번 장면의 깊이 장부 텍스처.
• bNeedsPrePass = PrePass가 필요한지 나타내는 참/거짓 값.
• RenderPrePass(...) = 실제 번호표 붙이기 시간을 실행하는 함수.
• &FirstStageDepthBuffer = 첫 번째 깊이 결과를 함수가 바꿔서 돌려줄 수 있게 주소를 넘김.
🔁 이제 다시 보자.
먼저 AddClearDepthStencilPass로 깊이 장부를 빈 종이로 만든다.
그다음 bNeedsPrePass가 참이면 RenderPrePass가 장면을 한 번 훑으며 깊이 값을 채워.
주석의 populating the scene depth buffer and HiZ가 핵심이야.
"색을 칠한다"가 아니라 "깊이 버퍼와 HiZ를 채운다"라고 쓰여 있지.

그럼 bNeedsPrePass는 누가 정하냐. Deferred renderer 쪽은 아주 짧게 답한다.

DeferredShadingRenderer.cpp:474

bool FDeferredShadingSceneRenderer::ShouldRenderPrePass() const { return (DepthPass.EarlyZPassMode != DDM_None || DepthPass.bEarlyZPassMovable != 0); }
🔤 기호 사전 — 실행 여부 판단
• bool = 참/거짓을 돌려주는 함수.
• const = 이 함수가 렌더러 상태를 바꾸지 않는다는 약속.
• return = 이 값을 함수 결과로 돌려줘.
• DepthPass.EarlyZPassMode != DDM_None = Early-Z 모드가 "안 함"이 아니면 필요함.
• || = 또는.
• DepthPass.bEarlyZPassMovable != 0 = 움직이는 물체도 Early-Z에 포함해야 하면 필요함.

판단은 복잡하지 않아. EarlyZPassMode가 DDM_None이 아니거나, movable까지 Early-Z에 넣어야 하면 PrePass를 돈다. 즉 "번호표 붙이기 모드가 켜져 있냐"를 묻는 문장이라고 보면 돼.

🌱 이 개념은 왜 생겼나 — 색상 쓰기 끄기(CW_NONE)
• 원래 구조: 메시를 그리면 당연히 화면 색도 쓰고 깊이도 쓰는 한 묶음처럼 느껴져.
• 그런데 문제: PrePass에서 물감까지 칠하면 같은 종이 인형을 두 번 색칠하는 꼴이야. BasePass의 비싼 색칠을 줄이려던 목표가 깨져.
• 그래서 필요한 것: "지금은 물감 금지, 번호표만 적어"라는 상태가 필요해. CW_NONE은 Color Write None, 색상 쓰기 없음이라는 표지야.

3. PrePass는 색을 안 쓴다 — 깊이만 쓰는 상태로 잠근다

PrePass가 BasePass처럼 색을 찍는다면 의미가 없어. 비싼 색칠을 줄이려고 하는데 이미 색칠을 해 버리면 헛수고잖아. 그래서 깊이 패스 상태는 색상 쓰기를 꺼 둔다.

DepthRendering.cpp:516

void SetupDepthPassState(FMeshPassProcessorRenderState& DrawRenderState) { // Disable color writes, enable depth tests and writes. DrawRenderState.SetBlendState(TStaticBlendState<CW_NONE>::GetRHI()); DrawRenderState.SetDepthStencilState(TStaticDepthStencilState<true, CF_DepthNearOrEqual>::GetRHI()); }
🔤 기호 사전 — 색 없이 깊이만 쓰기
• void = 값을 돌려주지 않고 상태만 세팅하는 함수.
• FMeshPassProcessorRenderState& = 메시 패스가 쓸 렌더 상태 묶음. &라서 원본을 바꾼다.
• SetBlendState = 색을 어떻게 섞고 쓸지 정하는 상태.
• TStaticBlendState<CW_NONE> = Color Write None. 색상 채널에 쓰지 말라는 뜻.
• SetDepthStencilState = 깊이/스텐실 테스트와 쓰기 상태를 정함.
• CF_DepthNearOrEqual = 더 가까우거나 같은 깊이면 통과하는 비교 방식.
• GetRHI() = 실제 그래픽 API 쪽에서 쓸 상태 객체를 꺼내는 호출.
🔁 이제 다시 보자.
CW_NONE이 "물감 금지"야.
대신 SetDepthStencilState(...true...)로 깊이 장부 쓰기는 켠다.
그러니까 PrePass는 화면 색을 만드는 시간이 아니라,
칸마다 앞자리 깊이 번호만 적는 시간이야.

색을 안 쓴다는 건 단순한 최적화가 아니야. 의도 자체가 달라. BasePass는 픽셀 셰이더에서 머티리얼 값을 계산하고 GBuffer에 여러 장을 쓴다. PrePass는 "이 픽셀이 앞에 있냐"만 중요해. 그래서 가능하면 위치만 쓰는 버텍스 경로, 기본 머티리얼, 픽셀 셰이더 생략 같은 길을 타려고 한다.

4. 실제 RenderPrePass — 깊이 패스를 돌리고 필요하면 2단계도 한다

이제 RenderPrePass 본체의 핵심을 보자. 함수 앞쪽에는 병렬 경로와 뷰별 패스 생성이 길게 있지만, 결정적인 끝부분은 짧다. EarlyZPassMode가 꺼져 있지 않으면 DepthPass를 그리고, 필요하면 첫 단계 깊이 버퍼를 복사한 뒤 SecondStageDepthPass를 한 번 더 돈다.

DepthRendering.cpp:631

// Draw a depth pass to avoid overdraw in the other passes. if (DepthPass.EarlyZPassMode != DDM_None) { // Render primary depth pass. RenderDepthPass(EMeshPass::DepthPass); // Evaluate if any second stage depth buffer processing is required bool bUsesSecondStageDepthPass = false; for (int32 ViewIndex = 0; ViewIndex < InViews.Num(); ++ViewIndex) { FViewInfo& View = InViews[ViewIndex]; bUsesSecondStageDepthPass |= View.bUsesSecondStageDepthPass; } // Copy depth buffer and render secondary depth pass if needed. if(bUsesSecondStageDepthPass) { FRDGTextureDesc FirstStageDepthBufferDesc = FRDGTextureDesc::Create2D(SceneDepthTexture->Desc.Extent, PF_DepthStencil, FClearValueBinding::DepthFar, TexCreate_DepthStencilTargetable | TexCreate_ShaderResource); *FirstStageDepthBuffer = GraphBuilder.CreateTexture(FirstStageDepthBufferDesc, TEXT("FirstStageDepthBuffer")); for (int32 ViewIndex = 0; ViewIndex < InViews.Num(); ++ViewIndex) { FViewInfo& View = InViews[ViewIndex]; if (View.bUsesSecondStageDepthPass) { DepthCopy::AddViewDepthCopyPSPass(GraphBuilder, View, SceneDepthTexture, *FirstStageDepthBuffer); } } // Dispatch and render the meshes RenderDepthPass(EMeshPass::SecondStageDepthPass); } }
🔤 기호 사전 — PrePass 본체
• // Draw a depth pass to avoid overdraw... = 다른 패스의 overdraw를 피하려고 깊이를 먼저 그린다는 주석.
• DepthPass.EarlyZPassMode != DDM_None = Early-Z 모드가 켜져 있는지 확인.
• RenderDepthPass(EMeshPass::DepthPass) = 기본 깊이 패스를 실행.
• bUsesSecondStageDepthPass = 두 번째 단계 깊이 패스가 필요한 뷰가 하나라도 있는지 모으는 bool.
• |= = 기존 값과 새 값을 OR로 합쳐서 다시 저장.
• FRDGTextureDesc::Create2D = 2D 텍스처 설명서를 만듦.
• PF_DepthStencil = 깊이/스텐실 용도 포맷.
• DepthCopy::AddViewDepthCopyPSPass = 현재 깊이를 첫 단계 깊이 버퍼로 복사하는 패스 추가.

🌱 이 개념은 왜 생겼나 — Position-only 깊이 경로
• 원래 구조: 번호표를 붙일 때도 원래 머티리얼을 다 읽고, 잎 무늬나 금속 값까지 들고 오면 확실하긴 해.
• 그런데 문제: 꽉 막힌 벽은 색종이 무늬가 뭐든 깊이는 외곽 위치로 정해져. 그런 벽 1만 개에 텍스처 준비까지 시키면 연필 작업이 물감 작업처럼 무거워져.
• 그래서 필요한 것: 깊이에 필요한 위치만 읽는 가벼운 길이 필요해. 그래서 bPositionOnly, bUseDefaultMaterial 같은 선택지가 생겨. 단, 구멍 있는 마스크 재질은 WritesEveryPixel로 따로 봐야 해.

5. 어떤 메시가 번호표 붙이기에 들어가나

PrePass가 켜졌다고 모든 메시가 무조건 들어오는 건 아니야. 투명 재질은 보통 깊이 장부 하나로 간단히 처리하기 어렵고, 마스크 재질은 구멍 때문에 픽셀 셰이더가 필요할 수 있고, 움직이는 물체는 velocity 패스와 역할을 나눌 수 있어.

FDepthPassMeshProcessor::ShouldRender는 재질과 모드를 보고 "이 메시를 깊이 패스에 넣을까?"를 판단한다. 또 가능하면 기본 머티리얼과 position-only 경로를 쓰려고 한다. 색칠을 안 할 거니까, 진짜 머티리얼을 다 들고 올 필요가 없을 때가 많기 때문이야.

마스크 재질은 조심해야 해. 나뭇잎 텍스처를 떠올려 봐. 사각형 폴리곤은 크지만, 알파 마스크 때문에 실제 잎사귀 부분만 보이고 나머지는 구멍이야. 이걸 그냥 위치만 보고 깊이에 꽉 채우면, 잎사귀 사이 구멍까지 막힌 것으로 기록된다. 그러면 BasePass에서 뒤쪽 물체가 잘못 사라질 수 있어. 그래서 Material.WritesEveryPixel과 DDM_MaskedOnly 같은 조건이 들어간다.

서버로 치면 "대상 ID가 존재한다"만으로 공격 성공 처리하면 안 되는 상황과 같아. 스텔스인지, 무적 상태인지, 맵 이동 중인지 같은 조건이 있으면 추가 검사를 해야 하지. PrePass도 무조건 싼 길만 타면 그림이 틀어져. 싼 길을 타되, 깊이 장부가 BasePass와 맞아야 해.

7. 우리 서버·DirectX랑 비교

DirectX 기초로 보면 PrePass는 별난 마법이 아니야. DepthStencilView를 렌더 타깃처럼 묶고, 색상 렌더타깃 쓰기는 끄고, 깊이 테스트와 깊이 쓰기를 켠 상태로 메시를 한 번 그리는 거야. 그 결과 depth buffer에 가장 가까운 표면의 z가 남는다. 그다음 BasePass에서 같은 화면을 그릴 때, 깊이 테스트가 뒤쪽 픽셀을 빨리 떨어뜨린다.

서버 감각으로는 사전 필터야. 스킬 공식, DB 기록, 보상 계산 전에 대상/거리/상태 검사를 먼저 하는 것과 같아. 렌더링에서는 픽셀 셰이더, 텍스처 샘플, GBuffer 쓰기 전에 깊이 버퍼를 먼저 본다. 둘 다 비싼 일을 하기 전에, 싼 정보로 버릴 수 있는 걸 먼저 버린다는 구조야. 다만 서버 검사는 우리가 코드로 if를 직접 쓰는 느낌이 강하고, GPU Early-Z는 파이프라인 상태와 하드웨어가 도와주는 영역이 커. 렌더러 코드는 "깊이를 먼저 정확히 채우는 상태"를 만들어 주고, 실제 픽셀 셰이더 생략은 GPU가 할 수 있게 길을 열어 주는 구조야.

8. 이 챕터에서 헷갈리면 안 되는 것

첫째, PrePass는 최종 색을 만들지 않아. CW_NONE 때문에 색상 쓰기를 꺼. 깊이 장부를 만드는 시간이야.

둘째, PrePass가 항상 이득은 아니야. 번호표 붙이기도 메시를 한 번 더 훑는 비용이 있어. 그래서 DDM_None, DDM_AllOccluders, DDM_AllOpaque 같은 모드가 있다.

셋째, 마스크 재질은 조심해야 해. 나뭇잎이나 철망처럼 구멍이 있는 재질은 깊이만 대충 쓰면 뒤쪽 픽셀이 잘못 죽을 수 있다. 그래서 WritesEveryPixel 조건이 나온다.

넷째, PrePass와 occlusion culling은 이어지지만 같은 말은 아니야. PrePass는 깊이 장부를 채우는 일이고, occlusion culling은 그 장부나 HiZ를 이용해 "아예 안 보이는 물체"를 더 크게 거르는 일이다.

Q1. PrePass가 왜 필요한가요? 그림을 두 번 그리는 거 아닌가요?

답 보기
두 번 그리는 게 아니라, 비싼 색칠을 줄이려고 싼 번호표를 먼저 붙이는 거야. 실제 화면은 한 픽셀 위에 벽·캐릭터·나무·이펙트가 여러 겹 겹쳐. 뒤에 가려져 어차피 안 보일 픽셀도 픽셀 셰이더를 태우면 낭비야 — 픽셀 셰이더는 텍스처 여러 장 읽고, 노멀 풀고, GBuffer 여러 장에 쓰거든. 그래서 PrePass가 색 없이 깊이만 싸게 먼저 깔아서, BasePass에서 뒤쪽 픽셀을 Early-Z로 빨리 떨어뜨리게 해. 도화지 칸마다 "제일 앞 종이가 몇 번째 깊이인지" 숫자만 먼저 적는 거지.

↳ 서버 감각으로 대응시키면요?

답 보기
CM_ATTACK 하나 왔을 때 대상이 죽었는지, 거리가 맞는지, 맵이 같은지 확인도 안 하고 비싼 스킬 공식·DB 기록·드랍 계산부터 돌리면 손해잖아. 먼저 싼 검사로 "이 요청 처리 대상 맞아?"를 걸러야지. 렌더링에서 그 싼 검사가 깊이 버퍼고, 색칠 전에 그걸 먼저 채우는 게 PrePass야. "비싼 일 전에 싼 정보로 버릴 거 버린다"는 구조가 똑같아.

Q2. PrePass가 항상 이득인가요? 안 하는 게 나은 경우도 있나요?

답 보기
항상 이득은 아니야. PrePass도 공짜가 아니거든 — 색만 안 쓸 뿐 버텍스는 돌고, 래스터라이즈도 하고, 드로우 명령도 쌓아. 작은 소품이 잔뜩이고 픽셀 셰이더가 가벼우면, 깊이만 한 번 더 그리는 비용이 절약보다 더 클 수 있어. 반대로 벽·산·건물처럼 큰 가림막이 많고 머티리얼이 비싸면 PrePass가 크게 이겨. 그래서 언리얼은 EDepthDrawingMode로 "안 함/가림막만/불투명 전부" 같은 범위를 고를 수 있게 해뒀어.

↳ 그럼 PrePass를 돌지 말지는 코드에서 뭐가 정하나요?

답 보기
ShouldRenderPrePass()가 정하는데, 판단은 아주 짧아. EarlyZPassMode가 DDM_None이 아니거나, movable(움직이는 물체)까지 Early-Z에 넣어야 하면 PrePass를 돌아. 결국 "번호표 붙이기 모드가 켜져 있냐"를 묻는 문장이야. 그 손잡이(EDepthDrawingMode)가 곧 비용과 절약을 맞추는 조절기인 거지.

Q3. PrePass는 색을 안 쓴다고 했는데, 그게 왜 중요한가요?

답 보기
PrePass가 BasePass처럼 색을 찍으면 의미가 없어. 비싼 색칠을 줄이려는 건데 이미 색칠을 해버리면 헛수고잖아. 그래서 깊이 패스 상태를 CW_NONE(Color Write None, 색상 쓰기 없음)으로 잠가. 대신 깊이 쓰기는 켜. 즉 PrePass는 화면 색을 만드는 시간이 아니라 칸마다 앞자리 깊이 번호만 적는 시간이야. 이건 단순 최적화가 아니라 의도 자체가 다른 거지 — 가능하면 위치만 읽는 버텍스 경로, 픽셀 셰이더 생략 같은 가벼운 길을 타려고 해.

↳ 그럼 아무 메시나 다 위치만 읽는 가벼운 길로 처리해도 되나요?

답 보기
아니, 마스크 재질은 조심해야 해. 나뭇잎 텍스처를 떠올려봐 — 폴리곤은 크지만 알파 마스크 때문에 실제 잎사귀 부분만 보이고 나머지는 구멍이야. 이걸 위치만 보고 깊이에 꽉 채우면 잎사귀 사이 구멍까지 막힌 걸로 기록돼서, BasePass에서 뒤쪽 물체가 잘못 사라져. 그래서 Material.WritesEveryPixel이나 DDM_MaskedOnly 같은 조건으로 걸러. 싼 길(bPositionOnly)을 타되, 깊이 장부가 BasePass와 정확히 맞아야 해. 서버로 치면 "대상 ID 존재"만으로 공격 성공 처리하면 안 되고 스텔스·무적·이동중 같은 조건을 더 봐야 하는 거랑 같아.

Q4. PrePass랑 오클루전 컬링은 같은 거 아닌가요? 둘 다 깊이 쓰잖아요.

답 보기
이어지지만 같은 말은 아니야. PrePass는 깊이 장부를 채우는 일이고, 오클루전 컬링은 그 장부나 HiZ를 이용해 "아예 안 보이는 물체"를 더 크게 거르는 일이야. PrePass는 픽셀 단위로 "이 픽셀이 앞이냐"를 정리해서 Early-Z를 돕고, 오클루전 컬링은 프리미티브 단위로 "이 물체는 draw 후보에서 빼자"를 판단해. 층위가 달라 — 하나는 픽셀 낭비를 줄이고, 하나는 물체 자체를 파이프라인에서 빼.

↳ 그럼 PrePass가 만든 깊이는 그 뒤로 누가 어떻게 쓰나요?

답 보기
두 방향으로 쓰여. 하나는 바로 다음 BasePass가 그 깊이 장부를 믿고 진짜 보이는 픽셀 위주로 GBuffer를 채워(Early-Z로 뒤쪽 픽셀 셀프 제거). 또 하나는 그 깊이를 SceneDepthTexture로 들고 HiZ(계단식 요약본)로 접어둬서, 큰 물체가 화면을 얼마나 가리는지 큰 칸부터 빠르게 검사하는 오클루전 쪽에서 참고해. 실행 자체는 EMeshPass::DepthPass로 도는데, 이건 앞 장에서 배운 "미리 구워둔 그리기 명령을 패스에서 실행한다"랑 바로 이어져.

↳ 두 번째 단계 깊이 패스(SecondStageDepthPass)는 왜 또 있나요?

답 보기
기본은 DepthPass 한 번이면 충분해. 근데 일부 뷰가 요구하면, 첫 단계 결과를 FirstStageDepthBuffer로 따로 복사해 보관한 뒤 SecondStageDepthPass를 한 번 더 돌아. 어떤 효과는 "PrePass 도중 시점의 깊이"와 "전체 깊이"를 둘 다 필요로 하거든 — 예를 들어 특정 물체를 뺀 상태의 깊이 스냅샷이 뒤 패스 입력으로 필요할 때야. 항상 도는 게 아니라 bUsesSecondStageDepthPass가 켜진 뷰가 있을 때만 붙는 조건부 추가 단계라, 큰 그림에선 "필요하면 깊이를 두 판 만든다" 정도로 잡으면 돼.

이 챕터에서 끝내는 말

  • PrePass는 색을 그리는 패스가 아니라 깊이 장부를 먼저 채우는 패스야.
  • ShouldRenderPrePass()는 Early-Z 모드가 켜져 있는지 보고 실행 여부를 정한다.
  • SetupDepthPassState()는 CW_NONE으로 색상 쓰기를 끄고 깊이 쓰기를 켠다.
  • RenderPrePass()는 overdraw를 줄이려고 EMeshPass::DepthPass를 실행한다.
  • FDepthPassMeshProcessor는 재질 조건을 보고 어떤 메시가 깊이에 들어갈지 고른다.

🧠 머리 속 한 줄 요약

PrePass는 BasePass의 비싼 픽셀 셰이더를 덜 낭비하려고, 색칠 전에 화면 칸마다 가장 앞 표면의 깊이 번호표를 먼저 붙여 두는 Early-Z 준비 시간이다.
