셰이더 — GPU에서 도는 작은 프로그램

언리얼 렌더링 · 08 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 ".usf/.ush, 정점/픽셀/컴퓨트 셰이더, FGlobalShader가 한 줄로 이어지는 구조"가 잡힌다.

왜 이걸 배워? — 문제의식부터

네가 서버를 짜봤으면 패킷 디스패처 감각은 이미 있어. CM_MOVE라는 번호만 있다고 로직이 도는 게 아니지. 그 번호가 어느 핸들러로 가는지, 어떤 바디를 읽는지, 어느 스레드에서 처리되는지가 전부 맞아야 해.

렌더링도 똑같아. CPU가 "이 텍스처 밉맵 만들어"라고 말해도 GPU는 C++ 함수를 직접 호출하지 못해. GPU가 실행하는 건 이미 컴파일된 작은 프로그램이고, 그 프로그램이 셰이더야.

이 연결이 틀리면 바로 터진다. C++은 MainCS를 찾는데 .usf 안에 그 함수가 없거나, SF_Compute라고 등록했는데 함수 모양이 픽셀 셰이더라면 컴파일 단계에서 막힌다. 서버로 치면 패킷 ID는 있는데 핸들러 시그니처가 안 맞는 상황이야.

그래서 언리얼도 같은 문제를 만났고, 답이 셰이더 타입 등록 장부야. C++ 클래스는 "어느 파일, 어느 함수, 어느 GPU 스테이지"인지 들고 있고, .usf 파일은 실제 GPU에서 돌 HLSL 코드를 들고 있다.

왜 지금 배우냐면, 앞 장의 PSO 안에는 결국 셰이더 손잡이가 들어간다. → pso 다음 장은 그 셰이더가 어떻게 컴파일되는지 본다. → shader-compile 그러니까 이번 장은 "GPU 프로그램의 주소록"을 먼저 읽는 자리야.

0. 비유부터 — 주방 레시피 카드와 주문표

이번 챕터는 주방으로 생각하자. GPU는 요리사고, CPU는 매니저야.

매니저가 "밉맵 만들어!"라고 소리친다고 요리가 나오진 않아. 주방에는 실제 레시피 카드가 있어야 하고, 매니저 책상에는 그 레시피를 가리키는 주문표가 있어야 해.

  • .usf = 실제 조리 시작점이 있는 메인 레시피 카드
  • .ush = 여러 레시피가 같이 보는 공용 메모장
  • MainVS = 재료 위치를 잡는 손질 담당
  • MainPS = 접시에 색을 얹는 플레이팅 담당
  • MainCS = 칸을 나눠 여러 요리사가 동시에 처리하는 작업반
  • FGlobalShader = C++ 매니저가 들고 있는 전역 주문표
  • IMPLEMENT_GLOBAL_SHADER = 주문표에 파일·함수·조리대를 찍는 도장

이 비유를 끝까지 끌고 간다. 셰이더를 읽는다는 건 두 장을 같이 보는 일이야. 하나는 .usf 레시피 카드고, 다른 하나는 C++ 주문표다.

🌱 이 개념은 왜 생겼나 — .usf와 .ush
• 원래 구조: 레시피를 그냥 아무 파일 하나에 다 적고, 매니저가 그 파일 이름을 직접 들고 가도 돼.
• 그런데 문제: 메인 요리 레시피와 공용 양념 메모가 섞이면 "뭘 컴파일해야 하지?"가 바로 헷갈려. 공용 메모장까지 메인 요리처럼 굽게 되면 주문이 깨져.
• 그래서 필요한 것: "실제로 구울 메인 레시피"와 "같이 끼워 읽는 메모장"을 이름표로 나눠야 해. 그래서 .usf는 메인 레시피, .ush는 include용 공용 메모장이야.
🧱 먼저 알아야 할 것 — 파일 이름표와 주소
• 파일 이름표: 이름 끝의 짧은 꼬리말은 이 종이가 어떤 종류인지를 알려주는 표식이다.
• 주소: 물건이 어디에 있는지 적은 길 안내다. 실제 물건이 아니라 찾아가기 위한 말이다.
• 같은 주소 규칙: 모두가 같은 방식으로 주소를 적어야 서로 같은 곳을 찾는다.
이게 잡히면 아래 설명이 얹힌다.

1. .usf와 .ush — 먼저 파일 규칙부터

언리얼 셰이더는 그냥 윈도우 경로로 움직이지 않아. /Engine/Private/ComputeGenerateMips.usf 같은 가상 셰이더 경로로 움직여. 그 경로 끝에는 usf나 ush가 와야 한다.

🔤 기호 사전 — 가상 셰이더 경로
• FPathViews::GetExtension = 파일 확장자만 뽑는 도구야.
• FStringView = 문자열을 복사하지 않고 바라보는 얇은 손잡이야.
• ContainsByPredicate = 목록을 돌면서 조건에 맞는 게 있는지 찾는 함수야.
• TEXT("usf") / TEXT("ush") = 언리얼 문자열로 감싼 확장자 이름이야.
• && / || = &&는 "그리고", ||는 "또는"이야.
• ReportVirtualShaderFilePathError = 잘못된 셰이더 경로를 에러로 남기는 함수야.
🔁 이제 다시 보자. 이 코드는 확장자를 뽑고 → 공유 헤더면 .h만 허용하고 → 일반 셰이더 경로면 .usf 또는 .ush만 허용해. 즉 주방 레시피와 공용 메모장은 정해진 이름표를 달아야 한다는 뜻이야.

그런데 .usf와 .ush는 역할이 같지 않아. 둘 다 셰이더 소스 경로로 인정되지만, C++ 주문표가 직접 컴파일 대상으로 가리키는 메인 파일은 .usf야.

🔤 기호 사전 — .usf 컴파일 체크
• checkf(...) = 조건이 틀리면 메시지를 찍고 멈추는 검사야.
• FPaths::GetExtension = 파일명에서 확장자를 꺼낸다.
• InSourceFilename = C++ 주문표가 가리키는 셰이더 파일 이름이야.
• \ = 매크로가 다음 줄까지 이어진다는 표시야.
• Only .usf files should be compiled = 이 주문표는 .usf 메인 레시피를 컴파일해야 한다는 못박기야.

여기서 정리하자. .usf는 펼쳐서 컴파일할 메인 레시피 카드고, .ush는 그 안에서 include하는 공용 메모장이다.

🧱 먼저 알아야 할 것 — 주문표는 실제 일을 대신하지 않는다
• 기록 카드: 카드에는 해야 할 일의 이름과 필요한 재료가 적힐 뿐, 카드 자체가 일을 하지는 않는다.
• 가리키기: 창고 두 번째 칸처럼 글자가 실제 물건이 있는 곳을 가리킬 수 있다.
• 한 칸만 틀려도: 이름이나 자리가 하나만 틀려도 엉뚱한 물건을 꺼내게 된다.
이게 잡히면 아래 설명이 얹힌다.

2. FGlobalShader — 전역 주문표

FGlobalShader는 특정 머티리얼에 묶이지 않는 셰이더의 C++ 껍데기야. 화면 복사, 밉맵 생성, 텍스처 클리어 같은 엔진 공용 작업에 자주 나온다.

밉맵 생성 코드에서 주문표가 어떻게 생겼는지 보자. 같은 .usf 파일을 두고, 컴퓨트·정점·픽셀 스테이지가 각각 다른 진입 함수를 가리킨다.

🔤 기호 사전 — FGlobalShader 주문표
• IMPLEMENT_GLOBAL_SHADER = C++ 클래스, .usf 파일, 함수 이름, 스테이지를 묶는 도장이야.
• FGenerateMipsVS : public FGlobalShader = FGenerateMipsVS가 전역 셰이더 주문표를 물려받는다는 뜻이야.
• DECLARE_GLOBAL_SHADER = 이 클래스가 전역 셰이더 타입이라고 선언하는 매크로야.
• SHADER_USE_PARAMETER_STRUCT = 셰이더 입력값을 구조체로 받겠다는 선언이야.
• BEGIN_SHADER_PARAMETER_STRUCT = GPU에 넘길 재료 목록을 여는 줄이야.
• SF_Vertex / SF_Pixel / SF_Compute = 어느 GPU 조리대에서 돌지 정하는 스테이지 값이야.
• OutEnvironment.SetDefine = 컴파일 전에 #define 값을 넣는 줄이야.
🔁 이제 다시 보자. FGenerateMipsCS는 MainCS와 SF_Compute를 묶고, FGenerateMipsVS는 MainVS와 SF_Vertex를 묶고, FGenerateMipsPS는 MainPS와 SF_Pixel을 묶는다. 같은 레시피 카드라도 어느 함수와 어느 조리대를 고르느냐에 따라 완전히 다른 셰이더가 돼.

이 한 줄을 볼 때는 네 칸만 읽으면 돼.

🌱 이 개념은 왜 생겼나 — FGlobalShader
• 원래 구조: C++ 코드가 .usf 파일명, MainPS 같은 함수 이름, 조리대 이름을 그때그때 직접 들고 가도 돼.
• 그런데 문제: 밉맵, 화면 복사, 텍스처 클리어 같은 공용 주문이 늘어나면 네 칸 중 하나만 틀려도 엉뚱한 레시피가 나가. 매번 손글씨 주문표를 새로 쓰는 꼴이야.
• 그래서 필요한 것: C++ 매니저가 들고 다닐 정식 주문표가 필요해. 머티리얼에 묶이지 않는 전역 주문표가 바로 FGlobalShader야.
🧱 먼저 알아야 할 것 — 장부에 올리고 이름으로 찾기
• 장부: 많은 카드를 한곳에 모아 적어 두면 나중에 빠뜨리지 않고 찾을 수 있다.
• 이름표: 사람 이름으로 전화번호를 찾듯, 이름표가 있으면 긴 내용을 다시 뒤질 필요가 없다.
• 정렬: 가나다순으로 꽂아 두면 찾는 시간이 줄고 새 카드도 맞는 자리에 넣을 수 있다.
이게 잡히면 아래 설명이 얹힌다.

3. Shader.cpp — 주문표를 장부에 꽂는다

IMPLEMENT_GLOBAL_SHADER는 겉으로는 한 줄이지만, 결국 FShaderType을 만들고 전역 장부에 등록한다. 그 장부 항목이 파일명, 함수명, 스테이지를 보관한다.

🔤 기호 사전 — FShaderType 장부
• : ShaderTypeForDynamicCast(...) = 생성자 본문 전에 멤버들을 채우는 초기화 목록이야.
• SourceFilename(InSourceFilename) = 주문표의 .usf 파일명을 장부에 저장한다.
• FunctionName(InFunctionName) = MainCS 같은 진입 함수 이름을 저장한다.
• Frequency(InFrequency) = SF_Vertex 같은 스테이지 값을 저장한다.
• check(CheckVirtualShaderFilePath(...)) = 가상 셰이더 경로 규칙을 다시 검사한다.
• GlobalListLink.LinkHead(GetTypeList()) = 전역 셰이더 타입 목록에 이 타입을 건다.
• GetNameToTypeMap().Add(HashedName, this) = 이름으로 다시 찾을 수 있게 맵에 등록한다.
• SortedTypes.Insert = 정렬된 타입 목록에도 꽂아 넣는다.
🔁 이제 다시 보자. C++ 주문표의 파일명은 SourceFilename, 함수명은 FunctionName, 스테이지는 Frequency에 들어간다. 그리고 GlobalListLink와 GetNameToTypeMap()에 등록된다. 서버 디스패처 테이블에 패킷 핸들러를 꽂는 것과 같은 느낌이야.

여기까지가 C++ 쪽 준비다. 아직 GPU 코드는 안 돌았다. 엔진이 "나중에 이 이름을 보면 이 파일의 이 함수를 이 스테이지로 컴파일해"라고 장부에 적어둔 단계야.

🌱 이 개념은 왜 생겼나 — FShaderType 장부
• 원래 구조: 주문표 객체가 각자 자기 파일명과 함수명을 들고 있으면 돼. 필요한 코드가 아는 주문표만 직접 꺼내 쓰는 방식이야.
• 그런데 문제: 셰이더가 수십, 수백 개로 늘면 컴파일할 때도, 캐시에서 찾을 때도 "전체 주문표 목록"이 필요해. 서버 핸들러를 맵에 안 꽂고 파일마다 숨겨둔 것과 비슷해.
• 그래서 필요한 것: 모든 주문표를 한 장부에 꽂아 이름으로 다시 찾게 해야 해. 그 장부 항목이 FShaderType이고, IMPLEMENT_GLOBAL_SHADER가 거기에 도장을 찍어.
🧱 먼저 알아야 할 것 — 큰 판을 칸으로 나눠 맡기기
• 큰 일: 큰 종이를 한 사람이 다 칠하면 오래 걸린다.
• 칸 번호: 종이를 작은 칸으로 나누고 각 사람에게 번호를 주면 자기 칸만 보면 된다.
• 같은 규칙: 모두가 같은 규칙으로 계산하면 나중에 칸들을 모아도 하나의 결과가 된다.
이게 잡히면 아래 설명이 얹힌다.

4. 실제 .usf — 컴퓨트 셰이더

이제 주문표가 가리킨 레시피 카드를 열자. FGenerateMipsCS는 ComputeGenerateMips.usf의 MainCS를 가리켰다. 그 함수가 실제로 있다.

ComputeGenerateMips.usf:23

[numthreads(8, 8, 1)] void MainCS(uint3 DT_ID : SV_DispatchThreadID) { float2 UV = TexelSize * (DT_ID.xy + 0.5f); #if GENMIPS_SRGB half4 outColor = MipInSRV.SampleLevel(MipSampler, UV, 0); outColor = half4(LinearToSrgb(outColor.xyz), outColor.w); #else float4 outColor = MipInSRV.SampleLevel(MipSampler, UV, 0); #endif #if GENMIPS_SWIZZLE MipOutUAV[DT_ID.xy] = outColor.zyxw; #else MipOutUAV[DT_ID.xy] = outColor; #endif }
🔤 기호 사전 — 컴퓨트 셰이더
• [numthreads(8, 8, 1)] = 한 작업반에 GPU 스레드가 8×8×1명 있다는 뜻이야.
• uint3 DT_ID : SV_DispatchThreadID = 이 스레드가 전체 작업판에서 맡은 칸 좌표야.
• float2 UV = 텍스처를 찍을 2D 좌표야.
• SampleLevel = 특정 밉 레벨에서 텍스처를 읽는 함수야.
• half4 / float4 = 색 네 성분을 담는 숫자 묶음이야.
• MipOutUAV[DT_ID.xy] = outColor = 이 스레드가 맡은 출력 칸에 색을 쓴다.
🔁 이제 다시 보자. MainCS는 작업반 함수야. GPU 스레드마다 DT_ID.xy가 다르고, 각 스레드는 자기 칸의 UV로 입력 텍스처를 읽은 뒤 출력 텍스처의 자기 칸에 색을 쓴다. 정점도 삼각형도 없어. 그냥 작업판을 잘라 병렬 처리하는 방식이야.

컴퓨트 셰이더는 일반 병렬 작업에 강해. 밉맵 생성, 컬링, 타일 분류, 통계 계산 같은 곳에서 자주 나온다. 주방 비유로는 큰 도마를 64칸씩 나눠서 요리사들에게 맡기는 작업반이다.

🌱 이 개념은 왜 생겼나 — 컴퓨트 셰이더
• 원래 구조: 정점 셰이더로 재료 위치를 잡고, 픽셀 셰이더로 접시에 색을 얹으면 화면 그림은 꽤 많이 그릴 수 있어.
• 그런데 문제: 밉맵 만들기처럼 텍스처 1024×1024칸을 계산해야 하는 일은 삼각형을 그리는 척하면서 처리하면 어색해. 사실은 "그림"보다 "칸별 계산 작업"에 가까워.
• 그래서 필요한 것: GPU 요리사들에게 칸 번호를 나눠 주고 "너는 네 칸만 계산해"라고 시키는 작업반이 필요해. 그게 컴퓨트 셰이더야.

5. 같은 .usf 안의 정점/픽셀 셰이더

같은 파일 아래에는 MainVS와 MainPS도 있다. 아까 C++ 주문표에서 SF_Vertex, SF_Pixel로 등록한 그 함수들이야.

ComputeGenerateMips.usf:80

void MainVS(in float4 InPosition : ATTRIBUTE0, in float2 InUV : ATTRIBUTE1, out float4 OutPosition : SV_POSITION, out float2 OutUV : TEXCOORD0) { OutPosition = InPosition; OutPosition.xy = -1.0f + 2.0f * InPosition.xy; OutPosition.xy *= float2( 1, -1 ); OutUV = InUV; } void MainPS(float4 InPosition : SV_POSITION, float2 InUV : TEXCOORD0, out float4 OutColor : SV_Target0) { OutColor = MipInSRV.SampleLevel(MipSampler, InUV + HalfTexelSize, Level); }
🔤 기호 사전 — 정점/픽셀 셰이더
• ATTRIBUTE0 / ATTRIBUTE1 = 정점 버퍼에서 들어오는 입력 칸이야.
• SV_POSITION = GPU 래스터라이저가 이해하는 화면 위치야.
• TEXCOORD0 = 다음 단계로 넘기는 텍스처 좌표 통로야.
• SV_Target0 = 픽셀 셰이더가 0번 렌더 타깃에 쓸 색이야.
• out float4 OutColor = 함수 밖으로 색 네 성분을 내보내겠다는 뜻이야.
• InUV + HalfTexelSize = 텍스처 좌표를 반 픽셀만큼 보정해서 찍는 계산이야.

정점 셰이더는 "재료 위치 손질" 담당이다. 픽셀 셰이더는 "접시에 색 얹기" 담당이다. 컴퓨트 셰이더는 "도마 칸 나눠서 병렬 작업" 담당이다.

중요한 건 함수 이름만으로 스테이지가 정해지는 게 아니라는 점이야. 진짜 장부에는 C++의 IMPLEMENT_GLOBAL_SHADER(..., "MainPS", SF_Pixel)처럼 함수 이름과 스테이지가 같이 박힌다.

6. 한눈에 보는 흐름

GenerateMips.cpp:38 IMPLEMENT_GLOBAL_SHADER(FGenerateMipsCS, "...usf", "MainCS", SF_Compute) | v Shader.cpp:262 SourceFilename / FunctionName / Frequency 저장 GlobalListLink.LinkHead(GetTypeList()) | v ShaderCore.cpp:1664 가상 경로와 usf/ush 확장자 검사 | v ComputeGenerateMips.usf:23 void MainCS(uint3 DT_ID : SV_DispatchThreadID) | v GPU 스레드들이 각자 DT_ID.xy 칸에 결과 기록

정점/픽셀은 같은 구조에서 마지막 함수만 바뀐다.

FGenerateMipsVS + MainVS + SF_Vertex → 정점 위치와 UV를 넘김

FGenerateMipsPS + MainPS + SF_Pixel → SV_Target0에 색을 씀

이제 FGlobalShader를 보면 겁먹지 말고 네 칸만 읽어. C++ 타입, .usf 파일, 진입 함수, 스테이지. 이 네 칸이 맞으면 주문표와 레시피가 연결된다.

우리 서버·DirectX 랑 비교

서버 디스패처랑 거의 같은 감각으로 보면 된다.

서버언리얼 셰이더
패킷 ID셰이더 타입 이름
핸들러 함수.usf 진입 함수
패킷 바디셰이더 파라미터 구조체
디스패처 등록IMPLEMENT_GLOBAL_SHADER
핸들러 테이블FShaderType 전역 목록/맵

차이는 실행 위치야. 패킷 핸들러는 CPU에서 돈다. 셰이더 본문은 GPU에서 돈다. C++ 클래스 FGenerateMipsPS 자체가 GPU에서 도는 게 아니라, 그 클래스가 가리킨 .usf 함수가 컴파일되어 GPU에서 돈다.

DirectX 경험으로는 이렇게 매핑하면 돼.

DirectX 감각언리얼 이름
HLSL 파일.usf

entry point"MainVS", "MainPS", "MainCS"

셰이더 리소스 바인딩FParameters → shader-parameters
PSO의 VS/PS 슬롯앞 장의 PSO → pso

우리 서버에서 패킷 ID와 핸들러가 어긋나면 디버깅이 지옥이지. 렌더링에서도 셰이더 타입과 .usf 진입 함수가 어긋나면 똑같다. 그래서 IMPLEMENT_GLOBAL_SHADER 한 줄을 정확히 읽는 게 중요해.

이 챕터에서 딱 이것만

  1. .usf는 메인 셰이더 레시피고, .ush는 공용 include 메모장이다.
  2. FGlobalShader는 머티리얼 밖 전역 셰이더의 C++ 주문표다.
  3. IMPLEMENT_GLOBAL_SHADER는 C++ 타입, 파일, 함수, 스테이지를 묶는다.
  4. Shader.cpp의 FShaderType은 그 정보를 장부에 저장하고 전역 목록에 등록한다.
  5. GPU에서 도는 건 C++ 클래스가 아니라 .usf 안의 MainVS / MainPS / MainCS다.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. 셰이더가 뭐고, C++ 코드랑 어떻게 연결되나요?

답 보기
셰이더는 GPU에서 도는 작은 프로그램이야. CPU가 "밉맵 만들어"라고 해도 GPU는 C++ 함수를 직접 못 불러 — GPU가 실행하는 건 이미 컴파일된 그 작은 프로그램이거든. 그래서 두 장을 같이 봐야 해: .usf에 있는 실제 HLSL 레시피랑, C++이 들고 있는 주문표(FGlobalShader). 서버 디스패처랑 똑같은 감각이야 — CM_MOVE 번호만 있다고 로직이 도는 게 아니라 어느 핸들러로 가는지가 맞아야 하는 거지.

↳ 그럼 C++ 클래스 자체가 GPU에서 도는 건가요?

답 보기
아니, 이게 헷갈리는 지점이야. FGenerateMipsPS 같은 C++ 클래스는 GPU에서 안 돌아. 그건 "어느 파일, 어느 함수, 어느 스테이지"를 가리키는 주문표일 뿐이고, 실제로 GPU에서 도는 건 그 주문표가 가리킨 .usf 안의 MainPS 함수가 컴파일된 거야. C++은 CPU에서 주소록 역할만 하고, 진짜 요리는 GPU 조리대에서 .usf 레시피가 하는 거지.

Q2. .usf랑 .ush는 왜 나눠져 있나요?

답 보기
.usf는 실제로 컴파일할 메인 레시피 카드고, .ush는 여러 레시피가 같이 include하는 공용 메모장이야. 안 나누면 "뭘 컴파일해야 하지?"가 바로 헷갈려 — 공용 양념 메모까지 메인 요리처럼 구우면 주문이 깨지잖아. 그래서 C++ 주문표가 컴파일 대상으로 직접 가리키는 건 항상 .usf고, 코드에도 ".usf만 컴파일해야 한다"는 검사가 박혀 있어. DirectX 감각으론 HLSL 파일 대 HLSL include야.

Q3. IMPLEMENT_GLOBAL_SHADER 한 줄은 큰 그림에서 뭘 하는 건가요?

답 보기
네 칸을 하나로 묶는 도장이야 — C++ 타입, .usf 파일, 진입 함수 이름, GPU 스테이지. 예를 들면 "FGenerateMipsPS = ComputeGenerateMips.usf의 MainPS를 SF_Pixel로." 재밌는 건 같은 .usf 파일이라도 어느 함수·어느 스테이지를 고르냐에 따라 완전히 다른 셰이더가 된다는 거야. 같은 파일에서 MainVS+SF_Vertex, MainPS+SF_Pixel, MainCS+SF_Compute가 다 갈라져 나와.

↳ 그 등록이 왜 전역 장부에 꽂혀야 하나요?

답 보기
셰이더가 수백 개로 늘면 컴파일할 때도, 캐시에서 찾을 때도 "전체 목록"이 필요하거든. 주문표가 각자 자기 파일명만 숨겨 들고 있으면 엔진이 전체를 훑을 수가 없어. 그래서 IMPLEMENT_GLOBAL_SHADER가 FShaderType 장부 항목을 만들어서 전역 목록이랑 이름 맵에 꽂아둬. 서버에서 패킷 핸들러를 파일마다 숨기지 않고 디스패처 테이블에 등록하는 거랑 똑같아 — 그래야 "이 이름 보면 이 파일 이 함수를 이 스테이지로 컴파일해"를 나중에 찾지.

↳ 네 칸 중 하나만 틀리면 어떻게 되나요?

답 보기
바로 터지거나 엉뚱한 게 나가. C++은 MainCS를 찾는데 .usf에 그 함수가 없으면 컴파일에서 막히고, SF_Compute로 등록했는데 함수 모양이 픽셀 셰이더면 안 맞아. 서버로 치면 패킷 ID는 있는데 핸들러 시그니처가 안 맞는 상황이야. 그래서 IMPLEMENT_GLOBAL_SHADER 한 줄을 정확히 읽는 게 중요해.

Q4. 컴퓨트 셰이더는 정점/픽셀 셰이더랑 왜 따로 있나요?

답 보기
정점 셰이더는 "재료 위치 손질", 픽셀 셰이더는 "접시에 색 얹기"라서 그림 그리기 파이프라인에 묶여 있어. 근데 밉맵 생성이나 컬링, 타일 분류 같은 건 사실 "그림"이 아니라 칸별 계산 작업이거든. 삼각형 그리는 척하면서 처리하면 어색해. 그래서 GPU 스레드들에게 칸 번호를 나눠 주고 "너는 네 칸만 계산해"라고 시키는 작업반이 필요한 거고, 그게 컴퓨트 셰이더야. 정점도 삼각형도 없이 큰 도마를 나눠 병렬로 처리하는 방식이지.

↳ 이번 장 내용이 앞의 PSO랑 어떻게 이어지나요?

답 보기
PSO 카드 안의 큰 항목 하나가 바로 셰이더 손잡이였잖아. 이 장은 그 손잡이가 실제로 어디를 가리키는지를 푼 거야 — FGlobalShader 주문표가 .usf의 어느 함수·어느 스테이지를 묶는지. 그러니까 PSO의 VS/PS 슬롯에 꽂히는 게 이 장에서 등록한 셰이더 타입들이고, 다음 장에선 그게 어떻게 컴파일되는지로 넘어가.
