Lumen Diffuse Indirect — 간접광이 모이는 곳

언리얼 렌더링 · 31 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "Lumen의 diffuse GI가 화면 프로브를 세우고, 화면 추적과 레이 트레이싱/SDF 추적을 섞어 간접광을 모으는 흐름"이 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX를 조금 해봤으면 직접광은 감이 와. 라이트 위치에서 노멀을 보고, 그림자 맵을 보고, 픽셀에 빛을 더하면 돼. 서버로 치면 CM_ATTACK 하나 받아서 대상 하나에게 데미지 주는 정도야.

그런데 간접광은 그렇게 단순하지 않아. 빨간 벽에 빛이 맞으면 그 빨간 빛이 바닥으로 튀고, 바닥에서 또 캐릭터 발밑으로 퍼져. 이걸 픽셀마다 정직하게 여러 방향으로 쏘면 4K 화면에서는 수백만 픽셀 * 여러 레이야. 프레임 안에 못 끝내거나, 끝내도 노이즈가 심해서 화면이 지글거려.

언리얼도 같은 문제를 만났고, 답이 Lumen Screen Probe Gather야. 모든 픽셀이 각자 뛰지 않고, 화면에 듬성듬성 프로브를 세운 뒤 그 프로브들이 레이를 쏴서 간접광을 모은다. 먼저 화면 안에서 맞춰보고, 안 되면 하드웨어 레이 트레이싱이나 SDF 추적으로 월드까지 나간다.

왜 지금 배우냐면, 앞 장 lumen-overview에서 "Lumen이 실시간 전역 조명을 한다"는 큰 그림을 봤어. 이번 장은 그중 diffuse indirect, 즉 벽과 바닥을 타고 퍼지는 부드러운 간접광이 실제 코드에서 어디로 모이는지 보는 장이야. 다음 temporal-aa로 가면 이렇게 모은 결과를 시간에 걸쳐 안정화하는 쪽으로 넘어간다.

0. 비유부터 — 야시장 조명 검사원

야시장 골목을 생각해봐. 가게마다 전구가 있고, 천막 색도 다르고, 바닥도 젖어 있어.

어느 손님 얼굴이 얼마나 밝아 보이는지 알려면 전구만 보면 안 돼. 빨간 천막에서 튄 빛, 흰 벽에서 반사된 빛, 바닥에서 올라온 빛까지 봐야 해.

그런데 손님 한 명 한 명마다 검사원을 붙이면 돈이 터져. 그래서 시장 관리소는 화면 위에 일정 간격으로 조명 검사원을 세워. 이게 스크린 프로브야.

검사원은 팔방으로 작은 탐침 막대, 즉 레이를 뻗는다. 먼저 현재/이전 화면 장부를 뒤져보고, 거기서 못 찾으면 하드웨어 RT나 SDF 추적으로 골목 안까지 나간다.

너무 먼 동네 정보는 조명 창고, 즉 radiance cache에서 꺼내고, 검사원이 모은 결과를 주변 손님 픽셀에게 나눠준다.

이번 장의 비유는 끝까지 이거야.

픽셀은 손님, 스크린 프로브는 검사원, 레이는 탐침 막대, radiance cache는 조명 창고.

1. 먼저 문지기 — Lumen diffuse GI를 켜도 되는가

Lumen diffuse indirect는 무조건 도는 패스가 아니야.

프로젝트 설정, 포스트프로세스 설정, show flag, Path Tracing/Debug 모드, 그리고 추적 데이터가 있는지까지 통과해야 해.

야시장으로 치면 "오늘 시장 열었냐?", "검사원 출동 허가 났냐?", "골목 지도가 있냐?"를 먼저 보는 문지기야.

• bool = 참/거짓 하나를 돌려주는 함수라는 뜻이야.
• const FScene* Scene = 씬을 가리키는 포인터인데, 이 함수 안에서는 내용을 바꾸지 않겠다는 약속이야.
• && = 앞 조건도 참이고 뒤 조건도 참이어야 통과한다는 "그리고".
• == = 두 값이 같은지 본다.

• Lumen::UseHardwareRayTracedScreenProbeGather = 하드웨어 레이 트레이싱으로 스크린 프로브를 추적할 수 있는지 묻는 함수야.
• Lumen::IsSoftwareRayTracingSupported() = 하드웨어 RT가 아니어도 소프트웨어 추적 길이 있는지 보는 함수야.
🔁 이제 다시 보자. 이 코드는 Lumen 기능 허용 → GI 방식이 Lumen인지 확인 → 전역 조명 show flag 확인 → PathTracing/Debug 제외 → 하드웨어 RT나 소프트웨어 추적 가능 여부 확인으로 읽으면 돼. 검사원이 출동하려면 시장도 열려 있고, 장비도 있어야 하는 거야.

여기서 마지막 줄이 중요해.

UseHardwareRayTracedScreenProbeGather 또는 IsSoftwareRayTracingSupported가 있어야 해.

즉 Lumen diffuse는 그냥 색 보정 패스가 아니라, 실제로 추적할 수 있는 길이 있어야 켜진다.

🌱 이 개념은 왜 생겼나 — Final Gather
• 원래 구조: 전구 빛, 그림자, 벽에서 튄 빛을 각 픽셀이 알아서 바로 더하면 돼.
• 그런데 문제: 야시장 골목은 빨간 천막, 젖은 바닥, 먼 가게빛이 서로 섞여. 픽셀마다 같은 골목을 다시 뒤지면 16.6ms 안에 버거워져.
• 그래서 필요한 것: 흩어진 간접광을 마지막에 한 번 모으는 검사반이 필요해. 그래서 이름도 Final Gather, 마지막으로 긁어모으는 단계야.

2. Final Gather에서 어느 검사반을 고르나

Lumen diffuse의 큰 입구는 final gather야.

여기서 세 갈래 중 하나를 고른다.

Irradiance Field Gather, ReSTIR Gather, 아니면 우리가 보는 Screen Probe Gather.

이번 장의 주인공은 마지막 else 안에 있어.

LumenScreenProbeGather.cpp:2134

else { Outputs = RenderLumenScreenProbeGather( GraphBuilder, SceneTextures, FrameTemporaries, LightingChannelsTexture, View, ViewIndex, PreviousViewInfos, MeshSDFGridParameters, RadianceCacheParameters, ScreenSpaceBentNormalParameters, TranslucencyVolumeRadianceCacheParameters, ComputePassFlags); }
🔤 기호 사전 — gather 방식 고르기
• else = 앞의 특수 gather 조건들이 안 맞으면 마지막 기본 길로 간다는 뜻이야.
• Outputs = ... = 이 gather 방식이 만든 간접광 결과를 Outputs에 담는다는 뜻이야.
• GraphBuilder = RDG 패스를 등록하는 작업장 관리자야. 검사원에게 일감을 올리는 곳이라고 보면 돼.
• RadianceCacheParameters = 조명 창고를 샘플링할 때 필요한 좌표표와 텍스처 묶음이야.

이 코드만 보면 Screen Probe Gather는 "기본반"처럼 보여.

특수한 gather를 쓰지 않으면 결국 화면에 검사원을 깔고, 그 검사원들이 간접광을 모으는 방식으로 간다.

서버로 치면 특수 라우팅이 없으면 기본 패킷 핸들러로 들어가는 흐름이야.

🌱 이 개념은 왜 생겼나 — Screen Probe
• 원래 구조: 손님 픽셀마다 검사원을 붙여서 여러 방향으로 빛을 물어보면 돼.
• 그런데 문제: 4K면 손님이 830만 명쯤이야. 각자 8방향만 봐도 탐침이 6천만 개를 넘어가서 시장 관리소가 터져.
• 그래서 필요한 것: 화면 격자마다 대표 검사원을 세우고 주변 픽셀이 같이 쓰게 하자. 화면 위 탐침이라서 Screen Probe야.

3. 검사원을 화면 격자에 세운다

RenderLumenScreenProbeGather에 들어오면 먼저 프로브의 해상도와 화면 격자를 잡아.

모든 픽셀마다 검사원을 세우지 않아.

ScreenProbeDownsampleFactor로 듬성듬성 세우고, 프로브 하나가 여러 방향을 본다.

그래서 이름이 Screen Probe야.

4. 프로브가 쓸 결과 장부를 만들고 추적을 시작한다

검사원을 세웠으면 결과를 적을 장부가 필요해.

TraceRadiance는 각 레이가 가져온 빛 색을 담는 장부고, TraceHit은 어디에 맞았는지/맞았는지 여부를 담는 장부야.

그 다음 TraceScreenProbes가 진짜 조사 일을 시작한다.

🔤 기호 사전 — 추적 장부와 호출
• EPixelFormat = 텍스처 한 칸이 어떤 형식으로 저장되는지 나타내는 enum이야.
• FRDGTextureDesc::Create2D = RDG용 2D 텍스처 설명서를 만든다.
• TexCreate_ShaderResource | TexCreate_UAV = 셰이더에서 읽을 수도 있고 UAV로 쓸 수도 있게 비트 플래그를 합친 거야.
• CreateTexture = RDG에 새 텍스처 자원을 등록한다.
• CreateUAV = 컴퓨트 셰이더가 그 텍스처에 쓸 수 있는 손잡이를 만든다.
• TraceScreenProbes(...) = 지금까지 준비한 프로브와 장부를 들고 실제 레이 조사를 시작하는 함수야.
🔁 이제 다시 보자. 먼저 빛 색 장부 TraceRadiance를 만들고 → 맞은 곳 장부 TraceHit을 만들고 → TraceScreenProbes에 넘긴다. 검사원이 빈 조사표를 받고 골목으로 나가는 순간이야.

호출 인자의 GLumenGatherCvars.TraceMeshSDFs != 0 && Lumen::UseMeshSDFTracing(...)는 하드웨어 RT가 아니어도 Mesh SDF를 쓸 수 있으면 소프트웨어 추적 길을 열어둔다는 뜻이야.

이제 TraceScreenProbes 안으로 내려가자.

🌱 이 개념은 왜 생겼나 — Screen Trace
• 원래 구조: 검사원이 레이를 쏠 때마다 바로 골목 전체, 그러니까 월드 추적으로 보내면 돼.
• 그런데 문제: 바로 앞 벽이나 바닥은 이미 현재/이전 화면 장부에 있는데도 매번 비싼 출장 조사를 하게 돼. 가까운 단서까지 하드웨어 RT나 SDF로 찾으면 낭비야.
• 그래서 필요한 것: 먼저 화면 장부 안에서 맞춰보는 싼 첫 확인이 필요해. 화면 안에서 추적하니까 Screen Trace야.

5. 먼저 화면 안에서 맞춰본다

검사원은 처음부터 골목 끝까지 뛰지 않아.

이미 화면에 보이는 정보가 있으면 그걸 먼저 쓴다.

이게 screen trace야.

현재/이전 화면의 깊이, 색, HZB 같은 자료로 "이 방향으로 뻗은 레이가 화면 안에서 어디에 닿을 수 있나"를 먼저 본다.

• EngineShowFlags.LumenScreenTraces = 에디터/렌더 설정 쪽 show flag가 허용하는지 보는 스위치야.
• View.FinalPostProcessSettings.LumenFinalGatherScreenTraces = 이 뷰의 포스트프로세스 설정에서 final gather screen trace가 켜졌는지 보는 값이야.

화면 추적은 싸고 빠른 첫 확인이야.

하지만 화면 밖에 있거나, 이전 프레임 정보로 못 믿겠거나, 가려진 뒤쪽이면 실패할 수 있어.

그 실패한 레이들을 위해 다음 단계가 필요해.

🌱 이 개념은 왜 생겼나 — 화면 밖 추적(하드웨어 RT/SDF)
• 원래 구조: 화면 장부에서 못 찾은 레이는 그냥 miss로 두고 하늘빛 정도만 주면 돼.
• 그런데 문제: 카메라 밖 빨간 벽이나 문 뒤 바닥도 빛을 튕겨. 화면에 없다고 버리면 골목 모서리 간접광이 꺼지거나 움직일 때 확 튀어.
• 그래서 필요한 것: 화면 밖 골목까지 나가는 두 번째 조사 루트가 필요해. 장비가 있으면 하드웨어 RT, 아니면 SDF, 즉 표면까지의 거리장 지도를 따라가.

6. 화면 밖은 하드웨어 RT 또는 SDF 추적으로 간다

이제 핵심 조합이 나온다.

TraceScreenProbes는 화면에서 먼저 맞춰본 뒤, 남은 레이를 하드웨어 RT 또는 SDF 추적으로 보낸다.

하드웨어 RT가 켜져 있으면 RenderHardwareRayTracingScreenProbe.

아니면 Mesh SDF를 컬링하고, 맞는 것만 compact해서 TraceMeshSDFs.

마지막에는 남은 miss에도 radiance cache/sky/voxel 쪽 처리를 적용한다.

아래 토막은 길지만, 흐름을 한 번에 봐야 해.

🔁 이제 다시 보자. 이 흐름은 bUseHardwareRayTracing이면 하드웨어 RT 검사반으로 보내고 → 아니면 SDF용 골목 격자를 만들고 → unresolved trace만 CompactTraces로 모아서 Mesh SDF를 추적한다. 화면 장부에서 못 찾은 빛을 진짜 골목 조사로 넘기는 장면이야.

여기서 중요한 건 "하나만 쓴다"가 아니라는 점이야.

스크린 프로브는 결과를 담는 그릇이고, 그 안의 레이가 여러 경로를 탄다.

가까운 화면 정보가 있으면 화면 추적.

하드웨어 RT가 가능하면 진짜 레이 트레이싱.

아니면 Mesh SDF/Heightfield/Global SDF.

이 코드 바로 뒤에서는 남은 miss가 TraceVoxels와 radiance cache/sky 쪽으로 보강된다.

그래서 Lumen diffuse는 단일 알고리즘이라기보다 검사원 배치 + 여러 조사 루트 + 결과 합치기에 가깝다.

ShouldRenderLumenDiffuseGI는 feature flag와 환경 체크야.

RenderLumenFinalGather는 라우터야.

RenderLumenScreenProbeGather는 요청 컨텍스트와 버퍼를 준비하는 핸들러 입구야.

TraceScreenProbes는 실제 워커 큐야.

그 안에서 화면 추적, 하드웨어 RT, SDF, radiance cache가 우선순위를 두고 처리된다.

우리 서버·DirectX 랑 비교

우리 서버에서 몬스터 AI를 매 tick 모든 몬스터가 모든 유저를 전수조사하면 바로 터져.

그래서 보통 공간 그리드, 섹터, 관심영역, 캐시를 둔다.

Lumen diffuse도 똑같아.

모든 픽셀이 모든 방향으로 월드 레이를 쏘면 터지니까, 화면 위에 프로브 그리드를 세운다.

그 프로브만 대표로 조사하고, 결과를 주변 픽셀에게 나눠준다.

DirectX 경험으로 보면 TraceRadiance와 TraceHit은 UAV로 쓰는 중간 렌더 타깃이야.

FComputeShaderUtils::AddPass는 컴퓨트 셰이더 dispatch를 RDG에 올리는 장면이고, PermutationVector는 #define 조합으로 셰이더 바이너리를 고르는 장면이야.

하드웨어 RT 경로는 DXR의 ray generation/inline ray tracing 쪽 감각으로 보면 되고, SDF 경로는 거리장 텍스처를 타고 가는 소프트웨어 ray marching으로 보면 된다.

결정적 차이는 이거야.

서버의 관심영역은 "누구에게 어떤 패킷을 보낼까"를 줄이고, Lumen의 screen probe는 "어떤 픽셀이 직접 레이를 쏠까"를 줄인다.

둘 다 많은 개체의 일을 대표 샘플과 캐시로 줄이는 기술이야.

이 챕터에서 딱 이것만

  • Lumen diffuse GI는 ShouldRenderLumenDiffuseGI를 통과해야 돈다.
  • 기본 final gather 경로는 RenderLumenScreenProbeGather로 들어간다.
  • Screen Probe는 픽셀마다가 아니라 화면 격자마다 세운 조명 검사원이다.
  • TraceScreenProbes 안에서 화면 추적, 하드웨어 RT, Mesh SDF/Global SDF, radiance cache가 순서대로 엮인다.
  • TraceRadiance와 TraceHit은 프로브 레이가 가져온 빛과 히트 정보를 적는 중간 장부다.
