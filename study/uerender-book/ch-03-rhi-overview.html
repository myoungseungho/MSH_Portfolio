RHI — CPU가 GPU에게 말 거는 법

언리얼 렌더링 · 03 / 42

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "언리얼이 D3D12/Vulkan 차이를 어디서 가리고, CPU가 어떤 공용 창구로 GPU에게 말 거는지"가 잡힌다.
🧱 먼저 알아야 할 것 — 같은 부탁을 여러 말로 해야 할 때
• 같은 부탁: "문 열어줘"라는 일은 같아도 집, 차, 사물함마다 여는 방법과 부르는 말이 다를 수 있다.
• 중간 사람: 부탁하는 사람은 쉬운 말로 한 번만 말하고, 중간 사람이 상대에게 맞는 말로 바꿔 전한다.
• 하나로 모으기: 종류가 늘어날수록 모두에게 직접 말하기보다 한곳에 맡기는 편이 덜 헷갈린다.
이게 잡히면 아래 RHI 설명이 얹힌다.

왜 이걸 배워? — 문제의식부터

네가 서버를 짜봤으면 이미 비슷한 구조를 알아.

게임 로직은 "이 유저에게 이동 패킷 보내"라고 말하지, 매번 IOCP의 WSASend 세부 옵션을 직접 만지면 안 돼.

DirectX를 만져봤다면 GPU에게 말 거는 일이 훨씬 까다롭다는 것도 알아.

디바이스, 큐, 커맨드 리스트, 리소스 상태, 셰이더 바이트코드까지 정확히 맞춰야 하거든.

그런데 엔진이 D3D12, Vulkan, Metal, NullRHI를 렌더러 곳곳에서 직접 상대하면 어떻게 될까?

텍스처 하나 만들 때도 D3D12면 ID3D12Resource, Vulkan이면 VkImage 식으로 갈라져.

셰이더 하나 만들 때마다 if D3D12, if Vulkan이 퍼지면 기능 하나 고칠 때 플랫폼 수만큼 버그가 늘어나.

그래서 언리얼도 같은 문제를 만났고, 답이 RHI(Render Hardware Interface) 야.

렌더러는 "픽셀 셰이더 만들어", "백버퍼 줘", "프레임 끝났어" 같은 공용 언어로 말한다.

실제 번역은 선택된 RHI 백엔드가 한다.

D3D12RHI가 잡히면 D3D12 말로, VulkanRHI가 잡히면 Vulkan 말로 내려가는 식이야.

왜 지금 배우냐면, 앞 장 render-thread에서 렌더 스레드가 분리되는 이유를 봤어.

이제 그 렌더 스레드가 GPU에게 명령을 내릴 문을 알아야 해.

다음 장 rhi-commandlist는 그 문으로 들어갈 명령을 어떻게 쌓는지 보고, d3d12-backend는 공용 말이 진짜 D3D12 호출로 바뀌는 지점까지 내려갈 거야.

🌱 이 개념은 왜 생겼나 — RHI(Render Hardware Interface)
• 원래 구조: 렌더러가 D3D12면 D3D12 창구, Vulkan이면 Vulkan 창구로 직접 뛰어가서 GPU에게 말하면 돼.
• 그런데 문제: 텍스처 하나, 셰이더 하나 만들 때마다 나라별 말이 갈라져. 기능 1개 고쳐도 D3D12/Vulkan/Metal 줄을 전부 만지면 버그가 나라 수만큼 늘어.
• 그래서 필요한 것: 앞에는 공용 출국 창구 하나를 세우고, 뒤 직원이 각 나라 말로 번역하게 하자. Render Hardware Interface, 줄여서 RHI야. 렌더러가 하드웨어 쪽과 말하는 인터페이스라는 뜻이야.

0. 비유부터 — 공항의 공용 출국 창구

공항을 생각해보자.

너는 여행객이고, 목적지는 여러 나라야.

미국은 영어, 일본은 일본어, 프랑스는 프랑스어를 쓴다.

네가 나라별 서류와 항공사 내부 양식을 전부 외워야 한다면 여행이 아니라 고문이지.

그래서 공항에는 공용 출국 창구가 있어.

너는 창구에 "이 사람을 이 나라로 보내줘", "짐은 이만큼이야", "탑승 준비 끝났어"라고 말한다.

창구 뒤 직원이 항공사별 양식을 알아서 처리해.

RHI가 딱 이 창구야.

CPU 쪽 렌더러는 GDynamicRHI라는 공용 창구 손잡이를 잡고 말한다.

창구 뒤에는 D3D12 직원, Vulkan 직원, Metal 직원, NullRHI 직원이 앉을 수 있어.

중요한 건 렌더러가 항공사 창고까지 직접 뛰어다니지 않는다는 거야.

소스 위치 (아래 코드는 전부 이 클론의 실제 파일에서 그대로 뽑음)
• 공통 구현: Engine/Source/Runtime/RHI/Private/DynamicRHI.cpp
• 공통 인터페이스: Engine/Source/Runtime/RHI/Public/DynamicRHI.h
• Windows 백엔드 선택: Engine/Source/Runtime/RHI/Private/Windows/WindowsDynamicRHI.cpp
🌱 이 개념은 왜 생겼나 — FDynamicRHI
• 원래 구조: 공용 창구가 있다면 렌더러가 "열어", "닫아", "셰이더 만들어" 같은 말을 아무렇게나 던져도 될 것 같아.
• 그런데 문제: D3D12 직원은 Init이 있는데 Vulkan 직원은 이름이 다르면, 홀 직원이 매번 "너는 뭐라고 불러?"부터 물어야 해. 창구가 3개만 돼도 호출 규칙이 엉켜.
• 그래서 필요한 것: 모든 직원이 반드시 지킬 메뉴판이 필요해. 그 설계도가 FDynamicRHI야. virtual 함수들은 "뒤 직원이 자기 방식으로 채워라"라는 빈칸이야.
🧱 먼저 알아야 할 것 — 약속표와 실제 담당자
• 약속표: 여러 사람이 함께 일하려면 "열기, 닫기, 이름 말하기"처럼 꼭 해야 할 일을 같은 이름으로 적어둔다.
• 실제 담당자: 약속표에는 빈칸만 있고, 각 담당자가 자기 방식대로 빈칸을 채운다.
• 부르는 쪽: 부탁하는 사람은 담당자가 누구인지 몰라도 약속표에 적힌 이름으로 부를 수 있다.
이게 잡히면 아래 FDynamicRHI 설명이 얹힌다.

1. RHI 창구의 모양 — FDynamicRHI

먼저 공용 창구의 간판부터 보자.

FDynamicRHI는 "RHI라면 최소한 이런 일을 해야 한다"는 약속을 적어둔 타입이야.

DynamicRHI.h:205

class FDynamicRHI { public: using FRHICalcTextureSizeResult = ::FRHICalcTextureSizeResult; /** Declare a virtual destructor, so the dynamic RHI can be deleted without knowing its type. */ RHI_API virtual ~FDynamicRHI(); /** Initializes the RHI; separate from IDynamicRHIModule::CreateRHI so that GDynamicRHI is set when it is called. */ virtual void Init() = 0; /** Called after the RHI is initialized; before the render thread is started. */ virtual void PostInit() {} /** Shutdown the RHI; handle shutdown and resource destruction before the RHI's actual destructor is called (so that all resources of the RHI are still available for shutdown). */ virtual void Shutdown() = 0; virtual const TCHAR* GetName() = 0; virtual ERHIInterfaceType GetInterfaceType() const { return ERHIInterfaceType::Hidden; } virtual FDynamicRHI* GetNonValidationRHI() { return this; }
🔤 기호 사전 — FDynamicRHI 간판
• class FDynamicRHI = "RHI 창구라면 이런 모양이어야 해"라고 적은 설계도야.
• public: = 밖에서 부를 수 있는 메뉴판 영역이야.
• virtual = 자식 백엔드가 자기 방식으로 갈아끼울 수 있는 함수야.
• = 0 = 몸통이 없는 순수가상 함수. D3D12/Vulkan 같은 실제 직원이 반드시 채워야 해.
• Init() = 창구 문 열기. 실제 디바이스와 기본 상태를 준비하는 시작점이야.
• Shutdown() = 창구 닫기. 리소스가 살아 있을 때 안전하게 정리하는 함수야.
• GetName() = 오늘 창구 뒤에 누가 앉았는지 이름을 물어보는 함수야.
• ERHIInterfaceType::Hidden = 기본 정체성은 숨김. 실제 백엔드는 D3D12, Vulkan 같은 이름표를 줄 수 있어.
🔁 이제 다시 보자. FDynamicRHI는 구현이 아니라 약속이야. 렌더러는 "창구야, 열어", "창구야, 닫아"라고만 말하고, 실제로 D3D12 디바이스를 만들지 Vulkan 인스턴스를 만들지는 뒤 직원이 처리한다.

서버로 치면 INetworkTransport 아래에 TcpTransport, UdpTransport, LoopbackTransport를 꽂는 구조와 비슷해.

게임 로직은 Send()만 부른다.

RHI도 렌더러에게 그런 공용 언어를 준다.

🌱 이 개념은 왜 생겼나 — GDynamicRHI
• 원래 구조: 창구 설계도가 있어도, 렌더러가 매번 "오늘은 D3D12 창구? Vulkan 창구?"를 찾아다니면 돼.
• 그런데 문제: BasePass, Shadow, Lumen 같은 코드가 전부 같은 질문을 반복하면, 공항 안내판이 수백 장으로 흩어진 꼴이야. 하나만 바뀌어도 전부 확인해야 해.
• 그래서 필요한 것: "오늘 열린 창구는 여기야"라고 가리키는 전역 손잡이 하나가 필요해. 그게 GDynamicRHI야. 렌더러는 그 손잡이만 잡고 말하면 돼.
🧱 먼저 알아야 할 것 — 손잡이와 빈자리
• 손잡이: 무거운 물건을 직접 안고 다니지 않고, 그게 어디 있는지 가리키는 끈만 쥐고 있어도 된다. 끈만 따라가면 물건을 찾는다.
• 빈자리: 아직 가리킬 물건이 없으면, 손잡이가 아무것도 안 가리키는 빈 상태로 있을 수 있다.
이게 잡히면 아래 GDynamicRHI 설명이 얹힌다.

2. 창구 손잡이 — GDynamicRHI

공항에는 여러 항공사가 있어도 승객은 안내판에 적힌 "오늘 여기로 오세요" 창구 하나를 찾아가.

언리얼의 그 안내판이 전역 포인터 GDynamicRHI야.

DynamicRHI.cpp:34

// Globals. FDynamicRHI* GDynamicRHI = NULL; RHIGetGPUUsageType RHIGetGPUUsage = nullptr; bool bDriverDenylistMessageShown = false;
🔤 기호 사전 — 전역 RHI 손잡이
• FDynamicRHI* = FDynamicRHI 실물을 직접 들고 있는 게 아니라, 그 실물을 가리키는 손잡이야.
• GDynamicRHI = 오늘 선택된 RHI 창구. D3D12일 수도, NullRHI일 수도 있어.
• NULL = 아직 창구가 안 정해졌다는 빈값이야.
• nullptr = 새 C++식 빈 포인터야.
• bool = 참/거짓 값. 드라이버 경고 팝업을 이미 보여줬는지 기록해.

렌더러 곳곳은 "D3D12 객체 어디 있어?"라고 묻지 않는다.

대부분은 GDynamicRHI를 통해 공용 함수로 간다.

창구 뒤 직원이 D3D12인지 Vulkan인지는 이 손잡이 안쪽 문제야.

🌱 이 개념은 왜 생겼나 — RHIInit
• 원래 구조: 프로그램 시작하자마자 렌더러가 알아서 창구를 하나 잡고 쓰면 될 것 같아.
• 그런데 문제: 어떤 PC는 렌더링을 못 하고, 어떤 설정은 Vulkan을 원하고, Windows와 Linux는 고르는 방법도 달라. 첫 주문이 오기 전에 창구가 비어 있으면 바로 터져.
• 그래서 필요한 것: 엔진 시작 때 "렌더링 가능해?", "어느 플랫폼이야?", "어느 창구 열까?"를 한 번 정하는 입구가 필요해. 그게 RHIInit이야.

3. 시작할 때 창구를 고른다 — RHIInit

GDynamicRHI는 엔진 시작 중 RHIInit에서 채워진다.

렌더링을 아예 할 수 없는 상황이면 NullRHI.

렌더링을 할 수 있으면 플랫폼이 실제 Dynamic RHI를 만든다.

• void RHIInit(bool bHasEditorToken) = 값을 돌려주지 않는 RHI 초기화 함수야.
• if (!GDynamicRHI) = 아직 창구가 없을 때만 안쪽 초기화를 한다. !는 참/거짓 뒤집기야.

• GRHICommandList.LatchBypass() = 커맨드 리스트 우회 옵션을 커맨드라인에서 붙잡아둔다.
• FApp::CanEverRender() = 이 실행 환경이 애초에 렌더링을 할 수 있는지 묻는다.
• InitNullRHI() = 진짜 GPU 창구 대신 아무것도 그리지 않는 Null 창구를 연다.
• PlatformCreateDynamicRHI() = Windows/Linux/Android 같은 플랫폼별 코드에게 "오늘 쓸 RHI 창구 만들어줘"라고 맡긴다.
🔁 이제 다시 보자. RHIInit은 셰이더 플랫폼 정보와 커맨드 리스트 설정을 잡고, 렌더링 불가 환경이면 InitNullRHI()로 빈 창구를 열어. 렌더링 가능하면 PlatformCreateDynamicRHI()로 실제 창구를 만든다. 공항에서 "오늘 어느 항공사 카운터를 열지" 정하는 장면이야.

Windows가 뭘 고를지는 Windows 파일이 정하고, Linux가 뭘 고를지는 Linux 파일이 정해.

4. Windows는 D3D12/Vulkan 모듈 이름을 고른다

Windows 쪽은 선택지를 실제 모듈 이름으로 바꾼다.

여기서 D3D12와 Vulkan 차이가 창구 뒤로 밀려난다.

🔤 기호 사전 — 선택지를 모듈 이름으로 바꾸기
• switch = 값이 무엇인지에 따라 여러 갈래 중 하나를 고르는 문법이야.
• case EWindowsRHI::D3D12 = 선택지가 D3D12라면 이 줄을 탄다는 뜻이야.
• return TEXT("D3D12RHI") = 호출한 쪽에 D3D12RHI라는 모듈 이름을 돌려준다.
• VulkanRHI = Vulkan 직원이 들어 있는 모듈 이름이야.
• default: check(false); = 예상 못 한 값이면 개발 중에 바로 터뜨리는 안전장치야.

짧지만 이 토막이 "D3D12/Vulkan 차이를 가리는 층"을 잘 보여줘.

앞면은 EWindowsRHI라는 엔진 선택지야.

뒤쪽은 D3D12RHI, VulkanRHI라는 실제 모듈 이름이야.

승객은 공용 창구로 가고, 공항은 내부 항공사 이름표를 찾아간다.

• nullptr = 아직 만든 창구가 없다는 빈값이야.
• RequestedFeatureLevel = 이 창구가 어느 기능 레벨로 열릴지 담는 값이야.
• LoadedRHIModuleName = 실제로 로드한 모듈 이름표야.
• LoadDynamicRHIModule(...) = 설정과 지원 여부를 보고 모듈을 고르는 함수야.
• DynamicRHIModule->CreateRHI(...) = 모듈에게 "이 기능 레벨로 실제 RHI 객체 만들어"라고 시킨다.
• GLoadedRHIModuleName = 나중에 로그나 프로파일러가 "오늘 D3D12RHI 씀" 같은 정보를 볼 수 있게 저장하는 이름표야.
🔁 이제 다시 보자. PlatformCreateDynamicRHI()는 LoadDynamicRHIModule로 모듈을 고르고, 모듈이 있으면 CreateRHI로 실제 FDynamicRHI 자식 객체를 만든다. 그래서 공통 RHIInit은 Windows가 D3D12를 골랐는지 Vulkan을 골랐는지 몰라도 GDynamicRHI = PlatformCreateDynamicRHI(); 한 줄로 받아올 수 있어.

여기서 드디어 GDynamicRHI가 채워진다.

6. 공용 함수들은 GDynamicRHI로 보낸다

창구가 정해졌으면 이제 상위 렌더러는 공용 함수만 부르면 된다.

아래는 셰이더를 만드는 작은 래퍼들이야.

직접 D3D12 API를 부르지 않고 GDynamicRHI->...로 넘긴다.

🔤 기호 사전 — 공용 생성 함수
• inline = 헤더 안에 작게 펼칠 수 있는 함수라는 뜻이야.
• FPixelShaderRHIRef = 픽셀 셰이더 RHI 리소스 손잡이야.
• TArrayView<const uint8> Code = 셰이더 바이트코드를 복사하지 않고 바라보는 얇은 창이야.
• const FSHAHash& Hash = 셰이더 코드의 해시를 참조로 받는다.
• LLM_SCOPE(ELLMTag::Shaders) = 메모리 추적에서 "셰이더 관련 작업"이라고 표시하는 범위야.
• return GDynamicRHI->RHICreatePixelShader(...) = 공용 함수가 실제 창구 뒤 직원에게 일을 넘기는 줄이야.
🔁 이제 다시 보자. 렌더러가 RHICreatePixelShader를 부르면 이 함수가 직접 D3D12 API를 호출하지 않아. GDynamicRHI->RHICreatePixelShader로 넘긴다. D3D12 창구가 열렸으면 D3D12 방식으로 만들고, 다른 창구가 열렸으면 그쪽 방식으로 만든다.

이게 렌더러를 살려준다.

BasePass, Shadow, Lumen 같은 상위 렌더링 코드는 "픽셀 셰이더 필요해"라고만 말하면 돼.

D3D12의 루트 시그니처나 Vulkan의 디스크립터 셋 같은 디테일은 백엔드 쪽으로 내려간다.

실제 D3D12 백엔드 안쪽은 → d3d12-backend
🧱 먼저 알아야 할 것 — 끝내기 전 남은 일 비우기
• 남은 줄: 가게 문을 닫기 전에 기다리던 손님을 먼저 처리해야 한다.
• 빌린 물건: 빌린 도구는 주인이 아직 쓸 때 버리면 사고가 나니, 순서대로 반납해야 한다.
• 빈 표시: 다 치운 뒤에는 "이제 없음"이라고 표시해야 다음 사람이 헷갈리지 않는다.
이게 잡히면 아래 RHIExit 설명이 얹힌다.

7. 열었으면 닫는다 — RHIExit

창구는 시작할 때만 중요한 게 아니야.

끝날 때도 중요해.

GPU 명령이 남아 있는데 디바이스를 먼저 부수면 사고 난다.

그래서 종료 때는 캐시를 정리하고, 밀린 명령을 플러시하고, RHI를 닫고, 포인터를 비운다.

DynamicRHI.cpp:432

void RHIExit() { if (!GUsingNullRHI && GDynamicRHI != NULL) { // Clean up all cached pipelines PipelineStateCache::Shutdown(); // Flush any potential commands queued before we shut things down. FRHICommandListExecutor::GetImmediateCommandList().ImmediateFlush(EImmediateFlushType::FlushRHIThread); // Destruct the dynamic RHI. GDynamicRHI->Shutdown(); delete GDynamicRHI; GDynamicRHI = NULL; #if RHI_ENABLE_RESOURCE_INFO FRHIResource::StopTrackingAllResources(); #endif } else if (GUsingNullRHI) { // If we are using NullRHI flush the command list here in case somethings has been added to the command list during exit calls FRHICommandListExecutor::GetImmediateCommandList().ImmediateFlush(EImmediateFlushType::FlushRHIThreadFlushResources); FRHICommandListExecutor::GetImmediateCommandList().ImmediateFlush(EImmediateFlushType::FlushRHIThread); } GRHICommandList.CleanupGraphEvents(); }
🔤 기호 사전 — RHI 종료
• RHIExit() = RHI 창구를 닫는 엔진 종료 루틴이야.
• !GUsingNullRHI && GDynamicRHI != NULL = NullRHI가 아니고 실제 창구가 있을 때만 일반 종료를 탄다.
• PipelineStateCache::Shutdown() = 미리 구워둔 파이프라인 상태 캐시를 정리한다.
• ImmediateFlush(EImmediateFlushType::FlushRHIThread) = 밀린 RHI 스레드 명령을 즉시 밀어낸다.
• GDynamicRHI->Shutdown() = 창구 뒤 직원에게 "네 리소스부터 안전하게 정리해"라고 시킨다.
• delete GDynamicRHI = 창구 객체 자체를 메모리에서 없앤다.
• GDynamicRHI = NULL = 이제 창구 손잡이가 빈값이라고 표시한다.

종료는 PipelineStateCache::Shutdown()으로 PSO 캐시를 치우고, ImmediateFlush로 밀린 명령을 비운 뒤, GDynamicRHI->Shutdown()으로 실제 백엔드 리소스를 정리한다.

공항으로 치면 승객 줄을 다 처리하고, 항공사 카운터 장비를 반납하고, 안내판에서 창구 번호를 지우는 순서야.

콜/데이터 흐름 한눈에

엔진 시작 | v RHIInit (:278) | +-- 렌더링 불가 -> InitNullRHI (:60) | +-- 렌더링 가능 | v PlatformCreateDynamicRHI (:1243, WindowsDynamicRHI.cpp) | v LoadDynamicRHIModule (:1147, WindowsDynamicRHI.cpp) | +-- D3D12 -> "D3D12RHI" (:141) +-- Vulkan -> "VulkanRHI" (:142) | v DynamicRHIModule->CreateRHI(...) | v GDynamicRHI = 실제 FDynamicRHI 자식 객체 | v 상위 렌더러 공용 호출 | +-- RHICreatePixelShader (:1093) +-- RHICreateVertexShader (:1099) +-- RHICreateMeshShader (:1105) | v GDynamicRHI->RHI...() | v D3D12RHI / VulkanRHI / NullRHI 실제 구현 | v GPU 드라이버와 하드웨어 엔진 종료 | v RHIExit (:432)

이 그림에서 제일 중요한 선은 GDynamicRHI = PlatformCreateDynamicRHI()야.

이 한 줄 때문에 위쪽 렌더러는 공용 언어를 쓰고, 아래쪽 백엔드는 자기 나라 말을 쓴다.

우리 서버·DirectX 랑 비교

우리 조선 서버랑 비교하면 RHI는 "게임 로직과 실제 IO 구현 사이의 어댑터"야.

서버 로직은 SP_ITEM_DROP을 보낸다고 말하지, 그게 TCP send buffer에 몇 바이트로 쪼개져 들어가는지는 전송 계층이 처리해.

RHI도 비슷해.

렌더러는 "픽셀 셰이더 만들어"라고 말하지, D3D12에서 루트 시그니처와 PSO 캐시를 어떻게 엮는지는 D3D12RHI가 처리해.

DirectX 경험이 있으면 ID3D12Device, ID3D12CommandQueue, ID3D12GraphicsCommandList부터 떠올릴 거야.

언리얼 상위 렌더러는 그 이름들을 매번 직접 만지지 않아.

앞쪽에서는 FRHITexture, FRHIBuffer, FRHICommandList, FDynamicRHI 같은 언리얼식 단어를 먼저 본다.

대신 상위 렌더러가 플랫폼 분기 지옥에 빠지지 않게 막는 거야.

이 챕터에서 딱 이것만

  • RHI는 렌더러가 GPU 백엔드에게 말하는 공용 창구야.
  • FDynamicRHI는 그 창구가 지켜야 할 인터페이스고, GDynamicRHI는 오늘 선택된 창구 손잡이야.
  • RHIInit은 PlatformCreateDynamicRHI()로 실제 백엔드를 만들고, Windows는 D3D12RHI나 VulkanRHI 같은 모듈을 고른다.
  • 상위 렌더러의 RHICreatePixelShader 같은 공용 함수는 직접 D3D12를 부르지 않고 GDynamicRHI->...로 넘긴다.
  • 다음 장 rhi-commandlist는 이 창구에 제출할 명령 묶음을 어떻게 쌓는지 보는 장이야.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. RHI가 정확히 뭐고, 왜 필요한가요?

답 보기
RHI(Render Hardware Interface)는 렌더러가 GPU 백엔드에게 말하는 공용 창구야. 렌더러는 "픽셀 셰이더 만들어", "백버퍼 줘", "프레임 끝났어" 같은 공용 언어로만 말하고, 실제 번역은 선택된 백엔드(D3D12·Vulkan·Metal)가 해. 안 나누면 텍스처 하나 만들 때도 D3D12면 ID3D12Resource, Vulkan이면 VkImage 식으로 갈라져서, 기능 하나 고칠 때 플랫폼 수만큼 버그가 늘어. 공항의 공용 출국 창구랑 같아 — 승객은 창구에 "이 나라로 보내줘"라고만 말하고, 창구 뒤 직원이 항공사별 양식을 알아서 처리하는 거지.

↳ 앞 장 render-thread에서 봤던 렌더 스레드랑은 어떻게 이어지나요?

답 보기
렌더 스레드는 "게임 스레드와 분리된 CPU 쪽 주방"이었잖아. 그 주방이 GPU에게 명령을 내릴 문이 바로 RHI야. 렌더 스레드가 만든 렌더 명령이 결국 이 공용 창구를 통해 GPU로 내려가. 그래서 순서가 "게임 스레드 → 렌더 스레드 → RHI 창구 → 실제 백엔드"로 이어지는 거야.

Q2. FDynamicRHI랑 GDynamicRHI는 뭐가 다른가요?

답 보기
FDynamicRHI는 창구가 지켜야 할 약속표(인터페이스)야. "RHI라면 최소한 Init, Shutdown, GetName은 해야 해" 하고 빈칸(virtual)을 적어둔 설계도지. GDynamicRHI는 그 설계도를 실제로 채운 오늘 선택된 창구 손잡이(전역 포인터)야. BasePass·Shadow·Lumen 같은 코드가 전부 "오늘 D3D12야? Vulkan이야?"를 반복해서 물으면 안내판이 수백 장으로 흩어지니까, "오늘 열린 창구는 여기야"라고 가리키는 손잡이 하나를 둔 거야.

↳ 그 손잡이는 언제, 어떻게 채워지나요?

답 보기
엔진 시작 때 RHIInit에서 딱 한 번 정해져. 렌더링을 아예 못 하는 환경이면 NullRHI(아무것도 안 그리는 빈 창구)를 열고, 할 수 있으면 PlatformCreateDynamicRHI()로 실제 창구를 만들어. Windows면 그 안에서 D3D12RHI·VulkanRHI 같은 모듈 이름을 골라 로드해. 첫 주문이 오기 전에 창구가 비어 있으면 바로 터지니까, 시작할 때 "렌더링 가능해? 어느 플랫폼이야? 어느 창구 열까?"를 한 번에 정하는 거야.

Q3. Windows에서 D3D12냐 Vulkan이냐 하는 차이는 어디서 가려지나요?

답 보기
Windows 전용 코드가 엔진 선택지(EWindowsRHI::D3D12 같은)를 실제 모듈 이름("D3D12RHI", "VulkanRHI")으로 바꿔서 로드해. 여기서 D3D12/Vulkan 차이가 창구 뒤로 밀려나. 앞면은 엔진 공용 선택지고, 뒷면은 실제 나라별 항공사 카운터야. 승객은 공용 창구로 가고, 공항이 내부 항공사 이름표를 찾아가는 셈이지. 그래서 공통 RHIInit은 Windows가 뭘 골랐는지 몰라도 GDynamicRHI = PlatformCreateDynamicRHI() 한 줄로 받아올 수 있어.

↳ 그럼 RHICreatePixelShader 같은 공용 함수를 부르면 실제로 뭐가 일어나요?

답 보기
그 함수가 직접 D3D12 API를 부르는 게 아니라 GDynamicRHI->RHICreatePixelShader(...)로 넘겨. D3D12 창구가 열렸으면 D3D12 방식으로 만들고, 다른 창구면 그쪽 방식으로 만들어. 덕분에 BasePass·Shadow·Lumen 같은 상위 코드는 "픽셀 셰이더 필요해"라고만 말하면 되고, D3D12 루트 시그니처나 Vulkan 디스크립터 셋 같은 디테일은 백엔드로 내려가. 이게 상위 렌더러를 플랫폼 분기 지옥에서 살려주는 거야.

Q4. 우리 서버나 DirectX 직접 짜던 경험이랑 비교하면요?

답 보기
서버로 치면 RHI는 게임 로직과 실제 IO 구현 사이의 어댑터야. 로직은 "이 유저에게 이동 패킷 보내"라고 말하지, 그게 TCP send buffer에 몇 바이트로 쪼개지는지는 전송 계층이 처리하잖아. RHI도 렌더러가 "픽셀 셰이더 만들어"라고만 말하고, D3D12 루트 시그니처·PSO 캐시를 어떻게 엮는지는 D3D12RHI가 처리해. DirectX 직접 짜봤으면 ID3D12Device·ID3D12CommandQueue부터 떠오르겠지만, 언리얼 상위 렌더러는 그 이름들을 매번 직접 만지지 않고 FRHITexture·FRHICommandList 같은 언리얼식 단어를 먼저 봐.

↳ 그럼 창구는 닫을 때도 순서가 중요한가요?

답 보기
응, GPU 명령이 남아 있는데 디바이스를 먼저 부수면 사고가 나. 그래서 종료(RHIExit) 때는 PSO 캐시 정리 → 밀린 명령 플러시 → 백엔드 리소스 정리(Shutdown) → 손잡이 비우기 순서를 지켜. 공항으로 치면 승객 줄 다 처리하고, 카운터 장비 반납하고, 안내판에서 창구 번호를 지우는 순서야. 서버에서 세션 버퍼를 아직 쓰는 중에 free하면 터지는 거랑 똑같은 감각이지.

↳ 그럼 RHI는 "언제·무슨 순서로"까지 정하나요?

답 보기
아니, 거기서 층을 구분해야 해. RHI는 "무슨 장비 언어로"(통역)만 맡아 — "픽셀 셰이더 만들어", "삼각형 그려" 같은 말을 D3D12/Vulkan 말로 바꾸는 거지. "언제·무슨 순서로 실행할지"(진행표)는 위쪽의 RDG가, 그 명령을 어떤 종이에 쌓아 제출할지는 다음 장 rhi-commandlist가 맡아. RHI 창구는 어느 나라 말로 번역하느냐만 책임진다고 보면 돼.
