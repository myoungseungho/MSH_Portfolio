왜 이걸 배워? — 문제의식부터

DirectX를 만져봤으면 셰이더 컴파일은 낯설지 않아. HLSL을 쓰고, DXC 같은 컴파일러를 태우고, 나온 바이트코드를 PSO에 꽂지.

그런데 언리얼은 그 단순한 그림보다 훨씬 커. 같은 .usf라도 플랫폼, 엔트리 함수, 머티리얼 옵션, 레이 트레이싱, bindless, 개발용 디버그 플래그가 다르면 결과가 갈라져.

이걸 매번 생으로 컴파일하면 에디터 켜자마자 "Compiling Shaders 6000" 같은 숫자가 뜨고, 작은 머티리얼 수정 하나에도 몇 분씩 멈춘다.

서버로 치면 클라 하나 들어올 때마다 CM_* 디스패치 테이블과 SP_* 메타데이터를 전부 새로 만드는 꼴이야.

언리얼도 같은 문제를 만났고, 답이 셰이더 컴파일 파이프라인과 캐시야.

.usf를 바로 GPU에 던지는 게 아니라, 컴파일 환경을 붙이고, 전처리하고, 플랫폼 백엔드가 최종 코드를 만들고, 결과를 해시와 DDC에 넣어 다음엔 다시 안 하려 해.

앞 장 shader-basics에서는 "셰이더는 GPU에서 도는 작은 프로그램"까지만 봤어.

다음 장 shader-parameters에서는 C++ 값이 셰이더 변수에 꽂히는 길을 볼 거야.

그 사이에 "그 작은 프로그램이 애초에 어떻게 만들어지고 캐시에 박히는가"를 잡아야 뒤가 읽힌다.

0. 비유부터 — 식당 주방의 레시피 인쇄소

이번 장의 비유는 식당 주방의 레시피 인쇄소야.

원본 레시피가 하나 있어도 주문 옵션은 계속 달라져.

김치볶음밥 하나도 매운맛, 안 매운맛, 치즈 추가, 포장용, 홀용이 갈라지잖아.

주방은 이렇게 돈다고 치자.

  1. 레시피 원본 — .usf/.ush 파일.
  2. 주문 옵션 붙이기 — 컴파일 환경, define, 플랫폼 설정.
  3. 작업지시서 정리 — include와 조건문이 정리된 전처리 결과.
  4. 매장별 기계로 인쇄 — D3D, Vulkan, Metal 백엔드 컴파일.
  5. 완성 카드 보관 — 캐시/DDC.

셰이더 컴파일도 이거야.

원본 레시피만으로는 부족하고, 주문 옵션까지 합쳐야 진짜 결과가 나온다.

그리고 같은 주문이 다시 오면 창고에서 완성 카드를 꺼내야지, 매번 새로 인쇄하면 장사가 안 된다.

🌱 이 개념은 왜 생겼나 — 컴파일 환경
• 원래 구조: 원본 레시피(.usf) 하나를 그대로 기계에 넣고 카드 하나만 뽑으면 제일 단순해.
• 그런데 문제: 같은 김치볶음밥도 매운맛, 치즈 추가, 포장용이 갈라지듯이 같은 셰이더도 플랫폼, 함수 이름, bindless 설정이 달라지면 결과가 달라져.
• 그래서 필요한 것: 원본 옆에 "이번 주문 옵션"을 붙이는 상자가 필요해. 그게 컴파일 환경이야.
🧱 먼저 알아야 할 것 — 원본에 붙는 조건표
• 원본: 같은 요리법이나 놀이 규칙도 기본 종이는 하나일 수 있다.
• 조건표: "매운맛", "포장", "어린이용"처럼 작은 쪽지가 붙으면 해야 할 일이 달라진다.
• 같은지 판단하기: 원본만 같다고 같은 결과가 아니고, 붙은 쪽지까지 같아야 같은 결과다.
이게 잡히면 아래 컴파일 환경 설명이 얹힌다.

1. 먼저 주문 옵션을 붙인다

주요 소스인 Shader.cpp에서 먼저 볼 곳은 FShaderType::ModifyCompilationEnvironment야.

셰이더 타입마다 "이번 컴파일에 어떤 define과 바인딩 정보를 넣을지"를 여기서 환경에 적어 넣는다.

레시피 원본에 "치즈 추가, 포장용, 3번 매장 기계용" 같은 주문 메모를 붙이는 단계야.

Shader.cpp:480

🔤 기호 사전 — 컴파일 환경 만들기
• FShaderType:: = FShaderType 안에 있는 함수라는 뜻이야.
• const = 이 함수가 자기 상태를 함부로 바꾸지 않겠다는 약속이야.
• & OutEnvironment = 환경 상자를 복사하지 않고 원본에 바로 적겠다는 뜻이야.
• (*ModifyCompilationEnvironmentRef)(...) = 타입별 환경 설정 함수를 함수 포인터로 부르는 거야.
• ShaderBindingLayout = 셰이더가 리소스를 어떤 모양으로 받을지 적은 배치표야.
• ->RHILayout = 포인터가 가리키는 물건 안의 RHILayout을 꺼내는 화살표야.
• Frequency == SF_RayHitGroup = 레이 트레이싱 hit group 셰이더인지 확인하는 조건이야.
• SetDefine(FunctionName, FunctionName) = 셰이더 안에서 #ifdef 함수이름으로 갈라탈 수 있게 define을 박는 거야.

같은 .usf라도 이 환경이 달라지면 다른 주문이 된다.

서버에서 같은 패킷 ID라도 시즌 플래그나 지역 설정이 다르면 다른 처리로 가는 것과 비슷해.

여기서부터 캐시 키가 달라질 씨앗이 생긴다.

🔁 이제 다시 보자. 타입별 설정 함수가 환경을 채우고 → 바인딩 레이아웃이 있으면 RHI용 레이아웃을 넣고 → 일반 셰이더면 함수 이름을 define으로 박아. 이어 읽으면 "원본 레시피에 이번 주문 옵션을 붙인다"는 뜻이야.
🌱 이 개념은 왜 생겼나 — 전처리
• 원래 구조: 주문 옵션을 붙였으니 바로 매장별 기계에 넣어 구우면 될 것 같아.
• 그런데 문제: 레시피 안에 "소스 레시피 참고", "매운맛이면 이 줄 사용" 같은 include와 조건문이 남아 있으면 기계마다 읽는 방식이 꼬일 수 있어.
• 그래서 필요한 것: 먼저 레시피를 펼치고 조건을 정리한 작업지시서가 필요해. 그 정리 단계가 전처리야.
🧱 먼저 알아야 할 것 — 미리 펼쳐 한 장으로 정리하기
• 참고 펼치기: "3쪽 표를 붙여라"라고 적혀 있으면 실제로 그 표를 가져와 옆에 붙인다.
• 조건 고르기: "비 오면 우산, 맑으면 모자"처럼 지금 맞는 줄만 남긴다.
• 정리본: 여기저기 흩어진 종이를 한 사람이 바로 읽을 수 있게 한 묶음으로 만든다.
이게 잡히면 아래 전처리 설명이 얹힌다.

2. .usf를 바로 굽지 않고 전처리한다

이제 ShaderCore.cpp의 실제 파이프라인으로 내려가자.

전처리는 include를 펼치고, define을 적용하고, 조건부 코드를 정리해서 백엔드가 먹기 좋은 작업지시서로 만드는 단계야.

언리얼 C++ 코드에서 보이는 대표 중간 산출물은 FShaderPreprocessOutput이다.

ShaderCore.cpp:1804

static void PreprocessShaderInternal( const IShaderFormat* Backend, FShaderCompileJob& Job, const FShaderCompilerEnvironment& Environment) { if (!GBreakOnPreprocessJob.IsEmpty()) { if (Job.Input.DebugGroupName.Contains(GBreakOnPreprocessJob, ESearchCase::IgnoreCase)) { UE_DEBUG_BREAK(); } } double PreprocessStartTime = FPlatformTime::Seconds(); Job.PreprocessOutput.bSucceeded = Backend->PreprocessShader(Job.Input, Environment, Job.PreprocessOutput); Job.PreprocessOutput.PreprocessTime = FPlatformTime::Seconds() - PreprocessStartTime; if (Job.PreprocessOutput.bSucceeded && Backend->RequiresSecondaryCompile(Job.Input, Environment, Job.PreprocessOutput)) { PreprocessStartTime = FPlatformTime::Seconds(); Job.SecondaryPreprocessOutput = MakeUnique<FShaderPreprocessOutput>(); Job.SecondaryPreprocessOutput->bIsSecondary = true; Job.SecondaryPreprocessOutput->bSucceeded = Backend->PreprocessShader(Job.Input, Environment, *Job.SecondaryPreprocessOutput); Job.SecondaryPreprocessOutput->PreprocessTime = FPlatformTime::Seconds() - PreprocessStartTime; // Mark the main job preprocess output as failed if the secondary preprocess fails, even if the primary succeeds // This means the job submission code only needs to check one flag to determine whether to actually submit the job // (no point in trying to compile if either of the two preprocess steps fail) Job.PreprocessOutput.bSucceeded &= Job.SecondaryPreprocessOutput->bSucceeded; } }
🔤 기호 사전 — 전처리 단계
• static void = 객체 없이 부를 수 있고 돌려주는 값은 없는 함수야.
• const IShaderFormat* Backend = 플랫폼별 셰이더 컴파일러 손잡이야.
• FShaderCompileJob& Job = 컴파일 일감 하나야. 입력, 전처리 결과, 최종 출력이 이 안에 들어 있어.
• FPlatformTime::Seconds() = 현재 시간을 재서 걸린 시간을 계산하려는 거야.
• Backend->PreprocessShader(...) = 백엔드에게 "먼저 전처리해줘"라고 시키는 호출이야.
• Job.PreprocessOutput = 전처리된 작업지시서 상자야.
• RequiresSecondaryCompile = 보조 전처리/컴파일이 더 필요한지 묻는 함수야.
• MakeUnique<FShaderPreprocessOutput>() = 보조 전처리 결과 상자를 새로 만드는 거야.
• &= = 왼쪽 값과 오른쪽 값을 AND 해서 다시 왼쪽에 저장하는 표기야.

여기서 "중간표현"을 너무 거창하게 잡지 말자.

이 파일에서 직접 보이는 중간 결과는 Job.PreprocessOutput이야.

원본 .usf도 아니고 최종 GPU 바이트코드도 아닌, 백엔드로 넘길 준비가 된 작업지시서다.

🔁 이제 다시 보자. 시간을 재고 → Backend->PreprocessShader로 전처리하고 → 결과를 Job.PreprocessOutput에 넣고 → 필요하면 보조 전처리도 한다. 이어 읽으면 "레시피 원본을 매장 기계가 읽기 좋은 작업지시서로 정리한다"야.
🌱 이 개념은 왜 생겼나 — 백엔드
• 원래 구조: 언리얼 본체가 D3D, Vulkan, Metal 카드를 전부 직접 뽑으면 단순해 보여.
• 그런데 문제: 매장 기계가 다르면 종이 크기와 잉크가 달라. D3D용 결과와 Metal용 결과를 한 기계가 똑같이 뽑는다고 믿으면 바로 깨져.
• 그래서 필요한 것: 공통 주방은 작업지시서까지만 만들고, 마지막 인쇄는 매장별 기계에 맡겨야 해. 그 손잡이가 백엔드야.

3. 백엔드가 최종 코드를 만든다

전처리가 끝나면 이제 진짜 컴파일이야.

렌더코어가 모든 플랫폼 컴파일러를 직접 품고 있지는 않아.

IShaderFormat이라는 백엔드 인터페이스를 통해 D3D, Vulkan, Metal 같은 쪽으로 넘긴다.

ShaderCore.cpp:1950

static void InvokeCompile(const IShaderFormat* Compiler, FShaderCompileJob& Job, const FString& WorkingDirectory, FString& OutExceptionMsg, FString& OutExceptionCallstack) { #if PLATFORM_WINDOWS __try #endif { // decompress if necessary; this is a no-op if source is not compressed. Job.PreprocessOutput.DecompressCode(); if (Job.SecondaryOutput.IsValid()) { check(Job.SecondaryPreprocessOutput.IsValid()); Job.SecondaryPreprocessOutput->DecompressCode(); Compiler->CompilePreprocessedShader(Job.Input, Job.PreprocessOutput, *Job.SecondaryPreprocessOutput, Job.Output, *Job.SecondaryOutput, WorkingDirectory); } else { Compiler->CompilePreprocessedShader(Job.Input, Job.PreprocessOutput, Job.Output, WorkingDirectory); } }
🔤 기호 사전 — 백엔드 컴파일 단계
• InvokeCompile = 실제 백엔드 컴파일 호출을 감싸는 함수야.
• IShaderFormat* Compiler = 플랫폼별 셰이더 컴파일러 인터페이스야.
• FString& WorkingDirectory = 작업 폴더 문자열을 원본 참조로 받는 거야.
• #if PLATFORM_WINDOWS = 윈도우 빌드일 때만 아래 코드를 넣는 전처리 조건이야.
• __try = 윈도우 예외를 잡기 위한 특수 구문이야.
• DecompressCode() = 전처리 결과가 압축돼 있으면 풀고, 아니면 아무 일도 안 해.
• IsValid() = 보조 출력 상자가 있는지 확인하는 함수야.
• CompilePreprocessedShader = 전처리된 셰이더를 최종 출력으로 바꾸는 백엔드 호출이야.

핵심 줄은 Compiler->CompilePreprocessedShader(...)야.

언리얼은 "무엇을 어떤 환경으로 컴파일할지"를 정리하고, 최종 언어 변환은 백엔드 기계에 맡긴다.

서버로 치면 공통 패킷 프레임워크가 CM_LOGIN을 로그인 모듈로 넘기고, 실제 처리는 그 모듈이 하는 구조랑 비슷해.

🔁 이제 다시 보자. 전처리 결과 압축을 풀고 → 보조 출력이 있으면 보조 결과도 풀고 → CompilePreprocessedShader로 백엔드에 넣는다. 이어 읽으면 ".usf 원본이 아니라 전처리된 결과를 플랫폼 컴파일러에 넘긴다"는 말이 보인다.
🌱 이 개념은 왜 생겼나 — 입력 해시(캐시 키)
• 원래 구조: 같은 .usf 파일명이면 같은 완성 카드라고 보고 창고에서 꺼내 쓰면 편해.
• 그런데 문제: 파일명은 같은데 치즈 추가 define 하나가 바뀌면 완전히 다른 카드야. 예전 카드를 쓰면 화면이 틀린 재료로 그려져.
• 그래서 필요한 것: 파일명 말고 주문 옵션, 매장, 정리된 작업지시서까지 다 섞은 카드 번호가 필요해. 그게 입력 해시, 캐시에서 찾을 때 쓰는 키야.
🧱 먼저 알아야 할 것 — 물건을 헷갈리지 않게 찾는 번호표
• 번호표: 가방을 맡길 때 이름 대신 번호표를 받으면, 나중에 같은 번호로 정확히 찾을 수 있다.
• 작은 차이: 색이나 크기가 조금만 달라도 다른 물건이면 번호표도 달라야 한다.
• 보관함: 자주 다시 쓸 물건은 번호표와 함께 넣어 두면, 다음엔 새로 만들지 않고 꺼내 쓴다.
이게 잡히면 아래 캐시 키 설명이 얹힌다.

4. 캐시 키는 원본 파일명이 아니라 입력 지문이다

셰이더 컴파일이 느린 가장 큰 이유는 조합이 많기 때문이야.

원본, 엔트리 포인트, 타깃, 포맷, define, 공유 환경, 전처리 결과가 전부 결과를 바꿀 수 있어.

그래서 언리얼은 입력 전체를 해시로 만든다.

이 해시가 같아야 "같은 레시피 카드"라고 믿을 수 있다.

ShaderCore.cpp:4363

FShaderCompilerInputHash FShaderCompileJob::GetInputHash() { if (bInputHashSet) { return InputHash; } FMemoryHasherBlake3 Hasher; FGuid ShaderCacheVersionLocal = UE_SHADER_CACHE_VERSION; Hasher << ShaderCacheVersionLocal; uint32 FormatVersion = GetTargetPlatformManagerRef().ShaderFormatVersion(Input.ShaderFormat); Hasher << FormatVersion; Hasher << Input.PreferredShaderCodeFormat; FShaderTarget Target = Input.Target; Hasher << Target; Hasher << Input.EntryPointName; // Include this flag, so shader pipeline jobs get a different hash from single shader jobs, even if the preprocessed shader is otherwise the same. 🔤 기호 사전 — 입력 해시 만들기
• FShaderCompilerInputHash = 컴파일 입력을 대표하는 지문 같은 값이야.
• bInputHashSet = 이미 해시를 계산했는지 보는 bool 플래그야.
• FMemoryHasherBlake3 = 여러 값을 넣어 강한 해시를 만드는 도구야.
• Hasher << 값 = 값을 해시 재료로 밀어 넣는 표기야.
• UE_SHADER_CACHE_VERSION = 셰이더 캐시 전체 버전이야.
• Input.ShaderFormat = D3D, Vulkan, Metal 같은 목표 포맷 이름이야.
• Input.EntryPointName = 셰이더 안에서 시작할 함수 이름이야.
• Input.bBindlessEnabled = bindless 설정이 켜졌는지 보는 값이야.
• MergedEnvironment.Merge(...) = 개인 환경과 공유 환경을 합치는 작업이야.
• auto HashDirectives = [...] = 그 자리에서 작은 익명 함수를 만드는 람다야.
• PreprocessOutput.EditSource() = 전처리된 소스 본문을 해시 재료로 넣는 거야.

이 코드가 "작은 define 하나 바꿨는데 왜 다시 컴파일하지?"의 답이야.

해시 재료가 하나라도 바뀌면 도장 번호가 달라진다.

도장 번호가 달라지면 창고에서 예전 카드를 못 꺼내고 새로 인쇄해야 한다.

틀린 셰이더를 재사용하면 화면이 깨지니까, 정확성을 위해 비싼 길을 다시 타는 거야.

5. DDC에는 최종 카드가 들어간다

캐시 키가 맞으면 언리얼은 이미 만든 결과를 다시 쓰고 싶어 한다.

그 결과가 DDC 레코드로 저장되는 모습도 실제 코드에 있다.

여기서는 셰이더 객체 데이터와 코드 버퍼, 심볼 버퍼를 한 박스에 넣는다.

ShaderSerialization.cpp:63

UE::DerivedData::FCacheRecord FShaderCacheSaveContext::BuildCacheRecord(const UE::DerivedData::FCacheKey& Key) { Finalize(); UE::DerivedData::FCacheRecordBuilder RecordBuilder(Key); RecordBuilder.AddValue(ShaderObjectDataValue, ShaderObjectData); int32 CodeIndex = 0; // Code buffers are already compressed, don't waste cycles attempting (and failing) to recompress them const ECompressedBufferCompressor CodeComp = ECompressedBufferCompressor::NotSet; const ECompressedBufferCompressionLevel CodeCompLevel = ECompressedBufferCompressionLevel::None; // Use a meta field to indicate whether we are adding symbol values to this record; we do so to prevent per-value overhead of symbol buffers if they are empty // (each value in a cache record has a 64 byte overhead, which can be significant when we're pushing millions of individual shader cache records) bool bHasSymbols = false; for (FCompressedBuffer& SymbolsBuf : ShaderSymbols) { bHasSymbols |= (SymbolsBuf.GetRawSize() > 0); } for (FCompositeBuffer& CodeBuf : ShaderCode) { RecordBuilder.AddValue(ShaderCodeDataValue.MakeIndexed(CodeIndex), UE::DerivedData::FValue(FCompressedBuffer::Compress(CodeBuf, CodeComp, CodeCompLevel))); if (bHasSymbols) { RecordBuilder.AddValue(ShaderSymbolsDataValue.MakeIndexed(CodeIndex), UE::DerivedData::FValue(ShaderSymbols[CodeIndex])); } CodeIndex++; }
🔤 기호 사전 — DDC 레코드 저장
• UE::DerivedData::FCacheRecord = DDC에 넣을 한 박스 같은 레코드야.
• FCacheKey& Key = 이 박스를 찾을 때 쓸 키야.
• Finalize() = 저장 전에 내부 데이터를 마무리하는 호출이야.
• FCacheRecordBuilder RecordBuilder(Key) = 이 키로 캐시 레코드를 조립할 빌더를 만드는 거야.
• AddValue(...) = 레코드 안에 이름 붙은 값을 추가하는 함수야.
• ShaderObjectDataValue = 셰이더 맵/객체 쪽 데이터 칸 이름이야.
• ShaderCodeDataValue.MakeIndexed(CodeIndex) = 여러 코드 버퍼 중 몇 번째인지 붙여 저장하는 거야.
• FCompressedBuffer::Compress(...) = 버퍼를 압축된 형태의 값으로 감싸는 호출이야.
• bHasSymbols |= ... = 심볼 버퍼가 하나라도 있으면 true로 유지하는 표기야.
• CodeIndex++ = 다음 코드 버퍼 번호로 하나 올리는 거야.

주석에 힌트가 있어.

"millions of individual shader cache records"라고 적혀 있지.

수백 개 수준이 아니라 수백만 개 레코드까지 생각하고 저장 구조를 만든다는 뜻이야.

그래서 캐시가 없으면 느리고, 캐시가 있으면 살 만해진다.

콜/데이터 흐름 한눈에

.usf / .ush 원본 | | Shader.cpp:480 v FShaderCompilerEnvironment | | ShaderCore.cpp:1804 v FShaderPreprocessOutput | | ShaderCore.cpp:1950 v FShaderCompilerOutput | | ShaderCore.cpp:4363 v FShaderCompilerInputHash | | ShaderSerialization.cpp:63 v DDC cache record

이 흐름을 비유로 다시 말하면,

원본 레시피에 주문 옵션을 붙이고,

작업지시서로 정리하고,

매장별 프린터가 최종 카드를 뽑고,

카드 번호를 만들어 창고에 넣는 거야.

우리 서버·DirectX 랑 비교

DirectX 기초 감각으로는 "HLSL 넣고 DXIL 나오면 끝"처럼 보인다.

언리얼은 그 앞뒤가 더 커.

원본은 .usf/.ush와 include 묶음이고,

옵션은 FShaderCompilerEnvironment 전체고,

중간 결과는 FShaderPreprocessOutput이고,

최종 컴파일은 IShaderFormat 백엔드가 맡고,

결과는 해시와 DDC에 저장된다.

우리 서버랑도 닮았어.

패킷 핸들러를 매번 문자열 검색으로 찾으면 느리니까 서버 시작 때 디스패치 테이블을 만들잖아.

DB 메타도 자주 쓰는 건 캐시하고, 같은 요청은 가능하면 재사용하지.

셰이더 컴파일도 마찬가지야.

다만 비용 단위가 훨씬 커서, 캐시 미스가 나면 전처리와 백엔드 컴파일이라는 비싼 길로 내려간다.

이 챕터에서 딱 이것만

  • .usf는 바로 GPU 코드가 되지 않는다. 먼저 컴파일 환경이 붙고 전처리된다.
  • C++ 레벨에서 보이는 핵심 중간 산출물은 FShaderPreprocessOutput이다.
  • 최종 컴파일은 IShaderFormat::CompilePreprocessedShader 백엔드가 맡는다.
  • 캐시 키는 원본 파일명이 아니라 버전, 포맷, 엔트리, 환경, 전처리 소스까지 포함한 입력 지문이다.
  • DDC는 최종 셰이더 코드와 메타데이터를 저장해 다음 비싼 컴파일을 피하게 해준다.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. 셰이더 컴파일이 왜 파이프라인이라고 부를 만큼 커지나요? HLSL 넣으면 바이트코드 나오는 거 아닌가요?

답 보기
DirectX 기초 감각으론 "HLSL 넣고 DXIL 나오면 끝"인데, 언리얼은 같은 .usf라도 조합이 갈라져. 플랫폼, 엔트리 함수, 머티리얼 옵션, 레이 트레이싱, bindless, 디버그 플래그가 다르면 결과가 달라지거든. 김치볶음밥 하나도 매운맛·치즈추가·포장용이 갈라지는 것처럼. 그래서 원본 옆에 "이번 주문 옵션(컴파일 환경)"을 붙이고 → 전처리하고 → 플랫폼 백엔드가 최종 코드를 만들고 → 해시랑 캐시에 넣는 파이프라인이 되는 거야.

↳ 매번 생으로 컴파일하면 뭐가 망가지나요?

답 보기
에디터 켜자마자 "Compiling Shaders 6000" 뜨고, 작은 머티리얼 수정 하나에도 몇 분씩 멈춰. 조합이 워낙 많아서 그래. 서버로 치면 클라 하나 들어올 때마다 CM_* 디스패치 테이블이랑 메타데이터를 전부 새로 만드는 꼴이야. 그래서 캐시가 없으면 못 버티고, 있으면 살 만해지는 거지.

Q2. 왜 .usf를 바로 백엔드에 넣지 않고 전처리를 먼저 하나요?

답 보기
레시피 안에 include랑 조건문(#if)이 남아 있으면 매장별 기계마다 읽는 방식이 꼬일 수 있거든. 그래서 include를 다 펼치고, define을 적용하고, 조건부 코드를 정리해서 백엔드가 먹기 좋은 작업지시서로 만드는 게 전처리야. C++ 레벨에서 그 중간 산출물이 FShaderPreprocessOutput이고, 원본 .usf도 아니고 최종 GPU 바이트코드도 아닌 그 사이 단계야.

↳ 그럼 최종 컴파일은 렌더코어가 직접 하나요?

답 보기
아니, 렌더코어는 작업지시서까지만 만들고 진짜 인쇄는 플랫폼 백엔드에 맡겨. IShaderFormat이라는 백엔드 인터페이스를 통해 D3D·Vulkan·Metal 쪽으로 넘기는 거지. 매장 기계가 다르면 종이 크기랑 잉크가 다르니까 한 기계가 다 뽑는다고 믿으면 깨져. 서버로 치면 공통 패킷 프레임워크가 CM_LOGIN을 로그인 모듈로 넘기고 실제 처리는 그 모듈이 하는 구조랑 같아.

Q3. 캐시 키가 그냥 파일명이면 안 되나요?

답 보기
절대 안 돼. 파일명은 같은데 치즈 추가 define 하나만 바뀌어도 완전히 다른 카드거든. 예전 카드를 그냥 쓰면 화면이 틀린 재료로 그려져. 그래서 언리얼은 캐시 버전·목표 포맷·엔트리 함수·bindless 설정·컴파일 환경·전처리된 소스 본문까지 입력 전체를 해시로 섞어서 "입력 지문"을 만들어. 이 지문이 같아야만 "같은 레시피 카드"라고 믿는 거야.

↳ 그래서 "작은 define 하나 바꿨는데 왜 또 컴파일하지?"가 되는 건가요?

답 보기
맞아, 바로 그거야. 해시 재료가 하나라도 바뀌면 도장 번호가 달라지고, 도장 번호가 달라지면 창고에서 예전 카드를 못 꺼내니까 새로 인쇄해야 해. 짜증나 보여도 정확성 때문에 일부러 그러는 것이야 — 틀린 셰이더를 재사용하면 화면이 깨지니까, 안전하게 비싼 길을 다시 타는 거지.

Q4. DDC는 왜 있고 큰 그림에서 뭘 하나요?

답 보기
DDC는 완성된 셰이더 카드를 보관하는 창고야. 입력 지문이 맞으면 이미 만든 결과를 다시 꺼내 쓰고, 없으면 그때만 비싼 전처리·백엔드 컴파일 길로 내려가. 코드 주석에 "수백만 개 레코드(millions of shader cache records)"라고 적혀 있을 만큼 규모를 크게 잡고 설계했어. 서버로 치면 자주 쓰는 DB 메타를 캐시하고 같은 요청은 재사용하는 거랑 같은데, 비용 단위가 훨씬 커서 캐시 미스 한 번의 대가가 크다는 게 차이야.

↳ 그럼 이 장 내용이 앞뒤 챕터랑 어떻게 이어져요?

답 보기
앞 장(shader-basics)에선 "셰이더는 GPU에서 도는 작은 프로그램"이고 C++ 주문표가 .usf 함수를 가리킨다까지 봤어. 이 장은 그 작은 프로그램이 애초에 어떻게 만들어지고 캐시에 박히는가를 채운 거고. 다음 장(shader-parameters)에선 C++ 값이 그 컴파일된 셰이더의 변수 칸에 어떻게 꽂히는지로 넘어가. 셋을 이으면 "등록 → 컴파일/캐시 → 값 바인딩"이라는 셰이더 한살이가 완성돼.
