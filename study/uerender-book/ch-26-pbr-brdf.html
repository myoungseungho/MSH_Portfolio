BRDF.ush — PBR 수식이 코드로

언리얼 렌더링 · 26 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "PBR에서 말하는 D/G/F가 실제 UE 셰이더 코드에서 어디에 있고, 어떻게 최종 스페큘러 한 덩어리로 합쳐지는지"가 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX를 조금 만져봤으면 dot(N, L)로 밝기 구하는 건 익숙할 거야. 노멀과 빛 방향이 비슷하면 밝고, 비스듬하면 어둡다. 서버로 치면 패킷 헤더 읽고 wID로 핸들러 타는 수준이야. 입구 규칙은 단순하지.

그런데 진짜 재질은 거기서 끝나지 않아. 플라스틱, 금속, 젖은 바닥, 거친 돌이 다 같은 dot(N, L)이면 화면이 바로 가짜처럼 보여. 러프니스 0.05짜리 금속과 러프니스 0.8짜리 벽돌이 같은 방식으로 번쩍이면, 아티스트가 재질을 아무리 잘 찍어도 빛이 망쳐. 라이트가 100개가 아니라 1개만 있어도 "이 표면은 왜 비닐 같지?"가 터진다.

그래서 언리얼도 같은 문제를 만났고, 답이 BRDF야. BRDF는 "빛이 이 방향에서 들어와서 저 방향으로 나갈 때, 표면이 얼마나 돌려보내나"를 정하는 조리법이야. 언리얼은 그 조리법을 BRDF.ush 안에 잘게 쪼개서 둔다. D_GGX, Vis_SmithJointApprox, F_Schlick 같은 이름이 그 조리법 카드야.

왜 지금 배우냐면, 앞에서 우리는 GBuffer에 재질 정보를 눕히고 → basepass-gbuffer, 라이트가 그걸 읽어 빛을 얹는 흐름을 봤어 → deferred-lighting. 이제 "빛을 얹는다"의 속살을 봐야 해. 다음 장은 셰이더 순열 → shader-permutation이라서, 수식 자체를 모르면 #if로 갈라지는 변형이 더 안 읽힌다. 오늘은 수학을 외우는 날이 아니라, 수식 이름이 실제 코드에서 어떤 재료를 맡는지 잡는 날이야.

0. 비유부터 — 탕후루 코팅 레시피

이번 챕터는 탕후루 코팅으로 보자. 과일 겉에 설탕 코팅을 입히는데, 반짝임이 그냥 "설탕 있음" 하나로 끝나지 않아.

첫째, 설탕 알갱이가 얼마나 고르게 서 있나. 고운 코팅이면 빛이 한 방향으로 예쁘게 모이고, 울퉁불퉁하면 여기저기로 퍼진다. 이게 D, 특히 D_GGX야. 표면 위 작은 거울 조각들이 어느 방향으로 많이 서 있는지 세는 카드야.

둘째, 알갱이끼리 서로 가리나. 아무리 반짝이는 알갱이가 있어도 옆 알갱이가 빛이나 카메라를 막으면 안 보여. 이게 G이고, UE 코드에선 Vis라는 이름으로 많이 나온다. Vis = G / (4*NoL*NoV)라서, 실제 코드에선 Vis_Smith...가 이 가림 값을 미리 나눠 둔 형태로 준다.

셋째, 보는 각도에 따라 더 반짝이나. 탕후루를 정면에서 보면 덜 번쩍이다가 가장자리로 돌리면 확 반짝이는 느낌이 있지. 이게 F, Fresnel이야. UE에선 F_Schlick이 빠른 근사 버전으로 많이 보인다.

마지막으로 이 세 카드를 곱한다. 알갱이가 얼마나 그 방향을 향했는지(D) × 가리지 않고 보이는지(Vis) × 각도 때문에 얼마나 반사되는지(F). 이게 스페큘러 BRDF의 중심이야. 오늘은 이 설탕 코팅 레시피를 실제 셰이더 코드로 읽는다.

1. 먼저 재료 이름부터 — NoV, NoL, VoH를 상자에 담는다

BRDF 코드는 N, V, L, H라는 방향 벡터를 계속 쓴다. 처음 보면 이름이 너무 짧아서 더 무서운데, 사실 다 주방 재료 라벨이야.

  • N = 표면 노멀, 코팅면이 위를 보는 방향.
  • V = 카메라로 가는 방향, 네 눈 쪽.
  • L = 빛이 오는 방향.
  • H = V와 L의 중간 방향, 작은 거울 조각이 딱 맞게 서 있어야 하는 방향.

언리얼은 이걸 매번 새로 계산하지 않게 BxDFContext에 담아둔다. 식당 주방에서 "소금, 설탕, 물엿"을 작은 종지에 미리 담아두는 거랑 같아.

BRDF.ush:24

void Init( inout BxDFContext Context, half3 N, half3 V, half3 L ) { Context.NoL = dot(N, L); Context.NoV = dot(N, V); Context.VoL = dot(V, L); float InvLenH = rsqrt( 2 + 2 * Context.VoL ); Context.NoH = saturate( ( Context.NoL + Context.NoV ) * InvLenH ); Context.VoH = saturate( InvLenH + InvLenH * Context.VoL ); //NoL = saturate( NoL ); //NoV = saturate( abs( NoV ) + 1e-5 ); Context.XoV = 0.0f; Context.XoL = 0.0f; Context.XoH = 0.0f; Context.YoV = 0.0f; Context.YoL = 0.0f; Context.YoH = 0.0f; }
🔤 기호 사전 — 방향 재료 상자
• half / half3 = GPU에서 쓰는 작은 실수 타입. half3는 실수 3개짜리 벡터야.
• NoV = N dot V의 줄임말. 표면 노멀과 카메라 방향이 얼마나 같은지.
• VoL = V dot L. 카메라 방향과 빛 방향의 관계야.
• inout = 함수 안에서 받은 상자를 고쳐서 밖에도 반영한다는 뜻.
• dot(N, L) = 두 방향이 얼마나 같은 방향인지 재는 내적.
• rsqrt(...) = 제곱근의 역수. 1 / sqrt(x)를 빠르게 구하는 GPU식 도구야.
• saturate(...) = 값을 0에서 1 사이로 눌러 담는다.
• 0.0f = 실수 0. f는 float 계열 숫자라는 표시야.
🔁 이제 다시 보자. Context.NoL = dot(N, L)은 빛이 표면을 얼마나 정면으로 때리는지 담고 → Context.NoV = dot(N, V)는 카메라가 표면을 얼마나 정면으로 보는지 담고 → InvLenH로 중간 방향 H를 정규화해서 → NoH, VoH까지 채운다. 탕후루 코팅을 만들기 전에 "빛 각도, 눈 각도, 반짝일 중간 각도"를 종지에 담는 장면이야.

여기서 NoL, NoV, NoH, VoH 네 개가 특히 자주 나온다. 수식 이름은 짧지만 뜻은 단순해. NoL이 낮으면 빛이 옆에서 스치고, NoV가 낮으면 카메라가 표면을 얕게 본다. NoH는 작은 거울 조각이 빛과 눈 사이의 딱 맞는 방향을 얼마나 향했는지다. VoH는 Fresnel에서 자주 쓰는 "보는 방향과 반쪽 벡터의 각도"야.

비유로 다시 말하면: 탕후루를 조명 아래 둔다. 빛이 어디서 오는지, 네 눈이 어디 있는지, 설탕 알갱이가 어느 방향으로 서 있어야 반짝이는지 먼저 적어둔다. 그다음 레시피 카드들이 이 값을 꺼내 쓴다.

2. PBR 레시피의 공식 — D, G, F가 나눠 맡는다

BRDF.ush는 친절하게 자기 안에 공식 메모를 남겨놨다. 이 메모가 오늘의 지도야. 특히 마지막 줄이 중요해. 스페큘러 BRDF는 D*G*F / (4*NoL*NoV)인데, UE는 Vis = G / (4*NoL*NoV)로 묶어서 D*Vis*F로 읽는다.

BRDF.ush:169

// D = Microfacet NDF // G = Shadowing and masking // F = Fresnel // Vis = G / (4*NoL*NoV) // f = Microfacet specular BRDF = D*G*F / (4*NoL*NoV) = D*Vis*F half3 Diffuse_Lambert( half3 DiffuseColor ) { return DiffuseColor * (1 / PI); }
🔤 기호 사전 — BRDF 공식 메모와 diffuse
• // = 주석. GPU가 실행하지 않고 사람이 읽는 메모야.
• D = microfacet normal distribution function. 작은 거울 조각 방향 분포야.
• G = shadowing/masking. 빛이나 눈길이 작은 돌기에 가려지는 정도야.
• F = Fresnel. 각도에 따라 반사율이 바뀌는 규칙이야.
• Vis = G / (4*NoL*NoV)를 미리 묶은 값. UE 코드에서 가림 항이 이 이름으로 자주 나와.
• half3 Diffuse_Lambert = RGB 3개짜리 diffuse 값을 돌려주는 함수.
• PI = 원주율. Lambert diffuse는 에너지를 반구로 나누려고 1 / PI를 곱한다.
🔁 이제 다시 보자. 주석은 D, G, F가 각각 "알갱이 방향", "서로 가림", "각도 반사"라고 말하고 → Vis는 G를 편하게 쓰려고 나눗셈까지 접어둔 이름이고 → Diffuse_Lambert는 색을 PI로 나눠 기본 난반사를 만든다. 탕후루로 치면 설탕 반짝임 말고 과일 자체 색이 퍼지는 기본맛이 여기야.

이 챕터의 주인공은 스페큘러 쪽이야. Diffuse는 "과일 속살", Specular는 "설탕 코팅 반짝임"으로 잡고 가면 된다.

3. D — GGX는 작은 거울 조각이 어디를 보는지 센다

D_GGX는 "작은 거울 조각들이 H 방향으로 얼마나 많이 서 있나"를 계산한다. PBR 글에서 GGX, Trowbridge-Reitz라고 부르는 그 분포야. 러프니스가 낮으면 반짝임이 좁게 모이고, 높으면 넓게 퍼진다.

BRDF.ush:329

// GGX / Trowbridge-Reitz // [Walter et al. 2007, "Microfacet models for refraction through rough surfaces"] float D_GGX( float a2, float NoH ) { float d = ( NoH * a2 - NoH ) * NoH + 1; // 2 mad return a2 / ( PI*d*d ); // 4 mul, 1 rcp }
🔤 기호 사전 — GGX 분포
• float D_GGX(...) = 실수 하나를 돌려주는 GGX 분포 함수.
• a2 = alpha 제곱. 보통 roughness를 제곱하고 또 제곱한 값이 들어온다.
• NoH = 노멀과 반쪽 벡터의 내적. 작은 거울이 딱 맞는 방향을 얼마나 향했는지.
• mad = multiply-add. 곱하고 더하는 GPU 친화 연산을 말해.
• rcp = reciprocal, 역수. 여기 주석은 나눗셈 비용 힌트야.
🔁 이제 다시 보자. D_GGX는 NoH와 a2로 d를 만들고 → a2 / (PI*d*d)를 돌려준다. 탕후루 코팅으로 치면 설탕 알갱이가 반짝일 방향으로 얼마나 많이 서 있는지 세는 카드야.

왜 하필 GGX를 많이 쓰냐면 꼬리가 예쁘게 길기 때문이야. Blinn-Phong처럼 너무 깔끔하게 죽는 하이라이트보다, 실제 거친 표면의 긴 반짝임 꼬리를 더 그럴듯하게 낸다. 금속 모서리나 거친 바닥에서 "번쩍임이 번져 나가는 느낌"이 바로 이 꼬리에서 온다.

DirectX 튜토리얼의 specular는 보통 pow(max(dot(R, V), 0), Shininess)로 시작해. 그건 "하이라이트을 얼마나 좁힐까" 하나만 만지는 느낌이지. GGX는 같은 일을 하되, 에너지 보존과 실제 표면 통계에 맞춘 카드라고 보면 된다.

4. Vis — 보이긴 보이나, 서로 가리나

작은 거울 조각이 좋은 방향을 보고 있어도, 그 조각이 실제로 보인다는 보장은 없어. 울퉁불퉁한 설탕 코팅 안쪽의 알갱이는 앞 알갱이에 가릴 수 있다. 빛도 못 들어가고, 카메라도 못 본다. 이 가림을 다루는 게 G고, UE 코드에선 Vis로 접혀 나온다.

BRDF.ush:382

// Smith term for GGX // [Smith 1967, "Geometrical shadowing of a random rough surface"] float Vis_Smith( float a2, float NoV, float NoL ) { float Vis_SmithV = NoV + sqrt( NoV * (NoV - NoV * a2) + a2 ); float Vis_SmithL = NoL + sqrt( NoL * (NoL - NoL * a2) + a2 ); return rcp( Vis_SmithV * Vis_SmithL ); } // Appoximation of joint Smith term for GGX // [Heitz 2014, "Understanding the Masking-Shadowing Function in Microfacet-Based BRDFs"] float Vis_SmithJointApprox( float a2, float NoV, float NoL ) { float a = sqrt(a2); float Vis_SmithV = NoL * ( NoV * ( 1 - a ) + a ); float Vis_SmithL = NoV * ( NoL * ( 1 - a ) + a ); return 0.5 * rcp( Vis_SmithV + Vis_SmithL ); } // [Heitz 2014, "Understanding the Masking-Shadowing Function in Microfacet-Based BRDFs"] float Vis_SmithJoint(float a2, float NoV, float NoL) { float Vis_SmithV = NoL * sqrt(NoV * (NoV - NoV * a2) + a2); float Vis_SmithL = NoV * sqrt(NoL * (NoL - NoL * a2) + a2); return 0.5 * rcp(Vis_SmithV + Vis_SmithL); }
🔤 기호 사전 — Smith visibility
• Vis_Smith = Smith 방식으로 가림 값을 계산하는 함수.
• NoV = 표면을 카메라가 보는 각도. 낮으면 거의 옆에서 보는 상태야.
• NoL = 빛이 표면을 때리는 각도. 낮으면 빛이 스치듯 들어와.
• sqrt(...) = 제곱근. 거칠기와 각도에서 가림 모양을 만든다.
• rcp(...) = 역수. 1 / x를 GPU식으로 표현한 거야.
• Vis_SmithJointApprox = 카메라 쪽 가림과 빛 쪽 가림을 같이 근사한 빠른 버전.
• 0.5 * rcp(...) = 나눗셈을 역수로 바꿔 곱하는 형태. 셰이더에서 흔해.
• float Vis_SmithJoint(float a2, float NoV, float NoL) = 공백 스타일은 조금 다르지만 같은 HLSL 함수 선언이야.

Vis_SmithJointApprox가 실시간 렌더링에서 특히 자주 보인다. 정확한 물리식만 밀면 비용이 커질 수 있으니, 화면에서 충분히 비슷한 근사를 쓰는 거야. 서버에서 매 패킷마다 무거운 DB 조회를 하지 않고 캐시된 값이나 근사 인덱스를 쓰는 것과 감각이 비슷해. 정확도와 비용 사이에서 프레임 시간을 지키는 선택이지.

탕후루 비유로는 이렇다. 설탕 알갱이가 반짝일 방향을 보고 있어도, 안쪽에 묻힌 알갱이는 네 눈에 안 보인다. 또 빛이 옆에서 오면 알갱이 뒤쪽에 그림자가 생긴다. Vis는 "그 알갱이가 실제로 조명과 카메라 양쪽에 열린 상태냐"를 깎는 계수야.

5. F — 가장자리에서 더 번쩍이는 Fresnel

Fresnel은 렌더링 초보가 제일 자주 "왜 이러지?" 하는 현상이다. 정면에서는 덜 반사하던 표면이, 비스듬히 보면 갑자기 더 반사한다. 물가나 유리 가장자리를 보면 바로 느낄 수 있어.

UE는 기본적으로 Schlick 근사를 쓴다. Pow5(1 - VoH) 하나로 각도 효과를 싸게 만든다. 그리고 더 직접적인 Fresnel 함수도 같이 둔다.

BRDF.ush:422

// [Schlick 1994, "An Inexpensive BRDF Model for Physically-Based Rendering"] float3 F_Schlick( float3 SpecularColor, float VoH ) { float Fc = Pow5( 1 - VoH ); // 1 sub, 3 mul //return Fc + (1 - Fc) * SpecularColor; // 1 add, 3 mad // Anything less than 2% is physically impossible and is instead considered to be shadowing return saturate( 50.0 * SpecularColor.g ) * Fc + (1 - Fc) * SpecularColor; } float3 F_Schlick(float3 F0, float3 F90, float VoH) { float Fc = Pow5(1 - VoH); return F90 * Fc + (1 - Fc) * F0; }
🔤 기호 사전 — Schlick Fresnel
• float3 = RGB처럼 실수 3개짜리 값.
• SpecularColor = 정면에 가까울 때의 기본 반사 색이라고 보면 된다.
• VoH = 보는 방향과 반쪽 벡터의 내적. 각도 반사 계산의 손잡이야.
• Fc = Fresnel curve의 중간 계수. 가장자리로 갈수록 커진다.
• SpecularColor.g = RGB 중 초록 채널. 여기선 밝기 대표값처럼 써서 2% 아래를 다룬다.
• saturate( 50.0 * SpecularColor.g ) = 너무 낮은 스페큘러를 그림자처럼 취급하려고 0~1로 누르는 값.
• F0 / F90 = 정면 반사율과 90도 가장자리 반사율.
🔁 이제 다시 보자. Fc = Pow5(1 - VoH)가 각도 때문에 커지는 가장자리 계수를 만들고 → 첫 번째 F_Schlick은 SpecularColor와 섞어 기본 Fresnel을 만들고 → 두 번째 오버로드는 F0와 F90을 직접 받아 정면과 가장자리 반사를 섞는다. 탕후루를 정면에서 볼 때와 옆으로 돌려 볼 때 설탕 코팅이 다르게 번쩍이는 바로 그 규칙이야.

같은 파일에는 좀 더 직접적인 Fresnel 계산도 있다. 하지만 이 챕터에선 F_Schlick만 잡아도 충분해. 핵심 감각은 "비스듬할수록 반사가 세진다" 하나야. 서버에서 암호화 수식의 모든 증명을 몰라도, 어느 지점에서 키가 섞이는지 알아야 콜체인을 읽을 수 있잖아. 여기도 똑같다.

6. 진짜 조명 모델에서 합치기 — D * Vis * F

이제 설탕 코팅 카드 세 장을 한 접시에 올려보자. BRDF.ush는 카드 창고고, ShadingModels.ush는 그 카드를 꺼내 실제 기본 조명 모델에 끼우는 쪽이야. 여기서 SpecularGGX가 D, Vis, F를 나란히 계산하고 곱한다.

ShadingModels.ush:171

float3 SpecularGGX( float Roughness, float3 SpecularColor, BxDFContext Context, FAreaLight AreaLight ) { float a2 = Pow4( Roughness ); float Energy = EnergyNormalization( a2, Context.VoH, AreaLight ); // Generalized microfacet specular float D = D_GGX( a2, Context.NoH ) * Energy; float Vis = Vis_SmithJointApprox( a2, Context.NoV, AreaLight.NoL ); float3 F = F_Schlick( SpecularColor, Context.VoH ); return (D * Vis) * F; }
🔤 기호 사전 — 실제 스페큘러 조립
• SpecularGGX = GGX 기반 스페큘러 조명 값을 만드는 함수.
• Pow4( Roughness ) = 러프니스를 네 번 곱한 값. 여기선 a2로 들어가 GGX 폭을 정한다.
• EnergyNormalization(...) = 면광원 같은 상황에서 에너지 균형을 맞추는 보정값.
• FAreaLight AreaLight = 면적을 가진 라이트 정보 상자.
• D_GGX(...) = 작은 거울 조각의 방향 분포 카드.
• Vis_SmithJointApprox(...) = 빛과 눈 양쪽 가림을 접은 visibility 카드.
• F_Schlick(...) = 각도별 반사율 카드.
• return (D * Vis) * F = 세 카드를 곱해 최종 스페큘러 RGB를 돌려준다.
🔁 이제 다시 보자. a2 = Pow4(Roughness)로 거칠기 폭을 만들고 → D_GGX로 설탕 알갱이 방향 분포를 구하고 → Vis_SmithJointApprox로 가려진 만큼 깎고 → F_Schlick으로 가장자리 반사를 키운 뒤 → (D * Vis) * F로 최종 반짝임을 만든다. 아까 주석의 f = D*Vis*F가 여기서 진짜 코드 한 줄이 된 거야.

이 토막 하나가 오늘의 핵심이다. BRDF.ush에 흩어진 함수들은 따로 노는 수학 장식이 아니야. 실제 조명 모델이 D, Vis, F를 꺼내서 곱한다. 그러니까 렌더Doc이나 셰이더 디버깅에서 스페큘러가 이상하면, "D가 이상한가? Vis가 너무 깎나? F가 너무 세나?"로 나눠서 생각할 수 있다.

탕후루로 다시 말하면: 설탕 알갱이가 반짝일 방향으로 얼마나 있나. 그 알갱이가 빛과 눈에 가리지 않나. 보는 각도 때문에 얼마나 더 번쩍이나. 이 셋을 곱하면 "이 픽셀의 코팅 반짝임"이 된다.

7. 러프니스 하나가 셋을 흔든다

PBR에서 Roughness는 단순히 "흐릿함" 슬라이더가 아니야. SpecularGGX만 봐도 Pow4(Roughness)가 D_GGX와 Vis_SmithJointApprox에 같이 들어간다. 거칠기가 커지면 작은 거울 조각 분포가 넓어지고, 가림 계산도 바뀐다.

아티스트 입장에선 슬라이더 하나지만, 셰이더 입장에선 여러 레시피 카드의 공통 재료야. 하이라이트가 너무 작고 날카로우면 D와 roughness를 의심하고, 가장자리만 지나치게 번쩍이면 F를 본다. 비스듬한 면이 너무 어두우면 Vis가 많이 깎고 있는지 본다. 서버 장애에서 "렉나요"를 네트워크, DB, 락, 게임 루프로 쪼개 보는 것과 같은 태도야.

8. 콜/데이터 흐름 한눈에

GBuffer / Material: Roughness, SpecularColor, WorldNormal │ ▼ BxDFContext Init BRDF.ush:24 NoL, NoV, NoH, VoH 계산 │ ▼ SpecularGGX ShadingModels.ush:171 │ ├─ D_GGX BRDF.ush:331 방향 분포 ├─ Vis_SmithJointApprox BRDF.ush:393 빛/눈 가림 └─ F_Schlick BRDF.ush:423 각도 반사 │ ▼ return (D * Vis) * F 이 픽셀의 스페큘러 코팅값

이 흐름을 한 문장으로 읽으면 이래. 재질이 GBuffer에 러프니스와 색을 남기고, 조명 단계가 BxDFContext로 각도 종지를 채운 뒤, D_GGX, Vis_SmithJointApprox, F_Schlick을 차례로 꺼내 곱한다. 그 결과가 라이트 색과 섀도, 감쇠와 섞여 화면 위 스페큘러가 된다.

중요한 건 BRDF.ush가 직접 "픽셀 색 최종값"을 다 만들지는 않는다는 점이야. 여긴 수식 카드 보관함이다. 실제 조명 모델은 ShadingModels.ush, 디퍼드/포워드/루멘/패스트레이싱 쪽에서 이 카드를 가져다 쓴다.

9. 우리 서버·DirectX 랑 비교

우리 조선 서버로 치면 BRDF.ush는 SP_* 핸들러 본문이 아니라 공용 계산 유틸에 가깝다. 예를 들어 데미지 공식이 CalcHitRate, CalcCritical, CalcDefenseReduce로 쪼개져 있고, 실제 SP_ATTACK에서 그걸 조립한다고 해보자. BRDF.ush의 D_GGX, Vis_SmithJointApprox, F_Schlick이 바로 그 공용 계산 함수들이야. ShadingModels.ush의 SpecularGGX는 "공격 한 번 처리하면서 명중, 방어, 치명을 합치는 곳"에 가깝다.

락 감각으로도 볼 수 있다. 서버에서 공유 상태를 그냥 막 건드리면 레이스가 나니까, 입력을 작은 값으로 정리하고 정해진 함수만 통과시키잖아. 렌더링에서도 재질을 아무 임의 조명 공식에 던지지 않는다. Roughness, SpecularColor, NoV, NoL 같은 정해진 값으로 BRDF 함수를 통과시켜야 재질이 일관된다.

DirectX 기초와 비교하면 더 쉽다. 기본 튜토리얼은 대충 이렇게 간다:

  • diffuse = max(dot(N, L), 0)
  • specular = pow(max(dot(R, V), 0), Shininess)
  • color = diffuse + specular

UE의 PBR은 그 자리에 더 물리적인 카드를 넣은 거야. pow 하나로 하이라이트를 조이는 대신 D_GGX가 표면 통계를 맡는다. 그냥 dot만 보고 밝히는 대신 Vis_Smith...가 작은 돌기 가림을 깎는다. 각도 반사는 F_Schlick이 맡는다.

그래서 PBR 셰이더를 읽을 때 "수학이 많다"로 보면 막힌다. "옛날 DirectX specular를 세 명의 담당자로 쪼갰다"로 보면 훨씬 낫다. D는 하이라이트 모양 담당, Vis는 가림 담당, F는 가장자리 반사 담당. 이 정도만 잡아도 코드가 갑자기 사람이 쓴 문장처럼 보인다.

10. 이 챕터에서 딱 이것만

  • BxDFContext는 NoL, NoV, NoH, VoH 같은 각도 재료를 미리 담는 상자야.
  • D_GGX는 작은 거울 조각의 방향 분포, 즉 하이라이트 모양을 만든다.
  • Vis_SmithJointApprox는 빛과 눈 방향에서 생기는 미세 가림을 깎는다.
  • F_Schlick은 비스듬히 볼수록 반사가 세지는 Fresnel을 싸게 근사한다.
  • 실제 조립은 SpecularGGX의 return (D * Vis) * F; 한 줄로 드러난다.

이 다섯 개를 말로 설명할 수 있으면 통과야. 공식 전체를 외울 필요는 없어. 대신 "이 함수가 레시피의 어느 카드인가"를 잃지 않으면 된다.
