BasePass → GBuffer — 재질 정보를 화면에 눕히다

언리얼 렌더링 · 20 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "BasePass가 왜 여러 렌더타깃을 붙이고, 그 위에 재질 정보를 나눠 적는지"가 잡힌다.

왜 이걸 배워? — 문제의식부터

네가 DirectX로 삼각형을 그려봤으면 RenderTarget 하나에 색을 쓰는 건 익숙할 거야.

픽셀 셰이더가 float4 하나를 내보내고, 백버퍼나 텍스처 하나에 색이 찍히는 흐름.

그런데 큰 게임 화면은 이걸로 부족해.

나중에 조명을 계산하려면 픽셀마다 색만 있으면 안 돼.

그 픽셀이 어느 방향을 보고 있는지, 얼마나 거친 표면인지, 금속인지, 어떤 셰이딩 모델인지도 필요해.

이걸 조명 계산 때마다 다시 물체를 전부 그려서 얻는다면 어떻게 될까?

1024개의 라이트가 있는 도시 밤 장면에서, 라이트 하나마다 모든 메시를 다시 그리는 꼴이 돼.

서버로 치면 CM_ATTACK 하나 처리할 때마다 DB에서 캐릭터 전체 상태를 다시 조인해서 긁어오는 느낌이야.

화면 한 픽셀에 필요한 재질 정보를 미리 한 번 저장해두지 않으면, 뒤쪽 라이팅 패스가 계속 같은 질문을 반복하게 돼.

언리얼도 같은 문제를 만났고, 답이 BasePass가 GBuffer에 재질 정보를 눕혀놓는 것이야.

BasePass는 "최종 조명 색"을 완성하는 패스가 아니야.

디퍼드 렌더링에서는 먼저 재질의 신분증을 화면 크기의 여러 텍스처에 적어둬.

색, 노멀, 러프니스, 셰이딩 모델 같은 정보를 GBufferA, GBufferB, GBufferC... 여러 칸에 나눠 담는 거지.

왜 지금 배우냐면, 앞 장 prepass-depth에서 깊이부터 깔았어.

이제 "보이는 표면"이 어느 픽셀에 있는지 대충 알았으니, 그 표면의 재질 정보를 깔 차례야.

그리고 다음 장 basepass-shader에서는 픽셀 셰이더 안으로 들어가서 실제 재질 값이 어떻게 포장되는지 볼 거야.

이번 장은 그 직전.

C++ 렌더러가 GBuffer 식판을 준비하고, BasePass가 그 식판에 메시를 그리게 연결하는 장면을 잡는다.

🌱 이 개념은 왜 생겼나 — GBuffer
• 원래 구조: 픽셀 셰이더가 바로 최종 색 하나를 만들어서 화면 한 장에 찍으면 제일 단순해.
• 그런데 문제: 도시 밤 장면처럼 라이트가 1024개면, 라이트마다 "이 픽셀 노멀이 뭐야? 러프니스는?"을 다시 물어봐야 해. 같은 밥을 매번 새로 푸는 꼴이야.
• 그래서 필요한 것: 보이는 픽셀의 재질 신분증을 먼저 식판 칸에 눕혀두자. Geometry 정보를 담는 Buffer라서 GBuffer야.

0. 비유부터 — 급식 식판에 반찬을 칸별로 눕히기

오늘 비유는 급식 식판이야.

한 접시에 모든 음식을 섞어 담으면 먹을 때 편할까?

밥, 국, 김치, 고기, 소스를 다 섞어버리면 나중에 "고기만 조금 더", "국물만 따로" 같은 처리가 불가능해.

그래서 식판에는 칸이 있어.

밥 칸, 국 칸, 반찬 칸, 소스 칸.

GBuffer도 똑같아.

화면의 픽셀 하나가 식판 하나라고 생각해.

BasePass는 그 픽셀 식판에 이렇게 나눠 담아:

  • SceneColor 칸: 기본 색이나 특수 경로의 색
  • GBufferA 칸: 노멀 같은 표면 방향 정보
  • GBufferB 칸: 금속성, 스페큘러, 러프니스 같은 재질 성질
  • GBufferC 칸: 베이스 컬러, 셰이딩 모델 같은 식별 정보
  • GBufferD/E 칸: 더 필요한 보조 정보
  • Velocity 칸: 움직임 벡터가 필요할 때

정확히 어떤 정보가 어느 칸에 들어가느냐는 플랫폼과 레이아웃에 따라 바뀔 수 있어.

그래서 C++은 "식판 칸을 몇 개 준비할지"를 먼저 정하고, 셰이더에는 "이번 식판 레이아웃은 이거야"라고 알려줘.

픽셀 셰이더는 그 규칙대로 GBuffer라는 도시락 내용을 MRT 여러 칸에 나눠 쓴다.

이번 장은 끝까지 이 그림으로 간다.

BasePass = 급식 배식 시간.

GBuffer = 칸 나뉜 식판.

Deferred Lighting = 나중에 식판을 보고 소스를 뿌리는 시간.

🌱 이 개념은 왜 생겼나 — GBUFFER_LAYOUT
• 원래 구조: 식판 칸 번호를 C++과 셰이더가 그냥 약속해. "1번은 노멀, 2번은 재질" 하고 머릿속에 고정하는 거야.
• 그런데 문제: 어떤 플랫폼은 Velocity 칸이 붙고, 어떤 경로는 Substrate가 칸을 더 써. 한쪽만 번호를 다르게 알면 김치를 국칸에 붓는 사고가 나.
• 그래서 필요한 것: 이번 프레임 식판 배치표를 컴파일 주문서에 박아야 해. 그 배치표 이름이 GBUFFER_LAYOUT이야.

1. 먼저 셰이더에게 식판 규격을 알려준다

BasePass는 아무 렌더타깃에나 마구 쓰지 않아.

셰이더 컴파일 단계에서 "이번 GBuffer 레이아웃은 무엇인가"를 define으로 박아.

여기서 GBUFFER_LAYOUT이 나온다.

식판을 만들기 전에 "5칸짜리냐, 속도 칸이 강제로 붙느냐"를 주문서에 적는 장면이야.

🔤 기호 사전 — 셰이더 주문서
• FShaderCompilerEnvironment& OutEnvironment = 셰이더 컴파일러한테 넘길 주문서 상자야. &는 원본 상자를 직접 건드린다는 뜻으로 보면 돼.
• SetDefine = 셰이더 코드 안에서 쓸 #define 값을 미리 박는 함수야.
• TEXT("GBUFFER_LAYOUT") = 언리얼 문자열 표기. 셰이더에 전달할 이름표야.

• || = 또는. 둘 중 하나라도 맞으면 참이야.
• ? ... : ... = 조건에 따라 둘 중 하나를 고르는 짧은 if야.

🔁 이제 다시 보자. SetDefine("GBUFFER_LAYOUT", GBufferLayout)로 셰이더에 식판 규격을 알려주고 → SetBasePassRenderTargetOutputFormat으로 출력 칸 포맷을 맞추고 → 필요하면 VelocityIndex 칸의 포맷까지 지정해. 즉 BasePass 셰이더가 나중에 어느 칸에 어떤 모양으로 쓸지, 컴파일 전에 주문서를 작성하는 장면이야.

여기서 중요한 건 GBUFFER_LAYOUT이 단순 설명용 이름이 아니라는 거야.

셰이더가 실제로 분기하고, 어떤 MRT 슬롯을 쓸지 결정하는 기준이 돼.

서버 패킷으로 치면 wID만 보고 핸들러를 고르는 게 아니라, 그 wID에 맞는 패킷 구조체 크기와 필드 배치까지 같이 정하는 느낌이야.

2. BasePass가 쓸 식판 칸들을 모은다

이제 렌더러가 실제 렌더타깃들을 모아.

RenderBasePass 안에서 BasePassTextures 배열을 만들고, 거기에 GBuffer 렌더타깃들을 채운다.

식판 창고에서 오늘 쓸 칸들을 꺼내오는 장면이야.

🔤 기호 사전 — BasePass 식판 모으기
• TStaticArray<..., MaxSimultaneousRenderTargets> = 최대 MRT 개수만큼 미리 칸을 가진 고정 배열이야.
• FTextureRenderTargetBinding = "이 텍스처를 렌더타깃 칸에 묶겠다"는 바인딩 정보야.
• uint32 = 0 이상의 정수를 담는 32비트 숫자야.
• SceneTextures.GetGBufferRenderTargets = 씬이 가진 GBuffer 텍스처들을 BasePass용 배열에 채워주는 함수야.
• Substrate::AppendSubstrateMRTs = Substrate 재질 시스템이 필요로 하는 추가 MRT 칸을 뒤에 붙이는 처리야.
• TArrayView = 실제 배열을 복사하지 않고 "이 범위만 볼게" 하는 얇은 창문이야.
• FRDGTextureRef = RDG 안에서 텍스처를 가리키는 손잡이야.
🔁 이제 다시 보자. BasePassTextures라는 식판 칸 배열을 만들고 → GetGBufferRenderTargets가 SceneColor와 GBuffer들을 채우고 → Substrate가 필요하면 칸을 더 붙이고 → MakeArrayView로 실제 쓸 개수만큼 잘라서 본다. 마지막 BasePassDepthTexture는 식판 옆에 같이 놓는 깊이 장부야.

여기서 SceneTextures는 이미 앞쪽 패스들이 준비한 화면 크기 텍스처 묶음이야.

BasePass가 새로 색칠할 대상은 대충 하나가 아니고, 여러 개야.

DirectX로 말하면 OMSetRenderTargets에 RTV 하나가 아니라 RTV 배열을 넘기는 상황이야.

3. SceneTextures는 SceneColor 다음에 GBufferA~E를 꽂는다

그럼 GetGBufferRenderTargets는 안에서 뭘 넣을까?

보면 첫 슬롯은 SceneColor고, GBuffer를 쓰는 설정이면 A부터 E와 Velocity를 인덱스에 맞춰 꽂는다.

식판 첫 칸은 항상 큰 밥칸이고, 나머지는 설정표를 보고 반찬 칸을 배치하는 식이야.

uint32 FSceneTextures::GetGBufferRenderTargets( TArrayView<FTextureRenderTargetBinding> RenderTargets, EGBufferLayout Layout) const { uint32 RenderTargetCount = 0; // All configurations use scene color in the first slot. RenderTargets[RenderTargetCount++] = FTextureRenderTargetBinding(Color.Target); if (Config.bIsUsingGBuffers) { struct FGBufferEntry { FGBufferEntry(const TCHAR* InName, FRDGTextureRef InTexture, int32 InIndex) : Name(InName) , Texture(InTexture) , Index(InIndex) {} const TCHAR* Name; FRDGTextureRef Texture; int32 Index; }; const FGBufferBindings& Bindings = Config.GBufferBindings[Layout]; const FGBufferEntry GBufferEntries[] = { { TEXT("GBufferA"), GBufferA, Bindings.GBufferA.Index }, { TEXT("GBufferB"), GBufferB, Bindings.GBufferB.Index }, { TEXT("GBufferC"), GBufferC, Bindings.GBufferC.Index }, { TEXT("GBufferD"), GBufferD, Bindings.GBufferD.Index }, { TEXT("GBufferE"), GBufferE, Bindings.GBufferE.Index }, { TEXT("Velocity"), Velocity, Bindings.GBufferVelocity.Index } }; for (const FGBufferEntry& Entry : GBufferEntries) { checkf(Entry.Index <= 0 || Entry.Texture != nullptr, TEXT("Texture '%s' was requested by FGBufferInfo, but it is null."), Entry.Name); if (Entry.Index > 0) { RenderTargets[Entry.Index] = FTextureRenderTargetBinding(Entry.Texture); RenderTargetCount = FMath::Max(RenderTargetCount, uint32(Entry.Index + 1)); } } } // Forward shading path else if (IsUsingBasePassVelocity(Config.ShaderPlatform)) { RenderTargets[RenderTargetCount++] = FTextureRenderTargetBinding(Velocity); } return RenderTargetCount; }
🔤 기호 사전 — SceneTextures가 식판을 채우는 법
• const = 이 함수가 자기 객체를 함부로 바꾸지 않겠다는 약속이야.
• RenderTargets[RenderTargetCount++] = 현재 번호 칸에 넣고, 번호를 하나 올린다는 뜻이야.
• Config.bIsUsingGBuffers = 지금 렌더링 설정이 GBuffer를 쓰는지 보는 참/거짓 값이야.
• struct FGBufferEntry = GBuffer 한 칸의 이름, 텍스처, 인덱스를 묶은 작은 상자야.
• Bindings.GBufferA.Index = GBufferA가 MRT 몇 번 칸에 들어갈지 적힌 번호야.
• checkf = 조건이 깨지면 메시지를 내고 터뜨리는 개발용 안전핀이다.
• FMath::Max = 둘 중 더 큰 값을 고르는 언리얼 수학 함수야.
🔁 이제 다시 보자. SceneColor를 먼저 0번 칸에 꽂고 → GBuffer를 쓰면 GBufferEntries 배열에 A, B, C, D, E, Velocity 후보를 만든 뒤 → 각 항목의 Index가 0보다 크면 그 번호 칸에 텍스처를 꽂아. 그래서 BasePass 입장에서는 "몇 개의 렌더타깃이 붙었는지"를 RenderTargetCount로 알 수 있어.

이 코드가 이 챕터의 핵심이야.

디퍼드의 GBuffer는 추상 개념이 아니야.

실제로 GBufferA, GBufferB, GBufferC, GBufferD, GBufferE, Velocity라는 텍스처들이 렌더타깃 배열 칸에 들어간다.

여기서 0번 SceneColor를 먼저 넣고, GBuffer 항목들은 Bindings가 말하는 인덱스로 들어가.

즉 이름과 슬롯 번호가 완전히 고정된 상수처럼 보이지만, 실제로는 플랫폼과 레이아웃 설정이 끼어들 수 있어.

그래서 앞 절의 GBUFFER_LAYOUT이 필요했던 거야.

셰이더와 C++이 같은 식판 배치표를 봐야 하니까.

🌱 이 개념은 왜 생겼나 — 렌더타깃 바인딩
• 원래 구조: 그림 그릴 종이가 하나면 "여기에 그려"라고 텍스처 하나만 넘기면 끝이야.
• 그런데 문제: BasePass 식판은 SceneColor, GBufferA~E, Velocity, Depth까지 여러 칸이야. 드로우 중간에 칸 묶음이 흔들리면 메시마다 다른 식판에 배식해버려.
• 그래서 필요한 것: 오늘 쓸 칸들을 한 묶음으로 잠가서 패스에 넘기는 손잡이가 필요해. 그게 렌더타깃 바인딩이야.

4. 렌더타깃 바인딩을 만들고 BasePass 내부로 넘긴다

식판 칸들을 모았으면 이제 "이 칸들에 그려라"라고 패스에 묶어야 해.

깊이 스텐실도 같이 붙이고, 그 상태로 RenderBasePassInternal에 넘긴다.

이 지점부터는 식판 칸 구성이 흔들리면 안 된다는 뜻이야.

BasePass 내부에서 수많은 메시 드로우가 같은 렌더타깃 묶음을 보고 달려야 하니까.

서버로 치면 패킷 처리 중간에 세션 send buffer 구조를 바꾸면 안 되는 것과 같아.

한 프레임의 BasePass 동안은 "오늘 식판 배치표"가 고정돼 있어야 해.

우리 서버 감각으로 말하면, 같은 패킷 파싱 결과를 DB 테이블 하나에만 쓰는 게 아니라 Character, InventoryLog, CombatState 여러 테이블에 한 트랜잭션으로 나눠 쓰는 느낌이야.

한 번의 사실을 여러 칸에 정리해두면, 뒤에서 읽기가 쉬워져.

🌱 이 개념은 왜 생겼나 — MRT
• 원래 구조: 픽셀 셰이더 한 번은 색 하나만 뱉고, 텍스처 하나에만 적는다고 생각하면 쉬워.
• 그런데 문제: GBufferA, B, C, D를 따로 채우려고 메시를 네 번 그리면 BasePass 배식 줄이 네 배로 길어져. 같은 학생을 네 번 줄 세우는 거야.
• 그래서 필요한 것: 픽셀 셰이더 한 번으로 여러 식판 칸에 동시에 쓰는 출구가 필요해. Multiple Render Targets, 줄여서 MRT야.

6. 픽셀 셰이더는 GBuffer를 MRT 배열에 흩뿌린다

C++은 식판을 준비하고, 셰이더를 그 식판에 연결했어.

그럼 픽셀 셰이더 끝에서는 어떤 일이 일어날까?

BasePassPixelShader 쪽을 보면 EncodeGBuffer가 OutGBufferA/B/C/D/E를 만들고, 그것들을 Out.MRT[...]에 넣는다.

다음 장 basepass-shader에서 이 안을 자세히 볼 거고, 이번 장에서는 "진짜 여러 렌더타깃에 나눠 쓴다"는 증거만 잡자.

BasePassPixelShader.usf:2359

float4 OutGBufferA = 0; float4 OutGBufferB = 0; float4 OutGBufferC = 0; EncodeGBuffer(GBuffer, OutGBufferA, OutGBufferB, OutGBufferC, OutGBufferD, OutGBufferE, OutVelocity, QuantizationBias); Out.MRT[1] = OutGBufferA; Out.MRT[2] = OutGBufferB; Out.MRT[3] = OutGBufferC; #if GBUFFER_HAS_VELOCITY Out.MRT[4] = OutVelocity; #endif Out.MRT[GBUFFER_HAS_VELOCITY ? 5 : 4] = OutGBufferD; #if GBUFFER_HAS_PRECSHADOWFACTOR Out.MRT[GBUFFER_HAS_VELOCITY ? 6 : 5] = OutGBufferE; #endif
🔤 기호 사전 — 셰이더가 식판에 담는 순간
• float4 = 숫자 4개짜리 벡터야. 렌더타깃 한 픽셀에 RGBA처럼 담기 좋다.
• EncodeGBuffer = 재질 정보 묶음 GBuffer를 실제 렌더타깃에 쓸 수 있는 압축된 값들로 포장하는 함수야.
• Out.MRT[1] = 출력 MRT 배열의 1번 칸이야. 0번은 앞에서 SceneColor 쪽으로 쓰이는 흐름이라 GBufferA는 여기서 1번에 들어가.
• #if GBUFFER_HAS_VELOCITY = Velocity 칸이 있는 설정일 때만 안쪽 코드를 컴파일한다는 뜻이야.
• GBUFFER_HAS_PRECSHADOWFACTOR = 미리 계산된 그림자 팩터 칸이 필요한지 보는 셰이더 define이야.
• QuantizationBias = 값을 텍스처 포맷에 넣을 때 생기는 양자화 오차를 줄이려는 보정값이야.
🔁 이제 다시 보자. EncodeGBuffer가 재질 도시락을 OutGBufferA/B/C/D/E와 OutVelocity로 나누고 → Out.MRT[1], [2], [3]에 A/B/C를 꽂고 → Velocity가 있으면 [4]에 꽂고 → 나머지 D/E는 설정에 따라 뒤 슬롯에 꽂아. C++이 준비한 식판 칸과 셰이더의 MRT 번호가 여기서 맞물린다.

이 코드를 보면 디퍼드 렌더링의 핵심이 아주 노골적으로 보여.

BasePass는 "빛 받은 최종 색"을 끝까지 계산하지 않아.

대신 조명 계산에 필요한 재질 정보를 여러 텍스처에 분산 저장한다.

조명 패스는 나중에 화면 픽셀을 돌면서 이 GBuffer 칸들을 읽어.

그 픽셀의 월드 노멀을 보고 빛 방향과 dot을 하고, 러프니스를 보고 하이라이트 폭을 정하고, 베이스 컬러를 보고 반사 색을 정한다.

그러니까 BasePass는 배식이고, Deferred Lighting은 식판 검사 후 소스 뿌리기야.

GBUFFER_LAYOUT으로 식판 규격을 맞추고, SceneTextures에서 실제 칸을 꺼내고, BasePassRenderTargets로 묶고, BasePass 메시를 그리면, 픽셀 셰이더가 Out.MRT[]에 재질 정보를 나눠 쓴다.

우리 서버·DirectX 랑 비교

DirectX 경험이 있으면 MRT부터 떠올리면 돼.

보통은 RTV 하나를 묶고 픽셀 셰이더가 SV_Target0 하나를 쓴다.

BasePass의 GBuffer 경로는 RTV 배열을 묶고, 픽셀 셰이더가 여러 SV_Target에 값을 쓰는 방식이야.

UE 코드에서는 그 RTV 배열이 FRenderTargetBindingSlots와 FTextureRenderTargetBinding으로 감싸져 있고, RDG 패스 파라미터에 들어간다.

서버 경험으로 보면 더 쉽다.

우리가 전투 로그를 처리할 때 한 덩어리 이벤트를 여러 캐시에 나눠 저장하잖아.

현재 HP, 마지막 피격 시간, 어그로 점수, 로그 테이블이 다 따로 있을 수 있어.

한 곳에 JSON 통째로만 넣어두면 나중에 "어그로만 빠르게 읽기"가 느려져.

GBuffer도 그래.

픽셀 하나의 재질 정보를 한 텍스처에 통째로 우겨넣지 않고, 조명 패스가 빠르게 읽기 좋은 칸들로 나눠 둔다.

GBufferA가 노멀 성격의 정보를, GBufferB/C가 재질 성질과 색 성격의 정보를 담는 식으로 말이야.

정확한 packing은 다음 장 basepass-shader에서 본다.

이번 장에서는 BasePass C++이 그 칸들을 준비하고 연결한다는 것만 잡으면 돼.

또 하나.

PrePass에서 깊이를 먼저 깔아둔 이유가 여기서 이어져.

BasePass 픽셀 셰이더는 재질 값을 계산하고 여러 MRT에 쓰니까 싸지 않아.

앞 장 prepass-depth의 깊이 정보가 있으면 안 보이는 픽셀을 덜 칠할 수 있어.

서버에서 락 잡기 전에 "이 요청은 처리 대상인가"를 빠르게 거르는 것과 같은 감각이야.

비싼 일은 대상이 확정된 뒤에 한다.

이 챕터에서 딱 이것만

  • BasePass는 디퍼드 경로에서 최종 조명을 완성하는 패스가 아니라, 재질 정보를 GBuffer 식판에 눕히는 패스야.
  • C++은 GBUFFER_LAYOUT과 렌더타깃 출력 포맷을 셰이더 컴파일 환경에 알려줘.
  • SceneTextures.GetGBufferRenderTargets가 SceneColor와 GBufferA~E, Velocity 후보를 렌더타깃 배열에 꽂아.
  • PassParameters->RenderTargets = BasePassRenderTargets 때문에 BasePass 메시 드로우가 그 여러 칸에 동시에 쓴다.
  • 픽셀 셰이더 끝에서는 EncodeGBuffer 결과가 Out.MRT[] 슬롯들로 나뉘어 들어간다.

🎯 원리 한 줄 요약

BasePass는 화면 픽셀마다 재질 신분증을 한 번 계산해서, SceneColor 하나가 아니라 GBufferA/B/C/D/E 같은 여러 MRT 식판 칸에 나눠 눕혀두는 디퍼드 렌더링의 배식 시간이다.
