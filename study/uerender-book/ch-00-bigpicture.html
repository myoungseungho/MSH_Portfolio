큰 그림 — 한 프레임이 그려지기까지

언리얼 렌더링 · 00 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "언리얼이 한 프레임을 어떤 부서들에 넘기며 최종 화면까지 만드는가"의 전체 지도가 잡힌다.

왜 이걸 배워? — 문제의식부터

렌더링을 처음 보면 단어가 한꺼번에 쏟아져. ViewFamily, SceneRenderer, BasePass, RDG, RHI, GBuffer, Nanite, Lumen. 이걸 각각 외우면 금방 길을 잃어.

서버로 치면 CM_ATTACK 핸들러만 열어놓고, 소켓 수신, 세션 버퍼, 패킷 큐, 게임 로직 스레드, DB 저장, 브로드캐스트 흐름을 모르는 상태랑 같아. 함수 하나는 보이는데 "얘가 왜 여기서 호출되지?"가 전부 흐려지는 거지.

이 큰 그림이 없으면 뒤에서 바로 터진다. RenderBasePass가 왜 GraphBuilder를 받는지, 깊이 버퍼가 왜 이미 있어야 하는지, RHI 명령이 왜 렌더러 코드 안에서 바로 보이지 않는지, 한 프레임이 왜 수십 개 패스로 쪼개지는지 감이 안 와.

언리얼도 같은 문제를 만났고, 답은 프레임을 여러 책임 구역으로 쪼개서 릴레이하는 것이야. 게임 월드가 바로 GPU를 때리지 않는다. 렌더러가 촬영을 기획하고, RDG가 촬영 순서표를 만들고, RHI가 장비 공통 언어로 바꾸고, D3D12RHI가 실제 DirectX 호출로 내려보낸다.

그래서 00장은 노선도야. 지금은 각 역 내부를 파지 않는다. 대신 "어느 역 다음에 어느 역이 오는지"를 잡는다. 다음 장부터는 이 노선도의 한 칸씩 확대해서 본다.

0. 비유부터 — 영화 촬영장 한 컷 만들기

한 프레임은 영화 촬영장의 사진 한 장이라고 생각하자.

사진 한 장을 찍으려면 배우와 소품이 지금 위치에 있어야 해. 그다음 카메라를 정하고, 감독을 배정하고, 바닥에 위치 표시를 하고, 배우의 옷감과 재질 정보를 기록하고, 조명을 켜고, 색보정하고, 마지막으로 극장 스크린에 건다.

렌더링도 이 순서로 읽으면 돼.

소품 최신화 = 게임 월드 상태를 렌더 쪽에 맞춤 카메라 세팅 = ViewFamily / View 감독 배정 = FDeferredShadingSceneRenderer 또는 FMobileSceneRenderer 바닥 표시 = PrePass / Depth 재질 기록 = BasePass / GBuffer 조명 켜기 = Deferred Lighting 색보정 = PostProcess 상영관으로 보내기 = RDG → RHI → D3D12RHI

언리얼 렌더링은 거대한 촬영장이고, 한 프레임은 "지금 이 순간의 장면을 찍어서 화면에 거는 일"이야. 이 비유를 끝까지 끌고 갈게.

1. 폴더 지도부터

이 책에서 인용하는 렌더링 소스는 여기 안에 있어.

_study/UE_Graphics/Engine/ Source/Runtime/Renderer/ 촬영 감독과 패스 흐름 Source/Runtime/RenderCore/ RDG, 셰이더 공통, 렌더 스레드 기반 Source/Runtime/RHI/ GPU에게 말하는 공통 명령 언어 Source/Runtime/D3D12RHI/ D3D12 실제 구현 Shaders/Private/ GPU에서 도는 .usf/.ush 대본

오늘 잡을 큰 길은 이거야.

게임 월드 → FRendererModule::BeginRenderingViewFamily → FSceneRenderBuilder → FDeferredShadingSceneRenderer / FMobileSceneRenderer → FSceneRenderer::Render → PrePass / BasePass / Lighting / PostProcess → FRDGBuilder::ExecutePass → RHICommandList → D3D12RHI / GPU

각 줄은 뒤 챕터의 입구야. 오늘은 역 이름과 방향만 잡는다.

2. 게임 쪽에서 촬영표를 만든다

한 프레임의 렌더링은 게임 쪽에서 "이 카메라 묶음을 그려줘" 하고 요청하면서 시작해. 그 요청 안에서 FSceneRenderBuilder가 렌더러를 촬영표에 등록한다.

SceneRendering.cpp:5200

for (FSceneRenderer* SceneRenderer : SceneRenderers) { SceneRenderer->ViewFamily.DisplayInternalsData.Setup(World); SceneRenderBuilder.AddRenderer(SceneRenderer, bShowHitProxies ? TEXT("HitProxies") : TEXT("ViewFamilies"), [] (FRDGBuilder& GraphBuilder, const FSceneRenderFunctionInputs& Inputs) { RenderViewFamily_RenderThread(GraphBuilder, Inputs.Renderer, Inputs.SceneUpdateInputs); return true; }); }
🔤 기호 사전 — 촬영표 등록 토막
• for (...) = 여러 렌더러를 하나씩 꺼내 반복한다.
• FSceneRenderer* = 렌더러를 가리키는 포인터.
• SceneRenderer->ViewFamily = 렌더러 안의 카메라 묶음을 꺼낸다.
• AddRenderer(...) = 촬영표에 "이 렌더러를 실행해" 하고 등록한다.
• [] (...) { ... } = 나중에 실행할 작은 함수 덩어리, 람다야.
• FRDGBuilder& GraphBuilder = RDG 촬영 순서표를 만드는 담당자. &는 원본 참조에 가까워.
• return true = 이 렌더 함수가 일을 했다고 알려준다.
🔁 이제 다시 보자. 렌더러마다 AddRenderer로 촬영표에 올리고, 등록된 람다 안에서 RenderViewFamily_RenderThread가 호출돼. 영화로 치면 "오늘 감독이 찍을 장면을 촬영표에 올리는 장면"이야.

여기서 아직 GPU 명령이 나간 게 아니야. 먼저 "무엇을 어떤 순서로 찍을지"를 적는 중이야. 서버에서 IOCP 워커가 바로 캐릭터를 때리지 않고, 패킷을 큐와 핸들러 흐름에 태우는 것과 비슷해.

3. 디퍼드 감독이냐 모바일 감독이냐

플랫폼과 기능 레벨에 따라 촬영 방식이 달라. PC/콘솔의 큰 줄기는 보통 디퍼드 렌더러고, 모바일은 별도 렌더러가 맡는다.

SceneRenderBuilder.cpp:511

if (ShadingPath == EShadingPath::Deferred) { OutRenderers.Add(new FDeferredShadingSceneRenderer(ViewFamily, HitProxyConsumer)); } else { check(ShadingPath == EShadingPath::Mobile); OutRenderers.Add(new FMobileSceneRenderer(ViewFamily, HitProxyConsumer)); }
🔤 기호 사전 — 감독 선택 토막
• if = 조건이 맞으면 안쪽을 실행한다.
• ShadingPath == EShadingPath::Deferred = 촬영 방식이 디퍼드인지 묻는다.
• new FDeferredShadingSceneRenderer(...) = 디퍼드 렌더러를 새로 만든다.
• OutRenderers.Add(...) = 만든 렌더러를 목록에 넣는다.
• else = 앞 조건이 아니면 이쪽으로 온다.
• check(...) = 가정이 틀리면 개발 중 바로 터뜨리는 안전 검사.

디퍼드 렌더러는 이 책의 큰 줄기야. PrePass, BasePass, GBuffer, Deferred Lighting 같은 챕터들이 여기서 나온다. 모바일은 "다른 감독도 있다"까지만 기억하고 지나가자.

4. 렌더 스레드 출입문

렌더러가 정해졌으면 렌더 스레드 쪽 함수가 호출돼. 일반 화면이면 Renderer->Render(...)로 들어간다.

SceneRendering.cpp:4895

static void RenderViewFamily_RenderThread(FRDGBuilder& GraphBuilder, FSceneRenderer* Renderer, const FSceneRenderUpdateInputs* SceneUpdateInputs) { FSceneViewFamily& ViewFamily = Renderer->ViewFamily; LLM_SCOPE(ELLMTag::SceneRender); SCOPE_CYCLE_COUNTER(STAT_TotalSceneRenderingTime); SCOPED_NAMED_EVENT_TCHAR_CONDITIONAL(*ViewFamily.ProfileDescription, FColor::Red, !ViewFamily.ProfileDescription.IsEmpty()); if (ViewFamily.EngineShowFlags.HitProxies) { Renderer->RenderHitProxies(GraphBuilder, SceneUpdateInputs); } else { Renderer->Render(GraphBuilder, SceneUpdateInputs); } Renderer->FlushCrossGPUFences(GraphBuilder); }
🔤 기호 사전 — 렌더 스레드 진입 토막
• static void = 이 파일 안에서 쓰는 함수이고, 돌려주는 값은 없다.
• FSceneRenderer* Renderer = 렌더러를 가리키는 포인터.
• const FSceneRenderUpdateInputs* = 바꾸지 않을 입력 묶음을 가리키는 포인터.
• Renderer->ViewFamily = 렌더러 안의 카메라 묶음을 꺼낸다.
• SCOPE_CYCLE_COUNTER = 시간 측정용 표식.
• ViewFamily.EngineShowFlags.HitProxies = 선택/에디터용 특수 렌더 모드인지 보는 깃발.
• Renderer->Render(...) = 실제 장면 렌더링으로 들어가는 문.
🔁 이제 다시 보자. RenderViewFamily_RenderThread는 촬영장 출입문이야. ViewFamily를 꺼내고 → 계측 표식을 걸고 → 특수 모드면 RenderHitProxies, 아니면 Render로 들어가. 앞에서 디퍼드 감독이 만들어졌다면 이 문 뒤는 FDeferredShadingSceneRenderer::Render야.

5. 먼저 깊이를 깐다

디퍼드 렌더러는 보통 깊이를 먼저 만든다. 누가 앞에 있고 뒤에 있는지 알면, 뒤에 가려질 픽셀을 비싸게 칠하지 않아도 되거든. 영화 촬영장으로 치면 배우들이 설 위치를 바닥에 먼저 붙이는 거야.

DeferredShadingRenderer.cpp:2378

const ERenderTargetLoadAction DepthLoadAction = ERenderTargetLoadAction::EClear; AddClearDepthStencilPass(GraphBuilder, LocalSceneTextures.Depth.Target, DepthLoadAction, StencilLoadAction); // Draw the scene pre-pass / early z pass, populating the scene depth buffer and HiZ if (bNeedsPrePass) { RenderPrePass(GraphBuilder, InViews, LocalSceneTextures.Depth.Target, InstanceCullingManager, &FirstStageDepthBuffer); } else { // We didn't do the prepass, but we still want the HMD mask if there is one RenderPrePassHMD(GraphBuilder, InViews, LocalSceneTextures.Depth.Target); }
🔤 기호 사전 — 깊이 먼저 토막
• const = 아래에서 이 값을 바꾸지 않겠다는 약속.
• ERenderTargetLoadAction::EClear = 렌더 타깃을 쓰기 전에 깨끗이 지우겠다는 선택지.
• AddClearDepthStencilPass(...) = 깊이/스텐실 버퍼를 지우는 패스를 RDG에 추가한다.
• bNeedsPrePass = 프리패스가 필요한지 보는 참/거짓 깃발.
• RenderPrePass(...) = 깊이 먼저 그리는 패스.
• LocalSceneTextures.Depth.Target = 이번 장면의 깊이 텍스처 대상.
• &FirstStageDepthBuffer = 변수의 주소를 넘긴다.
🔁 이제 다시 보자. AddClearDepthStencilPass로 깊이 칠판을 지우고 → bNeedsPrePass면 RenderPrePass로 깊이를 채워. 이게 끝나야 뒤 촬영팀이 "어느 픽셀이 앞에 있는지"를 알고 낭비를 줄인다.

자세한 건 → prepass-depth에서 다시 본다.

6. 재질 정보를 화면에 눕힌다

깊이가 준비되면 화면 픽셀마다 "이 물체는 무슨 재질인가"를 적는다. 디퍼드 렌더링에서는 이 정보가 GBuffer에 들어간다. 색, 노멀, 거칠기, 금속성 같은 재료표를 먼저 적어두고, 빛은 나중에 따로 얹는다.

DeferredShadingRenderer.cpp:2902

{ if (!bHasRayTracedOverlay) { RenderBasePass(*this, GraphBuilder, Views, SceneTextures, DBufferTextures, BasePassDepthStencilAccess, ForwardScreenSpaceShadowMaskTexture, InstanceCullingManager, bNaniteEnabled, Scene->NaniteShadingCommands[ENaniteMeshPass::BasePass], NaniteRasterResults); } if (!bAllowReadOnlyDepthBasePass) { AddResolveSceneDepthPass(GraphBuilder, Views, SceneTextures.Depth); }
🔤 기호 사전 — 베이스패스 토막
• !bHasRayTracedOverlay = 레이트레이싱 오버레이가 없을 때. !는 참/거짓을 뒤집는다.
• RenderBasePass(...) = 불투명 물체의 기본 재질 정보를 그리는 큰 패스.
• *this = 지금 이 렌더러 객체 자체를 넘긴다.
• Views = 카메라들. 분할 화면이면 여러 개일 수 있다.
• SceneTextures = 깊이, 색, GBuffer 같은 장면 텍스처 묶음.
• ENaniteMeshPass::BasePass = Nanite 쪽에서도 BasePass용 명령을 고른다는 뜻.
• AddResolveSceneDepthPass(...) = 깊이 텍스처를 뒤 패스들이 읽기 좋은 상태로 정리한다.
🔁 이제 다시 보자. RenderBasePass는 배우의 옷감, 색, 표면 방향 같은 정보를 화면 버퍼에 적는 단계야. 아직 최종 예쁜 화면이 아니라, 조명을 얹기 위한 재료표를 만드는 중이야.

이 부분은 → basepass-gbuffer와 → basepass-shader에서 다시 들어간다.

7. 빛, 후처리, 마무리는 뒤에 온다

프리패스와 베이스패스만으로는 아직 영화가 아니야. 배우 위치와 재질표는 있는데 조명도 없고 색보정도 없거든.

조명 켜기RenderLights (DeferredShadingRenderer.cpp:3314)deferred-lighting
간접광/AORenderDiffuseIndirectAndAmbientOcclusion (DeferredShadingRenderer.cpp:3329)lumen-diffuse
반사/하늘빛RenderDeferredReflectionsAndSkyLighting (DeferredShadingRenderer.cpp:3339)lumen-overview

큰 함수 하나가 GPU를 한 번 때리고 끝나는 구조가 아니야. 작은 촬영팀들이 패스를 추가하고, RDG가 그 순서를 관리한다.

8. RDG가 패스를 실제 실행으로 바꾼다

앞에서 계속 GraphBuilder가 나왔지. 이건 "지금 당장 GPU에게 명령한다"가 아니라, "이 패스를 촬영표에 올린다"에 가까워. RDG는 패스들의 의존성을 보고, 필요한 배리어를 넣고, 실행 순서를 잡고, 실제 RHI 커맨드 리스트에 넘긴다.

RenderGraphBuilder.cpp:3482

void FRDGBuilder::ExecutePass(FRHIComputeCommandList& RHICmdListPass, FRDGPass* Pass) { // Note that we must do this before doing anything with RHICmdListPass. // For example, if this pass only executes on GPU 1 we want to avoid adding a // 0-duration event for this pass on GPU 0's time line. SCOPED_GPU_MASK(RHICmdListPass, Pass->GPUMask); RHICmdListPass.SwitchPipeline(Pass->Pipeline); ExecutePassPrologue(RHICmdListPass, Pass); Pass->Execute(RHICmdListPass); ExecutePassEpilogue(RHICmdListPass, Pass); }
🔤 기호 사전 — RDG 실행 토막
• FRDGBuilder::ExecutePass = RDG 빌더 안의 패스 실행 함수.
• FRHIComputeCommandList& = RHI 명령을 적는 목록의 원본 참조.
• FRDGPass* Pass = 실행할 RDG 패스를 가리키는 포인터.
• SCOPED_GPU_MASK = 어느 GPU에서 실행할지 범위를 잡는 표식.
• SwitchPipeline = 그래픽/컴퓨트 같은 GPU 파이프라인을 바꾼다.
• ExecutePassPrologue = 본 실행 전 준비를 한다.
• Pass->Execute(...) = 패스의 실제 몸통을 실행한다.
• ExecutePassEpilogue = 끝난 뒤 정리를 한다.
🔁 이제 다시 보자. RDG는 SwitchPipeline으로 장비를 맞추고 → ExecutePassPrologue로 준비하고 → Pass->Execute로 촬영하고 → ExecutePassEpilogue로 정리해. 패스 몸통만 부르는 게 아니라 앞뒤 안전 절차까지 붙이는 촬영 진행표야.

이게 → rdg의 핵심이고, 여기서 내려간 RHICmdListPass가 → rhi-commandlist의 세계로 이어진다.

9. 더 아래에는 RHI와 D3D12RHI가 있다

RDG가 패스를 실행하면 그 안의 드로우나 디스패치가 RHI 명령으로 쌓인다. RHI는 "D3D12냐 Vulkan이냐"를 숨긴 공통 언어야. Windows D3D12 환경이면 끝단에서 D3D12RHI가 실제 DirectX 12 호출로 바꾼다.

RDG Pass → RHICommandList → DrawIndexedPrimitive (RHICommandList.h:3973) → FD3D12CommandContext::RHIDrawIndexedPrimitive (D3D12Commands.cpp:1270) → GraphicsCommandList()->DrawIndexedInstanced 계열 (D3D12Commands.cpp:1297)

언리얼의 RenderBasePass가 직접 DrawIndexedInstanced를 부르는 게 아니야. 중간에 RDG와 RHI라는 촬영표/장비 통역을 지나간다.

우리 서버·DirectX 랑 비교

서버 관점으로 보면 이래.

서버에서렌더링에서
IOCP 워커가 소켓 이벤트를 받음게임 쪽이 BeginRenderingViewFamily로 렌더 시작
세션/패킷 객체를 만들고 큐에 넣음FSceneRenderBuilder가 렌더러와 RDG 작업 등록
싱글스레드 게임 로직이 순서대로 처리렌더 스레드가 Renderer->Render로 패스 구성
send queue가 소켓 API로 내려감RHICommandList가 D3D12RHI로 내려감

공통점은 바로 때리지 않고 중간 계층을 태운다는 거야. 서버도 워커 스레드에서 곧바로 캐릭터 HP를 깎지 않지. 락, 순서, 소유 스레드 때문에 큐와 핸들러가 필요해.

렌더링도 마찬가지야. 게임 스레드가 곧바로 DrawIndexedInstanced를 때리면 안 돼. 렌더 스레드 소유 데이터, GPU 리소스 수명, 리소스 배리어, 플랫폼별 RHI 차이를 다 맞춰야 해.

DirectX에서 직접 하던 커맨드 리스트 기록, PSO 바인딩, 렌더타깃 설정, 드로우 호출을 언리얼은 Renderer → RDG → RHI → D3D12RHI로 나눠 맡긴다.

영화로 다시 말하면, 감독이 카메라 셔터를 직접 누르지 않는다. 감독은 촬영 순서를 정하고, 조감독이 스케줄을 맞추고, 장비팀이 카메라를 세팅하고, 카메라 기사가 셔터를 누른다.

이 챕터에서 딱 이것만

  • 한 프레임은 BeginRenderingViewFamily에서 시작해 렌더러와 RDG 패스로 내려간다.
  • FSceneRenderBuilder는 이번 프레임 촬영표를 만들고 렌더러 실행 함수를 등록한다.
  • 디퍼드면 FDeferredShadingSceneRenderer가 만들어지고, 주요 패스들이 거기서 나온다.
  • 디퍼드의 큰 순서는 PrePass → BasePass/GBuffer → Lighting → PostProcess → Finish다.
  • RDG는 패스 몸통만 실행하지 않고 앞뒤 준비/정리와 RHI 연결까지 맡는다.

🎯 원리 한 줄 요약

언리얼의 한 프레임은 게임 월드가 바로 GPU를 치는 게 아니라, Renderer가 촬영을 기획하고 RDG가 순서표를 실행하고 RHI/D3D12RHI가 실제 장비 명령으로 내려보내는 긴 릴레이다.
