🧱 먼저 알아야 할 것 — 이름표와 실제 자리
• 이름표: 사물함에 "철수"라고 붙어 있어도, 실제 가방은 몇 번째 칸 안에 들어 있다.
• 실제 자리: 이름만 알아서는 꺼낼 수 없고, 어느 줄 몇 번째 칸인지도 알아야 한다.
• 약속 맞추기: 부르는 이름과 찾아갈 자리가 서로 맞아야 엉뚱한 칸을 열지 않는다.
이게 잡히면 아래 설명이 얹힌다.

왜 이걸 배워? — 문제의식부터

앞에서 셰이더는 GPU에서 도는 작은 프로그램이라고 했어. shader-basics 그리고 그 셰이더가 컴파일될 때, 어떤 파라미터 이름을 쓰는지도 같이 정리된다고 봤지. shader-compile

근데 아직 제일 실전 질문이 남아. Parameters.TexelSize = ...로 C++ 값을 넣으면, 그 값은 어떻게 HLSL의 TexelSize 자리까지 갈까?

이걸 모르면 렌더링 코드를 읽을 때 FParameters 구조체가 전부 마술처럼 보여. 텍스처 SRV, UAV, 샘플러, 유니폼 버퍼가 C++ 멤버처럼 생겼는데, GPU 입장에서는 슬롯 번호와 리소스 핸들이 필요하잖아.

문제는 이름, 타입, 위치야. 셰이더는 TexelSize라는 이름을 요구하고, C++ 구조체는 어떤 바이트 오프셋에 TexelSize 값을 들고 있어. 둘이 이름도 맞아야 하고, 크기도 맞아야 하고, 읽는 위치도 맞아야 해.

우리 서버로 치면 SP_LOGIN이 AccountID를 원했는데, 패킷 구조체 오프셋이 밀려서 월드 ID를 읽는 상황이야. 패킷도 필드 이름과 위치가 맞아야 하듯, 셰이더 파라미터도 C++ 필드와 HLSL 변수의 약속이 맞아야 해.

그래서 이번 챕터는 그 약속표를 만든다. SHADER_PARAMETER 매크로가 멤버 선언을 넘어 메타데이터를 만들고, ShaderParameterStruct.cpp가 그 메타데이터를 셰이더 컴파일 결과와 맞춘 뒤, 마지막에 RHI 커맨드 리스트에 실제 값을 붙이는 흐름을 본다.

🧱 먼저 알아야 할 것 — 줄지어 선 칸과 떨어진 거리
• 줄지어 선 칸: 긴 서랍장처럼 작은 칸들이 처음부터 끝까지 순서대로 놓여 있다고 생각하면 된다.
• 시작점: 맨 앞 칸을 하나 정하면, 다른 칸은 거기서 몇 칸 떨어졌는지로 찾을 수 있다.
• 크기: 어떤 물건은 한 칸만 쓰고, 어떤 물건은 여러 칸을 이어서 쓴다.
이게 잡히면 아래 설명이 얹힌다.

0. 비유부터 — 급식판과 배식표

이번 장은 급식판 비유로 가자.

C++의 FParameters 구조체는 급식판이야. TexelSize 칸, MipInSRV 칸, MipOutUAV 칸, MipSampler 칸이 있어.

SHADER_PARAMETER는 칸 이름표야. "이 칸은 TexelSize, 타입은 FVector2f, 식판 시작점에서 몇 바이트 떨어짐"까지 적어 둔다.

셰이더 컴파일러가 만든 FShaderParameterMap은 오늘의 배식표야. GPU 셰이더가 "나는 TexelSize를 몇 번 버퍼 몇 번째 자리에서 먹을 거야"라고 적은 표지.

FShaderParameterBindings는 배식 동선표야. C++ 식판의 어느 칸을 읽어서 셰이더의 어느 슬롯에 줄지 적어 둔다.

마지막 SetShaderParameters는 배식원이야. 동선표를 보고 C++ 메모리에서 값을 꺼내 FRHIBatchedShaderParameters에 담고, RHI 커맨드 리스트에 "이 셰이더 실행할 때 이 반찬들 같이 내보내"라고 넘긴다.

🌱 이 개념은 왜 생겼나 — 셰이더 파라미터 구조체(FParameters)
• 원래 구조: 셰이더에 줄 값을 함수 인자처럼 하나씩 넘기면 될 것 같아. TexelSize 따로, 텍스처 따로, 샘플러 따로.
• 그런데 문제: 셰이더 하나가 값 10개, 텍스처 4개, 샘플러 2개를 원하면 배식원이 매번 "몇 번째 칸?"을 외워야 해. 칸 하나 밀리면 국 자리에 반찬이 들어가.
• 그래서 필요한 것: 값들을 한 급식판에 담고, 칸 이름까지 같이 붙이는 구조가 필요해. 그 식판이 FParameters야.
🧱 먼저 알아야 할 것 — 미리 펼쳐지는 글자 약속
• 글자 바꾸기: 공책에 "여기에 이름 쓰기"라고 적어 두면, 나중에 그 자리에 실제 이름을 끼워 넣을 수 있다.
• 미리 펼치기: 어떤 글은 일을 시작한 뒤 실행되는 게 아니라, 시작 전에 더 긴 글로 바뀐다.
• 한 줄이 여러 일: 짧은 약속 한 줄이 펼쳐지면 이름 적기, 칸 만들기, 검사하기 같은 여러 줄이 될 수 있다.
이게 잡히면 아래 설명이 얹힌다.

1. 사용자는 이렇게 쓴다 — FParameters 식판

먼저 실제 사용 예시부터 보자. GenerateMips.cpp의 컴퓨트 셰이더가 파라미터 구조체를 이렇게 선언해.

GenerateMips.cpp:25

BEGIN_SHADER_PARAMETER_STRUCT(FParameters, ) SHADER_PARAMETER(FVector2f, TexelSize) SHADER_PARAMETER_RDG_TEXTURE_SRV(Texture2D, MipInSRV) SHADER_PARAMETER_RDG_TEXTURE_UAV(RWTexture2D, MipOutUAV) SHADER_PARAMETER_SAMPLER(SamplerState, MipSampler) END_SHADER_PARAMETER_STRUCT()
🔤 기호 사전 — 위 코드 인용
• BEGIN_SHADER_PARAMETER_STRUCT = 셰이더에 줄 식판 구조체를 시작해.
• FParameters = 이 식판의 C++ 타입 이름이야.
• SHADER_PARAMETER(FVector2f, TexelSize) = TexelSize라는 일반 값 칸이야.
• SHADER_PARAMETER_RDG_TEXTURE_SRV = RDG 텍스처를 읽기용 SRV로 넘기는 칸이야.
• SHADER_PARAMETER_RDG_TEXTURE_UAV = RDG 텍스처를 쓰기용 UAV로 넘기는 칸이야.
• SHADER_PARAMETER_SAMPLER = 텍스처 샘플링 방식을 넘기는 칸이야.
🔁 이제 다시 보자. 위 코드는 그냥 C++ 멤버 선언처럼 보여도, 실제로는 "셰이더가 먹을 식판의 칸 목록"이야. 숫자, 읽기 리소스, 쓰기 리소스, 샘플러가 한 판에 모이고, 각 칸 이름이 나중에 HLSL 변수 이름과 맞춰진다.

첫 번째 핵심은 이거야. SHADER_PARAMETER는 멤버를 만들 뿐 아니라, 나중에 바인딩할 수 있도록 이름표와 좌표표도 만든다.

🌱 이 개념은 왜 생겼나 — FShaderParametersMetadata
• 원래 구조: FParameters 메모리만 있으면 C++은 값을 다 알 것 같아. 그냥 식판 시작 주소를 들고 가면 되겠지.
• 그런데 문제: 마지막 제출 때는 void* 시작 주소 하나만 남아. TexelSize가 0바이트째인지 16바이트째인지 모르면 배식원이 눈감고 칸을 찍는 거야.
• 그래서 필요한 것: 식판 전체 크기와 칸 목록을 적은 설계도가 필요해. 값 자체가 아니라 설명서라서 FShaderParametersMetadata야.

2. 구조체 전체 설명서 — FShaderParametersMetadata

BEGIN_SHADER_PARAMETER_STRUCT가 펼쳐지면 구조체 전체 설명서를 만들 수 있어. 진짜 정의는 ShaderParameterMacros.h에 있다.

#define INTERNAL_SHADER_PARAMETER_GET_STRUCT_METADATA(StructTypeName) \ { \ static FShaderParametersMetadata StaticStructMetadata(\ FShaderParametersMetadata::EUseCase::ShaderParameterStruct, \ EUniformBufferBindingFlags::Shader, \ TEXT(#StructTypeName), \ TEXT(#StructTypeName), \ nullptr, \ nullptr, \ FTypeInfo::FileName, \ FTypeInfo::FileLine, \ sizeof(StructTypeName), \ StructTypeName::zzGetMembers()); \ return &StaticStructMetadata; \ }
🔤 기호 사전 — 위 코드 인용
• static FShaderParametersMetadata = 한 번 만들어 오래 들고 있는 구조체 설명서야.
• ShaderParameterStruct = 이 설명서의 용도가 셰이더 파라미터 구조체라는 뜻이야.
• EUniformBufferBindingFlags::Shader = 셰이더 바인딩에 쓰인다고 표시해.
• TEXT(#StructTypeName) = FParameters 같은 타입 이름을 문자열로 바꿔 넣어.
• sizeof(StructTypeName) = 식판 전체 크기를 바이트로 잰 값이야.
• zzGetMembers() = 식판 안 칸 목록을 가져오는 함수야.

FShaderParametersMetadata는 실제 값이 아니야. 식판 전체 설계도야. 이름, 용도, 파일 위치, 전체 크기, 멤버 목록을 들고 있다.

왜 전체 크기가 필요할까? 나중에 void* InParametersData 하나가 들어왔을 때, 어디까지가 이 파라미터 구조체 데이터인지 알아야 하니까.

3. SHADER_PARAMETER 한 줄이 칸 설명서가 된다

이번엔 칸 하나를 보자. SHADER_PARAMETER(FVector2f, TexelSize) 같은 한 줄은 내부적으로 멤버와 FMember 설명서를 같이 만든다.

• alignas(TypeInfo::Alignment) = GPU가 기대하는 정렬에 맞춰 멤버를 놓아.

🔁 이제 다시 보자. SHADER_PARAMETER 한 줄은 두 일을 해. Parameters.TexelSize처럼 쓸 C++ 멤버를 만들고, 동시에 TexelSize의 이름·타입·오프셋을 FMember로 저장한다.

여기서 STRUCT_OFFSET이 중요해. 제출 단계에서는 구조체 시작 주소 하나만 들어오니까, 각 멤버 값을 읽으려면 "시작 주소 + 멤버 오프셋"이 필요해.

서버 패킷으로 치면 LoginPacket에서 AccountID가 몇 바이트째인지 자동으로 적어 두는 셈이야.

4. C++ 설명서와 셰이더 배식표를 맞춘다

이제 ShaderParameterStruct.cpp의 Bind가 나온다. 이 함수는 C++ 구조체 멤버를 순회하면서 셰이더에서 찾을 이름과 C++ 메모리 오프셋을 만든다.

ShaderParameterStruct.cpp:46

void Bind( const FShaderParametersMetadata& StructMetaData, const TCHAR* MemberPrefix, uint32 GeneralByteOffset) { const TArray<FShaderParametersMetadata::FMember>& StructMembers = StructMetaData.GetMembers(); for (const FShaderParametersMetadata::FMember& Member : StructMembers) { EUniformBufferBaseType BaseType = Member.GetBaseType(); FString CppName = FString::Printf(TEXT("%s::%s"), StructMetaData.GetStructTypeName(), Member.GetName()); // Ignore rasterizer binding slots entirely since this actually have nothing to do with a shader. if (BaseType == UBMT_RENDER_TARGET_BINDING_SLOTS) { if (!RenderTargetBindingSlotCppName.IsEmpty()) { UE_LOG(LogShaders, Fatal, TEXT("Render target binding slots collision: %s & %s"), *RenderTargetBindingSlotCppName, *CppName); } RenderTargetBindingSlotCppName = CppName; continue; } // Ignore RDG access types when binding to shaders. if (IsRDGResourceAccessType(BaseType)) { continue; } // Compute the shader member name to look for according to nesting. FString ShaderBindingName = FString::Printf(TEXT("%s%s"), MemberPrefix, Member.GetName()); uint16 ByteOffset = uint16(GeneralByteOffset + Member.GetOffset()); check(uint32(ByteOffset) == GeneralByteOffset + Member.GetOffset());
🔤 기호 사전 — 위 코드 인용
• Bind(...) = 식판 설명서와 셰이더 배식표를 맞추는 함수야.
• StructMetaData.GetMembers() = SHADER_PARAMETER들이 만든 칸 목록을 꺼내.
• BaseType = 이 칸의 큰 타입 분류야.
• CppName = FParameters::TexelSize 같은 C++ 쪽 이름이야.
• continue = 이 칸은 셰이더 바인딩 대상이 아니니 다음 칸으로 넘어가.
• ShaderBindingName = 셰이더 파라미터 맵에서 찾을 이름이야.
• ByteOffset = 실제 C++ 구조체 메모리 안에서 이 칸을 읽을 위치야.
🔁 이제 다시 보자. Bind는 멤버마다 이름표를 읽고, 셰이더에서 찾을 이름을 만들고, C++ 메모리 좌표를 계산한다. 급식판으로 말하면 "이 칸 이름이 뭐고, 식판 어디에 있고, 배식 대상이 맞나"를 확인하는 단계야.

렌더 타겟 바인딩 슬롯은 셰이더 변수 자체가 아니니까 건너뛴다. RDG access 타입도 직접 바인딩 값이 아니라 의존성 표시 쪽이라 건너뛴다. 중첩 구조체면 접두어를 붙여서 이름을 펼친다.

🌱 이 개념은 왜 생겼나 — FShaderParameterBindings
• 원래 구조: 매번 제출할 때 C++ 칸 이름을 보고 셰이더 배식표에서 다시 찾으면 될 것 같아.
• 그런데 문제: 프레임마다 패스가 수십 개씩 돌고, 셰이더마다 칸도 여러 개야. 배식 때마다 이름표를 전부 다시 뒤지면 밥 나가기 전에 줄이 막혀.
• 그래서 필요한 것: 한 번 찾은 "C++ 몇 바이트째 → 셰이더 몇 번 슬롯" 동선을 적어 둬야 해. 그 동선표가 FShaderParameterBindings야.

5. 이름을 찾으면 Bindings에 적는다

이제 셰이더 컴파일 결과에서 그 이름을 찾는다. ParametersMap->FindParameterAllocation(...)이 셰이더 배식표 조회야.

찾으면 타입별로 Bindings 목록에 넣는다. 숫자 값은 Parameters, 일반 유니폼 버퍼 참조는 ParameterReferences, RDG 유니폼 버퍼는 GraphUniformBuffers로 간다.

서버에서 패킷 디스크립터를 한 번 만들고, 실제 패킷 바이트는 매번 다르게 읽는 것과 비슷해.

🌱 이 개념은 왜 생겼나 — 유니폼 버퍼 바인딩
• 원래 구조: 숫자 값은 그냥 몇 바이트 복사하면 돼. 그러면 텍스처나 큰 공용 값 묶음도 똑같이 복사하면 될 것 같아.
• 그런데 문제: 4KB짜리 공용 상수 묶음을 패스마다 통째로 복사하고, 텍스처까지 값처럼 옮기려 하면 식판이 아니라 창고를 들고 뛰는 꼴이야.
• 그래서 필요한 것: 큰 묶음은 GPU가 볼 수 있는 버퍼 객체로 두고, 셰이더 슬롯에는 그 손잡이만 꽂아야 해. 그래서 유니폼 버퍼를 바인딩해.
🧱 먼저 알아야 할 것 — 물건과 손잡이는 다르다
• 물건 통째로 옮기기: 무거운 상자를 매번 들고 가면 힘도 들고 시간도 걸린다.
• 손잡이만 건네기: 상자가 이미 창고에 있으면 "저 상자 써"라고 번호표나 열쇠만 건네도 된다.
• 사용 표시: 빌려 쓴 물건은 목록에 체크해 둬야, 나중에 치우거나 다시 쓸 때 헷갈리지 않는다.
이게 잡히면 아래 설명이 얹힌다.

상수 값 흐름은 이래. InParametersData 시작 주소 → Parameter.ByteOffset → Parameter.ByteSize만큼 복사 → BufferIndex, BaseIndex 위치로 제출.

유니폼 버퍼 흐름은 이래. 구조체 안의 FRDGUniformBufferBinding이나 FUniformBufferBinding을 읽음 → 실제 RHI 유니폼 버퍼를 꺼냄 → GetParameterIndex(Parameter) 슬롯에 붙임.

RDG 유니폼 버퍼는 중간에 MarkResourceAsUsed()가 붙는다. 그래프가 "이 패스가 이 리소스를 썼다"는 사실을 알아야 하니까.

우리 서버·DirectX랑 빗대기

렌더링에서는 패킷 대신 셰이더 파라미터 구조체가 있어. 셰이더 컴파일 결과가 "필요한 필드 목록"이고, FShaderParameterBindings가 패킷 디스패치 테이블 같은 역할을 한다.

차이는 실행 장소야. 서버 패킷은 CPU 함수가 읽지만, 셰이더 파라미터는 GPU 셰이더가 읽을 수 있도록 RHI 슬롯에 꽂아야 해.

DirectX로 보면 SetPipelineState, SetGraphicsRoot..., DrawInstanced 사이에 들어가는 바인딩 작업과 닮았어. 언리얼은 그 플랫폼별 세부 작업을 RHI 뒤에 숨기고, 앞에서는 FParameters 구조체 하나로 다루게 해 준다.

이번 챕터에서 헷갈린 말

  1. SHADER_PARAMETER는 런타임 함수 호출이 아니라 컴파일 전 매크로야.
  2. FShaderParametersMetadata는 실제 값이 아니라 구조체 설명서야.
  3. FShaderParameterMap은 셰이더 컴파일 결과에서 온 이름·슬롯 표야.
  4. FShaderParameterBindings는 값 보관함이 아니라 읽는 방법과 제출 위치를 담은 지도야.
  5. ByteOffset은 C++ 구조체 안에서 멤버를 찾는 좌표야.
  6. 유니폼 버퍼는 숫자 복사가 아니라 RHI 유니폼 버퍼 객체를 슬롯에 붙이는 참조로 봐야 해.

Q1. Parameters.TexelSize = ...로 넣은 C++ 값이 어떻게 HLSL의 TexelSize까지 가나요?

답 보기
셋이 맞아야 해 — 이름, 크기, 위치. 셰이더는 TexelSize라는 이름을 요구하고, C++ 구조체는 어떤 바이트 오프셋에 그 값을 들고 있어. 큰 그림은 이래: SHADER_PARAMETER 매크로가 멤버 선언을 넘어 이름표·오프셋 메타데이터까지 만들고 → Bind가 그 메타데이터를 셰이더 컴파일 결과랑 맞춰서 동선표(Bindings)를 만들고 → 제출 때 SetShaderParameters가 그 동선표대로 C++ 메모리에서 값을 읽어 RHI 슬롯에 꽂아. 급식판으로 치면 칸 이름표 → 배식 동선표 → 배식원 순서야.

↳ 이거 안 맞으면 뭐가 망가지나요?

답 보기
엉뚱한 값이 엉뚱한 자리에 꽂혀. 우리 서버로 치면 SP_LOGIN이 AccountID를 원했는데 패킷 구조체 오프셋이 밀려서 월드 ID를 읽는 상황이야. 급식판으로는 칸 하나 밀려서 국 자리에 반찬이 들어가는 거고. 그래서 이름·크기·위치 약속을 자동으로 적어두고 컴파일 때 검사까지 하는 거야 — 눈감고 칸 찍으면 안 되니까.

Q2. FShaderParametersMetadata는 왜 필요한가요? C++이 FParameters 메모리를 다 아는 거 아닌가요?

답 보기
문제는 마지막 제출 때 void* 시작 주소 하나만 남는다는 거야. 그 시점엔 컴파일러가 알던 타입 정보가 사라져. TexelSize가 0바이트째인지 16바이트째인지 모르면 배식원이 눈감고 칸을 찍는 꼴이지. 그래서 식판 전체 크기랑 칸 목록을 적은 설계도가 따로 필요해. 값 자체가 아니라 설명서라서 FShaderParametersMetadata야. 전체 크기를 아는 이유도 "어디까지가 이 파라미터 구조체 데이터인지" 알아야 해서고.

↳ 그 오프셋은 어디서 오나요?

답 보기
SHADER_PARAMETER 한 줄이 두 일을 동시에 해. Parameters.TexelSize처럼 쓸 실제 C++ 멤버를 만들고, 동시에 그 멤버의 이름·타입·오프셋을 FMember 설명서로 저장해. 오프셋은 STRUCT_OFFSET으로 "구조체 시작점에서 이 칸까지 몇 바이트"를 재서 자동으로 박혀. 서버 패킷으로 치면 LoginPacket에서 AccountID가 몇 바이트째인지 자동으로 적어두는 셈이야.

Q3. Bind가 만드는 Bindings 지도에는 값이 들어가나요?

답 보기
아니, 값이 아니라 "읽는 방법"이 들어가. "구조체 메모리의 어느 오프셋을 읽어서 셰이더의 어느 버퍼 몇 번 슬롯에 넣을지"라는 동선표야. Bind가 C++ 멤버를 순회하면서 셰이더 컴파일 결과(배식표)에서 같은 이름을 찾아 그 동선을 기록해. 핵심은 이거야 — 같은 셰이더 타입은 이 지도를 한 번만 만들어두고, 매 프레임 다른 FParameters 인스턴스만 읽어서 제출해.

↳ 왜 매번 다시 안 찾고 지도를 미리 만들어두나요?

답 보기
프레임마다 패스가 수십 개씩 돌고 셰이더마다 칸도 여러 개니까, 배식 때마다 이름표를 전부 다시 뒤지면 밥 나가기 전에 줄이 막혀. 그래서 한 번 찾은 "C++ 몇 바이트째 → 셰이더 몇 번 슬롯" 동선을 FShaderParameterBindings에 적어두는 거야. 서버에서 패킷 디스크립터를 한 번 만들고 실제 패킷 바이트는 매번 다르게 읽는 것과 똑같은 최적화야.

Q4. 유니폼 버퍼는 왜 그냥 값처럼 복사 안 하고 참조로 꽂나요?

답 보기
숫자 값이야 몇 바이트 복사하면 되는데, 4KB짜리 공용 상수 묶음을 패스마다 통째로 복사하면 식판이 아니라 창고를 들고 뛰는 꼴이거든. 텍스처까지 값처럼 옮기려 하면 더 심하고. 그래서 큰 묶음은 GPU가 볼 수 있는 버퍼 객체로 두고, 셰이더 슬롯엔 그 손잡이만 꽂아. 상자를 통째로 나르지 말고 창고에 있는 상자의 번호표만 건네는 거지. 그래서 제출 코드가 상수는 SetShaderParameter로 복사하고, 유니폼 버퍼는 AddResourceParameter로 참조를 붙여 갈라놓은 거야.

↳ RDG 유니폼 버퍼에 MarkResourceAsUsed()가 붙는 건 왜예요?

답 보기
RDG(다음 장 주제)가 "이 패스가 이 리소스를 실제로 썼다"는 사실을 알아야 하거든. 그래야 그래프가 패스 간 의존성을 잡고, 리소스 수명이랑 배리어를 자동으로 챙겨. 안 쓰인 리소스는 정리하고, 쓰인 리소스는 순서를 맞춰야 하니까. 그래서 값을 꽂는 김에 "나 이거 썼어"를 그래프에 체크해두는 거야 — 빌려 쓴 물건을 목록에 표시해두는 거랑 같아.

머리 속 한 줄 요약

SHADER_PARAMETER는 C++ 식판의 칸 이름표를 만들고, ShaderParameterStruct.cpp는 그 이름표를 셰이더 컴파일 배식표와 맞춰 Bindings 지도를 만든 다음, SetShaderParameters가 그 지도대로 C++ 메모리의 값과 유니폼 버퍼를 RHI 셰이더 슬롯에 꽂는다.
