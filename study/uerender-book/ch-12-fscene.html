FScene — 렌더러가 보는 세계

언리얼 렌더링 · 12 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "UWorld가 아니라 렌더 스레드의 FScene이 무엇을 들고 있고, 프리미티브가 어떻게 들어오고 나가는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

서버를 짜봤으면 익숙한 그림이 하나 있어. DB에는 캐릭터 원본 데이터가 있고, 게임 로직에는 CChosunPlayer 같은 런타임 객체가 있고, 네트워크 송신 쪽에는 패킷으로 뽑기 좋은 별도 상태가 있어. 원본 하나를 모든 스레드가 그대로 만지지 않잖아.

DirectX도 비슷해. 월드에 "나무가 있다"는 말만으로는 GPU가 못 그려. GPU가 필요한 건 월드 행렬, 바운드, 머티리얼, 버퍼, 그릴 때 쓸 proxy 같은 렌더용 자료야. 게다가 UE는 게임 스레드와 렌더 스레드가 나뉘어 있어. 게임 스레드의 UPrimitiveComponent를 렌더 스레드가 마음대로 뒤지면 바로 레이스가 난다.

이게 없으면 뭐가 터질까? 프레임마다 UWorld를 처음부터 훑어서 보이는 것만 찾는다고 해보자. 액터가 10만 개 있으면 매 프레임 10만 개를 게임 객체 상태까지 건드려야 해. 한쪽에서는 액터가 삭제되는데 다른 쪽에서는 그 포인터로 그림자를 만들 수도 있어. 그리고 컬링, 그림자, Lumen, Nanite, BasePass가 전부 "내가 그릴 물건 목록 어디 있어?" 하고 같은 질문을 반복한다.

언리얼도 같은 문제를 만났고, 답이 FScene이야. FScene은 게임 월드 자체가 아니라 렌더러가 보는 세계 장부야. 그 장부 안에는 렌더용 프리미티브 목록, proxy, 변환 행렬, bounds, occlusion 정보, ray tracing 정보 같은 것들이 빽빽하게 들어간다.

그래서 지금 이걸 배운다. 앞 권에서 우리는 렌더 스레드, RHI, 셰이더, RDG까지 봤어. 이제 "무엇을 그릴까"의 첫 장이 필요해. 다음 장 PrimitiveSceneProxy는 게임 객체와 렌더 객체의 경계를 더 깊게 볼 거고 → scene-proxy, 그 다음 프러스텀 컬링은 FScene 안에 모인 프리미티브를 어떻게 걸러내는지 볼 거야 → frustum-culling.

0. 비유부터 — 공연장 무대감독의 장부

공연장을 떠올려봐. 밖에는 진짜 배우와 소품 창고가 있어. 배우는 밥도 먹고, 휴대폰도 보고, 의상도 갈아입어. 하지만 무대감독이 공연 중에 필요한 정보는 전부가 아니야.

무대감독 장부에는 이런 것만 적혀 있으면 돼.

  • 이 배우가 지금 무대 위에 올라와 있는지
  • 어느 위치에 서야 하는지
  • 조명을 받아야 하는지
  • 뒤쪽 그림자막에 영향을 주는지
  • 빨리 찾을 수 있게 몇 번 슬롯에 꽂혀 있는지
  • 퇴장하면 어떤 장부 줄을 지워야 하는지

UWorld는 공연장 전체야. 배우 대기실, 매표소, 창고, 휴게실까지 다 있어. FScene은 그중 무대감독이 들고 있는 공연용 장부야. 렌더러는 이 장부만 보고 "이번 프레임에 뭘 그릴지"를 판단한다.

프리미티브 등록은 배우가 무대에 올라오는 절차야. 퇴장은 배우가 무대에서 내려가고 장부에서 지워지는 절차야. 핵심은 하나야. 배우 본인(UPrimitiveComponent)이 렌더 스레드 장부에 직접 뛰어들지 않는다. 렌더용 대리인(FPrimitiveSceneProxy)과 장부 줄(FPrimitiveSceneInfo)을 만들어서 넘긴다.

이번 장은 이 장부가 어떤 칸을 갖는지, 배우가 어떻게 장부에 들어오는지, 퇴장할 때 어떤 칸들이 같이 지워지는지를 보는 장이야.

소스 위치 (아래 코드는 전부 이 클론의 실제 파일에서 그대로 뽑음)
• 장부 구조: Engine/Source/Runtime/Renderer/Private/ScenePrivate.h
• 등록/해제 구현: Engine/Source/Runtime/Renderer/Private/RendererScene.cpp
🌱 이 개념은 왜 생겼나 — FScene
• 원래 구조: 그냥 UWorld 하나를 렌더러도 같이 보면 될 것 같아. 무대감독이 공연장 전체 지도와 배우 대기실까지 다 뒤지는 식이야.
• 그런데 문제: 배우가 10만 명이면 매 프레임 대기실 문까지 다 열어봐야 해. 한쪽에서 배우를 내보내는 중인데 렌더 스레드가 같은 배우를 읽으면 장부가 찢어져.
• 그래서 필요한 것: 렌더러가 볼 것만 따로 적은 공연용 장부가 필요해. 그게 FScene이야. 월드가 아니라 "그릴 세계"만 압축해서 들고 있는 장부야.
🧱 먼저 알아야 할 것 — 물건의 위치와 '한 장으로 옮기는 표'
• 위치는 숫자로: 물건이 공간 어디에 있는지는 숫자 세 개(앞뒤·좌우·위아래)로 적어. 어느 쪽으로 돌았는지, 얼마나 큰지도 다 숫자로 적을 수 있어.
• 한 장으로 옮기는 표: 그 위치·기울기·크기를 한 장의 표에 모아 적어두면, 물건을 옮기거나 돌릴 때 이 표 하나만 바꾸면 통째로 따라 움직여. 그래서 물건마다 이런 표를 하나씩 들고 다녀. 수학에서 이 표를 행렬이라고 불러.
이게 잡히면 아래 '위치표(행렬)를 물건 수만큼 나란히 든 장부' 설명이 얹힌다.

1. FScene은 월드가 아니라 렌더러의 압축 장부야

먼저 FScene 안에 어떤 칸들이 있는지 봐야 해. 중요한 건 TArray가 하나가 아니라 여러 개라는 점이야. 프리미티브 하나가 들어오면 Primitives, PrimitiveTransforms, PrimitiveSceneProxies, PrimitiveBounds 같은 배열의 같은 index에 관련 정보가 나란히 들어간다.

이건 서버의 세션 배열을 떠올리면 쉽다. Sessions[i], PlayerIds[i], LastPacketTime[i], SendQueues[i]가 같은 i를 공유하면, 한 명을 찾았을 때 관련 데이터를 빠르게 쭉 뽑을 수 있지. FScene도 같은 식으로 렌더러가 자주 훑는 데이터를 packed array로 들고 있다.

ScenePrivate.h:2948

/** Packed array of primitives in the scene. */ TArray<FPrimitiveSceneInfo*> Primitives; /** Packed array of all transforms in the scene. */ TScenePrimitiveArray<FMatrix> PrimitiveTransforms; /** Packed array of primitive scene proxies in the scene. */ TArray<FPrimitiveSceneProxy*> PrimitiveSceneProxies; /** Packed array of primitive bounds. */ TScenePrimitiveArray<FPrimitiveBounds> PrimitiveBounds;
🔤 기호 사전 — FScene 장부 칸
• TArray<...> = 언리얼식 동적 배열이야. 필요하면 커지고, index로 바로 찾는다.
• FPrimitiveSceneInfo* = 프리미티브 장부 줄을 가리키는 포인터야. *는 실물이 아니라 주소표라는 뜻이야.
• FPrimitiveSceneProxy* = 게임 객체 대신 렌더 스레드가 보는 대리인 포인터야.
• TScenePrimitiveArray<FMatrix> = 프리미티브 수만큼 들고 있는 행렬 배열이야. FMatrix는 위치·회전·스케일을 담는 4x4 변환표로 보면 돼.
• PrimitiveBounds = 빠른 컬링을 위해 쓰는 바운드 장부야.
🔁 이제 다시 보자. Primitives는 장부 줄 → PrimitiveTransforms는 위치표 → PrimitiveSceneProxies는 렌더용 대리인 → PrimitiveBounds는 충돌박스처럼 빠른 범위 검사표야. 같은 index로 묶여 있으니 렌더러가 "5번 배우 어디 있지?" 하면 관련 칸을 줄줄이 꺼낼 수 있다.

여기서 초보가 자주 헷갈리는 포인트가 있어. FScene은 액터 트리나 컴포넌트 계층을 예쁘게 들고 있는 자료구조가 아니야. 렌더러가 빨리 훑기 좋은 압축된 배열 묶음이야.

왜 배열일까? 컬링은 수천, 수만 개 bounds를 훑어야 해. BasePass는 보이는 mesh를 계속 모아야 해. MeshDrawCommand 캐시는 프리미티브별 상태를 index로 잡아야 해 → mesh-draw-command. 이런 곳에서는 포인터 따라 복잡한 UObject 트리를 걷는 것보다 packed array가 훨씬 유리해.

공연장 비유로 다시 말하면, 무대감독은 배우 주민등록등본을 들고 있지 않아. 공연 중 필요한 "무대 위치표, 조명표, 퇴장표"만 얇은 장부에 따로 뽑아 들고 있는 거야.

🌱 이 개념은 왜 생겼나 — FPrimitiveSceneProxy / FPrimitiveSceneInfo
• 원래 구조: 배우 본인(UPrimitiveComponent)을 장부에 바로 꽂으면 쉬워 보여. 무대감독이 배우에게 직접 "어디 서?" 하고 묻는 거야.
• 그런데 문제: 배우는 게임플레이, 에디터, 수명 관리까지 들고 있어. 렌더 스레드가 그걸 매번 만지면 락이 걸리고, 삭제 중 포인터를 잡으면 바로 사고야.
• 그래서 필요한 것: 렌더용 대리 카드와 관리 줄을 따로 만든다. Proxy는 배우의 공연용 모습, SceneInfo는 장부에서 몇 번 칸인지 적는 운영표야.

2. 등록 입구 — 게임 객체에서 렌더용 proxy를 만든다

프리미티브 등록은 FScene::AddPrimitive에서 시작해. 하지만 AddPrimitive 자체는 얇고, 실제 일은 BatchAddPrimitivesInternal 안에서 한다.

핵심은 이 순서야.

  1. Primitive에서 FPrimitiveSceneProxy를 만든다.
  2. 그 proxy를 품는 FPrimitiveSceneInfo를 만든다.
  3. transform, bounds 같은 첫 상태를 모은다.
  4. 렌더 스레드 커맨드로 넘긴다.

먼저 proxy와 scene info가 만들어지는 토막을 보자. 여기가 배우 본인이 무대감독 장부에 바로 들어가는 대신, "공연용 대리인"과 "장부 줄"을 만드는 순간이야.

RendererScene.cpp:1402

FPrimitiveSceneProxy* PrimitiveSceneProxy = nullptr; if (Primitive->GetPrimitiveComponentInterface()) { checkf(!Primitive->GetSceneProxy(), TEXT("Primitive has already been added to the scene!")); PrimitiveSceneProxy = Primitive->GetPrimitiveComponentInterface()->CreateSceneProxy(); check(SceneData.SceneProxy == PrimitiveSceneProxy); // CreateSceneProxy has access to the shared SceneData and should set it properly } else { check(!Primitive->ShouldRecreateProxyOnUpdateTransform()); // recreating proxies when updating the transform requires a IPrimitiveComponentInterface PrimitiveSceneProxy = Primitive->GetSceneProxy(); } if(!PrimitiveSceneProxy) { // Primitives which don't have a proxy are irrelevant to the scene manager. continue; } // Create the primitive scene info. FPrimitiveSceneInfo* PrimitiveSceneInfo = new FPrimitiveSceneInfo(Primitive, this); PrimitiveSceneProxy->PrimitiveSceneInfo = PrimitiveSceneInfo;
🔤 기호 사전 — proxy와 scene info 만들기
• nullptr = 아직 아무것도 가리키지 않는 빈 포인터야.
• if (...) = 조건이 맞으면 안쪽을 실행하라는 뜻이야.
• Primitive->... = Primitive가 가리키는 객체의 기능을 부르는 화살표야.
• checkf(...) / check(...) = 개발 중 말이 안 되는 상태면 바로 터뜨리는 안전장치야.
• CreateSceneProxy() = 게임 컴포넌트에서 렌더 스레드용 대리인을 만드는 함수야.
• continue = 이번 반복은 건너뛰고 다음 프리미티브로 넘어가라는 뜻이야.
• new FPrimitiveSceneInfo(Primitive, this) = 새 장부 줄을 만들고, 이 FScene에 붙인다는 뜻이야.
🔁 이제 다시 보자. CreateSceneProxy()로 렌더용 대리인을 만들고 → proxy가 없으면 장부에 올릴 가치가 없으니 건너뛰고 → new FPrimitiveSceneInfo(Primitive, this)로 장부 줄을 만든다. 배우 본인이 아니라 배우의 무대용 카드가 만들어지는 장면이야.

여기서 FPrimitiveSceneProxy와 FPrimitiveSceneInfo를 구분해야 해.

FPrimitiveSceneProxy는 "렌더 스레드에서 볼 수 있는 컴포넌트의 그림자 사본"에 가까워. 월드 행렬, bounds, 머티리얼 relevance, shadow 여부 같은 렌더용 질의가 붙어 있어.

FPrimitiveSceneInfo는 그 proxy를 FScene 안에서 관리하기 위한 장부 줄이야. PackedIndex, PersistentIndex, static mesh 목록, light interaction, octree id 같은 렌더러 내부 관리 정보가 붙는다.

서버로 치면 proxy는 "클라에 보내기 좋은 캐릭터 스냅샷"이고, scene info는 "그 스냅샷이 어느 세션 배열 index에 있고 어떤 시스템에 등록됐는지 적은 관리 레코드"야.

3. 게임 스레드에서 바로 꽂지 않고 렌더 커맨드로 넘긴다

proxy와 scene info를 만들었다고 바로 Primitives.Add를 하지 않아. 여기가 중요해. FScene의 핵심 배열은 렌더 스레드 세계야. 그래서 등록도 렌더 커맨드로 넘겨 순서를 보장한다.

아래 토막에는 그 이유가 주석으로 박혀 있어. SetTransform과 CreateRenderThreadResources가 순서대로 실행되도록 render thread command를 enqueue 한다.

RendererScene.cpp:1459

if (!CreateCommands.IsEmpty()) { // Must enqueue RT commands to ensure SetTransform & CreateRenderThreadResources are executed in-order. ENQUEUE_RENDER_COMMAND(AddPrimitiveCommand)( [this, CreateCommands = MoveTemp(CreateCommands)](FRHICommandListBase& RHICmdList) { for (const FCreateCommand& Command : CreateCommands) { FScopeCycleCounter Context(Command.PrimitiveSceneProxy->GetStatId()); Command.PrimitiveSceneProxy->SetTransform(RHICmdList, Command.RenderMatrix, Command.WorldBounds, Command.LocalBounds, Command.AttachmentRootPosition); Command.PrimitiveSceneProxy->CreateRenderThreadResources(RHICmdList); AddPrimitiveSceneInfo_RenderThread(Command.PrimitiveSceneInfo, Command.PreviousTransform); } }); }
🔤 기호 사전 — 렌더 커맨드 넘기기
• IsEmpty() = 배열이 비었는지 물어보는 함수야.
• ENQUEUE_RENDER_COMMAND(...) = 렌더 스레드에서 실행할 일을 큐에 넣는 매크로야.
• [this, CreateCommands = MoveTemp(CreateCommands)] = 람다가 나중에 쓸 값을 잡아두는 캡처 목록이야.
• FRHICommandListBase& = 렌더 명령을 기록할 수 있는 명령 리스트를 참조로 받는다는 뜻이야.
• for (const FCreateCommand& Command : CreateCommands) = CreateCommands 안의 명령을 하나씩 꺼내 읽는 반복문이야.
• SetTransform(...) = 렌더용 proxy에 위치와 bounds를 세팅해.
• CreateRenderThreadResources(...) = 렌더 스레드에서 필요한 GPU/렌더 리소스를 준비해.
• AddPrimitiveSceneInfo_RenderThread(...) = 이제 이 장부 줄을 렌더 스레드 쪽 등록 흐름에 넘긴다.
🔁 이제 다시 보자. ENQUEUE_RENDER_COMMAND가 "무대감독한테 전달할 쪽지"를 만들고 → 렌더 스레드에서 SetTransform으로 위치를 세팅하고 → CreateRenderThreadResources로 무대 장비를 준비하고 → AddPrimitiveSceneInfo_RenderThread로 장부 등록을 예약한다. 게임 스레드가 장부를 직접 고치는 게 아니라 쪽지를 보내는 구조야.

이 구조는 앞에서 배운 렌더 스레드 분리와 정확히 이어져 → render-thread. 게임 스레드는 "배우가 생겼다"는 사실을 만들고, 렌더 스레드는 "그 배우를 장부에 어느 슬롯으로 꽂을지"를 결정한다.

AddPrimitiveSceneInfo_RenderThread 안에서는 바로 모든 배열을 다 채우는 게 아니라, PrimitiveUpdates.EnqueueAdd(...) 쪽으로 밀어 넣는다. 그리고 한 프레임의 적당한 지점에서 UpdateAllPrimitiveSceneInfos가 add/remove/update를 한꺼번에 처리한다.

공연장으로 치면, 배우가 대기실에서 "저 올라갑니다"라고 말하면, 무대감독이 즉시 조명표 전체를 뒤집는 게 아니야. 먼저 큐시트에 "등장 예정"으로 적고, 씬 전환 타이밍에 실제 무대 배치표를 한꺼번에 갱신한다.

🌱 이 개념은 왜 생겼나 — PackedIndex / PersistentIndex
• 원래 구조: 장부에 배우 정보를 한 줄씩 넣고, 그 줄 번호만 믿으면 될 것 같아.
• 그런데 문제: 중간 배우가 퇴장하면 빈칸이 생겨. 10만 칸을 훑는데 구멍이 많으면 느리고, 뒤 배우를 당겨오면 예전 줄 번호가 갑자기 다른 배우를 가리켜.
• 그래서 필요한 것: 빠르게 훑는 현재 칸 번호(PackedIndex)와 오래 추적하는 번호(PersistentIndex)를 나눠. 촘촘한 장부와 안정적인 손잡이를 둘 다 잡는 거야.

4. 진짜 등록 — packed array의 같은 index에 꽂힌다

이제 실제로 FScene의 packed array에 들어가는 장면을 보자. UpdateAllPrimitiveSceneInfos 안에서 추가될 프리미티브들을 모아 처리하다가, 아래처럼 여러 배열에 같은 순서로 Add한다.

이게 FScene 장부의 핵심이다. 한 프리미티브는 Primitives에만 들어가는 게 아니라, transform, proxy, bounds, flags, component id, static mesh update flag까지 함께 들어간다.

RendererScene.cpp:5708

for (int32 AddIndex = StartIndex; AddIndex < AddedLocalPrimitiveSceneInfos.Num(); AddIndex++) { FPrimitiveSceneInfo* PrimitiveSceneInfo = AddedLocalPrimitiveSceneInfos[AddIndex]; Primitives.Add(PrimitiveSceneInfo); const FMatrix LocalToWorld = PrimitiveSceneInfo->Proxy->GetLocalToWorld(); PrimitiveTransforms.Add(LocalToWorld); PrimitiveSceneProxies.Add(PrimitiveSceneInfo->Proxy); PrimitiveBounds.AddUninitialized(); PrimitiveFlagsCompact.AddUninitialized(); PrimitiveVisibilityIds.AddUninitialized(); PrimitiveOctreeIndex.Add(0); PrimitiveOcclusionFlags.AddUninitialized(); PrimitiveComponentIds.AddUninitialized(); PrimitiveOcclusionBounds.AddUninitialized(); #if WITH_EDITOR PrimitivesSelected.Add(PrimitiveSceneInfo->Proxy->WantsEditorEffects() || PrimitiveSceneInfo->Proxy->IsSelected()); #endif #if RHI_RAYTRACING PrimitiveRayTracingFlags.AddZeroed(); PrimitiveRayTracingDatas.AddZeroed(); PrimitiveRayTracingGroupIds.Add(Experimental::FHashElementId()); #endif PrimitivesNeedingStaticMeshUpdate.Add(false); PrimitivesNeedingUniformBufferUpdate.Add(true); const int32 SourceIndex = PrimitiveSceneProxies.Num() - 1; PrimitiveSceneInfo->PackedIndex = SourceIndex; check(PrimitiveSceneInfo->PersistentIndex.IsValid()); PersistentPrimitiveIdToIndexMap[PrimitiveSceneInfo->PersistentIndex.Index] = SourceIndex;
🔤 기호 사전 — packed array에 꽂기
• int32 = 32비트 정수야. 배열 index에 자주 쓴다.
• AddedLocalPrimitiveSceneInfos[AddIndex] = 추가할 목록에서 AddIndex번째 장부 줄을 꺼낸다.
• Primitives.Add(...) = FScene의 프리미티브 배열 끝에 하나를 붙인다.
• const FMatrix LocalToWorld = 바꾸지 않을 월드 변환 행렬 하나를 만든다는 뜻이야.
• AddUninitialized() = 일단 칸만 만들고 값은 나중에 채우겠다는 뜻이야.
• #if WITH_EDITOR = 에디터 빌드일 때만 이 줄들을 컴파일한다는 전처리 조건이야.
• #if RHI_RAYTRACING = ray tracing 지원 빌드일 때만 이 줄들을 넣는다.
• PackedIndex = 지금 packed array에서 몇 번 칸인지 적어두는 번호야.
• PersistentPrimitiveIdToIndexMap = 오래 유지되는 primitive id에서 현재 packed index로 찾아가는 지도야.
🔁 이제 다시 보자. Primitives.Add로 장부 줄을 꽂고 → PrimitiveTransforms.Add로 위치표를 꽂고 → PrimitiveSceneProxies.Add로 대리인을 꽂고 → 마지막에 PackedIndex와 PersistentPrimitiveIdToIndexMap을 맞춘다. 같은 배우의 정보가 여러 장부 칸에 같은 번호로 정렬되는 장면이야.

여기서 PackedIndex와 PersistentIndex를 구분해야 해. PackedIndex는 현재 배열에서 몇 번째냐야. 삭제와 정렬 때문에 바뀔 수 있어. packed array를 촘촘히 유지하려면 누군가 빠질 때 뒤쪽 애가 앞으로 당겨질 수 있으니까.

반대로 PersistentIndex는 그 프리미티브의 수명 동안 더 안정적으로 추적하기 위한 번호야. 다른 렌더 시스템이 "저 프리미티브를 시간에 걸쳐 계속 추적해야 한다"면 packed index만 믿기 어렵다. 그래서 PersistentPrimitiveIdToIndexMap이 둘 사이를 연결한다.

서버 비유로 말하면 이렇다. PackedIndex는 현재 접속자 배열의 index야. 중간 유저가 나가면 뒤쪽 유저를 당겨와서 index가 바뀔 수 있어. PersistentIndex는 그 세션을 계속 가리키기 위한 내부 핸들에 가깝다. 빠른 순회와 안정 추적을 둘 다 잡으려면 둘이 필요해.

5. 등록 뒤에 붙는 후속 시스템들

배우를 장부에 꽂았다고 끝이 아니야. 무대감독은 조명팀, 그림자팀, 특수효과팀에도 알려야 해. UE 렌더러도 마찬가지야.

추가된 프리미티브는 velocity, distance field, Lumen, ray tracing, runtime virtual texture, static mesh draw list 같은 여러 시스템에 차례로 연결된다. 이 장에서는 코드를 길게 다 펼치지 않고 이름만 잡자.

  • VelocityData.UpdateTransform — 이전/현재 transform을 알아야 모션 벡터를 만들 수 있어.
  • DistanceFieldSceneData.AddPrimitive — distance field 기반 효과에 넣는다.
  • LumenAddPrimitive — Lumen scene에 반영한다.
  • QueueAddToScene — octree, light interaction 같은 scene 연결로 넘어간다.
  • QueueAddStaticMeshes — static mesh draw command 준비 쪽으로 간다 → mesh-draw-command.

이걸 보면 FScene이 단순한 배열 하나가 아니라는 게 보이지. FScene은 여러 렌더링 서브시스템의 허브야. 프리미티브가 장부에 들어오면 그 사실을 그림자, GI, ray tracing, draw command 캐시에 전파한다.

공연장으로 치면 배우 이름을 출연자 명단에 넣는 것만으로는 공연이 안 돼. 조명 큐와 무대 동선도 같이 갱신돼야 한다.

6. 해제 입구 — 게임 객체와 proxy를 먼저 떼어낸다

이제 배우 퇴장을 보자. 삭제도 등록과 같은 원칙을 따른다. 게임 스레드에서 바로 Primitives.RemoveAt을 하지 않는다. 먼저 primitive가 들고 있던 scene proxy를 떼어내고, 렌더 스레드 커맨드로 "이 장부 줄 삭제해"를 보낸다.

아래 토막은 BatchRemovePrimitivesInternal의 렌더 커맨드 부분이야. RemovePrimitiveSceneInfo_RenderThread로 장부 삭제를 예약하고, proxy의 렌더 스레드 리소스도 파괴한다.

RendererScene.cpp:2040

if (!DestroyCommands.IsEmpty()) { // must run RT cmds in order here too ENQUEUE_RENDER_COMMAND(FRemovePrimitiveCommand)( [this, DestroyCommands = MoveTemp(DestroyCommands)](FRHICommandListBase&) { for (const FDetachCommand& Command : DestroyCommands) { RemovePrimitiveSceneInfo_RenderThread(Command.PrimitiveSceneInfo); Command.PrimitiveSceneProxy->DestroyRenderThreadResources(); if(Command.AttachmentCounter) { Command.AttachmentCounter->Decrement(); } } }); }
🔤 기호 사전 — 퇴장 커맨드
• DestroyCommands = 제거해야 할 프리미티브들의 삭제 쪽지 묶음이야.
• MoveTemp(DestroyCommands) = 이 배열의 소유권을 람다 안으로 옮긴다는 뜻이야.
• FRHICommandListBase& = 여기서는 이름 없이 받는다. 명령 리스트가 필요 없더라도 렌더 커맨드 형식상 받을 수 있어.
• RemovePrimitiveSceneInfo_RenderThread(...) = 렌더 스레드 장부에서 삭제할 대상으로 예약한다.
• DestroyRenderThreadResources() = proxy가 렌더 스레드에서 만든 리소스를 정리한다.
• AttachmentCounter = 이 primitive가 scene에 붙어 있는 동안 올라가는 카운터야.
• Decrement() = 카운터를 하나 내린다. 퇴장했으니 붙어 있는 수를 줄이는 거야.
🔁 이제 다시 보자. 삭제도 ENQUEUE_RENDER_COMMAND로 렌더 스레드에 쪽지를 보내고 → RemovePrimitiveSceneInfo_RenderThread로 장부 삭제를 예약하고 → DestroyRenderThreadResources로 무대 장비를 치우고 → AttachmentCounter를 내린다. 등록과 똑같이 퇴장도 무대감독 큐를 거쳐.

여기서 RemovePrimitiveSceneInfo_RenderThread는 내부적으로 delete를 바로 하지 않고 PrimitiveUpdates.EnqueueDelete(...) 쪽으로 넣는다. 왜 그럴까? 등록과 삭제가 같은 프레임에 같이 올 수 있고, 배열을 정렬된 packed 상태로 유지해야 하고, 다른 렌더 시스템도 "빠지는 애들"을 한꺼번에 알아야 하기 때문이야.

서버에서도 비슷해. 세션 하나가 나갔다고 IOCP 콜백 한가운데서 모든 월드 리스트와 길드 리스트와 파티 리스트를 바로 다 지우면 위험해. 보통 "삭제 예정"으로 표시하고, 게임 루프의 안전한 지점에서 관련 컨테이너를 한꺼번에 정리하지. FScene도 그 방식이야.

7. 진짜 해제 — packed array 끝으로 밀고 한꺼번에 자른다

packed array는 빈 구멍을 싫어해. 중간에 구멍이 나면 순회가 느려지고, index 기반 자료들이 꼬이기 쉬워. 그래서 UE는 삭제할 프리미티브들을 타입별로 모아, 뒤쪽으로 swap해 보낸 다음, 끝 부분을 RemoveAt으로 잘라낸다.

아래 토막이 그 핵심이야. 제거될 primitive의 PackedIndex를 무효화하고, 끝으로 몰린 구간을 여러 packed array에서 같은 박자로 잘라낸다.

RendererScene.cpp:5479

RemovedPrimitiveIndices[RemoveIndex] = RemovedLocalPrimitiveSceneInfos[RemoveIndex]->PackedIndex; PrimitiveSceneInfo->PackedIndex = INDEX_NONE; } //Remove all items from the location of StartIndex to the end of the arrays. int RemoveCount = RemovedLocalPrimitiveSceneInfos.Num() - StartIndex; int SourceIndex = Primitives.Num() - RemoveCount; Primitives.RemoveAt(SourceIndex, RemoveCount, EAllowShrinking::No); PrimitiveTransforms.Remove(RemoveCount, EAllowShrinking::No); PrimitiveSceneProxies.RemoveAt(SourceIndex, RemoveCount, EAllowShrinking::No);
🔤 기호 사전 — packed array에서 빼기
• INDEX_NONE = "유효한 index가 없다"는 언리얼의 대표 값이야.
• RemovedPrimitiveIndices[...] = 삭제 전에 예전 index를 백업해두는 배열이야.
• RemoveCount = 이번에 잘라낼 개수야.
• SourceIndex = 삭제할 묶음이 시작되는 배열 index야.
• RemoveAt(SourceIndex, RemoveCount, ...) = SourceIndex부터 RemoveCount개를 지운다.
• EAllowShrinking::No = 배열 메모리 용량은 굳이 줄이지 말라는 뜻이야. 자주 넣고 빼면 매번 메모리 재할당하는 게 더 비싸다.
🔁 이제 다시 보자. 먼저 삭제될 배우의 PackedIndex를 INDEX_NONE으로 무효화하고 → 끝으로 몰린 삭제 구간의 RemoveCount를 계산하고 → Primitives, PrimitiveTransforms, PrimitiveSceneProxies 같은 장부 칸을 같은 구간만큼 함께 자른다. 한 장부만 지우는 게 아니라 같은 번호로 묶인 모든 장부 칸을 같이 지우는 거야.

이게 왜 중요한지 감이 와야 해. Primitives[10]을 지웠는데 PrimitiveTransforms[10]이 그대로 있으면, 다음 프레임에 다른 배우가 남의 위치표를 들고 무대에 서는 꼴이 된다. 그래서 지울 때도 여러 배열이 같은 박자로 움직여야 해.

삭제 뒤에는 PrimitiveSceneInfo->RemoveFromScene, FreeGPUSceneInstances, DistanceFieldSceneData.RemovePrimitive, LumenRemovePrimitive 같은 후속 정리가 이어진다. 등록 때 조명팀과 그림자팀에 알려줬다면, 퇴장 때도 "이 배우 이제 없어"를 알려야 한다.

8. 콜/데이터 흐름 한눈에

전체 흐름을 무대 장부로 다시 그리면 이렇게야.

이 그림에서 제일 중요한 선은 두 개야.

첫째, UPrimitiveComponent에서 곧바로 draw call이 나오지 않는다. 렌더용 proxy와 scene info를 거쳐 FScene 장부에 들어간다.

둘째, 등록/삭제가 호출 즉시 packed array를 찌르지 않는다. 렌더 커맨드와 PrimitiveUpdates를 거쳐 안전한 지점에서 한꺼번에 처리된다.

이 두 선을 놓치면 이후 챕터가 다 헷갈려. 프러스텀 컬링이 왜 UWorld가 아니라 FScene 배열을 훑는지, MeshDrawCommand가 왜 FPrimitiveSceneInfo를 물고 있는지, Lumen과 distance field가 왜 primitive add/remove 이벤트에 붙는지 전부 여기서 갈라진다.

9. 우리 서버·DirectX 랑 비교

우리 조선 서버 쪽으로 비유하면 FScene은 월드 객체 전체가 아니라 게임 루프가 빨리 훑는 runtime index 테이블에 가깝다. DB 원본이나 스크립트 원본을 매 틱 뒤지지 않고, 현재 접속자, 현재 섹터, 현재 관심 목록을 별도 컨테이너로 잡아두는 것과 같다.

UPrimitiveComponent는 원본 게임 객체야. 여기에는 게임플레이 상태, 에디터 상태, UObject 수명, 컴포넌트 계층 같은 렌더링 외의 사정이 많아. 렌더 스레드가 이걸 직접 물고 가면 락 지옥이 생긴다.

FPrimitiveSceneProxy는 송신용 스냅샷에 가깝다. 게임 객체에서 렌더링에 필요한 정보만 뽑아 렌더 스레드가 읽기 좋은 모양으로 만든다. 다음 장이 바로 이 경계를 파는 장이야 → scene-proxy.

FPrimitiveSceneInfo는 서버의 세션 관리 레코드다. 몇 번 배열 칸에 있는지, 어떤 light와 연결됐는지, static mesh command가 준비됐는지, GPU scene instance가 있는지 같은 운영 정보를 들고 있다.

DirectX 관점에서는 FScene이 "그릴 수 있는 물건들의 CPU-side scene database"라고 보면 돼. DX 샘플에서는 보통 std::vector<MeshObject> 하나로 충분해. 하지만 UE에서는 그림자, Nanite, Lumen, ray tracing, occlusion, editor selection까지 같이 돌아가니까 하나의 vector가 아니라 여러 packed array와 보조 시스템으로 쪼개진다.

그리고 RDG와도 역할이 달라. RDG는 "이번 프레임 패스와 리소스를 어떻게 실행할까"의 주문 보드였지 → rdg. FScene은 "이번 프레임에 등장 가능한 배우들이 누구인가"의 장부야. RDG가 요리 순서표라면, FScene은 냉장고와 재료 목록이 아니라 오늘 무대에 올라갈 배우 명단과 위치표야.

10. 이 챕터에서 딱 이것만

  • FScene은 UWorld가 아니라 렌더러가 보는 세계 장부야.
  • 프리미티브는 UPrimitiveComponent 그대로가 아니라 FPrimitiveSceneProxy와 FPrimitiveSceneInfo로 들어온다.
  • 등록은 게임 스레드에서 proxy/info를 만들고, 렌더 커맨드로 넘긴 뒤, UpdateAllPrimitiveSceneInfos에서 packed array에 반영된다.
  • 해제도 바로 지우지 않고 delete 예약을 거쳐 packed array의 여러 칸을 같은 박자로 제거한다.
  • PackedIndex는 빠른 배열 순회용 현재 위치, PersistentIndex는 더 안정적인 추적용 번호로 보면 된다.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. FScene은 왜 있나요? 렌더러가 그냥 UWorld를 보면 안 되나요?

답 보기
UWorld는 공연장 전체야 — 배우 대기실, 매표소, 창고, 휴게실까지 다 있어. 렌더러가 매 프레임 이걸 처음부터 훑으면, 액터가 10만 개면 10만 개를 게임 객체 상태까지 건드려야 해. 게다가 한쪽에서 액터를 삭제하는데 렌더 스레드가 같은 포인터로 그림자를 만들면 레이스가 나. FScene은 게임 월드 자체가 아니라 렌더러가 보는 세계 장부, 즉 무대감독이 들고 다니는 공연용 장부야. 렌더용 프리미티브 목록, proxy, 변환 행렬, bounds, occlusion 정보만 압축해서 들고 있어.

↳ 그 장부가 왜 하필 여러 개의 packed array로 되어 있나요?

답 보기
컬링은 수만 개 bounds를 훑고, BasePass는 보이는 mesh를 계속 모으고, MeshDrawCommand 캐시는 프리미티브별 상태를 index로 잡아. 이런 데선 포인터 따라 복잡한 UObject 트리를 걷는 것보다 packed array가 훨씬 빨라. 그리고 Primitives[i], PrimitiveTransforms[i], PrimitiveSceneProxies[i]가 같은 index를 공유하니까, "5번 배우 어디 있지?" 하면 관련 칸을 줄줄이 뽑아. 서버의 Sessions[i], PlayerIds[i], SendQueues[i]가 같은 i를 쓰는 거랑 똑같아.

Q2. 게임 객체(UPrimitiveComponent)가 FScene 장부에 직접 안 들어가고 왜 대리인을 거치나요?

답 보기
배우 본인(UPrimitiveComponent)은 게임플레이, 에디터, UObject 수명 관리까지 다 들고 있어. 렌더 스레드가 이걸 매번 만지면 락이 걸리고, 삭제 중 포인터를 잡으면 바로 사고야. 그래서 렌더용 대리 카드 FPrimitiveSceneProxy랑 장부 줄 FPrimitiveSceneInfo를 따로 만들어서 넘겨. proxy는 "클라에 보내기 좋은 캐릭터 스냅샷", scene info는 "그 스냅샷이 어느 세션 배열 index에 있고 어떤 시스템에 등록됐는지 적은 관리 레코드"야.

↳ 등록할 때 게임 스레드에서 바로 Primitives.Add를 하면 안 되나요?

답 보기
안 돼. FScene의 핵심 배열은 렌더 스레드 세계라, 게임 스레드가 직접 찌르면 레이스가 나. 그래서 ENQUEUE_RENDER_COMMAND로 "무대감독한테 전달할 쪽지"를 만들어 넘기고, 렌더 스레드가 SetTransform·CreateRenderThreadResources를 순서대로 실행해. 서버에서 IOCP 콜백 한가운데서 월드 리스트를 바로 안 고치고, 게임 루프 안전한 지점에서 처리하는 거랑 같아.

↳ 쪽지를 보냈다고 바로 배열에 꽂히는 것도 아니라던데요?

답 보기
맞아, 한 번 더 미뤄. AddPrimitiveSceneInfo_RenderThread도 바로 배열을 채우는 게 아니라 PrimitiveUpdates.EnqueueAdd로 밀어넣고, 한 프레임의 적당한 지점에서 UpdateAllPrimitiveSceneInfos가 add/remove/update를 한꺼번에 처리해. 배우가 "저 올라갑니다" 하면 큐시트에 "등장 예정"으로 적어두고, 씬 전환 타이밍에 배치표를 통째로 갱신하는 거야. 등록과 삭제가 같은 프레임에 섞여도 packed array를 정렬된 채로 유지할 수 있어.

Q3. PackedIndex랑 PersistentIndex는 왜 둘 다 필요한가요?

답 보기
packed array는 구멍을 싫어해. 중간 배우가 퇴장하면 뒤쪽 배우를 앞으로 당겨와서 촘촘하게 유지하는데, 그러면 줄 번호가 바뀌어. PackedIndex는 "지금 이 배열에서 몇 번째냐"라 빠른 순회엔 좋지만 삭제/정렬로 계속 변해. 다른 렌더 시스템이 "저 프리미티브를 시간에 걸쳐 계속 추적"해야 하면 이걸 못 믿어. 그래서 수명 동안 안정적인 PersistentIndex를 따로 두고, PersistentPrimitiveIdToIndexMap이 둘을 연결해. 빠른 순회랑 안정 추적을 둘 다 잡는 거야.

↳ 서버 경험이랑 대응시키면요?

답 보기
PackedIndex는 현재 접속자 배열의 index야 — 중간 유저 나가면 뒤 유저를 당겨와서 index가 바뀌지. PersistentIndex는 그 세션을 계속 가리키는 내부 핸들에 가까워. 접속자 배열을 빠르게 순회하는 거랑, 특정 세션을 오래 안정적으로 추적하는 건 다른 요구라 둘이 필요한 거야.

Q4. 프리미티브 하나 등록하면 배열에 꽂고 끝인가요?

답 보기
아니야. FScene은 단순 배열이 아니라 여러 렌더 서브시스템의 허브야. 배우를 장부에 꽂으면 무대감독이 조명팀·그림자팀·특수효과팀에도 알려야 하듯, 추가된 프리미티브는 velocity(모션 벡터), distance field, Lumen, ray tracing, static mesh draw list에 차례로 연결돼. 삭제도 똑같아 — 등록 때 알려줬으면 퇴장 때도 "이 배우 이제 없어"를 그 시스템들에 다 알려야 해.

↳ 삭제할 때 Primitives[10]만 지우면 왜 안 되나요?

답 보기
Primitives[10]을 지웠는데 PrimitiveTransforms[10]이 그대로 남으면, 다음 프레임에 다른 배우가 남의 위치표를 들고 무대에 서는 꼴이 돼. 같은 index로 묶인 모든 장부 칸이 같은 박자로 움직여야 해. 그래서 UE는 삭제할 것들을 뒤쪽으로 swap해 모은 뒤, 끝 구간을 여러 배열에서 같은 개수만큼 한꺼번에 RemoveAt으로 잘라내. index 정합성을 지키려고 이렇게 하는 거야.

↳ FScene이랑 RDG는 역할이 어떻게 다른가요?

답 보기
층이 달라. RDG는 "이번 프레임 패스와 리소스를 어떻게 실행할까"의 요리 순서표(주문 보드)였어. FScene은 "이번 프레임에 등장 가능한 배우가 누구인가"의 명단과 위치표야. RDG가 조리 과정이라면, FScene은 오늘 무대에 올라갈 배우 명단인 셈이지. 컬링·그림자·mesh draw command가 전부 이 FScene 배열을 훑는 게 다음 챕터들로 이어져.

🎯 원리 한 줄 요약

FScene은 게임 월드를 렌더 스레드가 안전하고 빠르게 훑을 수 있도록 proxy와 scene info의 packed array로 다시 적어둔 무대감독 장부야.
