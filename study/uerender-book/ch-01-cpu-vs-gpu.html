두 세계 — CPU와 GPU는 왜 따로인가

언리얼 렌더링 · 01 / 42

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "CPU가 명령을 만들고 GPU가 대량으로 실행한다"는 큰 경계선이 잡힌다.
🧱 먼저 알아야 할 것 — 일을 나눠 맡기기
• 역할 나누기: 한 사람이 모든 일을 다 하는 대신, 계획을 세우는 사람과 손으로 처리하는 사람을 나누면 일이 빨라질 수 있다.
• 작업표: 매번 말로 시키는 대신 할 일을 종이에 적어 한 번에 넘기면, 시키는 사람도 덜 바쁘고 받는 사람도 바로 움직일 수 있다.
• 기다림: 맡긴 일을 바로 확인하려고 멈춰 서면, 일을 나눈 이득이 줄어든다.
이게 잡히면 아래 CPU/GPU 역할 분리 설명이 얹힌다.

왜 이걸 배워? — 문제의식부터

잠깐. 렌더링 코드를 읽기 전에 제일 먼저 박아야 할 감각이 있어. CPU와 GPU는 한 몸처럼 보이지만, 실제로는 서로 다른 두 작업장이야. DirectX를 조금 해봤다면 Device, CommandList, Resource, Fence 같은 이름을 봤을 거고, 서버를 해봤다면 IOCP 워커와 게임 로직 스레드를 나눠본 적이 있을 거야. 렌더링도 딱 그 문제에서 출발해.

이 구분을 안 잡고 들어가면 뭐가 터지냐? 픽셀 하나 그릴 때마다 CPU가 "여기 빨강, 저기 파랑" 하고 일일이 지시한다고 상상해봐. 1920x1080 화면이면 픽셀만 207만 개야. 60FPS면 1초에 1억 2400만 개가 넘고, 그 위에 그림자, 후처리, 반투명까지 얹으면 CPU가 말하다가 하루가 가. 반대로 GPU에게 아무 계획 없이 데이터를 막 던지면, GPU는 수천 손이 있어도 무엇을 먼저 칠해야 하는지 몰라서 멈칫해.

그래서 언리얼도 같은 문제를 만났고, 답은 역할 분리야. CPU는 장면을 보고 "무엇을 그릴지, 어떤 리소스를 만들지, 어떤 순서로 실행할지"를 정한다. GPU는 그 명령 묶음을 받아서 정점, 삼각형, 픽셀을 엄청나게 많이 동시에 처리한다. 이 둘 사이의 통역사가 RHI고, 이번 장의 핵심 소스가 DynamicRHI.cpp야.

왜 하필 지금 이걸 배우냐? 뒤에서 render-thread, rhi-commandlist, rdg, basepass-gbuffer를 읽게 되면 계속 "명령을 쌓는다", "GPU 리소스 상태를 바꾼다", "읽어오면 느리다"는 말이 나온다. 이 장에서 CPU/GPU 경계를 먼저 잡아야, 다음 장들의 코드가 "왜 이렇게 돌아가는지" 허공에 뜨지 않아.

0. 비유부터

초등학교 운동장에 거대한 벽화를 그린다고 해보자.

CPU는 담임 선생님이야. 선생님은 학생 한 명보다 손이 빠르진 않아. 대신 전체 그림을 알고 있어. "1반은 하늘, 2반은 나무, 3반은 사람, 이 줄부터 칠해" 하고 계획을 세워.

GPU는 운동장에 쫙 깔린 수천 명의 손이야. 한 명 한 명은 단순한 일을 해. "네 칸 색칠해", "이 점의 밝기 계산해", "이 삼각형 안쪽을 채워" 같은 일. 하지만 동시에 움직이면 무시무시하게 빠르다.

문제는 둘이 같은 책상에 앉아 있지 않다는 거야. 선생님이 운동장 전체에 대고 매초 수백만 번 소리칠 수는 없어. 그래서 선생님은 작업 지시서를 만든다. 어떤 반이 뭘 칠할지, 물감은 어디 있는지, 먼저 칠할 구역은 어디인지 적어서 넘겨.

언리얼에서 이 작업 지시서가 커맨드 리스트고, 그 지시서를 실제 그래픽 API 말로 바꾸는 경계가 RHI야. 오늘은 그 경계의 입구를 볼 거야.

🌱 이 개념은 왜 생겼나 — RHI(FDynamicRHI)
• 원래 구조: 선생님(CPU)이 작업반마다 말투를 따로 외워. D3D12 작업반이면 D3D12 말, Vulkan이면 Vulkan 말로 바로 지시하는 거야.
• 그런데 문제: PC, 콘솔, 모바일마다 작업반이 바뀌면 렌더러 코드 곳곳에 "이 작업반이면 이렇게"가 퍼져. 벽화 한 장 칠하려고 규칙표가 3~4벌로 갈라지는 셈이야.
• 그래서 필요한 것: 선생님이 보는 공통 계약서가 필요해. 실제 작업반은 뒤에서 바뀌어도, 앞에서는 같은 문으로 말하게 하는 경계가 RHI고 그 계약서가 FDynamicRHI야.

1. 먼저 경계선부터 — FDynamicRHI는 계약서다

CPU 쪽 C++ 코드는 GPU를 직접 붙잡고 일하지 않아. 언리얼은 먼저 "그래픽 하드웨어에게 말 거는 공통 계약서"를 세워. 그 계약서가 FDynamicRHI야.

🔤 기호 사전 — RHI 계약서 첫 장
• class FDynamicRHI = "RHI라는 큰 계약서를 여기서 정의한다"는 뜻이야.
• public: = 밖에서도 부를 수 있는 기능들이 이 아래에 온다는 표지야.
• virtual = 자식 클래스가 자기 방식으로 갈아끼울 수 있는 함수라는 뜻이야.
• = 0 = 몸통이 없는 순수가상 함수야. "반드시 자식이 구현해"라는 빈칸이야.
• TCHAR* = 언리얼 문자열 문자 포인터야. 이름 같은 글자 데이터를 가리켜.
• const = 이 함수가 객체 상태를 바꾸지 않는다는 약속이야.
🔁 이제 다시 보자. FDynamicRHI는 GPU 자체가 아니야.
Init(), Shutdown(), GetName()처럼 꼭 필요한 구멍을 뚫어둔 계약서야.
D3D12, Vulkan, Metal은 이 구멍을 자기 방식으로 채운다.
선생님이 "작업반은 반드시 출석 체크와 퇴근 정리를 해야 해"라고 규칙을 적어둔 셈이지.

여기서 중요한 건 = 0이야. 언리얼의 공통 렌더링 코드는 "D3D12냐 Vulkan이냐"를 매번 직접 묻지 않아. 그냥 FDynamicRHI 계약을 보고 말해. 실제 작업반이 D3D12인지 Vulkan인지는 시작할 때 정해진다.

2. 엔진 시작 때 — 어떤 작업반을 부를지 고른다

여기서 GDynamicRHI가 중요해. 언리얼 렌더링 코드 대부분은 결국 이 전역 포인터 뒤로 들어간다. CPU가 GPU에게 말할 때 직접 "D3D12 함수 호출!" 하고 외치지 않고, GDynamicRHI라는 문을 통과해.

3. Windows에서는 — D3D12냐 다른 RHI냐를 모듈로 고른다

PlatformCreateDynamicRHI()는 플랫폼마다 다르다. Windows 쪽 구현을 보면 "어떤 RHI 모듈을 로드할지"가 코드에 그대로 나와.

• bTryWithNewConfig = 다시 다른 설정으로 시도할지 나타내는 참/거짓 값이야.
• do { ... } = 최소 한 번은 실행하고 조건에 따라 반복하는 반복문이야.

• DynamicRHIModule && DynamicRHIModule->IsSupported(...) = 모듈이 있고, 이 PC에서 지원되면 통과한다는 조건이야.

이 코드는 왜 CPU/GPU 분리 이야기와 연결될까? CPU 쪽 언리얼 코드는 "D3D12 작업반", "Vulkan 작업반"을 런타임에 고를 수 있어야 해. GPU마다, OS마다, 기능 레벨마다 가능한 말투가 다르거든. 그래서 공통 계약서 FDynamicRHI가 있고, Windows에서는 그 계약서를 채울 모듈을 골라서 로드한다.

말하자면 선생님이 벽화 작업 전에 "오늘은 분필팀이야? 물감팀이야? 스프레이팀이야?" 확인하는 과정이야.

🌱 이 개념은 왜 생겼나 — 커맨드 리스트
• 원래 구조: 선생님이 운동장에 바로 소리쳐. "1번 칸 빨강, 2번 칸 파랑" 하고 말할 때마다 학생들이 즉시 움직이는 구조야.
• 그런데 문제: 207만 픽셀 화면에서 이런 말을 매번 즉시 보내면 선생님은 외치느라 묶이고, 학생들은 다음 말을 기다리느라 멈칫해. 서버에서 패킷 하나마다 락 잡고 기다리는 꼴이야.
• 그래서 필요한 것: 지시를 작업표에 쌓아두고 한 번에 넘기는 종이가 필요해. 그게 커맨드 리스트야. CPU는 적고, RHI/GPU는 자기 줄에서 읽어.

4. 명령은 말로 바로 실행되지 않는다 — 큐에 넣고 fence를 친다

이제 제일 중요한 병목 감각으로 가자. CPU와 GPU가 따로 일한다는 말은, CPU가 지시를 적는 시간과 GPU가 실행하는 시간이 서로 어긋날 수 있다는 뜻이야. 잘 짜면 둘이 동시에 달린다. 못 짜면 한쪽이 다른 쪽을 기다린다.

DynamicRHI.cpp 안에 이 경계가 아주 작게 보이는 코드가 있다. 텍스처 레퍼런스를 업데이트할 때, RHI 커맨드 리스트에 람다를 넣고 바로 fence를 친다.

TRefCountPtr<FRHITextureReference> Ref = TextureRef; RHICmdList.EnqueueLambda(TEXT("FDynamicRHI::RHIUpdateTextureReference"), [TextureRef = MoveTemp(Ref), InReferencedTexture](FRHICommandListBase&) { FRHITexture* ReferencedTexture = InReferencedTexture ? InReferencedTexture : FRHITextureReference::GetDefaultTexture(); TextureRef->SetReferencedTexture(ReferencedTexture); }); RHICmdList.RHIThreadFence(true); }
🔤 기호 사전 — enqueue와 fence
• FRHICommandListBase& RHICmdList = RHI 명령을 담는 리스트를 참조로 받는다는 뜻이야.
• FRHITextureReference* TextureRef = 텍스처 참조 객체를 가리키는 포인터야.
• TRefCountPtr = 참조 카운트로 수명을 붙잡는 스마트 포인터야.
• EnqueueLambda = "이 코드를 지금 바로 하지 말고 RHI 명령 큐에 넣어"라는 호출이야.
• [TextureRef = MoveTemp(Ref), InReferencedTexture] = 람다가 나중에 쓸 값을 붙잡아두는 캡처 목록이야.
• RHIThreadFence(true) = RHI 스레드와의 경계에 울타리를 세워서 여기까지 처리되길 기다리게 하는 호출이야.
🔁 이제 다시 보자. CPU는 TRefCountPtr로 객체 수명을 붙잡고,
EnqueueLambda로 "나중에 RHI 쪽에서 이 작업 해"라고 큐에 넣어.
람다 안에서는 실제 참조 텍스처를 고르고 SetReferencedTexture를 호출해.
마지막 RHIThreadFence(true)는 "이 지시서가 RHI 스레드 쪽으로 넘어가 처리될 때까지 선을 긋자"는 장치야.

이 토막이 정말 중요해. CPU가 모든 일을 즉시 실행하면 단순해 보이지만 느려져. 그래서 언리얼은 명령을 큐에 넣고, RHI 스레드와 GPU 쪽이 자기 순서대로 처리하게 만든다.

하지만 fence는 공짜가 아니야. fence는 선생님이 작업지시서를 넘긴 뒤, "잠깐, 이거 끝났는지 확인하고 다음 말 할게" 하고 멈추는 거야. 꼭 필요할 때는 써야 하지만, 매 픽셀, 매 리소스마다 걸면 병목이 된다.

서버로 치면 IOCP 워커에게 일을 던져놓고, 매 패킷마다 WaitForSingleObject로 완료를 기다리는 꼴이야. 큐를 둔 의미가 사라지지.

🌱 이 개념은 왜 생겼나 — readback
• 원래 구조: 선생님이 학생들에게 칠하라고 시킨 뒤, 필요하면 바로 "그 칸 무슨 색이야?" 하고 물어보면 될 것 같아.
• 그런데 문제: 학생들이 아직 칠하는 중이면 전부 흐름이 멈춰. 183번째 칸 색 하나 확인하려고 GPU가 하던 일을 끝낼 때까지 CPU가 기다릴 수 있어.
• 그래서 필요한 것: GPU 결과를 CPU로 되가져오는 특별한 길을 따로 조심해서 써야 해. 이 되읽기가 readback이고, 필요하면 staging/fence/한 프레임 지연으로 충격을 줄여.

5. 반대 방향이 더 비싸다 — GPU에서 CPU로 읽어오기

CPU가 GPU에게 지시를 보내는 것도 비용이 있지만, GPU가 계산한 결과를 CPU가 다시 읽어오는 건 더 조심해야 해. 왜냐하면 GPU가 아직 칠하는 중일 수 있거든. CPU가 "그 픽셀 값 지금 줘"라고 하면, GPU 작업이 끝날 때까지 기다려야 할 수 있어.

DynamicRHI.cpp에는 surface data를 읽어와 색 배열로 바꾸는 기본 fallback이 있다. 주석부터 이미 느리다고 말하고 있어.

DynamicRHI.cpp:468

// Default fallback; will not work for non-8-bit surfaces and it's extremely slow. void FDynamicRHI::RHIReadSurfaceData(FRHITexture* Texture, FIntRect Rect, TArray<FLinearColor>& OutData, FReadSurfaceDataFlags InFlags) { TArray<FColor> TempData; RHIReadSurfaceData(Texture, Rect, TempData, InFlags); OutData.SetNumUninitialized(TempData.Num()); for (int32 Index = 0; Index < TempData.Num(); ++Index) { OutData[Index] = TempData[Index].ReinterpretAsLinear(); } }
🔤 기호 사전 — surface readback
• RHIReadSurfaceData = 렌더 타깃이나 텍스처 표면 데이터를 CPU 배열로 읽어오는 함수야.
• FRHITexture* Texture = GPU 쪽 텍스처를 가리키는 손잡이야.
• TArray<FLinearColor>& OutData = 결과를 담아줄 배열 참조야.
• TArray<FColor> TempData = 먼저 8비트 색 배열로 임시 데이터를 받는 공간이야.
• for = 배열 원소를 하나씩 돌며 처리하는 반복문이야.

여기서 읽어야 할 건 "색 변환 루프" 자체보다 방향이야. GPU 쪽 표면을 CPU 배열 OutData로 가져오는 순간, 작업장 경계를 거꾸로 건너온다. 주석의 "extremely slow"가 그냥 겁주는 말이 아니야.

벽화 비유로 보면, 선생님이 멀리서 작업을 시켜놓고 "야, 지금 183번째 칸 정확히 무슨 색인지 종이에 적어서 가져와"라고 부르는 거야. 학생들이 다 칠하던 손을 멈추고, 그 칸을 확인하고, 종이를 다시 교무실로 가져와야 해.

그래서 렌더링 코드는 CPU readback을 최대한 피한다. 필요하다면 staging resource, GPU fence, 한 프레임 지연 같은 장치를 써. 나중에 오클루전 컬링이나 GPU 프로파일링에서 이 감각이 또 나온다. GPU 결과를 CPU가 즉시 요구하면 병목이 생긴다.

6. 그래서 통신이 병목이다

CPU와 GPU가 따로 있는 이유는 분명해. CPU는 복잡한 판단, 분기, 오브젝트 관리, 게임 로직에 강하다. GPU는 같은 종류의 계산을 엄청 많이 동시에 처리하는 데 강하다.

문제는 그 사이를 건너는 순간이야. 명령을 너무 자주 보내면 CPU가 지시서 작성에 묶인다. 리소스를 너무 자주 바꾸면 드라이버와 RHI가 상태 전환에 묶인다. GPU 결과를 CPU가 즉시 읽으면 GPU가 끝날 때까지 CPU가 멈춘다. fence를 남발하면 큐를 만들어놓고도 동기 실행처럼 굴러간다.

그래서 렌더링 성능의 첫 감각은 "GPU가 빠르다"가 아니야. 정확히는 GPU가 한 번 일감을 받으면 빠르다야. 일감 준비와 전달, 그리고 되가져오기가 비싸다.

벽화 비유로 다시 말하면 이래. 학생 수천 명은 색칠을 잘한다. 하지만 선생님이 매 칸마다 뛰어다니며 지시하면 망한다. 반대로 선생님이 큰 작업표를 잘 나눠주고, 학생들이 자기 구역을 오래 칠하게 만들면 빠르다.

언리얼이 커맨드 리스트, RHI 스레드, RDG, PSO, resource transition을 갖는 이유가 여기서 나온다. 전부 "작업표를 크게 만들고, 순서를 맞추고, 기다림을 줄이기" 위한 장치야.

콜/데이터 흐름 한눈에

게임 코드 / 렌더러 상위 코드 | | 장면 판단, 리소스 생성 요청, 그리기 순서 결정 v RHI 공통 인터페이스 | | GDynamicRHI, GRHICommandList, EnqueueLambda v 플랫폼 RHI 구현 | | FD3D12DynamicRHI / Vulkan / Metal v 그래픽 API와 드라이버 | | command queue, resource, barrier, fence v GPU | | 정점 수천 개, 픽셀 수백만 개를 병렬 처리 v 화면 / 렌더 타깃 되돌아오는 길: GPU 결과 -> readback/staging/fence -> CPU 배열 이 길은 특히 조심해야 해.

우리 서버·DirectX 랑 비교

게임 서버 관점으로 보면 CPU/GPU 분리는 IOCP 구조랑 꽤 닮았어.

서버에서렌더링에서
게임 로직 스레드가 무엇을 할지 결정한다CPU/렌더 스레드가 무엇을 그릴지 결정한다
IOCP 워커는 완료 통지를 받아 큐로 넘긴다RHI/드라이버/GPU는 커맨드 큐를 실행한다
매 패킷마다 락 잡고 기다리면 느리다매 명령마다 fence/readback 하면 느리다
큰 단위로 묶어 보내면 효율이 좋다draw/dispatch/resource update도 묶어야 효율이 좋다
공유 상태는 락이나 큐로 순서를 맞춘다GPU 리소스는 transition/barrier로 순서를 맞춘다

DirectX 관점으로 보면 더 직접적이야. FDynamicRHI는 언리얼의 공통 그래픽 API 문이고, FD3D12DynamicRHI는 D3D12 쪽 실제 구현이야. GRHICommandList는 D3D12 command list/queue 감각으로 보면 되고, RHIThreadFence는 fence로 CPU와 GPU/RHI 스레드 진행을 맞추는 장치로 보면 된다.

단, 정확히 1:1로 외우면 안 돼. 언리얼은 여러 RHI와 여러 스레드 모델을 감추기 위해 한 겹 더 싸고 있어. 이 장에서는 그 한 겹이 왜 필요한지만 잡으면 돼.

이 챕터에서 딱 이것만

  • CPU는 지시하는 뇌고, GPU는 수천 명이 동시에 칠하는 손이야.
  • 둘은 같은 함수 호출 세계에 있지 않고, RHI와 커맨드 리스트를 사이에 두고 말해.
  • GDynamicRHI는 런타임에 선택된 실제 RHI 구현으로 들어가는 전역 문이야.
  • 빠른 건 GPU 계산 자체고, 비싼 건 명령 전달, 상태 전환, fence, readback이야.
  • 다음부터 나오는 렌더 스레드, RHICommandList, RDG는 전부 이 기다림을 줄이려는 구조야.

Q1. CPU와 GPU를 왜 굳이 다른 세계로 나눠서 봐야 하나요?

답 보기
둘이 잘하는 게 완전히 다르거든. CPU는 복잡한 판단·분기·오브젝트 관리, 즉 "무엇을 어떤 순서로 그릴지 계획"에 강해. GPU는 같은 계산을 수백만 개 동시에 처리하는 "대량 색칠"에 강하고. 영화 촬영장으로 치면 CPU는 전체 그림을 아는 감독이고, GPU는 운동장에 깔린 수천 명의 손이야. 감독 한 명이 픽셀 207만 개를 직접 칠할 순 없고, 손 수천 개는 계획이 없으면 뭘 먼저 칠할지 몰라서 멈칫해. 그래서 계획하는 쪽과 실행하는 쪽을 나눈 거야.

↳ 그럼 "GPU가 빠르다"가 렌더링 성능의 핵심인가요?

답 보기
정확히는 "GPU가 한 번 일감을 받으면 빠르다"야. 색칠하는 손 자체는 무시무시하게 빨라. 비싼 건 일감을 준비해서 전달하는 것, 그리고 결과를 되가져오는 거야. 감독이 매 칸마다 운동장까지 뛰어다니며 지시하면 학생 수천 명이 있어도 망해. 큰 작업표를 잘 나눠주고 각자 자기 구역을 오래 칠하게 만들어야 빠른 거지.

Q2. RHI랑 FDynamicRHI는 왜 있는 건가요?

답 보기
CPU 쪽 렌더러가 GPU를 직접 붙잡고 일하지 않게 하려고. FDynamicRHI는 "그래픽 하드웨어에게 말 거는 공통 계약서"야. Init(), Shutdown(), GetName()처럼 꼭 필요한 구멍만 뚫어두고, D3D12·Vulkan·Metal이 그 구멍을 자기 방식으로 채워. 안 나누면 벽화 한 장 칠하는 코드가 "D3D12면 이렇게, Vulkan이면 저렇게"로 갈라져서 규칙표가 플랫폼 수만큼 늘어나. 위쪽 렌더러는 계약서만 보고 말하고, 실제 작업반이 누구인지는 시작할 때 정해지는 거야.

↳ 그럼 렌더러 코드가 "지금 D3D12야? Vulkan이야?"를 매번 물어보나요?

답 보기
아니, 그게 핵심이야. 엔진 시작 때 GDynamicRHI = PlatformCreateDynamicRHI() 한 줄로 실제 작업반이 전역 포인터에 한 번 꽂혀. 그다음부터 렌더링 코드 대부분은 그냥 이 GDynamicRHI라는 문만 통과해. "D3D12 함수 호출!"이라고 직접 외치지 않아. 매번 묻는 대신 시작할 때 한 번 정해두는 구조라 곳곳에 플랫폼 분기가 안 퍼지는 거지.

Q3. CPU가 GPU에게 명령을 왜 바로 실행 안 시키고 큐에 쌓나요?

답 보기
즉시 실행하면 단순해 보이지만 느려지거든. 207만 픽셀 화면에서 "여기 빨강, 저기 파랑"을 매번 즉시 보내면 CPU는 외치느라 묶이고 GPU는 다음 말을 기다리느라 멈칫해. 그래서 지시를 작업표(커맨드 리스트)에 쌓아두고 한 번에 넘겨. CPU는 적기만 하고, RHI/GPU는 자기 줄에서 자기 속도로 읽어. 그래야 둘이 동시에 달릴 수 있어.

↳ 그럼 fence는 왜 걸어요? 큐에 넣었으면 끝 아닌가요?

답 보기
가끔은 "여기까지 진짜 처리됐는지" 확인하고 다음으로 가야 할 때가 있어. fence가 그 울타리야. 근데 공짜가 아니야 — fence는 감독이 작업지시서 넘긴 뒤 "잠깐, 이거 끝났는지 확인하고 다음 말 할게" 하고 멈추는 거거든. 꼭 필요할 때만 써야 해. 매 픽셀·매 리소스마다 걸면 큐를 둔 의미가 사라져. 우리 서버로 치면 IOCP 워커에게 일 던져놓고 매 패킷마다 WaitForSingleObject로 완료를 기다리는 꼴이지.

↳ GPU 결과를 CPU로 읽어오는 건요? 그것도 그냥 비슷한 비용인가요?

답 보기
아니, 그 방향(readback)이 훨씬 더 비싸. GPU가 아직 칠하는 중일 수 있는데 CPU가 "그 픽셀 값 지금 줘"라고 하면, GPU 작업이 끝날 때까지 CPU가 멈춰 서서 기다려야 하거든. 소스 주석에도 대놓고 "extremely slow"라고 써 있어. 감독이 멀리서 시켜놓고 "183번째 칸 무슨 색인지 적어서 가져와"라고 부르면 학생들이 칠하던 손 멈추고 확인해서 다시 가져와야 하잖아. 그래서 렌더링 코드는 CPU readback을 최대한 피하고, 꼭 필요하면 staging·fence·한 프레임 지연으로 충격을 줄여.

Q4. 예전에 DirectX 직접 짜던 거랑 비교하면 이 계층이 뭐가 좋은 건가요?

답 보기
DirectX 손으로 짤 땐 ID3D12Device, CommandQueue, command list, resource state, fence를 전부 직접 맞췄잖아. 언리얼은 그 위에 한 겹을 더 씌워서 여러 RHI(D3D12·Vulkan·Metal)와 여러 스레드 모델을 감춘 거야. FDynamicRHI가 공통 그래픽 API 문이고 FD3D12DynamicRHI가 실제 D3D12 구현이야. 단, 1:1로 외우면 안 돼 — 이 장의 목표는 그 "한 겹"이 왜 필요한지만 잡는 거야.

↳ 이 장을 한 문장으로 요약하면 뭐라고 말하겠어요?

답 보기
CPU는 큰 작업표를 만들고 GPU는 그 작업표를 병렬로 칠한다. 렌더링 병목은 대개 칠하는 손 자체보다, 두 세계 사이를 너무 자주 건너게 만들 때 생긴다. 그래서 뒤에 나오는 렌더 스레드·RHICommandList·RDG가 전부 "이 건너감을 줄이려는 구조"라고 이해하면, 다음 장들이 허공에 안 떠.
