라이팅 — GBuffer에 빛을 얹다

언리얼 렌더링 · 22 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "디퍼드 라이팅이 왜 라이트마다 화면을 다시 훑고, 그래도 라이트가 많을 때 유리한지"가 잡힌다.

왜 이걸 배워? — 문제의식부터

DirectX를 조금 만져봤으면 이런 식으로 생각하기 쉬워.

"물체를 그릴 때 픽셀 셰이더에서 조명까지 계산하면 되잖아?"

맞아.

라이트가 하나면 그게 제일 직관적이야.

메시 하나 그리고, 재질 보고, 노멀 보고, 라이트 방향 넣고, 최종 색을 바로 찍으면 돼.

그런데 도시 밤 장면처럼 라이트가 300개쯤 있으면 문제가 터져.

포워드 방식으로 단순하게 가면 물체를 그릴 때마다 "이 물체에 닿는 라이트가 몇 개인지"를 계속 데리고 다녀야 해.

더 나쁘게 생각하면 라이트마다 메시를 다시 그리는 꼴이 돼.

메시 10만 개, 픽셀 수백만 개, 라이트 수백 개가 서로 곱해지면 GPU가 같은 재질 질문을 너무 많이 반복해.

서버로 치면 CM_ATTACK 하나 처리할 때마다 캐릭터 인벤토리, 장비, 버프, 길드 정보를 DB에서 매번 다시 조인하는 느낌이야.

언리얼도 같은 문제를 만났고, 답이 디퍼드 라이팅이야.

앞 장 basepass-gbuffer와 basepass-shader에서 이미 표면 정보를 GBuffer에 눕혀놨어.

이제 라이팅 패스는 메시를 다시 묻지 않고, 화면 픽셀의 GBuffer를 읽어서 "이 픽셀에 이 라이트 하나를 더하면 얼마냐"만 계산해.

왜 지금 배우냐면 순서가 딱 여기야.

prepass-depth에서 깊이를 깔고, basepass-gbuffer에서 재질 신분증을 깔고, basepass-shader에서 그 신분증을 실제로 포장하는 걸 봤어.

이제 그 신분증 위에 빛을 얹는 차례야.

다음 장 shadow-maps에서는 라이트가 "가려졌는가"를 따로 볼 거고, 이번 장은 그 직전의 본체 흐름을 잡는다.

0. 비유부터 — 투명 셀로판을 한 장씩 얹는 색칠놀이

이번 비유는 투명 셀로판이야.

밑그림 종이가 하나 있어.

그 종이에는 이미 물체의 모양, 방향, 재질, 거칠기 같은 메모가 적혀 있어.

이 밑그림이 GBuffer야.

그 위에 빨간 조명 셀로판을 한 장 얹어.

그러면 빨간 조명이 닿는 부분만 색이 더해져.

다음엔 파란 조명 셀로판을 얹어.

그다음엔 노란 조명 셀로판을 얹어.

셀로판을 얹을 때마다 밑그림을 다시 그리지는 않아.

밑그림에 적힌 "여긴 금속", "여긴 위쪽을 보는 노멀", "여긴 거친 표면" 같은 메모를 읽고 빛 색만 더해.

디퍼드 라이팅이 딱 이거야.

BasePass = 밑그림 만들기.

Lighting = 셀로판을 한 장씩 얹기.

방향광은 화면 전체를 덮는 큰 셀로판이야.

포인트 라이트나 스폿 라이트는 동그라미나 원뿔 모양 셀로판이야.

라이트가 닿지 않는 픽셀까지 칠하면 낭비니까, 언리얼은 구나 원뿔 같은 기하를 그려서 영향권 안쪽만 픽셀 셰이더가 돌게 해.

이제 실제 코드에서 이 셀로판 공장이 어떻게 돌아가는지 보자.

🌱 이 개념은 왜 생겼나 — 라이트 정렬(SortKey)
• 원래 구조: 셀로판 더미가 있으면 보이는 순서대로 하나씩 얹으면 될 것 같아. 빨간 조명, 파란 조명, 그림자 있는 조명도 그냥 온 순서대로.
• 그런데 문제: 조명 300개 중 어떤 건 그림자, 어떤 건 IES, 어떤 건 채널 조건이 있으면 매번 "너는 어느 길이야?"를 다시 물어봐. 주방에서 주문서마다 냄비를 바꾸는 꼴이라 손이 꼬여.
• 그래서 필요한 것: 먼저 특징을 꼬리표로 적고 비슷한 셀로판끼리 줄 세워야 해. 그 꼬리표가 SortKey야. 말 그대로 정렬할 때 쓰는 키야.

1. 라이트를 먼저 줄 세운다 — 어떤 셀로판부터 얹을까

렌더러는 바로 RenderLight를 부르지 않아.

먼저 씬에 있는 라이트들을 훑고, 이 뷰에서 정말 그릴 라이트인지 확인해.

그리고 그림자, 라이트 함수, IES, 라이팅 채널 같은 특징을 SortKey에 적어둬.

밑그림 위에 셀로판을 얹기 전에, 셀로판 더미를 분류하는 장면이야.

🔤 기호 사전 — 라이트 줄 세우기
• ShouldRenderLightViewIndependent() = 뷰와 상관없이 이 라이트가 기본적으로 그릴 만한지 묻는 검사야.
• && = "그리고"야. 앞 조건도 맞고 뒤 조건도 맞아야 안으로 들어가.
• for (int32 ViewIndex = 0; ... ) = 뷰가 여러 개면 하나씩 돌아보는 반복문이야.
• new(SortedLights) = 일반 new가 아니라 배열 안에 바로 자리를 잡아 객체를 만드는 언리얼식 배치 생성이야.
• SortKey.Fields = 정렬용 꼬리표 묶음이야. 라이트 타입, 그림자 여부, 라이트 함수 여부를 적어둬.
• bShadowed = b로 시작하니 참/거짓 값이야. 그림자를 그려야 하는 라이트인지 표시해.
• Proxy-> = 렌더 스레드용 라이트 대리자한테 물어보는 화살표야.

여기서 중요한 건 라이트를 그냥 리스트에 넣는 게 아니라는 점이야.

언리얼은 "이 셀로판은 그림자가 있나?", "특수 무늬가 있나?", "특정 라이팅 채널만 칠하나?"를 먼저 적어.

왜냐면 이 꼬리표가 뒤에서 경로를 나누거든.

어떤 라이트는 clustered로 묶어서 처리하고, 어떤 라이트는 표준 디퍼드로 하나씩 처리하고, 어떤 라이트는 그림자 때문에 따로 간다.

🔁 이제 다시 보자. ShouldRenderLightViewIndependent()로 라이트 자체를 거르고 → 각 View에서 ShouldRenderLight를 확인하고 → FSortedLightSceneInfo를 만들고 → SortKey.Fields에 특징을 적어. 이어 읽으면 "라이트를 바로 칠하지 않고, 먼저 셀로판 더미에 이름표를 붙인다"야.
🌱 이 개념은 왜 생겼나 — Clustered Deferred
• 원래 구조: 표준 디퍼드는 라이트마다 셀로판 한 장을 들고 화면을 다시 훑어. 라이트가 적으면 이게 단순하고 좋아.
• 그런데 문제: 작은 전등 500개가 도시 골목에 있으면, 픽셀 하나가 실제로 만나는 전등은 몇 개뿐인데도 라이트마다 계속 지나가. 안 닿는 셀로판까지 들고 왔다 갔다 하는 거야.
• 그래서 필요한 것: 화면을 작은 격자 상자들로 나누고, 각 상자에 들어오는 라이트만 꽂아두자. 이렇게 무리(cluster)로 묶어 꺼내 쓰는 디퍼드 길이 Clustered Deferred야.

2. 큰 갈림길 — 묶어서 칠할까, 하나씩 칠할까

이제 RenderLights로 들어와.

여기서 핵심 질문은 이거야.

"여러 작은 셀로판을 격자에 넣고 한 번에 처리할 수 있나?"

그게 가능하면 clustered deferred로 간다.

안 되면 표준 디퍼드, 즉 라이트마다 화면을 다시 훑는 길로 간다.

LightRendering.cpp:1572

// Currently they have a special path anyway in case of standard deferred so always skip the simple lights int32 StandardDeferredStart = SortedLightSet.SimpleLightsEnd; bool bRenderSimpleLightsStandardDeferred = SortedLightSet.SimpleLights.InstanceData.Num() > 0; UE_CLOG(ShouldUseClusteredDeferredShading(ViewFamily.GetShaderPlatform()) && !AreLightsInLightGrid(), LogRenderer, Warning, TEXT("Clustered deferred shading is enabled, but lights were not injected in grid, falling back to other methods (hint 'r.LightCulling.Quality' may cause this).")); // True if the clustered shading is enabled and the feature level is there, and that the light grid had lights injected. if (ShouldUseClusteredDeferredShading(ViewFamily.GetShaderPlatform()) && AreLightsInLightGrid()) { // Tell the trad. deferred that the clustered deferred capable lights are taken care of. // This includes the simple lights StandardDeferredStart = SortedLightSet.ClusteredSupportedEnd; // Tell the trad. deferred that the simple lights are spoken for. bRenderSimpleLightsStandardDeferred = false; AddClusteredDeferredShadingPass(GraphBuilder, SceneTextures, SortedLightSet, ShadowSceneRenderer.VirtualShadowMapMaskBits, ShadowSceneRenderer.VirtualShadowMapMaskBitsHairStrands, LightingChannelsTexture); } if (bRenderSimpleLightsStandardDeferred) { RenderSimpleLightsStandardDeferred(GraphBuilder, SceneTextures, SortedLightSet); }
🔤 기호 사전 — clustered와 standard 갈림길
• StandardDeferredStart = 표준 디퍼드로 하나씩 칠하기 시작할 라이트 인덱스야.
• SimpleLightsEnd = simple light 구간의 끝이야. 여기 전까지는 작은 라이트 묶음이라고 보면 돼.
• UE_CLOG = 조건이 참일 때만 로그를 찍는 매크로야.
• ShouldUseClusteredDeferredShading(...) = clustered deferred를 쓸 설정과 플랫폼 조건이 되는지 묻는 함수야.
• AreLightsInLightGrid() = 라이트들이 격자에 제대로 주입됐는지 확인해.
• AddClusteredDeferredShadingPass(...) = 가능한 라이트들을 한 번에 처리하는 clustered 패스를 추가해.
• RenderSimpleLightsStandardDeferred(...) = simple light를 표준 디퍼드 방식으로 따로 그리는 함수야.

여기서 clustered는 "작은 셀로판들을 격자 상자에 미리 꽂아두고, 픽셀마다 필요한 것만 꺼내는 방식"이야.

그게 되면 StandardDeferredStart를 앞으로 당겨서 이미 처리된 라이트는 표준 디퍼드가 다시 건드리지 않게 해.

반대로 격자에 못 넣었거나 특수 조건이 있으면 표준 디퍼드 길로 남겨둬.

디퍼드 라이팅을 공부할 때 헷갈리기 쉬운 점이 여기야.

"디퍼드 = 무조건 라이트마다 한 번"은 현대 UE에서는 절반만 맞아.

작고 조건이 단순한 라이트는 clustered/tiled로 묶을 수 있어.

하지만 그림자, 라이트 함수, 방향광, 특수 경로 같은 라이트는 여전히 표준 디퍼드의 셀로판 한 장씩 얹는 흐름을 탄다.

🌱 이 개념은 왜 생겼나 — 표준 디퍼드(RenderLight)
• 원래 구조: 물체를 그릴 때 재질도 보고 조명도 보고 최종 색까지 바로 찍으면 돼. 라이트 하나짜리 방이면 제일 이해하기 쉬워.
• 그런데 문제: 라이트가 100개면 같은 벽돌 재질 질문을 100번 다시 하게 돼. 서버에서 캐릭터 스탯은 같은데 공격 이벤트마다 DB 조인을 새로 하는 느낌이야.
• 그래서 필요한 것: 재질 질문은 BasePass에서 미리 끝내고, 나중에 라이트만 하나씩 더하자. 조명을 뒤로 미뤘다(deferred)는 뜻 그대로, 그 한 장씩 더하는 호출이 RenderLight야.

3. 표준 디퍼드의 본체 — 라이트마다 RenderLight

이제 진짜 오늘의 문장으로 내려가자.

표준 디퍼드 경로에서는 라이트 인덱스를 돌면서 RenderLight를 부른다.

이게 "라이트마다 화면을 한 번 더"의 C++ 형태야.

LightRendering.cpp:1632

for (int32 LightIndex = StandardDeferredStart; LightIndex < UnbatchedLightStart; LightIndex++) { // Render the light to the scene color buffer, using a 1x1 white texture as input const FSortedLightSceneInfo& SortedLightInfo = SortedLights[LightIndex]; const FLightSceneInfo* LightSceneInfo = SortedLightInfo.LightSceneInfo; RenderLight(GraphBuilder, Scene, View, SceneTextures, LightSceneInfo, nullptr, LightingChannelsTexture, false /*bRenderOverlap*/, false /*bCloudShadow*/, SortedLightInfo.bIsCompatibleWithLightFunctionAtlas); }
🔤 기호 사전 — 라이트마다 한 번
• for (int32 LightIndex = ... ) = 라이트 배열을 시작부터 끝 직전까지 하나씩 돈다는 뜻이야.
• StandardDeferredStart = 표준 디퍼드가 맡을 첫 라이트야.
• UnbatchedLightStart = 묶어서 처리하지 않는 특수 라이트 구간이 시작되는 지점이야.
• const FSortedLightSceneInfo& = 정렬된 라이트 정보를 복사하지 않고 별명으로 읽겠다는 뜻이야.
• FLightSceneInfo* = 렌더러가 쓰는 실제 라이트 정보 포인터야.
• nullptr = 여기서는 별도 shadow mask 텍스처가 없다는 빈칸 표시야.
• false /*bCloudShadow*/ = 값은 false인데, 주석으로 어떤 인자인지 붙여놓은 거야.
🔁 이제 다시 보자. LightIndex를 하나씩 올리면서 → SortedLights[LightIndex]에서 라이트 정보를 꺼내고 → 그 안의 LightSceneInfo를 뽑고 → RenderLight(...)를 호출해. 이어 읽으면 "표준 디퍼드는 셀로판 한 장마다 RenderLight 한 번"이야.

여기서 메시를 다시 그리는 코드는 없어.

SceneTextures가 같이 넘어가고 있지?

그 안에 SceneColor, Depth, GBuffer uniform buffer가 들어 있어.

즉 라이트 패스는 "메시 목록"이 아니라 "이미 깔린 화면 텍스처들"을 들고 들어간다.

이게 디퍼드가 라이트 많을 때 버티는 핵심이야.

재질 셰이더를 라이트마다 다시 돌리는 게 아니라, GBuffer를 재사용한다.

4. 픽셀 셰이더에게 식판을 넘긴다

RenderLight 안쪽에서는 픽셀 셰이더 파라미터를 만든다.

여기서 SceneTextures, shadow mask, lighting channel, deferred light uniform이 한데 묶여.

셀로판 한 장을 얹기 위해 필요한 도구 꾸러미를 싸는 장면이야.

• Out.SceneTextures = 픽셀 셰이더가 읽을 장면 텍스처 묶음이야. GBuffer도 이 길로 들어가.
• SceneTexturesUniformBuffer = 여러 텍스처와 샘플러를 한 묶음으로 셰이더에 넘기는 상자야.
• ? ... : ... = 조건이 맞으면 앞 값, 아니면 뒤 값을 고르는 짧은 if야.
• WhiteDummy = 진짜 텍스처가 없을 때 대신 쓰는 흰색 기본 텍스처야.
• TStaticSamplerState<...>::GetRHI() = GPU 샘플러 상태를 가져오는 코드야. 점 샘플링, 클램프 같은 규칙을 담아.
• Out.DeferredLight = 지금 칠할 라이트 하나의 색, 방향, 반경 같은 정보를 담은 uniform buffer야.
• *LightSceneInfo = 포인터가 가리키는 실제 라이트 정보를 꺼내 함수에 넘긴다는 뜻이야.

이 토막을 보면 디퍼드 라이팅의 입력물이 보인다.

하나는 SceneTextures야.

이건 밑그림 종이야.

다른 하나는 DeferredLight야.

이건 지금 얹을 셀로판 한 장의 색과 모양이야.

그리고 LightAttenuationTexture는 그림자나 감쇠 마스크 쪽 입력이야.

아직 shadow-maps를 안 봤으니 여기서는 "빛이 얼마나 막혔는지 적힌 마스크" 정도로만 잡자.

🌱 이 개념은 왜 생겼나 — 라이트 기하(구/원뿔)
• 원래 구조: 라이트 하나를 칠하려면 화면 전체에 큰 셀로판을 덮으면 돼. 방향광처럼 태양이면 이게 맞아.
• 그런데 문제: 방 구석 작은 전구 하나 때문에 4K 화면 전체 픽셀을 다 깨우면 낭비야. 전구가 닿지도 않는 하늘, 바닥 끝, 벽 뒤까지 계산하게 돼.
• 그래서 필요한 것: 라이트가 닿는 모양만 그려서 그 안의 픽셀만 깨우자. 포인트는 구, 스폿은 원뿔이라서 라이트 기하를 셀로판 모양처럼 쓰는 거야.
🧱 먼저 알아야 할 것 — 불빛은 닿는 데까지만, 멀수록 약해진다
• 불빛의 범위: 방에서 손전등을 켜면 앞쪽만 밝고 방 전체가 다 밝아지진 않아. 작은 전구일수록 닿는 거리가 짧다.
• 멀수록 약함: 촛불 가까이는 환하고, 멀어질수록 어두워지다가 결국 안 닿는다.
• 해는 다르다: 햇빛은 워낙 멀고 세서 방 안 어디든 거의 똑같이 닿아. 방향만 있고 "여기까지만"이 없다.
이게 잡히면 아래 "닿는 모양(구/원뿔)만 칠한다" 설명이 얹힌다.

5. 방향광은 전체 화면, 로컬 라이트는 구나 원뿔

이제 InternalRenderLight가 실제 그리기 명령을 만든다.

방향광은 태양처럼 화면 전체에 영향을 준다고 봐.

그래서 큰 셀로판 한 장을 화면 전체에 덮는다.

반대로 포인트, 스폿, 렉트 라이트는 영향권이 있으니 구나 원뿔 모양을 그려.

그 기하 안에 들어온 픽셀만 픽셀 셰이더가 돈다.

🔁 이제 다시 보자. 방향광이면 DrawRectangle로 화면 전체 셀로판을 덮고 → 로컬 라이트면 radial 셰이더 변형을 고르고 → 깊이 범위를 줄이고 → 포인트/렉트는 DrawSphere, 스폿은 DrawCone을 그려. 이어 읽으면 "라이트마다 화면을 훑되, 로컬 라이트는 영향권 모양으로 훑는다"야.

여기서 "화면을 한 번 더"라는 말이 더 정확해져.

방향광은 정말 화면 전체야.

하지만 포인트 라이트는 화면 전체가 아니라 구가 덮는 픽셀만이야.

스폿 라이트는 원뿔이 덮는 픽셀만이야.

그래서 디퍼드 라이팅은 라이트 수가 많아도 무조건 전체화면 * 라이트수로만 터지지 않아.

작은 라이트는 작은 셀로판만 얹는다.

그리고 더 많은 작은 라이트는 clustered path가 먼저 먹을 수도 있어.

🧱 먼저 알아야 할 것 — 같은 칸에 계속 더하면 쌓인다
• 더하기 누적: 저금통에 동전을 넣을 때마다 금액이 쌓이듯, 한 자리에 숫자를 여러 번 더하면 점점 커진다.
• 하나씩 차례로: 한 번에 다 넣지 않고 하나 더하고 또 하나 더하기를 반복해도, 결과는 지금까지 쌓인 총합이다.
• 밝기도 숫자: 화면 한 점의 밝기도 숫자여서, 빛을 하나 더할 때마다 그 점이 그만큼 더 밝아진다.
이게 잡히면 아래 "빛을 한 장씩 더해 쌓는다" 설명이 얹힌다.

6. 픽셀 셰이더 — GBuffer를 읽고 빛을 더한다

마지막은 셰이더야.

여기서 진짜로 "GBuffer에 빛을 얹는다"가 나온다.

픽셀 위치에서 GetScreenSpaceData로 GBuffer를 읽고, 그 픽셀이 조명을 받을 수 있으면 라이트 데이터를 만들고, 감쇠와 그림자까지 반영해서 GetDynamicLighting을 부른다.

결과는 OutColor += Radiance.

더하기다.

셀로판을 여러 장 얹는다는 비유가 여기서 정확히 맞아.

🔁 이제 다시 보자. GetScreenSpaceData로 밑그림 메모를 읽고 → ShadingModelID > 0인 픽셀만 통과시키고 → LightData와 LightAttenuation을 만들고 → GetDynamicLighting으로 이번 라이트 색을 구하고 → OutColor += Radiance로 누적해. 아까는 HLSL 외계어였는데 이제 "셀로판 한 장의 색을 SceneColor에 더한다"로 읽히지?

이제 전체 그림이 잡혀.

BasePass가 재질 정보를 눕혔으니, 라이팅 패스는 물체를 다시 묻지 않는다.

픽셀마다 GBuffer를 읽는다.

라이트 하나의 정보를 읽는다.

둘을 섞어 나온 빛을 SceneColor에 더한다.

그리고 다음 라이트가 또 들어와서 같은 일을 한다.

이게 디퍼드 라이팅의 핵심 반복문이야.

우리 서버·DirectX 랑 비교

서버 쪽으로 치면 GBuffer는 "캐릭터 스냅샷 캐시"야.

매 패킷마다 DB를 다시 긁지 않고, 이미 메모리에 펴둔 캐릭터 상태를 읽는 거지.

라이팅 패스는 SP_* 처리처럼 그 스냅샷에 이벤트 하나를 얹는 느낌이야.

라이트 하나가 들어오면 "이 픽셀 상태에 이 라이트 효과를 더하면 얼마냐"만 계산해.

DirectX 경험으로 치면 더 직접적이야.

포워드는 메시를 그리는 픽셀 셰이더 안에서 라이트까지 끝낸다.

디퍼드는 MRT에 재질 정보를 먼저 쓰고, 나중에 fullscreen quad나 sphere/cone draw로 SceneColor에 additive blending을 한다.

이때 중요한 차이는 셰이더 입력이야.

포워드 픽셀 셰이더의 입력은 보통 정점에서 보간된 재질/노멀/UV야.

디퍼드 라이팅 픽셀 셰이더의 입력은 화면 좌표와 GBuffer야.

그래서 라이트가 많을수록 이득이 난다.

재질을 다시 평가하지 않으니까.

다만 공짜는 아니야.

GBuffer를 저장하는 메모리 대역폭이 든다.

반투명은 GBuffer에 잘 눕히기 어려워서 별도 경로가 필요하다. → translucency

라이트가 화면 전체를 많이 덮으면 라이트 패스 비용도 커진다.

그러니까 디퍼드는 "항상 빠름"이 아니라, 복잡한 재질과 많은 라이트를 분리해서 반복 질문을 줄이는 구조야.

이 챕터에서 딱 이것만

  1. BasePass는 최종 조명을 끝내지 않고 GBuffer 신분증을 먼저 만든다.
  1. RenderLights는 라이트를 clustered/simple/standard deferred 경로로 나눈다.
  1. 표준 디퍼드 경로는 for LightIndex로 라이트마다 RenderLight를 호출한다.
  1. 방향광은 DrawRectangle로 화면 전체를 훑고, 포인트/스폿/렉트는 DrawSphere나 DrawCone으로 영향권만 훑는다.
  1. 픽셀 셰이더는 GetScreenSpaceData로 GBuffer를 읽고 OutColor += Radiance로 이번 라이트를 SceneColor에 더한다.

🧠 면접 리뷰 — 진짜 이해했는지 확인

면접관이 이 챕터를 파고든다고 생각해봐. 코드를 외웠나가 아니라, 이게 왜 필요하고 큰 그림에서 어떻게 도는지를 네 말로 재구성할 수 있으면 통과야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

공짜 아니야. GBuffer를 저장하고 읽는 메모리 대역폭 비용이 들어. 반투명은 픽셀 하나에 여러 표면이 겹쳐서 GBuffer 한 칸에 눕히기 어려우니 별도 경로가 필요하고(→ translucency). 라이트가 화면 전체를 크게 덮으면 라이트 패스 비용도 커져. 그러니까 디퍼드는 "항상 빠름"이 아니라 복잡한 재질과 많은 라이트를 분리해서 반복 질문을 줄이는 구조야.

↳ 라이트를 바로 RenderLight 부르지 않고 먼저 줄 세우는(SortKey) 이유는요?

답 보기
특징이 제각각인 셀로판을 온 순서대로 얹으면 매번 "너는 어느 길이야?"를 다시 물어봐야 하거든 — 그림자 있는 라이트, IES 무늬 라이트, 특정 채널만 칠하는 라이트가 섞여 있으니까. 그래서 SortKey에 그림자 여부·라이트 타입·채널 같은 꼬리표를 먼저 적어서 비슷한 것끼리 줄 세우고 경로를 가른다(clustered로 묶을지, 표준 디퍼드로 하나씩 갈지). 주방에서 주문서마다 냄비를 바꾸지 않고 같은 조리법끼리 모아 처리하는 거랑 같아.

Q2. "디퍼드 = 라이트마다 화면을 무조건 한 번 더 훑는다"가 맞나요?

답 보기
현대 UE에서는 절반만 맞아. 그림자·라이트 함수·방향광 같은 라이트는 여전히 표준 디퍼드로 셀로판 한 장씩(RenderLight) 얹어. 하지만 작고 조건 단순한 라이트가 수백 개면, 화면을 작은 격자 상자로 나누고 각 상자에 들어오는 라이트만 꽂아두는 Clustered Deferred로 묶어서 한 번에 처리해. 골목 전등 500개를 라이트마다 화면 훑기로 하면 낭비니까, 픽셀이 실제 만나는 몇 개만 격자에서 꺼내 쓰는 거야.

↳ 그 갈림길(clustered로 갈지 표준으로 갈지)은 뭘 보고 정해요?

답 보기
RenderLights에 들어오기 전에 라이트를 먼저 줄 세워(SortKey) — 그림자 있나, IES 무늬 있나, 특정 라이팅 채널만 칠하나 같은 특징을 꼬리표로 적어. 그리고 clustered 설정·플랫폼 조건이 되고 라이트가 격자에 제대로 주입됐으면 clustered 패스가 먼저 그 라이트들을 먹고, StandardDeferredStart를 앞으로 당겨서 표준 디퍼드가 이미 처리된 라이트는 다시 안 건드리게 해. 격자에 못 넣거나 특수 조건이면 표준 디퍼드로 남겨.

Q3. 로컬 라이트(포인트·스폿) 하나 칠하려고 화면 전체 픽셀을 다 깨우나요?

답 보기
아니야, 그러면 낭비야. 방 구석 전구 하나 때문에 4K 화면 전체를 깨우면 안 닿는 하늘·벽 뒤까지 계산하잖아. 그래서 방향광(태양)만 화면 전체 사각형(DrawRectangle)으로 덮고, 포인트/렉트는 구(DrawSphere), 스폿은 원뿔(DrawCone) 같은 영향권 기하를 그려서 그 안에 든 픽셀만 픽셀 셰이더가 돌게 해. 여기에 depth bounds test까지 걸어서 깊이 범위 밖 픽셀도 덜 건드려.

↳ 그럼 라이트가 많아지면 결국 "화면크기 × 라이트수"로 터지는 거 아닌가요?

답 보기
그래서 안 그런 거야. 작은 라이트는 작은 셀로판(구·원뿔)만 얹으니 화면 전체가 아니라 영향권 픽셀만 든다. 게다가 작은 라이트가 많으면 clustered path가 먼저 격자로 묶어서 먹어버려. 그래서 디퍼드는 라이트 수가 늘어도 무조건 전체화면 × 라이트수로 폭발하지 않는 거지.

Q4. 픽셀 셰이더 안에서 실제로 "빛을 얹는다"는 게 무슨 연산인가요?

답 보기
핵심은 딱 OutColor += Radiance, 즉 더하기(누적)야. 픽셀 위치에서 GetScreenSpaceData로 GBuffer 신분증을 읽고 → ShadingModelID > 0인 조명 받을 픽셀만 통과시키고 → 라이트 데이터와 그림자·감쇠 마스크를 만들어 → GetDynamicLighting으로 이번 라이트 색을 구해 → SceneColor에 더해. 셀로판을 한 장씩 얹으면 밝기가 쌓이는 그 비유가 여기서 정확히 맞아. 다음 라이트도 들어와서 같은 일을 반복하는 게 디퍼드의 핵심 반복문이야.

↳ 그 픽셀 셰이더의 입력이 포워드랑 뭐가 다른가요?

답 보기
포워드 픽셀 셰이더 입력은 보통 정점에서 보간된 재질·노멀·UV야 — 그리는 그 메시의 정보지. 디퍼드 라이팅 픽셀 셰이더 입력은 화면 좌표와 GBuffer 텍스처야 — 이미 눕혀진 화면을 읽는 거야. 그래서 라이트마다 재질을 다시 평가하지 않아. DirectX 감각으로는, MRT에 재질을 먼저 쓰고 나중에 fullscreen quad나 sphere/cone draw로 SceneColor에 additive blending을 하는 구조야.
