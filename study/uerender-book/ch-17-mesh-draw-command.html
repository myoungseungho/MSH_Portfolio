MeshDrawCommand — 그리기 명령을 미리 구워둔다

언리얼 렌더링 · 17 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "언리얼이 왜 매 프레임 메시 상태를 새로 조립하지 않고 FMeshDrawCommand로 미리 구워두는가"가 잡힌다.
🧱 먼저 알아야 할 것 — 물건의 모양과 그걸 담아둔 숫자 목록
• 모양 = 작은 삼각형 수천 개(메시): 게임 속 칼, 나무, 벽은 사실 작은 삼각형을 잔뜩 이어 붙인 껍데기야. 삼각형 하나는 모서리 점 세 개의 위치(숫자)로 적어.
• 버퍼 = 숫자를 죽 늘어놓은 목록칸: 그 꼭짓점 위치들, 점을 잇는 순서 번호들을 컴퓨터가 한 줄로 쌓아둔 칸이야. "버텍스 버퍼", "인덱스 버퍼"가 그런 목록칸 이름이야.
• 그리기 = 목록 보고 모양 하나 찍으라는 주문서 한 장: 화면에 물체 하나를 내보내려면 "이 목록 써서 이렇게 그려"라는 주문서를 적어 보내야 해. 이 챕터는 그 주문서를 매번 새로 쓰지 않는 이야기야.
이게 잡히면 아래 조리표(주문표) 이야기가 얹힌다.

왜 이걸 배워? — 문제의식부터

너는 서버에서 패킷을 매번 처음부터 해석하면 안 된다는 걸 이미 알아. CM_ATTACK 하나가 들어올 때마다 핸들러 테이블을 새로 만들고, DB 프로시저 이름을 다시 찾고, 락 순서를 다시 계산하면 서버가 버티겠어? 그래서 우리는 시작할 때 테이블을 만들고, 자주 쓰는 포인터를 잡아두고, 런타임에는 "누가 보냈고 무엇을 실행할까"만 빠르게 본다.

렌더링도 똑같아. 화면에 스태틱 메시가 5만 개 있고, 그중 2만 개가 이번 프레임에 보인다고 해보자. 매 프레임마다 "이 메시의 버텍스 버퍼는 뭐지, 인덱스 버퍼는 뭐지, 셰이더 바인딩은 뭐지, PSO는 뭐지"를 전부 다시 조립하면 CPU가 먼저 쓰러져. GPU가 아무리 빨라도, CPU가 명령서를 늦게 써주면 주방은 손 놓고 기다리는 꼴이야.

그래서 언리얼도 같은 문제를 만났고, 답이 FMeshDrawCommand야. 그리기 직전 RHI에 넘길 재료를 "한 장짜리 주문표"로 미리 구워둔다. 그리고 프레임마다 하는 일은 훨씬 작아져. 보이는 주문표만 꺼내고, 비슷한 주문표끼리 정렬하고, 같은 상태면 여러 개를 한 번에 그릴 수 있게 묶는다.

왜 지금 배우냐면, 앞의 frustum-culling·occlusion-culling은 "무엇을 그릴지"를 고르는 단계였어. 이제는 고른 것들을 "어떤 순서와 어떤 상태로 GPU에 낼지"로 내려가야 해. 다음 deferred-overview부터는 실제 패스들이 줄줄이 나오는데, 그 패스들이 메시를 그릴 때 손에 쥐는 기본 주문표가 바로 이거야.

0. 비유부터 — 도시락 가게의 미리 적어둔 조리표

도시락 가게를 생각해보자. 점심시간에 손님 1000명이 몰려와. 주문 들어올 때마다 주방장이 "밥은 어디 있지, 소스는 뭐지, 반찬은 몇 칸이지, 포장지는 무슨 색이지"를 처음부터 확인하면 줄이 끝나지 않아.

그래서 가게는 인기 메뉴마다 조리표를 미리 만들어둔다. 제육 도시락 조리표에는 이런 게 적혀 있어.

  • 밥 한 칸
  • 제육 소스
  • 김치 반찬
  • 검은 포장 용기
  • 젓가락 포함

점심시간에는 메뉴판을 새로 쓰지 않아. 오늘 주문이 들어온 조리표만 꺼내. 그다음 주방 효율을 위해 이렇게 줄 세워.

  • 같은 포장 용기끼리 모으기
  • 같은 소스끼리 모으기
  • 같은 메뉴가 여러 개면 한 번에 볶기

FMeshDrawCommand가 바로 이 조리표야. 버텍스 스트림, 인덱스 버퍼, PSO, 셰이더 바인딩, 몇 개 그릴지 같은 걸 미리 담아둔다. FVisibleMeshDrawCommand는 오늘 실제로 주문 들어온 조리표 스티커야. StateBucketId는 "같은 메뉴라서 한 팬에 같이 볶아도 됨"이라는 묶음 번호야.

이 비유를 끝까지 끌고 가자. 캐싱은 조리표를 미리 인쇄해두는 거고, 정렬은 주방 동선대로 줄 세우는 거고, 머지는 같은 메뉴 여러 개를 한 팬에 볶는 거야.

🌱 이 개념은 왜 생겼나 — MeshDrawCommand 캐싱
• 원래 구조: 메시가 보일 때마다 주방장이 "버텍스 버퍼는 어디, 인덱스 버퍼는 어디, PSO는 뭐지?"를 그 자리에서 새로 적는 식이야.
• 그런데 문제: 스태틱 메시 5만 개 중 2만 개가 보이면, 같은 조리표를 2만 번 다시 쓰느라 CPU가 먼저 줄 서. GPU 주방은 주문표가 늦어서 손 놓고 기다려.
• 그래서 필요한 것: 잘 안 바뀌는 조리표는 씬에 들어올 때 미리 구워두자. 그 한 장짜리 draw 주문표가 FMeshDrawCommand야.

1. FMeshDrawCommand는 RHI 바로 위의 주문표다

먼저 주문표 자체가 뭘 담는지 보자. 정의는 MeshPassProcessor.h에 있고, 주석이 대놓고 말해준다. 이건 "draw call을 완전히 설명하는 데이터"이고, 지원되는 경우 프리미티브가 씬에 들어올 때 캐시된다.

MeshPassProcessor.h:1214

* FMeshDrawCommand fully describes a mesh pass draw call, captured just above the RHI. FMeshDrawCommand should contain only data needed to draw. For InitViews payloads, use FVisibleMeshDrawCommand. * FMeshDrawCommands are cached at Primitive AddToScene time for vertex factories that support it (no per-frame or per-view shader binding changes). * Dynamic Instancing operates at the FMeshDrawCommand level for robustness. Adding per-command shader bindings will reduce the efficiency of Dynamic Instancing, but rendering will always be correct. * Any resources referenced by a command must be kept alive for the lifetime of the command. FMeshDrawCommand is not responsible for lifetime management of resources. For uniform buffers referenced by cached FMeshDrawCommand's, RHIUpdateUniformBuffer makes it possible to access per-frame data in the shader without changing bindings. */ class FMeshDrawCommand { public: /** * Resource bindings */ FMeshDrawShaderBindings ShaderBindings; FVertexInputStreamArray VertexStreams; FRHIBuffer* IndexBuffer; /** * PSO */ FGraphicsMinimalPipelineStateId CachedPipelineId;
🔤 기호 사전 — 주문표의 정체
• FMeshDrawCommand = 메시 하나를 그리는 데 필요한 RHI 직전 주문표야.
• RHI = 언리얼이 DirectX/Vulkan 같은 진짜 그래픽 API로 말 걸기 직전의 공통 층이야.
• cached = 매번 새로 만들지 않고, 만들어둔 걸 다시 쓴다는 뜻이야.
• Primitive AddToScene time = 메시가 렌더 씬에 등록되는 시점. 점심 전에 조리표를 인쇄하는 순간이야.
• FMeshDrawShaderBindings = 셰이더에 꽂을 리소스 묶음. 소스통, 밥통 위치 같은 거야.
• FVertexInputStreamArray = GPU가 읽을 버텍스 버퍼 입구 목록이야.
• FRHIBuffer* = RHI 버퍼를 가리키는 포인터. *는 실물이 아니라 주소표라고 보면 돼.
• CachedPipelineId = PSO를 바로 찾을 수 있는 저장된 번호야.
🔁 이제 다시 보자. FMeshDrawCommand는 RHI 바로 위 draw call 설명서고 → ShaderBindings, VertexStreams, IndexBuffer, CachedPipelineId를 들고 있고 → 가능한 경우 Primitive AddToScene time에 캐시돼. 이어 읽으면 "매 프레임 조리표를 새로 쓰지 말고, 미리 인쇄한 조리표를 들고 그리자"가 된다.

여기서 중요한 말이 두 개야.

첫째, FMeshDrawCommand는 그리기에 필요한 데이터만 담아야 해. 뷰별 가시성, 정렬, 컬링 같은 "오늘 주문 상황"은 FVisibleMeshDrawCommand 쪽으로 빠진다. 조리표에는 메뉴 레시피만 적고, 오늘 몇 번 손님이 주문했는지는 따로 붙이는 식이야.

둘째, 캐시된 명령은 매 프레임·매 뷰마다 바뀌는 셰이더 바인딩이 없어야 효율이 좋아. 매 손님마다 소스가 다르면 같은 제육 도시락이라도 한 팬에 못 볶잖아. 그래서 주석도 "per-command shader bindings를 추가하면 Dynamic Instancing 효율이 줄어든다"고 말한다.

2. 조리표는 프리미티브가 씬에 들어올 때 구워진다

스태틱 메시가 씬에 등록될 때, 언리얼은 패스별로 메시 프로세서를 돌려서 캐시 가능한 draw command를 만든다. 이 장면은 PrimitiveSceneInfo.cpp에 있다. AddMeshBatch가 실제 명령을 만들고, GetCommandInfoAndReset()이 방금 만든 명령의 캐시 위치를 돌려준다.

🔤 기호 사전 — 조리표 굽는 순간
• AddMeshBatch = 메시 배치를 처리하라는 호출. 주석대로 내부에서 FinalizeCommand까지 이어져.
• FCachedMeshDrawCommandInfo = 진짜 명령이 어디 저장됐는지 알려주는 작은 영수증이야.
• CommandIndex = 일반 캐시 리스트 안의 위치야.
• StateBucketId = 같은 상태끼리 묶는 버킷 번호야. 이게 있으면 나중에 머지 후보가 된다.
• StaticMeshCommandInfos = 이 스태틱 메시가 패스별로 가진 캐시 영수증 배열이야.
🔁 이제 다시 보자. 패스가 CachedMeshCommands를 지원하면 → CreateMeshPassProcessor로 그 패스 전용 요리사를 만들고 → AddMeshBatch로 조리표를 굽고 → GetCommandInfoAndReset()으로 저장 위치 영수증을 받는다. 마지막에 StaticMeshCommandInfos에 꽂으니, 다음 프레임부터는 같은 메시가 레시피를 다시 쓰지 않아도 돼.

이게 캐싱의 첫 번째 절반이야. 스태틱 메시가 렌더 씬에 들어오는 순간, "이 메시를 BasePass에서 어떻게 그릴지", "DepthPass에서는 어떻게 그릴지" 같은 주문표가 패스별로 준비된다. 매 프레임 시야 계산은 따로 하지만, 레시피 자체는 이미 창고에 있다.

🌱 이 개념은 왜 생겼나 — FVisibleMeshDrawCommand
• 원래 구조: 미리 구운 조리표 FMeshDrawCommand에 "오늘 보임, 정렬값, 컬링 정보"까지 그냥 덧붙이면 될 것 같아.
• 그런데 문제: 같은 제육 조리표라도 오늘 몇 번 손님이 주문했는지, 카메라에 보이는지, primitive id가 어디인지는 매 프레임 바뀌어. 원본 조리표에 덧칠하면 다음 프레임 창고 조리표가 꼬여.
• 그래서 필요한 것: 레시피 원본은 그대로 두고, 오늘 주문 스티커만 따로 붙이자. 그 한 프레임짜리 스티커가 FVisibleMeshDrawCommand야.

3. 프레임에는 보이는 조리표만 꺼낸다

앞 장에서 프러스텀 컬링과 오클루전 컬링을 봤지. 그 결과 "이번 뷰에서 이 프리미티브가 보인다"가 나오면, 언리얼은 캐시된 주문표를 꺼내서 FVisibleMeshDrawCommand로 만든다. 레시피 원본은 FMeshDrawCommand고, 오늘 주문 스티커가 FVisibleMeshDrawCommand야.

🔤 기호 사전 — 오늘 보이는 주문만 꺼내기
• bUseCachedMeshCommand = 캐시된 명령을 써도 되는지 모은 참/거짓 값이야.
• && = 모든 조건이 참이어야 한다는 "그리고"야.
• !!(...) = 값을 확실한 참/거짓으로 바꾸는 습관적인 표기야.
• StaticMeshCommandInfoIndex = 이 패스용 캐시 영수증이 몇 번째 칸에 있는지야.
• VisibleCachedDrawCommands = 이번 프레임에 실제로 보이는 draw command 목록이야.
• AddUninitialized() = 빈칸만 먼저 만들고 곧바로 채우겠다는 뜻이야.
• ? : = 조건이 맞으면 앞쪽, 아니면 뒤쪽을 고르는 짧은 if야.
• StateBucketId >= 0 = 상태 버킷에 들어간 공유 명령인지 확인하는 조건이야.
• Setup(...) = 보이는 명령 스티커에 원본 명령과 뷰용 정보를 붙이는 초기화야.
🔁 이제 다시 보자. bUseCachedMeshCommand가 참이면 → StaticMeshCommandInfos에서 캐시 영수증을 꺼내고 → StateBucketId가 있으면 버킷의 공유 명령을, 없으면 일반 리스트의 명령을 가리킨다. 그 포인터를 NewVisibleMeshDrawCommand.Setup(...)에 넣으니, 오늘 보이는 주문표가 완성돼.

여기서 아주 중요한 분리가 보여. FMeshDrawCommand는 레시피 원본이라 여러 프레임을 살아남을 수 있어. FVisibleMeshDrawCommand는 이번 프레임의 뷰에서만 필요한 포장 스티커라 한 프레임짜리야.

이 구조가 없으면 컬링 뒤에 매번 레시피를 다시 써야 해. 하지만 지금은 "보이는가?"만 새로 판단하고, "어떻게 그릴까?"는 이미 구워진 명령을 참조한다.

4. 패스 셋업은 생성, 보정, 정렬, 인스턴싱 준비 순서로 간다

이제 MeshDrawCommands.cpp로 내려가자. 패스 셋업 태스크는 동적 메시 명령을 만들고, 뷰 오버라이드를 적용하고, 정렬하고, GPU Scene 쪽 인스턴스 컬링 준비까지 이어간다. 우리가 볼 핵심은 가운데다. Context.MeshDrawCommands.Sort(FCompareFMeshDrawCommands())가 주방 줄 세우기야.

🌱 이 개념은 왜 생겼나 — 동적 인스턴싱(StateBucketId)
• 원래 구조: 보이는 조리표를 하나씩 draw call로 내면 돼. 도시락 하나 주문 들어올 때마다 팬 올리고, 소스 잡고, 한 개 만들고 끝.
• 그런데 문제: 같은 메시 100개가 같은 PSO와 셰이더 바인딩을 쓰는데도 100번 따로 그리면, 주방은 같은 팬을 100번 들었다 놔. CPU도 상태 확인을 100번 해.
• 그래서 필요한 것: 같은 상태는 StateBucketId로 같은 버킷에 넣고, 주문표 하나의 NumInstances만 늘려 한 번에 볶자. 그게 동적 인스턴싱이야.

5. 같은 상태면 여러 주문을 한 팬에 볶는다

정렬만 해도 상태 변경 비용은 줄어. 하지만 더 욕심낼 수 있어. 같은 메시 상태, 같은 버텍스 스트림, 같은 셰이더 바인딩이면 draw call 여러 개를 하나의 instanced draw로 합칠 수 있다. 이게 동적 인스턴싱이야.

아래 코드는 BuildMeshDrawCommandPrimitiveIdBuffer 안의 핵심이다. 이미 정렬된 목록을 앞에서부터 훑으면서 StateBucketId가 이전과 같으면 기존 명령의 NumInstances를 늘린다.

왜 굳이 새 FMeshDrawCommand를 복사할까? 캐시된 원본 명령은 여러 프레임, 여러 프리미티브가 공유할 수 있어. 그 원본의 NumInstances를 바로 바꾸면 창고 조리표 자체가 변해버린다. 그래서 한 프레임짜리 저장소 MeshDrawCommandStorage에 복사본을 만들고, 그 복사본만 "이번 팬에서 3인분"처럼 바꾼다.

여기서 PrimitiveIdBufferOffset도 같이 움직인다. 한 draw call로 여러 프리미티브를 그리려면 셰이더가 "나는 지금 몇 번째 프리미티브를 그리고 있지?"를 알아야 해. 그 답을 primitive id 버퍼에 적어두고, 명령에는 그 시작 위치를 붙인다.

🌱 이 개념은 왜 생겼나 — StateCache
• 원래 구조: 주문표 하나 낼 때마다 "PSO 꽂고, 버텍스 스트림 꽂고, 셰이더 바인딩 꽂아"를 매번 다시 말해.
• 그런데 문제: 정렬 덕분에 같은 제육 주문 50개가 이어져도, 똑같은 포장대와 소스통을 50번 다시 세팅하면 바뀐 게 없는데 CPU 시간이 새.
• 그래서 필요한 것: 방금 RHI에 꽂은 상태를 작은 메모장에 적어두고, 다를 때만 바꾸자. 그 메모장이 StateCache야.

6. 제출할 때는 구워둔 상태를 RHI에 꽂는다

마지막으로, 이 주문표가 진짜 draw로 바뀌는 순간을 보자. FMeshDrawCommand::SubmitDrawBegin은 캐시된 pipeline id로 PSO를 찾고, 필요할 때만 새 PSO를 적용하고, 버텍스 스트림과 셰이더 바인딩을 RHI 커맨드 리스트에 꽂는다.

여기서 StateCache가 조용히 큰일을 한다. 정렬로 비슷한 주문표를 붙여놨기 때문에, 이전 draw와 같은 PSO가 이어질 확률이 높아진다. 그러면 SetGraphicsPipelineStateCheckApply를 건너뛸 수 있다. 같은 포장 용기를 계속 쓰면 포장대를 바꿀 필요가 없는 것과 같아.

실제 draw 호출은 바로 뒤 SubmitDrawEnd에서 DrawIndexedPrimitive, DrawIndexedPrimitiveIndirect, DrawPrimitive 같은 RHI 호출로 이어진다. 이 챕터에서 중요한 건 draw 함수 이름을 외우는 게 아니야. 그 draw 직전에 필요한 상태가 이미 FMeshDrawCommand 안에 포장되어 있고, 정렬 덕분에 상태 변경을 최소화한다는 점이야.

우리 서버·DirectX 랑 비교

서버 관점으로 보면 FMeshDrawCommand는 패킷 핸들러 디스패치 테이블에 가깝다. 패킷이 올 때마다 switch 전체를 새로 구성하지 않고, 미리 만든 테이블에서 핸들러를 찾잖아. 렌더러도 메시가 보일 때마다 PSO와 바인딩을 새로 조립하지 않고, 캐시된 명령을 꺼낸다.

FVisibleMeshDrawCommand는 이번 틱의 이벤트 큐 항목이야. 원본 핸들러는 공유하고, 이번 이벤트의 sender id 같은 것만 따로 붙는 식이지. StateBucketId는 같은 DB 작업을 파라미터만 바꿔 배치 처리하려는 감각과 닮았다.

DirectX 관점으로 보면 더 직관적이야. 직접 D3D12를 쓰면 draw 전에 PSO, VB/IB, descriptor, root parameter를 세팅하고 DrawIndexedInstanced를 부르잖아. 언리얼의 FMeshDrawCommand는 그 반복 세팅을 엔진 구조 안에서 미리 포장한 거고, StateCache는 직전 상태와 같으면 다시 세팅하지 않게 돕는다. 서버에서 락 순서와 배치 순서를 정해 경합을 줄이는 것처럼, 렌더러도 PSO와 버퍼 상태를 정렬하고 머지해서 CPU 비용을 줄인다.

이 챕터에서 딱 이것만

  • FMeshDrawCommand는 RHI 바로 위의 메시 draw 주문표야.
  • 스태틱 메시의 캐시 가능한 명령은 프리미티브가 씬에 들어올 때 패스별로 구워진다.
  • 프레임에는 캐시 원본을 직접 다시 만들지 않고, 보이는 것만 FVisibleMeshDrawCommand로 꺼낸다.
  • SortKey와 StateBucketId로 줄 세워서 PSO 변경을 줄이고, 같은 버킷은 dynamic instancing으로 합칠 수 있다.
  • 제출 순간에는 CachedPipelineId, VertexStreams, ShaderBindings를 RHI에 꽂고, StateCache로 중복 세팅을 피한다.
