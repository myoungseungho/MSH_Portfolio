한 프레임 전체 되짚기 — 그리고 우리 서버

언리얼 렌더링 · 35 / 36

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "00장에서 본 한 프레임 트리를 실제 코드 위치와 서버 감각으로 다시 설명하는 힘"이 잡힌다.

왜 이걸 배워? — 문제의식부터

너는 이제 책을 한 바퀴 돌았어. CPU/GPU, 렌더 스레드, RHI, RDG, FScene, View, 컬링, PrePass, BasePass, GBuffer, 라이팅, 섀도, Nanite, Lumen, TAA, 후처리, 프로파일링까지 봤지. 근데 마지막에 꼭 한 번 다시 묶어야 해.

서버도 똑같아. 처음엔 CM_ATTACK 하나만 파다가, 나중엔 "수신 → 디코딩 → 세션 → 게임 큐 → 로직 → 브로드캐스트 → DB" 전체 흐름으로 다시 보잖아. 그걸 못 하면 장애가 났을 때 "이 패킷이 왜 여기서 두 번 처리되지?" 같은 질문에 답을 못 해. 렌더링도 그래.

이 정리가 없으면 실제 프로젝트에서 바로 터진다. 프레임이 33ms까지 튀었는데 BasePass가 문제인지, RenderLights가 문제인지, 후처리인지, 아니면 RDG 배리어와 리소스 수명이 꼬인 건지 감이 안 와. 서버에서 락 경합인지 DB 지연인지 패킷 폭주인지 못 가르는 상태랑 같아.

언리얼도 같은 문제를 만났고, 답은 한 프레임을 부서별 릴레이로 쪼개고, 그 부서의 입구 코드를 명확히 두는 것이야. 게임 월드는 직접 GPU를 때리지 않는다. 렌더러가 촬영을 짜고, RDG가 순서표를 만들고, RHI가 공통 장비 언어로 내리고, D3D12RHI 같은 백엔드가 진짜 API 호출로 바꾼다.

그래서 마지막 장은 00장으로 돌아오는 장이야. 앞 챕터들은 각 부서를 확대해서 봤고, 여기서는 다시 줌아웃한다. "아, 이 함수가 그때 본 역이었구나" 하고 한 프레임 전체 노선도를 다시 손에 쥐는 거야.

0. 비유부터 — 촬영장 하루 영업 마감표

00장에서 한 프레임을 영화 촬영장 한 컷이라고 했지. 이제 마지막 장에서는 그 촬영장이 하루 영업을 어떻게 마감하는지 보자.

감독이 오늘 찍을 장면을 촬영표에 올린다. 조감독이 카메라와 배우를 확인한다. 바닥팀이 배우 위치 표시를 먼저 깐다. 의상팀이 재질 정보를 기록한다. 조명팀이 빛을 얹는다. 색보정팀이 최종 화면 느낌을 만든다. 마지막으로 진행팀이 촬영표를 실제 장비 명령으로 내려보낸다.

언리얼 한 프레임도 이 순서야.

촬영표 등록 = FSceneRenderBuilder에 렌더러 등록 카메라/배우 확인 = InitViews와 visibility 바닥 표시 = PrePass 의상표 기록 = BasePass와 GBuffer 조명 켜기 = RenderLights 색보정 = AddPostProcessingPasses 장비 실행 = FRDGBuilder::Execute

이번 장에서는 새 지식을 많이 넣지 않는다. 대신 앞에서 배운 조각들을 이 촬영장 마감표에 꽂아 넣을 거야.

🌱 이 개념은 왜 생겼나 — 한 프레임 트리
• 원래 구조: 화면 한 장을 그냥 "그린다" 한 단어로 봐도 돼. 감독이 카메라 켜고, 배우 세우고, 조명 켜고, 끝.
• 그런데 문제: 프레임이 33ms로 튀면 어디가 막혔는지 몰라. 배우가 많은 건지, 조명이 많은 건지, 색보정실이 느린 건지 한 덩어리라서 못 찾아.
• 그래서 필요한 것: 하루 촬영을 부서별 가지로 쪼갠 지도야. 그래서 트리처럼 입구에서 가지가 갈라지고, 마지막에 다시 장비 실행으로 모인다고 보는 거야.
🧱 먼저 알아야 할 것 — 가지가 갈라지는 그림(조직도) 읽기
• 위에서 아래로 갈라진다: 조직도나 가계도처럼, 맨 위에 하나가 있고 아래로 내려갈수록 가지가 여러 개로 갈라져. 아래로 갈수록 더 잘게 나뉜 세부 일이야.
• 들여쓰기가 깊을수록 하위: 글로 그린 가지 그림에서는 안쪽으로 더 들어가(들여쓰기) 적힌 줄이 바로 위 줄의 하위 가지야. 폴더 안의 폴더처럼.
이게 잡히면 아래 한 프레임을 부서별 가지로 쪼갠 트리 설명이 얹힌다.

1. 00장 트리로 돌아가기

먼저 전체 트리를 다시 보자. 각 줄은 이미 앞 챕터에서 한 번 이상 본 부서야.

한 프레임 │ ├─ 입구: 게임 쪽이 렌더러를 촬영표에 올림 │ └─ BeginRenderingViewFamilies → FSceneRenderBuilder │ ├─ 렌더러: 이번 카메라 묶음을 실제 패스로 쪼갬 │ └─ FDeferredShadingSceneRenderer::Render │ ├─ 무엇을 그릴지 고름 │ └─ BeginInitViews / visibility task / mesh pass setup │ ├─ 실제로 그림 │ ├─ PrePass │ ├─ BasePass │ ├─ RenderLights │ ├─ translucency / Nanite / Lumen / shadow 계열 │ └─ AddPostProcessingPasses │ └─ 실행과 하드웨어 └─ FRDGBuilder::Execute → RHI command list → D3D12RHI

서버식으로 말하면 이거야. 패킷 하나가 들어와서 곧장 캐릭터 HP를 깎지 않듯이, 화면 한 장도 곧장 DrawIndexedInstanced로 가지 않아. 중간에 소유권, 순서, 버퍼 수명, 병렬 작업, 플랫폼 차이를 처리하는 층이 있어.

🌱 이 개념은 왜 생겼나 — FSceneRenderBuilder(촬영표)
• 원래 구조: 렌더 요청이 오면 그 자리에서 바로 RenderViewFamily_RenderThread를 불러서 쭉 그리면 단순해.
• 그런데 문제: 뷰 패밀리가 여러 개고, 히트 프록시 같은 특수 촬영도 섞이면 "누가 오늘 촬영할 감독인지"를 한곳에 모아야 해. 안 그러면 순서표가 흩어져.
• 그래서 필요한 것: 이번 프레임에 돌 렌더러들을 먼저 촬영표에 올리는 상자야. 이름 그대로 Scene Render를 Build하는 사람, FSceneRenderBuilder야.
🧱 먼저 알아야 할 것 — 바로 안 하고 할 일을 적어두었다가 나중에 실행
• 적어두기: 마트에서 물건을 볼 때마다 사는 게 아니라, 살 것을 목록에 적어두었다가 나중에 한꺼번에 계산하지. 일을 "지금 당장"이 아니라 "목록에 등록"만 해둘 수 있어.
• 나중에 한꺼번에: 목록이 다 차면 그제서야 순서대로 실제로 실행해. 그래서 등록하는 순간엔 아직 아무 일도 벌어지지 않은 거야.
이게 잡히면 아래 렌더러를 촬영표에 등록만 하고 나중에 실행한다는 설명이 얹힌다.

2. 입구 — 촬영표에 감독을 올린다

프레임의 시작점은 "이 뷰 패밀리를 렌더링해"라는 요청이야. 여기서 이미 만들어진 SceneRenderer들을 FSceneRenderBuilder에 등록한다. 등록된 람다는 나중에 렌더 스레드에서 실행돼.

SceneRendering.cpp:5200

for (FSceneRenderer* SceneRenderer : SceneRenderers) { SceneRenderer->ViewFamily.DisplayInternalsData.Setup(World); SceneRenderBuilder.AddRenderer(SceneRenderer, bShowHitProxies ? TEXT("HitProxies") : TEXT("ViewFamilies"), [] (FRDGBuilder& GraphBuilder, const FSceneRenderFunctionInputs& Inputs) { RenderViewFamily_RenderThread(GraphBuilder, Inputs.Renderer, Inputs.SceneUpdateInputs); return true; }); }
🔤 기호 사전 — 촬영표 등록 코드
• for = 여러 렌더러를 하나씩 돌면서 같은 일을 한다.
• FSceneRenderer* = 렌더러 실물을 가리키는 손잡이. *는 포인터야.
• -> = 포인터가 가리키는 물건 안으로 들어가 기능이나 값을 꺼낸다.
• AddRenderer(...) = 이번 프레임 촬영표에 렌더러 일을 등록한다.
• [] (...) { ... } = 나중에 실행할 작은 함수 덩어리, 람다야.
• FRDGBuilder& = RDG 순서표를 만드는 객체를 원본 그대로 받는다. &는 참조야.
• return true = 이 등록 함수가 일을 했다고 알려준다.
🔁 이제 다시 보자. SceneRenderers를 하나씩 꺼내고 → ViewFamily 내부 표시 데이터를 세팅하고 → SceneRenderBuilder.AddRenderer로 촬영표에 올리고 → 나중에 RenderViewFamily_RenderThread를 부르게 해. 아까 말한 "감독을 오늘 촬영표에 올리는 장면"이 이 코드야.

여기서 중요한 건 아직 GPU가 움직이지 않았다는 거야. 우리는 주문표를 만든 거지, 주방 불판을 켠 게 아니야. 서버로 치면 IOCP 완료 통지를 받자마자 월드 상태를 바꾸는 게 아니라, 게임 로직 큐로 넘길 작업을 등록하는 느낌이야.

🌱 이 개념은 왜 생겼나 — InitViews와 visibility
• 원래 구조: 월드에 있는 배우를 전부 다 그리면 돼. 카메라 밖에 있든 벽 뒤에 있든 일단 의상팀과 조명팀으로 보내는 거야.
• 그런데 문제: 배우가 10만 명인데 화면엔 2천 명만 보이면 9만 8천 명한테도 옷 입히고 조명 쏘는 셈이야. 한 프레임 16.6ms 예산이 바로 터져.
• 그래서 필요한 것: 먼저 카메라와 뷰를 준비하고, 보일 가능성이 있는 배우만 추리는 관문이 필요해. 그래서 InitViews가 판을 깔고, visibility가 "보이는가"를 따지는 거야.

3. 카메라와 배우 확인 — InitViews와 visibility

촬영표에 오른 뒤에는 카메라가 보는 배우만 골라야 해. 안 보이는 배우까지 전부 의상 입히고 조명 비추면 비용이 터진다. 그래서 visibility 단계가 있어.

여기서 동적 메시 수집을 시작하고, 데칼/섀도 같은 부가 작업도 겹쳐서 돌리려고 시도한다. 렌더링은 순서대로만 걷는 게 아니라, 가능한 일은 겹쳐서 밀어 넣는 구조야.

// Start processing dynamic mesh elements tasks early enough to overlap with shadows and GPU scene update. TaskDatas.VisibilityTaskData->StartGatherDynamicMeshElements(); #if RHI_RAYTRACING // Start processing dynamic ray tracing instances early enough to overlap with shadows and GPU scene update. if (TaskDatas.RayTracingGatherInstances != nullptr) { RayTracing::BeginGatherDynamicRayTracingInstances(*TaskDatas.RayTracingGatherInstances); } #endif if (!ViewFamily.EngineShowFlags.HitProxies) { TaskDatas.Decals = FDecalVisibilityTaskData::Launch(GraphBuilder, *Scene, Views); } // Attempt to launch dynamic shadow tasks early before finalizing visibility. if (bRendererOutputFinalSceneColor) { BeginInitDynamicShadows(GraphBuilder, TaskDatas, InstanceCullingManager); }
🔤 기호 사전 — 보이는 배우 고르기 코드
• TaskDatas = 이번 visibility 단계에서 쓸 작업 묶음 상자야.
• StartGatherDynamicMeshElements() = 움직이는 메시들을 모으기 시작한다.
• #if RHI_RAYTRACING = 레이트레이싱 기능이 켜진 빌드에서만 이 코드가 살아난다.
• != nullptr = 빈손이 아니면, 즉 실제 객체가 있으면.
• *TaskDatas.RayTracingGatherInstances = 포인터 손잡이 안의 실물을 꺼낸다.
• !ViewFamily.EngineShowFlags.HitProxies = 히트 프록시 모드가 아닐 때. !는 반대로 뒤집는 표시야.
• FDecalVisibilityTaskData::Launch(...) = 데칼 visibility 작업을 시작한다.
• BeginInitDynamicShadows(...) = 동적 그림자 준비를 가능하면 일찍 시작한다.

이 코드는 "배우 명단을 보고, 실제 카메라에 잡힐 사람만 골라오면서, 그림자팀과 데칼팀도 미리 부르는 장면"이야. 서버에서 한 틱 안에 AI, 이동, 전투, 브로드캐스트 준비를 순서만 맞춰 겹치는 것과 비슷해.

여기서 프러스텀 컬링은 → frustum-culling, 오클루전은 → occlusion-culling, 메시 명령 준비는 → mesh-draw-command와 이어진다.

4. 바닥 표시 — PrePass는 깊이를 먼저 깐다

보일 배우를 골랐으면, 먼저 바닥 표시를 해. 누가 앞에 있고 누가 뒤에 있는지 깊이 버퍼에 깔아두는 거야.

깊이가 있으면 뒤에 가려질 픽셀을 비싼 픽셀 셰이더로 칠하지 않아도 돼. 식당으로 치면 조리 전에 자리표를 먼저 깔아서, 음식이 엉뚱한 테이블로 가지 않게 하는 거야.

DeferredShadingRenderer.cpp:2378

const ERenderTargetLoadAction DepthLoadAction = ERenderTargetLoadAction::EClear; AddClearDepthStencilPass(GraphBuilder, LocalSceneTextures.Depth.Target, DepthLoadAction, StencilLoadAction); // Draw the scene pre-pass / early z pass, populating the scene depth buffer and HiZ if (bNeedsPrePass) { RenderPrePass(GraphBuilder, InViews, LocalSceneTextures.Depth.Target, InstanceCullingManager, &FirstStageDepthBuffer); }
🔤 기호 사전 — 깊이 먼저 까는 코드
• const = 이 값은 아래에서 바꾸지 않겠다는 약속이야.
• ERenderTargetLoadAction::EClear = 렌더 타깃을 쓰기 전에 깨끗이 지운다는 선택지.
• AddClearDepthStencilPass(...) = 깊이/스텐실 버퍼를 지우는 RDG 패스를 추가한다.
• LocalSceneTextures.Depth.Target = 이번 장면에서 쓸 깊이 텍스처의 실제 대상.
• if (bNeedsPrePass) = 프리패스가 필요하면 안쪽을 실행한다.
• RenderPrePass(...) = 깊이만 먼저 그리는 패스.
• &FirstStageDepthBuffer = 변수의 주소를 넘긴다. 함수가 그 칸을 채울 수 있게 하는 거야.
🔁 이제 다시 보자. DepthLoadAction을 EClear로 잡고 → AddClearDepthStencilPass로 깊이 칠판을 비우고 → bNeedsPrePass가 참이면 RenderPrePass로 깊이를 먼저 채워. 촬영장 바닥에 배우 위치 테이프를 먼저 붙이는 단계로 읽으면 된다.

프리패스의 더 자세한 이유는 → prepass-depth에서 봤다. 여기서는 "뒤 단계가 싸게 일하게 하려고 먼저 깊이를 깐다"만 잡으면 돼.

5. 의상표 기록 — BasePass는 GBuffer 재료를 만든다

깊이가 준비되면 이제 배우의 의상표를 적는다. 디퍼드 렌더링에서 이 의상표가 GBuffer야. 색, 노멀, 러프니스, 금속성 같은 "빛을 계산할 재료"를 화면 좌표에 적어두는 거지.

BasePass 내부에서는 뷰마다 메시 드로우 커맨드를 꺼내고, RDG 패스를 추가하고, 실제 드로우는 그 패스 람다 안에서 한다.

const bool bShouldRenderView = View.ShouldRenderView(); if (auto* Pass = View.ParallelMeshDrawCommandPasses[EMeshPass::BasePass]; Pass && bShouldRenderView) { Pass->BuildRenderingCommands(GraphBuilder, Scene->GPUScene, PassParameters->InstanceCullingDrawParams); GraphBuilder.AddPass( RDG_EVENT_NAME("BasePass"), PassParameters, ERDGPassFlags::Raster, [&View, Pass, PassParameters](FRDGAsyncTask, FRHICommandList& RHICmdList) { SetStereoViewport(RHICmdList, View, 1.0f); Pass->Draw(RHICmdList, &PassParameters->InstanceCullingDrawParams); });
🔤 기호 사전 — BasePass 드로우 코드
• bShouldRenderView = 이 뷰를 진짜 그릴지 나타내는 참/거짓 값이야.
• auto* Pass = ... = 타입은 컴파일러가 맞히고, 우리는 포인터 손잡이만 받는다.
• EMeshPass::BasePass = 메시 패스 중 BasePass용 명령 묶음을 고른다.
• Pass && bShouldRenderView = 패스가 있고, 뷰도 그려야 할 때만.
• BuildRenderingCommands(...) = 실제 그릴 명령들을 준비한다.
• GraphBuilder.AddPass(...) = RDG 순서표에 새 패스를 추가한다.
• ERDGPassFlags::Raster = 래스터라이즈 방식의 그래픽 패스라는 표시야.
• FRHICommandList& RHICmdList = 실제 RHI 명령을 적는 커맨드 리스트.
• Pass->Draw(...) = 준비한 메시 명령을 실제 RHI 커맨드 리스트에 그린다.
🔁 이제 다시 보자. View.ShouldRenderView()로 이 카메라를 그릴지 확인하고 → BasePass용 메시 패스를 꺼내고 → BuildRenderingCommands로 주문서를 만들고 → GraphBuilder.AddPass에 넣어. 그 패스가 실행될 때 Pass->Draw가 RHI 명령을 적는다. 의상팀이 바로 극장에 화면을 거는 게 아니라, RDG 촬영표에 "이 의상 촬영 컷"을 올리는 거야.

이게 → basepass-gbuffer의 중심이고, 픽셀 셰이더 안에서 실제 GBuffer를 어떻게 쓰는지는 → basepass-shader에서 봤다.

6. 조명 켜기 — 빛은 재료표 위에 얹는다

BasePass가 끝나면 화면에는 "최종 색"이 아니라 "빛을 계산할 재료표"가 있다. 이제 조명팀이 들어와.

디퍼드 렌더링의 장점은 여기서 나온다. 물체마다 모든 라이트를 다시 그리는 게 아니라, GBuffer를 읽고 화면 공간에서 라이트를 얹는다. 라이트가 많을수록 이 구조가 유리해지는 이유가 여기야.

LightRendering.cpp:1580

// True if the clustered shading is enabled and the feature level is there, and that the light grid had lights injected. if (ShouldUseClusteredDeferredShading(ViewFamily.GetShaderPlatform()) && AreLightsInLightGrid()) { // Tell the trad. deferred that the clustered deferred capable lights are taken care of. // This includes the simple lights StandardDeferredStart = SortedLightSet.ClusteredSupportedEnd; // Tell the trad. deferred that the simple lights are spoken for. bRenderSimpleLightsStandardDeferred = false; AddClusteredDeferredShadingPass(GraphBuilder, SceneTextures, SortedLightSet, ShadowSceneRenderer.VirtualShadowMapMaskBits, ShadowSceneRenderer.VirtualShadowMapMaskBitsHairStrands, LightingChannelsTexture); } if (bRenderSimpleLightsStandardDeferred) { RenderSimpleLightsStandardDeferred(GraphBuilder, SceneTextures, SortedLightSet); }
🔤 기호 사전 — 조명 선택 코드
• ShouldUseClusteredDeferredShading(...) = 클러스터드 디퍼드 조명 방식을 쓸지 묻는다.
• ViewFamily.GetShaderPlatform() = 이 뷰 패밀리가 돌 셰이더 플랫폼을 꺼낸다.
• && = 두 조건이 모두 참이어야 한다는 뜻.
• AreLightsInLightGrid() = 라이트 그리드에 처리할 라이트가 있는지 확인한다.
• SortedLightSet.ClusteredSupportedEnd = 클러스터드 방식으로 처리 가능한 라이트 구간의 끝.
• bRenderSimpleLightsStandardDeferred = false = 단순 라이트를 전통 디퍼드 쪽에서 다시 그리지 않게 끈다.
• AddClusteredDeferredShadingPass(...) = 클러스터드 디퍼드 조명 패스를 RDG에 추가한다.
• RenderSimpleLightsStandardDeferred(...) = 필요하면 단순 라이트를 전통 디퍼드 방식으로 그린다.

이 코드에서 보이는 핵심은 "한 가지 조명 길만 있는 게 아니다"야. 기능 레벨, 라이트 그리드, 섀도, 머리카락, VSM 같은 조건에 따라 길이 갈라진다. 하지만 네가 잡아야 할 큰 방향은 단순해. BasePass가 만든 재료표 위에 조명 패스가 빛을 얹는다.

조명의 자세한 흐름은 → deferred-lighting, 그림자 쪽은 → shadow-maps와 → virtual-shadow-maps로 이어진다.

7. 색보정과 화면 마감 — 후처리는 마지막 도장이다

조명까지 끝나도 아직 사람이 보는 최종 화면은 아니야. HDR 색을 LDR로 바꾸고, TAA로 시간 누적을 하고, 블룸과 톤매핑을 붙이고, 업스케일과 디버그 표시까지 처리해야 해.

프레임 큰 함수 안에서 후처리 입구는 AddPostProcessingPasses야. 실제 호출 위치는 DeferredShadingRenderer.cpp:3943에 있고, 후처리 내부의 패스 스위치는 PostProcessing.cpp:731 근처에서 MotionBlur, Tonemap, FXAA, SMAA 같은 항목을 켜고 끈다.

여기는 앞 장 → postprocess-chain에서 이미 봤으니까 마지막 장에서는 위치만 기억하면 돼. 촬영장 비유로는 색보정실이야. 카메라가 찍은 HDR 원본을 최종 상영관 규격에 맞게 손보는 곳이지.

TAA는 → temporal-aa, Lumen과 간접광은 → lumen-overview · lumen-diffuse, 성능 확인은 → gpu-profiling으로 다시 연결된다.

8. RDG 실행 — 촬영표를 장비 명령으로 바꾼다

지금까지 GraphBuilder.AddPass가 계속 나왔어. 이건 그 자리에서 바로 GPU를 때리는 게 아니야. RDG 순서표에 패스를 쌓는 거야.

마지막에는 RDG가 순서표를 컴파일하고, 배리어를 모으고, 리소스를 준비하고, 실제 실행 단계로 넘긴다. 아래 토막은 그 마감 절차의 중심이야.

RenderGraphBuilder.cpp:1891

Compile(); CollectPassBarriersTask = AddSetupTask([this] { CompilePassBarriers(); CollectPassBarriers(); }, TaskPriority, bParallelCompileResources);
🔤 기호 사전 — RDG 마감 코드
• Compile() = RDG 그래프를 실행 가능한 계획으로 정리한다.
• CollectPassBarriersTask = 패스 사이 리소스 상태 전환을 모으는 작업 손잡이야.
• AddSetupTask(...) = 실행 전에 해야 할 준비 작업을 태스크로 등록한다.
• [this] = 람다 안에서 지금 RDG 빌더 자기 자신을 쓰겠다는 뜻.
• CompilePassBarriers() = 패스마다 필요한 배리어 정보를 계산한다.
• CollectPassBarriers() = 계산된 배리어들을 실행에 쓸 수 있게 모은다.
• TaskPriority = 이 준비 작업의 우선순도야.
• bParallelCompileResources = 리소스 컴파일을 병렬로 할 수 있는지 보는 깃발.
🔁 이제 다시 보자. Compile()로 촬영표 전체를 실행 계획으로 바꾸고 → AddSetupTask 안에서 CompilePassBarriers()와 CollectPassBarriers()를 돌려 리소스 상태 전환을 챙겨. 즉 RDG는 "패스 목록"만 들고 있는 게 아니라, GPU가 안전하게 읽고 쓸 수 있도록 사이사이 신호등까지 세우는 진행팀이야.

서버로 치면 이건 락 순서와 큐 flush를 정리하는 층이야. 패킷 핸들러들이 하고 싶은 일을 다 적어놨다고 끝이 아니지. 어떤 스레드에서, 어떤 순서로, 어떤 공유 자원을 잡고 놓을지 맞춰야 사고가 안 나. RDG가 렌더링에서 그 안전장치 역할을 한다고 보면 돼.

10. 앞 챕터들을 이 지도에 다시 꽂아보기

이제 앞 장들이 어디였는지 다시 꽂아보자. [cpu-vs-gpu]와 [render-thread]는 "왜 바로 GPU를 때리지 않는가"였고, 그 답이 RenderViewFamily_RenderThread와 RHICmdList 경계에 있다. [rdg]는 "왜 그래프가 필요한가"였고, 그 답이 CompilePassBarriers()에 있다. [fscene], [scene-proxy], [view-family]는 렌더러가 보는 세계와 카메라였고, visibility가 그 자료로 오늘 찍을 배우를 고른다. [frustum-culling], [occlusion-culling], [mesh-draw-command]는 낭비를 줄이는 준비였다. [prepass-depth], [basepass-gbuffer], [basepass-shader]는 바닥 표시와 의상표 기록이었다. [deferred-lighting], [shadow-maps], [virtual-shadow-maps]는 그 의상표 위에 빛과 그림자를 얹는 단계였다. [nanite-overview], [lumen-overview], [temporal-aa], [postprocess-chain], [gpu-profiling]은 메인 도로 옆에 붙는 현대 렌더러의 전용 차선들이야.

우리 서버·DirectX 랑 비교

우리 조선 서버의 한 틱과 렌더 한 프레임은 많이 닮았다.

서버 한 틱은 IOCP 완료 통지 수집 → 세션/패킷 큐 정리 → 게임 로직 대상 고르기 → 이동/전투/스킬/AI 처리 → 변경분 브로드캐스트 → DB나 로그 후처리로 간다. 렌더 한 프레임은 렌더 요청 등록 → View와 Scene 상태 정리 → visibility → PrePass/BasePass → Lighting/Nanite/Lumen/Shadow → PostProcess → RDG/RHI 실행으로 간다.

공통점은 바로 실행하지 않고, 중간 표현을 만든 뒤, 안전한 순서로 처리한다는 거야. 서버에서 여러 워커가 같은 캐릭터를 동시에 고치면 터지니까 게임 로직 큐나 단일 월드 스레드로 모으지. 렌더링도 게임 스레드가 GPU 리소스를 마음대로 만지면 터져서 렌더 스레드, RDG, RHI 같은 소유 경계를 둔다.

서버에서 락은 "공유 상태를 언제 누가 만지나"를 통제한다. 렌더링에서 배리어는 "GPU 리소스를 언제 읽고 쓰나"를 통제한다. CompilePassBarriers()가 낯설어 보여도, 서버 감각으로는 락 순서표와 비슷하게 보면 돼.

DirectX 12를 직접 만져봤다면 커맨드 리스트 열기, 렌더타깃 상태 전환, PSO 세팅, 디스크립터 바인딩, 드로우 호출, 큐 제출을 직접 했을 거야. 언리얼에서도 그 일은 사라지지 않아. 다만 Renderer가 어떤 패스를 만들지 정하고, RDG가 리소스 수명과 배리어를 맞추고, RHICommandList가 플랫폼 공통 명령을 적고, D3D12RHI가 실제 D3D12 호출로 바꾼다.

프레임이 느리면 서버 장애 보듯 쪼개서 봐. 대상이 너무 많으면 visibility와 mesh draw command, 깊이 낭비면 PrePass, 재료 기록이 무거우면 BasePass와 셰이더, 빛이 무거우면 RenderLights와 shadow/Lumen, 마지막이 무거우면 TAA와 후처리, CPU 준비가 무거우면 InitViews와 RDG compile을 보면 된다.

마지막으로 한 번 더 줄이면 이거야. 촬영표 등록 → 카메라/배우 확인 → 보이는 배우만 추림 → 깊이 기록 → GBuffer 기록 → 빛과 그림자 → 후처리 → RDG 배리어 → RHI/D3D12RHI. 이게 이 책 전체야.

이 챕터에서 딱 이것만

  • 한 프레임은 SceneRenderBuilder에 렌더러를 올리는 촬영표 등록에서 시작한다.
  • InitViews와 visibility는 "오늘 카메라에 잡힐 배우"만 추려서 뒤 비용을 줄인다.
  • PrePass → BasePass → RenderLights → PostProcess가 디퍼드 프레임의 큰 뼈대다.
  • GraphBuilder.AddPass는 즉시 실행이 아니라 RDG 순서표에 패스를 올리는 일이다.
  • RDG의 CompilePassBarriers()는 GPU 리소스 읽기/쓰기 순서를 안전하게 맞추는 신호등이다.

🧠 면접 리뷰 — 진짜 이해했는지 확인

이건 마무리 장이야. 세부 함수 하나가 아니라, 한 프레임 전체가 왜 이렇게 생겼고 어떻게 도는지를 네 말로 재구성할 수 있으면 이 책을 소화한 거야. 먼저 스스로 답해보고, 막히면 펴서 확인해. ↳ 표시는 앞 답을 파고드는 꼬리질문이야.

Q1. 언리얼의 한 프레임을 처음부터 끝까지 큰 그림으로 설명해보세요.

Q2. 이 책 내내 "바로 안 하고 등록만 한다"가 반복되던데, 왜 이 패턴이 렌더링의 뼈대인가요?

답 보기
촬영표에 감독 올리기(AddRenderer), 패스 등록(GraphBuilder.AddPass) 다 "지금 실행"이 아니라 "목록에 등록"이야. 마트에서 물건 볼 때마다 사는 게 아니라 목록에 적어뒀다 한꺼번에 계산하는 거지. 왜냐면 패스가 수십 개로 쪼개지면 누가 어떤 텍스처를 먼저 만들고 누가 읽는지 의존성이 꼬여. 그래서 일단 다 등록해두고, RDG가 그 목록을 컴파일해서 순서·배리어를 자동으로 챙긴 뒤 몰아서 실행해. 서버에서 IOCP 완료 통지 받자마자 월드를 바꾸지 않고 게임 로직 큐로 넘기는 거랑 같은 이유야.

↳ RDG의 CompilePassBarriers()를 서버 감각으로 옮기면 뭐예요?

답 보기
락 순서표야. 서버에서 락은 "공유 상태를 언제 누가 만지나"를 통제하고, 렌더링에서 배리어는 "GPU 리소스를 언제 읽고 쓰나"를 통제해. RDG는 패스 목록만 들고 있는 게 아니라 Compile()로 실행 계획을 짠 뒤 사이사이 신호등(배리어)을 세워서, GPU가 아직 안 만든 텍스처를 읽거나 쓰는 중인 걸 읽는 사고를 막아. CompilePassBarriers()가 낯설어도 락 순서 정리하는 층이라고 보면 돼.

Q3. 디퍼드 렌더링이 이 큰 그림의 중심 줄기인데, 왜 이렇게 설계했나요?

답 보기
물체마다 모든 라이트를 다시 그리면 조명이 많을수록 같은 픽셀에 조명 계산을 반복하게 돼. 그래서 순서를 뒤집었어 — BasePass에서 먼저 화면 좌표마다 색·노멀·러프니스·금속성 같은 재료표(GBuffer)를 적어두고, RenderLights가 그 재료표를 읽어 화면 공간에서 빛을 얹어. 물체 수가 아니라 화면 픽셀 수 기준으로 조명을 계산하니까, 라이트가 많을수록 이 구조가 유리해지는 거야. 그게 디퍼드(미룬)의 핵심이야.

↳ 그럼 프레임이 33ms로 튀었을 때, 이 지도를 어떻게 병목 찾기에 쓰나요?

답 보기
서버 장애 보듯 부서별로 쪼개서 봐. 대상이 너무 많으면 visibility·mesh draw command, 깊이 낭비면 PrePass, 재료 기록이 무거우면 BasePass와 셰이더, 빛이 무거우면 RenderLights·shadow·Lumen, 마지막이 무거우면 TAA·후처리, CPU 준비가 무거우면 InitViews와 RDG compile을 봐. 한 덩어리로 "그린다"로 보면 못 찾지만, 트리로 쪼개져 있으니까 GPU stat 이름표로 어느 가지가 늦은지 짚을 수 있는 거야. 이 지도의 실용적 가치가 여기서 나와.

Q4. Nanite·Lumen·TAA 같은 현대 렌더러 기능은 이 뼈대에서 어디에 붙나요?

답 보기
메인 도로 옆에 붙는 전용 차선이야. 뼈대(촬영표 → visibility → PrePass → BasePass → Lighting → PostProcess → RDG 실행)는 그대로고, Nanite는 지오메트리 처리에, Lumen은 간접광/반사 쪽에, TAA는 후처리 앞 시간 안정화 관문에, 프로파일링은 그 위에 얹은 계측 층에 붙어. 그래서 새 기능이 들어와도 큰 릴레이 구조 자체는 안 바뀌어 — 어느 부서에 확장 차선을 붙였는지만 알면 돼. 이 책을 한 문장으로 줄이면 이거야: 촬영표 등록 → 배우 추림 → 깊이 → GBuffer → 빛·그림자 → 후처리 → RDG 배리어 → RHI/D3D12RHI.
