﻿# CH25 · 반투명은 왜 어려운가

대상 독자: 게임 서버는 아는데 렌더링은 처음인 사람.
이 챕터가 끝나면 "왜 반투명은 GBuffer에 그냥 넣지 않고, 따로 그리고, 순서까지 신경 쓰는가"가 잡힌다.

왜 이걸 배워? — 문제의식부터

너는 이미 서버에서 순서가 중요한 처리를 많이 봤어. CM_ATTACK 다음에 CM_MOVE가 오느냐, 반대로 오느냐에 따라 결과가 달라지잖아. 락도 마찬가지야. A 락 잡고 B 락 잡는 순서와, B 락 잡고 A 락 잡는 순서가 꼬이면 데드락이 나. 렌더링에도 똑같이 순서 때문에 터지는 물건이 있어. 그게 반투명이야. 불투명 벽은 쉬워. 가까운 벽 하나가 픽셀을 차지하면 뒤쪽 벽은 안 보여. 그래서 디퍼드는 GBuffer에 "이 픽셀의 제일 앞 표면 하나"만 적어도 돼. 색, 노멀, 러프니스, 메탈릭 같은 정보를 한 번 눕혀놓고, 나중에 빛을 계산하면 끝이었지. → basepass-gbuffer 그런데 유리창은 달라. 앞 유리창 색 40%, 뒤 네온사인 색 60%, 그 뒤 안개 색 조금. 이건 "제일 앞 표면 하나"로 끝나지 않아. 뒤에 뭐가 이미 그려져 있는지, 앞뒤 순서가 어떻게 되는지, 알파를 어떤 방식으로 섞을지가 결과를 바꿔. 이걸 GBuffer에 억지로 넣으면 뭐가 터질까? 픽셀 하나에 유리 조각 3장이 겹친 순간, GBuffer 칸 하나로는 누구 색을 저장해야 할지 답이 없어. 앞 유리의 노멀을 저장하면 뒤 유리가 사라지고, 뒤 유리를 저장하면 앞 유리가 사라져. 심지어 섞는 식도 빛 계산 뒤에 색 버퍼와 섞어야 하니, "나중에 라이팅할 재료 정보"만 저장하는 디퍼드 방식과 결이 안 맞아. 언리얼도 같은 문제를 만났고, 답이 반투명 전용 포워드 패스와 정렬이야. 불투명은 디퍼드로 GBuffer에 깔고, 반투명은 그 결과 위에 따로 그린다. 필요하면 낮은 해상도 별도 버퍼에 그리고, 나중에 합성한다. 그리고 가능한 한 뒤에서 앞으로 그리려고 정렬 키를 챙긴다. 왜 지금 배우냐면, 바로 앞에서 그림자와 VSM까지 봤고 → virtual-shadow-maps, 이제 "불투명 세계"만으로는 프레임이 안 끝난다는 걸 볼 차례야. 이 챕터를 잡아야 다음 PBR 수식 → pbr-brdf로 넘어갔을 때도, "이 재질은 어느 패스에서 계산되는가"를 헷갈리지 않아.

0. 비유부터 — 셀로판지를 겹쳐서 무대 보기

초등학교 미술 시간에 색 셀로판지 써봤지? 빨간 셀로판지 한 장을 눈앞에 대면 세상이 빨갛게 보여. 파란 셀로판지를 그 앞에 또 대면 색이 또 바뀌어. 중요한 건 이거야. 셀로판지는 뒤 배경을 지우지 않고 섞어. 불투명 스티커는 다르다. 스티커를 붙이면 뒤 그림은 그냥 가려져. 그래서 스티커는 "제일 앞 스티커 하나"만 알면 돼. 하지만 셀로판지는 뒤 그림과 앞 셀로판지를 같이 봐야 해. 그리고 셀로판지 여러 장이면 어떤 장을 먼저 겹치느냐가 중요해져. 이 챕터에서 계속 이 비유로 갈 거야.

  • 불투명 물체 = 스티커.
  • GBuffer = 픽셀마다 제일 앞 스티커 정보를 적는 장부.
  • 반투명 물체 = 셀로판지.
  • 반투명 패스 = 스티커 작업 끝난 뒤, 셀로판지를 따로 겹치는 작업.
  • 정렬 = 먼 셀로판지부터 가까운 셀로판지까지 순서대로 놓는 일.

자, 이제 언리얼 코드가 이 셀로판지를 어떻게 따로 다루는지 보자.

2. 패스 이름은 실제 MeshPass로 바뀐다

위의 ETranslucencyPass는 "반투명 작업 종류"야. GPU에 그리기 명령을 모을 때는 이걸 EMeshPass로 바꿔야 해. 언리얼은 그 매핑을 아주 노골적으로 둔다. TranslucentRendering.cpp:164

EMeshPass::Type TranslucencyPassToMeshPass(ETranslucencyPass::Type TranslucencyPass) { EMeshPass::Type TranslucencyMeshPass = EMeshPass::Num; switch (TranslucencyPass) { case ETranslucencyPass::TPT_TranslucencyStandard: TranslucencyMeshPass = EMeshPass::TranslucencyStandard; break; case ETranslucencyPass::TPT_TranslucencyStandardModulate: TranslucencyMeshPass = EMeshPass::TranslucencyStandardModulate; break; case ETranslucencyPass::TPT_TranslucencyAfterDOF: TranslucencyMeshPass = EMeshPass::TranslucencyAfterDOF; break; case ETranslucencyPass::TPT_TranslucencyAfterDOFModulate: TranslucencyMeshPass = EMeshPass::TranslucencyAfterDOFModulate; break; case ETranslucencyPass::TPT_TranslucencyAfterMotionBlur: TranslucencyMeshPass = EMeshPass::TranslucencyAfterMotionBlur; break; case ETranslucencyPass::TPT_TranslucencyHoldout: TranslucencyMeshPass = EMeshPass::TranslucencyHoldout; break; case ETranslucencyPass::TPT_AllTranslucency: TranslucencyMeshPass = EMeshPass::TranslucencyAll; break; } check(TranslucencyMeshPass != EMeshPass::Num); return TranslucencyMeshPass; }
🔤 기호 사전 — 패스 매핑
• EMeshPass::Type = "메시를 어느 그리기 통에 넣을지"를 나타내는 enum 타입이야.
• ETranslucencyPass::Type = "반투명 작업 종류"를 나타내는 enum 타입이야.
• switch (TranslucencyPass) = TranslucencyPass 값이 뭔지 보고 여러 갈래 중 하나를 고르는 문법이야.
• case ...: = 이 값이면 여기로 오라는 표지판이야.
• break = 이 갈래 일을 끝냈으니 switch 밖으로 나가라는 말이야.
• check(...) = 개발 중 틀린 상태면 바로 터뜨려서 잡는 언리얼 검사야.
• return TranslucencyMeshPass = 고른 mesh pass를 호출한 쪽에 돌려준다.
🔁 이제 다시 보자. TPT_TranslucencyStandard는 EMeshPass::TranslucencyStandard로, AfterDOF는 EMeshPass::TranslucencyAfterDOF로, All은 EMeshPass::TranslucencyAll로 바뀐다. 즉 셀로판지 종류표가 실제 그리기 명령 통으로 변환되는 장면이야.

이게 왜 중요하냐면, mesh pass가 갈라져야 정렬, 셰이더, 블렌드 상태, 렌더타깃을 따로 묶을 수 있어. 불투명 BasePass는 GBuffer를 채우는 통이고, 반투명 mesh pass는 이미 깔린 장면 위에 섞는 통이야. 이름에 BasePass가 다시 보인다고 헷갈리면 안 돼. 언리얼은 FBasePassMeshProcessor 같은 공통 장비를 재사용하지만, TranslucencyPass 값을 넘겨서 반투명 전용 상태로 굴린다. 식당 비유로 말하면 같은 집게를 써도, 스티커 붙이는 작업대와 셀로판지 겹치는 작업대는 다르다는 뜻이야.

3. 왜 별도 버퍼가 필요하냐 — scene color를 직접 읽을 수 없어서

반투명 셀로판지는 뒤 배경이 필요해. 근데 렌더타깃에 지금 쓰고 있는 SceneColor를 동시에 읽으면 GPU 입장에선 위험해져. 내가 쓰는 종이를 바로 읽으면서 다시 같은 종이에 쓰는 꼴이거든. 그래서 코드가 먼저 말한다. "Scene color를 scene texture로 직접 참조 못 하니 copy를 쓴다." 그리고 경우에 따라 별도 반투명 색 텍스처를 만든다. TranslucentRendering.cpp:1488

여기가 디퍼드와 크게 갈라지는 지점이야. GBuffer는 "나중에 빛 계산할 재료 정보"를 저장하는 장부였지. 반투명은 장부에 재료 하나를 적는 문제가 아니라, 이미 나온 화면 색과 섞는 문제야. 그래서 SceneColorCopyTexture가 나오고, SharedColorTexture 같은 별도 렌더타깃이 나온다. DirectX로 치면 같은 RTV를 바인딩해서 쓰면서 SRV로 동시에 읽으려 하면 안 되는 상황을 피해 가는 거야.

4. 실제 그리기 — 색은 쓰고, 깊이는 주로 읽는다

이제 내부 그리기 함수로 내려가 보자. 여기서 반투명은 렌더타깃 0번에 색을 쓴다. 깊이는 DepthRead_StencilWrite로 잡는다. 말 그대로 기존 깊이로 "앞에 막힌 건 그리지 말라"는 테스트는 하지만, 불투명처럼 depth를 확정해서 뒤를 지워버리는 식이 아니야. 셀로판지는 앞뒤로 여러 장이 겹칠 수 있으니까, 제일 가까운 한 장만 depth에 박아버리면 뒤 셀로판지가 사라진다. TranslucentRendering.cpp:1323

• View.ParallelMeshDrawCommandPasses[MeshPass] = 이 뷰에서 해당 mesh pass의 그리기 명령 묶음을 꺼내는 표기야.
• BuildRenderingCommands(...) = 실제 GPU draw command를 준비하는 호출이야.
🔁 이제 다시 보자. 먼저 색 렌더타깃을 ELoad로 열어 기존 장면 위에 쓸 준비를 하고 → depth는 읽기 중심으로 붙이고 → 반투명 패스를 mesh pass로 바꾼 뒤 → 그 통의 draw command를 만든다. 즉 이미 붙은 스티커 배경 위에 셀로판지를 따로 올리는 장면이야.

이 코드만 봐도 반투명이 왜 포워드 느낌인지 보여. GBuffer에 재질을 적고 끝나는 게 아니라, 각 반투명 메시를 다시 draw command로 꺼내서 색 버퍼에 바로 영향을 준다. 라이트와 재질 처리를 위해 uniform parameter도 따로 채우지만, 큰 구조는 "화면에 직접 섞는 draw"야. 그래서 비용도 가볍지 않아. 반투명 픽셀이 화면을 많이 덮으면, 불투명처럼 Early-Z로 확 줄이기 어렵고, 셰이더가 여러 번 돈다. 유리 파티클이 화면 전체를 덮으면 프레임이 떨어지는 이유가 여기야.

5. 섞는 법 — 알파 블렌드 상태가 진짜 핵심이다

반투명은 결국 색을 섞는 문제야. 불투명은 "내 색으로 덮어"면 되지만, 반투명은 "내 색 일부 + 뒤 배경 일부"야. 그 공식이 blend state에 박힌다. BLEND_Translucent에서 언리얼이 어떤 블렌드를 쓰는지 보자. BasePassRendering.cpp:355

case BLEND_Translucent: case BLEND_TranslucentColoredTransmittance: // When Substrate is disabled, this falls back to simple Translucency. if (InTranslucencyPassType != ETranslucencyPass::TPT_TranslucencyHoldout) { // Note: alpha channel used by separate translucency, storing how much of the background should be added when doing the final composite // The Alpha channel is also used by non-separate translucency when rendering to scene captures, which store the final opacity DrawRenderState.SetBlendState(TStaticBlendState<CW_RGBA, BO_Add, BF_SourceAlpha, BF_InverseSourceAlpha, BO_Add, BF_Zero, BF_InverseSourceAlpha>::GetRHI()); }
🔤 기호 사전 — 알파 블렌드
• case BLEND_Translucent: = 재질 blend mode가 일반 반투명이면 이 갈래로 온다는 뜻이야.
• InTranslucencyPassType = 지금 처리 중인 반투명 패스 종류야.
• != = 같지 않다는 비교야.
• DrawRenderState.SetBlendState(...) = draw할 때 쓸 블렌드 공식을 GPU 상태에 넣는 호출이야.
• TStaticBlendState<...> = 컴파일 시점에 정해진 블렌드 상태 템플릿이야.
• BF_SourceAlpha = 새로 그리는 셀로판지의 알파를 비율로 쓰겠다는 뜻이야.
• BF_InverseSourceAlpha = 1 - 알파를 비율로 쓰겠다는 뜻이야.
• GetRHI() = RHI 레벨에서 쓸 실제 GPU 상태 객체를 꺼내는 호출이야.
🔁 이제 다시 보자. BLEND_Translucent 재질이면 holdout이 아닌 한 SetBlendState로 SourceAlpha와 InverseSourceAlpha 조합을 건다. 풀어 읽으면 "새 셀로판지 색은 알파만큼, 뒤 배경은 1-알파만큼 남겨서 더해"라는 뜻이야.

이게 바로 GBuffer가 곤란한 이유야. GBuffer에는 아직 "뒤 배경 최종 색"이 없어. GBuffer 단계에서는 색 하나를 최종 화면에 섞는 게 아니라, 나중에 조명 계산할 재료 정보를 적고 있을 뿐이야. 그런데 BF_InverseSourceAlpha는 이미 있는 destination color, 즉 뒤 배경 색이 필요해. 셀로판지를 섞으려면 뒤 그림이 이미 있어야 한다는 말이지. 그래서 반투명은 불투명과 라이팅이 어느 정도 끝난 뒤, scene color를 배경으로 삼아 따로 온다.

6. 정렬 — 셀로판지는 뒤에서 앞으로 붙여야 한다

이제 가장 렌더링다운 문제가 나온다. 반투명 두 장이 겹치면 순서가 결과를 바꿔. 뒤 셀로판지를 먼저 섞고, 앞 셀로판지를 나중에 섞어야 자연스럽다. 그래서 언리얼은 반투명 mesh draw command에 정렬 키를 만든다. 여기엔 우선순위, 거리 오프셋, primitive 안 mesh id가 들어간다. BasePassRendering.cpp:438

FMeshDrawCommandSortKey CalculateTranslucentMeshStaticSortKey(const FPrimitiveSceneProxy* RESTRICT PrimitiveSceneProxy, uint16 MeshIdInPrimitive) { uint16 SortKeyPriority = 0; float DistanceOffset = 0.0f; if (PrimitiveSceneProxy) { const FPrimitiveSceneInfo* PrimitiveSceneInfo = PrimitiveSceneProxy->GetPrimitiveSceneInfo(); SortKeyPriority = (uint16)((int32)PrimitiveSceneInfo->Proxy->GetTranslucencySortPriority() - (int32)SHRT_MIN); DistanceOffset = PrimitiveSceneInfo->Proxy->GetTranslucencySortDistanceOffset(); } FMeshDrawCommandSortKey SortKey; SortKey.Translucent.MeshIdInPrimitive = MeshIdInPrimitive; SortKey.Translucent.Priority = SortKeyPriority; SortKey.Translucent.Distance = *(uint32*)(&DistanceOffset); // View specific, so will be filled later inside VisibleMeshCommands. return SortKey; }
🔤 기호 사전 — 반투명 정렬 키
• FMeshDrawCommandSortKey = draw command를 어떤 순서로 실행할지 비교할 때 쓰는 열쇠야.
• const FPrimitiveSceneProxy* = 렌더 스레드가 보는 primitive 대리 객체를 가리키는 포인터야.
• uint16 = 16비트짜리 부호 없는 정수야.
• RESTRICT = 이 포인터 별칭을 최적화할 수 있게 알려주는 힌트야.
• GetTranslucencySortPriority() = 사용자가 지정할 수 있는 반투명 정렬 우선순위를 가져오는 호출이야.
• GetTranslucencySortDistanceOffset() = 거리 정렬에 더할 오프셋을 가져오는 호출이야.
• (uint16) / (int32) = 값을 다른 숫자 타입으로 바꿔 읽는 캐스팅이야.
• *(uint32*)(&DistanceOffset) = float 비트를 uint32처럼 꺼내 정렬 키 칸에 넣는 낮은 레벨 표기야.
🔁 이제 다시 보자. PrimitiveSceneProxy가 있으면 정렬 우선순위와 거리 오프셋을 읽고 → SortKey.Translucent 칸에 mesh id, priority, distance를 채워 → 그 키를 돌려준다. 셀로판지마다 "몇 번째로 붙일지" 번호표를 만드는 장면이야.

정렬이 완벽하냐고 물으면, 아니야. 삼각형끼리 서로 교차하거나, 한 물체 안에서 앞뒤가 꼬이면 단순 객체 정렬로는 완벽히 못 풀어. 그래서 언리얼에도 OIT 같은 별도 경로가 있고, OIT::IsSortedPixelsEnabled 같은 코드가 보인다. 하지만 기본 감각은 이거야. 불투명은 depth buffer가 순서를 해결해주지만, 반투명은 blend 순서가 결과라서 정렬 키가 필요하다. 서버로 치면 TCP가 순서를 보장해주는 패킷과, 네가 직접 시퀀스 번호를 붙여 재정렬해야 하는 UDP 패킷의 차이에 가깝다.

8. 우리 서버·DirectX 랑 비교

우리 서버 감각으로 보면 반투명은 "순서 보장 없는 이벤트를 나중에 합성하는 시스템"이야. 불투명은 비교적 단순해. 가까운 놈이 이기고, depth buffer가 판정해. 서버로 치면 "마지막 상태 하나만 남기면 되는 위치 스냅샷"에 가까워. 반투명은 로그 누적이야. 이벤트 순서가 바뀌면 결과도 바뀐다. +10% 버프, -30% 디버프, 최종 배율 적용 같은 게 순서에 따라 달라지는 것처럼, 알파 블렌드도 destination color가 무엇이냐에 따라 결과가 달라져. DirectX 경험으로 보면 더 직관적이야. 불투명은 depth write 켜고 렌더타깃을 덮는다. 반투명은 보통 depth test는 하되 depth write는 조심하고, blend state를 켠다. 그리고 SRV/RTV 충돌을 피하려고 scene color copy나 별도 render target을 쓴다. 언리얼 코드에서 그 흔적이 그대로 보였어. SceneColor 플래그를 빼고, copy texture를 쓰고, FRenderTargetBinding(... ELoad)로 기존 장면 위에 그린다. 서버에서 "같은 컨테이너를 순회하면서 동시에 수정하지 말고 복사본이나 큐를 써라"와 비슷한 감각이야. 읽는 것과 쓰는 것을 분리해야 꼬이지 않는다.

9. 이 챕터에서 딱 이것만

  • 디퍼드 GBuffer는 픽셀당 대표 표면 하나를 저장하는 데 강해서, 여러 장 겹치는 반투명을 담기 어렵다.
  • 반투명은 이미 만들어진 scene color 위에 알파 블렌드로 섞어야 하므로 별도 포워드식 mesh pass로 간다.
  • 언리얼은 Standard, AfterDOF, AfterMotionBlur, Holdout 같은 반투명 패스를 나눠서 실행한다.
  • 별도 반투명은 scene color copy와 별도 color/depth 리소스를 써서 읽기/쓰기 충돌과 후처리 순서를 피한다.
  • 반투명은 blend 순서가 결과를 바꾸므로 TranslucencySortPriority, distance offset 같은 정렬 키를 챙긴다.

10. 마지막으로 셀로판지 비유 다시 접기

불투명 렌더링은 스티커야. 제일 앞 스티커가 붙으면 뒤는 안 보여. 그래서 GBuffer에는 "이 픽셀의 제일 앞 스티커 정보"만 적어도 된다. 반투명 렌더링은 셀로판지야. 뒤 배경이 있어야 색이 정해지고, 여러 장이면 순서가 결과를 바꾼다. 그래서 언리얼은 스티커 작업을 끝낸 뒤, 셀로판지를 따로 꺼내서, 작업지와 복사본을 준비하고, 번호표대로 겹친다. 이게 이 챕터의 전부야. TranslucentRendering.cpp가 길어 보이는 이유도 이제 보여. 반투명 자체가 한 기능이 아니라, "언제", "어디에", "어떤 순서로", "어떤 블렌드로"를 모두 품은 합성 문제이기 때문이야.

🎯 원리 한 줄 요약

반투명은 GBuffer에 한 표면으로 눕힐 수 없는 셀로판지라서, 언리얼은 불투명 디퍼드 결과 위에 별도 포워드식 패스로 그리고, 알파 블렌드와 정렬 키로 순서를 관리한다.
