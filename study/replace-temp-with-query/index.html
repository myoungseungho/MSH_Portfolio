Refactoring #14

Replace Temp with Query

임시 변수를 질의 함수로 바꾸기

임시 변수를 질의로 바꾼다는 게 무슨 뜻이에요?
계산 결과를 담는 임시 변수 대신, 그 계산을 수행하는 메서드를 만드는 것이에요.

예를 들어, basePrice라는 변수에 가격 계산 결과를 저장해서 여러 번 쓴다고 해봐요. 이걸 GetBasePrice()라는 메서드로 바꾸는 거예요.

변수를 읽는 대신, 메서드를 호출해서 값을 얻는 방식이죠.
왜 굳이 그렇게 해야 하죠? 변수가 더 간단하지 않나요?
좋은 질문이에요! 이 기법의 핵심 이점들이 있어요:

1. 재사용성
메서드로 만들면 다른 곳에서도 같은 계산을 쓸 수 있어요. 변수는 그 함수 안에서만 유효하죠.

2. 의도 표현
GetBasePrice()는 "기본 가격을 구한다"는 의도가 명확해요. 변수 이름만으로는 "어떻게 계산되는지"가 안 보이죠.

3. Extract Method 준비
긴 메서드를 쪼갤 때, 임시 변수가 많으면 추출이 어려워요. 질의 메서드로 바꾸면 추출이 쉬워집니다.

📋 비유: 계산기 vs 메모

메모에 "123 + 456 = 579"라고 적어두고 계속 보는 것 vs
필요할 때마다 계산기로 123 + 456을 치는 것

메모(변수)는 빠르지만 그 자리에서만 유효해요. 계산기(질의)는 어디서든 같은 답을 줍니다.
성능 문제는 없나요? 매번 계산하면 느리지 않을까요?
자주 나오는 걱정이에요. 하지만:

1. 대부분의 경우 체감 안 됨
현대 컴퓨터에서 단순 계산 몇 번 더 하는 건 무시할 수준이에요.

2. 성능 문제는 측정 후 판단
"느릴 것 같다"가 아니라, 실제로 프로파일링해서 병목인지 확인하세요.

3. 필요하면 캐싱
정말 느리다면 메서드 내부에서 캐싱하면 돼요. 호출하는 쪽은 몰라도 됩니다.

⚠️ 진짜 주의해야 할 경우

반복문 안에서 매번 호출되는 무거운 계산일 때만 조심하세요.

예: 10만 번 도는 루프 안에서 DB 조회를 매번 한다? 그건 문제.

하지만 단순한 수식 계산? 걱정 안 해도 돼요.
언제 이 기법을 쓰고, 언제 변수를 그대로 두나요?
질의로 바꾸면 좋은 경우:

- 같은 계산이 여러 메서드에서 필요할 때
- 계산 로직에 이름을 붙여서 의도를 드러내고 싶을 때
- 메서드를 추출하려는데 임시 변수가 방해될 때
- 변수가 한 번만 할당되고 변하지 않을 때

변수를 유지하는 게 나은 경우:

- 루프 안에서 여러 번 사용되는 무거운 계산
- 계산 결과가 중간에 변할 수 있을 때 (스냅샷 필요)
- 디버깅 시 중간값을 확인해야 할 때

💡 판단 기준

"이 값이 다른 곳에서도 필요할까?"
"이 계산에 이름을 붙이면 더 명확해질까?"

둘 다 Yes라면 질의 메서드로 바꾸세요.
진행 절차를 알려주세요.
단계별 진행:

1단계: 변수가 한 번만 할당되는지 확인
→ 여러 번 할당되면 먼저 분리해야 해요

2단계: 계산 로직을 메서드로 추출
→ GetBasePrice() 같은 이름으로 메서드 생성

3단계: 변수 사용처를 메서드 호출로 교체
→ basePrice를 쓰던 곳을 GetBasePrice()로 변경

4단계: 테스트
5단계: 변수 선언 제거

IDE의 리팩토링 기능을 활용하면 자동으로 처리해줘요.

📌 Replace Temp with Query 핵심 정리

  • 임시 변수 대신 계산을 수행하는 메서드 사용
  • 재사용성과 의도 표현이 좋아짐
  • Extract Method의 선행 작업으로 유용
  • 성능은 실제 측정 후 판단할 것
  • 무거운 계산이 반복되는 경우만 주의
