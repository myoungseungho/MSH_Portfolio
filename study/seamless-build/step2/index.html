STEP 2 — 게이트: 재접속을 숨긴다

클라는 게이트 1개에만 붙는다. 칸을 넘어도 재접속하지 않는다 — 담당 서버 교체는 게이트가 뒤에서 몰래 한다.

STEP 2의 목적

STEP 1의 결핍("경계마다 끊고 재접속 = 프리즈")을 푼다. 클라와 존 서버들 사이에 게이트(리버스 프록시)를 둬서, 클라의 연결을 하나로 고정하고 담당 서버 교체를 숨긴다.

🎥 실제 작동 — 3D 뷰어 (STEP 2)

STEP 1과 같은 9칸이지만, 경계를 넘을 때 빨간 '재접속(프리즈)'이 아니라 초록 '게이트가 담당 서버 교체 (연결은 그대로)' 배너가 뜬다. 클라(뷰어)는 게이트에 연결 1개로 끝까지 — 재접속 0회.

✅ 지금 되는 것

· 클라는 게이트(:9000)에 연결 1개 유지, 칸을 넘어도 재접속 0회

· 경계를 넘으면 게이트가 뒤에서 담당 존 서버를 몰래 교체(연결은 그대로) → 프리즈 소멸

· 9칸 색·번호, 머리 위 점(담당 존 색)은 STEP 1과 동일

❌ 아직 안 되는 것 (다음 단계에서)

· 여전히 옆 칸이 안 보임(연결 문제만 풀림, 데이터는 그대로) → STEP 3 고스팅

· 경계 너머 상호작용/전투 없음 → STEP 4·5

Part 1. 게이트는 무엇을 하나?

STEP 1은 칸을 넘을 때마다 클라가 재접속했다. 어떻게 없애지?

클라와 서버들 사이에 중개소(게이트)를 하나 둔다. 클라는 게이트에만 붙고, 담당 존 서버가 바뀌는 건 게이트가 뒤에서 처리한다. 클라 입장에선 연결이 처음부터 끝까지 하나다.

STEP 1: 클라 ──(칸 넘으면 끊고 재접속)──▶ 존 서버 ← 프리즈가 클라에 노출 STEP 2: 클라 ──(항상 연결)──▶ 게이트 ──(뒤만 교체)──▶ 존 서버 ← 클라는 모름

Part 2. 게이트가 담당 서버를 어떻게 정하나?

게이트는 클라가 어느 칸인지 어떻게 알지?

클라가 보내는 이동 패킷(CM_MOVE) 안의 위치를 게이트가 들여다본다. 그 위치로 칸을 계산하고, 칸이 바뀌면 뒤 서버를 갈아끼운다.

// 게이트: 클라의 이동을 보고, 칸이 바뀌면 백엔드만 교체
var (type, data) = await ReadFramed(cli); // 클라 → 게이트 var m = Deserialize<CM_MOVE>(data); int nz = ZoneOf(m.X, m.Y); if (nz != zone) { // ★ 뒤 연결만 교체 — 클라 연결(cli)은 건드리지 않는다 downCts.Cancel(); backend.Dispose(); zone = nz; backend = await ConnectBackend(9001 + zone); _ = Pump(backend.GetStream(), cli, ...); // 새 백엔드→클라 파이프 재시작 } await SendFramed(backend.GetStream(), type, data); // 게이트 → 현재 백엔드

Part 3. 연결 ↔ 세션의 분리

담당 서버가 바뀌는데 왜 클라 연결은 안 끊기지?

게이트가 연결을 둘로 나눠 들기 때문이다. 앞 연결(클라↔게이트)과 뒤 연결(게이트↔존 서버). 담당이 바뀌면 뒤 연결만 끊고 새 서버에 다시 붙는다. 앞 연결은 손도 안 대니 클라는 아무 일 없이 이어진다.

이게 '연결(전화선)'과 '세션(대화)'의 분리다. 전화선(뒤)을 바꿔도 대화(앞)는 안 끊긴다.

[C] → 이동 (11,5) (연결은 그대로) [GATE] C1 zone 0→1 : 백엔드 교체 (클라는 그대로!) [C] → 이동 (21,5) (연결은 그대로) [GATE] C1 zone 1→2 : 백엔드 교체 (클라는 그대로!) [C] 산책 끝 — 한 번도 재접속 안 했다

❌ 남은 결핍: 연결 문제는 풀렸지만 데이터 문제는 그대로 — 게이트는 지금 붙은 한 서버 데이터만 전달하니 옆 칸은 여전히 안 보임. → STEP 3 고스팅.

★ 이야기로 (A→Z)

네트워크를 몰라도 읽히게.

STEP 1에서 저는 월드를 9칸으로 나눠 부하를 나눴습니다. 근데 클라가 칸을 넘을 때마다 지금 서버와 연결을 끊고 새 서버에 다시 붙어야 했습니다. 그 재접속하는 잠깐이 프리즈로 보였습니다. 유저가 벽에 부딪히는 느낌이죠. 이걸 없애고 싶었습니다.

제가 떠올린 방법은, 클라와 서버들 사이에 '중개소'를 하나 두는 것이었습니다. 클라는 이 중개소(게이트)에만 붙습니다. 그리고 담당 서버가 바뀌는 지저분한 일은 중개소가 뒤에서 처리합니다.

리버스 프록시 / 게이트 — 손님(클라)을 대신해 뒤의 여러 서버 중 알맞은 곳에 연결해주는 중개 서버입니다. 손님은 중개소 하나만 상대하면 됩니다.

게이트가 어느 서버로 보낼지는, 클라가 보내는 이동 패킷 안의 위치를 보고 정했습니다. 위치로 칸을 계산해, 칸이 바뀌면 뒤 서버를 갈아끼웁니다. 여기서 핵심은, 게이트가 연결을 둘로 나눠 든다는 점입니다. 앞쪽(클라와의 연결)과 뒤쪽(존 서버와의 연결)입니다. 담당이 바뀌면 뒤쪽만 끊고 새로 연결하고, 앞쪽은 절대 건드리지 않습니다.

연결 ↔ 세션 분리 — '연결'은 전화선, '세션'은 대화 내용입니다. 뒤 전화선을 몰래 바꿔도 앞 전화선(클라와의)은 그대로라, 대화가 안 끊깁니다.

실제로 돌려보니, 클라는 걷는 내내 '연결은 그대로'였고 한 번도 재접속하지 않았습니다. 대신 게이트 로그에는 'zone 0→1 백엔드 교체'가 조용히 찍혔습니다. 프리즈가 사라진 겁니다.

그런데 이걸로 다 풀린 건 아니었습니다. 클라는 여전히 옆 칸이 안 보였습니다. 게이트는 지금 붙어있는 한 서버의 데이터만 전달할 뿐, 옆 칸 서버의 정보를 합쳐주진 않으니까요. 여기서 깨달은 게 이 스텝의 교훈입니다: "연결 문제와 데이터 문제는 다르다." 게이트는 연결 문제(재접속)를 풀었지만, 데이터 문제(옆 칸이 안 보임)는 손도 못 댔습니다. 그건 다음 단계 — 이웃 서버끼리 경계 부근 상태를 공유하는 '고스팅'(STEP 3)의 몫입니다.

핵심 정리

  • 게이트(리버스 프록시)를 클라와 존 서버 사이에 둔다. 클라는 게이트에만 붙는다.
  • 게이트가 클라 위치를 보고 담당 존 서버를 판단 → 바뀌면 '뒤 연결만' 교체(앞 연결 유지).
  • 연결(전화선) ↔ 세션(대화)의 분리: 재접속이 클라에게서 사라짐(프리즈 소멸).
  • 단, 연결 문제만 해결. 옆 칸 안 보임(데이터 문제)은 그대로 → STEP 3 고스팅.
  • 교훈: 연결 문제와 데이터 문제는 다르다.
