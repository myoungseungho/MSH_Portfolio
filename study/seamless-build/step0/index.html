STEP 0 — 첫 삽은 왜 '파이프 뚫기'인가

왜 9대가 아니라 1대부터, 그 안에서도 왜 틱·몬스터가 아니라 '두 프로세스가 바이트를 주고받기'가 첫 삽인지. Walking Skeleton과 핵심 C# 코드.

이 문서의 약속

우리는 "왜 여기에 삽을 떠야 하는지" 모르면 땅을 파지 않는다. 그래서 코드보다 먼저 '문제의식'을 세운다. 코드는 그 결론의 최소 형태(Walking Skeleton)만 소개한다 — 전체 구현이 아니라 뼈대다.

Part 1. 왜 9대가 아니라 '1대'부터?

목표는 서버 9대 분산인데, 왜 1대짜리부터 만들어?

손은 9대를 짜고 싶겠지만, 물어보자. 경계를 넘었을 때 그게 '심리스하게' 된 건지 '깨진' 건지, 뭘 기준으로 판단할 거야? 매끈한 단일 월드를 한 번도 안 본 상태에선 비교 대상이 없어. 그래서 STEP 0은 이후 모든 스텝을 재는 기준선(baseline)이야.

그리고 9대가 하는 일 = 1대가 하는 일(틱·이동·브로드캐스트·몬스터) + 분산의 어려움이야. 1대짜리도 없이 9대를 짜다 버그가 나면 '게임 로직 버그냐 분산 버그냐'를 동시에 디버깅하게 돼.

그래서 STEP 0의 세 가지 존재 이유:

① 기준선 — '이만큼 매끈한가?'로 이후를 잰다.

② 토대 — 틱·이동·브로드캐스트는 9대든 1대든 어차피 다 해야 한다.

③ 변수 분리 — 게임 로직을 먼저 고정하면, STEP 1부터의 버그는 100% 분산 버그. 범인이 절반으로 준다.

Part 2. STEP 0 안에서도 — 왜 틱·몬스터가 아니라 '이것'부터?

STEP 0엔 틱, 좌표 딕셔너리, 브로드캐스트, 몬스터가 있잖아. 뭐부터 파?

하나씩 반문해보자.

틱 루프부터 짜면 콘솔에 뭐가 보여? tick 1... tick 2... — 혼자 도는 시계야. 멀티플레이어의 본질(두 프로세스의 대화)이 안 보여.

몬스터 AI부터 짜면? 배회하는데 그걸 봐줄 클라가 없어. 누구한테 위치를 보내지?

이제 핵심 질문: 틱 결과 전송도, 몬스터 위치 전파도, 브로드캐스트도 — 이 모든 게 전제하는 단 하나는?

"두 프로세스가 바이트를 주고받을 수 있다."

이게 안 되면 나머지 전부가 공중부양이야. 그리고 이건 STEP 0에서 가장 위험한 미지수(소켓·포트·async accept·프레이밍)이기도 해. 위험한 건 코드 20줄일 때 부딪히는 게 낫지, 틱·몬스터 코드 수백 줄 밑에 파묻힌 뒤가 아니라.

🦴 Walking Skeleton 원칙

기능별로 완성해서 마지막에 합치지 않는다. 가장 얇지만 끝에서 끝까지 관통하는 슬라이스를 먼저 만들고, 거기에 살을 붙인다.

그 첫 슬라이스가 바로 '파이프 뚫기' — 서버가 listen하고, 클라가 connect해서, 메시지 하나가 건너가 콘솔에 찍히는 것. 틱도 몬스터도 브로드캐스트도 그 뒤다.

Part 3. 첫 삽은 정확히 뭐고, '됐다'는 뭘로 아나?

그래서 최소 형태가 뭐야?

서버 프로세스가 listen하고, 클라 프로세스가 connect해서, 이동 메시지 딱 하나를 보내면, 서버가 받아서 콘솔에 찍는다. 틱 없음, 브로드캐스트 없음, 몬스터 없음, 클라도 하나뿐.

이 20~30줄이 증명하는 것: 프로세스 경계를 넘는 바이트, 소켓/포트/connect·accept, async 수신, 그리고 한 메시지가 선 위에서 어떻게 생겼고 수신자가 어디서 끝나는지 아는가(프레이밍).

👁️ "됐다"의 그림 [클라 콘솔] → sent MoveRequest(x=10, y=5) ← playerId 안 담음 [서버 콘솔] ← recv from P1 (소켓으로 앎): move(10,5) owner=S0 └ 신원은 '연결'이 증명 └ 주인은 서버가 정함(지금은 늘 S0)

Part 4. 3가지 설계 — 패킷 · 프레이밍 · 역할

파이프 하나 뚫는데 정할 게 뭐가 있어? 그냥 소켓 열면 되잖아.

메시지 하나를 보내려는 순간, 세 가지를 반드시 답해야 해: ① 패킷이 뭘 담나(+누가 신원을 정하나) ② 한 패킷이 어디서 끝나나(프레이밍) ③ 누가 listen이고 누가 connect냐. 하나씩 짚자. (C#, .NET 콘솔)

// ① 패킷 — 방향에 따라 둘로 갈린다 (Shared/Packets.cs)
enum PacketType : byte { MoveRequest = 1, ActorState = 2 } // 메시지 '종류 번호' // 클라 → 서버 (요청): playerId 없음(서버가 소켓으로 앎), authority 없음(서버가 정함) readonly record struct MoveRequest(float X, float Y); // 서버 → 클라 (상태 방송): '누구'인지 '주인이 누구'인지 서버가 찍어서 내려줌 readonly record struct ActorState(int PlayerId, float X, float Y, byte AuthorityServerId);

왜 playerId를 클라가 안 보내나? 서버는 접속 순간 그 소켓에 playerId를 배정하고 기억해둬. 그래서 그 소켓으로 온 요청은 이미 누군지 앎. 만약 클라가 playerId를 담으면? 악성 클라가 "나 5번이야, 저기로 이동"이라고 남의 캐릭을 조종할 수 있어. 신원은 '연결'이 증명하지, 클라의 자기신고로 정하지 않는다 — 이게 서버 권위의 첫 갈림길.

AuthorityServerId는 왜 ActorState(방송)에만? '주인이 누구'는 서버가 정하는 값이라 클라 요청엔 자리가 없어. 값은 STEP 0에서 늘 0(서버 1대)이지만 지금 넣어두면, STEP 3~4에서 클라가 머리 위 색점을 그 값으로 칠할 때 패킷 포맷 대공사를 안 해도 돼.

// ② 프레이밍 — [길이 4][타입 1][데이터...] (TCP는 스트림이라 경계를 우리가 그린다)
"무조건 8바이트 읽어"는 MoveRequest 하나뿐일 땐 되지만, 가변 패킷(채팅·방송)이 오면 무너진다: 선 위: [MoveReq 8B][Chat "hello" 5B] ← TCP라 한 덩어리로 뭉쳐 도착 8바이트씩: [MoveReq ✓][hello + 다음 3B ✗] → 이후 전부 밀림 = desync 💥 길이 접두사: [8][MoveReq][5][hello] → 항상 정확히 한 패킷씩 ✓
// [길이 4][타입 1][데이터]. 길이=어디서 끝나나, 타입=무슨 종류냐. static async Task SendFramedAsync(NetworkStream s, PacketType type, byte[] data) { int len = 1 + data.Length; // 타입 1 + 데이터 await s.WriteAsync(BitConverter.GetBytes(len)); // [길이 4] await s.WriteAsync(new[] { (byte)type }); // [타입 1] await s.WriteAsync(data); // [데이터] } static async Task<(PacketType type, byte[] data)> ReadFramedAsync(NetworkStream s) { int len = BitConverter.ToInt32(await ReadExactlyAsync(s, 4)); // 길이 var body = await ReadExactlyAsync(s, len); // 타입+데이터 통째로 return ((PacketType)body[0], body[1..]); // 첫 바이트 = 타입 } // TCP는 '요청한 만큼'이 아니라 '지금 온 만큼'을 준다 → 다 모일 때까지 루프 static async Task<byte[]> ReadExactlyAsync(NetworkStream s, int n) { var buf = new byte[n]; int off = 0; while (off < n) { int read = await s.ReadAsync(buf.AsMemory(off, n - off)); if (read == 0) throw new IOException("연결 끊김"); off += read; } return buf; }

길이는 "어디서 끝나나"(경계), 타입은 "무슨 종류냐"(해석법). 받는 쪽은 길이로 한 덩어리를 떼고 → 타입으로 switch 갈래를 나눠. 이 패킷 하나만 보면 과하지만, 가변 패킷이 오는 순간 필수라 지금 깐다. (.NET 7+엔 Stream.ReadExactlyAsync 내장이지만 원리를 보려 손으로 폈다.)

// ③ 역할 — 서버 listen / 클라 connect. (프레이밍 함수는 Connection 클래스로 감싸 방향-무관)
// ── Server: listen하고, 접속마다 async 수신 루프 ── var listener = new TcpListener(IPAddress.Loopback, 9001); // 클라용 포트 listener.Start(); int nextId = 1; while (true) { var client = await listener.AcceptTcpClientAsync(); int playerId = nextId++; // ★ 접속 순간 '서버가' 신원 배정 (클라 아님) _ = HandleClientAsync(client, playerId); // ★ await 안 함 → 다음 accept를 안 막음 } static async Task HandleClientAsync(TcpClient client, int playerId) { using var stream = client.GetStream(); while (true) { var (type, data) = await ReadFramedAsync(stream); if (type == PacketType.MoveRequest) { var m = Codec.DecodeMove(data); // 신원은 연결이 증명 → playerId는 서버가 앎. 주인도 서버(S0). Console.WriteLine($"[S0] ← from P{playerId}: move({m.X},{m.Y}) owner=S0"); } } } // ── Client: connect하고 MoveRequest 하나 보냄 ── using var conn = new TcpClient(); await conn.ConnectAsync(IPAddress.Loopback, 9001); var data = Codec.EncodeMove(new MoveRequest(10, 5)); await SendFramedAsync(conn.GetStream(), PacketType.MoveRequest, data); // playerId 안 담음 Console.WriteLine("[C] → sent MoveRequest(10, 5)");

왜 _ = HandleClientAsync(...)로 await를 안 걸까? await를 걸면 그 클라 수신 루프가 끝날 때까지(=영원히) 다음 accept를 못 해. '막지 않고' 던져두고 곧장 다음 접속을 받아 — 한 스레드로 여러 클라를 저글링.

역할은 지금 왜 이렇게 잡나? 첫 삽엔 서버 listen·클라 connect만 쓰지만, STEP 1에선 서버가 둘 다 해(이웃에게 listen도, connect도). 그래서 프레이밍을 방향-무관 Connection 추상으로 감싸두면 피어 연결을 갈아엎지 않고 덧붙여. 그때 중복 연결(A→B와 B→A)을 막으려 "번호 작은 서버가 큰 서버에게만 connect" 같은 규칙을 둔다.

Part 5. 첫 삽이 '남긴 결핍' — 다음 삽의 동기

파이프는 뚫렸어. 근데 이건 아직 게임이 아니잖아?

맞아. 그리고 그 '안 되는 것'이 정확히 다음 삽을 가리켜:

❌ 클라가 둘이면? 서버가 받기만 하고 아무한테도 안 뿌려 → 둘이 서로 못 봄. → 다음 삽 = 브로드캐스트.

❌ 클라가 가만있으면 세상이 안 흘러(몬스터도 안 움직임) → 다음 삽 = 틱(심장).

보이지? STEP 0조차 미시적으로 '실패가 목차'로 쪼개진다. 파이프 → 브로드캐스트 → 틱 → 몬스터 순으로 살을 붙이면, 그게 STEP 0 완성이야.

핵심 정리

  • 9대가 아니라 1대부터: ① 심리스를 잴 기준선 ② 어차피 필요한 토대 ③ 게임로직을 고정해 이후 버그를 '분산 버그'로 좁힘.
  • STEP 0 안의 첫 삽은 틱·몬스터가 아니라 '두 프로세스가 바이트를 주고받기' — 나머지 전부가 그 위에 선다(Walking Skeleton).
  • 메시지 하나를 보내려면 세 가지를 답해야 한다: ① 패킷(방향 따라 MoveRequest/ActorState) ② 프레이밍 [길이][타입][데이터] ③ 역할(listen·connect).
  • 신원은 '연결'이 증명한다 — playerId는 클라가 안 보내고 서버가 소켓으로 안다(서버 권위). authority도 서버가 정한다.
  • 프레이밍의 길이=경계, 타입=종류. 가변 패킷이 오는 순간 필수(desync 방지). AuthorityServerId는 값이 0이어도 지금 넣어 STEP 3 색점을 공짜로.
  • accept 루프는 클라 핸들러를 await하지 않는다 — 한 스레드로 여러 클라를 저글링하기 위해.
  • 첫 삽의 결핍(둘이 서로 못 봄 / 세상이 안 흐름)이 다음 삽(브로드캐스트 / 틱)을 부른다.
