STEP 0 — 첫 삽은 왜 '파이프 뚫기'인가

왜 9대가 아니라 1대부터, 그 안에서도 왜 틱·몬스터가 아니라 '두 프로세스가 바이트를 주고받기'가 첫 삽인지. Walking Skeleton과 핵심 C# 코드.

이 문서의 약속

우리는 "왜 여기에 삽을 떠야 하는지" 모르면 땅을 파지 않는다. 그래서 코드보다 먼저 '문제의식'을 세운다. 코드는 그 결론의 최소 형태(Walking Skeleton)만 소개한다 — 전체 구현이 아니라 뼈대다.

Part 1. 왜 9대가 아니라 '1대'부터?

목표는 서버 9대 분산인데, 왜 1대짜리부터 만들어?

손은 9대를 짜고 싶겠지만, 물어보자. 경계를 넘었을 때 그게 '심리스하게' 된 건지 '깨진' 건지, 뭘 기준으로 판단할 거야? 매끈한 단일 월드를 한 번도 안 본 상태에선 비교 대상이 없어. 그래서 STEP 0은 이후 모든 스텝을 재는 기준선(baseline)이야.

그리고 9대가 하는 일 = 1대가 하는 일(틱·이동·브로드캐스트·몬스터) + 분산의 어려움이야. 1대짜리도 없이 9대를 짜다 버그가 나면 '게임 로직 버그냐 분산 버그냐'를 동시에 디버깅하게 돼.

그래서 STEP 0의 세 가지 존재 이유:

① 기준선 — '이만큼 매끈한가?'로 이후를 잰다.

② 토대 — 틱·이동·브로드캐스트는 9대든 1대든 어차피 다 해야 한다.

③ 변수 분리 — 게임 로직을 먼저 고정하면, STEP 1부터의 버그는 100% 분산 버그. 범인이 절반으로 준다.

Part 2. STEP 0 안에서도 — 왜 틱·몬스터가 아니라 '이것'부터?

STEP 0엔 틱, 좌표 딕셔너리, 브로드캐스트, 몬스터가 있잖아. 뭐부터 파?

하나씩 반문해보자.

틱 루프부터 짜면 콘솔에 뭐가 보여? tick 1... tick 2... — 혼자 도는 시계야. 멀티플레이어의 본질(두 프로세스의 대화)이 안 보여.

몬스터 AI부터 짜면? 배회하는데 그걸 봐줄 클라가 없어. 누구한테 위치를 보내지?

이제 핵심 질문: 틱 결과 전송도, 몬스터 위치 전파도, 브로드캐스트도 — 이 모든 게 전제하는 단 하나는?

"두 프로세스가 바이트를 주고받을 수 있다."

이게 안 되면 나머지 전부가 공중부양이야. 그리고 이건 STEP 0에서 가장 위험한 미지수(소켓·포트·async accept·프레이밍)이기도 해. 위험한 건 코드 20줄일 때 부딪히는 게 낫지, 틱·몬스터 코드 수백 줄 밑에 파묻힌 뒤가 아니라.

🦴 Walking Skeleton 원칙

기능별로 완성해서 마지막에 합치지 않는다. 가장 얇지만 끝에서 끝까지 관통하는 슬라이스를 먼저 만들고, 거기에 살을 붙인다.

그 첫 슬라이스가 바로 '파이프 뚫기' — 서버가 listen하고, 클라가 connect해서, 메시지 하나가 건너가 콘솔에 찍히는 것. 틱도 몬스터도 브로드캐스트도 그 뒤다.

Part 3. 첫 삽은 정확히 뭐고, '됐다'는 뭘로 아나?

그래서 최소 형태가 뭐야?

서버 프로세스가 listen하고, 클라 프로세스가 connect해서, 이동 메시지 딱 하나를 보내면, 서버가 받아서 콘솔에 찍는다. 틱 없음, 브로드캐스트 없음, 몬스터 없음, 클라도 하나뿐.

이 20~30줄이 증명하는 것: 프로세스 경계를 넘는 바이트, 소켓/포트/connect·accept, async 수신, 그리고 한 메시지가 선 위에서 어떻게 생겼고 수신자가 어디서 끝나는지 아는가(프레이밍).

👁️ "됐다"의 그림 [클라 콘솔] → sent Move(P1, x=10, y=5) [서버 콘솔] ← recv Move(P1, x=10, y=5) auth=S0 └─ 값은 항상 0이어도 필드는 지금부터 있다

Part 4. 핵심 코드 — 왜 이렇게 짰나

파이프 하나 뚫는데 정할 게 뭐가 있어? 그냥 소켓 열면 되잖아.

메시지 하나를 보내려는 순간, 세 가지를 반드시 답해야 해: ① 패킷이 뭘 담나 ② 한 패킷이 어디서 끝나나(프레이밍) ③ 누가 listen이고 누가 connect냐. 하나씩 코드로 보자. (C#, .NET 콘솔)

// ① Shared/Packet.cs — 서버·클라가 함께 쓰는 최소 패킷
enum PacketType : byte { Move = 1 } // 최소한만. 단 AuthorityServerId(권위 서버)는 지금 넣는다 — // 값은 STEP 0에서 항상 0이지만, STEP 3~4의 '머리 위 색점'을 공짜로 만든다. readonly record struct MovePacket( int PlayerId, float X, float Y, byte AuthorityServerId);

왜 AuthorityServerId를 지금? STEP 3에서 클라가 각 액터의 주인 색을 칠하려면 그 값이 패킷에 있어야 해. 지금 1바이트를 넣으면, 나중에 패킷 포맷을 바꾸고 직렬화를 전부 고치는 대공사를 안 해도 돼. '권위'를 STEP 0부터 일급 개념으로 취급하는 습관이기도 하고.

// ② 프레이밍 — TCP는 '스트림'이라 경계를 우리가 그려야 한다
// [4바이트 길이][페이로드]. 수신자는 먼저 길이를 읽어 '어디서 끝나는지'를 안다. static async Task SendFramedAsync(NetworkStream s, byte[] payload) { var len = BitConverter.GetBytes(payload.Length); // 길이 접두사 4바이트 await s.WriteAsync(len); await s.WriteAsync(payload); } static async Task<byte[]> ReadFramedAsync(NetworkStream s) { var lenBuf = await ReadExactlyAsync(s, 4); // 길이 4바이트 '정확히' int len = BitConverter.ToInt32(lenBuf); return await ReadExactlyAsync(s, len); // 그만큼 페이로드 '정확히' } // TCP는 '요청한 만큼'이 아니라 '지금 온 만큼'을 준다 → 다 모일 때까지 루프 static async Task<byte[]> ReadExactlyAsync(NetworkStream s, int n) { var buf = new byte[n]; int off = 0; while (off < n) { int read = await s.ReadAsync(buf.AsMemory(off, n - off)); if (read == 0) throw new IOException("연결 끊김"); off += read; } return buf; }

왜 길이 접두사? TCP는 메시지 경계가 없는 바이트 스트림이라, [패킷A][패킷B]를 보내도 뭉치거나 쪼개져 도착해. "앞 4바이트 = 이 패킷 N바이트"를 붙이면 수신자가 정확히 한 패킷을 떼어낼 수 있어. ReadExactlyAsync의 while이 바로 '찔끔찔끔 오는 걸 다 모으는' 루프고. (.NET 7+엔 Stream.ReadExactlyAsync가 내장이지만, 원리를 보려 손으로 폈다.)

// ③ Server — listen하고, 접속마다 'async 수신 루프'
var listener = new TcpListener(IPAddress.Loopback, 9001); listener.Start(); Console.WriteLine("[S0] listen :9001"); while (true) { var client = await listener.AcceptTcpClientAsync(); // 접속을 async로 기다림 _ = HandleClientAsync(client); // ★ await 안 함 → 이 클라를 기다리며 다음 accept를 막지 않음 } static async Task HandleClientAsync(TcpClient client) { using var stream = client.GetStream(); while (true) { var payload = await ReadFramedAsync(stream); // 한 패킷 통째로 var p = Packet.DecodeMove(payload); Console.WriteLine($"[S0] ← recv Move(P{p.PlayerId}, {p.X}, {p.Y}) auth=S{p.AuthorityServerId}"); } }

왜 _ = HandleClientAsync(client)로 await를 안 걸까? 여기서 await를 걸면 그 클라의 수신 루프가 끝날 때까지(=영원히) 다음 accept를 못 해. 그래서 '막지 않고' 던져두고 곧장 다음 접속을 받아. 한 스레드가 여러 클라를 저글링하는 그 구조야 — 느린 클라 하나가 전체를 얼리지 않게.

// ④ Client — connect하고 Move 하나 보냄
using var client = new TcpClient(); await client.ConnectAsync(IPAddress.Loopback, 9001); using var stream = client.GetStream(); var p = new MovePacket(PlayerId: 1, X: 10, Y: 5, AuthorityServerId: 0); await SendFramedAsync(stream, Packet.EncodeMove(p)); Console.WriteLine("[C] → sent Move(P1, 10, 5)");

Part 5. 첫 삽이 '남긴 결핍' — 다음 삽의 동기

파이프는 뚫렸어. 근데 이건 아직 게임이 아니잖아?

맞아. 그리고 그 '안 되는 것'이 정확히 다음 삽을 가리켜:

❌ 클라가 둘이면? 서버가 받기만 하고 아무한테도 안 뿌려 → 둘이 서로 못 봄. → 다음 삽 = 브로드캐스트.

❌ 클라가 가만있으면 세상이 안 흘러(몬스터도 안 움직임) → 다음 삽 = 틱(심장).

보이지? STEP 0조차 미시적으로 '실패가 목차'로 쪼개진다. 파이프 → 브로드캐스트 → 틱 → 몬스터 순으로 살을 붙이면, 그게 STEP 0 완성이야.

핵심 정리

  • 9대가 아니라 1대부터: ① 심리스를 잴 기준선 ② 어차피 필요한 토대 ③ 게임로직을 고정해 이후 버그를 '분산 버그'로 좁힘.
  • STEP 0 안의 첫 삽은 틱·몬스터가 아니라 '두 프로세스가 바이트를 주고받기' — 나머지 전부가 그 위에 선다(Walking Skeleton).
  • 메시지 하나를 보내려면 세 가지를 답해야 한다: 패킷 내용 / 프레이밍(길이 접두사) / 역할(listen·connect).
  • AuthorityServerId는 값이 0이어도 지금 넣는다 — STEP 3~4 색점을 공짜로 만든다.
  • accept 루프는 클라 핸들러를 await하지 않는다 — 한 스레드로 여러 클라를 저글링하기 위해.
  • 첫 삽의 결핍(둘이 서로 못 봄 / 세상이 안 흐름)이 다음 삽(브로드캐스트 / 틱)을 부른다.
