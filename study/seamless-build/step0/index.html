STEP 0 — 단일 서버 미니 MMO, 처음부터 끝까지

왜 9대가 아니라 1대부터인지, 그 안에서 무엇을 어떤 순서로·왜 그렇게 만들었는지. 그리고 네트워크를 몰라도 읽히는 A→Z 이야기.

STEP 0의 목적 (한 단어: 기준선)

9대로 찢기 전에, 제대로 도는 서버 1대짜리 게임부터 만든다. 이후 모든 단계는 "이 1대만큼 매끈한가?"로 잰다.

완성 모습 = 연결 → 방송 → 틱 → 몬스터. 두 클라가 서로 보이고, 세상이 스스로 흐르고, 몬스터가 배회하는 단일 서버 미니 MMO. (C#, .NET 콘솔)

🎥 실제 작동 — 3D 뷰어 (STEP 0)

단일 서버 + Raylib(C#) 얇은 뷰어. 빨간 큐브(몬스터)는 서버가 스폰·이동해 20Hz로 방송하고, 뷰어는 받아서 그린다(HUD의 수신 pkt/s·하트비트가 그 증거). 파란 캡슐은 WASD/마우스로 조종.

✅ 지금 되는 것

· 단일 서버가 몬스터를 스폰·이동, 매 틱(20Hz) 네트워크 방송 → 뷰어는 '받아서 그림'(몬스터 = 서버 소유)

· WASD/마우스로 3인칭(TPS) 캐릭터 조종, 내 위치를 서버에 보고

· 서버 HUD(수신 pkt/s·하트비트)로 "로컬 게임이 아니라 서버-클라"임을 시각화

❌ 아직 안 되는 것 (STEP 0라서 — 다음 단계에서)

· 서버 1대뿐 → 존 분할·경계 없음 (STEP 1)

· 옆 칸 표시(고스트)·심리스 이주·경계 너머 공격(로켓) 없음 (STEP 3~5)

· 전투(몬스터 HP·잡기)·다른 플레이어 상호작용 없음

· 렌더는 기본 도형(캡슐/큐브) + 절차적 애니메이션(에셋 없음)

Part 1. 왜 9대가 아니라 '1대'부터?

목표는 서버 9대 분산인데, 왜 1대짜리부터?

손은 9대를 짜고 싶지만 두 가지가 걸린다. ① 기준이 없다 — 매끈한 단일 월드를 한 번도 안 본 상태에선 "심리스하게 됐는지"를 비교할 대상이 없다. ② 범인이 겹친다 — 9대가 하는 일 = 1대가 하는 일(틱·이동·방송·몬스터) + 분산의 어려움. 한 방에 짜다 버그가 나면 "게임 버그냐 분산 버그냐"를 동시에 디버깅하게 된다.

그래서 STEP 0의 존재 이유는 셋: ① 기준선, ② 어차피 필요한 토대, ③ 변수 분리(게임 로직을 먼저 고정 → STEP 1부터의 버그는 100% 분산 버그).

Part 2. 삽 1 — 파이프(연결): 두 프로세스가 바이트를 주고받기

STEP 0 안에서도, 왜 틱·몬스터가 아니라 '이것'부터?

틱·몬스터·방송, 그 모든 게 전제하는 단 하나는 "두 프로세스가 바이트를 주고받을 수 있다"이다. 이게 안 되면 나머지가 다 공중부양. 그리고 이건 STEP 0에서 가장 위험한 미지수(소켓·프레이밍)라, 코드 20줄일 때 부딪히는 게 낫다. → Walking Skeleton: 가장 얇지만 끝에서 끝까지 관통하는 슬라이스를 먼저 만든다.

메시지 하나 보내려면 세 가지를 정해야 한다: ① 패킷(뭘 담나) ② 프레이밍(어디서 끝나나) ③ 역할(누가 listen/connect).

// ① 패킷 — 방향에 따라 둘로 갈린다 (Shared/Packets.cs)
enum PacketType : byte { CM_MOVE = 1, SM_MOVE = 2 } // 메시지 종류 번호 // 클라→서버: playerId 없음(서버가 소켓으로 앎), authority 없음(서버가 정함) readonly record struct CM_MOVE(float X, float Y); // 서버→클라: '누가' '주인이 누구'인지 서버가 찍어 내려줌 readonly record struct SM_MOVE(int PlayerId, float X, float Y, byte AuthorityServerId);

신원은 '연결'이 증명한다 — playerId를 클라가 담으면 "나 5번이야"라고 남을 사칭할 수 있어, 서버가 소켓으로 안다. AuthorityServerId는 늘 0이지만 STEP 3의 '머리 위 색점'을 위해 지금 자리를 만든다.

// ② 프레이밍 — [길이 4][타입 1][데이터] (TCP는 스트림이라 경계를 우리가 긋는다)
"8바이트씩 읽기"는 패킷 하나뿐일 땐 되지만, 가변 패킷(채팅·방송)이 오면 무너진다: 선: [MoveReq 8B][Chat "hello" 5B] → TCP라 한 덩어리로 뭉쳐 도착 → 8씩 읽으면 desync 💥 길이 접두사: [8][MoveReq][5][hello] → 항상 정확히 한 통씩 ✓
// ③ 역할 — 서버 listen / 클라 connect. accept 루프는 핸들러를 await하지 않는다(저글링)
// 서버 var listener = new TcpListener(IPAddress.Loopback, 9001); listener.Start(); while (true) { var tcp = await listener.AcceptTcpClientAsync(); int playerId = nextId++; // 신원은 서버가 배정 _ = HandleClientAsync(tcp, playerId); // await 안 함 → 다음 손님을 안 막음 }

✅ 두 콘솔에 → sent / ← recv가 같이 뜨면 파이프가 뚫린 것. ❌ 남은 결핍: 클라가 둘이면 서버가 받기만 하고 안 뿌려 서로 못 봄 → 다음 삽 = 방송.

Part 3. 삽 2 — 방송: 서로 보인다

클라가 둘이면 왜 서로 안 보이지? 어떻게 고치나?

서버가 A의 이동을 받기만 하고 B에게 안 알려주니까. 고침 = 서버가 A의 이동을 받으면 접속한 '모두'에게 되뿌린다. 이때 SM_MOVE가 처음 등장 — 받는 쪽이 '누가 움직였는지' 알아야 하니 서버가 playerId를 찍는다.

방송하려면 서버가 '지금 누가 접속했나' 목록을 들어야 하고, 여기서 첫 공유 상태 → 첫 동시성이 등장한다. 여러 손님 핸들러가 다른 스레드에서 동시에 그 목록을 건드리니, 스레드 안전 자료구조(ConcurrentDictionary) + 연결별 보내기 직렬화(SemaphoreSlim)로 막았다.

// A의 이동을 받으면 → SM_MOVE로 만들어 '나 빼고 전원'에게 var sm = Codec.Serialize(new SM_MOVE(self.PlayerId, m.X, m.Y, 0)); foreach (var other in clients.Values) if (other.PlayerId != self.PlayerId) await other.SendAsync(PacketType.SM_MOVE, sm);

✅ 클라1 화면 👀 P2 이동, 클라2 화면 👀 P1 이동. ❌ 남은 결핍: 안 움직이면 안 보임(움직일 때만 방송) + 세상이 스스로 안 흐름 → 다음 삽 = 틱.

Part 4. 삽 3 — 틱(심장): 세상이 스스로 흐른다

아무도 입력 안 해도 몬스터가 움직이고 시간이 흘러야 하잖아. 누가 굴리지?

틱(심장박동). 일정 간격마다 "한 프레임 진행!" 하고 세상을 갱신한다. 구조를 확 바꿨다: 네트워크(async)는 받은 걸 큐에 넣기만, 틱 루프(한 스레드)가 꺼내 차례차례 처리.

그 결과 — 세상(world)을 틱 스레드 혼자 만지니, 지난 삽의 동시성 장치가 다 사라졌다: 평범한 Dictionary로 복귀, SemaphoreSlim 제거. 유일한 스레드 안전 지점은 큐 하나. (진짜 게임 서버가 쓰는 방식.) 덤으로 매 틱 전원 위치를 방송하니 '안 움직여도 계속 보임'도 해결.

while (true) { // 틱 루프 = 심장, 단일 스레드 게임 로직 while (inbox.TryDequeue(out var cmd)) { /* 입장·이동·퇴장 처리 (락 없이!) */ } foreach (var (id, pos) in world) // 현재 상태를 방송 /* SM_MOVE 전원에게 */ ; Console.WriteLine($"tick #{tick} | {conns.Count}명"); // 0명이어도 계속 뛴다 await Task.Delay(TickMs); }

✅ tick #1 | 0명이 접속자 없을 때도 찍힘 = 세상이 스스로 흐름. ❌ 남은 결핍: 아직 '스스로 움직이는 것'이 없음 → 다음 삽 = 몬스터.

Part 5. 삽 4 — 몬스터: 스스로 움직인다 (STEP 0 완성)

몬스터는 어떻게 넣지?

틱이 이미 '매 틱 world 갱신 → 방송'을 하니, 몬스터는 그 안에 '매 틱 조금씩 움직이기' 한 단계만 얹으면 된다. 그래서 코드가 거의 안 늘었다. 틱을 먼저 만든 게 몬스터의 준비 작업이었던 셈.

// 매 틱, 몬스터를 스스로 움직인다 (입력 없이). 벽에 닿으면 튕김. foreach (var id in monsters.Keys.ToList()) { var mo = monsters[id]; float nx = mo.X + mo.VX, ny = mo.Y + mo.VY; /* 0~20 범위 벗어나면 속도 반전 */ monsters[id] = (nx, ny, mo.VX, mo.VY); } // 방송은 SM_MONSTER 타입으로 (SM_MOVE 모양 재사용, 봉투 타입만 다름)

✅ 접속자 0명일 때도(tick #1 | 0명 | M1(6,5)), 클라가 멈춰도, 몬스터가 스스로 배회. STEP 0 완성. ❌ STEP 0의 한계: 서버 1대뿐 → 스케일 아웃 불가 → STEP 1: 3×3으로 찢기('경계'라는 새 문제 등장).

쓰인 개념 한 줄 사전 (쉽게)

개념쉽게 말하면
소켓두 프로그램 사이에 놓인 '전화선'. 서버는 문을 열고(listen) 기다리고, 클라는 그 문으로 들어간다(connect).
바이트 / 직렬화선으로 오가는 건 글자가 아니라 숫자 덩어리(바이트). 구조체를 바이트 줄로 펴는 게 직렬화, 되살리는 게 역직렬화.
TCP 스트림 / 프레이밍TCP는 바이트를 '끝없는 물줄기'로 보내 편지 경계가 없다. 그래서 앞에 [길이][타입]을 붙여 '한 통'을 표시하는 게 프레이밍.
async (비동기)'기다리는 동안 딴 일 하기'. 한 손님 데이터를 기다리며 붙어있지 않고, 오면 알려달라 하고 다른 손님을 처리 → 한 일꾼이 여럿을 저글링.
동시성여러 일꾼(스레드)이 같은 걸 동시에 만지면 깨질 수 있는 문제. 해결: 안전한 자료구조를 쓰거나, 아예 한 일꾼만 만지게 모은다(틱).
틱서버의 심장박동. 일정 간격마다 세상을 한 번씩 갱신. 입력이 없어도 세상이 스스로 흐르게 한다.

★ A부터 Z까지 — 이야기로

네트워크를 처음 보는 사람도 읽히게. "처음엔 이렇게 생각했고, 그래서 이걸 만들었는데, 이런 문제가 있어 이런 고려를 했다"의 흐름.

저는 '프로세스 9개가 나눠 든 하나의 월드'를 만들고 싶었습니다. 그런데 9개를 한 번에 만들면, 잘 됐는지 비교할 기준도 없고, 버그가 나도 '게임 문제냐 분산 문제냐'를 못 가립니다. 그래서 먼저 서버 1대짜리 제대로 도는 게임부터 만들기로 했습니다. 이게 STEP 0입니다.

서버 1대짜리 게임엔 뭐가 필요할지 생각해봤습니다. 결국 게임은 '여러 사람이 접속해서, 서로 보고, 세상이 살아 움직이는' 것입니다. 그런데 그 모든 것의 바닥엔 딱 하나가 깔려 있어야 합니다 — 두 컴퓨터(프로세스)가 서로 대화할 수 있어야 합니다. 이게 안 되면 나머지가 다 소용없습니다. 그래서 첫 목표를 '연결'로 잡았습니다.

연결이 뭔지 생각해봤습니다. 한 프로그램(서버)이 '문을 열고 기다리고', 다른 프로그램(클라)이 '그 문으로 들어가는' 겁니다.

소켓 — 이 문과 대화 통로를 소켓이라 합니다. 쉽게 말하면 두 프로그램 사이에 놓인 전화선입니다. 서버는 문을 여는(listen) 소켓을, 클라는 걸어 들어가는(connect) 소켓을 씁니다.

그런데 이 선으로 오가는 건 글자나 그림이 아니라 바이트(숫자 덩어리)였습니다. 그래서 제가 보내고 싶은 정보('나 (10,5)로 이동')를 바이트로 바꿔야 했습니다.

직렬화 — 구조체를 바이트 줄로 '펴는 것'입니다. 받는 쪽은 반대로 바이트를 구조체로 되살립니다(역직렬화). 저는 이걸 타입마다 새로 짜지 않고, '원시 숫자로만 된 구조체면 메모리를 통째로 복사'하는 방식으로 한 번에 처리했습니다.

여기서 첫 함정을 만났습니다. 제가 쓴 통신 방식(TCP)은 바이트를 끝없이 이어지는 물줄기로 보냅니다. 편지 봉투처럼 '여기까지가 한 통'이라는 경계가 없습니다. 편지를 연달아 보내면 받는 쪽이 어디서 끊어야 할지 모릅니다.

프레이밍 — 그래서 각 편지 앞에 '길이'를 붙였습니다("이 편지는 8바이트야"). 그리고 '무슨 편지인지'도 알려주려 '타입 번호'도 붙였습니다. 그래서 제 편지는 항상 [길이][타입][내용] 모양이 됐습니다.

또 하나 고민이 있었습니다. 서버는 손님을 한 명만 받는 게 아니라 여러 명이 동시에 붙습니다. 그런데 한 손님의 데이터를 '기다리는' 동안 다른 손님들이 멈추면 안 됩니다.

async(비동기) — 쉽게 말하면 '기다리는 동안 딴 일 하기'입니다. '데이터 올 때까지 붙어서 기다리기' 대신 '오면 알려줘' 하고 다른 손님을 처리합니다. 그래서 일꾼(스레드) 하나가 여러 손님을 저글링할 수 있습니다.

이렇게 첫 삽 — 클라가 서버에 붙어 이동 편지 하나를 보내고, 서버가 받아 콘솔에 찍는 것 — 을 완성했습니다. 두 콘솔에 같은 내용이 뜨는 걸 보고 '파이프가 뚫렸다'고 확인했습니다. 중요한 건, 신원(누가 보냈나)을 클라가 적게 하지 않았다는 점입니다. 클라가 "나 5번이야"라고 적으면 남을 사칭할 수 있으니, 서버가 '그 소켓이 누구 연결인지'로 스스로 압니다.

근데 여기까진 아직 게임이 아니었습니다. 문제: 클라가 둘이면 서로 안 보입니다. 서버가 A의 이동을 받기만 하고 B한테 안 알려주니까요. 그래서 다음으로 방송을 만들었습니다. 서버가 A의 이동을 받으면, 접속한 모두에게 'A가 여기로 갔다'를 되뿌리는 겁니다. 이때 받는 쪽이 '누구의 이동인지' 알아야 해서, 서버가 playerId를 찍어 내려보냈습니다.

방송을 만들려니 서버가 '지금 누가 접속해 있는지' 목록을 들고 있어야 했습니다. 그런데 여기서 둘째 함정을 만났습니다.

동시성 — 손님마다 처리를 '동시에' 돌리니, 그 목록을 여러 일꾼이 동시에 건드리게 됐습니다. 동시에 건드리면 목록이 깨질 수 있습니다. 그래서 '동시에 건드려도 안전한 목록'을 썼습니다. (이건 임시방편이었고, 다음 단계에서 더 깔끔히 정리합니다.)

방송까지 되니 둘이 서로 보였습니다. 근데 또 문제가 둘. 가만히 서 있으면 안 보입니다(움직일 때만 방송하니까). 그리고 더 근본적으로 아무도 입력 안 하면 세상이 멈춰 있습니다. 몬스터가 배회하고 시간이 흐르려면 '입력과 상관없이 스스로 도는 심장'이 필요했습니다.

틱 — 일정 간격마다 세상을 한 번씩 갱신하는 심장박동입니다. 저는 구조를 이렇게 바꿨습니다: 네트워크는 받은 걸 '큐(줄)'에 넣기만 하고, 틱이 그 큐를 꺼내 한 일꾼으로 차례차례 처리합니다.

틱을 넣으니 놀라운 일이 생겼습니다. 세상(플레이어 위치)을 이제 한 일꾼만 만지니까, 아까 골치였던 '동시성' 장치가 다 필요 없어졌습니다. 평범한 목록으로 돌아갔습니다. 이게 사실 진짜 게임 서버들이 쓰는 방식(싱글스레드 게임 로직 + 비동기 네트워크)입니다. 그리고 틱이 매번 '모두의 현재 위치'를 방송하니, 가만 서 있어도 계속 보이게 됐습니다. 앞의 문제도 자동으로 풀린 거죠.

마지막으로 몬스터를 넣었습니다. 틱이 이미 '매 틱 세상을 갱신하고 방송'하고 있었으니, 몬스터는 그 안에 '매 틱 조금씩 움직이기'만 얹으면 됐습니다. 그래서 코드가 거의 안 늘었습니다. 아무도 접속 안 해도, 클라가 가만있어도, 몬스터가 스스로 배회했습니다. 로그의 tick #1 | 0명 | M1(6,5)이 그 증거입니다 — 접속자가 없는데도 몬스터가 이미 한 칸 움직였습니다.

이렇게 연결 → 방송 → 틱 → 몬스터 순서로, 각 단계가 '안 되는 것'을 남기고 그게 다음 단계를 부르는 방식으로, 제대로 도는 단일 서버 미니 MMO를 완성했습니다. 이게 앞으로 9대로 찢을 때 '이만큼 매끈한가'를 재는 기준선입니다.

돌아보면 제가 매 순간 지킨 기준이 넷 있었습니다. ① 토대부터(남이 기대는 것을 먼저 만든다). ② 눈에 보이게(로그로 확인 못 하면 됐는지 모른다). ③ 범인을 하나로(한 번에 하나만 바꿔서, 깨지면 원인이 하나이게). ④ 되게 먼저, 예쁘게 나중(본질이 증명되기 전엔 잡음에 손대지 않는다). 개념 자체는 검색하면 나오지만, '어떤 상황에서 어떤 기준으로 이 순서로 풀었는가'가 이 프로젝트의 진짜 내용입니다.

핵심 정리

  • STEP 0 = 9대로 찢기 전 '기준선'. 1대부터인 이유: 비교 기준 + 토대 + 변수 분리.
  • 순서: 연결(파이프) → 방송(서로 보임) → 틱(스스로 흐름) → 몬스터(스스로 움직임). 각 단계의 결핍이 다음을 부른다.
  • 연결엔 소켓·직렬화·프레이밍·async가 필요했고, 신원은 서버가 소유(사칭 방지).
  • 방송에서 첫 동시성이 등장 → 틱으로 '한 스레드에 모으기'를 하니 동시성 장치가 사라짐(진짜 게임 서버 방식).
  • 몬스터는 틱 위에 '매 틱 이동' 한 단계만 얹어 완성.
  • 관통한 기준 4: 토대부터 · 눈에 보이게 · 범인을 하나로 · 되게 먼저 예쁘게 나중.
