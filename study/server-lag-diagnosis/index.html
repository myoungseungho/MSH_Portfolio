이 서버만 왜 느리지? 원인 추적 5단계

라이브 서버 렉 진단 - 체계적 소거법으로 접근하기

시니어는 감이 아니라 소거법으로 찾는다

"7번 서버만 렉 걸린다"는 신고가 들어왔어. 뭐부터 봐야 해?

일단 코드부터 뒤지면 안 돼.

신입이 가장 많이 하는 실수가 바로 "코드에 문제 있겠지?" 하고 디버거부터 여는 거야.

그런데 실제 라이브 서버 장애의 원인 분포를 보면:

게임 이벤트 (보스, 공성전, 유저 몰림) 80%
80%
특정 유저 비정상 행동 (패킷 어뷰징, 봇) 15%
15%
진짜 서버 이슈 (메모리 릭, 스레드 데드락) 5%

80%는 코드 문제가 아니라 게임 컨텍스트 문제야.

기술 프로파일링 전에 "이 서버에서 지금 뭐가 벌어지고 있는지"를 먼저 확인하는 게 시간을 아끼는 방법이야.

비유: 병원 응급실

환자가 배가 아프다고 왔어. 바로 CT 찍어? 아니지.
"뭐 드셨어요?", "언제부터 아팠어요?" 먼저 물어보잖아.

서버도 같아. "이 서버에서 지금 무슨 일이 벌어지고 있어?"부터 물어봐야 해.

Step 1. 하드웨어 레벨 확인 (30초)

그러면 제일 먼저 뭘 봐?

모니터링 대시보드를 켜.

Grafana 같은 도구로 해당 서버와 정상 서버의 지표를 나란히 비교하는 거야. 30초면 돼.

Grafana (그라파나)가 뭔데?

정의: 서버의 상태(CPU, 메모리, 네트워크 등)를 실시간 그래프로 보여주는 모니터링 도구.

왜 필요: 숫자만 나열하면 변화를 읽기 어렵지만, 그래프로 보면 "어느 시점에 튀었는지" 한눈에 보여.

안 쓰면: 서버에 직접 접속해서 명령어를 하나하나 쳐야 하고, 정상 서버와 비교하기도 힘들어.

확인할 4가지 지표와, 각각이 비정상일 때 의미하는 것:

지표 비정상 기준 의심 원인
CPU 사용률 100% 고정 게임 로직 과부하 or 무한루프
메모리 사용률 90% 이상 메모리 릭 or 스왑(Swap) 발생
디스크 I/O 평소 대비 급증 로깅 과도 or 스왑 발생
네트워크 대역폭 포화 상태 패킷 폭주 (유저 밀집 or 공격)
스왑(Swap)이 뭐야?

정의: 메모리(RAM)가 부족할 때, 디스크를 임시 메모리처럼 쓰는 것.

왜 문제: 디스크는 RAM보다 수백~수천 배 느려. 스왑이 발생하면 서버가 극심하게 느려져.

안 막으면: 메모리 부족 → 스왑 → 디스크 I/O 폭증 → 서버 전체가 멈춤 수준으로 느려짐.

[정상 서버 vs 7번 서버 비교] 정상 서버 7번 서버 CPU: 35% vs 98% ← 여기! Memory: 62% vs 64% Disk I/O: 12MB/s vs 15MB/s Network: 200Mbps vs 220Mbps → CPU만 비정상 → "게임 로직 or 무한루프" 쪽을 파면 됨

정상 서버와 비교하는 게 핵심이야. 절대값만 보면 "원래 이 정도인가?" 판단이 안 돼. 옆에 놓고 비교해야 "어디가 튀었는지" 보여.

Step 2. 프로세스 레벨 확인 (1분)

Step 1에서 CPU가 높다는 걸 알았어. 그다음은?

스레드(Thread)별 CPU 사용률을 봐야 해.

서버는 보통 여러 스레드가 동시에 돌아가거든. 그 중 어떤 스레드가 CPU를 독점하고 있는지 알아야 원인을 좁힐 수 있어.

스레드(Thread)가 뭔데?

정의: 하나의 프로그램 안에서 독립적으로 실행되는 작업 단위. 프로세스 안의 "일꾼"이라고 생각하면 돼.

왜 필요: 게임 서버는 "게임 로직 계산", "DB 쿼리", "네트워크 패킷 처리" 같은 여러 일을 동시에 해야 하니까 스레드를 나눠서 병렬로 처리해.

안 쓰면: 한 번에 한 가지 일만 가능. DB 쿼리 기다리는 동안 게임 로직도 멈추고, 패킷도 못 받아.

[7번 서버 스레드별 CPU 사용률] Thread-Main (게임 로직): 92% ← 범인! Thread-DB (쿼리 처리): 3% Thread-Network (패킷 I/O): 2% Thread-Timer (스케줄러): 1% → 게임 로직 스레드가 CPU를 독점 → "게임 로직에서 뭔가 무거운 계산이 돌고 있다"

어떤 스레드가 범인인지에 따라 다음 행동이 달라져:

범인 스레드 의심 원인 다음 행동
게임 로직 보스 레이드, 대규모 전투, 무한루프 Step 3 (게임 컨텍스트 확인)
DB 쿼리 느린 쿼리, DB 서버 과부하 DB 슬로우 쿼리 로그 확인
네트워크 패킷 폭주, 비정상 클라이언트 패킷 로그 분석

대부분은 게임 로직 스레드가 범인이야. 그러니까 다음 스텝인 "게임 컨텍스트 확인"으로 넘어가자.

Step 3. 게임 컨텍스트 확인 (핵심!)

게임 로직이 무겁다는 건 알았어. 근데 "왜" 무거운지는 어떻게 알아?

여기서부터가 게임 서버 프로그래머만의 영역이야.

일반 서버 개발자는 "CPU 높네 → 프로파일링하자"로 바로 가. 근데 게임 서버는 다르거든.

게임 서버는 "서버에서 지금 어떤 게임 이벤트가 벌어지고 있는지"를 아는 것만으로도 원인을 80% 좁힐 수 있어.

구체적으로 뭘 확인해?

이 질문들을 순서대로 던져봐:

[게임 컨텍스트 체크리스트] 1. 해당 서버에서 특별한 게임 이벤트 진행 중인가? - 보스 레이드? - 공성전? - 대규모 이벤트? (2배 경험치 등) 2. 특정 맵에 유저가 몰려 있는가? - 이벤트 NPC 앞에 500명? - 신규 던전 오픈해서 입구에 밀집? 3. 특정 유저가 비정상 행동을 하고 있는가? - 초당 수백 개 패킷 보내는 봇? - 해킹 툴로 비정상 좌표 이동?

예를 들어 이런 상황이야:

실제 사례: "7번 서버만 느려요"

확인해보니 7번 서버에서 월드 보스 레이드가 진행 중이었어.
보스 주변에 300명이 밀집 → AOI 계산 폭증 → 틱 처리 시간 초과 → 렉

코드 문제가 아니야. 300명이 같은 곳에 모인 게 원인이야.
해결: 보스 방 최대 인원 제한 or 보스 스킬 AOI 최적화.

"이 단계에서 80%는 원인이 드러난다."

남은 20%만 기술적 프로파일링이 필요해. 그게 다음 스텝이야.

Step 4. 프로파일링 (원인 특정)

게임 컨텍스트에서도 원인이 안 보여. 이제 뭐 해?

이제 진짜 기술적 프로파일링을 해야 해.

"코드의 어떤 함수가 CPU를 잡아먹고 있는지" 정확히 찾는 단계야.

상황에 따라 3가지 방법 중 하나를 써:

Flame Graph (플레임 그래프)가 뭐야?

정의: 프로그램이 실행되는 동안 "어떤 함수가 얼마나 오래 실행됐는지"를 불꽃 모양 그래프로 보여주는 도구.

왜 필요: 코드가 수만 줄이면 "어디가 느린지" 감으로 못 찾아. Flame Graph는 가장 넓은 막대가 가장 오래 걸린 함수니까, 눈으로 바로 병목을 찾을 수 있어.

안 쓰면: "이 함수가 느린 것 같은데..." 하고 감으로 추측 → 삽질 → 시간 낭비.

[Flame Graph 읽는 법] ←——————————— 넓을수록 오래 걸린 함수 ———————————→ |=================== UpdateWorld() ===================| |======= ProcessCombat() =======| |== MoveNPC() ==| |== CalcDamage() ==| |= ApplyBuff() =| → UpdateWorld()가 가장 넓다 = 가장 오래 걸림 → 그 안에서 ProcessCombat()이 절반 차지 → CalcDamage()를 최적화하면 효과가 크겠다!

상황별 접근법:

A) 프로파일러 연결 가능한 경우

서버에 프로파일러를 붙여서 Flame Graph를 뽑아.

가장 정확하지만, 프로파일러 자체가 서버에 부하를 줘서 라이브 서버에는 부담이 클 수 있어.

B) 프로파일러 연결 불가한 경우 (라이브 부담)

서버에 미리 심어둔 내장 성능 카운터를 확인해.

[내장 성능 카운터 예시] 틱(Tick)당 처리 시간: 정상 16ms / 현재 85ms ← 5배 느림! DB 쿼리 응답 시간: 정상 2ms / 현재 3ms ← 정상 패킷 처리량: 정상 5000/s / 현재 12000/s ← 2.4배! → 틱 처리 시간이 5배 느리고, 패킷도 2배 이상 → "많은 유저의 패킷을 한 틱 안에 처리하느라 느려진 것"
틱(Tick)이 뭐야?

정의: 서버가 게임 세계를 한 번 업데이트하는 주기. "서버의 심장 박동"이라고 생각하면 돼.

왜 필요: 서버는 "유저 입력 처리 → 게임 로직 계산 → 결과 전송"을 한 틱에 다 해야 해. 보통 초당 20~60틱 (50ms~16ms 간격).

안 지키면: 틱이 밀리면 유저들이 체감하는 렉이 생겨. 16ms 틱인데 85ms 걸리면, 유저 화면에서 캐릭터가 뚝뚝 끊기는 거야.

C) 로그 분석

A, B 둘 다 안 되면 서버 로그를 뒤져.

Warning/Error 로그를 시간순으로 보면서, 정상 서버 로그와 패턴을 비교해.

"정상 서버에는 없는데 7번 서버에만 반복되는 Warning"이 있다면 그게 단서야.

방법 정밀도 라이브 부담 사전 준비
A) Flame Graph 매우 높음 높음 프로파일러 설치
B) 내장 카운터 중간 거의 없음 코드에 미리 심어야 함
C) 로그 분석 낮음 없음 로깅 체계 필요

Step 5. 재현 & 확인

원인 후보를 찾았어. 이제 바로 고치면 되는 거 아니야?

"후보"를 찾은 거지, "확정"이 아니야.

라이브 서버에 검증 안 된 수정을 바로 배포하면 더 큰 사고가 날 수 있어.

반드시 재현 → 수정 → 검증 순서를 밟아야 해.

[재현 & 확인 플로우] 원인 후보 발견 | v 스테이징(테스트) 서버에서 동일 조건 재현 시도 | +------ 재현 성공 ------+ | | v v 원인 확정 수정 & 패치 | | v v 수정 코드 작성 스테이징에서 검증 | | v v 스테이징 검증 라이브 배포 | +------ 재현 실패 ------+ | | v v 해당 서버에 더 상세한 로그를 더 상세한 로그 ON 켜고 모니터링 지속
스테이징(Staging) 서버가 뭐야?

정의: 라이브 서버와 동일한 환경이지만, 실제 유저가 접속하지 않는 테스트 전용 서버.

왜 필요: 라이브에서 직접 테스트하면 실제 유저에게 피해가 가잖아. 스테이징은 "안전한 실험실"이야.

안 쓰면: "이거 고치면 될 것 같은데?"로 라이브에 바로 배포 → 더 큰 장애 → 긴급 롤백 → 야근.

재현이 안 되는 경우가 더 무서워.

"특정 시간대에만", "특정 유저 조합에서만" 발생하는 버그는 재현이 안 될 수 있어.

이럴 때는 해당 서버에 더 상세한 로그 레벨을 켜놓고, 다음 발생을 기다리면서 데이터를 모아야 해.

재현 불가 = 포기가 아니라, "더 많은 정보를 모으는 단계"로 전환하는 것.

평상시에 해놔야 하는 것

사고가 터지고 나서 모니터링을 붙이면 안 돼?

"사고 나서 모니터링 붙이면 이미 늦다."

사고가 터지면 모두가 패닉 상태야. 그때 "어... 대시보드 어떻게 만들지?" 하면 골든 타임을 날려.

평상시에 이미 세팅해둬야 사고 때 30초 만에 원인을 좁힐 수 있어.

최소한 뭘 모니터링해야 해?

서버별로 최소 4가지 지표를 항상 대시보드에 띄워놔야 해:

지표 왜 봐야 하는지 경보 기준 예시
서버 틱 소요 시간 렉의 직접적 지표. 이게 밀리면 유저가 렉을 느낌 목표 틱(16ms)의 2배 = 32ms 초과 시 경보
동접 수 유저 밀집 감지. 특정 서버만 동접 급증하면 이벤트/몰림 평균의 1.5배 초과 시 경보
DB 쿼리 평균 응답 시간 DB 병목 감지. 쿼리가 느려지면 전체 틱이 밀림 10ms 초과 시 경보
패킷 처리량 비정상 트래픽 감지. 봇/어뷰징 시 급증 평균의 2배 초과 시 경보

전체 진단 플로우를 한 장으로 정리하면:

[서버 렉 진단 5단계 플로우] "7번 서버 렉 신고!" | v Step 1. 하드웨어 지표 확인 (30초) CPU / Memory / Disk / Network 정상 서버와 비교 | v Step 2. 스레드별 CPU 확인 (1분) 어떤 스레드가 CPU 독점? 게임 로직? DB? 네트워크? | v Step 3. 게임 컨텍스트 확인 (핵심) 보스전? 공성전? 유저 몰림? 비정상 유저? 봇? === 여기서 80% 원인 발견 === | v (안 찾으면) Step 4. 프로파일링 A) Flame Graph (정밀, 부담 큼) B) 내장 성능 카운터 (실용적) C) 로그 분석 (최후 수단) | v Step 5. 재현 & 확인 스테이징 재현 → 수정 → 검증 → 배포 재현 불가 → 상세 로그 ON → 대기

핵심 정리: 서버 렉 진단 5단계
