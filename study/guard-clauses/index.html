Refactoring #19

Guard Clauses

보호 구문 - 예외 상황을 먼저 처리하라

보호 구문이 뭐예요?
함수 시작 부분에서 예외 상황을 먼저 처리하고 빠져나가는 패턴이에요.

"이 조건이 아니면 바로 리턴"하는 방식으로, 정상 흐름에 집중할 수 있게 해줘요.

중첩된 if-else 대신, 비정상 케이스를 함수 초반에 걸러내는 거죠.
왜 좋은 건가요? 기존 if-else가 뭐가 문제죠?
중첩 if-else의 문제를 보세요:

"사용자가 있으면, 그 사용자가 활성 상태면, 권한이 있으면, 결제 수단이 있으면... 처리한다"

이런 코드는: - 들여쓰기가 계속 깊어짐 (화살표 모양 코드)
- 정상 흐름이 어디인지 한눈에 안 보임
- 실수로 else를 빼먹기 쉬움

Guard Clause를 쓰면:

"사용자 없으면 리턴. 비활성이면 리턴. 권한 없으면 리턴. 결제 수단 없으면 리턴. → 이제 정상 처리."

들여쓰기 1단계. 정상 흐름이 눈에 확 들어와요.

🚪 비유: 경비실 검문

건물 입구에서 체크하면: - 신분증 없음? → 돌려보냄 - 예약 없음? → 돌려보냄 - 출입 금지자? → 돌려보냄

검문 통과한 사람만 건물 안으로.

코드도 함수 입구에서 걸러내면 본체가 깔끔해져요.
함수 중간에 return이 여러 개 있으면 안 좋다고 들었는데요?
오래된 미신이에요!

예전에 "단일 출구 원칙"이라는 게 있었어요. 함수에 return이 하나만 있어야 한다는 거죠.

하지만 이건 옛날 언어의 한계 때문이었어요: - 리소스 정리가 return 전에 있어야 했음 - goto 남용을 막으려는 의도

현대 언어에서는: - 자동 메모리 관리 (GC) - RAII, try-finally, using 등

오히려 Guard Clause의 장점이 더 커요: - 조기 리턴으로 비정상 케이스 빨리 처리 - 중첩 줄여서 가독성 향상 - 정상 경로가 명확해짐
어떤 경우에 Guard Clause를 쓰나요?
이런 상황에서 효과적이에요:

1. null/빈 값 체크
"파라미터가 null이면 바로 리턴"

2. 권한/조건 검증
"관리자가 아니면 에러 리턴"

3. 상태 검증
"이미 처리됐으면 스킵"

4. 입력값 범위 체크
"음수면 0 리턴"

공통점: 비정상/예외 케이스를 먼저 쳐내는 것

💡 Guard Clause 적용 기준

"이 조건이 아니면 이 함수에서 할 일이 없다"

→ 바로 리턴!
Guard Clause로 변환하는 절차가 있나요?
단계별 변환:

1단계: 가장 바깥 조건 확인
→ if (condition) { ... 긴 코드 ... }

2단계: 조건을 뒤집어서 조기 리턴
→ if (!condition) return;

3단계: 기존 else 제거
→ 이제 else가 필요 없어요

4단계: 다음 중첩에 반복
→ 하나씩 꺼내서 Guard로 변환

5단계: 테스트

결과: 들여쓰기가 줄고, 정상 흐름만 남아요.
주의할 점은요?
주의해야 할 상황들:

1. 리턴값이 있는 함수
조기 리턴 시 적절한 값(null, 0, false 등)을 리턴해야 해요.

2. 부작용(side effect) 주의
조기 리턴 전에 로그를 남기거나 정리할 게 있는지 확인.

3. 과도한 Guard
Guard가 10개 넘으면? 함수가 너무 많은 일을 하는 신호. 함수 분리를 고려하세요.

⚠️ 예외 던지기 vs 리턴

- 프로그래밍 오류 (null이면 안 되는데 null): 예외 - 정상적인 예외 상황 (데이터 없음): 리턴

Guard Clause는 주로 후자에 사용해요.

📌 Guard Clauses 핵심 정리

  • 예외 상황을 함수 초반에 처리하고 조기 리턴
  • 중첩 if-else를 평면적인 구조로 변환
  • 정상 흐름에 집중할 수 있게 해줌
  • "단일 출구 원칙"은 현대에서는 적용 안 해도 됨
  • Guard가 너무 많으면 함수 분리 고려
