왜 32비트 게임은 4GB 이상 못 쓸까?

32비트 주소 체계의 한계와 64비트 전환

Part 1. 32비트의 수학적 한계

왜 하필 4GB야?

2^32 = 4,294,967,296 (약 43억)이기 때문이야.

32비트 = 32자리 이진수 = 표현 가능한 숫자가 약 43억 개.

32비트 주소의 한계: 주소 = 메모리의 "집 번호" 32비트 주소: ┌────────────────────────────────────────────────────────────┐ │ 0000 0000 0000 0000 0000 0000 0000 0000 (0x00000000) │ │ ~ │ │ 1111 1111 1111 1111 1111 1111 1111 1111 (0xFFFFFFFF) │ └────────────────────────────────────────────────────────────┘ ↓ 2^32 = 4,294,967,296 가지 주소 ↓ 1바이트씩 주소를 붙이면: 최대 4GB 메모리 주소 지정 가능 비유: ┌────────────────────────────────────────────────────────────┐ │ 32비트 = 8자리 전화번호 │ │ │ │ 00000000 ~ 99999999 = 1억 개 번호 │ │ │ │ 아무리 전화기가 많아도, 번호가 1억 개 뿐이면 │ │ 1억 대 이상은 연결 불가! │ └────────────────────────────────────────────────────────────┘
근데 4GB인데 왜 2GB밖에 못 써?

Windows에서 4GB 중 절반을 커널(운영체제)이 사용하기 때문이야!

32비트 Windows 메모리 분할: ┌────────────────────────────────────────────────────────────┐ │ │ │ 0x00000000 ┌──────────────────────────────────────┐ │ │ │ │ │ │ │ 유저 공간 (User Space) │ │ │ │ │ │ │ │ 프로그램이 쓸 수 있는 영역 │ │ │ │ │ │ │ │ 2GB (기본) │ │ │ │ │ │ │ 0x7FFFFFFF ├──────────────────────────────────────┤ │ │ │ │ │ │ │ 커널 공간 (Kernel Space) │ │ │ │ │ │ │ │ 운영체제가 사용하는 영역 │ │ │ │ (드라이버, 시스템 캐시 등) │ │ │ │ │ │ │ │ 2GB (예약됨) │ │ │ │ │ │ │ 0xFFFFFFFF └──────────────────────────────────────┘ │ │ │ └────────────────────────────────────────────────────────────┘ 왜 절반이나 커널에? 1. 커널 코드/데이터 2. 하드웨어 드라이버 3. 파일 시스템 캐시 4. 페이지 테이블 자체 5. 보안 (CPU 취약점 대응: KPTI/Meltdown)

Part 2. /LARGEADDRESSAWARE 플래그

2GB를 늘리는 방법 없어?

/LARGEADDRESSAWARE 플래그를 켜면 조건부로 더 쓸 수 있어!

/LARGEADDRESSAWARE 효과: ┌───────────────────────────────────────────────────────────────┐ │ 조건 │ 유저 공간 │ 커널 공간 │ ├───────────────────────────────────┼─────────────┼─────────────┤ │ 32비트 OS + 플래그 없음 │ 2GB │ 2GB │ │ 32비트 OS + 플래그 + /3GB 부트 │ 3GB │ 1GB │ │ 64비트 OS + 플래그 (32비트 앱) │ 4GB │ N/A │ │ 64비트 OS + 플래그 없음 │ 2GB │ N/A │ └───────────────────────────────────────────────────────────────┘ 핵심: 64비트 Windows에서 32비트 프로그램을 돌릴 때 /LARGEADDRESSAWARE 켜면 4GB까지 사용 가능!
// Visual Studio에서 /LARGEADDRESSAWARE 설정 방법 1: 링커 옵션 프로젝트 속성 → 링커 → 시스템 → 큰 주소 인식 → "예" 방법 2: 커맨드라인 link.exe /LARGEADDRESSAWARE myapp.obj 방법 3: 이미 빌드된 EXE 수정 editbin.exe /LARGEADDRESSAWARE myapp.exe // 주의사항! // 포인터를 int로 캐스팅하는 코드가 있으면 문제 발생 void* ptr = malloc(100); int addr = (int)ptr; // 0x80000000 이상이면 음수가 됨! // signed int 최대값: 0x7FFFFFFF
/LARGEADDRESSAWARE 켜면 뭘 조심해야 해?

주소가 2GB를 넘어갈 수 있으니 포인터를 정수로 변환하는 코드를 점검해야 해.

흔한 버그 패턴: 문제 1: 포인터를 int로 캐스팅 ┌────────────────────────────────────────────────────────────┐ │ void* ptr = 0x90000000; // 2GB 이상 주소 │ │ int val = (int)ptr; // val = -1879048192 (음수!) │ │ if (val > 0) { ... } // 실패! │ │ │ │ 해결: intptr_t 또는 uintptr_t 사용 │ │ uintptr_t val = (uintptr_t)ptr; // OK │ └────────────────────────────────────────────────────────────┘ 문제 2: 포인터 차이 계산 ┌────────────────────────────────────────────────────────────┐ │ char* start = 0x10000000; │ │ char* end = 0xA0000000; │ │ int diff = end - start; // 오버플로우! │ │ │ │ 해결: ptrdiff_t 사용 │ │ ptrdiff_t diff = end - start; // OK │ └────────────────────────────────────────────────────────────┘ 문제 3: 메모리 맵 파일 크기 ┌────────────────────────────────────────────────────────────┐ │ // 2GB 이상 파일 매핑 시 │ │ DWORD fileSize = GetFileSize(hFile, NULL); │ │ // DWORD는 4GB까지 OK지만, 2GB 넘는 매핑 실패 가능 │ └────────────────────────────────────────────────────────────┘

Part 3. 64비트의 광활한 세계

64비트면 메모리가 얼마나 돼?

이론상 2^64 = 16 엑사바이트야. 하지만 현재 CPU는 48비트 주소만 사용해.

64비트 메모리 주소: 이론상: 2^64 = 18,446,744,073,709,551,616 바이트 = 16 EB (엑사바이트) = 지구상 모든 데이터의 수천 배 실제 (현재 CPU): ┌────────────────────────────────────────────────────────────┐ │ 48비트 주소 사용 (Intel/AMD 64비트 CPU) │ │ │ │ 2^48 = 256 TB (테라바이트) │ │ │ │ Windows 64비트: │ │ - 유저 공간: 128 TB │ │ - 커널 공간: 128 TB │ │ │ │ vs 32비트: │ │ - 유저 공간: 2 GB │ │ │ │ 64,000배 증가! │ └────────────────────────────────────────────────────────────┘ 미래 대비: - AMD64는 최대 52비트까지 확장 가능 (4 PB) - 주소 비트가 더 필요해지면 CPU 업그레이드로 대응
64비트의 단점은?

포인터 크기가 2배가 되니까, 메모리를 더 많이 먹어.

64비트의 트레이드오프: 포인터 크기 증가: ┌────────────────────────────────────────────────────────────┐ │ 32비트: 포인터 = 4바이트 │ │ 64비트: 포인터 = 8바이트 │ │ │ │ 포인터를 많이 쓰는 자료구조에서 메모리 사용량 증가 │ │ │ │ 예: 연결 리스트 노드 │ │ │ │ 32비트: 64비트: │ │ struct Node { struct Node { │ │ int data; // 4B int data; // 4B │ │ Node* next; // 4B int padding; // 4B │ │ }; // 8B Node* next; // 8B │ │ }; // 16B │ │ │ │ 노드당 2배 메모리! │ └────────────────────────────────────────────────────────────┘ 캐시 효율 저하: ┌────────────────────────────────────────────────────────────┐ │ L1 캐시: 32KB (고정) │ │ │ │ 32비트: 32KB / 4B = 8,192개 포인터 캐시 가능 │ │ 64비트: 32KB / 8B = 4,096개 포인터 캐시 가능 │ │ │ │ → 캐시 미스 증가 가능 │ └────────────────────────────────────────────────────────────┘ 그래도 64비트가 훨씬 이득인 이유: - 메모리 한계 해소 - 레지스터 2배 (r8~r15 추가) - SIMD 레지스터 확장 - 보안 기능 (ASLR 효과 증가)

Part 4. 게임의 64비트 전환

게임을 64비트로 바꾸려면?

단순 리컴파일만으론 안 되고, 코드 점검이 필요해.

// 64비트 전환 시 체크리스트 // 1. 포인터 정수 변환 // 나쁜 예 int addr = (int)pointer; // 좋은 예 uintptr_t addr = (uintptr_t)pointer; // 2. 구조체 패킹 (네트워크, 파일 저장) #pragma pack(push, 1) struct SaveData { int id; // 4B void* ptr; // 4B(32) vs 8B(64) - 주의! int value; // 4B }; #pragma pack(pop) // 해결: 포인터 대신 오프셋이나 ID 저장 // 3. printf 포맷 printf("ptr: %x", ptr); // 32비트에서만 동작 printf("ptr: %p", ptr); // 이식성 있음 printf("size: %zu", size); // size_t용 // 4. WoW64 호환 // 32비트 DLL은 64비트 프로세스에서 로드 불가! // 서드파티 라이브러리 64비트 버전 필요
실제 게임 64비트 전환 사례: 월드 오브 워크래프트: ┌────────────────────────────────────────────────────────────┐ │ 2004년 출시 → 32비트 │ │ 2017년 Legion 확장팩 → 64비트 전용 │ │ │ │ 전환 이유: │ │ - 텍스처 품질 향상으로 메모리 부족 │ │ - 대규모 레이드에서 오브젝트 수 한계 │ │ - 모딩(애드온) 메모리 사용량 증가 │ └────────────────────────────────────────────────────────────┘ 마비노기: ┌────────────────────────────────────────────────────────────┐ │ 2004년 출시 → 32비트 │ │ 2024년 현재 → 여전히 32비트 + /LARGEADDRESSAWARE │ │ │ │ 문제: │ │ - 20년간 누적된 레거시 코드 │ │ - 서드파티 라이브러리 의존성 │ │ - 전환 비용 vs 유지 비용 계산 │ └────────────────────────────────────────────────────────────┘ 신규 게임: ┌────────────────────────────────────────────────────────────┐ │ 2015년 이후 출시 게임은 대부분 64비트 │ │ │ │ - Unreal Engine 4/5: 64비트 기본 │ │ - Unity: 64비트 빌드 지원 │ │ - 콘솔: PS4/Xbox One부터 64비트 전용 │ └────────────────────────────────────────────────────────────┘

Part 5. 확인하는 방법

내 프로그램이 32비트인지 64비트인지 어떻게 알아?

여러 방법이 있어:

// 방법 1: 작업 관리자 // 프로세스 이름 옆에 "(32비트)"가 있으면 32비트 // 방법 2: 코드에서 확인 #if defined(_WIN64) printf("64비트 빌드\n"); #elif defined(_WIN32) printf("32비트 빌드\n"); #endif // 방법 3: 포인터 크기로 확인 printf("포인터 크기: %zu바이트\n", sizeof(void*)); // 4 → 32비트, 8 → 64비트 // 방법 4: dumpbin 도구 // 명령 프롬프트에서: // dumpbin /headers myapp.exe | findstr "machine" // 8664: x64, 14c: x86
게임 클라이언트 확인 예시: 작업 관리자: ┌────────────────────────────────────────────────────────────┐ │ 이름 CPU 메모리 설명 │ ├────────────────────────────────────────────────────────────┤ │ game.exe (32비트) 15% 1,800MB 레거시 게임 │ │ game64.exe 22% 4,200MB 64비트 버전 │ │ steam.exe 2% 180MB Steam 클라이언트 │ └────────────────────────────────────────────────────────────┘ Process Explorer 상세 정보: ┌────────────────────────────────────────────────────────────┐ │ Image: game.exe │ │ Platform: 32-bit │ │ Virtual Size: 1,980 MB / 2,048 MB (96.7%) │ │ ASLR: Enabled │ │ LARGEADDRESSAWARE: Yes │ └────────────────────────────────────────────────────────────┘

핵심 정리

  • 32비트 = 2^32 = 4GB - 주소를 표현할 수 있는 숫자의 한계
  • Windows 2GB 제한 - 4GB 중 절반을 커널이 사용
  • /LARGEADDRESSAWARE - 64비트 OS에서 32비트 앱이 4GB까지 사용 가능
  • 64비트 = 128TB - 사실상 메모리 한계 해소
  • 64비트 단점 - 포인터 2배 → 메모리 증가, 캐시 효율 저하
  • 전환 시 주의 - 포인터-정수 변환, 구조체 패킹, 서드파티 라이브러리
  • 신규 게임 - 2015년 이후로는 대부분 64비트 기본
