MMO 서버인데 싱글스레드라고? 멀티스레드 게임 루프의 4가지 패턴

IOCP는 멀티인데 메시지 처리는 싱글 — 다른 MMO들은 어떻게 하고 있을까?

Part 1. 우리 서버는 왜 싱글스레드야?

IOCP 쓰면 멀티스레드 아니야?

네트워크 I/O만 멀티스레드야. 패킷을 받고 보내는 건 여러 워커 스레드가 처리하지만, 받은 메시지를 실제로 처리하는 건 메인 루프 하나에서 순차적으로 해.

비유하면 우체국이야. 배달부(IOCP 워커)는 여러 명이지만, 편지를 열어보고 답장 쓰는 사람(게임 로직)은 한 명이야.

📦 우리 서버 구조 (IOCP + 싱글스레드 로직) [클라이언트들] ──패킷──▶ [IOCP 워커 스레드 4개] ──큐──▶ [메인 루프 1개] (네트워크: 멀티) (게임 로직: 싱글) 메인 루프가 하는 일: while(true) { 1. 큐에서 메시지 꺼내기 2. 메시지 처리 (공격, 이동, 아이템...) 3. DB 호출 (동기) 4. 결과 패킷 전송 }
그게 왜 문제가 안 돼?

가장 큰 장점은 레이스 컨디션이 원천 차단된다는 거야. 플레이어 A가 아이템을 옮기는 도중에 플레이어 B가 그 아이템을 주울 일이 없어. 한 번에 하나씩 순서대로 처리하니까.

락(Lock)도 필요 없고, 데드락도 불가능하고, 디버깅도 쉬워. 20년 넘게 운영되는 게임 서버들이 대부분 이 방식인 이유가 있어.

그럼 뭐가 문제야?

동접 1,000명까지는 괜찮아. 근데 동접 5,000명, 10,000명이 되면?

메인 루프 한 바퀴 도는 데 걸리는 시간이 늘어나. 메시지가 초당 50,000개 쌓이면, 한 스레드로는 밀려. 처리 지연 → 유저 렉 → 이탈.

Part 2. 멀티스레드 게임 로직이 어려운 이유

그냥 스레드 여러 개 돌리면 안 돼?

안 돼. 게임 서버의 근본 문제는 상태 공유야.

플레이어 A가 몬스터를 공격하는 도중에, 스레드 2에서 플레이어 B도 같은 몬스터를 공격하면? 몬스터 HP가 동시에 바뀌면서 꼬여.

💥 상태 공유 문제 스레드 1: A가 몬스터 공격 → HP 읽기(100) → 30 빼기 → HP 쓰기(70) 스레드 2: B가 몬스터 공격 → HP 읽기(100) → 50 빼기 → HP 쓰기(50) 결과: HP = 50 (틀림! 정답은 20) 원인: 두 스레드가 동시에 HP 100을 읽었기 때문
락 걸면 되잖아?

맞아, 락으로 해결은 돼. 근데 게임은 "모든 게 연결"되어 있어.

A가 B를 공격하면: 데미지 계산 → 버프 확인 → HP 감소 → 사망 판정 → 경험치 → 퀘스트 → 아이템 드롭 → 파티 분배.

이 모든 데이터에 락을 걸면? 사실상 싱글스레드랑 같아져. 락 기다리는 시간 때문에 오히려 더 느릴 수도 있어.

그럼 방법이 없어?

있어. 핵심은 "공유 상태를 없애거나, 공유 범위를 줄이는 것"이야.

이걸 해결하는 패턴이 크게 4가지 있어. 다른 MMO들이 실제로 쓰고 있는 방법들이야.

Part 3. 패턴 1 — 존(Zone) 기반 스레딩

존 기반이 뭐야?

월드를 구역(Zone)으로 쪼개서, 각 구역을 별도 스레드(또는 별도 프로세스)가 담당하는 거야.

WoW(월드 오브 워크래프트)가 대표적이야. 각 대륙(Eastern Kingdoms, Kalimdor)이나 던전 인스턴스가 별도 스레드에서 돌아가.

🗺️ 존 기반 스레딩 (WoW 스타일) [월드 서버] ├─ 스레드 1: 동부 왕국 ── 플레이어 3,000명 ├─ 스레드 2: 칼림도어 ── 플레이어 2,500명 ├─ 스레드 3: 아웃랜드 ── 플레이어 1,200명 ├─ 스레드 4~20: 던전 인스턴스들 └─ 메시지 큐: 존 간 통신 (귓말, 거래, 파티) 핵심: 같은 존 안에서는 싱글스레드! 존이 다르면 서로 간섭 없음
비유하면?

아파트 관리야. 101동, 102동, 103동 각각 관리인이 따로 있어. 자기 동 안에서는 혼자 다 처리하고(싱글스레드), 다른 동이랑 연락할 일 있으면 관리사무소(메시지 큐)를 통해.

문제점은?

존 경계를 넘을 때가 문제야.

플레이어가 존 A에서 존 B로 이동하면? 한 스레드에서 다른 스레드로 캐릭터 데이터를 이관해야 해. 이때 잠깐 끊기거나 로딩이 생겨.

그리고 한 존에 사람이 몰리면 (공성전, 월드보스) 그 스레드만 병목이 돼. "오그리마 렉"이 이거야.

항목 존 기반 스레딩
대표 게임 WoW, EVE Online (솔라 시스템 단위)
장점 구현 간단, 존 내부는 싱글스레드의 안전성
단점 존 경계 이동 시 끊김, 인구 쏠림 시 병목
적합한 게임 존/채널 구분이 명확한 MMO

Part 4. 패턴 2 — Actor 모델

Actor 모델은 뭐가 다른데?

존 기반이 "지역"으로 나누는 거라면, Actor 모델은 "객체"로 나누는 거야.

각 엔티티(플레이어, 몬스터, NPC)가 자기만의 메일박스를 갖고, 메시지를 받아서 순차 처리해. 공유 메모리가 아예 없어.

📬 Actor 모델 [Player A Actor] ←── 메일박스: 공격 결과, 버프 적용, ... └─ 자기 상태만 수정 (HP, MP, 인벤토리) [Monster X Actor] ←── 메일박스: 피격, AI 틱, ... └─ 자기 상태만 수정 (HP, 위치, 타겟) A가 X를 공격하면? 1. A Actor → X Actor에게 메시지: "30 데미지" 2. X Actor가 자기 메일박스에서 꺼내서 처리 3. X Actor → A Actor에게 메시지: "경험치 100" 핵심: 남의 상태를 직접 안 건드려. 메시지로만 소통.
어디서 쓰여?

Erlang/OTP 기반 게임 서버들이 이 방식이야. Riot Games가 LoL 채팅 서버에 Erlang을 썼고, 일부 인디 MMO들이 Elixir(Erlang VM)로 만들어.

개념적으로는 우리 서버의 IOCP 메시지 큐도 비슷해 — 다만 우리는 큐가 하나고 처리자도 하나인 거지.

문제점은?

범위 공격이 골치야. A가 주변 10명에게 광역기를 쓰면? 10개의 Actor에게 각각 메시지를 보내고, 각각의 응답을 기다려야 해.

메시지 왕복이 많아지면 지연(latency)이 쌓여. 싱글스레드에서는 for문 한 번이면 끝날 걸, Actor 모델에서는 비동기 메시지 10번이 필요해.

항목 Actor 모델
대표 사례 Erlang/OTP, Akka(Java), Orleans(.NET)
장점 락 없음, 분산 확장 용이, 장애 격리
단점 광역 처리 시 메시지 폭발, 디버깅 어려움
적합한 게임 개체 간 상호작용이 적은 게임, 채팅/로비 서버

Part 5. 패턴 3 — ECS 병렬 시스템

ECS가 멀티스레드랑 무슨 관련이야?

ECS(Entity Component System)에서는 로직이 System 단위로 분리돼 있어.

핵심은: 서로 다른 데이터를 읽는 System들은 동시에 돌릴 수 있다는 거야.

⚡ ECS 병렬 시스템 (Overwatch 스타일) 프레임 1개 처리: [병렬 가능] ─┬─ MovementSystem (Position, Velocity 읽기/쓰기) ├─ AISystem (AIState, Target 읽기/쓰기) └─ AnimationSystem (AnimState 읽기/쓰기) ↓ 전부 끝나면 [순차 처리] ─── CombatSystem (HP, Damage 읽기/쓰기) ↓ [병렬 가능] ─┬─ RenderSystem (Position, Mesh 읽기) └─ UISystem (HP, Name 읽기) 핵심: 같은 Component를 안 건드리는 System끼리는 동시 실행!
Overwatch가 이거 쓴다고?

맞아. Blizzard의 Tim Ford가 GDC 2017에서 발표했어. Overwatch는 ECS 아키텍처를 쓰고, System의 읽기/쓰기 대상이 명시적이라서 어떤 System이 병렬 가능한지 자동으로 판단할 수 있어.

Unity의 DOTS(Data-Oriented Technology Stack)도 같은 원리야. Burst Compiler가 자동으로 병렬 가능한 Job을 찾아서 멀티스레드로 돌려.

문제점은?

기존 코드를 ECS로 바꾸는 게 대공사야. OOP로 짠 코드를 ECS로 전환하려면 사실상 다시 짜는 거거든.

그리고 전투처럼 여러 Component를 동시에 건드리는 System은 결국 순차 처리해야 해서, 병렬화 이득이 제한적일 수 있어.

항목 ECS 병렬 시스템
대표 사례 Overwatch, Unity DOTS, Unreal Mass
장점 자동 병렬화 가능, 캐시 친화적, 성능 극대화
단점 기존 OOP 전환 불가, 전투 로직 병렬화 한계
적합한 게임 신규 프로젝트, 대규모 시뮬레이션

Part 6. 패턴 4 — 공간 분할 (Spatial Partitioning)

존 기반이랑 뭐가 달라?

존 기반은 고정된 구역이야. "이 대륙은 이 스레드". 경계가 바뀌지 않아.

공간 분할은 동적이야. 사람이 많은 곳은 잘게 쪼개고, 사람이 없는 곳은 합쳐. 경계가 실시간으로 움직여.

🔲 동적 공간 분할 (SpatialOS 스타일) 평소: ┌──────────────────┐ │ 워커 1 │ ← 넓은 영역, 유저 적음 │ │ └──────────────────┘ 공성전 시작: ┌────┬────┬────┬────┐ │ W1 │ W2 │ W3 │ W4 │ ← 같은 영역을 4개로 쪼갬 │50명│50명│50명│50명│ 워커(스레드) 4개가 분담 └────┴────┴────┴────┘ 핵심: 부하에 따라 워커 수를 실시간 조절
어디서 쓰여?

SpatialOS(Improbable)가 이 방식이야. 수백 명이 한 전장에 모여도 자동으로 워커를 늘려서 처리해.

핵심 아이디어: 게임 월드를 하나의 분산 시스템으로 보고, 각 서버 워커가 월드의 일부를 담당하되, 경계가 유동적이야.

문제점은?

경계에 걸친 엔티티 처리가 악몽이야. 플레이어 A가 워커 1과 워커 2의 경계에 서 있으면, 어느 워커가 A를 담당하지?

엔티티 마이그레이션(워커 간 이동) 로직이 극도로 복잡해. SpatialOS가 이걸 플랫폼 레벨에서 해결해주는 거지만, 직접 구현하면 난이도가 매우 높아.

항목 공간 분할
대표 사례 SpatialOS(Improbable), 자체 구현 엔진
장점 동적 스케일링, 공성전 같은 밀집 상황 대응
단점 경계 처리 극도로 복잡, 인프라 비용 높음
적합한 게임 대규모 오픈월드 PvP, 메타버스

Part 7. 4가지 패턴 비교 — 뭘 골라야 해?

패턴 분할 단위 공유 상태 구현 난이도 확장성
싱글스레드 (현재) 없음 전부 공유 (문제없음) 쉬움 1 코어 한계
존 기반 지역(Zone) 존 내부만 공유 보통 존 수만큼
Actor 모델 객체(Entity) 공유 없음 보통~어려움 높음
ECS 병렬 시스템(System) Component 단위 어려움 코어 수만큼
공간 분할 동적 영역 경계 부분만 공유 매우 어려움 매우 높음
우리 같은 서버는 어떤 게 현실적이야?

20년 된 OOP 코드를 ECS나 Actor로 바꾸는 건 사실상 새로 짜는 거야. 현실적인 선택지는:

1. 존/채널 기반 스레딩 — 기존 코드 거의 안 건드리고, 채널별로 프로세스를 분리. 가장 현실적.

2. 신규 프로젝트라면 — ECS + 병렬 시스템이 미래지향적.

3. 핵심은 "어디서 상태를 나눌 것인가"야. 나누는 단위가 다를 뿐, 원리는 같아.

결국 싱글스레드가 나쁜 건 아니야?

전혀 아니야. 동접 수천 명 수준이면 싱글스레드가 최선의 선택이야. 복잡도가 낮고, 버그가 적고, 유지보수가 쉬워.

멀티스레드는 "성능이 부족할 때" 어쩔 수 없이 선택하는 거지, 더 좋아서 쓰는 게 아니야. 복잡도는 반드시 비용이 되거든.

실무에서 주의할 점

멀티스레드 = 더 좋은 게 아니야. 싱글스레드로 충분하면 싱글이 최선이야.

기존 서버를 멀티스레드로 바꾸는 건 리팩토링이 아니라 재작성에 가까워.

"채널 분리"가 가장 적은 비용으로 가장 큰 효과를 내는 방법이야.

핵심 정리: MMO 멀티스레드 게임 루프

  • 싱글스레드 로직의 핵심 장점 = 레이스 컨디션 원천 차단, 락 불필요
  • 멀티스레드가 어려운 이유 = 게임 상태가 전부 연결되어 있어서 락 범위가 넓어짐
  • 존 기반 (WoW) = 지역별로 스레드 분리, 가장 현실적
  • Actor 모델 (Erlang) = 객체별 메일박스, 공유 메모리 제거, 광역기 처리가 약점
  • ECS 병렬 (Overwatch) = System 단위 자동 병렬화, 신규 프로젝트에 적합
  • 공간 분할 (SpatialOS) = 동적 영역 분할, 최강 확장성, 최고 난이도
  • 현실적 선택: 싱글로 충분하면 싱글, 부족하면 존/채널 분리부터
