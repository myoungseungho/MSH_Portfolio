MMO 서버인데 싱글스레드라고? 멀티스레드 게임 루프의 4가지 패턴

IOCP는 멀티인데 메시지 처리는 싱글 — 다른 MMO들은 어떻게 하고 있을까?

Part 1. 우리 서버는 왜 싱글스레드야?

IOCP 쓰면 멀티스레드 아니야?

먼저 하나 물어볼게. IOCP 워커 스레드가 4개 돌고 있으면, 게임 로직도 4배 빨라질까?

아니야. 네트워크 I/O만 멀티스레드야. 패킷을 받고 보내는 건 여러 워커가 하지만, 받은 메시지를 실제로 처리하는 건 메인 루프 하나에서 순차적으로 해.

비유하면 우체국이야. 배달부(IOCP 워커)는 여러 명이지만, 편지를 열어보고 답장 쓰는 사람(게임 로직)은 한 명이야.

📦 우리 서버 구조 (IOCP + 싱글스레드 로직) [클라이언트들] ──패킷──▶ [IOCP 워커 스레드 4개] ──큐──▶ [메인 루프 1개] (네트워크: 멀티) (게임 로직: 싱글) 메인 루프가 하는 일: while(true) { 1. 큐에서 메시지 꺼내기 2. 메시지 처리 (공격, 이동, 아이템...) 3. DB 호출 (동기) 4. 결과 패킷 전송 }
그게 왜 문제가 안 돼?

가장 큰 장점은 레이스 컨디션이 원천 차단된다는 거야. 플레이어 A가 아이템을 옮기는 도중에 플레이어 B가 그 아이템을 주울 일이 없어. 한 번에 하나씩 순서대로 처리하니까.

락(Lock)도 필요 없고, 데드락도 불가능하고, 디버깅도 쉬워. 20년 넘게 운영되는 게임 서버들이 대부분 이 방식인 이유가 있어.

그럼 뭐가 문제야?

새벽 3시에 전화가 왔어. '서버 터졌습니다.'

공성전에 2,000명이 몰렸는데, 메인 루프가 밀리기 시작한 거야. 큐에 메시지가 3만 개 쌓이고, 유저들은 5초째 화면이 멈춰 있었어.

이게 싱글스레드의 천장이야. CPU 코어 1개의 처리량에 물리적 한계가 있거든. 동접 1,000명까지는 여유롭지만, 한 곳에 수천 명이 몰리면 그 한 스레드가 감당을 못 해.

그래서 다른 MMO들은 어떻게 했을까? 메시지 처리 자체를 멀티스레드로 가져간 게임들이 있어.

Part 2. 멀티스레드 게임 로직이 어려운 이유

그냥 스레드 여러 개 돌리면 안 돼?

안 돼. 왜 안 되는지 직접 보여줄게.

HP 100인 몬스터가 있어. 스레드 2개가 동시에 공격해. A는 30 데미지, B는 50 데미지.

최종 HP가 뭐라고 생각해?

💥 정답: 20이 아니야 스레드 1: A가 공격 → HP 읽기(100) → 30 빼기 → HP 쓰기(70) ✓ 스레드 2: B가 공격 → HP 읽기(100) → 50 빼기 → HP 쓰기(50) ✓ 최종 HP = 50 (70도 될 수 있어) 정답은 20이어야 하는데, 50이 됐어. 원인: 두 스레드가 "동시에" HP 100을 읽었기 때문 이걸 레이스 컨디션(Race Condition)이라고 해.
락 걸면 되잖아?

멀티스레드 하면 보통 락(Lock)부터 떠올리잖아?

"락만 잘 걸면 된다" — 그게 함정이야.

게임은 "모든 게 연결"되어 있거든. A가 B를 공격하면: 데미지 계산 → 버프 확인 → HP 감소 → 사망 판정 → 경험치 → 퀘스트 → 아이템 드롭 → 파티 분배.

이 모든 데이터에 락을 걸면? 사실상 싱글스레드랑 같아져. 락 기다리는 시간 때문에 오히려 더 느릴 수도 있어.

그럼 방법이 없어?

있어. 핵심은 "공유 상태를 없애거나, 공유 범위를 줄이는 것"이야.

이걸 해결하는 패턴이 크게 4가지 있어. 실제 MMO들이 쓰고 있는 방법이야.

Part 3. 패턴 1 — 존(Zone) 기반 스레딩

"공유 범위를 줄인다"는 게 뭔데?

아파트로 생각해봐.

지금 우리 서버는 관리인 1명이 아파트 전체를 관리해. 101동부터 110동까지 혼자 다 해.

만약 동마다 관리인을 따로 두면? 101동 관리인은 101동만, 102동은 102동만 담당해. 자기 동 안에서는 혼자 일하니까 충돌이 없어.

이게 존(Zone) 기반 스레딩이야. 월드를 구역으로 쪼개서, 각 구역을 별도 스레드가 담당하는 거야.

🗺️ 존 기반 스레딩 (WoW 스타일) [월드 서버] ├─ 스레드 1: 동부 왕국 ── 플레이어 3,000명 ├─ 스레드 2: 칼림도어 ── 플레이어 2,500명 ├─ 스레드 3: 아웃랜드 ── 플레이어 1,200명 ├─ 스레드 4~20: 던전 인스턴스들 └─ 메시지 큐: 존 간 통신 (귓말, 거래, 파티) 핵심: 같은 존 안에서는 싱글스레드! 존이 다르면 서로 간섭 없음
WoW가 이거 쓴다고?

WoW(월드 오브 워크래프트)가 대표적이야. 각 대륙이나 던전 인스턴스가 별도 스레드에서 돌아가.

EVE Online도 솔라 시스템 단위로 나눠. 성계 하나가 하나의 "존"인 셈이야.

근데 한 존에 사람이 3,000명 몰리면?

그게 문제야. 존은 고정이니까, 한 존에 사람이 몰리면 그 스레드만 병목이 돼.

WoW에서 오그리마(수도)에 동접 몰릴 때 렉 걸리는 거 — "오그리마 렉"이 바로 이거야.

그리고 존 경계를 넘을 때도 문제야. 플레이어가 존 A에서 존 B로 이동하면, 한 스레드에서 다른 스레드로 캐릭터 데이터를 이관해야 해. 이때 잠깐 끊기거나 로딩이 생겨.

항목 존 기반 스레딩
대표 게임 WoW, EVE Online (솔라 시스템 단위)
장점 구현 간단, 존 내부는 싱글스레드의 안전성
단점 존 경계 이동 시 끊김, 인구 쏠림 시 병목
적합한 게임 존/채널 구분이 명확한 MMO

Part 4. 패턴 2 — Actor 모델

존 기반은 "지역"으로 나누잖아. 그것 말고 다른 방법은?

존 기반이 아파트를 "동" 단위로 나눈 거라면, Actor 모델은 "세대" 단위로 나눈 거야.

각 엔티티(플레이어, 몬스터, NPC)가 자기만의 메일박스를 갖고 있어. 남의 상태를 직접 안 건드리고, 메시지를 보내서 소통해.

직접 안 건드린다는 게 무슨 뜻이야?

우리 서버에서 A가 몬스터 X를 공격하면 이렇게 하지?

monster->hp -= damage; — 몬스터 HP를 직접 수정해.

Actor 모델에서는 달라. A가 X한테 "30 데미지" 메시지를 보내. X는 자기 메일박스에서 그 메시지를 꺼내서 자기가 직접 HP를 깎아. 남의 메모리를 직접 건드리는 코드가 없으니까 락이 필요 없어.

📬 Actor 모델 [Player A Actor] ←── 메일박스: 공격 결과, 버프 적용, ... └─ 자기 상태만 수정 (HP, MP, 인벤토리) [Monster X Actor] ←── 메일박스: 피격, AI 틱, ... └─ 자기 상태만 수정 (HP, 위치, 타겟) A가 X를 공격하면? 1. A Actor → X Actor에게 메시지: "30 데미지" 2. X Actor가 자기 메일박스에서 꺼내서 처리 3. X Actor → A Actor에게 메시지: "경험치 100" 핵심: 남의 상태를 직접 안 건드려. 메시지로만 소통.
그럼 광역기 쓰면? 주변 10명한테 데미지 주는 건?

여기서 문제가 터져. A가 광역기를 쓰면 10개의 Actor에게 각각 메시지를 보내고, 각각의 응답을 기다려야 해.

싱글스레드에서는 for문 한 번이면 끝나는 걸, Actor 모델에서는 비동기 메시지 10번이 필요해. 메시지 왕복이 많아지면 지연이 쌓여.

Erlang/OTP 기반 게임 서버나 Riot Games의 채팅 서버가 이 방식을 쓰는데, 전투처럼 상호작용이 빈번한 곳보다는 상호작용이 적은 서비스에 더 적합해.

항목 Actor 모델
대표 사례 Erlang/OTP, Akka(Java), Orleans(.NET)
장점 락 없음, 분산 확장 용이, 장애 격리
단점 광역 처리 시 메시지 폭발, 디버깅 어려움
적합한 게임 개체 간 상호작용이 적은 게임, 채팅/로비 서버

Part 5. 패턴 3 — ECS 병렬 시스템

존 기반은 "지역"을 나누고, Actor는 "객체"를 나눴잖아. 또 뭘 나눌 수 있어?

"작업"을 나눌 수 있어.

이동, AI, 전투, 애니메이션 — 이런 작업(System)별로 나눠서, 서로 다른 데이터를 쓰는 작업들은 동시에 돌리는 거야.

이게 ECS(Entity Component System) 병렬 시스템이야.

어떤 작업이 동시에 돌 수 있는데?

생각해봐. 이동(Position, Velocity)이랑 AI(AIState, Target)랑 — 건드리는 데이터가 겹쳐?

안 겹쳐. 그러면 동시에 돌려도 돼.

반대로 전투(HP, Damage)랑 이동(Position)은? HP 깎으면서 위치도 바꾸면 문제가 생길 수 있으니까, 이건 순서대로 해야 해.

핵심: 같은 데이터를 안 건드리는 System끼리는 자동으로 병렬 실행할 수 있어.

⚡ ECS 병렬 시스템 (Overwatch 스타일) 프레임 1개 처리: [병렬 가능] ─┬─ MovementSystem (Position, Velocity) ├─ AISystem (AIState, Target) └─ AnimationSystem (AnimState) ↓ 전부 끝나면 [순차 처리] ─── CombatSystem (HP, Damage) ↓ [병렬 가능] ─┬─ RenderSystem (Position, Mesh) └─ UISystem (HP, Name) 핵심: 같은 Component를 안 건드리는 System끼리는 동시 실행!
실제로 이거 쓰는 게임이 있어?

Blizzard의 Overwatch가 대표적이야. GDC 2017에서 Tim Ford가 발표했어. System의 읽기/쓰기 대상이 명시적이라서 어떤 System이 병렬 가능한지 자동으로 판단할 수 있어.

근데 기존 OOP 코드를 ECS로 바꾸는 건 사실상 다시 짜는 거야. 우리 서버처럼 20년 된 코드를 ECS로 전환하는 건 현실적이지 않아. 신규 프로젝트에서 시작할 때 선택지야.

항목 ECS 병렬 시스템
대표 사례 Overwatch, Unity DOTS, Unreal Mass
장점 자동 병렬화 가능, 캐시 친화적, 성능 극대화
단점 기존 OOP 전환 불가, 전투 로직 병렬화 한계
적합한 게임 신규 프로젝트, 대규모 시뮬레이션

Part 6. 패턴 4 — 공간 분할 (Spatial Partitioning)

존 기반이 고정 구역이라 사람 몰리면 병목이 생겼잖아. 그거 해결한 방법은 없어?

있어. 존 기반의 약점을 정확히 찔렀어.

존 기반은 경계가 고정이야. "이 대륙은 이 스레드" 식이라 바뀌지 않아.

공간 분할은 경계가 움직여. 사람이 많은 곳은 잘게 쪼개고, 사람이 없는 곳은 합쳐. 실시간으로.

🔲 동적 공간 분할 (SpatialOS 스타일) 평소: ┌──────────────────┐ │ 워커 1 │ ← 넓은 영역, 유저 적음 │ │ └──────────────────┘ 공성전 시작: ┌────┬────┬────┬────┐ │ W1 │ W2 │ W3 │ W4 │ ← 같은 영역을 4개로 쪼갬 │50명│50명│50명│50명│ 워커(스레드) 4개가 분담 └────┴────┴────┴────┘ 핵심: 부하에 따라 워커 수를 실시간 조절
완벽해 보이는데, 문제는?

플레이어 A가 워커 1과 워커 2의 경계에 서 있으면 어떻게 될까?

어느 워커가 A를 담당하지? A한테 날아오는 광역기는 누가 처리해?

경계에 걸친 엔티티 처리가 악몽이야. 엔티티를 워커 간에 실시간으로 이관하는 로직이 극도로 복잡해.

SpatialOS(Improbable)가 이걸 플랫폼 레벨에서 해결해주는 거지만, 직접 구현하면 난이도가 최상급이야.

항목 공간 분할
대표 사례 SpatialOS(Improbable), 자체 구현 엔진
장점 동적 스케일링, 공성전 같은 밀집 상황 대응
단점 경계 처리 극도로 복잡, 인프라 비용 높음
적합한 게임 대규모 오픈월드 PvP, 메타버스

Part 7. 비교 — 뭘 골라야 해?

패턴 분할 단위 공유 상태 구현 난이도 확장성
싱글스레드 (현재) 없음 전부 공유 (문제없음) 쉬움 1 코어 한계
존 기반 지역(Zone) 존 내부만 공유 보통 존 수만큼
Actor 모델 객체(Entity) 공유 없음 보통~어려움 높음
ECS 병렬 시스템(System) Component 단위 어려움 코어 수만큼
공간 분할 동적 영역 경계 부분만 공유 매우 어려움 매우 높음
우리 같은 서버는 어떤 게 현실적이야?

20년 된 OOP 코드를 ECS나 Actor로 바꾸는 건 사실상 새로 짜는 거야. 현실적인 선택지는:

1. 존/채널 기반 스레딩 — 기존 코드 거의 안 건드리고, 채널별로 프로세스를 분리. 가장 현실적.

2. 신규 프로젝트라면 — ECS + 병렬 시스템이 미래지향적.

3. 핵심은 "어디서 상태를 나눌 것인가"야. 나누는 단위가 다를 뿐, 원리는 같아.

결국 싱글스레드가 나쁜 건 아니야?

전혀 아니야. 동접 수천 명 수준이면 싱글스레드가 최선의 선택이야. 복잡도가 낮고, 버그가 적고, 유지보수가 쉬워.

멀티스레드는 "성능이 부족할 때" 어쩔 수 없이 선택하는 거지, 더 좋아서 쓰는 게 아니야. 복잡도는 반드시 비용이 되거든.

실무에서 주의할 점

멀티스레드 = 더 좋은 게 아니야. 싱글스레드로 충분하면 싱글이 최선이야.

기존 서버를 멀티스레드로 바꾸는 건 리팩토링이 아니라 재작성에 가까워.

"채널 분리"가 가장 적은 비용으로 가장 큰 효과를 내는 방법이야.

핵심 정리: MMO 멀티스레드 게임 루프

  • 싱글스레드 로직의 핵심 장점 = 레이스 컨디션 원천 차단, 락 불필요
  • 멀티스레드가 어려운 이유 = 게임 상태가 전부 연결되어 있어서 락 범위가 넓어짐
  • 존 기반 (WoW) = 지역별로 스레드 분리, 가장 현실적
  • Actor 모델 (Erlang) = 객체별 메일박스, 공유 메모리 제거, 광역기 처리가 약점
  • ECS 병렬 (Overwatch) = System 단위 자동 병렬화, 신규 프로젝트에 적합
  • 공간 분할 (SpatialOS) = 동적 영역 분할, 최강 확장성, 최고 난이도
  • 현실적 선택: 싱글로 충분하면 싱글, 부족하면 존/채널 분리부터
