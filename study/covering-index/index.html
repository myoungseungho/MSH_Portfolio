Covering Index - 데이터 페이지 안 가고 인덱스에서 모든 걸 해결

Part 1. 책에서 원하는 정보 찾기

DB 인덱스가 뭐야?

책의 목차(색인)와 같아.

800페이지 책에서 "Parameter Sniffing"을 찾으려면?

목차 보고 페이지 찾아서 가면 되지.

맞아! 이게 일반적인 인덱스 사용법이야.

목차 → 페이지 번호 확인 → 해당 페이지로 이동 → 내용 읽기

그럼 Covering Index는 뭐가 달라?

목차에 원하는 정보가 다 있어서 본문 안 봐도 되는 것!

예: "Parameter Sniffing - 해결책: RECOMPILE (P.234)"

목차만 보고도 "해결책은 RECOMPILE"이란 걸 알 수 있음.

📖 일반 인덱스 사용: 목차 확인 → "P.234" 발견 → 234페이지로 이동 → 내용 읽기 (2단계: 목차 + 본문) 📖 Covering Index: 목차 확인 → 목차에 정보 다 있음 → 끝! (1단계: 목차만)

Part 2. 이걸 DB에서 보면

DB에서는 어떤 상황이야?

캐릭터 레벨 랭킹을 조회한다고 하자.

-- 레벨 Top 10 조회 SELECT i32CharSID, i32Level FROM TCharacter ORDER BY i32Level DESC TOP 10
i32Level에 인덱스 있으면 빠르겠네?

인덱스 구조를 보자.

🗂️ IX_Level 인덱스 (i32Level에만): ┌─────────────────────────────────────┐ │ i32Level │ RowID (데이터 위치) │ ├──────────┼──────────────────────────┤ │ 99 │ → 데이터 페이지 #142 │ │ 98 │ → 데이터 페이지 #87 │ │ 97 │ → 데이터 페이지 #256 │ └──────────┴──────────────────────────┘ ❓ 문제: i32CharSID를 알려면? → 데이터 페이지로 가야 함 (추가 I/O)
아 인덱스에 레벨만 있고, CharSID는 없구나!

그래서 인덱스로 레벨 순서는 알지만,

CharSID를 알려면 데이터 페이지로 다시 가야 해.

이걸 Key Lookup 또는 RID Lookup이라고 해.

Part 3. Key Lookup이 느린 이유

데이터 페이지 한 번 더 가는 게 그렇게 느려?

1건이면 괜찮아. 1만 건이면?

인덱스에서 1만 건 찾음 ↓ 1만 번 데이터 페이지 방문 (각각 다른 위치) ↓ Random I/O 1만 번! 💥 ✨ 반면 Covering Index라면: 인덱스에서 1만 건 찾음 → 끝! (데이터 페이지 방문 0번)
1만 번 랜덤 I/O... 진짜 느리겠다.

디스크 랜덤 읽기는 순차 읽기보다 100배 느릴 수 있어.

SSD도 랜덤 I/O는 순차보다 느림.

Part 4. Covering Index 만들기

그럼 어떻게 하면 Covering Index가 돼?

SELECT하는 모든 컬럼을 인덱스에 포함시키면 돼.

-- 쿼리가 필요한 컬럼: i32CharSID, i32Level -- Covering Index 생성 CREATE INDEX IX_Level_Cover ON TCharacter (i32Level DESC, i32CharSID)
🗂️ IX_Level_Cover 인덱스 (Covering): ┌─────────────────────────────────────┐ │ i32Level │ i32CharSID │ (RowID) │ ├──────────┼────────────┼────────────┤ │ 99 │ 12345 │ ... │ │ 98 │ 67890 │ ... │ │ 97 │ 11111 │ ... │ └──────────┴────────────┴────────────┘ ✅ 이제 인덱스만 보면: - 레벨 순서도 알고 - CharSID도 알고 - 데이터 페이지 갈 필요 없음!
SELECT에 있는 컬럼을 다 인덱스에 넣으면 되는 거네?

맞아! 추가로 WHERE 조건에 쓰이는 컬럼도 있어야 해.

-- 이 쿼리를 Covering하려면 SELECT i32CharSID, szCharName FROM TCharacter WHERE i32WorldNo = 1 AND i32Level >= 90 -- 인덱스에 필요한 컬럼: -- 1. WHERE 조건: i32WorldNo, i32Level -- 2. SELECT 컬럼: i32CharSID, szCharName CREATE INDEX IX_World_Level_Cover ON TCharacter (i32WorldNo, i32Level) INCLUDE (i32CharSID, szCharName)

Part 5. 실행 계획에서 확인하기

Covering Index가 적용됐는지 어떻게 알아?

실행 계획에서 확인할 수 있어.

❌ Covering 안 됨: ┌────────────────┐ ┌─────────────────┐ │ Index Seek │ → │ Key Lookup │ │ (IX_Level) │ │ (TCharacter) │ └────────────────┘ └─────────────────┘ ↓ ↓ 인덱스에서 찾음 데이터 페이지 추가 방문 ✅ Covering Index 적용: ┌───────────────────────────┐ │ Index Seek │ │ (IX_Level_Cover) │ │ ✨ Key Lookup 없음! │ └───────────────────────────┘ ↓ 인덱스에서 모두 해결
Key Lookup이 없으면 Covering된 거구나!

맞아! SSMS에서 실행 계획 보면 Index Seek만 있으면 성공.

Key Lookup이나 RID Lookup이 보이면 Covering 안 된 것.

Part 6. 실제로 얼마나 빨라져?

성능 차이가 체감될 정도야?

상황에 따라 10배~100배 차이 날 수 있어.

시나리오 Key Lookup Covering Index
1만 건 조회 12,000 I/O 120 I/O
조회 시간 2.5초 0.05초
CPU 시간 높음 낮음
와, 50배 차이?

특히 대량 조회일수록 차이가 커.

랭킹, 리스트, 검색 등에서 효과가 크지.

Part 7. 주의해야 할 점

모든 인덱스를 Covering으로 만들면 안 돼?

인덱스 크기가 커져. 저장공간과 쓰기 성능 영향.

⚠️ 인덱스가 커지면: 1. 저장 공간 증가 - 원래: 100MB 인덱스 - INCLUDE 추가 후: 500MB 인덱스 2. INSERT/UPDATE 느려짐 - 인덱스 유지비용 증가 - 쓰기 작업마다 더 많은 데이터 갱신 3. 메모리 사용량 증가 - 인덱스를 메모리에 올리는데 더 많은 공간 필요
그럼 언제 Covering Index를 써야 해?

다음 조건을 만족할 때:

상황 Covering Index
자주 실행되는 쿼리 적용 추천
대량 데이터 조회 (1000건+) 효과 큼
가끔 실행 (하루 1-2회) 효과 적음
단건 조회 (PK로 1건) 불필요

실전 예시: 문파 랭킹 조회

-- 프로시저: gp_LoadMunpaRank -- 문파 레벨+점수 순으로 Top 50 조회 SELECT TOP 50 i32MunpaSID, szMunpaName, i32Level, i64Score FROM TMunpa WHERE i32WorldNo = @i32WorldNo ORDER BY i32Level DESC, i64Score DESC -- Covering Index 생성 CREATE INDEX IX_Munpa_Rank_Cover ON TMunpa (i32WorldNo, i32Level DESC, i64Score DESC) INCLUDE (i32MunpaSID, szMunpaName) -- 결과: -- Before: Index Seek + Key Lookup (850ms) -- After: Index Seek only (15ms)

⚠️ Covering Index 설계 원칙

1. WHERE 조건 컬럼은 인덱스 키에 (검색용)

2. SELECT 컬럼은 INCLUDE에 (조회용)

3. ORDER BY 컬럼도 인덱스 키에 (정렬용)

📝 핵심 정리

  • Covering Index = 인덱스만으로 쿼리 완료 (테이블 방문 X)
  • Key Lookup 제거 → Random I/O 감소 → 대폭 성능 향상
  • SELECT, WHERE, ORDER BY에 쓰이는 모든 컬럼 포함
  • 단, 인덱스 크기 증가 → 쓰기 성능 영향 고려
  • 자주 실행되는 대량 조회 쿼리에 특히 효과적
