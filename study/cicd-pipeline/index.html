CI/CD Pipeline

코드 머지하면 자동으로 배포되는 마법의 파이프라인

Part 1: CI/CD가 뭐야?

CI/CD가 뭔지 쉽게 설명해줘
비유: 자동차 공장의 자동화 라인

수동 생산: 작업자가 부품 하나하나 손으로 조립 → 느리고 실수 많음
자동화 라인: 컨베이어 벨트 위에서 자동 조립 → 빠르고 일관됨

CI/CD = 소프트웨어의 자동화 생산 라인!

CI (Continuous Integration) - 지속적 통합 ───────────────────────────────────────── 개발자가 코드 푸시 ↓ 자동으로 빌드 ↓ 자동으로 테스트 ↓ 문제 있으면 알림! "코드를 자주 합치고, 자동으로 검증하자" CD (Continuous Delivery/Deployment) - 지속적 배포 ───────────────────────────────────────── 테스트 통과 ↓ 자동으로 배포 준비 ↓ (승인 버튼 or 자동) 배포! ↓ 서비스에 반영 "언제든 배포할 수 있는 상태를 유지하자"
CI랑 CD가 어떻게 다른 거야?
구분 CI (통합) CD (배포)
목적 코드 품질 검증 서비스에 반영
자동화 빌드 + 테스트 배포 준비 + 릴리스
타이밍 코드 푸시할 때마다 테스트 통과 후
결과 "빌드 성공/실패" "배포 완료"
CD의 두 가지 의미
- Continuous Delivery: 배포 준비까지 자동, 실제 배포는 승인 후
- Continuous Deployment: 배포까지 완전 자동화

Part 2: 왜 CI/CD가 필요해?

수동으로 빌드하고 배포하면 안 돼?
수동 배포의 비극 (금요일 오후 5시)

개발자: "빌드할게요..." (30분)
개발자: "테스트 돌릴게요..." (1시간)
개발자: "서버에 올릴게요..." (실수로 잘못된 브랜치 배포)
개발자: "앗, 잘못 올렸다!"

결과: 금요일 저녁 장애 → 주말 근무 확정
CI/CD가 있다면

개발자: "코드 푸시!" (10초)
CI/CD: 자동 빌드 → 자동 테스트 → 자동 배포 (15분)
CI/CD: "배포 완료!" 알림

결과: 실수 원천 차단, 빠른 피드백
CI/CD의 핵심 이점이 뭐야?

빠른 피드백

코드 푸시 후 10분 안에 "문제 있어요!" 알림. 문제를 빨리 알수록 고치기 쉬움

일관된 품질

같은 테스트를 매번 자동 실행. "내 PC에서는 됐는데..." 방지

배포 두려움 제거

자동화된 프로세스로 언제든 자신 있게 배포. 금요일도 OK!

이력 추적

누가, 언제, 무엇을 배포했는지 기록. 문제 시 롤백 쉬움

Part 3: 파이프라인은 어떻게 생겼어?

CI/CD 파이프라인의 전체 흐름을 보여줘
전형적인 CI/CD 파이프라인: [1. Source] [2. Build] [3. Test] ─────────── ────────── ───────── Git Push → 코드 빌드 → 단위 테스트 PR 생성 의존성 설치 통합 테스트 브랜치 머지 컴파일 E2E 테스트 [4. Package] [5. Deploy] [6. Monitor] ──────────── ─────────── ──────────── Docker 이미지 → Dev 배포 → 로그 확인 아티팩트 저장 Staging 배포 메트릭 확인 버전 태깅 Prod 배포 알람 대기
각 단계별로 자세히 설명해줘
단계 하는 일 실패하면?
1. Source 코드 변경 감지 (Push, PR) 파이프라인 시작 안 함
2. Build 소스 코드 → 실행 파일 컴파일 에러 알림
3. Test 자동화된 테스트 실행 테스트 실패 알림, 배포 중단
4. Package 배포 가능한 형태로 패키징 이미지 빌드 실패
5. Deploy 실제 서버에 배포 롤백 또는 재시도
6. Monitor 배포 후 상태 확인 자동 롤백 트리거

Part 4: 실제 CI/CD 설정 (GitHub Actions)

GitHub Actions로 CI/CD를 만들어보자

GitHub Actions는 가장 많이 사용되는 CI/CD 도구 중 하나입니다.

# .github/workflows/ci-cd.yml name: CI/CD Pipeline # 언제 실행할지 on: push: branches: [main, develop] # main, develop에 푸시하면 pull_request: branches: [main] # main PR이면 jobs: # 1단계: 빌드 build: runs-on: ubuntu-latest steps: - name: 코드 체크아웃 uses: actions/checkout@v3 - name: Node.js 설정 uses: actions/setup-node@v3 with: node-version: '18' cache: 'npm' - name: 의존성 설치 run: npm ci - name: 빌드 run: npm run build - name: 빌드 결과물 저장 uses: actions/upload-artifact@v3 with: name: build-output path: dist/ # 2단계: 테스트 test: needs: build # 빌드 성공 후 실행 runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: 단위 테스트 run: npm test - name: 커버리지 리포트 run: npm run coverage # 3단계: 배포 (main 브랜치만) deploy: needs: test # 테스트 성공 후 실행 if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest steps: - name: 빌드 결과물 다운로드 uses: actions/download-artifact@v3 with: name: build-output - name: 서버에 배포 run: | echo "배포 스크립트 실행" ./deploy.sh production
핵심 키워드들을 설명해줘
키워드 설명 예시
on: 언제 파이프라인 실행할지 push, pull_request, schedule
jobs: 실행할 작업 목록 build, test, deploy
needs: 의존성 (먼저 실행할 job) needs: build
runs-on: 실행할 환경 ubuntu-latest, windows-latest
steps: 순서대로 실행할 명령 checkout, install, build
if: 조건부 실행 if: github.ref == 'refs/heads/main'

Part 5: 테스트 자동화

CI에서 어떤 테스트를 돌려야 해?
테스트 피라미드 (CI에서 실행 순서): /\ / \ E2E 테스트 (10%) / \ - 실제 시나리오 테스트 /------\ - 느리지만 확실 / \ / \ 통합 테스트 (20%) / \ - 컴포넌트 간 연동 /--------------\- DB, API 연동 확인 / \ / \ 단위 테스트 (70%) --------------------\ - 함수, 클래스 단위 - 빠르고 많이
테스트 종류 실행 시점 소요 시간
단위 테스트 모든 커밋 1~5분
통합 테스트 PR 생성/머지 5~15분
E2E 테스트 배포 전 15~30분
부하 테스트 야간/주간 30분~2시간
테스트 실패하면 어떻게 돼?
Fail Fast 원칙
테스트 하나라도 실패하면 → 파이프라인 즉시 중단 → 배포 안 함!
이유: 버그 있는 코드가 프로덕션에 나가면 안 되니까
PR 머지 블로킹
GitHub에서 "CI 통과해야만 머지 가능" 설정 가능
→ 테스트 실패하면 머지 버튼 비활성화

Part 6: 배포 전략

배포할 때 서비스가 안 끊기게 하려면?

무중단 배포 전략들:

1. 롤링 배포 (Rolling) ─────────────────────── 기존: [v1][v1][v1][v1] ↓ 진행: [v2][v1][v1][v1] (1개씩 교체) ↓ 진행: [v2][v2][v1][v1] ↓ 완료: [v2][v2][v2][v2] 장점: 점진적, 리소스 효율적 단점: 롤백 시간 오래 걸림 2. 블루-그린 배포 (Blue-Green) ─────────────────────────────── Blue (현재): [v1][v1][v1][v1] ← 트래픽 Green (대기): [v2][v2][v2][v2] ↓ (스위치) Blue (대기): [v1][v1][v1][v1] Green (현재): [v2][v2][v2][v2] ← 트래픽 장점: 즉시 롤백 가능 단점: 2배 리소스 필요 3. 카나리 배포 (Canary) ─────────────────────── 기존: [v1][v1][v1][v1][v1][v1][v1][v1][v1][v1] (100%) ↓ 카나리: [v2] (10%) + [v1][v1][v1][v1][v1][v1][v1][v1][v1] (90%) ↓ (문제 없으면) 확대: [v2][v2][v2][v2][v2] (50%) + [v1][v1][v1][v1][v1] (50%) ↓ 완료: [v2][v2][v2][v2][v2][v2][v2][v2][v2][v2] (100%) 장점: 위험 최소화, 점진적 검증 단점: 복잡한 설정 필요
어떤 전략을 선택해야 해?
상황 추천 전략 이유
리소스 제한 롤링 추가 서버 불필요
빠른 롤백 필수 블루-그린 스위치 한 번으로 롤백
신규 기능 검증 카나리 일부 유저만 테스트
게임 서버 롤링 + 카나리 채널 단위 점진 배포

Part 7: CI/CD 베스트 프랙티스

CI/CD 잘 운영하는 팁 알려줘

Fast Feedback

파이프라인은 10분 이내. 느리면 개발자가 안 기다리고 다른 일 함 → 빠른 테스트 먼저, 느린 테스트는 병렬로

Fail Fast

문제가 생기면 바로 중단. 계속 진행해봤자 시간 낭비 → 빠른 테스트를 앞에 배치

환경 일관성

Dev = Staging = Prod (최대한 동일하게). "내 PC에서는 됐는데" 방지 → Docker로 환경 고정

시크릿 관리

비밀번호, API키는 코드에 절대 넣지 마! → 환경변수, Secret Manager 사용

롤백 준비

이전 버전 항상 보관. 문제 시 원클릭 롤백 → 아티팩트 버전 관리 필수

피해야 할 안티패턴은?
CI/CD 안티패턴 TOP 5

1. 테스트 없이 배포: 테스트 스킵하면 버그 직행
2. 수동 단계 남겨두기: "이건 수동으로 해야 해" = 실수 발생점
3. 너무 느린 파이프라인: 30분 넘으면 개발자가 우회함
4. 실패 무시하기: "어차피 작동하잖아" = 기술 부채 축적
5. 롤백 계획 없음: 문제 터지면 패닉 상태

핵심 정리: CI/CD Pipeline

  • CI (지속적 통합): 코드 푸시 → 자동 빌드 → 자동 테스트
  • CD (지속적 배포): 테스트 통과 → 자동 배포 (또는 승인 후)
  • 파이프라인: Source → Build → Test → Package → Deploy → Monitor
  • 배포 전략: 롤링, 블루-그린, 카나리 중 상황에 맞게 선택
  • 핵심 원칙: Fast Feedback, Fail Fast, 환경 일관성, 롤백 준비
  • 목표: 자동화로 실수 방지, 빠른 피드백, 자신 있는 배포!
