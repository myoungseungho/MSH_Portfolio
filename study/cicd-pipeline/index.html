CI/CD Pipeline

코드 머지하면 자동으로 테스트 도는 법

1. CI/CD가 뭐야?

수동으로 빌드하면 안 돼?

사람은 실수한다!

수동 배포의 문제: 금요일 오후 5시: 개발자 A: "빌드할게요..." (30분 후) 개발자 A: "테스트 돌릴게요..." (1시간 후) 개발자 A: "서버에 올릴게요..." (실수로 dev 브랜치 배포) 개발자 A: "앗, 잘못 올렸다!" 결과: - 금요일 저녁 장애 - 주말 근무 확정 - "누가 배포했어?!" 범인 찾기
CI랑 CD는 뭐가 달라?
CI (Continuous Integration): 코드 변경 -> 자동 빌드 -> 자동 테스트 "코드 품질을 계속 검증" CD (Continuous Delivery/Deployment): 테스트 통과 -> 자동 배포 준비 -> (승인 후) 배포 "언제든 배포할 수 있는 상태 유지" 전체 흐름: [Git Push] -> [CI: 빌드/테스트] -> [CD: 배포] | | 자동 실행 자동 or 승인 후

2. 파이프라인은 어떻게 생겼어?

게임 서버 CI/CD는?
게임 서버 CI/CD 파이프라인: [1. Source] [2. Build] [3. Test] Git Push -> CMake 빌드 -> 단위 테스트 PR 생성 Docker 빌드 통합 테스트 부하 테스트 [4. Artifact] [5. Deploy] [6. Monitor] 빌드 저장 -> Dev 배포 -> 로그 확인 이미지 푸시 Staging 배포 메트릭 확인 Prod 배포 알람 대기
GitHub Actions로 보여줘
# .github/workflows/ci-cd.yml name: Game Server CI/CD on: push: branches: [main, develop] pull_request: branches: [main] jobs: # 1. 빌드 build: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: Setup Build Environment run: | sudo apt-get update sudo apt-get install -y cmake g++ libboost-all-dev - name: Build run: | mkdir build && cd build cmake .. -DCMAKE_BUILD_TYPE=Release make -j$(nproc) - name: Upload Artifact uses: actions/upload-artifact@v3 with: name: game-server path: build/bin/ # 2. 테스트 test: needs: build runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - name: Download Artifact uses: actions/download-artifact@v3 - name: Run Unit Tests run: ./build/bin/test_runner --gtest_output=xml:test-results.xml - name: Run Integration Tests run: | docker-compose up -d ./scripts/integration_test.sh docker-compose down - name: Upload Test Results uses: actions/upload-artifact@v3 with: name: test-results path: test-results.xml # 3. 배포 (main 브랜치만) deploy: needs: test if: github.ref == 'refs/heads/main' runs-on: ubuntu-latest steps: - name: Deploy to Staging run: | ./scripts/deploy.sh staging - name: Run Smoke Tests run: | ./scripts/smoke_test.sh staging - name: Deploy to Production if: success() environment: name: production run: | ./scripts/deploy.sh production

3. 빌드 자동화

C++ 게임 서버 빌드는?
# CMakeLists.txt cmake_minimum_required(VERSION 3.16) project(GameServer VERSION 1.0.0) set(CMAKE_CXX_STANDARD 17) # 의존성 find_package(Boost REQUIRED COMPONENTS system thread) find_package(Protobuf REQUIRED) # 소스 파일 file(GLOB_RECURSE SOURCES "src/*.cpp") # 실행 파일 add_executable(game_server ${SOURCES}) target_link_libraries(game_server Boost::system Boost::thread protobuf::libprotobuf ) # 테스트 enable_testing() add_subdirectory(tests) # 설치 install(TARGETS game_server DESTINATION bin)
# Dockerfile (멀티스테이지 빌드) # 1. 빌드 스테이지 FROM ubuntu:22.04 AS builder RUN apt-get update && apt-get install -y \ cmake g++ libboost-all-dev libprotobuf-dev WORKDIR /app COPY . . RUN mkdir build && cd build && \ cmake .. -DCMAKE_BUILD_TYPE=Release && \ make -j$(nproc) # 2. 런타임 스테이지 FROM ubuntu:22.04 RUN apt-get update && apt-get install -y \ libboost-system1.74.0 libboost-thread1.74.0 COPY --from=builder /app/build/bin/game_server /usr/local/bin/ EXPOSE 9000 CMD ["game_server"]

4. 테스트 자동화

어떤 테스트를 자동화해?
테스트 종류 실행 시점 소요 시간
단위 테스트 모든 커밋 1~5분
통합 테스트 PR 생성/머지 5~15분
E2E 테스트 배포 전 15~30분
부하 테스트 야간/주간 30분~2시간
게임 서버 단위 테스트 예시는?
// tests/test_inventory.cpp #include #include "inventory.h" class InventoryTest : public ::testing::Test { protected: void SetUp() override { inventory = new Inventory(MAX_SLOTS); } void TearDown() override { delete inventory; } Inventory* inventory; }; TEST_F(InventoryTest, AddItem_Success) { Item sword(1001, "검", 1); EXPECT_TRUE(inventory->AddItem(sword)); EXPECT_EQ(inventory->GetItemCount(), 1); } TEST_F(InventoryTest, AddItem_FullInventory) { // 인벤토리 가득 채우기 for (int i = 0; i < MAX_SLOTS; i++) { inventory->AddItem(Item(i, "아이템", 1)); } // 추가 시도 Item extra(9999, "추가 아이템", 1); EXPECT_FALSE(inventory->AddItem(extra)); } TEST_F(InventoryTest, RemoveItem_NotFound) { EXPECT_FALSE(inventory->RemoveItem(9999)); } TEST_F(InventoryTest, StackItem_SameType) { Item potion1(2001, "포션", 10); Item potion2(2001, "포션", 5); inventory->AddItem(potion1); inventory->AddItem(potion2); // 같은 아이템이 합쳐져야 함 EXPECT_EQ(inventory->GetItemCount(), 1); EXPECT_EQ(inventory->GetItem(2001)->GetQuantity(), 15); }

5. 배포 자동화

쿠버네티스 배포는?
# k8s/deployment.yaml apiVersion: apps/v1 kind: Deployment metadata: name: game-server spec: replicas: 3 selector: matchLabels: app: game-server template: metadata: labels: app: game-server spec: containers: - name: game-server image: registry.example.com/game-server:${VERSION} ports: - containerPort: 9000 env: - name: GAME_ENV value: production resources: requests: memory: "512Mi" cpu: "500m" limits: memory: "2Gi" cpu: "2000m" readinessProbe: httpGet: path: /health port: 9000 initialDelaySeconds: 10 livenessProbe: httpGet: path: /health port: 9000 initialDelaySeconds: 30
# scripts/deploy.sh #!/bin/bash ENV=$1 VERSION=$(git rev-parse --short HEAD) echo "Deploying version $VERSION to $ENV..." # 1. 이미지 태그 docker tag game-server:latest registry.example.com/game-server:$VERSION docker push registry.example.com/game-server:$VERSION # 2. 쿠버네티스 배포 kubectl set image deployment/game-server \ game-server=registry.example.com/game-server:$VERSION \ -n $ENV # 3. 롤아웃 대기 kubectl rollout status deployment/game-server -n $ENV # 4. 검증 ./scripts/smoke_test.sh $ENV echo "Deployment completed!"

6. 실전 팁

CI/CD 구축할 때 주의할 점?
CI/CD 베스트 프랙티스: 1. Fast Feedback - 빌드/테스트는 10분 이내 - 느리면 개발자가 안 기다림 - 캐시 적극 활용 2. Fail Fast - 빠른 테스트 먼저 실행 - 실패하면 즉시 중단 - 피드백 빠르게 제공 3. 환경 일관성 - Dev = Staging = Prod (최대한) - Docker로 환경 고정 - "내 PC에서는 됐는데" 방지 4. 시크릿 관리 - 비밀번호는 환경변수/Secret Manager - 코드에 하드코딩 절대 금지 5. 롤백 준비 - 이전 버전 항상 보관 - 원클릭 롤백 가능하게

# .github/pull_request_template.md ## 변경 사항 - ## 테스트 - [ ] 단위 테스트 추가/수정 - [ ] 로컬에서 통합 테스트 통과 ## 체크리스트 - [ ] 코드 리뷰 요청 - [ ] CI 파이프라인 통과 - [ ] 문서 업데이트 (필요시) - [ ] DB 마이그레이션 확인 (필요시) ## 배포 영향 - [ ] 즉시 배포 가능 - [ ] 배포 전 준비 필요: ___

핵심 정리: CI/CD Pipeline

  • CI - 코드 변경 시 자동 빌드 + 테스트
  • CD - 테스트 통과 시 자동 배포 (또는 승인 후)
  • 빌드 - CMake + Docker 멀티스테이지
  • 테스트 - 단위 -> 통합 -> E2E -> 부하
  • 배포 - 쿠버네티스 롤링 업데이트
  • 핵심 - 자동화로 실수 방지, 빠른 피드백!
