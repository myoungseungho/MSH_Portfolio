분산 트랜잭션이 2PC 없이 되는 이유

Saga 패턴 - 보상 트랜잭션으로 분산 환경에서 일관성 유지하기

Part 1. 분산 환경에서 트랜잭션이 왜 어려워?

DB 하나면 트랜잭션 쉬운데, 뭐가 문제야?

게임에서 서버 간 아이템 거래를 생각해봐.

A서버 유저가 B서버 유저에게 아이템 판매.

💱 크로스서버 거래 시나리오: [A서버] [B서버] 유저 A ──아이템 판매──▶ 유저 B │ │ ▼ ▼ A의 DB B의 DB ├─ 아이템 제거 ├─ 골드 차감 └─ 골드 추가 └─ 아이템 추가 ❓ 만약 A의 DB는 성공, B의 DB는 실패하면? → A는 아이템 잃고 골드도 못 받음 → B는 골드도 안 빠지고 아이템도 없음 → 둘 다 손해/이득 불공정!
그냥 BEGIN TRANSACTION으로 묶으면 안 돼?

DB가 다르면 안 돼.

트랜잭션은 같은 DB 안에서만 동작해.

❌ 일반 트랜잭션의 한계: BEGIN TRANSACTION UPDATE A_DB.Inventory ... ← A서버 DB UPDATE B_DB.Inventory ... ← B서버 DB (다른 DB!) COMMIT → 에러! 다른 DB에는 트랜잭션이 안 걸림 → A_DB만 롤백되거나, 아예 안 됨

Part 2. 2PC(Two-Phase Commit)는 왜 안 써?

분산 트랜잭션 하려면 2PC 쓰라던데?

2PC = 2단계 커밋이야.

모든 참여자에게 "커밋해도 돼?" 물어보고, 다 OK하면 커밋.

🔐 2PC (Two-Phase Commit) 동작: [1단계: Prepare] Coordinator: "커밋 준비됐어?" ├──▶ A서버 DB: "OK 준비됨" ✓ └──▶ B서버 DB: "OK 준비됨" ✓ [2단계: Commit] Coordinator: "다들 OK했으니 커밋해!" ├──▶ A서버 DB: COMMIT ✓ └──▶ B서버 DB: COMMIT ✓ 완료!
잘 되는 것 같은데 뭐가 문제야?

Coordinator가 죽으면?

모든 참여자가 영원히 대기해야 해.

💀 2PC의 치명적 약점: [1단계: Prepare] Coordinator: "커밋 준비됐어?" ├──▶ A서버 DB: "OK 준비됨" 🔒 락 걸고 대기 └──▶ B서버 DB: "OK 준비됨" 🔒 락 걸고 대기 [Coordinator 사망!] 💥 A서버 DB: "Coordinator 응답 없음... 계속 대기..." 🔒 B서버 DB: "Coordinator 응답 없음... 계속 대기..." 🔒 → 락이 안 풀림! → 다른 트랜잭션도 전부 대기 → 서비스 전체 마비 위험!
2PC 문제점 영향
Coordinator SPOF 죽으면 전체 마비
동기 방식 모두 응답까지 대기 (느림)
락 유지 시간 긴 락 = 병목
확장성 참여자 많을수록 느려짐

Part 3. Saga 패턴이 뭔데?

그래서 대안이 뭐야?

Saga = 작은 트랜잭션들의 연속

실패하면 보상 트랜잭션으로 되돌려.

🎭 Saga 패턴 핵심 개념: [일반 트랜잭션] BEGIN ──▶ 작업1 ──▶ 작업2 ──▶ 작업3 ──▶ COMMIT 실패하면 전체 ROLLBACK [Saga] 작업1 ──▶ 작업2 ──▶ 작업3 │ │ │ ▼ ▼ ▼ 보상1 보상2 보상3 실패하면? 이미 완료된 작업들을 "보상"으로 되돌림! 예: 작업3 실패 시 작업1 ✓ ──▶ 작업2 ✓ ──▶ 작업3 ✗ │ │ ▼ ▼ 보상2 실행 (실패했으니 보상 불필요) ▼ 보상1 실행 결과: 원래 상태로 복구!
보상 트랜잭션이 뭐야?

이미 한 일을 취소하는 작업이야.

ROLLBACK이 아니라, 반대 작업을 실행하는 거야.

🔄 보상 트랜잭션 예시: [크로스서버 아이템 거래] 정방향 작업: T1: A서버 - 아이템 제거 T2: A서버 - 골드 추가 T3: B서버 - 골드 차감 T4: B서버 - 아이템 추가 보상 작업 (역방향): C1: A서버 - 아이템 복구 (T1의 보상) C2: A서버 - 골드 제거 (T2의 보상) C3: B서버 - 골드 환불 (T3의 보상) C4: B서버 - 아이템 제거 (T4의 보상) T3 실패 시: T1 ✓ → T2 ✓ → T3 ✗ ↓ C2 실행 (골드 제거) ↓ C1 실행 (아이템 복구) → A유저는 원래대로 아이템 보유!

Part 4. 누가 Saga를 관리해?

각 서비스가 알아서 해? 아니면 중앙에서 관리해?

두 가지 방식이 있어:

Choreography = 각자 알아서

Orchestration = 중앙에서 지휘

💃 Choreography (분산형): 각 서비스가 이벤트로 소통, 중앙 관리자 없음 [A서버] ──이벤트: 아이템 제거됨──▶ [Message Queue] │ ▼ [B서버] ◀──이벤트 수신, 골드 차감 시도 │ └──성공/실패 이벤트 발행──▶ [Message Queue] │ ▼ [A서버] ◀──결과 수신, 필요시 보상 실행 장점: 중앙 장애점 없음, 느슨한 결합 단점: 흐름 파악 어려움, 디버깅 힘듦
🎼 Orchestration (중앙형): Saga Orchestrator가 전체 흐름 관리 [Saga Orchestrator] │ ├──1. A서버에 요청: "아이템 제거해" │ ◀── A서버: "OK 완료" │ ├──2. A서버에 요청: "골드 추가해" │ ◀── A서버: "OK 완료" │ ├──3. B서버에 요청: "골드 차감해" │ ◀── B서버: "실패!" ✗ │ └──4. 보상 실행 ├── A서버에 요청: "골드 제거해" (C2) └── A서버에 요청: "아이템 복구해" (C1) 장점: 흐름 명확, 디버깅 쉬움 단점: Orchestrator가 SPOF 될 수 있음
비교 Choreography Orchestration
결합도 느슨함 강함
흐름 파악 어려움 명확함
디버깅 이벤트 추적 필요 중앙에서 확인
SPOF 없음 Orchestrator
복잡한 흐름 관리 어려움 관리 쉬움
게임에서는 뭘 써?

대부분 Orchestration을 써.

거래 실패 시 "왜 실패했는지" 추적이 중요하거든.

Part 5. 게임에서 Saga 적용 예시

실제 게임에서 어디에 쓰여?

여러 서버/서비스에 걸친 작업에:

🎮 게임에서 Saga 활용: 1️⃣ 크로스서버 거래소 ├─ T1: 판매자 서버 - 아이템 에스크로 ├─ T2: 거래소 서버 - 매물 등록 ├─ T3: 구매자 서버 - 골드 차감 ├─ T4: 구매자 서버 - 아이템 지급 └─ T5: 판매자 서버 - 골드 지급 T3 실패 시 → C2(매물 취소) → C1(아이템 반환) 2️⃣ 서버 이전 (캐릭터 이동) ├─ T1: 원본 서버 - 캐릭터 잠금 ├─ T2: 대상 서버 - 캐릭터 생성 ├─ T3: 원본 서버 - 캐릭터 삭제 T2 실패 시 → C1(잠금 해제) 3️⃣ 결제 처리 ├─ T1: 결제 서버 - 결제 승인 ├─ T2: 게임 서버 - 캐시 지급 ├─ T3: 로그 서버 - 결제 기록 T2 실패 시 → C1(결제 취소/환불)
구체적인 코드로 보여줘

Orchestrator 기반 Saga 예시:

// Saga 정의 class CrossServerTradeSaga { // 정방향 스텝들 vector<SagaStep> m_steps = { { "아이템 에스크로", EscrowItem, RestoreItem }, { "골드 차감", DeductGold, RefundGold }, { "아이템 지급", GiveItem, RemoveItem }, { "골드 지급", GiveGold, DeductGold }, }; void Execute() { for (int i = 0; i < m_steps.size(); i++) { if (!m_steps[i].action()) // 실행 실패 { // 보상 실행 (역순) Compensate(i - 1); return; } } } void Compensate(int fromStep) { // 역순으로 보상 실행 for (int i = fromStep; i >= 0; i--) { m_steps[i].compensate(); } } };

Part 6. Saga 구현 시 주의할 점

Saga 쓸 때 조심할 게 있어?

몇 가지 중요한 포인트가 있어:

⚠️ Saga 구현 핵심 주의사항: 1️⃣ 멱등성 (Idempotency) 같은 작업 2번 해도 결과가 같아야 함 ❌ 잘못된 예: GiveGold() { player.gold += 1000; } → 2번 호출하면 2000 증가! ✅ 올바른 예: GiveGold(txId) { if (alreadyProcessed(txId)) return; player.gold += 1000; markProcessed(txId); } 2️⃣ 보상도 실패할 수 있음 보상 작업도 실패하면? → 재시도 큐에 넣고 계속 시도 → 또는 수동 개입 알림 3️⃣ 타임아웃 처리 너무 오래 걸리면? → 타임아웃 후 보상 실행 → 상태: "처리 중" → "타임아웃" → "보상 완료"
보상 중에 서버가 죽으면?

Saga 상태를 저장해둬야 해.

어디까지 했는지 기록해서 재시작 후 이어서 보상.

💾 Saga 상태 저장: [Saga 상태 테이블] ┌─────────┬──────────────┬─────────┐ │ SagaID │ CurrentStep │ Status │ ├─────────┼──────────────┼─────────┤ │ 12345 │ 3 │ RUNNING │ │ 12346 │ 2 │ COMPENSATING │ │ 12347 │ 4 │ COMPLETED │ └─────────┴──────────────┴─────────┘ 서버 재시작 시: 1. Status=RUNNING인 Saga 조회 2. CurrentStep부터 이어서 실행 3. Status=COMPENSATING인 Saga 조회 4. 남은 보상 작업 이어서 실행

⚠️ Saga 패턴 주의사항

1. 멱등성 필수 - 재시도해도 결과가 같아야 함

2. 보상은 "의미적 롤백" - DB ROLLBACK이 아니라 반대 작업 실행

3. 상태 저장 - 중간에 죽어도 복구할 수 있게

4. 격리성 없음 - 중간 상태가 다른 트랜잭션에 보일 수 있음

💡 Saga vs 2PC 선택 기준

• 2PC: 강한 일관성 필수, 짧은 트랜잭션, 참여자 적음

• Saga: 최종 일관성 OK, 긴 트랜잭션, 마이크로서비스

• 게임에서는: 대부분 Saga가 적합 (서버 간 독립성 중요)

📝 핵심 정리

  • 2PC = 모두 준비 → 모두 커밋, 하지만 블로킹 문제
  • Saga = 작은 트랜잭션 연속 + 실패 시 보상 트랜잭션
  • 보상 = ROLLBACK이 아니라 "반대 작업" 실행
  • Choreography = 이벤트 기반, Orchestration = 중앙 관리
  • 멱등성 + 상태 저장 = Saga 구현의 핵심
