Part 1. 파라미터가 100개?

캐릭터 저장 프로시저가 왜 이렇게 복잡해?

게임 캐릭터 저장 보면...

-- gp_save_pc 프로시저 시그니처 CREATE PROCEDURE gp_save_pc @i32CharSID INT, @i32Level INT, @i32Exp BIGINT, @i32Str INT, @i32Dex INT, @i32Con INT, @i32Int INT, @i32Wis INT, @i32Cha INT, ... (90개 더) AS

파라미터가 100개가 넘어.

스킬, 인벤토리, 퀘스트까지 하면 더 늘어나고.

그게 왜 문제야?

네트워크 오버헤드: 매번 100개 파라미터 직렬화

유지보수 지옥: 컬럼 추가할 때마다 C++/SP 양쪽 수정

디버깅 어려움: 어떤 파라미터가 잘못됐는지 찾기 힘듦

Part 2. TVP가 뭔데?

📦 택배 비유

기존 방식: 물건 100개를 각각 택배로 보냄 (100번 배송)

TVP 방식: 박스 1개에 물건 100개 담아서 1번 배송

같은 물건인데 배송 횟수가 100배 차이!
그래서 TVP가 정확히 뭐야?

Table-Valued Parameter

= 테이블 형태의 데이터를 하나의 파라미터로 전달하는 것.

┌─────────────────────────────────────────────────────┐
│                    기존 방식                         │
├─────────────────────────────────────────────────────┤
│  EXEC sp_save @p1, @p2, @p3, ... @p100             │
│       ↓    ↓    ↓         ↓                        │
│      개별 파라미터 100개 전달                        │
└─────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────┐
│                    TVP 방식                          │
├─────────────────────────────────────────────────────┤
│  EXEC sp_save @DataTable                            │
│       ↓                                             │
│  ┌──────────────────────────────┐                   │
│  │ ID  │ Name  │ Value │ ...   │  ← 테이블 1개     │
│  ├─────┼───────┼───────┼───────┤                   │
│  │  1  │ Level │  99   │       │                   │
│  │  2  │ Str   │  50   │       │                   │
│  │  3  │ Dex   │  30   │       │                   │
│  └──────────────────────────────┘                   │
└─────────────────────────────────────────────────────┘

Part 3. TVP 만드는 방법

어떻게 만들어?

3단계로 진행해.

-- Step 1: 테이블 타입 정의 CREATE TYPE CharacterStatType AS TABLE ( StatID INT NOT NULL, StatValue BIGINT NOT NULL ); -- Step 2: 프로시저에서 TVP 파라미터 사용 CREATE PROCEDURE gp_save_pc_v2 @i32CharSID INT, @Stats CharacterStatType READONLY -- TVP는 READONLY 필수! AS BEGIN -- 스탯 테이블에 MERGE MERGE INTO TCharacterStat AS target USING @Stats AS source ON target.CharSID = @i32CharSID AND target.StatID = source.StatID WHEN MATCHED THEN UPDATE SET StatValue = source.StatValue WHEN NOT MATCHED THEN INSERT (CharSID, StatID, StatValue) VALUES (@i32CharSID, source.StatID, source.StatValue); END;
READONLY가 왜 필요해?

TVP는 읽기 전용이야.

프로시저 안에서 수정 불가. 대신 빠르게 전달할 수 있어.

TVP의 제약

• READONLY: 프로시저 내에서 수정 불가
• OUTPUT 안 됨: 반환값으로 사용 불가
• 임시 테이블 아님: 영구적인 타입으로 정의해야 함

Part 4. C++에서 TVP 사용하기

게임 서버는 C++인데 어떻게 연동해?

ODBC에서 TVP 지원해. SQL Server Native Client 필요.

// C++에서 TVP 전달하는 방법 (개념) // 1. TVP용 바인딩 구조체 struct StatRow { SQLINTEGER statId; SQLBIGINT statValue; }; // 2. 배열 준비 StatRow stats[100]; stats[0] = { 1, 99 }; // Level = 99 stats[1] = { 2, 50 }; // Str = 50 // ... // 3. TVP로 바인딩 SQLBindParameter(hstmt, 1, // 파라미터 번호 SQL_PARAM_INPUT, SQL_C_DEFAULT, SQL_SS_TABLE, // TVP 타입! 100, // 행 개수 0, "CharacterStatType", // 타입 이름 0, NULL); // 4. 실행 SQLExecDirect(hstmt, "EXEC gp_save_pc_v2 @CharSID=?, @Stats=?", SQL_NTS);
ODBC TVP 지원 버전

• SQL Server Native Client 11.0 이상 필요
• Windows ODBC Driver 17 이상 권장
• 기존 gniDB 래퍼 수정 필요할 수 있음
기존 코드 많이 바꿔야 해?

래퍼 클래스 하나 만들면 돼.

// 간편하게 쓰기 위한 래퍼 예시 class CTVPBuilder { public: void AddRow(int statId, __int64 value) { m_rows.push_back({statId, value}); } void BindToStatement(SQLHSTMT hstmt, int paramIndex) { // 내부적으로 SQLBindParameter 호출 } private: std::vector m_rows; }; // 사용법 CTVPBuilder tvp; tvp.AddRow(STAT_LEVEL, pChar->GetLevel()); tvp.AddRow(STAT_STR, pChar->GetStr()); tvp.AddRow(STAT_DEX, pChar->GetDex()); // ... db.Execute("gp_save_pc_v2", charSID, tvp);

Part 5. 성능이 얼마나 좋아질까?

TVP 쓰면 실제로 빨라져?

배치 작업에서 극적인 차이가 나.

100개 스탯 저장 (1,000명 동시)

개별 파라미터
850 ms
100,000번 바인딩
TVP 방식
120 ms
1,000번 바인딩

7배 빠름!

파라미터 바인딩 오버헤드가 대폭 줄어든 거야.

항목 개별 파라미터 TVP
네트워크 왕복 파라미터마다 직렬화 테이블 1개로 직렬화
SP 컴파일 파라미터 100개 파싱 파라미터 2개 파싱
유지보수 컬럼 추가 시 양쪽 수정 테이블 타입만 수정
에러 추적 어떤 파라미터가 문제? 테이블 데이터로 확인

Part 6. 게임 서버에서 어디에 적용할까?

우리 게임 DB에서 TVP 쓸 만한 데가 어디야?

배열/리스트 형태 데이터를 저장하는 곳에 효과적.

적용 대상 현재 방식 TVP 적용 시
인벤토리 저장 chunk_data로 바이너리 덩어리 아이템별 행으로 저장 (유연성 ↑)
스킬 저장 스킬마다 개별 파라미터 스킬 테이블 1개로 전달
퀘스트 진행 퀘스트별 UPDATE 쿼리 MERGE로 일괄 처리
로그 기록 INSERT 여러 번 TVP로 배치 INSERT
-- 예: 퀘스트 진행 상황 일괄 저장 CREATE TYPE QuestProgressType AS TABLE ( QuestID INT NOT NULL, Step INT NOT NULL, Count INT NOT NULL, Completed BIT NOT NULL ); CREATE PROCEDURE gp_save_quests @i32CharSID INT, @Quests QuestProgressType READONLY AS BEGIN MERGE INTO TQuestProgress AS target USING @Quests AS source ON target.CharSID = @i32CharSID AND target.QuestID = source.QuestID WHEN MATCHED THEN UPDATE SET Step = source.Step, Count = source.Count, Completed = source.Completed WHEN NOT MATCHED THEN INSERT (CharSID, QuestID, Step, Count, Completed) VALUES (@i32CharSID, source.QuestID, source.Step, source.Count, source.Completed); END;
TVP 도입 체크리스트

1. SQL Server 2008 이상 확인
2. ODBC Driver 버전 확인 (Native Client 11+)
3. 기존 프로시저와 병행 운영 가능 (점진적 전환)
4. 테이블 타입 변경 시 프로시저 재컴파일 필요

핵심 정리: TVP

  • TVP = 테이블 형태 데이터를 1개 파라미터로 전달
  • 파라미터 100개 → 1개로 줄여서 오버헤드 감소
  • MERGE 문과 함께 쓰면 INSERT/UPDATE 일괄 처리
  • 배치 작업에서 7배 이상 성능 향상 가능
  • 유지보수 편해짐: 컬럼 추가 시 테이블 타입만 수정
  • 주의: READONLY, ODBC 드라이버 버전 확인 필요
  • 적용 대상: 인벤토리, 스킬, 퀘스트, 로그 등 리스트 데이터
