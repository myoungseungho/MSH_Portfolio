에셋 번들이란?

게임 리소스의 배포 단위 - 동적 로딩과 효율적 업데이트를 위한 핵심 기술

Part 1. 에셋 번들의 정의

에셋 번들이 정확히 뭐야? 그냥 파일 압축이랑 뭐가 달라?

에셋 번들(Asset Bundle)은 게임 에셋들을 런타임에 로드 가능한 형태로 패키징한 아카이브입니다.

일반 ZIP 압축과의 핵심 차이점:

일반 ZIP 압축:
┌─────────────────────────────────────────────────────────┐
│  압축 데이터 → 해제 → 원본 파일 → 엔진 Import → 사용    │
│  [texture.png] → 해제 → PNG 파일 → Import 처리 → 텍스처 │
└─────────────────────────────────────────────────────────┘
  ⚠️ 문제: Import 과정이 느림, 런타임에 Import 불가

에셋 번들:
┌─────────────────────────────────────────────────────────┐
│  이미 Import된 데이터 → 압축 해제만 → 즉시 사용        │
│  [serialized texture] → 해제 → 바로 GPU 전송 가능!     │
└─────────────────────────────────────────────────────────┘
  ✓ 핵심: 엔진이 이해하는 직렬화된 형태로 저장됨

에셋 번들 안에는 이미 엔진 Import 처리가 완료된 데이터가 들어있습니다. 텍스처는 이미 특정 압축 포맷(DXT, ASTC 등)으로 변환되어 있고, 메시는 GPU가 바로 읽을 수 있는 버텍스 버퍼 형태입니다.

에셋, 리소스, 에셋 번들의 차이가 뭐야?

자주 혼동되는 세 가지 개념을 명확히 구분해보겠습니다:

┌─────────────────────────────────────────────────────────────────────┐
│                        용어 정의                                      │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  에셋 (Asset)                                                       │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │ 게임에서 사용되는 모든 데이터 조각                              │  │
│  │ 예: 텍스처, 메시, 사운드, 프리팹, 스크립트, 설정 파일          │  │
│  │ → 개념적 단위                                                  │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                            ↓                                        │
│  Resources (Unity 특정)                                             │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │ Resources 폴더에 있는 에셋들                                   │  │
│  │ Resources.Load()로 런타임 로드 가능                            │  │
│  │ → 항상 빌드에 포함됨, 이름 기반 로드                           │  │
│  │ ⚠️ 주의: 앱 시작 시 인덱싱 비용 발생                           │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                            ↓                                        │
│  에셋 번들 (Asset Bundle)                                           │
│  ┌──────────────────────────────────────────────────────────────┐  │
│  │ 에셋들을 묶어서 만든 배포 가능한 패키지                         │  │
│  │ 외부에서 다운로드하여 런타임 로드 가능                          │  │
│  │ → 버전 관리, 부분 업데이트, 용량 분리 가능                      │  │
│  └──────────────────────────────────────────────────────────────┘  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

핵심 차이는 배포 시점과 방식입니다:

  • 빌드에 포함된 에셋: 앱과 함께 항상 설치됨
  • Resources 에셋: 빌드에 포함되지만 동적 로드 가능
  • 에셋 번들: 앱과 별도로 배포/다운로드 가능
그럼 에셋 번들 안에 실제로 뭐가 들어있어?

에셋 번들은 크게 세 가지 섹션으로 구성됩니다:

에셋 번들 파일 구조 (.bundle, .unity3d, .assetbundle)
┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 1. 헤더 (Header)                                        │   │
│  │    - 번들 버전 (Unity 버전 호환성)                       │   │
│  │    - 압축 타입 (None, LZMA, LZ4)                        │   │
│  │    - 번들 크기 정보                                      │   │
│  │    - 체크섬 (CRC32)                                     │   │
│  └─────────────────────────────────────────────────────────┘   │
│                           │                                     │
│                           ↓                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 2. 파일 테이블 (File Table / Manifest)                  │   │
│  │    - 포함된 에셋 목록                                    │   │
│  │    - 각 에셋의 오프셋, 크기                              │   │
│  │    - 에셋 간 의존성 정보                                 │   │
│  │    - 에셋 타입 정보                                      │   │
│  └─────────────────────────────────────────────────────────┘   │
│                           │                                     │
│                           ↓                                     │
│  ┌─────────────────────────────────────────────────────────┐   │
│  │ 3. 에셋 데이터 (Serialized Assets)                      │   │
│  │    ┌──────────────┐ ┌──────────────┐ ┌──────────────┐   │   │
│  │    │ Texture2D    │ │ Mesh        │ │ Material     │   │   │
│  │    │ (ASTC/DXT)   │ │ (Vertices)  │ │ (Shader Ref) │   │   │
│  │    │ Width/Height │ │ Indices     │ │ Properties   │   │   │
│  │    │ Mipmap Data  │ │ Normals     │ │ Textures     │   │   │
│  │    └──────────────┘ └──────────────┘ └──────────────┘   │   │
│  └─────────────────────────────────────────────────────────┘   │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

중요한 점은 에셋이 직렬화(Serialized)된 형태로 저장된다는 것입니다. Unity의 경우 YAML이 아닌 바이너리 직렬화, Unreal의 경우 cooked 데이터입니다.

Part 2. 에셋 번들이 필요한 이유

그냥 빌드에 다 넣으면 안 돼? 왜 번들로 분리해?

에셋 번들이 필요한 핵심 이유들을 살펴보겠습니다:

문제 1: 앱 크기 제한

모바일 스토어는 다운로드 크기를 제한합니다:

  • Google Play: APK 150MB (AAB 확장으로 극복 가능)
  • App Store: 셀룰러로 200MB, Wi-Fi 무제한
  • Steam: 제한 없지만 큰 파일은 설치 포기율 증가
앱 크기가 게임 설치에 미치는 영향:

앱 크기         셀룰러 설치율    Wi-Fi 설치율
50MB 이하        ▓▓▓▓▓▓▓▓▓▓      ▓▓▓▓▓▓▓▓▓▓   (높음)
100MB            ▓▓▓▓▓▓▓░░░      ▓▓▓▓▓▓▓▓▓▓
200MB            ▓▓▓▓░░░░░░      ▓▓▓▓▓▓▓▓▓░
500MB            ▓░░░░░░░░░      ▓▓▓▓▓▓▓░░░
1GB+             ░░░░░░░░░░      ▓▓▓▓▓░░░░░   (낮음)

해결책: 핵심 에셋만 앱에 포함, 나머지는 번들로 후속 다운로드

문제 2: 전체 재설치 없는 업데이트

새 캐릭터나 맵을 추가할 때마다 전체 앱을 재설치해야 한다면?

에셋 번들 없이 업데이트:
┌──────────────────────────────────────────────────────────────┐
│ 앱 v1.0 (2GB) ──[새 캐릭터 추가]──→ 앱 v1.1 (2.1GB)         │
│                                                              │
│ 사용자 입장:                                                  │
│ 1. 스토어에서 2.1GB 재다운로드                               │
│ 2. 기존 앱 삭제                                              │
│ 3. 새 앱 설치                                                │
│ 4. 로그인, 설정 다시...                                      │
│                                                              │
│ ⏱️ 시간: 30분~1시간                                          │
│ 📶 데이터: 2.1GB 소모                                        │
└──────────────────────────────────────────────────────────────┘

에셋 번들로 업데이트:
┌──────────────────────────────────────────────────────────────┐
│ 앱 v1.0 (500MB) + 번들들 (1.5GB)                             │
│                                                              │
│ 새 캐릭터 추가:                                              │
│ 게임 내에서 character_new.bundle (100MB) 다운로드            │
│                                                              │
│ ⏱️ 시간: 2~3분                                               │
│ 📶 데이터: 100MB만 소모                                      │
│ ✓ 앱 재설치 없음, 플레이 중 다운로드 가능                    │
└──────────────────────────────────────────────────────────────┘
Resources 폴더를 쓰면 동적 로딩이 되잖아. 왜 번들을 써?

Unity의 Resources 폴더는 동적 로딩이 가능하지만, 심각한 문제들이 있습니다:

Resources 폴더의 문제점

문제 1: 빌드 크기
┌─────────────────────────────────────────────────────────────┐
│ Resources 폴더의 모든 에셋은 빌드에 100% 포함됩니다!       │
│                                                             │
│ Resources/                                                  │
│ ├── Characters/     (500MB)  ← 전부 빌드에 포함           │
│ ├── Maps/           (1GB)    ← 전부 빌드에 포함           │
│ └── Effects/        (200MB)  ← 전부 빌드에 포함           │
│                                                             │
│ 앱 크기: 기본 + 1.7GB (Resources 전체)                     │
│ 사용하든 안 하든 무조건 포함됨!                             │
└─────────────────────────────────────────────────────────────┘

문제 2: 시작 시간 증가
┌─────────────────────────────────────────────────────────────┐
│ 앱 시작 시 Resources 전체 인덱싱 발생                       │
│                                                             │
│ Resources 파일 수    인덱싱 시간 (모바일)                   │
│ 100개               ~100ms                                  │
│ 1,000개             ~500ms                                  │
│ 10,000개            ~2초                                    │
│ 50,000개            ~10초                                   │
│                                                             │
│ 사용자: "앱이 왜 이렇게 오래 걸려?"                         │
└─────────────────────────────────────────────────────────────┘

문제 3: 업데이트 불가
┌─────────────────────────────────────────────────────────────┐
│ Resources는 앱의 일부 → 수정하려면 앱 업데이트 필수        │
│                                                             │
│ 새 스킨 추가?    → 앱 스토어 심사 (1~7일)                   │
│ 버그 수정?       → 앱 스토어 심사 (1~7일)                   │
│ 이벤트 콘텐츠?   → 앱 스토어 심사 (1~7일)                   │
│                                                             │
│ 에셋 번들: 서버에 올리면 즉시 반영!                         │
└─────────────────────────────────────────────────────────────┘

공식 권장사항: Unity는 Resources 폴더 사용을 최소화하고, 에셋 번들 또는 Addressables 사용을 권장합니다.

그럼 언제 Resources를 쓰고 언제 에셋 번들을 써야 해?
사용 시나리오별 권장 방식:

┌─────────────────────────────────────────────────────────────────┐
│ 시나리오                              권장 방식                  │
├─────────────────────────────────────────────────────────────────┤
│ 앱 전체에서 항상 필요한 에셋          StreamingAssets / 빌드    │
│ (기본 UI, 폰트, 필수 사운드)                                    │
│                                                                 │
│ 씬 전환 시 바뀌는 에셋                에셋 번들 (또는 씬에 포함) │
│ (맵 텍스처, 배경음악)                                           │
│                                                                 │
│ 사용자 선택에 따라 로드               에셋 번들                  │
│ (캐릭터 스킨, 장비 외형)                                        │
│                                                                 │
│ 업데이트/패치될 가능성 있는 에셋      에셋 번들 (필수!)         │
│ (이벤트, 새 콘텐츠)                                             │
│                                                                 │
│ 프로토타입/테스트 중                  Resources (편의상)        │
│ (출시 전에 번들로 이관 필요)                                    │
└─────────────────────────────────────────────────────────────────┘

원칙: "출시 후 변경 가능성이 있다면 에셋 번들"

Part 3. 에셋 번들 압축 방식

에셋 번들 압축에는 어떤 옵션이 있어?

Unity 기준으로 세 가지 압축 옵션이 있습니다:

1. 무압축 (Uncompressed)
┌─────────────────────────────────────────────────────────────┐
│ 특징: 압축하지 않음                                          │
│                                                             │
│ 장점:                                                        │
│ - 로딩 매우 빠름 (압축 해제 CPU 비용 0)                      │
│ - 번들의 특정 에셋만 로드 가능 (랜덤 액세스)                 │
│                                                             │
│ 단점:                                                        │
│ - 파일 크기 최대                                             │
│ - 다운로드 시간 ↑, 저장 공간 ↑                              │
│                                                             │
│ 사용 시점: 로컬 스토리지 충분 + 로딩 속도 최우선              │
└─────────────────────────────────────────────────────────────┘

2. LZMA (Chunk Based)
┌─────────────────────────────────────────────────────────────┐
│ 특징: 번들 전체를 하나의 스트림으로 압축                     │
│                                                             │
│ 장점:                                                        │
│ - 압축률 최고 (파일 크기 최소)                               │
│ - 다운로드 트래픽 ↓                                         │
│                                                             │
│ 단점:                                                        │
│ - 전체 해제 필요 (부분 로드 불가)                            │
│ - 메모리 스파이크 발생                                       │
│ - 로딩 느림                                                  │
│                                                             │
│ 사용 시점: 다운로드 크기 최소화가 최우선 (모바일 네트워크)    │
└─────────────────────────────────────────────────────────────┘

3. LZ4 (Chunk Based) - 권장!
┌─────────────────────────────────────────────────────────────┐
│ 특징: 청크 단위 압축 (각 에셋을 개별 압축)                   │
│                                                             │
│ 장점:                                                        │
│ - 압축/해제 매우 빠름                                        │
│ - 필요한 에셋만 해제 가능 (랜덤 액세스)                      │
│ - 메모리 효율적                                              │
│                                                             │
│ 단점:                                                        │
│ - LZMA보다 압축률 낮음 (보통 20~30% 더 큼)                   │
│                                                             │
│ 사용 시점: 대부분의 상황에서 권장                            │
└─────────────────────────────────────────────────────────────┘
LZMA vs LZ4 차이를 좀 더 구체적으로 비교해줘

실제 수치로 비교해보겠습니다:

100MB 에셋 번들 기준 비교:

                    LZMA            LZ4             무압축
압축 후 크기        ~25MB           ~35MB           100MB
압축률              ~75%            ~65%            0%

전체 로드 시간
(SSD 기준)          ~2초            ~0.3초          ~0.1초
(HDD 기준)          ~3초            ~0.5초          ~0.3초
(모바일 기준)       ~5초            ~0.8초          ~0.4초

단일 에셋 로드      전체 해제 필수   해당 청크만      즉시
메모리 피크         ~150MB          ~40MB           ~20MB
                   (원본+압축)      (청크만)        (에셋만)
// Unity에서 압축 방식 지정 var options = BuildAssetBundleOptions.None; // LZMA (기본값이었으나 현재는 LZ4가 권장됨) options = BuildAssetBundleOptions.None; // LZMA 압축 // LZ4 압축 (권장) options = BuildAssetBundleOptions.ChunkBasedCompression; // 무압축 options = BuildAssetBundleOptions.UncompressedAssetBundle; BuildPipeline.BuildAssetBundles( outputPath, options, BuildTarget.StandaloneWindows64 );

실무 권장 전략

  • 다운로드 번들: LZ4 (빠른 로드 + 적당한 압축)
  • 스트리밍 번들: LZ4 (부분 로드 필수)
  • 초기 설치 번들: LZMA → LZ4 재압축 (다운로드 최소화)
LZMA로 다운로드 받고 LZ4로 재압축한다는 게 무슨 말이야?

Unity에서 자주 쓰는 최적화 기법입니다:

다운로드 최적화 + 로딩 최적화를 동시에:

┌────────────────────────────────────────────────────────────────┐
│ 1단계: 서버 저장 (LZMA 압축)                                   │
│                                                                │
│   [원본 100MB] ──LZMA──→ [25MB] 서버에 업로드                  │
│                          ↓                                     │
│                     다운로드 트래픽 최소화                      │
└────────────────────────────────────────────────────────────────┘
                           ↓
┌────────────────────────────────────────────────────────────────┐
│ 2단계: 클라이언트 수신 후 재압축                                │
│                                                                │
│   [25MB LZMA] ──해제──→ [100MB] ──LZ4 압축──→ [35MB LZ4]       │
│                                               ↓                │
│                                          로컬에 저장           │
│                                          (디스크: 35MB)        │
└────────────────────────────────────────────────────────────────┘
                           ↓
┌────────────────────────────────────────────────────────────────┐
│ 3단계: 게임 플레이 시 (LZ4에서 로드)                            │
│                                                                │
│   [35MB LZ4] ──빠른 해제──→ 필요한 에셋만 메모리에              │
│              (부분 로드 가능)                                   │
└────────────────────────────────────────────────────────────────┘
// Unity Caching 시스템은 이를 자동으로 처리 가능 var request = UnityWebRequestAssetBundle.GetAssetBundle( bundleUrl, hash, 0 // CRC (0 = 검증 안 함) ); // 캐싱 API는 LZMA 번들을 LZ4로 재압축하여 캐시함 yield return request.SendWebRequest(); // 이후 로드는 캐시된 LZ4 버전에서 빠르게! var bundle = DownloadHandlerAssetBundle.GetContent(request);

에셋에 번들 이름을 일일이 지정하는 게 번거로운데, 자동화할 수 없어?

AssetPostprocessor나 에디터 스크립트로 자동화할 수 있습니다:

// 폴더 기반 자동 번들 이름 지정 using UnityEditor; using System.IO; public class AutoBundleNamer : AssetPostprocessor { void OnPreprocessAsset() { // Assets/Bundles/ 하위 에셋만 처리 if (!assetPath.StartsWith("Assets/Bundles/")) return; // 폴더 구조를 번들 이름으로 변환 // Assets/Bundles/Characters/Hero/ → characters_hero string relativePath = assetPath.Replace("Assets/Bundles/", ""); string directory = Path.GetDirectoryName(relativePath); if (!string.IsNullOrEmpty(directory)) { string bundleName = directory .Replace(Path.DirectorySeparatorChar, '_') .Replace(Path.AltDirectorySeparatorChar, '_') .ToLower(); var importer = assetImporter; importer.assetBundleName = bundleName; } } } // 결과 예시: // Assets/Bundles/Characters/Hero/hero_model.fbx → characters_hero // Assets/Bundles/Characters/Hero/hero_texture.png → characters_hero // Assets/Bundles/Maps/Forest/forest_terrain.asset → maps_forest

더 정교한 자동화가 필요하다면 Addressables를 사용하는 것이 좋습니다. Addressables는 그룹 기반으로 번들을 자동 관리합니다.

Part 5. 에셋 번들 로딩과 언로딩

에셋 번들을 어떻게 로드해?

에셋 번들 로딩에는 두 단계가 있습니다:

에셋 번들 로딩 2단계:

1단계: 번들 로드 (컨테이너 열기)
┌─────────────────────────────────────────────────────────────┐
│ AssetBundle bundle = AssetBundle.LoadFromFile(path);        │
│                                                             │
│ 이 시점에서:                                                 │
│ - 번들 헤더와 파일 테이블이 메모리에 로드됨                  │
│ - 실제 에셋 데이터는 아직 로드되지 않음                      │
│ - 의존성 정보 확인 가능                                      │
└─────────────────────────────────────────────────────────────┘
                           ↓
2단계: 에셋 로드 (실제 데이터 가져오기)
┌─────────────────────────────────────────────────────────────┐
│ GameObject prefab = bundle.LoadAsset("Hero");   │
│                                                             │
│ 이 시점에서:                                                 │
│ - 요청한 에셋의 직렬화된 데이터가 역직렬화됨                 │
│ - 텍스처, 메시 등 실제 데이터가 메모리에 로드                │
│ - GPU 리소스가 생성됨 (텍스처, 버퍼 등)                      │
└─────────────────────────────────────────────────────────────┘
// 로컬 파일에서 동기 로드 public GameObject LoadHeroSync() { string bundlePath = Path.Combine( Application.streamingAssetsPath, "characters_hero" ); // 1단계: 번들 로드 AssetBundle bundle = AssetBundle.LoadFromFile(bundlePath); if (bundle == null) { Debug.LogError("Failed to load bundle!"); return null; } // 2단계: 에셋 로드 GameObject heroPrefab = bundle.LoadAsset<GameObject>("HeroPrefab"); return heroPrefab; } // 비동기 로드 (권장) public IEnumerator LoadHeroAsync() { string bundlePath = Path.Combine( Application.streamingAssetsPath, "characters_hero" ); // 1단계: 번들 비동기 로드 var bundleRequest = AssetBundle.LoadFromFileAsync(bundlePath); yield return bundleRequest; AssetBundle bundle = bundleRequest.assetBundle; // 2단계: 에셋 비동기 로드 var assetRequest = bundle.LoadAssetAsync<GameObject>("HeroPrefab"); yield return assetRequest; GameObject heroPrefab = assetRequest.asset as GameObject; // 사용 Instantiate(heroPrefab); }
서버에서 다운로드하는 건 어떻게 해?

UnityWebRequest를 사용하여 원격 서버에서 번들을 다운로드합니다:

public IEnumerator DownloadAndLoadBundle(string bundleUrl) { // 캐싱을 위한 해시 (버전 관리) using (var request = UnityWebRequestAssetBundle.GetAssetBundle( bundleUrl, new Hash128(), // 버전 해시 (실제로는 서버에서 받아옴) 0 // CRC (0 = 검증 안 함) )) { // 다운로드 진행 var operation = request.SendWebRequest(); while (!operation.isDone) { // 진행률 표시 Debug.Log($"Downloading: {request.downloadProgress * 100:F1}%"); yield return null; } if (request.result != UnityWebRequest.Result.Success) { Debug.LogError($"Download failed: {request.error}"); yield break; } // 번들 획득 (자동으로 캐시됨) AssetBundle bundle = DownloadHandlerAssetBundle.GetContent(request); // 에셋 로드 var assetRequest = bundle.LoadAssetAsync<GameObject>("HeroPrefab"); yield return assetRequest; Instantiate(assetRequest.asset as GameObject); } }
UnityWebRequestAssetBundle 캐싱 동작:

첫 번째 요청 (캐시 없음):
┌─────────────────────────────────────────────────────────────┐
│ GetAssetBundle(url, hash) → 서버에서 다운로드                │
│                           → LZMA면 LZ4로 재압축              │
│                           → 로컬 캐시에 저장                  │
│                           → 번들 반환                        │
└─────────────────────────────────────────────────────────────┘

두 번째 요청 (캐시 있음, 같은 hash):
┌─────────────────────────────────────────────────────────────┐
│ GetAssetBundle(url, hash) → 캐시에서 즉시 로드!              │
│                           → 네트워크 요청 없음               │
│                           → 번들 반환                        │
└─────────────────────────────────────────────────────────────┘

세 번째 요청 (캐시 있지만 hash 변경):
┌─────────────────────────────────────────────────────────────┐
│ GetAssetBundle(url, newHash) → 기존 캐시 무효화             │
│                              → 서버에서 새로 다운로드        │
│                              → 새 버전 캐시                  │
└─────────────────────────────────────────────────────────────┘
언로드는 어떻게 해? 메모리 관리가 중요할 텐데

에셋 번들 언로드에는 두 가지 모드가 있습니다. 이 차이를 이해하는 것이 매우 중요합니다:

bundle.Unload(false) vs bundle.Unload(true)

Unload(false) - 번들만 해제:
┌─────────────────────────────────────────────────────────────┐
│ 호출 전:                                                     │
│ ┌─────────┐        ┌─────────────┐                          │
│ │ Bundle  │───────→│ Prefab      │                          │
│ │ (메모리)│        │ (메모리)    │ ←── GameObject(씬에 있음)│
│ └─────────┘        └─────────────┘                          │
│                                                             │
│ Unload(false) 호출 후:                                       │
│ ┌─────────┐        ┌─────────────┐                          │
│ │ Bundle  │ ✗      │ Prefab      │ ✓ 유지!                  │
│ │ 해제됨  │        │ (메모리)    │ ←── GameObject 정상 작동 │
│ └─────────┘        └─────────────┘                          │
│                                                             │
│ ⚠️ 문제: 같은 번들 다시 로드하면 Prefab이 중복!              │
└─────────────────────────────────────────────────────────────┘

Unload(true) - 번들 + 로드된 에셋 모두 해제:
┌─────────────────────────────────────────────────────────────┐
│ 호출 전:                                                     │
│ ┌─────────┐        ┌─────────────┐                          │
│ │ Bundle  │───────→│ Prefab      │ ←── GameObject           │
│ └─────────┘        └─────────────┘                          │
│                                                             │
│ Unload(true) 호출 후:                                        │
│ ┌─────────┐        ┌─────────────┐                          │
│ │ Bundle  │ ✗      │ Prefab      │ ✗ 해제됨!                │
│ │ 해제됨  │        │             │                          │
│ └─────────┘        └─────────────┘                          │
│                          ↑                                   │
│                    GameObject의 참조 → Missing!              │
│                    ⚠️ 핑크색 텍스처, 누락된 메시             │
└─────────────────────────────────────────────────────────────┘

Unload 사용 시 주의사항

  • Unload(true): 해당 번들의 에셋을 참조하는 오브젝트가 없을 때만 안전
  • Unload(false): 메모리 누수 가능성, 번들 재로드 시 중복
  • 권장: 씬 전환 시 Unload(true), 참조 카운팅 사용
// 안전한 언로드를 위한 참조 카운팅 public class BundleManager { private Dictionary<string, BundleRef> m_LoadedBundles = new(); private class BundleRef { public AssetBundle Bundle; public int RefCount; } public AssetBundle LoadBundle(string bundleName) { if (m_LoadedBundles.TryGetValue(bundleName, out var bundleRef)) { bundleRef.RefCount++; return bundleRef.Bundle; } var bundle = AssetBundle.LoadFromFile(GetBundlePath(bundleName)); m_LoadedBundles[bundleName] = new BundleRef { Bundle = bundle, RefCount = 1 }; return bundle; } public void ReleaseBundle(string bundleName) { if (!m_LoadedBundles.TryGetValue(bundleName, out var bundleRef)) return; bundleRef.RefCount--; if (bundleRef.RefCount <= 0) { bundleRef.Bundle.Unload(true); // 참조 0이면 안전하게 전체 해제 m_LoadedBundles.Remove(bundleName); } } }

Part 6. Unity Asset Bundle vs Unreal Pak

Unreal에서는 에셋 번들 대신 뭘 써?

Unreal Engine은 Pak 파일을 사용합니다. 개념은 비슷하지만 구현 방식이 다릅니다:

Unity Asset Bundle vs Unreal Pak 비교:

┌────────────────────────────────────────────────────────────────┐
│                    Unity Asset Bundle                           │
├────────────────────────────────────────────────────────────────┤
│ 단위: 개발자가 정의한 그룹                                      │
│ 빌드: BuildPipeline API로 명시적 빌드                          │
│ 로드: AssetBundle.LoadFromFile() 명시적 호출                   │
│ 압축: LZMA, LZ4, 무압축 선택                                   │
│ 버전: 개발자가 매니페스트로 관리                               │
│                                                                │
│ 특징:                                                           │
│ - 세밀한 제어 가능                                              │
│ - 학습 곡선 있음                                                │
│ - Addressables로 추상화 가능                                   │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│                    Unreal Pak 파일                              │
├────────────────────────────────────────────────────────────────┤
│ 단위: 청크 기반 자동 분류 또는 수동 Chunk ID                    │
│ 빌드: 쿠킹 파이프라인에서 자동 생성                            │
│ 로드: 엔진이 자동 마운트 (대부분 투명하게 처리)                │
│ 압축: Zlib, Oodle (플랫폼별 최적)                              │
│ 버전: 패치 시스템과 통합 (ChunkDownloader)                     │
│                                                                │
│ 특징:                                                           │
│ - 엔진이 많은 부분 자동 처리                                    │
│ - 상대적으로 쉬움                                               │
│ - 커스텀 제어 시 복잡                                           │
└────────────────────────────────────────────────────────────────┘
Unreal의 청크 시스템은 어떻게 동작해?

Unreal은 에셋을 자동으로 청크(Chunk)로 분류합니다:

Unreal 청크 구조:

┌─────────────────────────────────────────────────────────────┐
│ Chunk 0 (항상 설치)                                          │
│ - Engine 코어 에셋                                           │
│ - 게임 시작에 필수적인 에셋                                   │
│ - Startup 맵                                                  │
└─────────────────────────────────────────────────────────────┘
        ↓ (선택적 다운로드)
┌─────────────────────────────────────────────────────────────┐
│ Chunk 1 ~ N (온디맨드 다운로드)                              │
│ - Primary Asset Labels로 지정된 에셋                         │
│ - 또는 자동 청크 할당                                        │
│                                                             │
│ 예시:                                                        │
│ Chunk 1: Chapter1_Map + 관련 에셋                           │
│ Chunk 2: Chapter2_Map + 관련 에셋                           │
│ Chunk 3: DLC_Content                                        │
└─────────────────────────────────────────────────────────────┘

│ character_hero.bundle      - 영웅 전용 에셋 (공유 참조)     │
│ map_forest.bundle          - 숲 맵 전용 에셋                │
│                                                             │
│ 의존성:                                                      │
│ character_hero → shared_materials                           │
│ map_forest → shared_textures, shared_materials              │
└─────────────────────────────────────────────────────────────┘
번들 크기는 어느 정도가 적당해?

번들 크기에는 트레이드오프가 있습니다:

번들 크기 트레이드오프:

너무 작은 번들 (1MB 이하):
┌─────────────────────────────────────────────────────────────┐
│ 장점:                                                        │
│ - 세밀한 로드 제어                                           │
│ - 사용하지 않는 에셋 로드 최소화                             │
│                                                             │
│ 단점:                                                        │
│ - 번들 수 폭증 (1000개+)                                     │
│ - 많은 HTTP 요청 (네트워크 오버헤드)                        │
│ - 의존성 관리 복잡                                           │
│ - 각 번들당 헤더/메타데이터 오버헤드                        │
└─────────────────────────────────────────────────────────────┘

너무 큰 번들 (100MB+):
┌─────────────────────────────────────────────────────────────┐
│ 장점:                                                        │
│ - 번들 수 적음, 관리 쉬움                                    │
│ - HTTP 요청 적음                                             │
│                                                             │
│ 단점:                                                        │
│ - 작은 업데이트에도 전체 재다운로드                          │
│ - 메모리 비효율 (일부만 필요해도 전체 로드)                 │
│ - 다운로드 실패 시 재시도 부담                              │
└─────────────────────────────────────────────────────────────┘

권장 크기:
┌─────────────────────────────────────────────────────────────┐
│ 플랫폼        권장 번들 크기        비고                     │
│ 모바일        2~10MB               네트워크 불안정 고려      │
│ 콘솔/PC       5~50MB               더 여유 있음              │
│ 스트리밍      1~5MB                빠른 로드 필요            │
│                                                             │
│ 예외:                                                        │
│ - 대용량 텍스처 아틀라스: 단독 번들로 분리                  │
│ - 영상/오디오: 크기보다 스트리밍 여부가 중요                │
└─────────────────────────────────────────────────────────────┘
번들 버전 관리는 어떻게 해야 해?

버전 관리는 에셋 번들 시스템의 핵심입니다:

에셋 번들 버전 관리 전략:

1. 매니페스트 + 해시 기반 (표준)
┌─────────────────────────────────────────────────────────────┐
│ 서버의 manifest.json:                                        │
│ {                                                            │
│   "bundles": {                                               │
│     "characters_hero": {                                     │
│       "hash": "abc123...",                                   │
│       "crc": 1234567890,                                     │
│       "size": 5242880,                                       │
│       "dependencies": ["shared_materials"]                   │
│     },                                                       │
│     "shared_materials": {                                    │
│       "hash": "def456...",                                   │
│       ...                                                    │
│     }                                                        │
│   },                                                         │
│   "version": "1.2.3"                                         │
│ }                                                            │
│                                                             │
│ 클라이언트 로직:                                             │
│ 1. 매니페스트 다운로드 (작은 JSON)                           │
│ 2. 로컬 캐시의 해시와 비교                                   │
│ 3. 해시 다르면 → 해당 번들만 재다운로드                     │
└─────────────────────────────────────────────────────────────┘

2. 파일명에 해시 포함 (CDN 캐시 친화적)
┌─────────────────────────────────────────────────────────────┐
│ 파일 구조:                                                   │
│ bundles/                                                     │
│ ├── characters_hero_abc123.bundle                           │
│ ├── characters_hero_xyz789.bundle  (새 버전)                │
│ └── shared_materials_def456.bundle                          │
│                                                             │
│ 장점:                                                        │
│ - CDN 캐시 무효화 불필요 (URL이 바뀌니까)                   │
│ - 롤백 쉬움 (이전 URL로 변경)                               │
│                                                             │
│ 단점:                                                        │
│ - 서버에 여러 버전 축적                                      │
│ - 오래된 버전 정리 필요                                      │
└─────────────────────────────────────────────────────────────┘
// 매니페스트 기반 버전 체크 예시 public class BundleVersionChecker { private Dictionary<string, string> m_LocalHashes; public IEnumerator CheckForUpdates() { // 서버에서 최신 매니페스트 다운로드 using (var request = UnityWebRequest.Get(MANIFEST_URL)) { yield return request.SendWebRequest(); var manifest = JsonUtility.FromJson<BundleManifest>( request.downloadHandler.text ); // 업데이트 필요한 번들 목록 List<string> bundlesToUpdate = new(); foreach (var bundle in manifest.bundles) { if (!m_LocalHashes.TryGetValue(bundle.name, out var localHash) || localHash != bundle.hash) { bundlesToUpdate.Add(bundle.name); } } // 업데이트 필요한 번들 다운로드 foreach (var bundleName in bundlesToUpdate) { yield return DownloadBundle(bundleName); } } } }

핵심 정리

  • 에셋 번들이란? 런타임에 로드 가능한 형태로 에셋을 패키징한 아카이브. Import 완료된 직렬화 데이터 포함
  • 왜 필요한가? 앱 크기 최소화, 동적 업데이트, 부분 다운로드, Resources 폴더의 한계 극복
  • 압축 옵션: LZMA(최고 압축률), LZ4(빠른 로드, 권장), 무압축(최고 속도)
  • 로딩 2단계: 번들 로드(컨테이너 열기) → 에셋 로드(실제 데이터)
  • 언로드 주의: Unload(true)는 참조 중인 에셋도 해제 - 참조 카운팅 필수
  • 그룹핑 전략: 공유 에셋은 별도 번들, 콘텐츠별로 논리적 그룹, 2~50MB 권장
  • 버전 관리: 매니페스트 + 해시 비교로 변경된 번들만 업데이트
