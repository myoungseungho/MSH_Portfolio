프로시저 호출 1개가 왜 100ms나 걸려?

SP 컴파일 오버헤드와 Plan Cache - 첫 호출이 느린 이유

Part 1. 이상하다, 첫 번째 호출만 느려

프로시저 호출하는데 처음만 100ms, 두 번째부터는 5ms야. 왜 그래?

첫 호출 때 컴파일이 일어났거든.

SQL Server는 프로시저를 실행하기 전에 "실행 계획"을 만들어야 해.

실행 계획? 그게 뭔데?

네비게이션 경로라고 생각하면 돼.

"서울에서 부산 가기" → 어떤 길로 갈지 미리 계산하는 거야.

[프로시저 첫 호출 - 컴파일 발생] EXEC gp_LoadCharacter @CharNo = 12345 │ ├─ 1단계: 구문 분석 (Parsing) ─────────── 5ms │ "문법 맞아? 테이블 있어?" │ ├─ 2단계: 최적화 (Optimization) ──────── 50ms ← 여기가 비싸! │ "인덱스 쓸까? 풀스캔 할까? JOIN 순서는?" │ ├─ 3단계: 실행 계획 캐싱 ─────────────── 5ms │ Plan Cache에 저장 │ └─ 4단계: 실제 실행 ──────────────────── 5ms 데이터 가져오기 총합: 65ms (컴파일 55ms + 실행 5ms)

최적화 단계가 가장 비싸.

테이블 통계 확인, 인덱스 비교, 여러 경로 시뮬레이션...

Part 2. Plan Cache - 한 번 만든 계획은 재사용

두 번째 호출은 왜 빠른 거야?

Plan Cache에 저장된 걸 재사용하니까.

[프로시저 두 번째 호출 - 캐시 히트] EXEC gp_LoadCharacter @CharNo = 67890 │ ├─ Plan Cache 확인 ──────────────────── 0.1ms │ "gp_LoadCharacter 계획 있네!" │ └─ 바로 실행 ────────────────────────── 5ms 캐시된 계획 사용 총합: 5.1ms (컴파일 0ms!)
그럼 Plan Cache는 영원히 유지돼?

아니. 여러 이유로 사라질 수 있어:

캐시가 사라지는 경우 왜?
서버 재시작 메모리 초기화
메모리 부족 오래된 계획부터 제거
프로시저 수정 ALTER PROCEDURE 실행
통계 업데이트 테이블 데이터 변경 많을 때
스키마 변경 인덱스 추가/삭제

서버 재시작 직후에 첫 접속자들이 느린 건 이 때문이야.

모든 프로시저가 다시 컴파일되니까.

Part 3. 컴파일이 매번 일어나는 최악의 케이스

캐시 안 되고 매번 컴파일되는 경우도 있어?

있어. 가장 흔한 실수가 Dynamic SQL이야.

-- ❌ 나쁜 예: 동적 SQL (매번 컴파일) CREATE PROCEDURE gp_SearchItem @ItemName NVARCHAR(50) AS BEGIN DECLARE @sql NVARCHAR(MAX) SET @sql = 'SELECT * FROM TItem WHERE ItemName = ''' + @ItemName + '''' EXEC(@sql) -- 매번 새 SQL = 매번 컴파일! END
호출 1: EXEC gp_SearchItem '장검' → SQL: "SELECT * FROM TItem WHERE ItemName = '장검'" → 컴파일 (새 SQL이니까) 호출 2: EXEC gp_SearchItem '단검' → SQL: "SELECT * FROM TItem WHERE ItemName = '단검'" → 컴파일 (또 새 SQL이니까!) 문자열이 다르면 = 다른 SQL = 매번 컴파일
-- ✅ 좋은 예: 파라미터화 (캐시 재사용) CREATE PROCEDURE gp_SearchItem @ItemName NVARCHAR(50) AS BEGIN SELECT * FROM TItem WHERE ItemName = @ItemName -- 파라미터만 바뀌므로 같은 계획 재사용 END

파라미터화하면 SQL 구조가 같으니까 캐시 재사용 가능!

Part 4. 일부러 재컴파일하는 경우

근데 가끔은 새로 컴파일하는 게 나을 때도 있지 않아?

맞아. 데이터 분포가 극단적으로 다를 때.

이걸 Parameter Sniffing 문제라고 해.

[극단적 데이터 분포 예시] 테이블: TPlayer (100만 명) ├── ServerID = 1: 50만 명 (50%) └── ServerID = 99: 10명 (0.001%) 첫 호출: @ServerID = 1 (50만 명) → 최적화: "풀스캔이 낫겠다" → 이 계획이 캐시됨 두번째: @ServerID = 99 (10명) → 캐시된 계획 사용 (풀스캔) → 10명 찾는데 50만 건 스캔?! 비효율!
그럼 어떻게 해?

세 가지 방법이 있어:

1. WITH RECOMPILE - 매번 재컴파일

EXEC gp_FindPlayer @ServerID = 99 WITH RECOMPILE
항상 최적의 계획. 대신 컴파일 비용 발생.

2. OPTION(RECOMPILE) - 특정 쿼리만

프로시저 내 특정 쿼리에만 적용.
SELECT * FROM TPlayer WHERE ServerID = @ServerID OPTION(RECOMPILE)

3. OPTIMIZE FOR - 특정 값 기준

OPTION(OPTIMIZE FOR (@ServerID = 50))
중간값 기준으로 계획 생성.

대부분의 경우 캐시 재사용이 이득이야.

RECOMPILE은 정말 필요할 때만!

Part 5. 서버 시작 직후가 느린 이유

게임 서버 재시작하면 처음 몇 분 동안 느려. 왜 그래?

Plan Cache가 비어있거든.

첫 접속자들이 모든 프로시저를 컴파일시키는 거야.

[서버 시작 직후 상황] 09:00 서버 재시작 └── Plan Cache: 비어있음 09:01 첫 번째 유저 로그인 ├── gp_LoadAccount → 컴파일 (50ms) ├── gp_LoadCharacter → 컴파일 (100ms) ├── gp_LoadInventory → 컴파일 (80ms) └── 총 로그인 시간: 500ms+ (느림!) 09:02 두 번째 유저 로그인 ├── gp_LoadAccount → 캐시 히트 (5ms) ├── gp_LoadCharacter → 캐시 히트 (5ms) └── 총 로그인 시간: 50ms (빠름!)
미리 워밍업 할 수 있어?

할 수 있어! 더미 호출로 캐시를 채우는 거야.

-- 서버 시작 시 워밍업 스크립트 -- 자주 쓰는 프로시저들을 미리 한 번씩 호출 EXEC gp_LoadAccount @AccountNo = 1 EXEC gp_LoadCharacter @CharNo = 1 EXEC gp_LoadInventory @CharNo = 1 EXEC gp_LoadQuest @CharNo = 1 EXEC gp_LoadSkill @CharNo = 1 -- ... 모든 주요 프로시저

실제 유저가 들어오기 전에 Plan Cache를 미리 채워두면

첫 유저도 빠르게 로그인할 수 있어.

Part 6. Plan Cache 상태 확인하기

현재 캐시된 계획들을 볼 수 있어?

DMV로 확인 가능해.

-- 캐시된 프로시저와 사용 횟수 SELECT TOP 20 OBJECT_NAME(object_id) AS proc_name, execution_count, total_elapsed_time / 1000 AS total_ms, total_elapsed_time / execution_count / 1000 AS avg_ms, cached_time FROM sys.dm_exec_procedure_stats ORDER BY execution_count DESC
-- Plan Cache 메모리 사용량 SELECT type AS cache_type, entries_count, single_pages_kb + multi_pages_kb AS total_kb FROM sys.dm_os_memory_cache_counters WHERE type = 'CACHESTORE_SQLCP' -- SQL 계획 캐시
캐시를 강제로 비울 수도 있어?

가능하지만, 운영 중엔 절대 하지 마.

-- ⚠️ Plan Cache 전체 비우기 (테스트 환경에서만!) DBCC FREEPROCCACHE -- 특정 프로시저만 비우기 DECLARE @plan_handle VARBINARY(64) SELECT @plan_handle = plan_handle FROM sys.dm_exec_procedure_stats WHERE OBJECT_NAME(object_id) = 'gp_LoadCharacter' DBCC FREEPROCCACHE(@plan_handle)

핵심 정리

  • 첫 호출이 느린 이유 = 실행 계획 컴파일 (최적화 비용)
  • Plan Cache = 컴파일된 계획 저장소 → 재사용으로 빨라짐
  • 동적 SQL = 문자열이 다르면 매번 컴파일 (피할 것)
  • WITH RECOMPILE = 극단적 데이터 분포일 때만 사용
  • 서버 시작 워밍업 = 더미 호출로 캐시 미리 채우기
  • dm_exec_procedure_stats = 캐시 상태 모니터링
