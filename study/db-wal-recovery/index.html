커밋했는데 서버가 죽으면? — WAL이 데이터를 살리는 법

먼저 로그에 적고 나중에 반영 — Write-Ahead Logging, 순차 쓰기, redo/undo 복구, 체크포인트

30초 요약

버퍼 풀 편의 숙제: 더티 페이지가 디스크 반영 전 죽으면 유실. WAL이 이걸 막아.

WAL(Write-Ahead Logging) = '데이터 페이지를 바꾸기 전에, 변경 내용을 로그에 먼저 적어라'.

로그는 순차 쓰기라 빠르고 작음 → 커밋 순간 로그만 디스크에 있으면 안전. 데이터는 나중에 몰아서.

죽으면 로그를 재생: 커밋된 건 redo(재적용), 커밋 안 된 건 undo(되돌림) → 정확히 그 시점으로 복구.

Part 1. 딜레마 — 더티는 위험한데, 매번 쓰면 느리다

버퍼 풀 편에서 봤지 — 더티 페이지가 디스크 가기 전에 죽으면 유실이었잖아. 그냥 바꿀 때마다 바로 디스크에 쓰면 안 돼?

그럼 두 가지가 터져.

① 느려. 데이터 페이지는 디스크 여기저기 흩어져 있어서 매번 쓰면 랜덤 쓰기 폭발(버퍼 풀이 왜 있었는지 도루묵).

② 쓰다 죽으면 오히려 더 위험. 8KB 페이지를 쓰는 도중 정전되면 반만 써진 페이지(찢어진 페이지)가 돼 — 원본까지 깨져.

그럼 어쩌라는 거야? 바로 쓰지도, 안 쓰지도 못하잖아.

여기서 발상의 전환이 나와. "무거운 데이터 페이지 말고, '뭘 바꿨는지'라는 가벼운 메모(로그)만 먼저 안전하게 적어두면?"

데이터 자체는 천천히 반영해도, 로그만 살아있으면 죽었다 살아나서 로그 보고 다시 만들 수 있잖아. 이게 WAL의 핵심이야.

Part 2. WAL — 로그를 데이터보다 먼저

WAL이 정확히 무슨 규칙이야?

Write-Ahead Logging = "데이터 페이지를 (디스크에) 쓰기 전에, 그 변경 내용을 로그에 먼저 적어라."

순서가 생명이야:

1. 변경 내용을 로그에 append ("TX1: P3의 HP 100→70")

2. 로그에 COMMIT 기록 → 이게 디스크 로그에 닿는 순간 '커밋 확정'. 유저에게 성공 응답.

3. 실제 데이터 페이지(P3)는 RAM에서만 바뀐 채(더티) → 디스크엔 나중에 반영.

2번 이후엔 언제 죽어도 안전해 — 로그에 다 있으니까. 아래에서 순서를 밟아봐.

그럼 커밋했는데 3번(데이터 반영) 전에 죽으면?

괜찮아. 로그에 'TX1 COMMIT'이 있으니, 살아날 때 로그를 보고 P3를 70으로 다시 만들어(redo). 유저한테 커밋 성공이라 해놓고 데이터가 사라지는 일이 없어져.

반대로 로그에 COMMIT이 없는데 데이터만 어쩌다 반영됐으면? 그건 되돌려(undo). (Part 4에서)

📝 WAL — 데이터보다 '로그'를 먼저 적는다

▶ 단계 진행으로 커밋 한 건이 처리되는 순서를 봐. 핵심은 '데이터 페이지를 디스크에 쓰기 전에, 변경 내용을 로그에 먼저 적는다'는 것.

HP 100→70으로 바꾸는 커밋 한 건이야. 로그와 데이터가 각각 언제 디스크에 닿는지 봐.

Part 3. 왜 로그가 빠른가 — 순차 vs 랜덤

로그도 결국 디스크에 쓰는 거잖아. 그건 안 느려?

여기가 핵심 트릭이야. 로그는 '순차 쓰기'라 훨씬 빨라.

• 로그: 파일 끝에 계속 이어 붙이기(append)만 함 — 디스크 헤드가 한 곳에 머물러. 순차 쓰기.

• 데이터 페이지: 바뀐 페이지가 파일 여기저기 흩어져 있어 — 매번 다른 위치로 점프. 랜덤 쓰기.

특히 HDD에선 순차가 랜덤보다 수십~수백 배 빨라. 그래서 '작고 순차적인 로그'만 먼저 확정하고, '무겁고 랜덤한 데이터'는 나중에 몰아서 쓰는 게 이득이야.

🏃 왜 로그가 더 빠른가 — 순차 쓰기 vs 랜덤 쓰기

로그는 파일 끝에 이어 붙이기만(순차), 데이터 페이지는 여기저기 흩어진 위치에 쓰기(랜덤)야. 100번 쓰기로 비교해봐. (예시값)

Part 4. 죽었다 살아나기 — redo & undo

실제로 죽었다 켜지면 DB가 뭘 해?

로그를 처음부터 재생하며 두 가지 정리를 해:

1. REDO(재적용): 로그엔 COMMIT이 있는데 데이터 페이지엔 아직 반영 안 된 것 → 로그대로 다시 적용. (커밋했다 약속했으니 지켜야지)

2. UNDO(되돌림): 데이터엔 반영됐는데 로그에 COMMIT이 없는 것(커밋 전 죽음) → 원래대로 되돌림. (커밋 안 했으니 없던 일로)

그 둘만 하면 진짜 딱 그 시점으로 돌아가?

응. '커밋된 것은 전부 살아있고(redo), 커밋 안 된 것은 전부 사라진(undo)' 상태 = 원자성·지속성이 지켜진 일관된 상태야. 이게 ACID의 A(원자성)와 D(지속성)를 실제로 구현하는 방법이야.

커밋된 것과 안 된 것이 섞인 채로 💥 크래시를 눌러봐. 그다음 🔄 복구를 누르면, 로그를 보고 '커밋된 건 다시 적용(redo), 커밋 안 된 건 되돌리기(undo)'로 정확히 원상복구해.

Part 5. 체크포인트 & 로그 관리

로그를 계속 append하면 무한정 쌓이잖아. 복구 때 처음부터 다 재생해?

그래서 체크포인트가 있어(버퍼 풀 편에서 만난 그거). 체크포인트 = '이 시점까지의 더티는 디스크에 다 반영했다'는 표시. 복구는 마지막 체크포인트 이후의 로그만 재생하면 되니 시간이 확 줄어.

그리고 반영 끝난 옛 로그 구간은 재사용/정리해(복구 모델이 Simple이면 자동, Full이면 백업 후) — 그래서 로그가 무한정 안 커져.

결국 WAL이 보장하는 게 뭐야? 한 줄로.

"커밋했다고 응답한 데이터는, 그 직후 서버가 죽어도 절대 잃지 않는다" — 이게 ACID의 D(Durability, 지속성)야.

그 비결은 딱 하나 — 무거운 데이터보다 '가볍고 순차적인 로그'를 먼저 안전하게 확정하고, 죽으면 그 로그로 redo/undo해서 정확한 시점을 재구성하는 것. MSSQL·Oracle·PostgreSQL·MySQL 다 이 원리야(이름만 트랜잭션 로그/redo log/WAL로 다를 뿐).

핵심 정리

  • 딜레마: 더티를 바로 디스크에 쓰면 느리고(랜덤) 찢어진 페이지 위험, 안 쓰면 죽을 때 유실.
  • WAL = 데이터 페이지를 쓰기 전에 '변경 내용'을 로그에 먼저 적는 규칙.
  • 커밋 = 로그에 COMMIT이 디스크에 닿는 순간 확정 → 이후 죽어도 안전. 데이터는 나중에 반영.
  • 로그가 빠른 이유 = 순차 쓰기(append) vs 데이터의 랜덤 쓰기. 작고 빠른 것부터 확정.
  • 복구 = 로그 재생. 커밋된 것 redo(재적용) + 커밋 안 된 것 undo(되돌림) → 정확한 시점.
  • 체크포인트로 재생 구간을 줄이고 로그를 정리. WAL = ACID의 D(지속성)를 구현하는 방법.
