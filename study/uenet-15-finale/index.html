종합 — UE 데디서버는 왜 우리 같은 MMO를 못 하나

16챕터를 한 줄로 꿰고, UE가 못하는 것 = 우리가 하는 것을 못 박는다

30초 결론

UE 네트워크는 '세션형'(1 프로세스 = 1 월드, 보통 ~100명)에 최적화된, 엔진 내장 복제·RPC 시스템이야.

UE가 '못'하는 것 — 영속 상태, DB 연동, 서버간 메시징, 수천 명 상시 — 이 4가지가 정확히 '우리 서버가 하는 것'이야.

그래서 Iris가 나와도 UE로 MMO가 되는 게 아니라, 둘은 애초에 다른 문제를 푸는 도구야.

Part 1. 16챕터를 한 줄로

지금까지 뭘 본 거야?

바닥(소켓·TCP/UDP·직렬화·IOCP)부터 시작해, 우리 서버를 기준점으로 잡고, UE의 엔진(NetDriver·Channel·Bunch·핸드셰이크)을 거쳐, 핵심인 복제(리플리케이션·Push·Dormancy·Relevancy)와 이동 예측, 그리고 대규모(ReplicationGraph·Iris)까지 왔어.

전부 관통하는 명제 하나: 서버가 진실, 클라는 복제본. 나머지는 '그걸 어떻게 빠르고 정확하게'의 디테일이었어.

Part 2. 동접을 올려봐 — 포화 vs 확장

UE와 우리의 결정적 차이를 봐.

탭으로 ① UE 세션형 ② 우리 MMO 를 바꾸고 동접 슬라이더를 올려봐.

UE는 한 월드라 정원에서 막혀(빨강). 우리는 동접이 늘면 채널(프로세스)을 더 띄워 수평 확장해(초록).

그럼 누가 더 좋은 거야?

좋고 나쁨이 아니라 '다른 문제'야. UE는 '한 판(세션) 안의 정밀한 액션 동기화'를 엔진이 다 해줘서 압도적으로 편해. 우리는 '영속 세계 + 수천 명 + 거래/DB'를 위해 직접 만든 거고.

FPS·배틀로얄을 우리 구조로 짜면 미련하고, MMO를 UE 데디서버만으로 짜면 벽에 부딪혀. 도구를 문제에 맞춰.

Fortnite는 100명 같이 하잖아? 그게 UE 한계야?
Fortnite는 ReplicationGraph + Epic의 광범위한 자체 최적화로 한 매치 100명을 안정시켰어 — 일반 UE 프로젝트가 그대로 받으면 보통 32~64명이 안정선. Epic이 엔진을 직접 다듬어서 가능한 수준이지, 박스 그대로의 UE 한계는 더 낮아. MMO 수천 명은 한 월드론 여전히 불가능 — 채널·존 샤딩으로만 가능.

Part 5. 그래서 뭘 얻었나 (메타)

엔진 소스를 다 외울 것도 아닌데 왜 읽었어?

Epic이 20년 다듬은 '답안지'를 읽은 거야. 쓰려고가 아니라 '설계 결정'을 보려고.

50점만 이해해도, 그 위에 AI를 얹으면 'LLM에게 정확한 질문을 던지고 방향을 잡는 사람'이 돼. 코드를 다 짜는 사람이 아니라, 무엇을 어떻게 만들지 판단하는 사람.

한 문장으로 마무리하면?

서버가 진실, 클라는 복제본 — 이 한 명제 위에서 UE는 '세션형 액션'을, 우리는 '영속 MMO'를 각자의 방식으로 푼다. 둘을 비교해 보니, 같은 원리를 어디까지·어떻게 끌고 가느냐가 곧 아키텍처 선택이더라.

핵심 정리

  • 관통 명제: 서버가 진실, 클라는 복제본 + RPC. 나머지는 전부 '빠르고 정확하게'의 디테일
  • UE = 세션형(1 월드 ~100명) 엔진 내장 복제·RPC·이동예측 — 액션에 압도적으로 편함
  • UE가 못하는 것(영속·DB·서버간·수천명) = 정확히 우리가 하는 것
  • Iris도 복제 효율 개선일 뿐, MMO를 주진 않음 — 둘은 다른 문제를 푸는 도구
  • 우리 ↔ UE: IOCP+Gate↔NetDriver, 패킷↔Bunch, CM_/SM_↔RPC, AOI↔Relevancy, 샤딩↔1월드
  • 메타: 50점 이해 + AI = 코드 다 짜는 사람이 아니라 방향을 잡는 사람

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 채널·존으로 쪼개면 채널 간 거래·대화는 어떻게?

이게 MMO의 진짜 난이도 — 분산 트랜잭션·정합성 문제가 그대로 들어와.

  • 거래: 다른 채널 사람과 1:1 거래는 보통 막거나(같은 채널만), 거래소(공용 DB) 경유로 풀어. 직접 거래는 "양 채널 모두 트랜잭션 합의"가 필요해 복잡.
  • 전체 채팅: 별도 채팅 서버를 두고 모든 게임 서버가 거기 붙어. 채팅은 게임 상태와 분리.
  • 친구·길드: 글로벌 서비스(별도 서버)로 분리. 게임 서버는 캐시만 갖고 진실은 글로벌에.
우리 서버가 풀고 있는 진짜 문제 = "단일 권위의 단순함을 잃고 분산 정합성을 다루는 것". UE 데디서버 위에 이걸 다 직접 깔아야 MMO가 됨.
Q. UE의 편한 복제/RPC만 떼어 우리 영속 구조에 얹을 순 없어?

개념(자동 복제·관련성·예측 보정)은 충분히 차용 가능해. 실제로 많은 MMO 회사가 자체 엔진에 "UE식 복제 레이어"를 직접 구현해.

  • 차용 좋음: 복제 선언 방식(Replicated 매크로), 관련성 추리기, 이동 예측 사이클.
  • 그대로 못 가져옴: UE의 NetDriver·NetConnection 자체는 1월드 가정이라 큰 작업.
  • 실전: UE를 클라엔진으로만 쓰고, 서버는 자체. 클라 사이드는 UE의 CharacterMovement·OnRep 같은 거 활용, 서버는 우리 식 메시지 처리.
로스트아크·블레이드 앤 소울 같은 게임이 이 패턴 — 클라는 UE/언리얼 엔진, 서버는 자체 구현.
Q. 한 채널 1코어가 천장이면 공성전 3000명 정답은?

완벽한 정답은 없어. 조합으로 풀어:

  • 인원 상한: 한 채널 정원을 두고, 넘으면 다른 채널로 분산. 같은 길드만 같은 채널로 매칭.
  • 관람 모드: 직접 참여자는 100~200명, 나머지는 가벼운 관람 클라로(상태만 받고 행동 X).
  • 관심 영역 강화: 같은 채널이어도 시야 밖은 정보 최소화.
  • 시간 분산: 공성전을 여러 시간대·여러 성으로 분산. 동시 인원 분산.
  • 핫스팟 분리: 성 내부와 외부를 별도 인스턴스로.
[총인원 = 1차 채널 × N + 관람 모드 + 시간대 × 성 N개] 예: 3000명 흡수 채널 1: 액티브 200 + 관람 800 = 1000 채널 2: 액티브 200 + 관람 800 = 1000 채널 3: 액티브 200 + 관람 800 = 1000 └─ 같은 길드는 같은 채널, 채널 간 결과 집계

이게 리니지·아이온 같은 거대 PvP를 굴리는 현실의 답. "한 곳에 다 모이지 않게" 설계로 푸는 거야.

Q. 다시 만든다면 UE에서 뭘 베끼고 뭘 버려?

베낄 것 / 버릴 것을 명확히:

베낄 것
• 객체 단위 자동 복제(Replicated 선언)
• 관련성/AOI를 엔진이 알아서 추리기
• 클라 예측 + 서버 보정 사이클(CharacterMovement)
• NetGUID 같은 객체 식별 자동화
버릴 것
• "1 프로세스 = 1 월드" 전제
• 영속 상태 무관 가정
• 단일 권위·세션 종료=상태 소멸
• 단일 NetDriver 가정

이상적: UE의 "복제 편의성·예측 정확성"을 가져오면서, 우리 식 "영속·샤딩·DB·서버간 메시징"을 유지. 즉 클라 측 UE 코드는 살리고, 서버 측은 우리 구조로 — 많은 한국 MMO가 이 길.
