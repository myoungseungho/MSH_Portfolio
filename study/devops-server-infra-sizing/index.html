CPU 16코어 샀는데 왜 4코어만 쓰고 있어?

게임 서버 인프라 사이징 — CPU·메모리·네트워크 부하 분석과 클라우드 머신 최적 배치

Part 1. 서버 머신 스펙, 감으로 고르면 어떻게 돼?

서버 느리면 CPU 좋은 거 사면 되는 거 아냐?

많은 사람이 그렇게 생각해. 그리고 실제로 그렇게 해서 돈을 날려.

실화를 하나 들려줄게.

8코어 서버가 느려서 16코어로 업그레이드했어. 비용 2배. 근데 체감 성능 차이? 거의 없었어.

왜냐면 그 서버는 스레드 7개만 쓰고 있었거든. 8코어에서 이미 코어가 남아돌고 있었는데, 16코어로 바꿔봤자 놀고 있는 코어만 늘어난 거야.

서버 머신을 고를 때 봐야 하는 4가지 자원: ┌─────────────────────────────────────────────┐ │ 서버 머신 │ │ │ │ 🧠 CPU 💾 메모리 │ │ - 코어 수 - 동접 × 유저당 메모리 │ │ - 클럭(GHz) - 버퍼, 큐 크기 │ │ - IPC(세대) - DB 캐시 │ │ │ │ 🌐 네트워크 💿 디스크 │ │ - 대역폭(Mbps) - 로그 쓰기 속도 │ │ - 패킷 수(PPS) - DB 저장 시 I/O │ │ - 레이턴시(ms) │ └─────────────────────────────────────────────┘ 이 4개 중 어디가 병목인지 모르면 → 엉뚱한 곳에 돈을 쓰게 됨
그럼 어떤 지식이 있어야 '이 서버엔 이 스펙이면 된다'고 말할 수 있어?

크게 3단계야:

1단계: 서버가 내부에서 뭘 하는지 안다

→ 스레드 구조, 메인 루프, DB 호출 방식

2단계: 실제 부하를 측정할 수 있다

→ CPU 사용률, 메모리 점유, 네트워크 트래픽

3단계: 측정값 → 머신 스펙으로 번역한다

→ '이 부하엔 이 인스턴스 타입이면 충분하다'

이 3단계를 순서대로 가보자.

Part 2. CPU — 코어 수 vs 클럭 속도, 뭐가 더 중요해?

CPU 살 때 코어 수랑 클럭 중에 뭘 먼저 봐?

서버 구조에 따라 다른데, 게임 서버는 대부분 클럭(단일 코어 성능)이 더 중요해.

이유: 게임 서버의 메인 루프는 보통 싱글스레드야. 전투 판정, 아이템 처리, 퀘스트 진행 — 이걸 전부 1개 스레드가 순차적으로 처리해.

게임 서버의 전형적인 스레드 구조: 네트워크 스레드 (IOCP) 메인 스레드 ┌──────────────────┐ ┌──────────────────┐ │ 소켓에서 패킷 수신 │ │ 큐에서 메시지 꺼냄 │ │ 복호화 │ ─큐─▶ │ 게임 로직 처리 │ │ 큐에 넣기 │ │ DB 호출 (동기) │ │ │ │ 결과 전송 │ └──────────────────┘ └──────────────────┘ ×4개 (대부분 대기 중) ×1개 (항상 바쁨) ★ ★ = 이게 병목. 이 스레드의 속도 = 서버 성능
그럼 예를 들어, 8코어 3.0GHz vs 4코어 4.5GHz면?

게임 서버라면 4코어 4.5GHz가 더 빠름.

메인 스레드는 1코어만 쓰니까:

- 8코어 3.0GHz → 메인 스레드 속도: 3.0GHz

- 4코어 4.5GHz → 메인 스레드 속도: 4.5GHz (50% 빠름)

나머지 코어는? IOCP 스레드 4개 + OS + DB 프로세스 돌리면 끝이야. 8코어까지 필요 없어.

그럼 코어 수가 중요한 경우는 없어?

있어. 한 머신에 서버 프로세스를 여러 개 올릴 때.

게임 서버 1개가 7스레드만 쓰면:

- 16코어 머신에 서버 2개 → 14스레드 (코어 여유 있음)

- 16코어 머신에 서버 3개 → 21스레드 (좀 빡빡)

이런 식으로 코어 수 = 같은 머신에 올릴 수 있는 프로세스 수로 보는 게 맞아.

또, 웹 서버나 DB 서버처럼 멀티스레드로 병렬 처리하는 서버는 코어 수가 직접적인 성능 향상으로 이어져.

서버 유형 코어 수 중요? 클럭 중요? 이유
게임 서버 (싱글스레드 루프) △ ★★★ 메인 루프가 1코어만 씀
웹 서버 (Nginx, Node.js) ★★ ★★ 워커 프로세스 × 코어 수
DB 서버 (MSSQL, MySQL) ★★★ ★★ 쿼리 병렬 실행에 코어 사용
빌드 서버 (CI/CD) ★★★ ★ 병렬 컴파일에 코어 수 직결

Part 3. IOCP 스레드 — 왜 늘려도 빨라지지 않아?

IOCP가 뭔데?

Windows에서 제공하는 비동기 네트워크 I/O 처리 구조야.

우체국 비유가 딱이야:

- 우체부 = IOCP 워커 스레드 (우체통에서 편지 꺼내서 분류함에 넣는 역할)

- 사장님 = 메인 스레드 (분류함에서 편지 꺼내서 실제 업무 처리)

- 분류함 = ReadQueue (CriticalSection 잠금으로 보호)

IOCP 스레드가 하는 일은 단순해: 소켓에서 데이터가 오면 꺼내서, 복호화하고, 큐에 넣기. 끝.

그럼 IOCP 스레드를 4개에서 8개로 늘리면? 우체부가 늘었으니 빨라져야 하잖아.

직감적으로는 그렇지. 하지만 맞춰봐 — 우체부 4명이 하루에 편지를 100통 처리할 수 있는데, 실제로 하루에 들어오는 편지가 30통이면?

우체부를 8명으로 늘려도 처리하는 편지는 30통 그대로야.

IOCP 스레드의 실제 시간 사용을 보면:

IOCP 스레드 1개의 시간 사용 (동접 1000명 기준): ██░░░░░░░░░░░░░░░░░░ 대기 (GetQueuedCompletionStatus) 90% █░░░░░░░░░░░░░░░░░░░ 실제 작업 (복호화 + InQueue) 10% 스레드 4개의 총 처리 용량: ████████████████████████████████ 400% 실제 들어오는 패킷량: ████████░░░░░░░░░░░░░░░░░░░░░░ 40% → 4개로도 이미 남아도는 상태 → 8개로 늘리면? 95% 놀고 있는 스레드가 8개가 될 뿐
근데 이론적으로, 코어가 충분하면 스레드 늘려도 해는 없는 거 아냐? 1스레드 = 1코어잖아.

맞아, 그 이론은 정확해.

16코어에서 11스레드(IOCP 8개 + 3개)면 컨텍스트 스위칭 없음.

실제로 해가 되는 경우는:

- 8코어에서 IOCP 8개(총 11스레드) → 11 > 8이라 컨텍스트 스위칭 발생 → 메인 스레드가 밀림

- 16코어에서 IOCP 8개(총 11스레드) → 11 < 16이라 컨텍스트 스위칭 없음 → 해는 없음

하지만 해가 없는 것 ≠ 이득이 있는 것. 놀고 있는 스레드를 더 만드는 거라 성능 향상은 0이야.

상황 IOCP 4개 IOCP 8개 판정
8코어 머신 7스레드 < 8코어 ✓ 11스레드 > 8코어 ✗ 느려짐 (컨텍스트 스위칭)
16코어 머신 7스레드 < 16코어 ✓ 11스레드 < 16코어 ✓ 동일 (이득 없음)
패킷 폭주 시 처리 용량 넉넉 처리 용량 더 넉넉 극단 상황에서만 의미
그럼 IOCP 스레드 수의 정답은?

일반적으로 CPU 코어 수 × 1~2가 권장값이야.

하지만 진짜 중요한 건 공식이 아니라 측정이야:

1. 현재 IOCP 스레드들의 CPU 사용률을 봐

2. 10% 미만이면 → 이미 충분 (줄여도 됨)

3. 70% 이상이면 → 늘려야 함

4. ReadQueue 오버플로우가 발생하면 → 확실히 부족

대부분의 게임 서버에서는 4개면 동접 수천 명까지 문제없어.

Part 4. 메모리 — 동접 1000명이면 얼마나 필요해?

서버 메모리는 뭐가 차지해?

게임 서버에서 메모리를 먹는 주범 3가지:

1. 유저당 메모리

- 캐릭터 데이터 (스탯, 인벤토리, 퀘스트)

- 소켓 버퍼 (수신 + 송신)

- 세션 정보

2. 고정 메모리

- ReadQueue (10MB 기본)

- CSV 데이터 테이블 (게임 데이터)

- 클라이언트 배열 (최대 접속자 슬롯)

3. DB 캐시

- DB 서버가 같은 머신에 있다면 이게 제일 큼

구체적으로 계산하면?

실제 예시로 계산해보자:

유저 1명당:

- 캐릭터 구조체: ~8KB

- 인벤토리 (200슬롯 × 아이템 구조체): ~16KB

- 소켓 수신 버퍼: 88KB (MAX_ONETIME_RECEIVE_BUFFER)

- 소켓 송신 버퍼: 설정값 (보통 8~256KB)

- 합계: 약 120~370KB/유저

동접 1000명이면:

- 유저 메모리: 120MB ~ 370MB

- 고정 메모리: ~200MB

- OS + 기타: ~500MB

- 합계: 약 1~1.5GB

동접 5000명이면:

- 유저 메모리: 600MB ~ 1.8GB

- 고정 + OS: ~700MB

- 합계: 약 1.5~3GB

동접 유저 메모리 고정 메모리 합계 권장 RAM
500명 60~180MB ~700MB ~1GB 4GB
1,000명 120~370MB ~700MB ~1.5GB 4GB
3,000명 360MB~1.1GB ~700MB ~2GB 8GB
5,000명 600MB~1.8GB ~700MB ~3GB 8GB
10,000명 1.2~3.7GB ~700MB ~5GB 16GB
메모리는 넉넉하게 잡으면 안 돼?

클라우드에서는 메모리 = 돈이야. 월 과금이니까.

- 4GB 인스턴스: 월 ~5만원

- 16GB 인스턴스: 월 ~15만원

- 64GB 인스턴스: 월 ~50만원

실제로 3GB만 쓰는데 64GB를 신청하면 매달 35만원을 버리는 거야.

그래서 측정해서 실사용량 × 1.5~2배로 잡는 게 정석이야.

Part 5. 네트워크 — 대역폭 얼마면 충분해?

게임 서버 네트워크 비용이 클까?

생각보다 안 커. 계산해보면:

게임 패킷은 보통 50~200바이트로 작아.

동접 1000명, 초당 패킷 10개/유저 기준:

- 수신: 1000명 × 10패킷 × 100바이트 = 1MB/초

- 송신: 보통 수신의 3~5배 = 3~5MB/초

- 합계: 약 40~50Mbps

100Mbps 회선이면 동접 1000명은 여유야.

그럼 네트워크가 병목인 경우는?

두 가지 상황에서 터져:

1. 브로드캐스트 폭발

100명이 한 화면에 모이면 → 각 유저에게 99명의 이동 패킷 전송

= 100 × 99 × 50바이트 × 초당 5회 = 2.5MB/초 (이 지역만)

공성전에 3000명이 모이면? 수학적으로 불가능한 수치가 나와.

2. 대용량 패킷

캐릭터 로딩 시 인벤토리 전체 전송 = 수십KB

동시 로그인 러시(점검 해제 후) → 순간 폭주

자원 측정 도구 주요 지표 위험 신호
CPU Task Manager, perf 코어별 사용률 % 메인 스레드 코어 90%↑
메모리 Task Manager, VMMap Working Set, Commit 물리 RAM 80%↑
네트워크 perfmon, netstat Bytes/sec, PPS 대역폭 70%↑
디스크 perfmon, iostat Queue Length, IOPS Queue > 2

Part 6. 클라우드 머신 실전 배치 — NCP/AWS에서 어떻게 골라?

클라우드 인스턴스 유형이 너무 많은데, 게임 서버는 뭘 골라?

클라우드 인스턴스는 보통 이렇게 나눠져:

- 범용 (General Purpose): CPU/메모리 균형 — 대부분의 게임 서버

- 컴퓨팅 최적화 (Compute Optimized): 높은 클럭 — 싱글스레드 병목인 게임 서버에 최적

- 메모리 최적화 (Memory Optimized): 대용량 RAM — DB 서버

- 스토리지 최적화: 높은 I/O — 로그 서버

게임 서버(싱글스레드 메인루프)라면 컴퓨팅 최적화 인스턴스가 가성비 최고야. 코어 수보다 단일 코어 클럭이 높은 타입.

실전에서 어떻게 배치해?

우리 서버 구조 기준으로 실전 예시:

방법 1: 프로세스별 머신 분리 (안전, 비쌈)

- 게임서버 1대 = 4코어 고클럭 × 1대

- GameDB서버 = 4코어 × 1대

- DB(MSSQL) = 8코어 메모리최적화 × 1대

방법 2: 한 머신에 여러 프로세스 (효율적)

- 16코어 머신에 게임서버 2개 + GameDB 2개 = 28스레드/16코어

- 비용 절감 효과: 머신 4대 → 1대

판단 기준은 총 스레드 수 ≤ 코어 수 × 1.5 를 넘지 않는 것.

클라우드 머신 배치 예시 (16코어 머신 1대): ┌─────────────────────────────────────────────┐ │ 16코어 머신 (32GB RAM) │ │ │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ Game11 │ │ Game12 │ │ │ │ 7스레드 │ │ 7스레드 │ │ │ │ 코어 0~3 │ │ 코어 4~7 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ ┌─────────────┐ ┌─────────────┐ │ │ │ GameDB1 │ │ GameDB2 │ │ │ │ 7스레드 │ │ 7스레드 │ │ │ │ 코어 8~11 │ │ 코어 12~15 │ │ │ └─────────────┘ └─────────────┘ │ │ │ │ 총 28스레드 / 16코어 = 1.75배 (약간 오버) │ │ → 실제로는 대부분 대기 상태라 OK │ └─────────────────────────────────────────────┘
비용 절감 팁 있어?

1. 측정 먼저, 스펙 나중

최소 스펙으로 시작 → 모니터링 → 병목 발견 → 해당 자원만 업그레이드

2. 스케일 아웃 > 스케일 업

16코어 1대(비쌈) < 8코어 2대(쌈) — 게임 서버는 프로세스 단위로 나뉘니까

3. 자원별로 다른 인스턴스

게임 서버 → 컴퓨팅 최적화 (고클럭)

DB 서버 → 메모리 최적화 (대용량 RAM)

로그 서버 → 범용 (대충 돌아도 됨)

4. 야간/비피크 시간 축소

새벽 2~7시 동접 100명인데 풀스펙 유지? 클라우드는 시간제야.

OS/시스템 기초 🔧 2. 서버 내부 구조 ├─ 프로세스 vs 스레드 ├─ 스레드 모델 (싱글/멀티) ├─ 컨텍스트 스위칭 비용 ├─ 메인 루프 구조 ├─ 가상 메모리 / Working Set ├─ 네트워크 I/O (IOCP, epoll) ├─ CPU 캐시 (L1/L2/L3) ├─ 동기 vs 비동기 DB ├─ 커널 모드 vs 유저 모드 └─ 메시지 큐 / 버퍼 구조 └─ CriticalSection / 뮤텍스 📊 3. 모니터링/측정 ☁️ 4. 클라우드/인프라 ├─ CPU 프로파일링 ├─ 인스턴스 타입 이해 ├─ 메모리 분석 (VMMap, Heap) ├─ 네트워크 토폴로지 ├─ 네트워크 측정 (PPS, BPS) ├─ 로드밸런서 ├─ 병목 식별법 ├─ 오토스케일링 └─ 부하 테스트 (더미 클라이언트) └─ 비용 최적화
이걸 다 알아야 해?

전부 전문가 수준일 필요는 없어. 레벨별로 나누면:

레벨 1 — 최소 필수 (이것만 알아도 삽질 방지)

- 스레드 모델 이해 (우리 서버가 스레드 몇 개 쓰는지)

- CPU 코어 vs 클럭의 차이

- Task Manager에서 프로세스별 CPU/메모리 읽기

- 클라우드 인스턴스 카탈로그 읽는 법

레벨 2 — 실전 운영 (비용 최적화 가능)

- 유저당 메모리 계산

- 네트워크 대역폭 추정

- perfmon/모니터링 도구 사용

- 부하 테스트로 한계점 파악

레벨 3 — 아키텍처 수준 (설계 단계에서 판단)

- IOCP/epoll 내부 동작 원리

- CriticalSection 경쟁과 스레드 수의 관계

- DB 동기/비동기의 성능 차이

- NUMA, CPU affinity 최적화

공부 주제 왜 필요한지 추천 학습 방법
OS 스레드/프로세스 서버가 CPU를 어떻게 쓰는지 이해 OSTEP 교재 (무료), Windows Internals
IOCP / epoll 네트워크 엔진의 스레드 구조 이해 MSDN 문서 + 실제 서버 코드 읽기
perfmon / 모니터링 실제 부하를 숫자로 보는 능력 라이브 서버에서 직접 측정해보기
클라우드 인스턴스 카탈로그 스펙 → 비용 변환 능력 NCP/AWS 가격 계산기 실습
부하 테스트 한계점을 사전에 파악 더미 클라이언트로 동접 올려보기

흔한 실수 — 이것만 피해도 절반은 성공

CPU 느리면 코어 수부터 늘린다 → 싱글스레드 서버면 클럭이 중요

메모리 넉넉하게 64GB 신청 → 실사용 3GB인데 매달 35만원 낭비

스레드 늘리면 무조건 빨라진다 → 병목이 아닌 곳을 늘리면 오히려 느려짐

감으로 스펙 결정 → 측정 없이 결정하면 과잉 또는 부족

모든 서버에 같은 스펙 적용 → 게임/DB/로그 서버는 병목이 다 다름

핵심 정리

  • 게임 서버 CPU: 코어 수보다 단일 코어 클럭(GHz)이 중요 — 메인 루프가 싱글스레드
  • IOCP 스레드 늘리기: 이미 90% 놀고 있으면 늘려도 의미 없음 — 병목이 아닌 곳 최적화는 효과 0
  • 코어 수의 실질적 가치: 한 머신에 서버 프로세스를 더 올릴 수 있는 '방 수'
  • 메모리 산정: 유저당 메모리 × 최대 동접 × 1.5~2배 = 필요 RAM
  • 인프라 사이징 핵심: 측정 → 병목 식별 → 해당 자원만 업그레이드 (감이 아닌 숫자로)
  • 서버 프로그래머의 가치: 이 판단을 할 수 있느냐가 '관리직'과 '매출 기여자'의 차이
