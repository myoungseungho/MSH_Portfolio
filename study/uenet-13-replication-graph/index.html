ReplicationGraph — 1000명이 한 곳에 모이면

관련성 계산을 N×M에서 확 줄이는 공간 격자

30초 요약

기본 관련성 검사 = 매 틱 클라마다 모든 액터와 거리 계산 → N×M (수천 명이면 폭발).

ReplicationGraph = 액터를 공간 격자(노드)에 미리 넣어두고, 클라는 '자기 셀 + 이웃'만 검사.

우리 채널·존 격자(AOI 그리드)와 같은 발상 — 비교를 N×M에서 확 줄임.

Part 1. 관련성 계산도 비싸다

Ch11에서 '관련 있는 것만 보낸다'고 했잖아. 그게 또 문제야?

보내는 건 줄었지. 근데 '누가 관련 있나'를 알려면 매 틱 거리 계산을 해야 해. 클라 1천 명 × 액터 1만 개 = 천만 번 비교. 보내기 전에 이 계산만으로 서버가 죽어.

공성전에 한 곳으로 몰리면 더 심해 — 그래서 '관련성 계산 자체'를 빠르게 해야 해.

어떻게 빠르게?

공간을 격자로 나눠 액터를 미리 칸에 넣어둬(버킷). 그럼 클라는 자기가 있는 칸과 이웃 칸만 보면 돼 — 멀리 있는 칸은 거리 계산조차 안 해.

이게 ReplicationGraph. 우리가 AOI를 그리드 셀로 관리하던 거랑 똑같아.

Part 2. 전수 vs 그리드

검사량 차이를 봐.

탭으로 ① 전수 검사 ② ReplicationGraph 를 바꿔봐. 노란 점이 '거리 계산하는 액터'야.

전수는 모든 액터가 노랑, 그리드는 '내 셀 + 이웃 8칸'만 노랑. 플레이어가 움직여도 항상 주변만 본다는 걸 확인해.

0이 클라가 검사하는 액터
80전체 액터

그럼 ReplicationGraph면 MMO 되나?

아니. ReplicationGraph는 '관련성 계산을 빠르게' 해서 한 서버가 감당하는 인원을 늘려주는 거지(예: 100명대 안정), 영속 상태·DB·서버간 통신·수천 명 상시는 별개야.

우리는 애초에 채널·존으로 프로세스를 쪼개 그 한계를 넘은 거고. 이 차이가 마지막 챕터(Ch15)의 결론이야.

Part 4. 실제로는?

ReplicationGraph는 어떻게 구성돼?

UReplicationGraph 아래에 여러 'Node'가 있어. UReplicationGraphNode_GridSpatialization2D(공간 격자), AlwaysRelevant 노드(항상 관련), 팀/플레이어 전용 노드 등.

각 노드가 '이 클라에게 보낼 액터 목록'을 만들어 합쳐. 게임마다 노드를 커스텀해서 자기 맵 특성에 맞춰.

Iris는 또 뭐야?

ReplicationGraph 다음 세대 복제 시스템이야. 데이터 지향(배치 처리)으로 복제 효율을 더 끌어올린 거 — 다음 챕터에서 봐.

UE 클래스UReplicationGraph + Node 조합

UReplicationGraph 아래에 여러 Node를 조합해서 '이 클라에게 보낼 액터 목록'을 만든다. 핵심 노드 3종 + 게임별 커스텀.

// 게임 시작 시 그래프 구성 class UMyReplicationGraph : public UReplicationGraph { void InitGlobalGraphNodes() { AddGlobalGraphNode( CreateNewNode<UReplicationGraphNode_GridSpatialization2D>()); AddGlobalGraphNode( CreateNewNode<UReplicationGraphNode_AlwaysRelevant>()); } }; // 자주 쓰는 노드 // • GridSpatialization2D : 공간 격자 // • AlwaysRelevant : 모두에게 항상 // • TeamConnectionList : 같은 팀에게만
우리 서버

채널·존 프로세스 단위 분리. 한 채널 안에선 AOI 그리드로 추리기.

언리얼

한 월드 안에서 노드 조합으로 추리기. 게임 특성에 맞게 커스텀 노드 작성.

핵심 정리

  • 관련성 계산도 비쌈: 전수 = 클라 × 액터 (N×M)
  • ReplicationGraph = 공간 격자 노드로 '내 셀 + 이웃'만 검사 → 비교 급감
  • = 우리 AOI 그리드/존과 같은 발상
  • 이걸로 한 서버 수용 인원↑, 하지만 여전히 1 월드 — 영속·DB·수천명은 별개
  • UReplicationGraphNode_GridSpatialization2D 등 노드 조합, 다음 세대 = Iris

이런 것도 궁금하지 않아?

읽다 보면 떠오르는 꼬리질문 — 눌러서 펼쳐봐

Q. 격자 셀 크기는 어떻게 정해?

황금 규칙은 "시야 반경의 절반~한 배"야.

[셀 크기 트레이드오프] 너무 크면: • 한 셀 안 액터 많음 → 안에서 다시 N² • 멀리까지 검사 → 무의미한 비교 너무 작으면: • 셀 자체가 너무 많음 → 메모리 + 관리 비용 • 빠른 액터는 매 프레임 셀 이동 적정: 시야 반경(~50m)와 비슷

실측 + 튜닝:

  • 대표 시나리오(공성전·일반 사냥)에서 한 클라가 검사하는 액터 수 측정.
  • 너무 많으면 셀 줄이기, 셀 전환 비용이 크면 셀 늘리기.
  • 맵 영역마다 다른 크기 — 광장은 작게, 광야는 크게.
Q. 마을 광장 한 셀에 1000명 몰리면 그 안에서 또 N²이잖아?

맞아 — 핫셀 문제. ReplicationGraph만으론 못 풀어.

대응 단계별:

  • 셀 안 우선순위: 모두를 매 틱 동기화하지 않고, 가까운 사람·중요한 액터부터.
  • 업데이트 빈도 차등: 가까운 30명은 60Hz, 그 다음 70명은 10Hz, 멀리는 1Hz.
  • 관전 모드 분리: 직접 참여 안 하는 사람은 "관전 클라"로 보고 가벼운 정보만.
  • 최후의 카드 — 프로세스 샤딩: 그 광장을 별도 서버 인스턴스로 분리(우리의 채널).
UE 단일 서버로는 1000명 동접지 핫셀이 사실상 불가능. MMO 규모는 결국 채널·존으로 쪼개야 풀려 — Ch15의 결론이 이거.
Q. 빠른 액터는 매 프레임 셀을 바꿔 등록/해제 비용이 더 크지 않아?

맞는 위험. 해결책은 두 가지:

  • 히스테리시스: 셀 전환에 약간의 여유. 셀 경계에서 살짝 넘어도 바로 안 옮기고, 일정 거리 들어가면 그제야 전환. 자잘한 왕복을 줄여.
  • 예외 처리: 발사체·미사일처럼 매우 빠른 액터는 별도 노드로(공간 격자에 안 넣고 다른 방식으로 관리).
[히스테리시스] 셀 A 경계 (x=100) x=98: 셀 A x=101: 아직 셀 A (여유 5) x=106: 이제 셀 B로 이동 x=104: 다시 셀 A 안 옴 (반대 방향은 더 안쪽까지) └─ 왕복 진동 방지
Q. 셀 경계에 걸친 액터는 두 셀에 다 넣어? 중복 복제 안 돼?

응, 양쪽 셀에 등록은 해. 그래야 양쪽 셀의 관전자 모두 그 액터를 보게 되거든. 단 복제는 한 번만:

[중복 방지] 액터 X가 셀 A,B 양쪽에 등록 클라 1(셀 A 관전): 후보 목록에 X 한 번 클라 2(셀 B 관전): 후보 목록에 X 한 번 → 각 클라 입장에선 X 한 번씩 복제 → 서버 전체로는 X 두 번 처리되지만 클라 1·2가 다른 클라라 정상

중복 처리는 그래프 노드 합치는 단계에서 자동으로(dedup). 한 클라의 최종 액터 목록엔 같은 액터가 한 번만 들어가.
