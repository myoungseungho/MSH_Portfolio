요청이 폭주해도 서버가 안 죽는 이유

Back Pressure로 시스템 과부하 방지하기

Part 1. 요청 폭주하면 뭐가 문제야?

신규 서버 오픈인데 갑자기 10만 명이 몰리면?

Back Pressure 없으면 이렇게 돼:

[Back Pressure 없는 시스템] 유저 요청: 초당 10,000개 서버 처리량: 초당 1,000개 시간 경과: 1초: 큐에 9,000개 쌓임 2초: 큐에 18,000개 쌓임 3초: 큐에 27,000개 쌓임 ... 💥 메모리 폭발 → 서버 다운
그냥 큐에 쌓아두면 나중에 처리하면 되는 거 아냐?

무한히 쌓을 수 없어!

• 메모리 한계 → OOM(Out of Memory)

• 처리 지연 → 유저는 "응답 없음"

• 연쇄 장애 → 다른 서버까지 영향

Part 2. Back Pressure가 뭔데?

Back Pressure가 뭐야?

"밀어내는 압력"이라는 뜻이야.

처리 못할 만큼 들어오면, 입구에서 막거나 늦춰버리는 거.

[Back Pressure 비유] 🚿 샤워기 비유: - 물(요청)이 너무 세게 나오면? → 수도꼭지를 잠금! - 배수구(서버)가 막히기 전에 물을 줄이는 것 🚗 고속도로 비유: - 차(요청)가 너무 많으면? → 진입 신호등으로 조절! - 도로(서버)가 막히기 전에 진입 속도를 늦추는 것
그러면 유저 요청을 거절한다는 거야?

일부는 거절하거나 늦추는 게 전체를 살리는 방법이야.

100명 다 죽이는 것보다, 20명 거절하고 80명 살리는 게 낫지.

Part 3. 전략 1: 거절하기 (Drop)

[거절 전략] if (queue.size() >= MAX_QUEUE_SIZE) { return "서버가 바쁩니다. 잠시 후 다시 시도해주세요."; // HTTP 503 Service Unavailable // 또는 HTTP 429 Too Many Requests } 게임 서버 예: - 매칭 큐 꽉 참 → "잠시 후 다시 시도해주세요" - 채팅 도배 → 일정 속도 이상 메시지 무시
유저한테 에러 보여주는 게 괜찮아?

친절한 메시지로 안내하면 돼:

• "접속자가 많습니다. 순번: 1,234"

• "잠시 후 자동 재시도됩니다"

서버 죽는 것보단 대기열이 훨씬 나아.

Part 4. 전략 2: 속도 제한 (Rate Limiting)

[Rate Limiting] 규칙: "각 유저당 초당 10회만 허용" 유저 A: 1초에 100번 요청 → 10번만 처리, 90번은 거절 (429 Too Many Requests) 구현 방법: 1️⃣ Token Bucket - 버킷에 토큰이 일정 속도로 채워짐 - 요청할 때마다 토큰 1개 소모 - 토큰 없으면 거절 2️⃣ Sliding Window - 최근 1초간 요청 수 카운트 - 한도 초과하면 거절
게임에서 언제 써?

• API 호출: 상점 새로고침 도배 방지

• 채팅: 초당 메시지 수 제한

• 매크로 방지: 비정상적 속도 감지

Part 5. 전략 3: 모아서 처리 (Buffering)

[Buffering + Batching] [안 좋은 방식] 로그 1개 → DB INSERT 로그 1개 → DB INSERT 로그 1개 → DB INSERT (초당 10,000번 INSERT → DB 죽음) [좋은 방식 - Buffer] 로그 1개 → 버퍼에 저장 로그 1개 → 버퍼에 저장 ... (1000개 모임) → 한 번에 BULK INSERT! (초당 10번 INSERT → DB 여유)
버퍼가 넘치면?

여기서도 Back Pressure 적용:

• 버퍼 80% 차면 → Producer에게 "천천히" 신호

• 버퍼 100% 차면 → Producer 일시 중단

Part 6. 전략 4: 차단기 (Circuit Breaker)

하위 서버가 느려지면 어떻게 해?

문제 있는 서버로 요청 자체를 안 보내버려.

[Circuit Breaker 패턴] 상태 3가지: ┌─────────────────────────────────────────────────┐ │ CLOSED (정상) │ │ → 요청 정상 전달 │ │ → 실패 5번 연속? → OPEN으로 전환 │ └─────────────────────────────────────────────────┘ ↓ 실패 누적 ┌─────────────────────────────────────────────────┐ │ OPEN (차단) │ │ → 요청 즉시 실패 반환 (하위 서버 호출 안 함) │ │ → 30초 후 → HALF-OPEN으로 전환 │ └─────────────────────────────────────────────────┘ ↓ 타임아웃 ┌─────────────────────────────────────────────────┐ │ HALF-OPEN (테스트) │ │ → 1개 요청만 보내봄 │ │ → 성공? → CLOSED로 복귀 │ │ → 실패? → OPEN으로 다시 │ └─────────────────────────────────────────────────┘

결제 서버가 죽었는데 계속 호출하면?

→ 게임 서버 스레드가 다 결제 대기하다 멈춤

→ Circuit Breaker로 빠르게 실패 처리!

Part 7. 게임 서버 Back Pressure 사례

[게임 서버 Back Pressure 적용] 1️⃣ 로그인 큐 - 동시 접속 한도: 10,000명 - 초과 시: 대기열 (순번 표시) - 이미 접속 중인 유저 보호 2️⃣ 매칭 큐 - 매칭 요청 초당 100개 제한 - 초과 시: "잠시 후 다시 시도" - 매칭 서버 과부하 방지 3️⃣ 로그 버퍼 - 로그 버퍼 크기: 10,000개 - 80% 차면: flush 주기 단축 - 100% 차면: 오래된 로그 드롭 4️⃣ DB 연결 풀 - 최대 연결: 100개 - 대기 큐: 500개 - 큐 꽉 차면: 즉시 에러 반환 5️⃣ 채팅 Rate Limit - 유저당 초당 5개 메시지 - 초과 시: 메시지 무시 - 도배/스팸 방지

핵심 정리

  • Back Pressure = 처리량 초과 시 입구에서 제어
  • 거절(Drop) = 큐 꽉 차면 503/429 반환
  • Rate Limiting = 유저/IP당 요청 속도 제한
  • Buffering = 모아서 배치 처리, 버퍼도 제한
  • Circuit Breaker = 문제 서버 호출 자체를 차단
  • 핵심 = 일부 거절해서 전체를 살린다
