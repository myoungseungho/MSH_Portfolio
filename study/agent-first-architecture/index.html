AI가 짜기 좋은 서버 구조가 따로 있다고?

인간이 짠 서버 vs AI 에이전트 퍼스트 서버 — 왜 구조가 달라야 하는가

Part 1. 인간은 코드를 어떻게 짜왔을까?

20년 된 게임 서버 코드를 열어봤더니 파일 하나가 26만 글자야. 이게 정상이야?

놀랍지만, 꽤 흔해. 인간이 코드를 짜는 방식을 생각해보면 이해가 돼.

인간 개발자는 IDE(개발 도구)로 프로젝트 전체를 "본다". 파일이 아무리 커도 Ctrl+F로 원하는 곳에 갈 수 있고, 머릿속에 전체 구조를 그려놓고 있으니까.

[인간 개발자의 코드 읽기 방식] 머릿속 지도 (전체 구조를 "알고 있음") │ ├── "아, 던전 입장은 GameMsg.cpp 1247번 줄이지" ├── "DB 저장은... 거기서 호출하는 DCM 메시지 따라가면 돼" └── "이 전역 변수는 여기서만 쓰이는 거야" (경험으로 앎) → 파일이 크든 작든, 머릿속에 다 있으니까 문제없음 → 5년차 개발자의 "감"으로 코드를 탐색함
그럼 인간이 짠 코드의 특징이 뭐야?

크게 5가지 특징이 있어:

[인간이 짠 서버 코드의 전형적 특징] 1. 거대한 파일 └── 프로토콜 정의 파일 하나가 26만 글자 (8,000줄+) └── 메시지 핸들러 하나에 수천 줄 2. 암묵적 연결 └── 전역 변수, 싱글턴으로 어디서든 접근 └── "이거 어디서 바뀌는지"는 경험으로 앎 3. 기능이 여러 파일에 흩어짐 └── "던전 입장" 하나에 GameMsg.cpp + DungeonMgr.cpp + ServerMsg.cpp + Procedure_*.h + CSV... (5~10개 파일) 4. 관례가 머릿속에만 존재 └── "이 프로젝트에서는 m_ 접두사를 쓴다" └── "DB 저장은 항상 이 패턴이다" └── → 문서화 안 됨, 신입이 물어봐야 알 수 있음 5. 점진적 누적 └── 2005년에 만든 구조 위에 2010년 기능 추가 └── 2015년에 또 추가... 리팩토링 시간은 없었음
이게 나쁜 코드라는 뜻이야?

아니, 나쁜 게 아니야. 인간에게 최적화된 코드인 거야.

인간은 "넓고 얕게" 볼 수 있어. IDE로 프로젝트 전체를 조감하고, 경험으로 "감"을 잡지. 그래서 파일이 크고, 연결이 암묵적이어도 작업할 수 있었던 거야.

문제는... AI 에이전트는 이 "감"이 없다는 거야.

Part 2. AI 에이전트는 코드를 어떻게 읽을까?

AI도 코드 잘 짜잖아. ChatGPT한테 물어보면 바로 답 주는데?

짧은 코드 한 조각은 잘해. 근데 수십만 줄짜리 실제 프로젝트를 다루는 건 완전히 다른 문제야.

AI 에이전트가 코드를 읽는 방식을 먼저 이해해야 해:

[AI 에이전트의 코드 읽기 방식] 컨텍스트 윈도우 (한 번에 볼 수 있는 양 = 제한적) │ ├── 파일을 "요청해서" 하나씩 읽음 ├── 한 번에 약 500~2000줄 정도가 적정 ├── 이전 세션의 기억 없음 (매번 처음부터) └── "이 변수가 어디서 바뀌는지"를 grep으로 검색 → 파일이 8,000줄이면? 한 번에 못 읽음 → 부분만 보고 판단해야 함 → 실수 확률 증가
그러니까 인간은 "전체를 보는" 방식이고, AI는 "부분을 읽는" 방식?

정확해. 비유하면 이래:

[비유: 도서관에서 책 찾기] 인간 사서 (10년 경력): "아, 그 책? 3층 왼쪽 두 번째 선반 중간쯤에 있어" → 전체 도서관 구조가 머릿속에 있음 → 한 번도 안 가본 코너도 "대충" 알고 있음 AI 로봇 사서 (매일 기억 리셋): "3층 왼쪽 선반을 스캔합니다... 없습니다" "3층 오른쪽 선반을 스캔합니다... 찾았습니다!" → 매번 처음부터 검색해야 함 → 한 번에 선반 하나씩만 볼 수 있음 → 대신, 한 선반 안에서는 초고속으로 정확하게 찾음
그럼 AI는 인간보다 못한 거야?

아니, 다른 거지. 핵심 차이를 표로 보면:

특성 인간 개발자 AI 에이전트
시야 넓고 얕게 (전체 조감) 좁고 깊게 (파일 단위)
기억 경험 누적 (10년치 "감") 세션마다 리셋 (매번 처음)
패턴 인식 비슷한 코드면 "대충" 파악 동일 패턴이면 100% 정확 복제
검색 능력 Ctrl+F, "기억나는 키워드" 정규식 전수 검색, 빠짐없음
동시 작업 1명 = 1작업 병렬 에이전트 5~10개 동시 투입
실수 피곤하면 실수, 컨디션 영향 패턴 벗어나면 실수, 컨디션 무관

핵심 통찰

AI 에이전트는 "좁고 깊게" 보는 데 탁월하고, "넓고 얕게" 파악하는 데 약하다.

그런데 인간이 짠 코드는 "넓고 얕게" 볼 수 있는 사람을 전제로 설계되어 있다.

여기서 구조적 불일치가 발생한다.

Part 3. 구체적으로 뭐가 문제야?

실제로 AI 에이전트가 2000년대 서버 코드를 다룰 때 뭐가 힘들어?

실제 MMORPG 서버 코드 사례로 보여줄게. 이건 진짜 겪은 문제들이야.

[고통 1: 거대 파일 — 컨텍스트 윈도우 초과] TIProtocol.h = 261KB (약 8,000줄) TIProtocolServer.h = 279KB (약 8,500줄) AI 에이전트의 컨텍스트 윈도우 ≈ 500~2,000줄이 적정 → 파일의 1/4만 읽고 판단해야 함 → "나머지 6,000줄에 관련 코드가 있을 수도 있는데..." → 부분만 보고 답하니까 틀리는 경우 발생
[고통 2: 인코딩 — 도구 자체가 작동 안 함] C++ 소스 파일: EUC-KR 인코딩 (2000년대 표준) AI 편집 도구: UTF-8만 지원 → AI가 파일을 수정하면? → 한글 주석 전부 깨짐: "던전 입장" → "????? ????" → 파일 전체가 손상됨 결과: AI의 표준 편집 도구를 못 쓰고 우회 도구(바이트 레벨 편집기)를 매번 사용 → 작업 속도 절반 이하로 떨어짐
[고통 3: 산탄총 수술 — 한 기능에 파일 10개] "던전 입장 기능을 수정해줘" AI가 찾아야 하는 파일들: 1. GameMsg.cpp (클라이언트 메시지 수신) 2. DungeonMgr.cpp (던전 로직) 3. ServerMsg.cpp (서버 간 메시지) 4. Procedure_*.h (DB 프로시저 바인딩) 5. TIProtocol.h (메시지 구조체 정의) 6. TIProtocolServer.h (서버 메시지 정의) 7. CSVFile_Dungeon.h (던전 데이터 파일) 8. TIDefineServer.h (상수 정의) 9. .vcxproj (빌드 설정) 10. SQL 프로시저 (DB 저장 로직) → 10개 파일을 전부 찾고, 읽고, 이해하고, 수정 → 하나라도 빠뜨리면 빌드 에러 or 런타임 버그 → 분석 에이전트만 3개 병렬로 돌려야 겨우 파악
[고통 4: 암묵적 의존성 — grep으로 못 찾는 연결] // 글로벌 싱글턴으로 어디서든 접근 가능 CDungeonMgr::GetInstance()->EnterDungeon(pPC); // 이 함수를 누가 호출하는지 찾으려면? // grep "EnterDungeon" → 30곳에서 발견! // 근데 어떤 게 "진짜" 호출이고 어떤 게 주석? // 어떤 순서로 호출되는지는? → 인간: "아, 이건 GameMsg에서 호출하는 거야" (경험) → AI: 30개 결과를 전부 읽고 분석해야 함 (비용 큼)
실제로 얼마나 차이 나?

같은 작업에 대한 체감 비교야:

작업 인간 개발자 (5년차) AI 에이전트 (현재 구조)
"던전 입장 로직 어디 있어?" "DungeonMgr.cpp야" (5초) grep + 10개 파일 분석 (분석팀 3개 병렬, 수 분)
"이 기능 수정해줘" 관련 파일 열고 수정 (30분) 영향 범위 분석 → 수정 → 빌드 루프 (수 시간)
"맞게 수정한 건지 확인" 서버 켜고 테스트 (10분) 서버 기동 후 사람에게 확인 요청 (자동화 어려움)

Part 4. 왜 이런 차이가 생기는 거야?

인간이 짠 코드가 왜 AI에게 안 맞는지, 근본 원리가 뭐야?

한 문장으로 요약하면:

"인간은 암묵지(暗默知)로 보완하고, AI는 명시지(明示知)만 읽을 수 있다."

[암묵지 vs 명시지] 암묵지 (Tacit Knowledge): = 경험으로만 알 수 있는, 문서화되지 않은 지식 = "이 프로젝트에서 m_ 접두사는 멤버 변수야" = "이 파일은 건드리면 안 돼, 3년 전 장애 났었어" = "이 패턴은 항상 이렇게 쓰는 거야" 명시지 (Explicit Knowledge): = 코드, 문서, 주석에 적혀 있는 지식 = README.md에 "이 모듈은 던전 시스템입니다" = 코드에 // 이 함수는 파티원 레벨을 검증합니다 = MANIFEST.yaml에 "의존성: party, inventory"
아, 인간은 코드에 안 적혀 있어도 "아는" 게 많구나

바로 그거야. 인간 팀에서는 이게 잘 돌아가. 물어보면 되니까.

근데 AI 에이전트는? 물어볼 선배가 없어. 코드에 적혀 있는 것만 읽을 수 있어.

[비유: 요리 레시피] 인간 셰프 (10년 경력): 레시피: "소금 적당히, 불 세기 적당히, 느낌 봐서 뒤집기" → 문제없음. "적당히"가 뭔지 경험으로 앎 AI 로봇 셰프 (매번 리셋): 레시피: "소금 적당히" → "적당히가 몇 그램입니까?" → "불 세기가 몇 도입니까?" → "느낌이... 뭡니까?" AI에게 주는 레시피: "소금 3g, 중불(180°C), 앞면 갈변 시 뒤집기(약 2분 30초)" → 완벽하게 재현 가능. 매번 동일한 결과.
그러니까 AI용 코드는 "소금 3g"처럼 모든 게 명시적이어야 한다?

정확해. 이게 핵심 원리야.

인간이 짠 코드 = "소금 적당히" (암묵지에 의존)

AI 퍼스트 코드 = "소금 3g" (명시지로만 구성)

이 원리 하나에서 모든 구조적 차이가 나오는 거야.

근본 원리

인간 중심 코드: 암묵지로 빈 곳을 채운다. 코드에 안 적혀 있어도 경험으로 보완.

에이전트 퍼스트 코드: 모든 것이 명시적. 코드와 메타데이터만 보면 100% 이해 가능.

이 차이가 파일 크기, 모듈 구조, 의존성 관리, 테스트 방식까지 전부 결정한다.

Part 5. 그럼 AI에게 최적화된 구조는 어떻게 생겼어?

같은 MMORPG 서버를 처음부터 AI 에이전트가 짠다면?

핵심 원칙은 "한 기능 = 한 폴더 = 완전 자급자족"이야.

[에이전트 퍼스트 서버 구조] game-server/ │ ├── _meta/ ← AI의 "지도" │ ├── ARCHITECTURE.md (전체 구조 설명) │ ├── CONVENTIONS.md (코딩 규칙 - 명시적!) │ └── dependency-graph.json (모듈 간 관계 - 기계 판독용) │ ├── core/ ← 인프라 (거의 안 건드림) │ ├── network/ (통신 엔진) │ ├── database/ (DB 연결) │ └── scheduler/ (타이머) │ ├── features/ ← 게임 기능 (AI 주 작업 영역) │ ├── dungeon/ ← 던전 = 이 폴더 안에 전부 있음! │ │ ├── MANIFEST.yaml (이 모듈의 "설명서") │ │ ├── handler.cpp (메시지 처리) │ │ ├── logic.cpp (비즈니스 로직) │ │ ├── queries.cpp (DB 쿼리) │ │ ├── types.h (데이터 구조) │ │ └── tests/ (자동 테스트) │ │ │ ├── quest/ (퀘스트 - 같은 구조) │ ├── combat/ (전투 - 같은 구조) │ └── inventory/ (인벤토리 - 같은 구조) │ └── codegen/ ← 반복 코드 자동 생성기 └── from-schema.py (스키마 → C++ 코드)
기존 구조랑 뭐가 달라?

기존 구조와 나란히 비교하면 차이가 확 보여:

관점 인간 중심 (기존) 에이전트 퍼스트
파일 크기 8,000줄짜리 프로토콜 파일 파일당 500줄 이하
기능의 위치 5~10개 파일에 흩어짐 한 폴더 안에 전부
규칙/관례 선배한테 물어봐야 앎 MANIFEST.yaml에 명시
의존성 전역 싱글턴 (암묵적) 명시적 import/선언
인코딩 EUC-KR (도구 제한) UTF-8 (모든 도구 호환)
검증 서버 켜고 수동 테스트 단위 테스트 자동 실행
반복 작업 DB 바인딩 수동 작성 스키마 → 코드 자동 생성
구체적으로 어떤 원리가 적용된 거야?

5가지 원리가 있어. 전부 아까 말한 "소금 3g" 원칙에서 나온 거야:

Part 6. 에이전트 퍼스트 5대 원리

원리 1: MANIFEST가 뭐야? 왜 필요해?

모듈마다 붙어 있는 "설명서"야. AI가 이 파일 하나만 읽으면 이 모듈의 모든 걸 파악할 수 있어.

[MANIFEST.yaml - 모듈의 설명서] name: dungeon description: "파티 던전 입장, 진행, 보상 시스템" files: handler: handler.cpp # 메시지 수신 진입점 logic: logic.cpp # 비즈니스 로직 queries: queries.cpp # DB 쿼리 dependencies: - party # 파티 시스템 - inventory # 인벤토리 (보상 지급) messages: - CM_DUNGEON_ENTER # 클라이언트 → 서버 - SM_DUNGEON_ENTER_RESULT # 서버 → 클라이언트 tables: - TDungeon # DB 테이블
[MANIFEST가 만드는 차이] 기존: "던전 입장 로직 수정해줘" → grep으로 CM_ENTER_DUNGEON 찾기 → 핸들러 찾기 → 매니저 찾기 → DB 찾기 → 영향 범위 분석에 에이전트 3개 투입 → 파악에만 수 분 소요 에이전트 퍼스트: "던전 입장 로직 수정해줘" → features/dungeon/MANIFEST.yaml 읽기 (10초) → handler.cpp + logic.cpp + queries.cpp 읽기 (30초) → 바로 수정 시작
원리 2: 파일 크기 제한이 왜 중요해?

AI의 컨텍스트 윈도우에 파일 전체가 들어가야 정확하게 수정할 수 있거든.

[파일 크기와 정확도의 관계] 파일 크기 AI가 볼 수 있는 비율 정확도 ───────── ────────────────── ──────── 200줄 100% 매우 높음 500줄 100% 높음 2,000줄 50% 보통 8,000줄 12% 낮음 (부분만 보고 추측) → 절대 규칙: 한 파일 500줄 이하! → 500줄 = 약 15KB → 어떤 AI 모델이든 한 번에 처리 가능
원리 3: 스키마 기반 코드 생성이 뭐야?

반복적인 "틀에 박힌" 코드를 AI가 직접 짜는 게 아니라, 설계도(스키마)에서 자동으로 만드는 방식이야.

[기존: 수동 바인딩 코드] DB에 새 필드 추가하려면: 1. SQL 프로시저 수정 2. C++ Procedure_*.h 바인딩 코드 작성 → offsetof() 매크로 정확히 맞추고 → 타입 변환 처리하고 → 버퍼 크기 계산하고... 3. 핸들러에 호출 코드 추가 4. .vcxproj 빌드 설정에 파일 등록 → AI가 실수하기 딱 좋은 구간 (바이트 레벨 정밀도 필요)
[에이전트 퍼스트: 스키마 → 자동 생성] 1. 스키마 파일에 한 줄 추가: - { name: BestTime, type: int, default: 0 } 2. 코드 생성기 실행: python codegen/from-schema.py dungeon.schema.yaml 3. 자동으로 생성되는 것들: ✅ C++ 구조체 (types.h) ✅ DB 바인딩 코드 (queries.cpp) ✅ SQL 마이그레이션 스크립트 ✅ 메시지 직렬화 코드 → AI는 "무엇을 추가할지"만 결정 (What) → "어떻게 바인딩할지"는 기계가 처리 (How)
원리 4: 단위 테스트가 왜 AI한테 특히 중요해?

현재 가장 큰 문제: AI가 코드를 수정해도 맞는지 확인하려면 서버를 직접 켜야 해.

서버 8개 켜고, 클라이언트 접속하고, 직접 테스트하고... 이걸 AI 혼자 자동으로 할 수 없어.

[현재: 검증에 사람이 필수] AI가 코드 수정 → 빌드 (자동 가능) → 서버 8개 기동 (복잡) → 더미 클라이언트 접속 (설정 필요) → 해당 기능 수동 테스트 (사람만 가능) → 결과 확인 (사람의 눈) → AI의 자율성: 50% (수정까지만 자동, 검증은 사람)
[에이전트 퍼스트: 서버 안 켜도 검증] // features/dungeon/tests/test_enter.cpp TEST(DungeonEnter, 레벨부족_입장불가) { auto player = 테스트_플레이어_생성(레벨: 10); auto result = 던전로직::입장시도(player, 레벨30_던전); EXPECT(result == 입장실패_레벨부족); } TEST(DungeonEnter, 이미던전중_입장불가) { auto player = 테스트_플레이어_생성(레벨: 50); player.현재던전 = 1; auto result = 던전로직::입장시도(player, 다른_던전); EXPECT(result == 입장실패_이미진행중); } AI 워크플로우: 코드 수정 → 테스트 실행 → 통과? → 완료! ↓ 실패 에러 분석 → 재수정 → 재테스트 (자동 루프) → AI의 자율성: 95% (수정 + 검증까지 전자동)
원리 5: 명시적 의존성이 뭐야?

"이 모듈이 다른 모듈의 뭘 쓰는지"가 코드에 드러나는 거야.

[기존: 암묵적 의존성] // 전역 싱글턴 — 아무 데서나 접근 가능 void EnterDungeon(CGamePC* pPC) { CPartyMgr::GetInstance()->GetParty(pPC); // 파티 시스템 CInventoryMgr::GetInstance()->AddItem(pPC); // 인벤토리 CQuestMgr::GetInstance()->CheckQuest(pPC); // 퀘스트 // → 이 함수가 3개 시스템에 의존한다는 사실을 // 코드를 "읽어야" 알 수 있음 }
[에이전트 퍼스트: 명시적 의존성] // 필요한 컴포넌트를 명시적으로 요청 void EnterDungeon(Entity player, int dungeonId) { auto& dungeon = player.get<DungeonComponent>(); auto& combat = player.get<CombatComponent>(); // → "dungeon"과 "combat"에 의존한다는 걸 // 첫 두 줄만 봐도 알 수 있음 // → MANIFEST.yaml에도 동일하게 기록됨 } → AI가 첫 두 줄만 읽어도 의존성 파악 완료 → 인간이 전체를 읽어야 했던 것과 대조적

Part 7. 재밌는 역설

결국 에이전트 퍼스트 구조가 더 좋은 거야?

여기서 재밌는 역설이 나와.

AI를 위해 설계한 구조가 인간 신입 개발자에게도 가장 친절한 구조라는 거야.

[AI 에이전트 vs 신입 개발자 — 놀라운 공통점] AI 에이전트: ✗ 프로젝트 경험 없음 (매번 처음) ✗ "선배한테 물어보기" 불가 ✗ 한 번에 전체를 볼 수 없음 ✗ 암묵적 규칙을 모름 신입 개발자 (1일차): ✗ 프로젝트 경험 없음 ✗ 선배한테 물어보기 부담스러움 ✗ IDE 열었는데 파일이 500개... ✗ 암묵적 규칙을 모름 둘 다 "명시적이고, 작고, 자급자족하는 모듈"이 필요!
그러면 왜 처음부터 이렇게 안 만들었어?

두 가지 이유가 있어:

1. 비용: MANIFEST 작성, 테스트 코드, 모듈 분리... 초기 투자가 크다

2. 필요 없었다: 팀이 5~10명이면 "물어보면 되니까". 암묵지가 잘 작동했어

근데 지금은 상황이 달라졌어. 코드를 수정하는 주체가 "사람"에서 "AI 에이전트"로 바뀌고 있거든.

그럼 기존 프로젝트는 어쩌라고?

현실적인 답: 기존 코드를 전부 다시 짜는 건 불가능해.

대신 "AI의 약점을 보완하는 레이어"를 씌울 수 있어:

[현실적 접근: 기존 코드 + AI 보조 레이어] 기존 프로젝트 (바꾸지 않음) │ ├── server_Game/ (기존 그대로) ├── server_GameDB/ (기존 그대로) │ └── _agent/ ← AI 보조 레이어 추가 ├── docs/ │ ├── GAME_CONTENT_INDEX.md (어디에 뭐가 있는지 지도) │ └── gniServer-reference.md (네트워크 엔진 설명서) ├── tools/ │ ├── analysis_trace.py (코드 흐름 추적 자동화) │ ├── safe_file_editor.py (인코딩 안전 편집) │ └── build_runner.py (빌드 자동화) └── knowledge/ ├── failure_memory/ (AI의 실수 기록 → 반복 방지) └── analysis_cache/ (분석 결과 캐시 → 재분석 방지) → 원본은 안 건드리고 → AI가 읽을 수 있는 "메타 레이어"를 추가 → 이것만으로도 AI 작업 효율 2~3배 향상

에이전트 퍼스트 ≠ 만능

오버 엔지니어링 주의 — MANIFEST, 스키마, 테스트를 "관리"하는 비용도 있음. 1인 프로젝트에 이걸 다 적용하면 오히려 느려질 수 있음

AI도 실수함 — 구조가 아무리 좋아도 AI가 100% 정확한 건 아님. 사람의 검증은 여전히 필수

실시간 로직 — 전투, 스킬 같은 초저지연 로직은 결국 최적화된 C++ 코드가 필요. 구조적 깔끔함과 성능은 때로 트레이드오프

핵심 정리

  • 인간은 암묵지로 보완한다 — 코드에 안 적혀 있어도 경험으로 알 수 있음
  • AI는 명시지만 읽는다 — 코드와 메타데이터에 적힌 것만 이해 가능
  • 기존 코드 = "소금 적당히" — 인간에겐 OK, AI에겐 해석 불가
  • 에이전트 퍼스트 = "소금 3g" — 모든 것이 명시적, 매번 동일하게 재현
  • 핵심 5원리 — MANIFEST(지도), 500줄(크기제한), 스키마(코드생성), 테스트(자동검증), 명시적 의존성
  • 역설 — AI를 위한 구조가 신입 개발자에게도 가장 친절한 구조
  • 기존 프로젝트 — 다시 짜지 않아도 "AI 보조 레이어"로 효율 향상 가능
