파티셔닝 vs 샤딩, 뭐가 다를까?

테이블을 나누는 것과 DB 서버를 나누는 것

Part 1. 파티셔닝은 뭐였지?

파티셔닝이 뭐야?

테이블 하나를 내부적으로 나눠서 저장하는 것.

[파티셔닝] DB 서버 1대 ├── 파티션 1 (2021년) ├── 파티션 2 (2022년) ├── 파티션 3 (2023년) └── 파티션 4 (2024년) → 한 서버 안에서 테이블만 쪼갬
그럼 샤딩은?

DB 서버 자체를 여러 대로 분산하는 것.

[샤딩] DB 서버 A ── 유저 1~100만 DB 서버 B ── 유저 100만~200만 DB 서버 C ── 유저 200만~300만 → 서버 자체를 여러 대로 나눔

Part 2. 핵심 차이

파티셔닝 샤딩
나누는 대상 테이블 DB 서버
서버 수 1대 여러 대
구현 난이도 쉬움 어려움
확장성 서버 1대 한계 무한 확장 가능

Part 3. MMORPG에서의 구조

우리 게임은 서버 11, 12, 13... 각각 DB 따로 있는데, 이것도 샤딩이야?

아니, 그건 "완전 격리" 구조야.

[완전 격리 - 대부분의 한국 MMORPG] 서버 11 ─ DB_11 ─ 유저들 서버 12 ─ DB_12 ─ 유저들 서버 13 ─ DB_13 ─ 유저들 → 서로 절대 안 만남. 완전히 다른 세계. → 구현 쉬움, 문제 격리됨
[샤딩] 게임 서버 ─┬─ DB 샤드 1 (유저 1~100만) ├─ DB 샤드 2 (유저 100만~200만) └─ DB 샤드 3 (유저 200만~300만) → 나눠 저장하지만, 서로 만날 수 있음 (거래, 파티 등) → "하나의 세계"인데 DB만 분산
11서버 유저랑 12서버 유저가 거래하려면?

"월드 트레이드 서버" 같은 공용 공간으로 이동해서 거래.

이건 "공유 존(Shared Zone)" 패턴이야. 샤딩이랑은 다른 접근.

Part 4. 샤딩이 진짜 필요한 상황

[이런 상황] - 유저 500만 명이 "하나의 월드"에서 플레이 - 한 DB로 감당 안 됨 - 근데 모든 유저가 서로 만날 수 있어야 함 → 샤딩 필요!

실제 사례:

• EVE Online - 전 세계 유저가 하나의 우주

• 알비온 온라인 - 싱글 샤드, 모든 유저 같은 세계

• 모바일 게임 - 유저 수천만 명, 샤딩 거의 필수

Part 5. 해시 샤딩 (ID % N)

유저 300만 명을 DB 3대에 나눠 저장해. "유저 150만 번"은 어느 DB로 가야 해?

유저 ID를 3으로 나눈 나머지!

유저 ID % 3 = 0 → DB 샤드 0 유저 ID % 3 = 1 → DB 샤드 1 유저 ID % 3 = 2 → DB 샤드 2 유저 150만 → 1500000 % 3 = 0 → DB 샤드 0으로!

이걸 샤드 키(Shard Key)라고 해. 유저 ID가 샤드 키인 거지.

장점은?

✅ 데이터가 균등하게 분배됨. 핫스팟 없음.

Part 6. 해시 샤딩의 문제: 리샤딩

유저가 많아져서 DB를 3대 → 4대로 늘리고 싶어

큰 문제 발생!

유저 150만 3: - 기존 (3대): 1500003 % 3 = 0 → DB 샤드 0 - 변경 (4대): 1500003 % 4 = 3 → DB 샤드 3 → 위치가 바뀜! 데이터 이동 필요!

리샤딩(Resharding) 문제:

• DB 추가/제거할 때마다 데이터 대이동 발생

• 서비스 중단하거나, 복잡한 마이그레이션 필요

Part 7. 범위 샤딩

리샤딩 문제 해결하려면?

나눗셈 말고 범위로 나누자.

[범위 샤딩] 유저 ID 1 ~ 100만 → DB 1 유저 ID 100만 ~ 200만 → DB 2 유저 ID 200만 ~ 300만 → DB 3
DB 추가하면?
유저 ID 1 ~ 100만 → DB 1 (그대로) 유저 ID 100만 ~ 200만 → DB 2 (그대로) 유저 ID 200만 ~ 300만 → DB 3 (그대로) 유저 ID 300만 ~ 400만 → DB 4 (새로 추가!) → 기존 데이터 안 건드려도 됨!
그럼 범위 샤딩이 더 좋네?

새로운 문제가 생겨.

유저 ID 1~100만 (2020년 가입) → DB 1 → 거의 접속 안 함 💤 유저 ID 100만~200만 (2022년) → DB 2 → 보통 유저 ID 200만~300만 (2024년) → DB 3 → 폭주 🔥 → "핫스팟" 문제 발생!

비용은 3대 내는데, 실제론 1대가 다 처리하는 꼴.

Part 8. 해시 vs 범위 비교

방식 리샤딩 부하 분산
해시 샤딩 (ID % N) ❌ 데이터 대이동 ✅ 균등
범위 샤딩 (ID 범위) ✅ 쉬움 ❌ 핫스팟
둘 다 단점이 있네. 실무에선 어떻게 해?

처음부터 DB를 넉넉하게 잡는다.

[현실적인 해결책] 해시 샤딩 + 처음부터 넉넉하게 - DB 3대 필요해도 10대로 시작 - 나중에 추가 안 해도 되게 설계 - 리샤딩 자체를 안 하는 게 목표 → 샤딩은 복잡하니까, 최대한 리샤딩 안 하게!

핵심 정리

  • 파티셔닝 = 테이블을 나눔 (서버 1대)
  • 샤딩 = DB 서버를 나눔 (서버 여러 대)
  • 완전 격리 = 서버별 DB 분리, 유저 간 상호작용 불가 (대부분의 한국 MMORPG)
  • 해시 샤딩 = ID % N, 균등 분배 but 리샤딩 어려움
  • 범위 샤딩 = ID 범위, 리샤딩 쉬움 but 핫스팟
  • 실무 해결책 = 처음부터 DB 넉넉하게 잡아서 리샤딩 피하기
