왜 내 클라우드 서버가 새벽에 혼자 재부팅됐을까?

네이버 클라우드 / AWS / Azure 다 똑같다 - 가상화, 하이퍼바이저, 메모리 오버커밋과 풍선 드라이버, 그리고 강제 리셋

Part 1. 클라우드에서 빌린 서버, 진짜 컴퓨터 한 대일까?

네이버 클라우드에서 서버 한 대 빌렸어. 이게 진짜 내 컴퓨터 한 대 맞아?

아니야. 거대한 물리 서버 한 대 위에 여러 손님의 가상 컴퓨터(VM)가 동시에 얹혀서 돌아가. 너는 그중 한 칸을 빌린 거야.

비유로 보면 - 물리 서버 = 원룸 건물 한 채, VM = 세입자. 너는 건물을 통째로 산 게 아니라 방 하나를 임대한 거지.

그럼 옆방에 누가 사는지 내가 알 수 있어?

몰라. 하이퍼바이저가 방끼리 벽을 쳐서 격리해주거든. 근데 전기/수도(=CPU/RAM) 배관은 건물이 공유야. 그래서 옆방이 물을 콸콸 쓰면 내 방 수압이 떨어질 수 있어. 이게 뒤에 나올 사건의 씨앗이야.

하이퍼바이저(hypervisor)가 정확히 뭐 하는 애야?

물리 서버 한 대의 CPU/RAM/디스크를 잘게 쪼개서 각 VM 에게 너는 8코어 32GB 처럼 나눠주는 관리 소프트웨어야. 건물 관리인이라고 보면 돼. 손님(게스트 OS)이 CPU 줘 하면 진짜 하드웨어에 연결해주고, 손님끼리 안 부딪치게 통제해.

중요한 건 - 이 관리인은 손님 VM 의 전원도 마음대로 내릴 수 있다는 거야. 이게 핵심이라 기억해 둬.

Part 2. 왜 남의 VM 이랑 같이 묶어서 파는 거야?

한 물리 서버에 한 손님씩만 주면 깔끔하잖아. 왜 굳이 섞어?

돈 때문이야. 물리 서버 한 대는 비싸. 한 손님이 통째로 쓰면 임대료가 살벌하게 비싸져. 여러 손님이 나눠 쓰면 한 명당 값이 1/n 로 떨어져. 클라우드가 싸고 유연한 근본 이유가 이거야.

근데 32GB 짜리 VM 10개면 320GB 인데, 호스트 RAM 이 256GB 밖에 없어도 팔 수 있어?

맞춰봐 - 못 팔 것 같지? 실제론 팔아. 이걸 오버커밋(overcommit) 이라고 해.

왜 되냐면, 대부분 VM 은 빌린 32GB 를 항상 다 쓰진 않거든. 평소엔 절반도 안 써. 그래서 주는 합계가 물리 용량보다 커도, 동시에 다 풀로 쓸 리는 없다에 베팅하고 초과 판매를 해.

비유: 항공사가 좌석 100석 비행기에 표를 105장 파는 오버부킹이랑 똑같아 - 노쇼가 있을 거라 믿고. 은행도 예금 전액을 금고에 안 두고 일부만 두잖아. 같은 원리야.

오버커밋 - 256GB 호스트에 320GB 를 팔 수 있는 이유 (슬라이더를 끝까지 밀어봐)
물리 RAM 사용물리 초과 = 회수 압박
오버커밋, 그럼 손님한텐 손해 아냐? 좋은 점만 있는 건 아닐 텐데.

공짜 장점은 없지. 3종 세트로 정리할게.

1) 비교 대상(지금 대안): 베어메탈(물리 서버 통째 임대) - 내 자원 확실히 다 내 것.

2) 나은 점: 오버커밋 환경은 가격이 몇 배 싸고, 몇 분 안에 생성/삭제 가능(탄력).

3) 잃는 것: 이웃 VM 의 영향을 받고(시끄러운 이웃), 호스트가 메모리를 도로 회수하려 들 수 있어. 바로 이 회수 압박이 우리 한양 사고를 낸 범인이야.

Part 3. 호스트가 메모리 부족하면? - 풍선(balloon) 드라이버

손님 10명이 갑자기 다 메모리를 끝까지 쓰면? 256인데 320 약속했잖아.

호스트가 다급해져. 물리 RAM 은 256뿐인데 수요가 320으로 몰리면 부족분을 어딘가에서 도로 가져와야 해. 그 도구가 바로 풍선이야.

풍선? 메모리랑 풍선이랑 무슨 상관이야?

VM 안에 호스트가 심어둔 작은 대리인(풍선 드라이버, XenTools 에 포함)이 있어. 호스트가 메모리 좀 돌려줘 하면 이 대리인이 VM 안에서 메모리를 의도적으로 점령해 버려(풍선을 부풀림). 그러면 게스트 OS 는 아 이 메모리는 쓸 수 없네 하고 손 떼고, 그만큼을 호스트가 회수해 다른 VM 에 줘.

비유: 뷔페(물리 RAM)에서 직원이 빈 접시를 거두며 이제 그만 가져가세요 하는 게 풍선이야. 자리(메모리)를 도로 확보하는 거지.

풍선 드라이버 - 호스트가 메모리를 도로 가져가는 법
우리 VM (32GB 할당)
게임이 쓰는 중풍선(호스트가 회수)빈 메모리
근데 그 대리인이 싫어 하고 버티면? (위 시뮬레이터에서 협조 거부 켜봐)

그게 바로 우리 사건의 핵심 용어 uncooperative_balloon_driver = true 야. 호스트가 메모리 돌려달라고 했는데 풍선 드라이버가 제때 응답을 안 한 상태야.

응답을 안 하면 호스트가 그냥 포기해?

아니. 호스트는 그 메모리가 다른 VM 을 살리는 데 필요해. 그래서 강하게 나와 - 심하면 그 VM 을 강제로 리셋해서 메모리를 통째 회수해 버려. 위 위젯에서 협조 거부 켜고 버튼 누르면 보이는 그 강제 리셋이 실제로 새벽에 우리 한양에 생긴 일이야.

협조를 안 한 게 아니라 못 한 걸 수도 있잖아?

정확해. 그게 핵심 반박 포인트야. 풍선 드라이버가 uncooperative 가 되는 경우는 두 가지야 - (1) 게스트가 진짜 메모리가 꽉 차서 내놓을 게 없거나(우리 책임 가능성), (2) 호스트가 너무 과하게/급하게 돌려달라고 해서 시간 안에 못 맞춘 경우(호스트 책임). 어느 쪽인지 가리는 게 다음 Part 의 핵심이야.

Part 4. 그래서 우리 서버가 새벽에 재부팅된 진짜 이유

우리 한양3 서버가 새벽 4시 28분에 혼자 죽었다 살아났어. 뭐가 일어난 거야?

순서대로면 - 같은 호스트의 다른 VM 들이 메모리를 폭증 -> 호스트가 우리한테 풍선 명령 -> 우리 풍선 드라이버가 제때 응답 못함(uncooperative) -> 호스트가 우리 VM 을 강제 리셋. 아래 타임라인을 단계별로 쌓아봐.

한양3 재부팅 사건 재구성 (2026-06-14) - 다음 단계로 쌓아봐
04:2x 같은 호스트의 다른 VM 들이 메모리를 폭증 -> 물리 256GB 가 빠듯해짐 (오버커밋 상황)
-> 호스트가 우리 VM 에 "메모리 좀 돌려줘" 풍선(balloon) 명령 전송
! 우리 풍선 드라이버가 제때 응답 못 함 -> uncooperative_balloon_driver = true
04:28:09 호스트가 VM 강제 리셋 -> Kernel-Power 41 / Bugcheck 없음 (전원 단절형, 블루스크린 아님)
04:30:05 자동 복구(auto-recovery) 부팅 완료 - 다운타임 약 1분 50초
재부팅됐으면 그냥 우리 윈도우(OS)가 죽은 거 아니야?

이게 가장 흔한 오해야. 아니야. 증거가 명확해 - 우리가 뜬 이벤트 로그에 Kernel-Power 41 과 예기치 않은 종료(6008)가 찍혔고, 결정적으로 Bugcheck(정지 코드)가 비어 있었어. 윈도우가 스스로 충돌(블루스크린)했다면 정지 코드와 메모리 덤프가 남아. 비어 있다는 건 덤프 남길 틈도 없이 전원이 끊긴 거야.

근데 왜 전원이 끊겼다가 호스트 탓으로 연결돼?

간단해. 게스트 OS 는 자기 자신의 전원을 못 끊어. 가상 머신이라 콘센트가 없거든. 그리고 메모리 부족으로 윈도우가 죽으면 버벅거리거나 프로세스를 죽일 뿐, 박스 전원을 내리진 않아. 그런데 우리는 전원이 끊긴 시그니처였지. 그걸 할 수 있는 건 한 단계 아래 - 호스트(하이퍼바이저)뿐이야. 그래서 이 재부팅은 호스트가 한 게 확실해.

Part 5. 그래서 누구 탓이야? - 책임 분해

네이버가 VM 내부 탓이래. 맞아?

절반만 맞아. 풍선 드라이버가 uncooperative 였던 게 트리거인 건 맞지만, 실제 강제 리셋은 호스트가 했고, 애초에 풍선을 부풀린 건 호스트의 오버커밋 상황이거든. 둘 다 책임이 있어.

구분 게스트(우리) 책임일 수 있는 것 호스트(NCP) 책임일 수 있는 것
풍선이 부푼 이유 게임 프로세스 메모리 누수/스파이크 호스트 메모리 오버커밋 압박
uncooperative 원인 XenTools 구버전/멈춤 회수 목표가 과하거나 급함
강제 리셋 결정 - (게스트는 못 함) 호스트가 리셋을 선택(마이그레이션 대신)
그래서 우리가 확인해본 결과는?

둘 다 게스트 무혐의 쪽으로 나왔어. 재부팅 직전 30분간 (1) 윈도우 메모리 고갈 이벤트(Event 2004)가 0건 - 게스트는 메모리가 마른 적 없음. (2) XenTools 서비스(xenagent/xenbus_monitor/XenSvc)가 전부 Running - 툴도 정상. 즉 네이버가 지목한 두 용의자가 게스트 쪽엔 안 보여. 그러면 무게가 호스트 오버커밋/회수목표 쪽으로 기울어.

(생각해보기) 그럼 베어메탈(전용 물리 서버)를 쓰면 이 문제는 사라져?

정답은 안 줄게. 직접 생각해봐 - 오버커밋도 이웃도 없으면 풍선 회수 압박은 사라지겠지. 그럼 그 대가로 무엇을 포기해야 할까? (힌트: 가격과 탄력성)

Part 6. AWS / Azure 도 똑같아? - 모든 클라우드의 공통 원리

이건 네이버 클라우드만 그런 거야? AWS, Azure 는 다르지 않아?

이름만 다를 뿐 원리는 똑같아. 전부 하이퍼바이저 위에 VM 을 올리고, 오버커밋하고, 메모리를 동적으로 조절하고, 호스트 이상 시 VM 을 재시작(auto-recovery)해.

라이브 마이그레이션은 뭐야? 왜 그게 중요해?

실행 중인 VM 을 전원 안 끄고 다른 물리 호스트로 통째 옮기는 기술이야. 호스트가 바빠도 손님은 거의 못 느끼지. 그래서 우리가 NCP 한테 왜 마이그레이션 대신 강제 리셋했냐 고 따질 수 있는 거야. 덜 파괴적인 선택지가 있었으니까.

그럼 실무에서 우리가 뭘 주의해야 해?

세 가지. 1) 게임서버처럼 메모리를 상시 꽉 쓰는 애는 풍선 회수 1순위 타깃 - 중요 서버는 전용 호스트(Dedicated)를 검토. 2) 내 VM 메모리 추이를 직접 모니터링해두면 우리 탓이냐 너희 탓이냐 를 바로 가린다. 3) 재부팅 같은 사건은 호스트 이벤트 로그를 운영사에 당당히 요구할 것 - 그들이 내부 탓이라고 하면 Kernel-Power 41 + Bugcheck 없음 과 자기네 SYSTEM 재부팅 로그를 근거로 되물어라.

게임 서버가 특히 위험한 이유

게임 서버는 접속자/맵 데이터를 메모리에 상주시켜 올려둔다 -> 호스트 입장에선 풍선으로 회수하기 어려운 VM -> uncooperative 플래그 타깃 1순위.

강제 리셋은 전원 단절과 같아서, 마지막 자동저장(보통 60초 주기) 이후 미저장분은 날아갈 수 있다 -> 하드 리셋 후엔 데이터 유실 점검 필수.

오버커밋 환경에선 우리가 잘못해서가 아니라도 언제든 이웃/호스트 사정으로 재부팅될 수 있다 -> 단일 VM 에 단일 장애점(SPOF)을 두지 말 것.

핵심 정리

  • 클라우드 서버 = 물리 서버 한 대 위 하이퍼바이저가 쪼개 나눠준 VM 한 칸 - 나만의 컴퓨터가 아니다.
  • 오버커밋: 물리 256GB 에 320GB 를 판다 - 평소 다 안 쓰니까. 대신 메모리 회수 압박이 생긴다.
  • 풍선(balloon) 드라이버: 호스트가 VM 안에서 메모리를 점령해 도로 회수하는 장치.
  • uncooperative_balloon_driver=true = 호스트 회수 요청에 VM 풍선이 응답 못함 -> 호스트가 강제 리셋.
  • Kernel-Power 41 + Bugcheck 없음 = 블루스크린이 아니라 전원 단절형 = 호스트가 강제 리셋한 증거.
  • AWS / Azure / NCP 모두 같은 원리 - 이름과 디테일만 다르다. 중요 서버는 전용 호스트 + 모니터링 + SPOF 회피.
