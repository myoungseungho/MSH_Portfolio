서버 60fps면 렉 없는 거 아니야?

클라 프레임, 서버 틱레이트, 네트워크 지연 — 진짜 '렉 없는 1프레임'의 조건

Part 1. 서버 60fps면 렉 없는 거 아니야?

클라가 60fps잖아. 서버도 60fps 이상이면 이론적으로 렉 없는 거 아니야?

나도 처음에 그렇게 생각했어. 클라가 1프레임(16.67ms) 안에 화면을 그리니까, 서버도 16.67ms 안에 처리하면 매 프레임마다 최신 데이터가 있겠지?

근데 하나 빠진 게 있어. 서버가 처리를 끝내도, 그 결과가 클라한테 도착하는 데 시간이 걸려.

서울에서 부산까지 택배 보내는 거랑 같아. 공장(서버)이 아무리 빨리 만들어도, 택배(네트워크)가 이동하는 시간은 줄일 수 없어.

네트워크 시간이 얼마나 걸리는데?

유저가 키를 누르고 결과를 보기까지, 이런 여정을 거쳐야 해:

🔄 유저 입력 → 화면 반영까지의 전체 여정 [1] 유저가 키를 누름 ↓ [2] 패킷이 서버로 날아감 ── 15ms (RTT의 절반) ↓ [3] 서버 틱 대기 ── 최대 16.67ms (60틱 기준) ↓ [4] 서버가 처리함 ── ~1ms ↓ [5] 결과 패킷이 클라로 날아감 ── 15ms (RTT의 절반) ↓ [6] 클라 프레임 대기 ── 최대 16.67ms ↓ [7] 화면에 반영됨 총 지연 = 15 + 16.67 + 1 + 15 + 16.67 = 약 64ms (최악) = 15 + 8 + 1 + 15 + 8 = 약 47ms (평균)
47ms면 3프레임이잖아. 서버 60fps인데도?

그래. 서버가 60fps여도, 유저는 최소 3프레임 전 세상을 보고 있어.

서버 연산 시간은 이 중에 고작 1ms야. 나머지 46ms는 전부 네트워크 왕복(30ms)과 틱/프레임 대기 시간이야. 서버를 아무리 빠르게 해도 이 46ms는 못 줄여.

Part 2. 숫자로 따져보자 — 렉 없는 조건

그럼 진짜로 '렉 없는 1프레임' 하려면 뭐가 필요해?

전체 파이프라인이 16.67ms(1프레임) 안에 끝나야 해.

역산해보자:

- 네트워크 왕복(RTT) = 최대 10ms

- 서버 틱 대기 = 최대 3ms (서버 300틱 이상)

- 서버 처리 = 최대 1ms

- 클라 프레임 대기 = 최대 2ms

합계 = 16ms. 겨우 1프레임.

RTT 10ms 이하는 같은 건물 안 LAN이나 가능해. 인터넷에서는 불가능해.

인터넷에서는 RTT가 보통 얼마야?

같은 도시 내 서버면 10~30ms, 서울↔부산이면 30~50ms, 한국↔일본이면 50~80ms, 한국↔미국이면 150~200ms.

RTT 30ms만 돼도, 네트워크 왕복만으로 이미 2프레임을 써버려. 서버가 아무리 빨라도.

조건 총 지연 프레임 수 (60fps) 체감
LAN (RTT 5ms, 서버 300틱) ~12ms 1프레임 이내 렉 없음
같은 도시 (RTT 20ms, 서버 128틱) ~32ms 약 2프레임 거의 안 느낌
일반 인터넷 (RTT 40ms, 서버 60틱) ~57ms 약 3.5프레임 민감하면 느낌
원거리 (RTT 80ms, 서버 60틱) ~97ms 약 6프레임 확실히 느림
해외 (RTT 150ms, 서버 60틱) ~167ms 약 10프레임 0.17초 딜레이
사람이 렉을 느끼는 기준이 있어?

있어. 사람의 인지 기준:

- 50ms 이내: 즉각 반응으로 느낌 (FPS 게임 기준)

- 100ms 이내: 대부분 못 느낌 (MMO 기준)

- 200ms 이상: 확실히 느림

- 500ms 이상: "렉이다" 확신

MMO에서 100ms면 6프레임인데 — RTT 60ms 이내면 충분하다는 뜻이야.

Part 3. 서버를 2배 빠르게 하면?

서버를 60틱에서 128틱으로 올리면 얼마나 나아져?

계산해볼까.

RTT 40ms 환경에서:

- 60틱 서버: 20 + 8.3 + 1 + 20 + 8.3 = 57.6ms

- 128틱 서버: 20 + 3.9 + 1 + 20 + 8.3 = 53.2ms

4.4ms 차이. 0.26프레임. 거의 못 느껴.

서버 틱을 2배로 올렸는데, 전체 지연에서 줄어든 건 4ms뿐이야. 왜? 네트워크 왕복 40ms가 그대로니까.

📊 서버 틱레이트 올렸을 때 효과 전체 지연 57.6ms의 구성 (60틱, RTT 40ms): [네트워크 왕복] ████████████████████████ 40ms (69%) [서버 틱 대기] █████ 8.3ms (15%) [클라 프레임대기] █████ 8.3ms (14%) [서버 처리] ▌ 1ms (2%) → 서버가 건드릴 수 있는 건 "서버 틱 대기" 8.3ms뿐 → 나머지 49.3ms는 서버가 아무리 빨라도 못 줄여
그럼 서버 빠르게 하는 건 의미 없어?

의미 없진 않아. 근데 투자 대비 효과가 적어.

서버 틱레이트를 2배로 올리면 CPU 비용도 거의 2배가 돼. 그 비용으로 서버를 유저 가까운 곳(엣지 서버)에 하나 더 두면 RTT 자체를 20ms 줄일 수 있어. 그게 훨씬 효과적이야.

실무에서 유저가 '렉'을 호소하면 서버 CPU부터 보잖아? 근데 CPU 10%야. 서버는 멀쩡한데 유저는 렉을 느껴. 대부분 원인이 네트워크야.

Part 4. 그래서 게임들은 어떻게 하는데?

네트워크를 못 줄이면 어떻게 해?

클라이언트가 속여.

유저가 W키를 눌러서 앞으로 가. 서버 응답이 올 때까지 47ms 기다리면? 유저는 "렉"이라고 느껴.

그래서 클라이언트 예측(Client-side Prediction)을 써. 서버 응답 안 기다리고, "나는 앞으로 갈 거야"를 먼저 화면에 반영해버려. 서버 응답이 나중에 오면 그때 보정해.

🎮 클라이언트 예측 (Client-side Prediction) 예측 없을 때: [W키 누름] ──47ms 대기── [서버 응답] → 캐릭터 이동 유저: "왜 이렇게 느려??" 예측 있을 때: [W키 누름] → 바로 이동 시작 (예측) ··47ms 후·· [서버 응답] → 위치 보정 유저: "쾌적하다!" 만약 예측이 틀렸으면? (벽에 부딪힌 경우) → 캐릭터가 순간 "텔레포트" 됨 (러버밴딩)
다른 사람의 움직임은 어떻게 해?

내 캐릭터는 예측으로 속일 수 있지만, 상대방 캐릭터는 상대가 뭘 할지 모르니까 예측이 안 돼.

그래서 보간(Interpolation)을 써. 서버에서 온 패킷 2개 사이를 부드럽게 이어서 그리는 거야. 실제로는 과거 데이터를 보고 있는 건데, 부드럽게 움직이니까 자연스러워 보여.

대신 대가가 있어. 상대방이 실제 있는 위치보다 항상 약간 과거의 위치를 보고 있다는 거야.

FPS에서 '분명 먼저 쐈는데 내가 죽었다'가 이것 때문이야?

맞아. 내 화면에서 상대가 A 위치에 있어서 쐈는데, 실제 서버에서 상대는 이미 B 위치로 갔어. 내가 본 건 50ms 전의 모습이었거든.

그래서 지연 보상(Lag Compensation)이 있어. 서버가 "이 유저는 50ms 전 세상을 보고 있었겠구나" 하고, 과거 시점에서 히트 판정을 해줘. 이래야 공평해.

Part 5. 장르별 기준 — 몇 틱이면 충분해?

서버가 클라보다 빠르면 더 좋은 거 아니야? 서버 120틱, 클라 60fps면?

생각해봐. 서버가 1초에 120번 결과를 보내도, 클라는 60번밖에 못 그려. 나머지 60개는 버려지거나 평균 내야 해.

서버 틱이 클라 fps를 넘어가면, 넘어간 만큼은 거의 낭비야. 그래서 서버 틱 = 클라 fps로 맞추거나, 오히려 더 낮게 잡는 게임이 대부분이야.

게임 장르 서버 틱레이트 클라 fps 왜 이 값?
CS2 FPS 64틱 (서브틱) 300+ 총알 판정 정밀도. 서브틱으로 64틱 안에서 보간
Valorant FPS 128틱 144+ 경쟁 FPS의 최고 기준
Overwatch 2 FPS 63틱 60~144 론칭 때 21→63으로 상향
포트나이트 배틀로얄 30틱 60~120 100명 동시, 틱 높이면 서버비 폭발
LoL AOS 30틱 60~240 스킬 판정에 30이면 충분
WoW MMO 약 20틱 60+ 이동/전투에 20이면 충분
조선협객전 MMO 가변 (싱글루프) 60 메시지 큐 방식, 틱 개념 없음
FPS는 128틱인데 MMO는 왜 20틱이면 충분해?

FPS에서는 0.01초 차이로 승패가 갈려. 총알이 빗나가냐 맞냐의 문제야.

MMO에서는? 칼 휘두르는 애니메이션이 0.5초야. 20틱이면 0.05초 간격인데, 0.5초 애니메이션 안에서 0.05초 차이를 느낄 수 있어? 못 느껴.

필요한 정밀도가 장르마다 다른 거야. 비용 대비 효과가 안 나오면 틱을 올릴 이유가 없어.

정리: 렉의 진짜 원인

서버 틱레이트는 전체 지연의 15%에 불과해. 나머지 85%는 네트워크야.

서버가 '빠르게 처리'하는 것과 유저가 '빠르게 느끼는' 것은 완전히 다른 문제야.

렉 없는 1프레임(16.67ms)은 LAN이 아니면 물리적으로 불가능해. 인터넷에서는 3프레임 이상 지연이 정상이야.

핵심 정리: 서버 틱레이트 vs 클라 프레임레이트

  • 서버 60fps ≠ 렉 없음. 전체 파이프라인(네트워크 + 서버 + 클라)이 총 지연을 결정해
  • 일반 인터넷(RTT 40ms)에서 서버 60틱이면 총 지연 약 57ms = 3.5프레임
  • 서버 60→128틱으로 올려도 4ms(0.26프레임)만 개선. 네트워크가 병목
  • 클라이언트 예측 + 보간으로 '속여서' 체감 지연을 줄이는 게 핵심
  • FPS: 64~128틱 (정밀 판정), MMO: 20~30틱 (충분), 배틀로얄: 30틱 (서버비 제약)
  • 인지 기준: 50ms 이내 = FPS 합격, 100ms 이내 = MMO 합격, 200ms 이상 = 렉

생각해볼 질문

우리 서버는 고정 틱이 아니라 '메시지 큐' 방식이야. 이게 틱 기반보다 유리한 점이 있을까?

서버를 서울에서 부산 유저 근처로 옮기면 RTT가 20ms 줄어. 서버 틱을 2배로 올리는 것과 뭐가 더 효과적일까?

모바일 게임은 네트워크 상태가 더 불안정해. 틱레이트를 어떻게 설계해야 할까?
