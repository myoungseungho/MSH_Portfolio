# MSH Portfolio 문서 작성 에이전트 지침

> 이 파일은 AI 에이전트가 일관된 스타일로 문서를 생성하기 위한 필수 지침입니다.

---

## 1. 핵심 원칙 (반드시 준수)

### 스캐폴딩 방식
- **쉬운 것 → 어려운 것** 순서로 설명
- 한 번에 하나의 개념만 도입
- 새 개념 도입 시 반드시 이전 개념과 연결

### 인지적 델타 최소화
- 독자가 이미 아는 것에서 출발
- 모르는 개념은 비유로 먼저 설명
- 전문 용어는 처음 등장할 때 반드시 설명

### Q&A 대화형
- 모든 섹션은 **질문으로 시작**
- 독자가 궁금해할 만한 질문 → 답변 구조
- 질문은 구어체로 자연스럽게

### 코드보다 개념
- 원리 이해가 먼저, 코드는 보조
- 코드 없이도 개념이 전달되어야 함
- 코드가 필요하면 주석을 풍부하게

## 2. 문서 구조

```
<header>
  - 후킹되는 제목
  - 부제목 (다루는 개념 요약)
</header>

<Part 1~N>
  각 Part는 하나의 핵심 질문을 다룸
  - Q&A 대화
  - 다이어그램
  - 코드 (필요시)
  - 비교 표 (필요시)
</Part>

<실전 가이드>
  실무에서 어떻게 적용하는지

<주의사항>
  warning-box로 함정 안내

<핵심 정리>
  summary-box로 5줄 내외 정리
</nav>
```

## 3. 컴포넌트 사용법

### 질문 (.q)
```html
<div class="q">왜 서버 3대가 필요해?</div>
```
- 독자의 호기심을 자극하는 질문
- "왜", "어떻게", "뭐가 다른데" 형태

### 답변 (.a)
```html
<div class="a">
    <p>1대면 그 서버 죽으면 끝이야.</p>
    <p>3대면 1대가 죽어도 <span class="highlight">과반수</span>가 살아있어.</p>
</div>
```
- 짧고 명확한 설명
- 한 문단에 한 가지 내용만

### 다이어그램 (.diagram-box)
```
📦 리더 선출 과정:

1단계: 후보 선언
├─ Server A: "나 리더 할래!" (투표 요청)
├─ Server B: "ㅇㅋ 찬성" ✓
└─ Server C: "ㅇㅋ 찬성" ✓

2단계: 과반수 확보
└─ A가 2표 받음 (3대 중 2대 = 과반수)
└─ A가 리더 확정! 👑
```
- ASCII 아트로 시각화
- 이모지 적극 활용
- 단계별로 명확하게

### 비교 표 (.compare-table)
```html
<table class="compare-table">
    <tr>
        <th>항목</th>
        <th>단일 서버</th>
        <th>3대 클러스터</th>
    </tr>
    <tr>
        <td>장애 허용</td>
        <td class="bad">0대</td>
        <td class="good">1대</td>
    </tr>
</table>
```
- `.good` = 녹색 배경 (좋은 것)
- `.bad` = 빨간 배경 (나쁜 것)
- `.warn` = 주황 배경 (주의)

### 강조 표시
- `<span class="highlight">핵심 키워드</span>` - 파란색
- `<span class="key-point">중요 포인트</span>` - 녹색
- `<span class="warning">주의사항</span>` - 빨간색

## 4. 톤앤매너

### 반말 사용
- ✅ "~해", "~야", "~거든", "~잖아"
- ❌ "~합니다", "~입니다"

### 친근한 설명
- ✅ "서버 하나 죽으면 어떡해?"
- ❌ "단일 장애점(SPOF)이 발생합니다"

### 비유 활용
- ✅ "반장 선거처럼 투표해서 리더 뽑아"
- ❌ "리더 선출 알고리즘이 실행됩니다"

### 게임 서버 맥락
- 항상 게임 서버 상황에 맞춰 설명
- 예: "길드 마스터 DB가 날아가면..."
- 예: "월드보스 HP를 3개 서버가 동시에..."

## 5. 제목 작성법

### 후킹형 제목
- ✅ "서버 3대가 '누가 리더야?'를 정하는 법"
- ✅ "DB 죽었는데 게임은 왜 돌아가?"
- ❌ "Raft 합의 알고리즘 개요"
- ❌ "Circuit Breaker 패턴"

### 질문형
- "왜 ~할까?"
- "어떻게 ~하지?"
- "~하면 어떻게 돼?"

### 놀라움 유발
- "~인데 ~한다고?"
- "~없이 ~되는 이유"

---

## 6. Part 분할 기준

### 각 Part는 하나의 핵심 질문
```
Part 1. 왜 서버 1대가 아니라 3대야?
Part 2. 리더는 어떻게 뽑아?
Part 3. 리더가 죽으면?
Part 4. 실제로 어디서 써?
```

### Part당 Q&A 2~4개
- 너무 많으면 분할
- 너무 적으면 합치기

### 다이어그램은 Part당 1~2개
- 핵심 흐름 시각화
- 복잡하면 단계별로 분리

## 7. 체크리스트 (문서 완성 전 확인)

### 구조
- [ ] Part 1이 가장 기본적인 "왜?"를 다루는가?
- [ ] 각 Part가 이전 Part를 전제하는가?
- [ ] 마지막에 실전 가이드가 있는가?
- [ ] 핵심 정리(summary-box)가 있는가?

### 내용
- [ ] 전문 용어 첫 등장 시 설명했는가?
- [ ] 게임 서버 맥락으로 예시를 들었는가?
- [ ] 다이어그램으로 핵심 흐름을 보여줬는가?
- [ ] 비교 표로 차이점을 명확히 했는가?

### 톤
- [ ] 반말로 작성했는가?
- [ ] 질문형으로 호기심을 유발했는가?
- [ ] 비유를 충분히 활용했는가?

### 스타일
- [ ] highlight, key-point, warning이 적절히 사용됐는가?
- [ ] 코드에 주석이 충분한가?
- [ ] 다이어그램에 이모지가 있는가?
